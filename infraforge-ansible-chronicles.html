🧠 WHAT IS ANSIBLE?
⚡ THE CORE IDEA

Ansible is an agentless IT automation tool that lets you describe what your infrastructure should look like — and then makes it so. You write simple YAML files called Playbooks, and Ansible connects to your servers over SSH and executes the instructions.

Agentless means: nothing is installed on the target servers. Ansible runs from a single Control Node (your laptop or CI server). It uses SSH — which every Linux server already has. That's it.

Idempotent means: you can run the same playbook 100 times and the result is always the same. If nginx is already installed, Ansible won't try to install it again. This is what makes Ansible safe to run repeatedly.

🔄 HOW ANSIBLE WORKS — STEP BY STEP
🔁 EXECUTION FLOW

1. You run: ansible-playbook site.yml -i inventory.ini

2. Ansible reads the inventory file to know which servers to target.

3. Ansible reads the playbook to know what tasks to execute.

4. Ansible connects to each server over SSH (no agent, no daemon — just SSH).

5. Ansible temporarily copies a small Python script to the server, runs it, captures the result, then deletes it.

6. Ansible reports back: OK (already correct), CHANGED (made a change), FAILED (error), SKIPPED (condition not met).

💼 INTERVIEW Q&A — CHAPTER 1
What makes Ansible different from Puppet or Chef?
Ansible is agentless — it uses SSH only, so nothing is installed on managed nodes. Puppet and Chef require agents (daemons) running on every server, which adds overhead and security surface. Ansible also uses simple YAML (Playbooks) vs DSLs. The tradeoff: Puppet/Chef can be faster at scale due to pull-based model, but Ansible wins on simplicity and zero-setup managed nodes.
What is idempotency in Ansible and why does it matter?
Idempotency means running the same playbook multiple times produces the same result. If nginx is installed, Ansible won't reinstall it — it returns "OK" not "CHANGED." This is critical in production: you can re-run a playbook as a drift correction tool without fear of breaking things that are already correct.
What is a Control Node vs a Managed Node?
Control Node: the machine where Ansible is installed and playbooks are run from (your laptop, CI server). Managed Node: the target servers being configured. Ansible only needs to be installed on the Control Node. Managed Nodes only need Python and SSH access.

📋 WHAT IS INVENTORY?
🗂️ INVENTORY EXPLAINED

Inventory is simply a list of servers that Ansible knows about. You can organize them into groups (web, db, cache), and groups can be nested. Ansible supports two formats: INI format (simpler) and YAML format (more flexible). For large real-world projects, YAML inventory is preferred.

💼 INTERVIEW Q&A — CHAPTER 2
What is the difference between static and dynamic inventory?
Static inventory is a fixed file (INI/YAML) you maintain manually. Dynamic inventory is a script or plugin that queries an external source (AWS EC2, GCP, Azure, Kubernetes) at runtime to get the current list of servers. In production at cloud-native companies, dynamic inventory is preferred because servers scale up/down automatically. For AWS, the aws_ec2 plugin queries EC2 API and builds inventory from tags.
What is ansible_host and when do you need it?
ansible_host is a connection variable that specifies the actual IP or DNS name to SSH into. You need it when the alias name (e.g., "web-01") doesn't resolve to a real DNS name. In environments without DNS, all servers are referenced by IP, so ansible_host is always required.
How does group hierarchy work in Ansible inventory?
Ansible has a built-in group called "all" containing every host. You create custom groups (webservers, dbservers) and can nest them using :children. Variables defined at a child group level override those at the parent level. This lets you set environment-wide defaults at the "production" group level and override them per sub-group.

📋 PLAYBOOK STRUCTURE
📄 ANATOMY OF A PLAYBOOK

A Playbook is a YAML file containing one or more Plays. A Play targets a group of servers and defines a list of Tasks to run on them. A Task calls a Module (built-in action). Think of it as: Playbook → Plays → Tasks → Modules

 playbooks/deploy-webserver.yml
---
# InfraForge — Web Server Setup Playbook
# Deploy nginx + FluxServe app on all web servers

- name: Setup and Deploy FluxServe Web Servers   # Play name (shown in output)
  hosts: webservers                               # target group from inventory
  become: yes                                      # use sudo for all tasks
  gather_facts: yes                               # collect server info first

  vars:                                            # play-level variables
    app_version: "1.0.0"
    app_dir: "/opt/fluxserve"
    nginx_config_src: "../templates/nginx.conf.j2"

  tasks:                                           # list of tasks to run

    - name: Update apt package cache              # task 1: refresh package list
      apt:                                         # apt module (Debian/Ubuntu)
        update_cache: yes                         # run "apt update"
        cache_valid_time: 3600                    # skip if cache < 1hr old

    - name: Install nginx web server
      apt:
        name: nginx                               # package name
        state: present                            # ensure it IS installed

    - name: Install required Python packages
      apt:
        name:                                      # install multiple packages
          - python3
          - python3-pip
          - python3-venv
        state: present

    - name: Create application directory
      file:                                        # file module: manage files/dirs
        path: "{{ app_dir }}"                     # variable substitution
        state: directory                          # ensure it's a directory
        owner: www-data                          # nginx user owns this dir
        mode: "0755"                              # permissions (rwxr-xr-x)

    - name: Copy application files to server
      copy:                                        # copy module
        src: "../app/"                            # source on control node
        dest: "{{ app_dir }}/"                    # destination on managed node
        owner: www-data
        mode: preserve                            # keep original file permissions

    - name: Deploy nginx configuration
      template:                                    # template module (Jinja2)
        src: "{{ nginx_config_src }}"
        dest: "/etc/nginx/sites-available/fluxserve"
        owner: root
        mode: "0644"

    - name: Enable nginx site (symlink)
      file:
        src: "/etc/nginx/sites-available/fluxserve"
        dest: "/etc/nginx/sites-enabled/fluxserve"
        state: link                              # create a symlink

    - name: Ensure nginx is started and enabled on boot
      service:                                     # service module
        name: nginx
        state: started                            # make sure it's running NOW
        enabled: yes                             # auto-start on server reboot

💼 INTERVIEW Q&A — CHAPTER 3
What is the difference between command and shell modules?
Both run commands on remote hosts. The "command" module runs the command directly (no shell interpretation) — it's safer and preferred. The "shell" module runs via /bin/sh, so it supports pipes (|), redirects (>), and environment variables. Use command for simple commands, shell only when you need shell features. The shell module is slightly less secure because it can be affected by shell injection if variables are unsanitized.
How do you run a playbook in check mode and why?
ansible-playbook site.yml --check runs the playbook in "dry-run" mode — it tells you what WOULD change but makes no actual changes. Essential before running in production to validate logic. Combine with --diff to also show the specific content changes in files.

🔍 ANSIBLE FACTS — SERVER AUTO-Discovery
🤖 WHAT ARE FACTS?

When gather_facts: yes is set (which is the default), Ansible automatically collects data about each server before running any tasks. These are called Facts — structured data about the host.

Facts are accessible as variables: ansible_facts['os_family'] or shorthand ansible_os_family

 playbooks/facts-demo.yml
---
- name: Demo - Using Facts in Tasks
  hosts: all
  gather_facts: yes

  tasks:
    - name: Show OS family
      debug:
        msg: "Host {{ inventory_hostname }} runs {{ ansible_os_family }}"

    - name: Show available memory
      debug:
        msg: "Memory: {{ ansible_memtotal_mb }} MB total, {{ ansible_memfree_mb }} MB free"

    - name: Set a custom fact based on environment
      set_fact:
        is_high_memory: "{{ ansible_memtotal_mb > 4096 }}"

    - name: Register command output as a variable
      command: cat /etc/hostname
      register: hostname_result             # capture output into variable

    - name: Print registered result
      debug:
        msg: "Hostname is: {{ hostname_result.stdout }}"
                                              # .stdout = standard output of command
                                              # .rc = return code (0=success)
                                              # .stderr = error output

CHAPTER 05 · CONDITIONALS & LOOPS
Smart Automation: "Do This ONLY IF..."
InfraForge has a mix of Ubuntu 20.04 and 22.04 servers. The package names are different on each. Plus you need to create 10 users, 5 directories, and install 8 packages — writing 23 separate tasks would be insane. You need when (conditionals) to run tasks only when conditions are met, and loop to repeat tasks over lists. Together they make automation intelligent.
 playbooks/smart-setup.yml
---
- name: InfraForge — Smart Server Setup
  hosts: all
  become: yes

  vars:
    app_users:                           # a list variable
      - deploy
      - monitor
      - backup

    required_packages:
      - curl
      - vim
      - git
      - htop
      - unzip

    log_dirs:
      - path: "/var/log/fluxserve"
        mode: "0755"
      - path: "/var/log/fluxserve/access"
        mode: "0755"
      - path: "/var/log/fluxserve/error"
        mode: "0750"

  tasks:

    # ── CONDITIONALS ─────────────────────────────────────

    - name: Install packages on Debian/Ubuntu only
      apt:
        name: "{{ item }}"
        state: present
      loop: "{{ required_packages }}"
      when: ansible_os_family == "Debian"  # ONLY if Ubuntu/Debian

    - name: Install packages on RedHat/CentOS only
      yum:
        name: "{{ item }}"
        state: present
      loop: "{{ required_packages }}"
      when: ansible_os_family == "RedHat"  # ONLY if RHEL/CentOS

    - name: Only run in production environment
      debug:
        msg: "PRODUCTION MODE - extra hardening applied"
      when: env == "production"            # check variable value

    - name: Run only on high-memory servers
      debug:
        msg: "High memory node - enabling extra cache"
      when: ansible_memtotal_mb >= 8192   # compare numbers

    - name: Multiple conditions (AND)
      debug:
        msg: "Ubuntu 22.04 production server"
      when:
        - ansible_distribution == "Ubuntu"  # condition 1
        - ansible_distribution_version == "22.04"  # condition 2 (AND)
        - env == "production"               # condition 3 (AND)

    # ── LOOPS ────────────────────────────────────────────

    - name: Create application service users
      user:
        name: "{{ item }}"                 # {{ item }} = current loop element
        shell: "/bin/bash"
        create_home: yes
        state: present
      loop: "{{ app_users }}"              # iterate over the list

    - name: Create log directories with custom permissions
      file:
        path: "{{ item.path }}"            # item.path = dict key access
        state: directory
        mode: "{{ item.mode }}"
        owner: www-data
      loop: "{{ log_dirs }}"               # loop over list of dicts

    - name: Loop with index (loop_var)
      debug:
        msg: "Server {{ my_idx + 1 }}: {{ item }}"
      loop: "{{ app_users }}"
      loop_control:
        loop_var: item
        index_var: my_idx               # loop index starts at 0
        label: "{{ item }}"              # what to show in output

💼 INTERVIEW Q&A — CHAPTER 5
How do you write an OR condition in Ansible when:?
Use Python's "or" keyword in a single string: when: "env == 'production' or env == 'staging'". For AND, use the YAML list form (multiple dashes) OR the "and" keyword: when: "env == 'production' and ansible_memtotal_mb > 4096".
What is the difference between loop and with_items?
They both iterate over a list, but loop: is the modern recommended approach (Ansible 2.5+). with_items: is the legacy syntax and is deprecated. with_items: also flattens single-level nested lists automatically, which loop: does not. For new playbooks always use loop:.
CHAPTER 06 · HANDLERS & TAGS
Restart nginx ONLY When Config Changes
You push a new nginx.conf. Three tasks check it. Ansible runs them. Two say "ok" (already up to date). One says "changed" (config updated). Only THEN should nginx restart — not every time. Restarting nginx on every single playbook run (even when nothing changed) is dangerous in production — it causes brief downtime. Handlers solve this: restart nginx only when something actually changed.
 playbooks/handlers-and-tags.yml
---
- name: InfraForge — Nginx with Handlers and Tags
  hosts: webservers
  become: yes

  handlers:                               # defined SEPARATELY from tasks

    - name: restart nginx                 # handler name (must match notify:)
      service:
        name: nginx
        state: restarted

    - name: reload nginx                  # graceful reload (no downtime)
      service:
        name: nginx
        state: reloaded

    - name: restart application
      systemd:
        name: fluxserve
        state: restarted

  tasks:

    # ── NGINX SETUP (tagged: nginx) ──────────────────────
    - name: Install nginx
      apt:
        name: nginx
        state: present
      tags:
        - nginx
        - install

    - name: Deploy nginx main config
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: reload nginx             # triggers handler IF this task changes
      tags:
        - nginx
        - config

    - name: Deploy nginx site config
      template:
        src: fluxserve.conf.j2
        dest: /etc/nginx/sites-available/fluxserve
      notify:                           # can notify multiple handlers
        - reload nginx
        - restart application
      tags:
        - nginx
        - config

    # ── APP DEPLOY (tagged: app, deploy) ─────────────────
    - name: Copy application code
      copy:
        src: ../app/
        dest: /opt/fluxserve/
      notify: restart application
      tags:
        - app
        - deploy

    # ── MONITORING (tagged: monitoring) ─────────────────
    - name: Install node exporter
      apt:
        name: prometheus-node-exporter
        state: present
      tags:
        - monitoring
        - install

💼 INTERVIEW Q&A — CHAPTER 6
When exactly do handlers run?
Handlers run at the END of the play, after ALL tasks have completed. Even if 5 tasks all notify the same handler, it only runs ONCE. You can force handlers to run mid-play using the "meta: flush_handlers" task — useful when a later task depends on the handler having run (e.g., app restart needed before healthcheck task).
What is the "always" tag and how is it special?
If you tag a task with "always", it runs regardless of what --tags or --skip-tags you pass. Useful for setup tasks (gather facts, check prerequisites) that must always run. Similarly "never" means the task ONLY runs if explicitly targeted with --tags never.

💼 INTERVIEW Q&A — CHAPTER 7
What is the difference between vars/main.yml and defaults/main.yml in a role?
defaults/main.yml has the LOWEST precedence — it's meant to be overridden by calling playbooks, inventory vars, or host_vars. Think of it as "factory settings." vars/main.yml has HIGHER precedence — it's hard values that shouldn't be changed by callers. In practice: use defaults/ for anything a user of the role might want to customize, use vars/ for internal role constants that should never change.
What is ansible-galaxy and how do you use it in production?
Ansible Galaxy is the official hub for sharing and downloading Roles and Collections. In production, you define a requirements.yml listing all external roles/collections with specific versions. You then run ansible-galaxy install -r requirements.yml to install them — this is checked into git so your pipeline always installs the exact same versions. Never rely on the latest tag in production.
CHAPTER 08 · JINJA2 TEMPLATES
One nginx.conf for Every Environment
Dev uses port 3000. Staging uses port 8080. Production uses port 443 with SSL. The nginx.conf files are nearly identical except for 5 values. Maintaining 3 separate config files is a maintenance nightmare. With Jinja2 Templates, you write ONE template file with placeholders, and Ansible fills in the correct values for each environment at deploy time. Your nginx.conf becomes a living document.
 roles/nginx/templates/nginx.conf.j2
# nginx.conf — Generated by Ansible for {{ inventory_hostname }}
# Environment: {{ env | default('development') }}
# Generated: {{ ansible_date_time.iso8601 }}
# DO NOT EDIT MANUALLY — managed by Ansible

user {{ nginx_user }};
worker_processes {{ nginx_worker_processes }};
error_log /var/log/nginx/error.log {{ 'warn' if env == 'production' else 'debug' }};

events {
    worker_connections {{ nginx_worker_connections }};
    multi_accept on;
}

http {
    sendfile on;
    tcp_nopush on;
    keepalive_timeout {{ nginx_keepalive_timeout }};

{% if nginx_ssl_enabled %}
    # SSL Configuration (production only)
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers on;
    ssl_session_cache shared:SSL:10m;
{% endif %}

    # Rate limiting for production
{% if env == 'production' %}
    limit_req_zone $binary_remote_addr zone=api:10m rate={{ rate_limit | default('100r/s') }};
{% endif %}

    server {
        listen {{ nginx_listen_port }};
        server_name {{ nginx_server_name }};
        root {{ nginx_root_dir }};

{% for upstream in app_upstreams %}
        # Backend: {{ upstream.name }}
        location {{ upstream.path }} {
            proxy_pass http://{{ upstream.host }}:{{ upstream.port }};
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }
{% endfor %}

{% if env != 'production' %}
        # Debug endpoint (dev/staging only)
        location /debug {
            return 200 "Server: {{ inventory_hostname }} | Env: {{ env }}";
        }
{% endif %}
    }
}

💼 INTERVIEW Q&A — CHAPTER 8
What is the difference between the copy module and the template module?
copy transfers files exactly as-is from control node to managed node — no processing. template processes the source file through Jinja2 first — replacing all {{ }} variables and {% %} logic — then transfers the rendered result. Always use template for config files that need dynamic values. Use copy for static files like SSL certificates, binary files, or static scripts.
How do you prevent accidental manual edits to Ansible-managed files?
Add a comment at the top of the template: "# This file is managed by Ansible. Manual changes WILL BE OVERWRITTEN." Many teams also use the ansible_managed special variable: {{ ansible_managed }} which expands to a string like "Ansible managed: nginx.conf.j2 modified on 2024-01-15 by ubuntu on control-node." This makes it clear to anyone looking at the file that it's managed by Ansible.

💼 INTERVIEW Q&A — CHAPTER 9
How do you manage multiple vault passwords for different environments?
Use vault IDs. You can encrypt files with different passwords: ansible-vault encrypt --vault-id prod@~/.vault_prod secrets.yml and ansible-vault encrypt --vault-id dev@~/.vault_dev secrets.yml. Then run the playbook with: ansible-playbook site.yml --vault-id prod@~/.vault_prod --vault-id dev@~/.vault_dev. Ansible figures out which password to use for each file automatically.
What is the naming convention for vault variables and why?
Best practice: prefix vault variables with "vault_" (e.g., vault_db_password). Then in your non-encrypted vars.yml, create a plain variable that references it: db_password: "{{ vault_db_password }}". This way, anyone reading vars.yml can see that db_password exists and where it's used — without needing vault access. The vault file only needs to be opened when changing the secret.

 site.yml — With Rolling Update Strategy
---
- name: Deploy FluxServe to Web Servers — Rolling Update
  hosts: webservers
  become: yes
  serial: "{{ serial_batches | default('30%') }}"
    # serial: "30%" = deploy to 30% of servers at a time
    # With 3 servers: deploys 1, checks, deploys 1, checks, deploys 1
    # Default: 30% of fleet. Override with -e serial_batches=1 for 1-at-a-time

  max_fail_percentage: 0
    # 0% = if ANY server fails, abort the entire play immediately
    # 50% = allow up to 50% of servers to fail before aborting

  pre_tasks:                           # run BEFORE roles
    - name: Remove server from load balancer
      uri:
        url: "http://{{ lb_api_url }}/drain/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost           # run this task on control node, not server

    - name: Wait for connections to drain
      pause:
        seconds: 10

  roles:
    - common
    - nginx
    - fluxserve-app

  post_tasks:                          # run AFTER roles
    - name: Health check — wait for app to be ready
      uri:
        url: "http://{{ ansible_default_ipv4.address }}/health"
        status_code: 200
      retries: 10                       # try 10 times
      delay: 5                          # wait 5 seconds between retries

    - name: Re-add server to load balancer
      uri:
        url: "http://{{ lb_api_url }}/enable/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost

# InfraForge Rollback Playbook
# Triggered automatically by pipeline on health check failure
# Or manually: ansible-playbook rollback.yml -e "rollback_version=abc123"

- name: Rollback FluxServe to Previous Version
  hosts: webservers
  become: yes

  tasks:
    - name: Check if previous version backup exists
      stat:
        path: "/opt/fluxserve-backup"
      register: backup_exists

    - name: Fail if no backup available
      fail:
        msg: "No backup found! Manual intervention required."
      when: not backup_exists.stat.exists

    - name: Stop current application
      service:
        name: fluxserve
        state: stopped

    - name: Restore previous version from backup
      command: |
        rsync -av /opt/fluxserve-backup/ /opt/fluxserve/

    - name: Start application with previous version
      service:
        name: fluxserve
        state: started

    - name: Verify rollback health
      uri:
        url: "http://{{ ansible_default_ipv4.address }}/health"
        status_code: 200
      retries: 5
      delay: 3

    - name: Notify team of rollback
      uri:
        url: "{{ slack_webhook_url }}"
        method: POST
        body_format: json
        body:
          text: "⚠️ ROLLBACK executed on {{ inventory_hostname }}! Auto-triggered."
      delegate_to: localhost

💼 FINAL INTERVIEW Q&A — PRODUCTION ANSIBLE
How do you implement zero-downtime deployments with Ansible?
Use serial: to deploy to a subset of servers at a time (e.g., serial: 1 or serial: "30%"). In pre_tasks: remove the server from the load balancer before deploying. In post_tasks: verify health before re-adding to load balancer. Set max_fail_percentage: 0 to abort if any server fails. This ensures traffic always flows through healthy servers while others are being updated.
What is delegate_to and when would you use it?
delegate_to: runs a specific task on a DIFFERENT host than the current inventory host. Common uses: hitting an API endpoint on the control node (delegate_to: localhost) — like notifying a load balancer to drain a server, running database migrations from a specific machine, or fetching data from one server and storing it on another. The task still uses the current host's variables but executes on the delegated host.
What is Molecule and how does it differ from regular Ansible testing?
Molecule is a testing framework specifically for Ansible roles. It spins up temporary infrastructure (Docker containers, VMs, cloud instances), runs your role against them, verifies the expected state using verify.yml, and tears everything down. Regular ansible-playbook --check is a "dry run" with no real execution. Molecule actually runs your playbook in isolated containers and verifies real state — nginx is installed, the service is running, the config syntax is valid. It's the closest thing to unit tests for Ansible roles.
Explain the difference between pre_tasks, roles, and post_tasks execution order.
Execution order is strict: pre_tasks run first (before any roles), then roles execute in listed order, then tasks: (if any), then post_tasks last. Handlers are flushed between each section. This ordering is critical for patterns like: pre_tasks (remove from LB) → roles (deploy) → post_tasks (health check, re-add to LB). Note: if both tasks: and roles: are in a play, roles actually run BEFORE tasks: — which surprises people. pre_tasks is the reliable way to ensure something runs before roles.
How do you handle secrets rotation in Ansible Vault at scale?
For small teams: ansible-vault rekey vault.yml changes the password, update it in your CI secret. For larger scale, integrate with HashiCorp Vault or AWS Secrets Manager using the community.hashi_vault or amazon.aws collections — fetch secrets at runtime using lookup() plugins (lookup('community.hashi_vault.hashi_vault', 'secret/db_password')) rather than storing them in Ansible Vault at all. The pipeline retrieves fresh secrets from the secrets manager at deploy time, so rotation happens centrally.
