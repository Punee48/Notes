Error Handling —
block / rescue / always

Handle failures gracefully like a senior engineer. Use try-catch logic in Ansible, auto-rollback on failure, and guarantee cleanup tasks always run — even when things break.

blockrescuealwaysignore_errorsfailed_whenchanged_when
📖 TechNova Story — Chapter 11

It's deployment day at TechNova. Ravi runs the deploy playbook on 50 production web servers. On server web23, the new JAR file is missing from S3. The playbook crashes mid-way — 22 servers got the new app, 28 servers still have the old version. The whole team is debugging at midnight.

Ravi tells you: "Puneeth, we need a smarter deployment — if something fails, automatically rollback the servers that were being updated, and ALWAYS send a Slack notification no matter what happens. Just like try-catch-finally in Java."

Ansible has exactly this — block / rescue / always.

🧠 block/rescue/always — The Ansible Try-Catch

Think of it like Java/Python exception handling:

concept — Java vs Ansible comparison
// JAVA:                         |  # ANSIBLE:
try {                            |  block:
  doSomething();                 |    - name: Do something risky
  doSomethingElse();             |    - name: Do something else
} catch (Exception e) {         |  rescue:
  rollback();                    |    - name: Rollback on failure
  alertTeam();                   |    - name: Alert the team
} finally {                     |  always:
  sendNotification();            |    - name: Always send notification
  cleanup();                     |    - name: Always cleanup
}                                |

Hands-on Lab — Full Deployment with Auto-Rollback

🔧 Lab — playbooks/deploy_with_error_handling.yml
playbooks/deploy_with_error_handling.yml
---
- name: TechNova — Deploy App with Auto-Rollback
  hosts: appservers
  become: true
  vars:
    app_version: "2.5.0"
    app_jar: "technova-app-{{ app_version }}.jar"
    app_dir: /opt/technova/app
    backup_dir: /opt/technova/backup

  tasks:

    # ── STEP 1: BACKUP current version before touching anything ──
    - name: Backup current application version
      copy:
        src: "{{ app_dir }}/technova-app.jar"
        dest: "{{ backup_dir }}/technova-app.jar.bak"
        remote_src: yes
        # remote_src: yes means the src file is ALREADY on the remote server
        # (not on your control node) — copy server-to-server
      ignore_errors: yes
      # ignore_errors: yes — if no existing jar (first deploy), continue anyway
      # Without this, the whole play would stop if the backup fails

    # ── STEP 2: THE MAIN DEPLOYMENT with block/rescue/always ──
    - name: Main deployment block
      block:
        # ╔══════════════════════════════════╗
        # ║  BLOCK = "try" section           ║
        # ║  Tasks that MIGHT fail go here   ║
        # ║  If ANY task fails → jump to     ║
        # ║  rescue section immediately       ║
        # ╚══════════════════════════════════╝

        - name: Stop the running application
          service:
            name: technova-app
            state: stopped

        - name: Download new JAR from S3
          aws_s3:
            # aws_s3 module — downloads from S3 bucket
            bucket: technova-releases
            object: "releases/{{ app_jar }}"
            dest: "{{ app_dir }}/{{ app_jar }}"
            mode: get
            # If the JAR doesn't exist in S3, this task FAILS
            # → Ansible jumps to RESCUE section immediately
            # → The "Start app" and "Health check" tasks below are SKIPPED

        - name: Replace app JAR with new version
          copy:
            src: "{{ app_dir }}/{{ app_jar }}"
            dest: "{{ app_dir }}/technova-app.jar"
            remote_src: yes

        - name: Start the application with new version
          service:
            name: technova-app
            state: started

        - name: Wait for app to be ready (health check)
          uri:
            url: "http://localhost:8080/actuator/health"
            status_code: 200
          retries: 5
          # retries: 5 → try this task up to 5 times before failing
          delay: 10
          # delay: 10 → wait 10 seconds between each retry
          # Total wait = up to 50 seconds before giving up
          register: health_result
          until: health_result.status == 200
          # until: keep retrying UNTIL this condition is true

      rescue:
        # ╔══════════════════════════════════╗
        # ║  RESCUE = "catch" section        ║
        # ║  Runs ONLY when block fails      ║
        # ║  Auto-rollback logic goes here   ║
        # ╚══════════════════════════════════╝

        - name: LOG — Deployment failed, starting rollback
          debug:
            msg: "⚠️  Deployment FAILED on {{ inventory_hostname }}. Rolling back to previous version."

        - name: Stop broken new version (if started)
          service:
            name: technova-app
            state: stopped
          ignore_errors: yes
          # ignore_errors: yes — in rescue, be lenient, we're in recovery mode
          # Even if stop fails (service never started), continue rollback

        - name: Restore backup JAR (ROLLBACK)
          copy:
            src: "{{ backup_dir }}/technova-app.jar.bak"
            dest: "{{ app_dir }}/technova-app.jar"
            remote_src: yes

        - name: Start old (rolled-back) version
          service:
            name: technova-app
            state: started

        - name: Set deployment status fact for notification
          set_fact:
            deploy_status: "FAILED — rolled back"
            deploy_color: "danger"

      always:
        # ╔══════════════════════════════════╗
        # ║  ALWAYS = "finally" section      ║
        # ║  Runs ALWAYS — success OR fail   ║
        # ║  Cleanup, notifications here     ║
        # ╚══════════════════════════════════╝

        - name: Set success status if not already set (block succeeded)
          set_fact:
            deploy_status: "SUCCESS"
            deploy_color: "good"
          when: deploy_status is not defined

        - name: Send Slack notification (always, regardless of outcome)
          slack:
            # Uses the community.general.slack module (install collection first)
            token: "{{ vault_slack_token }}"
            msg: "TechNova Deploy {{ app_version }} on {{ inventory_hostname }}: {{ deploy_status }}"
            color: "{{ deploy_color }}"
          ignore_errors: yes
          # ignore_errors: yes — don't fail deployment JUST because Slack is down

        - name: Cleanup downloaded temp files
          file:
            path: "{{ app_dir }}/{{ app_jar }}"
            state: absent
            # state: absent = delete the file if it exists
            # Always clean up temp downloads, success or fail
          ignore_errors: yes

failed_when and changed_when — Precise Control

failed_when and changed_when examples
- name: Check if our app process is running
  shell: pgrep -f technova-app
  register: app_process
  failed_when: false
  # failed_when: false → NEVER mark this task as failed
  # pgrep returns exit code 1 if process not found
  # Without failed_when: false, Ansible would stop here with an error
  # With it: we capture the output and handle it ourselves with when:

- name: Custom fail condition — fail if output contains "ERROR"
  shell: cat /var/log/technova/app.log | tail -5
  register: log_output
  failed_when: "'FATAL' in log_output.stdout"
  # failed_when with a string condition
  # This task FAILS if the word "FATAL" appears in the last 5 log lines
  # Even if the shell command itself returns exit code 0 (success)
  # You define what "failure" means for your business logic

- name: Run database migration script
  shell: python3 /opt/technova/migrate.py
  register: migration_result
  changed_when: "'Applied' in migration_result.stdout"
  # changed_when: custom condition for when this task is "changed"
  # If migration output contains "Applied" → mark as changed (migrations ran)
  # If output says "Nothing to apply" → mark as ok (no change)
  # This makes your PLAY RECAP accurate and meaningful

- name: Get nginx version — never changes anything
  command: nginx -v
  changed_when: false
  # changed_when: false → always mark as "ok", never "changed"
  # Getting a version never changes server state
  # Without this, Ansible would report "changed" every run (misleading!)
🎯 Interview Questions — Chapter 11
Q1: What is the difference between block/rescue/always in Ansible and when do you use it?
block groups tasks together like a "try" clause. rescue runs only when any task in the block fails — like "catch". always runs unconditionally after block and rescue, whether success or failure — like "finally". Use this pattern for: deployment with auto-rollback, operations that need guaranteed cleanup (deleting temp files), and tasks that must send notifications regardless of outcome (Slack alerts, email notifications).
Q2: What is the difference between ignore_errors and failed_when?
ignore_errors: true tells Ansible: "if this task fails, log it but continue to the next task anyway" — blunt, no condition. failed_when lets you define precisely what constitutes "failure" using a custom condition. For example: failed_when: "'ERROR' in result.stdout" — the task only fails if the output contains "ERROR", not on any other error condition. failed_when: false means "never consider this task failed regardless of exit code". Use failed_when for precise, business-logic-driven failure detection.
Q3: What are retries and until in Ansible tasks?
retries sets how many times to retry a task that fails. delay sets the seconds to wait between retries. until defines the condition that, when true, stops the retry loop (success condition). For example, a health check: retries: 10, delay: 15, until: health.status == 200 — keep checking every 15 seconds, up to 10 times (150 seconds total), until the app returns HTTP 200. Without until, it retries on every failure. This pattern is essential for waiting for services to come up after a restart.
Q4: When does rescue run vs when does it NOT run?
The rescue section runs when any task in the block fails (non-zero exit code, module error, etc.). It does NOT run if all block tasks succeed. It also does NOT run if the failure is in the rescue section itself (a failed rescue task stops the play). The always section runs in both cases — block success, block failure, rescue success, or rescue failure. One exception: if the entire host becomes unreachable (SSH drops), neither rescue nor always will run on that host.

Tags —
Selective Task Execution

Label tasks with tags and run only specific parts of a playbook. Deploy only the app code without reinstalling packages. Restart only services without any other tasks. Tags save enormous time in production.

📖 TechNova Story — Chapter 12

TechNova's full deployment playbook takes 25 minutes to run — it installs packages, creates users, deploys code, runs DB migrations, configures Nginx, and restarts services. But 90% of the time, only the app JAR file changes between releases.

Developer Arun says: "Puneeth, can we just deploy the new JAR and restart the service? We don't need to redo the Nginx config, user creation, and package installs every time — that's wasting 20 minutes per release!"

🔧 Lab — Tagging a Production Playbook
playbooks/site.yml — with comprehensive tags
---
- name: TechNova Full Setup and Deploy
  hosts: appservers
  become: true

  tasks:

    # ── SETUP TASKS (run only on first install) ──
    - name: Install required packages
      apt: name={{ item }} state=present
      loop: [java-17-openjdk, curl, wget, git]
      tags:
        - install
        - setup
        - packages
        # "tags:" can be a list — this task gets ALL three tags
        # Run with --tags install OR --tags setup OR --tags packages
        # Any matching tag will include this task

    - name: Create application directories
      file: path=/opt/technova state=directory
      tags: [setup, directories]
      # Short bracket syntax — same as list format above

    - name: Create deploy user
      user: name=deploy state=present
      tags: [setup, users]

    # ── CONFIG TASKS ──
    - name: Deploy application config from template
      template:
        src: app.properties.j2
        dest: /opt/technova/app.properties
      notify: Restart AppService
      tags: [config, deploy]
      # Tagged with "config" AND "deploy"
      # Running --tags config → this task runs
      # Running --tags deploy → this task also runs

    - name: Deploy Nginx config
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: Restart Nginx
      tags: [config, nginx]

    # ── DEPLOY TASKS ──
    - name: Stop application service
      service: name=technova-app state=stopped
      tags: [deploy, restart]

    - name: Download and copy new application JAR
      copy:
        src: /tmp/technova-app-{{ app_version }}.jar
        dest: /opt/technova/app/technova-app.jar
      tags: [deploy, code]
      # Tagged with "deploy" and "code"
      # When you run: ansible-playbook site.yml --tags deploy
      # Only tasks with tag "deploy" run → this and service tasks
      # The install and user creation tasks are SKIPPED → saves 20 minutes!

    - name: Start application service
      service: name=technova-app state=started
      tags: [deploy, restart]

    # ── SPECIAL: ALWAYS tag ──
    - name: Verify application health (run with ANY tag)
      uri: url=http://localhost:8080/health status_code=200
      tags: [always]
      # "always" is a SPECIAL tag — this task runs REGARDLESS of which --tags flag you use
      # Even if you run --tags deploy, this health check still runs
      # Use "always" for essential safety checks that must run every time

    # ── SPECIAL: NEVER tag ──
    - name: Full database reset (DANGEROUS — only run explicitly)
      shell: mysql -u root -p{{ vault_db_pass }} technova_db < /tmp/reset.sql
      tags: [never, db_reset]
      # "never" is a SPECIAL tag — this task NEVER runs unless you EXPLICITLY request it
      # Running: ansible-playbook site.yml → SKIPPED
      # Running: ansible-playbook site.yml --tags all → STILL SKIPPED
      # Running: ansible-playbook site.yml --tags db_reset → NOW it runs
      # Use "never" for destructive/dangerous tasks as a safety guard

  handlers:
    - name: Restart AppService
      service: name=technova-app state=restarted
    - name: Restart Nginx
      service: name=nginx state=reloaded

Running with Tags — Command Reference

terminal — all tag run options
# ── LIST available tags in a playbook ──
ansible-playbook site.yml --list-tags
# Output: [install, setup, packages, config, deploy, code, restart, ...]

# ── LIST which tasks would run for a specific tag (no actual execution) ──
ansible-playbook site.yml --tags deploy --list-tasks
# Shows which tasks have "deploy" tag — verify before running!

# ── RUN only tasks tagged "deploy" ──
# → Only JAR copy, service stop/start run. Package install skipped.
ansible-playbook -i inventory/hosts.ini site.yml --tags deploy

# ── RUN multiple tags (tasks with ANY of these tags run) ──
ansible-playbook site.yml --tags "deploy,config"

# ── SKIP specific tags (run everything EXCEPT these) ──
# Run full playbook but SKIP the "packages" tasks
ansible-playbook site.yml --skip-tags packages

# ── RUN ALL tasks including "never" tagged ones ──
# This is the ONLY way to run tasks with tag "never"
ansible-playbook site.yml --tags never,db_reset

# ── RUN only restart tasks after a manual config change ──
ansible-playbook site.yml --tags restart

# ── Combine tags with limit (run deploy on web01 only) ──
ansible-playbook site.yml --tags deploy --limit web01
🧠 Tag Inheritance in Roles

When you apply a tag to a role import, ALL tasks inside that role inherit that tag — you don't need to tag every individual task inside the role.

site.yml — tag inheritance
- name: Setup TechNova
  hosts: all
  roles:
    - role: nginx
      tags: [nginx, webserver]
      # ALL tasks inside roles/nginx/tasks/main.yml now have "nginx" and "webserver" tags
      # Run: --tags nginx → runs ALL nginx role tasks
      # Without this inheritance, you'd need to tag each task inside the role
    - role: mysql
      tags: [mysql, database]
🎯 Interview Questions — Chapter 12
Q1: What is the difference between the "always" and "never" special tags?
Tasks tagged with always run no matter which --tags flag you use — even if you run --tags deploy, the "always" tagged task runs too. Use for safety checks, health checks, or notifications that must always happen. Tasks tagged with never are the opposite — they never run by default, not even with --tags all. They only run when explicitly requested with their specific tag name. Use for dangerous or rarely-needed operations like database resets or destructive cleanup.
Q2: How do tags help in a production CI/CD pipeline?
In production CI/CD, tags dramatically reduce deployment time. A "full deploy" pipeline runs all tags for initial setup. A "code deploy" pipeline uses --tags deploy — only deploys new code and restarts services (2 minutes instead of 20). A "config update" pipeline uses --tags config — only pushes config changes and reloads services. A "restart only" pipeline uses --tags restart for emergency service restarts. Each Jenkins job or GitHub Actions workflow can target a specific tag, giving fine-grained control over what runs.

🔧 Step 2 — Create the Dynamic Inventory File
inventory/aws_ec2.yml — TechNova dynamic inventory
---
plugin: amazon.aws.aws_ec2
# "plugin:" tells Ansible which inventory plugin to use
# "amazon.aws.aws_ec2" is from the amazon.aws collection you just installed
# Ansible detects this is a dynamic inventory (not static) because of this line
# FILE NAMING RULE: file must end with "aws_ec2.yml" or "aws_ec2.yaml"
# Ansible uses the filename suffix to auto-detect the plugin

regions:
  - ap-south-1
  # Which AWS regions to query for EC2 instances
  # Can list multiple: [ap-south-1, us-east-1, eu-west-1]
  # TechNova is in Mumbai (ap-south-1)

filters:
  # "filters:" narrows down WHICH instances to include in inventory
  # Only instances matching ALL filters appear in your Ansible inventory
  instance-state-name: running
  # Only RUNNING instances — skip stopped, terminated, pending
  # This prevents Ansible from trying to SSH to terminated instances
  tag:Project: TechNova
  # Only instances tagged "Project=TechNova" — ignore other teams' servers
  # This is how you scope inventory to your specific project

keyed_groups:
  # "keyed_groups:" creates Ansible inventory groups based on EC2 tags or attributes
  # Each rule generates group names automatically from tag values

  - prefix: env
    key: tags.Environment
    # Creates groups like: env_production, env_staging, env_dev
    # Any instance tagged "Environment=production" → goes into "env_production" group
    # Now you can target: ansible-playbook deploy.yml -i aws_ec2.yml --limit env_production

  - prefix: role
    key: tags.Role
    # Creates groups like: role_webserver, role_appserver, role_dbserver
    # Any instance tagged "Role=webserver" → goes into "role_webserver" group

  - prefix: az
    key: placement.availability_zone
    # Creates groups like: az_ap_south_1a, az_ap_south_1b
    # Useful for AZ-aware deployments (deploy to one AZ at a time)

hostnames:
  - private-ip-address
  # What to use as the hostname in Ansible output
  # "private-ip-address" → shows 10.0.1.25 in Ansible output
  # Other options: public-ip-address, dns-name, tag:Name

compose:
  # "compose:" builds Ansible variables from EC2 instance attributes
  # These become available in your playbooks as variables
  ansible_host: private_ip_address
  # ansible_host: the actual IP Ansible will SSH to
  # Using private_ip_address = connects via AWS internal network (faster, free)
  # Your control node must be inside AWS (EC2 or VPN) for this to work
  ansible_user: "'ubuntu'"
  # ansible_user: SSH username — hardcoded to 'ubuntu' (note: double quotes + single quotes)
  # For Amazon Linux: "'ec2-user'"
  ec2_instance_type: instance_type
  # Creates variable ec2_instance_type = "t3.medium" etc.
  # Useful for conditional tasks: when: ec2_instance_type == "t3.large"
  ec2_name: tags.Name
  # Creates variable ec2_name from the EC2 Name tag

include_filters:
  - tag:Managed: ansible
  # Only include instances with tag "Managed=ansible"
  # An extra layer of safety — must be explicitly tagged for Ansible management

🎯 Interview Questions — Chapter 13
Q1: How does Ansible dynamic inventory work with AWS EC2?
The amazon.aws.aws_ec2 inventory plugin uses boto3 (Python AWS SDK) to call the AWS EC2 DescribeInstances API at runtime. It fetches all running instances matching your filters (region, tags, state) and builds an Ansible inventory on-the-fly. The keyed_groups config creates Ansible groups based on EC2 tags — so instances tagged "Role=webserver" automatically appear in the "role_webserver" group. No file needs updating when instances are added or removed.
Q2: How do you configure AWS credentials for Ansible dynamic inventory?
AWS credentials can be provided in several ways (in priority order): 1. Environment variables: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY. 2. AWS credentials file at ~/.aws/credentials (configured by aws configure). 3. IAM Role attached to the EC2 instance running Ansible — best practice for production! The IAM role needs ec2:DescribeInstances permission at minimum. Using an IAM role means zero credentials in any file, which is the most secure approach.
Q3: What is keyed_groups in the aws_ec2 inventory plugin?
keyed_groups automatically creates Ansible inventory groups based on EC2 instance attributes or tags. For example, key: tags.Environment with prefix: env creates groups like env_production, env_staging, env_dev — populated automatically from EC2 tags. This is powerful because you don't manually define any groups — they emerge from your EC2 tag values. Add a tag to a new instance and it automatically appears in the correct group.

🧠 What is an Ansible Collection?

A Collection is a distribution format for Ansible content — it packages related modules, roles, plugins, and documentation into one installable unit. Before Collections (Ansible < 2.9), all modules lived in one huge repository. Now, AWS modules are in amazon.aws, Docker modules in community.docker, Kubernetes modules in kubernetes.core — each maintained by its own team and versioned independently.

🎯 Interview Questions — Chapter 14
Q1: What is the difference between Ansible Roles and Ansible Collections?
Roles are a way to organize and reuse playbook code (tasks, handlers, templates) for a specific purpose — like a "nginx role" or "mysql role". They contain YAML and Jinja2 files. Collections are a packaging format that can contain roles, modules (Python code), plugins, and documentation. Think of it this way: amazon.aws Collection provides the EC2, S3, VPC modules (Python code). Your nginx Role uses those modules in YAML tasks. Collections give you new capabilities; Roles organize how you use those capabilities.
Q2: What is FQCN and why should you use it?
FQCN (Fully Qualified Collection Name) is the full module path: collection_namespace.collection_name.module_name — for example amazon.aws.ec2_instance. Using FQCN is best practice because: (1) it avoids ambiguity when two collections have modules with the same name, (2) it makes your playbook self-documenting (you can see exactly which collection a module comes from), and (3) it prevents breakage if Ansible's default module search path changes. Short names (just ec2_instance) work but can cause confusion in large projects.
Q3: What is delegate_to and run_once used for?
delegate_to: localhost makes a specific task run on your control node instead of the remote server — even though the play targets remote servers. Useful for: API calls (AWS, Slack, Jira), database queries from your local machine, creating local files. run_once: true runs a task only once per play, on the first host in the batch — even if targeting 100 servers. Useful for: sending one notification instead of 100, running one database migration even when targeting all app servers, creating a single shared resource.

---
- name: TechNova — Zero-Downtime Rolling Deployment
  hosts: role_webserver
  # Targeting 50 web servers from dynamic inventory
  become: true
  gather_facts: true

  serial: 5
  # "serial: 5" — process 5 servers at a time in each "batch"
  # Ansible runs the ENTIRE play on batch 1 (servers 1-5) first
  # After ALL tasks complete successfully on batch 1 → move to batch 2 (6-10)
  # This means at most 5 servers are "in transition" at any time
  # The other 45 servers keep serving traffic during the update

  # serial can also be a PERCENTAGE:
  # serial: "10%"  → 10% of 50 hosts = 5 servers per batch
  # serial: "20%"  → 10 servers per batch

  # serial can be a LIST for progressive rollout:
  # serial: [1, 5, 10]
  # First batch: 1 server (canary), then 5, then 10, then rest
  # CANARY RELEASE PATTERN built-in!

  max_fail_percentage: 20
  # max_fail_percentage: 20
  # If MORE than 20% of hosts fail in a batch → STOP entire deployment
  # Do NOT update remaining servers
  # Example: batch of 5 servers, 2 fail (40%) → exceeds 20% → STOP
  # This prevents a cascading failure from propagating to all servers

  vars:
    app_version: "{{ version | default('latest') }}"
    alb_arn: "{{ lookup('env', 'TG_ARN') }}"
    health_check_url: "http://localhost:8080/actuator/health"

  tasks:

    - name: STEP 1 — Deregister server from ALB target group
      amazon.aws.elb_target:
        target_group_arn: "{{ alb_arn }}"
        target_id: "{{ ansible_default_ipv4.address }}"
        target_port: 8080
        state: absent
        # Removes this server from ALB — traffic stops going to it
        # Existing connections drain (users finish their current requests)
      delegate_to: localhost
      # ALB API call runs from control node, not from the web server

    - name: STEP 2 — Wait for connection drain (30 seconds)
      pause:
        seconds: 30
        # "pause" module — just waits. No task, no shell command.
        # ALB deregistration delay is 30s by default
        # Active connections finish during this wait
        # After this, no new requests reach this server

    - name: STEP 3 — Stop the running application
      service: name=technova-app state=stopped

    - name: STEP 4 — Deploy new application JAR
      copy:
        src: /tmp/technova-app-{{ app_version }}.jar
        dest: /opt/technova/app/technova-app.jar
        owner: deploy
        mode: '0755'

    - name: STEP 5 — Start application with new version
      service: name=technova-app state=started

    - name: STEP 6 — Health check — wait for app to be ready
      uri:
        url: "{{ health_check_url }}"
        status_code: 200
      retries: 12
      delay: 10
      until: health_result.status == 200
      register: health_result
      # Try every 10 seconds, up to 12 times (2 minutes total)
      # If app doesn't respond with 200 in 2 minutes → task FAILS
      # → max_fail_percentage kicks in → deployment STOPS

    - name: STEP 7 — Re-register server to ALB (only if healthy!)
      amazon.aws.elb_target:
        target_group_arn: "{{ alb_arn }}"
        target_id: "{{ ansible_default_ipv4.address }}"
        target_port: 8080
        state: present
        # Server is BACK in ALB — traffic resumes to it
        # We only reach this step if health check PASSED
        # If health check failed → play stopped → this never runs
        # → Server stays OUT of ALB (broken server never serves traffic)
      delegate_to: localhost

🎯 Interview Questions — Chapter 15
Q1: How do you implement zero-downtime rolling deployment with Ansible?
Use serial to deploy to batches of servers at a time. The pattern: 1) Remove server from ALB target group, 2) Wait for connection drain, 3) Stop old app, 4) Deploy new version, 5) Start new app, 6) Health check (retries until healthy), 7) Re-add to ALB. With serial: 5 on 50 servers, at any given time 45 servers are still serving traffic while 5 are being updated. Only healthy servers are re-added to ALB. max_fail_percentage stops the entire deployment if too many servers fail in a batch.
Q2: What is the difference between strategy: linear and strategy: free?
linear (default) runs Task 1 on all hosts, waits for all to finish, then runs Task 2 on all hosts — all hosts stay in lockstep. If one slow server takes 5 minutes on Task 1, all other servers wait for it before moving to Task 2. free lets each host run all tasks at its own pace — fast servers don't wait for slow ones. Free is useful for independent tasks like package installations across many servers where you want maximum speed, but it can cause issues if later tasks depend on all servers having completed earlier ones.
Q3: What is max_fail_percentage and why is it important?
max_fail_percentage defines the threshold at which Ansible aborts the entire play. If the percentage of failed hosts in a batch exceeds this number, Ansible stops processing all remaining batches. For example, with serial: 10 and max_fail_percentage: 30: if 4 out of 10 servers fail (40%), Ansible stops. This is a circuit breaker for deployments — prevents a broken release from propagating to all servers. Without it, Ansible continues to the next batch even if the current batch has critical failures, potentially taking down the entire fleet.

Q1: Why do enterprises use Ansible Tower instead of plain Ansible?
Enterprises use Tower because plain Ansible lacks: (1) Audit trail — every job run is logged with who ran it, when, which servers, full output — required for compliance (SOC2, ISO27001). AWX is the open-source upstream project that Tower is built from — free to use. It runs on Kubernetes and gets frequent updates. 🎯 Interview Questions — Chapter 18
Q1: How does Tower handle SCM (Git) project syncing?
Tower maintains a local clone of your Git repository. When you click "Sync" or enable "Update on Launch", Tower runs a git pull to fetch the latest code. The "Update Revision on Launch" option ensures every Job Template run uses the current HEAD of the specified branch — so if a developer pushes a fix to Git, the next Tower job automatically uses the updated playbook without any manual sync. You can also set a specific branch, tag, or commit hash for stability.
Q2: What types of credentials does Tower support and give examples?
Tower supports many credential types: Machine (SSH private key + username + sudo password for Linux servers), Source Control (GitHub/GitLab token for private repos), Amazon Web Services (access key + secret key for AWS API calls), Vault (Ansible Vault password for decrypting vault-encrypted files), Container Registry (Docker Hub/ECR credentials), Google Compute Engine (GCP service account). Each type automatically injects the credential in the right format at job runtime.
Q3: Why should credentials be stored in Tower instead of in playbooks?
Storing credentials in Tower (not in playbooks or group_vars): (1) Security — encrypted at rest, never exposed in code, version control, or logs. (2) Principle of least privilege — users get "Use" permission (can use in jobs) without "Read" permission (can't see the value). (3) Centralized rotation — update the SSH key in one Tower credential and it's updated for all Job Templates using it. (4) Audit — Tower logs which credential was used in each job. (5) No credential sprawl — keys aren't copied to multiple laptops and servers.

🎯 Interview Questions — Chapter 19
Q1: What is a Survey in Ansible Tower and how does it work?
A Survey is a form presented to the user before a Job Template runs. It collects user input (text, dropdown choices, integers, passwords) and passes those values as extra_vars to the Ansible playbook. Surveys enable self-service deployments — developers who know nothing about Ansible can fill in a form (version number, environment, count) and trigger automated deployments. Survey variables have high priority like any extra_vars but can be restricted — you can validate format, set min/max for integers, and mark fields as required.
Q2: What is a Workflow Template and when would you use it over a single Job Template?
A Workflow Template chains multiple Job Templates with conditional logic — on success go here, on failure go there. Use a Workflow Template when: your deployment process has multiple stages (test → deploy staging → integration test → deploy prod), you need approval gates (a manager must approve before production deploy), you want to run multiple playbooks in sequence or parallel, or you need different inventories/credentials at different stages. A single Job Template is for one playbook on one inventory. A Workflow is for an end-to-end automated pipeline.
Q3: What is a Workflow Approval node and what problem does it solve?
A Workflow Approval node is a manual gate in the workflow pipeline. When the workflow reaches this node, it pauses and sends notifications to designated approvers. The approvers review the situation and either approve (pipeline continues) or deny (pipeline stops). This solves the problem of fully automated production deployments that nobody can pause — with an approval node, a manager gets to review staging test results before production changes are deployed. Approvals can have timeouts (auto-deny after X hours if nobody responds).

🎯 Interview Questions — Chapter 20
Q1: How does Tower's RBAC enable self-service deployments while maintaining security?
Tower's RBAC achieves this through granular per-object permissions. Developers get "Execute" role on specific Job Templates — they can launch jobs and see output. But they don't get access to Credentials (can't see SSH keys), can't edit Job Templates (can't change which servers are targeted), and can't create new automation. The SSH key is injected by Tower at runtime in a secure execution container. Developers deploy apps they own without ever having SSH access to servers — this is the principle of least privilege in practice.
Q2: What are the 4 main roles on a Tower resource and what does each allow?
Admin: full control — create, edit, delete, run, view, and manage permissions on the resource. Execute: launch/run only — can trigger Job Templates but cannot modify them. Used for developers/operators who need to run automation. Use: can reference the resource in other objects — like a developer can "Use" a credential in a Job Template without seeing its value. Read: view-only — see configuration and history but cannot change or run anything. Used for auditors and monitoring teams.
Q3: How do you handle onboarding and offboarding users in Tower at enterprise scale?
At enterprise scale, manual user management in Tower doesn't work. The solution is LDAP/Active Directory integration. Tower's LDAP config maps AD groups to Tower teams automatically — members of "DevOps-AD-Group" automatically join "DevOps-Team" in Tower, members of "Developers-AD-Group" join "Dev-Team". When an employee is onboarded, HR adds them to the correct AD group — Tower access is automatic. When they leave, HR disables their AD account — Tower access is immediately revoked. This is the enterprise-standard approach that scales to thousands of users.
