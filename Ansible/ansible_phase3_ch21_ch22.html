Part 1 — Schedules: Automating Automation

🧠 What is a Tower Schedule?

A Tower Schedule is a timer attached to a Job Template or Workflow Template that triggers it automatically at a specific time — without anyone clicking Launch. It works exactly like a Linux cron job, but managed through the Tower UI with all the benefits of Tower (audit trail, RBAC, notifications). You can create multiple schedules on one template — for example, run a health-check every hour AND a full compliance scan every Sunday.

Creating Schedules via Playbook (Infrastructure as Code)

🧠 Why manage schedules as code?

In enterprise environments, Tower config itself should be version-controlled — not just your playbooks. If your Tower database is lost and restored, you need to recreate all schedules, credentials, and job templates. The awx.awx collection lets you manage Tower configuration through Ansible playbooks.

playbooks/tower_configure_schedules.yml
---
- name: Configure TechNova Tower Schedules as Code
  hosts: localhost
  connection: local
  gather_facts: false
  collections:
    - awx.awx
    # awx.awx collection has modules to manage Tower itself
    # Install: ansible-galaxy collection install awx.awx

  vars:
    tower_host: "https://your-tower-host"
    tower_username: admin
    tower_password: "{{ vault_tower_password }}"
    # These are your Tower admin credentials
    # Alternatively use tower_token (preferred in CI/CD)

  tasks:

    - name: Create Weekly OS Patching Schedule
      awx.awx.schedule:
        # awx.awx.schedule module creates/updates Tower schedules
        name: "Weekly OS Patching — Sunday 3AM IST"
        state: present
        # state: present = create if not exists, update if exists
        unified_job_template: "OS Patch All Servers"
        # unified_job_template = the Job Template name this schedule runs
        rrule: "DTSTART;TZID=Asia/Kolkata:20240101T030000 RRULE:FREQ=WEEKLY;BYDAY=SU"
        # rrule = RFC 5545 iCalendar recurrence rule format
        # DTSTART;TZID=Asia/Kolkata:20240101T030000
        #   → Start date: 2024-01-01, time: 03:00:00 in Asia/Kolkata timezone
        # RRULE:FREQ=WEEKLY;BYDAY=SU
        #   → Repeat frequency: weekly, on day: Sunday (SU)
        # Tower uses iCal format internally — even when you use the UI,
        # Tower converts your selection to this format in the database
        enabled: true
        # enabled: true = schedule is active and will run
        # enabled: false = schedule exists but is paused
        tower_host: "{{ tower_host }}"
        tower_username: "{{ tower_username }}"
        tower_password: "{{ tower_password }}"

    - name: Create Daily Backup Verification Schedule
      awx.awx.schedule:
        name: "Daily Backup Verification — 2AM IST"
        state: present
        unified_job_template: "Verify DB Backups"
        rrule: "DTSTART;TZID=Asia/Kolkata:20240101T020000 RRULE:FREQ=DAILY"
        # FREQ=DAILY with no BYDAY = runs every day without exception
        enabled: true
        tower_host: "{{ tower_host }}"
        tower_username: "{{ tower_username }}"
        tower_password: "{{ tower_password }}"

    - name: Create Health Check every 15 minutes
      awx.awx.schedule:
        name: "Health Check — Every 15 Minutes"
        state: present
        unified_job_template: "Health Check All Services"
        rrule: "DTSTART:20240101T000000Z RRULE:FREQ=MINUTELY;INTERVAL=15"
        # FREQ=MINUTELY;INTERVAL=15 = run every 15 minutes
        # DTSTART:...Z = Z suffix means UTC timezone (no TZID= needed)
        enabled: true
        tower_host: "{{ tower_host }}"
        tower_username: "{{ tower_username }}"
        tower_password: "{{ tower_password }}"

Part 2 — Notifications: Know the Moment Something Happens

🧠 How Tower Notifications Work

A Notification Template is a configuration for one notification channel (Slack channel, email server, PagerDuty API, etc.). You create it once and attach it to many Job Templates. For each Job Template, you choose WHEN to send: on Start, on Success, or on Failure (or all three). Tower supports 10+ notification types out of the box — no additional plugins needed.

All Notification Types — What TechNova Uses

💬
Slack MOST USED
Posts to a Slack channel via Incoming Webhook URL. Supports custom message with job details, colored attachment (green=success, red=fail). TechNova uses #devops-alerts for all Tower events.
📧
Email
Sends email via SMTP. Supports HTML. Tower sends job name, status, who launched it, link to output, and optionally the full stdout. Use for failures + management reports.
🚨
PagerDuty CRITICAL ALERTS
Creates PagerDuty incidents from Tower job failures. Auto-resolves when next run succeeds. Perfect for critical jobs that need on-call paging — production deploy failures wake up the on-call engineer at 3 AM.
🔗
Webhook (Generic)
HTTP POST to any URL with JSON payload. Use to integrate with Jira (create tickets on failure), custom dashboards, MS Teams via incoming webhook, or any system with an HTTP API.
🌐
Mattermost / Rocket.Chat
Open-source alternatives to Slack. Same webhook-based approach. TechNova's on-premise teams that can't use Slack use Mattermost hosted internally.
📊
Grafana Oncall / OpsGenie
Enterprise alerting platforms. Similar to PagerDuty — creates on-call incidents with escalation policies. OpsGenie is popular in Indian enterprises using Atlassian stack.

  connection: local
  gather_facts: false

          # For Slack: token is the OAuth token (optional if using webhook)

          # hex_color: accent color (empty = use Tower's default green/red)

          started:

        tower_oauthtoken: "{{ tower_token }}"
        # tower_oauthtoken: use API token instead of username+password

      awx.awx.notification_template:
        name: "TechNova Email Alerts"
        state: present
        organization: "TechNova Corp"
        notification_type: email
        notification_configuration:
          username: ansible-tower@technova.com
          password: "{{ vault_smtp_password }}"
          host: smtp.office365.com

            - devops@technova.com
            - ravi.kumar@technova.com
          sender: ansible-tower@technova.com
          port: 587
          use_tls: true

🎯 Interview Questions — Chapter 21
Q1: How do Tower Schedules work and what format do they use internally?
Tower Schedules use the iCalendar (RFC 5545) RRULE format internally, though the UI lets you set them using friendly dropdowns. A schedule is attached directly to a Job Template or Workflow Template. When the scheduled time arrives, Tower's internal scheduler (Celery Beat) triggers a job run exactly as if someone clicked Launch manually — with the same inventory, credentials, and extra vars configured in the template. You can create multiple schedules on one template and toggle them on/off without deleting.
Q2: What is the difference between Tower Notifications and sending alerts in Ansible playbooks directly?
Sending alerts directly in playbooks (using the slack or mail module) ties your notification logic to your playbook code — if you want to change the Slack channel, you edit playbooks. Tower Notifications are centralized and decoupled — configure once in Tower, attach to any Job Template. Tower also sends notifications about tower-level events (job failed to start, host became unreachable) that your playbook code never sees. Tower notifications also include context that playbooks can't provide: who launched the job, duration, direct link to the full output in Tower UI.
Q3: If a scheduled job fails, how does Tower handle the next scheduled run?
Tower schedules are independent of job results. If a scheduled run fails, Tower does NOT stop the schedule — the next scheduled run happens as normal at the configured time. You must configure failure notifications (Slack, Email, PagerDuty) so your team is alerted immediately after a failure. Tower also records the last scheduled job result in the schedule list view — you can see "Last run: Failed" at a glance. For recurring jobs where a failure should block the next run, you need to implement that logic in your playbook using a state file or external check.
Q4: How do you ensure Tower sends notifications in IST (Indian Standard Time) format?
Tower stores all timestamps in UTC internally. When creating a schedule, set the Time Zone field to Asia/Kolkata — Tower converts your local time to UTC internally. For notifications, the {{ job.started }} and {{ job.finished }} variables are UTC ISO timestamps. To display IST in your message, you either rely on recipients converting UTC, or customize the notification message to add "+05:30" note. In enterprise setups, Slack and email clients typically show times in the user's local timezone automatically.

Part 1 — Understanding the Tower REST API

🧠 Tower API Architecture

Tower exposes a full RESTful API at /api/v2/ that mirrors everything you can do in the UI. Every Tower object (Job Templates, Jobs, Inventories, Credentials, Users) has API endpoints you can: GET (read), POST (create/launch), PATCH (update), and DELETE (remove). The API is self-documenting — browse to https://your-tower/api/v2/ in a browser to see all available endpoints with interactive documentation.

Key API Endpoints — The Ones You Use Every Day

Tower REST API — endpoint reference
# BASE URL: https://your-tower-host/api/v2/
# ─────────────────────────────────────────────────────────────────

## AUTHENTICATION
GET   /api/v2/me/                          # who am I? verify token works
GET   /api/v2/tokens/                       # list my API tokens
POST  /api/v2/users/{id}/tokens/            # create a new API token
DELETE /api/v2/tokens/{id}/                # revoke a token

## JOB TEMPLATES
GET   /api/v2/job_templates/               # list all job templates
GET   /api/v2/job_templates/{id}/          # get specific template by ID
POST  /api/v2/job_templates/{id}/launch/   # ⭐ LAUNCH a job template
GET   /api/v2/job_templates/{id}/schedules/ # list schedules for template

## JOBS (running and completed)
GET   /api/v2/jobs/                        # list all jobs
GET   /api/v2/jobs/{id}/                   # ⭐ get job STATUS and details
GET   /api/v2/jobs/{id}/stdout/            # ⭐ get full playbook output
GET   /api/v2/jobs/{id}/cancel/            # check if job can be cancelled

Authentication — Creating and Using API Tokens

🧠 Token vs Username/Password Authentication

Tower API supports both basic auth (username:password) and OAuth2 tokens. Always use tokens in scripts and CI/CD — never hardcode your password. Tokens can be scoped (read-only vs full access), have expiry dates, and can be revoked individually without changing the account password. If a token is leaked, revoke that specific token — your account remains secure.

Hands-on Lab 1 — Launch a Job and Poll for Status

🔧 The Complete Job Launch → Monitor Pattern

This is the pattern you use in Jenkins, GitHub Actions, or any script. Three steps: (1) Find the template ID, (2) Launch the job, (3) Poll until complete.

terminal — complete launch-and-wait script
#!/bin/bash
# TechNova Tower Job Launch Script
# Usage: ./launch_job.sh [app_version]

TOWER_HOST="https://tower.technova.internal"
TOWER_TOKEN="AbCdEfGhIjKlMnOpQrStUvWxYz123456"
APP_VERSION="${1:-latest}"    # First argument or "latest" as default

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# STEP 1: Find the Job Template ID by name
# We need the numeric ID (not name) for the launch endpoint
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
echo "🔍 Looking up Job Template ID..."

TEMPLATE_ID=$(curl -s \
  "${TOWER_HOST}/api/v2/job_templates/" \
  -H "Authorization: Bearer ${TOWER_TOKEN}" \
  | python3 -c "
import sys, json
data = json.load(sys.stdin)
for t in data['results']:
    if t['name'] == 'Deploy TechNova App':
        print(t['id'])
        break
")
# python3 inline script: parses JSON, finds template by name, prints its ID

echo "✅ Template ID: ${TEMPLATE_ID}"

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# STEP 2: Launch the Job Template
# POST to /api/v2/job_templates/{id}/launch/
# Send extra_vars to pass variables into the playbook
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
echo "🚀 Launching deployment for version ${APP_VERSION}..."

LAUNCH_RESPONSE=$(curl -s -X POST \
  "${TOWER_HOST}/api/v2/job_templates/${TEMPLATE_ID}/launch/" \
  -H "Authorization: Bearer ${TOWER_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{
    \"extra_vars\": {
      \"app_version\": \"${APP_VERSION}\",
      \"deploy_env\": \"production\",
      \"serial_count\": 5
    },
    \"limit\": \"role_webserver\"
  }")
# "extra_vars": key-value pairs that become variables in the playbook
# "limit": optional - restrict to specific hosts (like --limit in CLI)
# These override the Job Template's configured extra_vars

JOB_ID=$(echo $LAUNCH_RESPONSE | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")
# Extract the "id" field from the JSON response
# This is the Job ID (different from Template ID) for THIS specific run

echo "✅ Job launched! Job ID: ${JOB_ID}"
echo "📋 View in Tower: ${TOWER_HOST}/#/jobs/${JOB_ID}"

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# STEP 3: Poll for job completion
# Keep checking every 15 seconds until status is not "running"
# Status values: pending, waiting, running, successful, failed, canceled
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
echo "⏳ Waiting for job to complete..."

while true; do
  STATUS=$(curl -s \
    "${TOWER_HOST}/api/v2/jobs/${JOB_ID}/" \
    -H "Authorization: Bearer ${TOWER_TOKEN}" \
    | python3 -c "import sys,json; j=json.load(sys.stdin); print(j['status'])")
    # GET /api/v2/jobs/{id}/ → returns job object with "status" field

  echo "  Status: ${STATUS}"

  if [ "${STATUS}" = "successful" ]; then
    echo "✅ ✅ DEPLOYMENT SUCCESSFUL!"
    exit 0   # exit 0 = success (Jenkins marks build as PASSED)
  elif [ "${STATUS}" = "failed" ] || [ "${STATUS}" = "canceled" ]; then
    echo "❌ DEPLOYMENT FAILED! Status: ${STATUS}"
    echo "📋 View details: ${TOWER_HOST}/#/jobs/${JOB_ID}"
    exit 1   # exit 1 = failure (Jenkins marks build as FAILED)
  fi

  sleep 15  # wait 15 seconds before checking again
done

Hands-on Lab 2 — Jenkins Pipeline Calling Tower

🔧 Lab — Complete Jenkinsfile with Tower Integration

This Jenkinsfile implements the full TechNova CI/CD pipeline: build → test → push to ECR → trigger Tower deployment → verify success.

Jenkinsfile — Jenkins pipeline with Tower API integration
// TechNova Jenkins Pipeline — Full CI/CD with Ansible Tower
pipeline {
    agent any

    environment {
        // Environment variables available in all stages
        APP_VERSION    = "${BUILD_NUMBER}"
        // BUILD_NUMBER is a Jenkins built-in var — auto-increments each build
        ECR_REPO       = "123456789.dkr.ecr.ap-south-1.amazonaws.com/technova-app"
        TOWER_HOST     = "https://tower.technova.internal"
        TOWER_JT_ID    = "5"
        // TOWER_JT_ID: the Job Template ID in Tower
        // Find it: Tower UI → Templates → inspect URL: /templates/job_template/5/
    }

    stages {

        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/technova/app.git'
                // git: checkout the source code
                // branch: 'main' = always build from main branch
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean package -DskipTests'
                // sh: run shell command
                // mvn clean package: build the Java JAR file
                // -DskipTests: skip unit tests here (run in next stage)
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
                // Run all unit tests
                // If any test fails → Jenkins marks stage as FAILED
                // → subsequent stages do NOT run
                // → Tower deploy is never triggered (safe!)
            }
            post {
                always {
                    junit 'target/surefire-reports/**/*.xml'
                    // junit: publish test results in Jenkins UI
                    // Jenkins shows test pass/fail counts per build
                }
            }
        }

        stage('Build and Push Docker Image') {
            steps {
                script {
                    // script{}: allows Groovy code in declarative pipeline
                    sh """
                        # Login to AWS ECR
                        aws ecr get-login-password --region ap-south-1 \
                          | docker login --username AWS --password-stdin ${ECR_REPO}

                        # Build Docker image
                        docker build -t technova-app:${APP_VERSION} .

                        # Tag for ECR
                        docker tag technova-app:${APP_VERSION} ${ECR_REPO}:${APP_VERSION}

                        # Push to ECR
                        docker push ${ECR_REPO}:${APP_VERSION}

                        # Also tag as "latest"
                        docker tag technova-app:${APP_VERSION} ${ECR_REPO}:latest
                        docker push ${ECR_REPO}:latest
                    """
                }
            }
        }

        stage('Deploy via Ansible Tower') {
            steps {
                script {
                    // Read the Tower API token from Jenkins Credentials Store
                    // NEVER hardcode tokens in Jenkinsfile — store in Jenkins creds
                    withCredentials([
                        string(credentialsId: 'tower-api-token', variable: 'TOWER_TOKEN')
                        // string: type of credential (plain text secret)
                        // credentialsId: the ID you gave this credential in Jenkins
                        // variable: the env var name to inject the secret into
                    ]) {
                        // LAUNCH the Tower Job Template via API
                        def launchResponse = sh(
                            returnStdout: true,
                            // returnStdout: true — capture the command output as a string
                            script: """
                                curl -sk -X POST \\
                                  ${TOWER_HOST}/api/v2/job_templates/${TOWER_JT_ID}/launch/ \\
                                  -H "Authorization: Bearer ${TOWER_TOKEN}" \\
                                  -H "Content-Type: application/json" \\
                                  -d '{
                                    "extra_vars": {
                                      "app_version": "${APP_VERSION}",
                                      "image_tag": "${APP_VERSION}",
                                      "ecr_repo": "${ECR_REPO}"
                                    }
                                  }'
                            """
                        ).trim()
                        // .trim(): remove trailing newline from curl output

                        // Parse the Job ID from the JSON response
                        def launchJson = readJSON text: launchResponse
                        // readJSON: Jenkins Pipeline utility to parse JSON string
                        def jobId = launchJson.id
                        echo "Tower Job ID: ${jobId}"
                        echo "View in Tower: ${TOWER_HOST}/#/jobs/${jobId}"

                        // POLL for job completion
                        timeout(time: 30, unit: 'MINUTES') {
                            // timeout: abort if job takes more than 30 minutes
                            waitUntil {
                                // waitUntil: retry the block until it returns true
                                sleep(time: 15, unit: 'SECONDS')
                                // sleep 15 seconds between each poll

                                def statusResponse = sh(
                                    returnStdout: true,
                                    script: """
                                        curl -sk \\
                                          ${TOWER_HOST}/api/v2/jobs/${jobId}/ \\
                                          -H "Authorization: Bearer ${TOWER_TOKEN}"
                                    """
                                ).trim()

                                def statusJson = readJSON text: statusResponse
                                def status = statusJson.status
                                echo "Current status: ${status}"

                                if (status == 'failed' || status == 'canceled') {
                                    error("Tower deployment FAILED! Status: ${status}")
                                    // error(): marks Jenkins stage as FAILED and stops pipeline
                                }

                                return status == 'successful'
                                // return true → waitUntil stops, pipeline continues
                                // return false → waitUntil sleeps 15s and tries again
                            }
                        }

                        echo "✅ Deployment SUCCESSFUL via Ansible Tower!"
                    }
                }
            }
        }

        stage('Smoke Test') {
            steps {
                sh """
                    sleep 10
                    curl -f https://app.technova.com/health
                    # -f flag: curl exits with code 1 if HTTP status >= 400
                    # Jenkins sees non-zero exit → marks stage FAILED
                """
            }
        }
    }

    post {
        // post: runs after all stages, regardless of result
        success {
            echo '✅ Pipeline completed successfully!'
        }
        failure {
            echo '❌ Pipeline FAILED!'
        }
        always {
            // Cleanup Docker images to save disk space
            sh "docker rmi technova-app:${APP_VERSION} || true"
            // "|| true" prevents cleanup failure from failing the build
        }
    }
}

    # If build-and-test fails → deploy-via-tower is SKIPPED
    environment: production
    # environment: production → triggers GitHub's required reviewers feature
    # If configured in GitHub → a team member must approve before this job runs
    # This is GitHub's manual approval gate (like Tower Workflow approval node)

    steps:
      - name: Launch Tower Job Template
        id: launch
        run: |
          RESPONSE=$(curl -sk -X POST \
            ${{ env.TOWER_HOST }}/api/v2/job_templates/${{ env.TOWER_JT_ID }}/launch/ \
            -H "Authorization: Bearer ${{ secrets.TOWER_API_TOKEN }}" \
            -H "Content-Type: application/json" \
            -d '{
              "extra_vars": {
                "app_version": "${{ needs.build-and-test.outputs.image-tag }}",
                "ecr_repo": "${{ env.ECR_REPO }}"
              }
            }')
          # secrets.TOWER_API_TOKEN: stored in GitHub Secrets
          # needs.build-and-test.outputs.image-tag: the image tag from the previous job

          echo "response=$RESPONSE" >> $GITHUB_OUTPUT
          # $GITHUB_OUTPUT: special file — write "key=value" to share with next steps
          JOB_ID=$(echo $RESPONSE | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")
          echo "job_id=$JOB_ID" >> $GITHUB_OUTPUT

      - name: Wait for Tower Job to Complete
        run: |
          JOB_ID="${{ steps.launch.outputs.job_id }}"
          echo "Polling Tower Job ID: $JOB_ID"

          for i in $(seq 1 60); do
            # Loop up to 60 times = 60 × 15 seconds = 15 minutes max wait
            STATUS=$(curl -sk \
              ${{ env.TOWER_HOST }}/api/v2/jobs/${JOB_ID}/ \
              -H "Authorization: Bearer ${{ secrets.TOWER_API_TOKEN }}" \
              | python3 -c "import sys,json; print(json.load(sys.stdin)['status'])")

            echo "Attempt $i/60 — Status: $STATUS"

            if [ "$STATUS" = "successful" ]; then
              echo "✅ Tower deployment SUCCESSFUL!"
              exit 0
            elif [ "$STATUS" = "failed" ] || [ "$STATUS" = "canceled" ]; then
              echo "❌ Tower deployment FAILED! Status: $STATUS"
              exit 1
            fi

            sleep 15
          done

          echo "⏰ Timeout: Tower job did not complete in 15 minutes"
          exit 1

⭐ Pro Tips — Production API Best Practices
  • Create dedicated service account tokens — create a separate Tower user "jenkins-bot" or "github-actions-bot" with minimal permissions (only Execute on specific templates). Use that user's token in CI/CD. Never use the admin token in pipelines.
  • Set token expiry dates — create tokens with an expiry date (e.g., 90 days). Rotate them regularly. Set a reminder to renew before expiry to avoid surprise pipeline failures.
  • Use --insecure (-k) carefully — if Tower uses a self-signed SSL cert, curl needs the -k flag. In production, use a proper certificate (Let's Encrypt or your company's CA) and remove -k.
  • Timeout every API poll loop — always add a maximum timeout (30 minutes in Jenkins, 15 minutes in GitHub Actions) to prevent zombie pipeline runs if Tower goes down mid-job.
  • Check job output on failure — when a Tower job fails, your pipeline should fetch and print the job stdout: curl .../jobs/{id}/stdout/ — this saves engineers from having to open the Tower UI to debug.
  • Use awx CLI with --monitor in simple scripts — for simple shell scripts where you don't need custom logic, awx job_templates launch 5 --monitor handles all the polling automatically with proper exit codes.
🎯 Interview Questions — Chapter 22
Q1: How do you integrate Ansible Tower with Jenkins CI/CD?
The integration uses Tower's REST API. In the Jenkins pipeline: (1) Store the Tower API token as a Jenkins Secret (credentialsId). (2) Use withCredentials to inject the token into environment. (3) After building and pushing Docker image, make a POST to /api/v2/job_templates/{id}/launch/ with the new version as extra_vars. (4) Capture the returned Job ID. (5) Poll /api/v2/jobs/{job_id}/ every 15 seconds until status is "successful" or "failed". (6) Use the exit code to mark the Jenkins build as passed or failed. This creates a clear boundary: Jenkins handles build/test/push, Tower handles deployment with RBAC and audit trail.
Q2: Why use API tokens instead of username/password for Tower API calls?
API tokens are preferred for several reasons: (1) Tokens can be scoped to read or write — a read-only token cannot launch jobs even if leaked. (2) Tokens can have expiry dates — automatic credential rotation. (3) Individual tokens can be revoked without changing the account password — if one token is compromised, revoke it without affecting other pipelines using different tokens. (4) Using username/password in scripts creates a dependency on the account password — if the password changes, all scripts break. (5) Tokens can be tied to a service account (jenkins-bot user) with minimal permissions — principle of least privilege.
Q3: What is the awx CLI and when would you use it vs the REST API directly?
The awx CLI (awxkit package) wraps the Tower REST API in user-friendly commands. Use awx CLI when: (1) running Tower operations from your terminal interactively (checking job status, viewing outputs), (2) writing simple shell scripts where you don't need custom JSON parsing, (3) Tower configuration automation (creating credentials, templates) where awx.awx collection modules might be overkill. Use the REST API directly when: integrating with systems that can't install Python packages (some CI/CD environments), needing fine-grained control over the HTTP request, or building custom tools in languages other than Python.
Q4: How do you pass Ansible playbook variables from Jenkins to Ansible Tower?
Use the extra_vars field in the API POST body when launching a job template. Example: {"extra_vars": {"app_version": "2.5.1", "env": "production"}}. These become the highest-priority variables in the Ansible playbook (same as -e flag). Important: the Job Template must have "Prompt on Launch" enabled for Extra Variables, otherwise Tower will ignore extra_vars sent via API and use only the template's configured vars. Alternatively, use Tower Surveys — Jenkins can send survey answers via the API: {"survey_values": {"app_version": "2.5.1"}}.
Q5: How does GitHub Actions deployment to production differ from just using Ansible CLI directly?
Several key differences: (1) RBAC enforced — Tower RBAC ensures only authorized templates can deploy to production, even if the GitHub Actions token is compromised. (2) Audit trail — Tower records every deployment with who triggered it (the service account), which version, which servers, full output — required for compliance. (3) Credential security — Tower's SSH keys and AWS credentials never leave Tower, even though GitHub Actions triggered the job. (4) Approval gates — combine GitHub Environments (require reviewer) with Tower Workflow approval nodes for two-layer human approval. (5) Rollback capability — if deployment fails, Tower's configured rollback logic runs automatically — GitHub Actions just sees the final result.
