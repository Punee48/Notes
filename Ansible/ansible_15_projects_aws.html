🔧 Core Playbook
nginx_webfarm.yml
---
- name: Enforce Nginx Web Farm Config — TechNova
  hosts: tag_Role_webserver   # aws_ec2 dynamic inventory group
  become: true
  vars:
    site_bucket: s3://technova-static-site
    nginx_version: 1.24.0

  tasks:
    - name: Ensure Nginx is installed (correct version)
      apt:
        name: "nginx={{ nginx_version }}-*"
        state: present
        update_cache: yes

    - name: Deploy nginx.conf from template (detect drift)
      template:
        src: templates/nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        mode: '0644'
      register: nginx_conf_result
      notify: Reload Nginx

    - name: Sync website files from S3
      amazon.aws.aws_s3:
        bucket: technova-static-site
        mode: list
      register: s3_files

    - name: Alert if config drift was detected and fixed
      community.general.slack:
        token: "{{ vault_slack_token }}"
        msg: "⚠️ Config drift FIXED on {{ inventory_hostname }}"
        channel: "#devops-alerts"
      when: nginx_conf_result.changed
      delegate_to: localhost

  handlers:
    - name: Reload Nginx
      service: name=nginx state=reloaded

🎯 Interview Q&A
Q: How does Ansible detect and fix configuration drift?
Ansible's template and copy modules compare the desired state (from your playbook) to the current state on the server. If they differ, status = "changed" — Ansible overwrites with the correct config. Running the same playbook hourly via Tower creates a continuous drift correction loop — any manual change is reverted within one hour.

Automated OS Patching with Pre/Post Health Checks
Patch 100 EC2 instances every Sunday at 3 AM with rolling updates — automatically remove from ALB before patching, verify health after reboot, re-add to ALB. Zero manual steps, zero downtime.
EC2ALBapt/yum RollingRebootTower
📖 Real Company Story
A fintech company has 100 EC2 instances that need monthly OS security patches. Previously, an ops team worked through the night manually patching servers one by one. Once they forgot to remove a server from the ALB before rebooting — customers hit 502 errors for 4 minutes. Your job: fully automate patching with proper ALB lifecycle management and a rollback if any server doesn't come back healthy after reboot.
🔧 Core Playbook
os_patching.yml
---
- name: Rolling OS Patch — Fintech Production
  hosts: tag_Patching_enabled
  become: true
  serial: "10%"
  max_fail_percentage: 10

  tasks:
    - name: Deregister from ALB target group
      amazon.aws.elb_target:
        target_group_arn: "{{ vault_tg_arn }}"
        target_id: "{{ ansible_ec2_instance_id }}"
        state: absent
        deregister_targets_in_s_deregistration_delay: 30
      delegate_to: localhost

    - name: Apply all security patches
      apt:
        upgrade: safe        # only security patches
        update_cache: yes
      register: patch_result

    - name: Reboot if kernel was updated
      reboot:
        reboot_timeout: 180
        post_reboot_delay: 30
        msg: "Rebooting for OS patch — Ansible managed"
      when: patch_result.changed

    - name: Wait for app port 8080 to be ready
      wait_for:
        port: 8080
        host: localhost
        timeout: 120
        state: started

    - name: Re-register to ALB (only if healthy)
      amazon.aws.elb_target:
        target_group_arn: "{{ vault_tg_arn }}"
        target_id: "{{ ansible_ec2_instance_id }}"
        state: present
      delegate_to: localhost

🎯 Interview Q&A
Q: How do you patch EC2 instances without downtime?
Use Ansible's serial keyword to patch servers in batches (e.g., 10% at a time). Before patching each batch: deregister from ALB so traffic stops going to them. Patch and reboot. Verify the app is healthy on the expected port. Then re-register to ALB. At any time, 90% of servers are serving traffic. max_fail_percentage aborts if too many servers fail to come back healthy.

Golden AMI Builder — Pre-baked AWS Machine Images
Use Ansible to build a "golden" AWS AMI — a pre-configured machine image with all software, security settings, and agents pre-installed. New EC2 instances launch ready to serve in under 90 seconds.

build_golden_ami.yml

  vars:

Automated RDS Backup, Verification & Disaster Recovery
Automatically snapshot RDS databases, verify backups are restorable by actually restoring them to a test instance, run data integrity checks, then terminate the test instance. Full DR testing on autopilot.
RDSS3mysqldump DR TestingTowerPagerDuty
📖 Real Company Story
A healthcare company had daily RDS snapshots but never tested them. When a data corruption incident happened, they tried restoring the snapshot — it was corrupt. 6 hours of data lost. Regulators were not happy. Your job: build automated DR testing that restores every backup to a test RDS instance, queries key tables to verify data integrity, generates a compliance report, and alerts via PagerDuty if any backup fails verification.
🔧 Core Playbook
rds_backup_verify.yml
---
- name: RDS Backup Verification — DR Testing
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    source_db_id: technova-prod-db
    test_db_id: "technova-dr-test-{{ ansible_date_time.epoch }}"

  tasks:
    - name: Get latest automated RDS snapshot
      amazon.aws.rds_snapshot_info:
        db_instance_identifier: "{{ source_db_id }}"
        snapshot_type: automated
      register: snapshots

    - name: Set latest snapshot ID
      set_fact:
        latest_snapshot: "{{ snapshots.snapshots | sort(attribute='snapshot_create_time') | last }}"

    - name: Restore snapshot to test RDS instance
      amazon.aws.rds_instance:
        id: "{{ test_db_id }}"
        creation_source: snapshot
        snapshot_identifier: "{{ latest_snapshot.db_snapshot_identifier }}"
        db_instance_class: db.t3.medium
        state: present
        wait: yes
        wait_timeout: 900   # 15 min for restore to complete

    - name: Run data integrity checks on restored DB
      community.mysql.mysql_query:
        login_host: "{{ test_db_endpoint }}"
        login_user: admin
        login_password: "{{ vault_db_password }}"
        query: "SELECT COUNT(*) as row_count FROM patients WHERE created_at > DATE_SUB(NOW(), INTERVAL 24 HOUR)"
      register: integrity_check

    - name: Fail if no recent records found (corrupt backup)
      assert:
        that: "integrity_check.query_result[0][0].row_count | int > 0"
        fail_msg: "CRITICAL: Backup may be corrupt — no recent records!"

    - name: Terminate test DB instance (cleanup)
      amazon.aws.rds_instance:
        id: "{{ test_db_id }}"
        state: absent
        skip_final_snapshot: yes
📋 What You Learn
  • rds_snapshot_info and rds_instance modules
  • Jinja2 filters: sort() | last for latest snapshot
  • mysql_query module for data integrity verification
  • assert module for compliance-based failure conditions
  • Tower PagerDuty integration on failure
🎯 Interview Q&A
Q: How do you test database backups automatically with Ansible?
The playbook finds the latest RDS snapshot, restores it to a temporary test instance (separate from production), runs SQL queries to verify data integrity (row counts, recent records), asserts the results meet expected thresholds, generates a compliance report, and terminates the test instance. If any assertion fails, Tower notifies PagerDuty. This gives you verified backups with zero manual effort.

EKS Cluster Bootstrap & App Deployment via Ansible
Use Ansible to configure an existing EKS cluster — install cluster addons (metrics-server, AWS load balancer controller, Cluster Autoscaler), deploy namespaces, RBAC, and push your microservices via Kubernetes manifests.
EKSKubernetes HelmkubectlTower
📖 Real Company Story
A SaaS company's DevOps team uses Terraform to create EKS clusters but then manually kubectl-applies 40 YAML files for addons, RBAC, and initial deployments. Setting up a new environment takes half a day of error-prone manual steps. Your job: use Ansible to fully bootstrap an EKS cluster after Terraform creates it — reproducible, automated, idempotent cluster configuration in 10 minutes.
🔧 Core Playbook
eks_bootstrap.yml
---
- name: Bootstrap EKS Cluster — TechNova SaaS
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    cluster_name: technova-eks-prod
    aws_region: ap-south-1
    namespaces: [frontend, backend, monitoring, staging]

  tasks:
    - name: Update kubeconfig for EKS cluster
      command: aws eks update-kubeconfig --name {{ cluster_name }} --region {{ aws_region }}

    - name: Create application namespaces
      kubernetes.core.k8s:
        api_version: v1
        kind: Namespace
        name: "{{ item }}"
        state: present
      loop: "{{ namespaces }}"

    - name: Install metrics-server via Helm
      kubernetes.core.helm:
        name: metrics-server
        chart_ref: metrics-server/metrics-server
        release_namespace: kube-system
        state: present
        values:
          replicas: 2

    - name: Install AWS Load Balancer Controller
      kubernetes.core.helm:
        name: aws-load-balancer-controller
        chart_ref: eks/aws-load-balancer-controller
        release_namespace: kube-system
        values:
          clusterName: "{{ cluster_name }}"
          serviceAccount.create: false
          serviceAccount.name: aws-load-balancer-controller

    - name: Deploy TechNova microservices
      kubernetes.core.k8s:
        src: "k8s/{{ item }}.yml"
        state: present
      loop:
        - frontend-deployment
        - backend-deployment
        - redis-statefulset
📋 What You Learn
  • kubernetes.core collection — k8s and helm modules
  • EKS kubeconfig management via Ansible
  • Helm chart installation with value overrides
  • Namespace and RBAC management from Ansible
  • Tower workflow: Terraform EKS → Ansible Bootstrap → Deploy
🎯 Interview Q&A
Q: Why use Ansible to manage Kubernetes instead of just kubectl/Helm directly?
Ansible adds idempotency, variable management, secret handling (Vault), and Tower integration. You can run the same EKS bootstrap playbook on any cluster and get identical results. Secrets like image pull credentials and TLS certs are encrypted with Vault. Tower provides audit trail, RBAC (devs can run deploy jobs, not cluster admin jobs), and scheduling. Pure kubectl scripts lack all of these enterprise-grade features.

Automated Linux User Lifecycle Management Across AWS Fleet
Onboard new engineers (create Linux users, set up SSH keys, assign groups) and offboard departing engineers (revoke access, delete keys, disable accounts) across all EC2 instances automatically from a single source of truth.
EC2IAMSSH Keys authorized_keysTower
📖 Real Company Story
An IT company has 150 EC2 instances. When a developer joins, the ops team manually SSHes into each relevant server and creates the user. When someone leaves, they miss 3 servers — the ex-employee's SSH key remains valid on production for weeks. Security audit finds this. Your job: single YAML file defines all users. Ansible enforces it across all servers. Add a user in the YAML → instantly provisioned. Remove them → instantly revoked everywhere.
🔧 Core Playbook
user_management.yml
---
- name: User Lifecycle Management — All EC2 Instances
  hosts: all
  become: true
  vars_files:
    - users/active_users.yml      # single source of truth
    - users/offboarded_users.yml  # employees who left

  tasks:
    - name: Create active user accounts
      user:
        name: "{{ item.username }}"
        groups: "{{ item.groups | join(',') }}"
        shell: /bin/bash
        state: present
        create_home: yes
        comment: "{{ item.full_name }} — {{ item.team }}"
      loop: "{{ active_users }}"

    - name: Set authorized SSH key for each active user
      authorized_key:
        user: "{{ item.username }}"
        key: "{{ item.ssh_public_key }}"
        state: present
        exclusive: true  # remove any OTHER keys not in this list
      loop: "{{ active_users }}"

    - name: OFFBOARD — Lock and expire departed users
      user:
        name: "{{ item.username }}"
        password_lock: yes
        expires: 1   # expires Jan 1 1970 = immediately expired
        shell: /sbin/nologin
      loop: "{{ offboarded_users }}"

    - name: Remove SSH keys for offboarded users
      authorized_key:
        user: "{{ item.username }}"
        key: ""
        state: absent
      loop: "{{ offboarded_users }}"
📋 What You Learn
  • user and authorized_key modules for lifecycle management
  • exclusive: true to prevent unauthorized SSH keys
  • vars_files for separating active vs offboarded users
  • Tower triggered by HR system webhook on employee status change
  • Compliance reporting via Tower job history
🎯 Interview Q&A
Q: How do you ensure a departed employee's access is revoked across all servers instantly?
A single YAML file defines all authorized users with their SSH public keys. When an employee leaves, their entry moves from active_users.yml to offboarded_users.yml. Tower is triggered via a webhook (from HR system) which runs the user management playbook. The authorized_key module with exclusive:true removes their key and the user module with password_lock:yes blocks login. All 150 servers are updated in parallel within 2 minutes.

Full Observability Stack Deployment — CloudWatch + Prometheus + Grafana
Deploy and configure a complete monitoring stack across your AWS fleet — CloudWatch agent on all EC2s, Prometheus node exporters, Grafana dashboards — from a single Ansible run. No more manual agent installation.
CloudWatchPrometheus GrafanaNode ExporterTower

observability_stack.yml
---
- name: Deploy Observability Stack — All EC2 Instances
  hosts: all
  become: true

  roles:

Blue-Green Deployment with Instant Rollback on AWS ALB
Maintain two identical production environments (Blue and Green). Deploy new version to inactive environment, run health checks, then flip the ALB to send 100% traffic to the new version. Rollback is a 10-second ALB switch.
ALBTarget Groups Blue-GreenRoute53Tower Workflow
📖 Real Company Story
A payment gateway company cannot afford any downtime during deployments. Their previous rolling deploys caused 2-minute windows where some users hit old code and some hit new code — causing session inconsistencies in payment flows. Your job: implement blue-green deployment where the switch is instantaneous. If the new version has any issue, rollback is a single click that completes in 10 seconds.
🔧 Core Playbook
blue_green_deploy.yml
---
- name: Blue-Green Deployment — Payment Gateway
  hosts: localhost
  connection: local

  vars:
    alb_arn: "{{ vault_alb_arn }}"
    blue_tg_arn: "{{ vault_blue_tg_arn }}"
    green_tg_arn: "{{ vault_green_tg_arn }}"

  tasks:
    - name: Determine which environment is currently LIVE
      amazon.aws.elb_listener_info:
        load_balancer_arn: "{{ alb_arn }}"
      register: listeners

    - name: Set active and inactive environments
      set_fact:
        active_env: "{{ 'blue' if listeners.listeners[0].default_actions[0].target_group_arn == blue_tg_arn else 'green' }}"
        inactive_env: "{{ 'green' if listeners.listeners[0].default_actions[0].target_group_arn == blue_tg_arn else 'blue' }}"

    - name: Deploy new version to INACTIVE environment
      include_playbook: deploy_to_env.yml
      vars:
        target_env: "{{ inactive_env }}"
        app_version: "{{ new_version }}"

    - name: Health check — inactive env MUST pass before switching
      uri:
        url: "http://{{ inactive_env }}-internal.technova.com/health"
        status_code: 200
      retries: 10
      delay: 15
      until: health_check.status == 200
      register: health_check

    - name: SWITCH — point ALB to new environment (the actual flip)
      amazon.aws.elb_listener:
        load_balancer_arn: "{{ alb_arn }}"
        protocol: HTTPS
        port: 443
        default_actions:
          - Type: forward
            TargetGroupArn: "{{ green_tg_arn if active_env == 'blue' else blue_tg_arn }}"
        state: present

    - name: ROLLBACK playbook — run separately if needed
      debug:
        msg: "To rollback: run rollback.yml — switches ALB back in 10 seconds"

📋 What You Learn
  • elb_listener module for ALB target group switching
  • Dynamic set_fact to determine blue vs green state
  • Jinja2 ternary expressions for environment selection
  • Tower Workflow with Approval node for production switch
  • Instant rollback via separate Job Template
🎯 Interview Q&A
Q: Explain Blue-Green deployment and how you implement rollback.
Blue and Green are two identical production environments. At any time, one is live (receiving ALB traffic) and one is idle. Deploy to the idle environment, run health checks, then switch the ALB listener to point to it. Rollback is simply switching the ALB back to the previous environment — takes 10 seconds with zero redeployment needed. The old version is still running and healthy on the previous environment.

Automated SSL Certificate Lifecycle — Let's Encrypt + ACM
Automatically issue, renew, and deploy SSL certificates to all web servers using Let's Encrypt with Route53 DNS challenge. Never have a certificate expiry incident again — certificates auto-renew 30 days before expiry.
Let's EncryptRoute53 ACMACMETower Schedule
📖 Real Company Story
An online marketplace's SSL certificate expired at 3 AM on a Saturday. All browsers showed "Not Secure" warnings. Customer trust evaporated. Sales dropped 60% until an engineer manually renewed the cert 4 hours later. The cert had been manually managed in a spreadsheet. Your job: automate SSL lifecycle completely — issue certs via Let's Encrypt, deploy to Nginx, import to ACM, and schedule auto-renewal.
🔧 Core Playbook
ssl_cert_lifecycle.yml
---
- name: SSL Certificate Lifecycle Management
  hosts: localhost
  connection: local

  vars:
    domains:
      - technova.com
      - www.technova.com
      - api.technova.com
    cert_email: devops@technova.com
    cert_dir: /etc/letsencrypt/live/technova.com

  tasks:
    - name: Check certificate expiry (days remaining)
      community.crypto.x509_certificate_info:
        path: "{{ cert_dir }}/cert.pem"
      register: cert_info
      ignore_errors: yes   # cert might not exist yet

    - name: Calculate days until expiry
      set_fact:
        days_until_expiry: "{{ ((cert_info.not_after | to_datetime('%Y%m%d%H%M%SZ')) - (ansible_date_time.iso8601 | to_datetime('%Y-%m-%dT%H:%M:%SZ'))).days }}"
      when: cert_info is not failed

    - name: Issue/Renew certificate via ACME DNS challenge
      community.crypto.acme_certificate:
        account_key_src: /etc/letsencrypt/account.key
        csr: /etc/letsencrypt/technova.csr
        dest: "{{ cert_dir }}/cert.pem"
        chain_dest: "{{ cert_dir }}/chain.pem"
        acme_directory: https://acme-v02.api.letsencrypt.org/directory
        acme_version: 2
        challenge: dns-01
      when: cert_info is failed or days_until_expiry | int < 30
      register: cert_challenge

    - name: Create Route53 DNS TXT record for ACME challenge
      amazon.aws.route53:
        zone: technova.com
        record: "_acme-challenge.{{ item.key }}"
        type: TXT
        value: "{{ item.value['dns-01'].resource_value }}"
        state: present
      loop: "{{ cert_challenge.challenge_data | dict2items }}"
      when: cert_challenge.changed

    - name: Import new certificate to AWS ACM
      amazon.aws.aws_acm:

lambda_trigger_tower.py (the bridge)
import boto3, json, urllib3, os

def lambda_handler(event, context):
    # EventBridge sends EC2 instance details here
    instance_id = event['detail']['EC2InstanceId']

    # Get instance private IP from EC2 API
    ec2 = boto3.client('ec2')
    response = ec2.describe_instances(InstanceIds=[instance_id])
    private_ip = response['Reservations'][0]['Instances'][0]['PrivateIpAddress']

    # Trigger Tower Job Template via REST API
    tower_url = f"{os.environ['TOWER_HOST']}/api/v2/job_templates/{os.environ['TEMPLATE_ID']}/launch/"
    token = os.environ['TOWER_TOKEN']  # from Secrets Manager

    payload = json.dumps({
        "limit": private_ip,  # target only this specific new instance
        "extra_vars": {
            "new_instance_id": instance_id,
            "new_instance_ip": private_ip
        }
    })

    http = urllib3.PoolManager()
    resp = http.request('POST', tower_url,
        body=payload,
        headers={
            'Authorization': f'Bearer {token}',
            'Content-Type': 'application/json'
        })

    return {'statusCode': 200, 'body': resp.data.decode()}

Multi-Region Disaster Recovery Failover Automation
Automate complete DR failover from Mumbai (ap-south-1) to Singapore (ap-southeast-1) — promote read replica to primary, update Route53 DNS, validate all services, and send incident report. Full region failover in under 10 minutes via Tower one-click.

📖 Real Company Story
A supply chain company's Mumbai AWS region had an unexpected outage (not a full AWS outage — their VPC was misconfigured during a routine change). They had a Singapore DR environment but failing over required 15 manual steps across AWS console, DNS provider, and internal systems — documented in a 20-page runbook. It took 47 minutes. Your job: encode the entire DR runbook into an Ansible Tower Workflow. Failover becomes a single click, completing in under 10 minutes, with zero steps missed.
🔧 DR Failover Playbook
dr_failover.yml
---
- name: DR Failover — Mumbai to Singapore
  hosts: localhost
  connection: local
  gather_facts: true

  vars:
    primary_region: ap-south-1
    dr_region: ap-southeast-1
    primary_db: technova-prod-mumbai
    replica_db: technova-replica-singapore

  tasks:
    - name: STEP 1 — Verify primary region is truly unreachable
      uri:
        url: https://health.technova.com
        timeout: 10
      register: primary_health
      ignore_errors: yes

    - name: Abort if primary is actually reachable (false alarm)
      fail:
        msg: "Primary is REACHABLE — aborting DR failover to prevent split-brain!"
      when: primary_health.status is defined and primary_health.status == 200

    - name: STEP 2 — Promote Singapore RDS replica to primary
      amazon.aws.rds_instance:
        id: "{{ replica_db }}"
        region: "{{ dr_region }}"
        read_replica: false   # breaks replication, promotes to standalone
        state: present
        wait: yes
      register: promoted_db

    - name: STEP 3 — Scale up Singapore EC2 ASG to full capacity
      amazon.aws.autoscaling_group:
        name: technova-web-sg-asg
        region: "{{ dr_region }}"
        min_size: 10
        max_size: 50
        desired_capacity: 20

    - name: STEP 4 — Wait for Singapore instances to be healthy
      pause:
        seconds: 120
        prompt: "Waiting 2 minutes for Singapore ASG to scale up..."

    - name: STEP 5 — Verify Singapore app health
      uri:
        url: https://sg-internal.technova.com/health
        status_code: 200
      retries: 10
      delay: 15

    - name: STEP 6 — Switch Route53 to Singapore (the actual failover)
      amazon.aws.route53:
        zone: technova.com
        record: www.technova.com
        type: A
        value: "{{ sg_alb_ip }}"  # Singapore ALB IP
        ttl: 60   # low TTL for fast propagation
        state: present
        alias: true

    - name: STEP 7 — Send DR incident report to all stakeholders
      community.general.mail:
        to:
          - cto@technova.com
          - operations@technova.com
          - oncall@technova.com
        subject: "🚨 DR FAILOVER COMPLETED — {{ ansible_date_time.iso8601 }}"
        body: |
          DR Failover completed at {{ ansible_date_time.iso8601 }}
          Primary region {{ primary_region }}: UNREACHABLE
          DR region {{ dr_region }}: ACTIVE
          RDS replica promoted: {{ promoted_db.endpoint.address }}
          DNS updated: www.technova.com → Singapore ALB
          Action required: Investigate Mumbai outage
        host: "{{ vault_smtp_host }}"
