What Exactly is Ansible?

🧠 Core Concept

Ansible is an open-source IT automation tool built by Red Hat. It is written in Python and uses SSH to connect to your servers and execute tasks.

Think of Ansible like this: Imagine you are a manager who has 200 workers (servers). Instead of calling each worker one by one and giving them instructions, you write down all the instructions on a paper (called a Playbook) and give it to your assistant (Ansible). Your assistant then goes to all 200 workers simultaneously, reads the instructions, and makes sure every worker does exactly what is written — and if a worker has already done something, the assistant skips that step for them.

Key Terms — Know These for Interviews

Ansible Key Terminology
TermWhat It Means — Simple Explanation
Control Node The machine where Ansible is installed. This is YOUR machine or a dedicated automation server. Ansible runs FROM here. This is the "manager" machine.
Managed Node The target servers that Ansible configures. These are your 200 TechNova servers. You do NOT install Ansible on these — they only need Python (usually already there) and SSH access.
Agentless Ansible does NOT require you to install any agent/software on managed nodes. It connects using plain SSH — same way you manually SSH into servers. This makes setup extremely simple.
Inventory A file listing all your managed nodes (servers). Like an address book — you list all server IPs/hostnames and group them (webservers, appservers, dbservers).
Playbook A YAML file containing a set of tasks to run on servers. This is your "automation script" — but written in simple, readable YAML instead of complex Bash.
Module A pre-built function in Ansible that does a specific job — like installing packages (apt), managing services (service), copying files (copy). Ansible has 3000+ modules.
Task A single action in a Playbook — like "install Nginx" or "start the service". Each task calls one Module with parameters.
Idempotent Most important concept! Running a playbook 10 times gives the same result as running it once. If Nginx is already installed, Ansible won't install it again. It checks current state first and only acts if a change is needed. This prevents duplication and makes automation safe.
YAML YAML Ain't Markup Language — the file format Ansible uses for playbooks and inventory. Uses indentation (spaces, not tabs!) to show structure. Very human-readable — like writing a list of instructions in English.
🧠 Step-by-Step: What Happens When You Run Ansible

When you run ansible-playbook playbook.yml, this is what happens internally:

  • Step 1 — Read Inventory: Ansible reads your inventory file to know which servers to target and their IPs.
  • Step 2 — Read Playbook: Ansible reads your YAML playbook to understand what tasks to run and in what order.
  • Step 3 — Gather Facts: Ansible SSHes into each server and runs the setup module to collect server info (OS, RAM, CPU, network). These are called "Facts".
  • Step 4 — Execute Tasks: For each task in the playbook, Ansible writes a small Python script to a temp directory on the remote server, executes it, reads the output, then deletes the temp file.
  • Step 5 — Report Results: For every task on every server, Ansible tells you: OK (no change needed), Changed (change was made), or Failed.
  • Step 6 — Run Handlers: If any task triggered a notification (like "restart Nginx"), handlers run now, at the end.

# "apt"   = Ubuntu's package manager (like a software store)

# ====================================================
sudo apt update

# STEP 2: Install software-properties-common
# This gives us the "add-apt-repository" command
# Without this, we cannot add custom repositories
# "-y" means "yes to all prompts — don't ask me to confirm"
# ====================================================
sudo apt install software-properties-common -y

# ====================================================
# STEP 3: Add the official Ansible PPA repository
# PPA = Personal Package Archive
# Ubuntu's default repo has an OLDER version of Ansible
# This PPA gives us the LATEST version directly from Ansible
# "--yes"    = auto-confirm adding the repo
# "--update" = refresh package list immediately after adding
# "ppa:ansible/ansible" = the official Ansible PPA address
# ====================================================
sudo add-apt-repository --yes --update ppa:ansible/ansible

# ====================================================
# STEP 4: Install Ansible
# Now that we have the correct repo, we can install it
# ====================================================
sudo apt install ansible -y

# ====================================================
# STEP 5: Verify the installation
# Should output: ansible [core 2.15.x] ...
# This confirms Ansible is installed and shows version
# ====================================================
ansible --version

💡 Important Tip — YAML Indentation Rule

YAML uses spaces for indentation — NEVER tabs. This is the number one mistake beginners make. If you use a tab character instead of spaces, your playbook will fail. Always use 2 spaces per indentation level. Configure your text editor (VS Code, Vim) to convert Tab key to 2 spaces when editing YAML files.

🎯 Interview Questions — Chapter 1
Q1: What is Ansible and what problem does it solve?
Ansible is an open-source IT automation tool from Red Hat used for configuration management, application deployment, and task automation. It solves the problem of manually managing hundreds of servers — instead of SSHing into each server one by one, you write a single YAML playbook describing what you want, and Ansible applies it to all servers simultaneously using SSH.
Q2: Why is Ansible called agentless and what is the benefit?
Ansible is called agentless because it does NOT require any software or agent to be pre-installed on the target servers. It uses SSH (which is already enabled on most Linux servers) to connect and execute tasks. The benefit: no setup overhead on managed nodes, no ports to open beyond SSH, no agent version compatibility issues, and no security concerns from running a persistent agent process on every server.
Q3: What is idempotency in Ansible? Give a real example.
Idempotency means running the same operation multiple times produces the same result without side effects. In Ansible, if you have a task to install Nginx (state: present), and Nginx is already installed on the server, Ansible will check first and skip the installation — it will NOT install it again or break the existing installation. You can safely run the same playbook daily without worrying about duplicate installs, file overwrites, or config corruption.
Q4: What is the difference between a Control Node and a Managed Node?
Control Node is the machine where Ansible is installed and from where you run ansible-playbook commands — typically your workstation or a CI/CD server. Managed Nodes are the target servers being configured — Ansible SSHes into these and runs tasks on them. Managed nodes only need Python installed (which Ubuntu/CentOS have by default) and SSH access. No Ansible installation required on managed nodes.
Q5: What happens internally when you run ansible-playbook?
Ansible reads the inventory to identify target servers, reads the playbook for tasks, then SSHes into each managed node. For each task, Ansible writes a temporary Python script to the remote server's /tmp directory, executes it, captures the output (OK, Changed, or Failed), deletes the temp script, and reports the result. This happens for every task on every server.

📖 The TechNova Story — Chapter 2

Ravi gives you a spreadsheet with 200 server IPs. He says:

"Puneeth, these 50 IPs are web servers running Nginx. These 80 IPs are app servers running our Java app. These 70 IPs are database servers running MySQL. Some servers are in Production, some in Staging, some in Dev. We need to be able to run commands on all web servers together, or all production servers together, or just one specific server."

You need a way to tell Ansible about all these servers and their groupings. That is the Inventory file.

🧠 What is an Inventory File?

An Inventory file is a list of all your servers that Ansible will manage. It tells Ansible:

1. Where are your servers? (IP addresses or hostnames)
2. How to group them? (webservers, appservers, dbservers)
3. How to connect? (which SSH user, which key, which port)
4. What variables apply? (per host or per group)

Inventory files can be in INI format (.ini — like a config file) or YAML format (.yml). INI is simpler to read for beginners. We will learn both.

🔧 Lab — Create Your First Inventory File
inventory/hosts.ini — TechNova Complete Inventory 
# ============================================
# TECHNOVA SYSTEMS — ANSIBLE INVENTORY FILE
# ============================================
# Lines starting with # are comments — Ansible ignores them
# Square brackets [ ] define a GROUP NAME

# ---- WEB SERVERS GROUP ----
# All servers listed under [webservers] belong to this group
[webservers]
web01 ansible_host=192.168.1.10 ansible_user=ubuntu
web02 ansible_host=192.168.1.11 ansible_user=ubuntu
web03 ansible_host=192.168.1.12 ansible_user=ubuntu

# ---- APP SERVERS GROUP ----
[appservers]
app01 ansible_host=192.168.1.20 ansible_user=ubuntu
app02 ansible_host=192.168.1.21 ansible_user=ubuntu
app03 ansible_host=192.168.1.22 ansible_user=ubuntu

# ---- DATABASE SERVERS GROUP ----
[dbservers]
db01  ansible_host=192.168.1.30 ansible_user=ubuntu ansible_port=22
db02  ansible_host=192.168.1.31 ansible_user=ubuntu ansible_port=22

# ---- GROUP OF GROUPS ----
# ":children" means this group CONTAINS other groups
# "production" group = ALL servers from all three groups below
[production:children]
webservers
appservers
dbservers

# ---- GROUP VARIABLES ----
# ":vars" sets variables for ALL servers in that group
# Every server in [webservers] automatically gets http_port=80
[webservers:vars]
http_port=80
app_env=production
nginx_version=latest

[dbservers:vars]
mysql_port=3306
db_name=technova_db

Word-by-Word — Every Line Explained

Line-by-line explanation
Line / KeywordWhat It Means — Full Explanation
[webservers] Group definition. Square brackets define a group name. Any server listed BELOW this line (until the next [group]) is part of this group. Group names can be anything — webservers, web_prod, tier1, etc. This is what you reference in playbooks with hosts: webservers.
web01 Server alias / nickname. This is NOT the actual IP — it is the name you give this server in Ansible. It appears in output messages. You can name it anything: web01, prod-nginx-01, server-mumbai. Ansible uses the alias in reports.
ansible_host=192.168.1.10 The actual IP address or DNS hostname that Ansible will SSH into. This is the real address of your server. Without this, Ansible tries to SSH to "web01" which won't resolve.
ansible_user=ubuntu The SSH username Ansible uses to log in. For AWS EC2 with Ubuntu, this is always ubuntu. For Amazon Linux 2, it is ec2-user. For CentOS, it is centos. For your own VMs, it might be root or your username.
ansible_port=22 SSH port number. Default is 22. If your server uses a non-standard SSH port (like 2222 for security), specify it here. You only need to write this if the port is NOT 22.
[production:children] Group of Groups. The :children suffix means "this group contains other groups as its members". So "production" is a parent group containing webservers, appservers, and dbservers. When you run a playbook targeting "production", it runs on ALL servers from all three child groups.
[webservers:vars] Group variables. The :vars suffix means "these are variables that apply to every server in the webservers group". Any variable defined here is automatically available in playbooks running on webservers. No need to define it in the playbook itself.
http_port=80 A variable definition. This creates a variable named http_port with value 80. In playbooks, you can reference it as {{ http_port }} and it will substitute to 80 for all webservers.

Pro Tip — ansible.cfg Configuration File

💡 Tip — Set Default Inventory in ansible.cfg

Instead of typing -i inventory/hosts.ini every single time, you can create an ansible.cfg file in your project directory. Ansible automatically reads it.

ansible.cfg — project configuration file 
# ansible.cfg — Ansible reads this automatically
# Place this in the ROOT of your project directory

[defaults]
# Default inventory file — no need to type -i every time
inventory = inventory/hosts.ini

# Default SSH user — no need to set ansible_user in inventory
remote_user = ubuntu

# Path to your SSH private key
private_key_file = ~/.ssh/technova-key.pem

# Don't check SSH host key fingerprint (useful for new servers)
# In production, set this to True for security
host_key_checking = False

# Number of servers to connect to in parallel
forks = 10

# Retry failed hosts — saves to a .retry file
retry_files_enabled = True

[privilege_escalation]
# Become sudo by default for all tasks
become = True
become_method = sudo
become_user = root
🎯 Interview Questions — Chapter 2
Q1: What is an Ansible Inventory and what are the two common formats?
An Ansible Inventory is a file that lists all the servers (managed nodes) that Ansible will manage, along with their connection details and group memberships. The two formats are: INI format (uses square brackets for groups, simple key=value pairs — easier to read for beginners) and YAML format (uses YAML structure — more flexible, supports complex nested variables, preferred in modern projects).
Q2: What is [group:children] used for in Ansible inventory?
The :children suffix creates a parent group that contains other groups. For example, [production:children] with webservers, appservers, and dbservers listed means "production" is an umbrella group. When you run a playbook targeting "production", it runs on every server across all three child groups. This is useful for running tasks on all production servers with one command.
Q3: What is the difference between static and dynamic inventory?
Static inventory is a file you write manually — you hard-code all server IPs and groups. Works well when server count is fixed. Dynamic inventory uses a plugin or script that queries a cloud provider (like AWS EC2, GCP, Azure) at runtime and automatically returns the current list of running servers. When Auto Scaling adds new EC2 instances, dynamic inventory picks them up automatically without any file changes.
Q4: What connection variables does Ansible support in inventory?
Key Ansible connection variables: ansible_host (actual IP/hostname), ansible_user (SSH username), ansible_port (SSH port, default 22), ansible_ssh_private_key_file (path to PEM file), ansible_password (SSH password — use vault to encrypt this), ansible_become (true/false for sudo), ansible_connection (ssh, local, winrm, docker).

🧠 What are Ad-hoc Commands?

Ad-hoc commands are single-line Ansible commands that run a specific task on one or more servers without writing a playbook. Think of them as "quick fire" automation — useful for one-time tasks, emergency fixes, information gathering, or testing a module before putting it in a playbook.

Syntax: ansible [target] -i [inventory] -m [module] -a "[arguments]" [options]

The Ad-hoc Command Syntax — Every Part Explained

Anatomy of an ad-hoc command
PartExampleMeaning
ansible ansible The ansible command for running ad-hoc tasks (different from ansible-playbook which runs YAML files)
[target] webservers Which servers to target. Can be: a group name (webservers), a single host (web01), all hosts (all), or a pattern (web*)
-i -i inventory/hosts.ini Path to your inventory file. Short for --inventory. If ansible.cfg has inventory set, you can skip this.
-m -m ping Module to use. Short for --module-name. Every Ansible task uses a module. "ping" tests connectivity. "apt" installs packages. "service" manages services.
-a -a "name=nginx state=present" Arguments to pass to the module. Short for --args. Parameters the module needs to do its job. In quotes if multiple args.
--become --become Become root (sudo). Required for system-level operations like installing packages, managing services, writing to /etc/. Without this, you'll get "Permission denied".
-b -b Short form of --become. Same thing — use whichever you prefer.
-f -f 20 Forks — number of parallel connections. Default is 5. Use -f 50 to connect to 50 servers at the same time.

Hands-on Lab — All Essential Ad-hoc Commands

🔧 Lab — Run These and Understand Each
terminal — ad-hoc command reference 
# ==================================================
# 1. PING MODULE — Test if servers are reachable
# This is NOT an ICMP ping. It tests SSH connectivity
# and that Ansible can execute on the remote server.
# ==================================================
ansible all -i inventory/hosts.ini -m ping

# Ping only one specific server
ansible web01 -i inventory/hosts.ini -m ping

# Ping using a pattern — all hosts starting with "web"
ansible "web*" -i inventory/hosts.ini -m ping


# ==================================================
# 2. SHELL MODULE — Run any shell command
# Runs through /bin/sh — can use pipes, redirects
# ==================================================

# Check uptime on all web servers
ansible webservers -i inventory/hosts.ini -m shell -a "uptime"

# Check disk space
ansible all -i inventory/hosts.ini -m shell -a "df -h"

# Check free memory
ansible all -i inventory/hosts.ini -m shell -a "free -m"

# Delete old log files — emergency fix!
ansible webservers -i inventory/hosts.ini -m shell \
  -a "find /var/log/app -name '*.log' -mtime +7 -delete" --become

# Check which processes are running
ansible all -i inventory/hosts.ini -m shell -a "ps aux | grep nginx"


# ==================================================
# 3. APT MODULE — Install/remove packages (Ubuntu)
# state=present: install if not already installed
# state=absent: uninstall the package
# state=latest: install OR upgrade to latest version
# --become is REQUIRED for apt (needs root/sudo)
# ==================================================

# Install Nginx on all web servers
ansible webservers -i inventory/hosts.ini \
  -m apt -a "name=nginx state=present update_cache=yes" --become

# Install multiple packages (use loop in playbook for many)
ansible all -i inventory/hosts.ini \
  -m apt -a "name=git state=present" --become

# Uninstall a package
ansible webservers -i inventory/hosts.ini \
  -m apt -a "name=apache2 state=absent" --become


# ==================================================
# 4. SERVICE MODULE — Manage system services
# state=started: start the service if not running
# state=stopped: stop the service if running
# state=restarted: stop and start (even if running)
# state=reloaded: reload config without full restart
# enabled=yes: start service on server boot
# ==================================================

# Start and enable Nginx
ansible webservers -i inventory/hosts.ini \
  -m service -a "name=nginx state=started enabled=yes" --become

# Restart Nginx on all web servers
ansible webservers -i inventory/hosts.ini \
  -m service -a "name=nginx state=restarted" --become

# Stop MySQL on db servers
ansible dbservers -i inventory/hosts.ini \
  -m service -a "name=mysql state=stopped" --become


# ==================================================
# 5. COPY MODULE — Copy files from control to managed
# src: file on YOUR machine (control node)
# dest: where to put it on the remote server
# mode: file permissions (like chmod)
# owner: who owns the file on remote server
# ==================================================

# Copy a config file to all web servers
ansible webservers -i inventory/hosts.ini \
  -m copy -a "src=/tmp/nginx.conf dest=/etc/nginx/nginx.conf owner=root mode=0644" --become

# Write content directly to a file (no src file needed)
ansible all -i inventory/hosts.ini \
  -m copy -a "content='Hello from Ansible\n' dest=/tmp/test.txt"


# ==================================================
# 6. FETCH MODULE — Copy files FROM server TO you
# Opposite of copy — pulls files FROM managed nodes
# ==================================================

# Fetch /var/log/nginx/error.log from all web servers
ansible webservers -i inventory/hosts.ini \
  -m fetch -a "src=/var/log/nginx/error.log dest=/tmp/logs/"


# ==================================================
# 7. FILE MODULE — Manage files, dirs, permissions
# state=directory: create a directory
# state=file: ensure file exists with permissions
# state=absent: delete file or directory
# state=link: create a symbolic link
# ==================================================

# Create a directory on all servers
ansible all -i inventory/hosts.ini \
  -m file -a "path=/opt/technova state=directory owner=ubuntu mode=0755" --become

# Delete a file on all servers
ansible all -i inventory/hosts.ini \

🎯 Interview Questions — Chapter 3
Q1: What is the difference between an ad-hoc command and a playbook?
Ad-hoc commands are single-line commands for quick, one-time tasks — like checking disk space, emergency log cleanup, or testing a module. Playbooks are YAML files for repeatable, documented, multi-step automation — used in CI/CD pipelines, configuration management, and anything that needs consistency over time. If you will run it more than once, write a playbook.
Q2: What is the difference between the shell and command modules?
The command module executes programs directly without going through the system shell — so it cannot use pipes (|), redirects (>, <), or shell variables ($HOME). It is safer and preferred for simple commands. The shell module runs commands through /bin/sh — so you CAN use pipes, redirects, and environment variables. Use shell only when you need those shell features; use command for everything else.
Q3: Why do some ad-hoc commands need --become?
--become tells Ansible to escalate privileges using sudo on the remote server. Tasks that require root access — like installing packages with apt, managing system services with systemctl, writing to /etc/ directories — all need --become. Without it, the task fails with "Permission denied" because the SSH user doesn't have root privileges by default.

🧠 YAML Basics — Rules You Must Know

Before writing playbooks, you need to understand YAML's syntax rules:

  • Indentation = Structure: YAML uses spaces (NEVER tabs) to show hierarchy. 2 spaces per level is standard in Ansible.
  • --- at top: Every YAML file starts with three dashes. It means "start of document".
  • - (dash) = List item: A dash before an item means it's part of a list. Playbooks are lists of plays. Tasks are lists of task objects.
  • key: value pairs: Everything in YAML is key-value. name: nginx means key="name", value="nginx".
  • Strings with spaces need quotes: name: "setup nginx web server". Simple words don't need quotes.
  • true/false/yes/no: Boolean values. In Ansible, both work. become: true and become: yes are identical.
  • {{ variable }}: Double curly braces are Jinja2 variable substitution — used in playbooks to insert variable values.

---
# "---" tells YAML parsers this is the start of a YAML document
# Without this, some tools may not recognize the file as YAML

- name: Setup and Configure Nginx on TechNova Web Servers
  # "- name:" starts a new PLAY (a set of tasks for specific hosts)
  # The dash "-" makes this an item in a list (playbooks are lists of plays)
  # "name:" gives this play a human-readable label shown in output

  hosts: webservers
  # "hosts:" tells Ansible WHERE to run this play
  # "webservers" must match a group name in your inventory file
  # Can also be: all, web01, "web*", web01,app01 (comma-separated)

  become: true
  # "become: true" enables privilege escalation (sudo) for ALL tasks in this play
  # This is like running every task with "sudo" in front
  # Required for: apt install, service management, writing to /etc/
  # Without this, you'd need "become: true" on each task individually

  gather_facts: true
  # "gather_facts: true" (default) tells Ansible to collect server info first
  # This runs the "setup" module automatically at the start
  # Collected facts: OS type, IP, RAM, CPU, disk — usable as variables
  # Set to false to skip fact gathering and speed up playbook (when you don't need facts)

  vars:
  # "vars:" block defines variables used within this play
  # These variables can be referenced as {{ variable_name }} in tasks
    nginx_port: 80
    # Simple variable: nginx_port = 80
    # Reference it in tasks as: {{ nginx_port }}
    app_name: "technova-web"
    # String variable with quotes (has a hyphen, so quotes are safer)
    nginx_worker_processes: 4
    # Number of worker processes for Nginx

  tasks:
  # "tasks:" is the list of actions to perform on the target hosts
  # Tasks execute in ORDER — top to bottom, one by one
  # If any task FAILS, Ansible stops on that host (by default)

    - name: Update apt package cache
      # "- name:" starts a new TASK. The dash makes it a list item.
      # "name:" gives a human-readable label shown in output
      # Task names help you understand what failed if something goes wrong
      ansible.builtin.apt:
      # "ansible.builtin.apt:" is the module name (Fully Qualified Collection Name)
      # You can also write just "apt:" (short form — both work)
      # This module manages Ubuntu/Debian packages (like apt-get)
        update_cache: yes
        # update_cache: yes = runs "apt-get update" before this task
        # Refreshes the package list so we know the latest versions
        cache_valid_time: 3600
        # cache_valid_time: 3600 = only update cache if it's older than 3600 seconds (1 hour)
        # This prevents unnecessary "apt update" on every single playbook run
        # If you ran the playbook 10 minutes ago, it skips the update

    - name: Install Nginx web server
      apt:
      # Using short form "apt:" — same as ansible.builtin.apt
        name: nginx
        # "name:" is the package name to install
        # Can also be a list for multiple packages: name: [nginx, curl, git]
        state: present
        # "state: present" = install if not installed, do nothing if already installed
        # This is idempotency in action — running this 100 times is safe
        # Other options: absent (uninstall), latest (upgrade to newest version)

    - name: Create TechNova web root directory
      file:
      # "file" module manages files, directories, and symbolic links
        path: /var/www/technova
        # "path:" is the directory or file path to manage
        state: directory
        # "state: directory" = create this directory if it doesn't exist
        owner: www-data
        # "owner:" sets which Linux user owns this directory
        # www-data is the Nginx user — it needs to read files from here
        group: www-data
        # "group:" sets the group ownership
        mode: '0755'
        # "mode:" sets file permissions in octal format
        # 0755 = owner:rwx, group:r-x, others:r-x
        # Always use quotes for mode to avoid YAML treating it as a number

    - name: Deploy TechNova index.html homepage
      copy:
      # "copy" module copies files from control node to managed nodes
        content: |
          # "content:" lets you write file content directly in the playbook
          # The "|" pipe character means "multiline string — preserve newlines"
          # Alternative is "src:" which copies an existing file from control node
          <html><body><h1>TechNova Web Server {{ inventory_hostname }}</h1></body></html>
          # {{ inventory_hostname }} is an Ansible special variable
          # It holds the server alias from your inventory (like web01, web02)
          # So each server gets a unique page showing its own name
        dest: /var/www/technova/index.html
        # "dest:" is where to put the file on the remote server
        owner: www-data
        group: www-data
        mode: '0644'
        # 0644 = owner:rw-, group:r--, others:r-- (typical for web files)
      notify: Restart Nginx
      # "notify:" triggers a Handler when this task CHANGES something
      # If the file content is already identical, no change = no handler runs
      # "Restart Nginx" must match the handler name EXACTLY (case-sensitive)

    - name: Ensure Nginx service is started and enabled
      service:
      # "service" module manages system services (systemd/upstart/sysv)
        name: nginx
        # "name:" is the service name as it appears in systemctl
        state: started
        # "state: started" = make sure nginx is running RIGHT NOW
        # If already running: no change (idempotent!)
        # If stopped: starts it
        enabled: yes
        # "enabled: yes" = enable nginx to START AUTOMATICALLY on server reboot
        # This is equivalent to: systemctl enable nginx
        # Without this, nginx stops after a server restart and app is down

    - name: Capture Nginx service status
      command: systemctl status nginx
      register: nginx_status
      # "register:" saves the output of this task into a variable
      # "nginx_status" is now a variable containing:
      #   nginx_status.stdout — the text output of the command
      #   nginx_status.stderr — any error messages
      #   nginx_status.rc     — return code (0=success, non-zero=failure)
      changed_when: false
      # "changed_when: false" tells Ansible: this task never "changes" anything
      # It's just reading status. Without this, Ansible would mark it as "changed"
      # every time which is misleading in your output report
      ignore_errors: yes
      # "ignore_errors: yes" — continue to next task even if this one fails

    - name: Print Nginx status result
      debug:
      # "debug" module prints messages — does NOT change anything on the server
      # Perfect for troubleshooting and showing information
        msg: "Nginx status on {{ inventory_hostname }}: {{ nginx_status.stdout_lines[0] }}"
        # "msg:" the message to print
        # {{ inventory_hostname }} = the server alias (web01, web02...)
        # {{ nginx_status.stdout_lines[0] }} = first line of the status output
        # stdout_lines is a list, [0] gets the first item

    - name: Verify Nginx responds with HTTP 200
      uri:
      # "uri" module makes HTTP requests — like curl in Ansible
        url: "http://localhost:{{ nginx_port }}"
        # "url:" the HTTP URL to request
        # {{ nginx_port }} uses the variable defined in vars: section
        method: GET
        # "method:" HTTP method — GET, POST, PUT, DELETE
        status_code: 200
        # "status_code: 200" — this task FAILS if Nginx doesn't return HTTP 200 OK
        # This is your automated health check — confirms Nginx is actually serving pages
        timeout: 10
        # "timeout: 10" — fail if no response within 10 seconds

  handlers:
  # "handlers:" section — tasks that run ONLY when notified
  # They run at the END of the play, AFTER all tasks complete
  # Even if notified 10 times, a handler runs only ONCE
    - name: Restart Nginx
      # Handler name MUST match the "notify:" value exactly
      service:
        name: nginx
        state: restarted

🎯 Interview Questions — Chapter 4
Q1: What is the difference between a Play and a Playbook in Ansible?
A Playbook is the entire YAML file that can contain one or more Plays. A Play is a single block starting with - name: that maps a set of tasks to a specific group of hosts. One Playbook can have: Play 1 targeting webservers (sets up Nginx) and Play 2 targeting dbservers (sets up MySQL) — both in the same YAML file, running sequentially.
Q2: What does gather_facts do and when would you disable it?
gather_facts: true (default) makes Ansible run the setup module at the beginning of each play — SSH into every server, collect system information (OS, IP, RAM, CPU, disk) and store it as variables called "Facts". You disable it (gather_facts: false) when: your playbook doesn't need any system facts, you want to speed up the playbook (fact gathering adds 3-5 seconds per server), or when targeting a large number of servers where the time savings are significant.
Q3: What is the register keyword in Ansible?
register captures the output of a task into a variable for later use in the same play. The captured variable contains: .stdout (standard output text), .stderr (error messages), .rc (return code — 0 means success), .stdout_lines (output split into a list by newlines). You commonly use register to check a command's output and make decisions — like "if the app version is old, download the new one".
Q4: What is --check mode and why is it important in production?
--check mode (dry run) runs the playbook in simulation mode — Ansible calculates what WOULD change but makes zero actual changes on the servers. It is critically important in production because: (1) you can see what will be modified before it happens, (2) catch mistakes like wrong file paths or incorrect variables before they cause downtime, (3) use with --diff to see exact file content differences. Best practice: always run --check --diff before touching production servers.
Q5: In the PLAY RECAP, what does each field mean?
ok: tasks that ran successfully (includes both changed and unchanged). changed: tasks that actually modified something on the server. unreachable: servers that Ansible couldn't SSH into (network issue, server down, wrong IP). failed: tasks that returned an error — non-zero if you have issues to investigate. skipped: tasks that had a when condition that evaluated to false. A healthy run shows changed=0 on the second run (idempotency confirmed).

6 Ways to Define Variables — Priority Order

🧠 Variable Priority (Lowest → Highest)

When the same variable is defined in multiple places, the HIGHER priority wins. This is one of the most common interview topics.

  • 1. Role defaults (roles/rolename/defaults/main.yml) — LOWEST priority, easily overridden
  • 2. Inventory file variables (ansible_host, etc. in hosts.ini)
  • 3. group_vars/all.yml — applies to ALL groups
  • 4. group_vars/groupname.yml — applies to specific group
  • 5. host_vars/hostname.yml — applies to one specific server
  • 6. Playbook vars: section — defined in the play itself
  • 7. vars_files: in playbook — loaded from separate YAML files
  • 8. Task vars: (set_fact) — set during play execution
  • 9. -e / --extra-vars — HIGHEST priority, overrides EVERYTHING

🎯 Interview Questions — Chapter 5
Q1: What is the variable precedence order in Ansible?
From lowest to highest priority: role defaults → inventory variables → group_vars/all → group_vars/groupname → host_vars/hostname → playbook vars: → vars_files: → set_fact → --extra-vars / -e (highest — overrides everything). When the same variable name exists in multiple places, the one with higher priority wins. This is critical to understand for debugging unexpected variable values.
Q2: What is the difference between group_vars and host_vars?
group_vars/groupname.yml defines variables that apply to all servers in that specific group. host_vars/hostname.yml defines variables for one specific server — overriding any group variable with the same name (because host_vars has higher priority). Use group_vars for common settings, host_vars when one specific server needs a different value.
Q3: What are Ansible Facts and how are they different from regular variables?
Ansible Facts are variables automatically gathered from managed nodes by the setup module at the start of each play. They are not defined by you — Ansible detects them from the server (OS, IP, RAM, disk). Regular variables are explicitly defined by you in group_vars, host_vars, playbook vars, etc. Facts are prefixed with ansible_ (ansible_os_family, ansible_memtotal_mb). You can turn off fact gathering with gather_facts: false to speed up playbooks when you don't need server info.

Q1: What is the difference between loop and with_items?
loop is the modern way (introduced in Ansible 2.5) and is the recommended approach for all new playbooks. with_items is the older syntax that still works — you'll see it in legacy code at many companies. They do the same thing. One key difference: with_items flattens nested lists, while loop does not. Q2: How do you use AND vs OR logic in Ansible when conditions?
For AND logic: write when as a list — all conditions must be true: when: [condition1, condition2]. For OR logic: write on one line with "or": when: condition1 or condition2. You can combine: when: (condition1 or condition2) and condition3. Parentheses work like in Python for grouping.

Handlers —
Triggered Actions

Handlers are smart tasks that only run when needed. Restart Nginx only when its config changes. Reload MySQL only when a config file is updated. Prevent unnecessary service restarts that cause downtime.

handlers notify listen changed_when flush_handlers
📖 The TechNova Story — Chapter 7

TechNova runs its playbook every night at 2 AM for configuration drift correction. The playbook always runs the task "Restart Nginx" — even if absolutely nothing changed. This means Nginx restarts every night, dropping active connections unnecessarily.

Ravi says: "Puneeth, our monitoring shows brief connection drops every night at 2 AM. Can we restart Nginx ONLY when its config file actually changes?"

This is exactly what Handlers solve — triggered actions that run ONLY when something actually changed.

🧠 How Handlers Work — The Key Rules
  • Only runs when notified: A handler does nothing unless a task explicitly calls notify: HandlerName
  • Only runs on change: A task only notifies its handler when it actually CHANGES something (status = changed, not ok)
  • Runs at end of play: Handlers don't run immediately — they run AFTER all tasks in the play complete
  • Runs only once: Even if notified 10 times (by 10 different tasks), a handler runs only ONCE — preventing multiple unnecessary restarts
  • Name must match exactly: The notify value must match the handler name character-for-character (case-sensitive)

playbooks/nginx_with_handlers.yml 
---
- name: Configure TechNova Nginx with Smart Restart
  hosts: webservers
  become: true

  tasks:

      apt: name=nginx state=present
      # No notify here — installing Nginx doesn't need a restart

      #   → task status = "ok" (no change) → handler NOT triggered → no restart!
      # If the file IS different (you updated nginx.conf):

      # Even if BOTH config files changed, the handler runs only ONCE
      # Ansible is smart enough to not restart Nginx twice!

      copy:
        src: files/ssl-cert.pem

      # No notify — this just ensures it's running, no config change

  handlers:
  # Handlers section — these are DEFINED like tasks but only run when NOTIFIED
  # They run in the ORDER they are defined here, at the END of the play

    - name: Restart Nginx
      # Name MUST match notify: value exactly — "Restart Nginx"
      service:

🎯 Interview Questions — Chapter 7
Q1: What is an Ansible Handler and when does it execute?
A Handler is a special task that only runs when explicitly notified by another task that made a change. Handlers run at the end of the entire play, after all tasks complete. If a task has notify: Restart Nginx but its status is "ok" (no change was made), the handler is NOT triggered. If notified multiple times in one play, the handler runs only ONCE. This prevents unnecessary service restarts.
Q2: What is the difference between state: restarted and state: reloaded for a service?
state: restarted performs a full stop then start — picks up all config changes but causes a brief service interruption (active connections are dropped). state: reloaded sends a SIGHUP signal to the service to re-read config without stopping — zero downtime. However, not all services support reload (Nginx does, some older services don't). Check the service documentation. Prefer reload for production to avoid brief outages.
Q3: What is meta: flush_handlers and when would you use it?
meta: flush_handlers forces all pending (notified but not yet executed) handlers to run immediately at that point in the playbook, instead of waiting until the end of the play. Use it when you need a handler to complete before the next task runs — for example: copy new config → immediately restart service → then run health check. Without flush_handlers, the health check would run before the restart.

🧠 What is a Jinja2 Template?

A Jinja2 template is a text file with variable placeholders and logic. When Ansible runs the template module, it processes the file through the Jinja2 engine — replaces all {{ variable }} placeholders with actual values and evaluates all {% if %} and {% for %} blocks — producing a final, rendered config file that is then copied to the server.

Files use the .j2 extension by convention. They live in the templates/ directory of your project.

🔧 Lab — Write TechNova's Nginx Template
templates/nginx.conf.j2 — Jinja2 Template 
# ======================================================
# TechNova Nginx Configuration
# GENERATED BY ANSIBLE — DO NOT EDIT MANUALLY
# Generated for: {{ inventory_hostname }}
#    on date   : {{ ansible_date_time.date }}
# {{ inventory_hostname }} is the server alias (web01, web02...)
# {{ ansible_date_time.date }} is an Ansible fact for today's date
# ======================================================

# {{ nginx_worker_processes | default(4) }} ← Jinja2 filter
# "| default(4)" means: if nginx_worker_processes is not defined, use 4
# Filters transform variable values — like functions in programming
worker_processes {{ nginx_worker_processes | default(4) }};

events {
    worker_connections {{ nginx_worker_connections | default(1024) }};
    multi_accept on;
}

http {
    sendfile on;
    keepalive_timeout 65;
    types_hash_max_size 2048;

    # ===== CONDITIONAL BLOCK =====
    # {% if %} is Jinja2 logic — NOT output, just a condition
    # {% %} blocks with logic are NOT included in the rendered file
    # Only the content between them is output
    {% if app_environment == "production" %}
        # This block ONLY appears in the production nginx.conf file
    server_tokens off;          # Hide Nginx version for security
    gzip on;
    gzip_min_length 1024;
    {% elif app_environment == "staging" %}
        # This block appears ONLY in staging nginx.conf
    server_tokens on;           # Show version for debugging
    gzip off;
    {% else %}
        # This appears in Dev (any other environment)
    server_tokens on;
    gzip off;
    {% endif %}
        # "{% endif %}" closes the if block — mandatory

    server {
        # {{ nginx_port }} — filled from group_vars/webservers.yml
        # Dev servers get 8080, Staging 8443, Production 80 or 443
        listen {{ nginx_port }} default_server;

        server_name {{ ansible_fqdn }};
                # ansible_fqdn is an Ansible fact — full hostname like web01.technova.com

        root {{ web_root | default('/var/www/html') }};
        index index.html;

                # Log file paths using variables
        access_log /var/log/nginx/{{ app_name }}-access.log combined;
        error_log  /var/log/nginx/{{ app_name }}-error.log {{ nginx_log_level | default('warn') }};
                # nginx_log_level: "debug" in dev, "warn" in production
                # | default('warn') — use warn if variable not defined

        location / {
            proxy_pass http://localhost:{{ app_port | default(3000) }};
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }

                # ===== FOR LOOP IN TEMPLATE =====
                # Generate location blocks for each allowed API path
        {% for path in allowed_api_paths | default(['/api', '/health']) %}
        location {{ path }} {
            proxy_pass http://localhost:{{ app_port | default(3000) }}{{ path }};
        }
        {% endfor %}
                # {% for path in allowed_api_paths %} — loops over the list
                # "path" is the loop variable — changes each iteration
                # {% endfor %} closes the for loop
    }
}

🎯 Interview Questions — Chapter 8
Q1: What is the difference between the copy and template modules?
The copy module transfers a file from the control node to managed nodes exactly as-is — no variable substitution, no logic processing. The template module processes the file through the Jinja2 templating engine first, replacing all {{ variable }} placeholders with actual values and evaluating {% if %}/{% for %} logic, THEN copying the rendered result to the server. Use copy for static files; use template when config needs to vary per server, group, or environment.
Q2: What are Jinja2 filters and give 3 common examples?
Jinja2 filters transform variable values — like functions. They are applied using the pipe character (|). Common examples: {{ nginx_port | default(80) }} — use 80 if nginx_port is undefined; {{ "hello world" | upper }} — convert to uppercase (HELLO WORLD); {{ ansible_memtotal_mb | int }} — convert to integer; {{ my_list | join(', ') }} — join a list into a comma-separated string; {{ password | password_hash('sha512') }} — hash a password for /etc/shadow.

🧠 How Ansible Vault Works

Ansible Vault uses AES-256 symmetric encryption to encrypt any YAML file or string value. The encrypted content is safe to commit to Git — it looks like garbage text. When you run a playbook, Ansible decrypts the values in memory — they are never written to disk in plaintext. The vault password is the key that locks and unlocks everything.

🎯 Interview Questions — Chapter 10
Q1: What encryption does Ansible Vault use and how does it work at runtime?
Ansible Vault uses AES-256 symmetric encryption. The vault password you provide is used to derive an encryption key that locks your secrets. When you run a playbook with vault-encrypted files, Ansible decrypts them in memory only — the plaintext values are never written to disk and exist only in RAM during the playbook execution. After the playbook finishes, the decrypted values are gone.
Q2: What is the difference between ansible-vault encrypt and encrypt_string?
ansible-vault encrypt file.yml encrypts an entire file — the whole YAML file becomes encrypted gibberish. Nobody can read any variable from it without the vault password. ansible-vault encrypt_string 'value' --name 'varname' encrypts a single string value — you can paste the output into a regular (unencrypted) YAML file. This means non-sensitive variables in the same file are still readable, while just the sensitive ones are encrypted. Most teams prefer this approach for better code readability.
Q3: How do you handle vault passwords in a CI/CD pipeline like Jenkins or GitHub Actions?
Store the vault password as a secret in your CI/CD platform — Jenkins Credentials or GitHub Actions Secrets. In the pipeline, write the secret to a temporary file (echo "$VAULT_PASS" > /tmp/.vault_pass), pass it to ansible-playbook with --vault-password-file /tmp/.vault_pass, and delete the file after the run. The vault password itself is never stored in any code file — only in the secrets management system. This is the industry-standard approach for automating Ansible in CI/CD.
Q4: What is the vault_ variable naming convention and why use it?
The convention is to prefix vault variables with vault_ (e.g., vault_db_password) in the encrypted file, then create a corresponding unencrypted variable in main.yml that references it (e.g., db_password: "{{ vault_db_password }}"). Benefits: (1) tasks use the clean variable name (db_password), (2) it's immediately clear in the encrypted file which variables are sensitive, (3) the main.yml shows the structure of all variables without revealing secrets — making code review easier.
