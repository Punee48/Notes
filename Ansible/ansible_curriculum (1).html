🧠 Core Concept — What is Ansible?

Ansible is an open-source IT automation tool created by Red Hat. It lets you write a simple text file (called a Playbook) describing what you want on your servers — and Ansible will SSH into all your servers and do it automatically, at the same time, without you touching each server manually.

Why Ansible over shell scripts? Shell scripts break on different OS versions, don't handle errors gracefully, and can't run on 100 servers at once easily. Ansible is idempotent (run it 100 times, same result), readable, and has 3000+ built-in modules.

🎯 Interview Questions — Chapter 1
Q: What is Ansible and why is it called agentless?
Ansible is an open-source automation tool from Red Hat used for configuration management, application deployment, and task automation. It is called agentless because you do NOT need to install any software or agent on the target servers. Ansible simply uses SSH to connect and execute tasks — making it lightweight and easy to set up.
Q: What is a Control Node and a Managed Node?
Control Node is the machine where Ansible is installed and from where you run playbooks. Managed Nodes are the target servers that Ansible configures — no Ansible installation needed on them, just Python and SSH access.
Q: What is idempotency in Ansible?
Idempotency means running the same Ansible playbook multiple times gives the same result without causing any side effects. For example, if Nginx is already installed, Ansible will NOT install it again — it checks current state first. This prevents duplication and ensures consistency.
CH-02 Inventory Files — Managing Your Servers
Tell Ansible which servers to manage. Write static inventory files, group servers by role, and set per-host variables.

📖 Story Context

TechNova has 200 servers in 3 groups — Web Servers (running Nginx), App Servers (running Java), and DB Servers (running MySQL). You need to tell Ansible about all of them so it knows where to run commands. The Inventory file is your server address book.

🧠 Core Concept — Inventory

The Inventory file tells Ansible where your servers are (IP or hostname) and how to group them. Ansible reads this file and knows: "When I say 'run on webservers', I should SSH into these 5 IP addresses." You can also set variables per host or per group directly in the inventory.

🔧 Hands-on — Write TechNova's Inventory File
inventory/hosts.ini 
# This is TechNova's main inventory file
# Square brackets define a GROUP name

[webservers]
web01 ansible_host=192.168.1.10 ansible_user=ubuntu
web02 ansible_host=192.168.1.11 ansible_user=ubuntu
web03 ansible_host=192.168.1.12 ansible_user=ubuntu

[appservers]
app01 ansible_host=192.168.1.20 ansible_user=ubuntu
app02 ansible_host=192.168.1.21 ansible_user=ubuntu

[dbservers]
db01  ansible_host=192.168.1.30 ansible_user=ubuntu ansible_port=22

# Group of groups — "all prod servers"
[production:children]
webservers
appservers
dbservers

# Variables that apply to ALL servers in webservers group
[webservers:vars]
http_port=80
app_env=production
Line / KeywordWord-by-word Meaning
[webservers]Square brackets define a GROUP. Any server listed below this line, until the next group, belongs to the "webservers" group. You can target this entire group in one command.
web01This is the alias name (nickname) you give the server. You can call it anything. Ansible will use this name in output messages.
ansible_host=The actual IP address or DNS hostname of the server. Ansible will SSH to this address.
ansible_user=The SSH username to log in with. For AWS EC2 Ubuntu, this is always 'ubuntu'. For Amazon Linux, it is 'ec2-user'.
[production:children]":children" means this group CONTAINS other groups. So "production" group = all webservers + appservers + dbservers combined. Very useful for running something on all servers at once.
[webservers:vars]":vars" means variables that apply to EVERY server in the webservers group. http_port=80 will be available as a variable in any playbook running on webservers.

🎯 Interview Questions — Chapter 2
Q: What is the difference between static and dynamic inventory in Ansible?
Static inventory is a manually written file (hosts.ini or YAML) where you hard-code server IPs. Dynamic inventory uses a script or plugin that automatically fetches server details from a cloud provider like AWS EC2 at runtime — so when new EC2 instances are added, Ansible knows about them automatically without changing any file.
Q: What is [group:children] in Ansible inventory?
It is used to create a group of groups. For example, [production:children] with webservers and appservers listed means "production" group is a parent that contains all servers from both child groups. Running a playbook on "production" will target all servers in both groups.
CH-03 Ad-hoc Commands — Quick One-liners
Run quick tasks on servers without writing a playbook. Restart services, check disk space, copy files — all from the command line.
ad-hoc -m module ping shell copy
📖 Story Context

It's Friday 5 PM. TechNova's web servers are running out of disk space. Your manager says: "Quick! Delete the old log files from all 50 web servers NOW." You don't have time to write a full playbook. Ansible Ad-hoc commands let you fire a one-liner that runs on all 50 servers simultaneously in under 10 seconds.

🔧 Essential Ad-hoc Commands
terminal — ad-hoc examples 
# SYNTAX: ansible [target] -i [inventory] -m [module] -a "[arguments]"

# 1. Ping all servers to check if they're reachable
ansible all -i hosts.ini -m ping

# 2. Check uptime on all web servers (shell module runs any shell command)
ansible webservers -i hosts.ini -m shell -a "uptime"

# 3. Check disk space on all servers
ansible all -i hosts.ini -m shell -a "df -h"

# 4. Install Nginx on all webservers (apt module for Ubuntu)
ansible webservers -i hosts.ini -m apt -a "name=nginx state=present" --become

# 5. Start and enable Nginx service
ansible webservers -i hosts.ini -m service -a "name=nginx state=started enabled=yes" --become

# 6. Copy a file from control node to managed nodes
ansible webservers -i hosts.ini -m copy -a "src=/tmp/app.conf dest=/etc/nginx/app.conf" --become

# 7. Delete old log files (run as root with --become)
ansible webservers -i hosts.ini -m shell -a "rm -f /var/log/app/*.log" --become

# 8. Reboot all servers (use carefully!)
ansible all -i hosts.ini -m reboot --become
Flag / OptionMeaning
-i hosts.ini"-i" means inventory. Tells Ansible which inventory file to read. If not given, it looks at /etc/ansible/hosts by default.
-m ping"-m" means module. "ping" is the module name. Ansible has 3000+ modules for every task imaginable.
-a "...""-a" means arguments. The parameters you pass to the module. For "apt" module, you pass "name=nginx state=present".
--becomeBecome root (sudo). Required for system-level tasks like installing packages or managing services. Equivalent to running with sudo.
state=present"present" means install it if not already installed. Ansible first checks if Nginx is already there — if yes, it skips. This is idempotency in action.
state=startedFor the service module: "started" means ensure the service is running. If already running, Ansible does nothing.
🎯 Interview Questions — Chapter 3
Q: What is the difference between the shell module and the command module?
The "command" module runs a command directly without going through the shell — so it cannot use pipes (|), redirects (>), or environment variables ($HOME). The "shell" module runs commands through the actual shell (/bin/sh), so you CAN use pipes, redirects, and environment variables. Always prefer "command" when you don't need shell features — it's safer and more secure.
Q: When should you use ad-hoc commands vs. playbooks?
Ad-hoc commands are for quick, one-time tasks like checking disk space, restarting a service, or emergency fixes that you don't need to repeat or document. Playbooks are for repeatable, documented automation — things you run in CI/CD pipelines, scheduled jobs, or any task that needs consistency across environments.
CH-04 Your First Playbook — YAML Deep Dive
Write your first real Ansible Playbook to install and configure Nginx on TechNova's web servers. Every YAML line explained word-by-word.
playbook YAML tasks modules nginx
📖 Story Context

TechNova wants to set up Nginx on all 50 web servers. With ad-hoc, you'd run separate commands one by one. Now you'll write a Playbook — a single YAML file that does everything in sequence: install Nginx, configure it, start the service, and verify it. Run this one file and all 50 servers are configured in 2 minutes.

🔧 TechNova Nginx Setup Playbook
playbooks/setup_nginx.yml 
---                          # Every YAML file starts with three dashes
# This means: "Start of YAML document"

- name: Setup Nginx on TechNova Web Servers
  # "name" is a human-readable label for this PLAY (a group of tasks)

  hosts: webservers
    # "hosts" tells Ansible: run this play on all servers in [webservers] group
    # "webservers" matches exactly the group name in your inventory file

  become: true
    # "become: true" means: use sudo for all tasks in this play
    # Without this, apt install would fail (permission denied)

  vars:
      # "vars" section: define variables for this play
    nginx_port: 80
    app_name: "technova-web"

  tasks:
      # "tasks" is a LIST of actions to perform, in order, top to bottom

    - name: Update apt package cache
      ansible.builtin.apt:
              # "ansible.builtin.apt" is the full module name for apt package manager
              # You can also just write "apt:" (short form)
        update_cache: yes
                # update_cache: yes = runs "apt update" before doing anything
        cache_valid_time: 3600
                # cache_valid_time: 3600 = if cache was updated in last 1 hour, skip
                # This avoids running "apt update" on every single playbook run

    - name: Install Nginx web server
      apt:
        name: nginx
                # "name" is the package name to install
        state: present
                # "state: present" = install if not installed, skip if already installed
                # Other states: absent (uninstall), latest (upgrade to newest)

    - name: Ensure Nginx service is started and enabled
      service:
        name: nginx
        state: started
                # started = make sure it is running right now
        enabled: yes
                # enabled: yes = start Nginx automatically on server reboot

    - name: Verify Nginx is responding
      uri:
                # "uri" module: make an HTTP request and check the response
        url: "http://localhost:{{ nginx_port }}"
                # {{ nginx_port }} is variable substitution — uses the var defined above
        status_code: 200
                # status_code: 200 = fail this task if Nginx doesn't return HTTP 200 OK

🎯 Interview Questions — Chapter 4
Q: What is the difference between a Play and a Playbook?
A Playbook is the entire YAML file that can contain multiple Plays. A Play is a single block starting with "- name:" that targets a specific group of hosts. For example, one Playbook can have Play 1 targeting webservers and Play 2 targeting dbservers — both in the same file, running in sequence.
Q: What does state: present vs state: latest mean in the apt module?
state: present means install the package if it's not there, but if it's already installed (any version), leave it alone. state: latest means always upgrade to the newest available version. In production, "present" is safer because "latest" can unexpectedly upgrade critical packages and break things.
Q: What is --check mode and when do you use it?
--check (also called dry-run mode) runs the playbook without making any actual changes on the servers. It shows you what WOULD change if you ran it for real. Always use --check before running playbooks on production servers — it's your safety net to catch mistakes before they cause downtime.

Using facts — playbooks/check_os.yml 
---
- name: Gather and use server facts
  hosts: all
  tasks:

    - name: Print server OS and memory info
      debug:
                # debug module: just prints a message — great for troubleshooting
        msg: "Server {{ inventory_hostname }} runs {{ ansible_os_family }}
               with {{ ansible_memtotal_mb }} MB RAM"
                # ansible_os_family: auto-collected fact (Debian, RedHat, etc.)

🎯 Interview Questions — Chapter 5
Q: What is the variable precedence order in Ansible?
Ansible follows a priority order (lowest to highest): role defaults → inventory vars → group_vars/all → group_vars/groupname → host_vars → playbook vars → extra vars (-e flag). The -e flag (extra vars) always wins over everything. This means you can override any variable from the command line without touching your files.
Q: What are Ansible Facts and how are they collected?
Ansible Facts are variables automatically gathered from managed nodes at the beginning of every playbook run, using the "setup" module. They contain OS type, IP address, CPU count, RAM, disk info, and more. You can turn off fact gathering with "gather_facts: false" to speed up playbooks when you don't need this information.
CH-06 Conditionals & Loops — Smart Automation
Make playbooks intelligent — run tasks only when conditions are met, and loop over lists of packages, users, or files.
when loop with_items conditionals
📖 Story Context

TechNova has both Ubuntu AND CentOS servers. The apt command only works on Ubuntu; CentOS needs yum. You need ONE playbook that installs packages correctly on BOTH — using when conditions. Also, you need to install 10 packages — instead of writing 10 tasks, you'll use a loop.

🔧 when + loop — Multi-OS Playbook
playbooks/install_packages.yml 
---
- name: Install packages on TechNova servers (multi-OS)
  hosts: all
  become: true

  vars:
    common_packages:
            # This is a YAML list — each item starts with a dash
      - git
      - curl
      - wget
      - htop
      - unzip

  tasks:

    - name: Install packages on Ubuntu/Debian systems
      apt:
        name: "{{ item }}"
                # {{ item }} is the loop variable — holds current item in each iteration
        state: present
      loop: "{{ common_packages }}"
            # "loop" iterates over the list — runs this task once per item
            # First run: item=git, Second: item=curl, etc.
      when: ansible_os_family == "Debian"
            # "when" is a conditional — this task ONLY runs if the server OS is Debian/Ubuntu
            # ansible_os_family is an Ansible Fact (auto-collected at start)

    - name: Install packages on CentOS/RHEL systems
      yum:
        name: "{{ item }}"
        state: present
      loop: "{{ common_packages }}"
      when: ansible_os_family == "RedHat"
            # This task runs ONLY on CentOS/RHEL — skipped on Ubuntu

    - name: Create TechNova application users
      user:
        name: "{{ item.username }}"
                # item.username — accessing a property of a dict in the loop
        groups: "{{ item.group }}"
        state: present
      loop:
        - { username: deploy, group: www-data }
        - { username: monitor, group: adm }
        - { username: backup, group: sudo }
                # Loop over a list of dictionaries
                # Each iteration: item = { username: "deploy", group: "www-data" }
🎯 Interview Questions — Chapter 6
Q: What is the difference between loop and with_items in Ansible?
"loop" is the modern, recommended way to iterate in Ansible (introduced in 2.5). "with_items" is the older syntax that still works. They do the same thing — loop through a list and run the task for each item. "loop" is preferred in new playbooks; "with_items" still appears in legacy code you'll see in companies.
CH-07 Handlers — Triggered Actions
Run tasks only when something changes — like restarting Nginx only when its config file is updated, not on every playbook run.
handlers notify changed_when service restart
📖 Story Context

TechNova updates the Nginx configuration file regularly. But Nginx only picks up new config after a restart. If you put "restart nginx" as a regular task, it restarts Nginx EVERY time you run the playbook — even when the config didn't change. This causes unnecessary downtime. Handlers are smart — they only run when triggered by a change.

🔧 Handlers Example
playbooks/nginx_config.yml 
---
- name: Configure Nginx for TechNova
  hosts: webservers
  become: true

  tasks:
    - name: Copy Nginx configuration file
      copy:
        src: files/nginx.conf
        dest: /etc/nginx/nginx.conf
        owner: root
        mode: '0644'
      notify: Restart Nginx
            # "notify" is the trigger word
            # If this task makes ANY change on the server,
            # it will call the handler named "Restart Nginx"
            # If the config was ALREADY identical, no change = no handler runs

  handlers:
      # Handlers section: define tasks that only run when notified
      # Handlers run at the END of the play, not immediately
    - name: Restart Nginx
            # This name MUST exactly match the "notify:" value above
      service:
        name: nginx
        state: restarted
🎯 Interview Questions — Chapter 7
Q: What is a Handler in Ansible and when does it execute?
A Handler is a special task that only runs when explicitly triggered (notified) by another task that made a change. Handlers run at the END of the entire play, after all tasks complete. If a task is notified multiple times in one play (e.g., 3 config files were updated), the handler runs only ONCE — preventing multiple unnecessary restarts.
CH-08 Jinja2 Templates — Dynamic Config Files
Generate configuration files dynamically using variables. One template creates different configs for Dev, Staging, and Production automatically.
template jinja2 .j2 files dynamic config
📖 Story Context

TechNova's Nginx config for Dev should listen on port 8080, Staging on 8443, Production on 443. Instead of 3 config files, you write ONE template with {{ nginx_port }} — and Ansible fills in the correct port value based on which environment you're deploying to. Magic!

🔧 Jinja2 Template Example
templates/nginx.conf.j2 
# Ansible-managed — Do not edit manually!
# Generated for: {{ inventory_hostname }} on {{ ansible_date_time.date }}

worker_processes {{ nginx_worker_processes | default(4) }};
# default(4) is a Jinja2 filter — if variable not defined, use 4

events {
    worker_connections 1024;
}

http {
    server {
        listen {{ nginx_port }};
                # {{ nginx_port }} is filled by group_vars or extra vars

        server_name {{ ansible_fqdn }};
                # ansible_fqdn is an Ansible fact — auto-detected full domain name

        {% if app_environment == "production" %}
        # This block only appears in production config
        access_log /var/log/nginx/access.log combined;
        error_log  /var/log/nginx/error.log warn;
        {% else %}
        access_log /var/log/nginx/access.log combined;
        error_log  /var/log/nginx/error.log debug;
        {% endif %}

        location / {
            proxy_pass http://localhost:{{ app_port | default(3000) }};
        }
    }
}
playbooks/deploy_nginx_config.yml — using template 
---
- name: Deploy Nginx config using template
  hosts: webservers
  become: true
  tasks:
    - name: Generate and deploy Nginx config from template
      template:
        src: templates/nginx.conf.j2
                # "src" is the .j2 template file on your control node
        dest: /etc/nginx/nginx.conf
                # "dest" is where the RENDERED file goes on the managed node
        owner: root
        group: root
        mode: '0644'
      notify: Restart Nginx
🎯 Interview Questions — Chapter 8
Q: What is the difference between copy and template modules?
The copy module transfers a file exactly as-is from control node to managed node — no modification. The template module processes the file through the Jinja2 templating engine first, replacing all {{ variable }} placeholders and {% if %} logic with actual values before copying. Use template when your config file needs to be different per environment or server.

🎯 Interview Questions — Chapter 9
Q: What is the difference between vars/ and defaults/ in a role?
vars/main.yml has high-priority variables that are hard to override — use for things that must stay fixed within the role. defaults/main.yml has the lowest priority — they're fallback values that any playbook or inventory variable can easily override. Best practice: put all role variables in defaults/ so they're easily customizable by users of the role.
CH-10 Ansible Vault — Secrets Management
Encrypt passwords, API keys, and database credentials inside your Ansible files. Never commit plaintext secrets to Git again.
ansible-vault encrypt secrets --vault-password-file
📖 Story Context

TechNova's playbook has the MySQL root password in plain text in a YAML file. A developer accidentally pushed it to GitHub. The security team is panicking. You need to encrypt secrets so they're safe in Git but Ansible can still use them at runtime. Ansible Vault is the answer.

CH-11Error Handling, Debugging & rescue/always Blocks
Handle failures gracefully. Use block/rescue/always for try-catch logic. Use ignore_errors, failed_when, and changed_when for smart failure detection.
blockrescuealwaysfailed_whenignore_errors
📖 Story Context

A deployment at TechNova failed halfway — 10 servers got the new app but 40 didn't. Ansible stopped when one server failed. You need a playbook that tries deployment, catches failures gracefully, rolls back bad servers, and always sends a Slack notification — success or failure.

🔧 block / rescue / always — Python try/catch equivalent
playbooks/deploy_with_error_handling.yml
---
- name: Deploy TechNova App with Error Handling
  hosts: appservers
  become: true
  tasks:

    - name: Deploy application with rollback capability
      block:
              # BLOCK = "try" — tasks that might fail
        - name: Stop old application
          service: name=technova-app state=stopped

        - name: Copy new application files
          copy:
            src: /tmp/app-v2.tar.gz
            dest: /opt/technova/app.tar.gz

        - name: Start new application
          service: name=technova-app state=started

      rescue:
              # RESCUE = "catch" — runs ONLY if any task in block fails
        - name: Rollback — restore previous version
          shell: cp /opt/technova/backup/app-previous.tar.gz /opt/technova/app.tar.gz

        - name: Restart with old version
          service: name=technova-app state=restarted

      always:
              # ALWAYS = "finally" — runs regardless of success or failure
        - name: Send deployment status notification
          debug:
            msg: "Deployment finished on {{ inventory_hostname }}"
🎯 Interview Questions — Chapter 11
Q: What is the difference between ignore_errors and failed_when?
ignore_errors: true makes Ansible continue to the next task even if this one fails — the failure is logged but playbook continues. failed_when lets you define a custom condition for failure, like "fail if the output contains the word ERROR". ignore_errors is blunt; failed_when is precise and the better choice in production.

CH-15Ansible Strategies — Free, Linear & Serial
Control how Ansible executes tasks across multiple hosts — all at once, one by one, or batch-by-batch for zero-downtime rolling deploys.
serialstrategy: freemax_fail_percentagerolling update
📖 Story Context

TechNova has 50 web servers in production. If you deploy to all 50 at the same time and the new version is broken, all 50 servers go down simultaneously — total outage. Using serial, you deploy to 5 servers at a time, verify health, then continue — a true rolling deploy with zero downtime.

🔧 Rolling Deployment with serial
playbooks/rolling_deploy.yml
---
- name: Rolling Deploy — TechNova Web Servers
  hosts: webservers
  become: true
  serial: 5
    # serial: 5 means run on only 5 servers at a time
    # When those 5 complete all tasks, move to next 5
    # You can also write serial: "20%" — 20% of total hosts at a time

  max_fail_percentage: 10
    # Stop the entire play if more than 10% of servers fail
    # This prevents a cascading failure across all servers

  tasks:
    - name: Remove server from load balancer
      shell: aws elbv2 deregister-targets --target-group-arn {{ tg_arn }} ...

    - name: Deploy new app version
      copy: src=app-v2.jar dest=/opt/app/

    - name: Restart app service
      service: name=technova-app state=restarted

    - name: Health check — verify app is responding
      uri: url=http://localhost:8080/health status_code=200

    - name: Re-add server to load balancer
      shell: aws elbv2 register-targets --target-group-arn {{ tg_arn }} ...

A Survey is a form that appears before a Job Template runs, asking the user to input variables like "Which version to deploy?" or "Which environment?". The inputs become extra_vars for the playbook. CH-20RBAC — Role Based Access Control
Control who can see, run, or edit what in Tower. Give developers deployment access without admin rights. Create teams and assign granular permissions.
organizationsteamsuserspermissionsLDAP
🧠 Tower RBAC Hierarchy
  • Organization — Top-level container. TechNova has one: "TechNova Corp"
  • Teams — Groups within organization: DevTeam, OpsTeam, SecTeam
  • Users — Individual people. Assigned to teams or directly to resources
  • Roles on resources — Admin, Execute, Read. A user gets "Execute" on a Job Template = can run it but not edit or delete it
🧠 Practical RBAC for TechNova
  • DevTeam: Execute permission on "Deploy App" Job Template — can run deployments
  • DevTeam: NO access to Production Inventory or Credentials — can't see server IPs or SSH keys
  • OpsTeam: Admin on all Job Templates — can create, edit, run everything
  • SecTeam: Read permission on all jobs — can view audit logs but can't run anything
🎯 Interview Questions — Chapter 20
Q: How does RBAC work in Ansible Tower?
In Ansible Tower, RBAC works at a resource level. Every resource (Job Template, Inventory, Credential, Project) has roles: Admin (full control), Execute (run only), Use (attach to templates), and Read (view only). You assign these roles to Users or Teams. This allows organizations to give developers one-click deployment access without exposing SSH keys, server IPs, or playbook code.
