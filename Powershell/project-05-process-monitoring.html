Quick Recap of Projects 1–4

We've collected data (Project 1), classified it against thresholds (Project 2), sampled it over time (Project 3), and checked a named list with error handling (Project 4). This project shifts focus from "servers and services" to individual running processes — and introduces sorting, ranking, and grouping, which we haven't needed until now.

The Story — Why We're Building This

A batch reconciliation job on WINBATCH04 went wrong last week — a bug caused it to spawn a new worker process every few seconds without closing the old ones. By the time anyone noticed, there were over 80 copies of the same executable running, and the server ground to a halt.

Our manager wants two things from this project: a report of the top CPU and memory consuming processes on a server (so we can spot something abnormal at a glance), and a check for any process name running more instances than expected — which would have caught the batch job problem long before it became an outage.

Concepts First — Before We Touch Code

1. Get-Process and Its Key Properties

PropertyMeaning
IdThe process ID (PID) — unique per running instance
ProcessNameThe executable name without ".exe"
CPUTotal processor time consumed since the process started, in seconds
WorkingSet64Current physical memory usage, in bytes
A subtlety worth knowingCPU here is cumulative total seconds of processor time used since the process started — not a live percentage like Project 3's LoadPercentage. A process that's been running for days will naturally show a high CPU number even if it's idle right now; that's a different measurement than "percent busy at this instant."

2. Sort-Object -Descending

By default Sort-Object sorts ascending (smallest/earliest first). -Descending flips that — essential for "show me the biggest consumers first."

3. Select-Object -First N

After sorting, Select-Object -First 5 keeps only the first 5 objects from the pipeline — combined with descending sort, this gives us "top 5 by whatever we sorted on."

Get-Process
→
Sort-Object CPU -Descending
→
Select-Object -First 5
→
Top 5 CPU Consumers

4. Group-Object — Counting Instances

Group-Object ProcessName gathers all processes that share the same name into groups. Each group object has a Count property (how many instances) and a Group property (the actual process objects in that group) — exactly what we need to detect "too many copies of the same process."

Get-Process | Group-Object ProcessName | Sort-Object Count -Descending | Select-Object -First 5

5. Measure-Object -Sum

We used -Average and -Maximum in Project 3; -Sum adds every value together — useful here for "total memory used by all instances of this process combined," which can matter more than any single instance's memory usage.

6. Byte-to-MB Conversion, Revisited

Same idea as Project 1's GB conversion, but processes are usually small enough that megabytes (1MB) are the more readable unit than gigabytes.

Full Script — Get-ProcessHealthReport.ps1

# =====================================================================
# Get-ProcessHealthReport.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Identify top resource-consuming processes and runaway instance counts
# =====================================================================

$ComputerName        = $env:COMPUTERNAME     # The server being checked
$TopCount             = 5                     # How many top processes to show per metric
$MaxInstancesAllowed  = 10                    # Any process name running more copies than this is flagged

Write-Host "`n=== PROCESS HEALTH REPORT: $ComputerName ===" -ForegroundColor Magenta   # Section header

# ---------------------------------------------------------------
# STEP 1: Get all running processes once, reuse the data for everything below
# ---------------------------------------------------------------
$AllProcesses = Get-Process   # One call, reused for CPU ranking, memory ranking, and grouping

# ---------------------------------------------------------------
# STEP 2: Top CPU consumers
# ---------------------------------------------------------------
$TopCpu = $AllProcesses |                       # Starts from every process we collected
    Sort-Object CPU -Descending |               # Orders them highest CPU-seconds first
    Select-Object -First $TopCount |            # Keeps only the top N
    Select-Object ProcessName, Id,              # Chooses which properties to keep for display
                  @{Name="CPU_Seconds"; Expression={ [math]::Round($_.CPU, 1) }}   # Custom calculated property, rounded

Write-Host "`n--- Top $TopCount by CPU (seconds) ---" -ForegroundColor Cyan
$TopCpu | Format-Table -AutoSize                # Displays as a neat table

# ---------------------------------------------------------------
# STEP 3: Top Memory consumers
# ---------------------------------------------------------------
$TopMemory = $AllProcesses |
    Sort-Object WorkingSet64 -Descending |      # Orders them highest memory usage first
    Select-Object -First $TopCount |
    Select-Object ProcessName, Id,
                  @{Name="MemoryMB"; Expression={ [math]::Round($_.WorkingSet64 / 1MB, 1) }}   # Bytes converted to MB

Write-Host "`n--- Top $TopCount by Memory (MB) ---" -ForegroundColor Cyan
$TopMemory | Format-Table -AutoSize

# ---------------------------------------------------------------
# STEP 4: Detect runaway instance counts (same process name running too many times)
# ---------------------------------------------------------------
$InstanceGroups = $AllProcesses |               # Starts from every process again
    Group-Object ProcessName |                  # Groups by shared process name
    ForEach-Object {                            # Processes each group one at a time

        $TotalMemoryMB = ($_.Group | Measure-Object -Property WorkingSet64 -Sum).Sum / 1MB   # Sums memory across the whole group

        [PSCustomObject]@{
            ProcessName   = $_.Name                                   # The shared process name for this group
            InstanceCount = $_.Count                                    # How many copies are running
            TotalMemoryMB = [math]::Round($TotalMemoryMB, 1)           # Combined memory across all instances
            Status        = if ($_.Count -gt $MaxInstancesAllowed) { "TOO MANY INSTANCES" } else { "NORMAL" }   # if can produce a value directly
        }
    }

$Problems = $InstanceGroups | Where-Object { $_.Status -eq "TOO MANY INSTANCES" }   # Filters down to only flagged groups

Write-Host "`n--- Instance Count Check (limit: $MaxInstancesAllowed) ---" -ForegroundColor Cyan
if ($Problems.Count -gt 0) {                    # Only true if at least one process name exceeded the limit
    $Problems | Sort-Object InstanceCount -Descending | Format-Table -AutoSize   # Shows worst offenders first
    Write-Host "$($Problems.Count) process name(s) exceeded the instance limit!" -ForegroundColor Red
}
else {
    Write-Host "No process exceeded $MaxInstancesAllowed instances." -ForegroundColor Green
}

# ---------------------------------------------------------------
# STEP 5: Export everything to CSV for record-keeping
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) {             # Creates the reports folder if it doesn't exist
    New-Item -ItemType Directory -Path ".\reports" | Out-Null
}
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"  # Sortable timestamp for filenames

$InstanceGroups | Export-Csv -Path ".\reports\ProcessInstances_$Timestamp.csv" -NoTypeInformation   # Full instance report
$TopCpu         | Export-Csv -Path ".\reports\TopCpu_$Timestamp.csv" -NoTypeInformation             # Top CPU snapshot
$TopMemory      | Export-Csv -Path ".\reports\TopMemory_$Timestamp.csv" -NoTypeInformation           # Top memory snapshot

Write-Host "`nReports saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

Select-Object ProcessName, Id, @{Name="CPU_Seconds"; Expression={ ... }}

  • ProcessName, Id — plain property names are kept as-is.
  • @{Name="CPU_Seconds"; Expression={...}} — this is a calculated property: a hash table telling Select-Object "create a new column called CPU_Seconds, whose value comes from running this script block against each object." This is how we rename and reshape data on the fly, rather than being stuck with the original property names and raw values.
  • $_ inside the Expression script block refers to the current process being processed — same meaning as in Where-Object/ForEach-Object.

Group-Object ProcessName | ForEach-Object { ... $_.Group ... $_.Count ... $_.Name ... }

  • After Group-Object, each object in the pipeline is a group, not an individual process. $_.Name is the shared process name for that group; $_.Count is how many processes are in it; $_.Group is an array containing the actual original process objects, which is why we can pipe $_.Group into Measure-Object to sum their memory.

($_.Group | Measure-Object -Property WorkingSet64 -Sum).Sum / 1MB

  • -Sum — requests the total across all objects instead of an average or maximum.
  • .Sum — pulls that specific number out of the object Measure-Object returns, same pattern as .Average in Project 3.

Status = if ($_.Count -gt $MaxInstancesAllowed) { "TOO MANY INSTANCES" } else { "NORMAL" }

  • Just like Project 3's Challenge 3 showed, an if/else statement can be used directly as an expression that produces a value — here it's assigned straight into a property inside the object constructor, without needing a separate variable first.

Architecture & Data Flow

Get-Process (once)
→
Sort + Select (CPU)
Get-Process (once)
→
Sort + Select (Memory)
Get-Process (once)
→
Group-Object → Sum Memory per Group
→
Flag Instance Overload

Notice we called Get-Process exactly once and stored it in $AllProcesses, then reused that same snapshot three different ways. Calling a data-collection cmdlet repeatedly when you already have the data in memory wastes effort and — worse — could give inconsistent results if the process list changes slightly between separate calls.

Production Incident Walkthrough

Applying this script retroactively to the WINBATCH04 incident: the instance-count check would have shown ReconcileWorker.exe — InstanceCount: 84 — TOO MANY INSTANCES the moment the count crossed our 10-instance limit, likely hours before the server became unresponsive.
  • Why flag by count instead of only by total CPU/memory? Early on, 15 lightweight worker processes might not show up in a Top-5-by-memory list at all — each individually looks small. The instance count is often the earliest warning sign, well before combined resource usage becomes visibly abnormal.
  • Why not hardcode the limit as "10" directly inside the if statement? Exactly the same reasoning as every threshold in this course so far — $MaxInstancesAllowed as a named variable means Operations can tune it per server role without touching the logic itself.

Security & Best Practices

Best practice reinforced hereJust like Project 4, this script only detects and reports — it does not call Stop-Process automatically. Killing processes automatically based on a threshold is risky (what if it's a legitimate, temporarily busy batch job?) and belongs in the Advanced stage with proper -WhatIf/-Confirm safeguards.
Standard user is enoughReading process information for reporting purposes doesn't require administrative rights on most systems — keep monitoring scripts running with the least privilege that gets the job done.

Interview Preparation

Q1. What's the difference between the CPU property on Get-Process and the LoadPercentage we used in Project 3?

Answer: CPU on a process is cumulative processor-seconds consumed since that process started — it only ever goes up. LoadPercentage is a live, instantaneous percentage of overall system CPU usage. They answer different questions: "how much total work has this process done" versus "how busy is the CPU right now."

Follow-up: "How would you estimate a process's live CPU percentage instead?" — Answer: sample its CPU-seconds value twice with a known time gap between samples and calculate the rate of change — a technique we'll formalize with Get-Counter in a later project.

Q2. Why did the script call Get-Process only once and reuse the result?

Answer: Process lists can change between calls (processes starting/stopping), so re-querying for each report risks inconsistent data across the CPU, memory, and instance-count sections. Storing one snapshot and reusing it also avoids unnecessary repeated system calls.

Follow-up: "Is there a downside to using one snapshot for everything?" — Answer: yes — if the report runs for a long time, that snapshot could go stale relative to the live system by the time you review it; for very time-sensitive checks you'd re-snapshot deliberately, not accidentally.

Q3. What does Group-Object actually return, and how did we use .Group?

Answer: It returns one object per unique value of the grouped property, each with Name (the value), Count (how many items shared it), and Group (the original items themselves). We used .Group to pipe the original process objects for each name into Measure-Object -Sum to total their memory.

Follow-up: "Could you get the same total without Group-Object?" — Answer: yes, with Where-Object { $_.ProcessName -eq $Name } per name in a loop, but that's far less efficient and more code than one Group-Object call.
