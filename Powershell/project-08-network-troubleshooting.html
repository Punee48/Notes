The Story — Why We're Building This

A ticket comes in: WINAPP15 can't reach the core banking database server. Is it DNS? Is the server down? Is it a firewall blocking the specific port? Nobody knows yet, and manually running ping, then telnet, then nslookup by hand against every possible target takes time during an active incident.

Our manager wants one script that checks a defined list of critical targets — each with its expected port (e.g. the database server on port 1433, a web service on port 443) — and reports exactly which layer is failing: DNS resolution, ping reachability, or the specific port.

Concepts First — Before We Touch Code

1. The Three Layers of "Can I Reach This Server?"

1. DNS Resolution
→
2. Ping (ICMP)
→
3. Specific Port (TCP)
Why check all three separatelyEach layer fails for a different reason: DNS failure means the name doesn't resolve to an address at all. Ping failure with working DNS often means the server is down or ICMP is blocked. A working ping but a failed port test almost always means a firewall or the specific application/service isn't listening — three different root causes, three different fixes, and checking them separately tells you exactly where to look.

2. Resolve-DnsName

Resolve-DnsName -Name "example.com" -ErrorAction SilentlyContinue

Attempts to turn a hostname into an IP address, the same job nslookup does — if this fails, nothing past this point will work, regardless of firewalls or server health.

3. Test-Connection — Modern Ping

Test-Connection -ComputerName "example.com" -Count 2 -Quiet
  • -Count 2 — sends 2 ICMP echo requests instead of the default (which can vary by version).
  • -Quiet — instead of returning detailed ping results, returns a simple $true/$false — perfect for a health-check script that just needs a yes/no answer.

4. Test-NetConnection — Checking a Specific Port

Test-NetConnection -ComputerName "example.com" -Port 443 -InformationLevel Quiet
  • -Port 443 — attempts an actual TCP connection to that specific port, which is what proves an application is actually listening there, not just that the server itself is reachable.
  • -InformationLevel Quiet — same idea as -Quiet above: returns a simple boolean rather than a verbose diagnostic object.
Common ports worth knowing443 (HTTPS), 80 (HTTP), 1433 (SQL Server), 3389 (Remote Desktop), 5985/5986 (WinRM — we'll use these heavily starting with the remoting projects), 445 (SMB file shares).

5. Modeling Targets as an Array of PSCustomObjects

Instead of a flat array of names (Project 4's approach), each target here needs two pieces of information — a name and a port — so we model the list as an array of small objects, one per target.

$Targets = @(
    [PSCustomObject]@{ Name = "CoreDB01";  Port = 1433; Description = "Core Banking Database" },
    [PSCustomObject]@{ Name = "WebSvc01";  Port = 443;  Description = "Internal Web Service" }
)
Pattern evolutionNotice the progression across this course: Project 4 used a simple string array; here we need structured, multi-field data per item, so we reach for an array of objects instead. Recognizing when you've outgrown a simple list and need structured objects is a real design skill, not just syntax.

6. Combining Multiple Checks into One Overall Status

A target is only fully healthy if all three checks pass. We'll use -and (from Project 4) again here to combine three boolean results into one overall verdict, while still reporting each layer individually so the failure point is obvious.

Full Script — Test-NetworkConnectivity.ps1

# =====================================================================
# Test-NetworkConnectivity.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Check DNS, ping, and port reachability across critical targets
# =====================================================================

# ---------------------------------------------------------------
# Defined list of targets - each with a name, expected port, and description
# ---------------------------------------------------------------
$Targets = @(                                                    # Array of structured target objects
    [PSCustomObject]@{ Name = "www.microsoft.com"; Port = 443; Description = "Reference web endpoint (HTTPS)" },
    [PSCustomObject]@{ Name = "8.8.8.8";            Port = 53;  Description = "Public DNS server (should be reachable)" },
    [PSCustomObject]@{ Name = "doesnotexist.invalidbank.test"; Port = 443; Description = "Intentionally broken target - tests DNS failure" }
)

$Results = @()   # Will hold one result object per target

Write-Host "`n=== NETWORK CONNECTIVITY CHECK ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Loop through every target and run all three checks
# ---------------------------------------------------------------
foreach ($Target in $Targets) {                                  # $Target is one PSCustomObject per iteration

    Write-Host "`nChecking $($Target.Name) ($($Target.Description))..." -ForegroundColor Cyan

    # --- Check 1: DNS Resolution ---
    $DnsOk = $false                                                # Assume failure until proven otherwise
    try {
        Resolve-DnsName -Name $Target.Name -ErrorAction Stop | Out-Null   # Discards the result, we only care if it succeeded
        $DnsOk = $true                                              # Only reached if resolution succeeded
    }
    catch {
        $DnsOk = $false                                             # DNS resolution failed
    }

    # --- Check 2: Ping (ICMP) - only attempted if DNS succeeded, since a name that can't resolve can't be pinged ---
    $PingOk = $false
    if ($DnsOk) {                                                  # No point pinging a name that doesn't even resolve
        $PingOk = Test-Connection -ComputerName $Target.Name -Count 2 -Quiet -ErrorAction SilentlyContinue
    }

    # --- Check 3: Specific Port ---
    $PortOk = $false
    if ($DnsOk) {                                                  # Same reasoning - skip if DNS already failed
        $PortResult = Test-NetConnection -ComputerName $Target.Name -Port $Target.Port -InformationLevel Quiet -WarningAction SilentlyContinue
        $PortOk = $PortResult                                        # Test-NetConnection -InformationLevel Quiet returns a boolean directly
    }

    # --- Combine into an overall status ---
    $OverallOk = $DnsOk -and $PingOk -and $PortOk                  # All three must be true for full health

    $Status = if ($OverallOk) { "HEALTHY" }                         # if/else producing a value directly (Project 2/3/6 pattern)
              elseif (-not $DnsOk) { "DNS FAILURE" }
              elseif (-not $PingOk) { "UNREACHABLE (Ping Failed)" }
              else { "PORT BLOCKED ($($Target.Port))" }

    $Results += [PSCustomObject]@{                                  # Records this target's full result
        Target      = $Target.Name
        Description = $Target.Description
        DnsOk       = $DnsOk
        PingOk      = $PingOk
        PortOk      = $PortOk
        Port        = $Target.Port
        Status      = $Status
    }

    $Color = switch ($Status) {                                    # Reuses the switch-on-value pattern from Project 3
        "HEALTHY" { "Green" }
        default    { "Red" }
    }
    Write-Host "  Result: $Status" -ForegroundColor $Color
}

# ---------------------------------------------------------------
# STEP 2: Export the full report
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) {                                # Creates the reports folder if missing
    New-Item -ItemType Directory -Path ".\reports" | Out-Null
}
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"                    # Sortable timestamp for the filename
$Results | Export-Csv -Path ".\reports\NetworkCheck_$Timestamp.csv" -NoTypeInformation

# ---------------------------------------------------------------
# STEP 3: Summarize
# ---------------------------------------------------------------
$HealthyCount = ($Results | Where-Object { $_.Status -eq "HEALTHY" }).Count   # Counts fully healthy targets
$TotalCount   = $Results.Count

Write-Host "`n=== SUMMARY ===" -ForegroundColor Magenta
Write-Host "$HealthyCount of $TotalCount targets fully healthy." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

Resolve-DnsName -Name $Target.Name -ErrorAction Stop | Out-Null

  • Same try/catch-with-ErrorAction-Stop pattern from Projects 4 and 7 — we don't actually need the returned DNS records, only whether the call succeeded or threw, so the result is discarded with Out-Null (first seen in Project 6) rather than stored.

if ($DnsOk) { $PingOk = Test-Connection ... }

  • Skipping the ping and port checks entirely when DNS already failed avoids wasted time waiting on timeouts for a target we already know can't be reached by name — an efficiency detail that matters more as the target list grows.

$OverallOk = $DnsOk -and $PingOk -and $PortOk

  • Chaining -and across three boolean variables — all three must independently be $true for the combined expression to evaluate $true, extending the two-condition -and usage from Project 4 to three.

$Status = if ($OverallOk) {"HEALTHY"} elseif (-not $DnsOk) {"DNS FAILURE"} elseif (-not $PingOk) {...} else {...}

  • An if/elseif/elseif/else chain (Project 2's pattern) that pinpoints exactly which layer failed, checked in logical order: if DNS failed, nothing past it could have worked, so that's reported first; only if DNS succeeded but ping failed do we report a ping problem; only if both succeeded but the port didn't do we report a port-specific issue.

$Color = switch ($Status) { "HEALTHY" {"Green"} default {"Red"} }

  • The same status-to-color switch pattern from Project 3, simplified here to just two outcomes since every non-healthy status should read as a problem requiring attention.

Production Incident Walkthrough

Back to WINAPP15's database connectivity ticket: our script reports DNS resolves fine, ping succeeds, but port 1433 is blocked. That single line of output rules out "the server is down" and "DNS is broken" in seconds, and points the investigation directly at a firewall rule or the SQL Server service itself — not a network-wide outage.
  • Why does checking all three layers matter more than just "can I ping it"? A server can be fully up and pingable while the specific application port is still closed — pinging alone would have given a false sense that "the network is fine," sending the investigation in the wrong direction entirely.
  • Why skip ping/port checks after a DNS failure instead of still attempting them? Attempting a ping or port test against a name that can't resolve just wastes time on a guaranteed failure/timeout — once we know why it can't be reached, further checks at that target don't add new information.

Best practice reinforced hereStructuring the target list as objects with named fields (Name, Port, Description) instead of parallel arrays keeps related data bundled together — a lesson that will matter even more once configuration moves into external files (servers.csv, config.psd1) in upcoming intermediate projects.

Interview Preparation

Q1. Why check DNS, ping, and the specific port separately instead of just trying to connect to the application directly?

Answer: Each layer isolates a different possible root cause. Checking them independently and in order (DNS, then ping, then port) tells you precisely where connectivity breaks down instead of just "it doesn't work," which speeds up root-cause analysis significantly during an incident.

Follow-up: "What would you check next if all three of these pass but the application still doesn't work?" — Answer: application-layer issues — authentication, application logs, or the service's own health/response, since network-layer connectivity has already been ruled out at that point.

Q2. Why might ping fail while the server and application are both completely healthy?

Answer: Many production servers and firewalls deliberately block ICMP (ping) traffic for security reasons, even while allowing legitimate application traffic on specific ports — so a failed ping alone doesn't prove an outage.

Follow-up: "So why include a ping check in this script at all if it's not fully reliable?" — Answer: it's still useful as one data point (especially in environments where ICMP is allowed), and a ping failure combined with a DNS success at least narrows things toward "reachable by name but not responding at the network layer," which is still meaningful alongside the port test.

Q3. Why did the script switch from a plain string array (Project 4) to an array of PSCustomObjects for the target list?

Answer: Each target needs more than one associated piece of data (a port number and a description alongside the name) — a plain array of strings can only hold one value per item, so structured objects were needed to keep related fields bundled together per target.

Follow-up: "How would you load this same target list from an external CSV file instead of hardcoding it?" — Answer: Import-Csv -Path "targets.csv" returns exactly this same shape of objects automatically — we'll do exactly this in the upcoming CSV/data-driven configuration projects.
