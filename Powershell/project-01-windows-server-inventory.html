The Story — Why We're Building This

We've just joined the Windows Infrastructure Automation team at ABC Bank. The bank runs more than 1,000 Windows Servers across Development, QA, UAT, Production, and Disaster Recovery.

Every morning, the Windows Operations team manually logs into critical servers to check basic health information — hostname, OS version, uptime, memory, and disk space. It takes hours, and it's error-prone because it depends on someone remembering to check every server.

Our manager has given us our very first automation task: build a PowerShell script that collects basic inventory information from a Windows server and prints it in a clean, structured way. This is the foundation every later automation (health checks, patching, IIS, Active Directory) will build on.

Concepts First — Before We Touch Code

1. What is PowerShell?

PowerShell is a command-line shell and a scripting language built on the .NET runtime. Unlike older shells (like Command Prompt or Bash), PowerShell doesn't just move text around — it moves .NET objects. That single difference is why PowerShell is so powerful for Windows automation: when you ask for a list of services, you don't get a block of text you have to parse — you get real objects with properties and methods you can use directly.

Why does this exist?Windows administrators needed a way to automate repetitive administrative work (services, disks, event logs, AD) without writing full C# programs. Microsoft built PowerShell to expose the entire Windows management surface as scriptable objects.

3. Console, Windows Terminal, and VS Code

  • powershell.exe / pwsh.exe — the actual engine that runs your commands.
  • Windows Terminal — a modern terminal app that can host PowerShell, Command Prompt, and WSL in tabs. It's just the "window", not the engine.
  • VS Code + PowerShell Extension — where we'll actually write and debug scripts. It gives us IntelliSense, syntax checking, and a built-in debugger.

4. Cmdlets and Verb-Noun Naming

A cmdlet (pronounced "command-let") is a built-in PowerShell command. Every cmdlet follows a strict Verb-Noun naming pattern, e.g. Get-Service, Get-Process, Get-ComputerInfo. The verb tells you the action (Get, Set, New, Remove, Start, Stop), the noun tells you the target. This consistency means once you know the pattern, you can often guess a cmdlet's name.

Common mistakeBeginners often try to remember every cmdlet by heart. Instead, learn the verb list (Get-Verb) and rely on discovery commands (next section) — production engineers look things up constantly; that's normal.

5. Discovery Cmdlets: Get-Help, Get-Command, Get-Member

  • Get-Command *service* — finds cmdlets whose name contains "service".
  • Get-Help Get-Service -Full — shows full documentation, parameters, and examples for a cmdlet.
  • Get-Member — shows the type, properties, and methods of whatever object was piped into it. This is the single most important discovery tool in PowerShell.
Production habitWhenever you're unsure what an object looks like, pipe it into Get-Member. We'll do this constantly in this project.

6. Variables, Data Types, Arrays, Hash Tables

  • $Name = "WIN-SRV01" — a variable. The $ tells PowerShell "this word refers to a stored value", not a literal string or command name.
  • $Count = 5 — a number (integer).
  • $IsOnline = $true — a boolean ($true/$false).
  • $Servers = @("SRV01","SRV02") — an array: an ordered list of items. The @() tells PowerShell "build a collection", even if it ends up with one item or zero items.
  • $Config = @{ Name = "SRV01"; Env = "PROD" } — a hash table: key–value pairs, using @{}. Arrays are for ordered lists of similar items; hash tables are for named settings/lookups.

7. Objects, Properties, and Methods

Nearly everything in PowerShell is an object. An object has properties (data about it, e.g. $Server.Name) and methods (actions it can perform, e.g. $Service.Stop()). The dot (.) after a variable means "access something that belongs to this object".

8. The Pipeline — Objects, Not Text

Get-Service
→

→
Pipeline |
→

The pipe symbol | takes the objects produced by the command on its left and feeds them, one at a time, into the command on its right. Because these are real objects (not plain text lines like in Bash), the receiving command can filter, sort, or reformat based on actual properties — no text-parsing needed.

9. Select-Object, Where-Object, ForEach-Object, Sort-Object, Group-Object, Measure-Object

Sort-ObjectOrders objects by a property
Group-ObjectGroups objects by a shared property value
Measure-ObjectCalculates count, sum, average, min, max of property values

10. The Automatic Variable $_

$_ means "the current object flowing through the pipeline right now". Inside a Where-Object or ForEach-Object script block, $_ refers to whichever object is currently being processed.

11. File Operations (what we'll use here)

  • New-Item -ItemType Directory — creates a folder.
  • Out-File / Set-Content — writes text to a file.
  • Export-Csv — writes objects to a CSV file, preserving column structure.

12. CIM/WMI — How PowerShell Talks to Windows for Inventory Data

WMI (Windows Management Instrumentation) is Windows' built-in management database — it holds structured information about the OS, hardware, disks, and more. Get-CimInstance is the modern cmdlet that queries WMI through the CIM (Common Information Model) standard. We'll use it to pull OS name, version, and total memory.

Full Script — Get-ServerInventory.ps1

This is a complete, working script. Every important line has an inline comment. Save this exactly as Get-ServerInventory.ps1.

# =====================================================================
# Get-ServerInventory.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Collect basic inventory information from a Windows server
# =====================================================================

$ComputerName = $env:COMPUTERNAME          # Reads the local machine's name from an environment variable

Write-Host "Collecting inventory for $ComputerName..." -ForegroundColor Cyan   # Prints a status message in cyan text

# ---------------------------------------------------------------
# STEP 1: Get Operating System information using CIM
# ---------------------------------------------------------------
$OSInfo = Get-CimInstance -ClassName Win32_OperatingSystem   # Queries WMI/CIM for OS-level details as an object

# ---------------------------------------------------------------
# STEP 2: Get Computer System information (manufacturer, model, RAM)
# ---------------------------------------------------------------
$SystemInfo = Get-CimInstance -ClassName Win32_ComputerSystem   # Queries WMI/CIM for hardware-level details

# ---------------------------------------------------------------
# STEP 3: Get Disk information for all fixed local drives
# ---------------------------------------------------------------
$DiskInfo = Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=3"   # DriveType=3 means "local fixed disk"

# ---------------------------------------------------------------
# STEP 4: Calculate uptime from the OS's last boot time
# ---------------------------------------------------------------
$LastBoot = $OSInfo.LastBootUpTime          # Extracts the LastBootUpTime property from the OS object
$Uptime = (Get-Date) - $LastBoot            # Subtracts boot time from the current time to get a TimeSpan object

# ---------------------------------------------------------------
# STEP 5: Build a single, clean custom object with just what we need
# ---------------------------------------------------------------
$InventoryReport = [PSCustomObject]@{        # Creates a new custom object with named properties, in our own order
    ServerName      = $ComputerName                                   # Stores the computer name
    OperatingSystem = $OSInfo.Caption                                  # Human-readable OS name, e.g. "Microsoft Windows 11 Pro"
    OSVersion       = $OSInfo.Version                                  # Numeric OS version string
    Manufacturer    = $SystemInfo.Manufacturer                        # Hardware manufacturer (e.g. Dell, HP, VMware)
    Model           = $SystemInfo.Model                                # Hardware/VM model
    TotalMemoryGB   = [math]::Round($SystemInfo.TotalPhysicalMemory / 1GB, 2)  # Converts bytes to GB, rounds to 2 decimals
    LastBootTime    = $LastBoot                                       # When the machine was last started
    UptimeDays      = [math]::Round($Uptime.TotalDays, 2)             # Uptime expressed in days
}

# ---------------------------------------------------------------
# STEP 6: Build one object per disk (so CSV export has one row per disk)
# ---------------------------------------------------------------
$DiskReport = $DiskInfo | ForEach-Object {    # Sends each disk object, one at a time, into this script block
    [PSCustomObject]@{                        # Builds a clean custom object for this specific disk
        ServerName   = $ComputerName                                          # Repeats server name so each row is self-contained
        DriveLetter  = $_.DeviceID                                            # $_ is "this disk"; DeviceID is like "C:"
        SizeGB       = [math]::Round($_.Size / 1GB, 2)                        # Total disk size converted to GB
        FreeGB       = [math]::Round($_.FreeSpace / 1GB, 2)                   # Free space converted to GB
        FreePercent  = [math]::Round(($_.FreeSpace / $_.Size) * 100, 1)       # Free space as a percentage of total size
    }
}

# ---------------------------------------------------------------
# STEP 7: Display the results on screen
# ---------------------------------------------------------------
Write-Host "`n=== SERVER INVENTORY SUMMARY ===" -ForegroundColor Magenta   # Prints a section header; `n adds a blank line first
$InventoryReport | Format-List                                            # Displays the summary object, one property per line

Write-Host "`n=== DISK INVENTORY ===" -ForegroundColor Magenta            # Prints another section header
$DiskReport | Format-Table -AutoSize                                      # Displays disk rows as a neat auto-sized table

# ---------------------------------------------------------------
# STEP 8: Export both reports to CSV files for record-keeping
# ---------------------------------------------------------------
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"       # Builds a sortable timestamp string, e.g. 20260804_091530

$InventoryReport |                                     # Sends the summary object into the pipeline
    Export-Csv -Path ".\reports\Inventory_$Timestamp.csv" -NoTypeInformation   # Writes it to CSV without the extra .NET type header line

$DiskReport |                                          # Sends the disk rows into the pipeline
    Export-Csv -Path ".\reports\Disks_$Timestamp.csv" -NoTypeInformation       # Writes disk data to its own CSV file

Write-Host "`nReports saved to .\reports\" -ForegroundColor Green   # Confirms where the output files were saved

Line-by-Line Explanation

We already explained the concepts above. Here we walk through the exact symbols and syntax used in this specific script, piece by piece, so nothing is assumed.

$ComputerName = $env:COMPUTERNAME

  • $ComputerName — a new variable we are creating to hold the machine name.
  • = — the assignment operator: "store the right-hand value into the left-hand variable".
  • $env:COMPUTERNAME — an environment variable. The $env: prefix tells PowerShell "look this up in the operating system's environment variables", not in our script's own variables.

Get-CimInstance -ClassName Win32_OperatingSystem

  • Get-CimInstance — the cmdlet that queries the CIM/WMI management layer.
  • -ClassName — a named parameter telling the cmdlet which WMI class to query.
  • Win32_OperatingSystem — the specific WMI class that holds OS-level data (caption, version, boot time, etc).

Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=3"

  • -Filter — a parameter that lets WMI filter results on the server side (inside the query itself), which is more efficient than pulling everything and filtering afterward with Where-Object.
  • "DriveType=3" — a WMI query string; DriveType 3 specifically means "local fixed disk" (as opposed to removable, network, or CD-ROM drives).

$Uptime = (Get-Date) - $LastBoot

  • (Get-Date) — the parentheses force PowerShell to run Get-Date first and use its result, rather than treating the whole line differently.
  • - — here the minus operator is being used on two DateTime objects. PowerShell is smart enough to know that subtracting one date from another produces a TimeSpan object (a duration), not a plain number.

[PSCustomObject]@{ ServerName = $ComputerName; ... }

  • [PSCustomObject] — a type accelerator that tells PowerShell "build a real custom object", not just a hash table.
  • @{ } — a hash table literal listing key–value pairs. When cast to [PSCustomObject], each key becomes a property name, and property order is preserved exactly as written — this matters because it controls the column order later in Format-Table and CSV export.
  • ServerName = $ComputerName — inside the hash table, = assigns a value to a named key/property.

[math]::Round($SystemInfo.TotalPhysicalMemory / 1GB, 2)

  • [math] — refers to the .NET System.Math class directly. PowerShell can call .NET classes with square brackets when there's no cmdlet for what we need.
  • ::Round(...) — the double-colon calls a static method (a method that belongs to the class itself, not to a specific object instance).
  • $SystemInfo.TotalPhysicalMemory — the dot accesses the TotalPhysicalMemory property (in raw bytes) on the $SystemInfo object.
  • / 1GB — PowerShell has built-in size constants (1KB, 1MB, 1GB, 1TB) that are just large numbers under the hood. Dividing bytes by 1GB converts the value to gigabytes.
  • , 2 — the second argument to Round: "round to 2 decimal places".

$DiskInfo | ForEach-Object { [PSCustomObject]@{ ... $_.DeviceID ... } }

  • | — pipes each disk object from $DiskInfo into the next command, one at a time.
  • ForEach-Object { } — runs the code inside the curly braces once for every object received.
  • $_ — inside that script block, represents "the current disk object being processed right now".
  • $_.DeviceID — the drive letter property of the current disk (e.g. "C:").

Write-Host "`n=== SERVER INVENTORY SUMMARY ===" -ForegroundColor Magenta

  • Write-Host — prints directly to the console. Unlike Write-Output, its output cannot be captured by the pipeline — it's for human-facing display only. (We'll cover why that distinction matters for automation in a later project.)
  • ` n (backtick-n) — an escape sequence inside a double-quoted string meaning "insert a newline here". The backtick is PowerShell's escape character.
  • -ForegroundColor Magenta — a parameter that sets the text color in the console.

Export-Csv -Path ".\reports\Inventory_$Timestamp.csv" -NoTypeInformation

  • Export-Csv — converts pipeline objects into CSV rows and writes them to a file.
  • -Path — where to save the file. .\ means "relative to the current folder".
  • $Timestamp inside the double-quoted string — PowerShell automatically substitutes the variable's value into the string; this is called string interpolation.
  • -NoTypeInformation — by default, older PowerShell versions add a comment line at the top of the CSV describing the .NET type. This switch removes that line so the CSV opens cleanly in Excel.

  • PowerShell Host — the program you typed into (VS Code terminal, Windows Terminal, ISE). It's just the "window".
  • PowerShell Engine — the actual runtime that interprets and executes your script.
  • Parser — reads your script's text and checks it's syntactically valid PowerShell.
  • Command Discovery — for each cmdlet name (like Get-CimInstance), the engine locates which module/binary actually implements it.
  • Parameter Binding — matches the values you typed (like -ClassName Win32_OperatingSystem) to the cmdlet's defined parameters.
  • Pipeline Execution — objects flow from one cmdlet to the next through |.
  • .NET / CIM Objects — the actual data returned, backed by .NET types under the hood.
  • Console + CSV Output — the final human-readable and file-based results we produced.

WMI is a long-standing Windows management framework. When you call Get-CimInstance, PowerShell talks to a background Windows process that queries the WMI repository (a structured database of system information maintained by Windows itself) and hands the results back as objects.

Troubleshooting Cheat Sheet

SymptomLikely Root CauseFix
Script won't run: "cannot be loaded because running scripts is disabled" Execution Policy is set to Restricted Run Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass for the current session, or -Scope CurrentUser for a lasting local change
"Get-CimInstance is not recognized" Very old PowerShell version, or a broken/incomplete install Check $PSVersionTable.PSVersion; install PowerShell 7 from Microsoft's official source
Disk report shows no rows -Filter "DriveType=3" excluded all drives (e.g. running inside a container/VM with unusual disk types) Temporarily remove the filter, inspect DriveType values with Get-Member, then adjust
CSV file not created The reports folder doesn't exist, or you're in the wrong working directory Confirm your folder with Get-Location; re-run Step 3 from the lab to create .\reports
Numbers show too many decimal places or look wrong Division was done before unit conversion, or rounding wasn't applied Double-check the order of operations: divide by 1GB first, then round
Debugging tipWhen something looks wrong, don't guess — insert a temporary line like $OSInfo | Get-Member right after the query to see every real property name available. Remove it once you've confirmed what you need.

Common Mistakes to Avoid

  • Using Write-Host everywhere instead of returning real objects — makes output impossible to reuse or pipe further.
  • Filtering with Where-Object when the source cmdlet already supports server-side filtering (like WMI's -Filter) — slower and less efficient.
  • Forgetting that dividing large byte counts without converting units produces misleading numbers.

Interview Preparation

Q1. What's the core difference between PowerShell and traditional shells like Bash?

Answer: Traditional shells pass plain text between commands, requiring text parsing (grep, awk, sed). PowerShell passes structured .NET objects through the pipeline, so downstream commands can access real properties and methods directly, without parsing strings.

Follow-up: "Can you give an example of a bug this design prevents?" — Answer: parsing failures when column widths or locale-based date formats change; with objects, you access .Name or .Date directly regardless of display formatting.

Q2. What does $_ represent, and where can you use it?

Answer: It's an automatic variable representing the current object in the pipeline, valid inside script blocks like Where-Object, ForEach-Object, and Process blocks of advanced functions.

Follow-up: "What happens if you use $_ outside a pipeline script block?" — Answer: it will be $null or refer to an unrelated value; it only has meaning inside a block actively receiving pipeline input.

Q3. Why did we use Get-CimInstance instead of the older Get-WmiObject?

Answer: Get-CimInstance is the modern replacement — it works over WS-Management (used for remoting later), is cross-platform-compatible in PowerShell 7, and is actively maintained. Get-WmiObject is deprecated and removed entirely from PowerShell 7.

Follow-up: "What protocol does Get-CimInstance use for remote queries?" — Answer: WSMan/WinRM by default (we'll cover this deeply in the remoting projects).

Q4. Why build a [PSCustomObject] instead of just printing strings?

Answer: Objects preserve structure and types, can be piped into Export-Csv, ConvertTo-Json, filtering, or sorting — string output can only be displayed, not reused.

Follow-up: "How would you turn this into JSON instead of CSV?" — Answer: pipe the object into ConvertTo-Json and write it with Set-Content — we'll do this in a later project.
