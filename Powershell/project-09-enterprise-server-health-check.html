🚀 Welcome to Stage 2 — Intermediate

Beginner-stage projects hardcoded almost everything — server names, thresholds, target lists — directly in the script. That's fine for learning one concept at a time, but it means changing anything requires editing code. Stage 2 shifts toward data-driven automation: scripts that read their configuration from external files, so the same script can run against 1 server or 500 without a single code change.

Quick Recap of the Beginner Stage (Projects 1–8)

We built individual checks for disk space (Project 2), services (Project 4), and network connectivity (Project 8) — each as its own standalone script with hardcoded values. Today we combine all three into one unified health check, and take the first step toward removing hardcoded values by reading server lists and thresholds from external files instead.

The Story — Why We're Building This

Operations currently runs three separate scripts every morning — one for disks, one for services, one for connectivity — against a list of servers someone maintains by memory. Our manager wants one unified health check that runs all three checks per server, reads the server list from a CSV file the team can update without touching any code, and reads its thresholds from a separate settings file — exactly the kind of separation between "code" and "configuration" that real enterprise automation requires.

Concepts First — Before We Touch Code

1. Why Separate Configuration from Code

The core principleHardcoded values mean every change requires editing and re-testing a script. External configuration means the Operations team can update the server list or a threshold themselves, safely, without touching PowerShell code at all — and the script itself never needs to change just because the environment did.

2. CSV Configuration with Import-Csv

ServerName,CheckDisk,CheckServices,ServicesToCheck
localhost,Yes,Yes,"Spooler;BITS"
$Servers = Import-Csv -Path ".\config\servers.csv"   # Reads the CSV and returns an array of PSCustomObjects
  • Import-Csv — reads a CSV file and automatically converts each row into a PSCustomObject, with column headers becoming property names. This is the same object shape we've been building manually with [PSCustomObject]@{} since Project 1 — now it comes straight from a file instead.

3. PowerShell Data Files (.psd1) for Settings

A .psd1 file holds structured settings using PowerShell's own hash table syntax — safer than a script file because it can only contain data, never executable code.

@{
    DiskWarningPercent  = 20
    DiskCriticalPercent = 10
    ReportPath          = ".\reports"
}
$Config = Import-PowerShellDataFile -Path ".\config\settings.psd1"   # Safely loads the settings as a hash table
  • Import-PowerShellDataFile — reads a .psd1 file into a hash table. It's deliberately restricted to only understand data (numbers, strings, hash tables, arrays) — it will refuse to run a file containing actual commands, which makes it a safer choice than dot-sourcing a script for configuration purposes.

4. Splatting — Passing a Hash Table as Parameters

When a cmdlet call has many parameters, splatting lets you define them once in a hash table and pass the whole thing at once, instead of a long, hard-to-read single line.

$PortTestParams = @{                          # Defines the parameters as a hash table
    ComputerName      = $ServerName
    Port              = 445
    InformationLevel  = "Quiet"
    WarningAction     = "SilentlyContinue"
}
$PortOk = Test-NetConnection @PortTestParams   # The @ sign "splats" the hash table as named parameters
  • The @ sign (instead of $) in front of the variable name is what triggers splatting — it tells PowerShell "unpack this hash table's keys and values as separate named parameters," rather than passing the hash table itself as a single argument.
Why this mattersBeyond readability, splatting means the same parameter set can be reused across multiple calls, or conditionally built up (adding a key only if needed) before the actual cmdlet call — something a long inline parameter list can't do cleanly.

5. Combining Three Existing Checks into One Function

Rather than copy-pasting the disk/service/connectivity logic from Projects 2, 4, and 8, we wrap each as its own function and call all three per server — the same "reusable function" idea from Project 2, now composing multiple functions together.

Full Script — Invoke-ServerHealthCheck.ps1

# =====================================================================
# Invoke-ServerHealthCheck.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Unified disk/service/connectivity health check, driven by config files
# =====================================================================

# ---------------------------------------------------------------
# STEP 1: Load configuration from external files - nothing hardcoded here
# ---------------------------------------------------------------
$Config  = Import-PowerShellDataFile -Path ".\config\settings.psd1"   # Loads thresholds and paths as a hash table
$Servers = Import-Csv -Path ".\config\servers.csv"                     # Loads the server list as objects

Write-Host "`n=== ENTERPRISE SERVER HEALTH CHECK ===" -ForegroundColor Magenta
Write-Host "Loaded $($Servers.Count) server(s) from config.`n" -ForegroundColor Cyan

# ---------------------------------------------------------------
# FUNCTION: Disk check (based on Project 2's logic, now threshold-driven by $Config)
# ---------------------------------------------------------------
function Test-DiskHealth {
    param([string]$ServerName)                              # Which server to check

    $Disks = Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=3" -ComputerName $ServerName -ErrorAction SilentlyContinue

    $WorstStatus = "HEALTHY"                                 # Assume healthy until a worse disk is found
    foreach ($Disk in $Disks) {                                # Checks every local fixed disk
        $FreePercent = [math]::Round(($Disk.FreeSpace / $Disk.Size) * 100, 1)

        if ($FreePercent -lt $Config.DiskCriticalPercent) { $WorstStatus = "CRITICAL" }        # Worst possible result
        elseif ($FreePercent -lt $Config.DiskWarningPercent -and $WorstStatus -ne "CRITICAL") { $WorstStatus = "WARNING" }  # Only downgrade if not already CRITICAL
    }
    return $WorstStatus                                        # One combined result for all disks on this server
}

# ---------------------------------------------------------------
# FUNCTION: Service check (based on Project 4's logic)
# ---------------------------------------------------------------
function Test-ServiceHealth {
    param(
        [string]$ServerName,                                  # Which server to check
        [string[]]$ServiceNames                                 # Array of service names to verify
    )

    $AllRunning = $true                                          # Assume healthy until proven otherwise
    foreach ($SvcName in $ServiceNames) {                          # Checks each named service
        try {
            $Svc = Get-Service -Name $SvcName -ComputerName $ServerName -ErrorAction Stop
            if ($Svc.Status -ne "Running") { $AllRunning = $false }   # Any non-running service fails the check
        }
        catch {
            $AllRunning = $false                                     # A missing service also fails the check
        }
    }
    if ($AllRunning) { return "HEALTHY" } else { return "ISSUE FOUND" }
}

# ---------------------------------------------------------------
# FUNCTION: Connectivity check (based on Project 8's logic, using splatting)
# ---------------------------------------------------------------
function Test-ServerConnectivity {
    param([string]$ServerName)                                 # Which server to check

    $PortTestParams = @{                                         # Splatted parameter set (concept #4 above)
        ComputerName     = $ServerName
        Port             = 445                                    # SMB - a reasonable general "is it up" port
        InformationLevel = "Quiet"
        WarningAction    = "SilentlyContinue"
    }
    $PortOk = Test-NetConnection @PortTestParams                  # Splats the hash table as named parameters

    if ($PortOk) { return "REACHABLE" } else { return "UNREACHABLE" }
}

# ---------------------------------------------------------------
# STEP 2: Run all applicable checks per server, based on the CSV's Yes/No flags
# ---------------------------------------------------------------
$Results = @()   # Will hold one combined result object per server

foreach ($Server in $Servers) {                                  # $Server is one row from servers.csv

    Write-Host "Checking $($Server.ServerName)..." -ForegroundColor Cyan

    $DiskStatus = "SKIPPED"                                        # Default if this check wasn't requested
    if ($Server.CheckDisk -eq "Yes") {                               # Only runs if the CSV said to
        $DiskStatus = Test-DiskHealth -ServerName $Server.ServerName
    }

    $ServiceStatus = "SKIPPED"
    if ($Server.CheckServices -eq "Yes") {                           # Only runs if the CSV said to
        $ServiceList = $Server.ServicesToCheck -split ";"              # Splits "Spooler;BITS" into an array
        $ServiceStatus = Test-ServiceHealth -ServerName $Server.ServerName -ServiceNames $ServiceList
    }

    $ConnStatus = Test-ServerConnectivity -ServerName $Server.ServerName   # Always checked - baseline reachability

    $Results += [PSCustomObject]@{                                  # One combined record per server
        ServerName      = $Server.ServerName
        DiskStatus      = $DiskStatus
        ServiceStatus   = $ServiceStatus
        Connectivity    = $ConnStatus
        CheckedAt       = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }
}

# ---------------------------------------------------------------
# STEP 3: Display and export the combined report
# ---------------------------------------------------------------
Write-Host "`n=== RESULTS ===" -ForegroundColor Magenta
$Results | Format-Table -AutoSize

if (-not (Test-Path $Config.ReportPath)) {                        # Uses the path FROM CONFIG, not hardcoded
    New-Item -ItemType Directory -Path $Config.ReportPath | Out-Null
}
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path "$($Config.ReportPath)\HealthCheck_$Timestamp.csv" -NoTypeInformation

Write-Host "`nReport saved to $($Config.ReportPath)\" -ForegroundColor Green

Line-by-Line Explanation

$Config = Import-PowerShellDataFile -Path ".\config\settings.psd1"

  • After this line, $Config is a plain hash table — $Config.DiskWarningPercent works exactly like accessing a property, because hash table keys and object properties both use dot notation in PowerShell.

if ($FreePercent -lt $Config.DiskCriticalPercent) { $WorstStatus = "CRITICAL" }

  • Same threshold-comparison logic from Project 2's Get-DiskStatus function, but the numbers now come from the loaded config file instead of being typed directly into the script — change the .psd1 file, and every future run uses the new threshold automatically.

elseif ($FreePercent -lt $Config.DiskWarningPercent -and $WorstStatus -ne "CRITICAL")

  • The extra -and $WorstStatus -ne "CRITICAL" condition prevents a later, less-severe disk from downgrading an already-CRITICAL result back to WARNING — since we're now checking multiple disks per server and need to preserve the worst result across all of them, not just the last one checked.

$ServiceList = $Server.ServicesToCheck -split ";"

  • CSV cells can only hold plain text, so multiple service names are packed into one cell separated by semicolons ("Spooler;BITS"). The -split operator (first seen in Project 7) turns that single string back into a proper array we can loop over.

$PortOk = Test-NetConnection @PortTestParams

  • This single line is equivalent to writing Test-NetConnection -ComputerName $ServerName -Port 445 -InformationLevel Quiet -WarningAction SilentlyContinue — splatting doesn't change what happens, only how readable and reusable the parameter list is.

[string[]]$ServiceNames (in the function's param block)

  • [string[]] — the square brackets after the type mean "an array of this type," constraining the parameter to accept a list of strings rather than a single one, matching what -split produces.

Architecture & Configuration Flow

$Config hash table

→

$Servers objects
$Config + $Servers
→
Per-Server Function Calls

Combined Report

Notice the script itself contains zero server names and zero threshold numbers — every environment-specific value flows in from the two config files. This is the architectural shift Stage 2 is built around: the logic lives in the script; the environment-specific facts live in configuration, and the two never mix.

Production Incident Walkthrough

Six months from now, ABC Bank decommissions a server and onboards three new ones. With the old three separate hardcoded scripts, someone would need to edit and re-test three different .ps1 files. With this unified, config-driven version, Operations just edits servers.csv — no PowerShell knowledge, no code review, no risk of breaking script logic while updating a server list.
  • Why put thresholds in a separate file from the server list? They change for different reasons and on different schedules — thresholds might be tuned occasionally by the automation team, while the server list changes routinely as infrastructure changes. Separating them means each can be owned and edited by the right people without touching the other.
  • Why use .psd1 for settings instead of another CSV? Settings here are a small, fixed set of named values (not a repeating list of rows), which fits a hash table naturally — and Import-PowerShellDataFile's restriction to data-only content makes it a safer choice than a script file for something Operations might edit.

Security & Best Practices

Best practice reinforced hereImport-PowerShellDataFile was chosen deliberately over dot-sourcing a .ps1 settings file — a .psd1 file cannot contain executable commands, so even if it were tampered with, it couldn't be used to run arbitrary code through this script. Prefer data-only formats for configuration whenever the content doesn't need to execute anything.
Still no credentials in this projectAll checks in this lab run locally; once we reach the remoting projects, we'll extend this exact config-driven structure to support PSCredential per server, rather than hardcoding anything sensitive into CSV or psd1 files.

Common Mistakes to Avoid

  • Hardcoding a fallback value "just in case" the config file is missing, defeating the purpose of externalizing it.
  • Letting a later, healthier sub-check silently overwrite an earlier CRITICAL result.
  • Putting frequently-changing data (like a server list) into the same file as rarely-changing settings.

Interview Preparation

Q1. Why separate the server list (CSV) from the settings (psd1) instead of one combined config file?

Answer: They have different shapes (a repeating list of rows vs a fixed set of named settings) and different change patterns (frequent list updates vs occasional threshold tuning) — keeping them separate lets each be owned, edited, and validated independently without one change risking the other.

Follow-up: "What would you do if you needed per-server thresholds instead of one global set?" — Answer: add threshold columns directly to servers.csv, or move to a richer format like JSON that can nest settings per server — we'll cover JSON specifically in an upcoming project.

Q2. What does splatting actually change about how a cmdlet call executes?

Answer: Nothing about execution — splatting is purely a readability and reusability convenience; Test-NetConnection @PortTestParams and writing out every -Param value individually produce identical results. The benefit is being able to build, inspect, reuse, or conditionally modify the parameter set before the call happens.

Follow-up: "Can you combine splatting with additional individual parameters on the same call?" — Answer: yes — you can splat a hash table and still add explicit -Parameter value pairs on the same line as long as there's no conflict between them.

Q3. Why did Test-DiskHealth need extra logic to avoid downgrading a CRITICAL result?

Answer: A server can have multiple disks; if disk C: is CRITICAL but disk D: is only WARNING and gets checked afterward in the loop, a naive implementation would let the WARNING result overwrite the CRITICAL one — the added condition ensures the function always reports the single worst status found across all disks, not just whichever was checked last.

Follow-up: "How would you report all disk issues individually instead of just the worst one?" — Answer: instead of tracking a single $WorstStatus string, build an array of per-disk result objects (like Project 2 did) and return the whole collection, letting the caller decide how to summarize it.
