Quick Recap of Projects 1–27

Project 27 audited who has access to privileged groups. This project asks a related question from a different angle: are there accounts nobody's actually using anymore? Dormant accounts are a real security exposure — every one is a credential that could be compromised and go unnoticed, since nobody's watching it. We'll reuse Project 2/20's threshold-classification pattern, and Project 21's defense-in-depth caution for the optional disable action.

The Story — Why We're Building This

An auditor's question during ABC Bank's annual security review: "How many accounts in your domain haven't logged in for over 90 days, and what's your process for handling them?" Nobody has a good answer — there's no routine check for this. Our manager wants a report of inactive accounts, classified by how long they've been dormant, with a clearly separate, cautiously-guarded option to actually disable the most severely inactive ones.

Concepts First — Before We Touch Code

1. LastLogonDate — and Its Important Limitation

The single most important thing to understand in this project AD accounts have both lastLogon (not replicated between domain controllers — only accurate on the specific DC a user last authenticated against) and lastLogonTimestamp (replicated, but only updated roughly every 9-14 days by default, not on every single logon). PowerShell's convenient LastLogonDate property is based on the replicated lastLogonTimestamp — meaning it can be up to ~2 weeks "behind" reality. A report treating LastLogonDate as perfectly precise could be off by two weeks in either direction.

2. Why This Matters for Threshold Design

Given that built-in imprecision, thresholds for "inactive" should be set with enough margin that a 2-week measurement uncertainty doesn't matter much — a 90-day threshold easily absorbs a 2-week margin of error; a 14-day threshold would not.

3. Search-ADAccount — A Purpose-Built Alternative

Search-ADAccount -AccountInactive -TimeSpan "90.00:00:00" -UsersOnly
  • Search-ADAccount -AccountInactive -TimeSpan — a cmdlet specifically built for this exact use case, handling the LastLogonDate lookup and comparison internally.
  • -TimeSpan "90.00:00:00" — a TimeSpan string format: days.hours:minutes:seconds, here meaning 90 days.
  • -UsersOnly — excludes computer accounts, which also have logon timestamps but represent a different kind of "inactivity" not relevant to a people-focused audit.

4. Threshold Classification — Reused from Projects 2 and 20

Same shape again: Warning at (say) 60 days, Critical at 90+ days, giving Operations a sense of urgency rather than one flat "inactive" bucket.

5. Detection vs the Optional Disable — Extra Caution, Like Project 21

Disabling an account is reversible, but still needs real caution Unlike deleting a certificate (Project 21) or removing a firewall rule, disabling an AD account is relatively easy to reverse — but a wrongly-disabled account for someone on extended leave, or a service account whose "user" never logs in interactively by design, can still cause a real, disruptive incident. This script keeps disable as a distinct, separately-invoked, ShouldProcess-guarded action — never bundled automatically into the detection run.

6. Excluding Service Accounts and Known Exceptions

Some accounts (service accounts, break-glass emergency accounts) may legitimately show no interactive logon for long periods by design — a config-driven exclusion list (Project 9's pattern) prevents these from being flagged or, worse, disabled incorrectly.

Full Script — Find-InactiveAccounts.ps1

# =====================================================================
# Find-InactiveAccounts.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Detect (and optionally, cautiously, disable) inactive AD accounts
# NOTE: LastLogonDate can lag real activity by up to ~2 weeks (replication interval)
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]
param(
    [switch]$WhatIf = $true,
    [switch]$DisableCritical              # Opt-in only - detection always runs regardless; this just enables the extra disable step
)

Import-Module ActiveDirectory -ErrorAction Stop

$WarningDays  = 60
$CriticalDays = 90
$ExcludedAccounts = (Import-Csv ".\config\excluded-accounts.csv").SamAccountName   # Service accounts / known exceptions

$LogPath = ".\logs\InactiveAccounts.log"
function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

Write-Host "`n=== INACTIVE ACCOUNT DETECTION ===" -ForegroundColor Magenta
Write-Host "Note: LastLogonDate can lag real activity by up to ~2 weeks due to AD replication.`n" -ForegroundColor Yellow

# ---------------------------------------------------------------
# STEP 1: Find accounts inactive beyond the WARNING threshold (broadest net)
# ---------------------------------------------------------------
$InactiveAccounts = Search-ADAccount -AccountInactive -TimeSpan "$WarningDays.00:00:00" -UsersOnly |
    Where-Object { $_.Enabled -eq $true }                              # Only currently-enabled accounts are meaningful findings

$Results = @()

foreach ($Account in $InactiveAccounts) {                              # Loops through every inactive account found

    if ($Account.SamAccountName -in $ExcludedAccounts) {                 # Skips known service/exception accounts entirely
        continue
    }

    $DaysInactive = if ($Account.LastLogonDate) {
        ((Get-Date) - $Account.LastLogonDate).Days
    } else {
        "Never logged on"                                                  # Some accounts may have NO recorded logon at all
    }

    # ---------------------------------------------------------------
    # STEP 2: Classify (Project 2/20's threshold pattern, reused)
    # ---------------------------------------------------------------
    $Status = if ($DaysInactive -eq "Never logged on") { "CRITICAL (never logged on)" }
              elseif ($DaysInactive -ge $CriticalDays) { "CRITICAL" }
              elseif ($DaysInactive -ge $WarningDays) { "WARNING" }
              else { "HEALTHY" }                                            # Shouldn't occur given the search threshold, but kept for completeness

    $Results += [PSCustomObject]@{
        SamAccountName = $Account.SamAccountName
        Name           = $Account.Name
        LastLogonDate  = $Account.LastLogonDate
        DaysInactive   = $DaysInactive
        Status         = $Status
    }

    $Color = if ($Status -like "CRITICAL*") { "Red" } else { "Yellow" }
    Write-Host "  [$Status] $($Account.SamAccountName) - last logon: $(if($Account.LastLogonDate){$Account.LastLogonDate}else{'never'})" -ForegroundColor $Color
}

# ---------------------------------------------------------------
# STEP 3: Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\InactiveAccounts_$Timestamp.csv" -NoTypeInformation

$CriticalList = $Results | Where-Object { $_.Status -like "CRITICAL*" }
Write-Host "`nSummary: $($CriticalList.Count) CRITICAL, $(($Results | Where-Object {$_.Status -eq 'WARNING'}).Count) WARNING inactive account(s)." -ForegroundColor Cyan

# ---------------------------------------------------------------
# STEP 4: OPT-IN ONLY - disable CRITICAL accounts, with extra guarding
# ---------------------------------------------------------------
if ($DisableCritical) {
    Write-Host "`n--- DISABLE CRITICAL ACCOUNTS (opt-in) ---" -ForegroundColor Red

    foreach ($Critical in $CriticalList) {

        # Re-verify the exclusion list ONE MORE TIME immediately before disabling - Project 21's defense-in-depth pattern
        if ($Critical.SamAccountName -in $ExcludedAccounts) {
            Write-Log -Status "ERROR" -Message "SAFETY CHECK: skipped $($Critical.SamAccountName) - on exclusion list"
            continue
        }

        if ($PSCmdlet.ShouldProcess($Critical.SamAccountName, "Disable Inactive AD Account")) {
            Disable-ADAccount -Identity $Critical.SamAccountName
            Write-Log -Status "SUCCESS" -Message "Disabled inactive account: $($Critical.SamAccountName) (inactive $($Critical.DaysInactive) days)"
            Write-Host "  Disabled: $($Critical.SamAccountName)" -ForegroundColor Green
        }
        else {
            Write-Host "  PREVIEW: Would disable $($Critical.SamAccountName)" -ForegroundColor Yellow
        }
    }
}
else {
    Write-Host "`n(Run with -DisableCritical to enable the opt-in disable step for CRITICAL accounts.)" -ForegroundColor Cyan
}

Line-by-Line Explanation

Search-ADAccount -AccountInactive -TimeSpan "$WarningDays.00:00:00" -UsersOnly

  • Building the TimeSpan string from the $WarningDays variable rather than hardcoding "60" — the search casts the widest net (WARNING threshold) so both WARNING and CRITICAL accounts get picked up in one query, with classification happening afterward in code.

Where-Object { $_.Enabled -eq $true }

  • Filters out accounts that are already disabled — an already-disabled inactive account isn't a new finding worth flagging; it's already in the desired state, similar in spirit to Project 4's idempotent "already healthy, no action needed" checks.

$DaysInactive = if ($Account.LastLogonDate) { ((Get-Date) - $Account.LastLogonDate).Days } else { "Never logged on" }

  • Some accounts (created but never used, or very old accounts predating reliable logon tracking) can have a completely empty LastLogonDate — treating that as its own labeled case, rather than crashing on the date math or misreporting it as some default number, keeps the report both accurate and honest.

The re-check of $ExcludedAccounts immediately before Disable-ADAccount

  • Directly mirrors Project 21's double-check pattern — even though the exclusion filter was already applied earlier when building $Results, re-verifying it again immediately before the irreversible-feeling action (disabling someone's account) provides the same defense-in-depth protection against a future code change accidentally weakening the earlier filter.

if ($DisableCritical) { ... } else { Write-Host "(Run with -DisableCritical...)" }

  • The disable step is gated behind an entirely separate opt-in switch, not just -WhatIf:$false — someone must explicitly ask for disabling to even be considered, on top of then needing to also pass -WhatIf:$false for it to actually happen. Two independent, deliberate opt-ins are required before anything gets disabled.

Detection and disabling are architecturally two separate paths through this script, joined only by sharing the same classification data — detection always runs and is always safe; disabling requires two separate, explicit opt-ins layered on top. This mirrors the deliberate friction built into Project 25's restore operation: the more consequential the action, the more explicit steps should stand between "script runs" and "change happens."

Production Incident Walkthrough

The first run of this detection script (no disable, just reporting) turns up 40 accounts inactive over 90 days. Manual review by the security team finds most are genuinely departed contractors and former employees whose accounts were never cleaned up — but two are legitimate employees who were on extended medical leave, correctly excluded from disabling by being added to the exclusion list before anyone ever ran -DisableCritical.
  • Why does running detection-only first, before ever considering the disable option, matter here? It gives humans a chance to review the findings and update the exclusion list (or investigate individual cases) before any account is actually touched — exactly the workflow this script's two-step opt-in design encourages, rather than a single command that detects and disables in the same breath.

Security & Best Practices

The core lesson of this projectEven a relatively reversible action (disabling, not deleting) deserves layered, deliberate friction when it operates at scale across potentially many accounts automatically — two separate opt-ins (a dedicated switch, plus -WhatIf:$false) make it very unlikely anyone triggers disabling by accident.
Best practice reinforced hereUnderstanding a data source's real-world limitations (LastLogonDate's replication lag) before building logic on top of it prevents a whole class of "the report is technically wrong" problems — always understand what a property actually measures, not just what its name suggests.

Common Mistakes to Avoid

  • Treating LastLogonDate as perfectly precise, especially for tight thresholds.
  • Forgetting to exclude legitimate service/exception accounts before disabling anything.
  • Bundling detection and disabling into one automatic step with no separate opt-in.
  • Crashing or misreporting on accounts with no recorded logon at all.

Interview Preparation

Q1. Why can LastLogonDate be inaccurate by up to two weeks, and why does that matter for this script's design?

Answer: LastLogonDate is based on lastLogonTimestamp, which is deliberately only replicated across domain controllers every 9-14 days by default (to limit replication traffic) rather than on every single logon — so a very recent logon might not yet be reflected. Thresholds need enough margin (this script uses 60/90 days) that this lag doesn't meaningfully affect the classification.

Follow-up: "How would you get more precise, real-time logon information if you truly needed it?" — Answer: query the non-replicated lastLogon attribute directly against every domain controller and take the most recent value found — more accurate but significantly more expensive to query across a large domain.

Q2. Why does disabling require both a separate -DisableCritical switch AND -WhatIf:$false, rather than just one flag?

Answer: Layering two independent, deliberate opt-ins makes it very unlikely someone triggers account disabling by accident — a single flag could be added carelessly or copy-pasted from an example without full consideration, while requiring two separate deliberate choices adds meaningful, appropriate friction for an action affecting potentially many people's accounts at once.

Follow-up: "Is there a risk that too much friction discourages legitimate use of the automation?" — Answer: possibly, which is why detection (the safe, always-valuable part) runs unconditionally and needs no special flags at all — the friction is deliberately concentrated only around the genuinely risky action, not the reporting.

Q3. Why exclude service accounts from this audit rather than letting them show up and just manually skipping them each time?

Answer: Service accounts often legitimately show no interactive logon for long periods by design — including them every run would create persistent noise a human has to mentally filter out each time, and worse, could result in one accidentally being disabled if the -DisableCritical path is ever used without careful review. An explicit exclusion list makes this exception permanent and code-enforced, not dependent on someone remembering it each time.

Follow-up: "How would you catch a NEW service account that wasn't yet added to the exclusion list?" — Answer: this is exactly the kind of gap that motivates re-verifying the exclusion list immediately before disabling (the defense-in-depth check in Step 4) — but ultimately, keeping the exclusion list current is a process discipline the script alone can't fully guarantee, which is why -DisableCritical remains opt-in and reviewed rather than fully automatic.
