Quick Recap of Projects 1–16

This project is a synthesis, much like Project 9's unified health check — but aimed specifically at patching readiness. We reuse disk space logic (Project 2) and service checks (Project 4), and add one genuinely new check: detecting whether a server is already waiting on a pending reboot, which is one of the most common reasons a patching run fails or behaves unexpectedly.

The Story — Why We're Building This

Last patch Tuesday, three servers failed their patch installation. Investigation found each had a different root cause: one had almost no free disk space, one already had a reboot pending from a previous, forgotten change, and one had a critical service already unhealthy before patching even started. All three problems were detectable in advance — nobody checked beforehand. Our manager wants a "go/no-go" readiness check that runs before any patching window, catching all three conditions automatically.

Concepts First — Before We Touch Code

1. What "Pending Reboot" Actually Means

Why this matters for patching specificallyWindows tracks when certain changes (a previous update, a file rename operation, a component servicing operation) require a restart to fully complete. If a server already has a reboot pending and a new patch is installed on top of that unfinished state, the result can be unpredictable — from patches silently not fully applying to the server becoming unstable. Checking for this before patching is a well-known, important precaution.

2. The Three Places Windows Records a Pending Reboot

Registry LocationSet By
HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPendingComponent-Based Servicing (CBS) — deep OS component changes
HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequiredWindows Update specifically
HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\PendingFileRenameOperationsAny operation that needs to rename/delete a file currently in use
Why check all three instead of just oneDifferent kinds of changes set different indicators — checking only the Windows Update one, for example, would completely miss a pending reboot caused by a file-in-use operation from an application installer. A thorough check needs to look in all three places and treat any of them being present as "reboot is pending."

3. Checking for a Key's Existence vs Reading a Value

Some of these indicators are about whether the key itself exists at all (CBS RebootPending), while others are about whether a specific value is set inside an existing key (PendingFileRenameOperations) — reusing Test-Path for the first, and Get-ItemProperty for the second, exactly the registry techniques from Project 13.

4. Combining Three Independent Readiness Checks

Same "collect several checks, combine into one verdict" shape as Project 9's unified health check — here specifically producing a single READY / NOT READY decision, since that's what a patching workflow actually needs to act on.

5. Why This Is Read-Only, Not Auto-Remediating

Detecting a pending reboot doesn't mean the script should reboot the server itself — that decision belongs to a scheduled maintenance window, not an automated readiness check. This script's job is to inform the go/no-go decision, not make it.

Full Script — Test-PatchReadiness.ps1

# =====================================================================
# Test-PatchReadiness.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Pre-patching go/no-go readiness check (disk, services, pending reboot)
# =====================================================================

$ComputerName       = $env:COMPUTERNAME
$MinFreeDiskPercent = 15                                    # Below this, patching is considered risky (Project 2's pattern)
$CriticalServices   = @("Spooler", "BITS")                    # Reused list style from Project 4

$ReadinessChecks = @()   # Will hold one result per individual check

Write-Host "`n=== PATCH READINESS CHECK: $ComputerName ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# CHECK 1: Disk space (Project 2's logic, reused)
# ---------------------------------------------------------------
$Disks = Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=3"
$DiskOk = $true                                                # Assume healthy until proven otherwise
foreach ($Disk in $Disks) {
    $FreePercent = [math]::Round(($Disk.FreeSpace / $Disk.Size) * 100, 1)
    if ($FreePercent -lt $MinFreeDiskPercent) {
        $DiskOk = $false                                          # Any disk below threshold fails the whole check
        Write-Host "  Disk $($Disk.DeviceID) low: $FreePercent% free (need $MinFreeDiskPercent%+)" -ForegroundColor Red
    }
}
$ReadinessChecks += [PSCustomObject]@{ CheckName = "Disk Space"; Passed = $DiskOk }

# ---------------------------------------------------------------
# CHECK 2: Critical services (Project 4's logic, reused)
# ---------------------------------------------------------------
$ServicesOk = $true
foreach ($SvcName in $CriticalServices) {
    try {
        $Svc = Get-Service -Name $SvcName -ErrorAction Stop
        if ($Svc.Status -ne "Running") {
            $ServicesOk = $false
            Write-Host "  Service '$SvcName' is $($Svc.Status), expected Running" -ForegroundColor Red
        }
    }
    catch {
        $ServicesOk = $false
        Write-Host "  Service '$SvcName' not found" -ForegroundColor Red
    }
}
$ReadinessChecks += [PSCustomObject]@{ CheckName = "Critical Services"; Passed = $ServicesOk }

# ---------------------------------------------------------------
# CHECK 3: Pending reboot - checked in all three known locations
# ---------------------------------------------------------------
$RebootPending = $false                                          # Assume no pending reboot until proven otherwise

# Location A: Component-Based Servicing - existence of the key itself is the signal
if (Test-Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPending") {
    $RebootPending = $true
    Write-Host "  Pending reboot detected: Component-Based Servicing" -ForegroundColor Red
}

# Location B: Windows Update - existence of this key means an update needs a restart
if (Test-Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired") {
    $RebootPending = $true
    Write-Host "  Pending reboot detected: Windows Update" -ForegroundColor Red
}

# Location C: Pending file rename operations - a specific VALUE inside an existing key
$PendingRenames = Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager" -Name "PendingFileRenameOperations" -ErrorAction SilentlyContinue
if ($PendingRenames) {
    $RebootPending = $true
    Write-Host "  Pending reboot detected: Pending file rename operations" -ForegroundColor Red
}

$RebootOk = -not $RebootPending                                   # "OK" means NO reboot pending
$ReadinessChecks += [PSCustomObject]@{ CheckName = "No Pending Reboot"; Passed = $RebootOk }

# ---------------------------------------------------------------
# STEP 4: Combine into one overall verdict
# ---------------------------------------------------------------
$OverallReady = ($ReadinessChecks | Where-Object { -not $_.Passed }).Count -eq 0   # READY only if every check passed

Write-Host "`n=== READINESS SUMMARY ===" -ForegroundColor Magenta
$ReadinessChecks | ForEach-Object {                                 # Prints each check's pass/fail clearly
    $Color = if ($_.Passed) { "Green" } else { "Red" }
    $Symbol = if ($_.Passed) { "PASS" } else { "FAIL" }
    Write-Host "  [$Symbol] $($_.CheckName)" -ForegroundColor $Color
}

$VerdictColor = if ($OverallReady) { "Green" } else { "Red" }
$Verdict = if ($OverallReady) { "READY FOR PATCHING" } else { "NOT READY - resolve issues above first" }
Write-Host "`nOVERALL: $Verdict" -ForegroundColor $VerdictColor

# ---------------------------------------------------------------
# STEP 5: Export
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$ReadinessChecks | Export-Csv -Path ".\reports\PatchReadiness_$Timestamp.csv" -NoTypeInformation
Write-Host "Report saved to .\reports\" -ForegroundColor Cyan

Line-by-Line Explanation

if (Test-Path "HKLM:\...\Component Based Servicing\RebootPending") { $RebootPending = $true }

  • For this indicator, the presence of the key itself is the signal — Windows doesn't put a meaningful value inside it, it just creates the key when a reboot becomes pending and removes it once resolved. This is why Test-Path (existence check) is the right tool here, not Get-ItemProperty (value read).

$PendingRenames = Get-ItemProperty -Path "...\Session Manager" -Name "PendingFileRenameOperations" -ErrorAction SilentlyContinue

  • This is the opposite case — the Session Manager key always exists (it's a core part of Windows), but the specific PendingFileRenameOperations value inside it is only present when there's actually something pending, so we check for that specific value's existence rather than the key's.

$RebootOk = -not $RebootPending

  • A small but important naming/logic detail: every other check in this script is phrased as "is this healthy" ($DiskOk, $ServicesOk), so we deliberately invert $RebootPending into $RebootOk here to keep every check's meaning consistent — "true means good" — right before they're combined, avoiding a mixed-polarity bug where some checks mean "true = good" and others accidentally mean "true = bad."

$OverallReady = ($ReadinessChecks | Where-Object { -not $_.Passed }).Count -eq 0

  • Rather than writing a long -and chain of every individual boolean (which would need editing every time a check is added or removed), this filters the collection of check results for any failures and confirms there are zero — a pattern that scales cleanly as more readiness checks get added over time without ever needing to touch this line again.

Every check in this script produces the exact same simple shape — a name and a Passed boolean — regardless of how different the underlying logic is (CIM queries, service checks, three separate registry lookups). This consistency is precisely what makes the final "count the failures" step so simple, and it's the same uniform-result-shape discipline from Project 10 applied to read-only checks instead of remediation actions.

Production Incident Walkthrough

With this script now running before every patch window, one server shows "FAIL: No Pending Reboot" a full day before the scheduled patching. Operations reboots it proactively during a quiet period, and by the time the actual patch window arrives, it passes clean — avoiding exactly the kind of stacked-pending-changes problem that caused one of last month's three failures.
  • Why is catching this a day in advance so much better than discovering it during the patch window? A failed readiness check found early gives Operations time to schedule a low-impact remediation (like a planned reboot); the same problem discovered mid-patch-window turns into an unplanned, time-pressured scramble during a window that likely has other servers waiting too.

Security & Best Practices

Best practice reinforced hereChecking all three known pending-reboot indicators, rather than just one, illustrates a broader principle: when a real-world condition can be signaled multiple different ways, a thorough check needs to look everywhere it might appear, not just the most common or most convenient location.
Informing, not decidingThis script deliberately stops at reporting a verdict — it never reboots the server or takes any corrective action itself. Whether and when to act on a NOT READY result is an operational scheduling decision that belongs with Operations, not baked into an automated check.

Common Mistakes to Avoid

  • Checking only one of the three pending-reboot indicators and missing the others.
  • Mixing "true means healthy" and "true means problem" across different checks before combining them.
  • Having the readiness script itself trigger a reboot — that decision belongs to a human-scheduled process.

Interview Preparation

Q1. Why check three different registry locations for a pending reboot instead of just one?

Answer: Different subsystems (Component-Based Servicing, Windows Update, general file-rename operations) record a pending reboot in different places — checking only one would miss reboots triggered by the others, giving a false "all clear" in cases where a reboot is genuinely still needed.

Follow-up: "Are there other, less common indicators you might also want to check in a fully thorough implementation?" — Answer: SCCM/ConfigMgr-specific pending reboot flags, or a pending computer rename, are additional real-world indicators some organizations also check, depending on what management tools are in use.

Q2. Why does this script produce a Passed boolean for each check instead of just printing pass/fail text directly?

Answer: Storing a structured boolean per check (rather than only printing text) lets the script programmatically compute an overall verdict by examining the collection afterward, and also produces a clean, structured CSV export — text alone would require re-parsing to determine the overall result.

Follow-up: "How would you add a fourth check without changing the overall-verdict logic?" — Answer: simply append another [PSCustomObject]@{ CheckName = ...; Passed = ... } to $ReadinessChecks — the verdict calculation automatically accounts for it since it just counts failures across the whole collection.

Q3. Why does the script stop at reporting NOT READY instead of automatically rebooting or fixing found issues?

Answer: A reboot has operational impact and needs to happen at an approved, scheduled time — automatically triggering one the moment a readiness check runs could interrupt active work or violate change-control expectations. This script's role is to inform a scheduling decision, not to make it.

Follow-up: "How might you eventually integrate this into an automated patching pipeline while still respecting that boundary?" — Answer: have the readiness check gate entry into a patching workflow (only proceed if READY), but keep any reboot or remediation as a distinct, separately-approved step — a preview of the CI/CD-style pipeline thinking we'll build toward in the DevOps stage.
