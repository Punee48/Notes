Quick Recap of Projects 1–6

We've collected data, classified it, sampled it, checked named lists with error handling, ranked/grouped processes, and safely cleaned up files with -WhatIf. This project reads from a completely new data source: the Windows Event Log — a place where Windows itself, and every application on it, records what happened and when.

The Story — Why We're Building This

WINAPP09 has rebooted twice this week with no scheduled maintenance window and no one admitting to doing it manually. Our manager suspects either a hardware/power issue or an application crash severe enough to bring the whole box down, but nobody wants to scroll through Event Viewer by hand across multiple logs and thousands of entries looking for a needle in a haystack.

Our task: build a script that searches the System log for unexpected shutdown/restart events and the Application log for Critical/Error-level events, within a configurable time window, and summarizes what it finds so a human can quickly spot the pattern.

Concepts First — Before We Touch Code

1. What the Windows Event Log Actually Is

Windows / Application
→
Windows Event Log Service
→
.evtx Files on Disk
→
Get-WinEvent

Event Objects in PowerShell

Windows and installed applications constantly write structured records — called events — to the Windows Event Log service, which stores them in .evtx files under C:\Windows\System32\winevt\Logs. Different categories go into different logs — the two we care about today are System (OS-level events like restarts) and Application (events raised by installed software).

2. Get-WinEvent vs the Older Get-EventLog

Get-EventLogGet-WinEvent
Older, simpler syntaxModern, more powerful, works with newer log formats
Windows PowerShell only, being phased outWorks in both Windows PowerShell and PowerShell 7
Filters client-side (slower on large logs)Supports -FilterHashtable for fast server-side filtering
Why we're using Get-WinEventJust like choosing Get-CimInstance over Get-WmiObject back in Project 1, we default to the modern cmdlet here — it's faster on large logs and is the one still being actively maintained.

3. -FilterHashtable — Fast, Server-Side Filtering

Get-WinEvent -FilterHashtable @{
    LogName   = "System"                    # Which log to search
    Level     = 1,2                          # 1 = Critical, 2 = Error
    StartTime = (Get-Date).AddDays(-7)      # Only events from the last 7 days
}
  • This is a hash table (from Project 1) used as a structured set of filter criteria. Filtering this way happens efficiently at the log-reading level, instead of pulling every event first and filtering afterward with Where-Object — critical for performance on logs with tens of thousands of entries.

5. Event IDs Worth Knowing for This Project

Event IDLogMeaning
6008SystemThe system previously shut down unexpectedly (not a clean shutdown)
41SystemKernel-Power: the system rebooted without cleanly shutting down first (often power loss or a hard hang)
1074SystemA clean, intentional shutdown or restart, and who/what initiated it
Why these specific IDs6008 and 41 are two of the most well-known "something went wrong" signals in Windows administration — they're exactly what we'd expect to find if WINAPP09's mystery reboots were caused by a crash or power event rather than a planned restart.

6. Grouping Events to Find Patterns

Same Group-Object technique from Project 5 — here applied to event Id or ProviderName, to answer "which specific error is happening over and over" instead of just listing every occurrence individually.

Full Script — Get-EventLogReport.ps1

# =====================================================================
# Get-EventLogReport.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Search System/Application logs for restart and error events
# =====================================================================

$ComputerName  = $env:COMPUTERNAME     # The server being checked
$DaysBack      = 7                      # How many days of history to search
$RestartEventIds = @(6008, 41, 1074)   # Event IDs related to shutdowns/restarts (System log)

$StartTime = (Get-Date).AddDays(-$DaysBack)   # The earliest time we care about

Write-Host "`n=== EVENT LOG REPORT: $ComputerName (last $DaysBack days) ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Search the System log for restart-related events
# ---------------------------------------------------------------
$RestartEvents = @()   # Will hold restart-related events if any are found

try {
    $RestartEvents = Get-WinEvent -FilterHashtable @{        # Fast, server-side filtered query
        LogName   = "System"                                    # Search the System log
        Id        = $RestartEventIds                             # Only these specific event IDs
        StartTime = $StartTime                                    # Only within our time window
    } -ErrorAction Stop                                            # Turns "no matching events" into a catchable error
}
catch {
    Write-Host "No restart-related events found in the System log for this period." -ForegroundColor Green
}

if ($RestartEvents.Count -gt 0) {                              # Only runs if something was actually found
    Write-Host "`n--- RESTART / SHUTDOWN EVENTS FOUND ---" -ForegroundColor Red
    foreach ($Event in $RestartEvents) {                         # Loops through each matching event
        Write-Host "  $($Event.TimeCreated)  [ID $($Event.Id)]  $($Event.ProviderName)" -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 2: Search the Application log for Critical/Error events
# ---------------------------------------------------------------
$AppErrors = @()   # Will hold application-level error events

try {
    $AppErrors = Get-WinEvent -FilterHashtable @{               # Another server-side filtered query
        LogName   = "Application"                                 # Search the Application log this time
        Level     = 1,2                                             # 1 = Critical, 2 = Error (comma means "either")
        StartTime = $StartTime
    } -ErrorAction Stop
}
catch {
    Write-Host "`nNo Critical/Error events found in the Application log for this period." -ForegroundColor Green
}

# ---------------------------------------------------------------
# STEP 3: Group Application errors by source to find repeat offenders
# ---------------------------------------------------------------
if ($AppErrors.Count -gt 0) {                                  # Only runs if something was found

    $GroupedErrors = $AppErrors |                                 # Starts from the raw error events
        Group-Object -Property ProviderName |                       # Groups by which application logged them
        Sort-Object Count -Descending                                # Worst offenders first

    Write-Host "`n--- APPLICATION ERRORS BY SOURCE ---" -ForegroundColor Red
    foreach ($Group in $GroupedErrors) {                           # Loops through each source group
        Write-Host "  $($Group.Name): $($Group.Count) error(s)" -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 4: Build a combined report and export it
# ---------------------------------------------------------------
$AllFindings = @()   # Will hold every finding as a clean, exportable row

foreach ($Event in $RestartEvents) {                            # Adds each restart event to the report
    $AllFindings += [PSCustomObject]@{
        Category    = "System Restart"
        TimeCreated = $Event.TimeCreated
        EventId     = $Event.Id
        Source      = $Event.ProviderName
        Message     = ($Event.Message -split "`n")[0]              # Keeps just the first line for a readable CSV
    }
}

foreach ($Event in $AppErrors) {                                # Adds each application error to the report
    $AllFindings += [PSCustomObject]@{
        Category    = "Application Error"
        TimeCreated = $Event.TimeCreated
        EventId     = $Event.Id
        Source      = $Event.ProviderName
        Message     = ($Event.Message -split "`n")[0]
    }
}

if (-not (Test-Path ".\reports")) {                              # Creates the reports folder if missing
    New-Item -ItemType Directory -Path ".\reports" | Out-Null
}
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"                  # Sortable timestamp for the filename
$AllFindings | Export-Csv -Path ".\reports\EventLogReport_$Timestamp.csv" -NoTypeInformation

Write-Host "`nSummary: $($RestartEvents.Count) restart event(s), $($AppErrors.Count) application error(s)." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

Get-WinEvent -FilterHashtable @{ LogName = "System"; Id = $RestartEventIds; StartTime = $StartTime } -ErrorAction Stop

  • Id = $RestartEventIds — passing an array of numbers here means "match any of these IDs," not just one; the hash table key accepts a single value or a list interchangeably.
  • -ErrorAction Stop — same technique from Project 4. Get-WinEvent actually throws an error (not just an empty result) when a filter matches zero events, so we deliberately catch that specific, expected "no results" case rather than letting it look like a script failure.

Level = 1,2

  • Windows Event Log levels are numeric: 1=Critical, 2=Error, 3=Warning, 4=Information, 5=Verbose. Listing two numbers separated by a comma inside the hash table, just like the Id array above, means "match either of these levels."

($Event.Message -split "`n")[0]

  • -split "`n" — the split operator breaks a string into an array of pieces wherever the given separator appears; here we split on newline characters, since event messages are often several lines long.
  • [0] — array index syntax (first seen conceptually back in the concepts overview) grabs just the first piece — the summary line — keeping our CSV readable instead of packing a huge multi-line message into one cell.

Group-Object -Property ProviderName | Sort-Object Count -Descending

  • Directly reuses the Project 5 grouping pattern, just pointed at a new property — proof that Group-Object is a general-purpose tool, not something specific to processes.

Production Incident Walkthrough

Our report comes back showing two Event ID 41 (Kernel-Power) entries in the System log, timestamped almost exactly when Operations noticed WINAPP09 had rebooted — and zero related Application errors around those same times.
  • What does "41 present, no correlating app errors" suggest? Event ID 41 specifically means Windows itself didn't get a chance to shut down cleanly — pointing toward a hardware, power, or OS-level hang rather than an application crash, which would usually leave its own error trail in the Application log first.
  • Why search both logs even though the problem turned out to be System-level? Before running the script, we didn't know that — ruling out application-level causes is just as valuable as confirming the System-level ones, and doing both in one pass saves a second investigation round-trip.

Security & Best Practices

Best practice reinforced here-FilterHashtable filters at the source instead of pulling every event and filtering with Where-Object afterward — on a busy Production server's event log, this is the difference between a query that finishes in under a second and one that takes minutes and consumes significant memory.
Read-only, still local-onlyThis script only reads event logs; it makes no changes to the system, and it's still targeting the local machine. Remote event log queries (which do need proper credential handling) come with the remoting projects later in the course.

Common Mistakes to Avoid

  • Pulling all events and filtering with Where-Object instead of using -FilterHashtable — much slower on real servers.
  • Forgetting that "no matching events" is a normal, expected outcome to handle gracefully, not a script error.
  • Dumping the full multi-line Message property into a CSV cell without trimming it first.

Interview Preparation

Q1. Why is -FilterHashtable preferred over piping Get-WinEvent into Where-Object?

Answer: -FilterHashtable filters events at the log-reading level (closer to the source), so PowerShell never has to load and hold irrelevant events in memory just to discard them. Piping into Where-Object retrieves everything first and filters client-side, which is far slower and more memory-intensive on large logs.

Follow-up: "Are there filtering needs FilterHashtable can't express, where Where-Object is still needed?" — Answer: yes — complex conditions like text matching inside the Message property aren't supported by FilterHashtable, so you'd filter by the structured fields first with FilterHashtable, then refine further with Where-Object on the smaller result set.

Q2. What does Event ID 41 specifically tell you that a generic "the server rebooted" doesn't?

Answer: It indicates the system restarted without a clean shutdown sequence completing first — pointing toward power loss, a hardware fault, or a hang/crash severe enough that Windows couldn't shut down gracefully, as opposed to a normal, intentional restart.

Follow-up: "How would you distinguish a power-related cause from a hang?" — Answer: correlate with hardware/BMC logs or other System log entries around the same timestamp — a topic that goes beyond what PowerShell alone can determine and typically needs hardware-level diagnostics.

Q3. Why catch "no events found" as an expected outcome instead of treating any error as a failure?

Answer: A clean server with nothing to report is a perfectly normal and desirable result — treating it as a script failure would create false alarms and erode trust in the automation. Distinguishing "nothing found" from "something actually went wrong retrieving data" keeps the reporting meaningful.

Follow-up: "How would you tell those two cases apart in the catch block if you needed to?" — Answer: inspect $_.Exception.Message for the specific "no events were found" text versus other error text, and branch your handling accordingly rather than treating every catch identically.
