The Story — Why We're Building This

The banking portal occasionally returns 503 errors for a few minutes before recovering on its own — a classic symptom of an application pool crashing and needing a recycle. Operations currently has to notice the alerts, log into the server, and manually recycle the pool through IIS Manager, losing several minutes each time. Our manager wants the same kind of safe, automatic recovery we built for Windows Services in Project 10 — but for application pools.

Concepts First — Before We Touch Code

1. What an Application Pool Actually Is

Not the same thing as the siteA website in IIS is just configuration — bindings, folder paths, settings. An application pool is the actual worker process (w3wp.exe) that runs the site's code and holds it in memory. Multiple sites can share one pool, or each can have its own — recycling a pool restarts that worker process, similar in spirit to restarting a Windows service (Project 10), but specifically for a web application's runtime.

2. Checking Application Pool State

Get-WebAppPoolState -Name "DefaultAppPool"

Returns the pool's current state — Started, Stopped, or a transitional state like Stopping.

3. Recycling vs Stopping/Starting — An Important Distinction

ActionWhat HappensCmdlet
RecycleGracefully starts a new worker process, finishes in-flight requests on the old one, then retires it — minimal disruptionRestart-WebAppPool
Stop + StartImmediately kills the worker process, then starts a fresh one — every in-flight request is droppedStop-WebAppPool / Start-WebAppPool
Why this distinction matters for our incidentRecycling is the standard, low-disruption way to refresh a healthy-but-stuck pool. Stop/Start is a heavier hammer, more appropriate when a pool is already fully stopped and recycling wouldn't apply — our script needs to choose the right tool for the actual state it finds, not use the same action regardless.

4. Idempotency and Retry — Reused Directly from Project 10

The exact same shape: check current state first, only act if actually needed, retry with a capped attempt count, log everything, return a consistent result object — nothing new to learn here, just a new target for a pattern you already know well.

5. SupportsShouldProcess — Also Reused

Recycling a live application pool affects real traffic, exactly like Project 22's binding change — the same -WhatIf preview discipline applies.

Full Script — Repair-AppPoolHealth.ps1

# =====================================================================
# Repair-AppPoolHealth.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Idempotent, retry-capable IIS application pool health check and recovery
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]
param(
    [switch]$WhatIf = $true,
    [string[]]$AppPoolNames = @("DefaultAppPool")   # The pool(s) we're responsible for keeping healthy
)

Import-Module WebAdministration -ErrorAction Stop

$LogPath    = ".\logs\AppPoolRecovery.log"
$MaxRetries = 3
$RetryDelaySeconds = 5

function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

# ---------------------------------------------------------------
# FUNCTION: Idempotent, WhatIf-aware, retry-capable app pool recovery
# ---------------------------------------------------------------
function Repair-AppPool {
    [CmdletBinding(SupportsShouldProcess)]
    param([string]$AppPoolName)

    try {
        $State = Get-WebAppPoolState -Name $AppPoolName -ErrorAction Stop

        # --- Idempotency check ---
        if ($State.Value -eq "Started") {                          # Already healthy - Project 10's exact pattern
            Write-Log -Status "INFO" -Message "$AppPoolName already Started - no action needed"
            return [PSCustomObject]@{ AppPoolName = $AppPoolName; Action = "NONE (already running)"; Success = $true }
        }

        if ($PSCmdlet.ShouldProcess($AppPoolName, "Recover Application Pool")) {

            $Attempt = 0
            $Recovered = $false

            while (-not $Recovered -and $Attempt -lt $MaxRetries) {   # Capped retry loop, identical to Project 10
                $Attempt++
                Write-Log -Status "INFO" -Message "$AppPoolName is $($State.Value) - recovery attempt $Attempt of $MaxRetries"

                try {
                    if ($State.Value -eq "Stopped") {                  # Choosing the RIGHT action for the actual state
                        Start-WebAppPool -Name $AppPoolName -ErrorAction Stop   # Stopped pools need Start, not Recycle
                    }
                    else {
                        Restart-WebAppPool -Name $AppPoolName -ErrorAction Stop   # Any other non-Started state gets a graceful recycle
                    }
                    Start-Sleep -Seconds 2
                    $State = Get-WebAppPoolState -Name $AppPoolName     # Re-reads current state
                    if ($State.Value -eq "Started") { $Recovered = $true }
                }
                catch {
                    Write-Log -Status "WARNING" -Message "$AppPoolName recovery attempt $Attempt failed: $($_.Exception.Message)"
                }

                if (-not $Recovered -and $Attempt -lt $MaxRetries) {
                    Start-Sleep -Seconds $RetryDelaySeconds
                }
            }

            if ($Recovered) {
                Write-Log -Status "SUCCESS" -Message "$AppPoolName recovered after $Attempt attempt(s)"
                return [PSCustomObject]@{ AppPoolName = $AppPoolName; Action = "RECOVERED"; Success = $true }
            }
            else {
                Write-Log -Status "ERROR" -Message "$AppPoolName FAILED to recover after $MaxRetries attempt(s)"
                return [PSCustomObject]@{ AppPoolName = $AppPoolName; Action = "RECOVERY FAILED"; Success = $false }
            }
        }
        else {
            return [PSCustomObject]@{ AppPoolName = $AppPoolName; Action = "PREVIEWED (WhatIf)"; Success = $null }
        }
    }
    catch {
        Write-Log -Status "ERROR" -Message "$AppPoolName not found: $($_.Exception.Message)"
        return [PSCustomObject]@{ AppPoolName = $AppPoolName; Action = "NOT FOUND"; Success = $false }
    }
}

# ---------------------------------------------------------------
# MAIN
# ---------------------------------------------------------------
Write-Host "`n=== APPLICATION POOL RECOVERY ===" -ForegroundColor Magenta
$Results = @()

foreach ($PoolName in $AppPoolNames) {
    Write-Host "`nChecking $PoolName..." -ForegroundColor Cyan
    $Result = Repair-AppPool -AppPoolName $PoolName -WhatIf:$WhatIf
    $Results += $Result

    $Color = if ($Result.Success -eq $true) { "Green" } elseif ($Result.Success -eq $false) { "Red" } else { "Yellow" }
    Write-Host "  $($Result.Action)" -ForegroundColor $Color
}

if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\AppPoolRecovery_$Timestamp.csv" -NoTypeInformation

Write-Host "`nAudit log: $LogPath" -ForegroundColor Cyan

Line-by-Line Explanation

if ($State.Value -eq "Started") { ... return ... }

  • Get-WebAppPoolState returns an object whose actual state string lives in a .Value property, rather than being the object itself — a small but important detail to notice when working with a cmdlet for the first time; always check the real shape of what's returned rather than assuming.

if ($State.Value -eq "Stopped") { Start-WebAppPool ... } else { Restart-WebAppPool ... }

  • This is the one genuinely new piece of logic compared to Project 10: rather than always calling one fixed recovery action, the script chooses Start for a fully stopped pool versus Restart (recycle) for any other non-Started state — because attempting to "recycle" an already-stopped pool doesn't make sense, and a stopped pool specifically needs to be started.

Everything else in Repair-AppPool

  • Deliberately unchanged from Project 10's Repair-CriticalService: the [CmdletBinding(SupportsShouldProcess)] attribute, the ShouldProcess check, the capped while retry loop, the consistent result-object shape, and the structured logging are all copied directly. This is intentional — once a pattern is proven correct, reusing it exactly (rather than reinventing a similar-but-subtly-different version) reduces risk and speeds up development.

Production Incident Walkthrough

This script runs on a 5-minute schedule (using Project 11's scheduling technique). At 2 AM, the banking portal's application pool crashes into a stuck state; within 5 minutes, the script detects it, correctly chooses to recycle (not stop/start, since the pool wasn't fully stopped) it, confirms recovery, and logs the whole sequence — customer-facing downtime measured in single-digit minutes instead of however long it would have taken someone to notice and respond manually overnight.
  • Why does choosing Restart over Stop+Start matter for customer impact specifically? A recycle (Restart-WebAppPool) lets in-flight requests on the old worker process finish before it's retired, while Stop+Start would abruptly terminate every active request immediately — for a banking application, dropped in-flight transactions are a much bigger problem than a few extra seconds of graceful transition.

Common Mistakes to Avoid

  • Confusing an application pool with the website configuration itself.
  • Always recycling regardless of state, instead of starting a pool that's fully stopped.
  • Using Stop+Start when a graceful Restart would minimize disruption to in-flight requests.
  • Reinventing a slightly different, unproven recovery pattern instead of reusing Project 10's tested one.

Interview Preparation

Q1. What's the difference between an IIS website and an IIS application pool?

Answer: A website is configuration — bindings, physical path, settings. An application pool is the actual worker process that executes the site's code and holds it in memory. One pool can serve multiple sites, or each site can have a dedicated pool; recycling a pool restarts that worker process without changing the site's configuration.

Follow-up: "If two sites share one app pool and it crashes, what's the impact?" — Answer: both sites go down together, since they depend on the same worker process — a good reason larger or more critical sites are often given their own dedicated pool rather than sharing.

Q2. Why does this script check the pool's state before deciding whether to Start or Restart it?

Answer: "Restart" implies something was already running that needs cycling; a fully stopped pool has nothing running to cycle, and needs to be explicitly started instead. Choosing the wrong action for the actual state could fail or behave unexpectedly, so checking state first ensures the right operation is used.

Follow-up: "What IIS-specific transitional states might complicate this logic further in a fully production-hardened version?" — Answer: states like "Stopping" or "Starting" represent a pool mid-transition — a more robust script might wait briefly and re-check rather than immediately attempting another action against a pool that's already in the middle of changing state.

Q3. Why does this project deliberately reuse Project 10's exact recovery pattern instead of writing something new?

Answer: The underlying problem — detect an unhealthy thing, check if action is really needed, act safely with preview support, retry a bounded number of times, log everything, return a consistent result — is genuinely the same shape regardless of whether the "thing" is a Windows Service or an IIS application pool. Reusing a pattern that's already been reasoned through carefully reduces the chance of introducing a new, unproven bug.

Follow-up: "At what point would you extract this shared logic into a reusable function or module instead of copying it between scripts?" — Answer: once a third or fourth thing needs the same recovery shape (a foreshadowing of the Module Development stage later in the course), extracting a generic Repair-Resource-style function that accepts the resource-specific check/start/restart logic as parameters would avoid the duplication entirely.
