Projects 19-20 gave us discovery and monitoring. The Story — Why We're Building This

The certificate flagged as CRITICAL by Project 20's monitor has now been renewed by the certificate authority — we have a new .pfx file ready to import. At the same time, three genuinely expired certificates have been sitting in the store for months, cluttering every future inventory report. Our manager wants one script that can safely import the new certificate (without duplicating it if already present) and safely remove — but only ever already-expired certificates, never anything still valid, no matter what.

Concepts First — Before We Touch Code

1. Import-PfxCertificate — Bringing In a New Certificate

$SecurePassword = Read-Host -Prompt "Enter PFX password" -AsSecureString   # Never plaintext (Project 4's security note, applied)
Import-PfxCertificate -FilePath ".\NewCert.pfx" -CertStoreLocation "Cert:\LocalMachine\My" -Password $SecurePassword
  • -AsSecureString — masks the password as it's typed and stores it as a SecureString in memory rather than plain text, the exact concept the original course spec insisted on since the very beginning: never hardcode or display credentials in plain text.
  • Import-PfxCertificate — imports a certificate and its private key from a .pfx file, unlike a plain .cer import which wouldn't include the key.

2. Idempotency by Thumbprint — Not by Subject Name

Why thumbprint, not SubjectMultiple certificates can share the exact same Subject name (an old one and its renewal, for instance) — the Thumbprint is the one property guaranteed unique to a specific certificate. Checking "is this exact certificate already installed" must use the thumbprint, or an idempotency check based on Subject could wrongly treat a genuinely new, renewed certificate as a duplicate. 
$AlreadyPresent = Get-ChildItem "Cert:\LocalMachine\My" | Where-Object { $_.Thumbprint -eq $NewCertThumbprint }

3. Removing a Certificate — Remove-Item on the Cert: Drive

Remove-Item -Path "Cert:\LocalMachine\My\$Thumbprint"

Same Remove-Item cmdlet from Project 6's file cleanup, here targeting a certificate path instead — another example of PowerShell's provider model letting one cmdlet work consistently across very different kinds of data.

4. The Critical Safety Rule for This Project

Never remove anything that isn't ALREADY expiredThis script's removal logic checks NotAfter against right now, in code, immediately before deleting — it does not trust a list of "certificates to remove" supplied from anywhere else without re-verifying that condition itself. A script that blindly deletes whatever it's told to, without independently confirming the safety condition, is one bad input away from removing something still in active use.

5. ShouldProcess for Both Import and Removal — Reused from Projects 10, 13, 14

Both actions get their own ShouldProcess check, so either can be previewed independently before anything actually happens — by now a completely familiar pattern.

Full Script — Manage-CertificateStore.ps1

# =====================================================================
# Manage-CertificateStore.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Safely remove ALREADY-EXPIRED certificates only. Never touches valid ones.
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]      # Same pattern from Projects 10, 13, 14
param(
    [switch]$WhatIf = $true
)

$StorePath = "Cert:\LocalMachine\My"
$LogPath   = ".\logs\CertStoreChanges.log"

function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

Write-Host "`n=== CERTIFICATE STORE CLEANUP ===" -ForegroundColor Magenta
Write-Host "This script ONLY removes certificates that are ALREADY EXPIRED.`n" -ForegroundColor Yellow

# ---------------------------------------------------------------
# STEP 1: Find candidates - re-verify expiry independently, right here, right now
# ---------------------------------------------------------------
$AllCerts = Get-ChildItem -Path $StorePath -ErrorAction SilentlyContinue

$ExpiredCerts = $AllCerts | Where-Object {
    $_.NotAfter -lt (Get-Date)                                     # THE safety condition - checked directly, not trusted from elsewhere
}

Write-Host "Found $($ExpiredCerts.Count) already-expired certificate(s) out of $($AllCerts.Count) total.`n" -ForegroundColor Cyan

$Results = @()

foreach ($Cert in $ExpiredCerts) {                                  # Only ever loops over certificates we just independently confirmed are expired

    $DaysExpired = ((Get-Date) - $Cert.NotAfter).Days

    Write-Host "Expired: $($Cert.Subject) (expired $DaysExpired day(s) ago, thumbprint $($Cert.Thumbprint))" -ForegroundColor Yellow

    if ($PSCmdlet.ShouldProcess($Cert.Thumbprint, "Remove Expired Certificate ($($Cert.Subject))")) {

        # Re-verify ONE MORE TIME, immediately before deleting - defense in depth against any logic error above
        if ($Cert.NotAfter -lt (Get-Date)) {

            Write-Log -Status "INFO" -Message "Removing expired cert: Subject='$($Cert.Subject)' Thumbprint=$($Cert.Thumbprint) ExpiredOn=$($Cert.NotAfter)"

            Remove-Item -Path "$StorePath\$($Cert.Thumbprint)" -Force -ErrorAction Stop

            Write-Log -Status "SUCCESS" -Message "Removed thumbprint $($Cert.Thumbprint)"
            $Results += [PSCustomObject]@{ Thumbprint = $Cert.Thumbprint; Subject = $Cert.Subject; Action = "REMOVED" }
            Write-Host "  Removed." -ForegroundColor Green
        }
        else {
            # This branch should be unreachable given the filter above - logged loudly if it's ever somehow hit
            Write-Log -Status "ERROR" -Message "SAFETY CHECK FAILED - skipped removal of $($Cert.Thumbprint), NotAfter no longer in the past"
            Write-Host "  SAFETY CHECK FAILED - skipped." -ForegroundColor Red
        }
    }
    else {
        $Results += [PSCustomObject]@{ Thumbprint = $Cert.Thumbprint; Subject = $Cert.Subject; Action = "PREVIEWED (WhatIf)" }
        Write-Host "  PREVIEW: Would remove this expired certificate." -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 2: Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\CertCleanup_$Timestamp.csv" -NoTypeInformation

Write-Host "`nAudit log: $LogPath" -ForegroundColor Cyan
Write-Host "REMINDER: Only already-expired certificates were ever considered for removal." -ForegroundColor Yellow

Line-by-Line Explanation

$ExpiredCerts = $AllCerts | Where-Object { $_.NotAfter -lt (Get-Date) }

  • This is the single line responsible for scope safety in the entire script — every certificate that ever reaches the removal logic below has already passed through this exact filter, independently, right here.

if ($Cert.NotAfter -lt (Get-Date)) { ... } else { # unreachable, logged loudly }

  • This second check re-verifies the exact same condition immediately before the actual Remove-Item call — technically redundant given the filter above already guarantees it, but deliberately included as defense in depth: if a future edit ever changed how $ExpiredCerts gets built and accidentally weakened that filter, this second check would still catch the mistake and refuse to delete, rather than silently trusting the earlier logic.

Remove-Item -Path "$StorePath\$($Cert.Thumbprint)" -Force -ErrorAction Stop

  • The path is built by combining the store location with the specific certificate's thumbprint — this targets exactly one certificate, not a wildcard or a broader match, minimizing any chance of accidentally removing something else.
  • -ErrorAction Stop here means if removal somehow fails, the script surfaces that clearly rather than silently continuing as if it succeeded.

Write-Log -Status "ERROR" -Message "SAFETY CHECK FAILED..."

  • Logging this specific, should-be-impossible scenario loudly (rather than just quietly skipping) means if it were ever somehow triggered, it would be immediately visible in the audit log as something requiring investigation — silent failures in safety logic are far more dangerous than loud ones.

Architecture & Defense-in-Depth Flow

Get-ChildItem (all certs)
→
Filter: NotAfter < Now
→
$ExpiredCerts (only)
foreach Expired Cert
→
ShouldProcess
→
RE-CHECK NotAfter < Now
→
Remove-Item

Notice the expiry condition is checked twice — once to build the candidate list, once again immediately before deletion. This double-check is a direct, code-level expression of Project 15's "some changes deserve more caution than others" lesson: even with a narrow, well-reasoned scope, redundant safety checks around irreversible actions cost almost nothing and catch real mistakes.

Production Incident Walkthrough

A year from now, someone modifies this script to also accept a list of thumbprints from an external file, intending to make it more flexible. Because the "re-check NotAfter immediately before removal" logic was left in place, a mistake in that new file-reading code — accidentally including a still-valid certificate's thumbprint — gets caught and logged as a SAFETY CHECK FAILED entry instead of silently deleting a certificate still in active use.
  • Why does this defense-in-depth pattern matter more here than in most other projects? Certificate removal is immediately destructive and can cause an outage the instant it happens (unlike, say, a misconfigured monitoring threshold, which just produces a wrong report) — the cost of a redundant check is near zero, while the cost of skipping it, if the primary logic is ever weakened by a future change, could be significant.

Security & Best Practices

The core lesson of this projectWhen an action is irreversible and potentially high-impact, checking the safety condition once is often not enough — checking it again, immediately before the point of no return, costs almost nothing and provides real protection against future changes weakening the earlier logic.
Best practice reinforced hereIdentifying certificates by Thumbprint rather than Subject for both idempotency and removal avoids an entire class of mistakes where two different certificates happen to share a name — always prefer the most specific, guaranteed-unique identifier available.

Concepts Learned

  • Never trusting a "to-do list" for a destructive action without independently re-verifying it
  • Logging a should-be-impossible failure loudly rather than silently skipping it

Common Mistakes to Avoid

  • Checking idempotency by Subject name instead of the unique Thumbprint.
  • Trusting an externally-supplied list of things to delete without re-verifying the safety condition yourself.
  • Only checking a destructive condition once, with no redundancy before the point of no return.
  • Hardcoding or displaying a PFX password in plain text instead of using SecureString.

Interview Preparation

Q1. Why does this script check certificate expiry twice — once to build the list, once again right before deletion?

Answer: The second check is defense in depth: it's technically redundant given the first filter, but protects against a future code change accidentally weakening or bypassing that first filter. For an irreversible action like certificate removal, that redundancy is cheap insurance against a class of mistakes that would otherwise be hard to catch in review.

Follow-up: "Doesn't this violate the DRY (Don't Repeat Yourself) coding principle?" — Answer: DRY is a good general default, but safety-critical checks around irreversible actions are a reasonable exception — the small duplication cost is worth the protection it provides, similar to how safety-critical systems in other engineering disciplines often use redundant, independent checks deliberately.

Q2. Why use Thumbprint instead of Subject to identify a specific certificate for removal or idempotency checks?

Answer: Subject names aren't guaranteed unique — a renewed certificate typically has the same Subject as the one it replaces. Thumbprint is a cryptographic fingerprint unique to that exact certificate, making it the only reliable way to say "this specific certificate, and not any other one that happens to share a name."

Follow-up: "Are there any downsides to relying on Thumbprint?" — Answer: a thumbprint changes if a certificate is ever re-issued or re-signed, even with identical other details, so scripts that reference a specific thumbprint need updating whenever a certificate is renewed — usually acceptable given the safety benefit, but worth knowing.

Q3. Why does the script log a SAFETY CHECK FAILED case that "should be unreachable" instead of just leaving that code path out?

Answer: Code that's logically unreachable today can become reachable after a future change nobody fully traces through — explicitly handling and loudly logging that case means if it ever does happen, it's immediately visible and investigable, rather than either crashing unhelpfully or silently doing nothing.

Follow-up: "How would you alert someone in real time if this ERROR log entry ever appeared?" — Answer: this is exactly the kind of condition worth wiring into the REST API/ServiceNow integration projects later in the course, where a log entry could automatically open a ticket or send a notification rather than only being visible if someone manually reviews the log file.
