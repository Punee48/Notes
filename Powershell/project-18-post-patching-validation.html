Quick Recap of Projects 1–17

Project 17 answered "is this server ready to be patched?" This project answers the equally important follow-up question nobody always remembers to ask: "did patching actually work, and is the server healthy now?" We reuse the multi-check-to-one-verdict framework from Project 17, add a genuinely new check (Get-HotFix), and fold in Project 7's event log technique to catch new errors that appeared right after the reboot.

The Story — Why We're Building This

Patch Tuesday finished overnight. The patching tool reports "success" for every server — but our manager has seen that claim be wrong before: a patch can report success while a dependent service fails to restart, or while the actual update never fully applied due to an interrupted reboot. "I don't want to trust the patching tool's word for it. I want our own independent script to verify each server is actually healthy after patching, not just that the installer didn't error out."

Concepts First — Before We Touch Code

1. Why "The Installer Said Success" Isn't Enough

A healthy skepticism worth havingA patch installer reporting success only confirms the installation process completed without error — it says nothing about whether the server actually came back up correctly afterward, whether dependent services recovered, or whether the reboot fully completed. Independent post-patch validation closes that gap.

2. Get-HotFix — Confirming What's Actually Installed

Get-HotFix | Sort-Object InstalledOn -Descending | Select-Object -First 5
  • Get-HotFix — queries installed updates directly from Windows, independent of whatever the patching tool itself reported — the same "verify from a different source than the one that made the claim" principle as double-checking a service restart rather than trusting the restart command's exit code alone.
  • InstalledOn — the date a given update was applied; sorting descending and taking the first few shows the most recent patching activity.

3. Confirming the Pending Reboot Actually Cleared

We reuse Project 17's three-location pending-reboot check — but now checking that it's $false, confirming the reboot that (presumably) already happened actually resolved the pending state, rather than the server coming back up with the condition still lingering.

4. Services Should Be Running Again — Reused from Projects 4 and 17

The exact same critical-services check, run again post-patch: a service that was fine before patching but failed to come back up after the reboot is one of the most common real-world patching side effects.

5. New Errors Since the Reboot — Reusing Project 7's Technique

$LastBoot = (Get-CimInstance Win32_OperatingSystem).LastBootUpTime
Get-WinEvent -FilterHashtable @{ LogName = "Application"; Level = 1,2; StartTime = $LastBoot }
  • Instead of a fixed "last 7 days" window like Project 7, we scope the event search to since the last boot — precisely the window that matters for catching problems the reboot itself may have introduced.

6. Combining Four Checks into One Verdict — Same Shape as Project 17

Recent patch installed, no pending reboot, services healthy, no new critical errors — four independently meaningful checks, combined exactly the way Project 17 combined its three.

Full Script — Test-PostPatchValidation.ps1

# =====================================================================
# Test-PostPatchValidation.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Independently verify server health AFTER a patching cycle
# =====================================================================

$ComputerName     = $env:COMPUTERNAME
$CriticalServices = @("Spooler", "BITS")
$MaxDaysSincePatch = 35                                       # Flags if nothing installed recently (missed patch cycle)

$ValidationChecks = @()

Write-Host "`n=== POST-PATCH VALIDATION: $ComputerName ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# CHECK 1: Recent patch installation (new - Get-HotFix)
# ---------------------------------------------------------------
$RecentHotfixes = Get-HotFix | Sort-Object InstalledOn -Descending
$LatestPatch    = $RecentHotfixes | Select-Object -First 1     # The single most recent update

$PatchOk = $false
if ($LatestPatch -and $LatestPatch.InstalledOn) {                # Some hotfix entries lack a date - guard against that
    $DaysSincePatch = ((Get-Date) - $LatestPatch.InstalledOn).TotalDays
    $PatchOk = $DaysSincePatch -le $MaxDaysSincePatch
    Write-Host "  Most recent patch: $($LatestPatch.HotFixID) on $($LatestPatch.InstalledOn) ($([math]::Round($DaysSincePatch,0)) days ago)" -ForegroundColor Cyan
}
$ValidationChecks += [PSCustomObject]@{ CheckName = "Recent Patch Installed"; Passed = $PatchOk }

# ---------------------------------------------------------------
# CHECK 2: Pending reboot cleared (Project 17's logic, reused, now expecting $false)
# ---------------------------------------------------------------
$RebootPending = $false
if (Test-Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPending") { $RebootPending = $true }
if (Test-Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired") { $RebootPending = $true }
$PendingRenames = Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager" -Name "PendingFileRenameOperations" -ErrorAction SilentlyContinue
if ($PendingRenames) { $RebootPending = $true }

$RebootClearedOk = -not $RebootPending
if (-not $RebootClearedOk) {
    Write-Host "  Pending reboot STILL present after patching - investigate" -ForegroundColor Red
}
$ValidationChecks += [PSCustomObject]@{ CheckName = "Pending Reboot Cleared"; Passed = $RebootClearedOk }

# ---------------------------------------------------------------
# CHECK 3: Critical services running (Project 4/17's logic, reused)
# ---------------------------------------------------------------
$ServicesOk = $true
foreach ($SvcName in $CriticalServices) {
    try {
        $Svc = Get-Service -Name $SvcName -ErrorAction Stop
        if ($Svc.Status -ne "Running") {
            $ServicesOk = $false
            Write-Host "  Service '$SvcName' did not come back up: $($Svc.Status)" -ForegroundColor Red
        }
    }
    catch {
        $ServicesOk = $false
        Write-Host "  Service '$SvcName' not found" -ForegroundColor Red
    }
}
$ValidationChecks += [PSCustomObject]@{ CheckName = "Critical Services Running"; Passed = $ServicesOk }

# ---------------------------------------------------------------
# CHECK 4: No new critical errors since the last boot (Project 7's technique, reused)
# ---------------------------------------------------------------
$LastBoot = (Get-CimInstance Win32_OperatingSystem).LastBootUpTime   # The reboot presumably caused by patching

$NewErrors = @()
try {
    $NewErrors = Get-WinEvent -FilterHashtable @{ LogName = "Application"; Level = 1,2; StartTime = $LastBoot } -ErrorAction Stop
}
catch { }   # No errors since boot is a normal, good outcome - Project 7's pattern

$NoNewErrorsOk = $NewErrors.Count -eq 0
if (-not $NoNewErrorsOk) {
    Write-Host "  $($NewErrors.Count) new Application error(s) since last boot ($LastBoot)" -ForegroundColor Red
}
$ValidationChecks += [PSCustomObject]@{ CheckName = "No New Errors Since Boot"; Passed = $NoNewErrorsOk }

# ---------------------------------------------------------------
# STEP 5: Combine into one verdict (identical shape to Project 17)
# ---------------------------------------------------------------
$OverallHealthy = ($ValidationChecks | Where-Object { -not $_.Passed }).Count -eq 0

Write-Host "`n=== VALIDATION SUMMARY ===" -ForegroundColor Magenta
$ValidationChecks | ForEach-Object {
    $Color = if ($_.Passed) { "Green" } else { "Red" }
    $Symbol = if ($_.Passed) { "PASS" } else { "FAIL" }
    Write-Host "  [$Symbol] $($_.CheckName)" -ForegroundColor $Color
}

$Verdict = if ($OverallHealthy) { "PATCHING VALIDATED - SERVER HEALTHY" } else { "VALIDATION FAILED - investigate before closing the patch ticket" }
Write-Host "`nOVERALL: $Verdict" -ForegroundColor $(if ($OverallHealthy) { "Green" } else { "Red" })

# ---------------------------------------------------------------
# STEP 6: Export
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$ValidationChecks | Export-Csv -Path ".\reports\PostPatchValidation_$Timestamp.csv" -NoTypeInformation
Write-Host "Report saved to .\reports\" -ForegroundColor Cyan

Line-by-Line Explanation

$LatestPatch = $RecentHotfixes | Select-Object -First 1

  • Same Top-N pattern from Project 5, here reduced to just the single most recent result — we don't need the full history, only the newest entry, to answer "was anything installed recently."

if ($LatestPatch -and $LatestPatch.InstalledOn) { ... }

  • A defensive double-check: some hotfix entries (particularly very old ones, or certain update types) don't always populate InstalledOn. Checking both that a patch exists and has a usable date avoids a crash trying to do date math against $null.

$LastBoot = (Get-CimInstance Win32_OperatingSystem).LastBootUpTime

  • Reuses the exact property from Project 1's uptime calculation, but here it defines the starting point for our event search rather than being used to calculate a duration — the same piece of data serving a different purpose depending on the script's goal.

$RebootClearedOk = -not $RebootPending

  • Notice this is the exact inverse framing from Project 17, where $RebootOk meant "no reboot was pending yet" (a pre-patching good sign); here $RebootClearedOk means "no reboot is pending anymore" (a post-patching good sign) — same underlying check, different meaning depending on when in the patching lifecycle it's run.

$ValidationChecks | Where-Object { -not $_.Passed }).Count -eq 0

  • Identical line to Project 17's verdict calculation — proof that once you build a good, reusable pattern for "combine several pass/fail checks into one verdict," it transfers directly to a new project with a completely different set of underlying checks.

Production Incident Walkthrough

The patching tool reports 100% success across 30 servers overnight. Our validation script, run automatically afterward, flags one server: services are fine, no pending reboot, a patch installed today — but 14 new Application-log Critical/Error events appeared since the reboot, all from the same provider. The patching tool's job (install updates) succeeded; the server's actual health did not, and only independent validation caught the difference.
  • Why is this exactly the gap Project 7's technique was needed to close? None of the other three checks (patch date, reboot, services) would have caught an application quietly failing in a new way after restart — only scanning the event log for the post-boot window surfaces that kind of problem.
  • Why validate independently instead of just trusting the patching tool's success report? A patching tool's "success" typically means its own installation steps completed — it has no visibility into whether the server's applications are actually behaving normally afterward, which is a fundamentally different, broader question.

Security & Best Practices

Best practice reinforced hereScoping the event log search to since last boot rather than a fixed window is a meaningful improvement over Project 7's fixed 7-day window for this specific use case — the right time window depends on what question you're actually asking, and "what went wrong since the thing that might have caused it" is often more precise than an arbitrary calendar period.
Independent verification as a security principleTrusting a single source's self-reported success (the patching tool) without independent confirmation is a pattern worth being suspicious of well beyond just patching — the same reasoning applies to deployment tools, backup systems, and anything else that reports its own success.

Interview Preparation

Q1. Why build a separate post-patch validation script instead of just trusting the patch management tool's success report?

Answer: A patching tool's success typically only confirms its own installation process completed without error — it doesn't verify the server's actual runtime health afterward (services, application errors, whether a required reboot fully completed). Independent validation checks the outcome that actually matters, not just the process that was supposed to produce it.

Follow-up: "What's a real-world example where a tool's 'success' and actual health diverge?" — Answer: an installer can complete successfully while a dependent Windows service that was manually stopped beforehand simply never gets restarted afterward — the patch itself installed fine, but the server isn't actually back to a healthy state.

Q2. Why scope the event log check to "since LastBootUpTime" instead of a fixed window like Project 7 used?

Answer: The relevant question here is specifically "did anything go wrong because of this reboot," so the natural, precise boundary is the reboot time itself — a fixed window (like "last 7 days") would either miss recent-but-pre-reboot context or include irrelevant older noise, depending on how it's set.

Follow-up: "When would a fixed window still be the better choice over a dynamic one?" — Answer: when there's no natural event to anchor to, or when you specifically want a consistent, comparable period across many different checks or servers regardless of when each one last rebooted.

Q3. This script's verdict logic is nearly identical to Project 17's. Is that duplication a problem?

Answer: Not really — the verdict-combination logic (count failures, zero means pass) is a small, stable, generic pattern; what's genuinely different between the two projects is the actual list of checks being combined. In a more mature codebase, this shared logic would likely be extracted into its own reusable function (foreshadowing the module-development stage later in the course) rather than staying duplicated across scripts.

Follow-up: "What would that shared function look like?" — Answer: something like Get-OverallVerdict -Checks $ValidationChecks that takes any array of Name/Passed objects and returns the combined boolean plus a formatted summary — reusable across this, Project 17, and any future readiness-style check.
