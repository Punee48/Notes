The Story — Why We're Building This

A customer-facing banking portal went down for eleven minutes last quarter because its SSL certificate expired and nobody had it on a calendar. Concepts First — Before We Touch Code

1. The Certificate Store as a PowerShell Drive

The same pattern as HKLM: and HKCU:Just as Project 13 showed the registry exposed as HKLM:/HKCU:, Windows' certificate store is exposed as the Cert: drive — browsable with the exact same Get-ChildItem you'd use on real files or registry keys.
PathContains
Cert:\LocalMachine\MyMachine-level certificates with their private keys — where server/SSL certificates usually live
Cert:\LocalMachine\RootTrusted root certificate authorities
Cert:\CurrentUser\MyCertificates specific to the current user's profile

2. Browsing Certificates with Get-ChildItem

Get-ChildItem -Path "Cert:\LocalMachine\My"

Returns every certificate in that store location as an X509Certificate2 object — a real .NET type, not something PowerShell invented, which is why certificate objects have such rich built-in properties.

3. Key Certificate Properties

PropertyMeaning
SubjectWho/what the certificate identifies (e.g. CN=portal.abcbank.internal)
IssuerWho issued/signed the certificate
NotBefore / NotAfterThe certificate's valid date range
ThumbprintA unique fingerprint identifying this exact certificate
HasPrivateKeyWhether the private key is present — required for a certificate to actually be usable for HTTPS/TLS on this server

4. Calculating Days Until Expiry

Same date-subtraction-produces-a-TimeSpan technique from Projects 1, 6, and 17 — here applied to NotAfter instead of uptime or file age.

$DaysUntilExpiry = ($Cert.NotAfter - (Get-Date)).Days
Order matters hereNotice the subtraction is NotAfter - Now, not Now - NotAfter (the reverse of Project 1's uptime calculation) — because we want a positive number of days remaining for a certificate that hasn't expired yet. Getting this backwards produces a negative number that reads confusingly.

5. Why HasPrivateKey Matters

A subtle but important distinctionA certificate without its private key can still appear in the store (e.g. exported for trust purposes) but cannot actually be used to terminate HTTPS/TLS connections on that server. An inventory that doesn't check this could misleadingly list a certificate as "available" when it's not actually deployable there.

6. Building a Complete Inventory Across Multiple Store Locations

A thorough discovery checks more than just My — different certificate types and purposes live in different store locations, so a complete inventory needs to enumerate each relevant location separately.

Full Script — Get-CertificateInventory.ps1

# =====================================================================
# Get-CertificateInventory.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Build a complete inventory of certificates across store locations
# =====================================================================

$ComputerName  = $env:COMPUTERNAME
$StoreLocations = @(                                            # Which certificate store paths to inventory
    "Cert:\LocalMachine\My",                                      # Server/SSL certificates with private keys
    "Cert:\LocalMachine\Root"                                      # Trusted root certificate authorities
)

$Inventory = @()   # Will hold one record per certificate found

Write-Host "`n=== CERTIFICATE INVENTORY: $ComputerName ===" -ForegroundColor Magenta

foreach ($StorePath in $StoreLocations) {                         # Loops through each store location we care about

    Write-Host "`nScanning $StorePath..." -ForegroundColor Cyan
    $Certificates = Get-ChildItem -Path $StorePath -ErrorAction SilentlyContinue   # Lists every cert in this location

    foreach ($Cert in $Certificates) {                               # Loops through each certificate found

        $DaysUntilExpiry = ($Cert.NotAfter - (Get-Date)).Days          # Positive = still valid, negative = already expired

        $Inventory += [PSCustomObject]@{
            StoreLocation    = $StorePath
            Subject          = $Cert.Subject
            Issuer           = $Cert.Issuer
            Thumbprint       = $Cert.Thumbprint
            NotBefore        = $Cert.NotBefore
            NotAfter         = $Cert.NotAfter
            DaysUntilExpiry  = $DaysUntilExpiry
            HasPrivateKey    = $Cert.HasPrivateKey
        }
    }

    Write-Host "  Found $($Certificates.Count) certificate(s)." -ForegroundColor Cyan
}

# ---------------------------------------------------------------
# Show a quick summary sorted by expiry, soonest first
# ---------------------------------------------------------------
Write-Host "`n=== CERTIFICATES SORTED BY EXPIRY (SOONEST FIRST) ===" -ForegroundColor Magenta
$Inventory | Sort-Object DaysUntilExpiry | Select-Object -First 10 |
    Format-Table Subject, DaysUntilExpiry, HasPrivateKey -AutoSize

# ---------------------------------------------------------------
# Export the full inventory
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Inventory | Export-Csv -Path ".\reports\CertInventory_$Timestamp.csv" -NoTypeInformation

Write-Host "`nTotal certificates inventoried: $($Inventory.Count)" -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

$Certificates = Get-ChildItem -Path $StorePath -ErrorAction SilentlyContinue

  • The exact same cmdlet used on real folders since Project 6, here browsing a certificate store instead — the strongest illustration yet of how consistently PowerShell's provider model lets one cmdlet work across completely different underlying data sources.

$DaysUntilExpiry = ($Cert.NotAfter - (Get-Date)).Days

  • .Days instead of .TotalDays (used in earlier projects) — .Days gives the whole-number day component of a TimeSpan, which is what we want for a simple "days remaining" display; .TotalDays would give a more precise decimal, useful in different contexts like Project 3's uptime percentage calculations.

$Inventory | Sort-Object DaysUntilExpiry | Select-Object -First 10

  • Notice this sorts ascending (the default, no -Descending needed) — for expiry dates, the smallest/most-urgent number should come first, the opposite of Project 5's Top-N-by-resource-usage pattern which wanted the largest values first.

StoreLocation = $StorePath as a recorded property

  • Recording which store location each certificate came from (rather than just merging everything into one undifferentiated list) preserves useful context — a certificate found in My vs Root means very different things and would be handled differently by whoever reviews this report.

Production Incident Walkthrough

Running this inventory script across ABC Bank's application servers for the first time surfaces something nobody expected: a certificate for an internal reporting tool that expired eight months ago, sitting unnoticed in LocalMachine\My the whole time, because that particular tool happened to still accept the connection anyway with a browser warning nobody who used it thought to report.
  • Why would a script built purely for "discovery" surface a real problem before any monitoring logic exists? Simply having a complete, visible list of every certificate — including expiry dates — is often enough to reveal a problem a human can spot immediately, even before any automated threshold logic is layered on top. Good inventories have value on their own, not just as input to more automation.

Security & Best Practices

Private keys are sensitiveThis script only reads metadata (Subject, expiry, thumbprint) — it never exports or handles the actual private key material, which should always be treated as highly sensitive and never casually copied, logged, or included in a report.
Best practice reinforced hereRecording HasPrivateKey as a distinct, visible column rather than silently assuming every certificate is usable prevents a false sense of coverage — "we have a certificate for this" and "we have a certificate we can actually deploy" are different claims, and this inventory is honest about which one applies to each entry.

Common Mistakes to Avoid

  • Subtracting dates in the wrong order and getting a confusing negative "days until expiry."
  • Only checking one store location and missing certificates that live elsewhere.
  • Assuming every listed certificate is deployable without checking HasPrivateKey.
  • Treating a long-dated root CA certificate's expiry the same way as a short-lived server certificate.

Interview Preparation

Q1. Why does this script check both LocalMachine\My and LocalMachine\Root instead of just one?

Answer: They serve different purposes — My holds the server's own identity certificates (typically with private keys, used for things like HTTPS), while Root holds trusted certificate authorities used to validate other certificates. A complete inventory needs to account for both, since they represent different kinds of risk if something's wrong.

Follow-up: "What other store locations might a truly complete audit also check?" — Answer: Cert:\LocalMachine\CA (intermediate certificate authorities) and Cert:\LocalMachine\WebHosting (used specifically by IIS on newer Windows versions) are common additional locations worth including.

Q2. Why does HasPrivateKey matter for a certificate inventory?

Answer: A certificate without its private key present can be viewed and its metadata inspected, but cannot actually be used to terminate TLS/HTTPS connections on that server — an inventory that doesn't distinguish this could misleadingly suggest a certificate is ready to use when it isn't.

Follow-up: "How would a certificate end up in the store without its private key?" — Answer: it can happen when a certificate is exported and imported in a format (like a .cer rather than a .pfx) that deliberately excludes the private key, often done intentionally for trust/distribution purposes rather than for actual TLS use on that machine.

Q3. Why build this as a pure discovery/inventory script instead of adding expiry alerting directly in this project?

Answer: Separating "find everything" from "decide what's urgent" keeps each piece focused and independently testable/reusable — the same "collect, then decide" separation used since Project 2's disk space classification. A clean inventory is also useful on its own, immediately, even before any threshold logic exists on top of it.

Follow-up: "What would you need to add to turn this into a monitoring script?" — Answer: exactly what Project 20 will build — warning/critical day thresholds and status classification, following the same pattern established back in Project 2's disk space monitor.
