Quick Recap of Projects 1–14

Project 14 drew a line: auto-create missing firewall rules, but never auto-modify existing ones. This project draws that line even earlier — auditing NTFS permissions is valuable, but changing them automatically is genuinely dangerous (a wrong permission change can lock out a service account and take down an application instantly). We'll build a thorough, read-only audit and explicitly explain why remediation stays a human decision here.

The Story — Why We're Building This

A routine security review at ABC Bank found that a folder containing customer statement exports had "Everyone: Modify" permissions — meaning literally any authenticated user on the network could read, edit, or delete customer financial documents. Nobody remembers granting that; it likely happened months ago during a rushed troubleshooting session and was never reverted. Our manager wants a script that audits folder permissions across a list of sensitive paths and flags any grant to broad, higher-risk identities like "Everyone" or "Authenticated Users" — without changing anything automatically.

Concepts First — Before We Touch Code

1. ACL and ACE — The Two Core Concepts

Terminology worth getting exactly rightAn ACL (Access Control List) is the complete set of permissions attached to a file or folder. Each individual permission grant or denial within that list is a separate ACE (Access Control Entry) — "who gets what access, allow or deny." A folder has one ACL, made up of potentially many ACEs.

2. Get-Acl and the Access Property

$Acl = Get-Acl -Path "C:\SomeFolder"
$Acl.Access   # An array of individual ACEs (FileSystemAccessRule objects)
  • Get-Acl — reads the full ACL for a file or folder path.
  • .Access — the property containing every individual ACE as a separate object — this is what we'll loop through to examine each permission grant one at a time.

3. Key ACE Properties

PropertyMeaning
IdentityReferenceWho this entry applies to (a user, group, or built-in identity like "Everyone")
FileSystemRightsWhat access is granted (Read, Write, Modify, FullControl, etc.)
AccessControlTypeAllow or Deny
IsInheritedTrue if this permission came from a parent folder rather than being set directly here

4. Why IsInherited Matters for Prioritizing Findings

Explicit vs inherited grantsA permission inherited from a parent folder is usually part of the organization's standard structure and less likely to be a one-off mistake. A permission set explicitly on this specific folder (IsInherited = $false) is more likely to be a deliberate — or accidental — override, and deserves closer scrutiny during an audit.

5. Identifying High-Risk Broad Identities

Certain built-in Windows identities represent an extremely wide audience:

IdentityRepresents
EveryoneEvery user, including unauthenticated/anonymous access in some configurations
Authenticated UsersAny successfully logged-in user, domain-wide
UsersThe built-in local/domain Users group — typically very broad membership

A Write, Modify, or FullControl grant to any of these on a sensitive folder is almost always worth flagging for review.

6. Config-Driven Audit Targets — Reusing the Project 9/14 Pattern

Which folders count as "sensitive" and which identities are actually expected/approved both belong in configuration, not hardcoded in the script — the same separation of concerns we've applied since Project 9.

7. Why This Project Never Auto-Remediates

The most important lesson in this projectUnlike a missing firewall rule (safe to create — it can only add access that was supposed to exist), an NTFS permission change can remove access a legitimate service account or application depends on to function. Getting it wrong can cause an outage instantly, and untangling exactly what access was needed after the fact can be surprisingly hard. This is a case where detection provides nearly all the value, and remediation absolutely requires a human who understands the business context.

Full Script — Invoke-NtfsPermissionAudit.ps1

# =====================================================================
# Invoke-NtfsPermissionAudit.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Audit-only report of NTFS permissions on sensitive folders
# NOTE: This script NEVER modifies permissions - detection only, by design.
# =====================================================================

$AuditPaths     = Import-Csv -Path ".\config\audit-paths.csv"     # Config-driven target list (Project 9/14 pattern)
$HighRiskGroups = @("Everyone", "Authenticated Users", "BUILTIN\Users")   # Broad identities worth flagging
$RiskyRights    = @("Modify", "FullControl", "Write")               # Access levels serious enough to flag

$Findings = @()   # Will hold every ACE we examine, flagged or not

Write-Host "`n=== NTFS PERMISSION AUDIT (READ-ONLY) ===" -ForegroundColor Magenta
Write-Host "This script only reports findings - it never modifies permissions.`n" -ForegroundColor Yellow

foreach ($Target in $AuditPaths) {                                  # $Target is one row from audit-paths.csv

    $Path = $Target.FolderPath
    Write-Host "Auditing $Path..." -ForegroundColor Cyan

    if (-not (Test-Path $Path)) {                                    # Confirms the folder actually exists first
        Write-Host "  Path not found - skipping." -ForegroundColor Yellow
        continue                                                       # Moves to the next target without erroring the whole script
    }

    $Acl = Get-Acl -Path $Path                                        # Reads the full ACL for this folder

    foreach ($Ace in $Acl.Access) {                                    # Loops through every individual ACE (permission entry)

        $Identity = $Ace.IdentityReference.ToString()                   # The "who" - converted to a plain string for comparison
        $Rights   = $Ace.FileSystemRights.ToString()                     # The "what access" - as a string, may combine multiple rights

        # Checks whether this identity is one of our known broad/high-risk groups
        $IsHighRiskIdentity = $HighRiskGroups | Where-Object { $Identity -like "*$_*" }

        # Checks whether the granted rights include anything from our risky list
        $HasRiskyRights = $false
        foreach ($Risky in $RiskyRights) {                                # Checks each risky right individually
            if ($Rights -like "*$Risky*") { $HasRiskyRights = $true }       # FileSystemRights can combine multiple flags in one string
        }

        $IsFlagged = ($IsHighRiskIdentity -and $HasRiskyRights -and $Ace.AccessControlType -eq "Allow")

        $Findings += [PSCustomObject]@{                                  # Records EVERY ACE examined, flagged or not - full transparency
            FolderPath   = $Path
            Identity     = $Identity
            Rights       = $Rights
            AccessType   = $Ace.AccessControlType
            IsInherited  = $Ace.IsInherited
            RiskLevel    = if ($IsFlagged) { "HIGH RISK" } else { "Normal" }
        }

        if ($IsFlagged) {                                                # Only prints a warning line for actual findings
            $InheritedNote = if ($Ace.IsInherited) { "(inherited)" } else { "(explicitly set on this folder)" }
            Write-Host "  HIGH RISK: '$Identity' has '$Rights' access $InheritedNote" -ForegroundColor Red
        }
    }
}

# ---------------------------------------------------------------
# Export the full findings report and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Findings | Export-Csv -Path ".\reports\NtfsAudit_$Timestamp.csv" -NoTypeInformation

$HighRiskCount = ($Findings | Where-Object { $_.RiskLevel -eq "HIGH RISK" }).Count
Write-Host "`nSummary: $HighRiskCount high-risk permission grant(s) found across $($AuditPaths.Count) folder(s)." -ForegroundColor Cyan
Write-Host "Full report (including normal entries, for complete transparency): .\reports\" -ForegroundColor Green
Write-Host "`nREMINDER: No permissions were changed. Review findings and remediate manually with proper change control." -ForegroundColor Yellow

Line-by-Line Explanation

$Acl = Get-Acl -Path $Path / foreach ($Ace in $Acl.Access)

  • One Get-Acl call retrieves the entire permission set for the folder at once; the foreach loop then examines each individual grant separately, since a folder typically has several ACEs (one for Administrators, one for SYSTEM, one for a specific application account, etc.), not just one.

$IsHighRiskIdentity = $HighRiskGroups | Where-Object { $Identity -like "*$_*" }

  • This checks whether $Identity contains any of our known risky group names, using -like with wildcards on both sides — necessary because IdentityReference often includes a domain or machine prefix (e.g. "BUILTIN\Users" or "NT AUTHORITY\Authenticated Users"), so an exact match against a bare name like "Users" would miss real matches.
  • Notice $_ here refers to each item from $HighRiskGroups as Where-Object loops through them — a different pipeline than the ACE loop we're inside, a good reminder that $_'s meaning always depends on which immediately-surrounding pipeline it belongs to.

foreach ($Risky in $RiskyRights) { if ($Rights -like "*$Risky*") { $HasRiskyRights = $true } }

  • FileSystemRights is a flags enumeration — a single ACE's rights value can represent multiple combined permissions at once (e.g. "Modify, Synchronize"), which is why we check whether the string contains any risky keyword rather than trying to match the whole value exactly.

$IsFlagged = ($IsHighRiskIdentity -and $HasRiskyRights -and $Ace.AccessControlType -eq "Allow")

  • Three conditions chained with -and: the identity must be broad/risky, AND the rights must include something serious, AND — importantly — the entry must actually be an Allow rule. A Deny entry for "Everyone: Modify" would mean the opposite of what we're looking for (explicitly blocking broad access, which is a good thing), so excluding Deny entries from being flagged prevents a confusing false positive.

Recording every ACE, flagged or not, into $Findings

  • Same "log everything checked, not just problems" philosophy from Project 4's service audit — a complete record proves the audit actually examined every permission on every folder, not just the ones that turned out to be interesting.

Human Review & Manual Remediation

The flow deliberately ends at "human review", not at "fix." This is the architectural expression of the security principle from Project 14 taken one step further — some categories of change are simply outside what automation should decide on its own, however confident the detection logic is.

Production Incident Walkthrough

Six months earlier, a well-meaning script did attempt automatic NTFS remediation — stripping "Everyone" access from a folder flagged as risky. It turned out a legacy reporting service account was actually a member of a group nested inside "Authenticated Users" and depended on that broad grant to function; the automated fix broke nightly reconciliation reports for two days before anyone traced it back to the "helpful" permission change. That incident is exactly why this project's script only ever reports.
  • Why is this failure mode worse than, say, Project 10's failed service restart? A failed restart is visible almost immediately and is itself reversible (try again, or start manually). A permission removal can silently break something that only runs occasionally (like a nightly batch job) — the failure might not surface for hours or days, by which point tracing it back to "a script changed a permission" is much harder.
  • Doesn't flagging without fixing waste the automation's potential? Not in this case — the hardest and most time-consuming part of the original problem was finding the risky grant across hundreds of folders manually; automating detection captures nearly all the value, while leaving the comparatively quick "someone reviews and approves the fix" step to a human who has the business context to do it safely.

Security & Best Practices

The core lesson of this entire projectNot every detected problem should be auto-remediated, even when the fix seems technically obvious. Permission changes on shared resources can have consequences that aren't visible from the permission data alone — this is a judgment call that belongs to a human with business context, supported by good tooling (this script), not replaced by it.
Best practice reinforced hereRecording every ACE examined (not just the flagged ones) into the report gives an auditor complete confidence the check was thorough — partial visibility into an audit is almost as bad as no audit at all when compliance is on the line.

Common Mistakes to Avoid

  • Flagging Deny entries as if they were risky grants — they're the opposite.
  • Exact-matching identity names instead of accounting for domain/BUILTIN prefixes.
  • Building automatic permission remediation without a very strong reason and strict controls.
  • Only recording flagged findings, losing the ability to prove the whole audit was thorough.

Interview Preparation

Q1. What's the difference between an ACL and an ACE?

Answer: An ACL is the complete permission set on an object; an ACE is one individual entry within that set — one specific identity's specific grant or denial. A folder has one ACL made up of potentially many ACEs.

Follow-up: "What's the difference between a DACL and a SACL?" — Answer: a DACL (Discretionary ACL) controls who has access; a SACL (System ACL) controls what gets audited/logged — Get-Acl by default works with the DACL, which is what this script inspects.

Q2. Why exclude Deny entries from being flagged as high risk in this script?

Answer: A Deny entry for a broad group like "Everyone" is the security team actively restricting access, not granting it — flagging it as a risk would be exactly backwards; only Allow entries granting risky rights to broad identities represent the exposure we're auditing for.

Follow-up: "Are there scenarios where a Deny entry itself is worth reviewing?" — Answer: yes — an unexpected Deny entry could be blocking a legitimate account from needed access, which is a different kind of problem (availability, not security exposure) that a separate check could look for.

Q3. Why does this script never attempt to remove or modify a flagged permission automatically?

Answer: Permission data alone doesn't reveal business context — a broad-looking grant might be load-bearing for something that only runs occasionally, and removing it automatically risks breaking functionality in a way that may not surface immediately, making root-cause tracing much harder than with more immediately-visible failures.

Follow-up: "If the business insisted on some level of automated remediation here, what controls would you want in place first?" — Answer: at minimum, a documented approval/change-ticket requirement per change, a dry-run/impact-analysis step showing exactly what would be affected, and likely a rollback snapshot of the ACL taken immediately before any change — substantially more governance than Project 14's firewall rule creation needed.
