Quick Recap of Projects 1–29

Projects 27, 28, and 29 each answered one question in isolation: who has privileged group access, who's inactive, whose password is expiring. This project asks the more useful combined question: for privileged accounts specifically, are any of them exhibiting MULTIPLE risk signals at once? An account that's both privileged AND inactive AND has a stale password is a materially higher risk than one with just a single flag — exactly the kind of synthesis Project 17 modeled for patch readiness, now applied to identity risk.

The Story — Why We're Building This

The annual security audit wants a single answer to a compound question: "Show us every privileged account, and for each one, tell us if it's actively used, whether its password is current, and whether it's still legitimately needed." Pulling this together today means three separate people running three separate reports and manually cross-referencing SamAccountNames in a spreadsheet. Our manager wants one script that identifies every privileged account and enriches it with all three risk signals in a single pass.

Concepts First — Before We Touch Code

1. Finding Privileged Accounts: The AdminCount Attribute

Get-ADUser -Filter { AdminCount -eq 1 } -Properties AdminCount, PasswordLastSet, LastLogonDate
What AdminCount actually meansActive Directory automatically sets AdminCount = 1 on any account that is (or ever was) a member of certain protected privileged groups (Domain Admins, Enterprise Admins, and similar). Importantly, this flag is sticky — it doesn't automatically clear itself if the account is later removed from the privileged group, which makes it a genuinely useful "has this account ever had elevated privileges" signal, distinct from (and complementary to) Project 27's current-membership check.

2. Why AdminCount and Current Group Membership Tell Different Stories

SignalTells You
AdminCount = 1Ever was privileged (sticky flag, doesn't auto-clear)
Currently in Domain Admins (Project 27)Currently, actively privileged right now

An account with AdminCount = 1 but not currently in any privileged group is a genuinely interesting finding: it once had elevated access that was properly removed, but the sticky flag remains — worth knowing about, distinct from a currently-privileged account.

3. Combining Three Prior Projects' Logic

For each privileged account found, we enrich it with:

  • Days since last logon (Project 28's calculation)
  • Days until/since password expiry (Project 29's calculation)
  • Currently a member of a privileged group, or just AdminCount-flagged (Project 27's distinction)

4. A Combined Risk Score — Simple, Transparent Weighting

Rather than a single pass/fail, we'll build a simple point-based risk indicator: each concerning signal (inactive, password stale, no longer actually in a privileged group despite the flag) adds to a combined score, giving reviewers a way to prioritize the accounts most worth investigating first.

5. Still Detection-Only

Consistent with Projects 15 and 27 — this audit never modifies group membership, disables accounts, or resets passwords. It synthesizes information for human review.

Full Script — Invoke-PrivilegedAccountAudit.ps1

# =====================================================================
# Invoke-PrivilegedAccountAudit.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Comprehensive, read-only privileged account risk audit (synthesis project)
# =====================================================================

Import-Module ActiveDirectory -ErrorAction Stop

$InactiveDaysThreshold  = 60                                     # Reused thinking from Project 28
$PasswordStaleThreshold = 90                                     # Reused thinking from Project 29
$PrivilegedGroups = @("Domain Admins", "Enterprise Admins")      # Reused from Project 27's config-driven idea, inlined here for simplicity

Write-Host "`n=== PRIVILEGED ACCOUNT AUDIT (READ-ONLY, SYNTHESIS) ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Find every account ever flagged as privileged (AdminCount)
# ---------------------------------------------------------------
$PrivilegedAccounts = Get-ADUser -Filter { AdminCount -eq 1 -and Enabled -eq $true } `
    -Properties AdminCount, PasswordLastSet, PasswordNeverExpires, LastLogonDate

Write-Host "Found $($PrivilegedAccounts.Count) account(s) flagged with AdminCount=1.`n" -ForegroundColor Cyan

# ---------------------------------------------------------------
# STEP 2: Build the current effective membership of each privileged group (Project 27's technique)
# ---------------------------------------------------------------
$CurrentPrivilegedMembers = @()
foreach ($GroupName in $PrivilegedGroups) {
    $CurrentPrivilegedMembers += (Get-ADGroupMember -Identity $GroupName -Recursive -ErrorAction SilentlyContinue |
        Where-Object { $_.objectClass -eq "user" }).SamAccountName
}
$CurrentPrivilegedMembers = $CurrentPrivilegedMembers | Select-Object -Unique   # Removes duplicates if someone's in multiple groups

$Results = @()

foreach ($Account in $PrivilegedAccounts) {                        # Loops through every AdminCount-flagged account

    $RiskScore = 0                                                    # Starts at zero, accumulates per concerning signal
    $RiskFactors = @()                                                  # Human-readable list of WHY this account is risky

    # --- Signal 1: Currently privileged, or just flagged? (Project 27's distinction) ---
    $CurrentlyPrivileged = $Account.SamAccountName -in $CurrentPrivilegedMembers
    if (-not $CurrentlyPrivileged) {
        $RiskScore += 1
        $RiskFactors += "AdminCount set but NOT currently in a privileged group (stale flag)"
    }

    # --- Signal 2: Inactivity (Project 28's calculation) ---
    $DaysInactive = if ($Account.LastLogonDate) { ((Get-Date) - $Account.LastLogonDate).Days } else { $null }
    if ($null -eq $DaysInactive -or $DaysInactive -ge $InactiveDaysThreshold) {
        $RiskScore += 2                                                  # Weighted higher - inactive AND privileged is a serious combination
        $RiskFactors += if ($null -eq $DaysInactive) { "Never logged on" } else { "Inactive $DaysInactive days" }
    }

    # --- Signal 3: Password age (Project 29's calculation, simplified to age rather than full expiry) ---
    $PasswordAgeDays = if ($Account.PasswordLastSet) { ((Get-Date) - $Account.PasswordLastSet).Days } else { $null }
    if (-not $Account.PasswordNeverExpires -and ($null -eq $PasswordAgeDays -or $PasswordAgeDays -ge $PasswordStaleThreshold)) {
        $RiskScore += 1
        $RiskFactors += if ($null -eq $PasswordAgeDays) { "Password never set" } else { "Password $PasswordAgeDays days old" }
    }

    $Results += [PSCustomObject]@{
        SamAccountName       = $Account.SamAccountName
        Name                 = $Account.Name
        CurrentlyPrivileged  = $CurrentlyPrivileged
        DaysInactive         = $DaysInactive
        PasswordAgeDays      = $PasswordAgeDays
        RiskScore            = $RiskScore
        RiskFactors          = $RiskFactors -join "; "                    # Flattened to one string for CSV-friendliness
    }
}

# ---------------------------------------------------------------
# STEP 3: Sort by risk score, highest (most concerning) first
# ---------------------------------------------------------------
$Results = $Results | Sort-Object RiskScore -Descending

foreach ($Result in $Results) {
    $Color = if ($Result.RiskScore -ge 3) { "Red" } elseif ($Result.RiskScore -ge 1) { "Yellow" } else { "Green" }
    Write-Host "  [$($Result.RiskScore)pt] $($Result.SamAccountName) - $($Result.RiskFactors)" -ForegroundColor $Color
}

# ---------------------------------------------------------------
# STEP 4: Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\PrivilegedAudit_$Timestamp.csv" -NoTypeInformation

$HighRisk = ($Results | Where-Object { $_.RiskScore -ge 3 }).Count
Write-Host "`nSummary: $HighRisk high-risk (score 3+) privileged account(s) out of $($Results.Count) total." -ForegroundColor Cyan
Write-Host "REMINDER: No accounts or group memberships were changed. Review and remediate manually." -ForegroundColor Yellow

Line-by-Line Explanation

Get-ADUser -Filter { AdminCount -eq 1 -and Enabled -eq $true } -Properties AdminCount, PasswordLastSet, PasswordNeverExpires, LastLogonDate

  • One query, four explicitly requested properties — everything the rest of the script needs is fetched in a single round-trip to AD, rather than making separate calls per signal, which would be significantly slower across many accounts.

$RiskScore = 0 / $RiskFactors = @()

  • Two parallel pieces of information tracked per account: a number for sorting/prioritization, and a human-readable explanation for why that number is what it is — a report that only showed "risk score: 3" without explaining what contributed to it would be far less actionable for whoever reviews it.

$RiskScore += 2 for inactivity, vs += 1 for the other two signals

  • Not every risk signal is equally concerning — a privileged account that's been completely inactive for months is arguably more urgent than one with a slightly stale password, so the weighting reflects that judgment explicitly in the code rather than treating every signal as equally important.

$RiskFactors -join "; "

  • The opposite operation of -split (used throughout this course since Project 7) — combines an array of strings into one, here with "; " as the separator, producing a single CSV-friendly cell instead of an array that wouldn't export cleanly.

$Results | Sort-Object RiskScore -Descending

  • Descending this time, not ascending — for a risk score, higher means more urgent/concerning, the opposite ordering logic from Project 19/20's "soonest expiry first" ascending sorts, another reminder that the right sort direction depends entirely on what the number represents.

Production Incident Walkthrough

The audit's top-scoring result: an account with AdminCount=1, NOT currently in any privileged group, 140 days inactive, and a 200-day-old password. Investigation reveals it belonged to a contractor whose engagement ended five months ago — their privileged access was properly revoked at the time (explaining why they're not currently in Domain Admins), but the account itself was never disabled, and the sticky AdminCount flag correctly preserved the historical record that flagged it for this audit in the first place.
  • Why did this account surface here when Project 27's audit alone wouldn't have caught it? Project 27 only checks current group membership — since this contractor was properly removed from Domain Admins, they wouldn't appear as an unapproved current member. It took the AdminCount flag (Project 30's addition) combined with inactivity to reveal that the account itself, not just its group access, was never properly cleaned up.

Common Mistakes to Avoid

  • Confusing AdminCount=1 with "currently privileged" — they answer different questions.
  • Producing a risk score with no explanation of what drove it.
  • Treating every risk signal as equally weighted when some are genuinely more concerning than others.
  • Re-deriving individual signal calculations from scratch instead of reusing Projects 27-29's proven logic.

Interview Preparation

Q1. What does the AdminCount attribute actually tell you, and why is it described as "sticky"?

Answer: AD automatically sets AdminCount=1 on any account that is or has ever been a member of certain protected privileged groups. It's called sticky because AD doesn't automatically clear it back to 0 when the account is later removed from that group — making it a durable historical record of past privileged access, not just current status.

Follow-up: "Why would Microsoft design it to not auto-clear?" — Answer: as a security feature — it helps administrators identify accounts that once had elevated access and may still have residual permissions or protective ACL settings applied from that period, which wouldn't be visible if the flag simply disappeared once someone left the group.

Q2. Why weight the inactivity signal higher than the password-age signal in this script's risk score?

Answer: A privileged account that's completely inactive is a more concerning combination than one that's actively used but has a slightly stale password — an unused privileged account sitting dormant is exactly the kind of credential that could be compromised or misused without anyone noticing, since nobody's actively watching it.

Follow-up: "How would you justify or adjust these specific weights in a real organization?" — Answer: weights should reflect the organization's actual risk priorities, ideally set collaboratively with the security team rather than a developer's own guess — this script's weights are a reasonable starting point, not a definitive standard.

Q3. This project reuses logic from Projects 27, 28, and 29 rather than introducing much new PowerShell syntax. What's the actual learning value here?

Answer: Real-world reporting and automation work often involves exactly this kind of synthesis — combining already-solved individual problems into a more useful combined view — rather than constantly learning brand-new syntax. Recognizing when a new requirement is really "combine what I already know how to do" rather than "learn something entirely new" is itself a valuable, transferable skill.

Follow-up: "How does this compare to Project 17's role in the Intermediate stage?" — Answer: directly analogous — Project 17 synthesized disk, service, and reboot checks into one patch-readiness verdict; this project synthesizes group membership, activity, and password-age checks into one privileged-account risk score. Same architectural idea, different domain.
