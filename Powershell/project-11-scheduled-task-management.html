Quick Recap of Projects 1–10

Project 10 gave us Repair-ServiceHealth.ps1 — a safe, idempotent, logged service-recovery script. It's still only useful if a human remembers to run it. This project closes that gap: we'll schedule it to run automatically using Windows Task Scheduler, managed entirely through PowerShell, using the same SupportsShouldProcess and idempotency patterns from Project 10.

The Story — Why We're Building This

Our manager is happy with the service recovery script, but points out the obvious gap: "This is great, but someone still has to remember to run it. I want it running automatically every hour, and I want a way to check whether the scheduled task itself is healthy — because an automation that silently stopped running is worse than not having automation at all, since everyone assumes it's still protecting us."

Concepts First — Before We Touch Code

1. The Three Building Blocks of a Scheduled Task

Trigger (WHEN)
+
Action (WHAT)
+
Settings (HOW)
=
Registered Task
ComponentCmdletAnswers
TriggerNew-ScheduledTaskTriggerWhen should this run? (daily, at logon, every N minutes)
ActionNew-ScheduledTaskActionWhat program/script should it execute?
SettingsNew-ScheduledTaskSettingsSetHow should it behave? (retry on failure, run on battery, etc.)

Each of these cmdlets builds one piece of the task as an object in memory — nothing is actually scheduled yet until we combine them and register the result.

2. Building Each Piece

$Action = New-ScheduledTaskAction `
    -Execute "powershell.exe" `                                 # The program to run
    -Argument "-NoProfile -ExecutionPolicy Bypass -File `"C:\PS-Masterclass\Project10\Repair-ServiceHealth.ps1`" -WhatIf:`$false"

$Trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Hours 1) -RepetitionDuration ([TimeSpan]::MaxValue)

$Settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 5)
  • -Execute "powershell.exe" — scheduled tasks run a program, not a script directly; we point it at PowerShell itself and pass our script as an argument.
  • -NoProfile — skips loading the user's PowerShell profile, keeping scheduled runs fast and predictable rather than depending on whatever customizations happen to be in someone's profile.
  • -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Hours 1) -RepetitionDuration ([TimeSpan]::MaxValue) — a common idiom for "run every hour, forever": a one-time trigger that then repeats indefinitely, rather than a literal daily/weekly schedule.
  • -StartWhenAvailable — if the scheduled time was missed (server was off), run it as soon as possible afterward instead of skipping that run entirely.

3. Register-ScheduledTask — Actually Creating It

Register-ScheduledTask -TaskName "ABCBank-ServiceRecovery" -Action $Action -Trigger $Trigger -Settings $Settings -RunLevel Highest -User "SYSTEM"
  • -RunLevel Highest — runs the task with elevated (administrator) privileges, needed since restarting services requires that level of access.
  • -User "SYSTEM" — runs as the built-in SYSTEM account rather than a specific person's login, so the task keeps working even if that person changes their password, leaves the team, or isn't logged in.

4. Idempotency, Again — Don't Register the Same Task Twice

What goes wrong without this checkRunning a registration script twice without checking first would either error out (task name already exists) or, worse on some systems, create confusing duplicate/overlapping schedules. Exactly the same idempotency principle from Projects 6 and 10 — check current state, act only if a change is actually needed.
$ExistingTask = Get-ScheduledTask -TaskName $TaskName -ErrorAction SilentlyContinue
if ($ExistingTask) {
    Write-Host "Task already exists - skipping registration" -ForegroundColor Yellow
}
else {
    # register it
}

5. Verifying Task Health with Get-ScheduledTaskInfo

Registering a task once isn't the whole story — our manager specifically wants to know if it's still working. Get-ScheduledTaskInfo reports the last time it ran and what happened.

PropertyMeaning
LastRunTimeWhen the task last executed
LastTaskResultExit code from the last run — 0 means success
NextRunTimeWhen it's scheduled to run next
Why LastTaskResult = 0 mattersThis follows the same convention as most command-line programs: an exit code of 0 means success, any non-zero value means something went wrong. Checking this is how we detect "the task ran but the script inside it failed," not just "the task exists."

Full Script — Register-RecoveryTask.ps1

# =====================================================================
# Register-RecoveryTask.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Idempotently register and verify the hourly service recovery task
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]      # Enables -WhatIf/-Confirm at the script level (Project 10 pattern)
param(
    [switch]$WhatIf = $true                   # Safe by default
)

$TaskName   = "ABCBank-ServiceRecovery"
$ScriptPath = "C:\PS-Masterclass\Project10\Repair-ServiceHealth.ps1"   # The script this task will run

Write-Host "`n=== SCHEDULED TASK MANAGEMENT: $TaskName ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Idempotency check - does the task already exist?
# ---------------------------------------------------------------
$ExistingTask = Get-ScheduledTask -TaskName $TaskName -ErrorAction SilentlyContinue   # $null if not found

if ($ExistingTask) {
    Write-Host "Task '$TaskName' already exists (State: $($ExistingTask.State)) - skipping registration." -ForegroundColor Yellow
}
else {
    # -----------------------------------------------------------
    # STEP 2: Build the three components - nothing is scheduled yet
    # -----------------------------------------------------------
    $Action = New-ScheduledTaskAction `                                     # WHAT to run
        -Execute "powershell.exe" `
        -Argument "-NoProfile -ExecutionPolicy Bypass -File `"$ScriptPath`" -WhatIf:`$false"

    $Trigger = New-ScheduledTaskTrigger `                                    # WHEN to run - every hour, indefinitely
        -Once -At (Get-Date) `
        -RepetitionInterval (New-TimeSpan -Hours 1) `
        -RepetitionDuration ([TimeSpan]::MaxValue)

    $Settings = New-ScheduledTaskSettingsSet `                                # HOW it should behave
        -StartWhenAvailable `                                                   # Catch up if a run was missed
        -RestartCount 3 `                                                        # Retry the TASK itself up to 3 times if it fails
        -RestartInterval (New-TimeSpan -Minutes 5)

    # -----------------------------------------------------------
    # STEP 3: Register the task - respects -WhatIf automatically
    # -----------------------------------------------------------
    if ($PSCmdlet.ShouldProcess($TaskName, "Register Scheduled Task")) {        # Same ShouldProcess pattern from Project 10

        Register-ScheduledTask `
            -TaskName $TaskName `
            -Action $Action `
            -Trigger $Trigger `
            -Settings $Settings `
            -RunLevel Highest `                                                    # Needed to restart services
            -User "SYSTEM" `                                                        # Runs independent of any one person's login
            -Description "ABC Bank - Hourly automated service recovery check (Project 10 script)" | Out-Null

        Write-Host "Task '$TaskName' registered successfully." -ForegroundColor Green
    }
    else {
        Write-Host "PREVIEW: Would register task '$TaskName' to run hourly." -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 4: Verify current task health, regardless of whether we just created it
# ---------------------------------------------------------------
$TaskInfo = Get-ScheduledTask -TaskName $TaskName -ErrorAction SilentlyContinue

if ($TaskInfo) {
    $Info = Get-ScheduledTaskInfo -TaskName $TaskName    # Pulls run history/results for the task

    Write-Host "`n--- TASK HEALTH ---" -ForegroundColor Cyan
    Write-Host "State:          $($TaskInfo.State)"
    Write-Host "Last Run Time:  $($Info.LastRunTime)"
    Write-Host "Last Result:    $($Info.LastTaskResult)  $(if ($Info.LastTaskResult -eq 0) {'(SUCCESS)'} elseif ($null -eq $Info.LastRunTime) {'(NEVER RUN YET)'} else {'(NON-ZERO - CHECK LOGS)'})"
    Write-Host "Next Run Time:  $($Info.NextRunTime)"
}
else {
    Write-Host "`nTask does not exist yet (preview mode, or registration was skipped)." -ForegroundColor Yellow
}

Line-by-Line Explanation

-Argument "-NoProfile -ExecutionPolicy Bypass -File `"$ScriptPath`" -WhatIf:`$false"

  • -ExecutionPolicy Bypass — scheduled tasks run non-interactively, so there's no user present to approve an execution policy prompt; Bypass avoids the task silently failing due to policy restrictions, scoped only to this one launch of PowerShell (same safe, narrow-scope idea as Project 1's -Scope Process).
  • The backtick before each embedded double-quote (`") and before $false (`$false) are escape sequences — since this whole argument is itself inside a double-quoted string, we need to escape the inner quotes so PowerShell doesn't think the string ends early, and escape the dollar sign so $false is passed through literally as text for powershell.exe to interpret later, rather than PowerShell trying to substitute a variable named $false right now.

New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Hours 1) -RepetitionDuration ([TimeSpan]::MaxValue)

  • New-TimeSpan -Hours 1 — builds a TimeSpan object representing a duration (1 hour), the same underlying .NET type we've been producing since Project 1's uptime calculation, just built directly this time instead of by subtracting two dates.
  • [TimeSpan]::MaxValue — a static property (not a method this time, no parentheses needed) on the TimeSpan type representing the largest possible duration — used here as a practical stand-in for "repeat forever."

$ExistingTask = Get-ScheduledTask -TaskName $TaskName -ErrorAction SilentlyContinue

  • When no task with that name exists, this returns $null rather than throwing — so if ($ExistingTask) naturally evaluates to $false for "not found" without needing a try/catch here, a simpler pattern than Project 4's service check because a missing scheduled task is a fully expected, first-run scenario rather than something we need detailed error information about.

"$(if ($Info.LastTaskResult -eq 0) {'(SUCCESS)'} elseif (...) {...} else {...})"

  • Another use of the subexpression operator $( ) from Project 5, here wrapping an entire if/elseif/else chain so its result can be embedded directly inside a larger interpolated string — a compact way to add conditional text to a single Write-Host line without extra variables.

Windows' Task Scheduler service is the OS component actually responsible for watching the clock and launching tasks — our PowerShell commands are just a convenient interface to define and query what it manages. Under the hood, each registered task is stored as an XML definition, though we never need to touch that directly thanks to the ScheduledTasks module's cmdlets.

Production Incident Walkthrough

Two months later, someone reorganizes folders on WINAPP22 and accidentally deletes the Repair-ServiceHealth.ps1 file the scheduled task points to. The task still "exists" and still fires every hour — but LastTaskResult starts showing a non-zero error code every single run, completely invisible unless someone specifically checks.
  • Why is "the task exists" not enough to trust the automation is working? A task can be present, enabled, and firing on schedule while the thing it's supposed to run is broken, missing, or erroring every time — exactly why we built the health-verification step (Step 4) as a separate concern from registration.
  • How would you catch this kind of silent failure going forward? Run this same verification script (or the health-check portion of it) as its own periodic check — a script that checks whether another automation is still healthy is a legitimate and common pattern, sometimes called a "watchdog."

Security & Best Practices

Why SYSTEM instead of a personal accountRunning automation under an individual's credentials means the task breaks the moment that person's password changes, their account is disabled, or they leave the company — using the built-in SYSTEM account (or, in a real enterprise environment, a dedicated service account with only the permissions it needs) keeps automation stable and independent of any one person.
Best practice reinforced here-ExecutionPolicy Bypass is scoped to just this one launch of PowerShell inside the scheduled task's action, not applied system-wide — the same narrow-scope principle as every execution policy change we've made since Project 1.

Common Mistakes to Avoid

  • Registering a task without checking whether it already exists, risking duplicates.
  • Assuming a task that "exists" is automatically working correctly.
  • Scheduling automation under a personal user account instead of SYSTEM or a service account.
  • Forgetting -ExecutionPolicy Bypass, causing silent failures with no interactive prompt to reveal why.

Interview Preparation

Q1. What are the three components you need to define before registering a scheduled task, and what does each control?

Answer: A Trigger (when it runs), an Action (what it runs), and Settings (how it behaves — retry behavior, whether to catch up on missed runs, etc). All three are built as separate objects first, then combined during Register-ScheduledTask.

Follow-up: "Can one task have multiple triggers or multiple actions?" — Answer: yes — both -Trigger and -Action accept arrays, so a single task can run multiple times per day via different triggers, or perform multiple actions in sequence.

Q2. Why check Get-ScheduledTask before calling Register-ScheduledTask instead of just always registering?

Answer: Registering a task with a name that already exists either errors out or can create confusing duplicate scheduling — the same idempotency principle applied throughout this course: check current state, only change what actually needs to change.

Follow-up: "What if you wanted to update an existing task's settings instead of leaving it alone?" — Answer: use Set-ScheduledTask to modify an existing task in place, rather than unregistering and re-registering it — worth branching to explicitly rather than treating "exists" as always meaning "skip."

Q3. Why is checking LastTaskResult important, beyond just confirming the task exists and is enabled?

Answer: A task can be correctly registered, enabled, and firing on schedule while the script it runs is failing every single time — LastTaskResult reveals whether the actual work succeeded, not just whether the scheduling mechanism itself is intact.

Follow-up: "How would you turn this health check into an actual alert instead of just console output?" — Answer: wrap the LastTaskResult check in a condition that writes to the same audit log from Project 10, or exits with a non-zero code itself if unhealthy, so it can be monitored by another layer of automation or alerting.
