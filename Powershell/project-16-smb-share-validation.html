Quick Recap of Projects 1–15

Project 15 audited NTFS permissions on folders. This project audits a different, related layer: SMB shares — the network-facing doorway into those same folders. We'll reuse the associated-object query pattern from Project 14 (share, then its access rules, as separate linked objects) and the detection-only philosophy from Project 15.

The Story — Why We're Building This

Following up on the NTFS permission incident from Project 15, the security team asks a related question: "NTFS looked bad on that folder — but what about the network share pointing at it? Is the share itself also wide open?" This reveals a gap in most people's understanding: a folder's NTFS permissions and its SMB share permissions are two separate, independent gates. Our manager wants a script that audits share-level permissions specifically, since a share can be misconfigured even when the underlying folder's NTFS permissions are perfectly fine.

Concepts First — Before We Touch Code

1. The "Double Gate" — Share Permissions AND NTFS Permissions

Network User
→
Share Permission Gate
→
NTFS Permission Gate
→
Actual File Access
The single most important concept in this projectWhen a file is accessed over the network via a share, both the share permission and the underlying NTFS permission apply, and the more restrictive of the two always wins. A share set to "Everyone: Full Control" is not automatically a problem if the underlying NTFS permissions are properly locked down — but it removes a layer of defense, and in practice, share permissions are very often left wide open "because NTFS handles the real security," which is exactly the kind of assumption worth verifying rather than trusting.

2. Get-SmbShare — Listing Shares

Get-SmbShare | Select-Object Name, Path, Description

Lists configured shares on the local machine — the network-visible names (like \\SERVER\Statements) and which local folder path each one actually points to.

3. Get-SmbShareAccess — The Associated Permission Object

Get-SmbShareAccess -Name "Statements"
Same pattern as Project 14Just like a firewall rule's port details lived on a separate, associated Get-NetFirewallPortFilter object, a share's permissions live on a separate Get-SmbShareAccess result rather than directly on the Get-SmbShare object — recognizing this recurring "main object + associated details object" pattern makes learning new Windows administration modules faster over time.
PropertyMeaning
AccountNameWho this share-level permission applies to
AccessRightFull, Change, or Read
AccessControlTypeAllow or Deny

4. Share-Level Rights Are Simpler Than NTFS Rights

Unlike NTFS's many combinable FileSystemRights flags (Project 15), share permissions only have three levels: Read, Change (read/write/delete), and Full (Change plus permission management) — a much smaller, simpler set to reason about.

5. Comparing the Two Layers Together

A genuinely useful audit checks both layers for the same share and reports them side by side — revealing cases where the share is wide open even though NTFS is locked down (a partially-mitigated risk worth knowing about) versus cases where both layers are wide open (the real emergency).

6. Still Detection-Only

Same reasoning as Project 15 — changing share or NTFS permissions can break legitimate access in ways that aren't obvious from the permission data alone, so this script reports and never modifies.

Full Script — Test-SmbShareCompliance.ps1

# =====================================================================
# Test-SmbShareCompliance.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Audit SMB share AND underlying NTFS permissions together (read-only)
# =====================================================================

$HighRiskGroups = @("Everyone", "Authenticated Users", "BUILTIN\Users")   # Same risky identity list as Project 15
$Findings = @()

Write-Host "`n=== SMB SHARE COMPLIANCE AUDIT (READ-ONLY) ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Get every share on this machine, excluding Windows' built-in admin shares
# ---------------------------------------------------------------
$Shares = Get-SmbShare | Where-Object { $_.Name -notlike "*$" }   # Admin shares like C$, ADMIN$ end in $ - not relevant here

foreach ($Share in $Shares) {                                       # $Share is one share object

    Write-Host "`nAuditing share '$($Share.Name)' -> $($Share.Path)" -ForegroundColor Cyan

    # -------------------------------------------------------
    # STEP 2: Get the SHARE-level permissions (associated object, Project 14 pattern)
    # -------------------------------------------------------
    $ShareAccess = Get-SmbShareAccess -Name $Share.Name

    foreach ($Access in $ShareAccess) {                                # Loops through each share-level permission entry

        $IsHighRiskIdentity = $HighRiskGroups | Where-Object { $Access.AccountName -like "*$_*" }
        $IsBroadRight       = $Access.AccessRight -in @("Full", "Change")   # Read-only grants are lower priority
        $ShareFlagged       = ($IsHighRiskIdentity -and $IsBroadRight -and $Access.AccessControlType -eq "Allow")

        # -----------------------------------------------------
        # STEP 3: Cross-check against the underlying NTFS permissions (Project 15's technique, reused)
        # -----------------------------------------------------
        $NtfsFlagged = $false
        if (Test-Path $Share.Path) {                                    # Confirms the underlying folder is actually reachable
            $Acl = Get-Acl -Path $Share.Path
            foreach ($Ace in $Acl.Access) {
                $NtfsIsHighRisk = $HighRiskGroups | Where-Object { $Ace.IdentityReference.ToString() -like "*$_*" }
                $NtfsIsRisky    = $Ace.FileSystemRights.ToString() -match "Modify|FullControl|Write"
                if ($NtfsIsHighRisk -and $NtfsIsRisky -and $Ace.AccessControlType -eq "Allow") {
                    $NtfsFlagged = $true                                     # At least one risky NTFS grant also exists
                }
            }
        }

        # -----------------------------------------------------
        # STEP 4: Combine both layers into one overall risk picture
        # -----------------------------------------------------
        $OverallRisk = if ($ShareFlagged -and $NtfsFlagged) { "CRITICAL (both layers open)" }
                       elseif ($ShareFlagged) { "MODERATE (share open, NTFS may mitigate)" }
                       elseif ($NtfsFlagged) { "MODERATE (NTFS open, share may mitigate)" }
                       else { "Normal" }

        $Findings += [PSCustomObject]@{
            ShareName    = $Share.Name
            SharePath    = $Share.Path
            Identity     = $Access.AccountName
            ShareRight   = $Access.AccessRight
            ShareFlagged = $ShareFlagged
            NtfsFlagged  = $NtfsFlagged
            OverallRisk  = $OverallRisk
        }

        if ($OverallRisk -ne "Normal") {
            $Color = if ($OverallRisk -like "CRITICAL*") { "Red" } else { "Yellow" }
            Write-Host "  $OverallRisk - '$($Access.AccountName)': Share=$($Access.AccessRight)" -ForegroundColor $Color
        }
    }
}

# ---------------------------------------------------------------
# Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Findings | Export-Csv -Path ".\reports\SmbAudit_$Timestamp.csv" -NoTypeInformation

$CriticalCount = ($Findings | Where-Object { $_.OverallRisk -like "CRITICAL*" }).Count
Write-Host "`nSummary: $CriticalCount critical (both-layer) finding(s) across $($Shares.Count) share(s)." -ForegroundColor Cyan
Write-Host "REMINDER: No permissions were changed. Review and remediate manually." -ForegroundColor Yellow

Line-by-Line Explanation

$Shares = Get-SmbShare | Where-Object { $_.Name -notlike "*$" }

  • Windows automatically creates administrative shares (C$, ADMIN$, IPC$) on every machine, all ending in a dollar sign — filtering these out with -notlike "*$" keeps the audit focused on shares someone actually created intentionally for a business purpose.

$IsBroadRight = $Access.AccessRight -in @("Full", "Change")

  • Reusing the -in operator from Project 4, here checking against share-level rights (which, unlike NTFS's combinable flags, are always exactly one of Read/Change/Full) — a simpler check than Project 15's flags-based rights matching, precisely because share rights are a simpler model.

$OverallRisk = if ($ShareFlagged -and $NtfsFlagged) {...} elseif ($ShareFlagged) {...} elseif ($NtfsFlagged) {...} else {...}

  • This four-branch chain is the "double gate" concept translated directly into code: both layers open is the worst case (CRITICAL), either layer alone being open is still worth knowing about but is potentially mitigated by the other layer (MODERATE), and only when neither layer shows a risky grant do we call it Normal.

if (Test-Path $Share.Path) { ... } before the NTFS check

  • A share's configured path could theoretically point at a folder that no longer exists (moved, deleted, or on disconnected removable storage) — checking first prevents Get-Acl from erroring out and stopping the whole audit over one broken share.

Production Incident Walkthrough

Our audit reveals the customer statements share has "Everyone: Full" at the share level — but the underlying NTFS permissions turn out to be properly locked down to just the finance team's security group. The overall risk shows MODERATE rather than CRITICAL: the share layer is technically wrong, but the NTFS layer is actually preventing real unauthorized access.
  • Why still flag and fix the share-level issue if NTFS already protects the data? Defense in depth — relying on a single layer of protection means one future NTFS misconfiguration (exactly like Project 15's incident) would immediately become fully exploitable with no share-level backstop at all. Both layers should independently reflect least-privilege, not just whichever one happens to currently be doing the real work.
  • Why does this matter enough to build a whole separate audit instead of just relying on the Project 15 NTFS audit? Because share and NTFS permissions are configured through completely different tools and often by different people at different times — nothing guarantees they stay in sync, which is exactly why they need independent verification.

Security & Best Practices

Defense in depth, made concreteThis project is a direct, hands-on illustration of defense in depth: two independent layers of protection are both worth getting right, even when one alone would technically be "enough" — because layers fail independently, and relying on just one turns a single future mistake into a full exposure.
Best practice reinforced hereFiltering out administrative shares (C$, ADMIN$) keeps the audit's signal-to-noise ratio high — a report cluttered with expected, standard Windows shares would bury the handful of findings that actually matter.

Common Mistakes to Avoid

  • Assuming a locked-down NTFS folder means the share permissions don't matter.
  • Including built-in administrative shares in a business-focused audit, adding noise.
  • Treating "both layers open" the same as "one layer open" — they represent very different risk levels.

Interview Preparation

Q1. If a share is set to "Everyone: Full Control," does that mean anyone can do anything to the files?

Answer: Not necessarily — the underlying NTFS permissions on the folder still apply independently, and the more restrictive of the two layers wins. A wide-open share pointing at a folder with properly locked NTFS permissions is still meaningfully protected, though it's still a best-practice violation worth fixing.

Follow-up: "So why fix it if NTFS is already protecting the data?" — Answer: defense in depth — relying on only one layer means a single future NTFS mistake becomes immediately and fully exploitable, with no share-level backstop at all.

Q2. Why does share-level access use a simpler rights model (Read/Change/Full) than NTFS?

Answer: Share permissions were designed as a coarser, network-level gate, historically simpler by design; NTFS permissions offer much finer-grained control (individual rights like Delete, Take Ownership, etc., combinable as flags) because they operate at the file system level where more precise control is useful.

Follow-up: "Given NTFS is more granular, why not just set share permissions wide open everywhere and rely entirely on NTFS?" — Answer: that's a common real-world practice, but it removes a layer of protection and depends entirely on NTFS always being configured correctly — exactly the assumption Project 15's incident showed can fail.

Q3. Why check Test-Path on the share's underlying folder before running the NTFS audit portion?

Answer: A share's configured path isn't guaranteed to still exist — the folder could have been moved, deleted, or be on disconnected storage — checking first avoids an error that would otherwise stop the audit partway through instead of gracefully skipping just that one broken share.

Follow-up: "Should a share pointing at a non-existent path itself be flagged as a finding?" — Answer: arguably yes — it likely represents stale configuration worth cleaning up, even though it's a different kind of issue (broken config) rather than a security exposure.
