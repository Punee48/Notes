Quick Recap of Projects 1–21

Project 21 got a renewed certificate safely into the certificate store. But a certificate sitting in the store does nothing on its own — it has to be bound to a website before browsers actually see it. This project closes that final gap, introducing the IIS: PSDrive — the same provider-drive pattern we've now seen for the file system, registry, and certificate store.

The Story — Why We're Building This

The renewed certificate from Project 21 is sitting correctly in the certificate store — but the banking portal website is still serving the old, soon-to-expire one, because nobody's told IIS to actually use the new certificate yet. Our manager wants a script that binds a given certificate (by thumbprint) to a specific site and port, safely and idempotently, so this final deployment step isn't a manual, error-prone click through IIS Manager.

Concepts First — Before We Touch Code

1. The WebAdministration Module and the IIS: Drive

The same pattern, one more timeJust like HKLM: for the registry and Cert: for certificates, importing the WebAdministration module exposes IIS configuration as an IIS: PSDrive — sites, application pools, and bindings all become browsable, exactly like folders.
Import-Module WebAdministration
Get-ChildItem "IIS:\Sites"

2. What a Binding Actually Is

A binding connects a website to a specific IP address, port, and (for HTTPS) a certificate. One site can have multiple bindings — e.g. port 80 for HTTP and port 443 for HTTPS, each configured independently.

3. Viewing Existing Bindings with Get-WebBinding

Get-WebBinding -Name "Default Web Site"

Shows every binding configured for a site, including protocol, IP, port, and (for HTTPS bindings) whether a certificate hash is currently attached.

4. Binding a Certificate — Two Different Approaches

ApproachHow
New-WebBinding + certificate assignmentCreates the binding, then attaches a certificate via the IIS:\SslBindings path

# Attaching a certificate to an existing HTTPS binding via the SslBindings path
$BindingPath = "IIS:\SslBindings\0.0.0.0!443"
Get-Item "Cert:\LocalMachine\My\$Thumbprint" | New-Item -Path $BindingPath
  • IIS:\SslBindings\0.0.0.0!443 — the exclamation mark separates IP address from port in this particular provider path format; 0.0.0.0 means "any IP address" on port 443.
  • Piping a certificate object (from the Cert: drive we already know from Project 19) directly into New-Item on the IIS: drive is a genuinely elegant example of PowerShell's provider model letting two completely different subsystems (certificates and web server config) interoperate through the same object pipeline.

5. Idempotency — Don't Rebind What's Already Correctly Bound

Same principle as every remediation project since Project 10: check whether the site's current binding already uses the correct certificate thumbprint before doing anything, and skip cleanly if it does.

6. Why This Needs ShouldProcess

Changing a live website's certificate binding affects real traffic immediately — exactly the kind of action that deserves -WhatIf preview support before ever running for real, following Projects 10, 13, 14, and 21's established pattern.

Full Script — Set-IisCertificateBinding.ps1

# =====================================================================
# Set-IisCertificateBinding.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Idempotently bind a certificate to an IIS site's HTTPS binding
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]
param(
    [switch]$WhatIf = $true,
    [string]$SiteName        = "Default Web Site",
    [string]$CertThumbprint  = "PUT_YOUR_TEST_CERT_THUMBPRINT_HERE",
    [int]$Port                = 443
)

Import-Module WebAdministration -ErrorAction Stop   # Makes the IIS: drive and Get-WebBinding/New-WebBinding available

$LogPath = ".\logs\IisBindingChanges.log"
function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

Write-Host "`n=== IIS CERTIFICATE BINDING: $SiteName ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Ensure an HTTPS binding exists on the target port at all
# ---------------------------------------------------------------
$ExistingBinding = Get-WebBinding -Name $SiteName -Protocol "https" -Port $Port -ErrorAction SilentlyContinue

if (-not $ExistingBinding) {
    Write-Host "No HTTPS binding on port $Port yet." -ForegroundColor Yellow

    if ($PSCmdlet.ShouldProcess("$SiteName`:$Port", "Create HTTPS Binding")) {
        New-WebBinding -Name $SiteName -Protocol "https" -Port $Port -IPAddress "*"   # Creates the binding shell first, cert attached next
        Write-Log -Status "INFO" -Message "Created HTTPS binding for $SiteName on port $Port"
        $ExistingBinding = Get-WebBinding -Name $SiteName -Protocol "https" -Port $Port   # Re-fetch now that it exists
    }
    else {
        Write-Host "PREVIEW: Would create HTTPS binding on port $Port." -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 2: Check whether the CORRECT certificate is already attached (idempotency)
# ---------------------------------------------------------------
$CurrentThumbprint = if ($ExistingBinding.CertificateHash) { $ExistingBinding.CertificateHash } else { $null }

if ($CurrentThumbprint -eq $CertThumbprint) {
    Write-Host "Binding already uses the correct certificate ($CertThumbprint) - no action needed." -ForegroundColor Green
    Write-Log -Status "INFO" -Message "Binding for $SiteName`:$Port already correct - no change made"
}
else {
    Write-Host "Current cert: $(if ($CurrentThumbprint) {$CurrentThumbprint} else {''})  Desired: $CertThumbprint" -ForegroundColor Cyan

    if ($PSCmdlet.ShouldProcess("$SiteName`:$Port", "Attach certificate $CertThumbprint")) {

        Write-Log -Status "INFO" -Message "BEFORE CHANGE: $SiteName`:$Port had cert '$CurrentThumbprint'"   # Backup-before-change, Project 13's pattern

        $BindingPath = "IIS:\SslBindings\0.0.0.0!$Port"                                  # The provider path for this IP/port combination

        if (Test-Path $BindingPath) {                                                      # An SSL binding entry might already exist here
            Remove-Item -Path $BindingPath -Force                                            # Clear it before attaching the new certificate
        }

        Get-Item "Cert:\LocalMachine\My\$CertThumbprint" |                                  # Fetches the certificate object (Project 19/21's Cert: drive)
            New-Item -Path $BindingPath | Out-Null                                            # Attaches it to this IP/port via the IIS provider

        Write-Log -Status "SUCCESS" -Message "AFTER CHANGE: $SiteName`:$Port now bound to cert '$CertThumbprint'"
        Write-Host "Certificate bound successfully." -ForegroundColor Green
    }
    else {
        Write-Host "PREVIEW: Would attach certificate $CertThumbprint to $SiteName`:$Port" -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 3: Final verification
# ---------------------------------------------------------------
$FinalBinding = Get-WebBinding -Name $SiteName -Protocol "https" -Port $Port -ErrorAction SilentlyContinue
$FinalThumbprint = if ($FinalBinding) { $FinalBinding.CertificateHash } else { $null }

Write-Host "`nFinal verified binding certificate: $(if ($FinalThumbprint) {$FinalThumbprint} else {''})" -ForegroundColor Cyan
Write-Host "Audit log: $LogPath" -ForegroundColor Cyan

Line-by-Line Explanation

Import-Module WebAdministration -ErrorAction Stop

  • Unlike CIM or the registry (available by default), IIS management cmdlets and the IIS: drive only become available after explicitly importing this module — -ErrorAction Stop ensures a clear failure immediately if IIS management tools aren't installed, rather than confusing "command not found" errors later in the script.

Get-WebBinding -Name $SiteName -Protocol "https" -Port $Port -ErrorAction SilentlyContinue

  • Filtering by both protocol and port narrows this to exactly the one binding we care about — a site could have several HTTPS bindings on different ports, and we don't want to accidentally match the wrong one.

$CurrentThumbprint = if ($ExistingBinding.CertificateHash) { $ExistingBinding.CertificateHash } else { $null }

  • A binding can exist without any certificate attached yet (e.g. right after being newly created in Step 1) — this guards against comparing against a missing property and produces a clean $null in that case, feeding into the same "no value yet" handling pattern used for registry values in Project 13.

if (Test-Path $BindingPath) { Remove-Item -Path $BindingPath -Force }

  • An SSL binding "slot" for a given IP/port combination can only hold one certificate at a time — if one's already attached (even the wrong one), it must be cleared before a new one can be attached in its place, which is why this removal happens as part of the same guarded, ShouldProcess-checked block rather than being skipped.

Get-Item "Cert:\LocalMachine\My\$CertThumbprint" | New-Item -Path $BindingPath

  • This single line crosses two completely different PowerShell providers: Get-Item reads a specific certificate object off the Cert: drive, and pipes that same object into New-Item operating on the IIS: drive — the certificate object itself carries enough information (its raw certificate data) for the IIS provider to attach it correctly.

Production Incident Walkthrough

A manual certificate rebind last year went wrong when someone forgot to clear the old SSL binding entry first — the attempt to attach the new certificate silently failed, and the site kept serving the old, soon-to-expire certificate for two more weeks before anyone noticed the change hadn't actually taken effect. This script's explicit clear-then-attach sequence, plus its final verification step, exists specifically to prevent that exact failure mode from recurring.
  • Why does the script re-fetch and print the final bound thumbprint at the end, rather than trusting the New-Item call succeeded? Exactly the same "verify, don't just trust" principle from Project 13's registry work — a change silently not taking effect is a real, observed failure mode for IIS bindings specifically, so an explicit final check catches it immediately instead of leaving it to be discovered days later.

Interview Preparation

Q1. What's the difference between a certificate being "in the store" and a website "using" it?

Answer: A certificate sitting in Cert:\LocalMachine\My is just present on the server — nothing uses it automatically. A website only actually serves a given certificate once it's explicitly bound to that site's HTTPS binding; Projects 21 and 22 together cover both halves of getting a renewed certificate fully deployed.

Follow-up: "Could the same certificate be bound to multiple sites?" — Answer: yes, the same certificate (by thumbprint) can be attached to multiple bindings across multiple sites, as long as it's a valid match for each site's hostname(s).

Q2. Why does the script remove an existing SSL binding entry before attaching a new certificate, rather than just overwriting it directly?

Answer: The IIS:\SslBindings\IP!Port path can only hold one certificate binding at a time for that specific IP/port combination — attempting to create a new item there while one already exists can fail or behave unpredictably, so explicitly clearing it first ensures a clean, predictable replacement.

Follow-up: "What real-world incident does this pattern specifically guard against?" — Answer: exactly the one described in this project's incident walkthrough — a rebind that silently fails because the old binding entry was never cleared, leaving the site serving the old certificate without any obvious error.

Q3. Why is piping a Cert: object directly into New-Item on the IIS: drive considered elegant, rather than just error-prone magic?

Answer: It's a direct, visible expression of PowerShell's object pipeline and provider model working as designed — the certificate object carries everything the IIS provider needs, so no manual translation, string formatting, or external tool call is required to connect the two subsystems. It's the same underlying design philosophy as Project 1's very first pipeline example, now paying off in a genuinely practical, cross-subsystem task.

Follow-up: "What would the equivalent look like without PowerShell's provider model?" — Answer: historically, binding a certificate to IIS required calling netsh http add sslcert with manually formatted string parameters (IP:port, certificate hash, app ID) — functionally similar, but without the object-based safety and readability PowerShell's approach provides.
