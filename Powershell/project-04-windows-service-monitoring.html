Quick Recap of Projects 1–3

So far we've collected inventory data, added threshold-based status classification with functions and if/elseif/else, and sampled changing metrics with loops and switch statements. This project introduces checking a specific named list of things we care about — not "all services", but "the services this bank considers critical" — plus our first real error handling.

The Story — Why We're Building This

ABC Bank runs a small set of Windows services that absolutely must stay running on application servers — things like the print spooler for statement printing, the Windows Time service (critical for transaction timestamps and Kerberos authentication), and a few internal application services. Last month, someone manually disabled a service during troubleshooting and forgot to turn it back on. It stayed down for three days before anyone noticed.

Our manager wants a script that checks a defined list of critical services, reports which are running, which are stopped, and — importantly — which ones are supposed to start automatically but currently aren't running. It should also handle gracefully checking for a service that doesn't exist on a given server, rather than crashing.

Concepts First — Before We Touch Code

1. Get-Service and Its Key Properties

PropertyMeaning
NameThe service's short internal name (e.g. "Spooler")
DisplayNameThe human-friendly name shown in Services.msc
StatusCurrent state: Running, Stopped, Paused, etc.
StartTypeHow the service is configured to start: Automatic, Manual, Disabled

2. Why a Fixed List of Service Names, Not "Check Everything"

Design decisionA server can have 150+ services, most of which nobody cares about. Production monitoring should check a deliberately chosen, named list of services that actually matter to the business — this keeps alerts meaningful instead of drowning Operations in noise about irrelevant services.

3. Arrays of Strings

$CriticalServices = @("Spooler", "W32Time", "BITS")   # An ordered list of service names to check

Each item here is a plain string — the internal Name value Get-Service expects, not the DisplayName shown in the Services app.

4. try / catch / finally — Handling Errors Gracefully

By default, asking for a service that doesn't exist causes Get-Service to write a non-terminating error and return nothing. To handle this deliberately — and to prepare you for cases later where errors are terminating (like remote connection failures) — we wrap the check in try/catch.

try {
    $Service = Get-Service -Name "SomeService" -ErrorAction Stop   # Forces the error to be terminating so catch can react
}
catch {
    Write-Warning "Service not found: $($_.Exception.Message)"     # Runs only if the try block threw an error
}
finally {
    Write-Verbose "Check attempted for SomeService"                 # Always runs, whether it succeeded or failed
}
  • try { } — the block of code we want to attempt, watching for errors.
  • -ErrorAction Stop — by default many cmdlet errors are "non-terminating" and won't trigger catch at all; this parameter forces the error to stop and be catchable.
  • catch { } — runs only if the try block threw a terminating error; $_ here refers to the error record, and $_.Exception.Message gives the human-readable error text.
  • finally { } — always runs, whether or not an error occurred — useful for cleanup steps that must happen either way (we'll lean on this more once we're opening remote connections).

5. The -in Operator

$Value -in $Array checks whether a single value exists anywhere inside a collection — cleaner than writing a manual loop just to check membership.

6. The "Automatic but Stopped" Problem

Why this specific combination mattersA service set to Manual or Disabled and currently stopped might be perfectly intentional. But a service configured as Automatic (meaning "start with Windows") that is currently Stopped almost always signals something went wrong — either it crashed, or someone stopped it and never restarted it. This exact combination is one of the most common real-world Windows health checks.

Full Script — Test-ServiceHealth.ps1

# =====================================================================
# Test-ServiceHealth.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Verify a named list of critical Windows services are healthy
# =====================================================================

$ComputerName = $env:COMPUTERNAME     # The server being checked

# ---------------------------------------------------------------
# The list of services ABC Bank considers critical on this server role.
# Replace with real names from your machine, plus one fake one to test error handling.
# ---------------------------------------------------------------
$CriticalServices = @("Spooler", "BITS", "FakeServiceXYZ")   # Ordered list of internal service names to check

$Results = @()   # Empty array that will hold one result object per service

Write-Host "`n=== SERVICE HEALTH CHECK: $ComputerName ===" -ForegroundColor Magenta   # Section header

# ---------------------------------------------------------------
# STEP 1: Loop through the named list and check each service
# ---------------------------------------------------------------
foreach ($ServiceName in $CriticalServices) {          # $ServiceName becomes each string in the array, one at a time

    try {                                                # Attempt the check; watch for a "service not found" error
        $Service = Get-Service -Name $ServiceName -ErrorAction Stop   # -ErrorAction Stop makes a missing service throw

        # Decide the health status for a service that WAS found
        if ($Service.Status -eq "Running") {             # Simple case: it's running, so it's healthy
            $Status = "RUNNING"
        }
        elseif ($Service.StartType -eq "Automatic" -and $Service.Status -ne "Running") {  # The dangerous combination
            $Status = "STOPPED (SHOULD BE RUNNING)"        # Automatic service that isn't running - a real problem
        }
        else {
            $Status = "STOPPED (BY DESIGN)"                # Manual/Disabled and stopped - likely intentional
        }

        $Results += [PSCustomObject]@{                     # Adds a result row for this service
            ServerName  = $ComputerName
            ServiceName = $ServiceName
            DisplayName = $Service.DisplayName               # Human-friendly name from the found service object
            StartType   = $Service.StartType                 # Automatic / Manual / Disabled
            Status      = $Status                              # Our computed health label
        }
    }
    catch {                                                 # Runs only if Get-Service could not find the service
        $Results += [PSCustomObject]@{                       # Still adds a row, so the report shows every service we checked
            ServerName  = $ComputerName
            ServiceName = $ServiceName
            DisplayName = "N/A"                                # No display name available - the service doesn't exist
            StartType   = "N/A"
            Status      = "NOT FOUND"                           # Clear label for a missing service, not a crash
        }
        Write-Warning "Service '$ServiceName' was not found on $ComputerName."   # Also logs a warning to the console
    }
}

# ---------------------------------------------------------------
# STEP 2: Print color-coded results
# ---------------------------------------------------------------
foreach ($Result in $Results) {                            # Loops through every result we collected above

    $Line = "{0,-16} {1,-30} {2}" -f $Result.ServiceName, $Result.DisplayName, $Result.Status   # Aligned columns

    if ($Result.Status -eq "RUNNING") {
        Write-Host $Line -ForegroundColor Green              # Healthy
    }
    elseif ($Result.Status -like "STOPPED (SHOULD BE RUNNING)*") {   # -like allows a simple wildcard match
        Write-Host $Line -ForegroundColor Red                 # Real problem
    }
    elseif ($Result.Status -eq "NOT FOUND") {
        Write-Host $Line -ForegroundColor DarkYellow          # Configuration mismatch, needs review
    }
    else {
        Write-Host $Line -ForegroundColor Gray                # Stopped by design - informational only
    }
}

# ---------------------------------------------------------------
# STEP 3: Export to CSV
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) {                          # Creates the reports folder if it's missing
    New-Item -ItemType Directory -Path ".\reports" | Out-Null
}
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"               # Sortable timestamp for the filename
$Results | Export-Csv -Path ".\reports\ServiceHealth_$Timestamp.csv" -NoTypeInformation   # Saves every row

# ---------------------------------------------------------------
# STEP 4: Summarize problems found
# ---------------------------------------------------------------
$ProblemCount = ($Results | Where-Object { $_.Status -like "STOPPED (SHOULD BE RUNNING)*" -or $_.Status -eq "NOT FOUND" }).Count

Write-Host "`nSummary: $ProblemCount service(s) need attention." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

foreach ($ServiceName in $CriticalServices) { ... }

  • Same foreach keyword from Project 2, now looping over an array of strings we defined ourselves rather than objects returned by a cmdlet — a reminder that foreach works on any collection, not just CIM results.

Get-Service -Name $ServiceName -ErrorAction Stop

  • -Name $ServiceName — passes our loop variable as the service name to look up; on each loop iteration this points at a different string from the array.
  • -ErrorAction Stop — overrides the cmdlet's default error behavior for this one call, turning a "service not found" into a terminating error our catch block can react to.

elseif ($Service.StartType -eq "Automatic" -and $Service.Status -ne "Running")

  • -and — both sides must be true for the whole condition to match: the service must be configured as Automatic and not currently running.
  • -ne — "not equal to"; used here instead of checking every non-running state individually (Stopped, Paused, etc.) since we just care that it isn't Running.

catch { $Results += [PSCustomObject]@{ ... Status = "NOT FOUND" } ... }

  • Notice the catch block still builds a result row rather than just printing a warning and moving on — this keeps every checked service represented in the final report, which matters for auditing: "we checked this and it wasn't there" is different information from "we never checked it."
  • $_ inside a catch block refers to the error record, not a pipeline object — a different meaning of $_ than the one from earlier projects, depending on context.

"{0,-16} {1,-30} {2}" -f $Result.ServiceName, $Result.DisplayName, $Result.Status

  • {0,-16} — inside the format string, the number after the comma sets a minimum field width; the minus sign left-aligns the text and pads it with spaces, so columns line up visually in the console.

$Result.Status -like "STOPPED (SHOULD BE RUNNING)*"

  • -like — a wildcard comparison operator (different from -eq). The trailing * matches "anything after this point," letting us match the status string even though we don't repeat the exact same text everywhere it's used.

Architecture & Execution Flow

→
Found?
Yes → classify Status

→

Every path through the loop — found-and-healthy, found-and-broken, or not-found — ends up producing exactly one result row. That consistency is what makes the final report trustworthy: nothing silently disappears.

Windows Internals: How Get-Service Talks to Windows

PowerShell
→
Get-Service cmdlet
→
Service Control Manager (SCM)
→
Registered Windows Services
→
ServiceController Objects Returned

The Service Control Manager is the Windows component responsible for starting, stopping, and tracking every registered service. When a service name doesn't exist in the SCM's registry of known services, that's exactly the condition our try/catch is built to handle.

Production Incident Walkthrough

This script runs nightly across 50 application servers. Tonight, 47 report all-green, 2 report a service stopped-but-should-be-running, and 1 fails entirely because someone typo'd a service name in the config list months ago and nobody noticed.
  • Why does a typo'd service name matter as much as a real outage? A permanently mistyped name means that "service" has never actually been checked — it's a silent monitoring gap that looks like coverage but isn't. This is exactly why NOT FOUND gets its own distinct status instead of being lumped in with STOPPED.
  • Should the script exit early when it hits the first NOT FOUND? No — for the same reason as Project 2's incident: stopping early would mean the 2 real stopped-service problems on other servers never get reported.

Security & Best Practices

Best practice reinforced hereWe deliberately did not add code to automatically restart stopped services in this project. Detecting and reporting a problem is a separate, safer first step from taking automated corrective action — we'll introduce controlled, auditable remediation (with -WhatIf/-Confirm support) in the Advanced stage.
Least privilege reminderReading service status requires only standard read access; restarting services requires elevated rights. Keep detection scripts running with the minimum privilege they actually need.

Interview Preparation

Q1. What's the difference between a terminating and a non-terminating error in PowerShell?

Answer: A non-terminating error is reported but the cmdlet keeps going and the script continues; a terminating error stops execution of that statement immediately and can be caught with try/catch. Many cmdlets default to non-terminating errors, which is why -ErrorAction Stop is often needed to make try/catch actually work.

Follow-up: "What's $ErrorActionPreference and how does it relate?" — Answer: it's a script/session-wide default for how cmdlets handle errors when no explicit -ErrorAction is given; setting it to Stop affects every cmdlet in scope rather than one call at a time.

Q2. Why check StartType alongside Status instead of just Status?

Answer: Status alone can't distinguish an intentionally-disabled service from a critical one that crashed — combining both tells us whether "stopped" is expected or a real problem.

Follow-up: "What about a service set to Manual that should actually be running by policy?" — Answer: that's a configuration-drift case; a more advanced version of this script could compare StartType against an expected baseline value per service, not just check whether it's Automatic.

Q3. Why does the catch block still add a row to $Results instead of just skipping the service?

Answer: The report needs to show everything that was supposed to be checked, including checks that failed — otherwise a missing/misconfigured entry silently disappears and looks like full coverage when it isn't.

Follow-up: "How would you alert specifically on NOT FOUND separately from STOPPED?" — Answer: filter $Results with Where-Object { $_.Status -eq "NOT FOUND" } and route those to a different notification, since they usually mean a config problem, not a service outage.
