Quick Recap of Projects 1–28

Project 28 found accounts nobody's using. This project finds the opposite problem: accounts people are using, whose passwords are about to expire — a preventable helpdesk-ticket generator if nobody warns users in advance. We'll reuse the Warning/Critical threshold pattern one more time, applied to a genuinely new calculation: figuring out exactly when a password will expire from the domain's own policy.

The Story — Why We're Building This

Every month, the helpdesk sees a predictable spike in "I'm locked out" tickets — all from users whose passwords expired without warning. Windows can show an expiry warning at login, but plenty of ABC Bank staff use remote access methods that don't always surface that prompt clearly. Our manager wants a proactive report emailed (well — for now, generated) each week: everyone whose password will expire in the next 14 days, so IT or the users themselves can act before it becomes a lockout.

Concepts First — Before We Touch Code

1. Why You Can't Just Read "Expiry Date" Directly

There's no simple ExpiryDate propertyActive Directory doesn't store a password's expiry date directly — it stores PasswordLastSet (when it was last changed) and relies on the domain's password policy (specifically MaxPasswordAge) to determine how long after that a password remains valid. Calculating actual expiry requires combining both pieces of information.

2. Getting the Domain's Password Policy

Get-ADDefaultDomainPasswordPolicy

Returns the domain-wide password policy, including MaxPasswordAge as a TimeSpan — how long a password is valid before it must be changed.

3. Calculating Actual Expiry

$ExpiryDate = $User.PasswordLastSet + $MaxPasswordAge   # Adding a TimeSpan to a DateTime
  • Adding a TimeSpan (the policy's max age) directly to a DateTime (PasswordLastSet) produces a new DateTime — the actual date this specific user's password expires, given when they last changed it.

4. Fine-Grained Password Policies — A Real-World Complication

Worth knowing, even if this project simplifies itLarger organizations often have Fine-Grained Password Policies (FGPP) that override the default domain policy for specific groups (e.g. a stricter policy for admin accounts). A fully complete script would check for an applicable fine-grained policy per user with Get-ADUserResultantPasswordPolicy before falling back to the domain default — this project uses the domain default for clarity, with a coding challenge below extending it to handle fine-grained policies.

5. PasswordNeverExpires — An Important Exclusion

Accounts flagged with PasswordNeverExpires = $true (common for certain service accounts) have no meaningful expiry date at all — including them in a countdown report would either produce a nonsensical calculation or need special-case handling; cleanest to simply exclude them from this specific report.

6. Threshold Classification — Reused One More Time

Same Warning/Critical shape as Projects 2, 20, and 28 — here tuned to a much shorter timeframe (days, not weeks/months), since a password expiry is something a user needs to act on personally and soon.

Full Script — Get-PasswordExpiryReport.ps1

# =====================================================================
# Get-PasswordExpiryReport.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Proactively report on upcoming AD password expirations
# =====================================================================

Import-Module ActiveDirectory -ErrorAction Stop

$WarningDays  = 14                                              # Notify users starting 2 weeks out
$CriticalDays = 3                                                 # Urgent - expires within days

Write-Host "`n=== PASSWORD EXPIRATION REPORT ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Get the domain's password policy - the piece AD doesn't store per-user
# ---------------------------------------------------------------
$PasswordPolicy = Get-ADDefaultDomainPasswordPolicy
$MaxPasswordAge = $PasswordPolicy.MaxPasswordAge                 # A TimeSpan object

Write-Host "Domain max password age: $($MaxPasswordAge.Days) days`n" -ForegroundColor Cyan

# ---------------------------------------------------------------
# STEP 2: Get all enabled users with the properties we need
# ---------------------------------------------------------------
$Users = Get-ADUser -Filter { Enabled -eq $true } -Properties PasswordLastSet, PasswordNeverExpires |
    Where-Object { -not $_.PasswordNeverExpires -and $_.PasswordLastSet }   # Excludes never-expiring AND never-set accounts

$Results = @()

foreach ($User in $Users) {                                       # Loops through every eligible user

    $ExpiryDate = $User.PasswordLastSet + $MaxPasswordAge            # DateTime + TimeSpan = the actual expiry date
    $DaysUntilExpiry = ($ExpiryDate - (Get-Date)).Days                 # Positive = still valid, negative = already expired

    # ---------------------------------------------------------------
    # STEP 3: Classify (Project 2/20/28's threshold pattern)
    # ---------------------------------------------------------------
    $Status = if ($DaysUntilExpiry -lt 0) { "EXPIRED" }
              elseif ($DaysUntilExpiry -le $CriticalDays) { "CRITICAL" }
              elseif ($DaysUntilExpiry -le $WarningDays) { "WARNING" }
              else { "HEALTHY" }

    if ($Status -ne "HEALTHY") {                                    # Only records accounts that actually need attention
        $Results += [PSCustomObject]@{
            SamAccountName   = $User.SamAccountName
            Name             = $User.Name
            PasswordLastSet  = $User.PasswordLastSet
            ExpiryDate       = $ExpiryDate
            DaysUntilExpiry  = $DaysUntilExpiry
            Status           = $Status
        }
    }
}

# ---------------------------------------------------------------
# STEP 4: Display, sorted most urgent first
# ---------------------------------------------------------------
$Results = $Results | Sort-Object DaysUntilExpiry                  # Ascending - most urgent (or already expired) first

foreach ($Result in $Results) {
    $Color = switch ($Result.Status) {
        "EXPIRED"  { "Red" }
        "CRITICAL" { "Red" }
        "WARNING"  { "Yellow" }
    }
    Write-Host "  [$($Result.Status)] $($Result.SamAccountName) - expires $($Result.ExpiryDate.ToShortDateString()) ($($Result.DaysUntilExpiry) days)" -ForegroundColor $Color
}

# ---------------------------------------------------------------
# STEP 5: Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\PasswordExpiry_$Timestamp.csv" -NoTypeInformation

Write-Host "`nSummary: $($Results.Count) account(s) need attention (expired, critical, or warning)." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

$MaxPasswordAge = $PasswordPolicy.MaxPasswordAge

  • This property comes back as a real TimeSpan object (same .NET type from Project 1's uptime and Project 11's scheduling work) — ready to use directly in date arithmetic, no conversion needed.

Get-ADUser -Filter { Enabled -eq $true } -Properties PasswordLastSet, PasswordNeverExpires

  • -Properties — by default, Get-ADUser returns only a small set of common properties for performance reasons; anything else (like PasswordLastSet) must be explicitly requested, similar in spirit to how Select-Object shapes output, but here controlling what's actually retrieved from AD in the first place.

Where-Object { -not $_.PasswordNeverExpires -and $_.PasswordLastSet }

  • Two conditions combined with -and: exclude accounts explicitly set to never expire, AND exclude accounts with no recorded PasswordLastSet at all (extremely rare, but would break the date math that follows) — defensive filtering before any calculation is attempted.

$ExpiryDate = $User.PasswordLastSet + $MaxPasswordAge

  • The core calculation of the entire project: DateTime plus TimeSpan equals a new DateTime — this single line is what makes "proactive" possible, computing a real future date instead of just reporting how long ago the password was last changed.

if ($Status -ne "HEALTHY") { $Results += ... }

  • Unlike some earlier audits that recorded every item checked (Projects 4, 15), this report deliberately only keeps accounts needing attention — for a report specifically meant to drive action ("who needs to change their password soon"), including hundreds of healthy accounts would bury the actionable ones in noise. The right level of completeness depends on the report's actual purpose.

Architecture & Calculation Flow

Get-ADDefaultDomainPasswordPolicy
→
MaxPasswordAge (TimeSpan)
Get-ADUser (eligible users)
→
PasswordLastSet + MaxPasswordAge
→
ExpiryDate
→
Classify + Report

The key architectural insight is that policy (fetched once) and per-user data (fetched for everyone) are two separate pieces combined per-user in the loop — fetching the policy once outside the loop, rather than repeatedly inside it, is both more efficient and reflects that the policy is domain-wide, not something that varies per user in this simplified version.

Production Incident Walkthrough

This report, run weekly, catches a VP's account showing CRITICAL — 2 days until password expiry, during a week they're traveling internationally with limited IT support access. Because the report surfaced this in advance rather than the VP discovering it via a lockout while abroad, IT proactively reaches out with password-change guidance before it becomes an urgent, hard-to-resolve problem while traveling.
  • Why does the CRITICAL threshold matter separately from WARNING here? Two days notice is meaningfully different from two weeks notice in terms of what someone can realistically do about it — sorting the most urgent cases to the top (and giving them their own distinct, more alarming status) helps whoever's reviewing the report triage their limited time effectively.

Security & Best Practices

Best practice reinforced hereFetching the password policy once, outside the per-user loop, rather than re-querying it for every user, is a small performance detail that matters more as the user count grows — the same "fetch what's shared once, loop over what's per-item" thinking from Project 9's config-driven health check.
Still read-onlyThis script only reads and reports — it never resets or changes any password itself, appropriately leaving that action to the account owner or a formal password-reset process.

Interview Preparation

Q1. Why can't you just read a password's expiry date directly from an AD user object?

Answer: AD stores PasswordLastSet (when it was changed) per user, but the expiry rule (MaxPasswordAge) lives in the domain's password policy, separately. Expiry date has to be calculated by combining the two — there's no single stored property that already represents it for the simple case.

Follow-up: "What additional complexity exists in organizations using Fine-Grained Password Policies?" — Answer: different groups of users can have different MaxPasswordAge values via FGPP, overriding the domain default — a fully accurate script needs to check for an applicable fine-grained policy per user before falling back to the domain default, rather than assuming one policy applies to everyone.

Q2. Why exclude PasswordNeverExpires accounts from this report instead of just showing them with a very large days-until-expiry number?

Answer: That number wouldn't be meaningful or accurate — those accounts don't have a real expiry date at all under the current policy, so including them (even with a placeholder large number) could be misleading rather than informative. Cleanly excluding them keeps the report focused on what it's actually meant to answer.

Follow-up: "Should PasswordNeverExpires accounts be flagged in some OTHER report instead?" — Answer: yes, quite plausibly — an excessive number of PasswordNeverExpires accounts (especially on non-service accounts) is itself a security finding worth its own separate audit, distinct from this expiry countdown.

Q3. Why does this report only include accounts needing attention, while some earlier audits (like Project 4's service check) recorded every item examined?

Answer: The right level of completeness depends on the report's purpose — Project 4's audit needed to prove every service was actually checked, for coverage confidence. This report is meant to drive action (who should change their password soon), so including hundreds of healthy accounts would bury the few that actually need attention rather than adding useful confidence.

Follow-up: "How would you satisfy both needs at once, if you wanted both an action list and a full coverage record?" — Answer: export two separate outputs — a filtered "needs attention" list (like this script produces) and a separate complete audit log recording that every eligible user was checked, similar to how earlier projects separated console alerts from full CSV exports.
