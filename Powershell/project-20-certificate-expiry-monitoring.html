Concepts First — Before We Touch Code

1. Why Certificates Need Different Thresholds Than Disk Space

Different problem, different time scaleDisk space can fill up in hours; certificate renewal is a slower process that often involves a certificate authority, approval steps, and deployment scheduling. Certificate expiry thresholds are typically measured in weeks (Warning: 30-60 days) rather than the tighter percentages used for disk space — the threshold should match how much lead time the underlying fix actually needs.

2. Reusing the Exact Classification Pattern from Project 2

function Get-CertStatus {
    param([int]$DaysRemaining, [int]$WarnDays, [int]$CritDays)
    if ($DaysRemaining -lt $CritDays) { return "CRITICAL" }
    elseif ($DaysRemaining -lt $WarnDays) { return "WARNING" }
    else { return "HEALTHY" }
}

This is structurally identical to Project 2's Get-DiskStatus function — same shape, same logic, different unit (days instead of percent). Recognizing this kind of reusable shape is exactly what makes you faster at building new monitoring scripts over time.

3. Handling Already-Expired Certificates as a Fourth State

A case Project 2 didn't need to handleDisk space can't go negative, but a certificate's days-remaining absolutely can — an already-expired certificate needs its own distinct, most-severe status, checked before CRITICAL, not lumped in with it.

4. Filtering Down to What Actually Matters

Root CA certificates (from Project 19) often have decades of validity remaining — including them in an "urgent attention" report would be noise. This monitoring layer should focus specifically on certificates that actually have a private key (meaning they're deployable and in active use).

Full Script — Watch-CertificateExpiry.ps1

# =====================================================================
# Watch-CertificateExpiry.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Classify certificates by expiry urgency (Warning/Critical thresholds)
# =====================================================================

$WarningDays  = 60                                             # Below this many days remaining = WARNING
$CriticalDays = 30                                              # Below this many days remaining = CRITICAL

# ---------------------------------------------------------------
# FUNCTION: Classify a certificate's status (Project 2's Get-DiskStatus pattern, reused)
# ---------------------------------------------------------------
function Get-CertStatus {
    param(
        [int]$DaysRemaining,
        [int]$WarnLevel,
        [int]$CritLevel
    )
    if ($DaysRemaining -lt 0) { return "EXPIRED" }               # New fourth state - Project 2 never needed this
    elseif ($DaysRemaining -lt $CritLevel) { return "CRITICAL" }
    elseif ($DaysRemaining -lt $WarnLevel) { return "WARNING" }
    else { return "HEALTHY" }
}

Write-Host "`n=== CERTIFICATE EXPIRY MONITOR ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Gather certificates - only from My, and only ones with private keys (Project 19's HasPrivateKey filter)
# ---------------------------------------------------------------
$Certificates = Get-ChildItem -Path "Cert:\LocalMachine\My" -ErrorAction SilentlyContinue |
    Where-Object { $_.HasPrivateKey }                              # Only actively deployable certificates matter for this monitor

$Results = @()

foreach ($Cert in $Certificates) {                                # Loops through each deployable certificate

    $DaysRemaining = ($Cert.NotAfter - (Get-Date)).Days              # Same calculation from Project 19
    $Status = Get-CertStatus -DaysRemaining $DaysRemaining -WarnLevel $WarningDays -CritLevel $CriticalDays

    $Results += [PSCustomObject]@{
        Subject        = $Cert.Subject
        Thumbprint     = $Cert.Thumbprint
        NotAfter       = $Cert.NotAfter
        DaysRemaining  = $DaysRemaining
        Status         = $Status
    }
}

# ---------------------------------------------------------------
# STEP 2: Color-coded console output, sorted most urgent first
# ---------------------------------------------------------------
$Results = $Results | Sort-Object DaysRemaining                   # Most urgent (soonest/most negative) first

foreach ($Result in $Results) {
    $Color = switch ($Result.Status) {                              # Project 3's status-to-color switch, reused
        "EXPIRED"  { "Red" }
        "CRITICAL" { "Red" }
        "WARNING"  { "Yellow" }
        default     { "Green" }
    }
    Write-Host "  [$($Result.Status)] $($Result.Subject) - $($Result.DaysRemaining) days" -ForegroundColor $Color
}

# ---------------------------------------------------------------
# STEP 3: Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\CertExpiry_$Timestamp.csv" -NoTypeInformation

$NeedsAttention = ($Results | Where-Object { $_.Status -in @("EXPIRED","CRITICAL","WARNING") }).Count
Write-Host "`nSummary: $NeedsAttention of $($Results.Count) deployable certificate(s) need attention." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

if ($DaysRemaining -lt 0) { return "EXPIRED" }

  • Checked first, before CRITICAL — an expired certificate is a different, more severe category than "about to expire soon," and deserves its own label so a report reader immediately understands the difference between "act now" and "this already broke."

Where-Object { $_.HasPrivateKey }

  • Filters out certificates without a private key before any classification happens — reusing Project 19's discovery to focus this monitor's attention only on certificates that could actually be causing a real outage if they expire, rather than every certificate that happens to be present.

$Results = $Results | Sort-Object DaysRemaining

  • Ascending sort (Project 19's pattern), so the most urgent — including already-negative, expired entries — appear first, both in the console and implicitly in the exported CSV.

Production Incident Walkthrough

This script, run weekly, catches a certificate at 45 days remaining — WARNING status. Operations has plenty of time to request renewal through the normal certificate authority process. Compare this to the original incident that started this whole mini-track: an expiry nobody caught until the outage itself. The difference is entirely due to having a threshold-based check running proactively instead of discovering problems reactively.
  • Why is 60/30 days a reasonable starting threshold, rather than something tighter like Project 2's percentages? Certificate renewal has a real lead time — requesting, approving, and deploying a new certificate isn't an instant fix the way restarting a service is, so the warning threshold needs enough runway for that whole process to happen calmly rather than urgently.

Common Mistakes to Avoid

  • Using disk-space-style tight thresholds for something with a much longer real-world fix time.
  • Lumping EXPIRED in with CRITICAL instead of treating it as more severe.
  • Monitoring every certificate in the store instead of just the deployable ones.

Interview Preparation

Q1. Why are certificate expiry thresholds typically set in weeks/months rather than the tighter percentages used for disk space?

Answer: The underlying fix (certificate renewal) has a real process and lead time — requesting, approving, and deploying a new certificate — so the threshold needs to give enough runway for that process, unlike disk space where the fix (freeing space or expanding a volume) can often happen almost immediately.

Follow-up: "How might thresholds differ between an internal tool's certificate and a customer-facing one?" — Answer: a customer-facing certificate likely warrants longer lead time / earlier warning thresholds, given the higher visibility and business impact of it expiring compared to an internal-only tool.

Q2. Why check for EXPIRED as a separate condition before CRITICAL, rather than just treating a very negative number as CRITICAL too?

Answer: "About to expire" and "already expired" represent meaningfully different situations for whoever's responding — one is a warning to act soon, the other means something may already be broken right now. Distinguishing them in the report avoids underselling the urgency of an already-failed certificate.

Follow-up: "Would you ever want EXPIRED certificates to trigger an entirely different response than CRITICAL ones?" — Answer: yes, quite plausibly — EXPIRED might warrant immediate paging/escalation while CRITICAL (still valid but soon expiring) might only need a next-business-day ticket.

Q3. Why filter to HasPrivateKey certificates before applying expiry classification, rather than after?

Answer: Filtering first means classification logic only runs on certificates that could actually matter operationally, keeping the report focused — classifying everything and filtering afterward would work too, but doing the irrelevant work first is simply wasteful and risks accidentally leaving noise in if the later filter step is ever forgotten.

Follow-up: "Is there a case where you'd want to monitor expiry on certificates WITHOUT a private key too?" — Answer: trusted root/intermediate CA certificates do eventually expire and matter for validating other certificates — a separate, longer-horizon monitor for those could be a reasonable addition, just not mixed into this deployable-certificate-focused one.
