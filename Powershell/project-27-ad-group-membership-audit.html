Quick Recap of Projects 1–26

Project 26 created accounts. This project asks a different, equally important question: who has access to what, and is that access still correct? Specifically for privileged groups (like Domain Admins), where unauthorized membership is one of the most serious security findings an auditor can report. Same detection-only discipline as Project 15's NTFS audit, now applied to AD group membership.

The Story — Why We're Building This

A routine security review asks a simple-sounding question that turns out to be surprisingly hard to answer manually: "Exactly who currently has Domain Admin rights, and is everyone on that list still supposed to be there?" Two people who left contractor engagements months ago are still listed as members, added temporarily during a project and never removed. Our manager wants a script that audits privileged group membership against an approved list, and flags anyone who shouldn't be there — accounting for the fact that someone might have access through nested group membership, not just direct membership.

Concepts First — Before We Touch Code

1. Get-ADGroupMember — Direct Membership

Get-ADGroupMember -Identity "Domain Admins"

Lists everyone (and every group) directly added as a member of the specified group.

2. The Nested Group Problem

Why "direct membership" alone isn't enoughIf "Domain Admins" contains another group called "IT-Escalation-Team" as a member, then everyone in "IT-Escalation-Team" effectively has Domain Admin rights too — even though Get-ADGroupMember -Identity "Domain Admins" alone would only show "IT-Escalation-Team" as one entry, not each individual person inside it. A thorough privileged-access audit must account for this nesting, or it will significantly undercount who actually has access.
Get-ADGroupMember -Identity "Domain Admins" -Recursive
  • -Recursive — expands nested groups automatically, returning every individual user with effective membership, however many levels of group nesting deep that access actually comes from.

3. Get-ADPrincipalGroupMembership — The Reverse Direction

Get-ADPrincipalGroupMembership -Identity "jdoe"

Answers the opposite question: given a specific person, what groups do they belong to? Useful when investigating one individual's access rather than auditing a group's full membership.

4. Config-Driven Approved Membership Lists

Same pattern as every audit since Project 14: the list of who's supposed to be in a privileged group lives in configuration, not hardcoded — Operations/Security can update the approved list without touching script code.

5. Detection-Only — Reusing Project 15's Core Lesson

Group membership changes carry the same risk as NTFS permissions Automatically removing someone from Domain Admins based on a script's determination could break something genuinely needed and not yet reflected in the approved list — exactly the same reasoning from Project 15. This script reports discrepancies for human review; it never modifies group membership itself.

6. Why This Focuses on Privileged Groups Specifically

Auditing every group's membership in a large organization would be overwhelming and mostly low-value. Focusing specifically on high-privilege groups (Domain Admins, Enterprise Admins, and similarly sensitive custom groups) concentrates audit effort where the risk of unauthorized access is highest.

Full Script — Test-PrivilegedGroupMembership.ps1

# =====================================================================
# Test-PrivilegedGroupMembership.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Audit privileged AD group membership against an approved list (read-only)
# =====================================================================

Import-Module ActiveDirectory -ErrorAction Stop
$ApprovedConfig = Import-Csv -Path ".\config\approved-privileged-members.csv"

Write-Host "`n=== PRIVILEGED GROUP MEMBERSHIP AUDIT (READ-ONLY) ===" -ForegroundColor Magenta

$Findings = @()

foreach ($GroupConfig in $ApprovedConfig) {                          # $GroupConfig is one row - one group to audit

    $GroupName = $GroupConfig.GroupName
    $ApprovedList = $GroupConfig.ApprovedMembers -split ";"            # Splits "Administrator;jdoe" into an array (Project 9's technique)

    Write-Host "`nAuditing '$GroupName'..." -ForegroundColor Cyan

    # ---------------------------------------------------------------
    # STEP 1: Get EFFECTIVE membership, including nested groups
    # ---------------------------------------------------------------
    $ActualMembers = Get-ADGroupMember -Identity $GroupName -Recursive -ErrorAction SilentlyContinue |
        Where-Object { $_.objectClass -eq "user" }                      # -Recursive can still return group objects in some edge cases; keep only actual users

    Write-Host "  Found $($ActualMembers.Count) effective user member(s) (including nested group membership)." -ForegroundColor Cyan

    # ---------------------------------------------------------------
    # STEP 2: Compare actual vs approved
    # ---------------------------------------------------------------
    foreach ($Member in $ActualMembers) {                                # Loops through every effective member found

        $IsApproved = $Member.SamAccountName -in $ApprovedList             # Project 4's -in operator, reused

        $Findings += [PSCustomObject]@{
            GroupName      = $GroupName
            SamAccountName = $Member.SamAccountName
            Name           = $Member.Name
            Approved       = $IsApproved
        }

        if (-not $IsApproved) {
            Write-Host "  UNAPPROVED: $($Member.SamAccountName) ($($Member.Name)) has access to '$GroupName' but is not on the approved list" -ForegroundColor Red
        }
    }

    # ---------------------------------------------------------------
    # STEP 3: Also flag approved members who are NO LONGER actually members (list may be stale)
    # ---------------------------------------------------------------
    $ActualSamAccounts = $ActualMembers.SamAccountName
    foreach ($ApprovedName in $ApprovedList) {
        if ($ApprovedName -notin $ActualSamAccounts) {                     # Project 14's -notin operator, reused
            Write-Host "  NOTE: '$ApprovedName' is approved but not currently a member of '$GroupName' (list may need updating)" -ForegroundColor DarkYellow
        }
    }
}

# ---------------------------------------------------------------
# Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Findings | Export-Csv -Path ".\reports\GroupAudit_$Timestamp.csv" -NoTypeInformation

$UnapprovedCount = ($Findings | Where-Object { -not $_.Approved }).Count
Write-Host "`nSummary: $UnapprovedCount unapproved membership(s) found across $($ApprovedConfig.Count) privileged group(s)." -ForegroundColor Cyan
Write-Host "REMINDER: No group memberships were changed. Review and remediate manually." -ForegroundColor Yellow

Line-by-Line Explanation

Get-ADGroupMember -Identity $GroupName -Recursive | Where-Object { $_.objectClass -eq "user" }

  • -Recursive — this is the single most important line in the whole script; without it, a nested group's members would be invisible to this audit, exactly the gap that let the two departed contractors from our story go unnoticed.
  • Where-Object { $_.objectClass -eq "user" } — a defensive filter ensuring we only count real user accounts. In practice -Recursive should already resolve down to individual users, but explicitly filtering makes that assumption visible and safe rather than silently trusted.

$IsApproved = $Member.SamAccountName -in $ApprovedList

  • Same SamAccountName-based comparison from Project 26 — the reliable, unique identifier, used consistently across both AD projects for the same reason.

The second loop checking for stale approved entries

  • This is a genuinely useful, easy-to-overlook addition: an audit that only flags "unapproved people who ARE members" misses the equally important "approved people who are NO LONGER members" case — the approved list itself might be stale in either direction, and a thorough audit checks both.

Production Incident Walkthrough

Running this audit surfaces exactly the scenario from our story: two SamAccountNames appear in the "effective members" list for Domain Admins but aren't on the approved list. Digging further using Get-ADPrincipalGroupMembership confirms both gained access through a nested "Contractor-Escalation" group added to Domain Admins eight months ago and never cleaned up — invisible to anyone who'd only ever checked direct membership.
  • Why would a manual review checking Get-ADGroupMember without -Recursive have missed this? Without -Recursive, "Contractor-Escalation" would appear as a single group entry in Domain Admins' member list — technically visible, but easy to overlook or dismiss as "just another group," without realizing it grants effective access to everyone inside it.

Security & Best Practices

The core lesson of this project, againLike Project 15's NTFS audit, this script deliberately never modifies group membership — removing someone from a privileged group is a decision requiring human judgment and often a formal change process, not something a script should decide unilaterally, however confident its detection logic is.
Best practice reinforced hereAlways use -Recursive when auditing privileged group membership — a non-recursive check can significantly understate who actually has effective access, exactly as this project's incident demonstrated.

  • Two-directional audit comparison (unapproved-present AND approved-absent)
  • Focusing audit effort on high-privilege groups specifically
  • Detection-only for group membership, same as NTFS permissions

Common Mistakes to Avoid

  • Auditing group membership without -Recursive and missing nested access.
  • Only checking for unapproved additions, ignoring a stale approved list.
  • Automatically removing "unapproved" members without human review.

Interview Preparation

Q1. Why is -Recursive critical when auditing privileged group membership specifically?

Answer: Groups can be nested inside other groups — without -Recursive, a person gaining access through an intermediate nested group would be completely invisible to the audit, even though they have full effective privileged access. For high-risk groups like Domain Admins, that blind spot is exactly the kind of gap a real security review needs to catch.

Follow-up: "How deep can group nesting go, and does that create any performance concerns?" — Answer: AD technically allows multiple levels of nesting; -Recursive handles this automatically, though very deep or complex nesting structures can make membership harder to reason about for humans, which is itself often flagged as a governance concern separate from the technical audit.

Q2. Why does this audit check for approved members who are NO LONGER actual members, not just unapproved additions?

Answer: An approved list can go stale in either direction — someone might be added without approval (the more obviously dangerous case), but someone might also leave a group legitimately without the approved list being updated, silently making the reference list inaccurate for future audits. Checking both directions keeps the approved list itself trustworthy.

Follow-up: "Which of the two directions is more urgent to act on?" — Answer: unapproved-but-present is almost always the more urgent security finding; approved-but-absent is more of a housekeeping/documentation issue, though both are worth tracking.

Q3. Why focus this audit specifically on privileged groups rather than auditing every group in the domain?

Answer: Auditing every group would produce an overwhelming volume of low-value findings for most organizations — concentrating on high-privilege groups (Domain Admins, Enterprise Admins, and similarly sensitive custom groups) focuses limited audit and review effort where unauthorized access actually poses the greatest risk.

Follow-up: "How would you decide which OTHER groups deserve this same level of scrutiny?" — Answer: groups that grant access to sensitive systems or data (like a "Finance-Reporting-Admins" group) deserve similar treatment — the config-driven design of this script makes it trivial to extend the audit to additional groups just by adding rows to the CSV, no code changes needed.
