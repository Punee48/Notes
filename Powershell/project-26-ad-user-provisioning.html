Quick Recap of Projects 1–25

We now have a full toolkit: config-driven automation (Project 9), idempotency and ShouldProcess (Projects 10, 13, 21), and structured logging. This project applies all of it to a new target — Active Directory user accounts — provisioning new hires from a CSV, safely and without duplicating anyone who already exists.

The Story — Why We're Building This

ABC Bank's HR team sends a spreadsheet of new hires to IT every week. Currently, someone manually creates each Active Directory account by hand — a slow, error-prone process during busy onboarding weeks, and one where a typo'd username or a skipped account has caused real first-day problems for new employees. Our manager wants a script that reads a CSV of new hires and provisions their AD accounts automatically, safely skipping anyone who (intentionally or by CSV error) already has an account.

Concepts First — Before We Touch Code

Local Practice Lab vs EnterpriseActive Directory cmdlets require the ActiveDirectory PowerShell module (part of RSAT - Remote Server Administration Tools) and a real domain to connect to — there's no meaningful way to practice AD user creation on a standalone laptop. If you want fully hands-on practice: install RSAT's AD tools (Add-WindowsCapability -Online -Name Rsat.ActiveDirectory.DS-LDS.Tools~~~~0.0.1.0), and either use an existing test/lab domain if your organization has one, or build a small lab domain controller in a VM (a common, well-documented setup: a Windows Server evaluation VM with the AD DS role installed, promoted to a new forest). If that's not practical right now, read through this project closely — the exact same script would run unmodified against a real domain once you have access to one.

1. The ActiveDirectory Module

Import-Module ActiveDirectory
Get-ADUser -Filter *   # Lists every user in the domain

Like WebAdministration (Project 22), this module must be explicitly imported before its cmdlets and the AD: drive become available.

2. Idempotency by SamAccountName

$Existing = Get-ADUser -Filter "SamAccountName -eq '$Username'" -ErrorAction SilentlyContinue
Why SamAccountName specificallyA person's display name might not be unique (two "John Smith"s aren't impossible at a large bank), but SamAccountName (the login name, like jsmith) is guaranteed unique across the domain — exactly the same "use the truly unique identifier" lesson from Project 21's Thumbprint-based checks, applied here to people instead of certificates.

3. New-ADUser and Its Key Parameters

ParameterPurpose
-NameThe full display name
-SamAccountNameThe unique login name
-UserPrincipalNameThe login name in email format (user@domain.com)
-PathWhich Organizational Unit (OU) to create the account in
-AccountPasswordA SecureString initial password
-EnabledWhether the account is active immediately
-ChangePasswordAtLogonForces the new hire to set their own password on first login

4. Never Hardcode a Real Initial Password

Building on every prior security noteJust like Project 21's PFX password, an initial AD account password must never be typed as plain text in a script. We'll generate a random temporary password and immediately force a change at first logon — nobody, including the script's author, should ever know a real user's actual working password.

5. Organizational Units (OUs) — Where an Account Lives

AD organizes accounts into a hierarchy of OUs (e.g. OU=Employees,OU=Banking,DC=abcbank,DC=internal) — specifying the correct -Path ensures new accounts land in the right place for whatever Group Policy and permission structures apply to that OU.

6. CSV-Driven Bulk Provisioning — Reusing Project 9's Pattern

Same shape as Project 9's server list: read structured rows from a CSV, loop through them, act on each — just with new-hire details instead of server names.

Full Script — New-AdUserFromCsv.ps1

# =====================================================================
# New-AdUserFromCsv.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Idempotently provision AD user accounts from a CSV of new hires
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]
param(
    [switch]$WhatIf = $true
)

Import-Module ActiveDirectory -ErrorAction Stop
$NewHires = Import-Csv -Path ".\config\new-hires.csv"

$LogPath = ".\logs\Provisioning.log"
function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

Write-Host "`n=== AD USER PROVISIONING ===" -ForegroundColor Magenta
$Results = @()

foreach ($Hire in $NewHires) {                                    # $Hire is one row from new-hires.csv

    Write-Host "`nProcessing $($Hire.FirstName) $($Hire.LastName) ($($Hire.Username))..." -ForegroundColor Cyan

    # ---------------------------------------------------------------
    # STEP 1: Idempotency check by SamAccountName - the unique identifier
    # ---------------------------------------------------------------
    $Existing = Get-ADUser -Filter "SamAccountName -eq '$($Hire.Username)'" -ErrorAction SilentlyContinue

    if ($Existing) {
        Write-Host "  Account already exists - skipping." -ForegroundColor Yellow
        Write-Log -Status "INFO" -Message "$($Hire.Username) already exists - no action taken"
        $Results += [PSCustomObject]@{ Username = $Hire.Username; Action = "SKIPPED (already exists)" }
        continue                                                     # Moves to the next hire without attempting creation
    }

    # ---------------------------------------------------------------
    # STEP 2: Generate a random temporary password - never hardcoded
    # ---------------------------------------------------------------
    $TempPasswordPlain = -join ((65..90) + (97..122) + (48..57) | Get-Random -Count 16 | ForEach-Object { [char]$_ })
    $SecurePassword = ConvertTo-SecureString -String $TempPasswordPlain -AsPlainText -Force   # Immediately converted, never logged or displayed

    # ---------------------------------------------------------------
    # STEP 3: Create the account, respecting -WhatIf
    # ---------------------------------------------------------------
    if ($PSCmdlet.ShouldProcess($Hire.Username, "Create AD User Account")) {

        try {
            New-ADUser `
                -Name "$($Hire.FirstName) $($Hire.LastName)" `
                -GivenName $Hire.FirstName `
                -Surname $Hire.LastName `
                -SamAccountName $Hire.Username `
                -UserPrincipalName "$($Hire.Username)@abcbank.internal" `
                -Path $Hire.OuPath `
                -AccountPassword $SecurePassword `
                -Enabled $true `
                -ChangePasswordAtLogon $true `                        # Forces the new hire to set their own real password
                -Department $Hire.Department `
                -ErrorAction Stop

            Write-Log -Status "SUCCESS" -Message "Created account for $($Hire.Username) in $($Hire.OuPath)"
            Write-Host "  Account created." -ForegroundColor Green
            $Results += [PSCustomObject]@{ Username = $Hire.Username; Action = "CREATED" }
        }
        catch {
            Write-Log -Status "ERROR" -Message "Failed to create $($Hire.Username): $($_.Exception.Message)"
            Write-Host "  FAILED: $($_.Exception.Message)" -ForegroundColor Red
            $Results += [PSCustomObject]@{ Username = $Hire.Username; Action = "FAILED" }
        }
    }
    else {
        Write-Host "  PREVIEW: Would create account for $($Hire.Username)" -ForegroundColor Yellow
        $Results += [PSCustomObject]@{ Username = $Hire.Username; Action = "PREVIEWED (WhatIf)" }
    }
}

# ---------------------------------------------------------------
# Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\Provisioning_$Timestamp.csv" -NoTypeInformation

Write-Host "`nAudit log: $LogPath" -ForegroundColor Cyan
Write-Host "REMINDER: Temporary passwords were never logged or displayed - each new hire must change their password at first logon." -ForegroundColor Yellow

Line-by-Line Explanation

$Existing = Get-ADUser -Filter "SamAccountName -eq '$($Hire.Username)'" -ErrorAction SilentlyContinue

  • Unlike Get-ADUser -Identity (which throws if the account doesn't exist), -Filter simply returns nothing if no match is found — combined with -ErrorAction SilentlyContinue, this gives us a clean $null/not-$null check without needing try/catch for what's an entirely normal, expected first-run scenario.

$TempPasswordPlain = -join ((65..90) + (97..122) + (48..57) | Get-Random -Count 16 | ForEach-Object { [char]$_ })

  • (65..90) + (97..122) + (48..57) — three ranges of ASCII character codes (uppercase letters, lowercase letters, digits), combined into one array using + on arrays (which concatenates them, rather than adding numbers, since both sides are arrays here).
  • Get-Random -Count 16 — picks 16 random values from that combined pool, without repeats being guaranteed excluded but with genuine randomness per character.
  • [char]$_ — converts each numeric ASCII code back into its actual character.
  • -join — the join operator, here used with no explicit separator (defaulting to none), combining the array of individual characters into one continuous password string.

$SecurePassword = ConvertTo-SecureString -String $TempPasswordPlain -AsPlainText -Force

  • The plaintext password exists in memory only briefly, purely to be immediately converted — it's never written to the log, never displayed with Write-Host, and the variable holding it isn't included in anything exported to CSV. Compare this to the explicit warning in the original course requirements: this line alone doesn't "make it safe" — the discipline of never displaying or persisting $TempPasswordPlain anywhere else in the script is what actually matters.

-ChangePasswordAtLogon $true

  • This is the real safety mechanism for the temporary password: since the new hire is forced to set their own password immediately, the random one we generated only ever needs to work for a single first login — nobody needs to know or communicate it securely afterward.

continue after logging a SKIPPED result

  • Reused from Project 15's Challenge 2 — immediately moves to the next CSV row once we know this one needs no action, keeping the rest of the loop's creation logic from running unnecessarily.

Production Incident Walkthrough

HR accidentally sends the same new-hires CSV twice in one week due to a scheduling mix-up. Because the script checks SamAccountName before creating anything, the second run correctly identifies every account from the first run as already existing and skips them cleanly — no duplicate accounts, no errors, no manual cleanup needed, and the audit log clearly shows both runs and exactly what each one did.
  • Why does idempotency matter especially for user provisioning, more than say a one-off certificate task? Provisioning scripts often run on a recurring schedule against a data source (HR's export) that isn't fully under IT's control — the same person's data might appear in more than one export by mistake, and the script needs to handle that gracefully rather than assuming every run starts from a clean slate.

Security & Best Practices

The core lesson of this projectA temporary password that's randomly generated, immediately converted to SecureString, never displayed or logged, and paired with a mandatory first-logon change is the correct pattern for any script that needs to set an initial credential — contrast this with the explicitly banned $Password = "MyPassword123" pattern warned against since the very beginning of this course.
Best practice reinforced hereChecking SamAccountName (the guaranteed-unique identifier) rather than a person's name for idempotency avoids an entire class of mistakes, the same principle as Project 21's Thumbprint-based certificate checks.

Common Mistakes to Avoid

  • Checking for an existing account by display name instead of SamAccountName.
  • Hardcoding, logging, or displaying a real temporary password anywhere.
  • Forgetting -ChangePasswordAtLogon, leaving a script-generated password as someone's permanent one.

Interview Preparation

Q1. Why check for an existing account using SamAccountName rather than the person's full name?

Answer: Full names aren't guaranteed unique across an organization, while SamAccountName is enforced unique by Active Directory itself — checking against the truly unique identifier avoids both false positives (two different "John Smith"s treated as the same person) and false negatives (missing a genuine duplicate because of a formatting difference in how the name was typed).

Follow-up: "What would you do if two new hires in the same CSV batch would generate the same SamAccountName?" — Answer: the script should detect that collision before attempting creation and flag it for manual resolution (e.g. a numbered suffix), rather than letting AD's own uniqueness constraint cause an unhandled error mid-batch.

Q2. Why generate a random temporary password instead of using a company-standard default password for new accounts?

Answer: A shared or predictable default password is a well-known security weakness — anyone who knows the pattern could access any newly-provisioned account before the real user logs in for the first time. A unique random password combined with a mandatory change at first logon eliminates that window of vulnerability.

Follow-up: "How would the new hire actually receive this temporary password if it's never displayed or logged?" — Answer: in a real implementation, it would typically be communicated through a separate secure channel (e.g. directly to the hiring manager or IT helpdesk via an established secure process) — this script intentionally does not solve that distribution problem, since doing so safely is a distinct concern from account creation itself.

Q3. This script's structure is very similar to Project 14's firewall rule provisioning. Why?

Answer: Both are "read desired state from config, check if it already exists, create only what's missing" workflows — the same underlying pattern applies regardless of whether the resource being managed is a firewall rule or an AD user account. Recognizing this recurring shape is what lets you approach a new kind of provisioning task quickly, rather than starting from scratch each time.

Follow-up: "What's genuinely different about provisioning people versus provisioning infrastructure?" — Answer: the security stakes around credentials (this project's password handling) and the downstream human impact of getting it wrong (a new hire unable to work on day one) — the core automation pattern is similar, but the safety considerations around identity data are meaningfully higher.
