CPU and Memory Monitoring with Sampling

A single snapshot lies. Learn why real monitoring samples CPU and memory over time, and build a script that does it properly using loops.

Quick Recap of Projects 1–2

We now know how to pull OS/hardware/disk data with Get-CimInstance, wrap results in [PSCustomObject], classify status with if/elseif/else inside a function, and export to CSV. This project adds a new dimension: data that changes from second to second, which a single snapshot can't represent honestly.

The Story — Why We're Building This

A ticket lands on our desk: WINAPP12 is "randomly slow" during the day, but every time the Operations team checks Task Manager, everything looks fine. Our manager explains the problem: "CPU and memory usage spikes for a few seconds and then drops. A single check at 2:00 PM tells you nothing about what happened at 1:47 PM. We need a script that samples usage over a window of time and reports the pattern, not just one instant."

Today we build a CPU and memory monitor that takes multiple samples over time, using our first real loop.

Concepts First — Before We Touch Code

1. Why a Single Reading Is Misleading

The core problemCPU usage in particular can swing from 5% to 95% within a second. A monitoring script that checks once and moves on can easily catch the calm moment and miss the spike entirely — exactly what happened to Operations checking Task Manager manually.

2. The for Loop

A for loop repeats a block of code a known, fixed number of times — perfect for "take exactly 5 samples."

for ($i = 1; $i -le 5; $i++) {   # Repeats the block for i = 1,2,3,4,5
    Write-Host "Sample $i"        # Runs once per loop iteration
}
  • $i = 1 — the initializer: runs once, before the loop starts, setting up a counter variable.
  • $i -le 5 — the condition: checked before every iteration; the loop continues only while this is true.
  • $i++ — the incrementer: runs after every iteration; ++ is shorthand for "add 1 to this variable".

3. Start-Sleep

Start-Sleep -Seconds 2 pauses script execution for the given duration. We use it between samples so our readings are spread out over real time, instead of firing instantly one after another.

4. Growing an Array with +=

$Samples += $NewValue appends a new item to an existing array. We'll use this to build up a list of readings across our sampling loop.

Performance noteBehind the scenes, PowerShell arrays have a fixed size — += actually creates a brand-new array each time and copies everything over. For a handful of samples like ours, this is completely fine. For thousands of items, a growable [System.Collections.Generic.List[object]] is more efficient — worth knowing, not worth worrying about yet.

5. Measure-Object for Aggregation

Measure-Object -Average -Maximum -Minimum calculates statistics across a collection of numbers — exactly what we need to summarize multiple CPU samples into one meaningful average and peak.

6. The switch Statement — A Cleaner Alternative to if/elseif/else

switch ($true) {                      # Evaluates each condition below against $true
    ($AvgCpu -ge 90) { "CRITICAL" }    # First matching condition wins
    ($AvgCpu -ge 70) { "WARNING" }
    default           { "HEALTHY" }    # Runs if nothing above matched
}
  • switch ($true) — an idiom: instead of switching on a single value, we switch on $true and list boolean expressions as the cases, so whichever expression evaluates to $true first is the one that runs. This reads almost like an if/elseif chain but is often considered cleaner for many-branch logic.
  • default — the fallback case, equivalent to else.
if/elseif vs switchBoth are valid; switch tends to read better with many branches (4+), while if/elseif (from Project 2) is often clearer for 2–3 branches. We're using switch here specifically so you're comfortable with both by the time we reach more complex projects.

7. CPU Load via CIM

Get-CimInstance Win32_Processor exposes a LoadPercentage property — a live snapshot of current CPU utilization, ready to sample repeatedly.

Full Script — Get-CpuMemoryMonitor.ps1

# =====================================================================
# Get-CpuMemoryMonitor.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Sample CPU and memory usage over time instead of a single snapshot
# =====================================================================

$ComputerName   = $env:COMPUTERNAME     # The server being monitored
$SampleCount    = 5                     # How many samples to take
$SampleInterval = 3                     # Seconds to wait between samples
$CpuWarnLevel   = 70                    # CPU% average considered a warning
$CpuCritLevel   = 90                    # CPU% average considered critical

$CpuSamples = @()                        # Empty array that will hold each CPU reading
$MemSamples = @()                        # Empty array that will hold each memory reading

Write-Host "`n=== CPU & MEMORY MONITOR: $ComputerName ===" -ForegroundColor Magenta   # Section header
Write-Host "Taking $SampleCount samples, $SampleInterval seconds apart...`n" -ForegroundColor Cyan

# ---------------------------------------------------------------
# STEP 1: Sampling loop - take multiple readings over time
# ---------------------------------------------------------------
for ($i = 1; $i -le $SampleCount; $i++) {          # Repeats once per sample, i goes 1 to SampleCount

    $CpuInfo = Get-CimInstance -ClassName Win32_Processor          # Queries current CPU state
    $CpuLoad = ($CpuInfo | Measure-Object -Property LoadPercentage -Average).Average   # Averages across logical processors if more than one

    $OSInfo = Get-CimInstance -ClassName Win32_OperatingSystem      # Queries current memory state
    $TotalMemKB = $OSInfo.TotalVisibleMemorySize                     # Total memory in KB
    $FreeMemKB  = $OSInfo.FreePhysicalMemory                          # Free memory in KB
    $UsedMemPercent = [math]::Round((($TotalMemKB - $FreeMemKB) / $TotalMemKB) * 100, 1)   # % of memory currently used

    $CpuSamples += $CpuLoad            # Appends this sample's CPU reading to the array
    $MemSamples += $UsedMemPercent     # Appends this sample's memory reading to the array

    Write-Host ("Sample {0}/{1}  CPU: {2}%   Memory: {3}%" -f $i, $SampleCount, $CpuLoad, $UsedMemPercent)  # Shows this sample

    if ($i -lt $SampleCount) {          # Don't sleep after the very last sample - no point waiting
        Start-Sleep -Seconds $SampleInterval   # Pauses before taking the next sample
    }
}

# ---------------------------------------------------------------
# STEP 2: Aggregate the samples into meaningful statistics
# ---------------------------------------------------------------
$CpuStats = $CpuSamples | Measure-Object -Average -Maximum -Minimum   # Calculates avg/max/min across all CPU samples
$MemStats = $MemSamples | Measure-Object -Average -Maximum -Minimum   # Calculates avg/max/min across all memory samples

$AvgCpu = [math]::Round($CpuStats.Average, 1)   # Rounds the average CPU for display
$MaxCpu = [math]::Round($CpuStats.Maximum, 1)   # Rounds the peak CPU seen during sampling

# ---------------------------------------------------------------
# STEP 3: Classify overall CPU status using a switch statement
# ---------------------------------------------------------------
$CpuStatus = switch ($true) {                    # Evaluates each case against $true; first match wins
    ($AvgCpu -ge $CpuCritLevel) { "CRITICAL" }   # Average CPU at/above critical threshold
    ($AvgCpu -ge $CpuWarnLevel) { "WARNING"  }   # Average CPU at/above warning threshold
    default                      { "HEALTHY"  }   # Neither condition matched
}

# ---------------------------------------------------------------
# STEP 4: Build the final summary object
# ---------------------------------------------------------------
$Summary = [PSCustomObject]@{
    ServerName   = $ComputerName                              # Which server this summary is for
    SampleCount  = $SampleCount                                # How many samples were taken
    AvgCpuPct    = $AvgCpu                                      # Average CPU usage across all samples
    MaxCpuPct    = $MaxCpu                                      # Peak CPU usage seen
    AvgMemPct    = [math]::Round($MemStats.Average, 1)         # Average memory usage across all samples
    MaxMemPct    = [math]::Round($MemStats.Maximum, 1)         # Peak memory usage seen
    CpuStatus    = $CpuStatus                                   # HEALTHY / WARNING / CRITICAL
    CheckedAt    = Get-Date -Format "yyyy-MM-dd HH:mm:ss"      # When this check completed
}

# ---------------------------------------------------------------
# STEP 5: Display the summary, color-coded by status
# ---------------------------------------------------------------
Write-Host "`n=== SUMMARY ===" -ForegroundColor Magenta   # Section header
$Summary | Format-List                                     # Prints every property on its own line

$Color = switch ($CpuStatus) {                # A second switch, this time on an actual value instead of $true
    "CRITICAL" { "Red" }                       # Maps each status string to a console color
    "WARNING"  { "Yellow" }
    default     { "Green" }
}
Write-Host "Overall CPU Status: $CpuStatus" -ForegroundColor $Color   # Final status line in the matching color

# ---------------------------------------------------------------
# STEP 6: Export to CSV
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) {                          # Creates the reports folder if it doesn't exist yet
    New-Item -ItemType Directory -Path ".\reports" | Out-Null
}
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"               # Sortable timestamp for the filename
$Summary | Export-Csv -Path ".\reports\CpuMem_$Timestamp.csv" -NoTypeInformation   # Saves the summary row

Write-Host "`nReport saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

for ($i = 1; $i -le $SampleCount; $i++) { ... }

  • Already covered the mechanics above — here $SampleCount is a variable instead of a hardcoded number, so changing one setting at the top of the script changes how many times the loop runs.

($CpuInfo | Measure-Object -Property LoadPercentage -Average).Average

  • -Property LoadPercentage — tells Measure-Object which property on each object to do math on (a machine can report one Win32_Processor object per physical socket, so this averages them if there's more than one).
  • -Average — a switch parameter requesting the average be calculated.
  • The surrounding parentheses run the whole pipeline first, then .Average pulls just that one number out of the result object Measure-Object returns.

$CpuSamples += $CpuLoad

  • += — "append this value to the existing array and store the result back in the same variable." Combines addition and assignment in one operator, same idea as increment shorthand but for arrays.

if ($i -lt $SampleCount) { Start-Sleep -Seconds $SampleInterval }

  • This check prevents an unnecessary final sleep after the last sample — a small but real detail that keeps the script from wasting time once there's nothing left to sample.

$CpuStatus = switch ($true) { (...) {"CRITICAL"} (...) {"WARNING"} default {"HEALTHY"} }

  • Just like an if statement can produce a value, a switch statement's matched result can be assigned directly to a variable — $CpuStatus receives whichever branch's output matched first.

$Color = switch ($CpuStatus) { "CRITICAL" {"Red"} "WARNING" {"Yellow"} default {"Green"} }

  • This is the more traditional form of switch: it compares $CpuStatus directly against each literal case value ("CRITICAL", "WARNING") rather than evaluating boolean expressions — useful to see both styles side by side in the same script.

Architecture & Sampling Flow

for loop (5x)
→
Get-CimInstance (CPU + Memory)
→
Append to Sample Arrays
→
Start-Sleep
→
(repeat)
Sample Arrays
→
Measure-Object (Avg/Max/Min)
→
switch Classification
→
Console + CSV

Notice the two-phase shape: an inner loop that collects over time, followed by an aggregation step that summarizes after the fact. This pattern reappears constantly in monitoring automation — collect first, judge second.

Production Incident Walkthrough

Suppose our 5 samples come back as: 12%, 15%, 94%, 18%, 14%. A single check at almost any other moment would have completely missed the 94% spike that's actually causing WINAPP12's slowness.
  • Why report both Average and Maximum? Average (30.6% here) looks healthy and would hide the problem; Maximum (94%) reveals the spike Operations actually needs to investigate. Reporting only one number would mislead in one direction or the other.
  • Why not just increase SampleCount to something huge, like 1000? More samples mean more accuracy, but also a much longer-running script and more resource usage from the monitoring itself. In later projects we'll discuss scheduled, shorter recurring checks instead of one giant sampling window.

Interview Preparation

Q1. Why does this script report both average and maximum CPU instead of just one number?

Answer: Average can mask short spikes that are actually causing performance problems; maximum reveals the peak. Reporting both gives a fuller picture than either alone.

Follow-up: "What statistic would you add to catch a CPU that's consistently high, not just spiky?" — Answer: Minimum — if the minimum sample is also high, that points to sustained load rather than a brief spike.

Q2. When would you choose a for loop over a foreach loop?

Answer: for fits when you know how many iterations you need up front and need a counter (like taking exactly 5 timed samples); foreach fits when you're iterating over an existing collection of items rather than counting repetitions.

Follow-up: "Could you rewrite this sampling loop using while instead of for?" — Answer: yes, with a counter variable incremented manually inside the loop and the condition checked at the top — functionally equivalent, just different syntax emphasis.

Q3. What's the practical difference between the two switch statements used in this script?

Answer: switch ($true) evaluates boolean expressions per case (good for range/threshold logic); switch ($CpuStatus) matches a variable directly against literal case values (good for simple value-to-value mapping, like status-to-color).

Follow-up: "Could a hash table replace the second switch?" — Answer: yes — @{"CRITICAL"="Red";"WARNING"="Yellow"}["HEALTHY"]-style lookups work too and can be more compact for pure value mapping with no ranges involved.
