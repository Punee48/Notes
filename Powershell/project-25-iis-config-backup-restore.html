The Story — Why We're Building This

Before every IIS change — a new site deployment, a certificate rebind, an app pool setting tweak — our manager wants an automatic configuration backup taken first, just in case. And when something does go wrong, Operations needs a fast, reliable way to restore the last known-good configuration rather than manually reconstructing settings from memory. "I want backups to just happen automatically before we touch anything risky, and I want restore to be safe enough that I'm not more worried about the restore itself breaking something."

Concepts First — Before We Touch Code

1. Backup-WebConfiguration and Restore-WebConfiguration

Backup-WebConfiguration -Name "PrePatch_20260817_143000"
Restore-WebConfiguration -Name "PrePatch_20260817_143000"
  • Backup-WebConfiguration — creates a complete, named snapshot of IIS's entire configuration (all sites, app pools, and settings), stored by Windows itself under %windir%\System32\inetsrv\backup.
  • Restore-WebConfiguration — replaces the entire current IIS configuration with a named backup — a big, all-or-nothing operation, not a selective undo of just one recent change.
Restore is total, not selectiveRestoring a backup replaces all current IIS configuration with the backup's state — any sites or changes made after that backup was taken are gone, not just the one thing that went wrong. This is a meaningfully different (and more consequential) kind of operation than most of the targeted, single-resource changes earlier in this course.

2. Listing Available Backups

Get-WebConfigurationBackup

Returns every named backup currently stored, with its creation time — the natural first step before any restore, since you need to know exactly what's available and when it was taken.

3. Naming Backups Meaningfully

A timestamped, purpose-labeled name (like PreDeployment_20260817_143000) is far more useful during an actual incident than a generic name — the same "descriptive over convenient" principle behind good logging since Project 10.

4. Retention Cleanup — Reusing Project 6/12's Pattern

Backups accumulate over time just like the log files (Project 6) and HTML reports (Project 12) did before them — the same age-based cleanup pattern applies, just targeting Get-WebConfigurationBackup results instead of files on disk directly.

5. Why Restore Needs Extra Caution Beyond Just ShouldProcess

The most consequential action in this entire mini-track Given restore replaces the entire configuration, this script requires an explicit backup name to be passed — it will never guess, default to "the most recent," or restore automatically as part of any other workflow. A human must deliberately specify exactly which backup to restore, every single time.

Full Script — Manage-IisConfigBackup.ps1

# =====================================================================
# Manage-IisConfigBackup.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Backup, list, and (carefully) restore IIS configuration
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]
param(
    [switch]$WhatIf = $true,
    [ValidateSet("Backup", "List", "Restore")]                    # Restricts input to exactly these three values
    [string]$Action,
    [string]$Label,                                                  # Used for Backup
    [string]$BackupName,                                             # Used for Restore - REQUIRED, never guessed
    [int]$RetentionDays = 30
)

Import-Module WebAdministration -ErrorAction Stop
$LogPath = ".\logs\ConfigBackup.log"
function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

switch ($Action) {

    "Backup" {
        $Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
        $BackupLabel = if ($Label) { "$Label`_$Timestamp" } else { "Backup_$Timestamp" }   # Meaningful, timestamped name

        Write-Host "`n=== IIS CONFIG BACKUP: $BackupLabel ===" -ForegroundColor Magenta

        if ($PSCmdlet.ShouldProcess($BackupLabel, "Create IIS Configuration Backup")) {
            Backup-WebConfiguration -Name $BackupLabel
            Write-Log -Status "SUCCESS" -Message "Created backup: $BackupLabel"
            Write-Host "Backup created: $BackupLabel" -ForegroundColor Green
        }
        else {
            Write-Host "PREVIEW: Would create backup named $BackupLabel" -ForegroundColor Yellow
        }

        # --- Retention cleanup (Project 6/12's pattern, reused) ---
        $CutoffDate = (Get-Date).AddDays(-$RetentionDays)
        $OldBackups = Get-WebConfigurationBackup | Where-Object { $_.CreationDate -lt $CutoffDate }

        if ($OldBackups.Count -gt 0) {
            Write-Host "`nRemoving $($OldBackups.Count) backup(s) older than $RetentionDays days..." -ForegroundColor Yellow
            foreach ($Old in $OldBackups) {
                if ($PSCmdlet.ShouldProcess($Old.Name, "Remove Old Backup")) {
                    Remove-WebConfigurationBackup -Name $Old.Name
                    Write-Log -Status "INFO" -Message "Removed old backup: $($Old.Name)"
                }
            }
        }
    }

    "List" {
        Write-Host "`n=== AVAILABLE IIS CONFIG BACKUPS ===" -ForegroundColor Magenta
        Get-WebConfigurationBackup | Sort-Object CreationDate -Descending |
            Format-Table Name, CreationDate -AutoSize
    }

    "Restore" {
        if (-not $BackupName) {                                       # Restore NEVER proceeds without an explicit name
            Write-Host "ERROR: -BackupName is required for Restore. This script will never guess or default." -ForegroundColor Red
            Write-Log -Status "ERROR" -Message "Restore attempted without -BackupName - refused"
            return                                                       # Exits the script entirely - no restore path without this
        }

        $TargetBackup = Get-WebConfigurationBackup | Where-Object { $_.Name -eq $BackupName }
        if (-not $TargetBackup) {
            Write-Host "ERROR: Backup '$BackupName' not found. Run -Action List to see available backups." -ForegroundColor Red
            Write-Log -Status "ERROR" -Message "Restore attempted for non-existent backup: $BackupName"
            return
        }

        Write-Host "`n=== RESTORE WARNING ===" -ForegroundColor Red
        Write-Host "Restoring '$BackupName' (created $($TargetBackup.CreationDate)) will REPLACE the ENTIRE current" -ForegroundColor Yellow
        Write-Host "IIS configuration, including any sites or changes made after that backup was taken.`n" -ForegroundColor Yellow

        if ($PSCmdlet.ShouldProcess($BackupName, "RESTORE IIS Configuration (replaces ALL current config)")) {
            Write-Log -Status "WARNING" -Message "RESTORING configuration from backup: $BackupName - replaces entire current config"
            Restore-WebConfiguration -Name $BackupName
            Write-Log -Status "SUCCESS" -Message "Restore completed from backup: $BackupName"
            Write-Host "Restore completed." -ForegroundColor Green
        }
        else {
            Write-Host "PREVIEW: Would restore from '$BackupName', replacing all current IIS configuration." -ForegroundColor Yellow
        }
    }
}

Line-by-Line Explanation

[ValidateSet("Backup", "List", "Restore")] [string]$Action

  • [ValidateSet(...)] — a parameter validation attribute restricting the allowed values to exactly this list; passing anything else causes PowerShell itself to reject the call with a clear error, before any of the script's own logic even runs — a cleaner alternative to manually checking if ($Action -notin @(...)) partway through the script.

if (-not $BackupName) { ... return } inside the Restore case

  • This is the single most important safety line in the whole script: there is no default, no "most recent" fallback, no way to trigger a restore without explicitly typing the exact backup name. The return here exits the entire script immediately, guaranteeing no restore logic below it can possibly run without this condition being satisfied first.

switch ($Action) { "Backup" { ... } "List" { ... } "Restore" { ... } }

  • A traditional value-matching switch (the second form from Project 3), here used to route the script into one of three completely different workflows based on a single parameter — a clean way to build a multi-purpose script without three separate files.

Get-WebConfigurationBackup | Where-Object { $_.CreationDate -lt $CutoffDate }

  • Structurally identical to Project 6's file-age filtering and Project 12's report-retention logic — just pointed at Get-WebConfigurationBackup's results instead of Get-ChildItem's, another example of one well-understood pattern transferring directly to a new data source.

Notice how many independent gates stand between "someone runs this script with -Action Restore" and an actual restore happening: a required parameter with no default, an existence check against real available backups, an explicit on-screen warning describing the consequences, and finally the standard ShouldProcess preview/confirm mechanism. For an action this consequential, that's a deliberate, appropriate amount of friction — restore should never feel like something that could happen by accident.

Production Incident Walkthrough

A junior engineer, following an incident runbook under pressure, runs this script with -Action Restore but forgets to specify -BackupName. Instead of guessing, defaulting to "most recent," or silently doing nothing, the script immediately and clearly refuses, explaining exactly what's missing and pointing to -Action List to find the right name — turning a potential "restored the wrong backup during a stressful incident" mistake into a simple, immediately obvious, and easily corrected error message.
  • Why is refusing loudly better than silently picking a sensible-seeming default here? During an actual incident, someone under pressure benefits far more from an immediate, clear "you're missing required information" than from the script guessing what they probably meant — a wrong guess executed confidently is much more dangerous than an obvious refusal that prompts the person to slow down and specify exactly what they intend.

Security & Best Practices

The core lesson of this projectNot every safety mechanism needs to be exotic — sometimes the most effective protection is simply refusing to proceed without an explicit, unambiguous, required input, with no convenient default that could be triggered accidentally. This is a pattern worth carrying forward to any script capable of a similarly consequential, broad-impact action.
Best practice reinforced hereDescriptive, timestamped backup names aren't just nice-to-have — during an actual incident, being able to immediately tell backups apart by name (rather than needing to cross-reference creation dates manually) meaningfully speeds up recovery.

Interview Preparation

Q1. Why does this script refuse to run a restore without an explicit -BackupName, rather than defaulting to the most recent backup?

Answer: Restoring is a total replacement of IIS configuration — defaulting to "most recent" could restore the wrong point in time if someone forgot the parameter during a stressful incident, silently undoing more recent legitimate changes. Requiring explicit specification forces a deliberate decision every time, which is appropriate given how consequential the action is.

Follow-up: "Isn't requiring an explicit parameter every time less convenient?" — Answer: yes, deliberately so — the added friction is the point; for an action this broad and irreversible, a small amount of required deliberateness is a reasonable tradeoff against the risk of an accidental or mistaken restore.

Q2. What's the key difference between this project's "restore" and, say, Project 21's certificate removal, in terms of blast radius?

Answer: Project 21's removal was scoped to one specific, independently-reverified certificate. This project's restore replaces the entire IIS configuration at once — every site, pool, and setting — making its potential blast radius far larger and its consequences much harder to reason about in advance, which is why it warrants even more caution than a single-resource operation.

Follow-up: "How might you reduce that blast radius if partial/selective restore were a real requirement?" — Answer: Restore-WebConfiguration doesn't support partial restores natively, so achieving that would likely mean manually comparing the backup's exported config against current config and selectively reapplying only specific settings — a much more involved, custom process than the built-in cmdlet provides.

Q3. Why use [ValidateSet] for the -Action parameter instead of checking valid values manually inside the script?

Answer: [ValidateSet] rejects an invalid value immediately, before any of the script's logic runs at all, and PowerShell itself generates a clear, standard error message — this is more reliable and less code than manually checking if ($Action -notin @(...)) somewhere in the body, where it's possible to accidentally place the check after code that shouldn't run for an invalid value.

Follow-up: "What other parameter validation attributes might be useful elsewhere in this course's scripts?" — Answer: [ValidateRange] for numeric bounds (like a retry count or day threshold), [ValidateNotNullOrEmpty] for required strings, and [ValidateScript] for fully custom validation logic — all enforce correctness before a script's real logic runs, rather than after.
