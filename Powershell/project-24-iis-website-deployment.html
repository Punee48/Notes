Quick Recap of Projects 1–23

We've bound certificates to existing sites (Project 22) and recovered application pools (Project 23). This project goes one step further back in the lifecycle: creating a brand-new site from scratch — its own application pool, the site itself, folder structure, and HTTPS binding — all from one config file, following Project 9's config-driven philosophy applied to a full deployment instead of a health check.

The Story — Why We're Building This

ABC Bank is launching a new internal reporting portal. Historically, standing up a new IIS site meant a checklist: create the folder, create an app pool, create the site, set the binding, attach a certificate — five manual steps, each a chance for a typo or a skipped step. Our manager wants one script that reads a simple deployment config and performs all five steps consistently, idempotently, every time — whether it's this new portal or the next dozen sites after it.

Concepts First — Before We Touch Code

1. The Five Steps of Standing Up a Site

Each step depends on the one before it — you can't bind a site that doesn't exist yet, and a site needs an app pool to run in. This ordering isn't arbitrary; it reflects real dependencies, and our script's structure follows it directly.

2. New-WebAppPool and New-Website

New-WebAppPool -Name "ReportingPortalPool"
New-Website -Name "ReportingPortal" -PhysicalPath "C:\inetpub\ReportingPortal" -ApplicationPool "ReportingPortalPool" -Port 8443 -Ssl
  • New-WebAppPool — creates a new, empty application pool with default settings.
  • New-Website — creates the site itself, immediately associating it with the app pool and setting up an initial binding in one call.

3. Idempotency Across FIVE Different Resource Types

More moving parts than any project so farUnlike Project 10's single service or Project 21's single certificate type, this script must independently check "does this already exist" for a folder, an app pool, a site, AND a binding — each with its own existence-check cmdlet. Getting any one of these wrong could mean either an error on a re-run, or worse, a duplicate/conflicting resource.

4. Combining Everything Learned in This Mini-Track

This project deliberately doesn't introduce much brand-new syntax — it's primarily an exercise in composition: taking Project 9's config-driven approach, Project 22's binding+certificate logic, and Project 23's WebAdministration familiarity, and combining them into one coherent deployment workflow.

5. Why Order of Operations Matters for ShouldProcess Previews

With five dependent steps, a -WhatIf preview needs to clearly show what would happen at each step, including steps that depend on an earlier step's (previewed, not real) outcome — worth being thoughtful about how preview output reads when steps build on each other.

Full Script — Deploy-IisWebsite.ps1

# =====================================================================
# Deploy-IisWebsite.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: End-to-end, idempotent IIS site deployment from config
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]
param(
    [switch]$WhatIf = $true
)

Import-Module WebAdministration -ErrorAction Stop
$Config = Import-PowerShellDataFile -Path ".\config\site-deployment.psd1"   # Project 9's config pattern, reused

$LogPath = ".\logs\Deployment.log"
function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

Write-Host "`n=== DEPLOYING SITE: $($Config.SiteName) ===" -ForegroundColor Magenta

# ---------------------------------------------------------------
# STEP 1: Physical folder
# ---------------------------------------------------------------
if (-not (Test-Path $Config.PhysicalPath)) {
    if ($PSCmdlet.ShouldProcess($Config.PhysicalPath, "Create Folder")) {
        New-Item -ItemType Directory -Path $Config.PhysicalPath -Force | Out-Null
        Write-Log -Status "INFO" -Message "Created folder $($Config.PhysicalPath)"
        Write-Host "[1/5] Folder created." -ForegroundColor Green
    }
    else { Write-Host "[1/5] PREVIEW: Would create folder $($Config.PhysicalPath)" -ForegroundColor Yellow }
}
else { Write-Host "[1/5] Folder already exists." -ForegroundColor Green }

# ---------------------------------------------------------------
# STEP 2: Application pool
# ---------------------------------------------------------------
if (-not (Test-Path "IIS:\AppPools\$($Config.AppPoolName)")) {
    if ($PSCmdlet.ShouldProcess($Config.AppPoolName, "Create Application Pool")) {
        New-WebAppPool -Name $Config.AppPoolName | Out-Null
        Write-Log -Status "INFO" -Message "Created app pool $($Config.AppPoolName)"
        Write-Host "[2/5] Application pool created." -ForegroundColor Green
    }
    else { Write-Host "[2/5] PREVIEW: Would create app pool $($Config.AppPoolName)" -ForegroundColor Yellow }
}
else { Write-Host "[2/5] Application pool already exists." -ForegroundColor Green }

# ---------------------------------------------------------------
# STEP 3: The site itself
# ---------------------------------------------------------------
if (-not (Test-Path "IIS:\Sites\$($Config.SiteName)")) {
    if ($PSCmdlet.ShouldProcess($Config.SiteName, "Create Website")) {
        New-Website -Name $Config.SiteName `
                     -PhysicalPath $Config.PhysicalPath `
                     -ApplicationPool $Config.AppPoolName `
                     -Port $Config.Port -Ssl | Out-Null                # -Ssl marks the initial binding as HTTPS
        Write-Log -Status "INFO" -Message "Created site $($Config.SiteName) on port $($Config.Port)"
        Write-Host "[3/5] Site created." -ForegroundColor Green
    }
    else { Write-Host "[3/5] PREVIEW: Would create site $($Config.SiteName)" -ForegroundColor Yellow }
}
else { Write-Host "[3/5] Site already exists." -ForegroundColor Green }

# ---------------------------------------------------------------
# STEP 4 & 5: Certificate binding (Project 22's exact logic, reused)
# ---------------------------------------------------------------
$ExistingBinding = Get-WebBinding -Name $Config.SiteName -Protocol "https" -Port $Config.Port -ErrorAction SilentlyContinue
$CurrentThumbprint = if ($ExistingBinding.CertificateHash) { $ExistingBinding.CertificateHash } else { $null }

if ($CurrentThumbprint -eq $Config.CertThumbprint) {
    Write-Host "[4-5/5] Certificate already correctly bound." -ForegroundColor Green
    Write-Log -Status "INFO" -Message "Binding already correct - no change made"
}
else {
    if ($PSCmdlet.ShouldProcess("$($Config.SiteName):$($Config.Port)", "Bind Certificate")) {
        $BindingPath = "IIS:\SslBindings\0.0.0.0!$($Config.Port)"
        if (Test-Path $BindingPath) { Remove-Item -Path $BindingPath -Force }
        Get-Item "Cert:\LocalMachine\My\$($Config.CertThumbprint)" | New-Item -Path $BindingPath | Out-Null
        Write-Log -Status "SUCCESS" -Message "Bound certificate $($Config.CertThumbprint) to $($Config.SiteName):$($Config.Port)"
        Write-Host "[4-5/5] Certificate bound." -ForegroundColor Green
    }
    else { Write-Host "[4-5/5] PREVIEW: Would bind certificate $($Config.CertThumbprint)" -ForegroundColor Yellow }
}

Write-Host "`nDeployment sequence complete. Audit log: $LogPath" -ForegroundColor Cyan

Line-by-Line Explanation

if (-not (Test-Path "IIS:\AppPools\$($Config.AppPoolName)")) { ... }

  • Reusing Test-Path once again — this time against the IIS: drive's AppPools path — proving yet again that the provider model means the exact same existence-check idiom from files (Project 6) and the registry (Project 13) works unchanged here too.

New-Website -Name ... -Port $Config.Port -Ssl

  • -Ssl — tells New-Website to create its initial binding as HTTPS rather than the default HTTP, saving a separate New-WebBinding call for the common case of a site that should be HTTPS-only from the start.

Steps 4-5 being one combined block

  • Notice the certificate binding logic is copied nearly verbatim from Project 22 — this is intentional reuse (the same philosophy as Project 23's reuse of Project 10), not an accident. Once binding logic is proven correct, copying it into a new orchestration script is safer than rewriting a similar-but-different version from scratch.

Five independent if (-not (Test-Path ...)) blocks in sequence

  • Each step's idempotency check is completely self-contained — Step 3 doesn't need to know whether Step 2 actually ran a change or found an existing pool, it just needs the pool to exist by the time it runs. This loose coupling between steps means each one can be reasoned about independently, and a script re-run partway through a previous failure will correctly pick up wherever it left off.

Each arrow in the second row represents both a dependency (you need the thing on the left before the thing on the right makes sense) and an independent idempotency checkpoint. This "ordered chain of independently-safe steps" shape is exactly how real infrastructure-as-code and deployment automation tools are structured under the hood — you're building the same mental model those tools are built on, just with plain PowerShell.

Production Incident Walkthrough

Halfway through deploying the reporting portal on a real server, the script fails at Step 4 due to an unrelated, transient network hiccup reading the certificate store. Because each step independently checks "does this already exist" before acting, simply re-running the exact same script picks up right where it left off — the folder, app pool, and site (already created in Steps 1-3) are correctly detected as already present and skipped, and only the failed binding step actually runs again.
  • Why does idempotency matter even more here than in a single-resource script like Project 21? With five dependent steps, a partial failure is much more likely than with one action — without per-step idempotency, recovering from a partial failure would require manually figuring out exactly which steps already succeeded before re-running, which defeats much of the point of automating the deployment in the first place.

Troubleshooting Cheat Sheet

SymptomLikely Root CauseFix
Script fails at Step 3 (site creation)The port is already in use by another site's bindingChoose a different port in the config, or check existing bindings with Get-WebBinding across all sites
Site created but shows a 503 error when browsedThe app pool exists but isn't started, or the physical folder has no contentCheck app pool state (Project 23's technique) and confirm at least a placeholder index.html exists in the folder
Re-running the script still tries to recreate an existing resourceA Test-Path check is targeting the wrong IIS: path formatConfirm exact paths with Get-ChildItem "IIS:\Sites" / "IIS:\AppPools" to compare against what the script checks
Certificate binding step fails even though Steps 1-3 succeededWrong thumbprint in the config, or the certificate doesn't exist in LocalMachine\MyConfirm with Get-ChildItem "Cert:\LocalMachine\My" that the thumbprint in site-deployment.psd1 is exactly correct

Interview Preparation

Q1. Why does each of the five deployment steps have its own independent idempotency check, instead of one overall "has this deployment run before" flag?

Answer: A single overall flag can't handle partial failures correctly — if the script died after Step 2, an overall flag would either incorrectly skip everything on re-run (if set too early) or incorrectly redo everything including the already-successful steps (if not set until the end). Independent per-step checks mean the script always does exactly the remaining necessary work, regardless of where a previous run stopped.

Follow-up: "How does this relate to how tools like Terraform or Ansible work?" — Answer: those tools are built around exactly this idea at a much larger scale — they compare desired state against actual state for every resource independently and only change what's different, which is precisely what this project does by hand for five specific IIS resources.

Q2. Why is the certificate binding logic copied from Project 22 rather than rewritten for this script?

Answer: That logic was already carefully reasoned through — including the specific "clear-then-attach" sequence needed to avoid the silent-failure incident described in Project 22. Reusing it directly avoids reintroducing a bug that's already been solved once.

Follow-up: "What would you do differently if you were building this for a real production codebase rather than a learning project?" — Answer: extract the shared binding logic into its own reusable function (or eventually a module function, foreshadowing the Module Development stage), called from both Project 22's standalone script and this deployment script, rather than maintaining two separate copies of the same logic.

Q3. What real infrastructure risk does this script's ordering (folder → pool → site → binding → certificate) protect against?

Answer: Each step depends on the previous one succeeding — creating a site before its app pool exists, for example, either fails outright or silently falls back to a default pool that wasn't intended. Following the true dependency order prevents these kinds of partial, inconsistent deployments.

Follow-up: "Is there ever a reason to change this order?" — Answer: generally no for this specific set of resources, since the dependencies are fixed by how IIS itself works — but in deployments with more resource types, understanding true dependencies (rather than an arbitrary convenient order) is essential to getting a multi-step deployment right.
