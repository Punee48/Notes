Concepts First — Before We Touch Code

1. Detection vs Remediation — Why We Waited Until Now

Why Projects 2, 4, 5, and 7 stayed read-onlyEvery prior monitoring project deliberately stopped at reporting. Taking automated action requires more safety machinery — proper -WhatIf support, logging, idempotency, retry limits — which is exactly what this project adds. Never jump straight to automated remediation without those safety layers in place first.

2. Building Your Own -WhatIf/-Confirm Support: SupportsShouldProcess

Project 6 relied on Move-Item's built-in support for -WhatIf. Now we're writing our own function that performs a real action (Restart-Service) — to get proper -WhatIf/-Confirm support on our own function, we opt in explicitly:

function Repair-CriticalService {
    [CmdletBinding(SupportsShouldProcess)]     # Opts this function into -WhatIf/-Confirm support
    param([string]$ServiceName)

    if ($PSCmdlet.ShouldProcess($ServiceName, "Restart Service")) {   # Asks: "should this action actually happen?"
        Restart-Service -Name $ServiceName      # Only reached if ShouldProcess returned $true
    }
}
  • [CmdletBinding(SupportsShouldProcess)] — an attribute placed above param() that tells PowerShell "this function supports the standard risk-management switches." It automatically adds -WhatIf and -Confirm as available parameters — we don't declare them ourselves.
  • $PSCmdlet.ShouldProcess($Target, $Action) — the automatic variable $PSCmdlet becomes available once CmdletBinding is present. ShouldProcess checks whether -WhatIf or -Confirm was passed by the caller and handles the preview/prompt automatically — it returns $true only when the real action should actually run.
This is the real mechanism behind every built-in -WhatIf Every cmdlet that supports -WhatIf — Remove-Item, Stop-Service, Restart-Service — is built exactly this way internally. You're not learning a workaround; you're learning the actual pattern PowerShell itself uses.

3. Idempotency — Don't Fix What Isn't Broken

Recall from earlier projectsAn idempotent script checks current state before making a change, and does nothing if the desired state already exists. Here: if a service is already Running, restarting it anyway would cause an unnecessary (and potentially disruptive) interruption — we check first, and only act if actually needed.

4. Structured Logging

ABC Bank wants an audit trail — a format like Timestamp | Server | Operation | Status | Message appended to a log file, so every automated action taken is reviewable later, not just visible in a console window that closes when the script finishes.

function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2} | {3}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $env:COMPUTERNAME, $Status, $Message
    Add-Content -Path $LogPath -Value $Line   # Appends one line to the log file without overwriting existing content
}
  • Add-Content — appends text to a file, creating it if it doesn't exist yet, unlike Set-Content/Out-File (used in earlier projects) which overwrite the file's entire contents each time.

5. Retry Logic with a Hard Limit

A restarted service doesn't always come up instantly or successfully on the first try. We'll attempt up to a fixed number of retries, with a short pause between attempts, and give up (loudly, not silently) if it never recovers — an unlimited retry loop is a production hazard, not a safety feature.

Full Script — Repair-ServiceHealth.ps1

# =====================================================================
# Repair-ServiceHealth.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Detect and safely auto-recover critical services, with full audit logging
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]     # Makes the WHOLE SCRIPT support -WhatIf/-Confirm, not just a function
param(
    [switch]$WhatIf = $true                  # Safe by default, same philosophy as Project 6
)

$CriticalServices = @("Spooler", "BITS")   # The services we're responsible for keeping healthy
$LogPath          = ".\logs\ServiceRecovery.log"
$MaxRetries       = 3                        # Never retry forever
$RetryDelaySeconds = 5                        # Pause between retry attempts

# ---------------------------------------------------------------
# FUNCTION: Structured audit logging
# ---------------------------------------------------------------
function Write-Log {
    param(
        [string]$Message,                     # What happened
        [string]$Status = "INFO"                # INFO / SUCCESS / WARNING / ERROR
    )
    $Line = "{0} | {1} | {2} | {3}" -f `                                  # Builds one structured log line
                (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $env:COMPUTERNAME, $Status, $Message
    Add-Content -Path $LogPath -Value $Line     # Appends without overwriting previous entries
}

# ---------------------------------------------------------------
# FUNCTION: Idempotent, WhatIf-aware, retry-capable service recovery
# ---------------------------------------------------------------
function Repair-CriticalService {
    [CmdletBinding(SupportsShouldProcess)]      # This function ALSO supports -WhatIf/-Confirm independently
    param(
        [string]$ServiceName                      # Which service to check and, if needed, recover
    )

    try {
        $Service = Get-Service -Name $ServiceName -ErrorAction Stop   # Attempt to find the service

        # --- Idempotency check: is action even needed? ---
        if ($Service.Status -eq "Running") {          # Already healthy - nothing to do
            Write-Log -Status "INFO" -Message "$ServiceName already running - no action needed"
            return [PSCustomObject]@{ ServiceName = $ServiceName; Action = "NONE (already running)"; Success = $true }
        }

        # --- Action needed: attempt recovery, respecting -WhatIf ---
        if ($PSCmdlet.ShouldProcess($ServiceName, "Restart Service")) {   # Checks -WhatIf/-Confirm before acting

            $Attempt = 0                                 # Tracks how many attempts we've made
            $Recovered = $false                            # Tracks whether we succeeded

            while (-not $Recovered -and $Attempt -lt $MaxRetries) {   # Retry loop with a hard ceiling
                $Attempt++                                              # Counts this attempt
                Write-Log -Status "INFO" -Message "$ServiceName is $($Service.Status) - restart attempt $Attempt of $MaxRetries"

                try {
                    Start-Service -Name $ServiceName -ErrorAction Stop    # Attempts to start the service
                    Start-Sleep -Seconds 2                                  # Brief pause before checking status
                    $Service = Get-Service -Name $ServiceName               # Re-reads the current status
                    if ($Service.Status -eq "Running") {                     # Confirms it actually came up
                        $Recovered = $true
                    }
                }
                catch {
                    Write-Log -Status "WARNING" -Message "$ServiceName restart attempt $Attempt failed: $($_.Exception.Message)"
                }

                if (-not $Recovered -and $Attempt -lt $MaxRetries) {        # Only sleep if we're going to retry again
                    Start-Sleep -Seconds $RetryDelaySeconds
                }
            }

            if ($Recovered) {
                Write-Log -Status "SUCCESS" -Message "$ServiceName successfully recovered after $Attempt attempt(s)"
                return [PSCustomObject]@{ ServiceName = $ServiceName; Action = "RESTARTED"; Success = $true }
            }
            else {
                Write-Log -Status "ERROR" -Message "$ServiceName FAILED to recover after $MaxRetries attempt(s) - manual intervention required"
                return [PSCustomObject]@{ ServiceName = $ServiceName; Action = "RESTART FAILED"; Success = $false }
            }
        }
        else {
            # ShouldProcess returned $false - meaning -WhatIf was specified, so nothing actually happened
            return [PSCustomObject]@{ ServiceName = $ServiceName; Action = "PREVIEWED (WhatIf)"; Success = $null }
        }
    }
    catch {
        Write-Log -Status "ERROR" -Message "$ServiceName not found: $($_.Exception.Message)"
        return [PSCustomObject]@{ ServiceName = $ServiceName; Action = "NOT FOUND"; Success = $false }
    }
}

# ---------------------------------------------------------------
# MAIN: Check and repair every critical service
# ---------------------------------------------------------------
Write-Host "`n=== SERVICE RECOVERY: $env:COMPUTERNAME ===" -ForegroundColor Magenta
$Results = @()

foreach ($SvcName in $CriticalServices) {                     # Loops through our list of critical services
    Write-Host "`nChecking $SvcName..." -ForegroundColor Cyan
    $Result = Repair-CriticalService -ServiceName $SvcName -WhatIf:$WhatIf   # Passes WhatIf through explicitly
    $Results += $Result

    $Color = if ($Result.Success -eq $true) { "Green" } elseif ($Result.Success -eq $false) { "Red" } else { "Yellow" }
    Write-Host "  $($Result.Action)" -ForegroundColor $Color
}

# ---------------------------------------------------------------
# Export summary and finish
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\ServiceRecovery_$Timestamp.csv" -NoTypeInformation

Write-Host "`nFull audit log: $LogPath" -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

[CmdletBinding(SupportsShouldProcess)] at both script level and function level

  • Placing this at the very top of the script (before the script's own param()) makes -WhatIf a recognized parameter for the whole script, not just one function inside it. We also placed it on Repair-CriticalService so that function is independently well-behaved even if called from somewhere else later.

if ($Service.Status -eq "Running") { ... return ... }

  • This is the idempotency check happening before ShouldProcess is even called — if nothing needs to change, we don't ask "should I restart this?" at all, because the answer is "there's nothing to restart." Early return here keeps the function's logic simple by exiting before the rest of the recovery logic runs.

if ($PSCmdlet.ShouldProcess($ServiceName, "Restart Service")) { ... } else { ... }

  • When -WhatIf was passed, PowerShell automatically prints a "What if: Performing the operation Restart Service on target ServiceName" message and ShouldProcess returns $false — the else branch runs instead of the real recovery logic, which is exactly how Move-Item -WhatIf behaved back in Project 6, just implemented in code we wrote ourselves this time.

while (-not $Recovered -and $Attempt -lt $MaxRetries) { ... }

  • A while loop (new keyword, though conceptually related to Project 3's Challenge 2 rewrite) continues as long as its condition stays true. Here that means "keep trying until we've recovered, OR we've hit the retry ceiling" — both conditions matter, since either one becoming true should stop the loop.

return [PSCustomObject]@{ ServiceName = $ServiceName; Action = "NONE (already running)"; Success = $true }

  • Every exit path from this function — already healthy, successfully recovered, failed after retries, not found, or previewed — returns the same shape of object (ServiceName/Action/Success). This consistency is what makes it safe to collect every result into one $Results array and treat them uniformly afterward, regardless of which path was taken.

Success = $null (in the WhatIf preview branch)

  • Deliberately different from $true/$false — a preview didn't succeed or fail, it simply didn't happen. Using $null here lets later code (like the color-coding logic) distinguish "this was only previewed" from an actual pass/fail result.

Architecture & Safety Flow

Get-Service
→
Already Running?
→
Yes → Log + Exit (idempotent)
Not Running
→
ShouldProcess Check
→
-WhatIf? → Preview Only
Real Run
→
Retry Loop (max 3)
→
Recovered or Failed
→
Log + Report

Every layer in this flow exists to answer one safety question before acting: is action even needed (idempotency), is this actually supposed to happen right now (ShouldProcess), and how many times should we reasonably try before giving up and alerting a human (retry ceiling).

Production Incident Walkthrough

Three weeks after this script goes live, it silently and successfully recovers Spooler on WINAPP22 at 3 AM — nobody had to wake up, and the audit log shows exactly when it happened and how many attempts it took. Separately, on WINAPP31, the same service fails to recover after 3 attempts; the script logs an ERROR entry and exits without endlessly retrying, and Operations investigates a deeper issue during business hours instead of the automation looping forever in the background.
  • Why cap retries instead of trying indefinitely? A service that won't recover after 3 reasonable attempts likely has a real underlying problem (corrupt files, a dependency also down, a resource conflict) that blind retrying won't fix — an endless retry loop wastes resources and delays the human escalation that's actually needed.
  • Why is the audit log as important as the fix itself? In a banking environment, "something changed a production service automatically" must always be traceable — who/what did it, when, and why — both for troubleshooting and for compliance review.

Security & Best Practices

Least privilege still appliesRestarting services typically requires local administrator rights. In a real enterprise environment, this script would run under a dedicated service account with just enough delegated permission to manage the specific services it's responsible for (a preview of the JEA - Just Enough Administration - concept we'll cover formally in the Security stage), not a full admin account.
Best practice reinforced hereThe audit log captures every outcome — including "already healthy, did nothing" — not just failures or successful fixes. A complete audit trail proves what the automation checked, not only what it changed.

Common Mistakes to Avoid

  • Restarting a service that's already running, causing unnecessary disruption.
  • Writing a retry loop with no maximum attempt count.
  • Logging only failures, leaving no record of successful or no-action-needed checks.
  • Returning differently-shaped objects from different code paths, breaking downstream reporting.

Interview Preparation

Q1. What does SupportsShouldProcess actually add to a function, mechanically?

Answer: It adds automatic -WhatIf and -Confirm parameters and makes the $PSCmdlet.ShouldProcess() method available. Calling ShouldProcess checks whether those switches were used and handles the preview message or confirmation prompt automatically, returning a boolean the function then uses to decide whether to actually perform the action.

Follow-up: "What happens if you forget to check ShouldProcess's return value and just always run the action?" — Answer: -WhatIf would print the preview message but the destructive action would still execute anyway — the attribute alone doesn't enforce safety; the code must actually branch on the result.

Q2. Why check idempotency before calling ShouldProcess, rather than after?

Answer: If no action is needed, there's nothing meaningful to preview or confirm — asking "should I restart this?" when the service is already healthy would be misleading and would clutter -WhatIf output with no-op previews.

Follow-up: "Would the script behave differently if you checked ShouldProcess first?" — Answer: a -WhatIf run would show "What if: Restart Service" even for services that didn't need it at all, which misrepresents what a real run would actually do.

Q3. Why does the retry loop have both a success condition and an attempt-count condition?

Answer: Either condition alone is insufficient: checking only success could loop forever on a service that never recovers; checking only attempt count would keep retrying even after success, wasting time and potentially restarting an already-healthy service again.

Follow-up: "How would you add exponential backoff instead of a fixed delay between retries?" — Answer: multiply $RetryDelaySeconds by the attempt number (or by 2 each time) before each Start-Sleep call, so later retries wait progressively longer — useful when a service needs more time to stabilize with each attempt.
