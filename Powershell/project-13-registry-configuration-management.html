Quick Recap of Projects 1–12

We've built ShouldProcess-aware, idempotent remediation (Project 10), scheduled it (Project 11), and reported on it (Project 12). This project applies that exact same safety discipline to a new and much riskier target: the Windows Registry — a place where a wrong change can genuinely break a server, so the caution we've been building matters more here than almost anywhere else so far.

The Story — Why We're Building This

ABC Bank's security team has a new baseline requirement: a specific registry-based configuration setting must be present and correctly set on every server, as part of a compliance audit. Manually opening regedit on hundreds of servers isn't realistic, and nobody wants a script blindly overwriting registry values without knowing what was there before. Our manager wants a script that checks the current value first, only changes it if actually needed, records what the value was before changing it, and previews every change before making it.

Concepts First — Before We Touch Code

1. The Registry as a PowerShell Drive

A genuinely elegant designPowerShell exposes the registry as if it were a file system, using drives like HKLM: (HKEY_LOCAL_MACHINE) and HKCU: (HKEY_CURRENT_USER). This means commands you already know from working with files — Test-Path, Get-ChildItem, New-Item — work on the registry too, with registry keys behaving like folders and registry values behaving like file contents.
Registry HivePowerShell DriveContains
HKEY_LOCAL_MACHINEHKLM:Machine-wide settings, affecting all users
HKEY_CURRENT_USERHKCU:Settings for the currently logged-on user only

2. Reading Registry Values with Get-ItemProperty

Get-ItemProperty -Path "HKCU:\Software\ABCBankAutomation" -Name "LogLevel" -ErrorAction SilentlyContinue
  • -Path — the registry key (like a folder).
  • -Name — the specific value inside that key (like a file within the folder) we want to read.
Key vs Value — a common point of confusionA registry key is a container (like a folder); a value lives inside a key and has its own name, type, and data (like a file's content). "Set a registry key" is technically imprecise — you set a value inside a key. Being precise about this distinction avoids real mistakes.

3. Registry Value Types

TypePowerShell ParameterUsed For
String (REG_SZ)-PropertyType StringPlain text
DWord (REG_DWORD)-PropertyType DWord32-bit numbers — very common for on/off flags (0/1) and settings
Binary (REG_BINARY)-PropertyType BinaryRaw byte data
MultiString (REG_MULTI_SZ)-PropertyType MultiStringAn array of strings

4. Creating Keys and Setting Values Safely

if (-not (Test-Path $KeyPath)) {                          # Test-Path works on registry paths too
    New-Item -Path $KeyPath -Force | Out-Null                # Creates the key if it doesn't exist
}
New-ItemProperty -Path $KeyPath -Name "LogLevel" -Value 2 -PropertyType DWord -Force   # Creates or overwrites the value
  • New-ItemProperty ... -Force — creates the value if it doesn't exist yet, or overwrites it if it does; without -Force it would error on an already-existing value.

5. Backup Before Change

Why this matters more here than in prior projectsUnlike a stopped service (easy to just start again) or a moved log file (still sitting in an archive folder), an incorrectly changed registry value can be genuinely hard to undo if you didn't record what it was before. We capture the "before" value and log it as part of every change — cheap insurance against a mistake.

6. Idempotency, Applied to a Single Value

Same principle as every prior project: read the current value first, and only call New-ItemProperty/Set-ItemProperty if the current value is actually different from the desired one — an already-correct value needs no action, logged or otherwise.

Full Script — Set-RegistryConfig.ps1

# =====================================================================
# Set-RegistryConfig.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Safely validate and enforce a registry configuration value
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]      # Same pattern from Project 10 - enables -WhatIf/-Confirm
param(
    [switch]$WhatIf = $true                   # Safe by default
)

$KeyPath      = "HKCU:\Software\ABCBankAutomation"   # Sandboxed practice key - safe for any user to modify
$ValueName    = "LogLevel"
$DesiredValue = 2                                       # The value we want to enforce (e.g. 2 = "Verbose logging enabled")
$ValueType    = "DWord"
$LogPath      = ".\logs\RegistryChanges.log"

# ---------------------------------------------------------------
# FUNCTION: Structured audit logging (same pattern as Project 10)
# ---------------------------------------------------------------
function Write-Log {
    param([string]$Message, [string]$Status = "INFO")
    $Line = "{0} | {1} | {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Status, $Message
    Add-Content -Path $LogPath -Value $Line
}

Write-Host "`n=== REGISTRY CONFIGURATION CHECK ===" -ForegroundColor Magenta
Write-Host "Target: $KeyPath\$ValueName (desired: $DesiredValue)`n" -ForegroundColor Cyan

# ---------------------------------------------------------------
# STEP 1: Ensure the key itself exists before we try to read/write a value inside it
# ---------------------------------------------------------------
if (-not (Test-Path $KeyPath)) {                          # Test-Path works identically on registry paths
    Write-Host "Key does not exist yet." -ForegroundColor Yellow

    if ($PSCmdlet.ShouldProcess($KeyPath, "Create Registry Key")) {   # ShouldProcess check before creating
        New-Item -Path $KeyPath -Force | Out-Null
        Write-Log -Status "INFO" -Message "Created registry key $KeyPath"
        Write-Host "Key created." -ForegroundColor Green
    }
    else {
        Write-Host "PREVIEW: Would create key $KeyPath" -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 2: Read the CURRENT value, if any, before making any decision
# ---------------------------------------------------------------
$CurrentProperty = Get-ItemProperty -Path $KeyPath -Name $ValueName -ErrorAction SilentlyContinue   # $null if not set yet
$CurrentValue    = if ($CurrentProperty) { $CurrentProperty.$ValueName } else { $null }               # Extracts just the value, or $null

Write-Host "Current value: $(if ($null -eq $CurrentValue) {''} else {$CurrentValue})" -ForegroundColor Cyan

# ---------------------------------------------------------------
# STEP 3: Idempotency check - only act if the value is actually wrong or missing
# ---------------------------------------------------------------
if ($CurrentValue -eq $DesiredValue) {                     # Already correct - nothing to do
    Write-Host "Value already correct - no action needed." -ForegroundColor Green
    Write-Log -Status "INFO" -Message "$ValueName already set to $DesiredValue - no change made"
}
else {
    # -----------------------------------------------------------
    # STEP 4: Change needed - preview or apply, respecting -WhatIf
    # -----------------------------------------------------------
    if ($PSCmdlet.ShouldProcess("$KeyPath\$ValueName", "Set value to $DesiredValue")) {

        # Backup the "before" state into the log BEFORE changing anything
        Write-Log -Status "INFO" -Message "BEFORE CHANGE: $ValueName was '$CurrentValue' (target: $DesiredValue)"

        New-ItemProperty -Path $KeyPath -Name $ValueName -Value $DesiredValue -PropertyType $ValueType -Force | Out-Null

        Write-Log -Status "SUCCESS" -Message "AFTER CHANGE: $ValueName set to $DesiredValue"
        Write-Host "Value updated to $DesiredValue." -ForegroundColor Green
    }
    else {
        Write-Host "PREVIEW: Would change $ValueName from '$CurrentValue' to '$DesiredValue'" -ForegroundColor Yellow
    }
}

# ---------------------------------------------------------------
# STEP 5: Final verification read - confirms what's ACTUALLY there now
# ---------------------------------------------------------------
$FinalProperty = Get-ItemProperty -Path $KeyPath -Name $ValueName -ErrorAction SilentlyContinue
$FinalValue    = if ($FinalProperty) { $FinalProperty.$ValueName } else { $null }

Write-Host "`nFinal verified value: $(if ($null -eq $FinalValue) {''} else {$FinalValue})" -ForegroundColor Cyan
Write-Host "Audit log: $LogPath" -ForegroundColor Cyan

Line-by-Line Explanation

$KeyPath = "HKCU:\Software\ABCBankAutomation"

  • This string looks exactly like a file path, and PowerShell treats it exactly like one, because HKCU: is a registered PSDrive pointing at the registry rather than a disk — the same -Path-based cmdlets we've used on real files all work here unchanged.

$CurrentProperty = Get-ItemProperty -Path $KeyPath -Name $ValueName -ErrorAction SilentlyContinue

  • A missing value produces a non-terminating error by default; -ErrorAction SilentlyContinue (Project 5's narrow-use pattern) lets us treat "not set yet" as an expected first-run possibility rather than a script failure, similar to how a missing scheduled task was treated in Project 11.

$CurrentValue = if ($CurrentProperty) { $CurrentProperty.$ValueName } else { $null }

  • Get-ItemProperty returns an object whose properties are named after the registry values themselves — so $CurrentProperty.LogLevel would give us the number directly. Because our value name is stored in a variable ($ValueName) rather than typed literally, we use $CurrentProperty.$ValueName — PowerShell evaluates the variable first to get the property name, then looks up that property, letting the script work with any value name without hardcoding it in two places.

if ($CurrentValue -eq $DesiredValue) { ... } else { ... }

  • This is the entire idempotency decision in one line — everything before it exists just to gather the information needed to answer this single question accurately.

Write-Log -Status "INFO" -Message "BEFORE CHANGE: $ValueName was '$CurrentValue' ..."

  • Logging the "before" value happens before New-ItemProperty runs, not after — if the change itself somehow failed partway through, we'd still have a record of what the value was beforehand, preserving the audit trail's usefulness even in a failure scenario.

New-ItemProperty -Path $KeyPath -Name $ValueName -Value $DesiredValue -PropertyType $ValueType -Force

  • Reusing New-ItemProperty (rather than switching to Set-ItemProperty for updates) with -Force works for both "value doesn't exist yet" and "value exists but is wrong" — one code path handles both cases instead of branching into two separate cmdlet calls.

Production Incident Walkthrough

A less careful version of this script, without a "before" log entry, runs against 40 servers to enforce a new setting. Three weeks later, someone reports unexpected application behavior possibly related to that setting change, and Operations needs to know what the value was before the script touched it, on each affected server, to help isolate the cause. Because our version logs the before-state on every actual change, that history exists; a version that only logged "changed to X" would leave no way to reconstruct what any given server looked like beforehand.
  • Why is "already correct, no action taken" also worth logging? It proves the check actually ran on that server, rather than leaving a gap that looks identical to "the script never executed here at all" — an important distinction during an audit or incident review.

Security & Best Practices

Why this lab avoids HKLMReal security-baseline registry changes almost always target HKLM (machine-wide) and require administrator rights — deliberately practicing first against a safe HKCU sandbox key means you can make mistakes risk-free while learning the pattern, before ever pointing similar logic at a real system setting.
Best practice reinforced hereLogging the "before" value before making any change is a small addition that makes a registry-modifying script meaningfully safer and more auditable — cheap to add, expensive to be missing when you actually need it.

Common Mistakes to Avoid

  • Confusing a registry key with a registry value — they're different things.
  • Blindly overwriting a registry value without recording what it was before.
  • Forgetting the trailing colon on registry drive names.
  • Trusting that a write succeeded without a final verification read.

Interview Preparation

Q1. What's the precise difference between a registry key and a registry value?

Answer: A key is a container, analogous to a folder — it can contain other keys (subkeys) and values. A value lives inside a key and has its own name, data type, and data, analogous to a file within a folder. "Setting a registry key" is imprecise language; you set a value that lives inside a key.

Follow-up: "How would you list every value inside a key using PowerShell?" — Answer: Get-ItemProperty -Path $KeyPath without -Name returns an object with every value in that key as its properties.

Q2. Why re-read the value at the end of the script instead of trusting that New-ItemProperty succeeded?

Answer: A cmdlet reporting success doesn't guarantee the environment now matches intent in every edge case (permissions quirks, unexpected type coercion, remote timing issues in more advanced scenarios) — an explicit final read confirms the actual current state, rather than assuming based on the absence of an error.

Follow-up: "How would you handle it if the final verification showed the change didn't actually take effect?" — Answer: log an ERROR-level entry (same pattern as Project 10's failed-recovery case) and flag it for manual investigation rather than silently reporting success.

Q3. Why does this script use HKCU for the lab instead of HKLM, given real security settings usually live in HKLM?

Answer: HKCU requires no elevated privileges and only affects the current user's profile, making it safe to practice against without any risk of impacting the whole machine — the underlying Test-Path/Get-ItemProperty/New-ItemProperty pattern is identical for HKLM, just requiring Administrator rights and much more caution about what's actually being changed.

Follow-up: "What would you add to this script before pointing it at a real HKLM security setting?" — Answer: stronger confirmation prompts (perhaps requiring explicit -Confirm rather than defaulting it off), a documented rollback value, and likely running it first in a test/DEV environment identical to Project 9's multi-stage promotion path (DEV → UAT → Production).
