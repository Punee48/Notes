Concepts First — Before We Touch Code

1. Comparison Operators

Why letters, not symbols?PowerShell uses -lt instead of < because the angle brackets are already used for redirection in the shell. Using words like -lt avoids that clash and reads almost like plain English.

2. Logical Operators

  • -and — both conditions must be true
  • -or — at least one condition must be true
  • -not / ! — reverses a condition (true becomes false)

3. if / elseif / else

This is how PowerShell makes decisions. It checks a condition; if true, it runs one block of code, otherwise it can check further conditions or fall through to a default block.

4. Why Two Thresholds Instead of One?

Production practiceReal monitoring almost never uses a single cutoff. A Warning threshold (e.g. 20% free) gives operations time to plan; a Critical threshold (e.g. 10% free) means "act now." One threshold either causes alert fatigue (too sensitive) or misses the early warning window (too loose).

5. Functions — Our First Reusable Block

A function packages a piece of logic under a name so we can call it repeatedly instead of copying code. We'll introduce a small one here; Project 09+ will go much deeper into parameters and validation.

function Get-DiskStatus {      # Defines a new function named Get-DiskStatus
    param($FreePercent)        # Declares one input value the function expects
    if ($FreePercent -lt 10) { "CRITICAL" }        # Returns the word CRITICAL when under 10%
    elseif ($FreePercent -lt 20) { "WARNING" }     # Returns WARNING when under 20% (but not under 10%)
    else { "HEALTHY" }                              # Otherwise, returns HEALTHY
}
  • function Get-DiskStatus { } — defines a reusable block of code under a Verb-Noun name, just like a built-in cmdlet.
  • param($FreePercent) — declares the function's input; when we call Get-DiskStatus -FreePercent 8, the value 8 is bound to this variable.
  • Whatever value is produced last inside the function (here, the quoted word) is automatically returned as the function's output — no explicit return needed, though we'll use return explicitly in later, more complex functions for clarity.

6. Color-Coded Console Output

Write-Host -ForegroundColor lets us visually distinguish status at a glance — Red for Critical, Yellow for Warning, Green for Healthy. This mirrors how real monitoring dashboards use color.

Full Script — Get-DiskSpaceMonitor.ps1

# =====================================================================
# Get-DiskSpaceMonitor.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Monitor local disk space and flag Warning/Critical thresholds
# =====================================================================

$ComputerName     = $env:COMPUTERNAME     # The server we are checking (local machine for this lab)
$WarningThreshold = 20                    # Free space percent below which we consider a disk "WARNING"
$CriticalThreshold = 10                   # Free space percent below which we consider a disk "CRITICAL"

# ---------------------------------------------------------------
# FUNCTION: Decide the status label for a given free-space percent
# ---------------------------------------------------------------
function Get-DiskStatus {                          # Defines a reusable decision function
    param(
        [double]$FreePercent,                       # The free space percentage to evaluate
        [double]$WarnLevel,                          # The warning threshold to compare against
        [double]$CritLevel                            # The critical threshold to compare against
    )

    if ($FreePercent -lt $CritLevel) {                # First check the most severe condition
        return "CRITICAL"                              # Immediately exits the function with this value
    }
    elseif ($FreePercent -lt $WarnLevel) {             # Only checked if the CRITICAL condition was false
        return "WARNING"                                # Exits the function with this value
    }
    else {                                              # Runs only if neither condition above matched
        return "HEALTHY"                                # Exits the function with this value
    }
}

# ---------------------------------------------------------------
# STEP 1: Collect local fixed disks using CIM (same approach as Project 1)
# ---------------------------------------------------------------
$DiskInfo = Get-CimInstance -ClassName Win32_LogicalDisk -Filter "DriveType=3"   # DriveType=3 = local fixed disk

# ---------------------------------------------------------------
# STEP 2: Build a status report, one object per disk
# ---------------------------------------------------------------
$DiskReport = $DiskInfo | ForEach-Object {           # Processes each disk object one at a time
    $FreePercent = [math]::Round(($_.FreeSpace / $_.Size) * 100, 1)   # Calculates free space percentage

    $Status = Get-DiskStatus -FreePercent $FreePercent `   # Calls our function with named parameters
                              -WarnLevel $WarningThreshold `
                              -CritLevel $CriticalThreshold

    [PSCustomObject]@{                                # Builds one clean record for this disk
        ServerName  = $ComputerName                    # Which server this disk belongs to
        DriveLetter = $_.DeviceID                       # e.g. "C:"
        SizeGB      = [math]::Round($_.Size / 1GB, 2)   # Total size in GB
        FreeGB      = [math]::Round($_.FreeSpace / 1GB, 2)  # Free space in GB
        FreePercent = $FreePercent                       # Free space as a percentage
        Status      = $Status                            # HEALTHY / WARNING / CRITICAL
    }
}

# ---------------------------------------------------------------
# STEP 3: Print color-coded results to the console
# ---------------------------------------------------------------
Write-Host "`n=== DISK SPACE MONITOR: $ComputerName ===" -ForegroundColor Magenta   # Section header

foreach ($Disk in $DiskReport) {                      # Loops through each disk record one at a time
    $Line = "{0}  {1} GB free of {2} GB ({3}%)  -  {4}" -f `   # Builds a formatted display line
                $Disk.DriveLetter, $Disk.FreeGB, $Disk.SizeGB, $Disk.FreePercent, $Disk.Status

    if ($Disk.Status -eq "CRITICAL") {                # Chooses the display color based on status
        Write-Host $Line -ForegroundColor Red          # Red for CRITICAL
    }
    elseif ($Disk.Status -eq "WARNING") {
        Write-Host $Line -ForegroundColor Yellow        # Yellow for WARNING
    }
    else {
        Write-Host $Line -ForegroundColor Green          # Green for HEALTHY
    }
}

# ---------------------------------------------------------------
# STEP 4: Export the report to CSV for the operations team
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) {                    # Checks whether the reports folder already exists
    New-Item -ItemType Directory -Path ".\reports" | Out-Null   # Creates it silently if missing
}

$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"         # Builds a sortable timestamp for the filename

$DiskReport |                                            # Sends the disk records into the pipeline
    Export-Csv -Path ".\reports\DiskSpace_$Timestamp.csv" -NoTypeInformation   # Writes them to CSV

# ---------------------------------------------------------------
# STEP 5: Summarize how many disks need attention
# ---------------------------------------------------------------
$CriticalCount = ($DiskReport | Where-Object { $_.Status -eq "CRITICAL" }).Count   # Counts CRITICAL disks
$WarningCount  = ($DiskReport | Where-Object { $_.Status -eq "WARNING"  }).Count   # Counts WARNING disks

Write-Host "`nSummary: $CriticalCount Critical, $WarningCount Warning disk(s) found." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

function Get-DiskStatus { param(...) if... elseif... else... }

  • function Get-DiskStatus — declares a new function; PowerShell now treats Get-DiskStatus as a callable command for the rest of the script.
  • param([double]$FreePercent, ...) — declares typed parameters. [double] constrains the input to a decimal number; if something else is passed, PowerShell will try to convert it or throw an error.
  • return "CRITICAL" — the return keyword immediately exits the function and hands back the given value as the function's output. Using explicit return here (rather than just leaving a bare value) makes the exit point obvious to a reader.

Get-DiskStatus -FreePercent $FreePercent -WarnLevel $WarningThreshold -CritLevel $CriticalThreshold

  • This calls our function the exact same way we'd call a built-in cmdlet — with named parameters. The backtick ` at the end of a line is PowerShell's line-continuation character, letting a single logical command span multiple lines for readability.

"{0} {1} GB free of {2} GB ({3}%) - {4}" -f $Disk.DriveLetter, $Disk.FreeGB, ...

  • This is the format operator -f. The string on the left contains numbered placeholders ({0}, {1}, …); each is replaced, in order, by the corresponding value listed after -f. It's a clean way to build a readable line from several variables without messy string concatenation.

foreach ($Disk in $DiskReport) { ... }

  • foreach (...) — a looping keyword (different from the ForEach-Object cmdlet used earlier). It loops over a collection already in memory, assigning each item in turn to the loop variable $Disk.
  • $Disk in $DiskReport — reads naturally as "for each $Disk in the collection $DiskReport".
foreach keyword vs ForEach-Object cmdletThey look similar but work differently: foreach loads the whole collection into memory first and doesn't use the pipeline; ForEach-Object receives one object at a time through the pipeline and can start working before the whole collection is ready. For small in-memory collections like ours, either works fine — the distinction matters more at scale, which we'll revisit in the parallel-processing projects.

if (-not (Test-Path ".\reports")) { New-Item ... | Out-Null }

  • Test-Path — returns $true or $false depending on whether a path exists.
  • -not — reverses that boolean, so the block runs only when the folder is missing.
  • | Out-Null — discards the object that New-Item would normally output to the console, keeping our output clean since we don't need to see it here.

($DiskReport | Where-Object { $_.Status -eq "CRITICAL" }).Count

  • The parentheses run the entire pipeline first (filter down to only CRITICAL disks), then .Count is applied to the resulting collection — a property every PowerShell array-like collection exposes, telling us how many items it contains.

Compared to Project 1, we've added a decision layer between raw data collection and output. This separation — collect, then decide, then report — is a pattern you'll see in almost every monitoring script we build for the rest of the course.

Production Incident Walkthrough

Imagine this script runs against 200 servers tonight (we'll actually build multi-server support in later projects). 185 report HEALTHY, 12 report WARNING, and 3 report CRITICAL.
  • Should the script stop when it finds a CRITICAL disk? No — stopping would prevent us from checking the remaining servers. Monitoring scripts should keep going and report everything, not halt on the first problem.
  • How do we make sure Operations doesn't miss the 3 CRITICAL servers among 200 rows? The Summary line at the end (Step 5) plus color-coding solves this for a human reading the console; in a later project we'll add automatic email/ticket alerts so nobody has to read every row.
  • How do we avoid alert fatigue? This is exactly why we used two thresholds instead of one — WARNING servers are visible but not urgent, so Operations can triage by severity instead of treating every alert as an emergency.

Best practice reinforced hereThresholds are stored as named variables at the top of the script ($WarningThreshold, $CriticalThreshold) rather than "magic numbers" buried inside the logic. This makes the script easy to tune without hunting through code — a small habit that matters a lot once scripts grow to hundreds of lines.

Common Mistakes to Avoid

  • Checking the least severe condition first — always check CRITICAL before WARNING, or a critical disk could incorrectly be reported as only a warning.
  • Hardcoding threshold numbers directly inside if statements instead of named variables.
  • Letting a monitoring script stop entirely on the first bad result instead of continuing to check everything.

Interview Preparation

Q1. Why check the CRITICAL condition before WARNING in an if/elseif chain?

Answer: elseif conditions are only evaluated if the earlier ones were false — so if WARNING were checked first with a broad condition (like "less than 20%"), a disk at 5% free would match it and never reach the CRITICAL check. Ordering from most to least severe (or most to least specific) avoids that.

Follow-up: "How would you write this differently using a switch statement?" — Answer: a switch with a script-block condition per case can express the same logic; we'll cover switch directly in an upcoming intermediate project.

Q2. What's the difference between the foreach keyword and the ForEach-Object cmdlet?

Answer: foreach is a language keyword that loops over a collection already fully loaded in memory. ForEach-Object is a cmdlet that receives objects one at a time through the pipeline, which can be more memory-efficient for very large or streamed datasets.

Follow-up: "Which would you choose when piping output directly from Get-CimInstance across 500 remote servers?" — Answer: ForEach-Object, since it processes and can act on each object as it arrives rather than waiting for the entire set to load.

Q3. Why did we wrap the threshold logic in a function instead of writing it inline?

Answer: Wrapping it in Get-DiskStatus means the same threshold logic can be reused for any disk, any server, or even other resources (e.g. memory) later, without duplicating the if/elseif chain everywhere it's needed. It also makes the logic independently testable.

Follow-up: "How would you unit test this function?" — Answer: with Pester, calling Get-DiskStatus with known inputs and asserting the expected status string — covered in the Pester testing project later in the course.
