Quick Recap of Projects 1–13

Project 8 checked whether a port was reachable from the outside; this project checks the firewall configuration itself from the inside — are the rules that should exist actually there, actually enabled, and actually allowing what we expect? We'll also reuse Project 9's config-driven CSV approach and Project 10/13's ShouldProcess-and-idempotency discipline for any rule we need to create.

The Story — Why We're Building This

The banking application team says their new service needs inbound port 8443 open, and swears they already requested it. Nobody can confirm whether the firewall rule actually exists, is enabled, or was created correctly, without someone manually opening Windows Defender Firewall with Advanced Security and hunting through hundreds of rules. Our manager wants a script that reads a list of required rules from a config file (same CSV-driven approach as Project 9), validates each one against the real firewall, and — only if genuinely missing — creates it safely.

Concepts First — Before We Touch Code

1. The NetSecurity Module

CmdletPurpose
Get-NetFirewallRuleLists firewall rules and their high-level properties (Enabled, Direction, Action, Profile)
Get-NetFirewallPortFilterGets the port/protocol details associated with a rule
New-NetFirewallRuleCreates a new rule, optionally in one step with its port details

2. Why Port Info Isn't Directly on the Rule Object

A genuinely important design detailUnlike a service object (Project 4) where everything you need is one property away, a firewall rule's port and protocol information live on a separate, associated object. This reflects how Windows Firewall itself is structured internally — one rule can have multiple filter types attached (port, address, application, security) — so Get-NetFirewallRule alone won't tell you what port a rule covers.
$Rule = Get-NetFirewallRule -DisplayName "Core Banking App"
$PortInfo = $Rule | Get-NetFirewallPortFilter                # Follows the association from rule to its port details
$PortInfo.LocalPort                                            # e.g. 8443
  • $Rule | Get-NetFirewallPortFilter — piping the rule object into this cmdlet (rather than passing a name) uses the rule's internal association to find its linked port filter — the same underlying pattern as Get-Process | Get-NetworkPath style associated-object cmdlets you'll encounter elsewhere in Windows administration.

3. Key Rule Properties

PropertyMeaning
DisplayNameHuman-readable rule name
EnabledTrue/False — is the rule active
DirectionInbound or Outbound
ActionAllow or Block
ProfileWhich network profile(s) it applies to — Domain, Private, Public, or Any

4. Firewall Profiles — Why They Matter

Domain vs Private vs PublicWindows applies different rule sets depending on which network profile is active. A rule scoped only to "Domain" won't help on a server connected to a "Public" network profile — checking a rule exists isn't enough; it also needs to apply to the right profile for the environment it's protecting.

5. Creating a Rule with New-NetFirewallRule

New-NetFirewallRule `
    -DisplayName "Core Banking App" `
    -Direction Inbound `
    -Action Allow `
    -Protocol TCP `
    -LocalPort 8443 `
    -Profile Domain,Private
  • Unlike the two-step read pattern, New-NetFirewallRule can set both the rule and its port details in one call — the module provides convenience parameters that create the associated port filter object behind the scenes for you.

6. Reusing the Config-Driven Pattern from Project 9

Required rules live in a CSV — RuleName,Port,Protocol,Profile — so Operations can request a new port be validated/opened by editing a spreadsheet-like file, not by asking someone to modify PowerShell code.

Full Script — Test-FirewallCompliance.ps1

# =====================================================================
# Test-FirewallCompliance.ps1
# ABC Bank - Windows Infrastructure Automation Team
# Purpose: Validate and enforce required inbound firewall rules from config
# =====================================================================

[CmdletBinding(SupportsShouldProcess)]      # Same pattern from Projects 10 and 13
param(
    [switch]$WhatIf = $true
)

$RequiredRules = Import-Csv -Path ".\config\required-rules.csv"   # Config-driven, Project 9 pattern
$Results = @()

Write-Host "`n=== FIREWALL COMPLIANCE CHECK ===" -ForegroundColor Magenta
Write-Host "Validating $($RequiredRules.Count) required rule(s) from config.`n" -ForegroundColor Cyan

foreach ($Required in $RequiredRules) {                          # $Required is one row from the CSV

    Write-Host "Checking $($Required.RuleName) (port $($Required.Port)/$($Required.Protocol))..." -ForegroundColor Cyan

    # ---------------------------------------------------------------
    # STEP 1: Look for an existing rule with this exact name
    # ---------------------------------------------------------------
    $ExistingRule = Get-NetFirewallRule -DisplayName $Required.RuleName -ErrorAction SilentlyContinue

    $Status = "UNKNOWN"

    if ($ExistingRule) {
        # -------------------------------------------------------
        # STEP 2: Rule exists - verify it's actually correct, not just present
        # -------------------------------------------------------
        $PortInfo = $ExistingRule | Get-NetFirewallPortFilter    # Follows the rule-to-port association

        $PortMatches = ($PortInfo.LocalPort -eq $Required.Port) -and ($PortInfo.Protocol -eq $Required.Protocol)
        $IsEnabled   = $ExistingRule.Enabled -eq $true
        $IsAllow     = $ExistingRule.Action -eq "Allow"
        $IsInbound   = $ExistingRule.Direction -eq "Inbound"

        if ($PortMatches -and $IsEnabled -and $IsAllow -and $IsInbound) {   # ALL conditions must hold - Project 8's -and chaining
            $Status = "COMPLIANT"
            Write-Host "  Rule exists and is correctly configured." -ForegroundColor Green
        }
        else {
            $Status = "MISCONFIGURED"                                        # Exists, but something about it is wrong
            Write-Host "  Rule exists but is misconfigured (Enabled=$IsEnabled, Action=$($ExistingRule.Action), Port=$($PortInfo.LocalPort))" -ForegroundColor Red
        }
    }
    else {
        # -------------------------------------------------------
        # STEP 3: Rule missing - create it, respecting -WhatIf
        # -------------------------------------------------------
        Write-Host "  Rule not found." -ForegroundColor Yellow

        if ($PSCmdlet.ShouldProcess($Required.RuleName, "Create Firewall Rule")) {

            New-NetFirewallRule `
                -DisplayName $Required.RuleName `
                -Direction Inbound `
                -Action Allow `
                -Protocol $Required.Protocol `
                -LocalPort $Required.Port `
                -Profile $Required.Profile `
                -ErrorAction Stop | Out-Null

            $Status = "CREATED"
            Write-Host "  Rule created." -ForegroundColor Green
        }
        else {
            $Status = "MISSING (previewed)"
            Write-Host "  PREVIEW: Would create this rule." -ForegroundColor Yellow
        }
    }

    $Results += [PSCustomObject]@{
        RuleName = $Required.RuleName
        Port     = $Required.Port
        Protocol = $Required.Protocol
        Status   = $Status
        CheckedAt = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }
}

# ---------------------------------------------------------------
# STEP 4: Export and summarize
# ---------------------------------------------------------------
if (-not (Test-Path ".\reports")) { New-Item -ItemType Directory -Path ".\reports" | Out-Null }
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$Results | Export-Csv -Path ".\reports\FirewallCompliance_$Timestamp.csv" -NoTypeInformation

$NonCompliant = ($Results | Where-Object { $_.Status -notin @("COMPLIANT", "CREATED") }).Count
Write-Host "`nSummary: $NonCompliant of $($Results.Count) rule(s) need attention." -ForegroundColor Cyan
Write-Host "Report saved to .\reports\" -ForegroundColor Green

Line-by-Line Explanation

$PortInfo = $ExistingRule | Get-NetFirewallPortFilter

  • This is the associated-object pattern from the concepts section, applied for real: we can't get the port from $ExistingRule directly, so we pipe the rule object itself into Get-NetFirewallPortFilter, which uses the rule's internal identity to find and return its linked port filter object.

$PortMatches = ($PortInfo.LocalPort -eq $Required.Port) -and ($PortInfo.Protocol -eq $Required.Protocol)

  • Values coming from a CSV ($Required.Port) are always strings, while $PortInfo.LocalPort may come back as a different underlying type — PowerShell's -eq operator handles this kind of comparison gracefully in most cases by converting types as needed, but it's worth being aware this comparison is happening across potentially different types, unlike Project 13's DWord-to-integer registry comparison which was more strictly numeric.

if ($PortMatches -and $IsEnabled -and $IsAllow -and $IsInbound) { ... }

  • Four separate boolean checks chained with -and — extending the pattern from Project 8's three-layer network check to four conditions, because "compliant" here means all of these must be true simultaneously: right port, enabled, allowing (not blocking), and inbound.

$Status = "MISCONFIGURED" vs $Status = "MISSING (previewed)"

  • Notice this script distinguishes three different problem states — MISCONFIGURED (exists but wrong), MISSING (doesn't exist at all), and the WhatIf-specific preview variant — rather than lumping every non-compliant result into one generic "BAD" status. This level of detail is what actually helps someone fix the problem quickly, versus just knowing something's wrong.

Where-Object { $_.Status -notin @("COMPLIANT", "CREATED") }

  • -notin — the negated form of -in (first seen in Project 4): checks that a value is not present in the given list — here, "anything except these two good outcomes counts as needing attention," which is more robust than trying to explicitly list every possible bad status.

Notice this script checks for three distinct outcomes per rule, not just "exists or not": a rule can be entirely missing, present but wrong, or present and correct — and only the "missing" path involves creating anything. A misconfigured existing rule is deliberately not auto-corrected here; it's flagged for review, since silently changing an existing rule someone else configured carries more risk than creating a new one that wasn't there at all.

Production Incident Walkthrough

Our report comes back showing "ABCBank-CoreApp: MISCONFIGURED (Enabled=False)" — the rule exists with the exact right port, but it's disabled. This immediately explains the application team's connectivity complaint without anyone needing to dig further: someone or something disabled the rule after it was originally created correctly, likely during a security sweep or a conflicting policy change.
  • Why report MISCONFIGURED separately instead of just re-enabling it automatically? A disabled rule might have been disabled deliberately and for a good reason nobody documented — automatically flipping it back on could reintroduce a security exposure someone intentionally closed. Flagging for human review is safer than assuming the CSV's desired state is always correct in every case.
  • Why check all four conditions instead of just checking whether the rule is enabled? A rule could be enabled but pointing at the wrong port, or enabled but set to Block instead of Allow — each of those would look "present and enabled" while still not doing what's actually needed.

Security & Best Practices

Why misconfigured rules aren't auto-fixedThis script deliberately only ever creates missing rules automatically — it never modifies or re-enables an existing rule, even one that's technically wrong. Changing something that already exists and was presumably configured by someone, for some reason, carries more risk than adding something that plainly wasn't there.
Best practice reinforced hereRules are validated against all four relevant properties (port, enabled, action, direction), not just existence — a compliance check that only confirms "a rule with this name exists" would miss most of the ways a rule can actually be wrong.

Interview Preparation

Q1. Why doesn't Get-NetFirewallRule return the port number directly?

Answer: A firewall rule can have several different kinds of filters attached to it (port, address, application, security) as separate associated objects — this mirrors how Windows Firewall itself models rules internally, so retrieving port-specific details requires a separate, associated query via Get-NetFirewallPortFilter.

Follow-up: "What other 'Get-NetFirewall*Filter' cmdlets might exist, based on that pattern?" — Answer: Get-NetFirewallAddressFilter and Get-NetFirewallApplicationFilter follow the same associated-object idea for IP address ranges and specific application paths, respectively.

Q2. Why check Enabled, Action, and Direction in addition to the port number?

Answer: A rule with the exact right port could still be disabled, set to Block instead of Allow, or scoped to Outbound instead of Inbound — any one of those would mean the rule doesn't actually provide the access it appears to at a glance, so all relevant properties need validation, not just the port.

Follow-up: "How would you extend this to also validate the Profile matches what's required?" — Answer: add a fifth boolean check comparing $ExistingRule.Profile against $Required.Profile, following the exact same -and chaining already used for the other four conditions.

Q3. Why does this script only create missing rules and never modify existing misconfigured ones?

Answer: An existing rule might have been intentionally changed by someone for a reason not captured in this script's config — automatically overwriting it risks undoing a deliberate, undocumented decision. Creating something that's genuinely absent is lower-risk than modifying something that already exists.

Follow-up: "If the business wanted misconfigured rules auto-corrected too, what would you add first?" — Answer: a stronger audit trail (like Project 10/13's before/after logging) plus likely a mandatory human approval step or change ticket reference before allowing automatic correction of existing configuration — auto-remediation of something pre-existing needs more governance than creating something new.
