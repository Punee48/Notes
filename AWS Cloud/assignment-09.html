04 Architecture Decision Making

Decision: CloudTrail — Single Region Trail vs. Organization/Multi-Region Trail

Namma ippo single account, single region (ap-south-1) mattum thaan operate pannurom, so oru simple single-region trail podalam nu thonum. Aana enterprise-la, oru engineer accidentally velaru region-la (say, us-east-1) resource create pannirundha, andha activity namma trail-la varaadhu — blind spot. So namma multi-region trail select pannurom — namma velaru region use pannalainaalum, andha coverage free-a irukku, and future-la multi-region expand aanaalum, ondrum change pannanum vendaam.

Decision: CloudWatch Dashboard vs. Third-Party Observability Tool (Grafana/Datadog)

CloudWatch DashboardThird-party (Grafana/Datadog)
Setup costNative, zero extra infra, straight-a AWS metrics-oda integrate aagumExtra infra (self-host Grafana) or extra monthly SaaS cost
Fits namma current scaleAama — single account, konjam services mattum irukkuOverkill ippolaikku, aana multi-cloud aana bodhu worth pannum

Decision: CloudWatch Dashboard, ippolaikku. Namma innum single-cloud (AWS mattum), single-account. Third-party tool-oda real value varradhu multi-cloud illa romba complex-aana correlation thevai irundha thaan — namma andha stage-ku innum varala. "Namma actual thevai enna" nu paathu decide pannurathu than namma course mudivu ella time-lyum.

05 AWS Console — Manual Steps

  1. CloudTrail create pannuvom. CloudTrail console → Create trail → name quote-portal-audit-trail → "Apply trail to all regions" ON pannunga → S3 bucket create pannunga (new, dedicated bucket — Assignment 1/4-oda bucket-ay use pannaadheenga, audit trail-ku thani bucket venum) → log file validation ON pannunga (ithu, trail file tamper aagala nu cryptographically verify pannum).
  2. Audit bucket-ku Object Lock enable pannunga. S3 console → andha new bucket → creation time-lay Object Lock enable pannanum (bucket create aana appuram add panna mudiyaadhu) → compliance mode, minimum retention 1 year. Ithu, Assignment 4-la namma paatha "true deletion-ku separate action venum" pattern-oda strongest version — audit logs ah yaarum, edit panna kooda mudiyaadhu.
  3. CloudWatch Dashboard create pannunga. CloudWatch console → Dashboards → Create dashboard → name quote-portal-ops → widgets add pannunga: ALB HealthyHostCount + HTTPCode_Target_5XX_Count, ASG GroupInServiceInstances, RDS CPUUtilization + DatabaseConnections, Assignment-1 reconciliation job-oda custom success metric.
  4. SNS Topic create pannunga. SNS console → Create topic → Standard type → name quote-portal-alerts → subscription add pannunga (email — on-call team-oda distribution list).
  5. Existing alarms-ah ella SNS-oda link pannunga. Assignment 3, 6, 7, 8-la namma create panna alarms edukkunga → each-oda Actions tab-la → SNS topic quote-portal-alerts add pannunga. Ippo varaikkum antha alarms fire aana, console-la mattum theriyum — yaarukkum notify aagalaye. Ithu than namma ippo fix pannurom.
  6. Centralized log group create pannunga (optional but recommended). CloudWatch Logs → naama already irukura different log groups (app, RDS, VPC flow logs) ah oru dashboard-la, one metric filter through, easy-a search panna mudiyara maadhiri organize pannunga.

06 AWS CLI

# Create the SNS topic for critical alerts
TOPIC_ARN=$(aws sns create-topic --name quote-portal-alerts --query 'TopicArn' --output text)
aws sns subscribe --topic-arn $TOPIC_ARN --protocol email --notification-endpoint oncall@quoteportal.example

# Create the multi-region CloudTrail trail
aws cloudtrail create-trail \
  --name quote-portal-audit-trail \
  --s3-bucket-name quote-portal-audit-logs \
  --is-multi-region-trail \
  --enable-log-file-validation
aws cloudtrail start-logging --name quote-portal-audit-trail

# Attach the SNS topic to an existing alarm (e.g. the ASG minimum-capacity one from Assignment 7)
aws cloudwatch put-metric-alarm \
  --alarm-name quote-portal-asg-at-minimum \
  --alarm-actions $TOPIC_ARN

07 Terraform Implementation

main.tf — Audit Bucket & CloudTrail

main.tf (part 1 of 3)
resource "aws_s3_bucket" "audit_logs" {
  bucket = "quote-portal-audit-logs"
  # Separate, dedicated bucket — deliberately NOT reused from Assignment 1 or
  # 4, since audit trail data has a completely different access/retention
  # policy than application data, and mixing the two is bad practice.
}

resource "aws_s3_bucket_object_lock_configuration" "audit_logs" {
  bucket = aws_s3_bucket.audit_logs.id
  rule {
    default_retention {
      mode = "COMPLIANCE"
      years = 1
    }
  }
  # COMPLIANCE mode means NOBODY — including the account root user — can
  # delete or shorten the retention on these objects before it expires.
  # This is deliberately stronger than the "governance mode" Object Lock
  # option mentioned back in Assignment 4's challenge, because audit trail
  # integrity is exactly the case that demands the strongest guarantee.
}

resource "aws_cloudtrail" "main" {
  name                          = "quote-portal-audit-trail"
  s3_bucket_name                = aws_s3_bucket.audit_logs.id
  is_multi_region_trail         = true
  enable_log_file_validation    = true
  include_global_service_events = true
  # include_global_service_events captures IAM/Route53-type events, which
  # aren't tied to any specific region but still matter for audit coverage.
}

main.tf — Centralized SNS Alerting

main.tf (part 2 of 3)
resource "aws_sns_topic" "alerts" {
  name = "quote-portal-alerts"
}

resource "aws_sns_topic_subscription" "oncall_email" {
  topic_arn = aws_sns_topic.alerts.arn
  protocol  = "email"
  endpoint  = var.oncall_email
  # Terraform can create the subscription, but AWS still requires the
  # recipient to manually confirm it via the email AWS sends — this is by
  # design, so nobody can subscribe an inbox that isn't actually theirs.
}

resource "aws_cloudwatch_metric_alarm" "alb_5xx_spike" {
  alarm_name          = "quote-portal-alb-5xx-spike"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods   = 2
  metric_name          = "HTTPCode_Target_5XX_Count"
  namespace             = "AWS/ApplicationELB"
  period                = 60
  statistic             = "Sum"
  threshold             = 10
  dimensions            = { LoadBalancer = aws_lb.main.arn_suffix }
  alarm_actions          = [aws_sns_topic.alerts.arn]
  alarm_description      = "More than 10 backend 5XX errors within a minute, sustained across 2 periods"
  # evaluation_periods = 2 means the threshold must be breached across TWO
  # consecutive checks before alarming — avoids paging someone for one
  # single noisy minute that self-resolves immediately.
}

10 Production Incident

Rendu vaaram kazhichu, dashboard live aana appuram

Oru naal, RDS DatabaseConnections metric slowly climb aagudhu, aana threshold cross pannala — so alarm fire aagala. On-call engineer dashboard-ah routine-a paakumbodhu, connection count normal-oda romba adjacent-a irukurathu kavanichaanga, aana confirm panna theriyala idhu real problem-a illa normal growth-a nu.

Investigation

CloudWatch metric history-ah last 30 days paathaanga — connection count steadily climb aayidhu, andha proportion-la application traffic increase aagala. Ithu, oru application bug-la connection pool properly close aagaama irukkura pattern (connection leak) nu suspect pannanga.

Root Cause

Application code-la, oru specific error path-la, DB connection release pannaama exception throw aayidum — so andha specific error trigger aana ovvoru thadavaiyum, oru connection "leak" aagum, slowly accumulate aagum.

Immediate Fix

App instances-ah rolling restart pannaanga (ASG-oda instance refresh feature use pannalam) — connection count reset aachu.

Permanent Fix

Application team, andha error path-la proper finally block/connection cleanup add pannanga. Additionally, namma trend-based alarm add pannom — absolute threshold mattum illama, "last 24 hours-la connection count 50%-ku mela steadily climb aana" nu detect pannura alarm, idhu maadhiri slow-leak pattern-ah, hard-threshold cross aagura munnaadiye, catch pannum.

Lessons Learned

  • Ella problem-um oru hard threshold cross pannaadhu — slow, steady drift pattern (like a connection leak) detect panna, trend-based alarms venum, static threshold mattum podhaadhu.
  • Dashboard-ah oru engineer manually, routine-a paakurathu, namma automated alarms miss panna edhaavadhu catch pannalam — dashboard automated alerting-ku substitute illa, aana oru useful safety net.

17 Interview Preparation

Q1 · Monitoring FundamentalsCloudTrail-ukum CloudWatch-ukum enna difference?

CloudTrail "yaaru enna pannanga" nu track pannum — API-level actions, who/when/what, audit-kaaga. CloudWatch "system ippo eppadi irukku" nu track pannum — metrics, logs, alarms, real-time operational health-kaaga. Rendும் "monitoring" nu sonnaalum, rendும் completely different purpose — oru security/compliance-kaaga, innoru operations-kaaga.

Follow-up: "Rendையும் onnu serthu use pannura example sollunga?" — Oru security group rule maatram RDS-ah publicly accessible aakithu nu suspect pannirundha, CloudTrail-la yaaru andha change pannanga nu paakalam, CloudWatch/VPC Flow Logs-la andha change-oda impact (unexpected inbound traffic) evlo real-a irundhudhu nu correlate pannalam.
Q2 · SecurityObject Lock COMPLIANCE mode ethukku, GOVERNANCE mode why not?

GOVERNANCE mode-la, special IAM permission (s3:BypassGovernanceRetention) irukura yaaravadhu, retention-ah override panna mudiyum — legitimate use cases-ku flexibility kudukkum. COMPLIANCE mode-la, root user kooda, retention period mudiyara varaikkum, edhavum delete/modify panna mudiyaadhu — no bypass, ever. Audit trail data-ku, ithan correct choice, ethaavadhu insider yaaravadhu evidence tamper panna try pannaalum, adhu structurally impossible-a irukkanum.

Follow-up: "COMPLIANCE mode-oda downside enna?" — Genuine mistake (wrong bucket-la accidentally sensitive data podranum) pannirundhaalum, adhu retention expire aagara varaikkum remove panna mudiyaadhu — so bucket selection romba careful-a pannanum, munnadiye.
Q3 · Production ScenarioOru metric slowly drift aayidhu, aana static threshold cross pannala. Epdi idha detect pannuveenga?

Static threshold alarms, "line cross aacha illaya" nu mattum kekkum — gradual trend catch panna, oru different approach venum: either CloudWatch Anomaly Detection (baseline pattern-ah learn panni, andha baseline-la irundhu deviate aana alert pannum), illa manual-a, "last N hours-la X% change aacha" nu compare pannura oru custom alarm. Ithu exactly namma incident-la panna fix.

Follow-up: "Anomaly Detection vs manual trend alarm — eppo edhu use pannuveenga?" — Anomaly Detection, seasonal/cyclical pattern (daily traffic curve) irukura metric-ku nalla fit aagum — manual baseline set panna kashtam. Manual trend alarm, simple, predictable "should stay roughly flat" metrics-ku (connection count, disk usage) easy-a understand pannalam, debug pannalam.
Q4 · Cost OptimizationCloudTrail-ku data events (S3 object-level, Lambda invocation-level) enable pannuveengala, ellame-ku?

Illa, blanket-a ellame-ku illa — data events, management events-ah vida romba volume adhigam (every single S3 GetObject, ovvoru Lambda invoke), so cost significantly higher-a irukkum. Namma andha level of granularity specific-a compliance/security requirement irundha mattum (like, "ivvalavu sensitive bucket-la yaaru access pannanga specific-a venum" nu) andha specific bucket-ku mattum enable pannuvom, account-wide blanket-a illa.

Follow-up: "Namma quote-portal-audit-logs bucket-ku data events venuma?" — Andha bucket-oda content namma own audit logs — adhukku data-event-level tracking, romba meta (logs-oda logs) aagidum; management-event coverage already namma trail-oda creation/config changes track pannum, adhu podhum.
Q5 · Terraformok_actions ethukku venum, alarm_actions mattum podhaadha?

alarm_actions, problem start aana notify pannum. ok_actions, adhu resolve aana (back to normal state) notify pannum. Rendையும் vechuko na, on-call team-ku, "problem start aachu" mattum illama, "problem fix aayidhu" nu kooda visibility kidaikkum — especially, oru auto-healing mechanism (like ASG replacing a failed instance) andha problem-ah tha fix pannirundha, adhu automatically resolve aanadhu, team-ku confirm pannalam.

Follow-up: "ok_actions illama irundha enna risk?" — Alarm silently resolve aagum, aana yaarukkum theriyaadhu adhu actually fix aachaanu — engineer manually console poi confirm pannanum, andha automatic visibility illama.
Q6 · Manager RoundPriya kekraanga — "namma monitoring enterprise-grade-a irukka, illa ippozhaikku podhuma" nu evaluate pannunga.

Ippozhaikku, namma single account, single application-ku romba solid-a irukku — centralized dashboard, wired alerting, tamper-proof audit trail, trend-based detection ellame irukku. "Enterprise-grade" nu sollumbodhu, next natural gap enna nu naan explicitly sollanum: multi-account structure varumbodhu (Assignment 21), namma ippo panna single-account CloudTrail/dashboard pattern, oru centralized Log Archive account-ku expand pannanum — ippo panna vela waste aagaadhu, aana scale panna innum vela irukku nu transparent-a sollanum.

Follow-up: "Andha next step-ku enna specific-a change aagum?" — CloudTrail organization trail-a maarum (single account trail-ku badhila), S3 audit bucket oru dedicated Log Archive account-ku move aagum — ella account-oda logs-um oru central, restricted-access location-la collect aagum, adhaan Assignment 21-oda core idea.
