01

Business Scenario

NovaStack Bank's Production Support team currently learns about a down service the same way most immature shops do: a customer complains, or a synthetic monitor fires an alert that's already 5–10 minutes stale. Across the estate of 60+ internal services, there is no consistent, automation-driven health-check sweep that Infra Ops can run proactively — each app team built its own ad-hoc curl script, if anything at all.

After a Sev-1 incident where the core ledger reconciliation service was silently down for 40 minutes before anyone noticed, the Production Support Manager has mandated a standardized health-check automation framework: one Ansible-driven sweep, run on a schedule and on-demand, checking service state, port reachability, and application-level health endpoints across every registered service — with results pushed straight into the monitoring stack and ServiceNow.

Why this can't stay manualAd-hoc, per-team health scripts mean inconsistent coverage, no single source of truth, and — as the incident proved — real gaps where nothing is checked at all. A single automated framework guarantees every registered service gets the same rigor of check on the same cadence.

This project reuses the dynamic inventory and AAP scheduling patterns from Projects 1–2, and introduces a new concept: a self-registering service catalog that drives what gets checked, so onboarding a new service to health-checking is a data change, not a code change.

Authentication

Health checks run over the same SSH service-account pattern for process/port checks, plus a read-only HTTP call to each service's health endpoint — no authentication needed for most, but where a health endpoint requires a token, it's retrieved from Vault per Project 3's pattern, scoped read-only.

Ansible Design

Architect's note

The role takes zero service-specific logic — everything comes from the catalog. This is the key design decision: onboarding service #61 is a YAML pull request, never a role change.

Code & Roles

catalog/services.yml 
---
# This is the single file every app team edits. Nothing in the role
# needs to change when a new service is onboarded -- that's the point.
services:
  - name: ledger-reconciliation-svc
    port: 8443
    health_path: /actuator/health
    expect_status: 200
    expect_body_contains: "UP"
    check_interval_seconds: 60
    auto_create_incident: true
  - name: card-auth-svc
    port: 8443
    health_path: /health
    expect_status: 200
    expect_body_contains: "ok"
    check_interval_seconds: 30
    auto_create_incident: true
roles/health_check/tasks/main.yml 
---
# Three layers of check, cheapest first -- no point hitting an HTTP
# endpoint if the port isn't even open. This ordering keeps the sweep fast.
- name: Layer 1 -- TCP port reachability
  ansible.builtin.wait_for:
    host: "{{ inventory_hostname }}"
    port: "{{ svc_port }}"
    timeout: 5
  register: port_check
  failed_when: false

- name: Layer 2 -- process is actually running
  ansible.builtin.command: "pgrep -f {{ svc_name }}"
  register: process_check
  changed_when: false
  failed_when: false
  when: port_check.failed | default(false) == false

# Layer 3 only runs if layers 1 and 2 passed -- avoids a misleading
# "HTTP check failed" result when the real problem is the process is dead.
- name: Layer 3 -- application health endpoint
  ansible.builtin.uri:
    url: "https://{{ inventory_hostname }}:{{ svc_port }}{{ svc_health_path }}"
    status_code: "{{ svc_expect_status }}"
    return_content: true
  register: http_check
  failed_when: false
  when:
    - port_check.failed | default(false) == false
    - process_check.rc | default(1) == 0

- name: Push result to Prometheus Pushgateway
  ansible.builtin.uri:
    url: "http://pushgateway.internal.novastack.bank/metrics/job/health_sweep/instance/{{ inventory_hostname }}"
    method: POST
    body: "health_status{{ '{' }}service=\"{{ svc_name }}\"{{ '}' }} {{ 1 if (svc_expect_body_contains | default('') in http_check.content | default('')) else 0 }}"
  delegate_to: localhost

- name: Auto-create ServiceNow incident on failure, if opted in
  ansible.builtin.uri:
    url: "https://novastack.service-now.com/api/now/table/incident"
    method: POST
    headers:
      Authorization: "Bearer {{ lookup('community.hashi_vault.hashi_vault', 'secret/data/snow/api') }}"
    body_format: json
    body:
      short_description: "Health check failed: {{ svc_name }} on {{ inventory_hostname }}"
      urgency: 2
  delegate_to: localhost
  when:
    - svc_auto_create_incident | default(false)
    - not (svc_expect_body_contains | default('') in http_check.content | default(''))

Execution flow, in plain terms

Every service in the catalog gets the same three-layer check: is the port open, is the process alive, does the health endpoint say it's actually healthy. Only a genuine failure — not just a slow response — triggers a ServiceNow incident, and only for services that opted in, which is what keeps this from becoming ticket-flood noise.

Testing Strategy

  • Intentionally stop a DEV service to confirm the three-layer check correctly identifies the failure layer
  • Validate no false positives over a 48-hour UAT soak before enabling auto-incident creation in PROD
13

Production Deployment

Rolled out in waves of 10 services, each wave watched for 48 hours before the next, with auto-incident creation initially disabled and enabled only after false-positive rate is confirmed near zero.

14

Rollback Procedure

Disable the scheduled job template in AAP, or remove a specific service's catalog entry — the framework is entirely additive and non-invasive to target hosts, so rollback is a scheduling/config change, never a host-level revert.

15

Troubleshooting

False positives flooding ServiceNow Symptom: Incidents created for a service that's actually healthy.
Root cause (typical): Health endpoint returns 200 during a slow GC pause with a stale cached "UP" body.
Fix: Tighten expect_body_contains matching and add a retry-before-alert threshold rather than alerting on a single failed check.
16

Monitoring & Validation

Grafana dashboard shows sweep coverage (are all 60 catalog services actually reporting) as its own top-level metric — a silent gap in coverage is itself something Production Support needs to see.

Interview Preparation

Why check port, process, and HTTP endpoint separately instead of just hitting the health URL?
Layering lets the failure message be precise — "port closed" versus "process dead" versus "app unhealthy" are different root causes needing different responses, and checking cheap-to-expensive avoids wasted HTTP calls when the port's already down.
How does this scale as new services are added?
It's entirely catalog-driven — the role has zero service-specific code, so onboarding is a YAML pull request reviewed like any other change, not a code change to the automation itself.
