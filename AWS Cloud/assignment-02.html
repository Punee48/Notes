Assignment 02 of 25 · Foundation

Designing a Secure VPC with Public and Private Network Tiers

A general insurance company wants to put a customer-facing policy quote portal on AWS. Security has one non-negotiable rule: production servers cannot be directly exposed to the internet. The application team still needs a public endpoint. We're building the network these two requirements both live inside.

Difficulty: Foundation Domain: Insurance Services: VPC · Subnets · IGW · NAT GW · Route Tables · NACLs IaC: Console + CLI + Terraform Est. lab time: 2–3 hrs
Progress: Assignment 2 of 25

01 Production Story

Security Team — Ananya Reddy

"We've approved moving forward with the online policy quote portal. Before a single server goes up, I want the network design in front of me. Non-negotiable: no application server, and absolutely no database, sits in a subnet with a route to the internet. If it doesn't need to be reached from the internet, it doesn't get a public IP and it doesn't get a route to one. I don't care that it's 'just internal for now' — that's how things drift into being exposed six months later."

Application Team — Karthik Iyer

"Understood on the security side, but customers need to actually reach this thing over HTTPS from their browser. And our app servers still need to call out to third-party rating APIs and pull OS patches — they can't be fully cut off from the internet either, they just can't be reachable FROM it."

Why this is Assignment 2

Assignment 1 leaned on the account's default VPC — a flat, single-tier network where everything shares one address space with a route to the internet. That was fine for a background job nobody calls into. It is not fine the moment "public endpoint" and "database must be unreachable from the internet" are both requirements at once. That tension is exactly what public/private subnet design solves.

Current Environment

  • Nothing built yet for this workload — we're starting from a clean slate rather than retrofitting the default VPC.
  • Assignment 1's reconciliation job continues running in its own default-VPC setup; unrelated to this workload.

03 Architecture Design

One VPC, two Availability Zones, two tiers per AZ: a public subnet that can be reached from (and reach out to) the internet, and a private subnet that can reach out but can never be reached from the internet. This assignment builds the network only — compute, load balancer, and database go in the subnets in Assignments 3 and 8.

VPC CIDR: 10.20.0.0/16. Public subnets get a route to the Internet Gateway directly. Private subnets route outbound traffic through a NAT Gateway that lives in the public subnet of the same AZ — this avoids cross-AZ data transfer charges and means an AZ failure doesn't take down another AZ's outbound path.

Security Architecture

  • Security Groups (stateful, instance-level) will be defined per-workload in later assignments once there's actually compute to attach them to.
  • Network ACLs (stateless, subnet-level) are set here as a second layer: private subnet NACLs explicitly deny inbound traffic from 0.0.0.0/0 on all ports except the ephemeral return-traffic range, so even a misconfigured security group later can't accidentally open a private subnet to the world.
  • VPC Flow Logs enabled at the VPC level from creation, per Ananya's requirement — captures accepted and rejected traffic for every ENI in the VPC.

04 Architecture Decision Making

Decision: NAT Gateway vs. NAT Instance

NAT GatewayNAT Instance (EC2)
ManagementFully managed by AWS — no patching, no scaling to configureYou manage the OS, patch it, and size it yourself
AvailabilityHighly available within its AZ by designSingle EC2 instance — its own single point of failure
ThroughputScales automatically up to 100 GbpsCapped by the instance type you chose
CostHourly charge + per-GB data processing chargeJust the (usually cheaper) EC2 instance cost

Decision: NAT Gateway. The operational overhead of patching and right-sizing a NAT instance isn't worth the cost savings for an insurance company's production customer portal — and Security's whole point in this assignment is reducing operational risk, not adding a self-managed component to the security boundary.

Decision: One NAT Gateway per AZ vs. One Shared NAT Gateway

A single shared NAT Gateway in one AZ is cheaper, but every private subnet in the other AZ would then depend on a resource outside its own AZ — meaning an AZ failure could take down outbound connectivity for a private subnet in a completely different, otherwise-healthy AZ. Since Assignment requirements already demand a two-AZ design for availability, undermining that with a single NAT Gateway would be inconsistent. Decision: one NAT Gateway per AZ, accepting the doubled NAT cost as the price of the availability requirement Priya's org already committed to.

05 AWS Console — Manual Steps

We're building this by hand in the console first so the underlying pieces (route tables, associations, gateways) are visible and concrete, before we hand the exact same architecture to Terraform below. In real teams you'd rarely build production this way — but seeing every click makes the Terraform far less abstract.

Console → VPC service → all steps below, in order
  1. Create the VPC. VPC console → Your VPCs → Create VPC → choose "VPC only" → IPv4 CIDR 10.20.0.0/16 → name it quote-portal-vpc. This allocates the address space; nothing inside it exists yet.
  2. Create four subnets. Subnets → Create subnet, selecting quote-portal-vpc each time: public-a (10.20.1.0/24, AZ ap-south-1a), public-b (10.20.2.0/24, AZ ap-south-1b), private-a (10.20.11.0/24, AZ ap-south-1a), private-b (10.20.12.0/24, AZ ap-south-1b). A subnet is just a CIDR carved out of the VPC and pinned to one AZ — it isn't "public" or "private" yet; that label only becomes real once we attach route tables in step 5.
  3. Create and attach an Internet Gateway. Internet Gateways → Create internet gateway → name quote-portal-igw → create → then Actions → Attach to VPC → select quote-portal-vpc. An IGW with nothing attached does nothing; a VPC without an attached IGW has no path to the internet at all, public subnets or not.
  4. Allocate Elastic IPs and create two NAT Gateways. Elastic IPs → Allocate Elastic IP address (repeat twice). Then NAT Gateways → Create NAT gateway → subnet public-a, connectivity type "Public", select one Elastic IP → repeat for public-b with the second Elastic IP. NAT Gateways must sit in a public subnet — they need their own route to the internet to forward traffic on behalf of the private subnets.
  5. Create and configure the public route table. Route Tables → Create route table → name public-rt, VPC quote-portal-vpc → open it → Routes → Edit routes → Add route: destination 0.0.0.0/0, target = the Internet Gateway → Subnet associations → Edit → associate both public-a and public-b. This is the step that actually makes those two subnets "public" — the label is just shorthand for "has a route table sending internet-bound traffic to an IGW."
  6. Create and configure two private route tables. Create private-rt-a → add route 0.0.0.0/0 → target = nat-gw-a → associate with private-a only. Repeat: private-rt-b → target nat-gw-b → associate with private-b only. Keeping them separate (rather than one shared private route table) is what makes each AZ's outbound path independent, matching the decision above.
  7. Harden the private subnets' Network ACL. Network ACLs → create private-nacl → inbound rules: allow ephemeral TCP return traffic (1024–65535) from 0.0.0.0/0, deny everything else lower-numbered; no rule allowing unsolicited inbound on 80/443/22 from the internet. Associate with both private subnets. This is a second, stateless layer behind whatever security groups get attached to instances later.
  8. Enable VPC Flow Logs. Select quote-portal-vpc → Flow logs tab → Create flow log → filter "All", destination CloudWatch Logs, create/select an IAM role with permission to publish logs. This satisfies Ananya's audit requirement immediately, not as a follow-up task.
Why we don't stay in the console

Eight manual steps, done correctly, is manageable once. It is not manageable for a "dev," "qa," and "prod" copy of this same network, and it is not repeatable, reviewable, or diffable when Ananya's team wants to audit exactly what changed and when. That's the whole reason the rest of this course pushes toward Terraform as the primary method — the Terraform below produces the identical architecture you just clicked through.

06 AWS CLI — Same Architecture, Scriptable

bash
# 1. Create the VPC and capture its ID for later commands
VPC_ID=$(aws ec2 create-vpc \
  --cidr-block 10.20.0.0/16 \
  --query 'Vpc.VpcId' --output text)
aws ec2 create-tags --resources $VPC_ID --tags Key=Name,Value=quote-portal-vpc

# 2. Create the public subnet in AZ-A
PUB_A=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID --cidr-block 10.20.1.0/24 \
  --availability-zone ap-south-1a \
  --query 'Subnet.SubnetId' --output text)

# 3. Create and attach the Internet Gateway
IGW_ID=$(aws ec2 create-internet-gateway --query 'InternetGateway.InternetGatewayId' --output text)
aws ec2 attach-internet-gateway --vpc-id $VPC_ID --internet-gateway-id $IGW_ID

# 4. Create the public route table, add the default route, associate the subnet
RT_PUB=$(aws ec2 create-route-table --vpc-id $VPC_ID --query 'RouteTable.RouteTableId' --output text)
aws ec2 create-route --route-table-id $RT_PUB --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW_ID
aws ec2 associate-route-table --route-table-id $RT_PUB --subnet-id $PUB_A
CommandWhat it doesReversible?
create-vpcAllocates the VPC address spaceYes — delete-vpc (only once everything inside it is deleted)
create-routeAdds a single route to an existing route table — does not create the table itselfYes — delete-route
associate-route-tableLinks a subnet to a route table, which is what actually determines the subnet's traffic behaviorYes — disassociate-route-table, but the subnet then falls back to the VPC's main route table

We're showing four of the eight console steps here in CLI form for illustration — the full script (all four subnets, both NAT Gateways, both private route tables, the NACL, and flow logs) follows the identical pattern and is what the Terraform below encodes declaratively instead of imperatively.

07 Terraform Implementation

Same architecture a third time — this time declared once, applied consistently, and destroyable in one command. This is what actually ships to Ananya's team for review going forward.

variables.tf

variables.tf
variable "vpc_cidr" {
  description = "CIDR block for the quote portal VPC"
  type        = string
  default     = "10.20.0.0/16"
}

variable "azs" {
  description = "Availability Zones to spread the network across"
  type        = list(string)
  default     = ["ap-south-1a", "ap-south-1b"]
}

variable "public_subnet_cidrs" {
  type    = list(string)
  default = ["10.20.1.0/24", "10.20.2.0/24"]
}

variable "private_subnet_cidrs" {
  type    = list(string)
  default = ["10.20.11.0/24", "10.20.12.0/24"]
  # Numbered starting at .11 rather than .3, deliberately leaving 10.20.3.0/24
  # through 10.20.10.0/24 free for a future tier (cache, additional pools)
  # without renumbering anything that already exists — the scalability
  # requirement from the table above.
}

main.tf — VPC, Subnets, Internet Gateway

main.tf (part 1 of 3)
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true
  # DNS hostnames must be enabled for resources we add later (ALB, RDS) to
  # get resolvable DNS names — off by default on a manually-created VPC.
  tags = { Name = "quote-portal-vpc" }
}

resource "aws_subnet" "public" {
  count                   = length(var.public_subnet_cidrs)
  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.public_subnet_cidrs[count.index]
  availability_zone       = var.azs[count.index]
  map_public_ip_on_launch = true
  # count.index walks 0,1 — pairing each CIDR with the AZ at the same list
  # position. map_public_ip_on_launch means anything launched here gets a
  # public IP automatically — appropriate ONLY for this public tier.
  tags = { Name = "public-${var.azs[count.index]}", Tier = "public" }
}

resource "aws_subnet" "private" {
  count             = length(var.private_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.private_subnet_cidrs[count.index]
  availability_zone = var.azs[count.index]
  # No map_public_ip_on_launch here — defaults to false. Anything launched
  # in this subnet gets NO public IP, satisfying Security's core requirement
  # at the network layer, independent of whatever security group is applied.
  tags = { Name = "private-${var.azs[count.index]}", Tier = "private" }
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "quote-portal-igw" }
}

main.tf — NAT Gateways & Route Tables

main.tf (part 2 of 3)
resource "aws_eip" "nat" {
  count  = length(var.azs)
  domain = "vpc"
  # One Elastic IP per AZ — each NAT Gateway needs its own static public IP.
}

resource "aws_nat_gateway" "main" {
  count         = length(var.azs)
  allocation_id = aws_eip.nat[count.index].id
  subnet_id     = aws_subnet.public[count.index].id
  # Placed in the PUBLIC subnet of the SAME AZ index — this is what keeps
  # each AZ's outbound path independent, per the architecture decision above.
  tags = { Name = "nat-gw-${var.azs[count.index]}" }
  depends_on = [aws_internet_gateway.main]
  # Explicit dependency: a NAT Gateway needs the IGW to already be attached
  # to route through, even though no attribute reference forces that order.
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
  tags = { Name = "public-rt" }
}

resource "aws_route_table_association" "public" {
  count          = length(aws_subnet.public)
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
  # Both public subnets share ONE route table — they have identical routing
  # needs, so there's no reason to duplicate it.
}

resource "aws_route_table" "private" {
  count  = length(var.azs)
  vpc_id = aws_vpc.main.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.main[count.index].id
  }
  # TWO separate route tables (not one) — each private subnet routes through
  # ONLY its own AZ's NAT Gateway, per the per-AZ decision above.
  tags = { Name = "private-rt-${var.azs[count.index]}" }
}

resource "aws_route_table_association" "private" {
  count          = length(aws_subnet.private)
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}

main.tf — Hardened NACL & Flow Logs

main.tf (part 3 of 3)
resource "aws_network_acl" "private" {
  vpc_id     = aws_vpc.main.id
  subnet_ids = aws_subnet.private[*].id
  # [*] applies this one NACL to every private subnet in the list.

  ingress {
    rule_no    = 100
    protocol   = "tcp"
    action     = "allow"
    cidr_block = "0.0.0.0/0"
    from_port  = 1024
    to_port    = 65535
    # Allows RETURN traffic for connections the private instance itself
    # initiated (e.g. the reply to an outbound API call) — NACLs are
    # stateless, so return traffic must be explicitly allowed.
  }
  egress {
    rule_no    = 100
    protocol   = "-1"
    action     = "allow"
    cidr_block = "0.0.0.0/0"
    from_port  = 0
    to_port    = 0
  }
  # No rule allowing unsolicited inbound on 22/80/443 from 0.0.0.0/0 — the
  # implicit final rule in any NACL is DENY, so anything not explicitly
  # allowed above is blocked by default. This is the network-layer backstop.
  tags = { Name = "private-nacl" }
}

resource "aws_cloudwatch_log_group" "vpc_flow_logs" {
  name              = "/vpc/quote-portal/flow-logs"
  retention_in_days = 90
  # 90 days to satisfy a typical audit look-back window; adjust to whatever
  # Ananya's team's actual compliance retention requirement turns out to be.
}

resource "aws_iam_role" "flow_logs" {
  name = "vpc-flow-logs-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "vpc-flow-logs.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy" "flow_logs" {
  role = aws_iam_role.flow_logs.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["logs:CreateLogStream", "logs:PutLogEvents"]
      Resource = "${aws_cloudwatch_log_group.vpc_flow_logs.arn}:*"
    }]
  })
}

resource "aws_flow_log" "main" {
  vpc_id               = aws_vpc.main.id
  log_destination      = aws_cloudwatch_log_group.vpc_flow_logs.arn
  log_destination_type = "cloud-watch-logs"
  iam_role_arn         = aws_iam_role.flow_logs.arn
  traffic_type         = "ALL"
  # ALL captures both ACCEPT and REJECT records — REJECT records are what
  # let us later detect "something tried to reach the private tier and was
  # blocked," which matters for both security review and troubleshooting.
}

08 Validation & Testing

  • Network test: launch a temporary EC2 instance in a private subnet — confirm it receives no public IP, and confirm curl to an external URL from inside it succeeds (proving outbound-via-NAT works).
  • Security test: from your own machine, attempt to reach the private instance's private IP directly — must fail, since there's no route from the internet into that subnet at all.
  • Isolation test: confirm each AZ's NAT Gateway only appears in that AZ's route table — no cross-AZ NAT dependency.
  • Flow Logs test: confirm log records appear in CloudWatch Logs within a few minutes of test traffic, including a REJECT record for the blocked direct-access attempt above.

09 Monitoring & Observability

VPC Flow Logs are the primary observability surface for a network-only assignment — there's no application yet to monitor. We watch for REJECT records against the private subnets specifically, since any REJECT there is either a misconfiguration being caught by the NACL (good) or a sign that something in the private tier is trying to reach somewhere it shouldn't (worth investigating).

10 Production Incident

Design review, two days later

Ananya's team runs a routine review of the new VPC before sign-off and flags something: the private route tables show a route to 0.0.0.0/0 via NAT Gateway, which is correct — but a review of the account's CloudTrail history shows someone briefly attached an Internet Gateway route directly to private-rt-a during testing yesterday, then removed it. Nothing was compromised, but it means for a window of time yesterday, private-a had a live path to the internet.

Investigation

bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=CreateRoute \
  --query "Events[].[EventTime,Username,CloudTrailEvent]" --output table

CloudTrail shows an engineer manually ran aws ec2 create-route against private-rt-a pointing at the IGW while debugging an unrelated connectivity issue, intending it as temporary, and manually removed it afterward — but never went back through Terraform.

Root Cause

A manual, out-of-band change made directly against AWS instead of through the Terraform-managed configuration. Because Terraform wasn't re-applied, terraform plan would have shown this as drift if anyone had run it during that window — but nobody did, so the gap was only caught by a manual CloudTrail review.

Immediate Fix

Confirmed the manual route was already removed; ran terraform plan immediately to confirm current state now matches code with zero drift.

Permanent Fix

Restricted the IAM permissions of engineers who don't own this Terraform stack so they cannot call ec2:CreateRoute directly against production route tables — debugging should happen in a scratch/dev VPC, not by mutating the production network by hand.

Monitoring Improvement

Added a scheduled terraform plan (via CI, introduced properly in Assignment 14) that runs nightly and alerts if any drift is detected, so manual changes like this surface automatically instead of relying on someone remembering to check CloudTrail.

Lessons Learned

  • Terraform only protects you if it's the only path to making changes — manual console/CLI access to the same resources is a standing risk.
  • Drift detection needs to be scheduled and automatic, not something someone has to remember to run.

15 Acceptance Criteria

  • VPC spans two Availability Zones with one public and one private subnet per AZ
  • Private subnets have zero route to an Internet Gateway; outbound-only via per-AZ NAT Gateway
  • An instance placed in a private subnet has no public IP by default

16 Practice Challenge

Ananya comes back: "Good network. Now — what if an engineer's laptop needs to reach an instance in the private subnet for legitimate debugging, without opening it to the whole internet and without giving out a permanent public IP anywhere?"

Requirement: Add a way for one specific, known IP (an engineer's office/VPN IP) to reach instances in the private subnets, without changing the private subnets' "no route to IGW" property.

Acceptance Criteria: Private subnets still have zero IGW route. The access path is scoped to a specific source IP, not 0.0.0.0/0. No permanent public IP is added to any private instance.

Hints: Think about where the "entry point" for legitimate access should live relative to the public/private boundary you already built.

Challenge Solution

Add a small bastion host (or, better in a modern account, AWS Systems Manager Session Manager with no bastion at all) — a single instance in a public subnet with a security group allowing SSH only from the engineer's specific IP/32. Engineers SSH into the bastion first, then SSH again from the bastion into the private instance using its private IP. The private subnet's route table is completely untouched — the private instance still has no route to the internet; the bastion is simply another resource that happens to sit inside the same VPC and can reach it over the VPC's internal routing, which works regardless of the private subnet's internet routing. The SSM Session Manager variant is actually preferable and removes the need for a bastion or any open SSH port at all — we build that properly once IAM and Systems Manager are covered in more depth in a later assignment.

17 Interview Preparation

Q1 · NetworkingWhat actually makes a subnet "public" in AWS — is it a setting on the subnet itself?

No — there's no literal "public" flag on the subnet resource itself (aside from the auto-assign-public-IP setting, which is convenience, not the security boundary). A subnet is public purely because its associated route table has a route sending 0.0.0.0/0 traffic to an Internet Gateway. Change the route table association and the exact same subnet becomes private.

Follow-up: "So could I make a 'public' subnet private without touching the subnet resource at all?" — Yes, exactly — disassociate it from the public route table and associate it with a private one; the subnet's CIDR and AZ never change.
Q2 · SecurityWhy use both security groups and network ACLs instead of just security groups?

Defense in depth. Security groups are stateful and attached at the instance/ENI level — a single misconfigured security group is a single point of failure for that instance's exposure. NACLs are stateless, apply at the subnet level, and act as a second, independent layer — so a mistake in one security group doesn't automatically expose the whole subnet, because the NACL still has to allow the traffic too.

Follow-up: "Why 'stateless' for NACLs specifically matter?" — Because you must explicitly allow both the request AND the response traffic (e.g. ephemeral port range for return traffic) — security groups handle that automatically since they track connection state.
Q3 · Production ScenarioHow would you detect if someone manually changed a route table outside of Terraform?

Two ways: reactively, via CloudTrail — CreateRoute/ReplaceRoute events show exactly who changed what and when. Proactively, by scheduling terraform plan to run regularly (e.g. nightly in CI) and alerting if it reports any drift — a plan showing unexpected changes means the real infrastructure no longer matches the code, regardless of why.

Follow-up: "What would you do if you found drift like this in a live production VPC?" — Investigate via CloudTrail before touching anything, understand whether the drifted state is currently safe, then either update Terraform to match a legitimate change or run apply to correct back to the intended state — never blindly apply without understanding what changed and why first.
Q4 · Cost OptimizationWhen would one shared NAT Gateway be the right call instead of one per AZ?

When the workload's availability requirement doesn't actually demand AZ-independent outbound paths — for example, a dev/test environment where a temporary loss of outbound internet during an AZ event is an acceptable trade-off for lower cost. The decision should follow the stated availability requirement, not a blanket "always use N NAT Gateways" rule.

Follow-up: "How would you phase this — start with one, add more later?" — Yes, that's reasonable for a dev environment: start with a single shared NAT Gateway, and revisit per-AZ NAT Gateways only if/when that environment's requirements change to demand true AZ independence.
Q5 · TerraformWhy use count with a list variable here instead of writing four separate subnet resource blocks?

count paired with indexing into var.public_subnet_cidrs and var.azs lets one resource block generate N subnets from N list entries — adding a third AZ later means adding one CIDR and one AZ to the variables, not writing new resource blocks. It keeps the code's size proportional to genuine complexity, not to how many subnets happen to exist today.

Follow-up: "What's a downside of count versus for_each here?" — count indexes by position, so inserting an element in the middle of the list (rather than appending) can cause Terraform to see it as changing every subsequent resource; for_each keyed by a stable name avoids that. We'll use for_each once we move to reusable modules in Assignment 13.
Q6 · Manager RoundSecurity wants two NAT Gateways for availability; Finance is asking why the network bill doubled. How do you handle that conversation?

I'd bring both stakeholders the same trade-off table I used to make the decision — cost delta, what specifically breaks with a single shared NAT Gateway during an AZ event, and let the actual availability requirement (which came from the business, via Security) drive the decision rather than defaulting to either "cheapest" or "safest" without naming the trade-off out loud. If the availability requirement is real and documented, the cost is the cost of meeting it — but that should be a visible decision, not something Finance discovers after the fact.

Follow-up: "What would make you revisit that decision later?" — If the workload turned out to be far less availability-sensitive than assumed, or if AWS introduced a cheaper HA NAT option — either would be a legitimate reason to reopen the trade-off, not a reason to have skipped the conversation the first time.
