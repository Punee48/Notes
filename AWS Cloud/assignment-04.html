Building Reliable S3 and EBS Storage & Backup Workflows

Two workloads are now live — Raj's reconciliation job and Karthik's quote portal. Neither has a real backup story yet: reports could be deleted or overwritten with no way back, and the app instance's disk has never been snapshotted. Finance also wants to know why the S3 bucket's storage bill keeps climbing.

Progress: Assignment 4 of 25

01 Production Story

Finance — Deepa Krishnan

"I'm looking at this month's AWS bill and the S3 line item has grown every single month since Assignment 1 went live. Nothing's being deleted, apparently — is that expected?"

Infrastructure Manager — Priya Nandan

"Separately — I asked Karthik what happens if the quote portal's EC2 instance disk gets corrupted, and the honest answer was 'we'd have to rebuild it from scratch and lose whatever's on it.' That's not acceptable for something customer-facing. And on the reconciliation side — what happens if the report-writing script has a bug and overwrites three months of good reports with garbage in one bad run? Right now, nothing stops that and nothing gets us the old version back. Fix both."

Why this is Assignment 4

Assignment 1 created an S3 bucket with versioning already enabled — but versioning alone with no lifecycle policy is exactly why Deepa's bill keeps growing: every overwritten object keeps every old version forever, billed forever. Assignment 3 created an EC2 instance with an EBS root volume that has never been backed up. This assignment fixes both: S3 lifecycle rules that make versioning sustainable, and an automated EBS snapshot schedule.

03 Architecture Design

Two independent backup mechanisms for two different kinds of data: S3 lifecycle management for object versions (the reconciliation reports), and Amazon Data Lifecycle Manager for EBS snapshots (the app instance's disk). Neither needs any new compute or network component — this is entirely a policy/configuration layer on top of what Assignments 1 and 3 already built.

Object writtenDay 0 · Standard
Overwrittenold version kept
Day 30old version → Standard-IA
Day 90old version → Glacier IR
Day 365old version expired/deleted

Only non-current (old, overwritten) versions move through this lifecycle — the current version of every object stays in Standard storage, fully and immediately readable, exactly as it is today. This is the detail that makes the policy safe: nothing about today's data access pattern changes; only the cost of keeping history around changes.

EBS Snapshot Architecture

A Data Lifecycle Manager (DLM) policy targets the app instance's volume by tag, takes a snapshot daily, and automatically deletes snapshots older than the retention window — no Lambda function or cron job required, since DLM is a native, managed AWS scheduler for exactly this job.

04 Architecture Decision Making

Decision: S3 Storage Class Transition Path

ClassRetrievalRelative CostUse here
S3 StandardImmediateHighestCurrent version of every object — actively used
S3 Standard-IAImmediate, per-GB retrieval fee~45% cheaper storageOld versions 30–90 days old — rarely accessed but occasionally needed
S3 Glacier Instant RetrievalImmediate, higher retrieval fee~68% cheaper storageOld versions 90–365 days old — audit/recovery only
Expire (delete)—ZeroOld versions past 365 days — no business or compliance reason to keep them longer

Decision: the transition path above. Deep Archive was considered and rejected — its multi-hour retrieval time is a poor fit for "we might need last quarter's report during an audit conversation this afternoon," which Glacier Instant Retrieval still satisfies at a much lower cost than Standard.

Decision: DLM vs. Manual Snapshots vs. AWS Backup

Manual snapshotData Lifecycle ManagerAWS Backup
SchedulingNone — someone has to rememberNative tag-based scheduling, built for exactly EBS/AMICentralized, cross-service (EBS, RDS, DynamoDB, EFS...) with one policy engine
Fits this needNo — exactly the problem being fixedYes — this is a single-service (EBS), straightforward daily-snapshot needOverkill for one EBS volume; earns its complexity once multiple services need centralized backup (introduced later once RDS is in the picture)

Decision: DLM for this assignment. AWS Backup becomes the right answer once we're coordinating backup policy across EBS and RDS and other services from one place — worth revisiting once the database assignment (8) adds a second thing to back up.

05 AWS Console — Manual Steps

  1. Add a lifecycle rule to the existing reconciliation bucket. S3 console → select the bucket from Assignment 1 → Management tab → Create lifecycle rule → scope: apply to all objects → under "Noncurrent version transitions," add Standard-IA at 30 days and Glacier Instant Retrieval at 90 days → under "Noncurrent version expiration," set 365 days.
  2. Enable default encryption and Block Public Access. Same bucket → Properties → Default encryption → enable SSE-S3 (or SSE-KMS if a customer-managed key is required later) → Permissions tab → confirm all four "Block Public Access" settings are ON (they're on by default for new buckets, but confirm explicitly rather than assume).
  3. Tag the app instance's EBS volume. EC2 console → Volumes → select the app instance's root volume → Tags → add Backup = daily. DLM policies target by tag, so this is what makes the volume discoverable to the policy created next.
  4. Create the DLM lifecycle policy. EC2 console → Lifecycle Manager → Create lifecycle policy → resource type EBS volume → target tag Backup = daily → schedule: daily at a chosen time → retention: keep 7 most recent snapshots → assign the IAM role DLM needs (AWS offers a default service-linked role for this).
  5. Verify. Wait for the first scheduled run (or trigger manually if the console offers it) → Snapshots → confirm a new snapshot tagged by the DLM policy appears against the app instance's volume.

07 Terraform Implementation

main.tf — S3 Lifecycle, Encryption, Public Access Block

main.tf (part 1 of 2)
resource "aws_s3_bucket_server_side_encryption_configuration" "reconcile" {
  bucket = aws_s3_bucket.reconcile_bucket.id  # references Assignment 1's bucket resource
  rule {
    apply_server_side_encryption_by_default { sse_algorithm = "AES256" }
    # SSE-S3 (AES256) — AWS-managed keys, no extra KMS cost or key management
    # overhead. Sufficient here; SSE-KMS is revisited once compliance work in
    # Assignment 23 may require customer-managed keys specifically.
  }
}

resource "aws_s3_bucket_public_access_block" "reconcile" {
  bucket                  = aws_s3_bucket.reconcile_bucket.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
  # All four set true explicitly rather than relying on the account-level
  # default — this bucket's security posture doesn't depend on account-wide
  # settings someone else might change later.
}

resource "aws_s3_bucket_lifecycle_configuration" "reconcile" {
  bucket = aws_s3_bucket.reconcile_bucket.id

  rule {
    id     = "noncurrent-version-management"
    status = "Enabled"

    noncurrent_version_transition {
      noncurrent_days = 30
      storage_class   = "STANDARD_IA"
    }
    noncurrent_version_transition {
      noncurrent_days = 90
      storage_class   = "GLACIER_IR"
    }
    noncurrent_version_expiration {
      noncurrent_days = 365
    }
    # All three actions apply ONLY to noncurrent (old, overwritten) versions —
    # the current/live version of every object is untouched by this rule,
    # which is exactly why this doesn't change how the reconciliation job
    # reads today's report.
  }
}

main.tf — EBS Snapshot Automation via DLM

main.tf (part 2 of 2)
resource "aws_ebs_volume" "app_root_tag" {
  # NOTE: the root volume itself is created implicitly by aws_instance.app
  # from Assignment 3. We tag it via aws_ec2_tag rather than redefining the
  # volume resource, since Terraform doesn't manage an instance's root
  # volume as a separate top-level resource by default.
}

resource "aws_ec2_tag" "app_volume_backup_tag" {
  resource_id = data.aws_ebs_volume.app_root.id
  key         = "Backup"
  value       = "daily"
}

data "aws_ebs_volume" "app_root" {
  filter {
    name   = "attachment.instance-id"
    values = [aws_instance.app.id]
  }
  filter {
    name   = "attachment.device"
    values = ["/dev/xvda"]
  }
}

resource "aws_iam_role" "dlm_role" {
  name = "dlm-lifecycle-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "dlm.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy_attachment" "dlm_policy" {
  role       = aws_iam_role.dlm_role.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSDataLifecycleManagerServiceRole"
  # AWS-managed policy scoped specifically to DLM's snapshot/delete actions —
  # no need to hand-write a custom policy for a well-defined AWS service role.
}

resource "aws_dlm_lifecycle_policy" "app_daily_snapshot" {
  description        = "Daily snapshot of quote-portal app root volume"
  execution_role_arn = aws_iam_role.dlm_role.arn
  state              = "ENABLED"

  policy_details {
    resource_types = ["VOLUME"]

    target_tags = {
      Backup = "daily"
      # Matches the tag applied above — DLM discovers volumes by tag, not by
      # explicit ID, so any future volume tagged the same way is auto-included.
    }

    schedule {
      name = "daily-snapshot-schedule"
      create_rule {
        interval      = 24
        interval_unit = "HOURS"
        times         = ["03:00"]
      }
      retain_rule {
        count = 7
        # Keeps the 7 most recent snapshots (one week); older ones are auto-
        # deleted by DLM itself — no separate cleanup job needed.
      }
      tags_to_add = { SnapshotCreator = "DLM" }
      copy_tags    = true
    }
  }
}

08 Validation & Testing

  • Lifecycle test: overwrite a test object in the bucket twice, then confirm via aws s3api list-object-versions that both the current and noncurrent versions exist and are retrievable by version ID.
  • Encryption test: aws s3api head-object on any object confirms ServerSideEncryption: AES256 is present without having specified it at upload time.
  • Public access test: attempt to make an object public via a bucket policy change — must be rejected by the Block Public Access settings, proving the control actually blocks rather than just warns.
  • DLM test: confirm a snapshot with the SnapshotCreator=DLM tag appears against the app volume within 24 hours, or trigger an on-demand policy run if testing without waiting a full day.
  • Restore test: create a new EBS volume from the most recent snapshot and confirm it mounts with the expected data — a snapshot that's never been test-restored isn't a verified backup, it's an assumption.

10 Production Incident

Three weeks after go-live

Raj reports that a bug in a recent reconciliation script deployment overwrote two weeks of good reports with malformed output before anyone noticed. Merchandising needs the original good reports back today.

Investigation

bash
aws s3api list-object-versions \
  --bucket <bucket-name> --prefix "reports/" \
  --query "Versions[?Key=='reports/2026-07-20.csv']" --output table

The command returns multiple versions per affected key — the malformed current version plus the good noncurrent version from before the bad deployment, exactly as versioning was designed to preserve.

Root Cause

A code bug in the reconciliation script (unrelated to storage/backup configuration) wrote malformed data. This is included as an incident here specifically because it's the first real test of whether the versioning/lifecycle setup actually pays off in practice.

Immediate Fix

bash
# Restore a specific object to its prior good version by copying that
# version ID over the current one (S3 has no in-place "revert" operation —
# a copy is how you make an old version the new current version)
aws s3api copy-object --bucket <bucket-name> \
  --copy-source "<bucket-name>/reports/2026-07-20.csv?versionId=<good-version-id>" \
  --key reports/2026-07-20.csv

Repeated per affected object across the two-week window to fully restore Merchandising's data.

Permanent Fix

Not a storage-layer fix this time — the real fix is upstream, in the reconciliation script's own output validation (flagged back to Raj's team) — but this incident is exactly why the noncurrent-version retention window is 365 days and not something shorter: a two-week-old bug being caught late was still well within the recovery window.

Lessons Learned

  • Versioning is only useful if the retention window is long enough to cover realistic "how long before someone notices" timelines — a 7-day expiration would have already lost this data.
  • S3 has no "undo" — recovery is always a copy-forward of an old version, worth knowing before you're doing it under time pressure.

16 Practice Challenge

Priya comes back: "What if someone — accidentally or maliciously — deletes an object entirely, not just overwrites it? Does versioning even help with that?"

Requirement: Prevent an object from being permanently, irrecoverably deleted from the reconciliation bucket, even by someone with delete permissions.

Acceptance Criteria: A "delete" action against a versioned object must still leave the object recoverable. A separate, harder-to-invoke action should be required to truly, permanently purge data.

Hints: What does S3 versioning actually do when you call DeleteObject on a versioned bucket, as opposed to a non-versioned one? What additional bucket-level feature adds a time-boxed grace period on top of that?

Challenge Solution

In a versioned bucket, a normal DeleteObject call doesn't actually erase data — it adds a "delete marker" as the new current version, while the previous version remains in the bucket, fully recoverable by removing the delete marker or restoring the prior version ID. True permanent deletion requires a separate call specifying the exact version ID to purge — a materially different, harder-to-invoke action than an everyday delete. For additional protection against even that, enable S3 Object Lock in governance or compliance mode with a retention period, which prevents version deletion outright until the retention period expires, even for an IAM principal that otherwise has delete permissions — the strongest guarantee available, and the right answer if Priya's concern extends to malicious/insider deletion, not just accidental.

17 Interview Preparation

Q1 · AWS FundamentalsDoes enabling S3 versioning cost anything by itself?

Not directly — enabling versioning has no charge on its own. The cost comes from what versioning causes: every overwritten or deleted object keeps its prior versions in storage, and you pay standard storage rates for all of them unless a lifecycle policy manages that growth. This is exactly the gap this assignment closed.

Follow-up: "Could you have unbounded cost growth even with a lifecycle policy?" — Only if the policy's expiration action is missing or set too far out relative to actual write frequency — the policy bounds the cost, but only if its retention window is deliberately chosen, not left at "forever" by default.
Q2 · SecurityWhat's the difference between S3 default encryption and Block Public Access, and why do you need both?

They protect against different things. Default encryption ensures data at rest is encrypted regardless of who uploaded it or how — protects against unauthorized access to the underlying storage. Block Public Access prevents the bucket or its objects from ever being made publicly reachable, regardless of any bucket policy or ACL someone might apply — protects against exposure. A bucket can be fully encrypted and still be world-readable if Block Public Access isn't enabled, and vice versa — they're independent controls addressing independent risks.

Follow-up: "If someone explicitly needs a public bucket later — say, for static website hosting — what would you do?" — Explicitly disable Block Public Access only on that specific bucket, as a deliberate, reviewed exception — never as an account-wide default.
Q3 · Production ScenarioSomeone reports an important S3 object is "gone." Walk through your recovery steps.

First confirm the bucket has versioning enabled at all — if not, this may be genuinely unrecoverable and that's a hard truth to deliver. If it does, run list-object-versions on that key to see whether there's a delete marker (meaning it was "deleted," recoverable) versus the object having actually never existed or been permanently purged. If a delete marker exists, remove it or copy the prior version back into place as the new current version.

Follow-up: "What if list-object-versions shows nothing at all for that key?" — That means either the key never existed as typed (check for a typo/prefix mismatch first) or it was permanently purged via a version-specific delete — the latter is unrecoverable without Object Lock having been enabled beforehand.
Q4 · Cost OptimizationWhy Glacier Instant Retrieval instead of regular Glacier or Glacier Deep Archive for old report versions?

Regular Glacier and Deep Archive both require an explicit restore request with a retrieval delay ranging from minutes to many hours before the data is accessible again — fine for true archival, poor fit for "we might need last quarter's report during a same-day audit conversation." Glacier Instant Retrieval gives nearly all of the storage-cost savings of the deeper tiers while keeping millisecond retrieval, which matches how this data actually gets accessed in practice — rarely, but without notice.

Follow-up: "When would Deep Archive actually be the right choice?" — Data with a genuinely long, known-rare access pattern and a real tolerance for retrieval delay — e.g. multi-year regulatory records nobody expects to touch except in a formal audit with lead time.
Q5 · TerraformWhy is EBS snapshot automation done via a separate DLM resource instead of an attribute on the aws_instance resource?

Snapshot scheduling is a lifecycle policy that operates independently of the instance's own lifecycle — the instance could be terminated and recreated while the snapshot policy (and its historical snapshots) persists untouched, since it targets by tag rather than by a hard reference to one specific instance. Coupling it directly to the instance resource would mean losing snapshot history the moment the instance is replaced, which defeats the purpose of a backup.

Follow-up: "What happens to existing snapshots if you delete the aws_dlm_lifecycle_policy resource?" — The policy itself is deleted (no more new snapshots scheduled), but existing snapshots it already created are untouched — Terraform doesn't cascade-delete data resources a policy created, only the policy resource itself.
Q6 · Manager RoundFinance wants to cut backup/versioning retention to save cost. How do you have that conversation?

I'd bring the actual incident data — this exact reconciliation bug was caught two weeks after the fact and was still recoverable because the retention window was 365 days, not 7 or 30. I'd frame the retention window as directly tied to "how long could a real problem go unnoticed," not as an arbitrary number, and let Finance weigh the storage cost (which, after the lifecycle policy, is already a fraction of the original unbounded growth) against a concrete example of what a shorter window would have cost the business in lost, unrecoverable data.

Follow-up: "What if Finance still wants it shorter after that?" — That's a legitimate business risk trade-off for them to make with full information — my job is to make sure the trade-off is visible and quantified, not to unilaterally decide it, and to document the decision so it isn't silently reversed later without anyone remembering why 365 days was chosen.
