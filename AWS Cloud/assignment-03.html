01 Production Story

Application Team — Karthik Iyer

"Network's approved, thanks. Now I need somewhere to actually run the quote portal — it's a Node.js app, stateless, serves an HTTP health endpoint at /health. We'll eventually run more than one copy of it for redundancy, but let's get one working end to end first: customer hits our domain over HTTPS, request lands on the app, app responds. And per Ananya's rules, the actual app server can't have a public IP — so whatever sits in front of it in the public subnet needs to be the only thing customers ever actually touch."

Why this is Assignment 3

We now have a network with a real public/private boundary and nothing running in either tier. This assignment is about the thing that sits exactly on that boundary — a load balancer in the public subnet forwarding to an application server that never has a public IP of its own. We're deliberately running a single EC2 instance behind the ALB, not an Auto Scaling Group yet — that's Assignment 7, once we've earned it by seeing what a single-instance failure actually looks like first.

03 Architecture Design

Customer BrowserHTTPS
↓
Application Load Balancerpublic subnets, both AZs · sg-alb
↓ HTTP :3000 (only from sg-alb)
EC2 App Instanceprivate subnet, AZ-A · sg-app
↓ health check GET /health every 30s
Target Grouptracks instance health, drives routing

The ALB terminates the customer's HTTPS connection and forwards plain HTTP to the app instance over port 3000 — internal traffic inside the VPC doesn't need its own TLS layer for this foundation assignment (we revisit end-to-end encryption once compliance requirements are introduced later). The target group is the object that actually tracks which registered instances are healthy; the ALB's listener rule just says "send matching requests to this target group," and the target group decides which specific instance(s) currently qualify.

Security Architecture — Security Group Chaining

Rather than writing the app's security group to allow port 3000 from a CIDR range, we reference the ALB's security group ID directly as the source. This means the app instance accepts traffic only from something that is itself a member of sg-alb — if a future engineer launches an unrelated EC2 instance in the same VPC, it cannot reach the app on port 3000 no matter what subnet or IP it has, because it isn't a member of the referenced security group.

04 Architecture Decision Making

Decision: ALB vs. NLB vs. Direct EC2 Exposure

Direct EC2Network Load BalancerApplication Load Balancer
Fits this workloadWould require a public IP on the app instance — violates Security's core rule outrightOperates at L4 — routes TCP, has no visibility into HTTP paths/headers/health at the app layerOperates at L7 — understands HTTP, can health-check /health, route by path later if needed
Health checkingNone — nothing in front to detect a dead instanceTCP-level only (port open or not)HTTP-level — can confirm the app actually returns 200 on /health, not just that the port is open
TLS terminationApp itself must handle TLS certsSupported (TLS listener) but no HTTP awareness beyond thatNative, plus HTTP→HTTPS redirect rules

Decision: Application Load Balancer. Direct EC2 exposure is disqualified immediately by the security requirement. Between ALB and NLB, this is an HTTP application where we specifically want an HTTP-aware health check (a port being open doesn't mean the app is actually serving correctly) — that alone makes ALB the right fit. NLB becomes the right answer later in the course for a non-HTTP protocol or extreme low-latency/high-throughput requirement, neither of which applies here.

05 AWS Console — Manual Steps

  1. Create the app security group. EC2 console → Security Groups → Create security group → name sg-app, VPC = quote-portal-vpc → no inbound rules yet (added after the ALB's security group exists, so we can reference it).
  2. Create the ALB security group. Create security group → name sg-alb → inbound: HTTPS (443) from 0.0.0.0/0, HTTP (80) from 0.0.0.0/0 (redirected to HTTPS by the listener rule, not left open as plain HTTP) → outbound: all traffic (default).
  3. Add the app's inbound rule referencing sg-alb. Go back to sg-app → Inbound rules → Edit → add rule: type Custom TCP, port 3000, source = sg-alb (search by security group ID, not a CIDR). This is the security-group-chaining step described above.
  4. Launch the app instance. EC2 → Launch instance → Amazon Linux 2023 → t3.micro → network: quote-portal-vpc, subnet private-a, disable auto-assign public IP → security group sg-app → user data: install Node.js and start the quote-portal app listening on port 3000 with a /health route.
  5. Create the target group. EC2 console → Target Groups → Create target group → target type "Instances" → protocol HTTP, port 3000, VPC quote-portal-vpc → health check path /health, healthy threshold 2, unhealthy threshold 2, interval 30s → register the app instance as a target.
  6. Create the ALB. Load Balancers → Create → Application Load Balancer → internet-facing → VPC quote-portal-vpc → map both public subnets (public-a, public-b) → security group sg-alb → listener HTTP:80 → default action: forward to the target group created above. (An HTTPS:443 listener with an ACM certificate is added once a domain/cert exists — noted as a follow-up, not blocking this lab.)
  7. Verify target health. Target Groups → select the group → Targets tab → confirm status transitions to healthy within about a minute of the instance passing its first couple of health checks.

06 AWS CLI

bash
# Create the ALB security group first (app SG needs to reference its ID)
SG_ALB=$(aws ec2 create-security-group \
  --group-name sg-alb --description "ALB ingress" --vpc-id $VPC_ID \
  --query 'GroupId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_ALB \
  --protocol tcp --port 80 --cidr 0.0.0.0/0

# Create the app security group referencing sg-alb as the source — not a CIDR
SG_APP=$(aws ec2 create-security-group \
  --group-name sg-app --description "App tier ingress" --vpc-id $VPC_ID \
  --query 'GroupId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_APP \
  --protocol tcp --port 3000 --source-group $SG_ALB

# Create the target group with an HTTP health check on /health
TG_ARN=$(aws elbv2 create-target-group \
  --name quote-portal-tg --protocol HTTP --port 3000 --vpc-id $VPC_ID \
  --health-check-path /health --healthy-threshold-count 2 \
  --unhealthy-threshold-count 2 --health-check-interval-seconds 30 \
  --query 'TargetGroups[0].TargetGroupArn' --output text)
Command / FlagMeaning
--source-group $SG_ALBSets the rule's source to a security group ID instead of a CIDR — this is the chaining mechanism, not achievable by CIDR alone since instances can change IPs
--healthy-threshold-count 2Number of consecutive successful checks before a target is marked healthy and starts receiving traffic
--health-check-interval-seconds 30How often the target group polls /health — combined with the thresholds, this determines how fast a failure is detected

07 Terraform Implementation

main.tf — Security Groups

main.tf (part 1 of 3)
resource "aws_security_group" "alb" {
  name   = "sg-alb"
  vpc_id = aws_vpc.main.id  # references the VPC resource from Assignment 2's Terraform

  ingress {
    description = "HTTP from internet (redirected to HTTPS by listener rule)"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  egress {
    from_port = 0
    to_port   = 0
    protocol  = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
  tags = { Name = "sg-alb" }
}

resource "aws_security_group" "app" {
  name   = "sg-app"
  vpc_id = aws_vpc.main.id

  ingress {
    description     = "App port, ALB only"
    from_port        = 3000
    to_port           = 3000
    protocol          = "tcp"
    security_groups   = [aws_security_group.alb.id]
    # security_groups (not cidr_blocks) is the security-group-chaining rule —
    # only network interfaces that are members of sg-alb can reach port 3000,
    # regardless of what subnet or IP they have.
  }
  egress {
    from_port = 0
    to_port   = 0
    protocol  = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
  tags = { Name = "sg-app" }
}

main.tf — Target Group & ALB

main.tf (part 3 of 3)
resource "aws_lb_target_group" "app" {
  name        = "quote-portal-tg"
  port        = 3000
  protocol    = "HTTP"
  vpc_id      = aws_vpc.main.id
  target_type = "instance"

  health_check {
    path                = "/health"
    healthy_threshold   = 2
    unhealthy_threshold = 2
    interval            = 30
    matcher             = "200"
    # matcher = "200" means ONLY an HTTP 200 counts as healthy — a 500 error
    # page served on /health would still fail the check, which is what we want.
  }
}

resource "aws_lb_target_group_attachment" "app" {
  target_group_arn = aws_lb_target_group.app.arn
  target_id        = aws_instance.app.id
  port             = 3000
}

resource "aws_lb" "main" {
  name               = "quote-portal-alb"
  internal           = false
  load_balancer_type = "application"
  security_groups    = [aws_security_group.alb.id]
  subnets            = aws_subnet.public[*].id
  # [*] passes BOTH public subnet IDs — an ALB requires subnets in at least
  # two AZs to be created at all, which is a built-in HA guarantee.
}

resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.main.arn
  port              = 80
  protocol          = "HTTP"

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.app.arn
  }
  # A production listener would be HTTPS:443 with an ACM certificate, and
  # this HTTP:80 listener would instead redirect to it. Left as HTTP-only
  # here since no domain/certificate exists yet for this lab.
}

output "alb_dns_name" {
  value = aws_lb.main.dns_name
  # AWS auto-generates a DNS name for the ALB — this is what you curl to
  # test, before any custom domain is wired up in Assignment 10 (Route 53).
}

08 Validation & Testing

  • End-to-end test: curl http://$(terraform output -raw alb_dns_name) returns the placeholder app response.
  • Health check test: Target group shows the instance as healthy in the console within ~60 seconds of launch.
  • Security test: attempt curl to the app instance's private IP on port 3000 from your own machine — must fail (no route in from outside the VPC at all, per Assignment 2).
  • Security-group-chaining test: launch a throwaway instance in the same VPC with an unrelated security group, SSH into it, and attempt curl to the app instance's private IP on port 3000 — must fail, proving the rule really is scoped to sg-alb membership, not just "anything inside the VPC."
  • Failure test: stop the app process on the instance manually (kill the Node process) — confirm the target group marks it unhealthy within two failed checks and the ALB starts returning a 502 rather than silently hanging.

10 Production Incident

Two days after go-live

Karthik reports customers intermittently see a "502 Bad Gateway" page. The target group console shows the instance flipping between healthy and unhealthy every few minutes rather than being consistently down.

Investigation

bash — from the instance
top
free -m
journalctl -u # (if running as a systemd service — for this lab, check the process directly)
ps aux | grep node

Memory usage on the t3.micro climbs steadily and the Node process is periodically OOM-killed and restarted by a watchdog script, which briefly fails health checks during each restart window — explaining the flapping pattern rather than a hard failure.

Root Cause

t3.micro's 1 GiB of RAM is undersized for the actual application once real traffic and dependencies were deployed (the placeholder app in this lab is intentionally trivial — Karthik's real app has a larger memory footprint). This is a capacity-planning gap, not a code bug.

Immediate Fix

Manually stopped and resized the instance to t3.small to restore stable service while a permanent fix is planned.

Permanent Fix

Updated the Terraform instance_type variable to t3.small as the new baseline, and flagged that this workload will need real Auto Scaling (Assignment 7) rather than a single hand-sized instance, since "guess the right instance size once" doesn't hold up as traffic grows.

Validation

Monitored UnHealthyHostCount over the following 24 hours — zero flaps after the resize.

Monitoring Improvement

Added a CloudWatch alarm on the instance's MemoryUtilization (via the CloudWatch agent, since EC2 doesn't report memory by default) so a memory-pressure trend shows up before it starts failing health checks, not just after.

Lessons Learned

  • A target flapping between healthy/unhealthy is a different failure signature than a hard-down target — it usually points to a resource-pressure or restart-loop issue, not a network problem.
  • EC2 doesn't report memory utilization to CloudWatch out of the box — you have to install the CloudWatch agent to see it at all, and its absence is easy to miss until you need it.

16 Practice Challenge

Karthik comes back: "We're about to demo this to the business, and I don't want a plain http:// URL with a random AWS DNS name on the screen. Can we at least get this on HTTPS?"

Requirement: Add an HTTPS listener to the ALB. It's fine to use a self-signed or ACM-issued certificate for a placeholder domain for this lab.

Acceptance Criteria: ALB accepts HTTPS:443 traffic and forwards to the existing target group; HTTP:80 requests are redirected to HTTPS rather than served directly.

Hints: You'll need an ACM certificate (even a manually-validated one for a test domain) and a second listener resource, plus a change to the existing HTTP listener's default action.

Challenge Solution

Request a certificate via aws_acm_certificate (or import an existing one), validate it, then add an aws_lb_listener resource on port 443 with protocol = "HTTPS", certificate_arn pointing at the validated cert, and the same forward default action to the existing target group. Change the existing HTTP:80 listener's default_action from forward to type = "redirect" with status_code = "HTTP_301" and protocol = "HTTPS", port = "443" — this is the standard pattern of "accept HTTP only to immediately bounce it to HTTPS," never serving real content over plain HTTP. Full Route 53 domain integration (so the ALB has a real hostname instead of the AWS-generated one) is Assignment 10's territory.

17 Interview Preparation

Q1 · AWS FundamentalsWhat's the difference between a listener, a listener rule, and a target group?

A listener is what the load balancer opens to accept connections on a given port/protocol (e.g. HTTPS:443). Listener rules attached to it decide, based on conditions like path or host header, which target group a given request goes to. The target group is the pool of actual backends plus the health check configuration — it's the layer that tracks which instances are currently eligible to receive traffic.

Follow-up: "When would you need more than one target group?" — Path- or host-based routing to different backend services behind the same ALB, e.g. /api/* to one target group and everything else to another — introduced properly once we build a multi-service architecture later in the course.
Q2 · SecurityWhy reference the ALB's security group as the source instead of the VPC's CIDR block?

A CIDR-based rule would allow anything inside that IP range to reach the app, including any other instance an engineer launches in the same VPC or subnet later — accidentally or otherwise. Referencing the ALB's security group ID scopes the rule to "only things that are members of this specific security group," which is a much tighter and more intentional boundary that doesn't erode as the VPC grows.

Follow-up: "Does this work across VPCs?" — No — security group references only work within the same VPC (or peered VPCs with specific configuration); it's not a general cross-account/cross-VPC mechanism.
Q3 · Production ScenarioA target is flapping between healthy and unhealthy in the console. What's your triage order?

First distinguish "the target never became healthy" from "it was healthy and started flapping" — the latter, as in the incident above, usually points to a resource or restart-loop issue on the instance rather than a network/security-group problem, since it worked at least once. I'd check instance-level metrics (CPU, memory if available) and application logs for restart or crash patterns before touching any network configuration.

Follow-up: "What if memory metrics aren't available at all?" — That's itself diagnostic: EC2 doesn't report memory to CloudWatch without the CloudWatch agent installed, so its absence tells you monitoring coverage has a gap worth closing regardless of what's actually causing the flapping.
Q4 · Cost OptimizationIs it ever worth skipping an ALB and exposing EC2 directly to save the fixed cost?

Only when there's no genuine requirement for HTTP-aware routing, health checking, or TLS termination at that layer — e.g. a truly single-purpose internal dev/test instance with no availability requirement. For anything customer-facing or requiring health-based failover, the ALB's fixed cost buys real operational and security value (nothing else gives you an HTTP-aware health check or a stable entry point independent of any one instance's lifecycle) — I wouldn't cut it purely to save the baseline charge.

Follow-up: "What's a cheaper alternative that still avoids direct exposure?" — A properly scoped bastion/SSM approach for internal-only tools, as covered in Assignment 2's challenge — different problem than a customer-facing HTTPS endpoint, though.
Q5 · TerraformWhy is aws_lb_target_group_attachment a separate resource instead of an attribute on the target group itself?

Decoupling target registration from the target group definition means the target group's configuration (health check, port, protocol) can be managed independently of which specific instances happen to be attached right now — which matters a lot once we move to Auto Scaling Groups in Assignment 7, where the ASG itself manages attachments dynamically rather than Terraform hardcoding a fixed instance ID.

Follow-up: "How does this change with an ASG instead of a static instance?" — The ASG resource gets a target_group_arns argument instead of individual attachment resources, and AWS handles registering/deregistering instances automatically as the group scales.
Q6 · Manager RoundHow do you decide when a single-instance deployment is acceptable versus needing redundancy from day one?

Against the actual stated availability requirement, not a default instinct either way. Here, Karthik explicitly said "let's get one working end to end first" — meaning the redundancy requirement is real but sequenced deliberately, not skipped. I flagged the single point of failure clearly in the architecture review rather than quietly shipping it as if it were the final state, so it's a known, tracked gap with a plan (Assignment 7) rather than a surprise found later.

Follow-up: "What if that incident had caused a customer-facing outage instead of just flapping?" — That would be a strong argument to pull the ASG work forward in priority rather than sequencing it later — the sequencing decision should be revisited against real production impact, not treated as fixed.
