01

Business Scenario

NovaStack Bank's Cloud Platform team provisions new EC2 instances for application teams roughly 15 times a week — a new UAT node, a scaled-out PROD instance, a short-lived DEV sandbox. Provisioning today is done by hand in the AWS console: instance launch, tagging (often inconsistent — a major driver of a recent cost-allocation audit finding that couldn't attribute 30% of compute spend to a cost center), security group attachment, and manual onboarding into monitoring and patching.

Finance and Cloud Platform leadership have jointly asked Automation Engineering to build an EC2 lifecycle automation: standardized, tag-enforced provisioning through a self-service request, automatic enrollment into the patching (Project 2) and health-check (Project 4) pipelines on launch, and a safe, auditable decommissioning path.

Why this can't stay manualInconsistent manual tagging is directly why 30% of spend can't be attributed — that's a real finance and audit problem, not just an efficiency one. Automated, enforced tagging at launch time is the only reliable fix.

This project is the first to work directly with the AWS API via Ansible's amazon.aws collection, and it closes the loop with Projects 2 and 4 by auto-registering new instances into existing pipelines rather than waiting for the next scheduled discovery.

Authentication

Ansible Design

Architect's note

Tag enforcement happens as a pre-flight assertion before the instance is ever launched, not a post-launch cleanup step — failing closed before spending money is a materially better design than launching first and fixing tags after.

Code & Roles

roles/ec2_provision/tasks/main.yml 
---
# Fail BEFORE launch if any mandatory tag is missing from the request --
# this is the actual fix for the audit finding, not a nice-to-have.
- name: Assert all mandatory tags are present in the request
  ansible.builtin.assert:
    that:
      - request_tags.cost_center is defined
      - request_tags.environment is defined
      - request_tags.owner is defined
      - request_tags.application is defined
      - request_tags.data_classification is defined
    fail_msg: "Provisioning refused: one or more mandatory tags missing from request. No instance launched, no cost incurred."

- name: Launch EC2 instance from the approved environment AMI baseline
  amazon.aws.ec2_instance:
    name: "{{ request_tags.application }}-{{ request_tags.environment }}-{{ instance_sequence }}"
    image_id: "{{ approved_ami_baselines[request_tags.environment] }}"
    instance_type: "{{ requested_instance_type }}"
    vpc_subnet_id: "{{ environment_subnets[request_tags.environment] }}"
    security_groups: "{{ default_security_groups[request_tags.environment] }}"
    tags: "{{ request_tags | combine({'ManagedBy': 'ansible-ec2-lifecycle', 'ProvisionedDate': ansible_date_time.date}) }}"
    wait: true
  register: launch_result

- name: Register new instance into the health-check catalog (Project 4)
  ansible.builtin.lineinfile:
    path: "{{ health_check_catalog_path }}"
    line: "  - name: {{ launch_result.instances[0].tags.application }}\n    host: {{ launch_result.instances[0].private_ip_address }}"
  delegate_to: localhost
  # This is what closes the loop with Project 4 -- the new instance
  # is monitored from minute one, not from the next manual discovery pass.

- name: Register new instance into the patch inventory tag group (Project 2)
  amazon.aws.ec2_tag:
    resource: "{{ launch_result.instances[0].instance_id }}"
    tags:
      PatchGroup: "{{ request_tags.environment }}-standard"
  delegate_to: localhost

Execution flow, in plain terms

The assertion at the top means an incomplete request never results in a launched (and billed) instance — it fails fast, before AWS is even called. Once launched, the instance is immediately wired into both the patch pipeline's dynamic inventory tags and the health-check catalog, so it's fully managed from the moment it exists rather than waiting to be "discovered" later.

Rollback Procedure

Disable the ServiceNow catalog item to fall back to manual console provisioning; already-provisioned instances are unaffected since tagging and registration happened at launch time, not via an ongoing process.

Troubleshooting

Instance launches but doesn't appear in health-check catalog Symptom: New instance is up but not showing in the Project 4 dashboard.
Root cause (typical): Catalog registration task ran before the instance's private IP was fully allocated.
Fix: Add an explicit wait/retry on IP availability before the registration task; re-run registration manually for the affected instance in the interim.

Interview Preparation

Why assert on tags before launch instead of tagging after?
Tagging after launch still incurs cost for an untracked instance if the process fails partway — asserting first means an incomplete request costs the bank nothing and fails with a clear, immediate message instead of creating exactly the untracked-spend problem we were asked to fix.
How does this integrate with the patching and health-check projects you built earlier?
Provisioning directly appends the new instance into both pipelines' catalogs at launch time — Project 2's patch tag group and Project 4's health-check catalog — so there's no gap between "instance exists" and "instance is managed," instead of waiting for their next scheduled discovery cycle.
