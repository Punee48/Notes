Implementing VPC Endpoints and Controlled Egress

Right now, every time the app tier talks to S3 or Secrets Manager, that traffic leaves the VPC through the NAT Gateway and travels over the public AWS network backbone before it ever reaches those services — even though both are AWS services in the same region. Ananya wants to know why "internal" traffic is taking the most exposed possible path.

Difficulty: Intermediate Domain: Insurance Services: VPC Endpoints · PrivateLink · Endpoint Policies IaC: Console + CLI + Terraform Est. lab time: 2.5–3.5 hrs
Progress: Assignment 11 of 25

01 Production Story

Security Team — Ananya Reddy

"I was reviewing VPC Flow Logs and noticed every S3 and Secrets Manager call from the app tier is routing out through the NAT Gateway, onto the public internet path, before it reaches an AWS service that's sitting in the exact same region as us. That's more exposure than necessary for traffic that never needed to leave AWS's own network at all. And separately — I want to know exactly what the app tier can reach out to on the internet. Right now the security group allows all outbound traffic to anywhere. That's too broad for a production system handling customer data."

Why this is Assignment 11

Every AWS-to-AWS call the app tier makes — to S3 (Assignment 1's bucket, Assignment 4's lifecycle-managed objects), to Secrets Manager (Assignment 5's rating-API key and Assignment 8's DB credentials) — currently takes the long way around through the NAT Gateway. A VPC Endpoint creates a private, direct path from inside the VPC straight to an AWS service, without touching the internet or even the NAT Gateway at all. We also tighten the app tier's security group to a specific, named allowlist instead of "anywhere," closing Ananya's second concern in the same pass.

03 Architecture Design

App Instance (sg-app)Assignment 7's ASG
↓ private, AWS backbone only
S3 Gateway Endpointroute-table-based, no ENI, free
↕ separately
Secrets Manager Interface EndpointPrivateLink ENI in each private subnet
↓ only remaining NAT-routed traffic
NAT Gatewayrating API + OS patching only, egress-restricted

Two different endpoint mechanisms are in play here, and they work differently under the hood. The S3 Gateway Endpoint isn't a network device at all — it's a special route-table entry that AWS resolves internally, adding a target for S3's IP ranges directly into the private subnets' route tables. The Secrets Manager Interface Endpoint is a real Elastic Network Interface (ENI) with a private IP, deployed via AWS PrivateLink into each private subnet, and DNS resolution for secretsmanager.ap-south-1.amazonaws.com is transparently redirected to that private ENI instead of the public endpoint.

04 Architecture Decision Making

Decision: Gateway Endpoint vs. Interface Endpoint — Not a Free Choice, AWS Decides Per Service

Gateway EndpointInterface Endpoint (PrivateLink)
Supported servicesOnly S3 and DynamoDBMost other AWS services, including Secrets Manager, KMS, EC2, SSM
MechanismRoute table entry — no ENI, no hourly chargeENI with a private IP per subnet — hourly charge per endpoint per AZ, plus per-GB data processing
DNS behaviorNo DNS change needed — route table handles it transparentlyRequires "Private DNS" enabled on the endpoint so existing service hostnames resolve to the private IP automatically

This isn't really a decision we get to make freely — S3 only supports the Gateway type, Secrets Manager only supports the Interface type. What we do decide is to use whichever type each service supports, rather than routing either through NAT just because it's simpler to reason about one mechanism instead of two.

Decision: Endpoint Policies — Should Every Endpoint Trust Everything?

By default, a VPC Endpoint has no restrictive policy — anything with network access to it and valid IAM permissions can use it to reach the service. We attach an explicit endpoint policy to the S3 Gateway Endpoint restricting it to only the specific buckets this VPC's workloads actually use (the reconciliation bucket and audit-logs bucket), so even a compromised instance inside this VPC can't use the endpoint as a path to some unrelated S3 bucket in the account or another account entirely.

05 AWS Console — Manual Steps

  1. Create the S3 Gateway Endpoint. VPC console → Endpoints → Create endpoint → service category "AWS services" → search s3 → select the Gateway type entry (com.amazonaws.ap-south-1.s3) → VPC quote-portal-vpc → route tables: select both private-tier route tables (from Assignment 2) → policy: custom, restricting to the reconciliation and audit-logs bucket ARNs specifically.
  2. Create the Secrets Manager Interface Endpoint. Create endpoint again → search secretsmanager → select the Interface type → VPC quote-portal-vpc → subnets: both private subnets (one ENI per AZ) → security group: a new sg-vpce allowing HTTPS (443) inbound from sg-app only → enable "Private DNS names" so the existing secretsmanager.ap-south-1.amazonaws.com hostname the app already uses resolves to the private endpoint automatically, with zero application code change.
  3. Tighten sg-app's egress rule. EC2 console → sg-app → Outbound rules → Edit → remove the blanket "all traffic to 0.0.0.0/0" rule → add specific rules: HTTPS (443) to the rating API's known IP range/prefix list, HTTPS (443) to sg-vpce, and HTTP/HTTPS to the OS patch repository's IP range if needed.
  4. Verify DNS resolution from inside an app instance. SSM into an instance → nslookup secretsmanager.ap-south-1.amazonaws.com → the returned IP should now be a private VPC IP (10.20.x.x), not a public AWS IP — confirming Private DNS is correctly redirecting the call.
  5. Confirm S3 traffic no longer transits NAT. VPC Flow Logs (Assignment 2/9) → filter for S3's IP ranges from the app subnet — should show zero flow records through the NAT Gateway's ENI for S3 traffic after the endpoint is live.

# Create the S3 Gateway Endpoint, attached to both private route tables
aws ec2 create-vpc-endpoint \
  --vpc-id $VPC_ID --service-name com.amazonaws.ap-south-1.s3 \
  --route-table-ids $PRIVATE_RT_A_ID $PRIVATE_RT_B_ID \
  --policy-document file://s3-endpoint-policy.json

# Create the Secrets Manager Interface Endpoint with Private DNS enabled
aws ec2 create-vpc-endpoint \
  --vpc-id $VPC_ID --service-name com.amazonaws.ap-south-1.secretsmanager \
  --vpc-endpoint-type Interface \
  --subnet-ids $PRIVATE_A_SUBNET_ID $PRIVATE_B_SUBNET_ID \
  --security-group-ids $SG_VPCE_ID \
  --private-dns-enabled

# Confirm DNS now resolves privately from inside the app instance
nslookup secretsmanager.ap-south-1.amazonaws.com

07 Terraform Implementation

main.tf — S3 Gateway Endpoint With a Restrictive Policy

main.tf (part 1 of 3)
resource "aws_vpc_endpoint" "s3" {
  vpc_id       = aws_vpc.main.id
  service_name = "com.amazonaws.${var.region}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = [aws_route_table.private[0].id, aws_route_table.private[1].id]
  # Both AZs' private route tables — this endpoint has no ENI or AZ concept
  # of its own; it's purely a routing target attached wherever needed.

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = ["s3:GetObject", "s3:PutObject", "s3:ListBucket"]
      Resource = [
        aws_s3_bucket.reconcile_bucket.arn,
        "${aws_s3_bucket.reconcile_bucket.arn}/*",
        aws_s3_bucket.audit_logs.arn,
        "${aws_s3_bucket.audit_logs.arn}/*"
      ]
      # Principal = "*" here is scoped down by RESOURCE, not principal — this
      # policy governs what the ENDPOINT itself will forward, regardless of who
      # asks; actual caller identity is still separately checked by each
      # bucket's own IAM/bucket policy. This is a second, independent layer —
      # same defense-in-depth pattern as the KMS key policy from Assignment 5.
    }]
  })
}

main.tf — Secrets Manager Interface Endpoint

main.tf (part 2 of 3)
resource "aws_security_group" "vpce" {
  name   = "sg-vpce"
  vpc_id = aws_vpc.main.id

  ingress {
    description     = "HTTPS from app tier only"
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]
  }
  egress { from_port = 0; to_port = 0; protocol = "-1"; cidr_blocks = ["0.0.0.0/0"] }
  tags = { Name = "sg-vpce" }
}

resource "aws_vpc_endpoint" "secretsmanager" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${var.region}.secretsmanager"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.vpce.id]
  private_dns_enabled = true
  # private_dns_enabled = true means the app's existing code — already
  # calling the standard secretsmanager..amazonaws.com hostname
  # since Assignment 5 — needs ZERO code change. DNS resolution alone
  # silently redirects it to the private endpoint.
}

08 Validation & Testing

  • Route table test: aws ec2 describe-route-tables on the private route tables shows a new route with the S3 prefix-list ID as destination and the Gateway Endpoint as target.
  • DNS test: from inside an app instance, nslookup secretsmanager.ap-south-1.amazonaws.com resolves to a private 10.20.x.x address.
  • Functional test: the app still successfully retrieves both secrets (rating API key, DB credentials) and reads/writes S3 objects — zero application code change required, confirming both endpoints are working transparently.
  • Flow log test: Flow Logs show zero S3/Secrets Manager traffic through the NAT Gateway's ENI after the endpoints are live — only the rating API traffic remains NAT-routed.
  • Negative test: temporarily attempt an outbound call from the app instance to an arbitrary, unlisted external host — must fail, confirming the tightened egress allowlist is actually enforced, not just documented.

10 Production Incident

Shortly after the egress tightening deployed

The reconciliation job from Assignment 1 — which shares the same VPC but runs on its own instance outside the ASG — starts failing. Its S3 uploads work fine, but its CloudWatch Logs delivery starts silently failing, and nobody notices until log gaps are spotted days later during a routine review.

Investigation

The reconciliation instance's own security group was tightened at the same time as sg-app's, using a copy-pasted egress ruleset — but CloudWatch Logs uses its own separate service endpoint (logs.ap-south-1.amazonaws.com), which wasn't included in either the S3 Gateway Endpoint (wrong service entirely) or the new Secrets Manager Interface Endpoint (also wrong service) — and the blanket NAT-routed egress that used to silently cover it was removed without a like-for-like CloudWatch Logs endpoint added in its place.

Root Cause

An incomplete audit of exactly which AWS services a workload calls before tightening its egress rules — S3 and Secrets Manager were the two explicitly named in this assignment's story, but CloudWatch Logs (added quietly back in Assignment 1) was overlooked entirely.

Immediate Fix

Temporarily restored broader egress on the reconciliation instance's security group to stop the log-gap bleeding while a proper fix was built.

Permanent Fix

Terraform addition
resource "aws_vpc_endpoint" "logs" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${var.region}.logs"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.vpce.id]
  private_dns_enabled = true
}
# A third Interface Endpoint, same pattern as Secrets Manager — added
# specifically because this incident surfaced the gap.

Validation

Re-tightened the reconciliation instance's egress, confirmed CloudWatch Logs delivery resumed with zero gaps over the following 48 hours.

Lessons Learned

  • Tightening egress requires a complete inventory of every AWS service a workload actually calls, not just the ones a specific security review happened to name — a partial list creates exactly this kind of silent gap.
  • A "silent" failure (logs stop arriving, nothing crashes) is more dangerous than a loud one — worth a specific alarm on log ingestion rate dropping to zero, not just on error rates.

17 Interview Preparation

Q1 · NetworkingWhat's the actual mechanical difference between a Gateway Endpoint and an Interface Endpoint?

A Gateway Endpoint is a route table entry — no network interface, no IP address of its own, and AWS resolves it internally as a routing target for a specific service's IP prefix list. An Interface Endpoint is a real ENI with a private IP address deployed into a subnet via AWS PrivateLink, and DNS (if Private DNS is enabled) is redirected to that ENI's IP instead of the service's public endpoint. Only S3 and DynamoDB support the Gateway type; nearly everything else that supports VPC Endpoints at all uses the Interface type.

Follow-up: "Why does that mechanical difference matter for cost?" — A route table entry has no infrastructure to run and bill for; an ENI is a provisioned resource with an hourly charge per AZ plus data processing — which is exactly why Gateway Endpoints are free and Interface Endpoints aren't.
Q2 · SecurityWhy give the S3 Gateway Endpoint its own policy document — doesn't the IAM role's own S3 policy already control access?

They're two independent layers, same defense-in-depth pattern used with the KMS key policy in Assignment 5. The IAM role's policy controls what that specific caller identity is allowed to do. The endpoint policy controls what the endpoint itself will forward, regardless of caller — so even if a role somewhere in the account had overly broad S3 permissions, traffic through THIS endpoint specifically is still capped to the buckets named in the endpoint policy. One control being correct doesn't make the other redundant.

Follow-up: "What would happen if the IAM policy allowed a bucket the endpoint policy didn't?" — The call would be denied — the endpoint policy is evaluated in addition to IAM, not instead of it, so the more restrictive of the two effectively wins for traffic passing through that endpoint.
Q3 · Production ScenarioAfter tightening egress rules, a workload starts silently failing on a service call nobody thought to check. How do you find every affected service before it becomes an incident?

Don't rely purely on a manual inventory from memory — that's exactly what missed CloudWatch Logs in this assignment's incident. Cross-reference against actual VPC Flow Log data filtered to the NAT Gateway's ENI over a representative time window (long enough to catch anything that only runs occasionally, like a nightly job) — the logs show ground truth about what's actually being called, which is more reliable than any mental or documented list.

Follow-up: "How would you catch this before it ever reached production?" — Deploy the egress tightening to a staging/dev environment carrying representative traffic first, and watch for any error spike or silent metric drop (like log ingestion rate) over a full operational cycle — including nightly/weekly jobs — before promoting the same change to production.
Q4 · Cost OptimizationIs it ever not worth adding a VPC Interface Endpoint for a given service?

Yes — if the traffic volume to that service is genuinely small, the Interface Endpoint's fixed hourly charge (times the number of AZs) could exceed what the equivalent NAT Gateway data-processing charge would have cost for that light traffic. The security argument (keeping traffic off the public path) can still justify it regardless of the cost comparison, but it's worth explicitly checking rather than assuming an endpoint always pays for itself — for high-traffic services like S3 and Secrets Manager in this assignment, it clearly does.

Follow-up: "How would you actually measure whether it paid off?" — Compare the NAT Gateway's per-GB data processing charge for that service's traffic volume before, against the Interface Endpoint's fixed hourly cost after — a direct, measurable comparison rather than an assumption.
Q5 · TerraformWhy does the Gateway Endpoint need no corresponding security group rule, while the Interface Endpoint does?

A Gateway Endpoint operates at the routing layer — traffic destined for S3's IP prefix gets redirected to it via the route table before security groups even become relevant to that hop in the same way. An Interface Endpoint is a real ENI sitting in a subnet, and like any ENI, it needs a security group controlling what can actually connect to it — which is why sg-vpce exists and why sg-app's egress rule references it explicitly.

Follow-up: "Does the app tier's security group need an explicit egress rule for the S3 Gateway Endpoint traffic at all?" — As long as sg-app allows general outbound HTTPS to wherever it's actually headed, the route table silently redirects S3-bound traffic to the endpoint instead of NAT — no endpoint-specific egress rule is required for the Gateway type the way it is for the Interface type.
Q6 · Manager RoundHow do you explain to Ananya that a security improvement caused an outage (the CloudWatch Logs gap), without it sounding like the whole initiative was a mistake?

I'd be direct that it was a real gap in execution, not a flaw in the underlying approach — the egress-tightening principle is correct and stays; what was incomplete was the service inventory behind it. I'd walk through exactly how the gap was found and closed, and the process change (cross-referencing against actual Flow Log data, not just a mental list) that prevents the same class of mistake next time a similar change ships. Framing it as "the security work surfaced its own gap and we fixed the gap" is both honest and accurate — it's not spin, it's what actually happened.

Follow-up: "What would you do differently before the next egress-tightening change?" — Run the Flow-Log-based service inventory FIRST, before writing any restrictive rule, rather than tightening first and discovering gaps reactively — the challenge in this assignment is exactly that inventory step, now moved earlier in the process going forward.
