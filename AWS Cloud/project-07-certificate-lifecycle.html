01

Business Scenario

NovaStack Bank runs roughly 900 internal TLS certificates across load balancers, application servers, and internal APIs, issued by an internal enterprise CA. Certificate expiry has caused three customer-facing outages in the past year — each one a case of a certificate nobody was tracking quietly expiring at 2am. The current process is a shared spreadsheet that's chronically out of date.

Platform Engineering has asked Automation Engineering to build a certificate lifecycle pipeline: discover every certificate in the estate, track expiry centrally, auto-renew via the internal CA's ACME-compatible endpoint well ahead of expiry, and deploy the renewed certificate with a zero-downtime reload — no spreadsheet, no 2am surprises.

Why this can't stay manualA spreadsheet has no enforcement mechanism and no reminder that actually gets acted on in time. Three outages from the same root cause is a clear signal the process itself needs to be replaced with something that runs and renews on its own.

This introduces a new concept versus prior projects: discovery-first automation — the pipeline must first find out what it doesn't know it's managing, before it can manage it.

08

Authentication

The automation authenticates to the internal CA's ACME endpoint using a dedicated client certificate issued specifically for this pipeline, stored as an AAP credential. Target-host deployment uses the standard SSH service-account pattern, with sudo scoped to certificate file placement and service reload commands only.

Ansible Design

Architect's note

Discovery, renewal, and deployment are three separate roles with a database in between, not one monolithic role — this lets discovery run far more often (daily) than renewal needs to (only near expiry), and lets a renewal failure be retried without re-running discovery.

Code & Roles

roles/cert_discovery/tasks/main.yml 
---
# Discovery probes the actual TLS handshake rather than trusting any
# config file -- config drift is exactly how certs go untracked in the
# first place, so we verify what's really being served.
- name: Probe live TLS certificate expiry
  community.crypto.x509_certificate_info:
    path: /dev/stdin
    content: "{{ lookup('pipe', 'openssl s_client -connect ' + inventory_hostname + ':443 -servername ' + inventory_hostname + ' /dev/null | openssl x509') }}"
  register: cert_info
  delegate_to: localhost

- name: Upsert discovered certificate into inventory database
  community.postgresql.postgresql_query:
    db: cert_inventory
    query: >
      INSERT INTO certificates (hostname, expiry_date, issuer, last_seen)
      VALUES (%s, %s, %s, now())
      ON CONFLICT (hostname) DO UPDATE
      SET expiry_date = EXCLUDED.expiry_date, last_seen = now()
    positional_args:
      - "{{ inventory_hostname }}"
      - "{{ cert_info.not_after }}"
      - "{{ cert_info.issuer_ou }}"
  delegate_to: localhost
roles/cert_renew/tasks/main.yml 
---
- name: Request renewal from internal CA via ACME
  community.crypto.acme_certificate:
    account_key_src: "{{ acme_account_key_path }}"
    csr: "{{ csr_path }}"
    dest: "{{ cert_output_path }}"
    acme_directory: "https://ca.internal.novastack.bank/acme/directory"
  register: renewal_result

# A failed renewal alerts a human immediately -- this line exists
# specifically because the original problem was a SILENT failure.
- name: Alert Platform Engineering on renewal failure
  ansible.builtin.uri:
    url: "{{ slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: "Certificate renewal FAILED for {{ inventory_hostname }} — {{ renewal_result.msg | default('unknown error') }}. Manual intervention required before expiry."
  delegate_to: localhost
  when: renewal_result.failed | default(false)

Execution flow, in plain terms

Discovery independently verifies what's actually being served on the wire and keeps the inventory database current — this is what replaces the spreadsheet. Renewal only runs against certs the inventory says are approaching expiry, requests a new cert from the internal CA, and pages a human the moment anything fails, rather than letting a failure disappear into a job log nobody reads.

Testing Strategy

Production Deployment

Three phases by risk: internal APIs first, then internal app servers, then customer-facing load balancer certs last — each phase watched for a full renewal cycle before the next begins.

14

Rollback Procedure

Every previous certificate is retained in the inventory's backup table before replacement; rollback redeploys the prior cert and reloads the service — the same deploy role, pointed at the old file.

15

Troubleshooting

ACME renewal fails validation Symptom: renewal_result reports a failed domain validation challenge.
Root cause (typical): Internal DNS record for the validation subdomain was never created for a newly discovered host.
Fix: Raise a DNS request to Network team; the Slack alert already fired so this is caught well before expiry, not at 2am.

Interview Preparation

Why build discovery before renewal logic?
You can't reliably automate renewal for certificates you don't know exist — the original outages were caused by exactly that gap. Discovery independently verifies the live TLS state rather than trusting a config file, which is what actually closes the gap the spreadsheet couldn't.
How do you guarantee a renewal failure doesn't repeat the original problem?
Every failure path pages a human immediately via Slack with the specific error, and the 30-day lead time before actual expiry gives real time to fix a failed renewal manually if needed — the automation is designed to fail loudly, never silently.
