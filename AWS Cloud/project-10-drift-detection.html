01

Business Scenario

NovaStack Bank has spent the last nine projects building strong enforcement automation — hardening, patching, compliance remediation. But there's a gap: nothing tells Infra Ops when a server has quietly drifted away from its intended state between scheduled runs. A recent incident traced back to an engineer manually changing a firewall rule during a live investigation and never reverting it — undetected for six weeks until it caused a connectivity failure.

Infrastructure Ops has asked Automation Engineering to build a continuous configuration drift detection system: define the desired state for every managed config domain (SSH, firewall, sudoers, key services) in Git as the single source of truth, run frequent, safe, read-only comparisons against live state, and alert immediately when live state diverges — before drift becomes an incident.

Why this can't stay manualEnforcement-only automation still allows six weeks of undetected manual drift between runs. Detection has to run far more frequently than enforcement, and has to be visible to Infra Ops as its own signal, independent of whether an incident has already happened.

This project introduces Git as the enforced desired-state source of truth and check-mode diffing as a first-class monitoring signal, not just a pre-deploy safety check like in earlier projects.

Ansible Design

Architect's note

Detection and correction are entirely separate job templates with separate RBAC, never combined. Running --check --diff is the detection job's entire contract — it must be structurally incapable of changing anything, which is stronger than just "we don't intend to."

Code & Roles

playbooks/drift_check.yml 
---
# check_mode: true is set at the PLAY level, not per-task -- this is a
# structural guarantee, not a convention every task author has to remember.
- name: Configuration drift detection sweep
  hosts: all
  check_mode: true
  diff: true
  tasks:
    - name: Compare SSH configuration against desired state
      ansible.builtin.include_role:
        name: ssh_hardening   # the exact Project 1 role -- reused, not rewritten
      register: ssh_drift_result

    - name: Compare firewall rules against desired state
      ansible.posix.firewalld:
        service: "{{ item.service }}"
        state: "{{ item.state }}"
        permanent: true
      loop: "{{ desired_firewall_rules }}"
      register: firewall_drift_result

    # check_mode tasks report changed=true when live state differs from
    # desired state -- that "changed" flag IS the drift signal here,
    # repurposed from its normal "did I make a change" meaning.
    - name: Record and alert on any detected drift
      ansible.builtin.include_role:
        name: drift_alert
      when: >
        ssh_drift_result.changed | default(false) or
        firewall_drift_result.changed | default(false)
roles/drift_alert/tasks/main.yml 
---
- name: Persist drift finding with full diff detail
  community.postgresql.postgresql_query:
    db: drift_tracking
    query: >
      INSERT INTO drift_events (hostname, domain, diff_detail, detected_at)
      VALUES (%s, %s, %s, now())
    positional_args:
      - "{{ inventory_hostname }}"
      - "{{ drift_domain }}"
      - "{{ drift_diff | to_json }}"
  delegate_to: localhost

- name: Alert Infra Ops on new drift
  ansible.builtin.uri:
    url: "{{ slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: "Drift detected on {{ inventory_hostname }} [{{ drift_domain }}] — live state no longer matches Git desired state."
  delegate_to: localhost

- name: Auto-create Security incident for security-relevant domains
  ansible.builtin.uri:
    url: "https://novastack.service-now.com/api/now/table/incident"
    method: POST
    body_format: json
    body:
      short_description: "Security-relevant config drift: {{ drift_domain }} on {{ inventory_hostname }}"
      urgency: 2
  delegate_to: localhost
  when: drift_domain in security_relevant_domains

Execution flow, in plain terms

Setting check_mode: true at the play level, not per task, means this playbook is structurally read-only — there's no task-level mistake that could turn it into an enforcement run. Any domain where live state differs from the Git-defined desired state gets recorded with full diff detail and alerted; security-relevant domains additionally auto-create an incident, while correction always stays a separate, human-launched job.

Rollback Procedure

Disable the scheduled job template; no host-level state to revert since the pipeline never writes to a target host.

Troubleshooting

Drift alert fires for every host on every run Symptom: 100% drift rate immediately after go-live.
Root cause (typical): The Git desired-state file doesn't yet match the currently-accepted production baseline — it was written aspirationally, not from the real fleet state.
Fix: Reconcile the desired-state repo against actual current PROD config first (a one-time baseline exercise with Infra Ops), then re-enable detection.

Interview Preparation

Why set check_mode at the play level instead of trusting each task to be read-only?
Play-level check_mode is a structural guarantee — even if someone later adds a task that would normally change state, it simply can't execute for real in this playbook. That's a much stronger safety property than relying on every task author remembering to write it read-only.
Why keep detection and correction as separate job templates instead of one auto-correcting pipeline?
Auto-correcting on detection risks silently erasing the evidence of why an engineer made a manual change in the first place — sometimes that change was a legitimate emergency fix that the desired state itself needs to catch up to, not the other way around. Keeping correction a deliberate, separate, human-triggered step preserves that judgment call.
