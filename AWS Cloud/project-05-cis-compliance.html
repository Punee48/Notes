01

Business Scenario

NovaStack Bank is required by its regulator to demonstrate CIS Benchmark Level 1 compliance across its RHEL estate, evidenced quarterly. Today, compliance validation is done by Security running a manual OpenSCAP scan on a sample of servers and extrapolating — which the last audit flagged as statistically insufficient. The regulator now expects 100% fleet coverage, with drift detected and remediated continuously, not just checked once a quarter.

Security has asked Automation Engineering to build a compliance-as-code pipeline: scan every server against the CIS baseline on a schedule, report pass/fail per control, and — for a pre-approved subset of low-risk controls — auto-remediate drift without waiting for a human.

Why this can't stay manualSampling isn't defensible to a regulator anymore, and manual remediation across 400+ servers per quarter isn't achievable within audit timelines. Continuous, automated scan-and-remediate is the only way to credibly claim full coverage.

This builds on Project 4's catalog-driven pattern — but the "catalog" here is the CIS control list itself, and it introduces a new concept: auto-remediation with a human-approval gate for anything above low risk.

Authentication

Same SSH service-account pattern as prior projects, with sudo scoped specifically to the read commands needed for each check, and a separate, narrower sudo scope for the remediation tasks — deliberately kept as two different privilege levels so a scan-only run can never accidentally have write access.

Ansible Design

Architect's note

Every control is implemented as a check/fix pair, never a single task — the check always runs, the fix only runs if the check fails AND the control's risk tier is auto_remediate. This makes the entire pipeline safely runnable in scan-only mode by flipping one variable.

├── catalog/cis_controls.yml
├── roles/cis_scan/tasks/
│   ├── main.yml
│   └── controls/
│       ├── 1_1_1_disable_unused_filesystems.yml
│       ├── 5_2_10_ssh_idle_timeout.yml
│       └── ...

Code & Roles

catalog/cis_controls.yml 
---
controls:
  - id: "5.2.10"
    description: "Ensure SSH idle timeout interval is configured"
    risk_tier: low
    auto_remediate: true
  - id: "1.1.1"
    description: "Ensure mounting of unused filesystems is disabled"
    risk_tier: medium
    auto_remediate: false   # requires ticket + manual approval before fix runs
roles/cis_scan/tasks/controls/5_2_10_ssh_idle_timeout.yml 
---
# The check is read-only and ALWAYS runs, regardless of auto_remediate --
# compliance status must be known even for controls we won't auto-fix.
- name: "CIS 5.2.10 -- Check ClientAliveInterval is set correctly"
  ansible.builtin.command: "sshd -T"
  register: sshd_effective_config
  changed_when: false

- name: "CIS 5.2.10 -- Record compliance status"
  ansible.builtin.set_fact:
    control_5_2_10_compliant: "{{ 'clientaliveinterval 300' in sshd_effective_config.stdout | lower }}"

# The fix only runs when the check failed AND this control's catalog
# entry says auto_remediate: true. This single `when` clause is what
# makes the entire framework safe to run in scan-only mode fleet-wide.
- name: "CIS 5.2.10 -- Remediate if non-compliant and approved for auto-fix"
  ansible.builtin.lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^ClientAliveInterval'
    line: 'ClientAliveInterval 300'
  notify: restart sshd
  when:
    - not control_5_2_10_compliant
    - cis_catalog['5.2.10'].auto_remediate | default(false)

- name: "CIS 5.2.10 -- Push compliance result to dashboard"
  ansible.builtin.uri:
    url: "http://pushgateway.internal.novastack.bank/metrics/job/cis_scan/instance/{{ inventory_hostname }}"
    method: POST
    body: 'cis_control_status{{ '{' }}control_id="5.2.10"{{ '}' }} {{ 1 if control_5_2_10_compliant else 0 }}'
  delegate_to: localhost

Execution flow, in plain terms

Every control checks itself first and always reports status, whether or not it's allowed to self-heal. Only controls explicitly marked auto_remediate: true in the catalog ever touch the host — everything else surfaces as a finding for Security and the app team to review, which is exactly the audit trail the regulator wants.

Testing Strategy

  • Scan-only mode validated against known-non-compliant DEV hosts to confirm detection accuracy first
  • Auto-remediation tested against a disposable UAT snapshot before any PROD enablement
13

Production Deployment

Phase 1: scan-only across full PROD fleet for two weeks, building a compliance baseline. Phase 2: auto-remediation enabled only for the 14 CAB-approved Low-risk controls, watched closely for the first cycle.

14

Rollback Procedure

Flip auto_remediate: false for any control in the catalog — takes effect on the next scheduled scan, immediately reverting that control to report-only.

15

Troubleshooting

A remediated control breaks an application Symptom: App team reports an incident immediately following a scan cycle.
Root cause (typical): A control was mis-classified as Low risk without accounting for one app's specific dependency.
Fix: Immediately set that control to auto_remediate: false, revert via the control's own rollback task, re-classify the risk tier with Security.
16

Monitoring & Validation

A Grafana compliance dashboard shows fleet-wide pass rate per control, trending over time — this is what Security and Internal Audit actually watch week to week rather than waiting for the quarterly export.

Interview Preparation

Why separate the check from the fix in every single control?
It lets the entire fleet run in safe, read-only scan mode at any time by controlling a single catalog flag, and it means compliance status is always known even for controls we've deliberately chosen not to auto-fix.
How would you convince Security to trust auto-remediation?
Start with scan-only to build a trustworthy baseline, only auto-fix the lowest-risk controls first with full before/after audit logging, and give them a one-flag kill switch per control — trust is built incrementally, not asked for up front.
