05 AWS Console — Manual Steps

  1. Hosted zone create pannunga. Route 53 console → Hosted zones → Create hosted zone → domain name quoteportal.example → Public hosted zone → create pannina odane, AWS 4 NS (name server) records kudukkum — ivvai namma domain registrar-la (GoDaddy, Namecheap, edhu use pannirundhaalum) update pannanum, DNS resolution ithu route 53-ku point aagum.
  2. ACM-la certificate request pannunga. Certificate Manager console → Request certificate → domain names: quoteportal.example mattum www.quoteportal.example (rendையும் oru certificate-la cover pannalam) → validation method: DNS validation → ACM oru CNAME record kudukkum, adha Route 53-la add pannanum (ACM Route 53-oda integrated irundha, "Create records in Route 53" button click pannினாலே automatic-a add aagidum).
  3. Certificate validate aagum varaikkum wait pannunga. Konjam minutes edukkum — status "Issued" aana appuram mattum next step-ku pogalam.
  4. ALB-la HTTPS listener add pannunga (Assignment 3-oda challenge complete pannurathu). EC2 console → Load Balancers → quote-portal-alb → Listeners → Add listener → HTTPS:443 → default action: forward to quote-portal-tg → certificate: ACM-la irundhu step 2-la issue aana certificate select pannunga → existing HTTP:80 listener-ah edit panni, action-ah "Redirect to HTTPS" nu maathunga.
  5. Alias A-record create pannunga. Hosted zone-ku poi → Create record → record name blank (root domain-ku) → record type A → toggle "Alias" ON → route traffic to: Application Load Balancer → region select pannunga → ALB select pannunga → create. www subdomain-kum innoru Alias record create pannunga, adhே ALB point pannirukkanum.
  6. Route 53 health check create pannunga. Route 53 → Health checks → Create health check → endpoint: ALB-oda DNS name, path /health → this feeds visibility now, and becomes the failover trigger in Assignment 22.
  7. Verify pannunga. Browser-la https://www.quoteportal.example type pannunga → HTTPS lock icon, valid certificate, application response kaanum. http:// try pannunga → automatic-a HTTPS-ku redirect aagi irukkanum.

06 AWS CLI

bash
# Create the hosted zone
ZONE_ID=$(aws route53 create-hosted-zone \
  --name quoteportal.example \
  --caller-reference "quote-portal-$(date +%s)" \
  --query 'HostedZone.Id' --output text)

# Request the ACM certificate with DNS validation
CERT_ARN=$(aws acm request-certificate \
  --domain-name quoteportal.example \
  --subject-alternative-names www.quoteportal.example \
  --validation-method DNS \
  --query 'CertificateArn' --output text)

# Create the Alias A-record pointing the root domain at the ALB
aws route53 change-resource-record-sets --hosted-zone-id $ZONE_ID \
  --change-batch '{
    "Changes": [{
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "quoteportal.example",
        "Type": "A",
        "AliasTarget": {
          "HostedZoneId": "'$ALB_HOSTED_ZONE_ID'",
          "DNSName": "'$ALB_DNS_NAME'",
          "EvaluateTargetHealth": true
        }
      }
    }]
  }'
Flag / FieldMeaning
--caller-referenceA unique idempotency token Route 53 requires per hosted zone creation call — prevents accidental duplicate zone creation on a retried request
"EvaluateTargetHealth": trueIthu than Alias record-ah, target (ALB)-oda health status track pannura maadhiri pannum — ALB itself unhealthy-na, Route 53 andha record-ah "unhealthy" nu treat pannum, future multi-region failover-ku foundation
$ALB_HOSTED_ZONE_IDALB-kum, oru fixed, region-specific hosted zone ID irukkum (namma domain-oda hosted zone illa) — AWS documentation-la, region-per-region list irukkum

07 Terraform Implementation

main.tf — Hosted Zone & ACM Certificate

main.tf (part 1 of 3)
resource "aws_route53_zone" "main" {
  name = "quoteportal.example"
}

resource "aws_acm_certificate" "main" {
  domain_name               = "quoteportal.example"
  subject_alternative_names = ["www.quoteportal.example"]
  validation_method          = "DNS"

  lifecycle {
    create_before_destroy = true
    # If this certificate is ever replaced (e.g. adding another SAN), the NEW
    # cert is issued before the old one is destroyed — avoids a gap where the
    # ALB's HTTPS listener has no valid certificate to reference at all.
  }
}

resource "aws_route53_record" "cert_validation" {
  for_each = {
    for dvo in aws_acm_certificate.main.domain_validation_options : dvo.domain_name => {
      name   = dvo.resource_record_name
      record = dvo.resource_record_value
      type   = dvo.resource_record_type
    }
  }
  # for_each here because a cert with 2 SANs (root + www) produces 2
  # separate validation records — this dynamically creates exactly as many
  # records as ACM actually needs, without hardcoding a count.
  zone_id = aws_route53_zone.main.zone_id
  name    = each.value.name
  type    = each.value.type
  records = [each.value.record]
  ttl     = 60
}

resource "aws_acm_certificate_validation" "main" {
  certificate_arn         = aws_acm_certificate.main.arn
  validation_record_fqdns = [for record in aws_route53_record.cert_validation : record.fqdn]
  # This resource doesn't create anything itself — it BLOCKS Terraform until
  # ACM actually confirms validation succeeded, so nothing downstream (the
  # HTTPS listener) tries to reference a still-pending certificate.
}

main.tf — HTTPS Listener & HTTP Redirect (completing Assignment 3's challenge)

main.tf (part 2 of 3)
resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.main.arn
  port               = 443
  protocol           = "HTTPS"
  certificate_arn    = aws_acm_certificate_validation.main.certificate_arn
  ssl_policy          = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  # A modern TLS security policy — supports TLS 1.3 while staying backward
  # compatible with TLS 1.2 clients, rather than allowing older/weaker
  # protocol versions by default.

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.app.arn
  }
}

resource "aws_lb_listener" "http_redirect" {
  load_balancer_arn = aws_lb.main.arn
  port               = 80
  protocol           = "HTTP"

  default_action {
    type = "redirect"
    redirect {
      port        = "443"
      protocol    = "HTTPS"
      status_code = "HTTP_301"
    }
  }
  # Replaces Assignment 3's plain HTTP-forwarding listener entirely — HTTP
  # traffic is now ALWAYS bounced to HTTPS, never served directly.
}

main.tf — Alias Records & Health Check

main.tf (part 3 of 3)
resource "aws_route53_record" "root" {
  zone_id = aws_route53_zone.main.zone_id
  name    = "quoteportal.example"

  zone_id = aws_route53_zone.main.zone_id
  name    = "www.quoteportal.example"
  type    = "A"
  alias {
    name                   = aws_lb.main.dns_name
    zone_id                = aws_lb.main.zone_id
    evaluate_target_health = true
  }
}

resource "aws_route53_health_check" "alb" {
  fqdn              = aws_lb.main.dns_name
  port               = 443
  type               = "HTTPS"
  resource_path      = "/health"
  failure_threshold  = 3
  request_interval   = 30
  # Not wired to any failover routing policy yet — that's Assignment 22's
  # job once a second region actually exists to fail over TO. For now this
  # purely feeds visibility (Assignment 9's dashboard) and groundwork.
  tags = { Name = "quote-portal-alb-health" }
}

10 Production Incident

Campaign launch day, morning

Ritu campaign email anuppitaanga, aana konjam customers "site not found" nu report pannaanga — aana majority customers-ku correctly work aagudhu. Weird — same domain, different result different users-ku.

Investigation

bash
dig quoteportal.example
# Locally resolves correctly — so the problem isn't Route 53 itself

Andha specific customers-oda ISP/local DNS resolver, namma NS record change-ah innum propagate pannala — namma registrar-la NS records update panni innum konjam mani neram (few hours) aagirundhadhu mattum, aana global DNS propagation, TTL caching-oda base pannirundhu, sometimes 24-48 hours varaikkum edukkum, ella resolver-lyum ஒரே சமயம் illa.

Root Cause

DNS propagation delay — namma Route 53-la ondrum wrong pannala, aana namma NS record change, worldwide-a ella DNS resolver-lyum ஒரே நேரத்தில் kaanum nu expect pannirunthadhu, adhu unrealistic expectation. Ithu, technical mistake illa, planning/communication gap.

Immediate Fix

Onnume "fix" panna mudiyaadhu real-time-la — propagation, wait pannanum. Ritu-ku update kudutthom, "next few hours-la resolve aagum" nu.

Permanent Fix / Prevention

Process-level fix: future campaign launches-ku, DNS/domain changes-ah kammi-kammi 48-72 hours munnadiye pannanum, launch date-ku close-a illama. Additionally, NS record TTL-ah konjam kammi vecha (already low by default for NS records, aana explicit-a confirm pannanum), future changes propagate aaga edukkura time-ah minimize pannalam.

Lessons Learned

  • DNS changes instant illa — global propagation timeline (few hours to 48 hours) explicitly plan pannanum, especially business-critical launch date-oda munnaadi.
  • "Namakku correctly work aagudhu" nu namma test panradhu, ella users-kum work aagum nu guarantee illa — DNS caching, different resolvers different time-la update aagum.

16 Practice Challenge

Karthik kekraaru: "Namma next version-ah, small % customers-ku mattum test pannanum full rollout pannuradhukku munnadi — 'canary' testing maadhiri. DNS layer-la ithu panna mudiyuma?"

Requirement: Small percentage of traffic-ah oru different target (e.g., a test/staging target group) route pannunga, remaining majority traffic normal production-ku pogum maadhiri, DNS level-la.

Acceptance Criteria: Traffic split percentage-based-a control panna mudiyanum, easy-a adjust panna mudiyanum without a major re-architecture.

Challenge Solution

Route 53 Weighted Routing Policy use pannunga — same record name (www.quoteportal.example) ku, rendு vera aws_route53_record resource create pannunga, vera vera set_identifier mattum weight value vechu (e.g., production target 95, canary target 5) — Route 53, automatic-a andha weight-oda proportion-la traffic split pannும். Weight easy-a adjust pannalam (95/5 → 80/20 → 50/50) gradual rollout-ku, ondrume application-level change venaam. Idhுக்கு, ALB listener rules-oda path-based routing kooda alternative-a irukkum, aana DNS-level weighted routing, "completely separate infrastructure stack-ku test traffic route pannanum" scenario-ku better fit, ALB listener rule "same infra, different path" scenario-ku better fit.

17 Interview Preparation

Q1 · DNS FundamentalsRoute 53 Alias record-ah, standard CNAME-ku vida, evlo different?

Alias record Route 53-oda proprietary extension — AWS resources (ALB, CloudFront, S3 website) ku direct-a point pannalam, root/apex domain-லேயும் use pannalam (CNAME-ku andha restriction irukku, DNS RFC standard-படி). Query pannumbodhu charge illa AWS target-ku point pannumbodhu, and target resource-oda underlying IP maara, automatic-a track pannும், manual update venaam.

Follow-up: "Yeppo CNAME use pannuveenga, Alias illama?" — Non-AWS external target (namma control illatha oru third-party service) point pannanum-na, illa subdomain (root illama) point pannum bodhu, adhu AWS resource illama irundha.
Q2 · SecurityACM certificate free-a irukku, aana yean namma "always use TLS" nu default-a pannikkanum?

Plain HTTP, data-ah plaintext-la transmit pannும் — customer-oda quote data, personal info, ellame intercept panna mudiyum in-transit. Free-a irundhu, zero downside irukkumbodhu, HTTPS-ah default-a pannaadha reason edhuvum illa. Modern browsers kooda, HTTP-only sites-ku "Not Secure" warning kaattum, which affects customer trust directly.

Follow-up: "ACM certificate expire aagumbodhu enna aagum?" — DNS-validated certificates, AWS automatic-a renew pannும், andha validation record hosted zone-la irundha varaikkum — adhан exactly namma andha record-ah protect pannanum nu sonna reason.
Q3 · Production ScenarioOru domain change pannina appuram, sila users "site not found" nu report pannaanga, majority-ku correctly work aagudhu. Epdi triage pannuveenga?

First step-ah, "namma-side problem-a, illa propagation delay-a" nu distinguish pannanum — namma own dig query correctly resolve aana, and affected users specific geography/ISP-la cluster aayirundha, DNS propagation delay romba likely. Adhukku "fix" panna edhuvum illa except wait pannuradhu — aana andha explanation-ah clearly communicate pannuradhு, business stakeholders-ku, romba mukkiyam.

Follow-up: "Future launches-ku ithai epdi prevent pannuveenga?" — DNS changes-ah launch date-ku romba close-a pannaama, munnadiye (48-72 hours) pannuradhu, exactly indha incident-la panna permanent fix.
Q4 · Cost OptimizationRoute 53 health check evlo pannalam, cost effect enna?

Ovvoru health check-kum small per-month charge irukku, so "namma actually monitor panna venum" nu decide panna, blanket-a ella endpoint-kkum podradhu illama. Namma case-la, oru health check (main ALB endpoint) podhum ippolaikku — future multi-region setup varumbodhu, per-region health check venum, adhுவும் justified cost-தான், ovvoru region-oda independent health visibility venum-na.

Follow-up: "Health check vs CloudWatch alarm — rendும் same purpose-ah?" — Illa — CloudWatch alarm, AWS-internal metrics track pannும் (ALB target health, straight from inside AWS). Route 53 health check, external vantage point-lerundhu (multiple global locations-lerundhu) check pannும், so "AWS-oda internal view mattum illama, external user perspective-ல enna kaanudhu" nu kooda confirm pannும் — different, complementary signal.
Q5 · Terraformaws_acm_certificate_validation resource, actually enna "create" pannும்?

Technically ondrume "create" pannaadhu — idhu oru blocking/waiting resource, ACM andha certificate-ah "Issued" status-ku maaruradha varaikkum Terraform apply-ah pause pannும். Idhu illama, downstream resources (namma HTTPS listener) andha certificate-ah reference panna try pannும், adhu innum "Pending validation" state-la irundhaalும் — race condition, intermittent apply failures create pannும்.

Follow-up: "Idhu illama enna specific error varum?" — HTTPS listener create pannும் bodhu, "certificate not found/not valid" maadhiri error, especially first-time apply-la, DNS validation innum propagate aagatha samayathula.
Q6 · Manager RoundRitu, campaign launch-oda DNS propagation delay-ah "namma mistake" nu frame pannuraanga. Epdi respond pannுவீங்க?

Naan adha "namma-side execution mistake" nu illama, "planning gap namma munnamே anticipate pannirukkanum" nu honestly frame pannுவேன் — DNS propagation, namma control-la illatha oru real, well-known technical constraint, aana adha campaign timeline planning-la account pannாதadhு namma responsibility. Naan concrete-a, "next launch-ku 72 hours munnadiye DNS changes pannுவோம்" nu process fix propose pannுவேன், same mistake repeat aagாம இருக்க.

Follow-up: "Marketing team-oda trust epdi rebuild pannுவீங்க இந்த மாதிரி event-க்கு அப்புறம்?" — Transparent-a, exactly enna nadandhுchு nu technical detail-oda explain pannுவேன் (jargon illama), and future launches-ku oru shared checklist create pannுவேன் (DNS changes, cert issuance, propagation buffer) — dono teams-ум munnadiye same timeline-ah expect pannும் maadhiri.
