01

Business Scenario

With tagging now enforced across AWS (Project 11) and Azure (Project 12), Finance can finally see spend by cost center clearly — and what they see is not good: roughly 22% of compute spend is going to instances running below 5% CPU utilization for 30+ days, and a further chunk to non-PROD instances left running 24/7 that only need to be up during business hours. FinOps has quantified a potential $340K/year in savings, but identifying and safely acting on it manually, across two clouds, isn't realistic at the pace instances are provisioned.

Automation Engineering has been asked to build a multi-cloud rightsizing pipeline: identify idle and oversized resources using real utilization data, recommend or (for pre-approved low-risk cases) automatically resize/schedule them, and report savings back to FinOps — without ever touching a PROD instance without a human in the loop.

Why this can't stay manual$340K/year in identified waste across a fleet that grows every week from Projects 11 and 12's self-service provisioning isn't something a periodic manual spend review can keep up with — it needs to be a continuous, automated feedback loop tied to real usage data.

This project directly builds on the tagging foundation of Projects 11–12, adding CloudWatch/Azure Monitor utilization data as a new input, and introduces the concept of recommend vs auto-act gating based on environment risk.

Authentication

Ansible Design

Architect's note

The PROD exclusion is enforced at two independent layers — the IAM/RBAC policy itself cannot stop a PROD-tagged instance, and the playbook additionally asserts the environment tag before acting. Two independent enforcement layers mean neither a policy misconfiguration nor a code bug alone can cause a PROD instance to be stopped by this pipeline.

Code & Roles

roles/utilization_analysis/tasks/main.yml 
---
- name: Pull 30-day CPU utilization from CloudWatch
  amazon.aws.cloudwatch_metric_alarm_info:
    name_prefix: "{{ inventory_hostname }}-cpu"
  register: cw_metrics
  delegate_to: localhost
  when: cloud_provider == "aws"

- name: Classify instance based on utilization pattern
  ansible.builtin.set_fact:
    rightsizing_classification: >-
      {{ 'idle' if avg_cpu_30d < 5
         else 'oversized' if avg_cpu_30d < 20 and instance_size_tier == 'large'
         else 'correctly_sized' }}
  vars:
    avg_cpu_30d: "{{ cw_metrics.metrics | map(attribute='average') | list | average }}"

- name: Record recommendation for FinOps report
  community.postgresql.postgresql_query:
    db: finops_tracking
    query: >
      INSERT INTO rightsizing_recommendations (hostname, environment, classification, potential_monthly_savings)
      VALUES (%s, %s, %s, %s)
    positional_args:
      - "{{ inventory_hostname }}"
      - "{{ instance_tags.environment }}"
      - "{{ rightsizing_classification }}"
      - "{{ estimated_savings | default(0) }}"
  delegate_to: localhost
roles/auto_schedule/tasks/main.yml 
---
# Layer 2 of the PROD exclusion -- the IAM policy is layer 1. Even if
# this task were somehow reached for a PROD instance, this assertion
# stops it before any stop/start API call is made.
- name: Hard guardrail -- refuse to schedule anything tagged PROD
  ansible.builtin.assert:
    that: instance_tags.environment != "prod"
    fail_msg: "Refusing to auto-schedule a PROD-tagged instance. This action is out of scope by design."

- name: Confirm instance is opted in to auto-scheduling
  ansible.builtin.assert:
    that: instance_tags.auto_schedule_optin | default('false') == 'true'
    fail_msg: "Instance not opted in to auto-scheduling — skipping."

- name: Stop idle DEV/UAT instance outside business hours
  amazon.aws.ec2_instance:
    instance_ids: "{{ instance_id }}"
    state: stopped
  when:
    - rightsizing_classification == "idle"
    - not within_business_hours

Execution flow, in plain terms

Analysis classifies every tagged instance from its real 30-day utilization data and records a recommendation regardless of environment. Only the scheduling role can actually stop anything, and it refuses twice before doing so — once via IAM policy that structurally cannot touch PROD, and again via an explicit in-playbook assertion — plus a separate opt-in check, so a team's legitimately idle-looking instance is never stopped without their consent.

Production Deployment

Analysis runs across all environments from day one (read-only, zero risk). Auto-scheduling is enabled only for explicitly opted-in DEV/UAT instances; PROD never receives automated action in this project — only recommendations delivered to app teams for manual review.

14

Rollback Procedure

Remove the auto_schedule_optin tag from any instance to immediately exclude it; stopped instances are simply restarted by the owning team, no automation-side rollback needed since stop/start is inherently reversible.

Troubleshooting

Team complains their DEV instance was stopped mid-task Symptom: An opted-in instance stopped during active use.
Root cause (typical): "Business hours" window didn't account for a team working outside standard hours occasionally.
Fix: Offer a temporary opt-out tag the team can self-apply before known off-hours work, rather than removing opt-in entirely.

Interview Preparation

Why two separate layers of PROD protection instead of just one?
Any single control can fail — a policy misconfiguration or a code bug. Two independent layers, IAM at the infrastructure level and an explicit assertion at the playbook level, mean both would have to fail simultaneously for a PROD instance to ever be touched, which is a much stronger guarantee for a bank than trusting either one alone.
Why opt-in scheduling instead of just applying it to all idle DEV/UAT instances?
"Idle" from a 30-day CPU average can still mean legitimately important — a team doing occasional off-hours load testing, for example. Opt-in respects that teams know their own usage patterns better than a utilization metric does, and avoids the automation eroding trust by surprising someone.
