Implementing Auto Scaling and Production Health Checks

The marketing campaign Priya warned about is three weeks out. Two fixed instances won't survive a 10x traffic spike, and nobody wants to be manually launching instances at 11 PM. Time to replace the manually-managed pair from Assignment 6 with a real Auto Scaling Group.

01 Production Story

Infrastructure Manager — Priya Nandan

"Marketing just confirmed the campaign date. Historical data from similar campaigns at other companies suggests 8-10x normal traffic for about four hours, then it tapers off over the rest of the day. I need this to scale up automatically when it happens and scale back down afterward — I'm not paying for ten instances at 2 AM three days later because somebody forgot to scale back down manually."

Why this is Assignment 7

Assignment 6 ended by naming exactly this gap: a fixed count = 2 can't respond to load on its own. An Auto Scaling Group takes over ownership of "how many instances should exist right now" from us entirely — it launches more when a scaling policy's metric crosses a threshold, terminates extras when load drops, and replaces any instance that fails its health check, all without a human in the loop. We reuse the exact Launch Template built in Assignment 6 — nothing about the instance definition itself changes, only who's managing how many of them exist.

03 Architecture Design

The Auto Scaling Group (ASG) sits between the Launch Template and the target group, replacing the manual count = 2 instance management from Assignment 6 entirely — it now owns instance count, placement across both AZs, health-check-driven replacement, and target group registration, none of which we manage by hand anymore.

The ASG's own health check is configured as ELB type, not just EC2 — meaning it defers to the target group's HTTP health check (built in Assignment 3) to decide whether an instance is truly healthy, not merely whether the underlying EC2 instance is running. This is the direct answer to "production health checks" in this assignment's title: an EC2 status check alone would happily call a instance "healthy" even if the app inside it crashed on boot.

04 Architecture Decision Making

Decision: Target Tracking vs. Step Scaling vs. Simple Scaling

Simple ScalingStep ScalingTarget Tracking
How it decidesOne alarm, one fixed adjustment, then a cooldown before it can act againMultiple alarm thresholds, different adjustment sizes per thresholdYou specify a target value (e.g. "keep average CPU at 50%"); AWS manages the alarms and adjustments itself
Fits an unpredictable 8-10x spikePoorly — a single fixed step can't respond proportionally to a spike of unknown exact sizeBetter, but requires hand-tuning multiple thresholds in advanceWell — automatically adds/removes capacity proportional to how far off-target the metric actually is, without pre-guessing every threshold

Decision: Target Tracking, tracking average CPU utilization at 50%. It requires the least manual tuning and responds proportionally whether the spike turns out to be 5x or 12x, rather than being calibrated for one guessed number in advance — appropriate given marketing's own estimate is a range, not a precise figure.

Decision: EC2 Health Check vs. ELB Health Check on the ASG

ASG's default EC2 health check only asks "is the instance's underlying hardware/hypervisor status OK" — it says nothing about whether the application inside actually started successfully. Setting health_check_type = "ELB" makes the ASG defer to the target group's own HTTP health check on /health instead — an instance where EC2 itself is fine but the Node process crashed on boot is correctly identified as unhealthy and replaced, exactly the gap an EC2-only check would miss.

05 AWS Console — Manual Steps

  1. Deregister and terminate the manually-managed instances from Assignment 6. Target Groups → deregister both. EC2 → terminate both — the ASG will launch its own replacements from the same Launch Template momentarily.
  2. Create the Auto Scaling Group. EC2 console → Auto Scaling Groups → Create Auto Scaling group → select the existing quote-portal-app-lt launch template → VPC quote-portal-vpc, subnets: both private subnets → attach to the existing target group quote-portal-tg (this is what registers new instances automatically going forward).
  3. Configure health checks. On the health check step: enable "Turn on Elastic Load Balancing health checks" (this is the ELB health check type described above) → health check grace period: 90 seconds (enough time for the app to boot and pass its first health check before the ASG considers a slow-starting instance a failure).
  4. Set group size. Minimum 2, Desired 2, Maximum 8 — the minimum of 2 preserves the AZ-redundancy floor from Assignment 6 even with zero scaling activity.
  5. Add a target tracking scaling policy. After creation → Automatic scaling tab → Create dynamic scaling policy → target tracking → metric: Average CPU Utilization → target value: 50.
  6. Verify. Confirm the ASG's instances list shows 2 running instances, both showing healthy in the target group, and both appearing in different AZs.

06 AWS CLI

bash
# Create the ASG referencing the existing launch template and target group
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name quote-portal-asg \
  --launch-template LaunchTemplateName=quote-portal-app-lt,Version='$Latest' \
  --min-size 2 --max-size 8 --desired-capacity 2 \
  --vpc-zone-identifier "$PRIVATE_A_SUBNET_ID,$PRIVATE_B_SUBNET_ID" \
  --target-group-arns $TG_ARN \
  --health-check-type ELB --health-check-grace-period 90

# Attach a target tracking scaling policy targeting 50% average CPU
aws autoscaling put-scaling-policy \
  --auto-scaling-group-name quote-portal-asg \
  --policy-name cpu-target-tracking \
  --policy-type TargetTrackingScaling \
  --target-tracking-configuration '{
    "PredefinedMetricSpecification": {"PredefinedMetricType": "ASGAverageCPUUtilization"},
    "TargetValue": 50.0
  }'

07 Terraform Implementation

main.tf — Auto Scaling Group (replaces Assignment 6's count = 2 instances)

main.tf (part 1 of 2)
resource "aws_autoscaling_group" "app" {
  name                = "quote-portal-asg"
  vpc_zone_identifier = aws_subnet.private[*].id
  target_group_arns   = [aws_lb_target_group.app.arn]
  # Attaching the SAME target group from Assignment 3 — the ALB's listener
  # and routing rules need zero changes; only who's registered changes.

  min_size         = 2
  max_size         = 8
  desired_capacity = 2

  health_check_type         = "ELB"
  health_check_grace_period = 90

  launch_template {
    id      = aws_launch_template.app.id  # from Assignment 6, unchanged
    version = "$Latest"
  }

  tag {
    key                 = "Name"
    value               = "quote-portal-app-asg"
    propagate_at_launch = true
    # propagate_at_launch = true means every instance the ASG creates
    # automatically inherits this tag — without it, instances would launch
    # untagged and be harder to identify in the console/CLI.
  }

  lifecycle {
    ignore_changes = [desired_capacity]
    # Once scaling policies are managing desired_capacity dynamically, we
    # don't want Terraform fighting the ASG by resetting it back to 2 on
    # every apply — this tells Terraform "manage everything about this
    # resource except this one field, which the scaling policy now owns."
  }
}

main.tf — Target Tracking Scaling Policy

main.tf (part 2 of 2)
resource "aws_autoscaling_policy" "cpu_target_tracking" {
  name                   = "cpu-target-tracking"
  autoscaling_group_name = aws_autoscaling_group.app.name
  policy_type            = "TargetTrackingScaling"

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value = 50.0
    # AWS manages the underlying CloudWatch alarms and step adjustments
    # itself — we only declare the target, not the mechanics of reaching it.
  }
}

resource "aws_cloudwatch_metric_alarm" "asg_min_capacity" {
  alarm_name          = "quote-portal-asg-at-minimum"
  comparison_operator = "LessThanOrEqualToThreshold"
  evaluation_periods  = 1
  metric_name         = "GroupInServiceInstances"
  namespace           = "AWS/AutoScaling"
  period              = 300
  statistic           = "Average"
  threshold           = 2
  dimensions          = { AutoScalingGroupName = aws_autoscaling_group.app.name }
  alarm_description   = "Fires if in-service instance count drops to the redundancy floor — same signal as Assignment 6's HealthyHostCount alarm, now driven by the ASG"
}

08 Validation & Testing

  • Baseline test: ASG shows 2 running instances across both AZs, both healthy in the target group.
  • Scale-out test: generate synthetic CPU load on the instances (e.g. a simple stress test script) and confirm the ASG launches additional instances within a few minutes as average CPU crosses 50%.
  • Grace period test: confirm a newly-launched instance is NOT terminated for failing health checks during its first 90 seconds, even if the app takes a beat to start — the grace period should visibly prevent premature termination.
  • Self-healing test: manually terminate one instance from the console directly (not via the ASG) — confirm the ASG detects the reduced count and launches a replacement automatically, with zero manual relaunch.
  • Scale-in test: stop the synthetic load and confirm the ASG gradually terminates excess instances back down toward the minimum of 2, not abruptly all at once.

10 Production Incident

Load test, three days before the campaign

During a scheduled load test simulating the expected campaign traffic, the ASG scales out as expected — but roughly a third of the new instances get terminated and relaunched repeatedly instead of settling into a healthy state, and CPU across the group stays elevated even as instance count climbs.

Investigation

bash
aws autoscaling describe-scaling-activities \
  --auto-scaling-group-name quote-portal-asg \
  --query "Activities[?contains(Cause,'health check')]" --output table

# On a freshly-launched, about-to-be-terminated instance, before it dies:
aws ssm start-session --target $NEW_INSTANCE_ID
tail -f /var/log/cloud-init-output.log

The scaling activity log shows a pattern of instances being terminated for failing ELB health checks right around the 90-second grace period boundary — not immediately, and not much later. On the instance itself, the app is still installing Node dependencies at the 90-second mark under the increased boot-time contention of many simultaneous launches sharing the same NAT Gateway bandwidth (from Assignment 2) for package downloads.

Root Cause

The 90-second grace period, tuned during calm single-instance testing in earlier assignments, doesn't hold up when many instances boot simultaneously and compete for the same outbound NAT bandwidth to download dependencies — a scale-dependent problem that never appeared until an actual load test exercised it.

Immediate Fix

Manually increased the ASG's desired capacity further to compensate for the churn during the remainder of the load test.

Permanent Fix

Terraform change
  health_check_grace_period = 180  # was 90 — doubled to absorb simultaneous-boot contention

Also flagged a longer-term fix: baking dependencies into a custom AMI at build time (Assignment 16's territory once containers/image-building is covered properly) rather than installing them fresh on every boot, which would remove this bottleneck at its root instead of just giving it more time.

Validation

Re-ran the load test with the increased grace period — zero premature terminations, all new instances reached healthy state on their first attempt.

Lessons Learned

  • A grace period tuned under light, single-instance conditions can silently fail under the very load-testing conditions it exists to handle — always load test the actual scaling behavior, not just the steady state.
  • Shared infrastructure (like a NAT Gateway's bandwidth) that was invisible as a bottleneck at low scale can become one under simultaneous multi-instance boot — a reminder that HA and scaling decisions interact with earlier network decisions, not just compute ones.

16 Practice Challenge

Priya comes back: "The campaign goes live at a known time — 9 AM. Do we really need to wait for CPU to actually climb before we start scaling, or can we get ahead of it?"

Requirement: Add a mechanism that proactively increases capacity ahead of a known, scheduled traffic event, rather than relying purely on reactive target tracking.

Acceptance Criteria: Capacity increases before the campaign's known start time, not only after CPU crosses the target-tracking threshold. The reactive target tracking policy from this assignment should remain in place as a safety net for anything beyond the scheduled bump.

Hints: Auto Scaling Groups support more than one kind of scaling action simultaneously.

Challenge Solution

Add an ASG scheduled action (aws_autoscaling_schedule in Terraform) that sets a higher minimum and desired capacity at a specific date/time shortly before 9 AM on the campaign day, and a second scheduled action later that evening reverting the minimum back to 2 once the campaign traffic has subsided. This runs alongside the existing target tracking policy, not instead of it — the scheduled action gets ahead of the known event by pre-warming capacity, while target tracking remains active as a safety net in case actual traffic exceeds what the scheduled bump anticipated. This is the standard pattern for "known event, unknown exact magnitude" — schedule for the known part, track for the unknown part.

17 Interview Preparation

Q1 · Auto ScalingWhat's the difference between an ASG's health check and a target group's health check, and why does it matter which type the ASG uses?

The target group's health check (HTTP /health) determines whether that specific target receives forwarded traffic. The ASG's own health check determines whether an instance should be terminated and replaced entirely. If the ASG is set to EC2-only health checks, it can consider an instance "healthy" (and never replace it) even while the target group has already marked it unhealthy and stopped sending it traffic — you'd end up with a permanently broken instance sitting idle instead of being cleaned up. Setting the ASG to ELB health check type makes it defer to the target group's judgment, closing that gap.

Follow-up: "Could an instance ever be EC2-healthy and ELB-unhealthy at the same time?" — Yes — that's exactly the load-test incident above: the EC2 instance itself was running fine, but the app inside hadn't finished starting, so the ELB health check correctly failed it while EC2 status checks would have shown it as fine.
Q2 · AWS FundamentalsWhy target CPU utilization specifically, and when would that be the wrong metric to scale on?

CPU is a reasonable default for a compute-bound workload where request handling genuinely consumes CPU proportionally to load. It's the wrong choice when the actual bottleneck is elsewhere — e.g. an application that's I/O-bound waiting on a slow downstream API, where CPU might stay low even as requests queue up and latency degrades. In that case, a custom metric like ALB RequestCountPerTarget or application-reported queue depth would better reflect real load.

Follow-up: "How would you know CPU was the wrong metric before it caused a problem in production?" — Load testing, exactly as done in this assignment's incident — observe which metric actually correlates with degraded response time or errors under realistic load, rather than assuming CPU is representative without checking.
Q3 · Production ScenarioAn ASG shows desired capacity of 6 but only 4 instances are actually in service. How do you investigate?

describe-scaling-activities is the first stop — it shows the specific cause of any failed or pending launch, whether that's a capacity limit, a launch template issue, or repeated health-check failures like the incident in this assignment. I'd distinguish "instances failing to launch at all" from "instances launching but then being terminated for failing health checks" — very different root causes requiring different fixes.

Follow-up: "What AWS-side limit could cause launches to fail even with a correct launch template?" — An EC2 service quota (vCPU limit) in that region/account, or insufficient capacity of that specific instance type in one of the target AZs at that moment — both are worth checking before assuming the problem is in your own configuration.
Q4 · Cost OptimizationHow would you further reduce cost on top of what target tracking already provides?

Mixing Spot Instances into the ASG's capacity for the portion of load above the guaranteed minimum — Spot pricing is substantially cheaper, and losing a Spot instance mid-spike is tolerable precisely because the ASG replaces it automatically and the baseline 2-instance minimum can stay on On-Demand for guaranteed availability. This is worth introducing carefully, not blanket, since Spot capacity can be reclaimed by AWS with short notice.

Follow-up: "What would make Spot a bad fit here specifically?" — If the campaign traffic is genuinely business-critical revenue-generating capacity where even a brief Spot reclaim during peak minutes is unacceptable — in that case, keeping the whole group On-Demand and accepting the higher cost may be the right trade-off.
Q5 · TerraformWhy add lifecycle { ignore_changes = [desired_capacity] } to the ASG resource?

Once a target tracking policy is actively managing capacity, the real-world desired_capacity value changes outside of Terraform constantly, as traffic rises and falls. Without ignore_changes, every subsequent terraform apply would see that drift and try to reset it back to the hardcoded value in code — fighting the scaling policy and potentially undoing an in-progress scale-out. The ignore_changes block tells Terraform "this one field is legitimately owned by something else at runtime, don't treat its drift as something to correct."

Follow-up: "Is this a general pattern, or specific to Auto Scaling?" — General — any time something outside Terraform legitimately and continuously modifies a specific attribute of a resource Terraform otherwise manages, ignore_changes on that specific attribute is the right tool, rather than removing the whole resource from Terraform management.
Q6 · Manager RoundHow would you present the load-test incident to leadership ahead of the real campaign — as a success or a failure?

As a success, and I'd frame it that way explicitly: the entire point of load testing three days before the real event was to find exactly this kind of problem somewhere other than in front of live customers. Finding and fixing a grace-period bug during a scheduled test, with time to spare, is the system working as intended — the failure mode we were actually trying to avoid was discovering this during the real campaign with real customer impact.

Follow-up: "What would you want in place before the next major traffic event, based on what you learned here?" — A standing practice of load testing any significant architecture or scaling change before it's needed for real, not just before this one known campaign — the value came from testing under realistic conditions ahead of time, and that should be a repeatable habit, not a one-off.
