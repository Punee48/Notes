01 Production Story

Security Team — Ananya Reddy

"Found it during a routine review of the app instance's user data: a third-party rating-API key, in plaintext, baked right into the launch script. Anyone with ec2:DescribeInstanceAttribute permission — which is a lot of people in a growing account — can read it. That's the immediate fire. But while I'm here: I want a full pass. Why this closes the Foundation stage

Every prior assignment has quietly practiced pieces of this — IAM instance roles instead of access keys (Assignment 1), least-privilege S3 policies (Assignments 1 and 4), security-group chaining (Assignment 3). This assignment makes IAM, secrets, and encryption the explicit subject rather than a supporting detail, and fixes the one real gap that slipped through: a secret that was never a secret at all.

03 Architecture Design

App Instance (sg-app)assumes reconcile/app IAM role
↓ secretsmanager:GetSecretValue only
Secrets Managerrating-api-key, encrypted with a customer-managed KMS key
↓ decrypt permission via key policy + IAM
KMS CMKrating-api-key-cmk — controls who can decrypt, independent of Secrets Manager access

Two independent layers of access control here, deliberately: the IAM policy decides who can call GetSecretValue, and the KMS key policy separately decides who can decrypt the resulting ciphertext. Both must allow the caller — this is why a customer-managed key, not the AWS-managed default, is worth the extra setup: it gives Security a second, independently auditable control point over exactly this kind of sensitive credential.

04 Architecture Decision Making

Decision: Secrets Manager vs. Systems Manager Parameter Store (SecureString)

Parameter Store (SecureString)Secrets Manager
CostFree for standard parametersPer-secret monthly charge
Automatic rotationNot built in — requires a custom Lambda + scheduling yourselfNative rotation scheduling, with built-in rotation Lambdas for RDS/common services
Fits this needWorkable, but rotation has to be hand-builtPurpose-built for exactly "credential that should rotate on a schedule"

Decision: Secrets Manager for the rating-API key, specifically because Ananya's requirement includes rotation without a redeploy — that's Secrets Manager's core value proposition. Parameter Store SecureString remains the right, cheaper choice for static configuration values that don't need rotation (revisit case by case, not a blanket either/or).

Decision: AWS-Managed KMS Key vs. Customer-Managed Key (CMK)

The AWS-managed key (aws/secretsmanager) works with zero setup but its key policy can't be customized — access is governed entirely by IAM. A customer-managed key adds its own key policy as a second, independent control: even someone with a broad IAM policy can't decrypt this specific secret unless the CMK's key policy also names them. Decision: customer-managed key, specifically for this one sensitive external credential — not applied blanket to every secret in the account, since that would add operational overhead with no proportional security gain for lower-sensitivity values.

05 AWS Console — Manual Steps

  1. Create the customer-managed KMS key. KMS console → Customer managed keys → Create key → symmetric, "Encrypt and decrypt" → key administrators: your security/platform team → key usage permissions: leave empty for now, added explicitly per-role below rather than granted broadly.
  2. Create the secret in Secrets Manager. Secrets Manager console → Store a new secret → "Other type of secret" → key/value: api_key = the actual rating-API key → encryption key: select the CMK from step 1 → name it quote-portal/rating-api-key.
  3. Grant the app's IAM role access. IAM console → find reconcile-job-role's sibling app role (or create quote-portal-app-role if the app instance is still using the security-group-only setup from Assignment 3) → attach an inline policy allowing secretsmanager:GetSecretValue scoped to exactly that one secret's ARN.
  4. Update the CMK's key policy. Back in KMS → the key from step 1 → Key policy → add a statement allowing kms:Decrypt for the app role's ARN specifically — this is the second, independent control described in the architecture section.
  5. Enable IAM Access Analyzer. IAM console → Access Analyzer → Create analyzer → type "Account" → this continuously scans for resources (S3 buckets, IAM roles, KMS keys) shared with anyone outside the account and surfaces findings automatically.
  6. Enforce MFA for human users. IAM console → Policies → Create policy using a standard AWS-provided "deny all actions except managing your own MFA device unless MFA is present" JSON template → attach to the group all human IAM users belong to.
  7. Remove the plaintext key from user data. Update the app instance's launch configuration to fetch the secret at boot via the AWS CLI/SDK instead of embedding it — redeploy the instance so the new user data takes effect (a stopped instance's user data change doesn't apply until it's actually relaunched from an updated launch configuration or template).

07 Terraform Implementation

main.tf — KMS Key & Secret

main.tf (part 1 of 3)
resource "aws_kms_key" "rating_api_key_cmk" {
  description             = "CMK for the quote portal rating-API secret"
  deletion_window_in_days = 30
  # deletion_window_in_days gives a mandatory recovery period before a key
  # deletion is irreversible — protects against an accidental "destroy" from
  # permanently locking out access to everything encrypted under this key.

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid       = "AllowAccountRootFullAccess"
        Effect    = "Allow"
        Principal = { AWS = "arn:aws:iam::${data.aws_caller_identity.current.account_id}:root" }
        Action    = "kms:*"
        Resource  = "*"
        # Standard baseline statement so the account's admins can still manage the
        # key via IAM policy — without this, ONLY statements explicitly listed
        # here would ever be able to touch the key, including root/admins.
      },
      {
        Sid       = "AllowAppRoleDecrypt"
        Effect    = "Allow"
        Principal = { AWS = aws_iam_role.quote_portal_app.arn }
        Action    = ["kms:Decrypt", "kms:DescribeKey"]
        Resource  = "*"
        # This is the SECOND independent control described in the architecture
        # section — the app role must be named HERE, in the key policy, not just
        # granted broad IAM permissions, to actually decrypt this secret.
      }
    ]
  })
}

resource "aws_kms_alias" "rating_api_key" {
  name          = "alias/rating-api-key-cmk"
  target_key_id = aws_kms_key.rating_api_key_cmk.key_id
}

resource "aws_secretsmanager_secret" "rating_api_key" {
  name       = "quote-portal/rating-api-key"
  kms_key_id = aws_kms_key.rating_api_key_cmk.arn
}

resource "aws_secretsmanager_secret_version" "rating_api_key" {
  secret_id     = aws_secretsmanager_secret.rating_api_key.id
  secret_string = jsonencode({ api_key = var.rating_api_key })
  # var.rating_api_key is marked sensitive = true below — Terraform will
  # redact it from plan/apply console output, though it's still visible in
  # state, which is why the state file itself must be stored encrypted with
  # restricted access (covered when we introduce remote state in Assignment 12).
}

main.tf — App Role, Least-Privilege Secret Access, MFA Policy

main.tf (part 2 of 3)
resource "aws_iam_role" "quote_portal_app" {
  name = "quote-portal-app-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "ec2.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy" "quote_portal_secret_access" {
  name = "read-rating-api-secret-only"
  role = aws_iam_role.quote_portal_app.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = "secretsmanager:GetSecretValue"
      Resource = aws_secretsmanager_secret.rating_api_key.arn
      # Scoped to ONE secret's exact ARN, and ONLY GetSecretValue — this role
      # cannot list other secrets, create new ones, or modify this one.
    }]
  })
}

data "aws_iam_policy_document" "require_mfa" {
  statement {
    sid       = "DenyAllExceptListedIfNoMFA"
    effect    = "Deny"
    actions   = ["*"]
    resources = ["*"]
    condition {
      test     = "BoolIfExists"
      variable = "aws:MultiFactorAuthPresent"
      values   = ["false"]
    }
    not_action = [
      "iam:CreateVirtualMFADevice", "iam:EnableMFADevice",
      "iam:ListMFADevices", "iam:ListVirtualMFADevices",
      "iam:ResyncMFADevice", "sts:GetSessionToken"
    ]
    # not_action carves out the handful of actions a user genuinely needs to
    # SET UP their own MFA device in the first place — without this carve-out,
    # a user with no MFA yet would be locked out of ever enabling it.
  }
}

resource "aws_iam_policy" "require_mfa" {
  name   = "require-mfa-for-console-users"
  policy = data.aws_iam_policy_document.require_mfa.json
}

08 Validation & Testing

  • Secret retrieval test: from the app instance, confirm get-secret-value succeeds using the instance role — no access keys involved anywhere in the process.
  • Negative test: from an unrelated IAM role/instance, attempt the same call — must fail with AccessDenied at the IAM layer even before KMS is evaluated.
  • KMS independence test: temporarily grant a role broad secretsmanager:* IAM permissions but do NOT add it to the CMK's key policy — confirm it still can't decrypt the secret, proving the two layers are genuinely independent.
  • MFA test: attempt any non-MFA-setup console action as a human user without an MFA device registered — must be denied.
  • No-plaintext test: aws ec2 describe-instance-attribute --attribute userData against the app instance, decode the base64 output, and confirm no API key string appears anywhere in it.

10 Production Incident

During the review itself

While auditing existing roles, Ananya's team finds that the reconcile-job-role from Assignment 1 was, at some point, manually granted s3:* on the whole account by an engineer troubleshooting an unrelated access issue months ago — and never scoped back down. It was never exploited, but it sat there as a standing, unnecessarily broad grant for months.

Investigation

bash
aws iam list-role-policies --role-name reconcile-job-role
aws iam get-role-policy --role-name reconcile-job-role --policy-name <name>
aws iam get-account-authorization-details --filter Role \
  --query "RoleDetailList[?RoleName=='reconcile-job-role']"

Confirms an inline policy separate from the one Terraform manages — proof this was a manual, out-of-band grant, echoing the exact drift pattern from Assignment 2's incident.

Root Cause

An engineer, while debugging an unrelated access-denied error under time pressure, widened the policy as a fast fix and never narrowed it back — a common, human pattern, not a one-off mistake by a careless engineer.

Immediate Fix

Removed the manually-added inline policy, confirming via the Assignment-1 acceptance tests that the reconciliation job still functions correctly with only its original least-privilege Terraform-managed policy.

Permanent Fix

Restricted iam:PutRolePolicy and iam:AttachRolePolicy to a small platform-team group for roles tagged as Terraform-managed, so "quick manual fix under pressure" is no longer even possible for most engineers — they have to go through the Terraform change instead, which forces the change to be reviewed and eventually reconciled with code.

Monitoring Improvement

Added the scheduled drift-detection job (same mechanism introduced in Assignment 2) to specifically flag IAM policy drift, not just network drift.

Lessons Learned

  • "Temporary" broad grants made under pressure are the most common source of standing over-permission — the fix has to make the safe path (going through Terraform) faster or at least not much slower than the unsafe one, or people will keep taking the shortcut.
  • A least-privilege policy defined in Terraform is only as good as the account's actual IAM permissions preventing someone from manually widening it outside that code.

16 Practice Challenge

Ananya comes back: "Good. Now — the third-party rating API rotates their keys quarterly and emails us the new one. Right now that means someone manually updating Secrets Manager and hoping they remember. Can we make rotation itself less error-prone, even if we can't fully automate against a third party we don't control?"

Requirement: Reduce the manual-error surface of quarterly key rotation without requiring the third party to support any AWS-native rotation protocol.

Acceptance Criteria: Old and new key versions are both auditable. A rotation should never involve editing application code or redeploying the instance.

Hints: Secrets Manager supports "rotation" as a concept even for secrets whose rotation logic can't be fully automated against an external, uncooperative third party.

Challenge Solution

Because the application already reads the secret at boot/runtime via GetSecretValue rather than having it baked into an image, rotation only ever requires calling aws secretsmanager put-secret-value with the new key — the app already fetches whatever the current value is, so no code change or redeploy is needed. For the "less error-prone" half: write a small custom Lambda rotation function (Secrets Manager supports custom rotation Lambdas, not just its built-in ones for RDS-style services) that's triggered manually by an engineer pasting the new key into a parameter, rather than editing the secret directly in the console — this gives a single, auditable, logged entry point for the rotation action instead of an ad hoc console edit, and Secrets Manager automatically retains the previous version so the old key remains inspectable during the transition window.

17 Interview Preparation

Q1 · SecurityWhy have both an IAM policy and a KMS key policy control access to the same secret — isn't that redundant?

It's defense in depth, not redundancy — they're independently controlled and can be managed by different teams. IAM controls "who can call this API"; the KMS key policy controls "who can decrypt data under this specific key," and both must agree. A mistake widening one (like the IAM drift incident in this assignment) doesn't automatically expose the secret if the key policy is still tight — which is exactly why the incident here didn't turn into an actual breach.

Follow-up: "What's the downside of always using a customer-managed key for everything?" — Operational overhead — you now own key policy management, rotation scheduling (if desired), and cost per key; appropriate for high-sensitivity secrets, unnecessary overhead for low-sensitivity configuration values.
Q2 · IAMWhat's a permission boundary and how is it different from a regular IAM policy attached to a role?

A permission boundary sets the maximum possible permissions a role or user can ever have, regardless of what identity-based policies are later attached to it — it's a ceiling, not a grant. A role can have a permission boundary allowing up to s3:* and an attached policy granting s3:*, but the effective permission is always the intersection of the two. It's most useful for letting less-privileged engineers create IAM roles themselves without risking privilege escalation, since anything they create is capped by the boundary regardless of what policy they attach.

Follow-up: "Would a permission boundary have prevented this assignment's incident?" — Yes, potentially — if reconcile-job-role had a permission boundary capping it well below s3:*, the manual over-grant would have been ineffective even after being applied, since the boundary would have capped the effective permission regardless.
Q3 · Production ScenarioHow would you find every place a specific secret has actually been accessed from, after the fact?

CloudTrail logs every secretsmanager:GetSecretValue call with the calling identity, source IP, and timestamp — filter events by that specific secret's ARN and event name to build a full access history, which is exactly the audit trail Ananya's compliance requirement depends on.

Follow-up: "What if CloudTrail wasn't enabled at the time?" — Then that access history is simply unavailable — which is itself the argument for CloudTrail being on by default from account creation, not something enabled reactively after an incident prompts the question.
Q4 · Cost OptimizationWhen would Parameter Store be preferable to Secrets Manager purely on cost grounds?

For a large number of low-sensitivity configuration values that don't need rotation — Parameter Store's standard tier is free, while Secrets Manager charges per secret. A team with hundreds of config values would see a meaningful cost difference; the right split is Secrets Manager for values that genuinely need rotation or the extra access controls, Parameter Store SecureString for everything else.

Follow-up: "Can Parameter Store use a customer-managed KMS key too?" — Yes — SecureString parameters can be encrypted under a CMK exactly like Secrets Manager secrets; the main functional gap versus Secrets Manager is native rotation scheduling, not encryption capability.
Q5 · TerraformWhy mark a variable sensitive = true if it's still visible in the Terraform state file regardless?

sensitive = true only redacts the value from CLI output (plan/apply logs, which often end up in CI logs, terminal scrollback, or screen shares) — a very real and common leak vector. It does nothing to protect the state file itself, which is why state must separately be stored in an encrypted, access-controlled remote backend (introduced properly in Assignment 12) — the two protections address different exposure points and neither substitutes for the other.

Follow-up: "So how would you actually supply this variable's value safely?" — Via a gitignored .tfvars file, an environment variable set at apply time, or pulled from Secrets Manager/Parameter Store itself via a data source — never hardcoded into a committed .tf file.
Q6 · Manager RoundSecurity wants MFA enforced for everyone immediately. Engineering is worried about being locked out mid-sprint. How do you roll this out?

I wouldn't flip the enforcing policy on for everyone in one shot. I'd first identify anyone without MFA already registered, give them a defined window with clear self-service instructions to enroll (the carve-out policy above already allows enrollment actions without MFA present, so nobody's locked out of setting it up), confirm coverage, and only then attach the enforcing policy account-wide — with a clear rollback plan if something legitimate breaks. The goal is getting to Ananya's non-negotiable requirement without an avoidable, disruptive outage caused by the rollout itself.

Follow-up: "What about service accounts or automation that can't use MFA at all?" — Those should already be using IAM roles rather than long-lived IAM user credentials wherever possible (the same principle from Assignment 1) — MFA enforcement targets human console/CLI users specifically, not machine-to-machine role assumption.
