01

Business Scenario

Following a disaster-recovery strategy review, NovaStack Bank has designated Azure as the DR region for its core banking platform, standing up a parallel VM estate that must stay configuration-consistent with the AWS PROD fleet from Project 11. Today there is no Azure automation at all — the DR environment was stood up manually as a one-time exercise eight months ago and has already drifted, which a recent DR test proved when a failover simulation failed due to a missing NSG rule that existed in AWS but was never replicated to Azure.

Automation Engineering has been asked to build Azure VM lifecycle automation mirroring the AWS pattern from Project 11 — provisioning, tagging, and NSG rule management — with an explicit cross-cloud parity check that flags when the Azure DR environment has drifted from its AWS PROD counterpart.

Why this can't stay manualA DR environment that silently drifts from PROD isn't actually DR — it's a false sense of safety, as the failed failover test proved directly. Automation is the only way to guarantee ongoing parity between two independently managed clouds.

This project reuses the tag-enforcement and pre-flight-assertion patterns from Project 11, applied to the azure.azcollection collection, and introduces the new concept of cross-cloud parity checking as its own automated comparison.

08

Authentication

Provisioning uses an Azure Service Principal (AAP credential) scoped via RBAC to the DR resource group only. The parity checker additionally needs read-only cross-cloud access — AWS read-only IAM role plus the same Azure Service Principal with read scope — kept as two distinct, minimally-scoped credentials.

Ansible Design

Architect's note

The parity checker is deliberately its own role, decoupled from provisioning — it must be able to detect drift regardless of which pipeline (or manual console action) caused it, the same design principle as Project 10 applied across two clouds instead of one.

Code & Roles

roles/azure_provision/tasks/main.yml 
---
# Same fail-closed tag assertion pattern as Project 11's AWS role --
# deliberately kept consistent so both clouds enforce identical governance.
- name: Assert mandatory tags present before provisioning
  ansible.builtin.assert:
    that:
      - request_tags.cost_center is defined
      - request_tags.environment is defined
      - request_tags.dr_pair_instance_id is defined
    fail_msg: "Provisioning refused: mandatory tags missing, including DR pairing reference to the AWS instance."

- name: Create resource group if not present
  azure.azcollection.azure_rm_resourcegroup:
    name: "{{ dr_resource_group }}"
    location: "{{ dr_region }}"

- name: Provision Azure VM mirroring the AWS PROD counterpart
  azure.azcollection.azure_rm_virtualmachine:
    resource_group: "{{ dr_resource_group }}"
    name: "{{ request_tags.application }}-dr"
    vm_size: "{{ azure_equivalent_size[requested_instance_type] }}"
    image: "{{ approved_azure_image }}"
    tags: "{{ request_tags | combine({'ManagedBy': 'ansible-azure-dr'}) }}"
roles/cross_cloud_parity/tasks/main.yml 
---
- name: Fetch AWS security group rules for the PROD counterpart
  amazon.aws.ec2_security_group_info:
    filters:
      group-id: "{{ aws_prod_sg_id }}"
  register: aws_sg
  delegate_to: localhost

- name: Fetch Azure NSG rules for the DR counterpart
  azure.azcollection.azure_rm_securitygroup_info:
    resource_group: "{{ dr_resource_group }}"
    name: "{{ azure_dr_nsg_name }}"
  register: azure_nsg
  delegate_to: localhost

# The two clouds describe rules completely differently -- this normalizes
# both into a common {port, protocol, source} shape before comparing,
# which is the actual engineering work of "cross-cloud parity".
- name: Normalize and compare rule sets
  ansible.builtin.set_fact:
    parity_gaps: "{{ aws_normalized_rules | difference(azure_normalized_rules) }}"
  vars:
    aws_normalized_rules: "{{ aws_sg.security_groups[0].ip_permissions | map('extract_rule_shape') | list }}"
    azure_normalized_rules: "{{ azure_nsg.securitygroups[0].security_rules | map('extract_rule_shape') | list }}"

- name: Alert DR owner on any parity gap
  ansible.builtin.uri:
    url: "{{ slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: "DR parity gap detected: {{ parity_gaps | length }} rule(s) present in AWS PROD but missing in Azure DR for {{ request_tags.application }}."
  delegate_to: localhost
  when: parity_gaps | length > 0

Execution flow, in plain terms

Azure provisioning mirrors Project 11's fail-closed tagging discipline exactly, with an added DR-pairing tag linking each Azure VM back to its AWS counterpart. The parity checker independently pulls live rule state from both clouds' APIs, normalizes them into a common shape since AWS and Azure model network rules differently, and alerts specifically on what's missing — which is exactly the class of gap that caused the failed DR test.

Testing Strategy

  • Deliberately removed one NSG rule in a UAT Azure resource group to confirm the parity checker detects and reports it accurately
  • Validated the rule normalization logic against several real AWS/Azure rule pairs before trusting the comparison broadly
13

Production Deployment

Before enabling ongoing parity checks, a full one-time reconciliation pass closes all currently known gaps between AWS PROD and the existing (drifted) Azure DR environment — the checker then runs daily going forward to prevent recurrence.

14

Rollback Procedure

Disable the scheduled parity-check job template; Azure provisioning rollback follows the same VM-deletion path as any standard resource cleanup, unrelated to the parity logic.

15

Troubleshooting

Parity checker reports false gaps Symptom: Alerts fire for rules that are actually equivalent between clouds.
Root cause (typical): The rule-shape normalization logic doesn't correctly handle Azure's "Any" protocol matching against AWS's explicit protocol list.
Fix: Extend the normalization filter to handle the specific protocol-matching edge case; add it as a regression test case.
16

Monitoring & Validation

A parity dashboard tracks open gap count over time — the target is zero standing gaps, reviewed by the DR team ahead of every scheduled failover test.

Interview Preparation

What was the hardest part of comparing state across two different clouds?
AWS and Azure model network security rules with different shapes and terminology — the real engineering work wasn't calling either API, it was normalizing both into a common representation before any comparison could be meaningful.
How is this different from Project 10's drift detection?
Project 10 compares live state against a single Git-defined desired state within one cloud. This compares live state between two independently managed clouds against each other — there's no single desired-state file, the source of truth is "whatever AWS PROD actually has," which is a fundamentally different comparison problem.
