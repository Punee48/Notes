01

Business Scenario

NovaStack Bank's digital channels team is migrating the mobile banking API layer onto OpenShift, moving away from static VMs. Today, onboarding a new microservice team onto the OpenShift cluster is a two-week manual process — a platform engineer hand-creates the namespace, resource quotas, network policies, and service accounts by running oc commands from memory, with no two namespaces provisioned quite the same way. This inconsistency already caused one incident where a missing resource quota let a single misbehaving pod exhaust a shared node's memory.

Platform Engineering has asked Automation Engineering to build a namespace-as-a-service pipeline: application teams request an OpenShift namespace via ServiceNow, and Ansible provisions a fully governed, consistent namespace — quotas, network policies, RBAC, and a starter deployment — in minutes instead of weeks.

Why this can't stay manualInconsistent manual namespace setup is exactly what caused the resource-exhaustion incident, and a two-week onboarding time is actively blocking the OpenShift migration timeline. Standardized, automated provisioning fixes both the consistency and the speed problem at once.

This is the first project using the kubernetes.core collection against the OpenShift API, and it reuses the fail-closed request-validation pattern from Projects 11 and 12 applied to Kubernetes resource definitions.

Authentication

The automation authenticates to the OpenShift API using a dedicated ServiceAccount with cluster-role permissions scoped to namespace, quota, network policy, and RBAC object creation only — it cannot modify existing namespaces it doesn't own or touch cluster-level configuration.

Ansible Design

Architect's note

Every governance object (quota, network policy, RBAC) is defined as a Jinja2-templated Kubernetes manifest, applied via the same idempotent k8s module call pattern — consistency isn't enforced by code review discipline, it's structurally guaranteed because there's only one template family, parameterized by tier.

├── templates/
│   ├── namespace.yml.j2
│   ├── resourcequota.yml.j2

Code & Roles

vars/quota_tiers.yml 
---
# The tier system is what turns "resource exhaustion incident" into
# "impossible by construction" -- no namespace can be created without
# a quota from this table.
quota_tiers:
  small:
    cpu_limit: "2"
    memory_limit: "4Gi"
    pod_count: 10
  medium:
    cpu_limit: "8"
    memory_limit: "16Gi"
    pod_count: 30
  large:
    cpu_limit: "20"
    memory_limit: "48Gi"
    pod_count: 75
roles/ns_provision/tasks/main.yml 
---
- name: Assert requested tier is a known, approved value
  ansible.builtin.assert:
    that: requested_tier in quota_tiers
    fail_msg: "Provisioning refused: '{{ requested_tier }}' is not an approved quota tier. Choose small, medium, or large."

- name: Create the namespace
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'namespace.yml.j2') }}"

# Quota is applied in the SAME task run as namespace creation, not as
# a follow-up step -- there is no window where the namespace exists
# without a quota attached, which is exactly the gap that caused the
# original incident.
- name: Apply resource quota for the requested tier
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'resourcequota.yml.j2') }}"

- name: Apply default-deny network policy baseline
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'networkpolicy-default-deny.yml.j2') }}"

- name: Bind requesting team to namespace-admin role
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'rolebinding.yml.j2') }}"

- name: Verify quota is actually enforced before handing namespace to the team
  kubernetes.core.k8s_info:
    kind: ResourceQuota
    namespace: "{{ requested_namespace }}"
  register: quota_check
  failed_when: quota_check.resources | length == 0
  # A final read-back check -- we don't just trust that the apply
  # succeeded, we confirm the quota object genuinely exists before
  # telling the requesting team their namespace is ready.

Execution flow, in plain terms

An invalid tier request is rejected before anything is created. Namespace and quota are applied back-to-back in the same run, closing the exact window that let one misbehaving pod exhaust a node in the original incident, followed by the network policy baseline and RBAC binding. The final read-back check confirms the quota object is really there — not just that the API call returned success — before the namespace is considered ready.

Rollback Procedure

Disable the ServiceNow catalog item to pause new self-service requests; an incorrectly provisioned namespace's governance objects can be re-applied with corrected values via the same idempotent role, without deleting the namespace itself.

Troubleshooting

Team reports their pods won't communicate cross-namespace Symptom: App-to-app calls fail immediately after onboarding.
Root cause: This is expected — the default-deny network policy baseline blocks all traffic until explicitly allowed.
Fix: Not a bug — team submits a follow-up request for a specific NetworkPolicy allow-rule to the namespaces they need to reach, reviewed by Security given it's a deliberate exception to the default posture.

Monitoring & Validation

Onboarding time (request submitted → namespace ready) is tracked as the primary success metric, alongside a cluster-wide dashboard confirming zero namespaces exist without an attached ResourceQuota — the direct proof the original incident class is closed.

Security Considerations

  • Default-deny network policy means every namespace starts maximally restricted, with access explicitly granted rather than implicitly open
  • The provisioning ServiceAccount cannot modify namespaces it didn't create, limiting blast radius of a credential compromise

Interview Preparation

How does this prevent the resource-exhaustion incident from happening again?
The quota is applied in the same automated run as the namespace itself, with a read-back verification before the namespace is handed off — there's no manual step where someone could forget it, and no window where the namespace exists without a quota already enforced.
Why default-deny network policy instead of default-allow with monitoring?
Default-deny means a misconfiguration fails toward "nothing works, investigate immediately" rather than "everything's silently reachable" — for a bank's internal network, an explicit-allow model is the safer default even though it adds a follow-up request step for legitimate cross-namespace traffic.
