01

Business Scenario

NovaStack Bank runs Tenable vulnerability scans weekly across the full server estate, producing a report of thousands of CVE findings. Today, Security triages the report and manually raises individual ServiceNow tickets to Infra Ops for remediation — a process so slow that the bank's mean-time-to-remediate for Critical CVEs is 21 days, well past the regulator's 14-day SLA for Critical findings.

Security has asked Automation Engineering to build a vulnerability remediation pipeline that ingests the Tenable scan output directly, maps each CVE to an available fix (package update, config change, or a documented compensating control), auto-remediates what's safe to auto-remediate, and drives everything else through a fast, SLA-tracked ticket queue instead of a manual triage pass.

Why this can't stay manualManual triage of thousands of findings a week is why the SLA is already being missed. The bank needs the scan-to-remediation loop to be measured in hours for the auto-fixable cases, and days — not weeks — for everything else.

This project directly reuses Project 5's check/fix and risk-tier patterns, but the trigger source changes from a static control catalog to a live external scanner feed, and adds CVSS-based prioritization.

Ansible Design

Architect's note

Critical findings are hard-coded to never auto-remediate, regardless of what the risk-tier catalog says for that CVE — this is a deliberate guardrail in the orchestrator itself, not just a catalog setting, so a catalog misconfiguration can't accidentally auto-patch a Critical finding.

Code & Roles

playbooks/remediation_cycle.yml 
---
- name: Vulnerability remediation cycle
  hosts: all
  tasks:
    - name: Ingest latest findings for this host from Tenable
      ansible.builtin.include_role:
        name: vuln_ingest

    - name: Map each finding to an available fix
      ansible.builtin.include_role:
        name: vuln_map_fix

    # Hard guardrail lives HERE, in the orchestrator, not only in the
    # catalog -- a catalog typo must never be able to auto-patch a Critical.
    - name: Auto-remediate only Low/Medium findings with a known fix
      ansible.builtin.include_role:
        name: vuln_remediate
      loop: "{{ mapped_findings | selectattr('severity', 'in', ['low','medium']) | selectattr('fix_available', 'equalto', true) | list }}"
      loop_control:
        loop_var: finding

    - name: Raise SLA-tracked tickets for everything else
      ansible.builtin.include_role:
        name: vuln_ticket_queue
      loop: "{{ mapped_findings | rejectattr('severity', 'in', ['low','medium']) | list }}"
      loop_control:
        loop_var: finding
roles/vuln_remediate/tasks/main.yml 
---
- name: Apply the specific package version fix for this CVE
  ansible.builtin.dnf:
    name: "{{ finding.package_name }}-{{ finding.fixed_version }}"
    state: present
  register: remediation_result

- name: Trigger a targeted re-scan of just this finding
  ansible.builtin.uri:
    url: "https://tenable.internal.novastack.bank/api/scans/targeted"
    method: POST
    body_format: json
    body:
      host: "{{ inventory_hostname }}"
      plugin_id: "{{ finding.plugin_id }}"
  delegate_to: localhost
  # We verify against the scanner's own re-check rather than trusting
  # our own "package updated" result -- the scanner is the source of
  # truth Security actually reports against.

Execution flow, in plain terms

Every host's findings are ingested, mapped to a fix, then split by severity: Low/Medium with a known fix go straight to auto-remediation, everything else — including all Criticals regardless of fix availability — goes to a ticket queue with an SLA clock. Verification is done by triggering a real targeted re-scan, not by trusting the playbook's own "changed" status.

Rollback Procedure

Disable auto-remediation per severity tier; a bad package update can be rolled back via dnf history undo as in Project 1's pattern.

Troubleshooting

Fix mapping is wrong for a CVE Symptom: Package updated but re-scan still shows the finding.
Root cause (typical): Mapping engine matched the wrong CVE-to-package version, common with backported security patches.
Fix: Correct the mapping entry, re-run for that specific finding, feed the correction back into the mapping engine's rule set.

Interview Preparation

Why hard-code the Critical guardrail in the orchestrator instead of just the catalog?
A catalog is data anyone with edit access could get wrong; a hard-coded severity check in the orchestrating playbook is a structural guarantee that survives a catalog mistake — defense in depth for the highest-stakes decision in the pipeline.
Why verify with a targeted re-scan instead of trusting the Ansible result?
Ansible reporting "changed" only proves a command ran, not that the vulnerability is actually gone from the scanner's perspective — and the scanner's result is what Security and the regulator actually trust as evidence.
