Deploying a Basic AWS Workload and Understanding Its Operational Lifecycle

Our first assignment as the newly-formed Cloud Engineering function inside a mid-size retail company: get one internal application off a laptop and into AWS, the right way — with an IAM role instead of hardcoded keys, a security group instead of "allow all," and CloudWatch watching it instead of nobody.

01 Production Story

Infrastructure Manager — Priya Nandan

"We just hired our first Cloud Engineer — that's you. Our Merchandising team has been running an internal inventory-reconciliation script on Raj's personal laptop for the last eight months. Every night he runs a Python job by hand that pulls a CSV export, reconciles stock counts, and writes a report. Last week he was on leave for two days and nobody ran it. The warehouse team made reorder decisions off stale numbers and we over-ordered by about 4,000 units of a seasonal SKU.

I don't want a laptop to be a single point of failure for a business process again. I want this running on AWS: always available, not tied to one person's machine, and something the rest of the team can see and operate — not a black box only Raj understands. Security has one hard requirement already: no long-lived AWS access keys sitting in a script. Can you take this and come back with something we can actually run in production?"

Why this is Assignment 1

Every AWS journey has to start somewhere concrete. Rather than opening with "what is EC2," we're going to hit the wall that makes EC2, IAM roles, and basic monitoring necessary in the first place — a real workload that needs to leave someone's laptop. Every service introduced below is introduced because this story requires it, not because it's next on a syllabus.

Existing Environment

  • Script runs manually on an employee laptop via cron-like scheduling that only fires when the laptop is on and logged in.
  • AWS access keys for S3 (where the CSV export lands) are hardcoded in the script.
  • No monitoring — if the job fails silently, nobody finds out until someone downstream notices bad numbers.
  • No version control, no documented runbook, no backup engineer who can run it.

03 Architecture Design

High-Level Architecture

At this stage we're intentionally simple: one EC2 instance, running in the account's default VPC, with an IAM role attached (not access keys), reading and writing to two S3 locations, with CloudWatch watching basic health. No load balancer, no auto scaling, no multi-AZ — none of that is justified yet by the requirements above, and adding it now would be solving a problem the business doesn't have.

EventBridge Schedulertriggers job nightly at 01:00
↓
EC2 Instance (t3.micro)runs reconciliation script
↓ assumes
IAM Instance Rolescoped S3 read/write policy — no access keys
↓ reads / writes
S3 Bucket/inbound (raw CSV) · /reports (output)
↓ emits metrics/logs
CloudWatchLogs + Alarm on job failure

Note there's no Internet Gateway path drawn for inbound traffic — nothing calls this instance from the internet. It only reaches out to AWS APIs (S3, CloudWatch) over the default VPC's route to the internet, or better, via a VPC endpoint (we introduce endpoints properly in Assignment 11 — for now, outbound-only internet access through the default VPC is acceptable for a foundation lab).

Security Architecture

  • No inbound access from the internet at all — this instance doesn't serve traffic, so there is no reason to open any inbound port except SSH, and even that is scoped to a specific IP for lab purposes.
  • IAM instance role, not IAM user access keys — the instance assumes a role and gets short-lived, automatically-rotated credentials via the EC2 metadata service.
  • Least privilege S3 policy — the role can only GetObject/ListBucket on the inbound prefix and PutObject on the reports prefix. It cannot delete objects, touch other buckets, or call unrelated AWS APIs.

04 Architecture Decision Making

Decision: IAM Instance Role vs. Access Keys

We could generate an IAM user, create an access key/secret pair, and store it in the script or an environment variable. This is the fastest thing to set up and it's exactly what got Raj's laptop into trouble — a credential that lives forever, that can be copied, committed to a repo, or left on a laptop that gets stolen.

An IAM instance role is attached to the EC2 instance itself. AWS automatically supplies temporary credentials to anything running on that instance via the instance metadata service, and those credentials rotate automatically roughly every 6 hours. There is no secret to leak, because there's no long-lived secret at all.

Decision: IAM instance role. This directly satisfies Security's hard requirement and costs nothing extra to implement.

Decision: EC2 vs. Lambda for This Job

EC2 (t3.micro, scheduled)Lambda
Fits the jobYes, but it's a running server for a 2-minute jobYes — this is a short, stateless, event-triggered batch job
CostInstance runs (or must be started/stopped) even though it's idle 23h58m/dayPay only for the ~2 minutes of execution per night — effectively free tier forever
Operational overheadPatch the OS, manage the instance lifecycleNo OS to patch, no instance to manage
Why we're still choosing EC2 here

Lambda is genuinely the better production answer for this exact workload, and we'll build the Lambda version of a scheduled job in a later assignment once serverless concepts (execution role, layers, timeouts, packaging) have been introduced properly. For this foundation assignment, the learning objective is EC2 fundamentals and the instance lifecycle — so we're deliberately using EC2 even though Lambda would be the better real-world choice for a 2-minute nightly script. Priya, as our stakeholder, is fine with this because the point right now is "get it off the laptop and into AWS safely" — we'll optimize architecture in later assignments (see Assignment 18: serverless).

05 Hands-On Implementation

Prerequisites

  • An AWS account with console + programmatic access for your own IAM user (not root)
  • AWS CLI v2 installed and configured (aws configure) with your personal IAM user credentials — this is fine for you as the engineer; the workload itself must not use long-lived keys
  • Terraform installed (v1.6+)
  • A default VPC in your target region (every new AWS account has one unless it was deliberately removed)

Folder Structure

06 Terraform Implementation

We're introducing Terraform starting now, even for something this small, because the habit of describing infrastructure as code — rather than clicking it into existence — is worth building from day one. Every resource below is explained argument by argument.

variables.tf

variables.tf

  # The AWS region we deploy into. Declaring it as a variable (instead of
  # hardcoding it in every resource) means the same code can target another
  # region just by overriding this one value.
  description = "AWS region to deploy the reconciliation workload into"
  type        = string
  default     = "ap-south-1"
}

variable "instance_type" {
  description = "EC2 instance type for the batch job"
  type        = string
  default     = "t3.micro"
  # t3.micro is free-tier eligible and far more than this 2-minute script needs.
}

variable "bucket_name" {
  description = "S3 bucket for inbound CSV exports and outbound reports"
  type        = string
  # No default — S3 bucket names are globally unique across ALL AWS accounts,
  # so we force the caller to supply one rather than risk a collision.
}

variable "allowed_ssh_cidr" {
  description = "CIDR block allowed to SSH into the instance (your IP /32, not 0.0.0.0/0)"
  type        = string
}

main.tf — Networking & Security Group

main.tf (part 1 of 3)
provider "aws" {
  region = var.region
  # Tells the AWS provider which region's API endpoint to talk to for every
  # resource below that doesn't explicitly override it.
}

data "aws_vpc" "default" {
  default = true
  # A data source READS existing infrastructure instead of creating it.
  # We're deliberately using the account's default VPC for this foundation
  # lab rather than building a custom VPC — that's Assignment 2's job.
}

data "aws_subnets" "default" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.default.id]
  }
  # Fetches every subnet ID that belongs to the default VPC so we can pick one.
}

resource "aws_security_group" "reconcile_sg" {
  name        = "reconcile-job-sg"
  description = "Security group for the nightly reconciliation instance"
  vpc_id      = data.aws_vpc.default.id

  # INBOUND: only SSH, only from the engineer's own IP. Nothing else needs to
  # reach this box — it doesn't serve any traffic.
  ingress {
    description = "SSH from engineer workstation only"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.allowed_ssh_cidr]
  }

  # OUTBOUND: allow all. The instance needs to reach S3 and CloudWatch APIs
  # over HTTPS; restricting egress further is a hardening step we revisit
  # once we introduce VPC endpoints (Assignment 11).
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name    = "reconcile-job-sg"
    Project = "inventory-reconciliation"
  }
}

main.tf — IAM Role (no access keys)

main.tf (part 2 of 3)
resource "aws_iam_role" "reconcile_role" {
  name = "reconcile-job-role"

  # The assume_role_policy is the TRUST policy — it defines WHO/WHAT is
  # allowed to assume this role. Here, only the EC2 service itself may.
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "ec2.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy" "reconcile_s3_policy" {
  name = "reconcile-s3-access"
  role = aws_iam_role.reconcile_role.id

  # This is the PERMISSIONS policy — what the role can actually DO once
  # assumed. Scoped to exactly the two prefixes this job touches, and only
  # the specific S3 actions it needs. No s3:DeleteObject, no wildcard "s3:*".
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid      = "ReadInboundCSV"
        Effect   = "Allow"
        Action   = ["s3:GetObject", "s3:ListBucket"]
        Resource = [
          "${aws_s3_bucket.reconcile_bucket.arn}",
          "${aws_s3_bucket.reconcile_bucket.arn}/inbound/*"
        ]
      },
      {
        Sid      = "WriteReports"
        Effect   = "Allow"
        Action   = ["s3:PutObject"]
        Resource = ["${aws_s3_bucket.reconcile_bucket.arn}/reports/*"]
      }
    ]
  })
}

resource "aws_iam_instance_profile" "reconcile_profile" {
  name = "reconcile-job-profile"
  role = aws_iam_role.reconcile_role.name
  # An instance profile is the container that actually attaches an IAM role
  # to an EC2 instance — you can't attach a role to an instance directly,
  # it has to go through this profile resource.
}

  instance_type          = var.instance_type
  subnet_id              = data.aws_subnets.default.ids[0]

resource "aws_cloudwatch_log_group" "reconcile_logs" {
  name              = "/reconcile-job/execution"
  retention_in_days = 30
  # Without an explicit retention period, CloudWatch Logs keeps everything
  # forever, which quietly costs money. 30 days is enough to debug a failed
  # run without paying to store logs from six months ago.
}

resource "aws_cloudwatch_metric_alarm" "instance_status_check" {
  alarm_name          = "reconcile-instance-status-check-failed"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods   = 1
  metric_name         = "StatusCheckFailed"
  namespace           = "AWS/EC2"
  period              = 300
  statistic           = "Maximum"
  threshold           = 0
  dimensions          = { InstanceId = aws_instance.reconcile_instance.id }
  alarm_description   = "Fires if the reconciliation instance fails an EC2 status check"
  # A StatusCheckFailed > 0 means AWS itself has detected the instance is
  # unreachable or has an underlying hardware/software problem.
}
terraform plan → apply, what happens internally

terraform init downloads the AWS provider plugin and sets up the local (or remote) state backend. terraform plan reads your current .tf files, compares them against the last known state, and calls AWS's describe-type APIs to see what already exists — producing a diff of what it intends to create/change/destroy, without touching anything yet. terraform apply re-runs that plan and, after your confirmation, calls the actual create/update AWS APIs in dependency order (the IAM role before the instance profile before the EC2 instance, because Terraform builds a dependency graph from the resource references you wrote, like aws_iam_role.reconcile_role.name).

PartMeaning
describe-instancesRead-only subcommand — lists EC2 instances. Safe to run any time; changes nothing.

--queryA JMESPath expression that trims the (very verbose) raw JSON response down to just the fields we care about.

Expected output: one row showing the instance ID, state (running), and the IAM instance profile ARN — confirming the role attached correctly and there's no access key involved.

aws sts get-caller-identity \
  --endpoint-url # (run this FROM INSIDE the instance via SSM/SSH, not your laptop)

Run from inside the instance, this confirms the instance is authenticating as the reconcile-job-role — not as your personal IAM user — proving the role-based credential chain works end to end. This command is read-only and safe; reversing it isn't applicable since it changes nothing.

08 Validation & Testing

  • Infrastructure test: terraform plan shows zero pending changes after apply — confirms actual AWS state matches code (no drift).
  • Security test: attempt to SSH into the instance from an IP other than allowed_ssh_cidr — connection must time out, confirming the security group is doing its job.
  • IAM test: from inside the instance, attempt aws s3 ls s3://some-other-random-bucket — must fail with AccessDenied, confirming least privilege (the role can't touch buckets outside its policy).
  • Application test: manually trigger reconcile.py once via SSH and confirm a report object lands under s3://<bucket>/reports/.
  • Failure test: stop the instance manually and confirm the CloudWatch alarm transitions to ALARM state within one evaluation period.

10 Production Incident

02:15 AM — On-call phone

The reconciliation report never landed in S3 last night. Merchandising notices at 8 AM standup because the dashboard they built off it is empty. Nobody paged anyone — there's no alarm yet for "the job ran but produced nothing," only for "the whole instance is unreachable." The instance itself shows as running and healthy in the console.

Investigation

bash — from the instance via SSH
tail -n 100 /var/log/cloud-init-output.log
crontab -l
sudo cat /var/log/reconcile-job.log

The crontab entry is present and correct. The log shows the script started at 01:00 as scheduled, but exited after 2 seconds with a Python traceback:

reconcile-job.log
botocore.exceptions.ClientError: An error occurred (AccessDenied) when calling
the GetObject operation: User: arn:aws:sts::...:assumed-role/reconcile-job-role/i-0abc...
is not authorized to perform: s3:GetObject on resource:
"arn:aws:s3:::retail-reconcile-prod/inbound/2026-08-07/stock_export.csv"

Root Cause

The Merchandising team's export tool writes the daily CSV to a date-partitioned path — inbound/2026-08-07/... — but our IAM policy above only grants access to inbound/* at one level, and the bucket's actual object key has an extra path segment the policy's wildcard doesn't match the way we assumed, combined with the fact that the export landed under a slightly different prefix than what was scoped in review. In short: the IAM policy's resource ARN pattern and the application's actual S3 key layout were never verified against each other before go-live.

Immediate Fix

Manually run aws s3 cp using an engineer's own (properly scoped, temporary) credentials to move last night's file into the reconciliation flow so Merchandising can get an up-to-date report the same morning.

Permanent Fix

Corrected IAM policy resource
Resource = [
  "${aws_s3_bucket.reconcile_bucket.arn}",
  "${aws_s3_bucket.reconcile_bucket.arn}/inbound/*"   # /* already matches all nested prefixes/keys —
]                                                       # the real bug was a stale bucket policy from a
                                                          # prior manual test that explicitly DENIED this path
                                                          # and was never cleaned up. Removed the conflicting
                                                          # bucket policy statement; IAM Deny always overrides Allow.

Validation

Re-ran the script manually the next night against a test object placed at the same date-partitioned path; confirmed successful GetObject and a report written to reports/.

Monitoring Improvement

Added a second CloudWatch alarm based on a custom metric the script now publishes on completion (ReconcileJobSuccess = 1), so "the job ran but failed" is now detectable — not just "the instance is down."

Prevention / Lessons Learned

  • Always check for both IAM identity-based policies and any resource-based bucket policy — an explicit Deny anywhere in the evaluation always wins over an Allow.
  • Test the actual IAM policy against a real object key before go-live, not just against the "shape" of the path.
  • "The instance is running" is not the same as "the job succeeded" — status checks alone are insufficient monitoring for a batch job.

11 Troubleshooting Methodology

The instinct under pressure is to jump straight to "let's just widen the IAM policy." Resist that. The senior-engineer path is always: symptom → evidence → recent changes → metrics/logs → narrow down → root cause → fix → validate → prevent recurrence. Widening a policy without understanding why access was denied just trades one incident for a future security incident.

16 Practice Challenge

Priya comes back: "Finance asked why we're paying for a server that's idle 99.9% of the time. Can you make this cost-efficient without losing the security properties we just built?"

Requirement: Redesign the compute layer so nothing runs (and nothing is billed) except during the ~2 minutes the job actually executes, while keeping the no-access-keys, least-privilege security posture.

Acceptance Criteria: No compute resource is billed while idle; the IAM role's trust policy and permissions policy pattern still apply; the job still triggers automatically on a nightly schedule.

Hints: What AWS compute service bills only for execution time? What triggers it on a schedule without a permanently-running server?

Challenge Solution

Replace the EC2 instance + user_data cron job with an AWS Lambda function containing the same reconcile.py logic, triggered by an Amazon EventBridge scheduled rule (cron expression, e.g. cron(0 1 * * ? *) for 01:00 daily). The Lambda gets its own execution role (conceptually identical to the EC2 instance role — a trust policy allowing lambda.amazonaws.com to assume it, and the same scoped S3 permissions policy). No server exists between invocations, so there is nothing to bill while idle, and no SSH/security-group surface at all since nothing is ever "up" waiting for a connection. This is exactly the architecture we'll build properly, with full serverless concepts, in the Serverless assignment later in the course.

17 Interview Preparation

Q1 · AWS FundamentalsWhy use an IAM role instead of an IAM user with access keys for a workload running on EC2?

An IAM role attached via an instance profile provides temporary, automatically-rotating credentials through the instance metadata service — there's no long-lived secret to leak, rotate manually, or accidentally commit to source control. Access keys are static until manually rotated and are a common source of credential leaks in real incidents.

Follow-up: "How does the instance actually retrieve those credentials?" — Via the EC2 Instance Metadata Service (IMDS) at 169.254.169.254; the AWS SDK/CLI checks this automatically as part of its default credential provider chain.
Q2 · SecurityIf a bucket policy explicitly denies an action and an IAM policy explicitly allows it, what happens?

Deny always wins. AWS evaluates all applicable policies — identity-based and resource-based — and if any statement explicitly denies an action, that overrides any allow, regardless of where the allow came from.

Follow-up: "How would you debug an unexpected AccessDenied?" — Check the IAM policy attached to the role/user, any resource-based policy (bucket policy), any SCPs at the Organization level, and any permission boundaries — in that order of likelihood for a single-account setup.
Q3 · Production ScenarioA nightly batch job's EC2 instance shows healthy in the console, but the expected output never appeared. Walk me through your triage.

Start with evidence, not assumptions: check the application-level logs (not just instance health) since "instance healthy" only confirms EC2/OS-level status checks, not application success. Pull CloudWatch Logs or SSH in and check the script's own log file for exceptions, confirm the schedule actually fired, and check IAM/network access from the instance's perspective before assuming the code itself is broken.

Follow-up: "What would you add to catch this earlier next time?" — A custom CloudWatch metric published by the application itself on success/failure, with an alarm on that metric — instance-level health checks alone can't tell you whether the job logic succeeded.
Q4 · Cost OptimizationWhen would you choose EC2 over Lambda for a scheduled job, given Lambda is usually cheaper for short workloads?

When the job's runtime, memory, or dependency footprint exceeds Lambda's limits (15-minute max execution, package size limits), when it needs a persistent local filesystem/state between invocations, or when the workload is genuinely long-running rather than short and bursty. For a 2-minute CSV job, Lambda is the better default — EC2 only makes sense if there's a concrete reason it doesn't fit Lambda's model.

Follow-up: "What if the job occasionally runs 20+ minutes during peak season?" — That crosses Lambda's timeout ceiling, which would push the decision toward Fargate (serverless containers with no timeout limit) rather than falling back to a full EC2 instance.
Q5 · TerraformWhat's the difference between terraform plan and terraform apply, and why run plan first?

plan computes and displays the diff between desired state (your code) and actual state (what's really in AWS, tracked via the state file) without changing anything. apply executes that diff. Running plan first — ideally reviewed by a second engineer — is how you catch an unintended destroy/replace (like a change that forces resource recreation) before it happens in a real environment.

Follow-up: "What's a change that would force resource replacement rather than an in-place update?" — Changing an EC2 instance's AMI ID, for example — Terraform will show that as destroy-then-create, not update-in-place, because AMI isn't a mutable attribute of a running instance.
Q6 · Manager RoundHow do you decide how much infrastructure to build for a small internal tool versus over-engineering it?

I map the architecture to the actual stated requirements, not to what I know how to build. In this assignment, the business need was "always available, secure, off one laptop" — that's satisfied by one instance, one IAM role, basic monitoring. Adding auto scaling, multi-AZ, or a load balancer wouldn't address any requirement Priya actually raised, and would add operational and cost overhead without business justification. I'd rather ship the right-sized solution and revisit it explicitly when requirements change than build for a scale that isn't there yet.

Follow-up: "What would make you reconsider that decision?" — If the job's output became business-critical in real time rather than a nightly batch, or if the business explicitly asked for higher availability guarantees — at that point the added complexity would be justified by a real requirement.
