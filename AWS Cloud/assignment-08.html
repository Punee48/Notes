Designing and Operating a Managed Relational Database Architecture

Every quote the portal generates today disappears the moment the request finishes — there's nowhere durable to store it. Karthik needs real persistence, and this time the requirement everyone anticipated back in Assignment 2 finally arrives: a database tier that must never be reachable from the internet, and must survive an AZ failure exactly like the app tier now does.

Difficulty: Intermediate Domain: Insurance Services: RDS PostgreSQL · Multi-AZ · Read Replica IaC: Console + CLI + Terraform Est. lab time: 3–4 hrs
Progress: Assignment 8 of 25

01 Production Story

Application Team — Karthik Iyer

"We've been demoing with an in-memory placeholder this whole time — every quote vanishes the second the process restarts, which the ASG now does automatically whenever it scales in. We need a real database. Customers, policies, generated quotes — needs to persist, needs to survive a database failure, and per Ananya's original rule from Assignment 2, it absolutely cannot be reachable from anywhere except our app tier."

Why this is Assignment 8

Remember Assignment 2's CIDR planning note — "leaving headroom for a future tier without re-addressing anything that exists"? This is that future tier. We're adding a dedicated, even-more-isolated data subnet pair to the existing VPC, separate from the app tier's private subnets, so the database sits behind a second network boundary even relative to the app servers that talk to it — not just behind the internet-facing boundary from Assignment 2.

03 Architecture Design

RDS Standbydata-b subnet · same instance class, not directly reachable

Two new data subnets — 10.20.21.0/24 and 10.20.22.0/24 — join the VPC from Assignment 2, one per AZ, using CIDR ranges Assignment 2 deliberately left free. A DB Subnet Group spans both, which is what lets RDS Multi-AZ place the standby in the second AZ automatically. Neither data subnet has a route to an Internet Gateway or a NAT Gateway at all — the database tier doesn't need outbound internet access the way the app tier does, so it gets none, tightening the boundary even further than the app tier's own private subnets.

04 Architecture Decision Making

Decision: RDS Multi-AZ vs. RDS Read Replica — Not the Same Thing

Multi-AZ (standby)Read Replica
ReplicationSynchronous — standby is always an exact, up-to-the-transaction copyAsynchronous — can lag behind the primary by a small amount
PurposeAutomatic failover for availability — standby is not queryable directly during normal operationRead scaling — offload read-heavy queries (e.g. reporting) from the primary; can itself be promoted to standalone in a DR scenario, but that's a manual/DR action, not automatic failover
Fits this requirementYes — this assignment's explicit requirement is automatic AZ failoverNot this assignment's requirement, though flagged as a near-term need once reporting queries start competing with live application traffic

Decision: enable Multi-AZ for the primary requirement. A read replica is noted as a likely Assignment-level addition later once reporting/analytics queries are a real, named requirement — adding one prematurely would be solving a problem that doesn't exist yet, echoing the "don't over-engineer" principle from Assignment 1.

Decision: RDS vs. Self-Managed PostgreSQL on EC2

Self-managed PostgreSQL on EC2 would require us to own patching, backup scripting, failover orchestration, and monitoring entirely by hand — essentially rebuilding, worse, everything RDS Multi-AZ provides natively. Given this is a mainstream relational workload with no unusual extension or version requirement RDS can't satisfy, RDS is the clear choice — the operational overhead of self-managing a database has no offsetting benefit here.

05 AWS Console — Manual Steps

  1. Create the two data subnets. VPC console → Subnets → Create subnet, in quote-portal-vpc: data-a (10.20.21.0/24, ap-south-1a), data-b (10.20.22.0/24, ap-south-1b). Neither is associated with any route table that has an IGW or NAT route — leave them on the VPC's default (no-internet) main route table, or an explicitly local-only route table.
  2. Create the DB security group. EC2 console → Security Groups → Create → name sg-db → inbound: PostgreSQL (5432) from source sg-app only — the same security-group-chaining pattern from Assignment 3, now applied one tier deeper.
  3. Create the DB Subnet Group. RDS console → Subnet groups → Create DB subnet group → VPC quote-portal-vpc → add both data-a and data-b. RDS Multi-AZ requires the subnet group to span at least two AZs to know where it's allowed to place the standby.
  4. Store the master credentials in Secrets Manager first. Secrets Manager console → Store a new secret → "Credentials for RDS database" type → generate a strong random password → name quote-portal/db-credentials. Doing this before creating the RDS instance lets us reference the secret directly during creation rather than setting a password by hand and rotating it in afterward.
  5. Create the RDS instance. RDS console → Create database → Engine: PostgreSQL → Templates: Production → enable Multi-AZ deployment → DB subnet group from step 3 → VPC security group: sg-db only → Public access: No → credentials: "Manage master credentials in Secrets Manager" pointing at the secret from step 4 → enable automated backups with a defined retention window and point-in-time recovery.
  6. Grant the app role read access to the DB secret. IAM console → the app role from Assignment 5 → add an inline policy for secretsmanager:GetSecretValue scoped to this new secret's ARN specifically, alongside (not replacing) its existing rating-API-key permission.
  7. Verify connectivity from an app instance. SSM into a running app instance → psql against the RDS endpoint using credentials fetched at runtime from Secrets Manager → confirm connection succeeds.

06 AWS CLI

aws rds create-db-subnet-group \
  --db-subnet-group-name quote-portal-db-subnets \
  --db-subnet-group-description "Data tier subnets" \
  --subnet-ids $DATA_A_SUBNET_ID $DATA_B_SUBNET_ID

# Create the Multi-AZ RDS instance, credentials auto-managed in Secrets Manager
aws rds create-db-instance \
  --db-instance-identifier quote-portal-db \
  --engine postgres --engine-version 16.3 \
  --db-instance-class db.t3.medium \
  --allocated-storage 50 \
  --multi-az \
  --db-subnet-group-name quote-portal-db-subnets \
  --vpc-security-group-ids $SG_DB_ID \
  --no-publicly-accessible \
  --manage-master-user-password \
  --backup-retention-period 7

07 Terraform Implementation

main.tf — Data Subnets & DB Security Group

main.tf (part 1 of 3)
variable "data_subnet_cidrs" {
  type    = list(string)
  default = ["10.20.21.0/24", "10.20.22.0/24"]
  # The exact headroom Assignment 2 deliberately reserved by starting
  # private subnets at .11 instead of .3 — no re-addressing needed anywhere.
}

resource "aws_subnet" "data" {
  count             = length(var.data_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.data_subnet_cidrs[count.index]
  availability_zone = var.azs[count.index]
  # No map_public_ip_on_launch, and — critically — NOT associated with any
  # route table that has an IGW or NAT route. RDS instances here have no
  # path to or from the internet at all, tighter than the app tier's private
  # subnets which at least have outbound-via-NAT.
  tags = { Name = "data-${var.azs[count.index]}", Tier = "data" }
}

resource "aws_security_group" "db" {
  name   = "sg-db"
  vpc_id = aws_vpc.main.id

  ingress {
    description     = "PostgreSQL, app tier only"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]
    # Same security-group-chaining pattern as Assignment 3's sg-app rule,
    # now one tier deeper — the DB will never accept a connection from
    # anything that isn't a member of sg-app, regardless of subnet or IP.
  }
  egress {
    from_port = 0; to_port = 0; protocol = "-1"; cidr_blocks = ["0.0.0.0/0"]
  }
  tags = { Name = "sg-db" }
}

resource "aws_db_subnet_group" "main" {
  name       = "quote-portal-db-subnets"
  subnet_ids = aws_subnet.data[*].id
}

main.tf — RDS Instance

main.tf (part 2 of 3)
resource "aws_db_instance" "main" {
  identifier     = "quote-portal-db"
  engine         = "postgres"
  engine_version = "16.3"
  instance_class = "db.t3.medium"
  allocated_storage = 50
  storage_encrypted = true
  # Encryption at rest, consistent with the S3 encryption posture from
  # Assignment 4 — no reason for the database to be the one unencrypted
  # store of sensitive customer/policy data in the whole architecture.

  multi_az               = true
  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]
  publicly_accessible    = false

  manage_master_user_password = true
  # Terraform provisions the secret in Secrets Manager on our behalf and
  # wires it to the instance — we never see or set a plaintext password
  # anywhere in this configuration.

  backup_retention_period = 7
  backup_window           = "17:00-17:30"   # UTC — chosen to land in the lowest-traffic window
  deletion_protection     = true
  # deletion_protection = true means `terraform destroy` will FAIL against
  # this specific resource until explicitly disabled — a deliberate guard
  # rail against a database being destroyed by an ordinary destroy run.

  skip_final_snapshot = false
  final_snapshot_identifier = "quote-portal-db-final"
  # Even when deletion IS intentional, a final snapshot is taken first —
  # belt-and-suspenders alongside deletion_protection above.
}

output "db_secret_arn" {
  value = aws_db_instance.main.master_user_secret[0].secret_arn
  # Exposes the auto-generated secret's ARN so it can be referenced by the
  # app role's IAM policy below without hardcoding anything.
}

main.tf — App Role Access to DB Secret

main.tf (part 3 of 3)
resource "aws_iam_role_policy" "app_db_secret_access" {
  name = "read-db-credentials-only"
  role = aws_iam_role.quote_portal_app.id  # same role from Assignment 5, extended — not a new role
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = "secretsmanager:GetSecretValue"
      Resource = aws_db_instance.main.master_user_secret[0].secret_arn

      # separately-scoped secret permissions (rating API key + DB credentials),
      # each least-privilege on its own, rather than one broad grant covering
      # "all secrets" which would violate the least-privilege posture from
      # Assignment 5.
    }]
  })
}

08 Validation & Testing

  • Connectivity test: from an app instance, connect using credentials fetched from Secrets Manager at runtime — confirm success.
  • Isolation test: attempt the same connection from an unrelated instance not in sg-app — must fail, and confirm the RDS instance has no public endpoint at all via describe-db-instances.
  • Failover test: trigger a manual failover (aws rds reboot-db-instance --force-failover) and measure application-observed downtime — should be brief (typically under a couple of minutes) and self-recovering, with no manual DNS or connection-string change required, since the endpoint hostname stays the same across failover.
  • Backup/restore test: perform a point-in-time restore to a new, temporary DB instance and confirm the restored data matches expectations — an untested backup is an assumption, same principle as Assignment 4's EBS snapshot test.
  • Encryption test: confirm StorageEncrypted: true via describe-db-instances.

10 Production Incident

During the failover test itself

The manual failover test triggers as expected — but the application logs show a burst of connection errors lasting nearly four minutes, longer than the "typically under a couple of minutes" expectation, and the ASG's scale-out (still armed from Assignment 7's target tracking) fires unnecessarily in response to the resulting error-driven CPU spike from retry storms.

Investigation

bash — application logs
grep "connection refused\|timeout" /var/log/quote-portal/app.log | wc -l
# Large count clustered in a tight time window right after failover began

The application's database client library is using default connection settings with no retry backoff and a long TCP timeout — each request that hit the old (now-standby) endpoint during the failover window hung for its full timeout duration before failing, rather than failing fast and retrying, and simultaneous requests were making the problem compound rather than recovering gracefully.

Root Cause

Not an RDS problem — Multi-AZ failover itself worked as designed. The gap was entirely in the application's connection handling: no short connection timeout, no exponential backoff retry logic, so a brief infrastructure-level failover turned into an extended application-level error storm.

Immediate Fix

None needed for RDS itself — failover completed successfully. Flagged the connection-handling gap to Karthik's team as the actual fix required.

Permanent Fix

Application team implemented a short (2-3 second) connection timeout with exponential backoff retry, so a brief failover now results in a handful of fast-failing, fast-retrying requests instead of a pile of long-hanging ones.

Validation

Re-ran the failover test after the application fix — observed downtime dropped to under 30 seconds, and the ASG's CPU-based scaling policy no longer misfired in response.

Lessons Learned

  • RDS Multi-AZ handles the infrastructure side of failover correctly — but the application's connection-handling behavior determines whether that translates into a brief blip or an extended outage from the user's perspective.
  • An infrastructure event (DB failover) can trigger a seemingly unrelated symptom elsewhere (unnecessary ASG scale-out) — worth checking cross-system effects, not just the directly-affected component, when investigating.

16 Practice Challenge

Karthik comes back: "The finance team wants a daily report querying quote volume and conversion rates — running that against the primary database during business hours is exactly the kind of thing you flagged as a future need. Is now the time?"

Requirement: Add reporting query capacity without letting reporting workload compete with live application traffic on the primary database.

Acceptance Criteria: Reporting queries run against a separate database endpoint. The primary database's performance for live application traffic is unaffected by reporting query load.

Hints: This is precisely the scenario the Multi-AZ vs. Read Replica comparison earlier flagged as the trigger for revisiting that decision.

Challenge Solution

Add an RDS Read Replica (aws_db_instance with replicate_source_db pointing at the primary) — a separate instance receiving asynchronously-replicated data, with its own distinct endpoint. Finance's reporting queries point at the replica's endpoint instead of the primary's; because replication is asynchronous, there's a small, generally acceptable lag for reporting purposes, but zero query-level contention with live application traffic on the primary. This is exactly the "not this assignment's requirement, but flagged for later" item from the architecture decision section — now the actual, named business need (Finance's daily report) is what justifies adding it, rather than adding it speculatively.

17 Interview Preparation

Q1 · DatabasesWalk through exactly what happens, mechanically, during an RDS Multi-AZ failover.

The synchronous standby in the second AZ is already an up-to-date, continuously replicated copy of the primary. On failover — whether triggered by an actual failure or manually for testing — RDS promotes the standby to primary and updates the DNS record behind the instance's existing endpoint hostname to point at it. Applications don't need any endpoint or connection-string change; they simply need to handle the brief window where the old connection is no longer valid and DNS is propagating, which is exactly the gap this assignment's incident exposed in the application's connection handling.

Follow-up: "Why didn't the application just automatically reconnect cleanly?" — Because its database client was using long timeouts with no retry/backoff logic — it hung on the stale connection rather than failing fast and attempting a fresh connection against the (already-updated) DNS record.
Q2 · NetworkingWhy give the data subnets no internet route at all, when the app tier's private subnets at least have outbound-via-NAT?

The app tier genuinely needs outbound access for things like the third-party rating API and OS patching. The database tier has no equivalent legitimate need to reach the internet — RDS handles its own patching internally as a managed service. Removing even the outbound path entirely is a "why would this ever need it" security posture, not a functional requirement compromise, and it reduces the theoretical blast radius if the database tier were ever compromised through some other vector.

Follow-up: "What if the database needed to call an external service for some reason, like a compliance webhook?" — That would be a deliberate, reviewed exception requiring a NAT Gateway route added specifically for that data subnet — not a default, and worth questioning whether that logic actually belongs at the application tier instead.
Q3 · Production ScenarioAn induced failover test takes far longer than expected. How do you determine whether the problem is RDS itself or something else?

Check RDS event history first — it will show exactly when the failover started and completed at the infrastructure level. If that duration looks normal (RDS Multi-AZ failovers are typically well under a couple of minutes) but application-observed downtime is much longer, the gap is almost certainly application-side connection handling, as diagnosed in this assignment — not an RDS problem to escalate to AWS support.

Follow-up: "What application-level fix specifically closes that gap?" — Short connection timeouts paired with exponential backoff retry logic, so the application fails fast on a stale connection and retries quickly against the now-updated endpoint, rather than hanging on a long default timeout.
Q4 · Cost OptimizationIs Multi-AZ always worth the roughly doubled database cost?

Only when automatic failover with minimal downtime is a genuine business requirement — for this customer-facing insurance portal, yes, given the earlier app-tier outage story already established what an unplanned outage costs the business. For a genuinely non-critical internal tool with tolerance for a longer manual-recovery window, single-AZ RDS with reliable automated backups (and accepting a restore-from-backup RTO instead of near-instant failover) could be the right, cheaper call — the decision should follow the actual availability requirement, same pattern as every prior cost-vs-availability decision in this course.

Follow-up: "What's the RTO/RPO difference between Multi-AZ failover and restoring from an automated backup?" — Multi-AZ failover: RTO typically under a couple of minutes, RPO near-zero (synchronous replication). Backup restore: RTO could be tens of minutes to hours depending on data volume, RPO bounded by how recently a backup/transaction log was taken — a materially different guarantee.
Q5 · TerraformWhy does deletion_protection matter for a resource already managed carefully through Terraform code review?

Code review catches intentional, reviewed changes — it doesn't protect against a mistaken terraform destroy run against the wrong workspace, a bad merge that accidentally removes the resource block, or a CI pipeline misconfiguration that applies against production instead of a dev environment. deletion_protection is a runtime guard rail independent of anything in the code review process — it requires an explicit, separate, deliberate action to disable before deletion can proceed at all, which is exactly the kind of extra friction you want on your one stateful, hard-to-recover resource.

Follow-up: "Would you apply deletion_protection to every RDS instance, including dev/test?" — Generally not with the same rigidity — dev/test databases are expected to be disposable, and unnecessary friction there just slows down legitimate teardown/rebuild cycles; the protection should scale with how costly losing that specific database would actually be.
Q6 · Manager RoundFinance wants read access to production data for reporting. How do you evaluate that request?

I wouldn't grant direct query access to the primary database — that risks exactly the contention problem this assignment's practice challenge describes, and it's also a security-scope question (does Finance's tooling need the same access level as the application itself?). I'd propose the read-replica pattern from the challenge: a separate, appropriately-scoped endpoint and credential set for reporting, isolated from live application traffic and load-tested independently, so a heavy or poorly-written report query can never degrade the customer-facing application.

Follow-up: "What if Finance's reporting needs grow well beyond simple queries against a replica?" — That's the point to evaluate a dedicated data warehouse or analytics pipeline (covered later in the course's data-processing/reporting territory) rather than continuing to scale a transactional database's read replica for an increasingly analytical workload — different tools for different access patterns.
