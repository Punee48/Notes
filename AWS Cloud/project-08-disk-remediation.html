Disk-Space Remediation Automation
Proactive, Allowlisted Cleanup Pipeline

01

Business Scenario

NovaStack Bank's Infra Ops team gets paged on average 12 times a month for disk-space-critical alerts across the RHEL fleet — almost always the same root causes: unrotated application logs, orphaned core dumps, or a stale package cache. Each page currently means an engineer manually SSHing in at whatever hour, figuring out what's safe to delete, and clearing it — repetitive, error-prone (there's real risk of deleting something that shouldn't be touched), and a poor use of on-call time.

Infra Ops has asked Automation Engineering to build a disk-space remediation pipeline: proactively monitor disk usage trends, safely reclaim space from a well-defined, approved set of reclaimable paths before a page ever fires, and only escalate to a human when the automated safe-cleanup isn't enough.

Why this can't stay manual12 pages a month for the same handful of root causes is pure toil — it's solvable with a well-scoped, safe, repeatable cleanup routine, freeing on-call time for genuinely novel problems instead.

This project introduces proactive threshold-based automation (acting before the page fires, not after) and a strict allowlist design pattern, since "safely delete files" is exactly the kind of task where an architect must be conservative by default.

Ansible Design

Architect's note

The role is check-then-act at every single path, never a blind wildcard delete. Each reclaim action independently verifies the target matches the allowlist pattern and an age threshold before touching anything — defense in depth against a catalog typo.

Code & Roles

catalog/reclaim_allowlist.yml 
---
reclaim_paths:
  - path: "/var/log/*.log.[0-9]*"
    min_age_days: 14
    action: delete
  - path: "/var/crash/*/vmcore"
    min_age_days: 7
    action: delete
  - path: "/var/cache/dnf"
    action: clean_cache
roles/disk_cleanup/tasks/main.yml 
---
- name: Check current disk usage on monitored filesystem
  ansible.builtin.shell: "df --output=pcent / | tail -1 | tr -d '% '"
  register: disk_usage_before
  changed_when: false

- name: Proceed only if usage exceeds warning threshold
  ansible.builtin.meta: end_host
  when: disk_usage_before.stdout | int < warning_threshold_percent

# Loop over the allowlist ONLY -- there is no path in this role that
# isn't explicitly named in the catalog. No wildcards outside this loop,
# no "clean up anything old", ever.
- name: Reclaim space from allowlisted paths only
  ansible.builtin.find:
    paths: "{{ item.path | dirname }}"
    patterns: "{{ item.path | basename }}"
    age: "{{ item.min_age_days }}d"
  register: found_files
  loop: "{{ reclaim_paths | selectattr('action', 'equalto', 'delete') | list }}"
  when: item.action == "delete"

- name: Delete matched, aged, allowlisted files
  ansible.builtin.file:
    path: "{{ item.path }}"
    state: absent
  loop: "{{ found_files.results | map(attribute='files') | flatten }}"
  loop_control:
    label: "{{ item.path }}"

- name: Clean package manager cache if listed
  ansible.builtin.command: dnf clean packages
  when: reclaim_paths | selectattr('action', 'equalto', 'clean_cache') | list | length > 0
  changed_when: true

- name: Re-check disk usage after cleanup
  ansible.builtin.shell: "df --output=pcent / | tail -1 | tr -d '% '"
  register: disk_usage_after
  changed_when: false

# If cleanup wasn't enough, escalate to a human with real numbers --
# the automation never just retries blindly or expands its own scope.
- name: Escalate to ServiceNow if still above critical after cleanup
  ansible.builtin.uri:
    url: "https://novastack.service-now.com/api/now/table/incident"
    method: POST
    body_format: json
    body:
      short_description: "Disk critical on {{ inventory_hostname }} after automated cleanup: {{ disk_usage_after.stdout }}% used"
      urgency: 1
  delegate_to: localhost
  when: disk_usage_after.stdout | int >= critical_threshold_percent

Execution flow, in plain terms

The role only proceeds past the warning threshold, only ever touches files matching an exact catalog entry and age minimum, and re-measures after cleanup. If usage is still critical, it escalates with the real before/after numbers rather than attempting anything outside its allowlist — the automation's job is to solve the easy 90% safely and hand the hard 10% to a human with useful context.

14

Rollback Procedure

Disable the scheduled job template — deleted files (rotated logs, aged core dumps) are not restorable by design, which is exactly why the allowlist and age thresholds are reviewed conservatively before go-live, not loosened after.

15

Troubleshooting

Cleanup runs but disk usage barely changes Symptom: Escalation incident fires repeatedly on the same host.
Root cause (typical): The real space consumer isn't in the allowlist at all — e.g. an application writing an ever-growing file outside /var/log.
Fix: This is exactly the intended behavior — escalate to a human who investigates the actual cause, rather than automation guessing and expanding its own scope.

Interview Preparation

How do you make an automated "delete files" task safe?
Strict allowlisting with no wildcards outside the catalog, an explicit minimum age on everything, and always re-measuring and escalating rather than expanding scope when cleanup isn't sufficient — the automation is deliberately conservative by design, not just by luck.
Why trigger at a warning threshold instead of the critical/paging threshold?
The entire point is to act before the page fires — triggering at the same threshold that pages on-call would just mean the automation and the human race each other, defeating the purpose of reducing toil.
