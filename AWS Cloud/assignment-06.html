Building a Highly Available Multi-AZ Application Architecture

The quote portal has been running fine on its single app instance — until AWS performs planned maintenance on the underlying host and that instance goes down for eleven minutes. Zero customers could get a quote. Priya wants to know why "AZ failure" was ever an acceptable risk we shipped with.

Difficulty: Intermediate Domain: Insurance Services: EC2 · ALB · Launch Template · Multi-AZ Targets IaC: Console + CLI + Terraform Est. lab time: 2.5–3.5 hrs
Progress: Assignment 6 of 25

01 Production Story

Infrastructure Manager — Priya Nandan

"We flagged this risk back in Assignment 3 and I signed off on shipping it anyway to get something working — that was the right call then. It's not the right call anymore. We just had an eleven-minute outage because the single app instance sat on hardware that AWS decided to retire. I want the quote portal running from at least two Availability Zones, for real, today — not 'we'll add Auto Scaling eventually.' If one AZ disappears entirely, customers should not notice."

Why this is Assignment 6, not Assignment 7's Auto Scaling

It's tempting to jump straight to an Auto Scaling Group as "the" HA answer. But understanding what ASG actually automates requires first seeing what you'd otherwise do by hand: launch a second instance in a second AZ using the exact same configuration as the first, register both with the target group, and prove the ALB routes around a failure. We do that manually here — using a Launch Template so both instances are defined identically rather than hand-typed twice — and Assignment 7 replaces this manual multi-instance management with an ASG that does it automatically, including replacing a failed instance, which is the piece manual management can't do.

03 Architecture Design

App Instance 1same Launch Template · target group member
AZ-B · private-b
App Instance 2same Launch Template · target group member

The ALB is already multi-AZ by nature (Assignment 3) — what was missing was anything for it to route to in the second AZ. This assignment adds a second app instance in private-b, built from the exact same Launch Template as the first, and registers both with the existing target group. The ALB's own health-check-driven routing (also built in Assignment 3) already knows how to stop sending traffic to an unhealthy target — we're not changing that logic, just finally giving it two targets to choose between instead of one.

Why "Stateless" Matters Here

If the app stored a customer's in-progress quote data only in that instance's local memory, losing that instance mid-session would lose their progress even though the ALB successfully failed over to the surviving instance — technically "available," but functionally broken for that customer. The requirement above exists specifically to catch that gap before it becomes a real incident; the actual data-layer fix (an external session store or database) comes with Assignment 8's database work.

04 Architecture Decision Making

Decision: Launch Template vs. Hand-Configuring Each Instance Separately

We could launch the second instance through the console by hand, copying settings from the first. That's exactly how configuration drift starts — a slightly different AMI version, a forgotten security group, a typo in user data that only shows up on one of the two instances. A Launch Template captures the AMI, instance type, security groups, and user data once, as a versioned object; both instances reference the same template version, guaranteeing they're identical by construction rather than by careful copying. This also happens to be the exact object Assignment 7's Auto Scaling Group will consume directly — building it now isn't wasted work, it's the on-ramp to the next assignment.

Decision: Manual Second Instance vs. Jumping Straight to Auto Scaling Group

Manual second instance (this assignment)Auto Scaling Group (Assignment 7)
Handles AZ failureYes — surviving instance keeps servingYes
Replaces a failed instance automaticallyNo — an engineer has to notice and relaunchYes — this is ASG's core job
Scales with trafficNo — fixed at two instances regardless of loadYes, with scaling policies

Decision: manual multi-AZ first. This satisfies Priya's immediate, specific requirement (survive an AZ failure) today, while making the automatic-replacement and traffic-based-scaling gap explicit and visible rather than silently deferred — the practice challenge below deliberately surfaces that exact gap.

05 AWS Console — Manual Steps

  1. Create a Launch Template from the existing instance's configuration. EC2 console → Launch Templates → Create launch template → AMI, instance type (t3.small, per Assignment 3's incident fix), security group sg-app, IAM instance profile quote-portal-app-role, and the same user data used for the original instance → name it quote-portal-app-lt.
  2. Launch the second instance from the template, in the other AZ. Launch Templates → select it → Actions → Launch instance from template → override subnet to private-b only (everything else inherited from the template) → launch.
  3. Register the new instance with the existing target group. Target Groups → quote-portal-tg → Targets → Register targets → select the new AZ-B instance, port 3000 → save.
  4. Confirm both targets go healthy. Wait for both to show healthy in the target group — the ALB now has two viable destinations for every incoming request.
  5. (Recommended) Relaunch the original instance from the same Launch Template too. So both instances are now genuinely defined by the same template rather than one being a legacy hand-configured instance and one being template-launched — eliminates any residual drift between them.

06 AWS CLI

bash
# Launch the second instance from the template into private-b
aws ec2 run-instances \
  --launch-template LaunchTemplateName=quote-portal-app-lt,Version='$Latest' \
  --subnet-id $PRIVATE_B_SUBNET_ID

# Register it with the existing target group
aws elbv2 register-targets \
  --target-group-arn $TG_ARN \
  --targets Id=$NEW_INSTANCE_ID,Port=3000

# Watch both targets' health transition to healthy
watch -n5 "aws elbv2 describe-target-health --target-group-arn $TG_ARN \
  --query 'TargetHealthDescriptions[].[Target.Id,TargetHealth.State]' --output table"
FlagMeaning
Version='$Latest'Always launches from the most recently created version of the template, rather than pinning to a specific version number — appropriate while actively iterating; production would typically pin an explicit tested version
register-targetsAdds a target to an existing target group's tracked pool — does not affect the ALB's listener/routing configuration itself, only who's eligible to receive forwarded traffic

07 Terraform Implementation

main.tf — Launch Template

main.tf (part 1 of 2)
resource "aws_launch_template" "app" {
  name_prefix   = "quote-portal-app-"
  image_id      = "ami-0f5ee92e2d63afc18"
  instance_type = "t3.small"  # t3.small per Assignment 3's memory-sizing incident fix

  iam_instance_profile {
    name = aws_iam_instance_profile.quote_portal_app.name
    # References the role from Assignment 5 that can read the rating-API secret
  }

  vpc_security_group_ids = [aws_security_group.app.id]

  user_data = base64encode(file("${path.module}/user_data.sh"))
  # Launch templates require user_data as base64 — Terraform's base64encode()
  # handles the encoding; the underlying script content is unchanged from
  # what the single instance in Assignment 3 used.

  tag_specifications {
    resource_type = "instance"
    tags          = { Name = "quote-portal-app", Tier = "app" }
  }

  lifecycle {
    create_before_destroy = true
    # If this template is ever updated, Terraform creates the NEW version of
    # the template before anything references the old one is torn down —
    # relevant once instances/ASGs actually reference "$Latest" or a specific
    # version and we don't want a gap with no valid template to launch from.
  }
}

resource "aws_iam_instance_profile" "quote_portal_app" {
  name = "quote-portal-app-profile"
  role = aws_iam_role.quote_portal_app.name  # role defined in Assignment 5's Terraform
}

main.tf — Two Instances From the Template, Both Registered

main.tf (part 2 of 2)
resource "aws_instance" "app" {
  count     = 2
  subnet_id = aws_subnet.private[count.index].id
  # count.index 0 → private[0] (private-a), 1 → private[1] (private-b) —
  # this single resource block, with count = 2, replaces both the original
  # Assignment 3 single-instance resource AND the manual second instance —
  # both now come from one identical definition, satisfying the
  # no-configuration-drift requirement by construction.

  launch_template {
    id      = aws_launch_template.app.id
    version = "$Latest"
  }

  tags = { Name = "quote-portal-app-${count.index + 1}" }
}

resource "aws_lb_target_group_attachment" "app" {
  count            = length(aws_instance.app)
  target_group_arn = aws_lb_target_group.app.arn
  target_id        = aws_instance.app[count.index].id
  port             = 3000
  # One attachment resource per instance in the count — both get registered
  # to the SAME target group created back in Assignment 3, so the ALB's
  # listener and routing rules don't need to change at all.
}
Note on replacing Assignment 3's single-instance resource

This Terraform replaces the single aws_instance.app resource from Assignment 3 with a count = 2 version of the same name — terraform plan against a prior state will show this as one instance being left alone (index 0, if IDs line up) and one new instance being created (index 1), not a destroy-and-recreate of everything. Always review the plan output for exactly this kind of resource-count change before applying, per the Terraform habit established back in Assignment 1.

08 Validation & Testing

  • Baseline test: both targets show healthy in the target group simultaneously.
  • AZ failure simulation: stop the AZ-A instance entirely (simulating the AZ-A outage from the story) → confirm the target group marks it unhealthy within the configured threshold, and repeated curl requests to the ALB continue succeeding, now served entirely by the AZ-B instance.
  • Recovery test: restart the AZ-A instance → confirm it rejoins as healthy and the ALB resumes distributing traffic across both.
  • Statelessness spot-check: send a sequence of requests that would reveal server-side session state if any existed (e.g. repeated calls to an endpoint that would behave differently on a "second visit" if state were kept in memory) and confirm behavior is identical regardless of which instance answers.

10 Production Incident

One week after go-live

A scheduled AWS maintenance event affects the AZ-B instance. This time, nobody notices anything — support tickets stay at zero, and the on-call engineer only learns about it the next morning from a CloudWatch alarm history, not from an angry customer.

Investigation

The HealthyHostCount < 2 alarm (added per the monitoring note above) fired at the time of the maintenance event and auto-resolved once AWS's maintenance completed and the instance came back healthy — exactly the intended behavior, functioning as designed rather than as an incident requiring intervention.

Root Cause

Not applicable in the traditional sense — this "incident" is included specifically because it demonstrates the fix working. The same category of event that caused an eleven-minute customer-visible outage in the story now resolves with zero customer impact and a clean audit trail.

Lessons Learned

  • The real measure of whether an HA fix works isn't "did we build the failover mechanism" — it's "did a subsequent real failure event actually go unnoticed by customers," and this is the first evidence that it does.
  • An alarm on "degraded but still serving" (1 of 2 healthy) is what gave visibility into this event at all — without it, this recovery would have gone completely unlogged and unverified.

16 Practice Challenge

Priya comes back: "Good — AZ failure is handled. But Karthik just told me next month's marketing campaign could 10x our traffic for a few hours. Two fixed instances won't handle that, and I don't want to be manually launching a third and fourth instance at 11 PM the night before the campaign."

Requirement: Identify exactly what manual step in today's design would have to happen for a traffic spike, and name the AWS feature that would remove the need for a human to do it.

Acceptance Criteria: Correctly describe what's missing (not implement it yet — that's Assignment 7) and why today's fixed count = 2 can't respond to a traffic spike on its own.

Challenge Solution

Today, "more capacity" means an engineer manually changing count from 2 to some higher number, running terraform apply, and hoping they did it before the traffic spike rather than during it — there is no mechanism watching load and reacting automatically, and no mechanism scaling back down afterward to avoid paying for capacity nobody needs at 2 AM. That's precisely what an Auto Scaling Group replaces: it manages a dynamic (not fixed) number of instances from the same Launch Template we already built here, driven by scaling policies tied to real metrics like CPU or request count, launching new instances automatically as load rises and terminating them as it falls — and, as a bonus we didn't get manually, automatically replacing any instance that fails a health check without anyone paging on-call to relaunch it by hand. That's the entirety of Assignment 7.

17 Interview Preparation

Q1 · High AvailabilityIs an Application Load Balancer alone enough to make an application highly available?

No — the ALB itself is inherently multi-AZ and highly available, but it can only route to whatever targets are actually registered and healthy. If every registered target lives in one AZ, losing that AZ takes the application down regardless of how resilient the ALB is. HA requires both a resilient routing layer AND actual redundant capacity behind it in more than one failure domain — this assignment is entirely about the second half of that equation.

Follow-up: "What's the minimum number of AZs typically considered for production HA?" — Two is the common minimum baseline for surviving a single AZ failure; three is often preferred for workloads with quorum-based systems (like certain databases) that need a tie-breaking majority.
Q2 · AWS FundamentalsWhat does a Launch Template actually solve that launching instances individually doesn't?

Consistency and versioning. It captures the full instance specification — AMI, instance type, security groups, IAM profile, user data — as a single, versioned, reusable object. Every instance launched from it is guaranteed identical by construction, and if the specification needs to change, you create a new template version rather than remembering to manually update every existing and future instance the same way.

Follow-up: "What's the difference between a Launch Template and the older Launch Configuration?" — Launch Configurations are immutable and legacy — they can't be modified or versioned, and AWS recommends Launch Templates for all new work; Launch Templates support versioning, mixed instance types/purchase options, and are the only option compatible with some newer EC2 features.
Q3 · Production ScenarioHow would you verify an HA design actually works, rather than just assuming it does because you built it?

The same way this assignment did — deliberately induce the failure you're claiming to survive (stop an instance, simulate the AZ-down scenario) in a controlled way, and observe real behavior: does the target group actually detect it, does the ALB actually route around it, does the application actually keep responding successfully throughout. An HA claim that's never been tested by an actual induced failure is a hope, not a verified property.

Follow-up: "How would you do this safely in an actual production environment, not just a lab?" — Chaos-engineering-style controlled failure injection during a defined low-traffic maintenance window, with the team on standby and a clear rollback plan — the same principle at production scale, with appropriate blast-radius controls.
Q4 · Cost OptimizationIs doubling instance count always the right way to achieve AZ redundancy?

Not necessarily — it's the simplest and most predictable, but for workloads with genuinely variable load, right-sizing via Auto Scaling (Assignment 7) rather than a fixed doubled count can achieve the same redundancy at lower average cost, since it scales down during low-traffic periods instead of paying for two full-size instances around the clock. For workloads with flat, predictable load, a fixed multi-AZ count like this assignment's can be perfectly reasonable and simpler to reason about.

Follow-up: "When would you actually prefer the fixed-count approach even knowing ASG exists?" — When predictability and operational simplicity matter more than cost optimization — e.g. a workload with genuinely flat traffic where the added complexity of scaling policies wouldn't earn its keep.
Q5 · TerraformWhy use count = 2 with subnet indexing here instead of two separate named resource blocks?

Same reasoning as Assignment 2's subnet resources — one resource block scales cleanly (change count to 3 or 4 later without adding new blocks), and it structurally guarantees both instances share every other attribute, which is exactly the no-drift requirement from this assignment. Two separate named blocks would let them silently diverge over time as someone edits one and forgets the other.

Follow-up: "What breaks if you later want the two instances to have genuinely different configurations?" — That's a sign count is the wrong tool — at that point for_each with a map of per-instance overrides, or genuinely separate resource blocks, would better express "these are meaningfully different," rather than forcing artificial uniformity where it no longer fits.
Q6 · Manager RoundHow would you explain to a non-technical stakeholder why this assignment cost twice as much as Assignment 3 to run?

I'd tie it directly to the incident that triggered it: an eleven-minute outage where customers couldn't get quotes, caused by depending on a single server. Doubling the compute cost buys the specific, measurable outcome that the exact same category of event — verified by the follow-up maintenance incident in this assignment — now resolves with zero customer impact. I'd frame it as the cost of the outage we already had, prevented from happening again, rather than an abstract "best practice" tax.

Follow-up: "What if they push back that the cost still feels too high?" — That's the moment to bring in Assignment 7's Auto Scaling as the next lever — the same redundancy without paying for two full-size instances at all times, by scaling down during low-traffic hours instead of staying fixed at two.
