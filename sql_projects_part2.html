Organization Hierarchy with Recursive CTE

Scenario: Wipro / Accenture — Building org-chart queries and BOM (Bill of Materials) tree traversal

Recursive CTEANCHOR + RECURSIVE member MAXRECURSIONHierarchyidSelf-Join
The Story
The HR Director at Wipro walks up to you with a printed org chart. "I need SQL to show me every employee under CTO Ramesh — all levels, not just direct reports. Also, next to each employee, show their level number (CEO = Level 1, his direct reports = Level 2, and so on)." This is a classic tree traversal problem. The Employee table has a self-referencing foreign key: each employee stores the ID of their manager. A Recursive CTE solves this elegantly — it starts from the top (the anchor), then repeatedly joins to itself until it reaches leaf nodes with no more reports.

Step 1 — Self-Referencing Table
Employees with Manager Hierarchy
USE OrgDB;
GO

CREATE TABLE OrgEmployees (
    EmpID      INT PRIMARY KEY,
    EmpName    NVARCHAR(100),
    Title      NVARCHAR(100),
    ManagerID  INT NULL
    -- ManagerID is NULL for the CEO (no manager above)
    -- For everyone else, it references another row in this SAME table
    -- This is called a SELF-REFERENCING foreign key
);
-- Note: We don't add FOREIGN KEY here to keep inserts simple
-- In production: FOREIGN KEY REFERENCES OrgEmployees(EmpID)
GO

-- Build a 4-level hierarchy
INSERT INTO OrgEmployees VALUES
  (1,  'Narayana Murthy',  'CEO',              NULL),   -- Level 1: no manager
  (2,  'Ramesh Babu',     'CTO',              1),     -- Level 2: reports to CEO
  (3,  'Anitha Rao',      'CFO',              1),     -- Level 2: reports to CEO
  (4,  'Kiran Kumar',     'Dev Manager',      2),     -- Level 3: reports to CTO
  (5,  'Priya Sharma',    'QA Manager',       2),     -- Level 3: reports to CTO
  (6,  'Suresh Hegde',    'Senior Developer', 4),     -- Level 4
  (7,  'Deepa Nair',      'Developer',        4),     -- Level 4
  (8,  'Arun Patel',      'QA Engineer',      5);    -- Level 4
GO
Step 2 — The Recursive CTE
Recursive CTE — Full Org Tree Traversal
-- A Recursive CTE has TWO parts connected by UNION ALL:
-- 1. ANCHOR MEMBER: the starting point (no recursion here)
-- 2. RECURSIVE MEMBER: references the CTE itself to go one level deeper
-- SQL Server keeps running the recursive member until no new rows come back

WITH OrgTree AS (

    -- === ANCHOR MEMBER: Start from the CEO (ManagerID IS NULL) ===
    SELECT
        EmpID,
        EmpName,
        Title,
        ManagerID,
        1                             AS Level,
        -- Start at Level 1 for the CEO
        CAST(EmpName AS NVARCHAR(1000)) AS OrgPath
        -- OrgPath: a string showing the full path like "CEO > CTO > Manager"
    FROM OrgEmployees
    WHERE ManagerID IS NULL
    -- Anchor: only the top-level person with no manager

    UNION ALL
    -- UNION ALL connects the anchor and recursive parts
    -- Must be UNION ALL (not UNION) in recursive CTEs

    -- === RECURSIVE MEMBER: Join employees to their manager from OrgTree ===
    SELECT
        e.EmpID,
        e.EmpName,
        e.Title,
        e.ManagerID,
        ot.Level + 1,
        -- Each time we go one level deeper, increment Level by 1
        CAST(ot.OrgPath + ' → ' + e.EmpName AS NVARCHAR(1000))
        -- Build the path string by appending current employee's name
    FROM OrgEmployees e
    -- e = the child (current level employee)
    INNER JOIN OrgTree ot
    -- ot = the CTE itself (the parent's row from the previous iteration)
        ON e.ManagerID = ot.EmpID
    -- Connect: child's ManagerID = parent's EmpID
)

-- Final SELECT from the fully-built CTE
SELECT
    Level,
    REPLICATE('    ', Level - 1) + EmpName AS IndentedName,
    -- REPLICATE('    ', n) adds indentation spaces based on level
    Title,
    OrgPath
FROM OrgTree
ORDER BY OrgPath
OPTION (MAXRECURSION 100);
-- MAXRECURSION 100: safety limit — stop after 100 levels
-- Default is 100. Set to 0 for unlimited (risky — infinite loops possible)

How Recursion Works — Step by Step

Iteration 1Anchor runs: returns CEO row. Level=1, OrgPath="Narayana Murthy"
Iteration 2Recursive member joins OrgEmployees to last result. Finds CTO and CFO (ManagerID=1). Level=2.
Iteration 3Recursive member joins again. Finds Dev Manager and QA Manager (ManagerID=2,3). Level=3.
Iteration 4Finds Developers and QA Engineers. Level=4. No more children → recursion stops.
UNION ALLAll results from all iterations are combined into one final result set. That's what you SELECT from.
Interview Questions

🎤 Likely Interview Questions

Q: Explain the structure of a Recursive CTE.
A Recursive CTE has two mandatory parts joined by UNION ALL. The first part is the Anchor Member — a regular SELECT that defines the starting rows (the root of the tree). The second part is the Recursive Member — it references the CTE itself and joins to find the next level of rows. SQL Server runs the recursive member repeatedly, each time using the results of the previous run, until no new rows are returned. You must always include MAXRECURSION to prevent infinite loops.
Q: Where do you use Recursive CTEs in real projects?
Three main use cases in MNC projects: First, Organization Hierarchy (employee-manager trees). Second, Bill of Materials — a product made of sub-parts, each sub-part having its own sub-parts. Third, Category trees in e-commerce — Electronics → Mobile Phones → Smartphones → Android. Any parent-child tree stored in a self-referencing table is a recursive CTE use case.

Temporal Tables — Full Data History Tracking

Scenario: ICICI Bank — Track every change to account records with time-travel queries

System-Versioned Temporal TableFOR SYSTEM_TIME AS OF History TablePERIOD FOR SYSTEM_TIME
The Story
An ICICI Bank auditor calls: "Show me the exact balance of account #1001 as it was on January 15th at 10 AM." With a normal table, this is impossible — you only have the current value. With SQL Server's Temporal Tables (introduced in SQL Server 2016), SQL Server automatically maintains a shadow history table that records every change with start and end timestamps. You can literally time-travel and query what the data looked like at any point in the past with a single SQL keyword: FOR SYSTEM_TIME AS OF. This is one of the most impressive features to mention in an interview.
Step 1 — Create Temporal Table
System-Versioned Temporal Table
USE BankDB;
GO

CREATE TABLE AccountBalances (
    AccountID    INT              PRIMARY KEY,
    AccountHolder NVARCHAR(100),
    Balance      DECIMAL(15,2),

    -- These two columns are MANDATORY for temporal tables
    -- SQL Server fills them automatically — never insert them manually
    ValidFrom    DATETIME2        GENERATED ALWAYS AS ROW START NOT NULL,
    -- ValidFrom: timestamp when this version of the row became current
    ValidTo      DATETIME2        GENERATED ALWAYS AS ROW END   NOT NULL,
    -- ValidTo: timestamp when this version was superseded (9999-12-31 if still current)

    -- Define which columns are the period columns
    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH (
    -- Enable system versioning and name the history table
    SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.AccountBalances_History)
    -- SQL Server automatically creates AccountBalances_History table
    -- Every old version of every row is stored there automatically
);
GO

-- Insert initial data
INSERT INTO AccountBalances (AccountID, AccountHolder, Balance)
VALUES (1001, 'Ravi Shankar', 50000.00);
GO

-- Simulate a deposit: balance goes from 50000 to 75000
UPDATE AccountBalances
SET Balance = 75000.00
WHERE AccountID = 1001;
-- SQL Server automatically saves the old row (Balance=50000) to the History table
GO

-- Simulate a withdrawal
UPDATE AccountBalances
SET Balance = 60000.00
WHERE AccountID = 1001;
GO
Step 2 — Time Travel Queries
FOR SYSTEM_TIME — Query Past States
-- See current state
SELECT * FROM AccountBalances;
-- Shows Balance = 60000 (latest)

-- TIME TRAVEL: What was the balance at a specific moment in the past?
SELECT * FROM AccountBalances
FOR SYSTEM_TIME AS OF '2024-01-15 10:00:00'
-- Returns the row as it existed at that exact timestamp
-- SQL Server checks history table to find the version valid at that time
WHERE AccountID = 1001;

-- See ALL versions of a row (current + all historical)
SELECT * FROM AccountBalances
FOR SYSTEM_TIME ALL
-- ALL: returns every version of every row ever stored
WHERE AccountID = 1001
ORDER BY ValidFrom;
-- You'll see 3 rows: original 50000, then 75000, then 60000

-- See all rows valid during a specific DATE RANGE
SELECT * FROM AccountBalances
FOR SYSTEM_TIME BETWEEN '2024-01-01' AND '2024-03-01'
WHERE AccountID = 1001;
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between Temporal Tables and a manually built Audit Trigger?
Both track data changes. But a Temporal Table is built into SQL Server — you don't write any trigger code. SQL Server automatically maintains the history table with no performance overhead from developer-written triggers. Temporal Tables also give you the elegant FOR SYSTEM_TIME syntax for time-travel queries. Audit triggers require manual coding and maintenance. For compliance-heavy industries like banking and insurance, Temporal Tables are the professional choice because they're tamper-evident and fully managed by the engine.

Row-Level Security — Multi-Tenant SaaS Application

Scenario: Zoho / Freshworks — Each customer company sees only its own data, zero code changes

CREATE SECURITY POLICYSECURITY_PREDICATE Inline TVFSESSION_CONTEXTMulti-tenancy
The Story
Zoho CRM stores data for 10,000 companies in one single database table. Each company (tenant) must only see their own rows — never another company's data. The naive solution is to add WHERE TenantID = @MyID in every query. But developers forget to add this clause, causing data leaks. SQL Server's Row-Level Security (RLS) solves this at the database level — you define a security policy once, and SQL Server automatically filters rows for every query, every stored procedure, every user — without any application code change. This is a premium concept used in every enterprise SaaS product.
Step 1 — Create Tables and Sample Data
Multi-Tenant Setup
USE SaaSDB;
GO

CREATE TABLE Tenants (
    TenantID   INT PRIMARY KEY,
    TenantName NVARCHAR(100),
    DBUser     NVARCHAR(100)  -- SQL login username for this tenant
);

CREATE TABLE CustomerData (
    RecordID   INT IDENTITY(1,1) PRIMARY KEY,
    TenantID   INT NOT NULL,
    CustomerName NVARCHAR(100),
    Revenue    DECIMAL(12,2)
);

INSERT INTO Tenants VALUES
  (1, 'TechCorp India',  'user_techcorp'),
  (2, 'RetailMart Ltd', 'user_retailmart');

INSERT INTO CustomerData (TenantID,CustomerName,Revenue) VALUES
  (1, 'Client A', 500000),  -- belongs to TechCorp
  (1, 'Client B', 320000),  -- belongs to TechCorp
  (2, 'Client C', 150000),  -- belongs to RetailMart
  (2, 'Client D', 290000);  -- belongs to RetailMart
GO
Step 2 — Create Security Predicate and Policy
Row-Level Security — Filter Predicate
-- Step 1: Create an Inline Table-Valued Function as the security predicate
-- This function decides which rows a user is allowed to see
-- It returns a table: if the table has a row, access is GRANTED
-- If the table is empty, access is DENIED for that row
CREATE FUNCTION Security.fn_TenantFilter (@TenantID INT)
RETURNS TABLE
WITH SCHEMABINDING
-- SCHEMABINDING: prevents anyone from dropping the table while this function references it
AS
RETURN
    SELECT 1 AS AccessGranted
    FROM dbo.Tenants
    WHERE
        TenantID = @TenantID
        AND DBUser = USER_NAME()
        -- USER_NAME() returns the current SQL login name
        -- So user_techcorp only passes this check for TenantID=1
GO

-- Step 2: Create the Security Policy that applies the function
CREATE SECURITY POLICY TenantSecurityPolicy
ADD FILTER PREDICATE Security.fn_TenantFilter(TenantID)
ON dbo.CustomerData,
-- FILTER PREDICATE: silently hides rows (no error, just not shown)
ADD BLOCK PREDICATE Security.fn_TenantFilter(TenantID)
ON dbo.CustomerData AFTER INSERT
-- BLOCK PREDICATE: prevents INSERT of rows for other tenants
WITH (STATE = ON);
-- STATE = ON: activate the policy immediately
GO

-- Test: connect as user_techcorp and run this query
-- Result: only TechCorp rows appear — RetailMart rows are invisible
SELECT * FROM dbo.CustomerData;
-- No WHERE clause needed! RLS handles it automatically.

-- Disable the policy (for testing as admin)
ALTER SECURITY POLICY TenantSecurityPolicy WITH (STATE = OFF);
Interview Questions

🎤 Likely Interview Questions

Q: What is Row-Level Security and why is it better than adding WHERE clauses in application code?
Row-Level Security (RLS) is a SQL Server feature where you define a security predicate at the database level. The database engine automatically applies it to every SELECT, INSERT, UPDATE, or DELETE — regardless of which user, stored procedure, or application code runs the query. Application-code WHERE clauses can be forgotten or bypassed by developers writing ad-hoc queries. RLS cannot be bypassed because it's enforced at the storage engine level, making it a much more reliable security boundary for multi-tenant applications.

JSON Data Processing Pipeline

Scenario: PayTM / Razorpay — Parsing payment gateway JSON responses into relational tables

OPENJSONJSON_VALUEJSON_QUERY FOR JSON PATHISJSONJSON_MODIFY
The Story
PayTM's payment gateway sends transaction confirmations as JSON strings to your SQL Server. Your job is to parse these JSON payloads, extract order IDs, amounts, customer info, and save them into proper relational tables. You also need to generate JSON output for the mobile app API — turning SQL rows into JSON. SQL Server 2016+ supports JSON natively, and MNC interviewers love asking about it because REST APIs send JSON everywhere today.
Step 1 — Parsing JSON into Rows
OPENJSON — Parse JSON to Table Rows
USE PaymentDB;
GO

-- Declare a variable holding a sample JSON payment response
DECLARE @PaymentJSON NVARCHAR(MAX) = N'
{
    "order_id": "ORD-20240115-001",
    "status": "SUCCESS",
    "amount": 4999.00,
    "currency": "INR",
    "customer": {
        "name": "Puneeth Kumar",
        "email": "puneeth@example.com",
        "phone": "9876543210"
    },
    "items": [
        {"product": "Laptop Stand",  "qty": 1, "price": 3000},
        {"product": "USB Hub",       "qty": 2, "price": 999}
    ]
}';

-- ISJSON validates if the string is valid JSON before processing
IF ISJSON(@PaymentJSON) = 1
BEGIN
    PRINT 'Valid JSON';

    -- JSON_VALUE extracts a single scalar value from JSON
    -- The path starts with $ (root), then use . for object properties
    SELECT
        JSON_VALUE(@PaymentJSON, '$.order_id')          AS OrderID,
        JSON_VALUE(@PaymentJSON, '$.amount')             AS Amount,
        JSON_VALUE(@PaymentJSON, '$.status')             AS Status,
        JSON_VALUE(@PaymentJSON, '$.customer.name')      AS CustomerName,
        -- Use dot notation to navigate nested objects
        JSON_VALUE(@PaymentJSON, '$.customer.email')     AS Email,
        JSON_QUERY(@PaymentJSON, '$.items')              AS ItemsJSON;
        -- JSON_QUERY extracts an entire object or array (not a scalar)
        -- Use JSON_QUERY for arrays and nested objects, JSON_VALUE for strings/numbers

    -- OPENJSON parses a JSON array into multiple rows
    -- Each element in the items array becomes one row
    SELECT
        item.product,
        item.qty,
        item.price,
        item.qty * item.price AS LineTotal
    FROM OPENJSON(@PaymentJSON, '$.items')
    -- OPENJSON(json_string, path): read the array at $.items
    WITH (
        -- WITH clause: tell OPENJSON what columns to extract and their types
        product NVARCHAR(100) '$.product',
        qty     INT           '$.qty',
        price   DECIMAL(10,2) '$.price'
    ) AS item;
END
GO
Step 2 — SQL to JSON Output
FOR JSON PATH — Convert SQL Result to JSON
-- Create a payments table and query it as JSON for API response
CREATE TABLE Payments(
    PaymentID INT IDENTITY(1,1) PRIMARY KEY,
    OrderID   VARCHAR(50),
    Amount    DECIMAL(10,2),
    Status    VARCHAR(20)
);
INSERT INTO Payments(OrderID,Amount,Status) VALUES
  ('ORD-001', 4999, 'SUCCESS'),
  ('ORD-002', 1299, 'FAILED');

-- FOR JSON PATH: turn SQL result into JSON
SELECT
    PaymentID             AS id,
    OrderID               AS order_id,
    Amount                AS amount,
    Status                AS status
FROM Payments
FOR JSON PATH, ROOT('payments');
-- Output: {"payments":[{"id":1,"order_id":"ORD-001","amount":4999,"status":"SUCCESS"}, ...]}
-- ROOT('payments') wraps the array inside a named JSON object
GO
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between JSON_VALUE and JSON_QUERY?
JSON_VALUE extracts a single scalar value from a JSON string — like a string, number, or boolean. It returns NVARCHAR(4000). JSON_QUERY extracts a JSON fragment — an object or array — and returns it as a JSON string. If you try to use JSON_VALUE on an array, it returns NULL. Always use JSON_QUERY for nested objects and arrays, and JSON_VALUE for primitive values.

Change Data Capture (CDC) System

Scenario: Infosys Analytics Team — Capturing incremental data changes for data warehouse sync

CDC Enablecdc.fn_cdc_get_all_changes __$operationLSN trackingETL Integration
The Story
The data warehouse team at Infosys has a problem. Every night at 11 PM, they run a full data load from the OLTP database to the data warehouse — copying 50 million rows. It takes 6 hours and blocks the OLTP system. Their manager says: "We don't need to copy everything. Just capture what CHANGED since last night — inserts, updates, and deletes — and sync only those." This is exactly what Change Data Capture (CDC) does. It reads from SQL Server's transaction log and captures every change automatically into CDC system tables. It's a premium feature used in every enterprise data pipeline.
Step 1 — Enable CDC
Enable CDC on Database and Table
USE RetailDB;
GO

-- Step 1: Enable CDC on the entire database
EXEC sys.sp_cdc_enable_db;
-- This enables CDC at the database level
-- Creates the cdc schema and required system tables
-- Requires SQL Server Agent to be running (check Services)
GO

-- Step 2: Enable CDC on a specific table (Orders)
EXEC sys.sp_cdc_enable_table
    @source_schema   = N'dbo',
    -- schema of the table to track
    @source_name     = N'Orders',
    -- name of the table to track
    @role_name       = NULL,
    -- NULL means no special role required to query CDC tables
    @supports_net_changes = 1;
    -- 1 = track NET changes (final state of row after multiple updates)
    -- 0 = track ALL changes (every individual change in sequence)
GO

-- Verify CDC is enabled
SELECT name, is_cdc_enabled
FROM sys.databases
WHERE name = 'RetailDB';

SELECT source_schema, source_table, is_tracked_by_cdc
FROM cdc.change_tables;
GO
Step 2 — Query CDC Changes
Reading CDC Changes for ETL
-- Make some changes to the Orders table (CDC will capture them)
INSERT INTO Orders(CustomerID,ProductID,OrderDate,Quantity,TotalAmount)
VALUES(1,1,'2024-03-01',2,150000);

UPDATE Orders SET TotalAmount = 145000 WHERE OrderID = 1;

DELETE FROM Orders WHERE OrderID = 2;
GO

-- Get the LSN (Log Sequence Number) range to query
-- LSN is the position in the transaction log
DECLARE @from_lsn BINARY(10), @to_lsn BINARY(10);

-- sys.fn_cdc_get_min_lsn: earliest LSN captured for this table
SET @from_lsn = sys.fn_cdc_get_min_lsn('dbo_Orders');

-- sys.fn_cdc_get_max_lsn: latest LSN in the log right now
SET @to_lsn   = sys.fn_cdc_get_max_lsn();

-- Query all changes between these LSN values
SELECT
    __$operation,
    -- __$operation tells you what happened:
    -- 1 = DELETE (old value)
    -- 2 = INSERT (new value)
    -- 3 = UPDATE BEFORE (old value)
    -- 4 = UPDATE AFTER (new value)
    CASE __$operation
        WHEN 1 THEN 'DELETE'
        WHEN 2 THEN 'INSERT'
        WHEN 3 THEN 'UPDATE - Before'
        WHEN 4 THEN 'UPDATE - After'
    END AS ChangeType,
    OrderID,
    CustomerID,
    TotalAmount
FROM cdc.fn_cdc_get_all_changes_dbo_Orders(
    @from_lsn,
    @to_lsn,
    'all'  -- 'all' returns both before and after images of updates
             -- 'all update old' returns only old values for updates
)
ORDER BY __$start_lsn;
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between CDC and Change Tracking in SQL Server?
Both capture data changes but with different detail levels. CDC reads from the transaction log and stores the actual old and new column values — you know exactly what changed and to what value. Change Tracking only records which rows changed and the type of change (insert/update/delete) — it doesn't store the actual data. CDC is used when you need to know the exact values that changed, like in ETL pipelines. Change Tracking is lighter and used when you just need to know if a row changed, like in mobile app sync scenarios.

ETL Pipeline with Staging & Data Quality Checks

Scenario: TCS Data Engineering — Pure T-SQL ETL from raw staging to production warehouse

Staging TablesData CleansingBULK INSERT OPENROWSETETL LoggingSSIS Alternative
The Story
TCS's client sends a daily CSV file with 200,000 sales records. The raw file has messy data — duplicate rows, NULL amounts, invalid dates, wrong formats. Your job as the SQL Developer is to build a pure T-SQL ETL pipeline: Stage 1 loads the raw CSV into a staging table (no validation). Stage 2 runs data quality checks — remove duplicates, fix NULLs, validate date formats. Stage 3 inserts clean data into the production fact table and logs how many rows were loaded, how many were rejected, and why. This is what a real ETL engineer does every day in MNC data teams.
Step 1 — Staging Table and BULK INSERT
Raw Data Load via BULK INSERT
USE DataWarehouse;
GO

-- Stage 1: Raw staging table — accepts everything, no constraints
CREATE TABLE stg_SalesRaw (
    OrderID      NVARCHAR(50),   -- varchar in staging, not INT — raw data may have garbage
    CustomerName NVARCHAR(200),
    ProductCode  NVARCHAR(50),
    Quantity     NVARCHAR(20),   -- raw: may contain 'N/A' instead of number
    UnitPrice    NVARCHAR(20),
    OrderDate    NVARCHAR(30),   -- raw: date format may be DD-MM-YYYY or YYYY/MM/DD
    LoadedOn     DATETIME DEFAULT GETDATE()
);

-- BULK INSERT loads a flat file directly into a table
-- Much faster than INSERT row-by-row
BULK INSERT stg_SalesRaw
FROM 'C:\ETL\daily_sales.csv'
WITH (
    FIELDTERMINATOR = ',',     -- column separator in the CSV
    ROWTERMINATOR   = '\n',    -- row separator (newline)
    FIRSTROW        = 2,        -- skip row 1 (header row)
    TABLOCK                      -- table-level lock for faster load
);
GO
Step 2 — Data Cleansing and Load to Production
ETL Cleansing Procedure with Logging
-- ETL Log table to track each run
CREATE TABLE ETL_RunLog (
    RunID         INT IDENTITY(1,1) PRIMARY KEY,
    RunDate       DATETIME DEFAULT GETDATE(),
    TotalRaw      INT,
    Duplicates    INT,
    InvalidRows   INT,
    LoadedToFact  INT,
    Status        VARCHAR(20)
);

CREATE PROCEDURE sp_ETL_SalesLoad
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @TotalRaw INT, @Dupes INT, @Invalid INT, @Loaded INT;

    SELECT @TotalRaw = COUNT(*) FROM stg_SalesRaw;

    -- Step 1: Remove exact duplicate rows (keep one per OrderID)
    WITH CTE_Dedup AS (
        SELECT *,
            ROW_NUMBER() OVER (PARTITION BY OrderID ORDER BY LoadedOn) AS RN
        FROM stg_SalesRaw
    )
    DELETE FROM CTE_Dedup WHERE RN > 1;
    -- Delete from a CTE: SQL Server deletes the underlying rows
    -- RN > 1 means: delete all duplicates, keep only the first occurrence
    SET @Dupes = @TotalRaw - @@ROWCOUNT;

    -- Step 2: Insert valid rows into production fact table
    INSERT INTO fact_Sales(OrderID, CustomerName, ProductCode, Quantity, UnitPrice, OrderDate)
    SELECT
        OrderID,
        TRIM(CustomerName),
        -- TRIM removes leading and trailing spaces
        ProductCode,
        TRY_CAST(Quantity AS INT),
        -- TRY_CAST: like CAST but returns NULL instead of error for invalid values
        -- 'N/A' → NULL instead of crashing the entire load
        TRY_CAST(UnitPrice AS DECIMAL(10,2)),
        TRY_CONVERT(DATE, OrderDate, 105)
        -- TRY_CONVERT with style 105 = DD-MM-YYYY format
        -- Returns NULL if the date string is invalid
    FROM stg_SalesRaw
    WHERE
        OrderID IS NOT NULL
        AND TRY_CAST(Quantity AS INT) IS NOT NULL
        AND TRY_CAST(UnitPrice AS DECIMAL(10,2)) IS NOT NULL
        AND TRY_CONVERT(DATE, OrderDate, 105) IS NOT NULL;
        -- Only insert rows where ALL conversions succeed
    SET @Loaded = @@ROWCOUNT;
    SET @Invalid = @TotalRaw - @Dupes - @Loaded;

    -- Step 3: Log the run statistics
    INSERT INTO ETL_RunLog(TotalRaw,Duplicates,InvalidRows,LoadedToFact,Status)
    VALUES(@TotalRaw, @Dupes, @Invalid, @Loaded, 'SUCCESS');

    -- Step 4: Clear staging for next run
    TRUNCATE TABLE stg_SalesRaw;
    -- TRUNCATE removes all rows instantly without logging each row
    -- Much faster than DELETE for clearing staging tables
END;
GO
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between TRUNCATE and DELETE?
DELETE removes rows one at a time and logs each deletion in the transaction log — slow on large tables, but can be rolled back and can have a WHERE clause. TRUNCATE removes all rows at once by deallocating data pages — extremely fast, minimal logging, resets IDENTITY columns, but cannot have a WHERE clause and cannot be used on tables with foreign key references. For clearing staging tables in ETL, always prefer TRUNCATE.
Q: What is TRY_CAST and why use it over CAST in ETL pipelines?
CAST throws an error and stops the entire batch if a value cannot be converted. TRY_CAST returns NULL for invalid conversions instead of throwing an error. In ETL pipelines where you're loading potentially dirty data from external sources, TRY_CAST lets you process all rows and identify bad data gracefully — rather than having the entire load fail because of one bad row.

Database Mail & Automated Alert System

Scenario: Capgemini DBA Team — SQL Agent Jobs with email notifications for ETL failures

Database Mailsp_send_dbmailSQL Server Agent Agent JobsJob StepsSchedules

Your ETL job runs every day at 2 AM. One day, it silently fails. Nobody knows until Monday morning when the BI team complains that reports show weekend data is missing. The solution: Database Mail. Query Optimization & Execution Plan Analysis

Scenario: Accenture Performance Team — Tuning slow queries from 45 seconds to under 1 second

SET STATISTICS IOExecution PlanIndex Seek vs Scan Parameter SniffingRECOMPILESARGability
The Story
A senior Accenture consultant calls you to a war room at 10 PM. "This report query was running in 3 seconds last month. Now it takes 45 seconds and the CXO is waiting." You calmly open SSMS, press Ctrl+M to enable Actual Execution Plan, run the query, and immediately spot the problem: a Table Scan on a 10-million-row table because a function is wrapped around an indexed column in the WHERE clause — making the index useless. You fix one line of code. The query now runs in 0.8 seconds. This is the highest-value skill a SQL Developer can demonstrate in any interview.
The Most Important Query Optimization Rules
Anti-Pattern 1 — Functions on Indexed Columns (SARGability)
-- SARGable = Search ARGument ABLE = the WHERE clause CAN use an index
-- Non-SARGable = function wraps the column = index is IGNORED = full scan

-- ❌ BAD: YEAR() function on OrderDate prevents index use
-- SQL Server must call YEAR() on EVERY row to evaluate the condition
-- This causes a full TABLE SCAN even if OrderDate has an index
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024;

-- ✅ GOOD: Rewrite to use a range — allows INDEX SEEK
-- SQL Server can use the index to jump directly to dates in 2024
SELECT * FROM Orders
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';

-- ❌ BAD: CONVERT on column for string comparison
SELECT * FROM Customers
WHERE CONVERT(VARCHAR, CustomerID) = '1001';

-- ✅ GOOD: Cast the parameter, not the column
SELECT * FROM Customers
WHERE CustomerID = CAST('1001' AS INT);
Anti-Pattern 2 — SELECT * and NOLOCK Hint
-- ❌ BAD: SELECT * sends all columns across network
-- If the table has 50 columns but you need 3, you're wasting I/O and memory
SELECT * FROM Orders;

-- ✅ GOOD: Always specify only the columns you need
SELECT OrderID, CustomerID, TotalAmount
FROM Orders;

-- Measuring I/O before and after optimization
SET STATISTICS IO ON;
-- After running the query, SSMS shows:
-- "logical reads 8432" → how many 8KB pages were read from memory/disk
-- Lower logical reads = better performance
SET STATISTICS IO OFF;
Anti-Pattern 3 — Parameter Sniffing and Fix
-- Parameter Sniffing: SQL Server compiles a query plan based on the FIRST
-- parameter value it sees. If that plan is bad for other parameter values,
-- the stored procedure runs slowly for those values.

-- ❌ Vulnerable stored procedure
CREATE PROCEDURE sp_GetOrders_Bad @CustomerID INT
AS
    SELECT * FROM Orders WHERE CustomerID = @CustomerID;
-- Plan for CustomerID=1 (100,000 rows) may be terrible for CustomerID=999 (2 rows)

-- ✅ Fix 1: OPTION (RECOMPILE) — recompile plan each execution
CREATE PROCEDURE sp_GetOrders_Fix1 @CustomerID INT
AS
    SELECT * FROM Orders
    WHERE CustomerID = @CustomerID
    OPTION (RECOMPILE);
    -- Forces SQL Server to create a fresh plan every time
    -- Slightly more CPU overhead but always gets the optimal plan

-- ✅ Fix 2: Local variable trick — breaks the sniff
CREATE PROCEDURE sp_GetOrders_Fix2 @CustomerID INT
AS
BEGIN
    DECLARE @LocalID INT = @CustomerID;
    -- Copying to local variable: SQL Server can't sniff local variables
    -- It uses average statistics instead of the specific value's stats
    SELECT * FROM Orders WHERE CustomerID = @LocalID;
END;
📋 Reading Execution Plans — Quick Reference Press Ctrl+M in SSMS before running a query to see the Actual Execution Plan. Look for: Index Seek = good (jumps to exact rows). Index Scan = reads entire index (acceptable on small tables). Table Scan / Clustered Index Scan = reads ENTIRE table (investigate immediately). Key Lookup = index found the row but had to go back to main table for extra columns — add INCLUDE columns to fix. Fat arrows between nodes = large number of rows flowing — look at the widest arrow as your first tuning target.
Interview Questions

🎤 Likely Interview Questions

Q: What is SARGability? Give an example of a non-SARGable query and how to fix it.
SARGable means the WHERE clause condition can use an index seek. A non-SARGable condition wraps the indexed column in a function — like WHERE YEAR(OrderDate) = 2024 or WHERE UPPER(Name) = 'JOHN'. The function forces SQL Server to evaluate every row, making the index useless. Fix: move the function to the parameter side — WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'. This lets SQL Server use the index to jump directly to matching rows.

SQL Server Security — Roles, Schemas & TDE Encryption

Scenario: Healthcare MNC — HIPAA-compliant database with least-privilege access and encryption

Database RolesGRANT / REVOKE / DENY Column-Level SecurityTDEAlways Encrypted
The Story
Your company passes a HIPAA security audit. The auditor flags: "Developers have SELECT permission on the Patients table which contains Social Security Numbers and medical records — this violates least-privilege principle." Your task: create a proper permission model. Developers get read access to only the columns they need. The app service account gets only EXECUTE on stored procedures — no direct table access. Sensitive columns like SSN are encrypted using Always Encrypted so even the DBA cannot read them. This is exactly what every MNC does in regulated industries.
Step 1 — Logins, Users, and Roles
Permission Model — Least Privilege
USE HospitalDB;
GO

-- Create SQL Server logins (server level)
CREATE LOGIN dev_user     WITH PASSWORD = 'Dev@Secure123!';
CREATE LOGIN app_service  WITH PASSWORD = 'App@Secure456!';
GO

-- Create database users (database level) mapped to logins
CREATE USER dev_user    FOR LOGIN dev_user;
CREATE USER app_service FOR LOGIN app_service;
GO

-- Create custom database roles (groups of permissions)
CREATE ROLE ReadOnlyDev;
-- A role is like a team: assign permissions to the team, add users to the team

-- Grant column-level SELECT — only non-sensitive columns for developers
-- They CANNOT see SSN or MedicalHistory columns
GRANT SELECT ON Patients (PatientID, FullName, DateOfBirth, Gender)
TO ReadOnlyDev;
-- Column-level permissions: list specific columns in parentheses

-- Add the dev user to the role
ALTER ROLE ReadOnlyDev ADD MEMBER dev_user;

-- App service account: only EXECUTE on stored procedures, no direct table access
GRANT EXECUTE ON sp_AdmitPatient  TO app_service;
GRANT EXECUTE ON sp_UpdateSalary  TO app_service;
-- EXECUTE permission: app_service can call the procedures
-- but inside the procedure, it uses the procedure owner's permissions
-- This is called OWNERSHIP CHAINING — a key security concept

-- Explicitly DENY sensitive columns (belt and suspenders)
DENY SELECT ON Patients (SSN, MedicalHistory) TO ReadOnlyDev;
-- DENY always wins over GRANT — even if user gets GRANT elsewhere
GO

-- Verify permissions
SELECT * FROM sys.database_permissions
WHERE grantee_principal_id = DATABASE_PRINCIPAL_ID('ReadOnlyDev');
Step 2 — Transparent Data Encryption
TDE — Encrypt the Entire Database at Rest
-- TDE encrypts the physical database FILES on disk
-- If someone steals the .mdf file, they cannot read it without the certificate
-- Applications and users see NO change — decryption is transparent

-- Step 1: Create a master key in the master database
USE master;
GO
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'MasterKey@Secure2024!';
GO

-- Step 2: Create a certificate to protect the TDE encryption key
CREATE CERTIFICATE HospitalDBCert
WITH SUBJECT = 'TDE Certificate for HospitalDB',
EXPIRY_DATE = '2030-12-31';
GO

-- Step 3: Create the Database Encryption Key inside the database
USE HospitalDB;
GO
CREATE DATABASE ENCRYPTION KEY
WITH ALGORITHM = AES_256
-- AES_256 = industry-standard 256-bit encryption
ENCRYPTION BY SERVER CERTIFICATE HospitalDBCert;
GO

-- Step 4: Enable TDE on the database
ALTER DATABASE HospitalDB
SET ENCRYPTION ON;
GO

-- Verify encryption status
SELECT db_name(database_id) AS DatabaseName, encryption_state, percent_complete
FROM sys.dm_database_encryption_keys;
-- encryption_state: 3 = fully encrypted
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between GRANT, REVOKE, and DENY?
GRANT gives a permission to a user or role. REVOKE removes a previously granted or denied permission — it returns the user to a neutral state. DENY explicitly blocks a permission — even if the user gets GRANT through another role, DENY always wins. This hierarchy matters: DENY > GRANT > no permission. In security-critical environments, always use DENY on sensitive columns rather than just not granting access.
Q: What is Ownership Chaining in SQL Server?
When a stored procedure and the tables it accesses have the same owner (usually dbo), SQL Server skips permission checks on the tables when the procedure runs. This means you can grant EXECUTE on a stored procedure without granting SELECT/INSERT on the underlying tables — the procedure runs with the owner's permissions. This is a safe way to give application accounts database access without exposing raw tables.

High Availability — AlwaysOn & Backup Strategy

Scenario: Production DBA Role — Implementing backup/restore strategy and understanding AlwaysOn AG

BACKUP DATABASERESTORE DATABASERecovery Models AlwaysOn AG ConceptsRTO / RPOPoint-in-Time Restore
The Story
It's Friday at 4:30 PM. A junior developer accidentally runs DELETE FROM Orders without a WHERE clause. 2 million rows gone. The CTO calls: "Can we restore it?" You calmly respond: "Yes — we have transaction log backups every 15 minutes. I'll do a point-in-time restore to 4:25 PM — we lose only 5 minutes of data." Knowing backup and restore strategy — including Recovery Point Objective (RPO) and Recovery Time Objective (RTO) — is what separates a professional SQL Developer from a junior one. This is the most important topic for senior interview rounds.
Recovery Models — Must Know
Recovery Models & When to Use Each
-- SQL Server has 3 recovery models
-- They control how much data you can recover and how big the log grows

-- 1. SIMPLE: log is truncated after each checkpoint
--    ✅ Use for: Dev/Test databases, data warehouses loaded in bulk
--    ❌ Cannot: do log backups or point-in-time restore
ALTER DATABASE TestDB SET RECOVERY SIMPLE;

-- 2. FULL: entire transaction log is kept until you back it up
--    ✅ Use for: Production OLTP databases (banking, retail, healthcare)
--    ✅ Can: do point-in-time restore (restore to exact moment before accident)
ALTER DATABASE HospitalDB SET RECOVERY FULL;

-- 3. BULK_LOGGED: like FULL but bulk operations use minimal logging
--    ✅ Use for: Mixed workloads with occasional large bulk loads
ALTER DATABASE DataWarehouse SET RECOVERY BULK_LOGGED;
GO
Backup Strategy — The 3-2-1 Rule in SQL Server
Full, Differential, and Log Backup Schedule
-- === FULL BACKUP — Weekly (Sunday night) ===
-- Full backup: copies the entire database
-- COMPRESSION reduces backup file size by 60-80%
-- STATS = 10 shows progress every 10%
BACKUP DATABASE HospitalDB
TO DISK = 'D:\Backups\HospitalDB_Full_20240114.bak'
WITH
    COMPRESSION,
    STATS = 10,
    NAME = 'HospitalDB Full Backup - Jan 14 2024';
GO

-- === DIFFERENTIAL BACKUP — Daily (Mon-Sat at midnight) ===
-- Differential backup: only changes since the LAST FULL backup
-- Much smaller and faster than a full backup
BACKUP DATABASE HospitalDB
TO DISK = 'D:\Backups\HospitalDB_Diff_20240115.bak'
WITH DIFFERENTIAL, COMPRESSION, STATS = 10;
GO

-- === TRANSACTION LOG BACKUP — Every 15 minutes ===
-- Log backup: captures all transactions since last log backup
-- Allows point-in-time restore (restore to exact minute)
-- Also keeps the log file from growing forever in FULL recovery model
BACKUP LOG HospitalDB
TO DISK = 'D:\Backups\HospitalDB_Log_20240115_1645.bak'
WITH COMPRESSION, STATS = 10;
GO
Disaster Recovery — Point-in-Time Restore
RESTORE — Recover to Before the Accident (4:25 PM)
-- Scenario: Accidental DELETE at 4:30 PM on January 15, 2024
-- Goal: restore to 4:25 PM (just before the accident)

-- Step 1: First take a tail-log backup (captures the last transactions)
-- NO_TRUNCATE: even though the database may be damaged, backup what's in the log
BACKUP LOG HospitalDB
TO DISK = 'D:\Backups\HospitalDB_TailLog.bak'
WITH NO_TRUNCATE;
GO

-- Step 2: Restore the last FULL backup (NORECOVERY = leave in restoring state)
-- NORECOVERY means: don't make this operational yet, more backups to apply
RESTORE DATABASE HospitalDB
FROM DISK = 'D:\Backups\HospitalDB_Full_20240114.bak'
WITH
    NORECOVERY,
    REPLACE,      -- overwrite existing database
    STATS = 10;
GO

-- Step 3: Apply the last DIFFERENTIAL backup
RESTORE DATABASE HospitalDB
FROM DISK = 'D:\Backups\HospitalDB_Diff_20240115.bak'
WITH NORECOVERY, STATS = 10;
GO

-- Step 4: Apply transaction log backups one by one up to 4:25 PM
RESTORE LOG HospitalDB
FROM DISK = 'D:\Backups\HospitalDB_Log_20240115_1600.bak'
WITH NORECOVERY;
GO

-- Final log backup with STOPAT — stop applying at exactly 4:25 PM
RESTORE LOG HospitalDB
FROM DISK = 'D:\Backups\HospitalDB_Log_20240115_1615.bak'
WITH
    RECOVERY,    -- RECOVERY = final restore step, bring database online
    STOPAT = '2024-01-15 16:25:00';
    -- STOPAT: apply only transactions up to this exact moment
    -- Database comes online with data as it was at 4:25 PM
GO

PRINT 'Database restored to 4:25 PM. Accidental DELETE reversed.';
AlwaysOn Availability Groups — Concept Summary

AlwaysOn AG — What Every Senior Interview Expects You to Know

Primary ReplicaThe main server that handles all read/write operations. Only one primary at a time in an AG.
Secondary ReplicaOne or more standby servers that receive log records from the primary and stay in sync. Can be used for read-only queries to offload reporting load from primary.
Synchronous CommitPrimary waits for secondary to confirm log written before committing. Zero data loss but slight latency. Use for same-datacenter HA.
Asynchronous CommitPrimary commits without waiting for secondary. Possible data loss on failover. Use for DR replicas in remote datacenters where network latency is high.
AG ListenerA virtual network name that clients connect to. After failover, the listener automatically points to the new primary — applications don't need to change connection strings.
RPO / RTORPO (Recovery Point Objective) = how much data loss is acceptable (e.g., 15 minutes of transactions). RTO (Recovery Time Objective) = how quickly the system must be back online (e.g., within 2 minutes). AlwaysOn with synchronous commit targets RPO = 0, RTO < 30 seconds.
Interview Questions

🎤 Likely Interview Questions

Q: A developer accidentally deleted all rows in a production table at 3 PM. Logs show the last full backup was at midnight. What do you do?
First, immediately take a tail-log backup to capture all transactions right up to the moment before recovery. Then restore in sequence: the midnight Full backup with NORECOVERY, then the differential backup taken at noon with NORECOVERY, then transaction log backups from noon onwards, using STOPAT set to just before 3 PM. The final RESTORE LOG uses WITH RECOVERY to bring the database online. This is a point-in-time restore — possible only in FULL recovery model with regular log backups. This is why 15-minute log backup schedules exist in every production environment.
Q: What is the difference between RTO and RPO?
RPO — Recovery Point Objective — defines how much data loss the business can tolerate. If RPO is 1 hour, you must take log backups at least every hour. RTO — Recovery Time Objective — defines how quickly the system must be available again after an outage. If RTO is 5 minutes, a manual restore process taking 2 hours is not acceptable — you need AlwaysOn AG for near-instant automatic failover. Both are business decisions communicated as SLAs, and the DBA/SQL Developer's job is to design the backup and HA strategy to meet them.
Q: What is the difference between a FULL backup and a DIFFERENTIAL backup?
A Full backup copies the entire database — every page. A Differential backup copies only the pages that changed since the LAST FULL backup. This is why differentials get progressively larger throughout the week (more pages change), and why you take a new full backup weekly — to reset the differential base. To restore, you always need: the last Full backup + the last Differential + all subsequent Log backups. You never need intermediate differentials.
