PROJECT 27 OF 30 · DAY-TO-DAY OPERATIONS

Compliance Automation

Proving, at scale and on a schedule, that every server actually meets ABC Bank's security baseline — not just assuming it does.

1. The Production Story

Day 27 at ABC Bank. The bank's information security policy mandates every Linux server meet a defined hardening baseline — password aging rules, disabled root SSH login, a minimum firewall configuration, and more. Historically, compliance was "checked" by an engineer manually reviewing a sample of servers before an audit — never all of them, and never consistently. Today we build a scan that checks every server, every week, against every rule, automatically.

2. Compliance Scanning vs Health Checking

Project 25's health check asks "is this server currently working?" A compliance scan asks a different question: "is this server currently configured the way policy requires?" A server can be perfectly healthy and still be non-compliant — for example, root SSH login enabled works fine operationally but violates security policy. These are deliberately separate playbooks with separate purposes.

3. ABC Bank's CIS-Based Baseline (Subset)

RuleWhy It's Required
Root SSH login disabledForces privilege escalation through named, audited accounts instead of anonymous root access
Password minimum age ≥ 1 day, maximum ≤ 90 daysStandard password rotation policy, aligned with CIS Benchmark recommendations
Firewall (firewalld) activeBaseline network protection on every host, not just at the perimeter
No world-writable files in /etcPrevents unauthorized configuration tampering

4. The Full Compliance Scan Playbook (Check-Only)

---
# File: playbooks/compliance_scan.yml — CHECK ONLY, never modifies anything
- name: ABC Bank CIS Baseline Compliance Scan
  hosts: linux_servers
  become: yes
  gather_facts: no

  tasks:
    - name: Check if root SSH login is disabled
      ansible.builtin.command: grep -E '^PermitRootLogin\s+no' /etc/ssh/sshd_config
      register: root_login_check
      changed_when: false
      failed_when: false            # Don't fail the play here — we want to collect ALL findings, not stop at the first one

    - name: Check password maximum age policy
      ansible.builtin.command: grep '^PASS_MAX_DAYS' /etc/login.defs
      register: pass_age_check
      changed_when: false
      failed_when: false

    - name: Check firewalld is active
      ansible.builtin.systemd:
        name: firewalld
      register: firewall_check

    - name: Check for world-writable files in /etc
      ansible.builtin.shell: find /etc -xdev -type f -perm -0002 | wc -l
      register: world_writable_check
      changed_when: false

    - name: Build this host's compliance findings
      ansible.builtin.set_fact:
        compliance_findings:
          root_ssh_disabled: "{{ root_login_check.rc == 0 }}"
          password_policy_ok: "{{ 'PASS_MAX_DAYS   90' in pass_age_check.stdout | default('') }}"
          firewall_active: "{{ firewall_check.status.ActiveState == 'active' }}"
          no_world_writable_files: "{{ world_writable_check.stdout | int == 0 }}"

    - name: Publish this host's compliance result to the Workflow
      ansible.builtin.set_stats:            # Same technique introduced in Project 25 — surfaces per-host results upward
        data:
          compliance_report: "{{ compliance_findings }}"
Deliberate design choiceEvery check uses failed_when: false or an equivalent non-failing pattern. A compliance scan's job is to report findings across the whole fleet, not to stop partway through — an engineer reviewing results needs the complete picture, not a scan that halted at server 3 of 54.

5. Generating a Consolidated Compliance Report

Because every host publishes its own compliance_report stat, the Job's final summary (visible in the AAP Job Output's "Details" view) shows a per-host breakdown of all four findings — this becomes the raw material for the audit-ready report. A follow-on step (often a small script run outside AAP, or a Workflow node calling the AAP API) aggregates these per-host stats into a single spreadsheet or dashboard for the compliance team.

6. Remediation — A Separate, Deliberate Step

Why we don't auto-fix findings in the same playbookIt's tempting to have this playbook automatically disable root SSH login or start firewalld the moment it finds a violation. ABC Bank deliberately keeps scan and remediation as two separate Job Templates — a scan should never silently change production servers. Findings are reviewed by a human first; remediation is then run explicitly, using the same Approval Node pattern from Project 20 for any production-impacting fix.

7. Hands-On: Scheduling the Weekly Scan

10. Interview Prep — Say This Out Loud

"How is a compliance scan different from a health check in Ansible?"

A health check asks whether a server is currently working correctly; a compliance scan asks whether it's configured according to policy — a server can be perfectly healthy and still be non-compliant, so they're deliberately separate playbooks with separate purposes.

"Why keep compliance scanning and remediation as separate Job Templates?"

A scan should never silently change production servers — findings need human review first. Keeping them separate, with remediation gated behind an explicit Approval Node when needed, avoids an automated scan accidentally becoming an unreviewed automated change.

11. Wrap-Up

Key Learnings

  • Compliance scanning checks configuration against policy, distinct from health checking.
  • failed_when: false lets a scan collect complete findings across the whole fleet instead of stopping at the first violation.
  • Scan and remediation stay separate Job Templates — never auto-fix inside a scan.
