Understanding AAP Architecture

What is actually running behind that login screen, and why it's built this way for a bank.

1. The Production Story

Day 2 at ABC Bank. Yesterday we launched a demo Job Template and watched it succeed — good, but our Team Lead stopped us in the corridor this morning with a pointed question: "If the Controller server goes down at 2 AM during a patching window, does the whole bank's automation stop? Where does the playbook actually execute — on the Controller, or somewhere else? And how does AAP reach servers sitting inside our restricted core-banking network zone, which has almost no firewall rules open?"

We didn't have a confident answer. So today, before we touch another Job Template, we are going to open up AAP and understand what is physically running, where, and why it was designed this way — the same way our Team Lead had to understand it before signing off on the architecture with the Infrastructure and Network Security teams.

2. Why We Need This Today

In Project 01 we treated AAP as one black box: log in, click Launch, watch output. That's enough to run a job, but not enough to be trusted with production incidents. When a job hangs, fails to reach a host, or the whole platform feels slow, the first question a senior engineer asks is "which component is the problem?" — Controller, Execution Environment, or the network path to the mesh node. You can't answer that without knowing the architecture.

3. The Big Picture — Three Layers

AAP is not one application. Ask any Red Hat architect and they'll draw it as three separate layers that talk to each other over an API. Keep this mental model — everything else in this project is detail underneath these three boxes.

Answer to our Team Lead's first questionNotice there are two Controller nodes sharing one database. AAP in a real bank deployment is clustered — if one Controller node goes down at 2 AM, the other keeps serving the UI and API, and running jobs are not dropped. This is exactly why ABC Bank's platform team sized the Controller as a 2-node (minimum) cluster.

4. Controller — What's Actually Inside

"Controller" is the name for what used to be called Ansible Tower. It is a Django-based web application plus a REST API, backed by a PostgreSQL database, with a task dispatcher that hands work to execution nodes. When you use the web UI, every single click is really just the browser calling that same REST API underneath — which is exactly why anything you can do by clicking, a pipeline can also do by calling the API directly (we use this in Project 22 for CI/CD integration).

Web/API Server

Handles your login, renders the UI, and exposes the REST endpoints. This is what you're talking to when you click anything.

Task Dispatcher

Decides which execution node should run a given job, based on Instance Groups (we'll meet these properly when we cover capacity planning in later projects).

PostgreSQL Database

Stores every Organization, Credential (encrypted), Template, and the complete history/log of every job ever run. This is the database an auditor is really asking about when they ask "prove who ran this change."

Common misconceptionNew engineers often think the playbook runs "on the Controller." It almost never does in a real deployment — the Controller only decides where to run it and shows you the streamed result. The actual execution happens one layer down, inside an Execution Environment on an execution node. Keep reading.

5. Execution Environments — Where Code Actually Runs

An Execution Environment (EE) is a container image — think of it as a sealed toolbox. Inside that toolbox is a specific version of Python, a specific version of Ansible core, and every Ansible Collection ABC Bank has approved (for example ansible.windows for our Windows fleet, community.vmware for our virtualization team). When a job launches, AAP starts a fresh container from this image, runs the playbook inside it, then throws the container away.

Why not just install Ansible directly on the Controller?Answer
Version conflictsThe Linux team may need an older community.general collection than the Windows team's playbooks require — two different EE images solve this cleanly with zero conflict.
ConsistencyEvery engineer's job runs inside the identical container image, so "it worked on my laptop" style bugs disappear entirely.
SecurityThe container is disposable — nothing persists on it between jobs, so there is nothing on it for an attacker to later exploit.
Day-to-day relevanceWhen a job fails with a "module not found" error, your first suspicion should be "wrong Execution Environment selected on this Job Template" — not "Ansible is broken." We practice diagnosing exactly this in Project 28.

6. Automation Mesh & Execution Nodes

This is the direct answer to our Team Lead's third question. ABC Bank's network is segmented — the core banking zone, the DMZ, and the internal corporate zone are all separated by firewalls with very few open ports between them. If the Controller (sitting in the corporate zone) tried to SSH directly into a core-banking server, Network Security would have to open a wide SSH rule between two sensitive zones — that request would almost certainly be rejected.

Instead, AAP deploys small, lightweight execution nodes physically inside each zone. The Controller talks to these nodes over one single encrypted mesh connection (outbound-friendly), and the execution node then does the actual SSH/WinRM hop to nearby servers, since it's already sitting inside that zone.

Answer to our Team Lead's second questionThe Automation Mesh is exactly how AAP reaches the core-banking zone without a broad SSH rule — Network Security only had to approve one narrow mesh port between zones, instead of opening SSH bank-wide.

7. Automation Hub

Automation Hub is a private content library, separate from the public Ansible Galaxy. Before any Collection (a bundle of reusable modules/roles, e.g. community.windows) goes into an ABC Bank Execution Environment, the security team reviews it and publishes an approved copy into Hub. Engineers only ever pull content from Hub, never straight from the open internet.

Why this mattersThis is a direct BFSI compliance control — it stops a compromised or malicious public collection from ever reaching a production banking server, because the only path in is through a reviewed, internal Hub.

12. Interview Prep — Say This Out Loud

"Explain the AAP architecture end to end."

Walk through the three layers: Control Plane (Controller cluster + PostgreSQL), Content (Automation Hub + Git Projects), and Execution (Automation Mesh nodes running Execution Environment containers). Emphasize that the Controller decides and logs, but never itself executes the playbook.

"Why does AAP use Execution Environments instead of installing Ansible directly on the Controller?"

Consistency, isolation of dependency versions between teams, and security — the container is disposable so nothing persists between jobs.

"How does AAP automate a segmented network without opening broad firewall rules?"

Automation Mesh — lightweight execution nodes are deployed inside each network zone, and the Controller talks to them over one narrow, outbound-friendly mesh link, instead of the Controller itself reaching directly into a restricted zone.

13. Wrap-Up

Key Learnings

  • AAP has three layers: Control Plane, Content, Execution — and playbooks run in the Execution layer, not on the Controller.
  • Automation Mesh is how AAP crosses segmented banking network zones without wide firewall rules.
  • Execution Environments are disposable containers, which is why "module not found" points to the wrong EE, not a broken install.

Resume Point
