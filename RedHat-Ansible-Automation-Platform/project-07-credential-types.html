Credential Types

What a Credential Type actually is under the hood — and how to build one AAP doesn't ship with.

1. The Production Story

Day 7 at ABC Bank. Our Team Lead drops a new requirement: later in this track (Project 26, Production Release) we'll need our workflows to automatically open and update an incident ticket in ServiceNow, the bank's ITSM tool, whenever a production job runs. ServiceNow needs an API token and instance URL — but AAP has no built-in "ServiceNow" Credential Type.

Before we can even think about that integration, we need to understand what a Credential Type actually is — because the fix is not a workaround, it's a first-class AAP feature: we're going to build our own Credential Type from scratch.

2. Why "Machine" Isn't Enough for Every Case

In Project 06 we only used the Machine type. But a Credential Type is really just a form definition — it describes which input fields to show (username, key, token, URL...) and, separately, which environment variables or file injections to hand to the playbook at runtime. AAP ships with common ones built in, but banks always end up needing at least one custom type for an internal tool nothing generic covers.

4. The Credential Types Screen

Where: Administration → Credential Types (a separate area from the day-to-day Resources menu, since this is a platform-configuration activity). Who uses it: Automation Admins only, and typically only once per new external system the bank wants to integrate. What you see: a list of every type — built-in ones are read-only; custom ones can be edited.

5. Building a Custom Credential Type

A custom Credential Type has exactly two parts, both written in YAML: the Input Configuration (what fields the admin sees and fills in when creating a Credential of this type) and the Injector Configuration (how those field values get exposed to the playbook at runtime — as environment variables, extra variables, or a temporary file).

6. Every Part Explained

PartWhat it means
Input Configuration → fieldsList of form fields — each has an id, a label, a type (string, boolean), and whether it's a secret (masked and encrypted like a password).
Input Configuration → requiredWhich of those fields must be filled before Save is allowed.
Injector Configuration → envMaps a field to an environment variable name the playbook/module can read at runtime.
Injector Configuration → extra_varsAlternative to env vars — exposes the field as an Ansible variable directly usable inside {{ }} in the playbook.

7. Hands-On: Building a ServiceNow Custom Credential Type

  • Click Administration → Credential Types → Add.
  • Name: ServiceNow ITSM API
  • Input Configuration — paste the YAML below, defining an instance URL and an API token field.
  • Injector Configuration — paste the second YAML below, exposing both as environment variables.
  • Click Save. A new Credential Type now appears in the dropdown whenever anyone creates a Credential — exactly alongside Machine and Vault.
# Input Configuration — defines what the admin fills in on the Add Credential form
fields:
  - id: instance_url        # Internal field name, used to reference this value later
    type: string             # Plain text field
    label: ServiceNow Instance URL  # What the admin sees on the form
  - id: api_token
    type: string
    label: ServiceNow API Token
    secret: true              # Masked on screen and encrypted at rest, like a password
required:
  - instance_url
  - api_token

# Injector Configuration — defines how the playbook receives these values at runtime
env:
  SNOW_INSTANCE_URL: '{{ instance_url }}'   # Playbook/module reads this as a normal environment variable
  SNOW_API_TOKEN: '{{ api_token }}'          # Same for the token — never printed in job output
Production tipOnce this Credential Type exists, our upcoming ServiceNow integration (Project 26) just creates one Credential of this type and attaches it to the relevant Workflow — the same clean "create once, reference everywhere" pattern we've used since Project 06.

10. Interview Prep — Say This Out Loud

"When would you build a custom Credential Type instead of using a built-in one?"

When integrating with a system AAP has no native type for — like an internal ITSM tool such as ServiceNow. You define the input fields once and how they're injected into the playbook at runtime, and from then on it behaves exactly like any built-in Credential Type.

"What are the two parts of a custom Credential Type?"

Input Configuration, which defines the form fields shown to whoever creates a Credential of that type, and Injector Configuration, which defines how those values reach the playbook at runtime — usually as environment variables or extra variables.

11. Wrap-Up

Key Learnings

  • A Credential Type is a form definition plus a runtime injection rule — nothing more.
  • Built-in types cover the common cases; custom types are a first-class, supported way to add your own.
  • Marking a field secret: true is what masks and encrypts it — easy to forget.
