Turning "it's broken, help" into a repeatable five-layer diagnostic method — built from every failure pattern in this track.

1. The Production Story

Day 28 at ABC Bank. Priya gets paged: the nightly Cards Health Check failed, but she's not sure whether the problem is AAP itself, the network, the Credential, or the playbook. Our Team Lead uses this as the teaching moment for today: "Don't guess. 2. A Methodology, Not a Guessing Game

Across Projects 01–27 we've seen dozens of specific failure scenarios. Today we organize all of them into one reusable framework, so a new failure — one we've never seen before — still gets diagnosed the same systematic way.

3. The Five-Layer Diagnostic Model

graph TD A[1. Platform Layer

Does this user/credential have permission?] B --> C[3. Content Layer

Work top to bottom — a Layer 5 playbook bug is meaningless to chase if Layer 1's Controller cluster is actually degraded. Each layer traces back to specific projects in this track.

5. Reading Job Output Like a Senior Engineer

  • Start at the bottom, not the top. The final error is usually what actually stopped the job — scroll up from there to see what led into it, rather than reading top-down.
  • Identify which task failed by name — every task in our playbooks throughout this track has a descriptive name: precisely so this is obvious at a glance.
  • Check the "msg" field in the failure block — Ansible almost always explains exactly what went wrong in plain language, not just an exit code.
  • Cross-reference against the Matrix above to jump straight to the right layer instead of investigating randomly.

6. Using Verbosity Levels Deliberately

LevelWhen to Use
0 (Normal)Default for routine runs — enough detail for a healthy job.
1–2First troubleshooting step — shows task-level results and basic variable values.
3Shows full connection details — useful for Layer 4 (Connectivity) issues like SSH/WinRM handshake failures.
4+Extremely detailed, including raw module input/output — reserved for genuinely stuck problems, since it's noisy and can be slow on large Inventories.
Production tipRelaunch a failed job at a higher Verbosity rather than guessing — the "Relaunch" button (Job Output toolbar) lets you re-run with different Verbosity without editing the Job Template itself.

7. Hands-On: Diagnosing a Real Multi-Layer Failure

Scenario: Priya's nightly Cards Health Check job shows "Failed" this morning. Let's work through the five layers together, exactly as she should.
  • Layer 1: Check Administration → Instances — Controller cluster and execution nodes all show healthy. Not the cause. Move on.
  • Layer 2: This job ran on a Schedule (a system trigger, not Priya), so RBAC isn't relevant here — Schedules run with the Template's own configured Credential regardless of who's logged in. Move on.
  • Layer 3: Check the Project's last sync — succeeded, correct commit. Execution Environment field on the Template — correctly set. Not the cause. Move on.
  • Layer 4: Job Output shows all 42 hosts connected successfully — no SSH errors. Not the cause. Move on.
  • Layer 5: One specific task, "Fail if root partition is over 90% full" (from Project 12's playbook), shows Failed on exactly one host — cards-app-lin-07. This is a genuine finding, not a platform problem: that server's disk is actually full.
  • Resolution: This isn't a troubleshooting bug at all — it's the health check correctly doing its job. Priya opens an infra ticket to clear space on cards-app-lin-07, exactly the outcome Project 15's Notification was built to surface.
The real lessonNot every "failure" is a bug in our automation — sometimes the automation is working exactly as designed, correctly catching a real infrastructure problem. Layer-by-layer diagnosis tells you which situation you're in, quickly.

9. Interview Prep — Say This Out Loud

"Walk me through how you'd troubleshoot a failed AAP job you've never seen before."

Work through five layers in order: platform health (Controller/mesh), access (RBAC/permissions), content (Project sync, correct Execution Environment), connectivity (Credential, network path), and finally execution (the playbook logic itself). Working top-down avoids chasing a playbook bug when the real problem is, say, a degraded mesh node.

"How do you decide which Verbosity level to relaunch a failed job at?"

Start at 1–2 for general task-level detail; go to 3 specifically for connectivity issues where you need to see the SSH/WinRM handshake; reserve 4+ for genuinely stuck problems since it's noisy and slower on large inventories.

10. Wrap-Up

Key Learnings

  • Five layers — Platform, Access, Content, Connectivity, Execution — cover nearly every failure category in AAP.
  • Read Job Output from the bottom up, and cross-reference against a known matrix instead of guessing.
  • Not every failure is a bug — sometimes automation is correctly catching a real problem.
