PROJECT 17 OF 30 · INFRASTRUCTURE LAYER

Automation Mesh (Deep Dive)

Beyond "one node per zone" — how AAP actually reaches a network segment with no direct route at all.

1. The Production Story

Day 17 at ABC Bank. The Payment Switch servers sit in an even more restricted network segment than the DMZ — a segment so locked down that Network Security won't allow AAP's Controller to establish even the single narrow mesh link we set up in Project 02 for the DMZ and Core Banking zones. There's no direct path at all from the Controller's zone to this one.

Our Team Lead explains this doesn't break our design — it's exactly the scenario Automation Mesh was built for. Today we go deeper than Project 02's introduction and add a hop node: an intermediate relay that lets the Controller reach the Payment Switch zone indirectly, through a path Network Security has actually approved.

2. From "One Node Per Zone" to a Real Mesh

Project 02 showed a simple star pattern — Controller talking directly to one execution node per zone. A real "mesh" earns its name when nodes can relay traffic for each other, not just talk directly to the Controller. This is what lets AAP reach a zone that has no direct network path to the Controller at all, as long as some already-connected node has a path into it.

3. The Three Node Types

Control Node

Runs the Controller web/API and the PostgreSQL-backed job dispatcher. Decides which execution node should run each job. This is what we clustered back in Project 02.

Execution Node

Actually runs the Execution Environment container and connects out (SSH/WinRM) to managed hosts in its own zone.

Hop Node

Relays mesh traffic only — it never runs a job itself. Its only purpose is forwarding encrypted mesh connections from the Controller to an execution node it otherwise couldn't reach directly.

4. The Instances & Instance Groups Screens

Where: Administration → Instances (individual nodes, their type and health) and Administration → Instance Groups (logical pools of execution nodes that Organizations/Inventories get pinned to, exactly as we configured back in Projects 03 and 09). Who uses it: Automation Admins / Platform team, in coordination with Network Security whenever a new zone is being onboarded.

6. Hands-On: Adding a Hop Node for the Payment Switch Zone

  • Infra deploys a small hop-node VM in a semi-restricted segment that both the Controller's zone and the Payment Switch zone are allowed to reach — agreed with Network Security beforehand.
  • Click Administration → Instances → Add.
  • Hostname: mesh-hop-paysw.abcbank.internal; Node Type: Hop.
  • Peers: set this hop node's peer relationship to the Controller cluster.
  • Deploy the actual Payment Switch execution node inside the restricted zone, and set its Peers to point at the new hop node — not directly at the Controller, since no such path exists.
  • Save both. Add the new execution node to a new Instance Group, e.g. payment-switch-execution, then pin the Payment Switch Organization/Inventory to that group, exactly as we did for the DMZ group in Projects 03 and 09.

7. How AAP Picks a Path Through the Mesh

When a job targets the Payment Switch Inventory, the Controller doesn't need to know the whole path manually — it looks up which Instance Group owns that Inventory, finds the execution node in that group, and the mesh layer itself relays the connection through however many hop nodes the configured Peers chain requires. From an engineer's point of view, launching this job looks identical to launching one against the DMZ — the routing complexity is entirely invisible above the Instance Group layer.

8. Resilience — What Happens When a Node Fails

FailureImpact
One Controller node in the cluster goes downNo impact — the other Controller node(s) continue serving (Project 02)
A hop node goes down with no redundant peer pathEvery zone reachable only through that hop node becomes unreachable until it's restored — this is why production mesh designs add a second hop node as a redundant path for critical zones
An execution node in one zone goes downOnly jobs targeting that zone's Instance Group are affected; other zones are unaffected
Design decision worth rememberingABC Bank added a second, redundant hop node for the Payment Switch path specifically because it's a Tier-1 critical system — a single hop node would be a single point of failure for that entire zone's automation.

11. Interview Prep — Say This Out Loud

"What's the difference between a hop node and an execution node in Automation Mesh?"

An execution node actually runs the Execution Environment container and connects out to managed hosts in its zone. A hop node runs no jobs at all — its only job is relaying encrypted mesh traffic between the Controller and an execution node it can't reach directly, letting AAP cross network segments with no direct route.

"How would you design mesh resilience for a Tier-1 critical zone?"

Avoid a single hop node as the only path into that zone — add a redundant hop node with an alternate peer path, so one node failure doesn't cut off automation to the entire zone.

12. Wrap-Up

Key Learnings

  • Three node types: Control, Execution, and Hop — only Hop nodes exist purely to relay mesh traffic.
  • A hop node lets AAP reach a zone with no direct path from the Controller, as long as an approved indirect path exists.
  • Critical zones need a redundant hop-node path to avoid a single point of failure.
