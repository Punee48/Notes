Running Windows Playbooks

The 12 Windows servers we onboarded back in Project 10 finally get their first real automation.

1. The Production Story

Day 22 at ABC Bank. A recurring ticket type finally reaches automation: the Internet Banking team's Windows-hosted middleware service occasionally hangs and needs a controlled restart — today done manually, by RDP-ing into each server one at a time. Priya tries adapting yesterday's Linux playbook and it fails immediately — there's no SSH, no sudo, and the module names are completely different. Today we build this correctly for Windows from the ground up.

2. Why Windows Isn't "Just SSH With Extra Steps"

Ansible manages Windows through an entirely different connection protocol — WinRM (Windows Remote Management) — and a separate set of modules prefixed ansible.windows.* or community.windows.*, mirroring but not identical to their Linux ansible.builtin.* counterparts. This is exactly why we built a dedicated Windows Execution Environment back in Project 16 — the Linux EE simply doesn't contain these Collections.

3. WinRM — The Connection Method Explained

ConceptLinux (SSH) EquivalentWindows (WinRM)
TransportSSH, port 22WinRM, port 5986 (HTTPS) or 5985 (HTTP, avoided in production)
AuthenticationSSH key pairKerberos (preferred, ties into ABC Bank's existing Active Directory) or NTLM
Privilege escalationsudoUsually not needed — the service account itself is granted the specific local rights it needs, since Windows privilege escalation via Ansible is more limited than sudo
Production requirementABC Bank mandates HTTPS WinRM (port 5986) with a valid certificate — plain HTTP WinRM sends credentials with weak protection and would never pass a security review.

4. Setting Up the Windows Machine Credential

  • Resources → Credentials → Add, Type = Machine (same object type as Project 06 — Windows just uses different sub-fields).
  • Username: svc_ib_ansible@ABCBANK.INTERNAL — an Active Directory service account, using the realm-qualified format Kerberos expects.
  • Password: the service account's AD password (rotated regularly per ABC Bank policy — unlike Linux, Windows Machine Credentials commonly use password auth rather than a key).
  • Under Privilege Escalation, leave as None — this account is already a member of the correct local Windows group with exactly the rights it needs, so no escalation step is required.

5. The Full Windows Service Restart Playbook

---
# File: playbooks/windows_restart_middleware.yml
- name: Controlled Restart of IB Middleware Service   # Play name — shown in AAP Job Output
  hosts: windows_servers                          # Targets the Group built in Project 11
  gather_facts: yes

  tasks:
    - name: Check current service status
      ansible.windows.win_service_info:          # Windows equivalent of querying systemctl status
        name: IBMiddlewareSvc
      register: svc_status

    - name: Report current state before touching anything
      ansible.builtin.debug:                     # debug module works identically on both platforms
        msg: "Current state: {{ svc_status.services[0].state }}"

    - name: Stop the middleware service
      ansible.windows.win_service:               # Windows equivalent of ansible.builtin.systemd
        name: IBMiddlewareSvc
        state: stopped

    - name: Clear the temporary cache directory before restart
      ansible.windows.win_file:                  # Windows equivalent of ansible.builtin.file
        path: C:\IBApp\cache
        state: absent

    - name: Start the middleware service
      ansible.windows.win_service:
        name: IBMiddlewareSvc
        state: started

    - name: Confirm the service is running again
      ansible.windows.win_service_info:
        name: IBMiddlewareSvc
      register: final_status
      failed_when: final_status.services[0].state != 'started'  # Explicitly fail the job if the service didn't come back up

6. Hands-On: Wiring This Into a Job Template

  • Commit the playbook to Cards-Payments-Playbooks (or a shared platform repo, since this serves the Internet Banking team), sync the Project.
  • Build a Job Template: IB - Restart Middleware Service, Inventory = the Internet Banking Inventory, Credential = the Windows Machine Credential above.
  • Execution Environment: select ABC-Bank-Windows-EE — the custom image we built in Project 16, containing ansible.windows. Forgetting this step is the single most common reason this template would fail with "module not found."
  • Grant Execute to the relevant Team, launch, and confirm the final task's explicit pass/fail check works correctly.

7. Common Linux-to-Windows Gotchas

Habit From LinuxCorrect Windows Approach
Using ansible.builtin.command for everythingPrefer dedicated ansible.windows.* modules — they're idempotent and Windows-aware, unlike raw PowerShell commands
Using forward-slash pathsWindows paths use backslashes: C:\IBApp\cache, and YAML requires care with escaping
Assuming become: yes is neededUsually unnecessary — Windows rights come from the service account's own group membership, not a sudo-style escalation

9. Troubleshooting

SymptomLikely Cause
Job fails immediately with a WinRM connection errorPort 5986 blocked by firewall, certificate issue, or Kerberos authentication misconfigured
"Module not found" for any ansible.windows.* taskWrong Execution Environment selected — must be the custom Windows EE from Project 16, not the Linux one
Service fails to restart and job doesn't catch itMissing an explicit failed_when check — always verify final state rather than assuming success

10. Interview Prep — Say This Out Loud

"How does Ansible connect to and manage Windows servers?"

Through WinRM instead of SSH, ideally over HTTPS with Kerberos authentication tied into Active Directory. Windows-specific modules like ansible.windows.win_service handle tasks that on Linux would use different modules like systemd or file.

"Why might a Windows playbook fail with a 'module not found' error even though the connection succeeds?"

The Job Template is very likely using a Linux-only Execution Environment that doesn't contain the ansible.windows Collection — the fix is selecting the correct custom Windows EE, not debugging the connection itself.

11. Wrap-Up

Key Learnings

  • Windows automation uses WinRM (ideally HTTPS + Kerberos), not SSH.
  • Dedicated ansible.windows.* modules replace Linux builtin modules — there's no cross-platform shortcut.
  • Always select the matching Windows Execution Environment, or every task fails with module-not-found.
