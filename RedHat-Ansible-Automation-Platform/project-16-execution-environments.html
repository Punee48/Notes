Execution Environments (Deep Dive)

Opening the sealed toolbox we've been referencing since Project 02, and building our own.

1. The Production Story

Day 16 at ABC Bank. Ravi's team wants to add a new playbook that manages Windows servers using the ansible.windows Collection — but when he tests it, the job fails with a "module not found" error, even though the Machine Credential and WinRM connection are configured correctly. Our Team Lead recognizes this instantly: "Your Execution Environment doesn't have that collection baked in. Time to build a proper one instead of hoping the default image happens to include everything we need." Today we go past the conceptual introduction from Project 02 and actually build a custom Execution Environment for ABC Bank.

2. What's Actually Inside That Container

Recall from Project 02: an Execution Environment is a container image with Python, ansible-core, and a defined set of Collections. Concretely, that means three ingredients combine to build one: a base image (usually Red Hat's supported ee-minimal), a list of Python package dependencies, and a list of Ansible Collections. AAP ships default EEs, but any bank will eventually need its own — exactly the Windows Collection gap Ravi just hit.

3. The Execution Environments Screen

Where: left nav, under Resources → Execution Environments. Who uses it: Automation Admins register and manage them; engineers simply pick one from a dropdown on a Job Template (as we did in Project 12). What you see: a list of registered EE images, each pointing to an image location in a container registry (like Automation Hub or a private registry).

5. Building a Custom EE with ansible-builder

The actual image is built outside AAP, using Red Hat's ansible-builder tool, from three definition files committed to Git — the same "everything lives in version control" principle we established with Projects in Project 08.

# execution-environment.yml — top-level build definition read by ansible-builder
version: 3                          # Schema version of this build spec
images:
  base_image:
    name: registry.redhat.io/ansible-automation-platform/ee-minimal-rhel9:latest  # Red Hat's supported minimal base
dependencies:
  galaxy: requirements.yml         # Points to the Collections file below
  python: requirements.txt         # Points to any extra Python packages needed

# requirements.yml — Collections to bake into this image
collections:
  - name: ansible.windows        # Provides win_* modules Ravi's playbook needs
    version: "2.3.0"            # Pinned version — never "latest" in a bank environment
  - name: community.windows
    version: "2.1.0"
  • Automation Admin runs ansible-builder build -t abcbank/windows-ee:1.2.0 -f execution-environment.yml — this reads all three files and produces the container image.
  • Push the built image to ABC Bank's private container registry (never a public registry, per Project 07's Automation Hub philosophy of only using bank-approved content).

6. Hands-On: Registering the New EE in AAP

  • Click Resources → Execution Environments → Add.
  • Name: ABC-Bank-Windows-EE
  • Image: registry.abcbank.internal/aap/windows-ee:1.2.0
  • Pull: Only if not present locally.
  • Click Save. Now go back to Ravi's Job Template, change the Execution Environment field to this new one, and relaunch — the "module not found" error is gone, because ansible.windows now genuinely exists inside the container.

7. Versioning and Rollback

Production tipAlways tag EE images with a specific version (1.2.0), never latest. If a new EE version introduces a regression, rolling back is as simple as pointing the Execution Environment's Image field back to the previous tag — exactly the same rollback safety we get from Git commit pinning in Project 08.

9. Troubleshooting

SymptomLikely Cause

10. Interview Prep — Say This Out Loud

"How would you troubleshoot a 'module not found' error in AAP?"

Check which Execution Environment the Job Template is using and confirm the required Collection is actually baked into that image — it's almost never a broken Ansible install, it's usually the wrong or outdated EE selected.

"How do you build a custom Execution Environment, and what goes into it?"

Using ansible-builder with three files: execution-environment.yml (base image and pointers), requirements.yml (Ansible Collections, version-pinned), and requirements.txt (extra Python packages). The result is built into a container image, pushed to a private registry, and registered in AAP.

11. Wrap-Up

Key Learnings

  • An EE is a container image = base image + Python deps + Ansible Collections, built with ansible-builder.
  • "Module not found" almost always means the wrong EE, not a broken Ansible install.
  • Always pin EE image tags to a specific version — never "latest" — for safe rollback.
