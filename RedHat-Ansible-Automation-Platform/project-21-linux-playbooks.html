4. The Full Multi-Role User Management Playbook

---
# File: playbooks/create_service_account.yml
- name: Create Reconciliation Service Account       # Play name — shown in AAP Job Output
  hosts: cards_app_tier                            # Targets the role-based Group we built in Project 11
  become: yes                                       # Escalate privileges (sudo) — required to create users
  gather_facts: yes

  vars:
    service_account: svc_reconciliation            # Centralized here so it's easy to reuse this playbook for future accounts
    ssh_pubkey_path: files/svc_reconciliation.pub  # Public key file committed alongside the playbook in Git

  tasks:
    - name: Ensure the service account group exists
      ansible.builtin.group:
        name: "{{ service_account }}"
        state: present                        # "present" means create it if missing, do nothing if it already exists

    - name: Ensure the service account user exists
      ansible.builtin.user:
        name: "{{ service_account }}"
        group: "{{ service_account }}"
        shell: /bin/bash
        create_home: yes
        state: present

    - name: Deploy the account's authorized SSH key
      ansible.posix.authorized_key:                # Dedicated module for managing authorized_keys safely
        user: "{{ service_account }}"
        state: present
        key: "{{ lookup('file', ssh_pubkey_path) }}"  # Reads the public key file from the Project's Git repo

    - name: Grant limited sudo rights for the reconciliation service
      ansible.builtin.copy:
        dest: /etc/sudoers.d/{{ service_account }}
        content: "{{ service_account }} ALL=(ALL) NOPASSWD: /usr/local/bin/recon_job.sh\n"  # Scoped to ONE script only — never a blanket sudo grant
        mode: '0440'                     # Sudoers files must be exactly this permission or sudo rejects them
        validate: 'visudo -cf %s'       # Syntax-checks the file before accepting it — prevents a broken sudoers file locking out sudo entirely

    - name: Confirm the account was created successfully
      ansible.builtin.command: id {{ service_account }}
      register: id_check
      changed_when: false                 # A read-only check task should never report as a "change"

    - name: Report result
      ansible.builtin.debug:
        msg: "{{ service_account }} confirmed: {{ id_check.stdout }}"

5. Why We Split This Into Roles (In Real Projects)

For a task this size, one playbook file is fine — but ABC Bank's larger playbooks are organized as Ansible Roles (a standard folder structure with tasks/, handlers/, templates/, defaults/). A "user_management" role could be reused across many playbooks — creating svc_reconciliation today, and a future svc_reporting next month — without copy-pasting the same five tasks again.

Production tipThe rule of thumb our Team Lead uses: if a set of tasks will plausibly be reused in a second playbook, promote it to a Role. If it's truly a one-off, a single playbook file like the one above is fine.

7. Idempotency — The Most Important Ansible Concept

Notice every task above uses state: present, not an imperative command like "create user." If we run this playbook a second time against a server that already has the account, Ansible checks the current state first and reports the task as ok (no change) rather than failing or duplicating anything. This property — safe to run repeatedly with the same result — is called idempotency, and it's why we can safely re-run this exact template if a new server is added to cards_app_tier next month, without worrying about the 42 existing servers.

Common mistakeUsing ansible.builtin.command with a raw useradd shell command instead of the user module. The raw command isn't idempotent — running it twice would either error ("user already exists") or, worse, silently do something unintended, whereas the user module handles this correctly by design.

9. Troubleshooting

SymptomLikely Cause
Sudoers task fails validationSyntax error in the sudoers content string — the validate: 'visudo -cf %s' line is deliberately catching this before it's applied
SSH key task fails with "file not found"The public key file wasn't committed to the Project's Git repo, or the Project hasn't been re-synced since the commit

10. Interview Prep — Say This Out Loud

"What is idempotency, and why does it matter in Ansible?"

It means running the same playbook multiple times produces the same end state without unwanted side effects — Ansible checks the current state before acting, so a "create user" task run twice doesn't fail or duplicate anything the second time. It matters because it lets us safely re-run playbooks against a growing server fleet without manually tracking what's already been done.

"How would you grant a service account limited, not blanket, sudo rights?"

Write a scoped sudoers entry limited to the specific script or command the account needs — never ALL=(ALL) ALL — and always validate the sudoers file with visudo -cf before applying it, so a syntax error can't lock out sudo entirely.

11. Wrap-Up

Key Learnings

  • Idempotency (state: present, not raw commands) is what makes playbooks safely re-runnable.
  • Scoped sudoers entries, validated with visudo, are the correct way to grant limited privilege escalation.
  • Promote tasks to a reusable Role once you'll need the same logic in a second playbook.
