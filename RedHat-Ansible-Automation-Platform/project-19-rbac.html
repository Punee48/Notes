PROJECT 19 OF 30 · MILESTONE — ACCESS LAYER

Role Based Access Control

Formalizing the "who can do what" question we've been answering informally since Priya's first day.

1. The Production Story

Day 19 at ABC Bank. The internal audit team is scheduling their quarterly review of the automation platform, and they've sent a specific request ahead of time: "Show us, precisely, who can view versus who can edit versus who can execute each production Job Template — not a verbal explanation, an actual access matrix we can verify against the system."

We've been granting Teams "Execute" access informally since Project 12. Today, we formalize the complete RBAC model so we can answer the audit with confidence, object by object.

2. RBAC — The Piece We've Been Previewing

Every object we've built — Organizations, Credentials, Projects, Inventories, Templates — supports the same underlying access model. A Role is a named bundle of permissions (like "can launch, but not edit"), and it's granted to a User or a Team against one specific object. This is what actually enforces everything Organizations and Teams only set the stage for.

3. Where Roles Actually Get Assigned

Where: on the object itself — every Credential, Project, Inventory, and Template has an "Access" (or "Team Access" / "User Access") tab, exactly like the one we used in Project 12. Who uses it: Automation Admins, and delegated Team Leads for objects they've been given Admin rights on. There's no single central "permissions matrix" screen — access is always granted per object, which is precisely why the Project 12-style tab we've used repeatedly is the real mechanism.

5. How Roles Inherit Down the Object Tree

Granting a Team the Admin role on an Organization cascades down to every object inside it, without needing to repeat the grant on each Credential, Project, and Template individually. Granting a role directly on one specific Template only affects that Template. Understanding this distinction is exactly what prevents both over-granting (accidentally admin-ing an entire Organization when only one Template was intended) and under-granting (repeating the same manual grant across dozens of objects).

6. Hands-On: Formalizing ABC Bank's Access Model

  • Cards-Payments-Engineers Team (Priya, Ravi): Execute role on all non-production Templates directly; Execute role on approved production Templates directly — never Admin, and never granted at the Organization level (least privilege).
  • Cards-Payments-Approvers Team (Ravi, senior members): Additionally granted the Approve role, but only on the specific Approval Nodes inside relevant Workflows — set up properly in Project 20.
  • Cards-Payments-Admins Team (a small group): Admin role granted at the Organization level, since they're trusted to manage every Credential/Project/Template within their own business unit's boundary.
  • Internal Audit (individual Auditor-type Users, not a Team role grant at all): the platform-wide Auditor user type from Project 04 already gives read-only visibility everywhere — no additional RBAC grant needed.
  • Document this exact mapping in a simple table and hand it to the audit team ahead of their review — this is the "access matrix" they asked for.
Common mistakeGranting Admin at the Organization level "to save time" instead of the narrower object-level grant that was actually needed. This is the single most common over-privileging mistake auditors flag — always grant the least broad role that gets the job done.

7. LDAP-Backed Team Membership

ABC Bank doesn't manually manage Team membership by hand forever — AAP can be configured to map an existing corporate LDAP/Active Directory group (e.g. CN=CardsPaymentsEngineers,OU=Groups) directly onto a Team. When HR adds someone to that AD group, they automatically become a Team member in AAP on their next login, inheriting whatever RBAC roles that Team already has — no manual AAP-side step required.

10. Interview Prep — Say This Out Loud

"Explain how RBAC works in AAP."

Every object — Organizations, Credentials, Projects, Inventories, Templates — supports role grants to a User or Team. Roles like Read, Execute, Admin, Use, and Approve define what can be done. Roles granted at a broader level, like an Organization, cascade down to everything inside it, while roles granted directly on one object only affect that object.

"What's the most common RBAC mistake you'd watch for in an audit?"

Over-granting — assigning Admin at the Organization level when a narrower, object-level Execute or Use role would have been sufficient. Least privilege means granting the smallest role that still gets the job done.

11. Wrap-Up

Key Learnings

  • Roles (Read, Execute, Admin, Use, Approve) are granted per object, to a User or Team.
  • Broader grants (Organization-level) cascade down; object-level grants stay narrow.
  • LDAP-backed Team membership removes manual AAP-side onboarding steps.
