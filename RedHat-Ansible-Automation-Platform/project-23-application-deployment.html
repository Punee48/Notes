Application Deployment

Filling in the "Cards - Deploy Application Build" node we've referenced since Project 13 with a real, safe rolling deployment.

1. The Production Story

Day 23 at ABC Bank. Since Project 13, our Deployment Pipeline workflow has referenced a "Cards - Deploy Application Build" Job Template — but we never actually built it; it was a placeholder. Today the Release team hands us the real requirement: deploy a new application build across all 42 Cards application servers, but never all 42 at once — if a bad build goes out, it should only ever affect a small batch before the deployment automatically stops.

2. What "Deployment" Really Means Here

At its core, deploying this application means: stop the running service, replace the application artifact with the new version, update its configuration file with environment-specific values, and start it back up — then verify it's actually healthy before moving to the next batch of servers. The risk isn't any single step; it's doing this across 42 servers with no safety net if something goes wrong midway.

3. Our Rolling Deployment Strategy

graph LR B1[Batch 1
5 servers] --> Check1{Healthy?} Check1 -->|Yes| B2[Batch 2
5 servers] Check1 -->|No| Stop[Deployment halts
remaining servers untouched] B2 --> Check2{Healthy?} Check2 -->|Yes| More[... continues in batches of 5] Check2 -->|No| Stop

This is called a rolling deployment — updating a small batch, confirming health, then proceeding. It trades a bit of speed for a huge amount of safety: a bad build is caught after 5 servers, not 42.

4. The Full Deployment Playbook

---
# File: playbooks/deploy_cards_app.yml
- name: Rolling Deployment - Cards Application
  hosts: cards_app_tier                    # Group built in Project 11
  become: yes
  serial: "5"                          # Process only 5 hosts at a time — the core of our rolling strategy
  max_fail_percentage: 0               # If even ONE host in a batch fails, stop before starting the next batch

  vars:
    build_version: "{{ app_version }}"    # Comes from a Survey question (Project 18 pattern) — which version to deploy

  tasks:
    - name: Stop the Cards application service
      ansible.builtin.systemd:
        name: cardsapp
        state: stopped

    - name: Deploy the new application artifact
      ansible.builtin.get_url:                # Downloads the build artifact from our internal artifact repository
        url: "https://artifacts.abcbank.internal/cardsapp/{{ build_version }}/cardsapp.jar"
        dest: /opt/cardsapp/cardsapp.jar
        mode: '0750'
        owner: cardsapp
        backup: yes                    # Ansible automatically keeps a timestamped copy of the file it replaces

    - name: Update application configuration from template
      ansible.builtin.template:               # Renders a Jinja2 template file, substituting variables — not a plain copy
        src: templates/application.yml.j2
        dest: /opt/cardsapp/config/application.yml
        owner: cardsapp
        mode: '0640'

    - name: Start the Cards application service
      ansible.builtin.systemd:
        name: cardsapp
        state: started

    - name: Wait for the application health endpoint to respond
      ansible.builtin.uri:                     # Polls an HTTP endpoint until it returns a healthy response
        url: http://localhost:8080/health
        status_code: 200
      register: health_check
      retries: 6                          # Try up to 6 times...
      delay: 10                           # ...waiting 10 seconds between each try (up to 1 minute total)
      until: health_check.status == 200

5. serial and max_fail_percentage Explained

KeywordWhat it controls
serial: "5"Instead of running every task against all 42 hosts simultaneously, Ansible processes them in batches of 5, running the entire play to completion on one batch before starting the next.
max_fail_percentage: 0Zero tolerance — if even one host in the current batch fails any task, Ansible stops before touching the next batch, leaving the remaining 37 (in our example) untouched and still on the old version.
Production tipSome teams set serial as a list, like serial: [2, 5, 10] — deploy to 2 first (a canary batch), then 5, then 10, growing confidence with each successful batch. ABC Bank keeps it simple with a flat 5 for this application, but the list form is worth knowing for higher-risk deployments.

7. Rollback — What Happens If a Batch Fails

Because we set backup: yes on the artifact deployment task, every replaced cardsapp.jar leaves a timestamped copy behind on that server. If Batch 1 fails its health check, the remaining 37 servers are simply never touched — they're still running the previous, known-good version. Rolling back the 5 affected servers means re-running a simple "restore from backup" playbook against just that batch, not the whole estate. We'll build a formal rollback playbook when we cover Production Release fully in Project 26.

10. Interview Prep — Say This Out Loud

"How would you design a safe rolling deployment in Ansible?"

Use the serial keyword to process hosts in small batches rather than all at once, set max_fail_percentage to control tolerance for failures within a batch, and add a genuine post-deployment health check with retries before considering a batch successful — so a bad build is caught early instead of hitting the whole fleet.

"What's the difference between the copy and template modules?"

copy transfers a file as-is. template renders a Jinja2 template file first, substituting variables — used here so the same config file can generate different content per environment or version without maintaining separate static files.

11. Wrap-Up

Key Learnings

  • serial + max_fail_percentage together implement a safe rolling deployment.
  • A real health check with retries, not just "service started," is what actually confirms deployment success.
  • backup: yes on file changes gives a lightweight rollback path for free.
