Groups

Ending the copy-paste of the same host variable 42 times — and finally letting one playbook target "all Linux servers" in a single line.

1. The Production Story

Day 11 at ABC Bank. Yesterday we typed os_family: RedHat onto all 42 Linux hosts, one at a time. Priya points out — fairly — that if the bank ever moves to a different Linux distribution, we'd have to edit 42 hosts individually. Ravi adds a second problem: our upcoming health-check playbook needs to target "every Linux application server," but right now there's no way to say that in one line — we'd have to list all 42 hostnames by hand inside the playbook, which nobody wants to maintain.

Today we fix both problems with Groups — a way to tag hosts together and attach shared variables once, at the group level, instead of the host level.

2. Why Groups Solve Yesterday's Repetition

A Group is simply a named collection of Hosts, which can itself carry Group Variables that every member host inherits automatically. Instead of setting os_family: RedHat on 42 separate Host objects, we set it once on a Group called linux_servers, and every current and future member of that Group picks it up for free.

3. The Groups Screen

Where: inside an Inventory — Resources → Inventories → Cards-Payments-Servers → Groups tab. Who uses it: Automation Admins, when structuring an Inventory. What you see: a tree of Groups, each expandable to show member Hosts and, if nested, child Groups.

Groups can contain other Groups, not just Hosts directly. This lets us build a hierarchy that mirrors how the business actually thinks about its servers.

7. Variable Precedence — A Critical Detail

What happens if a Host Variable and a Group Variable disagree? Ansible has a defined precedence order, and getting this wrong is a classic source of "why did it use the wrong value" bugs.

Precedence (lowest to highest, simplified)Example
1. Group Variables (parent group)cards_payments_all sets patch_window: standard
2. Group Variables (child group)cards_db_tier overrides with patch_window: extended
3. Host Variables (most specific, wins)One specific database host overrides again with patch_window: manual-only
Common mistakeSetting a variable at the Host level "just to be safe" out of habit, when it really belongs at the Group level. This silently blocks the Group Variable from ever taking effect for that host, and six months later nobody remembers why that one server behaves differently.

9. Troubleshooting

SymptomLikely Cause

Nested group structure causes a host to be targeted twice unexpectedlyA host belongs to two Groups both referenced separately in a play — usually harmless but worth being intentional about

10. Interview Prep — Say This Out Loud

"Why use Groups instead of setting variables directly on each Host?"

Groups let you set a shared variable once for every member instead of repeating it on every individual host, and they let a playbook target a whole category of servers — like "all Linux servers" — in one line, instead of maintaining a hardcoded hostname list.

"If a Group Variable and a Host Variable conflict, which wins?"

The more specific one wins — Host Variables override Group Variables, and a child Group's variables override its parent Group's, following Ansible's standard variable precedence.

11. Wrap-Up

Key Learnings

  • Groups can nest, mirroring how the business actually organizes servers.
  • Host Variables always beat Group Variables when they conflict — the most specific setting wins.
