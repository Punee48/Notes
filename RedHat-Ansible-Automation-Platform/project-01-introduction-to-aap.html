Introduction to Red Hat Ansible Automation Platform

A Knowledge Transfer session, taught the way a Senior Automation Architect would teach a new joiner on a banking production support desk.

1. The Production Story

We have joined ABC Bank as a DevOps Engineer.

The Infrastructure Automation Team manages more than 3,000 Linux and Windows servers that run core banking, payments, and internet banking applications.

Every day, engineers get tickets asking them to patch servers, run health checks, validate SSL certificates, restart middleware, create OS users, clean up logs, and verify compliance. Until now, every one of these tickets was closed by an engineer manually typing ansible-playbook commands from a jump server, using a personal SSH key and a text file inventory saved on their own laptop.

The bank has decided this can no longer continue, and has purchased Red Hat Ansible Automation Platform (AAP) so that every automation task is centrally managed, logged, and controlled.

Our Team Lead has given us one task for this sprint: "Learn AAP from the ground up, and by the end of the month I want you running production tickets through the platform, not from your own terminal."

Today is Day 1. We are not touching a playbook yet — first we need to understand what AAP actually is, and why the bank chose it over what we were already doing.

2. Business Case — Why This Project Exists

QuestionAnswer in the ABC Bank Context
Current manual processEngineers SSH into a jump box, pull playbooks from Git manually, keep SSH keys on their own laptops, and run ansible-playbook by hand for every ticket.
Problems with this processNo central log of who ran what; SSH keys and vault passwords sit on individual laptops; no approval step before a playbook touches production; if the engineer resigns, nobody knows what access they had.
Risk to the bankAn unreviewed playbook could restart the wrong middleware on a live payments server. In a BFSI audit, "who ran this change and who approved it" must be answerable in seconds — today it is not.
Business impactRegulatory audit findings, delayed incident response (engineers on leave = tribal knowledge lost), and inconsistent execution (two engineers may run the same playbook slightly differently).
Why automation is requiredVolume (3,000+ servers) makes manual, laptop-based execution unsustainable and unauditable.
Why AAP specificallyIt centralizes credentials (never exposed to the engineer), enforces Role-Based Access Control, keeps a permanent log of every job, supports approval gates for production changes, and is the automation layer Red Hat supports under the bank's existing enterprise support contract.
Alternatives consideredJenkins-only pipelines; open-source AWX; bash/cron scripts wrapped around ansible-playbook.
Why alternatives were rejectedJenkins has no native inventory/credential model for infrastructure and would need heavy custom plugins. AWX has no enterprise support contract, which BFSI compliance will not accept for production. Cron/bash scripts have no RBAC, no audit trail, and no approval workflow at all.
Solution design (short version)All playbooks live in Git → AAP Controller pulls them → engineers launch pre-built Job Templates (they never see raw credentials) → every run is logged and, for production, gated behind an approval step.

3. So, What Is AAP?

Ansible Automation Platform is not a replacement for Ansible. Ansible itself — the open-source engine that reads a YAML playbook and connects over SSH/WinRM to run tasks — stays exactly the same underneath. AAP is the control layer that sits on top of that engine so an entire bank can use it safely as a team, instead of one engineer running it from a laptop.

Think of plain Ansible as a car engine. AAP is the car built around that engine — the dashboard, the locked ignition that only authorized drivers can start, the black-box recorder that logs every trip, and the central garage that all the cars are checked out from.

4. The Core Building Blocks (High Level)

We will go deep into each of these in later projects. For today, just learn what each piece is for, so the vocabulary makes sense.

Controller

The main web application and API. This is what we log into. It stores Projects, Inventories, Credentials, Templates, and every Job's history.

Execution Environment

A container image that carries Ansible plus every collection ABC Bank needs (Linux, Windows, VMware, network modules). Every job runs inside one of these, so results are identical no matter which engineer clicked Launch.

Automation Hub

A private, curated store of trusted Ansible Collections and roles that ABC Bank's security team has approved — nobody pulls random roles from the public internet into production.

Automation Mesh

A network of execution nodes that lets AAP reach servers across different data centers and network zones (e.g. DMZ vs core banking zone) without opening broad firewall rules.

Project

A pointer to a Git repository containing our playbooks. AAP syncs it, so the platform always runs the version of code that is actually in Git — never a copy sitting on someone's laptop.

Job Template

A saved, reusable combination of "this playbook + this inventory + this credential." This is the object an engineer actually clicks to run something.

6. Hands-On Lab — Your First Job Template

Goal for today: run one safe, read-only job (a connectivity check) through AAP, so you see the full loop end to end before we learn the theory behind each screen.

Prerequisites

  • Your Team Lead has created your AAP login and added you to the ABC-Bank-Infra Organization.
  • A demo Project called demo-linux-healthcheck already exists, pointing at a Git repo with one playbook.
  • A demo Inventory called demo-linux-servers already exists with 2 test hosts.

Step-by-step: Launching an existing Job Template

  • Click Resources → Templates. This opens the list of every Job Template you are allowed to see.
  • Find "Demo - Linux Health Check" and click on its name (not the rocket icon yet) — this opens the template details so you can see what it is made of before running it: which Project, which Inventory, which Credential.
  • Click the rocket-shaped Launch icon on the right of that row.
  • If the template has a Survey (a short form), fill it in. Our demo template has none, so it goes straight to execution.
  • You land on the Job Output screen automatically. Watch the log stream — this is Ansible running live, exactly like it would from a terminal, except now every line is being saved permanently.
  • When it finishes, the status badge turns green (Successful). Click Details on the same screen to see which template, which inventory, and which user (you) ran this job — this is the audit trail the bank needed.

The playbook behind this template

This is the actual playbook the template above is running. Every line is commented so you know exactly what it is doing — get used to reading playbooks this way from day one.

---
# File: healthcheck.yml — a safe, read-only playbook used to prove connectivity
- name: Linux Health Check          # Name shown as the Play in AAP's Job Output
  hosts: linux_servers                # Target the "linux_servers" group defined in the AAP Inventory
  gather_facts: yes                    # Ask Ansible to collect OS, memory, and disk info before running tasks

  tasks:
    - name: Check disk space          # A human-readable label for this task, shown in the log
      ansible.builtin.command: df -h    # Runs the Linux "df -h" command on the remote server
      register: disk_output              # Save the command's output into a variable named disk_output

    - name: Show disk space result
      ansible.builtin.debug:              # The debug module simply prints something to the job log
        var: disk_output.stdout_lines    # Print the disk_output variable we captured above

    - name: Check server uptime
      ansible.builtin.command: uptime      # Runs the Linux "uptime" command on the remote server
      register: uptime_output

    - name: Show uptime result
      ansible.builtin.debug:
        var: uptime_output.stdout_lines
Line-by-line explanation (click to expand)
LineMeaning
hosts: linux_serversTells Ansible which group of machines to run against. In AAP this group name must exist inside the Inventory we selected on the Job Template — it is not something typed on the command line anymore.
gather_facts: yesRuns an implicit first step that collects details like OS version and memory. Costs a few seconds; we keep it on for health checks because later tasks may depend on this data.
ansible.builtin.commandThe safest module for running a plain shell command with no side effects. We avoid shell here since we don't need pipes or redirection, and command is slightly safer against injection.
registerCaptures the module's result (stdout, return code, etc.) into a named variable so we can use it in a later task.
ansible.builtin.debugPurely for visibility — prints a variable into the job log. It changes nothing on the server, which is why this whole playbook is safe to run in production without an approval gate.
Common mistakeNew engineers often use shell for everything out of habit. Reserve shell only for when you truly need shell features like pipes (|) or redirection (>); otherwise command is safer and is what most banking security reviews expect to see.

7. What Actually Happens When You Click Launch

This is the part most new engineers skip — but understanding it is what lets you troubleshoot later instead of panicking. When you clicked the rocket icon above, this sequence ran in the background:

sequenceDiagram participant You participant Controller participant EE as Execution Environment participant Node as Managed Server You->>Controller: Click Launch Controller->>Controller: Check your RBAC permission on this Template Controller->>Controller: Load Inventory (linux_servers group) Controller->>Controller: Decrypt stored Credential (SSH key) in memory only Controller->>EE: Start a container with the playbook + Ansible EE->>Node: Establish SSH connection Node-->>EE: Gather facts EE->>Node: Run each task in order Node-->>EE: Return results EE-->>Controller: Stream stdout back live Controller-->>You: Job Output updates in real time Controller->>Controller: Save final status + full log permanently
The most important detail for securityAt no point did the SSH key touch your screen or your laptop. It was decrypted only inside the Execution Environment's memory for the duration of the job, then discarded. This is the single biggest reason BFSI auditors approve AAP.

Habit to build nowAlways read the Job Output top to bottom before asking for help — the exact task that failed, and the error right under it, usually tells you 90% of the story. We build a full troubleshooting playbook of our own in Project 28.

10. Interview Prep — Say This Out Loud, Not Just Read It

"What is Ansible Automation Platform, in your own words?"

Something like: "Plain Ansible is a great automation engine, but it doesn't scale to a team on its own — no shared credential store, no audit trail, no approvals. AAP wraps that same engine with a Controller, centralized credentials, RBAC, and Execution Environments, so a whole bank can automate safely instead of one engineer running it from a laptop."

"Walk me through what happens when someone clicks Launch on a Job Template."

Talk through the sequence diagram above in your own words: permission check → inventory loaded → credential decrypted in memory → Execution Environment spins up → SSH to the host → tasks run → output streamed back → result logged permanently.

"Why didn't ABC Bank just use plain open-source AWX?"

AWX has no enterprise support contract or SLA from Red Hat, which most BFSI compliance and vendor-risk teams will not accept for a system that can change production servers. AAP gives the same engine with support, certified content, and a defined upgrade path.

11. Wrap-Up

Key Learnings

  • AAP is a control layer over plain Ansible — Ansible itself doesn't change.
  • Controller, Execution Environment, Project, Inventory, Credential, Job Template are the six words you now need to use correctly.
  • Credentials are never exposed to the person running the job.

Resume Point

"Onboarded onto Red Hat Ansible Automation Platform; executed governed Job Templates against Linux infrastructure within a BFSI production support environment."
