Best Practices

Every rule we've learned across 28 projects, distilled into one reference we'll actually reach for.

1. The Production Story

Day 29 at ABC Bank. Two new engineers join the Cards & Payments automation team next month. Our Team Lead asks us to prepare the one document that captures everything we've learned — not a 28-chapter retelling, but the checklist a new engineer should genuinely keep open in a second tab during their first month.

2. Access & Governance Checklist

  • Grant the narrowest RBAC role that gets the job done — Execute over Admin, object-level over Organization-level (Project 19)
  • Every Organization mirrors a real business/audit boundary — never create one "to be safe"; never merge two that need separation (Project 03)
  • Attach roles to Teams, not individual Users, so onboarding/offboarding is a single Team membership change (Project 05, 19)
  • Deactivate, never delete, a User with job history (Project 04)
  • Production Approval Nodes always have a timeout — never leave it infinite (Project 20)

3. Content & Playbook Checklist

  • Every task uses an idempotent module (state: present/absent) — never a raw shell command for something a dedicated module already handles (Project 21)
  • Every YAML line has an inline comment explaining what and why, not just what (all projects)
  • Secrets always come from a Credential, never hardcoded in a playbook or committed to Git (Project 06, 07)
  • Sudoers/privilege changes are always scoped to one command and validated with visudo (Project 21)
  • Pin Execution Environment image tags to a specific version — never "latest" (Project 16)
  • Promote repeated task sequences into a Role once they're used in a second playbook (Project 21)

4. Release & Deployment Checklist

  • Production Projects pin to an immutable Git tag, never a branch, with Update Revision on Launch disabled (Project 08, 26)
  • Every deployment uses serial + max_fail_percentage: 0 to cap blast radius (Project 23)
  • Every deployment verifies success with a genuine health check (endpoint/service), never just "task completed" (Project 12, 25)
  • Patch waves always include a soak period between non-critical and critical batches (Project 24)
  • Production changes always route through an Approval Node tied to RBAC's Approve role (Project 20)

5. Operations Checklist

  • Schedules always have an explicitly set Time Zone — never trust the default (Project 14)
  • Notifications fire on Failure by default; add Success only when routine confirmation is genuinely needed, to avoid alert fatigue (Project 15)
  • Compliance scans never remediate inline — findings are reviewed by a human before any fix is applied (Project 27)
  • Diagnose failures layer by layer (Platform → Access → Content → Connectivity → Execution) before assuming it's a bug (Project 28)

6. Five Anti-Patterns to Never Repeat

Anti-PatternWhy It's Dangerous
Granting Organization-level Admin "to save time"Massively over-privileges a Team beyond what any single task needed (Project 19)
Leaving "Update Revision on Launch" enabled in productionA merge to main can silently change what a scheduled job runs at 2 AM (Project 08)
Using raw shell/command instead of a dedicated moduleBreaks idempotency — safe to run once, unsafe to run twice (Project 21)
Auto-remediating inside a compliance scanTurns a read-only audit tool into an unreviewed production change (Project 27)
Infinite Approval Node timeoutsA single absent approver can silently stall a release indefinitely (Project 20)

7. The One-Page New-Joiner Cheat Sheet

Give this to Day-1 new joiners verbatim 1) Organizations separate business units — never cross that boundary. 2) Credentials are write-only forever — you'll never see a secret again after saving it. 3) A Job Template only works with the right EE selected — "module not found" almost always means the wrong EE. 4) Every production change needs an Approval Node with a sane timeout. 5) When something fails, check Platform → Access → Content → Connectivity → Execution, in that order, before assuming it's a playbook bug.

8. Interview Prep — Rapid Fire

QuestionOne-Line Answer
What's the biggest RBAC mistake to avoid?Over-granting Admin at the Organization level instead of narrow, object-level roles.
Why pin production to a Git tag, not a branch?Tags are immutable — guarantees exactly the reviewed code deploys, with zero ambiguity.
What makes a playbook safely re-runnable?Idempotent modules (state: present/absent), not raw shell commands.
Why separate compliance scanning from remediation?A scan should never silently change production; fixes need human review and often an Approval gate.
What's the first thing to check when a job fails?Platform health, before assuming it's a playbook or connectivity bug.
