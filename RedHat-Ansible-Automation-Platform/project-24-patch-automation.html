Patch Automation

Turning the monthly patch cycle — historically ABC Bank's single most dreaded manual weekend — into a governed, waved rollout.

1. The Production Story

Day 24 at ABC Bank. Every month, security patching used to mean an entire weekend of engineers manually running yum update across every server in a fixed order, hoping nothing broke. Our Team Lead reminds us this is precisely the highest-risk manual process we've been asked to eliminate since Project 01's business case. Today we finally build it properly — using the patch_group host variable we set all the way back in Project 10.

2. Why Patch Automation Is Its Own Discipline

Patching isn't just "install updates" — it needs waving (not every server at once), reboot handling (some patches require a restart, some don't), and pre/post validation (confirm the server is actually healthy before and after). Get any of these wrong and a routine monthly patch cycle becomes an outage.

3. Patch Waves — Using the patch_group Variable

Recall from Project 10: every host has a patch_group variable (wave-1, wave-2, etc.). ABC Bank patches non-critical servers in Wave 1 first, waits 48 hours to confirm no issues, then patches critical Wave 2 servers — the exact same "prove it's safe on a small batch first" philosophy as Project 23's rolling deployment, just applied over days instead of minutes.

4. The Full Patch Automation Playbook

---
# File: playbooks/patch_linux_servers.yml
- name: Monthly Security Patching
  hosts: "{{ patch_wave }}"              # Survey-driven (Project 18) — e.g. "wave-1" or "wave-2", not hardcoded
  become: yes
  serial: "10%"                     # Percentage form of serial — patch 10% of the wave at a time
  max_fail_percentage: 0

  tasks:
    - name: Record currently installed kernel version (for post-patch comparison)
      ansible.builtin.command: uname -r
      register: kernel_before
      changed_when: false

    - name: Apply all available security patches
      ansible.builtin.dnf:                     # dnf module — idempotent package management for RHEL9
        name: "*"
        state: latest
        security: true                  # Restrict to security-classified updates only, not every package
      register: patch_result

    - name: Check if a reboot is required
      ansible.builtin.stat:
        path: /var/run/reboot-required     # Marker file the OS creates when a patch needs a restart to take effect
      register: reboot_marker

    - name: Reboot the server if required
      ansible.builtin.reboot:                 # Dedicated reboot module — waits for the host to come back online automatically
        reboot_timeout: 600
      when: reboot_marker.stat.exists       # Only reboot hosts that actually need it — not the whole batch unconditionally

    - name: Confirm server is reachable and healthy after patching
      ansible.builtin.ping:

    - name: Report kernel version change
      ansible.builtin.command: uname -r
      register: kernel_after
      changed_when: false

    - name: Show before/after kernel comparison
      ansible.builtin.debug:
        msg: "Kernel before: {{ kernel_before.stdout }}, after: {{ kernel_after.stdout }}"

5. Reboot Handling Explained

Design ChoiceWhy
Check for a reboot marker file firstNot every patch needs a reboot — unconditionally rebooting every server wastes a maintenance window and causes unnecessary downtime
Use the dedicated reboot moduleHandles the tricky part correctly: waiting for the host to actually go down, then come back up and become SSH-reachable again, before Ansible moves on — a raw shell reboot command can't do this reliably
serial: "10%"Even within one wave, we don't reboot everything simultaneously — losing 10% of a wave's capacity briefly is manageable; losing 100% at once is not

6. Hands-On: Scheduling the Monthly Patch Cycle

  • Build the Job Template: Cards - Monthly Patching, with a Survey (Project 18) for patch_wave, single-choice dropdown with options wave-1 and wave-2.
  • Create a Schedule (Project 14) for the second Saturday of each month, 22:00 IST, pre-filling patch_wave: wave-1.
  • Create a second Schedule two days later, pre-filling patch_wave: wave-2 — giving the 48-hour soak period described above.
  • Attach a Notification (Project 15) on Failure to alert the team immediately if any host in a wave fails to come back healthy.

7. Proving Compliance After the Fact

Direct answer to a recurring audit question"Which servers were patched, when, and with what result?" is answered entirely by Job history — every scheduled patching run is logged exactly like a manual one (Project 14's core benefit), with the before/after kernel comparison we deliberately built into the playbook giving concrete before/after evidence, not just a "job succeeded" checkbox.

10. Interview Prep — Say This Out Loud

"How would you design a safe, waved patch automation process?"

Group servers by criticality using a host or group variable, patch the least critical wave first, allow a soak period to catch issues, then proceed to more critical waves — combined with serial batching and conditional reboot handling so only hosts that actually need a restart get one.

"Why use the dedicated reboot module instead of a shell reboot command?"

The reboot module correctly waits for the host to go down and come back up, re-establishing connectivity before Ansible proceeds — a raw shell command can't track that, and Ansible would either error out or falsely report success while the host is still restarting.

11. Wrap-Up

Key Learnings

  • Waved patching (using the patch_group variable from Project 10) with a soak period catches bad patches before they hit critical servers.
  • Only reboot hosts that actually need it, using a reboot marker check.
  • Before/after evidence (like kernel version) turns Job history into genuine compliance proof.
