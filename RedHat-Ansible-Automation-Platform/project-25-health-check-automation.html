Health Check Automation

Growing Project 01's simple disk-space check into a real, multi-dimensional health framework reused everywhere in this track.

1. The Production Story

Day 25 at ABC Bank. Our health check has quietly been doing one thing this whole time — checking disk space. But every Workflow we've built since Project 13 relies on "the pre-check passed" as its safety gate. Our Team Lead points out the gap: "If the deployment pipeline's pre-check only looks at disk space, and the actual outage was caused by high CPU or a hung process, our safety gate wouldn't have caught it at all." Today we build a real, multi-dimensional health check and make it the standard used everywhere in this track from now on.

2. From "One Check" to a Real Health Framework

A production-grade health check validates several independent dimensions of server health, reports a clear pass/fail per dimension, and an overall pass/fail the Workflow can branch on — exactly the "real pass/fail signal" principle we established back in Project 12.

3. The Five Health Dimensions We'll Check

DimensionWhy It Matters
Disk spaceA full disk can silently crash logging, temp files, or the application itself.
Memory usageHigh memory pressure often precedes an application crash or severe slowdown.
CPU loadSustained high load indicates the server can't safely take on more (e.g. deployment) work.
Critical service statusThe application itself must actually be running, not just the OS being reachable.
Application health endpointThe deepest check — confirms the application can actually serve a request, not just that its process exists.

4. The Full Multi-Dimensional Health Check Playbook

---
# File: playbooks/full_healthcheck.yml
- name: Cards Application - Full Health Check
  hosts: cards_app_tier
  gather_facts: yes                    # We need ansible_facts for memory/CPU checks below

  tasks:
    - name: Check disk space on root partition
      ansible.builtin.shell: df --output=pcent / | tail -1 | tr -d '% '
      register: disk_pct
      changed_when: false

    - name: Check available memory percentage
      ansible.builtin.set_fact:
        mem_available_pct: "{{ (ansible_memfree_mb / ansible_memtotal_mb * 100) | round(1) }}"  # Uses facts gathered automatically at play start

    - name: Check 1-minute CPU load average
      ansible.builtin.shell: cat /proc/loadavg | awk '{print $1}'
      register: cpu_load
      changed_when: false

    - name: Check the Cards application service is active
      ansible.builtin.systemd:
        name: cardsapp
      register: svc_status

    - name: Check the application health endpoint
      ansible.builtin.uri:
        url: http://localhost:8080/health
        status_code: 200
      register: endpoint_check
      ignore_errors: true              # Don't crash the play here — we want to evaluate and report ALL five dimensions, not stop at the first failure

    - name: Evaluate overall health and fail clearly if anything is wrong
      ansible.builtin.assert:
        that:
          - disk_pct.stdout | int < 90
          - mem_available_pct | float > 10
          - cpu_load.stdout | float < 4.0
          - svc_status.status.ActiveState == 'active'
          - endpoint_check.status == 200
        fail_msg: "Health check FAILED — disk: {{ disk_pct.stdout }}%, mem free: {{ mem_available_pct }}%, load: {{ cpu_load.stdout }}, service: {{ svc_status.status.ActiveState }}, endpoint: {{ endpoint_check.status | default('unreachable') }}"
        success_msg: "All five health dimensions passed"

5. set_stats — Feeding Results Back to the Workflow

Recall the "Set Stats" node type mentioned in Project 13. Adding a set_stats task lets this playbook pass a summary value up to the Workflow level, which a later node (like the Approval Node's description in Project 20) can then display to a human, rather than making them dig through raw Job Output.

- name: Publish a summary stat for the Workflow
  ansible.builtin.set_stats:
    data:
      health_summary: "disk={{ disk_pct.stdout }}% mem_free={{ mem_available_pct }}% load={{ cpu_load.stdout }}"

6. Hands-On: Building a Reusable Health Check Workflow

  • Commit full_healthcheck.yml to Cards-Payments-Playbooks, sync the Project.
  • Update the existing Cards - Linux Health Check Job Template (Project 12) to point at this new, richer playbook instead of the original disk-only version — everything downstream (the Schedule from Project 14, the Notification from Project 15, and the Deployment Pipeline's pre-check node from Project 13) automatically benefits without any of those objects needing to change.
  • Relaunch and confirm the Job Output now clearly reports all five dimensions in the assert's success or failure message.
Why this upgrade was safeBecause we always referenced this Job Template by name from Workflows, Schedules, and Notifications — never hardcoded the playbook file elsewhere — swapping its underlying playbook for a better one required touching only one place. This is the payoff of the "configure once, reuse everywhere" pattern we've followed since Project 06.

8. Troubleshooting

SymptomLikely Cause
Assert fails but the fail_msg doesn't show which dimensionCheck the raw individual task results in Job Output — the assert message reports all values, but reading it carefully is still necessary
Endpoint check task crashes the whole play immediatelyignore_errors: true missing — without it, a single unreachable endpoint stops evaluation of the remaining dimensions
Memory percentage calculation looks wrongFacts weren't gathered (gather_facts: yes missing), so ansible_memfree_mb/ansible_memtotal_mb are undefined

9. Interview Prep — Say This Out Loud

"What would you check in a production-grade health check playbook, beyond just disk space?"

At minimum disk, memory, CPU load, the critical service's actual running state, and a real application health endpoint — the endpoint check is the deepest signal, since a process can technically be "running" while the application itself is unresponsive.

"Why use ignore_errors on one task but assert everything together at the end?"

So a single failing dimension (like an unreachable endpoint) doesn't stop the play from evaluating the other dimensions — the final assert then gives one clear, complete pass/fail signal covering everything, rather than an incomplete report from stopping early.

10. Wrap-Up

Key Learnings

  • A real health check validates several independent dimensions, not just one.
  • ignore_errors on individual checks plus one final assert gives a complete report, not an early bail-out.
  • Referencing Job Templates by name everywhere (never hardcoding playbook files elsewhere) lets you upgrade a playbook once and every downstream Workflow/Schedule/Notification benefits automatically.
