Credentials

The object that finally lets Priya and Ravi's jobs actually reach a server — without either of them ever seeing a password or key.

1. The Production Story

Day 6 at ABC Bank. Priya asks a very reasonable question in the team stand-up: "If I'm going to run a playbook against our Cards servers, where do I paste in the SSH key?"

Our Team Lead's answer surprises her: "You don't. You will never see it, never type it, and never even know where it's stored. That's the whole point." Today we create the Credential object that makes this true — the SSH private key for the Cards & Payments servers gets uploaded once, by an Automation Admin, encrypted inside AAP's database, and from that point on every Job Template simply references it by name.

2. Why Credentials Are AAP's Crown Jewels

Go back to the Business Case in Project 01: the single biggest audit failure in ABC Bank's old manual process was SSH keys and vault passwords sitting on individual engineers' laptops. Credentials in AAP solve exactly this — a secret is entered once, encrypted at rest in the Controller's database, and from then on is only ever decrypted in-memory, inside the Execution Environment, for the duration of a single job. Nobody — not Priya, not Ravi, not even most Automation Admins — can retrieve the raw value again through the UI.

Common misconceptionPeople sometimes assume an admin can "view" a stored credential later to check it. They can't — the field only ever accepts new input; it never displays the existing secret back. If a key needs rotating, you upload a new one; you cannot read the old one out.

3. The Credentials Screen

Where: left nav, under Resources → Credentials. Who uses it: Automation Admins create and own them; regular engineers only ever select a Credential by name inside a Job Template — they never open this screen to view secrets. What you see: a list of Credentials, each tagged with its Type (Machine, Vault, SCM, Cloud, etc.) and Organization.

4. Common Credential Types We'll Use at ABC Bank

Machine

SSH key or username/password used to log into a Linux/Windows managed node to run the actual playbook tasks.

Source Control (SCM)

Credentials AAP uses to pull our playbooks from Git — covered fully when we build our first Project object in Project 08.

Vault

The password used to decrypt Ansible Vault-encrypted variables inside a playbook (e.g. a database password embedded in code). Covered in depth further down this page.

We'll meet more specialised types — Cloud (AWS/Azure), Network, and custom Credential Types — properly in Project 07.

6. Hands-On: Creating the Cards Linux Machine Credential

  • Click Resources → Credentials → Add.
  • Name: Cards-Payments-Linux-SSHKey
  • Organization: ABC-Bank-Cards-Payments
  • Credential Type: select Machine.
  • Username: svc_cards_ansible — the dedicated service account Infra created for automation, never a personal login.
  • SSH Private Key: paste the key contents (the Automation Admin does this once, from a secure vault export, not from their own laptop).
  • Privilege Escalation Method: sudo; Username: root.
  • Click Save. The Credential now exists. Nobody — including us — can view that key's contents again through the UI.
Production tipAlways use a dedicated service account (svc_cards_ansible), never an individual engineer's personal SSH key. If Priya leaves the bank, her personal key being disabled must never break automation — the service account is independent of any one person.

7. Vault Credentials — Protecting Secrets Inside Playbooks

Sometimes a playbook itself needs a secret — for example, a database password used inside a task. We never write that in plain text in Git. Instead, it's encrypted with ansible-vault before being committed, and a separate Vault Credential in AAP stores the password needed to decrypt it at runtime.

# group_vars/cards_db.yml — committed to Git in its encrypted form
$ANSIBLE_VAULT;1.1;AES256
63383439396462633...(unreadable ciphertext, safe to store in Git)

When a Job Template that references this vaulted file runs, AAP automatically supplies the Vault Credential's password to decrypt it in-memory, inside the Execution Environment — the plaintext database password is never written to disk and never shown in the Job Output log.

8. What Happens to a Credential at Runtime

sequenceDiagram participant Priya participant Controller participant EE as Execution Environment participant Node as Managed Server Priya->>Controller: Launch Job Template (selects nothing credential-related) Controller->>Controller: Look up attached Machine Credential Controller->>Controller: Decrypt SSH key in memory only Controller->>EE: Inject decrypted key into a short-lived, isolated file inside the container EE->>Node: SSH using that key EE->>EE: Discard key when job finishes; container destroyed Note over Priya: Priya never sees the key at any point

10. Troubleshooting

SymptomLikely Cause
Job fails at "Permission denied (publickey)"Wrong username on the Machine Credential, or the service account's public key isn't authorized on the target server
Job fails to decrypt a vaulted variable fileVault Credential not attached to the Job Template, or the vault ID doesn't match what encrypted the file
Task fails with a permissions error even though SSH succeededPrivilege Escalation method/username misconfigured — check sudo settings on the Credential

11. Interview Prep — Say This Out Loud

"How does AAP keep SSH keys secure compared to engineers running ansible-playbook manually?"

Keys are entered once by an admin into an encrypted, write-only Credential object. They're decrypted only in-memory inside a disposable Execution Environment for the duration of one job, then discarded — no engineer ever sees or handles the raw key, unlike a manual setup where keys sit on individual laptops.

"How would you protect a database password referenced inside a playbook?"

Encrypt the variable file with ansible-vault before committing to Git, and create a separate Vault Credential in AAP holding the decryption password, attached to the relevant Job Template — the plaintext value never appears in Git or in job logs.

12. Wrap-Up

Key Learnings

  • Credential fields are write-only — no one can read a stored secret back through the UI.
  • Always use a dedicated service account for Machine Credentials, never a personal login.
  • Vault Credentials decrypt vaulted playbook variables at runtime, in-memory only.

Resume Point

"Implemented encrypted, least-exposure credential management in Red Hat AAP for BFSI production automation, eliminating laptop-stored SSH keys."
