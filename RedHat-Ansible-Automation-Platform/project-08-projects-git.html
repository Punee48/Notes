Projects (Git Integration)

Finally connecting AAP to the actual playbook code — and guaranteeing the platform runs exactly what's in Git, nothing more.

1. The Production Story

Day 8 at ABC Bank. We have Users, a Team, and a Credential — but zero playbooks anywhere inside AAP. Priya asks where she should upload her playbook files once she's written one. Our Team Lead corrects the assumption immediately: "You never upload a playbook to AAP directly. You commit it to our Git repository like any other code change, with a pull request and a review. AAP only ever pulls from Git — it is never the source of truth itself."

Today we create AAP's Project object, pointing it at the Cards & Payments team's Git repository, so that whatever is merged to the main branch is exactly what runs in production — no exceptions, no local copies.

2. Why "Projects" Isn't a Vague Word Here

In AAP, a Project has one narrow, precise meaning: a pointer to a source-controlled location (almost always Git) containing playbooks, roles, and related files. AAP periodically or manually "syncs" this Project, which means it clones or pulls the repository onto local storage that Execution Environments can read from when a job runs.

Why not just upload files through the UI?Answer
No code reviewA file uploaded through a UI has no pull request, no peer review, no history — completely unacceptable for banking change control.
No version historyGit gives us exactly which commit is running, who wrote it, and the ability to roll back instantly.
No single source of truthUploaded files could silently drift from what's in Git, so nobody could trust the repository as the definitive record.

3. The Projects Screen

Where: left nav, under Resources → Projects. Who uses it: Automation Admins create/configure Projects; engineers only see the sync status when troubleshooting a Job Template that uses one. What you see: a list of Projects, each with a status badge (Successful, Failed, Running) showing the last sync result.

5. Git Repository Structure We'll Use

graph TB Repo[cards-payments-playbooks repo] Repo --> A[playbooks/] Repo --> B[roles/] Repo --> C[group_vars/] Repo --> D[host_vars/] Repo --> E[inventories/ optional, most inventories live in AAP itself] Repo --> F[requirements.yml Collections this repo depends on]

This mirrors a completely normal Ansible project layout — AAP adds nothing repo-side. That's intentional: the same repo could technically still be run with plain ansible-playbook from a laptop in an emergency, though at ABC Bank that path is disabled by policy outside AAP.

6. Hands-On: Connecting the Cards & Payments Repo

  • First, an Automation Admin creates a Source Control Credential: Resources → Credentials → Add, Type = Source Control, using a Git deploy key with read-only access to the repo — never a personal developer token.
  • Click Resources → Projects → Add.
  • Name: Cards-Payments-Playbooks
  • Organization: ABC-Bank-Cards-Payments
  • Source Control Type: Git
  • Source Control URL: the repo's SSH clone URL.
  • Source Control Branch: main
  • Source Control Credential: select the deploy-key Credential created above.
  • Click Save. AAP performs an initial sync automatically — watch the status badge turn green.
Production tipAlways use a read-only deploy key scoped to this one repository, not a personal GitHub token. If Priya's personal token expires or is revoked when she changes teams, the Project's sync must keep working regardless.

7. What Happens During a Sync

sequenceDiagram participant Controller participant Git as Git Repository participant Storage as AAP Local Project Storage Controller->>Git: Authenticate using SCM Credential Git-->>Controller: Confirm access Controller->>Git: Pull latest commit on configured branch Git-->>Controller: Return files Controller->>Storage: Write files to versioned local Project storage Controller->>Controller: Record exact commit hash synced Note over Controller: Job Templates using this Project now reference this commit

Notice the last step — AAP records the exact commit hash. This is a direct answer to an audit question we'll get eventually: "which version of the playbook actually ran on this date?" The Job's details always show the commit hash, not just the branch name.

8. SCM Update Options Explained

OptionNon-Production SettingProduction Setting
Update Revision on LaunchEnabled — always test against the very latest commit.Disabled — production only runs a commit that was explicitly synced and reviewed, not whatever happens to be newest at 2 AM.
Source Control Branchmain (or a feature branch for testing)Often pinned to a release tag, e.g. v2.4.0, for controlled releases (we'll formalize this in Project 26).
Common mistakeLeaving "Update Revision on Launch" enabled for a production Project. This means a merge to main at 1:59 AM could silently change what a 2:00 AM scheduled production job runs — completely bypassing change control. Production Projects should sync deliberately, not automatically on every launch.

11. Interview Prep — Say This Out Loud

"Why does AAP integrate with Git instead of letting engineers upload playbooks directly?"

Git gives peer review, version history, and a single source of truth. AAP's Project object just syncs from Git and records the exact commit hash that ran, so every job is traceable to a specific reviewed change — uploading files directly would bypass all of that.

"Why would you disable 'Update Revision on Launch' for a production Project?"

To stop a merge to the main branch from silently changing what a production job runs at launch time — production should only ever run a commit that was deliberately synced and reviewed, not whatever is newest at that instant.

12. Wrap-Up

Key Learnings

  • A Project is only a pointer to Git — AAP is never the source of truth for playbook code.
  • Every sync records the exact commit hash that ran, which is the audit answer to "what version executed?"
  • Disable auto-update-on-launch for production to keep change control intact.

Resume Point

"Integrated Red Hat AAP with Git version control (SCM-backed Projects), enforcing commit-level traceability for BFSI production automation."
