Hosts

Populating our empty Inventory shell with the actual Cards & Payments servers.

1. The Production Story

Day 10 at ABC Bank. The Cards-Payments-Servers Inventory exists but is completely empty. Infra has sent over a spreadsheet listing 42 Linux application servers and 12 Windows servers, each with its own hostname, IP address, and role (application tier vs. database tier). Our task today is to bring this list into AAP correctly — not just as names, but with the metadata a playbook will actually need at runtime, like which OS family each host runs, so future playbooks can behave differently for Linux vs. Windows without us hand-writing separate inventories.

2. A Host Is More Than Just a Hostname

A Host object in AAP holds the connection address, plus a set of Host Variables in YAML/JSON — arbitrary key-value data a playbook can read via hostvars. This is what lets one generic "patch servers" playbook behave correctly across a mixed Linux/Windows estate without a mess of if-else logic hardcoded everywhere.

3. The Hosts Screen

Where: not a separate top-level nav item — Hosts live inside an Inventory. Open Resources → Inventories → Cards-Payments-Servers, then click the Hosts tab. Who uses it: Automation Admins, and sometimes delegated Team Leads for their own team's Inventory. What you see: a table of hosts with their name, connection status (from the last job that touched them), and enabled/disabled state.

4. Every Field Explained (Add Host form)

5. Hands-On: Adding Our First Hosts

  • Open Resources → Inventories → Cards-Payments-Servers → Hosts tab → click Add.
  • Name: cards-app-lin-01.abcbank.internal
  • Variables: paste the YAML below.
  • Click Save. Repeat for the remaining 41 Linux and 12 Windows servers — in Section 7 below we cover a faster, bulk way to do this instead of clicking Add 54 times.
# Host variables for cards-app-lin-01
ansible_host: 10.20.14.11          # Actual IP Ansible connects to (Name field can be a friendly label instead)
ansible_connection: ssh       # Connect via SSH (would be "winrm" for a Windows host)
os_family: RedHat              # Custom variable our playbooks check to branch Linux-specific logic
app_tier: cards-application    # Custom variable identifying this server's role
patch_group: wave-1            # Custom variable used later by our Patch Automation project

6. Host Variables in Depth

VariableBuilt-in or custom?Purpose
ansible_hostBuilt-in (recognized by Ansible core)Overrides the connection address if the Name field is a friendly label rather than a resolvable hostname.
ansible_connectionBuilt-inTells Ansible whether to use SSH (Linux) or WinRM (Windows) for this host.
os_family, app_tier, patch_groupCustom (our own choice)Not recognized by Ansible itself — purely for our own playbooks to read and branch logic on, e.g. patch Wave 1 servers before Wave 2.
Production tipSet Host Variables at the most specific level that's actually true for that one host. Anything shared by many hosts (like os_family: RedHat for every Linux server) is usually better placed on the Group instead — which is exactly what Project 11 covers next, and prevents repeating the same variable 42 times.

7. Adding Hosts in Bulk

Clicking Add 54 times isn't realistic. In practice, Automation Admins use the AAP REST API (or the awx/controller Ansible Collection) to script host creation directly from Infra's spreadsheet, converted to CSV or YAML first. We'll build this properly once we cover the REST API in our CI/CD integration project later in the track — for today, know that this bulk pattern exists and is the realistic day-to-day approach.

8. Enabled vs Disabled Hosts

A real scenario this solvescards-app-lin-07 goes into hardware maintenance for two days. Instead of deleting it from the Inventory (losing its Host Variables and history) or leaving it in and risking a failed job against an unreachable server, we simply toggle it to Disabled. Every Job Template targeting its Group silently skips it until we re-enable it.

11. Interview Prep — Say This Out Loud

"What's the difference between a built-in and a custom host variable?"

Built-in ones like ansible_host and ansible_connection are recognized directly by Ansible core to control how it connects. Custom ones, like an os_family or patch_group tag, mean nothing to Ansible itself — they're just data our own playbooks read to make decisions, like which patch wave a server belongs to.

"How would you temporarily take a server out of automation without losing its configuration?"

Toggle it to Disabled rather than deleting it — every job targeting its group skips it automatically, but its Host Variables and history are preserved for when it's re-enabled.

12. Wrap-Up

Key Learnings

  • A Host holds connection details plus arbitrary Host Variables a playbook can read.
  • Shared variables belong on a Group, not repeated on every Host — a preview of Project 11.
  • Disable, don't delete, a host that's temporarily out of service.
