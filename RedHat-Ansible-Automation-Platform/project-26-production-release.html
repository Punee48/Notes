PROJECT 26 OF 30 · MILESTONE — RELEASE ENGINEERING

Production Release

Every object built since Day 1 assembles into one formal, ITSM-integrated release process.

1. The Production Story

Day 26 at ABC Bank. The Release team asks for one final piece before Cards & Payments' first fully-automated production release: every deployment must automatically open a ServiceNow change ticket, update it as each stage completes, and close it out with the final result — exactly the ServiceNow integration we prepared the groundwork for all the way back in Project 07's custom Credential Type and Project 15's webhook notification type. Today we assemble everything.

2. Assembling 25 Projects Into One Release Process

Nothing new is being invented today — this project is deliberately an assembly exercise, pulling together: the Git-pinned Project (08), the structured Inventory (09–11), the Job Template pattern (12), Workflow branching (13), Scheduling if needed (14), Notifications (15), the correct Execution Environment (16), Surveys for release parameters (18), RBAC (19), Approval gating (20), the rolling deployment (23), and the multi-dimensional health check (25).

3. Wiring In the ServiceNow Integration

  • Create a Credential using the ServiceNow ITSM API Credential Type we built in Project 07, populated with ABC Bank's ServiceNow instance URL and API token.
  • Create a Webhook-type Notification Template (Project 15) pointed at a small internal API endpoint that translates AAP job events into ServiceNow change-ticket updates — "Job Started" opens the ticket, "Job Succeeded"/"Job Failed" closes it with the correct outcome.
  • Attach this Notification to the Production Release Workflow's Start, Success, and Failure triggers.
Why this matters to the businessRelease Managers no longer manually update a ServiceNow ticket during a deployment window — the automation itself keeps the change record accurate in real time, closing a long-standing gap between "what actually happened" and "what the ticket says happened."

4. Pinning the Release — Revisiting Project 08

Recall Project 08's warning about "Update Revision on Launch." For a real production release, we go one step further: the Project's Source Control Branch/Tag field is explicitly set to the release tag, e.g. v2.4.0, created in Git only after the Release Manager's formal sign-off — not main. This guarantees the deployment runs exactly the reviewed, tagged code, with zero ambiguity about which commit went to production.

6. Hands-On: Assembling the Full Pipeline

  • Confirm the Cards-Payments-Playbooks Project is pinned to tag v2.4.0, with Update Revision on Launch disabled.
  • Open the Cards - Deployment Pipeline Workflow (built incrementally since Project 13) and confirm every node from the diagram above is present: Health Check → Approval → Deploy → Smoke Test → (Success: Done / Failure: Rollback).
  • Attach the ServiceNow webhook Notification to the workflow's Start/Success/Failure triggers.
  • Run a full end-to-end test in a staging Inventory first, confirming a ServiceNow ticket is genuinely opened and closed correctly for both a successful and a deliberately-failed run.
  • Get sign-off from the Release Manager, then run the real production release against tag v2.4.0.

7. Rollback Path

If the post-deploy smoke test fails, the workflow routes to a dedicated Rollback Job Template — a playbook that restores the backup: yes artifact copies from Project 23 and reverts the config template to the previous version, then re-runs the health check to confirm the rollback itself succeeded. This is the formal version of the "restore from backup" idea introduced conceptually in Project 23.

10. Interview Prep — Say This Out Loud

"Walk me through a full production release pipeline you've built."

Describe the assembled workflow: pinned release tag in Git, multi-dimensional pre-check, a human Approval gate, batched rolling deployment with a real health-check verification, automatic rollback on smoke-test failure, and ServiceNow ticket lifecycle management tied to the workflow's start/success/failure events — all built from individually simple, reusable AAP objects.

"Why pin the Project to a Git tag instead of a branch for a production release?"

A branch like main can change at any moment; a tag is immutable once created. Pinning to a tag guarantees the exact reviewed code that was signed off is what actually deploys, with zero ambiguity.

11. Wrap-Up

Key Learnings

  • A real release pipeline is an assembly of individually simple AAP objects, not one giant custom playbook.
  • Pinning to an immutable Git tag removes all ambiguity about what code actually deployed.
  • ITSM integration via webhook Notifications keeps change records accurate automatically.
