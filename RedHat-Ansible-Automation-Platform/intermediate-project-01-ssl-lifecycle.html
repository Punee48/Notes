Enterprise SSL Certificate Lifecycle Automation

Discovery → backup → CSR → validation → approval → deployment → controlled restart → rollback — orchestrated end to end through Red Hat Ansible Automation Platform.

1. The Production Story

We are working as DevOps Automation Engineers for ABC Bank. The bank operates approximately 1,500 Linux servers and 900 Windows servers across Production and Disaster Recovery data centers. The Payments application is fronted by Apache, runs on Tomcat, and talks to Oracle — all secured with certificates issued by ABC Bank's internal PKI.

The Security Team has just flagged three certificates on the Payments estate expiring within 21 days. Today, the process is entirely manual and requires Linux, Middleware, Network, Security, and Application teams to coordinate a certificate swap by hand, over email and a shared spreadsheet. Six months ago, a mismatched private key during a manual swap took Payments offline for 40 minutes — the incident we'll revisit later in this project.

Our manager has assigned us to automate this entire lifecycle through AAP, while keeping the human approval step that Change Management still requires before anything touches production. Today we design and build that automation.

6. Custom Credential Type for the PKI API

ABC Bank's internal PKI issues certificates through a REST API requiring a bearer token. There's no built-in AAP Credential Type for this, so — exactly like the ServiceNow integration pattern from the Foundations track — we build one.

# Input Configuration — fields shown when creating a Credential of this type
fields:
  - id: pki_api_url          # Internal field name used to reference this value
    type: string
    label: Internal PKI API URL
  - id: pki_api_token
    type: string
    label: PKI API Bearer Token
    secret: true          # Masked on screen, encrypted at rest
required: [pki_api_url, pki_api_token]

# Injector Configuration — how the playbook receives these at runtime
env:
  PKI_API_URL: '{{ pki_api_url }}'
  PKI_API_TOKEN: '{{ pki_api_token }}'   # Never printed to Job Output; only readable as an env var inside the EE

playbooks/ssl_discover_and_backup.yml — Pre-Check Stage

---
- name: Discover Expiring Certificates and Backup Current State   # Play name shown in AAP Job Output
  hosts: payments_web                        # Targets the Apache/Tomcat front-end group
  become: yes                             # Reading /etc/pki paths requires elevated rights
  gather_facts: no

  vars:
    cert_path: /etc/httpd/ssl/payments.crt   # Path to the currently deployed certificate
    expiry_threshold_days: 21               "># Matches the Security team's 21-day flag from today's story

  tasks:
    - name: Read certificate details
      community.crypto.x509_certificate_info:  # Dedicated module — parses a cert file without shelling out to openssl
        path: "{{ cert_path }}"
      register: cert_info                    # Captures expiry date, issuer, subject, etc.

    - name: Calculate days until expiry
      ansible.builtin.set_fact:
        days_remaining: "{{ ((cert_info.not_after | to_datetime('%Y%m%d%H%M%SZ')) - (ansible_date_time.iso8601 | to_datetime('%Y-%m-%dT%H:%M:%SZ'))).days }}"
        # Breaking this down: cert_info.not_after is the cert's expiry timestamp from the module above.
        # to_datetime() converts the raw string into a Python datetime object Ansible can subtract.
        # Subtracting "now" from "expiry" gives a timedelta; .days extracts the whole number of days remaining.

    - name: Flag this host if within the rotation threshold
      ansible.builtin.set_fact:
        needs_rotation: "{{ (days_remaining | int) <= expiry_threshold_days }}"
        # days_remaining | int : the "int" filter converts the string result into a real integer for numeric comparison
        # <= expiry_threshold_days : true if fewer days remain than our 21-day policy threshold

    - name: Backup the current certificate with a timestamp
      ansible.builtin.copy:
        remote_src: yes                    # The source file already exists ON the remote host — don't look for it locally
        src: "{{ cert_path }}"
        dest: "{{ cert_path }}.bak.{{ ansible_date_time.iso8601_basic_short }}"  # Timestamped so multiple backups never overwrite each other
      when: needs_rotation             # Only backup hosts that actually need rotation — skip healthy ones

    - name: Report this host's certificate status
      ansible.builtin.set_stats:
        data:
          cert_status:
            host: "{{ inventory_hostname }}"
            days_remaining: "{{ days_remaining }}"
            needs_rotation: "{{ needs_rotation }}"
Line-by-line explanation of the trickiest task (click to expand)
FragmentMeaning
{{ }}Jinja2 delimiters — everything inside is evaluated as an expression, not treated as literal text.
cert_info.not_afterDot notation accessing the not_after key inside the cert_info dictionary registered by the earlier task — this is the certificate's raw expiry timestamp string.
| to_datetime('%Y%m%d%H%M%SZ')The pipe | applies a Jinja2 filter — to_datetime — to the value on its left, parsing the raw string into a proper datetime object using the given format code.
ansible_date_time.iso8601A built-in fact (automatically gathered) giving the managed node's current UTC time in ISO8601 format.
.daysProperty access on the resulting Python timedelta object from the subtraction — returns the whole number of days between the two datetimes.
| intConverts a string value to an actual integer type so numeric comparison (<=) works correctly.

playbooks/ssl_deploy_certificate.yml — Implementation Stage

---
- name: Deploy New Certificate to Apache and Tomcat
  hosts: payments_web
  become: yes
  serial: "1"                    # One server at a time — TLS-facing change, smallest possible blast radius

  vars:
    new_cert_path: "/tmp/payments_new.crt"   # Downloaded from PKI, staged before final placement
    live_cert_path: /etc/httpd/ssl/payments.crt

  block:                             # A block groups tasks so ONE rescue can cover all of them
    - name: Request signed certificate from internal PKI
      ansible.builtin.uri:
        url: "{{ lookup('env', 'PKI_API_URL') }}/issue"   # Reads the env var injected by our custom Credential Type
        method: POST
        headers:
          Authorization: "Bearer {{ lookup('env', 'PKI_API_TOKEN') }}"  # Token never appears in Job Output — read only via lookup at runtime
        body_format: json
        body:
          common_name: payments.abcbank.internal
        dest: "{{ new_cert_path }}"
      no_log: true                  # Suppresses this task's full output — extra safety, since headers include the bearer token

    - name: Validate the new certificate and private key match
      ansible.builtin.assert:
        that:
          - cert_modulus.stdout == key_modulus.stdout   # Two openssl modulus hashes registered by earlier (omitted for brevity) tasks — must be identical
        fail_msg: "Certificate and private key do NOT match — aborting deployment"

    - name: Deploy new certificate into place
      ansible.builtin.copy:
        remote_src: yes
        src: "{{ new_cert_path }}"
        dest: "{{ live_cert_path }}"
        mode: '0640'
      notify: reload apache          # Queues the "reload apache" handler — runs once, at the end of the play, not immediately

    - name: Flush handlers now so reload happens before our HTTPS validation below
      ansible.builtin.meta: flush_handlers   # Forces queued handlers to run immediately instead of waiting for play end

    - name: Validate HTTPS handshake with the new certificate
      ansible.builtin.uri:
        url: https://localhost:443/health
        validate_certs: yes        # Genuinely validate the chain, not just check the port is open
      register: https_check
      retries: 3
      delay: 5
      until: https_check.status == 200

  rescue:                            # Runs ONLY if any task in the block above failed
    - name: Restore the previous certificate from backup
      ansible.builtin.shell: cp $(ls -t {{ live_cert_path }}.bak.* | head -1) {{ live_cert_path }}
      # Finds the most recent timestamped backup file (from the pre-check playbook) and restores it

    - name: Reload Apache with the restored certificate
      ansible.builtin.systemd:
        name: httpd
        state: reloaded

    - name: Fail the play clearly, after rollback completed
      ansible.builtin.fail:
        msg: "Certificate deployment failed and was rolled back automatically. See job output above for the original error."

  always:                             # Runs whether the block succeeded OR the rescue ran
    - name: Clean up staged certificate file
      ansible.builtin.file:
        path: "{{ new_cert_path }}"
        state: absent

handlers:
  - name: reload apache
    ansible.builtin.systemd:
      name: httpd
      state: reloaded            # "reloaded" re-reads config/certs without dropping active connections — NOT a hard restart
Why reload, not restartstate: reloaded sends Apache a graceful signal to re-read its configuration and certificate files without terminating existing connections. A hard restarted briefly drops the listening socket entirely — unacceptable for a live payments endpoint.

8. Internal Execution Walkthrough

StepWhat Actually Happens
Inventory parsingAAP resolves payments_web against the selected Inventory, expanding it to the actual list of Apache/Tomcat front-end hosts.
Variable precedenceSurvey-supplied values (e.g. a chosen environment) override group_vars, which override role defaults — highest specificity wins, same principle as the Foundations track's Group/Host variable precedence.
Credential injectionThe PKI custom Credential's token is decrypted only inside the EE's memory and exposed as an environment variable — never written to disk, never shown in Job Output due to no_log.
SSH connection + multiplexingThe EE opens one SSH connection per host and reuses it (ControlPersist) across multiple tasks in the same play, avoiding a fresh handshake for every single task.
Module transferAnsible copies the small Python module (e.g. community.crypto.x509_certificate_info) to the remote host over that SSH connection, executes it there, then removes it.
Idempotency checkModules like copy checksum the destination file first — if it already matches the source, the task reports ok, not changed.
JSON resultEvery module returns structured JSON (success/failure, changed flag, any registered data) back over the same SSH channel to the Controller.

11. Credential Security

Never hardcoded, anywhere in this project PKI API token · Private key material · Certificate passphrase (if any). All flow exclusively through the custom Credential Type's environment-variable injection, read at runtime via lookup('env', ...), and the task requesting the certificate is marked no_log: true so the Authorization header is never printed to Job Output even accidentally.

RBAC (from the Foundations track) restricts who can even select this Credential on a new Job Template — only Automation Admins have the "Use" role on it; regular Middleware engineers can launch templates that already reference it, but can never see or extract its value.

12. Failure Handling & Idempotency

ScenarioBehavior
PKI API request failsBlock/rescue catches it — rescue restores the backed-up certificate and reloads Apache, so the server never ends up with no certificate in place at all.
Certificate/key mismatch detectedThe explicit assert task fails deployment before the file is ever copied into the live path — the old certificate is untouched.
HTTPS post-validation failsrescue triggers, restoring the previous certificate and reloading — the play then fails loudly rather than silently leaving a broken state.
1 of 5 servers fails mid-rolloutserial: "1" means each host completes fully (including its own rescue path) before the next begins — a single host's failure never blocks or corrupts the others.
Re-running after a successful deploymentThe copy task for a certificate that's already correctly in place reports ok, not changed — idempotent by the module's built-in checksum comparison.

13. Rollback

Rollback here is automatic and embedded in the block/rescue structure — not a separate manual step. The sequence is: backup (pre-check stage) → deploy → validate → on any failure, restore the most recent backup and reload → confirm the reload succeeded → fail the play with a clear message. This mirrors, but goes one step further than, the Foundations track's backup: yes pattern by actively restoring rather than just leaving a backup file for a human to find later.

Standalone rollback playbookplaybooks/ssl_rollback.yml exists separately for the rare case a bad certificate is discovered well after the deployment job finished (e.g. a delayed chain trust issue) — it accepts a target host and timestamp via Survey and restores that specific backup on demand.

14. Reporting

Every host's set_stats data (certificate status, rotation outcome) aggregates into the Workflow Job's summary, visible in AAP's Job Output "Details" view — the same technique used for the Foundations track's compliance scan. A downstream Workflow node (not shown in full here) calls a small script that formats this into an HTML report and attaches it to the CAB change ticket automatically, giving Change Management concrete evidence without anyone manually screenshotting Job Output.

18. Production Incident

Incident: Payments outage, 40 minutes, six months ago Impact: Payments application unavailable to customers for 40 minutes during a manual certificate swap.
Alert: Synthetic monitoring detected HTTPS handshake failures within 90 seconds of the manual restart.
Investigation: On-call engineer found Apache running but rejecting all TLS connections.

How to discuss this in an interviewDescribe it as a concrete example of designing a control (the modulus-matching assert) directly in response to a real incident, not a theoretical best practice — interviewers respond well to "I built X because Y actually happened," with a clear cause → automation-fix → prevention chain.

19. Interview Preparation

Scenario: "A certificate deployment fails midway through 5 servers. What happens?"

With serial: "1", each host completes its own full block/rescue cycle independently — a failure on host 2 triggers that host's own rescue (restore + reload + fail), while hosts 3–5 are simply never started. Nothing is left in a half-deployed state on any single host, and the workflow overall reports failure with a clear audit trail of exactly which host failed and why.

AAP: "Why use a custom Credential Type instead of a plain Vault-encrypted variable for the PKI token?"

A custom Credential Type integrates with AAP's RBAC — you can control exactly who has the "Use" role on it, it's masked in the UI, and it's reusable across every Job Template that needs it, with a single point of rotation. A Vault-encrypted variable sitting in Git has none of that access control or centralized rotation.

Ansible: "Explain block/rescue/always in this project."

block groups the request-deploy-validate sequence so a single rescue can catch any failure across all of them. rescue performs the actual rollback (restore backup, reload). always runs regardless of outcome — here, cleaning up the staged certificate file so it's never left behind whether the deployment succeeded or failed.

Security: "How do you prevent the PKI token from leaking into logs?"

no_log: true on the specific task that sends the Authorization header, combined with reading the token only via lookup('env', ...) at the moment it's needed rather than registering it into a variable that might get printed elsewhere.

Manager round: "How would you convince a skeptical Middleware team to trust this automation over their manual process?"

Point to the concrete incident this project directly prevents (the private-key mismatch outage), demonstrate the assert-based safety check live in DEV, and emphasize that Approval Nodes mean the team never loses control — they still explicitly sign off before production, the automation just removes the error-prone manual coordination underneath that decision.
