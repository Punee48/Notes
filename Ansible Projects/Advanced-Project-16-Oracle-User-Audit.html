Project 16: Oracle Database User Audit, Privilege Validation & Access Compliance

ABC Global Bank's 47 Oracle databases hold the most sensitive data in the bank — customer accounts, transaction history, loan records, and AML (Anti-Money Laundering) transaction logs. Access to this data is controlled through Oracle's user management system — but over years of operations, databases accumulate abandoned accounts, over-privileged application users, DBA accounts granted to developers, and default Oracle accounts with known passwords. PCI-DSS Requirement 8 mandates strict user account management. RBI's IT Framework requires quarterly access reviews. This project automates complete Oracle user and privilege auditing across all 47 databases — detecting violations, generating QSA-grade evidence, and automatically locking abandoned accounts.

🏦 1. The Banking Story

Setting: ABC Global Bank's Oracle database estate: 47 databases across CBS, LMS, FDS, AML, and regulatory reporting systems. Database security is managed by a 3-person DBA team who handle user creation, privilege grants, and quarterly access reviews — all manually via SQL*Plus and Oracle Enterprise Manager.

Incident 1 — The Ex-Employee Account: During an RBI IT audit, the auditor ran a query on the CBS production database: SELECT username FROM dba_users WHERE last_login > SYSDATE - 90 AND account_status = 'OPEN'. One result: RAJESH_DBA. Rajesh had left the bank 7 months ago. His DBA-level account was still open, had logged in 3 months ago, and had SELECT ANY TABLE privilege. The bank could not explain what Rajesh (or whoever used his credentials) had accessed in those 3 months. RBI issued a Critical finding: "Failure to revoke database access for terminated employees." Fine: ₹25 lakh. The bank had no process to notify the DBA team when HR terminated an employee.

Incident 2 — The Developer with DBA Rights: A developer (Priya) had been granted the DBA role in the LMS UAT database 2 years ago to "help debug a production issue." Nobody revoked it. The LMS UAT database shares a network segment with LMS production and has identical schema. Priya could query LMS production customer loan data from UAT by using a database link. A QSA discovered this during a PCI-DSS assessment: "Excessive privilege — developer can access cardholder data via database link." Critical finding.

Incident 3 — The Default Oracle Password: Oracle installations include default accounts (DBSNMP, SYSMAN, CTXSYS, etc.). On 3 older databases (migrated from Oracle 11g), these accounts were never locked and still had their default passwords. A penetration tester discovered DBSNMP with password "dbsnmp" was active on cbs-db-dr01. DBSNMP has monitoring privileges that could be used for reconnaissance. Critical security finding.

The Ask: "Audit every user account on every Oracle database every week. Find abandoned accounts (no login > 90 days), excessive privileges (DBA role on non-DBA users), default passwords, accounts that should be locked. Auto-lock abandoned accounts with approval. Give the CISO a quarterly access review report that satisfies RBI audit requirements."

📚 2. Oracle Security Concepts

Key Oracle Data Dictionary Views for Security
ViewWhat It ShowsKey Columns
DBA_USERSAll database user accountsUSERNAME, ACCOUNT_STATUS (OPEN/LOCKED/EXPIRED), LAST_LOGIN, CREATED, EXPIRY_DATE, PROFILE
DBA_SYS_PRIVSSystem privileges granted to users/rolesGRANTEE, PRIVILEGE (CREATE TABLE, DROP ANY TABLE, etc.), ADMIN_OPTION
DBA_ROLE_PRIVSRoles granted to usersGRANTEE, GRANTED_ROLE (DBA, SYSDBA, etc.), ADMIN_OPTION, DEFAULT_ROLE
DBA_TAB_PRIVSObject-level privileges (SELECT, INSERT on specific tables)GRANTEE, OWNER, TABLE_NAME, PRIVILEGE
DBA_PROFILESPassword and session policies per profilePROFILE, RESOURCE_NAME, LIMIT (PASSWORD_LIFE_TIME, FAILED_LOGIN_ATTEMPTS, etc.)
V$PWFILE_USERSUsers with SYSDBA/SYSOPER privilegeUSERNAME, SYSDBA, SYSOPER, SYSASM
Oracle Account Statuses — What Each Means
OPEN: Account is active and can log in. Normal state for active accounts.
LOCKED: Account is manually locked — cannot log in. Also set by DBA or failed login threshold.
EXPIRED: Password has expired (based on PASSWORD_LIFE_TIME in profile). User must change password on next login.
EXPIRED & LOCKED: Both conditions apply — account cannot log in at all.
LOCKED(TIMED): Automatically locked due to too many failed login attempts. Auto-unlocks after PASSWORD_LOCK_TIME.

In banking security policy: all accounts not actively used must be in LOCKED or EXPIRED & LOCKED state.
Default Oracle Accounts — The Security Risk
Oracle installations create dozens of internal accounts with default passwords. In older installations (pre-12c), these were not locked by default. Known risky accounts:

💻 8. Roles & Tasks — Complete Code

Role 1: oracle_user_check — Inactive Account Detection

roles/oracle_user_check/tasks/check_inactive_accounts.yml
---
# =====================================================================
# Detect Oracle accounts inactive for > 90 days
# Queries DBA_USERS — the source of truth for all DB user accounts
# =====================================================================

- name: Query inactive Oracle user accounts
  ansible.builtin.shell:
    cmd: |
      sqlplus -S {{ oracle_monitor_user }}/{{ oracle_monitor_password }}@{{ oracle_sid }} << 'EOF'
      SET PAGESIZE 0 FEEDBACK OFF VERIFY OFF HEADING OFF ECHO OFF
      SET COLSEP '|'

      SELECT
        u.username,
        u.account_status,
        TO_CHAR(u.last_login, 'YYYY-MM-DD HH24:MI:SS') AS last_login,
        TO_CHAR(u.created, 'YYYY-MM-DD')               AS created_date,
        TRUNC(SYSDATE - u.last_login)                  AS days_inactive,
        u.profile,
        NVL(u.authentication_type, 'PASSWORD')         AS auth_type
      FROM dba_users u
      WHERE u.account_status = 'OPEN'
        AND u.last_login IS NOT NULL
        AND u.last_login < SYSDATE - {{ oracle_inactive_warn_days }}
        AND u.oracle_maintained = 'N'
        AND u.username NOT IN (
          {{ oracle_excluded_usernames
             | map('regex_replace', '^(.*)$', "'\g<1>'")
             | join(',') }}
        )
      ORDER BY days_inactive DESC;
      EXIT;
      EOF
    executable: /bin/bash
  register: inactive_query_result
  become: true
  become_user: oracle
  no_log: true                                           # Hide credentials from logs
  changed_when: false
  environment:
    ORACLE_HOME: "{{ oracle_home }}"
    ORACLE_SID: "{{ oracle_sid }}"
    LD_LIBRARY_PATH: "{{ oracle_home }}/lib"

- name: Parse sqlplus output into structured user list
  ansible.builtin.set_fact:
    inactive_accounts: >-
      {{ inactive_accounts | default([]) + [{
        'username': item.split('|')[0] | trim,
        'status': item.split('|')[1] | trim,
        'last_login': item.split('|')[2] | trim,
        'created': item.split('|')[3] | trim,
        'days_inactive': item.split('|')[4] | trim | int,
        'profile': item.split('|')[5] | trim,
        'database': oracle_sid,
        'host': inventory_hostname,
        'lock_eligible': item.split('|')[4] | trim | int >= oracle_inactive_lock_days | int
      }] }}
  loop: >-
    {{ inactive_query_result.stdout_lines
       | reject('match', '^$')
       | reject('match', '^SQL.*')
       | list }}
  loop_control:
    label: "{{ item.split('|')[0] | trim }}"
  when: inactive_query_result.stdout_lines | length > 0

- name: Classify inactive accounts by severity
  ansible.builtin.set_fact:
    accounts_critical: >-
      {{ inactive_accounts | default([])
         | selectattr('days_inactive', 'ge', oracle_inactive_critical_days | int)
         | list }}
    accounts_warning: >-
      {{ inactive_accounts | default([])
         | selectattr('days_inactive', 'ge', oracle_inactive_warn_days | int)
         | selectattr('days_inactive', 'lt', oracle_inactive_critical_days | int)
         | list }}

- name: Log inactive account summary
  ansible.builtin.debug:
    msg:
      - "Oracle Inactive Account Audit — {{ inventory_hostname }} ({{ oracle_sid }})"
      - "Warning ({{ oracle_inactive_warn_days }}-{{ oracle_inactive_critical_days }}d): {{ accounts_warning | length }} accounts"
      - "CRITICAL (> {{ oracle_inactive_critical_days }}d): {{ accounts_critical | length }} accounts"
      - "Lock eligible: {{ inactive_accounts | default([]) | selectattr('lock_eligible') | list | length }} accounts"

- name: Alert on critical inactive accounts
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "oracle-inactive-{{ inventory_hostname }}-{{ oracle_sid }}"
      payload:
        summary: >-
          ⚠️ ORACLE INACTIVE ACCOUNTS: {{ accounts_critical | length }} accounts
          inactive > {{ oracle_inactive_critical_days }} days on
          {{ oracle_sid }} ({{ inventory_hostname }}).
          PCI-DSS Req 8.2.6 violation. Accounts: {{ accounts_critical
          | map(attribute='username') | list | join(', ') }}
        severity: error
        source: ansible-oracle-audit
        custom_details:
          database: "{{ oracle_sid }}"
          host: "{{ inventory_hostname }}"
          inactive_count: "{{ accounts_critical | length }}"
          accounts: "{{ accounts_critical | to_json }}"
          action_needed: "Review and lock via AAP oracle_lock_inactive job template"
    status_code: [202]
  delegate_to: localhost
  when: accounts_critical | length > 0

🔐 9. Privilege Audit Role

roles/oracle_privilege_audit/tasks/check_dba_role.yml
---
# =====================================================================
# Audit who has the DBA role and dangerous system privileges
# Compare against approved baseline — detect unauthorized grants
# =====================================================================

- name: Load approved DBA baseline for this database
  ansible.builtin.include_vars:
    file: "{{ playbook_dir }}/../approved_baselines/{{ oracle_sid | lower }}_approved_dbas.yml"
    name: approved_baseline
  failed_when: false                                     # Some DBs may not have baseline yet

- name: Query users with DBA role
  ansible.builtin.shell:
    cmd: |
      sqlplus -S {{ oracle_monitor_user }}/{{ oracle_monitor_password }}@{{ oracle_sid }} << 'EOF'
      SET PAGESIZE 0 FEEDBACK OFF VERIFY OFF HEADING OFF ECHO OFF
      SET COLSEP '|'
      SELECT
        rp.grantee,
        rp.granted_role,
        rp.admin_option,
        rp.default_role,
        u.account_status,
        TO_CHAR(u.last_login, 'YYYY-MM-DD') AS last_login
      FROM dba_role_privs rp
      JOIN dba_users u ON u.username = rp.grantee
      WHERE rp.granted_role IN (
        {{ oracle_dangerous_roles | map('regex_replace', '^(.*)$', "'\g<1>'") | join(',') }}
      )
      AND u.oracle_maintained = 'N'
      ORDER BY rp.granted_role, rp.grantee;
      EXIT;
      EOF
    executable: /bin/bash
  register: dba_role_query
  become: true
  become_user: oracle
  no_log: true
  changed_when: false
  environment:
    ORACLE_HOME: "{{ oracle_home }}"
    ORACLE_SID: "{{ oracle_sid }}"
    LD_LIBRARY_PATH: "{{ oracle_home }}/lib"

- name: Parse DBA role grant results
  ansible.builtin.set_fact:
    dba_role_grants: >-
      {{ dba_role_grants | default([]) + [{
        'username': item.split('|')[0] | trim,
        'role': item.split('|')[1] | trim,
        'admin_option': item.split('|')[2] | trim,
        'account_status': item.split('|')[4] | trim,
        'last_login': item.split('|')[5] | trim,
        'database': oracle_sid,
        'authorized': (item.split('|')[0] | trim in
                       approved_baseline.authorized_dba_users | default([]))
      }] }}
  loop: >-
    {{ dba_role_query.stdout_lines
       | reject('match', '^$')
       | reject('match', '^SQL.*')
       | list }}
  loop_control:
    label: "{{ item.split('|')[0] | trim }}"

- name: Identify unauthorized DBA role holders
  ansible.builtin.set_fact:
    unauthorized_dbas: >-
      {{ dba_role_grants | default([])
         | rejectattr('authorized', 'equalto', true)
         | list }}

- name: Fire P1 PagerDuty for unauthorized DBA role grants
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "oracle-unauthorized-dba-{{ inventory_hostname }}-{{ oracle_sid }}"
      payload:
        summary: >-
          🔴 UNAUTHORIZED DBA ACCESS: {{ unauthorized_dbas | length }} users
          have DBA role on {{ oracle_sid }} ({{ inventory_hostname }})
          who are NOT in the approved DBA list.
          Users: {{ unauthorized_dbas | map(attribute='username') | list | join(', ') }}.
          This was how the developer-with-DBA-rights incident occurred.
        severity: critical
        source: ansible-oracle-audit
        custom_details:
          database: "{{ oracle_sid }}"
          unauthorized_users: "{{ unauthorized_dbas | to_json }}"
          revoke_commands: >-
            {% for u in unauthorized_dbas %}
            REVOKE {{ u.role }} FROM {{ u.username }};
            {% endfor %}
    status_code: [202]
  delegate_to: localhost
  when: unauthorized_dbas | length > 0

- name: Query users with dangerous ANY system privileges
  ansible.builtin.shell:
    cmd: |
      sqlplus -S {{ oracle_monitor_user }}/{{ oracle_monitor_password }}@{{ oracle_sid }} << 'EOF'
      SET PAGESIZE 0 FEEDBACK OFF VERIFY OFF HEADING OFF ECHO OFF
      SET COLSEP '|'
      SELECT
        sp.grantee,
        sp.privilege,
        sp.admin_option,
        u.account_status
      FROM dba_sys_privs sp
      JOIN dba_users u ON u.username = sp.grantee
      WHERE sp.privilege IN (
        {{ oracle_dangerous_system_privileges
           | map('regex_replace', '^(.*)$', "'\g<1>'")
           | join(',') }}
      )
      AND u.oracle_maintained = 'N'
      AND sp.grantee NOT IN (
        {{ oracle_excluded_usernames
           | map('regex_replace', '^(.*)$', "'\g<1>'")
           | join(',') }}
      )
      ORDER BY sp.privilege, sp.grantee;
      EXIT;
      EOF
    executable: /bin/bash
  register: sys_priv_query
  become: true
  become_user: oracle
  no_log: true
  changed_when: false
  environment:
    ORACLE_HOME: "{{ oracle_home }}"
    ORACLE_SID: "{{ oracle_sid }}"
    LD_LIBRARY_PATH: "{{ oracle_home }}/lib"

- name: Parse system privilege results
  ansible.builtin.set_fact:
    dangerous_sys_privs: >-
      {{ dangerous_sys_privs | default([]) + [{
        'username': item.split('|')[0] | trim,
        'privilege': item.split('|')[1] | trim,
        'admin_option': item.split('|')[2] | trim,
        'database': oracle_sid
      }] }}
  loop: >-
    {{ sys_priv_query.stdout_lines

# =====================================================================
# Test if Oracle default accounts still use their default passwords
# Method: attempt connection — if successful, default password is active
# This is the check that catches the DBSNMP/tiger/ctxsys scenario

      fi

  loop_control:
    label: "Testing {{ item.key }}"

  become_user: oracle
  changed_when: false
  failed_when: false

    ORACLE_HOME: "{{ oracle_home }}"
    ORACLE_SID: "{{ oracle_sid }}"
    LD_LIBRARY_PATH: "{{ oracle_home }}/lib"

🎯 15. Interview Prep

Q: Why use sqlplus with SET COLSEP '|' instead of cx_Oracle for Oracle auditing in Ansible?
sqlplus approach advantages:
1. No Python library installation needed in the Execution Environment — sqlplus is already available on every Oracle database server
2. Works even when the Oracle Instant Client is not installed (sqlplus uses full Oracle client)
3. Simpler dependency chain — no cx_Oracle, no Python version conflicts
4. Output parsing via shell string operations is straightforward for structured queries using SET COLSEP

cx_Oracle advantages: Better error handling, native Python data types, connection pooling, no shell escaping issues with special characters in passwords

Best practice: For simple audit queries (< 10 columns, row counts < 1000), sqlplus is adequate. For complex queries returning many rows with potential special characters, cx_Oracle or the newer python-oracledb library is preferred. We use sqlplus with no_log:true to hide credentials and SET COLSEP '|' for reliable column separation.
Q: How does the approved baseline comparison work for DBA privilege drift detection?
The approved_baselines/ directory contains one YAML file per database, version-controlled in Git. Each file lists usernames explicitly approved to hold the DBA role or dangerous system privileges for that specific database:

# cbs_db01_approved_dbas.yml
authorized_dba_users:
  - DBA_PRIYA_01     # CBS DBA - approved 2024-01-15
  - DBA_SURESH_02    # CBS DBA - approved 2024-03-10
During the audit, we query DBA_ROLE_PRIVS for actual DBA holders. For each result, we check if the username is in approved_baseline.authorized_dba_users. Any username NOT in the list is flagged as unauthorized. This baseline-vs-actual comparison is the core of privilege drift detection — any new DBA grant (even legitimate ones that weren't added to the baseline) triggers an alert, forcing the DBA team to explicitly update the approved list.
Q: How do you detect default Oracle passwords without logging the credentials?
The key is no_log: true on the task that contains the default credential in its command string. This tells Ansible (and AAP) to suppress all output for that task — the command, its arguments, stdout, stderr, and return code are all hidden from job logs.

The detection logic: we attempt a sqlplus connection using the known default credential and run SELECT 'DEFAULT_PASSWORD_ACTIVE' FROM dual;. If this query returns our sentinel string, the connection succeeded — the default password is active. We then output "VULNERABLE:USERNAME" to stdout (without the password).

The register variable captures only "VULNERABLE/LOCKED/SECURE" prefixed output — the actual password never appears in the result facts. The PagerDuty alert includes the vulnerable account name but never the password. This satisfies the audit requirement (detected the issue) while maintaining credential security (password never in logs).
Q: What is oracle_maintained = 'Y' in DBA_USERS and why do we filter by it?
ORACLE_MAINTAINED is a column added in Oracle 12c to DBA_USERS. It's set to 'Y' for all accounts that are part of the Oracle database engine itself — SYS, SYSTEM, AUDSYS, XDB, WMSYS, GSMADMIN_INTERNAL, and about 50 other internal accounts.

These accounts: must exist for Oracle to function, often appear to have high privileges by design, and may not have recent last_login values (some only log in during upgrades). Including them in our inactive account audit would generate hundreds of false positives.

Filtering with WHERE oracle_maintained = 'N' restricts our audit to customer-created accounts (application users, DBA accounts, developer accounts, etc.) — the ones we actually manage and are responsible for auditing under PCI-DSS.

In Oracle 11g (which doesn't have this column), we use the fallback approach of explicitly excluding known Oracle internal accounts via AND username NOT IN ('SYS', 'SYSTEM', ...).
