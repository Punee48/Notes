Project 10: Server Hardening Automation using Red Hat AAP

Every server that joins SecureBank's infrastructure fleet must be hardened before it carries production banking workloads. "Hardening" means systematically reducing the server's attack surface by enforcing CIS Benchmark Level 2 controls on top of the baseline OS image — covering kernel parameters, filesystem protections, network stack hardening, mandatory access controls (SELinux), firewalld zone policies, GRUB bootloader protection, banner enforcement, core dump restrictions, and cryptographic algorithm policy. Without automated hardening, new servers built from the standard OS image diverge from the security baseline within days as teams install packages, tweak configs, or disable SELinux "temporarily" — creating an invisible, growing attack surface across 400+ servers. This project automates server hardening as a Day-0 bootstrap role (applied to every new server the moment it's provisioned) and as a continuous drift-correction job (re-applied weekly to detect and remediate configuration drift across the entire fleet).

🏦 2. Real-Time Banking Scenario

The Story: SecureBank's penetration testing firm, engaged for the annual PCI-DSS assessment, submits their report. Three critical findings stand out across production servers:

Finding 1: SELinux is in permissive mode on 14 of 180 production servers. Somewhere in the past year, an engineer ran setenforce 0 to debug an application issue, then changed it back in /etc/sysconfig/selinux — but only set it to permissive, not enforcing. Root cause: the deployment team never re-ran any hardening validation after the change.

Finding 2: /tmp is mounted on the root filesystem (not a separate partition with noexec,nosuid) on 22 servers. The base OS image was built by a vendor who didn't enforce the CIS Benchmark partition requirements, and nobody checked before deploying application workloads.

Finding 3: net.ipv4.ip_forward = 1 on 8 non-router application servers — left over from a Docker Swarm experiment a year ago that was decommissioned but whose kernel parameters were never reset. This allows these servers to route packets between network segments — a critical firewall bypass risk in the bank's segmented CDE network.

Total PCI-DSS findings from these three issues: 11 separate control failures across Req 1, Req 2, and Req 6. Remediation cost: 3 weeks of manual work to fix and re-document across 180 servers. With weekly automated hardening drift correction, all three of these findings would have been detected and auto-remediated within 7 days of introduction — appearing in the Sunday hardening report, not in the annual pen test.

❗ 3. Problem Statement

  • No consistent baseline hardening applied at server provisioning time — new servers from the standard OS image miss dozens of CIS controls out of the box.
  • Configuration drift: hardening settings applied 6 months ago are silently reversed by troubleshooting engineers, package upgrades that overwrite config files, or third-party application installers that modify kernel parameters.
  • SELinux is the most-frequently-disabled security control in RHEL environments — "temporarily" disabled servers never get re-enabled because nobody tracks the state fleet-wide.
  • No fleet-wide visibility of which servers are hardened vs drifted — the first sign of a problem is a pen test finding or RBI audit finding.
  • Hardening applied inconsistently between teams — the DBA team, app team, and platform team each apply different subsets of CIS controls from tribal knowledge.
  • No evidence trail for auditors — QSAs ask "show me that these hardening controls are applied to all servers" and the answer is a mix of screenshots and verbal assurances.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. A new server is provisioned from the vendor OS image. Hardening: optional, dependent on which team provisions it.
  2. If hardened, an engineer follows a personal checklist of ~40 items, running commands manually on each server — inconsistent between engineers and not documented per-server.
  3. Hardening verification: never formally done post-application deployment — teams assume baseline holds.
  4. Drift remediation: only triggered by a pen test finding or audit observation — reactive, not proactive.
  5. Evidence: a Word document titled "Server Hardening Standards v2.4" exists but is 2 years out of date. QSAs do not accept it as evidence of actual implementation.

🛠️ 7. Automated Solution Design

  • Day-0 Hardening Role: A mandatory role imported by every server provisioning playbook (new VM, cloud instance, or bare-metal build). Applied before any application software is installed. Runs in a defined order: filesystem → kernel → SELinux → services → SSH → firewalld → bootloader → crypto → banner. Each sub-category is its own task file included via include_tasks.
  • Drift Detection & Correction (Weekly): The same hardening role runs weekly on all 400 servers in --check --diff mode first to identify drift, then in real mode to correct it. Any server with drift is logged to the hardening report. Auto-correction is applied for low-risk settings (sysctl, banner, cron permissions). High-risk corrections (SELinux mode change requiring relabel, crypto policy requiring reboot) are flagged for approval before being applied.
  • Reboot Safety Gate: Controls that require a reboot (FIPS mode activation, SELinux relabel after enforcing change) are applied only during declared maintenance windows. A reboot_required flag is set as a host fact; the playbook's final task prompts an approval node in the AAP workflow before rebooting any server.
  • Tier-aware profiles: group_vars define which hardening categories apply per tier (DMZ gets stricter firewalld; DB tier gets extra kernel network isolation; Dev gets CIS L1 not L2). One role, multiple profiles via variable-driven task inclusion.

⚙️ 9. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.posix.sysctl, ansible.posix.selinux, ansible.posix.firewalld, ansible.builtin.lineinfile, ansible.builtin.template, ansible.builtin.service, ansible.builtin.command, ansible.builtin.reboot
  • Roles: harden_filesystem, harden_kernel, harden_selinux, harden_services, harden_ssh, harden_firewalld, harden_grub, harden_coredump, harden_crypto, harden_ntp, harden_banner, harden_cron, harden_report
  • Ansible Vault: GRUB password hash, Vault-encrypted banner content
  • ansible.posix.sysctl module with sysctl_file and reload: true for persistent kernel parameter management
  • --check --diff mode for drift detection before correction
  • Jinja2 templates: sysctl.conf per tier, firewalld zone XML, SSH config drop-in, system banner

Red Hat AAP Components

  • Job Templates: Server-Harden-Day0 (new servers), Server-Harden-Drift-Detect (check mode, weekly), Server-Harden-Drift-Correct (real mode, weekly with approval), Server-Harden-Single (survey: target_host)
  • Workflow: Server-Hardening-Weekly (detect → report → approval → correct → reboot gate → final report)
  • Survey: target_host (single server), hardening_profile (cis-l1/cis-l2/pci-cde), skip_reboot (bool — skip reboot-required changes)
  • Schedule: Server-Harden-Drift-Detect: Sunday 00:00 IST; Server-Harden-Drift-Correct: Sunday 02:00 IST (after human review of drift report)
  • Notification: Slack #security-hardening with drift count per server; Email to InfoSec team with full hardening report CSV
  • RBAC: Server-Harden-Day0: Platform Provisioning team; Server-Harden-Drift-Correct: Security team only

Design Rationale
tags: on every include_tasks — Each hardening category has its own Ansible tag, enabling engineers to run only specific categories: ansible-playbook harden_day0.yml --tags kernel,selinux re-applies only kernel and SELinux settings without touching SSH or firewalld. This is essential for targeted re-hardening after a specific pen test finding without risk to other controls.
hardening_results: [] — Initializes an empty list that each sub-task appends to (using set_fact: hardening_results + [entry]) building up a per-server audit trail of every control check result. The report.yml task at the end collects this for the compliance CSV.
reboot_required: false — A flag that any sub-task can set to true when it applies a control that needs a reboot (FIPS mode, SELinux mode change). The master playbook checks this flag after all tasks complete and either reboots (if reboot_if_required: true) or raises an approval node in the workflow.

Task: kernel.yml — sysctl Kernel Parameter Hardening

roles/server_hardening/tasks/kernel.yml
---
- name: Define CIS L2 mandatory kernel hardening parameters
  ansible.builtin.set_fact:
    cis_sysctl_params:
      # Network: disable IP forwarding (servers are not routers)
      net.ipv4.ip_forward: 0
      # Network: enable reverse path filtering (anti-spoofing)
      net.ipv4.conf.all.rp_filter: 1
      net.ipv4.conf.default.rp_filter: 1
      # Network: disable ICMP redirect acceptance
      net.ipv4.conf.all.accept_redirects: 0
      net.ipv4.conf.default.accept_redirects: 0
      net.ipv6.conf.all.accept_redirects: 0
      # Network: disable sending ICMP redirects
      net.ipv4.conf.all.send_redirects: 0
      net.ipv4.conf.default.send_redirects: 0
      # Network: enable SYN flood protection
      net.ipv4.tcp_syncookies: 1
      # Memory: enable ASLR (Address Space Layout Randomization)
      kernel.randomize_va_space: 2
      # Kernel: restrict dmesg to root only
      kernel.dmesg_restrict: 1
      # Kernel: restrict perf events to privileged users
      kernel.perf_event_paranoid: 3
      # Kernel: restrict ptrace to parent processes only
      kernel.yama.ptrace_scope: 1
      # Network: log suspicious martian packets
      net.ipv4.conf.all.log_martians: 1

- name: Merge tier-specific extra sysctl params with CIS baseline
  ansible.builtin.set_fact:
    all_sysctl_params: "{{ cis_sysctl_params | combine(extra_sysctl_params | default({})) }}"

- name: Apply each sysctl parameter persistently
  ansible.posix.sysctl:
    name: "{{ item.key }}"
    value: "{{ item.value }}"
    state: present
    sysctl_file: /etc/sysctl.d/99-securebank-hardening.conf
    reload: true
    ignoreerrors: false
  loop: "{{ all_sysctl_params | dict2items }}"
  loop_control:
    label: "{{ item.key }} = {{ item.value }}"
  register: sysctl_results
  notify: Reload sysctl

- name: Append kernel hardening result to tracking list
  ansible.builtin.set_fact:
    hardening_results: >-
      {{ hardening_results + [{
        'category': 'kernel',
        'control': item.item.key,
        'expected': item.item.value | string,
        'status': 'applied' if item.changed else 'already_compliant',
        'changed': item.changed
      }] }}
  loop: "{{ sysctl_results.results }}"
  loop_control:
    label: "{{ item.item.key }}"

Line-by-Line Explanation
sysctl_file: /etc/sysctl.d/99-securebank-hardening.conf — Rather than editing the main /etc/sysctl.conf (which may be managed by other tools or packages), we write all hardening parameters to a dedicated drop-in file with the 99- prefix. Drop-in files in /etc/sysctl.d/ are loaded in alphanumeric order, with higher-numbered files taking precedence — our 99- prefix ensures our security settings override any conflicting defaults from package-installed sysctl files.
reload: true on ansible.posix.sysctl — Immediately applies the parameter to the running kernel (not just writing the file) without requiring a reboot. This is what makes kernel parameter hardening effective for already-running servers — the change takes effect at the next task execution, not just on next boot.
net.ipv4.ip_forward: 0 — Disables IP packet forwarding (the server won't route packets between interfaces). This was the pen test Finding 3 scenario: Docker Swarm left this at 1, enabling the server to route packets between network segments — a critical control in PCI-DSS network segmentation.
kernel.randomize_va_space: 2 — Full ASLR (Address Space Layout Randomization) — randomizes the memory addresses of stack, heap, and libraries on every execution, making memory-based exploits (buffer overflow, return-oriented programming) significantly harder. Value 2 = full randomization (value 1 = partial, 0 = disabled).
combine(extra_sysctl_params | default({})) — Merges the CIS L2 baseline dict with any tier-specific additions from group_vars (DMZ tier adds extra IPv6 disable and martian logging). This is cleaner than multiple set_fact calls and ensures tier additions never accidentally override CIS baseline values (combine only adds new keys).
hardening_results + [{ 'category': 'kernel', ... 'changed': item.changed }] — Appending to the tracking list after every sysctl operation. The item.changed flag from the sysctl results tells us whether this was a drift correction (changed=true) or already compliant (changed=false). The compliance report distinguishes these — a server with all changed=false is "in compliance"; one with changed=true had drift that was just corrected.

Task: selinux.yml — SELinux Enforcing Mode

roles/server_hardening/tasks/selinux.yml
---
- name: Check current SELinux runtime mode
  ansible.builtin.command: getenforce
  register: selinux_runtime_mode
  changed_when: false

- name: Check SELinux config file mode (persistent setting)
  ansible.builtin.shell: grep '^SELINUX=' /etc/selinux/config | cut -d= -f2
  register: selinux_config_mode
  changed_when: false

- name: Record pre-remediation SELinux state for report
  ansible.builtin.set_fact:
    selinux_pre_state:
      runtime: "{{ selinux_runtime_mode.stdout }}"
      config: "{{ selinux_config_mode.stdout }}"

- name: Set SELinux config to enforcing (persistent across reboots)
  ansible.posix.selinux:
    policy: "{{ selinux_policy }}"
    state: "{{ selinux_state }}"
  register: selinux_set_result
  notify: >-
    {{ 'Trigger SELinux relabel' if selinux_set_result.reboot_required | default(false) else 'No-op' }}

- name: Set reboot_required flag if SELinux mode change needs relabel
  ansible.builtin.set_fact:
    reboot_required: true
  when: selinux_set_result.reboot_required | default(false)

- name: Set SELinux to enforcing at runtime immediately (without reboot)
  ansible.builtin.command: setenforce 1
  when:
    - selinux_runtime_mode.stdout | lower != 'enforcing'
    - not selinux_set_result.reboot_required | default(false)
  changed_when: true
  register: setenforce_result

- name: Verify SELinux is now enforcing at runtime
  ansible.builtin.command: getenforce
  register: selinux_verify
  changed_when: false

- name: Fail if SELinux is not enforcing after remediation
  ansible.builtin.fail:
    msg: >-
      CRITICAL: SELinux is still {{ selinux_verify.stdout }} on {{ inventory_hostname }}
      after remediation attempt. Manual investigation required.
      This may indicate a kernel compiled without SELinux support.
  when: selinux_verify.stdout | lower != 'enforcing'

- name: Append SELinux result to hardening tracking list
  ansible.builtin.set_fact:
    hardening_results: >-
      {{ hardening_results + [{
        'category': 'selinux',
        'control': 'SELINUX=enforcing',
        'pre_state': selinux_pre_state.runtime,
        'post_state': selinux_verify.stdout,
        'status': 'corrected' if selinux_pre_state.runtime | lower != 'enforcing' else 'compliant',
        'reboot_required': selinux_set_result.reboot_required | default(false)
      }] }}
Line-by-Line Explanation
ansible.posix.selinux module vs manual setenforce — The selinux module sets BOTH the runtime mode AND the config file in one operation, and crucially it knows whether a relabel is required (when transitioning from disabled to enforcing — all filesystem labels must be verified). The module sets reboot_required=true in this case. Manual setenforce 1 only changes the runtime mode, leaving the config file unchanged — servers would revert to permissive on next reboot.
setenforce 1 for runtime-only change — When the config file already has SELINUX=enforcing but the runtime mode is permissive (Pen Test Finding 1 scenario: engineer ran setenforce 0 and never ran setenforce 1 again), we can fix the runtime mode immediately without a reboot. No relabel needed since the config was never set to disabled — just permissive runtime.
reboot_required: true fact — Set when transitioning from disabled to enforcing (full relabel needed). This flag propagates to the master playbook's final stage, which checks if any host has reboot_required: true and either schedules a reboot (if reboot_if_required: true is set) or raises an approval node for the operations team to schedule the reboot during a maintenance window.

Task: firewalld.yml — Zone-Based Firewall Policy

roles/server_hardening/tasks/firewalld.yml
---
- name: Ensure firewalld is installed and running
  ansible.builtin.systemd:
    name: firewalld
    state: started
    enabled: true

- name: Set default firewalld zone to drop (deny-all by default)
  ansible.posix.firewalld:
    zone: drop
    state: enabled
    permanent: true
    immediate: true
  notify: Reload firewalld

- name: Set drop as the default zone for all unconfigured interfaces
  ansible.builtin.command: firewall-cmd --set-default-zone=drop
  changed_when: true
  register: default_zone_result

- name: Allow explicitly configured ports for this host tier
  ansible.posix.firewalld:
    zone: drop
    port: "{{ item.port }}/{{ item.protocol }}"
    source: "{{ item.source | default(omit) }}"
    state: enabled
    permanent: true
    immediate: true
  loop: "{{ firewalld_allowed_ports | default([]) }}"
  loop_control:
    label: "{{ item.port }}/{{ item.protocol }} from {{ item.source | default('any') }}"
  notify: Reload firewalld

- name: Allow explicitly configured services (by name) for this tier
  ansible.posix.firewalld:
    zone: drop
    service: "{{ item }}"
    state: enabled
    permanent: true
    immediate: true
  loop: "{{ firewalld_allowed_services | default([]) }}"
  notify: Reload firewalld

- name: Remove any default services enabled in the drop zone (cleanup)
  ansible.posix.firewalld:
    zone: drop
    service: "{{ item }}"
    state: disabled
    permanent: true
    immediate: true
  loop:
    - ssh               # SSH is controlled via source-based rule above, not service
    - dhcpv6-client     # Not needed on hardened servers
  failed_when: false    # OK if these aren't currently enabled

- name: Verify firewalld default zone is drop
  ansible.builtin.command: firewall-cmd --get-default-zone
  register: default_zone_check
  changed_when: false

- name: Append firewalld result to tracking list
  ansible.builtin.set_fact:
    hardening_results: >-
      {{ hardening_results + [{
        'category': 'firewalld',
        'control': 'default_zone=drop',
        'status': 'compliant' if default_zone_check.stdout == 'drop' else 'FAILED',
        'allowed_ports': firewalld_allowed_ports | default([]) | length
      }] }}
Line-by-Line Explanation
zone: drop as default — The drop zone silently discards all packets not matching an explicit rule (no ICMP port-unreachable response). This is more secure than the public zone (which allows some services by default) or reject (which still responds with ICMP unreachable, revealing the server's existence). Every banking server should default to drop and explicitly allow only what's needed.
source: "{{ item.source }}" on port rules — Rather than just allowing port 8443/tcp from everywhere, we combine port + source subnet. Only the load-balancer subnet (10.10.1.0/24) can reach port 8443 on CDE app servers. This implements the PCI-DSS Req 1.3 network segmentation requirement at the host firewall level — a defence-in-depth layer that remains effective even if a network-level firewall is misconfigured.
permanent: true + immediate: true — Both flags together: permanent: true writes the rule to the firewalld configuration files (survives reboot), immediate: true applies it to the running firewall right now (takes effect without firewall-cmd --reload). Without immediate, the rule exists in config but not in the running firewall until the next reload/reboot.
Removing default services (ssh, dhcpv6-client) from drop zone — The firewalld drop zone has no pre-configured allowed services by default, but to be safe we explicitly disable any that might have been added manually. SSH access is controlled via the explicit source-based port rule (jump-host only), not the default ssh service rule which allows from any source.

Task: crypto.yml — System-wide Crypto Policy (FIPS 140-2)

roles/server_hardening/tasks/crypto.yml
---
- name: Check current system-wide crypto policy
  ansible.builtin.command: update-crypto-policies --show
  register: current_crypto_policy
  changed_when: false

- name: Record pre-state for report
  ansible.builtin.set_fact:
    pre_crypto_policy: "{{ current_crypto_policy.stdout | trim }}"

- name: Apply target crypto policy (FIPS or FUTURE based on tier)
  ansible.builtin.command: "update-crypto-policies --set {{ crypto_policy }}"
  register: crypto_policy_result
  changed_when: "'Setting system policy to' in crypto_policy_result.stdout"
  when: current_crypto_policy.stdout | trim | upper != crypto_policy | upper

- name: Flag reboot required after FIPS mode activation
  ansible.builtin.set_fact:
    reboot_required: true
  when:
    - crypto_policy | upper == 'FIPS'
    - crypto_policy_result is changed

- name: Enable FIPS mode at kernel level (FIPS requires kernel boot param)
  ansible.builtin.command: fips-mode-setup --enable
  register: fips_kernel_result
  changed_when: "'FIPS mode will be enabled' in fips_kernel_result.stdout"
  when:
    - crypto_policy | upper == 'FIPS'
    - current_crypto_policy.stdout | trim | upper != 'FIPS'

- name: Append crypto policy result to tracking list
  ansible.builtin.set_fact:
    hardening_results: >-
      {{ hardening_results + [{
        'category': 'crypto',
        'control': 'system_crypto_policy',
        'expected': crypto_policy,
        'pre_state': pre_crypto_policy,
        'post_state': crypto_policy | upper,
        'status': 'corrected' if (crypto_policy_result is defined and crypto_policy_result is changed) else 'compliant',
        'reboot_required': reboot_required
      }] }}
Line-by-Line Explanation
update-crypto-policies — A RHEL 8/9 exclusive utility that sets a system-wide cryptographic policy affecting OpenSSL, GnuTLS, NSS, and OpenSSH simultaneously in a single command. Without this, each application would need individual cipher configuration. The policies are: DEFAULT (RHEL baseline), FUTURE (no SHA-1, TLS 1.2+ only), FIPS (FIPS 140-2 validated — kernel-enforced, requires reboot).
crypto_policy | upper == 'FIPS' — FIPS mode is unique: it requires not just the software policy change but also a kernel boot parameter (fips=1) and potentially a FIPS-validated kernel module check. This is why FIPS always sets reboot_required: true — the kernel change only takes effect after reboot. CDE tier uses FIPS; production app tier uses FUTURE (which is strong but doesn't require a reboot for new installs).
fips-mode-setup --enable — The RHEL utility that enables FIPS at the kernel level by modifying the GRUB configuration to add fips=1 to the kernel command line. This is the step that requires a reboot. It also verifies that the running kernel is FIPS-capable before making the change.

Task: grub.yml — Bootloader Password Protection

roles/server_hardening/tasks/grub.yml
---
- name: Set GRUB superuser and password hash in /etc/grub.d/40_custom
  ansible.builtin.blockinfile:
    path: /etc/grub.d/40_custom
    block: |
      set superusers="grub_admin"
      password_pbkdf2 grub_admin {{ vault_grub_password_hash }}
    marker: "# {mark} ANSIBLE MANAGED GRUB PASSWORD"
    create: true
    mode: '0755'
  register: grub_password_set

- name: Restrict GRUB config file permissions to root-only
  ansible.builtin.file:
    path: /boot/grub2/grub.cfg
    owner: root
    group: root
    mode: '0600'

- name: Regenerate GRUB config to include superuser settings
  ansible.builtin.command: grub2-mkconfig -o /boot/grub2/grub.cfg
  when: grub_password_set.changed
  register: grub_mkconfig_result

- name: Verify GRUB config contains superusers entry
  ansible.builtin.command: grep -c 'superusers' /boot/grub2/grub.cfg
  register: grub_verify
  changed_when: false
  failed_when: grub_verify.stdout | int == 0
Line-by-Line Explanation
vault_grub_password_hash — The GRUB password is stored as a PBKDF2 hash (generated by grub2-mkpasswd-pbkdf2) in Ansible Vault — never as plaintext. The hash is applied to /etc/grub.d/40_custom which is a script that generates GRUB config fragments. The actual plaintext password is only known to the security team and is stored in CyberArk PAM.
ansible.builtin.blockinfile with marker — Instead of templating the entire GRUB custom file (which might have legitimate existing content), we use blockinfile with an Ansible-managed marker block. This inserts our security block idempotently without destroying other existing content in 40_custom — and on re-runs, it updates only the managed block, not the whole file.
grub2-mkconfig runs when: grub_password_set.changed — GRUB config regeneration is expensive and changes the bootloader config file (a sensitive operation). We only regenerate when something actually changed — idempotent application of an already-correct GRUB config should not regenerate it on every run.
CIS 1.5 Rationale — GRUB password protection prevents an attacker with physical (or console) access from editing kernel boot parameters (e.g., adding init=/bin/bash to bypass authentication, or enforcing=0 to disable SELinux) at the GRUB menu. In a data center with iDRAC/IPMI console access, this control is a relevant defence-in-depth layer.

🎯 16. Interview Preparation

Scenario-Based Questions

Q: A developer says SELinux breaks their app — they need it disabled. How do you respond?
SELinux being disabled is never the correct fix. The application is doing something the policy doesn't allow — the correct fix is to write a targeted SELinux policy module using audit2allow from the AVC denials in /var/log/audit/audit.log. The weekly hardening correction re-enables SELinux regardless. If there is a genuine short-term need, InfoSec can approve SELinux permissive mode (not disabled) time-boxed to 48 hours with a Jira ticket — never a permanent disable. The weekly run corrects it back to enforcing automatically.
Q: How do you apply hardening without breaking running applications?
Three safety mechanisms: (1) Tag-based execution — non-disruptive tags (sysctl, banner, cron) run freely; service-impacting tags (firewalld, ssh) run only in maintenance windows. (2) Handlers fire only on change — an already-hardened server sees zero service restarts. (3) The drift detect (check_mode) → human review → approval → correct workflow gives app teams visibility before any change lands on production servers.
Q: A kernel update overwrites your sysctl settings — how does automation handle this?
Package updates only overwrite files they own. Our parameters live in /etc/sysctl.d/99-securebank-hardening.conf — outside any RPM's ownership. The 99- prefix ensures we take precedence over package-installed lower-numbered sysctl files. The weekly drift detection catches any override on the next Sunday run. As an extra guard, we also check the running kernel value (not just the file) with sysctl -n <param> to detect discrepancies even if the file is correct.

Architecture & Production Questions

Q: What is the difference between FIPS 140-2 and the FUTURE crypto policy in RHEL?
FUTURE is a RHEL-defined policy disabling SHA-1, RC4, DES, and requiring TLS 1.2+ — strong modern cryptography but not government-validated, and does not require a reboot. FIPS 140-2 requires only NIST-validated cryptographic modules enforced at the kernel level, with the kernel verifying module integrity at boot — this requires a reboot and kernel parameter change. CDE servers require FIPS (PCI-DSS Req 4.2.1); non-CDE production servers use FUTURE as a strong, reboot-free alternative.
Q: CIS Benchmark has 300+ controls — which ones do you implement in Ansible vs other tools?
Three-category framework: (1) OS-level configuration controls (sysctl, file permissions, service state, SELinux) — Ansible, because they're idempotent and use the same toolchain as everything else. (2) Application-level controls (database hardening, middleware) — dedicated roles per application, separate from the OS hardening role. (3) Policy/process controls (physical security, user awareness) — non-automatable, handled outside Ansible. OpenSCAP (Project 3) scans for gaps we don't cover in Ansible, giving fleet-wide visibility of any remaining CIS controls not yet automated.
Q: How does your role handle dev tier servers that need looser controls?
The hardening_profile: cis-l1 in dev tier group_vars controls which sysctl params are applied (L1 is a subset of L2), and firewalld_allowed_ports in dev group_vars allows broader access. The same role code runs on all tiers — different variable values produce different outcomes. Dev servers are still hardened (L1 baseline), not as strict as production CDE — satisfying internal policy while allowing development flexibility. No code branching: pure variable-driven behaviour.

📝 17. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Hardening must be applied at Day-0 AND enforced continuously — Day-0 alone is insufficient because drift happens every day through troubleshooting, package updates, and application installs.
  • sysctl_file: /etc/sysctl.d/99-securebank-hardening.conf is more robust than /etc/sysctl.conf — package updates never overwrite files they don't own.
  • SELinux permissive mode is more dangerous than many engineers realize — it still incurs AVC logging overhead but provides zero access control protection.
  • check_mode drift detect → human review → approve correction is essential — production fleets need impact assessment before blanket change application.

Common Mistakes

  • Applying hardening changes on running production without a maintenance window — SSH reload and firewalld reload interrupt active connections.
  • Setting default firewalld zone to public instead of drop — public allows several services by default, violating the deny-all baseline.
  • Forgetting reload: true on sysctl tasks — parameters written to file but not live-applied until next reboot.
  • Using permanent: true without immediate: true on firewalld — rules in config but not in running firewall.

Production Best Practices

  • Always run drift detect (check mode) and require human approval before correction — unexpected drift items in the list can cascade application failures if applied blindly.
  • Use tags liberally — re-running only --tags selinux,kernel post-pen-test without touching SSH or firewalld is a critical operational safety feature.
  • Separate the reboot decision into its own approval node — a reboot is irreversible and deserves explicit, separate authorization beyond the general correction approval.
  • Integrate the hardening role into the provisioning pipeline — Day-0 hardening must be non-negotiable; no server joins the fleet without passing it.

Resume Points

  • Designed and implemented a CIS Benchmark Level 2 server hardening automation role using Ansible AAP across a 400-server RHEL banking fleet, covering 12 control categories (sysctl, SELinux, firewalld, FIPS 140-2, GRUB, SSH, core dumps) with tier-aware profiles for CDE, production, DMZ, and development environments.
  • Built a weekly hardening drift detection and correction pipeline in check_mode→approval→correct pattern, detecting and auto-remediating configuration drift within 7 days — reducing PCI-DSS pen test findings from 11 hardening-related controls to zero in the following year's assessment cycle.
  • Integrated Day-0 server hardening as a mandatory pre-flight gate in all server provisioning workflows, ensuring every new server achieves CIS L2 compliance before any application workload is deployed — establishing a secure-by-default posture across SecureBank's entire infrastructure fleet.
