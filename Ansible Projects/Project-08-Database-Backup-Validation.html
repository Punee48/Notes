Project 8: Database Backup Validation Automation using Red Hat AAP

SecureBank runs Oracle RAC 19c for its Core Banking System (CBS), PostgreSQL 15 for its Payment Gateway and Digital Onboarding Portal, and Oracle 19c for NACH and Trade Finance — totalling 18 production databases across Mumbai DC and Chennai DR. RMAN, Data Pump, and pg_dump jobs run nightly producing backup sets. But "backup completed" in the scheduler log does NOT mean the backup is valid, restorable, or compliant. SecureBank discovered this the hard way during a DR drill: the RMAN backup that had been "succeeding" for 6 months was writing to a mount point that had silently unmounted — the backup files were zero bytes being written to local disk. This project automates end-to-end backup validation: backup file existence and size checks, RMAN VALIDATE, pg_restore dry-run, checksum integrity, restore-to-sandbox testing, RTO verification, and a compliance report — all orchestrated through Red Hat AAP and running every morning after the nightly backup window closes.

🏦 2. Real-Time Banking Scenario

The Story — Part 1 (Before Automation — The DR Drill Disaster): SecureBank's annual RBI-mandated DR drill is scheduled for a Saturday in April. The DBA team is confident — RMAN backup jobs have shown "Status: SUCCESS" in Oracle EM for 6 months without exception. At 9 AM on drill day, they initiate a restore of the CBS database to the DR Oracle RAC cluster. At 11 AM, the restore fails: the RMAN catalog shows backup pieces, but when RMAN tries to actually read the backup files from the designated NFS backup mount, every file is 0 bytes. Investigation reveals that 6 months ago, the NFS mount point silently unmounted after a storage team maintenance activity, and RMAN continued writing to the local stub directory — producing zero-byte files with valid RMAN catalog entries. 6 months of backups: completely worthless. The RBI inspector observes the failed drill. A written letter of non-compliance follows. The CISO's Monday morning is not pleasant.

Part 2 (After Automation): The same drill happens the following April. This time, the AAP-driven backup validation job runs at 6 AM every morning. The morning after the NFS unmount (which happens on the same Saturday as last year), the 6:00 AM validation job fires: backup files found, but sizes are all 0 bytes → immediate P1 PagerDuty alert fires at 6:08 AM. The storage team re-mounts NFS by 6:45 AM, RMAN re-runs an incremental, and by 9 AM the DR drill proceeds with a verified backup. The RBI inspector sees the alert, the rapid response, and the successful restore — it becomes a demonstration of mature backup governance rather than a catastrophic gap.

❗ 3. Problem Statement

  • Backup scheduler logs report "SUCCESS" even when the actual backup files are missing, zero-byte, or written to the wrong location — no file-level validation in the backup job itself.
  • RMAN VALIDATE (which actually reads backup blocks and checks checksums) is never run — only RMAN BACKUP is scheduled.
  • No automated restore-to-sandbox test — the only restore validation is the annual DR drill, which historically has uncovered critical failures too late.
  • No RPO tracking — nobody knows if last night's backup is within the 1-hour RPO for CBS until a restore is needed and someone checks the RMAN catalog manually.
  • Backup encryption not validated — files might exist and be the right size but unencrypted, violating PCI-DSS Req 3.5.
  • DR site backup copy not verified — the primary NFS backup exists, but whether it was successfully replicated to the Chennai DR site is unknown until a DR incident occurs.
  • No QSA-grade evidence — a scheduler "SUCCESS" log is not proof of a tested, restorable backup — PCI-DSS Req 12.3.4 specifically requires evidence of periodic restore testing.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. DBA checks Oracle Enterprise Manager dashboard — if backup job shows green, it's assumed good.
  2. Once a month (sometimes skipped), a DBA manually logs into the Oracle RAC node and runs rman target / followed by LIST BACKUPSET to confirm backup pieces are registered in the RMAN catalog.
  3. No file-level check — the RMAN catalog entry exists but whether the actual backup file on NFS is readable is never verified outside a DR drill.
  4. For PostgreSQL, a DBA occasionally runs pg_dump manually and checks the exit code — the dump file is not actually tested with pg_restore.
  5. DR site copy: assumed to work based on the NFS replication schedule — never independently verified.
  6. Restore test: only during annual DR drill — results documented in a Word document that sometimes lacks timestamps or specific metrics.

🛠️ 6. Automated Solution Design

The backup validation pipeline runs in four independently schedulable phases:

  • Phase 1 — Daily Backup Integrity Check (6:00 AM daily): For each database, verify backup files exist on both primary NFS and DR NFS paths, are non-zero in size, were created within the RPO window, have correct file permissions, and for RMAN backups: run RMAN VALIDATE BACKUPSET to actually read every block and confirm no corruption. For PostgreSQL: run pg_restore --list (dry-run, no actual restore) to confirm the dump file is structurally valid. Fire P1 alert on any failure — these are morning checks that must complete before business hours.
  • Phase 2 — Encryption Verification (daily, runs after Phase 1): For RMAN: query the RMAN catalog for encryption algorithm and wallet status. For PostgreSQL: check for .gpg extension or verify file header magic bytes. Any unencrypted backup in a CDE database triggers a P1 alert and auto-raises a ServiceNow incident (PCI-DSS violation).
  • Phase 3 — Monthly Sandbox Restore Test (1st Sunday each month, 00:00 IST): Restore the most recent full backup to a designated sandbox Oracle/PostgreSQL instance, measure restore duration (RTO validation), run a set of SQL smoke-test queries against the restored data to confirm logical consistency (not just structural restore), then drop the sandbox database. Full timing and result metrics included in the monthly report.
  • Phase 4 — Compliance Report Generation: Consolidates all validation results into a per-database compliance report (JSON + CSV) archived to the compliance NFS share and automatically emailed to the CISO, DBA lead, and the QSA's secure evidence portal.

⚙️ 8. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.builtin.stat, ansible.builtin.find, ansible.builtin.shell, ansible.builtin.command, ansible.builtin.uri, ansible.builtin.template
  • Roles: backup_file_check, backup_rman_validate, backup_pgsql_validate, backup_encrypt_check, backup_sandbox_restore, backup_report
  • Ansible Vault: Oracle RMAN catalog credentials, PostgreSQL superuser password, AWS S3 keys, sandbox DB passwords
  • no_log: true on all DB credential tasks
  • Jinja2 templates for RMAN scripts, pg_restore commands, SQL smoke test scripts, compliance CSV/JSON
  • Per-database block/rescue/always: rescue captures error context; always generates the partial report even on failure

Red Hat AAP Components

  • Execution Environment: Custom EE with Oracle Instant Client, cx_Oracle Python library, psycopg2, aws-cli
  • Credentials: Custom credential types for Oracle RMAN (TNS string + sysdba password), PostgreSQL superuser, AWS S3 (for backup copy verification), Vault credential for all DB passwords
  • Job Templates: DB-Backup-Integrity-Daily, DB-Backup-Encrypt-Check, DB-Sandbox-Restore-Monthly, DB-Backup-Compliance-Report
  • Workflow: DB-Backup-Validation-Full (chains all 4 phases; Phase 3 only on monthly trigger)
  • Schedule: Daily 06:00 IST (Phases 1+2+4); Monthly 1st Sunday 00:00 IST (Phase 3)
  • Notification: PagerDuty P1 on backup failure/encryption missing; Email to DBA + CISO on monthly restore report

Role: backup_file_check — File Existence, Size, Age & DR Copy Verification

roles/backup_file_check/tasks/main.yml
---
- name: Find most recent backup file on primary NFS path
  ansible.builtin.find:
    paths: "{{ backup_primary_path }}"
    patterns: "{{ backup_pattern | default('*') }}"
    age_stamp: mtime
    file_type: file
    recurse: false
  register: primary_backup_files

- name: Identify the newest backup file by modification time
  ansible.builtin.set_fact:
    latest_backup_file: >-
      {{ (primary_backup_files.files | sort(attribute='mtime', reverse=true) | first)
         if primary_backup_files.files | length > 0
         else {} }}

- name: Fail if no backup files found at all
  ansible.builtin.fail:
    msg: >-
      CRITICAL: No backup files found at {{ backup_primary_path }}
      for database {{ db_name }} on {{ inventory_hostname }}.
      Last known backup location is empty — possible NFS unmount or backup job failure.
  when: primary_backup_files.files | length == 0

- name: Fail if most recent backup file is below minimum size threshold
  ansible.builtin.fail:
    msg: >-
      CRITICAL: Latest backup file {{ latest_backup_file.path | basename }}
      is only {{ latest_backup_file.size }} bytes (minimum: {{ backup_min_size_bytes }}).
      This is likely a zero-byte file written when NFS was unmounted.
  when: latest_backup_file.size | int < backup_min_size_bytes | int

- name: Calculate backup age in hours
  ansible.builtin.set_fact:
    backup_age_hours: >-
      {{ ((ansible_date_time.epoch | int) - (latest_backup_file.mtime | int)) / 3600
         | round(2) | float }}

- name: Fail if backup is older than RPO + buffer threshold
  ansible.builtin.fail:
    msg: >-
      CRITICAL: Latest backup for {{ db_name }} is {{ backup_age_hours }} hours old.
      RPO target is {{ rpo_hours }} hours (with {{ backup_age_check_buffer_hours }}h buffer).
      Max allowed age: {{ rpo_hours | int + backup_age_check_buffer_hours | int }} hours.
      Backup job may have silently failed.
  when: >-
    backup_age_hours | float >
    (rpo_hours | int + backup_age_check_buffer_hours | int)

- name: Verify backup copy exists on DR NFS path
  ansible.builtin.stat:
    path: "{{ backup_dr_path }}/{{ latest_backup_file.path | basename }}"
  register: dr_copy_stat
  delegate_to: localhost

- name: Warn if DR copy is missing (not fail — may still be replicating)
  ansible.builtin.debug:
    msg: >-
      WARNING: DR copy of {{ latest_backup_file.path | basename }}
      not found at {{ backup_dr_path }}. Either replication is lagging
      or DR copy job failed. Flagging for report — no P1 until confirmed missing for > 2 hours.
  when: not dr_copy_stat.stat.exists

- name: Verify DR copy size matches primary (detect partial replication)
  ansible.builtin.fail:
    msg: >-
      CRITICAL: DR copy size mismatch for {{ db_name }}.
      Primary: {{ latest_backup_file.size }} bytes,
      DR copy: {{ dr_copy_stat.stat.size }} bytes.
      Replication may be truncated or corrupt.
  when:
    - dr_copy_stat.stat.exists
    - dr_copy_stat.stat.size | int != latest_backup_file.size | int

- name: Verify backup exists in S3 (offsite copy — 3-2-1 rule)
  ansible.builtin.command: >
    aws s3 ls s3://{{ backup_s3_bucket }}/{{ backup_s3_prefix }}/{{ latest_backup_file.path | basename }}
    --region ap-south-1
  register: s3_check
  changed_when: false
  failed_when: false
  environment:
    AWS_ACCESS_KEY_ID: "{{ vault_aws_access_key }}"
    AWS_SECRET_ACCESS_KEY: "{{ vault_aws_secret_key }}"
  delegate_to: localhost
  no_log: true

- name: Set backup file check status as host fact
  ansible.builtin.set_fact:
    backup_file_status:
      latest_file: "{{ latest_backup_file.path | basename }}"
      size_bytes: "{{ latest_backup_file.size }}"
      age_hours: "{{ backup_age_hours }}"
      rpo_hours: "{{ rpo_hours }}"
      rpo_ok: "{{ backup_age_hours | float <= rpo_hours | int + backup_age_check_buffer_hours | int }}"
      primary_ok: true
      dr_copy_exists: "{{ dr_copy_stat.stat.exists }}"
      dr_size_match: "{{ dr_copy_stat.stat.size | int == latest_backup_file.size | int if dr_copy_stat.stat.exists else false }}"
      s3_copy_exists: "{{ s3_check.rc == 0 }}"
Line-by-Line Explanation
sort(attribute='mtime', reverse=true) | first — Sorts the list of backup files by modification time (newest last → reversed → newest first) and selects the first (newest). This avoids relying on filename date sorting which can be unreliable with different naming conventions across Oracle RMAN and pg_dump outputs.
backup_min_size_bytes: 1048576 (1MB minimum) — The zero-byte file scenario from the story: NFS unmounted, RMAN writes to local stub dir, produces 0-byte files with valid RMAN catalog entries. The 1MB threshold catches not just zero-byte files but also suspiciously small backups from truncated writes. A real Oracle RMAN backup piece for a production CBS database should be gigabytes — 1MB minimum is extremely conservative and catches obvious failures without false positives.
RPO age calculation: (ansible_date_time.epoch | int - latest_backup_file.mtime | int) / 3600 — Epoch timestamp arithmetic in Jinja2. Subtracting the file's mtime (Unix epoch when file was last modified/written) from the current epoch gives elapsed seconds; dividing by 3600 gives hours. This is timezone-independent and works correctly regardless of the database server's locale settings.
delegate_to: localhost for DR and S3 checks — The DR NFS path and S3 are checked from the Ansible control node, not from the Oracle server. This simulates a genuine external perspective — if the Oracle server has network access to DR NFS directly (and it shouldn't in a well-segmented network), a server-side check might succeed even when the DR copy isn't independently accessible from the restore target.
dr_copy_stat.stat.size | int != latest_backup_file.size | int — Comparing byte-for-byte sizes detects partial replication (the DR copy exists but is truncated). This catches a scenario common with rsync-based replication where the transfer was interrupted mid-file — the destination file exists but is smaller than the source, meaning restore from DR would fail midway.
no_log: true on S3 check — The AWS credentials are passed as environment variables to the aws CLI command. Without no_log: true, the entire task including the environment dict (containing AWS_SECRET_ACCESS_KEY in plaintext) would appear in the AAP job log.

Role: backup_rman_validate — Oracle RMAN Block-Level Validation

roles/backup_rman_validate/tasks/main.yml
---
- name: Skip RMAN validation for non-Oracle databases
  ansible.builtin.meta: end_host
  when: db_type != 'oracle'

- name: Render RMAN VALIDATE script from template
  ansible.builtin.template:
    src: rman_validate.rcv.j2
    dest: "/tmp/rman_validate_{{ db_name }}.rcv"
    owner: "{{ oracle_user }}"
    group: "{{ oracle_user }}"
    mode: '0600'

- name: Execute RMAN VALIDATE BACKUPSET (actual block-level read and checksum check)
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ db_sid }};
     {{ oracle_home }}/bin/rman
     target /
     catalog {{ vault_rman_catalog_user }}/{{ vault_rman_catalog_pass }}@{{ rman_catalog_tns }}
     cmdfile=/tmp/rman_validate_{{ db_name }}.rcv
     log=/tmp/rman_validate_{{ db_name }}.log"
  register: rman_validate_result
  changed_when: false
  no_log: true

- name: Read RMAN validation log for results
  ansible.builtin.slurp:
    src: "/tmp/rman_validate_{{ db_name }}.log"
  register: rman_log_content

- name: Parse RMAN log for validation failures
  ansible.builtin.set_fact:
    rman_log_text: "{{ rman_log_content.content | b64decode }}"
    rman_errors: >-
      {{ rman_log_content.content | b64decode
         | regex_findall('(ORA-[0-9]+|RMAN-[0-9]+|validation failed)') }}

- name: Fail if RMAN validation found corrupt blocks or errors
  ansible.builtin.fail:
    msg: >-
      CRITICAL: RMAN VALIDATE found errors in backup for {{ db_name }}:
      {{ rman_errors | join(', ') }}.
      Full log: {{ rman_log_text | truncate(2000) }}
  when: rman_errors | length > 0

- name: Check RMAN encryption status from catalog
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ db_sid }};
     {{ oracle_home }}/bin/sqlplus -S /nolog << 'EOF'
     CONNECT {{ vault_rman_catalog_user }}/{{ vault_rman_catalog_pass }}@{{ rman_catalog_tns }}
     SELECT DISTINCT encrypted
     FROM rc_backup_piece
     WHERE db_name = '{{ db_name }}'
     AND completion_time > SYSDATE - 2;
     EXIT;
EOF"
  register: rman_encryption_check
  changed_when: false
  no_log: true

- name: Set RMAN validation status as host fact
  ansible.builtin.set_fact:
    rman_validation_status:
      validated: true
      errors: "{{ rman_errors }}"
      encrypted: "{{ 'YES' in rman_encryption_check.stdout | upper }}"
      validate_timestamp: "{{ ansible_date_time.iso8601 }}"

- name: Clean up temporary RMAN script and log files
  ansible.builtin.file:
    path: "{{ item }}"
    state: absent
  loop:
    - "/tmp/rman_validate_{{ db_name }}.rcv"
    - "/tmp/rman_validate_{{ db_name }}.log"
roles/backup_rman_validate/templates/rman_validate.rcv.j2
# RMAN Validation Script — Generated by Ansible AAP
# Database: {{ db_name }} | Validated at: {{ ansible_date_time.iso8601 }}
# Purpose: Validate most recent backup set for block corruption

CONFIGURE DEVICE TYPE DISK PARALLELISM 4 BACKUP TYPE TO BACKUPSET;

VALIDATE BACKUPSET
  (SELECT DISTINCT bs.recid
   FROM v$backup_set bs
   WHERE bs.completion_time = (
     SELECT MAX(completion_time)
     FROM v$backup_set
     WHERE backup_type IN ('D', 'I')
   )
  );

LIST FAILURE;
EXIT;
Line-by-Line Explanation
VALIDATE BACKUPSET vs BACKUP VALIDATE — Two different RMAN commands. BACKUP VALIDATE reads the datafiles from the database and checks if they could be backed up. VALIDATE BACKUPSET reads the actual existing backup pieces and validates their block checksums — confirming the backup files themselves are readable and uncorrupted. We want VALIDATE BACKUPSET because we're validating the backup artifact, not testing a new backup.
CONFIGURE DEVICE TYPE DISK PARALLELISM 4 — Runs the validation using 4 parallel RMAN channels, significantly speeding up validation of large backup sets. Without this, RMAN uses a single channel by default, which for a multi-GB CBS backup could take hours. For morning validation that must complete before 8 AM business hours, parallelism is critical.
su - {{ oracle_user }} -c "..." — RMAN must run as the Oracle software owner (typically the oracle OS user), not as root or the ansible service account. The su - (with hyphen for full login environment) ensures ORACLE_HOME and other Oracle environment variables are available. Alternative in newer deployments: use become_user: oracle with become: true in Ansible — cleaner but requires sudoers entry for the ansible user to become oracle.
regex_findall('(ORA-[0-9]+|RMAN-[0-9]+|validation failed)') — Extracts Oracle error codes from the RMAN log. ORA- errors are Oracle database errors; RMAN- errors are RMAN-specific. The regex captures all numeric error codes in one expression. If the list is empty, validation was clean; any entry means a corrupt block or I/O error was found.
LIST FAILURE at the end of the RMAN script — RMAN's Data Recovery Advisor automatically records any detected data failures. Running LIST FAILURE forces RMAN to check its failure catalog and include any known issues in the output, ensuring the log captures both validation findings AND any pre-existing failures DRA has detected.

  ansible.builtin.set_fact:
    latest_pg_dump: >-
      {{ (pg_backup_files.files | sort(attribute='mtime', reverse=true) | first).path
         if pg_backup_files.files | length > 0 else '' }}

- name: Run pg_restore dry-run (--list flag — parses dump structure without restoring)
  ansible.builtin.shell: >
    PGPASSWORD={{ vault_pg_superuser_pass }}
    pg_restore
    --list
    --username={{ pg_user }}
    --no-password
    {{ latest_pg_dump }}
  register: pg_restore_list
  changed_when: false
  no_log: true
  failed_when: pg_restore_list.rc != 0

- name: Validate dump file contains expected table of contents entries
  ansible.builtin.assert:
    that:
      - "'TABLE' in pg_restore_list.stdout"
      - "'INDEX' in pg_restore_list.stdout"
    fail_msg: >-
      pg_dump file {{ latest_pg_dump | basename }} appears structurally invalid —
      missing TABLE or INDEX entries in TOC. Dump may be truncated.
    success_msg: "pg_dump file {{ latest_pg_dump | basename }} structural validation PASSED"

- name: Check pg_dump file is not encrypted with missing passphrase (GPG check)
  ansible.builtin.shell: >
    file {{ latest_pg_dump }} | grep -i 'encrypted\|gpg\|PGP'
  register: encryption_check
  changed_when: false
  failed_when: false
  when: latest_pg_dump | regex_search('\.gpg$')

- name: Set PostgreSQL validation status as host fact
  ansible.builtin.set_fact:
    pgsql_validation_status:
      dump_file: "{{ latest_pg_dump | basename }}"
      toc_entries: "{{ pg_restore_list.stdout_lines | length }}"
      structural_ok: "{{ pg_restore_list.rc == 0 }}"
      encrypted: "{{ latest_pg_dump | regex_search('\\.gpg$') | bool }}"
      validate_timestamp: "{{ ansible_date_time.iso8601 }}"
Line-by-Line Explanation
pg_restore --list — The --list flag reads the pg_dump file's Table of Contents (TOC) and prints it without performing any actual restore operations. This is a completely non-destructive structural validation — if the dump file is corrupt or truncated, pg_restore --list fails (non-zero exit code), catching bad dumps without needing a target database. This is the PostgreSQL equivalent of RMAN VALIDATE BACKUPSET.
assert: "'TABLE' in pg_restore_list.stdout" — Even if pg_restore --list exits successfully, we verify the TOC actually contains table definitions. An empty or near-empty dump (e.g., from a failed transaction that was rolled back) might have a valid TOC structure but no real data. Checking for TABLE and INDEX entries ensures the dump contains meaningful database objects.
PGPASSWORD={{ vault_pg_superuser_pass }} — PostgreSQL password passed as an environment variable to the pg_restore command. The alternative (pg_hba.conf peer auth or .pgpass file) requires persistent configuration on the server. Using an environment variable keeps the credential in-process memory, but no_log: true ensures it doesn't appear in the AAP job output.

Line-by-Line Explanation
async: "{{ sandbox_restore_timeout_seconds }}" / poll: 60 — A full database restore can take hours. Without async, Ansible's SSH connection would time out waiting for the task to complete. async launches the task in the background and poll: 60 checks its status every 60 seconds, keeping the SSH session alive throughout the multi-hour restore without risk of connection timeout. The sandbox_restore_timeout_seconds: 14400 (4 hours) gives ample time for even the largest database.
RTO calculation: restore_duration_hours — The start epoch captured in restore_start_epoch (before RMAN runs) and the current epoch after completion gives us precise restore duration in hours. Comparing against rto_hours produces a boolean rto_compliant — the key metric in the monthly compliance report.
SELECT 'SMOKE_TEST_PASS' FROM dual — A sentinel string written at the very end of the SQL script only if all previous anonymous PL/SQL blocks completed without raising exceptions. The Ansible assert checks for this string in the SQL output — a clean, unambiguous pass/fail signal that doesn't require parsing complex query output.
RAISE_APPLICATION_ERROR(-20001, ...) inside PL/SQL — Oracle's mechanism for raising a user-defined exception from PL/SQL. If any smoke test fails (row count below expected minimum), this halts the SQL script with a non-success state, and the SMOKE_TEST_PASS sentinel is never printed — causing the Ansible assert to correctly fail the restore test.
Temp file cleanup with state: absent — RMAN scripts and SQL files can contain catalog credentials embedded in Oracle connection strings. Always clean up temporary files containing credentials, even within the same role that created them. This is especially critical for SQL scripts which contain the sandbox DBA password in the CONNECT string.

🔄 13. Execution Flow — Start to Finish

1
6:00 AM: AAP scheduler fires DB-Backup-Integrity-Daily. Custom EE with Oracle Instant Client and psycopg2 spins up. Vault credentials injected for RMAN catalog and pg superuser.
2
backup_file_check runs for each DB in parallel. For each: find newest file on primary NFS, calculate age vs RPO, size check (catches the zero-byte NFS unmount scenario), stat the DR NFS copy for existence and size match, aws s3 ls for offsite copy.
3
For Oracle databases: RMAN validate script rendered to /tmp, executed via su - oracle. RMAN reads every block in the most recent backup set and checks checksums. Log parsed for ORA-/RMAN- error codes.
4
For PostgreSQL: pg_restore --list run against the newest .dump file. Exit code 0 + TABLE/INDEX presence in TOC = structural validation passed.
5
Encryption check: Oracle queries rc_backup_piece for encrypted column; PostgreSQL checks for .gpg extension. Any unencrypted backup in a PCI-scope database triggers an immediate ServiceNow INC as a PCI-DSS violation.
6
All temp scripts and logs cleaned up from /tmp on remote hosts before play ends. DB credentials never persist in filesystem artifacts.
7
backup_report (run_once): all DB validation records aggregated from hostvars, compliance CSV generated, archived to NFS. PagerDuty fired for any FAIL status with per-DB custom details (age, RPO breach, RMAN errors, encryption status).
8
Monthly (1st Sunday): After daily checks pass and approval node approved: sandbox restore runs serially per database. RMAN restore to sandbox, duration measured, smoke test SQL runs against restored data, SMOKE_TEST_PASS sentinel checked.
9
Monthly report emailed to CISO, DBA lead, and uploaded to the QSA evidence portal — contains RTO actuals (e.g., "CBS restored in 2.4 hours — RTO target 4 hours — COMPLIANT") for each database. This is the PCI-DSS Req 12.3.4 evidence the QSA accepts.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: The RMAN scheduler says "SUCCESS" but RMAN VALIDATE finds corrupt blocks. Which do you trust and why?
RMAN VALIDATE, always. The scheduler's "SUCCESS" only means the backup job process completed without a fatal error — it does NOT mean the resulting backup files are readable or uncorrupted. RMAN VALIDATE actually reads every block from the physical backup files and verifies their checksums against what was written. Corrupt blocks detected during VALIDATE would be undetectable from the job status alone — they only manifest at restore time if not validated proactively. The RMAN scheduler is a job runner; RMAN VALIDATE is a correctness check. They serve fundamentally different purposes.
Q: What is the difference between RPO and RTO, and how does your automation validate both?
RPO (Recovery Point Objective) = maximum acceptable data loss measured in time — how old can the restored data be? We validate RPO by checking the backup file's modification time (mtime) against the current time and the per-database RPO_hours setting. If the backup is older than RPO + buffer, the backup job has missed its schedule and an alert fires. RTO (Recovery Time Objective) = how long the restore should take. We validate RTO by timing the sandbox restore (epoch timestamp before and after RMAN restore completes) and comparing the duration against the rto_hours target. The monthly report shows actual vs target RTO for every database — the key evidence for RBI Business Continuity compliance.
Q: A PCI-DSS auditor asks for evidence that database backups are tested. What do you provide?
The monthly backup compliance report CSV archived to NFS, which contains: restore date, restore duration, RTO vs target, smoke test pass/fail, and the AAP job ID for independent verification. The AAP job output itself (accessible by the QSA via read-only AAP access) shows every step of the restore process with timestamps. PCI-DSS Req 12.3.4 specifically requires "at least once every 12 months" restore testing — our monthly cadence exceeds this, and the report demonstrates 12 documented restore tests per year per database, each with RTO measurement and smoke test validation.

Architecture & Production Questions

Q: How do you handle the Oracle RMAN wallet/keystore for encrypted backups in the validation workflow?
Oracle Transparent Data Encryption (TDE) wallet or Oracle Key Vault must be accessible on the server running RMAN VALIDATE — the same wallet that was used during the backup, or a copy of it. For Ansible, this means the wallet is mounted/accessible in the oracle user's wallet location before RMAN runs. The wallet passphrase is managed via AAP's Vault credential and injected as an environment variable (ORACLE_WALLET_PASS) into the su - oracle shell command — not embedded in the RMAN script itself. Validating the encryption status via rc_backup_piece confirms the wallet is functional and encryption was applied during backup.
Q: Why run async on the sandbox restore task? What are the risks?
Without async, Ansible's SSH connection to the Oracle server would time out (typically 30-60 minutes) waiting for a multi-hour RMAN restore. Async launches the restore as a background process and Ansible polls its completion via a separate SSH command every 60 seconds. The risk: if the Ansible control node loses connectivity during the async job, the restore continues independently but Ansible loses track of its status. Mitigation: set a conservative async timeout (4 hours), and the RMAN log written to /tmp is read by a subsequent task to confirm completion state regardless of the async polling outcome.
Q: How do you validate that the backup copy on DR NFS actually represents a different physical failure domain from primary NFS?
We validate file existence and size parity on the DR NFS path, but physical isolation verification (is this really a different data center?) is outside Ansible's scope — it's a storage architecture concern. What we can add is an IP-level check: if primary NFS is mounted from 10.20.x.x (Mumbai) and DR NFS should be mounted from 10.30.x.x (Chennai), a pre-check can verify the NFS mount source IP falls in the expected subnet. For cloud DR (S3), the region parameter (ap-south-1 for primary, ap-southeast-1 for DR) enforces geographic separation at the S3 API level.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Backup scheduler "SUCCESS" ≠ backup validity. RMAN VALIDATE and pg_restore --list are the only trustworthy validators — they actually read the backup files.
  • Zero-byte files on unmounted NFS are one of the most common backup failures in enterprise environments — and completely invisible to scheduler monitoring.
  • async + poll is essential for long-running RMAN operations — SSH connection timeout is one of the top causes of Ansible task failure for DBA automation.
  • Clean up /tmp after every run — RMAN scripts and SQL files often contain DB credentials embedded in connection strings.

Common Mistakes

  • Using RMAN LIST BACKUPSET instead of VALIDATE BACKUPSET — LIST confirms the catalog entry exists; VALIDATE confirms the file is readable and uncorrupted. They are NOT equivalent.
  • Not checking DR copy independently — checking that the primary backup exists is necessary but not sufficient for 3-2-1 compliance.
  • Running monthly sandbox restores without async — RMAN restores hang Ansible, the SSH timeout kills the play, and the sandbox database is left in a partially restored state.
  • Not validating backup encryption — a backup that exists, is the right size, and is RMAN-validated but unencrypted is a PCI-DSS Req 3.5 violation.

Production Best Practices

  • Always validate both structure (RMAN VALIDATE / pg_restore --list) AND encryption status in the same daily job — they check different failure modes and both are mandatory.
  • Include actual RTO measurements in every monthly report, not just pass/fail — RTO drift (restore taking longer each month as DB grows) is a proactive indicator that DR capacity planning needs attention.
  • Keep the sandbox restore separate from production RMAN catalog — use a duplicate/auxiliary RMAN connection to sandbox, never restore to a target that shares catalog entries with production.
  • Set backup_age_check_buffer_hours conservatively (we use 2 hours) — backup completion time varies based on DB size; a tight buffer generates false positives on large DBs that take longer to backup.

  • Built a monthly sandbox restore automation workflow with RTO measurement and SQL smoke test validation, producing PCI-DSS Req 12.3.4 compliant restore test evidence that replaced manual quarterly DR drills as the primary audit artefact.
