Project 11: Windows Service Recovery Automation & Critical Service Health Monitoring

ABC Global Bank runs dozens of critical Windows services across 650 Windows servers — SQL Server Agent, IIS (W3SVC), MSMQ, Windows Event Log, Distributed Transaction Coordinator (MSDTC), Task Scheduler, and application-specific services like the CBS Windows Service, SWIFT Alliance Connector, and Payment Gateway service. When any of these stops unexpectedly, banking operations halt within minutes. This project automates complete Windows service health monitoring — checking service state, startup type, service account, dependency chain, and event log correlation — with intelligent auto-recovery that handles service dependencies in the correct order, validates recovery success, and escalates when auto-recovery fails.

🏦 1. The Banking Story

Setting: ABC Global Bank's payment processing infrastructure includes 18 Windows Server 2022 nodes running the Payment Gateway Service (PGS) — a critical banking application that processes NEFT, RTGS, and IMPS transactions. Each PGS instance is a Windows service that depends on: MSDTC (Distributed Transaction Coordinator), MSMQ (Message Queuing), SQL Server Agent, and a custom Certificate Management Service (CMS).

Incident 1 — The MSDTC Cascade: At 14:22 on a Wednesday, Windows Update silently restarted MSDTC on pgs-win04 (it had been set to auto-restart by a previous admin). PGS noticed the MSDTC restart after 45 seconds and crashed — throwing "Transaction coordinator has stopped responding." The NOC monitoring showed PGS as "stopped" but the alert email went to a distribution list that included 12 people, nobody of whom was on duty. PGS was down for 47 minutes before a user complaint reached the bank's helpdesk, who then escalated to the Windows team. NEFT processing on pgs-win04 was completely offline for 47 minutes.

Incident 2 — The Wrong Start Order: After a monthly patch reboot, pgs-win07 came back online with PGS attempting to start before MSDTC was fully ready. PGS failed with "MSDTC not available" — and because Windows had configured PGS to "Take No Action" on first failure, it stayed stopped. The Windows team manually started MSDTC first, waited 30 seconds, then manually started PGS. Total downtime: 18 minutes. This happened every month.

Incident 3 — The Service Account Lockout: The service account running the CBS Windows Service (ABCBANK\svc_cbs_win) got locked out by AD after a password change was applied to Active Directory but not to the Windows service. The service crashed and attempted to restart — each restart attempt used the old credentials, incrementing the lockout counter. By the time anyone noticed, the account was locked with 87 failed attempts. The service ran as "Access Denied" in a restart loop for 2 hours.

The Ask: "Monitor all critical Windows services every 5 minutes. Auto-restart them in the correct dependency order. Check service account validity. Correlate Windows Event Log to understand WHY a service stopped. Stop restart loops when we detect a repeated crash — escalate to humans instead."

📚 2. Windows Service Concepts

Windows Service States & Startup Types
StateMeaningAction
RunningService is active and processingNone — healthy
StoppedService is not runningCheck if should be running; start if needed
StopPendingService is in the process of stoppingWait; may indicate hang
StartPendingService is attempting to startWait; alert if persists > 60 seconds
PausedService is paused (rare)Usually intentional — check with team
Startup Types:
Automatic: starts at boot — most banking services
Automatic (Delayed Start): starts a few minutes after boot — avoids startup conflicts
Manual: only starts when explicitly requested
Disabled: cannot start — used for security (disabling unnecessary services)
Service Dependencies — The Correct Start Order
Windows services can declare dependencies on other services. When service A depends on service B, Windows ensures B starts before A.

The problem: Windows's dependency tracking only prevents A from starting if B hasn't started yet — it does NOT restart A automatically if B stops later. When MSDTC crashed in our incident, PGS also crashed — but Windows didn't automatically restart PGS when MSDTC came back up.

Our solution: When we detect PGS is stopped, we check its dependency chain first (using Get-Service -Name PGS | Select-Object -ExpandProperty ServicesDependedOn), start dependencies in the correct order, wait for each to stabilize, then start PGS.
Service Failure Actions (Windows Recovery Tab)
Every Windows service has configurable failure actions for the 1st, 2nd, and subsequent failures:
Take No Action: Service stays stopped (bad for banking)
Restart the Service: Windows auto-restarts (good but doesn't fix root cause)
Run a Program: Execute a script on failure
Restart the Computer: Reboot the server (extreme — only for truly critical services)

Banking best practice: 1st failure → Restart after 1 minute. 2nd failure → Restart after 2 minutes. 3rd failure → Run PagerDuty alert script. This prevents restart loops while still auto-recovering from transient failures.

❗ 4. Problem Statement

Current Issues

  • Alert emails to distribution lists — not targeted on-call alerts
  • No dependency ordering — services restarted in random order
  • No restart loop prevention — service account lockout from infinite retries
  • No event log correlation in alerts — engineers must RDP to investigate
  • Startup type not validated — services silently changed to Manual after troubleshooting
  • Service account health not monitored — lockouts discovered when service crashes

After Automation

  • PagerDuty P1 within 5 minutes of any critical service stopping
  • Dependency chain resolved automatically before restart attempt
  • Restart counter: stop after 3 attempts, escalate with event log evidence
  • Event Log last 10 entries included in every PagerDuty alert
  • Daily startup type audit — any change to Manual triggers Slack alert
  • Service account AD status validated every 30 minutes

Role 1: win_service_check

roles/win_service_check/tasks/get_service_states.yml
---
# =====================================================================
# Get state of all critical Windows services using PowerShell
# =====================================================================

- name: Query all critical service states in one PowerShell call
  ansible.windows.win_shell:
    cmd: |
      $services = @(
        {% for svc in critical_windows_services %}
        '{{ svc.name }}',
        {% endfor %}
      )
      $results = foreach ($name in $services) {
        $svc = Get-Service -Name $name -ErrorAction SilentlyContinue
        if ($svc) {
          [PSCustomObject]@{
            name          = $svc.Name
            status        = $svc.Status.ToString()        # Running, Stopped, etc.
            start_type    = $svc.StartType.ToString()     # Automatic, Manual, Disabled
            display_name  = $svc.DisplayName
            can_stop      = $svc.CanStop
            can_pause     = $svc.CanPauseAndContinue
            service_account = (Get-WmiObject Win32_Service -Filter "Name='$name'").StartName
          }
        } else {
          [PSCustomObject]@{
            name = $name
            status = 'NotFound'
            start_type = 'Unknown'
            display_name = 'Service Not Found'
            service_account = 'N/A'
          }
        }
      }
      $results | ConvertTo-Json -Depth 3
  register: service_states_raw
  changed_when: false

- name: Parse service state results
  ansible.builtin.set_fact:
    service_states: "{{ service_states_raw.stdout | from_json }}"
    # service_states: list of dicts with name, status, start_type, etc.

- name: Identify stopped critical services
  ansible.builtin.set_fact:
    stopped_services: >-
      {{ service_states
         | selectattr('status', 'equalto', 'Stopped')
         | list }}
    running_services: >-
      {{ service_states
         | selectattr('status', 'equalto', 'Running')
         | list }}
    not_found_services: >-
      {{ service_states
         | selectattr('status', 'equalto', 'NotFound')
         | list }}

- name: Log service state summary
  ansible.builtin.debug:
    msg:
      - "Windows Service Monitor — {{ inventory_hostname }}"
      - "Running: {{ running_services | map(attribute='name') | list | join(', ') }}"
      - "STOPPED: {{ stopped_services | map(attribute='name') | list | join(', ') | default('None') }}"
      - "Not Found: {{ not_found_services | map(attribute='name') | list | join(', ') | default('None') }}"

# =====================================================================
# Validate startup type for all critical services
# Any critical service changed to Manual/Disabled is a compliance risk
# =====================================================================

- name: Check startup type compliance for each service
  ansible.builtin.set_fact:
    startup_violations: >-
      {{ startup_violations | default([]) + [{
        'service_name': item.name,
        'current_startup': actual_service.start_type,
        'required_startup': item.required_startup,
        'compliant': (actual_service.start_type == item.required_startup
                      or actual_service.start_type == 'AutomaticDelayedStart')
      }]
      if (service_states | selectattr('name', 'equalto', item.name) | list | length > 0)
      else [] }}
  vars:
    actual_service: >-
      {{ service_states
         | selectattr('name', 'equalto', item.name)
         | first | default({'start_type': 'Unknown'}) }}
  loop: "{{ critical_windows_services }}"
  loop_control:
    label: "{{ item.name }}"

- name: Alert on startup type violations via Slack
  ansible.builtin.uri:
    url: "{{ slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: >-
        ⚠️ *Windows Service Startup Type Violation — {{ inventory_hostname }}*
        The following critical services have INCORRECT startup type:
        {% for v in startup_violations | rejectattr('compliant') | list %}
        • {{ v.service_name }}: Current={{ v.current_startup }}
          Required={{ v.required_startup }}
        {% endfor %}
        _A service set to Manual/Disabled will NOT restart after reboot!_
    status_code: [200]
  delegate_to: localhost
  when: startup_violations | rejectattr('compliant') | list | length > 0
roles/win_service_check/tasks/check_restart_counter.yml
---
# =====================================================================
# Check and manage restart counters to prevent restart loops
# Uses Windows Registry to persist counter values across Ansible runs
# =====================================================================

- name: Ensure registry path for restart counters exists
  ansible.windows.win_regedit:                         # win_regedit: manage registry
    path: "{{ restart_counter_reg_path }}"             # HKLM:\SOFTWARE\ABCBank\AnsibleServiceMonitor
    state: present                                      # Create path if not exists

- name: Read current restart counters for stopped services
  ansible.windows.win_shell:
    cmd: |
      $regPath = '{{ restart_counter_reg_path }}'
      $counters = @{}
      {% for svc in stopped_services %}
      try {
        $val = (Get-ItemProperty -Path $regPath -Name '{{ svc.name }}_restarts'
                -ErrorAction Stop).'{{ svc.name }}_restarts'
        $counters['{{ svc.name }}'] = [int]$val
      } catch {
        $counters['{{ svc.name }}'] = 0   # First failure — counter starts at 0
      }
      {% endfor %}
      $counters | ConvertTo-Json
  register: restart_counters_raw
  changed_when: false
  when: stopped_services | length > 0

- name: Parse restart counter values
  ansible.builtin.set_fact:
    restart_counters: >-
      {{ restart_counters_raw.stdout | from_json
         if (stopped_services | length > 0 and restart_counters_raw.stdout is defined)
         else {} }}

- name: Classify stopped services as restart-eligible or escalation-needed
  ansible.builtin.set_fact:
    services_to_restart: >-
      {{ services_to_restart | default([]) + [item | combine({'restart_count': (restart_counters[item.name] | default(0) | int)})] }}
  loop: >-
    {{ stopped_services
       | selectattr('name', 'in',
           critical_windows_services
           | selectattr('max_restart_attempts', 'defined')
           | map(attribute='name') | list)
       | list }}
  when: >
    (restart_counters[item.name] | default(0) | int)
    < (critical_windows_services
       | selectattr('name', 'equalto', item.name)
       | map(attribute='max_restart_attempts')
       | first | default(3) | int)
  loop_control:
    label: "{{ item.name }}"

- name: Classify services that have exceeded restart limit
  ansible.builtin.set_fact:
    services_escalation_needed: >-
      {{ stopped_services
         | reject('name', 'in', services_to_restart | map(attribute='name') | list)
         | list }}

🔧 10. Service Recovery Role — Dependency-Ordered Restart

roles/win_service_recovery/tasks/resolve_dependencies.yml
---
# =====================================================================
# Resolve service dependency chain for each stopped service
# This is the key logic that prevents the "wrong start order" incident
# =====================================================================

- name: Get full dependency chain for each service to restart
  ansible.windows.win_shell:
    cmd: |
      function Get-ServiceDependencyChain {
        param([string]$ServiceName)
        $svc = Get-Service -Name $ServiceName -ErrorAction SilentlyContinue
        if (-not $svc) { return @() }

        $deps = @()
        foreach ($dep in $svc.ServicesDependedOn) {
          # Recursively get dependencies of dependencies
          $deps += Get-ServiceDependencyChain -ServiceName $dep.Name
          $deps += $dep.Name
        }
        return $deps | Select-Object -Unique
      }

      $allDeps = @{}
      $targetServices = @(
        {% for svc in services_to_restart %}
        '{{ svc.name }}',
        {% endfor %}
      )

      foreach ($svcName in $targetServices) {
        $chain = Get-ServiceDependencyChain -ServiceName $svcName
        $allDeps[$svcName] = $chain
      }

      $allDeps | ConvertTo-Json -Depth 5
  register: dependency_chains_raw
  changed_when: false
  when: services_to_restart | length > 0

- name: Parse dependency chain results
  ansible.builtin.set_fact:
    dependency_chains: >-
      {{ dependency_chains_raw.stdout | from_json
         if (services_to_restart | length > 0)
         else {} }}

- name: Log dependency resolution
  ansible.builtin.debug:
    msg:
      - "Service Dependency Resolution — {{ inventory_hostname }}"
      - "{% for svc, deps in dependency_chains.items() %}"
      - "{{ svc }}: depends on → {{ deps | join(' → ') | default('(no dependencies)') }}"
      - "{% endfor %}"
roles/win_service_recovery/tasks/start_service.yml
---
# =====================================================================
# Start services in correct dependency order
# 1. Start each dependency first (bottom of chain to top)
# 2. Wait for each to stabilize
# 3. Start the target service last
# 4. Increment restart counter in registry
# =====================================================================

- name: Start dependencies in correct order for each stopped service
  ansible.windows.win_service:                         # win_service: manage Windows services
    name: "{{ item }}"                                 # Dependency service name
    state: started                                     # Start if not already running
    start_mode: auto                                   # Also ensure startup type is Automatic
  loop: "{{ dependency_chains[target_service.name] | default([]) }}"
  loop_control:
    label: "Starting dependency: {{ item }}"
  register: dep_start_results
  failed_when: false                                   # Don't fail if dependency already running

- name: Wait for dependencies to stabilize
  ansible.builtin.pause:
    seconds: "{{ target_service_config.restart_delay_sec | default(10) }}"
    # Wait configured delay for each service — PGS needs 30s, MSDTC only 10s

- name: Start the target service
  ansible.windows.win_service:
    name: "{{ target_service.name }}"
    state: started
    start_mode: auto                                   # Enforce Automatic startup type
  register: service_start_result

- name: Increment restart counter in registry
  ansible.windows.win_regedit:
    path: "{{ restart_counter_reg_path }}"
    name: "{{ target_service.name }}_restarts"
    data: "{{ (restart_counters[target_service.name] | default(0) | int) + 1 }}"
    type: dword                                        # DWORD (32-bit integer) registry value

- name: Store timestamp of last restart attempt
  ansible.windows.win_regedit:
    path: "{{ restart_counter_reg_path }}"
    name: "{{ target_service.name }}_last_restart"
    data: "{{ ansible_date_time.iso8601 }}"
    type: string

- name: Verify service started successfully
  ansible.windows.win_service:
    name: "{{ target_service.name }}"
    state: started
  register: post_start_verify

- name: Send PagerDuty alert for stopped service (with event log context)
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "win-svc-{{ inventory_hostname }}-{{ target_service.name }}"
      payload:
        summary: >-
          {{ '✅ AUTO-RECOVERED' if post_start_verify.state == 'started' else '🔴 RESTART FAILED' }}:
          Windows service {{ target_service.name }} ({{ target_service.display }})
          on {{ inventory_hostname }}.
          Attempt {{ (restart_counters[target_service.name] | default(0) | int) + 1 }}/{{ target_service_config.max_restart_attempts }}.
        severity: "{{ 'error' if post_start_verify.state == 'started' else 'critical' }}"
        source: ansible-win-service-monitor

roles/win_event_log_collector/tasks/collect_service_events.yml
---
# =====================================================================
# Collect Windows Event Log entries related to stopped services
# These are included in PagerDuty alerts for faster diagnosis
# This is what makes alerts actionable vs generic "service stopped"
# =====================================================================

- name: Collect recent event log entries for stopped services
  ansible.windows.win_shell:
    cmd: |
      $lookbackTime = (Get-Date).AddMinutes(-{{ event_log_lookback_minutes }})
      $serviceNames = @(
        {% for svc in stopped_services %}
        '{{ svc.name }}',
        {% endfor %}
      )

      $allEvents = @()
      foreach ($svcName in $serviceNames) {
        # Look for events from both System and Application logs
        $events = Get-WinEvent -FilterHashtable @{
          LogName   = 'System','Application'
          StartTime = $lookbackTime
          Level     = 1,2,3         # Critical=1, Error=2, Warning=3
        } -ErrorAction SilentlyContinue |
        Where-Object {
          $_.Message -like "*$svcName*" -or
          $_.ProviderName -like "*$svcName*" -or
          $_.Message -like "*Service Control Manager*"
        } |
        Select-Object -First {{ event_log_max_entries }} |
        ForEach-Object {
          [PSCustomObject]@{
            time        = $_.TimeCreated.ToString('yyyy-MM-dd HH:mm:ss')
            level       = $_.LevelDisplayName
            source      = $_.ProviderName
            event_id    = $_.Id
            service     = $svcName
            message     = $_.Message.Substring(0, [Math]::Min(300, $_.Message.Length))
            # Truncate to 300 chars — PagerDuty has message size limits
          }
        }
        $allEvents += $events
      }

      if ($allEvents.Count -gt 0) {
        $allEvents | ConvertTo-Json -Depth 3
      } else {
        '[]'
      }
  register: service_events_raw
  changed_when: false
  when: stopped_services | length > 0

- name: Parse event log results
  ansible.builtin.set_fact:
    service_event_log_entries: >-
      {{ service_events_raw.stdout | from_json
         if (stopped_services | length > 0 and service_events_raw.stdout | trim != '[]')
         else [] }}

- name: Format event log summary for alerts
  ansible.builtin.set_fact:
    event_log_summary: >-
      {% for event in service_event_log_entries[:5] %}
      [{{ event.time }}] {{ event.level }} (EventID:{{ event.event_id }})
      Source: {{ event.source }}
      {{ event.message[:200] }}
      ---
      {% endfor %}
  when: service_event_log_entries | length > 0

- name: Log event analysis results
  ansible.builtin.debug:
    msg:
      - "Event Log Analysis — {{ inventory_hostname }}"
      - "Events found: {{ service_event_log_entries | length }}"
      - "{% for e in service_event_log_entries[:3] %}"
      - "[{{ e.time }}] {{ e.level }}: {{ e.message[:100] }}"
      - "{% endfor %}"

# Service Account AD Health Audit — Every 30 Minutes
# Checks if service accounts are locked, expired, or pw-expired
# Runs on AAP control node — queries AD via LDAP, not WinRM

      ansible.builtin.uri:
        url: "{{ pagerduty_integration_url }}"
        method: POST
        body_format: json
        body:
          routing_key: "{{ vault_pagerduty_routing_key }}"

🔄 14. Execution Flow

1
Every 5 minutes: Win-Service-Monitor fires. WinRM HTTPS connects to each Windows server (serial:5). Single PowerShell call queries all critical services' status, startup type, and service account in one round trip.
2
stopped_services list built. Event log collector runs — Get-WinEvent queries System + Application logs for the last 10 minutes, filtered by service name. Event summaries prepared for PagerDuty payload.
3
Restart counter checked from Windows Registry. If counter < max_restart_attempts: service goes to services_to_restart. If counter ≥ max: goes to services_escalation_needed — no more auto-retry.
4
For each service to restart: dependency chain resolved recursively via PowerShell function. Dependencies started in order (bottom of chain to top). Wait configured delay. Target service started last. Registry counter incremented.
5
Post-start verification: win_service state checked. PagerDuty alert fires with event log context. If recovered → PagerDuty auto-resolve + Slack "recovered" message. If still stopped → escalation PagerDuty P1 with all event log evidence.
6
Every 30 min: service account audit runs from AAP control node. ldapsearch checks lockoutTime for each domain service account. Locked account → immediate P1 PagerDuty BEFORE the service crashes — proactive prevention of Incident 3.

🎯 16. Interview Prep

Q: How do you prevent a restart loop when a service keeps crashing?
We use a registry-based restart counter that persists between Ansible runs. Each time we restart a service, we increment a DWORD counter at HKLM:\SOFTWARE\ABCBank\AnsibleServiceMonitor\ServiceName_restarts.

Before attempting a restart, we read this counter. If it equals or exceeds max_restart_attempts (configured per service), we stop attempting auto-recovery and instead send an escalation PagerDuty alert with the full Event Log context. The auto-recovery is deliberately stopped — we don't want to keep hammering a service that's crash-looping (which would cause the service account lockout from Incident 3).

The counter is reset to 0 when the service is successfully running again, or manually reset via an on-demand AAP job template survey that an engineer can run after fixing the root cause.
Q: Why use Windows Registry to store the restart counter instead of an Ansible variable?
Ansible variables exist only within a single playbook run — they are not persistent across runs. Our monitoring runs every 5 minutes as a new AAP job. Any variable set in run #1 is completely gone in run #2.

The Windows Registry is a persistent key-value store on the Windows server itself. A DWORD value written at 14:00 is still there at 14:05 when the next monitoring run executes. This is the only way to maintain state (like a crash counter) across multiple AAP job executions without an external database.

Alternative: store the counter in a file on the Windows server (e.g., C:\ProgramData\ABCBank\service_counters.json). The registry approach is preferable because: no file permission issues, survives service restarts, and is auditable via regedit.
Q: How does your solution handle the wrong start order problem?
The PowerShell function Get-ServiceDependencyChain recursively walks the service dependency tree starting from the target service. It calls $svc.ServicesDependedOn for the target, then recursively calls itself for each dependency — building a complete ordered list from the deepest dependency to the immediate parent.

For example, PGS depends on MSDTC which depends on RpcSs. The chain is: RpcSs → MSDTC → MSMQ → PGS. We start RpcSs first, wait for it to stabilize, then MSDTC, wait, then MSMQ, wait, then PGS. This matches exactly what Windows would do on a clean boot with the service dependency declarations.

The key insight: Windows enforces dependency start order at boot time, but NOT when services are manually stopped and restarted mid-operation. Our automation fills this gap.
Q: What Windows Event IDs are most useful for diagnosing service failures?
System Log — Service Control Manager:
• Event 7034: Service terminated unexpectedly — includes service name and termination count
• Event 7036: Service entered stopped/running state
• Event 7038: Service failed to log on as account — indicates service account credential issue
• Event 7000: Service failed to start — includes error code
• Event 7031: Service terminated with non-zero exit code

Application Log:
• Event 1000: Application error/crash — from the crashing application
• Event 1026: .NET application crash — for .NET services

Our event log collector filters for Events 7000, 7031, 7034, 7036, 7038 in the System log for quick diagnosis.
