Project 6: Log Rotation & Cleanup Automation using Red Hat AAP

SecureBank's 400+ server fleet generates over 2TB of logs every day — application logs, transaction audit trails, access logs, security logs, database alert logs, JVM GC logs, and middleware logs — across 14 banking applications. Without disciplined log lifecycle management, application servers hit disk-full conditions that instantly kill running processes, audit logs required for RBI/PCI-DSS compliance are lost before their mandatory retention period, and log forensics during security incidents become impossible because logs were deleted too aggressively. This project automates intelligent, policy-driven log rotation, compression, archival, and purge across the fleet — with retention policies mapped directly to RBI and PCI-DSS mandates, per-application customisation, and pre/post disk-space validation that prevents any cleanup run from accidentally deleting logs that are still needed for a live audit.

RHEL 8/9 Red Hat AAP 2.5 logrotate / journald RBI 10-Year Audit Retention PCI-DSS Log Retention NFS/S3 Archival Disk-Full Prevention rsyslog

📋 1. Business Requirement

SecureBank's log management must satisfy three competing constraints simultaneously:

ConstraintRequirementSource
Minimum RetentionTransaction audit logs: 10 years. Security/access logs: 5 years. Application logs: 1 year.RBI IT Framework §8.2, RBI Cyber Security Framework
PCI-DSS RetentionAll CDE audit logs retained for at least 12 months (3 months immediately accessible)PCI-DSS v4.0 Req 10.7
Disk Space SLALog partition must never exceed 85% utilisation (triggers P2 alert) or 95% (disk-full = application crash)SecureBank Internal SLA
Active AuditNever delete logs that are within the retention window of an active RBI/PCI audit — flagged in a "hold" registryInfoSec Legal Hold Policy

The log lifecycle policy for each log category: compress after 1 day → retain compressed on server for 7–30 days → archive to NFS/S3 for retention period → purge after retention window expires. Each application has its own policy defined in the inventory.

🏦 2. Real-Time Banking Scenario

The Story: It's 3:22 AM on a Tuesday. SecureBank's CBS application server cbs-app03 goes completely dark. The NOC fires a P1 alert — all 12 app tier servers are showing connection timeouts. The on-call engineer, Vikram, SSHs in via the out-of-band console and immediately sees: No space left on device. The /opt/securecore/logs partition is at 100%. Catalina.out has grown to 47GB because a developer pushed a new release with DEBUG logging accidentally left enabled. The application JVM cannot write its GC log and hangs. 40 minutes of complete transaction downtime follows — during month-end, when 200 corporate salary disbursements were pending. Two months later, a forensic investigator from the InfoSec team is investigating a suspected unauthorized access incident from 8 months ago. They request the access logs from that date. The logs don't exist — the previous junior engineer's ad-hoc cleanup script deleted everything older than 30 days, not knowing about the 5-year minimum retention for security logs. Now with the Ansible-driven log lifecycle automation in place, logrotate policies are configured uniformly via templates, disk utilisation is checked before and after every cleanup run, logs are compressed and staged to NFS for long-term retention before being purged locally, and a retention-hold registry prevents deletion of any log under an active legal or audit hold.

❗ 3. Problem Statement

  • No consistent logrotate configuration across 400 servers — each application team configured their own (or didn't), leading to wildly different rotation schedules, inconsistent compression, and varied retention periods.
  • Disk-full incidents caused by runaway log growth (DEBUG logging left on, exception storms writing megabytes/second) silently kill application processes at 3 AM.
  • No archival pipeline — old logs are deleted locally with no backup to NFS/S3, making forensic investigation and RBI audit evidence retrieval impossible for events older than 30 days.
  • No legal-hold awareness — ad-hoc cleanup scripts delete logs under active RBI inspection or PCI-DSS audit without any check against a hold registry.
  • JVM GC logs, core dump files, and heapdump files are never cleaned up — one OutOfMemoryError produces a 16GB heapdump that fills the disk for weeks.
  • No pre-cleanup validation — engineers sometimes accidentally delete active log files (not just rotated archives) that applications are still writing to, causing application log corruption.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. An engineer notices a monitoring alert or ticket: "Disk space on cbs-app03 at 82%."
  2. Engineer SSHs into the server and runs du -sh /opt/*/logs/* to find the biggest files.
  3. Engineer manually gzips or deletes old log files, usually anything with a date older than "a month ago" — without checking retention policy.
  4. No archival step — deleted logs are gone permanently.
  5. Engineer updates a spreadsheet ticket as "resolved."
  6. Three weeks later, the same server is at 82% again — the root cause (over-verbose logging config) is never addressed.
  7. No fleet-wide visibility — 399 other servers may be at 90% and nobody knows until they also hit alerts.

🛠️ 6. Automated Solution Design

The solution has four sequential phases, each independently executable as an AAP Job Template:

  • Phase 1 — Disk Scan & Report: Runs daily on all 400 servers. Collects disk utilisation per log partition, identifies the top 10 largest log directories, flags servers above thresholds (75% warn / 85% alert / 95% critical), and generates a fleet-wide disk utilisation report pushed to Grafana.
  • Phase 2 — Logrotate Config Enforcement: Deploys per-application logrotate configuration from Jinja2 templates based on inventory-defined log policies (rotate frequency, compression, retention count, post-rotate scripts). Ensures logrotate.d files are consistent and current across the fleet. Runs logrotate manually to force a rotation if the server is above the 85% threshold.
  • Phase 3 — Archival Pipeline: For each application's log directory, identifies files older than the "local retention" window (typically 7–30 days), checks against the legal-hold registry, compresses any uncompressed files, validates archive integrity (gzip -t), and copies to the designated NFS/S3 archival path — then deletes the local copy only after successful archive validation.
  • Phase 4 — JVM Artifact Cleanup: Locates and cleans heapdump (.hprof), core dump, and oversized GC log files that accumulate from JVM crashes. Sends a pre-deletion alert to the application team (heapdumps may be needed for debugging) with a configurable grace period before deletion.

⚙️ 8. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.builtin.find, ansible.builtin.file, ansible.builtin.shell, ansible.builtin.command, ansible.builtin.template, ansible.builtin.copy, ansible.builtin.synchronize, ansible.builtin.uri
  • Roles: log_disk_scan, log_rotate_enforce, log_archive, log_jvm_cleanup, log_report
  • Jinja2 templates: logrotate.d config per app, fleet disk report JSON, archival manifest CSV
  • ansible.builtin.find with age, size, patterns filters — filesystem queries without shell glob risks
  • ansible.posix.synchronize (rsync) for efficient NFS archival of large log sets
  • Legal-hold registry as a YAML file fetched from a trusted NFS path — checked before every deletion

Red Hat AAP Components

  • Job Templates: Log-Disk-Scan, Log-Rotate-Enforce, Log-Archive-Pipeline, Log-JVM-Cleanup
  • Workflow: Log-Lifecycle-Weekly (chains all 4 phases with disk-scan gate — if scan shows <75%, skip aggressive cleanup)
  • Survey: target_hosts (specific server or group), force_archive (bool — skip threshold, always archive), dry_run (bool — preview deletions without executing)
  • Schedule: Phase 1 daily; Phases 2–4 weekly Sunday maintenance window
  • Notification: Slack #disk-alerts for servers above 85%; Email to app team before JVM heapdump deletion
  • RBAC: dry_run launch available to all engineers; actual deletion requires "Log-Lifecycle-Admins" team

💻 11. Complete Project Code (Line-by-Line Explained)

Role: log_disk_scan

roles/log_disk_scan/tasks/main.yml
---
- name: Collect disk utilisation for all configured log partitions
  ansible.builtin.shell: >
    df -h {{ item.log_dir }} --output=source,size,used,avail,pcent,target |
    tail -1
  loop: "{{ log_policies | default([]) }}"
  loop_control:
    label: "{{ item.name }}"
  register: disk_usage_raw
  changed_when: false

- name: Parse disk utilisation percentage for each log directory
  ansible.builtin.set_fact:
    log_disk_stats: >-
      {{ log_disk_stats | default([]) + [{
        'policy_name': item.item.name,
        'log_dir': item.item.log_dir,
        'disk_info': item.stdout,
        'disk_pct': item.stdout.split()[-2] | replace('%','') | int
      }] }}
  loop: "{{ disk_usage_raw.results }}"
  loop_control:
    label: "{{ item.item.name }}"

- name: Find top-10 largest files in each log directory
  ansible.builtin.shell: >
    du -sh {{ item.log_dir }}/* 2>/dev/null |
    sort -rh | head -10
  loop: "{{ log_policies | default([]) }}"
  loop_control:
    label: "{{ item.name }}"
  register: top_files_raw
  changed_when: false

- name: Determine overall disk health status per policy
  ansible.builtin.set_fact:
    disk_health_status: >-
      {{
        'CRITICAL' if log_disk_stats | selectattr('disk_pct','ge', disk_critical_pct) | list | length > 0
        else 'ALERT'  if log_disk_stats | selectattr('disk_pct','ge', disk_alert_pct) | list | length > 0
        else 'WARN'   if log_disk_stats | selectattr('disk_pct','ge', disk_warn_pct) | list | length > 0
        else 'OK'
      }}

- name: Alert on high disk utilisation via Slack
  ansible.builtin.uri:
    url: "{{ vault_slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: >-
        :warning: *SecureBank Log Disk Alert* on `{{ inventory_hostname }}`
        Status: *{{ disk_health_status }}*
        {% for stat in log_disk_stats %}
        {{ stat.policy_name }}: {{ stat.disk_pct }}% used ({{ stat.log_dir }})
        {% endfor %}
  delegate_to: localhost
  when: disk_health_status in ['ALERT','CRITICAL']
  failed_when: false
Line-by-Line Explanation
df -h {{ item.log_dir }} --output=source,size,used,avail,pcent,target — We check the disk utilisation of the specific filesystem that contains each log directory, not always just /. In enterprise banks, /opt/securecore/logs is often on a separate LVM volume or NFS mount — checking root disk would give a false-negative if logs are on a dedicated partition filling up independently.
item.stdout.split()[-2] | replace('%','') | int — Extracts the percentage field from df output (second-to-last column in the --output format). The replace('%','') strips the percent sign before converting to integer for numeric comparison with thresholds. Using -2 (second from end) is more robust than a fixed column index which can shift with different df output widths.
du -sh /* | sort -rh | head -10 — -r = reverse (largest first), -h = human-readable sort (correctly handles KB/MB/GB ordering). This gives the on-call engineer immediate visibility into which specific log files are consuming the most space — critical for targeted cleanup rather than blind deletion.
selectattr('disk_pct','ge', disk_critical_pct) — Jinja2's selectattr with 'ge' (greater-than-or-equal) filter across the list of disk stats produces a cascading severity evaluation: if ANY log partition is critical, the overall status is CRITICAL — not just the worst individual one.

Role: log_rotate_enforce

roles/log_rotate_enforce/tasks/main.yml
---
- name: Deploy per-policy logrotate configuration from template
  ansible.builtin.template:
    src: logrotate_app.j2
    dest: "/etc/logrotate.d/securebank-{{ item.name }}"
    owner: root
    group: root
    mode: '0644'
    validate: '/usr/sbin/logrotate --debug %s'
    backup: true
  loop: "{{ log_policies | default([]) }}"
  loop_control:
    label: "{{ item.name }}"
  notify: Run logrotate now

- name: Verify logrotate global config has sensible defaults
  ansible.builtin.lineinfile:
    path: /etc/logrotate.conf
    regexp: '^compress'
    line: 'compress'
    state: present

- name: Ensure logrotate timer is enabled (systemd timer replaces legacy cron)
  ansible.builtin.systemd:
    name: logrotate.timer
    state: started
    enabled: true

- name: Force immediate logrotate execution if disk is above alert threshold
  ansible.builtin.command: >
    /usr/sbin/logrotate -f /etc/logrotate.d/securebank-{{ item.name }}
  loop: "{{ log_policies | default([]) }}"
  loop_control:
    label: "{{ item.name }}"
  when:
    - log_disk_stats | selectattr('policy_name','equalto', item.name)
                     | selectattr('disk_pct','ge', disk_alert_pct)
                     | list | length > 0
    - not dry_run | bool
  register: forced_rotate_result

roles/log_rotate_enforce/templates/logrotate_app.j2
# Managed by Ansible AAP — SecureBank Log Rotation Policy
# Application: {{ app_name }} | Policy: {{ item.name }}
# Log Category: {{ item.log_category }} | Retention: {{ item.archive_retention_days }} days (NFS)
# DO NOT EDIT MANUALLY — changes will be overwritten on next AAP run

{% for pattern in item.patterns %}
{{ item.log_dir }}/{{ pattern }} {
    {{ item.rotate_frequency }}
    rotate {{ item.rotate_count }}
    compress
    delaycompress
    missingok
    notifempty
    dateext
    dateformat -%Y%m%d
    copytruncate
    sharedscripts
    postrotate
        /usr/bin/systemctl reload {{ app_name }} > /dev/null 2>&1 || true
    endscript
}
{% endfor %}
Line-by-Line Explanation
validate: '/usr/sbin/logrotate --debug %s' — Before writing the logrotate config file, Ansible validates it using logrotate --debug which parses the config for syntax errors without actually rotating anything. Deploying a malformed logrotate config silently disables log rotation for that application — the validate step catches this before the file is written.
delaycompress — Compresses the previous rotation's log (not the most recent one just rotated). This matters because some applications (like Tomcat) re-open the log file by name after rotation and may still be writing to the uncompressed file for a short period. delaycompress prevents gzip from trying to compress a file that's still being written.
dateext + dateformat -%Y%m%d — Appends a date suffix to rotated logs (e.g., catalina.out-20260120) instead of numeric suffixes (catalina.out.1). Date-suffixed rotations are far more useful for forensic investigation and retention management because you can immediately tell which date range a log file covers without reading it.
copytruncate — Creates a copy of the current log file, then truncates the original to zero size — as opposed to moving the file and creating a new one. Required for applications that hold a file descriptor open to the log path (most Java/Tomcat apps do this) and cannot be SIGHUP'd to reopen a new file. The trade-off: there's a tiny window between copy and truncate where log entries could be lost — acceptable for application logs, never used for audit logs.
Force immediate logrotate if disk above threshold — The -f (force) flag bypasses logrotate's internal "has this already been rotated today?" check, rotating immediately regardless of schedule. Gated by the disk threshold check from the scan role — only triggered when genuinely needed, preventing unnecessary extra rotations on healthy servers.

Role: log_archive — The Core Archival Pipeline

roles/log_archive/tasks/main.yml
---
- name: Read active legal-hold registry from compliance NFS share
  ansible.builtin.slurp:
    src: "{{ legal_hold_registry_path }}"
  register: legal_hold_raw
  delegate_to: localhost
  run_once: true
  failed_when: false

- name: Parse legal-hold registry into usable fact
  ansible.builtin.set_fact:
    legal_hold_registry: "{{ legal_hold_raw.content | default('') | b64decode | from_yaml | default({}) }}"
  run_once: true

- name: Process each log policy for archival
  ansible.builtin.include_tasks: archive_policy.yml
  loop: "{{ log_policies | default([]) }}"
  loop_control:
    loop_var: policy
    label: "{{ policy.name }}"
roles/log_archive/tasks/archive_policy.yml
---
- name: "Find rotated log files eligible for archival — {{ policy.name }}"
  ansible.builtin.find:
    paths: "{{ policy.log_dir }}"
    patterns: "{{ policy.patterns | map('regex_replace', '$', '*') | list }}"
    age: "{{ policy.local_retention_days }}d"
    age_stamp: mtime
    recurse: false
    file_type: file
  register: files_to_archive

- name: "Compress any uncompressed eligible files before archival — {{ policy.name }}"
  ansible.builtin.command: "gzip -9 {{ item.path }}"
  loop: "{{ files_to_archive.files | rejectattr('path', 'match', '.*\\.gz$') | list }}"
  loop_control:
    label: "{{ item.path | basename }}"
  when:
    - files_to_archive.files | length > 0
    - not dry_run | bool

- name: "Re-find files after compression (paths have changed to .gz) — {{ policy.name }}"
  ansible.builtin.find:
    paths: "{{ policy.log_dir }}"
    patterns: "{{ policy.patterns | map('regex_replace', '$', '*.gz') | list }}"
    age: "{{ policy.local_retention_days }}d"
    age_stamp: mtime
    recurse: false
  register: compressed_files_to_archive

- name: "Validate gzip integrity of each file before archival — {{ policy.name }}"
  ansible.builtin.command: "gzip -t {{ item.path }}"
  loop: "{{ compressed_files_to_archive.files }}"
  loop_control:
    label: "{{ item.path | basename }}"
  register: gzip_integrity_checks
  changed_when: false

- name: "Identify files that failed integrity check (never archive corrupt files) — {{ policy.name }}"
  ansible.builtin.set_fact:
    corrupt_files: >-
      {{ gzip_integrity_checks.results
         | selectattr('rc', 'ne', 0)
         | map(attribute='item.path')
         | list }}

- name: "Alert on corrupt log files — {{ policy.name }}"
  ansible.builtin.debug:
    msg: "⚠️ CORRUPT LOG FILE on {{ inventory_hostname }}: {{ corrupt_files }} — skipping archival for these files"
  when: corrupt_files | length > 0

- name: "Check each file against legal-hold registry before archival — {{ policy.name }}"
  ansible.builtin.set_fact:
    archivable_files: >-
      {{ compressed_files_to_archive.files
         | rejectattr('path', 'in', legal_hold_registry.get('held_file_paths', []))
         | rejectattr('path', 'in', corrupt_files | default([]))
         | list }}
    held_files: >-
      {{ compressed_files_to_archive.files
         | selectattr('path', 'in', legal_hold_registry.get('held_file_paths', []))
         | list }}

- name: "Log held files that are skipped for deletion — {{ policy.name }}"
  ansible.builtin.debug:
    msg: >-
      LEGAL HOLD: Skipping deletion of {{ held_files | length }} file(s) on
      {{ inventory_hostname }} for policy {{ policy.name }} — files are under active hold:
      {{ held_files | map(attribute='path') | list }}
  when: held_files | length > 0

- name: "Create dated archival directory on NFS — {{ policy.name }}"
  ansible.builtin.file:
    path: "{{ log_archive_nfs_root }}/{{ policy.archive_subpath }}/{{ ansible_date_time.year }}/{{ ansible_date_time.month }}"
    state: directory
    mode: '0755'
  when:
    - archivable_files | length > 0
    - not dry_run | bool
  delegate_to: "{{ ansible_host }}"

- name: "Copy eligible compressed logs to NFS archive — {{ policy.name }}"
  ansible.builtin.copy:
    src: "{{ item.path }}"
    dest: "{{ log_archive_nfs_root }}/{{ policy.archive_subpath }}/{{ ansible_date_time.year }}/{{ ansible_date_time.month }}/{{ item.path | basename }}"
    remote_src: true
    mode: '0444'
  loop: "{{ archivable_files }}"
  loop_control:
    label: "{{ item.path | basename }}"
  register: archive_copy_results
  when: not dry_run | bool

- name: "Verify archived file exists on NFS before deleting local copy — {{ policy.name }}"
  ansible.builtin.stat:
    path: "{{ log_archive_nfs_root }}/{{ policy.archive_subpath }}/{{ ansible_date_time.year }}/{{ ansible_date_time.month }}/{{ item.path | basename }}"
  loop: "{{ archivable_files }}"
  loop_control:
    label: "{{ item.path | basename }}"
  register: archive_verify_results
  when: not dry_run | bool

- name: "Check no application process has the file open (lsof safety check) — {{ policy.name }}"
  ansible.builtin.shell: "lsof {{ item.path }} 2>/dev/null | wc -l"
  loop: "{{ archivable_files }}"
  loop_control:
    label: "{{ item.path | basename }}"
  register: lsof_checks
  changed_when: false
  when: not dry_run | bool

- name: "Delete local log file ONLY after archive verified AND file not open — {{ policy.name }}"
  ansible.builtin.file:
    path: "{{ item.0.path }}"
    state: absent
  loop: "{{ archivable_files | zip(archive_verify_results.results, lsof_checks.results) | list }}"
  loop_control:
    label: "{{ item.0.path | basename }}"
  when:
    - not dry_run | bool
    - item.1.stat.exists | default(false)
    - item.2.stdout | int == 0
  register: deletion_results

- name: "Dry-run summary — what WOULD be archived and deleted — {{ policy.name }}"
  ansible.builtin.debug:
    msg: >-
      [DRY RUN] Policy: {{ policy.name }} on {{ inventory_hostname }}
      Would archive {{ archivable_files | length }} file(s) to NFS
      Would skip {{ held_files | length }} file(s) under legal hold
      Files: {{ archivable_files | map(attribute='path') | map('basename') | list }}
  when: dry_run | bool
Line-by-Line Explanation
ansible.builtin.find with age: "{{ policy.local_retention_days }}d" + age_stamp: mtime — The find module's age parameter uses the file's modification time (mtime) to determine if it's older than the retention threshold. Using the Ansible module instead of a find shell command avoids shell injection risks from filenames with spaces or special characters — a real concern with log files from some middleware systems.
gzip -t integrity check — Validates the gzip file's internal checksum without decompressing it. A partially-written gzip file (from a crash mid-compression) will fail this check. We NEVER archive a corrupt file to NFS — corrupted archived evidence is arguably worse than no evidence, since it gives a false sense of compliance while being unrecoverable.
legal_hold_registry.get('held_file_paths', []) — The legal hold registry is a YAML file maintained by the InfoSec/Legal team on a compliance NFS share. When a forensic investigation or RBI inspection is in progress, InfoSec adds specific file paths (or glob patterns) to this registry. Our archival pipeline reads it at the start of every run and skips any matching files — preventing deletion of evidence relevant to a live investigation.
lsof {{ item.path }} | wc -l — Checks whether any running process currently has the file open for writing. A count of 0 means no process has it open and it's safe to delete. A count > 0 means an application process is still writing to it — deleting it would cause the application to lose log output silently (the process keeps the file descriptor open to the now-deleted file's inode, but disk space is not reclaimed until the FD closes). This is the most important safety check in the entire role.
Three-way zip loop: archivable_files | zip(archive_verify_results.results, lsof_checks.results) — Zips three parallel lists together so each deletion decision has access to: (item.0) the file path, (item.1) the NFS archive verification stat result, (item.2) the lsof count. ALL three conditions must be true to delete: file is in archivable list AND NFS copy verified AND no open file handles.
dry_run | bool gate on every destructive task — The dry_run: true default in group_vars means running the playbook without explicit -e dry_run=false NEVER deletes anything — it only reports what WOULD be done. This is the production safety default. Engineers must explicitly pass dry_run=false as a survey variable in AAP to perform real deletions. Senior engineers familiar with the pattern will recognise this as a common practice for irreversible operations.

roles/log_jvm_cleanup/tasks/main.yml
---
- name: Find JVM heapdump files (.hprof) in configured paths
  ansible.builtin.find:
    paths: "{{ jvm_artifact_paths | default(['/tmp', '/opt']) }}"
    patterns:
      - "*.hprof"
      - "java_pid*.hprof"
    recurse: true
    size: "100m"
    file_type: file
  register: heapdump_files

- name: Find Java core dump files
  ansible.builtin.find:
    paths: "{{ jvm_artifact_paths | default(['/tmp', '/opt']) }}"
    patterns:
      - "core.*"
      - "hs_err_pid*.log"
    recurse: true
    size: "1m"
    file_type: file
  register: core_dump_files

- name: Calculate total size of found JVM artifacts
  ansible.builtin.set_fact:
    heapdump_total_mb: "{{ heapdump_files.files | sum(attribute='size') // 1048576 }}"
    coredump_total_mb: "{{ core_dump_files.files | sum(attribute='size') // 1048576 }}"

- name: Notify application team before heapdump deletion (pre-deletion alert)
  ansible.builtin.uri:
    url: "{{ vault_slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: >-
        :warning: *JVM Heapdump Cleanup Scheduled* on `{{ inventory_hostname }}`
        Found {{ heapdump_files.files | length }} heapdump file(s)
        totalling *{{ heapdump_total_mb }}MB*
        Files: {{ heapdump_files.files | map(attribute='path') | list | join(', ') }}
        These will be deleted in 24 hours unless a hold is placed in the registry.
        Raise a ServiceNow change to preserve specific dumps.
  delegate_to: localhost
  when: heapdump_files.files | length > 0
  failed_when: false

- name: Delete heapdump files older than grace period (default 24h since alert)
  ansible.builtin.file:
    path: "{{ item.path }}"
    state: absent
  loop: "{{ heapdump_files.files }}"
  loop_control:
    label: "{{ item.path | basename }}"
  when:
    - not dry_run | bool
    - item.path not in legal_hold_registry.get('held_file_paths', [])
    - (ansible_date_time.epoch | int - item.mtime | int) > 86400
  register: heapdump_deletion_result

- name: Always delete hs_err (JVM crash log summary) files older than 7 days
  ansible.builtin.file:
    path: "{{ item.path }}"
    state: absent
  loop: "{{ core_dump_files.files | selectattr('path', 'match', '.*hs_err_pid.*') | list }}"
  loop_control:
    label: "{{ item.path | basename }}"
  when:
    - not dry_run | bool
    - (ansible_date_time.epoch | int - item.mtime | int) > 604800
Line-by-Line Explanation
size: "100m" on heapdump find — We only target heapdumps larger than 100MB. Small .hprof files (from JVM shutdown hooks or test frameworks) are common and harmless; the dangerous ones are the full-heap dumps from OutOfMemoryErrors that are typically 2–16GB. The size filter prevents over-aggressive cleanup of legitimate small diagnostic files.
Pre-deletion alert with a 24-hour grace period — Heapdumps are the only artifact that can definitively diagnose a JVM OutOfMemoryError or memory leak. Deleting them immediately destroys irreplaceable diagnostic evidence. The 24-hour window (enforced by checking mtime against current epoch minus 86400 seconds) gives developers time to copy the heapdump to their workstation before it's purged. This is a balance between disk management and incident debugging capability.
hs_err_pid*.log — JVM crash log summaries generated automatically by the JVM when it crashes (native crash, SIGSEGV, etc.). Unlike heapdumps, these are small text files (a few KB) containing thread states at crash time. We give these a 7-day retention (604800 seconds) rather than 24 hours because they're small and highly valuable for post-incident analysis.
item.mtime from the find module — The find module returns a mtime field (Unix timestamp) for each file in its results. Comparing against ansible_date_time.epoch (current Unix timestamp) gives us age in seconds without any date-string parsing — robust across timezones and locale settings.

🔄 13. Execution Flow — Start to Finish

1
Daily at 05:00 IST, Log-Disk-Scan runs across all 400 servers in parallel. df is run per log partition, top-10 largest files identified, disk health status computed per server.
2
Any server above 85% disk usage fires a Slack alert to #disk-alerts immediately. Any server above 95% fires a PagerDuty P1 (disk-critical = application crash risk).
3
Sunday 01:00 IST, Log-Lifecycle-Weekly workflow starts. Disk scan runs first. If all servers are healthy (<75%), the workflow skips the aggressive archival phase — no unnecessary log deletion on healthy systems.
4
Log-Rotate-Enforce: Jinja2 logrotate templates deployed (with logrotate --debug validation). Logrotate.timer confirmed active. For servers above 85%, logrotate -f is run immediately to force rotation.
5
Workflow pauses at Approval Node. The approver reviews the dry-run output from the previous run (showing exactly which files WOULD be archived and deleted) before approving real execution.
6
Log-Archive-Pipeline runs with dry_run=false. Legal-hold registry fetched from compliance NFS. For each policy, files older than local_retention_days are found, uncompressed ones are gzip -9'd, integrity-checked with gzip -t, NFS-copied, lsof-verified, then deleted locally.
7
Any held files are logged explicitly in the AAP job output and excluded from deletion. Any corrupt files are logged and excluded from both archival and deletion — they remain local for manual investigation.
8
Log-JVM-Cleanup: heapdumps and core dumps found. Pre-deletion Slack alert sent to the application team. Files older than 24 hours (grace period) and not under legal hold are deleted. hs_err files older than 7 days deleted always.
9
Log report generated: per-server before/after disk utilisation, total GB archived, total GB freed, count of held files skipped, count of corrupt files found. Archived to compliance NFS and linked in the AAP notification.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: A production server hits disk-full at 3 AM and the application crashes. Walk through your immediate response and how automation would have prevented it.
Immediate response: SSH via out-of-band console (SSH over main NIC fails if disk is full), identify largest files with du -sh /opt/*/logs/* | sort -rh | head -20, free up space by manually gzipping large plain-text logs, then restart the application. Long-term prevention: the daily disk-scan job would have flagged this server at 85% and triggered a forced logrotate. The weekly archival pipeline would have freed the space before reaching critical. Additionally, setting up /opt/*/logs as a separate LVM volume limits blast radius — a full log partition can't fill the root filesystem that the OS and app binaries need.
Q: How do you handle log files that are still being written to by a running application?
Two-pronged approach: (1) logrotate with copytruncate for applications that can't be SIGHUP'd to reopen log files — creates a copy then truncates the original, keeping the application's open file descriptor valid. (2) The lsof safety check in the archival role — we never delete a file that has active open file handles. Even after rotation, some applications may still have the old inode open; lsof catches this and skips the deletion, protecting the application from losing its log stream.
Q: An auditor asks for a specific transaction log from 3 years ago. How do you retrieve it?
The archival pipeline stores logs in a structured NFS path: /archive/{app}/{year}/{month}/{original_filename}.gz. With the date of the transaction, we can navigate directly to the right year/month path, find the file, gunzip it, and grep for the specific transaction ID. The archival manifest report (generated with every weekly run) also records exactly which files were archived on which dates — a metadata layer on top of the archive for fast forensic navigation.

Architecture & Production Questions

Q: What is the difference between logrotate's copytruncate and the default create directives?
create (default): renames the current log file (e.g., app.log → app.log.1), creates a new empty app.log, then sends SIGHUP to the application to reopen its log file descriptor to the new file. Requires the application to handle SIGHUP. copytruncate: creates a copy of the current app.log, then truncates the original to zero bytes — the application's existing file descriptor stays valid (still pointing to the same inode, now empty). Used when applications can't be safely SIGHUP'd or don't reopen log files on signal. Trade-off: tiny race condition between copy and truncate where log entries may be lost.
Q: Why use ansible.builtin.find instead of a shell find command?
Several reasons: (1) find module handles filenames with spaces, special characters, and Unicode correctly without shell quoting issues. (2) Results come back as a structured list of dicts with attributes (path, size, mtime) that can be filtered with Jinja2's selectattr and rejectattr — no text parsing required. (3) No shell injection risk — especially important when log directory paths or filenames come from user-provided variables. (4) Consistent behaviour across different operating systems and locales (shell find date parsing can vary).
Q: How do you handle the retention purge for NFS archives — who deletes logs after the 10-year retention period?
A separate scheduled playbook (not shown but part of the full solution) runs annually, finds files in the NFS archive older than the policy-defined retention period, and generates a deletion manifest for InfoSec approval before executing. This is a human-gated deletion because permanently deleting 10-year-old audit logs requires explicit legal sign-off — we never auto-delete from the long-term archive without an approval node in the workflow. In practice, most banks prefer to keep the NFS storage expanding rather than risk accidental deletion of RBI-mandatory audit evidence.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • The lsof check before deletion is the single most important safety pattern in log lifecycle automation — it's also the one most junior engineers omit.
  • dry_run: true as the default prevents accidental deletion during any test run. Force operators to explicitly opt in to real deletion via a survey variable.
  • Legal-hold registry checked before every purge — automation must be aware of active investigations; no audit framework accepts "the automation deleted it" as an excuse for missing evidence.
  • gzip -t integrity validation before deletion is mandatory — archiving a corrupt file then deleting the original leaves you with no recoverable evidence.

Common Mistakes

  • Using state: absent directly on log directories rather than files — one wrong path variable deletes an entire application's log history.
  • Not using delaycompress in logrotate — compressing the just-rotated file that an application still has open corrupts it.
  • Archiving to NFS without verifying the copy landed before deleting the source — NFS write errors silently produce zero-byte destination files.
  • Treating JVM heapdumps as "just disk waste" — they're the only artifact that can diagnose an OOM condition, and premature deletion destroys diagnostic capability.

Production Best Practices

  • Always mount log directories on separate LVM volumes from the root and OS filesystems — a log-full condition can't then kill the OS or other applications.
  • Set logrotate dateext on all policies — date-stamped rotated files make retention management and forensic navigation vastly easier than numeric suffixes.
  • Archive to multiple destinations (NFS primary + S3 secondary) for critical audit logs — NFS is fast but single-datacenter; S3 provides geographic redundancy for regulatory evidence.
  • Keep the legal-hold registry as a versioned, auditable YAML in a compliance-controlled Git repo — so you can prove what holds were active at any point in time.

Resume Points

  • Designed and implemented a policy-driven log lifecycle automation pipeline using Ansible AAP managing 2TB+ of daily log data across 400 banking application servers, with retention policies mapped to RBI (10-year transaction audit) and PCI-DSS (12-month CDE access log) mandates.
  • Engineered a legal-hold-aware archival pipeline with pre-archival gzip integrity validation and lsof-based open-file-handle safety checks, eliminating accidental evidence deletion during active RBI/PCI-DSS audits.
  • Implemented JVM artifact cleanup automation with pre-deletion alerts and configurable grace periods, recovering an average of 300GB/week across the production fleet while preserving heapdumps needed for active incident investigations.
