Project 13: Configuration Drift Detection & Remediation using Red Hat AAP

Configuration drift is the silent enemy of stable, secure banking infrastructure. A server that was perfectly configured 6 months ago has, through routine operations, emergency fixes, package upgrades, and human error, quietly diverged from its intended state. SELinux flipped to permissive. A sysctl parameter changed. An unauthorized cron job appeared. A critical service disabled. An SSH port changed from 22 to 2222 on one server. None of these changes are announced — they accumulate invisibly until they cause an incident or appear in an audit finding. SecureBank's 400-server fleet generates hundreds of such drift events every month. This project builds a comprehensive, multi-category configuration drift detection and remediation pipeline that goes beyond the OS hardening checks of Project 10 to cover application configurations, file integrity, service states, network configuration, scheduled jobs, and user account state — producing a daily drift dashboard and auto-remediating low-risk drift while escalating high-risk changes for human review.

🏦 2. Real-Time Banking Scenario

The Story: SecureBank's annual PCI-DSS QSA assessment is underway. The QSA asks for evidence of File Integrity Monitoring (FIM) on all CDE servers — PCI-DSS Req 11.5.2 mandates it. The InfoSec team scrambles. AIDE is installed on most CDE servers, but its database hasn't been updated in 4 months (meaning it's comparing against a 4-month-old baseline), and the nightly AIDE scan results are emailed to a shared mailbox that nobody actively monitors.

Separately, three P2 incidents in the past quarter had root causes traceable to configuration drift: (1) A dev engineer ran systemctl disable firewalld on a UAT server that shares a VLAN with production — firewalld was disabled, never re-enabled, and during a VLAN misconfiguration the UAT server briefly bridged traffic to a production segment. (2) An application team member edited /etc/hosts on a CBS app server to point a third-party API hostname to a staging IP for testing — forgot to revert it, causing production CBS to hit a staging endpoint for 3 days. (3) An unauthorized cron job was added by a contractor to /etc/cron.d/ on a payment gateway server to run a diagnostic script every 5 minutes — the script opened a reverse shell. It took 11 days to detect.

With Project 13's drift detection: the /etc/hosts modification is detected within 6 hours (next scheduled drift scan). The unauthorized cron job triggers a P1 alert within 6 hours. The firewalld disable is detected and auto-remediated within 6 hours. The QSA sees a daily AIDE report, Ansible drift dashboard, and 12-month drift event log — full PCI-DSS Req 11.5.2 evidence.

❗ 3. Problem Statement

  • No fleet-wide configuration baseline exists — without knowing the intended state, detecting drift is impossible. Configuration is what engineers remember it should be, not what it actually is.
  • AIDE (Advanced Intrusion Detection Environment) installed but unmaintained — 4-month-old baseline means FIM is comparing against a stale reference, not the current approved state.
  • Service state drift goes undetected — services disabled or enabled outside change management are invisible until an incident.
  • Unauthorized cron jobs are a known attack vector in banking environments — contractor access and application teams regularly add cron jobs without formal approval.
  • File permission drift — critical files (sudoers, sshd_config, /etc/passwd) should have specific permissions; unexpected changes are a pre-cursor to privilege escalation.
  • No CMDB reconciliation — CMDB says server X has 16GB RAM and runs Tomcat 10.1.18, but the actual server has 32GB and Tomcat 10.1.20. CMDB-driven compliance reports are meaningless.
  • Drift remediation is purely reactive — engineers fix things when reported, with no SLA tracking or evidence trail for audit.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. AIDE scans run nightly via cron, results emailed to a shared mailbox. Nobody reads these emails systematically.
  2. AIDE baseline updated "when someone remembers" — typically after a major release or when AIDE starts generating too many false positives from legitimate changes.
  3. Service state: checked manually during incidents. No proactive fleet-wide service state audit exists.
  4. Cron job audit: only performed on specific servers during security incidents. No baseline of approved cron jobs exists fleet-wide.
  5. CMDB: updated when engineers remember to raise a CMDB update ticket. Typically 2–6 weeks behind actual server state.
  6. Drift remediation: ad-hoc, documented in incident tickets (if at all). No SLA tracking or reporting to InfoSec or audit teams.

Core Ansible Components

  • check_mode: true globally on detection playbook — guaranteed no changes
  • block/rescue per category — one category failure never skips remaining categories
  • Jinja2: drift report HTML and CSV templates, ServiceNow CMDB payload template

Red Hat AAP Components

  • Job Templates: Drift-Detect-All (check mode), Drift-Remediate-Auto, Drift-Remediate-Manual (survey: target_host, category), AIDE-Baseline-Rebuild, CMDB-Reconcile
  • Workflow: Drift-Daily-Pipeline (detect → report → auto-remediate low-risk → escalate high-risk)
  • Schedule: Drift-Detect-All: every 6 hours; Drift-Remediate-Auto: daily 02:00 IST; CMDB-Reconcile + AIDE-Baseline-Rebuild: weekly Sunday 03:00 IST
  • Survey (Drift-Remediate-Manual): target_host, drift_category, dry_run
  • Notification: PagerDuty P1 for cron/FIM/permissions on CDE; Slack #drift-alerts for P2/P3; daily HTML report emailed to InfoSec
  • RBAC: Drift-Detect: read-only — all engineers; Drift-Remediate: InfoSec + Platform team only

drift_remediate_auto.yml
---
- name: SecureBank — Configuration Drift Auto-Remediation (Low-Risk Only)
  hosts: all_managed
  become: true
  gather_facts: true
  serial: "25%"
  max_fail_percentage: 10
  vars_files:
    - group_vars/vault.yml
  vars:
    # Auto-remediation ONLY for explicitly low-risk categories
    # File integrity (AIDE) and cron drift always require human approval
    auto_remediate_services: true
    auto_remediate_permissions: true
    auto_remediate_kernel: true
    auto_remediate_network_hosts: false   # /etc/hosts changes: human review required
    auto_remediate_cron: false            # Cron: always human review
    auto_remediate_aide: false            # AIDE findings: always human review

  roles:
    - role: drift_services
      when: auto_remediate_services | bool
    - role: drift_permissions
      when: auto_remediate_permissions | bool
    - role: drift_kernel
      when: auto_remediate_kernel | bool
    - role: drift_report
Design Rationale
check_mode: true at playbook level — Setting check_mode globally means EVERY task in EVERY role runs in check mode, regardless of whether individual tasks have check_mode: false overrides. This guarantees the detection playbook makes absolutely no changes. Running detection every 6 hours must be completely non-disruptive to production servers.
Separate detection and remediation playbooks — Detection and remediation are deliberately separate: detection runs every 6 hours on all 400 servers simultaneously. Remediation runs daily at 02:00 IST (low-traffic window) with serial:25% to avoid simultaneous restarts across the fleet. The detected drift list from the 6-hourly run feeds the daily remediation run.
drift_events: [] initialized in play vars — Every role appends its findings to this list via set_fact: drift_events: "{{ drift_events + [new_finding] }}". The drift_report role reads the complete list at the end to generate the per-server and fleet-wide report. This accumulation pattern ensures the report is complete even if one category has zero drift.

Role: drift_services — Service State Audit

roles/drift_services/tasks/main.yml
---
- name: Collect all systemd service facts
  ansible.builtin.service_facts:
  register: all_services

- name: Check required services are running and enabled
  ansible.builtin.set_fact:
    drift_events: >-
      {{ drift_events + [{
        'category': 'service_state',
        'server': inventory_hostname,
        'finding': 'REQUIRED_SERVICE_NOT_RUNNING',
        'service': item,
        'current_state': ansible_facts.services[item ~ '.service'].state | default('NOT_FOUND'),
        'expected_state': 'running',
        'severity': 'P1' if item in ['auditd','firewalld','sshd'] else 'P2',
        'auto_remediable': true,
        'detected_at': ansible_date_time.iso8601
      }] }}
  loop: "{{ required_services }}"
  when: >-
    ansible_facts.services[item ~ '.service'] is not defined or
    ansible_facts.services[item ~ '.service'].state != 'running'

- name: Check prohibited services are NOT running
  ansible.builtin.set_fact:
    drift_events: >-
      {{ drift_events + [{
        'category': 'service_state',
        'server': inventory_hostname,
        'finding': 'PROHIBITED_SERVICE_RUNNING',
        'service': item,
        'current_state': ansible_facts.services[item ~ '.service'].state | default('unknown'),
        'expected_state': 'stopped/absent',
        'severity': 'P1',
        'auto_remediable': true,
        'detected_at': ansible_date_time.iso8601
      }] }}
  loop: "{{ prohibited_services }}"
  when: >-
    ansible_facts.services[item ~ '.service'] is defined and
    ansible_facts.services[item ~ '.service'].state == 'running'

- name: AUTO-REMEDIATE — Restart required services that are not running
  ansible.builtin.systemd:
    name: "{{ item.service }}"
    state: started
    enabled: true
  loop: "{{ drift_events | selectattr('finding', 'equalto', 'REQUIRED_SERVICE_NOT_RUNNING') | selectattr('server', 'equalto', inventory_hostname) | list }}"
  loop_control:
    label: "{{ item.service }}"
  when:
    - not ansible_check_mode
    - auto_remediate_services | default(false) | bool
    - item.auto_remediable | bool

- name: AUTO-REMEDIATE — Stop prohibited services
  ansible.builtin.systemd:
    name: "{{ item.service }}"
    state: stopped
    enabled: false
  loop: "{{ drift_events | selectattr('finding', 'equalto', 'PROHIBITED_SERVICE_RUNNING') | selectattr('server', 'equalto', inventory_hostname) | list }}"
  loop_control:
    label: "{{ item.service }}"
  when:
    - not ansible_check_mode
    - auto_remediate_services | default(false) | bool
Line-by-Line Explanation
ansible.builtin.service_facts — Collects a dictionary of ALL systemd units and their state (running/stopped/failed), sub_state, and status (enabled/disabled). The result is stored in ansible_facts.services as a dict keyed by unit name (e.g., ansible_facts.services['firewalld.service']). This single module call replaces dozens of individual systemctl is-active commands.
ansible_facts.services[item ~ '.service'] — The ~ operator concatenates strings in Jinja2. Service names in the services dict always include the .service suffix. This pattern avoids duplicating the suffix in the required_services list while still looking up the correct key in the facts dict.
when: not ansible_check_mode on remediation tasks — The auto-remediation tasks explicitly check not ansible_check_mode before executing. This makes the same role file safe to include in both the detection playbook (check_mode=true, remediation skipped) and the remediation playbook (check_mode=false, remediation executes). No need for separate task files.
Severity classification inline: 'P1' if item in ['auditd','firewalld','sshd'] else 'P2' — Security-critical services (auditd, firewalld, sshd) being down is P1 (immediate pagerduty). Other required services (chronyd) being down is P2 (Slack alert, fix within 24h). The severity is embedded in the drift_event dict and drives the notification routing in the report role.

Role: drift_cron — Unauthorized Cron Job Detection

roles/drift_cron/tasks/main.yml
---
- name: Collect all cron files from system cron directories
  ansible.builtin.find:
    paths:
      - /etc/cron.d
      - /etc/cron.daily
      - /etc/cron.weekly
      - /etc/cron.monthly
      - /etc/cron.hourly
    file_type: file
    recurse: false
  register: system_cron_files

- name: Read approved cron fingerprints from baseline file
  ansible.builtin.slurp:
    src: "{{ approved_cron_fingerprints_file }}"
  register: approved_crons_raw
  failed_when: false

- name: Parse approved cron fingerprints
  ansible.builtin.set_fact:
    approved_crons: "{{ approved_crons_raw.content | b64decode | from_json if approved_crons_raw.content is defined else [] }}"

- name: Compute MD5 checksum of each discovered cron file
  ansible.builtin.stat:
    path: "{{ item.path }}"
    checksum_algorithm: md5
    get_checksum: true
  loop: "{{ system_cron_files.files }}"
  loop_control:
    label: "{{ item.path | basename }}"
  register: cron_file_stats

- name: Detect cron files not in the approved fingerprint list
  ansible.builtin.set_fact:
    drift_events: >-
      {{ drift_events + [{
        'category': 'unauthorized_cron',
        'server': inventory_hostname,
        'finding': 'UNAUTHORIZED_CRON_FILE',
        'cron_file': item.item.path,
        'md5_checksum': item.stat.checksum,
        'severity': 'P1',
        'auto_remediable': false,
        'remediation_note': 'Rename to .disabled and investigate',
        'detected_at': ansible_date_time.iso8601
      }] }}
  loop: "{{ cron_file_stats.results }}"
  loop_control:
    label: "{{ item.item.path | basename }}"
  when: >-
    item.stat.checksum not in (approved_crons | map(attribute='md5') | list)
    and item.item.path | basename not in (approved_crons | map(attribute='filename') | list)

- name: Collect all user crontabs
  ansible.builtin.shell: |
    for user in $(cut -d: -f1 /etc/passwd); do
      crontab -l -u "$user" 2>/dev/null && echo "USER:$user"
    done
  register: user_crontabs
  changed_when: false

- name: Flag any non-root user crontab entries as requiring review
  ansible.builtin.set_fact:
    drift_events: >-
      {{ drift_events + [{
        'category': 'user_crontab',
        'server': inventory_hostname,
        'finding': 'NON_ROOT_USER_CRONTAB_EXISTS',
        'detail': user_crontabs.stdout_lines | select('match','^USER:(?!root)') | list | join(', '),
        'severity': 'P2',
        'auto_remediable': false,
        'detected_at': ansible_date_time.iso8601
      }] }}
  when: user_crontabs.stdout | regex_search('USER:(?!root)')

- name: QUARANTINE — Rename unauthorized cron files to .disabled (non-destructive)
  ansible.builtin.shell: >
    mv {{ item.cron_file }} {{ item.cron_file }}.ansible-quarantine-{{ ansible_date_time.iso8601_basic_short }}
  loop: >-
    {{ drift_events
       | selectattr('finding','equalto','UNAUTHORIZED_CRON_FILE')
       | selectattr('server','equalto',inventory_hostname)
       | list }}
  loop_control:
    label: "{{ item.cron_file | basename }}"
  when:
    - not ansible_check_mode
    - quarantine_unauthorized_crons | default(false) | bool
  changed_when: true
Line-by-Line Explanation
MD5-based fingerprinting: checksum_algorithm: md5 — Each cron file's content is MD5-hashed. The approved fingerprints file stores both the approved filename AND the MD5 of its content. This detects two drift scenarios: (1) a new unknown file in /etc/cron.d (filename not in approved list) and (2) an approved-filename file whose content has been modified (filename matches but MD5 doesn't). The contractor reverse-shell scenario: a file named diagnostics appears in /etc/cron.d — unknown filename → immediate P1.
not in (approved_crons | map(attribute='md5') | list) — Jinja2 pipeline: extracts the 'md5' field from each dict in the approved_crons list, produces a list of approved hashes, then checks if the current file's hash is in that list. Two conditions combined with AND: neither the hash nor the filename should match an approved entry — avoids false positives for approved cron files whose content hasn't changed.
Quarantine rather than delete: mv ... .ansible-quarantine-timestamp — Unauthorized cron files are renamed to a quarantine extension rather than deleted. This preserves forensic evidence (what was the script doing?) while immediately disabling it (cron won't execute files with non-standard extensions). The security team can then review the quarantined file before deciding whether to restore it (if legitimate) or delete it (if malicious).
User crontab enumeration: crontab -l -u "$user" for every user in /etc/passwd — Iterates all system and user accounts checking for personal crontabs. Non-root user crontabs are flagged as P2 for review — not auto-quarantined because some application service accounts have legitimate crontabs. The flag triggers a review process, not immediate action.

Role: drift_network — /etc/hosts & Port Monitoring

roles/drift_network/tasks/main.yml
---
- name: Read current /etc/hosts content
  ansible.builtin.slurp:
    src: /etc/hosts
  register: etc_hosts_content

- name: Parse /etc/hosts into lines (strip comments and blanks)
  ansible.builtin.set_fact:
    current_hosts_entries: >-
      {{ (etc_hosts_content.content | b64decode).split('\n')
         | reject('match', '^#')
         | reject('match', '^\s*$')
         | map('trim')
         | list }}

- name: Detect unauthorized /etc/hosts entries
  ansible.builtin.set_fact:
    drift_events: >-
      {{ drift_events + [{
        'category': 'network_config',
        'server': inventory_hostname,
        'finding': 'UNAUTHORIZED_HOSTS_ENTRY',
        'entry': item,
        'severity': 'P1',
        'auto_remediable': false,
        'remediation_note': 'Manual investigation required — possible DNS spoofing or MITM setup',
        'detected_at': ansible_date_time.iso8601
      }] }}
  loop: "{{ current_hosts_entries }}"
  when: item not in approved_hosts_entries

- name: Collect all TCP/UDP listening ports
  ansible.builtin.shell: >
    ss -tlnpH | awk '{print $4}' | grep -oP ':\K[0-9]+$' | sort -un
  register: open_ports
  changed_when: false

- name: Detect unexpected listening ports not in approved baseline
  ansible.builtin.set_fact:
    drift_events: >-
      {{ drift_events + [{
        'category': 'network_config',
        'server': inventory_hostname,
        'finding': 'UNEXPECTED_LISTENING_PORT',
        'port': item,
        'severity': 'P2',
        'auto_remediable': false,
        'remediation_note': 'Identify the process and verify it is authorized',
        'detected_at': ansible_date_time.iso8601
      }] }}
  loop: "{{ open_ports.stdout_lines }}"
  when: item | int not in (approved_listening_ports | default([22, 8443, 1521, 6379, 61616]))
Line-by-Line Explanation
/etc/hosts drift — This is the scenario from the story: a developer mapped a third-party API hostname to a staging IP in /etc/hosts, causing CBS to hit staging for 3 days. The approved_hosts_entries list in group_vars defines exactly which entries should exist. Any line not in that list (after stripping comments and blank lines) is an unauthorized entry — flagged P1 for immediate investigation as it's a classic DNS poisoning or MITM setup technique.
ss -tlnpH | awk '{print $4}' | grep -oP ':\K[0-9]+' — Uses ss (socket statistics, the modern replacement for netstat) to list all TCP listening sockets. The awk extracts the local address:port column; the grep regex :\K[0-9]+$ captures only the port number after the last colon (handles both IPv4 127.0.0.1:22 and IPv6 [::]:22 format). The port list is then compared against an approved baseline.
auto_remediable: false for all network findings — Network configuration changes (/etc/hosts, unexpected ports) always require human investigation before remediation. An unexpected port might be a legitimate new service that needs CMDB and firewall updates — or it might be a reverse shell. Auto-removing it could break an approved service. Human review is mandatory for network drift.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: How do you differentiate between authorized configuration changes and configuration drift in your automation?
Three mechanisms: (1) AIDE baseline rebuild — every time an authorized change is deployed through the change management process, the AIDE-Baseline-Rebuild job is triggered post-deployment, updating the baseline to the new approved state. Changes detected after a baseline rebuild are by definition unauthorized. (2) Approved cron fingerprints file — maintained by the security team, updated through a formal change request. Any cron file not matching an approved fingerprint is unauthorized by definition. (3) Change window suppression — the drift detection playbook accepts a suppress_alerts_for_change_window: true flag that delays PagerDuty alerts during approved maintenance windows, reducing false positives during legitimate changes.
Q: What is PCI-DSS Req 11.5.2 and how does your automation satisfy it?
PCI-DSS Req 11.5.2 requires deploying a change-detection mechanism (such as file integrity monitoring tools) on all critical system files, configuration files, and content files, with alerting of unauthorized modification. Our automation satisfies this through: (1) AIDE installed and configured on all CDE servers, scanning against a maintained baseline, (2) nightly AIDE scans with results fed into the drift detection pipeline, (3) P1 alerts on any AIDE finding on CDE servers within 6 hours of detection, and (4) 12-month retention of all drift events and AIDE scan results as QSA evidence. The AIDE baseline rebuild audit log demonstrates that the baseline is kept current and that changes to the baseline are authorized and tracked.
Q: How do you prevent the drift detection from triggering false positives during a legitimate deployment?
Four strategies: (1) AIDE baseline rebuild is triggered as part of the deployment workflow (Project 12) after each release — the drift detection then compares against the post-release baseline. (2) Approved cron fingerprints file is updated as part of the release process before the deployment. (3) Maintenance window flag in the drift detection survey suppresses PagerDuty (but still logs to the event file) during known change windows. (4) For service state changes during upgrades (Project 11 rolling upgrade briefly stops services), the rolling upgrade workflow temporarily adds the affected services to a suppression list before stopping them.

Architecture & Production Questions

Q: How do you handle AIDE performance on a 400-server fleet? AIDE scans can be slow.
AIDE scan duration depends entirely on how many paths are in the aide.conf. The full AIDE scan (all filesystem paths) can take 20+ minutes on a busy server. For production banking servers, we use a targeted AIDE configuration that only monitors security-critical paths: /etc/, /usr/bin/, /usr/sbin/, /boot/, /lib/, and application config directories — not /var/, /tmp/, or /home/. Targeted scans complete in 2–5 minutes. The forks=50 setting in Ansible means all 400 servers run simultaneously, so fleet-wide AIDE takes as long as the slowest single scan plus coordination overhead — typically under 10 minutes total.
Q: Why use JSONL (JSON Lines) format for the drift event log rather than a single JSON file?
JSONL stores one JSON object per line, making the log file appendable without parsing and rewriting the entire file. With 400 servers scanning every 6 hours, appending individual events with lineinfile is atomic and safe for concurrent writes. A single large JSON array file would require reading, deserializing, appending, and reserializing the entire file on every event — not scalable at 400 servers × 6 checks/day × 7 drift categories. JSONL also works naturally with log analysis tools (grep, jq) and can be streamed to ELK or Splunk without parsing overhead.
Q: How does CMDB reconciliation handle a server that legitimately changed (e.g., RAM upgraded) vs one that's incorrectly registered?
From Ansible's perspective, there's no functional difference — Ansible facts are always authoritative for what the server actually IS. When Ansible detects RAM mismatch (CMDB says 16GB, actual is 32GB), it auto-updates the CMDB to 32GB regardless of why the discrepancy exists. The drift event log records the before/after values and timestamp. If the RAM upgrade was unauthorized (server was modified outside change management), the CMDB update is still correct — but the drift event log provides the evidence trail that a change occurred on a specific date, which the change management team can then investigate against their CAB records.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Configuration drift is continuous — it cannot be solved with a one-time audit. Only automated, scheduled detection creates the continuous visibility needed in a banking environment.
  • AIDE is only useful if the baseline is current — a 4-month-old baseline generates massive false positives from legitimate changes, causing alert fatigue that leads to the FIM system being ignored entirely.
  • Unauthorized cron jobs are one of the most common persistence mechanisms in banking server compromises — automated cron auditing with P1 alerting is a critical security control.
  • Separate detection from remediation — check_mode detection runs frequently and safely; remediation runs on a schedule with human review for high-risk categories.

Common Mistakes

  • Auto-remediating /etc/hosts changes — an unknown hosts entry might be evidence of an active compromise; auto-reverting it destroys forensic evidence and may alert the attacker that they've been detected.
  • Running AIDE --init after drift to "fix" the alert — this defeats the purpose of FIM entirely. AIDE baseline updates must only happen after verified authorized changes.
  • Using failed_when: true on aide --check — AIDE returns exit code 1 when it detects changes (normal behavior). Treating this as a task failure stops the play instead of processing the findings.
  • Not having an approved cron fingerprints file — without a baseline of what cron entries SHOULD exist, any cron audit is a manual comparison exercise with no automated enforcement.

Production Best Practices

  • Always quarantine (rename) rather than delete unauthorized files — forensic evidence is critical in a banking environment; deletion is irreversible and destroys the investigation trail.
  • AIDE configuration should cover /etc/, binary paths, and app configs — NOT /var/, /tmp/, or log directories. Monitoring volatile paths creates constant noise that masks real signals.
  • Integrate AIDE baseline rebuild into deployment workflows as a mandatory post-deploy step — not an optional manual step that gets forgotten.
  • Store drift event logs in JSONL format with 12-month retention on NFS — directly satisfies RBI IT Framework §8.2 and PCI-DSS Req 10.7 audit log retention requirements.
