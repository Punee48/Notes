Project 10: DNS, NTP & LDAP Infrastructure Validation Automation

DNS, NTP, and LDAP are the three invisible pillars of every banking IT environment. DNS failure means no application can resolve hostnames — Oracle TNS fails, application URLs break, monitoring loses visibility. NTP drift means Kerberos authentication breaks (AD-joined servers reject logins), Oracle RAC nodes split-brain, and audit log timestamps become legally unreliable. LDAP failure means no user can log into any Linux server via AD authentication — engineers are locked out, applications using LDAP authentication fail, and PAM-LDAP sessions drop. This project automates comprehensive validation of all three across all 3,500 Linux servers — checking from both the server perspective (is the client configured correctly?) and from the service perspective (is the server actually responding correctly?).

🏦 1. The Banking Story

Setting: ABC Global Bank's 3,500 Linux servers authenticate users via SSSD+LDAP against Active Directory. DNS resolution uses internal BIND servers. NTP synchronization uses internal Chrony servers (synchronized from RBI's NTP infrastructure). All three are critical for daily operations.

Incident 1 — The NTP Drift Catastrophe: A network routing change caused 847 servers in the Chennai DC to lose connectivity to the NTP servers. Over 4 days, their clocks drifted by 6 minutes 43 seconds. On the 5th day, Kerberos authentication failed on all 847 servers — engineers could not SSH using their AD credentials. The Kerberos protocol rejects authentication tickets older than 5 minutes. 847 servers were effectively locked out. Emergency fix: use root local login to manually re-sync NTP. Time to fix all 847 servers: 3.5 hours of frantic work by 8 engineers. Every Oracle RAC cluster in Chennai also showed clock skew warnings and one cluster fenced its second node as a precaution.

Incident 2 — The DNS Split-Brain: A misconfiguration in the primary BIND DNS server created a split-brain: the server returned different IP addresses for cbs-db01.abcbank.in depending on which server asked. Application servers in Mumbai got 10.10.4.10 (correct). Application servers in Chennai got 10.10.4.11 (wrong — that was CBS DB node 2, but applications expected to connect to node 1 for specific DG setup). Database connections from 200 Chennai app servers failed silently for 6 hours.

Incident 3 — The LDAP Lockout: The SSSD cache on 340 servers expired simultaneously (all provisioned on the same day with the same SSSD cache timeout). When SSSD tried to refresh from LDAP, the LDAP server was temporarily unreachable. All 340 servers fell back to cached credentials — which had expired. Engineers were locked out of 340 servers during a critical patching window.

The Ask: "Monitor DNS resolution, NTP drift, and LDAP connectivity from every server, every 15 minutes. Alert before drift becomes critical. Verify DNS returns the same answer from all servers. Auto-restart SSSD when LDAP binding fails."

📚 2. Key Concepts

DNS Validation — What to Check
Forward resolution: hostname → IP address. dig cbs-db01.abcbank.in A
Reverse resolution: IP → hostname. dig -x 10.10.4.10
Consistency check: all servers should get the same IP for the same hostname
Response time: DNS should respond within 500ms — slow DNS degrades all applications
DNS server reachability: is the configured resolver responding?
DNSSEC validation: enterprise BIND zones should be DNSSEC-signed

In banking, the most impactful check is cross-datacenter consistency — the same hostname must resolve to the same IP from every data center. Split-brain DNS (different answers from different locations) is extremely difficult to diagnose.
NTP Validation — Why It Matters So Much
Kerberos: Requires all clocks within 5 minutes (300 seconds) of each other. Drift beyond 5 minutes → ALL Kerberos authentication fails → engineers locked out, applications fail.
Oracle RAC: RAC nodes must be within 2ms of each other. Excessive skew → node eviction (CSS daemon fences the slow node).
Audit logs: RBI requires accurate timestamps on all security events. Clock skew makes log correlation legally unreliable.
TLS certificates: SSL handshake fails if the server clock is far outside the certificate validity window.

Tools: RHEL 8/9 uses chronyd (preferred) or ntpd. Check with chronyc tracking or ntpq -p.
LDAP/SSSD Validation — Authentication Stack
On RHEL 8/9 Linux servers joined to Active Directory:
SSSD (System Security Services Daemon): The main daemon that handles AD authentication, caches credentials, and bridges PAM/NSS to LDAP/Kerberos.
PAM (Pluggable Authentication Modules): Uses SSSD to authenticate users at SSH login.
NSS (Name Service Switch): Uses SSSD to resolve AD users/groups for file permissions.

What to validate:
• Is sssd.service running?
• Can SSSD bind to LDAP? (sssctl domain-status)
• Can we look up an AD user? (id username)
• Is the SSSD cache valid? (not expired)
• Is Kerberos ticket obtainable? (kinit)

💻 8. DNS Validation Role

roles/dns_validation/tasks/check_forward.yml
---
# =====================================================================
# Forward DNS Resolution Validation
# Checks every critical FQDN returns the expected IP
# This catches the "split-brain DNS" scenario from our incident
# =====================================================================

- name: Check DNS resolver port is reachable
  ansible.builtin.wait_for:
    host: "{{ item }}"                                   # DNS server IP
    port: 53                                              # DNS port
    timeout: 5
    state: started
  loop: "{{ dns_internal_resolvers }}"
  loop_control:
    label: "DNS server {{ item }}"
  register: dns_port_checks
  failed_when: false
  delegate_to: "{{ inventory_hostname }}"

- name: Initialize DNS check results
  ansible.builtin.set_fact:
    dns_check_results: []

- name: Resolve each critical FQDN using dig
  ansible.builtin.shell:
    cmd: >
      dig @{{ dns_internal_resolvers | first }}
          +short +time=3 +tries=1
          {{ item.key }} A
    # @resolver: use our internal DNS server
    # +short: return only the answer (IP address)
    # +time=3: 3-second timeout per query
    # +tries=1: only one attempt (fail fast)
    executable: /bin/bash
  register: dig_results
  loop: "{{ dns_critical_records | dict2items }}"
  loop_control:
    label: "Resolving {{ item.key }}"
  changed_when: false
  failed_when: false

- name: Evaluate DNS resolution results
  ansible.builtin.set_fact:
    dns_check_results: >-
      {{ dns_check_results + [{
        'fqdn': item.item.key,
        'expected_ip': item.item.value,
        'resolved_ip': item.stdout | trim | default('NXDOMAIN'),
        'correct': (item.stdout | trim == item.item.value),
        'timed_out': item.rc == 9,
        'nxdomain': item.stdout | trim == ''
      }] }}
  loop: "{{ dig_results.results }}"
  loop_control:
    label: "{{ item.item.key }}"

- name: Identify DNS resolution failures
  ansible.builtin.set_fact:
    dns_failures: >-
      {{ dns_check_results
         | rejectattr('correct', 'equalto', true)
         | list }}

- name: Log DNS resolution check results
  ansible.builtin.debug:
    msg:
      - "DNS Forward Resolution — {{ inventory_hostname }}"
      - "Checked: {{ dns_check_results | length }} FQDNs"
      - "All correct: {{ dns_failures | length == 0 }}"
      - "Failures: {{ dns_failures | map(attribute='fqdn') | list | join(', ') | default('None') }}"

- name: Alert on DNS resolution failures
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "dns-failure-{{ inventory_hostname }}-{{ item.fqdn | replace('.', '-') }}"
      payload:
        summary: >-
          🔴 DNS FAILURE on {{ inventory_hostname }}:
          {{ item.fqdn }} resolved to {{ item.resolved_ip }}
          but expected {{ item.expected_ip }}.
          Applications using this FQDN may connect to wrong server!
        severity: error
        source: ansible-dns-monitor
        custom_details:
          host: "{{ inventory_hostname }}"
          fqdn: "{{ item.fqdn }}"
          expected: "{{ item.expected_ip }}"
          actual: "{{ item.resolved_ip }}"
          nxdomain: "{{ item.nxdomain }}"
    status_code: [202]
  loop: "{{ dns_failures }}"
  loop_control:
    label: "{{ item.fqdn }}"
  when: dns_failures | length > 0
  delegate_to: localhost
roles/dns_validation/tasks/check_reverse.yml
---
# =====================================================================
# Reverse DNS Validation — PTR records
# Forward and reverse DNS must match — mismatch causes security warnings
# Some banking apps (Oracle, Kerberos) use PTR verification
# =====================================================================

- name: Perform reverse DNS lookup for each critical IP
  ansible.builtin.shell:
    cmd: >
      dig @{{ dns_internal_resolvers | first }}
          +short +time=3 +tries=1
          -x {{ item.value }} 2>/dev/null
    # -x IP: reverse lookup (creates IN-ADDR.ARPA query automatically)
    # Returns the PTR record for the IP
  register: reverse_dig_results
  loop: "{{ dns_critical_records | dict2items }}"
  loop_control:
    label: "Reverse lookup for {{ item.value }}"
  changed_when: false
  failed_when: false

- name: Check forward/reverse consistency
  ansible.builtin.set_fact:
    ptr_mismatches: >-
      {{ ptr_mismatches | default([]) + [{
        'ip': item.item.value,
        'expected_fqdn': item.item.key + '.',
        'ptr_result': item.stdout | trim | default('NO PTR RECORD'),
        'consistent': (item.stdout | trim | lower == (item.item.key + '.') | lower)
      }] }}
  loop: "{{ reverse_dig_results.results }}"
  loop_control:
    label: "{{ item.item.value }}"

- name: Warn on PTR record mismatches
  ansible.builtin.debug:
    msg: >-
      ⚠️ Reverse DNS mismatch on {{ inventory_hostname }}:
      IP={{ item.ip }} PTR={{ item.ptr_result }}
      Expected={{ item.expected_fqdn }}
  loop: "{{ ptr_mismatches | rejectattr('consistent') | list }}"
  loop_control:
    label: "{{ item.ip }}"

🕐 9. NTP Validation Role

roles/ntp_validation/tasks/check_offset.yml
---
# =====================================================================
# NTP Clock Offset Measurement using chronyc
# This is the check that would have caught the 6-minute drift incident
# =====================================================================

- name: Check if chronyd service is running
  ansible.builtin.service_facts:
  become: true

- name: Set NTP service status fact
  ansible.builtin.set_fact:
    ntp_service_running: >-
      {{ (ntp_service_name + '.service') in ansible_facts.services
         and ansible_facts.services[ntp_service_name + '.service'].state == 'running' }}

- name: Get chronyc tracking output (clock offset measurement)
  ansible.builtin.command:
    cmd: chronyc tracking
    # chronyc tracking: shows current NTP sync status
    # Key output lines:
    # "System time : 0.000012345 seconds slow of NTP time"
    # "Last offset : -0.000012345 seconds"
    # "RMS offset  : 0.000023456 seconds"
    # "Leap status : Normal" (or "Not synchronised")
  register: chronyc_tracking
  changed_when: false
  become: true
  failed_when: false

- name: Extract clock offset from chronyc output
  ansible.builtin.set_fact:
    ntp_offset_seconds: >-
      {{ chronyc_tracking.stdout
         | regex_search('System time\s*:\s*([\d.]+) seconds', '\\1')
         | first | default('9999') | float }}
    ntp_synchronized: >-
      {{ 'Not synchronised' not in chronyc_tracking.stdout
         and chronyc_tracking.rc == 0 }}
    ntp_leap_status: >-
      {{ chronyc_tracking.stdout
         | regex_search('Leap status\s*:\s*(.+)', '\\1')
         | first | default('Unknown') | trim }}
    # regex_search extracts the numeric offset value from chronyc output
    # default('9999'): if extraction fails, set to very high value to trigger alert

- name: Classify NTP offset severity
  ansible.builtin.set_fact:
    ntp_severity: >-
      {{ 'EMERGENCY' if ntp_offset_seconds | float >= ntp_offset_emergency_seconds
         else ('CRITICAL' if ntp_offset_seconds | float >= ntp_offset_critical_seconds
               else ('WARNING' if ntp_offset_seconds | float >= ntp_offset_warn_seconds
                     else 'OK')) }}

- name: Get NTP source reachability
  ansible.builtin.command:
    cmd: chronyc sources -v
    # chronyc sources: shows all configured NTP sources and their status
    # '*' prefix: currently syncing source
    # '+' prefix: acceptable source
    # '-' prefix: not currently used
    # '?' prefix: unreachable source
  register: chronyc_sources
  changed_when: false
  become: true
  failed_when: false

- name: Check if any NTP source is reachable
  ansible.builtin.set_fact:
    ntp_has_reachable_source: >-
      {{ chronyc_sources.stdout_lines
         | select('match', '^[*+].*')
         | list | length > 0 }}
    # Lines starting with * or + are reachable/usable sources

- name: Log NTP status
  ansible.builtin.debug:
    msg:
      - "NTP Status — {{ inventory_hostname }}"
      - "Service: {{ 'RUNNING' if ntp_service_running else 'STOPPED' }}"
      - "Synchronized: {{ ntp_synchronized }}"
      - "Offset: {{ ntp_offset_seconds }}s"
      - "Severity: {{ ntp_severity }}"
      - "Has reachable source: {{ ntp_has_reachable_source }}"

- name: Fire EMERGENCY PagerDuty alert — NTP drift near Kerberos failure threshold
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "ntp-emergency-{{ inventory_hostname }}"
      payload:
        summary: >-
          🚨 EMERGENCY NTP DRIFT: {{ inventory_hostname }} clock is
          {{ ntp_offset_seconds }}s off (Kerberos fails at 300s).
          AD authentication will BREAK on this server within minutes!
        severity: critical
        source: ansible-ntp-monitor
        custom_details:
          host: "{{ inventory_hostname }}"
          offset_seconds: "{{ ntp_offset_seconds }}"
          synchronized: "{{ ntp_synchronized }}"
          ntp_source_reachable: "{{ ntp_has_reachable_source }}"
          kerberos_failure_threshold: "300 seconds"
    status_code: [202]
  delegate_to: localhost
  when: ntp_severity == 'EMERGENCY'

- name: Fire CRITICAL PagerDuty alert — NTP drift high
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "ntp-critical-{{ inventory_hostname }}"
      payload:
        summary: >-
          ⚠️ CRITICAL NTP DRIFT: {{ inventory_hostname }} offset is
          {{ ntp_offset_seconds }}s (threshold: {{ ntp_offset_critical_seconds }}s).
          Investigate NTP connectivity immediately.
        severity: error
        source: ansible-ntp-monitor
    status_code: [202]
  delegate_to: localhost
  when: ntp_severity == 'CRITICAL'

- name: Auto-resolve NTP alert when offset returns to OK
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: resolve
      dedup_key: "ntp-critical-{{ inventory_hostname }}"
    status_code: [202]
  delegate_to: localhost
  when: ntp_severity == 'OK'
roles/ntp_validation/tasks/remediate_drift.yml
---
# =====================================================================
# NTP Drift Remediation — Force immediate clock resync
# Used when offset is too large for gradual slewing (chrony's default)
# =====================================================================

- name: Force immediate clock step using chronyc makestep
  ansible.builtin.command:
    cmd: chronyc makestep
    # makestep: immediately step the clock to the correct time
    # (rather than gradually slewing which can take hours for large offsets)
    # WARNING: This causes a discontinuous clock jump — safe for most apps
    # but can cause Oracle RAC clock-skew detection to trigger
    # Use only when drift is significant (> 60 seconds)
  register: makestep_result
  changed_when: true
  become: true

- name: Verify offset after forced step
  ansible.builtin.command:
    cmd: chronyc tracking
  register: post_step_tracking
  changed_when: false
  become: true

- name: Extract new offset after makestep
  ansible.builtin.set_fact:
    post_step_offset: >-
      {{ post_step_tracking.stdout
         | regex_search('System time\s*:\s*([\d.]+) seconds', '\\1')
         | first | default('unknown') }}

- name: Log remediation result
  ansible.builtin.debug:
    msg:
      - "NTP Drift Remediation — {{ inventory_hostname }}"
      - "Before offset: {{ ntp_offset_seconds }}s"
      - "After makestep: {{ post_step_offset }}s"
      - "makestep output: {{ makestep_result.stdout }}"

playbooks/dns_consistency_check.yml — Cross-DC DNS Check
---
# =====================================================================
# Cross-Datacenter DNS Consistency Check
# Verifies same FQDNs resolve to same IPs from different DCs
# This is the check that catches split-brain DNS
# =====================================================================
- name: DNS Cross-DC Consistency Validation
  hosts: all_linux
  gather_facts: false
  serial: 100                                # Faster — just DNS queries

  vars_files:
    - "{{ inventory_dir }}/group_vars/all/vault.yml"

  tasks:
    - name: Query each critical FQDN from this server's DNS resolver
      ansible.builtin.shell:
        cmd: >
          dig @{{ dns_internal_resolvers | first }}
              +short +time=3 {{ item.key }} A
      register: local_dns_results
      loop: "{{ dns_critical_records | dict2items }}"
      loop_control:
        label: "{{ item.key }} from {{ inventory_hostname }}"
      changed_when: false
      failed_when: false

    - name: Store DNS results as host fact for cross-server comparison
      ansible.builtin.set_fact:
        this_server_dns: >-
          {{ dict(local_dns_results.results
             | map(attribute='item.key')
             | zip(local_dns_results.results | map(attribute='stdout') | map('trim'))) }}
      # dict(keys, values): creates dict pairing FQDN with resolved IP per server

# Run on control node — aggregate all servers' results and find inconsistencies
- name: Identify DNS Inconsistencies Across Datacenters
  hosts: localhost
  gather_facts: false

  tasks:
    - name: Compare DNS answers across all servers
      ansible.builtin.set_fact:
        dns_inconsistencies: >-
          {{ dns_inconsistencies | default([]) + [{
            'fqdn': fqdn,
            'inconsistent': (hostvars.values()
                             | selectattr('this_server_dns', 'defined')
                             | map(attribute='this_server_dns')
                             | map(attribute=fqdn, default='N/A')
                             | list | unique | length > 1),
            'answers_seen': (hostvars.values()
                             | selectattr('this_server_dns', 'defined')
                             | map(attribute='this_server_dns')
                             | map(attribute=fqdn, default='N/A')
                             | list | unique)
          }] }}
      loop: "{{ dns_critical_records.keys() | list }}"
      loop_control:
        loop_var: fqdn

    - name: Alert on DNS inconsistencies (split-brain detection)
      ansible.builtin.uri:
        url: "{{ slack_webhook_url }}"
        method: POST
        body_format: json
        body:
          text: >-
            🔴 *DNS SPLIT-BRAIN DETECTED*
            The following FQDNs resolve to DIFFERENT IPs from different servers:
            {% for issue in dns_inconsistencies | selectattr('inconsistent') | list %}
            • {{ issue.fqdn }}: {{ issue.answers_seen | join(' vs ') }}
            {% endfor %}
            _This was the root cause of the 6-hour CBS connectivity incident!_
        status_code: [200]
      when: dns_inconsistencies | selectattr('inconsistent') | list | length > 0

🎯 15. Interview Prep

Q: Why is NTP drift critical for banking Linux servers, and what exactly breaks at 300 seconds?
Kerberos protocol: Requires all participants (clients and servers) to have clocks within 5 minutes (300 seconds) of each other. This is by design — it prevents replay attacks. An attacker capturing a Kerberos ticket cannot reuse it after 5 minutes because the timestamp embedded in the ticket will appear "too old" to the server.

When clock drift exceeds 300 seconds on a Linux server: the Kerberos ticket obtained by kinit (or by SSSD automatically) has a timestamp that the Domain Controller considers expired. The DC rejects it with "KRB5KRB_AP_ERR_SKEW" (clock skew too great). Every SSH login via AD credentials fails. Every application using Kerberos auth fails. The server effectively becomes inaccessible to AD users.

Our automation alerts at 250 seconds — giving engineers 50 seconds to respond before complete lockout.
Q: How does your cross-DC DNS consistency check detect split-brain DNS?
Split-brain DNS means the same FQDN resolves to different IPs from different network locations. Standard per-server monitoring can't detect this because each server only checks its own DNS answer — which looks correct from its perspective.

Our two-play approach: Play 1 runs on ALL client servers, stores DNS answers as this_server_dns host facts. Play 2 runs on localhost and accesses hostvars — Ansible's global dictionary of all host variables from all servers. By comparing the DNS answers across all hostvars entries, we can find FQDNs where different servers got different IPs. This is only possible because Ansible aggregates all host facts into hostvars, accessible from any play in the same playbook run.
Q: What is SSSD and how does it differ from directly querying LDAP?
SSSD (System Security Services Daemon) is a middleware daemon that sits between Linux system services (PAM, NSS) and identity providers (AD via LDAP+Kerberos).

Key advantages over direct LDAP:
1. Caching: SSSD caches user/group information locally. If AD is unreachable, users can still log in using cached credentials (for a configurable duration). Direct LDAP has no cache — AD outage = immediate lockout.
2. Kerberos integration: SSSD handles both LDAP (for user info) and Kerberos (for authentication) together. Direct LDAP only does password-based authentication.
3. Offline mode: When AD is unreachable, SSSD shows "Offline" status but continues serving cached data. Direct LDAP fails completely.

sssctl domain-status shows whether SSSD is in Online (talking to AD) or Offline (using cache) mode — crucial for identifying partial LDAP failures where SSSD is running but AD is unreachable.
Q: How do you handle the case where chronyc tracking output format varies between RHEL 8 and RHEL 9?
The regex pattern System time\s*:\s*([\d.]+) seconds uses \s* (zero or more whitespace) to handle spacing differences between versions. However, if the label itself changes (e.g., RHEL 9 might say "Clock error" instead of "System time"), the regex would return empty.

Defense strategies:
1. Use default('9999') — if regex returns nothing, set offset to 9999 to trigger alert (fail-safe: alerting on unknown is safer than ignoring)
2. Try multiple regex patterns and use the first non-empty match
3. Parse the full chronyc tracking output line by line and look for lines containing "second" or "offset"
4. Use chronyc -c (CSV mode in newer chrony) which gives machine-parseable output: chronyc -c tracking returns comma-separated values in a stable format across versions.
