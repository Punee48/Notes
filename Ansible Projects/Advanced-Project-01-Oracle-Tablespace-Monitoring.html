Project 01: Oracle Database Tablespace Monitoring & Automated Space Management

This is the first project of your 30-project Intermediate to Advanced Enterprise Ansible Automation series for Banking environments. We begin with one of the most critical daily DBA tasks in any bank running Oracle databases: tablespace monitoring and automated space management. Every Oracle DBA in a bank spends significant time monitoring tablespace usage, responding to "tablespace full" emergencies, and managing space. This project automates it completely — from monitoring to alerting to auto-extension to compliance reporting.

🏦 1. The Banking Story — How This Project Was Born

Setting: We joined ABC Global Bank as Senior DevOps Engineers. The bank operates 47 Oracle 19c databases across 3 data centers in Mumbai, Chennai, and Pune. These databases power the Core Banking System (CBS), Loan Management System (LMS), Treasury Management System (TMS), and the SWIFT messaging platform.

The Incident: On a Tuesday morning at 09:47 AM, the bank's Core Banking System threw a critical error across all 2,400 branch terminals simultaneously. NEFT, RTGS, and IMPS transactions were failing. The CBS application team escalated to P1 (the highest severity). After 38 minutes of investigation, the DBA team found the root cause: the CBS_DATA tablespace on the production Oracle RAC database had reached 100% capacity. The tablespace had 98.7% utilization at 8:00 AM — but nobody noticed because the monitoring alert was set at 95% and had been firing for 3 days. Nobody acted on the alert because "the DBA on duty didn't check emails over the weekend."

The Business Impact: 38-minute outage × 2,400 branches × estimated ₹50,000 per minute in lost transactions = ₹19 crore in direct impact. Plus RBI sent a formal letter asking for the root cause analysis and corrective actions within 7 days.

The Ask: Our manager called an emergency meeting. "We need automated tablespace monitoring that doesn't rely on someone checking emails. We need proactive space management. And we need a compliance report for RBI showing we have controls in place."

Our Solution: We designed and implemented a complete Oracle Tablespace Monitoring and Automated Space Management system using Ansible and Red Hat AAP — monitoring every 30 minutes, three-tier alerting, automatic datafile addition for approved tablespaces, and a daily compliance report. This is what we built.

📚 7. Oracle Database Concepts You Must Know

Senior Engineer Note: Before writing Ansible code for Oracle, you must understand these Oracle storage concepts. Many automation engineers fail Oracle DBA projects because they don't know the domain.
What is a Tablespace?
A tablespace is Oracle's logical storage container. Think of it like a folder. All database objects (tables, indexes) live inside tablespaces. A tablespace consists of one or more datafiles (physical files on disk).

Example: CBS_DATA tablespace has 3 datafiles: cbs_data01.dbf (10GB), cbs_data02.dbf (10GB), cbs_data03.dbf (8GB) = 28GB total. If all 28GB is used, no new data can be inserted → application fails.
Key Oracle Views for Monitoring
Oracle SQL — Key Monitoring Queries
-- DBA_TABLESPACE_USAGE_METRICS: Best view for percentage used
-- Available in Oracle 11g R2 and above
SELECT
    TABLESPACE_NAME,           -- Name of tablespace (e.g., CBS_DATA)
    TABLESPACE_SIZE / 1024 / 1024 / 1024 AS total_gb,  -- Total size in GB
    USED_SPACE / 1024 / 1024 / 1024 AS used_gb,        -- Used space in GB
    (TABLESPACE_SIZE - USED_SPACE) / 1024 / 1024 / 1024 AS free_gb,
    USED_PERCENT                -- Percentage used (critical metric)
FROM DBA_TABLESPACE_USAGE_METRICS
ORDER BY USED_PERCENT DESC;

-- DBA_DATA_FILES: Shows individual datafiles for a tablespace
SELECT
    TABLESPACE_NAME,
    FILE_NAME,                 -- Physical file path: /u02/oradata/CBS/cbs_data01.dbf
    BYTES / 1024 / 1024 AS size_mb,    -- Current size in MB
    MAXBYTES / 1024 / 1024 AS max_mb,  -- Max size if AUTOEXTEND ON
    AUTOEXTENSIBLE             -- YES or NO
FROM DBA_DATA_FILES
WHERE TABLESPACE_NAME = 'CBS_DATA'
ORDER BY FILE_NAME;
What is Auto-Extension?
When you create a datafile, you can enable AUTOEXTEND which allows Oracle to automatically grow the file when space runs out. However, relying only on AUTOEXTEND is dangerous — if the filesystem runs out of space, AUTOEXTEND will also fail. Our automation takes a different approach: we proactively add a new datafile when the tablespace reaches 85%, giving us control over which filesystem the new file goes on.
cx_Oracle Python Driver
Ansible connects to Oracle databases using a Python library called cx_Oracle (now renamed to python-oracledb). This must be installed in the Ansible Execution Environment. The library requires Oracle Instant Client to be available.

In Ansible, we use the community.oracle.oracle_query module or raw Python scripts via ansible.builtin.script with cx_Oracle.

⚙️ 8. Prerequisites

On Oracle Database Servers

  • Oracle 19c or 21c installed
  • DBA monitoring user created (read-only)
  • DBA admin user for extension operations
  • Oracle listener running on port 1521
  • TNS connectivity from AAP execution node
  • Python 3.8+ available

On AAP Execution Node

  • Oracle Instant Client 21.x installed
  • cx_Oracle or python-oracledb Python library
  • Custom Execution Environment (EE) with cx_Oracle
  • Oracle JDBC connectivity allowed (firewall: port 1521)
  • Vault credential for Oracle passwords

Create Oracle Monitoring User (DBA runs this once)

Oracle SQL — Create Monitoring User
-- Connect as SYSDBA to create the monitoring user
-- Run this on each Oracle database ONCE before automation starts

-- Create read-only monitoring user
CREATE USER ansible_monitor                          -- Username for Ansible read-only access
  IDENTIFIED BY "SecurePass@2024"                   -- Strong password (stored in Ansible Vault)
  DEFAULT TABLESPACE USERS                           -- Default tablespace for user
  TEMPORARY TABLESPACE TEMP                          -- Temp tablespace
  ACCOUNT UNLOCK;                                    -- Make sure account is unlocked

-- Grant minimum permissions for tablespace monitoring
GRANT CREATE SESSION TO ansible_monitor;             -- Allow login to database
GRANT SELECT ON DBA_TABLESPACES TO ansible_monitor;  -- View tablespace definitions
GRANT SELECT ON DBA_DATA_FILES TO ansible_monitor;   -- View datafiles
GRANT SELECT ON DBA_FREE_SPACE TO ansible_monitor;   -- View free space
GRANT SELECT ON DBA_TABLESPACE_USAGE_METRICS TO ansible_monitor;  -- Key monitoring view
GRANT SELECT ON V_$TABLESPACE TO ansible_monitor;    -- V$ view (note: V_$ not V$)
GRANT SELECT ON V_$DATABASE TO ansible_monitor;      -- Database info

-- Create admin user for extension operations (used only for ALTER TABLESPACE)
CREATE USER ansible_dba                              -- Admin user for extension
  IDENTIFIED BY "AdminSecure@2024"                   -- Stored in Ansible Vault (separate secret)
  ACCOUNT UNLOCK;

GRANT CREATE SESSION TO ansible_dba;                 -- Allow login
GRANT ALTER TABLESPACE TO ansible_dba;               -- Allow tablespace modification
GRANT CREATE TABLESPACE TO ansible_dba;              -- Allow new tablespace (future use)

-- Commit changes
COMMIT;

In AAP Production: You do NOT create this vault.yml file at all. Instead, you create a Custom Credential Type in AAP with fields for each Oracle password, then create a Credential of that type. AAP injects these as environment variables or extra vars when the job runs. This is more secure than vault files because passwords never touch the filesystem.

Role 1: oracle_tablespace_monitor

roles/oracle_tablespace_monitor/tasks/main.yml
---
# =====================================================================
# Oracle Tablespace Monitor — Main Task Entry Point
# Calls sub-task files in the correct order
# =====================================================================

- name: Display which database we are monitoring           # Shows in AAP job output
  ansible.builtin.debug:
    msg: >                                                  # Multi-line message using >
      Starting tablespace monitoring for
      DB: {{ oracle_sid }}
      Host: {{ inventory_hostname }}
      DC: {{ datacenter }}

- name: Ensure Python cx_Oracle library is available       # Pre-check before running
  ansible.builtin.command:                                 # Run shell command
    cmd: python3 -c "import cx_Oracle; print('OK')"       # Import test — exits 0 if OK
  register: cxoracle_check                                 # Save result to variable
  changed_when: false                                      # This task never "changes" anything
  failed_when: cxoracle_check.rc != 0                     # Fail if cx_Oracle not installed

- name: Copy tablespace query script to target server      # Upload our Python query script
  ansible.builtin.copy:                                    # Copy module: local file to remote
    src: "{{ role_path }}/files/query_tablespaces.py"     # Source: in role's files/ dir
    dest: /tmp/query_tablespaces.py                        # Destination on DB server
    mode: '0700'                                           # Executable, readable only by owner
    owner: oracle                                          # Oracle OS user owns the file
  # Why copy to /tmp? The ansible user may not have permission to write elsewhere.
  # /tmp is always writable. We clean up after execution.

- name: Execute tablespace query against Oracle database    # Run the Python script
  ansible.builtin.shell:                                   # Shell module (not command — need env)
    cmd: >
      python3 /tmp/query_tablespaces.py
      --host {{ ansible_host }}
      --port {{ oracle_port }}
      --sid {{ oracle_sid }}
      --user {{ oracle_monitor_user }}
      --password "{{ vault_oracle_monitor_pass }}"
    executable: /bin/bash                                   # Use bash for execution
  register: tablespace_query_result                         # Save the JSON output
  changed_when: false                                       # Query never changes the DB
  no_log: true                                              # CRITICAL: hides password from logs!
  # no_log: true prevents the password from appearing in AAP job output
  # Without this, anyone with AAP job view access can see the Oracle password

- name: Parse tablespace JSON results into Ansible variable # Convert JSON string to dict
  ansible.builtin.set_fact:                                 # Create an Ansible fact (variable)
    tablespace_data: "{{ tablespace_query_result.stdout | from_json }}"
    # from_json: Jinja2 filter that converts JSON string to Python dict/list
    # tablespace_data will be a list of dicts, one per tablespace

- name: Display tablespace summary                         # Human-readable output in AAP
  ansible.builtin.debug:
    msg: "Found {{ tablespace_data | length }} tablespaces on {{ oracle_sid }}"

- name: Include alert classification tasks                  # Call sub-task file
  ansible.builtin.include_tasks:                            # Include another task file
    file: classify_alerts.yml                               # Determines severity of each TSP

- name: Include alert sending tasks                         # Send notifications
  ansible.builtin.include_tasks:
    file: send_alerts.yml                                   # PagerDuty + Slack

- name: Remove temporary query script from server          # Cleanup — security best practice
  ansible.builtin.file:                                    # File module for file operations
    path: /tmp/query_tablespaces.py                        # File to remove
    state: absent                                          # absent = delete the file
  # Always clean up scripts that contain connection logic
roles/oracle_tablespace_monitor/tasks/classify_alerts.yml
---
# =====================================================================
# Classify each tablespace into severity levels
# This creates three lists: warning, critical, emergency
# =====================================================================

- name: Initialize alert lists as empty                    # Always initialize before using
  ansible.builtin.set_fact:
    warning_tablespaces: []                                # Will hold 75-85% tablespaces
    critical_tablespaces: []                               # Will hold 85-95% tablespaces
    emergency_tablespaces: []                              # Will hold >95% tablespaces

- name: Classify tablespaces into severity buckets
  ansible.builtin.set_fact:
    # ── EMERGENCY: > 95% ─────────────────────────────────────────────
    emergency_tablespaces: >-
      {{ tablespace_data
         | selectattr('used_percent', '>=', threshold_emergency)
         | list }}
    # selectattr: Jinja2 filter — select items where used_percent >= 95
    # list: Convert the filter result to an actual list

    # ── CRITICAL: between 85% and 95% ───────────────────────────────
    critical_tablespaces: >-

Python Query Script — cx_Oracle Integration

roles/oracle_tablespace_monitor/files/query_tablespaces.py
#!/usr/bin/env python3
"""
Oracle Tablespace Query Script
Usage: python3 query_tablespaces.py --host HOST --port PORT --sid SID
       --user USER --password PASS
Output: JSON array of tablespace data
"""

import cx_Oracle          # Oracle connectivity library
import json               # For JSON output (Ansible reads this)
import argparse           # For command-line argument parsing
import sys                # For exit codes

def parse_args():
    """Parse command line arguments"""
    parser = argparse.ArgumentParser(description='Query Oracle tablespace usage')
    parser.add_argument('--host', required=True, help='Oracle host')
    parser.add_argument('--port', required=True, type=int, help='Oracle listener port')
    parser.add_argument('--sid', required=True, help='Oracle SID')
    parser.add_argument('--user', required=True, help='Oracle username')
    parser.add_argument('--password', required=True, help='Oracle password')
    return parser.parse_args()

def query_tablespaces(host, port, sid, user, password):
    """Connect to Oracle and query tablespace usage"""

    # Build Oracle DSN (connection string)
    # Format: host:port/sid
    dsn = cx_Oracle.makedsn(host, port, sid=sid)

    # Connect to Oracle
    conn = cx_Oracle.connect(
        user=user,
        password=password,
        dsn=dsn,
        encoding="UTF-8"          # Always specify encoding
    )

    cursor = conn.cursor()        # Create cursor for SQL execution

    # Query tablespace usage from DBA_TABLESPACE_USAGE_METRICS
    # This view gives the most accurate used_percent
    sql = """
        SELECT
            t.TABLESPACE_NAME,
            ROUND(m.TABLESPACE_SIZE / 1024 / 1024 / 1024, 2) AS TOTAL_GB,
            ROUND(m.USED_SPACE / 1024 / 1024 / 1024, 2) AS USED_GB,
            ROUND((m.TABLESPACE_SIZE - m.USED_SPACE) / 1024 / 1024 / 1024, 2) AS FREE_GB,
            ROUND(m.USED_PERCENT, 2) AS USED_PERCENT,
            t.CONTENTS,
            t.STATUS
        FROM DBA_TABLESPACE_USAGE_METRICS m
        JOIN DBA_TABLESPACES t ON m.TABLESPACE_NAME = t.TABLESPACE_NAME
        WHERE t.CONTENTS != 'TEMPORARY'
        ORDER BY m.USED_PERCENT DESC
    """
    # We exclude TEMPORARY tablespaces because their usage fluctuates constantly
    # and they self-clean — alerting on them creates noise

    cursor.execute(sql)

    # Get column names from cursor description
    columns = [desc[0].lower() for desc in cursor.description]
    # .lower() converts column names to lowercase for consistency

    # Build list of dicts (one per tablespace)
    results = []
    for row in cursor.fetchall():
        results.append(dict(zip(columns, row)))
        # zip(columns, row): pairs column names with values
        # dict(...): converts paired tuples to a dictionary

    cursor.close()
    conn.close()
    return results

def main():
    args = parse_args()

    try:
        tablespaces = query_tablespaces(
            args.host, args.port, args.sid,
            args.user, args.password
        )
        # Output as JSON to stdout — Ansible captures this with register
        print(json.dumps(tablespaces, default=str))
        sys.exit(0)                               # Exit 0 = success

    except cx_Oracle.DatabaseError as e:
        # Output error as JSON so Ansible can parse it
        error = {"error": str(e), "host": args.host, "sid": args.sid}
        print(json.dumps(error), file=sys.stderr) # Write to stderr
        sys.exit(1)                               # Exit 1 = failure

if __name__ == "__main__":
    main()

- name: Log eligible tablespaces for extension

- name: Determine next datafile number for each tablespace
  # Oracle datafiles are usually named: tablespace_name_01.dbf, 02.dbf, etc.
  # We need to find the next available number
  ansible.builtin.shell:
    cmd: >
      python3 -c "
      import cx_Oracle, json

      conn = cx_Oracle.connect('{{ oracle_dba_user }}', '{{ vault_oracle_dba_pass }}', dsn)
      cur = conn.cursor()
      cur.execute('''
        SELECT TABLESPACE_NAME, COUNT(*) as FILE_COUNT,
               MAX(FILE_NAME) as LAST_FILE
        FROM DBA_DATA_FILES
        WHERE TABLESPACE_NAME = :1
        GROUP BY TABLESPACE_NAME
      ''', ['{{ item.tablespace_name }}'])
      row = cur.fetchone()
      print(json.dumps({'count': row[1], 'last_file': row[2]}))
      conn.close()
      "
  register: datafile_info
  loop: "{{ eligible_for_extension }}"
  loop_control:
    label: "{{ item.tablespace_name }}"
  changed_when: false
  no_log: true                                              # Hide Oracle credentials from logs

🔄 15. Execution Flow — What Happens Every 30 Minutes

1
AAP Scheduler fires every 30 min. Launches Oracle-Tablespace-Monitor job template. Custom Oracle-EE spins up.
2
Playbook runs against all 47 Oracle servers (serial:5, so 5 at a time). For each server: Python script uploaded to /tmp, cx_Oracle connects via TNS to Oracle DB, queries DBA_TABLESPACE_USAGE_METRICS, returns JSON.
3
Ansible parses JSON, runs through classify_alerts tasks. Creates three lists: emergency (>95%), critical (85-95%), warning (75-85%).
4
For emergency tablespaces: PagerDuty P1 fires immediately — on-call DBA woken up. For critical tablespaces: PagerDuty P2 fires. For warning: Slack message to #dba-alerts channel.
5
For CRITICAL tablespaces in the approved list (CBS_DATA, LMS_DATA etc.): auto-extension role triggers. New datafile added. PagerDuty auto-resolved after extension confirmed.
6
For CRITICAL tablespaces NOT in approved list (SYSTEM, UNDOTBS1): Workflow pauses at Approval Node. Slack message to DBA Lead with approve/deny link. DBA reviews and acts.
7
Daily at 06:00 AM: Compliance Report job generates HTML report with all tablespace statuses. Auto-emailed to CISO, DBA Lead, and RBI Compliance Team. Stored on NFS for 1 year.

🎯 17. Interview Preparation

Q: What is the difference between DBA_TABLESPACE_USAGE_METRICS and DBA_FREE_SPACE?
DBA_FREE_SPACE shows the raw free space in each tablespace but does NOT account for space that can be reclaimed (expired undo, unused extents). This can lead to over-reporting space as "full" when it's actually not.

DBA_TABLESPACE_USAGE_METRICS is newer (11g R2+) and gives a more accurate picture — it considers the actual used space vs total capacity including AUTOEXTEND potential. We always prefer this view for monitoring because it gives the USED_PERCENT directly without manual calculation.
Q: Why do you add a NEW datafile instead of just enabling AUTOEXTEND?
Two reasons:
1. Control over filesystem placement: AUTOEXTEND grows the existing datafile on the same filesystem. If that filesystem is almost full, AUTOEXTEND will also fail. Adding a new datafile allows us to choose a different filesystem — potentially a different SAN volume.
2. Size cap: AUTOEXTEND can grow unboundedly (up to OS limits) if MAXSIZE is not set. Explicitly adding a fixed-size datafile gives deterministic, controlled growth.
Q: How did you avoid exposing Oracle passwords in Ansible logs?
Three techniques:
1. no_log: true on any task that uses passwords in command arguments — prevents the entire task output from appearing in AAP job logs.
2. AAP Custom Credential Types — passwords are injected as environment variables, never passed as command-line arguments or stored in playbook files.
3. The Python script receives passwords as arguments, but since no_log: true is set on the calling Ansible task, the arguments never appear in logs.

Additionally, all Python temp scripts are removed immediately after execution to prevent credentials lingering on disk.
Q: Why use serial: 5 in the monitor playbook?
serial: 5 means Ansible processes 5 databases at a time, not all 47 simultaneously. Reasons:
1. Resource control: 47 simultaneous Oracle connections from the AAP node could exceed connection limits or overwhelm the monitoring infrastructure.
2. Graceful failure handling: If 5 databases are processed at a time and 2 fail, the remaining 42 databases still get monitored. Without serial, a single connection failure during parallel execution could cascade.
3. Network consideration: 47 simultaneous SCP transfers (uploading the Python script) could saturate bandwidth.
