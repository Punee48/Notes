Project 02: Oracle Database Listener Validation & Auto-Recovery Automation

The Oracle Listener is the front door to every Oracle database. When the listener goes down, every application that connects to Oracle — Core Banking, Loans, Treasury, SWIFT — loses connectivity instantly. This project automates listener health validation across all Oracle RAC and single-instance databases, detects failed or hanging listeners, restarts them automatically, validates TNS connectivity from application servers, analyzes listener logs for errors, and generates a daily listener health report.

🏦 1. The Banking Story

Setting: We are two months into our role at ABC Global Bank. The Oracle tablespace automation (Project 1) is running smoothly. Our manager calls us for an urgent meeting.

The Incident: It's 3:17 AM on a Thursday. The SWIFT payment processing system at ABC Bank attempts to send international wire transfers to correspondent banks. Every transaction fails with "ORA-12541: TNS:no listener." The SWIFT application team escalates to P1. The NOC engineer on duty tries to SSH into the database server — it's reachable. He runs lsnrctl status. The listener shows "The Listener is not currently known to be running." It had died silently at 2:44 AM. Nobody knows why. The DBA on call takes 22 minutes to be reached (asleep), another 8 minutes to SSH in and restart the listener. 30 minutes of SWIFT downtime — 47 international wire transfers queued, 3 already in breach of payment cutoff times. RBI SWIFT compliance team is involved. The estimated penalty: ₹2.5 crore.

Root Cause: A memory pressure event on the database server caused the listener process to be OOM-killed by the Linux kernel. There was no monitoring, no auto-restart, and no alert.

The Ask: "We need listeners monitored every 5 minutes. Auto-restart if down. And we need TNS connectivity validation from the application servers — not just from the DB server itself. A listener can appear up on the DB server but have TNS connectivity issues that only affect remote clients."

📚 2. Oracle Listener Concepts You Must Know

What is an Oracle Listener?
The Oracle Listener is a server-side process (not a database process) that accepts incoming TCP/IP connection requests and hands them off to the Oracle database. It runs independently of the database — you can restart the database without affecting the listener, and vice versa.

Default port: 1521 (TCP). In banking, this is often changed to a custom port for security.
Process name: tnslsnr on Linux
Config file: $ORACLE_HOME/network/admin/listener.ora
Control tool: lsnrctl (Listener Control Utility)
Key LSNRCTL Commands
LSNRCTL Command Reference
# Check listener status — returns detailed status including services registered
lsnrctl status

# Short version — returns just UP/DOWN
lsnrctl status | grep -i "Connecting to"

# Start the listener (run as oracle OS user)
lsnrctl start

# Stop the listener
lsnrctl stop

# Reload listener.ora without stopping (for config changes)
lsnrctl reload

# Check listener services (what databases are registered)
lsnrctl services

# Get listener version
lsnrctl version

# Check if listener port is open (from remote server)
# This validates TNS connectivity from application server perspective
tnsping CBS_PROD       # Uses TNS alias from tnsnames.ora
tnsping //hostname:1521/CBSPROD   # Direct TNS ping without alias
Oracle RAC Listener Architecture
In Oracle RAC (Real Application Clusters), each node has its OWN listener. A 2-node RAC has:
  • Node 1 Listener (LISTENER_NODE1): Port 1521 on node1 — serves clients connecting to node 1
  • Node 2 Listener (LISTENER_NODE2): Port 1521 on node2 — serves clients connecting to node 2
  • SCAN Listener (SCAN): Runs on the SCAN IP — clients connect here, SCAN distributes across nodes (Oracle 11g+)
Our automation must check ALL three listener types. A common mistake is only checking one node's listener in RAC.
Listener Log File Patterns to Monitor
Common Listener Error Patterns in listener.log
# Listener log location: $ORACLE_BASE/diag/tnslsnr/hostname/listener/trace/listener.log
# Or older Oracle: $ORACLE_HOME/network/log/listener.log

# Error patterns that indicate problems:
# TNS-01190: The user is not authorized to execute the requested listener command
# TNS-12541: TNS:no listener                 ← Listener is down
# TNS-12537: TNS:connection closed           ← Client disconnected abruptly
# TNS-01168: The listener has not been started ← Listener process missing
# ORA-12514: TNS:listener does not currently know of service ← DB not registered
# TNS-04061: The listener is already running ← Duplicate start attempt

# Warning patterns (not critical but worth monitoring):
# TNS-01168: Warning: could not register service  ← DB registration issue
# TNS-12549: TNS: operating system resource quota exceeded ← OS limits

❗ 4. Problem Statement

Current State (Manual)

  • DBA checks listener status once a day via email report from EM
  • No check from application server perspective — "listener up on DB server" ≠ "app can connect"
  • Auto-restart: not configured (Oracle restart not set up for listener)
  • RAC check: usually only one node checked, SCAN never validated
  • Listener log: never analyzed unless there's an incident
  • After SWIFT incident: 30-minute MTTR (Mean Time To Restore)

Target State (Automated)

  • Check every 5 minutes from AAP — 24x7
  • TNS ping validation FROM each application server
  • Auto-restart within 60 seconds of listener failure detection
  • MTTR reduced from 30 min to <2 minutes
  • RAC: all nodes + SCAN checked independently
  • Listener log: daily analysis, alert on error spikes

🛠️ 5. Solution Design

The automation is split into three playbooks that work together:

PlaybookFrequencyWhat It Does
oracle_listener_monitor.ymlEvery 5 minutesCheck process + port + auto-restart if down
oracle_tns_validation.ymlEvery 15 minutesRun tnsping FROM app servers to validate end-to-end TNS
oracle_listener_log_analysis.ymlDaily 02:00 AMParse listener.log for errors, generate daily report
Key Design Decision — Two-Perspective Monitoring: We monitor from BOTH the database server (is the listener process running?) AND the application servers (can the app server actually connect via TNS?). This is essential because firewall rule changes, network issues, or SCAN IP problems can break TNS connectivity even when the listener process appears healthy on the DB server.

roles/oracle_listener_check/tasks/check_process.yml
---
# =====================================================================
# Check if the tnslsnr (Oracle Listener) OS process is running
# =====================================================================

- name: Check if tnslsnr process is running on the server
  ansible.builtin.shell:                                   # shell module for process check
    cmd: "pgrep -f 'tnslsnr {{ oracle_listener_name }}' | wc -l"
    # pgrep -f: search processes by full command line
    # tnslsnr {{ oracle_listener_name }}: matches Oracle listener process
    # wc -l: count the number of matching PIDs
    # Result: "0" = no process, "1" or more = process running
  register: listener_process_count                         # Save result
  changed_when: false                                      # This never changes anything
  become: true                                             # Need root to see all processes
  become_user: root

- name: Set listener process status fact
  ansible.builtin.set_fact:
    listener_process_ok: "{{ listener_process_count.stdout | trim | int > 0 }}"
    listener_pid: "{{ listener_process_count.stdout | trim }}"
    # trim: removes whitespace from stdout
    # int: converts string to integer for comparison
    # > 0: true if at least one listener process found

- name: Log listener process check result
  ansible.builtin.debug:
    msg: >
      Listener process check on {{ inventory_hostname }}:
      Status={{ 'RUNNING' if listener_process_ok else 'NOT FOUND' }}
      Process count={{ listener_pid }}
roles/oracle_listener_check/tasks/check_port.yml
---
# =====================================================================
# Check if port 1521 is open and accepting connections
# A listener can be "running" but not actually accepting connections
# (e.g., if it's in the process of starting up or hung)
# =====================================================================

- name: Check if Oracle listener port is accepting TCP connections
  ansible.builtin.wait_for:                                # wait_for: checks TCP port
    host: "{{ ansible_host }}"                             # DB server IP
    port: "{{ oracle_port }}"                              # Default: 1521
    timeout: 10                                            # Wait max 10 seconds
    state: started                                         # started = port should be open
  register: port_check_result                              # Save result
  failed_when: false                                       # Don't fail playbook if port is down
  delegate_to: localhost                                   # Test from AAP controller perspective
  # delegate_to: localhost is CRITICAL here.
  # We want to test if the port is reachable from OUTSIDE the DB server.
  # If we run this ON the DB server, it would use localhost — not the same as
  # testing remote connectivity that applications need.

- name: Set port check status fact
  ansible.builtin.set_fact:
    listener_port_ok: "{{ port_check_result.elapsed is defined and port_check_result.elapsed < 10 }}"
    listener_port_response_ms: "{{ (port_check_result.elapsed | default(0) * 1000) | int }}"
    # elapsed: how many seconds it took to connect
    # Multiply by 1000 for milliseconds

- name: Log port check result
  ansible.builtin.debug:
    msg: >
      Listener port check {{ ansible_host }}:{{ oracle_port }}
      Result: {{ 'OPEN' if listener_port_ok else 'CLOSED/TIMEOUT' }}
      Response time: {{ listener_port_response_ms }}ms
roles/oracle_listener_check/tasks/check_lsnrctl.yml
---
# =====================================================================
# Run lsnrctl status and parse the output
# lsnrctl status gives detailed information about:
# - Is listener running?
# - What database services are registered?
# - What version is the listener?
# =====================================================================

- name: Run lsnrctl status as oracle OS user
  ansible.builtin.shell:                                   # shell needed for environment vars
    cmd: "lsnrctl status {{ oracle_listener_name }}"       # lsnrctl status LISTENER
  register: lsnrctl_output                                 # Capture full output
  changed_when: false                                      # Read-only — no changes
  failed_when: false                                       # Don't fail if listener is down
  become: true                                             # Switch to oracle OS user
  become_user: "{{ oracle_user }}"                         # Run as oracle user
  environment: "{{ oracle_env }}"                          # Set ORACLE_HOME, PATH etc.
  # become_user: oracle is critical — lsnrctl must run as the oracle OS user
  # Running as root or ansible user will give authentication errors

- name: Parse listener status from lsnrctl output
  ansible.builtin.set_fact:
    listener_lsnrctl_up: >-
      {{ 'TNS-01190' not in lsnrctl_output.stdout
         and 'not currently known to be running' not in lsnrctl_output.stdout
         and lsnrctl_output.rc == 0 }}
    # Three checks combined:
    # 1. TNS-01190: specific error code for "listener not authenticated" — means it's down
    # 2. "not currently known to be running" — the actual "down" message from lsnrctl
    # 3. rc == 0: successful exit code from lsnrctl

    listener_version: >-
      {{ lsnrctl_output.stdout
         | regex_search('Version ([0-9.]+)', '\\1')
         | first | default('unknown') }}
    # regex_search: extract listener version number from output
    # Example output line: "TNSLSNR for Linux: Version 19.0.0.0.0"

    listener_services_registered: >-
      {{ 'Services Summary...' in lsnrctl_output.stdout
         and 'has' in lsnrctl_output.stdout }}
    # If "Services Summary" is in output, at least one database service is registered
    # If no services registered, apps can't connect even if listener is up

- name: Log lsnrctl status result
  ansible.builtin.debug:
    msg:
      - "lsnrctl status on {{ inventory_hostname }}:"
      - "Listener running: {{ listener_lsnrctl_up }}"
      - "Version: {{ listener_version }}"
      - "Services registered: {{ listener_services_registered }}"

- name: Extract and display registered services from lsnrctl output
  ansible.builtin.debug:
    msg: "{{ lsnrctl_output.stdout_lines | select('match', '.*Service.*|.*Handler.*') | list }}"
  when: listener_lsnrctl_up | bool
roles/oracle_listener_check/tasks/check_scan.yml
---
# =====================================================================
# RAC-specific: Validate SCAN (Single Client Access Name) listener
# SCAN is the primary connection point for RAC — if SCAN fails, ALL
# applications lose connectivity regardless of per-node listener status
# =====================================================================

- name: Check SCAN hostname DNS resolution
  ansible.builtin.command:                                 # command module (no shell features needed)
    cmd: "nslookup {{ oracle_scan_name }}"                 # DNS lookup of SCAN hostname
  register: scan_dns_result
  changed_when: false
  failed_when: false
  delegate_to: localhost                                   # DNS check from external perspective

- name: Ping SCAN IP address to verify network reachability
  ansible.builtin.command:
    cmd: "ping -c 3 -W 2 {{ oracle_scan_ip }}"            # 3 pings, 2-second wait each
    # -c 3: send 3 ICMP packets
    # -W 2: wait 2 seconds for each response
  register: scan_ping_result
  changed_when: false
  failed_when: false
  delegate_to: localhost

- name: Check if SCAN listener port is open
  ansible.builtin.wait_for:
    host: "{{ oracle_scan_ip }}"                           # SCAN IP (not hostname — faster)
    port: "{{ oracle_port }}"                              # Port 1521
    timeout: 10
    state: started
  register: scan_port_result
  failed_when: false
  delegate_to: localhost

- name: Set SCAN validation status facts
  ansible.builtin.set_fact:
    scan_dns_ok: "{{ scan_dns_result.rc == 0 }}"           # DNS resolved successfully?
    scan_ping_ok: "{{ scan_ping_result.rc == 0 }}"         # SCAN IP is pingable?
    scan_port_ok: "{{ scan_port_result.elapsed is defined }}"  # SCAN port is open?
    scan_overall_ok: >-
      {{ scan_dns_result.rc == 0
         and scan_ping_result.rc == 0
         and scan_port_result.elapsed is defined }}

- name: Alert if SCAN is degraded
  ansible.builtin.debug:
    msg: >-
      ⚠️ SCAN ISSUE DETECTED on {{ oracle_sid }}:
      DNS={{ 'OK' if scan_dns_ok else 'FAIL' }}
      Ping={{ 'OK' if scan_ping_ok else 'FAIL' }}
      Port={{ 'OK' if scan_port_ok else 'FAIL' }}
  when: not scan_overall_ok
roles/oracle_listener_check/tasks/classify_status.yml
---
# =====================================================================
# Combine all check results into a single status determination
# Status options: UP | DOWN | HUNG | DEGRADED
# =====================================================================

- name: Determine overall listener status
  ansible.builtin.set_fact:
    listener_overall_status: >-
      {%- if listener_process_ok and listener_port_ok and listener_lsnrctl_up -%}
        {%- if listener_services_registered -%}
          UP
        {%- else -%}
          DEGRADED
        {%- endif -%}
      {%- elif listener_process_ok and not listener_port_ok -%}
        HUNG
      {%- else -%}
        DOWN
      {%- endif -%}
    # Decision tree:
    # process=YES, port=YES, lsnrctl=YES, services=YES → UP (all good)
    # process=YES, port=YES, lsnrctl=YES, services=NO  → DEGRADED (listener up but no DB registered)
    # process=YES, port=NO                              → HUNG (process exists but not accepting)
    # process=NO                                        → DOWN (process missing)

- name: Log final classification
  ansible.builtin.debug:
    msg: >-
      ══════════════════════════════════════════
      LISTENER STATUS: {{ listener_overall_status }}
      DB: {{ oracle_sid }} | Host: {{ inventory_hostname }}
      Process: {{ listener_process_ok }} | Port: {{ listener_port_ok }}
      LSNRCTL: {{ listener_lsnrctl_up }} | Services: {{ listener_services_registered }}
      ══════════════════════════════════════════

  become: true
  become_user: root                                        # Need root to kill oracle processes
  changed_when: true
  when: listener_overall_status == 'HUNG'                 # Only kill if HUNG, not just DOWN

# =====================================================================
# Run tnsping FROM each application server to validate TNS connectivity
# This runs on app servers, not Oracle DB servers
# =====================================================================

- name: Run tnsping for each TNS alias from this app server
  ansible.builtin.command:
    cmd: "tnsping {{ item }} 3"                            # 3 = number of ping attempts
    # tnsping: Oracle tool to test TNS connectivity
    # Simulates exactly what the JDBC driver does when connecting
    # Result: OK = TNS resolves and listener responds
    #         TNS-12541 = no listener
    #         TNS-12154 = TNS alias not found in tnsnames.ora
  register: tnsping_results
  loop: "{{ tns_aliases_to_validate }}"                    # Loop over all TNS aliases
  loop_control:
    label: "{{ item }}"                                    # Show alias name in AAP output
  changed_when: false
  failed_when: false                                       # Don't fail — we classify below
  environment:                                             # Oracle environment for tnsping
    ORACLE_HOME: "{{ app_oracle_home }}"
    TNS_ADMIN: "{{ app_tns_admin }}"                       # Where tnsnames.ora lives on app server
    LD_LIBRARY_PATH: "{{ app_oracle_home }}/lib"
    PATH: "{{ app_oracle_home }}/bin:/usr/bin:/bin"

- name: Parse tnsping results and detect failures
  ansible.builtin.set_fact:
    tns_failures: >-
      {{ tnsping_results.results
         | selectattr('rc', 'ne', 0)
         | list }}
    tns_successes: >-
      {{ tnsping_results.results
         | selectattr('rc', 'equalto', 0)
         | list }}

- name: Extract TNS response times for latency tracking
  ansible.builtin.set_fact:
    tns_response_times: >-
      {{ tnsping_results.results
         | selectattr('rc', 'equalto', 0)
         | map(attribute='stdout')
         | map('regex_search', 'OK \(([0-9]+) msec\)', '\\1')
         | map('first')
         | map('int')
         | list }}
    # regex_search: extracts the milliseconds from "OK (45 msec)" tnsping output
    # map('first'): extracts from regex group
    # map('int'): converts string to integer

- name: Alert if TNS connectivity failure from this app server
  ansible.builtin.uri:
    url: "{{ vault_slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: >-
        🔴 *TNS Connectivity FAILURE*
        *App Server:* {{ inventory_hostname }}
        *Failed TNS Aliases:*
        {% for f in tns_failures %}
        • {{ f.item }}: {{ f.stdout | default(f.stderr) | truncate(100) }}
        {% endfor %}
        _This means applications on {{ inventory_hostname }} CANNOT connect to Oracle_
    status_code: [200]
  delegate_to: localhost
  when: tns_failures | length > 0

- name: Log TNS validation summary
  ansible.builtin.debug:
    msg:
      - "TNS Validation from {{ inventory_hostname }}"
      - "Success: {{ tns_successes | map(attribute='item') | list | join(', ') }}"
      - "Failures: {{ tns_failures | map(attribute='item') | list | join(', ') | default('None') }}"
      - "Avg response time: {{ (tns_response_times | sum / tns_response_times | length) | round(0) | int }}ms"

    method: POST

🔄 14. Execution Flow

1
Every 5 minutes: AAP scheduler fires. Oracle-Listener-Monitor job launches. Custom Oracle-EE starts.
2
For each Oracle server (serial:10): pgrep checks tnslsnr process. wait_for tests port 1521 from AAP controller. lsnrctl status run as oracle user (become: oracle).
3
RAC servers: additionally check SCAN DNS resolution, SCAN IP ping, SCAN port connectivity. All three must pass for SCAN to be considered healthy.
4
classify_status.yml combines results: UP / DOWN / HUNG / DEGRADED per database.
5
If DOWN or HUNG: PagerDuty P1 fires immediately. Auto-recovery starts: kill zombie (if HUNG) → lsnrctl start → wait 15s → verify port open → verify services registered.
6
Recovery successful: PagerDuty auto-resolve. Slack notification: "Listener auto-recovered in 25 seconds." No human involvement needed — MTTR down from 30 min to under 2 min.
7
Recovery failed after max_restart_attempts: escalation PagerDuty alert fires. DBA on call is woken up with full context: what was tried, what failed, what to check next.
8
Every 15 minutes: TNS validation playbook runs on all app servers. tnsping executed from CBS app servers, SWIFT gateways. Any TNS failure = Slack alert — "App server X cannot connect to Oracle via TNS."

🎯 16. Interview Preparation

Q: Why use pgrep to check the listener process instead of lsnrctl status alone?
lsnrctl status requires the listener to respond to a management command — if the listener is hung (process exists but not responding), lsnrctl status will also hang waiting for a response. Using pgrep first gives us an immediate answer about whether the process exists without any risk of hanging. If pgrep shows the process exists but lsnrctl status hangs, we know the listener is HUNG vs DOWN — and the recovery action is different: HUNG needs kill + restart; DOWN just needs start.
Q: What is the difference between a HUNG and DOWN listener?
DOWN: The tnslsnr process does not exist at all. lsnrctl start will create a fresh listener process. Common cause: OOM kill, accidental manual stop.

HUNG: The tnslsnr process exists (pgrep finds it) but it's not accepting connections (port check fails) and lsnrctl status doesn't respond. The process is stuck. Common cause: resource exhaustion, file descriptor limit hit, or the listener is in the middle of a restart that never completed. Recovery: must kill -9 first, then start fresh.
Q: Why validate TNS connectivity from application servers, not just from the DB server?
Multiple scenarios can cause TNS to fail from app servers even when the listener appears healthy from the DB server itself:
1. Firewall rule change blocking port 1521 between app and DB subnets
2. SCAN IP or SCAN listener issue (common in RAC)
3. tnsnames.ora on the app server pointing to wrong IP/hostname
4. Network route issue between specific subnets

By running tnsping FROM the app server, we simulate exactly what the application's JDBC driver would experience. The listener can be perfectly healthy locally while all applications are failing to connect.
Q: How did you reduce MTTR from 30 minutes to under 2 minutes?
Three improvements:
1. Detection time: From 22 minutes (DBA being woken up and responding) to 5 minutes (automated check detects failure at next schedule run)
2. Recovery time: From 8 minutes (DBA SSHing in and running lsnrctl) to 30 seconds (automated recovery runs immediately after detection)
3. Alert quality: Instead of a generic "DB down" page, the PagerDuty alert now includes: which listener, which host, which status (DOWN vs HUNG), what recovery was attempted, and the AAP job URL with full logs — dramatically reducing investigation time even when automation fails and a human must intervene.
