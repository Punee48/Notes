Project 4: SSL/TLS Certificate Lifecycle Management using Red Hat AAP

An expired SSL certificate on a banking portal doesn't just break the website — it triggers browser "Not Secure" warnings that cause customers to abandon sessions, blocks mobile banking apps with certificate pinning, and can trigger PCI-DSS violations if cardholder-data-transmitting endpoints go unencrypted. SecureBank manages 340+ SSL/TLS certificates across internal APIs, customer-facing portals, mobile backends, SWIFT interfaces, and inter-service mTLS — all with different CAs (internal PKI, DigiCert, and Entrust), different key stores (Java KeyStore, OpenSSL PEM, PKCS#12), and different expiry dates. This project automates discovery, expiry monitoring, renewal (via internal EJBCA CA and DigiCert APIs), deployment, and post-renewal validation — replacing frantic manual renewal scrambles with a fully orchestrated, zero-surprise certificate lifecycle.

🏦 2. Real-Time Banking Scenario

The Story: It's a Saturday at 2:17 AM. SecureBank's NOC monitoring fires a P1 alert — the net banking portal (https://netbanking.securebank.in) is returning SSL handshake errors for customers across all browsers. A major banking Twitter account tweets "SecureBank website broken — can't login." The NOC wakes up Karthik, the on-call engineer. After 8 minutes of frantic investigation, the root cause is embarrassingly simple: the DigiCert SSL certificate on the Apache HTTPD load balancer expired at midnight. Nobody noticed because the only "monitoring" was a calendar reminder that three engineers had each assumed one of the others was handling. The renewal request was in an email thread from 3 weeks ago that nobody closed out. 40 minutes of customer impact, a mandatory RBI incident report, and a very difficult Monday morning for the CISO. Six months later, after the SSL Certificate Lifecycle Management automation project goes live, this exact scenario runs as a scheduled AAP job every morning at 6 AM: it scans every cert, finds that netbanking.securebank.in's cert will expire in 58 days, automatically submits the renewal to DigiCert's API, deploys the new cert to both Apache nodes with a graceful reload, and sends a Slack message saying "✅ Certificate renewed successfully — new expiry: 2027-08-14." Nobody wakes up at 2 AM ever again.

❗ 3. Problem Statement

  • No central inventory of all 340+ certs — they're discovered reactively, when they expire and break something.
  • Different cert stores (PEM, JKS, PKCS#12), different CAs (internal PKI, DigiCert, Entrust), different services (Apache, Tomcat, Nginx) — no single team has full visibility.
  • Manual renewal process: engineer generates CSR, emails it to the CA team, waits for the signed cert, manually copies it to each server, restarts the service — 4–6 steps, multiple people, 2–5 days end-to-end.
  • Java keystores require keytool commands; misconfiguration (wrong alias, wrong keystore password) causes Java apps to fail to start — silent failures only discovered post-restart.
  • No post-renewal validation — an engineer installs the cert, restarts Apache, and assumes it's working without confirming from the client perspective what cert is actually being served.
  • SWIFT certs have a 90-day proactive renewal mandate (SWIFT requirement) — the bank has been penalised before for renewing too late.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. Engineer notices a calendar reminder (or worse, a monitoring alert) that a cert is expiring.
  2. Logs into the server, generates a CSR manually: openssl req -new -newkey rsa:4096 -nodes -keyout server.key -out server.csr
  3. Emails the CSR to the CA team (internal PKI) or uploads it to the DigiCert web console.
  4. Waits 1–3 days for the signed certificate to be emailed back.
  5. Copies the cert and chain file to the server via SCP.
  6. Updates the Apache/Nginx/Tomcat configuration file to reference the new cert path.
  7. For Java apps: keytool -importcert with the right alias, keystore path, and password (often wrong on first attempt).
  8. Restarts / reloads the service.
  9. Manually runs openssl s_client -connect hostname:443 to check — no documentation of the validation result.
  10. Repeat for every server behind the load balancer (often forgotten — LB gets new cert, backends don't).

🛠️ 6. Automated Solution Design

The solution is organized into four independently executable phases:

  • Phase 1 — Discovery & Scan: Every morning at 6 AM, Ansible connects to every server in the cert inventory and reads the expiry date of each configured certificate using openssl s_client and openssl x509. Results are stored as host facts and aggregated into a daily expiry report (JSON → Grafana dashboard). Critical/warning/OK status calculated per cert.
  • Phase 2 — CSR Generation & CA Submission: For certs within the renewal threshold, Ansible generates a new 4096-bit RSA key and CSR on the target server (so the private key NEVER leaves the server), then submits the CSR to either the EJBCA REST API (internal CA) or DigiCert API (public CA), depending on the cert category.
  • Phase 3 — Certificate Deployment: Once the signed cert is available (polled from CA API), Ansible deploys it to the correct location per cert type: PEM files for Apache/Nginx, PKCS#12 import into JKS for Tomcat/Java apps. Old certs are backed up with timestamp before overwriting. Service reload is triggered via handlers.
  • Phase 4 — Post-Renewal Validation: Ansible connects to each endpoint from the control node using openssl s_client (simulating a real client TLS handshake) and validates: new cert is being served, expiry is >30 days, CN/SAN matches the expected hostname, the full chain is valid. Any validation failure raises a P1 alert immediately.

⚙️ 8. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.builtin.command (openssl, keytool), ansible.builtin.uri (CA APIs), ansible.builtin.copy, ansible.builtin.file, ansible.builtin.stat, ansible.builtin.template, ansible.builtin.get_url
  • Roles: cert_discovery, cert_csr_generate, cert_ca_submit, cert_deploy_pem, cert_deploy_jks, cert_validate, cert_report
  • Ansible Vault for CA API keys, keystore passwords, PKCS#12 import passwords
  • until / retries / delay for polling the CA API until the signed cert is ready
  • Jinja2 templates for CSR config (openssl.cnf), cert expiry dashboard JSON
  • block/rescue/always — rescue raises P1 alert; always takes backup regardless of success/fail

Red Hat AAP Components

  • Custom Inventory: cert_inventory.yml — a structured YAML inventory where each host has cert metadata (cert_path, cert_type, ca_type, renewal_days_threshold)
  • Credentials: Machine (SSH), Vault (keystore passwords), Custom Credential Types for DigiCert API key and EJBCA API token
  • Job Templates: Cert-Discovery-Scan, Cert-Renew-PEM, Cert-Renew-JKS, Cert-Validate-All
  • Survey: target_fqdn (for on-demand single-cert renewal), force_renew (bool — bypass threshold for emergency re-key)
  • Workflow: Cert-Renewal-Pipeline (discovery → renew-pem → renew-jks → validate → report)
  • Schedule: Daily 06:00 IST for discovery scan; renewal workflow triggered when scan finds certs within threshold
  • Notification: Slack (cert expiry digest) + PagerDuty (validation failure = P1)

💻 11. Complete Project Code (Line-by-Line Explained)

Role: cert_discovery

roles/cert_discovery/tasks/main.yml
---
- name: Initialize per-host cert status list
  ansible.builtin.set_fact:
    host_cert_statuses: []

- name: Check expiry for each certificate defined on this host
  ansible.builtin.command: >
    openssl x509 -noout -enddate -checkend {{ item.renewal_threshold_days * 86400 }}
    -in {{ item.cert_path }}
  loop: "{{ certs }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: cert_expiry_checks
  changed_when: false
  failed_when: false
  when: item.cert_type in ['pem', 'pkcs12']

- name: Extract exact expiry date for each PEM certificate
  ansible.builtin.command: >
    openssl x509 -noout -enddate -in {{ item.cert_path }}
  loop: "{{ certs }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: cert_expiry_dates
  changed_when: false
  when: item.cert_type in ['pem', 'pkcs12']

- name: Extract certificate serial number for audit trail
  ansible.builtin.command: >
    openssl x509 -noout -serial -in {{ item.cert_path }}
  loop: "{{ certs }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: cert_serials
  changed_when: false
  when: item.cert_type in ['pem', 'pkcs12']

- name: Build status record for each certificate
  ansible.builtin.set_fact:
    host_cert_statuses: "{{ host_cert_statuses + [cert_status_entry] }}"
  vars:
    expiry_result: "{{ cert_expiry_checks.results[loop_index] }}"
    expiry_date: "{{ cert_expiry_dates.results[loop_index].stdout | default('UNKNOWN') }}"
    serial: "{{ cert_serials.results[loop_index].stdout | default('UNKNOWN') }}"
    cert_status_entry:
      fqdn: "{{ item.fqdn }}"
      hostname: "{{ inventory_hostname }}"
      cert_path: "{{ item.cert_path }}"
      cert_type: "{{ item.cert_type }}"
      ca_type: "{{ item.ca_type }}"
      expiry_date: "{{ expiry_date }}"
      serial: "{{ serial }}"
      renewal_threshold_days: "{{ item.renewal_threshold_days }}"
      needs_renewal: "{{ expiry_result.rc == 1 }}"
      status: "{{ 'CRITICAL' if expiry_result.rc == 1 else 'OK' }}"
  loop: "{{ certs }}"
  loop_control:
    index_var: loop_index
    label: "{{ item.fqdn }}"
  when: item.cert_type in ['pem', 'pkcs12']

- name: Check JKS keystore certificate expiry
  ansible.builtin.command: >
    keytool -list -v -keystore {{ item.keystore_path }}
    -alias {{ item.keystore_alias }}
    -storepass {{ vault_jks_password }}
    -noprompt
  loop: "{{ certs }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: jks_expiry_checks
  changed_when: false
  no_log: true
  when: item.cert_type == 'jks'

- name: Flag any certificates needing renewal as host facts
  ansible.builtin.set_fact:
    certs_needing_renewal: "{{ host_cert_statuses | selectattr('needs_renewal', 'equalto', true) | list }}"
    all_cert_statuses: "{{ host_cert_statuses }}"
Line-by-Line Explanation
openssl x509 -noout -checkend {{ item.renewal_threshold_days * 86400 }} — The -checkend N flag is the key to threshold-based expiry detection: it returns exit code 0 if the cert will still be valid N seconds from now, or exit code 1 if it will have expired within that window. Multiplying renewal_threshold_days by 86400 converts days to seconds. This single command replaces the need to parse date strings and do calendar math in Ansible.
loop: "{{ certs }}" — Iterates over the structured list of cert definitions in host_vars/group_vars (our YAML inventory). Each host can have multiple certificates; this loop handles all of them cleanly without separate tasks per cert type.
loop_control: index_var: loop_index — Exposes the current iteration index as loop_index, which we use to correlate results across multiple parallel loop registrations (expiry_checks, expiry_dates, serials) — since all three loops run in the same order, matching by index is safe.
failed_when: false on expiry check — Exit code 1 from -checkend means "cert will expire" — a business condition, not an Ansible error. Without failed_when: false, every cert approaching expiry would abort the discovery scan rather than being logged for renewal.
no_log: true on JKS keytool task — The -storepass flag embeds the keystore password directly in the command line, which would otherwise appear in AAP's job output log visible to any user with job read access. no_log: true suppresses this task's entire output from being logged — critical when command arguments contain secrets.
selectattr('needs_renewal', 'equalto', true) — Jinja2 filter that selects only the cert records where needs_renewal is true from the full status list, giving us a clean list of certs to act on in subsequent roles without having to re-check each cert's status.

Role: cert_csr_generate

roles/cert_csr_generate/tasks/main.yml
---
- name: Skip host if no certificates need renewal
  ansible.builtin.meta: end_host
  when: certs_needing_renewal | default([]) | length == 0

- name: Ensure certificate backup directory exists
  ansible.builtin.file:
    path: "{{ cert_backup_dir }}/{{ ansible_date_time.iso8601_basic_short }}"
    state: directory
    owner: root
    group: root
    mode: '0700'
  register: backup_dir_result

- name: Back up existing private key before generating new one
  ansible.builtin.copy:
    src: "{{ item.key_path }}"
    dest: "{{ backup_dir_result.path }}/{{ item.fqdn }}.key.bak"
    remote_src: true
    mode: '0600'
  loop: "{{ certs_needing_renewal }}"
  loop_control:
    label: "{{ item.fqdn }}"
  when: item.cert_type in ['pem', 'pkcs12']

- name: Generate new 4096-bit RSA private key (private key never leaves server)
  ansible.builtin.command: >
    openssl genrsa -out {{ item.key_path }} {{ cert_key_size }}
  loop: "{{ certs_needing_renewal }}"
  loop_control:
    label: "{{ item.fqdn }}"
  args:
    creates: "{{ item.key_path }}.new"
  when: item.cert_type in ['pem', 'pkcs12']

- name: Set restrictive permissions on new private key immediately
  ansible.builtin.file:
    path: "{{ item.key_path }}"
    owner: root
    group: root
    mode: '0400'
  loop: "{{ certs_needing_renewal }}"
  loop_control:
    label: "{{ item.fqdn }}"
  when: item.cert_type in ['pem', 'pkcs12']

- name: Render per-cert OpenSSL CSR config from Jinja2 template
  ansible.builtin.template:
    src: openssl_csr.cnf.j2
    dest: "/tmp/{{ item.fqdn }}-csr.cnf"
    mode: '0600'
  loop: "{{ certs_needing_renewal }}"
  loop_control:
    label: "{{ item.fqdn }}"
  when: item.cert_type in ['pem', 'pkcs12']

- name: Generate Certificate Signing Request (CSR)
  ansible.builtin.command: >
    openssl req -new
    -key {{ item.key_path }}
    -out /tmp/{{ item.fqdn }}.csr
    -config /tmp/{{ item.fqdn }}-csr.cnf
    -{{ cert_digest }}
  loop: "{{ certs_needing_renewal }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: csr_results
  when: item.cert_type in ['pem', 'pkcs12']

- name: Read generated CSR content for CA submission
  ansible.builtin.slurp:
    src: "/tmp/{{ item.fqdn }}.csr"
  loop: "{{ certs_needing_renewal }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: csr_contents
  when: item.cert_type in ['pem', 'pkcs12']

- name: Store CSR content as fact indexed by FQDN
  ansible.builtin.set_fact:
    csr_map: "{{ csr_map | default({}) | combine({item.item.fqdn: item.content | b64decode}) }}"
  loop: "{{ csr_contents.results }}"
  loop_control:
    label: "{{ item.item.fqdn }}"
  when: item.content is defined

Line-by-Line Explanation
openssl genrsa -out {{ item.key_path }} {{ cert_key_size }} — The private key is generated directly on the target server — this is the fundamental security design principle: the private key never travels over the network, never exists on the Ansible control node, never appears in logs. The control node only transmits the public CSR to the CA and the signed cert back to the server.
mode: '0400' on the private key file — Read-only by root only. PCI-DSS Req 4.2.1 and general PKI security best practice mandate that private keys are readable by the minimum required process (the web server daemon, running as root or a restricted service account). 0400 is the most restrictive readable permission.
ansible.builtin.slurp — Reads a file from the remote host and returns its content base64-encoded as a fact — far safer than fetch (which writes to disk on the control node) for CSR files we only need temporarily to POST to a CA API.
content | b64decode — slurp always returns base64-encoded content; b64decode converts it back to the raw PEM text needed for the CA API POST body.
csr_map | combine({item.item.fqdn: ...}) — Builds a dictionary keyed by FQDN mapping to its CSR PEM text. Using combine() iteratively across loop results produces a single lookup dict that the next role (cert_ca_submit) uses to find the right CSR for each cert without re-reading files.
The SAN section {% for san in item.san_names %} — Modern browsers and TLS clients require the Subject Alternative Name extension — the CN alone is no longer sufficient for hostname validation (deprecated per RFC 2818 since 2000, enforced by browsers since ~2017). Every cert must have proper SAN entries matching all hostnames it will serve.

Line-by-Line Explanation
delegate_to: localhost on all CA API tasks — CA API calls originate from the Ansible control node (or EE container), not from the banking servers. The banking servers don't have internet access to reach DigiCert's public API, and we don't want to temporarily open firewall rules for that. The CSR travels: target server (generated) → control node (via slurp fact) → DigiCert cloud (via uri module from localhost) → control node (downloaded cert PEM) → target server (deployed via copy).
retries: 36 / delay: 50 / until: ...status == 'issued' — DigiCert typically issues OV/DV certificates within seconds to minutes via their API automation tier, but can take up to 30 minutes for some validation types. 36 × 50s = 1800s = 30 minutes total polling window — the until condition short-circuits as soon as the cert is ready.
selectattr('ca_type', 'equalto', 'digicert') — The DigiCert and EJBCA task files process only the certs that belong to their respective CA, selected by filtering the certs_needing_renewal list. This means a single host with mixed-CA certs is handled correctly without hardcoding per-cert logic.
no_log: true on every CA API task — API keys and bearer tokens appear in the request headers and body; without no_log: true these would be printed to the AAP job log in plaintext, creating a credential leak risk for anyone with job-read access.
EJBCA: certificate | b64decode — EJBCA's REST API returns the issued certificate as a base64-encoded DER or PEM string in the JSON response; we decode it to get the raw PEM text before storing it in new_cert_map.

- name: Reload nginx

Line-by-Line Explanation
notify: "Reload {{ item.service }}" — Dynamic handler name constructed from the cert's service variable (e.g., "Reload httpd" or "Restart securecore-tomcat"). This single pattern handles Apache graceful reload vs Tomcat full restart vs Nginx reload using one task with per-cert service metadata from the inventory — no conditional branching needed.
state: reloaded for Apache/Nginx vs state: restarted for Tomcat — Critical distinction: Apache and Nginx support graceful config reload (zero dropped connections — workers finish in-flight requests before applying new cert). Tomcat does not support graceful TLS reload; it requires a full restart — but since Tomcat is behind a load balancer (see Project 1), this is safe when combined with LB drain logic.
Post-deploy openssl x509 -noout -subject -in {{ item.cert_path }} — Immediately after writing the cert file, we verify it's valid PEM and readable. A copy of a truncated or corrupt cert (network error during transfer) would otherwise only be discovered when Apache fails to reload — a much worse time to discover the problem.

Role: cert_deploy_jks (Java KeyStore)

roles/cert_deploy_jks/tasks/main.yml
---
- name: Write new certificate content to temp PEM file on remote host
  ansible.builtin.copy:
    content: "{{ new_cert_map[item.fqdn] }}"
    dest: "/tmp/{{ item.fqdn }}-new.crt"
    mode: '0600'
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  when: new_cert_map[item.fqdn] is defined

- name: Convert PEM cert + key to PKCS#12 bundle
  ansible.builtin.command: >
    openssl pkcs12 -export
    -in /tmp/{{ item.fqdn }}-new.crt
    -inkey {{ item.key_path | default(item.pkcs12_path | replace('.p12', '.key')) }}
    -out {{ item.pkcs12_path }}
    -name {{ item.keystore_alias }}
    -passout pass:{{ vault_pkcs12_password }}
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  when: new_cert_map[item.fqdn] is defined
  no_log: true

- name: Back up existing Java KeyStore
  ansible.builtin.copy:
    src: "{{ item.keystore_path }}"
    dest: "{{ cert_backup_dir }}/{{ ansible_date_time.iso8601_basic_short }}/{{ item.fqdn }}.jks.bak"
    remote_src: true
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"

- name: Delete old certificate alias from JKS to avoid duplicate alias conflict
  ansible.builtin.command: >
    keytool -delete
    -alias {{ item.keystore_alias }}
    -keystore {{ item.keystore_path }}
    -storepass {{ vault_jks_password }}
    -noprompt
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  failed_when: false
  no_log: true

- name: Import new PKCS#12 bundle into Java KeyStore
  ansible.builtin.command: >
    keytool -importkeystore
    -srckeystore {{ item.pkcs12_path }}
    -srcstoretype PKCS12
    -srcstorepass {{ vault_pkcs12_password }}
    -destkeystore {{ item.keystore_path }}
    -deststoretype JKS
    -deststorepass {{ vault_jks_password }}
    -alias {{ item.keystore_alias }}
    -noprompt
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: jks_import_result
  no_log: true
  notify: "Restart securecore-tomcat"

- name: Verify the new alias exists in JKS with correct fingerprint
  ansible.builtin.command: >
    keytool -list -v
    -keystore {{ item.keystore_path }}
    -alias {{ item.keystore_alias }}
    -storepass {{ vault_jks_password }}
    -noprompt
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: jks_verify
  changed_when: false
  no_log: true

- name: Fail if JKS import did not produce a valid entry
  ansible.builtin.fail:
    msg: "JKS import verification FAILED for alias {{ item.item.keystore_alias }} on {{ inventory_hostname }}"
  loop: "{{ jks_verify.results }}"
  loop_control:
    label: "{{ item.item.fqdn }}"
  when: "'Certificate fingerprints' not in item.stdout"

- name: Remove temp PEM and PKCS12 files from /tmp (cleanup sensitive material)
  ansible.builtin.file:
    path: "{{ file_path }}"
    state: absent
  loop:
    - "/tmp/{{ item.fqdn }}-new.crt"
    - "{{ item.pkcs12_path }}"
  loop_control:
    loop_var: file_path
  loop: "{{ certs_needing_renewal | selectattr('cert_type', 'equalto', 'jks') | list }}"
Line-by-Line Explanation
keytool -delete before import with failed_when: false — If the old alias doesn't exist (first-time deployment), keytool returns an error. By deleting first with failure suppression, then importing, we avoid the "alias already exists" error on update scenarios while also handling new deployments cleanly — one task pattern for both cases.
keytool -importkeystore -srcstoretype PKCS12 — The modern, recommended way to import certificates into a JKS. Older approaches used -importcert which only imports the certificate, not the private key. The PKCS12 bundle carries both cert and private key together, which is what Tomcat needs to perform TLS termination.
'Certificate fingerprints' not in item.stdout — Rather than parsing complex keytool output with regex, we look for a reliable string that only appears in successful keytool list output of a valid key entry. If the alias wasn't imported correctly, this string won't be present, triggering the fail task before Tomcat is restarted with a broken keystore.
PKCS12 file cleanup (state: absent) — The PKCS12 bundle and temp PEM files contain sensitive key material. Leaving them in /tmp would be a PCI-DSS Req 3.3 violation (cleartext sensitive data retained unnecessarily). Always clean up temp cryptographic material immediately after use.

Role: cert_validate

roles/cert_validate/tasks/main.yml
---
- name: Perform TLS handshake to confirm new cert is being served (from control node)
  ansible.builtin.command: >
    openssl s_client
    -connect {{ item.fqdn }}:443
    -servername {{ item.fqdn }}
    -showcerts
    
    echo | openssl s_client -connect {{ item.fqdn }}:443 -servername {{ item.fqdn }} 2>/dev/null |
    openssl x509 -noout -enddate -checkend {{ validate_cert_min_days * 86400 }}
  loop: "{{ certs }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: served_cert_expiry
  delegate_to: localhost
  changed_when: false
  failed_when: served_cert_expiry.rc != 0

- name: Verify served certificate CN matches expected FQDN
  ansible.builtin.shell: >
    echo | openssl s_client -connect {{ item.fqdn }}:443 -servername {{ item.fqdn }} 2>/dev/null |
    openssl x509 -noout -subject | grep -i "{{ item.fqdn }}"
  loop: "{{ certs }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: cn_match_check
  delegate_to: localhost
  changed_when: false
  failed_when: cn_match_check.rc != 0

- name: Compile per-cert validation summary
  ansible.builtin.set_fact:
    cert_validation_summary: "{{ cert_validation_summary | default([]) + [validation_entry] }}"
  vars:
    validation_entry:
      fqdn: "{{ item.fqdn }}"
      tls_handshake: "{{ 'PASS' if tls_handshake_results.results[loop_index].rc == 0 else 'FAIL' }}"
      expiry_ok: "{{ 'PASS' if served_cert_expiry.results[loop_index].rc == 0 else 'FAIL' }}"
      cn_match: "{{ 'PASS' if cn_match_check.results[loop_index].rc == 0 else 'FAIL' }}"
      validated_at: "{{ ansible_date_time.iso8601 }}"
  loop: "{{ certs }}"
  loop_control:
    index_var: loop_index
    label: "{{ item.fqdn }}"
Line-by-Line Explanation
delegate_to: localhost on all validation tasks — Crucially, we validate by simulating a real client TLS connection from the Ansible control node, not from the target server itself. A server can always read its own cert file — but we need to confirm that the actual TLS stack (Apache/Nginx/Tomcat) is serving the new cert to network clients. Only a real TLS handshake from outside the server confirms this.
-servername {{ item.fqdn }} — Sets the TLS SNI (Server Name Indication) extension in the client hello, which is how modern multi-cert hosts (multiple certs on one IP) know which cert to serve. Without SNI, the server would serve its default cert, which might not be the one we just renewed.
</dev/null — Redirects stdin from /dev/null, causing openssl s_client to immediately close the connection after handshake instead of waiting for user input interactively — essential for non-interactive Ansible use.
-checkend {{ validate_cert_min_days * 86400 }} on the served cert — Even after successful deployment, this confirms the certificate being served by the TLS stack will remain valid for at least 30 more days. This catches edge cases where a stale cert is cached by the web server or the wrong cert is still being served from a misconfigured VirtualHost.

Design Rationale
serial: 1 on deployment plays — Certificate deployment is done one server at a time. This is more conservative than Projects 1 and 2 because a misconfigured cert causes a TLS handshake failure for every client — there is no "partial failure" mode. One server at a time ensures the first server's validation confirms before we touch the second.
role: cert_ca_submit / tasks_from: digicert — The tasks_from parameter overrides the default tasks/main.yml with a specific task file, allowing the same role to contain separate CA-implementation files selected at runtime. Cleaner than a single file with complex conditionals.

2
Ansible gathers facts on all cert-inventory hosts (ansible_date_time, ansible_host). Then cert_discovery loops over each host's certs list, running openssl x509 -checkend per cert on the remote host.
3
Exit codes from -checkend are translated into needs_renewal: true/false facts per cert. Failed checks build the certs_needing_renewal list. The expiry report JSON is generated and archived to NFS.
4
If any cert is within threshold, the Workflow pauses at the Approval Node. The Infrastructure lead reviews the expiry report (linked in the AAP notification) and approves renewal.
5
cert_csr_generate runs on each affected host: new RSA-4096 key generated directly on server, CSR config rendered from Jinja2 template with SANs, CSR generated and slurped to the control node as a base64 fact.
6
cert_ca_submit (DigiCert path): CSR content POSTed to DigiCert API from delegate_to: localhost. Order ID stored. URI module polls the order status endpoint every 50 seconds until status is "issued" (up to 30 minutes).
7
cert_ca_submit (EJBCA path): CSR POSTed to EJBCA REST API; response contains the signed cert immediately (internal CAs typically issue synchronously). Cert PEM stored in new_cert_map dict.
8
cert_deploy_pem copies the new cert PEM from the control-node fact to the target server via ansible.builtin.copy content: — no SCP, no intermediate file on control node disk. Handler triggers graceful Apache/Nginx reload.
9
cert_deploy_jks: cert PEM → PKCS12 via openssl → keytool importkeystore → JKS. Old alias deleted first to prevent duplicate-alias errors. JKS verified with keytool -list before Tomcat restart handler fires.
10
Temp PEM and PKCS12 files in /tmp immediately deleted after JKS import — sensitive material never left on disk.
11
cert_validate performs live TLS handshakes from the control node to each FQDN using openssl s_client, verifying: handshake succeeds, cert won't expire within 30 days, CN matches expected hostname.
12
AAP notification fires: Slack message with per-cert renewal summary and new expiry dates. If any validation failed, PagerDuty P1 alert fires immediately and the cert remains in the "needing renewal" list for the next day's scan.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: A cert was renewed and deployed but customers are still seeing the old cert. What do you check?
First check that the service was actually reloaded (handler fired): journalctl -u httpd --since "10 minutes ago". Then confirm the VirtualHost config references the correct cert path with apachectl -S or nginx -T. If both look correct, check for CDN/load balancer SSL offloading in front of the server — the LB itself may have its own cert that wasn't updated. Finally, check for stunnel or SSL-terminating middleware that might have its own cert cache.
Q: How do you handle certificate pinning in mobile banking apps during renewal?
Mobile apps with certificate pinning embed the certificate's public key hash (SPKI hash) in the app binary. Our renewal process preserves the same private key for pinned certs (we generate a new key only when force_renew=true or a key compromise is suspected) — just re-signing with a fresh cert from the CA against the existing key, keeping the SPKI hash unchanged. Key rotation for pinned certs requires coordinated mobile app release — flagged via a separate ServiceNow change request, not automated.
Q: How do you automate SWIFT certificate renewal when SWIFT mandates human approval in their process?
The Ansible workflow generates the CSR and stops at an AAP Approval Node — it cannot submit directly to SWIFT's CA (SWIFT has its own controlled issuance process). The approver takes the CSR from the AAP job output, submits it through SWIFT's Alliance Key Manager portal manually, and once the cert is issued, uploads it to a designated NFS path. A second workflow job (cert_deploy_swift.yml) then picks it up from that NFS path, deploys it, and validates — automation handles everything except the SWIFT-mandated human portal step.

Architecture & Production Questions

Q: Why generate the private key on the target server rather than on the control node?
The private key must never travel over the network in any form — even encrypted SSH transfer. If generated on the control node, it briefly exists in AAP's workspace/memory, in the SSH stream, and on the target server — three attack surfaces. Generated on the target server, it exists in exactly one place, permanently. This is PKI best practice and a PCI-DSS Req 3.5 (protect cryptographic keys) requirement.
Q: How do you handle wildcard certificates (*.securebank.in) versus per-hostname certs?
Wildcard certs are simpler operationally (one cert covers all subdomains) but have important drawbacks: they cannot be used for EV certificates (required for the main banking portal), they expose all subdomains if the private key is compromised, and they don't work for more than one level of subdomain (*.securebank.in doesn't cover a.b.securebank.in). We use per-hostname certs for all customer-facing and SWIFT endpoints; wildcards only for internal tooling like *.internal.securebank.in.
Q: What is the difference between cert renewal and cert rotation, and when would you force a rotation?
Renewal = same key pair, new certificate from CA (used for routine expiry management — preserves pinning). Rotation = new key pair + new certificate (used when private key compromise is suspected, when algorithm must change from RSA to ECDSA, or to comply with a security directive). Force rotation is triggered in this playbook via the force_renew=true survey variable, which skips the threshold check and generates a new key even for non-expiring certs. This is the incident-response path for suspected key compromise.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Private key generation must always happen on the target server — never on the control node. This is the single most important security principle in cert automation.
  • openssl x509 -checkend N is the clean, binary way to check threshold-based expiry — no date-string parsing or calendar arithmetic needed.
  • JKS deployment requires: delete old alias → convert PEM to PKCS12 → importkeystore → verify alias → clean temp files. Skipping any step causes silent failures discovered only at Tomcat restart.
  • Post-renewal validation must simulate a real client TLS handshake (openssl s_client from the control node) — reading the cert file locally proves nothing about what the TLS stack actually serves.

Common Mistakes

  • Leaving temp .key, .crt, .p12 files in /tmp after JKS import — a PCI-DSS cleartext key exposure finding.
  • Forgetting no_log: true on keytool and CA API tasks — exposes passwords and API keys in AAP job logs.
  • Using state: restarted instead of state: reloaded for Apache — causes dropped connections unnecessarily.
  • Not including SAN extension in CSR config — issued cert without SANs is rejected by modern browsers.

Production Best Practices

  • Set renewal thresholds conservatively — 60 days for public certs (DigiCert reissuance can take days if domain validation re-runs), 30 days for internal (fast issuance), 90 days for SWIFT (mandated).
  • Separate the "approve renewal" action (AAP approval node) from the "approve key rotation" action — different risk levels requiring different approval chains.
  • Always archive the pre-renewal cert with timestamped backup before overwriting — enables manual rollback if the new cert breaks something the validation didn't catch.
  • Use the validate parameter on Apache config templates to run apachectl -t before reloading — prevents deploying a cert the server's config can't find.

Resume Points

  • Eliminated certificate-expiry outages through a daily scheduled expiry-scanning job with threshold-based auto-renewal, reducing mean-time-to-renewal from 2–5 engineer-days to a fully automated sub-60-minute pipeline.
  • Implemented PKI-compliant private key management ensuring keys are generated and never leave target servers, with automated post-renewal TLS handshake validation, satisfying PCI-DSS Req 4.2.1 and RBI IT Framework §7.3 requirements.
