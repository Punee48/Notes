Project 14: PostgreSQL Streaming Replication Health Monitoring & Failover Validation

ABC Global Bank uses PostgreSQL 15 for its Fraud Detection System (FDS), Regulatory Reporting Database (RRD), and Customer Master Data store — all running in high-availability configurations with Patroni-managed streaming replication. PostgreSQL replication lag means the standby is falling behind the primary — if primary fails when lag is 5 minutes, the bank loses 5 minutes of fraud alerts, regulatory data, or customer records. Replication slot bloat fills primary disk and causes crash. This project automates complete PostgreSQL replication health validation: streaming lag measurement, replication slot health, Patroni cluster state, WAL archiving, connection pool (PgBouncer) monitoring, and pre-failover readiness checks.

🏦 1. The Banking Story

Setting: The Fraud Detection System (FDS) runs on PostgreSQL 15 with a 3-node Patroni cluster: fds-pg-primary (leader), fds-pg-replica1 (sync standby), fds-pg-replica2 (async standby). FDS processes 2 million transactions per day in real-time fraud scoring. The standby is used for reporting queries (fraud analytics, regulatory reports) to offload the primary.

Incident 1 — The Silent Lag: A batch process on the reporting team ran 47 simultaneous analytical queries on fds-pg-replica1. The replica fell so far behind the primary that replication lag reached 4 minutes 23 seconds. Nobody noticed — replication lag was not monitored. The next morning, the fraud analytics team ran their daily report and found 4 minutes of transactions missing. It turned out the replica was serving stale data — the report showed fraud counts from 4 minutes before the query ran. The team reported the discrepancy to RBI as a "data integrity issue." A regulatory inquiry followed.

Incident 2 — The Slot Bloat Disaster: A reporting application that connected to the primary using a replication slot for logical decoding was decommissioned — but nobody dropped the replication slot. Over 3 weeks, PostgreSQL retained all WAL (Write-Ahead Log) files since the slot was last used — the slot was "inactive" but held WAL. The primary disk filled completely. PostgreSQL crashed with "no space left on device." Primary disk: 500GB — WAL accumulated: 487GB in 3 weeks from one stale slot. Full outage: 2 hours while engineers identified the slot and cleared space.

Incident 3 — The Failed DR Drill: During the quarterly DR drill, the Patroni failover was initiated. It should have promoted fds-pg-replica1 to leader in under 30 seconds. Instead: replica1 had fallen 12 minutes behind primary (due to the load from Incident 1 that was never resolved). Patroni promoted it but 12 minutes of data was missing. The DR drill was declared a failure. RBI mandates successful quarterly DR drills for critical banking systems.

The Ask: "Monitor PostgreSQL replication lag every 5 minutes. Alert on replication slot bloat before it fills the disk. Validate Patroni cluster health. Before any DR drill, run a pre-flight check that blocks the drill if lag > 30 seconds. Give the DBA team a daily replication health report."

📚 2. PostgreSQL Replication Concepts

Streaming Replication — How PostgreSQL HA Works
PostgreSQL streaming replication works by streaming WAL (Write-Ahead Log) records from the primary to standbys in near-real-time:

Primary: Writes all changes to WAL first, then applies them. WAL is streamed to standbys.
Standby (Hot Standby): Continuously replays WAL from primary. Accepts read-only queries. Cannot accept writes.
Synchronous standby: Primary waits for standby to confirm WAL receipt before committing. Zero data loss but slight performance impact.
Asynchronous standby: Primary doesn't wait. Better performance but potential data loss if primary fails before WAL reaches standby.

Key views for monitoring:
pg_stat_replication: on primary — shows each standby's lag
pg_stat_wal_receiver: on standby — shows connection to primary
pg_replication_slots: on primary — shows all slots and retained WAL size
Replication Lag — What the Numbers Mean
PostgreSQL reports replication lag in multiple ways — all from pg_stat_replication:

write_lag: Time between primary writing WAL and standby receiving it (network lag)
flush_lag: Time between primary writing and standby flushing to disk (I/O lag)
replay_lag: Time between primary writing and standby replaying the change (apply lag)
sent_lsn - replay_lsn: Bytes of WAL the standby has not yet replayed (byte lag)

In banking, replay_lag is the critical metric — it represents how old the standby's data is. If primary fails when replay_lag = 4 minutes, the standby will be missing 4 minutes of transactions after promotion.
Replication Slots — A Double-Edged Sword
Replication slots guarantee that the primary retains WAL until every slot consumer has received it. This prevents the standby from falling too far behind and losing its replication connection.

Physical slots: Used by streaming standbys. Safe — standby continuously consumes WAL.
Logical slots: Used by logical replication (CDC tools like Debezium, pglogical). Dangerous if consumer disconnects — slot retains ALL WAL from disconnect point forever.

The danger: An inactive logical slot retains WAL indefinitely. The primary disk fills with WAL files. PostgreSQL crashes when disk is full. This is exactly Incident 2.

We monitor: pg_replication_slots — active (false = danger), pg_current_wal_lsn() - restart_lsn (bytes of retained WAL per slot). Alert when retained WAL > threshold.
Patroni — What It Adds on Top of Streaming Replication
Patroni is a high-availability template for PostgreSQL that adds:
Automatic failover: If primary becomes unreachable, Patroni automatically promotes the best standby
Leader election: Uses DCS (Distributed Configuration Store — etcd/Consul/ZooKeeper) for consensus
REST API: http://node:8008/ — returns cluster state as JSON
patronictl: CLI tool for cluster management and status

Patroni adds these monitoring checks beyond standard PostgreSQL:
• DCS connectivity (etcd/Consul must be reachable)
• Timeline divergence (split-brain detection)
• Switchover/failover history
• Cluster member count

💻 8. Roles & Tasks — Complete Code

Role 1: pg_replication_check — Primary View

roles/pg_replication_check/tasks/query_primary_stats.yml
---
# =====================================================================
# Query pg_stat_replication on primary node
# This view shows all connected standbys and their lag from primary's view
# =====================================================================

- name: Query pg_stat_replication on primary
  community.postgresql.postgresql_query:          # Module from community.postgresql
    db: postgres                                  # Connect to postgres maintenance DB
    login_user: "{{ pg_monitor_user }}"           # pg_monitor role — read-only monitoring
    login_password: "{{ vault_pg_monitor_password }}"
    login_host: localhost
    port: "{{ pg_port }}"
    query: |
      SELECT
        application_name,
        client_addr::text          AS client_ip,
        state,                     -- streaming / startup / catchup / backup / stopped
        sync_state,                -- sync / async / quorum / potential
        sent_lsn::text,            -- WAL position sent to standby
        write_lsn::text,           -- WAL position written to standby disk
        flush_lsn::text,           -- WAL position flushed on standby disk
        replay_lsn::text,          -- WAL position replayed on standby
        EXTRACT(EPOCH FROM write_lag)::numeric(10,2)  AS write_lag_sec,
        EXTRACT(EPOCH FROM flush_lag)::numeric(10,2)  AS flush_lag_sec,
        EXTRACT(EPOCH FROM replay_lag)::numeric(10,2) AS replay_lag_sec,
        -- Byte lag: how many bytes of WAL standby has not yet replayed
        (pg_current_wal_lsn() - replay_lsn)::bigint  AS replay_byte_lag
      FROM pg_stat_replication
      ORDER BY replay_lag DESC NULLS LAST;
  register: pg_replication_stats
  become: true
  become_user: postgres
  no_log: false

- name: Set replication facts from primary query results
  ansible.builtin.set_fact:
    primary_replication_data:
      cluster: "{{ pg_cluster }}"
      host: "{{ inventory_hostname }}"
      connected_standbys: "{{ pg_replication_stats.query_result | length }}"
      expected_standbys: "{{ pg_cluster_config[pg_cluster].expected_standbys }}"
      standbys: "{{ pg_replication_stats.query_result }}"
      has_sync_standby: >-
        {{ pg_replication_stats.query_result
           | selectattr('sync_state', 'in', ['sync', 'quorum'])
           | list | length > 0 }}
      max_replay_lag_sec: >-
        {{ pg_replication_stats.query_result
           | map(attribute='replay_lag_sec')
           | select('ne', none)
           | map('float')
           | max | default(0) | float | round(2) }}

- name: Classify overall replication severity
  ansible.builtin.set_fact:
    replication_severity: >-
      {{ 'DISCONNECTED' if primary_replication_data.connected_standbys | int
                           < primary_replication_data.expected_standbys | int
         else ('EMERGENCY' if primary_replication_data.max_replay_lag_sec | float
                              >= pg_lag_emergency_seconds | float
               else ('CRITICAL' if primary_replication_data.max_replay_lag_sec | float
                                   >= pg_lag_critical_seconds | float
                     else ('WARNING' if primary_replication_data.max_replay_lag_sec | float
                                        >= pg_lag_warn_seconds | float
                           else 'OK'))) }}

- name: Log replication health summary
  ansible.builtin.debug:
    msg:
      - "PostgreSQL Replication — {{ inventory_hostname }} ({{ pg_cluster }} primary)"
      - "Connected standbys: {{ primary_replication_data.connected_standbys }}/{{ primary_replication_data.expected_standbys }}"
      - "Sync standby present: {{ primary_replication_data.has_sync_standby }}"
      - "Max replay lag: {{ primary_replication_data.max_replay_lag_sec }}s"
      - "Severity: {{ replication_severity }}"
      - "Standbys: {{ primary_replication_data.standbys | map(attribute='application_name') | list | join(', ') }}"

- name: Alert on disconnected standbys
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "pg-standby-disconnected-{{ inventory_hostname }}"
      payload:
        summary: >-
          🔴 PostgreSQL STANDBY DISCONNECTED: {{ pg_cluster }} cluster on
          {{ inventory_hostname }} has only {{ primary_replication_data.connected_standbys }}/
          {{ primary_replication_data.expected_standbys }} standbys connected.
          NO HIGH AVAILABILITY — if primary fails, data loss will occur!
        severity: critical
        source: ansible-pg-monitor
        custom_details:
          cluster: "{{ pg_cluster }}"
          connected: "{{ primary_replication_data.connected_standbys }}"
          expected: "{{ primary_replication_data.expected_standbys }}"
          sync_standby: "{{ primary_replication_data.has_sync_standby }}"
    status_code: [202]
  delegate_to: localhost
  when: replication_severity == 'DISCONNECTED'

- name: Alert on high replication lag
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "pg-lag-{{ replication_severity | lower }}-{{ inventory_hostname }}"
      payload:
        summary: >-
          {{ '🚨 EMERGENCY' if replication_severity == 'EMERGENCY' else '⚠️ CRITICAL' }}:
          PostgreSQL replication lag on {{ pg_cluster }} cluster —
          {{ primary_replication_data.max_replay_lag_sec }}s behind primary.
          Standby data is {{ primary_replication_data.max_replay_lag_sec }}s stale.
          DR drill will FAIL if lag exceeds {{ pg_dr_max_lag_seconds }}s.
        severity: "{{ 'critical' if replication_severity == 'EMERGENCY' else 'error' }}"
        source: ansible-pg-monitor
        custom_details:
          cluster: "{{ pg_cluster }}"
          max_lag_seconds: "{{ primary_replication_data.max_replay_lag_sec }}"
          standbys: "{{ primary_replication_data.standbys | to_json }}"
    status_code: [202]
  delegate_to: localhost
  when: replication_severity in ['CRITICAL', 'EMERGENCY']

- name: Auto-resolve lag alert when replication is healthy
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: resolve
      dedup_key: "pg-lag-critical-{{ inventory_hostname }}"
    status_code: [202]
  delegate_to: localhost
  when: replication_severity == 'OK'
roles/pg_replication_check/tasks/query_standby_stats.yml
---
# =====================================================================
# Query pg_stat_wal_receiver on standby nodes
# This is the standby's own view of its replication connection
# =====================================================================

- name: Query pg_stat_wal_receiver on standby
  community.postgresql.postgresql_query:
    db: postgres
    login_user: "{{ pg_monitor_user }}"
    login_password: "{{ vault_pg_monitor_password }}"
    login_host: localhost
    port: "{{ pg_port }}"
    query: |
      SELECT
        status,                              -- streaming / startup / stopped
        receive_start_lsn::text,
        received_lsn::text,
        last_msg_send_time,
        last_msg_receipt_time,
        EXTRACT(EPOCH FROM (now() - last_msg_receipt_time))::int
          AS seconds_since_last_message,    -- Heartbeat freshness
        sender_host,                         -- Primary hostname
        sender_port,
        conninfo
      FROM pg_stat_wal_receiver;
  register: wal_receiver_stats
  become: true
  become_user: postgres
  no_log: false

- name: Check if standby is actively streaming
  ansible.builtin.set_fact:
    standby_health:
      host: "{{ inventory_hostname }}"
      cluster: "{{ pg_cluster }}"
      role: "{{ pg_role }}"
      streaming: >-
        {{ wal_receiver_stats.query_result | length > 0
           and wal_receiver_stats.query_result[0].status == 'streaming' }}
      seconds_since_heartbeat: >-
        {{ wal_receiver_stats.query_result[0].seconds_since_last_message | default(9999) | int
           if wal_receiver_stats.query_result | length > 0
           else 9999 }}
      sender_host: >-
        {{ wal_receiver_stats.query_result[0].sender_host | default('DISCONNECTED')
           if wal_receiver_stats.query_result | length > 0
           else 'DISCONNECTED' }}

- name: Alert if standby not streaming (from standby perspective)
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "pg-standby-not-streaming-{{ inventory_hostname }}"
      payload:
        summary: >-
          🔴 PostgreSQL STANDBY NOT STREAMING: {{ inventory_hostname }}
          ({{ pg_cluster }} {{ pg_role }} standby) is not receiving WAL from primary.
          Status: {{ wal_receiver_stats.query_result[0].status | default('NO RECEIVER') }}
        severity: critical
        source: ansible-pg-monitor
    status_code: [202]
  delegate_to: localhost
  when: not standby_health.streaming | bool

🔌 9. Replication Slot Monitoring Role

roles/pg_slot_monitor/tasks/check_slot_bloat.yml
---
# =====================================================================
# Monitor replication slot health — prevent the disk-fill incident
# Inactive slots + growing WAL retention = disk full + DB crash
# =====================================================================

- name: Query all replication slots with retained WAL size
  community.postgresql.postgresql_query:
    db: postgres
    login_user: "{{ pg_monitor_user }}"
    login_password: "{{ vault_pg_monitor_password }}"
    login_host: localhost
    port: "{{ pg_port }}"
    query: |
      SELECT
        slot_name,
        slot_type,                                      -- physical / logical
        database,
        active,                                         -- false = DANGER
        active_pid,
        restart_lsn::text,
        confirmed_flush_lsn::text,
        -- Bytes of WAL this slot is forcing the primary to retain
        (pg_current_wal_lsn() - restart_lsn)::bigint
          AS retained_wal_bytes,
        -- Convert to GB for readability
        round(
          (pg_current_wal_lsn() - restart_lsn)::numeric / 1073741824,
          2
        ) AS retained_wal_gb,
        -- Age in hours since slot was last used (for inactive slots)
        CASE WHEN NOT active THEN
          EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp())) / 3600
        ELSE 0 END AS inactive_hours
      FROM pg_replication_slots
      ORDER BY retained_wal_bytes DESC NULLS LAST;
  register: slot_stats
  become: true
  become_user: postgres

- name: Classify slots by health status
  ansible.builtin.set_fact:
    healthy_slots: >-
      {{ slot_stats.query_result
         | selectattr('active', 'equalto', true)
         | list }}
    inactive_slots: >-
      {{ slot_stats.query_result
         | selectattr('active', 'equalto', false)
         | list }}
    bloated_slots: >-
      {{ slot_stats.query_result
         | selectattr('retained_wal_gb', 'ge', pg_slot_retained_wal_warn_gb | float)
         | list }}

- name: Log slot health summary
  ansible.builtin.debug:
    msg:
      - "Replication Slots — {{ inventory_hostname }}"
      - "Total slots: {{ slot_stats.query_result | length }}"
      - "Active: {{ healthy_slots | length }}"
      - "INACTIVE: {{ inactive_slots | length }}"
      - "Bloated (> {{ pg_slot_retained_wal_warn_gb }}GB): {{ bloated_slots | length }}"
      - "{% for slot in bloated_slots %}"
      - "  {{ slot.slot_name }}: {{ slot.retained_wal_gb }}GB retained, active={{ slot.active }}"
      - "{% endfor %}"

- name: Alert P1 on critically bloated inactive slots
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "pg-slot-bloat-critical-{{ inventory_hostname }}-{{ item.slot_name }}"
      payload:
        summary: >-
          🚨 REPLICATION SLOT BLOAT: Slot '{{ item.slot_name }}' on
          {{ inventory_hostname }} is INACTIVE and retaining
          {{ item.retained_wal_gb }}GB of WAL.

    status_code: [202]
  loop: >-

       | selectattr('active', 'equalto', false)
       | selectattr('retained_wal_gb', 'ge', pg_slot_retained_wal_warn_gb | float)
       | list }}
  loop_control:

        db: postgres
        login_user: "{{ pg_monitor_user }}"
        login_password: "{{ vault_pg_monitor_password }}"

        port: "{{ pg_port }}"
        query: |
          SELECT
            application_name,
            state,
            sync_state,
            EXTRACT(EPOCH FROM replay_lag)::numeric(10,2) AS replay_lag_sec,

             and (preflight_lag.query_result
                  | selectattr('sync_state', 'in', ['sync', 'quorum'])
                  | list | length > 0) }}
        max_lag: >-

             | map(attribute='replay_lag_sec')

             | map('float')

🎯 15. Interview Prep

Q: What is the difference between write_lag, flush_lag, and replay_lag in pg_stat_replication?
All three measure different points in the WAL journey from primary to standby:

write_lag: Time from when primary writes WAL to when standby receives it and writes to its WAL buffer (memory). This is primarily network latency.
flush_lag: Time from primary write to standby flushing WAL to disk. Includes write_lag plus standby disk I/O time.
replay_lag: Time from primary write to standby applying (replaying) the WAL change to its data files. This is the most important — it represents how stale the standby's data is relative to the primary.

In banking, replay_lag is what we alert on — it directly answers "how old is the standby's data?" If replay_lag is 4 minutes and primary fails, the promoted standby will be missing 4 minutes of transactions.
Q: Why is an inactive replication slot dangerous and how do you detect it?
PostgreSQL guarantees that WAL files needed by active replication slots will never be deleted. When a slot becomes inactive (its consumer disconnects — e.g., a Debezium CDC application is decommissioned), PostgreSQL continues to retain ALL WAL since the slot last consumed. As the primary generates new WAL, this retained WAL accumulates on disk indefinitely.

Detection via SQL: SELECT slot_name, active, (pg_current_wal_lsn() - restart_lsn) / 1073741824.0 AS retained_gb FROM pg_replication_slots WHERE NOT active;

The formula pg_current_wal_lsn() - restart_lsn gives bytes of WAL the slot is forcing the primary to retain. Dividing by 1073741824 converts to GB. Alerting at 10GB gives the DBA team time to investigate and drop the slot before disk fills. The resolution is: SELECT pg_drop_replication_slot('slot_name');
Q: How does pg_monitor role enable secure monitoring without superuser?
PostgreSQL 10+ includes a built-in role pg_monitor that grants read access to all monitoring views — pg_stat_replication, pg_stat_wal_receiver, pg_replication_slots, pg_stat_activity, and others — WITHOUT requiring superuser.

This follows the principle of least privilege: our Ansible monitoring user (pg_monitor_user) needs only GRANT pg_monitor TO pg_monitor_user. If this monitoring account is compromised, the attacker can only read monitoring data — they cannot modify data, drop tables, or execute commands.

Compare to the alternative of granting superuser to the monitoring account — a compromised superuser can read all data, drop all tables, and execute arbitrary OS commands via COPY TO/FROM PROGRAM. In banking, this is unacceptable for a monitoring account used by Ansible.
Q: How does your DR pre-flight check prevent a failed DR drill?
The pg_dr_preflight.yml playbook queries pg_stat_replication and applies two blocking conditions via ansible.builtin.fail:
1. Lag check: max replay_lag across all standbys must be ≤ 30 seconds
2. Sync standby check: at least one standby with sync_state = 'sync' must be present

If either fails, the playbook fails with a clear message. In the AAP workflow, this failure blocks all subsequent nodes — the Patroni switchover never runs. The DBA Lead sees the failure reason immediately: "Replication lag is 720s — 12 minutes of transactions at risk." They fix the lag first, then re-run the pre-flight, then proceed with the drill.

This is the exact scenario from Incident 3 — 12-minute lag was present but undetected before the drill. Our automation would have caught it and blocked the drill until fixed.
