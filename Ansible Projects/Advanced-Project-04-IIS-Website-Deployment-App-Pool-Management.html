Project 04: Windows IIS Website Deployment & Application Pool Management

ABC Global Bank runs its Internet Banking Portal, Corporate Net Banking, and Internal HR Self-Service applications on Microsoft IIS (Internet Information Services) across 18 Windows Server 2019/2022 web servers. Deploying new application versions, managing SSL bindings, configuring application pools with correct service accounts, and validating site health after deployment — all done manually by the Windows admin team — takes 4–6 hours per release and frequently causes production incidents. This project automates the complete IIS lifecycle: application pool creation and configuration, website deployment with SSL binding, rolling deployment across web farm servers, post-deployment health validation, and automatic rollback on failure.

🏦 1. The Banking Story

Setting: ABC Global Bank's Internet Banking Portal (IBP) serves 4.2 million retail banking customers. It runs on IIS across 6 Windows Server 2019 nodes behind an ARR (Application Request Routing) load balancer. Every 3 weeks, a new release of the IBP application (.NET 6 application packaged as a ZIP) is deployed.

The Problem: The deployment process is entirely manual: a Windows administrator SSHs into each IIS server (actually RDPs — Remote Desktop), stops the application pool, extracts the new ZIP to the web root, reconfigures the web.config with environment-specific settings (different connection strings for Dev/UAT/Prod), starts the app pool, and manually checks if the site loads. They do this for all 6 servers sequentially. During the last deployment of IBP v3.4.1:

• Server 3 had the wrong connection string pasted (UAT database instead of Prod). 8,000 customers who hit that server got errors.
• Server 5's app pool was left stopped — the admin forgot to restart it. ARR continued routing traffic to the stopped server for 15 minutes until the health probe timed out.
• The SSL certificate binding on server 6 was not updated (the certificate was renewed last week but the IIS binding still pointed to the old expired cert). HTTPS connections on server 6 failed.

The Business Impact: 3 separate incidents from a single deployment. 2-hour total customer-facing degradation. ₹80 lakh estimated transaction loss. Customer complaints to RBI's Sachet portal about "bank website not working."

The Ask: "Automate the complete IIS deployment pipeline — configuration-driven, rolling deployment, automatic rollback, zero manual steps."

📚 2. IIS & Application Pool — Concepts You Must Know

IIS Architecture — Sites, App Pools, Applications
IIS (Internet Information Services) is Microsoft's web server. Understanding its hierarchy is essential:

Site: A top-level container with a binding (IP:Port:Hostname). Example: "ABC-Internet-Banking" bound to port 443 with SSL.
Application Pool: An isolated process that runs .NET code. Each site is assigned one app pool. App pools run under a specific Windows identity (service account). If an app pool crashes, only that site is affected.
Application: A web application within a site. A site can have multiple applications (virtual directories).
web.config: XML configuration file at the application root that controls .NET app behavior, connection strings, and app settings.

Key Ansible modules:
• community.windows.win_iis_website — create/modify/delete IIS websites
• community.windows.win_iis_webapppool — manage application pools
• community.windows.win_iis_webbinding — manage SSL/HTTP bindings
• ansible.windows.win_service — manage the W3SVC (World Wide Web Publishing Service)
Application Pool Identity — Critical for Banking
In banking, IIS application pools NEVER run as ApplicationPoolIdentity (default) or NetworkService. They always run as a dedicated Windows service account that has:
• Minimum permissions to the web root folder
• Access to the SQL Server database with a specific SQL login
• No local admin rights
• Password managed by Active Directory / CyberArk PAM

This is a PCI-DSS Req 7 requirement — least privilege access. Ansible automates setting the correct service account identity on each app pool.
SSL Binding in IIS — How It Works
An IIS SSL binding links a certificate (by thumbprint) to a site on a specific port. When a client connects to HTTPS, IIS presents the certificate matching the binding.

The certificate must be installed in the Windows Certificate Store (Local Machine → Personal) before creating the binding. Ansible's win_certificate_store module handles certificate import, and win_iis_webbinding creates the SSL binding using the certificate thumbprint.

❗ 4. Problem Statement

Root Causes of Incidents

  • Manual web.config editing → human copy-paste errors (wrong connection string)
  • No drain from LB before deployment → active traffic hit deploying server
  • No health gate → stopped app pool not detected before LB re-add
  • SSL binding not part of deployment checklist → expired cert binding not updated
  • Sequential manual deployment → 6 servers × 30 min each = 3 hours of risk
  • No rollback procedure → when things go wrong, rollback is manual and slow

Automation Fixes

  • Jinja2 template generates web.config per-environment — no manual editing
  • ARR LB API drain before deployment, re-add after health gate passes
  • Health gate: HTTP 200, app pool running, event log clean before re-add to LB
  • SSL certificate import + binding update included in deployment role
  • Rolling deploy: serial:1 ensures only one server at a time in deployment
  • Automatic rollback: restore backup ZIP, re-validate, alert if rollback also fails

Role 1: iis_setup — First-Time IIS Configuration

roles/iis_setup/tasks/install_iis_features.yml
---
# =====================================================================
# Install required IIS Windows Features
# Run once during server provisioning — idempotent (safe to re-run)
# =====================================================================

- name: Install IIS core web server feature
  ansible.windows.win_feature:                              # win_feature: installs Windows features
    name: Web-Server                                        # IIS base feature name
    state: present                                          # present = install if not already installed
    include_management_tools: true                          # Also install IIS Management Console
  register: iis_install_result

- name: Install IIS sub-features required for .NET banking apps
  ansible.windows.win_feature:
    name:                                                   # List of IIS sub-features
      - Web-Http-Errors                                     # Custom HTTP error pages
      - Web-Http-Logging                                    # IIS request logging (audit requirement)
      - Web-Stat-Compression                                # Static content compression
      - Web-Dyn-Compression                                 # Dynamic content compression
      - Web-Filtering                                       # Request filtering (security)
      - Web-IP-Security                                     # IP-based access control
      - Web-Url-Auth                                        # URL authorization
      - Web-Windows-Auth                                    # Windows Authentication
      - Web-Asp-Net45                                       # ASP.NET 4.5 support
      - Web-Net-Ext45                                       # .NET 4.5 extensibility
      - Web-ISAPI-Ext                                       # ISAPI extensions
      - Web-ISAPI-Filter                                    # ISAPI filters
      - Web-Mgmt-Console                                    # IIS Management Console
      - Web-Scripting-Tools                                 # IIS PowerShell tools
    state: present
    include_sub_features: false                             # false = don't auto-install children

- name: Ensure W3SVC (IIS) service is running and set to automatic startup
  ansible.windows.win_service:
    name: W3SVC                                             # IIS service name
    state: started                                          # Ensure it's running
    start_mode: auto                                        # Start automatically after reboot

- name: Reboot server if IIS installation requires it
  ansible.windows.win_reboot:                              # win_reboot: handles Windows restart
    reboot_timeout: 300                                    # Wait up to 5 minutes for reboot
    msg: "Rebooting after IIS feature installation"
  when: iis_install_result.reboot_required | default(false)
  # Only reboot if the feature installation specifically requires it
roles/iis_setup/tasks/create_app_pool.yml
---
# =====================================================================
# Create and configure IIS Application Pool
# App pools are the process container for .NET web applications
# =====================================================================

- name: Create IIS Application Pool for {{ iis_app_pool_name }}
  community.windows.win_iis_webapppool:                    # Module for IIS app pool management
    name: "{{ iis_app_pool_name }}"                        # Pool name: IBP-AppPool
    state: present                                          # present = create if doesn't exist
    attributes:                                             # Dictionary of pool attributes
      managedRuntimeVersion: "{{ app_pool_dotnet_version }}"   # v4.0 or empty for .NET Core
      managedPipelineMode: "{{ app_pool_pipeline_mode }}"  # Integrated (not Classic)
      startMode: "{{ app_pool_start_mode }}"               # AlwaysRunning (banking requirement)
      autoStart: true                                       # Start pool when IIS starts
      # Recycling settings — when to automatically restart the pool
      recycling.periodicRestart.time: "00:00:00"           # 00:00:00 = no time-based recycling
      recycling.periodicRestart.schedule: "{{ app_pool_recycling_schedule }}"  # Recycle at 2 AM
      processModel.idleTimeout: "{{ '00:00:00' if app_pool_idle_timeout == 0 else app_pool_idle_timeout }}"
      # idleTimeout: 00:00:00 = never shut down pool due to inactivity
      # Banking apps must always be warm — cold starts cause response time issues
      processModel.loadUserProfile: true                   # Load service account profile
      processModel.userName: "{{ iis_service_account }}"  # Identity: ABCBANK\svc_ibp_prod
      processModel.password: "{{ vault_iis_service_account_password }}"  # From Vault
      processModel.identityType: SpecificUser              # SpecificUser = named service account
      # SpecificUser vs ApplicationPoolIdentity:
      # ApplicationPoolIdentity = auto-created virtual account (default, least privilege)
      # SpecificUser = named domain account (required for DB access, file shares)
      # Banking always uses SpecificUser to control DB access via specific SQL login

- name: Verify app pool was created successfully
  community.windows.win_iis_webapppool:
    name: "{{ iis_app_pool_name }}"
    state: started                                          # Ensure pool is running after creation
  register: pool_status

- name: Log app pool creation result
  ansible.builtin.debug:
    msg: >
      App Pool {{ iis_app_pool_name }}:
      State={{ pool_status.state }}
      Identity={{ iis_service_account }}
roles/iis_setup/tasks/create_website.yml
---
# =====================================================================
# Create IIS Website and configure HTTP/HTTPS bindings
# =====================================================================

- name: Create web root directory for {{ iis_site_name }}
  ansible.windows.win_file:                                # win_file: Windows file/dir management
    path: "{{ iis_web_root }}"                             # C:\inetpub\wwwroot\IBP
    state: directory                                       # Create directory if not exists

- name: Set permissions on web root for app pool service account
  ansible.windows.win_acl:                                 # win_acl: Windows ACL management
    path: "{{ iis_web_root }}"
    user: "{{ iis_service_account }}"                      # ABCBANK\svc_ibp_prod
    rights: FullControl                                    # App pool needs full control to serve files
    type: allow
    state: present
    inherit: ContainerInherit,ObjectInherit               # Apply to all subfolders and files

- name: Create IIS Website {{ iis_site_name }}
  community.windows.win_iis_website:                       # Module for IIS website management
    name: "{{ iis_site_name }}"                            # Site name: ABC-Internet-Banking
    state: present                                          # Create if not exists
    port: 80                                               # Start with HTTP, SSL added next
    ip: "*"                                               # Listen on all IPs
    hostname: ""                                           # No host header for now
    physical_path: "{{ iis_web_root }}"                    # Web root path
    application_pool: "{{ iis_app_pool_name }}"            # Assign our app pool
    parameters: logfile.directory:C:\IIS-Logs\{{ iis_app_name }}  # Separate log folder per app

- name: Remove default HTTP binding (we only want HTTPS)
  community.windows.win_iis_webbinding:                   # Module for IIS bindings
    name: "{{ iis_site_name }}"
    protocol: http
    port: 80
    state: absent                                          # Remove HTTP binding (HTTPS only in banking)

- name: Configure HTTPS SSL binding
  community.windows.win_iis_webbinding:
    name: "{{ iis_site_name }}"
    protocol: https                                        # HTTPS protocol
    port: "{{ iis_site_port }}"                           # Port 443
    certificate_hash: "{{ ssl_cert_thumbprint }}"          # Certificate thumbprint (set later)
    certificate_store_name: My                             # Certificate store: Personal
    ssl_flags: 1                                           # 1 = SNI (Server Name Indication)
    state: present
  when: ssl_cert_thumbprint is defined

Role 2: iis_deploy — Rolling Deployment

roles/iis_deploy/tasks/drain_lb.yml
---
# =====================================================================
# Drain server from ARR Load Balancer before deployment
# Critical: ensures no new traffic reaches this server during deploy
# =====================================================================

- name: Remove {{ inventory_hostname }} from ARR web farm
  ansible.builtin.uri:                                     # API call to ARR LB
    url: "{{ arr_api_base }}/webfarm/{{ arr_lb_pool }}/server/{{ ansible_host }}/disable"
    method: POST
    status_code: [200, 204]
    timeout: 30
  delegate_to: localhost                                   # API call from Ansible control node
  # delegate_to: localhost because ARR API is called from the management network
  # not from the IIS server itself

- name: Wait 30 seconds for active connections to drain
  ansible.builtin.pause:
    seconds: 30
    # Why 30 seconds? HTTP keep-alive connections can last up to 30 seconds.
    # Without this pause, an active user's request could be interrupted mid-transaction
    # Banking standard: always drain for minimum 30 seconds (some banks use 60 seconds)

- name: Verify server is no longer receiving traffic
  ansible.builtin.uri:
    url: "{{ arr_api_base }}/webfarm/{{ arr_lb_pool }}/server/{{ ansible_host }}/status"
    method: GET
    return_content: true
  register: lb_status
  delegate_to: localhost

- name: Log LB drain confirmation
  ansible.builtin.debug:
    msg: "{{ inventory_hostname }} drained from {{ arr_lb_pool }}: {{ lb_status.json }}"
roles/iis_deploy/tasks/backup_current.yml
---
# =====================================================================
# Backup current web root before deploying new version
# This enables instant rollback if deployment fails
# =====================================================================

- name: Create backup directory for this deployment
  ansible.windows.win_file:
    path: "{{ backup_base_path }}\\{{ iis_app_name }}\\{{ ansible_date_time.iso8601_basic_short }}"
    state: directory                                       # Create timestamped backup folder

- name: Store backup path as fact for use in rollback tasks
  ansible.builtin.set_fact:
    current_backup_path: "{{ backup_base_path }}\\{{ iis_app_name }}\\{{ ansible_date_time.iso8601_basic_short }}"

- name: Copy current web root to backup location
  ansible.windows.win_xcopy:                              # win_xcopy: Windows file copy with recurse
    src: "{{ iis_web_root }}"                             # Source: current web root
    dest: "{{ current_backup_path }}"                     # Destination: timestamped backup
    recurse: true                                          # Copy all subdirectories
  register: backup_result

- name: Record current version being backed up (from version file if exists)
  ansible.windows.win_shell:
    cmd: >
      if (Test-Path "{{ iis_web_root }}\version.txt") {
        Get-Content "{{ iis_web_root }}\version.txt"
      } else { "unknown" }
  register: current_version_file
  changed_when: false

- name: Log backup completion
  ansible.builtin.debug:
    msg: >
      Backup complete for {{ inventory_hostname }}:
      Previous version: {{ current_version_file.stdout | trim }}
      Backed up to: {{ current_backup_path }}

              $daysLeft = ($cert.NotAfter - (Get-Date)).Days

🎯 16. Interview Preparation

Q: What is the difference between Application Pool identity types in IIS?
IIS App Pools support 4 identity types:
LocalSystem: Most privileged — full machine access. Never use in banking.
LocalService: Limited local rights. For non-domain apps.
NetworkService: Can access network resources as the machine account. Sometimes used.
ApplicationPoolIdentity: Auto-created virtual account (IIS AppPool\AppPoolName). Least privilege, secure default.
SpecificUser: Named domain account. Used in banking when the app needs to authenticate to SQL Server or network shares with specific, auditable credentials.

In banking, we use SpecificUser (domain service account) because: (1) SQL Server logins are mapped to specific Windows accounts for audit trail, (2) File share access is controlled per service account, (3) The account's actions are visible in Active Directory audit logs.
Q: Why use serial:1 and max_fail_percentage:0 for IIS rolling deployment?
serial:1: Deploys to exactly one server at a time. If we used serial:3 (3 servers simultaneously), we'd have 3 servers simultaneously unavailable from the LB — potentially 50% of the web farm down during deployment. With serial:1, only 1 of 6 servers (17%) is under deployment at any time — 5 of 6 servers always serving traffic.

max_fail_percentage:0: Any single server failure immediately stops the deployment. With a broken application version, we don't want to automatically continue deploying the same bad version to the remaining 5 servers. The 0% threshold means we stop as soon as one failure occurs, investigate, and fix before continuing.
Q: How does the web.config Jinja2 template prevent environment mix-ups?
Before automation, the web.config was manually copied from a template and the connection strings were edited manually for each environment. Human error inevitably led to UAT connection strings deployed to production (or vice versa).

With Jinja2 templating, the target_environment survey variable (production/uat/staging) drives ALL environment-specific values in the template. The connection strings, API URLs, session timeouts, debug mode, and custom error settings are all conditional on this single variable. It's physically impossible to get a UAT database connection string into a production deployment because the template doesn't allow it — only the vault_lms_db_server variable (which contains the production DB server for production deployments) is used.
Q: How do you handle the scenario where rollback also fails?
The rollback task includes its own health check after restoring the backup. If the rollback health check also fails:
1. PagerDuty P1 escalation fires — "BOTH deployment AND rollback failed on server X"
2. The server stays drained from the LB (it's unhealthy regardless — no point routing traffic to it)
3. A specific Slack message goes to the #incident channel with the server name, both failure details, and the backup path that was restored from
4. The remaining servers in the rolling deploy are protected by max_fail_percentage:0 — the deployment has already stopped
5. The Windows admin team manually investigates the specific server — may require RDP access to check IIS Manager and Event Logs directly
