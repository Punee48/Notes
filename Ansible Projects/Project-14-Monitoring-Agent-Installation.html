Project 14: Monitoring Agent Installation & Fleet-Wide Observability using Red Hat AAP

You cannot manage what you cannot measure. SecureBank's 400-server production fleet generates terabytes of metrics, logs, and traces every day — but until this project, only a fraction of that data reached the central observability stack. New servers are provisioned without monitoring agents. Old agents have stale configurations pointing to decommissioned collectors. Agent versions are inconsistent — some servers run Prometheus Node Exporter 1.2 while others have 1.8. Log forwarding is configured on 60% of servers and missing entirely on the rest. This project automates the complete observability agent lifecycle across 400 servers: installation of Prometheus Node Exporter (system metrics), Filebeat (log forwarding to Elasticsearch), Wazuh Agent (SIEM/security monitoring), and OpenTelemetry Collector (application traces and custom metrics) — all configured from Ansible templates, registered with their respective backends, and validated end-to-end before the play considers a server monitored.

🏦 2. Real-Time Banking Scenario

The Story: SecureBank's NOC receives a P1 alert at 2:47 AM — CBS transaction throughput has dropped 40%. The SRE on-call opens Grafana. Of the 12 CBS app servers, only 7 are showing metrics in Prometheus. The remaining 5 were provisioned 3 weeks ago but never had Node Exporter installed. The SRE has no CPU, memory, or disk data for those 5 servers during the incident. After a 90-minute investigation that would have taken 15 minutes with full metrics coverage, the root cause is found: 2 of the 5 unmonitored servers have 100% disk usage on /var/log/ causing Tomcat to stop writing logs and hang. The servers were not in the monitoring blackout — they simply never had an agent installed.

In parallel, a QSA conducting the PCI-DSS assessment asks for evidence of centralised log collection from all CDE servers. InfoSec pulls the Filebeat agent status across the CDE fleet: 14 of 62 CDE servers have Filebeat either missing or in a failed state. The QSA raises a finding: PCI-DSS Req 10.5 (protect audit logs) cannot be evidenced for those 14 servers.

With Project 14's automation: every new server provisioned through the standard workflow has all four agents installed, configured, and validated within the first 15 minutes of existence. Weekly agent health checks detect missing or failed agents across the fleet and auto-reinstall them. The PCI-DSS QSA review shows 400/400 servers with active Filebeat and Wazuh agents — no finding raised.

❗ 3. Problem Statement

  • New server provisioning does not include monitoring agent installation — agents are manually installed "when someone remembers," leading to monitoring gaps that persist for weeks.
  • Agent configurations are manually maintained — Prometheus scrape endpoints, Filebeat Elasticsearch hosts, Wazuh manager IPs are hardcoded in config files that diverge as infrastructure changes.
  • Agent version inconsistency — Node Exporter versions range from 1.2 to 1.8 across the fleet, with older versions missing critical metrics (e.g., CPU steal time, cgroup v2 metrics).
  • No agent health monitoring — a failed Filebeat agent silently stops shipping logs; the only way to discover this is when you look for logs during an incident and they're not there.
  • Wazuh agent registration is manual — each new server must be manually registered with the Wazuh manager, which requires access to both the manager API and the agent host simultaneously.
  • No Day-0 observability gate — servers go live without monitoring, making the first incident on a new server a debugging nightmare.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. New server provisioned. Engineer SSHes in, downloads the Node Exporter binary manually, creates a systemd unit file from memory, starts the service. Prometheus scrape config updated manually on the Prometheus server.
  2. Filebeat installed via yum install filebeat. Engineer manually edits /etc/filebeat/filebeat.yml — types the Elasticsearch host IP from memory (sometimes incorrectly). Filebeat started. Nobody checks if Elasticsearch is actually receiving data.
  3. Wazuh agent: engineer logs into Wazuh manager web UI, generates a registration key, SSHes to the new server, runs the agent registration command with the key. If the key expires before the engineer gets to the server, the process must restart.
  4. OpenTelemetry Collector: rarely installed — considered "optional" — resulting in no distributed tracing for the CBS application stack.
  5. Agent health: never checked proactively. Failed agents discovered during incidents when expected data is missing.

🛠️ 6. Automated Solution Design

Four monitoring agents, each with a dedicated role, all integrated into a single observability onboarding pipeline:

AgentRoleWhat It MonitorsBackend
Prometheus Node Exportermon_node_exporterCPU, memory, disk, network, filesystem metricsPrometheus → Grafana
Filebeat 8.xmon_filebeatSystem logs (/var/log/messages, audit.log), app logs (Tomcat, CBS)Elasticsearch → Kibana
Wazuh Agentmon_wazuhSecurity events, FIM, vulnerability detection, rootcheckWazuh Manager → Wazuh Dashboard
OpenTelemetry Collectormon_otelApplication traces, custom CBS metrics, JVM metrics via JMX receiverTempo (traces) → Grafana; Prometheus (metrics)

Key design decisions:

  • Backend registration via API from localhost: Prometheus scrape config updated via Prometheus HTTP SD (service discovery file); Wazuh agent registered via Manager REST API — both from delegate_to: localhost so the control node handles backend operations, not the target server.
  • Idempotent installation: Check installed version before downloading. Skip installation if already at target version. Upgrade only when version is below target.
  • End-to-end validation: After agent start, validate data actually reaches the backend — not just that the process is running. Node Exporter: Prometheus has a scrape target in UP state. Filebeat: test log line appears in Elasticsearch. Wazuh: agent shows ACTIVE in Wazuh manager API.
  • Day-0 gate: The provisioning workflow (Project 15) calls this role as a mandatory stage — server only proceeds to receive traffic after all four agents are validated active.

Role: mon_node_exporter — Install & Register with Prometheus

roles/mon_node_exporter/tasks/install.yml
---
- name: Check if Node Exporter is already installed and get version
  ansible.builtin.command: "{{ node_exporter_install_dir }}/node_exporter --version"
  register: ne_version_check
  changed_when: false
  failed_when: false

- name: Parse installed version (if any)
  ansible.builtin.set_fact:
    ne_installed_version: >-
      {{ ne_version_check.stdout
         | regex_search('version ([0-9.]+)', '\1')
         | first | default('0.0.0') }}

- name: Skip installation if already at target version
  ansible.builtin.meta: end_host
  when: ne_installed_version is version(node_exporter_version, '>=')

- name: Ensure node_exporter system user exists (no login shell)
  ansible.builtin.user:
    name: "{{ node_exporter_user }}"
    system: true
    shell: /sbin/nologin
    create_home: false
    comment: "Prometheus Node Exporter service account"

- name: Download Node Exporter binary from internal Nexus
  ansible.builtin.get_url:
    url: "{{ node_exporter_url }}"
    dest: "/tmp/node_exporter-{{ node_exporter_version }}.tar.gz"
    checksum: "sha256:{{ node_exporter_sha256 }}"
    mode: '0640'

- name: Extract Node Exporter binary
  ansible.builtin.unarchive:
    src: "/tmp/node_exporter-{{ node_exporter_version }}.tar.gz"
    dest: /tmp
    remote_src: true
    creates: "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"

- name: Install Node Exporter binary to install directory
  ansible.builtin.copy:
    src: "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"
    dest: "{{ node_exporter_install_dir }}/node_exporter"
    owner: "{{ node_exporter_user }}"
    group: "{{ node_exporter_user }}"
    mode: '0755'
    remote_src: true
  notify: Restart node_exporter

- name: Deploy Node Exporter systemd unit from template
  ansible.builtin.template:
    src: node_exporter.service.j2
    dest: /etc/systemd/system/node_exporter.service
    owner: root
    group: root
    mode: '0644'
  notify:
    - Reload systemd daemon
    - Restart node_exporter

- name: Enable and start Node Exporter service
  ansible.builtin.systemd:
    name: node_exporter
    state: started
    enabled: true
    daemon_reload: true

- name: Wait for Node Exporter to listen on metrics port
  ansible.builtin.wait_for:
    host: "{{ ansible_host }}"
    port: "{{ node_exporter_port }}"
    delay: 3
    timeout: 30

- name: Register server as Prometheus scrape target (file-based SD)
  ansible.builtin.template:
    src: prometheus_sd_target.json.j2
    dest: "{{ prometheus_sd_dir }}/{{ inventory_hostname }}.json"
    owner: prometheus
    group: prometheus
    mode: '0644'
  delegate_to: prometheus.securebank.in

- name: Clean up downloaded archives
  ansible.builtin.file:
    path: "{{ item }}"
    state: absent
  loop:
    - "/tmp/node_exporter-{{ node_exporter_version }}.tar.gz"
    - "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64"

---
- name: Query Prometheus API to confirm this target is UP
  ansible.builtin.uri:
    url: "{{ prometheus_url }}/api/v1/targets"
    method: GET
    headers:
      Authorization: "Bearer {{ vault_prometheus_token }}"

  delay: 20

    | selectattr('labels.instance', 'equalto', inventory_hostname + ':' + node_exporter_port | string)
    | selectattr('health', 'equalto', 'up')
    | list | length > 0

    node_exporter_validation_time: "{{ ansible_date_time.iso8601 }}"
Line-by-Line Explanation
ne_installed_version is version(node_exporter_version, '>=') — Ansible's version() Jinja2 test performs semantic version comparison (not string comparison). '1.8.1' >= '1.2.0' is true — correctly detects the server already has a sufficient version. String comparison would fail: '1.8.1' > '1.2.0' as strings compares character by character and gives unexpected results for multi-digit minor/patch versions.
system: true, shell: /sbin/nologin, create_home: false on user creation — Node Exporter runs as a dedicated system service account with no login capability, no home directory, and no interactive shell. This is the principle of least privilege for service accounts — if Node Exporter is compromised, the attacker gets an account that cannot log in interactively or write to a home directory.
--collector.systemd --collector.processes in ExecStart — Enables extra collectors beyond the default set. The systemd collector exposes per-service metrics (which units are active, failed, etc.) enabling Grafana dashboards that show service-level health alongside OS metrics. The processes collector exposes per-process metrics (open file descriptors, threads) critical for diagnosing JVM process resource exhaustion.
ProtectSystem=strict, PrivateTmp=yes, NoNewPrivileges=yes — systemd security hardening directives. ProtectSystem=strict mounts the OS filesystem read-only for the service (it can only write to explicitly allowed paths). PrivateTmp=yes gives the service its own /tmp namespace. NoNewPrivileges=yes prevents the process from gaining new capabilities via setuid/setgid. A monitoring agent that gets compromised cannot escalate privileges with these restrictions.
File-based SD: delegate_to: prometheus.securebank.in — Instead of calling the Prometheus API (which would require an HTTP reload), we write a JSON file to Prometheus's file_sd directory on the Prometheus server itself. Prometheus watches this directory and automatically discovers new targets within 5 seconds — no Prometheus restart needed, no API call needed. Each server gets its own JSON file named by hostname, making removal easy (file: state: absent) when a server is decommissioned.

Line-by-Line Explanation
filebeat test output — Filebeat's built-in connectivity test command verifies the Elasticsearch connection without starting full log shipping. It tests authentication, SSL certificate validation, and network reachability. Running this immediately after starting the service catches misconfigured Elasticsearch URLs or wrong API keys before they silently fail — the "nobody checks if data is arriving" problem.
multiline.pattern: '^type=' for audit logs — auditd writes multi-line records where continuation lines don't start with type=. Without multiline configuration, Filebeat would ship each line as a separate Elasticsearch document, breaking audit log parsing. The multiline config joins continuation lines to the previous record that starts with type=.
api_key: "{{ vault_elasticsearch_api_key }}" — Elasticsearch API key authentication instead of username/password. API keys can be scoped to specific indices, have built-in expiry, and can be revoked individually — more secure than a shared credential. The key is Vault-encrypted in Ansible Vault and injected at template render time.
fields_under_root: true — Places the custom fields (log_type, server, environment) at the top level of the Elasticsearch document rather than nested under a "fields" key. This makes Kibana queries simpler: server: cbs-app01 instead of fields.server: cbs-app01.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: How do you validate that a monitoring agent is actually working, not just that it is installed and running?
Three levels of validation, each proving a different layer: (1) Process running — systemctl status confirms the agent process is alive. Necessary but not sufficient. (2) Port/API reachable — wait_for port or filebeat test output confirms the agent can reach its backend. (3) Data arriving at backend — Prometheus up metric, Elasticsearch test log search, Wazuh agent status API. Level 3 is the only definitive proof the full pipeline works. A running Filebeat process with a typo in the Elasticsearch host would pass levels 1 and 2 but fail level 3 — which is exactly the scenario that causes incident investigation failures.
Q: Why use Prometheus file-based service discovery instead of static scrape configs?
Static configs require editing prometheus.yml and reloading Prometheus every time a server is added or removed — a manual, error-prone step. File-based SD (file_sd) lets Ansible write a JSON file per server to the Prometheus SD directory, and Prometheus automatically discovers it within 5 seconds with no restart needed. Decommissioning a server is as simple as deleting its SD JSON file. This makes server lifecycle operations (provisioning, decommission, DR failover) completely autonomous from a Prometheus configuration perspective.
Q: Wazuh registration requires both a manager API call and a command on the agent host. How does Ansible handle this two-sided operation?
The delegate_to pattern: the Wazuh Manager API call (to create the agent record and retrieve the registration key) runs from the Ansible control node (delegate_to: localhost) because the control node can reach the Wazuh Manager API. The key import command (manage_agents -i key) runs on the target server (the default execution target for the play). The registration key is passed between these two steps as an Ansible fact (set_fact: wazuh_agent_key). This two-phase approach via delegate_to is the standard pattern for operations that require both control plane (API) and data plane (SSH to target) interactions.

Architecture & Production Questions

Q: How do you handle monitoring agent installation on servers in a DMZ where direct Nexus access may be blocked?
Two approaches: (1) Ansible control node as relay — download the binary to the control node (delegate_to: localhost with get_url) then copy it to the target server (ansible.builtin.copy). This works when the control node has Nexus access but the DMZ server doesn't. (2) Local caching proxy — configure a Squid or nginx proxy in the DMZ network that caches Nexus artifact requests. Ansible points to the DMZ-local proxy URL. Approach 1 is simpler for occasional installations; approach 2 is better for large DMZ fleets where repeated downloads via the control node become a bottleneck.
Q: What happens to monitoring when a server undergoes Blue-Green deployment (Project 12) — does the Green server need agent reinstallation?
No reinstallation needed — the Green servers are long-running servers that already have all agents installed from their previous use as active Blue (before they were swapped to Green for the current deployment cycle). The agent configurations (Filebeat Elasticsearch endpoint, Wazuh manager address) are static and don't change with the application deployment. The only monitoring change needed during Blue-Green is that after the traffic switch, Grafana dashboards automatically show Green server metrics appearing more prominently as they receive load — no Ansible action needed.
Q: How do you handle Filebeat log backlog during a high-traffic period where Filebeat can't keep up with log generation?
Filebeat has a built-in queue (in-memory or disk-based) and handles backpressure by slowing down log reading rather than dropping events. In the Filebeat configuration, we set queue.mem.events: 4096 and queue.mem.flush.min_events: 512 for the in-memory queue. For high-throughput transaction logs on CBS servers, we configure a disk-based spool queue with queue.disk.max_size: 10gb which absorbs bursts without data loss. Filebeat's monitoring metrics (logged locally and shipped to Elasticsearch) include filebeat.harvester.open_files and libbeat.output.events.dropped — an alert on dropped events = 0 threshold breach signals a queue overflow situation requiring investigation.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • End-to-end backend validation (data arriving at backend) is the only meaningful proof a monitoring agent works — process running and port listening are necessary but insufficient.
  • File-based Prometheus SD makes server lifecycle operations autonomous — no manual prometheus.yml edits needed for server add/remove.
  • Wazuh agent registration is a two-sided operation requiring delegate_to for the manager API call and SSH for the key import — understanding this pattern prevents the "install but never register" failure mode.
  • Day-0 monitoring must be a blocking gate in the provisioning workflow — optional monitoring installation always gets skipped under time pressure.

Common Mistakes

  • Checking process state only — a misconfigured Filebeat process will run indefinitely while shipping nothing to Elasticsearch.
  • Hardcoding backend URLs in agent config files — when Elasticsearch or Wazuh manager IP changes, 400 config files need manual updates. Template-driven config with variables is the only scalable approach.
  • Installing Node Exporter as root — creates a security risk; always use a dedicated system service account with minimal permissions and systemd security hardening.
  • Not cleaning up downloaded archives — /tmp fills up on servers that are repeatedly updated, causing subsequent downloads to fail.

Production Best Practices

  • Use internal artifact mirrors (Nexus/Artifactory) for all agent binaries — never download directly from GitHub releases in production, which creates external dependencies during critical Day-0 provisioning.
  • Validate SHA-256 checksums on all downloads — a corrupted binary silently produces garbage metrics or fails to start, both of which are worse than a clean installation failure.
  • Configure systemd security hardening directives (ProtectSystem, NoNewPrivileges, PrivateTmp) on all monitoring agent units — monitoring agents are long-running, internet-connected processes that are attractive compromise targets.
  • Weekly health checks with auto-reinstall are more reliable than trying to make agents perfectly crash-proof — agents fail for environmental reasons (disk full, OOM, kernel updates). Detecting and reinstalling within 24 hours maintains the coverage SLA.
