Project 1: Core Banking Application Deployment using Red Hat AAP

This is the foundation project in your 15-project Ansible journey through Banking & Financial Services automation. You'll automate the end-to-end deployment of SecureBank's Core Banking Application (CBS) — the system that handles account management, transaction posting, and ledger updates — across Dev, UAT, and Production environments using Red Hat Ansible Automation Platform.

RHEL 8/9 Red Hat AAP 2.5 Java/Tomcat Core Banking App Multi-Tier Deployment Banking Domain Production Grade

📋 1. Business Requirement

SecureBank runs its Core Banking Solution (CBS) — a Java-based application named "SecureCore" deployed on Apache Tomcat, backed by an Oracle database — across three tiers: Web Tier (Apache HTTPD reverse proxy), Application Tier (Tomcat cluster), and Database Tier (Oracle RAC, accessed but not modified by Ansible).

The Release Engineering team must deploy new application builds (WAR files) every two weeks across 3 Dev servers, 4 UAT servers, and 12 Production servers (across 2 data centers — Mumbai DC and Chennai DR) with zero manual login to production boxes, full audit trail (mandatory for RBI/PCI-DSS compliance), and a rollback capability in case the release fails smoke tests.

🏦 2. Real-Time Banking Scenario

The Story: It's a Friday evening at SecureBank's NOC in Mumbai. The Release Manager, Priya, has just received sign-off from QA for build securecore-v4.8.2.war. Per RBI change management guidelines, this build must go to all 12 production app servers in the 10 PM–12 AM maintenance window, with a rollback plan ready in case transaction posting breaks after deployment. Two years ago, before automation, this used to take 3 engineers working until 3 AM, manually SCPing WAR files server-by-server, editing server.xml, restarting Tomcat, and tailing logs — with at least one server always "forgotten" or misconfigured. Today, Priya triggers a single AAP Job Template and watches every one of the 12 servers update identically and report back via Slack within 18 minutes.

❗ 3. Problem Statement

  • Manual deployment of WAR files across 12+ production servers is slow, error-prone, and not repeatable.
  • No standard, auditable way to confirm all servers are running the same application version.
  • Manual Tomcat restarts cause inconsistent downtime — some engineers do graceful shutdowns, others kill -9.
  • No automated rollback if smoke tests fail post-deployment.
  • No centralized log of who deployed what, when, and to which servers — a hard requirement for RBI/PCI-DSS audits.
  • Configuration drift: server.xml, context.xml, and JVM heap settings silently diverge between servers over time.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. Engineer logs into each Tomcat server individually via SSH using a shared service account password.
  2. Engineer manually stops Tomcat: sh /opt/securecore/tomcat/bin/shutdown.sh
  3. Engineer backs up the existing WAR (sometimes forgotten).
  4. Engineer SCPs the new WAR file from a jump host into /opt/securecore/tomcat/webapps/.
  5. Engineer manually edits context.xml if DB connection pool settings changed.
  6. Engineer starts Tomcat: sh /opt/securecore/tomcat/bin/startup.sh
  7. Engineer tails catalina.out manually to confirm "Server startup" message.
  8. Engineer manually hits the health endpoint with curl.
  9. Process repeated, server by server, for all 12 production nodes — sequentially, because nobody trusts doing it in parallel manually.

🛠️ 6. Automated Solution Design

We design a role-based Ansible solution orchestrated through AAP Workflow Templates that:

  • Takes the WAR file version as a survey input in AAP (so non-technical release managers can trigger it safely).
  • Runs pre-deployment health checks (disk space, Tomcat process status, DB connectivity) before touching anything.
  • Backs up the currently deployed WAR + config to a timestamped folder automatically (enables rollback).
  • Deploys to a canary batch first (1 server), runs smoke tests, then proceeds to the rest using Ansible's serial keyword.
  • Uses handlers to restart Tomcat only when the WAR/config actually changes (idempotency).
  • Sends a Slack/Email notification with pass/fail status per batch via AAP notification templates.
  • Provides a separate, equally automated Rollback Workflow triggered with one click if smoke tests fail.

💻 11. Complete Project Code (Line-by-Line Explained)

ansible.cfg

ansible.cfg
[defaults]
inventory = inventory/production/hosts.ini
roles_path = roles
host_key_checking = False
retry_files_enabled = False
vault_password_file = .vault_pass
forks = 12
timeout = 30

[ssh_connection]
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
Line-by-Line Explanation
inventory = inventory/production/hosts.ini — Tells Ansible where the default inventory file lives, so engineers don't need -i on every command. In AAP this is overridden by the AAP Inventory source, but kept here for local CLI testing.
host_key_checking = False — Disables SSH host-key prompts. Required in automation, since AAP runs unattended and a prompt would hang the job forever. Alternative: pre-populate known_hosts via a bootstrap role — safer for production, used in Project 10 (Server Hardening).
forks = 12 — Number of hosts Ansible talks to in parallel. We set this to exactly 12 because that's our full production app-tier count, but we still control real parallelism using serial in the playbook for safety.
pipelining = True — Reduces the number of SSH operations per task by executing modules without writing temp files first, significantly speeding up large playbook runs. Best practice for production-scale Ansible.
ControlPersist=60s — Reuses the same SSH connection for 60 seconds across multiple tasks instead of reconnecting every time — a major performance optimization for banking-scale inventories.

Role: tomcat_precheck

roles/tomcat_precheck/tasks/main.yml
---
- name: Check available disk space on webapps partition
  ansible.builtin.shell: df --output=avail -BM "{{ tomcat_webapps_dir }}" | tail -1 | tr -dc '0-9'
  register: disk_avail_mb
  changed_when: false

- name: Fail fast if less than 2GB free space available
  ansible.builtin.fail:
    msg: "Only {{ disk_avail_mb.stdout }}MB free on {{ inventory_hostname }} — need at least 2048MB before deployment"
  when: disk_avail_mb.stdout | int < 2048

- name: Verify Tomcat service is currently running (pre-deployment baseline)
  ansible.builtin.systemd:
    name: securecore-tomcat
  register: tomcat_status

- name: Record current Tomcat PID for later comparison
  ansible.builtin.set_fact:
    pre_deploy_tomcat_pid: "{{ tomcat_status.status.MainPID | default('0') }}"

- name: Test database connectivity from app server using tnsping equivalent (port check)
  ansible.builtin.wait_for:
    host: "{{ db_connection_url | regex_search('@([^:]+)', '\\1') | first }}"
    port: 1521
    timeout: 5
  register: db_check
  ignore_errors: true

- name: Fail deployment if database is unreachable from this app server
  ansible.builtin.fail:
    msg: "Cannot reach Oracle DB tier from {{ inventory_hostname }} — aborting deployment to prevent app starting with broken DB connectivity"
  when: db_check.failed
Line-by-Line Explanation
ansible.builtin.shell: df --output=avail ... — We use shell (not command) here because we need pipe (|) support for tail and tr. Best practice note: shell is avoided when a native module exists, but disk-space-with-pipe-parsing has no clean built-in module, so shell is justified here.
changed_when: false — This is a read-only check; without this, Ansible would mark it "changed" every run since shell tasks default to changed=true, polluting reports with false positives.
ansible.builtin.fail: ... when: disk_avail_mb.stdout | int < 2048 — Converts the captured string to an integer for numeric comparison, and stops the play immediately on this host if disk space is insufficient — a classic "fail fast" pre-check pattern that prevents a half-broken deployment.
ansible.builtin.systemd: name: securecore-tomcat — Used in "query mode" (no state: specified) purely to gather facts about the current service, not to change it. This is a common pattern for pre-checks.
db_connection_url | regex_search('@([^:]+)', '\\1') — Extracts just the DB hostname out of the full JDBC URL string using a Jinja2 regex filter, so we can pass a clean hostname to wait_for.
ignore_errors: true followed by an explicit fail — We deliberately don't let wait_for kill the play directly so that we can emit our own clear error message instead of Ansible's generic timeout error, which is much harder for the on-call engineer to interpret at 11 PM.

Role: cbs_backup

roles/cbs_backup/tasks/main.yml
---
- name: Create timestamped backup directory for this release
  ansible.builtin.file:
    path: "{{ cbs_backup_dir }}/{{ ansible_date_time.iso8601_basic_short }}"
    state: directory
    owner: "{{ tomcat_user }}"
    group: "{{ tomcat_group }}"
    mode: '0750'
  register: backup_dir

- name: Check if a previous WAR deployment exists
  ansible.builtin.stat:
    path: "{{ tomcat_webapps_dir }}/{{ cbs_app_name }}.war"
  register: existing_war

- name: Back up currently deployed WAR file before overwriting
  ansible.builtin.copy:
    src: "{{ tomcat_webapps_dir }}/{{ cbs_app_name }}.war"
    dest: "{{ backup_dir.path }}/{{ cbs_app_name }}.war.bak"
    remote_src: true
    owner: "{{ tomcat_user }}"
    group: "{{ tomcat_group }}"
  when: existing_war.stat.exists

- name: Back up current context.xml configuration
  ansible.builtin.copy:
    src: "{{ tomcat_home }}/conf/context.xml"
    dest: "{{ backup_dir.path }}/context.xml.bak"
    remote_src: true
  when: existing_war.stat.exists

- name: Write backup manifest with version, timestamp and operator
  ansible.builtin.copy:
    content: |
      backup_taken_at: {{ ansible_date_time.iso8601 }}
      previous_war_present: {{ existing_war.stat.exists }}
      triggered_by: "{{ tower_user_name | default('cli-user') }}"
      target_war_version: "{{ war_version }}"
    dest: "{{ backup_dir.path }}/manifest.yml"
Line-by-Line Explanation
ansible_date_time.iso8601_basic_short — A built-in Ansible fact (gathered automatically during the "Gathering Facts" phase) giving a sortable timestamp like 20260620T220000, ensuring every backup folder is unique and chronologically sortable.
register: existing_war + stat module — We never assume a WAR already exists (first-time deployments won't have one); stat safely checks existence so subsequent backup tasks can be conditionally skipped with when.
remote_src: true — Critical flag telling the copy module the source file lives ON the remote target, not on the Ansible control node. Forgetting this is one of the most common real-world Ansible mistakes — it would otherwise try to copy a file from the control node that doesn't exist there.
tower_user_name — A magic variable automatically injected by AAP into every job run, containing the username of whoever launched the job. This single line is what gives us our audit trail for "who deployed what" — a hard PCI-DSS/RBI requirement.

Role: cbs_deploy (Tasks, Handlers, Template)

roles/cbs_deploy/tasks/main.yml
---
- name: Render application context.xml from template
  ansible.builtin.template:
    src: context.xml.j2
    dest: "{{ tomcat_home }}/conf/context.xml"
    owner: "{{ tomcat_user }}"
    group: "{{ tomcat_group }}"
    mode: '0640'
    backup: true
  notify: Restart Tomcat service

- name: Deploy the new WAR artifact to webapps directory
  ansible.builtin.copy:
    src: "files/{{ cbs_app_name }}-{{ war_version }}.war"
    dest: "{{ tomcat_webapps_dir }}/{{ cbs_app_name }}.war"
    owner: "{{ tomcat_user }}"
    group: "{{ tomcat_group }}"
    mode: '0644'
  notify: Restart Tomcat service

- name: Ensure JVM heap settings are correctly set in setenv.sh
  ansible.builtin.lineinfile:
    path: "{{ tomcat_home }}/bin/setenv.sh"
    regexp: '^export CATALINA_OPTS='
    line: "export CATALINA_OPTS=\"-Xms{{ jvm_heap_min }} -Xmx{{ jvm_heap_max }} -Dapp.version={{ war_version }}\""
    create: true
    owner: "{{ tomcat_user }}"
    mode: '0750'
  notify: Restart Tomcat service

- name: Force handlers to run now so we control timing before smoke test
  ansible.builtin.meta: flush_handlers
roles/cbs_deploy/handlers/main.yml
---
- name: Restart Tomcat service
  ansible.builtin.systemd:
    name: securecore-tomcat
    state: restarted
    daemon_reload: true
  listen: "Restart Tomcat service"

- name: Wait for Tomcat port to come up after restart
  ansible.builtin.wait_for:
    host: "{{ ansible_host }}"
    port: "{{ cbs_app_port }}"
    delay: 5
    timeout: "{{ smoke_test_timeout }}"
  listen: "Restart Tomcat service"
roles/cbs_deploy/templates/context.xml.j2
<?xml version="1.0" encoding="UTF-8"?>
{# This file is managed by Ansible — do not edit manually, changes will be overwritten #}
<Context>
    <Resource name="jdbc/SecureCoreDS"
              auth="Container"
              type="javax.sql.DataSource"
              maxTotal="{{ jvm_heap_max | regex_replace('m','') | int // 64 }}"
              maxIdle="10"
              username="{{ vault_cbs_db_username }}"
              password="{{ vault_cbs_db_password }}"
              driverClassName="oracle.jdbc.OracleDriver"
              url="{{ db_connection_url }}"/>
</Context>
Line-by-Line Explanation — tasks, handlers & template
notify: Restart Tomcat service (used 3 times) — Each task that could change runtime behaviour notifies the same handler name. Ansible automatically de-duplicates — even though 3 tasks notify it, the handler runs exactly once at the end of the play, never 3 times. This is the core idempotency pattern.
backup: true on the template task — Tells Ansible to keep a local .timestamp~ backup of context.xml on the remote host itself, as a secondary safety net in addition to our explicit cbs_backup role.
lineinfile with regexp + line — Surgically replaces just the CATALINA_OPTS export line without touching the rest of setenv.sh, which may have other custom exports added by the JVM team. Safer than templating the whole file when only one line is owned by Ansible.
ansible.builtin.meta: flush_handlers — Forces any pending handlers to execute immediately rather than waiting until the very end of the play. We need this because the next role (cbs_smoketest) must run AFTER Tomcat has actually restarted, not after the whole play finishes.
listen: "Restart Tomcat service" — Two handler tasks both listen to the same notification name, meaning a single notify call triggers both: the restart AND the subsequent wait_for port check, in that defined order.
{{ vault_cbs_db_username }} / {{ vault_cbs_db_password }} — These variables are never stored in plaintext; they live in group_vars/vault.yml encrypted with ansible-vault, and in AAP are instead injected via a Vault Credential at runtime — they never touch disk in cleartext on the control node.
{# Jinja2 comment #} at the top of the template — Renders nothing in the final XML but documents in the source file that this is Ansible-managed, a best practice to stop engineers from hand-editing config that automation will silently overwrite on the next run.

Role: cbs_smoketest

roles/cbs_smoketest/tasks/main.yml
---
- name: Hit application health endpoint over HTTPS
  ansible.builtin.uri:
    url: "https://{{ ansible_host }}:{{ cbs_app_port }}{{ cbs_health_endpoint }}"
    method: GET
    status_code: 200
    validate_certs: false
    timeout: 10
  register: health_check
  retries: 6
  delay: 10
  until: health_check.status == 200

- name: Verify the deployed application version matches expected release
  ansible.builtin.uri:
    url: "https://{{ ansible_host }}:{{ cbs_app_port }}/securecore/version"
    method: GET
    return_content: true
  register: version_check

- name: Assert deployed version matches the target release
  ansible.builtin.assert:
    that:
      - "war_version in version_check.content"
    fail_msg: "Deployed version mismatch on {{ inventory_hostname }}! Expected {{ war_version }}, got {{ version_check.content }}"
    success_msg: "Version verified successfully on {{ inventory_hostname }}"

- name: Submit one synthetic test transaction (read-only balance enquiry)
  ansible.builtin.uri:
    url: "https://{{ ansible_host }}:{{ cbs_app_port }}/securecore/api/v1/test-account/balance"
    method: GET
    status_code: 200
  register: txn_test

- name: Mark host as healthy in deployment fact cache
  ansible.builtin.set_fact:
    deployment_status: "HEALTHY"
  delegate_to: localhost
  delegate_facts: true
Line-by-Line Explanation
retries: 6 / delay: 10 / until: — Tomcat applications can take 30-60 seconds to fully initialize Spring/Hibernate contexts after the port opens. Rather than guessing a fixed sleep, we poll every 10s up to 6 times (60s total) until we get a real 200 — far more reliable than pause.
validate_certs: false — Internal banking certs are often self-signed in lower environments; in production this is instead set to true with the internal CA bundle path, controlled via a group_var per environment — a key security distinction to call out in interviews.
ansible.builtin.assert — A clean, declarative way to fail the play with a custom message if a condition isn't met — far more readable than a manual fail + when combination for simple boolean checks.
test-account/balance synthetic transaction — A non-destructive, read-only API call against a dedicated test account that exists solely for monitoring — never call real customer-impacting endpoints during automated smoke tests.
delegate_to: localhost + delegate_facts: true — Stores the health result against the control node's fact cache (not the remote host's), so the next play (rollout-gate decision) can read consolidated health status across all hosts in one place.

Role: cbs_rollback

roles/cbs_rollback/tasks/main.yml
---
- name: Find latest backup folder
  ansible.builtin.find:
    paths: "{{ cbs_backup_dir }}"
    file_type: directory
  register: backup_folders

- name: Sort and select most recent backup
  ansible.builtin.set_fact:
    latest_backup: "{{ (backup_folders.files | sort(attribute='ctime', reverse=true) | first).path }}"

- name: Stop Tomcat before rollback
  ansible.builtin.systemd:
    name: securecore-tomcat
    state: stopped

- name: Restore previous WAR file from backup
  ansible.builtin.copy:
    src: "{{ latest_backup }}/{{ cbs_app_name }}.war.bak"
    dest: "{{ tomcat_webapps_dir }}/{{ cbs_app_name }}.war"
    remote_src: true
    owner: "{{ tomcat_user }}"
    group: "{{ tomcat_group }}"

- name: Restore previous context.xml from backup
  ansible.builtin.copy:
    src: "{{ latest_backup }}/context.xml.bak"
    dest: "{{ tomcat_home }}/conf/context.xml"
    remote_src: true

- name: Start Tomcat with restored configuration
  ansible.builtin.systemd:
    name: securecore-tomcat
    state: started

- name: Wait for application to come back healthy after rollback
  ansible.builtin.uri:
    url: "https://{{ ansible_host }}:{{ cbs_app_port }}{{ cbs_health_endpoint }}"
    status_code: 200
    validate_certs: false
  register: rollback_health
  retries: 6
  delay: 10
  until: rollback_health.status == 200
Line-by-Line Explanation
ansible.builtin.find + sort(attribute='ctime', reverse=true) — Dynamically discovers the most recent backup directory rather than hardcoding a timestamp, so rollback works correctly no matter when it's triggered.
Stop → restore WAR → restore config → start, in strict sequence — Deliberately NOT restarted in one systemd call; we stop first to guarantee Tomcat releases file locks on the WAR before we overwrite it, avoiding file-in-use errors seen with live overwrites.

  hosts: "{{ rollback_target | default('app_tier') }}"

  roles:

Line-by-Line Explanation — Playbooks
hosts: canary + serial: 1 + max_fail_percentage: 0 — The canary play targets exactly one host (cbs-app01) and tolerates ZERO failures — if the canary fails, the entire play stops immediately, before a single other production server is touched. This is the single most important safety pattern in this whole project.
hosts: app_tier_mumbai:!canary — The colon-bang syntax means "all hosts in app_tier_mumbai EXCEPT those also in the canary group" — preventing the canary host from being redeployed a second time in the full rollout play.
serial: "50%" — Deploys to half the remaining hosts at a time (so 2 batches for 7 remaining Mumbai hosts), balancing speed against blast-radius — losing at most half the app tier capacity if something goes wrong mid-batch.
max_fail_percentage: 10 — Allows the play to keep going even if up to 10% of hosts in a batch fail (handles one flaky host without aborting the whole release), while still being strict enough to catch systemic problems.
when: deploy_dr_site | default(true) | bool — Reads a boolean survey variable from AAP; release managers can choose to skip the DR site deploy entirely (e.g., during DR site maintenance) directly from the AAP launch screen.
hosts: "{{ rollback_target | default('app_tier') }}" in rollback.yml — Lets the rollback be scoped narrowly (e.g., just canary or just app_tier_mumbai) via an extra var passed at launch time, instead of always rolling back the entire fleet.

🔄 13. Execution Flow — Start to Finish

1
Priya logs into AAP UI, navigates to the CBS-Production-Release Workflow Template, clicks Launch, and fills the survey: war_version = v4.8.2.
2
AAP Controller resolves the Project (pulls latest playbook code from GitLab if not cached), spins up an Execution Environment container on an available Execution Node.
3
AAP injects the Machine credential (SSH private key) and Vault credential into the container at runtime — never written to disk in plaintext.
4
Ansible reads inventory/production/hosts.ini (or Smart Inventory), resolves the canary group to a single host: cbs-app01.
5
Gathering Facts phase runs implicitly first (unless gather_facts: false) — collects ansible_date_time, ansible_host, OS facts via the setup module, used later by cbs_backup and templates.
6
Roles execute in order: tomcat_precheck → cbs_backup → cbs_deploy → cbs_smoketest. Each task connects over SSH (pipelined, multiplexed connection), executes the corresponding Python module remotely, and returns JSON results.
7
Within cbs_deploy, three tasks notify the Restart Tomcat service handler. Ansible queues it once. meta: flush_handlers forces it to run immediately rather than waiting for end-of-play.
8
Handler restarts Tomcat via systemd, then waits for the port to open — blocking further tasks until the app is actually reachable.
9
cbs_smoketest polls the health endpoint and verifies the version string, asserting correctness; results streamed live to the AAP job output console.
10
If canary succeeds, the Workflow pauses at the Approval Node — Priya (or a designated approver) reviews the canary job log and clicks Approve.
11
CBS-Deploy-FullProd job template launches, applying the same roles to the remaining 11 servers in 50%-serial batches across Mumbai and Chennai DR.
12
On workflow completion, the Notification Template fires a Slack message and email with final status, job IDs, and duration — completing the audit trail required for RBI compliance.
13
If any stage fails beyond the tolerated max_fail_percentage, the corresponding failure-path edge in the workflow auto-triggers CBS-Rollback, restoring the previous WAR and config from the timestamped backup.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: A production deployment fails on host 4 of 12. What happens to hosts 5-12?
With serial: "50%" and max_fail_percentage: 10, if the failure rate within that batch exceeds 10%, Ansible stops launching further batches — hosts in the current batch already running may finish, but no new batch starts. The workflow's failure edge then triggers the rollback job template automatically.
Q: How do you ensure zero customers are impacted during deployment?
The Web Tier (HAProxy/HTTPD) is configured (in a separate role, often combined with Project 12: Blue-Green Deployment) to drain connections from an app server before it's taken out for deployment and only re-add it to the load-balancer pool after smoke tests pass — never deploying to all app servers simultaneously.
Q: How would you handle a WAR file that's too large for Git/AAP project sync?
WAR artifacts are not stored in the Ansible Git project at all in real life — they're pulled from an artifact repository (Nexus/Artifactory) using the get_url or maven_artifact module with checksum validation, referenced by version tag from the survey variable.

Production Support & Troubleshooting

Q: Job is "stuck" in AAP at the wait_for handler step. How do you debug?
Check AAP job stdout for the exact host; SSH manually and check journalctl -u securecore-tomcat -f and catalina.out for startup exceptions (commonly a DB connection pool failure or port already bound by a zombie process from a failed previous restart).
Q: How do you prevent two engineers from launching the same Job Template simultaneously?
Enable "Concurrent Jobs" = disabled (instance limit) on the Job Template in AAP, and/or use the throttle keyword in playbooks — AAP queues the second job until the first finishes rather than running both concurrently against the same hosts.
Q: Architecture question: why use a separate Execution Environment image instead of installing Oracle client on the AAP control node directly?
EEs are immutable, versioned containers — this guarantees the exact same Oracle Instant Client, Python, and collection versions every single run, regardless of which Execution Node in the cluster picks up the job, eliminating "works on one node, not another" drift.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Canary + serial + max_fail_percentage is the core safety pattern for any production rollout playbook.
  • Handlers + flush_handlers give you precise control over WHEN a restart happens relative to validation steps.
  • AAP Workflow approval nodes turn a risky one-click deploy into a controlled, auditable change process.
  • remote_src, become, and vault are the three flags most commonly forgotten by intermediate engineers.

Common Mistakes

  • Forgetting changed_when: false on read-only shell/command tasks, breaking idempotency reporting.
  • Hardcoding the backup folder path instead of timestamping it — overwrites previous backups silently.
  • Restarting Tomcat unconditionally instead of via notify/handler — causes unnecessary downtime on no-op runs.
  • Running full-fleet deployment without a canary gate — the #1 cause of bank-wide outages from bad releases.

Production Best Practices

  • Always vault-encrypt or externalize DB credentials — never plaintext in Git, ever.
  • Use --check --diff before every real production run as a dry-run habit.
  • Tag plays/roles (--tags precheck) so individual phases can be re-run without a full redeploy.
  • Keep rollback.yml as a first-class, equally tested playbook — not an afterthought.

Resume Points

  • Designed and implemented a canary-gated, serial-batch Ansible deployment pipeline for a core banking Tomcat application across 12+ production servers spanning primary and DR data centers, reducing release time from 4+ hours to under 20 minutes.
  • Built Red Hat AAP Workflow Templates with manual approval gates and automated rollback paths, achieving full audit-trail compliance for RBI/PCI-DSS change management requirements.
  • Implemented idempotent, handler-driven configuration management eliminating manual Tomcat restarts and configuration drift across the application tier.
