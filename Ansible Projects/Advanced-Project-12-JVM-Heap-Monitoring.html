Project 12: JVM Heap Monitoring, Thread Dump Collection & GC Analysis Automation

ABC Global Bank runs its Core Banking System (CBS), Loan Management System (LMS), and Payment Gateway on Java middleware — Apache Tomcat 10, JBoss EAP 7.4, and Oracle WebLogic 14c across 180 application servers. Java applications are uniquely vulnerable to OutOfMemoryError (OOM) — when the JVM heap fills up, the application freezes or crashes with no warning. Manual JVM monitoring requires DBAs and app teams to constantly check JConsole dashboards. This project automates JVM heap monitoring via JMX, automatic thread dump collection when heap is high (for developer analysis), heap dump triggering on OOM, GC pause analysis, and Tomcat connector thread pool monitoring — all producing evidence for the performance team and CISO.

🏦 1. The Banking Story

Setting: ABC Global Bank's Loan Management System (LMS) runs on JBoss EAP 7.4 across 12 application servers. The JVM heap is configured as 4GB (-Xmx4g). The LMS processes loan disbursements, EMI calculations, and credit limit checks for 850,000 active loan accounts.

Incident 1 — The Silent OOM: On a Monday morning (peak load — 47,000 customers checking loan status via mobile banking), the JVM heap on lms-app03 reached 98% utilization. The application entered "Stop-The-World" GC pauses — the entire JVM froze for 12-15 seconds at a time while GC ran. Customers saw "Request Timed Out" errors. The application eventually threw java.lang.OutOfMemoryError: Java heap space and crashed at 11:23 AM. Nobody noticed for 14 minutes because the monitoring system only checked process PID — the Tomcat process was still technically running (JBoss doesn't always exit on OOM). The thread was stuck in OOM state, consuming no CPU, appearing "up" to process monitors.

Incident 2 — The Thread Deadlock: The LMS payment processing module had a thread deadlock that locked 48 of 200 request processing threads. Response times increased from 200ms to 8+ seconds. No OOM — just slow. The app team needed a thread dump to diagnose the deadlock. Getting a thread dump required: engineer SSHing to each of 12 servers, finding the JBoss PID, running jstack, collecting the output, and emailing it to the developer. This took 45 minutes across 12 servers. By the time the developer got the thread dump from all 12 servers, the deadlock had self-resolved and the dumps were stale.

Incident 3 — The GC Tuning Request: The CISO asked for evidence that all JVM processes have adequate memory headroom. The app team had no centralized data — each engineer knew their 2-3 servers but nobody knew the fleet status. Generating the report took 3 days of manual data collection.

The Ask: "Monitor heap on all 180 JVM servers every 5 minutes. Auto-collect thread dumps when heap > 80%. Auto-trigger heap dump on OOM. Alert on high GC pause times. Give us a daily report of JVM health across the fleet."

📚 2. JVM & JMX Concepts

JVM Memory Pools — What to Monitor
Memory PoolWhat It StoresAlert When
Heap — Young Gen (Eden)New objects; cleared by Minor GC frequentlyRapid fill rate indicates high allocation
Heap — Old Gen (Tenured)Long-lived objects; cleared by Major GCAlert at 75% — Full GC when this fills = application freeze
MetaspaceClass metadata (Java 8+, replaced PermGen)Alert at 80% — class loading leak
Code CacheJIT-compiled native codeAlert at 90% — JIT disabled, performance degrades
Key insight: Most OOM errors come from Old Gen filling up. We primarily monitor Old Gen (Tenured) percentage.
JMX — How Ansible Queries JVM Metrics
JMX (Java Management Extensions) is Java's built-in monitoring API. Every JVM exposes JMX beans (MBeans) that contain runtime metrics — heap usage, thread counts, GC statistics, class loading, etc.

To enable JMX remote access, add these JVM flags:
-Dcom.sun.management.jmxremote
-Dcom.sun.management.jmxremote.port=9010
-Dcom.sun.management.jmxremote.authenticate=false

Ansible queries JMX using a Python script with the jmxquery library, or via jcmd / jstat command-line tools included in the JDK. We use both approaches — jstat for quick heap stats (no JMX port needed) and jmxquery for detailed Tomcat connector thread pool metrics.
Thread Dump vs Heap Dump — What Each Tells You
Thread Dump (jstack PID): Snapshot of all thread states at a moment in time. Shows what every thread is doing — which lock it holds, which it's waiting for. Used for: deadlock diagnosis, identifying "stuck" threads, finding which thread is causing high CPU.

Heap Dump (jmap -dump:format=b PID or jcmd PID GC.heap_dump): Complete snapshot of all objects in the JVM heap. Can be analyzed with tools like Eclipse MAT (Memory Analyzer Tool) or VisualVM. Used for: OOM analysis, memory leak detection, finding which objects are consuming heap.

Our automation strategy: Thread dump automatically when heap > 80% (early warning). Heap dump on OOM or heap > 95% (for post-mortem analysis). Thread dump collection is fast (< 1 second). Heap dump can be 1-4GB — requires adequate disk space.
GC Pause Analysis — Why It Matters in Banking
When the JVM runs Garbage Collection, it may stop all application threads (Stop-The-World pause). In banking:
Minor GC: Clears Young Gen. Usually 10-50ms. Acceptable.
Major/Full GC: Clears Old Gen. Can take 1-30+ seconds. CRITICAL — all transactions freeze during this time.

A 5-second GC pause on the CBS application server means 5 seconds where no transactions are processed, no API calls respond, no database writes complete. For RTGS/NEFT systems with strict timing requirements, GC pauses exceeding 2 seconds can cause transaction failures.

We monitor GC pause time using jstat -gcutil PID which shows: Young GC count, Young GC time, Full GC count, Full GC time. Increasing Full GC time is an early warning of OOM.

Role 1: jvm_discovery — Find All JVM Processes

roles/jvm_discovery/tasks/find_jvm_processes.yml
---
# =====================================================================
# Discover all running JVM processes dynamically
# Extracts: PID, app name, heap settings, JMX port
# Using jps (JDK tool) for reliable JVM-specific process listing
# =====================================================================

- name: List all running JVM processes using jps
  ansible.builtin.shell:
    cmd: "jps -lv 2>/dev/null || ps aux | grep java | grep -v grep"
    # jps: JDK tool — lists Java processes only
    # -l: show full main class name
    # -v: show JVM flags (including -Xmx heap setting)
    # Fallback: ps aux if jps not available
    executable: /bin/bash
  register: jvm_process_list
  changed_when: false
  become: true
  become_user: root

- name: Parse JVM processes into structured list
  ansible.builtin.set_fact:
    discovered_jvms: >-
      {{ discovered_jvms | default([]) + [{
        'pid': item.split()[0],
        'main_class': item.split()[1] | default('Unknown'),
        'app_name': (jvm_app_identifiers
                     | selectattr('pattern', 'in', item)
                     | map(attribute='app_name')
                     | first | default('Unknown-Java')),
        'xmx_mb': (item | regex_search('-Xmx([0-9]+)([gGmM])', '\\1', '\\2')
                   | default(['0', 'M'])),
        'jmx_port': (item | regex_search('jmxremote\\.port=([0-9]+)', '\\1')
                     | first | default(jmx_port | string))
      }] }}
  loop: "{{ jvm_process_list.stdout_lines | reject('match', '^[0-9]+ Jps.*') | list }}"
  loop_control:
    label: "PID {{ item.split()[0] | default('?') }}"
  # Reject the jps process itself from the list

- name: Fail if no JVM processes found (expected JVM is missing)
  ansible.builtin.debug:
    msg: >-
      ⚠️ WARNING: No JVM processes found on {{ inventory_hostname }}.
      Expected {{ middleware_type }} to be running.
      Check if the application server is down.
  when: discovered_jvms | default([]) | length == 0

- name: Log discovered JVMs
  ansible.builtin.debug:
    msg:
      - "JVM Discovery — {{ inventory_hostname }}"
      - "Found {{ discovered_jvms | length }} JVM process(es)"
      - "{% for jvm in discovered_jvms %}"
      - "  PID={{ jvm.pid }} App={{ jvm.app_name }} JMX={{ jvm.jmx_port }}"
      - "{% endfor %}"

Role 2: jvm_heap_check — Query Heap via jstat

roles/jvm_heap_check/tasks/query_heap_jstat.yml
---
# =====================================================================
# Query JVM heap metrics using jstat
# jstat is included in JDK — no external library needed
# =====================================================================

- name: Query heap utilization for each discovered JVM
  ansible.builtin.shell:
    cmd: >
      jstat -gcutil {{ item.pid }} 1 1 2>/dev/null
    # jstat -gcutil PID interval count
    # -gcutil: garbage collection utilization summary
    # Output columns: S0 S1 E O M CCS YGC YGCT FGC FGCT GCT
    # S0/S1: Survivor spaces %
    # E: Eden % (Young Gen)
    # O: Old Gen % ← KEY METRIC for OOM prediction
    # M: Metaspace %
    # YGC/YGCT: Young GC count/time
    # FGC/FGCT: Full GC count/time ← KEY for GC pause analysis
  register: jstat_outputs
  loop: "{{ discovered_jvms | default([]) }}"
  loop_control:
    label: "PID {{ item.pid }} ({{ item.app_name }})"
  changed_when: false
  become: true
  become_user: "{{ app_user }}"         # Run as app user (not root) to access JVM
  failed_when: false

- name: Parse jstat output into heap metrics per JVM
  ansible.builtin.set_fact:
    jvm_heap_metrics: >-
      {{ jvm_heap_metrics | default([]) + [{
        'pid': item.item.pid,
        'app_name': item.item.app_name,
        'host': inventory_hostname,
        'eden_pct': (item.stdout_lines | last | split() | list)[2] | float | round(1)
                    if item.stdout_lines | length >= 2 else 0,
        'old_gen_pct': (item.stdout_lines | last | split() | list)[3] | float | round(1)
                       if item.stdout_lines | length >= 2 else 0,
        'metaspace_pct': (item.stdout_lines | last | split() | list)[4] | float | round(1)
                         if item.stdout_lines | length >= 2 else 0,
        'full_gc_count': (item.stdout_lines | last | split() | list)[8] | int
                         if item.stdout_lines | length >= 2 else 0,
        'full_gc_time_sec': (item.stdout_lines | last | split() | list)[9] | float | round(2)
                            if item.stdout_lines | length >= 2 else 0,
        'jstat_failed': item.rc != 0
      }] }}
  loop: "{{ jstat_outputs.results }}"
  loop_control:
    label: "{{ item.item.app_name }} PID={{ item.item.pid }}"
  # Split the last line of jstat output (header is first line, data is second)

- name: Classify heap severity for each JVM
  ansible.builtin.set_fact:
    jvm_severity_map: >-
      {{ jvm_severity_map | default([]) + [{
        'pid': item.pid,
        'app_name': item.app_name,
        'old_gen_pct': item.old_gen_pct,
        'full_gc_count': item.full_gc_count,
        'severity': ('EMERGENCY' if item.old_gen_pct >= jvm_heap_emergency_percent
                     else ('CRITICAL' if item.old_gen_pct >= jvm_heap_critical_percent
                           else ('WARNING' if item.old_gen_pct >= jvm_heap_warn_percent
                                 else 'OK'))),
        'gc_severity': ('CRITICAL' if item.full_gc_count >= full_gc_count_critical
                        else ('WARNING' if item.full_gc_count >= full_gc_count_warn
                              else 'OK'))
      }] }}
  loop: "{{ jvm_heap_metrics | default([]) }}"
  loop_control:
    label: "{{ item.app_name }}"

- name: Log heap monitoring summary
  ansible.builtin.debug:
    msg:
      - "JVM Heap Monitor — {{ inventory_hostname }}"
      - "{% for jvm in jvm_severity_map %}"
      - "  {{ jvm.app_name }} PID={{ jvm.pid }}: OldGen={{ jvm.old_gen_pct }}%
          FullGC={{ jvm.full_gc_count }} — {{ jvm.severity }}"
      - "{% endfor %}"

- name: Fire PagerDuty EMERGENCY for JVMs near OOM
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "jvm-heap-emergency-{{ inventory_hostname }}-{{ item.pid }}"
      payload:
        summary: >-
          🚨 JVM HEAP EMERGENCY: {{ item.app_name }} PID={{ item.pid }}
          on {{ inventory_hostname }} Old Gen={{ item.old_gen_pct }}%.
          OutOfMemoryError IMMINENT. Auto-heap dump triggered.
        severity: critical
        source: ansible-jvm-monitor
        custom_details:
          host: "{{ inventory_hostname }}"
          app: "{{ item.app_name }}"
          pid: "{{ item.pid }}"
          old_gen_pct: "{{ item.old_gen_pct }}"
          full_gc_count: "{{ item.full_gc_count }}"
          action_taken: "Thread dump + Heap dump collection initiated"
    status_code: [202]
  loop: "{{ jvm_severity_map | selectattr('severity', 'equalto', 'EMERGENCY') | list }}"
  loop_control:
    label: "{{ item.app_name }}"
  delegate_to: localhost
  when: jvm_severity_map | selectattr('severity', 'equalto', 'EMERGENCY') | list | length > 0

- name: Fire PagerDuty CRITICAL for JVMs with high heap
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"

        source: ansible-jvm-monitor

  loop: "{{ jvm_severity_map | selectattr('severity', 'equalto', 'CRITICAL') | list }}"
  loop_control:
    label: "{{ item.app_name }}"
  delegate_to: localhost
  when: jvm_severity_map | selectattr('severity', 'equalto', 'CRITICAL') | list | length > 0
roles/jvm_heap_check/tasks/query_tomcat_jmx.yml
---
# =====================================================================
# Query Tomcat Connector Thread Pool via JMX (Jolokia HTTP bridge)
# Thread pool exhaustion = new requests rejected = application unavailable
# =====================================================================

- name: Query Tomcat connector thread metrics via Jolokia HTTP API
  ansible.builtin.uri:
    url: >-
      http://localhost:8778/jolokia/read/
      Catalina:name="http-nio-8080",type=ThreadPool/
      currentThreadCount,currentThreadsBusy,maxThreads
    # Jolokia: HTTP bridge to JMX — exposes JMX as REST API
    # URL format: /jolokia/read/MBean-Name/attribute1,attribute2
    # Catalina:name=...,type=ThreadPool: Tomcat's connector MBean
    method: GET
    return_content: true
    status_code: [200]
    timeout: 10
  register: jolokia_thread_data
  failed_when: false
  when: middleware_type == 'tomcat'

- name: Parse Tomcat thread pool metrics
  ansible.builtin.set_fact:
    tomcat_threads:
      current_total: "{{ jolokia_thread_data.json.value.currentThreadCount | int }}"
      current_busy: "{{ jolokia_thread_data.json.value.currentThreadsBusy | int }}"
      max_threads: "{{ jolokia_thread_data.json.value.maxThreads | int }}"

roles/jvm_gc_analysis/tasks/parse_gc_log.yml
---
# =====================================================================
# Parse GC Log File for Full GC Pause Patterns
# GC log gives historical pause data — jstat only gives current totals
# =====================================================================

- name: Read last 200 lines of GC log file
  ansible.builtin.shell:
    cmd: "tail -200 {{ gc_log_path }} 2>/dev/null || echo 'GC_LOG_NOT_FOUND'"
  register: gc_log_tail
  changed_when: false
  become: true
  failed_when: false

- name: Extract Full GC events from GC log (G1GC format)
  ansible.builtin.set_fact:
    full_gc_events: >-
      {{ gc_log_tail.stdout_lines
         | select('match', '.*GC\\(.*Full GC.*\\).*')
         | list }}
    # G1GC full GC log format:
    # [2024-01-15T14:23:45.123+0530] GC(42) Full GC (System.gc())
    # [2024-01-15T14:23:52.456+0530] GC(42) Pause Full (System.gc()) 2048M->1024M(4096M) 7324ms
    # We look for "Full GC" lines to count occurrences

- name: Extract pause durations from Full GC events
  ansible.builtin.set_fact:
    full_gc_pause_times: >-
      {{ full_gc_events
         | map('regex_search', '([0-9]+)ms', '\\1')
         | select('ne', none)
         | map('first')
         | map('int')
         | list }}
    # regex_search extracts the pause time in milliseconds

- name: Calculate GC statistics
  ansible.builtin.set_fact:
    gc_analysis:
      full_gc_count_recent: "{{ full_gc_events | length }}"
      max_pause_ms: "{{ full_gc_pause_times | max | default(0) }}"
      avg_pause_ms: >-
        {{ (full_gc_pause_times | sum / (full_gc_pause_times | length))
           | round(0) | int
           if full_gc_pause_times | length > 0 else 0 }}
      exceeds_warn_threshold: >-
        {{ full_gc_events | length >= full_gc_count_warn | int
           or (full_gc_pause_times | max | default(0) | int)
              >= (full_gc_pause_warn_sec * 1000) | int }}

- name: Alert on excessive Full GC activity
  ansible.builtin.uri:
    url: "{{ slack_webhook_url }}"
    method: POST
    body_format: json
    body:
      text: >-
        ⚠️ *JVM Full GC Alert — {{ inventory_hostname }}*
        *Full GC Events:* {{ gc_analysis.full_gc_count_recent }}
        *Max Pause:* {{ gc_analysis.max_pause_ms }}ms
        *Avg Pause:* {{ gc_analysis.avg_pause_ms }}ms
        {% if gc_analysis.max_pause_ms | int >= (full_gc_pause_critical_sec * 1000) | int %}
        🔴 CRITICAL: Pause exceeds {{ full_gc_pause_critical_sec }}s threshold
        Applications experienced {{ gc_analysis.max_pause_ms }}ms freeze
        {% endif %}
    status_code: [200]
  delegate_to: localhost
  when: gc_analysis.exceeds_warn_threshold | bool

🎯 15. Interview Prep

Q: Why do you collect 3 thread dumps 30 seconds apart instead of just one?
A single thread dump shows thread states at one moment — but it's hard to distinguish between a thread that's legitimately processing (briefly BLOCKED) and one that's deadlocked (permanently BLOCKED).

Three dumps 30 seconds apart reveal patterns: a thread stuck in BLOCKED state in all 3 dumps, waiting for the same lock, while the lock-holding thread is also WAITING — that's a deadlock signature. A thread that was BLOCKED in dump 1 but RUNNABLE in dump 2 was just temporarily waiting.

This is the same technique recommended by Oracle, IBM, and Java performance experts for deadlock diagnosis. Automated collection via Ansible eliminates the 45-minute manual process from Incident 2 — developers get all 3 dumps from all 12 servers within 2 minutes of heap threshold being exceeded.
Q: What is the difference between jstat, jmap, and jcmd for JVM monitoring?
jstat: Lightweight, real-time statistics reader. No JVM impact. Reads counters directly from JVM's shared memory. Best for continuous monitoring. Cannot trigger actions — read-only.

jmap: Can read heap summaries AND create heap dumps. Older tool — creates heap dumps by attaching to JVM using ptrace (can briefly pause the JVM). Less safe for production.

jcmd: Modern, preferred tool (Java 7+). Sends diagnostic commands to JVM via its own internal interface (no ptrace). GC.heap_dump is safer than jmap for production heap dumps. Also can: VM.flags (see JVM flags), Thread.print (thread dump), GC.run (trigger GC).

Our automation uses: jstat for continuous 5-minute heap monitoring, jstack for thread dumps (specifically designed for this), jcmd for heap dumps (safer than jmap in production).
Q: What is Stop-The-World GC and why is it critical in banking transaction systems?
Stop-The-World (STW) is a JVM GC mechanism where ALL application threads are paused while the garbage collector runs. During this pause: no transactions are processed, no API requests complete, no database writes happen — the JVM is completely frozen.

In banking, STW pauses matter for: RTGS (Real-Time Gross Settlement) — transactions have strict timing requirements. SWIFT payment gateways — messages must be processed within seconds. CBS transaction commits — customer-facing operations freeze.

Modern GC algorithms (G1GC, ZGC, Shenandoah) reduce STW pauses, but Full GC is still often STW. Monitoring Full GC pause times is essential — a 5-second Full GC pause in the Core Banking System means 5 seconds where 2,400 branch tellers see frozen screens. Our GC log analysis specifically tracks Full GC pause duration and alerts if any pause exceeds 2 seconds (our SLA threshold).
Q: How do you handle the case where a JVM is restarted between Ansible monitoring runs (new PID)?
Our JVM discovery role runs on EVERY 5-minute cycle — we use jps -lv (or ps aux | grep java) to dynamically discover all current JVM PIDs at the start of each run. We never store PIDs in inventory or variables that persist between runs.

This means: if Tomcat restarts between minute 10 and minute 15, the minute 15 run discovers the new PID automatically. The restart counter (stored separately for tracking crash loops) is keyed by app_name and hostname — not by PID. So the crash loop detection still works even after PID changes.

This is why dynamic JVM discovery is essential in banking — application servers restart regularly for deployments, patches, and OOM recovery. A static PID-based approach would miss new JVM instances.
