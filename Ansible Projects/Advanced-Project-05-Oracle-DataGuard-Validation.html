Project 05: Oracle Data Guard Failover Validation & DR Readiness Automation

Oracle Data Guard is the cornerstone of disaster recovery for Oracle databases in banking. It maintains a synchronized standby database in a secondary data center. When the primary site fails, Data Guard enables failover — switching the standby into production role. But Data Guard's health degrades silently: the MRP (Managed Recovery Process) can stop, redo log transport can lag hours behind, or the standby can diverge from the primary. This project automates complete Data Guard health validation — MRP status, transport lag, apply lag, redo log gaps, DG Broker configuration health, pre-failover readiness scoring, and post-failover role verification.

🏦 1. The Banking Story

Setting: ABC Global Bank runs the Core Banking System (CBS) on Oracle 19c RAC (2 nodes) in the primary Mumbai data center. A Data Guard standby database in Chennai serves as the DR site — capable of taking over if Mumbai goes down. RBI requires banks to demonstrate DR capability every quarter.

The Incident: On a Saturday at 11:42 PM, a fire suppression system accidentally discharged in the Mumbai data center's DB room. All Oracle servers shut down safely via power UPS logic. The DR team initiated CBS failover to Chennai. The standby database opened in read-write mode — but transaction processing immediately failed. After 90 minutes of frantic investigation, the DBA team discovered: the standby's MRP process had been stopped 4 days earlier during routine maintenance and never restarted. The standby had not applied any redo logs for 4 days — it was 4 days behind the primary. Failover succeeded, but 4 days of transactions were missing.

Regulatory Impact: RBI's Department of Regulation sent a show-cause notice. The bank's RTO (Recovery Time Objective) target was 4 hours — actual RTO was 6 hours including data reconciliation. RPO (Recovery Point Objective) was 0 (zero data loss) — actual RPO was 4 days. The bank was fined ₹5 crore and required to implement automated DR monitoring.

The Ask: "We need Data Guard health checked every 15 minutes, automated. We need the MRP status verified. We need transport and apply lag measured. And we need a pre-drill validation that BLOCKS the drill if DG is not healthy — we can never again start a DR drill against a 4-day-behind standby."

📚 2. Oracle Data Guard — Concepts You Must Know

Data Guard Architecture: Primary, Standby, MRP
Primary Database: The active production database. All application writes go here.

Standby Database: An identical copy of the primary — kept in sync via redo log shipping. The standby applies redo logs from the primary to stay current. In banking: typically in a separate data center.

MRP (Managed Recovery Process): The background process on the standby that automatically applies redo logs. If MRP stops, the standby stops receiving updates. This is the process that was not running in our incident. MRP is started with ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT.

Log Transport: The process of sending redo log data from primary to standby. Transport lag = how far behind the standby is in RECEIVING logs from primary.

Apply Lag: Even after logs are received, they must be applied by MRP. Apply lag = how far behind the standby is in APPLYING received logs. In production: both should be < 30 seconds.
Key Oracle DG Views and Commands
Oracle SQL — Key Data Guard Monitoring Queries
-- Run on PRIMARY to check DG configuration
SELECT DATABASE_ROLE, DB_UNIQUE_NAME, OPEN_MODE, PROTECTION_MODE
FROM V$DATABASE;

-- Run on PRIMARY to see all standby databases
SELECT DEST_ID, STATUS, TARGET, ARCHIVER, SCHEDULE,
       DESTINATION, ERROR, DB_UNIQUE_NAME
FROM V$ARCHIVE_DEST_STATUS
WHERE TARGET = 'STANDBY';

-- Run on STANDBY to check MRP (Managed Recovery Process) status
SELECT PROCESS, STATUS, THREAD#, SEQUENCE#, BLOCK#, BLOCKS
FROM V$MANAGED_STANDBY
WHERE PROCESS LIKE 'MRP%';
-- If no rows returned: MRP is NOT running!
-- STATUS should be 'APPLYING_LOG' (healthy) or 'WAIT_FOR_LOG' (waiting for next log)

-- Run on STANDBY to measure apply and transport lag
SELECT NAME, VALUE, DATUM_TIME
FROM V$DATAGUARD_STATS
WHERE NAME IN ('transport lag', 'apply lag',
               'apply finish time', 'estimated startup time');
-- transport lag: '+00 00:00:12' means 12-second transport lag
-- apply lag:     '+00 00:00:08' means 8-second apply lag
-- Format: +DD HH:MI:SS (days:hours:minutes:seconds)

-- Check for redo log gaps on standby (data divergence)
SELECT HIGH_SEQUENCE#, LOW_SEQUENCE#
FROM V$ARCHIVE_GAP;
-- Any rows here = SERIOUS PROBLEM: standby is missing redo logs
-- This indicates data loss will occur on failover

-- DGMGRL (Data Guard Broker) health check
-- Run: dgmgrl / as sysdba
-- DGMGRL> show configuration;
-- DGMGRL> show database verbose 'CBSSTBY';
Switchover vs Failover — Critical Difference
Switchover (Planned): A graceful role reversal. Primary becomes standby, standby becomes primary. ZERO data loss. Used for planned maintenance, DR drills. Both databases must be healthy and synchronized.

Failover (Unplanned): Emergency operation when primary is unavailable. Standby is activated as new primary. Possible data loss if standby was not fully synchronized (like our incident). Used when primary data center is down.

Our automation covers: validating if DG is ready for switchover (pre-drill), monitoring for conditions requiring failover (primary unreachable), and validating the DG configuration is healthy enough for either operation.
Protection Modes — How They Affect Banking
ModeHow It WorksData Loss RiskBanking Use Case

Maximum AvailabilityPrimary waits for standby when available. Falls back to async if standby unavailable.Zero when syncCommon for CBS, SWIFT
Maximum PerformancePrimary does NOT wait for standby. Async replication.Possible (seconds to minutes)Common for reporting databases

❗ 4. Problem Statement & Root Causes

Why the Incident Happened

  • MRP stopped during maintenance → nobody restarted it
  • No automated check of MRP status — only manual DBA dashboard
  • No alert when transport lag exceeded threshold
  • No pre-drill validation — DR drill started against degraded standby
  • RPO/RTO not continuously measured — only discovered during incident
  • DG Broker showed WARNING for 4 days — nobody saw it

What Automation Prevents

  • MRP check every 15 min → PagerDuty P1 within 15 min if MRP stops
  • Transport/apply lag measured continuously → alert before it grows critical
  • Pre-drill check BLOCKS drill if MRP not running or lag > threshold
  • Redo gap detection → immediate P1 — data divergence detected immediately
  • Daily report gives DBA team 24-hour visibility of DG health trends
  • Post-failover check confirms new primary is healthy before declaring DR complete

roles/dg_check_standby/tasks/check_mrp_status.yml
---
# =====================================================================
# Check MRP (Managed Recovery Process) status on standby
# MRP is the heartbeat of Data Guard — if it stops, standby falls behind
# =====================================================================

- name: Query MRP process status from V$MANAGED_STANDBY
  ansible.builtin.shell:
    cmd: >
      python3 /tmp/dg_query.py
      --host {{ ansible_host }}
      --port {{ oracle_port }}
      --sid {{ oracle_sid }}
      --user {{ oracle_monitor_user }}
      --password "{{ vault_oracle_monitor_pass }}"
      --query "SELECT PROCESS, STATUS, SEQUENCE#, BLOCK#
               FROM V\$MANAGED_STANDBY
               WHERE PROCESS LIKE 'MRP%'"
  register: mrp_query_result
  changed_when: false
  no_log: true                                             # Hide Oracle password from AAP logs
  become: true
  become_user: "{{ oracle_user }}"
  environment: "{{ oracle_env }}"

- name: Parse MRP query results
  ansible.builtin.set_fact:
    mrp_data: "{{ mrp_query_result.stdout | from_json }}"

- name: Determine MRP health status
  ansible.builtin.set_fact:
    mrp_is_running: "{{ mrp_data | length > 0 }}"
    mrp_status: >-
      {{ mrp_data[0].status if mrp_data | length > 0 else 'NOT_RUNNING' }}
    mrp_sequence: >-
      {{ mrp_data[0].sequence | default(0) if mrp_data | length > 0 else 0 }}
    # MRP healthy states:
    # APPLYING_LOG: MRP is actively applying redo from a log file
    # WAIT_FOR_LOG: MRP is waiting for next redo log (normal between logs)
    # WAIT_FOR_GAP: MRP waiting for a missing log — PROBLEM!
    # NOT_RUNNING: No MRP process at all — CRITICAL!
    mrp_is_healthy: >-
      {{ mrp_data | length > 0
         and mrp_data[0].status in ['APPLYING_LOG', 'WAIT_FOR_LOG'] }}

- name: Log MRP status
  ansible.builtin.debug:
    msg: >-
      MRP Status on {{ inventory_hostname }} ({{ oracle_sid }}):
      Running: {{ mrp_is_running }}
      Status: {{ mrp_status }}
      Current Sequence: {{ mrp_sequence }}
      Healthy: {{ mrp_is_healthy }}
roles/dg_check_standby/tasks/check_lag.yml
---
# =====================================================================
# Measure Transport Lag and Apply Lag from V$DATAGUARD_STATS
# These are the key metrics for RPO measurement
# =====================================================================

- name: Query Data Guard lag statistics from V$DATAGUARD_STATS
  ansible.builtin.shell:
    cmd: >
      python3 /tmp/dg_query.py
      --host {{ ansible_host }}
      --port {{ oracle_port }}
      --sid {{ oracle_sid }}
      --user {{ oracle_monitor_user }}
      --password "{{ vault_oracle_monitor_pass }}"
      --query "SELECT NAME, VALUE
               FROM V\$DATAGUARD_STATS
               WHERE NAME IN ('transport lag', 'apply lag',
                              'apply finish time')"
  register: lag_query_result
  changed_when: false
  no_log: true
  become: true
  become_user: "{{ oracle_user }}"
  environment: "{{ oracle_env }}"

- name: Parse lag query results into dict
  ansible.builtin.set_fact:
    lag_data_raw: "{{ lag_query_result.stdout | from_json }}"

- name: Build lag metrics dict for easy access
  ansible.builtin.set_fact:
    lag_metrics: >-
      {{ lag_data_raw | items2dict(key_name='name', value_name='value') }}
    # items2dict: converts list of {name:, value:} to {name: value}
    # Result: {'transport lag': '+00 00:00:08', 'apply lag': '+00 00:00:12'}

- name: Parse lag values from Oracle interval format to minutes
  # Oracle format: +DD HH:MI:SS (e.g., '+00 00:05:30' = 5 min 30 sec = 5.5 min)
  ansible.builtin.set_fact:
    transport_lag_raw: "{{ lag_metrics['transport lag'] | default('+99 99:99:99') }}"
    apply_lag_raw: "{{ lag_metrics['apply lag'] | default('+99 99:99:99') }}"

- name: Convert Oracle lag interval to total minutes
  ansible.builtin.set_fact:
    transport_lag_minutes: >-
      {{ (transport_lag_raw
          | regex_replace('\\+([0-9]+) ([0-9]+):([0-9]+):([0-9]+)', '\\1')
          | int * 1440)
         + (transport_lag_raw
            | regex_replace('\\+([0-9]+) ([0-9]+):([0-9]+):([0-9]+)', '\\2')
            | int * 60)
         + (transport_lag_raw
            | regex_replace('\\+([0-9]+) ([0-9]+):([0-9]+):([0-9]+)', '\\3')
            | int) }}
    apply_lag_minutes: >-
      {{ (apply_lag_raw
          | regex_replace('\\+([0-9]+) ([0-9]+):([0-9]+):([0-9]+)', '\\1')
          | int * 1440)
         + (apply_lag_raw
            | regex_replace('\\+([0-9]+) ([0-9]+):([0-9]+):([0-9]+)', '\\2')
            | int * 60)
         + (apply_lag_raw
            | regex_replace('\\+([0-9]+) ([0-9]+):([0-9]+):([0-9]+)', '\\3')
            | int) }}
    # regex_replace extracts days, hours, minutes separately
    # Formula: days×1440 + hours×60 + minutes = total minutes

- name: Classify lag severity
  ansible.builtin.set_fact:
    transport_lag_severity: >-
      {{ 'CRITICAL' if transport_lag_minutes | int >= dg_transport_lag_critical_minutes
         else ('WARNING' if transport_lag_minutes | int >= dg_transport_lag_warn_minutes
               else 'OK') }}
    apply_lag_severity: >-
      {{ 'CRITICAL' if apply_lag_minutes | int >= dg_apply_lag_critical_minutes
         else ('WARNING' if apply_lag_minutes | int >= dg_apply_lag_warn_minutes
               else 'OK') }}

- name: Log lag measurement results
  ansible.builtin.debug:
    msg:
      - "Data Guard Lag on {{ oracle_sid }} ({{ inventory_hostname }}):"
      - "Transport Lag: {{ transport_lag_raw }} ({{ transport_lag_minutes }} min) — {{ transport_lag_severity }}"
      - "Apply Lag:     {{ apply_lag_raw }} ({{ apply_lag_minutes }} min) — {{ apply_lag_severity }}"
roles/dg_check_standby/tasks/check_gaps.yml
---
# =====================================================================
# Check for Redo Log Archive Gaps on Standby
# A gap means the standby is MISSING redo log data — potential data loss
# This is the most critical Data Guard health check
# =====================================================================

- name: Query V$ARCHIVE_GAP for missing redo log sequences
  ansible.builtin.shell:
    cmd: >
      python3 /tmp/dg_query.py
      --host {{ ansible_host }}
      --port {{ oracle_port }}
      --sid {{ oracle_sid }}
      --user {{ oracle_monitor_user }}
      --password "{{ vault_oracle_monitor_pass }}"
      --query "SELECT THREAD#, LOW_SEQUENCE#, HIGH_SEQUENCE#,
                      (HIGH_SEQUENCE# - LOW_SEQUENCE# + 1) AS MISSING_COUNT
               FROM V\$ARCHIVE_GAP"
  register: gap_query_result
  changed_when: false
  no_log: true
  become: true
  become_user: "{{ oracle_user }}"
  environment: "{{ oracle_env }}"

- name: Parse archive gap results
  ansible.builtin.set_fact:
    archive_gaps: "{{ gap_query_result.stdout | from_json }}"

- name: Set gap health facts
  ansible.builtin.set_fact:
    has_archive_gaps: "{{ archive_gaps | length > 0 }}"
    total_missing_logs: >-
      {{ archive_gaps | map(attribute='missing_count') | map('int') | sum | default(0) }}

- name: Log archive gap check result
  ansible.builtin.debug:
    msg: >-
      Archive Gap Check on {{ oracle_sid }}:
      Gaps Found: {{ has_archive_gaps }}
      {% if has_archive_gaps %}
      ⚠️  MISSING LOG SEQUENCES:
      {% for gap in archive_gaps %}
      Thread {{ gap.thread }}: Sequence {{ gap.low_sequence }} to {{ gap.high_sequence }}
      ({{ gap.missing_count }} logs missing)
      {% endfor %}
      Total missing: {{ total_missing_logs }} archived redo logs
      {% else %}
      ✅ No archive gaps — standby has received all redo logs
      {% endif %}
roles/dg_check_standby/tasks/check_broker_standby.yml
---
# =====================================================================
# Check Oracle Data Guard Broker (DGMGRL) configuration health
# DG Broker provides centralized management and health status
# =====================================================================

- name: Run DGMGRL show configuration on standby
  ansible.builtin.shell:
    cmd: |
      echo "show configuration;" | \
      dgmgrl / "as sysdba" 2>/dev/null
      # dgmgrl / "as sysdba": connects using OS authentication (oracle user)
      # echo "show configuration;" | dgmgrl: pipe command to DGMGRL
      # DG Broker must be enabled for this to work
      # Shows status of ALL databases in DG configuration
  register: dgmgrl_config_output
  changed_when: false
  failed_when: false                                       # Don't fail if DGMGRL not configured
  become: true
  become_user: "{{ oracle_user }}"
  environment: "{{ oracle_env }}"

- name: Parse DGMGRL output for configuration health
  ansible.builtin.set_fact:
    dgmgrl_config_healthy: >-
      {{ 'SUCCESS' in dgmgrl_config_output.stdout
         and 'WARNING' not in dgmgrl_config_output.stdout
         and 'ERROR' not in dgmgrl_config_output.stdout }}
    dgmgrl_has_warning: "{{ 'WARNING' in dgmgrl_config_output.stdout }}"
    dgmgrl_has_error: "{{ 'ERROR' in dgmgrl_config_output.stdout }}"
    dgmgrl_not_configured: >-
      {{ dgmgrl_config_output.rc != 0
         or 'DGConnectIdentifier' not in dgmgrl_config_output.stdout }}

- name: Show DGMGRL detailed status for each database
  ansible.builtin.shell:
    cmd: |
      echo "show database verbose '{{ oracle_sid }}';" | \
      dgmgrl / "as sysdba" 2>/dev/null

---
# =====================================================================
# Pre-DR Drill Validation — Run BEFORE any planned switchover/failover
# Generates a readiness score — BLOCKS drill if any check fails
# =====================================================================
- name: Oracle Data Guard Pre-Drill Readiness Validation
  hosts: oracle_standby
  gather_facts: true

  vars_files:
    - "{{ inventory_dir }}/group_vars/all/vault.yml"

  tasks:
    - name: Upload query script
      ansible.builtin.copy:
        src: "{{ playbook_dir }}/../scripts/dg_query.py"
        dest: /tmp/dg_query.py
        mode: '0700'
        owner: "{{ oracle_user }}"

    - name: Run all standby checks
      ansible.builtin.include_role:
        name: dg_check_standby

    - name: Run all alerting
      ansible.builtin.include_role:
        name: dg_alert

    - name: Build pre-drill readiness report
      ansible.builtin.set_fact:
        predrill_checks:
          - name: MRP Running
            passed: "{{ mrp_is_healthy | bool }}"
            value: "{{ mrp_status }}"
            blocker: true
          - name: Zero Archive Gaps
            passed: "{{ not has_archive_gaps | bool }}"
            value: "{{ total_missing_logs }} missing logs"
            blocker: true
          - name: Transport Lag OK
            passed: "{{ transport_lag_severity == 'OK' }}"
            value: "{{ transport_lag_minutes }} minutes"
            blocker: false
          - name: Apply Lag OK
            passed: "{{ apply_lag_severity == 'OK' }}"
            value: "{{ apply_lag_minutes }} minutes"
            blocker: false
          - name: DG Broker Healthy
            passed: "{{ dgmgrl_config_healthy | bool }}"
            value: "{{ 'SUCCESS' if dgmgrl_config_healthy else 'WARNING/ERROR' }}"
            blocker: true

    - name: Identify blocking failures
      ansible.builtin.set_fact:
        blocking_failures: >-
          {{ predrill_checks
             | selectattr('blocker', 'equalto', true)
             | rejectattr('passed', 'equalto', true)
             | list }}

    - name: Display pre-drill readiness report
      ansible.builtin.debug:
        msg:
          - "════════════════════════════════════════════════════"
          - "  ORACLE DATA GUARD PRE-DRILL READINESS REPORT"
          - "  Database: {{ oracle_sid }} | {{ ansible_date_time.iso8601 }}"
          - "════════════════════════════════════════════════════"
          - "{% for check in predrill_checks %}"
          - "  {{ '✅' if check.passed else '❌' }} {{ check.name }}: {{ check.value }}{{ ' [BLOCKER]' if check.blocker and not check.passed else '' }}"
          - "{% endfor %}"
          - "════════════════════════════════════════════════════"
          - "  VERDICT: {{ '✅ READY FOR DR DRILL' if blocking_failures | length == 0 else '❌ DR DRILL BLOCKED — ' + blocking_failures | length | string + ' critical check(s) failed' }}"
          - "════════════════════════════════════════════════════"

    - name: Block DR drill if critical checks fail
      ansible.builtin.fail:
        msg: >-
          ❌ DR DRILL BLOCKED. The following critical checks FAILED:
          {% for f in blocking_failures %}
          • {{ f.name }}: {{ f.value }}
          {% endfor %}
          Resolve all blocking issues before attempting DR drill.
          A failed DR drill against a degraded standby can result in data loss.
      when: blocking_failures | length > 0

    - name: Remove query script
      ansible.builtin.file:
        path: /tmp/dg_query.py
        state: absent

1
Every 15 minutes: AAP scheduler fires. Play 1 runs on oracle_primary: queries V$DATABASE to confirm primary role, checks V$ARCHIVE_DEST_STATUS for transport to standby.
2
Play 2 runs on oracle_standby: dg_query.py connects to standby Oracle via cx_Oracle. V$MANAGED_STANDBY queried — MRP row checked. Status must be APPLYING_LOG or WAIT_FOR_LOG.
3
V$DATAGUARD_STATS queried for transport and apply lag. Oracle +DD HH:MI:SS interval format parsed to total minutes. transport_lag_minutes and apply_lag_minutes set as Ansible facts.
4
V$ARCHIVE_GAP queried. Any rows = IMMEDIATE P1 PagerDuty "ARCHIVE GAP DETECTED." This is the check that would have caught the 4-day gap in our story — every 15 minutes, not once a day.
5
DGMGRL show configuration run. Output parsed for SUCCESS/WARNING/ERROR states. DG Broker WARNING fires P2 PagerDuty — gives DBA time to investigate before it becomes a gap.
6
Pre-drill: DBA runs Oracle-DG-Pre-Drill-Check before quarterly drill. All 5 checks evaluated. If MRP not running OR archive gap exists → playbook fails with explicit message "DR DRILL BLOCKED." Drill cannot proceed. This is the technical gate that prevents a repeat of the incident.

🎯 14. Interview Preparation

Q: What is the difference between transport lag and apply lag in Oracle Data Guard?
Transport lag is how far behind the standby is in RECEIVING redo log data from the primary. If the primary has committed transactions up to SCN 1000, but the standby has only received redo up to SCN 950, the transport lag is the time equivalent of those 50 SCNs.

Apply lag is how far behind the standby is in APPLYING the received redo data. Even if the standby has received redo up to SCN 1000, MRP may have only applied up to SCN 980. Apply lag = 20 SCNs worth of time.

In banking, both must be monitored independently. Transport lag = network/archive issue. Apply lag = MRP performance issue. Both affect RPO but for different reasons.
Q: What does the pre-drill check blocking logic prevent?
The blocking logic prevents starting a DR drill against a degraded standby. The three blockers are:
1. MRP not running: Standby is not applying redo — could be hours or days behind. Failover would result in data loss equal to the unaplied lag.
2. Archive gaps: The standby is MISSING redo log files — specific transactions are permanently lost on the standby regardless of MRP state. Any failover will result in data loss for those gap sequences.
3. DG Broker ERROR: The broker has detected a configuration problem that may prevent successful switchover/failover execution.

Non-blocking warnings (transport lag < critical, apply lag < critical) allow the drill to proceed with awareness — they show on the report but don't stop the drill.
Q: How did you parse the Oracle lag interval format +DD HH:MI:SS in Ansible?
Oracle's V$DATAGUARD_STATS returns lag as an interval string like '+00 00:05:30' (zero days, zero hours, 5 minutes, 30 seconds). To convert to minutes for threshold comparison:

We use Jinja2's regex_replace filter with capture groups to extract days, hours, and minutes separately, then calculate: days × 1440 + hours × 60 + minutes.

The regex pattern \+([0-9]+) ([0-9]+):([0-9]+):([0-9]+) captures: group 1 = days, group 2 = hours, group 3 = minutes, group 4 = seconds. Each is converted to int and multiplied by the appropriate factor. This gives a total minutes value that can be compared against integer threshold variables.
Q: How would you automate the actual switchover command in Data Guard?
The switchover command itself (DGMGRL> switchover to CBSSTBY;) is a highly sensitive operation that should NOT be fully automated — it's a deliberate action that changes which database is primary. However, the pre-conditions and post-validation can be fully automated.

In practice: the pre-drill validation playbook ensures the system is ready, then an AAP Approval Node presents to the DBA: "Pre-flight passed. Run the DGMGRL switchover manually, then click Approve to trigger post-failover validation." The DBA executes the switchover via DGMGRL in their terminal, confirms it completed, then approves in AAP. The post-failover validation playbook runs automatically after approval — confirming roles are correct and new primary is accepting writes. This hybrid approach (automate the boring parts, keep human control on the critical command) is the industry standard in banking.
