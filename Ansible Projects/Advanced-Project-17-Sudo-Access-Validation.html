Project 17: Sudo Access Validation, sudoers Audit & Linux Privilege Compliance

In banking Linux servers, sudo is the gateway to root privileges. Every engineer who can run sudo su - can read any file, modify any config, and access any database on that server. Without continuous validation, sudo access accumulates over time — engineers move teams but keep their old sudo rules, developers get temporary sudo for debugging and it never gets removed, application service accounts get NOPASSWD sudo for restart scripts and nobody audits them. PCI-DSS Requirement 7 mandates least-privilege access. This project automates complete sudo access auditing across all 3,500 Linux servers — parsing sudoers files, validating against approved baselines, detecting NOPASSWD risks, running live sudo -l tests, and generating quarterly privilege review reports for the CISO.

🏦 1. The Banking Story

Setting: ABC Global Bank's 3,500 Linux servers have sudo access managed through a combination of /etc/sudoers, /etc/sudoers.d/ drop-in files, and LDAP-based sudo rules. The security policy allows sudo only for approved roles — Linux Admins (full sudo), DBA Team (only database-related commands), Application Team (only application restart commands). No developer should have sudo on production servers.

Incident 1 — The Developer with Root: A security audit found that developer Arun had arun ALL=(ALL) NOPASSWD: ALL in /etc/sudoers.d/dev-overrides on the CBS production server. This rule was added 14 months ago when Arun was debugging a memory issue and nobody removed it. Arun could run ANY command as root without even typing a password. When the auditor asked the security team, nobody knew the rule existed. PCI-DSS finding: "Unauthorized privileged access — developer has unrestricted root on CDE server."

Incident 2 — The Wildcard Disaster: The application team's restart rule was written as: appuser ALL=(root) NOPASSWD: /opt/app/bin/* The wildcard * matches ANY binary in /opt/app/bin/ — including bash, sh, or any script the attacker plants there. A malicious script placed at /opt/app/bin/evil.sh could be run as root. The security team didn't realize wildcards in sudo rules are a known escalation vector until a pen tester demonstrated it.

Incident 3 — The Missing visudo Validation: An engineer directly edited /etc/sudoers with vi instead of visudo. A syntax error slipped in: %dbateam ALL=(ALL NOPASSWD: /usr/bin/sqlplus — missing closing parenthesis. The next time any DBA tried to sudo, the entire sudo system on that server broke. ALL sudo stopped working — including the Linux admin team's emergency access. The server needed console access to fix it.

The Ask: "Audit every sudoers file and drop-in on every server weekly. Compare against the approved sudo rules list. Alert on NOPASSWD rules that aren't explicitly approved. Detect wildcard risks. Validate sudoers syntax using visudo. Generate a quarterly privilege review report for the CISO."

📚 2. Sudo Concepts — Theriyuma?

Sudo nu ketkaravudan, ellaarukkum theriyum — "super user do". Aana sudoers file-la irukka rules ellam therinja, nee oru thagaval security engineer aayiduva. Ippo oru by one paarkkalaam.
sudoers File Format — Line by Line

Every sudo rule follows this pattern — once you understand it, reading any sudoers file becomes easy:

WHO      WHERE=(AS_WHOM)   NOPASSWD:   WHAT
arun     ALL=   (root)               /usr/bin/systemctl restart tomcat
^user    ^host  ^run as    ^no pwd   ^allowed command

%dbateam ALL=   (oracle)   NOPASSWD: /usr/bin/sqlplus, /usr/bin/rman
^group(% prefix)           ^run as oracle user
FieldMeaningBanking Example
WHOUsername or %groupname (% = group)arun or %linux_admins
WHEREHostname or ALL (which servers this rule applies from)ALL = any server
AS_WHOMWhich user to run as (in parentheses)(root) or (oracle) or (ALL)
NOPASSWDSkip password prompt — risky if presentRemove if possible; require only where essential
WHATCommand(s) allowed — full path required/usr/bin/systemctl restart tomcat
Why NOPASSWD is Risky — Ithu Romba Dangerous
NOPASSWD rule iruntha, password type pannama root command run pannikkalaam. Enna aachu theriyuma? Attacker kitta user account kiledaichita — sudo kooda thevaiyilla. Directly root command run panniruvaan. Ithunaala PCI-DSS NOPASSWD-a romba restrict panniduthu.

Without NOPASSWD: attacker needs the user's password to escalate — an extra barrier.
With NOPASSWD: any script, cron job, or attacker with file-write access to a file executed by that user can run root commands silently — no interactive prompt, no audit trail of password entry.

Approved NOPASSWD exceptions in banking: application service accounts running specific restart commands (e.g., /usr/bin/systemctl restart tomcat) — but ONLY that exact command, no wildcards.

Wildcard Risk in sudo Rules — Kandippa Alert Pannanum
Wildcard (*) use panna, neenga nenaichathai vida adhigama allow aagidum. /opt/app/bin/* nu irundha, /opt/app/bin/bash kooda allow aagum. Ithu oru escalation vector — pen tester ellam idha first paapaan.

Risky patterns to detect:

  • /path/* — matches any file in that directory including bash, sh
  • /path/script.sh * — trailing * means any arguments, can be abused
  • ALL in the command position — means literally any command
  • /usr/bin/find * -exec — find with exec can run arbitrary commands
  • /usr/bin/vim * — vim can spawn a shell with :!bash
  • /usr/bin/python3 * — python can run arbitrary code

Role 1: sudo_file_audit — Find and Parse sudoers Files

Ippo namma first step — server-la irukka ellaa sudoers files-ayum kandupidikanum. /etc/sudoers mattum paaka kodam, /etc/sudoers.d/ folder-layum irukka ellaa files-ayum paakanum. Ithu taan Incident 1-la problem — dev-overrides file /etc/sudoers.d/-la hide aagirundhuchu, main file-la theriyalai.
roles/sudo_file_audit/tasks/find_sudoers_files.yml
---
# =====================================================================
# Find ALL sudoers files — main + drop-ins
# Ithu romba important: /etc/sudoers.d/ folder-layum hidden rules
# irukum. Ellaa files-ayum scan panna theriyum (Incident 1 explanation)
# =====================================================================

- name: Find main sudoers file and all drop-in files
  ansible.builtin.find:
    paths:
      - /etc                    # /etc/sudoers — this is the main sudoers file
      - /etc/sudoers.d          # /etc/sudoers.d/ — drop-in rules directory
                                # Engineers usually add their rules here
                                # Ellaarum idha mattum paakradhilla — that's the problem!
    patterns:
      - "sudoers"               # Match the main /etc/sudoers file
      - "*"                     # Match ALL files inside /etc/sudoers.d/
    file_type: file             # Only files, not directories
    recurse: false              # Don't go into sub-sub directories
  register: sudoers_files_found # Result: list of all found files with path, size, etc.
  become: true                  # Root needed to read /etc/sudoers (it's 0440 permissions)

- name: Log which sudoers files were found on this server
  ansible.builtin.debug:
    msg:
      - "Found {{ sudoers_files_found.files | length }} sudoers file(s) on {{ inventory_hostname }}"
      - "Files: {{ sudoers_files_found.files | map(attribute='path') | list | join(', ') }}"
      # Ithu helpful — engineer-ku ethana files irukku nu theriyum

- name: Read content of each sudoers file
  ansible.builtin.slurp:        # slurp module: reads file and returns base64 encoded content
                                # Regular copy or read would need temp files — slurp is cleaner
    src: "{{ item.path }}"      # item.path: each file path from the find result above
  register: sudoers_contents    # Result: list of file contents in base64
  loop: "{{ sudoers_files_found.files }}" # Loop through all found files
  loop_control:
    label: "Reading {{ item.path }}" # Show which file we're reading in output
  become: true                  # Root access needed to read these files

- name: Decode file contents and build flat list of all sudoers lines
  ansible.builtin.set_fact:
    all_sudoers_lines: >-
      {{ all_sudoers_lines | default([]) + [{
        'file': item.item.path,
        'lines': (item.content | b64decode).split('\n')
                 | reject('match', '^\\s*#.*')
                 | reject('match', '^\\s*$')
                 | list
      }] }}
      # b64decode: convert base64 back to text
      # .split('\n'): split into individual lines
      # reject('match', '^\\s*#.*'): remove comment lines (starting with #)
      # reject('match', '^\\s*$'): remove empty/blank lines
      # list: convert to list
      # Result: clean lines of actual sudo rules, no comments, no blanks
  loop: "{{ sudoers_contents.results }}"
  loop_control:
    label: "{{ item.item.path }}"
roles/sudo_file_audit/tasks/validate_syntax.yml
---
# =====================================================================
# Validate sudoers file syntax using visudo -c
# Ithu Incident 3-a prevent pannudhu — manual vi edit-la syntax error
# vanthudu, sudo-ve work aagalai. visudo -c check panniduvom.
# =====================================================================

- name: Run visudo -c syntax check on main sudoers file
  ansible.builtin.command:
    cmd: visudo -c -f /etc/sudoers
    # visudo -c: check mode — don't open editor, just validate syntax
    # -f /path: check a specific file (default is /etc/sudoers)
    # visudo is the ONLY correct way to validate sudoers — vi/nano can't detect errors
    # If syntax is OK: returns 0 with "/etc/sudoers: parsed OK"
    # If syntax is bad: returns non-zero with error description
  register: main_sudoers_syntax     # Save the result including return code and output
  changed_when: false               # This is a read-only check, not a change
  failed_when: false                # Don't fail the whole playbook — we'll handle the error
  become: true

- name: Run visudo -c on each drop-in file in /etc/sudoers.d/
  ansible.builtin.command:
    cmd: "visudo -c -f {{ item.path }}"
    # Same as above but for each drop-in file
    # Each file in /etc/sudoers.d/ is independently validated
  register: dropin_syntax_results   # List of results, one per drop-in file
  loop: >-
    {{ sudoers_files_found.files
       | rejectattr('path', 'equalto', '/etc/sudoers')
       | list }}
       # rejectattr: remove the main /etc/sudoers from the list
       # We want only the /etc/sudoers.d/* files here
  loop_control:
    label: "Checking syntax: {{ item.path }}"
  changed_when: false
  failed_when: false
  become: true

- name: Identify files with syntax errors
  ansible.builtin.set_fact:
    syntax_error_files: >-
      {{ syntax_error_files | default([]) + [{
        'file': item.item.path,
        'error': item.stderr | default(item.stdout)
      }] }}
      # rc != 0 means visudo found a syntax error in that file
      # We collect: which file has the error + what the error message says
  loop: "{{ dropin_syntax_results.results + [main_sudoers_syntax] }}"
  when: item.rc != 0              # Only add to list if there IS an error
  loop_control:
    label: "{{ item.item.path | default('/etc/sudoers') }}"

- name: Fire P1 PagerDuty for sudoers syntax errors
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "sudo-syntax-error-{{ inventory_hostname }}-{{ item.file | replace('/', '-') }}"
      payload:
        summary: >-
          🔴 SUDOERS SYNTAX ERROR on {{ inventory_hostname }}:
          File {{ item.file }} has a syntax error!
          sudo WILL BREAK for all users on this server if not fixed.
          This is how Incident 3 happened — direct vi edit caused a syntax error.
          Fix: visudo -f {{ item.file }}
        severity: critical         # P1 — syntax error means sudo can break on next sudo run
        source: ansible-sudo-audit
        custom_details:
          host: "{{ inventory_hostname }}"
          file: "{{ item.file }}"
          error_detail: "{{ item.error }}"
          fix_command: "visudo -f {{ item.file }}  # Use visudo, never vi directly!"
    status_code: [202]
  loop: "{{ syntax_error_files | default([]) }}"
  loop_control:
    label: "{{ item.file }}"
  delegate_to: localhost            # PagerDuty API call runs from AAP node, not target server
  when: syntax_error_files | default([]) | length > 0
roles/sudo_file_audit/tasks/parse_sudoers.yml
---
# =====================================================================
# Parse sudoers rules into structured data
# Ithu namma brain — raw text lines-a structured dict-a convert pannuvom
# Each rule: who, host, runas, nopasswd, commands — ellam extract pannuvom
# =====================================================================

- name: Parse each sudoers line into structured rule dictionary
  ansible.builtin.set_fact:
    parsed_sudo_rules: >-
      {{ parsed_sudo_rules | default([]) + [{
        'file': file_entry.file,
        'raw_line': line,
        'grantee': (line.split()[0] | default('')),
        'host': (line
                 | regex_search('^\\S+\\s+(\\S+)\\s*=', '\\1')
                 | first | default('UNKNOWN')),
        'runas': (line
                  | regex_search('\\(([^)]+)\\)', '\\1')
                  | first | default('root')),
        'nopasswd': ('NOPASSWD' in line),
        'commands': (line.split(':')[-1].strip()
                     if ':' in line
                     else line.split('=')[-1].strip()),
        'has_wildcard': ('*' in line),
        'has_all_commands': (line.split(':')[-1].strip() == 'ALL'
                             if ':' in line else False),
        'has_risky_command': (sudo_risky_commands
                              | map('lower')
                              | select('in', line | lower)
                              | list | length > 0)
      }] }}
      # Explanation of each extraction:
      #
      # grantee: first word on the line — the user or %group
      #   "arun ALL=(root) NOPASSWD: /usr/bin/vim" → "arun"
      #   "%dbateam ALL=(oracle) ..." → "%dbateam" (% prefix = group)
      #
      # host: the hostname field between user and =
      #   regex_search finds the word before the = sign
      #   Usually "ALL" meaning any host
      #
      # runas: the (user) in parentheses
      #   regex_search extracts what's inside ()
      #   "(root)" → "root", "(oracle)" → "oracle", "(ALL)" → "ALL"
      #
      # nopasswd: simple check — is "NOPASSWD" anywhere in the line?
      #   True → the user doesn't need to type password
      #   This is our key risk indicator
      #
      # commands: everything after the last colon
      #   "NOPASSWD: /usr/bin/sqlplus" → "/usr/bin/sqlplus"
      #   Multiple commands: "/usr/bin/sqlplus, /usr/bin/rman"
      #
      # has_wildcard: simple * check in the full line
      #   "/opt/app/bin/*" → True — DANGEROUS, log escalation vector
      #
      # has_all_commands: if the command field is literally "ALL"
      #   "(ALL) NOPASSWD: ALL" → has_all_commands=True — CRITICAL!
      #
      # has_risky_command: check if any known shell-escape command
      #   (vim, python, bash, find, etc.) appears in the line
  loop: >-
    {{ all_sudoers_lines
       | map(attribute='lines')
       | flatten
       | list }}
       # flatten: all_sudoers_lines has per-file lists, flatten makes one big list
       # We process every line from every file together
  loop_control:
    label: "Parsing line..."
  vars:
    file_entry: >-
      {{ all_sudoers_lines
         | selectattr('lines', 'contains', item)
         | first | default({'file': 'unknown'}) }}
         # Find which file this line came from — useful for reporting

🔍 9. Risk Classification Role

Ippo namma parsed rules ellam irukku. Enna risk irukku nu classify panna theriyum. Three levels: Critical (NOPASSWD: ALL — vandhe maatom), High (unapproved NOPASSWD — justify panna theriyuma?), Medium (wildcard or risky commands).
roles/sudo_risk_classifier/tasks/detect_nopasswd.yml
---
# =====================================================================
# NOPASSWD Detection and Classification
# Namba ellaa NOPASSWD rules-ayum collect pannuvom
# Then approved list-oda compare pannuvom
# Approve aagaadha NOPASSWD = automatic alert
# =====================================================================

- name: Extract all NOPASSWD rules from parsed sudo rules
  ansible.builtin.set_fact:
    all_nopasswd_rules: >-
      {{ parsed_sudo_rules | default([])
         | selectattr('nopasswd', 'equalto', true)
         | list }}
         # selectattr: filter only items where nopasswd = true
         # Ithu namma NOPASSWD rules list

- name: Separate approved vs unapproved NOPASSWD rules
  ansible.builtin.set_fact:
    approved_nopasswd_rules: >-
      {{ all_nopasswd_rules
         | selectattr('grantee', 'in', approved_nopasswd_grantees)
         | list }}
         # approved_nopasswd_grantees: from group_vars — list of approved users/groups
         # %dbateam, appuser, ansible — ithu mattum approved

    unapproved_nopasswd_rules: >-
      {{ all_nopasswd_rules
         | rejectattr('grantee', 'in', approved_nopasswd_grantees)
         | list }}
         # rejectattr: REMOVE the approved ones
         # Remaining = unapproved = alert vennum

- name: Identify CRITICAL rules — NOPASSWD: ALL (complete root bypass)
  ansible.builtin.set_fact:
    critical_rules: >-
      {{ parsed_sudo_rules | default([])
         | selectattr('nopasswd', 'equalto', true)
         | selectattr('has_all_commands', 'equalto', true)
         | list }}
         # Both nopasswd=true AND commands=ALL → maximum risk
         # "arun ALL=(ALL) NOPASSWD: ALL" → ithu taan Incident 1!
         # Ithu irundha, kandippa P1 alert

- name: Fire CRITICAL P1 PagerDuty — user has NOPASSWD ALL (unrestricted root)
  ansible.builtin.uri:

File parse pannavudu nalla irukku — aaana LDAP-based sudo rules irundha, file-la theriyaathu. Adhunaala sudo -l command run pannuvom — ithu "what can this user ACTUALLY do right now" nu sollum. File-based rules + LDAP rules — rendu-um ithu-la reflect aagum.

# =====================================================================
# Run sudo -l for each monitored user to get their ACTUAL privileges
# File audit-la LDAP rules theriyaathu — sudo -l-la ellam theriyum
# Ithu "live" test — current effective permissions exactly what it is
# =====================================================================

- name: Run sudo -l for each monitored user to list their privileges
  ansible.builtin.command:
    cmd: "sudo -l -U {{ item }}"
    # sudo -l: list allowed (and forbidden) commands for a user
    # -U username: check for a SPECIFIC user (only root can use -U)
    # Output shows:
    #   User arun may run the following commands on server01:
    #       (root) NOPASSWD: /usr/bin/vim  ← risky!
    #       (oracle) /usr/bin/sqlplus       ← password required, ok
    # Note: This runs as root (become: true) checking another user
  register: sudo_l_results         # Save the result for each user
  loop: "{{ sudo_monitored_users }}" # Loop through our monitored users list
  loop_control:
    label: "sudo -l for user: {{ item }}"
  changed_when: false              # Read-only check, nothing changes
  failed_when: false               # User might not exist on this server — don't fail
  become: true                     # Root needed to run sudo -l for another user

- name: Parse sudo -l output into structured privilege list
  ansible.builtin.set_fact:
    live_sudo_privileges: >-
      {{ live_sudo_privileges | default([]) + [{
        'user': item.item,
        'host': inventory_hostname,
        'output': item.stdout,
        'user_exists': (item.rc == 0),
        'can_sudo': ('may run the following' in item.stdout),
        'has_nopasswd_live': ('NOPASSWD' in item.stdout),
        'has_all_commands_live': (item.stdout | regex_search('NOPASSWD: ALL') is not none),
        'privilege_lines': (item.stdout_lines
                            | select('match', '.*\\(.*\\).*')
                            | list),
        'command_count': (item.stdout_lines
                          | select('match', '.*\\(.*\\).*')
                          | list | length)
      }] }}
      # user_exists: rc=0 means sudo -l ran successfully — user exists
      # can_sudo: output says "may run the following" — has at least one allowed command
      # has_nopasswd_live: NOPASSWD appears in actual runtime output
      #   Even if file says no NOPASSWD, LDAP might grant it — ithu live check catches it
      # has_all_commands_live: "NOPASSWD: ALL" in live output → critical!
      # privilege_lines: the actual command lines (they contain parentheses in output)
      # command_count: how many commands can this user run?
  loop: "{{ sudo_l_results.results }}"
  loop_control:
    label: "{{ item.item }}"

- name: Log live sudo privilege summary per user
  ansible.builtin.debug:
    msg:
      - "Live sudo privileges on {{ inventory_hostname }}:"

             parsed_sudo_rules | default([])
             | selectattr('nopasswd', 'equalto', true)
             | map(attribute='grantee')
             | list)
         | list }}
         # If user has NOPASSWD in live sudo -l output
         # BUT that user is NOT in our file-based NOPASSWD rules
         # → the NOPASSWD must be coming from LDAP!
         # Ithu detect panna romba difficult — ithunaala sudo -l important

- name: Alert on LDAP-granted NOPASSWD not visible in sudoers files

      failed_when: false         # grep returns 1 if no match found — that's OK

      ansible.builtin.uri:
        url: "{{ slack_webhook_url }}"
        method: POST
        body_format: json
        body:
          text: >-
            ⚠️ *Daily NOPASSWD Scan Alert — {{ inventory_hostname }}*
            NOPASSWD sudo rules found:
            ```
            {{ nopasswd_grep_result.stdout }}
            ```
            Verify these are in the approved exceptions list.
            If not recognized, treat as security incident.
        status_code: [200]
      delegate_to: localhost
      when:
        - nopasswd_grep_result.stdout | length > 0
        # Only alert if there ARE NOPASSWD rules
        - nopasswd_grep_result.stdout_lines
          | reject('search',
              approved_nopasswd_grantees | join('|'))
          | list | length > 0
          # AND at least one line does NOT contain an approved grantee name
          # approved_nopasswd_grantees: ["%dbateam", "appuser", "ansible"]

🎯 15. Interview Prep — Theriyuma? Seri, Paarkkalaam!

Q: Why is a wildcard (*) in a sudo rule a security risk?
Ithu interview-la romba common question. Simple ah sollanum na: wildcard use panna, neenga nenaichathai vida adhigama allow aagum. Ithu GTFOBins concept — theriyum, right?

When you write /opt/app/bin/*, sudo allows execution of ANY binary in that directory — including bash, sh, or any script placed there. An attacker with write access to /opt/app/bin/ can place a malicious script and run it as root.

Trailing argument wildcards are equally dangerous: /usr/bin/find * -exec allows -exec bash ; as arguments, which spawns a root shell. Always use full, explicit command paths with no wildcards in production sudo rules.

Q: What is the difference between sudo -l and parsing sudoers files directly?
Rendu approach-um use pannuvom — enna difference theriyuma?

Parsing sudoers files: reads the actual config files (/etc/sudoers, /etc/sudoers.d/*). Fast, no authentication needed beyond file read. But it MISSES LDAP/SSSD-based sudo rules — many enterprises push sudo rules via LDAP (sudoRule objectClass) instead of local files.

sudo -l: asks the running sudo system what a user can actually do right now — combining local file rules AND LDAP rules AND any other NSS sources. This is the ground truth. But it requires running as root (-U flag) and is slower per user.

Best practice: do both. File parse = fast inventory of local rules. sudo -l = verification of effective permissions including LDAP grants.

Q: How does visudo prevent sudoers syntax errors?
visudo enna special nu theriyuma? Direct vi-la edit panna enna aachu nu theriyuma? Incident 3-a explain panna, ithu taan best example.

visudo: opens a temp copy of sudoers for editing. When you save and exit, it runs a syntax check before replacing the live file. If syntax is bad — it refuses to save and shows you the error. The live sudoers file is never touched until the new version is verified correct.

Direct vi edit: you're editing the live file directly. A typo saved immediately corrupts the active sudoers. The next sudo command reads the broken file and can fail with "sudo: parse error" — breaking ALL sudo access on the server, including the admin team's emergency access. Console access is then required to fix it.

Our automation uses visudo -c -f filename (check-only mode, no editing) to detect existing syntax errors without modifying anything.

Q: How do you prevent the approved_baselines from becoming stale?
Baseline file update pannama vittutu, namma audit always "OK" kaatum — ithu false sense of security. Adhunaala Git workflow very important.

Three controls keep the baseline current:

1. Git-controlled baseline: Any change to approved_baselines/ requires a pull request, reviewed by the security team and approved by the CISO. Git history shows who approved what and when — full audit trail.

2. Drift detection: The audit compares BOTH directions — rules in sudoers that aren't in baseline (unauthorized additions) AND rules in baseline that aren't in sudoers (did someone remove an expected rule?). Both directions matter.

3. Quarterly revalidation: The CISO report requires sign-off every quarter confirming that the approved baseline still reflects current business needs. Old baselines must be reviewed and re-approved — prevents accumulation of outdated approvals.
