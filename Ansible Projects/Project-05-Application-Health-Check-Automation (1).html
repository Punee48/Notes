Project 5: Application Health Check Automation using Red Hat AAP

SecureBank's production ecosystem consists of 14 banking applications spanning the core banking system (CBS), payment gateway, SWIFT interface, mobile banking API, internet banking portal, RTGS/NEFT processors, FASTag integration, NACH (National Automated Clearing House), fraud detection engine, trade finance platform, treasury management system, loan origination system, digital onboarding portal, and the regulatory reporting engine. Every one of these must be verified as healthy after every deployment, every infrastructure change, every failover event, and on a scheduled basis every 5 minutes — producing a unified health dashboard consumed by the NOC, the application teams, and the RBI IT Framework–mandated incident reporting system. This project automates multi-layer health checks (infrastructure → application → business-logic → integration → database) across the entire fleet, replacing manual NOC verification calls with a single, structured, evidence-generating Ansible pipeline.

📋 1. Business Requirement

SecureBank's SLA with its corporate clients guarantees 99.95% availability for transaction processing — equating to a maximum of 26 minutes of downtime per month. The NOC (Network Operations Centre) operates 24×7 with a P1 MTTA (Mean Time to Acknowledge) SLA of 5 minutes. The RBI IT Framework §6.1 mandates that the bank maintain real-time visibility into the availability and performance of all critical technology systems.

Current health checks are fragmented: Nagios monitors some servers, Dynatrace APM covers some Java apps, a shell script on a cron job checks three endpoints, and the NOC manually dials the on-call engineer for anything else. There is no single, authoritative "is the bank healthy right now?" answer — the NOC pieced it together from five different dashboards during incidents. The requirement is a unified, structured health-check pipeline that assesses all 14 applications across 5 check layers, produces a single health status JSON consumed by Grafana, and raises alerts through PagerDuty with enough diagnostic context that the first responder can identify the failure layer (infra? app? DB? integration?) without making any additional calls or SSH sessions.

🏦 2. Real-Time Banking Scenario

The Story: It's a Monday morning at 9:47 AM. SecureBank's NACH (National Automated Clearing House) batch processor has silently entered a degraded state — the Java process is running, Nagios shows the host as "UP", but the NACH queue has been stalled for 22 minutes because the Oracle connection pool is exhausted. 60,000 ECS debit mandates are queued but not processing. The NOC hasn't noticed because their dashboard only shows the OS-level "ping" status — everything looks green. The first signal is an angry call from the NACH reconciliation team at 10:09 AM — 22 minutes after the stall began. By the time the root cause is identified (a runaway batch thread leaked all 50 DB connections), it's 10:31 AM — 44 minutes of NACH processing delay, requiring a manual RBI notification under the Cyber Security and Resilience Framework. Now, with the health check automation in place, Ansible's business-logic check — which validates that the NACH queue depth hasn't exceeded 1,000 records for more than 2 minutes — would have triggered a P2 PagerDuty alert at 9:49 AM, two minutes into the stall, long before any customer SLA was breached. The alert includes the queue depth, the DB connection pool utilization, and the last 10 error lines from the NACH log — everything the on-call engineer needs to act immediately without making a single SSH session.

❗ 3. Problem Statement

  • Health monitoring is fragmented across Nagios (infra ping), Dynatrace APM (some Java apps), manual cron scripts, and human observation — no single pane of glass.
  • Existing checks are infrastructure-layer only (ping, port, process running) — they cannot detect application-level degradation (slow DB queries, full queues, hung thread pools, failing business logic).
  • No synthetic transaction checks — a credit card authorization endpoint that returns HTTP 200 but produces incorrect authorization codes passes infrastructure monitoring but breaks the business.
  • No integration health checks — the CBS may be healthy but its downstream SWIFT gateway connection may be down, causing international transactions to silently fail.
  • Alert context is poor — PagerDuty fires "Host down" with an IP address; the on-call engineer spends the first 10 minutes of MTTA just figuring out what application and which layer failed.
  • No post-deployment health gate — after a release (Project 1), the release manager has no structured way to confirm all 14 application layers are healthy before declaring the release successful.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. NOC engineer checks Nagios for host availability (ping/port) — green/red per host.
  2. For app-level issues, engineer SSHs into the server and manually checks: ps aux | grep java, tail -200 /opt/app/logs/app.log | grep ERROR, curl -k https://localhost:8443/health.
  3. For DB connectivity, engineer runs a manual DB login: sqlplus user/pass@tns_alias <<< "select 1 from dual;".
  4. For integration health (SWIFT connectivity, payment gateway status), engineer calls the integration team on a phone bridge — there is no automated check.
  5. Post-deployment verification: release manager verbally confirms with 3–4 application team members over a conference call — no structured checklist, no documented evidence.
  6. RBI incident reporting: compliance team manually compiles a Word document describing the incident timeline, application affected, and customer impact — sourced from log screenshots, chat messages, and memory.

🔍 6. Health Check Catalogue (5 Layers × 14 Applications)

Each application is checked across 5 layers. Not every layer applies to every app — the inventory declares which checks to run per application:

Layer 1 — Infrastructure
Host Reachable (ping/TCP) CPU < 85% Memory < 90% Disk < 85% Load Average < (CPU×2)
Layer 2 — Process / Service
Systemd service active Process count expected JVM heap < 80% Thread pool not exhausted No zombie processes
Layer 3 — Application API
HTTP /health endpoint → 200 Response time < threshold SSL cert valid Version matches expected Error rate < 0.1%
Layer 4 — Business Logic
Synthetic test transaction Queue depth within limit Batch job running on schedule Settlement file generated Balance enquiry returns valid
Layer 5 — Integration / Downstream
SWIFT connectivity Payment gateway reachable Oracle DB pool stats Redis cache hit rate MQ broker connection

🛠️ 7. Automated Solution Design

  • Check execution: A single Ansible playbook loops over all 14 application definitions from the inventory. Each application declares which checks to run and what thresholds to use as host/group variables. Roles map to check layers — modular, independently testable.
  • Parallel execution: All 14 applications are checked in parallel (no serial batching needed for read-only health checks) using Ansible's default fork-based parallelism.
  • Threshold logic: Every check produces a status: UP, DEGRADED, or DOWN. Each threshold is a variable (not hardcoded) so each application team can tune their own SLAs without changing playbook code.
  • Synthetic transactions: For business-critical apps (CBS, Payment Gateway, NACH), Ansible runs a read-only synthetic test transaction against a dedicated test account/endpoint — confirming end-to-end business logic, not just infrastructure availability.
  • Rich alert context: When a check fails, the alert payload includes the failing layer, specific check name, actual vs threshold value, the last 20 lines of the application error log, and the AAP job URL — everything the on-call engineer needs in the first minute.
  • Unified health JSON output: All 14 applications' check results are aggregated into a single structured JSON file, pushed to a Prometheus Pushgateway or NFS path, and consumed by Grafana for the NOC dashboard.
  • AAP scheduling: Runs every 5 minutes as a scheduled job. Also triggered as the final stage of every deployment workflow (Project 1), patch workflow (Project 2), and certificate renewal workflow (Project 4) to confirm post-change health.

⚙️ 9. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.builtin.uri, ansible.builtin.command, ansible.builtin.shell, ansible.builtin.systemd, ansible.builtin.wait_for, ansible.builtin.setup (subset)
  • Roles: health_infra, health_process, health_app_api, health_business, health_integration, health_aggregator, health_alert
  • Custom facts: per-application health status collected as structured host facts, aggregated via hostvars
  • gather_subset: ['hardware', 'virtual', 'network'] for targeted fact collection (faster than full gather_facts)
  • Jinja2 templates: unified health JSON, PagerDuty alert payload, Slack rich message blocks
  • ignore_errors: true + explicit status tracking — health checks NEVER abort mid-run; every check runs to completion regardless of individual failures

Red Hat AAP Components

  • Execution Environment: EE with Prometheus client library (push metrics to Pushgateway)
  • Inventory: Application inventory with per-app health check configuration as host_vars
  • Credentials: Machine (SSH for local checks on app servers), Vault (DB passwords for pool stats, API keys for payment gateway health endpoint)
  • Job Template: Health-Check-All-Apps (no survey — always checks everything)
  • Schedule: Every 5 minutes (AAP supports cron-style schedules)
  • Callback Plugin: Custom callback that pushes AAP job results to Prometheus Pushgateway
  • Notification: Slack (#noc-alerts) + PagerDuty webhook on DEGRADED/DOWN detection
  • RBAC: All teams have read access to job output; only Platform team can modify the Job Template

📂 10. Inventory Structure

The health check inventory is application-centric, not server-centric. Each "host" in the inventory represents a logical application (not a physical server), with its own health check configuration. Checks that need to run on the server (process checks, log checks) use delegate_to to reach the actual server; checks that validate from the outside (API endpoint, TLS handshake) run from the control node.

💻 12. Complete Project Code (Line-by-Line Explained)

Role: health_infra — Layer 1 Infrastructure Checks

roles/health_infra/tasks/main.yml
---
- name: Skip infrastructure checks if not enabled for this application
  ansible.builtin.meta: end_host
  when: not (checks.infra | default(true) | bool)

- name: Gather targeted system facts (hardware subset only — faster than full gather)
  ansible.builtin.setup:
    gather_subset:
      - hardware
      - virtual
  delegate_to: "{{ ansible_host }}"

- name: Check CPU utilization on application server
  ansible.builtin.shell: >
    top -bn1 | grep "Cpu(s)" | awk '{print $2}' | cut -d'%' -f1
  register: cpu_usage
  changed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Check memory utilization
  ansible.builtin.shell: >
    free | awk '/^Mem:/{printf "%.0f", $3/$2 * 100}'
  register: mem_usage
  changed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Check disk utilization on root filesystem
  ansible.builtin.shell: >
    df / --output=pcent | tail -1 | tr -dc '0-9'
  register: disk_usage
  changed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Get current load average (1-minute)
  ansible.builtin.shell: >
    cat /proc/loadavg | awk '{print $1}'
  register: load_avg
  changed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Evaluate infrastructure health thresholds and set layer status
  ansible.builtin.set_fact:
    infra_status: >-
      {{
        'DOWN' if (ansible_facts.get('ansible_processor_vcpus', 1) | int == 0)
        else 'DEGRADED' if (
          cpu_usage.stdout | float > cpu_threshold_pct or
          mem_usage.stdout | int > memory_threshold_pct or
          disk_usage.stdout | int > disk_threshold_pct or
          load_avg.stdout | float > (ansible_facts.get('ansible_processor_vcpus', 2) | int * load_avg_multiplier)
        )
        else 'UP'
      }}
    infra_details:
      cpu_pct: "{{ cpu_usage.stdout | float | round(1) }}"
      mem_pct: "{{ mem_usage.stdout | int }}"
      disk_pct: "{{ disk_usage.stdout | int }}"
      load_avg_1m: "{{ load_avg.stdout | float | round(2) }}"
      cpu_threshold: "{{ cpu_threshold_pct }}"
      mem_threshold: "{{ memory_threshold_pct }}"
      disk_threshold: "{{ disk_threshold_pct }}"
Line-by-Line Explanation
gather_subset: ['hardware', 'virtual'] — Full gather_facts on 14 application servers costs 2–5 seconds per host (network round-trips for all fact modules). Limiting to hardware and virtual subsets gives us CPU count and memory info without collecting network interfaces, mounts, services, etc. — cutting fact collection time by ~60% while still giving us what the health check needs.
delegate_to: "{{ ansible_host }}" — Since the inventory is application-centric (not server-centric), the Ansible "host" is a logical app definition. We use delegate_to to reach the actual server IP defined in ansible_host. This pattern lets us keep application-level metadata in the inventory while still running SSH commands on the real servers.
top -bn1 | grep "Cpu(s)" | awk '{print $2}' — A non-blocking, single-run top invocation (-b = batch mode, -n1 = one iteration only). Alternative: vmstat 1 2 | tail -1 | awk '{print 100-$15}' — more accurate (averages over 1 second) but adds a 1-second delay per host. For a 5-minute health check cycle, either is acceptable; for near-real-time monitoring, vmstat is preferred.
Complex set_fact with nested ternary — The Jinja2 ternary chain 'DOWN' if ... else 'DEGRADED' if ... else 'UP' evaluates all threshold conditions in a single expression, producing a clean status string. This is more readable than nested when conditions across multiple set_fact tasks, and produces a single atomic status assignment.
infra_details dict alongside infra_status — We always capture the actual metric values even when status is UP. This means the PagerDuty alert on a DEGRADED/DOWN status includes "CPU: 94%, threshold: 85%" as the alert body — the on-call engineer knows the exact magnitude of the breach immediately.

Role: health_process — Layer 2 Process & JVM Checks

roles/health_process/tasks/main.yml
---
- name: Skip process checks if not enabled for this application
  ansible.builtin.meta: end_host
  when: not (checks.process | default(true) | bool)

- name: Check systemd service is in active (running) state
  ansible.builtin.command: "systemctl is-active {{ service_name }}"
  register: service_status
  changed_when: false
  failed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Verify expected process pattern is present in process table
  ansible.builtin.shell: "pgrep -c -f {{ process_pattern }}"
  register: process_count
  changed_when: false
  failed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Check for zombie processes belonging to this application
  ansible.builtin.shell: >
    ps aux | awk '$8=="Z" && /{{ process_pattern }}/ {count++} END{print count+0}'
  register: zombie_count
  changed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Get JVM heap usage via JMX (if Java application)
  ansible.builtin.shell: >
    JVM_PID=$(pgrep -f {{ process_pattern }} | head -1);
    jcmd $JVM_PID VM.native_memory summary 2>/dev/null |
    grep -oP 'used=\K[0-9]+' | head -1 || echo "0"
  register: jvm_heap_used
  changed_when: false
  failed_when: false
  delegate_to: "{{ ansible_host }}"
  when: "'tomcat' in service_name or 'java' in process_pattern"

- name: Retrieve last N lines of application error log for context
  ansible.builtin.shell: >
    tail -{{ log_tail_lines }} {{ log_path }} | grep -i "ERROR\|FATAL\|Exception" || true
  register: recent_errors
  changed_when: false
  failed_when: false
  delegate_to: "{{ ansible_host }}"

- name: Evaluate process health and set layer status
  ansible.builtin.set_fact:
    process_status: >-
      {{
        'DOWN'     if service_status.stdout != 'active' or process_count.stdout | int == 0
        else 'DEGRADED' if zombie_count.stdout | int > 0
        else 'UP'
      }}
    process_details:
      service_active: "{{ service_status.stdout }}"
      process_count: "{{ process_count.stdout | int }}"
      zombie_count: "{{ zombie_count.stdout | int }}"
      recent_errors: "{{ recent_errors.stdout_lines | default([]) }}"
      jvm_heap_used_kb: "{{ jvm_heap_used.stdout | default('N/A') }}"
Line-by-Line Explanation
systemctl is-active vs pgrep -c -f — We check both the systemd unit status AND the actual process existence separately. A service can be in activating state (systemd thinks it's running, but the process hasn't fully started) or active while the actual Java process has died but systemd hasn't yet detected it (within the StartLimitBurst window). Both checks together give a definitive process status.
pgrep -c (count mode) + failed_when: false — pgrep returns exit code 1 when no matching processes are found — we suppress this as a task failure and instead read stdout as a count. Zero means the process is completely absent.
ps aux | awk '$8=="Z"' — Column 8 of ps aux output is the process state field; Z = zombie. Zombie processes with matching names indicate child processes of our Java app that have exited but whose parent hasn't called wait() to collect their exit status — a memory/PID table leak that worsens over time and can eventually exhaust PIDs.
tail -{{ log_tail_lines }} | grep -i "ERROR\|FATAL" — Capturing recent error lines alongside the health status transforms the alert from "the process check failed" into "the process check failed AND these are the last 5 error lines: NullPointerException in TransactionService.java:247" — dramatically reducing MTTA by giving the on-call engineer immediate diagnostic context.
|| true at the end of the grep — If there are no matching error lines (healthy app), grep returns exit code 1, which would mark the task as failed without the || true override. This is an alternative to failed_when: false that works within a pipeline chain.

Role: health_app_api — Layer 3 Application API Checks

roles/health_app_api/tasks/main.yml
---
- name: Skip API checks if not enabled for this application
  ansible.builtin.meta: end_host
  when: not (checks.app_api | default(true) | bool)

- name: Check application health endpoint with response-time measurement
  ansible.builtin.uri:
    url: "https://{{ app_fqdn }}:{{ app_port }}{{ health_endpoint }}"
    method: GET
    status_code: 200
    validate_certs: true
    timeout: "{{ http_check_timeout }}"
    return_content: true
  register: health_api_result
  delegate_to: localhost
  failed_when: false
  ignore_errors: true

- name: Verify application version matches expected release
  ansible.builtin.uri:
    url: "https://{{ app_fqdn }}:{{ app_port }}{{ version_endpoint | default('/version') }}"
    method: GET
    return_content: true
    validate_certs: true
    timeout: "{{ http_check_timeout }}"
  register: version_check
  delegate_to: localhost
  failed_when: false
  when: version_endpoint is defined

- name: Evaluate API health and response time
  ansible.builtin.set_fact:
    api_status: >-
      {{
        'DOWN'     if health_api_result.status | default(-1) != 200
        else 'DEGRADED' if health_api_result.elapsed | default(9999) * 1000 > (response_time_threshold_ms | default(2000))
        else 'UP'
      }}
    api_details:
      http_status: "{{ health_api_result.status | default('UNREACHABLE') }}"
      response_time_ms: "{{ (health_api_result.elapsed | default(0)) * 1000 | round(0) | int }}"
      response_time_threshold_ms: "{{ response_time_threshold_ms | default(2000) }}"
      health_response_body: "{{ health_api_result.content | default('') | truncate(500) }}"
      deployed_version: "{{ version_check.content | default('UNKNOWN') | truncate(100) }}"
      expected_version: "{{ expected_version | default('N/A') }}"
      version_match: "{{ expected_version | default('') in (version_check.content | default('')) }}"
Line-by-Line Explanation
delegate_to: localhost on API checks — Application health endpoints are checked from the Ansible control node (EE container), simulating a real external client call. Checking from the server itself would succeed even if the network path from clients to the app is broken (e.g., firewall rule change, load balancer issue) — defeating the purpose of the check.
health_api_result.elapsed — The uri module automatically records the elapsed time of the HTTP request in seconds as a float (e.g., 1.847). Multiplying by 1000 converts to milliseconds for comparison against the per-app response_time_threshold_ms variable. This gives us a built-in response-time health check without any additional tooling.
failed_when: false on URI tasks — This is the most critical pattern in the entire health check project: health checks MUST NEVER fail the Ansible play. If a URI check fails with an exception (timeout, connection refused), we capture it in the register variable and handle it in the set_fact evaluation — the play continues checking all other applications regardless.
| truncate(500) on response body — Health endpoint responses can contain large JSON bodies; truncating to 500 chars prevents the health report JSON from ballooning to megabytes when aggregating 14 applications' full responses.
expected_version | default('') in (version_check.content | default('')) — Checks that the expected version string (from the inventory, updated as part of each deployment) appears somewhere in the version endpoint response — a simple but effective deployment verification that confirms the right version is actually running, not a stale deployment.

Role: health_business — Layer 4 Business Logic Checks

roles/health_business/tasks/main.yml
---
- name: Skip business checks if not enabled for this application
  ansible.builtin.meta: end_host
  when: not (checks.business | default(false) | bool)

- name: Run synthetic test transaction (read-only)
  ansible.builtin.uri:
    url: "https://{{ app_fqdn }}:{{ app_port }}{{ business_checks.synthetic_txn_url }}"
    method: GET
    status_code: 200
    return_content: true
    validate_certs: true
    timeout: "{{ http_check_timeout }}"
    headers:
      X-Health-Check: "ansible-synthetic"
      X-Request-ID: "hc-{{ ansible_date_time.epoch }}"
  register: synthetic_txn_result
  delegate_to: localhost
  failed_when: false
  when: business_checks.synthetic_txn_url is defined

- name: Verify synthetic transaction response contains expected field value
  ansible.builtin.set_fact:
    synthetic_txn_valid: >-
      {{
        (synthetic_txn_result.json is defined) and
        (business_checks.expected_txn_response_field is not defined or
         synthetic_txn_result.json.get(business_checks.expected_txn_response_field, '') ==
         business_checks.expected_txn_response_value | default(''))
      }}
  when: business_checks.synthetic_txn_url is defined

- name: Check queue depth via API (for batch processors like NACH)
  ansible.builtin.uri:
    url: "https://{{ app_fqdn }}:{{ app_port }}{{ business_checks.queue_depth_api }}"
    method: GET
    return_content: true
    validate_certs: true
  register: queue_depth_result
  delegate_to: localhost
  failed_when: false
  when: business_checks.queue_check | default(false) | bool

- name: Extract queue depth value from API response
  ansible.builtin.set_fact:
    current_queue_depth: "{{ queue_depth_result.json.depth | default(0) | int }}"
  when: business_checks.queue_check | default(false) | bool

- name: Evaluate business-layer health status
  ansible.builtin.set_fact:
    business_status: >-
      {{
        'DOWN' if (business_checks.synthetic_txn_url is defined and not synthetic_txn_valid | default(true))
        else 'DOWN' if (business_checks.queue_check | default(false) and
                        current_queue_depth | default(0) | int > business_checks.queue_depth_threshold | default(9999) | int)
        else 'UP'
      }}
    business_details:
      synthetic_txn_status: "{{ 'PASS' if synthetic_txn_valid | default(true) else 'FAIL' }}"
      synthetic_txn_response_ms: "{{ (synthetic_txn_result.elapsed | default(0)) * 1000 | round(0) | int }}"
      queue_depth: "{{ current_queue_depth | default('N/A') }}"
      queue_threshold: "{{ business_checks.queue_depth_threshold | default('N/A') }}"
Line-by-Line Explanation
X-Health-Check: "ansible-synthetic" header — Sending a custom HTTP header on synthetic transactions allows the application (if configured to recognize it) to route synthetic traffic to a test code path rather than real business logic, preventing test data from contaminating production transaction logs. Also allows the app to skip certain expensive operations (e.g., external fraud scoring) for synthetic check calls.
X-Request-ID: "hc-{{ ansible_date_time.epoch }}" — A unique, timestamp-based request ID per health check run. This header is typically logged by the application, allowing you to find the exact synthetic transaction in application logs during troubleshooting — even if the health check itself returned a valid response but something looked wrong.
synthetic_txn_result.json.get(field, '') — For the Payment Gateway, we don't just check HTTP 200 — we validate that the JSON response contains "status": "APPROVED". A gateway that returns 200 with "status": "DECLINED" (all transactions being declined) passes infrastructure monitoring but is completely broken from a business perspective. This is the "business logic" in the business-layer check.
NACH queue depth check — The scenario from our story: queue_depth_api returns JSON with a depth field. If depth exceeds 1,000 (the queue_depth_threshold), the application is flagged DOWN. This single check would have detected the NACH stall within 2 minutes, before any customer SLA was breached.

Role: health_integration — Layer 5 Downstream Integration Checks

roles/health_integration/tasks/main.yml
---
- name: Skip integration checks if not enabled for this application
  ansible.builtin.meta: end_host
  when: not (checks.integration | default(false) | bool)

- name: Check TCP reachability of each downstream dependency
  ansible.builtin.wait_for:
    host: "{{ item.host }}"
    port: "{{ item.port }}"
    timeout: "{{ port_check_timeout }}"
    state: started
  loop: "{{ integration_checks.downstream_hosts | default([]) }}"
  loop_control:
    label: "{{ item.name }}"
  register: downstream_checks
  delegate_to: localhost
  failed_when: false
  ignore_errors: true

- name: Check DB connection pool health via app admin endpoint
  ansible.builtin.uri:
    url: "https://{{ app_fqdn }}:{{ app_port }}{{ integration_checks.db_pool_url }}"
    method: GET
    return_content: true
    validate_certs: true
    timeout: "{{ http_check_timeout }}"
  register: db_pool_result
  delegate_to: localhost
  failed_when: false
  when: integration_checks.db_pool_url is defined

- name: Build list of failed downstream dependencies
  ansible.builtin.set_fact:
    failed_downstreams: >-
      {{ downstream_checks.results
         | selectattr('failed', 'equalto', true)
         | map(attribute='item.name')
         | list }}

- name: Evaluate integration health
  ansible.builtin.set_fact:
    integration_status: >-
      {{
        'DOWN'     if failed_downstreams | length == downstream_checks.results | length and
                      downstream_checks.results | length > 0
        else 'DEGRADED' if failed_downstreams | length > 0
        else 'UP'
      }}
    integration_details:
      downstream_total: "{{ downstream_checks.results | length }}"
      downstream_up: "{{ downstream_checks.results | rejectattr('failed', 'equalto', true) | list | length }}"
      downstream_down: "{{ failed_downstreams }}"
      db_pool_active: "{{ db_pool_result.json.activeConnections | default('N/A') }}"
      db_pool_max: "{{ db_pool_result.json.maxConnections | default('N/A') }}"
      db_pool_utilization_pct: >-
        {{
          ((db_pool_result.json.activeConnections | default(0) | int /
            db_pool_result.json.maxConnections | default(1) | int) * 100) | round(1)
          if db_pool_result.json is defined else 'N/A'
        }}
Line-by-Line Explanation
DEGRADED vs DOWN logic on downstreams — If ALL downstream hosts are unreachable, the application is DOWN (can't process anything). If SOME are unreachable (e.g., Visa gateway down but Mastercard up), the application is DEGRADED (partial functionality). This nuanced status prevents false P1 alerts for partial payment network outages where the bank's system itself is fine but a card network is having issues.
db_pool_utilization_pct — For the NACH scenario: if DB pool is at 100% utilization (all 50 connections exhausted), it's immediately visible in the integration check details. The alert includes "DB Pool: 50/50 active (100%)" — the on-call engineer knows instantly this is a connection pool exhaustion, not a code bug.
selectattr('failed', 'equalto', true) | map(attribute='item.name') — Chain of Jinja2 filters that extracts the name field (human-readable like "SWIFT Network") from only the failed loop results — producing a clean list like ["SWIFT Network (SWIFTNet Link)"] for the alert payload instead of a raw dict dump.

      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: resolve
      dedup_key: "securebank-health-{{ item }}-{{ ansible_date_time.date }}"

  loop: >-

Line-by-Line Explanation
dedup_key: "securebank-health-{{ item }}-{{ ansible_date_time.date }}" — PagerDuty uses the dedup_key to prevent duplicate alerts. The same dedup_key for the same app on the same date means: if the health check runs every 5 minutes and an app is DOWN for 30 minutes, PagerDuty only fires ONE alert (not 6), then acknowledges it when the resolve event fires. Without dedup_key, the on-call engineer would receive 6 identical P1 alerts per 30 minutes — alert fatigue destroying the NOC's ability to triage.
event_action: resolve on the second task — Ansible automatically sends resolve events to PagerDuty when a previously-alerting application's health check returns UP. This auto-closes the incident without a human having to manually resolve it — critical for high-frequency health checks where the NOC can't keep up with manual incident management at 5-minute intervals.
recent_errors: "{{ ... | join(' | ') | truncate(500) }}" — The last 20 error log lines are embedded directly in the PagerDuty custom_details — the on-call engineer sees the stack trace or error message in the PagerDuty notification on their phone, before they've opened a laptop. This is the "rich context" that reduces MTTA from 15 minutes to 3 minutes.
aap_job_url in alert — Embedding the direct link to the AAP job output in the PagerDuty alert means the responding engineer can open the full run output in one click, seeing every layer check result across all 14 applications in a single view — no SSH sessions needed for initial triage.

  hosts: all

  vars_files:
    - group_vars/vault.yml
  tasks:
    - name: Initialize all layer statuses to SKIP (prevents undefined errors in report)

        process_status: "SKIP"
        api_status: "SKIP"
        business_status: "SKIP"
        integration_status: "SKIP"
        infra_details: {}
        process_details: {}
        api_details: {}
        business_details: {}

    - health_infra
    - health_process
    - health_app_api
    - health_business
    - health_integration
    - health_aggregator
    - health_alert
Design Rationale — Why gather_facts: false?
gather_facts: false at the top level — This is a deliberate performance optimization. Full fact gathering on 14 application servers in sequence would take 30–60 seconds before any actual health check begins. Since we're running every 5 minutes, that's 10–20% of the check interval just on fact collection. Instead, each role that needs specific facts uses ansible.builtin.setup with a minimal gather_subset targeting only what it needs.
Initialize all statuses to "SKIP" — The aggregator role reads all layer status facts regardless of whether the check was enabled for the app. Initializing everything to "SKIP" in the first task means the aggregator's Jinja2 ternary chain can safely default to "SKIP" for disabled layers without causing undefined-variable errors in the report template.

🔄 14. Execution Flow — Start to Finish

1
AAP Scheduler fires the Health-Check-All-Apps job every 5 minutes. The EE container starts with Vault credentials injected (for Slack webhook URL, PagerDuty routing key).
2
All 14 application "hosts" are targeted in parallel (forks=14). Each application's first task initializes all layer statuses to "SKIP" — preventing undefined-variable failures downstream.
3
Layer 1 (Infra): setup with hardware subset runs via delegate_to: ansible_host on each real server. CPU, memory, disk, load average measured. Status set to UP/DEGRADED/DOWN with actual metric values stored in infra_details.
4
Layer 2 (Process): systemctl is-active, pgrep -c, zombie check, log tail — all run via delegate_to on the server. Recent error lines captured for alert context.
5
Layer 3 (API): uri module from delegate_to: localhost hits the health endpoint over HTTPS, measuring response time. Version check confirms expected version is running. Status DEGRADED if response > threshold.
6
Layer 4 (Business): Synthetic test transactions run from localhost for CBS (balance enquiry), Payment Gateway (auth test), NACH (queue depth via API). Any unexpected response value or queue depth breach → DOWN status.
7
Layer 5 (Integration): wait_for TCP checks on every downstream dependency. DB pool utilization extracted from admin endpoint. SWIFT connectivity verified. Failed downstream list compiled.
8
Aggregator (run_once): All 14 applications' health records collected from hostvars. Fleet summary computed (how many UP/DEGRADED/DOWN). Unified health_report.json generated from Jinja2 template. Prometheus metrics pushed to Pushgateway (Grafana polls this for the NOC dashboard).
9
Alert role (run_once): Any DEGRADED/DOWN apps trigger PagerDuty events with dedup_key, severity, and rich custom_details (failing layer, error lines, AAP job URL). Any previously-alerting apps now showing UP trigger PagerDuty resolve events (auto-close).
10
Total elapsed time for full 14-application, 5-layer check: approximately 45–90 seconds (within the 5-minute schedule interval). The remaining 3–4 minutes of each interval is idle — ready for the next run.

Scenario-Based Questions

Q: What is the difference between infrastructure monitoring (Nagios/ping) and the health checks you built here?
Infrastructure monitoring confirms the OS and network layer are responsive — the server is up, the port is open, the process exists. This misses: application-layer failures (the app is running but returning errors), business-logic failures (transactions are being silently declined), integration failures (the app is healthy but its downstream payment network is unreachable), and performance degradation (the API is responding but at 8 seconds instead of the SLA'd 2 seconds). The 5-layer model catches all of these, reducing false negatives (undetected real failures) dramatically.
Q: How do you prevent alert storms when 5 applications are all DOWN (e.g., a datacenter network outage)?
Two mechanisms: (1) PagerDuty dedup_key — each application has its own dedup_key, so 5 DOWN apps = 5 PagerDuty incidents (grouped in PagerDuty's service view, not 5 × 18 (checks per 5-min interval) = 90 alerts). (2) We add a fleet-level check in the aggregator: if more than 50% of applications are DOWN simultaneously, the alert summary says "Fleet-wide outage suspected — possible datacenter/network issue" at severity P0, allowing the NOC to escalate to the network team directly rather than treating 5 separate application incidents.
Q: How do synthetic transactions differ from actual user transactions, and why is that distinction important?
Synthetic transactions are read-only, use a dedicated test account (never a real customer account), are flagged with a custom header (X-Health-Check), and target non-destructive endpoints (balance enquiry, not fund transfer). The distinction is critical because: (1) we don't want synthetic test traffic contaminating real transaction counts in regulatory reporting; (2) a failed synthetic transaction is a health signal, not a real financial error requiring investigation; (3) we must never use real customer data or real money for automated health checks — a regulatory violation.

Architecture & Production Questions

Q: How do you ensure the health check itself doesn't add load to an already-stressed application?
Health endpoints are designed to be lightweight — they should not trigger database queries or downstream calls (just check in-memory cached status). Our synthetic transactions use dedicated test accounts with no business side-effects. The health check schedule (5 minutes) is far below the load threshold of any banking API. For extremely stressed apps, the integration_check's TCP port check adds ~1ms of load versus the uri module's full HTTP overhead — we can fall back to TCP-only checks if an app team requests it.
Q: What is the Prometheus Pushgateway pattern, and why push instead of scrape?
Prometheus normally scrapes (pulls) metrics from a /metrics endpoint on each server. AAP jobs are ephemeral — they run for 60-90 seconds then stop; there's no persistent /metrics endpoint for Prometheus to scrape. Pushgateway solves this: the job pushes its metrics to the Pushgateway (which persists them), and Prometheus scrapes the Pushgateway continuously. The trade-off: Pushgateway metrics are "stale" between job runs — Grafana shows the last known health status, not a live instantaneous view. Appropriate for a 5-minute check cycle.
Q: How would you scale this health check to 1,000 applications across multiple data centers?
AAP's execution node topology handles horizontal scaling: deploy dedicated execution nodes in each data center, configure AAP instance groups per DC, and split the application inventory by DC. The 5-layer check architecture is stateless and parallelism-safe — 1,000 apps at forks=500 per DC would still complete within the 5-minute interval. The report aggregation (run_once) becomes the bottleneck — at scale, we'd push metrics to Prometheus per-host (not aggregate in Ansible) and let Prometheus handle the fleet-wide view instead.

📝 17. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Health checks must NEVER abort mid-run — failed_when: false + ignore_errors: true on every check task is the most important pattern in this project.
  • 5-layer health checks (infra → process → API → business → integration) catch failure classes that no single monitoring tool covers alone.
  • Business-logic checks (queue depth, synthetic transaction response validation) are the highest-value checks because they detect failures that look healthy at every other layer.
  • PagerDuty dedup_key + auto-resolve is the difference between a useful alerting system and an alert-storm-generating noise machine.

Common Mistakes

  • Checking from the server itself instead of delegate_to: localhost for API/TLS checks — misses load-balancer and network-path failures.
  • Letting a failed health check abort the play — means 10 of 14 applications never get checked.
  • Not initializing layer statuses to "SKIP" before roles run — causes Jinja2 undefined-variable errors in the aggregation template for applications with some checks disabled.
  • No dedup_key on PagerDuty events — 5-minute check cycle × 2 hours of outage = 24 duplicate P1 alerts per application.

Production Best Practices

  • Make thresholds variables per-application, not hardcoded in playbooks — each app team knows their own SLA better than the platform team.
  • Include the AAP job URL in every PagerDuty alert — eliminates the "first 10 minutes of MTTA wasted figuring out what broke" problem.
  • Run health checks as the final stage of every deployment, patch, and cert renewal workflow — transforms point-in-time checks into continuous post-change gates.
  • Add a fleet-level "majority DOWN" detection — a single alert for datacenter-scale outages instead of N individual application alerts.

Resume Points

  • Designed and implemented a 5-layer (infrastructure, process, application API, business logic, integration) health check automation pipeline using Ansible AAP covering 14 banking applications, replacing fragmented monitoring with a unified health JSON fed to a Grafana NOC dashboard.
  • Reduced P1 MTTA from 15+ minutes to under 3 minutes by embedding rich diagnostic context (failing layer, error log lines, DB pool stats, AAP job URL) directly in PagerDuty alert payloads.
  • Implemented business-logic health checks including synthetic transaction validation and NACH queue-depth monitoring, detecting application-layer failures invisible to infrastructure monitoring — including a NACH stall scenario that would otherwise take 22+ minutes to detect manually.
