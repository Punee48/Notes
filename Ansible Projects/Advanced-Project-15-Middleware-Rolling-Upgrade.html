Project 15: Enterprise Middleware Rolling Upgrade Automation — Tomcat & JBoss EAP

Upgrading middleware (Apache Tomcat, JBoss EAP) across 180 application servers is one of the highest-risk activities in banking IT. A wrong version, a missed configuration file, a failed health check — any of these can take down the Core Banking System during business hours. Manual upgrades take 3 engineers × 8 hours per release cycle. This project automates the complete rolling upgrade lifecycle: pre-upgrade validation → LB drain → backup current version → upgrade → health check → LB re-add → rollback on failure. One server upgraded at a time (serial: 1), with automatic rollback if health checks fail, ensuring zero customer-facing downtime even when individual servers encounter issues.

🏦 1. The Banking Story

Setting: ABC Global Bank's Loan Management System (LMS) runs on 12 JBoss EAP 7.3 servers behind an HAProxy load balancer. The bank must upgrade to JBoss EAP 7.4 to address CVE-2023-3171 (a critical RCE vulnerability). The upgrade must happen within 30 days of the CVE disclosure (per RBI cybersecurity guidelines) and must not cause downtime during banking hours (09:00 – 18:00 IST).

Incident 1 — The Manual Upgrade Disaster: Six months ago, the team manually upgraded Tomcat from 9.0.70 to 9.0.75 on the CBS application cluster. Engineer A updated server 1-4. Engineer B updated server 5-8. Engineer C was supposed to update 9-12 but accidentally deployed the old application WAR file to the new Tomcat version (the WAR had a hard-coded path that changed between versions). Servers 9-12 ran the new Tomcat but with the old WAR config — causing inconsistent behavior where some customer requests succeeded (hitting servers 1-8) and some failed (hitting servers 9-12). The mixed-version state ran undetected for 3 days. 4,300 loan customers got incorrect EMI calculations during this window.

Incident 2 — No Rollback Plan: During a JBoss upgrade, server lms-app07's JVM ran out of PermGen space after the upgrade (the new version had slightly different memory requirements). JBoss crashed 4 minutes after startup. The engineer who did the upgrade had already moved on to the next server. Nobody had documented how to rollback. It took 45 minutes to identify the issue and manually restore the previous version from a backup that wasn't even current.

Incident 3 — The Missing Config File: A Tomcat upgrade on the payment gateway servers missed copying the custom logging.properties file. The new Tomcat used its default logging config, which rotated logs differently from the bank's log retention policy. An audit 3 months later found the gap in log retention — a PCI-DSS finding.

The Ask: "Automate middleware upgrades. Upgrade one server at a time. Drain LB before touching each server. Back up the current version before upgrading. Auto-rollback if health check fails. Validate all config files are present after upgrade. Alert the team with a detailed upgrade report."

📚 2. Rolling Upgrade Concepts

Rolling vs Big-Bang Upgrades
Big-Bang upgrade: Upgrade all servers simultaneously during a maintenance window. Faster but: all servers down at once, single point of failure if upgrade fails, rollback requires reverting all servers.

Rolling upgrade: Upgrade one server (or one batch) at a time. The remaining servers continue serving traffic. If one server's upgrade fails, it's rolled back and only that server is affected — the cluster remains operational.

serial: 1 in Ansible means: process exactly 1 server at a time. With 12 servers, Ansible completes the full upgrade-health_check-LB_re-add cycle on server 1 before starting server 2. This is the safest approach for banking — customers always have 11/12 servers available minimum.
max_fail_percentage — The Safety Valve
max_fail_percentage: 0 means: if ANY server fails during the rolling upgrade, Ansible stops processing remaining servers immediately. With 12 servers:
• Server 1 upgrades successfully → continue
• Server 2 upgrades successfully → continue
• Server 3 upgrade fails (health check fails) → STOP. Servers 4-12 remain on old version.

This prevents a cascading failure where a bad upgrade package takes down the entire cluster one server at a time. The cluster stays at partial capacity (servers 3-12 on old version, servers 1-2 on new) — fully operational, ready for manual investigation.

Combined with auto-rollback on the failed server, the cluster ends in a clean state: servers 1-2 on new version, servers 3-12 on old version, server 3 rolled back to old version.
HAProxy LB Drain — The Critical Step
Before upgrading a server, it must be removed from the load balancer's active pool so no new connections are sent to it. HAProxy supports several methods:

MAINT state: Immediately stops all traffic — existing connections dropped. Too aggressive for banking.
DRAIN state: No new sessions assigned, but existing sessions continue until they complete. This is the correct approach — allows in-flight requests to finish before upgrade begins.

HAProxy stats socket command:
echo "set server lms_backend/lms-app07 state drain" | socat stdio /var/run/haproxy/stats

We wait until the server's active connection count reaches 0 (with a configurable timeout) before proceeding with the upgrade. After upgrade and health check, we re-add the server:
echo "set server lms_backend/lms-app07 state ready" | socat stdio /var/run/haproxy/stats

💻 8. Roles & Tasks — Complete Code

Role 1: mw_preflight — Pre-Upgrade Validation

roles/mw_preflight/tasks/check_current_version.yml
---
# =====================================================================
# Verify current middleware version before attempting upgrade
# Prevents upgrading wrong version or already-upgraded servers
# =====================================================================

- name: Check current JBoss/Tomcat version
  ansible.builtin.shell:
    cmd: |
      {% if middleware_type == 'jboss' %}
      cat {{ middleware_home }}/version.txt 2>/dev/null \
        || {{ middleware_home }}/bin/standalone.sh --version 2>&1 \
        | grep -i "JBoss EAP" | head -1
      {% elif middleware_type == 'tomcat' %}
      {{ middleware_home }}/bin/version.sh 2>/dev/null \
        | grep "Server version" | awk -F'/' '{print $2}'
      {% endif %}
    executable: /bin/bash
  register: current_version_output
  changed_when: false
  become: true
  become_user: "{{ middleware_user }}"

- name: Set current version fact
  ansible.builtin.set_fact:
    detected_current_version: >-
      {{ current_version_output.stdout
         | regex_search('([0-9]+\.[0-9]+\.[0-9]+)', '\\1')
         | first | default('UNKNOWN') }}

- name: Fail if current version does not match expected
  ansible.builtin.fail:
    msg: >-
      VERSION MISMATCH on {{ inventory_hostname }}:
      Expected current version {{ current_version }},
      found {{ detected_current_version }}.
      This server may already be upgraded or on a different version.
      Manual investigation required.
  when: detected_current_version != current_version

- name: Check maintenance window
  ansible.builtin.fail:
    msg: >-
      MAINTENANCE WINDOW VIOLATION: Current time is {{ ansible_date_time.time }}.
      Upgrades are only allowed between {{ maintenance_window_start }}
      and {{ maintenance_window_end }}.
      Do not upgrade during banking hours (09:00-18:00 IST).
  when: >
    (ansible_date_time.hour | int >= 9
     and ansible_date_time.hour | int < 18)

- name: Check available disk space for upgrade
  ansible.builtin.shell:
    cmd: "df -BG {{ middleware_install_dir }} | tail -1 | awk '{print $4}' | tr -d G"
  register: available_gb
  changed_when: false
  become: true

- name: Fail if insufficient disk space
  ansible.builtin.fail:
    msg: >-
      INSUFFICIENT DISK SPACE on {{ inventory_hostname }}:
      {{ available_gb.stdout | trim }}GB available,
      need at least 5GB for upgrade package + backup.
  when: available_gb.stdout | trim | int < 5

- name: Log pre-flight success
  ansible.builtin.debug:
    msg:
      - "✅ Pre-flight PASSED for {{ inventory_hostname }}"
      - "  Current version: {{ detected_current_version }}"
      - "  Target version: {{ target_version }}"
      - "  Disk available: {{ available_gb.stdout | trim }}GB"

Role 2: mw_lb_drain — HAProxy Load Balancer Management

roles/mw_lb_drain/tasks/drain_server.yml
---
# =====================================================================
# Set server to DRAIN state in HAProxy before upgrade
# DRAIN: no new sessions, existing sessions complete naturally
# This ensures in-flight banking transactions are not interrupted
# =====================================================================

- name: Set server to DRAIN state in HAProxy
  ansible.builtin.shell:
    cmd: >
      echo "set server {{ haproxy_backend_name }}/{{ inventory_hostname.split('.')[0] }}
      state drain"
      | socat stdio {{ haproxy_stats_socket }}
    # socat: connects to HAProxy stats Unix socket
    # "set server backend/server state drain": graceful drain
    # inventory_hostname.split('.')[0]: extract short hostname (lms-app01 from FQDN)
  delegate_to: "{{ item }}"
  loop: "{{ haproxy_servers }}"
  loop_control:
    label: "Draining {{ inventory_hostname }} on {{ item }}"
  become: true
  register: drain_results

- name: Wait for active connections to reach zero
  ansible.builtin.shell:
    cmd: >
      echo "show stat" | socat stdio {{ haproxy_stats_socket }}
      | grep "{{ haproxy_backend_name }},{{ inventory_hostname.split('.')[0] }}"
      | cut -d',' -f18
    # show stat: dumps HAProxy stats CSV
    # column 18 is "scur" (sessions current) — active connections to this server
  register: active_connections
  delegate_to: "{{ haproxy_servers | first }}"
  until: active_connections.stdout | trim == '0'
  retries: "{{ (haproxy_drain_timeout_sec / 10) | int }}"
  delay: 10                                  # Check every 10 seconds
  become: true

- name: Log server drain completion
  ansible.builtin.debug:
    msg: >-
      ✅ {{ inventory_hostname }} drained from {{ haproxy_backend_name }}.
      Active connections: {{ active_connections.stdout | trim }}
      Server is safe to upgrade.
roles/mw_lb_drain/tasks/restore_server.yml
---
# =====================================================================
# Restore server to READY state in HAProxy after upgrade
# Used both after successful upgrade AND after rollback
# =====================================================================

- name: Set server back to READY state in HAProxy
  ansible.builtin.shell:
    cmd: >
      echo "set server {{ haproxy_backend_name }}/{{ inventory_hostname.split('.')[0] }}
      state ready"
      | socat stdio {{ haproxy_stats_socket }}
  delegate_to: "{{ item }}"
  loop: "{{ haproxy_servers }}"
  loop_control:
    label: "Re-adding {{ inventory_hostname }} on {{ item }}"
  become: true

- name: Verify connections resume to restored server
  ansible.builtin.shell:
    cmd: >
      echo "show stat" | socat stdio {{ haproxy_stats_socket }}
      | grep "{{ haproxy_backend_name }},{{ inventory_hostname.split('.')[0] }}"
      | cut -d',' -f19
    # column 19 is "stot" (total sessions) — should be incrementing
  register: total_sessions
  delegate_to: "{{ haproxy_servers | first }}"
  become: true

- name: Log LB restoration
  ansible.builtin.debug:
    msg: "✅ {{ inventory_hostname }} restored to {{ haproxy_backend_name }} — READY state"

Role 3: mw_backup + Role 4a: mw_tomcat_upgrade

roles/mw_backup/tasks/backup_current_version.yml
---
# =====================================================================
# Backup current middleware installation before upgrade
# This backup enables auto-rollback if upgrade fails
# =====================================================================

- name: Create timestamped backup directory
  ansible.builtin.file:
    path: "{{ middleware_backup_dir }}"
    state: directory
    mode: '0755'
    owner: "{{ middleware_user }}"
  become: true

- name: Create full backup of current middleware installation
  ansible.builtin.archive:
    path: "{{ middleware_home }}"                # Archive the full middleware dir
    dest: >-
      {{ middleware_backup_dir }}/
      {{ middleware_type }}-{{ current_version }}-
      {{ inventory_hostname }}-
      {{ ansible_date_time.epoch }}.tar.gz
    format: gz
    owner: "{{ middleware_user }}"
  register: backup_result
  become: true

- name: Store backup path as fact for rollback
  ansible.builtin.set_fact:
    backup_file_path: "{{ backup_result.dest }}"
    pre_upgrade_version: "{{ current_version }}"

- name: Verify backup file was created and has content
  ansible.builtin.stat:
    path: "{{ backup_file_path }}"
  register: backup_stat
  become: true

- name: Fail if backup is empty or missing
  ansible.builtin.fail:
    msg: "BACKUP FAILED: {{ backup_file_path }} is empty or missing. Cannot proceed with upgrade."
  when: not backup_stat.stat.exists or backup_stat.stat.size < 1024

- name: Log backup success
  ansible.builtin.debug:
    msg:
      - "✅ Backup created: {{ backup_file_path }}"
      - "   Size: {{ (backup_stat.stat.size / 1048576) | round(1) }}MB"
roles/mw_tomcat_upgrade/tasks/migrate_config.yml
---
# =====================================================================
# Migrate configuration files from old Tomcat to new version
# This is the critical step that prevented Incident 3 (missing logging.properties)
# =====================================================================

- name: Stop current Tomcat service
  ansible.builtin.service:
    name: "{{ middleware_service }}"
    state: stopped
  become: true

- name: Extract new Tomcat version to install directory
  ansible.builtin.unarchive:
    src: "{{ upgrade_package }}"               # From NFS package store
    dest: "{{ middleware_install_dir }}"
    remote_src: false                          # Package is on AAP node → push to server
    owner: "{{ middleware_user }}"
    group: "{{ middleware_user }}"
  become: true

- name: Migrate all required configuration files from old to new version
  ansible.builtin.copy:
    src: >-
      {{ middleware_install_dir }}/apache-tomcat-{{ current_version }}/conf/{{ item | basename }}
    dest: >-
      {{ middleware_install_dir }}/apache-tomcat-{{ target_version }}/conf/{{ item | basename }}
    owner: "{{ middleware_user }}"
    remote_src: true                           # Both src and dest are on the same server
    backup: true                               # Keep new version's default as .backup
  loop:
    - server.xml                               # Connector config (ports, SSL)

    # --overwrite: overwrite existing files

  become: true

    name: "{{ middleware_service }}"
    state: started
  become: true

- name: Verify old version health check passes after rollback
  ansible.builtin.uri:
    url: "{{ health_check_url }}"
    method: GET
    status_code: [200]
    timeout: 10

  retries: 12
  delay: 10

    url: "{{ slack_webhook_url }}"

🎯 15. Interview Prep

Q: Why use serial: 1 with max_fail_percentage: 0 for middleware upgrades?
serial: 1 ensures only one server is being upgraded at any moment. The remaining N-1 servers continue serving all customer traffic through the load balancer. If something goes wrong, 100% of traffic can be served by the healthy servers — the customer impact is zero.

max_fail_percentage: 0 means: if the upgrade fails on any single server (health check fails, rollback triggered), Ansible immediately stops processing ALL remaining servers. This prevents a bad upgrade package from progressively taking down the entire cluster one server at a time. With 12 servers, a bad upgrade could otherwise take down servers 1 through 12 sequentially — each one degrading capacity further until total outage.

The combination is the safest possible approach: one at a time, stop everything if anything fails.
Q: How does the rescue block enable automatic rollback?
Ansible's block/rescue/always structure mirrors try/catch/finally in programming. The rescue section runs ONLY if any task in the associated block fails:

tasks:
  - block:
      - include_role: name=mw_health_check
    rescue:
      - include_role: name=mw_rollback
If any health check task fails (HTTP returns non-200, version mismatch, config file missing, heap too high), the rescue block immediately runs the rollback role — stopping the failed new version, restoring from the tar.gz backup, restarting the old version, re-adding to HAProxy.

The rollback role ends with ansible.builtin.fail — which ensures the server is counted as failed, triggering max_fail_percentage: 0 to stop the upgrade on remaining servers.
Q: What is the difference between HAProxy DRAIN and MAINT states?
MAINT (Maintenance): Server is immediately removed from the pool. All existing connections are dropped instantly. New health checks stop. Use case: emergency removal when server is completely broken.

DRAIN: Server is removed from rotation for NEW sessions only. Existing sessions (in-flight requests) continue until they complete naturally. Health checks continue. Use case: graceful upgrade — allows a customer's loan calculation request to complete before the server is taken offline.

For banking upgrades, DRAIN is mandatory. Dropping mid-transaction connections could result in partial writes (loan approved in app but not committed to DB), which are extremely difficult to reconcile and can cause regulatory issues. We poll the active connection count every 10 seconds and only proceed with the upgrade when connections = 0 — guaranteeing every in-flight transaction has completed.
Q: How do you prevent a mixed-version cluster (like Incident 1)?
Two mechanisms:

1. Pre-upgrade version check: Before upgrading each server, we detect the current version using the middleware's version command. If it doesn't match current_version, the preflight check fails and the upgrade is blocked for that server. This prevents accidentally upgrading a server that's already at a different version.

2. Post-upgrade version audit: After the rolling upgrade completes, middleware_version_audit.yml queries ALL servers and collects their versions into a list. Using Jinja2's | unique filter, if the list has more than one element, a mixed-version state exists and a Slack alert fires.

This audit uses hostvars — each server stores its detected version as a host fact during the play, and the aggregation play on localhost accesses all hosts' facts via hostvars[hostname].version_outputs.stdout — the same cross-host comparison technique used in DNS consistency checking (Project 10).
