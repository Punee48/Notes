Project 2: Security Patch Management using Red Hat AAP

SecureBank's Information Security team mandates that every RHEL server — across Dev, UAT, DR, and Production — be patched against critical/important CVEs within strict SLAs (typically 72 hours for critical, 7 days for important), with zero unplanned downtime to transaction-processing systems. This project automates CVE-aware patching, reboot orchestration, and patch compliance reporting across SecureBank's ~400-server RHEL fleet using Red Hat AAP.

RHEL 8/9 Red Hat AAP 2.5 Satellite/Katello Patch Source CVE Compliance RBI/PCI-DSS Patch SLA Zero-Downtime Reboot Orchestration

📋 1. Business Requirement

SecureBank's InfoSec team subscribes to Red Hat Satellite errata feeds and receives a weekly CVE digest. Per the bank's internal Information Security Policy (aligned to RBI cyber-security framework and PCI-DSS Requirement 6.2 — "ensure all system components and software are protected from known vulnerabilities by installing applicable vendor-supplied security patches"), every server must be patched within a defined SLA based on CVE severity, with evidence retained for the annual PCI-DSS audit.

The fleet spans ~400 RHEL 8/9 servers: 120 Dev, 60 UAT, 180 Production (across Mumbai DC and Chennai DR), and 40 DMZ-facing servers (highest priority, externally exposed). Patching production transaction-processing servers requires coordination with the App Tier (Project 1) to avoid patching + restarting during business hours (8 AM – 8 PM IST) or month-end batch processing windows.

🏦 2. Real-Time Banking Scenario

The Story: It's a Tuesday morning. Red Hat publishes RHSA-2026:4821 — a critical OpenSSL CVE (remote code execution, CVSS 9.8) affecting every RHEL server fleet-wide. The CISO's office declares a P1 security incident with a 72-hour patch SLA. Before automation, the Linux team would spend two full days SSH-ing into servers in batches, running yum update manually, occasionally missing DMZ servers because they're on a separate jump host, and submitting a hand-typed Excel sheet to InfoSec as "evidence" — which auditors regularly reject as insufficiently verifiable. Today, Rajesh, the on-call Platform Engineer, instead launches the CVE-Emergency-Patch AAP Workflow, scopes it to "DMZ + CVSS>=9", watches all 40 DMZ hosts patch and reboot in controlled batches within 90 minutes, and the AAP job log itself becomes the audit evidence InfoSec submits to the RBI inspection team.

❗ 3. Problem Statement

  • No centralized, provable way to know which of 400 servers are patched against a specific CVE at any given moment.
  • Manual yum update patches everything indiscriminately — risky; banks need targeted errata-level patching (only apply the specific security advisory, not unrelated package bumps that could break the app).
  • Reboots after kernel/glibc patches must be orchestrated carefully — rebooting all 180 production servers at once would be a self-inflicted outage.
  • DMZ servers (most externally exposed, highest risk) are often patched last because they're hardest to reach manually — exactly backwards from the risk-based priority InfoSec requires.
  • No reliable evidence trail for auditors — Excel-based tracking is routinely flagged as a finding during PCI-DSS / RBI IS audits.
  • Patch failures (disk space exhaustion, repo unreachable, conflicting package locks) are discovered late, often after the maintenance window has closed.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. InfoSec emails a PDF of the weekly Red Hat errata digest to the Linux team distribution list.
  2. An engineer manually cross-references CVE IDs against a spreadsheet of "which servers run what" — frequently outdated.
  3. Engineer SSHs into each server, runs yum check-update, eyeballs the list, and runs yum update <package> by hand.
  4. Engineer manually checks needs-restarting -r to decide if reboot is needed.
  5. Engineer reboots servers one at a time, watching for the server to come back up via ping.
  6. Engineer manually updates an Excel tracker with hostname, CVE, patch date, and "Done" status.
  7. At month-end, someone manually compiles the Excel sheets from 4 different engineers into one master report for InfoSec.

🛠️ 6. Automated Solution Design

We design a CVE-driven, severity-prioritized patch workflow that:

  • Pulls applicable errata directly from Red Hat Satellite/Katello (the source of truth for what's available per host collection) rather than guessing from email digests.
  • Classifies hosts into priority tiers via inventory groups: dmz (patch first) → production_app (patch in controlled batches with health gates) → uat → dev (patch freely, no approval needed).
  • Applies patches at the advisory/errata level, not blanket yum update, scoped by CVE ID passed as a survey variable.
  • Detects whether a reboot is actually required (kernel/glibc/systemd updates) using needs-restarting, and only reboots when necessary — avoiding unnecessary downtime.
  • Reboots production app servers in serial batches with a post-reboot health check gate (reusing the smoke-test pattern from Project 1) before proceeding to the next batch.
  • Generates a machine-readable compliance report (CSV/JSON) per run, listing hostname, CVE/advisory, pre-patch and post-patch package versions, and timestamp — this becomes the audit evidence.
  • Sends the report automatically to InfoSec via AAP's notification system and archives it to a compliance S3/NFS bucket.

⚙️ 8. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.builtin.dnf (update_only, security filters), ansible.builtin.reboot, ansible.builtin.command (needs-restarting), ansible.builtin.uri
  • Roles: patch_inventory_check, patch_apply, patch_reboot_orchestrator, patch_compliance_report
  • serial with health-check gates between batches
  • block/rescue for per-host failure isolation without aborting the whole batch
  • Custom facts module via ansible.builtin.setup gather_subset for installed package versions
  • Jinja2 templates for CSV/JSON compliance report generation

Red Hat AAP Components

  • Inventory Source: Satellite/Katello inventory plugin — host collections auto-sync as inventory groups
  • Credentials: Machine (SSH), Satellite API credential (for errata lookups)
  • Job Templates: Patch-DMZ-Tier1, Patch-ProdApp-Tier2, Patch-UATDev-Tier3, Patch-ComplianceReport
  • Survey: advisory_id (e.g. RHSA-2026:4821), patch_severity_filter, maintenance_window_confirmed (bool)
  • Workflow Template: CVE-Emergency-Patch (tiered, with approval node before Tier 2 prod batches)
  • Scheduled Job: Monthly-Routine-Patch-Cycle (recurring schedule for non-emergency patch SLAs)
  • Notification Template: Slack + Email to InfoSec distribution list with compliance report attached
  • RBAC: Only Security-Approved-Patchers team can launch Tier 2 (production) job templates

💻 11. Complete Project Code (Line-by-Line Explained)

Role: patch_inventory_check

roles/patch_inventory_check/tasks/main.yml
---
- name: Gather currently installed package facts
  ansible.builtin.package_facts:
    manager: rpm

- name: Capture pre-patch kernel version for compliance report
  ansible.builtin.set_fact:
    pre_patch_kernel: "{{ ansible_kernel }}"

- name: Check if target advisory is applicable to this host
  ansible.builtin.command: "dnf updateinfo list --advisory={{ advisory_id }}"
  register: advisory_check
  changed_when: false
  failed_when: false

- name: Skip host if advisory does not apply
  ansible.builtin.meta: end_host
  when: advisory_check.stdout == ""

- name: Verify sufficient disk space in /var for package cache
  ansible.builtin.shell: df --output=avail -BM /var | tail -1 | tr -dc '0-9'
  register: var_disk_avail
  changed_when: false

- name: Fail fast if insufficient disk space for patching
  ansible.builtin.fail:
    msg: "Insufficient /var space on {{ inventory_hostname }}: {{ var_disk_avail.stdout }}MB available"
  when: var_disk_avail.stdout | int < 1024

- name: Confirm current time is within approved patch window (non-DMZ only)
  ansible.builtin.fail:
    msg: "Refusing to patch {{ inventory_hostname }} — outside maintenance window and host is business-hours sensitive"
  when:
    - requires_app_drain | default(false)
    - not (maintenance_window_confirmed | default(false) | bool)
Line-by-Line Explanation
ansible.builtin.package_facts: manager: rpm — Populates ansible_facts.packages with every installed RPM and its exact version, which the compliance report role later uses to prove "before" state for the audit evidence — without this, we'd have no proof of what version was running pre-patch.
dnf updateinfo list --advisory={{ advisory_id }} — Queries whether the specific CVE/advisory (e.g. RHSA-2026:4821) actually applies to this host's installed packages — critical because not every server runs OpenSSL-dependent services, and patching irrelevant advisories wastes the maintenance window.
failed_when: false — We never want this query command itself to fail the play (a non-applicable advisory isn't an error condition) — we handle the "not applicable" case explicitly in the next task instead.
ansible.builtin.meta: end_host — A clean way to skip all remaining tasks for ONLY this host without failing it or aborting the whole play for other hosts — the host is marked as intentionally skipped, not failed, in the final report.
requires_app_drain | default(false) combined with maintenance_window_confirmed — This is a hard safety gate: production app-tier hosts (flagged requires_app_drain: true in group_vars) refuse to patch unless the survey explicitly confirms the maintenance window — preventing an accidental mid-day production patch run.

Role: patch_apply

roles/patch_apply/tasks/main.yml
---
- name: Apply only the specified security advisory (errata-level patching)
  ansible.builtin.dnf:
    name: "*"
    security: true
    update_only: true
    state: latest
  register: patch_result
  notify: Flag reboot required check

- name: Capture post-patch package facts for compliance diff
  ansible.builtin.package_facts:
    manager: rpm

- name: Capture post-patch kernel version
  ansible.builtin.set_fact:
    post_patch_kernel: "{{ ansible_kernel }}"

- name: Force handlers to determine reboot necessity now
  ansible.builtin.meta: flush_handlers
roles/patch_apply/handlers/main.yml
---
- name: Flag reboot required check
  ansible.builtin.command: needs-restarting -r
  register: reboot_required_check
  changed_when: false
  failed_when: false
  listen: "Flag reboot required check"

- name: Record reboot requirement as a host fact
  ansible.builtin.set_fact:
    host_needs_reboot: "{{ reboot_required_check.rc == 1 }}"
  listen: "Flag reboot required check"
Line-by-Line Explanation
name: "*" + security: true + update_only: true — This combination is the key to errata-level patching: security: true restricts dnf to security advisories ONLY (not feature/bugfix updates), and update_only: true ensures it only upgrades packages already installed — it will never pull in a brand-new package. This is intentionally narrower and safer than a blanket yum update.
state: latest combined with the above — Without security: true, this same module call would behave like a full system update; the combination of all three parameters together is what makes this "CVE-targeted patching" rather than "patch everything."
needs-restarting -r — A standard RHEL utility (from the yum-utils/dnf-utils package) that returns exit code 1 if a reboot is needed (kernel, glibc, systemd, dbus updated) and 0 if not — far more reliable than guessing based on which packages were updated.
host_needs_reboot: "{{ reboot_required_check.rc == 1 }}" — Converts the raw exit code into a clean boolean fact that the next role (patch_reboot_orchestrator) consumes, keeping the reboot-decision logic isolated from the reboot-execution logic — separation of concerns, a key Ansible design best practice.

Role: patch_reboot_orchestrator

roles/patch_reboot_orchestrator/tasks/main.yml
---
- name: Drain host from load balancer before reboot (production app tier only)
  ansible.builtin.uri:
    url: "https://lb-api.securebank.in/v1/pool/securecore/drain/{{ inventory_hostname }}"
    method: POST
    status_code: 200
  delegate_to: localhost
  when:
    - host_needs_reboot | default(false)
    - requires_app_drain | default(false)

- name: Wait for in-flight connections to drain (max 60s)
  ansible.builtin.pause:
    seconds: 60
  when:
    - host_needs_reboot | default(false)
    - requires_app_drain | default(false)

- name: Reboot host if kernel/glibc/systemd patch requires it
  ansible.builtin.reboot:
    reboot_timeout: "{{ reboot_timeout }}"
    msg: "Rebooting for security patch {{ advisory_id }} — initiated by AAP job"
    pre_reboot_delay: 5
    test_command: uptime
  when: host_needs_reboot | default(false)

- name: Re-add host to load balancer pool after successful reboot
  ansible.builtin.uri:
    url: "https://lb-api.securebank.in/v1/pool/securecore/activate/{{ inventory_hostname }}"
    method: POST
    status_code: 200
  delegate_to: localhost
  when:
    - host_needs_reboot | default(false)
    - requires_app_drain | default(false)

- name: Post-reboot health check before declaring batch complete
  ansible.builtin.uri:
    url: "{{ health_check_url }}"
    status_code: 200
    validate_certs: false
  register: post_reboot_health
  retries: "{{ post_reboot_health_retries }}"
  delay: "{{ post_reboot_health_delay }}"
  until: post_reboot_health.status == 200
  when:
    - host_needs_reboot | default(false)
    - health_check_url is defined
Line-by-Line Explanation
delegate_to: localhost on the LB drain task — The load balancer API call must originate from the Ansible control node (or a designated API gateway), not from the target host itself, since the target host is about to reboot and can't reliably call out about its own draining.
ansible.builtin.reboot module with test_command: uptime — This is a purpose-built module (not a raw shutdown -r now via shell) that handles the entire reboot lifecycle: it disconnects, waits for the host to go down, waits for SSH to come back, then runs test_command to confirm the host is truly responsive before considering the task complete.
pre_reboot_delay: 5 — Gives a 5-second buffer before initiating reboot, allowing any in-flight SSH command output to flush back to the control node cleanly.
All reboot/drain tasks gated by when: host_needs_reboot | default(false) — This is what prevents unnecessary downtime: if the security patch was, say, an OpenSSL userspace library update with no kernel involvement, the host never reboots at all, satisfying the "minimize downtime" requirement directly.
Post-reboot health check reusing the retry/until pattern from Project 1 — Demonstrates a consistent, reusable validation pattern across projects; in a real codebase this would likely become a shared role imported by both projects.

Role: patch_compliance_report

roles/patch_compliance_report/tasks/main.yml
---
- name: Ensure compliance report directory exists on control node
  ansible.builtin.file:
    path: "{{ patch_report_dir }}"
    state: directory
    mode: '0750'
  delegate_to: localhost
  run_once: true

- name: Append this host's patch result to the consolidated compliance dataset
  ansible.builtin.set_fact:
    patch_record:
      hostname: "{{ inventory_hostname }}"
      advisory: "{{ advisory_id }}"
      pre_patch_kernel: "{{ pre_patch_kernel | default('n/a') }}"
      post_patch_kernel: "{{ post_patch_kernel | default('n/a') }}"
      rebooted: "{{ host_needs_reboot | default(false) }}"
      patch_status: "{{ 'SUCCESS' if (patch_result is defined and not patch_result.failed) else 'FAILED' }}"
      patched_at: "{{ ansible_date_time.iso8601 }}"
      patched_by: "{{ tower_user_name | default('cli-user') }}"

- name: Write per-host JSON fact for aggregation
  ansible.builtin.copy:
    content: "{{ patch_record | to_nice_json }}"
    dest: "{{ patch_report_dir }}/{{ inventory_hostname }}.json"
  delegate_to: localhost

- name: Aggregate all per-host JSON files into final compliance CSV report
  ansible.builtin.template:
    src: compliance_report.csv.j2
    dest: "{{ patch_report_archive }}/patch-compliance-{{ advisory_id }}-{{ ansible_date_time.iso8601_basic_short }}.csv"
  delegate_to: localhost
  run_once: true

Hostname,Advisory,PrePatchKernel,PostPatchKernel,Rebooted,Status,PatchedAt,PatchedBy

Line-by-Line Explanation
run_once: true on the directory-creation and final CSV-generation tasks — These two operations only need to happen ONCE across the entire play (not once per host), since they operate on the shared control-node filesystem; without run_once, every host in the batch would redundantly try to create the same directory and regenerate the same report.
delegate_to: localhost throughout this role — All compliance-report file writes happen on the Ansible control node (or in AAP, inside the Execution Environment's writable workspace), never on the banking servers themselves — keeping audit evidence centralized and tamper-resistant from the target hosts.
{{ patch_result is defined and not patch_result.failed }} — Defensive Jinja2 expression: patch_result won't exist for hosts that were skipped via end_host in the inventory_check role, so we check is defined first to avoid an undefined-variable error crashing the whole report generation.
{% for host in ansible_play_hosts_all %} in the Jinja2 template — Iterates over every host targeted by the play (a magic Ansible variable), pulling each host's previously-set patch_record fact out of hostvars to build one consolidated CSV row per server — this is how a single control-node task produces a fleet-wide report from per-host data.

- name: CVE Emergency Patch — Tier 2 Production App/DB (approval-gated)
  hosts: patch_tier2
  become: true
  serial: "{{ patch_serial_batch | default('25%') }}"
  max_fail_percentage: 0
  roles:
    - patch_inventory_check
    - patch_apply
    - patch_reboot_orchestrator
    - patch_compliance_report

- name: CVE Emergency Patch — Tier 3 UAT/Dev (no approval required)
  hosts: patch_tier3
  become: true
  serial: "100%"
  max_fail_percentage: 20
  roles:
    - patch_inventory_check
    - patch_apply
    - patch_compliance_report
Line-by-Line Explanation
DMZ play runs first, before production — This deliberately inverts the old manual order (where DMZ was patched last due to access friction) to align with InfoSec's actual risk priority: externally-exposed systems get patched fastest.
max_fail_percentage: 0 on Tiers 1 and 2 — Zero tolerance for failures in DMZ and production; a single host failing aborts that batch, forcing manual investigation rather than silently leaving a server unpatched against a critical CVE.
Tier 3 (UAT/Dev) skips the patch_reboot_orchestrator role entirely in this playbook (rebooted by a simpler, non-LB-aware fallback not shown) and tolerates 20% failures — lower environments don't need the same blast-radius protection as production.

  • Scheduled variant: a separate Monthly-Routine-Patch-Cycle schedule runs the same workflow on the 2nd Sunday of every month at 1 AM IST for routine (non-emergency) errata, with maintenance_window_confirmed pre-set to true via an extra_vars prompt default.

🔄 13. Execution Flow — Start to Finish

1
InfoSec declares CVE RHSA-2026:4821 a P1; Rajesh launches the CVE-Emergency-Patch workflow, entering advisory_id=RHSA-2026:4821 in the survey.
2
AAP resolves the Satellite-synced Smart Inventory, splitting hosts into patch_tier1 (DMZ), patch_tier2 (Prod), patch_tier3 (UAT/Dev) groups automatically based on Host Collection membership.
3
Patch-DMZ-Tier1 job launches first. For each DMZ host, patch_inventory_check confirms the advisory is actually applicable via dnf updateinfo list; non-applicable hosts are skipped via meta: end_host.
4
patch_apply runs dnf with security: true, update_only: true — applying ONLY the relevant security errata, never unrelated package bumps.
5
The handler checks needs-restarting -r immediately after patching (via flush_handlers) and sets host_needs_reboot as a fact.
6
patch_reboot_orchestrator reboots only hosts that need it, using the reboot module which handles disconnect/reconnect/health-verify natively.
7
patch_compliance_report writes a per-host JSON fact, then (run_once) aggregates all hosts' facts into one timestamped CSV via the Jinja2 template, looping over ansible_play_hosts_all and hostvars.
8
Workflow pauses at the Approval Node. A senior engineer reviews the DMZ job log and CSV, confirms zero failures, and approves.
9
Patch-ProdApp-Tier2 launches, draining each app server from the load balancer (delegate_to: localhost API call) before any reboot, patching in 25% serial batches with max_fail_percentage: 0.
10
After each production host reboots, a post-reboot health check polls the SecureCore health endpoint before the host is re-added to the load balancer pool and the next batch begins.
11
Patch-UATDev-Tier3 runs last with relaxed failure tolerance, patching lower environments without an approval gate.
12
Final workflow node sends the consolidated compliance CSV to InfoSec via Slack and email, and archives it to the NFS compliance bucket — this becomes the evidence submitted at the next RBI/PCI-DSS audit cycle.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: How do you patch 180 production servers without causing an outage?
Serial batching (25%) combined with a health-check gate between batches, load-balancer draining before reboot, and zero tolerance for failures (max_fail_percentage: 0) so a problem in batch 1 halts before batch 2 begins — the same canary-style safety pattern as Project 1's deployment.
Q: How do you guarantee you only patch the specific CVE, not unrelated packages?
Using the dnf module with both security: true and update_only: true together — this restricts to security errata only and never installs new packages, combined with an explicit dnf updateinfo list --advisory=<id> applicability check beforehand.
Q: Auditor asks for proof a specific server was patched on a specific date. What do you show them?
The per-host JSON fact and the aggregated compliance CSV — both timestamped, including patched_by (sourced from AAP's tower_user_name magic variable) and pre/post kernel versions — plus the underlying AAP Job's stdout log and Activity Stream entry as corroborating system-of-record evidence.

Production Support & Troubleshooting

Q: A production host fails to come back healthy after a patch-triggered reboot. What's your response?
The play already halts the batch (max_fail_percentage: 0), so no further hosts are touched. SSH/console into the host, check journalctl -xb for boot failures, verify the LB never re-added it (health gate failed, so it stays drained) — preventing user-facing impact while triaging.
Q: How do you handle a CVE that requires a package not currently installed (e.g., a new mitigation package)?
update_only: true intentionally won't install it — that's a deliberate design choice for routine emergency patching; a separate, explicitly-reviewed playbook task (or change ticket) is used when InfoSec mandates installing a brand-new compensating-control package, since that's a higher-risk change than a same-package security bump.
Q: Architecture question — why use Satellite/Katello instead of pointing all hosts directly at Red Hat CDN?
Satellite gives content-view-based staged promotion (patches tested in Dev's content view before being promoted to Production's content view), offline/airgapped capability common in bank data centers, and Host Collections that map cleanly to Ansible inventory groups for tiered patch rollout.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Errata-level patching (security + update_only) is fundamentally different and safer than blanket yum update.
  • needs-restarting -r is the reliable way to decide reboot necessity — never assume based on package name alone.
  • Risk-based patch ordering (DMZ first) often inverts the old manual habit of "easiest servers first."
  • Compliance reporting must be built into the playbook itself, not bolted on afterward — it's a first-class deliverable, not an afterthought.

Common Mistakes

  • Using plain yum update instead of advisory-scoped patching — pulls in unrelated changes that can break apps mid-incident.
  • Rebooting all servers in one serial:100% batch — defeats the entire purpose of batch-based risk reduction.
  • Forgetting to drain from the load balancer before reboot, causing dropped in-flight transactions.
  • Not handling the "advisory not applicable" case — causes false failures/noise across hosts that don't need the patch.

Production Best Practices

  • Always confirm applicability with updateinfo before patching — never assume every host needs every advisory.
  • Keep DMZ/external-facing inventory as its own tier with the strictest SLA and zero fail tolerance.
  • Generate machine-readable compliance evidence (JSON/CSV) on every single run — audits happen on a schedule you don't control.
  • Gate production reboots behind explicit maintenance_window_confirmed input — never assume the timing is safe.

Resume Points

  • Built a CVE-driven, tier-prioritized Ansible patch management pipeline across a ~400-server RHEL fleet integrated with Red Hat Satellite, reducing critical CVE remediation time from 2+ days to under 4 hours.
  • Designed reboot-orchestration logic with load-balancer drain/re-add and post-reboot health gating, eliminating unplanned production downtime during patch cycles.
  • Automated PCI-DSS/RBI patch compliance evidence generation, replacing manual Excel tracking with auditable, timestamped JSON/CSV reports embedded directly in the AAP job pipeline.
