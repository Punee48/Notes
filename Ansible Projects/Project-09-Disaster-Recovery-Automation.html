Project 9: Disaster Recovery (DR) Automation using Red Hat AAP

Disaster Recovery is the highest-stakes automation a bank can build. SecureBank's RBI-mandated Business Continuity Plan requires a Recovery Time Objective (RTO) of 4 hours and a Recovery Point Objective (RPO) of 1 hour for all Tier-1 banking systems (CBS, Payment Gateway, NACH). The DR site is SecureBank's Chennai Data Centre — a full mirror of the Mumbai primary DC — that must be capable of running all Tier-1 applications within 4 hours of a declared Mumbai DC outage. Before automation, the DR runbook was a 120-page Word document that required 12 engineers working in parallel with walkie-talkie coordination to execute in 6–8 hours — routinely failing the 4-hour RTO in annual drills. This project replaces that runbook with a fully orchestrated AAP Workflow that activates the Chennai DR site, performing: infrastructure pre-flight checks, Oracle Data Guard switchover, DNS failover, application tier startup in dependency order, load balancer reconfiguration, health gate validation at each stage, and automated RTO clock reporting — all executable by a single NOC engineer pressing one button.

🏦 2. Real-Time Banking Scenario

The Story: It's a Wednesday at 11:43 AM. A major fire suppression system discharge in SecureBank's Mumbai Powai data centre triggers an emergency evacuation. Within 8 minutes, power to the primary server room is cut. The Mumbai DC is offline. SecureBank's NOC receives a cascade of P0 alerts. The CISO declares a DR event at 11:51 AM. The RBI 4-hour RTO clock starts.

Before automation (previous year's drill): The NOC manager opens the 120-page DR runbook. 12 engineers join a conference bridge. Step 1: "SSH into Chennai Oracle server and run: ALTER DATABASE COMMIT TO SWITCHOVER TO PRIMARY WITH SESSION SHUTDOWN;" — but which engineer knows the correct Oracle DG switchover sequence? Which one has the Chennai jump-host credentials? 2 hours wasted on coordination before the database even switches over. Final RTO: 7h 22min. RBI non-compliance letter received 3 weeks later.

After automation (this year): At 11:53 AM — 2 minutes after the DR declaration — NOC Engineer Divya opens the AAP Web UI, navigates to the DR-Activate-Chennai-Full Workflow Template, confirms the survey: dr_reason="Mumbai DC power failure", declare_dr=true and clicks Launch. At 3:41 PM — 1 hour 50 minutes after launch, well within the 4-hour RTO — the health check workflow confirms all Tier-1 services are running on Chennai infrastructure, DNS has resolved to Chennai IPs, and the first test transaction through the CBS completes successfully. Divya sends the AAP job link to the CISO. RBI receives the RTO evidence report: 1h 50min — beating the 4-hour mandate by over 2 hours.

❗ 3. Problem Statement

  • 120-page DR runbook requires experienced engineers to interpret and execute — one wrong step (e.g., opening the Data Guard standby before cancelling redo apply) corrupts the standby database.
  • No dependency ordering enforcement — applications started before their database is ready fail silently; manual coordination via conference bridge adds 1–2 hours to RTO.
  • DNS failover is manual — updating 40+ DNS records one-by-one in the Chennai DNS server takes 45 minutes and is error-prone.
  • No health gate between stages — load balancers get reconfigured to point to Chennai app servers before those servers are even started, causing connection storms.
  • DR readiness not monitored daily — the first signal that something is wrong with the DR site (Data Guard lag, failed replication, mis-configured Chennai network) comes during the actual DR drill or worse, a real disaster.
  • No RTO clock — nobody precisely tracks when each step completed, making post-DR RTO reporting to RBI an exercise in guesswork and optimistic rounding.
  • Failback (returning to Mumbai after recovery) has no runbook at all — it's always improvised, taking 12+ hours and causing additional downtime.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. CISO declares DR event. NOC opens 120-page Word document runbook.
  2. 12 engineers split across conference bridge: DBA team handles Oracle, network team handles DNS, app team handles application startup, middleware team handles Apache/Tomcat.
  3. DBA manually SSHes Chennai Oracle standby, executes Data Guard switchover commands in exact sequence — any mistake corrupts the standby.
  4. Network team manually updates 40+ DNS A records in the Chennai DNS server using the web console — one-by-one, with manual verification after each.
  5. App team manually starts application services on Chennai servers in the correct order — usually forgetting the startup dependency chain, causing failures that require restart.
  6. LB team manually reconfigures HAProxy/F5 pools to point to Chennai app servers.
  7. Health verification: each team manually checks their own layer — no unified "DR is up" confirmation for the CISO.
  8. RTO clock: somebody retrospectively reconstructs the timeline from chat messages and email timestamps for the RBI report.

🛠️ 6. Automated Solution Design

The DR automation is built as an 8-stage sequenced AAP Workflow, where each stage must pass its health gate before the next stage begins. This enforces the correct dependency ordering (DB before App, App before LB) that the manual runbook could not reliably enforce under pressure.

StageOperationHealth GateEst. Duration
0 — Pre-flightValidate Chennai DR readiness: network reachability, Data Guard lag, disk space, service statusesAll pre-flight checks pass before any change5 min
1 — Data Guard SwitchoverOracle DG switchover CBS/NACH/Trade DBs from Mumbai (now unavailable) to Chennai standby — promote to primaryOracle DB open and accepting connections on Chennai15–30 min
2 — PostgreSQL FailoverPromote PostgreSQL streaming replica (PayGW, Onboarding DBs) to primary on Chennaipg_isready + test query succeeds on Chennai PG5 min
3 — DNS FailoverUpdate all banking application DNS A records to point to Chennai IPs — using nsupdate or F5 GTM APIDNS resolution for each FQDN returns Chennai IP from external resolver5–10 min
4 — Middleware StartStart Apache HTTPD, HAProxy, and messaging middleware on Chennai app tier (in order)Service active + port listening on each middleware host5 min
5 — Application StartStart all 14 banking applications on Chennai app servers in dependency order (CBS first, then dependent apps)Project 5 health check (all 5 layers) passes per application20–30 min
6 — Load Balancer CutoverReconfigure HAProxy/F5 LTM pools from Mumbai backend servers to Chennai servers; enable Chennai VIPsLB health check confirms all pool members active on Chennai5 min
7 — End-to-End ValidationRun synthetic transactions through the full stack (DNS → LB → App → DB) from an external perspectiveAll synthetic transactions succeed; AAP sends "DR ACTIVE" notification5 min

⚙️ 8. Ansible & AAP Components Used

Core Ansible Components

  • Modules: ansible.builtin.shell, ansible.builtin.command, ansible.builtin.uri, ansible.builtin.wait_for, ansible.builtin.systemd, ansible.builtin.template, ansible.builtin.nsupdate
  • Roles: dr_preflight, dr_dataguard_switchover, dr_postgres_promote, dr_dns_failover, dr_middleware_start, dr_app_start, dr_lb_cutover, dr_validate_e2e, dr_rto_report, dr_failback
  • Vault: Oracle sysdba passwords, PostgreSQL superuser, F5 API credentials, DNS TSIG key, AWS Route53 API key
  • block/rescue/always: rescue triggers automatic rollback attempt; always generates the partial RTO report even on failure
  • Magic variable ansible_date_time.epoch for RTO clock at each stage
  • delegate_to extensively — DR orchestration touches Mumbai hosts (pre-flight only), Chennai hosts (all changes), and localhost (DNS API, LB API calls)

Red Hat AAP Components

  • AAP Controller location: Hosted in Chennai DR site (or cloud) — NOT in Mumbai primary, which may be unavailable during a real DR event. AAP must be reachable when primary DC is down.
  • Execution Nodes: Dedicated execution nodes in Chennai — job execution must not depend on Mumbai connectivity
  • Job Templates: DR-Preflight-Check, DR-Stage1-DataGuard, DR-Stage2-PostgreSQL, DR-Stage3-DNS, DR-Stage4-Middleware, DR-Stage5-Apps, DR-Stage6-LB, DR-Stage7-Validate, DR-RTO-Report, DR-Failback-Pipeline
  • Workflow: DR-Activate-Chennai-Full (all stages chained with health gate approval nodes between Stages 5 and 6)
  • Survey: dr_reason (text), declare_dr (bool), skip_approval_gates (bool — emergency override), dr_scope (full / db-only / app-only)
  • RBAC: Only CISO, CTO, and NOC-DR-Authorized team can launch DR workflows — not general engineers
  • Notification: Every stage completion → Slack #dr-war-room + PagerDuty incident update + SMS to CISO via Twilio
  • Schedule: DR-Preflight-Check daily 07:00 IST — continuous readiness monitoring

💻 11. Complete Project Code (Line-by-Line Explained)

Role: dr_preflight — Daily DR Readiness Check

roles/dr_preflight/tasks/main.yml
---
- name: Record DR preflight start time
  ansible.builtin.set_fact:
    preflight_start_epoch: "{{ ansible_date_time.epoch | int }}"

- name: Check Chennai network connectivity — all DR hosts reachable
  ansible.builtin.wait_for:
    host: "{{ hostvars[item].ansible_host }}"
    port: 22
    timeout: 10
    state: started
  loop: "{{ groups['chennai_all'] }}"
  delegate_to: localhost
  register: connectivity_checks
  failed_when: false

- name: Identify unreachable Chennai hosts
  ansible.builtin.set_fact:
    unreachable_dr_hosts: >-
      {{ connectivity_checks.results
         | selectattr('failed', 'equalto', true)
         | map(attribute='item')
         | list }}

- name: Fail preflight if any critical Chennai host is unreachable
  ansible.builtin.fail:
    msg: >-
      DR READINESS FAILURE: The following Chennai DR hosts are unreachable via SSH:
      {{ unreachable_dr_hosts | join(', ') }}.
      DR activation cannot proceed until connectivity is restored.
  when: unreachable_dr_hosts | length > 0

- name: Check Oracle Data Guard redo apply lag on Chennai standby
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     {{ oracle_home }}/bin/sqlplus -S / as sysdba << 'EOF'
     SELECT FLOOR(VALUE/1000) AS LAG_SECONDS
     FROM V\$DATAGUARD_STATS
     WHERE NAME = 'apply lag';
     EXIT;
EOF"
  register: dg_lag_check
  changed_when: false
  no_log: false
  become: true
  become_user: "{{ oracle_user }}"
  delegate_to: "{{ groups['chennai_oracle_standby'][0] }}"

- name: Parse Data Guard lag seconds
  ansible.builtin.set_fact:
    dg_lag_seconds: >-
      {{ dg_lag_check.stdout_lines
         | select('match', '^[0-9]+$')
         | list | first | default('9999') | int }}

- name: Alert if Data Guard lag exceeds acceptable threshold
  ansible.builtin.fail:
    msg: >-
      DR READINESS WARNING: Oracle Data Guard apply lag is {{ dg_lag_seconds }} seconds
      (threshold: {{ max_acceptable_dg_lag_seconds }} seconds).
      RPO of 1 hour is at risk if DR is declared now.
      Investigate replication delay before activating DR.
  when: dg_lag_seconds | int > max_acceptable_dg_lag_seconds | int

- name: Check Chennai disk space on all critical mount points
  ansible.builtin.shell: df -h / /opt /var --output=pcent | tail -n +2 | tr -dc '0-9\n' | sort -rn | head -1
  register: chennai_disk_check
  delegate_to: "{{ item }}"
  loop: "{{ groups['chennai_app_tier'] }}"
  changed_when: false

- name: Verify PostgreSQL streaming replication lag on Chennai replica
  ansible.builtin.shell: >
    PGPASSWORD={{ vault_pg_superuser_pass }}
    psql -U postgres -h localhost -p {{ pg_port }} -c
    "SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))::INT AS lag_seconds;"
    --tuples-only --no-align
  register: pg_replication_lag
  delegate_to: "{{ groups['chennai_postgres_replica'][0] }}"
  changed_when: false
  no_log: true

- name: Set DR readiness status
  ansible.builtin.set_fact:
    dr_readiness:
      status: "READY"
      dg_lag_seconds: "{{ dg_lag_seconds }}"
      pg_replication_lag_seconds: "{{ pg_replication_lag.stdout | default('N/A') | trim }}"
      unreachable_hosts: "{{ unreachable_dr_hosts }}"
      checked_at: "{{ ansible_date_time.iso8601 }}"
Line-by-Line Explanation
delegate_to: localhost for connectivity checks — Network connectivity to Chennai is tested from the Ansible control node (which is ideally in the Chennai DC or cloud), not from the Mumbai production servers which may be unavailable during actual DR. The control node reaching Chennai is the correct perspective for DR readiness.
V$DATAGUARD_STATS where NAME = 'apply lag' — Oracle Data Guard's dynamic view that shows how far behind the standby is from the primary in terms of redo application. The value is in "seconds" format. During normal operation, synchronous DG (MAXAVAILABILITY mode) should show near-zero lag. A high lag means the RPO guarantee is at risk — if primary fails now, data up to lag_seconds of transactions would be lost.
pg_last_xact_replay_timestamp() — PostgreSQL's built-in function that returns the timestamp of the last transaction replayed on the streaming replica. Subtracting from now() gives the replication lag in seconds. Zero or near-zero means the replica is current; high lag means data loss risk at failover.
This role runs daily at 07:00 IST even when no DR is happening. Continuous readiness monitoring means the first sign of DG lag, unreachable hosts, or disk space issues on the DR site is caught in the morning report — not during an actual disaster when there's no time to troubleshoot.

Role: dr_dataguard_switchover — Oracle Data Guard Failover

roles/dr_dataguard_switchover/tasks/main.yml
---
- name: Record Data Guard switchover start time for RTO clock
  ansible.builtin.set_fact:
    dg_switchover_start: "{{ ansible_date_time.epoch | int }}"

- name: Check current Data Guard role on Chennai standby
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     echo 'SELECT DATABASE_ROLE FROM V\$DATABASE;' |
     {{ oracle_home }}/bin/sqlplus -S / as sysdba"
  register: dg_role_check
  changed_when: false
  become: true
  become_user: "{{ oracle_user }}"

- name: Skip DG switchover if database is already primary
  ansible.builtin.meta: end_host
  when: "'PRIMARY' in dg_role_check.stdout"

- name: Cancel redo apply on standby before promoting (mandatory step)
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     echo 'ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;' |
     {{ oracle_home }}/bin/sqlplus -S / as sysdba"
  register: cancel_apply_result
  changed_when: true
  become: true
  become_user: "{{ oracle_user }}"

- name: Wait 30 seconds for redo apply to fully stop
  ansible.builtin.pause:
    seconds: 30

- name: Activate standby database as new primary (RESETLOGS)
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     echo 'ALTER DATABASE ACTIVATE STANDBY DATABASE;' |
     {{ oracle_home }}/bin/sqlplus -S / as sysdba"
  register: activate_result
  changed_when: true
  become: true
  become_user: "{{ oracle_user }}"

- name: Open database with RESETLOGS after activation
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     echo 'ALTER DATABASE OPEN RESETLOGS;' |
     {{ oracle_home }}/bin/sqlplus -S / as sysdba"
  register: open_db_result
  changed_when: true
  become: true
  become_user: "{{ oracle_user }}"

- name: Wait for Oracle listeners to be ready for connections
  ansible.builtin.wait_for:
    host: "{{ ansible_host }}"
    port: 1521
    timeout: "{{ dg_wait_timeout }}"
    delay: 10
    state: started

- name: Validate database is open and accepting connections
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     echo 'SELECT STATUS FROM V\$INSTANCE;' |
     {{ oracle_home }}/bin/sqlplus -S / as sysdba"
  register: db_status_check
  changed_when: false
  become: true
  become_user: "{{ oracle_user }}"
  retries: 10
  delay: 30
  until: "'OPEN' in db_status_check.stdout"

- name: Record Data Guard switchover completion time
  ansible.builtin.set_fact:
    dg_switchover_duration_min: >-
      {{ ((ansible_date_time.epoch | int) - dg_switchover_start | int) / 60 | round(1) }}

- name: Update RTO clock with stage 1 completion
  ansible.builtin.set_fact:
    rto_clock:
      stage_1_dg_switchover:
        started_at: "{{ dg_switchover_start }}"
        completed_at: "{{ ansible_date_time.epoch | int }}"
        duration_min: "{{ dg_switchover_duration_min }}"
        status: "COMPLETE"
Line-by-Line Explanation
Skip if already PRIMARY — Idempotency in DR is critical. If the workflow is re-run after a partial failure, we must not re-execute an already-completed DG switchover — doing so on an already-primary database could corrupt it. The role-entry check makes the Data Guard switchover safe to re-run.
RECOVER MANAGED STANDBY DATABASE CANCEL — This is the mandatory first step before activating a standby. It stops the managed recovery process (MRP) that was applying redo from the now-unavailable primary. If MRP is not cancelled cleanly before activation, Oracle may raise ORA-16649 (possible failover occurred) or leave the database in an inconsistent state. The 30-second pause gives Oracle time to complete the cancel gracefully.
ALTER DATABASE ACTIVATE STANDBY DATABASE — This single SQL statement is the heart of the failover. It converts the physical standby into a standalone primary by applying any remaining redo in the standby redo logs and opening the database for read-write transactions. Note: this is ACTIVATE (for lost-primary failover scenarios) not SWITCHOVER (graceful planned switchover when primary is available). Since Mumbai DC is offline, we use ACTIVATE.
ALTER DATABASE OPEN RESETLOGS — Required after ACTIVATE to open the database for connections. RESETLOGS resets the online redo log sequence numbers — any old redo logs from the previous primary become invalid after this point, which is correct behaviour since the old primary is offline and we're starting fresh on the new primary.
retries: 10 / delay: 30 / until: "'OPEN' in db_status_check.stdout" — Oracle takes 30–300 seconds to open a large database after RESETLOGS (extent map construction, undo segment rollback, etc.). We poll every 30 seconds up to 5 minutes before declaring failure — far more reliable than a fixed pause that's either too short (fails) or too long (wastes precious RTO minutes).

Role: dr_postgres_promote — PostgreSQL Replica Promotion

roles/dr_postgres_promote/tasks/main.yml
---
- name: Record PostgreSQL promotion start time
  ansible.builtin.set_fact:
    pg_promote_start: "{{ ansible_date_time.epoch | int }}"

- name: Check current PostgreSQL recovery status (is it still a standby?)
  ansible.builtin.shell: >
    PGPASSWORD={{ vault_pg_superuser_pass }}
    psql -U postgres -h localhost -p {{ pg_port }}
    -c "SELECT pg_is_in_recovery();"
    --tuples-only --no-align
  register: pg_recovery_check
  changed_when: false
  no_log: true

- name: Skip PostgreSQL promotion if already primary
  ansible.builtin.meta: end_host
  when: "'f' in pg_recovery_check.stdout"

- name: Promote PostgreSQL replica to primary using pg_promote() function
  ansible.builtin.shell: >
    PGPASSWORD={{ vault_pg_superuser_pass }}
    psql -U postgres -h localhost -p {{ pg_port }}
    -c "SELECT pg_promote(wait => true, wait_seconds => 60);"
    --tuples-only --no-align
  register: pg_promote_result
  changed_when: true
  no_log: true

- name: Wait for PostgreSQL to complete promotion and accept write connections
  ansible.builtin.shell: >
    PGPASSWORD={{ vault_pg_superuser_pass }}
    psql -U postgres -h localhost -p {{ pg_port }}
    -c "SELECT pg_is_in_recovery();"
    --tuples-only --no-align
  register: pg_promote_verify
  changed_when: false
  retries: 12
  delay: 10
  until: "'f' in pg_promote_verify.stdout"
  no_log: true

- name: Validate a write transaction is possible (promotion fully complete)
  ansible.builtin.shell: >
    PGPASSWORD={{ vault_pg_superuser_pass }}
    psql -U postgres -h localhost -p {{ pg_port }}
    -d {{ db_name }}
    -c "CREATE TEMP TABLE dr_test_write (id INT); DROP TABLE dr_test_write;"
    --tuples-only --no-align
  register: pg_write_test
  changed_when: false
  no_log: true

- name: Update RTO clock with PostgreSQL promotion
  ansible.builtin.set_fact:
    rto_clock: >-
      {{ rto_clock | default({}) | combine({
        'stage_2_pg_promote': {
          'duration_min': ((ansible_date_time.epoch | int - pg_promote_start | int) / 60) | round(1),
          'status': 'COMPLETE'
        }
      }) }}
Line-by-Line Explanation
pg_is_in_recovery() — Returns t (true) if the database is currently a streaming replica in recovery mode, or f (false) if it's a primary. This is the idempotency check — if already primary ('f'), we skip promotion safely.
SELECT pg_promote(wait => true, wait_seconds => 60) — PostgreSQL 12+ built-in function to trigger replica promotion. The wait => true makes the SQL call block until promotion is complete (up to wait_seconds), making the Ansible task synchronous — it won't return until PostgreSQL has finished promoting. Older approach (touching pg_promote signal file) is asynchronous and requires separate polling.
Write validation with CREATE TEMP TABLE ... DROP TABLE — We don't just check that promotion completed; we actually attempt a write transaction to confirm the database accepts writes. A replica that partially promoted (e.g., promotion completed but WAL writer not started) might report pg_is_in_recovery() = f but still reject writes with "read-only transaction". This test catches that edge case.
rto_clock | combine({...}) — The Jinja2 combine filter merges a new stage entry into the existing rto_clock dict, building up a cumulative per-stage RTO timeline throughout the workflow. The final report role reads this dict to produce the RTO report with actual duration at each stage.

Role: dr_dns_failover — Fleet-Wide DNS Record Update

roles/dr_dns_failover/tasks/main.yml
---
- name: Record DNS failover start time
  ansible.builtin.set_fact:
    dns_failover_start: "{{ ansible_date_time.epoch | int }}"

- name: Define DNS records to update — Mumbai → Chennai IP mapping
  ansible.builtin.set_fact:
    dns_failover_records:
      - fqdn: netbanking.securebank.in
        old_ip: 10.20.1.100
        new_ip: 10.30.1.100
      - fqdn: mobileapi.securebank.in
        old_ip: 10.20.1.101
        new_ip: 10.30.1.101
      - fqdn: cbs-internal.securebank.in
        old_ip: 10.20.2.50
        new_ip: 10.30.2.50
      - fqdn: paymentgw.securebank.in
        old_ip: 10.20.6.50
        new_ip: 10.30.6.50
      - fqdn: nach.internal.securebank.in
        old_ip: 10.20.7.50
        new_ip: 10.30.7.50

- name: Update DNS A records using nsupdate (dynamic DNS update)
  ansible.builtin.nsupdate:
    key_name: "{{ dns_tsig_key_name }}"
    key_secret: "{{ vault_dns_tsig_secret }}"
    key_algorithm: hmac-sha256
    server: "{{ item[1].server }}"
    zone: "{{ item[1].zone }}"
    record: "{{ item[0].fqdn.split('.')[0] }}"
    type: A
    value: "{{ item[0].new_ip }}"
    ttl: "{{ dns_ttl }}"
    state: present
  loop: "{{ dns_failover_records | product(internal_dns_zones) | list }}"
  loop_control:
    label: "{{ item[0].fqdn }} → {{ item[0].new_ip }}"
  delegate_to: localhost

- name: Verify DNS resolution from external perspective after update
  ansible.builtin.command: "dig +short {{ item.fqdn }} @{{ internal_dns_zones[0].server }}"
  loop: "{{ dns_failover_records }}"
  loop_control:
    label: "{{ item.fqdn }}"
  register: dns_verify_results
  changed_when: false
  delegate_to: localhost
  retries: 6
  delay: 10
  until: item.new_ip in dns_verify_results.stdout

- name: Fail if any FQDN is not resolving to Chennai IP after DNS update
  ansible.builtin.fail:
    msg: >-
      DNS FAILOVER INCOMPLETE: {{ item.item.fqdn }} still resolving to
      {{ item.stdout }} instead of expected Chennai IP {{ item.item.new_ip }}.
      DNS propagation may be delayed or nsupdate failed.
  loop: "{{ dns_verify_results.results }}"
  loop_control:
    label: "{{ item.item.fqdn }}"
  when: item.item.new_ip not in item.stdout

- name: Update RTO clock with DNS failover completion
  ansible.builtin.set_fact:
    rto_clock: >-
      {{ rto_clock | default({}) | combine({
        'stage_3_dns_failover': {
          'records_updated': dns_failover_records | length,
          'duration_min': ((ansible_date_time.epoch | int - dns_failover_start | int) / 60) | round(1),
          'status': 'COMPLETE'
        }
      }) }}
Line-by-Line Explanation
ansible.builtin.nsupdate — The native Ansible module for RFC 2136 Dynamic DNS updates. Uses TSIG (Transaction SIGnature) authentication (key_name + key_secret) so the DNS server accepts programmatic record updates from authorized sources only. The TSIG secret is Vault-encrypted — never hardcoded in the playbook.
product(internal_dns_zones) | list — Cartesian product of DNS records × DNS zones, producing a loop over every combination. If there are 10 DNS records and 2 zones (primary and secondary DNS servers), the loop runs 20 iterations — updating both authoritative DNS servers for every record in one clean loop construct without nested loops.
ttl: "{{ dns_ttl }}" where dns_ttl: 60 — Setting a 60-second TTL during DR means any client that queries DNS will get fresh Chennai IPs within 60 seconds of the update, even if their local DNS resolver has the old Mumbai IP cached. Banks often pre-set low TTLs on critical FQDNs (30–300 seconds) in anticipation of DR — setting it low only at failover time adds propagation delay equal to whatever the previous high TTL was.
dig +short {{ item.fqdn }} @{{ dns_server }} — We verify DNS resolution by directly querying the authoritative DNS server (bypassing any resolver cache) using dig with explicit server specification. The +short flag returns only the IP address, making it easy to check with item.new_ip in dns_verify_results.stdout. The retry loop handles DNS propagation delay — up to 6 × 10 seconds = 60 seconds.

Role: dr_failback — Return to Mumbai Primary (Overview)

roles/dr_failback/tasks/main.yml (abbreviated — key concepts)
---
# Failback is the reverse of DR activation — returns operations to Mumbai
# when the primary site is restored.
# Critical: failback is ALWAYS done during a planned maintenance window
# Never failback under time pressure — Chennai can run indefinitely.

- name: Confirm Mumbai DC is fully restored and healthy before failback
  ansible.builtin.wait_for:
    host: "{{ hostvars[item].ansible_host }}"
    port: 22
    timeout: 10
  loop: "{{ groups['mumbai_oracle_primary'] }}"
  delegate_to: localhost

- name: Re-establish Oracle Data Guard replication (Chennai → Mumbai)
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     {{ oracle_home }}/bin/rman
     target sys/{{ vault_oracle_sys_pass }}@{{ chennai_tns }}
     auxiliary sys/{{ vault_oracle_sys_pass }}@{{ mumbai_tns }} <<'EOF'
     DUPLICATE TARGET DATABASE FOR STANDBY FROM ACTIVE DATABASE
     DORECOVER
     SPFILE;
EOF"
  no_log: true
  become: true
  become_user: "{{ oracle_user }}"
  async: 21600
  poll: 60

- name: Perform planned switchover back to Mumbai (graceful — no data loss)
  ansible.builtin.shell: >
    su - {{ oracle_user }} -c
    "export ORACLE_HOME={{ oracle_home }};
     export ORACLE_SID={{ oracle_sid }};
     echo 'ALTER DATABASE COMMIT TO SWITCHOVER TO STANDBY WITH SESSION SHUTDOWN;' |
     {{ oracle_home }}/bin/sqlplus -S / as sysdba"
  become: true
  become_user: "{{ oracle_user }}"
  delegate_to: "{{ groups['chennai_oracle_standby'][0] }}"

- name: Revert DNS records back to Mumbai IPs
  ansible.builtin.nsupdate:
    key_name: "{{ dns_tsig_key_name }}"
    key_secret: "{{ vault_dns_tsig_secret }}"
    server: "{{ item[1].server }}"
    zone: "{{ item[1].zone }}"
    record: "{{ item[0].fqdn.split('.')[0] }}"
    type: A
    value: "{{ item[0].old_ip }}"
    ttl: 300
    state: present
  loop: "{{ dns_failover_records | product(internal_dns_zones) | list }}"
  loop_control:
    label: "{{ item[0].fqdn }} → {{ item[0].old_ip }}"
  delegate_to: localhost
Key Failback Design Principles
Failback uses COMMIT TO SWITCHOVER TO STANDBY (graceful switchover) NOT ACTIVATE STANDBY DATABASE (emergency failover). Because Mumbai is restored and reachable, we perform a clean planned switchover — both databases negotiate the role swap with zero data loss. This is the critical difference between failover (emergency, possible data loss) and switchover (planned, zero data loss).
Re-establishing DG replication uses RMAN DUPLICATE FOR STANDBY FROM ACTIVE DATABASE — this refreshes the Mumbai standby from the currently-running Chennai primary without needing a backup, using the network to copy only changed blocks. This is the most efficient way to re-create a standby after a failover has occurred.
DNS TTL set back to 300 on failback — during DR the TTL was set to 60 seconds for fast propagation. After returning to Mumbai, we restore a longer TTL (300 seconds / 5 minutes) to reduce DNS query load on the authoritative servers.
The "never failback under pressure" principle — Chennai can run the bank indefinitely. The failback is always a planned maintenance window, never an emergency. This means the bank has time to properly verify Mumbai is fully restored, re-establish DG replication, validate the data is current, and schedule the cutover — avoiding a second incident caused by a rushed failback.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: What is the difference between Oracle Data Guard SWITCHOVER and FAILOVER (ACTIVATE)?
SWITCHOVER is a graceful, planned operation where both the primary and standby are available and cooperate to exchange roles — zero data loss guaranteed, original primary becomes a standby. FAILOVER (using ACTIVATE STANDBY DATABASE) is an emergency operation when the primary is unavailable — the standby promotes itself unilaterally, with potential for small data loss (any redo not yet shipped before the outage). In our DR scenario, Mumbai DC is completely offline, so we use ACTIVATE. When we failback later (Mumbai restored), we use SWITCHOVER — both sites are available, and we can do it cleanly.
Q: How do you ensure the AAP Controller itself is available during a Mumbai DC disaster?
AAP Controller is hosted in Chennai DC or an AWS ap-south-1 cloud region — never in Mumbai primary. This is the most important architectural decision in the entire DR automation project: the tool that orchestrates DR must not be in the site that's down. Execution Nodes are in Chennai DC for low-latency SSH to Chennai hosts. A second set of lightweight Execution Nodes in Mumbai handles routine Production jobs, but DR jobs use Chennai/cloud Execution Nodes exclusively.
Q: Walk me through what happens if the DR activation workflow fails at Stage 5 (App Start). What does the automation do?
Stage 5 has an explicit fail with "DR ACTIVATION BLOCKED" message if any application's health check doesn't pass. The workflow's failure edge (not shown but configured in AAP) sends a P1 PagerDuty alert with the specific failing application and the AAP job URL. Crucially, Stage 6 (LB cutover) has NOT run — no traffic is being sent to Chennai yet. The bank is in a degraded state (DBs running on Chennai, apps partially up, traffic still failing) but the situation is at least stable. The on-call DBA and app team investigate the specific failing app, manually resolve the issue, and re-run the Stage 5 job template before approving Stage 6.

Architecture & Production Questions

Q: How do you handle application configuration files that contain hardcoded Mumbai DC IPs?
This is the most common DR automation failure in practice. The correct architecture (enforced in Project 1's deployment): all database connection strings and internal service URLs in application config files use DNS FQDNs (managed via Project 9's DNS failover role) rather than hardcoded IPs. When DNS switches to Chennai, the apps automatically resolve to Chennai targets at next connection. Any app with hardcoded IPs is flagged in a configuration audit (related to Project 13's drift detection) and required to be updated before the next DR drill.
Q: What is the RPO implication of Oracle Data Guard running in MAXAVAILABILITY vs MAXPROTECTION mode?
MAXPROTECTION: synchronous redo shipping — every transaction is confirmed committed only after the standby acknowledges it. Zero data loss (RPO=0) but primary halts if the standby becomes unreachable. MAXAVAILABILITY: synchronous when possible, falls back to ASYNC if standby is unavailable — zero data loss when standby is healthy, some loss possible if it goes out of sync. MAXPERFORMANCE: async shipping — primary never waits for standby, lowest impact on throughput but highest potential data loss. SecureBank uses MAXAVAILABILITY — the most common production choice for banks that need near-zero RPO without risking primary availability from a standby network glitch.
Q: How do you test DR automation without impacting production? What is a "non-disruptive DR test"?
A non-disruptive DR test activates the Chennai DR site without switching production traffic. Stages 0–5 run (DB promote, DNS not changed, apps start on Chennai), and we run synthetic transactions directly against the Chennai app servers using their internal IPs — bypassing DNS. We measure timing, validate health, generate the RTO report — all the evidence RBI requires — without the DNS cutover (Stage 3) or LB cutover (Stage 6) that would impact live customers. The workflow has a survey flag dr_scope=drill-no-traffic-cutover that skips Stages 3 and 6, enabling quarterly non-disruptive DR tests supplementing the annual full drill.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • AAP Controller must be outside the primary DC — orchestrating DR from within the site that's down is the most common DR automation architecture mistake.
  • Dependency ordering in app startup is the #1 source of RTO waste in manual DR drills — automation enforces it perfectly every time.
  • ACTIVATE vs SWITCHOVER — knowing which Oracle DG command to use (emergency vs planned) is critical; using the wrong one wastes 30+ minutes or causes data inconsistency.
  • The RTO clock starts at DR declaration, not at AAP job launch — a few minutes' difference matters for RBI compliance reporting.

Common Mistakes

  • Hosting AAP in the primary DC — the orchestration tool fails precisely when you need it most.
  • Starting app tier before DB is ready — causes connection storms and app startup failures that add 30+ minutes to RTO.
  • Not verifying DNS resolution after nsupdate — the update may succeed but resolver caching can delay propagation longer than expected.
  • Using SWITCHOVER when primary is unavailable — SWITCHOVER requires primary cooperation; use ACTIVATE for unplanned outages.

Production Best Practices

  • Run quarterly non-disruptive DR tests (Stages 0–5 without DNS/LB cutover) — annual full drills are too infrequent to catch configuration drift.
  • Keep DNS TTLs low (60–300s) on all banking FQDNs permanently — not just at DR time — so that when DNS failover runs, propagation is fast.
  • Test the failback as carefully as the failover — an untested failback procedure is almost guaranteed to cause additional downtime.
  • Monitor Data Guard lag daily (the dr_preflight schedule) — discovering 6-hour lag during an actual DR event when Mumbai is on fire is exactly the wrong time.

Resume Points

  • Designed and implemented a fully automated, 8-stage Disaster Recovery activation workflow using Red Hat AAP, reducing SecureBank's RTO from 7+ hours (manual runbook) to 1h 50min — achieving RBI-mandated 4-hour RTO compliance for 14 Tier-1 banking applications across Mumbai and Chennai data centres.
  • Architected an Oracle Data Guard failover and PostgreSQL replica promotion automation pipeline with dependency-ordered application startup and health-gated stage progression, eliminating the 12-engineer conference-bridge coordination previously required for DR activation.
  • Built automated DR readiness monitoring (daily Oracle DG lag and Chennai connectivity checks) and end-to-end RTO clock reporting with stage-by-stage evidence, producing RBI Business Continuity Policy §6.2 compliant audit artefacts directly from the AAP job output.
