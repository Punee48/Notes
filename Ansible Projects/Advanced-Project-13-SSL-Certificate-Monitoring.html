Project 13: SSL Certificate Expiry Monitoring, Chain Validation & Compliance Dashboard

ABC Global Bank serves customers over HTTPS across 847 SSL endpoints — internet banking portal, mobile banking API, branch connectivity, SWIFT messaging, and inter-service communication. Each endpoint has an SSL certificate with an expiry date. An expired certificate causes browsers to display "Your connection is not private" — customers cannot log in, regulators raise findings, and the bank's reputation suffers. Beyond expiry, certificate chain breaks, weak cipher suites, and SHA-1 signatures are equally dangerous. This project automates complete SSL estate monitoring: expiry tracking, certificate chain validation, cipher suite compliance, SAN/CN validation, and a weekly SSL compliance dashboard for the CISO — covering every certificate on every server, in every keystore.

🏦 1. The Banking Story

Setting: ABC Global Bank has 847 SSL-enabled endpoints: 234 external-facing (internet banking, mobile APIs, payment gateways) and 613 internal (service-to-service, database connections, admin portals). Certificates are issued by the bank's internal CA for internal services, and by DigiCert/Sectigo for external services. Teams managing them: Network Security (external certs), Linux team (Apache/Tomcat), Windows team (IIS), Oracle DBA team (Oracle wallet), and the Java team (JKS keystores).

Incident 1 — The Expired Internet Banking Cert: At 00:01 AM on April 15th, the SSL certificate for netbanking.abcbank.in expired. It had been issued exactly 1 year ago and nobody had set a renewal reminder. By 06:30 AM when customers started their morning banking, every browser showed the red "Not Secure" warning. Safari and Chrome blocked access entirely. 140,000 customers could not access internet banking for 4 hours while the cert was emergency-renewed. RBI was notified. The bank paid ₹45 lakh for emergency certificate issuance with 2-hour SLA. Regulatory finding: "Inadequate certificate lifecycle management."

Incident 2 — The Broken Chain: A middleware team replaced the Apache SSL certificate on the payment API server but only uploaded the leaf certificate — not the intermediate CA certificate. Modern browsers (Chrome, Firefox) worked fine (they cached the intermediate from a previous connection). But the mobile banking app, which performed strict certificate chain validation, failed with "SSL Handshake Error." 23,000 mobile banking users could not make payments for 6 hours. Root cause: incomplete certificate chain (missing intermediate).

Incident 3 — The SHA-1 Audit Finding: A PCI-DSS QSA scan found 12 internal service certificates still using SHA-1 signatures (deprecated since 2017, prohibited in PCI-DSS v4.0). This was a "Critical" finding requiring remediation within 30 days.

The Ask: "Monitor every SSL certificate on every server. Alert 60 days before expiry. Validate the full chain (leaf + intermediate + root). Check cipher suites. Find all SHA-1 certs. Give the CISO a weekly report of our entire SSL estate."

Certificate Chain — Why It Must Be Complete
SSL certificates are not standalone — they form a chain:
Root CA Certificate (trusted by browsers/OS) → Intermediate CA Certificate → Leaf/Server Certificate

For SSL to work, the server must present ALL certificates in the chain (except the root, which the client already trusts). If the intermediate is missing:
• Browsers with cached intermediate: works (temporarily)
• Mobile apps with strict chain validation: fails with "Unable to verify the first certificate"
• Curl with default settings: may fail
• OpenSSL s_client: shows "verify error:num=20:unable to get local issuer certificate"

We validate chain completeness using openssl s_client -connect host:port -showcerts and counting the number of certificates in the PEM chain.

PlaybookScheduleScope

Two-Track Approach: We monitor SSL certificates two ways — network-level (connect to the endpoint over the network like a browser does, check what cert is actually served) and file-level (SSH to the server, read the keystore/PEM file directly). Network-level catches production configuration. File-level finds certs that are on the server but not yet deployed, expired certs that were never cleaned up, and certs in keystores that may have stale entries.

Role 1: ssl_network_check — Endpoint Certificate Monitoring

roles/ssl_network_check/tasks/check_endpoint_expiry.yml
---
# =====================================================================
# Check SSL certificate expiry by connecting to each endpoint
# This is the "browser view" — checks what's actually served
# =====================================================================

- name: Check SSL certificate for each endpoint
  ansible.builtin.shell:
    cmd: |
      # Connect to endpoint and get certificate expiry date
      EXPIRY=$(echo | timeout 10 openssl s_client \
        -connect {{ item.fqdn }}:{{ item.port }} \
        -servername {{ item.fqdn }} \
        2>/dev/null \
        | openssl x509 -noout -enddate 2>/dev/null \
        | cut -d= -f2)

      if [ -z "$EXPIRY" ]; then
        echo "CONNECTION_FAILED"
        exit 1
      fi

      # Calculate days until expiry
      EXPIRY_EPOCH=$(date -d "$EXPIRY" +%s 2>/dev/null)
      NOW_EPOCH=$(date +%s)
      DAYS_LEFT=$(( (EXPIRY_EPOCH - NOW_EPOCH) / 86400 ))

      # Get certificate details
      CERT_INFO=$(echo | timeout 10 openssl s_client \
        -connect {{ item.fqdn }}:{{ item.port }} \
        -servername {{ item.fqdn }} \
        2>/dev/null \
        | openssl x509 -noout \
          -subject -issuer -dates -fingerprint -sha256 2>/dev/null)

      echo "DAYS_LEFT=$DAYS_LEFT"
      echo "EXPIRY_DATE=$EXPIRY"
      echo "$CERT_INFO"
    executable: /bin/bash
  register: ssl_check_results
  loop: "{{ ssl_endpoints }}"
  loop_control:
    label: "{{ item.fqdn }}:{{ item.port }}"
  delegate_to: localhost                     # Run from AAP node — network-level check
  changed_when: false
  failed_when: false

- name: Parse SSL check results into structured data
  ansible.builtin.set_fact:
    ssl_endpoint_status: >-
      {{ ssl_endpoint_status | default([]) + [{
        'fqdn': item.item.fqdn,
        'port': item.item.port,
        'description': item.item.description,
        'category': item.item.category,
        'priority': item.item.priority,
        'connection_failed': ('CONNECTION_FAILED' in item.stdout),
        'days_left': (item.stdout
                      | regex_search('DAYS_LEFT=(-?[0-9]+)', '\\1')
                      | first | default(-1) | int),
        'expiry_date': (item.stdout
                        | regex_search('EXPIRY_DATE=(.+)', '\\1')
                        | first | default('UNKNOWN')),
        'subject': (item.stdout
                    | regex_search('subject=(.+)', '\\1')
                    | first | default('UNKNOWN')),
        'issuer': (item.stdout
                   | regex_search('issuer=(.+)', '\\1')
                   | first | default('UNKNOWN')),
        'expected_issuer': item.item.expected_issuer,
        'issuer_match': (item.item.expected_issuer in
                         (item.stdout | regex_search('issuer=(.+)', '\\1') | first | default(''))),
        'severity': ('EXPIRED' if (item.stdout
                                   | regex_search('DAYS_LEFT=(-?[0-9]+)', '\\1')
                                   | first | default(999) | int) <= 0
                     else ('P1' if (item.stdout
                                    | regex_search('DAYS_LEFT=(-?[0-9]+)', '\\1')
                                    | first | default(999) | int) <= ssl_expiry_p1_days
                           else ('P2' if (item.stdout
                                         | regex_search('DAYS_LEFT=(-?[0-9]+)', '\\1')
                                         | first | default(999) | int) <= ssl_expiry_p2_days
                                 else ('WARN' if (item.stdout
                                                  | regex_search('DAYS_LEFT=(-?[0-9]+)', '\\1')
                                                  | first | default(999) | int)
                                                 <= (item.item.min_days_warning | default(60))
                                       else 'OK'))))
      }] }}
  loop: "{{ ssl_check_results.results }}"
  loop_control:
    label: "{{ item.item.fqdn }}"

- name: Log SSL endpoint check summary
  ansible.builtin.debug:
    msg:
      - "SSL Endpoint Check Results:"
      - "Total endpoints: {{ ssl_endpoint_status | length }}"
      - "EXPIRED: {{ ssl_endpoint_status | selectattr('severity','equalto','EXPIRED') | list | length }}"
      - "P1 (< {{ ssl_expiry_p1_days }} days): {{ ssl_endpoint_status | selectattr('severity','equalto','P1') | list | length }}"
      - "P2 (< {{ ssl_expiry_p2_days }} days): {{ ssl_endpoint_status | selectattr('severity','equalto','P2') | list | length }}"
      - "WARN (< 60 days): {{ ssl_endpoint_status | selectattr('severity','equalto','WARN') | list | length }}"
      - "Connection failures: {{ ssl_endpoint_status | selectattr('connection_failed') | list | length }}"

- name: Fire PagerDuty P1 for EXPIRED or near-expiry certificates
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "ssl-expiry-{{ item.fqdn }}-{{ item.port }}"
      payload:
        summary: >-
          {{ '🚨 EXPIRED' if item.severity == 'EXPIRED' else '🔴 EXPIRING SOON' }}:
          SSL cert for {{ item.fqdn }}:{{ item.port }} —
          {{ 'ALREADY EXPIRED' if item.severity == 'EXPIRED'
             else 'expires in ' + item.days_left | string + ' days' }}.
          {{ item.description }} — customers {{ 'CANNOT' if item.severity == 'EXPIRED' else 'WILL SOON be unable to' }} connect!
        severity: critical
        source: ansible-ssl-monitor
        custom_details:
          fqdn: "{{ item.fqdn }}"
          port: "{{ item.port }}"
          days_left: "{{ item.days_left }}"
          expiry_date: "{{ item.expiry_date }}"
          issuer: "{{ item.issuer }}"
          action_required: "Renew and deploy SSL certificate immediately"
    status_code: [202]
  loop: >-
    {{ ssl_endpoint_status
       | selectattr('severity', 'in', ['EXPIRED', 'P1'])
       | list }}
  loop_control:
    label: "{{ item.fqdn }} ({{ item.days_left }} days)"
  delegate_to: localhost
  when: ssl_endpoint_status | selectattr('severity', 'in', ['EXPIRED', 'P1']) | list | length > 0

- name: Fire PagerDuty P2 for certificates expiring within {{ ssl_expiry_p2_days }} days
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "ssl-expiry-{{ item.fqdn }}-{{ item.port }}"
      payload:
        summary: >-
          ⚠️ SSL CERT EXPIRING: {{ item.fqdn }}:{{ item.port }}
          expires in {{ item.days_left }} days ({{ item.expiry_date }}).
          Schedule renewal before customers are impacted.
        severity: error
        source: ansible-ssl-monitor
    status_code: [202]
  loop: "{{ ssl_endpoint_status | selectattr('severity', 'equalto', 'P2') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  delegate_to: localhost

🔗 9. Chain Validation Role

roles/ssl_chain_validate/tasks/validate_chain.yml
---
# =====================================================================
# SSL Certificate Chain Validation
# Validates that the full chain (leaf + intermediate + root) is present
# This is the check that would have prevented the mobile banking incident
# =====================================================================

- name: Retrieve full certificate chain from each endpoint
  ansible.builtin.shell:
    cmd: |
      # -showcerts: show ALL certificates in the chain (not just leaf)
      CHAIN=$(echo | timeout 10 openssl s_client \
        -connect {{ item.fqdn }}:{{ item.port }} \
        -servername {{ item.fqdn }} \
        -showcerts \
        2>/dev/null)

      # Count number of certificates in chain
      CERT_COUNT=$(echo "$CHAIN" | grep -c "BEGIN CERTIFICATE")

      # Check if openssl verify succeeds with system trust store
      VERIFY=$(echo "$CHAIN" \
        | openssl x509 -noout -text 2>/dev/null \
        | grep "Issuer:" | head -1)

      # Check if chain verifies cleanly
      echo "$CHAIN" | openssl x509 2>/dev/null \
        | openssl verify -CAfile /etc/pki/tls/certs/ca-bundle.crt \
          2>&1 | head -1 > /tmp/verify_{{ item.fqdn | replace('.', '_') }}.txt

      VERIFY_RESULT=$(cat /tmp/verify_{{ item.fqdn | replace('.', '_') }}.txt)

      echo "CERT_COUNT=$CERT_COUNT"
      echo "VERIFY_RESULT=$VERIFY_RESULT"
    executable: /bin/bash
  register: chain_check_results
  loop: "{{ ssl_endpoints }}"
  loop_control:
    label: "{{ item.fqdn }}:{{ item.port }}"
  delegate_to: localhost
  changed_when: false
  failed_when: false

- name: Parse chain validation results
  ansible.builtin.set_fact:
    ssl_chain_status: >-
      {{ ssl_chain_status | default([]) + [{
        'fqdn': item.item.fqdn,
        'port': item.item.port,
        'description': item.item.description,
        'cert_count': (item.stdout
                       | regex_search('CERT_COUNT=([0-9]+)', '\\1')
                       | first | default(0) | int),
        'chain_complete': (item.stdout
                           | regex_search('CERT_COUNT=([0-9]+)', '\\1')
                           | first | default(0) | int) >= 2,
        'verify_ok': ('OK' in (item.stdout
                               | regex_search('VERIFY_RESULT=(.+)', '\\1')
                               | first | default('')))
      }] }}
  loop: "{{ chain_check_results.results }}"
  loop_control:
    label: "{{ item.item.fqdn }}"

- name: Alert on incomplete certificate chains
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "ssl-chain-broken-{{ item.fqdn }}-{{ item.port }}"
      payload:
        summary: >-
          🔴 BROKEN SSL CHAIN: {{ item.fqdn }}:{{ item.port }}
          Only {{ item.cert_count }} certificate(s) in chain
          (minimum 2 required: leaf + intermediate).
          Mobile apps and strict clients WILL FAIL SSL handshake.
          This caused the 6-hour mobile banking outage.
        severity: critical
        source: ansible-ssl-chain-monitor
        custom_details:
          fqdn: "{{ item.fqdn }}"
          certs_in_chain: "{{ item.cert_count }}"
          fix: "Add intermediate CA certificate to server's SSL configuration"
    status_code: [202]
  loop: "{{ ssl_chain_status | rejectattr('chain_complete') | list }}"
  loop_control:
    label: "{{ item.fqdn }}"
  delegate_to: localhost
  when: ssl_chain_status | rejectattr('chain_complete') | list | length > 0

        -subject -issuer -dates -fingerprint

    label: "{{ item }}"

        'file': item.item.path,
        'sha1_found': 'sha1WithRSAEncryption' in item.stdout | lower or
                      'sha-1' in item.stdout | lower
      }] }}
  loop: "{{ jks_contents.results | selectattr('sha1_found', 'defined') | list }}"
  when: jks_contents is defined

🎯 15. Interview Prep

Q: What is the difference between the network-level and file-level SSL monitoring approaches?
Network-level (openssl s_client): Connects to the endpoint over the network exactly like a browser does. Checks what certificate is ACTUALLY BEING SERVED right now. Catches: expired deployed cert, wrong cert served (CN mismatch), broken chain as seen by clients, TLS protocol version negotiated.

File-level (keytool, openssl x509 -in file): SSH to the server and read the certificate files directly. Catches: certs in keystores that aren't yet deployed, expired backup certs that were never cleaned up, weak algorithms in certs that aren't currently active, inventory of all certs across all keystores for a complete estate view.

Both are necessary — network-level catches what's affecting customers NOW, file-level catches what WILL become a problem and provides the complete inventory needed for compliance reporting.
Q: How do you detect a broken certificate chain using Ansible?
We use openssl s_client -showcerts which retrieves ALL certificates sent by the server (the leaf certificate plus any intermediate CAs the server includes in the TLS handshake). We then count the number of BEGIN CERTIFICATE markers in the output:

Count = 1: Only the leaf cert — broken chain. Mobile apps and strict clients will fail.
Count = 2: Leaf + Intermediate — correct and most common.
Count = 3: Leaf + Intermediate + Root — valid but unnecessary (root is in client trust store).

Any count less than 2 triggers a P1 alert. The fix is to add the intermediate CA certificate to the server's SSL configuration — in Apache this is the SSLCertificateChainFile or concatenating intermediate into the PEM; in Tomcat it's importing the intermediate into the JKS keystore.
Q: Why is SHA-1 prohibited in banking SSL certificates and what algorithm should replace it?
SHA-1 (Secure Hash Algorithm 1) produces a 160-bit hash. In 2017, Google's Project Zero team demonstrated the first practical SHA-1 collision attack ("SHAttered") — proving two different files could produce the same SHA-1 hash. This breaks the fundamental security property of certificate signatures: an attacker could theoretically create a fraudulent certificate with the same SHA-1 signature as a legitimate one.

Regulatory prohibitions: NIST deprecated SHA-1 in 2011. PCI-DSS v4.0 (effective 2025) explicitly prohibits SHA-1 in SSL/TLS certificates. RBI IT Framework §4.2 requires "industry-accepted cryptographic algorithms" — which excludes SHA-1.

Replacement: SHA-256 (part of the SHA-2 family) with RSA-2048 or higher, or ECDSA with P-256 or P-384 curves. SHA-256 is what all modern certificate authorities issue. Our automation flags any cert with sha1WithRSAEncryption in the signature algorithm field as a PCI finding requiring immediate replacement.
Q: How do you handle keystore passwords securely in Ansible?
Three mechanisms working together:

1. AAP Vault Credential: The keystore password is stored in the AAP Controller as an encrypted Vault credential. It's injected as vault_keystore_password variable at runtime — never stored in plaintext in inventory or playbooks.

2. no_log: true on the keytool task: Prevents AAP from recording the task output in its job logs. Without this, the storepass parameter with the password would appear in the AAP job output, which is visible to any AAP user who can view the job.

3. Separate per-server passwords: Production environments should have different keystore passwords per server. These are stored as separate Vault entries keyed by server name, retrieved dynamically: vault_keystore_passwords[inventory_hostname]. A single compromised server's keystore password doesn't expose all other servers' keystores.
