Project 15: Production Release Automation — The Capstone Orchestrator

Every production release at SecureBank is a coordinated operation involving infrastructure checks, security gates, deployment steps, validation tests, and compliance evidence generation — a process that currently takes 12 engineers, a 3-hour war room call, and produces inconsistent results depending on who is leading the release. Project 15 replaces this with a single AAP Master Release Workflow that orchestrates the complete production release pipeline end-to-end: change advisory board (CAB) validation via ServiceNow, infrastructure pre-flight (Project 9 DR readiness check, Project 10 hardening drift check, Project 14 monitoring coverage verification), code deployment via Blue-Green (Project 12), database migrations (Project 12's schema migration), post-deploy health checks (Project 5), certificate validity (Project 4), log forwarding confirmation (Project 14), and a signed compliance release receipt submitted to the audit trail. It is the pipeline that makes every preceding project's work visible, measurable, and governable — and it completes in under 45 minutes with a single engineer at the keyboard.

🏦 2. Real-Time Banking Scenario

The Story — Before (12 Engineers, 3-Hour War Room): CBS v5.2.0 release night. 11:00 PM. A bridge call with 12 participants. The Release Manager reads from a checklist: "Step 1 — confirm CR number is approved." The CAB coordinator checks ServiceNow on a shared screen. "Step 2 — Suresh, confirm all CBS servers are hardened." Suresh: "I think they are — I ran the hardening playbook last Sunday." "Step 3 — Priya, confirm backups are valid." Priya checks her email for the Project 8 report. 45 minutes later, they haven't started deploying. The deployment itself runs until 1:30 AM. The post-deployment check is a manual walkthrough by Rajesh. By 2:00 AM everyone is exhausted and signs off verbally. The release receipt is a Word document with "Release completed — no issues" written by the release manager the next morning from memory. The QSA asks for timestamped evidence of the deployment steps and who approved what. The Word document is not accepted.

After (1 Engineer, 44 Minutes, Complete Audit Trail): Divya opens AAP at 11:00 PM. Launches Rel-CBS-v5.2.0-Production. Survey: CR number = CHG0045821, release_version = 5.2.0. The workflow validates CHG0045821 is approved and the current time is inside the approved change window. Every pre-flight check runs automatically. Blue-Green deployment executes. Smoke tests pass. Traffic switches. Monitoring gate runs 10 minutes. At 11:44 PM — 44 minutes after launch — the workflow generates a signed JSON release receipt with every step timestamped, every approver named (from ServiceNow), every test result logged, and the AAP job URL for each stage. The receipt is automatically uploaded to the audit evidence repository. Divya sends the receipt link to the CISO. The QSA accepts it as complete PCI-DSS release evidence.

❗ 3. Problem Statement

  • No automated enforcement of CAB approval — releases proceed based on verbal confirmation that a CR is approved, not programmatic verification.
  • Pre-release checks are manual and inconsistent — infrastructure readiness (hardening, monitoring, DR) is verified on a best-efforts basis, often skipped under time pressure.
  • Release window not enforced — releases sometimes run outside the approved change window when they run long, creating unauthorized change audit findings.
  • No unified orchestration — each team (DBA, app, platform, network) executes their part independently using separate runbooks, with no system enforcing completion order or handoff between teams.
  • Release receipt is a post-hoc Word document — not a real-time, timestamped, system-generated record. QSAs consistently reject it as PCI-DSS evidence.
  • Rollback is not automated — the decision to rollback and the execution both depend on engineer judgment and availability at 2 AM under pressure.

New Roles (Project 15 specific)

  • rel_cab_gate — ServiceNow CR validation + change window check
  • rel_preflight — orchestrates P9/P10/P14 job template calls via AAP API
  • rel_receipt — signed JSON receipt generation, GPG signing, upload, ServiceNow CR close

Reused Workflows / Job Templates

  • DR-Preflight-Check (P9)
  • Server-Harden-Drift-Detect (P10)
  • Mon-Agent-Health-Check (P14)
  • SSL-Cert-Scan (P4)
  • DB-Backup-Integrity-Daily (P8)
  • BG-Deploy-CBS full workflow (P12)
  • App-Health-Check-All (P5)

Key AAP Features Used

  • Workflow Nesting: The Master Release Workflow calls the P12 Blue-Green Workflow as a node — AAP 2.5 supports nested workflow invocation
  • Parallel nodes: Stage 1 (P9+P10+P14) and Stage 2+3 (P4+P8) run in parallel — saves 15+ minutes vs sequential
  • Approval nodes: Two — one before deployment, one before traffic cutover
  • Survey: release_version, cr_number, release_env, run_schema_migration, post_monitor_minutes, skip_preflight (emergency override)
  • RBAC: Workflow launch restricted to Release Manager role; approval nodes restricted to CTO/CISO/Release Manager
  • Artifacts: Release receipt JSON passed between workflow nodes via AAP artifact store

💻 9. Complete Project Code (Line-by-Line Explained)

Role: rel_cab_gate — CAB Approval & Change Window Enforcement

roles/rel_cab_gate/tasks/main.yml
---
- name: Record pipeline start timestamp
  ansible.builtin.set_fact:
    pipeline_start_epoch: "{{ ansible_date_time.epoch | int }}"
    pipeline_start_iso: "{{ ansible_date_time.iso8601 }}"
    release_timeline: {}

- name: Fetch Change Request details from ServiceNow
  ansible.builtin.uri:
    url: >-
      {{ servicenow_instance }}/api/now/table/{{ snow_change_table }}
      ?sysparm_query=number={{ cr_number }}
      &sysparm_fields=number,state,approval,start_date,end_date,
        short_description,assigned_to.name,u_release_version
      &sysparm_limit=1
    method: GET
    url_username: "{{ vault_snow_user }}"
    url_password: "{{ vault_snow_pass }}"
    force_basic_auth: true
    return_content: true
    status_code: 200
  register: snow_cr_response
  delegate_to: localhost
  no_log: true

- name: Fail if CR not found in ServiceNow
  ansible.builtin.fail:
    msg: >-
      CAB GATE FAILED: Change Request {{ cr_number }} not found in ServiceNow.
      Verify the CR number and ensure it has been submitted.
  when: snow_cr_response.json.result | length == 0

- name: Extract CR details
  ansible.builtin.set_fact:
    cr_details: "{{ snow_cr_response.json.result[0] }}"

- name: Fail if CR is not in Approved state
  ansible.builtin.fail:
    msg: >-
      CAB GATE FAILED: {{ cr_number }} state is '{{ cr_details.state }}'
      (approval: '{{ cr_details.approval }}'). Release cannot proceed
      without an Approved change request. Have the CAB approve first.
  when: cr_details.approval != 'approved' or cr_details.state != '20'

- name: Validate release version matches CR description
  ansible.builtin.fail:
    msg: >-
      CAB GATE FAILED: CR {{ cr_number }} describes version
      '{{ cr_details.u_release_version }}' but release_version survey
      value is '{{ release_version }}'. Ensure you are launching
      the correct release against the correct CR.
  when:
    - cr_details.u_release_version is defined
    - cr_details.u_release_version != release_version

- name: Parse CR change window times
  ansible.builtin.set_fact:
    cr_window_start_epoch: "{{ (cr_details.start_date | to_datetime('%Y-%m-%d %H:%M:%S')).strftime('%s') | int }}"
    cr_window_end_epoch: "{{ (cr_details.end_date | to_datetime('%Y-%m-%d %H:%M:%S')).strftime('%s') | int }}"

- name: Fail if current time is BEFORE the approved change window
  ansible.builtin.fail:
    msg: >-
      CAB GATE FAILED: Current time ({{ ansible_date_time.iso8601 }})
      is before the approved change window start
      ({{ cr_details.start_date }}). Wait until the window opens.
  when: ansible_date_time.epoch | int < cr_window_start_epoch | int

- name: Fail if current time is AFTER the approved change window
  ansible.builtin.fail:
    msg: >-
      CAB GATE FAILED: Current time ({{ ansible_date_time.iso8601 }})
      is after the approved change window end ({{ cr_details.end_date }}).
      The window has passed. Open a new CR for a new change window.
  when: ansible_date_time.epoch | int > cr_window_end_epoch | int

- name: Update ServiceNow CR to In Progress
  ansible.builtin.uri:
    url: "{{ servicenow_instance }}/api/now/table/{{ snow_change_table }}/{{ cr_details.sys_id }}"
    method: PATCH
    body_format: json
    body:
      state: "30"
      work_notes: >-
        Automated release pipeline started by {{ tower_user_name | default('ansible-aap') }}
        at {{ ansible_date_time.iso8601 }}. AAP Workflow Job: {{ tower_job_id | default('N/A') }}.
    url_username: "{{ vault_snow_user }}"
    url_password: "{{ vault_snow_pass }}"
    force_basic_auth: true
    status_code: 200
  delegate_to: localhost
  no_log: true

- name: Add CAB gate result to release timeline
  ansible.builtin.set_fact:
    release_timeline: >-
      {{ release_timeline | combine({
        'stage_0_cab_gate': {
          'cr_number': cr_number,
          'cr_approved_by': cr_details['approval'],
          'change_window': cr_details.start_date ~ ' — ' ~ cr_details.end_date,
          'gate_passed_at': ansible_date_time.iso8601,
          'status': 'PASSED'
        }
      }) }}
Line-by-Line Explanation
cr_details.state != '20' — ServiceNow change request states are numeric: 20 = Scheduled (CAB approved), 30 = In Progress, 0 = New, -5 = Pending. Checking both state == '20' (Scheduled/approved) AND approval == 'approved' provides defense in depth — a CR can technically be in state 20 without full CAB approval in some ServiceNow configurations.
Version matching: cr_details.u_release_version != release_version — Cross-validates the survey's release_version against the custom field on the CR. This prevents a common human error: launching the release automation with the wrong version number against the right CR, or using last week's CR number for this week's release. The CR's version field (u_release_version) must match the survey input exactly.
Change window enforcement: two-sided check — The pipeline checks BOTH that the current time is not before the window start AND not after the window end. A release that runs long and extends beyond the change window is an unauthorized change — the pipeline refuses to continue deploying once the window has passed. This single technical control eliminates an entire class of audit findings about changes made outside approved windows.
CR state update to "30" (In Progress) — As soon as the CAB gate passes, the CR is updated in ServiceNow to "In Progress" with a work note including the AAP job ID. Any ITSM dashboard, change manager, or auditor can see in real time that the release is underway, who launched it, and at what time — without anyone manually updating the ticket.

Role: rel_preflight — Parallel Infrastructure Gates

roles/rel_preflight/tasks/main.yml
---
# Pre-flight checks call existing job templates via AAP API
# This role acts as an orchestrator — launching and monitoring sub-jobs

- name: Launch P9 DR Readiness Check via AAP API
  ansible.builtin.uri:
    url: "{{ aap_api_url }}/job_templates/{{ aap_dr_preflight_job_id }}/launch/"
    method: POST
    body_format: json
    body: {}
    headers:
      Authorization: "Bearer {{ vault_aap_api_token }}"
    status_code: 201
    return_content: true
  register: dr_job_launch
  delegate_to: localhost

- name: Launch P10 Hardening Drift Detect via AAP API
  ansible.builtin.uri:
    url: "{{ aap_api_url }}/job_templates/{{ aap_hardening_detect_job_id }}/launch/"
    method: POST
    body_format: json
    body: {}
    headers:
      Authorization: "Bearer {{ vault_aap_api_token }}"
    status_code: 201
    return_content: true
  register: hardening_job_launch
  delegate_to: localhost

- name: Launch P14 Monitoring Agent Health Check via AAP API
  ansible.builtin.uri:
    url: "{{ aap_api_url }}/job_templates/{{ aap_mon_health_job_id }}/launch/"
    method: POST
    body_format: json
    body: {}
    headers:
      Authorization: "Bearer {{ vault_aap_api_token }}"
    status_code: 201
    return_content: true
  register: mon_job_launch
  delegate_to: localhost

- name: Poll all three sub-jobs until completion (parallel monitoring)
  ansible.builtin.uri:
    url: "{{ aap_api_url }}/jobs/{{ item.job_id }}/"
    method: GET
    headers:
      Authorization: "Bearer {{ vault_aap_api_token }}"
    return_content: true
  loop:
    - { name: dr_readiness,  job_id: "{{ dr_job_launch.json.id }}" }
    - { name: hardening,     job_id: "{{ hardening_job_launch.json.id }}" }
    - { name: mon_coverage,  job_id: "{{ mon_job_launch.json.id }}" }
  loop_control:
    label: "{{ item.name }} (job {{ item.job_id }})"
  register: preflight_job_statuses
  delegate_to: localhost
  retries: 60
  delay: 30
  until: >-
    preflight_job_statuses.json.status in ['successful', 'failed', 'error', 'canceled']

- name: Collect preflight failures
  ansible.builtin.set_fact:
    preflight_failures: >-
      {{ preflight_job_statuses.results
         | selectattr('json.status', 'ne', 'successful')
         | map(attribute='item.name')
         | list }}

- name: Block release if any preflight check failed
  ansible.builtin.fail:
    msg: >-
      PREFLIGHT GATE FAILED: The following infrastructure checks did not pass:
      {{ preflight_failures | join(', ') }}.
      Resolve all infrastructure issues before attempting the release.
      AAP job links for investigation:
      {% for r in preflight_job_statuses.results %}
      {{ r.item.name }}: {{ aap_api_url | replace('/api/v2','') }}/#/jobs/playbook/{{ r.json.id }}
      {% endfor %}
  when: preflight_failures | length > 0

- name: Add preflight results to release timeline
  ansible.builtin.set_fact:
    release_timeline: >-
      {{ release_timeline | combine({
        'stage_1_preflight': {
          'dr_readiness': 'PASSED',
          'hardening_drift': 'PASSED',
          'monitoring_coverage': 'PASSED',
          'completed_at': ansible_date_time.iso8601,
          'status': 'PASSED'
        }
      }) }}
Line-by-Line Explanation
Launching sub-jobs via AAP REST API /launch/ — Rather than importing roles from Projects 9, 10, and 14 directly (which would create tight coupling), the release pipeline calls their existing AAP Job Templates via the AAP REST API. This is the correct architectural pattern: each project owns its own job templates; the release pipeline orchestrates them as named services. The AAP API returns a job ID immediately on launch (status 201), which we then poll to completion.
Polling with retries: 60 / delay: 30 — The three sub-jobs run in parallel (all three launched before any polling starts). We poll each job's status every 30 seconds for up to 30 minutes (60 × 30s). The until condition fires when the job reaches any terminal state. All three jobs must reach "successful" — any failure blocks the release.
AAP job links in failure message — When a preflight check fails, the failure message includes clickable AAP job URLs for each failing check. The release manager can immediately navigate to the specific job output to see which servers failed and why — without needing to search through AAP manually. This transforms a blocking failure from an opaque "preflight failed" into an actionable diagnostic tool.

Line-by-Line Explanation
GPG signing: gpg --detach-sign --armor — The release receipt JSON is GPG-signed with the bank's release management key. The detached signature (.asc file) is archived alongside the receipt. GPG signing provides non-repudiation — the receipt cannot be modified after the fact without invalidating the signature. A QSA can verify the signature to confirm the receipt is authentic and unmodified. This is the technical control that makes the release receipt audit-grade evidence vs a Word document that can be edited.
release_timeline | combine({stage_N: {...}}) — Each role in the pipeline appends its stage results to the release_timeline dict using the combine() filter. The receipt's stages field contains the complete timeline: every stage's start time, completion time, and pass/fail status — accumulated across all 10 stages of the pipeline. This is the per-step timestamp evidence RBI IT Framework §5.3 requires.
ServiceNow CR close with close_code: "successful" and close_notes containing the receipt path — The CR is automatically closed in ServiceNow with a full closure note including the release receipt path and AAP job URL. Change managers never need to manually close release CRs. The CMDB is automatically updated as a side effect of the CR closure (ServiceNow triggers CMDB updates on change close). No more backlog of open CRs that were completed weeks ago.
schema_version: "1.0" in the receipt — Future-proofing: when the receipt format evolves, the schema_version enables consumers (audit tools, SIEM, compliance dashboards) to handle multiple versions. A QSA portal parsing the receipt can branch on schema_version to handle format changes without breaking existing evidence parsing.

🎯 13. Interview Preparation — Capstone Questions

Architecture Questions

Q: How does Project 15 call the workflows from other projects? Why not just import the roles directly?
The release pipeline calls other projects' AAP Job Templates via the AAP REST API (/api/v2/job_templates/ID/launch/), receiving a job ID back and then polling until completion. This is the correct architectural pattern because: (1) Each project's Job Template has its own credentials, execution environment, inventory, and RBAC — importing the role directly would lose all that context. (2) Calling via API maintains loose coupling — Projects 9, 10, 12 can evolve independently without changing the release pipeline code. (3) The AAP API call model enables parallel execution (launch all three preflight jobs simultaneously, poll all three for completion) without Ansible's native serial/fork limitations.
Q: What happens if the release pipeline fails at Stage 3 (schema migration) — how is the system state?
The system is in a completely safe state. The schema migration (if it fails mid-way) leaves the database in whatever state Flyway reached — Flyway is transactional: if the migration script fails, the transaction is rolled back and the database is exactly as it was before migration started. The Green environment hasn't been deployed yet. The Blue environment is running normally serving 100% of traffic. The ServiceNow CR state is "In Progress" — the release manager closes it as "Unsuccessful" after investigation. No customer impact, no downtime, clean state throughout.
Q: How do you handle a scenario where the CAB gate passes but a critical P1 hardening drift is detected in the preflight?
The preflight role polls the P10 job status and checks for "successful" completion. If the P10 hardening drift detect job completes with P1 findings (the job itself is designed to succeed — detecting P1 drift is not a job failure), the preflight role reads the job's artifact (drift_summary.p1_findings > 0) and fails with a blocking message: "PREFLIGHT GATE FAILED: P1 hardening drift detected on servers X, Y, Z. Run Drift-Remediate and verify before releasing." The release cannot proceed until the drift is remediated and the P10 check passes clean. This enforces the security-before-release gate that the manual process could never reliably enforce.

Governance & Compliance Questions

Q: How does Project 15 satisfy PCI-DSS Req 6.5 (change management)?
PCI-DSS Req 6.5 requires a defined change control process including: documented authorization (CAB gate validates ServiceNow approval), testing before deployment (Stage 5 smoke tests against Green before any traffic touch), rollback plans (Blue environment remains active throughout; BG-Rollback job available), and post-change validation (Stage 7 health checks and Stage 8 monitoring gate). The signed release receipt documents all of these with system-authoritative timestamps — satisfying the evidence requirement. The QSA can verify: who approved the CR, when deployment started, what tests ran and passed, when the deployment completed, and that no downtime occurred.
Q: A release is in progress and the 60-minute approved change window is about to expire. What does the pipeline do?
The CAB gate check happens only at the start — it doesn't continuously monitor the window. However, after the monitoring gate completes (Stage 8), if the total pipeline duration exceeds the window, the CR close step (Stage 9) includes the actual completion timestamp. If the release ran past the window, the CR close notes reflect this, creating an automatic record of the overrun for the change manager to review. For future prevention, the pipeline's survey should include a warning calculation: "Estimated pipeline duration: 45 minutes. Your change window is 90 minutes. Proceed? Your estimated completion is at [time]." This pre-launch estimate reduces window overruns from planning failures.
Q: How would you extend Project 15 to support a multi-application release (CBS + Payment Gateway simultaneously)?
Three approaches: (1) Parallel BG workflows — launch both BG-Deploy-CBS and BG-Deploy-PayGW as parallel AAP workflow nodes, with a shared approval gate before either cutover. (2) Sequential with dependency — deploy CBS first, validate, then deploy PayGW (useful when PayGW depends on CBS API). (3) Feature flags — deploy both applications simultaneously with the new feature disabled via feature flags, then use the release pipeline's "enable feature flag" stage to turn on the feature atomically without another deployment. The receipt and CR model extend naturally: one CR per application, or one multi-application CR with sub-tasks — both patterns are supported in ServiceNow and the receipt schema already has an extensible stages structure.

📝 14. Key Learnings & Resume Points

Key Learnings

  • A release pipeline is only as strong as its gates — programmatic enforcement of CAB approval and change windows eliminates an entire class of audit findings that verbal confirmations cannot prevent.
  • Calling sub-workflows via AAP API is the correct pattern for orchestrating existing automation as named stages — it maintains loose coupling, preserves RBAC and credentials, and enables parallel execution.
  • GPG signing the release receipt transforms it from a document that can be edited to tamper-evident audit evidence — this single technical control is what QSAs accept as real proof vs a Word document.
  • Automated CR closure with full evidence in the work notes eliminates the change management backlog of open CRs for completed releases — a significant ITSM hygiene improvement.

Common Mistakes

  • Treating the approval node as the only gate — every stage should be a gate; approval is for human judgment, not a substitute for automated validation.
  • Not running preflight checks in parallel — sequential DR check → hardening check → monitoring check wastes 20+ minutes that could be saved with parallel execution.
  • Building the release pipeline as a monolithic playbook — calling sub-workflows via AAP API maintains each project's independence and avoids the "one giant playbook" antipattern.
  • Forgetting to update ServiceNow CR to "In Progress" at pipeline start — a CR stuck in Scheduled state while the release is running creates false ITSM reporting.

Production Best Practices

  • Build the CR version mismatch check — validating that the survey's release_version matches the CR's release version field prevents the most common human error in release launches (using the wrong CR number).
  • Always leave the Blue environment running for at least 24 hours post-release — the monitoring gate catches most issues, but some banking failures only manifest during the next business day's batch runs.
  • Store the release receipt path in the ServiceNow CR close notes — this creates a permanent link from the change record to the compliance evidence, making QSA reviews trivially easy.
  • Implement an emergency skip flag (skip_preflight: true) for genuine production emergencies — but require CISO-level approval in the survey acknowledgement, and always generate a full audit trail of what was skipped and why.
