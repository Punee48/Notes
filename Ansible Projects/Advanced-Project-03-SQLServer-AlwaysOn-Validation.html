Project 03: SQL Server Always-On Availability Group (AG) Validation & Health Monitoring

This project covers one of the most critical Windows automation challenges in banking: Microsoft SQL Server Always-On Availability Group health validation. SQL Server AG is the high-availability and disaster recovery solution used in banks for mission-critical databases like the Loan Management System (LMS), HR System, and Credit Card Processing. When an AG degrades — replica falls behind, synchronization breaks, or the listener fails — applications lose HA protection silently. This project automates complete AG health validation, synchronization lag monitoring, replica role verification, automatic alerting, and daily compliance reporting — all using Ansible with WinRM to manage Windows Server 2019 SQL Server nodes.

🏦 1. The Banking Story

Setting: ABC Global Bank uses SQL Server 2019 Always-On AG for the Loan Management System (LMS) — one of the bank's most critical applications with ₹45,000 crore in active loan portfolios. The AG runs across 3 nodes: Primary in Mumbai, Synchronous Secondary in Mumbai DR rack, and Asynchronous Secondary in Chennai for DR.

The Incident: During a quarterly DR drill, the infrastructure team initiates a planned failover of the LMS SQL Server AG from Mumbai Primary to the Synchronous Secondary. The failover fails. Investigation reveals: the synchronous secondary replica had been in a "NOT SYNCHRONIZING" state for 11 days. The secondary's transaction log had fallen 4.8 million transactions behind the primary. Nobody noticed because the monitoring alert for "AG synchronization" had been disabled 11 days ago when it was generating "too many false positives" during a maintenance window — and was never re-enabled.

Impact: The DR drill failed completely. The DR team had to rebuild the secondary replica from scratch — a 6-hour process. The LMS was unavailable for a planned maintenance window that stretched from 2 hours to 8+ hours. The business continuity team filed a formal report. Senior management demanded a permanent fix.

The Ask: "We need automated monitoring of ALL Always-On AG replicas every 10 minutes. We need the synchronization lag measured precisely. We need to know the moment any replica stops synchronizing — not 11 days later. And we need to prove to the RBI that we have HA monitoring controls in place."

📚 2. SQL Server Always-On AG — Concepts You Must Know

What is an Always-On Availability Group?
Always-On Availability Group (AG) is SQL Server's enterprise HA/DR solution. It maintains one or more identical copies (replicas) of a group of databases across multiple SQL Server instances.

Key Components:
• Primary Replica: The one replica that accepts read/write transactions. All writes go here.
• Secondary Replica: Receives and applies transaction log records from primary. Can be readable or not.
• Synchronous Commit: Primary waits for secondary to confirm before committing. Zero data loss. Suitable for same-DC or low-latency links.
• Asynchronous Commit: Primary does NOT wait for secondary. Some data loss possible in DR scenario. For geographically distant replicas.
• AG Listener: A virtual network name (VNN) with an IP that applications connect to — always points to the current primary.
Key SQL Server DMVs for AG Monitoring
SQL Server T-SQL — Key AG Monitoring Queries
-- sys.availability_groups: List of all AGs on this instance
SELECT name, ag_id, failure_condition_level, health_check_timeout
FROM sys.availability_groups;

-- sys.availability_replicas: All replicas (primary + all secondaries)
SELECT replica_server_name, availability_mode_desc, failover_mode_desc,
       role_desc, operational_state_desc, connected_state_desc,
       synchronization_health_desc
FROM sys.availability_replicas ar
JOIN sys.availability_groups ag ON ar.group_id = ag.group_id;

-- sys.dm_hadr_availability_replica_states: REAL-TIME replica states
-- This is the most important DMV for monitoring
SELECT rs.role_desc,                -- PRIMARY or SECONDARY
       rs.synchronization_health_desc, -- HEALTHY, PARTIALLY_HEALTHY, NOT_HEALTHY
       rs.connected_state_desc,     -- CONNECTED or DISCONNECTED
       rs.last_connect_error_number, -- Error code if disconnected
       ags.synchronization_state_desc, -- SYNCHRONIZED or SYNCHRONIZING or NOT SYNCHRONIZING
       ags.log_send_queue_size,     -- KB of log waiting to be sent to secondary
       ags.redo_queue_size,         -- KB of log waiting to be applied on secondary
       ags.log_send_rate,           -- KB/sec being sent
       ags.redo_rate                -- KB/sec being applied
FROM sys.dm_hadr_availability_replica_states rs
JOIN sys.dm_hadr_availability_group_states ags ON rs.group_id = ags.group_id;

WinRM — How Ansible Connects to Windows
Ansible uses WinRM (Windows Remote Management) to connect to Windows servers — the Windows equivalent of SSH. WinRM uses HTTP (port 5985) or HTTPS (port 5986).

Ansible needs the pywinrm Python library installed in the Execution Environment. The connection type is set to ansible.builtin.winrm or just winrm in inventory. All tasks use Windows-specific modules like ansible.windows.win_shell and community.windows.win_mssql.

  • SQL Server AG monitoring: manual dashboard checks once a day
  • Monitoring alerts disabled during maintenance → never re-enabled
  • Log send queue lag: never measured — discovered only during failover
  • No pre-drill validation — assumes AG is healthy before failover attempt

  • Log send queue and redo queue measured every run

  • Ansible + WinRM handles all Windows complexity
  • Daily HTML report auto-generated and emailed

Key Design Decision — Query Only from Primary: All AG health queries run against the PRIMARY replica. Secondary replicas can only see their own partial state. Querying the primary gives the authoritative view of ALL replica states including synchronization lag for every secondary. This is why we query sys.dm_hadr_availability_replica_states from the primary — it shows the status of every secondary from the primary's perspective.

🔧 7. WinRM Configuration — Connecting Ansible to Windows

Critical prerequisite: Before Ansible can manage Windows SQL Servers, WinRM must be configured on each Windows server. This is a one-time setup done by the Windows admin team.
PowerShell — Run on each Windows SQL Server to enable WinRM (one-time setup)
# Run this as Administrator on each SQL Server Windows node
# =====================================================================

# Enable WinRM service
Enable-PSRemoting -Force                              # Enables WinRM and starts the service

# Configure WinRM for HTTPS (more secure — use in production)
# This requires an SSL certificate on the Windows server
$cert = New-SelfSignedCertificate `                  # Create self-signed cert for lab
    -DnsName $env:COMPUTERNAME `                      # Certificate for this hostname
    -CertStoreLocation Cert:\LocalMachine\My          # Store in machine cert store

# Create WinRM HTTPS listener using the certificate
winrm create winrm/config/Listener?Address=*+Transport=HTTPS `
    "@{Hostname=`"$env:COMPUTERNAME`";CertificateThumbprint=`"$($cert.Thumbprint)`"}"

# Allow WinRM through Windows Firewall
netsh advfirewall firewall add rule `
    name="WinRM HTTPS" `
    protocol=TCP `
    dir=in `
    localport=5986 `
    action=allow

# Set WinRM authentication to allow Negotiate (Kerberos/NTLM)
winrm set winrm/config/service/auth '@{Negotiate="true"}'

# Verify WinRM is working
winrm enumerate winrm/config/listener               # Should show HTTPS listener on 5986

# Test from Ansible control node (Linux):
# curl -k https://lms-sql01.abcbank.in:5986/wsman
Install pywinrm on AAP Execution Environment (requirements.txt)
# execution_environment/requirements.txt
# Python libraries for Windows automation from Ansible
pywinrm>=0.4.3          # Core WinRM library — enables Ansible to talk to Windows
requests-kerberos       # For Kerberos authentication (domain-joined servers)
requests-ntlm           # For NTLM authentication (workgroup or simpler setups)
requests>=2.28.0        # HTTP library dependency for pywinrm

💻 11. Roles & Tasks — Complete Code

SQL Files — T-SQL Queries (stored as files in role)

roles/sqlserver_ag_query/files/query_ag_health.sql
-- =====================================================================
-- AG Health Query — Returns JSON-compatible output for Ansible parsing
-- Run on PRIMARY replica to get status of ALL replicas
-- =====================================================================
SET NOCOUNT ON;              -- Suppress row count messages in output

SELECT
    ag.name                        AS ag_name,         -- AG name: LMS_AG
    ar.replica_server_name         AS replica_server,  -- Server name of each replica
    ar.availability_mode_desc      AS availability_mode, -- SYNCHRONOUS_COMMIT or ASYNCHRONOUS
    ar.failover_mode_desc          AS failover_mode,   -- AUTOMATIC or MANUAL
    ars.role_desc                  AS current_role,    -- PRIMARY or SECONDARY
    ars.connected_state_desc       AS connected_state, -- CONNECTED or DISCONNECTED
    ars.synchronization_health_desc AS sync_health,    -- HEALTHY, PARTIALLY_HEALTHY, NOT_HEALTHY
    ags.synchronization_state_desc AS sync_state,      -- SYNCHRONIZED, SYNCHRONIZING, NOT SYNCHRONIZING
    ISNULL(ags.log_send_queue_size, 0) AS log_send_queue_kb,  -- KB waiting to be sent
    ISNULL(ags.redo_queue_size, 0)     AS redo_queue_kb,      -- KB waiting to be applied
    ISNULL(ags.log_send_rate, 0)       AS log_send_rate_kb,   -- KB/sec transmission rate
    ISNULL(ags.redo_rate, 0)           AS redo_rate_kb        -- KB/sec application rate
FROM
    sys.availability_groups ag
    INNER JOIN sys.availability_replicas ar
        ON ag.group_id = ar.group_id
    LEFT JOIN sys.dm_hadr_availability_replica_states ars
        ON ar.replica_id = ars.replica_id
    LEFT JOIN sys.dm_hadr_availability_group_states ags
        ON ag.group_id = ags.group_id
WHERE
    ag.name = '$(AG_NAME)'          -- sqlcmd variable substitution
ORDER BY
    ars.role_desc DESC,             -- PRIMARY first, then SECONDARY
    ar.replica_server_name;

-- Output format: each replica on one row with | separator for Ansible parsing
roles/sqlserver_ag_query/files/query_replica_lag.sql
-- =====================================================================
-- Per-database lag query — shows sync state for each database in the AG
-- This identifies WHICH specific database is behind, not just the replica
-- =====================================================================
SET NOCOUNT ON;

SELECT
    DB_NAME(drs.database_id)       AS database_name,      -- Which database
    ar.replica_server_name         AS replica_server,      -- On which replica
    drs.synchronization_state_desc AS db_sync_state,       -- SYNCHRONIZED/SYNCHRONIZING/etc
    drs.is_suspended               AS is_suspended,         -- 1 = manually suspended (issue!)
    ISNULL(drs.log_send_queue_size, 0) AS db_log_send_kb,  -- Per-DB log queue
    ISNULL(drs.redo_queue_size, 0)     AS db_redo_kb,      -- Per-DB redo queue
    drs.last_hardened_time         AS last_hardened_time    -- When last log hardened on secondary
FROM
    sys.dm_hadr_database_replica_states drs
    INNER JOIN sys.availability_replicas ar
        ON drs.replica_id = ar.replica_id
    INNER JOIN sys.availability_groups ag
        ON ar.group_id = ag.group_id
WHERE
    ag.name = '$(AG_NAME)'
    AND drs.is_local = 0            -- Only show remote (secondary) databases
ORDER BY
    drs.redo_queue_size DESC;       -- Largest lag first

Role 1: sqlserver_ag_query — Query AG Health from SQL Server

roles/sqlserver_ag_query/tasks/query_ag_status.yml
---
# =====================================================================
# Query SQL Server AG health using sqlcmd + T-SQL
# Runs on Windows SQL Primary via WinRM
# =====================================================================

- name: Copy T-SQL query files to SQL Server (Windows path)
  ansible.windows.win_copy:                                # win_copy: copies files to Windows
    src: "{{ role_path }}/files/query_ag_health.sql"      # Source: on Ansible control node
    dest: "C:\\Temp\\query_ag_health.sql"                 # Destination: Windows temp folder
    # Note: Windows paths use backslash — must be escaped as \\

- name: Copy replica lag query to SQL Server
  ansible.windows.win_copy:
    src: "{{ role_path }}/files/query_replica_lag.sql"
    dest: "C:\\Temp\\query_replica_lag.sql"

- name: Execute AG health query using sqlcmd
  ansible.windows.win_shell:                               # win_shell: runs PowerShell/cmd on Windows
    cmd: >-
      "{{ sqlcmd_path }}"
      -S localhost
      -E
      -v AG_NAME="{{ ag_name }}"
      -i C:\Temp\query_ag_health.sql
      -s "|"
      -W
      -h -1
    # -S localhost: connect to local SQL instance
    # -E: Windows Authentication (Trusted Connection) — no password needed
    #     The Windows service account running Ansible task IS the SQL login
    # -v AG_NAME=...: pass sqlcmd variable (used in SQL as $(AG_NAME))
    # -i: input SQL file to execute
    # -s "|": column separator — pipe character for easy parsing
    # -W: remove trailing spaces from each field
    # -h -1: no header row (pure data output for easy parsing)
  register: ag_health_raw
  changed_when: false                                      # Query doesn't change anything
  no_log: false                                            # OK to log — no passwords in output

- name: Parse AG health output into structured data
  ansible.builtin.set_fact:
    ag_replicas: >-
      {{ ag_health_raw.stdout_lines
         | reject('match', '^$')
         | map('split', '|')
         | map('map', 'trim')
         | map('list')
         | list }}
    # reject('match', '^$'): remove empty lines from sqlcmd output
    # map('split', '|'): split each line on the pipe delimiter
    # map('map', 'trim'): trim whitespace from each field
    # Result: list of lists [[ag_name, server, mode, failover, role, ...], ...]

- name: Convert raw list to list of dicts for easier processing
  ansible.builtin.set_fact:
    ag_replica_dicts: >-
      {{ ag_replicas | map('zip',
        ['ag_name','replica_server','availability_mode','failover_mode',
         'current_role','connected_state','sync_health','sync_state',
         'log_send_queue_kb','redo_queue_kb','log_send_rate_kb','redo_rate_kb'])
         | map('list')
         | map('community.general.dict')
         | list }}
    # zip: pairs each value with its column name
    # dict: converts paired tuples to a dictionary
    # Result: [{'ag_name': 'LMS_AG', 'replica_server': 'LMS-SQL01', 'current_role': 'PRIMARY', ...}]

- name: Display AG replica summary
  ansible.builtin.debug:
    msg:
      - "AG: {{ ag_name }} on {{ inventory_hostname }}"
      - "Replicas found: {{ ag_replica_dicts | length }}"
      - "States: {{ ag_replica_dicts | map(attribute='sync_state') | list | join(', ') }}"

# =====================================================================
# Validate AG Listener — DNS resolution and port check
# Runs from AAP control node (Linux) using delegate_to: localhost
# =====================================================================

- name: Resolve AG listener DNS name
  ansible.builtin.command:
    cmd: "nslookup {{ ag_listener_fqdn }}"                 # DNS lookup of listener FQDN
  register: listener_dns_result
  changed_when: false
  failed_when: false
  delegate_to: localhost                                    # Run on Linux AAP node, not Windows

- name: Check if AG listener port is accepting connections
  ansible.builtin.wait_for:
    host: "{{ ag_listener_ip }}"                           # Direct IP (not hostname — faster)
    port: "{{ ag_listener_port }}"                         # SQL Server port: 1433
    timeout: 15
    state: started
  register: listener_port_result
  failed_when: false
  delegate_to: localhost

- name: Test actual SQL Server connection through listener (connection string test)
  ansible.windows.win_shell:
    cmd: >-
      "{{ sqlcmd_path }}"
      -S {{ ag_listener_fqdn }},{{ ag_listener_port }}
      -E

6
Slack summary sent regardless of status — green confirmation if all healthy, red alert with replica details if issues found.
7
Pre-drill: DR team runs SQLServer-AG-Pre-Drill-Check manually before drill. All secondaries must be SYNCHRONIZED — playbook fails explicitly if any replica is behind, blocking the drill and preventing a repeat of the 11-day undetected lag scenario.

🎯 16. Interview Preparation

Q: How does Ansible connect to Windows — explain WinRM vs SSH?
Ansible uses SSH for Linux (default, port 22) and WinRM (Windows Remote Management) for Windows (HTTP port 5985 or HTTPS port 5986). WinRM is Microsoft's implementation of the WS-Management protocol — the Windows-native remote management API.

Key differences: SSH is encrypted by default; WinRM HTTP is plaintext (use HTTPS in production). SSH uses key-pair authentication; WinRM supports Basic, NTLM, Kerberos, and Certificate auth. SSH runs Bash/Shell commands; WinRM runs PowerShell/CMD on Windows.

In inventory, you set ansible_connection=winrm and the pywinrm Python library handles the WinRM protocol. All Windows-specific Ansible modules (win_shell, win_copy, win_service etc.) automatically use WinRM when this connection type is set.
Q: Why query the AG from the PRIMARY replica only?
SQL Server DMVs that show ALL replica states (sys.dm_hadr_availability_replica_states, sys.dm_hadr_availability_group_states) are only fully populated on the PRIMARY replica. On a secondary, these views only show the secondary's OWN state — not the state of other replicas.

Specifically, log_send_queue_size and redo_queue_size in sys.dm_hadr_availability_group_states show the LAG of secondaries AS SEEN BY THE PRIMARY. A secondary cannot tell you its own lag from the primary's perspective. So all meaningful AG monitoring queries must run on the primary.
Q: What is the difference between synchronous and asynchronous commit replicas in AG?
Synchronous Commit: The primary waits for the secondary to CONFIRM that it has hardened (written to disk) the transaction log records before committing the transaction to the client. This guarantees ZERO DATA LOSS on failover. Latency impact: ~1-3ms added to each transaction (depends on network latency to secondary). Used for: same-DC secondary, or DR with dedicated WAN link.

Asynchronous Commit: The primary does NOT wait for secondary confirmation. Transactions commit immediately. Secondary may be behind by some number of transactions. POTENTIAL DATA LOSS on unplanned failover (you lose whatever wasn't replicated). Used for: geographically distant DR replicas where network latency would unacceptably impact transaction response times.
Q: How would you handle an unplanned failover detection in this automation?
In the inventory, each SQL Server has an ag_expected_role host variable (PRIMARY or SECONDARY). After querying AG status, we compare current_role in the DMV with ag_expected_role in inventory.

If a server that's expected to be SECONDARY is now PRIMARY in the DMV — an unplanned failover occurred. We immediately fire a P1 PagerDuty alert: "UNPLANNED FAILOVER DETECTED: lms-sql02 is now PRIMARY but expected to be SECONDARY." This alert reaches the DBA team who can investigate whether the failover was expected, verify data integrity on the old primary, and decide whether to fail back.
