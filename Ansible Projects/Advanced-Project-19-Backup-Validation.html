Project 19: Backup Validation, Job Health Monitoring & Automated Restore Testing

Every bank has a backup policy. Very few banks actually verify that their backups work. A backup that has never been tested is not a backup — it's a hope. RBI's IT Framework §9 mandates that banks perform regular restore drills and maintain evidence of successful restoration. This project automates three things: daily backup job health monitoring (did last night's backup complete successfully?), backup age and completeness validation (is every critical database actually backed up and within RPO?), and automated restore testing (restore a sample backup to an isolated environment and verify data integrity — generating audit-grade evidence). Covers Oracle RMAN, Veeam B&R, and Linux file-level backups.

🏦 1. The Banking Story

Setting: ABC Global Bank runs backups across three platforms: Oracle RMAN for all 47 Oracle databases, Veeam Backup & Replication for 650 Windows VMs and 200 Linux VMs, and a custom shell-script based file backup for application config directories. The backup team of 4 engineers monitors backup status manually — logging into the Veeam console every morning and scanning a 300-line RMAN log file for errors.

Incident 1 — The Backup Nobody Noticed Failing: The Oracle RMAN backup for the CBS production database (cbs-db01) started failing silently 43 days ago. The cause: the NAS mount point where RMAN wrote backups was full. RMAN completed its run each night but wrote an error to the log and deleted the partial backup — so the database appeared to have "run" a backup, but no valid backup existed. Nobody checked the RMAN log deeply enough to see the error. During a production incident where cbs-db01's primary disk failed, the DBA team attempted to restore from the RMAN backup — and found 43 days of failed backups. The database had to be restored from a 44-day-old backup. 44 days of transaction history was lost. RBI declared this a critical failure of the bank's disaster recovery capability.

Incident 2 — The Veeam Job That Always Showed Green: Veeam was configured to back up the LMS application server VMs. One VM (lms-app07) had a large disk that was excluded from the backup job by mistake — the backup completed successfully (all other disks were backed up), but the application data disk was missing. The Veeam console showed the job as "Success" because the job itself completed without errors. When lms-app07's data disk failed, the restore from Veeam recovered all disks EXCEPT the data disk — the application was restored but had no data. The exclusion had been in place for 8 months.

Incident 3 — The Restore That Never Worked: The bank's quarterly DR drill included a restore test for the FDS (Fraud Detection System) PostgreSQL database. The restore had never been tested before. When the DBA team tried to restore, they discovered: the backup was compressed with a version of pgdump that was newer than the pgdump available on the restore target — the restore failed. The backup existed and was valid, but could not be restored with the tools available. RBI found this as: "Backup exists but restore procedure is untested and non-functional."

The Ask: "Check every backup job every morning. Alert if any backup is older than the RPO. Verify Oracle RMAN backups are actually restorable (crosscheck). Run automated restore tests monthly. Generate evidence reports for RBI inspection."

📚 2. Backup Concepts

RPO vs RTO — The Two Fundamental Backup Metrics

RPO (Recovery Point Objective): How much data can the bank afford to lose? If RPO = 4 hours, the most recent backup must be no older than 4 hours. If the primary database fails, we lose at most 4 hours of transactions. Banking RPOs: CBS = 15 minutes (replicated + frequent RMAN archivelogs), LMS = 4 hours, reporting databases = 24 hours.

RTO (Recovery Time Objective): How quickly must the system be restored? CBS RTO = 2 hours (must be back online within 2 hours of failure). This drives backup type choices — full daily + incremental hourly means faster restore than weekly full only.

Our automation validates RPO: is the most recent successful backup within the RPO window? If not, the bank is already outside its RTO compliance even before any incident occurs.

Oracle RMAN Backup Types and Validation

RMAN (Recovery Manager) is Oracle's built-in backup tool. It manages:

  • Full backup: Complete copy of all database blocks. Typically done weekly.
  • Incremental backup: Only changed blocks since last backup. Done daily or hourly.
  • Archivelog backup: Archived redo logs — provides point-in-time recovery between full backups. Critical for RPO compliance.

RMAN crosscheck: Verifies that backup pieces listed in the RMAN catalog actually exist on disk/tape. A backup can be "listed" in the catalog but the physical file deleted. Crosscheck detects this. Our automation runs RMAN> CROSSCHECK BACKUP; to catch the Incident 1 scenario — backup listed in catalog but files missing or corrupted.

RMAN LIST BACKUP SUMMARY: Shows the most recent backup for each database component with its completion status and size. We parse this to validate backup age and completeness.

Veeam Backup — Key Status Fields

Veeam Backup & Replication exposes its job and restore point data through:

  • Veeam REST API: Modern approach — HTTP calls to the Veeam B&R REST API server (port 9419). Returns JSON with job details, last result, and restore points.
  • PowerShell (Get-VBRJob, Get-VBRRestorePoint): Run on the Veeam server directly. More detailed but requires direct access.

Key fields to check: LastResult (Success/Warning/Failed), LastBackup (timestamp of last successful backup), TotalSize (backup size — zero means no data was backed up), and whether all VM disks are included in the backup scope.

💻 8. Roles & Tasks — Full Code with Comments

Role 1: backup_rman_check — Oracle RMAN Validation

roles/backup_rman_check/tasks/check_last_backup.yml
---
# =====================================================================
# Check Oracle RMAN backup job history from V$RMAN_BACKUP_JOB_DETAILS
# This view contains one row per RMAN backup job with its status,
# start time, end time, and whether it completed successfully
# We query this to answer: "When was the last SUCCESSFUL backup?"
# =====================================================================

- name: Query RMAN backup job history for the last 48 hours
  ansible.builtin.shell:
    cmd: |
      sqlplus -S {{ vault_oracle_monitor_user }}/{{ vault_oracle_monitor_pass }}@{{ oracle_sid }} << 'EOF'
      SET PAGESIZE 0 FEEDBACK OFF VERIFY OFF HEADING OFF ECHO OFF
      SET COLSEP '|'

      -- V$RMAN_BACKUP_JOB_DETAILS: one row per RMAN job session
      -- STATUS: COMPLETED, COMPLETED WITH WARNINGS, FAILED, RUNNING
      -- INPUT_TYPE: DB FULL, DB INCR, ARCHIVELOG, CONTROLFILE
      -- We look for the most recent COMPLETED job to get backup age
      SELECT
        TO_CHAR(END_TIME, 'YYYY-MM-DD HH24:MI:SS') AS end_time,
        STATUS,                                 -- Was this backup successful?
        INPUT_TYPE,                             -- What was backed up?
        INPUT_BYTES_PER_SEC/1024/1024,          -- MB/s throughput
        OUTPUT_BYTES/1024/1024/1024,            -- Total backup size in GB
        ELAPSED_SECONDS,                        -- How long the backup took
        -- Hours since this backup completed (how old is our most recent backup?)
        ROUND((SYSDATE - END_TIME) * 24, 2) AS hours_ago
      FROM V$RMAN_BACKUP_JOB_DETAILS
      WHERE END_TIME > SYSDATE - 2            -- Only last 48 hours
        AND STATUS IN ('COMPLETED', 'COMPLETED WITH WARNINGS', 'FAILED')
      ORDER BY END_TIME DESC                  -- Most recent first
      FETCH FIRST 5 ROWS ONLY;               -- Only the 5 most recent jobs
      EXIT;
      EOF
    executable: /bin/bash
  register: rman_job_history
  become: true
  become_user: oracle
  no_log: true                               # Hide database credentials from AAP logs
  changed_when: false
  environment:
    ORACLE_HOME: "{{ oracle_home }}"
    ORACLE_SID: "{{ oracle_sid }}"
    LD_LIBRARY_PATH: "{{ oracle_home }}/lib"

- name: Parse RMAN job history into structured backup list
  ansible.builtin.set_fact:
    rman_jobs: >-
      {{ rman_jobs | default([]) + [{
        'end_time': item.split('|')[0] | trim,
        'status': item.split('|')[1] | trim,
        'input_type': item.split('|')[2] | trim,
        'throughput_mbps': item.split('|')[3] | trim | float | round(1),
        'size_gb': item.split('|')[4] | trim | float | round(2),
        'elapsed_sec': item.split('|')[5] | trim | int,
        'hours_ago': item.split('|')[6] | trim | float | round(2),
        'database': oracle_sid
      }] }}
      # Split each line on | to extract individual columns
      # hours_ago: how long ago this backup completed — our key RPO metric
  loop: >-
    {{ rman_job_history.stdout_lines
       | reject('match', '^$')
       | reject('match', '^SQL.*')
       | list }}
  loop_control:
    label: "Parsing RMAN job line..."
  when: rman_job_history.stdout_lines | length > 0

- name: Find the most recent COMPLETED backup and check against RPO
  ansible.builtin.set_fact:
    # Get the most recent backup that has COMPLETED status (not failed)
    latest_successful_backup: >-
      {{ rman_jobs | default([])
         | selectattr('status', 'equalto', 'COMPLETED')
         | sort(attribute='hours_ago')
         | first | default({}) }}

    # Get the RPO for this database from our rpo_definitions variable
    # We need to find which rpo group this oracle_sid belongs to
    db_rpo_hours: >-
      {{ rpo_definitions.values()
         | selectattr('db_list', 'defined')
         | selectattr('db_list', 'contains', oracle_sid)
         | map(attribute='rpo_hours')
         | first | default(24) }}

- name: Calculate whether this database is within its RPO
  ansible.builtin.set_fact:
    backup_within_rpo: >-
      {{ latest_successful_backup.hours_ago | default(9999) | float
         <= db_rpo_hours | float }}
    hours_since_backup: "{{ latest_successful_backup.hours_ago | default(9999) }}"
    # backup_within_rpo: True = last backup is fresh enough
    # False = we've exceeded our RPO — bank is out of compliance right now

- name: Log backup status for this database
  ansible.builtin.debug:
    msg:
      - "RMAN Backup Status — {{ oracle_sid }} on {{ inventory_hostname }}"
      - "Last successful backup: {{ latest_successful_backup.end_time | default('NONE FOUND') }}"
      - "Hours since backup: {{ hours_since_backup }}h"
      - "RPO requirement: {{ db_rpo_hours }}h"
      - "Within RPO: {{ '✅ YES' if backup_within_rpo else '❌ NO — ALERT!' }}"
      - "Backup size: {{ latest_successful_backup.size_gb | default(0) }}GB"

- name: Fire PagerDuty P1 if database backup is outside RPO window
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "backup-rpo-miss-{{ oracle_sid }}-{{ inventory_hostname }}"
      payload:
        summary: >-
          🚨 BACKUP RPO MISSED: Oracle {{ oracle_sid }} on {{ inventory_hostname }}
          last successful backup was {{ hours_since_backup }} hours ago.
          RPO requirement is {{ db_rpo_hours }} hours.
          {{ 'No backups found in last 48 hours!' if hours_since_backup | float > 48
             else 'Backup is ' + (hours_since_backup | float - db_rpo_hours | float) | round(1) | string + ' hours overdue.' }}
          This is exactly the scenario that caused Incident 1 (43 days of failed backups).
        severity: critical
        source: ansible-backup-monitor
        custom_details:
          database: "{{ oracle_sid }}"
          host: "{{ inventory_hostname }}"
          hours_since_last_backup: "{{ hours_since_backup }}"
          rpo_requirement_hours: "{{ db_rpo_hours }}"
          last_job_status: "{{ rman_jobs | default([]) | map(attribute='status') | first | default('UNKNOWN') }}"
    status_code: [202]
  delegate_to: localhost
  when: not backup_within_rpo | bool

🔍 9. Oracle RMAN Crosscheck Role

roles/backup_rman_check/tasks/run_crosscheck.yml
---
# =====================================================================
# Run RMAN CROSSCHECK to verify backup pieces physically exist on disk
# This is the critical check that would have caught Incident 1:
# The RMAN catalog said backups existed, but the actual files on NAS
# were missing (NAS was full, RMAN deleted partial backups).
# CROSSCHECK verifies catalog entries against actual file existence.
# =====================================================================

- name: Run RMAN CROSSCHECK BACKUP against this database
  ansible.builtin.shell:
    cmd: |
      rman target {{ vault_oracle_rman_user }}/{{ vault_oracle_rman_pass }}@{{ oracle_sid }} << 'EOF'
      -- CROSSCHECK BACKUP: checks each backup piece in the RMAN catalog
      -- Verifies that the physical file actually EXISTS and is readable
      -- If a backup piece is on disk but corrupted: marks as EXPIRED
      -- If a backup piece is missing entirely: marks as EXPIRED
      -- Output: "crosschecked backup piece handle= AVAILABLE" (good)
      --         "crosschecked backup piece handle= EXPIRED"    (bad!)
      CROSSCHECK BACKUP;

      -- After crosscheck, list any backup pieces now marked as EXPIRED
      -- An EXPIRED backup cannot be used for recovery
      -- We capture this output to check if any pieces are expired
      LIST EXPIRED BACKUP SUMMARY;

      EXIT;
      EOF
    executable: /bin/bash
  register: rman_crosscheck_output
  become: true
  become_user: oracle
  no_log: true                               # Hides RMAN credentials from logs
  changed_when: false                        # Crosscheck marks metadata, but we treat as read
  environment:
    ORACLE_HOME: "{{ oracle_home }}"
    ORACLE_SID: "{{ oracle_sid }}"
    LD_LIBRARY_PATH: "{{ oracle_home }}/lib"
  timeout: 1800                              # 30 min timeout — crosscheck on large DBs takes time

- name: Check if any backup pieces are expired (physically missing or unreadable)
  ansible.builtin.set_fact:
    # Count lines containing EXPIRED in the LIST EXPIRED BACKUP SUMMARY output
    # "no expired backups found" means everything is intact
    expired_backup_count: >-
      {{ rman_crosscheck_output.stdout_lines
         | select('match', '.*EXPIRED.*')
         | reject('match', '.*no expired backups.*')
         | list | length }}

    # True if RMAN confirmed "no expired backups found" — all pieces intact
    all_backups_valid: >-
      {{ 'no expired backups found' in rman_crosscheck_output.stdout | lower }}

- name: Log RMAN crosscheck result
  ansible.builtin.debug:
    msg:
      - "RMAN Crosscheck Result — {{ oracle_sid }}"
      - "All backup pieces valid: {{ '✅ YES' if all_backups_valid else '❌ NO — EXPIRED PIECES FOUND' }}"
      - "Expired backup pieces: {{ expired_backup_count }}"

- name: Fire P1 alert if RMAN crosscheck found expired backup pieces
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "backup-rman-expired-{{ oracle_sid }}-{{ inventory_hostname }}"
      payload:
        summary: >-
          🚨 RMAN CROSSCHECK FAILED: {{ expired_backup_count }} expired backup
          pieces found for Oracle {{ oracle_sid }} on {{ inventory_hostname }}.
          These backup pieces are listed in the RMAN catalog but physically
          missing or corrupted on the backup storage. This database CANNOT
          be fully recovered from these backups. This is Incident 1 repeating.
          Immediate action: take a fresh full backup now.
        severity: critical
        source: ansible-backup-rman
        custom_details:
          database: "{{ oracle_sid }}"
          expired_piece_count: "{{ expired_backup_count }}"
          action_required: >-
            1. Run: RMAN> DELETE EXPIRED BACKUP; to clean catalog
            2. Check backup storage capacity (NAS free space)
            3. Run: RMAN> BACKUP DATABASE PLUS ARCHIVELOG; immediately
    status_code: [202]
  delegate_to: localhost
  when: not all_backups_valid | bool

roles/backup_veeam_check/tasks/query_veeam_api.yml
---
# =====================================================================
# Query Veeam B&R REST API to check all backup job statuses
# Veeam exposes its job data via REST API on port 9419
# This runs on localhost (AAP node) — no SSH to Veeam server needed
# =====================================================================

- name: Authenticate with Veeam B&R REST API to get a session token
  ansible.builtin.uri:
    url: "https://{{ veeam_server }}:{{ veeam_api_port }}/api/{{ veeam_api_version }}/token"
    method: POST
    body_format: form-urlencoded
    body:
      grant_type: password
      username: "{{ vault_veeam_username }}"
      password: "{{ vault_veeam_password }}"
      # Veeam uses OAuth2 token-based authentication
      # We POST credentials to /token endpoint and get back a Bearer token
      # This token is then used in the Authorization header for subsequent calls
    validate_certs: false              # Veeam often has self-signed SSL cert
    status_code: [200]
    timeout: 30
  register: veeam_auth_response
  delegate_to: localhost
  no_log: true                         # Hide credentials from AAP job logs

- name: Extract the access token from Veeam authentication response
  ansible.builtin.set_fact:
    veeam_token: "{{ veeam_auth_response.json.access_token }}"
    # access_token: the Bearer token for subsequent API calls
    # It's time-limited (usually 15-30 minutes) — enough for our audit

- name: Get list of all Veeam backup jobs
  ansible.builtin.uri:
    url: "https://{{ veeam_server }}:{{ veeam_api_port }}/api/{{ veeam_api_version }}/jobs"
    method: GET
    headers:
      Authorization: "Bearer {{ veeam_token }}"
      # Bearer token authentication — include in every API call
    validate_certs: false
    status_code: [200]
    timeout: 30
  register: veeam_jobs_response
  delegate_to: localhost

- name: Get the last session result for each backup job
  ansible.builtin.uri:
    url: "https://{{ veeam_server }}:{{ veeam_api_port }}/api/{{ veeam_api_version }}/jobs/{{ item.id }}/jobSessions?limit=1"
    # jobSessions: the history of individual backup runs for this job
    # limit=1: we only want the most recent run
    method: GET
    headers:
      Authorization: "Bearer {{ veeam_token }}"
    validate_certs: false
    status_code: [200]
    timeout: 30
  register: veeam_job_sessions
  loop: "{{ veeam_jobs_response.json.data }}"
  loop_control:
    label: "Getting sessions for: {{ item.name }}"
  delegate_to: localhost

- name: Build Veeam job status summary from API responses
  ansible.builtin.set_fact:
    veeam_job_statuses: >-
      {{ veeam_job_statuses | default([]) + [{
        'job_name': item.item.name,
        'job_id': item.item.id,
        'job_type': item.item.type,
        'last_result': (item.json.data | first).result.result
                       if item.json.data | length > 0
                       else 'Never Run',
        'last_end_time': (item.json.data | first).endTime
                         if item.json.data | length > 0
                         else 'Never',
        'duration_minutes': ((item.json.data | first).progressPercent | int)
                            if item.json.data | length > 0
                            else 0,
        'hours_ago': (((ansible_date_time.epoch | int)
                       - ((item.json.data | first).endTime
                          | to_datetime('%Y-%m-%dT%H:%M:%SZ')
                         ).strftime('%s') | int) / 3600) | round(1)
                     if (item.json.data | length > 0
                         and (item.json.data | first).endTime is defined)
                     else 9999,
        'failed': (item.json.data | first).result.result == 'Failed'
                  if item.json.data | length > 0
                  else true
      }] }}
      # Explanation of key fields:
      #   last_result: 'Success', 'Warning', or 'Failed'
      #     Success: backup completed, all VMs fully protected
      #     Warning: backup completed but some VMs had issues (Incident 2 scenario)
      #     Failed: backup did not complete
      #   hours_ago: calculated from endTime timestamp vs current epoch
      #     Used to check RPO compliance
      #   failed: boolean — true if last_result is Failed OR no runs found
  loop: "{{ veeam_job_sessions.results }}"
  loop_control:
    label: "{{ item.item.name }}"

- name: Identify failed or overdue Veeam jobs
  ansible.builtin.set_fact:
    failed_veeam_jobs: >-
      {{ veeam_job_statuses
         | selectattr('failed', 'equalto', true)
         | list }}
    warning_veeam_jobs: >-
      {{ veeam_job_statuses
         | selectattr('last_result', 'equalto', 'Warning')
         | list }}
    # Warning jobs: completed but flagged — possible disk exclusion (Incident 2)
    overdue_veeam_jobs: >-
      {{ veeam_job_statuses
         | selectattr('hours_ago', 'ge', rpo_definitions.windows_vms.rpo_hours | float)
         | list }}

    cmd: |
      sqlplus -S {{ vault_oracle_monitor_user }}/{{ vault_oracle_monitor_pass }}@{{ oracle_sid }} << 'EOF'
      SET PAGESIZE 0 FEEDBACK OFF HEADING OFF COLSEP '|'
      -- Find the most recent COMPLETED full database backup
      -- We'll restore this specific backup for our test
      SELECT
        BS_KEY,                            -- Backup set key (unique identifier)
        TO_CHAR(COMPLETION_TIME, 'YYYY-MM-DD HH24:MI:SS'),  -- When it completed
        INPUT_BYTES/1024/1024/1024,        -- Size in GB

      WHERE INPUT_TYPE = 'DB FULL'         -- Full database backup only
        AND STATUS = 'AVAILABLE'           -- Must be available (not expired)
        AND COMPLETION_TIME > SYSDATE - 7  -- Within last 7 days
      ORDER BY COMPLETION_TIME DESC
      FETCH FIRST 1 ROW ONLY;             -- Most recent only
      EXIT;
      EOF
    executable: /bin/bash
  register: backup_to_restore
  become: true
  become_user: oracle
  no_log: true
  changed_when: false

🎯 16. Interview Prep

Q: What is RMAN CROSSCHECK and why is it critical for banking?

RMAN maintains a catalog (repository) of all backup metadata — what was backed up, when, and where the backup pieces are stored. However, the catalog records can become out of sync with reality. Someone might manually delete backup files from the NAS, the NAS might run out of space and silently delete partial backups, or a disk failure might corrupt backup files that still appear as valid in the catalog.

RMAN CROSSCHECK physically verifies that every backup piece listed in the catalog actually exists on the storage medium and is accessible. Any piece that cannot be found or is corrupted is marked as EXPIRED. A subsequent LIST EXPIRED BACKUP shows exactly what's missing.

For banking: Incident 1 happened because RMAN ran nightly, the catalog said backups existed, but the backup files were being deleted by RMAN itself due to NAS being full. CROSSCHECK would have immediately shown expired pieces — alerting the team that no valid backup existed. Without CROSSCHECK, the first indication of failure was a production incident requiring restore.

Q: How do you generate RBI-compliant evidence for restore tests?

RBI IT Framework §9 requires banks to demonstrate that their backup and recovery procedures actually work. Evidence must include: what was restored, from which backup, when the test was performed, the results of the test, and who authorized it.

Our automation generates an HTML evidence certificate containing: the backup set key and completion timestamp, the restore start and end time, restore duration, integrity check results (table names and row counts from the restored database), the Ansible job ID for traceability, and the run timestamp with the approving engineer's AAP username.

The certificate is saved to a write-once NFS compliance store with date-stamped filenames. RBI inspectors can request these certificates for any quarter and verify both the test occurred and what the results were. The automation ensures tests run on schedule and evidence is captured consistently — eliminating the manual "we did a restore drill but forgot to document it" problem.

Q: How does the Veeam Warning status detection prevent the Incident 2 scenario?

Veeam marks a backup job as "Warning" (not "Failed") when the job completes but encounters non-fatal issues — including when some VM disks are excluded from the backup scope. The Veeam console shows a green-ish warning state, which looks acceptable at first glance. Most monitoring tools only alert on "Failed" status — missing the Warning state entirely.

Our automation explicitly checks for Warning status (not just Failed) and sends a dedicated Slack alert explaining that Warning status can indicate disk exclusions. The alert tells engineers to open the Veeam console and check the job statistics for excluded items. This way, an accidental exclusion that caused Incident 2 would have been caught on the next daily check rather than discovered 8 months later during an actual restore.

We also separately check the backup size (TotalSize > 0) because a job that completes but backs up zero data can show as Success in some Veeam configurations — another edge case our validation catches.

Q: What is RPO and how does your automation validate it?

RPO (Recovery Point Objective) defines the maximum acceptable data loss in terms of time. If CBS has an RPO of 15 minutes, the bank accepts losing at most 15 minutes of Core Banking transactions if the primary database fails right now.

Our automation validates RPO by calculating the age of the most recent successful backup and comparing it against the defined RPO threshold. For Oracle databases: we query V$RMAN_BACKUP_JOB_DETAILS, find the most recent row where STATUS = 'COMPLETED', and calculate (SYSDATE - END_TIME) * 24 to get hours since the last backup. If this value exceeds rpo_hours from our rpo_definitions variable, the RPO is already violated — even before any incident occurs.

This matters because by the time a production failure occurs, it's too late to discover the backup is 4 hours old when the RPO is 15 minutes. Daily RPO validation means the bank's leadership knows every morning whether their recovery objectives are being met.
