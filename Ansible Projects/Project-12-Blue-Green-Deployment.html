Project 12: Blue-Green Deployment Automation using Red Hat AAP

SecureBank's Core Banking System (CBS) releases a new version every 6 weeks. Each release must be deployed to production with zero downtime and an instant rollback capability guaranteed within 60 seconds if anything goes wrong post-cutover. Traditional rolling deployments (Project 1) are appropriate for patch releases, but major CBS versions — involving database schema changes, new API contracts, and JVM configuration changes — need a stronger guarantee: the old version must remain fully operational and instantly reactivatable until the new version has been validated under real production traffic. This is the Blue-Green deployment pattern. SecureBank runs two identical CBS environments: Blue (currently live, serving 100% of traffic) and Green (idle, receives the new version). The AAP workflow deploys to Green, runs automated acceptance tests, performs a health gate, executes a traffic switch via the F5 LTM, monitors production metrics for 10 minutes post-switch, and offers one-click rollback at any point. The idle environment is also used for UAT and load testing between releases — making infrastructure cost-effective while providing production-grade deployment safety.

🏦 2. Real-Time Banking Scenario

The Story: CBS v5.2.0 is ready for production. It includes a new loan origination module, 3 schema migrations, and updated payment processing logic. Release is scheduled for Saturday 11:00 PM — low-traffic window but still live banking hours.

Before Blue-Green automation: The release team takes a 90-minute maintenance window. All 12 CBS servers are stopped, the new WAR deployed, all 12 restarted. If anything is wrong, the rollback is deploying the old WAR back — another 45 minutes minimum. One bad release in 2023 caused a 2h 15min CBS outage on a Saturday night, catching late-night NEFT transfers. RBI issued a compliance notice.

After Blue-Green automation: At 11:00 PM on Saturday, Senior Engineer Rajesh launches the BG-Deploy-CBS AAP workflow with survey: app_version=5.2.0, release_environment=green, run_schema_migration=true. By 11:12 PM, the Green CBS cluster has v5.2.0 running and all smoke tests are passing. Rajesh reviews the smoke test report and approves the cutover. At 11:14 PM, the F5 LTM VIP switches from Blue pool to Green pool — CBS v5.2.0 is live. At 11:24 PM, the 10-minute monitoring gate confirms error rate 0.02% (below 1% threshold) and transaction latency unchanged. The workflow completes. Blue remains running as instant rollback insurance. At 11:30 PM, Rajesh goes to sleep. Total live deployment time: 24 minutes. Zero downtime. Zero customer impact.

❗ 3. Problem Statement

  • Each CBS release requires a planned maintenance window causing customer-visible downtime — 24×7 banking is incompatible with a deployment model that requires stopping all servers.
  • Rollback after a bad deployment is a full re-deployment of the old version — minimum 45 minutes of additional downtime on top of the initial outage.
  • No automated smoke tests before traffic is switched — the new version goes live and problems are discovered by customers or the NOC, not by pre-cutover validation.
  • Schema migrations run during the maintenance window with no backward-compatibility guarantee — if rollback is needed, the old code may not work with the migrated schema.
  • No structured post-deployment monitoring — issues in the first 10 minutes post-release are discovered through support calls, not automated alerting with auto-rollback.

🧑‍💻 5. Existing Manual Process (Before Automation)

  1. Release engineer sends maintenance window notification email 48 hours in advance.
  2. At window start: app team stops all 12 CBS Tomcat instances manually (SSH, stop script per server).
  3. DBA runs schema migration SQL scripts manually on Oracle RAC.
  4. App team deploys new WAR to each server via SCP, starts Tomcat, manually checks logs on each.
  5. Smoke testing: engineer manually clicks through the CBS web UI and checks a few key screens.
  6. If anything is wrong: deploy old WAR back (another 45 min), notify customers of extended outage.
  7. Post-deployment: no structured monitoring — NOC watches dashboards for 30 min then disperses.

🛠️ 6. Automated Solution Design

The Blue-Green deployment pipeline runs as a 7-stage AAP Workflow:

StageOperationGate
0 — Pre-flightVerify Green environment is idle, confirm Blue is healthy, check F5 connectivityAll checks pass before any change
1 — Schema MigrationRun Flyway/Liquibase backward-compatible migrations on Oracle RACMigration completes without errors; verify both old and new code can query key tables
2 — Green DeployStop Green Tomcats, deploy new WAR to all Green servers, start TomcatAll Green Tomcat instances healthy on port 8443
3 — Smoke TestsRun 25 automated API-level smoke tests against Green cluster (direct IP, bypassing LB)All 25 smoke tests pass; no 5xx responses; critical paths validated
4 — Approval GateRelease manager reviews smoke test report and approves traffic switchManual approval required before traffic touches Green
5 — Traffic CutoverF5 LTM VIP pool member change: Blue pool → Green pool (atomic, <5 sec)LB health check confirms Green pool members active; synthetic test through VIP passes
6 — Post-Deploy Monitor10-minute monitoring window: poll CBS error rate and latency from Prometheus; auto-rollback if threshold breachedError rate <1%, P95 latency <500ms for 10 minutes → release complete

💻 11. Complete Project Code (Line-by-Line Explained)

Role: bg_preflight — Environment Readiness Checks

roles/bg_preflight/tasks/main.yml
---
- name: Record deployment start epoch for RTO clock
  ansible.builtin.set_fact:
    deploy_start_epoch: "{{ ansible_date_time.epoch | int }}"
    active_color: "{{ 'blue' if release_environment == 'green' else 'green' }}"
    deploy_color: "{{ release_environment }}"

- name: Verify Blue (currently-live) cluster is fully healthy before we touch anything
  ansible.builtin.uri:
    url: "https://{{ hostvars[item].ansible_host }}:{{ tomcat_port }}/securecore/health"
    status_code: 200
    validate_certs: false
    timeout: 10
  loop: "{{ groups['cbs_' + active_color] }}"
  loop_control:
    label: "{{ item }}"
  delegate_to: localhost
  register: blue_health_checks

- name: Fail preflight if any currently-live server is unhealthy
  ansible.builtin.fail:
    msg: >-
      PREFLIGHT FAILED: {{ active_color | upper }} environment has unhealthy servers.
      Refusing to proceed with deployment — fix existing production issues first.
      Failing servers: {{ blue_health_checks.results
                         | selectattr('status', 'ne', 200)
                         | map(attribute='item') | list | join(', ') }}
  when: blue_health_checks.results | selectattr('status', 'ne', 200) | list | length > 0

- name: Verify Green environment is idle (not actively serving traffic)
  ansible.builtin.uri:
    url: "{{ f5_api_base }}/ltm/pool/{{ f5_green_pool }}/stats"
    method: GET
    headers:
      Authorization: "Basic {{ (vault_f5_user + ':' + vault_f5_pass) | b64encode }}"
    validate_certs: false
    return_content: true
  register: green_pool_stats
  delegate_to: localhost
  no_log: true

- name: Confirm F5 VIP is currently pointing to Blue pool
  ansible.builtin.uri:
    url: "{{ f5_api_base }}/ltm/virtual/{{ f5_cbs_vip }}"
    method: GET
    headers:
      Authorization: "Basic {{ (vault_f5_user + ':' + vault_f5_pass) | b64encode }}"
    validate_certs: false
    return_content: true
  register: vip_current_config
  delegate_to: localhost
  no_log: true

- name: Fail if VIP is already pointing to Green (deployment already in progress?)
  ansible.builtin.fail:
    msg: >-
      PREFLIGHT FAILED: F5 VIP {{ f5_cbs_vip }} is already pointing to the
      {{ f5_green_pool }} pool. Either a previous deployment is in progress or
      Green is already live. Investigate before proceeding.
  when: f5_green_pool in vip_current_config.json.pool | default('')

- name: Verify deployment artifact exists in Nexus before starting
  ansible.builtin.uri:
    url: "{{ war_artifact_url }}"
    method: HEAD
    status_code: 200
  delegate_to: localhost
  register: artifact_check

- name: Set preflight passed fact
  ansible.builtin.set_fact:
    preflight_passed: true
    preflight_timestamp: "{{ ansible_date_time.iso8601 }}"
Line-by-Line Explanation
active_color / deploy_color — Computed at play start from the release_environment survey variable. If deploying to green, active_color=blue (currently live). This makes every subsequent task color-agnostic — the same role works for deploying to either color without hardcoded "blue" or "green" references in task logic.
groups['cbs_' + active_color] — Dynamic group name construction. Instead of hardcoding groups['cbs_blue'], concatenating the color variable allows the same task to check whichever environment is currently live. This is how one preflight role handles both "deploy to green while blue is live" and "deploy to blue while green is live" (the rollback scenario).
method: HEAD on artifact check — A HEAD request to the Nexus artifact URL checks existence without downloading the 80MB WAR file. If the artifact doesn't exist (wrong version number in survey, build failed), the deployment fails at preflight — before any changes are made to any server.
Checking VIP current pool: f5_green_pool in vip_current_config.json.pool — Guards against launching a second parallel deployment when one is already in progress. If Green is already live (VIP pointing to green pool), deploying to it again would break the currently-live green environment. The preflight detects and blocks this dangerous scenario.

Role: bg_schema_migrate — Backward-Compatible Schema Migration

roles/bg_schema_migrate/tasks/main.yml
---
- name: Skip schema migration if not requested
  ansible.builtin.meta: end_play
  when: not run_schema_migration | bool

- name: Validate Flyway migration scripts exist for this version
  ansible.builtin.stat:
    path: "{{ flyway_migrations_dir }}"
  register: migrations_dir_stat

- name: Fail if migration directory for this version doesn't exist
  ansible.builtin.fail:
    msg: >-
      Schema migration directory {{ flyway_migrations_dir }} not found.
      Cannot run migration for version {{ app_version }}.
      Ensure DB migrations are included in the release package.
  when: not migrations_dir_stat.stat.exists

- name: Take RMAN backup before schema migration (safety net)
  ansible.builtin.shell: >
    su - oracle -c "
    export ORACLE_HOME=/u01/app/oracle/product/19.0.0/dbhome_1;
    export ORACLE_SID=CBSPROD;
    echo 'BACKUP DATABASE PLUS ARCHIVELOG;' |
    {{ oracle_home }}/bin/rman target / catalog {{ vault_rman_catalog_conn }}"
  delegate_to: "{{ groups['oracle_rac'][0] }}"
  become: true
  become_user: oracle
  no_log: true
  async: 3600
  poll: 30
  register: pre_migration_backup

- name: Run Flyway schema migration (dry-run first)
  ansible.builtin.shell: >
    {{ flyway_install_dir }}/flyway
    -url="{{ oracle_jdbc_url }}"
    -user="{{ vault_oracle_flyway_user }}"
    -password="{{ vault_oracle_flyway_pass }}"
    -locations="filesystem:{{ flyway_migrations_dir }}"
    -dryRunOutput=/tmp/flyway-dryrun-{{ app_version }}.sql
    migrate
  register: flyway_dryrun
  delegate_to: "{{ groups['oracle_rac'][0] }}"
  no_log: true
  changed_when: false

- name: Review dry-run output before applying
  ansible.builtin.debug:
    msg: "Flyway dry-run SQL preview: {{ flyway_dryrun.stdout_lines[-5:] | join(' | ') }}"

- name: Apply Flyway schema migration for real
  ansible.builtin.shell: >
    {{ flyway_install_dir }}/flyway
    -url="{{ oracle_jdbc_url }}"
    -user="{{ vault_oracle_flyway_user }}"
    -password="{{ vault_oracle_flyway_pass }}"
    -locations="filesystem:{{ flyway_migrations_dir }}"
    migrate
  register: flyway_migration_result
  delegate_to: "{{ groups['oracle_rac'][0] }}"
  no_log: true
  changed_when: "'Successfully applied' in flyway_migration_result.stdout"

- name: Verify backward compatibility — old app version still queries successfully
  ansible.builtin.shell: >
    su - oracle -c "
    export ORACLE_HOME=/u01/app/oracle/product/19.0.0/dbhome_1;
    export ORACLE_SID=CBSPROD;
    echo 'SELECT COUNT(*) FROM accounts;' |
    {{ oracle_home }}/bin/sqlplus -S {{ vault_oracle_app_user }}/{{ vault_oracle_app_pass }}@CBSPROD"
  delegate_to: "{{ groups['oracle_rac'][0] }}"
  register: backward_compat_check
  changed_when: false
  no_log: true

- name: Fail if backward compatibility check fails after migration
  ansible.builtin.fail:
    msg: >-
      CRITICAL: Backward compatibility check failed after schema migration.
      The existing Blue (v{{ active_app_version }}) cannot query key tables
      after the migration. Rolling back migration is required.
  when: backward_compat_check.rc != 0
Line-by-Line Explanation
Flyway -dryRunOutput — Flyway's dry-run mode generates the SQL that WOULD be applied without executing it. Logging this to a file and displaying the last 5 lines gives the release manager visibility into exactly what SQL will run against the production database before approving. The dry-run output is archived as part of the deployment receipt.
Pre-migration RMAN backup — An additional full backup taken immediately before schema migration. This is separate from the nightly backup (Project 8). If a migration goes wrong and needs to be rolled back at the database level, this backup is from minutes ago — not hours. The async: 3600 / poll: 30 handles the multi-minute backup without SSH timeout.
Backward compatibility validation — After migration, we verify that the OLD application version's key queries (SELECT COUNT(*) FROM accounts) still work. This confirms the migration is truly backward-compatible — both Blue (old version) and Green (new version) can coexist on the same schema during the cutover window. If this check fails, the cutover cannot proceed safely.

Role: bg_deploy_green — Deploy New Version to Green Environment

roles/bg_deploy_green/tasks/main.yml
---
- name: Stop all Green Tomcat instances before deployment
  ansible.builtin.systemd:
    name: "{{ tomcat_service }}"
    state: stopped
  delegate_to: "{{ item }}"
  loop: "{{ groups['cbs_' + deploy_color] }}"

- name: Back up current WAR on Green servers (one version rollback safety)
  ansible.builtin.shell: >
    cp {{ tomcat_webapps_dir }}/securecore.war
       {{ tomcat_webapps_dir }}/securecore.war.{{ ansible_date_time.iso8601_basic_short }}.bak
  args:
    creates: "{{ tomcat_webapps_dir }}/securecore.war.{{ ansible_date_time.iso8601_basic_short }}.bak"
  delegate_to: "{{ item }}"
  loop: "{{ groups['cbs_' + deploy_color] }}"
  failed_when: false

- name: Download new WAR from Nexus artifact repository
  ansible.builtin.get_url:
    url: "{{ war_artifact_url }}"
    dest: "/tmp/securecore-{{ app_version }}.war"
    checksum: "{{ war_checksum }}"
    owner: svcappuser
    mode: '0640'
  delegate_to: "{{ groups['cbs_' + deploy_color][0] }}"

- name: Distribute WAR to all Green servers in parallel
  ansible.builtin.copy:
    src: "/tmp/securecore-{{ app_version }}.war"
    dest: "{{ tomcat_webapps_dir }}/securecore.war"
    owner: svcappuser
    group: svcappgrp
    mode: '0640'
    remote_src: false
  delegate_to: "{{ item }}"
  loop: "{{ groups['cbs_' + deploy_color] }}"

- name: Remove previous Tomcat exploded webapp directory (force redeploy)
  ansible.builtin.file:
    path: "{{ tomcat_webapps_dir }}/securecore"
    state: absent
  delegate_to: "{{ item }}"
  loop: "{{ groups['cbs_' + deploy_color] }}"

- name: Start all Green Tomcat instances
  ansible.builtin.systemd:
    name: "{{ tomcat_service }}"
    state: started
  delegate_to: "{{ item }}"
  loop: "{{ groups['cbs_' + deploy_color] }}"

- name: Wait for all Green Tomcat instances to be listening on port
  ansible.builtin.wait_for:
    host: "{{ hostvars[item].ansible_host }}"
    port: "{{ tomcat_port }}"
    delay: 10
    timeout: 180
  loop: "{{ groups['cbs_' + deploy_color] }}"
  delegate_to: localhost

- name: Validate all Green Tomcat health endpoints return 200
  ansible.builtin.uri:
    url: "https://{{ hostvars[item].ansible_host }}:{{ tomcat_port }}/securecore/health"
    status_code: 200
    validate_certs: false
    timeout: 15
  loop: "{{ groups['cbs_' + deploy_color] }}"
  delegate_to: localhost
  retries: 5
  delay: 15
  register: green_health_after_deploy

- name: Confirm deployed version matches expected version
  ansible.builtin.uri:
    url: "https://{{ hostvars[groups['cbs_' + deploy_color][0]].ansible_host }}:{{ tomcat_port }}/securecore/version"
    return_content: true
    validate_certs: false
  register: deployed_version_check
  delegate_to: localhost

- name: Fail if deployed version does not match expected
  ansible.builtin.fail:
    msg: >-
      VERSION MISMATCH: Expected {{ app_version }} but deployed version
      endpoint returned: {{ deployed_version_check.content }}.
      Do not proceed with cutover.
  when: app_version not in deployed_version_check.content
Line-by-Line Explanation
delegate_to: "{{ item }}" inside loop — A loop over all Green servers with delegate_to per item. This runs each task on the target server rather than the Ansible control node. Download is done once to the first Green server (to avoid downloading the 80MB WAR 6 times), then copy distributes it — more efficient than 6 parallel downloads from Nexus.
state: absent on exploded webapp dir — Tomcat auto-deploys by extracting the WAR to a directory (securecore/). If this directory exists from the previous deployment, Tomcat may not re-extract the new WAR on startup, leaving the old extracted code in place even though the new WAR file is present. Deleting the exploded directory forces a clean re-extract on every deployment.
Version confirmation via /securecore/version endpoint — After startup, we call a dedicated version endpoint (a simple servlet that returns the build version from the MANIFEST.MF). This confirms the WAR that was deployed is the one that actually started, catching scenarios where Tomcat loaded a cached version or the wrong WAR was placed in the webapps directory.

Line-by-Line Explanation
Direct IP bypass of LB — Smoke tests hit the Green servers via their direct IPs, not through the F5 LTM VIP. The VIP still points to Blue at this stage. Testing via VIP would test the Blue environment. Testing via direct Green IP validates that the new code works independently before we commit to switching traffic. This is the defining characteristic of Blue-Green pre-cutover testing.
X-Test-Mode: "ansible-smoke-test" header — Allows the CBS application to identify smoke test traffic and exclude it from business metrics (transaction counts, fraud scoring, reporting). A smoke test fund transfer should not appear in the day's transaction reports. The application reads this header and routes the request through a test codepath that uses test account data but exercises the same business logic.
failed_when: false on the test loop — Allows all smoke tests to run even if some fail early, giving a complete picture of which tests pass and which fail. Without this, the first failed test would abort the entire loop and the release team would only know about the first failure, not all failures. The explicit assertion task after the loop evaluates all results at once.
Critical vs non-critical test distinction — Critical tests (health, account balance, fund transfer) block the cutover if they fail. Non-critical tests (NACH mandate query) produce warnings but don't block. This allows the release to proceed if a non-critical feature has a minor issue while ensuring core banking operations are verified.

Line-by-Line Explanation
PATCH /ltm/virtual/{{ f5_cbs_vip }} with body: { pool: green_pool } — The F5 BIG-IP iControl REST API allows changing the default pool of a virtual server with a single PATCH call. This is what makes the traffic switch nearly instantaneous (under 5 seconds) and atomic — there is no period where both pools are active simultaneously. All new connections after the PATCH go to Green; in-flight connections to Blue continue until they complete.
VIP verification before proceeding — After the PATCH, we immediately GET the virtual server config to confirm the pool assignment changed. This catches the rare case where the F5 API returns 200 but the change didn't persist (e.g., a config sync issue in an active-standby F5 pair). Without this check, the monitoring phase would be monitoring the wrong environment.
Synthetic E2E test through VIP — After confirming the F5 config, we hit the actual VIP IP (the same IP that customers reach) to confirm traffic is flowing to Green through the LB. This validates the entire path: DNS → VIP → Green pool member → Green Tomcat → health response. The retry loop handles the brief period where existing F5 connections are being drained.

Role: bg_post_monitor — 10-Minute Monitoring Gate with Auto-Rollback

roles/bg_post_monitor/tasks/main.yml
---
- name: Begin 10-minute post-deployment monitoring window
  ansible.builtin.set_fact:
    monitor_start_epoch: "{{ ansible_date_time.epoch | int }}"
    monitor_checks_passed: 0
    monitoring_active: true

- name: Run post-deployment monitoring polls (every 60 seconds for 10 minutes)
  block:
    - name: Poll CBS error rate from Prometheus
      ansible.builtin.uri:
        url: "{{ prometheus_url }}/api/v1/query"
        method: GET
        body_format: form-urlencoded
        body:
          query: "{{ cbs_error_rate_query }}"
        headers:
          Authorization: "Bearer {{ vault_prometheus_token }}"
        return_content: true
      register: error_rate_response
      delegate_to: localhost
      loop: "{{ range(post_monitor_minutes) | list }}"
      loop_control:
        label: "Minute {{ item + 1 }} of {{ post_monitor_minutes }}"
      vars:
        current_error_rate: >-
          {{ error_rate_response.json.data.result[0].value[1] | float
             if error_rate_response.json.data.result | length > 0
             else 0.0 }}
      failed_when: >-
        current_error_rate | float > error_rate_threshold | float

  rescue:
    - name: AUTO-ROLLBACK triggered — error rate exceeded threshold
      ansible.builtin.debug:
        msg: >-
          POST-DEPLOY MONITORING: Error rate {{ current_error_rate }} exceeds
          threshold {{ error_rate_threshold }}. Initiating automatic rollback.

    - name: Execute automatic rollback — switch F5 back to Blue pool
      ansible.builtin.uri:
        url: "{{ f5_api_base }}/ltm/virtual/{{ f5_cbs_vip }}"
        method: PATCH
        body_format: json
        body:
          pool: "/Common/{{ f5_blue_pool }}"
        headers:
          Content-Type: "application/json"
          Authorization: "Basic {{ (vault_f5_user + ':' + vault_f5_pass) | b64encode }}"
        validate_certs: false
        status_code: 200
      delegate_to: localhost
      no_log: true

    - name: Notify CISO and Release Manager of automatic rollback
      ansible.builtin.uri:
        url: "{{ vault_slack_webhook_url }}"
        method: POST
        body_format: json
        body:
          text: >-
            🚨 *AUTOMATIC ROLLBACK TRIGGERED* — CBS v{{ app_version }}
            Error rate exceeded {{ error_rate_threshold * 100 }}% threshold.
            Blue pool (v{{ active_app_version }}) restored.
            Total Green exposure time: {{ ansible_date_time.epoch | int - cutover_start_epoch | int }}s.
            Release team: investigate Green logs before retry.
      delegate_to: localhost

    - name: Fail the workflow after rollback
      ansible.builtin.fail:
        msg: "Deployment of v{{ app_version }} rolled back due to high error rate post-cutover."

- name: Monitoring gate passed — deployment successful
  ansible.builtin.debug:
    msg: >-
      ✅ POST-DEPLOY MONITORING PASSED — CBS v{{ app_version }} stable for
      {{ post_monitor_minutes }} minutes. Error rate within threshold.
      Deployment COMPLETE. Blue pool kept warm for manual rollback if needed.
Line-by-Line Explanation
block/rescue pattern for auto-rollback — The monitoring loop runs inside a block. When failed_when triggers (error rate exceeds threshold), Ansible's rescue section executes — triggering the F5 switch back to Blue, sending notifications, and then explicitly failing the workflow. This is the cleanest pattern for "run a monitor, rollback on failure" in Ansible.
loop: "{{ range(post_monitor_minutes) | list }}" — Creates a list [0, 1, 2, ... 9] for a 10-minute monitoring window. Each iteration polls Prometheus once, with the loop naturally pausing between iterations via the Prometheus query itself (each query takes a second or two). For a true 60-second poll interval, add ansible.builtin.pause: seconds: 58 before the URI task inside the loop.
error_rate_response.json.data.result[0].value[1] | float — Parses the Prometheus instant query response format. The result array contains metric objects; value[1] is the current metric value (a string in Prometheus's JSON format). Converting to float allows numeric comparison with the threshold. The default of 0.0 when no result exists handles the case where the CBS metric has no data yet (normal in the first 30 seconds post-cutover).
Blue pool kept running throughout — The entire monitoring window, the Blue cluster is still running the old version. This is what makes instant rollback possible: there is no "old version teardown" step. Blue only gets stopped (or repurposed for the next release) after the deployment is confirmed successful and the team manually runs a "Blue cleanup" job — typically the next day.

🎯 15. Interview Preparation

Scenario-Based Questions

Q: What is the difference between Blue-Green deployment and Rolling deployment, and when do you use each?
Rolling deployment (Project 1): replaces servers one at a time within a single pool — all servers eventually run the new version, but at any given moment some run old and some run new. Best for: patch releases, minor updates, no schema changes, where mixed-version briefly is acceptable. Blue-Green: two complete identical environments — one runs the new version while the other serves 100% of traffic until switch. Best for: major version releases, database schema changes, API contract changes, where you need instant rollback and zero mixed-version exposure. Blue-Green's downside: requires double the infrastructure. Banking prefers Blue-Green for major CBS releases precisely because instant rollback capability is worth the infrastructure cost.
Q: How do you handle database schema migrations safely in a Blue-Green deployment?
Three rules for Blue-Green-safe schema migrations: (1) Additive only — add new columns/tables, never remove or rename existing ones that Blue still uses. (2) Backward-compatible — both old (Blue) and new (Green) versions must be able to read from and write to the schema simultaneously during the cutover window. (3) Two-phase migration for breaking changes: Phase 1 (this release): add new structure, keep old structure. Phase 2 (next release after Blue is fully retired): remove old structure. We validate backward compatibility explicitly after migration by running key queries as the application user against the migrated schema before proceeding to deploy Green.
Q: What happens to in-flight transactions when the F5 switches from Blue to Green?
The F5 LTM's pool switch only affects NEW connections — in-flight connections to Blue continue until they complete naturally. F5's connection persistence tables maintain existing sessions to Blue servers until those connections close. This is why the switch is zero-downtime: no existing transaction is interrupted. The monitoring window is important precisely to catch any transactions that start on Green and reveal problems not caught by smoke tests. Banks with longer transaction durations (loan origination) sometimes configure a persistence timeout on the F5 to ensure all Blue connections drain completely before Blue is considered idle.

Architecture & Production Questions

Q: How long does the Blue environment stay running after a successful Green deployment?
At SecureBank, Blue stays running for at least 24 hours after a successful Green deployment. This covers: (1) Any issues discovered the next business day that weren't visible in the 10-minute monitoring window (e.g., a monthly batch job that runs at 3 AM). (2) The formal sign-off period — release is only "closed" after business sign-off the next morning. After sign-off, a "BG-Retire-Blue" job template is manually launched to stop Blue servers and redeploy them as the new Green (for the next release). This keeps infrastructure cost bounded — Blue is repurposed, not permanently idle.
Q: Could you run Blue and Green simultaneously for an A/B test or canary release using the same F5 setup?
Yes — with F5 LTM's ratio-based pool membership, you can send a percentage of traffic to Green (e.g., 10% Green, 90% Blue) for a canary validation before full cutover. This is a hybrid pattern between Blue-Green and canary. The F5 PATCH would set pool member ratios rather than switching the entire pool. In Ansible, this means two sequential PATCH calls: (1) add Green pool members with ratio=10; (2) after canary validation, patch to ratio=100 and remove Blue members. SecureBank uses full Blue-Green for CBS (too risky for partial exposure), but uses canary via F5 ratios for the Mobile Banking API Gateway where partial exposure is acceptable.
Q: How do you ensure the BG-Rollback job template is ALWAYS available, even if the main deployment AAP controller is under load?
BG-Rollback is configured as a standalone job template with the highest AAP scheduler priority and a dedicated execution node labeled "rollback-priority". It has no dependency on any workflow or other job — it can be launched independently. Additionally, a physical printed "break-glass" runbook containing the single curl command to execute the F5 API switch is kept in the NOC — completely bypassing AAP if needed. The F5 API switch command itself is simple enough that a NOC engineer can execute it directly in under 30 seconds with the break-glass credentials from CyberArk PAM.

📝 16. Key Learnings, Mistakes & Resume Points

Key Learnings

  • Blue-Green's core guarantee is that the old version is NEVER stopped until the new version is proven stable — this is what makes instant rollback possible and what distinguishes it from rolling deployments.
  • Smoke tests must hit Green directly (bypassing LB) — testing through the VIP before the switch validates the wrong environment.
  • Schema migrations must be backward-compatible — both Blue and Green must work on the same schema simultaneously during the cutover window.
  • The 10-minute post-cutover monitoring gate with auto-rollback is the most valuable safety net in the entire pipeline — issues that survive smoke tests often manifest only under real production traffic patterns.

Common Mistakes

  • Stopping Blue before Green is fully validated — eliminates rollback capability and converts Blue-Green into a regular deployment with downtime.
  • Smoke testing through the LB/VIP instead of direct Green IP — tests the wrong environment (Blue is still live on the VIP).
  • Running non-backward-compatible schema migrations — if rollback is needed, old Blue code can't work with the migrated schema.
  • Not verifying the VIP switch completed after the F5 PATCH — the API can return 200 while the change hasn't fully propagated in an HA F5 pair.

Production Best Practices

  • Keep BG-Rollback as a standalone, always-available job template — never bury rollback capability inside a workflow that might be blocked.
  • Always run preflight before touching anything — verify the currently-live environment is healthy BEFORE deploying to the idle environment. Never start a Blue-Green deploy on top of an already-degraded Blue cluster.
  • Use version endpoint validation after Green deploy — don't assume the right WAR was deployed; confirm via the application itself.
  • Set post-deploy monitoring threshold conservatively (1% error rate, not 5%) — it's better to auto-rollback from a false positive and investigate than to let a real issue affect customers for 10 minutes before triggering rollback.
