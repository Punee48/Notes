Project 08: VMware vSphere VM Validation & Infrastructure Health Monitoring

ABC Global Bank runs its entire infrastructure on VMware vSphere 8.0 — 4 vCenter clusters across 3 data centers managing 1,200 virtual machines. VM health validation, stale snapshot detection and cleanup, datastore capacity monitoring, HA/DRS cluster health, and VMware Tools version compliance are all checked manually by the virtualization team — a process that misses critical issues and consumes 20+ hours per week. This project automates complete vSphere infrastructure health validation using Ansible's community.vmware collection — connecting directly to vCenter API (no SSH to ESXi hosts needed) to validate every VM, every datastore, every cluster, and every snapshot across the entire estate.

🏦 1. The Banking Story

Setting: ABC Global Bank's virtualization estate: 4 vCenter clusters, 48 ESXi hosts, 1,200 VMs across Mumbai Primary, Mumbai DR, Chennai, and Pune data centers. The VM admin team of 6 engineers manages this manually via vSphere Client UI.

Incident 1 — The Snapshot Disaster: A VM snapshot taken for a middleware upgrade 8 months ago was never deleted. The snapshot delta file grew to 1.8TB on the datastore. The datastore (4TB total) ran out of space at 3:47 AM. 47 VMs on that datastore went read-only — all writes failed. Applications crashed. The CBS application server, LMS server, and 3 middleware nodes were all on that datastore. P1 incident. 2.5 hours to identify the root cause (stale snapshot) and extend the datastore. ₹3.5 crore in lost transactions.

Incident 2 — The HA Cluster Split: During a network maintenance window, an ESXi host was accidentally isolated. VMware HA should have restarted the VMs on that host on other hosts. It didn't — because the HA admission control policy had been changed from "Percentage of cluster resources reserved" to "Disabled" 3 months earlier by an engineer troubleshooting a performance issue. Nobody re-enabled it. 14 VMs were unavailable until the host was brought back manually.

Incident 3 — VMware Tools Out of Date: A critical VM had VMware Tools so outdated that when vMotion was attempted (to evacuate an ESXi host for maintenance), it failed. The host maintenance was delayed by 4 hours while tools were updated on 23 VMs one by one.

The Ask: "Automate VMware health checks. Alert on stale snapshots before they fill datastores. Validate HA is enabled on all clusters. Monitor datastore capacity. Check VMware Tools versions fleet-wide."

📚 2. VMware vSphere Concepts

vSphere Architecture — vCenter, Clusters, ESXi, VMs
vCenter Server: Central management platform for all ESXi hosts. All Ansible operations use the vCenter API — we never SSH directly to ESXi hosts.

ESXi Host: The physical hypervisor server that runs VMs. Multiple ESXi hosts form a cluster.

Cluster: Logical grouping of ESXi hosts with shared HA and DRS policies.
HA (High Availability): Automatically restarts VMs on other hosts if an ESXi host fails. Must be enabled on cluster.
DRS (Distributed Resource Scheduler): Automatically migrates VMs between hosts for load balancing.

Datastore: Shared storage pool (SAN/NAS) used by multiple ESXi hosts to store VM disk files (.vmdk).

Snapshot: Point-in-time capture of a VM's disk state. Creates delta disk files that grow as the VM writes data. Old snapshots consume massive disk space and degrade VM performance.
community.vmware Collection — How Ansible Talks to vCenter
The community.vmware Ansible collection communicates with vCenter's REST API and SOAP API (vSphere API). It does NOT require SSH to ESXi hosts or VMs.

Key connection parameters:
hostname: vCenter FQDN or IP
username: vCenter user (domain\user or user@domain)
password: vCenter password (from Ansible Vault)
validate_certs: Whether to verify SSL certificate

Every module in community.vmware passes these parameters, either per-task or via module_defaults at the play level. The Execution Environment must have pyVmomi installed — the Python VMware SDK.
Snapshots — Why They Are Dangerous
When a snapshot is taken, VMware creates a delta disk file alongside the base VMDK. Every write the VM makes goes to the delta file — not the base disk. The delta file grows continuously as long as the snapshot exists.

Problems with old snapshots:
1. Disk space: A busy VM can grow its snapshot delta by 50-100GB per day. After months, this fills datastores.
2. Performance: VM I/O must traverse the snapshot chain — old snapshots = slower disk I/O.
3. Backup failure: Many backup tools (Veeam, Commvault) skip VMs with existing snapshots.
4. vMotion impact: VMs with large snapshots take much longer to live-migrate.

Banking policy: snapshots must be deleted within 72 hours of creation. Our automation detects any snapshot older than 72 hours.

Role 1: vmware_vm_health — VM Power State & ESXi Host Validation

roles/vmware_vm_health/tasks/check_critical_vms.yml
---
# =====================================================================
# Check power state of all critical banking VMs
# Uses vmware_vm_info module to query vCenter API
# =====================================================================

- name: Gather VM information from vCenter
  community.vmware.vmware_vm_info:                     # Module: get VM details from vCenter
    hostname: "{{ vcenter_hostname }}"                  # vCenter FQDN
    username: "{{ vault_vcenter_username }}"            # vCenter service account
    password: "{{ vault_vcenter_password }}"            # From Vault credential
    validate_certs: "{{ validate_certs }}"
    vm_type: vm                                         # vm = only VMs (not templates)
    show_attribute: true                                # Include custom attributes
  register: all_vms_info
  delegate_to: localhost                                # API call from AAP node
  no_log: false                                         # Log task — credentials not in args

- name: Extract VM inventory as usable list
  ansible.builtin.set_fact:
    vm_list: "{{ all_vms_info.virtual_machines }}"
    # all_vms_info.virtual_machines: list of dicts, one per VM
    # Each dict contains: guest_name, power_state, ip_address, cluster,
    #                     datastore_url, guest_tools_status, etc.

- name: Check power state of critical VMs
  ansible.builtin.set_fact:
    critical_vm_status: >-
      {{ critical_vm_status | default([]) + [{
        'vm_name': item,
        'found': (vm_list | selectattr('guest_name', 'equalto', item) | list | length > 0),
        'power_state': (vm_list
                        | selectattr('guest_name', 'equalto', item)
                        | map(attribute='power_state')
                        | first | default('NOT FOUND')),
        'powered_on': (vm_list
                       | selectattr('guest_name', 'equalto', item)
                       | map(attribute='power_state')
                       | first | default('') == 'poweredOn')
      }] }}
  loop: "{{ critical_vms }}"
  loop_control:
    label: "{{ item }}"

- name: Identify critical VMs that are NOT powered on
  ansible.builtin.set_fact:
    vms_not_powered_on: >-
      {{ critical_vm_status
         | rejectattr('powered_on', 'equalto', true)
         | list }}

- name: Alert on critical VMs that are powered off
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "vmware-vm-down-{{ item.vm_name }}-{{ vcenter_hostname }}"
      payload:
        summary: >-
          🔴 CRITICAL VM DOWN: {{ item.vm_name }} is {{ item.power_state }}
          on vCenter {{ vcenter_hostname }}. Banking application may be unavailable!
        severity: critical
        source: "ansible-vmware-monitor"
        custom_details:
          vm_name: "{{ item.vm_name }}"
          power_state: "{{ item.power_state }}"
          found_in_vcenter: "{{ item.found }}"
          vcenter: "{{ vcenter_hostname }}"
    status_code: [202]
  loop: "{{ vms_not_powered_on }}"
  loop_control:
    label: "{{ item.vm_name }}"
  when: vms_not_powered_on | length > 0
  delegate_to: localhost

- name: Log VM power state summary
  ansible.builtin.debug:
    msg:
      - "Critical VM Health Check — {{ vcenter_hostname }}"
      - "Total critical VMs: {{ critical_vms | length }}"
      - "All powered on: {{ vms_not_powered_on | length == 0 }}"
      - "VMs with issues: {{ vms_not_powered_on | map(attribute='vm_name') | list | join(', ') | default('None') }}"
roles/vmware_vm_health/tasks/check_esxi_hosts.yml
---
# =====================================================================
# Check ESXi host connectivity and maintenance mode status
# =====================================================================

- name: Gather ESXi host information from vCenter
  community.vmware.vmware_host_info:                   # Module: get ESXi host details
    hostname: "{{ vcenter_hostname }}"
    username: "{{ vault_vcenter_username }}"
    password: "{{ vault_vcenter_password }}"
    validate_certs: "{{ validate_certs }}"
    properties:
      - name                                            # ESXi hostname
      - runtime.connectionState                         # connected/disconnected/notResponding
      - runtime.inMaintenanceMode                       # true/false — in maintenance mode?
      - runtime.powerState                              # poweredOn/poweredOff/standBy
      - config.product.version                          # ESXi version
      - hardware.memorySize                             # Total memory
  register: esxi_host_info
  delegate_to: localhost

- name: Identify disconnected or not-responding ESXi hosts
  ansible.builtin.set_fact:
    problem_esxi_hosts: >-
      {{ esxi_host_info.hosts
         | selectattr('runtime.connectionState', 'ne', 'connected')
         | list }}
    maintenance_hosts: >-
      {{ esxi_host_info.hosts
         | selectattr('runtime.inMaintenanceMode', 'equalto', true)
         | list }}

- name: Alert on disconnected ESXi hosts
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "esxi-disconnected-{{ item.name }}"
      payload:
        summary: >-
          🔴 ESXi HOST DISCONNECTED: {{ item.name }} state is
          {{ item['runtime.connectionState'] }} on {{ vcenter_hostname }}.
          VMs on this host may require HA restart!
        severity: critical
        source: "ansible-vmware-monitor"
        custom_details:
          host: "{{ item.name }}"
          connection_state: "{{ item['runtime.connectionState'] }}"
          in_maintenance: "{{ item['runtime.inMaintenanceMode'] }}"
    status_code: [202]
  loop: "{{ problem_esxi_hosts }}"
  loop_control:
    label: "{{ item.name }}"
  when: problem_esxi_hosts | length > 0
  delegate_to: localhost

- name: Warn about hosts in maintenance mode (informational)
  ansible.builtin.debug:
    msg: >-
      ℹ️  ESXi hosts in maintenance mode on {{ vcenter_hostname }}:
      {{ maintenance_hosts | map(attribute='name') | list | join(', ') | default('None') }}
      Note: Verify these are authorized maintenance windows

Role 2: vmware_datastore_monitor — Capacity Tracking

roles/vmware_datastore_monitor/tasks/check_datastore_capacity.yml
---
# =====================================================================
# Monitor datastore capacity — prevent the CBS-DS-01 incident
# =====================================================================

- name: Gather datastore information from vCenter
  community.vmware.vmware_datastore_info:              # Module: get datastore details
    hostname: "{{ vcenter_hostname }}"
    username: "{{ vault_vcenter_username }}"
    password: "{{ vault_vcenter_password }}"
    validate_certs: "{{ validate_certs }}"
    properties:
      - name
      - summary.capacity                               # Total capacity in bytes
      - summary.freeSpace                              # Free space in bytes
      - summary.type                                   # VMFS, NFS, vSAN, etc.
      - host                                           # Connected hosts
  register: datastore_info
  delegate_to: localhost

- name: Calculate usage percentage for each datastore
  ansible.builtin.set_fact:
    datastore_usage: >-
      {{ datastore_usage | default([]) + [{
        'name': item.name,
        'type': item['summary.type'],
        'capacity_gb': (item['summary.capacity'] | int / 1073741824) | round(1),
        'free_gb': (item['summary.freeSpace'] | int / 1073741824) | round(1),
        'used_gb': ((item['summary.capacity'] | int - item['summary.freeSpace'] | int)
                    / 1073741824) | round(1),
        'used_percent': (((item['summary.capacity'] | int - item['summary.freeSpace'] | int)
                           / item['summary.capacity'] | int) * 100) | round(1)
      }] }}
  loop: "{{ datastore_info.datastores }}"
  loop_control:
    label: "{{ item.name }}"
  when: item['summary.capacity'] | int > 0              # Skip datastores with 0 capacity
  # 1073741824 = 1GB in bytes (1024³)

- name: Classify datastores by severity
  ansible.builtin.set_fact:
    emergency_datastores: >-
      {{ datastore_usage
         | selectattr('used_percent', '>=', datastore_emergency_percent | float)
         | list }}
    critical_datastores: >-
      {{ datastore_usage
         | selectattr('used_percent', '>=', datastore_critical_percent | float)
         | selectattr('used_percent', '<', datastore_emergency_percent | float)
         | list }}
    warning_datastores: >-
      {{ datastore_usage
         | selectattr('used_percent', '>=', datastore_warn_percent | float)
         | selectattr('used_percent', '<', datastore_critical_percent | float)
         | list }}

- name: Fire PagerDuty P1 for emergency datastores (>95%)
  ansible.builtin.uri:
    url: "{{ pagerduty_integration_url }}"
    method: POST
    body_format: json
    body:
      routing_key: "{{ vault_pagerduty_routing_key }}"
      event_action: trigger
      dedup_key: "vmware-ds-emergency-{{ item.name }}"
      payload:
        summary: >-
          🚨 EMERGENCY: Datastore {{ item.name }} is {{ item.used_percent }}% full
          ({{ item.free_gb }}GB free of {{ item.capacity_gb }}GB total).
          VMs will go READ-ONLY if this fills completely!
        severity: critical
        source: ansible-vmware-monitor
        custom_details:
          datastore: "{{ item.name }}"
          used_percent: "{{ item.used_percent }}"
          free_gb: "{{ item.free_gb }}"
          capacity_gb: "{{ item.capacity_gb }}"
          vcenter: "{{ vcenter_hostname }}"

🔄 13. Execution Flow

1
Every 30 minutes: AAP fires vmware_health_monitor.yml. connection: local + delegate_to: localhost means all tasks run on the AAP execution node and call vCenter HTTPS API.
2
module_defaults applies vcenter credentials to all community.vmware modules automatically — no repetition per task. vmware_vm_info queries all 1,200 VMs in one API call.
3
selectattr filters critical VMs from the full VM list. Any critical VM not in poweredOn state → PagerDuty P1 fires. ESXi host not in connected state → PagerDuty P1 fires.
4
Datastore info gathered. Used percentage calculated (bytes math → GB → percentage). Tiered PagerDuty alerts: P1 for >95%, P2 for >85%, Slack warning for >75%.
5
Daily 01:00 AM: Snapshot audit. vmware_vm_snapshot_info returns all snapshots. Age calculated by comparing create_time to current epoch. Snapshots classified into warn/critical/auto-delete buckets.
6
If 7-day snapshots found: AAP approval node notifies VM team lead with count and VM names. Lead approves in AAP UI → vmware_guest_snapshot with state: absent deletes each snapshot. Datastore rechecked to confirm space recovered.

🎯 15. Interview Preparation

Q: How does Ansible connect to VMware — does it SSH into ESXi hosts?
No. Ansible uses the VMware vSphere API (SOAP and REST) via the community.vmware collection and the pyVmomi Python library. All tasks run with connection: local and delegate_to: localhost — meaning the Ansible execution node makes HTTPS calls to the vCenter API endpoint (port 443).

The inventory hosts are the vCenter server names — not individual VMs or ESXi hosts. Each VMware module receives the vCenter hostname, username, and password as parameters (via module_defaults or per-task). No SSH keys are needed, no agents on ESXi, no agents in VMs for these infrastructure-level checks.
Q: What is module_defaults and why did you use it?
module_defaults at the play level sets default parameter values for all modules matching a group or module name. We use group/community.vmware.vmware which applies to ALL community.vmware modules in the play.

Without module_defaults, every VMware task would need to repeat: hostname, username, password, validate_certs — 4 lines per task, across 20+ tasks = 80+ lines of repetition and 80+ potential places to update credentials.

With module_defaults, those 4 parameters are set once at the play level. Every community.vmware module in that play automatically inherits them. Cleaner, DRY (Don't Repeat Yourself), and easier to maintain when credentials rotate.
Q: How do you calculate snapshot age from the VMware API response?
The VMware API returns snapshot create_time in ISO 8601 format with UTC timezone, like: 2024-01-15T14:32:00.000000+00:00.

To calculate age in hours, we:
1. Get current time as Unix epoch: ansible_date_time.epoch | int
2. Convert snapshot create_time to epoch using Jinja2's to_datetime filter and strftime('%s')
3. Subtract: (current_epoch - snapshot_epoch) / 3600 = hours

This gives us the age in hours as a float, which we then compare to our thresholds (48h warning, 72h critical, 168h = 7-day auto-delete). The entire calculation happens in Ansible set_fact without any external tools.
Q: What is HA Admission Control and why does it matter?
VMware HA Admission Control is a policy that reserves cluster resources to ensure HA failover is always possible. Without it, HA might be enabled but have no available capacity to restart VMs when a host fails.

Example: A 4-host cluster at 100% resource utilization. An ESXi host fails. HA tries to restart its VMs on the remaining 3 hosts — but they're already at 100%. The VMs cannot start. HA "fails" despite being enabled.

Admission Control prevents this by reserving a percentage of cluster capacity (or a specific number of host failures worth of capacity) that cannot be used by normal VMs. The setting that was disabled in our incident prevented HA from having reserved capacity — hence the 14 VMs that didn't restart when the host was isolated.
