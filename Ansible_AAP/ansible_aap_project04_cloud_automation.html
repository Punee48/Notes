1 Project Overview

📌 Cloud Automation vs Configuration Management — What is the Difference?
In Projects 01 and 02, Ansible managed servers that already existed (patching, IIS config, user management). That is called Configuration Management. In this project, Ansible creates the infrastructure itself — VPCs, subnets, security groups, EC2 instances, S3 buckets, IAM roles, Azure VMs, VMware clones. This is called Cloud Provisioning or Infrastructure as Code (IaC). Ansible does not SSH into anything for provisioning — it talks directly to the cloud APIs (AWS API, Azure ARM API, VMware vCenter API) using the delegate_to: localhost pattern. The playbook runs entirely on the control node / exec node.

☁️ AWS Automation

VPC + Subnets, Security Groups, EC2 provisioning with AMI selection, S3 bucket creation and policies, IAM users/roles/policies, ELB, Auto Scaling Groups, Route53 DNS records.

☁️ Azure Automation

🖥️ VMware Automation

2 Business Requirement

🏦 Why GlobalTrust Bank Needs Cloud Automation

GlobalTrust Bank's digital banking platform processes 2 million transactions per day during normal operations. During festive seasons (Diwali, Dussehra, IPL finals) and salary credit days (1st and 7th of every month), transaction volume spikes to 8–10 million per day. The bank needs to provision additional EC2 capacity within 30 minutes of detecting load — impossible manually through the AWS Console when 20 new instances are needed at once. On the Azure side, the risk analytics team requests a new VM environment every Monday morning for weekly model runs — taking the infra team 2 days manually. For VMware, QA teams need fresh clones of production-like VMs for every sprint cycle.

🚨 The Problem Before Automation — Real Incidents
Incident 1: During Diwali 2023, the internet banking site went down for 40 minutes because the infra team was manually creating EC2 instances through the AWS Console one by one — by the time the 8th instance was being configured, the site had already crashed. ₹2.3 crore in lost transaction fees plus reputational damage.

Incident 2: A developer manually created an S3 bucket for temporary data — forgot to set the bucket policy, left it public. AWS sent a public bucket warning. Security team's panic response took 3 hours. RBI fined the bank for a data exposure risk. Post-incident action: all S3 bucket creation must go through Ansible with mandatory security policies enforced.
✅ Business Outcomes After Cloud Automation
  • 20 EC2 instances provisioned in 8 minutes (was 3 hours)
  • S3 buckets always created with mandatory encryption + no-public-access policy
  • Azure VM environment ready in 12 minutes (was 2 days)
  • VMware clones created from template in 5 minutes
  • 100% GitOps — every infra change tracked in Git with PR approval
  • IAM roles auto-created with least-privilege policies — no manual IAM work
  • Full audit trail in AAP — who provisioned what, when, with what parameters
  • Auto-decommissioning — test VMs deleted after 7 days automatically

💡 The delegate_to: localhost Pattern — Critical Concept
When Ansible provisions cloud resources (creates EC2 instances, creates S3 buckets), it is NOT SSHing into any server. It is calling the AWS/Azure/VMware API from the execution node itself. This is the delegate_to: localhost pattern — run this task locally (on the exec node) instead of on a remote managed node. The exec node has boto3/azure-sdk installed in the EE, so it can call the APIs directly. Your inventory for a provisioning playbook is usually hosts: localhost or hosts: 127.0.0.1. After EC2 instances are created, a second play targets them for configuration using SSH.

6 AWS VPC and Networking Automation

Before any EC2 instance can be provisioned, the network foundation must exist. In GlobalTrust Bank's AWS environment, we follow a hub-and-spoke VPC design — one central networking VPC and separate VPCs per environment (prod, staging, dev). The entire network is built and managed through Ansible playbooks — not the AWS Console.

playbooks/aws/aws_vpc_setup.yml — Complete VPC FoundationYAML
---
# ============================================================
# GlobalTrust Bank — AWS VPC Network Foundation
# Creates: VPC, Subnets, IGW, Route Tables, NAT Gateway
# ============================================================

- name: AWS VPC Foundation — GlobalTrust Bank Production
  hosts: localhost                       # Run on exec node — NOT on any remote server
  gather_facts: false
  connection: local                      # Local connection — API calls only, no SSH

  vars:
    aws_region: ap-south-1
    vpc_name: globaltrust-prod-vpc
    vpc_cidr: 10.11.0.0/16
    environment: production
    subnets:
      - name: public-subnet-1a
        cidr: 10.11.1.0/24
        az: ap-south-1a
        type: public
      - name: public-subnet-1b
        cidr: 10.11.2.0/24
        az: ap-south-1b
        type: public
      - name: private-app-subnet-1a
        cidr: 10.11.10.0/24
        az: ap-south-1a
        type: private
      - name: private-app-subnet-1b
        cidr: 10.11.11.0/24
        az: ap-south-1b
        type: private
      - name: private-db-subnet-1a
        cidr: 10.11.20.0/24
        az: ap-south-1a
        type: db

  tasks:

    - name: Create VPC for GlobalTrust Bank Production
      amazon.aws.ec2_vpc_net:
        name: "{{ vpc_name }}"
        cidr_block: "{{ vpc_cidr }}"
        region: "{{ aws_region }}"
        enable_dns_hostnames: true         # AWS assigns DNS names to EC2 instances
        enable_dns_support: true           # Enable internal DNS resolution
        tenancy: default                   # Shared hardware (use 'dedicated' for strict compliance)
        tags:
          Name: "{{ vpc_name }}"
          Environment: "{{ environment }}"
          ManagedBy: ansible
          Owner: devops-team
          CostCenter: digital-banking
        state: present
      register: vpc_result                  # Save VPC ID for use in subsequent tasks

    - name: Store VPC ID for later use
      ansible.builtin.set_fact:            # Create a runtime variable
        vpc_id: "{{ vpc_result.vpc.id }}"  # vpc_result.vpc.id = 'vpc-0a1b2c3d4e5f67890'

    - name: Create all subnets in the VPC
      amazon.aws.ec2_vpc_subnet:
        vpc_id: "{{ vpc_id }}"
        cidr: "{{ item.cidr }}"
        az: "{{ item.az }}"
        region: "{{ aws_region }}"
        map_public: "{{ true if item.type == 'public' else false }}"  # Public subnets auto-assign public IPs
        tags:
          Name: "{{ item.name }}"
          Type: "{{ item.type }}"
          Environment: "{{ environment }}"
          ManagedBy: ansible
        state: present
      loop: "{{ subnets }}"
      loop_control:
        label: "{{ item.name }}"
      register: subnet_results

    - name: Create Internet Gateway for public subnet internet access
      amazon.aws.ec2_vpc_igw:
        vpc_id: "{{ vpc_id }}"
        region: "{{ aws_region }}"
        tags:
          Name: "{{ vpc_name }}-igw"
          ManagedBy: ansible
        state: present
      register: igw_result

    - name: Create public route table — route internet traffic through IGW
      amazon.aws.ec2_vpc_route_table:
        vpc_id: "{{ vpc_id }}"
        region: "{{ aws_region }}"
        tags:
          Name: "{{ vpc_name }}-public-rt"
        routes:
          - dest: 0.0.0.0/0                # All internet traffic (0.0.0.0/0 = everything)
            gateway_id: "{{ igw_result.gateway_id }}"
        subnets:                           # Associate this route table with public subnets
          - 10.11.1.0/24
          - 10.11.2.0/24
        state: present

    - name: Display VPC creation summary
      ansible.builtin.debug:
        msg:
          - "✅ VPC Created: {{ vpc_id }}"
          - "  CIDR: {{ vpc_cidr }}"
          - "  Region: {{ aws_region }}"
          - "  Subnets: {{ subnet_results.results | length }}"
          - "  IGW: {{ igw_result.gateway_id }}"
Parameter / ConceptExplanation — Why It Matters
hosts: localhost + connection: localThis is the key pattern for all cloud provisioning. We run the playbook targeting localhost (the exec node itself). connection: local means Ansible does not try to SSH — it runs the task directly as Python code on the exec node, which calls the AWS API via boto3. No managed node is involved at this stage.
gather_facts: falseWhen hosts is localhost and connection is local, gathering facts (which normally SSHes to the host) is unnecessary. Also saves 5–10 seconds per play.
enable_dns_hostnames: trueThis tells AWS to assign DNS names like ip-10-11-1-5.ap-south-1.compute.internal to each EC2 instance. Required for internal service discovery and for the Ansible Dynamic Inventory plugin to resolve hostnames.
map_public: true (for public subnets)Servers in public subnets automatically get a public IP when this is true. For private app and DB subnets, this is false — servers only have private IPs and access the internet through a NAT Gateway. This is the standard banking security design.
vpc_result.vpc.idAfter creating the VPC, the module returns details about what was created. register: vpc_result saves this return data. vpc_result.vpc.id is the AWS VPC ID (like vpc-0a1b2c3d4e5f67890) — we need this ID to create subnets and other resources inside that VPC.
amazon.aws.set_fact vpc_idWe extract the VPC ID and store it as a runtime variable using set_fact. This makes it available for ALL subsequent tasks in ALL subsequent plays in the same playbook run — without having to write vpc_result.vpc.id every time.
routes: dest: 0.0.0.0/0A route table entry saying "for ANY destination IP (0.0.0.0/0), send traffic through the Internet Gateway." This is the route that gives public subnets internet access. Private subnets have a route to a NAT Gateway instead — outbound internet but no inbound from internet.

7 Security Groups Automation

Security Groups are AWS's virtual firewall — they control which traffic can reach your EC2 instances. In GlobalTrust Bank, every tier (web, app, database) has its own security group with carefully controlled inbound rules. Creating and maintaining these manually is error-prone and not auditable.

playbooks/aws/aws_security_groups.ymlYAML
---
- name: Create Security Groups — GlobalTrust Bank Tiered Architecture
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    aws_region: ap-south-1
    vpc_id: "{{ lookup('aws_ssm', '/globaltrust/prod/vpc_id') }}"
    # Read VPC ID from AWS SSM Parameter Store — secrets managed centrally

  tasks:

    - name: Create Web Tier Security Group (ALB → Web Servers)
      amazon.aws.ec2_security_group:
        name: globaltrust-web-sg
        description: Web tier — allows HTTPS from internet via ALB only
        vpc_id: "{{ vpc_id }}"
        region: "{{ aws_region }}"
        rules:                             # INBOUND rules
          - proto: tcp
            ports: [443]                  # HTTPS only — HTTP is blocked
            cidr_ip: 10.11.1.0/24         # Only from public subnet (where ALB lives)
            rule_desc: HTTPS from ALB subnet
          - proto: tcp
            ports: [22]
            cidr_ip: 10.11.0.0/16         # SSH only from within VPC (jump box)
            rule_desc: SSH from VPC internal only
        rules_egress:                      # OUTBOUND rules
          - proto: all
            cidr_ip: 0.0.0.0/0           # Allow all outbound (to internet via NAT)
        tags:
          Name: globaltrust-web-sg
          Tier: web
          ManagedBy: ansible
        state: present
      register: web_sg

    - name: Create Application Tier Security Group
      amazon.aws.ec2_security_group:
        name: globaltrust-app-sg
        description: App tier — allows traffic from web tier only
        vpc_id: "{{ vpc_id }}"
        region: "{{ aws_region }}"
        rules:
          - proto: tcp
            ports: [8080, 8443]           # App server ports
            group_id: "{{ web_sg.group_id }}"  # Source = web security group (not IP)
            rule_desc: Traffic from web tier only
          - proto: tcp
            ports: [22]
            cidr_ip: 10.11.0.0/16
            rule_desc: SSH from VPC internal
        rules_egress:
          - proto: all
            cidr_ip: 0.0.0.0/0
        tags:
          Name: globaltrust-app-sg
          Tier: app
          ManagedBy: ansible
        state: present
      register: app_sg

    - name: Create Database Tier Security Group (most restrictive)
      amazon.aws.ec2_security_group:
        name: globaltrust-db-sg
        description: DB tier — only app servers can connect to database
        vpc_id: "{{ vpc_id }}"
        region: "{{ aws_region }}"
        rules:
          - proto: tcp
            ports: [3306]               # MySQL port (or 1521 for Oracle)
            group_id: "{{ app_sg.group_id }}"  # ONLY from app security group
            rule_desc: MySQL from app tier only
        rules_egress:
          - proto: all
            cidr_ip: 0.0.0.0/0
        tags:
          Name: globaltrust-db-sg
          Tier: db
          ManagedBy: ansible
        state: present
ConceptExplanation
group_id as source (not cidr_ip)This is the advanced security pattern. Instead of saying "allow port 8080 from 10.11.10.0/24" (IP range), we say "allow port 8080 from any server that belongs to the globaltrust-web-sg security group." This is much more precise — if the web subnet IP range changes, the rule still works. If a new web server is added to the web-sg, it automatically gets access to app servers. This is AWS security groups as identity-based access control.
rules vs rules_egressrules = inbound (who can send traffic TO this server). rules_egress = outbound (where this server can send traffic). In banking, we restrict inbound strictly (only specific sources on specific ports) but allow all outbound (so servers can call APIs, download patches, etc.). For ultra-secure environments, you can also restrict egress.
lookup('aws_ssm', '/path')Instead of hardcoding the VPC ID in the playbook, we use the aws_ssm lookup plugin to read it from AWS Systems Manager Parameter Store. This means the VPC ID is stored centrally in one place, and all playbooks read from there. If you ever recreate the VPC, update one SSM parameter — all playbooks automatically use the new ID.

8 EC2 Instance Provisioning — The Diwali Emergency Playbook

This is the playbook that saved the bank on Diwali night. It provisions multiple EC2 instances in parallel, waits for them to be accessible, then runs the configuration role on them — all in under 9 minutes.

playbooks/aws/aws_ec2_provision.yml — Complete EC2 LifecycleYAML
---
# ============================================================
# GlobalTrust Bank — EC2 Instance Provisioning
# Two-play pattern: Play 1 = Provision (localhost API calls)
#                   Play 2 = Configure (SSH to new instances)
# ============================================================

# ===== PLAY 1: PROVISION EC2 INSTANCES =====
- name: PROVISION — Create EC2 instances via AWS API
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    aws_region: ap-south-1
    instance_count: "{{ count | default(2) }}"  # From AAP Survey — default 2
    instance_type: "{{ type | default('t3.large') }}"
    ami_id: ami-0c55b159cbfafe1f0           # RHEL 9 AMI in ap-south-1 (pre-approved)
    environment: "{{ env | default('staging') }}"
    subnet_id: "{{ lookup('aws_ssm', '/globaltrust/prod/private-app-subnet-1a') }}"
    security_group_ids:
      - "{{ lookup('aws_ssm', '/globaltrust/prod/app-sg-id') }}"
    key_name: globaltrust-prod-key          # EC2 key pair name in AWS
    iam_instance_profile: globaltrust-ec2-role  # IAM role attached to instances

  tasks:

    - name: Create {{ instance_count }} EC2 instances for Internet Banking
      amazon.aws.ec2_instance:
        name: "globaltrust-{{ environment }}-web-{{ item }}"
        instance_type: "{{ instance_type }}"
        image_id: "{{ ami_id }}"
        region: "{{ aws_region }}"
        key_name: "{{ key_name }}"
        security_groups: "{{ security_group_ids }}"
        vpc_subnet_id: "{{ subnet_id }}"
        iam_instance_profile: "{{ iam_instance_profile }}"
        ebs_volumes:
          - device_name: /dev/xvda
            ebs:
              volume_size: 50              # 50 GB root volume
              volume_type: gp3             # gp3 = better performance than gp2 at same price
              encrypted: true              # RBI mandates encryption at rest
              delete_on_termination: true
        network:
          assign_public_ip: false          # No public IP — instances are in private subnet
        metadata_options:
          http_tokens: required            # Require IMDSv2 (prevents SSRF attacks)
          http_endpoint: enabled
        user_data: |                        # Bootstrap script runs on first boot
          #!/bin/bash
          hostnamectl set-hostname globaltrust-{{ environment }}-web-{{ item }}
          useradd -m -s /bin/bash ansible-svc
          mkdir -p /home/ansible-svc/.ssh
          echo "{{ lookup('file', '~/.ssh/ansible_pub_key.pub') }}" >> /home/ansible-svc/.ssh/authorized_keys
          echo "ansible-svc ALL=(ALL) NOPASSWD: /usr/bin/yum,/usr/bin/dnf,/sbin/reboot" >> /etc/sudoers.d/ansible-svc
        tags:
          Name: "globaltrust-{{ environment }}-web-{{ item }}"
          Environment: "{{ environment }}"
          Role: web
          Application: internetbanking
          PatchGroup: group-a
          ManagedBy: ansible
          PatchEnabled: "true"
          LaunchedBy: "{{ ansible_user_id }}"  # Who launched this instance
          LaunchDate: "{{ ansible_date_time.date }}"
        state: running                      # Ensure instance is running (creates if not exists)
        wait: true                          # Wait until instance is in 'running' state
        wait_timeout: 300                  # Maximum 5 minutes to become running
      loop: "{{ range(1, instance_count | int + 1) | list }}"  # Loop 1 to N
      register: ec2_results

    - name: Wait for SSH to become available on all new instances
      ansible.builtin.wait_for:
        host: "{{ item.instances[0].private_ip_address }}"
        port: 22
        delay: 30                          # Wait 30 sec before first check (OS needs to boot)
        timeout: 300                       # Give 5 minutes for user_data script to run
        state: started
      loop: "{{ ec2_results.results }}"
      loop_control:
        label: "{{ item.instances[0].private_ip_address }}"

    - name: Add new instances to in-memory inventory for Play 2
      ansible.builtin.add_host:            # Dynamically add a host to inventory AT RUNTIME
        name: "{{ item.instances[0].private_ip_address }}"
        groups: newly_provisioned           # Add to a new runtime group called 'newly_provisioned'
        ansible_user: ansible-svc
        ansible_host: "{{ item.instances[0].private_ip_address }}"
        instance_id: "{{ item.instances[0].instance_id }}"
        instance_name: "{{ item.instances[0].tags.Name }}"
      loop: "{{ ec2_results.results }}"
      loop_control:
        label: "{{ item.instances[0].tags.Name }}"

# ===== PLAY 2: CONFIGURE NEW INSTANCES =====
- name: CONFIGURE — Apply baseline configuration to new EC2 instances
  hosts: newly_provisioned              # Target the in-memory group created by add_host above
  become: true
  gather_facts: true

  roles:
    - role: linux_patching               # Apply security patches immediately on provision
    - role: linux_baseline               # CIS hardening, user setup, monitoring agent
Module / ConceptExplanation
instance_count loop: range(1, N+1)The Jinja2 range() function generates a sequence of numbers. range(1, 4) = [1, 2, 3]. We use this to loop exactly N times — one loop iteration per instance to create. The item variable becomes the instance number (1, 2, 3...) which we use to name the instances uniquely.
metadata_options: http_tokens: requiredThis enforces IMDSv2 (Instance Metadata Service version 2) on the EC2 instance. IMDSv2 requires a session token to access the metadata service — this prevents SSRF (Server-Side Request Forgery) attacks where an attacker tricks the server into fetching its own AWS credentials from the metadata endpoint. This is a security best practice that RBI's cloud security framework requires.
user_dataUser data is a script that runs ONCE when the EC2 instance first boots (before Ansible connects). We use it to: set the hostname, create the ansible-svc user, add the SSH public key, configure sudoers. Without user_data, Ansible has no way to SSH into the brand-new instance because the ansible-svc user doesn't exist yet.
ansible.builtin.add_hostThis is the magic that connects Play 1 (provisioning) to Play 2 (configuration). add_host dynamically adds a host to Ansible's in-memory inventory during the current playbook run. We create a runtime group called "newly_provisioned" and add all the new EC2 private IPs to it. Play 2 then targets this group — SSH into all new instances and configure them. This is the standard two-play provisioning pattern.
ebs: encrypted: trueRBI's circular on IT Framework for Banks explicitly requires encryption at rest for all banking data. Enabling EBS encryption means the entire disk of the EC2 instance is encrypted using AWS KMS (Key Management Service). The encryption is transparent to the OS — but if someone physically steals the disk or takes a snapshot to another account, they cannot read the data without the KMS key.
state: runningUnlike state: present (which just ensures the instance exists), state: running ensures the instance exists AND is powered on. If the instance already exists but is stopped, Ansible starts it. Idempotent — running the playbook multiple times won't create duplicate instances.

16 VMware Snapshots — Pre-Patch Safety Net

playbooks/vmware/vmware_snapshots.ymlYAML
---
- name: VMware Snapshot Management — Pre and Post Patch
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    vcenter_hostname: vcenter.globaltrust.in
    vcenter_username: ansible-snapshot@vsphere.local
    vcenter_password: "{{ vault_vcenter_snap_password }}"
    snapshot_action: "{{ action | default('create') }}"
    target_vms: "{{ vms | default([]) }}"
    snapshot_name: "pre-patch-{{ ansible_date_time.date }}"

  tasks:

    - name: Create pre-patch snapshot for all target VMs
      community.vmware.vmware_guest_snapshot:
        hostname: "{{ vcenter_hostname }}"
        username: "{{ vcenter_username }}"
        password: "{{ vcenter_password }}"
        validate_certs: true
        datacenter: Mumbai-DC
        name: "{{ item }}"               # VM name from target list
        snapshot_name: "{{ snapshot_name }}"
        description: "Auto snapshot before monthly Linux compliance patching by Ansible"
        memory_dump: false              # Don't dump RAM to disk — snapshot disk only
        quiesce: true                   # Flush filesystem buffers (requires VMware Tools)
        state: present                  # Create the snapshot
      loop: "{{ target_vms }}"
      when: snapshot_action == 'create'

    - name: Remove old snapshots older than 7 days (storage management)
      community.vmware.vmware_guest_snapshot:
        hostname: "{{ vcenter_hostname }}"
        username: "{{ vcenter_username }}"
        password: "{{ vcenter_password }}"
        validate_certs: true
        datacenter: Mumbai-DC
        name: "{{ item }}"
        snapshot_name: "{{ old_snapshot_name }}"
        state: absent                   # Delete the snapshot
      loop: "{{ target_vms }}"
      when: snapshot_action == 'delete'
ParameterExplanation
quiesce: trueQuiescing means VMware Tools sends a signal to the OS to flush all pending writes from memory buffers to disk before taking the snapshot. Without quiescing, a snapshot might capture the disk mid-write — potentially in an inconsistent state. For banking applications, consistent snapshots are critical. Requires VMware Tools to be installed inside the VM.
memory_dump: falseIf true, VMware dumps the entire VM RAM to disk as part of the snapshot — allows reverting to the exact memory state. However, this can take 10–30 minutes for a 16 GB RAM server and uses massive storage space. For pre-patch snapshots, we only need the disk state (false) — we don't need to restore RAM state, we'll reboot after restore anyway.
state: absent (delete)Critical operational task — snapshots consume storage and VMware recommends keeping them for no more than 7 days. Snapshots cause disk I/O performance degradation over time. We automate snapshot cleanup 7 days after successful patching using state: absent.

19 Troubleshooting — Real Cloud Provisioning Issues

🚨 Issue 1: EC2 Provisioning Fails — AMI Not Found in Region
Error

fatal: [localhost]: FAILED! => {"msg": "The image id '[ami-0c55b159cbfafe1f0]' does not exist"}

Root Cause

AMI IDs are region-specific. The AMI ID ami-0c55b159cbfafe1f0 that works in ap-south-1 (Mumbai) does NOT exist in ap-southeast-1 (Singapore). When the playbook was updated to deploy in Singapore as well, nobody updated the AMI ID.

Fix — Dynamic AMI Lookup
Fix: Use ami_find to look up AMI dynamicallyYAML
# Instead of hardcoding AMI ID, find the latest RHEL 9 AMI dynamically
- name: Find the latest RHEL 9 AMI in current region
  amazon.aws.ec2_ami_info:
    region: "{{ aws_region }}"
    owners:
      - "309956199498"               # Red Hat's official AWS Account ID
    filters:
      name: "RHEL-9*GA*"               # Pattern: RHEL 9 General Availability
      architecture: x86_64
      root-device-type: ebs
    sort: creation_date
    sort_order: descending
    sort_end: 1                      # Return only the newest AMI
  register: rhel9_ami

- name: Set AMI ID from lookup result
  ansible.builtin.set_fact:
    ami_id: "{{ rhel9_ami.images[0].image_id }}"
# Now ami_id is always the latest RHEL 9 in whatever region you deploy to
🚨 Issue 2: Azure VM Provisioning Fails — Quota Exceeded
Error

Operation could not be completed as it results in exceeding approved standardDSv3Family Cores quota. Additional details - Deployment Model: Resource Manager, Location: centralindia, Current Limit: 20, Current Usage: 20, Additional Required: 4

Root Cause

Azure has per-subscription, per-region vCPU quotas. The analytics team tried to create 2 more Standard_D4s_v3 VMs (4 vCPUs each = 8 more vCPUs) but the quota was already at 20/20.

Resolution
Add pre-flight quota check before Azure VM provisioningYAML
# Add this check BEFORE the azure_rm_virtualmachine task
- name: Check Azure vCPU quota before provisioning
  azure.azcollection.azure_rm_quotainfo:
    resource_group: rg-analytics-prod
    resource_name: standardDSv3Family
    location: centralindia
  register: quota_info

- name: Fail if not enough quota remaining
  ansible.builtin.fail:
    msg: "❌ Insufficient Azure quota. Limit: {{ quota_info.properties.limit }}, Used: {{ quota_info.properties.current_value }}, Need: {{ vm_count * vm_vcpus }}. Submit quota increase request."
  when: (quota_info.properties.limit | int - quota_info.properties.current_value | int) < (vm_count | int * vm_vcpus | int)
Long-term Fix

Submit an Azure quota increase request via the Azure Portal or Azure CLI. Also, use Azure Spot VMs for analytics workloads — they are up to 90% cheaper and the quota limits are typically higher. The risk (Spot VMs can be evicted by Azure) is acceptable for batch analytics jobs that can be re-run.

🚨 Issue 3: VMware VM Stays in "Customization" State Forever
Symptom

The vmware_guest module runs, creates the VM, but hangs for 10 minutes at wait_for_customization: true and then times out. The VM exists in vCenter but is in a loop rebooting for customization.

Root Cause

VMware Guest Customization requires VMware Tools to be installed in the template. The rhel9-golden-template-v2 was re-built last week and the VMware Tools package (open-vm-tools) was accidentally removed during the CIS hardening process.

Fix
Verify template has VMware Tools before cloningYAML
# Add template validation task BEFORE cloning
- name: Verify Golden Template has VMware Tools installed
  community.vmware.vmware_guest_info:
    hostname: vcenter.globaltrust.in
    username: ansible-deploy@vsphere.local
    password: "{{ vault_vcenter_deploy_password }}"
    validate_certs: true
    datacenter: Mumbai-DC
    name: "{{ template_name }}"
  register: template_info

- name: Fail if VMware Tools not running in template
  ansible.builtin.fail:
    msg: "❌ VMware Tools status: {{ template_info.instance.guest_tools_status }}. Must be toolsOk for customization to work. Rebuild the golden template with open-vm-tools installed."
  when: template_info.instance.guest_tools_status != 'toolsOk'
🚨 Issue 4: S3 Bucket Creation Fails — Name Already Taken (Globally)
Error

BucketAlreadyExists: The requested bucket name is not available. The bucket namespace is shared by all users of the system.

Root Cause

S3 bucket names are globally unique across ALL AWS accounts. Someone else (in a different company, different AWS account) already has a bucket named globaltrust-app-logs-prod.

Fix — Always include AWS Account ID or unique suffix
Fix: Include AWS Account ID in bucket name for uniquenessYAML
# Best practice: include account ID in bucket name
vars:
  aws_account_id: "{{ lookup('amazon.aws.aws_account_attribute', attribute='account_id') }}"
  bucket_name: "globaltrust-app-logs-{{ aws_account_id }}"
  # Result: globaltrust-app-logs-123456789012
  # Guaranteed unique because your account ID is unique

# OR use a prefix with region:
  bucket_name: "globaltrust-{{ aws_region }}-app-logs-prod"
  # Result: globaltrust-ap-south-1-app-logs-prod

🟢 Beginner Questions

Q1. What is the delegate_to: localhost pattern in cloud automation?
When Ansible provisions cloud resources like EC2 instances, S3 buckets, or Azure VMs, it is not SSHing into any server — it is calling the cloud provider's API directly from the Ansible execution node. The delegate_to: localhost pattern tells Ansible to run a specific task on the local machine (the execution node) rather than on a remote managed node. connection: local at the play level sets this globally for all tasks in that play. The execution node has boto3 (for AWS) or azure-sdk (for Azure) installed in the Execution Environment, so it can call the cloud APIs directly. This is the fundamental pattern for all cloud provisioning with Ansible — Play 1 provisions via localhost API calls, and Play 2 configures the new servers via SSH after they are running.
Q2. How does Ansible handle idempotency for cloud resources like EC2 instances?
Ansible's AWS modules use the AWS API to check if a resource already exists before creating it. For example, the amazon.aws.ec2_instance module with state: running first calls DescribeInstances with the instance name tag to see if an instance with that name already exists. If it does and it's already running, the module reports "ok" (no change) and does nothing. If the instance is stopped, it starts it. If it doesn't exist, it creates it. This idempotency means you can run a provisioning playbook multiple times safely — it won't create 20 extra duplicate instances each time. The key to idempotency with EC2 is using the name parameter — this becomes an AWS Name tag, and the module uses this tag to find existing instances. Without a unique name, the module can't tell if an instance already exists.

🟡 Intermediate Questions

Q3. What is user_data in EC2 provisioning and why does Ansible need it?
User data is a shell script or cloud-init configuration that AWS runs on the EC2 instance when it first boots — before Ansible can SSH in. Ansible needs user_data to set up the prerequisites for the second play (configuration). Specifically, in our bank, the user_data script: sets the hostname, creates the ansible-svc service account, creates the .ssh directory and authorizes the Ansible SSH public key, and adds the sudoers entry for passwordless sudo. Without user_data, the brand-new EC2 instance has no ansible-svc user — Ansible's SSH would fail immediately in Play 2. The user_data runs once automatically on first boot via the cloud-init service, which is pre-installed on all RHEL AMIs. We use wait_for: port: 22 after provisioning to pause until the instance is fully booted and the user_data script has run.
Q4. How do you handle AWS credentials in Ansible securely? Compare IAM User keys vs IAM Roles.
There are two main methods. IAM User Access Keys — you create an IAM user, generate an Access Key ID and Secret Access Key, and store these in AAP as an Amazon Web Services credential. AAP encrypts them and injects as AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY environment variables when the job runs. The boto3 library automatically reads these variables. This method works everywhere — on-premise AAP, VM-based AAP — but keys must be rotated regularly (every 90 days as per our bank's security policy). The second method — IAM Instance Profile (strongly preferred when AAP runs on AWS EC2) — you attach an IAM role directly to the EC2 instance where AAP's execution nodes run. When boto3 makes an API call, it automatically gets temporary credentials from the AWS Instance Metadata Service (169.254.169.254) using the attached role. No access keys stored anywhere — credentials are rotated automatically by AWS every hour. This is the most secure method. In GlobalTrust Bank, our AAP execution nodes in Mumbai run on EC2 with an IAM role attached — no access keys anywhere. For our DR execution node which is on-premise (Hyderabad), we use access keys stored in AAP credentials.
Q5. What is the difference between a VMware VM template and cloning? When do you use each?
A VMware template is a master VM that has been converted to a "template" state — it cannot be powered on or modified directly. It is a read-only golden image. Cloning creates a full copy of the template as a new, independent VM. You use cloning (vmware_guest with template parameter) when you need to create a new VM from a standardised base image — for production provisioning, QA environment setup, or disaster recovery. The clone inherits all the OS configuration, installed packages, and settings from the template, then the customisation spec applies OS-specific changes like hostname, IP address, and DNS. In GlobalTrust Bank, we maintain two templates: rhel9-golden-template (minimal, fully CIS-hardened RHEL 9 — for production VMs) and qa-approved-template (RHEL 9 with testing tools, less restrictive hardening — for QA clones). The production template is updated monthly after patching. The QA template is a clone of the production template with testing additions. This separation ensures production VMs always get the hardened configuration while QA gets a slightly more accessible environment for testing.

🔴 Advanced Questions

Q6. How would you automate a blue-green deployment for the Internet Banking application on AWS?
Blue-green deployment maintains two identical production environments — Blue (current live) and Green (new version). Here is how we do it with Ansible in GlobalTrust Bank. Step 1 — Provision Green: Use our ec2_provision playbook to create a new ASG and target group (the Green environment) with the new application version, while Blue continues serving all traffic. Step 2 — Configure and Test: Apply the linux_baseline and application roles to Green instances. Run smoke tests against the Green target group health check URL directly (not through the public ALB). Step 3 — AAP Approval Node: The workflow pauses and sends a notification to the Release Manager with Green test results. RM must approve before traffic shifts. Step 4 — Traffic Shift: Use the elb_application_lb module to update the ALB listener rule — change the default action from forwarding to the Blue target group to forwarding to the Green target group. This is a near-instant switch — milliseconds. Step 5 — Monitor: Watch error rates for 30 minutes via Prometheus/Grafana. If error rate is acceptable, proceed to step 6. If errors spike, use the same playbook to immediately point ALB back to Blue — instant rollback. Step 6 — Decommission Blue: After 24 hours of stable Green operation, terminate the Blue ASG instances.
Q7. How do you manage costs in cloud automation? What Ansible features help with cost governance?
Cost governance is critical in banking where cloud bills are audited. We use several Ansible-driven cost controls. First, mandatory tagging enforcement — every cloud resource created by Ansible gets a CostCenter tag, Team tag, and Environment tag. Our S3 bucket module will fail if these tags are not provided in the variables. Tags enable AWS Cost Explorer to show costs by team or application. Second, auto-termination of temporary resources — QA VMs created for sprint testing get an AutoShutdown tag. A separate AAP scheduled job runs nightly and terminates any VM older than 14 days that has the QA environment tag. Third, right-sizing recommendations — after provisioning, we run a CloudWatch metrics playbook that checks average CPU utilization over 14 days. If average CPU is below 10%, we flag the instance for rightsizing (downgrade instance type). Fourth, S3 lifecycle policies — every S3 bucket we create has a lifecycle policy that moves objects to Glacier after 90 days (cost: $0.004/GB vs Standard $0.023/GB) and deletes after the retention period. Fifth, Reserved Instances tracking — we have a playbook that queries AWS Cost Explorer for on-demand EC2 usage patterns and generates a report recommending which instances to convert to Reserved Instances for 40-60% savings.
