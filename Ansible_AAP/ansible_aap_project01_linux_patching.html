2 Business Requirement

🏦 The Banking Application Context

GlobalTrust Bank runs its core banking platform — which handles net banking, ATM transactions, NEFT/RTGS transfers, and loan processing — on a fleet of 300+ Red Hat Enterprise Linux (RHEL) servers distributed across its data centers in Mumbai (primary) and Hyderabad (DR), plus AWS cloud (ap-south-1 region) for its digital banking front-end.

😓 The Existing Manual Process (Before Ansible)

Every month, the bank's IT Security team receives a list of 40–80 CVEs (Common Vulnerabilities and Exposures) from RBI (Reserve Bank of India) and its internal VAPT (Vulnerability Assessment and Penetration Testing) team. The Linux team then has to patch all servers manually. Here is what the old process looked like:

Manual Patching Process — Step by Step

Step 1 — Raise Change RequestThe Linux admin logs into ServiceNow, creates a Change Request (CR) for each environment, waits 3 days for CAB (Change Advisory Board) approval.
Step 2 — SSH to Each ServerEngineers SSH into each server one by one. With 300 servers, this alone takes 2 full days across 5 engineers.
Step 3 — Run yum updateOn each server, engineer runs sudo yum update -y, then checks if it completed, then reboots if kernel was updated. Waits for server to come back.
Step 4 — Service VerificationAfter reboot, manually check if application services (Oracle DB, JBoss, nginx, etc.) are running. Call application team for confirmation.
Step 5 — Update CMDBGo back to ServiceNow, update the Configuration Management Database (CMDB) with the patch version, mark CR as complete.
Step 6 — Send Report to CISOManually compile an Excel sheet with server name, patch status, kernel version, date — and email it to the Chief Information Security Officer (CISO).

🔒 Network & Authentication Details

🔑 SSH Authentication (Linux Servers)

Ansible uses a dedicated service account called ansible-svc on all managed nodes. Authentication is via SSH key pair (no passwords). The private key is stored securely in Ansible Vault. No root login is allowed — ansible-svc uses sudo with NOPASSWD for patch commands only.

  /usr/bin/dnf, \
  /sbin/reboot, \

6 Ansible Core Installation

📌 Why We Need To Know This
Even though AAP provides a full UI and automation platform, understanding how Ansible Core is installed on the command line is essential. Many Indian companies (mid-size IT firms, system integrators) use Ansible Core without AAP. In interviews, you will often be asked: "How do you install Ansible?" — so master this first.

📋 Prerequisites Before Installation

RHEL Subscription or Local RepoThe Ansible control node must have access to the RHEL BaseOS, AppStream, and EPEL repositories. In the bank, we use a local Satellite server as the yum repository mirror (no internet access in production networks).
Python 3.9 or HigherAnsible is written in Python. RHEL 8/9 ships with Python 3.9 by default. Check with python3 --version.
SSH Key GeneratedGenerate an SSH key pair for the ansible-svc service account before running any playbook.

⚙️ Installation Steps — Ansible Core on RHEL 9

Step 1: Subscribe to RHEL and enable reposBASH
# Register the system with Red Hat Subscription Manager
sudo subscription-manager register \
  --username=your_rhn_user \
  --password=your_rhn_password

# Attach the subscription
sudo subscription-manager attach --auto

# Enable the Ansible Automation Platform repository
sudo subscription-manager repos \
  --enable ansible-automation-platform-2.4-for-rhel-9-x86_64-rpms

# Verify repos are enabled
sudo subscription-manager repos --list-enabled
Command/ParameterWhat It Means — Word by Word
subscription-managerThis is Red Hat's tool for managing your RHEL subscription license. Think of it like activating Windows — without it, you cannot download Red Hat packages.
registerThis command tells Red Hat's servers: "Hello, this machine belongs to our account." It is like logging in for the first time.
--username / --passwordYour Red Hat Network (RHN) login credentials. In the bank, this is a shared service account managed by the IT team.
attach --autoThis automatically finds the best available subscription for this machine and attaches it. Like assigning a software license to a computer.
repos --enableThis unlocks a specific software repository (package store) for this machine. Without enabling a repo, yum cannot find the Ansible packages.
ansible-automation-platform-2.4-for-rhel-9-x86_64-rpmsThis is the exact name of the Red Hat repository that contains all AAP 2.4 software packages for RHEL 9 on 64-bit Intel/AMD CPUs.
Step 2: Install Ansible CoreBASH
# Install ansible-core package
sudo dnf install -y ansible-core

# Verify installation
ansible --version

# Expected output:
# ansible [core 2.15.x]
#   config file = /etc/ansible/ansible.cfg
#   configured module search path = ['/home/ansible-svc/.ansible/plugins/modules', ...]
#   ansible python module location = /usr/lib/python3.11/site-packages/ansible
#   ansible collection location = /home/ansible-svc/.ansible/collections:/usr/share/ansible/collections
#   executable location = /usr/bin/ansible
#   python version = 3.11.x

# Install additional useful Python packages
sudo dnf install -y python3-pip python3-boto3 python3-requests
Command/ParameterExplanation
dnf installDNF is the package manager for RHEL 8/9. It replaces the older yum command (though yum still works as it is now a symlink to dnf). install downloads and installs the package.
-yThis flag means "answer yes automatically to all confirmation prompts." Without it, dnf asks "Is this ok? [y/N]" for every step. In automation, we always use -y.
ansible-coreThis is the minimal Ansible package. It gives you the core engine, modules, and command-line tools (ansible, ansible-playbook, ansible-vault, ansible-galaxy, ansible-navigator).
ansible --versionThis verifies the installation worked. It shows the Ansible version, configuration file path, Python version, and collection paths — all critical for troubleshooting.
python3-boto3boto3 is the AWS SDK for Python. Ansible uses this to interact with AWS services (EC2, S3, Route53) when running AWS automation playbooks.
Step 3: Create Service Account and Configure SSHBASH
# Create the ansible service account on the CONTROL NODE
sudo useradd -m -s /bin/bash ansible-svc
sudo passwd ansible-svc  # Set a strong password

# Switch to the ansible-svc user
sudo su - ansible-svc

# Generate SSH key pair (no passphrase for automation)
ssh-keygen -t ed25519 -C "ansible-svc@globaltrust.in" -f ~/.ssh/id_ed25519 -N ""

# View the public key — you will copy this to all managed nodes
cat ~/.ssh/id_ed25519.pub
# Output looks like:
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIBm... ansible-svc@globaltrust.in

# Copy public key to a managed node (example: dev-app-01)
ssh-copy-id -i ~/.ssh/id_ed25519.pub ansible-svc@dev-app-01.globaltrust.in

# Test SSH connection (should NOT ask for password)
ssh -i ~/.ssh/id_ed25519 ansible-svc@dev-app-01.globaltrust.in
Command/ParameterExplanation
useradd -m -s /bin/bash ansible-svcCreates a Linux user called ansible-svc. The -m flag creates a home directory at /home/ansible-svc. The -s /bin/bash sets the login shell to bash.
ssh-keygen -t ed25519Generates an SSH key pair using the Ed25519 algorithm. Ed25519 is modern, fast, and more secure than the older RSA algorithm. This creates two files: id_ed25519 (private key — never share) and id_ed25519.pub (public key — safe to share).
-C "ansible-svc@globaltrust.in"This is a comment/label inside the public key. It helps identify which key belongs to whom when you look at the authorized_keys file on managed nodes.
-N ""Sets the passphrase to empty (no passphrase). For automation, we need passwordless key authentication so Ansible can connect without human interaction.
ssh-copy-idThis command copies your public key to the managed node's ~/.ssh/authorized_keys file. After this, SSH will allow you to login using only your private key — no password needed. This is how Ansible connects to managed nodes.
Step 4: Configure ansible.cfgINI
# File: /home/ansible-svc/globaltrust-ansible/ansible.cfg
# This is the main configuration file for Ansible behaviour

[defaults]
inventory          = ./inventory         # Where to find our inventory files
remote_user        = ansible-svc        # SSH user on all managed nodes
private_key_file   = ~/.ssh/id_ed25519  # SSH private key path
host_key_checking  = False              # Skip SSH host key verification (first connection)
log_path           = /var/log/ansible/ansible.log  # Log file path
forks              = 50                 # Run on 50 servers simultaneously
timeout            = 30                 # SSH connection timeout in seconds
retry_files_enabled= False             # Don't create .retry files on failure
stdout_callback    = yaml              # Output format (yaml is more readable)
callbacks_enabled  = timer, profile_tasks  # Show timing for each task

[privilege_escalation]
become             = True              # Use sudo to become root on managed nodes
become_method      = sudo              # Use sudo (not su, pbrun, etc.)
become_user        = root              # Escalate to root user
become_ask_pass    = False             # Don't ask for sudo password (NOPASSWD in sudoers)

[ssh_connection]
ssh_args           = -o ControlMaster=auto -o ControlPersist=60s  # SSH multiplexing for speed
pipelining         = True              # Reduces SSH connections, speeds up playbooks
ParameterExplanation — Why It Matters in Production
forks = 50This tells Ansible to connect to 50 servers at the same time (in parallel). Without this, Ansible processes one server at a time (default is 5). With 300 servers and forks=50, we process them in 6 batches — much faster. Be careful: too high a value can overload the control node's network and CPU.
become = TrueMost Linux administration tasks (installing packages, rebooting servers) require root privileges. Ansible connects as ansible-svc (non-root for security) and then uses sudo to become root only when needed. This is called privilege escalation.
pipelining = TrueNormally, Ansible uploads a Python script to the managed node, then runs it in a separate SSH connection. Pipelining combines these steps, reducing the number of SSH round-trips and making playbooks run 30-50% faster. This is a must-have for production environments with hundreds of servers.
ControlPersist=60sSSH multiplexing reuses the same SSH connection for multiple operations instead of opening a new connection each time. ControlPersist=60s keeps the SSH connection alive for 60 seconds after the last use. This dramatically speeds up execution on large inventories.

7 AAP 2.4 Installation

📌 AAP vs Ansible Core — What is the Difference?
Think of it this way: Ansible Core is like a car engine — it does the work but has no dashboard, no GPS, no comfortable seats. AAP (Automation Controller) is the complete car — same engine inside, but now you have a beautiful dashboard (web UI), role-based access control (RBAC), scheduling, approval workflows, audit logging, and integration with everything. Enterprise banks use AAP, not just Ansible Core.

📦 AAP 2.4 Components

🎮 Automation Controller

The central brain and UI. Everything in AAP — job templates, workflows, inventory, credentials — is managed here. Previously called "Ansible Tower."

🏪 Private Automation Hub

A local mirror/store for Ansible Collections and Execution Environment container images. Banks use this because they cannot pull from the internet in production.

📦 Execution Environments (EE)

Containerized environments (Podman/OCI) that contain Python, Ansible Core, and all required collections. Every job runs inside an EE for consistency and reproducibility.

⚠️ Common Installation Mistake in the Bank
The most common error during AAP installation in production environments is firewall blocking PostgreSQL port 5432 between the Controller and Database server. ConceptExplanation with Real Example
[dev] groupSquare brackets define a group name. All servers listed under [dev] belong to the "dev" group. When you run a playbook targeting "dev", it runs on exactly these servers. Think of it like a department list in a company directory.

tier=webA custom variable that tags this server as a "web" tier server. You can later use this in playbooks to make decisions — for example: "if this server is tier=app, run the JBoss validation check."
[linux_servers:children]The ":children" suffix means this group is made up of other groups (children). So "linux_servers" automatically includes all servers from dev, qa, uat, production, dr, and aws_ec2. This is very powerful for targeting all Linux servers in one shot.

playbooks/simple_example.yml — Understanding Every PartYAML
---
# ============================================================
# This is a simple playbook to understand the structure
# ============================================================

- name: My first banking playbook - Install and start nginx  # Play name (describe what this play does)
  hosts: dev                              # Target: run on all servers in 'dev' group
  become: true                            # Use sudo (we need root for package install)
  gather_facts: true                      # Collect server info before running tasks
  vars:                                   # Variables defined just for this play
    web_port: 80
    web_package: nginx

  tasks:                                  # The list of actions to perform

    - name: Install nginx web server       # Task 1: describe what this task does
      ansible.builtin.dnf:               # Use the dnf module (package manager)
        name: "{{ web_package }}"          # Package name using variable ({{ }} = Jinja2 template)
        state: present                   # Ensure it IS installed (present=install if missing)

    - name: Start and enable nginx service
      ansible.builtin.systemd:           # Use the systemd module (service manager)
        name: nginx
        state: started                   # Ensure service is running
        enabled: true                    # Enable auto-start on server reboot

    - name: Check if nginx is listening on port 80
      ansible.builtin.wait_for:          # Wait for a condition to be true
        port: "{{ web_port }}"
        state: started                   # Wait until port is open
        timeout: 30                      # Maximum wait time: 30 seconds

    - name: Show success message
      ansible.builtin.debug:             # Print information during playbook run
        msg: "nginx is running on {{ inventory_hostname }}"  # inventory_hostname = the server's name
Part of PlaybookExplanation — Think of It This Way
- name: (play level)The play name is the title of your entire operation. When Ansible runs, this is the first line printed on screen. Always write a clear, human-readable description like "Patch all DEV servers for CVE-2024-1086." Good play names make audit logs readable.
hosts: devThis is the most important line — it decides WHERE the playbook runs. It matches against your inventory groups. You can say hosts: all, hosts: production, hosts: dev,qa, or even a specific IP. In the bank, we NEVER use hosts: all for patching playbooks — too dangerous.
gather_facts: trueBefore running any task, Ansible runs the "setup" module on each server to collect facts — things like OS version, hostname, IP addresses, CPU count, available memory, disk space. We use these facts in our patching playbook (e.g., "if OS is RHEL 8, use yum; if RHEL 9, use dnf").
ansible.builtin.dnfThis is a module name in FQCN (Fully Qualified Collection Name) format. "ansible.builtin" means it is built into Ansible Core — no separate installation needed. "dnf" is the specific module for managing packages on RHEL/CentOS/Fedora systems. Using FQCN is a best practice because it avoids naming conflicts with custom modules.
state: presentIn Ansible, "state" describes the desired end state. "present" means "make sure it exists." "absent" means "make sure it is removed." "latest" means "install and always keep at the latest version." For security patching, we use "latest" to always get the newest version.
{{ web_package }}Double curly braces is Jinja2 template syntax. It means "replace this with the value of the variable named web_package." At runtime, Ansible substitutes {{ web_package }} with nginx. This makes playbooks reusable — change the variable, same playbook installs a different package.
inventory_hostnameThis is a special Ansible variable (called a magic variable) that automatically contains the name of the current server being processed. If Ansible is running on dev-app-01, inventory_hostname = "dev-app-01.globaltrust.in." This is how we make per-server log messages.

10 The Production Patching Playbook

Now we write the actual playbook that GlobalTrust Bank uses in production. This is the heart of the project. Read every line carefully — we will explain every word, every parameter, and every module.

playbooks/linux_compliance_patching.ymlYAML
---
# ============================================================
# GlobalTrust Bank — Linux Compliance Patching Playbook
# Purpose: Automated OS patching for RBI compliance
# Author: Priya Nair, DevOps Lead
# Version: 2.1
# ============================================================

# ===== PLAY 1: PRE-PATCH CHECKS =====
- name: PRE-PATCH — Validate server readiness before patching
  hosts: "{{ target_servers }}"             # Passed in via AAP Survey or -e flag
  become: true
  gather_facts: true
  serial: "10%"                             # Process 10% of servers at a time (rolling)
  vars:
    min_free_disk_gb: 5
    services_to_monitor:
      - nginx
      - jboss
    patch_log_file: "/var/log/ansible-patch/patch_{{ ansible_date_time.date }}.log"

  tasks:

    - name: Create patch log directory
      ansible.builtin.file:
        path: /var/log/ansible-patch
        state: directory                     # Ensure directory exists
        mode: '0755'
        owner: root

    - name: Check available disk space on /var partition
      ansible.builtin.shell:
        cmd: df -BG /var | awk 'NR==2 {gsub("G","",$4); print $4}'
      register: disk_check                   # Save output into variable 'disk_check'
      changed_when: false                    # df doesn't change anything — don't mark as changed

    - name: Fail if not enough disk space for patching
      ansible.builtin.fail:                  # Intentionally fail the playbook with a clear message
        msg: "❌ INSUFFICIENT DISK: {{ disk_check.stdout }}GB free on /var. Need {{ min_free_disk_gb }}GB. Server: {{ inventory_hostname }}"
      when: disk_check.stdout | int < min_free_disk_gb  # Only fail if disk is low

    - name: Record kernel version BEFORE patching
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_before
      changed_when: false

    - name: Check status of critical services before patching
      ansible.builtin.systemd:
        name: "{{ item }}"                    # Loop variable — 'item' takes each value from the list
      register: services_before
      loop: "{{ services_to_monitor }}"       # Loop over the services list
      ignore_errors: true                    # Don't stop if a service doesn't exist

    - name: Write pre-patch status to log file
      ansible.builtin.lineinfile:            # Add a line to a file
        path: "{{ patch_log_file }}"
        line: "PRE-PATCH | {{ inventory_hostname }} | Kernel: {{ kernel_before.stdout }} | Disk: {{ disk_check.stdout }}GB | Time: {{ ansible_date_time.iso8601 }}"
        create: true                        # Create the file if it does not exist

    - name: Display pre-check summary
      ansible.builtin.debug:
        msg:
          - "✅ Server: {{ inventory_hostname }}"
          - "  OS: {{ ansible_distribution }} {{ ansible_distribution_version }}"
          - "  Kernel Before: {{ kernel_before.stdout }}"
          - "  Free Disk: {{ disk_check.stdout }}GB"
          - "  PRE-CHECK: PASSED — Ready for patching"

# ===== PLAY 2: APPLY PATCHES =====
- name: PATCHING — Apply security patches to servers
  hosts: "{{ target_servers }}"
  become: true
  gather_facts: true
  serial: "10%"                             # Rolling — patch 10% at a time
  max_fail_percentage: 5                    # Stop if more than 5% of servers fail

  tasks:

    - name: Update all packages to latest (apply all security patches)
      ansible.builtin.dnf:
        name: "*"                             # * means all installed packages
        state: latest                        # Update to the latest available version
        security: true                       # Only install security updates (not all updates)
        update_cache: true                   # Refresh the package cache before updating
      register: patch_result                 # Store result to check if reboot is needed
      notify: Reboot if kernel updated       # Trigger handler if this task changed something

    - name: Force all handlers to run now (trigger reboot immediately)
      ansible.builtin.meta: flush_handlers  # Run handlers right now, not at end of play

# ===== PLAY 3: POST-PATCH VALIDATION =====
- name: POST-PATCH — Validate server health after patching
  hosts: "{{ target_servers }}"
  become: true
  gather_facts: true
  serial: "10%"

  tasks:

    - name: Wait for server to be reachable after reboot
      ansible.builtin.wait_for_connection:   # Wait for SSH to come back after reboot
        delay: 30                            # Wait 30 seconds before first check
        timeout: 600                         # Maximum wait: 600 seconds (10 minutes)

    - name: Collect fresh facts after reboot
      ansible.builtin.setup:               # Re-run fact gathering after reboot

    - name: Record kernel version AFTER patching
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_after
      changed_when: false

    - name: Verify critical services are running after patch
      ansible.builtin.systemd:
        name: "{{ item }}"
        state: started                       # ENSURE service is started (start it if not running)
      loop: "{{ services_to_monitor | default(['nginx']) }}"
      ignore_errors: true

    - name: Display post-patch summary
      ansible.builtin.debug:
        msg:
          - "✅ PATCH COMPLETE: {{ inventory_hostname }}"
          - "  Kernel Before: {{ kernel_before.stdout | default('N/A') }}"
          - "  Kernel After:  {{ kernel_after.stdout }}"
          - "  Patch Date: {{ ansible_date_time.date }}"
          - "  Status: SUCCESS — RBI Compliant ✅"

  handlers:                               # Handlers run ONLY when triggered by 'notify'

    - name: Reboot if kernel updated
      ansible.builtin.reboot:              # Reboot module — handles reboot + wait safely
        msg: "Rebooting for kernel patch — GlobalTrust Bank maintenance"
        connect_timeout: 5                # SSH connection timeout before reboot
        reboot_timeout: 600               # Wait up to 10 minutes for server to come back
        pre_reboot_delay: 5               # Wait 5 seconds before initiating reboot
        post_reboot_delay: 30             # Wait 30 seconds after reboot before next task

🔍 Deep Dive — Critical Concepts Explained

🔄 What is serial: "10%" and why is it essential for banking?

When you run a playbook without serial, Ansible processes ALL servers at the same time (parallel). Imagine patching all 200 production servers simultaneously — if the patch has a bug, all 200 servers go down at once. The entire bank stops.

With serial: "10%", Ansible processes only 10% of the servers (20 servers) at a time. It finishes those 20, checks they are healthy, then moves to the next 20. This is called a rolling update. If something goes wrong with the first batch, only 20 servers are affected — the remaining 180 are untouched.

📮 What is a Handler and why use notify?

A handler is a task that only runs when it is triggered (notified) by another task — and only if that task actually made a change. In our playbook, the dnf patching task sends a notify: Reboot if kernel updated signal. The handler (reboot) runs only if dnf actually updated something (changed=true). If all packages were already up to date (changed=false), the handler is never triggered — server is not rebooted unnecessarily. This is the Ansible way: idempotent, smart, and safe.

📊 What is register?

The register keyword saves the output of any task into a variable you can use later. When we run uname -r and register it as kernel_before, the variable contains everything about that command's execution: stdout (the output), stderr (error output), return code (0=success), and more. We can then reference kernel_before.stdout in later tasks to display or compare the kernel version. This is how we generate audit reports showing "kernel was 5.14.0-362 before patching and 5.14.0-427 after."

12 Ansible Vault — Protecting Bank Secrets

In a bank, you can never store passwords, SSH private keys, API tokens, or database credentials in plain text inside a Git repository. If a developer accidentally pushes a plain-text password to GitHub, it is visible to everyone and creates a massive security incident. Ansible Vault solves this by encrypting sensitive data using AES-256 encryption — the same standard used by banks for data protection.

Creating and Using Vault-encrypted filesBASH
# ===== CREATE A VAULT PASSWORD FILE =====

chmod 600 ~/.vault_pass             # Only owner can read this file

# ===== ENCRYPT A VARIABLES FILE =====

cat > inventory/group_vars/all/vault.yml << 'EOF'

💡 Pro Tip — Vault Best Practice in Banking
In GlobalTrust Bank, we split variables into two files inside group_vars/all/:

vars.yml — Non-sensitive variables (plain text, visible in Git): server names, port numbers, feature flags.
vault.yml — Sensitive variables only (encrypted): passwords, keys, tokens. Every sensitive variable name starts with vault_ prefix so it is immediately identifiable. Then in vars.yml, you reference: smtp_password: "{{ vault_smtp_password }}" — this way your playbooks reference clean names, but values are always vault-protected.

15 Execution Environments (EE)

16 Troubleshooting — Real Production Issues

🚨 Issue 1: SSH Connection Timeout During Patching
Symptoms

During Saturday night patching, the playbook starts failing with: UNREACHABLE! => Failed to connect to the host via ssh: ssh: connect to host prod-app-047 port 22: Connection timed out. But pinging the server from the exec node works fine.

Investigation Steps
Debugging SSH connection issuesBASH
# Step 1: Manually test SSH from exec node to the failing server
ssh -v -i ~/.ssh/id_ed25519 -o ConnectTimeout=10 ansible-svc@prod-app-047 echo "connected"

# Step 2: Check if port 22 is open
nc -zv prod-app-047.globaltrust.in 22
telnet prod-app-047.globaltrust.in 22

# Step 3: Check ansible.cfg SSH settings
ansible-config dump | grep -i ssh

# Step 4: Check server SSH service status (via out-of-band console)
# In VMware: Right-click VM → Open Console → Check systemctl status sshd

# Step 5: Check /var/log/secure on managed node
tail -100 /var/log/secure | grep ssh
Root Cause

The server had a high CPU load (98%) because a scheduled Oracle database backup job started at midnight (same time as patching window). The SSH daemon was accepting connections but could not spawn a new shell process fast enough — causing timeouts. This is called SSH connection starvation under high load.

Resolution
Fix: Increase SSH timeout and add retry logicYAML
# In ansible.cfg — increase timeout
[ssh_connection]
timeout = 60              # Increased from 30 to 60 seconds

# In the playbook — add retries for connection
- name: Wait for server to be reachable
  ansible.builtin.wait_for_connection:
    delay: 5
    timeout: 120
    sleep: 5
  retries: 3
  delay: 10
Preventive Measure

Coordinate with DBA team to move Oracle backup window to 6 AM Sunday (after patching completes at 4 AM). Also add a pre-check task that monitors server CPU load before beginning patching on each server — if load average is above 5.0, skip and alert.

🚨 Issue 2: Yum Dependency Error Blocks Patching
Symptoms

The patching task fails on 15 out of 200 production servers with error: Error: Problem: conflicting requests - package openssl-3.0.7 is filtered out by modular filtering

Investigation
Debug yum dependency conflictBASH
# On the failing server, run manually:
sudo dnf update --security -y --verbose 2>&1 | grep -i error

# Check which modules are enabled
sudo dnf module list | grep -i enabled

# Check if openssl is part of a module
sudo dnf module info openssl

# Try to update just openssl manually to understand the error
sudo dnf update openssl -y --verbose
Root Cause

Those 15 servers had a custom "banking-crypto" DNF module enabled (installed by the Security team 6 months ago for FIPS compliance). This module was locking the openssl version. The patching playbook tried to update openssl to a newer version that conflicted with the module's locked version.

Resolution
Fix: Add exclude list for FIPS-locked packagesYAML
- name: Apply security patches (exclude FIPS-locked packages)
  ansible.builtin.dnf:
    name: "*"
    state: latest
    security: true
    exclude:                     # Exclude these packages from update
      - openssl
      - openssl-libs
      - crypto-policies
  when: ansible_facts['fips_enabled'] | default(false)

17 Interview Preparation

💡 How to Answer Ansible Questions in an MNC Interview
Always start your answer with a real scenario from this project. Don't just say "Ansible is an automation tool." Say "In my project at GlobalTrust Bank, we used Ansible AAP to automate Linux patching across 300 servers — I'll explain how we did it..." This immediately shows the interviewer you have real production experience.

🟢 Beginner Questions

Q1. What is Ansible and why do companies use it over shell scripts?
Ansible is an open-source IT automation tool that automates tasks like server configuration, application deployment, and infrastructure management without requiring agents to be installed on managed servers. In our banking project, we chose Ansible over shell scripts for three main reasons. First, Ansible is idempotent — running the same playbook twice gives the same result without causing errors or double-installing packages. Shell scripts are not idempotent by default and require manual if-else checks everywhere. Second, Ansible has a huge library of built-in modules (over 3000) that handle edge cases, error handling, and platform differences — modules like dnf, systemd, reboot handle everything safely. Third, Ansible has Ansible Vault for securing credentials, and with AAP you get a web UI with RBAC, audit logging, scheduling, and approval workflows — things you cannot easily build with shell scripts.
Q2. What is the difference between a playbook, a play, and a task?
Think of it like a book. A Playbook is the entire book — the YAML file that contains everything. A Play is a chapter in that book — it has a target (hosts: production) and a list of things to do. A Task is a single sentence in that chapter — it calls one module to do one specific thing (install nginx, start a service, copy a file). One playbook can have multiple plays (e.g., Play 1 runs on web servers, Play 2 runs on DB servers). One play has multiple tasks. In our patching playbook, we had Play 1 for pre-checks (targeting all servers), Play 2 for patching (targeting all servers), and Play 3 for post-validation (targeting all servers).
Q3. What does "idempotent" mean in Ansible?
Idempotent means running the same operation multiple times produces the same result as running it once — no side effects, no errors. In Ansible, if you write a task "install nginx" and nginx is already installed, Ansible will say "ok" (no change) — it will not reinstall it or throw an error. This is unlike a shell script that might run yum install nginx again and cause unexpected issues. In our bank, this is critical for production safety — we can run our patching playbook daily for audit purposes, and on a fully patched server it will report everything as "ok" without making any changes. This also means if a patching job fails halfway through, you can re-run it safely — it will skip already-patched packages and continue from where it left off.

🟡 Intermediate Questions

Q4. How do you handle secrets and passwords in Ansible? Explain Ansible Vault.
In a banking environment, we never store passwords in plain text. Ansible Vault encrypts sensitive data using AES-256 encryption. We use it in two ways. First, we encrypt entire files — for example, our group_vars/all/vault.yml contains all passwords, SSH keys, and API tokens. We encrypt this file with ansible-vault encrypt vault.yml using a vault password. The encrypted file is safe to store in Git. Second, we encrypt individual variable values using ansible-vault encrypt_string — this is useful for encrypting a single password inside an otherwise plain-text YAML file. At runtime, we pass the vault password to the playbook using --vault-password-file ~/.vault_pass, or in AAP, we create a Vault Credential that is stored securely in the Controller database. A best practice I follow is keeping a naming convention: all encrypted variables start with vault_ so anyone reading the code immediately knows it is sensitive.
Q5. What is the difference between import_tasks and include_tasks?
This is a common interview question. import_tasks is static — it is processed at playbook parse time (before the playbook runs). This means tags applied to the import apply to all tasks inside the imported file. You cannot use variables in the file name with import_tasks. include_tasks is dynamic — it is processed at runtime, when that line is actually reached. This means you CAN use a variable in the file name (great for OS-specific tasks like include_tasks: "{{ ansible_os_family }}_tasks.yml"). However, tags do not automatically pass through to included tasks. In our patching role, we use import_tasks for pre_check, patch, and post_check because we want the tags (pre_check, patch, post_check) to work properly for selective execution. We use include_tasks for OS-specific handling where the filename depends on the OS version detected from facts.
Q6. What is the serial keyword and when do you use it?
The serial keyword controls how many servers Ansible processes at one time in a rolling update fashion. Without serial, Ansible runs all servers in parallel simultaneously. With serial: "10%", Ansible processes 10% of servers at a time — finishes them completely (all tasks), then moves to the next 10%. This is critical for production in banking. In our case with 200 production servers and serial: "10%", Ansible processes 20 servers at a time. If something goes wrong with the first batch, only 20 servers are affected. The remaining 180 are untouched. I also used max_fail_percentage: 5 alongside serial — this means if more than 5% of a serial batch fails, the entire workflow stops. This is a safety guardrail for high-availability environments where partial failures are acceptable but total failures are not.

🔴 Advanced / Scenario-Based Questions

Q7. A playbook fails on 30 out of 200 servers. How do you investigate and handle this?
First, I look at the error message in the AAP job output — is it a connection error (SSH timeout), a task error (yum conflict), or a system error (disk full)? I use -v or -vvv verbosity flags to see detailed output. If it is a pattern — for example, only RHEL 8.7 servers fail — that tells me it is OS-version-specific. I would also check if the failing servers belong to a specific network segment or hardware model. For investigation on the failing server: SSH in manually and run the failing command to see the actual error. Check relevant log files: /var/log/ansible-patch/, /var/log/yum.log, /var/log/dnf.log. For re-running selectively: Ansible creates a retry file listing failed hosts. I can use ansible-playbook site.yml -i inventory/ --limit @site.retry to run only on the failed servers after fixing the issue. In AAP, I would duplicate the job template, change the inventory limit to just the failed servers, and rerun. Preventively, I use block/rescue/always in the playbook so that even if patching fails, the post-check and notification tasks always run to alert the NOC team with the failure details.
Q8. How do you integrate Ansible with ServiceNow for Change Request automation?
We use the servicenow.itsm Ansible collection. The integration works in both directions. Before patching starts, our AAP Workflow Template reads the ServiceNow Change Request number (passed via Survey), validates it is in "Approved" state using the servicenow.itsm.change_request_info module, and only then proceeds. After patching completes, we use servicenow.itsm.change_request module to update the CR — set state to "Closed Complete", add a work note with the patch summary (how many servers patched, which kernel version, timestamp). The ServiceNow API credentials (URL, username, password) are stored in an AAP Custom Credential of type ServiceNow — encrypted, never visible in plain text. This creates a complete audit trail: every change in production has a CR number, and every CR has automated evidence of what was done.
Q9. What is an Execution Environment and why does AAP 2.4 use it?
An Execution Environment (EE) is a container image (OCI/Podman format) that packages together Ansible Core, Python, Python libraries, and Ansible Collections into a single, portable, version-locked environment. Before EEs, the Ansible control node had all collections and Python libraries installed directly on the OS. This created dependency conflicts ("collection X needs boto3 version 1.26 but collection Y needs 1.28") and made it impossible to upgrade without breaking something. With EEs, each job template can specify which EE to use — you can have one EE for AWS automation (with boto3 and amazon.aws collection), another for Linux patching (with ansible.posix, community.general), and another for Windows automation (with winrm). In our bank, we build custom EEs using ansible-builder, store them in our Private Automation Hub (offline), and assign them to job templates in the Controller. The EE runs as a Podman container on the Execution Node — isolated, reproducible, and version-controlled just like application Docker images.
Q10. Explain the difference between vars, defaults, group_vars, and host_vars — and their priority order.
Ansible has a variable precedence system — when the same variable is defined in multiple places, Ansible uses a priority order (higher number = higher priority). Understanding this is critical for production. The order from lowest to highest is: role defaults (lowest) → inventory group_vars → inventory host_vars → playbook vars → command line -e extra vars (highest). In practice: role defaults/main.yml defines safe default values that can be overridden by anything. group_vars/all.yml sets org-wide values for all servers. group_vars/production.yml sets values specific to PROD environment. host_vars/prod-app-001.yml overrides for a single critical server. -e extra_vars or AAP Survey overrides everything at runtime. In our bank, we use group_vars/production.yml to set serial: "5%" (smaller batches for PROD safety) while group_vars/dev.yml has serial: "50%" (faster for dev). The same playbook and role work for all environments — only the variables change.

🔧 Production Support Questions

Q11. How do you roll back if a patch breaks a production application?
We have a multi-layer rollback strategy. Layer 1 — VMware/AWS Snapshot: Before patching production, our pre-patch play takes a VM snapshot named "pre-patch-YYYY-MM-DD". If the application team reports an issue within the maintenance window, we revert the snapshot from the VMware console — this returns the server to its exact pre-patch state in under 5 minutes. Layer 2 — Kernel Rollback Playbook: We have a separate Ansible playbook that sets the default kernel back to the previous version using grubby --set-default-index=1 and reboots. This is faster than a snapshot if only the kernel is the issue. Layer 3 — Package Downgrade: For specific package issues, we use dnf downgrade openssl to go back to the exact previous version. The previous package is still in the yum cache unless cleaned. Layer 4 — ServiceNow Rollback CR: Any rollback action is documented in a new ServiceNow Change Request (Emergency CR) to maintain audit trail. RBI requires documentation of every change including rollbacks.
