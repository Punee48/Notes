1 Project Overview

📌 Why CI/CD + Ansible AAP Integration Matters
In Projects 01–04, Ansible playbooks were triggered manually — an engineer launches a job template in AAP or runs ansible-playbook from the command line. This is fine for infrastructure operations like patching. But for application deployments, you cannot ask a developer to manually launch a job in AAP every time they push code. The CI/CD pipeline must automatically trigger AAP after every successful build, test, and security scan. This is the bridge between development (Git) and operations (Ansible) — the heart of DevOps.

2 Business Requirement

🏦 GlobalTrust Bank's Deployment Reality

GlobalTrust Bank's Digital Banking team releases the Internet Banking application 3 times per week. Each release involves 15–20 microservices, 80+ EC2 instances, IIS configuration on 30 Windows servers, database migration scripts, and Route53 DNS updates. Before CI/CD integration with AAP, each deployment required the following chain: developer emails the DevOps team → DevOps engineer manually runs Ansible playbook → then manually runs another for IIS → then manually updates DNS → total time: 3–4 hours, 2 engineers occupied, high risk of human error.

🚨 The Deployment Incident That Triggered This Project
On March 15th, 2024 — a Friday afternoon release. Developer pushed code at 4:30 PM. DevOps engineer ran the deployment playbook but forgot to run the IIS configuration playbook (it was a "routine release" and she was rushed). The Windows IIS servers were serving old application DLLs while the Linux app servers had the new version. The result: users who hit Linux-backed microservices got correct data; users who hit Windows IIS got 500 errors. The mismatch caused corrupt transactions for 847 customers. 3-hour outage. ₹18 lakh in compensation. The CTO declared: "No deployment will ever again depend on an engineer remembering steps. Everything must be automated end-to-end."

  • All playbooks always run in correct sequence — enforced by pipeline
  • Every deployment logged in AAP with Git commit hash, author, timestamp

5 AAP REST API — The Foundation of All Integrations

Every CI/CD integration in this project — Jenkins, GitHub Actions, GitLab CI, Webhooks — works through the AAP REST API. Understanding the API is the foundation of everything else. AAP exposes a complete REST API that lets any external tool trigger jobs, check job status, read inventory, manage credentials, and much more.

🔵 What the AAP REST API Is
Think of the AAP REST API as the "remote control" for your Automation Controller. Instead of clicking buttons in the AAP web UI, you send HTTP requests (GET, POST, PATCH) to the controller's API endpoints from your CI pipeline. The API returns JSON responses. Every single thing you can do in the AAP UI can also be done through the API — creating job templates, launching jobs, checking job status, updating inventories, managing credentials. This is the key to automation — the UI is for humans, the API is for machines.

🔑 Key AAP API Endpoints Used in CI/CD

POST /api/v2/job_templates/{id}/launch/ Launch a Job Template. Most important endpoint in this project. Returns job ID for status tracking.
GET /api/v2/jobs/{id}/ Check status of a running or completed job. Poll this until status = successful or failed.
POST /api/v2/workflow_job_templates/{id}/launch/ Launch a Workflow Template (chains multiple job templates). Returns workflow_job ID.
GET /api/v2/workflow_jobs/{id}/ Check status of a running Workflow Job.
GET /api/v2/jobs/{id}/stdout/?format=txt Get the full text output of a completed job — useful for extracting deployment details.
POST /api/v2/inventories/{id}/refresh/ Trigger a dynamic inventory sync before deployment to ensure fresh server list.
GET /api/v2/job_templates/ List all job templates. Use ?name=Template+Name to find by name and get the ID.
POST /api/v2/tokens/ Create an OAuth2 access token for API authentication (better than username/password).

6 AAP API Authentication

Every API call to AAP must include authentication. There are three methods — we explain all three and tell you which to use where.

❌ Method 1: Basic Auth

Pass username:password in every request. Simple but insecure — password in every HTTP call. Use ONLY for testing/dev, never in production pipelines.

Basic AuthBASH
curl -u admin:password \
  https://aap-ctrl.../api/v2/jobs/

✅ Method 2: OAuth2 Bearer Token (RECOMMENDED)

Create a long-lived token in AAP, store it as a CI secret. Send as Bearer token header. This is the standard for all CI/CD integrations in GlobalTrust Bank.

Bearer TokenBASH
curl -H "Authorization: Bearer $AAP_TOKEN" \
  https://aap-ctrl.../api/v2/jobs/

🔵 Method 3: Personal Access Token (PAT)

User-specific token from AAP UI → User Settings → Tokens. Good for developer testing and debugging, not for automated pipelines.

Create Token via APIBASH
curl -X POST \
  -H "Content-Type: application/json" \
  -u admin:password \
  -d '{"description":"CI Token","scope":"write"}' \
  https://aap-ctrl.../api/v2/tokens/

7 Using Key API Endpoints — Complete Examples

🚀 Launching a Job and Polling for Completion

This is the core pattern used by every CI/CD tool. You launch a job via POST, get back a job ID, then poll the job status endpoint until the job finishes (successful or failed).

launch_aap_job.sh — Reusable shell function used by all CI toolsBASH
#!/bin/bash
# ============================================================
# Reusable AAP Job Launcher with Polling
# Usage: ./launch_aap_job.sh JOB_TEMPLATE_ID '{"extra_vars":{"env":"production"}}'
# ============================================================

AAP_URL="https://aap-ctrl.globaltrust.in"
AAP_TOKEN="${AAP_TOKEN}"                    # From CI environment secret
TEMPLATE_ID="${1:-42}"                       # Job Template ID
EXTRA_VARS="${2:-'{}'}"                      # Optional extra variables (JSON)
POLL_INTERVAL=10                             # Check every 10 seconds
MAX_WAIT=3600                                # Maximum wait: 60 minutes

# ===== STEP 1: Launch the job =====
echo "🚀 Launching AAP Job Template ID: ${TEMPLATE_ID}"
LAUNCH_RESPONSE=$(curl -sk \
  -X POST \
  -H "Authorization: Bearer ${AAP_TOKEN}" \
  -H "Content-Type: application/json" \
  -d "{\"extra_vars\": ${EXTRA_VARS}}" \
  "${AAP_URL}/api/v2/job_templates/${TEMPLATE_ID}/launch/")

# Extract the job ID from the response
JOB_ID=$(echo "${LAUNCH_RESPONSE}" | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")

if [ -z "${JOB_ID}" ]; then
  echo "❌ Failed to launch job. Response: ${LAUNCH_RESPONSE}"
  exit 1
fi
echo "📋 Job launched. Job ID: ${JOB_ID}"
echo "🔗 Monitor: ${AAP_URL}/#/jobs/${JOB_ID}/output"

# ===== STEP 2: Poll until completion =====
ELAPSED=0
while true; do
  STATUS=$(curl -sk \
    -H "Authorization: Bearer ${AAP_TOKEN}" \
    "${AAP_URL}/api/v2/jobs/${JOB_ID}/" \
    | python3 -c "import sys,json; d=json.load(sys.stdin); print(d['status'])")

  echo "⏳ Job ${JOB_ID} status: ${STATUS} (elapsed: ${ELAPSED}s)"

  case "${STATUS}" in
    "successful")
      echo "✅ AAP Job ${JOB_ID} completed SUCCESSFULLY"
      exit 0
      ;;
    "failed"|"error"|"canceled")
      echo "❌ AAP Job ${JOB_ID} FAILED with status: ${STATUS}"
      # Print job output for debugging in CI logs
      curl -sk -H "Authorization: Bearer ${AAP_TOKEN}" \
        "${AAP_URL}/api/v2/jobs/${JOB_ID}/stdout/?format=txt"
      exit 1
      ;;
    "running"|"pending"|"waiting")
      sleep "${POLL_INTERVAL}"
      ELAPSED=$((ELAPSED + POLL_INTERVAL))
      ;;
  esac

  if [ "${ELAPSED}" -ge "${MAX_WAIT}" ]; then
    echo "⏰ Timeout: Job ${JOB_ID} did not complete within ${MAX_WAIT} seconds"
    exit 1
  fi
done
Concept / CommandExplanation
POST .../job_templates/{id}/launch/The most important AAP API call. Sends a POST request to launch a specific job template. The {id} is the numeric ID of the job template in AAP (find it via the UI URL or GET /api/v2/job_templates/?name=...). The response includes the new job's ID which you use to track its progress.
extra_vars in POST bodyYou can pass runtime variables to the job from the CI pipeline. For example: {"extra_vars": {"target_env": "production", "app_version": "2.4.1", "git_commit": "abc123"}}. These become available in the playbook as {{ target_env }}, {{ app_version }}. This is how the CI pipeline passes build metadata to the Ansible deployment playbook.
Polling the job statusAfter launching, the CI script polls GET /api/v2/jobs/{id}/ every 10 seconds. The job status field cycles through: pending → waiting → running → successful (or failed/error/canceled). The CI step must wait here — it cannot proceed to the next pipeline stage until AAP deployment is confirmed complete. This blocking behavior ensures the pipeline stages are truly sequential.
stdout endpointIf the job fails, we fetch the full Ansible playbook output via /api/v2/jobs/{id}/stdout/?format=txt and print it to the CI logs. This is critical for debugging — without this, developers see "AAP job failed" with no context. With it, they see the exact Ansible error output in their CI pipeline logs.

8 AAP Webhooks — Direct Git-to-AAP Triggering

💡 Webhooks vs API Calls — When to Use Which
API calls from CI are used when you need the deployment to happen after CI steps (build, test, scan) — the CI pipeline calls AAP as one of its stages. AAP Webhooks are used when you want AAP to react directly to a Git event (push, merge) without going through any CI tool. For example: "When someone merges a change to the Ansible playbook repository, automatically trigger a compliance scan on all servers." No Jenkins or GitHub Actions involved — Git talks directly to AAP. Both patterns are used in GlobalTrust Bank for different use cases.

2
Get the Webhook URL and Key from AAP After saving, you see: Webhook URL: https://aap-ctrl.globaltrust.in/api/v2/job_templates/42/github/. Webhook Key: (a random secret — used to verify requests come from GitHub).

Configure Webhook in GitHub Repository GitHub repo → Settings → Webhooks → Add webhook. Payload URL: the AAP webhook URL above. Content type: application/json. Secret: paste the Webhook Key from AAP. Events: select "Pushes" and "Pull requests." Save.

9 Jenkins Integration — Overview

🔴 Jenkins in GlobalTrust Bank
Jenkins is the bank's primary CI tool for Java microservices — the Core Banking transaction processing system built with Spring Boot. Jenkins has been in use since 2016 and has 200+ pipelines. Rather than replacing Jenkins, we integrate it with AAP — Jenkins handles what it does well (compile Java, run JUnit tests, build JAR files, run SonarQube scans) and delegates infrastructure operations to AAP (deploy to servers, configure application servers, run health checks, update DNS).

🔌 Two Ways to Call AAP from Jenkins

Method 1 — Ansible Tower Jenkins Plugin

Install the "Ansible Tower" plugin in Jenkins. Configure AAP server credentials in Jenkins → Manage → Configure System. In Jenkinsfile, use the ansibleTower() step — one line to trigger AAP, wait for completion, and fail the build if AAP fails.

Best for: Teams already familiar with Jenkins plugins. Simple single job template triggers.

Method 2 — httpRequest Plugin / curl Shell Step

Use the Jenkins httpRequest plugin or a sh 'curl ...' step to call the AAP REST API directly. More control — you can pass custom extra_vars, handle responses, add custom retry logic.

Best for: Complex deployments needing custom logic. Passing build artifacts metadata to AAP.

// ============================================================
// GlobalTrust Bank — Core Banking Java Service CI/CD Pipeline
// Triggers: Push to main branch of core-banking.git
// ============================================================

pipeline {
  agent { label 'java-build-agent' }    // Run on Jenkins agent with Java 17 + Maven

  // ===== ENVIRONMENT VARIABLES =====
  environment {
    // Jenkins Credentials Store — never hardcode these
    AAP_TOKEN      = credentials('aap-cicd-token')       // AAP OAuth2 token (secret text)
    SONAR_TOKEN    = credentials('sonarqube-token')
    DOCKER_CREDS   = credentials('docker-registry-creds')  // username:password

    AAP_URL        = "https://aap-ctrl.globaltrust.in"
    APP_NAME       = "core-banking-svc"
    DOCKER_REGISTRY= "registry.globaltrust.in"

    // AAP Job Template IDs (find via API: GET /api/v2/job_templates/)
    JT_DEPLOY_DEV  = "45"              // "Deploy Core Banking — DEV" template ID
    JT_DEPLOY_QA   = "46"
    JT_DEPLOY_PROD = "47"
    JT_HEALTH_CHECK= "48"
    JT_ROLLBACK    = "49"
  }

  stages {

    // ===== STAGE 1: BUILD =====
    stage('Build') {
      steps {
        sh 'mvn clean package -DskipTests -Denv=ci'
        sh 'echo "Build artifact: $(ls target/*.jar)"'
      }
      post {
        success { echo "✅ Build successful: ${APP_NAME} v${env.BUILD_NUMBER}" }
        failure { error "❌ Build failed — pipeline aborted" }
      }
    }

    // ===== STAGE 2: UNIT TESTS =====
    stage('Unit Tests') {
      steps {
        sh 'mvn test -Dspring.profiles.active=test'
        junit 'target/surefire-reports/*.xml'      // Publish JUnit test results
      }
    }

    // ===== STAGE 3: SECURITY SCAN (SAST) =====
    stage('Security Scan') {
      steps {
        withSonarQubeEnv('SonarQube-Prod') {        // SonarQube plugin environment
          sh 'mvn sonar:sonar -Dsonar.projectKey=${APP_NAME}'
        }
      }
    }

    // ===== STAGE 4: QUALITY GATE =====
    stage('Quality Gate') {
      steps {
        timeout(time: 10, unit: 'MINUTES') {       // Wait max 10 min for SonarQube result
          waitForQualityGate abortPipeline: true    // Abort if quality gate fails
        }
      }
    }

    // ===== STAGE 5: BUILD DOCKER IMAGE =====
    stage('Build Docker Image') {
      steps {
        script {
          def imageTag = "${DOCKER_REGISTRY}/${APP_NAME}:${env.GIT_COMMIT[0..7]}"
          sh "docker build -t ${imageTag} ."
          sh "docker push ${imageTag}"
          env.DOCKER_IMAGE = imageTag               // Save for use in later stages
        }
      }
    }

    // ===== STAGE 6: DEPLOY TO DEV VIA AAP API =====
    stage('Deploy to DEV') {
      steps {
        script {
          // Call our reusable script — Method 2 (curl-based)
          sh """
            ./scripts/launch_aap_job.sh \${JT_DEPLOY_DEV} '{
              "extra_vars": {
                "target_env": "dev",
                "app_name": "${APP_NAME}",
                "docker_image": "${env.DOCKER_IMAGE}",
                "git_commit": "${env.GIT_COMMIT}",
                "build_number": "${env.BUILD_NUMBER}",
                "deployer": "jenkins-cicd"
              }
            }'
          """
        }
      }
    }

    // ===== STAGE 7: INTEGRATION TESTS ON DEV =====
    stage('Integration Tests') {
      steps {
        sh 'mvn verify -Pintegration-test -Denv=dev'
        sh './scripts/run_api_smoke_tests.sh dev'
      }
    }

    // ===== STAGE 8: DEPLOY TO QA VIA AAP =====
    stage('Deploy to QA') {
      steps {
        sh """./scripts/launch_aap_job.sh \${JT_DEPLOY_QA} '{"extra_vars":{"target_env":"qa","docker_image":"${env.DOCKER_IMAGE}"}}'"""
      }
    }

    // ===== STAGE 9: MANUAL APPROVAL BEFORE PROD =====
    stage('Production Approval') {
      when { branch 'main' }              // Only ask for approval on main branch
      steps {
        script {
          def approver = input(
            message: "Deploy ${APP_NAME} v${env.BUILD_NUMBER} to PRODUCTION?",
            submitterParameter: 'approver',
            parameters: [
              string(name: 'CHANGE_REQUEST', description: 'ServiceNow CR Number (CR0012345)')
            ]
          )
          env.APPROVED_BY = approver
          echo "✅ Production deployment approved by: ${approver}"
        }
      }
      post {
        aborted { error "❌ Production deployment declined" }
      }
    }

    // ===== STAGE 10: DEPLOY TO PRODUCTION VIA AAP =====
    stage('Deploy to PRODUCTION') {
      when { branch 'main' }
      steps {
        sh """
          ./scripts/launch_aap_job.sh \${JT_DEPLOY_PROD} '{
            "extra_vars": {
              "target_env": "production",
              "docker_image": "${env.DOCKER_IMAGE}",
              "cr_number": "${env.CHANGE_REQUEST}",
              "approved_by": "${env.APPROVED_BY}",
              "deployment_strategy": "blue_green"
            }
          }'
        """
      }
    }

    // ===== STAGE 11: POST-DEPLOY HEALTH CHECK =====
    stage('Health Check') {
      steps {
        sh """./scripts/launch_aap_job.sh \${JT_HEALTH_CHECK} '{"extra_vars":{"target_env":"production"}}'"""
      }
    }

  }  // end stages

  post {
    success {
      slackSend channel: '#deployments',
        color: 'good',
        message: "✅ ${APP_NAME} v${env.BUILD_NUMBER} deployed to PRODUCTION by ${env.APPROVED_BY}"
    }
    failure {
      // Trigger AAP rollback playbook on any pipeline failure in PROD stage
      script {
        if (env.STAGE_NAME == 'Deploy to PRODUCTION' || env.STAGE_NAME == 'Health Check') {
          sh """./scripts/launch_aap_job.sh \${JT_ROLLBACK} '{"extra_vars":{"target_env":"production"}}'"""
        }

🔐 Webhook Security — HMAC Signature Verification

AAP verifies webhook authenticity using HMAC-SHA256BASH
# How AAP verifies webhook requests are genuine (not forged)
# 1. When you configure the webhook in AAP, it gives you a Webhook Key
# 2. You paste this key into GitHub/GitLab as the webhook "Secret"
# 3. GitHub/GitLab signs every webhook payload with this key using HMAC-SHA256
# 4. AAP receives the payload + signature in X-Hub-Signature-256 header
# 5. AAP re-computes the signature from the payload and its stored key
# 6. If signatures match: genuine request, proceed to launch job
# 7. If signatures don't match: reject with 403 Forbidden

# This prevents attackers from sending fake webhooks to trigger deployments
# The webhook key must be kept secret (like a password)

# Testing webhook manually with signature (for debugging)
PAYLOAD='{"ref":"refs/heads/main","commits":[{"id":"abc123"}]}'
SECRET="your-aap-webhook-key"
SIG=$(echo -n "${PAYLOAD}" | openssl dgst -sha256 -hmac "${SECRET}" | awk '{print $2}')

curl -X POST \
  -H "Content-Type: application/json" \
  -H "X-Hub-Signature-256: sha256=${SIG}" \

🟢 Beginner Questions

Q1. What is the AAP REST API and why do CI/CD tools use it?
The AAP REST API is the programmatic interface to the Automation Controller — every action you can do in the AAP web UI (launch jobs, check status, manage credentials, update inventory) can also be done by sending HTTP requests to API endpoints. CI/CD tools use it because they need to trigger Ansible deployments automatically — a developer pushing code should not have to manually open the AAP UI and click "Launch." The CI pipeline calls the API to launch a job template, then polls the job status endpoint until the job completes, and either proceeds to the next pipeline stage (if successful) or fails the build (if the Ansible job failed). The key endpoint for CI/CD is POST /api/v2/job_templates/{id}/launch/ to start a job, and GET /api/v2/jobs/{id}/ to check its status. For workflow templates: POST /api/v2/workflow_job_templates/{id}/launch/ and GET /api/v2/workflow_jobs/{id}/.
Q2. How do you store and use the AAP token in GitHub Actions securely?
The AAP OAuth2 token is stored as a GitHub Repository Secret — an encrypted key-value pair stored at the repository level, accessible only to GitHub Actions workflows in that repository. You create it in Repository Settings → Secrets and variables → Actions → New repository secret. Name it AAP_TOKEN, paste the token value, save. In the GitHub Actions workflow YAML, you reference it as ${{ secrets.AAP_TOKEN }}. GitHub automatically injects it as an environment variable when the workflow runs and masks it in all job logs — so if you accidentally echo it, you see **** instead of the token value. This token is never in the code, never in logs, and never in the workflow YAML file — only in GitHub's encrypted secret storage. For production, we also mark it as a Protected secret — only available when running on protected branches (like main), preventing feature branch workflows from having production deployment access.

🟡 Intermediate Questions

Q3. What is an AAP Webhook and how is it different from calling the API from CI?
Both ultimately trigger an AAP job, but the direction of the call is different. When calling the API from CI, the CI pipeline makes an outbound HTTP POST to AAP — the CI tool is the initiator. This is used when you need the deployment to happen as part of a specific CI pipeline stage (after build, test, and scan). When using Webhooks, AAP receives an inbound HTTP POST from GitHub or GitLab directly — AAP is the receiver. This is used when you want AAP to react directly to a Git event (push, merge) without going through any CI tool. You configure the webhook receiver URL in AAP (Settings on the Job Template), copy it to GitHub/GitLab, and AAP automatically launches the job when GitHub sends the push event. The key security mechanism is HMAC-SHA256 signature verification — GitHub signs the payload with a shared secret, and AAP verifies the signature before launching anything. Without this verification, anyone who knew your webhook URL could trigger deployments.
Q4. How does Jenkins integrate with AAP? Compare the plugin method vs the curl method.
The Ansible Tower Jenkins Plugin provides a declarative ansibleTower() pipeline step. You configure the AAP server URL and credentials once in Jenkins global settings, then use it in Jenkinsfile with just the job template name, extra vars, and options. It handles authentication, job launch, polling, and failure detection automatically. Simplest to use, best for teams new to AAP integration. The curl method uses the sh 'curl ...' step to call the AAP REST API directly. You write a shell script that posts to /api/v2/job_templates/{id}/launch/, captures the job ID from the JSON response, then loops polling /api/v2/jobs/{id}/ until status is successful or failed. More verbose but gives full control — you can pass complex JSON extra_vars (build version, git commit, approver name), read the job output on failure for debugging, and handle partial failures with custom retry logic. In GlobalTrust Bank, we use the plugin for simple triggers like inventory refresh and health checks. We use the curl method for the main deployment pipeline because we need to pass rich metadata from the Jenkins build (Docker image tag, Maven artifact version, SonarQube scan result, approver name, ServiceNow CR number) as extra_vars to the AAP playbook. The playbook then uses these variables to deploy the correct version and update the CMDB.
Q5. Explain the Blue-Green deployment pattern and how you implemented it using AAP.
Blue-Green deployment maintains two identical production environments — Blue (currently live, serving all traffic) and Green (new version, initially receiving no traffic). The deployment process switches traffic from Blue to Green atomically, achieving zero downtime. We implemented this in GlobalTrust Bank using an AAP Workflow Template with eight job template nodes. The workflow: (1) verifies Blue is healthy, (2) provisions 20 new EC2 instances as Green environment, (3) deploys new Docker image to Green, (4) runs health checks against Green directly (not through ALB), (5) hits an AAP Approval Node — CISO must approve traffic shift in the AAP UI (gets Slack notification), (6) gradually shifts ALB traffic from Blue to Green using weighted target group rules (10% → 50% → 100%), (7) monitors Prometheus error rate for 5 minutes — if error rate exceeds 1%, automatically shifts traffic back to Blue (rollback), (8) terminates Blue EC2 instances after 30 minutes of stable Green operation. The key benefit over rolling deployment is instant rollback — if Green fails, we shift the ALB weight back to Blue in under 30 seconds. With rolling deployment, you can't easily undo changes on servers that were already updated. The cost of Blue-Green: you briefly run double the infrastructure (both Blue and Green simultaneously) — but for us this is 30–40 minutes of extra cost, which is acceptable for zero-downtime banking deployments. The CI pipeline triggers this entire workflow via a single POST to /api/v2/workflow_job_templates/15/launch/ with the docker image tag as an extra var.
Q6. What happens if the AAP API call fails mid-pipeline? How do you handle rollback?
We handle failure at multiple levels. In the polling script (launch_aap_job.sh), if the job status becomes "failed," "error," or "canceled," the script exits with code 1. In Jenkins, a non-zero exit code fails the pipeline stage. In GitHub Actions, a failed step marks the job as failed. In GitLab CI, it marks the job as failed and stops the pipeline. All three CI tools propagate the failure up and stop subsequent stages from running — preventing partial deployments. For rollback specifically: in the Jenkinsfile post failure block, we check if the failure happened in the Deploy to PRODUCTION or Health Check stage, and if so, we trigger a separate AAP rollback job template that switches the ALB weight back to Blue. In the Blue-Green workflow itself, if the Prometheus monitoring step detects elevated error rates, it automatically triggers the rollback as part of the workflow. This means rollback can happen either from the CI tool (Jenkins post block) or from within AAP (workflow failure path) — two safety nets. We also implement idempotency in all deployment playbooks — if a deployment fails halfway through, re-running the same playbook recovers gracefully. For example, if EC2 provisioning partially completed, the ec2_instance module with state: running won't create duplicate instances — it just starts the already-created ones.
Q7. How do you pass data from CI/CD to an Ansible playbook via extra_vars?
Extra variables (extra_vars) are passed in the HTTP POST body when launching a job via the AAP API. The body format is JSON: {"extra_vars": {"key": "value", "another_key": "another_value"}}. These become available as Ansible variables inside the playbook — you can reference them as {{ docker_image }}, {{ target_env }}, etc. For extra_vars to work via the API, the Job Template must have "Prompt on launch" enabled for the Extra Variables field — otherwise AAP ignores API-supplied extra_vars. In AAP UI: Job Template → Edit → Extra Variables → toggle "Prompt on launch" ON. We pass rich metadata from CI to AAP: the Docker image tag (so the playbook knows exactly which version to deploy), the git commit SHA (for CMDB tracking), the CI build number, the name of the engineer who approved the deployment (from Jenkins input() or GitHub Environment reviewer), and the ServiceNow Change Request number. The Ansible playbook then uses all of these to deploy the correct version, update the ServiceNow CR, and write audit evidence to the bank's compliance system. This complete data chain from developer's git push → CI metadata → Ansible → ServiceNow is what makes the deployment 100% auditable for RBI inspections.
