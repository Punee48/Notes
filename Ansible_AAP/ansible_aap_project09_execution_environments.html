🐳 Execution Environments (EE)

In AAP 2.x, every Ansible job runs inside a container — the Execution Environment. Understanding how to build, test, push, and use custom EEs is the most important skill difference between someone who uses AAP and someone who administers and builds AAP. This project covers it all from first principles.

1 Project Overview

📌 What Is an Execution Environment?
An Execution Environment (EE) is a container image that contains everything Ansible needs to run a playbook: the Ansible core engine, all Python dependencies (boto3, pywinrm, jinja2), all system packages (krb5-libs for Kerberos, openssl-devel), and all Ansible Collections. When AAP runs a job, it launches a container using the EE image, mounts the playbook inside it, runs the playbook, and destroys the container when done. Every job is isolated, reproducible, and self-contained. Think of it as a Docker image purpose-built for Ansible automation — and you build it with a tool called ansible-builder.

2 Why Execution Environments Replaced Python Virtualenvs

⚠️ The Old Way — Python Virtualenvs (AAP 1.x / Ansible Tower)
In Ansible Tower (the predecessor to AAP), dependency isolation was handled by Python virtualenvs. Each Job Template could specify a virtualenv that had its own Python packages. But virtualenvs only solve the Python problem — they don't isolate system packages (like krb5-libs for Windows Kerberos or libssl for HTTPS). If two Job Templates needed different versions of boto3, the admin had to create and maintain two virtualenvs manually on every Tower node. As the number of Job Templates grew, virtualenv management became a nightmare — "it works on this Tower node but not that one," "someone accidentally upgraded boto3 in the shared virtualenv and broke 5 Job Templates," and "adding a new Tower node requires manually recreating all virtualenvs."

❌ Python Virtualenv Problems

  • Must be created manually on every execution node
  • Only isolates Python — not system packages
  • No versioning — "the boto3 virtualenv" not "boto3 6.5.0 virtualenv"
  • Adding a new execution node = manually recreating all venvs
  • Drift: node A and node B may have different package versions
  • Cannot be tested locally — Tower-specific configuration

✅ Execution Environment Solutions

  • Container image — runs identically on any node with Podman
  • Isolates everything: Python, system packages, collections
  • Versioned container tags: ee-banking:1.2.0 is immutable
  • New execution node pulls image from registry — zero manual setup
  • Built from declarative files — reproducible and auditable
  • Test locally with ansible-navigator before deploying to AAP

3 Business Problem at GlobalTrust Bank

🚨 The "Works on My Tower" Problem
GlobalTrust Bank's Ansible Tower had 3 execution nodes. In 2023, the team upgraded the shared boto3 package on node-1 and node-2 but forgot node-3. For two weeks, AWS jobs ran fine when they landed on node-1 or node-2 but failed with cryptic Python import errors when they hit node-3. The RCA took 3 days to find — a single line in a Python dependency. More critically, the Windows Kerberos authentication stopped working on one node because someone upgraded the krb5-libs system package and it conflicted with the pywinrm version. The Security team declared: "We cannot have automation that behaves differently based on which server it happens to run on." This project is the migration to AAP 2.4 with Execution Environments — every job now runs in an identical container regardless of which execution node picks it up.

4 Project Story

📖 The Story — Building the Bank's Custom EE Library

After migrating from Ansible Tower to AAP 2.4, Priya's first task was building custom Execution Environments for the bank's specific needs. AAP ships with default EEs but they don't have pywinrm for Windows management, boto3 for AWS, the servicenow.itsm collection, or the bank's own globaltrust.banking collection. Priya designed three custom EEs: ee-linux-patching (lightweight, just what patching needs), ee-full-stack (everything — Windows, AWS, Azure, ServiceNow, monitoring), and ee-windows (Windows-specific with pywinrm and Kerberos). She wrote the ansible-builder definitions, tested them locally with ansible-navigator, pushed them to the Private Hub's container registry, and configured every Job Template in AAP to use the appropriate EE. The result: a new execution node added to the AAP cluster needs zero manual configuration — it pulls the EE image from the registry on first use and runs identically to every other node.

6 Anatomy of an Execution Environment Image

An EE is built as a multi-layer container image. Each layer adds components on top of the previous one. Understanding these layers helps you understand build errors and image sizes:

LAYER 1 — BASE Red Hat UBI9 (Universal Base Image) — minimal RHEL9 OS. Provides Python 3.11, dnf package manager, glibc. Source: registry.redhat.io/ansible-automation-platform/ee-minimal-rhel9
LAYER 2 — SYSTEM bindep.txt system packages installed via dnf/apt. Examples: krb5-devel (for Kerberos/Windows auth), openssl-devel, libffi-devel, gcc (for compiling Python C extensions). These are OS-level dependencies.
LAYER 3 — PYTHON requirements.txt Python packages installed via pip. Examples: boto3 (AWS SDK), pywinrm (Windows Remote Management), kubernetes (K8s Python client), jinja2, paramiko. These are Python library dependencies.
LAYER 4 — GALAXY requirements.yml Ansible Collections installed via ansible-galaxy. Examples: globaltrust.banking, amazon.aws, servicenow.itsm, ansible.windows. These are pulled from Private Automation Hub during the image build.
LAYER 5 — FINAL Any additional_build_steps (prepend_final / append_final) — custom commands like copying config files, setting environment variables, creating directories, or adding license files. The final layer that becomes the runnable image.
💡 Image Size Matters — Keep EEs Lean
Every time AAP runs a job on an execution node that doesn't already have the EE image cached, it pulls the entire image from the registry. A 2GB image takes 3–4 minutes to pull. That is 3–4 minutes of job startup time. GlobalTrust Bank has 3 EEs: ee-linux-patching (420MB — just patching tools), ee-windows (780MB — Windows/Kerberos dependencies), and ee-full-stack (1.2GB — everything). Use the smallest EE that has everything the playbook needs. Don't install boto3 in an EE that only does Linux patching.

8 The Two Key Tools

🔨 ansible-builder

A Python tool that reads your execution-environment.yml and generates a Containerfile (Dockerfile equivalent), then builds the EE image using Podman or Docker. Think of it as a specialised image build tool that knows Ansible's structure.

InstallBASH
pip install ansible-builder

Used for: building EE images from definition files.

🧭 ansible-navigator

A replacement for ansible-playbook that runs playbooks inside EE containers locally. It also provides an interactive terminal UI for browsing play results, hosts, tasks, and output. Use it to test EEs before pushing to AAP.

InstallBASH
pip install ansible-navigator

Used for: testing playbooks inside EE containers locally.

9 execution-environment.yml — Version 3 Format

📌 execution-environment.yml Is the Blueprint for Your EE
This single file defines everything about the container image ansible-builder will create. It references three separate files for the three dependency categories: galaxy (Ansible Collections), python (pip packages), and system (OS packages). Version 3 is the current format for ansible-builder 3.x — it uses a cleaner structure and supports multi-platform builds.

🏗️ ee-full-stack — GlobalTrust Bank Full Automation EE

ee-full-stack/execution-environment.yml — Complete definitionYAML
---
# execution-environment.yml — GlobalTrust Bank Full Stack EE
# Supports: Linux, Windows, AWS, Azure, ServiceNow, Monitoring
# Built with: ansible-builder 3.x (version 3 format)

version: 3                              # Use version 3 — current format for ansible-builder 3.x

images:
  base_image:
    name: registry.redhat.io/ansible-automation-platform-24/ee-minimal-rhel9:latest
    # Use Red Hat's official minimal EE as the base
    # Requires Red Hat subscription credentials in ansible-builder
    # Alternative for non-RH: ghcr.io/ansible/community-ee-base:latest

dependencies:
  galaxy: requirements.yml              # Ansible Collections file
  python: requirements.txt             # Python pip packages file
  system: bindep.txt                   # System packages (bindep format)

additional_build_steps:

  prepend_galaxy:                        # Run BEFORE installing collections
    - # Configure Private Hub as the galaxy server for collection installs
    - RUN ansible-galaxy collection install --upgrade \
        --server https://hub.globaltrust.in/api/galaxy/ \
        --token $AUTOMATION_HUB_TOKEN \
        globaltrust.banking:==1.2.0     # Pin to exact version in production EE

  prepend_final:                         # Run BEFORE finalizing the image
    - # Set bank's standard environment variables baked into the EE
    - ENV ANSIBLE_FORCE_COLOR=1
    - ENV ANSIBLE_HOST_KEY_CHECKING=False
    - ENV ANSIBLE_STDOUT_CALLBACK=yaml

  append_final:                          # Run AFTER all dependencies installed
    - # Add compliance note (for audit)
    - RUN echo "GlobalTrust Bank EE v1.2.0 — Built $(date -u +%Y-%m-%dT%H:%M:%SZ)" > /etc/ee-version
    - # Verify key Python packages installed correctly
    - RUN python3 -c "import boto3; import winrm; import kubernetes; print('All packages OK')"
    - # Verify key collections installed
    - RUN ansible-galaxy collection list | grep -E "(amazon.aws|servicenow.itsm|globaltrust.banking)"

build_arg_defaults:                      # Default values for Containerfile ARGs
  EE_BASE_IMAGE: registry.redhat.io/ansible-automation-platform-24/ee-minimal-rhel9:latest
  PKGMGR_PRESERVE_CACHE: "0"            # Don't preserve dnf cache in final image

options:
  package_manager_path: /usr/bin/dnf   # Explicit package manager (dnf for RHEL)
  skip_ansible_check: false             # Verify Ansible is present in base image
FieldExplanation
version: 3Specifies the execution-environment.yml schema version. Version 3 is for ansible-builder 3.x and later. Version 1 and 2 files are still supported but deprecated. Always use version 3 for new EE definitions — it has a cleaner structure and better error messages.
base_imageThe starting container image from which your EE is built. Red Hat provides official base images at registry.redhat.io (requires Red Hat subscription). The ee-minimal-rhel9 base has Ansible core and Python 3.11 but no collections or extra Python packages. This is the cleanest starting point — you control everything that is added on top. For air-gapped environments, mirror this base image to your Private Hub container registry first.
additional_build_stepsCustom Containerfile instructions inserted at specific points in the build. prepend_galaxy runs before collections are installed (e.g., configure the galaxy server). prepend_final runs before the final image layer is committed (set environment variables). append_final runs after all packages are installed (verify, add labels, clean cache). These are raw Containerfile commands: RUN, ENV, COPY, LABEL.
build_arg_defaultsDefault values for Containerfile ARG instructions. PKGMGR_PRESERVE_CACHE="0" tells dnf to clean its cache after installing packages, reducing the final image size. These can be overridden at build time with --build-arg.

🔍 The Generated Containerfile (What ansible-builder Creates)

context/Containerfile — auto-generated by ansible-builder (simplified view)DOCKERFILE
# Stage 1: Base — system packages
ARG EE_BASE_IMAGE=registry.redhat.io/.../ee-minimal-rhel9:latest
FROM ${EE_BASE_IMAGE} as base

# Install system packages (from bindep.txt)
RUN dnf install -y krb5-devel openssl-devel gcc openssh-clients git \
    && dnf clean all

# Stage 2: Galaxy — install Ansible collections
FROM base as galaxy
ARG ANSIBLE_GALAXY_CLI_COLLECTION_OPTS=""

# prepend_galaxy steps run here
RUN ansible-galaxy collection install --upgrade \
    --server https://hub.globaltrust.in/api/galaxy/ \
    globaltrust.banking:==1.2.0

# Install from requirements.yml
COPY _build/requirements.yml /build/requirements.yml
RUN ansible-galaxy collection install -r /build/requirements.yml

# Stage 3: Final — combine everything
FROM base as final

# Copy collections from galaxy stage
COPY --from=galaxy /usr/share/ansible /usr/share/ansible

# Install Python packages (from requirements.txt)
COPY _build/requirements.txt /build/requirements.txt
RUN pip3 install -r /build/requirements.txt

# prepend_final steps
ENV ANSIBLE_FORCE_COLOR=1
ENV ANSIBLE_HOST_KEY_CHECKING=False

# append_final steps
RUN echo "GlobalTrust Bank EE v1.2.0" > /etc/ee-version
RUN python3 -c "import boto3; import winrm; import kubernetes; print('All packages OK')"

💡 Design Principle: Smallest EE That Has Everything You Need
Before assigning an EE to a Job Template, ask: "What Python packages and collections does this playbook actually use?" If a Linux patching playbook only uses ansible.posix and globaltrust.banking.linux_baseline, it has zero need for boto3, pywinrm, or azure-mgmt-*. Using ee-linux-patching (420 MB) instead of ee-full-stack (1.2 GB) means 66% less storage per execution node, faster image pulls, smaller attack surface, and clearer intent — this Job Template is for Linux patching only.

13 Custom Build Steps — Advanced EE Customisation

Advanced additional_build_steps examplesYAML
---
version: 3

images:
  base_image:
    name: registry.redhat.io/ansible-automation-platform-24/ee-minimal-rhel9:latest

dependencies:
  galaxy: requirements.yml
  python: requirements.txt
  system: bindep.txt

additional_build_files:                  # Copy local files INTO the build context
  - src: files/globaltrust_ca.crt        # Bank's internal CA certificate
    dest: globaltrust_ca.crt
  - src: files/ansible.cfg              # Pre-configured ansible.cfg
    dest: ansible.cfg

additional_build_steps:

  prepend_base:                          # Run at the very start (base image stage)
    - # Install the bank's internal CA certificate — trusts internal HTTPS endpoints
    - COPY _build/globaltrust_ca.crt /etc/pki/ca-trust/source/anchors/
    - RUN update-ca-trust extract
    - # Without this, HTTPS calls to hub.globaltrust.in or hr-api.globaltrust.in would fail SSL

  prepend_galaxy:
    - # Set proxy for galaxy installs (bank routes internet through proxy)
    - ENV HTTPS_PROXY=http://proxy.globaltrust.in:8080
    - ENV NO_PROXY=hub.globaltrust.in,*.globaltrust.in

  append_final:
    - # Copy pre-configured ansible.cfg into the EE
    - COPY _build/ansible.cfg /home/runner/.ansible.cfg
    - # Add image labels for traceability
    - LABEL org.opencontainers.image.vendor="GlobalTrust Bank India Ltd"
    - LABEL org.opencontainers.image.version="1.2.0"
    - LABEL org.opencontainers.image.source="https://gitlab.globaltrust.in/ansible/ee-builds"
    - # Clean up build artifacts to reduce image size
    - RUN dnf clean all && rm -rf /var/cache/dnf /tmp/* /root/.cache/pip

14 Push EE to Private Automation Hub Container Registry

📌 Private Hub Has Two Registries
Private Automation Hub serves two types of content. (1) Collection Registry — stores Ansible Collections (the globaltrust.banking collection from Project 08). API path: /api/galaxy/. (2) Container Registry — stores Execution Environment images (Docker/Podman images). They are separate registries in the same Private Hub installation. This section is about the Container Registry.
Push workflow — tag, push, verify, configure in AAPBASH
# ===== 1: Build with correct tag (hub URL/namespace/name:version) =====
ansible-builder build \
  --file ee-full-stack/execution-environment.yml \
  --tag hub.globaltrust.in/globaltrust/ee-full-stack:1.2.0

# ===== 2: Also tag as 'latest' for convenience =====
podman tag \
  hub.globaltrust.in/globaltrust/ee-full-stack:1.2.0 \
  hub.globaltrust.in/globaltrust/ee-full-stack:latest

# ===== 3: Push both tags to Private Hub =====
podman push hub.globaltrust.in/globaltrust/ee-full-stack:1.2.0

15 ansible-navigator — Test EEs Locally

🧭 Why You Need ansible-navigator
ansible-navigator is the local tool for running Ansible playbooks inside EE containers — the same way AAP runs them. When you develop a playbook, instead of running ansible-playbook site.yml (which uses your local Python and collections), run ansible-navigator run site.yml which runs inside the EE container. This catches issues like "my EE doesn't have pywinrm" or "the playbook uses a filter from globaltrust.banking which I forgot to include in the EE" — before you push the EE to production and break a Job Template in AAP.

18 ansible-navigator.yml — Project Config File

💡 Stop Typing --execution-environment-image on Every Command
Create an ansible-navigator.yml file in your project root. ansible-navigator reads it automatically and applies the settings to every run. This is especially useful in CI/CD pipelines where you want consistent EE usage without long command-line arguments.
ansible-navigator.yml — Project-level configurationYAML
---
# ansible-navigator.yml
# Place in project root — auto-read by ansible-navigator

ansible-navigator:

  execution-environment:
    image: hub.globaltrust.in/globaltrust/ee-full-stack:1.2.0
    pull:
      policy: missing                  # missing = pull only if not cached locally

    enabled: true                       # Use EE (set to false for local Python)
    environment-variables:
      pass:                             # Pass these env vars from host into EE container

        - AWS_SECRET_ACCESS_KEY
        - AUTOMATION_HUB_TOKEN
      set:                              # Set these env vars inside EE (hard-coded values)
        ANSIBLE_FORCE_COLOR: "1"
        ANSIBLE_CALLBACKS_ENABLED: profile_tasks

  mode: stdout                         # stdout = behave like ansible-playbook (good for CI)
  # stdout | interactive  (interactive opens the TUI)

  logging:
    level: warning                     # warning | debug | critical
    file: ./ansible-navigator.log

  ansible:
    inventories:                        # Default inventory paths
      - ./inventory/

  playbook-artifact:
    enable: true                        # Save run artifacts (for replay and debugging)
    save-as: artifacts/{playbook_name}-{ts}.json

# Triggered on: changes to ee-builds/ directory

stages: [validate, build, test, push, notify]

variables:
  REGISTRY: hub.globaltrust.in

23 Interview Preparation

Q1. What is an Execution Environment in AAP 2.x? Why was it introduced?
An Execution Environment (EE) is a container image that provides the complete runtime for running Ansible playbooks in AAP 2.x. It contains: Ansible core engine, all required Python packages (boto3, pywinrm, kubernetes), system packages (krb5-libs for Kerberos), and Ansible Collections — all bundled as a portable, versioned container image. EEs were introduced to replace Python virtualenvs which were the isolation mechanism in Ansible Tower (AAP 1.x). Virtualenvs only isolated Python packages — they could not isolate system packages like krb5-libs or gcc. They also had to be created and maintained manually on every execution node, and any discrepancy between nodes caused "works on this node, fails on that node" bugs. At GlobalTrust Bank, we had exactly this problem — a boto3 upgrade on two of three Tower nodes broke AWS automation on the third node for two weeks before we found the cause. With EEs, the container image is identical on every execution node. A new execution node added to the AAP cluster just needs Podman installed — it pulls the EE image from the Private Hub container registry on first use and runs identically to every other node. The tool to build EE images is ansible-builder, and the tool to test playbooks inside EEs locally is ansible-navigator.
Q2. Explain the execution-environment.yml file and its key sections.
The execution-environment.yml file is the blueprint for building an EE image with ansible-builder. It has four main sections. images.base_image specifies the starting container image — we use Red Hat's official ee-minimal-rhel9 which has Ansible core and Python 3.11 but nothing else. dependencies points to three separate requirements files: galaxy (requirements.yml listing Ansible Collections), python (requirements.txt listing pip packages like boto3 and pywinrm), and system (bindep.txt listing OS packages like krb5-devel). The bindep format supports platform tags — krb5-devel [platform:rpm] installs only on RHEL/CentOS, libkrb5-dev [platform:dpkg] installs on Ubuntu. additional_build_steps is the most flexible section — it lets you insert raw Containerfile instructions at specific build stages: prepend_base runs at the very start (we use this to install the bank's internal CA certificate so HTTPS calls to internal APIs work), prepend_galaxy runs before collection installs (useful to configure the galaxy server URL), prepend_final and append_final bracket the final image layer (set ENV variables, add labels, run verification checks, clean cache). build_arg_defaults sets default values for Containerfile ARG instructions, like telling dnf not to preserve cache in the final image. ansible-builder reads this file and generates a multi-stage Containerfile then calls Podman to build the image.
Q3. What is ansible-navigator and how is it different from ansible-playbook?
ansible-navigator is a replacement for ansible-playbook that runs Ansible playbooks inside Execution Environment containers. When you run ansible-navigator run site.yml, it launches a Podman container using the specified EE image, mounts the playbook inside the container, runs it, and shows the output. The key difference from ansible-playbook is that ansible-navigator uses the EE container's Python, collections, and system packages — not your local machine's. This is critical for testing because it reveals problems before they appear in production AAP. For example, if your EE's requirements.txt forgot to include pywinrm, ansible-navigator run will fail with "ModuleNotFoundError: No module named 'winrm'" — the same error the AAP job would produce. Without ansible-navigator, you would discover this only after pushing to AAP, which wastes CI pipeline time and may impact production schedules. ansible-navigator also has an interactive terminal UI mode (the default without --mode stdout) where you can browse play results, drill into individual task outputs per host, and view module documentation — all inside the terminal. The ansible-navigator.yml config file lets you set the default EE image, environment variable passing, and logging options so you don't need to type --execution-environment-image on every command. In GlobalTrust Bank, every developer uses ansible-navigator locally — we retired ansible-playbook for any playbook intended for AAP.
Q4. How do you decide how many EEs to build and which EE to use for each job?
The design principle is: use the smallest EE that contains everything the playbook needs — nothing more. At GlobalTrust Bank, we analysed all Job Templates and found they clustered into five groups. Linux patching playbooks only need ansible.posix, globaltrust.banking (linux roles), and netaddr — we built ee-linux-patching at 420 MB. Windows automation needs pywinrm, requests-kerberos, krb5-devel, and ansible.windows — we built ee-windows at 780 MB. Cloud provisioning needs boto3, azure SDK, and cloud collections — ee-cloud at 950 MB. Complex deployment workflows need everything — ee-full-stack at 1.2 GB. Security scanning needs OpenSCAP tools and security modules — ee-security at 600 MB. The practical reasons for multiple EEs: faster job startup when execution nodes pull images (420 MB pulls in 30 seconds, 1.2 GB takes 4 minutes), smaller attack surface (a patching EE doesn't need cloud credentials or Windows tools so they can't be exploited even if a playbook is compromised), and clearer operational intent — when you assign ee-linux-patching to a Job Template, everyone knows this template only does Linux operations. In AAP, the EE is set at the Organisation level as a default, then overridden per Job Template. We audit quarterly to ensure no Job Template is using ee-full-stack when a smaller EE would suffice.
