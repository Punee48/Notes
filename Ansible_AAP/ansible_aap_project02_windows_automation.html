1 Project Overview

📌 The Big Difference From Project 01
In Project 01, we automated Linux servers using SSH — a protocol Linux speaks natively. Windows servers do NOT use SSH by default (though it can be enabled). Instead, Windows uses WinRM (Windows Remote Management) — Microsoft's own remote management protocol. Before Ansible can talk to a Windows server, you must configure WinRM. This is the most important concept in this entire project. Once WinRM is ready, Ansible uses special win_* modules (instead of the Linux modules) to do everything on Windows.

🏦 Use Case

Automate monthly Windows Update patching + IIS application server configuration + user hardening across 150+ Windows servers in a banking environment.

🛠️ Key Technologies

Windows Server 2019/2022, WinRM over HTTPS, pywinrm Python library, Ansible win_* modules, Kerberos/NTLM auth, AAP 2.4.

🎯 Automation Goals

Zero-touch Windows Updates, IIS site deployment, Windows service monitoring, local user provisioning, registry security hardening.

🔒 Authentication Methods

Method 1 — NTLM (Simple, Used in DEV/QA)

NTLM is a challenge-response authentication protocol built into Windows. For non-domain or simple environments, Ansible can authenticate using a local Windows administrator username and password via NTLM. It is simpler to set up but less secure than Kerberos.

group_vars for NTLM authYAML
# inventory/group_vars/dev_windows.yml
ansible_connection: winrm
ansible_winrm_transport: ntlm
ansible_port: 5986
ansible_winrm_server_cert_validation: ignore
ansible_user: ansible-svc
ansible_password: "{{ vault_win_password }}"

Method 2 — Kerberos (Enterprise, Used in PROD)

Kerberos is the Gold Standard for enterprise Windows authentication. It uses tickets issued by Active Directory — no passwords sent over the network. Ansible must have the python-kerberos library installed in the EE. This is what banks use in production.

group_vars for Kerberos authYAML
# inventory/group_vars/production_windows.yml
ansible_connection: winrm
ansible_winrm_transport: kerberos
ansible_port: 5986
ansible_winrm_server_cert_validation: validate
ansible_user: "ansible-svc@GLOBALTRUST.IN"
ansible_password: "{{ vault_win_domain_password }}"
ansible_winrm_kerberos_delegation: true

6 WinRM — The Foundation of Windows Automation

📌 The Most Important Concept in Windows Automation
WinRM is to Windows what SSH is to Linux. When you run an Ansible playbook targeting a Windows server, Ansible does NOT SSH into it. Instead, Ansible sends a SOAP/HTTP(S) message to the WinRM listener running on the Windows server. The WinRM listener receives the message, runs the included PowerShell script, and sends back the JSON result. This entire mechanism — setting up, securing, and troubleshooting WinRM — is what most Windows automation engineers spend 80% of their initial time on.

🔄 How Ansible Runs a Module on Windows

When you write a task like ansible.windows.win_service: name: spooler state: stopped, here is exactly what happens behind the scenes:

Step 1: Ansible reads the win_service module Python fileAnsible finds the win_service.py file from the ansible.windows collection. This file contains both the Python argument parser and embedded PowerShell code.
Step 2: Extracts the PowerShell scriptAnsible extracts the PowerShell code from inside the module and wraps your parameters into it. Something like: Stop-Service -Name "Spooler" -Force.
Step 3: Sends via WinRM to Windows ServerUsing the pywinrm Python library, Ansible connects to port 5986 (HTTPS), authenticates via Kerberos/NTLM, and sends the PowerShell script as a WinRM message.
Step 4: Windows executes PowerShellWinRM on the Windows server receives the message, runs the PowerShell code in a temporary PowerShell session, and captures the output.
Step 5: Returns JSON resultThe result (service stopped = changed: true, or already stopped = changed: false) is serialised as JSON and sent back over HTTPS to the Ansible exec node. Ansible displays ok, changed, or failed.

7 WinRM Setup — Enabling Ansible on Windows

This is the first thing you do on every Windows server you want to manage with Ansible. In the bank, we run this PowerShell script once — either manually (during initial setup), via Group Policy (GPO), or via a bootstrap Ansible playbook using a temporary Basic auth session.

🔧 Method 1 — Quick Setup Script (DEV / Lab)

Run this PowerShell on the Windows Server as AdministratorPOWERSHELL
# ============================================================
# GlobalTrust Bank — WinRM Quick Setup Script
# Run as: Administrator on each Windows Server
# ============================================================

# Step 1: Enable WinRM service and configure default settings
Enable-PSRemoting -Force
# This command does 4 things automatically:
# a) Starts the WinRM service
# b) Sets WinRM service to start automatically
# c) Creates a WinRM listener on port 5985 (HTTP)
# d) Adds a firewall rule to allow port 5985

# Step 2: Configure WinRM for Ansible
# This Ansible-provided script configures WinRM properly for all auth methods
$url = "https://raw.githubusercontent.com/ansible/ansible/devel/examples/scripts/ConfigureRemotingForAnsible.ps1"
$file = "$env:temp\ConfigureRemotingForAnsible.ps1"

# In bank (no internet): download this file from internal GitLab first
# Then run it:
powershell.exe -ExecutionPolicy ByPass -File $file

# Step 3: Verify WinRM listeners are created
winrm enumerate winrm/config/Listener
# Expected output shows TWO listeners:
# Listener [Source="GPO"]
#   Address = *
#   Transport = HTTP
#   Port = 5985
# Listener
#   Address = *
#   Transport = HTTPS
#   Port = 5986  <-- This is what we use in PROD

# Step 4: Verify from Ansible exec node (run on RHEL)
# curl --ntlm --user "ansible-svc:Password" -k https://win-dev-01:5986/wsman
Command / ParameterExplanation — Word by Word
Enable-PSRemoting -ForceThis PowerShell cmdlet (command-let) enables PowerShell Remoting on the Windows server. -Force suppresses all confirmation prompts — like -y in Linux commands. Without this, Windows asks "Are you sure?" at every step — impossible for automation.
Transport = HTTPS / Port = 5986WinRM can run over plain HTTP (port 5985) or encrypted HTTPS (port 5986). In production (banking), ALWAYS use HTTPS/5986 — plain HTTP transmits your Windows credentials in a way that can be intercepted on the network. HTTP is acceptable only in isolated DEV labs.
ConfigureRemotingForAnsible.ps1This is an official script maintained by the Ansible project. It configures WinRM with the correct settings that Ansible needs: enables NTLM auth, creates a self-signed SSL certificate for HTTPS, sets the memory limit for WinRM (important for large playbooks), and configures the WinRM service timeouts. Always use this script instead of manual configuration — it has all the edge cases handled.
ExecutionPolicy ByPassWindows PowerShell has an "Execution Policy" that controls which scripts can run. By default it is "Restricted" (no scripts at all). "ByPass" temporarily overrides this for this one command. We use ByPass rather than permanently changing the policy to maintain security hardening on the server.

🔐 Method 2 — Enterprise WinRM with Kerberos (PROD)

RHEL Execution Node — Install Kerberos dependenciesBASH
# On the Ansible EXECUTION NODE (RHEL) — install Kerberos client
sudo dnf install -y krb5-workstation krb5-libs python3-gssapi

# Configure Kerberos to know about our domain
sudo cat > /etc/krb5.conf << 'EOF'
[libdefaults]
  default_realm = GLOBALTRUST.IN
  dns_lookup_realm = false
  dns_lookup_kdc = true
  ticket_lifetime = 24h
  forwardable = true

[realms]
  GLOBALTRUST.IN = {
    kdc = ad01.globaltrust.in
    admin_server = ad01.globaltrust.in
  }

[domain_realm]
  .globaltrust.in = GLOBALTRUST.IN
  globaltrust.in = GLOBALTRUST.IN
EOF

# Test Kerberos: get a ticket for the ansible service account
kinit ansible-svc@GLOBALTRUST.IN
# Enter domain password when prompted

# Verify ticket was obtained
klist
# Output: Ticket cache: FILE:/tmp/krb5cc_1000
# Default principal: ansible-svc@GLOBALTRUST.IN
# Valid starting: Today 09:00  Expires: Tomorrow 09:00
ConceptExplanation — Simple Story
KerberosKerberos is like a railway station with a ticket counter (Active Directory). When you want to travel (connect to a Windows server), you first go to the ticket counter and prove your identity (username + password). The ticket counter gives you a ticket (TGT — Ticket Granting Ticket). You show this ticket at the train gate (Windows server) instead of showing your ID again. The Windows server trusts the ticket because it trusts the ticket counter (Active Directory). This way, your password is NEVER sent to the Windows server — only the ticket is. This is much more secure than NTLM.
kinitThis command ("Kerberos initialize") requests a Kerberos ticket for the ansible-svc user from Active Directory. It is equivalent to "logging in" to the Kerberos system. After kinit, Ansible can authenticate to ANY Windows server in the GLOBALTRUST.IN domain without re-entering the password.
default_realm = GLOBALTRUST.INThe "realm" in Kerberos is the security boundary — basically, your Active Directory domain name in UPPERCASE. When Ansible authenticates as ansible-svc@GLOBALTRUST.IN, the @GLOBALTRUST.IN tells Kerberos which domain/realm to authenticate against.
forwardable = trueThis allows the Kerberos ticket to be forwarded to other systems. In Ansible, this is needed because the Exec Node gets the ticket and needs to forward it to Windows servers. Without this, Kerberos authentication would fail at the Windows server.

8 AAP Credentials for Windows

📌 How AAP Handles Windows Credentials
In Project 01, we stored an SSH private key in AAP as a "Machine Credential." For Windows, the credential type is still "Machine Credential" — but instead of an SSH key, we store the Windows username and domain password. AAP encrypts this in its PostgreSQL database and injects it into the execution environment at runtime as environment variables — the playbook never sees the raw password.
Create Windows Machine Credential in AAP Controller Navigate to Credentials → Add → Machine Credential. Name: "Windows Domain Account". Username: ansible-svc@GLOBALTRUST.IN. Password: (enter the domain password — it will be encrypted). This credential is attached to every Windows job template.
Create Kerberos Credential Type (Custom) For enterprise Kerberos, we create a Custom Credential Type in AAP: Settings → Credential Types → Add. This stores the Kerberos realm, KDC (Key Distribution Center) address, and keytab file. The keytab allows Ansible to authenticate without entering a password each time — ideal for scheduled jobs that run overnight.
Update Execution Environment for pywinrm The EE must include pywinrm (the Python library that speaks WinRM) and python-kerberos. We create a separate EE named ee-windows-automation:1.0 for Windows playbooks.

9 Windows Modules — The Complete Arsenal

Just like how Linux has dnf, systemd, file modules — Windows has its own equivalent modules starting with win_. These are in two collections: ansible.windows (official, maintained by Red Hat) and community.windows (community, maintained by contributors). In an interview, always say the FQCN (Fully Qualified Collection Name).

ansible.windows.win_updates
Install Windows Updates (like Windows Update in GUI). Supports categories: SecurityUpdates, CriticalUpdates, UpdateRollups.
ansible.windows.win_service
Start, stop, restart, enable, disable Windows Services (like systemctl for Linux).
ansible.windows.win_user
Create, modify, delete local Windows user accounts. Set passwords, group memberships.
ansible.windows.win_group
Create and manage local Windows groups (like groupadd in Linux).
ansible.windows.win_regedit
Create, modify, delete Windows Registry keys and values. Critical for security hardening.
ansible.windows.win_file
Create files, directories, set permissions on Windows (like file module in Linux).
ansible.windows.win_copy
Copy files from Ansible control node to Windows server.
ansible.windows.win_template
Deploy Jinja2 templates to Windows servers (generate config files from templates).
ansible.windows.win_powershell
Run arbitrary PowerShell scripts on Windows. Use when no specific module exists.
ansible.windows.win_ping
Test WinRM connectivity to Windows servers (like ansible.builtin.ping for Linux).
ansible.windows.win_reboot
Reboot Windows server safely and wait for it to come back online (like ansible.builtin.reboot).
community.windows.win_iis_website
Create and manage IIS websites — name, port, path, application pool, state.
community.windows.win_iis_webapppool
Manage IIS Application Pools — .NET version, identity, auto-start, recycling.
community.windows.win_scheduled_task
Create and manage Windows Task Scheduler jobs — like cron for Windows.
community.windows.win_eventlog_entry
Read Windows Event Logs and write custom entries — useful for audit logging.
community.windows.win_firewall_rule
Manage Windows Firewall rules — add, remove, enable, disable rules.

🛡️ The Full Windows Patching Playbook

playbooks/windows_compliance_patching.ymlYAML
---
# ============================================================
# GlobalTrust Bank — Windows Compliance Patching Playbook
# Purpose: RBI + CERT-In patch compliance for Windows servers
# ============================================================

# ===== PLAY 1: PRE-PATCH CHECKS =====
- name: PRE-PATCH — Validate Windows server readiness
  hosts: "{{ target_servers }}"
  gather_facts: true
  serial: "15%"                             # 15% at a time for rolling update
  vars:
    win_patch_log_dir: 'C:\PatchLogs'
    min_disk_gb: 10                          # Windows needs more disk than Linux
    services_to_check:
      - W3SVC                               # IIS World Wide Web Publishing Service
      - MSSQLSERVER                         # SQL Server (if present)
      - wuauserv                            # Windows Update service itself

  tasks:

    - name: Test WinRM connection (Windows ping)
      ansible.windows.win_ping:             # Equivalent of ansible.builtin.ping for Windows

    - name: Check available disk space on C drive
      ansible.windows.win_powershell:       # Run custom PowerShell when no module exists
        script: |
          $disk = Get-PSDrive -Name C
          $freeGB = [math]::Round($disk.Free / 1GB, 2)
          return @{ free_gb = $freeGB }  # Return hashtable — Ansible converts to JSON
      register: disk_info

    - name: Fail if C drive does not have enough space
      ansible.builtin.fail:
        msg: "❌ C drive free space: {{ disk_info.output[0].free_gb }}GB. Need {{ min_disk_gb }}GB minimum for patching."
      when: disk_info.output[0].free_gb | float < min_disk_gb

    - name: Record Windows version and current patch level
      ansible.windows.win_powershell:
        script: |
          $os = Get-CimInstance Win32_OperatingSystem
          $hotfixes = (Get-HotFix | Sort-Object InstalledOn -Descending | Select-Object -First 1)
          return @{
            caption     = $os.Caption
            build       = $os.BuildNumber
            last_patch  = $hotfixes.HotFixID
            install_date = $hotfixes.InstalledOn.ToString("yyyy-MM-dd")
          }
      register: windows_info
      changed_when: false

    - name: Check status of critical services before patching
      ansible.windows.win_service:
        name: "{{ item }}"
      register: services_pre_status
      loop: "{{ services_to_check }}"
      ignore_errors: true                    # Service might not exist on all servers

    - name: Create patch log directory on Windows
      ansible.windows.win_file:             # Windows equivalent of ansible.builtin.file
        path: "{{ win_patch_log_dir }}"
        state: directory

    - name: Display pre-check summary
      ansible.builtin.debug:               # debug module works same on Linux and Windows
        msg:
          - "✅ Server: {{ inventory_hostname }}"
          - "  OS: {{ windows_info.output[0].caption }}"
          - "  Build: {{ windows_info.output[0].build }}"
          - "  Last Patch: {{ windows_info.output[0].last_patch }}"
          - "  Free Disk: {{ disk_info.output[0].free_gb }}GB"
          - "  PRE-CHECK: PASSED ✅"

# ===== PLAY 2: APPLY WINDOWS UPDATES =====
- name: PATCHING — Apply Windows Security Updates
  hosts: "{{ target_servers }}"
  gather_facts: false                      # Skip facts — already collected in Play 1
  serial: "15%"
  max_fail_percentage: 5

  tasks:

    - name: Install Windows Security Updates from WSUS
      ansible.windows.win_updates:          # The key module for Windows patching

Module / ParameterDeep Explanation — Word by Word
ansible.windows.win_updatesThis module is the equivalent of ansible.builtin.dnf for Windows. It talks to the Windows Update Agent (WUA) which in turn talks to either Microsoft's servers or your internal WSUS (Windows Server Update Services) server. In a bank, we always use WSUS — an internal update server that mirrors Microsoft's patches. category_names: SecurityUpdates, CriticalUpdatesWindows updates are categorised. "SecurityUpdates" are patches for CVEs — these are what CERT-In and RBI mandate. In a banking network, direct internet access from production servers is blocked by firewall — this setting ensures updates work via the internal WSUS server.

11 IIS Web Server Automation

GlobalTrust Bank's Internet Banking portal runs on IIS (Internet Information Services) — Microsoft's web server built into Windows Server. Every release of the banking application requires IIS configuration — creating new sites, managing application pools, setting bindings. Manually, this takes hours and is error-prone. Ansible automates it in minutes.

📌 IIS Concepts — Before You Read the Playbook
Think of IIS in three layers. An Application Pool is like a process manager — it runs your .NET application in an isolated process. A Website is the virtual site that has a port binding, a root directory, and points to an Application Pool. A Web Application is a sub-folder within a website that can have its own Application Pool. For GlobalTrust Bank's Internet Banking: AppPool = "IBankAppPool", Website = "InternetBanking", bound to port 443 (HTTPS).
playbooks/windows_iis_setup.ymlYAML
---
# GlobalTrust Bank — IIS Internet Banking Site Configuration

- name: Configure IIS for Internet Banking Application
  hosts: "{{ target_servers | default('windows_dev') }}"
  gather_facts: true

  vars:
    iis_site_name: InternetBanking
    iis_site_path: 'C:\inetpub\globaltrust\internetbanking'
    iis_app_pool_name: IBankAppPool
    iis_port_http: 80
    iis_port_https: 443
    iis_dotnet_version: v4.0

  tasks:

    - name: Ensure IIS is installed (Windows Feature)
      ansible.windows.win_feature:           # Install Windows Features (like yum install)
        name:
          - Web-Server                      # IIS itself
          - Web-Asp-Net45                   # ASP.NET 4.5 support
          - Web-Mgmt-Tools                  # IIS Management Tools
          - Web-Http-Logging                # HTTP request logging
          - Web-Basic-Auth                  # Basic Authentication module
          - Web-Windows-Auth                # Windows Authentication module
        state: present
        include_management_tools: yes
      register: iis_install

    - name: Reboot if IIS installation requires it
      ansible.windows.win_reboot:
        post_reboot_delay: 60
      when: iis_install.reboot_required

    - name: Create website root directory
      ansible.windows.win_file:
        path: "{{ iis_site_path }}"
        state: directory

    - name: Create IIS Application Pool for Internet Banking
      community.windows.win_iis_webapppool:
        name: "{{ iis_app_pool_name }}"
        state: present
        attributes:
          managedRuntimeVersion: "{{ iis_dotnet_version }}"  # .NET version for the pool
          managedPipelineMode: Integrated   # Integrated mode (modern, better performance)
          processModel.identityType: ApplicationPoolIdentity  # Run as built-in IIS identity
          recycling.periodicRestart.time: "00:00:00"         # Disable time-based recycling in bank
          startMode: AlwaysRunning           # Keep pool warm — no cold start latency

    - name: Create the Internet Banking IIS Website
      community.windows.win_iis_website:
        name: "{{ iis_site_name }}"
        state: started                      # Site should be running after creation
        port: "{{ iis_port_http }}"           # HTTP port (will redirect to HTTPS)
        ip: "*"                              # Listen on all IP addresses
        hostname: ""
        physical_path: "{{ iis_site_path }}" # Root directory of the website
        application_pool: "{{ iis_app_pool_name }}"  # Which AppPool to use

    - name: Add HTTPS binding (port 443) to Internet Banking site
      community.windows.win_iis_webbinding:
        name: "{{ iis_site_name }}"
        protocol: https
        port: "{{ iis_port_https }}"
        ip: "*"
        host_header: internetbanking.globaltrust.in
        ssl_flags: 0                         # 0 = use server cert, 1 = SNI (Server Name Indication)
        certificate_hash: "{{ iis_ssl_cert_thumbprint }}"  # SSL cert thumbprint from Vault
        certificate_store_name: My          # 'My' = Personal certificate store
        state: present

    - name: Set HTTP to HTTPS redirect using URL Rewrite rule
      community.windows.win_iis_webbinding:
        name: "{{ iis_site_name }}"
        protocol: http
        port: "{{ iis_port_http }}"
        state: absent                        # Remove HTTP binding — HTTPS only in production

    - name: Verify website is running and accessible
      ansible.windows.win_powershell:
        script: |
          $site = Get-WebSite -Name "{{ iis_site_name }}"
          if ($site.State -ne "Started") {
              throw "IIS site {{ iis_site_name }} is not in Started state. Current state: $($site.State)"
          }
          return @{ site_state = $site.State; site_id = $site.ID }
      register: site_check
      changed_when: false

    - name: Print IIS configuration result
      ansible.builtin.debug:
        msg: "✅ IIS Site '{{ iis_site_name }}' is {{ site_check.output[0].site_state }} on {{ inventory_hostname }}"
Module / ParameterExplanation
ansible.windows.win_featureWindows features are optional components like IIS, DNS Server, DHCP, Active Directory. They must be installed before use. This module is the equivalent of "Add Roles and Features" in Server Manager GUI. state: present installs, state: absent removes. Installing IIS often requires a reboot.
community.windows.win_iis_webapppool startMode: AlwaysRunningBy default, IIS Application Pools start only when the first HTTP request comes in (called "lazy loading"). For an Internet Banking site, this means the first customer after a reboot waits 10–15 seconds for the .NET application to warm up. AlwaysRunning starts the pool immediately on IIS start — first customer gets instant response. Critical for banking where every millisecond of latency matters.
managedPipelineMode: IntegratedThere are two IIS pipeline modes. "Classic" (old — for legacy ASP applications) and "Integrated" (modern — for ASP.NET MVC, Web API, .NET Core). The bank's Internet Banking runs on .NET 4.5 MVC — always use Integrated mode. It has better performance and supports HttpModules for authentication and audit logging.
certificate_hash (thumbprint)SSL certificates are identified by a thumbprint — a unique hash string like "A1B2C3D4E5F6...". The win_iis_webbinding module needs this thumbprint to find the right certificate in the Windows Certificate Store. The thumbprint is stored in Ansible Vault (it is sensitive because knowing the thumbprint can be used to identify the certificate). We use win_powershell to read it from the cert store and pass it here.

12 Windows Services Management

Windows Services are background processes that run regardless of whether anyone is logged in — just like Linux systemd services. In the bank, critical services include IIS (W3SVC), SQL Server (MSSQLSERVER), SQL Agent (SQLSERVERAGENT), and Windows Event Log (EventLog). Ansible's win_service module manages all of these.

playbooks/windows_services_management.ymlYAML
---
# Windows Services Management for GlobalTrust Bank

- name: Manage Windows Services — Banking Application Services
  hosts: "{{ target_servers }}"
  gather_facts: false

  vars:
    # List of services to ensure are always running
    required_services:
      - name: W3SVC
        display_name: IIS World Wide Web Publishing
        state: started
        start_mode: auto
      - name: WAS
        display_name: Windows Activation Service (IIS dependency)
        state: started
        start_mode: auto
      - name: EventLog
        display_name: Windows Event Log
        state: started
        start_mode: auto

    # Services that must be DISABLED (security hardening)
    disabled_services:
      - name: Spooler
        display_name: Print Spooler (PrintNightmare vulnerability)
      - name: RemoteRegistry
        display_name: Remote Registry (CIS benchmark — disable)
      - name: SNMP
        display_name: SNMP Service (deprecated, insecure)

  tasks:

    - name: Ensure required banking services are running
      ansible.windows.win_service:
        name: "{{ item.name }}"
        state: "{{ item.state }}"
        start_mode: "{{ item.start_mode }}"  # auto/manual/disabled
      loop: "{{ required_services }}"
      loop_control:
        label: "{{ item.display_name }}"   # Show friendly name in output (not technical name)

    - name: Disable insecure services (security hardening)
      ansible.windows.win_service:

      loop: "{{ disabled_services }}"

      ignore_errors: true                  # Service might not exist on all servers

    - name: Generate service status report
      ansible.windows.win_powershell:

          $services = @("W3SVC", "WAS", "EventLog", "Spooler", "RemoteRegistry")
          $report = $services | ForEach-Object {
              $svc = Get-Service -Name $_ -ErrorAction SilentlyContinue
              if ($svc) { @{ name=$_; status=$svc.Status.ToString(); startType=$svc.StartType.ToString() } }
          }
          return $report
      register: service_report
      changed_when: false

    - name: Display service status report
      ansible.builtin.debug:
        msg: "{{ service_report.output }}"

RBI issued an advisory that all banking Windows servers must disable this service if no printing is needed. In GlobalTrust Bank, none of the application servers need printing. Our playbook ensures Spooler is always stopped and disabled — any drift from this state is automatically corrected on the next playbook run. This is called configuration drift remediation — one of the most powerful uses of Ansible in enterprise banking.

14 Registry Automation — CIS Benchmark Hardening

The Windows Registry is a centralised database that stores all configuration settings for Windows — from system behaviour to application settings to security policies. Think of it like a massive key-value store, organised in a tree structure. For banking, the CIS (Center for Internet Security) benchmark for Windows Server defines hundreds of registry settings that must be configured for security compliance. Manually setting these on 150 servers is impossible. Ansible's win_regedit module makes it automatic.

playbooks/windows_registry_hardening.ymlYAML
---
# GlobalTrust Bank — Windows Registry Security Hardening
# Based on: CIS Microsoft Windows Server 2019 Benchmark v2.0

- name: Apply CIS Registry Hardening Settings
  hosts: "{{ target_servers }}"
  gather_facts: false

  vars:
    registry_settings:

      # ===== NETWORK SECURITY =====
      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa'
        name: LmCompatibilityLevel
        data: 5
        type: dword
        desc: Disable NTLM v1 and v2, allow only Kerberos (CIS 2.3.11.7)

      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa'
        name: RestrictAnonymous
        data: 1
        type: dword
        desc: Restrict anonymous access to named pipes and shares (CIS 2.3.10.1)

      # ===== DISABLE LEGACY PROTOCOLS =====
      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\SSL 2.0\Server'
        name: Enabled
        data: 0
        type: dword
        desc: Disable SSL 2.0 — broken, CVE-2014-3566 (POODLE)

      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server'
        name: Enabled
        data: 0
        type: dword
        desc: Disable TLS 1.0 — RBI mandates TLS 1.2+ for banking

      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.1\Server'
        name: Enabled
        data: 0
        type: dword
        desc: Disable TLS 1.1 — RBI mandates TLS 1.2+ for banking

      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Server'
        name: Enabled
        data: 1
        type: dword
        desc: ENABLE TLS 1.2 — Required for all banking applications

      # ===== WINDOWS REMOTE DESKTOP SECURITY =====
      - path: 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp'
        name: UserAuthentication
        data: 1
        type: dword
        desc: Require NLA (Network Level Authentication) for RDP — CIS 18.10.56.2

  tasks:

    - name: Apply all CIS registry hardening settings
      ansible.windows.win_regedit:          # The Windows Registry module
        path: "{{ item.path }}"             # Registry path (like a directory path in the registry tree)
        name: "{{ item.name }}"             # Registry value name (key within the path)
        data: "{{ item.data }}"             # Value to set (0=disabled, 1=enabled, or string)
        type: "{{ item.type }}"             # Data type: dword (integer), string, binary, multistring
        state: present                      # Ensure this registry entry exists with this value
      loop: "{{ registry_settings }}"
      loop_control:

Registry ConceptExplanation
HKLM:\SYSTEM\...HKLM stands for HKEY_LOCAL_MACHINE — the root of the Windows Registry for this computer. Everything under HKLM applies to the machine (all users). HKCU (HKEY_CURRENT_USER) is for per-user settings. In server automation, we almost always work with HKLM because we are configuring the server, not a user profile. The backslash (\) separates levels — like directories in a file path.
type: dwordDWORD means "Double Word" — a 32-bit integer (number). This is the most common registry type. Value 0 = disabled/off. Value 1 = enabled/on. Other types: string (REG_SZ) for text values, binary (REG_BINARY) for raw bytes, multistring (REG_MULTI_SZ) for multiple strings, qword (REG_QWORD) for 64-bit integers.
LmCompatibilityLevel: 5This setting controls which authentication protocols Windows allows. Value 5 = "Send NTLMv2 response only. Refuse LM and NTLM." This forces all network authentication to use only NTLMv2 (or preferably Kerberos). LM and NTLMv1 are broken and can be cracked easily. RBI requires this setting on all banking servers. Before Ansible, setting this on 150 servers was a week-long manual job.
TLS 1.0 / 1.1 Enabled: 0TLS 1.0 and 1.1 have known vulnerabilities (BEAST, POODLE, SWEET32 attacks). RBI's cybersecurity framework and PCI DSS (Payment Card Industry Data Security Standard) both mandate that banking systems use only TLS 1.2 or 1.3. Setting Enabled=0 disables these protocols at the Windows Schannel layer — meaning even if an application tries to use TLS 1.0, Windows refuses to establish the connection.

🚨 Issue 2: win_updates Takes Too Long — Timeout After 3600 Seconds
Symptoms

The win_updates task starts on production servers, but after 3600 seconds (1 hour) it fails with: fatal: [win-prod-047]: FAILED! => Unexpected failure during module execution. The connection was terminated while waiting for a response.

Root Cause

Windows Update can take more than 1 hour when installing many large updates (especially cumulative updates with service packs). The default WinRM timeout is 3600 seconds. The update process continues running on the Windows server, but Ansible's connection times out waiting for the response.

Resolution
Fix: Increase WinRM timeout for updatesYAML
# In group_vars/windows_production.yml
ansible_winrm_operation_timeout_sec: 7200   # 2 hours (default: 20 sec per operation)
ansible_winrm_read_timeout_sec: 7200         # 2 hours for reading response

# Also: use use_scheduled_task: true for very large updates
# This runs the update as a Windows Task (async) and polls for completion
ansible.windows.win_updates:
  category_names: [SecurityUpdates, CriticalUpdates]
  state: installed
  reboot: false
  use_scheduled_task: true      # Runs updates async via Task Scheduler
  schedule_task_username: SYSTEM
🚨 Issue 3: IIS App Pool Crashes After Patching
Symptoms

After Windows patching and reboot, the Internet Banking website returns 503 Service Unavailable. Monitoring alerts come in from the NOC. The IIS site is running but the Application Pool has stopped.

Investigation
Debug IIS AppPool crashPOWERSHELL
# Check Application Pool state
Get-WebConfiguration system.applicationHost/applicationPools/add | Select-Object name, state

# Check Windows Event Viewer for AppPool crash reason
Get-WinEvent -FilterHashtable @{LogName='System'; Id=5011} -MaxEvents 5

The .NET 4.5 framework was updated during patching, but the IIS Application Pool's .NET CLR was pointing to an older version path that changed after the update. The pool could not find its runtime and crashed on first request.

    script: |
      Import-Module WebAdministration
      $stoppedPools = Get-ChildItem IIS:\AppPools | Where-Object { $_.state -eq "Stopped" }
      foreach ($pool in $stoppedPools) {
          Start-WebAppPool -Name $pool.Name
          Write-Output "Started: $($pool.Name)"
      }
      return @{ restarted_count = $stoppedPools.Count }
🚨 Issue 4: Kerberos Clock Skew Error
Error Message

kerberos.exceptions.KerberosException: [Errno -1765328347] Kerberos cannot contact any KDC for realm 'GLOBALTRUST.IN' or more specifically Clock skew too great

Root Cause and Fix

Kerberos is extremely time-sensitive. If the clock difference between the Linux exec node and the Active Directory KDC (Key Distribution Center) is more than 5 minutes, Kerberos rejects all authentication attempts. This happens when NTP is not properly configured on the exec node.

# Verify sync
chronyc tracking

sudo cat >> /etc/chrony.conf << 'EOF'
server ad01.globaltrust.in iburst prefer
EOF

🟢 Beginner Questions

Q1. What is WinRM and why does Ansible need it for Windows?
WinRM stands for Windows Remote Management. It is Microsoft's implementation of the WS-Management protocol — a SOAP/HTTP-based protocol for remotely managing systems. Ansible needs WinRM to connect to Windows servers because Windows does not have SSH enabled by default. When Ansible runs a playbook targeting a Windows server, it does not SSH in — instead, it sends a WinRM message over HTTPS to port 5986 on the Windows server. The WinRM service on Windows receives this message, executes the included PowerShell code, and sends the JSON result back to Ansible. WinRM must be explicitly enabled on Windows servers before Ansible can manage them — it is off by default for security reasons. In our bank, we enabled WinRM using Microsoft's ConfigureRemotingForAnsible.ps1 script, which sets up HTTPS listener, creates a self-signed certificate, and configures the correct security settings for Ansible compatibility.
Q2. What is the difference between WinRM HTTP and WinRM HTTPS? Which do you use in production?
WinRM HTTP runs on port 5985 and transmits data unencrypted. Even though NTLM or Kerberos authentication is encrypted, the PowerShell commands and outputs travel in plain text over HTTP. Anyone on the same network can capture and read these — including commands that might contain sensitive information. WinRM HTTPS runs on port 5986 and uses TLS to encrypt all traffic — the entire session is encrypted end-to-end. In production banking, we ALWAYS use HTTPS/5986. RBI's security framework requires encrypted management channels. HTTP/5985 is acceptable only in isolated laboratory environments where there is no risk of eavesdropping. To use HTTPS, you need an SSL certificate on the Windows server — either a self-signed certificate (acceptable for internal automation) or a certificate from your internal CA (Certificate Authority). The ConfigureRemotingForAnsible.ps1 script automatically creates a self-signed certificate and sets up the HTTPS listener.
Q3. What Python library does Ansible use to communicate with Windows via WinRM?
Ansible uses pywinrm — a Python library that implements the WinRM protocol client. Without pywinrm installed in the Execution Environment, Ansible cannot connect to Windows at all. You install it with pip install pywinrm. For Kerberos authentication, you also need pywinrm[kerberos] which pulls in additional Kerberos dependencies. For NTLM authentication, requests-ntlm is needed. In our AAP setup, we created a dedicated Windows Execution Environment (ee-windows-automation:1.0) using ansible-builder — this EE has pywinrm, requests-kerberos, requests-ntlm, and the krb5-workstation system package all pre-installed. This EE is stored in our Private Automation Hub and assigned to all Windows job templates. This is the correct enterprise approach — not manually installing pywinrm on the control node.

🟡 Intermediate Questions

Q4. What are the different WinRM authentication methods? Which is most secure for banking?
There are four main WinRM authentication methods. Basic — username and password in plain base64 encoding. Never use in production — completely insecure. NTLM — challenge-response authentication. Better than Basic, supported without AD. Acceptable for isolated environments. Kerberos — ticket-based authentication via Active Directory. Most secure — no passwords sent over the network, uses time-limited tickets. Required for production banking environments. CredSSP — allows credential delegation (so the Windows server can authenticate to a third system on your behalf). Used for double-hop authentication scenarios. Security risk — only use when specifically needed. In GlobalTrust Bank, we use Kerberos for all production Windows servers. The ansible-svc domain account gets a Kerberos TGT (Ticket Granting Ticket) from AD, which is then used to authenticate to each Windows server without sending passwords. We use NTLM only in DEV/lab environments where joining the domain is not practical. Kerberos also requires that clocks be synchronised within 5 minutes between the Ansible exec node and Active Directory — this is a common production issue.
Q5. How does win_updates work? What is WSUS and why is it important in banking?
The win_updates module works by calling the Windows Update Agent (WUA) API on the target server. It tells the WUA to search for, download, and install updates matching the criteria you specify (category, KB article number, severity). The module then waits for the update operation to complete and returns whether a reboot is required. WSUS (Windows Server Update Services) is Microsoft's enterprise update management server. In a bank, you cannot allow 150 production Windows servers to download updates directly from Microsoft's internet servers — this creates unpredictable network traffic, uncontrolled patch versions, and security risks. Instead, WSUS mirrors all Microsoft updates internally. The security team tests each patch first, approves it for different computer groups, and only approved patches are served to servers. The win_updates module with server_selection: managed_server tells the Windows Update Agent to use WSUS instead of Microsoft's servers. This is a non-negotiable requirement in banking — you must have an internal patch testing and approval process before anything touches production.
Q6. Explain win_regedit. What are DWORD, STRING, and BINARY types?
The win_regedit module manages Windows Registry entries. The Windows Registry is a hierarchical database of configuration settings. It has hive roots (HKLM, HKCU, etc.), under which there are paths (folders), and within paths there are named values (keys) with their data and type. The module needs four things: path (where in the registry), name (what key), data (what value to set), and type (what format the data is in). DWORD (REG_DWORD) is a 32-bit integer — used for on/off switches (0 or 1), port numbers, timeout values. Most security settings use DWORD. STRING (REG_SZ) is a plain text string — used for file paths, server names, URLs. BINARY (REG_BINARY) is raw binary data — used for certificates, cryptographic keys, encoded configuration. MULTI_STRING (REG_MULTI_SZ) is a list of strings — used for settings that accept multiple values (like a list of allowed cipher suites for TLS). In our banking project, we used win_regedit extensively for CIS benchmark compliance — disabling SSL 2.0/3.0, TLS 1.0/1.1, enabling TLS 1.2, requiring NLA for RDP, restricting NTLM. All DWORD type. The key insight is that these are idempotent — running the playbook on an already-hardened server results in "ok" (no changes) — perfect for drift detection automation.

🔴 Advanced / Scenario Questions

Q7. A bank has a mix of Linux and Windows servers. How do you write one playbook/workflow that handles both?
There are two approaches. Approach 1 — Separate Plays in One Playbook. You write two plays in the same YAML file: Play 1 with hosts: linux_servers uses Linux modules (dnf, systemd, file). Play 2 with hosts: windows_servers uses Windows modules (win_updates, win_service). Both plays run in sequence when you run the playbook. Approach 2 — One Play with Conditionals using ansible_os_family. You have one play targeting all servers, but each task has a when condition: when: ansible_os_family == "RedHat" for Linux tasks and when: ansible_os_family == "Windows" for Windows tasks. This is cleaner for drift remediation scenarios where you want unified reporting. In our bank's production workflow, we use separate AAP Job Templates — one for Linux and one for Windows — and chain them together in a Workflow Template. This is the cleanest approach because it allows different Execution Environments (Linux EE for Linux, Windows EE with pywinrm for Windows), different credentials (SSH key for Linux, Kerberos for Windows), and different serial percentages (10% for Linux, 15% for Windows because Windows reboots take longer). The Workflow Template ties them together so the CISO sees a single unified compliance run.
Q8. How do you handle Windows modules that don't exist for your use case?
When no specific module exists for a Windows task, we use ansible.windows.win_powershell to run arbitrary PowerShell code. This module runs PowerShell on the remote Windows server and returns the output as structured data. The key trick is to return a PowerShell hashtable at the end of your script — Ansible automatically converts this to JSON and makes it available via the register variable. For example, when we needed to read the IIS Application Pool state (no specific module for checking state in older collection versions), we wrote: $pool = Get-WebConfiguration system.applicationHost/applicationPools/add[@name='IBankAppPool']; return @{ state = $pool.state }. The changed_when: false attribute is essential on any win_powershell task that only reads information — otherwise Ansible marks it as "changed" every time, which pollutes your reporting. We also use ansible.windows.win_command for simple command execution that returns text output, and ansible.windows.win_shell when we need shell features like pipes (|), output redirection (>), or if-else logic in cmd.exe. The difference: win_command runs an executable directly (no shell), win_shell runs through cmd.exe, win_powershell runs through PowerShell. Always prefer win_powershell for structured output.
Q9. Explain how you would automate onboarding of a new Windows server from scratch using Ansible AAP.
We have a "Windows Server Onboarding" workflow in AAP. Here is the complete flow: The Windows team provisions the VM in VMware or AWS and adds its IP to the inventory (or our Dynamic Inventory plugin picks it up automatically). A webhook triggers the AAP Workflow Template "Win-Server-Onboarding." Step 1 — Bootstrap: We first connect using Basic auth with a temporary local admin account. A task runs the ConfigureRemotingForAnsible.ps1 script to enable WinRM HTTPS, then joins the server to the GLOBALTRUST.IN Active Directory domain. After domain join, we switch to Kerberos auth for all subsequent connections. Step 2 — Baseline Configuration: We run the windows_baseline role — creates the ansible-svc service account, disables Guest and DefaultAccount, applies all CIS registry hardening settings, configures Windows Firewall rules, sets Event Log sizes, disables insecure services (Spooler, RemoteRegistry, SNMP), enables required services. Step 3 — Role-Specific Configuration: Based on the server_role variable (iis, sqlserver, fileserver), we apply additional roles. Step 4 — CMDB Update: We call the ServiceNow API to update the new server's Configuration Item with OS version, IP, patch level, owner team, and compliance status. Step 5 — Splunk Agent: We install and configure the Splunk Universal Forwarder using win_package module to start shipping Event Logs to the SOC. What used to take 3 days of manual work (RDP sessions, manual configuration, documentation) now takes 45 minutes — all automated, all documented, fully auditable.
