1 Project Overview

📌 The Big Picture — Monitoring + Automation = Self-Healing Infrastructure
Most organisations treat monitoring and automation as two separate disciplines. This project connects them. The goal is simple: when Prometheus detects a high-memory server, don't send a Slack alert that wakes up an engineer — send the alert AND automatically trigger an Ansible playbook that restarts the service causing the leak. When Splunk sees an nginx error spike, automatically run the nginx restart playbook. When a disk fills, auto-clean. When Grafana's dashboard shows a deployment anomaly, auto-rollback. This is self-healing infrastructure — the monitoring system drives the automation system, and humans only intervene for truly complex problems that need judgment.

🔴 Prometheus

Metrics collection and alerting for all Linux/Windows servers and applications. Node Exporter on every server.

🟠 Grafana

Dashboards for infrastructure health. Deployment status panels. Real-time Ansible job metrics.

🟢 Splunk

Log analysis, SIEM, and compliance reporting. Splunk Universal Forwarder on every server.

🔵 ELK Stack

Application log aggregation for Java Spring Boot and Python microservices. Filebeat ships logs.

2 Business Problem

🚨 The 2 AM Pattern — What Prompted This Project
Before this project, GlobalTrust Bank's on-call rotation received an average of 23 pager alerts per week outside business hours. 71% of those alerts were for problems that had known, repeatable fixes — disk full (clean logs), service crashed (restart), memory leak (restart service, send to dev team). An engineer was being woken up at 3 AM to type three commands on a server. The engineer spends 45 minutes resolving what a script could fix in 90 seconds. Times 16 such alerts per month, times 12 DevOps engineers in rotation — that is 192 hours of lost engineer sleep per year, significant burnout, and three resignation letters in 2023 citing on-call exhaustion.
✅ After Monitoring + Ansible Integration
  • Prometheus alert fires → Ansible remediates in under 2 minutes
  • On-call alert volume reduced from 23/week to 4/week (83% reduction)
  • Splunk UF deployed to 450 servers in 20 minutes via Ansible
  • Grafana shows Ansible job status alongside server health
  • All 3 resignations rescinded after on-call load reduced
  • MTTR (Mean Time To Repair) dropped from 45 min to 4 min
  • RBI: Full audit log of every remediation in Splunk
  • Slack/Teams alerts now fire AFTER auto-fix, not instead of it

5 Prometheus Server — Deploy with Ansible

🔴 Prometheus in GlobalTrust Bank
GlobalTrust Bank runs a centralised Prometheus server (3 replicas with Thanos for long-term storage) that scrapes metrics from all 450+ Linux and Windows servers, 35 application exporters, and AAP itself. The entire Prometheus deployment — server, Alertmanager, all configuration files, service setup, and firewall rules — is managed by Ansible. If someone accidentally changes prometheus.yml directly on the server, the next Ansible run restores it. Infrastructure as code enforced.
roles/prometheus/tasks/main.ymlYAML
---
# GlobalTrust Bank — Prometheus Server Installation Role
# Idempotent: safe to run again if Prometheus already installed

- name: Create prometheus system group
  ansible.builtin.group:
    name: prometheus
    system: true
    state: present

- name: Create prometheus system user
  ansible.builtin.user:
    name: prometheus
    group: prometheus
    system: true
    shell: /bin/false              # No login shell — service account only
    create_home: false
    state: present

- name: Create Prometheus directories
  ansible.builtin.file:
    path: "{{ item }}"
    state: directory
    owner: prometheus
    group: prometheus
    mode: '0755'
  loop:
    - /etc/prometheus
    - /etc/prometheus/rules                 # Alert rules directory
    - /var/lib/prometheus                     # Data directory (TSDB)
    - /var/log/prometheus

- name: Download Prometheus binary
  ansible.builtin.unarchive:
    src: "https://github.com/prometheus/prometheus/releases/download/v{{ prometheus_version }}/prometheus-{{ prometheus_version }}.linux-amd64.tar.gz"
    dest: /tmp/
    remote_src: true                      # Download on the remote server (not locally)

- name: Copy prometheus and promtool binaries to /usr/local/bin
  ansible.builtin.copy:
    src: "/tmp/prometheus-{{ prometheus_version }}.linux-amd64/{{ item }}"
    dest: "/usr/local/bin/{{ item }}"
    owner: root
    group: root
    mode: '0755'
    remote_src: true
  loop:
    - prometheus
    - promtool                               # Tool for validating config and rules
  notify: Restart prometheus

- name: Deploy prometheus.yml from template
  ansible.builtin.template:
    src: prometheus.yml.j2
    dest: /etc/prometheus/prometheus.yml
    owner: prometheus
    group: prometheus
    mode: '0644'
    validate: '/usr/local/bin/promtool check config %s'  # Validate before applying
  notify: Reload prometheus config

- name: Deploy Prometheus alert rules
  ansible.builtin.template:
    src: "{{ item }}.j2"
    dest: "/etc/prometheus/rules/{{ item }}"
    owner: prometheus
    group: prometheus
    mode: '0644'
    validate: '/usr/local/bin/promtool check rules %s'    # Validate rules before applying
  loop:
    - disk_alerts.yml
    - memory_alerts.yml
    - cpu_alerts.yml
    - service_alerts.yml
    - application_alerts.yml
  notify: Reload prometheus config

- name: Deploy Prometheus systemd service
  ansible.builtin.template:
    src: prometheus.service.j2
    dest: /etc/systemd/system/prometheus.service
    mode: '0644'
  notify: Reload systemd

- name: Ensure Prometheus is enabled and running
  ansible.builtin.systemd:
    name: prometheus
    state: started
    enabled: true
    daemon_reload: true

- name: Open Prometheus port in firewall
  ansible.posix.firewalld:
    port: "{{ item }}/tcp"
    permanent: true
    state: enabled
    immediate: true
  loop:
    - "9090"            # Prometheus UI and API
    - "9093"            # Alertmanager
templates/prometheus.service.j2 — Systemd unit fileINI
[Unit]
Description=Prometheus Metrics Server
Documentation=https://prometheus.io/docs
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=prometheus
Group=prometheus
ExecStart=/usr/local/bin/prometheus \
    --config.file=/etc/prometheus/prometheus.yml \
    --storage.tsdb.path=/var/lib/prometheus \
    --storage.tsdb.retention.time={{ prometheus_retention_days }}d \
    --web.listen-address=0.0.0.0:9090 \
    --web.enable-lifecycle \            # Enables /-/reload API for config reload without restart
    --log.level=info

ExecReload=/bin/kill -HUP $MAINPID    # SIGHUP = reload config gracefully
Restart=always
RestartSec=5s

[Install]
WantedBy=multi-user.target
ConceptExplanation
validate: promtool check config %sBefore Ansible applies the prometheus.yml file, it runs promtool check config on it. If the config has syntax errors or invalid references, the file is NOT deployed and the play fails safely. The %s is replaced by a temp file path. This prevents deploying a broken config that would crash Prometheus. Same pattern for alert rules with promtool check rules.
notify: Reload prometheus configInstead of restarting Prometheus (which causes a brief metrics gap), we use a reload — Prometheus reloads config live with no downtime. The handler sends SIGHUP to the process: systemctl kill -s HUP prometheus. Only triggered when config actually changed (Ansible's idempotency at work). Binary changes still require a full restart, hence the separate "Restart prometheus" handler.
--web.enable-lifecycleThis flag enables the HTTP reload API: POST http://localhost:9090/-/reload triggers a config reload without SIGHUP. Useful for automation and health checks. Our Ansible handler can also use ansible.builtin.uri to POST to this endpoint instead of using systemctl.
--storage.tsdb.retention.time=15dPrometheus stores metrics for 15 days in its local time-series database (TSDB). After 15 days, old data is deleted. For longer retention (6 months for RBI compliance), we feed Prometheus remote_write into a Thanos cluster or VictoriaMetrics. The value comes from the {{ prometheus_retention_days }} Ansible variable — one change in group_vars updates all Prometheus servers.

6 Node Exporter — Deploy to All 450 Servers

📡 What is Node Exporter?
Node Exporter is a lightweight Prometheus agent that runs on every Linux server and exposes system metrics — CPU usage, memory, disk, network, filesystem — as an HTTP endpoint on port 9100. Prometheus scrapes this endpoint every 15 seconds. Deploying Node Exporter to 450 servers manually would take hours. With Ansible, it takes 8 minutes across all servers simultaneously. And when a new server is provisioned (Project 04), the Node Exporter role runs automatically as part of the provisioning playbook.
roles/node_exporter/tasks/main.yml — Deploy to ALL Linux serversYAML
---
- name: Download Node Exporter
  ansible.builtin.unarchive:
    src: "https://github.com/prometheus/node_exporter/releases/download/v{{ node_exporter_version }}/node_exporter-{{ node_exporter_version }}.linux-amd64.tar.gz"
    dest: /tmp/
    remote_src: true
    creates: "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"

- name: Install node_exporter binary
  ansible.builtin.copy:
    src: "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"
    dest: /usr/local/bin/node_exporter
    owner: root
    group: root
    mode: '0755'
    remote_src: true
  notify: Restart node_exporter

- name: Create node_exporter systemd service
  ansible.builtin.copy:
    content: |
      [Unit]
      Description=Node Exporter — Prometheus system metrics
      After=network-online.target

      [Service]
      Type=simple
      User=nobody
      ExecStart=/usr/local/bin/node_exporter \
          --collector.systemd \
          --collector.processes \
          --web.listen-address=:9100

      Restart=always
      RestartSec=5s

      [Install]
      WantedBy=multi-user.target
    dest: /etc/systemd/system/node_exporter.service
    mode: '0644'
  notify:
    - Reload systemd
    - Restart node_exporter

- name: Enable and start node_exporter
  ansible.builtin.systemd:
    name: node_exporter
    state: started
    enabled: true
    daemon_reload: true

- name: Allow node_exporter port in firewall (only from Prometheus server)
  ansible.posix.firewalld:
    rich_rule: "rule family='ipv4' source address='{{ prometheus_server_ip }}' port port='9100' protocol='tcp' accept"
    permanent: true
    state: enabled
    immediate: true
  # Only allow Prometheus server to scrape — not open to the world

- name: Verify node_exporter is responding
  ansible.builtin.uri:
    url: http://localhost:9100/metrics
    status_code: 200
  register: ne_check
  retries: 5
  delay: 5

🚨 Alert Rules — Banking-Specific Thresholds

templates/disk_alerts.yml.j2 — Production disk alert rulesYAML
---
groups:
  - name: disk_alerts
    rules:

      - alert: DiskSpaceWarning
        expr: (1 - node_filesystem_avail_bytes{mountpoint!~"/boot.*|/sys.*|/proc.*"} / node_filesystem_size_bytes) * 100 > 80
        for: 5m                          # Alert only if condition persists for 5 minutes
        labels:
          severity: warning
          team: linux-ops
          auto_remediate: "false"       # At warning level, just notify — don't auto-fix
        annotations:
          summary: "Disk usage WARNING: {{ $labels.instance }} mount {{ $labels.mountpoint }} at {{ $value | printf \"%.1f\" }}%"
          description: "Disk {{ $labels.mountpoint }} on {{ $labels.instance }} is {{ $value | printf \"%.1f\" }}% full. Consider investigation before it becomes critical."
          runbook_url: "https://wiki.globaltrust.in/runbooks/disk-full"

      - alert: DiskSpaceCritical
        expr: (1 - node_filesystem_avail_bytes{mountpoint!~"/boot.*|/sys.*|/proc.*"} / node_filesystem_size_bytes) * 100 > 90
        for: 2m                          # Faster alert threshold for critical level
        labels:
          severity: critical
          team: linux-ops
          auto_remediate: "true"        # CRITICAL: trigger auto-remediation via AAP
          aap_job_template: "disk_emergency_cleanup"  # Which AAP job to trigger
        annotations:
          summary: "Disk CRITICAL: {{ $labels.instance }} at {{ $value | printf \"%.1f\" }}%"
          description: "CRITICAL disk space on {{ $labels.instance }}:{{ $labels.mountpoint }}. AAP auto-remediation will trigger within 60 seconds."
          runbook_url: "https://wiki.globaltrust.in/runbooks/disk-full"

      - alert: MemoryUsageCritical
        expr: (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100 > 92
        for: 5m
        labels:
          severity: critical
          auto_remediate: "true"
          aap_job_template: "memory_pressure_remediate"
        annotations:
          summary: "Memory CRITICAL: {{ $labels.instance }} at {{ $value | printf \"%.1f\" }}%"

      - alert: ServiceDown
        expr: up{job!="prometheus"} == 0   # Any target that is not responding
        for: 1m
        labels:
          severity: critical
          auto_remediate: "true"
          aap_job_template: "service_restart"
        annotations:
          summary: "Service DOWN: {{ $labels.job }} on {{ $labels.instance }}"

8 Alertmanager — Route Alerts to AAP + Notifications

🔴 Alertmanager's Job in This Architecture
Prometheus evaluates alert rules and sends all firing alerts to Alertmanager. Alertmanager's job is to route alerts intelligently — based on severity, time-of-day, team, and whether auto-remediation is available. Critical alerts with auto_remediate=true go to AAP's webhook first, then to Slack as information. Warning alerts go to Slack only. P1 alerts (banking system down) go to PagerDuty for human escalation. Maintenance window alerts are silenced. This intelligence lives in alertmanager.yml — deployed and managed by Ansible.
templates/alertmanager.yml.j2 — Complete Alertmanager routing configYAML
# GlobalTrust Bank — Alertmanager Configuration
# Managed by Ansible AAP — DO NOT EDIT DIRECTLY

global:
  resolve_timeout: 5m               # How long before an alert is marked as resolved
  slack_api_url: "{{ vault_slack_webhook_url }}"
  pagerduty_url: 'https://events.pagerduty.com/v2/enqueue'

templates:
  - '/etc/alertmanager/templates/*.tmpl'

route:
  group_by: [alertname, instance, severity]
  group_wait: 30s                   # Wait 30s before sending first alert in a group
  group_interval: 5m               # Wait 5m before sending additional alerts for same group
  repeat_interval: 4h              # Resend alert every 4h if still firing
  receiver: slack-infra-default    # Default receiver

  routes:
    # Route 1: Critical alerts with auto_remediate=true → AAP FIRST
    - match:
        severity: critical
        auto_remediate: "true"
      receiver: aap-auto-remediate
      continue: true                  # CRITICAL: continue=true means ALSO send to default route

    # Route 2: P1 — Core Banking Down → PagerDuty (for human escalation)
    - match:
        severity: critical
        team: core-banking
      receiver: pagerduty-critical
      continue: true

    # Route 3: Warning → Slack only, no PagerDuty, no AAP auto-fix
    - match:
        severity: warning
      receiver: slack-infra-warning
      repeat_interval: 2h

receivers:

  # ===== AAP AUTO-REMEDIATION RECEIVER =====
  - name: aap-auto-remediate
    webhook_configs:
      - url: "https://aap-ctrl.globaltrust.in/api/v2/job_templates/{{ aap_remediation_webhook_jt_id }}/launch/"
        http_config:
          bearer_token: "{{ vault_aap_alertmanager_token }}"
        send_resolved: true             # Also send webhook when alert resolves
        max_alerts: 20                  # Max alerts per webhook call

  # ===== SLACK — CRITICAL =====
  - name: slack-infra-default
    slack_configs:
      - channel: '#infrastructure-alerts'
        send_resolved: true
        icon_emoji: ':prometheus:'
        title: '{{ template "slack.title" . }}'
        text: '{{ template "slack.text" . }}'
        color: '{{ if eq .Status "firing" }}danger{{ else }}good{{ end }}'
        actions:
          - type: button
            text: View in Grafana
            url: '{{ (index .Alerts 0).Annotations.grafana_url }}'
          - type: button
            text: View AAP Job
            url: 'https://aap-ctrl.globaltrust.in'

  # ===== SLACK — WARNING ONLY =====
  - name: slack-infra-warning
    slack_configs:
      - channel: '#infrastructure-warnings'
        color: 'warning'
        send_resolved: true

  # ===== PAGERDUTY — P1 CRITICAL =====
  - name: pagerduty-critical
    pagerduty_configs:
      - routing_key: "{{ vault_pagerduty_integration_key }}"
        severity: critical
        description: '{{ .CommonAnnotations.summary }}'
        details:
          instance: '{{ .CommonLabels.instance }}'
          runbook: '{{ .CommonAnnotations.runbook_url }}'
ConceptExplanation
continue: trueBy default, Alertmanager stops at the first matching route and only sends to that receiver. continue: true tells it to keep checking routes after the match. In our config, a DiskSpaceCritical alert with auto_remediate=true matches Route 1 (sends to AAP) and because continue=true, also continues to match Route 3 (sends to Slack). So the alert triggers AAP AND notifies Slack. Without continue: true, only AAP would receive it.
aap-auto-remediate receiverThis is the most important receiver. It sends a POST to AAP's job template launch API (same as Project 05). When DiskSpaceCritical fires, Alertmanager calls the AAP API, which launches the disk_emergency_cleanup job template. The affected server hostname is in the Alertmanager payload — the playbook reads it from the webhook data using the awx_webhook_payload variable. No human involved.
send_resolved: trueWhen Alertmanager sends to AAP's webhook with send_resolved: true, AAP also receives a RESOLVED notification when the condition clears. This lets the playbook send a "RESOLVED" Slack message: "✅ Disk on prod-db-012 automatically cleaned. Space: 96% → 62%." The on-call engineer sees a resolved alert in the morning instead of being woken up.
group_wait / group_intervalgroup_wait=30s means Alertmanager waits 30 seconds before sending the first notification. This prevents alert storms where 10 servers hit 90% disk simultaneously — Alertmanager groups them into one notification per group (alertname+severity). group_interval=5m means after the first notification, wait 5 minutes before sending updates. repeat_interval=4h means resend the alert every 4 hours if still firing.

20 Custom Ansible Callback Plugin

💡 What is a Callback Plugin?
Ansible callback plugins are Python files that hook into Ansible's event system. Every time an Ansible event occurs — task started, task succeeded, task failed, playbook finished — the callback plugin's corresponding method is called automatically. You can write custom callback plugins to send events to any external system without adding notification tasks to every playbook. In GlobalTrust Bank, we have a custom callback plugin that sends every task result to a deployment audit system and updates a real-time Grafana dashboard via the Grafana API.
callback_plugins/globaltrust_audit.py — Custom callback pluginPYTHON
# callback_plugins/globaltrust_audit.py
# GlobalTrust Bank — Custom Ansible Callback Plugin
# Sends deployment events to internal audit system + Slack on failures

from ansible.plugins.callback import CallbackBase
import requests
import json
from datetime import datetime

DOCUMENTATION = '''
callback: globaltrust_audit
short_description: Send Ansible events to GlobalTrust audit system
type: notification
description:
  - Logs all task results to the bank's compliance audit system
  - Sends Slack notifications on task failures
'''

class CallbackModule(CallbackBase):

    CALLBACK_VERSION = 2.0
    CALLBACK_TYPE = 'notification'      # Type: notification (doesn't replace stdout)
    CALLBACK_NAME = 'globaltrust_audit'
    CALLBACK_NEEDS_ENABLED = True       # Must be enabled in ansible.cfg to activate

    def __init__(self):
        super().__init__()
        self.audit_api_url = "https://audit.globaltrust.in/api/ansible-events"
        self.slack_webhook = None

    def set_options(self, task_keys=None, var_options=None, direct=None):
        super().set_options(task_keys=task_keys, var_options=var_options, direct=direct)
        self.slack_webhook = self.get_option('slack_webhook_url')

    def v2_runner_on_ok(self, result):
        # Called when a task succeeds
        self._send_audit_event('task_success', result)

    def v2_runner_on_failed(self, result, ignore_errors=False):
        # Called when a task fails
        self._send_audit_event('task_failed', result)

        if not ignore_errors:             # Only alert if error is not deliberately ignored
            self._send_slack_alert(
                host=result._host.get_name(),
                task=result.task_name,
                error=result._result.get('msg', 'Unknown error')
            )

    def v2_playbook_on_stats(self, stats):
        # Called at the very end of a playbook run — provides overall stats
        summary = {}
        for host in stats.processed.keys():
            s = stats.summarize(host)
            summary[host] = s

        self._send_audit_event('playbook_complete', {
            'summary': summary,
            'timestamp': datetime.utcnow().isoformat()
        })

    def _send_audit_event(self, event_type, data):
        try:
            requests.post(
                self.audit_api_url,
                json={'event_type': event_type, 'data': str(data)},
                timeout=5                 # Never block Ansible for more than 5 seconds
            )
        except Exception:
            pass                          # Never crash Ansible due to audit API failure

    def _send_slack_alert(self, host, task, error):
        if not self.slack_webhook:
            return
        try:
            requests.post(
                self.slack_webhook,
                json={'text': f"❌ Ansible TASK FAILED\n*Host:* {host}\n*Task:* {task}\n*Error:* {error}"},
                timeout=5
            )
        except Exception:
            pass

Q1. How do you deploy Prometheus and Node Exporter using Ansible? What is the validate parameter used for?
We have Ansible roles for both Prometheus server and Node Exporter. The Node Exporter role deploys to all 450 Linux servers simultaneously using a playbook with no serial limit — they all install in parallel, taking about 8 minutes total. The Prometheus server role installs the binary from GitHub releases, creates a dedicated system user, sets up the systemd service, and deploys the configuration from a Jinja2 template. The key feature is the validate parameter on the template module: validate: '/usr/local/bin/promtool check config %s'. Before Ansible writes the rendered prometheus.yml to disk, it runs this validation command on a temporary copy. If promtool detects any configuration errors — wrong YAML syntax, undefined scrape targets, invalid relabel rules — the validation fails and the file is NOT deployed. Prometheus keeps running with the old valid configuration. This prevents configuration mistakes from taking down the monitoring system. Same approach for alert rules: validate: '/usr/local/bin/promtool check rules %s'. The %s is replaced by the temp file path automatically by Ansible.
Q2. How does Prometheus Alertmanager connect to Ansible AAP for auto-remediation?
When a Prometheus alert fires — for example DiskSpaceCritical when a partition exceeds 90% for 2 minutes — Prometheus sends this to Alertmanager. Alertmanager has a routing configuration that checks the alert's labels. If the alert has the label auto_remediate: "true" (which we set in the alert rule), Alertmanager routes it to a webhook receiver. That webhook receiver is configured with the AAP job template launch URL: POST to https://aap-ctrl.../api/v2/job_templates/60/launch/ with a Bearer token for authentication. The Alertmanager webhook payload contains all the alert details — instance name, alert name, severity, mountpoint. AAP receives this POST, launches the job template with the webhook payload available as the Ansible variable awx_webhook_payload. The playbook reads the affected server hostname from awx_webhook_payload.alerts[0].labels.instance, adds it to a dynamic inventory group using add_host, then runs the remediation tasks on that specific server. After cleanup, the playbook sends a Slack notification with before/after disk usage. The entire process from alert firing to disk cleaned and Slack notification: under 3 minutes. We also set send_resolved: true in Alertmanager so when the alert clears, another webhook fires to AAP which sends a RESOLVED message to Slack — the on-call engineer sees a complete story in Slack without being woken up.
Q3. How do you deploy Splunk Universal Forwarder to hundreds of servers using Ansible?
We have a Splunk UF role that runs against all managed servers simultaneously. The role does five things. First, it checks if Splunk is already installed using the stat module to check for the binary — this makes it idempotent and prevents reinstalling. Second, it downloads the Splunk RPM from our internal artifact server (not the internet) and verifies the SHA256 checksum — important for supply chain security in banking. Third, it deploys the outputs.conf from a template specifying the Heavy Forwarder addresses and SSL settings — all servers send logs to the same two HF nodes for failover. Fourth, it deploys a role-specific inputs.conf — web servers get nginx log collection, database servers get MySQL log collection, all servers get system and audit logs. The template filename uses the server_role variable: inputs.conf.{{ server_role }}.j2. Fifth, it accepts the Splunk license and enables the forwarder as a systemd service. The whole deployment to 450 servers runs in about 20 minutes. The power is in the role-specific inputs.conf — one role, multiple server types, all configured correctly automatically. When we add a new log file to monitor, we update the Jinja2 template and re-run the role — all 450 servers pick up the change in one Ansible run.
Q4. What is an Ansible Callback Plugin and why did you write a custom one?
An Ansible Callback Plugin is a Python class that inherits from CallbackBase and hooks into Ansible's internal event system. Every time something happens during an Ansible run — a task starts, a task succeeds, a task fails, the playbook ends — Ansible calls the corresponding method in all active callback plugins. This happens automatically without any changes to playbooks. We wrote the globaltrust_audit callback plugin for two reasons. First, we needed to send every task result to the bank's compliance audit system — this is required by RBI's IT audit framework. Adding a notification task to every playbook would be unmaintainable with 200+ playbooks. With a callback plugin, the audit event happens automatically for every task in every playbook. Second, we wanted immediate Slack alerts on any task failure in any playbook — the v2_runner_on_failed method sends a Slack message with the host, task name, and error message whenever any task fails with ignore_errors: false. The plugin is enabled in ansible.cfg with callbacks_enabled = globaltrust_audit. Key design principle: we always use try/except around the external API calls and never let the callback plugin crash Ansible. If the audit API is down, Ansible must still run — the plugin silently swallows the exception. Automation availability is more important than audit logging.
Q5. How do you send notifications to Slack and Teams from Ansible? What is the difference between the two approaches?
There are two approaches: using the dedicated Ansible module and using the uri module with an HTTP webhook. For Slack, the community.general.slack module provides a clean interface — you specify token, channel, message, color, and attachments with named parameters. It handles the Slack API authentication and message formatting automatically. For Teams, there is no Ansible module so we use the ansible.builtin.uri module to POST a JSON payload to the Teams Incoming Webhook URL — the body follows Microsoft's MessageCard format with themeColor, summary, sections, and facts fields. The advantages of using dedicated modules (like community.general.slack) over uri are: cleaner YAML syntax, better error messages, automatic retry, and module-level idempotency checking. The advantage of uri is universality — it works with any HTTP endpoint without needing additional collections installed in the Execution Environment. In practice, we use the slack module for internal team notifications where we want rich formatting, and uri for Teams and any custom webhook endpoint (PagerDuty, Grafana, ServiceNow). Both approaches use delegate_to: localhost because the HTTP call goes from the Ansible execution node to the notification endpoint — not from the managed server.
