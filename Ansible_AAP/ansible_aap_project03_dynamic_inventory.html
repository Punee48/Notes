⚡ Dynamic Inventory
Automatically Discover Servers from AWS · Azure · VMware vCenter

GlobalTrust Bank runs a hybrid cloud estate — 200+ VMs in VMware on-premises, 80+ EC2 instances in AWS, and 40+ VMs in Azure. With servers created and destroyed daily, a static inventory file becomes stale within hours. Dynamic Inventory solves this — Ansible automatically discovers and groups all servers in real time from the cloud APIs, every single time a playbook runs.

🏦 Domain: BFSI Hybrid Cloud ☁️ AWS + Azure + VMware ⚙️ Inventory Plugins 📅 Level: Intermediate → Advanced
☁️ AWS EC2 (amazon.aws) ☁️ Azure RM (azure.azcollection) 🖥️ VMware vCenter (community.vmware)

1 Project Overview

📌 The Core Problem Dynamic Inventory Solves
In Projects 01 and 02, we used a static hosts file where every server was manually listed. This works when you have a fixed set of servers that never change. But in a modern bank that uses cloud infrastructure, servers are created on demand, auto-scaled, and terminated. If you add a new EC2 instance at 9 AM and your patching runs at 10 AM, the static inventory has no idea the new server exists. Dynamic Inventory connects directly to AWS/Azure/VMware APIs and discovers all servers at the moment the playbook runs — always 100% accurate.

☁️ AWS EC2

Ansible queries the AWS EC2 API using the amazon.aws.aws_ec2 inventory plugin. Returns all running instances with their tags, regions, VPCs, and metadata.

☁️ Microsoft Azure

Ansible queries Azure Resource Manager using the azure.azcollection.azure_rm plugin. Returns all VMs with tags, resource groups, and OS info.

🖥️ VMware vCenter

Ansible queries vCenter's API using the community.vmware.vmware_vm_inventory plugin. Returns all VMs across datacenters with custom attributes and folders.

2 Business Requirement

🏦 GlobalTrust Bank's Hybrid Cloud Reality

GlobalTrust Bank has evolved from a pure on-premises data center to a hybrid cloud model over the last 3 years. Today the infrastructure looks like this: The Core Banking System (Finacle) and all regulatory databases remain on VMware vCenter in Mumbai and Hyderabad data centers (regulators require on-premise for core data). The Digital Banking front-end (mobile app APIs, internet banking) runs on AWS EC2 in ap-south-1 (Mumbai region). The analytics and reporting platform (Power BI, data pipelines) runs on Azure in Central India. This creates a complex multi-cloud + on-premise inventory that changes daily — new EC2 instances launched for seasonal load, VMs cloned in VMware for testing, Azure VMs created for reporting runs.

3 Project Story

📖 The Story — When the Inventory Lied and the Bank Paid

It is a Tuesday morning. Priya's team runs the monthly AWS patching playbook — the same one that worked perfectly last month. But this time, 23 EC2 instances return "UNREACHABLE" errors. Priya is confused. She logs into the AWS Console and discovers something alarming: the DevOps team had re-provisioned those 23 instances last week with new IPs (during an architecture migration), but nobody updated the Ansible static inventory file. The next patching run automatically discovered all 320 servers across all platforms — including 14 new ones that had been created that same morning. Zero misses. Zero stale IPs. The CISO was satisfied. The Security team closed the finding. This is the project you are building now.

⚠️ The File Naming Convention is Critical
Ansible recognises a YAML file as a Dynamic Inventory Plugin configuration based on its filename. The file must end with a specific suffix matching the plugin name. aws_ec2.yml or *.aws_ec2.yml triggers the amazon.aws.aws_ec2 plugin. azure_rm.yml triggers the Azure plugin. vmware.yml combined with the plugin: community.vmware.vmware_vm_inventory line triggers VMware. If you name the file wrong, Ansible treats it as a static inventory file and nothing works — this is the most common beginner mistake.

6 How Inventory Plugins Work — The Internals

Understanding this concept is critical for interviews. An inventory plugin is a small Python program that knows how to talk to a specific platform (AWS, Azure, VMware) and translate the platform's API response into Ansible's internal inventory format (hosts + groups + variables).

💡 Pro Tip — Mixing Static and Dynamic
You can have BOTH a static hosts file AND dynamic plugin files in the same inventory directory. Ansible reads ALL of them and merges the results. In GlobalTrust Bank, we use dynamic inventory for all cloud/VMware servers, but keep a few static entries for network devices (Cisco switches, F5 load balancers) that don't have cloud APIs. This is the real-world enterprise pattern — always a hybrid approach.

7 AWS Setup — IAM Role and Credentials

Before the aws_ec2 plugin can query AWS, it needs permission to call the EC2 API. In AWS, permissions are managed via IAM (Identity and Access Management). We create a dedicated IAM policy with read-only EC2 permissions and attach it to either an IAM User (with access keys) or an IAM Role (used when the AAP exec node is an EC2 instance itself).

☁️ IAM Permission Design — Principle of Least Privilege
The Ansible service account in AWS should have the MINIMUM permissions needed. For Dynamic Inventory (read-only discovery), we need only ec2:DescribeInstances, ec2:DescribeTags, and a few other Describe actions. We do NOT give ec2:* (all EC2 actions) — that would allow Ansible to delete EC2 instances, which is dangerous. This approach is called Principle of Least Privilege and is required by RBI's security framework.
IAM Policy for Ansible Dynamic Inventory (JSON)JSON
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AnsibleInventoryReadOnly",
      "Effect": "Allow",
      "Action": [
        "ec2:DescribeInstances",         // List all EC2 instances and their details
        "ec2:DescribeTags",              // Read EC2 tags (used for grouping)
        "ec2:DescribeRegions",           // List available regions
        "ec2:DescribeAvailabilityZones", // List AZs in a region
        "ec2:DescribeVpcs",              // VPC information for grouping
        "ec2:DescribeSubnets",           // Subnet information
        "ec2:DescribeSecurityGroups"     // Security group names for filters
      ],
      "Resource": "*"
    }
  ]
}

8 AWS EC2 Inventory Plugin — Complete Configuration

📄 inventory/aws_ec2.yml — Complete Production Config
---
# ============================================================
# GlobalTrust Bank — AWS EC2 Dynamic Inventory Plugin
# Plugin: amazon.aws.aws_ec2
# Queries: AWS ap-south-1 and ap-southeast-1
# ============================================================

plugin: amazon.aws.aws_ec2          # REQUIRED: tells Ansible which plugin to use

regions:                              # Which AWS regions to query
  - ap-south-1                       # Mumbai (primary)
  - ap-southeast-1                   # Singapore (DR)

aws_profile: globaltrust-ansible    # AWS CLI profile name (~/.aws/credentials)
# OR: set AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY environment variables
# In AAP: attach the AWS credential — env vars are auto-injected

# ===== FILTERS: Which instances to include =====
filters:
  instance-state-name: running      # ONLY running instances (not stopped/terminated)
  tag:ManagedBy: ansible            # Only instances tagged ManagedBy=ansible
# Without filters: the plugin returns ALL instances — even terminated ones
# That would cause Ansible to try connecting to non-existent servers

# ===== HOSTNAMES: How to identify each host =====
hostnames:
  - tag:Name                          # Use the 'Name' tag as the hostname (human-readable)
  - private_dns_name                 # Fallback: use AWS internal DNS if no Name tag
  - private_ip_address               # Final fallback: use private IP
# Order matters — first found value wins
# In production VPC: always use private IP/DNS (no public IPs on prod instances)

# ===== KEYED GROUPS: Automatic grouping from tags =====
keyed_groups:
  - key: tags.Environment             # Group by Environment tag
    prefix: aws_env                   # Group name: aws_env_production, aws_env_dev, etc.
    separator: "_"

  - key: tags.Role                    # Group by Role tag
    prefix: aws_role                  # Group: aws_role_web, aws_role_app, aws_role_db
    separator: "_"

  - key: tags.Application             # Group by Application tag
    prefix: aws_app
    separator: "_"

  - key: tags.OS                      # Group by OS type
    prefix: aws_os
    separator: "_"

  - key: tags.PatchGroup              # Group by patch group for staggered patching
    prefix: aws_patch
    separator: "_"

  - key: placement.availability_zone  # Group by AZ: aws_az_ap-south-1a, etc.
    prefix: aws_az
    separator: "_"

  - key: instance_type               # Group by instance type: aws_type_t3_medium
    prefix: aws_type
    separator: "_"

# ===== COMPOSE: Create custom Ansible variables from EC2 data =====
compose:
  ansible_host: private_ip_address  # Use private IP for SSH (production VPC)
  ansible_user: "'ec2-user' if tags.OS is defined and 'rhel' in tags.OS else 'ubuntu'"
  ec2_instance_id: instance_id      # Make instance_id available as a variable
  ec2_region: placement.region
  ec2_environment: tags.Environment
  ec2_role: tags.Role
  patch_group: tags.PatchGroup       # Available as {{ patch_group }} in playbooks

# ===== CACHE: Speed up repeated inventory calls =====
cache: true                          # Cache the API response locally
cache_plugin: jsonfile              # Store cache as JSON files
cache_timeout: 300                  # Cache is valid for 300 seconds (5 minutes)
cache_connection: /tmp/aws_inventory_cache  # Where to store cache files
# Without cache: every playbook run makes a fresh API call
# With cache: same data used for 5 min — much faster for frequent runs

9 Keyed Groups — Deep Dive

Keyed groups are the most powerful feature of inventory plugins. They automatically create Ansible groups from any field in the EC2 API response. Think of it as: "for every unique value of this field, create a group and put matching servers in it." No manual group maintenance ever.

🔍 How Keyed Groups Work — Step by Step Example

Suppose AWS has these 4 running EC2 instances with the following tags:

Server Nametags.Environmenttags.Roletags.PatchGroup
prod-web-001productionwebgroup-a
prod-web-002productionwebgroup-b
prod-app-001productionappgroup-a
dev-web-001devwebgroup-a

With the keyed_groups config we wrote, Ansible automatically creates these groups:

Auto-generated groups from the above 4 EC2 instancesTEXT
@all:
  |--@aws_env_production:          # prefix=aws_env, key=production
  |  |-- prod-web-001
  |  |-- prod-web-002
  |  |-- prod-app-001
  |--@aws_env_dev:
  |  |-- dev-web-001
  |--@aws_role_web:                # prefix=aws_role, key=web
  |  |-- prod-web-001
  |  |-- prod-web-002
  |  |-- dev-web-001
  |--@aws_role_app:
  |  |-- prod-app-001
  |--@aws_patch_group-a:           # prefix=aws_patch, key=group-a
  |  |-- prod-web-001
  |  |-- prod-app-001
  |  |-- dev-web-001
  |--@aws_patch_group-b:
  |  |-- prod-web-002

Now in your playbook you can say hosts: aws_env_production:&aws_role_web — which means "all servers that are in BOTH aws_env_production AND aws_role_web." This gives you prod-web-001 and prod-web-002. No static grouping. No maintenance. Just tags and logic.

🔗 Pattern Combinations in Playbooks Using Dynamic Groups

Using dynamic groups in playbook hosts patternYAML
---
# Targeting specific combinations of dynamic groups

# Example 1: All production EC2 instances
- name: Patch all production AWS servers
  hosts: aws_env_production

# Example 2: Production web servers only (intersection of two groups)
- name: Patch production web tier
  hosts: "aws_env_production:&aws_role_web"   # & = intersection (must be in BOTH groups)

# Example 3: All production servers EXCEPT database
- name: Patch all prod except DB (DBA team does DB separately)
  hosts: "aws_env_production:!aws_role_db"    # ! = exclude (not in this group)

# Example 4: Union — patch production AND staging together
- name: Patch production and staging web servers
  hosts: "aws_env_production:aws_env_staging:&aws_role_web"

# Example 5: Use patch groups for staggered rollout
- name: Patch group-a first (staggered patching)
  hosts: "aws_env_production:&aws_patch_group-a"

# Example 6: Target via AAP Survey (user picks at runtime)
- name: Patch selected environment
  hosts: "{{ 'aws_env_' + target_environment }}"  # target_environment from AAP Survey
PatternMeaning
aws_env_productionAll servers in the aws_env_production group (all production EC2 instances)
group1:&group2INTERSECTION — servers that are in BOTH group1 AND group2. Like SQL WHERE env='prod' AND role='web'
group1:!group2EXCLUSION — servers in group1 but NOT in group2. Like SQL WHERE env='prod' AND role != 'db'
group1:group2UNION — servers in group1 OR group2 (combined, deduplicated)
allEvery server from every inventory source — use with extreme care in production

10 Compose Variables — Setting Host Variables from EC2 Data

The compose section in the plugin config allows you to create Ansible variables dynamically for each host based on their EC2 metadata. This is how you make every EC2 instance "self-describing" — the server carries its own configuration context through its AWS tags.

Advanced compose examples — real bank use casesYAML
compose:

  # ===== SSH CONNECTION SETTINGS =====
  ansible_host: private_ip_address
  # Always use private IP in production VPC — no public IPs on prod servers

  ansible_user: "'ec2-user' if tags.get('OS','').startswith('rhel') else 'ubuntu'"
  # RHEL EC2 uses ec2-user, Ubuntu uses ubuntu — choose based on OS tag

  ansible_ssh_private_key_file: "'/home/ansible-svc/.ssh/globaltrust-prod.pem' if tags.get('Environment') == 'production' else '/home/ansible-svc/.ssh/globaltrust-dev.pem'"
  # Use different SSH keys for prod vs non-prod — different security boundaries

  # ===== BANK-SPECIFIC VARIABLES =====
  server_environment: tags.Environment
  # Available as {{ server_environment }} in every playbook

  application_name: tags.Application

  patch_window: "'saturday_2am_ist' if tags.get('Environment') == 'production' else 'friday_10pm_ist'"
  # Production patches Saturday 2 AM, non-prod Friday 10 PM

  ec2_instance_id: instance_id
  # Critical for taking snapshots before patching

  ec2_region: placement.region

  ec2_vpc_id: vpc_id

  requires_reboot_approval: "tags.get('Environment') == 'production'"
  # Production reboots require approval via AAP Approval Node — logic driven by tag
Compose ExpressionExplanation
private_ip_addressA direct field reference — this is the raw EC2 instance field name as returned by the boto3 API. The plugin makes all EC2 instance fields available as Jinja2 variables.
tags.EnvironmentAccess the value of the "Environment" tag. If the tag is not set, this returns None (empty). Always use tags.get('Environment', 'unknown') pattern for safer access when a tag might be missing.
"'ec2-user' if ... else 'ubuntu'"This is a Jinja2 inline conditional expression. The entire value is a Jinja2 expression evaluated at inventory build time. You can use Python-like syntax including string methods like .startswith(), .get(), .lower() inside these expressions.
placement.regionNested field access using dot notation. "placement" is an EC2 object that contains region, availability_zone, and tenancy. Use dot notation to access nested fields.

11 Azure Setup — Service Principal Authentication

☁️ Azure Authentication — Service Principal
Azure does not use access keys like AWS. Instead, Azure uses a Service Principal — think of it as an "application identity" in Azure Active Directory. The Service Principal is given permissions (via RBAC roles) to read VM information in specific Azure subscriptions and resource groups. Ansible authenticates to Azure as this Service Principal using four values: Subscription ID, Client ID (App ID), Client Secret (password), and Tenant ID (Azure AD directory ID).
Create Azure Service Principal for AnsibleBASH
# Using Azure CLI to create the Service Principal
az login  # Log in to Azure

# Get subscription ID
az account show --query id -o tsv
# Output: 12345678-abcd-1234-efgh-123456789012

# Create Service Principal with Reader role (read-only — least privilege)
az ad sp create-for-rbac \
  --name "ansible-inventory-sp" \
  --role Reader \
  --scopes /subscriptions/12345678-abcd-1234-efgh-123456789012
# Output:
# {
#   "appId": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",       ← This is Client ID
#   "displayName": "ansible-inventory-sp",
#   "password": "xxxxxxxxxxxxxxxxxxxx",                     ← This is Client Secret
#   "tenant": "ffffffff-gggg-hhhh-iiii-jjjjjjjjjjjj"      ← This is Tenant ID
# }

# Save these 4 values — they go into AAP Azure Credential
# AAP: Credentials → Add → Microsoft Azure Resource Manager

16 AAP Controller — Configuring Dynamic Inventory Sources

In AAP, you don't run plugin config files directly — instead you configure Inventory Sources inside the Controller UI. Each source points to a cloud platform and is configured with the appropriate credential. AAP then manages the inventory internally and makes it available to all job templates.

1
Create the Inventory Container Inventories → Add → Inventory. Name: "GlobalTrust Hybrid Cloud Inventory". Organisation: GlobalTrust Bank IT Operations. This is the container — it starts empty and you add sources to fill it.
2
Add AWS EC2 Source Inside the Inventory → Sources tab → Add. Name: "AWS EC2 — ap-south-1". Source: Amazon EC2. Credential: (select your AWS credential). Regions: ap-south-1. Source Variables: paste the contents of your aws_ec2.yml plugin config (without the plugin: line — AAP adds that). Enable: "Update on launch" ✅ — this re-queries AWS every time a job starts.
3
Add Azure RM Source Sources → Add. Name: "Azure Central India". Source: Microsoft Azure Resource Manager. Credential: (select Azure credential). Source Variables: paste azure_rm.yml contents. Enable "Update on launch" ✅.
4
Add VMware vCenter Source Sources → Add. Name: "VMware vCenter Mumbai". Source: VMware vCenter. Credential: Create a VMware vCenter credential first (Credentials → Add → VMware vCenter). Source Variables: paste vmware.yml contents. Enable "Update on launch" ✅.
5
Sync All Sources Inventory → Sources → Sync All. Watch as AAP queries AWS, Azure, and VMware simultaneously and populates the inventory. The Hosts tab shows all discovered servers with their groups and variables.
6
Attach Inventory to Job Template Templates → (any Job Template) → Edit → Inventory: select "GlobalTrust Hybrid Cloud Inventory". Now when the job runs, it uses all three cloud sources combined. The "Limit" field lets engineers restrict to a specific group (e.g., aws_env_production).
💡 "Update on Launch" vs Scheduled Sync
"Update on launch" means the inventory is refreshed every time a job starts — always fresh. This adds 2–10 seconds to job startup time (API call time). For jobs that run very frequently (every 5 minutes), this overhead adds up. Alternative: schedule an inventory sync every 10 minutes as a background task, and let jobs use the cached inventory. In GlobalTrust Bank, patching jobs run monthly — "update on launch" is fine. For a monitoring job running every minute, we'd use scheduled sync instead.

17 Inventory Filters — Safety Guards for Production

Filters are critical safety mechanisms. Without filters, a mistyped host pattern could run a playbook against ALL 335 servers across all three clouds simultaneously. Filters at the inventory plugin level, the playbook host pattern level, and the AAP job template level create a three-layer defence.

inventory/aws_ec2.yml — Adding strict filters for production safetyYAML
plugin: amazon.aws.aws_ec2
regions:
  - ap-south-1

# LAYER 1 FILTER: Only return instances that pass ALL these criteria
filters:
  instance-state-name: running          # Never target stopped/terminated instances
  tag:ManagedBy: ansible                # Only servers the Ansible team owns
  tag:PatchEnabled: "true"             # Must have opt-in patch tag
# PatchEnabled tag is set by the server owner — explicit opt-in for automation
# This prevents accidental patching of newly launched instances not yet configured

# LAYER 2 FILTER: Exclude specific servers
exclude_filters:
  - tag:PatchExclude: "true"           # Any server tagged PatchExclude=true is skipped
# DBA team can tag a DB server PatchExclude=true to defer its patch window
AAP Job Template — Limit field as third safety layerYAML
# In AAP Controller Job Template:
# Limit field: aws_env_production:&aws_patch_group-a
# Even though the full inventory has ALL environments,
# the job only runs against PROD Group-A servers

# In Playbook — limit host pattern from command line:
ansible-playbook site.yml \
  -i inventory/ \
  --limit "aws_env_production:&aws_role_web" \     # Only prod web servers
  -e "target_environment=production" \

18 Troubleshooting — Real Production Issues

🚨 Issue 1: Plugin Not Triggered — Treated as Static Inventory
Symptom

You create inventory/myfile.yml with the aws_ec2 plugin config. But when you run ansible-inventory -i inventory/myfile.yml --graph, it shows an empty inventory or a YAML parse error instead of EC2 instances.

Root Cause

The file is not being recognised as a dynamic inventory plugin config. Two possible reasons: (1) The filename doesn't end with aws_ec2.yml or .aws_ec2.yml, OR (2) The plugin: directive is missing or misspelled at the top of the file.

Fix: Check filename and plugin lineBASH
# WRONG filenames (will not trigger aws_ec2 plugin):
# inventory/aws.yml       ← wrong
# inventory/ec2.yaml      ← wrong (must be .yml not .yaml)
# inventory/production.yml ← wrong

# CORRECT filenames:
# inventory/aws_ec2.yml            ← correct (exact suffix)
# inventory/production.aws_ec2.yml ← correct (prefix.suffix format)
# inventory/globaltrust.aws_ec2.yml ← correct

# Also verify plugin: line is EXACTLY correct:
# plugin: amazon.aws.aws_ec2     ← CORRECT (FQCN)
# plugin: aws_ec2                ← WRONG (short name may not work)

# Also verify the plugin is enabled in ansible.cfg:
grep enable_plugins ansible.cfg
# Should show: amazon.aws.aws_ec2 in the list
🚨 Issue 2: ansible_host Not Set — SSH Fails with Wrong IP
Symptom

The plugin discovers EC2 instances but Ansible tries to SSH to the public DNS name or a wrong address. Error: UNREACHABLE! => Failed to connect to the host via ssh: ssh: Could not resolve hostname ec2-15-206-80-xxx.ap-south-1.compute.amazonaws.com

Root Cause

The compose section is missing ansible_host: private_ip_address. By default, the plugin uses the EC2 public DNS name as the hostname. In a production VPC, there is no public IP on servers — connections must use the private IP.

Fix
Fix: Add ansible_host to compose sectionYAML
compose:
  ansible_host: private_ip_address   # ALWAYS set this for private VPC

# Verify it worked:
ansible-inventory -i inventory/aws_ec2.yml --host prod-ibank-web-001 | grep ansible_host
# Should show: "ansible_host": "10.11.4.x"  (private IP)
🚨 Issue 3: VMware Plugin Returns No Hosts — guest.ipAddress is null
Symptom

The VMware plugin runs and discovers VMs (you can see them with --list) but the ansible_host is empty/null for many VMs. When the playbook runs, it fails with SSH to empty host.

Root Cause

VMware Tools is not installed or not running on the VMs. guest.ipAddress is populated by VMware Tools running inside the VM. Without VMware Tools, the vCenter API cannot retrieve the VM's IP address — it only knows the IP if the guest OS reports it back through VMware Tools.

Fix
Check VMware Tools and use fallback IPYAML
# Fix 1: Ensure VMware Tools is installed (use Ansible to install it)
# Fix 2: Use a fallback in compose section
compose:
  ansible_host: guest.ipAddress | default(omit)
  # omit = skip this variable if ipAddress is None
  # Fallback: use VM name-based DNS if your internal DNS has VM entries

# Fix 3: Filter out VMs with no IP
filters:
  - guest.toolsStatus == "toolsOk"  # Only include VMs where Tools are running
  - guest.ipAddress is not none      # Only include VMs with an IP address
🚨 Issue 4: Inventory Sync Takes 15+ Minutes — Timeouts in AAP
Symptom

The AAP inventory sync job takes 15–20 minutes and sometimes times out. The VMware source is the slowest — it hangs querying all 210 VMs with with_nested_properties: true.

Root Cause

Fetching all nested properties for 210 VMs from vCenter is very expensive — each VM requires multiple API calls. The with_nested_properties: true setting multiplies the API calls significantly.

Fix

  - guest.ipAddress
  - runtime.powerState
  - config.guestId

# Performance fix 3: Restrict scope

  - datacenter: Mumbai-DC
    folder: /Mumbai-DC/vm/PROD     # Only PROD folder — not all 210 VMs

In AAP, disable "Update on launch" for the VMware source. Instead, schedule an inventory sync every 30 minutes as a standalone job. Job templates use the cached inventory — no per-job API calls. This reduces job startup time from 15 minutes to under 5 seconds.

19 Interview Preparation — Dynamic Inventory

💡 Why This Topic Wins Interviews
Dynamic Inventory is a differentiating topic. Basic Ansible knowledge is common. But candidates who can confidently explain "we use the amazon.aws.aws_ec2 plugin with keyed_groups to automatically group EC2 instances by their Environment and Role tags, and combine it with VMware and Azure sources in AAP" immediately stand out. It shows cloud awareness, real-world experience, and understanding of enterprise-scale automation.

🟢 Beginner Questions

Q1. What is the difference between static and dynamic inventory in Ansible?
Static inventory is a file — usually called hosts or hosts.yml — where you manually list every server's IP address, hostname, and group membership. You must update this file every time a server is added, renamed, or removed. In small, stable environments this is acceptable. Dynamic inventory, on the other hand, does not use a manually maintained file. Instead, Ansible uses an inventory plugin — a Python program that connects to an external source like AWS EC2 API, Azure Resource Manager, or VMware vCenter at the moment the playbook runs. It fetches the current list of servers automatically, including their metadata and groups based on tags or folder structure. In GlobalTrust Bank, we use dynamic inventory for all cloud and VMware infrastructure — 335 servers across three platforms — with zero manual inventory maintenance. The key advantage: if a new EC2 instance is launched at 9 AM and the patching job runs at 10 AM, the dynamic inventory automatically includes the new instance. Static inventory would miss it completely.
Q2. What is an inventory plugin? Name the plugins you have used.
An inventory plugin is a Python module that Ansible uses to connect to a specific platform and translate its API response into Ansible's inventory format — a structure of hosts, groups, and variables. The plugin is triggered by a specially named YAML configuration file. I have used three inventory plugins in our banking project. First, amazon.aws.aws_ec2 — connects to the AWS EC2 API using boto3, fetches all running instances with their tags, and groups them using the keyed_groups feature. The config file must be named with the suffix aws_ec2.yml. Second, azure.azcollection.azure_rm — connects to Azure Resource Manager API using a Service Principal, fetches all VMs from specified resource groups, and groups by tags and location. Third, community.vmware.vmware_vm_inventory — connects to VMware vCenter's REST API, fetches all powered-on VMs with their properties, and groups by OS type and folder path. All three run simultaneously in AAP — the results are merged into a single unified inventory containing all 335 servers.

🟡 Intermediate Questions

Q3. What are keyed_groups and compose in inventory plugins? Explain with an example.
Both are sections in the inventory plugin configuration YAML file. keyed_groups automatically creates Ansible groups based on the values of EC2 tags or fields. For example, with keyed_groups: - key: tags.Environment, prefix: aws_env, if an EC2 instance has the tag Environment=production, Ansible automatically creates a group called aws_env_production and adds that instance to it. You don't create groups manually — they emerge from the data. If tomorrow someone launches 10 new instances with Environment=staging, a new group aws_env_staging is created automatically. In your playbook you can then say hosts: aws_env_production and it targets only production servers. compose creates or sets Ansible variables (hostvars) for each discovered host based on expressions. The most critical use is ansible_host: private_ip_address — this sets the SSH connection address to the private IP. Without this, Ansible uses the public DNS name by default, which doesn't work inside a private VPC. You can also create business-specific variables: ec2_environment: tags.Environment makes the environment tag available as {{ ec2_environment }} in every playbook task on that host. compose also supports Jinja2 expressions for conditional logic: ansible_user: "'ec2-user' if 'rhel' in tags.OS else 'ubuntu'".
Q4. How does Ansible authenticate to AWS for dynamic inventory? What are the security best practices?
There are three ways to authenticate. Method 1 — IAM User Access Keys: create a dedicated IAM user (ansible-inventory-svc), attach a read-only policy with only ec2:Describe* actions, generate access keys (AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY). Store these in AAP as an Amazon Web Services credential — AAP encrypts them and injects as environment variables. Best practice — rotate keys every 90 days. Method 2 — IAM Instance Profile (RECOMMENDED when AAP runs on EC2): attach an IAM Role directly to the EC2 instance where AAP's execution nodes run. No keys needed — AWS SDK automatically uses the instance metadata service to get temporary credentials. Method 3 — AssumeRole (for cross-account): one IAM user in the DevOps account assumes a role in the Production account using STS AssumeRole. Configure in the plugin with assume_role_arn. Security best practices I follow: never use the root AWS account, always use least privilege (only Describe actions, not full ec2:*), rotate keys regularly or use instance profiles, never store keys in the plugin YAML file or in Git, always use AAP credentials which encrypt and inject at runtime. Also, tag the IAM user with the team owner and automation purpose — helps in AWS access reviews during RBI audits.
Q5. How do you combine groups from multiple inventory sources in one playbook?
When you point Ansible to an inventory directory (not a single file), it reads all files in that directory — static hosts files, AWS plugin files, Azure plugin files, VMware plugin files — and merges them into a single unified inventory. All groups from all sources are available simultaneously. In our bank, I have groups like aws_env_production (from the AWS plugin), azure_env_production (from Azure plugin), and vmware_production (from VMware plugin + group_by task). I can combine them using Ansible's group pattern syntax in the hosts line: colon-separated groups for union, colon-ampersand for intersection, colon-exclamation for exclusion. For example, to patch all production Linux servers regardless of platform: hosts: "aws_env_production:azure_env_production:vmware_production" — this runs on all three combined. To patch only production web servers in AWS: hosts: "aws_env_production:&aws_role_web". The ampersand means intersection — must be in BOTH groups. This pattern-based targeting is how you write single playbooks that work across multi-cloud without hardcoding server names.
Q6. What is inventory caching and when do you use it?
Inventory caching stores the result of a dynamic inventory API call in a local file. On subsequent calls within the cache timeout period, Ansible reads from the local file instead of making another API call. You enable it with three settings in the plugin config: cache: true, cache_plugin: jsonfile (or redis/memcached), and cache_timeout: 300 (seconds). The cache is stored at the path specified by cache_connection. When to use it: when the inventory source is slow (VMware vCenter with 200+ VMs can take 2–3 minutes to query), when the same playbook is run multiple times in quick succession (test → fix → re-test cycles), or when you have multiple inventory sources and don't want all three APIs called on every run. When NOT to use it: for auto-scaling scenarios where EC2 instances are created and terminated frequently — a 5-minute cache might mean newly launched instances are missed for 5 minutes. Also in AAP, "Update on launch" with short cache_timeout gives you fresh data per job while still being faster than no caching at all. In GlobalTrust Bank, we use 300-second cache for AWS (EC2 fleet is fairly stable), 300-second for Azure, and 1800-second (30 minutes) for VMware (VMs are very stable on-premise).

🔴 Advanced / Scenario Questions

Q7. How would you handle a scenario where some EC2 instances don't have required tags?
This is a very real production problem. Developers sometimes launch instances without proper tags — no Environment tag, no Role tag. This means the keyed_groups logic won't work for those instances and they fall into the ungrouped group. Three strategies. Strategy 1 — Enforce tags at the AWS Organization level using AWS Config rules or Service Control Policies. Any instance without required tags gets automatically stopped after a grace period. Strategy 2 — Handle missing tags gracefully in the plugin using the default Jinja2 filter in compose: server_environment: "tags.get('Environment', 'unknown')". This creates a group aws_env_unknown for untagged instances — visible but separate. Strategy 3 — Add a filter to exclude untagged instances from automation: filters: tag:Environment: "*" — only include instances that have an Environment tag (any value). In our bank, we use a combination: AWS Config enforces tagging on new instances, the filter excludes untagged instances from automation, and a separate "Tag Compliance" job template runs weekly to identify and alert about untagged instances so the teams can fix them. This keeps the automation clean while ensuring compliance over time.
Q8. How is dynamic inventory configured in AAP Controller compared to running it from command line?
From the command line, you have a plugin config YAML file and pass it directly: ansible-inventory -i inventory/aws_ec2.yml --list. Authentication comes from environment variables or AWS credentials file. In AAP Controller, the approach is different. You create an Inventory object in AAP (a named container). Inside that Inventory, you add one or more Sources — each source corresponds to one plugin. The source type (Amazon EC2, Azure RM, VMware) tells AAP which plugin to use. The source's Variables field accepts the same YAML you would put in the config file (minus the plugin: line — AAP adds that automatically based on the source type). Authentication comes from an AAP Credential object — never from environment variables in the YAML. AAP injects the credentials as environment variables into the execution environment container at runtime. You can configure per-source settings like "Update on Launch" (refresh inventory when a job starts), "Overwrite" (existing hosts replaced by API data), and "Overwrite Variables" (hostvars from this source override other sources for the same host). In AAP, all sources under one Inventory are merged — exactly like having multiple plugin files in a directory. The result is a unified inventory visible in the Hosts tab.
