3 RBAC — Role-Based Access Control

🔐 RBAC Is the Foundation of Multi-Team AAP
RBAC in AAP answers one question: "Who is allowed to do what to which object?" Every object in AAP (Job Template, Inventory, Credential, Project, Organisation) has roles associated with it. You assign a User or Team to a role on a specific object — that gives them exactly those permissions on exactly that object, nothing more. A developer can have the Execute role on the "Deploy to DEV" job template but not on the "Deploy to PRODUCTION" template. They can view the DEV inventory but not the PRODUCTION inventory. They can see that a credential named "AWS Production Key" exists but cannot read its value or use it in any template they control.

📐 The Three Dimensions of RBAC

1. The Subject (Who)

User — Individual person with a login. Can be local (created in AAP) or external (LDAP/SSO).

Team — Group of users. Assign role to the Team once → all current and future team members get it.

2. The Role (What)

Admin — Full control: read, edit, delete, use, manage permissions.

Use — Can use the object (e.g., use a credential in a template) but not edit it.

Execute — Can launch a Job Template but not edit its definition.

Read — Can view but not change or use.

3. The Object (Which)

Job Templates, Workflow Templates, Inventories, Projects, Credentials, Organisations, Instance Groups.

Roles are always scoped to a specific object — "Execute on Job Template #42" not "Execute on all job templates."

💡 The Use Role on Credentials — A Critical Security Design
The Use role on a Credential is one of the most important security features in AAP. When a developer has the Use role on the "AWS Production IAM Credential," they can attach it to a Job Template and the template will use those AWS credentials when it runs. But the developer can never read the actual access key and secret — they are encrypted and only decrypted inside the Execution Environment at job runtime. This means developers can deploy to AWS using production credentials they literally cannot see or steal. This pattern is called credential delegation — the platform uses the credential on behalf of the user without exposing it.

7 LDAP Integration — Sync with Active Directory

📌 Why LDAP Integration Is Essential in Enterprise
GlobalTrust Bank has 2,000+ engineers. Creating and managing 2,000 AAP user accounts manually is impossible. When an engineer leaves the bank, you want their AAP access revoked automatically — not after someone remembers to delete them. LDAP integration solves both: AAP authenticates users against Active Directory (the same login they use for their laptop) and automatically syncs group membership to AAP teams. When HR adds someone to the AD group "AAP-DevOps-Team," they get DevOps team permissions in AAP within minutes of their next login.
AAP LDAP configuration (Settings → Authentication → LDAP)JSON
// AAP UI: Settings → Authentication → LDAP
// Or via API: POST /api/v2/settings/ldap/

{
  // ===== LDAP Server Connection =====
  "AUTH_LDAP_SERVER_URI": "ldaps://ad.globaltrust.in:636",
  "AUTH_LDAP_BIND_DN": "CN=aap-service,OU=ServiceAccounts,DC=globaltrust,DC=in",
  "AUTH_LDAP_BIND_PASSWORD": "ServiceAccountPassword123!",

  // ===== User Search — Find the user who is logging in =====
  "AUTH_LDAP_USER_SEARCH": [
    "OU=Users,DC=globaltrust,DC=in",
    "SCOPE_SUBTREE",
    "(sAMAccountName=%(user)s)"       // %(user)s = the username typed at login
  ],

  // ===== Map LDAP attributes to AAP user profile =====
  "AUTH_LDAP_USER_ATTR_MAP": {
    "first_name": "givenName",
    "last_name": "sn",
    "email": "mail"
  },

  // ===== Group Search — Find AD security groups =====
  "AUTH_LDAP_GROUP_SEARCH": [
    "OU=AAP-Groups,DC=globaltrust,DC=in",
    "SCOPE_SUBTREE",
    "(objectClass=group)"
  ],
  "AUTH_LDAP_GROUP_TYPE": "ActiveDirectoryGroupType",

  // ===== Map AD Groups → AAP Teams =====
  "AUTH_LDAP_TEAM_MAP": {
    "DevOps Engineers": {
      "organization": "GlobalTrust Bank IT Operations",
      "users": "CN=AAP-DevOps-Team,OU=AAP-Groups,DC=globaltrust,DC=in",
      "remove": true   // Remove from team if not in AD group (handles leavers)
    },
    "Application Developers": {
      "organization": "GlobalTrust Bank IT Operations",
      "users": "CN=AAP-App-Devs,OU=AAP-Groups,DC=globaltrust,DC=in",
      "remove": true
    },
    "AAP Platform Admins": {
      "organization": "GlobalTrust Bank IT Operations",
      "users": "CN=AAP-Platform-Admins,OU=AAP-Groups,DC=globaltrust,DC=in",
      "remove": true
    }
  },

  // ===== Organisation membership via LDAP =====
  "AUTH_LDAP_ORGANIZATION_MAP": {
    "GlobalTrust Bank IT Operations": {
      "admins": "CN=AAP-Platform-Admins,OU=AAP-Groups,DC=globaltrust,DC=in",
      "users": true,   // All authenticated LDAP users become org members
      "remove_admins": true,
      "remove_users": false
    }
  },

  // ===== SSL Certificate for LDAPS (secure LDAP) =====
  "AUTH_LDAP_CONNECTION_OPTIONS": {
    "OPT_X_TLS_CACERTFILE": "/etc/ssl/certs/globaltrust_ca.crt"
  }
}
Config KeyExplanation
AUTH_LDAP_USER_SEARCHTells AAP how to find a user in AD when they try to log in. The tuple has three parts: the base DN to search under, the search scope (SCOPE_SUBTREE = search all subdirectories), and the filter expression (sAMAccountName=%(user)s means "find the object whose Windows login name matches what the user typed"). When arjun.sharma logs in, AAP searches for sAMAccountName=arjun.sharma in OU=Users,DC=globaltrust,DC=in.
AUTH_LDAP_TEAM_MAPThe most powerful configuration key. It maps AD security groups to AAP Teams. When a user logs in, AAP checks which AD groups they belong to. If they are in CN=AAP-DevOps-Team, they are added to the "DevOps Engineers" AAP team. If remove: true and they are removed from the AD group (e.g., left the bank), they are removed from the AAP team on their next login attempt. This is how ex-employee access is automatically revoked.
remove: trueCritical for security. With remove: true, if a user is in the AAP team but NOT in the AD group, they are removed from the team at their next login. Without this, a user who leaves the DevOps team in AD retains their AAP DevOps team permissions forever. With remove: true, HR removing them from the AD group automatically removes their elevated AAP permissions.

8 Instance Groups — Route Jobs to Specific Nodes

📌 What Is an Instance Group?
An Instance Group is a named collection of AAP execution nodes (instances). When you assign an Instance Group to a Job Template, Inventory, or Organisation, AAP only executes that job on nodes in that group — not on any other execution node. This gives you complete control over where automation runs. GlobalTrust Bank uses three Instance Groups: ig-production (dedicated high-spec nodes for production jobs), ig-dev-qa (shared nodes for development and QA — can be overloaded without affecting production), and ig-dmz (isolated nodes in the DMZ network segment that can reach DMZ servers which other nodes cannot).

9 Types of Instances in AAP

Instance TypeWhat It DoesWhere It Runs
Control NodeRuns the AAP Control Plane — the web UI, API, job scheduling, and database. Does NOT run actual Ansible playbooks. It dispatches jobs to execution nodes.On-premises or cloud — needs high memory, good DB performance
Execution NodeActually runs Ansible playbooks inside EE containers. A job launched in AAP ends up running here. You can have many execution nodes for parallelism and isolation.On-premises, cloud, or remote network segments (DMZ, branch office)
Hop NodeA relay/proxy node. Traffic from the Control Plane passes through a Hop Node to reach Execution Nodes in isolated network segments. The Hop Node itself does not run playbooks.Network boundary — e.g., between corporate network and DMZ
Hybrid NodeRuns both Control Plane and Execution functions. Used for small/single-node AAP installations. Not recommended for large enterprise deployments.Single-server AAP setups (dev/test environments)

12 Job Slicing — Parallel Execution at Scale

📌 What Is Job Slicing?
Job Slicing takes one job that targets many hosts and splits it into multiple smaller child jobs (slices) that each run on a subset of the hosts — simultaneously, in parallel. Without slicing, a playbook targeting 300 Linux servers with serial: 10% processes 30 servers at a time, taking 3.5 hours. With 10 slices, AAP splits the 300 servers into 10 groups of 30 and runs all 10 slices simultaneously (one per execution node thread). Total time: 22–25 minutes. The playbook code is unchanged — slicing is configured in the Job Template, not the playbook.

13 Configuring Job Slicing

✅ Job Slicing Requires Zero Playbook Changes
The playbook runs identically inside each slice. The serial keyword in the playbook still works within each slice — if you have serial: 10% on a 30-server slice, it processes 3 servers at a time within that slice. Slicing only changes how AAP divides the inventory, not how Ansible processes hosts.
Enable Job Slicing on a Job Template via API and UIBASH
# ===== Configure Job Slicing via API =====
curl -sk -X PATCH -H "Authorization: Bearer $AAP_TOKEN" -H "Content-Type: application/json" \
  -d '{
    "job_slice_count": 10
  }' \
  $AAP_URL/api/v2/job_templates/42/

# ===== Result: =====

# Child jobs: JT_42_slice_1_of_10, JT_42_slice_2_of_10 ... JT_42_slice_10_of_10
# Each child job runs on ~30 hosts simultaneously
# Parent job completes when ALL child slice jobs complete

# ===== AAP UI steps: =====

14 When to Use Job Slicing vs serial

Featureserial (in playbook)Job Slicing (in AAP)
What it doesProcess N hosts at a time, sequentiallyRun N groups of hosts in parallel simultaneously
Effect on execution timeAdds time (sequential batching)Reduces time (parallel execution)
Why use itSafety — limit blast radius (only N servers down at once if something goes wrong)Speed — finish patching 300 servers in 25 min instead of 3.5 hours
Where configuredIn the playbook YAMLIn the AAP Job Template (zero playbook changes)
Can they be combined?YES — and this is the recommended production pattern. serial: 10% inside the playbook (safety) + Job Slices = 10 in the template (speed). Each slice processes 10% of its 30-server subset at a time.
💡 GlobalTrust Bank's Best Practice: Always Use Both Together
Monthly patching playbook has serial: 10% (process 3 servers at a time within each slice for rolling safety). Job Template has Job Slices = 10 (10 parallel slices of 30 servers each). Net result: at any given moment, up to 30 servers are being patched simultaneously (10 slices × 3 servers per slice), but no more. If something goes wrong with one slice, the other 9 keep going. The parent job reports failure only if a threshold of slices fail (configurable).

15 Schedules — Automated Job Triggering

📌 What Are AAP Schedules?
A Schedule in AAP is a time-based trigger attached to a Job Template, Workflow Template, Inventory Source, or Project. When the scheduled time arrives, AAP automatically launches the associated object — no human needed. Schedules use the RRULE (Recurrence Rule) standard from the iCalendar specification, which provides an extremely expressive syntax for defining repeating time patterns: "every Monday and Thursday at 2 AM" or "second Tuesday of every month at 11 PM" or "every weekday at 6 AM but only in January and February."

💡 RRULE Is a Standard — Learn It Once, Use Everywhere
RRULE is from the iCalendar RFC 5545 standard. The same syntax is used in Google Calendar, Outlook, and many scheduling tools. Understanding RRULE lets you express any time pattern in one line. Every RRULE starts with DTSTART (the first occurrence datetime) followed by the rule string.

Sliced patching job runs 10 slices. 8 succeed but 2 slices fail. The parent job reports FAILED.

Causes
  • The 30 hosts in those slices have a genuine issue (disk full, SSH timeout, yum error)
  • The slice ran on an execution node that had a resource issue (OOM on the exec node)
Investigate

Click the failed slice job (not the parent) in AAP to see its output. The slice's output shows which specific hosts failed and why. This re-runs only the failed subset without touching the 270 servers that already succeeded.

22 Interview Preparation — Advanced AAP Features

Q1. How does RBAC work in AAP? How did you implement it for multiple teams?
RBAC in AAP works on a simple model: Subject (User or Team) + Role + Object (specific AAP resource). Every object in AAP — Job Templates, Inventories, Credentials, Projects — has roles you can assign: Admin, Execute, Use, Update, and Read. These are always scoped to a specific object, never global. In GlobalTrust Bank, I designed a five-tier RBAC framework. The AAP Platform Admins team (2 people) have Organisation Admin role which gives them full control over everything. The DevOps Engineers team (8 people) have Execute role on all Job Templates, Use role on all Credentials, and Admin role on Inventories and Projects. The Application Developers team (25 people) have Execute role only on DEV-environment Job Templates and Read role on DEV inventories — they have zero visibility into production templates or credentials. The Security team has Read access to all inventories and job history for audit purposes. The NOC team can execute monitoring and alerting job templates only. We integrated this with Active Directory via LDAP. When a user logs in, AAP reads their AD group membership and automatically places them in the correct AAP team. When someone leaves the bank, HR removes them from the AD group, and remove: true in the LDAP team map removes their AAP access automatically. The key security design: credentials are never visible to anyone below Platform Admin level. Developers can use a credential — it runs as part of a job — but they can never read the actual secret value.
Q2. What are Instance Groups in AAP and why did you create multiple ones?
Instance Groups are named pools of AAP execution nodes. When you assign an Instance Group to a Job Template or Inventory, AAP only dispatches that job to nodes in that group. GlobalTrust Bank runs three Instance Groups for three distinct reasons. ig-production has two high-spec execution nodes (32 vCPU, 64 GB RAM each). All production job templates — patching, deployments, cloud provisioning — run exclusively on these nodes. This ensures production automation is never delayed because a development job is consuming resources. ig-dev-qa has one shared execution node for all development and QA environment automation. DEV deployments can queue here without affecting production. ig-dmz has one execution node physically located in the DMZ network segment. DMZ servers are not reachable from the corporate network where the other execution nodes live. The DMZ execution node can SSH to DMZ servers. Traffic from the AAP Control Plane to the DMZ execution node flows through a Hop Node at the network boundary — the Hop Node relays control traffic through the firewall without opening the DMZ servers to the corporate network. The practical result: when the WAF rule update Job Template runs, AAP dispatches it to the DMZ execution node which can reach the WAF — the corporate execution nodes literally cannot. This is an architectural security control, not just a configuration preference.
Q3. What is Job Slicing and when did you use it?
Job Slicing is an AAP feature that splits a single job targeting many hosts into multiple smaller parallel child jobs (slices), each running simultaneously on a subset of the hosts. You configure it in the Job Template — set Job Slice Count to N and AAP automatically divides the inventory into N groups of equal size and dispatches them as parallel jobs. The playbook code is unchanged. At GlobalTrust Bank, our monthly Linux compliance patching runs against 300 RHEL servers. Without slicing, with serial: 10% in the playbook, the job processes 30 servers at a time sequentially, taking about 3.5 hours. With Job Slices = 10, AAP creates 10 parallel slice jobs of 30 servers each. All 10 run simultaneously. Since the playbook still has serial: 10% inside each slice, each slice processes 3 servers at a time — so at peak, 30 servers are being patched simultaneously (10 slices × 3 servers). Total time: 22 minutes. We use both together: serial in the playbook for safety (rolling updates, limit blast radius per slice) and Job Slicing in the template for speed (parallel slices). Job Slicing and serial serve complementary roles: serial is about safety within a group, slicing is about parallelism across groups. Important caveat: Job Slicing works best when the playbook is stateless and hosts don't depend on each other. For deployments with load balancer draining and health checks, we don't use slicing — serial handles that sequencing carefully.
Q4. How do you schedule automated jobs in AAP? Explain RRULE.
AAP Schedules use the RRULE standard from the iCalendar RFC 5545 specification. A schedule has two parts: DTSTART defines the first occurrence (start date, time, and timezone), and the RRULE defines the recurrence pattern. The RRULE has multiple components separated by semicolons. FREQ is the primary recurrence frequency — MINUTELY, HOURLY, DAILY, WEEKLY, MONTHLY, or YEARLY. INTERVAL sets the gap — FREQ=WEEKLY;INTERVAL=2 means every two weeks. BYDAY specifies which days of the week — MO,TU,WE,TH,FR means weekdays, 1SU means first Sunday, 2TU means second Tuesday, -1FR means last Friday. BYMONTHDAY specifies the day of month — -1 means last day. COUNT limits total occurrences. UNTIL sets an end date. In GlobalTrust Bank, I configured five recurring schedules. The Linux patching schedule runs on the first Sunday of every month at 2 AM IST: DTSTART;TZID=Asia/Kolkata:20240101T020000 RRULE:FREQ=MONTHLY;BYDAY=1SU. Windows patching runs on the second Tuesday (Microsoft Patch Tuesday) at 11 PM IST: FREQ=MONTHLY;BYDAY=2TU. The AWS inventory sync runs every 30 minutes all day. The daily compliance scan runs Monday through Friday at 7 AM. Schedules can also be attached to Inventory Sources (auto-sync) and Projects (auto-pull from Git). The timezone is the trickiest part — always use TZID= in the DTSTART to specify the local timezone explicitly, otherwise times are interpreted as UTC and your 2 AM IST becomes 8:30 PM the previous evening.
Q5. How do you measure the ROI of Ansible automation for leadership?
Red Hat Automation Analytics (available through cloud.redhat.com, connected to AAP) provides the data foundation. The key feature is the Automation Calculator — you set a "manual time estimate" for each Job Template (how long this task would take a human to do manually), and the tool multiplies that by the number of successful runs to calculate total hours saved. In GlobalTrust Bank, I configured manual time estimates for every Job Template: Internet Banking deployment = 3.5 hours manually, Linux patching = 4 hours per window, AWS provisioning = 1.5 hours, CMDB updates = 30 minutes. Over Q3 2024, with 609+ job runs, the calculator showed 603+ hours saved — at our blended engineer cost of ₹3,500 per hour, that is ₹21 lakh in direct time savings. I present this to the CTO quarterly. Beyond time savings, I also quantify: cost of prevented incidents (before auto-remediation, 23 on-call alerts per week at 45 minutes each; now 4 per week = 855 engineer-hours saved annually), cost of zero-downtime deployments (no revenue loss from maintenance windows with Blue-Green), and RBI compliance value (previously at risk of ₹50 lakh fine for change management gaps — now zero gap). The complete business case for the AAP platform investment is always significantly larger than the direct time savings alone.
