🎫 ServiceNow ITSM Integration
Incident · Change Request · CMDB · Approval Workflow · Auto-Ticketing

GlobalTrust Bank uses ServiceNow as its enterprise ITSM platform — every infrastructure change, every incident, every compliance audit goes through ServiceNow. This project integrates Ansible AAP with ServiceNow so that automation creates tickets, validates approvals, updates CMDB, and closes Change Requests automatically — zero manual ITSM work.

🏦 Domain: BFSI ITSM 🎫 ServiceNow Tokyo/Vancouver 📦 servicenow.itsm collection 📅 Level: Intermediate → Advanced

1 Project Overview

📌 Why ServiceNow + Ansible Is Critical for Banking
RBI's IT Framework for Banks mandates that every infrastructure change in production must go through a formal Change Management process — documented, approved, implemented, and verified. ServiceNow is the bank's Change Management system. Without integration, DevOps engineers were doing double work: running Ansible playbooks AND manually updating ServiceNow tickets. With integration, Ansible does both automatically — the playbook runs AND updates the CR, creates audit evidence, and closes the ticket. This is the difference between automation that satisfies RBI auditors and automation that creates compliance gaps.

🚨 Incident Automation

Ansible detects infrastructure failures (disk full, service down, patch failure) and automatically creates ServiceNow incidents with full technical details — no manual ticket creation needed at 3 AM.

📋 Change Request Lifecycle

Ansible reads CR status before patching (must be Approved), updates work notes during execution, and closes CR with evidence after completion. Full ITIL change management automation.

🗄️ CMDB Auto-Update

After provisioning new servers (EC2, Azure VM, VMware clone), Ansible automatically creates/updates Configuration Items in ServiceNow CMDB — always in sync with actual infrastructure.

2 Business Requirement

🚨 RBI Audit Finding — The Trigger for This Project
During a 2023 RBI IT audit, the examiner found that 23% of production changes had no corresponding ServiceNow Change Request — or the CR was in "Open" state while the change had already been implemented. This violates RBI's change management guidelines. The bank was issued a Remediation Directive: within 60 days, implement automated CR lifecycle management ensuring every Ansible-driven production change is linked to an approved CR and the CR is automatically closed after implementation. Fine risk: ₹50 lakh. This project is that implementation.
✅ Target State After Integration
  • 100% of production Ansible runs linked to ServiceNow CR
  • Playbook validates CR is Approved before proceeding
  • Work notes added automatically at each phase (start/complete/fail)
  • CR state auto-transitions: Approved → Implement → Review → Closed
  • CMDB updated within 5 minutes of new server provisioning
  • Incidents created automatically on playbook failure
  • Full audit evidence in CR: what ran, when, by whom, result
  • RBI compliance: 100% change traceability

3 Project Story

📖 The Story — The 3 AM Incident That Logged Itself

It is 3:17 AM on a Tuesday. A disk on prod-app-047 reaches 98% capacity. Splunk detects it and fires an alert. The old process: the on-call engineer's pager goes off, they log in, check the server, create a ServiceNow incident, investigate the cause, clean logs, close the incident — all while half-asleep. Total time: 45 minutes to 2 hours.

After Priya's team implemented Ansible + ServiceNow integration, the same event goes differently. Splunk fires the alert → triggers an AAP webhook → Ansible runs the disk_remediation playbook → the playbook creates a ServiceNow incident (INC0098431) with full technical details, cleans old log files, adds work notes to the incident documenting what was done, and closes the incident with resolution evidence. Total time: 4 minutes. The on-call engineer wakes up in the morning, sees the closed incident in ServiceNow with a complete audit trail, and goes back to sleep. The CISO is delighted. The RBI auditor is delighted. Priya's team sleeps better. This is that integration.

6 servicenow.itsm Collection Setup

📌 The servicenow.itsm Collection
Red Hat and ServiceNow jointly developed the servicenow.itsm Ansible certified collection. It provides modules for every major ServiceNow object type. It is available on Ansible Automation Hub and Red Hat's Private Automation Hub. The collection uses ServiceNow's REST API (Table API) behind the scenes — every module is a well-tested wrapper around REST API calls with proper error handling and idempotency.
requirements.yml — Add servicenow.itsm to your Execution EnvironmentYAML
---
collections:
  - name: servicenow.itsm
    version: ">=2.3.0"               # Use 2.3+ for full CR lifecycle support
  - name: ansible.windows           # Still needed for managed nodes
  - name: amazon.aws
Key modules in servicenow.itsm collectionYAML
# servicenow.itsm modules — complete reference

# Incident management
servicenow.itsm.incident          # Create, update, close incidents
servicenow.itsm.incident_info     # Query/read incidents (read-only)

# Change request management
servicenow.itsm.change_request    # Create, update change requests
servicenow.itsm.change_request_info  # Read/query CRs
servicenow.itsm.change_request_task  # Tasks within a CR

# CMDB
servicenow.itsm.configuration_item        # Any CMDB CI
servicenow.itsm.configuration_item_info   # Read CMDB CIs

# Problem management
servicenow.itsm.problem           # Create/update problems

# Generic (when no specific module exists)
servicenow.itsm.api               # Generic Table API calls
servicenow.itsm.api_info          # Generic read from any table

💡 AAP Custom Credential Type for ServiceNow
In production, create a Custom Credential Type in AAP: Settings → Credential Types → Add. Input: host (URL), username, password. Injector: inject as environment variables SN_HOST, SN_USERNAME, SN_PASSWORD. The servicenow.itsm modules automatically read these env vars — no need to specify connection details in every playbook task. Store the credential once in AAP, attach to any job template that needs ServiceNow access.

playbooks/servicenow/incident_automation.ymlYAML
---
# GlobalTrust Bank — Incident Auto-Creation and Remediation
# Triggered by: Splunk alert → AAP webhook → this playbook

- name: Disk Full Incident — Auto-Detect, Create Ticket, Remediate, Close
  hosts: "{{ affected_server | default('all') }}"
  become: true
  gather_facts: true

  vars:
    snow_instance:
      host: "{{ SN_HOST }}"
      username: "{{ SN_USERNAME }}"
      password: "{{ SN_PASSWORD }}"
    disk_threshold_pct: 90
    log_dirs_to_clean:
      - /var/log/nginx
      - /var/log/jboss
      - /tmp

  tasks:

    # ===== PHASE 1: CHECK DISK =====
    - name: Check current disk usage on all filesystems
      ansible.builtin.shell:
        cmd: df -h | awk 'NR>1 {gsub("%",""); if ($5 > {{ disk_threshold_pct }}) print $0}'
      register: disk_check
      changed_when: false

    - name: Set flag if disk usage is critical
      ansible.builtin.set_fact:
        disk_critical: "{{ disk_check.stdout_lines | length > 0 }}"
        disk_details: "{{ disk_check.stdout }}"

    # ===== PHASE 2: CREATE SERVICENOW INCIDENT IF CRITICAL =====
    - name: Create ServiceNow Incident for disk full alert
      servicenow.itsm.incident:
        instance: "{{ snow_instance }}"
        state: present                    # Create the incident
        caller: ansible-automation          # ServiceNow user who "raised" the incident
        short_description: "CRITICAL: Disk usage >{{ disk_threshold_pct }}% on {{ inventory_hostname }} — Auto-remediation initiated"
        description: |
          Automated incident created by Ansible AAP.

          Server: {{ inventory_hostname }}
          OS: {{ ansible_distribution }} {{ ansible_distribution_version }}
          IP Address: {{ ansible_default_ipv4.address }}
          Detected at: {{ ansible_date_time.iso8601 }}

          Disk Usage Details:
          {{ disk_details }}

          Action: Ansible automation will attempt to clean old log files.
          AAP Job URL: https://aap-ctrl.globaltrust.in/#/jobs/{{ tower_job_id }}/output
        impact: medium                     # low / medium / high
        urgency: high                      # ServiceNow calculates Priority from Impact + Urgency
        category: infrastructure
        subcategory: disk
        other:                              # Any custom ServiceNow field
          assignment_group: Linux Operations
          cmdb_ci: "{{ inventory_hostname }}"  # Link to CMDB CI
      register: snow_incident
      when: disk_critical | bool
      delegate_to: localhost               # API call runs from exec node, not managed server

    - name: Store incident number for later
      ansible.builtin.set_fact:
        incident_number: "{{ snow_incident.record.number }}"
        incident_sys_id: "{{ snow_incident.record.sys_id }}"
      when: disk_critical | bool

    - name: Log incident number to console
      ansible.builtin.debug:
        msg: "🎫 ServiceNow Incident Created: {{ incident_number }} for {{ inventory_hostname }}"
      when: disk_critical | bool

    # ===== PHASE 3: REMEDIATE =====
    - name: Clean old log files (older than 7 days)
      ansible.builtin.find:
        paths: "{{ item }}"
        age: 7d                           # Files older than 7 days
        recurse: true
        patterns: ['*.log', '*.log.gz', '*.log.*']
      register: old_logs
      loop: "{{ log_dirs_to_clean }}"
      when: disk_critical | bool

    - name: Delete old log files found above
      ansible.builtin.file:
        path: "{{ item.path }}"
        state: absent
      loop: "{{ old_logs.results | map(attribute='files') | flatten }}"
      when: disk_critical | bool
      register: cleanup_result

    - name: Check disk after cleanup
      ansible.builtin.shell:
        cmd: df -h /var
      register: disk_after
      changed_when: false

    # ===== PHASE 4: UPDATE AND CLOSE INCIDENT =====
    - name: Add work note and resolve the incident
      servicenow.itsm.incident:
        instance: "{{ snow_instance }}"
        state: resolved                    # Move to Resolved state
        number: "{{ incident_number }}"     # Reference the incident we created above
        close_code: Solved (Permanently)
        close_notes: |
          AUTOMATED RESOLUTION by Ansible AAP Job #{{ tower_job_id }}

          Action taken: Deleted log files older than 7 days from:
          - /var/log/nginx, /var/log/jboss, /tmp
          Files removed: {{ cleanup_result.results | selectattr('changed') | list | length }}

          Disk status after cleanup:
          {{ disk_after.stdout }}

          Resolution time: {{ ansible_date_time.iso8601 }}
          Ansible playbook: incident_automation.yml
          No service restart required. Monitoring for recurrence.
        other:
          work_notes: "Ansible automated remediation completed successfully on {{ ansible_date_time.iso8601 }}"
      when: disk_critical | bool
      delegate_to: localhost
Module / ParameterExplanation
servicenow.itsm.incident state: present"present" creates a new incident if it doesn't exist, or updates it if the number parameter is provided. "resolved" moves the incident to the Resolved state. "absent" closes/cancels the incident. This follows the standard Ansible module state pattern — idempotent and declarative.
instance: {host, username, password}Connection details for the ServiceNow instance. In production, these come from environment variables (SN_HOST, SN_USERNAME, SN_PASSWORD) injected by the AAP Custom Credential — you don't need the instance parameter at all if those env vars are set. But explicitly specifying it in the task makes the playbook self-documenting.
delegate_to: localhostCritical pattern for ServiceNow integration. The ServiceNow API call is made FROM the Ansible exec node, not from the managed server (prod-app-047). Using delegate_to: localhost ensures the HTTP request goes from the exec node to ServiceNow's cloud platform. The managed server's variables ({{ inventory_hostname }}, {{ ansible_default_ipv4.address }}) are still available even when delegating.
other: cmdb_ciThe other parameter passes any ServiceNow field that doesn't have a dedicated module parameter. cmdb_ci links the incident to a Configuration Item in ServiceNow CMDB — so the incident appears in the CI's history and CMDB reports show "this server had 3 incidents last month." This linkage is critical for RBI audit trails.
tower_job_idA magic variable automatically provided by AAP when a playbook runs inside the Controller. It contains the numeric ID of the current AAP job. We include it in the incident description so the ServiceNow ticket links back to the exact AAP job — allowing anyone who sees the ticket to click through and see the full playbook output. This completes the audit chain: ServiceNow → AAP → Ansible output.

9 Change Request Lifecycle Automation

playbooks/servicenow/change_request_lifecycle.ymlYAML
---
# GlobalTrust Bank — Full CR Lifecycle Automation for Linux Patching
# This is a MASTER playbook — called with CR number as a variable

- name: Change Request Lifecycle — Linux Compliance Patching
  hosts: "{{ target_servers }}"
  become: true
  gather_facts: true
  serial: "10%"

  vars:
    cr_number: "{{ change_request_number }}"  # Passed from AAP Survey or CI pipeline
    snow_instance:
      host: "{{ SN_HOST }}"
      username: "{{ SN_USERNAME }}"
      password: "{{ SN_PASSWORD }}"

  tasks:

    # ===== PRE-FLIGHT: VALIDATE CR IS APPROVED =====
    - name: Read Change Request details from ServiceNow
      servicenow.itsm.change_request_info:
        instance: "{{ snow_instance }}"
        number: "{{ cr_number }}"
      register: cr_info
      delegate_to: localhost
      run_once: true                      # Only run this once even though serial targets many servers

    - name: Fail if CR not found
      ansible.builtin.fail:
        msg: "❌ Change Request '{{ cr_number }}' not found in ServiceNow. Aborting."
      when: cr_info.records | length == 0
      run_once: true

    - name: Store CR state and validate it is Implement (-1) or Scheduled (0)
      ansible.builtin.set_fact:
        cr_state: "{{ cr_info.records[0].state }}"
        cr_sys_id: "{{ cr_info.records[0].sys_id }}"
        cr_short_desc: "{{ cr_info.records[0].short_description }}"
      run_once: true

    - name: Fail if CR is not in an approved/implement state
      ansible.builtin.fail:
        msg: "❌ BLOCKED: CR {{ cr_number }} is in state '{{ cr_state }}'. Required: 'scheduled' (-1) or 'implement' (-1). Current CR state does not allow implementation. Contact Release Manager."
      when: cr_state not in ['-1', '0', 'implement', 'scheduled']
      run_once: true

    - name: Move CR to Implement state and add start work note
      servicenow.itsm.change_request:
        instance: "{{ snow_instance }}"
        number: "{{ cr_number }}"
        state: implement                   # Move to Implement state
        other:
          work_notes: "[{{ ansible_date_time.iso8601 }}] Ansible AAP Job #{{ tower_job_id }} started implementation. Target: {{ target_servers }} ({{ ansible_play_hosts | length }} servers). Playbook: linux_compliance_patching.yml"
      delegate_to: localhost
      run_once: true

    # ===== IMPLEMENTATION: PATCH SERVERS =====
    - name: Record kernel version before patching
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_before
      changed_when: false

    - name: Apply security patches
      ansible.builtin.dnf:
        name: "*"
        state: latest
        security: true
      register: patch_result
      notify: Reboot if kernel updated

    - name: Flush handlers immediately (trigger reboot)
      ansible.builtin.meta: flush_handlers

    - name: Record kernel version after patching
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_after
      changed_when: false

    # ===== POST: UPDATE CR PER-SERVER PROGRESS =====
    - name: Add per-server work note to CR
      servicenow.itsm.change_request:
        instance: "{{ snow_instance }}"
        number: "{{ cr_number }}"
        other:
          work_notes: "[{{ ansible_date_time.iso8601 }}] ✅ {{ inventory_hostname }} patched. Kernel: {{ kernel_before.stdout }} → {{ kernel_after.stdout }}. Updates installed: {{ patch_result.results | default([]) | length }}"
      delegate_to: localhost

  handlers:
    - name: Reboot if kernel updated
      ansible.builtin.reboot:
        reboot_timeout: 600
        post_reboot_delay: 30

# ===== SECOND PLAY: CLOSE CR AFTER ALL SERVERS DONE =====
- name: Close Change Request with full implementation evidence
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Move CR to Review state with implementation summary
      servicenow.itsm.change_request:
        instance:
          host: "{{ SN_HOST }}"
          username: "{{ SN_USERNAME }}"
          password: "{{ SN_PASSWORD }}"
        number: "{{ change_request_number }}"
        state: review
        close_code: successful
        close_notes: |
          IMPLEMENTATION COMPLETE — Ansible AAP Automation

          Summary:
          - Target Environment: {{ target_servers }}
          - Total Servers Patched: {{ ansible_play_hosts_all | length }}
          - Playbook: linux_compliance_patching.yml
          - AAP Job ID: {{ tower_job_id }}
          - Implementation Start: {{ implementation_start_time }}
          - Implementation End: {{ ansible_date_time.iso8601 }}

          All servers patched and verified.
          Post-patch validation: PASSED
          RBI Compliance: ACHIEVED

          Evidence available in AAP Job output:
          https://aap-ctrl.globaltrust.in/#/jobs/{{ tower_job_id }}/output
        other:
          work_notes: "All patching completed successfully. Closing CR as per automation policy."

    - name: Close CR
      servicenow.itsm.change_request:
        instance:
          host: "{{ SN_HOST }}"
          username: "{{ SN_USERNAME }}"
          password: "{{ SN_PASSWORD }}"
        number: "{{ change_request_number }}"
        state: closed

10 CR Validation Gate — Pre-Flight Safety Check

One of the most powerful use cases: Ansible refuses to run ANY production change unless a valid, approved ServiceNow CR exists. This enforces ITIL change management through technical controls — even if an engineer tries to run a playbook manually, Ansible blocks it without an approved CR.

roles/servicenow_gate/tasks/main.yml — Reusable CR validation roleYAML
---
# This role is included at the TOP of every production playbook
# Add to any playbook: roles: - servicenow_gate

- name: SNOW GATE — Validate Change Request before any production action
  block:

    - name: Check if CR number was provided
      ansible.builtin.fail:
        msg: "❌ BLOCKED: No change_request_number variable provided. All production changes require a ServiceNow CR. Use AAP Survey to provide the CR number."
      when: change_request_number is not defined or change_request_number | length == 0
      run_once: true

    - name: Validate CR format (must start with CR or CHG)
      ansible.builtin.fail:
        msg: "❌ BLOCKED: '{{ change_request_number }}' is not a valid CR number. Must start with 'CR' or 'CHG' (e.g., CR0012345 or CHG0045678)."
      when: not (change_request_number | regex_search('^(CR|CHG)[0-9]{7}$'))
      run_once: true

    - name: Query ServiceNow for CR details
      servicenow.itsm.change_request_info:
        instance:
          host: "{{ SN_HOST }}"
          username: "{{ SN_USERNAME }}"
          password: "{{ SN_PASSWORD }}"
        number: "{{ change_request_number }}"
      register: cr_validation
      delegate_to: localhost
      run_once: true

    - name: Fail if CR does not exist
      ansible.builtin.fail:
        msg: "❌ BLOCKED: CR {{ change_request_number }} does not exist in ServiceNow. Verify the CR number and try again."
      when: cr_validation.records | length == 0
      run_once: true

    - name: Extract CR state for validation
      ansible.builtin.set_fact:
        cr_current_state: "{{ cr_validation.records[0].state }}"
        cr_type: "{{ cr_validation.records[0].type }}"
        cr_risk: "{{ cr_validation.records[0].risk }}"
      run_once: true

    - name: Fail if CR is not in an approved state
      ansible.builtin.fail:
        msg: "❌ BLOCKED: CR {{ change_request_number }} is in state '{{ cr_current_state }}'. Ansible only proceeds when CR is 'scheduled' or 'implement'. Current state indicates the change has not been approved by CAB."
      when: cr_current_state not in ['scheduled', 'implement', '-1', '0']
      run_once: true

    - name: GATE PASSED — log to console and add work note
      ansible.builtin.debug:
        msg: "✅ GATE PASSED: CR {{ change_request_number }} is in state '{{ cr_current_state }}'. Proceeding with automation."
      run_once: true

  rescue:
    - name: ServiceNow query failed — block execution for safety
      ansible.builtin.fail:
        msg: "❌ BLOCKED: Cannot validate CR {{ change_request_number }} — ServiceNow is unreachable or query failed. Aborting for safety. Error: {{ ansible_failed_result.msg | default('unknown') }}"

17 Interview Preparation

Q1. How does Ansible integrate with ServiceNow for Change Management?
We use the servicenow.itsm certified Ansible collection which provides purpose-built modules for every ServiceNow object. The integration is bidirectional. Before any production change, the playbook calls servicenow.itsm.change_request_info to read the CR and validate it is in Approved/Scheduled state — if not, the playbook fails with a clear error message. This enforces that every Ansible production run must have an approved CR. During execution, the playbook calls servicenow.itsm.change_request to update the CR state to "Implement" and add work notes at each milestone — start, per-server completion, and end. After successful execution, the playbook transitions the CR to "Review" and then "Closed" with close_code=successful and detailed implementation evidence in close_notes. On failure, Ansible creates a ServiceNow Incident automatically and closes the CR as unsuccessful. All API calls use delegate_to: localhost because they go from the exec node to ServiceNow's API — not to the managed servers. In GlobalTrust Bank, this integration made us 100% RBI-compliant on change management from day one of implementation.
Q2. What is CMDB and how do you keep it in sync with Ansible?
CMDB (Configuration Management Database) is the ServiceNow repository that tracks all IT assets — servers, databases, applications, network devices — and their relationships. It is the single source of truth for the IT estate. The problem in most organisations: CMDB goes stale because new servers are provisioned but nobody updates ServiceNow manually. With Ansible, we added a CMDB update play to every cloud provisioning playbook. After a new EC2 instance or VMware VM is created and configured, Ansible automatically calls servicenow.itsm.configuration_item with state: present to create or update the CI (Configuration Item) in CMDB. We populate: hostname, IP address, OS version, CPU count, RAM, environment (production/staging), AWS instance ID, patch group, and provisioning date. When a server is decommissioned, the same module with state: absent removes it from CMDB. The result is a CMDB that is always within 5 minutes of reality — automatically maintained by the same automation that provisions the infrastructure. RBI's CMDB audit went from 23% stale entries to under 2% in the first quarter after implementation.
Q3. How do you create ServiceNow incidents automatically when Ansible playbooks fail?
Two methods, often used together. Method 1 — AAP Notification Templates: in AAP Controller, configure a Notification Template of type Webhook that sends a POST to the ServiceNow incident table API when a job fails. AAP provides Jinja2 variables like {{ job.name }}, {{ job.status }}, {{ job.explanation }} in the notification body. This creates an incident in ServiceNow within seconds of any AAP job failure — completely automatic, no playbook code needed. Method 2 — Playbook rescue block: within the playbook itself, use a block/rescue pattern. The rescue section runs only when tasks in the block fail, and it calls servicenow.itsm.incident to create an incident with the specific failure context. This is more detailed — it can include which specific task failed, the error output, affected server name. We use both in GlobalTrust Bank: AAP Notifications for catch-all failures, and rescue blocks for critical production operations where we want detailed incident context. The key parameter on the incident module is other: work_notes: "{{ ansible_failed_result.msg }}" to include the actual Ansible error in the incident work notes.
Q4. Explain run_once: true and delegate_to: localhost — why do ServiceNow tasks need both?
ServiceNow API tasks need both for different reasons. delegate_to: localhost means "run this task on the Ansible execution node, not on the managed server." When Ansible targets 300 Linux servers with serial processing, each task normally runs on each managed server. But ServiceNow API calls go to ServiceNow's cloud — they should never run on the managed server. delegate_to: localhost redirects the API call to the exec node, but the task's variables ({{ inventory_hostname }}, {{ ansible_default_ipv4.address }}) still come from the current managed server being processed — so you get the right server's data in the API call. run_once: true means "run this task only once regardless of how many servers are in the inventory." For CR validation (checking that the CR is approved), we only need to validate once — not 300 times. For closing the CR after patching, we only want one final CR update, not one update per server. Without run_once, the CR validation task would run 300 times, creating 300 API calls to ServiceNow just to validate one CR number. Combine both: delegate_to: localhost + run_once: true = API call runs once, from the exec node, with the right variables.
