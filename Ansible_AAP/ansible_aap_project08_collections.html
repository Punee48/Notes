GlobalTrust Bank has 15 DevOps engineers writing Ansible across 6 teams. Without Collections, every team duplicates the same roles, every team uses different variable names for the same concepts, and every new engineer starts from scratch. Collections solve this — one reusable, versioned, tested package of automation that every team installs and uses the same way.

1 Project Overview

📌 What Is an Ansible Collection?
Think of an Ansible Collection like a Python pip package, but for Ansible. Just like pip install requests gives every Python developer the same HTTP library, ansible-galaxy collection install globaltrust.banking gives every DevOps engineer at GlobalTrust Bank the same set of tested roles, custom modules, filter plugins, and inventory plugins — all in one versioned package. Collections solve the biggest problem in enterprise Ansible: code duplication and inconsistency across teams. Before Collections, every team had its own "user management role" with different variable names, different handlers, different tested scenarios. With a shared Collection, there is one user management role, one variable schema, one set of tests — and every team uses it.

🏷️ Collection Naming Convention

💡 Collection Namespace.Name Format — Very Important
Every Collection has a two-part name: namespace.collection_name. For example: amazon.aws (AWS Collection), servicenow.itsm (ServiceNow Collection), ansible.windows (Windows Collection). The namespace is typically the organisation or vendor name. GlobalTrust Bank's namespace is globaltrust and the Collection is named banking — so the full name is globaltrust.banking. When you use a module from a Collection in a playbook, you use the Fully Qualified Collection Name (FQCN): globaltrust.banking.provision_user. This removes all ambiguity about which module you are using.

2 Business Problem

🚨 The Duplication Problem — 6 Teams, 6 Different "linux_user" Roles
GlobalTrust Bank has 6 DevOps teams: Core Banking, Internet Banking, Risk Analytics, Infrastructure, Security, and Cloud Platform. Before Collections, every team had their own Ansible repository with their own versions of common roles. When the Security team changed the SSH configuration standard in 2023, they updated their own ssh_hardening role but forgot to tell the other 5 teams. 4 months later, an RBI cybersecurity audit found that 40% of servers had non-compliant SSH configurations. The audit finding was clear: lack of centralized Ansible standards and reuse. The corrective action: build a shared Collection that all teams use, publish it to Private Automation Hub, and enforce its use via AAP Job Template configuration.
✅ After globaltrust.banking Collection
  • One ssh_hardening role — all teams use the same version
  • Security team updates collection → all teams get update on next install
  • New engineer onboards: ansible-galaxy collection install globaltrust.banking
  • Collection version pinned in each project's requirements.yml
  • 100% SSH compliance on next audit cycle
  • Custom modules (provision_user, validate_cr) reduce 50-line tasks to 5
  • Private Automation Hub — collection not available outside corporate network
  • Execution Environments pre-baked with collection — no runtime installs

6 Using Collections in Playbooks — FQCN

📌 FQCN — Fully Qualified Collection Name
The FQCN format is: namespace.collection.module_name. For example: amazon.aws.ec2_instance, servicenow.itsm.incident, globaltrust.banking.provision_user. Always use FQCN in production playbooks. It removes all ambiguity — if two collections have a module with the same name, FQCN tells Ansible exactly which one to use. The older shorthand method using the collections: keyword at the play level is still valid but not recommended in new playbooks.
Using collections in playbooks — FQCN vs collections: keywordYAML
---
# ===== RECOMMENDED: FQCN (Fully Qualified Collection Name) =====
- name: Provision new banking application server
  hosts: localhost
  gather_facts: false
  tasks:
    - name: Provision EC2 instance
      amazon.aws.ec2_instance:           # FQCN: namespace.collection.module
        name: prod-banking-app-01
        instance_type: m5.xlarge
        state: running

    - name: Create SNOW Incident
      servicenow.itsm.incident:          # Different collection, same FQCN pattern
        state: present
        short_description: Server provisioned

    - name: Use bank's custom user provisioning module
      globaltrust.banking.provision_user: # Our own custom module
        username: arjun.sharma
        employee_id: GT-1234

---
# ===== OLDER STYLE: collections: shorthand (less recommended)
- name: Example with collections keyword
  hosts: all
  collections:                          # Declare collection namespace at play level
    - amazon.aws
    - globaltrust.banking
  tasks:
    - name: Now you can use short module names
      ec2_instance:                       # Ansible searches amazon.aws first (order matters!)
        name: test
    - name: Risk: if two collections have ec2_instance, wrong one might be used
      provision_user:                     # Searched in amazon.aws first, then globaltrust.banking
        username: test
# Conclusion: Always use FQCN for clarity and safety

---
# ===== Using Collection ROLES in playbooks =====
- name: Apply Linux baseline from bank collection
  hosts: linux_servers
  become: true
  roles:
    - role: globaltrust.banking.linux_baseline  # Role from collection
      vars:
        baseline_ntp_servers: ['ntp1.globaltrust.in', 'ntp2.globaltrust.in']
    - role: globaltrust.banking.ssh_hardening
    - role: globaltrust.banking.splunk_uf
      vars:
        server_role: appserver

7 requirements.yml — Declare Your Dependencies

💡 requirements.yml Is Like package.json for Ansible
Just like a Node.js project has package.json listing all npm dependencies, every Ansible project should have a requirements.yml listing all required collections (and optionally roles). When a new engineer clones the repo and runs ansible-galaxy collection install -r requirements.yml, they get exactly the right versions of all dependencies. AAP Execution Environments also use this file to pre-bake collections into Docker images (Project 09).
requirements.yml — Production collection dependency fileYAML
---
# GlobalTrust Bank — Ansible Collection Requirements
# Install: ansible-galaxy collection install -r requirements.yml
# Update:  ansible-galaxy collection install -r requirements.yml --upgrade

collections:

  # ===== Red Hat Certified Collections =====
  - name: ansible.posix              # firewalld, sysctl, authorized_key etc.
    version: ">=1.5.0"

  - name: ansible.windows            # win_updates, win_service etc.
    version: ">=2.3.0"

  - name: community.general          # slack, mail, ini_file etc.
    version: ">=8.0.0"

  # ===== Cloud Collections =====
  - name: amazon.aws
    version: ">=6.5.0,<7.0.0"        # Semantic version range: >=6.5 but NOT 7.x

  - name: azure.azcollection
    version: ">=2.0.0"

  # ===== ITSM / Monitoring =====
  - name: servicenow.itsm
    version: ">=2.3.0"

  # ===== Internal Bank Collection — from Private Automation Hub =====
  - name: globaltrust.banking
    version: ">=1.2.0,<2.0.0"        # Use 1.x only — 2.0 may have breaking changes
    source: https://hub.globaltrust.in/api/galaxy/  # Override source for internal collection

  # ===== Install from Git (for development/testing of unreleased versions) =====

8 Private Automation Hub — Internal Collection Registry

📌 Why GlobalTrust Bank Uses Private Automation Hub
Ansible Galaxy is public — anyone can download collections from it, but it also means internet access is needed at runtime. GlobalTrust Bank's production servers are in a network-isolated environment — they cannot reach the internet. Private Automation Hub (part of AAP 2.4) is an on-premises mirror and registry. It serves two purposes: (1) it mirrors approved public collections from Ansible Galaxy so the bank's automation can use them without internet access, and (2) it hosts the bank's own internal globaltrust.banking collection which must not be publicly accessible.
ansible.cfg — Point Ansible to Private Hub as the default serverYAML
# ansible.cfg — Configure Private Automation Hub as collection source
[galaxy]
server_list = automation_hub, galaxy_fallback

[galaxy_server.automation_hub]
url=https://hub.globaltrust.in/api/galaxy/
auth_url=https://hub.globaltrust.in/api/galaxy/v3/auth/token/
token={{ lookup('env', 'AUTOMATION_HUB_TOKEN') }}
# Token stored in AAP Credential, injected as env variable

[galaxy_server.galaxy_fallback]
url=https://galaxy.ansible.com
# Fallback to public galaxy if collection not in Private Hub
# In fully air-gapped environments, remove this section
Publishing workflow — From GitLab CI to Private HubBASH

10 galaxy.yml — The Collection's Identity File

📌 galaxy.yml Is the Heart of Every Collection
The galaxy.yml file defines everything about the collection: its name, version, author, description, license, and dependencies on other collections. It is the equivalent of package.json in Node.js or setup.py in Python. When you run ansible-galaxy collection build, Ansible reads galaxy.yml to name the output tarball. When you publish, galaxy.yml version determines which version is registered in the Hub. Changing the version number in galaxy.yml and rebuilding is how you release a new version.
galaxy.yml — globaltrust.banking collection manifestYAML
---
# galaxy.yml — Collection metadata for globaltrust.banking
namespace: globaltrust                  # Must match the directory name: globaltrust/banking/
name: banking                          # Collection name
version: 1.2.0                         # Semantic Versioning: MAJOR.MINOR.PATCH
readme: README.md

authors:
  - Priya Nair <priya.nair@globaltrust.in>
  - Arjun Sharma <arjun.sharma@globaltrust.in>

description: GlobalTrust Bank's official Ansible Collection — banking-specific automation roles, custom modules, and filter plugins. Internal use only.

license: [GPL-2.0-or-later]           # Or proprietary for internal use

tags: [banking, linux, windows, monitoring, itsm, security]

dependencies:                          # This collection requires these others to work
  ansible.posix: ">=1.5.0"
  community.general: ">=8.0.0"
  ansible.windows: ">=2.0.0"
  servicenow.itsm: ">=2.3.0"
# When someone installs globaltrust.banking, these dependencies install automatically

repository: https://gitlab.globaltrust.in/ansible/banking-collection
documentation: https://ansible-docs.globaltrust.in/collections/globaltrust/banking
issues: https://gitlab.globaltrust.in/ansible/banking-collection/issues

build_ignore:                          # Do NOT include these in the built tarball
  - .git
  - .gitignore
  - tests/                             # Tests not needed at runtime
  - *.retry
  - .venv/
FieldExplanation
version: 1.2.0Semantic versioning (SemVer): MAJOR.MINOR.PATCH. MAJOR change = breaking changes (variable renames, module removals). MINOR change = new features, backward compatible (new role added). PATCH change = bug fixes, backward compatible (typo fix in task). When users pin >=1.0.0,<2.0.0 in requirements.yml, they get all 1.x updates but are protected from 2.0 breaking changes. Never change a published version — always bump the version and republish.
dependenciesCollections that globaltrust.banking depends on. When someone installs globaltrust.banking, ansible-galaxy automatically also installs ansible.posix, community.general, etc. at the specified versions. This is similar to npm dependencies — you declare what you need, ansible-galaxy resolves the full dependency graph. Be careful: circular dependencies will cause install failures.
build_ignoreFiles and directories excluded from the built tarball. Tests are excluded because they add size without value at runtime. The .git directory must be excluded — it contains full version history and would bloat the tarball. Think of it like .npmignore or .gitignore but for collection builds.

12 Filter Plugins — Custom Jinja2 Filters

💡 What Is a Filter Plugin?
Jinja2 filters transform data inside templates and variable expressions. Built-in Ansible filters include | upper, | default('value'), | select(), | to_json. A custom filter plugin lets you add bank-specific data transformations — like masking credit card numbers for audit logs, or formatting account IDs according to the bank's internal format. Filters are Python functions decorated with FilterModule.
plugins/filter/banking_filters.py — Custom Jinja2 filtersPYTHON
#!/usr/bin/python
# plugins/filter/banking_filters.py
# GlobalTrust Bank — Custom Ansible Filter Plugins
# Part of globaltrust.banking collection
# Usage: "{{ card_number | globaltrust.banking.mask_card_number }}"

from __future__ import (absolute_import, division, print_function)
__metaclass__ = type


def mask_card_number(card_number):
    """
    Mask a credit/debit card number for audit log safety.
    Shows only last 4 digits: **** **** **** 1234
    
    Usage in playbook: "{{ transaction.card_number | globaltrust.banking.mask_card_number }}"
    """
    card_str = str(card_number).replace(' ', '').replace('-', '')
    if len(card_str) < 4:
        return '****'
    visible_digits = card_str[-4:]
    masked_groups = ['****'] * ((len(card_str) - 4) // 4)
    return ' '.join(masked_groups + [visible_digits])


def format_account_id(raw_id, branch_code='MUM'):
    """
    Format an account number to bank's standard: BRANCH-YEAR-SEQNUM
    Example: 12345 → MUM-2024-012345
    
    Usage: "{{ account_id | globaltrust.banking.format_account_id(branch_code='BLR') }}"
    """
    from datetime import datetime
    year = datetime.now().year
    return f"{branch_code}-{year}-{str(raw_id).zfill(6)}"


def gt_to_bool(value):
    """
    Convert bank system YES/NO strings to Python bool.
    Bank legacy systems use 'Y'/'N' not True/False.
    
    Usage: "{{ legacy_field | globaltrust.banking.gt_to_bool }}"
    """
    if isinstance(value, bool):
        return value
    return str(value).strip().upper() in ('Y', 'YES', 'TRUE', '1', 'ENABLED')


class FilterModule(object):
    """GlobalTrust Bank custom Ansible filter plugins."""

    def filters(self):
        return {
            'mask_card_number': mask_card_number,
            'format_account_id': format_account_id,
            'gt_to_bool': gt_to_bool,
        }
# FilterModule.filters() returns a dict: filter_name → Python function
# This registers the functions as Jinja2 filters in Ansible
Using custom filters in playbooksYAML
---
- name: Audit log task using bank custom filters
  hosts: localhost
  vars:
    transaction_card: "4532015112830366"
    new_account_id: 7823

    - name: Check legacy field
      ansible.builtin.debug:
        msg: "Active: {{ legacy_status | globaltrust.banking.gt_to_bool }}"
      # Output: "Active: True"

13 Custom Module — provision_user.py

📌 When to Write a Custom Module
Write a custom module when: (1) you find yourself repeating the same 30+ task sequence across playbooks — a module collapses it to one task. (2) you need to interact with a bank-specific internal API that has no existing Ansible module. (3) you need complex validation logic that is hard to express in Ansible YAML. In GlobalTrust Bank, the provision_user module wraps the bank's HR system API — creating a user in Ansible previously required 8 separate tasks (create user, set password, configure groups, set expiry, update HR API, send email, create SNOW ticket, update CMDB). The custom module does all of this in one task, with proper idempotency.
plugins/modules/provision_user.py — Complete custom modulePYTHON
#!/usr/bin/python
# plugins/modules/provision_user.py
# GlobalTrust Bank — Custom Ansible Module for User Provisioning
# Usage: globaltrust.banking.provision_user

from __future__ import absolute_import, division, print_function
__metaclass__ = type

DOCUMENTATION = r'''
---
module: provision_user
short_description: Provision a user in GlobalTrust Bank systems
description:
  - Creates or removes a system user and synchronizes with the bank's HR system.

from ansible.module_utils.basic import AnsibleModule
import subprocess
import pwd


def user_exists(username):
    try:
        pwd.getpwnam(username)
        return True
    except KeyError:
        return False


def run_module():
    module_args = dict(
        username=dict(type='str', required=True),
        employee_id=dict(type='str', required=True),
        state=dict(type='str', default='present', choices=['present', 'absent']),
        groups=dict(type='list', elements='str', default=[]),
        expiry_days=dict(type='int', default=0),
        hr_api_url=dict(type='str', default='https://hr-api.globaltrust.in'),
    )

    result = dict(changed=False, user_created=False, uid=None, message='')
    module = AnsibleModule(argument_spec=module_args, supports_check_mode=True)

    username = module.params['username']
    state = module.params['state']
    groups = module.params['groups']

    # ===== IDEMPOTENCY CHECK =====
    exists = user_exists(username)

    if state == 'present' and exists:
        # User already exists — check if anything needs updating
        user_info = pwd.getpwnam(username)
        result['uid'] = user_info.pw_uid
        result['message'] = f"User {username} already exists (uid={user_info.pw_uid}). No changes needed."
        module.exit_json(**result)          # Exit with changed=False — idempotent

    if state == 'absent' and not exists:
        result['message'] = f"User {username} does not exist. Nothing to remove."
        module.exit_json(**result)          # Already absent — no change

    # ===== CHECK MODE: Don't actually make changes =====
    if module.check_mode:
        result['changed'] = True
        result['message'] = f"CHECK MODE: Would {'create' if state=='present' else 'remove'} user {username}"
        module.exit_json(**result)

    # ===== MAKE THE CHANGE =====
    if state == 'present':
        cmd = ['useradd', '--create-home', '--shell', '/bin/bash']
        if groups:
            cmd.extend(['--groups', ','.join(groups)])
        cmd.append(username)

        rc, stdout, stderr = module.run_command(cmd)
        if rc != 0:
            module.fail_json(msg=f"Failed to create user {username}: {stderr}")

        user_info = pwd.getpwnam(username)
        result['changed'] = True
        result['user_created'] = True
        result['uid'] = user_info.pw_uid
        result['message'] = f"User {username} created successfully (uid={user_info.pw_uid})"

    elif state == 'absent':
        rc, stdout, stderr = module.run_command(['userdel', '--remove', username])
        if rc != 0:
            module.fail_json(msg=f"Failed to remove user {username}: {stderr}")
        result['changed'] = True
        result['message'] = f"User {username} removed successfully"

    module.exit_json(**result)


def main():
    run_module()


if __name__ == '__main__':
    main()
Module ComponentExplanation
DOCUMENTATION, EXAMPLES, RETURNThese three string constants are mandatory for every well-written Ansible module. DOCUMENTATION describes the module and all its parameters (becomes the output of ansible-doc globaltrust.banking.provision_user). EXAMPLES shows real usage in YAML format. RETURN describes what the module returns in its result dictionary. Without these, ansible-doc shows nothing useful and your module is unusable for other engineers.
AnsibleModule(supports_check_mode=True)Check mode (ansible-playbook --check) is a dry-run — show what WOULD change without actually changing anything. Setting supports_check_mode=True tells Ansible this module supports it. Inside the module, check module.check_mode and return early with changed=True (reporting what would have changed) without executing the actual commands. If supports_check_mode=False and someone runs --check, Ansible skips the module entirely.
Idempotency checkBefore making any change, we check if the desired state is already achieved (user already exists for state=present, user already absent for state=absent). If the current state matches the desired state, we call module.exit_json with changed=False immediately. This is the core of idempotency — running the same playbook 10 times should give the same result with no unneeded changes. All built-in Ansible modules follow this pattern.
module.run_command()The correct way to run shell commands in an Ansible module. Never use subprocess.check_output or os.system directly — module.run_command handles error detection, returns (rc, stdout, stderr), respects check mode, and integrates with Ansible's error handling system. Check the return code (rc == 0 means success) and call module.fail_json if the command fails.

19 Interview Preparation

Q1. What is an Ansible Collection? How is it different from a role?
An Ansible Role is a structured way to organize tasks, handlers, variables, templates, and files for one specific operational concern — like "configure nginx" or "deploy JBoss." A role is a single unit of automation logic. An Ansible Collection is a packaging format that bundles multiple roles, custom modules, filter plugins, inventory plugins, lookup plugins, and even complete playbooks together into one versioned, distributable package. Think of it this way: a role is like a single function, and a collection is like a library that contains many functions, utilities, and helper tools — all from the same vendor or team. When Red Hat ships the Amazon Web Services modules for Ansible, they ship them as the amazon.aws Collection — not as individual roles. The collection contains ec2_instance, s3_bucket, iam_role, and hundreds of other modules in one package with one version number and one install command. In GlobalTrust Bank, we built the globaltrust.banking Collection that contains 4 roles (linux_baseline, ssh_hardening, windows_hardening, splunk_uf), 2 custom modules (provision_user, validate_cr), 3 filter plugins, and 1 inventory plugin — all in one versioned package. Any team can install it with one command and immediately has access to all the bank's standardised automation.
Q2. What is FQCN and why should you always use it?
FQCN stands for Fully Qualified Collection Name. The format is namespace.collection.module_name. For example, amazon.aws.ec2_instance is the FQCN for the EC2 instance module in the amazon.aws collection. The alternative — the shorthand method using the collections: keyword at the play level — lets you write just ec2_instance: without the full namespace. The problem with shorthand is ambiguity. If your play declares two collections that both have a module called ec2_instance (unlikely but possible), Ansible uses the first one in the list — silently. With FQCN, there is zero ambiguity — exactly one module matches and it is explicit in the task definition. FQCN also makes playbooks self-documenting: anyone reading servicenow.itsm.incident immediately knows this is from the ServiceNow collection. With just incident:, they would have to check the play-level collections list. In production automation — especially in regulated environments like banking where every automation action is audited — clarity and traceability are non-negotiable. We enforce FQCN in code review for the globaltrust.banking collection and all playbooks that use it.
Q3. How do you write a custom Ansible module? What are the must-have components?
A custom Ansible module is a Python file placed in the plugins/modules/ directory of a Collection. The six must-have components are: (1) the DOCUMENTATION string — a YAML-formatted string that describes the module, all its parameters with types and descriptions, and whether they are required. This is what ansible-doc displays. (2) the EXAMPLES string — working YAML examples of the module's usage. (3) the RETURN string — documents what the module returns in its result dictionary. (4) the module_args dict passed to AnsibleModule — defines all accepted parameters, their types, defaults, and choices. (5) the idempotency check — before making any change, check if the desired state is already achieved and return early with changed=False if so. This is the most important correctness property. (6) support for check mode by setting supports_check_mode=True in AnsibleModule and checking module.check_mode before executing commands. The module must always call either module.exit_json() (success) or module.fail_json() (failure) — never raise exceptions or use sys.exit(). We wrote the provision_user module for GlobalTrust Bank which creates system users and synchronises with the HR system. What was previously 8 tasks in every user-management playbook is now one task. The module is idempotent — if the user already exists, it reports changed=False and exits immediately. It supports check mode — running the playbook with --check shows what would happen without actually creating any users.
Q4. What is Private Automation Hub and why did you use it instead of Ansible Galaxy?
Private Automation Hub is an on-premises Collection registry that ships with Red Hat Ansible Automation Platform. It serves as both a mirror of curated public Collections from Ansible Galaxy and a registry for the organisation's own internal Collections. GlobalTrust Bank uses Private Automation Hub for three reasons. Security: the bank's internal globaltrust.banking collection contains proprietary automation logic that must not be publicly accessible — it can only be published to and downloaded from the bank's internal Hub. Network isolation: production servers are in a network-isolated environment with no direct internet access — they cannot reach galaxy.ansible.com at runtime. The Private Hub is inside the corporate network, accessible to all servers. Content curation: before any public Collection (like amazon.aws or servicenow.itsm) is available in the Hub, the security team reviews and approves it. Engineers cannot use unapproved Collections. This prevents a scenario where someone installs a malicious community Collection without oversight. The configuration is simple — in ansible.cfg, set the galaxy server URL to the Private Hub address and provide an API token. Ansible treats it exactly like Galaxy, just at a different URL. Execution Environments also pull from Private Hub during image builds — the Collection is baked into the container image so no download happens at job runtime.
Q5. How do you version a Collection and what is semantic versioning in Ansible?
Ansible Collections use semantic versioning — MAJOR.MINOR.PATCH format. PATCH version (1.0.0 → 1.0.1) is for bug fixes — something was wrong and is now fixed, but all interfaces remain the same. No user needs to change their playbooks. MINOR version (1.0.1 → 1.1.0) is for new features that are backward compatible — new role added, new module added, new filter added. Existing playbooks that don't use the new feature are unaffected. MAJOR version (1.x.x → 2.0.0) signals breaking changes — a role was renamed, a variable name changed, a module parameter was removed. Users who upgrade must update their playbooks. In GlobalTrust Bank, teams specify their dependency in requirements.yml as version: ">=1.0.0,<2.0.0" — they get all 1.x updates automatically (including security fixes and new features) but are protected from 2.0 breaking changes. The workflow to release a new version: update the version field in galaxy.yml, update CHANGELOG.rst, commit, push a git tag (v1.2.0), and the GitLab CI pipeline automatically builds the tarball and publishes it to Private Hub. Published versions are immutable — once 1.2.0 is published, it cannot be changed. If a bug is found in 1.2.0, release 1.2.1 with the fix. This is the same contract as PyPI or npm packages.
