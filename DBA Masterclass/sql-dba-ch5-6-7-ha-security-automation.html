High Availability & Disaster Recovery

Design systems that never sleep. Master Always On Availability Groups, Failover Clustering, Log Shipping, and build ShopCart India's zero-downtime architecture.

ShopCart India just got funded — ₹50 crore Series A. The investors' first question to the CTO: "What's your uptime guarantee?" The CTO comes to you: "We need 99.99% uptime. The database can't be the single point of failure anymore."

Right now, ShopCart runs on ONE SQL Server. If it goes down — for a patch, a crash, a power cut — the entire platform is dead. Chapter 4 (backup/restore) gets you back in 40 minutes. But investors won't accept 40 minutes. They want seconds.

🎯 Goal: Design ShopCart India's HA/DR stack. Understand every solution the JD lists — Always On AGs, Failover Clustering, Log Shipping — and know which to use when.
1
HA vs DR — What's the Difference?
⚡

High Availability (HA)

Minimises planned & unplanned downtime on the SAME site. Failover happens automatically in seconds. Goal: near-zero RTO. Examples: Always On AG, Failover Cluster Instance (FCI).

🌍

Disaster Recovery (DR)

Protects against SITE-LEVEL disasters (data centre fire, city flood). Secondary is in a different location. Failover is manual. Goal: data survives a catastrophe. Examples: Log Shipping, AG with async replica in another region.

🎯

ShopCart's Stack

Primary: Always On AG (2 nodes, same data centre) → automatic failover in <30 sec. DR: Async AG replica in Mumbai (primary in Bengaluru) → manual failover, RPO ~seconds behind.

📊

The SLA Math

99.9% = 8.7 hr downtime/year. 99.99% = 52 min/year. 99.999% = 5.26 min/year. Always On AG (auto failover) can achieve 99.99%. Without HA: a single patch restart = 0.1% downtime hit.

2
The 4 HA/DR Solutions — Compared

Always On AG

★ RECOMMENDED
  • Database-level (not instance)
  • 1 Primary + up to 8 Secondaries
  • Synchronous = RPO ~0, RTO <30s
  • Asynchronous for cross-region DR
  • Readable secondaries (offload reports)
  • Requires WSFC + Enterprise/Standard

Failover Cluster (FCI)

INSTANCE-LEVEL
  • Entire SQL Server instance fails over
  • Shared storage (SAN/Azure shared disk)
  • Single copy of data (no data redundancy)
  • Protects against OS/hardware failure
  • Classic "active-passive" cluster
  • No readable secondary possible

Log Shipping

SIMPLE DR
  • Copies log backups to secondary server
  • RPO = log backup interval (15–60 min)
  • Works on ALL editions (incl. Standard)
  • Secondary in STANDBY = readable
  • Manual failover only
  • No automatic failover

Transactional Replication

DISTRIBUTION
  • Table/article level (not full DB)
  • Near real-time read replica
  • Used for scaling reads, not HA
  • Publisher → Distributor → Subscriber
  • Complex to set up and maintain
  • Not a primary DR solution

Always On Availability Groups — Deep Dive
📄 16_always_on_ag_setup.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 16_always_on_ag_setup.sql
-- CONTEXT: Two SQL Server nodes on Windows Server Failover Cluster (WSFC)
-- Node 1 (Primary): SHOPCART-SQL-01  →  Bengaluru data centre
-- Node 2 (Secondary): SHOPCART-SQL-02 →  Bengaluru data centre (HA)
-- Node 3 (Async Secondary): SHOPCART-SQL-03 → Mumbai DC (DR)
-- PRE-REQUISITES: WSFC created, SQL Server AG feature enabled
-- ════════════════════════════════════════════════════════════════

-- ══ STEP 1: Enable Always On on each SQL Server node ═════════════
-- This is done via SSMS → SQL Server Configuration Manager
-- OR via PowerShell (shown in Chapter 7):
-- Enable-SqlAlwaysOn -ServerInstance "SHOPCART-SQL-01" -Force
-- After enabling, SQL Server restarts. Then run SQL below.

-- ══ STEP 2: Create the Availability Group on the PRIMARY ════════
USE master;
GO

CREATE AVAILABILITY GROUP ShopCart_AG
WITH
(
    AUTOMATED_BACKUP_PREFERENCE = SECONDARY,
    -- AUTOMATED_BACKUP_PREFERENCE = SECONDARY: backups run on the secondary replica
    -- by default, freeing the primary for transactional load.
    -- Options: PRIMARY (always primary), SECONDARY (prefer secondary),
    --          SECONDARY_ONLY, NONE (backup can run on either).
    HEALTH_CHECK_TIMEOUT         = 30000,
    -- 30000 ms = 30 seconds. If the primary doesn't respond to health checks
    -- for 30 seconds, WSFC considers it failed and triggers auto-failover.
    DB_FAILOVER                  = ON,
    -- DB_FAILOVER = ON: if ANY database in the AG becomes unhealthy,
    -- the entire AG fails over. Ensures app always sees all DBs together.
    FAILURE_CONDITION_LEVEL      = 3
    -- FAILURE_CONDITION_LEVEL controls WHAT triggers automatic failover:
    -- 1 = Only SQL Server service down
    -- 2 = Level 1 + SQL Server not responding (default)
    -- 3 = Level 2 + critical system errors (recommended)
    -- 4 = Level 3 + moderate errors
    -- 5 = Any qualified failure conditions
)
FOR DATABASE ShopCartDB
-- FOR DATABASE: which databases join this AG. Can list multiple DBs.
-- Requirements: DB must be in FULL recovery model AND have a full backup taken.
REPLICA ON
    -- Define each server that participates in this AG:
    N'SHOPCART-SQL-01'
    WITH (
        ENDPOINT_URL          = N'TCP://SHOPCART-SQL-01.shopcart.local:5022',
        -- ENDPOINT_URL = the database mirroring endpoint on this server.
        -- SQL Server AG uses a dedicated TCP endpoint (port 5022 by default)
        -- for replica-to-replica communication (log shipping, health checks).
        AVAILABILITY_MODE     = SYNCHRONOUS_COMMIT,
        -- SYNCHRONOUS_COMMIT: Primary waits for secondary to CONFIRM log hardened
        -- before acknowledging the commit to the application.
        -- RESULT: RPO = 0 (zero data loss on failover). RTO < 30 seconds.
        -- COST: adds latency to every transaction (RTT to secondary).
        -- Use for same-site or low-latency secondary.
        --
        -- ASYNCHRONOUS_COMMIT: Primary does NOT wait for secondary.
        -- RESULT: Near-zero write latency. But RPO > 0 on failover.
        -- Use for cross-region DR replicas where network latency is high.
        FAILOVER_MODE         = AUTOMATIC,
        -- AUTOMATIC: WSFC automatically fails over to this replica if primary fails.
        -- MANUAL: Only manual failover (used for async replicas = DR nodes).
        SECONDARY_ROLE (ALLOW_CONNECTIONS = ALL)
    ),
    N'SHOPCART-SQL-02'
    WITH (
        ENDPOINT_URL          = N'TCP://SHOPCART-SQL-02.shopcart.local:5022',
        AVAILABILITY_MODE     = SYNCHRONOUS_COMMIT,
        FAILOVER_MODE         = AUTOMATIC,
        SECONDARY_ROLE (ALLOW_CONNECTIONS = READ_ONLY)
        -- READ_ONLY on secondary: allows reporting/analytics queries to run
        -- against the secondary, offloading the primary.
        -- Application connects via Listener (below) with ApplicationIntent=ReadOnly.
    ),
    N'SHOPCART-SQL-03'
    WITH (
        ENDPOINT_URL          = N'TCP://SHOPCART-SQL-03.shopcart.local:5022',
        AVAILABILITY_MODE     = ASYNCHRONOUS_COMMIT,
        -- ASYNC for Mumbai DR node — network latency is 40ms, unacceptable for SYNC.
        FAILOVER_MODE         = MANUAL,
        SECONDARY_ROLE (ALLOW_CONNECTIONS = READ_ONLY)
    );
GO

-- ══ STEP 3: Create the AG Listener ═══════════════════════════════
ALTER AVAILABILITY GROUP ShopCart_AG
ADD LISTENER N'ShopCart-Listener'
(
    WITH IP
    (
        (N'10.0.1.50', N'255.255.255.0')
    ),
    PORT = 1433
);
-- AG LISTENER = a virtual network name + IP address that ALWAYS points to the
-- current PRIMARY replica (even after failover).
-- Application connection string: "Server=ShopCart-Listener,1433;Database=ShopCartDB"
-- After failover: SQL-01 becomes secondary, SQL-02 becomes primary.
-- The Listener IP automatically points to SQL-02. App reconnects seamlessly.
-- THIS IS THE KEY: apps never need to change their connection string after failover.
GO

-- ══ STEP 4: Join secondary replicas to the AG ════════════════════
-- Run this on SHOPCART-SQL-02 and SHOPCART-SQL-03:

ALTER AVAILABILITY GROUP ShopCart_AG JOIN;
ALTER AVAILABILITY GROUP ShopCart_AG GRANT CREATE ANY DATABASE;
-- GRANT CREATE ANY DATABASE: allows the AG to automatically create the database
-- on the secondary after seeding. Required for automatic seeding.
GO

-- ══ MONITOR AG health ════════════════════════════════════════════
SELECT
    ag.name                     AS AGName,
    ar.replica_server_name       AS ServerName,
    ars.role_desc               AS Role,
    ars.operational_state_desc   AS State,
    ars.connected_state_desc    AS Connected,
    ars.synchronization_health_desc AS SyncHealth,
    ISNULL(CAST(drs.log_send_queue_size/1024.0 AS DECIMAL(10,1)),0)  AS LogSendQueueMB,
    -- log_send_queue_size: unsent log bytes on primary → secondary.
    -- HIGH value = secondary is falling behind = increased RPO risk.
    ISNULL(CAST(drs.redo_queue_size/1024.0 AS DECIMAL(10,1)),0)      AS RedoQueueMB
    -- redo_queue_size: log received but not yet applied on secondary.
    -- HIGH = secondary is applying changes slowly (CPU pressure on secondary?).
FROM      sys.availability_groups           ag
JOIN      sys.availability_replicas          ar   ON ag.group_id   = ar.group_id
JOIN      sys.dm_hadr_availability_replica_states ars ON ar.replica_id = ars.replica_id
LEFT JOIN sys.dm_hadr_database_replica_states  drs  ON ar.replica_id = drs.replica_id
ORDER BY ag.name, ars.role_desc;

-- ══ Manual Failover (planned maintenance) ═════════════════════════
-- Run on the TARGET secondary you want to become primary:
ALTER AVAILABILITY GROUP ShopCart_AG FAILOVER;
-- FAILOVER (no FORCE) = graceful planned failover. Zero data loss.
-- Both replicas must be SYNCHRONOUS and SYNCHRONIZED before this works.
-- Use for: OS patching the primary, planned maintenance.
-- FORCE FAILOVER WITH ALLOW DATA LOSS → emergency only for async replicas.

Log Shipping — Simple DR on Standard Edition
📄 17_log_shipping.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 17_log_shipping.sql
-- SCENARIO: ShopCart Standard Edition — no Always On AG.
-- Log Shipping = automated pipeline of log backups from Primary to Secondary.
-- Pipeline: Primary → Backup job → Share → Copy job → Restore job → Secondary
-- ════════════════════════════════════════════════════════════════

-- ══ PRIMARY SERVER: Configure log shipping ═══════════════════════
USE master;
EXEC sp_add_log_shipping_primary_database
    @database                   = N'ShopCartDB',
    @backup_directory           = N'\\SHOPCART-SQL-01\LogShipping',
    -- Shared network path — secondary server must be able to READ this path.
    @backup_share               = N'\\SHOPCART-SQL-01\LogShipping',
    @backup_job_name            = N'LSBackup_ShopCartDB',
    @backup_retention_period    = 4320,
    -- 4320 minutes = 3 days. Keep 3 days of log backups on the share.
    -- Adjust based on how far behind the secondary is allowed to get.
    @backup_threshold           = 60,
    -- Alert if no backup in 60 minutes (our RPO target).
    @threshold_alert_enabled    = 1,
    @history_retention_period   = 5760,  -- 4 days history in msdb
    @backup_compression         = 1;    -- compress log backups on the share
GO

-- ══ SECONDARY SERVER: Configure copy + restore ════════════════════
EXEC sp_add_log_shipping_secondary_primary
    @primary_server   = N'SHOPCART-SQL-01',
    @primary_database = N'ShopCartDB',
    @backup_source_directory = N'\\SHOPCART-SQL-01\LogShipping',
    @backup_destination_directory = N'D:\LogShippingLocal',
    -- COPY job moves files from the share to a LOCAL folder on the secondary.
    -- WHY local? Restore is faster reading from local disk than network share.
    @copy_job_name    = N'LSCopy_ShopCartDB',
    @restore_job_name = N'LSRestore_ShopCartDB',
    @file_retention_period  = 4320,
    @overwrite        = 1;

EXEC sp_add_log_shipping_secondary_database
    @secondary_database        = N'ShopCartDB',
    @primary_server            = N'SHOPCART-SQL-01',
    @primary_database          = N'ShopCartDB',
    @restore_delay             = 0,
    -- @restore_delay = 0 minutes = apply log backups immediately.
    -- Advanced use: set to 60 min to create a "delayed DR" — protection against
    -- logical errors (accidental DELETE). If you set 60 min delay, you have
    -- a 60-minute window to catch mistakes before they reach the secondary.
    @restore_mode              = 1,
    -- 0 = NORECOVERY (secondary stays in restoring, not readable)
    -- 1 = STANDBY (secondary is readable between restores = offline warm standby)
    @disconnect_users          = 1,
    -- Disconnect reporting users during each log restore (brief interruption).
    @restore_threshold         = 45,
    @threshold_alert_enabled   = 1,
    @history_retention_period  = 5760;
GO

-- ══ MONITOR log shipping status ═══════════════════════════════════
SELECT
    primary_server, primary_database, secondary_server,
    last_backup_file, last_backup_date,
    last_copied_file, last_copied_date,
    last_restored_file, last_restored_date,
    DATEDIFF(MINUTE, last_restored_date, GETDATE()) AS MinutesBehind
FROM msdb.dbo.log_shipping_monitor_secondary;
-- MinutesBehind = how far behind the secondary is from the primary.
-- Alert if this exceeds your RPO threshold (e.g., > 30 minutes).
Interview Preparation — Chapter 5

HA/DR Interview Questions

Q1 · AG Modes

Q: "What is the difference between synchronous and asynchronous commit in Always On AGs?"

A: In synchronous commit mode, the primary replica waits until the secondary has hardened (written to disk) the log record before acknowledging the transaction to the client. This guarantees zero data loss (RPO = 0) on failover because the secondary is always fully caught up. The trade-off is added latency on every write — the round-trip time between primary and secondary adds to transaction duration. For same data centre replicas (1–5ms RTT), this is acceptable. In asynchronous commit mode, the primary sends log records to the secondary but does NOT wait for confirmation — it acknowledges the client immediately. This means lower write latency, but on failover you could lose committed transactions that hadn't reached the secondary yet (RPO > 0). Use async for cross-region DR replicas where network latency would be too high for sync commit.

Q2 · Log Shipping vs AG

Q: "When would you choose Log Shipping over Always On AGs?"

A: Log Shipping is the right choice when you're on SQL Server Standard Edition (Always On AGs require Enterprise on versions before 2016, and Standard Edition AGs are limited to 2 nodes/1 database per AG). Log Shipping is also simpler to configure, requires no Windows Server Failover Cluster infrastructure, works across different SQL Server versions (useful during version upgrades), and supports a deliberate restore delay which provides protection against logical errors like accidental mass deletes — a feature AGs don't natively offer. The limitations: RPO is limited to the log backup interval (minimum ~5–15 minutes), failover is always manual, and the secondary in STANDBY is briefly unavailable during each log restore.

  3. Simulate Log Shipping manually: Take a log backup on ShopCartDB. Copy the .trn file to another folder. Restore it on the same instance as a different database name using WITH STANDBY. Now query the "secondary" — it should be readable!

🎯 Goal: Implement defence-in-depth security for ShopCartDB — no developer touches production PII, all access is logged, data is encrypted at rest, and sensitive columns are masked.
1
Security Layers — Defence in Depth
1

Authentication — Who Are You?

SQL Server Logins (server-level identity). Windows Login = Active Directory account. SQL Login = username + password stored in SQL Server. Always prefer Windows Auth in corporate environments — no passwords to manage, integrated with AD.

2

Authorisation — What Can You Do?

Database Users (linked to Logins) + Roles (groups of permissions). Grant permissions to ROLES, never to individual users. RBAC (Role-Based Access Control) — the foundation of least-privilege access.

3

Encryption — Protecting Data at Rest & In Transit

TDE (Transparent Data Encryption) = encrypts the entire .mdf and .ldf file. Nobody can steal the disk and read the data. TLS = encrypts data in transit (network). Always Encrypted = client-side encryption for the most sensitive columns.

4

Auditing — Who Did What and When?

SQL Server Audit writes events to a file, Windows Event Log, or Application Log. Captures: logins, schema changes, data access, permission changes. Required for PCI-DSS, HIPAA, and India's DPDP Act compliance.

Logins, Users & Role-Based Access Control
📄 18_security_rbac.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 18_security_rbac.sql
-- PURPOSE: Build ShopCart's role-based access control hierarchy
-- PRINCIPLE: Least Privilege — users get ONLY what they need.
-- ════════════════════════════════════════════════════════════════

-- ══ LAYER 1: Server-Level Logins ═════════════════════════════════
-- A LOGIN = identity at the SQL SERVER level (access to the instance).
-- Without a login, you cannot connect to SQL Server at all.

USE master;
GO

-- Application service account (your Node.js app connects as this)
CREATE LOGIN shopcart_app
    WITH PASSWORD = N'$h0pC@rt#AppSvc2024!',
    DEFAULT_DATABASE   = ShopCartDB,
    CHECK_POLICY       = ON,
    -- CHECK_POLICY = ON: applies Windows password complexity rules.
    -- Must have uppercase, lowercase, digit, special char.
    -- In production, use Windows Integrated Auth (no password) when possible.
    CHECK_EXPIRATION   = ON;
    -- CHECK_EXPIRATION = ON: password expires per Windows domain policy.
    -- Prevents stale passwords from living forever.

-- DBA team (Windows group — all DBAs in AD group get access)
CREATE LOGIN [SHOPCART\DBA-Team] FROM WINDOWS;
-- FROM WINDOWS = Windows/AD login. Authenticates via Kerberos.
-- Brackets [] allow spaces and special chars in login names.
-- The DBA team Windows group members all authenticate without SQL passwords.

-- Read-only analyst login
CREATE LOGIN shopcart_analyst
    WITH PASSWORD = N'An@lyst#Read2024!',
    DEFAULT_DATABASE = ShopCartDB,
    CHECK_POLICY = ON;
GO

-- ══ LAYER 2: Database Users (linked to Logins) ═══════════════════
-- A USER = identity within a SPECIFIC DATABASE.
-- Login → User mapping. One Login can map to multiple DBs.

USE ShopCartDB;
GO

CREATE USER shopcart_app       FOR LOGIN shopcart_app;
CREATE USER shopcart_analyst   FOR LOGIN shopcart_analyst;
CREATE USER [SHOPCART\DBA-Team]  FOR LOGIN [SHOPCART\DBA-Team];
GO

-- ══ LAYER 3: Custom Database Roles ═══════════════════════════════
-- Never grant permissions to individual users.
-- Create ROLES, grant permissions to roles, add users to roles.
-- WHY: When a person changes job, remove from role — one operation.
-- Adding a new person: add to role — they inherit all permissions.

CREATE ROLE ShopCart_AppRole;
-- App role: INSERT/UPDATE/DELETE on transactional tables, SELECT on all.

CREATE ROLE ShopCart_ReadOnly;
-- Analyst role: SELECT only. No DML allowed.

CREATE ROLE ShopCart_ReportRole;
-- Report role: SELECT on specific views only. Not raw tables.
GO

-- ══ Grant permissions TO ROLES (not to users) ════════════════════

-- Application role: full DML on all tables
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA::dbo  TO ShopCart_AppRole;
-- GRANT ... ON SCHEMA::dbo = grants permission on ALL objects in the dbo schema.
-- Much better than granting table by table. New tables auto-inherit the grant.
-- SCHEMA::dbo is the container — granting at schema level is the best practice.

GRANT EXECUTE ON SCHEMA::dbo          TO ShopCart_AppRole;
-- EXECUTE = can run stored procedures. App only calls SPs, not raw table queries.

-- Read-only role: SELECT only, explicitly DENY sensitive columns
GRANT SELECT ON SCHEMA::dbo            TO ShopCart_ReadOnly;
DENY  SELECT ON dbo.Payments(Amount)   TO ShopCart_ReadOnly;
-- Column-level DENY: even with SELECT on schema, the analyst CANNOT see
-- the Amount column in Payments. DENY overrides all GRANT permissions.
-- WHY: Analysts need to see who paid (OrderID, Method) but not how much.

-- Add users to roles
ALTER ROLE ShopCart_AppRole   ADD MEMBER shopcart_app;
ALTER ROLE ShopCart_ReadOnly  ADD MEMBER shopcart_analyst;
ALTER ROLE db_owner           ADD MEMBER [SHOPCART\DBA-Team];
-- db_owner = built-in role with full control of this database.
-- DBA team gets db_owner in ShopCartDB. But NOT sysadmin (server-level).
-- Principle of least privilege: DBA manages ShopCartDB, not the whole server.
GO

TDE, Data Masking & Row-Level Security
📄 19_encryption_masking.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 19_encryption_masking.sql
-- PURPOSE: TDE + Dynamic Data Masking + Row-Level Security
-- ════════════════════════════════════════════════════════════════

-- ══ PART A: Transparent Data Encryption (TDE) ════════════════════
-- TDE encrypts the ENTIRE database file (.mdf, .ldf, tempdb).
-- Protects against: stolen physical disk, stolen backup file.
-- Transparent = SQL Server decrypts automatically on legitimate access.
-- The encryption key hierarchy: Service Master Key → Database Master Key → Certificate → DEK

USE master;
GO

-- Step 1: Create a master key (encrypts the certificate)
CREATE MASTER KEY ENCRYPTION BY PASSWORD = N'M@sterK3y#ShopC@rt!';
-- The Database Master Key (DMK) in master DB is the ROOT of the key hierarchy.
-- This password is CRITICAL — if you lose it and the service master key is gone,
-- you CANNOT decrypt data. Store it in a secure vault (Azure Key Vault, HSM).
GO

-- Step 2: Create a certificate (protects the DEK)
CREATE CERTIFICATE ShopCart_TDE_Cert
    WITH SUBJECT = N'ShopCart India TDE Certificate',
    EXPIRY_DATE  = N'20261231';
-- EXPIRY_DATE: Set to 2+ years out. Plan to rotate before expiry.
-- CRITICAL: BACK UP THIS CERTIFICATE IMMEDIATELY after creation.
-- If the certificate is lost and you restore a TDE-encrypted backup to another server,
-- you CANNOT restore it without the certificate. It's permanently unreadable.
-- BACKUP CERTIFICATE ShopCart_TDE_Cert TO FILE = 'C:\Secure\TDE_Cert.cer'
-- WITH PRIVATE KEY (FILE = 'C:\Secure\TDE_Cert.pvk',
--                  ENCRYPTION BY PASSWORD = 'SecureVaultPassword');
GO

-- Step 3: Create the Database Encryption Key (DEK) in ShopCartDB
USE ShopCartDB;
GO
CREATE DATABASE ENCRYPTION KEY
    WITH ALGORITHM = AES_256
    ENCRYPTION BY SERVER CERTIFICATE ShopCart_TDE_Cert;
-- AES_256 = Advanced Encryption Standard, 256-bit key. Industry standard.
-- The DEK encrypts/decrypts all data pages as they're written/read.
-- ENCRYPTION BY SERVER CERTIFICATE = the DEK is itself encrypted by the certificate.
-- This key hierarchy means the raw data key is never exposed in plaintext.
GO

-- Step 4: Enable TDE on the database
ALTER DATABASE ShopCartDB
SET ENCRYPTION ON;
-- This starts the encryption scan. SQL Server encrypts ALL data pages in the background.
-- The database remains FULLY ONLINE during encryption — zero downtime.
-- Monitor progress:
SELECT
    db.name,
    dek.encryption_state_desc,
    dek.percent_complete,
    dek.key_algorithm,
    dek.key_length
FROM  sys.dm_database_encryption_keys  dek
JOIN  sys.databases                   db  ON dek.database_id = db.database_id;
-- percent_complete: shows 0–100% during initial encryption.
-- encryption_state_desc: UNENCRYPTED → ENCRYPTION IN PROGRESS → ENCRYPTED
GO

-- ══ PART B: Dynamic Data Masking (DDM) ═══════════════════════════
-- DDM hides sensitive data from non-privileged users AT QUERY TIME.
-- The real data is still stored — just displayed as masked values.
-- No code changes in application needed. Configured at column level.

ALTER TABLE Customers
ALTER COLUMN Email
    ADD MASKED WITH (FUNCTION = 'email()');
-- email() mask function: shows first letter + 'XXX' + '@' + domain.
-- e.g., 'arjun.sharma@gmail.com' → 'aXXX@XXXX.com'
-- Unmasked by users with UNMASK permission (DBAs, App user).
-- Masked for: shopcart_analyst, support staff, etc.

ALTER TABLE Customers
ALTER COLUMN Phone
    ADD MASKED WITH (FUNCTION = 'partial(0,"XXXXXX",4)');
-- partial(prefix_len, padding, suffix_len):
-- partial(0,"XXXXXX",4) = show 0 chars from start + XXXXXX + last 4 chars.
-- '9876543210' → 'XXXXXX3210'

ALTER TABLE Payments
ALTER COLUMN Amount
    ADD MASKED WITH (FUNCTION = 'default()');
-- default() mask: returns 0 for numeric types, 'XXXX' for strings, '1900-01-01' for dates.
-- Analysts see Amount = 0 for every payment. DBAs and app see real values.

-- Grant UNMASK to users who should see real data
GRANT UNMASK TO shopcart_app;
-- App service account sees real data (must process payments).
-- shopcart_analyst does NOT get UNMASK → always sees masked values.
GO

-- ══ PART C: Row-Level Security (RLS) ════════════════════════════
-- RLS filters rows based on WHO is running the query.
-- Use case: ShopCart has 5 regional managers. Each should ONLY see
-- orders from their own city — even if they query the same Orders table.

CREATE SCHEMA Security;
GO

CREATE FUNCTION Security.fn_OrderCityFilter
    (@ShippingCity NVARCHAR(100))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
(
    SELECT 1 AS fn_result
    WHERE
        USER_NAME() = 'shopcart_app'      -- App sees all rows
        OR IS_MEMBER('db_owner') = 1    -- DBAs see all rows
        OR @ShippingCity = USER_NAME()  -- Managers see only their city
);
-- USER_NAME() = returns the current database username.
-- If the "Bengaluru manager" user is named 'Bengaluru', they see only rows
-- where ShippingCity = 'Bengaluru'. Elegant and transparent.
-- WITH SCHEMABINDING = function schema-bound to prevent object drops.
GO

CREATE SECURITY POLICY OrderCityPolicy
ADD FILTER PREDICATE Security.fn_OrderCityFilter(ShippingCity)
    ON dbo.Orders,
ADD BLOCK PREDICATE  Security.fn_OrderCityFilter(ShippingCity)
    ON dbo.Orders
WITH (STATE = ON);
-- FILTER PREDICATE: silently removes rows the user shouldn't see from SELECT results.
-- BLOCK PREDICATE: prevents INSERT/UPDATE with values the user can't see.
-- WITH (STATE = ON): activate the policy immediately.
-- Now: SELECT * FROM Orders returns only rows matching the user's city filter.
-- The filter is INVISIBLE to the user — they don't see it, can't bypass it.

Interview Preparation — Chapter 6

Security Interview Questions

Q1 · TDE

Q: "Explain how TDE works and what it protects against. What are its limitations?"

A: TDE encrypts the database files (.mdf, .ndf, .ldf) and tempdb at the storage level using AES-256 encryption. The encryption is transparent — SQL Server automatically decrypts pages when reading them into the buffer pool and re-encrypts when writing to disk. It protects against physical theft of disk drives or backup media — a stolen .bak file without the TDE certificate is completely unreadable. The limitations: TDE doesn't protect data in memory (buffer pool) or in transit (use TLS/SSL for that). A legitimate user who has SQL Server access can still run SELECT * FROM Customers and see real data — TDE is at-rest protection only. For column-level protection of data even from authenticated users, Always Encrypted is the right tool.

Q2 · Login vs User

Q: "What is the difference between a SQL Server Login and a Database User?"

A: A Login is a server-level security principal that allows authentication to the SQL Server instance. Without a Login, you cannot connect to the server at all. A Database User is a database-level principal that is mapped to a Login and controls what that Login can do within a specific database. The relationship is: one Login can map to Users in multiple databases, but each database has its own User with its own permissions. This separation is important: the DBA might have a sysadmin Login (server-level) but in a specific database, the mapping could restrict them to read-only. Contained database users (introduced in SQL 2012) break this model — they authenticate directly to the database without a server-level Login, which is useful for AG failover scenarios.

SELECT @SQL += ''ALTER INDEX ['' + i.name + ''] ON ['' + OBJECT_NAME(i.object_id) + ''] ''

           ELSE ''REORGANIZE'' END + '';''

Interview Preparation — Chapter 7

Automation Interview Questions

Q1 · SQL Agent

Q: "A SQL Agent job failed last night. Walk me through how you diagnose it."

A: First, I check the Job History in SSMS (Agent → Jobs → right-click → View History) or query msdb.dbo.sysjobhistory to find the failing step and its error message. The error message tells me 80% of the time what's wrong — could be a T-SQL error, permission issue, or resource problem. Then I check the step's command — if it's T-SQL, I copy it and run it manually to reproduce the error. If it's a PowerShell step, I check the PowerShell error output in the job history. For intermittent failures, I look at the timing — did it run at an unusual time? Was there blocking (check sys.dm_exec_requests history via Query Store)? Was a backup running simultaneously (resource contention)? Finally, I check the Windows Event Log and SQL Server Error Log for any server-level events around the failure time.

Q2 · PowerShell Automation

Q: "How would you automate checking that all production databases have had a full backup in the last 24 hours across 10 SQL Server instances?"

A: With dbatools, it's a few lines: Get-DbaDbBackupHistory -SqlInstance $AllServers -Type Full | Where-Object {$_.End -lt (Get-Date).AddHours(-24)} | Select SqlInstance, Database, End. This queries each server's msdb.dbo.backupset through dbatools and returns any database whose last full backup is older than 24 hours. I'd wrap this in a scheduled PowerShell script that runs at 8 AM, and if the output contains any rows (missed backups), it sends an alert email via Send-DbaMail. This is more reliable than trusting SQL Agent jobs because it validates the backup actually happened — not just that the job ran.
