Chapter 1

The Database World — Architecture & First Steps

Before writing a single line of SQL, we need to understand what a database actually is and why SQL Server works the way it does. Everything you learn later will click better once you have this mental model.

Imagine you're hired as a DBA at ShopCart India — a fast-growing e-commerce company based in Bengaluru. They sell electronics, clothes, and daily essentials to 2 million customers.

Your manager says: "We store everything — every order, every payment, every product — in Microsoft SQL Server. Your first job is to understand this system so well that when it goes down at 2 AM, you can fix it before customers even notice."

Before you can administer anything, you need to understand what's actually happening inside SQL Server. Think of it like becoming a mechanic — you don't just press the gas pedal; you understand the engine.

🎯 Our goal for this chapter: Install SQL Server, understand its architecture, and connect to it — like an engineer, not a user.

1.1 — How SQL Server Actually Works (Mental Model)

SQL Server is not just a place to store data. It is a complex system with multiple layers, each doing a specific job. Here are the 6 components you need to permanently wire into your brain:

🧠

SQL OS Layer

SQL Server has its own mini OS-within-an-OS. It manages CPU threads, memory, and I/O independently from Windows. This is why SQL Server can have 256 GB RAM all to itself.

📦

Storage Engine

Responsible for reading and writing data to the actual .mdf and .ldf files on disk. All your tables, indexes, and stored procedures live in these files.

🔍

Query Processor

Takes your T-SQL query, compiles it, generates an execution plan, and executes it. This is where your "SELECT * FROM Orders" gets translated to actual disk reads.

💾

Buffer Pool (Memory)

SQL Server caches hot data pages in RAM. When you run a query, it checks RAM first (cache hit), then disk (cache miss). A good DBA maximizes cache hit ratio.

📝

Transaction Log (.ldf)

Every change to data is written here FIRST before touching the data file. This is how SQL Server can roll back transactions and recover from crashes. The foundation of ACID.

🔒

Lock Manager

When two queries touch the same row, the Lock Manager ensures they don't corrupt each other. This is why you'll see deadlocks and blocking in production environments.

💡
Why this matters in your interview: When an interviewer asks "What happens when SQL Server starts?" — you describe these layers. When they ask about performance issues, you connect it back to Buffer Pool and the Query Processor. This is senior-level thinking.

1.2 — Database Files: What Lives Where

Every database in SQL Server is made up of physical files on disk. Understanding these is fundamental for backup, recovery, and performance work.

🗄️

.mdf — Primary Data File

Stores actual data — your tables, indexes, views, stored procedures. Every database has exactly one .mdf file. ShopDB.mdf is where all your orders live.

📁

.ndf — Secondary Data File

Optional extra data files. When your .mdf is on one disk and you want to spread I/O, you add .ndf files on other disks. Used in large enterprise systems.

📋

.ldf — Log Data File

The transaction log. EVERY INSERT, UPDATE, DELETE is written here first. A DBA must manage log growth carefully — an out-of-space log = your database stops working.

1.3 — The 4 System Databases (You MUST Know These)

Database What It Does Why a DBA Cares
master The brain. Stores all logins, server configs, and metadata about every database. If master is corrupt, SQL Server won't start. Always back it up after any config change.
tempdb Temporary workspace. Sort operations, temp tables (#tables), row versioning all happen here. Heavy workloads can fill tempdb causing failures. Monitor constantly. Place on fast SSD.
model Template for new databases. Every new DB you create starts as a copy of model. If you want every new DB to have a specific setting by default — change model.
msdb The scheduler. SQL Agent jobs, backup history, and mail configs live here. Your automated backup jobs run via SQL Agent, so msdb must be healthy.
⚠️
Classic Interview Trap: "What happens if tempdb is full?" — Answer: SQL Server will throw error 1101/1105, queries that need temp space will fail, but the server itself keeps running. The fix: add a file, clear sessions, or add disk space.
Hands-On Lab 1

Installing SQL Server 2022 — Every Step Explained

We'll install SQL Server Developer Edition (free, full-featured). Think of this as setting up your local ShopCart India lab environment.

🏗️ Real-World Project · ShopCart India

Project Context: Building the Foundation

ShopCart India needs a new database server. You're setting up the development environment that will mirror production. Every configuration decision you make here maps to real DBA decisions: file placement, memory settings, and service accounts all matter.

Step 1 — Download SQL Server 2022 Developer Edition

⬇️ Download & Install Sequence

  1. Go to: https://www.microsoft.com/en-us/sql-server/sql-server-downloads
  2. Choose Developer edition — It's FREE and has ALL Enterprise features. Perfect for learning.
  3. Also download SSMS (SQL Server Management Studio): https://aka.ms/ssmsfullsetup — This is your GUI tool to interact with SQL Server.
  4. Run the SQL Server installer → Choose Custom installation (not Basic). This way you understand every option.

Step 2 — Critical Installation Choices (These Matter in Production)

Installation Screen What You Choose Why It Matters
Instance Configuration Named Instance: SHOPCART In production, servers often run multiple SQL instances (Dev/Prod/UAT). Named instances let you identify them. Connection: .\SHOPCART
Service Accounts Use NT SERVICE\MSSQL$SHOPCART SQL Server should never run as LocalSystem or Administrator. Least-privilege service accounts are a security requirement in the JD.
Authentication Mode Mixed Mode (Windows + SQL) Windows Auth for humans (more secure), SQL Auth for applications. Real production environments use both.
Data Directories Data: D:\SQLData, Log: E:\SQLLogs, Backup: F:\SQLBackup Separating data, logs, and backups to different disks prevents I/O contention and disk full situations from killing the server.
TempDB Files Set count to 4 (for a 4-core machine) Multiple tempdb files reduce contention on the PFS/GAM pages. Best practice = 1 file per core, max 8.
Max Server Memory Leave ~20% for Windows (e.g., 12GB on 16GB RAM → set max to 12288 MB) Without a max memory limit, SQL Server takes ALL RAM and Windows OS starts paging, causing the entire server to slow down.

Step 3 — Your First T-SQL Commands After Installation

Open SSMS, connect to .\SHOPCART. Now run these commands to verify your installation and configure the server properly.

📄 01_server_configuration.sql T-SQL 
-- ═══════════════════════════════════════════════════════════════
-- FILE: 01_server_configuration.sql
-- PURPOSE: Verify installation + apply baseline DBA configurations
-- CONTEXT: This is Day 1 setup for ShopCart India SQL Server
-- ═══════════════════════════════════════════════════════════════

-- ── STEP 1: Check which version of SQL Server we installed ───────
SELECT @@VERSION;
-- @@VERSION is a GLOBAL VARIABLE (marked by @@) built into SQL Server
-- It returns a string like: "Microsoft SQL Server 2022 (RTM) - 16.0.1000.6..."
-- WHY: Confirm you installed the right version. In production, version
-- determines which features you can use and which patches to apply.

-- ── STEP 2: Check the SQL Server service name ────────────────────
SELECT @@SERVICENAME;
-- Returns "SHOPCART" (our named instance)
-- WHY: Useful when scripting monitoring or automation — you need to know
-- the exact service name to restart it via PowerShell or Windows Services.

-- ── STEP 3: Set maximum server memory (CRITICAL DBA TASK) ────────
EXEC sp_configure 'show advanced options', 1;
-- sp_configure = a built-in system stored procedure for server settings
-- 'show advanced options' = the NAME of the configuration setting
-- 1 = the VALUE we're setting it to (1 = ON, 0 = OFF)
-- WHY: By default, advanced settings like memory are hidden.
-- We must enable this FIRST before we can change them.

RECONFIGURE;
-- RECONFIGURE applies the sp_configure change immediately.
-- Without this line, the change is staged but NOT applied.
-- WHY: SQL Server separates "set a value" from "apply the value" 
-- for safety — you won't accidentally apply a bad config instantly.

EXEC sp_configure 'max server memory (MB)', 12288;
-- 'max server memory (MB)' = sets the MAXIMUM RAM SQL Server can use
-- 12288 = 12 GB in megabytes (12 × 1024 = 12288)
-- WHY: Without this, SQL Server will grab ALL available RAM (e.g., 15.9 GB
-- out of 16 GB), leaving nothing for Windows, which causes the OS to 
-- page memory to disk = catastrophic performance degradation.
-- RULE OF THUMB: Leave 20% or 4GB (whichever is larger) for the OS.

RECONFIGURE;

EXEC sp_configure 'show advanced options', 0;
-- Turn advanced options back OFF as a security/cleanliness practice.
-- WHY: "Least privilege" mentality — don't leave the door open.

RECONFIGURE;

-- ── STEP 4: Enable two critical server features ───────────────────
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

EXEC sp_configure 'optimize for ad hoc workloads', 1;
-- WHAT: When enabled, SQL Server stores only a small stub in the plan cache
-- for the FIRST execution of an ad hoc query. The full plan is only cached
-- if the query runs a second time.
-- WHY: Without this, every unique one-off query bloats the plan cache in RAM.
-- In an e-commerce system like ShopCart, you get millions of slightly-different
-- ad hoc queries from the ORM layer — this WILL cause memory pressure. Enable it.

EXEC sp_configure 'backup compression default', 1;
-- WHAT: Makes all database backups compressed by default.
-- WHY: Compressed backups are 60–70% smaller. For ShopCart's 500 GB database,
-- this means backups take less disk space and finish faster (less I/O).
-- The JD specifically asks about backup strategies — this is an easy win.

RECONFIGURE;
EXEC sp_configure 'show advanced options', 0;
RECONFIGURE;

-- ── STEP 5: Verify all current configurations ────────────────────
EXEC sp_configure;
-- With no arguments, sp_configure LISTS all configuration settings.
-- Look for: max server memory = 12288, backup compression default = 1
-- WHY: Always VERIFY your changes. A DBA never assumes; they confirm.

-- ── STEP 6: Check all databases on this instance ─────────────────
SELECT
    name              AS DatabaseName,
    database_id       AS ID,
    state_desc        AS Status,
    recovery_model_desc AS RecoveryModel,
    CONVERT(VARCHAR, create_date, 103) AS CreatedOn
FROM sys.databases
ORDER BY database_id;
-- sys.databases = a SYSTEM CATALOG VIEW — a built-in virtual table that shows
--   metadata about all databases on this SQL Server instance.
-- name = the database name (master, tempdb, model, msdb = your 4 system DBs)
-- state_desc = ONLINE means healthy, SUSPECT = corruption, RESTORING = being restored
-- recovery_model_desc = FULL, BULK_LOGGED, or SIMPLE
--   FULL = full transaction log maintained (needed for point-in-time recovery)
--   SIMPLE = log truncated automatically (less recovery options)
--   WHY THIS MATTERS: For a production e-commerce DB like ShopCart,
--   you MUST use FULL recovery model to be able to restore to any point in time.
-- CONVERT(VARCHAR, create_date, 103) = formats the date as DD/MM/YYYY
--   103 is a SQL Server date style code for UK/India format
Word-by-Word Breakdown

Understanding the Key Commands

Code Fragment What It Does Why It Exists
EXEC sp_configure Calls the built-in system stored procedure that manages server-level settings. The only official way to change server-wide configs. Direct registry edits are unsupported.
'show advanced options', 1 Unlocks hidden settings in sp_configure. Without this, ~70 settings are invisible. SQL Server hides dangerous settings by default. You must explicitly say "I know what I'm doing."
RECONFIGURE Applies the staged sp_configure change to the running server without a restart. In production, you can't restart SQL Server to apply settings. RECONFIGURE applies them live.
@@VERSION Global variable (double-@ = server-scoped variable). Returns SQL Server version string. You need to know the exact version for patch planning, feature availability, and support tickets.
sys.databases A catalog view (built-in virtual table) in the sys schema showing all databases. SQL Server exposes its own metadata through catalog views. This is how you script health-checks.
recovery_model_desc Column from sys.databases showing FULL, SIMPLE, or BULK_LOGGED recovery mode. Determines what backup operations are available and how granularly you can recover data after a failure.
Lab 1B — Project Start

Creating the ShopCart Database — The Right Way

Most tutorials teach you to hit "New Database" in SSMS. A real DBA scripted everything. Here's how to create a properly configured production database with T-SQL.

📄 02_create_shopcart_database.sql T-SQL 
-- ═══════════════════════════════════════════════════════════════
-- FILE: 02_create_shopcart_database.sql
-- PURPOSE: Create ShopCart India production database with
--          enterprise-grade settings
-- ═══════════════════════════════════════════════════════════════

USE master;
-- USE master = switches context to the master database.
-- WHY: CREATE DATABASE must be run from master. You can't create a database
-- while you're already inside a user database. master is the control center.

GO
-- GO is NOT a T-SQL command — it is a batch separator signal to SSMS/sqlcmd.
-- It tells the tool: "send everything above this line to SQL Server as one batch."
-- WHY: Certain commands like USE, CREATE DATABASE, CREATE PROCEDURE must be
-- in their own batch (alone before a GO). This prevents "you can't mix these" errors.

-- ── Check if database already exists before creating ─────────────
IF EXISTS (
    SELECT 1 FROM sys.databases WHERE name = 'ShopCartDB'
)
BEGIN
    PRINT 'Database ShopCartDB already exists. Dropping it...';
    ALTER DATABASE ShopCartDB SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
    -- SET SINGLE_USER = Kick all existing connections OUT and block new ones.
    -- WITH ROLLBACK IMMEDIATE = don't wait for transactions to finish; kill them now.
    -- WHY: DROP DATABASE will fail if anyone is connected to it.
    -- In production you'd never do this without a maintenance window!
    DROP DATABASE ShopCartDB;
END
GO

-- ── Create the database with explicit file specifications ─────────
CREATE DATABASE ShopCartDB
ON PRIMARY
(
    NAME     = ShopCartDB_Data,
    -- NAME = the LOGICAL name of this file. Used in T-SQL commands.
    -- Think of it as a variable name you'll use in scripts like RESTORE, SHRINK.

    FILENAME = 'C:\SQLData\ShopCartDB.mdf',
    -- FILENAME = the physical path on disk. In a real server: D:\SQLData\
    -- WHY separate path from default? Putting data on a dedicated fast disk
    -- (separate from OS) prevents disk I/O bottlenecks and OS disk full issues.

    SIZE     = 512MB,
    -- SIZE = initial file size. Pre-allocate space to avoid auto-grow events.
    -- WHY: Auto-grow (when the file expands on demand) causes a BRIEF PAUSE
    -- in operations while the OS allocates disk space. On a busy system at
    -- 3 PM, this pause can cause timeouts. Pre-allocate = no surprises.

    MAXSIZE  = 50GB,
    -- MAXSIZE = maximum size this file can grow to. Safety ceiling.
    -- WHY: Without MAXSIZE, a runaway process (like a logging loop) can
    -- fill the entire disk and kill the server. MAXSIZE is your safety net.

    FILEGROWTH = 256MB
    -- FILEGROWTH = how much the file grows each time it needs more space.
    -- WHY 256MB? Growing in small increments (default is 64MB or 1%) causes
    -- frequent pause-and-grow events. Growing in large chunks means fewer
    -- events. The rule: FILEGROWTH should be at least 10% of current size.
)
LOG ON
(
    NAME       = ShopCartDB_Log,
    FILENAME   = 'C:\SQLData\ShopCartDB_log.ldf',
    -- LOG ON defines the transaction log file (.ldf) settings separately.
    -- WHY separate section: Log and data files have different access patterns.
    -- Logs are written SEQUENTIALLY (fast), data files are random-access.
    -- In enterprise: put log file on a separate physical disk from data file.
    SIZE       = 256MB,
    MAXSIZE    = 10GB,
    FILEGROWTH = 128MB
);
GO

-- ── Switch context to our new database ───────────────────────────
USE ShopCartDB;
GO

-- ── Set the recovery model to FULL (CRITICAL for production) ──────
ALTER DATABASE ShopCartDB
SET RECOVERY FULL;
-- RECOVERY FULL = Full recovery model.
-- WHAT IT MEANS: SQL Server keeps ALL transaction log records until you
--   explicitly back up the transaction log. This gives you point-in-time recovery.
-- WHY IT'S MANDATORY: If ShopCart gets a failed transaction at 2:47 PM and
--   their last full backup was at midnight, with FULL recovery + log backups
--   every 15 minutes, you can restore to 2:45 PM — only 2 minutes of data lost.
--   With SIMPLE recovery? You lose everything since midnight. That's 14 hours
--   of orders, payments, and customer data. Unacceptable for production.
GO

-- ── Set database-level compatibility ────────────────────────────
ALTER DATABASE ShopCartDB
SET COMPATIBILITY_LEVEL = 160;
-- COMPATIBILITY_LEVEL 160 = SQL Server 2022 features enabled.
-- WHY: If you upgrade SQL Server but want old query behavior temporarily,
-- you lower compat level. For a new database, always set to latest (160).
-- NUMBERS: 150 = 2019, 160 = 2022. Interview question: "How do you upgrade
-- a database without breaking existing queries?" Answer: Compat level staging.
GO

-- ── Verify the database was created correctly ─────────────────────
SELECT
    d.name                       AS DatabaseName,
    d.recovery_model_desc         AS RecoveryModel,
    d.compatibility_level         AS CompatLevel,
    d.state_desc                   AS State,
    CAST(mf.size * 8.0 / 1024 AS DECIMAL(10,2)) AS SizeMB
FROM       sys.databases     d
JOIN       sys.master_files  mf  ON d.database_id = mf.database_id
WHERE      d.name = 'ShopCartDB'
    AND    mf.type_desc = 'ROWS';
-- sys.master_files = catalog view listing physical file details for ALL databases.
-- mf.size = file size in 8KB pages. We convert: size × 8 ÷ 1024 = MB
-- CAST(...AS DECIMAL(10,2)) = format as decimal with 2 decimal places
-- WHERE type_desc = 'ROWS' = only the data file (not the log file)
-- JOIN: connects databases to their files via database_id (foreign key relationship)
Lab 1C — DBA Health Check

Your First Monitoring Script — The DBA Health Dashboard

The JD says "Proactively monitor database health, disk space, CPU, memory." Here is your first health-check script. A real DBA runs this (or schedules it) every morning.

📄 03_dba_health_check.sql T-SQL 
-- ═══════════════════════════════════════════════════════════════
-- FILE: 03_dba_health_check.sql
-- PURPOSE: Morning health check — run this every day to catch
--          issues before users report them
-- ═══════════════════════════════════════════════════════════════

-- ── CHECK 1: SQL Server uptime ────────────────────────────────────
SELECT
    DATEDIFF(DAY, sqlserver_start_time, GETDATE())  AS DaysRunning,
    sqlserver_start_time                              AS LastRestart
FROM sys.dm_os_sys_info;
-- sys.dm_os_sys_info = Dynamic Management View (DMV). 
--   DMVs start with sys.dm_ and show LIVE server state (not just metadata).
-- sqlserver_start_time = timestamp when SQL Server service last started.
-- DATEDIFF(DAY, start, now) = calculates days between two dates.
-- WHY: An unexpected recent restart time means someone (or something) restarted
-- the SQL Server — a potential incident. Daily check catches this.

-- ── CHECK 2: Memory pressure ──────────────────────────────────────
SELECT
    physical_memory_in_use_kb / 1024          AS MemUsedMB,
    page_fault_count                           AS PageFaults,
    memory_utilization_percentage              AS MemUsagePct
FROM sys.dm_os_process_memory;
-- sys.dm_os_process_memory = shows SQL Server process memory consumption.
-- physical_memory_in_use_kb / 1024 = convert KB to MB for readability.
-- page_fault_count = number of times SQL Server had to go to disk for memory.
--   A HIGH number = SQL Server is under memory pressure (RAM insufficient).
-- memory_utilization_percentage = what % of the allowed max memory is in use.
--   If consistently above 95%, you need more RAM or better query tuning.

-- ── CHECK 3: Database sizes and free space ────────────────────────
SELECT
    db.name                                        AS DatabaseName,
    SUM(mf.size) * 8 / 1024                        AS TotalSizeMB,
    SUM(FILEPROPERTY(mf.name, 'SpaceUsed')) * 8 / 1024 AS UsedMB,
    (SUM(mf.size) - SUM(FILEPROPERTY(mf.name, 'SpaceUsed')))
        * 8 / 1024                                  AS FreeMB
FROM  sys.databases  db
JOIN  sys.master_files mf  ON db.database_id = mf.database_id
WHERE  mf.type_desc = 'ROWS'
GROUP BY db.name
ORDER BY TotalSizeMB DESC;
-- SUM(mf.size) = total file size in 8KB pages, × 8 / 1024 = MB
-- FILEPROPERTY(name, 'SpaceUsed') = built-in function returning pages used.
-- FreeMB = the gap = how much space remains before the file must auto-grow.
-- GROUP BY = aggregate per database (one row per database).
-- WHY: A database at 95% capacity will auto-grow soon (performance impact)
-- or fail (if MAXSIZE hit). Alert when FreeMB drops below 10% of total.

-- ── CHECK 4: Currently running queries ───────────────────────────
SELECT
    r.session_id                              AS SessionID,
    r.status                                  AS Status,
    r.cpu_time                                AS CPUms,
    r.total_elapsed_time                      AS ElapsedMs,
    r.logical_reads                           AS LogicalReads,
    SUBSTRING(t.text, 1, 200)                 AS QueryText,
    s.login_name                              AS WhoIsRunning
FROM        sys.dm_exec_requests    r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle)  t
JOIN        sys.dm_exec_sessions   s  ON r.session_id = s.session_id
WHERE       r.session_id > 50
ORDER BY    r.total_elapsed_time DESC;
-- sys.dm_exec_requests = lists every currently EXECUTING query (not idle sessions).
-- sys.dm_exec_sql_text() = a TABLE-VALUED FUNCTION. Takes sql_handle (pointer
--   to a query in the plan cache) and returns the actual T-SQL text.
-- CROSS APPLY = apply this function to EVERY ROW in dm_exec_requests.
--   Think of it as a JOIN where the right side is a function call per row.
-- sys.dm_exec_sessions = all connected sessions (sleeping or active).
-- WHERE session_id > 50 = skip system sessions (1–50 are internal SQL Server workers).
-- logical_reads = how many 8KB data pages this query has read from the buffer pool.
--   High logical_reads = table scan instead of index seek = needs tuning.
-- WHY THIS QUERY: This is your "sp_who2 on steroids." Run it when someone says
-- "SQL Server is slow" — this shows EXACTLY what's running and costing resources.
Interview Preparation

Chapter 1 Interview Questions — CGI-Level

Based on the exact job description. These are the questions you'll face in a first or second round interview for this role.

Q1 · Architecture

Q: "What is the difference between .mdf and .ldf files?"

A: The .mdf is the primary data file that stores all your tables, indexes, views, and stored procedures. The .ldf is the transaction log file — every INSERT, UPDATE, and DELETE is written here FIRST before the data file is modified. This write-ahead logging (WAL) is how SQL Server maintains ACID compliance and enables point-in-time recovery. In production, you always want them on separate physical disks to maximize throughput and to prevent the log filling up data disk space.

Q2 · System Databases

Q: "What happens if the tempdb database is corrupt?"

A: tempdb is recreated fresh from the model database every time SQL Server starts. So if tempdb is corrupt, just restart the SQL Server service and it will automatically rebuild tempdb. This is why you never need to back up tempdb — it's always recreated at startup. However, if tempdb's disk is full or its files are misconfigured, SQL Server will fail to start.

Q3 · Recovery Models

Q: "A database is set to SIMPLE recovery model. What are the implications for disaster recovery?"

A: With SIMPLE recovery, SQL Server automatically truncates the transaction log after each checkpoint, which means you can only backup Full and Differential backups — no transaction log backups. This means your Recovery Point Objective (RPO) is at best the time of your last differential backup, which could be hours. You lose all data between the last backup and the failure. For any production OLTP system like an e-commerce database, SIMPLE recovery is unacceptable. FULL recovery + log backups every 15 minutes means your data loss is capped at 15 minutes maximum.

Q4 · Performance

Q: "SQL Server is consuming 95% of a 16 GB server's RAM. What do you check?"

A: First check if max server memory is configured — by default SQL Server has no limit and will use all available RAM. If it's not set, set it to leave ~20% for Windows (so ~12 GB max). Then check sys.dm_os_process_memory for page faults — high page fault count means RAM pressure. Next check what's in the plan cache using sys.dm_exec_cached_plans — you might have plan cache bloat from un-parameterized ad hoc queries (fix: enable 'optimize for ad hoc workloads'). Finally check if there are large queries doing table scans that are flooding the buffer pool.
