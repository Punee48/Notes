Database Schema — Designing the Tables

Before writing a single CREATE TABLE, a DBA must understand the data model. Here's the complete ShopCart India schema we'll build. Study the relationships between tables — this is called an Entity-Relationship (ER) model.

Customers
  • PK CustomerID
  • FirstName
  • LastName
  • Email
  • Phone
  • City
  • CreatedAt
  • IsActive
Categories
  • PK CategoryID
  • CategoryName
  • Description
Products
  • PK ProductID
  • FK CategoryID
  • ProductName
  • Price
  • StockQty
  • IsActive
Orders
  • PK OrderID
  • FK CustomerID
  • OrderDate
  • Status
  • TotalAmount
  • ShippingCity
OrderItems
  • PK OrderItemID
  • FK OrderID
  • FK ProductID
  • Quantity
  • UnitPrice
Payments
  • PK PaymentID
  • FK OrderID
  • PaymentDate
  • Method
  • Amount
  • Status
🔗
Relationship Chain: Customers → Orders (1-to-many). Orders → OrderItems (1-to-many). Products → OrderItems (1-to-many). Orders → Payments (1-to-1). Products → Categories (many-to-1). OrderItems is the junction table that resolves the many-to-many relationship between Orders and Products.

DDL — Data Definition Language: Creating the Tables

DDL commands define the structure of the database. They don't manipulate data — they create, alter, or drop the objects that hold data. Every keyword, constraint, and data type below is intentional and explained.

📄 04_ddl_create_tables.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 04_ddl_create_tables.sql
-- PURPOSE: Create the complete ShopCart India schema
-- RUN IN: ShopCartDB
-- ════════════════════════════════════════════════════════════════

USE ShopCartDB;
GO

-- ══ TABLE 1: Customers ════════════════════════════════════════════
CREATE TABLE Customers
(
    CustomerID   INT              IDENTITY(1,1)  NOT NULL,
    -- INT         = 4-byte integer. Holds values -2,147,483,648 to 2,147,483,647.
    --               For a customer ID, INT is fine. For truly massive systems: BIGINT.
    -- IDENTITY(1,1) = auto-increment. Seed=1 (start value), Increment=1 (add 1 each time).
    --               SQL Server generates this value automatically on every INSERT.
    --               You NEVER insert CustomerID manually — SQL Server does it.
    -- NOT NULL    = this column cannot be empty. Every customer MUST have an ID.

    FirstName    NVARCHAR(100)               NOT NULL,
    -- NVARCHAR(100) = Unicode variable-length string, up to 100 characters.
    --   N prefix = stores Unicode (N for National Character Set).
    --   WHY NVARCHAR not VARCHAR? ShopCart serves Indian customers.
    --   Names can contain Hindi, Tamil, Bengali characters — these need Unicode.
    --   VARCHAR stores only ASCII (English); NVARCHAR stores any language.
    --   The 100 = max length. If someone enters 5 characters, only 5+2 bytes used.
    --   (NVARCHAR is variable-length, so you only pay for what you use)

    LastName     NVARCHAR(100)               NOT NULL,
    Email        VARCHAR(255)                NOT NULL,
    -- Email uses VARCHAR (not NVARCHAR) because email addresses are always ASCII.
    -- 255 = max RFC standard email length.

    Phone        VARCHAR(15)                      NULL,
    -- NULL = this column IS allowed to be empty (optional field).
    -- Phone numbers are optional — not every customer provides one.
    -- VARCHAR(15) = enough for +91 9876543210 format (13 chars + some buffer)

    City         NVARCHAR(100)                    NULL,
    CreatedAt    DATETIME2(0)           NOT NULL   DEFAULT GETUTCDATE(),
    -- DATETIME2(0) = stores date AND time with 0 decimal seconds precision.
    --   DATETIME2 is the modern replacement for DATETIME. More storage-efficient.
    --   (0) = no fractional seconds. We don't need milliseconds for "when they joined".
    -- DEFAULT GETUTCDATE() = if you don't specify a value on INSERT, SQL Server
    --   automatically inserts the current UTC time.
    --   WHY UTC and not GETDATE()? ShopCart has customers from multiple time zones.
    --   Storing UTC avoids confusion. Convert to local time at the app layer.

    IsActive     BIT                      NOT NULL   DEFAULT 1,
    -- BIT = boolean in SQL Server. 0 = false, 1 = true. Stored in 1 byte.
    -- DEFAULT 1 = new customers are active by default.
    -- WHY BIT flag vs DELETE? We NEVER delete customers from the database
    -- (legal/audit requirements). Instead we "soft delete" by setting IsActive = 0.
    -- This pattern is standard in production systems.

    CONSTRAINT PK_Customers        PRIMARY KEY CLUSTERED (CustomerID),
    -- CONSTRAINT = named database rule. Naming constraints (PK_Customers vs just
    --   PRIMARY KEY) lets you reference them later in ALTER, error messages, scripts.
    -- PRIMARY KEY = enforces uniqueness + NOT NULL for CustomerID.
    --   Every table should have a primary key — it's the unique row identifier.
    -- CLUSTERED = the table rows are physically SORTED on disk by CustomerID.
    --   A clustered index IS the table. There can only be ONE clustered index per table.
    --   By default, primary keys are clustered. This means looking up by CustomerID
    --   is extremely fast — the data is physically ordered on disk by this key.

    CONSTRAINT UQ_Customers_Email  UNIQUE (Email),
    -- UNIQUE constraint = no two rows can have the same Email value.
    -- WHY: Email is how customers log in. Duplicate emails = two accounts for
    -- one person = billing nightmares. The database ENFORCES this, not the app.
    -- Database-level enforcement is safer than application-level: apps have bugs.

    CONSTRAINT CK_Customers_Email  CHECK (Email LIKE '%@%.%')
    -- CHECK constraint = a custom rule that every inserted/updated row must satisfy.
    -- Email LIKE '%@%.%' = email must contain @ AND a dot after it.
    --   % = wildcard (matches any characters). So '%@%.%' means:
    --   "any chars" + "@" + "any chars" + "." + "any chars"
    --   This is a basic email format validation at the database level.
    -- WHY: App validation can be bypassed. DB constraints cannot.
    --   If an app bug or direct INSERT sends 'notanemail', this constraint rejects it.
);
GO

-- ══ TABLE 2: Categories ═══════════════════════════════════════════
CREATE TABLE Categories
(
    CategoryID    INT           IDENTITY(1,1)  NOT NULL,
    CategoryName  NVARCHAR(100)               NOT NULL,
    Description   NVARCHAR(500)                    NULL,
    CONSTRAINT PK_Categories          PRIMARY KEY CLUSTERED (CategoryID),
    CONSTRAINT UQ_Categories_Name      UNIQUE (CategoryName)
);
GO

-- ══ TABLE 3: Products ═════════════════════════════════════════════
CREATE TABLE Products
(
    ProductID    INT              IDENTITY(1,1)  NOT NULL,
    CategoryID   INT                              NOT NULL,
    ProductName  NVARCHAR(200)                   NOT NULL,
    Price        DECIMAL(10,2)                   NOT NULL,
    -- DECIMAL(10,2) = exact fixed-point number. 10 = total digits, 2 = after decimal.
    -- Max value: 99,999,999.99 (₹ crores range — enough for even premium products).
    -- WHY DECIMAL not FLOAT? FLOAT is approximate. 0.1 + 0.2 in FLOAT = 0.30000000004.
    -- For money/prices, ALWAYS use DECIMAL. Financial data must be exact.
    -- NEVER use FLOAT or REAL for currency — this is a classic DBA lesson.

    StockQty     INT                              NOT NULL   DEFAULT 0,
    IsActive     BIT                              NOT NULL   DEFAULT 1,
    CreatedAt    DATETIME2(0)                    NOT NULL   DEFAULT GETUTCDATE(),

    CONSTRAINT PK_Products     PRIMARY KEY CLUSTERED (ProductID),
    CONSTRAINT FK_Products_Cat  FOREIGN KEY (CategoryID)
                                 REFERENCES Categories(CategoryID),
    -- FOREIGN KEY = links this table to Categories. CategoryID in Products
    --   MUST exist in the CategoryID column of the Categories table.
    -- WHY: Without this, you could insert a Product with CategoryID = 9999
    --   even if that category doesn't exist. FK prevents orphaned records.
    -- REFERENCES Categories(CategoryID) = the parent table and column.
    -- WHAT HAPPENS if you try to INSERT a Product with a non-existent CategoryID?
    --   SQL Server returns: "The INSERT statement conflicted with the FOREIGN KEY constraint"

    CONSTRAINT CK_Products_Price  CHECK (Price > 0),
    -- CHECK constraint: price MUST be greater than 0. No free products (intentional).
    -- This prevents a data entry error where someone enters -500 as a price.

    CONSTRAINT CK_Products_Stock   CHECK (StockQty >= 0)
    -- Stock can be 0 (out of stock) but never negative. No -5 units of a product.
);
GO

-- ══ TABLE 4: Orders ═══════════════════════════════════════════════
CREATE TABLE Orders
(
    OrderID      INT              IDENTITY(1000,1) NOT NULL,
    -- IDENTITY(1000,1) = starts from 1000 (not 1).
    -- WHY? Customers see order IDs. An OrderID of 1 or 2 tells them you're brand new
    -- with almost no orders. Starting at 1000 looks more established — a business decision
    -- that a DBA implements at the database level. Seed=1000, Increment=1.

    CustomerID   INT                              NOT NULL,
    OrderDate    DATETIME2(0)                    NOT NULL   DEFAULT GETUTCDATE(),
    Status       VARCHAR(20)                     NOT NULL   DEFAULT 'Pending',
    TotalAmount  DECIMAL(12,2)                   NOT NULL   DEFAULT 0,
    ShippingCity NVARCHAR(100)                        NULL,

    CONSTRAINT PK_Orders       PRIMARY KEY CLUSTERED (OrderID),
    CONSTRAINT FK_Orders_Cust   FOREIGN KEY (CustomerID)
                                 REFERENCES Customers(CustomerID),
    CONSTRAINT CK_Orders_Status CHECK (Status IN
        ('Pending', 'Processing', 'Shipped', 'Delivered', 'Cancelled'))
    -- CHECK with IN() = Status must be one of these exact values. Nothing else.
    -- WHY: Without this, developers might insert 'shipped', 'SHIPPED', 'Dispatch'...
    -- inconsistency in status values breaks every dashboard and report.
    -- The database enforces the valid state machine for order lifecycle.
);
GO

-- ══ TABLE 5: OrderItems (Junction Table) ══════════════════════════
CREATE TABLE OrderItems
(
    OrderItemID  INT              IDENTITY(1,1)  NOT NULL,
    OrderID      INT                              NOT NULL,
    ProductID    INT                              NOT NULL,
    Quantity     INT                              NOT NULL,
    UnitPrice    DECIMAL(10,2)                   NOT NULL,
    -- UnitPrice: WHY store the price again here when it's in Products table?
    -- IMPORTANT concept: Product prices CHANGE over time. If you look at the
    -- Products table for the price, you'd see today's price — not the price
    -- at the time of purchase. OrderItems.UnitPrice is the HISTORICAL price
    -- — what the customer actually paid. This is crucial for invoicing and accounting.

    CONSTRAINT PK_OrderItems       PRIMARY KEY CLUSTERED (OrderItemID),
    CONSTRAINT FK_OI_Order          FOREIGN KEY (OrderID)
                                     REFERENCES Orders(OrderID),
    CONSTRAINT FK_OI_Product        FOREIGN KEY (ProductID)
                                     REFERENCES Products(ProductID),
    CONSTRAINT CK_OI_Qty            CHECK (Quantity > 0)
);
GO

-- ══ TABLE 6: Payments ════════════════════════════════════════════
CREATE TABLE Payments
(
    PaymentID    INT              IDENTITY(1,1)  NOT NULL,
    OrderID      INT                              NOT NULL,
    PaymentDate  DATETIME2(0)                    NOT NULL   DEFAULT GETUTCDATE(),
    Method       VARCHAR(30)                     NOT NULL,
    Amount       DECIMAL(12,2)                   NOT NULL,
    Status       VARCHAR(20)                     NOT NULL   DEFAULT 'Pending',

    CONSTRAINT PK_Payments        PRIMARY KEY CLUSTERED (PaymentID),
    CONSTRAINT FK_Payments_Order   FOREIGN KEY (OrderID)
                                    REFERENCES Orders(OrderID),
    CONSTRAINT CK_Pay_Method       CHECK (Method IN
        ('UPI', 'CreditCard', 'DebitCard', 'NetBanking', 'COD', 'Wallet')),
    CONSTRAINT CK_Pay_Status       CHECK (Status IN
        ('Pending', 'Completed', 'Failed', 'Refunded')),
    CONSTRAINT CK_Pay_Amount       CHECK (Amount > 0)
);
GO

-- ── Verify all tables were created ─────────────────────────────
-- sys.tables = catalog view listing all user-created tables.
-- sys.columns = catalog view listing columns for each table.
-- This query gives you a complete schema overview.
SELECT
    t.name            AS TableName,
    c.name            AS ColumnName,
    tp.name           AS DataType,
    c.max_length      AS MaxLen,
    c.is_nullable     AS Nullable,
    c.is_identity     AS IsIdentity
FROM   sys.tables   t
JOIN   sys.columns  c   ON t.object_id = c.object_id
JOIN   sys.types    tp  ON c.user_type_id = tp.user_type_id
ORDER BY t.name, c.column_id;

GO

-- INSERT INTO: adds new rows to a table.
-- VALUES: the actual data. Order must match the column list exactly.
-- IDENTITY columns (CategoryID) are NEVER listed — SQL auto-generates them.

INSERT INTO Categories (CategoryName, Description)
VALUES
    ('Electronics',   'Mobiles, Laptops, Tablets and Accessories'),
    ('Clothing',      'Men, Women and Kids clothing'),
    ('Groceries',     'Daily essentials and packaged food'),
    ('Home & Kitchen', 'Appliances, cookware and home decor'),
    ('Books',          'Fiction, Non-fiction and Academic books');
-- Multi-row INSERT: one INSERT INTO, multiple VALUE tuples separated by commas.
-- This is MORE EFFICIENT than 5 separate INSERT statements.
-- WHY: Each INSERT is a round-trip to the database. One INSERT with 5 rows
-- = 1 transaction, 1 log write. 5 separate INSERTs = 5 transactions, 5 log writes.

-- ══ INSERT with OUTPUT clause — capture generated IDs ═════════════
INSERT INTO Customers
    (FirstName, LastName, Email, Phone, City)
OUTPUT
    INSERTED.CustomerID,
    INSERTED.FirstName + ' ' + INSERTED.LastName  AS FullName,

-- INSERTED is a special pseudo-table available inside INSERT/UPDATE/DELETE.
-- It contains the NEW values of the rows affected.

-- ══ INSERT with a TRANSACTION — critical for order creation ════════
BEGIN TRANSACTION;
-- BEGIN TRANSACTION = starts an explicit transaction.
-- Everything between BEGIN TRAN and COMMIT is treated as ONE atomic unit.
-- ATOMIC means: either ALL of it succeeds, or NONE of it does.
-- WHY: Creating an order involves inserting into Orders AND OrderItems.
-- If inserting into Orders succeeds but OrderItems fails (e.g., bad ProductID),
-- you'd have a phantom order with no items. The transaction prevents this.
-- This is the A in ACID — Atomicity.

BEGIN TRY
-- BEGIN TRY / END TRY = SQL Server's error handling block.
-- Any error inside TRY jumps execution to the CATCH block.
-- WHY: Transactions that error without being caught stay OPEN (uncommitted),
-- which holds LOCKS on the rows and blocks other queries. Always wrap
-- multi-statement transactions in TRY/CATCH.

    DECLARE @OrderID   INT;
    DECLARE @OrderTotal DECIMAL(12,2);
    -- DECLARE = creates a local variable. Scope: this batch only.
    -- @OrderID: will hold the newly created order's ID.
    -- The @ prefix = user-defined variable (vs @@ = system variable).

    INSERT INTO Orders (CustomerID, Status, ShippingCity)
    VALUES (1, 'Processing', 'Bengaluru');

    SET @OrderID = SCOPE_IDENTITY();
    -- SCOPE_IDENTITY() = returns the LAST IDENTITY value inserted in THIS scope.
    -- WHY SCOPE_IDENTITY() and not @@IDENTITY?
    --   @@IDENTITY returns the last identity value from ANY table in the session,
    --   including values inserted by triggers. If an INSERT triggers another INSERT
    --   on another table, @@IDENTITY would return the trigger's table's ID — WRONG.
    -- SCOPE_IDENTITY() only returns the ID from the current scope (this statement).
    -- This is a CLASSIC interview question: always use SCOPE_IDENTITY() in applications.

    INSERT INTO OrderItems (OrderID, ProductID, Quantity, UnitPrice)
    VALUES
        (@OrderID, 1, 1, 74999.00),   -- Samsung S24 × 1
        (@OrderID, 4, 2, 24999.00);  -- AirPods × 2

    SET @OrderTotal =
        (SELECT SUM(Quantity * UnitPrice)
         FROM OrderItems
         WHERE OrderID = @OrderID);
    -- Sub-select to calculate order total: (1 × 74999) + (2 × 24999) = 124997
    -- Assigning a SELECT result to a variable: SET @var = (SELECT ...)

    UPDATE Orders
    SET   TotalAmount = @OrderTotal
    WHERE OrderID     = @OrderID;
    -- UPDATE: modifies existing rows. Always use WHERE with UPDATE.
    -- NEVER run UPDATE without WHERE in production — it updates EVERY row.
    -- Classic horror story: UPDATE Orders SET Status='Cancelled' (forgot WHERE)
    -- → ALL 2 million orders cancelled. This is irreversible without a backup.

    INSERT INTO Payments (OrderID, Method, Amount, Status)
    VALUES (@OrderID, 'UPI', @OrderTotal, 'Completed');

    COMMIT TRANSACTION;
    PRINT 'Order created successfully. OrderID: ' + CAST(@OrderID AS VARCHAR);
    -- COMMIT = makes all changes permanent. Releases all locks.
    -- After COMMIT, the data is durably saved (D in ACID = Durability).
    -- CAST(@OrderID AS VARCHAR) = converts INT to string for the PRINT statement.
    -- PRINT only accepts strings — you must convert numbers first.

END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    -- ROLLBACK = undoes ALL changes in this transaction back to BEGIN TRANSACTION.
    -- This is the R in ACID — if anything fails, nothing is saved.
    -- The database is returned to the state it was in before BEGIN TRANSACTION.
    PRINT 'Error occurred: ' + ERROR_MESSAGE();
    -- ERROR_MESSAGE() = built-in function returning the error description text.
    -- Other error functions: ERROR_NUMBER(), ERROR_LINE(), ERROR_PROCEDURE()
END CATCH;
GO

JOINs — Combining Tables (The Most Critical Skill)

JOINs are the heart of SQL. A DBA who doesn't understand JOINs deeply cannot write business queries, debug performance issues, or explain execution plans. We'll cover all 5 types with ShopCart examples.

🔵

INNER JOIN

Only rows that match in BOTH tables. Most common. "Only customers who placed orders."

🟠

LEFT JOIN

ALL rows from left table + matched rows from right. "All customers, with orders if they exist."

🟣

RIGHT JOIN

ALL rows from right table + matched from left. Rarely used — flip tables and use LEFT JOIN instead.

⚪

FULL OUTER JOIN

ALL rows from BOTH tables. NULL where no match. "All customers and all orders, matched where possible."

🔴

CROSS JOIN

Every row from left × every row from right (Cartesian product). Use carefully — can produce millions of rows.

📄 06_joins_mastery.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 06_joins_mastery.sql
-- PURPOSE: Master all JOIN types with real ShopCart business questions
-- ════════════════════════════════════════════════════════════════

-- ══ INNER JOIN: Show all orders with customer details ═══════════
-- Business Question: "Give me a list of all orders with the customer name,
-- their city, and the order total."
-- Use INNER JOIN because: we only want orders that have a valid customer.

SELECT
    o.OrderID,
    c.FirstName + ' ' + c.LastName  AS CustomerName,
    -- String concatenation in T-SQL: use + operator.
    -- But WARNING: if either side is NULL, the result is NULL.
    -- Safe version: ISNULL(FirstName,'') + ' ' + ISNULL(LastName,'')
    -- Or: CONCAT(FirstName, ' ', LastName) — CONCAT handles NULLs as empty strings.
    c.City,
    o.OrderDate,
    o.Status,
    o.TotalAmount
FROM       Orders    o
-- FROM Orders o : "o" is a TABLE ALIAS — a short nickname for the table.
-- WHY ALIASES: Without them, you'd write Orders.OrderID, Orders.CustomerID...
-- everywhere. With aliases: o.OrderID, c.CustomerID. Cleaner and faster to type.
-- Also essential when joining a table to ITSELF (self-join).
INNER JOIN Customers c  ON o.CustomerID = c.CustomerID
-- INNER JOIN Customers c ON ... = links Orders to Customers on matching CustomerID.
-- ON clause = the join condition. The rows are matched where IDs are equal.
-- Only orders where CustomerID exists in Customers are returned.
-- If an order had CustomerID = 9999 (orphaned FK — our FK prevents this), 
-- it would NOT appear in INNER JOIN results.
ORDER BY   o.OrderDate DESC;
-- ORDER BY: sorts results. DESC = newest first. ASC = oldest first (default).

-- ══ MULTI-TABLE INNER JOIN: Full Order Details ════════════════════
-- Business Question: "Show me the complete receipt for every order:
-- customer name, product name, quantity, unit price, line total."
-- This requires joining 4 tables in a chain.

SELECT
    o.OrderID,
    CONCAT(c.FirstName, ' ', c.LastName)  AS Customer,
    cat.CategoryName,
    p.ProductName,
    oi.Quantity,
    oi.UnitPrice,
    oi.Quantity * oi.UnitPrice              AS LineTotal,
    o.Status                                  AS OrderStatus,
    pay.Method                               AS PayMethod
FROM       Orders      o
INNER JOIN Customers   c    ON o.CustomerID  = c.CustomerID
INNER JOIN OrderItems  oi   ON o.OrderID     = oi.OrderID
INNER JOIN Products    p    ON oi.ProductID  = p.ProductID
INNER JOIN Categories  cat  ON p.CategoryID  = cat.CategoryID
LEFT JOIN  Payments    pay  ON o.OrderID     = pay.OrderID
-- NOTE: We use LEFT JOIN for Payments because some orders might not have
-- a payment record yet (e.g., COD orders paid at delivery = payment comes later).
-- With INNER JOIN, those orders would disappear from results.
-- With LEFT JOIN, they appear with NULL in the payment columns.
-- READ THIS JOIN CHAIN like a story:
-- Start with Orders.
-- Connect to Customers (who placed each order?).
-- Connect to OrderItems (what products are in each order?).
-- Connect to Products (what are those products?).
-- Connect to Categories (what category are the products in?).
-- Optionally connect to Payments (was this order paid?).
-- SQL Server builds this result by processing joins left to right.
ORDER BY o.OrderID, p.ProductName;

-- ══ LEFT JOIN: Customers with NO orders ════════════════════════════
-- Business Question: "Which customers have registered but NEVER placed an order?"
-- This is called a LEFT ANTI JOIN — a LEFT JOIN where the right side is NULL.

SELECT
    c.CustomerID,
    CONCAT(c.FirstName, ' ', c.LastName)  AS CustomerName,
    c.Email,
    c.City,
    c.CreatedAt                                AS JoinedOn
FROM      Customers c
LEFT JOIN Orders    o    ON c.CustomerID = o.CustomerID
WHERE     o.OrderID IS NULL;
-- LEFT JOIN: Returns ALL Customers. For customers with matching orders,
-- the Orders columns are populated. For customers with NO orders,
-- the Orders columns are NULL.
-- WHERE o.OrderID IS NULL: FILTER to keep only those with NULL OrderID
-- = customers who never ordered. This is the Anti-Join pattern.
-- WHY NOT: WHERE o.CustomerID != c.CustomerID? This misses NULL rows entirely.
-- For "not exists" type queries: use LEFT JOIN ... WHERE right.col IS NULL
-- OR use NOT EXISTS (shown in CTEs section). Both are valid; performance varies.

-- ══ Aggregate with GROUP BY: Sales by City ═════════════════════════
-- Business Question: "What is the total revenue and number of orders per city?"

SELECT
    c.City,
    COUNT(DISTINCT o.OrderID)  AS TotalOrders,
    -- COUNT(DISTINCT OrderID) = count unique orders (not rows after join expansion).
    -- WHY DISTINCT: With multi-item orders, one OrderID appears multiple times
    -- in the join (once per OrderItem). Without DISTINCT: over-counting.
    COUNT(DISTINCT c.CustomerID) AS UniqueCustomers,
    SUM(o.TotalAmount)             AS TotalRevenue,
    AVG(o.TotalAmount)             AS AvgOrderValue,
    MAX(o.TotalAmount)             AS HighestOrder
FROM       Customers c
INNER JOIN Orders    o  ON c.CustomerID = o.CustomerID
WHERE      o.Status != 'Cancelled'
GROUP BY   c.City
-- GROUP BY: collapses all rows with the same City into ONE result row.
-- Aggregate functions (SUM, COUNT, AVG, MAX, MIN) calculate per group.
-- RULE: In a query with GROUP BY, every column in SELECT must either be:
--   1. In the GROUP BY clause, OR
--   2. Inside an aggregate function (SUM, COUNT, etc.)
-- You CANNOT select c.Email in this query without adding it to GROUP BY.
HAVING     COUNT(DISTINCT o.OrderID) > 1
-- HAVING = filters GROUPS (like WHERE but after GROUP BY).
-- WHERE filters individual rows BEFORE grouping.
-- HAVING filters grouped results AFTER aggregation.
-- MEMORY AID: WHERE = filter rows → GROUP BY → HAVING = filter groups → SELECT
-- This HAVING says: only show cities with more than 1 order.
ORDER BY   TotalRevenue DESC;

CTEs — Common Table Expressions (Your Superpower)

A CTE is a named temporary result set that you define once and then use in your main query. Think of it as a "named subquery" that makes complex queries readable and maintainable.

📄 07_ctes_advanced.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 07_ctes_advanced.sql
-- PURPOSE: CTEs, Window Functions, and advanced T-SQL
-- Business Question: "Show the top 3 spending customers per city,
-- including their rank and percentage of their city's total revenue."
-- This is the kind of query that separates a junior from a senior.
-- ════════════════════════════════════════════════════════════════

-- ══ CTE 1: Basic CTE — Customer Revenue ═══════════════════════════
WITH CustomerRevenue AS
(
    -- WITH keyword starts the CTE definition.
    -- CustomerRevenue = the name we give this temporary result set.
    -- AS (...) = the query that defines what CustomerRevenue contains.
    -- This runs FIRST and its results are held in memory for the main query.
    SELECT
        c.CustomerID,
        CONCAT(c.FirstName, ' ', c.LastName) AS CustomerName,
        c.City,
        COUNT(DISTINCT o.OrderID)          AS OrderCount,
        SUM(o.TotalAmount)                 AS TotalSpent
    FROM       Customers c
    INNER JOIN Orders    o  ON c.CustomerID = o.CustomerID
    WHERE      o.Status != 'Cancelled'
    GROUP BY   c.CustomerID, c.FirstName, c.LastName, c.City
),

-- Multiple CTEs: separate them with a comma after the closing parenthesis.
-- Each subsequent CTE can REFERENCE previous CTEs.

CityRevenue AS
(
    -- CTE 2: Total revenue per city — references CTE 1 (CustomerRevenue)
    SELECT
        City,
        SUM(TotalSpent)  AS CityTotal
    FROM  CustomerRevenue
    -- Notice: FROM CustomerRevenue — we're querying the first CTE!
    -- This is the power of CTEs: build complex logic in steps, each step
    -- using the previous step's result. Much more readable than nested subqueries.
    GROUP BY City
),

RankedCustomers AS
(
    -- CTE 3: Rank customers within their city by spending
    SELECT
        cr.CustomerName,
        cr.City,
        cr.OrderCount,
        cr.TotalSpent,
        cit.CityTotal,
        ROUND(cr.TotalSpent * 100.0 / cit.CityTotal, 1) AS PctOfCity,
        -- ROUND(value, 1) = round to 1 decimal place.
        -- × 100.0: multiplying by 100.0 (not 100) forces DECIMAL division.
        -- Integer / Integer = Integer in SQL. 3 / 4 = 0, not 0.75.
        -- 3 / 4.0 = 0.75. Always use 100.0 for percentage calculations.

        RANK() OVER
        (
            PARTITION BY cr.City
            ORDER BY     cr.TotalSpent DESC
        )                                           AS CityRank
        -- RANK() OVER (...) = Window Function! This is where things get powerful.
        -- Window functions compute values ACROSS a set of rows related to the current row,
        -- WITHOUT collapsing the rows like GROUP BY does.
        --
        -- RANK() = assigns a rank (1, 2, 3...) based on ORDER BY.
        --   If two customers have equal TotalSpent, both get the same rank
        --   and the next rank is skipped. Example: 1, 2, 2, 4 (not 1,2,2,3).
        --   Use DENSE_RANK() if you want: 1, 2, 2, 3 (no gaps).
        --
        -- OVER() = defines the WINDOW (the scope of rows the function sees).
        --   Without OVER, RANK would be meaningless.
        --
        -- PARTITION BY cr.City = restart the ranking for EACH city.
        --   Think of it like GROUP BY, but it doesn't collapse rows —
        --   it creates "windows" (groups) and ranks WITHIN each window.
        --   Result: Bengaluru customers ranked 1,2,3... Mumbai customers ranked 1,2,3...
        --
        -- ORDER BY cr.TotalSpent DESC = rank by highest spending first.
    FROM      CustomerRevenue cr
    JOIN      CityRevenue      cit  ON cr.City = cit.City
)

-- ══ MAIN QUERY: Use the CTEs ════════════════════════════════════
-- Now we have 3 CTEs. The main query just filters from the last one.
SELECT
    City,
    CityRank     AS RankInCity,
    CustomerName,
    OrderCount,
    TotalSpent,
    PctOfCity    AS PctOfCityRevenue
FROM  RankedCustomers
WHERE CityRank <= 3
-- Filter AFTER ranking: only top 3 per city.
-- WHY NOT use RANK() directly in WHERE clause?
-- WHERE is evaluated BEFORE window functions.
-- You CANNOT say WHERE RANK() OVER(...) <= 3.
-- Solution: Put the window function in a CTE or subquery, THEN filter.
-- This is why this query needed 3 CTEs — each step adds a layer of logic.
ORDER BY City, CityRank;

Window Functions — Analytics Without GROUP BY
📄 08_window_functions.sql T-SQL
-- Business Question: Running total of daily revenue + 7-day moving average

WITH DailyRevenue AS
(
    SELECT
        CAST(o.OrderDate AS DATE)  AS OrderDay,
        -- CAST(DATETIME2 AS DATE) = strips the time, keeps only the date part.
        -- Needed to GROUP BY day (not by exact timestamp).
        SUM(o.TotalAmount)         AS DayRevenue
    FROM  Orders o
    WHERE o.Status != 'Cancelled'
    GROUP BY CAST(o.OrderDate AS DATE)
)
SELECT
    OrderDay,
    DayRevenue,

    SUM(DayRevenue)
        OVER (ORDER BY OrderDay
              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
                                     AS RunningTotal,
    -- SUM() OVER (ORDER BY... ROWS BETWEEN...) = Running Total (cumulative sum).
    -- ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW:
    --   UNBOUNDED PRECEDING = from the very first row in the window
    --   CURRENT ROW = up to and including the current row
    -- So for each row: sum ALL previous rows + current row = running total.
    -- This is like an Excel running total column — extremely useful for finance dashboards.

    AVG(DayRevenue)
        OVER (ORDER BY OrderDay
              ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
                                     AS Avg7DayRevenue,
    -- 7-day moving average: average of current row + 6 rows before it.
    -- ROWS BETWEEN 6 PRECEDING AND CURRENT ROW = sliding window of 7 rows.
    -- Used in business intelligence to smooth out daily spikes/dips.
    -- Marketing teams use this to spot trends without noise.

    LAG(DayRevenue, 1, 0)
        OVER (ORDER BY OrderDay)  AS PreviousDayRevenue,
    -- LAG(column, offset, default) = gets the value from N rows BEFORE the current row.
    -- LAG(DayRevenue, 1, 0) = yesterday's revenue. If no previous row: return 0 (default).
    -- Its counterpart is LEAD() = gets a value from N rows AFTER (look ahead).
    -- USE CASE: "How does today's revenue compare to yesterday?"
    -- DayRevenue - LAG(DayRevenue,1,0) OVER (ORDER BY OrderDay) = daily change

    ROW_NUMBER()
        OVER (ORDER BY DayRevenue DESC)  AS RevenueRankAllTime
    -- ROW_NUMBER() = unique sequential number (no ties). Always 1,2,3,4,5...
    -- vs RANK(): 1,2,2,4 (ties get same rank, next is skipped)
    -- vs DENSE_RANK(): 1,2,2,3 (ties same rank, next is NOT skipped)
    -- USE CASE: ROW_NUMBER for pagination (OFFSET/FETCH). RANK for leaderboards.

FROM  DailyRevenue
ORDER BY OrderDay;

Stored Procedures & Functions — Production-Grade Code

Stored Procedures (SPs) are pre-compiled T-SQL programs stored in the database. The JD explicitly asks for stored procedure development. Here are two production-quality examples.

📄 09_stored_procedures.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 09_stored_procedures.sql
-- PURPOSE: Production stored procedures for ShopCart India
-- ════════════════════════════════════════════════════════════════

-- ══ SP 1: Place an Order (full business logic) ════════════════════
CREATE OR ALTER PROCEDURE usp_PlaceOrder
(
    @CustomerID    INT,
    @ProductIDs    NVARCHAR(MAX),
    -- NVARCHAR(MAX) = up to 2 GB of text. Used here to pass a JSON string
    -- containing the product list. JSON in SQL Server = modern approach.
    @Quantities    NVARCHAR(MAX),
    @PaymentMethod VARCHAR(30),
    @ShippingCity  NVARCHAR(100),
    @NewOrderID    INT            OUTPUT
    -- OUTPUT parameter: value is set INSIDE the procedure and returned to the caller.
    -- The calling application gets @NewOrderID after the procedure runs.
    -- Think of it like a function return value — but SQL procedures use OUTPUT params.
)
AS
BEGIN
    SET NOCOUNT ON;
    -- SET NOCOUNT ON = suppresses "X rows affected" messages.
    -- WHY: By default SQL Server sends a message after every DML operation.
    -- For a stored procedure with 10 statements, this means 10 messages back
    -- to the application — extra network overhead. NOCOUNT ON = silence them.
    -- Best practice: ALWAYS add SET NOCOUNT ON at the top of every stored procedure.

    DECLARE @OrderTotal  DECIMAL(12,2) = 0;
    DECLARE @ErrMsg      NVARCHAR(500);

    -- Validate: customer exists and is active
    IF NOT EXISTS (
        SELECT 1 FROM Customers
        WHERE  CustomerID = @CustomerID AND IsActive = 1
    )
    BEGIN
        RAISERROR('Customer %d does not exist or is inactive.', 16, 1, @CustomerID);
        -- RAISERROR = raise a custom error to the calling application.
        -- 'Customer %d...' = message template (%d = integer placeholder)
        -- 16 = severity level. 1-10 = informational. 11-16 = user errors.
        --   16 = user-correctable error (most common for validation).
        --   17-25 = system/hardware errors (reserved for SQL Server itself).
        -- 1 = state (arbitrary 1-255, used to identify where in code the error happened)
        RETURN;
        -- RETURN = immediately exits the stored procedure.
        -- Execution stops here; nothing below runs.
    END

    BEGIN TRANSACTION;
    BEGIN TRY

        INSERT INTO Orders (CustomerID, Status, ShippingCity)
        VALUES (@CustomerID, 'Pending', @ShippingCity);

        SET @NewOrderID = SCOPE_IDENTITY();

        -- Parse JSON product/quantity arrays and insert order items
        INSERT INTO OrderItems (OrderID, ProductID, Quantity, UnitPrice)
        SELECT
            @NewOrderID,
            p.ProductID,
            TRY_CAST(q.value AS INT),
            -- TRY_CAST = attempts CAST, returns NULL on failure (doesn't throw an error).
            -- vs CAST which throws an exception on invalid input.
            -- Defensive coding: prefer TRY_CAST for user-supplied data.
            p.Price
        FROM
            OPENJSON(@ProductIDs)  WITH (value INT '$')  AS pid
        JOIN
            OPENJSON(@Quantities)    WITH (value INT '$')  AS q
                ON pid.[key] = q.[key]
        -- OPENJSON = parses a JSON array into a rowset.
        -- e.g., @ProductIDs = '[1,3,4]' → rows: key=0,value=1; key=1,value=3; etc.
        -- We JOIN on [key] to match product IDs to their quantities positionally.
        JOIN  Products p  ON p.ProductID = pid.value;

        UPDATE Orders
        SET   TotalAmount = (SELECT SUM(Quantity * UnitPrice)
                              FROM   OrderItems
                              WHERE  OrderID = @NewOrderID)
        WHERE OrderID = @NewOrderID;

        INSERT INTO Payments (OrderID, Method, Amount, Status)
        SELECT @NewOrderID, @PaymentMethod, TotalAmount, 'Pending'
        FROM   Orders  WHERE OrderID = @NewOrderID;

        COMMIT TRANSACTION;

    END TRY
    BEGIN CATCH
        IF XACT_STATE() != 0 ROLLBACK TRANSACTION;
        -- XACT_STATE() = checks transaction state.
        --  1 = active committable transaction
        --  0 = no active transaction
        -- -1 = active but uncommittable (must rollback — cannot commit).
        -- Always check XACT_STATE() before ROLLBACK in CATCH blocks.
        -- If no transaction is open (!= 0) and you call ROLLBACK, you get an error.
        THROW;
        -- THROW = re-raises the caught error to the caller.
        -- Modern replacement for RAISERROR in CATCH blocks.
        -- Preserves original error number, severity, and state.
    END CATCH
END;
GO

-- ══ Execute the stored procedure ═════════════════════════════════
DECLARE @ReturnedOrderID INT;

EXEC usp_PlaceOrder
    @CustomerID    = 2,
    @ProductIDs    = '[2,10]',       -- OnePlus 12 + Atomic Habits
    @Quantities    = '[1,2]',
    @PaymentMethod = 'CreditCard',
    @ShippingCity  = 'Mumbai',
    @NewOrderID    = @ReturnedOrderID OUTPUT;
-- OUTPUT keyword here tells SQL Server to pass @ReturnedOrderID
-- as an output parameter — it receives the value SET inside the procedure.

PRINT 'New Order ID: ' + CAST(@ReturnedOrderID AS VARCHAR);
GO

-- ══ SP 2: Customer Lookup Function ════════════════════════════════
CREATE OR ALTER FUNCTION ufn_GetCustomerSummary
(
    @CustomerID  INT
)
RETURNS TABLE
-- Inline Table-Valued Function (iTVF): returns a TABLE result set.
-- INLINE means the function body is a single SELECT (no BEGIN/END).
-- SQL Server can inline this function into the calling query's execution plan
-- = same performance as writing the query directly. Unlike multi-statement TVFs.
AS
RETURN
(
    SELECT
        c.CustomerID,
        CONCAT(c.FirstName, ' ', c.LastName)  AS FullName,
        c.Email,
        c.City,
        COUNT(o.OrderID)          AS TotalOrders,
        ISNULL(SUM(o.TotalAmount), 0) AS LifetimeValue,
        -- ISNULL(expr, 0) = if expr is NULL, return 0 instead.
        -- A customer with no orders: SUM returns NULL (not 0).
        -- ISNULL converts that NULL to 0 for cleaner display.
        MAX(o.OrderDate)          AS LastOrderDate
    FROM      Customers  c
    LEFT JOIN Orders     o  ON c.CustomerID = o.CustomerID
                            AND o.Status != 'Cancelled'
    WHERE     c.CustomerID = @CustomerID
    GROUP BY  c.CustomerID, c.FirstName, c.LastName, c.Email, c.City
);
GO

-- Use the function — call with CROSS APPLY or SELECT ... FROM function()
SELECT *  FROM  dbo.ufn_GetCustomerSummary(1);

--   Functions: return a value/table, can be used in SELECT/WHERE/JOIN.
--   Stored Procedures: can't be used in SELECT, but can have OUTPUT params, 
--     execute DDL, and manage transactions. Use SPs for business logic,
--     functions for reusable calculations/lookups.
Interview Preparation — Chapter 2

T-SQL Interview Questions — CGI-Level

Q1 · Data Types

Q: "Why would you use DECIMAL instead of FLOAT for storing prices?"

A: FLOAT is an approximate data type — it stores values in binary floating point, which cannot represent all decimal fractions exactly. For example, 0.1 in binary is a repeating fraction, so 0.1 + 0.2 in FLOAT can equal 0.30000000004 instead of 0.30. For financial data like prices, payments, or invoices, you need exact values. DECIMAL(10,2) stores exactly 10 digits with 2 decimal places — no approximation, no rounding surprises. The rule: use DECIMAL or MONEY for currency, never FLOAT or REAL.

Q2 · SCOPE_IDENTITY

Q: "What's the difference between @@IDENTITY and SCOPE_IDENTITY()?"

A: Both return the last auto-generated identity value, but the scope differs critically. @@IDENTITY returns the last identity value inserted in the entire session — including values inserted by triggers. SCOPE_IDENTITY() returns only the last identity value inserted in the current scope (current stored procedure or batch). If your INSERT fires a trigger that inserts into another table with an IDENTITY column, @@IDENTITY returns that trigger table's ID, not your original table's ID — a serious bug. Always use SCOPE_IDENTITY() in application code.

Q3 · Window Functions

Q: "What is the difference between RANK(), DENSE_RANK(), and ROW_NUMBER()?"

A: All three assign numbers to rows based on ORDER BY within a window. ROW_NUMBER() always assigns unique sequential numbers: 1,2,3,4 — no ties, no gaps. RANK() handles ties by giving tied rows the same number but skipping the next: 1,2,2,4 (two rows tied at rank 2, rank 3 is skipped). DENSE_RANK() handles ties without skipping: 1,2,2,3. Use ROW_NUMBER() for pagination or deduplication. Use RANK()/DENSE_RANK() for leaderboards where ties matter. DENSE_RANK is preferred when you don't want gaps in ranking.

Q4 · Transactions

Q: "What is XACT_STATE() and why do you check it in a CATCH block?"

A: XACT_STATE() returns the state of the current transaction: 1 = active and committable, 0 = no active transaction, -1 = active but uncommittable (doomed transaction). In a CATCH block, you must check XACT_STATE() before calling ROLLBACK because if there's no active transaction (0) and you call ROLLBACK, SQL Server throws an error. More critically, a value of -1 means the transaction is doomed — you MUST rollback, you cannot commit it even if you wanted to. This usually happens with certain error severities that automatically doom the transaction.

Q5 · Constraint Design

Q: "Why store UnitPrice in the OrderItems table if it already exists in Products?"

A: This is a denormalization by design, not by accident. Product prices change over time. If you always look up the price from the Products table, a customer's invoice would show today's price — not what they actually paid. For example, if a customer paid ₹74,999 for a phone in January and the price drops to ₹69,999 in March, their January invoice should still show ₹74,999. The UnitPrice in OrderItems captures the historical price at the moment of purchase, which is essential for accurate invoicing, accounting, and financial audits.
