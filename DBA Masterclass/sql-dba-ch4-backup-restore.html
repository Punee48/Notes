Tuesday, 3:47 AM. Your phone rings. It's the on-call alert system: "ShopCartDB: Disk I/O failure. Database offline."

You log in remotely. The disk hosting the data file failed — a hardware fault. The database is in SUSPECT mode. Without a backup, 2 million customer records and every order ShopCart ever received is gone.

With a backup strategy in place? You restore from last night's full backup + today's differential + log backups running every 15 minutes. Data loss: maximum 15 minutes. Restore time: 40 minutes. You're back online before most users wake up.

🎯 Goal: Build and automate a production backup strategy for ShopCart India, understand every backup type deeply, and practice a complete point-in-time restore — because in DBA work, an untested restore is not a backup.
1
RPO & RTO — The Two Numbers That Define Your Strategy

Before writing a single BACKUP command, a DBA must understand what the business needs. Two numbers define everything: RPO and RTO.

⏱️

RPO — Recovery Point Objective

How much data loss is acceptable? If ShopCart says "we can lose at most 15 minutes of orders," RPO = 15 minutes. This drives your log backup frequency. RPO = 15 min → log backups every 15 min.

🚀

RTO — Recovery Time Objective

How fast must we recover? If ShopCart says "we must be back online within 2 hours," RTO = 2 hours. This drives your full backup size (affects restore time) and HA solution (Chapter 5).

🎯

ShopCart India SLA

RPO = 15 minutes (customers expect orders to survive). RTO = 60 minutes (an hour of downtime = acceptable for 3 AM incident). This translates to: Nightly full + hourly differential + 15-min log backups.

⚠️

Untested Restore = No Backup

A backup that has never been restored is an assumption. The JD specifically says "regular restore testing." Schedule monthly restore drills to a separate server. Many DBAs discover their backups were corrupt only when disaster strikes.

2
The 3 Backup Types — How They Work Together
F
Sunday 11:00 PM

Full Backup — The Foundation

Copies the ENTIRE database: all data pages and enough of the transaction log to make it consistent. Self-contained — you can restore from this alone. Large (ShopCart = ~50 GB). Taken weekly or nightly. ALL subsequent differential and log backups build on top of this.

D
Monday 6:00 PM

Differential Backup — The Accelerator

Copies only data pages that changed SINCE the last FULL backup (not since the last diff). Grows over time: Monday diff = small, Saturday diff = large. Faster to take than a full backup. To restore: Full + latest Differential + log backups from the diff onward.

L
Every 15 minutes

Transaction Log Backup — The Time Machine

Backs up the active transaction log since the LAST log backup. Small and fast. Enables point-in-time restore — you can restore to ANY minute within the backup chain. ALSO truncates the inactive log, preventing the .ldf file from filling up. Requires FULL recovery model.

R
Disaster at 3:47 AM

Restore Sequence — Getting Back

Step 1: Restore Full WITH NORECOVERY. Step 2: Restore last Differential WITH NORECOVERY. Step 3: Restore each Log backup in order WITH NORECOVERY. Step 4: Final restore WITH RECOVERY (brings DB online). Optionally add STOPAT to specify exact restore time.

The Complete Backup Strategy — Scripted & Automated
📄 13_backup_strategy.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 13_backup_strategy.sql
-- PURPOSE: Complete automated backup system for ShopCart India
-- ADAPTS: to any database by changing the @DatabaseName variable
-- ════════════════════════════════════════════════════════════════

USE master;
GO

-- ══ STORED PROCEDURE: Dynamic backup with naming conventions ══════
CREATE OR ALTER PROCEDURE usp_BackupDatabase
(
    @DatabaseName  SYSNAME,
    -- SYSNAME = a system data type alias for NVARCHAR(128).
    -- Used for database/object names — the standard SQL Server type for identifiers.
    @BackupType    VARCHAR(4),
    -- BackupType: 'FULL', 'DIFF', or 'LOG'
    @BackupPath    NVARCHAR(500) = N'C:\SQLBackup\'
    -- DEFAULT parameter: if not specified, uses this path.
    -- N prefix = Unicode string literal (needed for NVARCHAR parameters).
)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @BackupFile  NVARCHAR(600);
    DECLARE @BackupName  NVARCHAR(200);
    DECLARE @SQL         NVARCHAR(2000);
    DECLARE @Timestamp   VARCHAR(20);

    -- Build timestamp: YYYYMMDD_HHMMSS for sortable filenames
    SET @Timestamp = CONVERT(VARCHAR, GETDATE(), 112)
                     + '_'
                     + REPLACE(CONVERT(VARCHAR, GETDATE(), 108), ':', '');
    -- CONVERT(VARCHAR, GETDATE(), 112) = '20240315' (date format 112 = YYYYMMDD)
    -- CONVERT(VARCHAR, GETDATE(), 108) = '03:47:22' (time format 108 = HH:MM:SS)
    -- REPLACE(..., ':', '') = '034722' (remove colons for filename compatibility)
    -- Combined: '20240315_034722' — sorts chronologically in file explorer.

    -- Build filename based on backup type
    SET @BackupFile = @BackupPath
                     + @DatabaseName
                     + '_'
                     + @BackupType
                     + '_'
                     + @Timestamp
                     + CASE
                           WHEN @BackupType = 'LOG'  THEN '.trn'
                           ELSE '.bak'
                       END;
    -- .trn = transaction log backup convention. .bak = full/diff backup.
    -- Example: 'C:\SQLBackup\ShopCartDB_LOG_20240315_034722.trn'
    -- WHY separate extensions? Makes it easy to script: delete .bak older than
    -- 7 days but keep .trn files for log chain continuity.

    SET @BackupName = @DatabaseName + ' ' + @BackupType
                      + ' Backup - ' + @Timestamp;

    -- Build the dynamic BACKUP command
    SET @SQL =
        CASE @BackupType
            WHEN 'FULL' THEN
                'BACKUP DATABASE [' + @DatabaseName + ']'
            WHEN 'DIFF' THEN
                'BACKUP DATABASE [' + @DatabaseName + '] WITH DIFFERENTIAL,'
            WHEN 'LOG' THEN
                'BACKUP LOG [' + @DatabaseName + ']'
        END
        + ' TO DISK = N''' + @BackupFile + ''''
        + ' WITH COMPRESSION,'
        -- COMPRESSION = reduces backup file size by 60-70%. Free on Standard+ editions.
        + ' CHECKSUM,'
        -- CHECKSUM = SQL Server computes a checksum during backup and verifies during restore.
        -- If the backup file is corrupt (bit rot, bad disk), CHECKSUM catches it.
        -- Without CHECKSUM, you might have a corrupt backup and not know until you need it.
        + ' STATS = 10,'
        -- STATS = 10 = print a progress message every 10% of backup completion.
        -- Useful in maintenance scripts to confirm backup is progressing.
        + ' NAME = N''' + @BackupName + '''';
        -- NAME = human-readable label stored in the backup header.
        -- Visible in SSMS when you browse backup contents or in msdb.dbo.backupset.

    PRINT 'Executing: ' + @SQL;

    BEGIN TRY
        EXEC sp_executesql @SQL;
        -- sp_executesql = safely executes a dynamic T-SQL string.
        -- WHY NOT EXEC(@SQL)? sp_executesql supports parameterization (prevents SQL injection
        -- in dynamic SQL) and allows plan reuse. Always prefer sp_executesql for dynamic SQL.
        PRINT 'Backup completed: ' + @BackupFile;
    END TRY
    BEGIN CATCH
        PRINT 'BACKUP FAILED: ' + ERROR_MESSAGE();
        THROW;
    END CATCH
END;
GO

-- ══ EXECUTE the backup procedure ════════════════════════════════
-- Full backup (weekly, Sunday night)
EXEC usp_BackupDatabase
    @DatabaseName = 'ShopCartDB',
    @BackupType   = 'FULL',
    @BackupPath   = N'C:\SQLBackup\';

-- Differential backup (hourly during business hours)
EXEC usp_BackupDatabase
    @DatabaseName = 'ShopCartDB',
    @BackupType   = 'DIFF';   -- uses default path C:\SQLBackup\

-- Log backup (every 15 minutes)
EXEC usp_BackupDatabase
    @DatabaseName = 'ShopCartDB',
    @BackupType   = 'LOG';
GO

-- ══ VERIFY the backup file (ALWAYS do this after backup) ════════
RESTORE VERIFYONLY
FROM DISK = N'C:\SQLBackup\ShopCartDB_FULL_20240315_230000.bak'
WITH CHECKSUM;
-- RESTORE VERIFYONLY = reads the backup file and validates the checksum.
-- Does NOT restore anything — just confirms the file is readable and intact.
-- WITH CHECKSUM = verifies the checksum we embedded during backup.
-- If this command succeeds: backup is physically intact.
-- RULE: Never trust a backup until VERIFYONLY passes. Automate this check.
GO

-- ══ CHECK backup history (from msdb) ════════════════════════════
SELECT TOP 20
    bs.database_name                           AS Database,
    CASE bs.type
        WHEN 'D' THEN 'Full'
        WHEN 'I' THEN 'Differential'
        WHEN 'L' THEN 'Log'
    END                                        AS BackupType,
    bs.backup_start_date                       AS StartTime,
    bs.backup_finish_date                      AS FinishTime,
    DATEDIFF(SECOND,bs.backup_start_date,
              bs.backup_finish_date)           AS DurationSec,
    CAST(bs.backup_size / 1048576.0 AS DECIMAL(10,1)) AS SizeMB,
    CAST(bs.compressed_backup_size / 1048576.0
              AS DECIMAL(10,1))                AS CompressedMB,
    bmf.physical_device_name                  AS FilePath,
    bs.has_checksum                            AS HasChecksum
FROM      msdb.dbo.backupset             bs
JOIN      msdb.dbo.backupmediafamily     bmf
    ON bs.media_set_id = bmf.media_set_id
WHERE     bs.database_name = 'ShopCartDB'
ORDER BY  bs.backup_start_date DESC;
-- msdb.dbo.backupset = SQL Server writes a row here for every backup taken.
-- msdb.dbo.backupmediafamily = the physical file location of each backup.
-- This query is your backup audit log. Run it to answer:
-- "When was the last backup taken?" / "Is the backup schedule running?"
-- 1048576 = 1 MB in bytes (1024 × 1024). Dividing bytes → MB.

Point-in-Time Restore — The Real Disaster Recovery

This is the moment of truth. The disk failed at 3:47 AM. Here's the exact sequence to restore ShopCartDB to 3:45 AM — losing only 2 minutes of data.

📄 14_point_in_time_restore.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 14_point_in_time_restore.sql
-- SCENARIO: Disk failure at 3:47 AM. Restore to 3:45 AM.
-- We have: Sunday FULL, Monday DIFF (6 PM), LOG backups every 15 min.
-- STEPS: FULL (NORECOVERY) → DIFF (NORECOVERY) → LOGs (NORECOVERY) → RECOVERY
-- ════════════════════════════════════════════════════════════════

USE master;
GO

-- ══ PRE-RESTORE: Take a tail-log backup (if DB is still accessible) ═
-- If the database is still online/accessible (partial failure), take a final
-- log backup to capture any committed transactions between last scheduled
-- log backup and the point of failure. This closes the log chain.

BACKUP LOG ShopCartDB
TO DISK = N'C:\SQLBackup\ShopCartDB_LOG_TAILLOG.trn'
WITH NORECOVERY,
     COMPRESSION,
     CHECKSUM;
-- NORECOVERY in BACKUP LOG = puts the database in RESTORING state immediately.
-- Prevents new connections from coming in after the tail-log backup.
-- WHY: Ensures no new transactions are written while you're about to restore.
-- If the DB is completely offline/corrupt, skip this step.
GO

-- ══ STEP 1: Restore the FULL backup (WITH NORECOVERY) ════════════
RESTORE DATABASE ShopCartDB
FROM DISK = N'C:\SQLBackup\ShopCartDB_FULL_20240314_230000.bak'
WITH
    NORECOVERY,
    -- NORECOVERY = restore the data but DO NOT bring the database online yet.
    -- The DB goes into "Restoring..." state — users cannot connect.
    -- WHY: We must apply more backups (diff + logs) on top of this.
    -- If we used RECOVERY here, the DB comes online but we can't apply more backups.
    -- NORECOVERY = "I have more backups to apply, keep the DB in restoring state."
    REPLACE,
    -- REPLACE = overwrite the existing database. Use carefully.
    -- Needed when restoring over an existing database of the same name.
    STATS = 10,
    MOVE N'ShopCartDB_Data'  TO N'C:\SQLData\ShopCartDB.mdf',
    MOVE N'ShopCartDB_Log'   TO N'C:\SQLData\ShopCartDB_log.ldf';
-- MOVE: Redirects the restore to NEW file paths.
-- WHY USE MOVE:
--   1. Restoring to a different server (different drive letters)
--   2. The original path doesn't exist on this server
--   3. Restoring a copy alongside the original (need different file names)
-- MOVE 'LogicalName' TO 'PhysicalPath'
-- LogicalName = the NAME we used in CREATE DATABASE (ShopCartDB_Data, ShopCartDB_Log)
-- Find logical names: RESTORE FILELISTONLY FROM DISK = '...' before restoring.
GO

-- ══ STEP 2: Apply the DIFFERENTIAL backup (WITH NORECOVERY) ══════
RESTORE DATABASE ShopCartDB
FROM DISK = N'C:\SQLBackup\ShopCartDB_DIFF_20240315_180000.bak'
WITH NORECOVERY, STATS = 10;
-- Apply Monday 6 PM differential. Still NORECOVERY — more logs to come.
-- The DB is now at the state of Monday 6 PM.
-- All transactions between Sunday full and Monday 6 PM diff are applied.
GO

-- ══ STEP 3: Apply LOG backups in ORDER (still NORECOVERY) ════════
-- Apply each 15-minute log backup from 6 PM to 3:45 AM in sequence.
-- Log backups must be applied in CHRONOLOGICAL ORDER without gaps.
-- A SINGLE MISSING log backup breaks the chain — restore stops.

RESTORE LOG ShopCartDB
FROM DISK = N'C:\SQLBackup\ShopCartDB_LOG_20240315_180000.trn'
WITH NORECOVERY;

RESTORE LOG ShopCartDB
FROM DISK = N'C:\SQLBackup\ShopCartDB_LOG_20240315_181500.trn'
WITH NORECOVERY;

-- ... (continue for each 15-minute log backup)
-- ... Apply all logs up to and including the 3:30 AM backup

-- Last log before disaster: apply WITH STOPAT for exact point-in-time
RESTORE LOG ShopCartDB
FROM DISK = N'C:\SQLBackup\ShopCartDB_LOG_20240315_033000.trn'
WITH
    NORECOVERY,
    STOPAT = '2024-03-15 03:45:00';
-- STOPAT = apply log transactions only up to this timestamp.
-- Everything committed AFTER 3:45:00 is NOT applied.
-- This is "point-in-time recovery" — the crown jewel of FULL recovery model.
-- Data loss: only 2 minutes (3:45 to 3:47 when disk failed).
-- Without log backups (SIMPLE recovery): data loss = everything since Sunday = 29 hours.
GO

-- ══ STEP 4: Apply the tail-log backup (if taken) ════════════════
RESTORE LOG ShopCartDB
FROM DISK = N'C:\SQLBackup\ShopCartDB_LOG_TAILLOG.trn'
WITH NORECOVERY;
GO

-- ══ FINAL STEP: Bring the database ONLINE (WITH RECOVERY) ════════
RESTORE DATABASE ShopCartDB
WITH RECOVERY;
-- RECOVERY = "we're done applying backups — bring the database online."
-- SQL Server rolls back any uncommitted transactions (ensures consistency).
-- The database transitions from "Restoring..." to "Online".
-- Users can connect again. ShopCart is back.
-- TIMELINE: Disaster at 3:47 AM → Restore complete ~4:30 AM = 43 minutes.
-- RTO achieved: under 60-minute SLA. RPO achieved: 2 minutes of data loss.
GO

-- ══ VERIFY the restore was successful ════════════════════════════
SELECT name, state_desc, recovery_model_desc
FROM sys.databases
WHERE name = 'ShopCartDB';
-- Expected: state_desc = ONLINE, recovery_model_desc = FULL
-- If state is SUSPECT or RESTORING: something went wrong in the restore sequence.

DBCC CHECKDB — Database Integrity Verification
📄 15_dbcc_integrity.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- DBCC CHECKDB = Database Consistency Checker.
-- The most important maintenance command a DBA runs.
-- Checks: data page consistency, index consistency, system catalog integrity.
-- RULE: Run weekly. If CHECKDB reports errors, take a backup IMMEDIATELY
--       and investigate — corruption spreads.
-- ════════════════════════════════════════════════════════════════

DBCC CHECKDB ('ShopCartDB')
WITH
    NO_INFOMSGS,
    -- NO_INFOMSGS = suppress informational messages. Only show errors/warnings.
    -- Without this: thousands of "DBCC results for 'X'" lines fill the output.
    -- Use NO_INFOMSGS for scheduled jobs; remove it for manual investigation.
    ALL_ERRORMSGS;
    -- ALL_ERRORMSGS = show ALL error messages (default limits per object).
    -- Critical for production: don't truncate error output.

-- ══ LIGHTWEIGHT alternative for large databases ═══════════════════
-- Full CHECKDB on a 1 TB database can take hours. Use PHYSICAL_ONLY
-- for a fast check (checks page structure, not logical consistency).

DBCC CHECKDB ('ShopCartDB')
WITH PHYSICAL_ONLY, NO_INFOMSGS;
-- PHYSICAL_ONLY = check page headers and checksums only. Much faster.
-- Run PHYSICAL_ONLY daily, full CHECKDB weekly.

-- ══ CHECK LAST DBCC RUN DATE ══════════════════════════════════════
SELECT
    DATABASEPROPERTYEX('ShopCartDB', 'LastGoodCheckDbTime')
    AS LastGoodCheckDB;
-- DATABASEPROPERTYEX = returns a database property by name.
-- LastGoodCheckDbTime = when CHECKDB last ran successfully with zero errors.
-- If this is NULL or very old: alert! A database never checked could be silently corrupt.
-- Best practice: alert if LastGoodCheckDbTime > 7 days old.

-- ══ AUTOMATED MAINTENANCE SCHEDULE (schedule via SQL Agent) ══════
-- Sunday 11:00 PM — Full Backup + CHECKDB
-- Monday–Saturday 11:00 PM — Differential Backup
-- Every hour, 7 AM – 10 PM — Differential Backup
-- Every 15 minutes, 24×7 — Transaction Log Backup
-- Weekly — ALTER INDEX REBUILD (fragmented indexes)
-- Weekly — UPDATE STATISTICS
-- Daily — DBCC CHECKDB WITH PHYSICAL_ONLY
-- Monthly — TEST RESTORE to DR server (restore + CHECKDB on restored copy)
Interview Preparation

Backup & Restore — CGI Interview Questions

Q1 · Backup Strategy

Q: "What backup strategy would you implement for a 200 GB production OLTP database with RPO of 30 minutes and RTO of 2 hours?"

A: With a 200 GB database, FULL backups will take significant time, so I'd schedule them weekly (Sunday night off-peak) with compression enabled — compressed, a 200 GB database might back up to ~60 GB in 20–30 minutes. Differential backups every 2 hours during business hours capture the day's changes without the full overhead. Transaction log backups every 30 minutes (matching our RPO) ensure we can do point-in-time recovery to any 30-minute window. For RTO of 2 hours: restoring a 200 GB full + one differential + ~12 hours of logs should complete within RTO. I'd also pre-stage the backup files on the restore server during business hours to reduce restore time in a real incident.

Q2 · Log Management

Q: "The transaction log file is growing out of control and the disk is almost full. What do you do?"

A: First, I check the recovery model — if it's FULL but log backups aren't scheduled, the log can never auto-truncate and will grow indefinitely. Immediate fix: take a transaction log backup, which truncates inactive log portions and reclaims space within the file. Then check for open long-running transactions using DBCC OPENTRAN or sys.dm_exec_sessions — a stuck transaction prevents log truncation regardless of backups. I'd also check log_reuse_wait_desc in sys.databases: 'LOG_BACKUP' means we need log backups; 'ACTIVE_TRANSACTION' means a transaction is blocking truncation. After fixing the root cause, I can SHRINK the log file (DBCC SHRINKFILE) if needed — though shrinking is temporary and causes fragmentation, so I'd pre-size it properly afterward.

Q3 · Restore Scenarios

Q: "What is WITH NORECOVERY vs WITH RECOVERY in a RESTORE command?"

A: WITH NORECOVERY leaves the database in a "Restoring..." state — it applies the backup data but does not roll back uncommitted transactions or bring the database online. You use this when you have more backups to apply on top (differential or log backups). WITH RECOVERY tells SQL Server "this is the final restore — roll back uncommitted transactions and bring the database online." You only use RECOVERY on the very last restore in the sequence. A common mistake is using RECOVERY too early — for example, restoring the full backup WITH RECOVERY, which opens the database but then you can't apply the differential or logs because the restore chain is broken.

Q4 · DBCC CHECKDB

Q: "DBCC CHECKDB reported allocation errors on a production database. What are your next steps?"

A: Allocation errors mean SQL Server's internal bookkeeping (GAM/SGAM/PFS pages) is inconsistent with actual data. Immediate steps: 1) Take a full backup RIGHT NOW even of the corrupt state — I need the most recent data for comparison. 2) Check when the last clean CHECKDB ran using DATABASEPROPERTYEX to understand how long corruption may have existed. 3) Try DBCC CHECKDB WITH REPAIR_ALLOW_DATA_LOSS as a last resort — but this is destructive (deletes corrupt pages). 4) Better option: restore from the last known clean backup and apply logs up to just before corruption began. 5) Investigate root cause: failing disk, bad RAM, or storage controller issue — because corruption is usually a hardware symptom, not a SQL Server bug.
