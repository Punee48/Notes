Monday morning, 9:15 AM. Your phone rings. Priya, the product manager: "Arjun, our order listing page is taking 8 seconds. Customers are abandoning carts. The dev team says it's the database. Fix it."

You open SSMS and run the health check from Chapter 1. You see a query consuming 3.2 billion logical reads. Billion. The Orders table has 2 million rows and there's not a single index beyond the primary key.

This is your first real DBA war. Performance tuning is the most high-value, most visible skill in the JD. Let's build the toolkit that turns 8-second queries into 80-millisecond queries.

🎯 Goal: Understand HOW SQL Server finds data, build the right indexes, read execution plans, and use DMVs to proactively catch slow queries — before users complain.
1
How SQL Server Finds Data — The Mental Model

Before we optimize anything, we need to understand the two ways SQL Server retrieves rows. This is the foundation of all index work.

📚

Table Scan (Full Scan)

SQL Server reads every single page of the table, top to bottom. On a 2-million-row Orders table, this means reading ~16,000 data pages. Acceptable for tiny tables or when you need >30% of rows. Otherwise: catastrophic.

🎯

Index Seek

SQL Server navigates a B-tree index like a book index — jumps directly to the relevant rows. For a 2-million-row table, finds a specific CustomerID in 3–4 page reads instead of 16,000. This is the target.

🔄

Index Scan

Reads all rows IN the index (not the whole table). Better than a table scan if the index is narrow, but still sequential. Appears when the index doesn't cover all needed columns or predicate isn't selective.

🔑

Key Lookup (RID Lookup)

Found the row in the non-clustered index, but the query needs columns not in the index. SQL Server jumps back to the clustered index to fetch missing columns. Expensive at scale — often eliminated with covering indexes.

2
Index Types — Clustered vs Non-Clustered

🗂️ Clustered Index

  • The table IS the index (B-tree leaf pages = data pages)
  • Only ONE per table (physically sorts the rows)
  • Default: primary key gets clustered index
  • Lookups by clustered key = fastest possible
  • Range queries on the key are very efficient
  • Inserts into the middle can cause page splits

📑 Non-Clustered Index

  • Separate structure pointing TO the table rows
  • Up to 999 per table (but don't create 999)
  • Leaf pages contain index key + row locator
  • Key lookup needed if columns not in index
  • Covering index = include all needed columns
  • Write overhead: every DML updates the index
⚠️
Index Over-Creation is Real: Every index you create speeds up SELECTs but slows down INSERTs, UPDATEs, and DELETEs — because SQL Server must update every index on every write. ShopCart's order inserts (high-frequency) can be hurt by excessive indexes on the Orders table. Balance is everything.

USE ShopCartDB;

-- ══ STEP 1: Recreate with bigger dataset for tuning demo ══════════
-- First, let's see what SQL Server does WITHOUT indexes.
-- Enable statistics to see I/O and time cost:

SET STATISTICS IO ON;
-- SET STATISTICS IO ON = after each query, prints how many 8KB pages were read.
-- "logical reads" = pages read from the buffer pool (RAM).
-- "physical reads" = pages read from disk (cache miss).
-- HIGH logical reads = table/index scans. LOW logical reads = index seeks.

SET STATISTICS TIME ON;
-- SET STATISTICS TIME ON = prints parse, compile, and execution time in milliseconds.
-- "CPU time" = actual CPU work. "elapsed time" = wall-clock time.
-- After tuning, compare BEFORE and AFTER logical reads + elapsed time.

-- ══ THE SLOW QUERY (simulating the 8-second problem): ════════════
SELECT
    o.OrderID,
    c.FirstName, c.LastName,
    o.OrderDate,
    o.TotalAmount
FROM       Orders    o
INNER JOIN Customers c  ON o.CustomerID = c.CustomerID
WHERE      o.Status = 'Processing'
    AND    o.OrderDate >= '2024-01-01'
ORDER BY   o.OrderDate DESC;
-- Without indexes on Status or OrderDate:
-- Table Scan on Orders = reads ALL 2M rows.
-- Logical reads: ~16,000 pages. Elapsed: 8+ seconds.
-- Now press Ctrl+M in SSMS to enable "Include Actual Execution Plan" and run again.
-- You'll see a Table Scan icon with a warning triangle = missing index suggestion.

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
GO

-- ══ CREATE INDEX 1: Non-Clustered on Orders(Status, OrderDate) ════
CREATE NONCLUSTERED INDEX IX_Orders_Status_OrderDate
ON Orders (Status, OrderDate DESC)
INCLUDE (CustomerID, TotalAmount);
-- CREATE NONCLUSTERED INDEX = creates a separate B-tree structure for fast lookups.
-- IX_Orders_Status_OrderDate = naming convention: IX_ prefix, TableName, columns.
--   Consistent naming is a DBA standard. You'll thank yourself at 2 AM.
-- ON Orders (Status, OrderDate DESC) = the INDEX KEY COLUMNS.
--   Columns here are the ones in the WHERE clause and ORDER BY.
--   COLUMN ORDER MATTERS: Status first because WHERE filters on Status (equality).
--   Then OrderDate because we filter by range AND sort by it DESC.
--   Rule: Equality predicates first, then range predicates — this is "SARG" design.
--   (SARG = Search ARGument: predicates that can use an index efficiently)
-- INCLUDE (CustomerID, TotalAmount) = INCLUDED COLUMNS (not part of B-tree key).
--   These are stored at the LEAF level only — needed to answer the SELECT.
--   By including them, SQL Server doesn't need to do a Key Lookup to fetch them.
--   This makes the index a COVERING INDEX for this query.
--   WHY NOT put them in the key? Included cols don't affect the B-tree structure
--   and don't increase index depth — lower maintenance cost.
-- RESULT: SQL Server can now:
--   1. SEEK on Status = 'Processing' (jump directly to those rows)
--   2. Range filter on OrderDate >= 2024-01-01 (sequential read within the seek)
--   3. Return CustomerID, TotalAmount from the leaf (no key lookup)
-- Expected improvement: 16,000 logical reads → ~150 reads. Sub-100ms.

-- ══ CREATE INDEX 2: Covering index for customer lookup ════════════
CREATE NONCLUSTERED INDEX IX_Customers_Email
ON Customers (Email)
INCLUDE (FirstName, LastName, City, IsActive);
-- LOGIN QUERY: "Find customer by email at login time" — highest frequency query.
-- Index on Email (the search key) + Include login-relevant columns.
-- This is a covering index for the login flow: zero key lookups.

-- ══ CREATE INDEX 3: OrderItems for product-based lookups ══════════
CREATE NONCLUSTERED INDEX IX_OrderItems_ProductID
ON OrderItems (ProductID)
INCLUDE (OrderID, Quantity, UnitPrice);
-- "How many units of ProductID=1 have we sold total?"
-- Without index: scan all OrderItems rows.
-- With index: seek on ProductID = fast aggregation.

-- ══ FILTERED INDEX: Only index active products ════════════════════
CREATE NONCLUSTERED INDEX IX_Products_Active_Category
ON Products (CategoryID, Price)
INCLUDE (ProductName, StockQty)
WHERE IsActive = 1;
-- FILTERED INDEX = index only covers a SUBSET of rows (WHERE clause on the index).
-- WHY: 95% of product queries filter on IsActive = 1 (active products).
-- The 5% inactive products are never shown to customers.
-- By filtering, the index is SMALLER and FASTER than indexing all products.
-- Size: if 10% of products are inactive, the index is 10% smaller.
-- The query optimizer will use this index only when the query also has WHERE IsActive = 1.
-- This is a powerful technique for "soft-delete" tables.
GO

-- ══ VIEW INDEX FRAGMENTATION ══════════════════════════════════════
-- WHY: As data is inserted/deleted, index pages become fragmented.
-- Fragmentation = wasted space and sequential scans jumping around disk.
-- Check fragmentation weekly and rebuild/reorganize as needed.

SELECT
    obj.name                          AS TableName,
    idx.name                          AS IndexName,
    ROUND(ips.avg_fragmentation_in_percent,1)  AS FragPct,
    ips.page_count                     AS Pages,
    CASE
        WHEN ips.avg_fragmentation_in_percent < 5   THEN 'OK — No action'
        WHEN ips.avg_fragmentation_in_percent BETWEEN 5 AND 30 THEN 'REORGANIZE'
        ELSE                                                          'REBUILD'
    END                               AS Recommendation
FROM sys.dm_db_index_physical_stats
    (DB_ID(), NULL, NULL, NULL, 'LIMITED')  ips
JOIN sys.objects  obj  ON ips.object_id = obj.object_id
JOIN sys.indexes  idx  ON ips.object_id = idx.object_id
                       AND ips.index_id  = idx.index_id
WHERE obj.type = 'U'
    AND ips.page_count > 100
ORDER BY ips.avg_fragmentation_in_percent DESC;
-- sys.dm_db_index_physical_stats = DMV returning fragmentation info per index.
-- Parameters: (DB_ID() = current DB, NULL = all objects, NULL = all indexes,
--              NULL = all partitions, 'LIMITED' = fast mode, no deep row-level scan)
-- avg_fragmentation_in_percent: Rule of thumb:
--   < 5%  = No action needed
--   5-30% = ALTER INDEX ... REORGANIZE (online, incremental compaction)
--   > 30% = ALTER INDEX ... REBUILD (full rebuild, MUCH faster after but LOCKS table)
--           Use WITH (ONLINE = ON) on Enterprise Edition for zero-downtime rebuilds.

-- ══ REBUILD a fragmented index ════════════════════════════════════
ALTER INDEX IX_Orders_Status_OrderDate
ON Orders
REBUILD WITH (FILLFACTOR = 80, ONLINE = OFF);
-- FILLFACTOR = 80 means leave 20% of each index page empty.
-- WHY: New inserts fill the empty space instead of splitting the page.
-- Page splits cause fragmentation AND brief I/O pauses.
-- Rule: high-insert tables → lower FILLFACTOR (80-85). Read-heavy → 100.
-- ONLINE = OFF = table is locked during rebuild (faster).
-- ONLINE = ON = no locks but requires Enterprise Edition.

DMVs — Your Real-Time Diagnostic Toolkit
📄 11_performance_dmvs.sql T-SQL
-- ════════════════════════════════════════════════════════════════
-- FILE: 11_performance_dmvs.sql
-- PURPOSE: The DBA's diagnostic toolkit — run these when things go wrong
-- These are your "CAT scan" of the database
-- ════════════════════════════════════════════════════════════════

-- ══ DMV 1: Top 10 most expensive queries (all-time cached) ════════
-- The SINGLE most important query for a production DBA.
-- Every query SQL Server executes is cached in the Plan Cache.
-- This DMV reads that cache and ranks by total resource cost.

SELECT TOP 10
    SUBSTRING(qt.text,
               qs.statement_start_offset / 2 + 1,
               (CASE WHEN qs.statement_end_offset = -1
                     THEN LEN(CONVERT(NVARCHAR(MAX), qt.text)) * 2
                     ELSE qs.statement_end_offset
               END - qs.statement_start_offset) / 2 + 1
    )                                            AS QueryText,
    -- SUBSTRING extracts just the problematic statement from the batch.
    -- statement_start_offset / 2 = byte offset ÷ 2 = character position
    -- (NVARCHAR uses 2 bytes per char; offset is in bytes)
    qs.execution_count                           AS Executions,
    qs.total_logical_reads / qs.execution_count   AS AvgLogicalReads,
    qs.total_worker_time   / qs.execution_count   AS AvgCPUus,
    qs.total_elapsed_time  / qs.execution_count   AS AvgElapsedUs,
    qs.total_logical_reads                        AS TotalLogicalReads,
    qp.query_plan                                 AS ExecutionPlan
    -- query_plan column = the XML execution plan. Click the value in SSMS
    -- to open the graphical execution plan. Direct path to the problem.
FROM        sys.dm_exec_query_stats    qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle)    qt
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle)  qp
ORDER BY    qs.total_logical_reads DESC;
-- sys.dm_exec_query_stats = cached stats for every query in the plan cache.
--   Persists since last SQL Server restart or until plan is evicted.
-- sys.dm_exec_sql_text = table-valued function returning query text from handle.
-- sys.dm_exec_query_plan = table-valued function returning XML execution plan.
-- ORDER BY total_logical_reads DESC = worst I/O offenders first.
-- You can change to ORDER BY total_worker_time for worst CPU offenders.

-- ══ DMV 2: Missing Indexes (what SQL Server WISHES existed) ════════
-- The Query Optimizer logs every index it "wished" existed while processing queries.
-- These are stored in DMVs and are GOLD for tuning sessions.

SELECT TOP 20
    ROUND(migs.avg_total_user_cost
          * (migs.avg_user_impact / 100.0)
          * migs.user_seeks, 0)         AS ImprovementScore,
    -- ImprovementScore = estimated benefit of creating this index.
    -- Formula: cost × impact% × usage count. Higher = more urgent.
    -- This is NOT absolute cost — it's a relative priority score.
    migs.user_seeks                    AS TimesNeeded,
    ROUND(migs.avg_user_impact,1)      AS EstImprovementPct,
    mid.statement                      AS TableName,
    mid.equality_columns               AS EqualityColumns,
    -- Columns used in = predicates (put FIRST in the index key)
    mid.inequality_columns             AS InequalityColumns,
    -- Columns used in >, <, BETWEEN, LIKE (put AFTER equality columns)
    mid.included_columns               AS SuggestedIncludes,
    -- Suggested INCLUDE columns to make it a covering index.
    'CREATE INDEX IX_'
        + REPLACE(REPLACE(mid.statement,'[',''),']','')
        + ' ON ' + mid.statement
        + ' (' + ISNULL(mid.equality_columns,'')
        + CASE WHEN mid.inequality_columns IS NOT NULL
               THEN ', ' + mid.inequality_columns ELSE '' END
        + ')'
        + CASE WHEN mid.included_columns IS NOT NULL
               THEN ' INCLUDE (' + mid.included_columns + ')' ELSE '' END
    AS SuggestedCreateStatement
    -- Auto-generates a CREATE INDEX statement from the DMV data.
    -- CAUTION: Don't blindly run these. The optimizer can suggest redundant indexes.
    -- Always evaluate: Does this overlap an existing index? Is the query frequent enough?
    -- RULE: Missing index DMVs reset on service restart. High score after only 1 day
    -- of uptime = check if it was during a data load vs normal operation.
FROM      sys.dm_db_missing_index_details        mid
JOIN      sys.dm_db_missing_index_groups         mig
    ON mid.index_handle  = mig.index_handle
JOIN      sys.dm_db_missing_index_group_stats    migs
    ON mig.index_group_handle = migs.group_handle
WHERE     mid.database_id = DB_ID()
ORDER BY  ImprovementScore DESC;

-- ══ DMV 3: Blocking chains (who's blocking whom) ════════════════
SELECT
    blocking.session_id       AS BlockingSessionID,
    bt.text                   AS BlockingQuery,
    blocked.session_id        AS BlockedSessionID,
    wt.text                   AS BlockedQuery,
    blocked.wait_type         AS WaitType,
    blocked.wait_time / 1000  AS WaitSec
FROM        sys.dm_exec_requests  blocked
JOIN        sys.dm_exec_requests  blocking
    ON blocked.blocking_session_id = blocking.session_id
CROSS APPLY sys.dm_exec_sql_text(blocked.sql_handle)   wt
CROSS APPLY sys.dm_exec_sql_text(blocking.sql_handle)  bt
WHERE blocked.blocking_session_id > 0;
-- blocking_session_id > 0 = this session IS being blocked by someone.
-- Self-join on dm_exec_requests: "blocked" sessions joined to their "blocker".
-- WHY IT MATTERS: In a 24×7 production system, long-running transactions
-- hold locks and block other queries. One rogue report query can cascade-block
-- thousands of application requests. This query shows the chain immediately.

-- ══ DMV 4: Unused indexes (find what to DROP) ═════════════════════
SELECT
    OBJECT_NAME(i.object_id)  AS TableName,
    i.name                     AS IndexName,
    ius.user_seeks             AS Seeks,
    ius.user_scans             AS Scans,
    ius.user_updates           AS Updates
    -- user_updates = how many times this index was MODIFIED (insert/update/delete).
    -- If updates >> (seeks + scans): this index costs more to maintain than it helps.
    -- CANDIDATE FOR DROPPING.
FROM sys.indexes              i
LEFT JOIN sys.dm_db_index_usage_stats ius
    ON i.object_id = ius.object_id
    AND i.index_id = ius.index_id
    AND ius.database_id = DB_ID()
WHERE OBJECTPROPERTY(i.object_id, 'IsUserTable') = 1
    AND i.index_id > 0
    AND ISNULL(ius.user_seeks,0) = 0
    AND ISNULL(ius.user_scans,0) = 0
ORDER BY ISNULL(ius.user_updates,0) DESC;
-- CAUTION: Index usage stats reset on restart. Run this only after weeks of
-- normal production load — not immediately after deployment.
-- Always script DROP before executing — you may need to re-create it.

Query Anti-Patterns — What NOT To Write

These are the patterns that destroy performance in production. As a DBA, you'll find these in code reviews and query tuning sessions constantly.

#Anti-PatternWhy It's BadFix
1SELECT *Fetches all columns — many unneeded. Prevents covering indexes. Breaks code when schema changes.Always name columns explicitly.
2Function on column in WHERE
WHERE YEAR(OrderDate) = 2024		Makes the column non-SARGable. SQL Server cannot use an index on OrderDate — full scan.WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01'
3NOLOCK hint everywhere
WITH (NOLOCK)		Reads uncommitted data (dirty reads). Can return rows being rolled back = incorrect results. Data integrity risk.Use READ COMMITTED SNAPSHOT Isolation (RCSI) at DB level instead.
4Implicit conversions
WHERE CustomerID = '1'		CustomerID is INT but you pass a VARCHAR string. SQL Server converts every row — index unusable.Match data types: WHERE CustomerID = 1
5Cursor for row-by-rowSQL Server processes one row at a time = RBAR (Row By Agonizing Row). 100× slower than set-based operations.Rewrite as set-based UPDATE/INSERT...SELECT. Use CTEs or window functions.
6LIKE '%keyword%'Leading wildcard forces a full table scan. No index can help with a leading %.Use Full-Text Search (FTS) for text search. Or LIKE 'keyword%' (no leading %).
7UPDATE without WHEREUpdates EVERY row. Classic disaster. No transaction = no rollback.Always test with SELECT first. Wrap in BEGIN TRAN. Verify row count before COMMIT.
📄 12_anti_patterns_fixed.sql T-SQL
-- ══ Anti-Pattern 2 FIX: Non-SARGable → SARGable ══════════════════

-- BAD: Function wraps column — index on OrderDate cannot be used
SELECT * FROM Orders
WHERE YEAR(OrderDate) = 2024  AND  MONTH(OrderDate) = 3;
-- SQL Server must call YEAR() and MONTH() for EVERY row = table scan

-- GOOD: Range predicate — index on OrderDate can seek directly
SELECT OrderID, CustomerID, TotalAmount
FROM   Orders
WHERE  OrderDate >= '2024-03-01'
    AND  OrderDate  <  '2024-04-01';
-- SQL Server seeks to '2024-03-01' in the index and reads sequentially until
-- '2024-04-01'. Only reads the relevant pages = dramatically fewer logical reads.

-- ══ Anti-Pattern 3 FIX: NOLOCK → RCSI ════════════════════════════
ALTER DATABASE ShopCartDB
SET READ_COMMITTED_SNAPSHOT ON;
-- RCSI = Read Committed Snapshot Isolation.
-- WHAT IT DOES: Readers (SELECT) don't take shared locks.
--   Instead they read a row-version snapshot from tempdb (version store).
-- RESULT: Readers never block writers, writers never block readers.
--   This eliminates the #1 reason developers add WITH(NOLOCK) hints.
-- WHY BETTER THAN NOLOCK: RCSI always reads committed data (no dirty reads).
--   NOLOCK reads uncommitted data — you can read a row being rolled back.
-- COST: Uses tempdb for row versions. Monitor tempdb space after enabling.
-- ENABLE ONCE, forget about NOLOCK forever. This is enterprise best practice.
Interview Preparation

Performance Tuning — CGI Interview Questions

Q1 · Index Fundamentals

Q: "What is the difference between a clustered and non-clustered index? Can a table have multiple clustered indexes?"

A: A clustered index physically sorts the table data on disk — the B-tree leaf pages ARE the data pages. A table can have exactly ONE clustered index because you can only physically sort data one way. A non-clustered index is a separate B-tree structure that contains the indexed column values plus a pointer (row locator) to the actual data row. You can have up to 999 non-clustered indexes per table. When a non-clustered index doesn't contain all columns needed by a query, SQL Server does a Key Lookup (back to the clustered index) to fetch missing columns — this is where INCLUDE columns help by making covering indexes.

Q2 · Execution Plans

Q: "A query was fast yesterday but slow today. How do you investigate?"

A: First, I check if the query plan changed using sys.dm_exec_query_stats — compare cached plan stats to historical baselines. Common causes: 1) Stale statistics — run UPDATE STATISTICS. 2) Parameter sniffing — the plan was compiled for one parameter value but runs with another; fix with OPTION(RECOMPILE) or OPTIMIZE FOR. 3) Index fragmentation — check sys.dm_db_index_physical_stats and rebuild if >30%. 4) Data volume change — if rows increased dramatically, the optimizer might choose a different (worse) plan. 5) Lock blocking — check sys.dm_exec_requests for blocking_session_id. I'd also check if any schema changes or index drops happened using the default trace.

Q3 · NOLOCK

Q: "A developer added WITH(NOLOCK) to all queries to fix blocking. Is this correct?"

A: It's the wrong solution to a real problem. NOLOCK (READ UNCOMMITTED isolation) tells SQL Server to read data without taking shared locks, which eliminates read-write blocking. But the cost is dirty reads — you can read rows that are currently being modified and might be rolled back, meaning you're reading data that technically never existed in a committed state. For a financial system like ShopCart, a dirty read could show a payment as completed when it's actually being rolled back. The correct solution is enabling Read Committed Snapshot Isolation (RCSI) at the database level — this uses row versioning in tempdb so readers never block writers and always read committed data. No code changes needed, no dirty reads.

Q4 · Statistics

Q: "What are statistics in SQL Server and why do they matter for performance?"

A: Statistics are histograms that describe the distribution of data in a column or index. The query optimizer uses statistics to estimate how many rows a predicate will return — the cardinality estimate. For example, if it estimates a WHERE clause returns 100 rows, it might choose an index seek. If it estimates 100,000 rows, it might choose a table scan. Stale statistics cause bad estimates, leading to bad execution plans. By default SQL Server auto-updates statistics when about 20% of rows change (SQL 2016+ uses a dynamic threshold). As a DBA, I schedule weekly UPDATE STATISTICS with FULLSCAN on large tables during maintenance windows because the auto-update sample rate can be too low for very large tables.

🧪 Chapter 3 Practice Tasks

  1. Enable STATISTICS IO and TIME. Run the slow query (without indexes). Record logical reads. Then create IX_Orders_Status_OrderDate. Run the same query. Compare the logical reads — document the % improvement.
  2. Open Execution Plan (Ctrl+M). Look for Table Scan icons (warning triangles). Hover over an operator — read the "Estimated Rows" vs "Actual Rows". A large gap = bad statistics or parameter sniffing.
  3. Run the Missing Indexes DMV (file 11). Does SQL Server suggest any indexes you haven't created yet? Review the SuggestedCreateStatement and decide if it's worth creating.
  4. Test the anti-pattern: Write WHERE YEAR(OrderDate) = 2024 and check execution plan. Then rewrite as range predicate. Compare plans — do you see the change from Scan to Seek?
  5. Enable RCSI: Run ALTER DATABASE ShopCartDB SET READ_COMMITTED_SNAPSHOT ON. Verify with SELECT name, is_read_committed_snapshot_on FROM sys.databases WHERE name = 'ShopCartDB'.
