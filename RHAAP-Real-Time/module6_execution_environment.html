MODULE 6

The Execution Environment

Packaging everything Ansible needs into one portable, versioned container

1. What Is an Execution Environment, Really?

Puneeth, here's a simple way to picture it. In Module 5 we said Collections are like an "international calling plan" for Ansible. Now think of the Execution Environment (EE) as the entire phone itself — a self-contained container image that already has Ansible Core, the exact Collections we need (amazon.aws, azure.azcollection, kubernetes.core, redhat.openshift), and every underlying Python library those collections secretly depend on (like boto3 for AWS), all baked in together, at exact pinned versions.

When AAP runs your job, it doesn't run Ansible from "wherever it happens to be installed" — it launches this exact container image, runs the playbook inside it, and then throws the container away. This is what makes results reproducible: the same EE image gives the same behavior whether it runs in DEV testing today or in PROD six months from now.

2. Why the Default AAP Execution Environment Is Not Enough

AAP ships with a default EE, but it is intentionally general-purpose and lightweight — it does not include every possible cloud SDK, because that would make it enormous and slow to pull. It typically does not include the Azure Python SDK or the specific version of boto3/botocore our AWS collection needs, and it may not include the Kubernetes Python client needed for OpenShift Virtualization at all.

What happens if you try to use the default EE anyway: Your playbook will often fail with a confusing Python error like ModuleNotFoundError: No module named 'boto3', even though your collections/requirements.yml looks completely correct. This is a very common beginner trap — people assume installing the Ansible Collection is enough, forgetting that many collections are just a thin Ansible-flavored wrapper around a separate Python SDK, which must also be present inside the EE.

3. ansible-builder — The Tool That Builds Our EE

ansible-builder is a command-line tool (made by Red Hat) that reads a small set of definition files and produces a container image — you never have to hand-write a raw Dockerfile/Containerfile yourself, which keeps the process consistent and auditable.

4. execution-environment.yml, Line by Line

---
version: 3

images:
  base_image:
    name: registry.redhat.io/ansible-automation-platform-24/ee-minimal-rhel9:latest

dependencies:
  galaxy: collections/requirements.yml
  python: requirements.txt
  system: bindep.txt

additional_build_steps:
  append_base:
    - RUN echo "Built for ABC Payments Multi-Cloud Provisioning Project"

Explaining every line:

version: 3 — the schema version of the execution-environment.yml format itself; this tells ansible-builder which set of rules to use to read the rest of the file. Different major versions of ansible-builder expect different schema versions.

images: base_image: name: — the starting container image everything else gets layered on top of. We deliberately choose Red Hat's official minimal RHEL 9 EE base image rather than a random public image, because it is already hardened and supported under a Red Hat subscription — an important point for a regulated company.

dependencies: galaxy: — points to the exact collections/requirements.yml file we built in Module 5, so ansible-builder knows which Ansible Collections to install into the image.

dependencies: python: — points to a requirements.txt file listing raw Python packages (like boto3) that need to be installed with pip, separately from the Ansible Collections.

dependencies: system: — points to a bindep.txt file listing operating-system-level packages (like gcc or openssl-devel) that some Python packages need already present in order to compile/install successfully.

additional_build_steps — an escape hatch for any extra shell command you need run during the image build, here just a harmless label; in real projects this is sometimes used to add internal CA certificates so HTTPS to internal APIs is trusted.

5. The Supporting Files

requirements.txt — Python SDK dependencies 
boto3>=1.34.0,<2.0.0
botocore>=1.34.0,<2.0.0
msrestazure>=0.6.4
azure-mgmt-compute>=30.0.0
azure-mgmt-network>=25.0.0
azure-identity>=1.15.0
kubernetes>=29.0.0,<30.0.0
openshift>=0.13.2

boto3 / botocore — the official AWS SDK for Python; the amazon.aws collection's modules are actually thin Ansible wrappers that internally call these libraries to talk to the AWS API. Without them, every AWS module fails immediately.

azure-mgmt-compute, azure-mgmt-network, azure-identity — the Azure equivalents; different Azure resource types (VM, network) each need their own small SDK package, and azure-identity handles the authentication flow from Module 3.

kubernetes — the official Python client for the Kubernetes API, which kubernetes.core modules use under the hood to talk to any Kubernetes-compatible API, including OpenShift's.

openshift — an additional Python library some redhat.openshift collection modules need for OpenShift-specific object types beyond plain Kubernetes.

bindep.txt — system-level packages 
gcc [platform:rpm]
python3-devel [platform:rpm]
openssl-devel [platform:rpm]
libffi-devel [platform:rpm]

These are not Python packages — they are operating-system packages (installed via dnf/yum inside the container) that some Python packages need present in order to compile native extensions during installation. The [platform:rpm] tag tells ansible-builder "only install this on RPM-based systems like RHEL," since bindep can target multiple OS families.

6. Building and Registering the EE

Developer machine / CI pipeline | v ansible-builder build -t abc-multicloud-ee:1.0.0 -f execution-environment.yml | v Container image is built locally | v podman push abc-multicloud-ee:1.0.0 registry.abcbank.local/aap/abc-multicloud-ee:1.0.0 | v Private Container Registry (internal, not Docker Hub) | v Registered inside AAP as an "Execution Environment" object | v Attached to our Job Templates so every job run uses this exact image
Recommended for production — versioning and rollback: Always tag the image with a real version number (1.0.0), never just latest. If a new EE version breaks something in DEV, you can instantly point the Job Template back at the previous tag (1.0.0 instead of 1.1.0) while you investigate — this is your entire rollback strategy for the EE layer, and it takes seconds because no rebuild is needed, just a different tag reference.
