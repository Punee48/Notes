MODULES 27 – 29

Azure Lifecycle, OpenShift Lifecycle, and the Full Production Architecture

Proving the design actually works across all three platforms, then zooming out to see the whole system

Puneeth, Module 26 walked the Payment Gateway request through AWS, start to finish. The real test of a good multi-cloud design is: does the exact same story hold together on Azure and OpenShift too, with only the platform-specific pieces changing? Let's find out.

Module 27 — The Same Request, Provisioned on Azure

Same requirement, different platform: Application: Payment Gateway · Environment: DEV · Platform: Azure · Servers: pay-dev-app01, pay-dev-app02 · OS: RHEL 9 · CPU 4 · RAM 16GB · Disk 100GB · Port 8080 · Owner: Payments · Cost Center: PAY001

StageWhat changes vs. the AWS run in Module 26
RequirementNothing — same Module 1 checklist, same business need
Network / FirewallFirewall rule targets management.azure.com and login.microsoftonline.com instead of the AWS EC2 endpoint (Module 4)
AuthenticationAAP's Azure Credential (Service Principal or Managed Identity via Entra ID, Module 3) is used instead of the AWS IAM Role
Survey submittedRequester picks cloud_platform=azure — every other Survey answer is identical
WorkflowUnchanged — same Validate → Approval → Provisioning → Post-Config → Validation → CMDB → Notification nodes (Module 16)
Provisioninginclude_role: "{{ cloud_platform }}_provision" now dynamically resolves to azure_provision (Module 11) instead of aws_provision — this is the one line from Module 13 doing all the work
Post-configuration onwardIdentical — linux_baseline, validation, and notification roles don't know or care which cloud created the server
The real lesson of Module 27: Almost nothing about our Workflow, Survey, or post-provisioning code changed. The entire platform swap was absorbed by one dynamic include_role line and a different Credential object — this is exactly the payoff of the "one role per platform" design decision from Module 7.

Module 28 — The Same Request, Provisioned as an OpenShift Virtualization VM

Same requirement, third platform: Application: Payment Gateway · Environment: DEV · Platform: OpenShift Virtualization · same servers, same sizing, same business owner and cost center.

StageWhat changes vs. AWS/Azure
AuthenticationAAP's OpenShift Credential (namespace-scoped Service Account token, Module 3) instead of a cloud IAM identity
Provisioninginclude_role now resolves to openshift_provision (Module 12) — submits a VirtualMachine + DataVolume manifest instead of calling a direct create-VM API
IP discoveryRequires the extra "wait until phase is Running" poll from Module 12 — AWS/Azure both return the IP immediately on creation
Everything after thatIdentical — same add_host handoff into linux_baseline, validation, notification

AWS vs Azure vs OpenShift Virtualization — What's Actually Reusable

validate_request role (Module 9)✅ 100% reused — validation logic doesn't care which platform is chosen
provision_server.yml entry point (Module 13)✅ 100% reused — only the resolved role name changes

linux_baseline, validation, notification roles✅ 100% reused — they only care that a reachable Linux server landed in newly_provisioned

Workflow Template (Module 16)✅ 100% reused — same nodes, same approval gate
Why this matters for your resume and interviews: You can honestly say roughly 70-80% of this codebase is shared across all three clouds — only the actual "create the compute resource" step is platform-specific. That ratio is a strong, concrete number to quote when explaining the value of this design.

The one-paragraph summary you should be able to say confidently in an interview: "We built one AAP-driven pipeline that can provision a server on AWS, Azure, or OpenShift Virtualization from a single ServiceNow request. Requirement gathering, validation, the Workflow structure, and all post-provisioning steps are shared code; only the actual compute-creation step is platform-specific, selected dynamically at runtime with include_role. Every request is validated, approved, tagged for cost tracking, rolled back safely on failure in lower environments, and fully audited from request to CMDB record."
