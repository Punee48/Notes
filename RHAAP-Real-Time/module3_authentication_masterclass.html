Authentication Masterclass

How Ansible Automation Platform proves who it is to AWS, Azure, and OpenShift

1. Quick Recap — And Why Authentication Comes Before Code

Puneeth, imagine AAP as a new employee who just joined the company. Before this new employee can create even one server, security has to answer a basic question: "who are you, and what are you allowed to touch?" That question, and the process of answering it safely, is what this module is about.

This is one of the most commonly asked interview topics for any cloud automation role, so we will go slowly and build the full picture for all three platforms.

The one idea to hold onto through this whole module: in a good enterprise design, AAP never uses a permanent username/password. It always uses a short-lived, narrowly-scoped identity that can be revoked instantly and cannot be reused if it leaks. Every section below is really just a different platform's way of achieving that same goal.
AWS

How AAP Authenticates to AWS

Here is the full journey a request takes, from AAP to the actual EC2 API call:

AAP | AAP has a "Credential" object configured v Credential (AWS type) | holds either a long-term key OR a role to assume v IAM Role / Access Mechanism | v AWS STS (Security Token Service) | "AssumeRole" API call happens here v Temporary Credentials (valid for a short time, e.g. 1 hour) | v AWS API (this is what actually receives the request) | v EC2 (the instance gets created)
IAM Users vs IAM Roles — why Roles win in production

An IAM User is like giving someone a permanent badge with a password that never expires unless someone remembers to rotate it. An Access Key ID + Secret Access Key pair belongs to that user, and if it leaks — say, someone accidentally commits it to Git — an attacker can use it forever until someone notices and deletes it.

An IAM Role is different: nobody "owns" it permanently. Instead, something (an EC2 instance, or in our case AAP itself) is allowed to temporarily "put on" that role's identity by calling STS AssumeRole. AWS's Security Token Service checks that the caller is allowed to assume that role, and if yes, it hands back temporary credentials — an access key, secret key, and session token that expire automatically, usually within an hour. Even if these leak, they become useless very soon on their own.

Cross-Account Provisioning — why this matters at a real company

Large companies often keep DEV, QA, and PROD in separate AWS accounts, purely so a mistake in DEV can never accidentally touch PROD resources. AAP typically lives in one central "automation" account, and it assumes a different IAM Role in each target account (DEV Role, QA Role, PROD Role) depending on which environment it is provisioning into. This is exactly why the Role ARN is usually a variable, not a fixed value, in your playbooks.

Recommended for production: Use IAM Roles with STS AssumeRole, never long-lived IAM User access keys, for anything beyond a personal lab. If AAP itself runs on an EC2 instance, it can use an Instance Profile so it never even needs to store a key — AWS injects temporary credentials automatically. Rotate any credential that must exist regularly, and always follow least privilege: grant only the exact EC2/IAM actions the playbook needs, nothing broader.

3. Example IAM Policy for EC2 Provisioning

Below is a realistic (trimmed) least-privilege policy. Notice it does not say "Action": "*" — a real security team would reject that instantly.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowEC2Provisioning",
      "Effect": "Allow",
      "Action": [
        "ec2:RunInstances",
        "ec2:DescribeInstances",
        "ec2:DescribeImages",
        "ec2:DescribeSubnets",
        "ec2:DescribeSecurityGroups",
        "ec2:CreateTags"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AllowPassRoleForInstanceProfile",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::123456789012:role/payment-app-role"
    }
  ]
}

Explaining every important line, in plain words:

"Version": "2012-10-17" — this is simply the fixed AWS policy-language version number; every IAM policy has this exact line, it is not something you choose per project.

"Sid" — a friendly label for the statement, purely for humans reading the policy later; AWS ignores it functionally.

"Effect": "Allow" — tells AWS this statement grants permission (the alternative is "Deny", used to explicitly block something even if another statement allows it).

ec2:RunInstances — the actual permission that lets Ansible's amazon.aws.ec2_instance module create a new EC2 instance; without this exact permission, the API call is rejected with an AccessDenied error.

ec2:Describe* actions — these are read-only permissions the playbook needs just to look up things like which AMI or subnet exists, before it tries to create anything.

ec2:CreateTags — required separately from RunInstances, because tagging is technically a different permission — a very common "gotcha" that causes tagging to silently fail if forgotten.

iam:PassRole on a specific Resource ARN — this is a subtle but critical line: if you want the new EC2 instance to have an Instance Profile attached to it, AAP's own role must be explicitly allowed to "pass" that specific role to the new instance. Without this, EC2 creation fails even though RunInstances itself succeeded in the policy simulator.

"Resource": "arn:aws:...:role/payment-app-role" — notice this is scoped to one exact role, not "*". This stops AAP from being able to attach a more powerful role than the one it's supposed to use for this application — a real least-privilege control.

AZURE

How AAP Authenticates to Azure

AAP | v Azure Credential (configured inside AAP) | v Service Principal / Managed Identity | v Microsoft Entra ID (formerly Azure AD — the identity provider) | validates the identity and issues a token v OAuth Token (short-lived, scoped to specific permissions) | v Azure Resource Manager API (ARM — the front door for all Azure resource operations) | v Azure VM (gets created)
TermPlain-English meaning
Tenant IDIdentifies which company's Microsoft Entra ID directory this login belongs to
Subscription IDIdentifies the billing/resource boundary the VM will be created inside
Service PrincipalA non-human "application identity" in Entra ID, with a Client ID and either a Client Secret or a certificate — this is what AAP typically uses when it runs outside Azure
Managed IdentityAn identity Azure automatically assigns to an Azure resource (for example, if AAP itself runs on an Azure VM) — no secret to store or rotate at all
RBAC Role (Contributor / Custom Role)Defines exactly what the Service Principal or Managed Identity is allowed to do — Contributor is broad, a Custom Role scoped to just VM/network actions is safer
Recommended for production: Use a Managed Identity whenever AAP's execution nodes actually run inside Azure — it removes secrets entirely. When AAP runs outside Azure (on-prem, or another cloud), use a Service Principal with a certificate rather than a plain Client Secret where possible, scoped with a Custom Role instead of the broad built-in Contributor role.
OPENSHIFT

How AAP Authenticates to OpenShift

AAP | v OpenShift Credential (configured inside AAP) | v Service Account + Token | v OpenShift API (built on top of the Kubernetes API) | v Kubernetes API (authenticates and authorizes the request via RBAC) | v KubeVirt (the operator that understands VirtualMachine objects) | v VirtualMachine (gets created in the target namespace)
TermPlain-English meaning
Service AccountA non-human identity that lives inside a specific namespace, used by automation instead of a real user login
TokenA credential tied to the Service Account, presented on every API call to prove identity
Role / RoleBindingRole defines a set of permissions scoped to one namespace; RoleBinding attaches that Role to a specific Service Account — this is how you keep AAP's OpenShift access limited to only the payment-dev namespace, for example
ClusterRole / ClusterRoleBindingSame idea, but the permission applies cluster-wide instead of one namespace — normally avoided for an application-scoped automation like ours, since it's far broader than needed
Recommended for production: Create a dedicated Service Account per namespace (or per application team), bind it to a Role — never a ClusterRole — that only allows the specific verbs (get, list, create, update, delete) on the specific resources (virtualmachines, datavolumes, persistentvolumeclaims) it truly needs. This means even if the token leaks, the blast radius is one namespace, not the entire cluster.

Interview tip: If you can say this one sentence confidently, you will stand out: "In all three platforms, AAP never stores a permanent password — it holds a short-lived, narrowly-scoped token that is requested fresh and expires automatically, and its permissions follow least privilege through IAM policies, Azure RBAC, or Kubernetes RBAC."
