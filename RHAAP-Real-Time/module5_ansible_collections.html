Ansible Collections

The building blocks that let Ansible actually speak to AWS, Azure, and OpenShift

1. What Is a Collection, in Plain Words?

Puneeth, think about it this way: Ansible Core, by itself, is like a phone that can only make calls in your own country. It knows how to copy files, run shell commands, manage services — but it has no idea, out of the box, how to speak "AWS language" or "Azure language" or "Kubernetes language." A Collection is like an international calling plan you add to that phone — a packaged bundle of modules, roles, plugins, and documentation that teaches Ansible how to talk to one specific system.

For our project, we need three main collections: amazon.aws (teaches Ansible to speak AWS), azure.azcollection (teaches Ansible to speak Azure), and kubernetes.core together with redhat.openshift (teaches Ansible to speak OpenShift/Kubernetes, including VirtualMachine objects).

2. What Is FQCN, and Why Do We Always Use It?

FQCN stands for Fully Qualified Collection Name. Instead of writing just ec2_instance in a task, we always write amazon.aws.ec2_instance.

PartMeaning
amazonThe namespace — usually the publisher/vendor, here it means "published by the Amazon/AWS collection maintainers"
awsThe collection name itself, inside that namespace
ec2_instanceThe actual module name inside that collection
Why FQCN matters: Imagine two different collections both happen to ship a module simply called vm — one for VMware, one for OpenShift. If your playbook just says vm:, Ansible has to guess which one you meant, and in a large enterprise with dozens of collections installed, that guess can be wrong — silently running the wrong module, or failing outright. Writing the full redhat.openshift.kubevirt_vm removes all ambiguity, makes the playbook self-documenting (anyone reading it instantly knows which collection provides that task), and is considered mandatory style in every serious enterprise Ansible codebase.

3. Automation Hub vs Ansible Galaxy — Where Collections Come From

Ansible GalaxyRed Hat Automation Hub
Who publishes hereAnyone in the open-source communityRed Hat-certified and Red Hat-validated partners only
SupportNo official support — best effort from the communityBacked by a Red Hat support contract
Used in production banks/telcos?Rarely, except well-known community collectionsYes — this is the standard enterprise source
AccessPublic internetUsually mirrored internally as a Private Automation Hub, so servers never need direct internet access
Recommended for production: Pull certified collections (like amazon.aws, azure.azcollection) from a company-hosted Private Automation Hub, not the public internet. This gives security teams control over exactly which collection versions are approved, and avoids the firewall/proxy complexity from Module 4 for every single job run.

4. Building collections/requirements.yml, Line by Line

This file tells AAP (or ansible-galaxy collection install) exactly which collections, and which versions, your project depends on.

---
collections:
  - name: amazon.aws
    version: ">=7.0.0,<8.0.0"
    source: https://automation-hub.example.com/api/galaxy/

  - name: azure.azcollection
    version: ">=2.0.0,<3.0.0"
    source: https://automation-hub.example.com/api/galaxy/

  - name: kubernetes.core
    version: ">=3.0.0,<4.0.0"
    source: https://automation-hub.example.com/api/galaxy/

  - name: redhat.openshift
    version: ">=3.0.0,<4.0.0"
    source: https://automation-hub.example.com/api/galaxy/

  - name: community.general
    version: ">=8.0.0,<9.0.0"
    source: https://automation-hub.example.com/api/galaxy/

Explaining every line, in plain words:

--- — the standard marker that tells any YAML parser "a new YAML document starts here." Every Ansible YAML file begins with this.

collections: — the top-level key this file is required to have; it tells ansible-galaxy "everything below is a list of collections to install," as opposed to a roles: requirements file, which has a different structure.

- name: amazon.aws — the FQCN of the collection to install; note it is written as namespace.collection, without a module name, because here we're asking for the whole collection.

version: ">=7.0.0,<8.0.0" — a version range, not one fixed number. This means "give me any 7.x release, but never jump to 8.x automatically." We'll explain exactly why this matters in the next section on pinning.

source: https://automation-hub.example.com/api/galaxy/ — explicitly tells ansible-galaxy to fetch this collection from your company's Private Automation Hub URL, instead of defaulting to the public galaxy.ansible.com — this is what keeps collection installs inside the corporate network.

community.general — a broad, community-maintained collection with many small general-purpose modules (file/text manipulation, misc utilities) that our post-provisioning and validation roles will lean on later in the masterclass.

5. Version Pinning — Why We Never Just Say "Latest"

The problem with no version pin: If your requirements.yml doesn't specify a version, Ansible always installs the newest release available. Imagine your playbook works perfectly today, and three months later a new major version of amazon.aws is released that renames a parameter you're using. Your PROD job template runs that night, uses the new version automatically, and fails — with nobody having changed a single line of your own code. This is one of the most common real "it worked yesterday" production incidents in Ansible automation.

Pinning to a range (like >=7.0.0,<8.0.0) is the balanced enterprise approach: you still get bug fixes and small improvements within version 7, but you are protected from a breaking major-version jump happening silently. When you do want to move to version 8, you do it deliberately — test it, then bump the number in Git through a reviewed Pull Request.

ApproachWhen it's used
No version specifiedPersonal lab/learning only — never in a real project
Exact pin (version: 7.2.0)Very strict regulated environments (some banking PROD pipelines) where every change must be an explicit, reviewed decision
Range pin (>=7.0.0,<8.0.0)Most common enterprise approach — our recommendation for this project

6. Hands-On Task

Write your own collections/requirements.yml file (on paper or in a text editor) that includes the five collections above, but change the version ranges to pin each one to a major version one higher than shown here (for example, amazon.aws pinned to >=8.0.0,<9.0.0). This is just to build the muscle memory of reading and writing version ranges correctly — the exact numbers don't matter yet.
