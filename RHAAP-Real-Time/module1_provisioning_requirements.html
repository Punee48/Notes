1. The Business Problem — Why This Project Exists

Imagine this real situation. You are a DevOps Engineer at a mid-size company. It could be a bank, a telecom company, or an e-commerce company — the problem is the same everywhere. One Monday morning, the Payment application team sends an email to the Infrastructure team:

“We need three RHEL servers for the Payment application in DEV. Names: pay-dev-app01, pay-dev-app02, pay-dev-app03. 4 CPU, 16 GB RAM, 100 GB disk. Application listens on port 8080. Cost center PAY001.”

Today, a human infrastructure engineer reads this email, logs into the AWS console, clicks around for twenty minutes, picks a VPC, picks a subnet, picks an AMI, creates the EC2 instances one by one, tags them by hand, and then emails back “done.” This takes half a day. If the same request needs to happen in Azure or in an OpenShift Virtualization cluster too, it takes even longer, and it is done differently by whichever engineer is on duty that day.

This is slow, this is inconsistent, and this is risky — one engineer might forget to encrypt a disk, another might put the server in the wrong security zone. Our job in this masterclass is to remove the manual clicking and replace it with one automated, repeatable pipeline that can create a server on any of the three platforms, the same correct way, every single time.

2. How It Works Today (Manual World)

Application Team | sends an email or raises a ticket v Infrastructure Engineer (a human) | logs into AWS / Azure / OpenShift console by hand v Server is created — but the *steps* depend on which engineer is doing the work that day | v Email reply: "Server is ready"
Why this matters for the interview: When someone asks “why did your company automate this,” you should never say “because automation is cool.” You say: manual provisioning was slow, inconsistent between engineers, and had no audit trail of who approved what. That is a business answer, not a tool answer — and that is what makes you sound experienced.

3. The Target Flow — What We Are Building

Now look at the flow we are going to build across this entire masterclass. Do not worry if some words like “Survey” or “CMDB” are new right now — we will unpack every single box in a later phase. For today, just understand the shape of the journey.

Application Team raises a request | v ServiceNow / AAP Survey (a structured form, not an email) | v Red Hat Ansible Automation Platform (AAP) | v Validation (are the values even allowed?) | +----+----+ | | Approved Rejected | v Platform Selection | +---------+---------+ | | | AWS Azure OpenShift Virtualization | | | EC2 Azure VM KubeVirt VM | v Post-Provision Configuration (hostname, users, agents...) | v Validation (did it really come up healthy?) | v CMDB / ServiceNow Update (record of truth) | v Notification (tell the requester it is done)

Notice something important: the email becomes a form (Survey), and the human engineer becomes AAP. Nothing about the underlying need changes — the Payment team still needs three RHEL servers. What changes is who does the clicking, and that "who" is now a machine that never gets tired, never forgets a step, and always leaves a record behind.

4. Why We Gather Requirements Before Writing Any Code

Here is a mistake that junior engineers make: they open a laptop, start writing an ec2_instance task, and only halfway through realize they don't know which VPC to use, or whether the disk needs to be encrypted, or who is going to own the server for cost tracking. Then they have to stop, ask questions, and rewrite the playbook.

An experienced automation engineer works the opposite way. Before opening an editor, they build a checklist of every piece of information the automation will ever need, and they go collect it from the right teams. Only once every value has an answer — or a clearly marked example placeholder — do they start writing YAML. This is exactly the discipline this masterclass will build in you, phase by phase.

7. Understanding Each Group in Simple Words

A long table like the one above is easy to memorize but hard to actually understand. So let's slow down and group these 25 fields into five simple buckets, and talk through why each bucket exists — not just what it is.

🟦 Identity Fields — "What is this server called, and who does it belong to?"

HostnameApplication NameEnvironmentOwnerCost Center

Think of this as the server's ID card. Without a correct hostname and environment, an engineer at 2 AM debugging a production outage could easily connect to the wrong machine — for example, fixing DEV when PROD is actually broken. The cost center exists purely for finance: at the end of the month, someone has to answer "why did we spend ₹40,000 on cloud compute," and the tag tells them exactly which team to bill.

🟩 Compute & Storage Fields — "How big does this server need to be?"

OS/VersionCPUMemoryDisk SizeAdditional Disks

These fields decide how much money the server costs every month and whether the application will actually run smoothly. If CPU or memory is too small, the application will crash under load. If it is too large, the company wastes money. This is why these numbers usually come from a load test the Application Team already did — they are not guesses.

🟨 Network Fields — "How does traffic reach this server?"

Network/Subnet/VLANDNS/DomainNTPProxyApplication Port

A server that is created but cannot be reached is useless. The subnet decides which part of the company network the server lives in — for example, DEV servers should never sit in the same network as PROD servers, otherwise a DEV mistake could affect real customers. NTP (time sync) sounds small, but wrong server time breaks SSL certificates, logging timestamps, and authentication tokens — this is a very common real production incident.

🟥 Security Fields — "Who is allowed in, and how is it protected?"

SSH AccessService AccountAntivirus/EDRFirewall Rules

In a bank or any regulated company, an auditor will eventually ask: "prove that only approved people can log into this server, and prove it has antivirus running." If these fields are missing from day one, the server is created "non-compliant," and someone has to go back and fix it later — which is far more work than doing it correctly during provisioning.

🟪 Operations Fields — "How do we keep this server healthy over time?"

MonitoringBackupLoggingPatching GroupSupport Group

Creating a server is only day one of its life. It may run for three years. These fields make sure that if it goes down, the right monitoring alert fires, the right team gets paged, its data is backed up, and it gets its monthly security patches automatically instead of being forgotten and becoming a security risk.
