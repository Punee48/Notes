Enterprise Git Project Structure

Organizing the multi-cloud provisioning codebase the way a production team would

1. Why Structure Matters

Puneeth, picture joining a new company and being handed a Git repository with fifteen playbooks, all sitting loose in one folder, no roles, no separation between AWS and Azure code, secrets mixed in with logic. It would take you days just to understand where to even start reading. A well-structured repository is a gift you give to your future self and to every teammate who joins after you — it tells a story just by its folder names, before anyone reads a single line of YAML.

3. Why Each Folder Exists

PathWhy it exists
README.mdThe front door — explains what this repo does, how to run it, and who owns it. The first thing any new engineer or auditor reads.
ansible.cfgProject-level Ansible settings (like which inventory to use by default, retry behavior) so every engineer and AAP itself behaves identically, instead of relying on whatever is in someone's personal ~/.ansible.cfg.
collections/requirements.ymlFrom Module 5 — the exact Collections this project depends on.
execution-environment.ymlFrom Module 6 — how to build the container image this project runs inside.
inventory/For cloud API provisioning, we mostly run against localhost (explained fully in Module 14) — this folder still exists so the project has one clear, explicit inventory source rather than relying on AAP's implicit default.
group_vars/Variables shared across a whole group of hosts/environments — for example, values that are true for every DEV server regardless of platform.
host_vars/Variables specific to one single host — kept as an explicit folder even if mostly empty today, ready for post-provisioning per-host overrides.
vars/aws.yml, azure.yml, openshift.ymlPlatform-specific defaults (like default instance size mappings) kept separate per platform so an Azure change can never accidentally affect AWS logic.
roles/Each folder is one reusable, testable unit of work — this is where almost all the real logic lives, not directly in playbooks.
roles/validate_request/Checks every input value (Module 9) before anything is created — the "gatekeeper" role.
roles/aws_provision/, azure_provision/, openshift_provision/One role per platform — this is what lets us plug in a new cloud later without touching the other two.
roles/linux_baseline/Post-provisioning configuration common to any new Linux server, regardless of which cloud created it.
roles/validation/Confirms the server actually came up healthy after creation — the "did it really work" check.
roles/notification/Tells the requester and updates CMDB/ServiceNow — the final step of the story from Module 1's target flow diagram.
playbooks/Thin orchestration files that just call roles in the right order — kept deliberately short and readable, with almost no logic of their own.
playbooks/provision_server.ymlThe single entry point AAP's Job Template actually launches — dynamically includes the correct platform role based on a variable (built in Module 13).
templates/Jinja2 template files (like the cloud-init config) that get rendered with real variable values at runtime, kept separate from logic so non-Ansible engineers can still read/edit them.
Why one role per platform, instead of one giant role with "if AWS / if Azure" everywhere: If AWS logic and Azure logic live in the same role, a bug fix for Azure risks accidentally breaking AWS, because both are tangled in the same files. Separate roles mean each platform's code can be changed, tested, and even reviewed by a different subject-matter engineer, completely independently — this is the same reasoning a software engineer uses when splitting code into separate modules instead of one giant script.
