The AWS Master Playbook

A complete, production-style EC2 provisioning role — every line explained

1. What We're Building

Puneeth, this is the module where everything from Modules 1–9 finally comes together into real, working code: the requirement checklist, the AWS-specific values, the authentication flow, the collections, the variable design, and the validation gate. What follows is the aws_provision role's tasks/main.yml — the heart of our AWS automation.

2. The Full Role

---
# roles/aws_provision/tasks/main.yml

- name: Look up the latest approved RHEL 9 AMI
  amazon.aws.ec2_ami_info:
    region: "{{ aws_region }}"
    owners: ["self"]
    filters:
      name: "golden-rhel9-*"
      state: available
  register: ami_lookup

- name: Set the AMI ID to use for this build
  ansible.builtin.set_fact:
    ami_id: "{{ (ami_lookup.images | sort(attribute='creation_date') | last).image_id }}"

- name: Map CPU/memory to an AWS instance type
  ansible.builtin.set_fact:
    instance_type: "{{ instance_type_map[cpu ~ '-' ~ memory] | default('m5.large') }}"

- name: Check whether this server already exists (idempotency)
  amazon.aws.ec2_instance_info:
    region: "{{ aws_region }}"
    filters:
      "tag:Name": "{{ vm_name }}"
      instance-state-name: ["running", "stopped"]
  register: existing_instance

- name: Provision the EC2 instance
  amazon.aws.ec2_instance:
    name: "{{ vm_name }}"
    region: "{{ aws_region }}"
    image_id: "{{ ami_id }}"
    instance_type: "{{ instance_type }}"
    vpc_subnet_id: "{{ subnet_id }}"
    security_group: "{{ security_group_id }}"
    iam_instance_profile: "{{ instance_profile_name }}"
    key_name: "{{ ssh_key_name }}"
    volumes:
      - device_name: /dev/sda1
        ebs:
          volume_size: "{{ disk_size }}"
          encrypted: true
          kms_key_id: "{{ kms_key_id }}"
          delete_on_termination: true
    tags:
      Name: "{{ vm_name }}"
      Application: "{{ application }}"
      Environment: "{{ environment }}"
      Owner: "{{ owner }}"
      CostCenter: "{{ cost_center }}"
    wait: true
    state: running
  register: ec2_result
  when: existing_instance.instances | length == 0

- name: Wait for SSH to become reachable
  ansible.builtin.wait_for:
    host: "{{ ec2_result.instances[0].private_ip_address }}"
    port: 22
    delay: 10
    timeout: 300
  when: ec2_result is changed

- name: Add the new instance to in-memory inventory for post-config
  ansible.builtin.add_host:
    name: "{{ vm_name }}"
    groups: newly_provisioned
    ansible_host: "{{ ec2_result.instances[0].private_ip_address }}"
    instance_id: "{{ ec2_result.instances[0].instance_id }}"
  when: ec2_result is changed

- name: Produce the provisioning report
  ansible.builtin.set_stats:
    data:
      vm_name: "{{ vm_name }}"
      instance_id: "{{ ec2_result.instances[0].instance_id | default(existing_instance.instances[0].instance_id) }}"
      private_ip: "{{ ec2_result.instances[0].private_ip_address | default(existing_instance.instances[0].private_ip_address) }}"
      cloud_platform: aws
      status: "{{ 'created' if ec2_result is changed else 'already_existed' }}"

3. Line-by-Line Explanation

amazon.aws.ec2_ami_info — a read-only "info" module (notice it ends in _info, the Ansible naming convention for modules that only look things up and never change anything) that searches for AMIs matching our golden-image naming pattern, owned by our own account rather than the public marketplace.

filters: name: "golden-rhel9-*" — restricts the search to images following our internal naming convention; using a wildcard means we don't have to hardcode one specific AMI ID that will eventually go stale.

register: ami_lookup — captures the module's JSON output (a list of matching images) into a variable so later tasks can use it.

ami_lookup.images | sort(attribute='creation_date') | last — a Jinja2 pipeline: sort the list of matching images by creation date, then take the last one, meaning "the newest golden image available" — this keeps new servers always built from the latest approved image without us updating the playbook every time a new image is published.

instance_type_map[cpu ~ '-' ~ memory] — the ~ operator concatenates strings in Jinja2, so 4 and 16 become the lookup key "4-16" into a dictionary (defined in vars/aws.yml) that maps CPU/memory combinations to real AWS instance type names — this is how "4 CPU, 16GB" from Module 1 becomes m5.xlarge without the requester ever needing to know AWS instance type names.

ec2_instance_info with a tag:Name filter — this is our idempotency check (explained more in the next section): before creating anything, we ask AWS "does an instance with this exact Name tag already exist and is it running or stopped?"

amazon.aws.ec2_instance — the actual instance-creation module; every parameter below it maps directly to a value we gathered in earlier modules: vpc_subnet_id/security_group from Module 2's network values, iam_instance_profile from Module 3's authentication design, volumes.ebs.encrypted/kms_key_id from Module 2's security fields.

tags: block — every tag here maps directly back to a Module 1 checklist field; this is what lets Finance later answer "what did PAY001 spend on cloud compute this month" by simply filtering on the CostCenter tag.

wait: true, state: running — tells the module to not just fire the API call and return immediately, but to actually wait until AWS reports the instance as fully running before the task is considered complete — this matters because the very next task needs a real IP address to test SSH against.

when: existing_instance.instances | length == 0 — the entire creation task is skipped if our idempotency check already found a matching instance; this single line is what stops duplicate servers on a re-run, which we unpack fully in Module 19.

wait_for: ... port: 22 — actively polls the new instance's private IP on port 22 until SSH responds or the 300-second timeout is hit; this confirms not just "AWS says it's running" but "we can actually reach it," which is a meaningfully different and more useful check.

add_host — this is the bridge from "provisioning via cloud API" to "configuring via SSH," which Module 17 covers in depth; it adds the brand-new server into Ansible's in-memory inventory under a group called newly_provisioned, so a later play can target that group directly by name.

set_stats — writes structured data into the AAP job's "artifacts," visible in the Job Template output and usable by later Workflow nodes (Module 16) — this is how the final Notification/CMDB steps know the instance ID and IP without re-querying AWS.

4. Why This Playbook Is Idempotent

Run the playbook | v Check: does an instance named "pay-dev-app01" already exist? | +----+----+ | | Yes No | | Skip Create creation the instance | | +----+----+ | v Report the (existing or new) instance details either way
Why this matters: Without the ec2_instance_info check and the when condition, running this same playbook twice — say, because a Job Template got accidentally launched twice — would create two EC2 instances both trying to use the name pay-dev-app01, doubling the cost and confusing every downstream system. This check-then-act pattern is the standard way idempotency is achieved when a module itself doesn't already guarantee it by name.
