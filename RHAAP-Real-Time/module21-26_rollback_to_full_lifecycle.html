Module 21 — Rollback Strategy

Imagine this exact sequence goes wrong:

VM created ✅ ↓ Disk attached ✅ ↓ Network configured ✅ ↓ Post-provision configuration ❌ FAILED (e.g. monitoring agent install failed)

Now what? There are four possible responses, and choosing the wrong one by default is a real production mistake:

OptionWhen it's the right call
Delete the VM (full rollback)DEV/QA environments, or when the failure happened very early (e.g. the VM itself never finished booting) — cheap to just start over
Preserve the VM, flag it "unhealthy"PROD, or when the VM and its disk are expensive/slow to recreate, and a human should decide next steps rather than an automatic delete
Create an incident ticketAlways, for PROD failures — even if you also decide to delete, the incident record matters for audit and root-cause tracking
Retry automaticallyOnly for known-transient issues (e.g. SSH not reachable yet) — never for failures that indicate a real configuration problem, since blindly retrying those just wastes time and can mask the real issue
Our recommended default for this project: DEV/QA — automatically roll back (delete) on any failure, since recreating is cheap and fast, and speed matters more than caution there. PROD — never auto-delete; preserve the resource, mark it clearly (a tag like provisioning_status=failed), raise an incident automatically, and let a human engineer decide whether to fix forward or roll back manually. This asymmetry — aggressive auto-rollback in low environments, cautious human-in-the-loop in PROD — is a very common, very defensible enterprise pattern.
- name: Environment-aware rollback on failure
  block:
    - name: Run post-provision configuration
      ansible.builtin.include_role:
        name: linux_baseline

  rescue:
    - name: DEV/QA - delete the failed resource automatically
      ansible.builtin.include_role:
        name: "{{ cloud_platform }}_deprovision"
      when: environment in ['dev', 'qa']

    - name: PROD/UAT - tag as failed and stop, do not delete
      ansible.builtin.debug:
        msg: "PROD/UAT failure — VM preserved for investigation, incident will be raised"
      when: environment in ['uat', 'prod']

    - name: Always raise an incident on failure
      ansible.builtin.include_role:
        name: notification
      vars:
        notification_type: "incident"

when: environment in ['dev', 'qa'] vs ['uat', 'prod'] — this single conditional is what encodes our whole rollback policy directly in code, rather than leaving it as a decision an engineer has to remember to make manually every time.

Module 22 — Logging and Auditing

An auditor's favorite question is: "show me exactly who did what, and when, for this specific server." Here is everything we need to be able to answer that instantly.

What we trackWhere it comes from
Who requested the serverThe AAP user who launched the Job Template/Workflow, or the ServiceNow requester field (Module 23)
Who approved itThe AAP user who actioned the Approval Node (Module 16)
When the job ranAAP Job's built-in start/finish timestamps
Which playbook version ranThe exact Git commit hash AAP's Project sync recorded at launch time
Cloud account / subscription / clusterThe Credential object used, visible in the Job's Credential summary
VM ID and IPset_stats artifacts from Modules 10-12
Change NumberThe Survey answer from Module 15, carried through as a Workflow variable
Job ID and final resultAAP's own Job record — Success/Failed, with the full task-by-task log retained
Why the Git commit hash matters so much: "Update Revision on Launch" (Module 14) means every job run is tagged with the exact commit of the playbook that executed — so six months later, if someone asks "what did this automation actually do on that date," you can check out that exact commit and read the real code that ran, not just today's version of the repository.

Module 23 — ServiceNow Integration (Concept)

ServiceNow Catalog Item ("Request a Server") | v Requester fills the ServiceNow form | v Manager Approval (inside ServiceNow's own approval workflow) | v ServiceNow calls the AAP API (REST call to launch our Workflow Job Template, passing form fields as extra_vars — the Custom Credential Type built in an earlier module) | v AAP Workflow runs (everything from Modules 13-20) | v AAP calls back to ServiceNow's API (or ServiceNow polls the job status) | v CMDB record created/updated with VM ID, IP, owner | v ServiceNow ticket automatically closed, requester notified

The key integration idea: ServiceNow becomes the requester-facing "front door," while AAP stays the actual automation engine — neither system tries to do the other's job. ServiceNow is good at forms, approvals, and tracking tickets; AAP is good at actually talking to AWS/Azure/OpenShift.

The universal troubleshooting order, regardless of platform: Symptom → check the Job's task-level log first (what exact task/module failed) → check the platform's own event/activity log (CloudTrail, Azure Activity Log, oc describe) → identify root cause → apply the narrowest possible fix → add a Module 9-style validation check so the same mistake can't reach production silently again.

Module 25 — Testing

Feature branch ↓ Pull Request opened ↓ yamllint + ansible-lint run automatically (CI) ↓ Syntax check: ansible-playbook --syntax-check ↓ Molecule / role-level test (where applicable) ↓ Code Review by a teammate ↓ Merge to main ↓ AAP Project Sync picks up the new commit ↓ Test in DEV → QA → UAT → PROD (same playbook, different environment variable each time)
ToolWhat it catches
yamllintYAML formatting issues — indentation, trailing spaces, line length
ansible-lintAnsible-specific best-practice violations — missing FQCN, no changed_when on a shell task, deprecated syntax
ansible-playbook --syntax-checkBasic YAML/Jinja2 syntax errors, without actually running anything
MoleculeActually runs a role against a test container/instance and asserts the end state is correct — closest thing to a true unit test for a role
Why the same playbook, not different playbooks per environment: If DEV and PROD ran genuinely different code, testing in DEV would prove nothing about PROD. Our design instead keeps one playbook, and only the environment variable (and its associated group_vars) changes — so a successful DEV test is real evidence the PROD run will behave the same way.
