Variable Design

Turning the Module 1 checklist into real, well-organized Ansible variables

1. The Story So Far

Puneeth, remember the Payment Gateway checklist from Module 1 — hostname, CPU, memory, environment, owner, cost center? Those are not just facts on paper anymore; they need to become real variables our playbooks can read. The question this module answers is: of all the places Ansible lets you put a variable, which place should each one of our 25 fields actually live in? Getting this wrong is one of the most common sources of confusing bugs in real Ansible projects — a variable silently being overridden by another one you forgot existed.

2. Every Kind of Variable, and When to Use It

Variable TypeWhere it livesGood example from our project
Role Defaultsroles/aws_provision/defaults/main.ymlA sensible fallback like root_volume_size: 100 — used only if nothing else overrides it
Role Varsroles/aws_provision/vars/main.ymlValues the role itself controls and generally should not be overridden, like an internal mapping table
group_varsgroup_vars/all.yml, group_vars/aws.ymlShared values like ntp_server: ntp.abcbank.local, true for every DEV server on that platform
host_varshost_vars/pay-dev-app01.ymlA one-off override, like a specific server needing extra disk, that shouldn't apply to its siblings
extra_varsPassed at runtime, e.g. by AAPThe exact request-specific values: vm_name, cpu, memory, application
Survey VariablesDefined in the AAP Job Template Survey (Module 15)What the requester actually typed into the form — becomes extra_vars automatically
Credential VariablesInjected securely by AAP from a Credential object, never visible in plain YAMLAWS access key/secret, Azure Service Principal secret
Environment VariablesSet on the Execution Environment or Job TemplateHTTPS_PROXY, NO_PROXY from Module 4

The Variable File We'll Reuse Throughout This Masterclass

---
# vars/aws.yml
cloud_platform: aws
environment: dev
vm_name: pay-dev-app01
os_type: rhel9
cpu: 4
memory: 16
disk_size: 100
application: payment
owner: payment-team
cost_center: PAY001

cloud_platform: aws — the single variable that later decides, in Module 13, which platform-specific role actually runs; this is the "switch" for our whole multi-cloud design.

environment: dev — used both for naming and, importantly, for the input validation logic we build in Module 9 (only dev/qa/uat/prod are allowed).

vm_name, os_type, cpu, memory, disk_size — the direct technical values straight from the Module 1 checklist, used to build the actual AWS/Azure/OpenShift resource requests.

application, owner, cost_center — business metadata values used purely for tagging (Module 10) and CMDB updates (Module 22), not for sizing the server itself.

3. Variable Precedence — Who Wins When Two Places Disagree

Ansible has a well-defined order of who "wins" if the same variable name is set in more than one place. From lowest to highest priority (highest always wins):

1. Role defaults (lowest priority — easiest to override) 2. group_vars (all, then more specific groups) 3. host_vars 4. Play vars 5. Role vars 6. extra_vars (including AAP Survey answers) ← HIGHEST priority
Why this order matters in our project: We deliberately rely on this! Role defaults hold safe fallback values, but whatever the requester types into the AAP Survey (which becomes extra_vars) will always win over any default, no matter what. This is exactly the behavior we want — the person filling out the form should always control the final outcome, not a hardcoded fallback buried inside a role.

4. Where Secrets Should — and Should Never — Live

❌ Never here✅ Always here instead
Hardcoded inside a playbook or role taskAn AAP Credential object (Machine, AWS, Azure, or Vault type)
Committed into vars/aws.yml in Git, even "temporarily"Injected at runtime by AAP directly into environment variables the collection modules read automatically
Passed as a plain extra_vars string on the command linePulled from HashiCorp Vault / CyberArk via a lookup plugin at job runtime
Recommended for production: Nothing secret should ever be readable by opening a file in the Git repository — if you can grep and find a password or key in the repo, that is a security incident waiting to happen, and in a bank it would fail an audit outright.
