MODULE 9

Input Validation

The gatekeeper role — rejecting bad requests before they ever touch a cloud API

1. Why Validate Before Doing Anything Else

Puneeth, imagine someone fat-fingers the Survey and types environment as "Dev " with a trailing space, or types 500 for CPU by mistake. Without validation, that request sails straight through to AWS, and either fails halfway through with a confusing API error, or worse — actually succeeds and creates a hugely oversized, expensive server nobody asked for. The validate_request role's entire job is to catch problems like this at the very first step, in plain, readable error messages, before any cloud resource is touched.

2. The Validation Playbook

---
# roles/validate_request/tasks/main.yml

- name: Assert environment is one of the allowed values
  ansible.builtin.assert:
    that:
      - environment in ['dev', 'qa', 'uat', 'prod']
    fail_msg: "environment must be one of dev, qa, uat, prod — got '{{ environment }}'"
    success_msg: "Environment '{{ environment }}' is valid"

- name: Assert cloud_platform is supported
  ansible.builtin.assert:
    that:
      - cloud_platform in ['aws', 'azure', 'openshift']
    fail_msg: "cloud_platform must be aws, azure, or openshift — got '{{ cloud_platform }}'"

- name: Assert CPU is within allowed range
  ansible.builtin.assert:
    that:
      - cpu | int >= 1
      - cpu | int <= 16
    fail_msg: "cpu must be between 1 and 16 — got {{ cpu }}"

- name: Assert hostname matches naming standard
  ansible.builtin.assert:
    that:
      - vm_name is match('^[a-z]{3,10}-(dev|qa|uat|prod)-[a-z]{2,10}[0-9]{2}$')
    fail_msg: "vm_name '{{ vm_name }}' does not match naming standard app-env-role01"

- name: Fail explicitly if cost_center is missing
  ansible.builtin.fail:
    msg: "cost_center is required and cannot be empty"
  when: cost_center is not defined or cost_center | length == 0

3. Line-by-Line Explanation

ansible.builtin.assert — the FQCN of the built-in module that checks one or more conditions and stops the entire play immediately if any condition is false; we use the FQCN even for built-in modules, for the same consistency reason explained in Module 5.

that: — a list of conditions; every single condition in the list must evaluate to true, otherwise the assertion fails. Using a list (instead of one long combined expression) also makes it much easier to read which specific rule failed.

environment in ['dev', 'qa', 'uat', 'prod'] — this is the "allowed-value list" pattern: rather than trying to catch every possible wrong value, we only allow a small, known-good set, and reject everything else automatically — including typos we never even thought of.

fail_msg: — the exact human-readable message shown when the assertion fails; writing a clear message here (naming the actual bad value with {{ environment }}) saves the requester or engineer real debugging time later.

success_msg: — optional, purely for a friendlier job log when validation passes; has no effect on logic.

cpu | int >= 1 — the | int is a Jinja2 filter that converts the value to an integer before comparing; without it, values coming from a Survey or extra_vars can sometimes arrive as strings, and comparing a string to a number can behave unpredictably.

vm_name is match('^[a-z]{3,10}-(dev|qa|uat|prod)-[a-z]{2,10}[0-9]{2}$') — a regular expression check using the match Jinja2 test; it enforces our company's exact hostname pattern (application-environment-role, then two digits), rejecting anything that doesn't fit — like an uppercase letter or a missing environment segment.

ansible.builtin.fail — used instead of assert here because we want a fully custom condition combining "is not defined OR is empty," which reads more naturally as an explicit fail with a when clause than forcing it into assert's that list.

when: cost_center is not defined or cost_center | length == 0 — the task only runs (and fails the play) if this condition is true; note the two checks — first confirming the variable even exists, before trying to measure its length, otherwise Ansible would itself error out trying to check the length of something undefined.

4. The Validation Toolbox — Summary

ToolBest used for
assertMultiple related conditions, with a clear pass/fail message — our default choice
fail + whenA single custom condition that doesn't fit naturally into assert's list style
Regex (is match, is search)Enforcing naming standards, formats (like an email or a hostname pattern)
Allowed-value lists (in [...])Any field with a small, known set of valid options — environment, platform, OS family
Interview framing: If asked "how did you prevent bad requests from reaching AWS," the strong answer is: "We built a dedicated validate_request role that runs first in every playbook, using assert with allowed-value lists and regex, so invalid input fails fast with a clear message instead of partially provisioning something wrong."
