The Azure Master Playbook

The same Payment Gateway request, provisioned on Azure — every line explained

1. Same Story, Different Cloud

Puneeth, the business need has not changed at all — the Payment team still wants a RHEL 9 server, 4 CPU, 16GB RAM, tagged correctly. What changes is purely the vocabulary and the specific API calls, exactly like the concept map you memorized in Module 2. Read this module actively comparing it against Module 10 — that comparison is what will make you fluent across clouds instead of only knowing one.

2. The Full Role

---
# roles/azure_provision/tasks/main.yml

- name: Check whether this VM already exists (idempotency)
  azure.azcollection.azure_rm_virtualmachine_info:
    resource_group: "{{ resource_group }}"
    name: "{{ vm_name }}"
  register: existing_vm
  ignore_errors: true

- name: Create the Network Interface for the VM
  azure.azcollection.azure_rm_networkinterface:
    resource_group: "{{ resource_group }}"
    name: "{{ vm_name }}-nic"
    virtual_network: "{{ vnet_name }}"
    subnet: "{{ subnet_name }}"
    security_group: "{{ nsg_name }}"
  register: nic_result
  when: existing_vm.vms | default([]) | length == 0

- name: Provision the Azure Virtual Machine
  azure.azcollection.azure_rm_virtualmachine:
    resource_group: "{{ resource_group }}"
    name: "{{ vm_name }}"
    vm_size: "{{ vm_size_map[cpu ~ '-' ~ memory] | default('Standard_D2s_v5') }}"
    admin_username: "{{ admin_username }}"
    ssh_password_enabled: false
    ssh_public_keys:
      - path: "/home/{{ admin_username }}/.ssh/authorized_keys"
        key_data: "{{ ssh_public_key }}"
    image:
      offer: RHEL
      publisher: RedHat
      sku: "9-lvm-gen2"
      version: latest
    os_disk_size_gb: "{{ disk_size }}"
    managed_disk_type: "Premium_LRS"
    network_interfaces: "{{ vm_name }}-nic"
    tags:
      Application: "{{ application }}"
      Environment: "{{ environment }}"
      Owner: "{{ owner }}"
      CostCenter: "{{ cost_center }}"
  register: azure_result
  when: existing_vm.vms | default([]) | length == 0

- name: Wait for SSH to become reachable
  ansible.builtin.wait_for:
    host: "{{ azure_result.ansible_facts.azure_vm.properties.networkProfile.networkInterfaces[0].properties.ipConfigurations[0].properties.privateIPAddress }}"
    port: 22
    delay: 10
    timeout: 300
  when: azure_result is changed

- name: Add the new VM to in-memory inventory for post-config
  ansible.builtin.add_host:
    name: "{{ vm_name }}"
    groups: newly_provisioned
    ansible_host: "{{ azure_result.ansible_facts.azure_vm.properties.networkProfile.networkInterfaces[0].properties.ipConfigurations[0].properties.privateIPAddress }}"
  when: azure_result is changed

- name: Produce the provisioning report
  ansible.builtin.set_stats:
    data:
      vm_name: "{{ vm_name }}"
      cloud_platform: azure
      status: "{{ 'created' if azure_result is changed else 'already_existed' }}"

3. Line-by-Line Explanation

azure_rm_virtualmachine_info — Azure's equivalent of the AWS _info pattern from Module 10; a read-only lookup used purely for our idempotency check, wrapped in ignore_errors: true because this call actually raises an error (rather than returning an empty list) when the VM doesn't exist yet — a real Azure-specific quirk worth remembering for interviews.

azure_rm_networkinterface — unlike AWS, where the network interface is usually created implicitly as part of ec2_instance, Azure requires the NIC to be created as its own separate resource first, and then attached to the VM by name; this is one of the real structural differences between the platforms, not just naming.

vm_size_map[cpu ~ '-' ~ memory] — the exact same pattern from Module 10, just mapping to Azure VM size names like Standard_D4s_v5 instead of AWS instance types.

ssh_password_enabled: false plus ssh_public_keys — explicitly disables password-based login and injects an SSH public key instead, enforcing the same key-based access standard from Module 1's Security fields.

image: offer/publisher/sku/version — Azure identifies a VM image with four separate fields instead of AWS's single AMI ID; version: latest plays the same "always use the newest approved image" role that our AMI-sorting logic played in Module 10, but here Azure handles it natively.

managed_disk_type: "Premium_LRS" — chooses SSD-backed Premium storage with Locally Redundant Storage (three copies within one data center); this is Azure's version of the EBS encrypted/volume-type settings from Module 10, though note encryption itself is enabled separately through Azure's platform-managed key default or Key Vault, not this field.

tags: block — functionally identical purpose to the AWS tags block; same CostCenter/Application/Environment/Owner metadata, just using Azure's tagging mechanism.

The long azure_result.ansible_facts.azure_vm.properties.networkProfile...privateIPAddress path — Azure's module returns a deeply nested JSON structure describing the whole VM resource; this dotted path is simply "walking down" that structure to reach the actual private IP address, which is far more deeply nested than AWS's flatter instances[0].private_ip_address.

add_host and set_stats — identical in purpose and structure to Module 10; this is intentional — our downstream linux_baseline, validation, and notification roles from Module 7 do not care which cloud created the server, only that it landed in the newly_provisioned group with a reachable IP.

4. AWS vs Azure, Task by Task

Idempotency checkec2_instance_info filtered by Name tagazure_rm_virtualmachine_info by resource group + name (errors if missing)
Network setupImplicit — subnet/SG passed directly to instance moduleExplicit — NIC created as its own resource first
Image referenceSingle AMI ID, resolved dynamically by our own lookup taskFour fields (publisher/offer/sku/version), resolved natively by Azure

Interview tip: Being able to explain why Azure needs an explicit NIC step while AWS doesn't shows real hands-on depth, not memorized syntax — this is exactly the kind of comparison interviewers probe for.
