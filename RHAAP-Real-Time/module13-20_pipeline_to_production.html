Module 13 — The Common Multi-Cloud Playbook

Right now we have three separate roles: aws_provision, azure_provision, openshift_provision. We need one single entry point that AAP's Job Template actually launches, which picks the correct role automatically.

---
# playbooks/provision_server.yml

- name: Enterprise Multi-Cloud Server Provisioning
  hosts: localhost
  gather_facts: false

  pre_tasks:
    - name: Run input validation before anything else
      ansible.builtin.include_role:
        name: validate_request

  tasks:
    - name: Dynamically run the correct platform role
      ansible.builtin.include_role:
        name: "{{ cloud_platform }}_provision"

    - name: Run post-provisioning configuration
      ansible.builtin.include_role:
        name: linux_baseline
      when: os_type is search('rhel')

    - name: Validate the provisioned server
      ansible.builtin.include_role:
        name: validation

    - name: Send notification and update CMDB
      ansible.builtin.include_role:
        name: notification

hosts: localhost — this whole play runs on the AAP execution node itself, not on any managed server, because at this point in the flow there is no server yet to connect to — everything is API/cloud-SDK calls; we explain this fully in Module 14's Inventory section.

include_role: name: "{{ cloud_platform }}_provision" — this is the single most important line in the whole masterclass: because cloud_platform is a variable (aws, azure, or openshift), Ansible builds the role name dynamically at runtime — the string "aws_provision", "azure_provision", or "openshift_provision" is only known once the variable is resolved.

include_role vs import_role: import_role is resolved statically, at playbook-parsing time, before any variables from a Survey are even applied — so it cannot use a variable to pick which role to run. include_role is resolved dynamically, at actual execution time, task by task — which is exactly what lets us plug in the correct cloud role based on what the requester chose. This is a very common, very fair interview question: "why did you use include_role instead of import_role here?"

when: os_type is search('rhel') — a simple example of conditionally skipping a step; we don't want to run our RHEL-specific baseline role against a Windows server.

Why localhost, not a managed-host inventory?

A normal Ansible inventory lists real servers Ansible will SSH/WinRM into. But when we're creating a new AWS/Azure/OpenShift resource, there is no server yet to connect to — the "target" of the play is really the cloud provider's API, reached over HTTPS from wherever the playbook runs. So we point hosts: at localhost (meaning "the AAP execution node itself") and let the cloud collection modules make the outbound API calls. Only later, in Module 17, once the server actually exists, does a real managed-host connection (SSH/WinRM) come into play, via the add_host pattern from Modules 10–12.

Key Job Template settings to know: Privilege Escalation should be off for this template (it runs against localhost/APIs, not systems needing sudo yet); Ask Variables on Launch is disabled once the Survey is built, since the Survey supplies the variables instead; Concurrent Jobs is normally left disabled here, so two provisioning requests for the exact same server name can't race each other.

Module 17 — Post-Provisioning Configuration

Once the server actually exists (Modules 10–12 handled that), a second, very different phase begins: configuring the server itself over SSH/WinRM.

localhost / Cloud API automation (Modules 10-12) | v add_host adds the new server's real IP into Ansible's in-memory inventory, group "newly_provisioned" | v Newly Provisioned Server Configuration (this module) - Wait for connectivity (wait_for port 22/5986) - Configure hostname - Configure DNS registration - Configure NTP - Configure proxy settings - Mount and format additional disks - Create application users - SSH hardening (disable root login, disable password auth) - Install baseline packages - Install monitoring agent - Install logging/log-shipping agent - Install EDR/antivirus agent - Install backup agent - Register with the patch management system
Why add_host is the hinge of the whole design: Every task before add_host ran against localhost, talking to a cloud API. Every task after it runs against a real managed host, over SSH or WinRM, using ordinary Ansible modules like ansible.builtin.user or ansible.posix.mount. add_host is what lets a single playbook run smoothly transition from "create infrastructure" to "configure the operating system" without needing two completely separate playbook runs or a static inventory file prepared in advance.

Module 18 — Security Best Practices

✅ Do this❌ Never this
Store all secrets as AAP Credential objects, encrypted at rest in AAP's databaseHardcode a password or key inside a playbook or vars/*.yml file committed to Git
Use IAM Roles / Managed Identity / Service Accounts (Module 3) for short-lived accessUse a personal AWS/Azure login or a permanent shared password for automation
Pull dynamic secrets from Vault/CyberArk at job runtimeEmail or Slack a password to a teammate "just this once"
Scope every Role/RBAC assignment to the minimum needed (least privilege)Grant Contributor/Admin/ClusterRole broadly "to save time"
Rotate credentials on a schedule, and immediately after any suspected leakLeave the same Access Key active for years with no rotation
Inject SSH keys via cloud-init/Vault, never a shared static key pairReuse one SSH private key across every server in the company
Enable AAP job logging/auditing and review it periodicallyRun automation with logging disabled "for performance"
Why the "bad" examples are genuinely dangerous: A hardcoded key in Git doesn't just risk one server — Git history keeps every old commit, so even deleting the line later doesn't remove it from history unless the whole repo is scrubbed; and a broadly-scoped ClusterRole or Contributor role means one compromised token can affect far more than the one application it was meant for.

Module 19 — Idempotency, Formalized

Interview framing: "Our playbooks are idempotent because every provisioning role checks for an existing resource by name before creating anything, and skips creation if it's already there — so accidentally launching the same Job Template twice never creates duplicate, orphaned infrastructure."

Module 20 — Error Handling

- name: Attempt EC2 provisioning with safe error handling
  block:
    - name: Provision the EC2 instance
      amazon.aws.ec2_instance:
        name: "{{ vm_name }}"
        # ... same parameters as Module 10
      register: ec2_result

    - name: Wait for SSH, fail clearly if it never comes up
      ansible.builtin.wait_for:
        host: "{{ ec2_result.instances[0].private_ip_address }}"
        port: 22
        timeout: 300
      register: ssh_check
      failed_when: ssh_check is failed

  rescue:
    - name: Log the failure clearly
      ansible.builtin.debug:
        msg: "Provisioning failed for {{ vm_name }}: {{ ansible_failed_result.msg | default('unknown error') }}"

    - name: Attempt a safe rollback (terminate the half-created instance)
      amazon.aws.ec2_instance:
        instance_ids: "{{ ec2_result.instances[0].instance_id }}"
        state: absent
      when: ec2_result is defined and ec2_result.instances is defined

    - name: Re-raise the failure so the AAP job clearly shows Failed
      ansible.builtin.fail:
        msg: "Provisioning of {{ vm_name }} failed and was rolled back — see log above"

  always:
    - name: Always record that a provisioning attempt was made
      ansible.builtin.set_stats:
        data:
          last_attempt_vm: "{{ vm_name }}"
          last_attempt_time: "{{ ansible_date_time.iso8601 }}"

block: — groups the "happy path" tasks together, so a single rescue: can catch a failure from any task inside it, instead of adding error handling to each task individually.

failed_when: ssh_check is failed — explicitly controls what counts as failure for this task, useful when you want failure logic to be based on something more specific than the module's own default success/fail behavior.

rescue: — only runs if something inside block: failed; this is where we log the problem, and importantly, attempt to roll back the half-created instance rather than leaving an orphaned, un-tracked EC2 instance running and costing money.

ansible_failed_result.msg — a special variable Ansible populates inside a rescue block, holding the actual error message from whichever task failed — useful for a clear log message without guessing which task broke.

ansible.builtin.fail inside rescue — without this, a successful rescue would make the whole play report as "successful" even though the original provisioning failed; explicitly failing again ensures the AAP Job Template still shows red/Failed, which is important so nobody thinks the server was created when it wasn't.

always: — runs no matter what happened in block or rescue — here just used to record that an attempt happened at all, useful for audit trails even on total failure.

Why ignore_errors: true is dangerous if overused: it silently marks a failed task as "changed" or "ok" and lets the play continue as if nothing went wrong — perfectly fine for a truly optional step (like a best-effort cleanup task), but if used on a core provisioning task, it can let a play report success in AAP even though the server was never actually created, which is a very hard bug to trust or debug later. Prefer block/rescue or a precise failed_when instead, and reserve ignore_errors for genuinely non-critical steps only.

Other tools worth knowing: changed_when lets you control when a task is reported as "changed" versus "ok" (useful for command/shell tasks that don't naturally know); until/retries/delay (seen already in Module 12's phase-polling) retries a task a set number of times with a pause in between, useful for anything that might need a moment to become ready rather than truly failing.
