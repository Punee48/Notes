MODULE 12

The OpenShift Virtualization Master Playbook

Provisioning the same Payment Gateway servers as KubeVirt VirtualMachines

1. A Different Kind of API

Puneeth, this module feels different from Modules 10 and 11, and that's intentional. AWS and Azure both give you a dedicated "create a VM" API call. OpenShift instead asks you to describe the VM you want, as a structured YAML document (a "manifest"), and hand that description to the Kubernetes API — the actual work of creating the VM is then done by the KubeVirt operator watching for that description, not by Ansible itself. This is the "declarative" style Kubernetes is famous for, and it's a genuinely different mental model worth sitting with.

2. The Full Role

---
# roles/openshift_provision/tasks/main.yml

- name: Check whether this VM already exists (idempotency)
  kubernetes.core.k8s_info:
    api_version: kubevirt.io/v1
    kind: VirtualMachine
    namespace: "{{ namespace }}"
    name: "{{ vm_name }}"
  register: existing_vm

- name: Render the cloud-init configuration
  ansible.builtin.set_fact:
    cloud_init_data: "{{ lookup('template', 'cloud-init.yml.j2') }}"

- name: Create the VirtualMachine
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: kubevirt.io/v1
      kind: VirtualMachine
      metadata:
        name: "{{ vm_name }}"
        namespace: "{{ namespace }}"
        labels:
          app: "{{ application }}"
          environment: "{{ environment }}"
        annotations:
          owner: "{{ owner }}"
          cost-center: "{{ cost_center }}"
      spec:
        running: true
        template:
          metadata:
            labels:
              app: "{{ application }}"
          spec:
            domain:
              cpu:
                cores: "{{ cpu }}"
              resources:
                requests:
                  memory: "{{ memory }}Gi"
              devices:
                disks:
                  - name: rootdisk
                    disk:
                      bus: virtio
                  - name: cloudinitdisk
                    disk:
                      bus: virtio
                interfaces:
                  - name: paymentnet
                    bridge: {}
            networks:
              - name: paymentnet
                multus:
                  networkName: "{{ network_attachment_definition }}"
            volumes:
              - name: rootdisk
                dataVolume:
                  name: "{{ vm_name }}-rootdisk"
              - name: cloudinitdisk
                cloudInitNoCloud:
                  userData: "{{ cloud_init_data }}"
  register: vm_result
  when: existing_vm.resources | length == 0

- name: Create the DataVolume (boot disk cloned from golden image)
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: "{{ vm_name }}-rootdisk"
        namespace: "{{ namespace }}"
      spec:
        source:
          sourceRef:
            kind: DataSource
            name: "{{ golden_image_datasource }}"
            namespace: golden-images
        storage:
          resources:
            requests:
              storage: "{{ disk_size }}Gi"
          storageClassName: "{{ storage_class }}"
  when: existing_vm.resources | length == 0

- name: Wait for the VM to report Running
  kubernetes.core.k8s_info:
    api_version: kubevirt.io/v1
    kind: VirtualMachineInstance
    namespace: "{{ namespace }}"
    name: "{{ vm_name }}"
  register: vmi_status
  until: vmi_status.resources[0].status.phase | default('') == "Running"
  retries: 30
  delay: 10

- name: Add the new VM to in-memory inventory for post-config
  ansible.builtin.add_host:
    name: "{{ vm_name }}"
    groups: newly_provisioned
    ansible_host: "{{ vmi_status.resources[0].status.interfaces[0].ipAddress }}"

- name: Produce the provisioning report
  ansible.builtin.set_stats:
    data:
      vm_name: "{{ vm_name }}"
      cloud_platform: openshift
      status: "{{ 'created' if vm_result is changed else 'already_existed' }}"

3. The VirtualMachine Manifest, Field by Field

apiVersion: kubevirt.io/v1 — tells the Kubernetes API which API group and version understands this object type; without KubeVirt installed on the cluster, this apiVersion simply wouldn't exist and the request would be rejected.

kind: VirtualMachine — the object type — note this is the "desired state" wrapper object. It is not the running VM itself; it's the durable record that says "a VM by this name should exist and be running," similar in spirit to how a Kubernetes Deployment is not the same object as the Pods it creates.

metadata.labels — Kubernetes' native tagging mechanism, used for selecting/filtering objects (for example, "show me every VM with app: payment") — the functional equivalent of AWS/Azure tags.

metadata.annotations — similar to labels but not meant for selection/filtering, just attached metadata for humans or tooling to read — a good place for our CostCenter/Owner values, which we don't need to query against.

spec.running: true — explicitly tells KubeVirt "keep this VM powered on"; setting it to false would create the VM definition but leave it shut down — useful for pre-staging a VM without starting it yet.

spec.template — describes the actual VM instance that gets launched, in the same nested way a Kubernetes Deployment's spec.template describes the Pods it creates.

domain.cpu.cores and domain.resources.requests.memory — the direct CPU/memory sizing, straight from our Module 1 checklist values — no separate "instance type" name to map to, since KubeVirt lets you request raw CPU/memory directly (though real enterprises often still standardize using named InstanceTypes, mentioned in Module 2).

devices.disks — lists the virtual disks attached to the VM and which bus type connects them (virtio is the standard high-performance para-virtualized driver); note there are two disks here — the actual OS disk, and a second disk purely for delivering cloud-init configuration.

devices.interfaces and top-level networks — these two sections must always be paired by matching name; interfaces describes how the VM's virtual NIC connects (bridge: {}), while networks describes what that name actually points to outside the VM.

networks[].multus.networkName — this is the connection to Multus, a Kubernetes networking add-on that allows a Pod/VM to have more than one network interface. Instead of using only the cluster's default internal network, this line attaches our VM to a specific NetworkAttachmentDefinition object (created ahead of time by the Network team) representing our real corporate VLAN.

volumes[].dataVolume.name — connects the rootdisk disk device to an actual DataVolume object (created separately below) that holds the real disk data, cloned from our golden RHEL 9 image.

volumes[].cloudInitNoCloud.userData — injects our rendered cloud-init YAML directly as the VM's first-boot configuration, the same mechanism EC2 and Azure VMs also support, letting us set hostname, users, and SSH keys consistently across all three platforms.

4. The Ansible Tasks, Line by Line

kubernetes.core.k8s_info — the read-only lookup module, used first purely for our idempotency check, mirroring the _info pattern from both Module 10 and Module 11.

kubernetes.core.k8s with state: present — the single, universal module used to create any Kubernetes/OpenShift object; unlike AWS and Azure, which have a different module per resource type, Kubernetes automation typically uses this one module and simply changes the definition: YAML block passed to it — the object's kind field is what tells Kubernetes what to actually create.

kind: DataVolume, spec.source.sourceRef — a second, separate object that actually performs the disk cloning; it references a pre-published DataSource (our golden image, published once by the Platform team) rather than embedding a raw image URL, keeping golden-image management centralized.

storage.storageClassName — tells Kubernetes which underlying storage backend (SAN, NFS, Ceph) to actually allocate the disk from, matching the value gathered from the Storage team back in Module 2.

until / retries / delay on the VirtualMachineInstance lookup — this is Ansible's built-in retry loop; it re-checks the VM's live status every 10 seconds, up to 30 times (5 minutes total), until the phase field actually reports "Running" — this distinguishes "the object was accepted by the API" from "the VM has actually finished booting," a distinction that doesn't really exist the same way in the AWS/Azure modules, which handle the equivalent wait internally via wait: true.

vmi_status.resources[0].status.interfaces[0].ipAddress — this is how we discover the VM's IP address after boot: KubeVirt reports it back on the running VirtualMachineInstance object once the guest agent inside the VM reports in, which is why we needed to wait for "Running" first — the IP simply isn't known before that.
