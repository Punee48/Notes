Platform-Specific Requirements — AWS, Azure, OpenShift Virtualization

Taking the generic checklist from Module 1 and turning it into real, platform-specific values

1. Quick Recap

In Module 1, you filled in a generic 25-field checklist for a DEV server — hostname, CPU, memory, environment, and so on. That checklist answers "what does the application need?" But it does not yet answer "where exactly, on which cloud, does this server get created?" That second question is what Module 2 is about.

Here is the important idea for this module: the same Payment Gateway request — 3 RHEL servers, 4 CPU, 16 GB RAM — needs completely different platform details depending on whether Infrastructure decides to build it on AWS, Azure, or OpenShift Virtualization. Your job as the automation engineer is to know exactly which extra values each platform needs, and exactly which team in the company hands you that value.

AWS

Amazon Web Services — EC2 Requirements

Think of AWS like renting a flat inside a huge, gated township. Before you can even ask for a flat (an EC2 instance), you need to know which township (Account), which building (VPC), which floor (Subnet), and which security guard rules (Security Group) apply to you.

Why this matters: Notice almost none of these values are things you, the Ansible engineer, get to invent. Your playbook does not "decide" the VPC — it receives the VPC ID as a variable that someone else's team already approved. This is a very common interview question: "how did you get the VPC ID?" and the correct answer is never "I hardcoded it."

OPENSHIFT

OpenShift Virtualization — VM Requirements

OpenShift Virtualization is different from both AWS and Azure because you are not calling a public cloud API — you are talking to your company's own Kubernetes-based OpenShift cluster, and asking it to run a full virtual machine (using a technology called KubeVirt) instead of a lightweight container.

OpenShift Cluster / API URLThe address of the OpenShift cluster's control plane API that Ansible will talk toPlatform/OpenShift Team
Namespace / ProjectOpenShift's version of a logical boundary, similar in spirit to a Resource GroupApplication Team gets a dedicated namespace, e.g. payment-dev
StorageClassDefines what kind of underlying storage (SAN, NFS, Ceph) backs the VM's diskStorage/Platform Team
DataVolume / PVCThe actual disk object created for the VM, backed by a PersistentVolumeClaimGenerated by Ansible, sized from Module 1 disk requirement

NetworkAttachmentDefinition / MultusDefines how the VM attaches to a specific VLAN outside the default cluster network — Multus lets a VM/pod have more than one network interfaceNetwork/Platform Team

5. How Creating a VM Differs from Creating a Pod

Why is a KubeVirt VirtualMachine not "just another Pod"?

If you already know some Kubernetes, you know a Pod runs a container — a lightweight process sharing the host's kernel. A KubeVirt VirtualMachine is completely different under the hood: OpenShift actually launches a small helper Pod, and inside that Pod it runs a real virtual machine (using KVM/QEMU, the same virtualization technology as VMware or a traditional hypervisor), complete with its own kernel, its own boot process, and a virtual disk. Kubernetes just becomes the "control plane" that manages the placement, restart, and lifecycle of the VM — the same way it manages Pods — but what's actually running inside is a full guest operating system, not a container process.

This is exactly why a VM needs a DataVolume/PVC for a real virtual disk (a Pod usually doesn't need persistent block storage for its root filesystem), and why it needs cloud-init (a Pod gets configuration through environment variables and ConfigMaps, but a VM boots a real OS that expects cloud-init the same way an EC2 instance or Azure VM does).
