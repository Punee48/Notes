1. Explain your server provisioning automation architecture

Beginner: "I built an Ansible project that can create a server on AWS, Azure, or OpenShift. The user tells me which cloud they want, and my playbook creates the server there."

3+ Years: "I designed a multi-cloud provisioning solution using Red Hat Ansible Automation Platform. A requester submits a form — an AAP Survey — choosing the cloud, environment, and size. The request goes through a Workflow Template that validates the input, waits for manager approval, and then dynamically runs the correct role for AWS, Azure, or OpenShift Virtualization using include_role. After the server is created, the same pipeline configures it, validates it's healthy, updates CMDB, and notifies the requester."

Enterprise: "The architecture separates concerns clearly: a requester-facing layer like ServiceNow, an orchestration layer in AAP's Workflow Templates, platform-specific provisioning roles that are the only cloud-specific code in the whole system, and a shared post-provisioning layer that's completely cloud-agnostic. This meant roughly seventy to eighty percent of the codebase was reused across all three platforms, and adding a fourth cloud in the future would only mean writing one new role, not redesigning the pipeline."

2. How does AAP authenticate with AWS?

Beginner: "AAP has an AWS credential stored inside it with an access key, and it uses that to talk to AWS."

3+ Years: "We avoided long-term IAM user access keys. Instead, AAP's Credential is configured to assume an IAM Role using STS AssumeRole, which gives it short-lived, temporary credentials that expire automatically, usually within an hour. This limits the damage if anything ever leaked."

Enterprise: "We followed least-privilege IAM policies scoped to exactly the EC2 actions provisioning needed — RunInstances, the Describe calls, CreateTags, and a scoped PassRole — nothing broader. For cross-account setups, like separate DEV and PROD AWS accounts, AAP assumed a different Role per account, so a mistake in one environment could never touch another."

3. How does AAP authenticate with Azure?

Beginner: "AAP has an Azure credential with a client ID and secret that it uses to log in."

3+ Years: "We used a Service Principal registered in Microsoft Entra ID, with Client ID, Tenant ID, and a secret stored securely in AAP's Credential store. AAP requests an OAuth token from Entra ID, and that token is used to call the Azure Resource Manager API."

Enterprise: "Where the AAP execution nodes actually ran inside Azure, we preferred Managed Identity over a Service Principal, because it removes the need to store or rotate a secret at all. Where a Service Principal was necessary, we scoped it with a Custom RBAC Role limited to VM and network actions, instead of the broad built-in Contributor role."

4. How does AAP authenticate with OpenShift?

Beginner: "AAP uses a token to log into the OpenShift cluster."

3+ Years: "We created a dedicated Service Account inside the target namespace, and AAP's OpenShift Credential holds that Service Account's token. The token authenticates against the Kubernetes API, and Kubernetes RBAC checks what that Service Account is allowed to do."

Enterprise: "We deliberately used a namespace-scoped Role and RoleBinding, never a ClusterRole, so even if that token leaked, the blast radius was limited to one namespace, not the whole cluster. The Role only granted the exact verbs — get, list, create, update, delete — on the exact resources our automation needed, like virtualmachines and datavolumes."

5. How did you manage credentials?

Beginner: "I stored all the passwords and keys inside AAP so they weren't in the playbooks."

3+ Years: "Every secret — AWS keys, Azure Service Principal secret, OpenShift token, Git deploy key — was stored as its own AAP Credential object, encrypted in AAP's database, and injected only at job runtime. Nothing sensitive ever appeared in a playbook or in Git."

Enterprise: "For the most sensitive secrets, we integrated with HashiCorp Vault as a Credential source, so AAP pulled dynamic, short-lived secrets at the moment the job ran, instead of storing even an encrypted static copy long-term. We also had a rotation policy and reviewed credential usage as part of our audit process."

6. How did you implement idempotency?

Beginner: "Before creating a server, I check if it already exists, and if it does, I skip creating it again."

3+ Years: "Every provisioning role does a lookup first — ec2_instance_info on AWS, azure_rm_virtualmachine_info on Azure, k8s_info on OpenShift — filtered by the exact server name. The actual creation task only runs when that lookup comes back empty, using a when condition."

Enterprise: "This check-then-act pattern means running the same Job Template twice, even by accident, never creates duplicate infrastructure. It also means our provisioning reports work consistently whether the server was just created or already existed, since we always return the same final state — instance ID and IP — either way."

7. How did you prevent duplicate VMs?

Beginner: "Same as idempotency — I check first before creating."

3+ Years: "The idempotency check itself is the main defense. On top of that, we kept Concurrent Jobs disabled on the provisioning Job Template, so two people launching the same request at nearly the same time couldn't create a race condition where both checks pass before either creation finishes."

Enterprise: "We also enforced our naming standard through validation — a strict hostname pattern — so two different requesters couldn't accidentally target the same server name with slightly different casing or spacing and slip past the exists-check."

8. How did you handle failures?

Beginner: "If a task fails, Ansible stops and shows an error in the AAP job log."

3+ Years: "We wrapped the risky provisioning steps in block and rescue. If something failed inside the block, the rescue section logged a clear message using the failed task's actual error, and then explicitly failed again so the AAP job still showed as Failed, rather than quietly succeeding."

Enterprise: "We were careful about ignore_errors — we only used it on genuinely optional cleanup steps, never on the actual provisioning task, because overusing it can make a broken job look successful in AAP, which is a very hard thing to trust or debug later."

9. How did you design rollback?

Beginner: "If something fails, I delete the server that was partly created."

3+ Years: "Our rollback policy is environment-aware. In DEV and QA, on failure we automatically delete the half-created resource, because recreating is cheap and fast. In UAT and PROD, we never auto-delete — we preserve the resource, tag it as failed, and raise an incident so a human decides the next step."

Enterprise: "This asymmetry matters because a PROD resource might already have real data or real cost sunk into it, and an automatic delete could destroy evidence needed for root-cause analysis. The rescue block always raises a notification/incident regardless of environment, so nothing fails silently even if we choose not to delete."

10. How did you manage firewall requirements?

Beginner: "I asked the network team to open the ports my automation needed."

3+ Years: "I documented every connection AAP needed as a Source/Destination/Port/Protocol/Direction table before implementation even started — outbound HTTPS to the AWS, Azure, and OpenShift APIs, outbound SSH/WinRM to newly created servers, and connectivity to Git, Automation Hub, and Vault."

Enterprise: "I was precise about direction — almost everything is outbound from AAP — which made the firewall requests get approved faster since the network team didn't have to send follow-up questions. I also made sure our Execution Environment's proxy and NO_PROXY settings correctly separated public internet traffic from internal traffic."

11. How did you design AAP surveys?

Beginner: "I added questions for the things the playbook needs, like environment and server size."

3+ Years: "Each Survey question maps directly to a variable name the playbook already expects. I used Multiple Choice questions with a fixed allowed-value list wherever possible — like environment being only dev, qa, uat, or prod — instead of free text, to cut down on bad input before it even reaches validation."

Enterprise: "I treated the Survey as the first line of defense, and validate_request as the second, deeper line of defense — so even if someone launched the playbook outside AAP with hand-typed extra_vars, the same validation logic would still catch a bad request."

12. How did you implement approval?

Beginner: "I added an approval step in the Workflow before the server actually gets created."

3+ Years: "We used an AAP Workflow Approval Node placed right after input validation and before provisioning, with a timeout so a request doesn't sit forever if nobody responds. Only members of a specific Team with Approve permission on that node could action it."

Enterprise: "This gave us a clean audit trail — AAP records exactly who approved or denied, and when — which matters a lot in a regulated environment like banking, where you need to prove a human signed off before infrastructure was created."

13. How did you integrate ServiceNow?

Beginner: "ServiceNow is where the user submits the request, and it triggers AAP to run the automation."

3+ Years: "We designed it so ServiceNow owns the requester experience — the catalog form and manager approval — and once approved, it calls the AAP API to launch our Workflow Job Template, passing the form fields in as extra_vars."

Enterprise: "We kept a clear separation of concerns — ServiceNow never talks directly to AWS, Azure, or OpenShift, and AAP never manages ticket state. After the Workflow finishes, AAP's result updates the CMDB and, through the integration, the ServiceNow ticket closes automatically, so the requester sees one smooth experience even though two separate systems did the work."

14. How did you update CMDB?

Beginner: "After the server is created, I update CMDB with the details."

3+ Years: "Each provisioning role writes structured data — instance ID, IP, cloud platform — using set_stats. That data becomes available to later Workflow nodes as job artifacts, so our CMDB Update step reads it directly instead of re-querying the cloud API."

Enterprise: "This kept CMDB as close to real-time truth as possible, and combined with the Git commit hash AAP records per job, we could always trace a CMDB entry back to the exact automation code and approval that created it — important for audits."

15. How did you handle multiple environments?

Beginner: "The environment is just a variable — dev, qa, uat, or prod — that the user picks."

3+ Years: "We ran the exact same playbook across every environment — never a separate copy per environment — and let environment-specific behavior, like our rollback policy, come from a variable and group_vars rather than duplicated code. This meant a successful DEV test was real evidence PROD would behave the same way."

Enterprise: "Environments were also isolated at the infrastructure level — separate AWS accounts, separate Azure subscriptions or resource groups, and separate OpenShift namespaces — so even a mistake in automation logic couldn't cross environment boundaries."

16. How did you secure secrets?

Beginner: "I never put passwords or keys directly in the playbooks — I used AAP Credentials instead."

3+ Years: "All secrets lived in AAP Credential objects, encrypted at rest, injected only at runtime. We used short-lived identities everywhere possible — IAM Roles, Managed Identity, Service Account tokens — instead of static long-lived secrets."

Enterprise: "For our most sensitive integrations, we pulled dynamic secrets from Vault at job runtime rather than storing even an encrypted copy long-term, and we had a rotation cadence for anything that had to remain static, like Git deploy keys."

17. What problems did you face in production?

Beginner: "Sometimes a playbook that worked on my laptop failed when run from AAP."

3+ Years: "The most common real issue was a missing Python dependency inside the Execution Environment — a collection would be installed correctly, but the underlying SDK, like boto3 or the Kubernetes client, wasn't in the EE image, so the job failed with a ModuleNotFoundError even though the playbook code itself was correct."

Enterprise: "We also hit real firewall gaps that only showed up once we moved from lab testing to the actual AAP execution nodes, since those nodes sat in a different network segment than our personal workstations — this is exactly why we later formalized the firewall requirement table upfront, before implementation, for every new integration."

18. How did you troubleshoot them?

Beginner: "I looked at the AAP job log to see which task failed and why."

3+ Years: "I followed a consistent order — check the task-level AAP job log first to find the exact failing module and error, then check the platform's own event log, like CloudTrail on AWS or the Azure Activity Log, to confirm the root cause from the platform side too."

Enterprise: "Once I found the root cause, I didn't just fix that one instance — I added a validation check or an execution-environment fix so the same class of problem couldn't reach production again silently. That habit of closing the loop, not just patching the symptom, is something I try to carry into every project."
