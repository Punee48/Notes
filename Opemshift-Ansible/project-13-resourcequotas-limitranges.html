01 The Manager's Thirteenth Ticket — INFRA-2006

🏢 ABC Bank OpenShift Platform Team — Intermediate Week 6

The cluster is growing. 5 teams, 12 namespaces, no guardrails. Rajesh calls with an urgent governance problem:

"The fraud detection team accidentally deployed a batch job that requested 64 CPUs. It starved the payment API of resources for 20 minutes. Also, a new developer created a pod with no resource requests — the scheduler put it anywhere and it impacted the entire node. I need: (1) namespace-level caps — DEV teams can't use more than 4 CPUs total, PROD gets 16. (2) Force every container to have requests and limits — no pod without them. (3) Alert us before any namespace hits 80% of its quota so we can act before an incident."

This is cluster governance: ResourceQuota protects the cluster from namespace-level overconsumption; LimitRange protects individual pods from misconfiguration.

02 Why Quotas and Limits — The Multi-Tenant Problem

🏢
Noisy Neighbour
Without quotas, one namespace can consume all cluster CPU. Other namespaces starve. Pods get evicted. Incident.
💸
Cost Control
Each namespace maps to a team's budget. Quota = budget enforcement. DEV team can't accidentally spin up expensive resources.
⚡
Scheduler Sanity
Without requests, scheduler can't make intelligent placement. LimitRange forces requests → better scheduling decisions.
🔒
Security Posture
Object count quotas prevent resource exhaustion attacks. Prevent: 10,000 empty pods, 1,000 Secrets, overloading etcd.

03 ResourceQuota — Namespace-Level Caps

yamlComplete ResourceQuota Manifest
---
# ResourceQuota: namespace-level resource ceiling
# Scoped to a single namespace

apiVersion: v1
kind: ResourceQuota
metadata:
  name:      production-quota
  namespace: payment-prod
spec:
  hard:
    # ── Compute resources ──────────────────────────────────────
    requests.cpu:    "16"       # Max total CPU requests in namespace
    requests.memory: 32Gi      # Max total memory requests
    limits.cpu:      "32"       # Max total CPU limits
    limits.memory:   64Gi

    # ── Object counts ─────────────────────────────────────────
    pods:                   "100"  # Max total pods
    services:               "20"
    secrets:                "50"
    configmaps:             "50"
    persistentvolumeclaims: "10"
    services.loadbalancers: "2"   # Cap expensive LBs
    services.nodeports:     "0"   # Prohibit NodePorts in prod

    # ── Storage ────────────────────────────────────────────────
    requests.storage:       500Gi # Total PVC storage requests
    gp3-ssd.storageclass.storage.k8s.io/requests.storage: 200Gi
    # ↑ Per-StorageClass quota

04 LimitRange — Per-Container Defaults and Enforcement

yamlComplete LimitRange Manifest
---
# LimitRange: per-container/pod/PVC defaults and constraints
# Injected automatically into Pods at admission time

apiVersion: v1
kind: LimitRange
metadata:
  name:      production-limits
  namespace: payment-prod
spec:
  limits:

    # ── Container limits ────────────────────────────────────────
    - type: Container
      default:                   # Applied if container has no limits
        cpu:    "500m"
        memory: "512Mi"
      defaultRequest:            # Applied if container has no requests
        cpu:    "100m"
        memory: "128Mi"
      max:                        # Hard ceiling per container
        cpu:    "4"
        memory: "8Gi"
      min:                        # Hard floor per container
        cpu:    "50m"
        memory: "64Mi"
      maxLimitRequestRatio:       # Limit cannot exceed request × ratio
        cpu:    4              # limit ≤ 4 × request
        memory: 2              # limit ≤ 2 × request

    # ── PVC storage limits ──────────────────────────────────────
    - type: PersistentVolumeClaim
      max:
        storage: 100Gi            # No single PVC can exceed 100Gi
      min:
        storage: 1Gi              # No PVC smaller than 1Gi

    # ── Pod-level limits ────────────────────────────────────────
    - type: Pod
      max:
        cpu:    "8"              # Pod (all containers) max 8 CPUs
        memory: "16Gi"

05 ResourceQuota vs LimitRange — The Critical Distinction

ResourceQuota

  • Namespace-level aggregate cap
  • "Total CPU across all pods ≤ 16"
  • Checked at pod ADMISSION — pod rejected if quota exceeded
  • Requires pods to HAVE requests/limits set
  • Reports used vs hard in oc describe quota
  • Object count quotas (pods, services, secrets)

LimitRange

  • Per-container/pod/PVC constraint
  • "Each container must use 50m–4 CPUs"
  • Injected at pod CREATION — defaults added automatically
  • Solves the "no requests set" problem automatically
  • No usage tracking — just admission control
  • Ratio enforcement: limit ≤ N × request
💡
Critical Interaction: Quota + LimitRange Together

ResourceQuota with compute resource limits REQUIRES every pod to have requests/limits set — otherwise the pod is rejected. LimitRange solves this by auto-injecting defaults. Always deploy both together. Order matters: apply LimitRange first, then ResourceQuota. A namespace with ResourceQuota but no LimitRange means developers get confusing "quota exceeded" errors when they forget to set requests.

07 Role Implementation

yamlroles/openshift_quota/tasks/main.yml
---
# Apply LimitRange first, then ResourceQuota

- name: "[QUOTA] Apply LimitRange (must precede ResourceQuota)"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'limitrange.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  tags: [limits]

- name: "[QUOTA] Apply ResourceQuota"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'resourcequota.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  tags: [quota]

- name: "[QUOTA] Verify ResourceQuota applied"
  kubernetes.core.k8s_info:
    kind: ResourceQuota
    name: "{{ environment_name }}-quota"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: quota_verify

- name: "[QUOTA] Assert quota created"
  ansible.builtin.assert:
    that:
      - quota_verify.resources | length == 1
      - quota_verify.resources[0].spec.hard['requests.cpu'] is defined
    fail_msg: "ResourceQuota not applied correctly"

08 Quota Usage Report — Monitor Consumption

yamltasks/quota_usage_report.yml
---
# Query quota usage across all namespaces

- name: "[REPORT] Get all ResourceQuotas"
  kubernetes.core.k8s_info:
    kind: ResourceQuota
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_quotas

- name: "[REPORT] Build quota usage summary per namespace"
  ansible.builtin.set_fact:
    quota_summary: "{{ quota_summary | default([]) + [entry] }}"
  vars:
    hard_cpu:    "{{ item.spec.hard['requests.cpu'] | default('0') }}"
    used_cpu:    "{{ item.status.used['requests.cpu'] | default('0') }}"
    hard_mem:    "{{ item.spec.hard['requests.memory'] | default('0') }}"
    used_mem:    "{{ item.status.used['requests.memory'] | default('0') }}"
    hard_pods:   "{{ item.spec.hard['pods'] | default('0') }}"
    used_pods:   "{{ item.status.used['pods'] | default('0') }}"
    entry:
      namespace:   "{{ item.metadata.namespace }}"
      hard_cpu:    "{{ hard_cpu }}"
      used_cpu:    "{{ used_cpu }}"
      hard_memory: "{{ hard_mem }}"
      used_memory: "{{ used_mem }}"
      hard_pods:   "{{ hard_pods }}"
      used_pods:   "{{ used_pods }}"
  loop: "{{ all_quotas.resources }}"
  loop_control:
    label: "{{ item.metadata.namespace }}"

- name: "[REPORT] Identify near-limit namespaces (>80%)"
  ansible.builtin.set_fact:
    near_limit_ns: "{{ quota_summary | selectattr('used_pods','defined')
      | list }}"
    # In production: parse CPU/memory values, compute percentage

- name: "[REPORT] Generate HTML quota dashboard"
  ansible.builtin.template:
    src:  templates/quota_report.html.j2
    dest: "{{ report_output_dir | default('/tmp') }}/quota-report-{{ ansible_date_time.date }}.html"

09 Enforcement and Alerting

yamltasks/quota_alert.yml
---
# Alert when namespace quota exceeds 80% threshold

- name: "[ALERT] Check pod quota usage per namespace"
  ansible.builtin.set_fact:
    pod_usage_pct: "{{ ((item.used_pods | int) / (item.hard_pods | int) * 100) | int }}"
  loop: "{{ quota_summary }}"
  loop_control:
    label: "{{ item.namespace }}"
  register: usage_calcs

- name: "[ALERT] Send warning for >80% usage"
  community.general.slack:
    token:   "{{ vault_slack_token }}"
    channel: "#platform-alerts"
    color:   warning
    msg:     "⚠️ Quota Warning: namespace *{{ item.item.namespace }}* is at {{ item.ansible_facts.pod_usage_pct }}% pod quota ({{ item.item.used_pods }}/{{ item.item.hard_pods }} pods)"
  loop: "{{ usage_calcs.results }}"
  loop_control:
    label: "{{ item.item.namespace }}"
  when:
    - item.ansible_facts.pod_usage_pct | int > 80
    - item.ansible_facts.pod_usage_pct | int <= 95

- name: "[ALERT] Send critical alert for >95% usage"
  community.general.slack:
    token:   "{{ vault_slack_token }}"
    channel: "#platform-critical"
    color:   danger
    msg:     "🔴 CRITICAL: namespace *{{ item.item.namespace }}* is at {{ item.ansible_facts.pod_usage_pct }}% pod quota — pods will be REJECTED if quota exceeded!"
  loop: "{{ usage_calcs.results }}"
  loop_control:
    label: "{{ item.item.namespace }}"
  when: item.ansible_facts.pod_usage_pct | int > 95

10 Troubleshooting

SymptomRoot CauseFix
Pod rejected: "exceeded quota"Namespace ResourceQuota is fulloc describe quota -n namespace. Delete unused pods or request quota increase.
Pod rejected: "must specify limits"ResourceQuota exists but no LimitRange to inject defaultsApply LimitRange with defaultRequest/default. Pods without requests will then get defaults auto-injected.
Pod rejected: "exceeds max limit"Container requests more than LimitRange maxCheck LimitRange max. Reduce container resource request/limit. Or increase LimitRange max (requires admin).
Quota shows used=0 but pods existPods were created before ResourceQuota was applied — not counted retroactivelyQuota tracks new admissions. Existing pods are grandfathered. Quota counts will update as pods restart.
LimitRange not injecting defaultsContainer already has explicit requests/limits — LimitRange only injects when none setLimitRange defaults only apply when no value is specified. If container has limits, they're used as-is (must still be within min/max).

11 Interview Questions

What is the difference between ResourceQuota and LimitRange?
ResourceQuota: namespace-level aggregate ceiling. "This namespace can use no more than 16 CPUs total across all pods." Checked at admission — pod is rejected if adding it would exceed the quota. LimitRange: per-container/pod/PVC constraints. "Each container must use between 50m and 4 CPUs." Also auto-injects defaults when container has no requests/limits set. They solve different problems: Quota = multi-tenant isolation, LimitRange = per-pod safety. Both are needed together — Quota requires requests to be set, LimitRange ensures they always are.
A developer says their pod is rejected with "exceeded quota" but oc top shows plenty of free CPU. Why?
ResourceQuota tracks requests, not actual usage. If the namespace quota is requests.cpu: 4, and existing pods collectively request 3.8 CPU, there's only 0.2 CPU of quota left — even if actual usage is much lower. The scheduler reserves request capacity. The developer needs to either: reduce their pod's CPU request, delete other pods, or request a quota increase. oc top shows actual utilisation; oc describe quota shows requested vs quota limit.
Why must you deploy LimitRange before ResourceQuota?
If ResourceQuota exists with compute limits and a developer creates a pod without resource requests, the admission controller rejects it immediately: "must specify limits when ResourceQuota is present." LimitRange's job is to auto-inject default requests/limits so developers don't have to set them manually. If LimitRange doesn't exist, every pod needs explicit requests/limits or it gets rejected. Deploying LimitRange first ensures the safety net is in place before the quota enforcement kicks in.
How would you monitor namespace quota usage and alert before it's exceeded?
Query ResourceQuota objects with k8s_info — they contain both spec.hard (limits) and status.used (current usage). Calculate percentage: (used / hard) × 100. If >80%: Slack warning. If >95%: Slack critical + email. Schedule as daily RHAAP Job Template. Generate HTML report with per-namespace table showing all resource dimensions. This gives teams time to clean up or request quota increases before hitting the hard limit and blocking deployments.

Challenge 2 of 3

Write a task that compares the current ResourceQuota spec against your desired values from group_vars. If they differ, update and log the change. If identical, skip with a message.

▶ Show Answer
yamlIdempotent quota update
- name: "Get current ResourceQuota"
  kubernetes.core.k8s_info:
    kind: ResourceQuota
    name: "{{ environment_name }}-quota"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: current_quota

- name: "Check if quota update needed"
  ansible.builtin.set_fact:
    quota_needs_update: >-
      {{ current_quota.resources | length == 0
         or current_quota.resources[0].spec.hard['requests.cpu'] != quota_requests_cpu
         or current_quota.resources[0].spec.hard['requests.memory'] != quota_requests_memory
         or current_quota.resources[0].spec.hard['pods'] != quota_pods }}

- name: "Apply ResourceQuota (only if changed)"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'resourcequota.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  when: quota_needs_update | bool
  register: quota_update_result

- name: "Log outcome"
  ansible.builtin.debug:
    msg: "{{ 'Quota updated' if quota_needs_update else 'Quota unchanged — skipping' }}"
