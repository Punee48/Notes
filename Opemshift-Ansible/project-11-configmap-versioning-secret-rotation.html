01 The Manager's Eleventh Ticket — INFRA-2004

🏢 ABC Bank OpenShift Platform Team — Intermediate Week 4

Two incidents this month from the same root cause — configuration drift. Rajesh calls:

"First incident: someone updated the Payment API ConfigMap in PROD directly with 'oc edit'. The running pods never picked it up — they still had the old config loaded at startup. We didn't know. Second incident: the database password was supposed to rotate 90 days ago but the Secret in OpenShift still has the old one. The DBA rotated the DB password and now Payment API can't connect. We need: (1) a way to version ConfigMaps so pods always get the latest config, (2) an automated secret rotation procedure that updates OpenShift Secrets AND triggers pod restarts without dropping connections, and (3) the new password must be in Ansible Vault so it's in Git safely."

Two of the most critical operational challenges: config immutability and credential lifecycle management.

Acceptance Criteria

  • 1
    ConfigMap versioning with hash namingConfigMap name includes content hash: payment-api-config-a3f9b2. Content changes → new hash → new name → pod restart forced.
  • 2
    Immutable ConfigMapsSet immutable: true on ConfigMap. Prevents in-place mutation. Any change must create a new version. Old versions deleted after pods updated.
  • 3

  • 4

  • 5
    Ansible Vault rekeying workflowVault password changes. Re-encrypt all vault files with new password. Update RHAAP credential. Test decryption succeeds.
  • 6

02 The Config Drift Problem

🔄
Mutable ConfigMap Problem
Pod reads ConfigMap once at startup and loads it into memory. If you update the ConfigMap in-place, running pods still have old config. Environment variables are never refreshed. Only pod restart picks up new config.
📁
Volume Mount Exception
ConfigMap mounted as files (not env vars) DO update automatically — kubelet refreshes the mounted files every ~60s. But app must re-read the file. Environment variable injection never auto-updates.
⏰
Secret Expiry Problem
DB passwords, API keys, TLS certs all expire. Without rotation automation, teams let them expire (incident) or rotate manually (error-prone). OpenShift Secret doesn't auto-update. Pods use old credentials until restarted.
🔐
Vault Password Expiry
Ansible Vault password itself must rotate. When it does, all vault-encrypted files must be re-encrypted with the new password. A stale vault password in RHAAP = playbook can't decrypt secrets = deployment fails.

03 ConfigMap Versioning — Immutability Strategy

Version Strategy Options

StrategyNaming PatternProsCons
Timestamppayment-api-config-20240315-1430Human-readable, easy to traceAlways creates new version even if content unchanged. Old versions accumulate.
App versionpayment-api-config-v2-3-1Tied to app releaseConfig can change independently of app version. Mismatch risk.
Content hashpayment-api-config-a3f9b2c1Only creates new version when content actually changes. Idempotent.Hash is not human-readable. Need tooling to compare.
Sequence numberpayment-api-config-v003Simple, sortableRequires tracking last sequence. Not idempotent.
✅
Best Practice: Content Hash

Content hash is the industry standard (used by Helm, Kustomize). Hash only changes when config content changes → no unnecessary pod restarts. Ansible can compute it with {{ config_content | hash('sha256') | truncate(8, true, '') }}.

04 Hash-Based Versioning — Deep Dive

yaml tasks/versioned_configmap.yml — Hash-Based Strategy 
---
# ConfigMap versioning with content hash
# Same config content → same hash → same ConfigMap name → no restart
# Changed config → new hash → new ConfigMap → rolling restart


# Step 1: Build the config content dict
- name: "[CONFIG] Build config content"
  ansible.builtin.set_fact:
    config_data:
      APP_ENV:         "{{ environment_name }}"
      DATABASE_HOST:   "{{ database_host }}"
      DATABASE_PORT:   "{{ database_port | string }}"
      LOG_LEVEL:       "{{ app_log_level }}"
      CACHE_TTL:       "{{ cache_ttl | string }}"
      FEATURE_FLAGS:   "{{ feature_flags | to_json }}"

# Step 2: Compute hash of content
- name: "[CONFIG] Compute content hash"
  ansible.builtin.set_fact:
    config_content_str: "{{ config_data | to_json | sort }}"
    config_hash:        "{{ config_data | to_json | hash('sha256') | truncate(8, true, '') }}"
    cm_versioned_name:  "{{ app_name }}-config-{{ config_data | to_json | hash('sha256') | truncate(8, true, '') }}"

- name: "[CONFIG] Log versioned ConfigMap name"
  ansible.builtin.debug:
    msg:
      - "ConfigMap name: {{ cm_versioned_name }}"
      - "Hash: {{ config_hash }}"

# Step 3: Check if this version already exists (idempotency)
- name: "[CONFIG] Check if this ConfigMap version exists"
  kubernetes.core.k8s_info:
    kind: ConfigMap
    name: "{{ cm_versioned_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: cm_check

- name: "[CONFIG] Create new ConfigMap version"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ConfigMap
      metadata:
        name:      "{{ cm_versioned_name }}"
        namespace: "{{ app_namespace }}"
        labels:
          app:          "{{ app_name }}"
          config-hash:  "{{ config_hash }}"
          managed-by:   ansible
        annotations:
          created-by:    "ansible-rhaap"
          created-at:    "{{ ansible_date_time.iso8601 }}"
          config-source: "inventories/{{ environment_name }}/group_vars/all.yml"
      immutable: true              # Cannot be modified after creation
      data: "{{ config_data }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  when: cm_check.resources | length == 0   # Only create if this hash doesn't exist
  register: cm_created

# Step 4: Update Deployment to reference new ConfigMap
- name: "[CONFIG] Patch Deployment to use new ConfigMap version"
  kubernetes.core.k8s:
    state: patched
    kind: Deployment
    name: "{{ app_name }}"
    namespace: "{{ app_namespace }}"
    definition:
      spec:
        template:
          metadata:
            annotations:
              config-version: "{{ cm_versioned_name }}"
              config-updated: "{{ ansible_date_time.iso8601 }}"
          spec:
            containers:
              - name: "{{ app_name }}"
                envFrom:
                  - configMapRef:
                      name: "{{ cm_versioned_name }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  # Changing configMapRef name triggers rolling restart automatically

05 ConfigMap Lifecycle Role — Create, Update, Prune

yaml tasks/prune_old_configmaps.yml — Keep Last N Versions 
---
# Prune old ConfigMap versions — keep last N by creation time


- name: "[PRUNE] List all ConfigMap versions for this app"
  kubernetes.core.k8s_info:
    kind: ConfigMap
    namespace: "{{ app_namespace }}"
    label_selectors:
      - "app={{ app_name }}"
      - "managed-by=ansible"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_cm_versions

- name: "[PRUNE] Sort by creation time (oldest first)"
  ansible.builtin.set_fact:
    sorted_cms: "{{ all_cm_versions.resources
      | sort(attribute='metadata.creationTimestamp')
      | list }}"
    keep_count: "{{ cm_keep_versions | default(3) | int }}"

- name: "[PRUNE] Identify old versions to delete"
  ansible.builtin.set_fact:
    cms_to_delete: "{{ sorted_cms[:(sorted_cms | length - keep_count | int)] }}"

- name: "[PRUNE] Delete old ConfigMap versions"
  kubernetes.core.k8s:
    state: absent
    kind: ConfigMap
    name: "{{ item.metadata.name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  loop: "{{ cms_to_delete }}"
  loop_control:
    label: "Deleting: {{ item.metadata.name }}"
  when:
    - cms_to_delete | length > 0
    - item.metadata.name != cm_versioned_name   # Never delete current

06 Secret Rotation — Lifecycle and Strategies

Secret Rotation Lifecycle
Phase 0: Preparation Generate new credentials. Store both old and new in Ansible Vault. Prepare dual-credential window period.
Phase 1: Dual-Write Update Kubernetes Secret to include BOTH old and new credentials. Apps still use old credentials. This is the safety window.
Phase 2: Rolling Restart Trigger rolling restart of Deployment. New pods pick up new credentials from Secret. Old pods continue serving with old creds during transition.
Phase 3: Verify New Creds Work Smoke test new pods. Confirm DB connections succeed with new credentials. Monitor error rates.
Phase 4: Remove Old Creds Remove old credentials from Secret. Update Vault file. Rotate DB-side. Close the dual-credential window.

07 Zero-Downtime Secret Rotation Playbook

yaml playbooks/rotate_db_secret.yml — Full Rotation Procedure 
---
# Database password rotation — zero downtime
# Pre-requisite: vault_db_password_new is set in vars/secrets.yml (Vault-encrypted)


- name: "Secret Rotation: {{ app_name }} Database Password"
  hosts: localhost
  gather_facts: true
  vars_files:
    - "vars/secrets.yml"
  tasks:

    - name: "Rotation Safety Net"
      block:

        # ── PHASE 0: Pre-flight checks ─────────────────────────────────
        - name: "[PRE] Validate new password is defined and different"
          ansible.builtin.assert:
            that:
              - vault_db_password_new is defined
              - vault_db_password_new | length >= 16
              - vault_db_password_new != vault_db_password
            fail_msg: "vault_db_password_new must be defined, ≥16 chars, and different from current"

        - name: "[PRE] Get current replica count"
          kubernetes.core.k8s_info:
            kind: Deployment
            name: "{{ app_name }}"
            namespace: "{{ app_namespace }}"
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
          register: current_deploy

        - name: "[PRE] Set replica count"
          ansible.builtin.set_fact:
            rotation_replicas: "{{ current_deploy.resources[0].spec.replicas }}"

        # ── PHASE 1: Dual-credential window ────────────────────────────
        - name: "[PHASE1] Update Secret with BOTH old and new passwords"
          kubernetes.core.k8s:
            state: present
            definition:
              apiVersion: v1
              kind: Secret
              metadata:
                name:      "{{ app_name }}-secrets"
                namespace: "{{ app_namespace }}"
              stringData:
                database-password:     "{{ vault_db_password }}"      # OLD: still active
                database-password-new: "{{ vault_db_password_new }}"  # NEW: ready to use
                database-username:     "{{ vault_db_username }}"
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
          no_log: true

        # ── PHASE 2: Rolling restart (pods pick up new Secret) ─────────
        - name: "[PHASE2] Trigger rolling restart via annotation patch"
          kubernetes.core.k8s:
            state: patched
            kind: Deployment
            name: "{{ app_name }}"
            namespace: "{{ app_namespace }}"
            definition:
              spec:
                template:
                  metadata:
                    annotations:
                      secret-rotation: "{{ ansible_date_time.iso8601 }}"
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
          # The annotation change triggers rolling restart of all pods

        - name: "[PHASE2] Wait for rolling restart to complete"
          kubernetes.core.k8s_info:
            kind: Deployment
            name: "{{ app_name }}"
            namespace: "{{ app_namespace }}"
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
          register: restart_status
          until: restart_status.resources[0].status.readyReplicas | default(0) == rotation_replicas | int
          retries: 30
          delay: 10

        # ── PHASE 3: Verify new creds work ─────────────────────────────
        - name: "[PHASE3] Run smoke test to verify new DB connection"
          ansible.builtin.uri:
            url:            "https://{{ app_route_host }}/health/db"
            status_code:    200
            validate_certs: false
          register: db_health
          retries: 5
          delay: 5

        # ── PHASE 4: Remove old credentials ────────────────────────────
        - name: "[PHASE4] Update Secret with ONLY new password"
          kubernetes.core.k8s:
            state: present
            definition:
              apiVersion: v1
              kind: Secret
              metadata:
                name:      "{{ app_name }}-secrets"
                namespace: "{{ app_namespace }}"
              stringData:
                database-password:  "{{ vault_db_password_new }}"   # New IS now current
                database-username:  "{{ vault_db_username }}"
                # Old password key removed
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
          no_log: true

        - name: "[COMPLETE] Mark rotation successful"
          ansible.builtin.set_fact:
            rotation_outcome: "SUCCESS"

      rescue:
        - name: "[RESCUE] Rotation failed — restore old credentials"
          kubernetes.core.k8s:
            state: present
            definition:
              apiVersion: v1
              kind: Secret
              metadata:
                name:      "{{ app_name }}-secrets"
                namespace: "{{ app_namespace }}"
              stringData:
                database-password: "{{ vault_db_password }}"   # Restore old
                database-username: "{{ vault_db_username }}"
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
          no_log: true

        - name: "[RESCUE] Set failed outcome"
          ansible.builtin.set_fact:
            rotation_outcome: "FAILED_RESTORED"

      always:
        - name: "[ALWAYS] Log rotation to audit trail"
          ansible.builtin.lineinfile:
            path:   "/var/log/secret-rotation-audit.log"
            line:   "{{ ansible_date_time.iso8601 }},{{ app_name }},database-password,{{ environment_name }},{{ rotation_outcome | default('UNKNOWN') }}"
            create: true
          no_log: true   # Don't log the actual passwords

        - name: "[ALWAYS] Notify Slack"
          community.general.slack:
            token:   "{{ vault_slack_token }}"
            channel: "#security-ops"
            color:   "{{ 'good' if rotation_outcome == 'SUCCESS' else 'danger' }}"
            msg:     "🔑 Secret Rotation: {{ app_name }} DB password in {{ environment_name | upper }} — {{ rotation_outcome }}"

08 Ansible Vault Rekeying — Rotating the Vault Password

bash Vault Password Rotation — Step by Step 
# ── Step 1: Create new vault password file ─────────────────────────────
echo "NewStrongVaultPassword!2024" > ~/.vault-password-new
chmod 600 ~/.vault-password-new

# ── Step 2: Rekey each vault-encrypted file ────────────────────────────
# ansible-vault rekey: decrypt with old, re-encrypt with new
ansible-vault rekey \
  --vault-password-file ~/.vault-password \
  --new-vault-password-file ~/.vault-password-new \
  vars/secrets.yml

# Rekey all vault files in one command
find . -name "*.yml" -exec grep -l "ANSIBLE_VAULT" {} \; | \
  xargs ansible-vault rekey \
    --vault-password-file ~/.vault-password \
    --new-vault-password-file ~/.vault-password-new

# ── Step 3: Test decryption with new password ──────────────────────────
ansible-vault view vars/secrets.yml \
  --vault-password-file ~/.vault-password-new
# Should display plaintext content

# ── Step 4: Replace old password file ─────────────────────────────────
mv ~/.vault-password-new ~/.vault-password
# Old password file overwritten

# ── Step 5: Update RHAAP Credential ───────────────────────────────────
# RHAAP UI → Credentials → Vault Password Credential → Edit → paste new password
# OR via RHAAP REST API:
curl -X PATCH \
  https://rhaap.abcbank.internal/api/v2/credentials/15/ \
  -H "Authorization: Bearer $RHAAP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"inputs": {"vault_password": "NewStrongVaultPassword!2024"}}'

# ── Step 6: Test a playbook with new vault password ────────────────────
ansible-playbook playbooks/cluster_health_check.yml \
  --vault-password-file ~/.vault-password \
  -i inventories/dev --check
# Should run without decryption errors

09 External Secret Managers — Introduction

For enterprise PROD, Ansible Vault in Git is a good intermediate step. The gold standard is an external secret manager: HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault. These provide: audit logs for every secret access, automatic rotation, versioning, and fine-grained access control.

yaml Reading from HashiCorp Vault in Ansible 
---
# Read secrets from HashiCorp Vault instead of Ansible Vault
# Requires: community.hashi_vault collection + VAULT_ADDR + VAULT_TOKEN env vars


- name: "[SECRETS] Read DB password from HashiCorp Vault"
  ansible.builtin.set_fact:
    vault_db_password: "{{ lookup('community.hashi_vault.hashi_vault',
        'secret=secret/data/payment-api/db-password:password
         url=' + hashi_vault_addr +
         ' token=' + hashi_vault_token) }}"
  no_log: true

# Read from AWS Secrets Manager
- name: "[SECRETS] Read from AWS Secrets Manager"
  ansible.builtin.set_fact:
    aws_db_password: "{{ lookup('amazon.aws.aws_secret',
        'payment-api/db-password',
        region='us-east-1') | from_json | json_query('password') }}"
  no_log: true

# External Secret Operator (ESO) — declarative approach
# Create ExternalSecret CRD that syncs from vault to Kubernetes Secret automatically
- name: "[ESO] Create ExternalSecret referencing HashiCorp Vault"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: external-secrets.io/v1beta1
      kind: ExternalSecret
      metadata:
        name:      "{{ app_name }}-db-secret"
        namespace: "{{ app_namespace }}"
      spec:
        refreshInterval: "1h"         # ESO re-reads vault every hour
        secretStoreRef:
          name:  vault-backend
          kind:  ClusterSecretStore
        target:
          name:             "{{ app_name }}-secrets"
          creationPolicy:   Owner
        data:
          - secretKey:  database-password
            remoteRef:
              key:      "secret/payment-api/db"
              property: password
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"

11 Interview Questions

Why can't you just update a ConfigMap in-place to push new config to pods?
Environment variables (envFrom / env valueFrom) are injected at pod startup and never refreshed. Updating the ConfigMap in-place has no effect on running pods — they still have the old values in memory. Only a pod restart picks up new env vars. ConfigMap volume mounts (files) DO auto-refresh (~60s kubelet sync), but the app must re-read the file. The correct pattern for env-var configs is immutable versioned ConfigMaps: new content → new hash → new name → Deployment updated → rolling restart forced automatically.
Explain the dual-credential window in secret rotation. Why is it needed?
During a rolling restart, some pods run the old version (with old credentials) and some run the new version (with new credentials) simultaneously. If you switch to new-only credentials before all pods restart, old pods can't authenticate → connection errors → incident. The dual-credential window: Secret contains both old-key and new-key for the duration of the rolling restart. After all pods are restarted and verified working with new creds, remove the old key. This ensures zero dropped connections during rotation.
What is Ansible Vault rekeying and when would you do it?
Rekeying: decrypt with current vault password, re-encrypt with new vault password. The encrypted content stays the same; only the encryption key changes. When to do it: (1) vault password rotation policy (90-day cycle), (2) team member leaves (password compromise risk), (3) vault password exposed in logs or accidentally committed. Process: ansible-vault rekey --vault-password-file OLD --new-vault-password-file NEW file.yml. Then update RHAAP Credential with new password. Test decryption before deploying.
What is the External Secret Operator and when would you use it over Ansible Vault?
External Secret Operator (ESO): a Kubernetes operator that syncs secrets from external secret managers (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault) into Kubernetes Secrets automatically. Use ESO over Ansible Vault when: (1) you need automatic rotation without running a playbook, (2) compliance requires external audit log for every secret access, (3) secrets need to be shared across multiple teams/clusters, (4) you want fine-grained access control per secret. Ansible Vault: simpler, Git-native, good for medium teams. ESO: enterprise-scale with dedicated secret management.
How do you force a pod restart after a Secret change in Kubernetes?
Three methods: (1) kubectl/oc rollout restart: oc rollout restart deployment/payment-api — simplest, triggers rolling restart. (2) Annotation patch: patch deployment.spec.template.metadata.annotations with a unique value (timestamp). Annotation change triggers pod template hash change → rolling restart. (3) Scale down then up: set replicas=0, then replicas=N — not zero-downtime. Method 2 (annotation patch) is best for Ansible because it's idempotent-compatible and creates an audit trail in the deployment's history.
