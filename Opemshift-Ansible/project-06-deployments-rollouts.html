02 Kubernetes Deployments — Declarative Desired State

Why Deployments?

Direct pod creation (imperative: kubectl run payment-api) is fragile. Pod dies? Gone. Want 3 replicas? Manually create 3. Need to update image? Stop and restart manually.

Deployments (declarative): You describe what you want (3 replicas, image:v2, rolling update). Kubernetes continuously ensures reality matches your declaration. Pod crashes? Deployment auto-restarts it. Image gets updated? Deployment orchestrates rolling update. No manual intervention.

Pods (Ephemeral)

  • Direct pod creation
  • No automatic restart
  • Manual scaling
  • Manual updates
  • Use for: one-off tasks, debugging

ReplicaSets (Replica Control)

  • Maintains N replicas
  • Auto-restart failed pods
  • Label-based pod selection
  • Manual image updates
  • Use for: declarative replicas (rarely direct)

Deployments (Lifecycle Mgmt)

  • Manages ReplicaSets
  • Rolling/blue-green updates
  • Automatic revision history
  • Instant rollback
  • Use for: all stateless applications
📊
Deployment → ReplicaSet → Pods Hierarchy

Deployment is the highest-level abstraction. You create 1 Deployment. Deployment creates ReplicaSets (one per update). ReplicaSets manage Pods (replicas: 3 = 3 pods). When you update Deployment image, it creates NEW ReplicaSet, scales up new pods, scales down old pods. Old ReplicaSet kept in history for instant rollback.

03 Update Strategies — Rolling, Blue-Green, Canary

📈
Rolling Update
Gradually replace old pods with new. 1 old pod goes down, 1 new pod comes up. Process repeats until all replaced. Zero downtime but gradual version mix.
🔄
Blue-Green
Run two complete environments (blue=old, green=new). Route 100% traffic to blue. Test green fully. Switch traffic to green instantly. Rollback: switch back to blue instantly.
🕯️
Canary
Run new version alongside old. Route 10% traffic to new, 90% to old. Monitor new version. If stable, gradually shift 20%, 50%, 100%. Rollback: shift back to old.
Rolling Update Timeline

Initial State (3 replicas, image:v1):
[Pod1-v1] [Pod2-v1] [Pod3-v1]

Deployment updated to image:v2, maxUnavailable=1, maxSurge=1:

Step 1 (max 1 can be down, max 1 new can surge):
[Pod1-v1] [Pod2-v1] [Pod3-v1] → [Pod1-v2] [Pod2-v1] [Pod3-v1]
1 old replaced, 3 old + 0 new = 3 total (no surge yet)

Step 2:
[Pod1-v2] [Pod2-v2] [Pod3-v1] → [Pod1-v2] [Pod2-v2] [Pod3-v2]
All 3 new, 0 old. Update complete. No downtime.

04 Rolling Updates Deep Dive — Zero-Downtime Strategy

Deployment Manifest with Rolling Update

yaml Kubernetes Deployment - Rolling Update Configuration 
---
# Deployment: Rolling update strategy (default)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: production
  labels:
    app: payment
spec:
  replicas: 3                      # Always run 3 pods
  selector:                       # Pod selection (must match template labels)
    matchLabels:
      app: payment
      tier: backend

  # Update strategy
  strategy:
    type: RollingUpdate         # Replace one by one (zero downtime)
    rollingUpdate:
      maxUnavailable: 1          # Max 1 pod can be down at a time
      maxSurge: 1               # Max 1 extra pod (total 4 during update)
      # Alternative: percentages
      # maxUnavailable: 25%  (0.75 * 3 = 2 pods must be ready)
      # maxSurge: 25%        (up to 3.75 = 4 pods total)

  progressDeadlineSeconds: 600  # Abort if update not complete in 600s
  revisionHistoryLimit: 10      # Keep last 10 ReplicaSets for rollback

  template:                       # Pod template
    metadata:
      labels:
        app: payment
        tier: backend
        version: v2            # Label pods with version for tracking

    spec:
      # Scheduling constraints
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values: [payment]
                topologyKey: kubernetes.io/hostname
              # Prefer: spread pods across different nodes (fault tolerance)

      containers:
        - name: api
          image: payment-api:v2      # New version
          imagePullPolicy: Always # Always pull latest tag (for CI)
          ports:
            - name: http
              containerPort: 8080

          # Health checks (section 04)
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10

          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5

          # Resource management (section 05)
          resources:
            requests:                  # Minimum guaranteed
              cpu: "500m"
              memory: "512Mi"
            limits:                    # Maximum allowed
              cpu: "1000m"
              memory: "1Gi"

Update Terminology: maxUnavailable & maxSurge

Rolling Update Parameters
maxUnavailableMax pods that can be unavailable during update. If replicas=3, maxUnavailable=1, then min 2 pods must be ready at all times.
maxSurgeMax pods above desired replicas during update. If replicas=3, maxSurge=1, then up to 4 pods can run during update (3 + surge).
Trade-offConservative (maxUnavailable=0, maxSurge=1): safest, no downtime. Aggressive (maxUnavailable=1, maxSurge=0): fast but resource-limited.

05 Rollbacks & Revision History — Instant Recovery

How Rollback Works

Kubernetes keeps ReplicaSets in history. Each update creates new ReplicaSet. Old ReplicaSets scale down but remain (for rollback).

Day 1: Deploy v1
Deployment creates ReplicaSet-001. 3 pods running v1. ReplicaSets in history: [ReplicaSet-001 (active)]
Day 2: Update to v2
Deployment creates ReplicaSet-002. Scales up v2 pods, scales down v1. ReplicaSets: [ReplicaSet-001 (inactive), ReplicaSet-002 (active)]
Day 3: v2 Has Bug 🐛
One command: oc rollout undo. Deployment scales down ReplicaSet-002, scales up ReplicaSet-001. Instant rollback to v1. No redeployment needed.
Day 4: Update to v3
ReplicaSet-003 created. ReplicaSets: [001 (inactive), 002 (inactive), 003 (active)]. Revisions kept for history.

Rollback Commands

bash OpenShift Rollout Commands 
# View rollout history
oc rollout history deployment/payment-api -n production
# Output:
# REVISION    CHANGE-CAUSE
# 1           Initial deployment
# 2           Updated to v2
# 3           Updated to v3 (current)

# View details of specific revision
oc rollout history deployment/payment-api --revision=2
# Shows diff: image=payment-api:v2, replicas=3, etc

# Rollback to previous revision
oc rollout undo deployment/payment-api -n production
# Immediately reverts to revision 2 (one before current)

# Rollback to specific revision
oc rollout undo deployment/payment-api --to-revision=1 -n production
# Go back to v1 (revision 1)

# Watch rollout progress
oc rollout status deployment/payment-api -n production --watch
# Streams live updates as pods are replaced

06 Liveness & Readiness Probes — Ensuring Pod Health

❤️
Liveness Probe
Is the pod alive? If probe fails, Kubernetes restarts pod. Use for: detecting crashed app (still running but hung). Example: GET /health returns 200.
✅
Readiness Probe
Is the pod ready for traffic? If probe fails, pod removed from Service load balancer. Use for: detecting startup delay, warming up. Example: GET /ready returns 200 when initialized.

Probe Types

yaml Probe Examples: HTTP, Exec, TCP 
# HTTP Probe (most common)
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 15   # Wait 15s after container start before probing
  periodSeconds: 10       # Probe every 10 seconds
  timeoutSeconds: 3       # Wait max 3s for response
  failureThreshold: 3     # Restart after 3 consecutive failures

# Exec Probe (for scripts)
readinessProbe:
  exec:
    command:
      - "/bin/sh"
      - "-c"
      - "curl -f http://localhost:8080/health || exit 1"
  initialDelaySeconds: 5
  periodSeconds: 5

# TCP Probe (for raw TCP services)
livenessProbe:
  tcpSocket:
    port: 5432             # PostgreSQL
  initialDelaySeconds: 10
  periodSeconds: 10

07 Resource Requests & Limits — Fair Allocation

Requests vs Limits

Resource Management
Request (minimum)Guaranteed resources. Scheduler reserves this for pod. Pod will NOT start if cluster can't guarantee resources.
Limit (maximum)Hard ceiling. Pod cannot exceed. If CPU limit hit, pod is throttled. If memory limit hit, pod is OOMKilled (terminated).
CPU Units1 = 1 core. 500m = 0.5 cores. 100m = 0.1 cores. Set request=average, limit=peak.
Memory UnitsMi, Gi. 512Mi = 512 mebibytes. 1Gi = 1024 mebibytes. Request = expected usage, limit = max.

---
# Create Deployment with rolling update strategy


- name: "[DEPLOY] Create or update Deployment"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'deployment.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: deployment_result
  tags: [deploy]

- name: "[WAIT] Wait for rollout to complete"
  ansible.builtin.command:
    cmd: "oc rollout status deployment/{{ deployment_name }} -n {{ app_namespace }} --timeout=10m"
  environment:
    KUBECONFIG: "{{ kubeconfig_path }}"
  tags: [wait]

- name: "[VERIFY] Check Deployment status"
  kubernetes.core.k8s_info:
    kind: Deployment
    name: "{{ deployment_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: deployment_status
  tags: [verify]

- name: "[ASSERT] All replicas ready"
  ansible.builtin.assert:
    that:
      - deployment_status.resources[0].status.replicas == desired_replicas
      - deployment_status.resources[0].status.readyReplicas == desired_replicas
    fail_msg: "Deployment not ready: {{ deployment_status.resources[0].status }}"
  tags: [verify]

- name: "[LOG] Deployment successful"
  ansible.builtin.debug:
    msg:
      - "Deployment: {{ deployment_name }}"
      - "Replicas: {{ deployment_status.resources[0].status.replicas }}"
      - "Ready: {{ deployment_status.resources[0].status.readyReplicas }}"
      - "Updated: {{ deployment_status.resources[0].status.updatedReplicas }}"
  tags: [verify]

      ready: "{{ deploy_info.resources[0].status.readyReplicas | default(0) }}

- name: "Print rollout progress"
  ansible.builtin.debug:
    msg: "{{ rollout_summary }}"

11 Troubleshooting Guide

SymptomErrorRoot CauseFix
Pods not starting ImagePullBackOff Image not found or registry credentials missing Verify image exists: docker pull payment-api:v2. Check imagePullSecrets in Deployment.
Deployment stuck ProgressDeadlineExceeded Pod not becoming ready (readiness probe failing) Check pod logs: oc logs pod-name. Verify readiness probe endpoint is correct.
Pod crashing loop CrashLoopBackOff App error or liveness probe too strict Check logs. Increase liveness initialDelaySeconds. Verify app starts properly.
Not enough resources Insufficient cpu/memory Resource requests too high for available nodes Check node capacity: oc top nodes. Lower requests or add nodes.
Rollback stuck unable to compute revision ReplicaSet not in history (revisionHistoryLimit too low) Check history: oc rollout history deployment. Increase revisionHistoryLimit.

12 Interview Questions

Explain the difference between ReplicaSets and Deployments. When would you use each?
ReplicaSets manage pod replicas: ensure N pods running, restart failed pods. Deployments manage ReplicaSets: handle updates, rollbacks, revision history. Use Deployments for production (they handle everything). ReplicaSets are rarely created directly — Deployments create them. A Deployment is "I want 3 replicas of v1, then update to v2 safely". A ReplicaSet is just "I want 3 replicas".
Describe a rolling update. What are maxUnavailable and maxSurge?
Rolling update replaces pods one-at-a-time: old v1 pod down, new v2 pod up. Repeat until all replaced. Zero downtime. maxUnavailable (default 1) = max pods that can be down at once. maxSurge (default 1) = max extra pods above replicas during update. Example: 3 replicas, maxUnavailable=1, maxSurge=1. At any moment: min 2 old pods ready + up to 1 new pod = 3-4 pods total.
How does rollback work in Kubernetes?
Deployments keep ReplicaSets in history (revisionHistoryLimit=10 keeps last 10). Each update creates new ReplicaSet. Old ReplicaSets scale down but remain. Rollback: one command (oc rollout undo) scales down current ReplicaSet, scales up previous one. Instant — no redeployment, no new pods created, just state change. Check history: oc rollout history deployment/name.
What is the difference between liveness and readiness probes?
Liveness probe: "Is pod alive?" If fails, restart pod. Use for detecting hung processes. Readiness probe: "Is pod ready for traffic?" If fails, remove from Service load balancer. Use for detecting startup delays. Both use same probe mechanisms (HTTP GET, TCP, exec). Liveness typically checks: /health (returns 500 if broken). Readiness checks: /ready (returns 503 if initializing).
Explain resource requests vs limits.
Request (minimum): "I need this much guaranteed". Scheduler reserves this before starting pod. Pod guaranteed this much. Limit (maximum): "I can't use more than this". Pod throttled or killed if exceeded. Example: request=500m CPU (guaranteed), limit=1000m (won't exceed). Request = expected avg usage, limit = peak. Both help prevent noisy-neighbor problem where one app starves others.
