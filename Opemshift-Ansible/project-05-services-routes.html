02 Kubernetes Service Types — From Private to Public

ClusterIP (Default)

  • Internal IP only, not routable from outside cluster
  • Pods access via DNS: service-name.namespace.svc.cluster.local
  • Load balances across pod replicas automatically
  • Use for: internal service-to-service communication
  • Example: Fraud Detector → Payment API (internal)
  • No external port exposure

NodePort

  • Opens port on every node (30000-32767 default range)
  • External traffic can reach: node-ip:nodeport
  • Useful for on-premises, no cloud LB
  • Use for: testing, development, non-cloud deployments
  • Not recommended for production (high port numbers)
  • StaticIP not guaranteed across node restarts

LoadBalancer

  • Cloud provider provisions external load balancer (AWS ELB, Azure LB, etc)
  • Stable external IP automatically assigned
  • Traffic reaches pod via cloud infrastructure
  • Use for: cloud-based clusters, external APIs
  • Expensive (each Service = one LB)
  • OpenShift uses Routes instead (more flexible)

OpenShift Route

  • Built on top of Ingress (OpenShift-specific)
  • HTTP/HTTPS routing by hostname and path
  • TLS termination at route level
  • Use for: OpenShift production deployments
  • Single ingress controller handles all routes
  • More efficient than LoadBalancer per-Service

03 Service Manifest Deep Dive

ClusterIP Service (Internal Communication)

yaml Kubernetes Service - ClusterIP Type 
---
# Service: ClusterIP
# Internal service discovery. Pods access via DNS.

apiVersion: v1
kind: Service
metadata:
  name: payment-api                 # DNS name: payment-api.production.svc.cluster.local
  namespace: production
  labels:
    app: payment
spec:
  type: ClusterIP                  # Internal only
  clusterIP: 10.0.10.5             # Auto-assigned if not specified
  sessionAffinity: ClientIP     # Sticky sessions: same client → same pod
  sessionAffinityConfig:
    clientIPConfig:
      timeoutSeconds: 10800       # 3 hour sticky timeout
  ports:
    - name: http                       # Port name
      port: 8080                     # Service port (what clients access)
      targetPort: 8080            # Pod port (where container listens)
      protocol: TCP
  selector:                         # Route traffic to pods with these labels
    app: payment
    tier: backend

# Pod labels MUST match selector for traffic to route
# Example Pod:
#   labels:
#     app: payment
#     tier: backend
#   containers:
#     - name: api
#       ports:
#         - containerPort: 8080

04 OpenShift Routes — Exposing Services to the Internet

Route Manifest with TLS Termination

yaml OpenShift Route - HTTPS with TLS Termination 
---
# OpenShift Route: Expose Service to external clients
# TLS termination: HTTPS → HTTP backend

apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: payment-api
  namespace: production
  labels:
    app: payment
spec:
  host: payment-api.bank.com       # External DNS hostname (must be resolvable)
  path: /api                       # Optional: path-based routing

  # TLS Configuration: HTTPS
  tls:
    termination: edge              # edge=terminate at router, passthrough=passthrough to backend
    insecureEdgeTerminationPolicy: Redirect  # HTTP→HTTPS redirect
    certificate: |                  # TLS certificate (PEM format)
      -----BEGIN CERTIFICATE-----
      MIIDXTCCAkWgAwIBAgIJAJx...
      -----END CERTIFICATE-----
    key: |                          # Private key (PEM format)
      -----BEGIN PRIVATE KEY-----
      MIIEvQIBADANBgkqhkiG9w0...
      -----END PRIVATE KEY-----
    caCertificate: |              # CA chain (optional)
      -----BEGIN CERTIFICATE-----
      ...
      -----END CERTIFICATE-----

  # Backend Service
  to:
    kind: Service                 # Route traffic to Service
    name: payment-api            # Service name (in same namespace)
    weight: 100               # Traffic weight (for canary deployments)

  # Load balancing policy
  port:
    targetPort: 8080            # Service port to route to

  wildcardPolicy: None          # None=exact match, Subdomain=*.domain.com
🏗️
Route Architecture

External Client → HTTPS (port 443) → OpenShift Router (TLS termination) → Plain HTTP → Service (ClusterIP) → Load-balances across Pod Replicas. The Route terminates TLS at the edge (router), so backend pods see plain HTTP. This offloads crypto from app pods.

05 Service Discovery & DNS in Kubernetes

How Pods Discover Services

Service Discovery Flow

Pod in same namespace:
Pod looks up: "payment-api"
↓ Kubernetes DNS (CoreDNS)
Resolves to: payment-api.production.svc.cluster.local → 10.0.10.5
↓
Pod connects to 10.0.10.5:8080
↓ Service load-balances
Traffic routed to backend pods

Pod in different namespace:
Pod looks up: "payment-api.production"
↓
Resolves to: payment-api.production.svc.cluster.local → 10.0.10.5

DNS Record Types:
A records: payment-api.production.svc.cluster.local → 10.0.10.5 (ClusterIP)
SRV records: _http._tcp.payment-api.production.svc.cluster.local → (port info)

DNS Resolution Examples

bash DNS Lookups from Within Pods 
# From pod in production namespace:

# Option 1: Short name (same namespace)
nslookup payment-api
# Returns: 10.0.10.5 (ClusterIP)

# Option 2: Namespace-scoped
nslookup payment-api.production
# Returns: 10.0.10.5

# Option 3: Fully qualified domain name
nslookup payment-api.production.svc.cluster.local
# Returns: 10.0.10.5 (most explicit)

# From pod in different namespace (dev):
nslookup payment-api.production
# Returns: 10.0.10.5 (cross-namespace access)

# Service endpoints query
curl http://payment-api:8080/health
# Automatically load-balanced across pods

    api_key: "{{ ocp_token }}"
  register: route_result
  tags: [route]

- name: "[VERIFY] Service created and endpoints assigned"

    api_key: "{{ ocp_token }}"

  until: verify_service.resources[0].spec.clusterIP is defined
  retries: 5
  delay: 2
  tags: [verify]

08 Ingress & TLS Configuration Patterns

TLS Termination Options

🔒
Edge Termination
Route terminates TLS. Client ↔ Router: HTTPS. Router ↔ Pod: HTTP. Most common, offloads crypto.
🔐
Passthrough
Route passes TLS to backend. Client ↔ Pod: HTTPS end-to-end. Pod must handle TLS (mutual TLS, gRPC).
🛡️
Re-encrypt
Route terminates client TLS, re-encrypts to backend. Client ↔ Router ↔ Pod: both HTTPS. Extra security.

Certificate Management Pattern

# Option 1: Inline in Route (as shown earlier)

    that:
      - verify_service.resources[0].spec.clusterIP is defined

- name: "Verify Route has ingress hostname"
  ansible.builtin.assert:
    that:
      - verify_route.resources[0].status.ingress[0].host is defined
    fail_msg: "Route not assigned ingress host"

# Test 3: Pod can resolve service DNS
- name: "[TEST] Verify DNS resolution from pod"
  ansible.builtin.command:
    cmd: "oc exec -n {{ app_namespace }} -it {{ app_pod_name }} -- nslookup {{ app_service_name }}"
  environment:
    KUBECONFIG: "{{ kubeconfig_path }}"
  register: dns_test
  changed_when: false

- name: "[ASSERT] DNS resolution successful"
  ansible.builtin.assert:
    that:
      - 'Name:' in dns_test.stdout
    fail_msg: "DNS resolution failed. Output: {{ dns_test.stdout }}"

# Test 4: External connectivity to route
- name: "[TEST] HTTP health check to external route"
  ansible.builtin.uri:
    url: "https://{{ route_hostname }}/health"
    validate_certs: false        # Ignore self-signed cert warnings in test
    method: GET
    status_code: 200
  register: route_test
  until: route_test.status == 200
  retries: 5
  delay: 5

10 Troubleshooting Guide

SymptomErrorRoot CauseFix
Service has no endpoints Endpoints: 0/0 No pods match Service selector labels Verify pod labels: oc get pods --show-labels. Match selector in Service spec.
DNS resolution fails nslookup: can't resolve... Service name wrong, or coredns pod not running Check coredns: oc get pods -n kube-system -l k8s-app=kube-dns. Try FQDN: payment-api.production.svc.cluster.local
Route won't create HostAlreadyClaimed Another route already using that hostname Change hostname or delete existing route: oc delete route name
HTTPS connection fails SSL_ERROR_BAD_CERT_DOMAIN Certificate CN or SAN doesn't match route hostname Generate cert for correct domain: openssl req -subj "/CN=payment-api.bank.com"
Connection timeout to service Connection refused or timeout Port mismatch: service port ≠ pod container port Verify: Service spec.ports[].port and targetPort match pod containerPort.

11 Interview Questions

Explain the difference between ClusterIP, NodePort, and LoadBalancer Service types. When would you use each?
ClusterIP (default): internal-only, pods reach via DNS name (payment-api.prod.svc.cluster.local). Use for internal microservice communication. NodePort: opens a port on every node (30000-32767), external clients reach node-ip:nodeport. Use for testing, on-premises. LoadBalancer: cloud provider provisions external IP, stable endpoint for external APIs. Expensive (per-service). OpenShift prefers Routes instead: one ingress router, multiple routes via hostname.
What is service discovery in Kubernetes? How does DNS work?
Service discovery: pods find services by name instead of IP. Kubernetes runs CoreDNS (cluster DNS). When you create Service "payment-api" in namespace "production", DNS records created: payment-api.production.svc.cluster.local → ClusterIP. Pods query DNS to get IP, then connect. Within same namespace, short name works: "payment-api". Across namespaces: "payment-api.production". Service load-balances traffic automatically to healthy pods behind it.
How does a Route differ from a Service? Why would you use a Route?
Service: load balances traffic. Route: provides HTTP(S) ingress with hostnames and TLS. Service is layer 4 (TCP/UDP); Route is layer 7 (HTTP). Route enables: hostname-based routing (payment-api.bank.com), path-based routing (/api vs /admin), TLS termination, redirect HTTP→HTTPS. Multiple routes share one ingress controller (efficient). One LoadBalancer per Service would be expensive. Routes are OpenShift-specific (Kubernetes uses Ingress resource).
Explain TLS termination in a Route. Where does encryption happen?
Edge termination (most common): Client connects HTTPS (port 443) to OpenShift router. Router terminates TLS (decrypts). Router connects HTTP (plain) to Service backend pods. Route config specifies: certificate (for HTTPS), key, hostname (payment-api.bank.com). This offloads crypto from app pods. Pod sees plain HTTP, no crypto overhead. Client → Router: encrypted. Router → Pod: plain.
What happens if a pod crashes or is unhealthy? How does the Service respond?
Kubernetes continuously runs liveness and readiness probes (if configured). If readiness probe fails, pod is removed from Service endpoints. Traffic stops routing to that pod. Service load-balancer keeps traffic on healthy pods only. Deployment controller may restart the pod (if restartPolicy=Always). If all pods in service fail, requests to service fail (no healthy endpoints). This is why replicas matter: Deployment with 3 replicas = fault tolerance.

Challenge 3 of 3

Create a task that waits for all Service endpoints to be ready. The task should retry until the Service has at least N healthy pods behind it. Use until/retries.

▶ Show Answer
yamlWait for endpoints task
- name: "Wait for Service endpoints to be ready"
  kubernetes.core.k8s_info:
    kind: Endpoints
