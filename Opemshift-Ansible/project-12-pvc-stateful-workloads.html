02 Kubernetes Storage Architecture

Storage Object Hierarchy

Administrator layer:
StorageClass (gp3-ssd) ← Defines HOW storage is provisioned
↓ dynamic provisioning
PersistentVolume (pvc-abc123-xyz) ← Actual storage resource (AWS EBS, NFS, Ceph...)

Developer layer:
PersistentVolumeClaim (postgres-data) ← Request for storage (I need 50Gi, ReadWriteOnce)
↓ bound to PV automatically
Pod volume mount: /var/lib/postgresql ← Container sees storage as a filesystem path

PVC → PV binding: Kubernetes scheduler finds PV that satisfies PVC request
Dynamic provisioning: StorageClass auto-creates PV when PVC created (no manual PV needed)

03 PV, PVC, and StorageClass — Deep Dive

Core Storage Objects
StorageClass Defines storage "profile": provisioner (aws-ebs, ceph-rbd, nfs), parameters (iops, type), reclaim policy. Cluster-scoped. Admin creates. Multiple classes: gp2-spinning, gp3-ssd, cephfs-shared.
PersistentVolume (PV) Actual storage resource. Either manually created (static provisioning) or auto-created by StorageClass (dynamic). Cluster-scoped. Like a physical disk. Has capacity, access modes, reclaim policy.
PersistentVolumeClaim (PVC) Storage request from a namespace. "I need 50Gi, ReadWriteOnce, gp3-ssd StorageClass." Kubernetes finds or creates matching PV and binds them. Namespace-scoped. Deleted when done (if reclaim=Delete, PV deleted too).
Binding PVC + PV are 1:1 relationship. Once bound, nobody else can claim that PV. PVC phase: Pending → Bound → Released (if PVC deleted). Bound PVC can be mounted by Pods.
Reclaim Policy What happens to PV when PVC is deleted. Retain: PV stays, data safe, must manually reclaim. Delete: PV and underlying storage deleted automatically. Recycle (deprecated). Use Retain for DB data.

04 Access Modes — Who Can Mount What

ModeAbbrevMeaningUse CaseExample Backend
ReadWriteOnceRWOOne node can mount read-write. Multiple pods on SAME node OK.Databases, single-instance appsAWS EBS, Azure Disk
ReadOnlyManyROXMany nodes can mount read-only simultaneouslyShared config files, ML model servingNFS, CephFS
ReadWriteManyRWXMany nodes can mount read-write simultaneouslyShared file storage, content reposNFS, CephFS, Azure Files
ReadWriteOncePodRWOPOnly ONE pod (not just one node) can mount read-writeStrict single-writer guaranteeCSI drivers (k8s 1.22+)
⚠️
Critical: RWO and Deployment replicas > 1

A PVC with RWO access mode can only be mounted on ONE node at a time. If you use a Deployment with replicas=3 and RWO storage, pods on different nodes will fail to mount — only pods on the same node as the PV can attach. This is why databases use StatefulSets with 1 replica (primary) + replication, not Deployments with multiple replicas sharing one PVC.

05 StatefulSets vs Deployments — When to Use Each

Deployment (Stateless)

  • Pods are interchangeable — any pod is equivalent
  • Pod names: payment-api-7f8b9c-xkz2p (random suffix)
  • Pods can be scheduled on any node
  • All pods share config; no per-pod storage
  • Scale up: add identical pod
  • Scale down: remove any pod
  • Use for: APIs, web apps, workers — anything stateless

StatefulSet (Stateful)

  • Pods have stable identity — postgres-0, postgres-1
  • Pod names: postgres-0, postgres-1, postgres-2 (ordinal)
  • Pods get their own dedicated PVC each
  • Scale up: pods created in order (0, then 1, then 2)
  • Scale down: pods deleted in reverse order (2, then 1)
  • Stable DNS: postgres-0.postgres.ns.svc.cluster.local
  • Use for: databases, message queues, cache clusters

PostgreSQL StatefulSet Manifest

yaml PostgreSQL StatefulSet + Headless Service 
---
# Headless Service — enables stable DNS per pod
# postgres-0.postgres.fraud-detection.svc.cluster.local

apiVersion: v1
kind: Service
metadata:
  name:      postgres
  namespace: fraud-detection
spec:
  clusterIP: None              # Headless! No single IP — DNS resolves to pod IPs directly
  selector:
    app: postgres
  ports:
    - port: 5432
      name: postgres

---
# StatefulSet — stable identity + dedicated PVC per pod

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name:      postgres
  namespace: fraud-detection
spec:
  serviceName: postgres      # References headless Service above
  replicas: 1                # Primary only; replicas handled by Postgres streaming replication
  selector:
    matchLabels:
      app: postgres

  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name:  postgres
          image: postgres:15
          ports:
            - containerPort: 5432
          env:
            - name:  POSTGRES_DB
              value: frauddb
            - name:  POSTGRES_USER
              value: frauduser
            - name:  POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: postgres-secret
                  key:  password
          volumeMounts:
            - name:      postgres-data
              mountPath: /var/lib/postgresql/data
          resources:
            requests:
              cpu:    "500m"
              memory: "1Gi"
            limits:
              cpu:    "2000m"
              memory: "4Gi"
          livenessProbe:
            exec:
              command: ["pg_isready", "-U", "frauduser"]
            initialDelaySeconds: 30
            periodSeconds:       10
          readinessProbe:
            exec:
              command: ["pg_isready", "-U", "frauduser"]
            initialDelaySeconds: 5
            periodSeconds:       5

  # volumeClaimTemplates: each pod gets its OWN PVC
  # postgres-0 → postgres-data-postgres-0
  # postgres-1 → postgres-data-postgres-1 (if scaled)
  
  volumeClaimTemplates:
    - metadata:
        name: postgres-data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: gp3-ssd
        resources:
          requests:
            storage: 50Gi

06 PVC Automation with Ansible

yaml tasks/provision_pvc.yml — PVC Lifecycle Management 
---
# Provision a PVC and verify it binds successfully


- name: "[PVC] Create PersistentVolumeClaim"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: PersistentVolumeClaim
      metadata:
        name:      "{{ pvc_name }}"
        namespace: "{{ app_namespace }}"
        labels:
          app:        "{{ app_name }}"
          managed-by: ansible
        annotations:
          created-at:  "{{ ansible_date_time.iso8601 }}"
          purpose:     "{{ pvc_purpose | default('application-data') }}"
      spec:
        accessModes:
          - "{{ pvc_access_mode | default('ReadWriteOnce') }}"
        storageClassName: "{{ storage_class | default('gp3-ssd') }}"
        resources:
          requests:
            storage: "{{ pvc_size | default('10Gi') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: pvc_result

# Wait for PVC to bind (dynamic provisioning may take up to 30s)
- name: "[PVC] Wait for PVC to reach Bound state"
  kubernetes.core.k8s_info:
    kind: PersistentVolumeClaim
    name: "{{ pvc_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: pvc_status
  until:   pvc_status.resources[0].status.phase == "Bound"
  retries: 12
  delay:   5

- name: "[PVC] Extract bound PV name"
  ansible.builtin.set_fact:
    bound_pv_name:     "{{ pvc_status.resources[0].spec.volumeName }}"
    pvc_capacity:      "{{ pvc_status.resources[0].status.capacity.storage }}"
    pvc_storage_class: "{{ pvc_status.resources[0].spec.storageClassName }}"

- name: "[PVC] Log provisioning details"
  ansible.builtin.debug:
    msg:
      - "PVC: {{ pvc_name }} → {{ pvc_status.resources[0].status.phase }}"
      - "Bound to PV: {{ bound_pv_name }}"
      - "Capacity: {{ pvc_capacity }}"
      - "StorageClass: {{ pvc_storage_class }}"

      - "Ready replicas: {{ sts_status.resources[0].status.readyReplicas | default(0) }}"
      - "PVCs: {{ sts_pvcs.resources | length }} bound"

08 Automated Backup with CronJob

yaml PostgreSQL Backup CronJob 
---
# Daily pg_dump at 02:00 UTC, stored in backup PVC

apiVersion: batch/v1
kind: CronJob
metadata:
  name:      postgres-backup
  namespace: fraud-detection
spec:
  schedule: "0 2 * * *"          # 02:00 UTC daily
  successfulJobsHistoryLimit: 7   # Keep 7 days of successful job records
  failedJobsHistoryLimit:    3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name:  backup
              image: postgres:15
              command:
                - /bin/sh
                - -c
                - |
                    BACKUP_FILE="/backups/frauddb-$(date +%Y%m%d-%H%M%S).sql.gz"
                    echo "Starting backup to $BACKUP_FILE"
                    pg_dump -h postgres-0.postgres.fraud-detection.svc.cluster.local \
                            -U $POSTGRES_USER \
                            -d frauddb \
                            | gzip > $BACKUP_FILE
                    echo "Backup complete: $(ls -lh $BACKUP_FILE)"
                    # Prune backups older than 30 days
                    find /backups -name "*.sql.gz" -mtime +30 -delete
                    echo "Old backups pruned."
              env:
                - name:  POSTGRES_USER
                  value: frauduser
                - name:  PGPASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: postgres-secret
                      key:  password
              volumeMounts:
                - name:      backup-storage
                  mountPath: /backups
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: postgres-backups

09 PVC Expansion — Growing Storage Without Downtime

💡
Online PVC Expansion Requirement

PVC expansion requires: (1) StorageClass has allowVolumeExpansion: true, (2) Underlying storage driver supports online expansion (AWS EBS gp2/gp3, Ceph RBD). If supported, you can expand without pod restart. The filesystem is expanded while pod runs. If not supported, pod must be restarted to trigger filesystem resize.

yaml tasks/expand_pvc.yml — Storage Expansion Task 
---
# Expand PVC when storage usage exceeds threshold


- name: "[EXPAND] Get current PVC spec"
  kubernetes.core.k8s_info:
    kind: PersistentVolumeClaim
    name: "{{ pvc_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: current_pvc

- name: "[EXPAND] Extract current storage size"
  ansible.builtin.set_fact:
    current_size: "{{ current_pvc.resources[0].spec.resources.requests.storage }}"
    new_size:     "{{ pvc_new_size }}"     # Passed as variable e.g. "100Gi"

- name: "[EXPAND] Validate new size is larger"
  ansible.builtin.assert:
    that:
      - new_size != current_size
    fail_msg: "New size {{ new_size }} must be larger than current {{ current_size }}"

- name: "[EXPAND] Patch PVC with new storage request"
  kubernetes.core.k8s:
    state: patched
    kind: PersistentVolumeClaim
    name: "{{ pvc_name }}"
    namespace: "{{ app_namespace }}"
    definition:
      spec:
        resources:
          requests:
            storage: "{{ new_size }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"

- name: "[EXPAND] Wait for resize to complete"
  kubernetes.core.k8s_info:
    kind: PersistentVolumeClaim
    name: "{{ pvc_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: pvc_after_expand
  until: pvc_after_expand.resources[0].status.capacity.storage == new_size
  retries: 20
  delay:   15

- name: "[EXPAND] Log expansion result"
  ansible.builtin.debug:
    msg: "PVC {{ pvc_name }} expanded: {{ current_size }} → {{ new_size }}"

11 Interview Questions

Why can't you use a Deployment with multiple replicas for a database?
Two reasons. First: RWO (ReadWriteOnce) PVCs can only be mounted on one node. If you have 3 replicas on different nodes, only the node with the PV attached succeeds. Other replicas fail to start. Second: databases are not stateless. Two Postgres instances writing to the same disk simultaneously would corrupt data. Proper DB HA uses StatefulSets with 1 primary (RWO write) and replicas via streaming replication to their own PVCs. The StatefulSet gives each replica its own PVC and stable identity.
Explain the difference between static and dynamic PV provisioning.
Static provisioning: admin manually creates PersistentVolume objects describing existing storage (NFS export, SAN LUN). PVC then binds to a matching static PV. Manual, doesn't scale well. Dynamic provisioning: StorageClass with a provisioner plugin. When PVC is created, the provisioner automatically provisions the underlying storage (creates AWS EBS volume, Ceph RBD image) and creates the PV, then binds them. No admin action needed per PVC. Scales automatically. Dynamic provisioning is the standard for cloud and modern on-premises clusters.
What is a headless Service and why does a StatefulSet need one?
A headless Service has clusterIP: None. Instead of a single virtual IP, DNS queries return the individual pod IP addresses directly. Combined with a StatefulSet, this gives each pod a stable, predictable DNS name: postgres-0.postgres.namespace.svc.cluster.local. This is critical for databases: the application needs to connect to the primary (postgres-0) specifically, not any random replica. Regular Services hide pod identity behind a load-balanced VIP — that's correct for stateless apps but wrong for databases where the primary matters.
What is volumeClaimTemplates and how does it differ from a regular volume?
A regular volume in a Pod spec references a single PVC by name — all pods share that PVC. volumeClaimTemplates in a StatefulSet is a PVC template: when each pod is created, Kubernetes creates a unique PVC from the template. postgres-0 gets postgres-data-postgres-0, postgres-1 gets postgres-data-postgres-1. Each pod has isolated storage. This is essential for databases: each replica needs its own independent data directory. When the StatefulSet is deleted, these PVCs are NOT automatically deleted (data preservation). You must manually delete them.
Describe how you would automate storage capacity monitoring and expansion.
Query pod metrics with oc top or Prometheus for disk usage. Set threshold (e.g. 80% used). When exceeded, ansible task: (1) verify StorageClass has allowVolumeExpansion:true, (2) patch PVC spec.resources.requests.storage to new size, (3) poll until status.capacity.storage matches new size, (4) verify application still working. For filesystems that require pod restart: trigger rolling restart of StatefulSet. Alert Slack/email on expansion. Log to audit file. Schedule check as daily RHAAP Job Template.

Write a task that lists all PVCs in a namespace, checks their current capacity against their usage (using oc exec and df -h), and generates a report of PVCs that are above 75% utilisation. Include the PVC name, current size, used, available, and percentage.

yamlPVC utilisation check
- name: "Get all pods with PVC mounts"
  kubernetes.core.k8s_info:

    label: "{{ item.metadata.name }}"

    - item.stdout_lines | length > 1

    msg: "⚠️ High storage utilisation: {{ high_usage_pvcs }}"
  when: high_usage_pvcs | default([]) | length > 0

Write a task that takes a VolumeSnapshot of a PVC before a schema migration. If the migration fails, restore the PVC from the snapshot. Use block/rescue/always.

▶ Show Answer
yamlSnapshot before migration
- name: "Safe Schema Migration with Snapshot"
  block:

            resources:
              requests:
                storage: 50Gi
        host: "{{ ocp_api_url }}"
