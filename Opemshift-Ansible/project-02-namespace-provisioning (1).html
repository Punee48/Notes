02 k8s vs k8s_info — The Critical Difference

k8s_info (Project 01) — Read-Only

kubernetes.core.k8s_info queries the OpenShift API and returns information. It never changes anything. Completely safe to run 100 times.

k8s_info Behavior
k8s_info module
↓
Query OpenShift API: "Give me all nodes"
↓
API returns: "Here are 5 nodes"
↓
Result stored in variable
↓
Status: ok (no changes, no state modified)

k8s (Project 02) — Read + Write + Compare + Change

kubernetes.core.k8s is the workhorse. It applies Kubernetes YAML manifests to the cluster. But here is the genius: it is idempotent. It compares desired state with actual state and only makes changes if different.

kubernetes.core.k8s Module Workflow — Desired State Engine
You provide YAML manifest ← Desired state
↓
k8s module queries API: "Does this resource exist?"
↓ ↓
EXISTS DOES NOT EXIST
↓ ↓
Compare CREATE ← Easy path
↓ ↓
Same? CREATED
↓ ↓
YES NO
↓ ↓
OK PATCH
↓ ↓
(no change) (changed!)
✨
Why This Matters for Production

This is the essence of Infrastructure as Code (IaC). You describe what you want (YAML), Ansible figures out how to achieve it (create or patch), and guarantees idempotency. You can run it in automated CI/CD pipelines without fear. You can schedule it to run every day without duplicate resources piling up.

03 Idempotency Deep Dive — The Foundation of Production Automation

This is not just about preventing duplicate resources. Idempotency is how we make automation safe and trustworthy.

Three Runs: What Happens in Each

Run 1: Fresh Cluster (Namespace Does Not Exist)
k8s: state=present, kind=Namespace, name=app-dev
↓
Module checks: Does namespace app-dev exist?
↓
NO → Create namespace
↓
Result: changed ✓
Run 2: Same Manifest, Unchanged Cluster
k8s: state=present, kind=Namespace, name=app-dev
↓
Module checks: Does namespace app-dev exist?
↓
YES → Compare manifest with actual resource
↓
Manifest matches actual → No changes needed
↓
Result: ok ✓ (no change)
Run 3: After Manual Change (Someone edited namespace labels)
k8s: state=present, kind=Namespace, name=app-dev
↓
Module checks: Does namespace app-dev exist?
↓
YES → Compare manifest with actual resource
↓
Labels differ! Actual has extra label: "environment=staging"
↓
PATCH: Remove "environment=staging", apply desired labels
↓
Result: changed ✓ (drift corrected)
⚠️
Idempotency is Not Automatic

k8s provides idempotent behavior FOR KUBERNETES RESOURCE CHANGES. But Ansible playbooks can contain non-idempotent tasks (shell commands, API calls via curl, external scripts). It is your job as the automation engineer to ensure the entire playbook is idempotent — usually by using changed_when to control when Ansible reports a change, and testing the playbook by running it twice.

04 Kubernetes/OpenShift YAML Manifests

The k8s module takes Kubernetes YAML manifests as input. You can provide them inline (in the playbook) or as separate files. Let us understand the structure.

A Complete Namespace Manifest

yaml Example — Complete Namespace Manifest 
---
# Kubernetes Manifest — Namespace Object
# Every Kubernetes object has this structure

apiVersion: v1             # API version for Namespace. v1 = core API
kind: Namespace         # Resource type. "Namespace" tells Kubernetes this is a namespace
metadata:               # Metadata about this resource
  name: app-dev           # Name of the namespace. Required. Must be DNS-compliant (lowercase, hyphens OK)
  labels:               # Labels: key=value pairs for organization and selection
    tier: development    # Custom label: tier
    team: payments       # Custom label: team
    cost-center: "ACC123"      # Custom label: cost-center (quoted because it contains a dash)
    created-by: ansible   # Track that Ansible created this
  annotations:           # Annotations: longer-form metadata, often non-query data
    description: "DEV environment for Payments microservice"
    provisioned-by: "Ansible Automation Platform"
    provisioned-timestamp: "{{ ansible_date_time.iso8601 }}"

# OPTIONAL: spec field — most Namespaces don't have a spec
# (some resource types require specs; Namespace is minimal)
Breaking Down Namespace YAML
apiVersion: v1The Kubernetes API version for this resource. "v1" is the core/stable API. Namespace always uses v1. If this is wrong, kubectl/oc rejects the manifest.
kind: NamespaceThe resource type. Tells OpenShift: "This YAML describes a Namespace resource." Other kinds: Deployment, Pod, Service, Ingress, etc.
metadata.nameThe actual name of the namespace. This is how you reference it: oc get pods -n app-dev. Must be DNS-compliant (lowercase, numbers, hyphens).
metadata.labelsKey-value pairs used for selection and organization. You can query: "Get all namespaces with tier=development". Labels are searchable and filterable.
metadata.annotationsKey-value pairs for metadata that is NOT searchable/filterable. Often used for documentation, audit info, automation notes. No size limit like labels have.

ResourceQuota Manifest

A ResourceQuota limits total resource consumption in a namespace. Without it, one rogue deployment can consume all cluster CPU and memory.

yaml Example — ResourceQuota 
---
# ResourceQuota — Enforce namespace resource limits

apiVersion: v1
kind: ResourceQuota
metadata:
  name: app-dev-quota    # Name of this quota
  namespace: app-dev   # Which namespace this quota applies to
spec:
  hard:                # Hard limits — cannot exceed these
    requests.cpu: "4"        # Total CPU requested by all pods cannot exceed 4 cores
    requests.memory: "8Gi"  # Total memory requested cannot exceed 8GB
    limits.cpu: "8"          # Total CPU limits cannot exceed 8 cores
    limits.memory: "16Gi"    # Total memory limits cannot exceed 16GB
    pods: "100"            # Maximum 100 pods in this namespace

LimitRange Manifest

A LimitRange sets defaults and boundaries for individual pods/containers. ResourceQuota is namespace-total; LimitRange is per-pod.

yaml Example — LimitRange 
---
# LimitRange — Default and max limits for pods/containers

apiVersion: v1
kind: LimitRange
metadata:
  name: app-dev-limits
  namespace: app-dev
spec:
  limits:
    - type: Container          # Limits for individual containers
      default:                # If a pod/container doesn't specify limits, use these
        cpu: "500m"        # Default: 0.5 CPU
        memory: "512Mi"     # Default: 512MB
      defaultRequest:       # If a pod/container doesn't request resources, use these
        cpu: "250m"
        memory: "256Mi"
      max:                   # Maximum a container can use
        cpu: "4"
        memory: "4Gi"
      min:                   # Minimum a container can use
        cpu: "100m"
        memory: "128Mi"

The Role Structure Explained

An Ansible Role is a reusable, organized way to bundle tasks, variables, and templates. Instead of writing everything in one 500-line playbook, you organize it logically.

⚙️
defaults/main.yml
Default variable values. These are the "suggested" parameters. Can be overridden by playbooks or inventories.
✅
tasks/main.yml
The work. Tasks that execute when the role is called. This is where our k8s module calls happen.
🔔
handlers/main.yml
Triggered tasks — run only when a task notifies them. Example: restart a service after config change.
📄
templates/
Jinja2 templates. In our case: Namespace, ResourceQuota, LimitRange YAML manifests as .j2 files.
📋
vars/main.yml
Role-specific variables. Defaults can go in defaults/; variables set by the role can go in vars/.

08 The Role Tasks — Creating Namespace, Quota, Limits

yaml roles/openshift_namespace_provision/tasks/main.yml 
---
# Task: Create/Update OpenShift Namespace
# This is where kubernetes.core.k8s module does the work


- name: "Validate namespace name parameter"
  ansible.builtin.assert:
    that:
      - namespace_name is defined
      - namespace_name != 'default'
      - namespace_name != ''
    fail_msg: "ERROR: namespace_name must be provided and not 'default'. Passed: {{ namespace_name | default('UNDEFINED') }}"

# TASK 1 — Create or Update the Namespace
- name: "Create/update namespace with labels and annotations"
  kubernetes.core.k8s:
    state: present                    # Create if missing, update if different
    definition: "{{ lookup('template', 'namespace.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: namespace_creation_result
  tags: [namespace]

- name: "Debug: Namespace creation result"
  ansible.builtin.debug:
    msg: "Namespace: {{ namespace_creation_result.changed }} (changed=true means new, changed=false means updated/no-change)"
  tags: [namespace]

# TASK 2 — Apply ResourceQuota
- name: "Create/update ResourceQuota"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'quota.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: quota_creation_result
  tags: [quota]

# TASK 3 — Apply LimitRange
- name: "Create/update LimitRange"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'limits.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: limits_creation_result
  tags: [limits]

# TASK 4 — Verify Namespace Created Successfully
- name: "[VERIFY] Query created namespace"
  kubernetes.core.k8s_info:
    api_version: v1
    kind: Namespace
    name: "{{ namespace_name }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: namespace_verify_result
  tags: [verify]

# TASK 5 — Assert Namespace Exists and Has Correct Labels
- name: "[ASSERT] Namespace exists and has expected labels"
  ansible.builtin.assert:
    that:
      - namespace_verify_result.resources | length == 1   # Exactly one namespace found
      - namespace_verify_result.resources[0].metadata.labels.tier == namespace_tier
      - namespace_verify_result.resources[0].metadata.labels.team == namespace_team
    fail_msg: "Namespace creation/update failed or labels incorrect"
    success_msg: "Namespace {{ namespace_name }} verified with correct labels"
  tags: [verify]

# TASK 6 — Verify ResourceQuota
- name: "[VERIFY] Query ResourceQuota"
  kubernetes.core.k8s_info:
    api_version: v1
    kind: ResourceQuota
    namespace: "{{ namespace_name }}"
    name: "{{ namespace_name }}-quota"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: quota_verify_result
  tags: [verify]

- name: "[ASSERT] ResourceQuota exists"
  ansible.builtin.assert:
    that:
      - quota_verify_result.resources | length > 0
    fail_msg: "ResourceQuota was not created in namespace {{ namespace_name }}"
  tags: [verify]

# TASK 7 — Verify LimitRange
- name: "[VERIFY] Query LimitRange"
  kubernetes.core.k8s_info:
    api_version: v1
    kind: LimitRange
    namespace: "{{ namespace_name }}"
    name: "{{ namespace_name }}-limits"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: limits_verify_result
  tags: [verify]

- name: "[ASSERT] LimitRange exists"
  ansible.builtin.assert:
    that:
      - limits_verify_result.resources | length > 0
    fail_msg: "LimitRange was not created in namespace {{ namespace_name }}"
  tags: [verify]

# TASK 8 — Summary
- name: "[SUMMARY] Namespace provisioning complete"
  ansible.builtin.debug:
    msg:
      - "Namespace {{ namespace_name }} provisioning complete"
      - "  Namespace: {{ 'CREATED' if namespace_creation_result.changed else 'EXISTS' }}"
      - "  ResourceQuota: {{ 'CREATED' if quota_creation_result.changed else 'EXISTS' }}"
      - "  LimitRange: {{ 'CREATED' if limits_creation_result.changed else 'EXISTS' }}"
      - "All resources verified and healthy."
  tags: [always]

09 Code Explanation — Every Important Concept

Understanding the k8s Module Parameters

kubernetes.core.k8s Module Parameters
state: presentCreate or update the resource if it doesn't exist. Essential for idempotency — the module will create ONLY if missing, and patch only if different.
definition:The Kubernetes manifest (YAML) defining the resource. Can be a dict, string, or template lookup result.
lookup('template', 'namespace.yml.j2')Ansible function that renders the Jinja2 template file, interpolating all variables. Returns the rendered YAML as a string, which k8s then parses and applies.
host / api_key / validate_certsAuthentication details. Same as in Project 01. Tells k8s which cluster to connect to and with what token.
register: namespace_creation_resultCaptures the result object containing: .changed (bool) — did the module make changes; .failed (bool) — did it fail; .duration (seconds) — how long it took.

Understanding Idempotency in Practice

✅
What the k8s Module Actually Does

On Run 1 (namespace doesn't exist): k8s calls the OpenShift API: "Create this namespace." API returns "created". k8s records changed=true.

On Run 2 (same playbook, same variables): k8s calls the OpenShift API: "Get namespace app-dev". API returns the namespace. k8s compares: manifest says labels={tier: dev}, actual has labels={tier: dev}. Match! No patch needed. Records changed=false, status=ok.

On Run 3 (someone manually added a label): k8s gets the namespace, sees labels={tier: dev, extra: manual}. Manifest says labels should be {tier: dev}. Mismatch! k8s patches: remove "extra: manual". Records changed=true.

Understanding Template Lookup

How lookup('template', ...) Works
lookup()Ansible function that calls a plugin. Many types: 'template', 'file', 'vars', 'env'. In this case, 'template' means render a Jinja2 template.
'namespace.yml.j2'Relative path. Ansible looks in: role's templates/ folder. So it becomes: roles/openshift_namespace_provision/templates/namespace.yml.j2
Return valueA string containing the rendered YAML. All {{ }} expressions are replaced with variable values. This string is then parsed as YAML and applied to OpenShift.

10 Calling the Role — The Playbook

A role is useless without a playbook that calls it. Let us create the orchestration playbook.

yaml playbooks/provision_namespace.yml 
---
###############################################################################
# PLAYBOOK: Provision OpenShift Namespace
# TICKET:   INFRA-1002
# PURPOSE:  Create/update namespace with labels, resource quotas, limits
# CALLS:    roles/openshift_namespace_provision
###############################################################################

- name: "Provision OpenShift Namespace"
  hosts: localhost           # Run on Ansible control node / Execution Environment
  gather_facts: false           # No SSH needed
  connection: local          # Local execution (API calls)

  vars:
    # OpenShift API authentication
    ocp_token: "{{ lookup('env', 'K8S_AUTH_API_KEY') | default(vault_ocp_api_token, true) }}"

  tasks:

    - name: "Input validation: namespace name required"
      ansible.builtin.assert:
        that:
          - provision_namespace_name is defined
          - provision_namespace_name != ''
        fail_msg: "ERROR: provision_namespace_name variable must be supplied. Use: -e provision_namespace_name=app-dev"
      tags: [always]

    # CALL THE ROLE — Pass parameters as role arguments
    - name: "Call: Provision namespace role"
      ansible.builtin.include_role:
        name: openshift_namespace_provision
      vars:
        # Override role defaults with user input
        namespace_name: "{{ provision_namespace_name }}"
        namespace_team: "{{ provision_team | default('engineering') }}"
        namespace_tier: "{{ provision_tier | default(environment_code) }}"
        namespace_cost_center: "{{ provision_cost_center | default('ACC001') }}"
        namespace_description: "{{ provision_description | default('Application namespace') }}"

        # Vary resource limits by environment
        quota_cpu_requests: >-
          {{
            '2' if environment_code == 'dev'
            else '8' if environment_code in ['qa', 'uat']
            else '16'
          }}
        quota_memory_requests: >-
          {{
            '4Gi' if environment_code == 'dev'
            else '16Gi' if environment_code in ['qa', 'uat']
            else '32Gi'
          }}
      tags: [provision]

12 Introduction to Roles — Why They Matter for Enterprise Automation

Roles transform Ansible from a script tool to an enterprise framework. Here is why they are critical:

♻️
Reusability
Write once, use 100 times. "Provision a namespace" is a reusable component. Call it for DEV, QA, PROD with different parameters.
📚
Organization
Code is structured logically: tasks/ for work, defaults/ for parameters, templates/ for manifests. No 1000-line playbooks.

14 Interview Questions

What is the difference between kubernetes.core.k8s and kubernetes.core.k8s_info, and when would you use each?
k8s_info is read-only: it queries the API and returns information without modifying resources. Use it for validation, checking status, asserting prerequisites. k8s is the write module: it applies manifests using the desired-state model. It is idempotent — creates if missing, patches if different. Use k8s for deployments, creating/updating resources. Together: k8s_info validates pre-conditions, k8s makes the changes, k8s_info post-validates the result.
Explain idempotency in the context of the kubernetes.core.k8s module.
Idempotency means running the same automation 1 time or 100 times produces identical results. The k8s module achieves this by: (1) querying if the resource exists, (2) comparing desired manifest with actual resource, (3) creating only if missing, patching only if different, skipping if matching. Run the playbook 10 times: run 1 shows changed=3 (creates namespace, quota, limits); runs 2-10 show changed=0 (everything already correct). This is safe for scheduled automation and CI/CD pipelines.
What is an Ansible Role and why is it better than a monolithic playbook?
A Role is a structured directory containing tasks, defaults, templates, handlers, vars organized logically. It is reusable: "provision a namespace" is one role, called many times with different parameters. Advantages: (1) Reusability — no copy-paste, (2) Encapsulation — hides complexity, caller doesn't care about template lookup, (3) Organization — no 500-line files, (4) Testing — test in isolation, (5) Collaboration — one author, many users, changes propagate via Git, (6) Documentation — structure is self-documenting.
How do you pass parameters to an Ansible Role?
Roles have defaults/main.yml defining default values. Caller can override via: (1) -e flag: ansible-playbook ... -e namespace_name=app-dev, (2) vars in the playbook that calls the role, (3) inventory variables. Precedence: command-line (-e) > playbook vars > inventory > role defaults. Best practice: define all parameters in role defaults with sensible defaults, document them in README.
What is a Kubernetes manifest and what does it define?
A manifest is a YAML file describing a Kubernetes resource (desired state). Structure: apiVersion (API version), kind (resource type), metadata (name, labels, annotations), spec (resource-specific configuration). Example: a Namespace manifest defines the namespace name, labels (tier, team, cost-center), annotations (documentation, audit info). Manifests are declarative: you describe WHAT you want, Kubernetes makes it happen. Templating (Jinja2) allows dynamic values — replace {{ namespace_name }} with actual values at runtime.

Challenge 3 of 3

Write a test playbook that provisions a namespace, then verifies idempotency by running the provision role twice and asserting that the second run shows changed=0. Use the Ansible debug output to prove idempotency.

▶ Show Answer
yamlplaybooks/test_idempotency.yml
---
- name: "Test Idempotency of Namespace Provisioning"
  hosts: localhost
  gather_facts: false
  connection: local

  tasks:
    - name: "RUN 1: Provision test namespace"
      ansible.builtin.include_role:
        name: openshift_namespace_provision
      vars:
        namespace_name: "idempotent-test"
      register: run1_result

    - name: "RUN 1: Record result"
      ansible.builtin.set_fact:
        run1_changed: "{{ run1_result.changed }}"

    - name: "RUN 2: Provision same namespace again (idempotency check)"
      ansible.builtin.include_role:
        name: openshift_namespace_provision
      vars:
        namespace_name: "idempotent-test"
      register: run2_result

    - name: "RUN 2: Record result"
      ansible.builtin.set_fact:
        run2_changed: "{{ run2_result.changed }}"

    - name: "ASSERT: Run 1 should have changes"
      ansible.builtin.assert:
        that:
          - run1_changed | bool
        fail_msg: "Run 1 should have created resources (changed=true)"

    - name: "ASSERT: Run 2 should have NO changes (idempotency)"
      ansible.builtin.assert:
        that:
          - not (run2_changed | bool)
        fail_msg: "Run 2 should show no changes (changed=false). Idempotency FAILED."
        success_msg: "IDEMPOTENCY VERIFIED: Second run showed no changes"
