02 The Three Pillars of Observability

📜
Logs
What happened. Pod stdout/stderr. Application error messages. Container crash output. Query with: oc logs. Ansible: k8s_log module.
📊
Metrics
How much. CPU/memory usage over time. Request rate, error rate, latency. Query with: oc top, Prometheus. Ansible: command: oc top.
🔍
Traces
Where it went. Request path through microservices. Distributed tracing (Jaeger, Tempo). Shows which service caused latency.
📅
Events (Kubernetes)
What Kubernetes noticed. Pod OOMKilled, FailedScheduling, BackOff. Short-lived (1 hour default). Critical for diagnosing issues.
💓
Health Probes
Is it alive and ready? Liveness (restart), Readiness (traffic), Startup (boot time). Pod conditions reflect probe status.
📈
Conditions
Resource state flags. PodScheduled, Initialized, ContainersReady, Ready. Node: MemoryPressure, DiskPressure, Ready.

03 Complete Probe Architecture — All Three Probes

Project 06 introduced liveness and readiness probes. Project 07 completes the picture with the startup probe — and explains exactly how all three interact to protect your application.

Three Probe Lifecycle
Startup Probe Runs FIRST, after container starts. Disables liveness/readiness until it passes. Use for slow-starting apps (JVM, model loading). Only runs once at startup.
Readiness Probe Runs after startup probe passes. Continuous. Controls Service traffic. Fails → pod removed from load balancer. Passes → pod gets traffic. Keeps checking forever.
Liveness Probe Runs after startup probe passes. Continuous. Controls pod restart. Fails → Kubernetes kills and restarts pod. Keeps checking forever.
Probe Execution Order

Container Starts
↓
[STARTUP PROBE runs]
→ fails: wait and retry (failureThreshold × periodSeconds)
→ exceeds threshold: pod killed (CrashLoopBackOff)
↓ passes
[READINESS PROBE + LIVENESS PROBE run in parallel, continuously]
readiness fails → removed from Service (no traffic) → checks again
liveness fails 3× → pod RESTARTED by kubelet
↓ both pass
Pod serving traffic normally

04 Startup Probe — Protecting Slow-Starting Applications

yaml All Three Probes — Complete Example 
---
# Complete probe configuration: startup + readiness + liveness
# Scenario: JVM-based payment service takes up to 90s to start

containers:
  - name: payment-api
    image: payment-api:v2

    # STARTUP PROBE: Allow up to 90s for boot (30 retries × 3s = 90s)
    # Liveness/readiness DISABLED until this passes
    startupProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      failureThreshold: 30         # Retry 30 times
      periodSeconds: 3            # Every 3 seconds = 90s max startup
      # If 30 retries fail → pod killed → CrashLoopBackOff

    # READINESS PROBE: Traffic control — runs continuously after startup
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: 8080
      initialDelaySeconds: 0     # Start immediately after startup probe passes
      periodSeconds: 5            # Check every 5 seconds
      failureThreshold: 3         # 3 failures = remove from Service
      successThreshold: 1         # 1 success = add back to Service

    # LIVENESS PROBE: Restart control — runs continuously after startup
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
      initialDelaySeconds: 0
      periodSeconds: 10           # Check every 10s (less frequent)
      failureThreshold: 3         # 3 failures = RESTART pod
      timeoutSeconds: 5          # Fail if no response in 5s

05 Kubernetes Events — The Early Warning System

Kubernetes Events are the most underutilised observability tool. They capture everything the control plane does: pod scheduling, OOMKilling, image pulls, node conditions. Events expire after ~1 hour by default, making scheduled collection critical.

Querying Events with Ansible

yaml Query Warning Events Across All Namespaces 
---
# Collect Warning events across all namespaces

- name: "[EVENTS] Query all Warning events"
  kubernetes.core.k8s_info:
    api_version: v1
    kind: Event
    field_selectors:
      - type=Warning               # Only Warning events (not Normal)
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_warning_events

# Filter to last 1 hour only
- name: "[EVENTS] Filter recent events (last hour)"
  ansible.builtin.set_fact:
    recent_events: "{{ all_warning_events.resources | selectattr('lastTimestamp', 'defined')
      | selectattr('lastTimestamp', 'gt', (ansible_date_time.iso8601 | to_datetime('%Y-%m-%dT%H:%M:%SZ') - timedelta(hours=1)).strftime('%Y-%m-%dT%H:%M:%SZ'))
      | list }}"

# Categorise events by reason
- name: "[EVENTS] Categorise by reason"
  ansible.builtin.set_fact:
    oom_events:     "{{ recent_events | selectattr('reason', 'eq', 'OOMKilling') | list }}"
    backoff_events: "{{ recent_events | selectattr('reason', 'in', ['BackOff','CrashLoopBackOff']) | list }}"
    sched_events:   "{{ recent_events | selectattr('reason', 'eq', 'FailedScheduling') | list }}"
    node_events:    "{{ recent_events | selectattr('reason', 'eq', 'NodeNotReady') | list }}"

- name: "[EVENTS] Log event summary"
  ansible.builtin.debug:
    msg:
      - "Total Warning Events (last hour): {{ recent_events | length }}"
      - "OOMKilling: {{ oom_events | length }}"
      - "CrashLoop/BackOff: {{ backoff_events | length }}"
      - "FailedScheduling: {{ sched_events | length }}"
      - "NodeNotReady: {{ node_events | length }}"

06 Resource Monitoring — Node Capacity & Pod Usage

Node Capacity vs Allocatable

Node Resource Concepts
capacity Total physical resources on node. CPU cores, RAM bytes. What hardware provides.
allocatable Capacity minus system overhead (kubelet, OS, DaemonSets). What pods can actually request. Always use this for planning.
requests (sum) Sum of all pod requests on node. Scheduler uses this to decide if pod fits. requests ≤ allocatable = scheduled.
limits (sum) Sum of all pod limits. Can exceed allocatable (overcommit). If all pods hit limits simultaneously → memory pressure.
Pressure conditions MemoryPressure: node running low on memory. DiskPressure: low disk. PIDPressure: too many processes. All cause scheduling to stop.
yaml Node Health Check — Capacity & Pressure 
---
# Query nodes and check health conditions

- name: "[NODES] Query all nodes"
  kubernetes.core.k8s_info:
    kind: Node
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_nodes

# Parse each node's conditions and capacity
- name: "[NODES] Build node health summary"
  ansible.builtin.set_fact:
    node_health: "{{ node_health | default([]) + [node_entry] }}"
  vars:
    node_conditions: "{{ item.status.conditions | default([]) }}"
    ready_condition: "{{ node_conditions | selectattr('type','eq','Ready') | first | default({}) }}"
    mem_pressure: "{{ (node_conditions | selectattr('type','eq','MemoryPressure') | first | default({'status':'False'})).status == 'True' }}"
    disk_pressure: "{{ (node_conditions | selectattr('type','eq','DiskPressure') | first | default({'status':'False'})).status == 'True' }}"
    node_entry:
      name: "{{ item.metadata.name }}"
      ready: "{{ ready_condition.status | default('Unknown') }}"
      memory_pressure: "{{ mem_pressure }}"
      disk_pressure: "{{ disk_pressure }}"
      allocatable_cpu: "{{ item.status.allocatable.cpu | default('0') }}"
      allocatable_memory: "{{ item.status.allocatable.memory | default('0') }}"
  loop: "{{ all_nodes.resources }}"
  loop_control:
    label: "{{ item.metadata.name }}"

# Identify unhealthy nodes
- name: "[NODES] Flag unhealthy nodes"
  ansible.builtin.set_fact:
    unhealthy_nodes: "{{ node_health | selectattr('ready','ne','True') | list
      + node_health | selectattr('memory_pressure','eq',true) | list
      + node_health | selectattr('disk_pressure','eq',true) | list }}"

07 Pod Conditions — Deep Health Introspection

yaml Multi-Namespace Pod Scan with Health Classification 
---
# Comprehensive pod health scan across namespaces

- name: "[PODS] Query all pods across all namespaces"
  kubernetes.core.k8s_info:
    kind: Pod
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_pods

# Classify pods by health status
- name: "[PODS] Classify pod health"
  ansible.builtin.set_fact:
    pods_running:  "{{ all_pods.resources | selectattr('status.phase','eq','Running') | list }}"
    pods_pending:  "{{ all_pods.resources | selectattr('status.phase','eq','Pending') | list }}"
    pods_failed:   "{{ all_pods.resources | selectattr('status.phase','eq','Failed') | list }}"
    pods_oom:      "{{ all_pods.resources | selectattr('status.containerStatuses','defined')
      | selectattr('status.containerStatuses[0].lastState.terminated.reason','defined')
      | selectattr('status.containerStatuses[0].lastState.terminated.reason','eq','OOMKilled') | list }}"
    pods_crashloop: "{{ all_pods.resources | selectattr('status.containerStatuses','defined')
      | selectattr('status.containerStatuses[0].state.waiting.reason','defined')
      | selectattr('status.containerStatuses[0].state.waiting.reason','eq','CrashLoopBackOff') | list }}"
    pods_high_restarts: "{{ all_pods.resources | selectattr('status.containerStatuses','defined')
      | selectattr('status.containerStatuses[0].restartCount','gt', restart_threshold | default(10)) | list }}"

# Calculate cluster health score (0-100)
- name: "[SCORE] Calculate cluster health score"
  ansible.builtin.set_fact:
    health_score: "{{ [100
      - (pods_failed | length * 5)
      - (pods_crashloop | length * 10)
      - (pods_oom | length * 8)
      - (unhealthy_nodes | length * 20)
      - (oom_events | length * 3)
      - (backoff_events | length * 2),
      0] | max }}"

- name: "[SCORE] Set health status label"
  ansible.builtin.set_fact:
    health_status: "{{ 'HEALTHY' if health_score | int >= 80
      else ('DEGRADED' if health_score | int >= 60
      else 'CRITICAL') }}"

Main Playbook — Block/Rescue/Always Pattern

yaml playbooks/cluster_health_framework.yml 
---
# Cluster Health Framework — Production Playbook
# Runs daily at 07:00 via RHAAP scheduler

- name: "ABC Bank OpenShift Health Framework"
  hosts: localhost
  gather_facts: true             # Need ansible_date_time for timestamps
  vars_files:
    - "vars/secrets.yml"            # Ansible Vault: API token, SMTP creds, Slack URL
    - "vars/thresholds.yml"         # Health score thresholds, restart limits
  tasks:

    - name: "Health Framework — block/rescue/always"
      block:

        - name: "[INIT] Log framework start"
          ansible.builtin.debug:
            msg: "Health Framework started: {{ ansible_date_time.iso8601 }}"

        - name: "[PODS] Pod health scan"
          ansible.builtin.include_role:
            name: openshift_health_check
            tasks_from: check_pods.yml

        - name: "[NODES] Node condition scan"
          ansible.builtin.include_role:
            name: openshift_health_check
            tasks_from: check_nodes.yml

        - name: "[EVENTS] Warning event scan"
          ansible.builtin.include_role:
            name: openshift_health_check
            tasks_from: check_events.yml

        - name: "[SCORE] Calculate health score"
          ansible.builtin.include_role:
            name: openshift_health_check
            tasks_from: calculate_score.yml

        - name: "[REPORT] Generate HTML dashboard"
          ansible.builtin.include_role:
            name: openshift_health_check
            tasks_from: generate_report.yml

        - name: "[ALERT] Send email and Slack alerts"
          ansible.builtin.include_role:
            name: openshift_health_check
            tasks_from: send_alerts.yml

      rescue:
        - name: "[RESCUE] Health framework failed — send critical alert"
          community.general.slack:
            token: "{{ vault_slack_token }}"
            channel: "#openshift-alerts"
            color: danger
            msg: "⚠️ HEALTH FRAMEWORK FAILED on {{ inventory_hostname }} at {{ ansible_date_time.iso8601 }}. Manual check required."

      always:
        - name: "[ALWAYS] Log framework completion"
          ansible.builtin.debug:
            msg: "Health Framework completed: {{ ansible_date_time.iso8601 }}"

11 Troubleshooting Guide

SymptomError/ObservationRoot CauseFix
Pods stuck in Pending Events: FailedScheduling Insufficient CPU/memory on nodes, or node selector mismatch Check oc describe pod. Free node resources or adjust requests.
OOMKilled pods Events: OOMKilling, lastState.terminated.reason=OOMKilled Pod memory usage exceeds memory limit Increase memory limit. Investigate app memory leak. Profile with JVM heap dumps.
CrashLoopBackOff Restart count keeps growing, pod state=Waiting App crashes on start. Config error, missing env var, DB unreachable. Check oc logs pod --previous for last crash output.
Events API empty No events returned Events older than 1 hour expired, or querying wrong namespace Query without namespace filter. Check event TTL: default 1h. Deploy event archiver.
Health score always 100 Score not reflecting real issues Pod label selectors not matching correctly, filtering wrong pods Debug: print all_pods.resources | length to verify pods returned.

12 Interview Questions

Explain the three types of Kubernetes probes and when you'd use each.
Startup probe: fires first, protects slow-starting apps (JVM, ML models). Disables liveness/readiness until it passes. If it keeps failing (failureThreshold × period), pod killed. Readiness probe: continuous after startup, controls Service traffic. Fail → pod removed from load balancer. Recover → pod added back. Use for: "I'm temporarily busy". Liveness probe: continuous, controls restart. Fail 3× → pod killed and restarted. Use for: "I'm broken and need a restart".
What are Kubernetes Events? Why are they important for observability?
Events are objects that capture what Kubernetes did or noticed: pod scheduled, image pulled, OOMKilled, BackOff. Two types: Normal (informational) and Warning (problems). They expire after ~1 hour by default. Critical for diagnosing: why pod won't start (FailedScheduling), why pod died (OOMKilling), why deployment is stuck (BackOff). The most common thing missing from monitoring setups: Events are transient so you need to collect them continuously or they disappear.
What is the difference between node capacity and allocatable?
Capacity: total physical resources (CPU cores, RAM) on the node. Allocatable: capacity minus system overhead (kubelet, OS, kube-system DaemonSets). Allocatable is always less than capacity. Pods are scheduled against allocatable, not capacity. Example: 16 CPU node might have 15.5 allocatable. Always use allocatable for capacity planning. Scheduler sums all pod requests on a node and compares against allocatable to decide if a new pod fits.
How would you detect OOMKilled pods programmatically with Ansible?
Query all pods with k8s_info. Filter: status.containerStatuses[0].lastState.terminated.reason == 'OOMKilled'. This field only exists if pod was killed for exceeding memory limit. Also check Events for reason=OOMKilling. Both signals together confirm OOM. Solution: increase memory limit, optimise app memory, or investigate leak. Then alert via Slack and include in HTML report.
Describe your approach to building a health score from 0 to 100.
Start at 100. Deduct weighted penalties: each failed pod -5, each CrashLoop pod -10, each OOMKilled pod -8, each unhealthy node -20, each recent OOM event -3. Floor at 0. Classify: 80-100 = HEALTHY (green), 60-79 = DEGRADED (yellow), 0-59 = CRITICAL (red). Store score in log file for trending. Alert on Slack if below threshold. Adjust weights based on business criticality — unhealthy node costs more than a single failed pod.
