02 ConfigMaps vs Secrets — The Critical Distinction

ConfigMaps (Non-Sensitive)

  • Purpose: Store application configuration
  • Data: Database URLs, log levels, feature flags
  • Encryption: NOT encrypted in etcd
  • Access: Easy to read, visible in YAML
  • Size: Max 1 MB per ConfigMap
  • Use Case: Settings that change, not credentials
  • Example: APP_LOG_LEVEL=INFO

Secrets (Sensitive)

  • Purpose: Store sensitive credentials
  • Data: Passwords, API keys, tokens
  • Encryption: Base64 by default; enable etcd encryption
  • Access: Requires permissions; should be restricted
  • Size: Max 1 MB per Secret
  • Use Case: Anything that authenticates or authorizes
  • Example: DB_PASSWORD, API_KEY, TLS_CERT
🔐
Critical Security Reality

Base64 encoding is NOT encryption. Kubernetes Secrets are base64-encoded, not encrypted. They are vulnerable in etcd unless you enable encryption at rest. Always assume Secrets are readable by anyone with etcd access. Use external secret managers (HashiCorp Vault, AWS Secrets Manager) in production. Never commit unencrypted secrets to Git — always use Ansible Vault.

# Use for: database URLs, log levels, feature flags, etc.
# DO NOT use for: passwords, API keys, tokens

        "rate_limit_rps": 1000,
        "circuit_breaker_threshold": 0.5
      }

ConfigMap Consumption Patterns

Three Ways Pods Consume ConfigMaps
Environment VariablesEach key becomes an env var. Container sees: $DATABASE_HOST, $APP_LOG_LEVEL. Simple, but limited to string values.
Volume Mount (Files)ConfigMap mounted as directory with files. Container reads /etc/config/application.properties. Supports large configs and file formats.
Projected VolumeMix ConfigMap + Secret + Downward API in one volume. Most flexible. Combine config files + injected pod metadata.

04 Secrets Deep Dive — Protecting Sensitive Data

Secret Types

🔑
Opaque (generic)
Default type. Store any binary or text data. Username/password, API keys, database credentials.
🐳

For private image registry auth. Image pull secrets. Stores .dockercfg format.
🔐

TLS certificates and private keys. Ingress TLS termination, mutual TLS.
🎫

Username and password pairs. HTTP Basic Authentication.
🔒
ssh-auth
SSH private key authentication. Git SSH keys.
🧩

Bootstrap tokens for kubelets joining cluster. Cluster initialization.

Secret Manifest — Opaque Type

yaml Kubernetes Secret Manifest (Opaque) 
---
# Secret: Sensitive credentials
# Data is base64-encoded by Kubernetes (NOT encrypted unless etcd encryption enabled)
# Store plaintext secrets in Ansible Vault in version control

apiVersion: v1
kind: Secret
metadata:
  name: payment-api-secrets
  namespace: production
type: Opaque                       # Default type
data:                              # Base64-encoded values
  # These values are base64-encoded during manifest transmission
  # Plaintext stored in Ansible Vault, encrypted in etcd (if enabled)
  database-password: "eFkzQXBzMWQyUA=="     # base64(xYzAps1d2P)
  api-key: "c2stdDNzMDEyMzQ1"      # base64(sk-t3s012345)
  jwt-secret: "anNvbldlYlRva2VuU2VjcmV0"

# stringData field: plaintext at creation time, becomes base64 in etcd
stringData:                         # Kubernetes will base64-encode these
  tls-cert: |
    -----BEGIN CERTIFICATE-----
    MIIDXTCCAkWgAwIBAgIJAJx...
    -----END CERTIFICATE-----
  tls-key: |
    -----BEGIN PRIVATE KEY-----
    MIIEvQIBADANBgkqhkiG9w0...
    -----END PRIVATE KEY-----
⚠️
Base64 is NOT Encryption

Many engineers think Kubernetes Secrets are secure because they're base64-encoded. Base64 is just encoding, easily reversed. echo "eFkzQXBzMWQyUA==" | base64 -d reveals the password instantly. Secrets are only secure if: (1) etcd encryption at rest is enabled, (2) RBAC restricts Secret read access, (3) credentials are stored encrypted in Git (Ansible Vault).

05 Securing Secrets with Ansible Vault

Never commit plaintext secrets to Git. Use Ansible Vault to encrypt secrets, then decrypt at runtime.

Vault Workflow

bash Ansible Vault Command Examples 
# Create a new encrypted file for secrets
ansible-vault create vars/secrets.yml
# You will be prompted for a password (use strong, store securely)
# File is encrypted at rest in Git

# Edit encrypted file
ansible-vault edit vars/secrets.yml
# Prompts for password, opens editor, re-encrypts on save

# View encrypted file (read-only)
ansible-vault view vars/secrets.yml
# Shows decrypted content without editing

# Run playbook with vault password
ansible-playbook playbooks/deploy.yml \
  --vault-password-file ~/.vault-password
# OR use environment variable
ANSIBLE_VAULT_PASSWORD_FILE=~/.vault-password ansible-playbook playbooks/deploy.yml

# In RHAAP, use Credential Store for vault password (don't put in playbooks)

Tasks: Creating ConfigMap and Secret

yaml roles/openshift_app_config/tasks/main.yml 
---
# Create ConfigMap and Secret for application


- name: "[CONFIG] Create application ConfigMap"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'configmap.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: configmap_result
  tags: [config]

- name: "[SECRET] Create application Secret"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'secret.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  no_log: true                        # Hide from logs (contains secrets)
  register: secret_result
  tags: [secrets]

- name: "[VERIFY] ConfigMap created"
  kubernetes.core.k8s_info:
    kind: ConfigMap
    name: "{{ app_config_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: verify_configmap
  tags: [verify]

- name: "[ASSERT] ConfigMap exists"
  ansible.builtin.assert:
    that:
      - verify_configmap.resources | length == 1
    fail_msg: "ConfigMap creation failed"
  tags: [verify]

08 Pattern: ConfigMap and Secret as Pod Volumes

Applications need to READ configuration. Show how Deployment consumes ConfigMap + Secret.

Deployment With Mounted ConfigMap and Secret

yaml Example Deployment Consuming ConfigMap + Secret 
---
# Deployment that uses ConfigMap and Secret

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-api
  namespace: production
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: api
          image: payment-api:latest

          # Environment variables from ConfigMap
          envFrom:
            - configMapRef:
                name: payment-api-config    # All keys become env vars

          # Specific env var from Secret
          env:
            - name: DATABASE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: payment-api-secrets
                  key: database-password

          # Volume mount: ConfigMap as files
          volumeMounts:
            - name: config-volume
              mountPath: /etc/config
            - name: secret-volume
              mountPath: /etc/secrets
              readOnly: true

      # Define volumes referencing ConfigMap and Secret
      volumes:
        - name: config-volume
          configMap:
            name: payment-api-config
            defaultMode: 0644

        - name: secret-volume
          secret:
            secretName: payment-api-secrets
            defaultMode: 0400            # Read-only for security

10 Troubleshooting Guide

SymptomErrorRoot CauseFix
Pod won't start FailedMount: couldn't propagate object cache... ConfigMap or Secret doesn't exist, or wrong namespace Verify: oc get configmap -n . Ensure Deployment references correct names.
Env var not set Pod running but $DATABASE_HOST is empty ConfigMap key name doesn't match Deployment envFrom reference. Check exact key names in ConfigMap: oc get configmap -o yaml. Match in Deployment.
Secret access denied Forbidden: secrets "xxx" is forbidden ServiceAccount doesn't have permission to read Secrets (RBAC issue). Create Role/RoleBinding: apiGroups: [""], resources: ["secrets"], verbs: ["get", "list"]
Vault password wrong ERROR! Decryption failed Vault password file missing, wrong password, or wrong file specified. Verify: cat ~/.vault-password. Ensure permissions 600. Use --vault-password-file flag.
ConfigMap too large request entity too large ConfigMap data exceeds 1 MB limit per Kubernetes spec. Split into multiple ConfigMaps, or store file separately (PVC, object storage).

11 Interview Questions

What is the difference between ConfigMaps and Secrets, and when would you use each?
ConfigMaps store non-sensitive configuration: database URLs, log levels, feature flags. Secrets store sensitive data: passwords, API keys, tokens. ConfigMaps are NOT encrypted; Secrets should be. ConfigMaps are ~1 MB limit; so are Secrets. Both are Kubernetes resources — ConfigMaps for "what does the app do", Secrets for "how does it authenticate". Never put credentials in ConfigMaps; always use Secrets + encryption.
Base64 encoding appears in Kubernetes Secrets. Is that encryption?
No. Base64 is encoding, not encryption. It's reversible in seconds: echo "abc==" | base64 -d. Kubernetes Secrets are base64-encoded only for transport and storage format, not for security. To secure Secrets, enable etcd encryption at rest (--encryption-provider-config). Additionally, use RBAC to restrict Secret access, and store secret data encrypted in Git using Ansible Vault.
How do you handle environment-specific configuration in Ansible?
Use inventory-based variables. Create group_vars/dev.yml, group_vars/prod.yml with different values. When running playbook, specify inventory: ansible-playbook ... -i inventories/prod. Role gets variables from group_vars for that inventory. Same playbook, different environments, no code duplication. Sensitive values go in encrypted vault files (group_vars/prod/vault.yml).
When should you use volume mounts vs environment variables for ConfigMaps?
Environment variables: simple key-value config, small number of settings. Volume mounts: large config files (application.properties, nginx.conf), JSON/YAML configs, settings that don't map to env vars. Volume mount gives you a file path (e.g., /etc/config/app.properties) that application reads via filesystem. Env vars are simpler but limited to string values.
Describe the workflow for storing and using secrets securely.
1. Create Ansible Vault file: ansible-vault create vars/secrets.yml. 2. Add plaintext secrets inside (only you can read). 3. Commit encrypted file to Git (safe — it's encrypted). 4. Run playbook with vault password: ansible-playbook ... --vault-password-file ~/.vault-password. 5. Playbook decrypts secrets at runtime, creates Kubernetes Secret manifest. 6. Secret sent to API server, stored base64-encoded in etcd (or encrypted if etcd encryption enabled). 7. Pod mounts Secret volume or reads env var. Complete chain: encrypted in Git → decrypted at runtime → encrypted in etcd.
