02 What is OpenShift? (Understand Before You Automate)

Before we write a single line of Ansible, we need to understand what we are automating. You cannot automate something you do not understand.

OpenShift in Plain English

Imagine you need to run 50 different applications at ABC Bank. Each application needs to:

  • Start automatically if it crashes
  • Scale up when more users arrive
  • Have its own isolated network
  • Be updated without downtime
  • Be monitored at all times

Running this manually across hundreds of servers is impossible. OpenShift is a container platform that does all of this for you. It is built on Kubernetes (the open-source container orchestration engine) and adds enterprise security, developer tools, monitoring, and management features on top.

🧠
OpenShift API Server
The brain. Everything — Ansible, oc CLI, UI — talks to this HTTPS endpoint.
🖥️
Nodes
Virtual or physical machines that run containerized workloads (worker nodes) or control the cluster (master/control-plane nodes).
📦
Pods
The smallest unit. A Pod contains one or more containers (Docker/OCI). Your application runs inside a Pod.
🗂️
Namespaces / Projects
Isolated virtual boundaries within the cluster. DEV, QA, UAT each get their own namespace.
🔌
Services
Internal load balancers that route traffic to pods.
🌐
Routes
OpenShift-specific external URL that exposes your application to the internet.
OpenShift Internal Architecture
┌─────────────────────────────────────────────────────────────┐
│ OpenShift Cluster │
│ │
│ ┌─────────────────┐ ┌────────────────────────────┐ │
│ │ Control Plane │ │ Worker Nodes │ │
│ │ │ │ │ │
│ │ API Server ◀───┼─────┼── oc CLI / Ansible / UI │ │
│ │ etcd (DB) │ │ │ │
│ │ Scheduler │────▶│ ┌──────┐ ┌──────┐ │ │
│ │ Controller Mgr │ │ │ Pod │ │ Pod │ ... │ │
│ └─────────────────┘ │ └──────┘ └──────┘ │ │

💡
Key Insight

Everything in OpenShift is a resource (Node, Pod, Namespace, Deployment, etc.) and all resources are managed through the API Server via HTTPS. This is why Ansible can automate OpenShift — it simply makes API calls on your behalf.

03 What is Ansible? (And Why Does ABC Bank Use It?)

The Problem Without Ansible

Before automation, an engineer at ABC Bank would have to:

  1. Manually oc login to each cluster
  2. Manually run oc get nodes and copy output
  3. Manually check each namespace
  4. Manually write up the results
  5. Manually send an email
  6. Repeat this for every environment — DEV, QA, UAT, PROD, DR

This is slow, error-prone, and not auditable. If something breaks at 2 AM, nobody wants to do this manually.

Ansible in Plain English

Ansible is an automation tool that lets you describe what you want done in a simple YAML file called a Playbook, and Ansible will do it automatically — connecting to systems, making API calls, performing checks, handling errors, and reporting results.

🤖
Agentless
Ansible does NOT need software installed on the target. For OpenShift, it uses the API. For Linux servers, it uses SSH.
📝
YAML Playbooks
Human-readable automation scripts. Not a programming language — you describe WHAT you want, not HOW to do it.
🔌
Modules
Pre-built functions. Instead of writing API code, you call kubernetes.core.k8s_info.
♻️
Idempotent
Run the playbook 10 times — it only makes changes when needed. Same result every time.
📚
Collections
Packages of modules. kubernetes.core provides all OpenShift/Kubernetes modules.
🏗️
Roles
Reusable, organized automation components. Like functions in programming.
How Ansible Executes a Task
You write YAML describing desired state
↓
Ansible reads the Playbook
↓
Ansible loads the Collection (kubernetes.core)
↓
Collection calls OpenShift API via HTTPS
↓
OpenShift API validates authentication
↓
OpenShift API checks RBAC permissions
↓
OpenShift performs the operation
↓
Response returned to Ansible
↓
Ansible records: changed / ok / failed

04 What is RHAAP / AAP? (Where Playbooks Actually Run at ABC Bank)

You could run Ansible from your laptop. But that raises questions:

  • Where are the credentials stored safely?
  • Who approved this automation run?
  • What is the audit trail?
  • How does it run automatically at 6 AM?
  • How can the Manager track job status?
  • Who can see the output?

Red Hat Ansible Automation Platform (RHAAP/AAP) solves all of this. It is the enterprise platform that manages, executes, governs, and audits all Ansible automation.

🔐
Credential Store
OpenShift tokens, Vault passwords, SSH keys — all stored encrypted. Never in Git.
📅
Schedules
Run automation at 6 AM every weekday. Like cron, but enterprise-grade with history.
📋
Job Templates
Pre-configured automation runs. Define playbook, inventory, credentials, variables once. Run on demand.
🔄
Workflows
Chain multiple Job Templates with success/failure branching. Full deployment pipelines.
👥
RBAC
Control who can run, view, or edit automation. Junior engineers can run, not edit.
📦
Execution Environments
Container images with all required Ansible collections and Python libraries pre-installed.

06 OpenShift Authentication — The Right Way

This is one of the most important concepts. Never hard-code passwords or tokens.

How Authentication Works

Ansible connects to OpenShift using a Bearer Token. The token belongs to a ServiceAccount that has only the permissions needed for our health check — nothing more. This is called the Least Privilege Principle.

Authentication Flow
RHAAP Credential Store ← token encrypted here, never in Git
↓
Execution Environment starts
↓
RHAAP injects K8S_AUTH_API_KEY env variable into container
↓
Ansible playbook reads host/api_key from environment or variables
↓
kubernetes.core module sends HTTPS request with Authorization: Bearer <token>
↓
OpenShift API Server validates token against etcd
↓
RBAC checked: does this ServiceAccount have permission?
↓
YES → response returned → Ansible processes result

Creating the ServiceAccount in OpenShift

Before running any playbook, a cluster admin must create a ServiceAccount with read permissions:

bash Run these commands once as cluster-admin 
# Step 1: Create a dedicated namespace for our automation ServiceAccount
oc create namespace abc-ansible-automation

# Step 2: Create the ServiceAccount
# This is the identity our Ansible automation will use
oc create serviceaccount ansible-cluster-reader \
  --namespace abc-ansible-automation

# Step 3: Grant cluster-reader ClusterRole
# cluster-reader = read-only access to all resources cluster-wide
# This is the minimum privilege needed for health checks
oc adm policy add-cluster-role-to-user cluster-reader \
  system:serviceaccount:abc-ansible-automation:ansible-cluster-reader

# Step 4: Extract the ServiceAccount token
# OpenShift 4.11+ requires creating a Secret explicitly for long-lived tokens
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: ansible-cluster-reader-token
  namespace: abc-ansible-automation
  annotations:
    kubernetes.io/service-account.name: ansible-cluster-reader
type: kubernetes.io/service-account-token
EOF

# Step 5: Retrieve the token (do NOT commit this to Git)
oc get secret ansible-cluster-reader-token \
  --namespace abc-ansible-automation \
  -o jsonpath='{.data.token}' | base64 -d
What Each Command Does
create namespaceCreates an isolated OpenShift project to house our automation resources. Keeps things organized and secure.
create serviceaccountCreates a non-human identity in OpenShift. Like a user account, but for automation. Cannot log in interactively.
add-cluster-role-to-userGrants the ServiceAccount permission to read resources across the entire cluster. Read-only — cannot create or delete.
kubernetes.io/service-account-tokenCreates a long-lived token Secret associated with the ServiceAccount. Required in OCP 4.11+ for automation.
base64 -dDecodes the base64-encoded token from the Secret. The decoded value is what you put in RHAAP Credentials.
🔐
Security Rule — Never in Git

The token you extracted above must NEVER be placed in a file that is committed to Git. It goes into RHAAP Credentials or Ansible Vault. If a token is ever accidentally committed, rotate it immediately using oc delete secret and create a new one.

07 Collections — The Tools Ansible Uses to Talk to OpenShift

What is a Collection?

A Collection is a packaged set of Ansible modules, plugins, and roles. Instead of writing Python code to call the OpenShift API yourself, you install a Collection and it provides ready-made modules.

For OpenShift automation, we need the kubernetes.core collection. This gives us modules like:

ModuleWhat It DoesCommon Use
kubernetes.core.k8s_infoRead/query resources from OpenShiftGet nodes, pods, namespaces
kubernetes.core.k8sCreate, update, or delete resourcesApply YAML manifests
kubernetes.core.k8s_execExecute commands inside a podRun tests inside containers
kubernetes.core.helmManage Helm chart deploymentsDeploy Helm applications

08 Inventory & Variables — Telling Ansible About Our Clusters

What is an Inventory?

An Inventory tells Ansible about the systems it will interact with. For OpenShift automation, instead of listing SSH servers, we define our cluster API endpoints.

In production, we have separate inventories for each environment. This prevents a playbook written for DEV from accidentally running against Production.

ansible.cfg — Runtime Configuration

ini ansible.cfg 
# ansible.cfg
# This file configures Ansible's runtime behavior.
# Ansible looks for this file in the current directory first.

[defaults]
# Do not check SSH host keys (for OpenShift API, not SSH)
host_key_checking     = False

# Make playbook output more readable for humans
stdout_callback       = yaml

# Default inventory — used when no -i flag is provided
# We will override this per environment from RHAAP
inventory             = inventories/dev

# Retry failed tasks with a file (optional — here disabled)
retry_files_enabled   = False

# Show task timing at the end of the playbook
[callback_profile_tasks]
task_output_limit     = 20

Inventory File — DEV Cluster

yaml inventories/dev/hosts.yml 
---
# inventories/dev/hosts.yml
# Defines the DEV OpenShift cluster as an Ansible host.

  children:

09 Ansible Vault — Protecting Secrets

Even though the real token comes from RHAAP Credentials in production, during local development we use Ansible Vault to encrypt sensitive values so they can be safely included in Git.

⚠️
Important Distinction

In local development: use Ansible Vault to encrypt secrets in files.
In RHAAP production: use RHAAP Credential Store — the token is injected as an environment variable, Vault is used for additional secrets like SMTP passwords.

bash Terminal — Ansible Vault Commands 
# Create a vault-encrypted secrets file
ansible-vault create vars/secrets.yml

# Ansible will prompt for a vault password
# Then open an editor where you type your secrets:
#   ---
#   vault_ocp_api_token: "sha256~yourtokenhere"
#   vault_smtp_password: "smtp-secret-password"

# View an encrypted file without decrypting permanently
ansible-vault view vars/secrets.yml

# Edit an encrypted file
ansible-vault edit vars/secrets.yml

# Encrypt an existing plain file
ansible-vault encrypt vars/secrets.yml

# Decrypt permanently (only for migration, never commit decrypted)
ansible-vault decrypt vars/secrets.yml

# Run a playbook with vault — prompts for password
ansible-playbook playbooks/cluster_health_check.yml --ask-vault-pass

# Run with vault password file (for scheduled automation)
ansible-playbook playbooks/cluster_health_check.yml \
  --vault-password-file ~/.vault_pass.txt

The Complete Playbook

yaml playbooks/cluster_health_check.yml 
---
###############################################################################
# PLAYBOOK: OpenShift Cluster Health Check
# TICKET:   INFRA-1001
# AUTHOR:   ABC Bank OpenShift Platform Team
# PURPOSE:  Verify OpenShift cluster connectivity and resource health.
#           Generates an HTML report and sends email to Operations.
# RUNS ON:  RHAAP / Automation Controller
###############################################################################

- name: "OpenShift Cluster Health Check — ABC Bank"
  hosts: openshift_clusters         # Target: all hosts in this inventory group
  gather_facts: false               # Disable SSH fact-gathering; we use OpenShift API
  connection: local                  # All tasks run locally (API calls, not SSH)

  vars:
    # The OpenShift API token
    # In RHAAP: injected via K8S_AUTH_API_KEY environment variable
    # In local dev: comes from Vault or environment variable
    ocp_token: "{{ lookup('env', 'K8S_AUTH_API_KEY') | default(vault_ocp_api_token, true) }}"

    # Collection of health check results — we populate this throughout execution
    health_results:
      cluster_reachable:     "UNKNOWN"
      nodes_healthy:         "UNKNOWN"
      namespaces_healthy:    "UNKNOWN"
      no_problem_pods:       "UNKNOWN"
      overall_status:        "UNKNOWN"
      problem_pods:          []
      notready_nodes:        []
      missing_namespaces:    []
      errors:                []

  tasks:

    ##########################################################
    # TASK 1 — Record start time and metadata
    ##########################################################
    - name: "Record playbook start time"
      ansible.builtin.set_fact:
        playbook_start_time: "{{ ansible_date_time.iso8601 }}"
        playbook_start_epoch: "{{ ansible_date_time.epoch }}"
      tags: [always]                 # 'always' tag: this task ALWAYS runs, even with --tags filter

    ##########################################################
    # TASKS 2-6 — OpenShift Health Checks inside a BLOCK
    # Block allows us to catch errors with rescue/always
    ##########################################################
    - block:

        # TASK 2 — Verify OpenShift API is reachable
        # We use k8s_info to query the API version endpoint
        # If this fails, the API is down or authentication failed
        - name: "[PRE-CHECK] Verify OpenShift API connectivity and authentication"
          kubernetes.core.k8s_info:      # Module from kubernetes.core collection
            api_version: v1              # Use Kubernetes core API v1
            kind: Namespace              # Query Namespace resources (cheap, always exists)
            host: "{{ ocp_api_url }}"    # OpenShift API server URL from inventory
            api_key: "{{ ocp_token }}"  # Bearer token for authentication
            validate_certs: "{{ ocp_validate_certs }}"  # SSL cert verification
            name: kube-system            # Query a specific namespace that always exists
          register: api_connectivity_result  # Store result in variable for later use
          until: api_connectivity_result is not failed  # Retry until success
          retries: "{{ api_connect_retries }}"            # Max 3 retries
          delay: "{{ api_connect_delay }}"              # 10 seconds between retries
          tags: [connectivity, precheck]

        # Record connectivity success
        - name: "Record: API connectivity successful"
          ansible.builtin.set_fact:
            health_results: "{{ health_results | combine({'cluster_reachable': 'PASSED'}) }}"
          tags: [connectivity, precheck]

        # TASK 3 — Collect all nodes
        - name: "[CHECK] Collect all cluster nodes"
          kubernetes.core.k8s_info:
            api_version: v1
            kind: Node                  # Node resource — represents a physical/virtual machine
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
            validate_certs: "{{ ocp_validate_certs }}"
          register: all_nodes_result       # Contains .resources list of all nodes
          tags: [nodes]

        # TASK 4 — Find NotReady nodes using Jinja2 filtering
        - name: "[CHECK] Identify NotReady nodes"
          ansible.builtin.set_fact:
            # This is a Jinja2 expression — let's read it step by step:
            # all_nodes_result.resources    → list of all node objects from OpenShift
            # | selectattr(...)              → filter: keep only nodes where condition is true
            # item.status.conditions         → each node has a list of conditions
            # | selectattr('type','eq','Ready')  → find the condition where type == 'Ready'
            # | selectattr('status','ne','True') → keep where Ready status is NOT True
            # | list                          → convert filter result to a list
            # | length > 0                    → check if there are any such conditions
            notready_nodes_list: >-
              {{
                all_nodes_result.resources
                | selectattr('status.conditions', 'defined')
                | selectattr('status.conditions',
                    'contains_value', {'type': 'Ready', 'status': 'True'})
                | map(attribute='metadata.name')
                | list
              }}

            # Simpler approach: extract all node names and ready conditions
            node_health_list: >-
              {{
                all_nodes_result.resources | map(attribute='metadata.name') | list
              }}
          tags: [nodes]

        # TASK 4b — More reliable node readiness check
        - name: "[CHECK] Evaluate node readiness for each node"
          ansible.builtin.set_fact:
            notready_nodes_list: >-
              {{
                all_nodes_result.resources
                | selectattr('status.conditions', 'defined')
                | rejectattr('status.conditions | selectattr("type","eq","Ready")
                             | selectattr("status","eq","True") | list | length', 'gt', 0)
                | map(attribute='metadata.name')
                | list
              }}
          tags: [nodes]

        # TASK 5 — Assert node health
        - name: "[ASSERT] All nodes must be Ready"
          ansible.builtin.assert:
            that:
              - "notready_nodes_list | length == 0"   # Condition: no NotReady nodes
            fail_msg: "CRITICAL: {{ notready_nodes_list | length }} node(s) are NotReady: {{ notready_nodes_list | join(', ') }}"
            success_msg: "All {{ all_nodes_result.resources | length }} nodes are Ready"
          register: node_assertion_result
          ignore_errors: true             # Don't stop — record the failure and continue
          tags: [nodes]

        # Record node health status
        - name: "Record node health status"
          ansible.builtin.set_fact:
            health_results: >-
              {{
                health_results | combine({
                  'nodes_healthy': 'PASSED' if node_assertion_result is not failed else 'FAILED',
                  'notready_nodes': notready_nodes_list,
                  'total_nodes': all_nodes_result.resources | length
                })
              }}
          tags: [nodes]

        # TASK 6 — Check critical namespaces
        - name: "[CHECK] Verify critical namespace: {{ item }}"
          kubernetes.core.k8s_info:
            api_version: v1
            kind: Namespace
            name: "{{ item }}"             # Loop variable — current namespace name
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
            validate_certs: "{{ ocp_validate_certs }}"
          register: namespace_results
          loop: "{{ ocp_critical_namespaces }}"  # Iterate over list defined in inventory
          loop_control:
            label: "{{ item }}"             # Show namespace name in output (not whole dict)
          tags: [namespaces]

        # Identify missing namespaces from loop results
        - name: "[EVALUATE] Identify missing critical namespaces"
          ansible.builtin.set_fact:
            missing_ns_list: >-
              {{
                namespace_results.results
                | selectattr('resources', 'defined')
                | selectattr('resources', 'equalto', [])
                | map(attribute='item')
                | list
              }}
          tags: [namespaces]

        - name: "Record namespace health status"
          ansible.builtin.set_fact:
            health_results: >-
              {{
                health_results | combine({
                  'namespaces_healthy': 'PASSED' if missing_ns_list | length == 0 else 'FAILED',
                  'missing_namespaces': missing_ns_list
                })
              }}
          tags: [namespaces]

        # TASK 7 — Collect all pods across all namespaces
        - name: "[CHECK] Collect all pods cluster-wide"
          kubernetes.core.k8s_info:
            api_version: v1
            kind: Pod
            host: "{{ ocp_api_url }}"
            api_key: "{{ ocp_token }}"
            validate_certs: "{{ ocp_validate_certs }}"
            # No 'namespace' field = query ALL namespaces
          register: all_pods_result
          tags: [pods]

        # TASK 8 — Find pods in problem states
        - name: "[EVALUATE] Identify pods in problem states"
          ansible.builtin.set_fact:
            problem_pods_list: >-
              {{
                all_pods_result.resources
                | selectattr('status.containerStatuses', 'defined')
                | selectattr('status.containerStatuses', 'ne', none)
                | map(attribute='status') | list
              }}
            # Simpler: find pods where phase is not Running/Succeeded/Pending
            non_running_pods: >-
              {{
                all_pods_result.resources
                | rejectattr('status.phase', 'in', ['Running', 'Succeeded', 'Pending'])
                | map('combine', {})
                | list
              }}
          tags: [pods]

        - name: "Record pod health status"
          ansible.builtin.set_fact:
            health_results: >-
              {{
                health_results | combine({
                  'no_problem_pods': 'PASSED' if non_running_pods | length == 0 else 'WARNING',
                  'total_pods': all_pods_result.resources | length,
                  'problem_pod_count': non_running_pods | length
                })
              }}
          tags: [pods]

        # TASK 9 — Set overall status
        - name: "[EVALUATE] Determine overall cluster health status"
          ansible.builtin.set_fact:
            health_results: >-
              {{
                health_results | combine({
                  'overall_status': 'HEALTHY' if (
                    health_results.cluster_reachable == 'PASSED' and
                    health_results.nodes_healthy == 'PASSED' and
                    health_results.namespaces_healthy == 'PASSED'
                  ) else 'UNHEALTHY'
                })
              }}
          tags: [always]

      ##########################################################
      # RESCUE — Runs if any task in the block fails
      ##########################################################
      rescue:

        - name: "[RESCUE] Health check encountered a critical failure"
          ansible.builtin.debug:
            msg: "CRITICAL: Health check failed. Marking cluster as UNREACHABLE."

        - name: "[RESCUE] Set cluster status to FAILED"
          ansible.builtin.set_fact:
            health_results: >-
              {{
                health_results | combine({
                  'cluster_reachable': 'FAILED',
                  'overall_status': 'CRITICAL',
                  'errors': ['OpenShift API connection failed after ' ~ api_connect_retries ~ ' retries']
                })
              }}

      ##########################################################
      # ALWAYS — Runs regardless of block success or failure
      ##########################################################
      always:

        # TASK 10 — Calculate execution duration
        - name: "[REPORT] Calculate execution duration"
          ansible.builtin.set_fact:
            playbook_end_time: "{{ ansible_date_time.iso8601 }}"
            execution_duration_seconds: >-
              {{ (ansible_date_time.epoch | int) - (playbook_start_epoch | int) }}

        # TASK 11 — Generate HTML Report
        - name: "[REPORT] Generate HTML health check report"
          ansible.builtin.template:           # Render Jinja2 template to file
            src: "{{ report_template }}"          # Template file in templates/ directory
            dest: >-
              {{ report_output_dir }}/cluster_health_{{ ocp_cluster_name }}_{{ ansible_date_time.date }}.html
            mode: '0644'
          register: report_file_result

        # TASK 12 — Send email notification
        - name: "[NOTIFY] Send health check report email to Operations"
          community.general.mail:
            host: "{{ smtp_host }}"
            port: "{{ smtp_port }}"
            username: "{{ notification_email_from }}"
            password: "{{ vault_smtp_password }}"  # From Vault — never hard-coded
            to: "{{ notification_email_to }}"
            from: "{{ notification_email_from }}"
            subject: >-
              [{{ environment_name }}] OpenShift Health Check — {{ ocp_cluster_name }}
              — {{ health_results.overall_status }}
            body: "Please find the cluster health report attached."
            attach:
              - "{{ report_file_result.dest }}"    # Attach the HTML report
            subtype: html
          no_log: false                     # Allow logging except for password field
          ignore_errors: true             # Don't fail playbook if email fails
          tags: [notify]

        # TASK 13 — Debug: Print summary to console
        - name: "[SUMMARY] Print health check summary"
          ansible.builtin.debug:
            msg:
              - "===== OPENSHIFT CLUSTER HEALTH CHECK SUMMARY ====="
              - "Cluster    : {{ ocp_cluster_name }}"
              - "Environment: {{ environment_name }}"
              - "API URL    : {{ ocp_api_url }}"

              - "Node Health: {{ health_results.nodes_healthy }}"
              - "Namespaces : {{ health_results.namespaces_healthy }}"
              - "Pod Status : {{ health_results.no_problem_pods }}"
              - "OVERALL    : {{ health_results.overall_status }}"
              - "Duration   : {{ execution_duration_seconds }}s"
              - "Report     : {{ report_file_result.dest | default('N/A') }}"
              - "==================================================="
          tags: [always]

11 Code Explanation — Every Important Concept

Understanding YAML Playbook Structure

Top-Level Playbook Keywords
---Every YAML file starts with three dashes. This marks the start of the YAML document.
- name:The dash (-) marks the start of a list item. This is a Play — the top-level unit of a playbook. You can have multiple plays in one playbook file.
hosts:Tells Ansible which inventory hosts to run this play against. "openshift_clusters" matches the group name we defined in hosts.yml.
gather_facts: falseBy default, Ansible runs a "setup" module that collects facts (OS, memory, IP, etc.) from each host via SSH. We set this to false because we're using local API calls, not SSH — no facts to gather.
connection: localTells Ansible to run all tasks on the Ansible control node (or Execution Environment) itself, not to SSH into any machine. Perfect for API-based automation.
vars:Play-level variables. These are available to all tasks in this play. Lower precedence than inventory variables.
tasks:The list of actions to execute. Each task calls one module. Tasks run in order, top to bottom.

Understanding Block / Rescue / Always

This is one of the most important patterns in production Ansible. Think of it like a try/catch/finally in programming:

block / rescue / always — Execution Flow
block: ← This is like "try" — run these tasks normally
- task 1
- task 2
- task 3 ← FAILS ← Something goes wrong here
↓ Ansible jumps to rescue
rescue: ← Like "catch" — runs ONLY if block had a failure
- log the error
- set status=FAILED
↓ Always runs next
always: ← Like "finally" — runs regardless of success or failure
- generate report ← ALWAYS runs
- send email ← ALWAYS runs
✅
Why This Pattern is Critical

Without block/rescue/always, if the API connection fails, the playbook would stop immediately and no one would know. With this pattern, even if everything fails, the report is generated and the email is sent — Operations are always notified.

Understanding the register Keyword

How register Works
register: api_connectivity_resultSaves the entire output of the k8s_info module call into a variable called api_connectivity_result. This variable contains: .resources (list of OpenShift objects), .failed (bool), .changed (bool), .msg (string).
api_connectivity_result.resourcesThe list of Kubernetes/OpenShift objects returned. For a Namespace query, this is a list of Namespace objects.
api_connectivity_result is not failedJinja2 test — checks if the registered variable indicates the task failed. Used in the "until" condition for retry logic.

Understanding until / retries / delay

yamlRetry Logic Explained
until: api_connectivity_result is not failed
retries: 3
delay: 10
Retry Execution Flow
Attempt 1 → API call → FAILED (network blip)
↓ wait 10 seconds
Attempt 2 → API call → FAILED (still down)
↓ wait 10 seconds
Attempt 3 → API call → SUCCESS
↓ condition met: "not failed"
Task completes → moves to next task

If all 3 attempts fail → rescue block is triggered

Understanding Jinja2 Filters

Jinja2 is the templating engine built into Ansible. The | character is the filter separator — it passes data through a function.

Breaking Down a Complex Jinja2 Expression
all_nodes_result.resourcesThe list of Node objects returned by k8s_info. Each object is a dictionary representing an OpenShift Node.
| selectattr('status.conditions', 'defined')Filter: keep only nodes where the status.conditions field is defined (not null). Prevents errors on nodes with missing data.
| map(attribute='metadata.name')For each node object, extract the value of metadata.name (the node hostname). Transforms a list of objects into a list of strings.
| listConverts the map/select generator object into an actual Python list. Always needed after selectattr/map.
| combine({'key': 'value'})Merges a dictionary with new key-value pairs. Used to update our health_results tracking dictionary.
| default(vault_ocp_api_token, true)If the first value is empty/undefined, use vault_ocp_api_token instead. The "true" means treat empty string as undefined too.
| lengthReturns the count of items in a list. length == 0 means the list is empty.
| join(', ')Joins a list of strings with commas. ['node1', 'node2'] becomes "node1, node2".

Understanding set_fact

ansible.builtin.set_fact creates or updates variables during playbook execution. Unlike vars: which are static, set_fact lets you compute values dynamically based on task results.

💡
Why We Use a health_results Dictionary

Instead of 5 separate variables, we use one health_results dictionary. This makes it easy to pass all results to the Jinja2 HTML template in one variable, and to update individual fields using | combine() without overwriting the others.

15 Interview Questions

What is Ansible and why is it preferred over shell scripts for OpenShift automation?
Ansible is an agentless automation tool that uses YAML playbooks to define desired state. Unlike shell scripts, Ansible provides idempotency (safe to re-run), error handling with block/rescue/always, a rich module library that abstracts API complexity, built-in retry logic, and integration with RHAAP for enterprise scheduling, RBAC, and audit trails. Shell scripts can drift, have no error recovery pattern, and don't integrate natively with RHAAP.
What is the kubernetes.core collection and why do we use it?
kubernetes.core is an Ansible collection provided by Red Hat/community that contains modules for interacting with Kubernetes and OpenShift APIs. We use k8s_info to read resources, k8s to create/update/delete resources. It abstracts the raw HTTP API calls, handles authentication, and provides idempotent operations. Without it, we would need to write raw Python/curl code to interact with the API.
How does Ansible authenticate to OpenShift in production?
In production via RHAAP, we create an OpenShift/Kubernetes credential in RHAAP's credential store. This credential contains the API URL and a Bearer token belonging to a ServiceAccount. When the Job Template runs, RHAAP injects the token as the K8S_AUTH_API_KEY environment variable into the Execution Environment container. The kubernetes.core modules automatically read this environment variable. The token never appears in playbooks or Git.
Explain block / rescue / always in production context.
Block contains the main tasks — if any task fails, execution jumps to rescue instead of stopping. Rescue handles the failure — recording the error, sending alerts, initiating rollback. Always runs regardless of success or failure — used for report generation and notification so Operations are always informed. This prevents the worst-case scenario of automation failing silently with no one notified.
What is idempotency and how does kubernetes.core achieve it?
Idempotency means running the same automation multiple times produces the same result — no unintended changes. kubernetes.core achieves this by querying the current state of resources before applying changes. For k8s_info (read), it's always idempotent. For k8s (write), it compares the desired manifest with the existing resource and only patches if there is a difference. Running the health check playbook 10 times should produce no changes — only ok statuses.

  when:
    - >
      health_results.overall_status != 'HEALTHY'
      or email_on_healthy | bool

The or operator means: send email if cluster is unhealthy (always) OR if email_on_healthy is true (optionally on success). The | bool filter converts the string/var to a proper boolean.

yamlAnswer
- name: "CRITICAL: Report each NotReady node"
  ansible.builtin.debug:
    msg: "CRITICAL: Node {{ item }} is NotReady — immediate investigation required"
  loop: "{{ notready_nodes_list }}"
  loop_control:
    label: "{{ item }}"    # Show node name in output header
  when: notready_nodes_list | length > 0   # Skip entirely if list is empty
