01 The Manager's Eighth Ticket — INFRA-2001

🏢 ABC Bank OpenShift Platform Team — Intermediate Stage Begins

You've built foundation skills. Now Rajesh brings a ticket that changes how you think about automation:

"We have 12 microservices. Each needs to deploy to DEV, QA, UAT, PROD, and DR. That's 60 deployment playbooks. DEV has 1 replica and small resource limits. PROD has 5 replicas, strict limits, and needs approval gates. QA needs a specific image tag. Right now different engineers write different playbooks for each environment and we get drift. Can you build ONE playbook that handles all environments through variables? If a developer says 'deploy payment-api v2.3.1 to QA', the automation should just work."

This is the central intermediate challenge: eliminating duplication through intelligent parameterisation. The solution is Ansible's variable precedence system combined with a hierarchical inventory structure.

02 The Duplication Problem — Why Parameterisation Matters

⚠️
Anti-Pattern: One Playbook Per Environment

Junior engineers often create deploy_dev.yml, deploy_qa.yml, deploy_prod.yml. 12 services × 5 environments = 60 playbooks. Add one probe change → update 60 files. Miss one → environment drift. A bug fixed in DEV playbook doesn't get fixed in PROD playbook. This is the #1 automation anti-pattern in enterprise teams.

✅
Pro Pattern: One Role + Variable Hierarchy

One role: openshift_app_deploy. One playbook: deploy.yml. Environment selection at runtime: ansible-playbook deploy.yml -i inventories/prod. Variables drive behaviour. 12 services × 5 environments = still 1 role. Add a probe change → update 1 file. All environments benefit immediately.

03 Variable Precedence — Ansible's 22-Level System

Ansible resolves variable conflicts using a strict precedence order. Higher number = higher precedence = wins. Understanding this is the single most important concept for parameterised playbooks.

PrioritySourceExampleUse Case
1 (lowest)role defaultsroles/deploy/defaults/main.ymlFallback values if nothing else set
2inventory group_vars/allinventories/prod/group_vars/all.ymlCluster-wide defaults
3inventory group_vars/<group>inventories/prod/group_vars/prod.ymlEnvironment-specific values
4inventory host_vars/<host>inventories/prod/host_vars/master01.ymlPer-host overrides
5playbook vars_filesvars_files: [vars/app.yml]App-specific config loaded in play
6playbook varsvars: { replicas: 3 }Inline play variables
7role vars (main.yml)roles/deploy/vars/main.ymlRole internal constants (not overridable easily)
8task vars (set_fact)ansible.builtin.set_fact: x: 5Computed values during execution
22 (highest)extra_vars (-e)ansible-playbook ... -e app_image_tag=v2Runtime overrides, RHAAP Survey vars
💡
The Golden Rule of Variable Precedence

role defaults = "sensible defaults if nobody says otherwise". group_vars = "environment profile". extra_vars (-e) = "runtime operator override that beats everything". In RHAAP, Survey variables become extra_vars automatically — so Survey always wins.

06 Role defaults vs vars — When to Use Each

defaults/main.yml vs vars/main.yml
defaults/main.yml LOWEST precedence. Safe fallback values if nothing else is set. Should contain every variable the role uses, with sensible defaults. Easily overridden by group_vars, host_vars, or extra_vars.
vars/main.yml HIGH precedence (beats group_vars). Use sparingly for role-internal constants that should NOT be changed by inventory. Example: Kubernetes API version strings.
Rule of thumb If users/environments should be able to override it → defaults/. If it's an internal constant the role needs → vars/. Most variables belong in defaults/.
yaml roles/openshift_app_deploy/defaults/main.yml 
---
# Role defaults — lowest precedence
# These are OVERRIDDEN by group_vars and extra_vars
# Every variable used in tasks/templates must appear here


# Application identity
app_name:            "myapp"
app_version:         "v1"
app_image_tag:       "latest"
container_image:     "registry.abcbank.internal/{{ app_name }}:{{ app_image_tag }}"
container_port:      8080

# Deployment settings (overridden per environment)
app_replicas:         1               # DEV default; PROD overrides to 5
update_strategy:      "RollingUpdate"
max_surge:            1
max_unavailable:      0
revision_history_limit: 10

# Resource defaults (overridden per environment)
cpu_request:          "100m"
cpu_limit:            "500m"
memory_request:       "128Mi"
memory_limit:         "512Mi"

# Probe defaults (overridden per environment)

07 The Universal Deployment Role

tasks/main.yml — Fully Parameterised

yaml roles/openshift_app_deploy/tasks/main.yml 
---
# Universal deployment role — no environment-specific code
# All behaviour driven by variables


- name: "[VALIDATE] Assert required variables are set"
  ansible.builtin.assert:
    that:
      - ocp_api_url | length > 0
      - app_namespace | length > 0
      - app_name | length > 0
      - app_image_tag | length > 0
    fail_msg: "Required variables missing. Set ocp_api_url, app_namespace, app_name, app_image_tag."
  tags: [always, validate]

- name: "[INFO] Display deployment context"
  ansible.builtin.debug:
    msg:
      - "App: {{ app_name }}:{{ app_image_tag }}"
      - "Environment: {{ environment_name | upper }}"
      - "Namespace: {{ app_namespace }}"
      - "Replicas: {{ app_replicas }}"
      - "CPU: {{ cpu_request }} → {{ cpu_limit }}"
      - "Memory: {{ memory_request }} → {{ memory_limit }}"
  tags: [always]

- name: "[CONFIG] Create ConfigMap"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'configmap.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  tags: [config, deploy]

- name: "[DEPLOY] Apply Deployment manifest"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'deployment.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
    validate_certs: "{{ ocp_validate_certs }}"
  register: deploy_result
  tags: [deploy]

- name: "[WAIT] Wait for rollout"
  ansible.builtin.command:
    cmd: "oc rollout status deployment/{{ app_name }} -n {{ app_namespace }} --timeout={{ rollout_timeout | default('10m') }}"
  environment:
    KUBECONFIG: "{{ kubeconfig_path | default(omit) }}"
  tags: [deploy, wait]

- name: "[VERIFY] Check all replicas ready"
  kubernetes.core.k8s_info:
    kind: Deployment
    name: "{{ app_name }}"
    namespace: "{{ app_namespace }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: deploy_status
  until: deploy_status.resources[0].status.readyReplicas | default(0) == app_replicas | int
  retries: 20
  delay: 15
  tags: [verify]

08 Parameterised Templates — One Template, All Environments

jinja2 roles/openshift_app_deploy/templates/deployment.yml.j2 
---
# Universal Deployment Template
# Variables sourced from group_vars per environment

apiVersion: apps/v1
kind: Deployment
metadata:
  name:      {{ app_name }}
  namespace: {{ app_namespace }}
  labels:
    app:         {{ app_name }}
    version:     {{ app_image_tag }}
    environment: {{ environment_name }}
spec:
  replicas: {{ app_replicas }}         # 1=DEV, 2=QA, 5=PROD
  selector:
    matchLabels:
      app: {{ app_name }}
  strategy:
    type: {{ update_strategy }}
    rollingUpdate:
      maxSurge:       {{ max_surge }}
      maxUnavailable: {{ max_unavailable }}
  template:
    metadata:
      labels:
        app:         {{ app_name }}
        version:     {{ app_image_tag }}
        environment: {{ environment_name }}
    spec:
      containers:
        - name:  {{ app_name }}
          image: {{ container_image }}   # registry.../app_name:app_image_tag
          ports:
            - containerPort: {{ container_port }}
          resources:
            requests:
              cpu:    "{{ cpu_request }}"       # 100m DEV → 500m PROD
              memory: "{{ memory_request }}"   # 128Mi DEV → 512Mi PROD
            limits:
              cpu:    "{{ cpu_limit }}"
              memory: "{{ memory_limit }}"
          livenessProbe:
            httpGet:
              path: {{ liveness_path }}
              port: {{ container_port }}
            initialDelaySeconds: {{ liveness_initial_delay }}   # 10=DEV → 30=PROD
            periodSeconds:       {{ liveness_period }}
            failureThreshold:    {{ liveness_failure_threshold }}
          readinessProbe:
            httpGet:
              path: {{ readiness_path }}
              port: {{ container_port }}
            initialDelaySeconds: {{ readiness_initial_delay }}
            periodSeconds:       {{ readiness_period }}
          env:
            - name:  APP_ENV
              value: "{{ environment_name }}"
            - name:  LOG_LEVEL
              value: "{{ app_log_level }}"
            - name:  FEATURE_FRAUD
              value: "{{ feature_fraud_detection | string | lower }}"
            - name:  FEATURE_RATE_LIMIT
              value: "{{ feature_rate_limiting | string | lower }}"

09 Environment Playbooks — The Thin Orchestration Layer

With a parameterised role, the playbook becomes a thin 10-line file that just calls the role. The inventory selection does all the work.

yaml playbooks/deploy_app.yml — ONE playbook for all environments 
---
# Universal app deployment playbook
# Environment determined by -i inventories/<env>
# Image tag passed at runtime: -e app_image_tag=v2.3.1

- name: "Deploy {{ app_name | default('application') }} to {{ environment_name | default('dev') | upper }}"
  hosts: localhost
  gather_facts: false
  vars_files:
    - "vars/secrets.yml"       # Vault: ocp_token

  pre_tasks:
    - name: "Validate image tag provided"
      ansible.builtin.assert:
        that:
          - app_image_tag is defined
          - app_image_tag != 'latest'    # Enforce explicit tag in pipeline
        fail_msg: "app_image_tag must be set and not 'latest'. Use: -e app_image_tag=v2.3.1"

  roles:
    - role: openshift_app_deploy    # Single role, environment from inventory

# Usage:
# Deploy to DEV:
#   ansible-playbook playbooks/deploy_app.yml -i inventories/dev -e "app_name=payment-api app_image_tag=v2.3.1"
#
# Deploy to PROD:
#   ansible-playbook playbooks/deploy_app.yml -i inventories/prod -e "app_name=payment-api app_image_tag=v2.3.1"
#
# The ONLY difference is: -i inventories/dev vs -i inventories/prod
# All environment-specific behaviour comes from group_vars

11 Troubleshooting Guide

SymptomRoot CauseFix
Variable not overriding as expected Wrong precedence level. role vars/ beats group_vars. extra_vars beats everything. Run ansible-playbook ... -e "var=val" -v. Use ansible-inventory --vars to see merged vars per host.
DEV config deployed to PROD Wrong inventory specified: -i inventories/dev instead of -i inventories/prod Add pre_task assertion: assert: that: environment_name == expected_env. Add environment check in pipeline.
group_vars not loading File named wrong. Must be group_vars/all.yml or match group name exactly. Run ansible-inventory -i inventories/prod --list. Check hostvars and group memberships.
Latest tag deployed to PROD app_image_tag not set explicitly; default 'latest' used Add assert in pre_tasks: app_image_tag != 'latest'. Pipeline must always pass explicit tag.
RHAAP Survey var not taking effect Survey var name doesn't match playbook variable name exactly Survey variable names are case-sensitive. Match exactly. Check RHAAP job output for extra_vars section.

12 Interview Questions

Explain Ansible variable precedence. Which source wins when variables conflict?
Ansible has 22 precedence levels. Highest wins. From lowest to highest: role defaults → inventory group_vars/all → group_vars/<group> → host_vars → playbook vars_files → playbook vars → role vars → set_fact → extra_vars (-e). In practice: role defaults = safe fallback, group_vars = environment profile, extra_vars (-e) = runtime override that beats everything. RHAAP Survey answers become extra_vars, so they always win. Understanding this lets you build a single role that behaves differently per environment without code changes.
What is the difference between role defaults/ and role vars/?
defaults/main.yml: lowest precedence level (1 of 22). Easily overridden by group_vars, host_vars, extra_vars. Use for: every variable the role needs, with sensible fallback values. vars/main.yml: high precedence (level 17). Beats group_vars. Hard to override. Use for: internal role constants like API version strings that should not be user-configurable. Rule: if users or environments should control it, put it in defaults/. If it's a role-internal constant, put it in vars/.
How do you design a single Ansible role that works for DEV, QA, and PROD?
Use inventory hierarchy + group_vars. Create inventories/dev, inventories/qa, inventories/prod directories. Each has group_vars/all.yml with environment-specific values (replicas, resources, feature flags, cluster URL). Role defaults provide fallbacks. Templates reference variables, not hardcoded values. Run with: ansible-playbook deploy.yml -i inventories/prod -e app_image_tag=v2.3.1. Inventory selection switches all environment behaviour automatically. No code in the role knows or cares about environments — it just reads variables.
What prevents accidental deployment to PROD with DEV settings?
Multiple guards: (1) Assertion in pre_tasks: assert: environment_name == 'prod' when using PROD inventory. (2) Pipeline approval gate: RHAAP Workflow with human approval node before PROD job template runs. (3) Separate RHAAP credentials for PROD cluster — DEV engineers don't have PROD API token. (4) PROD Survey doesn't allow 'latest' image tag — explicit semver required. (5) Audit log: every RHAAP job shows who launched it, what variables were set, what changed.
How does a RHAAP Survey connect to Ansible variables?
RHAAP Survey fields define questions shown to the operator before launching a Job Template. Each field has a "Variable Name" (e.g., app_image_tag). When the operator submits the form, RHAAP passes all Survey answers as extra_vars to the playbook. extra_vars have the highest precedence in Ansible (level 22), so they override everything including group_vars and role defaults. This is how operators provide runtime inputs (image tag, target namespace, replica count) without editing playbooks.
