01 The Manager's Fourteenth Ticket — INFRA-2007

🏢 ABC Bank OpenShift Platform Team — Intermediate Week 7

A security audit has flagged the cluster. The auditor's report reads:

"Multiple pods are running with the default ServiceAccount which has more permissions than needed. The Ansible automation account has cluster-admin — that's too broad. Developers are using shared credentials to deploy. There's no audit trail for who did what. We need: (1) Each application pod runs with its own ServiceAccount with only the permissions it needs. (2) Ansible gets a dedicated ServiceAccount with just enough permissions to do its job. (3) Developers get namespace-level access only — no cluster-wide permissions. (4) We need an automated report of all RBAC bindings so auditors can see who can do what."

RBAC is the last major intermediate topic before we move to Advanced. It is also one of the most security-critical.

03 RBAC Objects — Complete Reference

Four Core RBAC Objects
ServiceAccountIdentity for a pod. Pods authenticate to API server using SA token. Every pod runs as a SA (default if not specified). Namespace-scoped.
RoleSet of permissions within ONE namespace. Cannot grant cross-namespace or cluster-level access. "Can read ConfigMaps in payment-prod." Namespace-scoped.
ClusterRoleSet of permissions cluster-wide OR for cluster-scoped resources (Nodes, PVs, StorageClasses). Can also be used in namespace-scoped binding via RoleBinding.
RoleBindingGrants a Role or ClusterRole to a Subject within ONE namespace. "payment-api-sa has payment-api-reader Role in payment-prod."
ClusterRoleBindingGrants a ClusterRole to a Subject cluster-wide. "ansible-sa has ansible-operator ClusterRole across ALL namespaces." Use sparingly.

apiVersion: v1
kind: ServiceAccount

  namespace: payment-prod
  labels:
    app:        payment-api

---
# Reference ServiceAccount in Pod spec:

spec:
  serviceAccountName: payment-api-sa
  automountServiceAccountToken: false   # Don't mount token unless needed
  containers: [...]

---
# Ansible: Create SA and extract token for automation use

- name: "Create Ansible automation ServiceAccount"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name:      ansible-automation-sa
        namespace: ansible-platform
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: sa_result

# In OpenShift 4.x, create a long-lived token Secret for SA
- name: "Create SA token Secret"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: Secret
      metadata:
        name:      ansible-automation-sa-token
        namespace: ansible-platform
        annotations:
          kubernetes.io/service-account.name: ansible-automation-sa
      type: kubernetes.io/service-account-token
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"

# Extract the token from the Secret
- name: "Extract SA token"
  kubernetes.core.k8s_info:
    kind: Secret
    name: ansible-automation-sa-token
    namespace: ansible-platform
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: sa_token_secret
  no_log: true

- name: "Decode token"
  ansible.builtin.set_fact:
    ansible_sa_token: "{{ sa_token_secret.resources[0].data.token | b64decode }}"
  no_log: true

05 Roles & ClusterRoles — Permission Definitions

yamlApplication Role + Ansible ClusterRole
---
# Role: least-privilege for payment-api pod
# Only needs to read its own ConfigMap and Secret

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name:      payment-api-reader
  namespace: payment-prod
rules:
  - apiGroups: [""]                 # "" = core API group (v1 resources)
    resources: [configmaps, secrets]
    verbs:     [get, list, watch]    # Read-only
    resourceNames:                   # Optional: specific resources only
      - payment-api-config
      - payment-api-secrets

---
# ClusterRole: Ansible automation — enough to manage cluster, not destroy it

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ansible-operator
rules:
  # Core resources
  - apiGroups: [""]
    resources:
      - namespaces
      - pods
      - services
      - configmaps
      - secrets
      - persistentvolumeclaims
      - resourcequotas
      - limitranges
      - serviceaccounts
    verbs: [get, list, watch, create, update, patch]
    # Note: no 'delete' for namespaces — safety guardrail

  # Apps resources
  - apiGroups: [apps]
    resources:
      - deployments
      - statefulsets
      - replicasets
      - daemonsets
    verbs: [get, list, watch, create, update, patch, delete]

  # Batch
  - apiGroups: [batch]
    resources: [jobs, cronjobs]
    verbs: [get, list, watch, create, update, patch, delete]

  # RBAC — can manage roles below its own level
  - apiGroups: [rbac.authorization.k8s.io]
    resources: [roles, rolebindings]
    verbs: [get, list, watch, create, update, patch]

  # OpenShift Routes
  - apiGroups: [route.openshift.io]
    resources: [routes]
    verbs: [get, list, watch, create, update, patch, delete]

06 RoleBindings — Connecting Subjects to Roles

yamlRoleBinding Examples
---
# RoleBinding 1: App SA gets reader role in its namespace

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name:      payment-api-reader-binding
  namespace: payment-prod
subjects:
  - kind:      ServiceAccount
    name:      payment-api-sa
    namespace: payment-prod
roleRef:
  kind:     Role
  name:     payment-api-reader
  apiGroup: rbac.authorization.k8s.io

---
# RoleBinding 2: Developer group gets view access to DEV namespace only

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name:      dev-team-view
  namespace: payment-dev
subjects:
  - kind:  Group             # Group = LDAP/SSO group
    name:  payment-developers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind:     ClusterRole      # Using built-in ClusterRole 'view'
  name:     view             # view=read-only, edit=read-write, admin=namespace admin
  apiGroup: rbac.authorization.k8s.io

---
# ClusterRoleBinding: Ansible SA gets operator ClusterRole cluster-wide

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: ansible-operator-binding
subjects:
  - kind:      ServiceAccount
    name:      ansible-automation-sa
    namespace: ansible-platform
roleRef:
  kind:     ClusterRole
  name:     ansible-operator
  apiGroup: rbac.authorization.k8s.io

07 Least Privilege Design Principles

PatternAnti-PatternBest Practice
Service AccountAll pods use default SA (shared, often overblown)One SA per application. automountServiceAccountToken: false unless needed.
Cluster-wide vs NamespaceClusterRoleBinding for everything (over-broad)Use namespace-scoped RoleBinding unless genuinely cluster-scoped.
VerbsAll verbs (*) including delete on critical resourcesOnly verbs the app actually needs. Never * in prod. Separate read vs write roles.
Resource NamesAccess to ALL secrets in namespaceUse resourceNames to limit to specific Secrets the app needs.
Automation accountscluster-admin for AnsibleCustom ClusterRole with only required resources and verbs. Never cluster-admin.

---
# Full RBAC provisioning: SA → Role → RoleBinding

- name: "[RBAC] Create ServiceAccount for each app"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name:      "{{ item }}-sa"
        namespace: "{{ app_namespace }}"
        labels:
          app:        "{{ item }}"
          managed-by: ansible
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  loop: "{{ app_service_accounts | default(['payment-api', 'fraud-detector']) }}"
  loop_control:
    label: "{{ item }}-sa"

- name: "[RBAC] Create application Role"
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'app_role.yml.j2') }}"
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  loop: "{{ app_service_accounts | default(['payment-api', 'fraud-detector']) }}"
  loop_control:
    label: "{{ item }}-reader role"

- name: "[RBAC] Bind Role to ServiceAccount"
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: rbac.authorization.k8s.io/v1
      kind: RoleBinding
      metadata:
        name:      "{{ item }}-reader-binding"
        namespace: "{{ app_namespace }}"
      subjects:
        - kind:      ServiceAccount
          name:      "{{ item }}-sa"
          namespace: "{{ app_namespace }}"
      roleRef:
        kind:     Role
        name:     "{{ item }}-reader"
        apiGroup: rbac.authorization.k8s.io
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  loop: "{{ app_service_accounts | default(['payment-api', 'fraud-detector']) }}"
  loop_control:
    label: "{{ item }}-reader-binding"

09 RBAC Audit — Who Can Do What

yamlRBAC Audit Playbook
---
# Audit all RoleBindings and ClusterRoleBindings

- name: "[AUDIT] Query all RoleBindings"
  kubernetes.core.k8s_info:
    kind: RoleBinding
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_rolebindings

- name: "[AUDIT] Query all ClusterRoleBindings"
  kubernetes.core.k8s_info:
    kind: ClusterRoleBinding
    host: "{{ ocp_api_url }}"
    api_key: "{{ ocp_token }}"
  register: all_crbs

- name: "[AUDIT] Flag overprivileged bindings (cluster-admin)"
  ansible.builtin.set_fact:
    cluster_admin_bindings: "{{ all_crbs.resources
      | selectattr('roleRef.name','eq','cluster-admin')
      | list }}"

- name: "[AUDIT] Alert on cluster-admin bindings"
  ansible.builtin.debug:
    msg:
      - "⚠️ cluster-admin bindings found: {{ cluster_admin_bindings | length }}"
      - "Subjects: {{ cluster_admin_bindings | map(attribute='subjects') | list }}"
  when: cluster_admin_bindings | length > 0

# Use oc auth can-i to verify specific permissions
- name: "[AUDIT] Verify payment-api-sa cannot delete pods"
  ansible.builtin.command:
    cmd: "oc auth can-i delete pods --as=system:serviceaccount:payment-prod:payment-api-sa -n payment-prod"
  environment:
    KUBECONFIG: "{{ kubeconfig_path }}"
  register: can_i_result
  changed_when: false
  failed_when:  false

- name: "[ASSERT] SA cannot delete pods (should be 'no')"
  ansible.builtin.assert:
    that:
      - can_i_result.stdout | trim == 'no'
    fail_msg: "SECURITY: payment-api-sa CAN delete pods — overprivileged!"

10 Troubleshooting

SymptomRoot CauseFix
Pod: "forbidden: User cannot get secrets"Pod's ServiceAccount doesn't have permission to read SecretsAdd Secret read permission to the SA's Role. Or check SA is correctly bound: oc auth can-i get secrets --as=system:serviceaccount:ns:sa-name
Ansible fails: "403 Forbidden"Ansible SA token doesn't have permission for the operationAdd the required verb/resource to ansible-operator ClusterRole. Re-apply ClusterRole.
RoleBinding created but SA still can't accessRoleBinding references wrong namespace for SA, or wrong SA nameVerify: oc get rolebinding -o yaml. Check subjects[0].namespace and name exactly match SA.
ClusterRole but namespace access still neededClusterRole + ClusterRoleBinding = cluster-wide. Use RoleBinding to scope ClusterRole to namespaceUse RoleBinding (not ClusterRoleBinding) with roleRef.kind: ClusterRole to scope it to one namespace.
SA token not mounting in podautomountServiceAccountToken: false set on SA or PodSet automountServiceAccountToken: true in Pod spec, or remove the override. Only disable when pod truly doesn't need API access.

11 Interview Questions

Explain the difference between Role and ClusterRole, and RoleBinding and ClusterRoleBinding.
Role: namespace-scoped permissions — grants access to resources in ONE namespace only. ClusterRole: cluster-scoped — grants access across all namespaces, or to cluster-scoped resources (Nodes, PVs). RoleBinding: grants a Role or ClusterRole to a Subject within ONE namespace. ClusterRoleBinding: grants a ClusterRole to a Subject cluster-wide. Key trick: you can use a RoleBinding to grant a ClusterRole in a specific namespace — this lets you define common roles once (ClusterRole) and bind them in individual namespaces (RoleBinding) without redefining the Role everywhere.
What is a ServiceAccount and why should each application have its own?
ServiceAccount: an identity for a pod to authenticate to the Kubernetes API server. Each pod runs as a SA and its permissions are defined by Roles bound to that SA. Using the default SA means all apps in a namespace share one identity with the same permissions — over-privileged and no audit trail. Dedicated SA per app: (1) least-privilege — payment-api gets only what payment-api needs, (2) audit trail — API audit log shows "payment-api-sa created a ConfigMap" not "default SA", (3) isolation — compromising one app's SA doesn't grant another app's permissions.
How would you design RBAC for an Ansible automation account?
Create dedicated ServiceAccount (ansible-automation-sa) in a locked-down namespace (ansible-platform). Create a custom ClusterRole (ansible-operator) with only the resources and verbs Ansible actually uses: get/list/watch/create/update/patch for Deployments, Services, ConfigMaps, Secrets, etc. No cluster-admin. No wildcard verbs. No delete for Namespaces. ClusterRoleBinding grants this ClusterRole cluster-wide. Extract SA token, store in Ansible Vault, use in group_vars as ocp_token. Rotate token periodically. This way Ansible has enough permissions to do its job but can't accidentally delete critical cluster objects.
What is oc auth can-i and how do you use it for RBAC validation?
oc auth can-i VERB RESOURCE --as=SUBJECT -n NAMESPACE. Tests if a subject has permission. Use --as=system:serviceaccount:namespace:sa-name to impersonate a ServiceAccount. Example: oc auth can-i delete pods --as=system:serviceaccount:payment-prod:payment-api-sa → should return "no". Use in Ansible assert tasks to automatically validate least-privilege design. Also run after RBAC changes to verify effect. Essential for RBAC audit automation.

Challenge 3 of 3

Write a validation task that uses oc auth can-i to test a list of required permissions for the Ansible ServiceAccount (should be YES) and a list of forbidden permissions (should be NO). Fail if any are incorrect.

▶ Show Answer
yamlRBAC validation matrix
- name: "Test REQUIRED permissions (should be yes)"
  ansible.builtin.command:
    cmd: "oc auth can-i {{ item.verb }} {{ item.resource }} --as=system:serviceaccount:ansible-platform:ansible-automation-sa"
  environment:
    KUBECONFIG: "{{ kubeconfig_path }}"
  register: required_checks
  changed_when: false
  failed_when: false
  loop:
    - {verb: get,    resource: deployments}
    - {verb: create, resource: configmaps}
    - {verb: patch,  resource: services}
  loop_control:
    label: "{{ item.verb }} {{ item.resource }}"

- name: "Assert all required permissions granted"
  ansible.builtin.assert:
    that: item.stdout | trim == 'yes'
    fail_msg: "RBAC FAIL: ansible-sa cannot {{ item.item.verb }} {{ item.item.resource }}"
  loop: "{{ required_checks.results }}"

- name: "Test FORBIDDEN permissions (should be no)"
  ansible.builtin.command:
    cmd: "oc auth can-i {{ item.verb }} {{ item.resource }} --as=system:serviceaccount:ansible-platform:ansible-automation-sa"
  register: forbidden_checks
  changed_when: false
  failed_when: false
  loop:
    - {verb: delete, resource: namespaces}
    - {verb: '*',    resource: '*'}
  loop_control:
    label: "{{ item.verb }} {{ item.resource }}"

- name: "Assert forbidden permissions denied"
  ansible.builtin.assert:
    that: item.stdout | trim == 'no'
    fail_msg: "SECURITY: ansible-sa CAN {{ item.item.verb }} {{ item.item.resource }} — overprivileged!"
  loop: "{{ forbidden_checks.results }}"
