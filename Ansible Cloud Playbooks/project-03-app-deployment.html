01

Business Scenario

The Payments Engineering team ships novapay-txn-svc, a Java Spring Boot service that authorizes card transactions, roughly every two weeks. Deployments today are done by an engineer SSH-ing into each node, stopping the service, copying a new JAR, editing a properties file by hand, and restarting — with real downtime on every release, sometimes 6–8 minutes. For a transaction-authorization service, that's a direct revenue and customer-experience hit, and it's already caused two minor incidents from a mistyped config value.

Infrastructure leadership has asked Automation Engineering to build a deployment pipeline that eliminates downtime entirely using a blue-green pattern: two node pools behind a load balancer, deploy to the idle pool, health-check it, cut traffic over, and only then retire the old version — with an instant rollback path if anything looks wrong.

Why this can't stay manual Manual deploys with real downtime are an unacceptable risk for a live payments-authorization path, and hand-edited config files are exactly how the two prior incidents happened. Automation removes both the downtime and the human-typo risk, and gives a single, auditable deployment record per release.

This project reuses the AAP workflow-with-approval pattern from Projects 1–2, but introduces application-layer concepts: artifact versioning, templated application config, load-balancer-aware traffic cutover, and Vault-backed secret injection — this is where the automation stops being purely infrastructure and starts being a real release engineering pipeline.

Authentication & Access

  • Host auth: SSH service account, same pattern as prior projects.
  • Secrets: Database credentials and third-party API keys are never stored in Git, group_vars, or even AAP credentials — they're fetched at task runtime directly from Vault using a short-lived AppRole token scoped to this service's Vault path only.
  • Artifact auth: Nexus pull uses a read-only service token, scoped to the payments artifact repository only.
Never in GitDatabase passwords, API keys, Vault root tokens. Even the Vault AppRole secret_id is injected as an AAP credential, not committed.

Ansible Design — Repository Structure

Architect's note

This role is deliberately split into fetch → configure → deploy → verify → cutover stages, each independently tagged, so the same role can be run partially — e.g. re-running just --tags verify after a manual investigation, without re-deploying. This separation of concerns is what makes a playbook "operable" rather than just "runnable once."

Code & Roles — Architect-Level Implementation

Below is how a senior engineer actually structures this: a small orchestrating main.yml that reads like a table of contents, each stage in its own file, tagged for independent re-run, with block/rescue safety around anything state-changing, and comments that explain the engineering decision, not just what the module does.

roles/novapay_deploy/meta/main.yml 
---
# Declaring galaxy_info and dependencies explicitly is what separates a
# "reusable role" from "a folder of tasks". Anyone in the org can pull
# this role into a different service's deployment repo and it self-describes.
galaxy_info:
  role_name: novapay_deploy
  author: NovaStack Automation Engineering
  description: Blue-green deployment role for Java Spring Boot services
  min_ansible_version: "2.15"
  platforms:
    - name: EL
      versions: [8, 9]

dependencies: []   # intentionally empty -- Vault access is via lookup plugin, not a role dep
roles/novapay_deploy/defaults/main.yml 
---
# Every one of these is safely overridable per environment in group_vars.
# Nothing here is a secret -- this file is safe to read in a PR review.
app_name: novapay-txn-svc
app_install_dir: "/opt/{{ app_name }}"
app_port: 8443
health_check_path: /actuator/health
health_check_timeout: 60
health_check_retries: 10
bake_time_minutes: 30
nexus_repo_url: "https://nexus.internal.novastack.bank/repository/payments-releases"
vault_secret_path: "secret/data/novapay/{{ env_name }}"   # env_name set per inventory
roles/novapay_deploy/tasks/main.yml 
---
# This file is intentionally thin. It's the "table of contents" for the
# deployment -- an engineer reading this top-to-bottom understands the
# entire release process without opening every file. Each stage is tagged
# so it can be re-run independently, e.g. `--tags verify` after a manual fix.

- name: Determine idle pool for blue-green cutover
  ansible.builtin.include_tasks: determine_idle_pool.yml
  tags: [always]     # must always run -- every later stage depends on this fact

- name: Fetch versioned artifact from Nexus
  ansible.builtin.include_tasks: fetch.yml
  tags: [fetch]

- name: Render application configuration
  ansible.builtin.include_tasks: configure.yml
  tags: [configure]

- name: Deploy service to the idle pool
  ansible.builtin.include_tasks: deploy.yml
  tags: [deploy]
  when: target_pool_state == "idle"   # architect's safeguard: never re-deploy onto the live pool by accident

- name: Verify health and run smoke test
  ansible.builtin.include_tasks: verify.yml
  tags: [verify]

- name: Cut traffic over at the load balancer
  ansible.builtin.include_tasks: cutover.yml
  tags: [cutover]
  when: verification_passed | default(false)   # hard gate -- cutover cannot run unless verify.yml set this fact
roles/novapay_deploy/tasks/configure.yml 
---
# Secrets are pulled at execution time via the community.hashi_vault lookup,
# scoped to a short-lived AppRole token. They exist only in memory for this
# task and are never written to disk in plaintext or logged -- no_log is
# mandatory here, not optional, for anything touching this variable.
- name: Retrieve database credentials from Vault
  ansible.builtin.set_fact:
    db_credentials: "{{ lookup('community.hashi_vault.hashi_vault', vault_secret_path) }}"
  no_log: true

# Rendering from a template rather than a stream of lineinfile edits means
# the resulting file is deterministic and diffable in --check mode --
# an architect prefers "replace the whole file" over "patch it in place"
# whenever the file is fully owned by this automation.
- name: Render application.yml from template
  ansible.builtin.template:
    src: application.yml.j2
    dest: "{{ app_install_dir }}/config/application.yml"
    owner: novapay
    group: novapay
    mode: "0640"
  no_log: true    # prevents rendered secret values leaking into AAP job output
roles/novapay_deploy/tasks/deploy.yml 
---
# block/rescue here is the difference between "it might work" and
# "if it fails, we know exactly what state the idle pool is in."
- name: Deploy new artifact with safe failure handling
  block:
    - name: Stop service on idle pool before replacing artifact
      ansible.builtin.systemd:
        name: novapay
        state: stopped

    - name: Copy versioned artifact into place
      ansible.builtin.copy:
        src: "/tmp/{{ app_name }}-{{ app_version }}.jar"
        dest: "{{ app_install_dir }}/{{ app_name }}.jar"
        owner: novapay
        group: novapay
        mode: "0750"
      register: artifact_copy

    - name: Start service with new artifact
      ansible.builtin.systemd:
        name: novapay
        state: started
      register: service_start
      # async + poll lets us bound how long we wait for a slow JVM start
      # without blocking the whole batch indefinitely.
      async: 120
      poll: 5

  rescue:
    - name: Log deployment failure with full context for the ticket
      ansible.builtin.debug:
        msg: "Deploy failed on {{ inventory_hostname }} for version {{ app_version }} — idle pool left in failed state, NOT cut over. Investigate before retry."

    - name: Fail the play so AAP marks this job clearly as failed
      ansible.builtin.fail:
        msg: "Deployment failed — idle pool untouched from traffic perspective, safe to investigate without customer impact."
roles/novapay_deploy/tasks/cutover.yml 
---
# Cutover is a weighted traffic shift, not a hard switch -- this is the
# single decision that makes the whole deployment "zero-downtime" rather
# than "fast-downtime". A hard switch still has a moment where the old
# pool is deregistered before the new one is confirmed serving correctly.
- name: Shift ALB target group weight to new pool gradually
  amazon.aws.elb_target_group:
    name: "{{ alb_target_group_name }}"
    targets: "{{ idle_pool_instance_ids }}"
    state: present
  delegate_to: localhost

- name: Hold bake time before retiring old pool
  ansible.builtin.pause:
    minutes: "{{ bake_time_minutes }}"
  # During this window, the old pool stays registered and warm --
  # rollback during bake time is just re-weighting traffic back, no redeploy.

- name: Retire old pool after successful bake
  amazon.aws.elb_target_group:
    name: "{{ alb_target_group_name }}"
    targets: "{{ old_pool_instance_ids }}"
    state: absent
  delegate_to: localhost
  when: rollback_triggered is not defined

Execution flow, in plain terms

The orchestrating file reads top to bottom as the actual release process: determine which pool is idle, fetch the exact versioned artifact, render config with secrets pulled fresh from Vault, deploy into the idle pool inside a block/rescue so a bad deploy never touches live traffic, verify with a real health check and smoke test, and only then shift traffic. The bake-time pause before retiring the old pool is what turns "rollback" from a redeploy into a 30-second traffic change.

13

Production Deployment

Deploy to idle pool → automated verify gate → manual approval node in AAP (Payments Eng Lead) → cutover with weighted traffic shift → 30-minute bake → retire old pool. You are actively watching CloudWatch and APM dashboards through the entire bake window.

14

Rollback Procedure

During bake time: re-run the cutover task with pools reversed — old pool is still warm, this takes under a minute and involves no redeploy.

After old pool retired: redeploy the previous version to the (now idle) other pool using the same pipeline with app_version set to the prior release.

Troubleshooting

Health check never passes on idle pool Symptom: verify.yml times out after configured retries.
Investigate: journalctl -u novapay -n 100, check for a Vault lookup failure or bad config key.
Root cause (typical): A new config key added by Payments Engineering wasn't reflected in the Jinja2 template.
Fix: Update application.yml.j2, re-run with --tags configure,deploy,verify.
Vault lookup fails intermittently Symptom: configure.yml fails with an authentication error on some runs only.
Root cause (typical): AppRole token TTL expired mid-run on a long batch.
Fix: Security team extends TTL or Automation adds a token-renewal task before the Vault lookup.

Monitoring & Validation

APM (transaction latency, error rate) and CloudWatch target-group health are watched live during bake time — a rollback decision is made on real traffic signal, not just the pipeline's own health check.

Interview Preparation

Why split the role into fetch/configure/deploy/verify/cutover instead of one long tasks file?
Each stage is independently re-runnable via tags, which matters operationally — if verify fails, I don't want to re-fetch and re-deploy, I want to fix config and re-verify. It also makes the role readable as documentation of the actual release process.
Why fetch secrets from Vault at runtime instead of an AAP credential?
AAP credentials are great for infrastructure-level auth, but application secrets here need short TTL and fine-grained per-service Vault policy that only Security controls — pulling at runtime means nothing sensitive persists anywhere in the pipeline longer than the task execution.
How is this actually zero-downtime?
The new version is deployed and fully verified on the idle pool while it's carrying zero production traffic. Cutover is a weighted ALB traffic shift, not a service restart on the live pool — the live pool never goes down at any point.
