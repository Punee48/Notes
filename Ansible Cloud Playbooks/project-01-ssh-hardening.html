01

Business Scenario

NovaStack Bank runs 420 RHEL 8 and RHEL 9 EC2 instances across its retail banking, payments, and core ledger platforms. During a quarterly external security assessment, the bank's Information Security team found that SSH daemon configuration across the fleet does not meet the organization's hardened baseline — weak key exchange algorithms are still permitted, root login over SSH is enabled on a subset of hosts, and idle sessions are not timed out.

This is flagged as a Sev-2 audit finding with a mandated remediation SLA of 30 days. Manually logging into 420 servers, editing sshd_config, and restarting the service is not acceptable — it's slow, inconsistent across engineers, impossible to prove in an audit, and risky for a live banking environment where a single fat-fingered config can lock out access to a production host.

Why this can't be manual A manual change on 420 hosts means 420 opportunities for human error, no consistent evidence trail for the auditor, and no safe way to re-run the same change identically in DEV, UAT, and PROD. Automation gives repeatability, idempotency, and a produced audit log per run — which is exactly what a bank's compliance function needs to sign off on.

Security raises a finding in ServiceNow, which becomes a Problem record owned by Infrastructure Operations. Infrastructure Ops determines this requires configuration automation and routes it to the Automation Engineering team — this is where you, as the assigned engineer, pick up the work.

Authentication & Access

  • Target host auth: SSH key-based, using a dedicated service account svc_ansible_infra with sudo rights scoped only to the tasks this role performs (via a restrictive sudoers entry, not full root sudo).
  • Credential storage: The private key is never in Git. It's stored as an AAP Machine Credential, encrypted at rest, and only exposed to the job at runtime.
  • AWS auth for dynamic inventory: An IAM role scoped to ec2:DescribeInstances only, attached as an AAP AWS credential — no long-lived access keys.
  • Access request process: You raise an Access Request ticket to Infra Ops requesting the service account be provisioned/added to the target host group; Security approves the sudoers scope.
Never in Git Private keys, AWS access keys, sudo passwords, or any AAP credential material. Git only ever holds the playbook, role, and non-sensitive variables.

Code & Role Implementation

roles/ssh_hardening/defaults/main.yml 
# Defaults are intentionally conservative and overridable per environment.
# PROD can override any of these in group_vars/prod.yml without touching the role.
ssh_permit_root_login: "no"
ssh_client_alive_interval: 300        # seconds before an idle session is probed
ssh_client_alive_count_max: 2         # probes before disconnect (10 min idle timeout total)
ssh_allowed_kex_algorithms:
  - curve25519-sha256
  - diffie-hellman-group16-sha512
ssh_backup_dir: /opt/ansible_backups/sshd_config   # used by rollback
ssh_bastion_exception_group: []       # hostnames excluded from root-login lockdown, set per env
roles/ssh_hardening/tasks/main.yml 
---
# 1. Pre-flight: back up the current config before touching anything.
#    This backup is what the CHG rollback plan actually refers to.
- name: Ensure backup directory exists
  ansible.builtin.file:
    path: "{{ ssh_backup_dir }}"
    state: directory
    mode: "0700"

- name: Back up current sshd_config with a run timestamp
  ansible.builtin.copy:
    src: /etc/ssh/sshd_config
    dest: "{{ ssh_backup_dir }}/sshd_config.{{ ansible_date_time.iso8601_basic_short }}"
    remote_src: true
    mode: "0600"

# 2. Render the hardened config from a template rather than editing in place.
#    A template is deterministic and idempotent -- re-running produces
#    the same file every time, which is exactly what a compliance audit wants.
- name: Deploy hardened sshd_config from template
  ansible.builtin.template:
    src: sshd_config.j2
    dest: /etc/ssh/sshd_config
    owner: root
    group: root
    mode: "0600"
    validate: "/usr/sbin/sshd -t -f %s"   # refuses to deploy a config that won't parse
  notify: restart sshd
  register: sshd_config_result

# 3. Never blindly restart sshd on a live banking host without a safety check.
#    Block/rescue lets us catch a bad restart and immediately roll back
#    in the same run, instead of leaving a host in an unknown state.
- name: Apply and verify sshd restart safely
  block:
    - name: Flush handlers to apply the restart now, in this block
      ansible.builtin.meta: flush_handlers

    - name: Confirm sshd is active after restart
      ansible.builtin.systemd:
        name: sshd
        state: started
      register: sshd_status

  rescue:
    - name: Restore previous config on failure
      ansible.builtin.copy:
        src: "{{ ssh_backup_dir }}/sshd_config.{{ ansible_date_time.iso8601_basic_short }}"
        dest: /etc/ssh/sshd_config
        remote_src: true
        mode: "0600"

    - name: Restart sshd with restored config
      ansible.builtin.systemd:
        name: sshd
        state: restarted

    - name: Fail the run so the batch stops and the engineer is alerted
      ansible.builtin.fail:
        msg: "sshd restart failed on {{ inventory_hostname }} — restored previous config. Investigate before continuing this batch."
roles/ssh_hardening/handlers/main.yml 
---
- name: restart sshd
  ansible.builtin.systemd:
    name: sshd
    state: restarted
    # Only fires if the templated config actually changed --
    # this is what makes the whole role idempotent on re-runs.

Execution flow, in plain terms

The role backs up the existing config, renders a new one from a Jinja2 template using environment-specific variables, validates the syntax with sshd -t before it's ever applied, and only restarts the service if the file actually changed. If the restart fails, the rescue block automatically restores the previous file and restarts again — so a single bad host fails loudly rather than silently breaking access.

Rollback Procedure

Rollback is largely automatic inside the role's rescue block, but if a whole batch needs reverting after the fact:

ansible-playbook rollback.yml -i inventories/prod -e "restore_timestamp=20260810T0100"

This restores the specific timestamped backup taken immediately before the change and restarts sshd, returning the host to its pre-change state.

Troubleshooting

sshd fails to restart after config change Symptom: Handler fires, systemd reports failed state.
Investigate: journalctl -u sshd -n 50, sshd -t manually on host.
Root cause (typical): An unsupported KexAlgorithm on an older OpenSSH build.
Fix: Rescue block auto-restores previous config; engineer adjusts the algorithm list for that OS version and re-runs.
Prevention: Add an OS-version-conditional variable file so RHEL 8 and RHEL 9 get different algorithm lists.
AAP job fails with "Permission denied (publickey)" Symptom: Job fails immediately at the Gathering Facts step.
Investigate: Confirm the service account key in the AAP Machine Credential matches what's authorized on the host.
Root cause (typical): Host was provisioned after the last key rotation and wasn't onboarded with the current service account key.
Fix: Raise access request to Infra Ops to add the key to the host's authorized_keys via the standard onboarding process.
Dynamic inventory returns zero hosts for an environment Symptom: Job template reports "No hosts matched."
Investigate: ansible-inventory -i inventories/prod/hosts.aws_ec2.yml --graph
Root cause (typical): Cloud team changed an EC2 tag key without notifying Automation.
Fix: Align inventory filter with actual tag key; raise a tagging-standard discussion with Cloud team to prevent recurrence.

Monitoring & Validation

A successful Ansible run doesn't guarantee the host is actually healthy. CloudWatch alarms on the SSH-related security group and host-level agent checks are watched for 30 minutes post-change per batch — if an unexpected spike in failed connection attempts or an unreachable-host alarm fires, the workflow is paused before the next batch proceeds.

Security Considerations

  • Least privilege: Service account sudo rights are scoped to only the commands this role needs.
  • Audit trail: Every AAP job run is logged with who launched it, when, against which inventory, and the full output — this is the evidence Security signs off on.
  • Compliance mapping: The role's variables map 1:1 to the line items in the Security baseline document, so the mapping itself is part of the audit evidence.

Interview Preparation

Why did you use a role instead of a single playbook?
Because this hardening logic needs to be reused across every RHEL host in the organization, not just this one fleet. A role is independently versionable, testable with Molecule, and easy for another engineer to review without wading through a monolithic playbook.
How is this idempotent?
The config is rendered from a template and compared to what's on disk — the handler only restarts sshd when the file content actually changes. Running it twice in a row produces zero changes on the second run.
What happens if a restart fails on a production host?
The block/rescue construct catches it immediately, restores the pre-change backup, restarts sshd again, and fails that host loudly so the batch stops rather than silently leaving a host inaccessible.
How would you scale this to 2,000 servers instead of 420?
Keep the same role, increase batch parallelism carefully, and split the AAP workflow into per-region or per-AZ job templates so a regional issue doesn't stall the entire fleet. I'd also add a Slack/ITSM notification per batch completion instead of watching job output manually.
What would you do if the application team rejected the change in UAT?
Get the specific technical reason — usually a monitoring agent relying on root SSH — document it as an exception in the requirement, add it to the bastion exception group variable, and re-run UAT rather than overriding their objection.
