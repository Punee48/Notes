01

Business Scenario

NovaStack Bank runs monthly patching under a regulatory-driven policy: all Critical and High CVEs must be remediated within 14 days of vendor release, applied first in DEV, then UAT, then PROD, always inside an approved maintenance window. The estate is mixed — 310 RHEL servers (yum/dnf, patched via a Satellite content view) and 180 Windows Servers (patched via WSUS-approved update groups).

Until now, patching has been handled by two separate teams running two separate manual processes — Linux Ops using shell scripts, Windows Ops using WSUS console clicks. This is inconsistent, slow (roughly 4 engineer-days per cycle), leaves inconsistent evidence, and has twice caused a patch cycle to miss the regulatory SLA. Infrastructure leadership has asked Automation Engineering to build one consolidated, OS-aware pipeline that treats patching as a single governed process regardless of platform.

Why this can't stay manual Two disconnected manual processes means two different audit trails, two different failure-recovery approaches, and no single dashboard leadership can trust for the regulator. A single automated pipeline with OS-specific logic gives one consistent evidence trail and a much smaller SLA-miss risk.

This builds directly on Project 1's foundation — same dynamic inventory approach, same AAP workflow-with-approval pattern — but introduces reboot orchestration, Windows/WinRM authentication, and a scheduled recurring job rather than a one-time remediation.

Approval Flow

You (Engineer)→ Automation Lead→ Linux Ops + Windows Ops Owners→ Standard Change Auto-Approval

Because this runs against a pre-approved Standard Change template, there's no ad-hoc CAB meeting each month — approval is effectively automatic once the template conditions (scope, window, rollback plan) are met. A full CAB review only re-triggers if scope changes materially, e.g. patching a new tier of PCI-scoped hosts for the first time.

Authentication & Access

LINUX (SSH)

  • Service account key, same pattern as Project 1
  • Sudo scoped to yum/dnf and systemctl reboot only

WINDOWS (WinRM)

  • Domain service account, authenticated over WinRM (HTTPS, port 5986)
  • Stored as an AAP Machine Credential of type "Windows"
  • Local admin rights scoped via a dedicated AD group, not Domain Admins

WinRM is new here versus Project 1's pure-SSH world: it needs a certificate-backed HTTPS listener configured on each Windows host (owned by Windows Ops), and the AAP execution environment must have pywinrm available.

Code & Role Implementation

playbooks/patch_cycle.yml 
---
# A single entry point that fans out to the correct OS-specific role.
# This keeps the AAP job template simple -- one template, two roles.
- name: Enterprise patch cycle
  hosts: all
  gather_facts: true
  serial: 20                     # batch size -- limits blast radius of a bad batch
  max_fail_percentage: 10        # pause the whole run if more than 10% of a batch fails
  tasks:
    - name: Apply Linux patching role
      ansible.builtin.include_role:
        name: patch_linux
      when: ansible_os_family == "RedHat"

    - name: Apply Windows patching role
      ansible.builtin.include_role:
        name: patch_windows
      when: ansible_os_family == "Windows"
roles/patch_linux/tasks/main.yml 
---
- name: Record pre-patch package state for rollback evidence
  ansible.builtin.command: rpm -qa
  register: pre_patch_state
  changed_when: false

- name: Apply available security patches via Satellite content view
  ansible.builtin.dnf:
    name: "*"
    security: true
    state: latest
  register: patch_result

# Only reboot if the patch set actually requires it (kernel/glibc) --
# unnecessary reboots on a banking host are themselves a risk.
- name: Check if a reboot is required
  ansible.builtin.stat:
    path: /var/run/reboot-required
  register: reboot_check
  failed_when: false

- name: Reboot host if required and not in exclusion list
  ansible.builtin.reboot:
    reboot_timeout: 600
    post_reboot_delay: 30
  when:
    - reboot_check.stat.exists | default(false)
    - inventory_hostname not in reboot_exclusion_list

- name: Verify critical services are active post-patch
  ansible.builtin.systemd:
    name: "{{ item }}"
    state: started
  loop: "{{ critical_services }}"    # e.g. sshd, chronyd, app-specific agents
roles/patch_windows/tasks/main.yml 
---
- name: Install approved Windows updates from WSUS
  ansible.windows.win_updates:
    category_names:
      - CriticalUpdates
      - SecurityUpdates
    state: installed
  register: win_patch_result

- name: Reboot if updates require it and host is not excluded
  ansible.windows.win_reboot:
    reboot_timeout: 900
  when:
    - win_patch_result.reboot_required
    - inventory_hostname not in reboot_exclusion_list

- name: Confirm target Windows services are running post-patch
  ansible.windows.win_service:
    name: "{{ item }}"
    state: started
  loop: "{{ critical_windows_services }}"

Execution flow, in plain terms

The top-level playbook fans out by OS family so one AAP job template can patch the entire mixed fleet. Each OS role patches, checks whether a reboot is genuinely required, skips hosts on the exclusion list, reboots safely with a timeout, and then confirms the critical services actually came back up — patching without that final check is how "patch succeeded" silently turns into "app is down" the next morning.

Testing Strategy

  • UAT run validated by each application team against their specific stack
  • Chaos check: intentionally exclude one host to confirm the exclusion-list logic actually skips it
13

Production Deployment

Batches of 20 hosts run serially with a health check gate between each batch. If max_fail_percentage is breached in any batch, the workflow halts automatically rather than continuing into the next batch — this is the single most important safety control in a fleet-wide patch run.

14

Rollback Procedure

LINUX

dnf history undo <transaction-id> using the transaction ID captured in the pre-patch evidence, followed by a service restart and validation.

WINDOWS

Get-WindowsUpdateLog to identify the KB, then wusa /uninstall /kb:<id> via a targeted Ansible task, followed by a reboot and service validation.

Troubleshooting

WinRM connection timeout Symptom: Job fails at "Gathering Facts" for Windows hosts only.
Investigate: Test manually with Test-WSMan <host> from a jump box.
Root cause (typical): WinRM HTTPS listener certificate expired.
Fix: Windows Ops renews the listener cert; re-run the job.
Prevention: Add a certificate-expiry check to the monthly pre-flight.
Host doesn't come back after reboot Symptom: ansible.builtin.reboot times out waiting for reconnection.
Investigate: Check AWS console for instance status; check system log via Systems Manager.
Root cause (typical): Kernel update boots into a version missing a required driver.
Fix: Boot into the previous kernel via GRUB (Infra Ops), then investigate the DKMS/module issue before re-patching.
Prevention: DEV/UAT patch cycles should already surface driver-incompatible kernels before PROD.

Monitoring & Validation

Post-patch, CloudWatch/host-agent dashboards are checked for each batch, and a compliance scan (via the same Satellite/WSUS tooling) confirms actual applied-patch state matches what Ansible reported — closing the loop between "the playbook said success" and "the host is provably compliant."

Security Considerations

  • WinRM traffic is HTTPS-only, never unencrypted HTTP
  • Patch content is only ever pulled from the bank's internal Satellite/WSUS — no host reaches public patch repositories directly
  • Reboot exclusions require documented justification, reviewed quarterly by Security to prevent permanent unpatched exceptions

Interview Preparation

Why route by ansible_os_family instead of separate playbooks per OS?
One entry point makes the AAP job template simpler to operate and schedule, while each OS still gets fully separate, independently testable logic in its own role. It also means the batching/serial/max_fail_percentage safety controls apply uniformly across the whole mixed fleet.
How do you avoid unnecessary reboots?
Both roles explicitly check whether the patch set actually requires a reboot — via reboot-required file on Linux and the win_updates reboot_required fact on Windows — instead of rebooting unconditionally after every patch run.
What's the difference between a Standard Change and a Normal Change here versus Project 1?
Project 1's SSH hardening was a one-time remediation needing full CAB review each time. This is a recurring, well-understood, low-risk process, so it runs under a pre-approved Standard Change template — CAB reviews the template itself periodically rather than every monthly run.
