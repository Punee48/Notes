Intake, Namespace & Template

📞 The Ask

Ravi drops a ticket link on your desk: "Puneeth, developers keep filing VM requests in Jira with garbage in them — no CPU count, typos in the namespace, requesting Windows templates that don't exist in our cluster. I want Ansible to reject bad requests BEFORE it ever touches the OpenShift API. Then pick the right VM template automatically based on the OS they asked for."

The example request you're building against: "Create a RHEL 9 VM called web-prod-01 with 4 CPU, 8 GB RAM, 100 GB disk and connect it to the production network." Your job today: turn that sentence into a validated set of Ansible variables, confirm the target namespace exists and has quota, and select the matching OPC-V VM template.

💡 Concept — What is OPC-V and Why Templates Matter

OPC-V (OpenShift Container Platform Virtualization) runs traditional VMs as native Kubernetes objects on top of KubeVirt. A VirtualMachine is a CRD — the same kubernetes.core.k8s module you use for Deployments and ConfigMaps also creates VMs, DataVolumes, and network attachments. This is the entire reason Ansible is a first-class citizen here: no separate hypervisor API, no vCenter SDK — just YAML manifests applied through the Kubernetes API.

VM Templates (in the openshift-virtualization-os-images and cluster template catalog) are pre-baked Template objects that already define the right disk bus, CPU model, and boot firmware for a given OS. Picking the wrong template for RHEL vs. a Windows guest silently produces a VM that never boots cleanly — so template selection is validated logic, not a guess.

🛠️ Hands-On — Step 1: Validate the Incoming Request
vars/vm_request.yml — the normalized request variables
# vars/vm_request.yml
# This is what the intake form / Jira automation drops in front of Ansible.
# Keeping it as plain vars means the SAME playbook can be triggered from
# AAP Job Template survey fields, an API call, or a local test run.
vm_request:
  name: "web-prod-01"
  os: "rhel9"
  # os must match a key in vm_template_map (Step 3) — anything else fails fast
  cpu_cores: 4
  memory_gb: 8
  disk_gb: 100
  namespace: "technova-prod-vms"
  network: "production"
  # network must resolve to a NetworkAttachmentDefinition name (Chapter 2)
playbooks/01_validate_request.yml
- name: Step 1 — Validate VM provisioning request
  hosts: localhost
  gather_facts: false
  vars_files:
    - vars/vm_request.yml
  tasks:

    - name: Assert every mandatory field is present and non-empty
      assert:
        that:
          - vm_request.name is defined and vm_request.name | length > 0
          - vm_request.os is defined
          - vm_request.cpu_cores is defined
          - vm_request.memory_gb is defined
          - vm_request.disk_gb is defined
          - vm_request.namespace is defined
          - vm_request.network is defined
        fail_msg: "Request is missing one or more mandatory fields — rejecting before it reaches OpenShift"
        success_msg: "All mandatory fields present"
      # This is the FIRST gate. Nothing below runs if a field is missing.
      # Rejecting here costs milliseconds. Rejecting after a DataVolume is
      # already 100GB into a PVC creation costs cleanup time and quota churn.

    - name: Assert VM name follows the DNS-1123 naming convention
      assert:
        that:
          - vm_request.name is match("^[a-z0-9]([-a-z0-9]*[a-z0-9])?$")
        fail_msg: "VM name '{{ vm_request.name }}' is not a valid Kubernetes object name (lowercase, alphanumeric, hyphens only)"
      # A VirtualMachine name IS a Kubernetes resource name — same rules as
      # a Pod or Service. Catching an invalid name here beats a cryptic
      # 422 error from the OpenShift API three tasks from now.

    - name: Assert CPU, memory, and disk sizes are sane and within policy caps
      assert:
        that:
          - vm_request.cpu_cores | int > 0
          - vm_request.cpu_cores | int <= 16
          - vm_request.memory_gb | int > 0
          - vm_request.memory_gb | int <= 64
          - vm_request.disk_gb | int >= 20
          - vm_request.disk_gb | int <= 500
        fail_msg: "Requested sizing exceeds self-service policy caps (max 16 vCPU / 64GB RAM / 500GB disk) — route to manual approval"
      # Enterprise concept: SELF-SERVICE CAPS. Anything above these numbers
      # should NOT auto-provision — it should open a manual approval workflow
      # instead (see the AAP Workflow Approval pattern from Phase 2, Ch 19).

    - name: Normalize and register the validated request as a fact
      set_fact:
        validated_request: "{{ vm_request | combine({'name': vm_request.name | lower}) }}"
      # combine() rebuilds the dict with a lower-cased name, so a request
      # typed as "Web-Prod-01" doesn't slip through as invalid later.

    - name: Display the validated request
      debug:
        var: validated_request
🛠️ Hands-On — Step 2: Validate the Target Namespace
playbooks/02_validate_namespace.yml
- name: Confirm namespace exists and has room in its ResourceQuota
  kubernetes.core.k8s_info:
    api_version: v1
    kind: Namespace
    name: "{{ validated_request.namespace }}"
  register: ns_lookup

- name: Fail fast if the namespace does not exist
  assert:
    that: ns_lookup.resources | length > 0
    fail_msg: "Namespace '{{ validated_request.namespace }}' does not exist — self-service does NOT create namespaces, only cluster-admins do"
# Enterprise boundary: self-service provisioning creates VMs INSIDE an
# existing, already-governed namespace. It never creates the namespace
# itself — that keeps RBAC, quotas, and network policies under platform-team control.

- name: Read the ResourceQuota for this namespace, if one is defined
  kubernetes.core.k8s_info:
    api_version: v1
    kind: ResourceQuota
    namespace: "{{ validated_request.namespace }}"
  register: quota_lookup

- name: Compute remaining CPU and memory headroom
  set_fact:
    quota_cpu_used: "{{ quota_lookup.resources[0].status.used['requests.cpu'] | default('0') }}"
    quota_cpu_hard: "{{ quota_lookup.resources[0].status.hard['requests.cpu'] | default('999') }}"
  when: quota_lookup.resources | length > 0
  # default('999') means "no quota object = treat as unrestricted" so this
  # task never crashes on namespaces that simply don't enforce quotas.

- name: Reject the request if it would exceed the namespace's CPU quota
  assert:
    that: (quota_cpu_hard | int) - (quota_cpu_used | int) >= (validated_request.cpu_cores | int)
    fail_msg: "Namespace '{{ validated_request.namespace }}' has insufficient CPU quota headroom for this request"
  when: quota_lookup.resources | length > 0

💡 Production Tip

Keep vm_template_map and the quota caps in group_vars/all/provisioning_policy.yml, not inline. Six months from now, adding Windows Server 2022 support should be a one-line data change reviewed by a platform engineer in a PR — never a playbook edit.

🎯 Interview Questions — Chapter 1
Q1: Why validate the request with `assert` before ever calling the Kubernetes API?
Because failing cheap beats failing expensive. An `assert` task costs nothing — no API call, no object created, no quota consumed. If the request is invalid, you want the playbook to stop in milliseconds with a clear `fail_msg`, not three tasks later after a DataVolume has already started importing 100GB of disk image. It also gives the requester (or the AAP job log) an immediately actionable error instead of a generic Kubernetes 422/403.
Q2: Why does self-service provisioning check the namespace but never create one?
Namespace creation carries RBAC bindings, network policies, and ResourceQuota decisions that are governance decisions, not provisioning decisions. Letting a self-service playbook create namespaces would let any developer silently create a new security boundary with default (often too permissive) settings. The enterprise pattern is: platform-admins create and govern namespaces; self-service playbooks only provision workloads inside namespaces that already exist and are already governed.
Q3: What's the purpose of a data-driven `vm_template_map` instead of hardcoding template names in tasks?
It separates policy (which templates exist and what they map to) from logic (how a request is validated and applied). Adding a new supported OS becomes a reviewable one-line YAML change instead of a code change to the playbook itself — this is the same principle as Ansible variable precedence and group_vars: keep environment-specific or catalog-specific facts out of task logic.

💡 Concept — DataVolumes, PVCs & StorageClasses

A DataVolume (from the Containerized Data Importer, CDI) is the OPC-V object that says "clone this boot source into a new PVC of this size, using this StorageClass." The VM's disk is not the boot image itself — it's a fresh PVC populated by the import/clone job the DataVolume controller runs. This decouples "where the golden image lives" from "what disk this particular VM boots off," so 50 VMs cloned from the same RHEL 9 source each get their own independent, writable disk.

💡 Concept — Network Attachment with Multus

By default, a VM (like a Pod) only gets the cluster's default pod network — fine for east-west traffic, useless for a VM that needs a real routable production IP. A NetworkAttachmentDefinition (NAD), managed by Multus, lets a VM attach a second interface bridged onto a real VLAN. Referencing an existing NAD by name in the VM spec is how "connect it to the production network" becomes a real, enforceable line in YAML.

🛠️ Hands-On — Step 4 & 5: Create the DataVolume (Boot Disk)
playbooks/04_create_datavolume.yml
- name: Create the DataVolume that clones the boot source into a new PVC
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: "{{ validated_request.name }}-boot-dv"
        namespace: "{{ validated_request.namespace }}"
      spec:
        source:
          pvc:
            # Clone from the golden image PVC that platform-team keeps
            # pre-populated in a shared 'golden-images' namespace.
            namespace: golden-images
            name: "{{ selected_template.boot_source }}"
        pvc:
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: "{{ validated_request.disk_gb }}Gi"
          # storageClassName intentionally omitted — inherits the
          # namespace's default StorageClass, which platform-team controls
          # per environment (e.g. ocs-storagecluster-ceph-rbd in prod).
  register: dv_result

- name: Wait until the DataVolume import/clone finishes
  kubernetes.core.k8s_info:
    api_version: cdi.kubevirt.io/v1beta1
    kind: DataVolume
    name: "{{ validated_request.name }}-boot-dv"
    namespace: "{{ validated_request.namespace }}"
  register: dv_status
  until: dv_status.resources[0].status.phase | default('') == 'Succeeded'
  retries: 30
  delay: 10
# retries=30, delay=10 → up to 5 minutes waiting for the clone. A 100GB
# clone on Ceph RBD is usually seconds (thin-clone), but importing from a
# registry/HTTP source can genuinely take minutes — size the wait to match.
🛠️ Hands-On — Step 6 & 7: VirtualMachine Spec — Network, CPU & Memory
playbooks/05_create_vm.yml
- name: Create the VirtualMachine object (stopped — Chapter 3 powers it on)
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: kubevirt.io/v1
      kind: VirtualMachine
      metadata:
        name: "{{ validated_request.name }}"
        namespace: "{{ validated_request.namespace }}"
        labels:
          app.kubernetes.io/managed-by: ansible-self-service
          technova.io/requested-os: "{{ validated_request.os }}"
      spec:
        # running:false — Step 8 (Chapter 3) explicitly powers it on.
        # Creating a VM in a "stopped" state first is the enterprise
        # pattern: it lets you validate the object was accepted by the
        # API server BEFORE you ever spend compute cycles booting it.
        running: false
        template:
          metadata:
            labels:
              kubevirt.io/domain: "{{ validated_request.name }}"
          spec:
            domain:
              cpu:
                cores: "{{ validated_request.cpu_cores }}"
              # 'cores' (not 'sockets'/'threads') is the simplest, most
              # common way to size vCPU for a self-service request — the
              # scheduler treats it as cores * 1 socket * 1 thread.
              resources:
                requests:
                  memory: "{{ validated_request.memory_gb }}Gi"
                # This request also drives the Kubernetes scheduler's
                # node-placement decision — same as a Pod's memory request.
              devices:
                disks:
                  - name: bootdisk
                    disk:
                      bus: virtio
                  - name: cloudinitdisk
                    disk:
                      bus: virtio
                interfaces:
                  - name: prod-net
                    bridge: {}
            # "bridge: {}" tells KubeVirt to bridge this interface onto
            # whatever NetworkAttachmentDefinition is named below — NOT
            # the default masquerade/pod network.
            networks:
              - name: prod-net
                multus:
                  networkName: "{{ validated_request.network }}-vlan-nad"
              # Resolves "production" → "production-vlan-nad", the
              # NetworkAttachmentDefinition platform-team already created
              # in this namespace for the production VLAN.
            volumes:
              - name: bootdisk
                dataVolume:
                  name: "{{ validated_request.name }}-boot-dv"
              - name: cloudinitdisk
                cloudInitNoCloud:
                  userData: "{{ lookup('template', 'templates/cloud-init-userdata.yml.j2') }}"
                # Rendered from a Jinja2 template so the root password hash
                # and hostname are injected per-request, never hardcoded.
templates/cloud-init-userdata.yml.j2
#cloud-config
hostname: {{ validated_request.name }}
chpasswd:
  list: |
    root:{{ vault_vm_root_password }}
  expire: false
# vault_vm_root_password is stored in an Ansible Vault-encrypted file /

⚠️ Common Mistake

Forgetting running: false and instead letting the VM come up powered-on on first create means a boot failure (bad cloud-init, unfinished DataVolume clone) shows up as a confusing CrashLoop-style VMI restart instead of a clean, inspectable "stopped" VM you can debug with oc describe vm before ever starting it.

🎯 Interview Questions — Chapter 2
Q1: Why is a VM's disk a DataVolume-backed PVC instead of using the golden image directly?
Because the golden image is shared, read-only, and reused across many VMs. If every VM booted directly off it, writes from one VM would corrupt it for all others. The DataVolume clones (or imports) that source into a brand-new, independent PVC per VM — same pattern as a container image (immutable, shared) versus a container's writable layer (per-instance).
Q2: What does the Multus NetworkAttachmentDefinition actually solve that the default pod network can't?
The default pod network is a cluster-internal overlay — fine for VM-to-VM or VM-to-Service traffic, but it isn't routable on the corporate network and doesn't give the VM a real, predictable IP on a specific VLAN. A NAD, consumed via bridge: {} in the VM spec, bridges a second NIC straight onto that VLAN so the VM gets a real production-routable address, exactly like a bare-metal server plugged into that switch port.
Q3: Why create the VM with `running: false` instead of powering it on immediately?
It separates "did the API accept my object" from "did the guest OS boot successfully." If you create-and-immediately-run in one step, any failure (unfinished disk clone, bad cloud-init YAML, missing NAD) surfaces as a confusing VMI crash-loop. Creating stopped first lets Ansible (and a human) inspect a clean, static object before spending compute cycles — then Step 8 explicitly flips it to running once everything else is verified.

Readiness, IP & Provisioning Report

Ravi's last requirement for this project: "Puneeth, 'Running' in the console doesn't mean the app team can actually log in. I've seen VMs sit at 'Running' for ten minutes because the guest agent never came up. Ansible needs to wait for REAL readiness, grab the actual IP, and email the requester a one-page summary — not make them dig through `oc get vm` themselves."

💡 Concept — "Running" vs. "Ready": VMI Conditions

A VirtualMachineInstance (VMI) is the running-instance counterpart to a VirtualMachine, conceptually like a Pod is to a Deployment. Its status.phase hits Running as soon as the virt-launcher pod starts the QEMU process — long before the guest OS has finished booting. The status.conditions array carries a separate AgentConnected condition, true only once the qemu-guest-agent inside the guest has phoned home. That's the signal that actually means "the OS is up and the guest agent can report facts like the IP address" — the one Ravi actually cares about.

🛠️ Hands-On — Step 8 & 9: Start the VM and Wait for True Readiness
playbooks/06_start_and_wait.yml
- name: Power on the VirtualMachine by flipping spec.running to true
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: kubevirt.io/v1
      kind: VirtualMachine
      metadata:
        name: "{{ validated_request.name }}"
        namespace: "{{ validated_request.namespace }}"
      spec:
        running: true
# kubernetes.core.k8s does a strategic merge by default, so this ONLY
# touches spec.running — it does not resend or clobber the disks,
# network, or CPU/memory block created in Chapter 2.

- name: Wait for the VirtualMachineInstance to reach phase Running
  kubernetes.core.k8s_info:
    api_version: kubevirt.io/v1
    kind: VirtualMachineInstance
    name: "{{ validated_request.name }}"
    namespace: "{{ validated_request.namespace }}"
  register: vmi_status
  until: vmi_status.resources | length > 0 and vmi_status.resources[0].status.phase | default('') == 'Running'
  retries: 18
  delay: 10
# Phase 1 gate: the virt-launcher pod exists and QEMU has started.
# This does NOT mean the guest OS has booted yet — see the next task.

- name: Wait for the guest agent to report the VM is truly ready
  kubernetes.core.k8s_info:
    api_version: kubevirt.io/v1
    kind: VirtualMachineInstance
    name: "{{ validated_request.name }}"
    namespace: "{{ validated_request.namespace }}"
  register: vmi_ready_check
  until: >
    vmi_ready_check.resources[0].status.conditions
    | selectattr('type', 'equalto', 'AgentConnected')
    | map(attribute='status') | list | first | default('False') == 'True'
  retries: 30
  delay: 10
# Phase 2 gate: qemu-guest-agent inside the guest OS has connected back.
# THIS is the condition that means "log in and it'll actually work" —
# exactly the gap Ravi complained about.
🛠️ Hands-On — Step 10 & 11: Validate IP and Generate the Report
playbooks/07_validate_ip_and_report.yml
- name: Extract the interface IP addresses reported by the guest agent
  set_fact:
    vm_interfaces: "{{ vmi_ready_check.resources[0].status.interfaces | default([]) }}"

- name: Find the IP on the production interface specifically
  set_fact:
    vm_production_ip: "{{ vm_interfaces | selectattr('name', 'equalto', 'prod-net') | map(attribute='ipAddress') | list | first | default('') }}"

- name: Fail if the VM never picked up an IP on the production network
  assert:
    that: vm_production_ip | length > 0
    fail_msg: "{{ validated_request.name }} is Ready but has no IP on prod-net — check the NAD and DHCP/VLAN config before handing this VM off"
# This is the enterprise safety net: "guest agent connected" is not the
# same guarantee as "has a real network address." Check both explicitly.

- name: Build the provisioning report
  set_fact:
    provisioning_report:
      vm_name: "{{ validated_request.name }}"
      namespace: "{{ validated_request.namespace }}"
      os: "{{ validated_request.os }}"
      template_used: "{{ selected_template.template_name }}"
      cpu_cores: "{{ validated_request.cpu_cores }}"
      memory_gb: "{{ validated_request.memory_gb }}"
      disk_gb: "{{ validated_request.disk_gb }}"
      production_ip: "{{ vm_production_ip }}"
      status: "READY"
      provisioned_at: "{{ lookup('pipe', 'date -u +%Y-%m-%dT%H:%M:%SZ') }}"

- name: Write the report to disk as JSON for auditing / downstream automation
  copy:
    content: "{{ provisioning_report | to_nice_json }}"
    dest: "/opt/technova/reports/{{ validated_request.name }}-provisioning.json"
  delegate_to: localhost

- name: Email the provisioning report to the requester
  community.general.mail:
    host: smtp.technova.internal
    to: "{{ requester_email }}"
    subject: "VM {{ validated_request.name }} is ready — {{ vm_production_ip }}"
    body: "{{ provisioning_report | to_nice_json }}"
  ignore_errors: true
# ignore_errors: true — SMTP being down should not make Ansible report
# the whole provisioning job as FAILED. The VM is genuinely ready; the
# notification is a nice-to-have layered on top, not the source of truth.

🎯 Interview Questions — Chapter 3
Q1: Why isn't `status.phase == Running` enough to consider a VM "ready" for handoff?
Running only confirms the virt-launcher pod started QEMU — it says nothing about whether the guest OS finished booting, whether cloud-init finished applying the password/SSH-key config, or whether the guest agent is even installed and running. The AgentConnected VMI condition is the actual signal that the guest OS is up and reporting back, which is why the playbook gates on that condition, with a separate `until`/`retries` loop, before doing anything else.
Q2: Why validate the production-network IP as a separate, explicit step instead of assuming it will be there once AgentConnected is true?
AgentConnected only proves the guest agent process is running — it doesn't guarantee every expected interface got an address (a misconfigured NAD, DHCP exhaustion, or a VLAN issue can all leave an interface without an IP even on a fully booted guest). Explicitly filtering status.interfaces for the prod-net interface and asserting it has a non-empty IP catches that class of failure before the VM is handed to the requester as "ready."
Q3: Why use `ignore_errors: true` on the email notification task but not on the IP-validation assert?
These represent two different failure severities. A failed IP validation means the actual deliverable is broken — the VM isn't genuinely usable — so it must fail the whole job. A failed email means the notification channel is down, which is unrelated to whether the VM itself succeeded. Using `ignore_errors: true` only on the notification keeps the job's pass/fail status meaningful: it reflects the state of the VM, not the state of the SMTP server.
