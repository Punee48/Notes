Secrets Management Integration: AWS Secrets Manager + Terraform

01The Enterprise Problem This Solves

Project 7's RDS instance used manage_master_user_password = true and deferred the actual credential question to this project. Every enterprise Terraform codebase eventually has to answer: where does a database password, an API key, or a third-party service token actually live, if not in a variable, a .tfvars file, or hardcoded in a resource block? This project builds the pattern for generating, storing, and consuming secrets through AWS Secrets Manager, and addresses the detail almost every tutorial glosses over: Terraform state itself is not a safe place for a plaintext secret to live, even when the resource managing that secret is Secrets Manager.

02The Story: The Password That Was "Managed by Secrets Manager" and Also in Plaintext in State

Production Incident Replay A team migrates database credentials into AWS Secrets Manager, feeling good about the security improvement — no more password sitting in a terraform.tfvars file checked into a private repo. Months later, a routine security audit pulls the Terraform state file for review (state files are frequently included in compliance backup scopes) and finds the database password sitting in plaintext inside the state's resource attributes anyway — because the Secrets Manager secret's value was set via a aws_secretsmanager_secret_version resource whose secret_string argument, by design, gets recorded into state just like any other resource attribute Terraform manages. Moving the secret's storage location to Secrets Manager didn't remove it from the one file Terraform always keeps a full copy of. The fix requires two separate things working together: marking sensitive arguments so Terraform redacts them from CLI output and plan diffs, and encrypting the state backend itself (Project 1's S3 bucket encryption) so a copy of state at rest is not a plaintext secret dump on its own.

03Deep Technical Explanation

Secrets Manager as the runtime source of truth, not Terraform variables

The core pattern: Terraform creates the secret container (aws_secretsmanager_secret) and, for initial bootstrapping, a generated value, but applications read the actual secret value at runtime directly from Secrets Manager's API — never from a Terraform variable, environment variable baked at build time, or anything that would require a Terraform apply to rotate. This decouples "who can read this secret at runtime" (an IAM permission on the application's role) from "who can manage this secret's lifecycle in Terraform" (a much smaller set of people/pipelines).

Terraform's sensitive = true: what it actually protects, and what it doesn't

Marking a variable or output sensitive = true redacts it from CLI plan/apply output and from the UI in Terraform Cloud — but it does not encrypt or omit the value from the raw state file itself, which is exactly the gap in this project's story. State-level protection has to come from the backend (Project 1's S3 encryption + tightly scoped IAM read access to that bucket), not from the sensitive flag alone.

Generating strong initial values without hardcoding them

The random_password resource generates a cryptographically random value entirely within Terraform's own execution — never typed by a human, never appearing in a PR diff — and that generated value is what gets written into the Secrets Manager secret. It's still technically present in state (per the caveat above), which is precisely why backend encryption isn't optional.

Rotation: automating what used to be a manual, risky, forgotten task

Secrets Manager supports attaching a Lambda function that automatically rotates a secret's value on a schedule, coordinating with the target resource (like RDS) so the change happens without breaking active connections. This turns "rotate the database password" from a rare, risky, manually-coordinated event into a routine, automated one.

05Step-by-Step Implementation

envs/prod/secrets.tf 
resource "random_password" "db_master" {
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?" # excludes chars RDS's password rules reject
}

resource "aws_secretsmanager_secret" "db_master" {
  name                    = "prod/rds/master-credentials"
  recovery_window_in_days = 7 # soft-delete window — protects against an accidental destroy
  kms_key_id              = aws_kms_key.secrets.arn # customer-managed key, not the default AWS-managed one
}

resource "aws_secretsmanager_secret_version" "db_master" {
  secret_id = aws_secretsmanager_secret.db_master.id
  secret_string = jsonencode({
    username = "app_admin"
    password = random_password.db_master.result # this value lands in state — backend encryption is what protects it there
  })

  lifecycle {
    ignore_changes = [secret_string] # once rotation starts managing this, Terraform must stop fighting it
  }
}

# --- Narrow IAM policy: only THIS specific secret, only GetSecretValue,
# attached to the application's role, not the CI/deploy role. ---
data "aws_iam_policy_document" "read_db_secret" {
  statement {
    actions   = ["secretsmanager:GetSecretValue"]
    resources = [aws_secretsmanager_secret.db_master.arn]
  }
}

resource "aws_iam_role_policy" "app_read_db_secret" {
  name   = "app-read-db-secret"
  role   = aws_iam_role.web.id # the web tier's own role from Project 6/4, not a broader one
  policy = data.aws_iam_policy_document.read_db_secret.json
}

5.3 — Rotation Lambda association

envs/prod/secrets-rotation.tf 
resource "aws_secretsmanager_secret_rotation" "db_master" {
  secret_id           = aws_secretsmanager_secret.db_master.id
  rotation_lambda_arn = aws_lambda_function.rotate_db_secret.arn # AWS-provided rotation function template for RDS credentials

  rotation_rules {
    automatically_after_days = 30 # routine 30-day rotation — no human action required
  }
}

Plain-English walkthrough

random_password ensures no human ever types or sees the initial credential value — it's generated entirely inside Terraform's execution. The lifecycle { ignore_changes = [secret_string] } block on the secret version is essential the moment rotation is turned on: without it, Terraform would try to "fix" the secret's value back to its original state on every apply, fighting the rotation Lambda that's deliberately changing it every 30 days. The IAM policy granting GetSecretValue is scoped to exactly one secret ARN and attached only to the application's own role — the CI/deploy role from Project 8 has no read access to this secret at all, following Project 4's least-privilege pattern. The KMS key is customer-managed rather than the AWS default specifically so key access itself can be audited and scoped independently of Secrets Manager's own permissions.

06Failure Scenarios — What Breaks in Real Life

Failure: rotation Lambda updates the secret, Terraform tries to revert it Without the ignore_changes lifecycle block, the next terraform apply after a rotation event overwrites the freshly-rotated password back to the value in state, potentially breaking active connections using the new password. Debug: confirm ignore_changes is present on any secret version resource once rotation is enabled — this is the single most common way to break a working rotation setup.
Failure: state file access is broader than the secret's own IAM policy The application's IAM role is correctly scoped to read only this one secret, but someone with read access to the Terraform state S3 bucket can read the plaintext value directly out of state, bypassing the Secrets Manager IAM boundary entirely. Debug: this is why state bucket access (Project 1) has to be audited with the same rigor as secret access itself — a narrow Secrets Manager policy provides no protection if the backend storing that value in plaintext is broadly readable.
Failure: rotation breaks a connection pool that cached the old credential The rotation Lambda updates RDS and Secrets Manager successfully, but a long-lived application connection pool doesn't re-fetch the new credential until its next scheduled refresh, and starts failing authentication in the meantime. Debug: ensure application connection pools re-resolve credentials from Secrets Manager on a refresh interval shorter than the rotation window, or handle authentication failures with an automatic credential refetch-and-retry.

07Interview Talking Points

"How do you keep secrets out of Terraform state, given that Terraform has to manage them?"
Be precise about what's actually true here: you can't fully keep a managed secret's value out of state, but you can encrypt the backend (Project 1), scope state read access tightly, and mark the sensitive fields so at least CLI output and plan diffs never leak it — layered mitigation, not a single silver bullet.
"Walk me through how you'd set up automatic credential rotation without breaking live connections."
Describe the Lambda-based rotation flow and the essential ignore_changes lifecycle detail — Terraform must stop trying to reconcile a value it no longer owns the day-to-day truth of, once rotation takes over.
