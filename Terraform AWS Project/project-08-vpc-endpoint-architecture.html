VPC Endpoint Architecture — Keeping AWS Traffic Off the Internet

Every S3 read, every Secrets Manager call, every SSM Agent heartbeat from our private subnets has been quietly routing out through the NAT Gateway and back into AWS over the public internet path. Today we give each of those services a private, direct on-ramp into the VPC — and along the way, discover (and properly adopt) an endpoint someone already created by hand.

01 The Banking Story

This month's AWS bill review turned up something odd: NAT Gateway data processing charges in Production are nearly triple what the team expected for the current traffic volume. Digging in, it turns out every S3 request from the payments-api pods, every Secrets Manager rotation call from Project 06, and every Session Manager heartbeat from Project 07 has been leaving the VPC through the NAT Gateway, out to the public internet, and back into AWS's public endpoints for those services — a round trip that costs money and, worse, is a network path a banking security review will always ask uncomfortable questions about.

While investigating, an engineer discovered something else: an S3 Gateway endpoint already exists in the Production VPC — created by hand, months ago, by someone no longer on the team, entirely outside Terraform. It works, so nobody's touched it, but it's now an untracked, undocumented resource that could be silently deleted by anyone with console access.

Our manager's brief: "Build proper VPC Endpoints for S3, Secrets Manager, and SSM across every environment. And that orphaned endpoint someone made by hand — bring it under Terraform's management properly. Don't destroy and recreate it; that would cause a brief outage. Import it."

02 Business Requirement, Risk & Impact

Business Requirement

Traffic to core AWS services (S3, Secrets Manager, SSM) from private subnets must stay entirely within the AWS network, never routing over the public internet.

Customer Requirement

The Security team wants a demonstrable network diagram where private subnet traffic to AWS APIs has no public internet path at all — a specific control banking network reviews check for.

Current Infrastructure

NAT Gateways from Project 02 handle all outbound traffic, including calls to AWS's own public service endpoints; one hand-created, untracked S3 Gateway endpoint exists in Production.

Existing Manual Process

None formalized — the one existing endpoint was a one-off fix by an engineer who is no longer with the team, with no record of why or how it was created.

Problems With Current Process

  • Unnecessary NAT Gateway data processing costs for traffic that never needed to leave AWS's network
  • An untracked, manually created resource that Terraform doesn't know about and could conflict with
  • A public-internet-adjacent network path for security-sensitive API calls (Secrets Manager, SSM)

Business Challenges

Banking network security reviews specifically look for AWS API traffic staying within the AWS network backbone — the current NAT-routed path doesn't clearly demonstrate that.

Risk Analysis

Medium: the untracked manual endpoint is a small but real risk — anyone with console access could delete it, and if we later run Terraform apply and try to create a duplicate S3 endpoint (a VPC can normally only have one Gateway endpoint per service), the apply would fail with a confusing error.

Business Impact

Unplanned NAT Gateway cost overruns compound across every environment and every month; the untracked resource is a small governance gap an audit would flag.

03 Why VPC Endpoints, and What We Rejected

Why VPC Endpoints (PrivateLink)

A VPC Endpoint creates a private, direct path from inside the VPC to a specific AWS service — Gateway endpoints (S3, DynamoDB) work via route table entries at no additional cost; Interface endpoints (Secrets Manager, SSM, most other services) create an Elastic Network Interface with a private IP directly in your subnets, backed by AWS PrivateLink. Either way, traffic never touches the public internet or a NAT Gateway.

Alternatives considered, and why they were rejected

Destroy and recreate the orphaned manual endpointSimplest to implement in TerraformWould cause a brief but real service disruption for anything currently using it — terraform import achieves the same end state with zero downtime

04 Terraform Concepts You Must Understand Before We Build

Importing Existing Infrastructure

What it is: bringing a resource that already exists in AWS — but was never created by Terraform — under Terraform's management, so it appears in state and future applies can manage it, without destroying and recreating the real resource.

Why it exists: infrastructure created by hand, by a different tool, or before Terraform adoption doesn't just disappear — import lets you adopt it into IaC management going forward without any outage.

Two ways to do it: the classic terraform import <address> <id> CLI command (imperative, run once, not saved anywhere), and the modern declarative import block (Terraform 1.5+, written directly in a .tf file and version-controlled, so the import is visible and repeatable in code review).

Critical nuance: importing only brings the resource into state — it does NOT generate the matching HCL configuration for you automatically (older Terraform versions) or does so only with terraform plan -generate-config-out (newer versions). Either way, you must carefully write configuration that matches the real resource's actual settings, or the very next plan will show unexpected changes.

Common mistake: importing a resource into state without first writing matching configuration — the next terraform plan then shows a huge, confusing diff trying to "fix" real infrastructure to match empty or incorrect config.

Reinforcing for_each — a Map of Endpoint Definitions

What it is: rather than writing three nearly-identical aws_vpc_endpoint resource blocks (one each for Secrets Manager, SSM, SSM Messages), we define one structured map variable and let a single resource block with for_each create all three — the same complex-variable pattern from Project 02's subnets, applied here to interface endpoints.

Why it matters here specifically: AWS regularly adds new services needing an Interface endpoint (SSM added a second one, "EC2 Messages", after SSM itself) — with for_each over a map, adding a fourth service is a one-line variable change, not a new resource block to write and maintain.

Data Sources — Reusing Route Table IDs from Project 02

What it is: the S3 Gateway endpoint needs to be associated with every private and database route table so instances in those subnets can reach S3 privately — we pull those route table IDs from Project 02's vpc-framework module outputs rather than re-declaring them.

05 AWS Concepts: Gateway vs. Interface Endpoints

Gateway Endpoints (S3, DynamoDB only)

Implemented as a route table target, not a network interface — traffic to S3 is redirected privately at the routing layer. No hourly charge, no data processing charge, and no private DNS configuration needed.

Interface Endpoints (everything else)

Creates an Elastic Network Interface with a private IP in your chosen subnets, backed by AWS PrivateLink. Charged per-hour per endpoint plus per-GB data processed — still typically far cheaper than the NAT Gateway data processing it replaces.

Private DNS

Enabling private_dns_enabled on an Interface endpoint means the standard AWS service hostname (e.g. secretsmanager.ap-south-1.amazonaws.com) resolves to the endpoint's private IP automatically — no application code changes needed at all.

Security

Interface endpoints get their own security group — scope it to allow inbound HTTPS only from the VPC's own CIDR, so only resources inside this VPC can use the endpoint.

High Availability

Deploy Interface endpoint network interfaces across the same multiple AZs as your application subnets — an endpoint only in one AZ becomes a single point of failure for every service that depends on it.

Cost

Gateway endpoints are free; Interface endpoints cost roughly $0.01/hour per AZ plus a small per-GB fee — still typically a net cost reduction once NAT Gateway data processing charges for the same traffic are removed.

Limitations

Not every AWS service supports Interface endpoints, and Gateway endpoints exist only for S3 and DynamoDB — always check AWS's current PrivateLink service list before assuming an endpoint is available for a given service.

09 Implementation — Full Production Code

environments/prod/vpc-endpoints.tf — S3 Gateway Endpoint (to be imported)

environments/prod/vpc-endpoints.tf (excerpt)
resource "aws_vpc_endpoint" "s3_gateway" {                          # Configuration written to match the EXISTING manually created endpoint exactly
  vpc_id            = var.vpc_id
  service_name      = "com.amazonaws.${var.aws_region}.s3"
  vpc_endpoint_type = "Gateway"                                       # Must match the real endpoint's type — S3 supports both, but this one was created as Gateway

  route_table_ids = concat(                                            # concat() merges the private and database route table ID lists from Project 02 into one list
    var.private_route_table_ids,
    var.database_route_table_ids
  )

  tags = {
    Name    = "s3-gateway-endpoint"
    Adopted = "true"                                                    # Documents in the resource itself that this was imported, not originally created by Terraform
  }
}

environments/prod/vpc-endpoints.tf — Interface Endpoints via for_each

environments/prod/vpc-endpoints.tf (excerpt)
variable "interface_endpoints" {                                     # Complex variable — one entry per Interface endpoint to create
  type = map(object({
    service_name_suffix = string                                       # e.g. "secretsmanager", appended to the standard com.amazonaws.. prefix
  }))
  default = {
    secretsmanager = { service_name_suffix = "secretsmanager" }
    ssm            = { service_name_suffix = "ssm" }
    ssmmessages    = { service_name_suffix = "ssmmessages" }           # Required alongside "ssm" for Session Manager's interactive channel specifically
  }
}

resource "aws_security_group" "vpc_endpoints" {
  name   = "vpc-interface-endpoints-sg"
  vpc_id = var.vpc_id

  ingress {
    from_port   = 443                                                   # PrivateLink endpoints communicate over HTTPS only
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = [var.vpc_cidr]                                        # Scoped to ONLY this VPC's own CIDR — nothing outside it can reach these endpoints
  }
}

resource "aws_vpc_endpoint" "interface" {
  for_each            = var.interface_endpoints                        # One resource instance per map entry — keyed by name, safe to add a 4th service later
  vpc_id              = var.vpc_id
  service_name        = "com.amazonaws.${var.aws_region}.${each.value.service_name_suffix}"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = var.private_subnet_ids                          # Deployed across every private-tier AZ for high availability
  security_group_ids  = [aws_security_group.vpc_endpoints.id]
  private_dns_enabled = true                                            # Lets existing application code keep using the standard AWS hostname with zero changes

  tags = { Name = "vpce-${each.key}" }
}

environments/prod/outputs.tf

environments/prod/outputs.tf
output "interface_endpoint_ids" {
  value = { for k, ep in aws_vpc_endpoint.interface : k => ep.id }
}

10 Importing the Existing Endpoint — Step by Step

Before touching anything, find the real endpoint's ID from the AWS console or CLI, and read its exact current configuration — this is the configuration your .tf file above must match precisely.

terminal — discover the real endpoint's settings
aws ec2 describe-vpc-endpoints --filters "Name=service-name,Values=com.amazonaws.ap-south-1.s3" \
  --query "VpcEndpoints[*].{Id:VpcEndpointId,RouteTables:RouteTableIds,Tags:Tags}"

Modern approach: declarative import block (Terraform 1.5+)

environments/prod/imports.tf
import {
  to = aws_vpc_endpoint.s3_gateway                                    # Must match the resource address in vpc-endpoints.tf exactly
  id = "vpce-0abc123def456789a"                                        # The real endpoint's ID, discovered via the AWS CLI command above
}
Keeping the import declared in a version-controlled import block (rather than running the imperative terraform import CLI command once, by hand, and never recording it) means any teammate, or a fresh CI/CD run, can reproduce exactly how this resource was adopted — a real audit-trail advantage for a banking codebase.

Verifying before applying

terminal
terraform plan
# Expected: "Terraform will perform the following actions: ... 0 to add, 0 to change, 0 to destroy"
# If the plan shows CHANGES to the endpoint, your .tf configuration doesn't yet match reality —
# fix the config, do NOT apply a plan that would modify a resource you just discovered and imported.
terraform apply   # Only once the plan is clean — this writes the import into state with no infrastructure change

Legacy approach, for comparison

terminal (older Terraform versions, or a one-off fix)
terraform import aws_vpc_endpoint.s3_gateway vpce-0abc123def456789a
The legacy CLI command achieves the same result but leaves no trace in version control — a teammate reviewing the Git history later would have no idea this resource was ever imported rather than created by apply. Prefer the import block for anything going through code review.

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
vpc_endpoint_type = "Gateway"Must exactly match the type of the real, pre-existing endpoint being importedGuessing "Interface" because that's more common for other services — S3's existing endpoint here was specifically created as Gateway; import fails or shows drift if the type doesn't match
concat(private_route_table_ids, database_route_table_ids)Merges two lists into one, used as the Gateway endpoint's full set of associated route tablesOnly associating the private route tables and forgetting database — database-tier instances needing S3 access (e.g. for backups) would then fail to reach it privately
private_dns_enabled = trueMakes the endpoint transparent to existing application code using the standard service hostnameLeaving this false — applications would need code changes to use the endpoint's specific DNS name instead of the standard AWS hostname
import { to = ..., id = ... }Declares an import as part of the configuration itself, applied on the next terraform applyLeaving the import block in the codebase permanently after the import succeeds — remove it once applied, since it has no further purpose and re-running it against an already-imported resource is a harmless no-op but unnecessary clutter

11 Execution Flow, Explained Internally

terraform plan with an import block present

Terraform reads the real resource's current state from AWS, compares it against your written configuration, and shows the import as a state action separate from any configuration drift — a clean import shows the resource being added to state with no attribute changes.

terraform apply — import step

Writes the resource into state exactly as read from AWS; if your configuration doesn't match, this step can still succeed at importing while leaving a subsequent drift that the next plan will want to "correct" — always verify a clean plan first.

terraform apply — new Interface endpoints

Creates the security group first (no dependency on anything else), then all three Interface endpoints in parallel via for_each, since none of them depend on each other.

Never apply an import alongside unrelated infrastructure changes in the same apply — isolate the import to its own review and apply, so if anything about the imported resource's configuration is subtly wrong, it's easy to identify and doesn't get tangled up with unrelated changes.

12 CI/CD Integration

.github/workflows/terraform-vpc-endpoints.yml
name: terraform-vpc-endpoints
on:
  pull_request:
    paths: ["environments/prod/vpc-endpoints.tf", "environments/prod/imports.tf"]

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - name: Plan
        run: terraform plan -no-color | tee plan.txt
      - name: Fail if the import would change the resource
        run: |                                                          # Extra safety net: block merge if the import isn't a clean, zero-change adoption
          if grep -q "~ resource \"aws_vpc_endpoint\" \"s3_gateway\"" plan.txt; then
            echo "Import would modify the existing endpoint — configuration doesn't match reality. Fix before merging."
            exit 1
          fi

14 Interview Preparation

Q: What's the difference between a Gateway and an Interface VPC endpoint?
Gateway endpoints (S3, DynamoDB only) work as a route table target with no hourly cost; Interface endpoints create an actual network interface with a private IP via AWS PrivateLink, supporting most other AWS services, and incur an hourly plus per-GB charge.
Q: How do you safely import an existing resource without causing downtime or unwanted changes?
Read the real resource's exact current configuration first, write matching Terraform configuration, use an import block (or the import CLI command) to bring it into state, then run terraform plan and confirm it shows zero changes before ever applying anything further.
Q: Does terraform import generate the HCL configuration for you?
Not by default — classic import only writes to state; you must write matching configuration yourself, or use the newer plan -generate-config-out flag to have Terraform draft a starting configuration you still need to review.
Q: Why put multiple Interface endpoints in one for_each block instead of separate resources?
It keeps the code DRY and makes adding a new required service endpoint (which AWS does periodically) a one-line variable change instead of a new resource block to write and maintain.
Manager round: How would you find every piece of infrastructure that exists outside Terraform's management today?
Run a drift/discovery tool like AWS Config's resource inventory or a Terraform-aware scanner against each account, cross-reference against terraform state list per environment, and treat any gap as a candidate for the same import workflow used here.
