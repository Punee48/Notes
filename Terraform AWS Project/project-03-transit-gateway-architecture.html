PROJECT 03 OF 40 · INTERMEDIATE

Transit Gateway Architecture — Connecting Every Account

We now have a versioned VPC framework running in four separate AWS accounts. None of them can talk to each other, and none can reach the on-prem data center. Today we build the hub that connects them all — safely, and without a single VPC peering connection to maintain.

01 The Banking Story

The Digital Banking Platform now has four live VPCs, each built from our Project 02 framework: Dev, UAT, Production, and Shared Services — each in its own AWS account, for blast-radius isolation. That isolation is working exactly as intended: they are so isolated that the new payments microservice in Production cannot reach the shared Active Directory servers sitting in the Shared Services account, and none of them can reach the on-prem core banking system over the existing Direct Connect link.

The naive fix — VPC peering between every pair of VPCs — was rejected in the design review. Peering connections don't transitively route (Dev-to-SharedServices and SharedServices-to-Prod peering doesn't let Dev reach Prod), and with 8 planned accounts by year end, that's up to 28 peering connections to create and maintain by hand.

Our manager's brief: "Build one central hub that every account connects to once. Use AWS's native cross-account sharing so we're not copying account IDs and resource ARNs into Slack messages every time we onboard a new account."

02 Business Requirement, Risk & Impact

Business Requirement

Every current and future AWS account must be able to reach Shared Services and the on-prem data center through one consistent, centrally governed network path.

Customer Requirement

Application teams need this connectivity to "just exist" — they should never need to request or configure a peering connection themselves.

Current Infrastructure

Four isolated VPCs (Dev, UAT, Prod, Shared Services) from Project 02, plus an existing Direct Connect link from the on-prem data center into the Shared Services account only.

Existing Manual Process

None yet — this is a brand-new capability. The "manual" alternative under discussion was ad hoc VPC peering requested per team, per pair of accounts.

Problems With a Peering-Based Approach

  • No transitive routing — connectivity has to be built pairwise, growing quadratically as accounts are added
  • Peering connections must each be individually accepted and have their own route table entries maintained
  • No single place to apply a network-wide firewall or inspection policy later

Business Challenges

The bank's security team requires a single, auditable network chokepoint between environments — not a mesh of point-to-point links nobody can reason about as a whole.

Risk Analysis

Medium: a hub misconfiguration could either cut off legitimate connectivity (availability risk) or, worse, accidentally allow Dev to route to Production (security risk) — route table design must be deliberate and reviewed.

Business Impact

Without this hub, the new payments microservice cannot reach Active Directory for authentication — a hard blocker for the platform's next release milestone.

03 Why Transit Gateway, and What We Rejected

Why AWS Transit Gateway

Transit Gateway acts as a managed regional router: every VPC attaches to it once, and Transit Gateway route tables decide who can reach whom — centrally, in one place, instead of scattered across dozens of peering connection route table entries. It also natively extends to the Direct Connect link, giving on-prem the same one-hub-many-spokes model as the cloud accounts.

Alternatives considered, and why they were rejected

AlternativeWhy consideredWhy rejected for ABC Bank
Full-mesh VPC PeeringNo extra AWS service or costNo transitive routing, and grows quadratically — unmanageable past a handful of accounts
AWS Cloud WANNewer, global-scale alternative to Transit GatewayABC Bank's entire footprint is one region today — Cloud WAN's multi-region orchestration is more than this stage needs; revisit when the DR region project goes live
Software VPN mesh (e.g. self-managed WireGuard)Cloud-agnostic, works identically on-prem and in AWSAdds operational burden (patching, HA, key rotation) that a managed AWS service removes entirely — not justified given Transit Gateway already meets the requirement

04 Terraform Concepts You Must Understand Before We Build

Data Sources

What it is: a data block reads information about a resource that already exists — created by Terraform elsewhere, by another team, or manually — without Terraform trying to manage or change it.

Why it exists: the Transit Gateway is created once, in the Shared Services account; every other account's Terraform needs to reference its ID to create an attachment, without ever being allowed to create or destroy the Transit Gateway itself.

Production example: the Dev account's Terraform uses data "aws_ec2_transit_gateway" to look up the Transit Gateway by tag, rather than hardcoding its ID as a string — so the same code works identically if the Transit Gateway is ever recreated.

Common mistake: hardcoding a resource ID (like tgw-0123456789abcdef0) directly into a downstream account's code — it works until that resource is recreated, then every downstream account silently breaks.

terraform_remote_state Data Source

What it is: a special data source that reads another root module's outputs directly from its remote state file (the S3 backend from Project 01), instead of that value being manually copied between teams.

Why it exists: the Shared Services account's Terraform run produces the Transit Gateway ID as an output. Rather than Slack-pasting that ID into four other accounts' tfvars files, each account's Terraform reads it directly and automatically stays in sync if it ever changes.

Internal working: at plan time, Terraform performs a read-only fetch of the specified state file from S3 and exposes its output values under data.terraform_remote_state.<name>.outputs.<output_name>.

Best practice: only use this for read-only cross-account references to intentionally-exported outputs — never as a substitute for a properly versioned module input, and never across a trust boundary the reading account isn't authorized to see.

Provider Aliases & Multi-Account Configuration

What it is: the alias argument on a provider block lets one Terraform configuration talk to more than one AWS account or region at once, by assuming a different IAM role per aliased provider.

Why it exists: accepting a Resource Access Manager (RAM) share and creating a Transit Gateway attachment technically happens in the spoke account, while the Transit Gateway itself lives in the hub (Shared Services) account — one Terraform run may need to act in both.

Production example: provider "aws" { alias = "shared_services" } assumes a cross-account IAM role into the Shared Services account purely to read the RAM share status, while the default (unaliased) provider manages resources in the spoke account itself.

Locals for Route Aggregation

What it is: a locals block used here to pre-compute the set of CIDR ranges each spoke account should route to the Transit Gateway, based on a shared map of environment-to-CIDR that lives in one place.

Why it exists: without a computed local, every spoke account's route table code would need to list every other account's CIDR by hand — exactly the kind of copy-paste drift Project 02 already taught us to avoid.

05 AWS Concepts: Transit Gateway & Resource Access Manager

What is Transit Gateway

A regional, managed router that VPCs and VPN/Direct Connect connections attach to. Traffic between two attachments is controlled by Transit Gateway route tables, not by the VPCs themselves.

Why it exists

It replaces a full mesh of point-to-point connections with a hub-and-spoke model, and lets a single team centrally control which spokes can reach which — critical for a bank that must prove Dev cannot reach Production.

What is AWS RAM

Resource Access Manager lets the Shared Services account share the Transit Gateway with other AWS accounts in the same AWS Organization, without those accounts needing their own copy of it or any cross-account IAM role for the attachment itself.

High Availability

Transit Gateway is inherently multi-AZ within a region; each VPC attachment should still specify subnets in at least two AZs for resilience.

Security

Multiple Transit Gateway route tables (not just one) let us put Dev/UAT in one route table that cannot reach Production's route table, while all three can reach Shared Services — enforced by AWS, not by convention.

Pricing

Charged per attachment-hour plus per-GB data processed through the Transit Gateway — worth monitoring as more accounts and higher-throughput workloads attach.

Limitations

Transit Gateway is regional — connecting to a second AWS region requires a peering attachment between two Transit Gateways, a topic for the Multi-Region DR project later in this series.

Best Practice

Use separate Transit Gateway route tables per trust boundary (e.g. "non-prod" and "prod") rather than one flat route table for every attachment.

07 Complete Solution Design

The Transit Gateway itself, its two route tables (non-prod and prod), and the RAM share are created once, in the Shared Services account's root module. Every spoke account (Dev, UAT, Prod) runs its own small root module that reads the Transit Gateway's ID via terraform_remote_state, accepts the RAM share, creates its own VPC attachment, and associates that attachment with the correct Transit Gateway route table.

Dev and UAT attachments associate with the non-prod Transit Gateway route table; Production associates with the prod route table. Shared Services associates with both, since it must be reachable from every environment.
  • Hub module (Shared Services account): Transit Gateway, two TGW route tables, RAM resource share, RAM principal associations for each spoke account ID.
  • Spoke module (Dev/UAT/Prod accounts): RAM share accepter, VPC attachment using subnet IDs from the Project 02 framework's output, TGW route table association, and a VPC route table entry (using the extra_routes hook we built into Project 02's routing module) pointing other environments' CIDRs at the Transit Gateway.

09 Implementation — Full Production Code

environments/shared-services/main.tf (the hub)

environments/shared-services/main.tf
resource "aws_ec2_transit_gateway" "hub" {                 # The central router every account will attach to
  description                    = "ABC Bank central Transit Gateway"
  amazon_side_asn                = 64512                    # Private ASN required by BGP — must not clash with the on-prem router's ASN
  default_route_table_association = "disable"                # We manage associations explicitly per route table — safer than the implicit default
  default_route_table_propagation = "disable"                # Same reasoning — explicit propagation only, nothing implicit
  tags = { Name = "abc-bank-tgw" }
}

resource "aws_ec2_transit_gateway_route_table" "non_prod" {  # Dev + UAT live here — cannot reach the prod route table
  transit_gateway_id = aws_ec2_transit_gateway.hub.id
  tags = { Name = "tgw-rt-non-prod" }
}

resource "aws_ec2_transit_gateway_route_table" "prod" {       # Production's isolated route table
  transit_gateway_id = aws_ec2_transit_gateway.hub.id
  tags = { Name = "tgw-rt-prod" }
}

resource "aws_ram_resource_share" "tgw_share" {               # Makes the Transit Gateway shareable with other accounts in the Organization
  name                      = "abc-bank-tgw-share"
  allow_external_principals = false                            # Restricts sharing to accounts INSIDE our AWS Organization only
}

resource "aws_ram_resource_association" "tgw" {                # Attaches the actual Transit Gateway resource to the share
  resource_arn       = aws_ec2_transit_gateway.hub.arn
  resource_share_arn = aws_ram_resource_share.tgw_share.arn
}

resource "aws_ram_principal_association" "spoke_accounts" {    # One association per spoke AWS account ID allowed to use the share
  for_each           = toset(var.spoke_account_ids)             # Keyed by account ID string — safe to add/remove accounts later
  principal          = each.value
  resource_share_arn = aws_ram_resource_share.tgw_share.arn
}

modules/tgw-spoke-attachment/main.tf

modules/tgw-spoke-attachment/main.tf
resource "aws_ec2_transit_gateway_vpc_attachment" "this" {   # Connects this spoke VPC to the shared Transit Gateway
  transit_gateway_id = var.transit_gateway_id
  vpc_id              = var.vpc_id
  subnet_ids          = var.attachment_subnet_ids

  transit_gateway_default_route_table_association = false      # We associate explicitly below, matching the hub's disabled defaults
  transit_gateway_default_route_table_propagation = false
}

resource "aws_ec2_transit_gateway_route_table_association" "this" {  # Puts this attachment into the correct route table (non-prod or prod)
  transit_gateway_attachment_id = aws_ec2_transit_gateway_vpc_attachment.this.id
  transit_gateway_route_table_id = var.tgw_route_table_id
}

resource "aws_ec2_transit_gateway_route_table_propagation" "this" {  # Lets this VPC's CIDR be learned by the route table it's associated with
  transit_gateway_attachment_id = aws_ec2_transit_gateway_vpc_attachment.this.id
  transit_gateway_route_table_id = var.tgw_route_table_id
}

resource "aws_route" "to_tgw" {                                 # Adds routes IN the VPC's own route tables pointing remote CIDRs at the TGW
  for_each = { for pair in setproduct(var.vpc_route_table_ids, var.remote_cidrs) :
               "${pair[0]}-${pair[1]}" => pair }                 # setproduct() creates every combination of route table x remote CIDR

  route_table_id         = each.value[0]
  destination_cidr_block = each.value[1]
  transit_gateway_id     = var.transit_gateway_id
}

environments/dev/main.tf
data "terraform_remote_state" "shared_services" {              # Reads the hub account's outputs directly from its S3 state file
  backend = "s3"
  config = {
    bucket = "abc-bank-terraform-state-2026"                     # Same bucket every project uses, from Project 01
    key    = "network/transit-gateway/terraform.tfstate"          # The specific state file the Shared Services account wrote to
    region = "ap-south-1"
  }
}

resource "aws_ram_resource_share_accepter" "tgw" {               # Dev account explicitly accepts the RAM invitation before it can attach
  share_arn = data.terraform_remote_state.shared_services.outputs.tgw_share_arn
}

module "tgw_attachment" {                                        # Our reusable spoke module from above
  source = "../../modules/tgw-spoke-attachment"

  transit_gateway_id     = data.terraform_remote_state.shared_services.outputs.transit_gateway_id
  tgw_route_table_id     = data.terraform_remote_state.shared_services.outputs.non_prod_route_table_id  # Dev goes into the NON-PROD table
  vpc_id                  = module.vpc.vpc_id                       # From Project 02's vpc-framework module, already in this same file
  attachment_subnet_ids   = module.vpc.subnet_ids_by_tier["private"]
  vpc_route_table_ids     = module.vpc.private_route_table_ids
  remote_cidrs            = ["10.30.0.0/16", "10.40.0.0/16"]       # Shared Services and on-prem CIDR ranges — Dev does NOT get Production's CIDR here

  depends_on = [aws_ram_resource_share_accepter.tgw]                # Explicit ordering: must accept the share before creating an attachment against it
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
default_route_table_association = "disable"Turns off Transit Gateway's automatic default route table so every association is explicit and reviewableLeaving the default enabled — every new attachment silently joins one flat route table with no segmentation
data "terraform_remote_state"Reads another root module's outputs straight from its state file in S3Forgetting the reading account's IAM role needs s3:GetObject permission on that specific state file — a cross-account permissions gap, not a Terraform bug
setproduct(a, b)Terraform function producing every combination pair from two lists — used to add a route in every VPC route table for every remote CIDRUsing nested for loops by hand instead — setproduct is clearer and less error-prone for this exact "every combination" need
depends_on = [aws_ram_resource_share_accepter.tgw]Forces explicit ordering where Terraform's automatic dependency graph can't infer it from a direct referenceOmitting it and hoping ordering works out — RAM acceptance and attachment creation aren't linked by any resource attribute reference, so Terraform needs the hint

11 Execution Flow, Explained Internally

Apply order across accounts

Shared Services must be applied first — its outputs are what every spoke account's terraform_remote_state data source reads. There is no way to apply a spoke before the hub exists.

terraform plan (spoke account)

Terraform performs a read-only fetch of the hub's state file during planning — if the hub's state changed since your last plan, your plan reflects the newest values automatically.

terraform apply (spoke account)

Accepts the RAM share, then (respecting depends_on) creates the VPC attachment, associates and propagates it into the correct TGW route table, then adds routes into the VPC's own route tables.

terraform destroy (spoke account)

Removes the VPC's routes to the TGW first, then the route table association/propagation, then the attachment itself — the reverse of creation order, computed automatically from the dependency graph.

Never destroy the hub's Transit Gateway while spoke attachments still reference it — always tear down every spoke first, or Terraform (correctly) will refuse the deletion.

12 CI/CD Integration — Ordered Pipeline

.github/workflows/terraform-network.yml
name: terraform-network
on:
  push:
    branches: [main]
    paths: ["environments/shared-services/**", "environments/dev/**", "environments/uat/**", "environments/prod/**"]

jobs:
  shared-services:                                              # Hub MUST run first — nothing else can succeed without its outputs
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/shared-services } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve

  dev-attachment:                                                # Waits for shared-services to finish before running
    needs: shared-services
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/dev } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve

  prod-attachment:                                                # Also waits on shared-services, but NOT on dev — they can run in parallel after the hub
    needs: shared-services
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve
Use the pipeline's own job-dependency graph (needs:) to mirror Terraform's cross-account dependency — the hub job gates every spoke job, exactly like terraform_remote_state gates it inside the code.

14 Interview Preparation

Q: Why Transit Gateway instead of VPC peering for a multi-account setup?
Peering doesn't route transitively and grows quadratically with account count; Transit Gateway is a single hub every account attaches to once, with centrally managed route tables controlling who reaches whom.
Q: How do you stop Dev from reaching Production through a shared hub?
Use separate Transit Gateway route tables per trust boundary — associate Dev/UAT attachments with a non-prod table and Production with a separate prod table that has no route back to non-prod.
Q: What does terraform_remote_state actually do, and what are its limits?
It performs a read-only fetch of another state file's outputs at plan time — it requires read access to that exact state object, and only exposes values the source module explicitly declared as outputs, nothing else in that state.
Q: Why disable Transit Gateway's default route table association and propagation?
The defaults implicitly put every new attachment into one shared route table — disabling them forces every association to be an explicit, reviewable Terraform resource, which matters for a bank's change-audit requirements.
Manager round: Production incident — Dev suddenly can reach Prod resources. How would you investigate?
Check the Transit Gateway route table associations first (has an attachment been placed in the wrong route table), then check VPC route tables for an unexpected route to the TGW with too broad a destination CIDR — the two most common causes of this exact class of incident.
