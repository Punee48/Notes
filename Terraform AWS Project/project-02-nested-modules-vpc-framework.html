PROJECT 02 OF 40 · INTERMEDIATE

Nested Modules & a Versioned, Registry-Style VPC Framework

Project 01 gave the team a safe place to store state. Now we give them a safe, reusable way to actually build network infrastructure — a VPC module built from smaller nested modules, published with semantic version tags so 39 future projects can consume it without copy-pasting a single line.

01 The Banking Story

Two weeks after we fixed the state-locking incident, ABC Bank's Digital Banking Platform program is ready to provision its first real network: a multi-tier VPC with public, private, and database subnets spread across three Availability Zones in ap-south-1.

Here's the catch: this same VPC pattern will be needed at least eight more times — once for Dev, once for UAT, once for Production, once for the Shared Services account, and again for a Disaster Recovery region. If we hand-write the VPC each time, a single subnetting mistake made once will be repeated eight times, and a future fix (like adding a fourth AZ) means editing eight separate copies.

Our manager's instruction this time: "Don't build a VPC. Build the thing that builds VPCs — properly modularized, properly versioned, so any engineer on any of our eight AWS accounts can pull an exact, tested version of it."

02 Business Requirement, Risk & Impact

Business Requirement

Every AWS account in the ABC Bank estate needs an identical, compliant network pattern, with zero hand-editing per account.

Customer Requirement

Application teams need predictable subnet layouts so their EKS clusters, RDS instances, and load balancers always land in the correct tier without guesswork.

Current Infrastructure

One hand-built VPC exists in the Dev account from before this program started, with subnet CIDRs chosen ad hoc and no documentation of which subnet is "public" versus "private."

Existing Manual Process

Whoever provisions the next account's VPC opens the Dev account's Terraform code, copies it into a new folder, and manually edits CIDR ranges and AZ names.

Problems With Current Process

  • Copy-paste drift: each copy silently diverges over time
  • A bug fix in one account's VPC code never reaches the other seven copies
  • No enforced naming or tagging standard across accounts

Business Challenges

Regulators expect consistent network segmentation (public/private/data tiers) across every environment that touches customer data — copy-paste drift makes that consistency unverifiable.

Risk Analysis

Medium-High: a manually copied VPC could accidentally place a database subnet's route table with a route to the Internet Gateway — a serious security exposure in a banking network.

Business Impact

A misconfigured subnet found during a security audit could delay the go-live of an entire environment while it's remediated and re-audited.

03 Why Nested Modules, Why Versioning, and What Else We Considered

Why nested modules (not one big flat module)

A single flat VPC module that creates everything inline becomes hundreds of lines long and hard to test in isolation. By splitting into small nested modules — subnets, routing, nat-gateway — each piece can be understood, tested, and reused on its own, while the top-level vpc-framework module composes them the way a recipe combines smaller prepared components.

Why Git-tag module versioning

If every account's backend.tf/main.tf references the module by a floating branch (like main), a change merged for the Dev account's convenience could silently break Production the next time someone runs terraform init -upgrade there. A Git tag (e.g. v1.2.0) freezes an exact, tested snapshot of the module that an account can upgrade to deliberately, on its own schedule.

04 Terraform Concepts You Must Understand Before We Build

Nested Modules

What it is: a module that itself calls other child modules, instead of only declaring raw resources. Our vpc-framework module doesn't create subnets directly — it calls a subnets module, which calls nothing further, keeping the nesting shallow and readable.

Why it exists: it lets you compose small, independently testable building blocks into a larger reusable pattern, mirroring how the VPC itself is naturally composed of smaller concerns (subnetting, routing, NAT).

Internal working: Terraform builds one combined dependency graph across all nesting levels — a resource in the routing child module can depend on an output from the subnets child module, and Terraform sequences the API calls correctly regardless of which module "owns" each resource.

Best practice: keep nesting to 2 levels deep at most (root → framework module → concern module). Terraform technically allows deeper nesting, but every extra level makes debugging a "why wasn't this created" question much harder.

Common mistake: reaching into a nested child module's internal resource directly from the root (e.g. module.vpc_framework.module.subnets.aws_subnet.private) instead of exposing it through an explicit output — this breaks the moment the inner module's implementation changes.

Module Versioning (Git Tags & ref=)

What it is: pinning a module's source to an exact Git commit or tag using ?ref=vX.Y.Z, instead of a mutable branch name.

Why it exists: without a pin, every terraform init -upgrade silently pulls whatever the latest commit on that branch happens to be — an account could be upgraded by accident.

Internal working: Terraform clones the Git repository at that exact ref into its local module cache (.terraform/modules) during init; changing the version means changing the ref and re-running init.

Production example: Production's main.tf pins ref=v1.2.0; when we later fix a bug and tag v1.3.0, Dev and UAT can adopt it immediately while Production stays on v1.2.0 until its own change window.

Best practice: follow semantic versioning — a patch release (v1.2.1) never changes required variables; a major release (v2.0.0) is allowed to introduce breaking changes, clearly documented in a CHANGELOG.

Count vs. for_each

What they are: both are meta-arguments that create multiple copies of a resource or module block from a single piece of code.

Why for_each is preferred for our subnets: count creates resources indexed 0,1,2 — if the middle AZ is ever removed from the list, Terraform sees it as "index 1 changed" and can destroy/recreate the wrong subnet. for_each keys each resource by a stable string (the AZ name itself), so removing one AZ only destroys that AZ's subnet, leaving the others untouched.

Production example: we use for_each = toset(var.availability_zones) to create one private subnet per AZ, keyed by the AZ name, not a numeric index.

Common mistake: using count = length(var.availability_zones) for anything that might be reordered or shrunk later — it looks identical to for_each in a plan with no changes, but behaves very differently the moment the list changes.

Dynamic Blocks

What it is: a way to generate a repeatable nested block (like a route table's multiple route blocks) from a list or map, instead of writing each one out by hand.

Why it exists: a private route table might need zero, one, or several routes depending on the environment (e.g. an extra route to a Transit Gateway only in Production) — a dynamic block lets that vary without maintaining separate .tf files per environment.

Production example: our routing module uses a dynamic "route" block driven by a var.extra_routes list, so Production can add a Transit Gateway route later without touching the module's code at all — only its input variables.

Complex Variables, Validation & Conditional Expressions

Complex variable: a variable typed as a list of objects, e.g. list(object({ name = string, cidr = string })), letting us pass structured subnet definitions instead of several parallel flat lists that could get out of sync with each other.

Variable validation: a validation block inside a variable that rejects bad input at plan time — for example, refusing a CIDR block that isn't a valid subnet of the VPC's overall range.

Conditional expression: Terraform's condition ? true_value : false_value syntax, used here to decide whether to create a NAT Gateway per-AZ (expensive, highly available) or a single shared NAT Gateway (cheaper, for non-production).

05 AWS Concepts: The Multi-Tier VPC Pattern

What / Why (3-Tier Subnetting)

Public subnets host only load balancers and NAT Gateways; private subnets host application workloads (EKS, EC2); database subnets host RDS/Aurora with no route to the internet at all — the standard banking network segmentation pattern.

High Availability

Every tier is duplicated across three Availability Zones, so the loss of one AZ never takes down the whole environment.

Disaster Recovery

The same module, given a different region variable, stands up an identical network shape in a DR region — covered fully in a later project.

Security

Database subnets have route tables with no 0.0.0.0/0 route at all — the module physically cannot create an internet path for them, by design, not by convention.

Cost / NAT Gateway trade-off

A NAT Gateway per AZ (3 total) maximizes availability but costs roughly 3x a single shared NAT Gateway — a conditional expression lets non-production environments opt for the cheaper single-NAT layout.

Limitations

Subnet CIDR ranges cannot be changed after creation without replacing the subnet — get the sizing right up front, sized for at least 3x expected IP usage per tier to leave room for growth.

07 Complete Solution Design

We build a standalone Git repository, terraform-aws-vpc-framework, containing one top-level module (vpc-framework) that composes three nested modules (subnets, routing, nat-gateway). Every AWS account's own Terraform root module (in the main terraform-abc-bank repository) calls this framework by Git URL and a pinned ref.

Keeping the module in its own Git repository (rather than a subfolder of the main repo) is what makes independent version tagging possible — a tag applies to the whole repo, so the module needs a repo of its own.
  • subnets module: creates public/private/database subnets across N AZs using for_each, from a structured variable of subnet definitions.
  • nat-gateway module: conditionally creates either one NAT Gateway per AZ or a single shared one, based on an ha_nat boolean variable.
  • routing module: builds route tables per tier, using a dynamic "route" block so extra routes (like a future Transit Gateway attachment) can be added purely through variables.
  • The framework module ties them together and exposes only the outputs other projects will need: VPC ID, and a map of subnet IDs per tier.

09 Implementation — Full Production Code

modules/subnets/variables.tf

modules/subnets/variables.tf
variable "vpc_id" {                                     # The VPC these subnets are created inside
  type        = string
  description = "ID of the VPC to create subnets in"
}

variable "subnet_definitions" {                          # A complex variable: list of structured subnet objects, not parallel flat lists
  type = list(object({
    name              = string                            # e.g. "public-a", "private-b", "db-c"
    cidr_block        = string                             # e.g. "10.10.1.0/24"
    availability_zone = string                             # e.g. "ap-south-1a"
    tier              = string                             # "public" | "private" | "database" — used for tagging and routing
  }))
  description = "Structured list of every subnet to create, one object per subnet"

  validation {                                             # Rejects bad tier values before any AWS API call is made
    condition     = alltrue([for s in var.subnet_definitions : contains(["public", "private", "database"], s.tier)])
    error_message = "Each subnet's tier must be one of: public, private, database."
  }
}

variable "tags" {
  type    = map(string)
  default = {}
}

modules/subnets/main.tf

modules/subnets/main.tf
resource "aws_subnet" "this" {
  for_each = { for s in var.subnet_definitions : s.name => s }   # Keys each subnet by its NAME string, not a numeric index — safe to add/remove subnets later

  vpc_id            = var.vpc_id
  cidr_block        = each.value.cidr_block                       # each.value is the current subnet object from the map above
  availability_zone  = each.value.availability_zone

  map_public_ip_on_launch = each.value.tier == "public"            # Conditional expression: only public-tier subnets auto-assign public IPs

  tags = merge(var.tags, {
    Name = each.value.name
    Tier = each.value.tier                                          # Tag used later by the routing module to group subnets by tier
  })
}

modules/subnets/outputs.tf

modules/subnets/outputs.tf
output "subnet_ids_by_tier" {                             # Groups subnet IDs by tier so the routing module can attach the right route table
  value = {
    for tier in ["public", "private", "database"] :
    tier => [for s in aws_subnet.this : s.id if s.tags["Tier"] == tier]
  }
  description = "Map of tier name to list of subnet IDs in that tier"
}

output "subnet_ids_by_name" {                             # Exposes each subnet individually, keyed by its own name
  value       = { for k, s in aws_subnet.this : k => s.id }
  description = "Map of subnet name to subnet ID"
}

modules/nat-gateway/variables.tf

modules/nat-gateway/variables.tf
variable "ha_nat" {                                       # true = one NAT Gateway per AZ (Production); false = single shared NAT Gateway (Dev/UAT)
  type        = bool
  description = "Whether to deploy a highly-available NAT Gateway per AZ"
}

variable "public_subnet_ids" {                            # NAT Gateways must live in PUBLIC subnets, keyed by AZ name
  type        = map(string)
  description = "Map of AZ name to public subnet ID, one NAT Gateway is created per entry when ha_nat is true"
}

modules/nat-gateway/main.tf

modules/nat-gateway/main.tf
locals {
  nat_azs = var.ha_nat ? keys(var.public_subnet_ids) : [keys(var.public_subnet_ids)[0]]  # Conditional expression: all AZs if HA, otherwise just the first AZ
}

resource "aws_eip" "nat" {
  for_each = toset(local.nat_azs)                          # One Elastic IP per NAT Gateway we're about to create
  domain   = "vpc"                                          # Required for EIPs used with NAT Gateways in a VPC
}

resource "aws_nat_gateway" "this" {
  for_each      = toset(local.nat_azs)
  allocation_id = aws_eip.nat[each.key].id                  # Matches the EIP created for the same AZ key
  subnet_id     = var.public_subnet_ids[each.key]           # NAT Gateway must be placed in the PUBLIC subnet of that same AZ

  tags = { Name = "nat-${each.key}" }
}

modules/nat-gateway/outputs.tf

modules/nat-gateway/outputs.tf
output "nat_gateway_ids_by_az" {
  value       = { for k, n in aws_nat_gateway.this : k => n.id }
  description = "Map of AZ name to its NAT Gateway ID (or the single shared one, repeated in ha_nat=false mode)"
}

variable "vpc_id" {

  type = string

  type = list(string)

  type = map(string)

  type = list(object({

modules/routing/main.tf

modules/routing/main.tf
resource "aws_route_table" "public" {                      # One shared public route table for all public subnets
  vpc_id = var.vpc_id

  route {
    cidr_block = "0.0.0.0/0"                                # Public tier routes everything to the Internet Gateway
    gateway_id = var.internet_gateway_id
  }

  tags = { Name = "rt-public" }
}

resource "aws_route_table_association" "public" {
  for_each       = toset(var.public_subnet_ids)
  subnet_id      = each.value
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table" "private" {
  for_each = var.private_subnet_ids_by_az                   # One route table PER AZ, so each can route to its own AZ's NAT Gateway
  vpc_id   = var.vpc_id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = var.nat_gateway_ids_by_az[each.key]     # Routes through the NAT Gateway that lives in the SAME AZ
  }

  dynamic "route" {                                          # Generates zero or more extra route blocks from the extra_routes variable
    for_each = var.extra_routes
    content {
      cidr_block = route.value.cidr_block                     # route.value refers to the current item from extra_routes
      gateway_id = route.value.gateway_id
    }
  }

  tags = { Name = "rt-private-${each.key}" }
}

resource "aws_route_table_association" "private" {
  for_each       = var.private_subnet_ids_by_az
  subnet_id      = each.value
  route_table_id = aws_route_table.private[each.key].id
}

resource "aws_route_table" "database" {                     # Deliberately has NO route block at all — no internet path exists for this tier
  vpc_id = var.vpc_id
  tags   = { Name = "rt-database" }
}

main.tf (top-level vpc-framework module)

terraform-aws-vpc-framework/main.tf
resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true
  tags                 = merge(var.tags, { Name = var.vpc_name })
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id
  tags   = { Name = "${var.vpc_name}-igw" }
}

module "subnets" {                                          # Nested module #1: creates every subnet from the structured variable
  source = "./modules/subnets"

  vpc_id             = aws_vpc.this.id
  subnet_definitions = var.subnet_definitions
  tags               = var.tags
}

module "nat_gateway" {                                       # Nested module #2: depends on subnets module's output
  source = "./modules/nat-gateway"

  ha_nat            = var.ha_nat
  public_subnet_ids = { for name, id in module.subnets.subnet_ids_by_name :
                         replace(name, "public-", "") => id if startswith(name, "public-") }
}

module "routing" {                                           # Nested module #3: depends on BOTH prior modules' outputs
  source = "./modules/routing"

  vpc_id                   = aws_vpc.this.id
  internet_gateway_id      = aws_internet_gateway.this.id
  public_subnet_ids        = module.subnets.subnet_ids_by_tier["public"]
  private_subnet_ids_by_az = { for name, id in module.subnets.subnet_ids_by_name :
                                replace(name, "private-", "") => id if startswith(name, "private-") }
  nat_gateway_ids_by_az    = module.nat_gateway.nat_gateway_ids_by_az
  extra_routes             = var.extra_routes
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
for_each = { for s in ... : s.name => s }Converts a list into a map keyed by name, required because for_each needs a map or set, not a listPassing a raw list straight to for_each — Terraform will error unless it's a map or a set of strings
validation blockFails plan with a clear message if a variable's value is invalidSkipping validation and letting AWS reject the bad value instead — a much less helpful error, seen only during apply
dynamic "route"Generates zero-to-many nested route blocks from a listWriting a fixed number of optional route blocks with count at the block level — not supported; nested blocks require dynamic
?ref=v1.2.0 in a Git module sourcePins the exact tagged commit to cloneOmitting ref entirely, which defaults to the repository's default branch — the exact drift risk this project prevents
startswith(name, "public-")Terraform string function used inside a for expression to filter a map by key prefixHardcoding subnet names elsewhere instead of deriving groupings from the tier tag or name prefix consistently

11 Execution Flow, Explained Internally

terraform init

Because source is a Git URL, Terraform clones the framework repository at the pinned ref into .terraform/modules/vpc — a completely separate step from downloading the aws provider plugin.

Dependency graph across nesting levels

Terraform sees that module.routing references module.nat_gateway.nat_gateway_ids_by_az, which itself references module.subnets.subnet_ids_by_name — so subnets are created first, then NAT gateways, then routing, automatically.

terraform plan

With for_each, the plan output lists each resource by its key (e.g. module.subnets.aws_subnet.this["private-a"]) rather than a numeric index — much easier to read in a review.

terraform apply

Creates the VPC and Internet Gateway first (no module dependency), then subnets, then NAT Gateways (which need subnet IDs), then route tables (which need both NAT Gateway and subnet IDs).

12 Module Versioning via Git Tags — Step by Step

terminal (inside terraform-aws-vpc-framework repo)
git add .
git commit -m "Add database tier route table with no internet route"
git tag -a v1.2.0 -m "v1.2.0: adds database tier, fixes NAT AZ mapping"
git push origin main --tags

Any consuming account keeps working with whatever ref it already has pinned. To adopt the new version deliberately:

terminal (inside environments/dev)
# Edit main.tf: change ?ref=v1.1.0 to ?ref=v1.2.0
terraform init -upgrade   # Re-clones the module at the new ref
terraform plan             # Review exactly what the new version changes before applying
Write a CHANGELOG.md entry for every tag. In a banking environment, "what exactly changed between v1.1.0 and v1.2.0" is a question an auditor will eventually ask, not just a curiosity.

13 CI/CD Integration — Two Pipelines

The framework repository gets its own pipeline that validates the module in isolation before it's ever tagged; the consuming account's repository gets a pipeline that plans/applies against a specific pinned version.

terraform-aws-vpc-framework/.github/workflows/validate-module.yml
name: validate-vpc-framework-module
on:
  pull_request:
    branches: [main]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.5"
      - name: fmt check
        run: terraform fmt -check -recursive
      - name: init (no backend, module validation only)
        run: terraform init -backend=false        # We only need to validate syntax/types here, not talk to any real backend
      - name: validate
        run: terraform validate
Tagging a release (git tag v1.x.x) is a separate, deliberate manual or semi-automated step — never auto-tag on every merge to main, since not every merge is meant to be a new consumable version.

15 Interview Preparation

Q: Why version a Terraform module with Git tags instead of just always using the latest code?
Pinning to a tag means an environment only changes when someone deliberately decides to upgrade it — protecting stable environments like Production from unrelated changes made for another environment's convenience.
Q: When would you choose count over for_each?
When creating a fixed number of genuinely identical, unnamed resources where order truly doesn't matter and the list will never shrink from the middle — for_each is the safer default for anything keyed by a meaningful identifier like a name or AZ.
Q: How deep should module nesting go?
Generally no more than two levels — root calls a framework module, which calls small single-purpose modules. Deeper nesting makes troubleshooting "why didn't this resource get created" significantly harder.
Q: How do dynamic blocks differ from for_each on a resource?
for_each on a resource creates multiple separate resource instances; a dynamic block creates multiple repeated nested blocks inside a single resource, such as several route blocks inside one route table.
Manager round: A team wants to skip the pinned ref and just point at main for faster iteration. How do you respond?
Explain the real incident risk — an untested change on main could apply to Production the next time someone runs an upgrade — and offer a faster release cadence (frequent patch tags) as the actual fix for slow iteration, rather than removing the safety pin.
