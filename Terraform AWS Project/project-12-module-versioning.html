Terraform Module Versioning and Private Module Registry Strategy

Intermediate-Advanced · Turning the modules built in Projects 2, 4, and 11 into a versioned product other teams can safely consume.

Semantic Versioning Private Registry Module Source Pinning Git Tag Releases Breaking Change Policy

01The Enterprise Problem This Solves

The VPC module from Project 2 and the IAM role module from Project 4 have been referenced so far with a plain relative path (source = "../../modules/vpc") — fine within a single repo, but it means every environment always gets whatever the module's code currently looks like on disk, with no way to adopt a change deliberately or roll one back. As soon as more than one team, or more than one repo, needs to consume the same module, an unpinned relative path stops being viable. This project turns those modules into versioned, independently releasable artifacts — consumed by explicit version constraint, published through a private module registry, with an explicit policy for what counts as a breaking change.

02The Story: The Module Update That Broke Three Teams at Once

Production Incident Replay The platform team improves the shared VPC module — adding the one_nat_per_az option from Project 2 as a genuinely good, backward-compatible enhancement. But in the same change, they also rename an output from subnet_ids to private_subnet_ids because the old name was ambiguous, reasoning that "it's a small cleanup, barely worth mentioning." Because every consuming team's root module referenced the shared module via an unpinned Git branch reference (source = "git::https://github.com/acme/modules.git//vpc?ref=main"), the very next terraform init any of those three teams runs — regardless of whether they intended to pick up any change at all — pulls in the renamed output and breaks their code with a cryptic "output not found" error, on three unrelated teams' unrelated deploys, on the same afternoon. Nothing about their own code changed; the ground moved under them. The fix isn't just "communicate changes better" — it's making it structurally impossible for a consumer to receive a breaking change without asking for it: explicit semantic version pinning, plus a documented policy for what triggers a major version bump.

03Deep Technical Explanation

Semantic versioning as a contract, not a formality

Semantic versioning (MAJOR.MINOR.PATCH) is a promise consumers rely on structurally: a patch release fixes a bug with no interface change; a minor release adds functionality in a backward-compatible way (a new optional variable with a sensible default, like one_nat_per_az); a major release contains any breaking change — a renamed or removed output, a variable that becomes required, a changed resource type that would force a destroy/recreate. The renamed output in this project's story should have been a major version bump, communicated as a deliberate, opt-in upgrade — not silently delivered to every consumer on a branch reference.

Version-pinned module sources instead of branch references

Terraform's module source argument supports a version constraint when sourcing from a registry (private or public), resolved against published, immutable releases — fundamentally different from a Git branch reference, which by definition points at whatever the branch's HEAD currently is. Pinning to version = "~> 2.1" means a consumer only ever receives 2.x patch/minor updates, and must deliberately change that constraint to receive anything in a new major version.

Private module registry mechanics

A private registry (Terraform Cloud's built-in registry, or a self-hosted equivalent) expects modules published as tagged Git releases following the naming convention terraform-<PROVIDER>-<NAME>, and resolves a source = "app.terraform.io/acme-org/vpc/aws" reference against those published version tags — giving consumers a searchable catalog of available modules and versions instead of needing to know exact Git repo URLs and paths.

05Step-by-Step Implementation

5.1 — Consuming a versioned module from the registry

envs/prod/main.tf 
module "network" {
  source  = "app.terraform.io/acme-org/vpc/aws" # registry address, not a relative path or Git URL
  version = "~> 2.1" # accepts 2.1.x and 2.2.x, but never 3.x — a deliberate upgrade is required for that

  name           = "acme-prod"
  vpc_cidr       = "10.1.0.0/16"
  azs            = ["us-east-1a", "us-east-1b", "us-east-1c"]
  one_nat_per_az = true
}

5.2 — Release automation for the modules repo

.github/workflows/release-module.yml (excerpt) 
on:
  push:
    tags: ['vpc/v*', 'iam-role/v*', 'eks/v*'] # per-module tag prefixes — one repo, independently versioned modules

jobs:
  validate-and-publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Determine module + version from tag
        run: |
          # tag looks like "vpc/v2.1.0" — split on "/" to get module name + version
          MODULE=$(echo $GITHUB_REF_NAME | cut -d/ -f1)
          echo "MODULE=$MODULE" >> $GITHUB_ENV

      - name: terraform validate the tagged module
        run: |
          cd modules/$MODULE
          terraform init -backend=false
          terraform validate # fail the release before it's ever published if the module itself is broken

      # The registry auto-discovers new tags matching its naming convention;
      # this job's real job is to gate the tag on validation passing first.

Plain-English walkthrough

The ~> 2.1 constraint operator is doing the entire job that would have prevented this project's story: it allows Terraform to automatically pick up any 2.1.x or 2.x.x release, but a 3.0.0 release — where the output rename would live — requires a human to explicitly edit the version constraint, turning a silent breaking change into a deliberate, reviewed decision. Tagging each module independently (vpc/v2.1.0 vs. iam-role/v1.4.0) inside one shared repo means the VPC module's major version bump doesn't force every other module in the repo to bump in lockstep — each module's version history reflects only its own changes. The release workflow validating the module before publish is a small but important detail: it means a broken module tag can never even become resolvable through the registry in the first place.

06Failure Scenarios — What Breaks in Real Life

Failure: a "minor" release accidentally contains a breaking change An engineer tags a change as a minor version bump, genuinely believing it's backward-compatible, but a variable's default value changed in a way that alters existing consumers' behavior without their code changing at all. Debug: maintain a checklist (renamed/removed outputs, new required variables, resource replacement) that must be reviewed before any tag is pushed, and treat "would this break someone silently" as the actual test — not just "did I add or remove a whole variable."
Failure: teams never upgrade because there's no forcing function Version pinning protects consumers from unwanted change, but taken to an extreme, some teams pin to an old major version indefinitely and never migrate, accumulating security and maintenance debt in old module versions. Debug: pair version pinning with a documented deprecation policy — old major versions get a defined support window, and the platform team tracks which teams are on which version to drive migration proactively rather than assuming it happens on its own.
Failure: registry publish succeeds but the module has an undetected logic bug terraform validate only catches syntax and type errors, not logic errors (like Project 2's mid-list AZ insertion issue) — a tag can pass validation and still ship a real behavioral bug. Debug: this is exactly why module releases benefit from the same policy-as-code and automated testing discipline (Terratest, or the compliance scanning from Project 22) applied before a version tag is ever pushed, not just a syntax check.
