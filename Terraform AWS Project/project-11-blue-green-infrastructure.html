Blue-Green Infrastructure — Zero-Downtime Deployments

Every release of payments-api today means a brief window where the old version is stopped before the new one is confirmed healthy — a small, real outage the team has just been accepting. Today we build two complete, parallel environments and a traffic-shifting mechanism so a release becomes reversible in seconds, not a leap of faith.

01 The Banking Story

The payments-api team deploys by replacing instances behind the existing ALB target group in place — stop the old version's instances, start the new version's instances, and hope the new version passes its health checks quickly. Last Thursday's release didn't: a configuration error wasn't caught until the new instances were already live and failing, and payments were degraded for six minutes while the team scrambled to roll back by redeploying the previous version from scratch.

Rolling back "by redeploying the old version" is itself the problem: it's not instant, and it's not guaranteed to work cleanly if the failure was partly due to infrastructure state, not just application code.

Our manager's brief: "Build blue-green properly. Two complete, independent environments, always both provisioned. Deploy the new version to the idle one, test it in isolation, then shift traffic — and if anything looks wrong, shifting back must be as fast as shifting forward was."

02 Business Requirement, Risk & Impact

Business Requirement

Deployments to payments-api must not cause any customer-facing downtime, and a bad release must be reversible within seconds, not minutes.

Customer Requirement

The release process needs a clear, observable "canary" period where the new version receives a small fraction of real traffic before receiving all of it.

Current Infrastructure

A single target group behind the Production ALB, with instances replaced in place during each deployment.

Existing Manual Process

Stop old instances, start new instances, watch health checks, manually redeploy the previous version if something goes wrong — an in-place replacement with no true isolation between old and new.

Problems With Current Process

  • No isolated environment to validate the new version against real traffic before it fully replaces the old one
  • Rollback means a fresh, slow redeploy of the previous version, not an instant switch
  • Any infrastructure-level issue with the new deployment (not just application bugs) surfaces only after the old version is already gone

Business Challenges

Customer-facing payment downtime, even briefly, is both a direct revenue and reputational concern and, past certain thresholds, a regulatory incident requiring formal reporting.

Risk Analysis

Medium-High: the six-minute incident from last week is a realistic preview of what a more serious release-time failure could cost without a fast, reliable rollback mechanism.

Business Impact

Every deployment currently carries real customer-facing risk — this directly limits how confidently and how often the team can ship improvements and fixes.

03 Why Blue-Green, and What We Rejected

Why Blue-Green over the alternatives

Blue-green keeps two complete, independent environments (target groups, and optionally full instance fleets) running simultaneously — traffic shifts between them at the DNS or load-balancer level, meaning rollback is just shifting the weight back, not a redeploy. The old version stays fully intact and running until the new one is proven, giving a true safety net the current in-place approach doesn't have.

Alternatives considered, and why they were rejected

04 Terraform Concepts You Must Understand Before We Build

External Data Sources

What it is: the data "external" data source runs an external program (a script) and captures its JSON output as usable Terraform values — a genuine escape hatch for information Terraform has no native way to determine.

Why it exists here: Terraform's own state knows which target group it created, but not which one is currently receiving live production traffic weight — that's a runtime fact about the ALB's listener rule, not something derivable purely from the last apply. A small script queries the ALB directly and reports back which color ("blue" or "green") is currently live, so this apply can safely target the idle one for the next deployment.

Contract: the external program must read optional JSON from stdin and write a flat JSON object of string values to stdout — Terraform enforces this exact shape and errors clearly if the script doesn't comply.

Best practice, and its limits: like provisioners, external data sources are a last resort — prefer a native data source whenever AWS exposes the information (it usually doesn't for "application-level current state" like this); keep the script's logic minimal, deterministic, and side-effect-free, since it runs on every single plan, not just apply.

Reinforcing Nested Modules for Blue/Green Symmetry

What it is: a single app-environment module, called twice — once with color = "blue", once with color = "green" — guaranteeing the two environments are structurally identical by construction, not by careful copy-pasting.

Why it matters here specifically: the entire safety guarantee of blue-green depends on both environments being genuinely equivalent infrastructure — any drift between hand-maintained "blue" and "green" resource blocks would undermine the whole pattern.

Conditional Expressions for Weight Calculation

What it is: reusing the condition ? a : b pattern to compute each target group's traffic weight from a single var.live_color and var.canary_percent pair, so a deployment's traffic shift is described by two simple variables rather than four independently-set weight values that could be set inconsistently.

05 AWS Concepts: Weighted ALB Routing

What is a Weighted Target Group Forward Action

An ALB listener rule can forward to multiple target groups simultaneously, each with a relative weight — e.g. 95% to blue, 5% to green — letting traffic shift gradually rather than as an instant all-or-nothing cutover.

Why it exists

It gives a genuine canary window even within a blue-green model: the new (idle) environment can receive a small, real slice of production traffic before taking 100%, catching issues that only appear under real load.

Two Complete Target Groups, One Listener Rule

Both "blue" and "green" target groups exist and have healthy, registered instances at all times — the listener rule's weights are the only thing that changes during a deployment, which is exactly why rollback is instantaneous.

Health Checks Per Target Group

Each target group has its own independent health check — the idle environment's instances must pass health checks on their own before receiving any traffic weight at all, catching infrastructure-level failures before they're customer-facing.

High Availability

Both blue and green target groups span the same multiple AZs from Project 02's VPC framework — blue-green doesn't reduce AZ-level redundancy, it adds a second, orthogonal safety dimension on top of it.

Cost

Running two complete environments simultaneously roughly doubles compute cost during the deployment window — for payments-api specifically, that cost is judged well worth the risk reduction; teams may choose rolling deployments for less critical, cost-sensitive services instead.

07 Complete Solution Design

A single app-environment module, called twice (once per color), creates a complete target group and Auto Scaling Group pair. An external data source script queries the ALB's current listener rule to determine which color is presently live, exposed to the rest of the configuration as data.external.current_state.result.live_color. The ALB listener rule uses a weighted forward action computed from two variables — live_color and green_weight — so a deployment is: deploy the new version to the idle color at 0% weight, verify it, then move weight to it incrementally, with an instant rollback path at every step.

09 Implementation — Full Production Code

scripts/current-live-color.sh

environments/prod/scripts/current-live-color.sh
#!/usr/bin/env bash
set -euo pipefail                                                     # Fail loudly on any error — a silently broken script would give Terraform bad data

RULE_ARN=$(cat | jq -r '.rule_arn')                                    # Reads the JSON Terraform sends on stdin and extracts the listener rule ARN

WEIGHTS=$(aws elbv2 describe-rules --rule-arns "$RULE_ARN" \
  --query "Rules[0].Actions[0].ForwardConfig.TargetGroups" --output json)

GREEN_WEIGHT=$(echo "$WEIGHTS" | jq -r '.[] | select(.TargetGroupArn | contains("green")) | .Weight')

if [ "$GREEN_WEIGHT" -ge 50 ]; then                                     # If green currently holds the majority of traffic, green is considered "live"
  echo '{"live_color": "green"}'
else
  echo '{"live_color": "blue"}'
fi

environments/prod/blue-green.tf

environments/prod/blue-green.tf
data "external" "current_state" {                                     # Runs the script above and captures its JSON output
  program = ["bash", "${path.module}/scripts/current-live-color.sh"]
  query = {
    rule_arn = aws_lb_listener_rule.payments_api.arn                    # Passed TO the script as JSON on stdin
  }
}

module "app_blue" {                                                    # Same module, called twice — guarantees structural symmetry between colors
  source = "./modules/app-environment"
  color  = "blue"
  vpc_id = var.vpc_id
  subnet_ids = var.private_subnet_ids
}

module "app_green" {
  source = "./modules/app-environment"
  color  = "green"
  vpc_id = var.vpc_id
  subnet_ids = var.private_subnet_ids
}

locals {
  green_weight = var.deployment_in_progress ? var.green_traffic_percent : (
    data.external.current_state.result.live_color == "green" ? 100 : 0    # Steady state: whichever color the script reports as live gets 100%
  )
  blue_weight = 100 - local.green_weight                                   # Always the complement — the two weights sum to exactly 100 by construction
}

resource "aws_lb_listener_rule" "payments_api" {
  listener_arn = var.alb_listener_arn
  priority     = 100

  action {
    type = "forward"
    forward {
      target_group {
        arn    = module.app_blue.target_group_arn
        weight = local.blue_weight
      }
      target_group {
        arn    = module.app_green.target_group_arn
        weight = local.green_weight
      }
    }
  }

  condition {
    path_pattern { values = ["/*"] }
  }
}

modules/app-environment/main.tf
resource "aws_lb_target_group" "this" {
  name     = "payments-api-${var.color}"                                # e.g. "payments-api-blue" — the color is baked into the resource name itself
  port     = 8080
  protocol = "HTTP"
  vpc_id   = var.vpc_id

  health_check {
    path                = "/healthz"
    healthy_threshold   = 3
    unhealthy_threshold = 3
    interval            = 15
  }
}

resource "aws_autoscaling_group" "this" {
  name                = "payments-api-${var.color}-asg"
  vpc_zone_identifier = var.subnet_ids
  target_group_arns   = [aws_lb_target_group.this.arn]
  min_size            = 2
  max_size            = 6
  desired_capacity    = 2                                                # Both colors run at real capacity ALWAYS — this is what makes rollback instant, not just "possible"

  launch_template {
    id      = var.launch_template_id
    version = "$Latest"
  }

  tag {
    key                 = "Color"
    value               = var.color
    propagate_at_launch = true
  }
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
data "external" program/queryPasses structured JSON to a script's stdin, captures structured JSON from its stdout as usable Terraform valuesWriting anything to the script's stdout other than the required flat JSON object — even a stray debug echo line breaks Terraform's parsing of the result
local.blue_weight = 100 - local.green_weightDerives one weight from the other, guaranteeing they always sum to exactly 100Setting both weights independently via separate variables — risks an invalid state (e.g. both at 100, or both at 0) that a single derived value structurally prevents
Two calls to the same app-environment moduleGuarantees blue and green are structurally identical, differing only in the color inputWriting blue and green as separate, hand-maintained resource blocks — the two would inevitably drift apart over time, undermining blue-green's core safety guarantee
desired_capacity = 2 on BOTH ASGs, alwaysKeeps the idle color running at real, warm capacity, not scaled to zeroScaling the idle environment to zero to save cost — this reintroduces a cold-start delay into rollback, defeating the "instant" rollback property that is blue-green's whole point

11 Execution Flow, Explained Internally

terraform plan — external data source execution

The script runs during EVERY plan, not just apply — it queries live AWS API state each time, so the plan's understanding of "which color is live" is always current, not cached from the last apply.

Deploying a new version

The new application version is baked into a new launch template version, referenced by the IDLE color's Auto Scaling Group — its instances roll out and pass health checks entirely before any traffic weight is shifted toward them.

Shifting traffic

Changing green_traffic_percent and re-applying only touches the aws_lb_listener_rule resource's forward block — no instances are created, destroyed, or restarted by a weight change alone.

Never destroy the "idle" color's infrastructure to save cost between deployments — doing so removes exactly the safety property (a warm, tested, instant rollback target) that justifies blue-green's extra cost in the first place.

12 CI/CD Integration

.github/workflows/terraform-blue-green-deploy.yml
name: blue-green-deploy
on:
  workflow_dispatch:
    inputs:
      target_weight:
        description: "Percentage of traffic to shift to the idle color (0-100)"
        required: true

jobs:
  shift-traffic:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve \
          -var="deployment_in_progress=true" \
          -var="green_traffic_percent=${{ github.event.inputs.target_weight }}"
      - name: Smoke test the shifted traffic
        run: ./scripts/smoke-test.sh                                    # Application-level check AFTER the shift — a second, independent verification beyond target group health
Running this as a manually-triggered, weight-parameterized workflow lets an engineer shift traffic in controlled steps (5% → 25% → 100%) with a smoke test between each, rather than an all-or-nothing cutover.

14 Interview Preparation

Q: What makes blue-green rollback "instant" compared to a rolling deployment rollback?
Both environments run at full, warm capacity simultaneously the whole time — rollback is just shifting the load balancer's weight back to the previously-live color, with no instance creation, deletion, or cold start involved.
Q: When would you reach for a data "external" source, and what's the risk?
Only when Terraform has no native way to learn a piece of runtime state it needs — like which color currently holds ALB traffic weight; the risk is that it runs an arbitrary script on every plan, so it must be fast, deterministic, and strictly limited to producing the required JSON output with no side effects.
Q: Why keep the idle color's Auto Scaling Group at full desired_capacity instead of scaling it to zero between deployments?
Scaling to zero would reintroduce a cold-start delay into rollback and into the next deployment's canary step, undermining blue-green's central promise of an instantly available, already-warm alternative environment.
Q: Why call the same module twice instead of writing separate blue and green resource blocks?
Calling one module twice guarantees both environments are structurally identical by construction — hand-maintained duplicate blocks inevitably drift apart over time, which would quietly undermine the safety guarantee blue-green is meant to provide.
Manager round: How would you decide between blue-green and a rolling deployment for a given service?
Weigh the service's criticality and blast radius of a bad deploy against the roughly doubled infrastructure cost of running two full environments — payments-api's direct customer and regulatory impact justifies it; a lower-stakes internal tool likely doesn't need the same investment.
