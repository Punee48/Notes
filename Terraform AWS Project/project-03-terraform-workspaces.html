Terraform Workspaces for Dev/QA/Staging/Prod Environment Isolation

Foundational-Intermediate · When to reach for workspaces, and — just as important — when NOT to.

01The Enterprise Problem This Solves

Project 1 solved environment isolation with separate directories, each with its own hardcoded backend key. That approach is deliberately explicit and safe, but it doesn't scale cleanly when a team needs many short-lived, near-identical environments — a QA environment per feature branch, an ephemeral environment per pull request, a personal sandbox per engineer. Copy-pasting a whole directory tree for every one of those is its own maintenance burden. Terraform workspaces solve a narrower version of the isolation problem: the same configuration, the same code, applied against multiple independent state files, switched with a single command. This project teaches workspaces properly — including the sharp edges that make them the wrong tool for permanent environments like prod, which is exactly why Project 1 used directories instead for the four core environments, and workspaces get reserved for the ephemeral, high-churn use case they're actually good at.

02The Story: The Workspace That Looked Like Prod But Wasn't

Production Incident Replay A platform engineer, moving fast, decides workspaces are cleaner than Project 1's directory-per-environment layout and migrates the whole team over — one root module, four workspaces: dev, qa, staging, prod. Everything works for weeks. Then a junior engineer, following a runbook that says "run terraform apply from the infra repo," does exactly that — from whatever workspace happened to be selected on their machine from the last thing they worked on. Nothing in the command, the directory, or the visible file tree told them which environment they were about to modify; terraform.workspace is invisible unless you explicitly run terraform workspace show first, and the runbook never mentioned it. The apply lands against prod. Nothing catastrophic happens — this time — but the retro is blunt: workspaces made every environment look identical at the point where a human makes the highest-risk decision, right before hitting enter on apply. The team's fix wasn't to abandon workspaces entirely; it was to confine them to disposable QA/feature environments where the blast radius of a mistake is small, and keep directories — with their unmistakably different file paths — for anything a mistake could actually hurt.

03Deep Technical Explanation

What a workspace actually changes under the hood

A Terraform workspace does exactly one thing mechanically: it changes the state file path the current backend reads and writes. With the S3 backend from Project 1, switching workspaces inserts a env:/<workspace-name>/ prefix in front of the configured key automatically — terraform workspace select qa against a key = "features/network.tfstate" backend reads and writes env:/qa/features/network.tfstate. Nothing else changes: not the code, not the provider config, not any file on disk. That's the entire mechanism — and also exactly why it's dangerous for anything where the code path visibly changing (like Project 1's separate directories) is a safety feature, not overhead.

The terraform.workspace interpolation

Because the code itself never changes between workspaces, any actual difference in behavior — instance sizing, tagging, feature flags — has to be driven from inside HCL using the built-in terraform.workspace value, typically through a lookup map keyed by workspace name. This is different from Project 1's approach, where each environment directory has its own terraform.tfvars file; here, all environments share one .tfvars-equivalent lookup table embedded directly in the code.

When workspaces are the right tool (and when they're not)

Workspaces fit best for ephemeral, structurally identical environments: a temporary QA stack spun up per feature branch and torn down after merge, or a personal dev sandbox. They fit poorly for environments that diverge structurally over time — prod typically ends up with different instance types, different HA settings, extra monitoring, and different variable values than dev, and forcing all of that through one shared code path with conditionals becomes harder to read than just letting the directories diverge, which is exactly why Project 1 did not use workspaces for the four core environments. The enterprise rule of thumb this project teaches: use directories (Project 1's pattern) for anything long-lived and structurally different; use workspaces for anything short-lived and structurally identical.

05Step-by-Step Implementation

5.1 — A root module for ephemeral per-PR QA stacks

feature-qa-stack/backend.tf 
terraform {
  backend "s3" {
    bucket         = "acme-tfstate-123456789012" # same bucket from Project 1's bootstrap
    key            = "features/qa-stack/terraform.tfstate" # workspace name is auto-prefixed onto this
    region         = "us-east-1"
    dynamodb_table = "terraform-lock-table"
    encrypt        = true
  }
}
feature-qa-stack/main.tf 
# A lookup table keyed by workspace name — this is the ONLY place
# behavior differs between workspaces, since the rest of the code
# is identical for every one of them.
locals {
  size_by_workspace = {
    default = "t3.micro" # "default" is the workspace that always exists, pre-created by Terraform
  }
  instance_type = lookup(local.size_by_workspace, terraform.workspace, "t3.micro")
  # lookup()'s third argument is the fallback for any workspace not
  # explicitly listed — every new PR workspace gets t3.micro by default.
}

resource "aws_instance" "qa_app" {
  ami           = var.qa_ami_id
  instance_type = local.instance_type

  tags = {
    Name      = "qa-${terraform.workspace}" # e.g. "qa-pr-1423" — visibly ties the instance to its workspace
    Workspace = terraform.workspace
    Ephemeral = "true" # flags this for the idle-resource cleanup module built in Project 19
  }
}

5.2 — CI-driven lifecycle for a per-PR workspace

.github/workflows/pr-qa-stack.yml (excerpt) 
on:
  pull_request:
    types: [opened, synchronize, closed]

jobs:
  qa-stack:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Select or create this PR's workspace
        run: |
          # -or-create avoids a separate existence-check step —
          # idempotent whether this is PR open or PR update.
          terraform workspace select -or-create pr-${{ github.event.pull_request.number }}

      - name: Apply (only when PR is open/updated)
        if: github.event.action != 'closed'
        run: terraform apply -auto-approve

      - name: Destroy and delete workspace (PR closed)
        if: github.event.action == 'closed'
        run: |
          terraform destroy -auto-approve
          terraform workspace select default
          terraform workspace delete pr-${{ github.event.pull_request.number }}
          # must switch back to "default" first — Terraform refuses to
          # delete whichever workspace is currently selected.

Plain-English walkthrough

This CI job treats a workspace's entire lifecycle as tied to a pull request's lifecycle: opening or updating a PR selects-or-creates a workspace named after the PR number and applies against it; closing the PR destroys that workspace's resources and deletes the workspace itself, so state never accumulates for PRs that no longer exist. The lookup() pattern in main.tf means every one of these dozens of ephemeral workspaces runs identical code — no one is hand-editing a new directory per PR the way Project 1's four core environments are maintained. Note the explicit switch back to the default workspace before deletion — this is a real Terraform CLI constraint, not a style choice, and forgetting it is the most common way this kind of pipeline breaks.

06Failure Scenarios — What Breaks in Real Life

Failure: apply lands in the wrong workspace, invisibly As in the story above — an engineer runs apply without checking terraform workspace show first, and it lands against whatever workspace was last selected on that machine. Debug/Prevent: never rely on workspaces for anything a mistaken apply could meaningfully damage; for those, use Project 1's directory pattern instead, where the working directory itself makes the target unmistakable.
Failure: orphaned workspaces accumulate forever A CI pipeline crashes between the destroy step and the workspace delete step for a closed PR. The workspace — and a lingering state file — is left behind indefinitely, and nobody notices until someone runs terraform workspace list and finds forty stale entries. Debug: a scheduled cleanup job (built out fully as part of Project 19's idle-resource cleanup) that lists workspaces older than N days with no corresponding open PR and destroys + deletes them.
Failure: shared code path masks real environment drift A "temporary" QA workspace lives for six months because nobody closed the PR, and the team starts treating it like a real environment — adding manual out-of-band changes the shared code doesn't account for. Debug: enforce a hard TTL on any workspace-based environment; if something needs to live longer than a sprint, that's the signal it belongs in Project 1's directory pattern instead, not a sign to special-case the workspace code further.

07Interview Talking Points

"When would you use Terraform workspaces versus separate root modules per environment?"
Give the rule directly: workspaces for ephemeral, structurally-identical environments (per-PR QA stacks); separate directories for long-lived environments that diverge structurally (prod vs. dev). Cite the invisible-context risk as the reason prod should never live in a workspace.
"What actually changes in Terraform's behavior when you switch workspaces?"
Be precise: only the state file key changes (via the automatic env:/<workspace>/ prefix); the code, provider config, and everything else stays identical, which is exactly why any per-environment difference has to be driven explicitly through terraform.workspace lookups in code.
