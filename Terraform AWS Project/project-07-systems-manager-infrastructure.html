PROJECT 07 OF 40 · INTERMEDIATE

Systems Manager Infrastructure — Retiring SSH, Automating Patching

No inbound port 22 or 3389 has ever been strictly necessary — it's just what everyone defaults to. Today we remove it entirely: Session Manager for shell access with full audit logging, Patch Manager for OS patching on a schedule, and Parameter Store for the non-secret configuration that doesn't belong in Secrets Manager.

01 The Banking Story

A recent penetration test flagged something the team already half-knew: the bastion host from an earlier network project still has port 22 open to a "trusted" corporate IP range — a range that, on closer inspection, includes an entire office building's guest WiFi. It's never been exploited, but the pen tester's report is blunt: "Any inbound SSH path is a standing attack surface, trusted range or not."

Separately, OS patching across the fleet is done by an engineer SSHing into each instance in turn, running apt update && apt upgrade by hand, on a schedule that depends entirely on that engineer remembering to do it — Production's database tier is three months behind on security patches.

Our manager's brief: "Close every inbound SSH and RDP port, permanently. Give engineers shell access through Session Manager instead — logged, and revocable in one place. And automate patching on a proper schedule so we stop relying on someone's memory."

02 Business Requirement, Risk & Impact

Business Requirement

No EC2 instance in any account should have an open inbound SSH/RDP path, and every instance must receive OS security patches on a defined, enforced schedule.

Customer Requirement

Engineers still need shell access for troubleshooting — just not through a standing network path that widens the attack surface.

Current Infrastructure

A bastion host with an inbound security group rule for SSH from a corporate IP range that turned out to be broader than intended.

Existing Manual Process

Engineers SSH to the bastion, then SSH again to the target instance; patching is a manual, memory-dependent task with no enforced cadence.

Problems With Current Process

  • Any open inbound SSH/RDP port is a standing attack surface, regardless of how the source range is scoped
  • SSH key management (rotation, revocation when an engineer leaves) is manual and error-prone
  • No consistent patch cadence — Production is measurably behind

Business Challenges

PCI-DSS explicitly requires timely security patching and controlled, logged remote access to systems that touch cardholder data — both gaps found here are direct compliance exposure.

Risk Analysis

High: an unpatched, internet-adjacent bastion host is a known, common initial-access vector in real breaches — this exact finding pattern appears in post-incident reports across the industry.

Business Impact

An unresolved pen-test finding of this severity can block the certification renewal the bank needs for its next audit cycle.

03 Why Systems Manager, and What We Rejected

Why AWS Systems Manager (Session Manager + Patch Manager)

Session Manager connects to an instance entirely through the SSM Agent's outbound connection to the Systems Manager service — no inbound port is ever opened, no bastion host is needed, and every session is automatically logged to CloudWatch and, if configured, S3, with full command history. Patch Manager runs on a schedule against instances grouped by tag, with a defined patch baseline and a maintenance window — no engineer needs to remember anything.

Alternatives considered, and why they were rejected

AlternativeWhy consideredWhy rejected for ABC Bank
Keep the bastion, tighten the IP range furtherSmallest immediate changeStill leaves a standing inbound path and manual SSH key management — treats the symptom, not the root cause the pen test actually flagged
AWS Client VPN for SSH accessRemoves the public bastion, still allows SSHStill relies on SSH keys and an open port inside the VPN — Session Manager removes both the key management burden and the open port entirely

04 Terraform Concepts You Must Understand Before We Build

Reinforcing Data Sources — SSM-Managed AMI Lookup

What it is: a data "aws_ssm_parameter" lookup against AWS's own public parameter path (e.g. /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64) that always resolves to the latest patched AMI ID for a given OS — no hardcoded, aging AMI ID anywhere in our code.

Why it exists: a hardcoded AMI ID drifts out of date the moment AWS publishes a newer patched image; reading it as a data source means every new instance launches from the current image automatically.

Local Values for Tag-Based Grouping

What it is: a locals block computing the exact tag key/value pair (PatchGroup = "prod-linux") that both the EC2 instances and the Patch Manager maintenance window's target definition must share — defined once, referenced in both places, so they can never silently drift apart.

Why it exists: if the instance tag and the patch group's target tag are defined independently in two different files, a typo in either one means instances silently stop receiving patches with no error raised anywhere.

Count for a Fixed-Size, Truly Interchangeable Resource Set

What it is: unlike Project 02's subnets (which needed for_each because each subnet was individually meaningful), this project uses count for the CloudWatch Log Group's retention configuration replicated identically across a small, genuinely interchangeable set of regions for DR readiness.

Why count is fine here: the items are truly identical and interchangeable — there's no meaningful "name" to key them by, and reordering them has no consequence, which is exactly the narrow case where count remains the simpler, correct choice over for_each.

05 AWS Concepts: Session Manager, Patch Manager & Parameter Store

What is Session Manager

A Systems Manager capability that opens a browser- or CLI-based shell session to an instance over an encrypted channel initiated outbound by the SSM Agent — no inbound security group rule is required at all.

Why it exists

It eliminates the SSH/RDP attack surface entirely while still giving engineers full shell access, with every session's start, end, and (optionally) every keystroke logged centrally.

What is Patch Manager

Applies a defined Patch Baseline (which categories of OS updates to auto-approve, and after what delay) to instances grouped by tag, inside a scheduled Maintenance Window — turning "someone remembers to patch" into "AWS runs this every second Tuesday at 2am."

What is Parameter Store

A hierarchical key-value store for non-secret configuration (feature flags, API endpoints, log levels) — cheaper and simpler than Secrets Manager for values that don't need automatic rotation or resource policies.

Security

Session Manager access is controlled purely by IAM policy — revoking an engineer's access means removing an IAM permission, not rotating or deleting an SSH key from every instance individually.

High Availability

Both Session Manager and Patch Manager are regional managed services with no HA configuration required from us — the SSM Agent on each instance simply needs outbound connectivity to the SSM service endpoint.

Pricing

Session Manager and Patch Manager are free to use; you pay only for the underlying EC2 instances and, if enabled, the CloudWatch Logs/S3 storage for session logs.

Limitations

Requires the SSM Agent installed and running, and either a NAT path or SSM VPC endpoints for fully private subnets to reach the Systems Manager service — a private instance with no such path cannot be managed by SSM at all.

07 Complete Solution Design

Every EC2 instance's IAM role gets the AmazonSSMManagedInstanceCore managed policy attached, and every security group drops its SSH/RDP inbound rules entirely — Session Manager needs zero inbound rules to function. Session logging is configured account-wide to write to the centralized logging bucket from Project 04, giving Security one place to review every shell session across every account.

A Patch Baseline defines auto-approval rules per severity (critical patches after 3 days, others after 7), and a Maintenance Window runs monthly against instances tagged PatchGroup, with the tag value and target definition computed from the same locals block so they cannot drift apart. Parameter Store holds non-secret application configuration under a per-environment hierarchical path (/abc-bank/prod/payments-api/log-level), read by applications via IAM role, no separate credential needed.

locals {
  patch_group_tag_key   = "PatchGroup"                              # Defined ONCE — referenced by both the EC2 instances' tags and the Patch Manager target below

environments/prod/ssm-session-manager.tf

environments/prod/ssm-session-manager.tf
data "aws_ssm_parameter" "latest_al2023_ami" {                     # Always resolves to AWS's current patched Amazon Linux 2023 AMI — never a hardcoded, aging AMI ID
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64"
}

resource "aws_iam_role_policy_attachment" "ssm_core" {               # Grants the instance role permission to register with and be managed by Systems Manager
  role       = aws_iam_role.app_instance.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}

resource "aws_ssm_document" "session_preferences" {                  # Custom document overriding Session Manager's default logging destination
  name            = "abc-bank-session-manager-preferences"
  document_type   = "Session"
  document_format = "JSON"

  content = jsonencode({
    schemaVersion = "1.0"
    description   = "Central session logging preferences for ABC Bank"
    sessionType   = "Standard_Stream"
    inputs = {
      s3BucketName                = var.central_session_log_bucket   # Same centralized-logging pattern from Project 04 — one place Security reviews every session
      s3EncryptionEnabled         = true
      cloudWatchLogGroupName      = aws_cloudwatch_log_group.sessions.name
      cloudWatchEncryptionEnabled = true
    }
  })
}

resource "aws_cloudwatch_log_group" "sessions" {
  name              = "/abc-bank/ssm-sessions"
  retention_in_days = 400                                             # Just over a year — session logs are an audit artifact, retained deliberately longer than routine app logs
}

resource "aws_security_group" "app_instance" {                       # Notice: NO ingress block for SSH/RDP at all — Session Manager needs none
  name   = "app-instance-sg"
  vpc_id = var.vpc_id

  egress {
    from_port   = 443                                                  # Only outbound HTTPS is needed for the SSM Agent to reach the Systems Manager service
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

environments/prod/ssm-patch-manager.tf

environments/prod/ssm-patch-manager.tf
resource "aws_ssm_patch_baseline" "linux_prod" {
  name             = "abc-bank-linux-prod-baseline"
  operating_system = "AMAZON_LINUX_2023"

  approval_rule {
    approve_after_days = 3                                             # Critical/security patches auto-approve quickly — balances stability testing against exposure window
    compliance_level    = "CRITICAL"
    patch_filter {
      key    = "CLASSIFICATION"
      values = ["Security"]
    }
    patch_filter {
      key    = "SEVERITY"
      values = ["Critical", "Important"]
    }
  }

  approval_rule {
    approve_after_days = 7                                             # Everything else gets a longer soak period before auto-approval
    patch_filter {
      key    = "CLASSIFICATION"
      values = ["Security", "Bugfix"]
    }
  }
}

resource "aws_ssm_maintenance_window" "monthly_patch" {
  name     = "abc-bank-prod-monthly-patch"
  schedule = "cron(0 2 ? * TUE#2 *)"                                    # 2 AM on the second Tuesday of every month — standard "Patch Tuesday+1week" cadence
  duration = 4                                                          # Hours — window closes automatically even if a task is still running
  cutoff   = 1                                                          # Stops starting NEW tasks 1 hour before the window ends, letting in-flight tasks finish cleanly
}

resource "aws_ssm_maintenance_window_target" "prod_linux" {
  window_id     = aws_ssm_maintenance_window.monthly_patch.id
  resource_type = "INSTANCE"

  targets {
    key    = "tag:${local.patch_group_tag_key}"                        # References the SAME local value the instances themselves are tagged with
    values = [local.patch_group_tag_value]
  }
}

resource "aws_ssm_maintenance_window_task" "run_patch_baseline" {
  window_id        = aws_ssm_maintenance_window.monthly_patch.id
  task_type        = "RUN_COMMAND"
  task_arn         = "AWS-RunPatchBaseline"                             # AWS-provided document that applies whichever patch baseline is registered as default for the OS
  priority         = 1
  service_role_arn = aws_iam_role.ssm_maintenance.arn
  max_concurrency  = "50%"                                              # Patches half the fleet at a time, keeping the service available throughout the window
  max_errors       = "10%"

  targets {
    key    = "WindowTargetIds"
    values = [aws_ssm_maintenance_window_target.prod_linux.id]
  }

  task_invocation_parameters {
    run_command_parameters {
      parameter {
        name   = "Operation"
        values = ["Install"]
      }
    }
  }
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
AmazonSSMManagedInstanceCore policy attachmentThe single permission an instance role needs to be manageable via Session Manager and Patch ManagerForgetting this attachment — the instance will show as "not connected" in the Systems Manager console even with the SSM Agent installed and running
(local.patch_group_tag_key) = local.patch_group_tag_valueUses a computed local value as a dynamic MAP KEY in a tags block — the parentheses tell Terraform to evaluate the expression as the key, not treat it as a literal stringWriting local.patch_group_tag_key = local.patch_group_tag_value without parentheses — Terraform would try to use the literal text as the key instead of evaluating it
cron(0 2 ? * TUE#2 *)AWS's six-field cron syntax for "2nd Tuesday of every month at 2 AM UTC"Using standard five-field Unix cron syntax — AWS Maintenance Windows require this specific six-field format with a day-of-week/day-of-month distinction
max_concurrency = "50%"Patches half the targeted fleet simultaneously, then the restSetting this to 100% for a Production database tier — patches the whole fleet at once, risking a simultaneous restart across every instance if a patch requires one

11 Execution Flow, Explained Internally

terraform apply — instance registration

After the instance launches with the SSM Agent pre-installed (standard on Amazon Linux 2023) and the IAM policy attached, it self-registers with Systems Manager within a few minutes — no explicit Terraform resource represents "registration" itself; it's a side effect of the agent and IAM role being correctly configured.

Maintenance Window execution (outside Terraform)

Terraform's job ends at defining the schedule, target, and task — AWS itself invokes the patch run at the scheduled cron time; Terraform has no further role until the definition changes.

terraform plan — Parameter Store for_each

Adding a new key to the feature_flags variable shows exactly one new parameter in the plan, keyed by name — removing a flag from the map shows exactly one deletion, nothing else affected.

Always dry-run a new Patch Baseline against a Dev or UAT maintenance window first — an auto-approval rule that's too aggressive could install an untested kernel update across Production's entire fleet in a single scheduled run.

12 CI/CD Integration

.github/workflows/terraform-ssm.yml
name: terraform-ssm
on:
  push:
    branches: [main]
    paths: ["environments/prod/ssm-*.tf"]

jobs:
  apply:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform validate
      - run: terraform plan -out=tfplan
      - run: terraform apply -auto-approve tfplan
      - name: Verify no SSH/RDP ingress remains
        run: |                                                          # Simple guardrail check: fail the pipeline if any security group still opens 22 or 3389
          terraform show -json tfplan | jq -e '
            [.resource_changes[] | select(.type=="aws_security_group") |
             .change.after.ingress[]? | select(.from_port==22 or .from_port==3389)] | length == 0
          '
Add this exact kind of automated guardrail check to CI/CD wherever a project's entire purpose is to remove a class of misconfiguration — it turns "we hope nobody re-adds SSH later" into a pipeline that actively fails the build if they do.

14 Interview Preparation

Q: How does Session Manager provide shell access with no open inbound port?
The SSM Agent on the instance initiates an outbound connection to the Systems Manager service; the engineer's session is relayed through that service-initiated channel, so no inbound listener or open port is ever required on the instance itself.
Q: How do you enforce that patches only auto-install after a soak period?
A Patch Baseline's approval_rule sets approve_after_days per classification/severity — a patch published today isn't eligible for auto-installation until that many days have passed, giving time for any widespread issues to surface first.
Q: Why compute the PatchGroup tag value as a local instead of hardcoding it in two places?
Hardcoding the same string independently in the instance's tags and the maintenance window target risks a silent typo mismatch — instances would simply never be selected for patching, with no error raised anywhere to catch it.
Q: When would you use Parameter Store instead of Secrets Manager?
Parameter Store suits non-secret configuration that doesn't need automatic rotation or cross-account resource policies — cheaper and simpler; Secrets Manager is for values needing rotation, versioning, and fine-grained resource-based sharing, as in Project 06.
Manager round: A pen tester asks how you'd prove no instance has SSH open. What's your answer?
Point to the CI/CD guardrail check that inspects every security group change in the Terraform plan and fails the build if any ingress rule opens port 22 or 3389 — a structural, enforced control, not a policy anyone has to remember to follow.
