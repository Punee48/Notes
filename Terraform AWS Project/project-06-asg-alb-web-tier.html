01The Enterprise Problem This Solves

A golden AMI sitting in the account isn't serving traffic. This project builds the tier that actually runs it in production: an Application Load Balancer distributing traffic across multiple Availability Zones, a Launch Template referencing Project 5's golden AMI, and an Auto Scaling Group that grows and shrinks the fleet based on real load — so a traffic spike is absorbed automatically instead of paging someone to launch instances by hand, and a quiet Tuesday night doesn't leave the team paying for peak-sized capacity around the clock.

02The Story: The Scale-Up That Came Too Late

Production Incident Replay A marketing email goes out at 9 AM and traffic to the checkout page triples in four minutes. The Auto Scaling Group is configured, but its scaling policy is a step-scaling policy tuned for gradual load, checking CPU every five minutes and adding one instance at a time. By the time it catches up, the ALB has already marked half the existing fleet unhealthy — not because the instances crashed, but because they were so saturated that health checks started timing out, and the ALB started pulling "unhealthy" targets out of rotation right when the fleet needed every instance it had. The fix that comes out of the postmortem isn't "add more instances by default" — capacity sized for a false peak is capacity wasted 359 days a year. It's switching from step scaling to target tracking, which reacts continuously and proportionally to load instead of in slow, fixed-size steps, combined with a health check grace period tuned so instances aren't marked unhealthy for being busy rather than actually broken.

03Deep Technical Explanation

Launch Template vs. the deprecated Launch Configuration

Launch Templates are the current, versioned way to define what an ASG launches — they support mixed instance types, multiple versions (so a new AMI version becomes a new template version, not a mutation of the only one), and integrate with Spot Fleet request options used later in Project 19. Launch Configurations are the older, immutable, unversioned predecessor; this project uses Launch Templates exclusively, and any tutorial still using Launch Configurations is teaching a deprecated pattern.

Target tracking vs. step scaling

Target tracking scaling policies work like a thermostat: you declare a target metric value (e.g., "keep average CPU at 50%"), and AWS's own control loop continuously adds or removes capacity to hold that target, reacting faster and more proportionally than a human-authored set of fixed steps. Step scaling requires manually defining CloudWatch alarm thresholds and how many instances to add at each threshold — more control, more upkeep, and as the story above shows, slower to react to a sharp, sudden spike unless tuned very aggressively. This project uses target tracking as the default and shows step scaling as the alternative for cases needing asymmetric scale-out/scale-in behavior.

Health checks: ALB health checks vs. ASG health checks are not the same check

An ASG can check instance health via EC2 status checks alone, or via the ALB target group's health check (health_check_type = "ELB"), which is nearly always the right choice for a web tier — EC2 status checks only catch a dead instance, not an application that's up but returning 500s on every request. The health check grace period is the window after an instance launches before the ASG starts honoring failed health checks against it at all — set too short, a slow-booting instance gets killed and replaced in an endless loop before the application ever finishes starting up.

Deregistration delay and connection draining

When the ASG terminates an instance (scale-in or replacement), the ALB's deregistration delay controls how long the target group keeps routing already-in-flight requests to that instance before forcibly closing connections — too short, and in-flight user requests get dropped mid-response; too long, and scale-in events take unnecessarily long to complete.

05Step-by-Step Implementation

envs/prod/alb.tf 
resource "aws_lb" "web" {
  name               = "acme-web-alb"
  internal           = false
  load_balancer_type = "application"
  security_groups    = [aws_security_group.alb.id]
  subnets            = values(module.network.public_subnet_ids) # spans every public subnet from Project 2

  enable_deletion_protection = true # blocks an accidental "terraform destroy" of prod's front door
}

resource "aws_lb_target_group" "web" {
  name     = "acme-web-tg"
  port     = 80
  protocol = "HTTP"
  vpc_id   = module.network.vpc_id
  target_type = "instance"

  health_check {
    path                = "/healthz" # app-level endpoint, not just TCP reachability
    interval            = 15
    healthy_threshold   = 2
    unhealthy_threshold = 3 # tolerates a couple of slow responses before pulling a target
    matcher             = "200"
  }

  deregistration_delay = 30 # seconds — in-flight requests get this long to finish before a hard cut
}

resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.web.arn
  port              = 443
  protocol          = "HTTPS"
  certificate_arn   = var.acm_certificate_arn
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.web.arn
  }
}
envs/prod/asg.tf 
resource "aws_launch_template" "web" {
  name_prefix   = "acme-web-"
  image_id      = data.aws_ami.app.id # resolved by Project 5's most-recent AMI data source
  instance_type = "t3.small"

  iam_instance_profile {
    name = aws_iam_instance_profile.web.name # scoped role from Project 4's least-privilege pattern
  }

  vpc_security_group_ids = [aws_security_group.web.id]

  # A new AMI version automatically becomes a new launch template
  # version — this block does not need to change when Project 5 bakes
  # a new image, since the AMI data source re-resolves at each plan.
  tag_specifications {
    resource_type = "instance"
    tags           = { Name = "acme-web" }
  }
}

resource "aws_autoscaling_group" "web" {
  name                = "acme-web-asg"
  vpc_zone_identifier = values(module.network.private_subnet_ids) # instances launch into the private tier
  target_group_arns   = [aws_lb_target_group.web.arn]
  health_check_type          = "ELB" # defer to the ALB's app-level health check, not just EC2 status
  health_check_grace_period  = 120 # seconds of grace after launch before failed checks count

  min_size         = 2
  max_size         = 10
  desired_capacity = 2

  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest" # always launch the newest template version, i.e. newest AMI
  }

  lifecycle {
    create_before_destroy = true # replace the ASG without a capacity gap on a rare full-recreate
  }
}

resource "aws_autoscaling_policy" "cpu_target_tracking" {
  name                   = "target-tracking-cpu"
  autoscaling_group_name = aws_autoscaling_group.web.name
  policy_type            = "TargetTrackingScaling"

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value = 50.0 # AWS's control loop adds/removes capacity continuously to hold this
  }
}

Plain-English walkthrough

The launch template intentionally never hardcodes an AMI ID directly in this file — it points at data.aws_ami.app.id from Project 5, so every new golden AMI bake is picked up automatically the next time this configuration is applied, without editing this file at all. health_check_type = "ELB" is the single most important line for catching the failure mode in this project's story: it means the ASG trusts the ALB's opinion of instance health (an actual HTTP request to /healthz), not just whether the EC2 instance is technically running. The target tracking policy replaces slower step-scaling with a continuous control loop — AWS handles the "how many instances, how fast" math internally rather than a human pre-defining fixed thresholds.

06Failure Scenarios — What Breaks in Real Life

Failure: health check grace period too short causes a launch loop An application takes 90 seconds to fully start, but the grace period is set to 30. The ASG marks the instance unhealthy before it ever finishes booting, terminates it, launches a replacement, and repeats indefinitely. Debug: check the application's actual cold-start time and set the grace period comfortably above it — this is a common root cause of an ASG that appears to be "stuck" cycling instances endlessly.
Failure: scale-in kills instances mid-request Deregistration delay is set to 0 or very low, and users see dropped connections exactly when the ASG scales in. Debug: raise deregistration delay to comfortably exceed the slowest legitimate request duration, and confirm the application handles SIGTERM gracefully rather than dropping connections instantly.
Failure: target tracking policy fights a manually-set desired_capacity An engineer manually sets desired_capacity via the console during an incident, and the next Terraform apply reverts it back to the value in code, right as the target tracking policy was also trying to adjust it — creating a confusing flapping capacity count. Debug: during an active incident, use Terraform to change desired_capacity (or temporarily suspend the scaling policy), not the console, so state and reality never diverge.

07Interview Talking Points

"How would you design auto scaling for a web tier with unpredictable traffic spikes?"
Lead with target tracking over step scaling for its continuous reaction, tie health check type to ELB rather than EC2 status for app-level accuracy, and mention tuning the health check grace period against actual application boot time as a concrete, learned detail.
"What happens to in-flight requests when an instance is scaled in?"
Explain deregistration delay precisely and its tradeoff: too short drops live requests, too long slows down legitimate scale-in events — and that the right value is driven by the application's actual max request duration.
