01The Enterprise Problem This Solves

Every AWS workload in this handbook — the ALB in Project 6, the RDS instance in Project 7, the EKS cluster in Project 11 — needs a VPC to live in, and every one of those projects will ask the same architectural question: where do public-facing resources go, where do application-tier resources go, and where does data live so it's never directly reachable from the internet? Copy-pasting VPC HCL into every project's root module means every inconsistency and every subnetting mistake gets duplicated 24 times over the rest of this handbook. The enterprise fix is a single, versioned, parameterized VPC module — write the network topology logic once, call it with different inputs for every environment and every future project.

02The Story: The Subnet That Was One CIDR Block Too Small

Production Incident Replay Six months after launch, the platform team gets a page: the Auto Scaling group for the checkout service can't launch new instances during a Black-Friday-style traffic spike. Not a quota problem, not an AMI problem — the private application subnet in us-east-1a is completely out of IP addresses. When the VPC was first hand-built eighteen months earlier, someone eyeballed a /26 for each private subnet — 64 addresses, minus 5 AWS reserves per subnet — and it looked like plenty at the time. Nobody wrote down the sizing rationale anywhere, and nobody built headroom for horizontal scaling into the plan. Because the network was created by hand, resizing it means either a disruptive re-CIDR of an already-running production VPC, or provisioning a parallel subnet and migrating live traffic across it under pressure, during the exact week traffic is highest.

The module built in this project treats subnet sizing as a parameter, computed consistently with cidrsubnet() from a single VPC CIDR input, with headroom for tier growth designed in from day one — so "how big should this subnet be" is a decision made once, deliberately, and documented in code, not improvised by whoever happened to be provisioning that day.

03Deep Technical Explanation

The three-tier subnet model

Enterprise network design almost universally splits a VPC into three logical tiers, each with a different exposure level. Public subnets hold resources that need a direct route to an Internet Gateway — load balancers, NAT gateways themselves, bastion hosts. Private (application) subnets hold compute that needs outbound internet access (for package installs, API calls) but must never accept unsolicited inbound connections from the internet — reached only through the NAT Gateway sitting in the public tier. Data subnets hold databases and caches with no route to the internet at all, in either direction — reachable only from the private application tier, on specific ports, via security groups. This project builds all three as a single reusable module, replicated across every Availability Zone the caller asks for.

Why for_each over count for subnet resources

Early Terraform code often used count with a list of AZs, but count identifies resources by their numeric index in state. If an AZ in the middle of the list is ever removed, every subnet after it shifts index, and Terraform proposes destroying and recreating subnets that never actually changed. for_each over a map keyed by AZ name avoids that entirely — a resource's identity in state is tied to its AZ name, not its position, so removing one AZ only touches that AZ's subnet.

Deterministic CIDR math with cidrsubnet()

Rather than hardcoding CIDR blocks per subnet, the module takes one VPC-wide CIDR block and carves it up programmatically with the built-in cidrsubnet(prefix, newbits, netnum) function — newbits controls how many additional bits are added to the prefix (determining subnet size), and netnum picks which specific subnet-sized block to return. Driving this from a tier index and an AZ index means the entire subnetting scheme for a 10-AZ, 3-tier VPC is generated from about a dozen lines of HCL, not 30 hardcoded CIDR strings that someone has to keep mentally consistent.

NAT Gateway placement and cost/availability tradeoff

A NAT Gateway is AWS-managed but zonal — it lives in one AZ, and if that AZ has an outage, private subnets routed through it lose outbound connectivity even though the private subnets themselves are healthy in other AZs. The enterprise-correct pattern is one NAT Gateway per AZ, each private subnet routing only through the NAT Gateway in its own AZ — eliminating cross-AZ data transfer charges and avoiding a single NAT Gateway becoming a blast-radius single point of failure for every AZ at once. This module supports both a single shared NAT Gateway (cheaper, for dev) and one-per-AZ (resilient, for prod) as a boolean input.

5.1 — Module directory layout

modules/vpc/variables.tf 
variable "name" {
  description = "Name prefix applied to every resource this module creates"
  type        = string
}

variable "vpc_cidr" {
  description = "CIDR block for the whole VPC, e.g. 10.0.0.0/16"
  type        = string
}

variable "azs" {
  description = "List of Availability Zones to spread the three tiers across"
  type        = list(string)
}

variable "one_nat_per_az" {
  description = "true = one NAT Gateway per AZ (prod). false = single shared NAT (dev/cost-saving)"
  type        = bool
  default     = false
}

variable "tags" {
  description = "Common tags merged onto every resource"
  type        = map(string)
  default     = {}
}
modules/vpc/main.tf 
# --- Convert the AZ list into a map keyed by AZ name, with a stable
# numeric index used only for CIDR math — this is what lets us use
# for_each instead of count for every resource below. ---
locals {
  az_map = { for idx, az in var.azs : az => idx }

  # Tier 0 = public, Tier 1 = private/app, Tier 2 = data.
  # newbits=8 on a /16 gives /24s — 251 usable IPs per subnet, per tier, per AZ.
  public_cidrs  = { for az, idx in local.az_map : az => cidrsubnet(var.vpc_cidr, 8, idx) }
  private_cidrs = { for az, idx in local.az_map : az => cidrsubnet(var.vpc_cidr, 8, idx + 10) }
  data_cidrs    = { for az, idx in local.az_map : az => cidrsubnet(var.vpc_cidr, 8, idx + 20) }
  # Offsetting by 10 and 20 leaves headroom to add up to 10 more AZs
  # to any tier later without CIDR blocks from different tiers colliding.
}

resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true # required for private DNS on many AWS-managed services (RDS, EKS)
  tags = merge(var.tags, { Name = "${var.name}-vpc" })
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id
  tags   = merge(var.tags, { Name = "${var.name}-igw" })
}

# ---------- PUBLIC TIER ----------
resource "aws_subnet" "public" {
  for_each                = local.public_cidrs
  vpc_id                  = aws_vpc.this.id
  availability_zone       = each.key
  cidr_block              = each.value
  map_public_ip_on_launch = true # instances here get a public IP automatically (ALBs, bastions)
  tags = merge(var.tags, { Name = "${var.name}-public-${each.key}", Tier = "public" })
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.this.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.this.id # every public subnet's default route goes to the IGW
  }
  tags = merge(var.tags, { Name = "${var.name}-public-rt" })
}

resource "aws_route_table_association" "public" {
  for_each       = aws_subnet.public
  subnet_id      = each.value.id
  route_table_id = aws_route_table.public.id # one shared public route table is fine — its route never differs by AZ
}

# ---------- NAT GATEWAYS ----------
resource "aws_eip" "nat" {
  # One EIP per NAT Gateway we're about to create — key set depends on
  # one_nat_per_az: either every AZ, or just the first AZ.
  for_each = var.one_nat_per_az ? local.az_map : { (var.azs[0]) = 0 }
  domain   = "vpc"
  tags     = merge(var.tags, { Name = "${var.name}-nat-eip-${each.key}" })
}

resource "aws_nat_gateway" "this" {
  for_each       = aws_eip.nat
  allocation_id = each.value.id
  subnet_id     = aws_subnet.public[each.key].id # NAT Gateway must sit in a public subnet
  tags          = merge(var.tags, { Name = "${var.name}-nat-${each.key}" })
  depends_on    = [aws_internet_gateway.this] # NAT provisioning fails if the IGW isn't attached yet
}

# ---------- PRIVATE (APP) TIER ----------
resource "aws_subnet" "private" {
  for_each          = local.private_cidrs
  vpc_id            = aws_vpc.this.id
  availability_zone = each.key
  cidr_block        = each.value
  tags = merge(var.tags, { Name = "${var.name}-private-${each.key}", Tier = "private" })
}

resource "aws_route_table" "private" {
  # One route table PER AZ (not shared) so each AZ's default route can
  # point at its own NAT Gateway when one_nat_per_az = true.
  for_each = local.az_map
  vpc_id   = aws_vpc.this.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = var.one_nat_per_az ? aws_nat_gateway.this[each.key].id : aws_nat_gateway.this[var.azs[0]].id
  }
  tags = merge(var.tags, { Name = "${var.name}-private-rt-${each.key}" })
}

resource "aws_route_table_association" "private" {
  for_each       = aws_subnet.private
  subnet_id      = each.value.id
  route_table_id = aws_route_table.private[each.key].id
}

# ---------- DATA TIER (no route to the internet, in either direction) ----------
resource "aws_subnet" "data" {
  for_each          = local.data_cidrs
  vpc_id            = aws_vpc.this.id
  availability_zone = each.key
  cidr_block        = each.value
  tags = merge(var.tags, { Name = "${var.name}-data-${each.key}", Tier = "data" })
}

resource "aws_route_table" "data" {
  # Deliberately no "route" block at all beyond the implicit local VPC
  # route Terraform/AWS adds automatically — no IGW, no NAT, no egress.
  vpc_id = aws_vpc.this.id
  tags   = merge(var.tags, { Name = "${var.name}-data-rt" })
}

resource "aws_route_table_association" "data" {
  for_each       = aws_subnet.data
  subnet_id      = each.value.id
  route_table_id = aws_route_table.data.id
}

Plain-English walkthrough

The locals block is the heart of the module: it turns a list of AZ strings into a stable map, then derives three separate CIDR maps — one per tier — by adding a fixed offset (10, 20) to the AZ index before passing it into cidrsubnet(). That offset trick is what guarantees the public, private, and data tiers can never accidentally compute the same CIDR block even as more AZs are added later. Every subnet-level resource then uses for_each over one of those maps, so state tracks each subnet by its AZ name, not by list position — add an AZ, and only that AZ's resources appear in the plan; nothing else moves. The private-tier route tables are deliberately not shared across AZs (unlike the public tier's single shared table) specifically so each AZ can route through its own NAT Gateway when resilience is worth the extra cost — that's the one_nat_per_az ternary doing its job in both the EIP and route-table resources. The data tier's route table has no route block beyond what AWS implicitly provides for in-VPC traffic — that absence is the security control, not an oversight.

06Failure Scenarios — What Breaks in Real Life

Failure: single NAT Gateway becomes an AZ-wide outage Dev's one_nat_per_az = false means every private subnet across every AZ routes through one NAT Gateway. If that AZ has an issue, every private subnet in every other AZ loses outbound internet access too, even though those AZs are otherwise perfectly healthy. Debug: this is expected and acceptable for dev — it's a deliberate cost tradeoff — but if it shows up in prod, check that one_nat_per_az is actually set to true in that environment's .tfvars.
Failure: adding an AZ mid-project triggers subnet recreation An engineer inserts a new AZ in the middle of the azs list instead of appending it. Because the module keys everything off the AZ name via for_each, this alone doesn't cause recreation — but if someone had used count instead (an easy mistake when extending the module), every subnet after the insertion point would show as "destroy and recreate" in the plan. Debug: always run terraform plan and read the change summary carefully before apply after any AZ list change — a plan proposing to destroy subnets that shouldn't be affected is the tell that count crept back into the code somewhere.
Failure: data subnet accidentally gets internet access A future engineer, troubleshooting connectivity for a data-tier resource, adds a NAT route to the data route table "just to test something" and forgets to remove it. Debug: this is exactly why compliance scanning in Project 22 (tfsec/Checkov) gets wired into CI before this handbook is done — a policy check that flags any route table associated with a subnet tagged Tier=data having a non-local route catches this before it ever reaches a real apply.

07Interview Talking Points

"How would you design a VPC module that multiple teams can reuse safely?"
Talk about parameterizing CIDR size and AZ count rather than hardcoding them, using for_each keyed by AZ name for resource stability, and exposing outputs as maps keyed by AZ so downstream modules (ALB, RDS) can consume exactly the subnet they need without guessing list order.
"Walk me through your three-tier subnet strategy and why data has no internet route."
Frame it as defense in depth: even if an application-tier instance is compromised, the data tier's route table makes exfiltration or inbound compromise of the database over the public internet structurally impossible, independent of security group rules, which are a second, separate layer.
