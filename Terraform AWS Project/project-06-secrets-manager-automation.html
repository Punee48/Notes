PROJECT 06 OF 40 · INTERMEDIATE

Secrets Manager Automation — Rotation, Sharing & Least Privilege

The payments team is manually rotating a database password by editing a Kubernetes secret every 90 days, on a calendar reminder that has already been missed twice. Today we make credential rotation fully automatic, share the secret safely across accounts, and never let a plaintext password touch our Terraform state.

01 The Banking Story

ABC Bank's security policy requires database credentials to rotate every 90 days. In practice, the payments-api team rotates their RDS password by hand: generate a new one, update it in the database, update the Kubernetes secret, restart the pods, and hope nothing else still references the old password. It's been missed twice already — once by three weeks, discovered only during a compliance review.

Separately, the CI/CD pipeline (running in a shared Tooling account) needs read access to this same secret to inject it during deployment — currently done by an engineer manually copying the password value into the pipeline's own secret store, a second place the plaintext password now lives, unrotated and un-audited.

Our manager's brief: "Automate the rotation completely — no human touches the password, ever. Share the secret with the Tooling account properly, with a resource policy, not a copy-paste. And nothing — not our Terraform state, not our Git history — should ever contain the actual password value."

02 Business Requirement, Risk & Impact

Business Requirement

Database credentials must rotate automatically on a fixed schedule, with zero manual steps and zero plaintext exposure anywhere in the toolchain.

Customer Requirement

The CI/CD pipeline needs read-only, audited access to the current credential value at deploy time, without a second copy existing anywhere else.

Current Infrastructure

RDS instance with a password set once at creation; a Kubernetes secret manually updated by an engineer every rotation cycle.

Existing Manual Process

An engineer generates a new password, updates the database, updates the Kubernetes secret, and manually notifies the CI/CD team to update their copy — four manual, error-prone steps.

Problems With Current Process

  • Missed rotations violate the bank's own 90-day security policy
  • The password exists in plaintext in at least two places (Kubernetes secret, CI/CD store)
  • No audit trail of who saw or used the plaintext value

Business Challenges

PCI-DSS and internal banking security standards both require documented, enforced credential rotation — a missed manual rotation is itself a compliance finding.

Risk Analysis

High: a leaked plaintext password in a second, less-controlled store (like a CI/CD tool) significantly widens the blast radius of any single credential leak.

Business Impact

A compliance finding around credential rotation can delay certification renewals the bank needs to continue processing card payments.

03 Why AWS Secrets Manager, and What We Rejected

Why Secrets Manager over the alternatives

Secrets Manager has native, built-in automatic rotation for RDS (via an AWS-provided or custom Lambda function), fine-grained resource-based policies for exact cross-account sharing, and full CloudTrail integration — every read of the secret value is itself an audited API call, unlike a Kubernetes secret which is just base64-encoded, not encrypted or individually access-logged by default.

04 Terraform Concepts You Must Understand Before We Build

Sensitive Variables & Outputs

What it is: marking a variable or output block with sensitive = true tells Terraform to redact that value from CLI output (plan, apply, console logs) — it does not encrypt it inside the state file itself.

Why it exists: without it, a generated database password would print in plaintext in every CI/CD log for anyone with pipeline read access to see — a direct leak vector we must close.

Critical nuance: sensitive = true hides the value from output/logs, but the raw value is still stored in the Terraform state file — this is exactly why Project 01's S3 backend encryption and tightly scoped IAM access to the state bucket matter as much as they do.

Best practice: for genuinely sensitive generated values, prefer letting Secrets Manager (or the random_password resource feeding directly into it) hold the value, and reference it by ARN elsewhere — never pass a secret value through a plain variable if you can avoid it.

The random Provider

What it is: a Terraform provider with no real infrastructure API — it just generates and stores random values (like random_password) as Terraform-managed resources, so the same value is reused consistently across plans instead of regenerating every time.

Why it exists: the very first password for a new RDS instance needs to come from somewhere — random_password generates it once, and because it's a real Terraform resource, it persists in state rather than changing on every apply.

Common mistake: regenerating a random_password by changing its length or character-set arguments without realizing this forces a new password and, if not paired with an update to the actual RDS instance, breaks the running application's existing connection.

Provisioners & null_resource (Used Sparingly, as a Last Resort)

What it is: a null_resource is a resource with no real infrastructure backing it, typically paired with a provisioner block (like local-exec) to run an arbitrary local command as part of the Terraform lifecycle.

Why we use it here, narrowly: immediately after Secrets Manager rotation is first configured, we trigger one initial rotation via the AWS CLI so the very first password (generated by random_password at creation time) is replaced by one Secrets Manager itself generated and knows how to rotate going forward — closing the gap between "created" and "under full rotation management."

Why provisioners are a last resort, not a first choice: Terraform has no visibility into what a local-exec command actually did — it can't plan, diff, or safely reconcile drift the way it can for a real resource. We reach for it here only because triggering a one-time rotation has no equivalent native resource, and we scope the blast radius by making it a single, idempotent AWS CLI call.

Best practice: always prefer a real provider resource over a provisioner when one exists (it almost always does for common infrastructure); when a provisioner truly is necessary, keep the command idempotent and narrowly scoped, exactly as we do here.

05 AWS Concepts: Secrets Manager Rotation & Cross-Account Sharing

What is Secrets Manager Rotation

A scheduled Lambda function (AWS-provided for RDS, or custom) that Secrets Manager invokes automatically — it generates a new credential, updates the database, tests the new credential, then marks it as the current version, all without human involvement.

Why it exists

It replaces exactly the four manual steps in our story with one automated, tested, repeatable workflow that cannot be forgotten on a calendar.

Resource-Based Policies for Cross-Account Sharing

A policy attached directly to the secret itself (not to an IAM role) that names the Tooling account as allowed to call secretsmanager:GetSecretValue — the CI/CD pipeline's own IAM role in the Tooling account still separately needs permission to assume into or call this, giving the same two-layer trust model we saw with S3 in Project 04.

Security: Versioning, Not Overwriting

Secrets Manager never overwrites a secret value in place — each rotation creates a new version, staged and tested before being promoted to "current," so a failed rotation can roll back to the previous working version.

High Availability

Secrets Manager is a regional, highly available managed service — no HA configuration is required on our part.

Pricing

Charged per secret per month plus per API call — with a database credential accessed only at pod startup and rotated quarterly, cost is minimal compared to the risk it removes.

Limitations

The rotation Lambda needs network access to both Secrets Manager's API and the RDS instance — for a private RDS instance, that means the Lambda must run inside the same VPC's private subnets, with a VPC endpoint or NAT path to reach Secrets Manager.

07 Complete Solution Design

A random_password resource generates the database's very first password, used only to bootstrap the RDS instance at creation — this value is never referenced anywhere else in the codebase. The password is immediately stored as an aws_secretsmanager_secret_version, and aws_secretsmanager_secret_rotation attaches AWS's pre-built RDS rotation Lambda on a 90-day schedule.

A resource policy on the secret grants the Tooling account's CI/CD role read-only GetSecretValue access — nothing else, and no write or delete permissions cross the account boundary. Finally, a single null_resource with a local-exec provisioner triggers one immediate rotation right after setup, so the bootstrap password from random_password is replaced by a Secrets-Manager-generated one before the application ever starts using it in earnest.

09 Implementation — Full Production Code

environments/prod/secrets.tf

environments/prod/secrets.tf
resource "random_password" "db_bootstrap" {                     # Only ever used ONCE, to bootstrap the RDS instance's initial password
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?"                       # Excludes characters RDS's password field disallows, like '@', '/', '"'
}

resource "aws_secretsmanager_secret" "db_credential" {
  name        = "payments-api/db-credential"
  description = "RDS credential for the payments-api database, rotated automatically every 90 days"
  kms_key_id  = var.secrets_kms_key_arn                            # Dedicated KMS key for secrets, separate from the logging key in Project 04
}

resource "aws_secretsmanager_secret_version" "db_credential_initial" {
  secret_id = aws_secretsmanager_secret.db_credential.id
  secret_string = jsonencode({                                     # Secrets Manager's RDS rotation Lambda expects this exact JSON shape
    username = "payments_app_user"
    password = random_password.db_bootstrap.result                  # The ONLY place this generated value is ever referenced
    engine   = "postgres"
    host     = aws_db_instance.payments.address
    port     = 5432
    dbname   = "payments"
  })

  lifecycle {
    ignore_changes = [secret_string]                                # After rotation takes over, Secrets Manager updates this value directly — Terraform must stop trying to reset it back
  }
}

resource "aws_secretsmanager_secret_rotation" "db_credential" {
  secret_id           = aws_secretsmanager_secret.db_credential.id
  rotation_lambda_arn = data.aws_lambda_function.rds_rotation.arn    # AWS-provided rotation function, deployed via the AWS Secrets Manager rotation Lambda SAR app

  rotation_rules {
    automatically_after_days = 90                                    # Matches ABC Bank's 90-day security policy exactly
  }
}

data "aws_iam_policy_document" "secret_resource_policy" {
  statement {
    sid     = "AllowToolingAccountReadOnly"
    effect  = "Allow"
    actions = ["secretsmanager:GetSecretValue", "secretsmanager:DescribeSecret"]  # Deliberately narrow — read-only, no PutSecretValue, no DeleteSecret
    principals {
      type        = "AWS"
      identifiers = [var.tooling_account_id]
    }
    resources = ["*"]                                                 # "*" here means "this secret" — resource policies are implicitly scoped to the secret they're attached to
  }
}

resource "aws_secretsmanager_secret_policy" "db_credential" {
  secret_arn = aws_secretsmanager_secret.db_credential.arn
  policy     = data.aws_iam_policy_document.secret_resource_policy.json
}

resource "null_resource" "trigger_initial_rotation" {               # Last-resort provisioner use, deliberately narrow and idempotent
  triggers = {
    rotation_configured = aws_secretsmanager_secret_rotation.db_credential.id  # Re-runs only if the rotation resource itself changes, not on every apply
  }

  provisioner "local-exec" {
    command = "aws secretsmanager rotate-secret --secret-id ${aws_secretsmanager_secret.db_credential.id} --region ${var.aws_region}"
  }

  depends_on = [aws_secretsmanager_secret_rotation.db_credential]     # Must run AFTER rotation is configured, or the API call has nothing to rotate against
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
lifecycle { ignore_changes = [secret_string] }Stops Terraform from reverting the secret back to its original bootstrap value after Secrets Manager rotates itOmitting this — every subsequent terraform apply would silently overwrite the rotated password back to the old bootstrap value, breaking the application
random_password.db_bootstrap.result used in exactly two placesBootstraps both the RDS instance and the initial secret version consistentlyGenerating a SECOND, different random password for the secret than the one set on the RDS instance — they must match on first creation, or the app can't authenticate until the first rotation runs
null_resource + local-execRuns a one-time AWS CLI call as part of the apply, outside Terraform's normal resource modelReaching for this pattern as a general-purpose escape hatch — always check for a native resource first; here, no native Terraform resource represents "trigger one rotation now"
Secret resource policy resources = ["*"]Refers to "this secret" implicitly, since resource-based policies are attached directly to a specific resourceConfusing this with an IAM identity-based policy, where "*" would mean literally every resource — the two policy types behave differently for the same wildcard

11 Execution Flow, Explained Internally

terraform plan

Because secret_string is under ignore_changes, a plan run after a real rotation has occurred correctly shows no diff for that attribute — even though the actual value in AWS has changed.

terraform apply — provisioner execution

The local-exec provisioner runs from wherever terraform apply itself is executing — typically the CI/CD runner — which must have the AWS CLI installed and credentials with secretsmanager:RotateSecret permission.

terraform destroy

Destroys the rotation schedule and secret policy first, then the secret itself (Secrets Manager applies a recovery window by default, so the secret isn't immediately unrecoverable), then the RDS instance.

A provisioner's success or failure is reported by Terraform, but Terraform cannot roll back what the command already did if a later step in the same apply fails — keep provisioner commands idempotent, exactly like the CLI rotation call here, which is always safe to re-run.

12 CI/CD Integration

.github/workflows/terraform-secrets.yml
name: terraform-secrets
on:
  push:
    branches: [main]
    paths: ["environments/prod/secrets.tf", "environments/prod/rds.tf"]

jobs:
  apply:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4                  # Needed so the local-exec provisioner's AWS CLI call has credentials on the runner
        with:
          role-to-assume: ${{ secrets.PROD_DEPLOY_ROLE_ARN }}
          aws-region: ap-south-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform plan -out=tfplan
      - run: terraform apply -auto-approve tfplan
Because this pipeline's role directly triggers a real secret rotation via local-exec, scope that role's secretsmanager:RotateSecret permission to this one specific secret ARN — not a wildcard across every secret in the account.

14 Interview Preparation

Q: Does marking a Terraform variable as sensitive encrypt it in the state file?
No — sensitive = true only redacts the value from CLI output and logs; the raw value is still stored in the state file, which is why encrypting and tightly restricting access to the state backend matters just as much.
Q: Why use ignore_changes on the secret version instead of just leaving rotation to update it freely?
Without ignore_changes, every subsequent terraform apply would see the rotated value as drift from the code's original bootstrap value and try to reset it back — breaking the application's live credentials.
Q: When is it acceptable to use a provisioner in Terraform?
Only when no native resource exists for the action needed, the command is idempotent and safely re-runnable, and the blast radius is narrow and well understood — as a last resort, not a first choice.
Q: How does cross-account secret sharing here differ from the RAM share in Project 03?
RAM shares an actual AWS resource (like a Transit Gateway) for the receiving account to attach to and manage; a Secrets Manager resource policy instead grants specific API actions (like GetSecretValue) on a resource that stays owned entirely by the source account — no attachment or acceptance step is needed on the other side.
Manager round: How would you prove to an auditor that nobody manually rotated this credential?
Point to the CloudTrail record of the rotation Lambda's automated API calls on a consistent 90-day cadence, cross-referenced against IAM access logs showing no human principal called PutSecretValue directly during that period.
