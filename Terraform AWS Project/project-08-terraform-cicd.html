01The Enterprise Problem This Solves

Every project so far in this handbook has been applied manually, by hand, from an engineer's laptop. That was deliberate for learning — but no enterprise team runs production Terraform this way. This project builds the pipeline that should sit in front of everything built so far: every pull request automatically produces a terraform plan posted as a PR comment for human review, merging to main automatically runs apply against that exact reviewed plan, and a scheduled job continuously checks whether reality has quietly diverged from what Terraform thinks it manages.

02The Story: The Apply That Didn't Match What Got Reviewed

Production Incident Replay A PR gets reviewed carefully — the reviewer reads the diff, checks the plan output pasted into the PR description by hand, and approves it. But the plan was generated locally, by the PR author, four days earlier, before two other unrelated PRs merged to main in between. By the time this PR is actually merged and someone runs apply from their laptop, the real state of main has moved — but the "plan" everyone reviewed and approved was already stale. The apply that actually executes is not the one the team signed off on. Nothing malicious happened; the process itself had no guarantee that plan and apply were ever the same operation. The fix isn't "review more carefully" — it's removing the human gap between plan and apply entirely: generate the plan in CI, save it as an artifact, and force the apply step to consume that exact saved plan file, so what gets reviewed is provably identical to what gets executed.

03Deep Technical Explanation

Plan-on-PR: making review possible before anything changes

A CI job triggered on every pull request runs terraform plan against the target environment and posts the output as a PR comment, giving human reviewers the exact resource-level diff before any code merges — turning "does this look right" from a guess based on reading HCL into a concrete, reviewable diff of real infrastructure changes.

Apply-on-merge, from the same saved plan — not a fresh one

The critical detail this project's story hinges on: the apply step must consume the identical plan file the PR comment was generated from (terraform plan -out=tfplan, then later terraform apply tfplan), not re-run plan fresh and hope it matches. Running a fresh plan at apply time reopens the exact gap that caused the incident above.

OIDC federation instead of long-lived AWS keys in CI

Building directly on Project 4's least-privilege IAM work, the pipeline authenticates to AWS via GitHub's OIDC provider and a role scoped to this specific repo and branch — no static AWS_ACCESS_KEY_ID secret sitting in GitHub Actions secrets waiting to be exfiltrated or to outlive someone's departure from the team.

Drift detection: catching changes Terraform didn't make

A scheduled job runs terraform plan against every environment on a fixed cadence with no code change involved, purely to detect drift — real infrastructure that no longer matches what Terraform's state expects, usually caused by a manual console change. A non-empty plan from this job is itself the alert.

05Step-by-Step Implementation

.github/workflows/terraform-pr-plan.yml 
on:
  pull_request:
    paths: ['envs/prod/**'] # only trigger when prod's actual config changes

permissions:
  id-token: write   # required for OIDC — this is what lets GitHub mint a short-lived AWS token
  contents: read
  pull-requests: write # required to post the plan as a PR comment

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults:
      run: { working-directory: envs/prod }
    steps:
      - uses: actions/checkout@v4

      - name: Assume plan-only OIDC role
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci-plan-prod # scoped to plan actions only, no write access
          aws-region: us-east-1

      - uses: hashicorp/setup-terraform@v3

      - name: terraform fmt check
        run: terraform fmt -check -recursive # fails the build on inconsistent formatting, cheap and fast

      - name: terraform init & validate
        run: |
          terraform init
          terraform validate

      - name: terraform plan
        run: terraform plan -out=tfplan -no-color | tee plan_output.txt

      - name: Upload plan artifact
        uses: actions/upload-artifact@v4
        with: { name: tfplan-${{ github.event.pull_request.number }}, path: envs/prod/tfplan }
        # this exact binary plan file is what "apply" will consume later —
        # never regenerated, only reused.

      - name: Post plan as PR comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('envs/prod/plan_output.txt', 'utf8');
            github.rest.issues.createComment({
              ...context.repo, issue_number: context.issue.number,
              body: `### Terraform Plan\n\`\`\`\n${plan}\n\`\`\``
            });
.github/workflows/terraform-apply.yml 
on:
  push:
    branches: [main]
    paths: ['envs/prod/**']

permissions:
  id-token: write
  contents: read

jobs:
  apply:
    runs-on: ubuntu-latest
    environment: production # GitHub Environments feature — enables a required-reviewer gate below
    defaults:
      run: { working-directory: envs/prod }
    steps:
      - uses: actions/checkout@v4

      - name: Assume apply-only OIDC role
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci-apply-prod # a DIFFERENT, more privileged role than the plan job's
          aws-region: us-east-1

      - uses: hashicorp/setup-terraform@v3
      - name: terraform init
        run: terraform init

      # NOTE: no "terraform plan" step here on purpose. In a real setup,
      # the plan artifact from the merged PR's plan job is downloaded and
      # reused here via actions/download-artifact, keyed off the merge
      # commit's originating PR — apply never generates its own fresh plan.
      - name: terraform apply (from the reviewed plan file)
        run: terraform apply -auto-approve tfplan
.github/workflows/terraform-drift-detection.yml (excerpt) 
on:
  schedule:
    - cron: "0 */6 * * *" # every 6 hours — catches drift well before it becomes an incident

jobs:
  drift-check:
    runs-on: ubuntu-latest
    steps:
      # ... same checkout/OIDC/init steps as the plan job above ...
      - name: Check for drift
        run: |
          terraform plan -detailed-exitcode -no-color
          # exit code 0 = no changes (no drift). exit code 2 = changes found
          # (drift!). exit code 1 = an actual error. Alerting logic branches
          # on this exit code in a follow-up step, not shown here.

Plain-English walkthrough

Two separate IAM roles — ci-plan-prod and ci-apply-prod — deliberately give the PR job narrower permissions than the merge job, following Project 4's least-privilege pattern: a PR from an untrusted branch should never be able to actually mutate infrastructure, only read enough to compute a plan. The apply workflow's comment calling out the missing fresh plan step is the single most important design decision in this project — apply consumes the artifact the plan job already produced and humans already reviewed, closing the exact gap that caused the incident in this project's story. The drift detection job reuses -detailed-exitcode, a flag purpose-built for exactly this: distinguishing "nothing changed" from "something changed" from "something broke," each with a different alerting response.

06Failure Scenarios — What Breaks in Real Life

Failure: two PRs against the same resource merge in quick succession PR A's plan is generated, reviewed, and approved. Before it merges, PR B — touching the same resource — merges first. PR A's saved plan file is now stale relative to real state, and applying it could fail or, worse, silently revert part of PR B's change. Debug: the apply job should re-validate that the merge commit's plan file was generated from a state matching the current main, and CI should refuse to apply a plan artifact older than the most recent successful apply — treat a stale-plan apply attempt as a hard failure, not a warning.
Failure: drift alert fatigue from expected, benign changes Some drift is expected and harmless — e.g., an AWS-managed tag added automatically by a service. If the drift detection job alerts on every run regardless, the team starts ignoring the channel entirely. Debug: use ignore_changes lifecycle blocks for genuinely expected out-of-band attributes, and reserve alerting for drift Terraform would actually try to revert.
Failure: CI state lock contention during concurrent PR plans Two PR plan jobs run concurrently against the same state and one fails with a lock error, even though neither is mutating anything — plan still briefly acquires a lock by default. Debug: configure CI concurrency limits (concurrency: in the workflow) to serialize plan jobs against the same environment's state, rather than letting them race.

07Interview Talking Points

"How do you make sure what gets reviewed in a PR is exactly what gets applied?"
Explain the saved-plan-artifact pattern precisely: generate once in the PR job, upload as an artifact, consume that exact file in the apply job — never regenerate the plan between review and execution.
"How would you detect infrastructure drift before it causes an incident?"
Describe the scheduled drift-detection job using -detailed-exitcode, and be ready to discuss the alert-fatigue tradeoff — not all drift deserves a page, and tuning that signal is part of running the pipeline well, not just building it.
