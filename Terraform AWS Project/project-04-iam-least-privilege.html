01The Enterprise Problem This Solves

Every resource this handbook builds from here forward — the CI/CD pipeline in Project 8, the EKS cluster in Project 11, the cross-account deployment role in Project 14 — needs an IAM identity with exactly enough permission to do its job and nothing more. The default failure mode on real teams under deadline pressure is IAM policies that start narrow and get widened every time something throws an AccessDenied error, until roles that were meant to manage one S3 bucket can quietly touch the entire account. This project builds the discipline and the reusable Terraform patterns — scoped policy documents, permission boundaries, naming and tagging conventions — that keep IAM narrow by construction instead of by post-hoc audit.

02The Story: The CI Role That Could Delete Anything

Production Incident Replay A CI/CD pipeline needs to deploy Lambda functions. Under deadline pressure, an engineer attaches AWSLambda_FullAccess to the pipeline's IAM role because the narrower, hand-written policy kept throwing AccessDenied on some permission nobody had time to track down. It works. The deploy ships. Eight months later, a dependency-confusion attack manages to get a malicious package into a build step running under that same role. Because the role's permissions were never actually scoped to "deploy this specific set of Lambda functions," the attacker's code — running with the CI role's full credentials — has permission to modify IAM policies, delete unrelated Lambda functions across the account, and read Secrets Manager entries that have nothing to do with the pipeline that was compromised. The postmortem's core finding isn't "we got attacked" — it's that a scoped policy would have contained the blast radius to the handful of resources the pipeline actually needed, turning a account-wide incident into a non-event.

03Deep Technical Explanation

Policy documents as data, not stringly-typed JSON

Terraform can attach IAM policy JSON as a raw heredoc string, but that approach loses all of Terraform's validation, interpolation, and readability. The aws_iam_policy_document data source generates correct JSON from structured HCL blocks, catching syntax errors at plan time instead of at apply time when AWS rejects malformed policy JSON.

Trust policies vs. permission policies — two different documents doing two different jobs

Every IAM role has a trust policy (who/what is allowed to assume this role) completely separate from its permission policy (what the role can do once assumed). Conflating these is a common mid-level mistake — a role can have a perfectly narrow permission policy but a trust policy so broad that any principal in the account, or worse, any AWS account, can assume it and inherit those permissions.

Permission boundaries: a ceiling, not a grant

A permission boundary is a second policy attached to a role or user that doesn't grant any permissions by itself — it caps the maximum permissions that role's own attached policies can ever grant, regardless of how those policies are later edited. This matters enormously for delegated IAM creation: if a platform team lets application teams create their own IAM roles via Terraform, a permission boundary ensures no application team can accidentally (or maliciously) create a role broader than the platform team intended, even if the application team's own policy document tries to grant iam:* or *:*.

Condition keys: narrowing "what" down to "what, exactly, under which circumstances"

A resource-scoped policy (Resource = aws_s3_bucket.this.arn) is necessary but often not sufficient. Condition keys add situational constraints — requiring MFA for destructive actions, restricting access to specific source IP ranges, or requiring a specific tag on the resource being acted on — turning "this role can touch this bucket" into "this role can touch this bucket, only via TLS, only from our CI runner's IP range."

05Step-by-Step Implementation

5.1 — Reusable IAM role module with a permission boundary

modules/iam-role/variables.tf 
variable "role_name" {
  type = string
}

variable "trust_policy_json" {
  description = "JSON trust policy string, typically from aws_iam_policy_document.assume_role.json"
  type        = string
}

variable "permission_policy_json" {
  description = "JSON permission policy string this role's actions are scoped to"
  type        = string
}

variable "boundary_policy_arn" {
  description = "ARN of the org-wide permission boundary policy — the hard ceiling on this role"
  type        = string
}
modules/iam-role/main.tf 
resource "aws_iam_role" "this" {
  name                 = var.role_name
  assume_role_policy   = var.trust_policy_json # the "who can assume this" document
  permissions_boundary = var.boundary_policy_arn # the hard ceiling — cannot be widened by the policy below

  # Every role this module creates gets a max session duration cap —
  # stops a leaked temporary credential from being useful indefinitely.
  max_session_duration = 3600
}

resource "aws_iam_role_policy" "this" {
  name   = "${var.role_name}-policy"
  role   = aws_iam_role.this.id
  policy = var.permission_policy_json # the "what this role can actually do" document
}

5.2 — Calling the module for a scoped CI deploy role

envs/prod/iam-ci-deploy.tf 
# --- Trust policy: only GitHub Actions' OIDC provider, and only for
# this exact repo, can assume this role. No IAM users, no wildcard repos. ---
data "aws_iam_policy_document" "ci_trust" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]
    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:acme/checkout-service:ref:refs/heads/main"]
      # scoped to the main branch of one specific repo — no other
      # repo, and no other branch of this repo, can assume this role.
    }
  }
}

# --- Permission policy: only allowed to update code on Lambda
# functions whose name starts with "checkout-", nothing else. ---
data "aws_iam_policy_document" "ci_permissions" {
  statement {
    sid     = "DeployCheckoutLambdasOnly"
    actions = [
      "lambda:UpdateFunctionCode",
      "lambda:PublishVersion",
    ]
    resources = ["arn:aws:lambda:us-east-1:123456789012:function:checkout-*"]
  }
}

module "ci_deploy_role" {
  source = "../../modules/iam-role"

  role_name              = "ci-deploy-checkout-service"
  trust_policy_json      = data.aws_iam_policy_document.ci_trust.json
  permission_policy_json = data.aws_iam_policy_document.ci_permissions.json
  boundary_policy_arn    = aws_iam_policy.org_boundary.arn
}

5.3 — The org-wide permission boundary

envs/prod/iam-boundary.tf 
# --- Deny anything that could be used to escalate privilege, no
# matter what any individual role's own permission policy grants. ---
data "aws_iam_policy_document" "org_boundary" {
  statement {
    sid       = "AllowEverythingByDefault"
    effect    = "Allow"
    actions   = ["*"]
    resources = ["*"]
    # The boundary's job is to DENY specific dangerous actions below —
    # it isn't meant to grant anything; the role's own policy still
    # has to grant each action separately.
  }
  statement {
    sid    = "DenyPrivilegeEscalation"
    effect = "Deny"
    actions = [
      "iam:CreatePolicyVersion",
      "iam:DeleteRolePermissionsBoundary", # prevents a role from removing its own ceiling
      "iam:CreateUser",
      "organizations:*",
    ]
    resources = ["*"]
  }
}

resource "aws_iam_policy" "org_boundary" {
  name   = "org-permission-boundary"
  policy = data.aws_iam_policy_document.org_boundary.json
}

Plain-English walkthrough

Three documents are doing three separate jobs here. The trust policy answers "who can become this role" and is scoped down to a single repo and branch via an OIDC condition key — not just "any GitHub Actions run anywhere." The permission policy answers "what can this role do" and is scoped to exactly two Lambda actions against a resource ARN pattern matching only checkout-* functions. The permission boundary answers a third, independent question: "no matter what the permission policy says, what's the absolute ceiling for any role this boundary is attached to" — and specifically denies the exact actions (like deleting one's own boundary, or creating IAM users) that would let a compromised role escalate its own privileges. All three together are what would have contained the incident in the story: even a fully compromised CI run under this role could not have touched IAM, could not have escaped to other Lambda functions, and could not have removed its own guardrail.

06Failure Scenarios — What Breaks in Real Life

Failure: "AccessDenied" gets fixed by widening instead of diagnosing A deploy fails with an opaque AccessDenied, and under time pressure an engineer adds a broad managed policy instead of reading the specific denied action out of CloudTrail. Debug: query CloudTrail for the exact eventName and errorMessage of the denied call, add only that specific action to the scoped policy document, and never reach for a `*FullAccess` managed policy as a first response.
Failure: permission boundary silently blocks a legitimate new action A role's own policy is updated to grant a new action the team genuinely needs, but the org-wide boundary from Project 4 doesn't allow it, and the resulting AccessDenied looks identical to a missing permission policy grant. Debug: CloudTrail's denied-event detail distinguishes "denied by identity policy" from "denied by permissions boundary" — always check which one before touching either document.
Failure: trust policy condition typo grants broader access than intended A trust policy meant to scope access to repo:acme/checkout-service:ref:refs/heads/main gets written with a wildcard, like repo:acme/*, "to make future repos easier" — silently letting every repo in the org assume a role meant for one service. Debug: policy-as-code scanning in Project 22 (tfsec/Checkov) should be configured specifically to flag overly broad principal or condition wildcards in trust policies before they ever reach apply.

07Interview Talking Points

"How do you enforce least privilege across a team that self-serves their own IAM roles in Terraform?"
Describe the permission boundary pattern specifically: the platform team owns one boundary policy that caps what any self-service role can ever be granted, so application teams can create their own roles freely without the platform team reviewing every single policy document by hand.
"Walk me through the difference between a trust policy and a permission policy."
Give the one-line distinction clearly: trust policy = who can become this identity; permission policy = what that identity can do once it has. Then note they're independently exploitable — a narrow permission policy behind an overly broad trust policy is still a real vulnerability.
