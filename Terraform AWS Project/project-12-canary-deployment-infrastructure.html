PROJECT 12 OF 40 · ADVANCED

Canary Deployment Infrastructure — Deployments That Roll Themselves Back

Project 11 gave engineers a fast, manual traffic-shifting mechanism. Today we hand the wheel to CloudWatch: an AWS-native canary deployment that shifts traffic automatically, in small steps, and reverts itself the moment error rate or latency crosses a defined threshold — no human needs to be watching at 2am for it to work correctly.

01 The Banking Story

Blue-green from Project 11 has already prevented one bad release from becoming an outage — an engineer noticed elevated error rates during a canary window and manually shifted weight back to blue within two minutes. It worked because someone happened to be watching the dashboard closely during that exact window.

The team's next release is scheduled for 6am, ahead of the business day, specifically so a slow rollout has time to prove itself before peak traffic. No engineer wants to be manually watching a dashboard at 6am, and nobody should have to.

Our manager's brief: "Automate this properly. Define the exact error-rate and latency thresholds that should trigger a rollback, and hand the decision to CloudWatch and CodeDeploy — not a person's judgment call at 6am. The system should be able to detect and revert a bad release entirely on its own."

02 Business Requirement, Risk & Impact

Business Requirement

Deployments must be able to detect their own failure against defined metrics and roll back automatically, without requiring a human to be actively monitoring at the time.

Customer Requirement

Releases scheduled outside business hours must be just as safe as releases made during the day, when more engineers are actively watching.

Current Infrastructure

Project 11's blue-green target groups and weighted listener rule, with all traffic-shifting decisions currently made manually by an engineer.

Existing Manual Process

An engineer watches dashboards during the canary window and manually reapplies Terraform with a lower weight if something looks wrong — entirely dependent on someone paying close attention at the right moment.

Problems With Current Process

  • Detection and response time depends entirely on how closely, and how quickly, a human is watching
  • Off-hours or low-staffed release windows have effectively weaker safety than business-hours releases
  • No consistent, objective definition of "this deployment has failed" — it's currently a judgment call

Business Challenges

The bank wants to increase release frequency for faster fixes and features — that's only safe to do if the safety net doesn't scale linearly with the number of engineers watching each release.

Risk Analysis

Medium: the risk isn't that deployments fail (they always might) — it's that failure detection and response time is currently inconsistent and staffing-dependent.

Business Impact

Automated rollback directly enables safer off-hours deployments, which reduces the business pressure to deploy only during risky, high-traffic daytime windows.

03 Why AWS CodeDeploy + CloudWatch Alarms, and What We Rejected

AWS CodeDeploy has purpose-built support for ECS and Lambda canary/linear deployments, with CloudWatch alarm integration for automatic rollback as a first-class, declarative feature — not something we'd need to hand-build with custom Lambda functions polling metrics ourselves.

04 Terraform Concepts You Must Understand Before We Build

The terraform_data Resource (Modern Alternative to null_resource)

What it is: a built-in resource (no provider needed) that replaces the older null_resource + random/hash-based trigger pattern — it holds arbitrary values in state and supports a dedicated triggers_replace argument that forces recreation cleanly when specific inputs change.

Why it exists: null_resource required pairing with the random provider or manual hashing tricks to force replacement on a specific change; terraform_data makes "recreate this placeholder when X changes" a direct, built-in argument instead of a workaround.

Production example: we use terraform_data to track the currently deployed application revision identifier — when it changes, downstream logic can detect that a new deployment needs to be registered with CodeDeploy, without needing any real cloud resource to represent that tracking.

Best practice: prefer terraform_data over null_resource in new code on modern Terraform versions — it needs no provider block and expresses trigger-based replacement more directly.

Reinforcing Dynamic Blocks — Alarm Thresholds from a Map

What it is: the CodeDeploy deployment group's alarm_configuration and our CloudWatch composite alarm both take a variable-length list of alarm names — built with a dynamic block from a structured map variable, so adding a fourth rollback-triggering metric later is a variable change, not a new resource block.

Reinforcing Conditional Expressions — Environment-Specific Canary Intervals

What it is: Production uses a slower, more cautious canary interval than UAT, computed with the same condition ? a : b pattern used throughout this series: canary_interval_minutes = var.environment == "production" ? 15 : 5.

05 AWS Concepts: CodeDeploy Canary & Alarm-Driven Rollback

What is a CodeDeploy Deployment Group

Defines HOW a deployment rolls out — which target groups are involved, the traffic-shifting strategy (canary, linear, or all-at-once), and what conditions trigger an automatic rollback.

Canary vs. Linear Deployment Config

Canary shifts a defined percentage immediately, waits an interval, then shifts the rest; Linear shifts in even increments repeatedly until 100% — canary suits ABC Bank's need to catch issues early with a small blast radius before commit to the rest.

CloudWatch Alarm-Based Auto Rollback

A deployment group's alarm_configuration references specific CloudWatch alarms — if any of them enters ALARM state during the deployment, CodeDeploy automatically reverts traffic to the previous version without waiting for the canary interval to complete naturally.

Composite Alarms

A single alarm that combines multiple underlying alarms with AND/OR logic — used here so "error rate high OR latency high" triggers rollback from one alarm reference, instead of managing multiple separate alarm conditions in the deployment group config.

Security

The CodeDeploy service role needs narrowly scoped permissions to modify the specific ALB listener rule and target groups involved — not broad ELB permissions across the whole account.

Limitations

Auto-rollback triggers reactively, after metrics cross a threshold — it doesn't prevent the bad version from receiving any traffic at all during the canary window; the canary percentage itself is what limits the blast radius before detection.

07 Complete Solution Design

Two CloudWatch alarms (5xx error rate, p99 latency) feed into one composite alarm using OR logic. A CodeDeploy application and deployment group reference Project 11's blue and green target groups, configured with a CodeDeployDefault.ECSCanary10Percent5Minutes-style canary strategy and an alarm_configuration block pointing at the composite alarm — if it fires during the canary window, CodeDeploy automatically reverts.

A terraform_data resource tracks the currently deployed application revision identifier, using triggers_replace to detect when a new revision is ready — giving downstream CI/CD steps a clean, Terraform-native signal without a real cloud resource needed just to track this piece of state.

09 Implementation — Full Production Code

environments/prod/canary-alarms.tf

environments/prod/canary-alarms.tf
resource "aws_cloudwatch_metric_alarm" "error_rate" {
  alarm_name          = "payments-api-5xx-error-rate"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods   = 2                                              # Requires 2 consecutive breaching periods — avoids a single noisy spike triggering rollback
  metric_name          = "HTTPCode_Target_5XX_Count"
  namespace            = "AWS/ApplicationELB"
  period               = 60
  statistic            = "Sum"
  threshold            = 10                                              # More than 10 five-hundred errors per minute is considered a real problem, not noise
  alarm_description    = "Triggers CodeDeploy auto-rollback on elevated 5xx errors during canary"
}

resource "aws_cloudwatch_metric_alarm" "latency" {
  alarm_name          = "payments-api-p99-latency"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods   = 2
  metric_name          = "TargetResponseTime"
  namespace            = "AWS/ApplicationELB"
  period               = 60
  extended_statistic    = "p99"                                          # p99, not average — a slow tail is exactly what a canary window should catch
  threshold             = 0.8                                             # 800ms — matches the bank's documented latency SLO for this service
  alarm_description     = "Triggers CodeDeploy auto-rollback on elevated p99 latency during canary"
}

resource "aws_cloudwatch_composite_alarm" "canary_rollback_trigger" {
  alarm_name = "payments-api-canary-rollback-trigger"
  alarm_rule = "ALARM(${aws_cloudwatch_metric_alarm.error_rate.alarm_name}) OR ALARM(${aws_cloudwatch_metric_alarm.latency.alarm_name})"  # EITHER condition alone is sufficient to trigger rollback
}

environments/prod/canary-codedeploy.tf

environments/prod/canary-codedeploy.tf
resource "aws_codedeploy_app" "payments_api" {
  name             = "payments-api"
  compute_platform = "ECS"                                               # Assumes payments-api has migrated to ECS by this point in the platform's evolution
}

resource "aws_codedeploy_deployment_config" "canary" {
  deployment_config_name = "payments-api-canary-10-percent"
  compute_platform        = "ECS"

  traffic_routing_config {
    type = "TimeBasedCanary"                                             # Shifts an initial percentage, waits, then shifts the rest — as opposed to "TimeBasedLinear"

    time_based_canary {
      interval   = var.environment == "production" ? 15 : 5              # Production waits longer per step — reinforces the conditional-expression pattern from earlier projects
      percentage = 10                                                     # Only 10% of traffic during the canary window, limiting blast radius before the alarm has a chance to fire
    }
  }
}

resource "aws_codedeploy_deployment_group" "payments_api" {
  app_name               = aws_codedeploy_app.payments_api.name
  deployment_group_name  = "payments-api-${var.environment}"
  service_role_arn        = aws_iam_role.codedeploy.arn
  deployment_config_name  = aws_codedeploy_deployment_config.canary.id

  auto_rollback_configuration {
    enabled           = true
    events             = ["DEPLOYMENT_FAILURE", "DEPLOYMENT_STOP_ON_ALARM"]  # Rolls back on either an outright failure OR an alarm-triggered stop
  }

  alarm_configuration {
    alarms  = [aws_cloudwatch_composite_alarm.canary_rollback_trigger.alarm_name]  # The ONE composite alarm covers both underlying conditions
    enabled = true
  }

  blue_green_deployment_config {                                          # Reuses the blue/green target group PAIR from Project 11 as CodeDeploy's own managed rotation
    deployment_ready_option {
      action_on_timeout = "CONTINUE_DEPLOYMENT"
    }
    terminate_blue_instances_on_deployment_success {
      action                            = "TERMINATE"
      termination_wait_time_in_minutes  = 5                                 # Keeps the old version briefly available even after a successful full shift, as a final safety window
    }
  }

  load_balancer_info {
    target_group_pair_info {
      target_group {
        name = module.app_blue.target_group_name                          # References Project 11's blue/green modules directly — this project builds ON that infrastructure, not instead of it
      }
      target_group {
        name = module.app_green.target_group_name
      }
      prod_traffic_route {
        listener_arns = [var.alb_listener_arn]
      }
    }
  }
}

environments/prod/canary-tracking.tf

environments/prod/canary-tracking.tf
resource "terraform_data" "deployed_revision" {                        # Built-in resource — no provider block needed, unlike null_resource historically requiring one implicitly
  input = var.app_revision_id                                            # Stores the current revision identifier as this resource's tracked value

  triggers_replace = [
    var.app_revision_id                                                   # Forces replacement of this resource specifically when the revision ID changes — nothing else triggers it
  ]
}

output "revision_change_detected" {
  value       = terraform_data.deployed_revision.id                      # Changes every time the resource is replaced — a clean signal a downstream pipeline step can compare against its last-seen value
  description = "Changes whenever a new application revision has been registered for deployment"
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
alarm_rule = "ALARM(...) OR ALARM(...)"Composite alarm's own small expression language combining underlying alarms with boolean logicUsing AND when OR is intended (or vice versa) — with AND here, a rollback would require BOTH error rate and latency to breach simultaneously, missing either issue occurring alone
events = ["DEPLOYMENT_FAILURE", "DEPLOYMENT_STOP_ON_ALARM"]Defines which categories of deployment problem trigger the automatic rollbackOnly including DEPLOYMENT_FAILURE and omitting DEPLOYMENT_STOP_ON_ALARM — the alarm-triggered stop wouldn't actually cause an automatic rollback without this specific event also being listed
terraform_data with triggers_replaceForces the resource to be destroyed and recreated (getting a new internal id) whenever the referenced value changesConfusing input with triggers_replace — input just stores a value; only triggers_replace controls when the resource itself is replaced
extended_statistic = "p99"Uses the 99th percentile rather than the average for the latency alarmUsing statistic = "Average" for a latency SLO — averages hide exactly the kind of tail latency spike a canary window is meant to catch

11 Execution Flow, Explained Internally

terraform apply — infrastructure setup

Creates the alarms, composite alarm, CodeDeploy application, deployment config, and deployment group — but triggers no actual deployment; CodeDeploy deployments themselves are created by the CI/CD pipeline via the AWS API/CLI, not by terraform apply.

A real deployment's automatic flow (outside Terraform)

CI/CD calls CodeDeploy's create-deployment API; CodeDeploy shifts 10% of traffic per the deployment config, waits the configured interval, continuously evaluates the composite alarm, and either proceeds to 100% or automatically reverts — entirely orchestrated by CodeDeploy itself.

terraform apply — revision change detection

When var.app_revision_id changes, the plan shows terraform_data.deployed_revision being replaced — a visible, reviewable signal in the plan output that a new revision is about to be tracked.

Terraform manages the canary DEFINITION (thresholds, percentages, alarm wiring) — it does not manage individual deployment EVENTS. Don't try to trigger a deployment via a provisioner or external data source; that's exactly the kind of action CI/CD, not infrastructure code, should own.

12 CI/CD Integration

.github/workflows/canary-deploy.yml
name: canary-deploy
on:
  push:
    branches: [main]
    paths: ["services/payments-api/**"]

jobs:
  infra:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve -var="app_revision_id=${{ github.sha }}"  # Updates tracking + ensures alarm/deployment-group config is current BEFORE triggering a real deployment

  deploy:
    needs: infra
    runs-on: ubuntu-latest
    steps:
      - name: Trigger CodeDeploy canary deployment
        run: |                                                          # The actual deployment trigger — deliberately NOT done via Terraform, as explained above
          aws deploy create-deployment \
            --application-name payments-api \
            --deployment-group-name payments-api-production \
            --revision revisionType=AppSpecContent,appSpecContent="{content=$(cat appspec.yaml)}"
Notice the clean split: the infra job (Terraform) owns the deployment STRATEGY definition; the deploy job (AWS CLI) owns triggering an actual deployment EVENT. Keeping these separate is a deliberate architectural choice, not an oversight.

14 Interview Preparation

Q: How does automatic canary rollback differ from what you built in the blue-green project?
Blue-green (Project 11) gave a fast, manually-triggered rollback mechanism; this project removes the human from the loop entirely — CloudWatch alarms and CodeDeploy's native rollback configuration detect and revert a bad deployment automatically, without anyone needing to be watching.
Q: Why use a composite alarm instead of listing multiple alarms directly in the deployment group?
A composite alarm lets you express boolean logic (like OR) between conditions cleanly in one place; CodeDeploy's alarm_configuration itself just references a list of alarms, evaluated as OR by default, but a composite alarm becomes essential once the logic needs to be more nuanced (like AND, or weighted combinations).
Q: Why doesn't Terraform trigger the actual CodeDeploy deployment?
Terraform manages the deployment STRATEGY's definition (thresholds, percentages, rollback rules) as durable infrastructure; triggering an individual deployment is an event-driven CI/CD action tied to a specific code revision, not a piece of infrastructure state Terraform should own or reapply repeatedly.
Q: What's the advantage of terraform_data over null_resource for tracking a changing value?
terraform_data is a built-in resource needing no provider, with a direct triggers_replace argument — cleaner than null_resource's older pattern of needing an external trigger mechanism like a hash or the random provider to force replacement.
Manager round: How would you choose the canary percentage and interval for a new service?
Balance blast radius against detection time — a smaller percentage and longer interval catches issues more cautiously but delays full rollout; base the choice on the service's criticality and how quickly its metrics reliably reflect real problems, tuning over successive real deployments.
