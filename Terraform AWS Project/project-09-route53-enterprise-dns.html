PROJECT 09 OF 40 · INTERMEDIATE

Route53 Enterprise DNS — Private Zones, Split-Horizon & Hybrid Resolution

Every account can now reach every other account over the network — but they're still addressing each other by raw IP addresses, hardcoded in application config. Today we give every environment a proper internal domain name, sharable across accounts, plus a resolver bridge so on-prem systems can resolve AWS names and vice versa.

01 The Banking Story

The payments-api team in Dev has a config file with a hardcoded private IP for the Shared Services Active Directory server. It worked, right up until last week when that instance was replaced during a routine patch cycle (Project 07) and got a new private IP — nobody remembered to update the six different config files across three environments that referenced the old address by number.

Meanwhile, our Dev, UAT, and Production environments are meant to be near-identical in shape (same VPC framework, same Transit Gateway pattern) but differ only in scale and a handful of settings — yet the team has been maintaining three almost-duplicate Terraform root modules for their DNS configuration, one per environment, that drift further apart every time someone updates one and forgets the other two.

Our manager's brief: "Give every environment a proper private DNS zone — dev.abcbank.internal, uat.abcbank.internal, prod.abcbank.internal — shared with every account that needs to resolve it. And find a way to manage all three from ONE set of Terraform code, not three copies that will inevitably drift."

02 Business Requirement, Risk & Impact

Business Requirement

Every internal service must be addressable by a stable DNS name, not a hardcoded IP, resolvable consistently across every AWS account and the on-prem data center.

Customer Requirement

Application teams need one place to update a DNS record when an underlying resource changes — not a search-and-replace across every environment's config files.

Current Infrastructure

No private DNS zones exist; every cross-service reference in application configuration is a hardcoded private IP address.

Existing Manual Process

When an IP changes, an engineer greps the codebase for the old address and manually updates every reference they can find — with no guarantee they found them all.

Problems With Current Process

  • IP changes silently break dependent services until someone notices and manually traces the failure back to a stale IP
  • Three near-duplicate Terraform configurations for Dev/UAT/Prod DNS, drifting apart over time
  • On-prem systems have no way to resolve AWS-hosted service names, and vice versa

Business Challenges

Predictable, documented service addressing is a basic expectation of any change-management process a banking audit will review — hardcoded IPs fail that expectation immediately.

Risk Analysis

Medium: the immediate risk is availability (broken references after routine changes), not security — but repeated incidents like the one in our story erode confidence in the platform's reliability during regulator-observed operations.

Business Impact

Each hardcoded-IP incident costs engineering time to trace and fix, and undermines the "infrastructure as code, not infrastructure as tribal knowledge" goal this entire 40-project series exists to build.

03 Why Route53 Private Zones + Terraform Workspaces, and What We Rejected

Why Route53 Private Hosted Zones

A Private Hosted Zone resolves DNS names only within associated VPCs (and, via Resolver, the on-prem network) — never publicly — giving ABC Bank internal service discovery without exposing internal naming or structure to the public internet at all.

Why Terraform Workspaces for this specific project

Dev, UAT, and Production's DNS zones are structurally identical — same record types, same resolver rule shape — differing only in the zone name and a few values. Workspaces let one set of .tf files be applied three times, once per workspace, each with its own isolated state file, instead of maintaining three physically separate copies of the same code.

04 Terraform Concepts You Must Understand Before We Build

Workspace Strategy

What it is: Terraform workspaces let one directory of .tf files maintain multiple, completely isolated state files — switching workspaces switches which state file subsequent commands operate against, without touching the code itself.

Why it exists: for near-identical environments differing mainly in a few input values, workspaces avoid the duplication of maintaining physically separate root modules, while still keeping each environment's state completely separate (a mistake in Dev's plan can never accidentally touch Prod's state).

Internal working: with the S3 backend from Project 01, Terraform stores each workspace's state at a path like env:/<workspace-name>/<original-key> inside the same bucket — one bucket, many isolated state objects.

When NOT to use workspaces: when environments genuinely differ in structure (different module versions, meaningfully different resource sets) — as we saw with Dev/UAT/Prod's VPC and Transit Gateway configuration in Projects 02-03, where separate directories per environment remain the better fit. Workspaces suit narrow, structurally-identical cases like this DNS project, not a whole account's infrastructure.

Common mistake: using terraform.workspace as the ONLY thing differentiating environments that actually need different variable values for many settings — this leads to sprawling conditional logic in every resource block; a dedicated .tfvars file per workspace (shown below) keeps this manageable.

The terraform.workspace Built-in Reference

What it is: a special expression, always available with no declaration needed, that returns the name of the currently selected workspace as a string — used here to compute the zone name and select the matching .tfvars file.

Production example: zone_name = "${terraform.workspace}.abcbank.internal" — running terraform workspace select prod then apply creates prod.abcbank.internal; switching to the dev workspace and applying again creates dev.abcbank.internal, from the exact same code.

Reinforcing Cross-Account Resource Sharing (Zone Association)

What it is: aws_route53_zone_association, called with an aliased provider (the same pattern from Project 03), associates a Private Hosted Zone created in one account with VPCs living in other accounts — DNS resolution doesn't stop at account boundaries any more than the Transit Gateway traffic does.

05 AWS Concepts: Private Zones, Split-Horizon & Resolver

What is a Private Hosted Zone

A Route53 zone that only resolves for VPCs explicitly associated with it — the exact same domain name could exist as a completely different public zone with different records, which is what "split-horizon DNS" refers to.

What is Route53 Resolver

The component that lets DNS queries cross the AWS/on-prem boundary — an Inbound Resolver Endpoint lets on-prem systems query AWS-hosted private zones; an Outbound Resolver Endpoint plus Resolver Rules let AWS resources query on-prem DNS servers for on-prem-only names.

Why it exists

Without Resolver, AWS's private DNS and the on-prem data center's DNS are two disconnected islands — Resolver bridges them so a single stable naming scheme can span the whole hybrid estate.

High Availability

Deploy Resolver endpoints across at least two AZs — a single-AZ resolver endpoint becomes a hybrid DNS single point of failure.

Security

Resolver endpoints have their own security groups — scope inbound/outbound DNS (port 53, TCP and UDP) tightly to only the on-prem DNS servers' and AWS resolver's known IP ranges.

Pricing

Charged per resolver endpoint per hour, plus per-query pricing for resolver rule evaluations — modest compared to the cost of another hardcoded-IP outage.

Limitations

A VPC can only be associated with Resolver rules from accounts sharing them via RAM (the same sharing mechanism from Project 03) or from within the same account — cross-account resolver rule sharing needs that extra step.

07 Complete Solution Design

One Terraform root module, driven by terraform.workspace, creates a Private Hosted Zone named ${terraform.workspace}.abcbank.internal, associates it with every account's VPC that needs it (via aliased providers, one per consuming account), and defines the environment's core service records. A separate, single-instance root module (not workspace-driven, since there's only ever one) creates the Inbound and Outbound Resolver Endpoints plus Resolver Rules bridging to the on-prem DNS servers.

Per-workspace differences (like how many VPCs a given environment's zone needs associating with) are driven by a <workspace>.tfvars file selected explicitly at plan/apply time — not by branching logic inside the .tf files themselves.

09 Implementation — Full Production Code

environments/dns/main.tf

environments/dns/main.tf
resource "aws_route53_zone" "environment" {
  name = "${terraform.workspace}.abcbank.internal"                    # Resolves to dev.abcbank.internal, uat.abcbank.internal, or prod.abcbank.internal depending on the active workspace

  vpc {
    vpc_id = var.primary_vpc_id                                        # Native association — the account that owns this zone's own VPC
  }

  tags = { Environment = terraform.workspace }
}

resource "aws_route53_zone_association" "shared_services" {           # Cross-account association, same aliased-provider pattern as Project 03's RAM sharing
  provider = aws.shared_services
  zone_id  = aws_route53_zone.environment.zone_id
  vpc_id   = var.shared_services_vpc_id
}

resource "aws_route53_record" "active_directory" {
  zone_id = aws_route53_zone.environment.zone_id
  name    = "ad.${terraform.workspace}.abcbank.internal"
  type    = "A"
  ttl     = 300                                                         # A short TTL — this exact record is what fixes the hardcoded-IP problem from our story
  records = [var.active_directory_ip]
}

resource "aws_route53_record" "payments_api" {
  zone_id = aws_route53_zone.environment.zone_id
  name    = "payments-api.${terraform.workspace}.abcbank.internal"
  type    = "CNAME"
  ttl     = 300
  records = [var.payments_api_alb_dns_name]                             # Points at the ALB's own DNS name — the ALB's underlying IPs can change freely with zero impact here
}

environments/dns-resolver/main.tf

environments/dns-resolver/main.tf
resource "aws_security_group" "resolver" {
  name   = "route53-resolver-sg"
  vpc_id = var.shared_services_vpc_id

  ingress {
    from_port   = 53                                                    # DNS uses both TCP and UDP on port 53 — both must be allowed
    to_port     = 53
    protocol    = "udp"
    cidr_blocks = [var.onprem_cidr]
  }
  ingress {
    from_port   = 53
    to_port     = 53
    protocol    = "tcp"
    cidr_blocks = [var.onprem_cidr]
  }
}

resource "aws_route53_resolver_endpoint" "inbound" {                    # Lets ON-PREM systems query AWS private zones
  name               = "abc-bank-inbound-resolver"
  direction          = "INBOUND"
  security_group_ids = [aws_security_group.resolver.id]

  dynamic "ip_address" {                                                 # Reinforces Project 02's dynamic block concept — one IP per AZ, from a list# Lets AWS RESOURCES query on-prem DNS servers
  name               = "abc-bank-outbound-resolver"
  direction          = "OUTBOUND"
  security_group_ids = [aws_security_group.resolver.id]

  dynamic "ip_address" {
    for_each = var.resolver_subnet_ids
    content {
      subnet_id = ip_address.value
    }
  }
}

resource "aws_route53_resolver_rule" "onprem_forward" {
  domain_name          = "abcbank.corp"                                  # The on-prem-only domain — anything under this suffix forwards to on-prem DNS
  name                 = "forward-to-onprem"
  rule_type            = "FORWARD"
  resolver_endpoint_id = aws_route53_resolver_endpoint.outbound.id

  target_ip {
    ip = var.onprem_dns_server_ip
    port = 53
  }
}

resource "aws_route53_resolver_rule_association" "prod_vpc" {
  resolver_rule_id = aws_route53_resolver_rule.onprem_forward.id
  vpc_id           = var.prod_vpc_id                                     # Associates the forwarding rule with Production specifically — repeat per VPC that needs on-prem resolution
}

10 Workspace Strategy — Step by Step

terminal
cd environments/dns
terraform init

terraform workspace new dev                     # Creates and switches to a new, isolated workspace
terraform workspace new uat
terraform workspace new prod

terraform workspace select dev                   # Switches the CLI's active workspace — subsequent commands target dev's own state
terraform plan  -var-file="dev.tfvars"
terraform apply -var-file="dev.tfvars"

terraform workspace select prod
terraform plan  -var-file="prod.tfvars"          # Same code, different workspace AND different tfvars — creates prod.abcbank.internal in a completely separate state file
terraform apply -var-file="prod.tfvars"

terraform workspace list                          # Shows all three, with an asterisk marking the currently active one
Always pair a workspace switch with the matching -var-file in the same command or a wrapper script — running apply against the prod workspace while accidentally still pointing at dev.tfvars is a realistic and dangerous mistake; many teams wrap this in a small shell script or CI/CD job matrix to make it foolproof.

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
terraform.workspaceReturns the current workspace's name as a string, usable anywhere an expression is validAssuming it needs to be declared as a variable — it's a built-in reference, always available with no declaration
vpc { vpc_id = ... } block on aws_route53_zoneThe FIRST VPC association, created inline with the zone itselfTrying to associate every VPC this way — only one can be set inline; every additional VPC needs a separate aws_route53_zone_association resource, as shown
Resolver Rule's domain_name = "abcbank.corp"Only queries for names ending in this suffix are forwarded on-prem — everything else resolves normally through AWSSetting this too broadly (e.g. as a wildcard covering AWS's own private zone) — would send internal AWS DNS queries needlessly out to on-prem, adding latency and a new failure dependency
TTL = 300 on recordsFive-minute cache lifetime — balances DNS query load against how quickly a change propagatesUsing a very high TTL (like 86400) on records tied to frequently-changing resources — exactly the kind of hardcoded-IP-like staleness this project exists to eliminate

11 Execution Flow, Explained Internally

terraform workspace select

Changes only which state file subsequent commands read/write — the .tf code on disk is completely unchanged; this is purely a state-targeting operation.

terraform plan with a workspace active

Every terraform.workspace reference in the code resolves to the active workspace's name for this specific plan — switch workspaces, and the exact same command computes a different name for the zone.

terraform destroy in the wrong workspace

Destroys only that workspace's resources — Dev's zone can be destroyed and recreated freely without any risk to Prod's zone, since they live in entirely separate state files under the same backend.

Always run terraform workspace show before any apply or destroy in this directory — it's easy to forget which workspace is currently active, and the code gives no visual warning in your terminal prompt unless you configure one yourself.

12 CI/CD Integration

.github/workflows/terraform-dns.yml
name: terraform-dns
on:
  push:
    branches: [main]
    paths: ["environments/dns/**"]

jobs:
  dns:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        environment: [dev, uat, prod]                                   # One job PER workspace, run in parallel — the matrix mirrors the workspace list exactly
    defaults: { run: { working-directory: environments/dns } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform workspace select ${{ matrix.environment }} || terraform workspace new ${{ matrix.environment }}
      - run: terraform apply -auto-approve -var-file="${{ matrix.environment }}.tfvars"
A CI/CD matrix job per workspace, each explicitly pairing the workspace name with its matching .tfvars file, removes the human-error risk of an engineer forgetting to switch both together on their own machine.

14 Interview Preparation

Q: When should you use Terraform workspaces versus separate directories per environment?
Workspaces suit environments that are structurally identical, differing only in a handful of input values — separate directories suit environments that genuinely differ in structure, module composition, or resource sets, since workspaces alone can't express that kind of structural divergence cleanly.
Q: Does switching Terraform workspaces change your code?
No — it only changes which state file subsequent commands read and write; the .tf configuration on disk is identical regardless of which workspace is active.
Q: What's the difference between a Private Hosted Zone and split-horizon DNS?
A Private Hosted Zone is the AWS mechanism that only resolves within associated VPCs; split-horizon DNS is the broader concept it enables — the same domain name resolving differently depending on whether the query comes from inside or outside the private network.
Q: Why do you need both Inbound and Outbound Resolver endpoints for hybrid DNS?
Inbound lets on-prem systems query AWS-hosted private zones; Outbound (paired with Resolver Rules) lets AWS resources query on-prem DNS servers — the two directions are independent and both are usually needed for full hybrid resolution.
Manager round: An engineer accidentally applied to the wrong workspace. How do you prevent that going forward?
Move environment applies into a CI/CD matrix job that explicitly pairs each workspace with its own tfvars file (removing manual workspace-switching from the human workflow entirely), and consider a wrapper script or shell prompt integration for anyone still applying locally.
