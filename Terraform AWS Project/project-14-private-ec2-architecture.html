PROJECT 14 OF 40 · ADVANCED

Private EC2 Architecture — a Hardened Baseline for Every Fleet

Session Manager retired the bastion in Project 07 — but that only removed one open port. Today we go further: no public IP anywhere, ever; the instance metadata service hardened against the exact request-smuggling technique behind several real-world cloud breaches; and encryption at rest enforced at the account level, not left to individual engineers to remember.

01 The Banking Story

A routine security review of a competitor bank's public breach report landed on the team's desk this week — the root cause was a server-side request forgery (SSRF) vulnerability in a web application that let an attacker query the EC2 Instance Metadata Service (IMDS) and steal the instance's IAM role credentials directly, entirely bypassing the application's own authentication. ABC Bank's instances are still running IMDSv1, the older protocol that vulnerability specifically exploits.

Separately, an audit of the account found three EC2 instances — created early in the program, before Project 02's VPC framework existed — still have public IP addresses assigned, a leftover from before the team standardized on private subnets. And EBS volume encryption has been "on by default" only because every engineer has remembered to tick the box; nothing structurally prevents someone from launching an unencrypted volume by mistake.

Our manager's brief: "Force IMDSv2 everywhere — no instance should ever be able to fall back to v1. Make encryption at rest the account-wide default, not a per-instance choice. And build the standard hardened instance module every future compute project in this series will use, so this is solved once, not 40 times."

02 Business Requirement, Risk & Impact

Business Requirement

Every EC2 instance in every account must enforce IMDSv2, have encrypted EBS volumes by default, and have no public IP address, without depending on individual engineer discipline.

Customer Requirement

The Security team wants one reusable, hardened instance module that every application team builds on — not 40 separately hardened (or not) instance configurations across the platform.

Current Infrastructure

Instances launched with IMDSv1 still permitted, EBS encryption dependent on per-resource configuration, and three legacy instances with public IPs from before Project 02.

Existing Manual Process

None formalized — hardening settings are whatever each engineer happened to configure (or not) on their own launch template or instance resource.

Problems With Current Process

  • IMDSv1 remains reachable, leaving an SSRF-to-credential-theft path open exactly like the breach report reviewed this week
  • EBS encryption isn't structurally guaranteed — a forgotten setting means unencrypted data at rest
  • Three legacy public-IP instances are a known, unaddressed exception to the private-only architecture the rest of this series has built

Business Challenges

PCI-DSS and general banking security standards both require encryption of stored cardholder-adjacent data and hardened access controls to compute infrastructure — both gaps here are direct compliance exposure, not just best-practice nice-to-haves.

Risk Analysis

High: the IMDSv1 exposure is not theoretical — it is the exact, named root cause of a real, publicly documented breach at another financial institution, making this a credible, not hypothetical, threat.

Business Impact

An SSRF-to-IAM-credential-theft path in Production could expose the very AWS resources (databases, secrets) the rest of this 40-project series has worked to protect.

03 Why a Structural, Account-Wide Baseline

Why enforce this structurally, not just by convention

A written standard ("always use IMDSv2") depends on every engineer remembering and correctly applying it, every time — exactly the kind of gap Project 05's permission boundaries were built to close for IAM. The same principle applies here: settings that can be structurally enforced (account-wide EBS encryption default, a shared hardened module) should be, rather than left to individual configuration discipline.

Alternatives considered, and why they were rejected

04 Terraform Concepts You Must Understand Before We Build

Reinforcing Data Sources — Filtered AMI Lookup with Owners

What it is: beyond Project 07's simple SSM parameter AMI lookup, data "aws_ami" with explicit owners and filter blocks lets us pin to a specific, security-team-approved custom hardened AMI (not just "whatever Amazon Linux published most recently") — critical when the AMI itself has pre-baked hardening beyond what user-data alone can configure.

Why the owners argument matters: without restricting to a specific, known account ID (ABC Bank's own AMI-building account, or Amazon's), a search by name alone could theoretically match an AMI published by an untrusted third party with a similar name — a real, documented AMI-spoofing risk.

Reinforcing Complex Variables — Security Group Rule Chaining via for_each

What it is: rather than hardcoding CIDR blocks in every security group rule, this module's ingress rules reference OTHER security group IDs by ID (e.g. "allow from the ALB's security group specifically") — built with for_each over a map of allowed source security groups, so adding a new permitted caller is a one-line variable change.

Why it's more secure than CIDR-based rules: a security-group-referenced rule automatically stays correct even if the source's IP address changes — CIDR-based rules require manual updates and are far easier to accidentally over-scope.

Reinforcing Module Design — One Hardened Module for Every Future Fleet

What it is: this project's entire deliverable is a single hardened-instance module encapsulating every setting from this page — IMDSv2, encryption, no public IP — so every later project in this series that needs compute simply calls this module instead of re-declaring an aws_instance resource with these settings copy-pasted in each time.

05 AWS Concepts: IMDSv2, EBS Encryption & No-Public-IP

What is IMDSv1 vs. IMDSv2

IMDSv1 answers metadata requests with a simple unauthenticated GET request — trivially exploitable via SSRF. IMDSv2 requires a session token obtained via a PUT request first, a request method most SSRF vulnerabilities (which typically only control the URL of a GET) cannot forge.

Why http_tokens = "required" matters

Setting this on the instance (or launch template) makes IMDSv2 mandatory — IMDSv1 requests are rejected outright, closing the exact exploit path from the breach report the team reviewed.

Account-Wide EBS Encryption Default

aws_ebs_encryption_by_default is a single, account-level (or per-region) setting that makes every newly created EBS volume encrypted automatically, with no per-resource argument required — structurally closing the "forgot to tick the box" gap.

Why No Public IP, Beyond "Defense in Depth"

Even with Session Manager (Project 07) removing the need for direct SSH, a public IP still exposes whatever else might be listening on the instance to the entire internet — removing it entirely, not just closing specific ports, is a meaningfully stronger posture.

Security Group Chaining

Referencing a source security group ID instead of a CIDR block means the rule automatically stays correct as the referenced resource's underlying instances change — a structural improvement over IP-based rules that also happens to be easier to audit at a glance.

Limitations

IMDSv2 enforcement can break older application code or third-party agents that hardcode IMDSv1-style unauthenticated requests — test thoroughly before enforcing account-wide, and budget time to update any non-compliant tooling first.

07 Complete Solution Design

An account-level aws_ebs_encryption_by_default resource is applied once per account/region, making encryption the structural default rather than a per-instance choice. A new modules/hardened-instance module wraps aws_instance with metadata_options { http_tokens = "required", http_endpoint = "enabled" }, associate_public_ip_address = false hardcoded (not even exposed as a variable — deliberately impossible to override), and an encrypted root block device.

The module's security group is built with for_each over a map of allowed source security group IDs, so every consumer declares exactly which other security groups may reach it, by reference — never by CIDR. The three legacy public-IP instances are migrated onto this module as a first, concrete adoption.

environments/prod/ebs-encryption-default.tf

environments/prod/ebs-encryption-default.tf
resource "aws_ebs_encryption_by_default" "account" {                  # Account/region-level setting — applies to EVERY future EBS volume automatically
  enabled = true
}

resource "aws_ebs_default_kms_key" "account" {                          # Pairs with the setting above — controls WHICH key encrypts by default
  key_arn = var.ebs_default_kms_key_arn                                  # A dedicated key, separate from the logging (Project 04) and secrets (Project 06) keys
}

  type = string

  type = string

variable "allowed_source_security_groups" {                             # Complex variable — maps a friendly name to a source security group ID allowed to reach this instance
  type        = map(object({

    port               = number
  }))
  default     = {}

modules/hardened-instance/main.tf

modules/hardened-instance/main.tf
data "aws_ami" "hardened_base" {
  owners      = [var.trusted_ami_account_id]                            # Restricts to ABC Bank's OWN AMI-building account — never search across all of AWS unscoped
  most_recent = true

  filter {
    name   = "name"
    values = ["abc-bank-hardened-al2023-*"]                              # Matches the bank's own pre-hardened, security-team-approved AMI naming convention
  }
  filter {
    name   = "state"
    values = ["available"]                                                # Excludes any AMI still mid-build or deregistered
  }
}

resource "aws_instance" "this" {
  ami                          = data.aws_ami.hardened_base.id
  instance_type                = var.instance_type
  subnet_id                    = var.subnet_id
  associate_public_ip_address  = false                                   # HARDCODED false — not a variable, so no consumer of this module can ever accidentally opt into a public IP
  vpc_security_group_ids       = [aws_security_group.this.id]

  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                  = "required"                             # Enforces IMDSv2 — IMDSv1 requests are rejected outright, closing the SSRF path from our story
    http_put_response_hop_limit  = 1                                        # Limits metadata responses to one network hop — prevents forwarding metadata requests through a proxy on the instance itself
  }

  root_block_device {
    encrypted   = true                                                    # Explicit here too, belt-and-braces alongside the account-wide default from ebs-encryption-default.tf

modules/hardened-instance/security-group.tf

modules/hardened-instance/security-group.tf
resource "aws_security_group" "this" {
  name   = "${var.name}-sg"
  vpc_id = var.vpc_id

  egress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]                                          # Outbound HTTPS only — for SSM Agent, package updates, etc. (Project 07/08 patterns)
  }
}

resource "aws_security_group_rule" "allowed_sources" {
  for_each = var.allowed_source_security_groups                          # One ingress rule PER named allowed source — keyed by name, not index, safe to add/remove individually

  type                     = "ingress"
  security_group_id        = aws_security_group.this.id
  from_port                = each.value.port
  to_port                  = each.value.port
  protocol                 = "tcp"
  source_security_group_id = each.value.security_group_id                # References ANOTHER security group by ID — never a raw CIDR block
}

modules/hardened-instance/outputs.tf

modules/hardened-instance/outputs.tf
output "instance_id" {
  value = aws_instance.this.id
}

output "security_group_id" {
  value = aws_security_group.this.id                                     # Exposed so OTHER instances can reference THIS one as an allowed source — chaining continues outward
}

10 Code Explanation Summary

Block / ArgumentWhat it doesCommon mistake to avoid
http_tokens = "required"Mandates IMDSv2's session-token flow, rejecting the older, SSRF-vulnerable IMDSv1 requests entirelyLeaving this as "optional" (the historical default) — that permits BOTH versions, leaving the exact vulnerability path open even though IMDSv2 is technically available
http_put_response_hop_limit = 1Limits how many network hops a metadata response can traverseLeaving this higher than necessary — a higher hop limit can allow metadata requests to be relayed through containers or proxies running on the instance, widening the SSRF blast radius even under IMDSv2
No variable exposed for associate_public_ip_addressA deliberate module design choice — the setting is hardcoded, not parameterizedThe opposite mistake: exposing every possible setting as a variable "for flexibility" — some settings (like this one) should be structurally fixed specifically to prevent misuse, not left configurable
source_security_group_id instead of cidr_blocksScopes an ingress rule to instances behind a specific security group, regardless of their changing IP addressesFalling back to a CIDR block "just to get it working quickly" — reintroduces exactly the IP-based fragility and over-broad access this pattern is designed to avoid

11 Execution Flow, Explained Internally

terraform apply — account-wide encryption default

Applies once per account/region; it has no effect on EBS volumes that already exist — only volumes created AFTER this setting is enabled are automatically encrypted, which is why the module's own root_block_device { encrypted = true } remains valuable as an explicit, resource-level guarantee too.

terraform apply — hardened-instance module

The data "aws_ami" lookup resolves first, then the instance and its security group are created, then each for_each-driven ingress rule is added — all inferred automatically from the resource reference graph.

Migrating a legacy instance

Moving from a public to a private subnet, with a completely different resource shape (module call vs. bare resource), is a destroy-and-recreate from Terraform's perspective — plan this migration during an approved maintenance window, not as a routine apply.

Enforcing IMDSv2 account-wide can break agents or scripts still using IMDSv1-style requests — audit and test every instance's running software against IMDSv2 before rolling this out broadly, especially for any legacy or third-party tooling.

.github/workflows/terraform-hardened-instance-check.yml
name: hardened-instance-guardrail
on:
  pull_request:
    paths: ["**/*.tf"]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform plan -out=tfplan
      - name: Fail if any new instance skips the hardened module or allows public IPs
        run: |                                                          # Structural guardrail — same spirit as Project 07's SSH-ingress check
          terraform show -json tfplan | jq -e '
            [.resource_changes[] | select(.type=="aws_instance") |
             select(.change.after.associate_public_ip_address == true)] | length == 0
          '
A pipeline-level check that fails the build on any new aws_instance with a public IP catches both mistakes AND any future attempt to bypass the hardened module by writing a bare aws_instance resource directly.

14 Interview Preparation

Q: How does IMDSv2 specifically defend against SSRF-based credential theft?
IMDSv2 requires a PUT request to obtain a session token before any metadata can be read — most SSRF vulnerabilities only let an attacker control the URL of a GET request, not craft an arbitrary PUT, so the token requirement blocks the typical exploitation path even when the SSRF flaw itself still exists.
Q: Why set http_put_response_hop_limit to 1?
It prevents the metadata response from being relayed through additional network hops such as a container or proxy running on the instance — without this limit, certain SSRF variants could still reach the metadata service indirectly even with IMDSv2 enforced.
Q: Why deliberately not expose associate_public_ip_address as a module variable?
Some settings are safer as structurally fixed rather than configurable — exposing this as an override would let any consumer of the module accidentally (or deliberately) reintroduce a public IP, defeating the module's core purpose.
Q: What's the advantage of security-group-referenced ingress rules over CIDR-based rules?
A security-group reference automatically stays accurate as the referenced resource's underlying IPs change over time, and is easier to audit at a glance ("what security group can reach this") than a list of IP ranges whose origin may not be obvious months later.
Manager round: How would you safely roll out IMDSv2 enforcement across an existing fleet without breaking anything?
Audit running software for IMDSv1 dependency first (via VPC Flow Logs or agent version inventories), fix or upgrade anything non-compliant, roll out enforcement to a low-risk environment first, then expand — the same staged rollout discipline used for the SCPs in Project 05.
