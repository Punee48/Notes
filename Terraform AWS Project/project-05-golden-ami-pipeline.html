Golden AMI Pipeline with Packer + Terraform for Immutable Infrastructure

Foundational-Intermediate · Bake it once, deploy it everywhere, never SSH in to patch it.

01The Enterprise Problem This Solves

The auto scaling group built in Project 6 needs to launch instances that are already correctly configured the moment they boot — the right OS packages, the right monitoring agent, the right hardened security baseline — without waiting on a slow configuration-management run after launch, and without any two instances in the fleet ever silently drifting from each other because someone SSH'd into one of them and made a manual fix at 2 AM. This project builds the pipeline that produces a single, versioned, pre-baked AMI — a "golden image" — using Packer to build it and Terraform to consume it, so "patch the fleet" becomes "bake a new AMI, roll it out," not "SSH into forty servers."

02The Story: The Server Nobody Could Reproduce

Production Incident Replay An EC2 instance behind the payments service starts throwing intermittent 500s. The on-call engineer needs to launch a replacement fast — except the instance was originally provisioned by hand two years ago, patched in-place a dozen times since by different engineers, each patch applied directly over SSH with no record kept anywhere. Nobody can say with confidence which OS packages, which OpenSSL version, or which cron jobs are actually running on it, because the running instance is the only documentation that ever existed. Launching a "replacement" from the original base AMI produces a server that behaves subtly differently — some environment variable set by a forgotten manual fix eighteen months ago is simply gone, and a downstream service that quietly depended on it starts failing in a new way. What should have been a five-minute instance swap turns into a multi-hour archaeology exercise, because the fleet was never actually identical — it just looked identical from the outside. A golden AMI pipeline makes this specific failure structurally impossible: every instance is baked from the exact same versioned image, and "what's actually on this server" is answered by reading the Packer template in Git, not by SSHing in and hoping.

03Deep Technical Explanation

Immutable infrastructure as a discipline, not just a buzzword

Immutable infrastructure means once an instance is launched, it is never modified in place — no patches, no config changes, no manual fixes applied to a running instance. Any change requires baking a new AMI and replacing the instance entirely. This trades a small amount of speed (you can't just SSH in and fix something instantly) for a much larger amount of certainty: every instance running a given AMI version is provably, byte-for-byte identical to every other instance running that version, because they were all launched from the same immutable image.

What Packer actually does, and where Terraform picks up

Packer's job stops the moment an AMI exists in your account — it launches a temporary build instance from a base AMI, runs your provisioning steps (OS packages, hardening, monitoring agents) against it, snapshots the result as a new AMI, and terminates the build instance. Packer never launches your production fleet. Terraform's job starts where Packer's ends: reading that baked AMI's ID (via the aws_ami data source, filtered by name pattern and a "most recent" sort) and using it as the ami_id input to the launch template that Project 6's Auto Scaling group consumes.

AMI versioning and the "most recent" data source pattern

Rather than hardcoding an AMI ID into Terraform (which would require a code change and a deploy every time a new image is baked), the standard pattern uses data "aws_ami" with a name_regex or tag filter plus most_recent = true, so Terraform always resolves to the latest AMI matching a naming convention at plan time. This is powerful but has a sharp edge covered directly in the failure scenarios below: it means the exact same Terraform code can resolve to a different AMI on two different days, purely because a new image was baked in between — a form of implicit drift that has to be deliberately managed.

Provisioning inside Packer: baking security and observability in, not bolting them on after

Because the AMI is the one artifact every instance in the fleet inherits from, it's the natural place to bake in things that should never depend on a post-boot step succeeding: CIS-hardening steps, the CloudWatch agent, log shipping configuration, and OS patches current as of the bake date. Anything baked here is guaranteed present the instant an instance boots — no race condition with a user-data script that might fail silently.

05Step-by-Step Implementation

5.1 — The Packer template

packer/app-image.pkr.hcl 
packer {
  required_plugins {
    amazon = {
      source  = "github.com/hashicorp/amazon"
      version = "~> 1.3"
    }
  }
}

source "amazon-ebs" "app" {
  # Base image: official Amazon Linux 2023, resolved by filter so the
  # build always starts from the latest patched base, not a stale AMI ID.
  source_ami_filter {
    filters = {
      name                = "al2023-ami-*-x86_64"
      virtualization-type = "hvm"
    }
    most_recent = true
    owners      = ["137112412989"] # Amazon's official AMI owner ID
  }

  instance_type = "t3.medium" # build instance size — unrelated to the fleet's runtime size
  ssh_username  = "ec2-user"

  # Every AMI this template produces is uniquely and sortably named.
  ami_name = "acme-app-{{timestamp}}"

  tags = {
    Name       = "acme-app-{{timestamp}}"
    BakedBy    = "packer"
    SourceRepo = "acme/golden-ami"
  }
}

build {
  sources = ["source.amazon-ebs.app"]

  provisioner "shell" {
    # Runs on the temporary build instance only — never on the fleet.
    inline = [
      "sudo dnf update -y",                          # current OS patches baked in at build time
      "sudo dnf install -y amazon-cloudwatch-agent", # observability baked in, not bolted on post-boot
      "sudo systemctl enable amazon-cloudwatch-agent",
    ]
  }

  provisioner "file" {
    source      = "files/cis-hardening.sh"
    destination = "/tmp/cis-hardening.sh"
  }

  provisioner "shell" {
    inline = [
      "sudo bash /tmp/cis-hardening.sh", # CIS benchmark hardening, baked into every instance uniformly
      "sudo rm /tmp/cis-hardening.sh",
    ]
  }
}

5.2 — Resolving the AMI in Terraform

envs/prod/ami.tf 
data "aws_ami" "app" {
  most_recent = true # always resolve to the newest matching AMI at plan time
  owners      = ["self"]     # only AMIs baked by this account's own Packer pipeline

  filter {
    name   = "name"
    values = ["acme-app-*"] # must match the ami_name pattern from the Packer template
  }

  filter {
    name   = "tag:BakedBy"
    values = ["packer"] # extra guardrail — excludes any manually-created AMI with a similar name
  }
}

output "resolved_ami_id" {
  # Always check this output after every plan — it's the fastest way
  # to confirm which AMI version a given apply is about to roll out.
  value = data.aws_ami.app.id
}

5.3 — Bake pipeline in CI

.github/workflows/bake-golden-ami.yml (excerpt) 
on:
  schedule:
    - cron: "0 3 * * 1" # weekly bake, Monday 3am — keeps OS patches current on a fixed cadence
  workflow_dispatch: {} # also allow an on-demand bake for urgent patches

jobs:
  bake:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build golden AMI
        run: |
          packer init packer/app-image.pkr.hcl
          packer build packer/app-image.pkr.hcl
      # A follow-up job (not shown) then triggers a Terraform plan/apply
      # in the deploy pipeline so the new AMI actually rolls out —
      # baking alone does not touch running infrastructure.

Plain-English walkthrough

The Packer template never touches production — it launches its own disposable build instance, provisions it, and throws it away, leaving only the AMI behind. The naming pattern acme-app-{{timestamp}} combined with Terraform's most_recent = true data source is what lets the fleet automatically pick up new bakes without anyone editing a hardcoded AMI ID anywhere. The weekly scheduled bake keeps OS patches from going stale even when no application code has changed — a discipline many teams skip until an unpatched CVE in a base image becomes the reason for an incident. Critically, baking a new AMI and rolling it out to the fleet are two separate steps: Packer produces the artifact, but nothing forces existing instances to use it until a Terraform apply against the Auto Scaling group (Project 6) actually triggers an instance refresh.

06Failure Scenarios — What Breaks in Real Life

Failure: "most_recent" AMI resolves differently between plan and apply A new AMI finishes baking in the gap between a terraform plan being reviewed and someone running apply an hour later — the applied AMI is not the one that was actually reviewed. Debug: in CI, always run plan and apply back-to-back in the same job run against the same saved plan file (terraform apply tfplan), never as separate manually-triggered steps with a gap between them.
Failure: a bad bake gets picked up fleet-wide before anyone notices A provisioning script bug bakes a broken CloudWatch agent config into the golden AMI, and the very next Auto Scaling event launches new instances from it — silently degrading observability across every new instance in the fleet. Debug: this is exactly why Project 15's blue/green cutover pattern matters even for AMI rollouts, not just application deploys — validate a new AMI against a small canary batch of instances before letting the full ASG instance-refresh roll it out everywhere.
Failure: build instance's temporary security group is too permissive Packer's default behavior opens a temporary security group for SSH access to the build instance during provisioning, and a misconfigured VPC/subnet choice for the build accidentally places it somewhere internet- reachable. Debug: always pin Packer's build to a private subnet with a scoped, temporary security group, and confirm in the template that ssh_interface/networking settings never default to a public subnet.

07Interview Talking Points

"How do you handle patching and configuration drift across a large EC2 fleet?"
Describe immutable infrastructure directly: nothing is ever patched in place; a new golden AMI is baked on a schedule (and on-demand for urgent CVEs), and drift is prevented structurally because every instance is byte-for- byte identical to every other instance on the same AMI version — there's no "config drift" to detect because there's no in-place config change possible.
"How does Terraform know which AMI to deploy without you hardcoding an ID?"
Explain the data "aws_ami" most-recent pattern precisely, and be ready to discuss its sharp edge: that the same code can resolve to a different AMI on different days, which is why plan and apply need to happen against the same saved plan file, not as separate disconnected steps.
