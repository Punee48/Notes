PROJECT 04 OF 40 · INTERMEDIATE

Centralized Logging Infrastructure Across Every Account

The network hub is live. Now we build its audit counterpart: one tamper-resistant logging account that every other account is required to ship CloudTrail, VPC Flow Logs, and application logs into — using cross-account IAM roles and templated bucket policies instead of another RAM share.

01 The Banking Story

A routine internal audit just asked a question nobody on the team could answer quickly: "Show us every IAM policy change made in the Production account over the last 90 days." The answer exists — CloudTrail is technically enabled in every account — but each account's trail writes to a local S3 bucket that any admin in that same account can also read, modify the bucket policy of, or even delete. That fails the auditor's very first test: logs must be stored somewhere the people being logged cannot tamper with.

Our manager's assignment: "Build one dedicated Logging account. Every other account's CloudTrail, VPC Flow Logs, and application logs get shipped there automatically, the moment the account is created — and nobody in Dev, UAT, Prod, or Shared Services should have the permissions to alter or delete a log once it lands."

02 Business Requirement, Risk & Impact

Business Requirement

Every account's audit trail must be centrally stored, immutable once written, and queryable across the whole estate for a single audit request.

Customer Requirement

The bank's Security and Compliance team needs one place to search logs, not four separate accounts with four separate access requests.

Current Infrastructure

CloudTrail enabled per-account, writing to a local bucket in that same account, readable and modifiable by that account's own administrators.

Existing Manual Process

An auditor's request today means separately logging into four accounts, exporting CloudTrail data from each, and manually merging it — slow, and each export is only as trustworthy as that account's own admins.

Problems With Current Process

  • Local admins can delete or alter their own account's trail — a serious tamper risk in a banking context
  • No unified view across accounts for incident investigation
  • Retention policy is set per-account, inconsistently

Business Challenges

Financial regulators require audit logs to be immutable and centrally retained for a defined period (commonly 7 years for banking) — a per-account bucket an admin can delete does not meet that bar.

Risk Analysis

High: a malicious or compromised admin in any single account could currently delete the evidence of their own actions — a direct regulatory and fraud-detection risk.

Business Impact

Failing this exact control in a regulatory audit can result in formal findings, fines, and mandated remediation timelines for a bank.

03 Why a Dedicated Logging Account, and What We Rejected

Why a separate AWS account for logging

Account-level isolation is the strongest boundary AWS offers. An admin with full permissions in the Production account still has zero permissions in the Logging account by default — so even a fully compromised Production account cannot reach in and delete its own historical logs.

Alternatives considered, and why they were rejected

04 Terraform Concepts You Must Understand Before We Build

Cross-Account IAM Roles (AssumeRole)

What it is: an IAM role in the Logging account with a trust policy that names specific other accounts as allowed to assume it, plus a separate role in each spoke account that CloudTrail/Flow Logs uses to write into the Logging account's bucket.

Why it exists: cross-account writes to S3 need explicit permission on both sides — the writer needs permission to write, and the bucket owner needs to explicitly allow that specific external account to do so. Neither side alone is sufficient.

Production example: the Logging account's bucket policy allows the cloudtrail.amazonaws.com service principal from a specific source account to write objects, using a condition on aws:SourceArn so no other account's CloudTrail can write there even if it tried.

Common mistake: writing a bucket policy that trusts "any CloudTrail, from anywhere" instead of scoping it to specific known account IDs — this would let an unrelated AWS account's CloudTrail write into your bucket if they happened to target it.

Template Files (templatefile function)

What it is: the templatefile() function renders an external .tpl file (usually a JSON IAM policy) as a string, substituting in variables — instead of writing enormous inline JSON blocks inside main.tf.

Why it exists: the bucket policy in this project must list a dynamic set of source account IDs and ARNs. Writing that as a raw inline string is unreadable and error-prone to escape correctly; a template file keeps the JSON structure separate from the Terraform logic that fills it in.

Production example: templatefile("${path.module}/policies/logging-bucket-policy.json.tpl", { account_ids = var.spoke_account_ids, bucket_arn = aws_s3_bucket.logs.arn }) renders the same policy shape for as many accounts as are passed in.

Alternative approach: Terraform's aws_iam_policy_document data source builds the same JSON without a separate file, using native HCL blocks — a good alternative when the policy doesn't need heavy templating logic; we compare both approaches below.

Terraform Functions Used in This Project

jsonencode(): converts an HCL map/list directly into a JSON string — useful for simpler policies that don't need a separate template file.

formatdate(): used to compute a human-readable lifecycle transition label in tags, from a base timestamp.

concat() and distinct(): combine and de-duplicate the list of source account IDs gathered from multiple environments before rendering the bucket policy template.

05 AWS Concepts: CloudTrail, Centralized S3, and KMS

What is an Organization Trail

A single CloudTrail trail, created once in the AWS Organization's management account, that automatically applies to and logs every member account — including future accounts created later, with zero per-account setup.

Why it exists

It removes the risk of a spoke account's admin disabling their own local trail — an organization trail cannot be disabled or altered from a member account at all.

S3 Object Lock (Compliance Mode)

Once enabled, Object Lock in Compliance mode prevents an object from being deleted or overwritten by any principal, including the AWS account root user, until the retention period expires — the true "immutability" a banking audit requires.

KMS Cross-Account Key Policy

The Logging account's KMS key (used to encrypt log objects) needs a key policy that explicitly grants spoke accounts' CloudTrail/Flow Logs roles permission to Encrypt, separate from the S3 bucket policy that grants PutObject — both layers must independently allow the write.

High Availability

S3 and CloudTrail are both regional-redundant by default; the Logging bucket itself needs no multi-AZ configuration to achieve this.

Pricing

CloudTrail management events are free for the first copy in an org trail; data events (e.g. S3 object-level logging) and storage/retention over years are the main ongoing costs to monitor.

Limitations

Object Lock must be enabled at bucket creation time — it cannot be turned on for an existing bucket, which is why this project creates the Logging bucket fresh with Object Lock specified up front.

Best Practice

Separate the CloudTrail log bucket from the VPC Flow Logs and application log buckets — different retention and access patterns, and it limits blast radius if one bucket's policy is ever misconfigured.

07 Complete Solution Design

A new Logging AWS account hosts two S3 buckets (CloudTrail logs, VPC Flow Logs) and one KMS key, all created by a dedicated root module. An AWS Organizations-level trail (configured from the management account, referencing the Logging account's bucket) captures every account's API activity automatically. Each spoke account's Project 02 VPC gets Flow Logs enabled, targeting the Logging account's Flow Logs bucket via a cross-account IAM role.

  • Logging account module: KMS key with a templated cross-account key policy, CloudTrail bucket with Object Lock (Compliance, 7-year retention), Flow Logs bucket with Object Lock (Compliance, 1-year retention), bucket policies rendered via templatefile().
  • Management account resource: a single aws_cloudtrail resource with is_organization_trail = true, pointing at the Logging account's bucket.
  • Spoke account module: aws_flow_log resource per VPC (reusing subnet/VPC IDs from Project 02), targeting the Logging account's S3 bucket with an IAM role scoped only to write flow log objects.

09 Implementation — Full Production Code

environments/logging/policies/flow-logs-bucket-policy.json.tpl

policies/flow-logs-bucket-policy.json.tpl
{
  "Version": "2012-10-17",
  "Statement": [
    %{ for account_id in account_ids ~}                        // templatefile directive: loops once per account ID passed in
    {
      "Sid": "AllowFlowLogsWrite-${account_id}",
      "Effect": "Allow",
      "Principal": { "Service": "delivery.logs.amazonaws.com" },
      "Action": "s3:PutObject",
      "Resource": "${bucket_arn}/AWSLogs/${account_id}/*",       // Interpolates BOTH the loop variable and an outer variable
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "${account_id}" }
      }
    }%{ if account_id != account_ids[length(account_ids) - 1] },%{ endif }
    %{ endfor ~}
  ]
}

environments/logging/main.tf

environments/logging/main.tf
resource "aws_kms_key" "logs" {                              # One shared key encrypts both log buckets in this account
  description             = "ABC Bank centralized logging KMS key"
  deletion_window_in_days = 30                                 # Long window — accidental deletion of this key would make all past logs unreadable
  policy                  = templatefile("${path.module}/policies/kms-key-policy.json.tpl", {
    spoke_account_ids = var.spoke_account_ids                  # Renders one Allow statement per spoke account, same pattern as the bucket policy
    logging_account_id = data.aws_caller_identity.current.account_id
  })
}

resource "aws_s3_bucket" "flow_logs" {
  bucket = "abc-bank-central-flow-logs-2026"
}

resource "aws_s3_bucket_versioning" "flow_logs" {
  bucket = aws_s3_bucket.flow_logs.id
  versioning_configuration { status = "Enabled" }               # Required precondition before Object Lock can be configured
}

resource "aws_s3_bucket_object_lock_configuration" "flow_logs" {  # Makes every object written here immutable for the retention period
  bucket = aws_s3_bucket.flow_logs.id
  rule {
    default_retention {
      mode = "COMPLIANCE"                                        # COMPLIANCE = cannot be shortened or deleted early by ANY principal, including root
      days = 365
    }
  }
}

resource "aws_s3_bucket_policy" "flow_logs" {                    # Applies the rendered template as the bucket's actual policy
  bucket = aws_s3_bucket.flow_logs.id
  policy = templatefile("${path.module}/policies/flow-logs-bucket-policy.json.tpl", {
    account_ids = var.spoke_account_ids
    bucket_arn  = aws_s3_bucket.flow_logs.arn
  })
}

data "aws_caller_identity" "current" {}                          # Reads the current (Logging) account's own ID, used inside the KMS key policy template

modules/vpc-flow-logs/main.tf

modules/vpc-flow-logs/main.tf
resource "aws_flow_log" "this" {
  vpc_id               = var.vpc_id
  traffic_type         = var.traffic_type
  log_destination_type = "s3"                                     # Writes directly to S3 rather than CloudWatch Logs — cheaper at this log volume
  log_destination       = var.central_log_bucket_arn               # Points cross-account at the Logging account's bucket — no IAM role needed for the S3 destination type

  destination_options {
    file_format        = "parquet"                                 # Columnar format — far cheaper and faster to query later with Athena than plain text
    per_hour_partition = true                                       # Partitions objects by hour, keeping Athena query scans small and cheap
  }

  tags = { Name = "vpc-flow-logs-${var.vpc_id}" }
}

11 Execution Flow, Explained Internally

Apply order

Logging account first (buckets, KMS key, policies), then the management account's organization trail (needs the bucket name as an output), then each spoke account's Flow Logs (needs the bucket ARN as an output) — three dependent applies, same pattern as Project 03's hub-then-spokes.

templatefile() at plan time

Terraform renders the template and computes its content hash during plan — if you change spoke_account_ids, the plan will show the bucket policy resource as "changed" even though no other line in main.tf was touched.

terraform apply — Object Lock nuance

Because Object Lock must be set at bucket creation, if you forget it on first apply, Terraform cannot retroactively add it — you'd need to create a brand-new bucket, another reason to get this right on the very first apply in a real account.

Never run terraform destroy against the Logging account's buckets while any retained objects are still inside their Compliance-mode lock window — AWS will refuse the deletion, by design, and Terraform will report the destroy as failed.

12 CI/CD Integration

.github/workflows/terraform-logging.yml
name: terraform-logging
on:
  push:
    branches: [main]
    paths: ["environments/logging/**"]

jobs:
  logging-account:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/logging } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform validate
      - name: Plan
        run: terraform plan -out=tfplan
      - name: Manual approval gate
        if: github.ref == 'refs/heads/main'
        uses: trstringer/manual-approval@v1                        # Compliance-mode buckets are unrecoverable if misconfigured — require a human sign-off before apply
        with:
          approvers: security-lead,platform-lead
      - run: terraform apply -auto-approve tfplan
Any pipeline touching Object Lock or KMS key policies in a banking environment should require a manual approval step — the blast radius of a mistake here (permanently un-writable or un-readable logs) is high enough to justify slowing down for a human review.

14 Interview Preparation

Q: Why does centralized logging need its own AWS account instead of just stricter bucket policies?
Account-level isolation means even a fully compromised admin credential in a spoke account has zero default permissions in the Logging account — a bucket policy alone still lives inside a boundary that account's own admins can eventually alter.
Q: What's the difference between S3 Object Lock's Compliance and Governance modes?
Compliance mode blocks deletion or retention shortening for every principal, including the account root user, until the retention period expires; Governance mode allows specifically-permitted IAM principals to override it — only Compliance mode satisfies a strict audit-immutability requirement.
Q: Why use templatefile() instead of just writing the JSON policy inline with jsonencode()?
Both work; templatefile() keeps a large, loop-heavy policy readable in its own file with template directives, while jsonencode() is often cleaner for smaller, non-repeating policies — the choice is about readability and maintainability, not capability.
Q: Why must an AWS Organization trail be created from the management account?
Only the management account (or a delegated administrator account) has the organizational visibility and permission to apply a single trail across every current and future member account — member accounts cannot create org-wide trails themselves.
Manager round: An auditor asks how you'd prove logs haven't been tampered with. What's your answer?
CloudTrail log file validation produces cryptographic digest files alongside the logs, and Object Lock in Compliance mode makes the underlying objects themselves undeletable and unmodifiable for their retention period — together they provide both tamper-evidence and tamper-resistance.
