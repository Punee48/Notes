PROJECT 01 OF 40 · INTERMEDIATE

Enterprise Remote State Management + Reusable Terraform Modules

We are laying the foundation every one of the next 39 projects will stand on: a locked, versioned, team-safe Terraform backend, and a module structure that scales to 200+ microservices without collapsing into copy-pasted spaghetti.

01 The Banking Story

We joined ABC Bank as DevOps Engineers on the Digital Banking Platform program.

The platform is being rebuilt as a set of 200+ microservices, spread across multiple AWS accounts and one on-premises data center that still hosts core banking batch jobs.

Right now, three engineers each run Terraform from their own laptops, using local terraform.tfstate files that live only on their machines. Nobody else on the team can see what infrastructure exists unless they ask in Slack. Last Friday, two engineers applied changes to the same VPC within ten minutes of each other — the second apply silently overwrote the first engineer's subnet changes, because Terraform had no way of knowing another apply was already running.

Our manager, the Infrastructure Lead for the Digital Banking Platform, has given us our first assignment: before we write a single line of application infrastructure, fix how the team stores and locks Terraform state, and build the first reusable module so every future project (VPC, EKS, RDS, Transit Gateway — all 39 of them) can be composed instead of rewritten from scratch.

02 Business Requirement, Risk & Impact

Business Requirement

The bank needs infrastructure changes to be safe, auditable, and repeatable across 200+ microservices, several AWS accounts, and an on-prem data center — without depending on any single engineer's laptop.

Customer Requirement

Internal customer = the Infrastructure & Platform teams. They need a shared source of truth for "what exists" and a way to collaborate on changes without stepping on each other.

Current Infrastructure

Manually provisioned VPCs, EC2s, and RDS instances. Terraform is used by individuals, but state lives locally per-laptop with no locking or history.

Existing Manual Process

Engineer runs terraform apply locally, e-mails or Slacks teammates "I'm applying now, don't touch it," and hopes nobody else runs Terraform at the same time.

Problems With Current Process

  • No shared state → nobody has a single source of truth
  • No locking → concurrent applies corrupt or overwrite each other's changes
  • Laptop loss = the state file (and the record of all infrastructure) is gone
  • No audit trail of who changed what, and when

Business Challenges

Banking regulators expect change management and audit trails for production infrastructure. A local .tfstate file satisfies none of that.

Risk Analysis

High: state file corruption or loss can force a full "import" of live production resources — a multi-day effort on a banking estate this size, during which no safe changes can be made.

Business Impact

A corrupted state file during a release window could delay the launch of the Digital Banking Platform, with direct cost and regulatory-reporting consequences.

03 Why IaC, Why Terraform, Why Not the Alternatives

Why Infrastructure as Code is required

With 200+ microservices, manual provisioning cannot keep pace, and it cannot produce the audit trail a bank's regulators require. IaC turns every infrastructure change into a reviewable, version-controlled, testable artifact — a pull request, not a click in the console.

Why Terraform was selected

Terraform is cloud-agnostic (needed because ABC Bank runs AWS and on-prem VMware), has a mature state model that supports locking and remote backends, and has a huge provider ecosystem (AWS, VMware, Active Directory, DNS) that lets one tool manage the entire hybrid estate described later in this series.

04 Terraform Concepts You Must Understand Before We Build

Backend & Remote State

What it is: the backend tells Terraform where to store its state file (the JSON record of every resource it manages) instead of on your local disk.

Why it exists: Terraform decides what to create, change, or destroy by comparing your .tf code against the state file. If every engineer has their own copy, Terraform has no single truth to compare against — that's exactly the bug ABC Bank hit last Friday.

Internal working: on every plan or apply, Terraform downloads the current state from the backend (here, an S3 object), computes the difference against your code, then uploads the new state back to S3 when the apply finishes.

Production example: ABC Bank will store state for this project at s3://abc-bank-terraform-state/network/vpc/terraform.tfstate — a path per environment/component, not one giant shared file.

Alternative approaches: Terraform Cloud/HCP Terraform (managed backend with built-in locking and no DynamoDB needed) — we will use this later in the series once the team is comfortable with the fundamentals.

State Locking

What it is: a mechanism that prevents two apply operations from running against the same state at the same time.

Why it exists: without it, two engineers running apply simultaneously can both read the same "before" state, both compute a plan, and both write conflicting results — the second write wins and silently discards the first engineer's changes. This is precisely the incident from our story.

Internal working: when the S3 backend is paired with a DynamoDB table, Terraform writes a lock record (a row keyed by the state file's path) into DynamoDB before it starts an apply, and deletes it when the apply finishes. A second apply that tries to start while that row exists is blocked and shown a "state locked" error with the lock ID and who holds it.

Common mistake: engineers who hit a lock error during a crashed apply sometimes run terraform force-unlock without first confirming no other apply is genuinely in progress — doing that carelessly re-introduces the exact race condition the lock exists to prevent.

Root Modules vs. Child Modules

What it is: the root module is the directory where you run terraform apply. A child module is a reusable, self-contained folder of Terraform code that the root module calls, the way a function is called from a program's main entry point.

Why it exists: without modules, provisioning 200 microservices' worth of infrastructure would mean copy-pasting the same VPC/S3/IAM code 200 times — any bug fix would need to be repeated 200 times too.

Production example: in this project we build a child module named modules/backend-bootstrap that creates the S3 bucket and DynamoDB lock table. Every future project's root module can call the same pattern instead of re-defining it.

Best practice: a module should do one job well (e.g. "create a state backend") and expose that behavior through clearly named variables in and outputs out — never reach into another module's internal resources directly.

Providers, Variables, Locals, Outputs

Provider: the plugin that lets Terraform talk to a specific API — here, the aws provider, which translates HCL resource blocks into AWS API calls.

Variable: an input to your configuration, supplied from outside (a .tfvars file, an environment variable, or a CI/CD pipeline) so the same code can be reused for dev, UAT, and production with different values.

Local value: a named expression computed inside the configuration, used to avoid repeating the same calculation or string in multiple places.

Output: a value the module or root configuration exposes after apply — for example, the S3 bucket name and DynamoDB table name this project creates, which every future project's backend.tf will need to reference.

05 AWS Concepts: S3 and DynamoDB as Terraform Backend Infrastructure

Amazon S3 (as the state store)

What / Why

Object storage used here to hold one JSON file per Terraform state. Chosen because it is durable, versionable, and encryptable at rest.

High Availability

S3 replicates objects across multiple Availability Zones within a region automatically — no configuration needed for AZ-level HA.

Disaster Recovery

Versioning (enabled in this project) means a bad or corrupted state write can be rolled back to a previous version instead of being lost.

Security

Bucket is private, encrypted with KMS, and blocks all public access — required for anything touching a bank's infrastructure metadata.

Pricing

State files are tiny (kilobytes), so cost is negligible — a few cents per month even with versioning enabled across dozens of components.

Limitations

S3 alone provides no native locking — that gap is exactly what DynamoDB fills below.

Amazon DynamoDB (as the lock table)

What / Why

A managed NoSQL database. Terraform uses one table with a primary key (LockID) to store a single row per state file while it's being modified.

High Availability

DynamoDB is multi-AZ by default with no extra configuration, matching S3's durability characteristics.

Security

Access is restricted to the CI/CD role and engineers' IAM roles via least-privilege IAM policy — nobody else can read or delete lock rows.

Pricing

Using on-demand capacity mode, cost is driven by request volume; for a lock table hit only during plan/apply, this is a few cents per month.

Performance

Single-digit millisecond reads/writes — locking adds effectively no noticeable delay to terraform apply.

Best Practice

Use one shared lock table per AWS account/region for all Terraform state, not one table per project — the table just needs a LockID string key.

07 Complete Solution Design

We will build a small, standalone bootstrap root module whose only job is to create the backend infrastructure itself (S3 bucket + DynamoDB table). This is a well-known Terraform chicken-and-egg problem: you cannot store a remote backend's own state remotely before the backend exists.

This bootstrap module runs with a local state file, one time, by a senior engineer. Every project after this one points its backend.tf at the S3 bucket and DynamoDB table this bootstrap creates.

Design decisions:

  • One shared state bucket for the whole account, with a state key (path) per component — e.g. network/vpc/terraform.tfstate, compute/eks/terraform.tfstate — so future projects each get an isolated state file inside the same bucket.
  • One shared DynamoDB lock table for the whole account — locking is keyed by state path, so one table safely serves every project.
  • Versioning + KMS encryption + public access block on the bucket, non-negotiable for a banking environment.
  • The bootstrap logic itself is written as a reusable child module (modules/backend-bootstrap) so it can be re-run identically for other AWS accounts (dev, UAT, prod) later in this series.

modules/backend-bootstrap/main.tf

modules/backend-bootstrap/main.tf
resource "aws_s3_bucket" "state" {                     # The bucket that will hold every Terraform state file
  bucket = var.state_bucket_name                       # Bucket name comes from the root module's variable — keeps this module generic

  tags = merge(var.tags, {                              # merge() combines the common tags with a Name tag specific to this resource
    Name = "${var.environment}-terraform-state"
  })
}

resource "aws_s3_bucket_versioning" "state" {          # Enables versioning so a bad state write can be rolled back
  bucket = aws_s3_bucket.state.id                       # References the bucket created above by its resource ID

  versioning_configuration {
    status = "Enabled"                                  # "Enabled" keeps every past version of the state object
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "state" {  # Forces encryption at rest
  bucket = aws_s3_bucket.state.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:kms"                          # Uses KMS rather than plain AES256 — a banking security requirement
    }
    bucket_key_enabled = true                             # Reduces KMS request cost by reusing a bucket-level data key
  }
}

resource "aws_s3_bucket_public_access_block" "state" {  # Belt-and-braces: makes it impossible for this bucket to ever be made public
  bucket = aws_s3_bucket.state.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_dynamodb_table" "lock" {                   # The lock table Terraform uses to prevent concurrent applies
  name         = var.lock_table_name                     # Table name comes from the root module's variable
  billing_mode = "PAY_PER_REQUEST"                        # On-demand pricing — no capacity planning needed for a low, spiky workload like this
  hash_key     = "LockID"                                 # Terraform's S3 backend expects the partition key to be named exactly "LockID"

  attribute {
    name = "LockID"                                       # Declares the LockID attribute as a string, matching the hash_key above
    type = "S"
  }

  tags = merge(var.tags, {
    Name = "${var.environment}-terraform-locks"
  })
}

11 Execution Flow, Explained Internally

terraform init

Downloads the aws provider plugin matching the version constraint, and (for future projects) initializes the S3 backend by checking connectivity and, if a state file exists, offering to migrate any local state into it.

terraform validate

Checks that the HCL syntax is correct and that resource arguments are internally consistent — this runs before any AWS API call is made.

terraform fmt

Rewrites files into Terraform's canonical formatting (indentation, alignment) — run this before every commit so diffs stay clean.

terraform plan

Builds a dependency graph from your resource blocks, reads current state, and calculates exactly what would change — nothing is created yet.

Execution / dependency graph

Terraform determines that aws_s3_bucket_versioning depends on aws_s3_bucket.state.id, so the bucket must be created first — this ordering is inferred automatically from resource references, not written by us.

terraform apply

Acquires the state lock (once this project's own bucket/table exist), executes the plan's AWS API calls in dependency order, then writes the new state and releases the lock.

terraform destroy

Reads current state, computes the reverse dependency order (delete things that depend on other things first), and removes each resource via the AWS API, then updates state to reflect the empty result.

Never manually delete the S3 state bucket or DynamoDB lock table once other projects depend on them — doing so orphans every project's remote state and forces a manual recovery.

12 CI/CD Integration — GitHub Actions

.github/workflows/terraform-bootstrap.yml
name: terraform-bootstrap                                # Pipeline name shown in the GitHub Actions tab

on:
  pull_request:
    paths: ["bootstrap/**", "modules/backend-bootstrap/**"]  # Only triggers when these folders change
  push:
    branches: [main]
    paths: ["bootstrap/**", "modules/backend-bootstrap/**"]

jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: bootstrap                       # All commands run from the root module's folder
    steps:
      - uses: actions/checkout@v4                           # Pulls the repository code onto the runner

      - uses: hashicorp/setup-terraform@v3                  # Installs the Terraform CLI matching versions.tf
        with:
          terraform_version: "1.7.5"

      - name: Terraform fmt check
        run: terraform fmt -check -recursive                # Fails the pipeline if any file isn't canonically formatted

      - name: Terraform init
        run: terraform init

      - name: Terraform validate
        run: terraform validate

      - name: Terraform plan
        run: terraform plan -out=tfplan                     # Saves the exact plan to a file so apply can't drift from what was reviewed

      - name: Terraform apply
        if: github.ref == 'refs/heads/main'                  # Only auto-applies on main — pull requests only get a plan
        run: terraform apply -auto-approve tfplan
Pull requests should show terraform plan output as a PR comment for peer review — treat every infrastructure change with the same review discipline as application code, which is exactly what banking change-management audits expect.

14 Interview Preparation

Q: Why do you need DynamoDB if you already have S3 for state?
S3 alone has no concept of "in progress" — two applies can both read the same object at once. DynamoDB's conditional writes give Terraform an atomic way to say "only one apply may hold this lock at a time."
Q: A teammate's laptop crashed mid-apply and now nobody can run Terraform. What do you do?
Confirm no apply is genuinely still running (check CI/CD, ask the team), inspect the lock info Terraform prints, then run terraform force-unlock <LOCK_ID> — never do this without first confirming the apply truly isn't in progress.
Q: Why does the bootstrap module use local state instead of the S3 backend it creates?
Because you cannot configure a backend that doesn't exist yet — the bootstrap has to run once with local state to create the very S3 bucket and DynamoDB table that later projects will use remotely.
Q: How would you structure state for 200 microservices without one giant state file?
One shared bucket, but a distinct state key (path) per component/project — e.g. network/vpc/terraform.tfstate, services/payments-api/terraform.tfstate — so a failure or lock in one project's state never blocks another's.
Manager round: Why not just use Terraform Cloud from day one and skip S3/DynamoDB entirely?
It's a completely valid alternative and we'll adopt it later in this series — but ABC Bank's first phase intentionally starts with the AWS-native backend so the team deeply understands what a managed backend is abstracting away, before relying on it.
