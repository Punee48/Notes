01The Enterprise Problem This Solves

The web tier from Project 6 is stateless and disposable — a failed instance is replaced automatically without anyone noticing. The database behind it is neither. This project builds a Multi-AZ RDS instance whose synchronous standby can take over in seconds during an AZ failure, automated backups with point-in-time recovery, and — critically, because this is the part almost every team skips — a scheduled, automated restore test that proves those backups actually work, instead of trusting them on faith until the day they're needed.

02The Story: The Backup That Had Never Been Restored

Production Incident Replay A bad migration script run against production corrupts a chunk of the orders table. The team's response plan is calm and confident: "we have automated daily backups, we'll restore to just before the migration ran." The restore is kicked off. Forty minutes later, it fails — the backup snapshot references a database parameter group setting that was changed three months ago and never reconciled with what the snapshot actually expects, an incompatibility nobody could have found by reading dashboards, because nobody had ever actually tried a restore since the backups were first configured. The team ends up reconstructing lost orders from application-level logs and customer support tickets instead of a five-minute RDS restore. The retro's single most important line: "automated backups" and "a working recovery process" are not the same claim, and the second one is only true if it's tested on a schedule, not assumed.

03Deep Technical Explanation

Multi-AZ: synchronous standby, not a read replica

RDS Multi-AZ provisions a synchronous standby replica in a different AZ. Every write is committed to the standby before being acknowledged to the application, so failover loses zero committed data — but this is not the same feature as a read replica: the standby is not queryable, exists purely for failover, and Multi-AZ alone doesn't add read capacity. Failover typically completes in under a minute and is triggered automatically by RDS on detecting a primary failure, or manually via a forced failover for planned maintenance.

Automated backups and the two recovery mechanisms they enable

RDS automated backups take a daily full snapshot plus continuous transaction log capture within the retention window, enabling two distinct recovery paths: restoring from a specific daily snapshot, or point-in-time recovery (PITR) to any second within the retention period by replaying transaction logs on top of the nearest snapshot. PITR is what would have let the team in the story restore to the exact second before the bad migration ran, rather than losing everything back to the previous daily snapshot.

Why a restore has to be tested, not just configured

A backup configuration can be syntactically correct and still produce a restore that fails in practice — parameter group incompatibilities, subnet group misconfpraiguration in the restore target, or IAM permissions that were never actually exercised. The only way to know a restore genuinely works is to actually run one, on a schedule, against a disposable target, and verify the restored data with a real query — treating "restore capability" as a tested feature of the system, not a checkbox in a backup configuration.

    name  = "log_min_duration_statement"
    value = "1000" # log queries over 1s — cheap, high-value observability
  }
}

resource "aws_db_instance" "main" {
  identifier     = "acme-prod-db"
  engine         = "postgres"
  engine_version = "15.4"
  instance_class = "db.r6g.large"

  allocated_storage     = 100
  max_allocated_storage = 500 # storage autoscaling ceiling — avoids manual resize pages
  storage_encrypted     = true

  db_subnet_group_name   = aws_db_subnet_group.main.name
  parameter_group_name   = aws_db_parameter_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]

  multi_az = true # synchronous standby in a second AZ — the core of this project

  backup_retention_period = 14 # days of automated backups + PITR window
  backup_window            = "03:00-04:00" # low-traffic window, UTC
  maintenance_window       = "mon:04:30-mon:05:30"

  deletion_protection = true # blocks "terraform destroy" from deleting prod's database by mistake
  skip_final_snapshot = false # always take one last snapshot even on a deliberate, approved destroy

  manage_master_user_password = true # RDS-managed credential in Secrets Manager — no plaintext password in this file (see Project 10)
}

5.2 — Automated restore test (CI-scheduled)

.github/workflows/rds-restore-test.yml (excerpt) 
on:
  schedule:
    - cron: "0 5 * * 0" # weekly, Sunday 5am — low-traffic window for the throwaway restore

jobs:
  restore-test:
    runs-on: ubuntu-latest
    steps:
      - name: Find latest automated snapshot
        run: |
          SNAP_ID=$(aws rds describe-db-snapshots \
            --db-instance-identifier acme-prod-db \
            --snapshot-type automated \
            --query 'reverse(sort_by(DBSnapshots,&SnapshotCreateTime))[0].DBSnapshotIdentifier' \
            --output text)
          echo "SNAP_ID=$SNAP_ID" >> $GITHUB_ENV

      - name: Restore snapshot into a throwaway instance
        run: |
          aws rds restore-db-instance-from-db-snapshot \
            --db-instance-identifier acme-restore-test-${{ github.run_id }} \
            --db-snapshot-identifier $SNAP_ID \
            --db-instance-class db.t3.medium \
            --no-multi-az # cheap single-AZ instance — this is a verification target, not prod

      - name: Wait for availability, then run verification query
        run: |
          aws rds wait db-instance-available --db-instance-identifier acme-restore-test-${{ github.run_id }}
          # verification script connects and confirms row counts / a known checksum
          ./scripts/verify_restore.sh acme-restore-test-${{ github.run_id }}

      - name: Tear down the throwaway instance
        if: always() # always clean up, even if verification failed, to avoid a cost leak
        run: |
          aws rds delete-db-instance \
            --db-instance-identifier acme-restore-test-${{ github.run_id }} \
            --skip-final-snapshot

Plain-English walkthrough

multi_az = true is the one-line difference between a database that survives an AZ failure in under a minute and one that requires a manual restore from backup during an outage — it's easy to miss in a code review because it looks like a minor boolean, but it's the single highest-leverage line in this entire file. manage_master_user_password = true hands credential generation and storage to RDS-integrated Secrets Manager instead of a Terraform variable, foreshadowing the dedicated secrets project. The restore test workflow is the part most teams skip: it doesn't just check that a snapshot exists, it actually restores one into a disposable instance, runs a real verification query against it, and tears it down — proving the recovery path works, on a schedule, well before an incident forces the team to find out the hard way.

06Failure Scenarios — What Breaks in Real Life

Failure: Multi-AZ failover surprises the application layer Failover changes the underlying instance's IP, and an application caching DNS resolutions aggressively keeps trying to reach the old (now-standby) address for longer than expected. Debug: confirm the application's DB connection pooling respects a reasonably short DNS TTL, and test a forced failover (aws rds reboot-db-instance --force-failover) outside of an actual incident to observe real application behavior.
Failure: parameter group change requires a reboot no one expected Some RDS parameters are "static" and only take effect after a reboot; a parameter group change applied via Terraform can silently queue a pending reboot that then happens unexpectedly during the next maintenance window. Debug: check apply_method on parameters in the group and use apply_immediately = false deliberately, scheduling any required reboot during a known low-traffic window instead of leaving it to chance.
Failure: restore test itself becomes a cost leak The teardown step in the restore-test pipeline fails silently (a bug, a permissions issue), and throwaway restore instances accumulate, quietly costing real money every week. Debug: the if: always() teardown step above is the mitigation, but pair it with the idle-resource cleanup module from Project 19 as a second line of defense that catches anything the pipeline itself misses.

07Interview Talking Points

"How do you know your database backups actually work?"
This is the single best question to demonstrate seniority on: describe the scheduled automated restore test specifically — restoring into a throwaway instance and running a real verification query — and contrast it explicitly with teams that only "know" backups work because a dashboard says a snapshot completed.
"Walk me through RDS Multi-AZ vs. read replicas — when would you use each?"
Multi-AZ is for availability (a synchronous, non-queryable standby for failover); read replicas are for read scaling (asynchronous, queryable copies). They solve different problems and are often used together, not as alternatives to each other.
