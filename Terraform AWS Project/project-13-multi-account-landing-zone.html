Multi-Account AWS Landing Zone with Terraform

Intermediate-Advanced · Organizations, Service Control Policies, and self-service account vending.

AWS Organizations SCPs Account Vending OU Structure Control Tower Concepts

01The Enterprise Problem This Solves

Every project so far in this handbook has assumed a single AWS account. Real enterprises don't run this way past a certain size — one account per environment, or one per team, or one per major workload, is standard practice specifically because it makes blast radius (a compromised credential, a runaway cost, an IAM mistake) contained by default at the account boundary, not just by IAM policy within a shared account. This project builds a landing zone: an AWS Organizations hierarchy of Organizational Units, Service Control Policies enforcing account-wide guardrails no IAM policy inside the account can override, and a self-service, Terraform- driven account vending process so new accounts start compliant on day one instead of being manually configured and drifting from standard.

02The Story: The New Account That Skipped Every Guardrail

Production Incident Replay A new team needs an AWS account for a short-lived proof of concept. Under time pressure, someone with Organization-level access creates the account by hand through the console, grants it broad admin access to move fast, and — meaning to circle back later — never applies the org's standard baseline: no mandatory CloudTrail logging, no restriction on leaving the AWS Organization, no region restriction, no default deny on disabling GuardDuty. The proof of concept quietly becomes a real, load-bearing internal tool over the following year, still running on that hand-built account, still missing every baseline control every other account in the org has. It's only discovered during an org-wide security audit — a full year later — that this one account has been operating completely outside every guardrail the rest of the organization takes for granted, because it was never vended through the standard process to begin with. The fix isn't a stricter audit cadence; it's making the compliant path the only path — Terraform-driven account vending that applies the SCP baseline and required logging as a non-optional part of account creation itself, so a "quick" account is never possible to create outside the guardrails.

03Deep Technical Explanation

Organizational Units as the unit of policy, not individual accounts

AWS Organizations lets accounts be grouped into a hierarchy of Organizational Units (OUs) — Service Control Policies attach to an OU (or the whole org root) and apply to every account nested under it automatically. Structuring OUs by risk/purpose (Security, Production, NonProduction, Sandbox) means a new account's guardrails are determined the moment it's placed into an OU, not configured account-by-account afterward.

Service Control Policies: a ceiling on the whole account, not just one role

An SCP is conceptually similar to Project 4's permission boundary, but scoped to an entire AWS account (or OU) rather than one IAM role — even the account's own root user cannot exceed what an SCP allows. A deny-based SCP attached at the OU level (e.g., "deny leaving the organization," "deny disabling GuardDuty," "deny regions outside us-east-1/us-west-2") is unconditional for every principal in every account under that OU, closing exactly the kind of gap in this project's story where an admin-privileged account had no org-enforced baseline at all.

Account vending as a Terraform-managed, self-service workflow

Rather than an engineer manually creating accounts through the console, aws_organizations_account lets Terraform provision new member accounts directly, immediately placed into the correct OU (inheriting its SCPs from the moment the account exists) and immediately bootstrapped with baseline resources — a CloudTrail trail, GuardDuty enablement, and a cross-account admin role for the platform team — via an account factory module consuming a simple request (team name, OU, environment type) as input.

05Step-by-Step Implementation

landing-zone/organization.tf 
resource "aws_organizations_organization" "main" {
  aws_service_access_principals = [
    "cloudtrail.amazonaws.com",
    "guardduty.amazonaws.com",
  ]
  feature_set = "ALL" # required for SCPs to be usable at all — CONSOLIDATED_BILLING alone can't enforce them
}

resource "aws_organizations_organizational_unit" "production" {
  name      = "Production"
  parent_id = aws_organizations_organization.main.roots[0].id
}

resource "aws_organizations_organizational_unit" "sandbox" {
  name      = "Sandbox"
  parent_id = aws_organizations_organization.main.roots[0].id
}
landing-zone/scps.tf 
data "aws_iam_policy_document" "deny_leave_org" {
  statement {
    effect    = "Deny"
    actions   = ["organizations:LeaveOrganization"]
    resources = ["*"]
  }
}

data "aws_iam_policy_document" "deny_disable_security_services" {
  statement {
    effect  = "Deny"
    actions = [
      "cloudtrail:StopLogging",
      "cloudtrail:DeleteTrail",
      "guardduty:DeleteDetector",
      "guardduty:DisassociateFromMasterAccount",
    ]
    resources = ["*"]
  }
}

data "aws_iam_policy_document" "deny_regions_outside_approved" {
  statement {
    effect    = "Deny"
    not_actions = ["iam:*", "organizations:*", "sts:*", "support:*"] # global services excluded from the region restriction
    resources = ["*"]
    condition {
      test     = "StringNotEquals"
      variable = "aws:RequestedRegion"
      values   = ["us-east-1", "us-west-2"]
    }
  }
}

resource "aws_organizations_policy" "baseline" {
  name = "org-baseline-guardrails"
  type = "SERVICE_CONTROL_POLICY"
  content = data.aws_iam_policy_document.deny_leave_org.json # in practice, statements are combined into one document — simplified here for clarity
}

resource "aws_organizations_policy_attachment" "baseline_to_root" {
  policy_id = aws_organizations_policy.baseline.id
  target_id = aws_organizations_organization.main.roots[0].id # attached at ROOT — applies to every OU and every account, no exceptions
}

5.2 — Account vending module

modules/account-factory/main.tf 
resource "aws_organizations_account" "this" {
  name  = "acme-${var.team_name}-${var.environment}"
  email = "aws-${var.team_name}-${var.environment}@acme.com" # must be a unique, real, monitored mailbox — root recovery depends on it
  parent_id = var.ou_id # account is placed directly into its OU at creation — SCPs apply immediately

  role_name = "OrganizationAccountAccessRole" # the cross-account role the platform team assumes into new accounts

  lifecycle {
    prevent_destroy = true # an account is never something "terraform destroy" should be able to remove casually
  }
}

# Baseline bootstrapped into the new account the moment it exists —
# assumes the cross-account role Terraform just gained via role_name above.
provider "aws" {
  alias = "new_account"
  assume_role {
    role_arn = "arn:aws:iam::${aws_organizations_account.this.id}:role/OrganizationAccountAccessRole"
  }
}

resource "aws_cloudtrail" "baseline" {
  provider                    = aws.new_account
  name                        = "org-baseline-trail"
  s3_bucket_name              = var.central_log_bucket # ships logs to the Security OU's central log archive account
  is_multi_region_trail       = true
  enable_log_file_validation  = true
}

resource "aws_guardduty_detector" "baseline" {
  provider = aws.new_account
  enable   = true
}

Plain-English walkthrough

Attaching the baseline SCP at the root of the organization, rather than to individual OUs one at a time, is the detail that closes the exact gap in this project's story — no account, including one created in a rush for a "quick" proof of concept, can ever exist outside these guardrails, because attachment happens at the top of the hierarchy every account descends from. The account factory module's use of a provider alias with assume_role is the mechanism that lets a single Terraform apply both create a new AWS account and immediately configure resources inside it — CloudTrail and GuardDuty are live in the new account before any human ever logs into it, closing the year-long gap where a hand-built account went unmonitored. The prevent_destroy lifecycle rule mirrors Project 1's state-bucket protection: an AWS account, like a state bucket, should never be something a routine terraform destroy can remove without a very deliberate, separate decision.

06Failure Scenarios — What Breaks in Real Life

Failure: an overly broad SCP accidentally blocks a legitimate workload The region-restriction SCP is written without excluding a global service the team didn't anticipate, and a legitimate API call starts failing account-wide with an opaque "explicit deny" error that doesn't say which SCP caused it. Debug: use IAM's policy simulator or CloudTrail's errorCode: AccessDenied events with the eventSource detail to identify which SCP statement fired, and always test new SCPs against a Sandbox OU account before attaching them to Production.
Failure: account vending module partially fails, leaving an account with no baseline Account creation succeeds, but the CloudTrail/GuardDuty bootstrap step fails due to a transient API error — the account now exists, is placed in the correct OU (so SCPs do apply), but is missing its baseline logging. Debug: make the account factory module idempotent and safely re-appliable, and add a scheduled compliance check (extending Project 9's policy-as-code pattern) that verifies every account in the org actually has CloudTrail and GuardDuty enabled, independent of whether vending succeeded cleanly.
Failure: cross-account role trust is too broad The OrganizationAccountAccessRole pattern is powerful by design (it's how the management account administers every member account), which also makes it a high-value target — if the management account's own credentials are compromised, every member account is reachable through this role. Debug: this is exactly why the management account itself needs the strictest access controls and MFA enforcement in the entire organization, and why cross-account CI/CD roles (Project 14) should use narrower, purpose-specific roles instead of this broad account-access role wherever possible.

07Interview Talking Points

"How would you design a multi-account AWS strategy for a growing organization?"
Describe the OU-by-purpose structure, SCPs attached at the level that guarantees coverage (root for universal guardrails, specific OUs for environment-specific ones), and Terraform-driven account vending so every account starts compliant — tied to a concrete story about what happens when that vending process is skipped.
"What's the difference between an SCP and an IAM permission boundary?"
SCPs cap an entire account (or OU) including its root user and apply org-wide; permission boundaries (Project 4) cap an individual IAM role or user within one account. They're structurally similar ceiling mechanisms operating at different scopes.
