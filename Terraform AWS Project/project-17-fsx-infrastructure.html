FSx Infrastructure — SMB File Shares for a Legacy Windows Estate

The recent merger brought a legacy .NET reporting application that expects a native Windows SMB file share with Active Directory-based permissions — something no amount of clever EFS access-point design (Project 16) can provide, because it simply isn't the right protocol for this workload.

01 The Banking Story

ABC Bank's recent acquisition of a smaller regional lender came with a legacy .NET reporting application that generates daily branch performance reports. It expects a Windows SMB file share, with folder permissions tied directly to specific Active Directory security groups — a completely different access model from the Linux/NFS world every project in this series has built so far.

The acquired company's IT team, before departing, left behind a single Windows file server running on an EC2 instance with local disk storage, no redundancy, and no backup schedule anyone can find documentation for. It has been "working" for three months on borrowed time.

Our manager's brief: "Give this application a proper, managed, highly available SMB file share, integrated with a real Active Directory, with automated backups. This is legacy, but it still processes real branch financial data — it doesn't get a lower security bar just because the application itself is old."

02 Business Requirement, Risk & Impact

Business Requirement

The legacy reporting application needs a highly available, backed-up SMB file share with folder-level permissions enforced through Active Directory security groups.

Customer Requirement

Branch managers accessing generated reports need permissions matching their existing AD group membership, with no separate access system to manage.

Current Infrastructure

A single, unmonitored EC2 instance running Windows File Server with local disk, no redundancy, and no confirmed backup process.

Existing Manual Process

None documented — the acquired team's original setup and operational knowledge left with them; the current server is effectively a black box the new team inherited.

Problems With Current Process

  • Single point of failure — no redundancy at the instance or storage level
  • Unverified or nonexistent backups for data supporting daily financial reporting
  • No integration with ABC Bank's own identity and access patterns from Project 05

Business Challenges

Financial reporting data, even from a legacy system, is subject to the same retention and availability expectations as the bank's own core systems — "it's old" isn't an accepted exception in a regulatory review.

Risk Analysis

High: a single-instance, unbackedup file server holding financial reporting data is a severe single point of failure with an unknown, and possibly zero, actual recovery capability today.

Business Impact

Loss of this server without a working backup could mean permanent loss of historical branch performance data, with no way to reconstruct it.

03 Why FSx for Windows File Server, and What We Rejected

Why FSx for Windows File Server

FSx for Windows File Server is a fully managed native Windows file system with genuine SMB protocol support, Active Directory integration for folder-level permissions, Multi-AZ deployment for automatic failover, and automated daily backups — solving every gap in the inherited setup as managed AWS capability rather than infrastructure the team has to operate themselves.

04 Terraform Concepts You Must Understand Before We Build

Reinforcing Sensitive Variables — the AD Admin Password

What it is: the AWS Managed Microsoft AD directory requires an administrator password at creation — generated via the same random_password resource from Project 06, immediately stored in Secrets Manager, and referenced as a sensitive = true variable so it never appears in plan/apply output.

Why this reinforces, not just repeats, Project 06: here the sensitive value is consumed by a DIFFERENT resource type (a Directory Service directory) at creation time, showing the same secret-handling discipline applies consistently across every AWS service that needs a credential, not just RDS.

Reinforcing Data Sources — Referencing an Existing Directory

What it is: if ABC Bank's Active Directory already exists (created by a different team or an earlier project not shown here), FSx references it via data "aws_directory_service_directory" rather than creating a brand new, second, unrelated directory — the same "read, don't recreate" principle from Project 08's VPC endpoint import, applied to a different resource type.

Reinforcing Conditional Expressions — Single-AZ vs. Multi-AZ Deployment Type

What it is: a lower environment (UAT) may use the cheaper Single-AZ FSx deployment type, while Production requires Multi-AZ — expressed with the same var.environment == "production" ? "MULTI_AZ_1" : "SINGLE_AZ_2" conditional pattern used throughout this series.

05 AWS Concepts: FSx for Windows & AWS Managed Microsoft AD

What is FSx for Windows File Server

A fully managed native Windows file system offering the SMB protocol and NTFS permissions, backed by AWS-managed redundant storage — a drop-in replacement for a self-managed Windows File Server instance, without the operational burden.

What is AWS Managed Microsoft AD

A genuine, AWS-hosted Microsoft Active Directory domain — not a compatibility layer — that FSx, and other AWS services, can join and use directly for authentication and permission enforcement.

Multi-AZ Deployment Type

Runs an active and standby file server across two AZs with automatic, transparent failover — directly resolving the single point of failure in the inherited setup.

Automated Backups

FSx takes automatic daily backups within a defined window and retains them for a configurable period — resolving the "no confirmed backup process" gap in the current infrastructure entirely as a managed feature.

Security

Folder-level NTFS permissions are enforced through AD group membership exactly as the legacy application expects — ABC Bank's own AD structure (or a dedicated OU within it) governs exactly who can read which branch's reports.

Limitations

FSx for Windows requires an Active Directory to join (AWS Managed AD, Simple AD, or a self-managed/on-prem AD reachable via the Transit Gateway from Project 03) — it cannot operate as a purely standalone file share the way EFS can.

07 Complete Solution Design

A random_password resource generates the AD administrator password once, immediately stored via the Project 06 Secrets Manager pattern. An aws_directory_service_directory of type MicrosoftAD is created (or referenced via data source if one already exists elsewhere in the estate), followed by an aws_fsx_windows_file_system joined to that directory, using Multi-AZ deployment in Production and a conditional expression to allow Single-AZ in lower environments.

Automated backups are configured with a defined daily window and 30-day retention. A Route53 CNAME (reusing Project 09's private zone pattern) gives the file share a stable internal name, decoupled from the FSx-generated DNS name, so a future migration or rebuild doesn't require reconfiguring every client.

11 Execution Flow, Explained Internally

terraform apply — directory creation

Provisioning a Microsoft AD directory takes considerably longer than most resources in this series (often 20-45 minutes) — Terraform waits for AWS to report the directory as Active before considering the resource successfully created.

terraform apply — FSx creation

The file system's active_directory_id reference means Terraform automatically waits for the directory to exist first — no explicit depends_on needed, since the reference itself establishes the dependency.

terraform apply — DNS record

Created last, once the file system's own generated DNS name is available as an output to reference in the CNAME record's records argument.

Changing deployment_type on an existing FSx file system is not an in-place update — it typically requires creating a new file system and migrating data, similar in spirit to the RDS Multi-AZ considerations from earlier projects. Plan this as a deliberate migration, not a routine variable change.

12 CI/CD Integration

.github/workflows/terraform-fsx.yml
name: terraform-fsx
on:
  push:
    branches: [main]
    paths: ["environments/prod/fsx-*.tf"]

jobs:
  apply:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve
        timeout-minutes: 60                                              # AD directory creation is slow — a default pipeline timeout would fail this step prematurely
Always set a generous pipeline timeout for any workflow touching Directory Service resources — a default 10-15 minute CI/CD timeout will likely fail before AD provisioning genuinely completes, even though the underlying apply would have succeeded given more time.

14 Interview Preparation

Q: Why does this legacy application need FSx instead of EFS from Project 16?
The application depends on native SMB protocol and NTFS/AD-based folder permissions — EFS is an NFS-based service designed for Linux/POSIX workloads and cannot serve this requirement; FSx for Windows is purpose-built for exactly this SMB/AD use case.
Q: What's the difference between AWS Managed Microsoft AD and Simple AD?
Managed Microsoft AD is a genuine, full-featured Microsoft Active Directory domain supporting trust relationships and advanced AD features; Simple AD is a lighter-weight, Samba-based compatible directory with a smaller feature set — the choice depends on what the consuming application actually requires.
Q: Why use a Route53 CNAME instead of giving clients the FSx-generated DNS name directly?
It decouples client configuration from the specific file system's identity — a future FSx rebuild or migration only requires updating one DNS record, rather than reconfiguring every client that connects to the share.
Q: How does this project apply the same secret-handling discipline as Project 06, despite being a different AWS service?
The AD administrator password is generated via random_password, immediately stored in Secrets Manager, and passed as a sensitive variable — the same pattern regardless of which specific resource (RDS then, Directory Service now) ultimately consumes the credential.
Manager round: How would you justify the cost of Multi-AZ FSx to a business stakeholder focused on cost?
Point directly to the current single point of failure and undocumented backup situation — the cost of Multi-AZ is small relative to the cost of losing branch financial reporting data entirely, which is the realistic alternative outcome the current setup risks.
