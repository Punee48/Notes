PROJECT 15 OF 40 · ADVANCED

ALB + NLB Enterprise Design — Static IPs Without Losing Layer 7

A new partner bank integration needs to allowlist ABC Bank's outbound IP addresses on their firewall — but an ALB's IP addresses aren't static, they can change at any time. Today we layer a Network Load Balancer in front of the existing ALB, giving partners fixed IPs to allowlist while keeping every path-based routing rule the ALB already provides.

01 The Banking Story

ABC Bank is integrating with a partner bank's settlement network for real-time payment confirmations. The partner's security team has one hard requirement, non-negotiable on their side: they will only accept inbound connections from a small, fixed allowlist of IP addresses — standard practice in interbank connectivity, but incompatible with how an Application Load Balancer works. An ALB's IP addresses are dynamic, drawn from a managed pool, and can change without notice; there is no way to give the partner a stable IP to allowlist directly from an ALB.

At the same time, the team doesn't want to give up path-based routing, host-based routing, and the other Layer 7 features the ALB already provides for the rest of the platform's HTTP traffic — ripping all of that out just to get static IPs would be trading one problem for a worse one.

Our manager's brief: "Put a Network Load Balancer in front of the existing ALB, with Elastic IPs the partner bank can allowlist once and never worry about again. Everything the ALB already does for routing stays exactly as it is."

02 Business Requirement, Risk & Impact

Business Requirement

The partner bank integration needs a small set of static, allowlist-able IP addresses, without sacrificing the ALB's existing Layer 7 routing capabilities for other traffic.

Customer Requirement

The partner's security team needs the IP list once, upfront, with a firm commitment it won't change without advance notice.

Current Infrastructure

A single ALB serving all HTTP(S) traffic to payments-api and related services, with dynamic, AWS-managed IP addresses.

Existing Manual Process

None — this is a new integration requirement the current architecture has no way to satisfy directly.

Problems With Current Process

  • ALB IPs are not static — no way to give the partner bank a stable allowlist target
  • A workaround of using a public NAT-based static IP scheme would route all traffic through a single choke point unnecessarily
  • Any solution must not disrupt the existing ALB-based routing for every other consumer of the platform

Business Challenges

Interbank settlement connectivity is often governed by a formal service agreement specifying exact network parameters — failing to provide a stable IP allowlist could delay or block the integration entirely.

Risk Analysis

Low-Medium: primarily a delivery/integration risk (the partnership can't go live without this) rather than a security risk — though the NLB's own security group and health checks still need the same rigor as everything else in this series.

Business Impact

Without a working static-IP solution, the settlement network integration — a committed business initiative with external dependencies and deadlines — cannot proceed to go-live.

03 Why NLB-in-Front-of-ALB, and What We Rejected

Why layer an NLB in front of the existing ALB

An NLB can have Elastic IPs assigned directly, per Availability Zone, and forwards traffic to a target group of type ip pointing at the ALB's own private IP addresses — giving the partner static IPs to allowlist while every existing ALB routing rule, listener, and target group continues working completely unchanged behind it.

04 Terraform Concepts You Must Understand Before We Build

Reinforcing Data Sources — Resolving the ALB's Private IPs Dynamically

What it is: the NLB's target group needs the ALB's actual private IP addresses as targets — since an ALB doesn't expose these as a simple resource attribute, we use data "aws_network_interface" filtered by the ALB's known ENI description pattern to resolve them.

Why it matters here specifically: ALB IPs can change over time (the exact reason this whole project exists) — resolving them via a data source at plan time, rather than hardcoding them once, means a future apply naturally picks up any change rather than silently pointing at stale IPs.

Reinforcing for_each — One Elastic IP and Target Group Attachment per AZ

What it is: the NLB needs one Elastic IP per Availability Zone it operates in, and one target group attachment per resolved ALB IP — both built with for_each over the VPC framework's AZ list from Project 02, keeping the pattern consistent with how this series has handled multi-AZ resources throughout.

Reinforcing Outputs for Cross-Team Communication

What it is: the whole point of this project's outputs is external — the resolved Elastic IP addresses need to be handed to the partner bank's integration team, not just used internally by other Terraform code, making clear, well-labeled outputs unusually important here.

05 AWS Concepts: Layering an NLB in Front of an ALB

Why NLB Supports Static IPs and ALB Doesn't

An NLB operates at Layer 4 and can have an Elastic IP directly assigned per AZ; an ALB operates at Layer 7 and is only ever addressable through its dynamic, AWS-managed DNS name and underlying IP pool.

Target Type "ip" for Non-EC2 Targets

An NLB target group normally targets EC2 instances by ID, but setting target_type = "ip" lets it target arbitrary IP addresses instead — including another load balancer's own private IPs, which is exactly this project's pattern.

Preserving Client IP

The NLB's target group can be configured to preserve the original client's source IP all the way through to the ALB and beyond — important for the partner's traffic to be correctly logged and identified at the application layer, not seen as coming from the NLB itself.

High Availability

One Elastic IP per AZ, matched to an NLB subnet mapping in that same AZ, ensures the static IP scheme doesn't become a single-AZ bottleneck — multi-AZ redundancy is preserved exactly as it is everywhere else in this series.

Security

The NLB itself has no security group (Network Load Balancers don't support them directly) — access control here happens at the target's security group (the ALB's own) and, ideally, a WAF or additional filtering layer for defense in depth.

Limitations

Because the NLB targets the ALB's IPs directly rather than through DNS, if those IPs change outside of a Terraform-managed update (which can happen), the data source must be re-resolved and target group attachments reapplied — this coupling is the main operational trade-off of this pattern.

07 Complete Solution Design

An aws_lb of type network is created in the same public subnets as the existing ALB, with one Elastic IP allocated per AZ via for_each, mapped in the NLB's own subnet_mapping blocks. A target group of target_type = "ip" and protocol TCP on port 443 is populated with the ALB's private IPs, resolved via data "aws_network_interface" filtered by the ALB's ENI description — re-resolved on every plan, so the target group stays accurate even as the ALB's underlying IPs change over time.

The output block presents the resolved Elastic IPs clearly, ready to be handed directly to the partner bank's integration team as the addresses to allowlist.

11 Execution Flow, Explained Internally

terraform apply — initial creation

Creates the Elastic IPs and NLB first, then resolves the ALB's current ENI IPs via the data source, then creates the target group attachments pointing at those specific resolved addresses.

terraform plan — after an ALB IP change

Because the data source re-resolves on every plan, an ALB IP change (from AWS's own management, e.g. after a scaling event) shows up as a target group attachment needing replacement — visible and reviewable in the plan, not a silent, undetected drift.

terraform apply — reattaching after drift

Removes the stale target group attachment and creates a new one pointing at the current IP — the partner-facing Elastic IPs themselves never change during this process, only the internal routing to the ALB.

The Elastic IPs handed to the partner bank are the stable part of this design — never destroy and recreate the aws_eip resources casually, since doing so changes the actual addresses the partner has allowlisted, requiring a coordinated change on their end too.

12 CI/CD Integration

.github/workflows/terraform-partner-nlb.yml
name: terraform-partner-nlb
on:
  pull_request:
    paths: ["environments/prod/partner-nlb.tf"]

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - name: Plan and flag any Elastic IP change
        run: |
          terraform plan -out=tfplan
          terraform show -json tfplan | jq -e '
            [.resource_changes[] | select(.type=="aws_eip") | select(.change.actions != ["no-op"])] | length == 0
          ' || echo "::warning::This plan would change the partner-facing Elastic IPs — coordinate with the partner bank before applying"
Flag, don't necessarily block, an Elastic IP change in CI/CD — sometimes it's genuinely intended (e.g. deliberate IP rotation), but it should never merge silently without someone consciously acknowledging the external coordination it requires.

14 Interview Preparation

Q: Why can't an ALB have a static Elastic IP directly, and how does an NLB solve that?
An ALB is a Layer 7, DNS-addressed service drawing from a dynamic, AWS-managed IP pool with no direct Elastic IP support; an NLB operates at Layer 4 and supports assigning an Elastic IP per AZ directly, so layering an NLB in front provides the static IP the ALB itself cannot.
Q: Why does the NLB's target group use target_type "ip" instead of "instance"?
The targets here are the ALB's own private IP addresses, not registered EC2 instances — target_type "ip" is required whenever the targets aren't EC2 instances the target group can reference by instance ID.
Q: What happens if the ALB's underlying IPs change, and how does this design handle it?
The data source resolving those IPs re-evaluates on every plan, so a change shows up as a reviewable target group attachment update in the next apply — the partner-facing Elastic IPs themselves remain completely unaffected by this internal change.
Q: Why health-check the ALB's actual application endpoint rather than just a TCP connection?
A TCP-only check would report healthy as long as the port responds, even if the ALB's listener is misconfigured or the backend service behind it is down — an application-level health check verifies the entire chain end to end.
Manager round: The partner bank asks why you can't just give them the ALB's IP addresses directly. How do you explain it?
ALB IP addresses are drawn from a dynamic, AWS-managed pool and can change without notice — providing them for a firewall allowlist would risk the partner's connectivity breaking unpredictably; the NLB layer gives a genuinely stable address specifically designed for this kind of external commitment.
