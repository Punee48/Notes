PROJECT 16 OF 40 · ADVANCED

Enterprise EFS Architecture — Shared Storage, Isolated by Design

A new document-processing workload needs every instance in the fleet to read and write the same files, at the same time — something no EBS volume can do. Today we build shared file storage that scales elastically and stays multi-tenant-safe, so three different services sharing one file system can never see each other's files.

01 The Banking Story

The compliance team's new document-processing pipeline scans uploaded loan documents across a fleet of worker instances — any worker might pick up any document, and several workers may need to read the same reference dataset simultaneously. An EBS volume (used everywhere else in this series) can only attach to one instance at a time, making it fundamentally the wrong tool here; the team's stopgap has been syncing files through S3 with a polling script, which is slow and occasionally leaves workers processing a half-uploaded file.

Looking ahead, two more teams — the statements-generation service and a new fraud-analytics batch job — have asked to share the same underlying file system for their own, unrelated document sets, to save on storage costs and operational overhead. That raises an immediate concern: nothing should let the fraud-analytics job accidentally read loan documents, or vice versa, even though they'd technically share the same EFS file system.

Our manager's brief: "Build proper shared storage — POSIX-compliant, mountable by many instances at once, encrypted at rest. And make sure that even though multiple teams will share one file system for cost reasons, each team is structurally confined to their own slice of it."

02 Business Requirement, Risk & Impact

Business Requirement

Multiple instances across multiple AZs must be able to read and write the same files concurrently, with encryption at rest and strict isolation between different teams' data sharing the same underlying file system.

Customer Requirement

The compliance team needs reliable, immediately-consistent file visibility across all workers — no polling delay, no risk of a worker reading a partially written file.

Current Infrastructure

An S3-based polling workaround for the compliance pipeline; no shared file storage solution exists yet for the other two teams' upcoming needs.

Existing Manual Process

A cron-scheduled script polls S3 for new objects and copies them locally to each worker — slow, occasionally inconsistent, and entirely custom-built rather than using a purpose-built shared storage service.

Problems With Current Process

  • S3 polling introduces delay and potential partial-file read races that a true shared file system doesn't have
  • No existing pattern for safely sharing one storage resource across multiple, mutually distrusting teams
  • Custom polling scripts are additional undocumented infrastructure the team has to maintain themselves

Business Challenges

Loan and fraud-analytics data both carry regulatory sensitivity — a shared storage design that doesn't structurally prevent cross-team access would itself become a compliance finding.

Risk Analysis

Medium: the risk isn't in EFS itself but in getting the multi-tenant isolation design wrong — a misconfigured access point could expose one team's documents to another's workers.

Business Impact

Slow, unreliable document availability directly delays loan processing turnaround times — a customer-facing metric the business actively tracks.

03 Why EFS, and What We Rejected

Why Amazon EFS

EFS is a fully managed, POSIX-compliant, elastic file system natively mountable by many instances across multiple AZs simultaneously — solving the concurrent-access requirement no EBS volume can meet, without the custom polling infrastructure the team has been maintaining as a workaround.

04 Terraform Concepts You Must Understand Before We Build

Reinforcing for_each — Mount Targets per AZ

What it is: an EFS file system needs one mount target per AZ it should be reachable from — built with for_each over Project 02's private subnet map, exactly the same multi-AZ resource pattern used for NAT Gateways and VPC endpoints throughout this series.

Reinforcing Complex Variables — Access Points per Team

What it is: a structured map variable defines each team's access point — its POSIX UID/GID and its confined root directory path — and a single for_each-driven aws_efs_access_point resource creates all of them, so onboarding a fourth team sharing this file system later is a one-line variable addition.

Why this matters for isolation specifically: each access point enforces its own root directory as that mount's effective root — a worker mounting via the fraud-analytics access point can never see or navigate to the compliance team's directory, even though both live on the same underlying EFS file system, because the access point makes the rest of the file system invisible to that mount entirely, not just access-denied.

Reinforcing Lifecycle & Encryption Patterns from Earlier Projects

What it is: the file system's own KMS encryption configuration follows the same dedicated-key-per-purpose pattern established in Project 04 (logging) and Project 06 (secrets) — a distinct key specifically for this shared file system, not a reused key from an unrelated purpose.

05 AWS Concepts: EFS, Mount Targets & Access Points

What is Amazon EFS

A managed NFS file system that scales storage capacity automatically and can be mounted concurrently by many EC2 instances (or other compute) across multiple AZs, with standard POSIX file permissions.

What is a Mount Target

An ENI, one per AZ, that gives instances in that AZ a local IP address to mount the file system through — required in every AZ any consuming instance runs in.

What is an EFS Access Point

An application-specific entry point into an EFS file system that enforces a specific POSIX user/group identity and a fixed root directory — the mount effectively cannot "see" anything outside that directory, providing real isolation, not just a permissions convention.

Why Access Points, Not Just Directory Permissions

Standard Unix directory permissions rely on every client correctly enforcing them — an access point makes the restriction structural at the AWS API level, so even a misconfigured or compromised worker instance mounting via the wrong access point simply cannot reach another team's directory.

Storage Classes & Lifecycle Management

EFS Lifecycle Management automatically moves files not accessed for a defined period (e.g. 30 days) to Infrequent Access storage, reducing cost for the (likely common) case of documents that are frequently read shortly after upload, then rarely touched again.

Security

Encryption at rest via a dedicated KMS key, combined with a security group restricting NFS (port 2049) access to only the fleet's own security groups — the same security-group-chaining pattern from Project 14.

Performance

EFS's "Elastic" throughput mode scales automatically with workload, removing the need to pre-provision throughput — a good default unless a workload has unusually predictable, sustained high-throughput needs.

07 Complete Solution Design

One aws_efs_file_system is created with encryption enabled via a dedicated KMS key and Lifecycle Management transitioning files to Infrequent Access after 30 days of no access. Mount targets are created via for_each across every private subnet from Project 02's VPC framework, with a security group permitting NFS only from the application fleet's own security groups (Project 14's chaining pattern).

A structured map variable defines each team's access point — POSIX UID/GID and confined root path — and a single for_each-driven resource creates one aws_efs_access_point per team. Each team's instances mount the file system using their own access point ID specifically, never the raw file system ID directly, which is what makes the isolation structural rather than convention-based.

11 Execution Flow, Explained Internally

terraform apply — file system and mount targets

Creates the KMS key and file system first, then one mount target per AZ in parallel (no dependency between different AZs' mount targets), then the security group and access points.

terraform apply — adding a fourth team

Adding one entry to the team_access_points map and reapplying shows exactly one new aws_efs_access_point resource in the plan — nothing about the existing three teams' access points is touched.

terraform destroy considerations

Mount targets must be destroyed before the file system itself — Terraform's dependency graph handles this ordering automatically, but any instance still actively mounted via NFS at destroy time will experience a hard failure, not a graceful unmount.

Never grant a worker instance's IAM role or security group access to more than one team's mount path "just in case" — the whole point of this design is that each fleet's blast radius is structurally confined to its own directory, and that guarantee only holds if access truly is one-team-per-access-point in practice, not just in the Terraform code.

  plan:
    runs-on: ubuntu-latest

      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform plan -out=tfplan
      - name: Flag any change to an access point's root_directory
        run: |                                                          # A changed root path is high-impact — it changes what a team's existing mounts can see
          terraform show -json tfplan | jq -e '
            [.resource_changes[] | select(.type=="aws_efs_access_point") |
             select(.change.actions != ["no-op"])] | length == 0
          ' || echo "::warning::This plan changes an EFS access point — verify isolation boundaries are still correct before merging"

14 Interview Preparation

Q: Why can't an EBS volume solve the concurrent multi-instance access requirement in this story?
EBS volumes attach to only one instance at a time (with a narrow multi-attach exception for specific instance types and use cases) — EFS is a genuinely shared, POSIX-compliant network file system designed for many concurrent readers and writers across multiple AZs.
Q: How do EFS Access Points provide real isolation, not just a permissions convention?
An access point confines a mount to a specific root subtree — anything outside that path is structurally invisible to that mount, not merely access-denied, so even a misconfigured client can't accidentally browse into another team's directory.
Q: Why give each team a separate access point instead of one shared mount with directory permissions?
Directory permissions rely on every client correctly enforcing them at the OS level; access points enforce the boundary at the AWS API level regardless of client behavior, which is a stronger and more auditable isolation guarantee for regulated data.
Q: What's the purpose of creation_info on an access point's root_directory block?
It defines the owner UID/GID and permissions applied WHEN the directory is first created by the access point — it has no effect on a directory that already exists, so it's specifically a bootstrap-time setting.
Manager round: Three teams want to share infrastructure to save cost — how do you evaluate whether that's safe?
Identify whether the underlying service offers a structural (not just conventional) isolation mechanism — as EFS Access Points do here — and only proceed with shared infrastructure when that mechanism exists; otherwise, the cost savings aren't worth the isolation risk, and separate resources are the safer choice.
