Zero Downtime Deployment — Instance Refresh, Draining & Launch Template Versioning

Not every service has migrated to ECS. The batch-processing fleet and a handful of legacy EC2-based services still deploy the old way: replace the launch template, then hope the Auto Scaling Group figures out the rest. Today we make that hope unnecessary — a managed, health-check-gated, connection-draining instance refresh.

01 The Banking Story

The nightly settlement batch service runs on a plain EC2 Auto Scaling Group — no ECS, no CodeDeploy from Project 12, just a launch template and an ASG. Deployments today mean updating the launch template's AMI, then manually terminating instances one at a time and watching the ASG replace them — a process an engineer described as "mostly fine, except for the one time it wasn't," referring to an incident where two instances were terminated too close together and in-flight settlement jobs on both were lost mid-processing.

Separately, connections to this service aren't drained cleanly on termination — an in-flight HTTP request to an instance being terminated sometimes gets a hard connection reset instead of finishing normally, something the batch service's client teams have quietly been retrying around rather than reporting as a bug.

Our manager's brief: "Give this fleet the same zero-downtime guarantee the containerized services get, using AWS's native Auto Scaling capabilities. No more manually babysitting instance termination, and no more silently-tolerated connection resets."

02 Business Requirement, Risk & Impact

Business Requirement

EC2/ASG-based services must be deployable with zero dropped connections and no risk of terminating more capacity than the service can safely lose at once.

Customer Requirement

Downstream teams calling this service need in-flight requests to complete normally during a deployment, not receive connection resets.

Current Infrastructure

An Auto Scaling Group with a launch template, updated manually, with instances terminated by hand one at a time by an engineer watching closely.

Existing Manual Process

Update the launch template's AMI reference, then manually terminate instances individually, waiting for the ASG to replace each one before terminating the next.

Problems With Current Process

  • Entirely dependent on an engineer's careful pacing — the exact incident from our story happened when that pacing broke down
  • No connection draining — in-flight requests can be abruptly reset instead of completing
  • No defined minimum healthy capacity enforced during the rollout — a mistake could terminate too much capacity simultaneously

Business Challenges

Settlement processing has strict completion guarantees — a job interrupted mid-processing due to infrastructure, not application logic, is a data-integrity concern the bank takes seriously.

Risk Analysis

Medium: the risk is bounded (batch jobs can generally be retried) but real — the incident in our story is exactly the kind of infrastructure-caused failure a properly managed rollout mechanism prevents structurally.

Business Impact

Interrupted settlement jobs require manual reconciliation and delay downstream processing — a direct operational cost every time it happens.

AWS Auto Scaling's Instance Refresh feature natively replaces instances in a controlled, health-check-gated way — respecting a minimum healthy percentage throughout, pausing on health check failures, and integrating with target group connection draining automatically. It requires no custom orchestration code, unlike the manual, engineer-paced process today.

04 Terraform Concepts You Must Understand Before We Build

Lifecycle — create_before_destroy

What it is: a lifecycle meta-argument that reverses Terraform's default replacement order — instead of destroying the old resource before creating its replacement, Terraform creates the new one first, then destroys the old one only once the new one exists successfully.

Why it exists here: the launch template must always have a new version created before anything references it — and applied to the Auto Scaling Group's launch_template block, create_before_destroy ensures a launch template replacement (rare, but possible on certain attribute changes) never leaves the ASG briefly pointing at nothing.

Production example: lifecycle { create_before_destroy = true } on the aws_launch_template resource — combined with name_prefix instead of a fixed name, since two resources can't share the same exact name even briefly during the overlap window this setting creates.

Common mistake: setting create_before_destroy = true but keeping a fixed name argument — Terraform will fail during the brief overlap window because AWS won't allow two resources with the identical name to exist simultaneously, even momentarily.

Launch Template Versioning — $Latest vs. Pinned Version

What it is: every update to a launch template's settings creates a new numbered version rather than overwriting the existing one — the Auto Scaling Group references either a specific version number, or the special value $Latest to always track the newest.

Why it matters here: using $Latest means updating the launch template alone is enough to define "what a deployment changes to" — the Instance Refresh, triggered separately, is what actually rolls that new version out to running instances gradually.

Reinforcing terraform_data for Refresh Triggering

What it is: Terraform has no native resource representing "start an instance refresh now" — like Project 12's revision tracking, we use terraform_data with triggers_replace keyed to the launch template's version, giving CI/CD a clean signal to call the Instance Refresh API when the tracked value changes.

05 AWS Concepts: Instance Refresh & Connection Draining

What is ASG Instance Refresh

A managed rollout that replaces instances in an Auto Scaling Group in controlled batches, respecting a minimum healthy percentage and pausing automatically if new instances fail health checks.

Why it exists

It removes the exact human-pacing dependency from our story — the ASG itself enforces that enough healthy capacity always remains, rather than relying on an engineer terminating instances at a safe pace by hand.

Minimum Healthy Percentage

A setting (e.g. 90%) defining the lowest percentage of the desired capacity that must remain healthy throughout the refresh — the ASG will not proceed to replace more instances if doing so would drop below this threshold.

Connection Draining (Deregistration Delay)

A target group setting that gives an instance being removed a grace period to finish in-flight requests before it's fully deregistered — directly solves the connection-reset problem from our story.

Warm Pools (Related, Complementary Feature)

Pre-initializes a pool of stopped instances ready to be quickly started during scale-out or refresh, reducing the time new capacity takes to become healthy — worth considering for services with slow boot/warm-up times, though not required for this specific fleet's needs.

High Availability

Instance Refresh respects the ASG's existing multi-AZ distribution — it doesn't refresh all instances in one AZ simultaneously by default, preserving the redundancy Project 02's VPC framework was built to provide.

Limitations

Instance Refresh only manages instance replacement — it doesn't itself validate application-level health beyond what the ASG's configured health check (EC2 or ELB) reports; a deeper canary-style metric check, as in Project 12, isn't part of this mechanism.

07 Complete Solution Design

The launch template uses name_prefix and create_before_destroy, so any change that requires template replacement (rare, but possible for certain immutable attributes) never leaves a gap. The Auto Scaling Group references $Latest and defines an instance_refresh block with a minimum healthy percentage of 90% and a checkpoint delay, so deployments proceed in controlled, health-verified batches rather than all at once or entirely by hand.

The target group's deregistration_delay is set to give in-flight requests time to complete before an instance is fully removed from rotation — directly resolving the connection-reset issue. A terraform_data resource, keyed to the launch template's version, gives CI/CD a clean, reviewable signal for when to call the Instance Refresh start API.

09 Implementation — Full Production Code

environments/prod/settlement-asg.tf

environments/prod/settlement-asg.tf
resource "aws_launch_template" "settlement" {
  name_prefix   = "settlement-batch-"                                   # name_prefix, NOT name — required to coexist briefly under create_before_destroy
  image_id      = data.aws_ssm_parameter.latest_al2023_ami.value        # Same always-current AMI pattern from Project 07
  instance_type = "r6g.xlarge"

  iam_instance_profile {
    name = aws_iam_instance_profile.settlement.name
  }

  lifecycle {
    create_before_destroy = true                                        # New template version exists before any replacement of this resource is even considered
  }
}

resource "aws_lb_target_group" "settlement" {
  name     = "settlement-batch-tg"
  port     = 8080
  protocol = "HTTP"
  vpc_id   = var.vpc_id

  deregistration_delay = 60                                              # Gives in-flight requests 60 seconds to complete before the instance is fully removed — THIS fixes the connection-reset problem

  health_check {
    path                = "/healthz"
    healthy_threshold   = 2
    unhealthy_threshold = 3
    interval            = 15
  }
}

resource "aws_autoscaling_group" "settlement" {
  name                = "settlement-batch-asg"
  vpc_zone_identifier = var.private_subnet_ids
  target_group_arns   = [aws_lb_target_group.settlement.arn]
  min_size            = 4
  max_size            = 10
  desired_capacity    = 4
  health_check_type          = "ELB"                                     # Uses target group health, not just EC2 status — catches application-level failures, not just instance-level ones
  health_check_grace_period  = 120

  launch_template {
    id      = aws_launch_template.settlement.id
    version = "$Latest"                                                  # Always tracks the newest launch template version — the version created by create_before_destroy above
  }

  instance_refresh {                                                      # The core zero-downtime mechanism this project exists to build
    strategy = "Rolling"

    preferences {
      min_healthy_percentage = 90                                         # Never lets healthy capacity drop below 90% of desired — directly prevents the "too much terminated at once" incident from our story
      instance_warmup        = 180                                         # Seconds to wait after an instance reports healthy before counting it toward the healthy percentage — accounts for app warm-up time
      checkpoint_delay        = 600                                        # Pauses this long between checkpoint percentages, giving time to observe each batch before continuing
      checkpoint_percentages   = [25, 50, 75, 100]                          # Explicit stopping points — the refresh pauses at each for review rather than running straight through
    }

    triggers = ["launch_template"]                                         # Automatically starts a NEW refresh whenever the launch template itself changes — no separate manual trigger needed
  }

  tag {
    key                 = "Name"
    value               = "settlement-batch"
    propagate_at_launch = true
  }
}

11 Execution Flow, Explained Internally

terraform apply — launch template change

create_before_destroy ensures a new template version is created before Terraform considers replacing the resource; because version = "$Latest", the ASG immediately recognizes the new version exists.

Automatic Instance Refresh trigger

Because triggers = ["launch_template"] is set, AWS itself starts a new Instance Refresh the moment it detects the launch template's latest version changed — this happens as a side effect of the apply, not a separate Terraform action.

Rollout batches

AWS replaces instances in batches sized to respect min_healthy_percentage, waits for each replaced instance to pass its target-group health check plus the instance_warmup period, and pauses at each configured checkpoint percentage.

A refresh that stalls at a checkpoint because new instances are failing health checks will NOT automatically roll back on its own — unlike Project 12's alarm-driven CodeDeploy rollback, Instance Refresh pauses and waits for manual intervention (cancel, or fix and retry) rather than reverting automatically.

12 CI/CD Integration

.github/workflows/settlement-deploy.yml
name: settlement-deploy
on:
  push:
    branches: [main]
    paths: ["services/settlement-batch/**"]

jobs:
  deploy:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: environments/prod } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve   # New AMI/launch template version applied — the instance_refresh trigger takes it from here automatically
      - name: Monitor the automatic Instance Refresh
        run: |
          REFRESH_ID=$(aws autoscaling describe-instance-refreshes \
            --auto-scaling-group-name settlement-batch-asg \
            --query "InstanceRefreshes[0].InstanceRefreshId" --output text)
          aws autoscaling wait instance-refresh-successful \
            --auto-scaling-group-name settlement-batch-asg \
            --instance-refresh-ids "$REFRESH_ID"                          # Pipeline waits for and reports the refresh's actual outcome, not just that apply succeeded
Always have the pipeline explicitly wait for and check the Instance Refresh's outcome, not just terraform apply's success — the apply only queues the change; the refresh itself, running asynchronously in AWS, is what determines whether the deployment actually succeeded.

14 Interview Preparation

Q: How does ASG Instance Refresh prevent the kind of incident described in this project's story?
min_healthy_percentage structurally enforces that a defined floor of capacity always remains healthy during the rollout — the ASG itself refuses to proceed if doing so would breach that floor, removing the dependency on an engineer's manual pacing.
Q: Why is create_before_destroy needed on the launch template, and what else does it require?
It ensures a replacement template version exists before the old one is even considered for removal, avoiding any gap; it requires name_prefix instead of a fixed name, since AWS won't allow two resources with an identical name to briefly coexist.
Q: Does Instance Refresh automatically roll back on failure?
No — it pauses at a failing checkpoint and waits for manual intervention; this differs from Project 12's CodeDeploy canary, which has native alarm-driven automatic rollback built in.
Q: What does deregistration_delay actually do, and why does it matter for a batch/API service?
It gives an instance being removed from a target group a grace period to finish in-flight requests before full deregistration — without it, requests in progress at the moment of termination can be abruptly reset instead of completing normally.
Manager round: When would you choose Instance Refresh over migrating a service to ECS with CodeDeploy canary?
Instance Refresh is the right immediate fix for existing EC2/ASG-based services needing safe rollouts now, without requiring a broader platform migration; ECS with CodeDeploy is preferable for services already on or moving to containers, given its native metric-driven automatic rollback that Instance Refresh doesn't provide.
