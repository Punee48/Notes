Policy-as-Code Guardrails with OPA (Cost Controls, Tagging Enforcement, Security Rules)

Intermediate-Advanced · Rules that block a bad apply automatically, so they don't depend on a human catching it in review.

OPA / Rego Conftest Policy as Code Cost Guardrails Tagging Enforcement

01The Enterprise Problem This Solves

Project 8's pipeline gets a human to look at a plan before it applies — but human review doesn't scale, misses things at the end of a long day, and can't be relied on as the only defense against an expensive or dangerous change. This project adds a second, automated layer: policy-as-code checks that evaluate every Terraform plan against machine-enforced rules — required tags, denied public S3 buckets, allowed instance types for cost control — and fail the pipeline automatically if a plan violates them, no human judgment call required in the moment.

02The Story: The $40,000 Instance Type Typo

Production Incident Replay An engineer testing a new workload accidentally writes instance_type = "p4d.24xlarge" instead of the intended t3.24xlarge — a one-character difference between a general-purpose instance and an 8-GPU machine-learning instance costing roughly 30 times as much per hour. The PR's plan output shows the change correctly, but it's buried in a 200-line diff during a busy sprint, and the reviewer approves it without clocking the instance type. The mistake runs in a scaling group with a minimum size of 3 for four days before a finance review catches the anomaly. The fix the team implements afterward isn't "review more carefully" — humans will always occasionally miss things in a large diff — it's an automated policy check that hard-fails any plan proposing an instance type outside an explicitly approved allowlist, so this exact class of mistake can never reach apply regardless of how thorough that day's reviewer happened to be.

03Deep Technical Explanation

Policy-as-code as a second, independent gate — not a replacement for review

Policy-as-code doesn't replace human review from Project 8; it adds a gate that can't get tired, distracted, or skip a line in a long diff. The two are complementary: humans judge intent and architecture ("does this change make sense"), automated policy judges hard rules ("is this change ever allowed, no matter who approved it").

Open Policy Agent (OPA) and Rego, evaluated against Terraform's plan JSON

Terraform can export a plan as structured JSON (terraform show -json tfplan), which Open Policy Agent, via the conftest CLI, evaluates against policies written in Rego, a purpose-built query language for expressing "is this data structure allowed." A policy is a set of rules that either pass or produce a deny message; conftest exits non-zero if any rule denies, which is what fails the CI job.

Why this runs against plan JSON, not raw HCL

Evaluating raw HCL would require re-implementing Terraform's own variable resolution, module expansion, and provider defaults inside the policy engine. Evaluating the plan JSON instead means policies see exactly what Terraform itself resolved every value to — the actual instance type after variables and defaults are applied, not the raw (and possibly parameterized) HCL expression.

Sentinel as the alternative, for teams on Terraform Cloud/Enterprise

HashiCorp's own Sentinel serves the identical purpose as OPA/Rego but is tightly integrated with Terraform Cloud/Enterprise's native run pipeline, evaluating plans automatically as part of every run without a separate CI step. This project builds the OPA/conftest pattern because it works with plain open-source Terraform and GitHub Actions from Project 8 without requiring Terraform Cloud — the concepts (deny rules against plan JSON) transfer directly if a team later adopts Sentinel.

04Architecture

Project 8's PR plan job, extended with one more step: terraform plan -out=tfplan │ ▼ terraform show -json tfplan > plan.json │ ▼ conftest test plan.json --policy policies/ │ ├─► policies/tagging.rego (deny: missing required tags) ├─► policies/cost-controls.rego (deny: disallowed instance types) └─► policies/security.rego (deny: public S3, open security groups) │ ▼ any DENY → CI job fails → PR cannot merge, regardless of human approval all pass → proceeds to the PR comment + human review step from Project 8

05Step-by-Step Implementation

policies/tagging.rego 
package terraform.tagging

# required tags every taggable resource must carry — this list is the
# single source of truth for the org's tagging standard.
required_tags := {"Environment", "ManagedBy", "Project"}

# iterate every resource_changes entry in the plan JSON whose action
# includes "create" or "update" (we don't need to re-check deletes).
deny[msg] {
  some resource in input.resource_changes
  resource.type == "aws_instance"
  contains(resource.change.actions, "create")

  tags := resource.change.after.tags
  missing := required_tags - {key | tags[key]}  # set difference: required minus present = missing
  count(missing) > 0

  msg := sprintf("resource %v is missing required tags: %v", [resource.address, missing])
}
policies/cost-controls.rego 
package terraform.cost

# Allowlist of instance types permitted without an explicit exception —
# this is exactly the guardrail that would have caught the story above.
allowed_instance_types := {
  "t3.micro", "t3.small", "t3.medium", "t3.large",
  "r6g.large", "r6g.xlarge",
}

deny[msg] {
  some resource in input.resource_changes
  resource.type == "aws_instance"
  contains(resource.change.actions, "create")

  it := resource.change.after.instance_type
  not allowed_instance_types[it] # Rego's "not" on a set membership check — true if NOT in the set

  msg := sprintf("resource %v requests disallowed instance_type %q — get a cost exception approved first", [resource.address, it])
}
policies/security.rego 
package terraform.security

# Deny any S3 bucket ACL resource that grants public read/write —
# a second, automated layer behind Project 2's data-tier routing controls.
deny[msg] {
  some resource in input.resource_changes
  resource.type == "aws_s3_bucket_public_access_block"
  contains(resource.change.actions, "create")

  after := resource.change.after
  after.block_public_acls == false

  msg := sprintf("resource %v does not block public ACLs — this requires a documented security exception", [resource.address])
}

5.1 — Wiring conftest into Project 8's plan job

.github/workflows/terraform-pr-plan.yml (added step) 
      - name: Export plan as JSON
        run: terraform show -json tfplan > plan.json

      - name: Install conftest
        run: |
          curl -L https://github.com/open-policy-agent/conftest/releases/download/v0.53.0/conftest_0.53.0_Linux_x86_64.tar.gz \
            | tar xz && sudo mv conftest /usr/local/bin

      - name: Run policy-as-code checks
        run: conftest test plan.json --policy ../../policies
        # non-zero exit on any deny[] rule firing — fails this CI job before
        # the plan is even posted for human review.

Plain-English walkthrough

Each Rego file targets one policy family and iterates input.resource_changes — the array of every resource change in the plan JSON — filtering to just the resource type and action it cares about. The deny[msg] pattern is Rego's idiom for a rule that produces a violation message whenever its body evaluates true; conftest collects every fired deny across every policy file and fails the run if there's at least one. Placing this step immediately after terraform plan and before the PR-comment step from Project 8 means a policy violation blocks the pipeline before a reviewer ever sees it — the cost-control policy specifically encodes the instance-type allowlist that would have caught this project's story automatically, independent of whether a human reviewer noticed the typo in a long diff.

06Failure Scenarios — What Breaks in Real Life

Failure: a legitimate exception gets hard-blocked with no path forward A team genuinely needs a GPU instance type for an ML workload, and the cost-control policy blocks it outright with no way to proceed short of editing the policy file itself. Debug: build an explicit exception mechanism — e.g., a resource tag like CostException = "APPROVED-JIRA-1234" that the policy checks for and allows through, so exceptions are auditable and approved, not achieved by disabling the check.
Failure: policy references a plan JSON field that changed between provider versions An AWS provider upgrade restructures part of the plan JSON schema, and a policy that worked yesterday silently stops matching anything (not failing loudly — just never triggering), giving false confidence that nothing's violating it. Debug: maintain policy unit tests (conftest supports this) with fixture plan JSON files covering both a passing and a violating case, run in CI whenever the provider version changes.
Failure: policy checks slow down every PR meaningfully As the policy set grows, conftest evaluation time creeps up, and engineers start feeling the CI pipeline as a drag rather than a safety net. Debug: profile and prune policies regularly, and prefer fewer, well-targeted rules (like the three above) over an ever-growing pile of speculative checks nobody's confirmed are still relevant.
