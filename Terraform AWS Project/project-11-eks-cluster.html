Private EKS Cluster Provisioning with Terraform

Intermediate-Advanced · Node groups, IRSA, and add-ons — the platform-engineering block begins here.

EKS Managed Node Groups IRSA OIDC Provider EKS Add-ons Private API Endpoint

01The Enterprise Problem This Solves

Beyond a certain scale, teams need more workload flexibility than a fixed Auto Scaling Group of EC2 instances (Project 6) provides — many small services, different resource shapes, faster deploy cycles. This project provisions a private, production-grade EKS cluster: no public API endpoint reachable from the internet, managed node groups instead of hand-rolled EC2 workers, and IRSA (IAM Roles for Service Accounts) so individual Kubernetes workloads get scoped AWS permissions — continuing Project 4's least-privilege pattern straight into the cluster, instead of every pod sharing one broad node-level IAM role.

02The Story: The Pod That Could Read Every Secret in the Account

Production Incident Replay A team migrates a service to EKS and, to get things working quickly under a deadline, attaches a broad IAM policy directly to the EC2 node role — the IAM identity shared by every pod scheduled onto that node, regardless of which team or service owns it. It works. Six weeks later, a completely unrelated internal tool gets deployed onto the same node pool, and someone notices — during a routine security review, thankfully, not an incident — that this unrelated tool's pods have full read access to every S3 bucket and Secrets Manager secret the original team's service needed, because IAM permissions in EKS without IRSA are scoped to the node, not the pod. Every workload sharing that node inherited every permission any workload on that node had ever needed. The fix is IRSA: instead of attaching permissions to the node, attach them to a Kubernetes service account via a trust relationship with the cluster's own OIDC provider, so each workload's pod only gets the AWS permissions explicitly granted to its own service account — the multi-tenant equivalent of Project 4's least-privilege IAM roles, applied at the pod level instead of the node level.

03Deep Technical Explanation

Why the API endpoint is private

An EKS cluster's Kubernetes API server can be exposed publicly, privately, or both. A private-only endpoint means kubectl and any cluster-admin API calls are only reachable from inside the VPC (or via VPN/bastion), eliminating an entire class of exposure — brute-forcing or exploiting the Kubernetes API from the open internet simply isn't possible if the API server was never reachable from there in the first place.

Managed Node Groups vs. self-managed nodes vs. Fargate

Managed Node Groups let AWS handle node provisioning, lifecycle, and graceful draining during updates, while still running on EC2 instances Terraform controls the sizing and networking of — the pragmatic middle ground between fully self-managed EC2 worker nodes (maximum control, maximum operational burden) and Fargate (zero node management, but less control over instance-level configuration and typically higher per-pod cost at scale).

IRSA: pod-level AWS permissions via OIDC federation

Every EKS cluster can expose its own OIDC identity provider. IRSA works by creating an IAM role whose trust policy trusts that specific cluster's OIDC provider, scoped further to one namespace and one Kubernetes service account name via a condition key — nearly identical in spirit to Project 4's OIDC-federated CI role, but the trusted identity provider is the cluster itself instead of GitHub Actions. A pod using that service account automatically receives temporary AWS credentials scoped to exactly that IAM role's permissions — nothing shared with any other workload on the same node.

EKS add-ons as Terraform-managed, not manually installed

Core cluster add-ons (VPC CNI, CoreDNS, kube-proxy, EBS CSI driver) are managed as first-class AWS-managed resources via aws_eks_addon, version-pinned and upgraded through Terraform rather than kubectl apply'd by hand — keeping the cluster's core networking and storage layer under the same change-controlled, reviewed pipeline as everything else in this handbook.

05Step-by-Step Implementation

envs/prod/eks.tf 
resource "aws_eks_cluster" "main" {
  name     = "acme-prod"
  role_arn = aws_iam_role.eks_cluster.arn
  version  = "1.29"

  vpc_config {
    subnet_ids              = values(module.network.private_subnet_ids) # control plane ENIs live in the private tier
    endpoint_private_access  = true
    endpoint_public_access   = false # the core security decision in this project — no public API endpoint
  }

  encryption_config {
    resources = ["secrets"] # encrypts Kubernetes Secrets at rest with a customer-managed KMS key
    provider {
      key_arn = aws_kms_key.eks.arn
    }
  }
}

# --- OIDC provider: the trust anchor every IRSA role in this cluster relies on ---
data "tls_certificate" "eks_oidc" {
  url = aws_eks_cluster.main.identity[0].oidc[0].issuer
}

resource "aws_iam_openid_connect_provider" "eks" {
  url             = aws_eks_cluster.main.identity[0].oidc[0].issuer
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = [data.tls_certificate.eks_oidc.certificates[0].sha1_fingerprint]
}

resource "aws_eks_node_group" "app" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "app-nodes"
  node_role_arn   = aws_iam_role.eks_node.arn # intentionally minimal — no app-specific permissions live here (see IRSA below)
  subnet_ids      = values(module.network.private_subnet_ids)

  scaling_config {
    min_size     = 3
    max_size     = 10
    desired_size = 3
  }

  instance_types = ["m6g.large"]
  capacity_type  = "ON_DEMAND"
}

# --- Core add-ons, version-pinned and Terraform-managed ---
resource "aws_eks_addon" "vpc_cni" {
  cluster_name  = aws_eks_cluster.main.name
  addon_name    = "vpc-cni"
  addon_version = "v1.18.1-eksbuild.1" # pinned — upgraded deliberately, not silently by AWS
}

resource "aws_eks_addon" "ebs_csi" {
  cluster_name             = aws_eks_cluster.main.name
  addon_name               = "aws-ebs-csi-driver"
  addon_version            = "v1.31.0-eksbuild.1"
  service_account_role_arn = aws_iam_role.ebs_csi_irsa.arn # the CSI driver itself runs under IRSA, not the node role
}

5.2 — IRSA for a single application's service account

envs/prod/irsa-checkout.tf 
# --- Trust policy: only the checkout-sa service account in the
# "checkout" namespace on THIS cluster's OIDC provider can assume this role. ---
data "aws_iam_policy_document" "checkout_irsa_trust" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]
    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.eks.arn]
    }
    condition {
      test     = "StringEquals"
      variable = "${replace(aws_iam_openid_connect_provider.eks.url, "https://", "")}:sub"
      values   = ["system:serviceaccount:checkout:checkout-sa"] # namespace:service-account-name, exact match only
    }
  }
}

module "checkout_irsa_role" {
  source = "../../modules/iam-role" # the same reusable module from Project 4

  role_name              = "checkout-s3-irsa"
  trust_policy_json      = data.aws_iam_policy_document.checkout_irsa_trust.json
  permission_policy_json = data.aws_iam_policy_document.checkout_s3_access.json # scoped to checkout-* buckets only
  boundary_policy_arn    = aws_iam_policy.org_boundary.arn # same org-wide ceiling from Project 4
}

Plain-English walkthrough

endpoint_public_access = false is the single line that closes off the entire "brute-force the Kubernetes API from the internet" attack surface. The OIDC provider resource is what makes IRSA possible at all — without it, there is no trust anchor for any pod-scoped IAM role to federate against. The condition key in the IRSA trust policy is doing exactly the same job Project 4's CI role trust policy did with a GitHub repo/branch condition — narrowing "who can assume this role" down to one exact namespace-and-service-account pair, so the incident in this project's story (one workload inheriting another's node-wide permissions) becomes structurally impossible: tool-sa in the internal-tools namespace simply cannot satisfy the sub condition scoped to checkout:checkout-sa, no matter what node it happens to be scheduled on.

06Failure Scenarios — What Breaks in Real Life

Failure: private-only endpoint blocks CI from running kubectl/helm Switching to a private-only API endpoint breaks a CI pipeline that was reaching the cluster over the public internet. Debug: either run CI from a self-hosted runner inside the VPC, or add a temporary, tightly scoped VPN/bastion path — never re-enable public access as the fix.
Failure: a workload's IRSA role omitted from its pod spec falls back to the node role A deployment YAML forgets the serviceAccountName field, defaults to the namespace's default service account, and the pod ends up with no IRSA role at all — falling back to whatever the shared node role grants, silently reintroducing the exact over-permissioning this project exists to prevent. Debug: use an admission controller or OPA Gatekeeper policy (extending Project 9's approach into the cluster) to deny any pod that doesn't specify a non-default service account with an IRSA annotation.
Failure: EKS add-on version pin falls behind and blocks a Kubernetes version upgrade A cluster version upgrade is attempted, but a pinned add-on version isn't compatible with the new Kubernetes minor version, and the upgrade fails partway. Debug: check AWS's EKS add-on compatibility matrix for the target Kubernetes version before bumping version on aws_eks_cluster, and stage add-on version bumps ahead of the cluster version bump, not simultaneously.

07Interview Talking Points

"How do you scope AWS permissions for individual workloads running in a shared EKS cluster?"
Describe IRSA precisely: OIDC federation between the cluster and IAM, condition-scoped to an exact namespace and service account, so permissions live at the pod level instead of the shared node level — directly preventing one workload from inheriting another's access.
"Why would you run EKS with a private-only API endpoint, and what does that break?"
Give the security rationale plainly, and be ready to discuss the real operational tradeoff — CI/CD and developer tooling need a network path into the VPC (self-hosted runners, VPN, bastion) since public access is off the table.
