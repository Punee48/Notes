The Foundation

The Story: Why Does Kubernetes Even Exist?

Before a single command — understand the pain that built K8s

📖 Story Time — The Problem That Built Kubernetes

It's 2013. You work at a startup called ShopEasy. Your app is a monolith — one giant application handling everything: user login, product catalog, payments, notifications, all in one codebase. You deploy it on a single EC2 server.

On Black Friday, traffic goes 10x. Your single server crashes. Customers lose orders. The CEO panics. You scramble to spin up more EC2s manually — copying configs, installing Node.js, praying nothing breaks. By the time you're ready, the sale is over.

Then your team decides to break the monolith into microservices — small independent services each in their own container. Now you have 15 services. But who manages them? Where does each container run? What if one crashes? How do you connect them? How do you deploy new versions without downtime?

That is exactly the problem Kubernetes was born to solve. Google had been running billions of containers for years using an internal system called Borg. They open-sourced the concept in 2014 as Kubernetes — a system that automatically manages, scales, heals, and connects containers for you.

1.1 What is Kubernetes?

Kubernetes (K8s) is a Container Orchestration Platform. "Orchestration" means it conducts your containers like a conductor conducts an orchestra — making sure every instrument plays at the right time, replaces musicians who fall sick, and scales the music louder when needed.

🏥
Self-Healing

If a container crashes, Kubernetes automatically restarts it. No manual intervention. Your app stays alive 24/7.

Auto
📈
Auto Scaling

Traffic spike at 3 PM? K8s spins up more containers. Traffic drops at 3 AM? It removes them. You pay only for what you use.

HPA

Rolling updates — K8s gradually replaces old containers with new ones so users never see an outage during deployment.

Rolling
🔗
Service Discovery

Services find each other by name, not IP. No need to hardcode addresses. K8s has a built-in DNS that routes traffic intelligently.

1.2 What is Amazon EKS?

🤔 The EKS Insight

Kubernetes is powerful — but setting it up yourself is painful. You need to install and maintain the Control Plane (the "brain" of K8s), handle upgrades, backups, HA. That's a full-time job.

Amazon EKS (Elastic Kubernetes Service) solves this. AWS manages the Control Plane for you. You just bring the worker nodes (EC2s or Fargate). EKS integrates natively with IAM, VPC, ALB, ECR, CloudWatch — so you get the full AWS ecosystem out of the box.

ℹ️
EKS vs Self-Managed K8s

EKS: AWS manages the master nodes (API Server, etcd, Controller Manager, Scheduler). You manage worker nodes. Cost: ~$0.10/hr per cluster + EC2 cost.
Self-managed: You manage everything. Cheaper but painful for production.

1.4 Core Kubernetes Objects — Plain English

K8s Object Real-World Analogy What it Does
Pod 🏠 A house (with 1-2 containers inside) The smallest deployable unit. Runs one or more containers that share network + storage.
Deployment 🏗️ A housing project (manages houses) Declares how many Pods to run. Handles rolling updates and rollbacks.
ReplicaSet 🔢 "Keep exactly 3 houses open" Ensures the desired number of identical Pods are always running.
Service 📫 A post office for a neighborhood Gives Pods a stable network address. Routes traffic to healthy Pods.
Ingress 🚪 The main gate to the neighborhood Routes HTTP/HTTPS traffic from outside into services. Like a reverse proxy.
ConfigMap 📋 A notice board with app settings Stores non-sensitive config (URLs, feature flags). Injected into Pods as env vars.
Secret 🔐 A safe for passwords Like ConfigMap but for sensitive data (passwords, API keys). Base64 encoded.
Namespace 🏙️ Different cities in one country Logical isolation within a cluster. E.g. dev, staging, production namespaces.
Node 🏭 A physical factory building A worker machine (EC2) that runs Pods. Managed by the control plane.
PersistentVolume 💾 A USB drive for data Storage that survives Pod restarts. Backed by EBS, EFS in AWS.

2.2 Create Your First EKS Cluster

📖 What eksctl actually does

When you run eksctl create cluster, it talks to AWS CloudFormation behind the scenes and creates: a VPC, 3 public + 3 private subnets, the EKS Control Plane, IAM roles, Security Groups, and EC2 Auto Scaling Groups for worker nodes. All automated. What used to take days of manual setup takes 15 minutes.

  cluster-config.yaml
YAML · eksctl config 
# This is an eksctl ClusterConfig file
# It describes everything about our EKS cluster

apiVersion: eksctl.io/v1alpha5      # Which version of eksctl config spec
kind: ClusterConfig                # Type of this file = cluster definition

metadata:
  name: shopeasy-cluster            # Name of our EKS cluster
  region: ap-south-1               # AWS region = Mumbai (closest to India)
  version: "1.29"                  # Kubernetes version to use

managedNodeGroups:                   # Define worker node groups
  - name: ng-workers               # Name for this group of nodes
    instanceType: t3.medium        # EC2 type: 2 vCPU, 4GB RAM (good for dev)
    desiredCapacity: 2             # Start with 2 EC2 worker nodes
    minSize: 1                     # Minimum 1 node (saves cost when idle)
    maxSize: 5                     # Scale up to 5 nodes under heavy load
    volumeSize: 20                 # 20 GB EBS disk per node (stores images)
    ssh:
      allow: true                   # Allow SSH into nodes for debugging
    iam:
      withAddonPolicies:
        albIngress: true            # Node can create AWS Load Balancers
        autoScaler: true            # Node can trigger EC2 Auto Scaling
        ebs: true                   # Node can attach EBS volumes

addons:                              # EKS-managed plugins to install
  - name: aws-ebs-csi-driver        # Allows K8s to use EBS for persistent storage
  - name: vpc-cni                  # AWS VPC networking plugin for pods
  - name: coredns                  # DNS resolution inside cluster
  - name: kube-proxy               # Network rules on each node

2.3 Word-by-Word: cluster-config.yaml Explained

YAML Key Value Detailed Explanation
apiVersion eksctl.io/v1alpha5 Tells eksctl which version of config schema to use. Like saying "I'm writing this in Format v5". Always check docs for latest version.
kind ClusterConfig What type of object this YAML describes. ClusterConfig = an entire EKS cluster definition.
metadata.name shopeasy-cluster The unique name AWS will give your cluster. Appears in EKS console. Use kebab-case (hyphens, no spaces).
region ap-south-1 AWS region where cluster is created. ap-south-1 = Mumbai. Always pick closest region to your users for lower latency.
instanceType: t3.medium 2 vCPU / 4GB The EC2 machine type for worker nodes. t3.medium is cost-effective for dev. Production: m5.xlarge or c5.2xlarge.
desiredCapacity: 2 2 nodes Start with 2 EC2 worker nodes. K8s spreads your Pods across these nodes for redundancy.
minSize / maxSize 1 to 5 The Cluster Autoscaler uses these limits. Never scales below 1 (ensures uptime). Never above 5 (cost control).
albIngress: true boolean Attaches an IAM policy to nodes allowing them to create/manage AWS Application Load Balancers. Needed for Ingress to work.
aws-ebs-csi-driver addon Container Storage Interface driver for EBS. Without this, your Pods can't create persistent volumes (databases would lose data on restart).
coredns addon The DNS server inside your cluster. Allows services to find each other by name (e.g., backend-service.default.svc.cluster.local).

3.1 Understanding a Pod (Smallest Unit)

📖 Pod Story

Imagine you want to deploy your Node.js API. In the old world, you'd SSH into an EC2 and run node server.js. In Kubernetes, you wrap that process in a Pod. A Pod is the "home" for your container — it gives it a network address, CPU/memory limits, environment variables, and lifecycle management.

A Pod can have 1 container (most common) or multiple "sidecar" containers that work together — like a logger container sitting next to your API container.

  pod-basic.yaml
YAML · Pod 
apiVersion: v1              # "v1" = core K8s API (Pods, Services, ConfigMaps)
kind: Pod                   # We're defining a Pod object
metadata:
  name: backend-pod         # Unique name for this pod in the namespace
  labels:                   # Labels are KEY-VALUE tags, used for selection
    app: backend            # Label: app=backend (Services use this to find pods)
    version: v1             # Custom label for version tracking
spec:                       # "spec" = the desired state — what should exist
  containers:               # List of containers inside this pod
  - name: backend           # Container name (used in logs: kubectl logs pod/backend-pod -c backend)
    image: 123456.dkr.ecr.ap-south-1.amazonaws.com/shopeasy-backend:v1
                              # Docker image from ECR (AWS's private registry)
    ports:
    - containerPort: 3000   # Port our Node.js app listens on (documentation only)
    env:                    # Environment variables injected into the container
    - name: NODE_ENV        # Variable name (process.env.NODE_ENV in Node.js)
      value: "production"  # Variable value
    resources:              # Resource limits — CRITICAL for production!
      requests:             # Minimum resources K8s guarantees this container gets
        memory: "128Mi"    # 128 Mebibytes RAM guaranteed
        cpu: "250m"        # 250 millicores = 0.25 CPU core
      limits:               # Maximum resources — container killed if exceeded
        memory: "512Mi"    # Max 512MB RAM (OOMKilled if exceeded)
        cpu: "500m"        # Max 0.5 CPU core

3.2 Why Pods Alone are Not Enough → Enter Deployments

⚠️
Never Deploy Pods Directly in Production

If you create a Pod manually and it crashes, K8s does NOT restart it — it's gone forever. Pods are ephemeral. You always use a Deployment which ensures the desired number of Pods are always running, handles updates, and enables rollbacks.

  backend-deployment.yaml
YAML · Deployment 
apiVersion: apps/v1                 # "apps/v1" = API group for Deployments, StatefulSets
kind: Deployment                    # This file defines a Deployment object

metadata:
  name: backend-deployment          # Name of the Deployment resource
  namespace: production             # Which K8s namespace this belongs to
  labels:
    app: backend

spec:
  replicas: 3                       # Run 3 identical Pods at all times
  selector:                         # Tells the Deployment WHICH pods to manage
    matchLabels:
      app: backend                  # Match pods with label app=backend

  strategy:                         # How to update pods (how to do rolling deploys)
    type: RollingUpdate             # Replace pods gradually, not all at once
    rollingUpdate:
      maxSurge: 1                  # Allow 1 extra pod during update (4 pods briefly)
      maxUnavailable: 0            # ZERO downtime — always keep all 3 running

  template:                         # This is the POD TEMPLATE — blueprint for each pod
    metadata:
      labels:
        app: backend               # MUST match selector.matchLabels above
        version: v2
    spec:
      containers:
      - name: backend
        image: 123456789.dkr.ecr.ap-south-1.amazonaws.com/shopeasy-backend:v2
        imagePullPolicy: Always    # Always pull fresh image (not cached). Use IfNotPresent in dev.
        ports:
        - containerPort: 3000

        envFrom:                   # Load ALL keys from a ConfigMap as env vars
        - configMapRef:
            name: backend-config  # Reference the ConfigMap named backend-config
        - secretRef:
            name: backend-secrets # Reference the Secret named backend-secrets

        resources:
          requests:
            memory: "128Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "1000m"           # Max 1 full CPU core

        livenessProbe:             # K8s checks this to know if container is ALIVE
          httpGet:
            path: /health         # K8s calls GET /health on the container
            port: 3000
          initialDelaySeconds: 30 # Wait 30s before first check (app startup time)
          periodSeconds: 10       # Check every 10 seconds

        readinessProbe:            # K8s checks this before sending traffic to pod
          httpGet:
            path: /ready          # Only route traffic when /ready returns 200
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5

Services & Ingress — Exposing Your App to the World

4.1 The 4 Types of Kubernetes Services

🔒
ClusterIP

Default type. Service is only reachable INSIDE the cluster. Perfect for inter-service communication (backend → database). No external access.

Internal
🚪
NodePort

Opens a port (30000-32767) on EVERY node's IP. External clients can hit any node:port. Good for dev/testing, not production.

Dev Only
☁️
LoadBalancer

Creates an AWS Classic Load Balancer automatically. Each service gets its own LB. Expensive if you have 10+ services.

AWS CLB
🎯
Ingress (Best)

One AWS ALB for all services. Routes by path (/api → backend, / → frontend). Cost-effective. Supports SSL/TLS, authentication, rate limiting.

Production ✅
  backend-service.yaml
YAML · Service 
apiVersion: v1
kind: Service

metadata:
  name: backend-service         # Name used by other services to reach this one
  namespace: production

spec:
  type: ClusterIP               # Internal only — frontend will call this by name
  selector:                     # Routes traffic to pods matching these labels
    app: backend                # Finds all pods with label app=backend
  ports:
  - name: http
    port: 80                   # The port THIS service listens on
    targetPort: 3000           # The port on the POD to forward traffic to
    protocol: TCP
  ingress.yaml
YAML · Ingress + AWS ALB 
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: shopeasy-ingress
  namespace: production
  annotations:                            # Annotations = instructions to the ALB controller
    kubernetes.io/ingress.class: alb       # Use AWS ALB (not nginx)
    alb.ingress.kubernetes.io/scheme: internet-facing
        # "internet-facing" = public ALB. Use "internal" for private VPC traffic
    alb.ingress.kubernetes.io/target-type: ip
        # Route traffic directly to Pod IPs (not node IPs). More efficient.
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:123456:certificate/xxx
        # ACM SSL certificate for HTTPS (free from AWS Certificate Manager)
    alb.ingress.kubernetes.io/ssl-redirect: "443"
        # Redirect all HTTP → HTTPS automatically
    alb.ingress.kubernetes.io/healthcheck-path: /health
        # ALB checks this path to decide if pods are healthy

spec:
  rules:                               # Routing rules — which URL goes where
  - host: shopeasy.yourdomain.com      # Domain name (must point to ALB in Route53)
    http:
      paths:
      - path: /api                    # Requests to /api/* go to backend
        pathType: Prefix             # Prefix = match /api, /api/users, /api/products...
        backend:
          service:
            name: backend-service   # Send to backend-service
            port:
              number: 80
      - path: /                        # All other requests go to frontend
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80

YAML · ConfigMap

  API_PORT: "3000"
  DB_HOST: "postgres-service"       # Service name (K8s DNS resolves this)
  DB_PORT: "5432"
  ALLOWED_ORIGINS: "https://shopeasy.yourdomain.com"
  LOG_LEVEL: "info"
  backend-secret.yaml
YAML · Secret 
apiVersion: v1
kind: Secret                        # For sensitive data — base64 encoded
metadata:
  name: backend-secrets
  namespace: production
type: Opaque                        # "Opaque" = generic secret (vs tls, dockerconfigjson)
data:
    # Values MUST be base64 encoded: echo -n "mypassword" | base64
  DB_PASSWORD: bXlzZWNyZXRwYXNzd29yZA==   # base64("mysecretpassword")
  JWT_SECRET: c3VwZXJzZWNyZXRqd3Q=       # base64("supersecretjwt")
  AWS_ACCESS_KEY: QUtJQVhYWFhYWFhYWFg=   # base64("AKIAXXXXXXXXXX")
🔴
Production Best Practice — Use AWS Secrets Manager

Never store real secrets in YAML files or commit them to git. In production, use AWS Secrets Manager + External Secrets Operator to sync secrets from AWS into K8s Secrets automatically. Or use IRSA (IAM Roles for Service Accounts) to give pods direct AWS access without any keys.

6.1 Horizontal Pod Autoscaler (HPA)

📖 The HPA Story

It's 11:59 PM on New Year's Eve. ShopEasy is running 3 backend pods. At midnight, 50,000 users hit the site simultaneously. CPU shoots to 90%. Without HPA, the 3 pods choke and users see errors.

With HPA configured, Kubernetes sees CPU > 70%, automatically creates 10 more pods within 60 seconds, and the load is distributed. At 2 AM when traffic drops, it scales back to 3. You pay only for what you use.

  backend-hpa.yaml
YAML · HorizontalPodAutoscaler 
apiVersion: autoscaling/v2             # autoscaling/v2 supports multiple metrics
kind: HorizontalPodAutoscaler

metadata:
  name: backend-hpa
  namespace: production

spec:
  scaleTargetRef:                       # WHICH deployment to scale
    apiVersion: apps/v1
    kind: Deployment
    name: backend-deployment           # Our backend deployment

  minReplicas: 2                        # Never go below 2 pods (HA minimum)
  maxReplicas: 20                       # Never exceed 20 pods (cost control)

  metrics:                              # Metrics that trigger scaling
  - type: Resource
    resource:
      name: cpu                        # Scale based on CPU utilization
      target:
        type: Utilization
        averageUtilization: 70         # Scale up when avg CPU > 70%
                                        # Scale down when avg CPU < 70%
  - type: Resource
    resource:
      name: memory                     # Also scale on memory
      target:
        type: Utilization
        averageUtilization: 80         # Scale up when avg memory > 80%

  behavior:                            # Control HOW FAST scaling happens
    scaleUp:
      stabilizationWindowSeconds: 60  # Wait 60s before scaling up again (avoid flapping)
      policies:
      - type: Pods
        value: 4                       # Add max 4 pods at a time
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300 # Wait 5 minutes before scaling DOWN (be conservative)
      policies:
      - type: Pods
        value: 2                       # Remove max 2 pods at a time
        periodSeconds: 60

name: Deploy ShopEasy to EKS       # Workflow name shown in GitHub UI

on:                                 # When should this workflow run?
  push:
    branches:
    - main                          # Only trigger on push to main branch
  workflow_dispatch:               # Also allow manual trigger from GitHub UI

env:                               # Global environment variables
  AWS_REGION: ap-south-1
  ECR_REPOSITORY: shopeasy-backend
  EKS_CLUSTER: shopeasy-cluster
  NAMESPACE: production

jobs:                              # Jobs = parallel or sequential work units
  deploy:                          # Job name
    runs-on: ubuntu-latest         # Run on a fresh Ubuntu container (GitHub provides this)
    steps:                         # Steps = ordered tasks inside the job

    - name: Checkout code          # Step 1: Get our code from GitHub
      uses: actions/checkout@v3    # Official GitHub action to clone repo

    - name: Configure AWS credentials
      uses: aws-actions/configure-aws-credentials@v2
      with:
        aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
                # Reads from GitHub Secrets (Settings → Secrets) — never hardcoded
        aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
        aws-region: ${{ env.AWS_REGION }}

    - name: Login to Amazon ECR
      id: login-ecr                # Give this step an ID so later steps can reference its outputs
      uses: aws-actions/amazon-ecr-login@v1
            # Runs: aws ecr get-login-password | docker login

    - name: Build and Push Docker image
      env:
        ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }}
        IMAGE_TAG: ${{ github.sha }}    # Tag image with git commit hash (unique & traceable)
      run: |
                # Build Docker image
        docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG ./backend
                # Push to ECR
        docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
                # Save image URI for next steps
        echo "image=$ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" >> $GITHUB_OUTPUT

    - name: Update kubeconfig for EKS
      run: aws eks update-kubeconfig --region $AWS_REGION --name $EKS_CLUSTER
            # This adds EKS credentials to ~/.kube/config so kubectl works

    - name: Deploy to EKS
      env:
        IMAGE_TAG: ${{ github.sha }}
      run: |
                # Update the image in deployment (rolling update)
        kubectl set image deployment/backend-deployment \
          backend=$ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG \
          -n $NAMESPACE
                # Wait for rollout to complete (fail CI if deployment fails)
        kubectl rollout status deployment/backend-deployment -n $NAMESPACE --timeout=5m

Essential kubectl Cheat Sheet + What's Next

Your daily commands + advanced topics to master next

# List all pods in a namespace $ kubectl get pods -n production
# List with node info (-o wide) $ kubectl get pods -n production -o wide
# Delete a pod (Deployment will recreate it) $ kubectl delete pod <pod-name> -n production
# Stream logs $ kubectl logs -f <pod-name> -n production
# Port-forward to access pod locally $ kubectl port-forward pod/<pod-name> 8080:3000 -n production
# Apply any YAML file $ kubectl apply -f deployment.yaml
# View rollout history $ kubectl rollout history deployment/backend-deployment -n production
# Rollback to specific revision $ kubectl rollout undo deployment/backend-deployment --to-revision=2 -n production
# Pause a rolling update $ kubectl rollout pause deployment/backend-deployment -n production
# Get events in a namespace (first place to look when things break) $ kubectl get events -n production --sort-by=.metadata.creationTimestamp
# Describe pod (shows: image pull errors, OOMKilled, etc.) $ kubectl describe pod <pod-name> -n production
# Check resource usage across pods $ kubectl top pods -n production
# Check node resource usage $ kubectl top nodes
# List all namespaces $ kubectl get namespaces
# List all resources in a namespace $ kubectl get all -n production
# View current context (which cluster kubectl is connected to) $ kubectl config current-context
# Switch between clusters $ kubectl config use-context <context-name>
# Delete entire cluster (careful!) $ eksctl delete cluster --name shopeasy-cluster --region ap-south-1
