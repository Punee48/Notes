Process Monitoring

A legacy batch processor, started by hand with nohup years ago, crashed on a Saturday. It wasn't a systemd service, so nothing was watching it at all.

🎯 Level: Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL ⏱️ Duration: 3 hrs

📖 The Story — The Process Nobody Officially Owned

Years before this course began, an engineer started NovaTrust's overnight transaction-reconciliation batch processor by hand with nohup java -jar reconciler.jar &, meaning to "set it up properly with systemd later." It never happened. The process just kept running, quietly, for years — invisible to Project 1's systemctl-based service checks, because it was never a systemd service at all. One Saturday, it crashed on an unhandled exception. Nobody restarted it, because nothing was watching it. Two days of transactions queued up, undetected, until Monday morning.

Priya's assignment: "We have processes on our servers that aren't managed by systemd — legacy tools, one-off scripts, things nobody's gotten around to properly packaging. I want a generic way to watch any process, using a PID file, that detects if it's crashed, checks it hasn't turned into some zombie state, verifies it's running as the right user, and can safely restart it — but never in an infinite crash loop that just burns the server down trying."

This project builds a generic safety net for exactly the kind of process that falls through every other monitoring approach in this course.
🔁 Reinforced from Projects 1–20
The mandatory dry-run/safety-gate philosophy, state-file tracking (now for restart attempts), and Project 20's heartbeat-style file-based signaling all return here, applied to keeping a specific process alive.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Monitor critical processes that aren't managed by systemd, detect crashes and abnormal states, and safely auto-restart them without risking an uncontrolled crash loop.

Customer Requirement

Ops needs both automatic recovery from a simple crash and a hard stop before repeated restart attempts become their own separate problem.

Banking Scenario

NovaTrust runs several legacy, non-systemd-managed processes (like the overnight transaction reconciler) started manually with nohup, alongside its properly systemd-managed services.

Existing Manual Process / Prior Automation Gap

Project 1's health check covers systemd services specifically — any process outside that model has had zero automated monitoring coverage for its entire operational life.

Problems With the Current Gap

A crashed non-systemd process gives no automatic signal at all — no failed-service notification, no restart attempt, nothing — it simply stops silently and stays stopped indefinitely.

Business Impact & Risk

Two days of unprocessed transaction reconciliation directly delays financial reporting accuracy and downstream processes that depend on it being current.

Why Automation Is Required

Only a script actively checking process liveness on a schedule can catch and recover from a crash of a process with no other supervision mechanism at all.

Solution Design

Each monitored process writes its own PID to a file at startup; a checker script verifies the PID is alive, healthy (not a zombie), and correctly owned, restarts it on failure up to a capped attempt count, and escalates to alert-only once that cap is reached rather than restarting forever.

Project Scope

In scope: PID-file-based liveness checking, zombie detection, ownership verification, and capped safe auto-restart. Out of scope: converting these processes to proper systemd services — a valid longer-term fix, but a separate migration project, not this one.

Expected Outcome

A crashed non-systemd process is automatically detected and restarted within minutes for a genuine one-off crash, while a process that's repeatedly failing is instead flagged for human investigation rather than endlessly restarted.

🧠 New Bash Concepts for This Project

1. The PID File Pattern

What: A monitored process writes its own process ID to a known file at startup (e.g., echo $$ > /var/run/reconciler.pid), which a separate monitoring script later reads to know exactly which process to check.
Why: Without a PID file, finding "the reconciler process" reliably from the outside would require fragile process-name matching (as seen with Project 14's pgrep -f) — a PID file gives a monitoring script one authoritative, unambiguous reference.

2. Checking Process Liveness Without Killing It (kill -0)

What: kill -0 "$pid" sends signal 0 — a special no-op signal that performs all of kill's normal permission and existence checks, without actually sending any real signal or affecting the process at all.
Why: This is the standard, safe way to answer "is this specific PID currently a running process" from a script — its exit code alone tells us, with zero side effects on the target process.

3. Detecting Stale PID Files

What: A PID file can persist on disk after the process it named has crashed (if the process itself never cleaned it up) — kill -0 failing against a PID that's present in the file is exactly this "stale PID file" condition.
Why: Without this check, a monitoring script might wrongly assume "PID file exists, therefore process is running," missing the crash entirely.

4. Detecting Zombie (Defunct) Processes

What: ps -o stat= -p "$pid" returns a process's state code; a Z in that code means the process has terminated but its parent hasn't yet "reaped" its exit status — a zombie.
Why: A zombie process's PID technically still "exists" (so kill -0 succeeds), but it's not actually doing any work — a naive liveness check alone would incorrectly report a zombie process as healthy.

5. Verifying Process Ownership (ps -o user=)

What: ps -o user= -p "$pid" returns the username actually running a given process — comparing this against an expected owner catches a process that's somehow running as the wrong user (e.g., accidentally started as root).
Why: A critical process unexpectedly running with elevated (root) privileges is a security concern independent of whether it's otherwise "healthy" — this check catches a class of problem invisible to a pure liveness check.

6. Safe, Capped Auto-Restart with a Rolling Attempt Counter

What: A state file tracking restart attempts and timestamps within a rolling time window; once attempts within that window exceed a configured maximum, the script stops restarting and escalates instead.
Why: An uncapped auto-restart against a process that crashes instantly on every launch (a genuine, unfixed bug) would restart it dozens of times per minute, consuming resources and masking the real problem behind an endless cycle of brief "healthy" windows.

7. Starting a Detached Background Process from a Script (nohup, disown)

What: nohup "$start_command" > "$log_file" 2>&1 & disown launches a process that survives even if the launching script's own session ends — nohup ignores the hangup signal, and disown removes it from the shell's own job-control tracking.
Why: The restart action itself needs to launch a genuinely independent, persistent process — not one that would die the moment our monitoring script's own execution finishes.

8. Why This Uses Scheduled Checks, Not a Continuous Supervisor Daemon

What: This project deliberately checks via cron on an interval, rather than running a continuously-executing supervisor process (like systemd, supervisord, or a custom always-on watchdog loop).
Why: Consistent with this entire course's scheduled-check philosophy — and honestly, for processes this important, migrating them to genuine systemd management (with its far more sophisticated, continuous supervision) remains the better long-term fix; this project is an interim safety net, not a replacement for that migration.

9. Distinguishing "Flapping" from a Simple One-Off Crash (Reinforced Judgment)

What: One restart within a long window is a normal recovery; several restarts within a short window is "flapping" — a fundamentally different, more serious finding requiring human investigation rather than more automated restarts.
Why: The same distinction Project 17 drew between a single new container restart and a genuine crash-loop pattern, now applied to a manually-restarted process instead of Docker's own restart policy.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Process monitoring helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- is_process_alive ----------
# Purpose: Return 0 if a PID currently exists as a real process (no signal actually sent)
is_process_alive() {
    local pid="$1"
    kill -0 "$pid" 2>/dev/null
}

# ---------- is_zombie ----------
is_zombie() {
    local pid="$1"
    local state
    state=$(ps -o stat= -p "$pid" 2>/dev/null | tr -d ' ')
    [[ "$state" == Z* ]]                              # State codes can have extra flag characters after Z
}

# ---------- get_process_owner ----------
get_process_owner() {
    local pid="$1"
    ps -o user= -p "$pid" 2>/dev/null | tr -d ' '
}

# ---------- count_recent_restarts ----------
# Purpose: Count how many restart attempts a process has had within the rolling window
count_recent_restarts() {
    local process_name="$1"
    [[ -f "$STATE_FILE" ]] || { echo 0; return; }

    local cutoff_epoch
    cutoff_epoch=$(date -d "-${RESTART_WINDOW_MINUTES} minutes" '+%s')

    grep "^${process_name}:" "$STATE_FILE" | awk -F':' -v cutoff="$cutoff_epoch" '$2 >= cutoff' | wc -l
}

# ---------- record_restart_attempt ----------
record_restart_attempt() {
    local process_name="$1"
    mkdir -p "$(dirname "$STATE_FILE")"
    echo "${process_name}:$(date '+%s')" >> "$STATE_FILE"
}

# ---------- start_process ----------
start_process() {
    local start_command="$1"
    local log_target="$2"
    nohup "$start_command" > "$log_target" 2>&1 &
    disown
}

Line-by-Line Highlights

  • kill -0 "$pid" 2>/dev/null — signal 0 is specifically defined by POSIX as performing error-checking (does this PID exist, do we have permission to signal it) without delivering any actual signal to the process.
  • [[ "$state" == Z* ]] — a glob match (not exact equality) because ps's state column can show Z combined with additional flag characters (like Z+ for a foreground zombie); matching just the leading Z catches all zombie variants.
  • awk -F':' -v cutoff="$cutoff_epoch" '$2 >= cutoff' — passing a Bash variable into awk via -v (parallel to jq's --arg from Projects 18-19), filtering the state file's timestamped restart records to only those within the rolling window before counting them.
  • nohup "$start_command" > "$log_target" 2>&1 & disown — the full detachment sequence: nohup ignores hangup signals, the trailing & backgrounds it, and disown removes it from the current shell's job table so it's genuinely independent once our monitoring script itself exits.

🩺 Main Script

scripts/process_monitor.sh
#!/bin/bash
# =====================================================================
# process_monitor.sh
# NovaTrust Bank - PID-File Process Monitoring with Safe Capped Auto-Restart
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/process_monitor.conf"

STATE_FILE="$SCRIPT_DIR/$STATE_FILE"
REGISTRY_FILE="$SCRIPT_DIR/../config/process_registry.txt"
[[ -f "$REGISTRY_FILE" ]] || { echo "ERROR: Process registry not found: $REGISTRY_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/process_monitor_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Process monitor run finished."' EXIT

log_message "INFO" "=== Starting process monitor check ==="

OVERALL_EXIT=0

while IFS=':' read -r process_name pid_file expected_user start_command; do
    process_name=$(echo "$process_name" | xargs)      # Trim whitespace from the colon-delimited registry format
    pid_file=$(echo "$pid_file" | xargs)
    expected_user=$(echo "$expected_user" | xargs)
    start_command=$(echo "$start_command" | xargs)
    [[ -z "$process_name" || "$process_name" == \#* ]] && continue

    if [[ ! -f "$pid_file" ]]; then
        log_message "FAIL" "$process_name: no PID file found - process was never started, or crashed and cleaned up its own PID file"
        OVERALL_EXIT=2
        continue
    fi

    PID=$(cat "$pid_file")

    if is_process_alive "$PID" && ! is_zombie "$PID"; then
        OWNER=$(get_process_owner "$PID")
        if [[ "$OWNER" != "$expected_user" ]]; then
            log_message "WARN" "$process_name: running as unexpected user '$OWNER' (expected '$expected_user')"
            [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
        else
            log_message "PASS" "$process_name: healthy (PID $PID, user $OWNER)"
        fi
        continue
    fi

    # ---------- Process is gone or a zombie: attempt safe, capped restart ----------
    REASON="crashed (stale PID)"
    is_zombie "$PID" 2>/dev/null && REASON="zombie state"
    log_message "FAIL" "$process_name: $REASON (PID $PID)"

    RECENT_RESTARTS=$(count_recent_restarts "$process_name")
    if [[ "$RECENT_RESTARTS" -ge "$MAX_RESTARTS_PER_WINDOW" ]]; then
        log_message "FAIL" "$process_name: FLAPPING - already restarted $RECENT_RESTARTS time(s) in the last $RESTART_WINDOW_MINUTES min. NOT restarting again. Escalating for investigation."
        OVERALL_EXIT=2
        continue
    fi

    log_message "WARN" "$process_name: attempting restart ($((RECENT_RESTARTS + 1))/$MAX_RESTARTS_PER_WINDOW this window)"
    start_process "$start_command" "$SCRIPT_DIR/$LOG_DIR/${process_name}_restart_stdout.log"
    record_restart_attempt "$process_name"
    [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1

done < "$REGISTRY_FILE"

log_message "INFO" "=== Process monitor check complete ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
process_name=$(echo "$process_name" | xargs)xargs with no arguments is a common idiom for trimming leading/trailing whitespace — useful here since the registry file's colon-delimited columns include spaces for human readability.
if is_process_alive "$PID" && ! is_zombie "$PID"; thenBoth conditions must hold for a process to be considered genuinely healthy — alive alone isn't sufficient, exactly as the zombie-detection concept explained.
REASON="crashed (stale PID)" then conditionally overwrittenDistinguishes the two different reasons a restart might be needed in the log message, even though both currently trigger the same restart logic — useful diagnostic detail without adding branching complexity.
if [[ "$RECENT_RESTARTS" -ge "$MAX_RESTARTS_PER_WINDOW" ]]; then ... continue; fiThis is the entire safety mechanism of the project in one conditional — once the cap is hit, the continue guarantees no restart attempt happens, no matter how many more times this script runs within the window.
record_restart_attempt "$process_name" only reached if under the capAttempts are only recorded when a restart is actually attempted — the counter accurately reflects real restart attempts, not just check-cycle iterations.

📄 README.md

README.md
# NovaTrust Bank - Process Monitor (PID-File Based)

## Usage
    ./scripts/process_monitor.sh

## Registering a Process
Add a line to config/process_registry.txt:
    name : pid_file_path : expected_running_user : start_command
The target process itself must write its own PID to pid_file_path on startup.

## What Gets Checked
1. Liveness via the PID file + kill -0
2. Zombie state via ps -o stat=
3. Running user vs expected user
4. Restart-attempt count within a rolling window (capped, never infinite)

## Exit Codes
    0 = All processes healthy
    1 = Wrong owner detected, OR a restart was attempted (recovering)
    2 = No PID file found, OR a process is FLAPPING (restart cap reached)

## Important
This is an interim safety net for non-systemd-managed processes. Migrating
these to proper systemd services remains the recommended long-term fix.

🔄 What Happens Internally

  1. Two entirely independent conditions gate a genuinely healthy verdict: is_process_alive and ! is_zombie — a process can pass the first and fail the second, which is exactly the scenario the zombie check exists to catch.
  2. The restart-attempt state file uses the same rolling-window counting technique as Project 3's leak detection, just measuring restart frequency instead of memory-usage trend — another example of one core pattern (persisted, timestamped events, counted within a window) generalizing across very different problems.
  3. nohup ... & disown genuinely detaches the new process from this monitoring script's own process tree — once process_monitor.sh exits (as it does after every cron-triggered run), the restarted process must keep running entirely independently.
  4. The restart cap check happens before any restart attempt, not after — a process that's already flapping never even attempts another restart, rather than attempting one and then deciding afterward whether it should have.

🛡️ Production Best Practices

Always Cap Auto-Restart Attempts

Any automated restart capability without a hard cap and escalation path can itself become an incident — a crash-looping process restarted endlessly wastes resources and delays real investigation.

Alive Isn't Enough — Check for Zombies Too

A PID existing doesn't guarantee useful work is happening; always pair liveness checks with a state check for non-systemd process supervision.

Verify Ownership as a Security Signal

An unexpectedly root-owned process is a security-relevant finding independent of whether the process is otherwise "healthy" — check it explicitly.

Genuinely Detach Restarted Processes

nohup plus disown together ensure a restarted process survives the monitoring script's own exit — either alone is often insufficient.

Prefer Proper Supervision Long-Term

PID-file monitoring is a legitimate interim safety net, but migrating critical non-systemd processes to real service management remains the better permanent fix.

Distinguish One-Off Recovery from Flapping

A single successful automated recovery and a repeatedly-failing process are different findings requiring different responses — never report them identically.

🎤 Interview Preparation

Scenario: A process shows healthy via kill -0, but application logs show it hasn't processed any real work in hours. What's the likely gap in this monitoring approach?
This project verifies the process exists and isn't a zombie, not that it's making genuine functional progress — a hung-but-technically-alive process (deadlocked, stuck waiting on an unresponsive dependency) would pass every check here; catching that would require an application-level signal, closer to Project 20's heartbeat pattern (proof of actual successful work) than this project's liveness check alone.
Production Support: A process was restarted successfully once, then the script reports FLAPPING on the very next check, only 5 minutes later. Is this expected?
If the restarted process crashed again almost immediately, yes — this is exactly the scenario the restart cap and window are designed to catch quickly; the underlying issue clearly isn't a one-off blip, and further blind restarts wouldn't help, making immediate escalation the correct behavior here.
Shell Scripting: Why use kill -0 instead of checking if a process shows up in ps aux | grep for its PID?
kill -0 is a direct, purpose-built existence-and-permission check via the kernel itself; parsing ps output with grep for a PID risks accidental substring matches (a PID like 123 matching within a longer PID like 1234) unless carefully anchored, making kill -0 both simpler and more reliable for this specific yes/no question.
Troubleshooting: The zombie check never triggers even when you can visually confirm a zombie process in "ps aux". What might be wrong?
Check whether the state-code glob match [[ "$state" == Z* ]] is actually receiving the state field correctly - a common issue is ps -o stat='s output format varying slightly (extra whitespace, unexpected columns) across different Linux distributions or ps implementations, breaking the exact match.
Manager Round: Why cap restarts at 3 within 60 minutes rather than either restarting indefinitely or only ever restarting once?
Restarting indefinitely risks masking and prolonging a real bug behind repeated brief "healthy" windows while consuming resources; restarting only once might fail to recover from a genuinely transient issue (a brief resource spike, a momentary dependency outage) that would have succeeded on a second attempt — a small capped number balances giving transient issues a real chance to resolve against quickly recognizing a genuine, unfixed problem.
Architecture: Why does this project use scheduled cron checks instead of a continuously-running supervisor loop, given that continuous supervision could theoretically detect a crash faster?
This mirrors the entire course's scheduled-check philosophy for consistency and simplicity of operations; the honest, better long-term answer for genuinely critical processes needing faster detection is proper systemd management (which provides real continuous supervision) rather than building a custom always-on Bash daemon, which this project explicitly acknowledges as a scope boundary rather than pretending to fully solve.
Best Practice: Why record a restart attempt only after successfully reaching the restart command, rather than before attempting it?
Actually, in this implementation, the attempt is recorded immediately after the restart command is issued regardless of whether the process ends up stabilizing - the goal is counting genuine restart attempts for cap purposes, not restart successes; a design choice worth being explicit about, since counting only confirmed-successful restarts could allow more actual attempts than intended within the safety window.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the reconciler's Saturday crash within minutes instead of two days?
A scheduled PID-file liveness check running every 5 minutes, with automatic restart on the very first detected crash — the reconciler would have been back up and processing within minutes of crashing, with a logged restart attempt as a record, rather than remaining down and completely unnoticed for the entire weekend.

Key Learnings

The PID-file pattern, safe existence checking with kill -0, zombie-state detection, process-ownership verification, capped restart-attempt tracking within a rolling window, and proper process detachment with nohup/disown.

Common Mistakes to Avoid
