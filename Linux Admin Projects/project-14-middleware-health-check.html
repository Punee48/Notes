Project 14 of 30 · Middleware

Middleware Health Check

The port was listening. The health endpoint said UP. And every real transfer request sat frozen for 30 seconds, waiting for a database connection that would never come free.

🎯 Level: Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + curl/jq ⏱️ Duration: 3 hrs

📖 The Story — Healthy on the Outside, Starved on the Inside

A rarely-hit error path in the NEFT Gateway application had a subtle bug: under a specific failure condition, it checked out a database connection from the pool and never returned it. Over several hours, connection by connection, the pool slowly filled with permanently "checked out" connections until every single one was exhausted. New transfer requests still connected to the application server just fine — the port was open, the process was running, and Project 8's lightweight /health endpoint (which didn't touch the database at all) kept reporting 200 UP. But every real request needing an actual database connection hung for 30 seconds and then failed.

Priya's take in the retro: "Our application health check was checking if the front door opens. It was never checking if there's actually anyone free at the counter to serve you. I want to know the connection pool's active-versus-max ratio, the thread pool's health, and whether the port's actually listening — three completely different signals, not just one shallow endpoint."

Today we go one layer deeper than Project 8 — past "the application responds" and into "the application's internal resources aren't secretly exhausted."
🔁 Reinforced from Projects 1–13
curl with timeouts (Project 8), tiered WARN/CRITICAL classification, and composite multi-signal health verdicts (Project 7's connectivity-vs-replication-vs-tablespace pattern) all return here for the middleware layer.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Detect middleware-layer resource exhaustion (connection pools, thread pools) before it causes customer-facing request failures, going beyond simple port/endpoint checks.

Customer Requirement

Ops needs visibility into internal application server resource saturation — signals invisible to both infrastructure monitoring (Projects 1-7) and shallow endpoint checks (Project 8).

Banking Scenario

NEFT Gateway and Core Banking services run inside a Java application server, each maintaining a JDBC connection pool to the database and an internal request-handling thread pool.

Existing Manual Process / Prior Automation Gap

Project 8's application health check validated the lightweight /health endpoint only — a design choice that, as this incident showed, doesn't exercise the same resources real transaction requests depend on.

Problems With Endpoint-Only Checks

A health endpoint deliberately kept lightweight (for good reason — Project 8 taught us not to make health checks themselves resource-heavy) can completely miss a resource pool that's silently exhausted for everything else.

Business Impact & Risk

Every real customer transfer request timing out for 30 seconds during a pool-exhaustion event is a direct, sustained customer-facing outage invisible to every monitoring layer built so far.

Why Automation Is Required

Only a script directly querying the application server's actual internal pool and thread metrics can detect this class of problem — no infrastructure-level or shallow-endpoint check can see inside the application's own resource management.

Solution Design

Check that the application's port is genuinely listening, query a management/metrics endpoint (or parse application logs where no such endpoint exists) for connection-pool active/idle/max figures, check the process's thread count, and combine all three signals into one composite verdict.

Project Scope

In scope: port-listening checks, connection-pool saturation percentage, thread-count monitoring, and composite health classification. Out of scope: JVM garbage-collection tuning analysis (a more specialized, separate concern).

Expected Outcome

A middleware health report showing port status, connection-pool saturation percentage, and thread count together — catching pool exhaustion the moment it starts trending upward, long before every connection is gone.

🧠 New Bash Concepts for This Project

1. Checking a Port Without External Tools (/dev/tcp)

What: Bash itself can attempt a raw TCP connection using timeout 3 bash -c ">/dev/tcp/$host/$port" — no nc or telnet installation required.
Why: /dev/tcp is a Bash built-in feature (not a real file), giving us a dependency-free way to verify a port is accepting connections, useful on minimal hosts where netcat may not be installed.
Common mistake: Forgetting to wrap it in timeout — a connection attempt to a filtered (not refused, just silently dropped) port can otherwise hang for the OS's full TCP timeout, which can be very long.

2. Querying a Metrics/Management Endpoint (Reinforced curl + jq)

What: Many Java application frameworks expose a metrics endpoint (e.g., Spring Boot Actuator's /actuator/metrics or a custom /internal/pool-status) returning JSON connection-pool statistics.
Why: This is the cleanest possible source of truth for pool state — far more reliable than trying to infer it indirectly.

3. Extracting Nested JSON Fields with jq

What: jq -r '.pool.active' pulls a specific nested field out of a JSON response directly — reinforcing Project 8's brief mention of jq, now put to full use.
Why: Pool metrics are typically nested inside a larger JSON structure; jq navigates that structure precisely, where grep could easily grab the wrong occurrence of a common field name.

4. Calculating Pool Saturation as a Percentage

What: SATURATION_PCT=$(( ACTIVE * 100 / MAX_POOL_SIZE )) — the exact same multiply-before-divide integer-arithmetic pattern from Project 13's compliance percentage, now applied to connection counts.
Why: A raw "active: 47" number means nothing without knowing the pool's actual maximum size — the percentage is what's actually meaningful and comparable across differently-sized pools on different servers.

5. Finding a Java Process's PID (pgrep -f)

What: pgrep -f "neft-gateway.jar" finds a process ID by matching against its full command line, not just its short process name (which for Java processes is usually just java, unhelpfully identical across every Java service on a host).
Why: -f is essential here — without it, pgrep java would match every single Java process on the server, giving no way to identify the specific one we care about.

6. Checking a Process's Thread Count (ps -o nlwp=)

What: ps -o nlwp= -p "$PID" prints the number of lightweight processes (threads) owned by a given PID.
Why: An application's internal thread pool exhausting itself (all worker threads stuck) often shows up as an abnormal total thread count on the process — a useful independent signal alongside the connection-pool percentage.

7. Extracting Numbers from Log Lines with grep -oP (Fallback Path)

What: grep -oP 'active=\K[0-9]+' — -o prints only the matched portion (not the whole line), -P enables Perl-compatible regex, and \K resets the match start, so only the digits after active= are actually printed.
Why: Where no metrics endpoint exists, an application server's own log lines (e.g., a periodic "pool stats: active=48 idle=2 max=50" line) are often the only available signal — this is a deliberate fallback for that reality.

8. Getting the Most Recent Matching Log Line

What: grep "pool stats" logfile | tail -n 1 — combining Project 5's grep familiarity with tail -n 1 to get only the freshest snapshot from a log that may contain many historical pool-stats lines.
Why: An old pool-stats line from hours ago is useless (and potentially misleading) for a real-time health check — only the most recent entry reflects current state.

9. Composite Health Verdicts Across Heterogeneous Signals (Reinforced)

What: Combining a boolean (port listening: yes/no), a percentage (pool saturation), and a raw count (thread count) into one overall HEALTHY/WARNING/CRITICAL verdict — the same "worst signal wins" philosophy from Project 7's connectivity/replication/tablespace combination.
Why: Different metric types require different comparison logic, but they must still combine cleanly into one actionable verdict for Ops to act on.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Middleware health check helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- is_port_listening ----------
# Purpose: Return 0 if a TCP port accepts a connection, using Bash's built-in /dev/tcp (no netcat needed)
is_port_listening() {
    local host="$1"
    local port="$2"
    timeout "$PORT_CHECK_TIMEOUT" bash -c "echo > /dev/tcp/$host/$port" 2>/dev/null
}

# ---------- get_pool_stats_from_endpoint ----------
# Purpose: Query a metrics endpoint and return "active idle max" via jq, or empty if unavailable
get_pool_stats_from_endpoint() {
    local metrics_url="$1"
    local response
    response=$(curl -s --connect-timeout "$HTTP_CONNECT_TIMEOUT" --max-time "$HTTP_MAX_TIME" "$metrics_url" 2>/dev/null)
    [[ -z "$response" ]] && { echo ""; return; }

    local active idle max
    active=$(echo "$response" | jq -r '.pool.active // empty' 2>/dev/null)
    idle=$(echo "$response" | jq -r '.pool.idle // empty' 2>/dev/null)
    max=$(echo "$response" | jq -r '.pool.max // empty' 2>/dev/null)

    [[ -z "$active" || -z "$max" ]] && { echo ""; return; }
    echo "$active $idle $max"
}

# ---------- get_pool_stats_from_log ----------
# Purpose: Fallback - parse the most recent pool-stats line from an application log file
# Expects lines like: "pool stats: active=48 idle=2 max=50"
get_pool_stats_from_log() {
    local log_path="$1"
    [[ -f "$log_path" ]] || { echo ""; return; }

    local latest_line
    latest_line=$(grep "pool stats:" "$log_path" | tail -n 1)
    [[ -z "$latest_line" ]] && { echo ""; return; }

    local active idle max
    active=$(echo "$latest_line" | grep -oP 'active=\K[0-9]+')
    idle=$(echo "$latest_line" | grep -oP 'idle=\K[0-9]+')
    max=$(echo "$latest_line" | grep -oP 'max=\K[0-9]+')

    [[ -z "$active" || -z "$max" ]] && { echo ""; return; }
    echo "$active $idle $max"
}

# ---------- get_thread_count ----------
# Purpose: Return the thread count of a process matched by a command-line pattern, or empty if not found
get_thread_count() {
    local process_pattern="$1"
    local pid
    pid=$(pgrep -f "$process_pattern" | head -n 1)      # head -n 1 in case of an unexpected duplicate match
    [[ -z "$pid" ]] && { echo ""; return; }
    ps -o nlwp= -p "$pid" | tr -d ' '
}

Line-by-Line Highlights

  • timeout "$PORT_CHECK_TIMEOUT" bash -c "echo > /dev/tcp/$host/$port" — redirecting to /dev/tcp/host/port is intercepted specially by Bash itself (it isn't a real filesystem path) and attempts a TCP connection; success or failure is reflected purely in the exit code.
  • jq -r '.pool.active // empty' — the // operator provides a default (here, an empty result) if the field is missing entirely, preventing jq from erroring out on a slightly different JSON shape than expected.
  • grep -oP 'active=\K[0-9]+' — \K is a Perl-regex feature meaning "keep everything matched so far out of the final result" — so only the digits after active= are printed, not the literal text active= itself.
  • pgrep -f "$process_pattern" | head -n 1 — defensively takes only the first match even though we expect exactly one, since an unexpected duplicate process shouldn't cause the whole check to error out on multiple PIDs.
  • ps -o nlwp= -p "$pid" | tr -d ' ' — ps's column output includes leading whitespace for alignment purposes; tr -d ' ' strips it so the value is a clean integer for later comparison.

🩺 Main Script

scripts/middleware_check.sh
#!/bin/bash
# =====================================================================
# middleware_check.sh
# NovaTrust Bank - Middleware Connection-Pool & Thread Health Check
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/middleware.conf"

SERVICES_FILE="$SCRIPT_DIR/../config/services.txt"
[[ -f "$SERVICES_FILE" ]] || { echo "ERROR: Services file not found: $SERVICES_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/middleware_check_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Middleware check run finished."' EXIT

log_message "INFO" "=== Starting middleware health check ==="

OVERALL_EXIT=0

while IFS=':' read -r host port metrics_url process_pattern log_path; do
    [[ -z "$host" || "$host" == \#* ]] && continue

    SERVICE_STATUS="HEALTHY"

    # ---------- Signal 1: Port listening ----------
    if ! is_port_listening "$host" "$port"; then
        log_message "FAIL" "$host:$port - port is NOT listening"
        SERVICE_STATUS="CRITICAL"
        OVERALL_EXIT=2
    else
        log_message "PASS" "$host:$port - port is listening"
    fi

    # ---------- Signal 2: Connection pool saturation (only meaningful if port is up) ----------
    if [[ "$SERVICE_STATUS" != "CRITICAL" ]]; then
        POOL_STATS=$(get_pool_stats_from_endpoint "$metrics_url")
        if [[ -z "$POOL_STATS" ]]; then
            log_message "WARN" "$host - metrics endpoint unavailable, falling back to log parsing"
            POOL_STATS=$(get_pool_stats_from_log "$log_path")
        fi

        if [[ -z "$POOL_STATS" ]]; then
            log_message "WARN" "$host - could not determine connection pool stats (endpoint AND log fallback both failed)"
        else
            read -r active idle max <<< "$POOL_STATS"
            SATURATION_PCT=$(( active * 100 / max ))

            if [[ "$SATURATION_PCT" -ge "$POOL_CRITICAL_PCT" ]]; then
                log_message "FAIL" "$host - pool saturation CRITICAL: ${SATURATION_PCT}% (active=$active, max=$max)"
                SERVICE_STATUS="CRITICAL"
                OVERALL_EXIT=2
            elif [[ "$SATURATION_PCT" -ge "$POOL_WARN_PCT" ]]; then
                log_message "WARN" "$host - pool saturation WARNING: ${SATURATION_PCT}% (active=$active, max=$max)"
                [[ "$SERVICE_STATUS" == "HEALTHY" ]] && SERVICE_STATUS="WARNING"
                [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
            else
                log_message "PASS" "$host - pool saturation healthy: ${SATURATION_PCT}% (active=$active, max=$max)"
            fi
        fi
    fi

    # ---------- Signal 3: Thread count ----------
    THREAD_COUNT=$(get_thread_count "$process_pattern")
    if [[ -z "$THREAD_COUNT" ]]; then
        log_message "WARN" "$host - could not find process matching '$process_pattern' to check thread count"
    elif [[ "$THREAD_COUNT" -gt "$THREAD_COUNT_MAX_HEALTHY" ]]; then
        log_message "WARN" "$host - thread count elevated: $THREAD_COUNT (threshold $THREAD_COUNT_MAX_HEALTHY)"
        [[ "$SERVICE_STATUS" == "HEALTHY" ]] && SERVICE_STATUS="WARNING"
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    else
        log_message "PASS" "$host - thread count healthy: $THREAD_COUNT"
    fi

    log_message "INFO" "$host - COMPOSITE VERDICT: $SERVICE_STATUS"

done < "$SERVICES_FILE"

log_message "INFO" "=== Middleware health check complete ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
SERVICE_STATUS="HEALTHY" at the top of each loop iterationResets the composite verdict fresh for each service — this variable only ever escalates (HEALTHY → WARNING → CRITICAL) within a single iteration, never downgrades once raised.
if [[ "$SERVICE_STATUS" != "CRITICAL" ]]; then before pool checksSkips pool-saturation checking entirely if the port itself is already down — a meaningless check (there's no live application to query) that would only add noise to the log.
POOL_STATS=$(get_pool_stats_from_endpoint ...) then fallbackTries the preferred, richer source (the metrics endpoint) first, only falling back to log-parsing if that specifically returns empty — this ordering reflects a genuine preference for structured data over log scraping.
[[ "$SERVICE_STATUS" == "HEALTHY" ]] && SERVICE_STATUS="WARNING"Only escalates from HEALTHY to WARNING — deliberately never downgrades an already-CRITICAL status back to WARNING, preserving the "worst signal wins" rule across all three checks.
Thread-count check runs regardless of pool statusThread exhaustion and connection-pool exhaustion are related but distinct failure modes — checking both independently, every time, ensures neither masks the other.

📄 README.md

README.md
# NovaTrust Bank - Middleware Health Check

## Usage
    ./scripts/middleware_check.sh

## Three Independent Signals Checked Per Service
1. Port listening (Bash /dev/tcp, no external tools needed)
2. Connection pool saturation % (metrics endpoint preferred, log-parsing fallback)
3. Application process thread count

## Composite Verdict
Each service gets ONE overall verdict (HEALTHY/WARNING/CRITICAL) reflecting
the WORST of its three individual signals - never averaged, never masked.

## Exit Codes
    0 = All services HEALTHY
    1 = At least one WARNING
    2 = At least one CRITICAL (port down or pool near exhaustion)

🔄 What Happens Internally

  1. /dev/tcp is handled entirely inside Bash's own process — no external command is spawned for the port check itself, only for the timeout wrapper protecting it.
  2. The endpoint-vs-log fallback decision happens once per service, per run, not cached across runs — a temporarily unavailable metrics endpoint doesn't permanently switch a service to log-parsing mode.
  3. jq's // default operator and the log-parsing fallback's own empty-string checks both funnel into the exact same "could not determine pool stats" handling downstream — the main script doesn't need to know or care which data source ultimately succeeded or failed.
  4. All three signals are checked independently within one loop iteration, with SERVICE_STATUS only ever escalating — this guarantees a WARNING-level thread count is never silently hidden just because the pool itself happened to be healthy.

🛡️ Production Best Practices

Check Internal Resources, Not Just External Responsiveness

A responsive port or a passing shallow health endpoint says nothing about internal resource exhaustion — check pools and threads directly wherever possible.

Prefer Structured Metrics Over Log Parsing

A proper metrics endpoint is far more reliable and less brittle than regex-parsing log lines — use log-parsing only as an explicit, clearly-labeled fallback.

Percentages Over Raw Counts

"Active: 47" is meaningless without knowing max pool size — always normalize to a percentage for meaningful, comparable thresholds.

Independent Signals, Composite Verdict

Check each resource independently, but combine into one clear verdict using "worst signal wins" — never average different signal types together.

Guard Every Network Call With Timeouts

Port checks, metrics-endpoint calls — anything touching the network needs the same timeout discipline established since Project 2.

Match Process Identification Precision to the Environment

pgrep -f with a specific, unique pattern is essential on any host running multiple same-named processes (like several Java services all showing as java).

🎤 Interview Preparation

Scenario: The composite verdict shows CRITICAL, but Project 8's application health check on the same service still shows HEALTHY. Is this a contradiction?
No — this is exactly the intended, complementary relationship between the two projects: Project 8 deliberately checks a lightweight endpoint that may not touch the database connection pool at all, while this project checks the pool directly; both can legitimately disagree because they're measuring genuinely different things.
Production Support: The script reports the metrics endpoint is unavailable every single run, always falling back to log parsing. What would you check?
Verify the metrics endpoint URL, port, and any authentication/TLS requirements are correct and reachable from the checking host specifically — a firewall rule allowing normal application traffic but blocking the jump box's access to an internal metrics port is a common, easy-to-miss cause.
Shell Scripting: Why use Bash's built-in /dev/tcp instead of just calling nc -z?
/dev/tcp requires no external dependency at all, which matters on minimal or hardened production images where netcat might deliberately not be installed for security reasons; the tradeoff is it's Bash-specific and won't work if a script is ever run under plain sh.
Troubleshooting: Thread count is always reported as empty even though the target Java process is clearly running. What's the likely bug?
The process_pattern configured for pgrep -f probably doesn't match the actual full command line of the running process (Java processes often have long, specific classpath arguments) — testing the exact pattern manually with pgrep -f against the real running process is the fastest way to confirm and fix this.
Manager Round: Why maintain both a metrics-endpoint path and a log-parsing fallback instead of just requiring every service to expose a proper metrics endpoint?
Not every legacy or third-party middleware component can be quickly modified to add a metrics endpoint; the fallback ensures monitoring coverage can still be extended pragmatically to older services while the ideal (a real metrics endpoint) is rolled out over time as a longer-term improvement.
Architecture: Why does the script skip pool-saturation checking entirely when the port check has already failed?
If the port isn't listening, there's no live application to query for pool statistics at all — attempting the check anyway would just produce a confusing, meaningless failure on top of the already-clear port-down finding, adding noise rather than additional signal.
Best Practice: Why does the composite verdict logic only ever escalate (HEALTHY → WARNING → CRITICAL) and never downgrade within one run?
This is the same "never downgrade a failure" principle from Project 1's exit-code handling, applied to a multi-signal composite instead of a single metric — a later, healthier-looking check must never silently overwrite an earlier finding of a real problem within the same evaluation.
Real Incident Discussion: What's the one design decision in this project that most directly would have caught the NEFT connection-pool exhaustion before every connection was gone?
Directly querying and calculating connection-pool saturation as a percentage, checked independently every 5 minutes — the pool would have crossed the 70% WARNING threshold hours before full exhaustion, giving Ops a clear early trend to act on instead of discovering the problem only once requests started actually failing.
