Project 25 of 30 · Reporting

Daily Infrastructure Health Report

During a board audit, someone asked "how healthy is our infrastructure right now" — and the honest answer required manually opening 24 separate log files.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL ⏱️ Duration: 3 hrs

📖 The Story — Twenty-Four Dashboards, Zero Single Answers

During a board-level audit review, a director asked a deceptively simple question: "How healthy is our infrastructure right now, overall?" Nobody in the room could answer it directly. NovaTrust now has 24 separate monitoring projects, each producing its own log file, its own report format, its own summary line buried at the bottom of its own output — genuinely excellent detailed coverage, with absolutely no single place to see the big picture.

Priya's assignment: "I want one email, every morning, that pulls together the latest result from every single monitoring project we've built — health checks, disk, memory, CPU, certificates, database, backups, patch compliance, all of it — into one report with one overall score. Leadership shouldn't need to know our folder structure to understand whether we're in good shape."

This project doesn't monitor anything new — its entire job is synthesizing everything Projects 1 through 24 have already been quietly producing into one coherent daily picture.
🔁 Reinforced from Projects 1–24
Every project's disciplined, consistent SUMMARY log-line convention (established since Project 1) is what makes this aggregation possible at all — a direct payoff of that consistency, maintained across 24 different domains.

🧠 New Bash Concepts for This Project

1. A "Registry of Registries"

What: A config file listing every monitoring project's name, its log directory, and its log-filename pattern — one entry per project, covering all 24 sources.
Why: Extending Project 20's registry-driven philosophy one level up: instead of registering individual jobs within one project, this registry catalogs entire projects, each with its own established logging convention.

2. Extracting Each Source's Latest SUMMARY Line

What: grep "SUMMARY" "$latest_log" | tail -n 1 — reusing the exact grep+tail pattern from Project 16's most-recent-match extraction, now applied across 24 structurally different log files that all happen to share one disciplined convention: a line containing the word SUMMARY.
Why: This works specifically because every prior project in this course consistently logged a [INFO] === SUMMARY: ... === line — a small convention decision made all the way back in Project 1 that pays off directly here.

3. Finding Today's (or the Most Recent) Log File Per Source

What: Each source project names its logs with a date (project_YYYYMMDD.log); finding "today's log" means constructing that exact filename, while gracefully falling back or flagging if it doesn't exist yet.
Why: Not every project necessarily ran yet today at the exact moment this aggregator runs — the aggregator must handle "log file for today doesn't exist" as a distinct, expected case, not an error.

4. Generating HTML from Bash with Heredocs (New Output Format)

What: cat <<EOF > report.html ... EOF — using a heredoc to emit multi-line HTML markup directly from a Bash script, mixing static template structure with dynamically-inserted variable values.
Why: Every prior project generated plain-text logs or CSV; this is the course's first project generating structured markup meant to be rendered visually, requiring careful attention to correctly embedding dynamic Bash values inside static HTML/CSS.

5. Dynamically Building an HTML Table from Looped Data

What: Looping over the registry, appending one <tr>...</tr> row per source to a growing HTML string variable, then inserting that accumulated string into the final report template.
Why: The report's central table has a variable number of rows (one per registered source) — this must be built programmatically inside the loop, not hand-written as static markup.

6. An Aggregate "Score of Scores"

What: Counting how many of the 24 sources report a healthy/passing status, then calculating OVERALL_PCT = (HEALTHY_SOURCES * 100) / TOTAL_SOURCES — the same multiply-before-divide formula from Project 13, now describing overall infrastructure posture instead of any single domain.

7. Sending HTML-Formatted Email (Reinforced Project 9, New Content-Type)

What: mail -a "Content-Type: text/html" -s "Subject" recipient < report.html — the -a flag adds a custom email header telling the recipient's mail client to render the body as HTML rather than plain text.
Why: Without this header, the carefully-formatted HTML report would arrive as an unreadable wall of raw markup tags instead of the polished visual report it's meant to be.

8. Inline CSS for Email-Client Compatibility (Practical Constraint)

What: Unlike a webpage that can link an external stylesheet, HTML email must generally use style="..." attributes directly on each element, since most email clients strip or ignore <style> blocks and external CSS entirely.
Why: A genuinely practical constraint worth knowing — the report's HTML generation must account for this, styling elements individually rather than relying on a shared stylesheet the way this very course's own HTML pages do.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Daily health report helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_source_summary ----------
# Purpose: Return today's SUMMARY line for one source, or empty if unavailable
get_source_summary() {
    local log_dir="$1"
    local filename_prefix="$2"
    local today
    today=$(date '+%Y%m%d')
    local log_file="$SCRIPT_DIR/$log_dir/${filename_prefix}${today}.log"

    [[ -f "$log_file" ]] || { echo ""; return; }
    grep "SUMMARY" "$log_file" | tail -n 1
}

# ---------- classify_summary_text ----------
# Purpose: Infer PASS/WARN/FAIL from a summary line's own content
classify_summary_text() {
    local summary="$1"
    if echo "$summary" | grep -qiE "critical|fail|breach|unreachable|non_compliant"; then
        echo "FAIL"
    elif echo "$summary" | grep -qiE "warn"; then
        echo "WARN"
    else
        echo "PASS"
    fi
}

# ---------- status_color ----------
status_color() {
    local status="$1"
    case "$status" in
        PASS)     echo "#1b7f4c" ;;
        WARN)     echo "#a15c00" ;;
        FAIL)     echo "#a3242f" ;;
        NO_DATA)  echo "#6b7280" ;;
    esac
}

# ---------- build_table_row ----------
build_table_row() {
    local name="$1"
    local status="$2"
    local detail="$3"
    local color
    color=$(status_color "$status")

    cat <
  ${name}
  
    ${status}
  
  ${detail}

EOF
}

Line-by-Line Highlights

  • get_source_summary constructs today's exact expected log filename from the registry's filename_prefix and today's date — mirroring how every source project names its own daily logs, established as a convention back in Project 1.
  • classify_summary_text infers a status purely from the summary line's own wording — a pragmatic approach given that 24 different projects' summary lines aren't identically structured, only similarly worded around key terms like "critical" or "warn."
  • build_table_row uses a heredoc to emit one complete, styled HTML table row per call — note every style is inline (style="...") on each element, per the email-client-compatibility constraint discussed in the concepts section.
  • Calling build_table_row once per source and accumulating its output is exactly how the main script builds the report's dynamic-length table, one row per registered project.

🩺 Main Script

scripts/daily_health_report.sh
#!/bin/bash
# =====================================================================
# daily_health_report.sh
# NovaTrust Bank - Consolidated Daily Infrastructure Health Report
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/daily_health_report.conf"

REGISTRY_FILE="$SCRIPT_DIR/../config/source_registry.txt"
[[ -f "$REGISTRY_FILE" ]] || { echo "ERROR: Source registry not found: $REGISTRY_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
TODAY_READABLE=$(date '+%B %d, %Y')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/daily_health_report_${TODAY}.log"
REPORT_FILE="$SCRIPT_DIR/$REPORT_DIR/daily_report_${TODAY}.html"
mkdir -p "$(dirname "$LOG_FILE")" "$(dirname "$REPORT_FILE")"

log_message "INFO" "=== Building daily infrastructure health report ==="

TABLE_ROWS=""
TOTAL_SOURCES=0
HEALTHY_SOURCES=0

while IFS=':' read -r name log_dir filename_prefix; do
    [[ -z "$name" || "$name" == \#* ]] && continue
    ((TOTAL_SOURCES++))

    SUMMARY=$(get_source_summary "$log_dir" "$filename_prefix")

    if [[ -z "$SUMMARY" ]]; then
        log_message "WARN" "$name: NO DATA (no log found for today)"
        TABLE_ROWS+="$(build_table_row "$name" "NO_DATA" "No log found for today")"
        continue
    fi

    STATUS=$(classify_summary_text "$SUMMARY")
    log_message "INFO" "$name: $STATUS - $SUMMARY"
    TABLE_ROWS+="$(build_table_row "$name" "$STATUS" "$SUMMARY")"

    [[ "$STATUS" == "PASS" ]] && ((HEALTHY_SOURCES++))

done < "$REGISTRY_FILE"

OVERALL_PCT=$(( HEALTHY_SOURCES * 100 / TOTAL_SOURCES ))
OVERALL_COLOR="#1b7f4c"
[[ "$OVERALL_PCT" -lt 90 ]] && OVERALL_COLOR="#a15c00"
[[ "$OVERALL_PCT" -lt 70 ]] && OVERALL_COLOR="#a3242f"

log_message "INFO" "=== SUMMARY: Overall infrastructure health ${OVERALL_PCT}% ($HEALTHY_SOURCES/$TOTAL_SOURCES sources healthy) ==="

# ---------- Assemble the full HTML report via heredoc ----------
cat < "$REPORT_FILE"




  

    
NovaTrust Bank

    
Daily Infrastructure Health Report

    
${TODAY_READABLE}

  

  

    

      
${OVERALL_PCT}%

      
Overall Infrastructure Health (${HEALTHY_SOURCES} of ${TOTAL_SOURCES} systems healthy)

    

    
      ${TABLE_ROWS}
    

      

        System
        Status
        Latest Summary
      

  

  

    Generated automatically at $(date '+%H:%M:%S %Z'). This report aggregates existing monitoring results and does not itself perform any checks.
  




EOF

log_message "INFO" "HTML report written to: $REPORT_FILE"

# ---------- Send as HTML email ----------
mail -a "Content-Type: text/html" -s "${EMAIL_SUBJECT_PREFIX} - ${OVERALL_PCT}% - ${TODAY_READABLE}" \
    -r "$EMAIL_FROM" "$EMAIL_TO" < "$REPORT_FILE"

log_message "INFO" "=== Daily report sent to $EMAIL_TO ==="

if [[ "$OVERALL_PCT" -lt 100 ]]; then
    exit 1
fi
exit 0

Every Line, Explained

LineExplanation
TABLE_ROWS+="$(build_table_row ...)"The += operator appends to a growing string variable on each loop iteration — by the time the loop finishes, TABLE_ROWS contains all 24 sources' complete HTML rows, ready to be dropped into the final template.
Three chained [[ ... ]] && OVERALL_COLOR=... linesEach condition can independently override the color, and since they're checked in order from least to most severe, a percentage below 70 correctly ends up red even though it's also technically below 90 (which would have set amber first) — order matters here.
${TABLE_ROWS} inside the heredocBash variable expansion happens naturally inside a heredoc exactly like any double-quoted context — this is what allows the dynamically-built, multi-row HTML string to be inserted directly into the static template structure.
mail -a "Content-Type: text/html" ...The critical header ensuring the recipient's email client renders this as a formatted report rather than displaying raw HTML tags as plain text.
Final if [[ "$OVERALL_PCT" -lt 100 ]]; then exit 1; fiEven this aggregation-only report follows the course's consistent exit-code discipline — useful if this script itself is ever wrapped by Project 9's alerting wrapper for an additional "overall health dropped" notification layer.

📌 Timing Matters for an Aggregator
This script must run after the sources it aggregates — scheduling it too early would show yesterday's or missing data for projects that haven't run yet that morning. Reviewing every source project's own cron schedule when choosing this timing is essential.

📄 README.md

README.md
# NovaTrust Bank - Daily Infrastructure Health Report

## Usage
    ./scripts/daily_health_report.sh

## Adding a New Source
Add a line to config/source_registry.txt:
    Display Name:relative/path/to/logs:log_filename_prefix_
No changes to the script itself are ever needed.

## What This Script Does NOT Do
It never re-runs any underlying check. It only reads each source project's
own already-generated SUMMARY log line for today and aggregates them.

## Handling Missing Data
A source with no log file for today is reported as NO DATA, distinctly
from PASS/WARN/FAIL, and does not count toward the healthy-sources total.

## Output
- HTML report archived daily: reports/daily_report_YYYYMMDD.html
- Emailed as HTML to EMAIL_TO in config/daily_health_report.conf

## Exit Codes
    0 = 100% of sources reporting healthy
    1 = Any source below 100% health or reporting NO DATA

🔄 What Happens Internally

  1. This script never touches any other project's actual monitoring logic — it strictly reads pre-existing log files, making it entirely decoupled from (and safe to modify without risk to) all 24 underlying monitoring systems.
  2. The HTML table's row count is determined entirely at runtime by how many entries exist in the registry file — adding a 25th monitored project next month means one new registry line, with zero script changes.
  3. The heredoc-based report template mixes static HTML/CSS structure with dynamic Bash variable expansion in one readable block — a genuinely different code-generation technique than this course's earlier CSV or JSON output, suited specifically to producing rich, structured markup.
  4. Every design decision about inline styling and content-type headers reflects the practical reality that HTML email rendering is far more constrained and inconsistent across clients than rendering a webpage — a real-world constraint worth understanding beyond just this course's own styled pages.

🛡️ Production Best Practices

Aggregators Should Never Re-Execute Underlying Checks

This project strictly reads existing results — re-running 24 projects' worth of checks just to build a summary would be wasteful, slow, and risk side effects far beyond this project's actual purpose.

Missing Data Is Its Own Status, Never Silence

A source with no data for today must be visibly flagged, never silently dropped from the report or miscounted as healthy.

Preserve Cross-Project Logging Conventions

This entire project only works because every prior project consistently logged a recognizable SUMMARY line — maintaining that discipline in any future project keeps this aggregator functional.

Design HTML Email for the Real Constraint

Inline styles, not external stylesheets or <style> blocks — email client rendering is far more restrictive and inconsistent than a modern browser.

Schedule Aggregators After Their Sources

An aggregation report is only as current as the underlying data it reads — always schedule it comfortably after every source project's own expected completion time.

Keep the Registry the Only Thing That Changes

Adding, removing, or renaming a monitored source should always be a config-file edit, never a change to the aggregation script's own logic.

🎤 Interview Preparation

Scenario: The report shows a source as NO DATA, but you can confirm that source's own script actually ran and completed successfully this morning. What's the likely gap?
Most likely a mismatch between the registry's configured filename pattern (or date format) and that source's actual log-naming convention — worth manually confirming the exact expected filename this aggregator is constructing against what the source project genuinely produces.
Production Support: The overall percentage seems lower than expected given how many sources show PASS in the detailed table. What calculation might explain this?
Check whether NO_DATA sources are being correctly counted in the denominator (TOTAL_SOURCES) while correctly excluded from the numerator (HEALTHY_SOURCES) — several NO_DATA entries can meaningfully drag down the overall percentage even when every source that did report data happened to show PASS.
Shell Scripting: Why does TABLE_ROWS use the += operator to accumulate HTML rather than writing each row directly to the report file as it's generated?
The overall summary section (showing the percentage and color) needs to appear before the table in the final HTML, but the percentage can only be calculated after the full loop over all sources completes — accumulating rows in a variable first, then inserting them into the template afterward, allows the summary and the table to be assembled in the correct final order despite being computed in a different order.
Troubleshooting: classify_summary_text is misclassifying a source's genuinely healthy summary line as FAIL. What's the likely cause?
The summary line probably contains one of the matched keywords (like "critical" or "fail") in a context that isn't actually indicating a problem — for example, a summary mentioning "Critical: 0" would still match a simple grep -qi critical pattern; this text-based classification approach has real, acknowledged limitations worth being aware of.
Manager Round: Why build this as a separate 25th project that reads other projects' logs, rather than having each of the 24 projects push their own results directly into a shared dashboard or database?
A read-only, decoupled aggregator can be added, modified, or even temporarily disabled without touching or risking any of the 24 existing, already-proven monitoring systems; a push-based shared-database approach would require modifying all 24 existing projects and introduces a shared dependency that, if broken, could affect every source's own ability to log normally.
Architecture: What's the fundamental limitation of inferring PASS/WARN/FAIL purely from keyword matching against each source's summary text, rather than a structured status field?
Text-based inference is inherently fragile against wording variations, coincidental keyword matches, or any future source project phrasing its summary differently than expected — a more robust design might have every project also emit a small structured status file (even just one word: PASS/WARN/FAIL) specifically for aggregation, rather than relying on parsing human-readable log text.
Best Practice: Why does this project deliberately keep the source registry as the ONLY thing that changes when adding a new monitored project?
This mirrors the config-driven-behavior principle established since Project 1 — keeping the aggregation logic itself completely generic and registry-driven means the script's own tested, working code never needs to change just because the set of things being monitored grows, reducing risk with every addition.
Real Incident Discussion: What's the single most direct design decision in this project that would have let leadership immediately answer "how healthy is our infrastructure" during that board audit?
The single overall health percentage, calculated across all 24 sources and prominently displayed at the very top of the report — instead of needing to manually check two dozen separate systems, the exact question the director asked would have had a direct, immediate, accurate answer sitting in that morning's inbox already.
