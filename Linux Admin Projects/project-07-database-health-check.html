Database Health Check

The morning a customer saw last week's account balance — because nobody was watching how far behind the replica had fallen.

🎯 Level: Intermediate 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + MySQL Client ⏱️ Duration: 2–3 hrs

📖 The Story — Stale Balances

A customer called the branch furious: their online banking dashboard showed a balance that didn't include a deposit made two days earlier. The Core Banking database uses a primary-replica setup — reports and balance lookups are served from a read replica to reduce load on the primary. That replica had silently fallen 51 hours behind, and nobody knew until the complaint came in.

Priya assigns the fix: "We need a database health check — can we actually connect, is replication keeping up, and is any table space filling up unexpectedly. And do this properly: I never want to see a database password sitting in plain text inside a script or show up when someone runs ps aux."

Today's project introduces two firsts: talking to a database from Bash, and handling credentials the way a real bank's audit team would actually require.
🔁 Reinforced from Projects 1–6
Tiered threshold classification, timeout-wrapped external calls, config-driven behavior, and the consolidated report pattern all continue.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Continuously verify database connectivity, replication lag, and table-space usage for Core Banking's database layer.

Customer Requirement

Ops needs to know immediately if a replica falls behind by more than a defined tolerance, before customers see stale data.

Banking Scenario

Core Banking runs a primary MySQL/MariaDB instance for writes and one or more read replicas serving balance lookups and reporting queries.

Existing Manual Process

None — replication lag was invisible until a customer-facing symptom (a stale balance) surfaced it.

Problems We're Solving Proactively

Replication lag can grow silently for hours under load, disk pressure, or a long-running query — with zero visible symptoms on the server itself (CPU/memory/disk can all look perfectly normal).

Business Impact & Risk

Stale balance or transaction data shown to customers is a direct trust and potential regulatory issue — customers reasonably expect their banking data to be current.

Why Automation Is Required

Replication lag in seconds is a number sitting inside the database itself — only a script querying it directly, on a schedule, can catch it before a human notices something's wrong externally.

Solution Design

Connect to each database instance using credentials stored securely outside the script, verify basic connectivity, query replication lag in seconds, and query table-space usage against a threshold — all with strict credential-file permission enforcement.

Project Scope

In scope: connectivity, replication lag (seconds behind primary), and table-space usage checks. Out of scope: query performance analysis or slow-query log parsing (a possible future project).

Expected Outcome

A report per database instance showing connectivity status, replication lag in seconds with a tiered classification, and table-space usage — with credentials never appearing in plain text in the script, logs, or process list.

🧠 New Bash Concepts for This Project

1. Querying a Database from Bash (mysql -e)

What: mysql --defaults-extra-file=creds.cnf -e "SELECT 1" runs a single SQL statement non-interactively and prints its result.
Why: This is the standard way any Bash script talks to a MySQL/MariaDB database without an interactive session.

2. Never Pass Passwords on the Command Line

What: A flag like -p'mypassword' is a serious security mistake — anything passed as a command-line argument is visible to any user on the same machine via ps aux or /proc/<pid>/cmdline, for as long as the process runs.
Why: On a shared jump box, this would leak the Core Banking database password to anyone who happened to run ps at the right moment.
Correct approach: --defaults-extra-file=/path/to/creds.cnf points MySQL at a config file containing the credentials — nothing sensitive ever appears as a process argument.

3. The .cnf Credentials File Pattern

What: A small file in MySQL's config format:

[client]
user=monitor_svc
password=************
host=corebanking-db-primary.novatrust.internal

Why: Keeps credentials in exactly one place, outside version control, readable only by the service account running the check.

4. Validating File Permissions Before Trusting a Secret (stat)

What: stat -c '%a' file prints a file's permission bits as a number, e.g. 600.
Why: Before ever using the credentials file, we verify it's 600 (owner read/write only) — if anyone else can read it, we refuse to proceed rather than silently using a leaky secret.
Production example: [[ "$(stat -c '%a' "$CREDS_FILE")" == "600" ]] || { echo "Insecure permissions"; exit 1; }

5. Clean, Parseable Query Output (-N -B)

What: mysql ... -N -B -e "SELECT ..." — -N (skip-column-names) removes header rows, -B (batch) uses tab-separated, non-decorated output.
Why: Without these flags, mysql's output is formatted with ASCII-art borders meant for humans — nearly impossible to parse reliably in a script.

6. Parsing SHOW REPLICA STATUS Output

What: This command returns many fields as columns; we care about one specifically: Seconds_Behind_Source (or the legacy name Seconds_Behind_Master).
Why: This single field is the direct, authoritative measure of replication lag in seconds — exactly what caused our incident when nobody was watching it.
Approach: Pipe the vertical (\G-style) output through grep and awk to extract just that one value cleanly.

7. Distinguishing Connection Failure from Query Failure

What: Check the mysql client's own exit code ($?) after a trivial SELECT 1 before attempting any real diagnostic query.
Why: "Can't connect at all" and "connected fine, but replication is broken" are two completely different problems requiring different responses — we must not let a connection failure be silently misreported as a replication issue.

8. Querying information_schema for Table-Space Usage

What: A query against MySQL's built-in information_schema.tables view can report data+index size per table or database in bytes.
Why: This is how we check "is a database's storage growing dangerously" from entirely inside SQL, without needing OS-level disk access to the database server.

9. Timeout-Wrapping Database Calls (Reinforced)

What: timeout 10 mysql --defaults-extra-file=... -e "..." — the same discipline applied to SSH (Project 2) and TLS handshakes (Project 6), now applied to database connections.
Why: A database under heavy load or network partition can hang a connection attempt indefinitely without this guard.

🧩 Utility Functions (Extended)

scripts/utils.sh (additions)
# ---------- verify_creds_permissions ----------
# Purpose: Refuse to proceed unless a credentials file is readable only by its owner (600)
verify_creds_permissions() {
    local creds_file="$1"
    [[ -f "$creds_file" ]] || { echo "MISSING"; return 1; }

    local perms
    perms=$(stat -c '%a' "$creds_file")               # e.g. "600", "644", "640"
    if [[ "$perms" != "600" ]]; then
        echo "INSECURE:$perms"
        return 1
    fi
    echo "OK"
    return 0
}

# ---------- db_check_connectivity ----------
# Purpose: Return 0 if a trivial query succeeds, non-zero otherwise
db_check_connectivity() {
    local creds_file="$1"
    timeout "$DB_CONNECT_TIMEOUT" mysql --defaults-extra-file="$creds_file" -N -B -e "SELECT 1;" >/dev/null 2>&1
    return $?
}

# ---------- get_replication_lag ----------
# Purpose: Return Seconds_Behind_Source (replication lag in seconds), or empty if not a replica / not available
get_replication_lag() {
    local creds_file="$1"
    # SHOW REPLICA STATUS returns one row of many columns in vertical \G format when piped through this connection;
    # grep isolates the one line we care about, awk grabs the value after the colon.
    timeout "$DB_CONNECT_TIMEOUT" mysql --defaults-extra-file="$creds_file" -e "SHOW REPLICA STATUS\G" 2>/dev/null |
        grep "Seconds_Behind_Source" | awk -F': ' '{print $2}'
}

# ---------- get_tablespace_usage_pct ----------
# Purpose: Return overall table-space usage as a percentage of a configured allocation ceiling
# (Simplified for teaching purposes: real environments often compare against a provisioned volume size instead)
get_tablespace_usage_pct() {
    local creds_file="$1"
    local allocated_gb="$2"

    local used_bytes
    used_bytes=$(timeout "$DB_CONNECT_TIMEOUT" mysql --defaults-extra-file="$creds_file" -N -B -e \
        "SELECT SUM(data_length + index_length) FROM information_schema.tables;" 2>/dev/null)

    [[ -z "$used_bytes" || "$used_bytes" == "NULL" ]] && { echo ""; return; }

    local allocated_bytes=$(( allocated_gb * 1024 * 1024 * 1024 ))
    echo $(( used_bytes * 100 / allocated_bytes ))     # Integer percentage
}

Line-by-Line Highlights

  • stat -c '%a' "$creds_file" — %a formats the permission bits as an octal number, exactly matching what chmod takes as input, making the comparison to "600" straightforward.
  • mysql --defaults-extra-file="$creds_file" ... — this single flag is what keeps the password out of both our script's arguments and the process list entirely; MySQL reads it directly from the file.
  • SHOW REPLICA STATUS\G | grep ... | awk -F': ' '{print $2}' — the \G vertical format prints each field as FieldName: value on its own line, which grep can isolate and awk (splitting on ": ") can cleanly extract.
  • [[ -z "$used_bytes" || "$used_bytes" == "NULL" ]] — defensive check for both an empty result (query failed silently) and SQL's literal NULL text (no tables found), treating both as "can't calculate" rather than crashing on invalid arithmetic.

🩺 Main Script

scripts/db_health_check.sh
#!/bin/bash
# =====================================================================
# db_health_check.sh
# NovaTrust Bank - Database Connectivity, Replication & Table-Space Check
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/db_health_check.conf"

INSTANCE_FILE="$SCRIPT_DIR/../config/db_instances.txt"
[[ -f "$INSTANCE_FILE" ]] || { echo "ERROR: Instance file not found: $INSTANCE_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/db_health_check_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Database health check run finished."' EXIT

log_message "INFO" "=== Starting database health check ==="

OVERALL_EXIT=0

while IFS=':' read -r instance_name creds_rel_path; do
    [[ -z "$instance_name" || "$instance_name" == \#* ]] && continue

    CREDS_FILE="$SCRIPT_DIR/$creds_rel_path"

    # ---------- Security gate: refuse insecure credential files outright ----------
    PERM_CHECK=$(verify_creds_permissions "$CREDS_FILE")
    if [[ "$PERM_CHECK" != "OK" ]]; then
        log_message "FAIL" "$instance_name: credentials file problem - $PERM_CHECK (expected file to exist with mode 600)"
        OVERALL_EXIT=2
        continue
    fi

    # ---------- Connectivity check ----------
    if ! db_check_connectivity "$CREDS_FILE"; then
        log_message "FAIL" "$instance_name: CONNECTION_FAILED"
        OVERALL_EXIT=2
        continue                                        # No point checking replication/table-space if we can't even connect
    fi
    log_message "PASS" "$instance_name: connectivity OK"

    # ---------- Replication lag check ----------
    LAG=$(get_replication_lag "$CREDS_FILE")
    if [[ -z "$LAG" ]]; then
        log_message "INFO" "$instance_name: not configured as a replica (no replication status) - skipping lag check"
    else
        if [[ "$LAG" -ge "$LAG_CRITICAL_SECONDS" ]]; then
            log_message "CRITICAL" "$instance_name: replication lag ${LAG}s (threshold ${LAG_CRITICAL_SECONDS}s)"
            OVERALL_EXIT=2
        elif [[ "$LAG" -ge "$LAG_WARN_SECONDS" ]]; then
            log_message "WARNING" "$instance_name: replication lag ${LAG}s (threshold ${LAG_WARN_SECONDS}s)"
            [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
        else
            log_message "PASS" "$instance_name: replication lag ${LAG}s (healthy)"
        fi
    fi

    # ---------- Table-space usage check (assumes a 100GB provisioned ceiling for this example) ----------
    TABLESPACE_PCT=$(get_tablespace_usage_pct "$CREDS_FILE" 100)
    if [[ -z "$TABLESPACE_PCT" ]]; then
        log_message "WARN" "$instance_name: could not calculate table-space usage"
    elif [[ "$TABLESPACE_PCT" -ge "$TABLESPACE_CRITICAL_PCT" ]]; then
        log_message "CRITICAL" "$instance_name: table-space usage ${TABLESPACE_PCT}%"
        OVERALL_EXIT=2
    elif [[ "$TABLESPACE_PCT" -ge "$TABLESPACE_WARN_PCT" ]]; then
        log_message "WARNING" "$instance_name: table-space usage ${TABLESPACE_PCT}%"
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    else
        log_message "PASS" "$instance_name: table-space usage ${TABLESPACE_PCT}%"
    fi

done < "$INSTANCE_FILE"

log_message "INFO" "=== Database health check complete ==="
exit $OVERALL_EXIT

LineExplanation

📄 README.md

README.md
# NovaTrust Bank - Database Health Check

## Usage
    ./scripts/db_health_check.sh

## Security Requirements (MANDATORY)
- Every file in creds/ MUST be chmod 600, owned by the account running this script.
- The creds/ directory MUST be listed in .gitignore. Never commit real credentials.
- The database account used (monitor_svc) MUST be read-only (SELECT, REPLICATION CLIENT).

## Checks Performed
1. Connectivity (SELECT 1)
2. Replication lag in seconds (SHOW REPLICA STATUS) - skipped gracefully on non-replica instances
3. Table-space usage percentage (information_schema)

## Exit Codes
    0 = All checks passed
    1 = At least one WARNING
    2 = At least one CRITICAL, CONNECTION_FAILED, or credentials security violation

🔄 What Happens Internally

  1. The permission gate runs before anything touches the network — refusing to even attempt a connection with insecure credentials is a deliberate "fail closed" security posture.
  2. Each mysql invocation is its own separate process, spawned fresh for connectivity, replication, and table-space queries — there's no persistent database session held open across the script's lifetime.
  3. --defaults-extra-file is read directly by the mysql client itself, not by our Bash script — Bash never sees or holds the password in any of its own variables at all.
  4. Connection failure short-circuits via continue, exactly like Project 2's unreachable-host handling — the same defensive pattern applied to a new kind of resource.

🛡️ Production Best Practices

Never Pass Secrets as Arguments

Command-line arguments are visible to other users on the same box via ps — always use a credentials file or environment variable instead.

Fail Closed on Insecure Permissions

A script should refuse to proceed with a misconfigured credentials file rather than optimistically continuing — this is the security equivalent of the "never downgrade a failure" rule from earlier projects.

Read-Only Monitoring Accounts

The database account used for health checks should never have write access — least privilege applies to service accounts just as much as to human users.

Separate Connection Failure from Data Failure

"Can't connect" and "connected but replication is broken" require completely different responses — never conflate them into one status.

Keep Credentials Out of Version Control

.gitignore the entire credentials directory from day one of the project, not as an afterthought.

Timeout Every Database Call

A database under load can hang a connection just as easily as an unresponsive SSH host or TLS endpoint — apply the same discipline consistently.

🎤 Interview Preparation

Scenario: Replication lag shows 0 seconds even though you know the replica is genuinely behind. What could be wrong?
The replica may not be running as a replica at all in this connection's view (perhaps this connection is actually reaching the primary due to a DNS/config error), or replication itself may be stopped entirely rather than lagging — Seconds_Behind_Source can show NULL (not 0) when replication is stopped, which our simplified script would need to explicitly check for as a further edge case.
Production Support: The script exits 2 (CRITICAL) but the log shows only a credentials permission failure, no actual database check ran. Is this correctly categorized?
Yes — a security control failure is deliberately treated with the same severity as a critical operational failure, on the principle that we'd rather over-escalate a security gap than silently proceed with a leaky credential.
Shell Scripting: Why use --defaults-extra-file instead of setting the MYSQL_PWD environment variable?
Both avoid the command-line-argument exposure problem, but MYSQL_PWD is explicitly documented by MySQL itself as insecure on some systems (visible via environment inspection of the process); --defaults-extra-file with a properly permissioned file is the more consistently recommended approach.
Troubleshooting: stat -c '%a' gives different output on a colleague's Mac. Why?
BSD-based stat (used on macOS) has entirely different flag syntax than GNU stat (used on Linux); this script targets Linux production servers specifically, so this is a known, acceptable platform constraint rather than a bug.
Manager Round: Why does a "read-only monitoring account" matter if we trust our own script's code?
Least privilege limits blast radius if the credentials file itself is ever compromised or the script is ever run in an unintended way — trusting our own code doesn't eliminate the value of limiting what a leaked credential could actually do.
Architecture: Why check table-space usage via SQL (information_schema) rather than just checking OS-level disk usage on the database server, like Project 2 already does?
OS-level disk usage tells you about the whole filesystem, but table-space usage tells you specifically how much of the database's own logical capacity is consumed — a database can be nowhere near a disk-full condition while still approaching an application-level storage ceiling that matters for capacity planning.
Best Practice: Why does a primary database (non-replica) log an INFO message instead of a WARNING when replication status is unavailable?
A primary legitimately has no replication status to report — that's an expected, normal condition, not a problem; using WARNING here would create alert fatigue and train Ops to start ignoring warnings, which is worse than not checking at all.
Real Incident Discussion: What's the one design decision in this project that would have caught the stale-balance incident before a customer did?
The tiered replication-lag check itself, running every 10 minutes — the 51-hour lag would have crossed both WARNING (30s) and CRITICAL (120s) thresholds within minutes of first falling behind, days before a customer noticed anything.
