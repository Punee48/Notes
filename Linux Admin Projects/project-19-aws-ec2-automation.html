AWS EC2 Automation Using Bash

The monthly AWS bill arrived, and Finance couldn't explain where 30% of it was even coming from — because nobody could say which team owned which instance.

🎯 Level: Advanced 🧠 New Concepts: 10 🏗️ Environment: Linux / WSL + AWS CLI ⏱️ Duration: 3 hrs

📖 The Story — The Bill Nobody Could Explain

NovaTrust's cloud cost-allocation review hit a wall: roughly 30% of the monthly EC2 bill couldn't be attributed to any specific business unit, because a large number of running instances were simply missing the required CostCenter and Owner tags. Digging further turned up something worse — a test instance, launched eight months earlier for a since-completed proof-of-concept, was still running, untagged, and completely forgotten, quietly costing money the entire time.

Priya's assignment: "Every EC2 instance needs a CostCenter and an Owner tag, full stop — untagged spend is spend nobody's accountable for. I want a script that audits every instance for these required tags, flags anything untagged as running suspiciously long, and can optionally fix simple cases automatically — but treat every AWS API call that changes something exactly as carefully as we've treated destructive Bash operations all course long."

For the first time, we're not managing a Linux server directly — we're managing infrastructure itself through a cloud provider's own API, using Bash as the orchestration layer.
🔁 Reinforced from Projects 1–18
The mandatory dry-run pattern (Project 5), credential security discipline (Project 7), date-based age calculation (Project 3), and JSON parsing with jq (Projects 17-18) all return here applied to a cloud provider's API instead of a Linux host.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Audit all EC2 instances for required cost-allocation tags, and identify long-running untagged instances as likely forgotten/orphaned resources.

Customer Requirement

Finance needs every dollar of EC2 spend attributable to a specific cost center and owner; Cloud Operations needs to catch forgotten resources before they run for months unnoticed.

Banking Scenario

NovaTrust runs a growing subset of workloads on AWS EC2 alongside its traditional on-premises Core Banking infrastructure, with tagging policy requiring CostCenter and Owner on every instance.

Existing Manual Process / Prior Automation Gap

Tagging was left to individual engineers' discipline at instance-launch time, with no independent verification step afterward — exactly how both the untagged-spend and the forgotten instance both went unnoticed for months.

Problems With Relying on Launch-Time Discipline Alone

A missed tag at launch time, with no follow-up audit, persists silently forever — nothing about a running, untagged instance is inherently visible as a problem until someone specifically goes looking.

Business Impact & Risk

Unattributable cloud spend undermines financial accountability and budget planning; forgotten long-running instances represent pure waste with zero business value being delivered.

Why Automation Is Required

Only a script continuously auditing every instance's actual tags against policy can catch a tagging gap immediately, rather than relying on the next ad-hoc cost review to stumble across it months later.

Solution Design

Query all running instances via the AWS CLI, check each for required tags, calculate running age for any non-compliant instance, and optionally apply a default remediation tag — with AWS's own --dry-run flag and our course-standard dry-run pattern both required before any real tagging change.

Project Scope

In scope: tag-compliance auditing, running-age calculation for untagged instances, and optional dry-run-gated auto-remediation of a default tag. Out of scope: automatically stopping or terminating suspected orphaned instances — a decision requiring human judgment, not automation.

Expected Outcome

A compliance report showing every instance's tag status and running age, clearly flagging long-running untagged instances as likely orphans, with a safe, dry-run-first path to apply corrective tags where appropriate.

🧠 New Bash Concepts for This Project

1. AWS CLI Credentials and Profiles

What: The AWS CLI reads credentials from ~/.aws/credentials (or environment variables, or an attached IAM role) — never as a command-line argument, for exactly the same reason Project 7 banned passing database passwords on the command line.
Why: Consistency with every credential-handling lesson so far: secrets belong in protected files or environment configuration, never in process arguments visible via ps.

2. Server-Side Filtering with --filters (Reinforced Project 18 Pattern)

What: aws ec2 describe-instances --filters "Name=instance-state-name,Values=running" filters at the AWS API level, only returning running instances — the same principle as Project 18's --field-selector.

3. JMESPath Queries with --query

What: The AWS CLI's own built-in query language, e.g. --query 'Reservations[].Instances[].[InstanceId,LaunchTime]', extracts and reshapes specific fields directly, similar in spirit to jsonpath from Project 18.
Why: For simpler extractions, --query avoids needing jq at all; for more complex logic (like checking whether a specific tag key exists), piping full --output json into jq is often clearer — the same "pick the right tool" judgment call from Project 18.

4. The Nested Reservations → Instances Structure

What: describe-instances' JSON wraps instances inside a Reservations array, itself containing an Instances array — a two-level nesting that must be flattened, typically with jq '.Reservations[].Instances[]'.
Why: This nested structure reflects how AWS originally grouped instances launched together in one API call — a historical quirk of the API that every script working with describe-instances output must account for.

5. Checking for a Specific Tag Key's Presence

What: jq -r --arg key "CostCenter" '.Tags[]? | select(.Key==$key) | .Value' — reusing Project 18's --arg and select() pattern, now checking AWS's Tags array (a list of {Key, Value} objects) instead of Kubernetes node conditions.
Why: AWS tags are stored as an array of key-value objects, not a simple map — the same array-filtering technique from Project 18 applies directly.

6. AWS's Own --dry-run Flag

What: Most AWS CLI mutating commands (including create-tags) support a native --dry-run flag that validates the call and permissions without actually making the change, returning a specific "would have succeeded" or a permissions error.
Why: This is a genuinely different guarantee than our own course-standard -n dry-run pattern — AWS's version actually round-trips to the API to validate IAM permissions, while our own dry-run flag simply skips the call locally; using both together is meaningfully safer than either alone.

7. Applying Tags with aws ec2 create-tags

What: aws ec2 create-tags --resources i-0123456789abcdef0 --tags Key=CostCenter,Value=UNASSIGNED-PENDING-REVIEW applies a tag to a specific instance by ID.
Why: This is the actual remediation action — deliberately applying an obviously-placeholder value (never a guessed real cost center) so a human still has to follow up and assign the correct one.

8. Calculating Running Age from Launch Time

What: AWS returns LaunchTime as an ISO 8601 timestamp; converting it to epoch seconds with date -d (reinforcing Project 6 and Project 3's date-arithmetic techniques) and subtracting from now gives running age in days.
Why: "Untagged" alone doesn't indicate urgency — "untagged AND running for 240 days" is what specifically identifies a likely-forgotten resource worth flagging distinctly.

9. AWS CLI Output Formats (--output json, Reinforced Choice)

What: Explicitly requesting --output json guarantees consistent, parseable output regardless of any user or environment default configuration (which might otherwise default to the human-oriented table format).
Why: Never rely on an ambient default output format for a script meant to run unattended via cron — always specify it explicitly, the same defensive principle behind always specifying full paths in cron entries since Project 1.

10. Least-Privilege IAM Roles for Automation (Reinforced Judgment)

What: The audit path only needs ec2:DescribeInstances (read-only); the remediation path additionally needs ec2:CreateTags — these should ideally be separate IAM roles/policies, not one broad set of permissions used for everything.
Why: The exact same least-privilege principle from Project 7's read-only database account and Project 10's scoped service account, now applied to cloud IAM permissions.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - EC2 tag audit helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_running_instances ----------
# Purpose: Return flattened JSON, one line per instance, for every running EC2 instance
get_running_instances() {
    aws ec2 describe-instances \
        --profile "$AWS_PROFILE" --region "$AWS_REGION" \
        --filters "Name=instance-state-name,Values=running" \
        --output json 2>/dev/null |
        jq -c '.Reservations[].Instances[]'
}

# ---------- get_tag_value ----------
# Purpose: Return a specific tag's value for an instance, or empty if not present
get_tag_value() {
    local instance_json="$1"
    local tag_key="$2"
    echo "$instance_json" | jq -r --arg key "$tag_key" '.Tags[]? | select(.Key==$key) | .Value'
}

# ---------- calculate_running_age_days ----------
calculate_running_age_days() {
    local launch_time="$1"
    local launch_epoch now_epoch
    launch_epoch=$(date -d "$launch_time" '+%s' 2>/dev/null) || { echo "0"; return; }
    now_epoch=$(date '+%s')
    echo $(( (now_epoch - launch_epoch) / 86400 ))
}

# ---------- apply_remediation_tag ----------
# Purpose: Apply the remediation tag, gated by AWS's own --dry-run first
# Returns 0 on success, 1 on failure (including a failed AWS dry-run check)
apply_remediation_tag() {
    local instance_id="$1"
    local tag_key="$2"

    # Step 1: AWS's own dry-run - actually validates IAM permissions against the real API
    if ! aws ec2 create-tags --profile "$AWS_PROFILE" --region "$AWS_REGION" \
        --resources "$instance_id" --tags "Key=${tag_key},Value=${REMEDIATION_TAG_VALUE}" \
        --dry-run 2>&1 | grep -q "DryRunOperation"; then
        log_message "FAIL" "$instance_id: AWS dry-run check failed for tag '$tag_key' - insufficient permissions or invalid request"
        return 1
    fi

    # Step 2: The real call, only reached after the dry-run above succeeded
    aws ec2 create-tags --profile "$AWS_PROFILE" --region "$AWS_REGION" \
        --resources "$instance_id" --tags "Key=${tag_key},Value=${REMEDIATION_TAG_VALUE}" >/dev/null 2>&1
}

Line-by-Line Highlights

  • jq -c '.Reservations[].Instances[]' — -c (compact) outputs one instance object per line rather than pretty-printed multi-line JSON, making it easy to loop over with a simple while read in the main script.
  • .Tags[]? | select(.Key==$key) — the ? guards against an instance with no Tags field at all (an untagged instance may omit the key entirely rather than have an empty array), preventing a jq error on that edge case.
  • grep -q "DryRunOperation" — AWS's dry-run success case returns a specific error message containing this exact text (a quirk of how AWS signals "this would have worked"); checking for it is the standard way scripts detect a successful AWS dry-run.
  • The remediation tag value UNASSIGNED-PENDING-REVIEW is deliberately an obvious placeholder, never a guessed real value — remediation here means "flag for human follow-up," not "silently guess the correct cost center."

🩺 Main Script

scripts/ec2_tag_audit.sh
#!/bin/bash
# =====================================================================
# ec2_tag_audit.sh
# NovaTrust Bank - EC2 Tag Compliance Audit with Optional Remediation
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/ec2_tag_audit.conf"

REMEDIATE="false"
DRY_RUN="true"                     # Default to dry-run for safety; must be explicitly turned off
while getopts "rlh" opt; do
    case $opt in
        r) REMEDIATE="true" ;;
        l) DRY_RUN="false" ;;       # -l = "live" - explicit opt-in required to make real changes
        h) echo "Usage: $0 [-r] [-l]   (-r = attempt remediation, -l = live mode, otherwise dry-run)"; exit 0 ;;
        *) echo "Usage: $0 [-r] [-l]"; exit 1 ;;
    esac
done

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/ec2_tag_audit_${TODAY}.log"
CSV_REPORT="$SCRIPT_DIR/$REPORT_DIR/ec2_tag_compliance_${TODAY}.csv"
mkdir -p "$(dirname "$LOG_FILE")" "$(dirname "$CSV_REPORT")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "EC2 tag audit run finished. Remediate: $REMEDIATE, Dry-run: $DRY_RUN"' EXIT

echo "instance_id,name,launch_time,age_days,missing_tags,status" > "$CSV_REPORT"

log_message "INFO" "=== Starting EC2 tag compliance audit (remediate=$REMEDIATE, dry-run=$DRY_RUN) ==="

COMPLIANT=0; NON_COMPLIANT=0; LIKELY_ORPHAN=0
OVERALL_EXIT=0

while IFS= read -r instance_json; do
    [[ -z "$instance_json" ]] && continue

    INSTANCE_ID=$(echo "$instance_json" | jq -r '.InstanceId')
    LAUNCH_TIME=$(echo "$instance_json" | jq -r '.LaunchTime')
    NAME=$(get_tag_value "$instance_json" "Name")
    [[ -z "$NAME" ]] && NAME="(unnamed)"

    MISSING_TAGS=()
    for required_tag in "${REQUIRED_TAGS[@]}"; do
        value=$(get_tag_value "$instance_json" "$required_tag")
        [[ -z "$value" ]] && MISSING_TAGS+=("$required_tag")
    done

    if [[ ${#MISSING_TAGS[@]} -eq 0 ]]; then
        log_message "PASS" "$INSTANCE_ID ($NAME): all required tags present"
        echo "$INSTANCE_ID,\"$NAME\",$LAUNCH_TIME,0,,COMPLIANT" >> "$CSV_REPORT"
        ((COMPLIANT++))
        continue
    fi

    AGE_DAYS=$(calculate_running_age_days "$LAUNCH_TIME")
    MISSING_LIST=$(IFS=,; echo "${MISSING_TAGS[*]}")

    if [[ "$AGE_DAYS" -ge "$ORPHAN_AGE_DAYS" ]]; then
        log_message "FAIL" "$INSTANCE_ID ($NAME): LIKELY ORPHAN - running ${AGE_DAYS}d, missing: $MISSING_LIST"
        echo "$INSTANCE_ID,\"$NAME\",$LAUNCH_TIME,$AGE_DAYS,\"$MISSING_LIST\",LIKELY_ORPHAN" >> "$CSV_REPORT"
        ((LIKELY_ORPHAN++))
        OVERALL_EXIT=2
    else
        log_message "WARN" "$INSTANCE_ID ($NAME): non-compliant - running ${AGE_DAYS}d, missing: $MISSING_LIST"
        echo "$INSTANCE_ID,\"$NAME\",$LAUNCH_TIME,$AGE_DAYS,\"$MISSING_LIST\",NON_COMPLIANT" >> "$CSV_REPORT"
        ((NON_COMPLIANT++))
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    fi

    if [[ "$REMEDIATE" == "true" ]]; then
        for missing_tag in "${MISSING_TAGS[@]}"; do
            if [[ "$DRY_RUN" == "true" ]]; then
                log_message "INFO" "[DRY-RUN] Would apply tag '$missing_tag' to $INSTANCE_ID"
            else
                if apply_remediation_tag "$INSTANCE_ID" "$missing_tag"; then
                    log_message "PASS" "$INSTANCE_ID: applied placeholder tag '$missing_tag'"
                else
                    log_message "FAIL" "$INSTANCE_ID: failed to apply tag '$missing_tag'"
                fi
            fi
        done
    fi

done < <(get_running_instances)

log_message "INFO" "=== SUMMARY: Compliant=$COMPLIANT | Non-Compliant=$NON_COMPLIANT | Likely Orphans=$LIKELY_ORPHAN ==="
log_message "INFO" "CSV report: $CSV_REPORT"

exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
DRY_RUN="true" as the default, before any flag parsingFollowing Project 5's house rule: any script capable of changing real infrastructure defaults to safe (dry-run) behavior, requiring an explicit -l to go live — never the other way around.
MISSING_TAGS=() then looping REQUIRED_TAGSChecks every required tag independently and collects all missing ones, rather than stopping at the first missing tag found — giving a complete picture in one pass.
if [[ "$AGE_DAYS" -ge "$ORPHAN_AGE_DAYS" ]]; then ... else ... fiThe same non-compliant instance can be classified two different ways depending on age — this is the specific distinction Acceptance Criterion 3 requires, and it directly drives the differing exit-code severity.
Remediation loop runs regardless of whether it's an orphan or merely non-compliantRemediation (tagging) is a response to "missing tags," not specifically to "orphan status" — the two concerns (severity classification, and remediation eligibility) are kept independent.
done < <(get_running_instances)Process substitution keeps the loop in the current shell so COMPLIANT, NON_COMPLIANT, and LIKELY_ORPHAN counters correctly accumulate — the same pattern reinforced since Project 12.

    0 = All instances compliant

🔄 What Happens Internally

  1. Two independent dry-run gates protect the remediation path: our own course-standard DRY_RUN variable (checked first, purely locally) and AWS's own --dry-run flag (which actually round-trips to the API) — either one alone would be a real safety gap.
  2. describe-instances' nested Reservations[].Instances[] structure is flattened once, centrally, inside get_running_instances, so the main script's loop works with clean, individual instance objects.
  3. Every required tag is checked independently and fully (collecting all missing tags, not stopping at the first) before any classification or remediation decision is made — giving both the report and any remediation action complete information.
  4. Remediation, when enabled, applies a deliberately fake placeholder value rather than attempting to guess a correct one — the script's job is flagging and creating a paper trail for human follow-up, never silently inventing business data.

🛡️ Production Best Practices

Never Pass Cloud Credentials as Arguments

Use named profiles, environment variables, or attached IAM roles — never embed keys directly in a script or pass them on the command line.

Layer Both Dry-Run Mechanisms

A cloud provider's own --dry-run (validating real permissions) and your script's own dry-run flag (skipping the call entirely) provide different, complementary safety guarantees — use both for any mutating cloud action.

Placeholder, Never Guessed, Remediation Values

Auto-remediation should flag and create an obvious paper trail for human follow-up, never silently invent plausible-looking business data like a cost center.

Least-Privilege IAM Per Function

Separate read-only audit permissions from tagging/remediation permissions — a script's blast radius should never exceed what its current task actually requires.

Always Specify Output Format Explicitly

Never rely on an ambient CLI default for output format in an unattended script — explicit --output json guarantees consistent, parseable results regardless of environment configuration.

Age-Aware Classification Beats Binary Compliance

A brand-new untagged instance and one running for eight months both technically violate policy, but represent very different urgency — factor age into severity, not just presence/absence.

Scenario: The audit reports an instance as LIKELY_ORPHAN, but it's actually a legitimate long-running production database server that was simply never tagged at launch. How does this project's design handle that gracefully?
The classification is a flag for human review, not an automatic termination decision — remediation (if enabled) only applies an obvious placeholder tag prompting someone to assign the correct real value, and the script deliberately never stops or terminates any instance, leaving that judgment call entirely to a human.
Production Support: The dry-run remediation preview shows "would apply" for every instance, but the live run then fails every single tag application. What's the likely cause?
The IAM permissions used for dry-run testing versus the live run may actually differ (different profile, or a policy change between runs), or more likely, the script's own local dry-run check was never actually validated against AWS's own --dry-run flag at all — only the live call's real permission requirement surfaced the gap.
Shell Scripting: Why check for the AWS dry-run flag's success via grep -q "DryRunOperation" instead of checking the command's exit code directly?
AWS's --dry-run deliberately returns a non-zero exit code even on "success," specifically because the request was intentionally not completed - the DryRunOperation text in the error message is how AWS distinguishes "this would have worked" from "this would have failed anyway," making the exit code alone insufficient to interpret correctly.
Troubleshooting: get_running_instances returns nothing at all, even though the AWS Console clearly shows running instances. What would you check first?
Confirm the AWS_REGION in config matches the region the instances are actually running in — the AWS CLI only queries the region specified (or its configured default), and instances in a different region are simply invisible to that particular API call, not an error condition.
Manager Round: Why does remediation apply an obvious placeholder value instead of trying to infer the correct CostCenter from some other signal (like the instance's VPC or security group)?
Any inference carries real risk of being wrong in a way that's silently accepted as correct, whereas an obvious placeholder guarantees a human must actively review and correct it — for financial cost-allocation data specifically, a visibly-wrong placeholder is safer than a plausible-but-incorrect guess.
Architecture: Why does this project deliberately stop short of automatically stopping or terminating suspected orphaned instances?
Determining whether a long-running untagged instance is truly abandoned versus simply under-documented but legitimately important requires business context and judgment a script cannot safely infer — automating detection is appropriate; automating termination based on a tag-compliance heuristic alone would risk real, possibly severe, business disruption.
Best Practice: Why use separate IAM permissions for audit mode versus remediation mode rather than one role with both permissions always available?
If the audit-only path (which should run unattended on a schedule) is ever compromised or misconfigured, limiting it to read-only DescribeInstances access means it structurally cannot make any real change to infrastructure, regardless of any bug in the script's own logic - the same defense-in-depth principle behind every least-privilege decision throughout this course.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the eight-month-forgotten test instance much sooner?
Combining tag-absence with running-age into one LIKELY_ORPHAN classification, checked on a daily schedule - the instance would have crossed the 90-day orphan threshold and appeared prominently in the very first report after that point, rather than remaining invisible for eight months until a manual cost review happened to notice it.
