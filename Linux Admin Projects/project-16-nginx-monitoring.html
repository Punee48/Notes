Project 16 of 30 · Web Tier

Nginx Monitoring

Nginx itself was fast and healthy. One backend behind it wasn't — and every proxied login request quietly came back as a 502.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL + Nginx stub_status ⏱️ Duration: 3 hrs

📖 The Story — The Reverse Proxy That Looked Perfectly Fine

NovaTrust's online banking portal sits behind Nginx as a reverse proxy, forwarding dynamic requests to a pool of application backend servers (and serving static assets directly). One backend server in that pool developed a slow memory leak and began timing out on every request it received — but Nginx itself remained completely healthy by every conventional measure: low connection count, fast responses for static content, low CPU. Customers hitting the affected backend simply saw a 502 Bad Gateway, seemingly at random, roughly a quarter of the time.

Priya's framing: "Nginx being healthy and Nginx's upstream backends being healthy are two different questions, and open-source Nginx doesn't give us a clean built-in status for the second one the way it does for the first. I want connection-state monitoring from Nginx's own status module, and I want us actively watching the error log for upstream failures — because that log is the only place this specific kind of problem actually shows up."

Today parallels Project 15's Apache work, but with a twist: Nginx's status format is completely different, and its most important failure mode here isn't visible in status metrics at all — only in its error log.
🔁 Reinforced from Projects 1–15
Project 15's status-endpoint pattern, Project 5's grep/log-analysis techniques, and tiered classification all return here, adapted to Nginx's different status format and a log-based detection signal.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Monitor Nginx's own connection-state health and detect upstream backend failures via error-log analysis, since open-source Nginx exposes no built-in per-upstream health status.

Customer Requirement

Ops needs to know when Nginx is proxying to a failing backend, distinctly from Nginx's own connection-handling health.

Banking Scenario

Nginx reverse-proxies dynamic requests to a pool of Core Banking application backends while directly serving static assets for the online banking portal.

Existing Manual Process / Prior Automation Gap

Project 15 built comparable monitoring for Apache; Nginx has never had equivalent coverage, and its most relevant failure mode here — a specific bad upstream — isn't captured by connection-state metrics at all.

Problems With the Current Gap

A single bad upstream server produces intermittent 502/504 errors invisible in Nginx's aggregate connection counts — only the error log records each individual upstream failure as it happens.

Business Impact & Risk

Intermittent gateway errors erode customer trust unpredictably and are notoriously hard to diagnose reactively, since "sometimes it works" symptoms rarely point clearly at their root cause.

Why Automation Is Required

Only continuous, automated error-log scanning can catch a pattern of repeated upstream failures in near real time — a human periodically glancing at logs would never catch an intermittent, low-frequency problem reliably.

Solution Design

Query Nginx's stub_status module for connection-state health, and separately scan the error log for upstream-failure patterns within a recent time window, counting occurrences and identifying which specific upstream address is implicated.

Project Scope

In scope: connection-state monitoring via stub_status, and upstream-failure detection via error-log pattern matching within a time window. Out of scope: automatic upstream removal from the pool (a load-balancer-level remediation concern, not monitoring).

Expected Outcome

A report showing Nginx's connection health alongside a specific count of recent upstream failures, by upstream address, catching the "which backend keeps failing" question the status module alone can never answer.

🧠 New Bash Concepts for This Project

1. Nginx's stub_status Format (Different from Apache's)

What: Nginx's status output is multi-line, positional text, not Key: Value pairs:

Active connections: 42
server accepts handled requests
 18293 18293 55012
Reading: 3 Writing: 12 Waiting: 27

Why: Unlike Apache's easily-grep-able Field: Value format, Nginx requires positional parsing — the numbers on line 3 have no labels at all, and line 4 packs three labeled values onto one line.

2. Positional Field Extraction with awk (Reinforced, New Context)

What: awk 'NR==3 {print $3}' grabs the third space-separated field specifically from the third line of output — since line 3's numbers (accepts, handled, total requests) have no labels, position is the only way to identify them.
Why: This is a different parsing challenge than every prior project's labeled-field extraction — a good example of when awk's positional field access is the right tool over grep.

3. Extracting Multiple Labeled Values from One Line

What: Reading: 3 Writing: 12 Waiting: 27 needs three separate grep -oP extractions from the same line, unlike Apache's one-value-per-line format.
Why: grep -oP 'Reading: \K[0-9]+', repeated with each label, cleanly isolates each of the three values regardless of their shared line.

4. Scanning Logs Within a Recent Time Window

What: Rather than scanning an entire (potentially huge) log file, filtering to only lines from roughly the last N minutes — using the log's own timestamps compared against a computed cutoff time.
Why: A months-old upstream failure is irrelevant to right-now's health; scanning the whole file on every run is also wasteful at scale.

5. Computing a Time Cutoff for Log Filtering

What: CUTOFF=$(date -d "-5 minutes" '+%Y/%m/%d %H:%M:%S') computes "5 minutes ago" in the same timestamp format Nginx writes to its error log, so a simple string comparison can filter recent lines.
Why: Reinforces Project 3 and Project 6's date-arithmetic techniques, now used to build a log-filtering boundary rather than a certificate or trend comparison.

6. Extracting an Upstream Address from a Log Line (grep -oP, Reinforced)

What: Nginx error-log lines for upstream failures typically include upstream: "http://10.0.4.22:8080/..." — extracting just the host:port portion with a targeted grep -oP pattern.
Why: Knowing "an upstream failed" is far less actionable than knowing exactly which upstream server failed, repeatedly.

7. Counting Occurrences Per Unique Value (sort | uniq -c)

What: Piping a list of extracted upstream addresses through sort | uniq -c produces a count of how many times each distinct address appeared — a classic, extremely common Bash idiom for exactly this kind of tallying.
Why: This is the cleanest way to answer "which upstream failed the most times in this window" without writing manual counting logic.

8. Nginx Configuration Testing (nginx -t, Parallel to Project 15)

What: nginx -t validates configuration syntax without reloading — Nginx's direct equivalent to Apache's apachectl configtest from Project 15.
Why: The same "validate before reload" discipline applies regardless of which web server is in use.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Nginx monitoring helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- fetch_stub_status ----------
fetch_stub_status() {
    curl -s --connect-timeout "$HTTP_CONNECT_TIMEOUT" --max-time "$HTTP_MAX_TIME" "$STATUS_URL" 2>/dev/null
}

# ---------- parse_active_connections ----------
parse_active_connections() {
    local raw_status="$1"
    echo "$raw_status" | grep "Active connections:" | grep -oP '[0-9]+'
}

# ---------- parse_connection_state ----------
# Purpose: Extract Reading/Writing/Waiting from the one line that packs all three together
# Arguments: $1 = raw status, $2 = state name (Reading/Writing/Waiting)
parse_connection_state() {
    local raw_status="$1"
    local state_name="$2"
    echo "$raw_status" | grep -oP "${state_name}: \K[0-9]+"
}

# ---------- compute_log_cutoff ----------
# Purpose: Return a timestamp string matching Nginx's error log format for "N minutes ago"
compute_log_cutoff() {
    date -d "-${WINDOW_MINUTES} minutes" '+%Y/%m/%d %H:%M:%S'
}

# ---------- get_recent_upstream_failures ----------
# Purpose: Return per-upstream failure counts (as "count address" lines) within the recent window
get_recent_upstream_failures() {
    local cutoff="$1"
    [[ -f "$NGINX_ERROR_LOG" ]] || return

    # awk compares each line's leading timestamp against the cutoff string - works because the
    # YYYY/MM/DD HH:MM:SS format sorts correctly as a plain string comparison, no date parsing needed per line
    awk -v cutoff="$cutoff" '$0 >= cutoff' "$NGINX_ERROR_LOG" |
        grep -i "upstream" |
        grep -oP 'upstream: "http://\K[0-9.]+:[0-9]+' |
        sort | uniq -c | sort -rn
}

Line-by-Line Highlights

  • grep "Active connections:" | grep -oP '[0-9]+' — a two-stage extraction: first isolate the right line, then pull just its number, avoiding any risk of accidentally matching a digit elsewhere in the full status output.
  • grep -oP "${state_name}: \K[0-9]+" — reused for Reading, Writing, and Waiting by simply passing a different state_name argument each time, avoiding three nearly-identical hardcoded functions.
  • awk -v cutoff="$cutoff" '$0 >= cutoff' — because Nginx's default log timestamp format (YYYY/MM/DD HH:MM:SS) happens to sort correctly as plain text, a simple string comparison works as a time filter without needing to parse each line's date individually — a neat, efficient shortcut worth recognizing.
  • sort | uniq -c | sort -rn — three chained commands: alphabetically sort the addresses (required before uniq -c can group them correctly), count occurrences of each, then re-sort numerically descending so the worst offender appears first.
📌 Why the String-Comparison Timestamp Trick Works Here
This only works because Nginx's default timestamp format is zero-padded and ordered from largest to smallest unit (year, month, day...) — the same property that makes YYYYMMDD filenames sort correctly throughout this entire course, going all the way back to Project 1's log-file naming.

🩺 Main Script

scripts/nginx_monitor.sh
#!/bin/bash
# =====================================================================
# nginx_monitor.sh
# NovaTrust Bank - Nginx Connection Health + Upstream Failure Detection
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/nginx_monitor.conf"

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/nginx_monitor_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Nginx monitor run finished."' EXIT

log_message "INFO" "=== Starting Nginx health check ==="

OVERALL_EXIT=0

# ---------- Signal 1: Connection state via stub_status ----------
RAW_STATUS=$(fetch_stub_status)
if [[ -z "$RAW_STATUS" ]]; then
    log_message "FAIL" "Could not reach Nginx stub_status endpoint: $STATUS_URL"
    OVERALL_EXIT=2
else
    ACTIVE=$(parse_active_connections "$RAW_STATUS")
    READING=$(parse_connection_state "$RAW_STATUS" "Reading")
    WRITING=$(parse_connection_state "$RAW_STATUS" "Writing")
    WAITING=$(parse_connection_state "$RAW_STATUS" "Waiting")

    if [[ -z "$ACTIVE" ]]; then
        log_message "WARN" "Could not parse Active connections from status response"
    elif [[ "$ACTIVE" -ge "$ACTIVE_CONN_CRITICAL" ]]; then
        log_message "FAIL" "Active connections CRITICAL: $ACTIVE (reading=$READING writing=$WRITING waiting=$WAITING)"
        OVERALL_EXIT=2
    elif [[ "$ACTIVE" -ge "$ACTIVE_CONN_WARN" ]]; then
        log_message "WARN" "Active connections elevated: $ACTIVE (reading=$READING writing=$WRITING waiting=$WAITING)"
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    else
        log_message "PASS" "Active connections healthy: $ACTIVE (reading=$READING writing=$WRITING waiting=$WAITING)"
    fi
fi

# ---------- Signal 2: Upstream failure detection from the error log ----------
CUTOFF=$(compute_log_cutoff)
log_message "INFO" "Scanning error log for upstream failures since $CUTOFF"

FAILURE_LINES=$(get_recent_upstream_failures "$CUTOFF")

if [[ -z "$FAILURE_LINES" ]]; then
    log_message "PASS" "No upstream failures detected in the last $WINDOW_MINUTES minute(s)"
else
    while read -r count address; do
        [[ -z "$address" ]] && continue

        if [[ "$count" -ge "$UPSTREAM_FAIL_CRITICAL_COUNT" ]]; then
            log_message "FAIL" "Upstream $address failed $count times in the last $WINDOW_MINUTES min - CRITICAL"
            OVERALL_EXIT=2
        elif [[ "$count" -ge "$UPSTREAM_FAIL_WARN_COUNT" ]]; then
            log_message "WARN" "Upstream $address failed $count times in the last $WINDOW_MINUTES min - WARNING"
            [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
        else
            log_message "INFO" "Upstream $address had $count failure(s) - below threshold, noted only"
        fi
    done <<< "$FAILURE_LINES"
fi

log_message "INFO" "=== Nginx health check complete ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
while read -r count address; do ... done <<< "$FAILURE_LINES"The here-string feeds the multi-line uniq -c output into the loop; read naturally splits each line's leading count and trailing address into the two named variables.
[[ -z "$address" ]] && continueGuards against a possible trailing blank line in the failure-lines output being misinterpreted as a real (empty) upstream entry.
Per-upstream tiered classification inside the loopEach upstream address gets its own independent WARNING/CRITICAL/below-threshold verdict — a single badly-behaving backend is identified specifically, not just folded into one vague "some upstream failed" message.
Two entirely independent signal blocks (connections, then upstream failures)Mirrors Project 15's structure exactly — each signal can independently escalate OVERALL_EXIT, and neither masks the other.

📌 Keep the Cron Interval and WINDOW_MINUTES Aligned
If the cron interval were longer than WINDOW_MINUTES, there would be gaps in error-log coverage between runs; keeping them equal (both 5 minutes here) ensures continuous coverage with no blind spots between checks.

📄 README.md

README.md
# NovaTrust Bank - Nginx Monitoring

## Requirements
- stub_status module enabled, restricted to localhost/internal access
- Read access to the Nginx error log

## Usage
    ./scripts/nginx_monitor.sh

## What Gets Checked
1. Connection state (Active/Reading/Writing/Waiting) via stub_status
2. Upstream failures in the error log within the last WINDOW_MINUTES, per upstream address

## Exit Codes
    0 = Connections healthy, no significant upstream failures
    1 = Elevated connections OR one or more upstreams at WARNING failure count
    2 = Critical connections OR status unreachable OR an upstream at CRITICAL failure count

🔄 What Happens Internally

  1. Two structurally different data sources feed one script: a live HTTP status query for connection state, and a log-file scan for upstream failures — reinforcing that "monitoring" isn't always one uniform technique even within a single check.
  2. The timestamp string-comparison trick in awk avoids the overhead of parsing every single log line's date into epoch seconds individually — a meaningful efficiency choice on a log file that could contain many thousands of lines.
  3. sort | uniq -c | sort -rn runs as three separate processes chained by pipes, each doing one focused job — a clean example of Unix's "small tools composed together" philosophy that's been implicit throughout this entire course.
  4. Per-upstream classification happens inside a loop reading pre-aggregated data, not by re-scanning the log once per upstream — the expensive log scan happens exactly once per run, regardless of how many distinct upstreams show up in the results.

🛡️ Production Best Practices

Treat Error Logs as a First-Class Monitoring Source

Where a tool exposes no structured metric for a failure mode, its own logs are often the only reliable signal — scan them deliberately, not just reactively during an incident.

Name the Specific Failing Component

"An upstream failed" is far less useful than "10.0.4.22:8080 failed 9 times" — always identify the specific resource, not just the category of problem.

Bound Log Scans to a Time Window

Scanning an entire log file on every run wastes resources and surfaces stale, irrelevant historical failures — always filter to a recent, meaningful window.

Align Scan Windows With Check Frequency

A monitoring interval shorter than the log-scan window risks redundant re-detection; longer risks gaps — keep them matched.

Restrict Status Endpoints (Reinforced from Project 15)

stub_status deserves exactly the same localhost-only restriction as Apache's server-status.

Validate Config Before Reload

nginx -t before any reload, exactly as apachectl configtest in Project 15 — this discipline should be universal across every web server type.

🎤 Interview Preparation

Scenario: The report shows healthy connection counts but flags one upstream as CRITICAL. What does this combination tell you, and where would you look next?
Nginx itself is handling load just fine — the problem is isolated to one specific backend server; the next step is investigating that exact backend directly (its own CPU/memory/connection-pool health, ideally using Projects 1-14's tooling against that specific host) rather than looking at Nginx or the load balancer layer.
Production Support: Upstream failures are being detected, but they're all several hours old and the problem seems to have already resolved. What might be wrong with the script?
Check whether the time-cutoff calculation or the string-comparison filtering in awk is actually working correctly — if the window filtering silently fails (e.g., a timestamp format mismatch), the script could be scanning far more of the log than intended and surfacing old, already-resolved incidents as if they were current.
Shell Scripting: Why does the timestamp string-comparison trick in awk work correctly without ever converting to epoch seconds?
Because Nginx's default log timestamp format (YYYY/MM/DD HH:MM:SS) is both zero-padded and ordered from largest to smallest time unit, plain lexicographic (alphabetical) string comparison happens to produce the same ordering as true chronological comparison — a property that wouldn't hold for a differently-ordered or non-zero-padded date format.
Troubleshooting: sort | uniq -c is producing what looks like duplicate entries for what should be the same upstream address. What's the likely cause?
A subtle formatting inconsistency in the extracted addresses — trailing whitespace, inconsistent capitalization, or a slightly different port representation between log lines — since uniq -c only merges lines that are exactly, byte-for-byte identical.
Manager Round: Why set different WARNING and CRITICAL failure-count thresholds for upstream failures instead of alerting on the very first failure?
A single isolated failure can be entirely normal transient network noise; requiring a repeated pattern within a defined window (3 for WARNING, 8 for CRITICAL here) distinguishes a genuine, ongoing backend problem from expected occasional blips, avoiding alert fatigue from over-sensitive thresholds.
Architecture: Why does this project rely on error-log scanning for upstream health instead of querying Nginx for structured per-upstream metrics directly?
Open-source Nginx (unlike its commercial Nginx Plus variant) doesn't expose structured per-upstream health status through any built-in module — the error log is genuinely the only available data source for this specific signal in the open-source version, making this design choice a real environmental constraint rather than a preference.
Best Practice: Why extract and count failures per individual upstream address rather than just tracking one aggregate "total upstream failures" number?
An aggregate count can't distinguish "one severely broken backend" from "many backends each failing occasionally due to normal network variance" — these represent very different operational situations requiring different responses, and only per-upstream breakdown reveals which one is actually happening.
Real Incident Discussion: What's the one design decision in this project that most directly would have identified the specific failing backend during the original incident?
Extracting the upstream address from each failure log line and tallying failures per address, rather than just detecting "an upstream error occurred somewhere" — this is precisely what would have pointed Ops directly at 10.0.4.22:8080 (or whichever backend) within minutes, instead of requiring manual log digging during a live, confusing, intermittent-error incident.
