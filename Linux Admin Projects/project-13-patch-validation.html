Project 13 of 30 · Security

Patch Validation

The rollout ran fleet-wide, everyone said "done" — and a security audit found 40 of 200 servers still vulnerable, weeks later.

🎯 Level: Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + SSH + dpkg ⏱️ Duration: 3 hrs

📖 The Story — "We Patched It" Meets "Did We, Though?"

A critical vulnerability was disclosed in a widely-used library, and NovaTrust's patch management team ran a fleet-wide update campaign. The rollout ticket was marked complete. Three weeks later, a routine external security scan found 40 of 200 Core Banking servers still running the vulnerable version — the automated patch job had silently failed on a subset of servers (some were unreachable that night, some had a package manager lock held by another process), and nobody had ever gone back to confirm the fix actually landed everywhere.

Priya's assignment: "Deploying a patch and verifying a patch are two completely different jobs, and we've only ever been doing the first one. I want a script that checks the actually installed version on every server against what we require, and gives us a compliance percentage we can hand straight to the audit team — not a deployment log that just tells us a command was sent."

Today we build the verification half of patch management — the half that would have caught this exact gap in days, not months.
🔁 Reinforced from Projects 1–12
The SSH-with-timeout fleet loop (Project 2), UNREACHABLE-vs-unhealthy distinction, and tiered/consolidated reporting all return here, applied to package versions instead of system metrics.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Independently verify, fleet-wide, that required security patches are actually installed — not merely assume success from a deployment job's exit code.

Customer Requirement

Security and Audit need a compliance percentage and a specific list of non-compliant servers, on demand and on a schedule, for regulatory patch-management reporting.

Banking Scenario

NovaTrust's 200 Core Banking servers run a mix of critical system packages (OpenSSL, OpenSSH, the OS kernel) that must meet minimum patched versions per security policy.

Existing Manual Process / Prior Automation Gap

A patch deployment tool pushed updates fleet-wide, but success was measured entirely by the deployment job's own reported status — no independent, after-the-fact verification step existed.

Problems With Deployment-Only Verification

A deployment job can report success while individual servers silently fail for reasons entirely outside the job's own visibility — an offline server that night, a held package lock, a partial failure masked by how the job aggregates results.

Business Impact & Risk

Forty vulnerable production Core Banking servers, undetected for weeks after a "completed" patch campaign, is precisely the kind of finding that triggers serious regulatory scrutiny.

Why Automation Is Required

Only a script independently querying actual installed package versions across all 200 servers, compared against an explicit required baseline, can catch a deployment gap the deployment tool itself missed.

Solution Design

Define a patch baseline (package name and minimum required version), query each server's actually-installed version over SSH, compare using proper version-comparison semantics, and generate both an operational log and a structured CSV compliance report.

Project Scope

In scope: querying installed package versions fleet-wide, proper version comparison, and CSV compliance reporting. Out of scope: actually applying the patches (a separate, deliberately distinct deployment concern from verification).

Expected Outcome

An on-demand or scheduled compliance report showing exactly which servers meet the required patch baseline, which don't (and by how much), and an overall fleet compliance percentage ready to hand directly to an auditor.

🧠 New Bash Concepts for This Project

1. Querying an Installed Package's Version (dpkg-query)

What: dpkg-query -W -f='${Version}' openssl prints just the installed version string of a package on Debian/Ubuntu systems, with no extra formatting.
-W (--show): query without requiring an exact match against the full package database listing format. -f: a custom output format string, here extracting only the Version field.

2. Detecting "Not Installed" vs. "Installed but Old"

What: dpkg-query exits non-zero and prints nothing useful if a package isn't installed at all — this must be checked and reported before attempting any version comparison.
Why: A completely missing package is a different, often more severe finding than an outdated one, and conflating them would mislead the audit report.

3. Correct Version Comparison (dpkg --compare-versions)

What: dpkg --compare-versions "$installed" ge "$required" returns true/false via exit code, using real package-versioning rules (handling things like 1.10 vs 1.9, epoch numbers, and pre-release suffixes correctly).
Why: Naive string comparison ([[ "$installed" \> "$required" ]]) gets this wrong constantly — for example, the string "1.9" sorts after "1.10" alphabetically, which is the opposite of the correct numeric answer.
Common mistake: Trying to roll your own version-comparison logic with cut/awk instead of using the purpose-built tool that already handles every edge case correctly.

4. The RPM Equivalent (rpm -q / rpmvercmp)

What: On RHEL/CentOS-family systems, rpm -q --qf '%{VERSION}-%{RELEASE}' package and rpmdev-vercmp serve the same two purposes as their Debian counterparts.
Why: Real banking environments often run mixed distributions — a production-grade script should be written with this in mind, even if this project's full implementation targets one family for clarity.

5. Structured CSV Report Generation from Bash

What: Building a proper CSV file line by line with printf, including a header row, suitable for opening directly in a spreadsheet for an audit submission.
Why: Audit and Security teams typically consume compliance data in spreadsheet form — a CSV report is far more directly useful to them than parsing our operational log file.

6. Escaping CSV Fields Safely

What: Wrapping any field that might contain a comma or quote in double quotes, with internal quotes doubled (" becomes "") — the standard CSV escaping rule.
Why: A hostname or version string is unlikely to contain a comma, but a defensively-written report generator should never assume that and risk silently corrupting the CSV structure.

7. Calculating a Compliance Percentage

What: PCT=$(( COMPLIANT_COUNT * 100 / TOTAL_COUNT )) — reusing Bash's integer arithmetic, ordering the multiplication before the division specifically to avoid losing precision (Bash truncates each intermediate step).
Why: A single fleet-wide compliance percentage is often the very first number an auditor or manager asks for — this must be calculated correctly and prominently in the report.

8. Looping Over Multiple Required Packages Per Server

What: A nested loop — for each server, for each required package in the baseline — reinforcing Project 4's CRITICAL_SERVICES array pattern, now with a package-and-version pair per entry instead of just a name.

9. Reusing the Remote-Command SSH Pattern for a New Purpose (Reinforced)

What: The exact timeout + BatchMode=yes + ConnectTimeout SSH pattern from Projects 2, 4, and 11, now querying package versions instead of disk usage, CPU processes, or performing a backup transfer.
Why: This is the payoff of building genuinely reusable patterns early in the course — the exact same reliable remote-execution approach now supports an entirely new use case with almost no new risk.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Patch validation helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- check_host_reachable ----------
check_host_reachable() {
    local host="$1"
    ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" "$SSH_USER@$host" exit
    return $?
}

# ---------- get_remote_package_version ----------
# Purpose: Return the installed version of a package on a remote host, or empty if not installed
get_remote_package_version() {
    local host="$1"
    local package="$2"
    timeout "$SSH_COMMAND_TIMEOUT" ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "$SSH_USER@$host" "dpkg-query -W -f='\${Version}' '$package' 2>/dev/null"
    # Note: if the package isn't installed, dpkg-query prints nothing and exits non-zero,
    # which command substitution captures as an empty string - exactly what we want to detect.
}

# ---------- meets_required_version ----------
# Purpose: Return 0 (true) if installed_version >= required_version, using real package-version semantics
meets_required_version() {
    local installed="$1"
    local required="$2"
    dpkg --compare-versions "$installed" ge "$required"
}

# ---------- csv_escape ----------
# Purpose: Wrap a field in quotes and double any internal quotes, per standard CSV escaping rules
csv_escape() {
    local field="$1"
    echo "\"${field//\"/\"\"}\""
}

# ---------- write_csv_row ----------
write_csv_row() {
    local host="$1" package="$2" required="$3" installed="$4" status="$5"
    printf '%s,%s,%s,%s,%s\n' \
        "$(csv_escape "$host")" "$(csv_escape "$package")" \
        "$(csv_escape "$required")" "$(csv_escape "$installed")" \
        "$(csv_escape "$status")" >> "$CSV_REPORT"
}

Line-by-Line Highlights

  • dpkg-query -W -f='\${Version}' '$package' — the \$ escaping is essential here: this string is being sent to a remote shell via SSH, and we need ${Version} to be interpreted by the remote dpkg-query's own format-string parser, not expanded as a local Bash variable before it's even sent.
  • dpkg --compare-versions "$installed" ge "$required" — this single command replaces what would otherwise be a genuinely tricky piece of custom parsing logic (splitting version numbers into components, handling epochs, comparing numerically) with one battle-tested, purpose-built tool call.
  • "${field//\"/\"\"}" — parameter expansion replacing every literal double-quote character with two double-quote characters, the CSV standard's escaping rule for a quote appearing inside an already-quoted field.
  • write_csv_row centralizes CSV formatting in exactly one place — every row, regardless of status, goes through the same escaping and formatting logic, preventing any inconsistency between different call sites.

🩺 Main Script

scripts/patch_validation.sh
#!/bin/bash
# =====================================================================
# patch_validation.sh
# NovaTrust Bank - Fleet-Wide Patch Compliance Verification
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/patch_validation.conf"

HOST_FILE="$SCRIPT_DIR/../config/servers_prod.txt"
BASELINE_FILE="$SCRIPT_DIR/../config/patch_baseline.txt"
[[ -f "$HOST_FILE" && -f "$BASELINE_FILE" ]] || { echo "ERROR: Missing host or baseline file" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/patch_validation_${TODAY}.log"
CSV_REPORT="$SCRIPT_DIR/$REPORT_DIR/compliance_report_${TODAY}.csv"
mkdir -p "$(dirname "$LOG_FILE")" "$(dirname "$CSV_REPORT")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Patch validation run finished."' EXIT

echo "hostname,package,required_version,installed_version,status" > "$CSV_REPORT"

log_message "INFO" "=== Starting fleet-wide patch validation ==="

# ---------- Load the patch baseline into an array of "package:version" entries ----------
mapfile -t BASELINE_ENTRIES < <(grep -v '^#' "$BASELINE_FILE" | grep -v '^$')

TOTAL_CHECKS=0
COMPLIANT_CHECKS=0
UNREACHABLE_HOSTS=0

while IFS= read -r host; do
    [[ -z "$host" || "$host" == \#* ]] && continue

    if ! check_host_reachable "$host"; then
        log_message "FAIL" "$host is UNREACHABLE - cannot verify patch compliance"
        write_csv_row "$host" "ALL" "N/A" "N/A" "UNREACHABLE"
        ((UNREACHABLE_HOSTS++))
        continue
    fi

    for entry in "${BASELINE_ENTRIES[@]}"; do
        IFS=':' read -r package required_version <<< "$entry"
        ((TOTAL_CHECKS++))

        installed_version=$(get_remote_package_version "$host" "$package")

        if [[ -z "$installed_version" ]]; then
            log_message "FAIL" "$host: $package is NOT INSTALLED (required: $required_version)"
            write_csv_row "$host" "$package" "$required_version" "NOT_INSTALLED" "NON_COMPLIANT"
            continue
        fi

        if meets_required_version "$installed_version" "$required_version"; then
            log_message "PASS" "$host: $package $installed_version meets requirement ($required_version)"
            write_csv_row "$host" "$package" "$required_version" "$installed_version" "COMPLIANT"
            ((COMPLIANT_CHECKS++))
        else
            log_message "FAIL" "$host: $package $installed_version is BELOW required $required_version"
            write_csv_row "$host" "$package" "$required_version" "$installed_version" "NON_COMPLIANT"
        fi
    done

done < "$HOST_FILE"

# ---------- Calculate fleet-wide compliance percentage ----------
if [[ "$TOTAL_CHECKS" -gt 0 ]]; then
    COMPLIANCE_PCT=$(( COMPLIANT_CHECKS * 100 / TOTAL_CHECKS ))
else
    COMPLIANCE_PCT=0
fi

log_message "INFO" "=== SUMMARY: $COMPLIANT_CHECKS / $TOTAL_CHECKS checks compliant (${COMPLIANCE_PCT}%) | Unreachable hosts: $UNREACHABLE_HOSTS ==="
log_message "INFO" "CSV report written to: $CSV_REPORT"

if [[ "$COMPLIANCE_PCT" -lt 100 || "$UNREACHABLE_HOSTS" -gt 0 ]]; then
    exit 2
fi
exit 0

Every Line, Explained

LineExplanation
mapfile -t BASELINE_ENTRIES < <(grep -v '^#' ... | grep -v '^$')Combines Project 4's mapfile technique with process substitution to load the baseline into an array while filtering out comments and blank lines in one pipeline, before any per-host processing begins.
IFS=':' read -r package required_version <<< "$entry"Splits each baseline entry into its two component fields — the same colon-delimited pattern used throughout the course since Project 6.
if [[ -z "$installed_version" ]]; then ...; continue; fiThe missing-package check happens before any version comparison is attempted — calling dpkg --compare-versions with an empty string would be a meaningless, potentially confusing comparison.
COMPLIANCE_PCT=$(( COMPLIANT_CHECKS * 100 / TOTAL_CHECKS ))Multiplication happens before division specifically to preserve precision — computing division first would truncate to 0 or 1 long before the percentage math has a chance to matter.
if [[ "$COMPLIANCE_PCT" -lt 100 || "$UNREACHABLE_HOSTS" -gt 0 ]]; then exit 2; fiDeliberately strict: anything less than full compliance, or any host we couldn't even verify, is treated as a reportable finding — an unreachable host is never silently excluded from the compliance question.

# NovaTrust Bank - Patch Validation

## Usage
    ./scripts/patch_validation.sh

## Output
- Operational log: logs/patch_validation_YYYYMMDD.log
- Audit-ready CSV: reports/compliance_report_YYYYMMDD.csv
  Columns: hostname, package, required_version, installed_version, status

## Status Values
    COMPLIANT      = installed version meets or exceeds required version
    NON_COMPLIANT  = installed version is below required, OR package not installed
    UNREACHABLE    = host could not be verified at all this run

## Exit Codes
    0 = 100% compliance across all reachable hosts, zero unreachable hosts
    2 = Any non-compliance found, OR any host was unreachable

## Note
This script only VERIFIES patch status. It does not install or apply patches.
Deployment and verification are deliberately separate concerns.

🔄 What Happens Internally

  1. The baseline is loaded once, before the host loop begins, rather than being re-read from disk for every single server — a small but meaningful efficiency gain at 200-server scale.
  2. Each package check is its own separate SSH call, meaning a 200-server fleet with 3 baseline packages results in 600 individual remote queries per run — worth knowing as a scaling consideration for a much longer baseline list.
  3. dpkg --compare-versions runs as a genuinely separate local process for every comparison, evaluating the exact same version-string rules Debian's own package manager uses internally, guaranteeing our compliance verdict matches what the system itself would consider "up to date."
  4. The CSV report and the operational log are written to independently, in parallel, throughout the run — one file is for a human troubleshooting the run itself, the other is a clean, structured artifact meant to leave the system entirely and go straight to an auditor.

🛡️ Production Best Practices

Never Trust Deployment Success Alone

A patch deployment job's own exit code proves it ran, not that every target server was actually reached and successfully updated — always verify independently afterward.

Use Real Version-Comparison Tools

dpkg --compare-versions (or the RPM equivalent) correctly handles every edge case of version-string semantics that a hand-rolled comparison would get wrong.

Distinguish Missing from Outdated

A package that's completely absent and one that's simply behind on updates represent different risks and different remediation steps — never merge them into one status.

Never Silently Exclude Unreachable Hosts

A host we couldn't verify is not the same as a host that's compliant — treat unreachability itself as a reportable compliance gap, not a data point to quietly drop from the denominator.

Produce Audit-Ready Output

A structured CSV that Security or Audit can open directly is far more useful in practice than requiring them to parse an operational log file themselves.

Keep Verification and Deployment Separate

A single script trying to both apply and verify patches muddies responsibility for failures — this project deliberately does verification only.

🎤 Interview Preparation

Scenario: The compliance report shows 100% for every package on a host, but you later learn that host was actually offline during the entire check window. How is this possible given the design?
This would indicate a bug — per this project's design, an unreachable host should always be written as its own UNREACHABLE row and excluded from the compliant-checks numerator; if it's showing 100% compliant instead, the reachability check likely isn't actually gating the per-package loop correctly.
Production Support: The script reports NON_COMPLIANT for a package you're certain was just patched. What do you check first?
Confirm exactly what version string the patch deployment actually installed (via manual dpkg-query on that host) versus what the baseline file requires — a common cause is the baseline itself listing a slightly wrong required version string, or an epoch prefix mismatch (like the 1: in the openssh-server baseline example) that a naive comparison would miss but dpkg --compare-versions handles correctly if written precisely.
Shell Scripting: Why does the remote dpkg-query command use an escaped \${Version} instead of a normal Bash variable reference?
This entire command string is being sent as literal text to the remote host via SSH; without the backslash, Bash would try to expand ${Version} as a local variable (which doesn't exist, so it would expand to nothing) before ever sending the command — the escape ensures the literal text ${Version} arrives intact for the remote dpkg-query to interpret itself.
Troubleshooting: Compliance percentage shows exactly 0% even though most servers actually have the correct package versions. What's a likely calculation bug?
Check whether the division is happening before the multiplication in a modified formula (which would truncate to zero for most realistic values), or whether COMPLIANT_CHECKS is being incremented in the wrong branch of the version-comparison conditional.
Manager Round: Why does this project only verify patches rather than also applying them in the same script?
Combining deployment and verification into a single script muddies accountability when something fails — was it the deployment mechanism or the verification logic? — and specifically, this project's entire reason for existing is to be an independent check separate from and not trusting the deployment tool's own success reporting.
Architecture: Why query package versions per-package with separate SSH calls instead of one combined remote command checking all required packages at once?
Separate calls are simpler and more directly attributable per-package in the log/report at the cost of more SSH round-trips; a combined single remote script (similar to Project 4's heredoc pattern) would reduce connection overhead at some cost to code simplicity — a legitimate optimization worth making at very large scale or with a much longer package baseline.
Best Practice: Why must the "package not installed" check happen before calling dpkg --compare-versions at all?
Passing an empty string as the installed-version argument into a version-comparison tool produces undefined or misleading results rather than a meaningful "not installed" signal — checking for emptiness first and branching separately is the only reliable way to guarantee that specific, distinct finding is reported accurately.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the 40-server gap within days of the original patch campaign?
Running this independent verification script immediately after the patch deployment campaign completed (rather than relying solely on the deployment tool's own success report) — the 40 non-compliant or unreachable servers would have shown up explicitly in that very first compliance report, rather than surfacing weeks later via an external security scan.
