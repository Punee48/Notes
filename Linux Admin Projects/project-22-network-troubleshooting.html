Project 22 of 30 · Diagnostics

Network Troubleshooting

"The partner connection is down" isn't a diagnosis. "DNS resolves, ping succeeds, but port 3306 is refused" is — and that difference used to cost engineers hours.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL ⏱️ Duration: 2–3 hrs

📖 The Story — An Hour of Manual Checks, One Command at a Time

NovaTrust's interbank settlement gateway — the connection to an external partner bank's SWIFT-adjacent infrastructure — started failing intermittently. Every time it happened, an engineer would manually run ping, wait, run traceroute, wait, try telnet against the specific port, wait, check DNS separately with dig — a fragmented, ad-hoc sequence that took the better part of an hour before anyone could even say which layer was actually failing.

Priya's assignment: "I want one command that runs the entire diagnostic sequence automatically — DNS, ping, basic path tracing, and the actual port we care about — and gives us a clear, single verdict: is this a DNS problem, a routing problem, a firewall problem, or is the partner's own service just down. 'The network is broken' has never once told anyone what to actually go fix."

Unlike every scheduled monitor built so far in this course, this project is a deliberately on-demand diagnostic tool — something an engineer runs by hand, right when something's wrong, aimed at a specific target given as an argument.
🔁 Reinforced from Projects 1–21
/dev/tcp port checking (Project 14), timeout-wrapped network calls (since Project 2), and structured multi-signal composite reporting all return here — now aimed at systematic diagnosis rather than scheduled health classification.

Business Requirement

Provide a single, systematic diagnostic tool that identifies exactly which network layer (DNS, routing, firewall, or the target service itself) is responsible for a connectivity failure.

Customer Requirement

Engineers need a clear, actionable verdict within seconds of running one command, not an hour of manually sequencing individual diagnostic tools.

Banking Scenario

NovaTrust's interbank settlement gateway depends on reliable network connectivity to external partner infrastructure, where intermittent failures have historically taken significant time to properly diagnose.

Existing Manual Process

An engineer runs ping, traceroute, and a manual port check as three completely separate, un-coordinated steps, interpreting each result manually before deciding what to try next.

Problems with the Manual Process

Slow, inconsistent between different engineers' habits, and easy to skip a step under time pressure during a live incident — exactly when a systematic approach matters most.

Business Impact & Risk

Every extra minute diagnosing (rather than fixing) an interbank settlement connectivity issue directly delays time-sensitive financial transactions with a real, external counterparty.

Why Automation Is Required

A single script running the full diagnostic battery consistently, every time, removes both the delay and the risk of a rushed engineer skipping a step during a live, stressful incident.

Solution Design

Given a target host and port, run DNS resolution, ping-based reachability/latency, a lightweight traceroute hop analysis, and a direct port-reachability check — always running the full battery regardless of individual results — then synthesize one clear diagnosis from the specific combination of outcomes.

Project Scope

In scope: DNS, ping/latency, basic traceroute hop analysis, and port reachability, combined into one synthesized diagnosis. Out of scope: deep packet inspection or firewall rule analysis — this tool identifies which layer is failing, not necessarily the exact underlying cause within that layer.

Expected Outcome

One command, given a target, that replaces an hour of fragmented manual diagnosis with a single, specific, actionable verdict in well under a minute.

🧠 New Bash Concepts for This Project

1. Controlled Ping Testing (ping -c, -W)

What: ping -c 5 -W 2 host sends exactly 5 packets (-c), waiting at most 2 seconds per reply (-W), then stops — never running indefinitely like a bare ping would.
Why: A script needs a bounded, predictable ping test, not an open-ended stream that would hang a diagnostic tool waiting for a human to press Ctrl+C.

2. Parsing Packet Loss and Latency from Ping Output

What: Ping's summary line includes text like 5 packets transmitted, 5 received, 0% packet loss and rtt min/avg/max/mdev = 12.1/14.3/18.9/2.1 ms — both extractable with grep -oP.
Why: A raw pass/fail from ping's exit code alone misses crucial nuance — 20% packet loss with high latency is a very different, more actionable finding than a clean 0%-loss, fast response.

3. Basic Traceroute Hop Analysis (traceroute)

What: traceroute -m 15 -w 2 host shows the path packets take, hop by hop, with * * * indicating a hop that didn't respond.
Why: Counting how many hops actually responded before the path goes silent (all *) helps localize where in the network path a problem exists — often the difference between "our own network," "the internet in general," and "the partner's own network."

4. Extracting the Last Responding Hop

What: Parsing traceroute's numbered hop lines, tracking the highest hop number that returned a real IP/hostname rather than all asterisks.
Why: This single number — "the path was still responding as of hop 8, then went silent" — is often the most actionable single fact in the entire diagnostic report during a real incident.

5. DNS Resolution Testing (getent hosts or dig +short)

What: getent hosts "$hostname" (using the system's own standard resolution mechanism) or dig +short "$hostname" (querying DNS directly) both test whether a hostname resolves to an IP at all.
Why: getent tests resolution exactly the way every other application on the system would experience it (including /etc/hosts overrides); dig tests DNS specifically, bypassing any local override — the two can legitimately give different, both-useful answers.

6. Always Running the Full Battery (Deliberate Departure from Earlier Projects' Gating)

What: Unlike Project 4's "only run the expensive check if the cheap one already found a problem" gating, this project deliberately runs all four diagnostic layers every single time, regardless of earlier results.
Why: A full diagnostic picture is exactly what's needed here — stopping early the moment DNS fails, for instance, would hide whether ping and port-level connectivity might also have separate problems, information genuinely useful for a complete incident report.

7. Synthesizing One Diagnosis from Multiple Signals

What: A decision structure (a series of if/elif checks in a specific, deliberate order) that maps the exact combination of DNS/ping/traceroute/port results onto one specific, human-readable diagnosis sentence.
Why: Raw results alone still require the reader to do the same interpretation work this project exists to eliminate — the synthesis step is what turns four separate data points into one immediately actionable conclusion.

8. Positional Arguments as the Primary Interface (Departure from Config-File-Driven Projects)

What: ./network_diagnose.sh partner-gateway.example.com 3306 — the target comes directly from command-line arguments, not a config file listing pre-known hosts.
Why: This tool is meant to diagnose any target an engineer names in the moment, during a live incident — fundamentally different from every prior scheduled-monitoring project's fixed, pre-registered target list.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Network diagnostic helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- check_dns_resolution ----------
# Purpose: Return the resolved IP, or empty if resolution failed
check_dns_resolution() {
    local hostname="$1"
    getent hosts "$hostname" 2>/dev/null | awk '{print $1}' | head -n 1
}

# ---------- run_ping_test ----------
# Purpose: Return "packet_loss_pct avg_latency_ms" (space-separated), or empty on total failure
run_ping_test() {
    local target="$1"
    local ping_output
    ping_output=$(ping -c "$PING_COUNT" -W "$PING_TIMEOUT_SECONDS" "$target" 2>/dev/null)

    local loss_pct avg_latency
    loss_pct=$(echo "$ping_output" | grep -oP '\d+(?=% packet loss)')
    avg_latency=$(echo "$ping_output" | grep -oP 'rtt min/avg/max/mdev = [\d.]+/\K[\d.]+')

    [[ -z "$loss_pct" ]] && { echo ""; return; }
    echo "$loss_pct ${avg_latency:-N/A}"
}

# ---------- get_last_responding_hop ----------
# Purpose: Return the highest traceroute hop number that got a real response (not all *)
get_last_responding_hop() {
    local target="$1"
    local traceroute_output
    traceroute_output=$(timeout 30 traceroute -m "$TRACEROUTE_MAX_HOPS" -w "$TRACEROUTE_TIMEOUT_SECONDS" "$target" 2>/dev/null)

    # Grep for hop lines that do NOT consist entirely of "* * *", then take the last matching hop number
    echo "$traceroute_output" | grep -vP '^\s*\d+\s+\*\s+\*\s+\*' | grep -oP '^\s*\K\d+' | tail -n 1
}

# ---------- check_port_reachable ----------
check_port_reachable() {
    local host="$1"
    local port="$2"
    timeout "$PORT_CHECK_TIMEOUT" bash -c "echo > /dev/tcp/$host/$port" 2>/dev/null
}

Line-by-Line Highlights

  • getent hosts "$hostname" | awk '{print $1}' — getent hosts queries exactly the same resolution mechanism (DNS, /etc/hosts, and any configured order between them) that every other application on the system uses, making it the most representative resolution test.
  • grep -oP '\d+(?=% packet loss)' — a lookahead assertion (?=...), only available with -P (Perl-compatible regex): matches digits that are followed by the literal text % packet loss, without including that trailing text in the captured output.
  • grep -vP '^\s*\d+\s+\*\s+\*\s+\*' — -v inverts the match, keeping only lines that do not match the "all three probes timed out" pattern, isolating genuinely responding hops.
  • grep -oP '^\s*\K\d+' | tail -n 1 — extracts just the leading hop number from each responding line (using \K exactly as in Project 14), then tail -n 1 takes the last one, since traceroute output is already in hop order.

🩺 Main Script

scripts/network_diagnose.sh
#!/bin/bash
# =====================================================================
# network_diagnose.sh
# NovaTrust Bank - On-Demand Multi-Layer Network Diagnostic Tool
# Usage: ./network_diagnose.sh  [port]
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/network_diagnose.conf"

if [[ $# -lt 1 ]]; then
    echo "Usage: $0  [port]" >&2
    exit 1
fi

TARGET_HOST="$1"
TARGET_PORT="${2:-}"                                  # Optional - empty if not provided

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/network_diagnose_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

log_message "INFO" "=== Diagnosing $TARGET_HOST${TARGET_PORT:+:$TARGET_PORT} ==="

# ---------- Layer 1: DNS ---------- (always runs)
RESOLVED_IP=$(check_dns_resolution "$TARGET_HOST")
if [[ -z "$RESOLVED_IP" ]]; then
    log_message "FAIL" "DNS: '$TARGET_HOST' did NOT resolve"
else
    log_message "PASS" "DNS: '$TARGET_HOST' resolved to $RESOLVED_IP"
fi

# ---------- Layer 2: Ping ---------- (always runs, regardless of DNS result)
PING_RESULT=$(run_ping_test "$TARGET_HOST")
if [[ -z "$PING_RESULT" ]]; then
    log_message "FAIL" "PING: host unreachable (100% loss or no response)"
    PACKET_LOSS=100
else
    read -r PACKET_LOSS AVG_LATENCY <<< "$PING_RESULT"
    if [[ "$PACKET_LOSS" -ge "$PACKET_LOSS_WARN_PCT" ]]; then
        log_message "WARN" "PING: degraded - ${PACKET_LOSS}% packet loss, avg latency ${AVG_LATENCY}ms"
    else
        log_message "PASS" "PING: healthy - ${PACKET_LOSS}% packet loss, avg latency ${AVG_LATENCY}ms"
    fi
fi

# ---------- Layer 3: Traceroute ---------- (always runs)
LAST_HOP=$(get_last_responding_hop "$TARGET_HOST")
if [[ -z "$LAST_HOP" ]]; then
    log_message "WARN" "TRACEROUTE: no hops responded at all"
else
    log_message "INFO" "TRACEROUTE: last responding hop was #$LAST_HOP (out of max $TRACEROUTE_MAX_HOPS)"
fi

# ---------- Layer 4: Port ---------- (always runs, if a port was given)
PORT_OPEN="unknown"
if [[ -n "$TARGET_PORT" ]]; then
    if check_port_reachable "$TARGET_HOST" "$TARGET_PORT"; then
        log_message "PASS" "PORT: $TARGET_PORT is reachable"
        PORT_OPEN="true"
    else
        log_message "FAIL" "PORT: $TARGET_PORT is NOT reachable (refused, filtered, or timed out)"
        PORT_OPEN="false"
    fi
fi

# ---------- Synthesis: one clear diagnosis from all four layers ---------- 
log_message "INFO" "=== DIAGNOSIS ==="
if [[ -z "$RESOLVED_IP" ]]; then
    log_message "INFO" "DNS resolution failure - check DNS configuration/records before investigating anything else"
elif [[ "$PACKET_LOSS" -eq 100 ]]; then
    log_message "INFO" "Host is completely unreachable at the network layer - likely a routing issue or an ICMP-blocking firewall (last responding hop: ${LAST_HOP:-none})"
elif [[ "$PACKET_LOSS" -ge "$PACKET_LOSS_WARN_PCT" ]]; then
    log_message "INFO" "Path is DEGRADED (${PACKET_LOSS}% packet loss) rather than fully down - investigate the network path around hop #${LAST_HOP:-unknown}"
elif [[ "$PORT_OPEN" == "false" ]]; then
    log_message "INFO" "Host is fully reachable at the network layer, but port $TARGET_PORT specifically is NOT - likely a firewall rule or the target service itself being down"
elif [[ "$PORT_OPEN" == "true" ]]; then
    log_message "INFO" "Fully healthy - DNS, ping, and port $TARGET_PORT are all working correctly"
else
    log_message "INFO" "DNS and ping are healthy - no port was specified to test further"
fi

exit 0

Every Line, Explained

LineExplanation
TARGET_PORT="${2:-}"Parameter expansion with a default of empty string — the port argument is genuinely optional, since some diagnoses (a general "can we reach this host at all") don't need one.
Every layer runs unconditionally, one after anotherDeliberately different from most of this course's gated checks — a complete diagnostic picture requires every layer's result, even if an earlier layer already found a problem.
elif [[ "$PACKET_LOSS" -eq 100 ]]; then before the degraded-loss checkOrdering matters in this synthesis logic: "completely unreachable" (100% loss) must be checked and reported distinctly before the more general "degraded" threshold check, since 100% loss is categorically a different finding than 20% loss, even though both technically exceed the WARN threshold.
Final else branch (no port specified)Ensures every possible combination of inputs produces some diagnosis line — never silently producing no verdict at all just because the optional port argument was omitted.

📄 README.md

README.md
# NovaTrust Bank - Network Diagnostic Tool

## Usage
    ./scripts/network_diagnose.sh partner-gateway.example.com
    ./scripts/network_diagnose.sh partner-gateway.example.com 3306

## What It Checks (always all four, every run)
1. DNS resolution (getent hosts)
2. Ping: packet loss % and average latency
3. Traceroute: last responding hop
4. Port reachability (if a port is given)

## Output
A synthesized DIAGNOSIS line at the end names the specific most-likely-failing
layer based on the full combination of results - not just raw tool output.

## Note
This is an on-demand diagnostic tool, not a scheduled monitor. It can still
be run periodically via cron against a known-critical link if continuous
monitoring is separately desired, but its primary use is manual investigation.

🔄 What Happens Internally

  1. Each of the four diagnostic layers runs as its own independent external command (getent, ping, traceroute, and Bash's own /dev/tcp), each with its own bounded timeout — no single hanging tool can block the others from at least attempting to run.
  2. The synthesis logic is deliberately ordered as a chain of specific elif conditions, checked from most fundamental (DNS) to most specific (port) — this ordering directly encodes the networking mental model of "check the foundational layer first" that an experienced engineer would apply manually.
  3. Every run is still logged to a dated file, even though this is an on-demand tool — preserving a record of past diagnostic runs is valuable for later reference during a post-incident review, exactly like every other project's logging discipline.
  4. Positional arguments, rather than a config file, are parsed with simple $1/$2 access — appropriate for a tool whose target genuinely varies on every single invocation, unlike every prior project's fixed, pre-registered target list.

🛡️ Production Best Practices

Always Bound Diagnostic Tools With Timeouts

ping, traceroute, and port checks can all hang indefinitely against an unresponsive target without explicit count/timeout flags — never rely on defaults.

Run the Full Battery, Don't Short-Circuit

Unlike routine health checks, a genuine diagnostic tool benefits from complete information even after an early layer already shows a problem.

Synthesize, Don't Just Dump Raw Output

The real value is in the interpretation step — turning four separate tool outputs into one specific, actionable sentence is what actually saves an engineer's time.

Order Synthesis Logic by Networking Fundamentals

Check DNS before ping, ping before port — mirroring the actual dependency chain of how these layers relate to each other.

Log Every Diagnostic Run

Even an on-demand tool benefits from a persistent record — a past diagnostic run is valuable evidence during a post-incident review.

Design for the Target That Varies

Not every tool in an operations toolkit should be config-file-driven — a genuinely ad-hoc diagnostic tool is better served by simple positional arguments.

🎤 Interview Preparation

Scenario: DNS resolves correctly and the port check succeeds, but ping shows 100% packet loss. Is this contradictory?
Not necessarily — many firewalls and security appliances deliberately block ICMP (ping) traffic while still allowing specific TCP ports through; this combination is actually a fairly common and legitimate real-world finding, not a sign of a bug in the diagnostic tool.
Production Support: The diagnosis says "host completely unreachable," but the last responding hop shows hop #12 out of a max of 15. What does this specific detail add?
It narrows the likely problem location — the path was clearly working correctly through at least 12 network hops, meaning the issue is most likely in the final few hops close to the destination (the partner's own edge/firewall) rather than somewhere in the broader internet path or NovaTrust's own network.
Shell Scripting: Why use grep -P (Perl-compatible regex) instead of standard grep for parsing ping and traceroute output?
Perl-compatible regex supports lookahead assertions (?=...) and the \K "reset match start" feature, both used here to extract a number immediately adjacent to specific surrounding text without including that text in the captured output — standard POSIX grep regex doesn't support either feature.
Troubleshooting: The script's traceroute step takes nearly the full 30-second timeout on every single run, even against healthy targets. Why?
Some networks have one or more intermediate hops that don't respond to traceroute probes at all (often by design, for security) even though the overall path to the final destination works perfectly fine — those specific hops each still consume their full per-hop timeout before traceroute moves on, adding up across many silent hops.
Manager Round: Why build a general-purpose diagnostic tool that takes any target as an argument, rather than a scheduled monitor specifically for the partner bank connection like every other project in this course?
The recurring need here is investigating whatever connectivity issue comes up next, not just one specific known link — a general tool serves this specific partner connection today and any other future connectivity question tomorrow, without needing a new project built for every new target that might need diagnosing.
Architecture: Why does this project deliberately abandon the "gate expensive checks behind cheap ones" pattern from Project 4?
Project 4's gating optimizes for running efficiently at scale across 200 servers on every routine cron cycle; this project optimizes for a single, one-off diagnostic session where complete information is far more valuable than saving a few seconds — the right pattern depends entirely on the actual use case, not a fixed rule to apply everywhere.
Best Practice: Why check DNS resolution using getent hosts rather than only querying DNS directly with dig?
getent hosts reflects exactly what every other real application on the system would experience when resolving that hostname (including any local /etc/hosts override), which is usually the more relevant, representative test; dig queries DNS specifically and can give a different, also-useful answer when local overrides are masking an underlying DNS problem.
Real Incident Discussion: What's the single most direct design decision in this project that would have cut the original hour-long manual diagnosis down to seconds?
Running all four diagnostic layers automatically, in one command, with the results synthesized into one specific verdict — the entire sequence of manually running and individually interpreting ping, traceroute, and a port check, one at a time, is replaced by a single invocation producing the same conclusion in well under a minute.
