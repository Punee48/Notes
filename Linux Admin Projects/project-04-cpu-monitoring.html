CPU Monitoring & Process-Level Attribution

System-wide CPU % told us something was wrong during last month's incident — but nobody could say what. Today we fix that.

🎯 Level: Intermediate 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL + SSH ⏱️ Duration: 2–3 hrs

📖 The Story — "Something's Eating the CPU, But What?"

Last month, corebanking-prod-07 hit 97% CPU for twenty-two minutes during the NEFT settlement window. The on-call engineer opened a ticket that just said "CPU high, investigating" — because our monitoring only ever reported the system-wide percentage. It took eleven minutes of manual top commands to discover a stuck end-of-day reconciliation batch job was the culprit.

In today's stand-up, Priya says: "A percentage number without a process name is just an alarm bell with no address. From now on, whenever CPU crosses WARNING, I want the script to also tell us which process is responsible — name, PID, and owner — right there in the same log line. No more eleven minutes of manual digging."

Today we teach our scripts to not just detect a problem, but point directly at the cause.
🔁 Reinforced from Projects 1–3
SSH-with-timeout, flock, config-driven thresholds, and the consolidated report/log pattern continue unchanged.

🏛️ Business Requirement & Banking Scenario

Business Requirement

When CPU usage breaches WARNING or CRITICAL, automatically identify and log the top CPU-consuming process(es) responsible.

Customer Requirement

On-call engineers want actionable detail in the very first alert, not a starting point for a manual investigation.

Banking Scenario

Batch jobs (end-of-day reconciliation, interest calculation) run alongside always-on services (Core Banking, NEFT Gateway) on the same servers, and either can be the cause of a spike.

Existing Manual Process

An engineer SSHs in and runs top interactively during the incident itself — precious minutes lost while the spike is still ongoing.

Problems with Manual Process

By the time someone logs in, a short-lived spiky process may have already finished, leaving no trace of what actually happened.

Business Impact & Risk

Extended root-cause investigation during a live incident extends downtime and delays the fix — every extra minute during a settlement window has direct financial impact.

Why Automation Is Required

Only an automated check running at the moment of the spike can capture which process was responsible — by the time a human logs in, the evidence may be gone.

Solution Design

Check system-wide CPU as before; the moment it crosses WARNING, additionally capture the top 3 CPU-consuming processes (PID, command, %CPU, user) and log them alongside the alert.

Project Scope

In scope: system CPU %, conditional top-process capture, day-over-day trend reuse from Project 3's pattern. Out of scope: killing or restarting the offending process automatically.

Expected Outcome

Any WARNING or CRITICAL CPU log line is immediately followed by the specific process(es) responsible — turning every alert into a head start on root cause, not just a symptom.

🧠 New Bash Concepts for This Project

1. ps -eo with Custom Output Columns

What: ps -eo pid,comm,%cpu,%mem,user --sort=-%cpu lists every process with exactly the columns we choose, pre-sorted.
Why: Unlike top (built for interactive viewing), ps is designed for scripting — clean, parseable, one-shot output.
Best practice: Always specify exact columns with -eo rather than parsing ps aux's human-oriented layout, which is harder to parse reliably.

2. Built-in Sorting: ps --sort=-%cpu vs external sort

What: ps can sort its own output (--sort=-%cpu = descending by CPU); alternatively, pipe to the external sort -k3 -nr command.
Why: Letting ps sort natively avoids a second process and a fragile column-number dependency — but it's worth knowing the external sort approach too, since not all commands support native sorting.
sort -k3 -nr breakdown: -k3 = sort by the 3rd field, -n = numeric (not alphabetic) comparison, -r = reverse (descending) order.

3. head -n to Cap Results

What: Returns only the first N lines of input.
Why: We want only the top 3 offenders, not the entire process table, to keep our logs and alerts readable.

4. Conditional (Lazy) Execution for Expensive Checks

What: Only run the process-listing command inside the if branch that already detected a breach — never unconditionally on every run.
Why: Listing and sorting every process on 200 servers every 5 minutes, when 99% of checks are healthy, wastes both local and remote resources for no benefit.
Production example: This "only pay the cost when something's actually wrong" pattern shows up constantly in production tooling — expensive diagnostics behind a cheap gate.

5. Capturing Multi-Line Output into an Array (mapfile)

What: mapfile -t PROCESSES <<< "$RAW_OUTPUT" splits a multi-line string into an array, one element per line, in one step.
Why: Our top-3-processes result is multiple lines; we want to loop over each one individually to format it for the log.
-t flag: strips the trailing newline from each captured line — without it, every array element would have an ugly trailing newline character.
Common mistake: Using PROCESSES=($RAW_OUTPUT) (word-splitting) instead of mapfile — this breaks on any process name or field containing spaces.

6. Sending a Multi-Command Block Over SSH with a Heredoc

What: ssh user@host bash -s <<'EOF' ... EOF sends an entire block of commands to run remotely, instead of one long single-quoted string.
Why: Our CPU-and-process check is now multiple commands — a heredoc keeps this readable instead of one unreadable escaped one-liner.
Quoting the delimiter (<<'EOF'): prevents the local shell from expanding any $variables inside the block before it's sent — everything inside is interpreted purely on the remote end.

7. Field Width Formatting with printf (Reinforced)

What: Continuing from Project 2, printf gives us aligned attribution lines like PID 4821 batch_recon.sh 62.3% svc_batch.
Why: A process attribution line is only useful if all its fields are easy to scan at a glance in a log file.

8. Command Existence Checks (command -v)

What: command -v ps >/dev/null 2>&1 checks whether a command exists before relying on it.
Why: Minimal container-based hosts sometimes strip ps to save space — we should fail with a clear message rather than a cryptic "command not found" buried in a log.
Best practice: Prefer command -v over which — which isn't guaranteed to exist on every minimal system, while command is a POSIX shell builtin.

🧩 Utility Functions (Extended)

scripts/utils.sh (additions)
# ---------- get_remote_cpu_usage ----------
# Purpose: Return current CPU usage % (integer) for a remote host - the cheap, always-run check
get_remote_cpu_usage() {
    local host="$1"
    timeout "$SSH_COMMAND_TIMEOUT" ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "$SSH_USER@$host" "top -bn1 | grep 'Cpu(s)' | awk '{print 100 - \$8}' | cut -d'.' -f1"
}

# ---------- get_top_processes ----------
# Purpose: Return the top N CPU-consuming processes as raw lines (pid, comm, %cpu, user)
# Only called when a threshold has ALREADY been breached - this is the "expensive" path
get_top_processes() {
    local host="$1"
    local count="$2"

    # Heredoc sends a small multi-command block to run entirely on the remote host.
    # Quoting 'EOF' means no local variable expansion happens before sending - everything
    # inside runs exactly as written, on the remote shell.
    timeout "$SSH_COMMAND_TIMEOUT" ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "$SSH_USER@$host" bash -s </dev/null 2>&1 || { echo "ps not found on this host"; exit 1; }
ps -eo pid,comm,%cpu,user --sort=-%cpu --no-headers | head -n ${count}
EOF
}

# ---------- format_process_line ----------
# Purpose: Turn one raw 'ps' output line into an aligned, readable attribution line
# Arguments: $1 = raw line (pid comm %cpu user)
format_process_line() {
    local raw="$1"
    # Read the 4 whitespace-separated fields into named variables in one shot
    read -r pid comm cpu user <<< "$raw"
    printf "      -> PID %-8s %-24s %-6s%% owner:%s\n" "$pid" "$comm" "$cpu" "$user"
}

Line-by-Line Highlights

  • ssh ... bash -s <<EOF ... EOF — bash -s tells the remote shell to read its script from stdin, which is exactly what our heredoc feeds it.
  • command -v ps >/dev/null 2>&1 || { ...; exit 1; } — a defensive guard so a minimal host without ps fails with a clear message instead of a confusing parse error later.
  • --sort=-%cpu — the leading - means descending order; without it, ps would sort ascending (lowest CPU first), which is the opposite of what we want.
  • read -r pid comm cpu user <<< "$raw" — a here-string feeds one line into read, which splits it on whitespace directly into four named variables in a single line, no array needed.
  • printf "... %-8s %-24s ..." — the - before each width number left-aligns the field, padding with spaces on the right, so every attribution line lines up in the log file.

🩺 Main Script

scripts/cpu_monitor.sh
#!/bin/bash
# =====================================================================
# cpu_monitor.sh
# NovaTrust Bank - CPU Monitor with Process-Level Attribution
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"

ENVIRONMENT="prod"
while getopts "e:h" opt; do
    case $opt in
        e) ENVIRONMENT="$OPTARG" ;;
        h) echo "Usage: $0 -e [prod|uat]"; exit 0 ;;
        *) echo "Invalid option. Usage: $0 -e [prod|uat]"; exit 1 ;;
    esac
done

source "$SCRIPT_DIR/../config/cpu_monitor.conf"
HOST_FILE="$SCRIPT_DIR/../config/servers_${ENVIRONMENT}.txt"
[[ -f "$HOST_FILE" ]] || { echo "ERROR: Host file not found: $HOST_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/cpu_monitor_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "CPU monitor run finished for environment: $ENVIRONMENT"' EXIT

log_message "INFO" "=== Starting CPU monitor for environment: $ENVIRONMENT ==="

OVERALL_EXIT=0
HEALTHY=0; WARNING=0; CRITICAL=0; UNREACHABLE=0

while IFS= read -r host; do
    [[ -z "$host" || "$host" == \#* ]] && continue

    if ! check_host_reachable "$host"; then
        log_message "FAIL" "$host is UNREACHABLE"
        ((UNREACHABLE++))
        OVERALL_EXIT=2
        continue
    fi

    CPU_PCT=$(get_remote_cpu_usage "$host")
    if [[ -z "$CPU_PCT" ]]; then
        log_message "WARN" "$host returned no CPU data"
        continue
    fi

    if [[ "$CPU_PCT" -ge "$CPU_FAIL_THRESHOLD" ]]; then
        STATUS="CRITICAL"; ((CRITICAL++)); OVERALL_EXIT=2
    elif [[ "$CPU_PCT" -ge "$CPU_WARN_THRESHOLD" ]]; then
        STATUS="WARNING"; ((WARNING++)); [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    else
        STATUS="HEALTHY"; ((HEALTHY++))
    fi

    log_message "$STATUS" "$host: CPU usage ${CPU_PCT}%"

    # ---------- THE GATE: only pay for process attribution when it's actually needed ----------
    if [[ "$STATUS" != "HEALTHY" ]]; then
        RAW_PROCESSES=$(get_top_processes "$host" "$TOP_PROCESS_COUNT")

        if [[ -n "$RAW_PROCESSES" ]]; then
            log_message "INFO" "$host: Top $TOP_PROCESS_COUNT CPU-consuming processes:"
            mapfile -t PROCESS_LINES <<< "$RAW_PROCESSES"    # Split multi-line output into an array, one line per element
            for line in "${PROCESS_LINES[@]}"; do
                format_process_line "$line" | tee -a "$LOG_FILE"
            done
        else
            log_message "WARN" "$host: Could not capture process attribution data"
        fi
    fi

done < "$HOST_FILE"

log_message "INFO" "=== SUMMARY ==="
log_message "INFO" "Healthy: $HEALTHY | Warning: $WARNING | Critical: $CRITICAL | Unreachable: $UNREACHABLE"

exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
if [[ "$STATUS" != "HEALTHY" ]]; thenThis single condition is the "lazy evaluation gate" — everything expensive below it only runs for the roughly 1% of checks that actually need it.
RAW_PROCESSES=$(get_top_processes "$host" "$TOP_PROCESS_COUNT")Captures the entire multi-line ps output as one string via command substitution — newlines are preserved inside the variable.
mapfile -t PROCESS_LINES <<< "$RAW_PROCESSES"Splits that string into an array, one element per original line, with the -t flag stripping trailing newlines from each.
for line in "${PROCESS_LINES[@]}"; doQuoting the array expansion ensures each line (which may contain multiple spaces between fields) is treated as one loop item, not split further.
format_process_line "$line" | tee -a "$LOG_FILE"Each formatted attribution line is printed to console and appended to the log in one step, consistent with every other logging call in this framework.

⚠️ Why 5 minutes here, but 30 for disk and daily for memory?
CPU spikes can start and end within seconds to minutes, unlike disk (which fills gradually) or memory leaks (which trend over days) — the check interval should always match how fast the underlying metric can actually change.

📄 README.md

README.md
# NovaTrust Bank - CPU Monitor with Process Attribution

## Usage
    ./scripts/cpu_monitor.sh -e prod

## Behavior
- CPU % is always checked (cheap).
- Top N CPU-consuming processes are captured ONLY when CPU is at/above WARNING (expensive, gated).

## Exit Codes
    0 = All hosts healthy
    1 = At least one WARNING
    2 = At least one CRITICAL or UNREACHABLE host

🔄 What Happens Internally

  1. Two separate SSH round-trips per breached host: one cheap call for the CPU percentage (always), and one heavier heredoc-based call for process attribution (only on breach) — deliberately not combined into one call, so the cheap path stays cheap.
  2. The heredoc's remote script runs as its own bash -s process on the target host — a genuinely separate interpreter instance from our local script.
  3. mapfile reads from the here-string's stdin internally and populates the array in the current shell — no subshell involved, so PROCESS_LINES remains usable afterward.
  4. read -r ... <<< "$raw" inside format_process_line runs in the function's own scope; because pid, comm, cpu, and user aren't declared local, they technically leak into the calling scope — worth tightening as a best-practice exercise.

🛡️ Production Best Practices

Gate Expensive Diagnostics

Never run a heavy diagnostic command on every single check — trigger it only when a cheap check already found a problem.

Use -eo, Not Human-Oriented Output

Script against ps -eo's stable column output, never ps aux's formatting, which can vary and is harder to parse reliably.

Scope Your Variables

Every function-local variable should be declared local to prevent silent leakage into the calling script (see this project's known gap above).

Match Check Interval to Metric Volatility

CPU (fast-changing) needs a shorter interval than disk (slow-changing) or memory trend (day-scale) — one-size-fits-all scheduling is a common mistake.

Fail Clearly on Missing Tools

Guard with command -v before relying on any external tool that might not exist on every host class.

Keep Attribution Actionable

PID + command + owner is the minimum needed for someone to safely decide the next action (investigate vs. kill vs. escalate).

🎤 Interview Preparation

Scenario: CPU is reported CRITICAL but the process attribution section is empty. What are the likely causes?
The remote ps command may not exist on that host (guarded by our command -v check, which would show a specific message), the SSH heredoc call may have hit its own timeout separately from the CPU check's timeout, or the spike ended between the two SSH calls.
Production Support: The script runs noticeably slower during a fleet-wide CPU incident. Why, and is that acceptable?
This is expected — the lazy-evaluation gate means the expensive ps attribution call only fires on unhealthy hosts, so a widespread incident naturally triggers more of those calls; it's an acceptable tradeoff since the alternative (always running it) would slow down every single check, every time.
Shell Scripting: Why use a heredoc for the remote ps command instead of one long quoted string like Projects 1–3 used?
The command is now a short multi-step block (existence check, then the actual ps pipeline) — a heredoc keeps it readable as normal-looking bash, rather than forcing awkward nested quoting and escaped $ signs into one line.
Troubleshooting: mapfile is undefined / command not found. What's wrong?
mapfile (alias readarray) is a Bash 4+ builtin — the script is likely being invoked with sh or on a very old Bash version; verify with bash --version and ensure the script is run as ./cpu_monitor.sh, not sh cpu_monitor.sh.
Manager Round: Why not just always run the process-attribution check — isn't more data always better?
At 200 servers checked every 5 minutes, an unconditional heavier remote call adds real SSH connection overhead and remote CPU cost with essentially zero value on the 99% of checks that are already healthy — it's a real, measurable cost with no corresponding benefit.
Architecture: Why capture the top 3 processes instead of just the single top one?
A spike is sometimes caused by several moderate processes running concurrently rather than one dominant one — capturing the top 3 gives a fuller picture without overwhelming the log with the entire process table.
Best Practice: What's the risk of the un-scoped variables inside format_process_line?
Without local, pid, comm, cpu, and user persist in whatever calls the function, potentially shadowing or corrupting a same-named variable elsewhere in a larger script — a subtle bug that gets harder to trace as scripts grow.
Real Incident Discussion: The original 22-minute CPU incident took 11 minutes of manual investigation. What single change from this project most directly addresses that?
The lazy-gated automatic process attribution — the exact investigation an engineer did manually with top is now captured automatically, in the same log entry, at the moment the spike is detected rather than minutes later.
