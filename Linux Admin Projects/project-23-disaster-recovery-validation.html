Project 23 of 30 · Resilience

Disaster Recovery Validation

When the real outage hit, failover took six hours against a one-hour target — and the DR database had been silently lagging for days before anyone knew.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL ⏱️ Duration: 3 hrs

📖 The Story — Assumed Ready, Actually Wasn't

A regional outage finally put NovaTrust's disaster recovery plan to a real test — and it failed the test badly. The mandated Recovery Time Objective (RTO) was one hour; actual failover took six. The mandated Recovery Point Objective (RPO) allowed for at most 15 minutes of data loss; the DR database replica, it turned out, had been silently lagging behind production by days, not minutes — a problem Project 7's replication-lag monitoring would have caught immediately, had it ever been deployed against the DR site specifically rather than only production.

In the aftermath, Priya's directive is unambiguous: "We validated our DR plan exactly once — during an actual disaster. That's backwards. I want a weekly DR-readiness check: is the DR replica within our RPO right now, can we actually reach the DR site's network, are our failover runbook scripts even syntactically valid, and do we have current backups sitting there. I want a scorecard, not a false sense of security."

This project deliberately validates readiness without ever triggering an actual failover — a real DR drill remains its own separate, carefully-planned, high-risk exercise, not something an unattended script should ever set in motion.
🔁 Reinforced from Projects 1–22
Project 7's replication-lag checking, Project 11's backup verification, Project 22's network diagnostics, and Project 13's compliance-percentage reporting all converge here into one readiness scorecard.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Continuously validate disaster recovery readiness — replica currency against RPO, DR-site connectivity, backup availability, and runbook integrity — without ever executing an actual failover.

Customer Requirement

Compliance and executive leadership need ongoing proof of DR readiness for regulatory reporting, not a one-time assumption tested only during a real disaster.

Banking Scenario

NovaTrust maintains a DR site with a replicated database, periodic backup copies, and documented failover runbooks intended to restore Core Banking operations within a mandated RTO/RPO during a regional outage.

Existing Manual Process / Prior Automation Gap

DR readiness had never been independently, continuously validated — the plan existed on paper and was assumed current, with its actual state discovered only during the real outage it was meant to handle.

Problems With Assumed Readiness

Every individual DR component (replication, backups, runbooks, network path) can silently degrade over time without any single obvious symptom — exactly the same class of "invisible until needed" risk this course has repeatedly confronted, now at the scale of an entire disaster recovery plan.

Business Impact & Risk

A DR plan that fails during the actual disaster it exists for represents the worst possible time to discover a gap — with real, ongoing business and regulatory consequences during the outage itself.

Why Automation Is Required

Only continuous, automated validation can catch DR-readiness gaps while there's still time to fix them — waiting for the next scheduled manual DR drill (often only annual) leaves long windows where a real gap could go completely undetected.

Solution Design

A weekly validation script checks DR replica lag against the defined RPO, tests DR-site network reachability, verifies recent backup files exist at the DR site, and confirms failover runbook scripts are present, executable, and syntactically valid — producing one composite readiness percentage and a detailed report.

Project Scope

In scope: read-only readiness validation across replication, network, backups, and runbook integrity. Explicitly out of scope, permanently: actually executing a failover, promoting a replica, or any other state-changing DR action — those remain deliberate, planned, human-led exercises.

Expected Outcome

A weekly DR-readiness scorecard catching replication lag, connectivity, backup, or runbook gaps within days rather than discovering them only during a real disaster — directly preventing a repeat of the six-hour failover.

🧠 New Bash Concepts for This Project

1. RPO Validation: Translating Replica Lag into Potential Data Loss

What: Reusing Project 7's SHOW REPLICA STATUS lag-checking technique, but reframing the result specifically against a business-defined RPO — "the DR replica is 8 minutes behind" becomes "if disaster struck right now, we'd lose up to 8 minutes of data, against an allowed maximum of 15."
Why: The same technical measurement (replication lag) takes on entirely different meaning and urgency when explicitly checked against a compliance-defined objective rather than just an operational threshold.

2. Why RTO Can't Be Directly Measured Without a Real Drill

What: Unlike RPO (which can be inferred from live replication lag), RTO — how long an actual failover would take — genuinely cannot be measured without performing a real failover, which is exactly the high-risk action this script must never do.
Why: This project validates readiness preconditions for a fast failover (working runbooks, current backups, healthy replication) as the best safe proxy available — it explicitly does not, and cannot, measure actual RTO without a genuine, carefully-planned drill.

3. Syntax-Only Validation Without Execution (bash -n)

What: bash -n script.sh parses a script for syntax errors without running a single line of it — -n stands for "no-exec."
Why: A failover runbook script sitting unused for months could have accumulated an unnoticed syntax error (a bad edit, an incomplete merge) — checking this without actually executing the runbook itself is the only safe way to validate it stays at least superficially correct.

4. Verifying Executability Without Running (-x Test, Reinforced)

What: [[ -x "$script" ]] — reinforcing the file-test operators used since Project 1, now specifically confirming a runbook script's execute permission bit is actually set, which bash -n alone does not check.
Why: A perfectly valid script that's lost its execute permission (a common side effect of certain file-copy operations) would fail to run during a real emergency exactly when it's needed most — both checks (syntax and permission) are necessary, and neither alone is sufficient.

5. Reusing Project 22's Diagnostic Functions Directly

What: source-ing Project 22's utils.sh (or a shared copy of its key functions) to reuse check_dns_resolution and check_port_reachable against the DR site specifically, rather than reimplementing equivalent logic.
Why: This is the course's "don't repeat yourself" philosophy in direct action — proven, tested diagnostic functions get reused across projects rather than rewritten with subtly different (and separately buggy) logic each time.

6. Composite Readiness Percentage Across Categories (Reinforced Project 13 Pattern)

What: READY_PCT=$(( PASSED_CHECKS * 100 / TOTAL_CHECKS )) — the same compliance-percentage formula from Project 13, now spanning four entirely different readiness categories (replication, network, runbooks, backups) rather than package versions.

7. An Explicit, Unconditional "Never Automate This" Boundary

What: Unlike every prior project's dry-run-then-live pattern (Projects 5, 10, 12, 19), this script has no live/remediation mode at all — there is no flag, no configuration option, no code path that performs any DR action whatsoever.
Why: Some actions are different in kind, not just degree, from the destructive-but-reversible operations earlier projects carefully gated with dry-run flags — an actual failover carries risk severe enough that this project draws a permanent, hard line rather than a configurable safety gate.

8. Building a Distributable Compliance Report (Reinforced Project 13's CSV Pattern)

What: The same structured CSV output technique from Project 13's patch-compliance report, now summarizing DR-readiness category by category for direct submission to Compliance/Audit.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - DR readiness helper functions
# (Assumes Project 7's DB functions and Project 22's network functions
#  are available - either copied in or sourced from their shared locations)
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- check_rpo_compliance ----------
# Purpose: Return "COMPLIANT lag_minutes" or "BREACH lag_minutes" for the DR replica
check_rpo_compliance() {
    local lag_seconds
    lag_seconds=$(timeout "$DB_CONNECT_TIMEOUT" mysql --defaults-extra-file="$DR_DB_CREDS_FILE" \
        -e "SHOW REPLICA STATUS\G" 2>/dev/null | grep "Seconds_Behind_Source" | awk -F': ' '{print $2}')

    [[ -z "$lag_seconds" ]] && { echo "UNKNOWN 0"; return; }

    local lag_minutes=$(( lag_seconds / 60 ))
    if [[ "$lag_minutes" -le "$RPO_MINUTES" ]]; then
        echo "COMPLIANT $lag_minutes"
    else
        echo "BREACH $lag_minutes"
    fi
}

# ---------- validate_runbook ----------
# Purpose: Return "VALID", "NOT_EXECUTABLE", or "SYNTAX_ERROR" for one runbook script - NEVER executes it
validate_runbook() {
    local runbook_path="$1"

    [[ -f "$runbook_path" ]] || { echo "MISSING"; return; }
    [[ -x "$runbook_path" ]] || { echo "NOT_EXECUTABLE"; return; }

    if bash -n "$runbook_path" 2>/dev/null; then
        echo "VALID"
    else
        echo "SYNTAX_ERROR"
    fi
}

# ---------- check_dr_backup_freshness ----------
# Purpose: Return the age in hours of the most recent file in the DR backup directory
check_dr_backup_freshness() {
    local backup_dir="$1"
    [[ -d "$backup_dir" ]] || { echo ""; return; }

    local newest_file
    newest_file=$(find "$backup_dir" -type f -printf '%T@ %p\n' 2>/dev/null | sort -rn | head -n 1 | cut -d' ' -f2-)
    [[ -z "$newest_file" ]] && { echo ""; return; }

    local file_epoch now_epoch
    file_epoch=$(stat -c '%Y' "$newest_file")
    now_epoch=$(date '+%s')
    echo $(( (now_epoch - file_epoch) / 3600 ))
}

Line-by-Line Highlights

  • check_rpo_compliance directly reuses Project 7's SHOW REPLICA STATUS parsing technique, but the final classification is against RPO_MINUTES — a compliance objective — rather than an operational WARN/CRITICAL threshold, illustrating how the same measurement serves different purposes in different contexts.
  • bash -n "$runbook_path" 2>/dev/null — critically, this never executes any line of the runbook; it only asks Bash's own parser "would this be valid to run," returning a non-zero exit code on any syntax problem without side effects.
  • find "$backup_dir" -type f -printf '%T@ %p\n' | sort -rn | head -n 1 — -printf '%T@' prints each file's modification epoch as a sortable number prefix; sorting numerically descending and taking the first line finds the single most recently modified file directly, without needing a separate loop.
  • Every function in this file is strictly read-only — note there is deliberately no function anywhere in this project that writes to, modifies, or executes anything related to the DR environment itself.

🩺 Main Script

scripts/dr_readiness_check.sh
#!/bin/bash
# =====================================================================
# dr_readiness_check.sh
# NovaTrust Bank - Disaster Recovery Readiness Validation
# READ-ONLY. This script NEVER executes a failover action of any kind.
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/dr_readiness.conf"

RUNBOOKS_FILE="$SCRIPT_DIR/../config/runbooks_registry.txt"
[[ -f "$RUNBOOKS_FILE" ]] || { echo "ERROR: Runbook registry not found: $RUNBOOKS_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/dr_readiness_${TODAY}.log"
CSV_REPORT="$SCRIPT_DIR/$REPORT_DIR/dr_readiness_${TODAY}.csv"
mkdir -p "$(dirname "$LOG_FILE")" "$(dirname "$CSV_REPORT")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "DR readiness check run finished."' EXIT

echo "category,item,status,detail" > "$CSV_REPORT"

log_message "INFO" "=== Starting DR readiness validation (READ-ONLY) ==="

TOTAL_CHECKS=0
PASSED_CHECKS=0

# ---------- Category 1: RPO / Replication ----------
RPO_RESULT=$(check_rpo_compliance)
read -r RPO_STATUS LAG_MINUTES <<< "$RPO_RESULT"
((TOTAL_CHECKS++))
if [[ "$RPO_STATUS" == "COMPLIANT" ]]; then
    log_message "PASS" "RPO: compliant - DR replica ${LAG_MINUTES}m behind (allowed: ${RPO_MINUTES}m)"
    echo "RPO,DR replica lag,COMPLIANT,${LAG_MINUTES} minutes behind" >> "$CSV_REPORT"
    ((PASSED_CHECKS++))
else
    log_message "FAIL" "RPO: $RPO_STATUS - DR replica ${LAG_MINUTES}m behind (allowed: ${RPO_MINUTES}m)"
    echo "RPO,DR replica lag,$RPO_STATUS,${LAG_MINUTES} minutes behind" >> "$CSV_REPORT"
fi

# ---------- Category 2: DR-site network reachability (reusing Project 22 techniques) ----------
((TOTAL_CHECKS++))
DR_RESOLVED_IP=$(check_dns_resolution "$DR_SITE_HOST")
if [[ -n "$DR_RESOLVED_IP" ]] && check_port_reachable "$DR_SITE_HOST" "$DR_SITE_PORT"; then
    log_message "PASS" "NETWORK: DR site $DR_SITE_HOST:$DR_SITE_PORT is reachable"
    echo "NETWORK,DR site connectivity,REACHABLE,$DR_SITE_HOST:$DR_SITE_PORT" >> "$CSV_REPORT"
    ((PASSED_CHECKS++))
else
    log_message "FAIL" "NETWORK: DR site $DR_SITE_HOST:$DR_SITE_PORT is NOT reachable"
    echo "NETWORK,DR site connectivity,UNREACHABLE,$DR_SITE_HOST:$DR_SITE_PORT" >> "$CSV_REPORT"
fi

# ---------- Category 3: Runbook integrity (never executed) ----------
while IFS= read -r runbook; do
    [[ -z "$runbook" || "$runbook" == \#* ]] && continue
    ((TOTAL_CHECKS++))

    RESULT=$(validate_runbook "$runbook")
    if [[ "$RESULT" == "VALID" ]]; then
        log_message "PASS" "RUNBOOK: $runbook is present, executable, and syntactically valid"
        echo "RUNBOOK,$runbook,VALID," >> "$CSV_REPORT"
        ((PASSED_CHECKS++))
    else
        log_message "FAIL" "RUNBOOK: $runbook - $RESULT"
        echo "RUNBOOK,$runbook,$RESULT," >> "$CSV_REPORT"
    fi
done < "$RUNBOOKS_FILE"

# ---------- Category 4: DR backup freshness ----------
((TOTAL_CHECKS++))
BACKUP_AGE_HOURS=$(check_dr_backup_freshness "$DR_BACKUP_DIR")
if [[ -z "$BACKUP_AGE_HOURS" ]]; then
    log_message "FAIL" "BACKUP: no backup files found at DR site ($DR_BACKUP_DIR)"
    echo "BACKUP,DR backup freshness,MISSING,no files found" >> "$CSV_REPORT"
elif [[ "$BACKUP_AGE_HOURS" -le "$BACKUP_MAX_AGE_HOURS" ]]; then
    log_message "PASS" "BACKUP: DR site backup is ${BACKUP_AGE_HOURS}h old (max allowed: ${BACKUP_MAX_AGE_HOURS}h)"
    echo "BACKUP,DR backup freshness,FRESH,${BACKUP_AGE_HOURS} hours old" >> "$CSV_REPORT"
    ((PASSED_CHECKS++))
else
    log_message "FAIL" "BACKUP: DR site backup is STALE - ${BACKUP_AGE_HOURS}h old (max allowed: ${BACKUP_MAX_AGE_HOURS}h)"
    echo "BACKUP,DR backup freshness,STALE,${BACKUP_AGE_HOURS} hours old" >> "$CSV_REPORT"
fi

# ---------- Composite readiness score ----------
READY_PCT=$(( PASSED_CHECKS * 100 / TOTAL_CHECKS ))
log_message "INFO" "=== DR READINESS SCORE: ${READY_PCT}% ($PASSED_CHECKS/$TOTAL_CHECKS checks passed) ==="
log_message "INFO" "CSV scorecard: $CSV_REPORT"

if [[ "$READY_PCT" -lt 100 ]]; then
    exit 2
fi
exit 0

🔄 What Happens Internally

  1. Four structurally different validation techniques — a database query, network diagnostics, static script analysis, and filesystem freshness checking — converge into one shared counter pair (TOTAL_CHECKS/PASSED_CHECKS), demonstrating how disparate readiness signals can combine into one meaningful composite metric.
  2. bash -n genuinely never executes the runbook — Bash's parser reads and validates the script's grammar entirely without running a single command inside it, making this check safe to run against even a runbook containing a real, destructive failover command.
  3. The complete absence of any execution code path for runbooks (not just a disabled flag, but no code that could execute one at all) is what makes this script's safety guarantee structural rather than merely configured — there's no setting to accidentally misconfigure into danger.
  4. The composite percentage treats every category as equally weighted in this implementation — a legitimate simplification worth flagging as a discussion point, since a real DR program might reasonably weight RPO compliance more heavily than, say, a single non-critical runbook's syntax.

🛡️ Production Best Practices

Never Automate an Actual Failover

DR readiness validation and DR execution are fundamentally different risk categories — keep them in permanently separate scripts, with no shared code path that could blur that line.

Validate Runbooks Without Running Them

bash -n plus an executable-bit check catches real, common failure modes (syntax drift, lost permissions) with zero risk of accidentally triggering a real action.

Reframe Technical Metrics Against Business Objectives

The same replication-lag measurement means something different, and carries different urgency, when explicitly checked against a defined RPO rather than a generic operational threshold.

Reuse Proven Diagnostic Code Across Projects

Project 22's network functions and Project 7's database functions being directly reusable here is the payoff of building genuinely modular, well-scoped utility functions throughout this course.

Treat Any Gap as Worth Flagging

DR readiness isn't a metric where 90% is "good enough" — a single broken runbook or one stale backup can be the exact thing that turns a real disaster into a much longer outage.

Test Continuously, Not Just During Annual Drills

Weekly automated validation catches degradation within days; relying solely on an annual manual drill leaves months of blind exposure between checks.

🎤 Interview Preparation

Scenario: The readiness score shows 100% every single week for months, then a real disaster still reveals a problem this script never caught. What's a plausible explanation?
This script validates specific, defined preconditions (replication currency, connectivity, runbook syntax, backup freshness) — it cannot validate everything about DR readiness, such as whether the runbook's actual logic (not just its syntax) correctly handles the specific failure scenario that occurred, or human factors like whether the on-call team actually knows how to execute the runbooks under pressure; 100% on this scorecard is necessary but not sufficient for full DR confidence.
Production Support: A runbook shows SYNTAX_ERROR in this week's report, but it ran successfully during a drill three months ago. What changed?
Someone very likely edited the runbook since that drill — perhaps updating a hostname or command — and introduced an error, or a change elsewhere (a referenced file, a sourced library) broke something the script depends on; this is exactly the kind of unnoticed drift the weekly check exists to catch quickly rather than discovering it during a real failover attempt.
Shell Scripting: Why is bash -n described as validating "syntax" specifically, and what kinds of runbook problems would it NOT catch?
bash -n only confirms the script parses as grammatically valid Bash — it would not catch a script that's syntactically perfect but logically wrong (e.g., pointing at the wrong DR database hostname, or a command that would fail at actual runtime due to a missing dependency); it's a narrow, safe check, not a full validation of correctness.
Troubleshooting: The composite readiness percentage shows 85% but you can't immediately tell which specific category is failing. How would you find out fast?
Check the CSV scorecard directly — it records category, item, and status for every individual check, making it straightforward to filter for any non-PASS/non-COMPLIANT/non-VALID/non-FRESH rows rather than needing to re-read the full operational log.
Manager Round: Why does this project treat every readiness category as equally weighted in the composite percentage, and is that actually the right approach?
Equal weighting is a simplification made for clarity in this implementation — a stronger real-world version might weight RPO compliance (directly regulatory-relevant) more heavily than a single non-critical runbook's syntax validity; this is a legitimate area for refinement based on the organization's actual risk priorities, worth discussing explicitly rather than assuming equal weighting is automatically correct.
Architecture: Why does this project explicitly avoid even a dry-run mode for failover actions, unlike nearly every other destructive-capable script in this course?
A dry-run flag still implies the underlying capability to execute exists somewhere in the code, gated by a flag that could be misconfigured or bypassed; for an action as high-risk and consequential as a real failover, this project instead ensures the execution capability simply doesn't exist in the code at all, which is a stronger guarantee than any configuration-based safety gate.
Best Practice: Why check DR backup freshness specifically at the DR site, rather than just trusting that Project 11's backup script already verified the backup was good at creation time?
Project 11 verifies the backup was correctly created and successfully transferred at the time it ran; this project instead verifies, independently and later, that a recent backup still actually exists and is current at the DR site right now — protecting against a separate failure mode, like a subsequent process accidentally deleting DR backups or a transfer job silently breaking sometime after Project 11's own check passed.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the days-long replication lag before the actual regional outage occurred?
Weekly, automated RPO-compliance checking against the DR replica specifically (not just production) — the lag would have crossed the 15-minute RPO threshold and appeared as a BREACH in the very first weekly readiness report after it began, giving weeks of advance warning instead of the gap being discovered only during the real disaster it was meant to protect against.
