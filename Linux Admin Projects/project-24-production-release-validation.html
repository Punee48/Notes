Project 24 of 30 · Release Engineering

Production Release Validation

The deploy command succeeded on all 200 servers. Fifteen of them, thanks to a caching bug, quietly kept running last week's code for seven days.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL + SSH + curl ⏱️ Duration: 3 hrs

📖 The Story — "Deployed" Doesn't Mean "Running the New Version"

A routine release went out to all 200 Core Banking servers. The deployment tool reported complete success on every single one. What nobody discovered for a full week was that an internal package-repository caching bug had silently served the previous release's artifact to 15 of those servers — the deploy command itself ran perfectly and exited zero on all 200, but 15 of them ended up running stale code, creating subtle data inconsistencies that surfaced only when an unrelated investigation happened to compare version numbers across servers.

Priya's assignment: "'The deploy command succeeded' has never once told us whether the new code is actually running. I want a validation gate that runs immediately after every deployment — checks the real running version on every single server against what we expected, runs a quick smoke test against critical functionality, confirms we could still roll back if needed — and gives one clear GO or NO-GO signal our pipeline can act on automatically."

This project produces a gate, not a monitor — its entire purpose is answering one question, definitively, within a tight time budget, immediately after a release.
🔁 Reinforced from Projects 1–23
Project 13's compliance-percentage pattern, Project 8's status+body validation (now as a focused smoke test), and Project 2's fleet-wide SSH loop all converge here into one deployment-gate script.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Independently verify, immediately after any production release, that the new version is actually running fleet-wide and that critical functionality works — producing one clear GO/NO-GO decision.

Customer Requirement

Release engineering needs an automated, fast, and reliable answer to "did this actually deploy correctly everywhere" that a CI/CD pipeline can act on without human intervention.

Banking Scenario

NovaTrust deploys Core Banking application updates across its 200-server fleet through an automated deployment tool, whose own success reporting had never been independently verified until now.

Existing Manual Process / Prior Automation Gap

Deployment success was measured entirely by the deployment tool's own exit code — no independent verification step confirmed the new version was actually running where it was supposed to be.

Problems With Trusting the Deploy Tool Alone

A deployment tool can succeed at everything within its own visibility (executing its deploy steps) while remaining completely blind to an external failure mode (a caching layer silently serving stale artifacts) entirely outside its awareness.

Business Impact & Risk

Seven days of a subset of servers running mismatched code versions created real data inconsistencies before detection — exactly the kind of subtle, compounding problem an immediate post-deploy check would have caught within minutes.

Why Automation Is Required

Only an independent, automated check — never trusting the deployment tool's own self-reported success — can catch a version mismatch or functional regression within the tight window immediately after a release, before it has time to cause real damage.

Solution Design

Immediately following a deployment, query every server's actual running version via its own version endpoint, compare against the expected release version from a deployment manifest, run a focused smoke test suite against critical endpoints, confirm the previous version's rollback artifact is still available, and produce one GO/NO-GO verdict within a strict time budget.

Project Scope

In scope: fleet-wide version verification, focused smoke testing, rollback-artifact availability checking, and a GO/NO-GO gate. Out of scope: performing the deployment or rollback itself — this script is a validation gate a pipeline consumes, not the deployment or rollback mechanism.

Expected Outcome

Within minutes of any release, a definitive GO/NO-GO answer — catching exactly the kind of partial, silently-stale deployment that took a full week to discover manually.

🧠 New Bash Concepts for This Project

1. Fleet-Wide Version Verification (Reinforced Project 13 Pattern, New Data Source)

What: Querying each server's own /version HTTP endpoint (via curl, reinforcing Project 8) and comparing against an expected version string — structurally identical to Project 13's package-version compliance check, just sourced from an application endpoint instead of dpkg-query.
Why: This is the single check that would have directly caught the caching-bug incident — a server serving stale code would report its old version string, immediately visible against the manifest's expected value.

2. The Deployment Manifest as Source of Truth

What: A small file, generated by the deployment pipeline itself (not this script), stating exactly which version was supposed to be deployed and to which servers — reinforcing the config-driven, external-source-of-truth pattern used since Project 1's threshold file.
Why: This script must never assume or infer the expected version from its own logic — it needs an authoritative, externally-provided statement of intent to validate reality against.

3. A Focused Smoke-Test Suite (Narrower Than Project 8's Monitoring Suite)

What: A small, deliberately minimal set of critical-path checks (e.g., "can we create a test transaction," "does the balance-lookup endpoint respond correctly") — reusing Project 8's status+body validation technique, but scoped tightly to what genuinely matters immediately post-deploy.
Why: A release gate needs to be fast and focused — this is not the place for Project 8's full continuous-monitoring endpoint list, but a specific, minimal subset chosen because it would catch a genuinely broken release quickly.

4. Rollback-Artifact Availability Checking

What: Confirming the previous release's deployable artifact (a package file, a container image tag, a specific backup) still exists and is accessible before declaring the new release fully validated.
Why: A release should never be considered "safely deployed" if rolling back is no longer actually possible — this check ensures the safety net is still there, independent of whether the new release itself looks fine.

5. Enforcing a Strict Time Budget (Reinforced timeout, New Context)

What: Wrapping the entire validation run in an outer timeout, not just individual network calls — timeout 300 bash -c 'run all validation steps' — ensuring the whole gate either completes or fails within a strict overall budget.
Why: A CI/CD pipeline typically cannot wait indefinitely for a validation gate — a hung gate blocking a release pipeline indefinitely is itself an operational problem this design must prevent.

6. The GO/NO-GO Exit-Code Convention for Pipeline Consumption

What: A strict, simple convention — exit 0 means GO, any non-zero exit means NO-GO — designed specifically to be consumed directly by an external CI/CD pipeline's own conditional logic (e.g., a Jenkins/GitLab CI step checking $?).
Why: This is a different audience than every prior project's exit code — not a human reading a log, but an automated pipeline making a real, consequential decision (proceed vs. hold vs. trigger rollback) based purely on this one number.

7. Fleet-Wide Version Consistency, Not Just Correctness

What: Checking not only "does each server report the expected version" but implicitly surfacing "are all servers reporting the same version as each other" — a mixed-version fleet is its own distinct problem even if some servers happen to match the manifest.
Why: A fleet where some servers run the new version and others still run the old one is a worse, more confusing state than a fleet uniformly on the old version — this distinction matters for how the NO-GO finding should be communicated.

8. This Script as a Pipeline Component, Not a Standalone Tool (Conceptual)

What: Unlike every previous project, this script is explicitly designed to be one step within a larger, external CI/CD pipeline (Jenkins, GitLab CI, GitHub Actions, or similar) — it doesn't deploy anything itself, and its output is meant to be consumed programmatically, not primarily read by a human.
Why: Understanding this script's role as a gate within a bigger automated system, rather than a complete end-to-end tool, is itself an important production-engineering concept — Bash scripts frequently serve as focused components inside much larger orchestrated systems.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Release validation helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_reported_version ----------
get_reported_version() {
    local version_url="$1"
    curl -s --connect-timeout "$HTTP_CONNECT_TIMEOUT" --max-time "$HTTP_MAX_TIME" "$version_url" 2>/dev/null |
        jq -r '.version // empty' 2>/dev/null
}

# ---------- run_smoke_test ----------
# Purpose: Return 0 if a single smoke test (status + body marker) passes
run_smoke_test() {
    local url="$1"
    local expected_status="$2"
    local expected_marker="$3"

    local body_file result http_status
    body_file=$(mktemp)
    result=$(curl -s -o "$body_file" --connect-timeout "$HTTP_CONNECT_TIMEOUT" --max-time "$HTTP_MAX_TIME" \
        -w "%{http_code}" "$url" 2>/dev/null)
    http_status="$result"

    local passed=1
    if [[ "$http_status" == "$expected_status" ]] && grep -qF -- "$expected_marker" "$body_file"; then
        passed=0
    fi
    rm -f "$body_file"
    return $passed
}

# ---------- check_rollback_artifact_available ----------
check_rollback_artifact_available() {
    local artifact_dir="$1"
    local previous_version="$2"
    [[ -e "$artifact_dir/${previous_version}" ]] || [[ -e "$artifact_dir/release-${previous_version}.tar.gz" ]]
}

Line-by-Line Highlights

  • jq -r '.version // empty' — assumes each server's /version endpoint returns a small JSON body like {"version":"2.14.3"}; the // default (reinforced from Projects 14, 18, 19) handles a missing field gracefully rather than erroring.
  • run_smoke_test reuses Project 8's exact status+body validation logic verbatim — a deliberate demonstration that a well-designed function from one project can be dropped directly into a different project with a genuinely different purpose (continuous monitoring vs. one-shot release gating) without modification.
  • check_rollback_artifact_available checks two plausible artifact-naming conventions with || — a defensive touch acknowledging that "how the previous release is stored" can reasonably vary by deployment tooling, without over-engineering the check.

🩺 Main Script

scripts/release_validation.sh
#!/bin/bash
# =====================================================================
# release_validation.sh
# NovaTrust Bank - Post-Deployment GO/NO-GO Validation Gate
# Exit 0 = GO. Any non-zero exit = NO-GO. Meant to be called by a CI/CD pipeline.
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/release_validation.conf"

MANIFEST_FILE="$SCRIPT_DIR/../config/deployment_manifest.txt"
SMOKE_TEST_FILE="$SCRIPT_DIR/../config/smoke_tests.txt"
[[ -f "$MANIFEST_FILE" ]] || { echo "ERROR: Deployment manifest not found: $MANIFEST_FILE" >&2; exit 1; }

TIMESTAMP=$(date '+%Y%m%d_%H%M%S')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/release_validation_${TIMESTAMP}.log"
mkdir -p "$(dirname "$LOG_FILE")"

log_message "INFO" "=== Starting post-deployment release validation (budget: ${VALIDATION_TIME_BUDGET_SECONDS}s) ==="

# ---------- Everything below runs inside ONE outer time budget ----------
timeout "$VALIDATION_TIME_BUDGET_SECONDS" bash -c '
    source "'"$SCRIPT_DIR"'/utils.sh"
    source "'"$SCRIPT_DIR"'/../config/release_validation.conf"
    LOG_FILE="'"$LOG_FILE"'"

    # Line 1 of the manifest: expected_version:previous_version
    read -r VERSION_LINE < "'"$MANIFEST_FILE"'"
    EXPECTED_VERSION="${VERSION_LINE%%:*}"
    PREVIOUS_VERSION="${VERSION_LINE##*:}"

    MISMATCH_COUNT=0
    TOTAL_SERVERS=0

    # ---------- Check 1: Fleet-wide version verification ----------
    while IFS=: read -r host version_url; do
        [[ -z "$host" || "$host" == \#* || "$host" == "$VERSION_LINE" ]] && continue
        [[ "$host" =~ ^https?:// ]] && continue   # Skip the version_url half when IFS splits oddly on full URLs

        ((TOTAL_SERVERS++))
        REPORTED=$(get_reported_version "$version_url")
        if [[ "$REPORTED" != "$EXPECTED_VERSION" ]]; then
            log_message "FAIL" "VERSION MISMATCH: $host reports '"'"'${REPORTED:-NONE}'"'"' (expected $EXPECTED_VERSION)"
            ((MISMATCH_COUNT++))
        else
            log_message "PASS" "$host: running expected version $EXPECTED_VERSION"
        fi
    done < "'"$MANIFEST_FILE"'"

    if [[ "$MISMATCH_COUNT" -gt 0 ]]; then
        log_message "FAIL" "=== NO-GO: $MISMATCH_COUNT of $TOTAL_SERVERS servers on wrong version ==="
        exit 1
    fi

    # ---------- Check 2: Smoke tests ----------
    SMOKE_FAILURES=0
    while IFS=: read -r url expected_status expected_marker; do
        [[ -z "$url" || "$url" == \#* ]] && continue
        if run_smoke_test "$url" "$expected_status" "$expected_marker"; then
            log_message "PASS" "SMOKE TEST: $url"
        else
            log_message "FAIL" "SMOKE TEST FAILED: $url"
            ((SMOKE_FAILURES++))
        fi
    done < "'"$SMOKE_TEST_FILE"'"

    if [[ "$SMOKE_FAILURES" -gt 0 ]]; then
        log_message "FAIL" "=== NO-GO: $SMOKE_FAILURES smoke test(s) failed ==="
        exit 1
    fi

    # ---------- Check 3: Rollback artifact availability ----------
    if ! check_rollback_artifact_available "$ROLLBACK_ARTIFACT_DIR" "$PREVIOUS_VERSION"; then
        log_message "FAIL" "=== NO-GO: rollback artifact for version $PREVIOUS_VERSION not found - no safety net available ==="
        exit 1
    fi
    log_message "PASS" "Rollback artifact for $PREVIOUS_VERSION is available"

    log_message "INFO" "=== GO: all $TOTAL_SERVERS servers on version $EXPECTED_VERSION, smoke tests passed, rollback available ==="
'
VALIDATION_EXIT=$?

if [[ "$VALIDATION_EXIT" -eq 124 ]]; then
    log_message "FAIL" "=== NO-GO: validation did NOT complete within the ${VALIDATION_TIME_BUDGET_SECONDS}s time budget ==="
    exit 1
fi

exit "$VALIDATION_EXIT"

Every Line, Explained

LineExplanation
timeout "$VALIDATION_TIME_BUDGET_SECONDS" bash -c '...'Wraps the entire multi-step validation sequence in one outer time budget — this is the whole-run enforcement described in the concepts section, distinct from the per-request timeouts already inside curl calls.
Variables re-sourced inside the bash -c blockA subshell launched via bash -c doesn't inherit the parent script's sourced functions/variables automatically, so utils.sh and the config are explicitly re-sourced inside the quoted block to make them available there.
VALIDATION_EXIT=$? immediately after the timeout callCaptures the actual result — either the validation logic's own exit code, or 124, which is timeout's specific, standard signal that the wrapped command was killed for exceeding its time budget.
if [[ "$VALIDATION_EXIT" -eq 124 ]]; then ...Distinguishes "the validation logic itself found a real problem" from "the validation simply ran out of time" — both are NO-GO outcomes, but this distinction is valuable for whoever investigates the failed pipeline run afterward.
Every failure path calls exit 1 inside the subshell, final line calls exit "$VALIDATION_EXIT"Strictly maintains the GO(0)/NO-GO(non-zero) convention throughout — this script's only real "output," in the sense a pipeline consumes, is this single exit code.

🔗 CI/CD Integration Point (Conceptual)

This script is a gate, not a standalone tool — it's designed to be one step inside a larger, external pipeline. A simplified example of how a pipeline might consume it:

Conceptual pipeline pseudocode (e.g., a Jenkins/GitLab CI stage)
stage("Post-Deploy Validation") {
    ./scripts/release_validation.sh
    if [ $? -eq 0 ]; then
        echo "GO - proceeding to mark release complete"
        # pipeline continues normally
    else
        echo "NO-GO - triggering automatic rollback"
        ./deploy_tool.sh rollback --to-version "$PREVIOUS_VERSION"
        # pipeline halts / pages on-call
    fi
}

📄 README.md

README.md
# NovaTrust Bank - Production Release Validation Gate

## Usage (invoked by CI/CD immediately after deployment)
    ./scripts/release_validation.sh

## GO/NO-GO Contract
    Exit 0   = GO   - safe to proceed, mark release complete
    Exit != 0 = NO-GO - hold or trigger rollback

## What Gets Checked (in order)
1. Every server's actual reported version matches the deployment manifest's expected version
2. A small, focused smoke-test suite against critical-path endpoints
3. The previous version's rollback artifact is still available

## Time Budget
The ENTIRE validation (not just individual network calls) must complete
within VALIDATION_TIME_BUDGET_SECONDS, or the result is automatically NO-GO.

## Note
This script does NOT deploy or roll back anything itself. It is a
validation gate meant to be called by an external CI/CD pipeline, which
is responsible for acting on the GO/NO-GO result.

🔄 What Happens Internally

  1. The outer timeout wraps the entire multi-step sequence, not just individual calls — a genuinely different scope of time-boxing than every prior project's per-request timeouts, appropriate for this script's role as a bounded pipeline gate.
  2. Exit code 124 is timeout's own specific signal for "the wrapped command was killed for running too long" — checking for this exact value lets the script distinguish a genuine validation failure from a budget-exceeded failure, even though both ultimately produce the same NO-GO exit code to the calling pipeline.
  3. Version verification, smoke testing, and rollback-artifact checking run as three sequential, independently-failing stages — mirroring Project 11's chained-verification philosophy, where any single stage's failure immediately short-circuits to a NO-GO rather than continuing to run further checks that couldn't change the outcome.
  4. The script's real "output" is a single number — everything else (the detailed log) exists for human troubleshooting after the fact, but the pipeline itself only ever needs to check $?.

🛡️ Production Best Practices

Never Trust a Deployment Tool's Self-Reported Success

Independent, external verification of the actual resulting state catches failure modes entirely outside the deployment tool's own visibility.

Keep Release Gates Fast and Focused

A smoke-test suite for a release gate should be deliberately minimal — this is not the place for comprehensive monitoring coverage, which belongs in continuous checks like Project 8.

Verify Rollback Is Actually Possible

A release isn't safely deployed if the safety net (rollback capability) has quietly become unavailable — check for this explicitly, don't assume it.

Bound the Entire Gate, Not Just Individual Calls

An outer time budget on the whole validation sequence prevents a hung gate from blocking an entire release pipeline indefinitely.

Design for a Programmatic Consumer

When the "reader" of a script's result is a pipeline rather than a human, the exit code contract must be simple, strict, and absolutely reliable — this is the entire interface.

Chain Validation Stages, Stop at First Failure

Once any stage fails, further checks can't change a NO-GO into a GO — short-circuiting saves time within the tight budget this kind of gate operates under.

🎤 Interview Preparation

Scenario: The validation gate reports GO, but customers report issues with the new release within an hour. What does this specifically tell you about the gate's limitations?
The gate validated exactly what it was designed to check — version consistency, a narrow smoke-test suite, and rollback availability — none of which guarantees the release is free of subtler functional bugs outside the smoke tests' specific coverage; this is an argument for periodically reviewing and expanding the smoke-test suite based on past incidents, not evidence the gate itself is broken.
Production Support: The pipeline shows a NO-GO, but the log shows all checks actually passed. What's the likely explanation?
The exit code 124 path — the outer time budget was exceeded even though the checks that did complete all passed; the pipeline correctly treated a timeout as NO-GO (since an incomplete validation provides no real assurance), but the specific cause was a slow run, not a genuine failing check.
Shell Scripting: Why does the script re-source utils.sh and the config file inside the timeout ... bash -c '...' block, when they were already sourced earlier in the same script?
bash -c '...' launches a genuinely new, separate Bash process that does not inherit the parent shell's sourced functions or variables (only exported environment variables would carry over, and functions aren't exported by default) — everything needed inside that subshell must be explicitly re-established there.
Troubleshooting: A GO result was produced, but investigating afterward, only 2 of the expected 3 servers were actually checked. What manifest-parsing bug would explain this?
The line-skipping logic (guarding against the version-declaration line and any malformed lines) may be too aggressive and accidentally skipping a legitimate server entry — worth adding an explicit TOTAL_SERVERS sanity check against the manifest's actual expected server count as an additional safeguard.
Manager Round: Why does this project keep its smoke-test suite deliberately smaller than Project 8's continuous monitoring endpoint list?
A release gate operates under a strict time budget and blocks the deployment pipeline while it runs — every additional check adds real latency to every single release; the smoke-test suite should contain only the highest-value checks that would reliably catch a genuinely broken release, leaving comprehensive ongoing coverage to the separate, continuously-running Project 8 monitoring.
Architecture: Why is this script explicitly described as not performing the deployment or rollback itself?
Separation of concerns: the deployment mechanism, this validation gate, and any rollback mechanism are three distinct responsibilities with different risk profiles and different appropriate owners/tools; combining them into one script would make each harder to test, reason about, and safely modify independently.
Best Practice: Why must the entire validation run inside one outer timeout, rather than relying solely on the individual timeouts already present on each curl call?
Individual per-call timeouts bound each single network request, but the cumulative time across many sequential servers and smoke tests could still add up to an unacceptably long total runtime even if every individual call is fast — the outer budget is the only mechanism that actually guarantees the whole gate finishes (or fails) within a time a CI/CD pipeline can reasonably tolerate.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the 15-server caching-bug incident within minutes instead of a week?
Independently querying each server's own reported /version value immediately after deployment, rather than trusting the deployment tool's own success report — the 15 stale servers would have shown a version mismatch in that very first post-deploy validation run, triggering an immediate NO-GO and likely an automatic rollback, rather than continuing to silently serve outdated code for seven full days.

Key Learnings

Independent post-deployment version verification, focused smoke-testing scoped for a fast release gate, rollback-artifact availability checking, whole-run time budgeting with timeout, and designing a script whose entire interface to its consumer is a single, strict exit-code contract.

Common Mistakes to Avoid

Trusting a deployment tool's own success reporting as sufficient proof, building an oversized smoke-test suite that slows every release, forgetting to check rollback availability, bounding only individual network calls instead of the whole validation run, and blurring the line between validation and actual deployment/rollback execution.
