Project 12 of 30 · Security

File Integrity Monitoring

A "quick fix" edited directly on a production NEFT config file, outside change control — and three weeks passed before anyone noticed.

🎯 Level: Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL ⏱️ Duration: 3 hrs

📖 The Story — The Edit Nobody Approved

A security review traced a string of subtle NEFT transfer-processing bugs back to a single configuration file that had been hand-edited directly on the production server three weeks earlier — no change ticket, no peer review, no record of who did it or why. Someone was almost certainly trying to fix a real problem quickly under pressure, and it worked, for a while, until it didn't.

Priya's directive is clear: "Every change to our critical configuration files needs to be either something we approved, or something we get alerted about immediately. I want a baseline of exactly what these files should look like, a daily comparison against that baseline, and a clear report of anything ADDED, REMOVED, or MODIFIED — with a proper, deliberate process for updating the baseline itself when we do approve a change."

Today's project protects something different again — not servers, not data, but the trustworthiness of the configuration that governs how NovaTrust's systems actually behave.
🔁 Reinforced from Projects 1–11
sha256sum (Project 11), associative arrays (Projects 2 & 4), and the mandatory dry-run/deliberate-authorization pattern (Project 5, Project 10) all return here in a security context.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Detect any unauthorized modification, addition, or removal of critical configuration files on Core Banking servers, within one daily cycle.

Customer Requirement

Security needs to distinguish between changes that went through proper change control and any that bypassed it — with a same-day detection window, not weeks.

Banking Scenario

Core Banking, NEFT Gateway, and Fraud Detection services all depend on configuration files that directly govern business logic, thresholds, and connection settings.

Existing Manual Process

None — file changes were entirely untracked outside of whatever the change-ticket process captured manually, with no independent technical verification that reality matched the record.

Problems We're Solving Proactively

A determined or well-intentioned-but-unauthorized direct edit leaves zero trace under the current setup — exactly what happened, and exactly why it took three weeks to trace.

Business Impact & Risk

Unauthorized configuration changes bypass every safeguard change control exists to provide — peer review, testing, rollback planning — and are a direct audit and security finding in a regulated banking environment.

Why Automation Is Required

Only a script comparing current file state against a trusted baseline, on a fixed schedule, can guarantee same-day detection of any unauthorized change, regardless of who made it or how quietly.

Solution Design

Establish a cryptographic checksum baseline for a defined set of critical files, compare against that baseline daily, clearly report ADDED/REMOVED/MODIFIED files, and provide a deliberate, logged process for updating the baseline only when a change is genuinely authorized.

Project Scope

In scope: content-checksum monitoring, permission/ownership monitoring, baseline management with an authorization step, and daily comparison reporting. Out of scope: real-time (inotify-based) file-change detection — this project is scheduled/batch-based, matching every other project's cadence.

Expected Outcome

Any unauthorized change to a monitored file is detected and reported within one day, while legitimate, approved changes can be incorporated into a new baseline through a clear, auditable, deliberate step.

🧠 New Bash Concepts for This Project

1. Building a Multi-File Checksum Manifest

What: Running sha256sum across every file in a monitored list and saving all results into one manifest file, one line per file — extending Project 11's single-file checksum to many files at once.
Why: A baseline needs to capture the state of an entire set of critical files together, as one point-in-time snapshot.

2. Capturing Permissions and Ownership (stat -c, Reinforced)

What: stat -c '%a %U:%G' file — extending Project 7's single-field permission check to also capture owner and group together.
Why: A file's content can be untouched while its permissions are quietly loosened (e.g., made world-writable) — content checksums alone would miss this entirely, so we track both.

3. Loading a Manifest into an Associative Array

What: Reading each baseline manifest line into BASELINE_CHECKSUMS["$filepath"]="$checksum", giving instant lookup by filename.
Why: Comparing "does this file's current checksum match its baseline" is a simple, fast array lookup rather than re-scanning the entire manifest file for every single comparison.

4. Detecting Added and Removed Files with Set Comparison

What: Comparing the set of filenames in the current scan against the set of filenames in the baseline — files in "current but not baseline" are ADDED; files in "baseline but not current" are REMOVED.
Why: An entirely new unauthorized file, or a file's outright deletion, are just as much integrity violations as a modified one — and require genuinely different detection logic than a checksum comparison.

5. Comparing Sorted Lists with comm

What: comm -23 sorted_current.txt sorted_baseline.txt prints lines unique to the first file only — exactly the "added" set; comm -13 gives the reverse (removed).
Why: comm is purpose-built for exactly this kind of set-difference operation on sorted text, and is more efficient and readable than a manual nested-loop comparison in Bash.
Requirement: Both input files must be sorted first (sort) — comm assumes sorted input and produces wrong results otherwise.

6. Iterating an Associative Array's Keys

What: for filepath in "${!BASELINE_CHECKSUMS[@]}"; do ... done — the ! prefix on an array expansion returns its keys rather than its values.
Why: We need to walk every file the baseline knows about to check whether each one still exists and still matches, not just process the current scan's files.

7. A Deliberately Separate "Update Baseline" Command

What: A completely distinct script invocation (requiring an explicit change-ticket argument) rather than any flag on the routine daily comparison run.
Why: Baseline acceptance is a security-sensitive action — it must never be reachable via any code path that also runs unattended from cron, precisely to prevent an unauthorized change from ever silently becoming the new "trusted" state.

8. Excluding Paths via Pattern Matching

What: Checking each candidate file against a configured list of exclude patterns using [[ "$file" == $pattern ]] glob matching before including it in the scan.
Why: Some files legitimately change often (rotating logs, generated cache files) and would create constant false-positive noise if included in integrity monitoring meant for genuinely static configuration.

9. A Change-Ticket-Referenced Audit Entry (Reinforced from Project 10)

What: Every baseline update records not just what changed, but the change-ticket reference and operator who authorized it — the exact same audit_log pattern from Project 10's user lifecycle project, applied to configuration instead of accounts.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - File Integrity Monitoring helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

audit_log() {
    local action="$1"; local detail="$2"
    local timestamp operator
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    operator="${SUDO_USER:-$(whoami)}"
    echo "${timestamp}|${operator}|${action}|${detail}" >> "$AUDIT_LOG"
}

# ---------- is_excluded ----------
# Purpose: Return 0 (true) if a file matches any configured exclude glob pattern
is_excluded() {
    local file="$1"
    local pattern
    for pattern in "${EXCLUDE_PATTERNS[@]}"; do
        [[ "$file" == $pattern ]] && return 0            # Unquoted $pattern is intentional - enables glob matching
    done
    return 1
}

# ---------- capture_file_state ----------
# Purpose: Print one manifest line for a file: path|checksum|perms|owner:group
capture_file_state() {
    local file="$1"
    [[ -f "$file" ]] || return 1

    local checksum perms owner_group
    checksum=$(sha256sum "$file" | awk '{print $1}')
    perms=$(stat -c '%a' "$file")
    owner_group=$(stat -c '%U:%G' "$file")

    echo "${file}|${checksum}|${perms}|${owner_group}"
}

# ---------- load_baseline ----------
# Purpose: Load the baseline manifest into three parallel associative arrays, keyed by file path
load_baseline() {
    while IFS='|' read -r path checksum perms owner_group; do
        [[ -z "$path" || "$path" == \#* ]] && continue
        BASELINE_CHECKSUM["$path"]="$checksum"
        BASELINE_PERMS["$path"]="$perms"
        BASELINE_OWNER["$path"]="$owner_group"
    done < "$BASELINE_FILE"
}

Line-by-Line Highlights

  • [[ "$file" == $pattern ]] — the pattern variable is deliberately left unquoted here so Bash treats it as a glob pattern (matching * and ? as wildcards) rather than a literal string; this is one of the rare intentional exceptions to "always quote your variables."
  • capture_file_state combines three separate pieces of state (checksum, permissions, owner) into one pipe-delimited manifest line — the same delimited-record pattern used for Project 7's instance file and Project 10's audit log.
  • load_baseline populates three separate associative arrays (checksum, perms, owner) all keyed by the same file path — keeping them separate rather than packing all three into one string value makes each individual comparison in the main script simpler and clearer.

🩺 Main Script — Daily Comparison

scripts/fim_check.sh
#!/bin/bash
# =====================================================================
# fim_check.sh
# NovaTrust Bank - Daily File Integrity Comparison (READ-ONLY on baseline)
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/fim.conf"

MONITORED_FILE="$SCRIPT_DIR/../config/monitored_paths.txt"
BASELINE_FILE="$SCRIPT_DIR/$BASELINE_FILE"
[[ -f "$BASELINE_FILE" ]] || { echo "ERROR: No baseline found. Run fim_update_baseline.sh first." >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/fim_check_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another FIM check instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "FIM check run finished."' EXIT

declare -A BASELINE_CHECKSUM BASELINE_PERMS BASELINE_OWNER
load_baseline

log_message "INFO" "=== Starting file integrity check against baseline ==="

# ---------- Build sorted current and baseline filename lists for comm ----------
CURRENT_LIST=$(mktemp)
BASELINE_LIST=$(mktemp)

while IFS= read -r file; do
    [[ -z "$file" || "$file" == \#* ]] && continue
    is_excluded "$file" && continue
    [[ -f "$file" ]] && echo "$file" >> "$CURRENT_LIST"
done < "$MONITORED_FILE"

printf '%s\n' "${!BASELINE_CHECKSUM[@]}" > "$BASELINE_LIST"

sort -o "$CURRENT_LIST" "$CURRENT_LIST"
sort -o "$BASELINE_LIST" "$BASELINE_LIST"

VIOLATIONS=0

# ---------- ADDED: in current, not in baseline ----------
while IFS= read -r added_file; do
    [[ -z "$added_file" ]] && continue
    log_message "FAIL" "ADDED (unauthorized new file): $added_file"
    audit_log "VIOLATION_ADDED" "$added_file"
    ((VIOLATIONS++))
done < <(comm -23 "$CURRENT_LIST" "$BASELINE_LIST")

# ---------- REMOVED: in baseline, not in current ----------
while IFS= read -r removed_file; do
    [[ -z "$removed_file" ]] && continue
    log_message "FAIL" "REMOVED (missing critical file): $removed_file"
    audit_log "VIOLATION_REMOVED" "$removed_file"
    ((VIOLATIONS++))
done < <(comm -13 "$CURRENT_LIST" "$BASELINE_LIST")

# ---------- MODIFIED: present in both, but checksum or permissions differ ----------
while IFS= read -r common_file; do
    [[ -z "$common_file" ]] && continue

    CURRENT_STATE=$(capture_file_state "$common_file")
    IFS='|' read -r _ current_checksum current_perms current_owner <<< "$CURRENT_STATE"

    if [[ "$current_checksum" != "${BASELINE_CHECKSUM[$common_file]}" ]]; then
        log_message "FAIL" "MODIFIED (content changed): $common_file"
        audit_log "VIOLATION_MODIFIED_CONTENT" "$common_file"
        ((VIOLATIONS++))
    elif [[ "$current_perms" != "${BASELINE_PERMS[$common_file]}" || "$current_owner" != "${BASELINE_OWNER[$common_file]}" ]]; then
        log_message "FAIL" "MODIFIED (permissions/owner changed): $common_file (now ${current_perms} ${current_owner})"
        audit_log "VIOLATION_MODIFIED_PERMS" "$common_file"
        ((VIOLATIONS++))
    fi
done < <(comm -12 "$CURRENT_LIST" "$BASELINE_LIST")

rm -f "$CURRENT_LIST" "$BASELINE_LIST"

if [[ "$VIOLATIONS" -eq 0 ]]; then
    log_message "PASS" "=== Integrity check clean: no unauthorized changes detected ==="
    exit 0
else
    log_message "FAIL" "=== Integrity check found $VIOLATIONS violation(s) - see log for details ==="
    exit 2
fi

Every Line, Explained

LineExplanation
printf '%s\n' "${!BASELINE_CHECKSUM[@]}" > "$BASELINE_LIST"Extracts every key (filename) from the associative array, one per line, using the ! keys-expansion syntax introduced in this project's concepts.
sort -o "$CURRENT_LIST" "$CURRENT_LIST"-o sorts a file in place, writing the result back to the same filename — required before comm can be used correctly.
done < <(comm -23 "$CURRENT_LIST" "$BASELINE_LIST")Process substitution (<(...)) feeds a command's output into the loop as if it were a file — this keeps the loop in the current shell (unlike piping), so VIOLATIONS correctly persists afterward.
comm -12 "$CURRENT_LIST" "$BASELINE_LIST"Unlike -23 (added) and -13 (removed), -12 prints lines common to both files — exactly the set of files needing a detailed checksum/permission comparison.
IFS='|' read -r _ current_checksum current_perms current_owner <<< "$CURRENT_STATE"The underscore _ is a conventional throwaway variable name for a field we don't need (the file path itself, already known from the loop variable).

🔐 The Baseline Update Command (Separate & Authorized-Only)

scripts/fim_update_baseline.sh
#!/bin/bash
# =====================================================================
# fim_update_baseline.sh
# NovaTrust Bank - AUTHORIZED-ONLY baseline update
# This script is NEVER called from cron or from fim_check.sh.
# It must be run manually by an authorized engineer with a change-ticket reference.
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/fim.conf"

MONITORED_FILE="$SCRIPT_DIR/../config/monitored_paths.txt"
BASELINE_FILE="$SCRIPT_DIR/$BASELINE_FILE"
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/fim_update_$(date '+%Y%m%d').log"
mkdir -p "$(dirname "$LOG_FILE")" "$(dirname "$BASELINE_FILE")"

CHANGE_TICKET=""
while getopts "t:h" opt; do
    case $opt in
        t) CHANGE_TICKET="$OPTARG" ;;
        h) echo "Usage: $0 -t CHANGE-TICKET-ID"; exit 0 ;;
        *) echo "Usage: $0 -t CHANGE-TICKET-ID"; exit 1 ;;
    esac
done

# ---------- Refuse to run without an explicit change-ticket reference ----------
[[ -n "$CHANGE_TICKET" ]] || { echo "ERROR: -t CHANGE-TICKET-ID is required. This action must be traceable to an approval." >&2; exit 1; }

echo "This will REPLACE the current integrity baseline for all monitored files."
echo "Change ticket: $CHANGE_TICKET"
read -r -p "Type YES to confirm: " CONFIRMATION
[[ "$CONFIRMATION" == "YES" ]] || { echo "Aborted - confirmation not received."; exit 1; }

TEMP_BASELINE=$(mktemp)
while IFS= read -r file; do
    [[ -z "$file" || "$file" == \#* ]] && continue
    is_excluded "$file" && continue
    if [[ -f "$file" ]]; then
        capture_file_state "$file" >> "$TEMP_BASELINE"
    else
        log_message "WARN" "Monitored file does not exist, skipping: $file"
    fi
done < "$MONITORED_FILE"

mv "$TEMP_BASELINE" "$BASELINE_FILE"

log_message "INFO" "Baseline updated. Change ticket: $CHANGE_TICKET. Files captured: $(wc -l < "$BASELINE_FILE")"
audit_log "BASELINE_UPDATED" "change_ticket=$CHANGE_TICKET files=$(wc -l < "$BASELINE_FILE")"

echo "Baseline updated successfully and logged under change ticket $CHANGE_TICKET."

Line-by-Line Highlights

  • [[ -n "$CHANGE_TICKET" ]] || { ...; exit 1; } — this single line is the entire security control of this script: no ticket reference, no baseline update, no exceptions.
  • read -r -p "Type YES to confirm: " CONFIRMATION — an interactive confirmation prompt, deliberately different from every other project's non-interactive design, because this action is meant to be a conscious, attended decision, never something that runs unattended.
  • TEMP_BASELINE=$(mktemp) then mv "$TEMP_BASELINE" "$BASELINE_FILE" — builds the entire new baseline in a temporary file first, only replacing the real baseline in one atomic mv at the very end, so a script failure partway through never leaves a half-written, corrupted baseline in place.
  • audit_log "BASELINE_UPDATED" "change_ticket=$CHANGE_TICKET ..." — every baseline acceptance is now permanently traceable to exactly who ran it, when, and under what approved change.

📄 README.md

README.md
# NovaTrust Bank - File Integrity Monitoring

## Daily Check (automated, read-only, safe to schedule)
    ./scripts/fim_check.sh

## Baseline Update (MANUAL, interactive, requires a change ticket - NEVER schedule this)
    ./scripts/fim_update_baseline.sh -t CHG0012345

## Exit Codes (fim_check.sh)
    0 = No unauthorized changes detected
    2 = ADDED, REMOVED, or MODIFIED file(s) detected

## Report Categories
    ADDED    = file exists now but is not in the baseline (unauthorized new file)
    REMOVED  = file is in the baseline but no longer exists (missing critical file)
    MODIFIED = file exists in both, but checksum and/or permissions/owner differ

## Security Note
fim_update_baseline.sh must remain a manual-only action, run by an authorized
engineer with a valid change ticket. It must never be added to any cron schedule.

🔄 What Happens Internally

  1. Two entirely separate scripts enforce one security boundary: fim_check.sh can only ever read the baseline; only fim_update_baseline.sh can write it, and that script is architecturally incapable of running unattended.
  2. comm requires pre-sorted input, which is why both filename lists are explicitly sorted with sort -o before any of the three comm calls — skipping this step would silently produce wrong ADDED/REMOVED results.
  3. Process substitution (<(...)) rather than a pipe keeps each comparison loop in the main shell, which is why VIOLATIONS correctly accumulates across all three loops instead of resetting in a subshell each time.
  4. The baseline file is replaced atomically via mv, never edited in place — this guarantees fim_check.sh (which might run concurrently, though flock also guards against this) never reads a partially-written baseline mid-update.

🛡️ Production Best Practices

Never Let the Checker Also Write the Baseline

Read and write responsibilities for security-critical state should live in architecturally separate scripts, not just separate code paths in one script.

Check Content AND Metadata

A checksum alone misses permission and ownership changes — both matter for true integrity, and both should be captured and compared independently.

Require Explicit Authorization for Trust Changes

Any action that changes what your system considers "known good" deserves its own deliberate gate — a change-ticket requirement here mirrors the credentials-permission gate in Project 7.

Write New State Atomically

Build a new baseline in a temp file and mv it into place at the very end — never edit trusted state files incrementally in place.

Distinguish Violation Types Clearly

ADDED, REMOVED, and MODIFIED each imply a different investigation and response — collapsing them into one generic "changed" status loses actionable information.

Keep Interactive Actions Interactive

A destructive or trust-altering action benefiting from a human's deliberate attention (like the YES confirmation here) should never be quietly made scriptable/automatable "for convenience."

🎤 Interview Preparation

Scenario: A file shows as MODIFIED, but the engineer swears they made an approved change last week and the baseline should already reflect it. What's the most likely explanation?
The approved change was deployed, but nobody actually ran fim_update_baseline.sh -t <ticket> afterward — the baseline update is a deliberate, separate manual step, not something that happens automatically just because a change was approved and deployed.
Production Support: fim_check.sh reports a REMOVED file, but the file clearly still exists when you check manually. What could cause this false positive?
Check whether the file's path recently changed (moved, renamed, or the monitored_paths.txt entry has a typo/stale path) — fim_check.sh only knows about the exact paths listed, so a legitimate rename would correctly show as both REMOVED (old path) and ADDED (new path) unless the monitored paths list and baseline are both updated together.
Shell Scripting: Why is the exclude-pattern variable left unquoted in [[ "$file" == $pattern ]] when the course has emphasized quoting everywhere else?
Quoting $pattern would make Bash treat wildcard characters like * as literal characters to match, rather than as glob wildcards — this is one of a small number of deliberate, well-understood exceptions to the general quoting rule, specifically because glob matching is the intended behavior here.
Troubleshooting: comm produces completely wrong ADDED/REMOVED output even though both files clearly contain the right filenames. What's the first thing to check?
Whether both input files were actually sorted immediately before the comm call — comm assumes sorted input and does not itself verify or warn about unsorted input, so a missed or failed sort step produces silently incorrect (not obviously erroring) results.
Manager Round: Why require an interactive YES confirmation on baseline updates instead of just trusting the -t change-ticket flag alone?
A flag alone can be scripted, automated, or fat-fingered by copy-pasting a command with the wrong ticket number; an interactive confirmation forces one final deliberate human moment before a security-trust-altering action, consistent with the same philosophy behind requiring interactive confirmation for other genuinely irreversible or high-trust actions.
Architecture: Why does the baseline separately track permissions and ownership rather than folding them into the checksum somehow?
A checksum is deliberately a pure function of file content only — mixing permission/ownership metadata into the same hash would make it impossible to distinguish "content changed" from "permissions changed" from the checksum comparison alone, which is exactly the distinction Acceptance Criterion 2 requires.
Best Practice: Why does fim_update_baseline.sh build the new baseline in a temp file and only move it into place at the very end, rather than writing directly to baseline.manifest?
If the script fails partway through scanning monitored files (a permission error, a missing file, a crash), writing directly to the real baseline file could leave it truncated or partially updated; building in a temp file and only replacing atomically at the end guarantees the real baseline is either fully old or fully new, never something in between.
Real Incident Discussion: What's the one design decision in this project that most directly would have caught the unauthorized NEFT config edit within a day instead of three weeks?
The daily scheduled fim_check.sh run itself, comparing against a baseline that only ever changes through the separate, ticket-gated update process — the direct edit would have shown as MODIFIED the very next morning, since no corresponding authorized baseline update had occurred to match it.
