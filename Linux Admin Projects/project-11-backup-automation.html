Backup Automation

The disaster recovery drill that discovered eight months of "successful" backups were actually silently corrupted, truncated tarballs nobody had ever tried to restore.

🎯 Level: Intermediate–Advanced 🧠 New Concepts: 10 🏗️ Environment: Linux / WSL + tar/rsync ⏱️ Duration: 3 hrs

📖 The Story — "Successful" Backups That Couldn't Be Restored

NovaTrust's annual Disaster Recovery drill went badly: the team tried restoring the Core Banking configuration backup from the previous night, and the tarball was corrupted — truncated partway through, likely because the disk ran out of space mid-write. The backup job's own exit code had been 0 ("success") every single night for eight months. Nobody had ever actually tried to restore one.

Priya doesn't mince words in the retro: "A backup that was never restored isn't a backup — it's a hope. From now on, every backup gets a checksum, we verify that checksum immediately after writing the archive, we verify it again after copying it offsite, and once a month, an automated job actually restores a sample and proves it's readable. 'The tar command exited zero' is no longer good enough."

Today we learn that in backup systems specifically, success is not "the command didn't error" — success is "we proved we can get the data back."
🔁 Reinforced from Projects 1–10
Disk-space pre-checks (Project 2), flock, retention-based pruning (Project 5), and dry-run safety patterns all return, now protecting Core Banking's actual data instead of just infrastructure metrics.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Guarantee that Core Banking configuration and data backups are not just created, but verified as intact and genuinely restorable.

Customer Requirement

Audit and Disaster Recovery planning require proof — not assumption — that any given night's backup can actually be restored if needed.

Banking Scenario

Core Banking configuration, transaction logs, and application state are backed up nightly to local storage, then copied offsite for disaster recovery purposes.

Existing Manual Process / Prior Automation Gap

A basic tar command ran nightly via cron, with success measured purely by its exit code — no checksum verification, no restore testing, no disk-space pre-check before starting.

Problems With Exit-Code-Only Verification

tar can exit 0 even against a disk that fills up mid-write in certain conditions, or produce a technically-complete-but-corrupted archive that nothing ever attempted to open until the drill.

Business Impact & Risk

Eight months of false confidence in disaster recovery readiness is precisely the kind of gap that turns a bad day into a catastrophic one when a real disaster actually strikes.

Why Automation Is Required

Checksum verification and periodic restore testing are exactly the kind of easy-to-skip manual steps that only survive long-term if a script performs them automatically, every single time, without depending on anyone remembering to check.

Solution Design

Pre-check available disk space, create a timestamped compressed archive, generate and verify a checksum immediately, copy offsite with rsync and verify the checksum again on the remote side, and run a separate monthly job that actually extracts and validates a sample from a real backup.

Project Scope

In scope: local archive creation, checksum generation/verification, offsite copy with integrity verification, retention pruning, and restore-test validation. Out of scope: full bare-metal disaster recovery orchestration (a much larger, separate initiative).

Expected Outcome

Every backup is checksum-verified at creation and after offsite transfer, with a monthly automated restore test proving the backup chain genuinely works — never again just "the command exited 0."

🧠 New Bash Concepts for This Project

1. Creating Compressed Archives with tar

What: tar -czf backup.tar.gz -C /source/dir . — -c create, -z gzip-compress, -f specify the archive filename, -C change to a directory first so paths inside the archive are relative, not absolute.
Why: -C specifically avoids baking an absolute path like /home/devops/corebanking/config into the archive, which would make restoring to a different location or server awkward.

2. Generating a Checksum (sha256sum)

What: sha256sum backup.tar.gz > backup.tar.gz.sha256 produces a cryptographic fingerprint of the exact file contents.
Why: Any corruption — even a single flipped bit from a disk error or a truncated write — produces a completely different checksum, making this the definitive way to detect it.

3. Verifying a Checksum (sha256sum -c)

What: sha256sum -c backup.tar.gz.sha256 re-computes the file's checksum right now and compares it against the stored value, printing OK or FAILED.
Why: This is the actual proof step — generating a checksum alone means nothing if nobody ever re-verifies it.

4. Disk-Space Pre-Checks Before Writing (Reinforced)

What: Using df (from Project 1) to confirm the destination has enough free space before starting a potentially large write, comparing available space against the estimated source size from du.
Why: This is the single change that would have most directly prevented the original incident — a backup that fails cleanly at the start (insufficient space) is infinitely better than one that fails silently midway through.

5. Efficient Offsite Copying with rsync

What: rsync -avz --timeout=60 backup.tar.gz user@offsite-host:/backups/ copies a file, resuming/retrying more gracefully than a plain file copy, and only transferring changed data on subsequent syncs of a directory.
-a (archive): preserves permissions, timestamps, and structure. -v: verbose. -z: compresses data during transfer.

6. Verifying Integrity After a Remote Transfer

What: Compute the checksum locally, transfer the checksum file itself alongside the archive, then SSH to the remote host and run sha256sum -c there too.
Why: A successful rsync exit code proves the transfer command completed — it does not, by itself, prove the bytes that arrived are byte-for-byte identical to what was sent; an independent remote verification closes that gap.

7. Restore Testing: Extracting to a Temporary Location

What: tar -xzf backup.tar.gz -C "$(mktemp -d)" extracts an archive into a fresh, disposable temporary directory (reinforcing Project 8's mktemp) purely to validate it, without touching any real environment.
Why: This is the step the original incident skipped entirely — checksum-valid is necessary but still not sufficient proof that the contents are what's expected; actually extracting and inspecting specific files closes that final gap.

8. Validating Expected Contents Post-Restore

What: After extraction, check that specific known files exist and are non-empty ([[ -s "$file" ]]) — -s tests that a file exists and has a size greater than zero.
Why: An archive could be checksum-valid yet still be missing a critical file if the original tar command's source path was wrong — this final content check catches that class of mistake.

9. Estimating Source Size Before Backing Up (du -sb, Reinforced)

What: Reusing Project 5's du -sb technique to estimate how large the resulting archive will roughly be, to compare against available destination space.
Why: A rough size estimate, checked against free space with a safety margin, is what actually prevents the "ran out of space mid-write" scenario from the incident.

10. Chained Verification with && Across Multiple Stages

What: create_archive && verify_checksum && copy_offsite && verify_remote_checksum — each stage only proceeds if the previous one genuinely succeeded.
Why: A backup pipeline with several distinct stages must never silently continue past a failed earlier stage — chaining with && (or explicit if checks, for clearer logging) enforces that a corrupted local archive, for instance, is never copied offsite and reported as a success.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Backup helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- has_sufficient_space ----------
# Purpose: Compare estimated backup size (with a safety margin) against actual free space at the destination
has_sufficient_space() {
    local source_dir="$1"
    local dest_dir="$2"

    local estimated_bytes free_bytes required_bytes
    estimated_bytes=$(du -sb "$source_dir" 2>/dev/null | awk '{print $1}')
    free_bytes=$(df -B1 --output=avail "$dest_dir" 2>/dev/null | tail -n 1 | tr -d ' ')

    # Required = estimated size + safety margin percentage on top
    required_bytes=$(( estimated_bytes + (estimated_bytes * MIN_FREE_SPACE_SAFETY_MARGIN_PCT / 100) ))

    [[ "$free_bytes" -ge "$required_bytes" ]]
}

# ---------- create_backup_archive ----------
# Purpose: Create a timestamped tar.gz archive with relative paths (via -C)
create_backup_archive() {
    local source_dir="$1"
    local archive_path="$2"
    tar -czf "$archive_path" -C "$(dirname "$source_dir")" "$(basename "$source_dir")"
}

# ---------- generate_checksum ----------
generate_checksum() {
    local file_path="$1"
    sha256sum "$file_path" > "${file_path}.sha256"
}

# ---------- verify_checksum ----------
# Purpose: Return 0 if the file's current checksum matches its stored .sha256 file
verify_checksum() {
    local file_path="$1"
    # Run sha256sum -c FROM the archive's own directory so the relative filename inside the .sha256 file resolves correctly
    (cd "$(dirname "$file_path")" && sha256sum -c "$(basename "$file_path").sha256" >/dev/null 2>&1)
}

# ---------- copy_offsite ----------
copy_offsite() {
    local file_path="$1"
    local checksum_path="${file_path}.sha256"
    rsync -avz --timeout=60 "$file_path" "$checksum_path" "${OFFSITE_USER}@${OFFSITE_HOST}:${OFFSITE_PATH}"
}

# ---------- verify_offsite_checksum ----------
# Purpose: SSH to the offsite host and verify the checksum matches THERE too, proving transfer integrity
verify_offsite_checksum() {
    local filename="$1"    # Just the filename, not the full local path
    timeout "$SSH_CONNECT_TIMEOUT" ssh -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "${OFFSITE_USER}@${OFFSITE_HOST}" \
        "cd '${OFFSITE_PATH}' && sha256sum -c '${filename}.sha256'" >/dev/null 2>&1
}

Line-by-Line Highlights

  • tar -czf "$archive_path" -C "$(dirname "$source_dir")" "$(basename "$source_dir")" — -C changes into the parent of the source directory first, so the archive contains a clean relative path (e.g. corebanking-config/...) rather than the full absolute path.
  • (cd "$(dirname "$file_path")" && sha256sum -c ...) — wrapped in a subshell ( ) so the cd only affects this one command, never leaking a changed working directory back into the rest of the script.
  • df -B1 --output=avail — -B1 forces byte-sized blocks (not the default human-readable units), and --output=avail asks df for exactly the one column we need.
  • rsync -avz --timeout=60 "$file_path" "$checksum_path" ... — transfers both the archive and its checksum file together in one call, ensuring they always travel as a matched pair.
  • ssh ... "cd '${OFFSITE_PATH}' && sha256sum -c '${filename}.sha256'" — runs the verification command entirely on the remote host, proving the bytes that actually landed there are intact, not just that our local copy was fine before sending.

🩺 Main Script

scripts/backup.sh
#!/bin/bash
# =====================================================================
# backup.sh
# NovaTrust Bank - Checksum-Verified Backup with Offsite Copy
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/backup.conf"

ARCHIVE_DIR="$SCRIPT_DIR/$ARCHIVE_DIR"
TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/backup_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")" "$ARCHIVE_DIR"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another backup instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Backup run finished."' EXIT

log_message "INFO" "=== Starting backup of $SOURCE_DIR ==="

ARCHIVE_NAME="${BACKUP_NAME_PREFIX}_${TODAY}.tar.gz"
ARCHIVE_PATH="$ARCHIVE_DIR/$ARCHIVE_NAME"

# ---------- Stage 1: Disk-space pre-check (the single most important lesson from the incident) ----------
if ! has_sufficient_space "$SOURCE_DIR" "$ARCHIVE_DIR"; then
    log_message "FAIL" "Insufficient disk space for backup - aborting BEFORE writing anything"
    exit 2
fi
log_message "PASS" "Disk space check passed"

# ---------- Stage 2: Create the archive ----------
if ! create_backup_archive "$SOURCE_DIR" "$ARCHIVE_PATH"; then
    log_message "FAIL" "tar archive creation failed"
    exit 2
fi
log_message "PASS" "Archive created: $ARCHIVE_NAME"

# ---------- Stage 3: Generate and verify checksum LOCALLY ----------
generate_checksum "$ARCHIVE_PATH"
if ! verify_checksum "$ARCHIVE_PATH"; then
    log_message "FAIL" "Local checksum verification FAILED - archive may be corrupted"
    exit 2                                              # Do NOT proceed to offsite copy with a bad archive
fi
log_message "PASS" "Local checksum verified successfully"

# ---------- Stage 4: Copy offsite ----------
if ! copy_offsite "$ARCHIVE_PATH"; then
    log_message "FAIL" "Offsite copy (rsync) failed"
    exit 2
fi
log_message "PASS" "Offsite copy completed"

# ---------- Stage 5: Verify checksum on the REMOTE side ----------
if ! verify_offsite_checksum "$ARCHIVE_NAME"; then
    log_message "FAIL" "Offsite checksum verification FAILED - transfer corruption suspected"
    exit 2
fi
log_message "PASS" "Offsite checksum verified successfully"

# ---------- Stage 6: Prune old local archives (reinforced Project 5 pattern) ----------
find "$ARCHIVE_DIR" -name "${BACKUP_NAME_PREFIX}_*.tar.gz*" -mtime +"$RETENTION_DAYS" -print0 |
    while IFS= read -r -d '' old_file; do
        rm -f "$old_file" && log_message "INFO" "Pruned old backup: $old_file"
    done

log_message "INFO" "=== Backup completed successfully: local AND offsite checksum-verified ==="
exit 0

Every Line, Explained

LineExplanation
if ! has_sufficient_space ...; then exit 2; fiPlaced as the very first stage, before tar ever runs — this single check is what directly addresses the root cause of the original incident.
generate_checksum "$ARCHIVE_PATH" then verify_checksum "$ARCHIVE_PATH"Deliberately two separate steps, not one — generating proves nothing by itself; only the immediate re-verification actually catches a corrupted write.
if ! verify_checksum ...; then exit 2; fi (before offsite copy)This is the chained-verification principle from this project's concepts section in action — a corrupted local archive must never be allowed to proceed to the offsite copy stage and get reported as a successful backup.
if ! verify_offsite_checksum ...; then exit 2; fiA successful rsync exit code alone (Stage 4) was not treated as sufficient proof — this independent remote re-check is what actually confirms transfer integrity.
Pruning loopDirectly reuses Project 5's null-byte-safe find -print0 / read -d '' pattern, applied here to real backup archives instead of log files.

📄 README.md

README.md
# NovaTrust Bank - Checksum-Verified Backup Automation

## Usage
    ./scripts/backup.sh              # Nightly full backup + offsite verification
    ./scripts/restore_test.sh         # Monthly restore validation (run separately)

## What "Success" Actually Means Here
A backup is only considered successful if ALL of the following hold:
1. Sufficient disk space was confirmed BEFORE writing began.
2. The local archive's checksum was generated AND independently re-verified.
3. The offsite copy completed AND its checksum was independently re-verified on the remote host.
Exit code 0 means all of the above - not just "tar didn't error."

## Exit Codes
    0 = Backup created and fully verified, locally and offsite
    2 = Failure at any stage (space, archive, local checksum, transfer, or remote checksum)

## Restore Testing
Run scripts/restore_test.sh monthly (or on-demand before a real DR drill) to
extract a real backup into a disposable temp directory and confirm expected
files are present and non-empty - this is what the original 8-month gap missed.

🔄 What Happens Internally

  1. Every stage gates the next one explicitly via if ! stage; then exit 2; fi — there's no code path where a failed earlier stage can silently be followed by a later one still running.
  2. The checksum file travels with the archive as an inseparable pair through both the local verification and the rsync transfer — this is deliberate, since verifying a checksum that didn't travel alongside its file proves nothing.
  3. Remote verification runs as a genuinely separate process on the remote host, via SSH — this is the only way to prove what actually arrived there, as opposed to trusting that a local check plus a successful transfer command implies remote correctness.
  4. Pruning only runs after every verification stage has already passed, at the very end — a script that failed partway through should never proceed to delete old (still-good) backups.

🛡️ Production Best Practices

Exit Code Alone Is Never Proof

Especially for backups — a command exiting 0 proves it ran to completion, not that its output is correct or complete.

Verify Immediately, Then Verify Again After Transfer

Local verification catches write-time corruption; remote verification catches transfer-time corruption — they check for different failure modes and both are required.

Check Space Before Writing, Not After Failing

A pre-check that aborts cleanly is vastly preferable to a mid-write failure that leaves a corrupted partial archive behind.

Test Restores, Not Just Backups

The only real proof a backup system works is a successful restore — schedule this as its own recurring, automated job, not an annual manual drill.

Chain Stages With Explicit Gates

Never let a later pipeline stage run after an earlier one has already failed — each stage's success must be a hard prerequisite for the next.

Keep the Checksum File With Its Archive

Generate, store, and transfer the checksum as an inseparable companion to the file it describes — a checksum that didn't travel with its file can't prove anything about what arrived.

🎤 Interview Preparation

Scenario: A backup's local checksum verifies successfully, but the offsite checksum verification fails. What does this specifically tell you?
The archive was written correctly on the source side — the problem occurred specifically during or after transfer (network corruption, an interrupted rsync, or a problem with the remote storage itself) rather than during the original archive creation.
Production Support: The disk-space pre-check is failing every night, but manually checking df -h shows plenty of free space. What's the likely bug?
Check the safety-margin percentage calculation and the units being compared — a common bug is comparing bytes from df -B1 against a value from du that wasn't actually captured in bytes (e.g., accidentally using human-readable du -sh output instead of du -sb).
Shell Scripting: Why is the cd inside verify_checksum wrapped in a subshell ( ) instead of a plain cd?
A subshell's cd only affects commands inside that parenthesized block; without it, the working directory change would persist for the rest of the script after the function returns, potentially breaking every subsequent relative-path operation.
Troubleshooting: The monthly restore test starts failing right after a backup is otherwise reported successful. What should you check first?
Confirm the restore test is actually selecting the most recent archive (not an older one due to a sorting bug), and separately verify the expected-files list inside the restore test itself hasn't gone stale relative to what's actually supposed to be in the backup now.
Manager Round: Why run restore testing monthly instead of after every single nightly backup?
A full extraction-and-validation restore test is more resource-intensive than the lightweight checksum verification already happening nightly; monthly strikes a practical balance between genuinely proving restorability on a regular cadence and not adding unnecessary load to every single night's backup window.
Architecture: Why use SSH plus a remote sha256sum -c call instead of simply trusting rsync's own built-in checksum comparison feature?
While rsync does have checksum-related options for deciding what to transfer, an independent, explicit post-transfer verification step is a deliberate, auditable, and simpler-to-reason-about proof point that doesn't depend on correctly understanding or configuring rsync's more nuanced internal comparison behavior.
Best Practice: Why does pruning old backups happen as the very last stage in the script, only after every verification has passed?
If an earlier stage fails, the script exits immediately and pruning code is never reached — this is a deliberate ordering choice ensuring a failed backup run never also deletes older, still-valid backups on the same bad day.
Real Incident Discussion: What is the single most direct design decision in this project that would have caught the original 8-month corruption gap?
Immediate local checksum verification right after archive creation — a truncated, disk-full-corrupted tarball would have failed sha256sum -c on the very first night it happened, rather than going completely undetected until a drill eight months later.
