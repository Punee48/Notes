Production-Grade Error Handling & Hardening

A near-miss in one of our own scripts revealed something uncomfortable: 28 projects, and utils.sh had been copy-pasted and subtly drifted apart every single time.

🎯 Level: Expert 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL + ShellCheck ⏱️ Duration: 3 hrs

📖 The Story — The Bug in Our Own Foundation

During a routine review, an engineer noticed something unsettling in Project 2's disk monitor: a pipeline where, under one specific edge case, a failed command in the middle of a pipe was silently swallowed — the script kept running with corrupted data as if nothing had gone wrong, and only pipefail's absence in that one specific code path let it happen. It was a near-miss, not a real incident — but it raised an uncomfortable question: how many of our other 27 scripts have a similar, still-undiscovered gap? And separately, everyone realized that utils.sh — copy-pasted fresh at the start of nearly every single project — had quietly drifted: slightly different versions of log_message, inconsistent flock boilerplate, small bugs fixed in some copies but never backported to others.

Priya calls for a hardening sprint: "Before we call this monitoring suite finished, I want every script run through ShellCheck, a proper ERR trap with line numbers on every script, a real understanding of exactly what set -e does and doesn't protect us from, and — this is the big one — one single, shared common.sh library replacing 28 separate, slowly-diverging copies of the same functions."

This project doesn't monitor anything new. It goes back through everything this course has built and makes it genuinely production-grade.
🔁 Reinforced from Projects 1–28
Every project's set -uo pipefail, flock locking, and log_message function get consolidated and hardened here — this is the course's most direct look back at everything built so far.

🧠 New Bash Concepts for This Project

1. set -e (errexit) and Why This Course Deliberately Avoided It Until Now

What: set -e causes a script to exit immediately when any command fails (returns non-zero) — sounds like exactly what we'd always want, but has well-known, surprising exceptions: it does not trigger inside a condition being tested (if failing_command; then), inside &&/|| chains, or for any command except the last in a pipeline (without pipefail).
Why we avoided it: This course consistently used explicit if ! command; then handle_error; fi checks instead — more verbose, but completely predictable, with none of set -e's notoriously inconsistent edge-case behavior across different Bash versions and contexts.

2. The ERR Trap with Line-Number Diagnostics

What: trap 'error_handler $? $LINENO' ERR — fires automatically whenever a command fails (works more consistently than relying on set -e alone), capturing both the failing exit code ($?) and the exact source-line number ($LINENO) where it happened.
Why: This gives every script in the suite automatic, precise, "which exact line failed and with what code" diagnostics — dramatically faster troubleshooting than scanning an entire script trying to infer where an unexpected failure actually occurred.

3. ShellCheck: Static Analysis for Bash

What: shellcheck script.sh analyzes a script without running it, flagging a wide range of common bugs — unquoted variables, unreachable code, incorrect test operators, and dozens of other well-documented pitfalls, each with a specific, explained warning code (like SC2086).
Why: Running every one of this course's 28 prior scripts through ShellCheck surfaces exactly the class of subtle bug (like the disk-monitor near-miss) that's easy to miss in manual review but mechanically detectable.

4. pipefail, Explained Precisely (Deeper Dive)

What: Without pipefail, a pipeline cmd1 | cmd2's exit code reflects only cmd2 — if cmd1 fails but cmd2 still succeeds (common with commands like grep or awk that happily process empty input), the overall pipeline reports success despite the real underlying failure. set -o pipefail changes this so the pipeline's exit code is the last command that failed, if any did.
Why revisit this now: The disk-monitor near-miss occurred specifically in a code path where this exact behavior wasn't fully accounted for — a concrete, real example makes the abstract explanation land far more clearly than it would in the abstract.

5. A Consolidated, Single-Source-of-Truth common.sh

What: One shared library file, containing the best, most correct version of every utility function that's been duplicated (and subtly drifted) across all 28 prior projects' individual utils.sh files.
Why: A bug fixed once in common.sh is fixed everywhere that sources it — eliminating the entire class of "fixed in project 14 but never backported to project 3" drift this hardening sprint exists to address.

6. A Generic, Reusable Retry-With-Backoff Function

What: Generalizing Project 8's endpoint-specific retry loop into retry_with_backoff "$max_attempts" "$delay_seconds" command args... — a function any script can call to retry any command, not just an HTTP check.
Why: The retry-with-backoff pattern is broadly useful far beyond Project 8's original HTTP context — generalizing it into the shared library means any future project gets this capability for free, without reimplementing it.

7. A Defensive Coding Checklist (Consolidated Retrospective)

What: A written checklist distilling this entire course's recurring defensive patterns: validate input before use, quote all variable expansions, fail closed on ambiguity, never trust external data, always time-bound network calls, and never silently swallow a failure.
Why: Writing these principles down explicitly, in one place, turns 28 projects' worth of individually-learned lessons into one reusable checklist for every future script NovaTrust ever writes.

8. Backward-Compatible Migration (Practical Refactoring Concern)

What: Migrating 28 existing, working, production-scheduled scripts to source a new shared library without breaking any of them — meaning common.sh must provide every function name each project already expects, with matching behavior.
Why: A hardening sprint that breaks working production monitoring while trying to improve it would be a serious, self-defeating mistake — this migration must be done carefully, verified project by project, not as one risky global find-and-replace.

📚 The Consolidated common.sh

common.sh
#!/bin/bash
# =====================================================================
# common.sh
# NovaTrust Bank - SINGLE SOURCE OF TRUTH for shared Bash utility functions
# Used by all monitoring projects. Fix bugs HERE ONLY - never in a project-
# local copy again.
# =====================================================================

# ---------- log_message ----------
# Purpose: The one, consistent logging function every project uses
log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "${LOG_FILE:-/dev/stdout}"
}

# ---------- error_handler ----------
# Purpose: Fired automatically by an ERR trap - reports exactly where and how a script failed
error_handler() {
    local exit_code="$1"
    local line_number="$2"
    log_message "CRITICAL" "Unexpected failure at line $line_number (exit code $exit_code). Script: ${BASH_SOURCE[1]:-unknown}"
}

# ---------- install_standard_error_trap ----------
# Purpose: One call every project's main script makes near the top, replacing manually
# writing the same trap line 28 separate times
install_standard_error_trap() {
    trap 'error_handler $? $LINENO' ERR
}

# ---------- acquire_lock ----------
# Purpose: The standard flock boilerplate, consolidated from its 28 slightly-different copies
acquire_lock() {
    local lock_file="$1"
    exec 200>"$lock_file"
    flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
}

# ---------- retry_with_backoff ----------
# Purpose: Generic retry logic for ANY command, generalized from Project 8's HTTP-specific version
# Usage: retry_with_backoff 3 5 curl -sf https://example.com/health
retry_with_backoff() {
    local max_attempts="$1"
    local delay_seconds="$2"
    shift 2                                          # Remaining args are the actual command to run

    local attempt=1
    while [[ "$attempt" -le "$max_attempts" ]]; do
        if "$@"; then
            return 0                                  # Success - stop retrying immediately
        fi
        log_message "WARN" "Attempt $attempt/$max_attempts failed for: $*"
        ((attempt++))
        [[ "$attempt" -le "$max_attempts" ]] && sleep "$delay_seconds"
    done
    log_message "FAIL" "All $max_attempts attempts failed for: $*"
    return 1
}

# ---------- require_root ----------
require_root() {
    [[ $EUID -eq 0 ]] || { echo "ERROR: This script must be run as root." >&2; exit 1; }
}
Example: how every project's scripts now start

source "$SCRIPT_DIR/../config/some_project.conf"
# ... this project's own genuinely unique logic continues below ...

Line-by-Line Highlights

  • log_message now defaults LOG_FILE to /dev/stdout via ${LOG_FILE:-/dev/stdout} if a calling script hasn't set it yet — a small defensive improvement over the 28 originals, some of which would have errored if called before LOG_FILE was defined.
  • error_handler uses ${BASH_SOURCE[1]:-unknown} — index [1] because [0] would refer to common.sh itself; index [1] is the actual calling project script, giving a genuinely useful "which script failed" detail.
  • retry_with_backoff's shift 2 removes the first two arguments (attempt count, delay), leaving "$@" holding exactly the command (and its own arguments) to actually retry — allowing this one function to wrap literally any command line.
  • Every function here is the deliberately-chosen best version found across the 28 original copies — this consolidation was itself a genuine code review exercise, not just a mechanical merge.

🔄 What Happens Internally

  1. The ERR trap fires automatically on any command's non-zero exit, without requiring set -e at all — this is deliberately more predictable than relying on errexit's well-known inconsistent edge cases, while still providing the diagnostic value people usually reach for set -e to get.
  2. $LINENO is a special Bash variable updated automatically on every line executed, meaning it always reflects exactly where the trap fired, with zero extra bookkeeping required in any calling script.
  3. Every project's migration is a mechanical, verifiable, one-line change (replacing a full local utils.sh with one source common.sh line) — low-risk precisely because common.sh was deliberately built to be behaviorally compatible with every project's existing expectations.
  4. ShellCheck runs entirely offline, against the script's text, never executing any of the code it analyzes — completely safe to run against even a script containing destructive commands, since nothing it flags is ever actually run.

🛡️ Production Best Practices

Prefer Explicit Checks Over set -e Alone

set -e's well-documented inconsistent behavior across contexts makes explicit if ! command checks more predictable for production scripts, even though it's more verbose.

Always Add an ERR Trap

Precise, automatic line-number diagnostics on any unexpected failure dramatically reduce troubleshooting time, at near-zero implementation cost.

Never Duplicate Shared Logic

A function copy-pasted more than once will drift — consolidate into one sourced library the moment a second project needs the same function.

Run Static Analysis Regularly, Not Just Once

ShellCheck should be part of an ongoing review habit for any new or modified script, not a one-time sprint exercise.

Understand pipefail's Exact Semantics

Know precisely what changes and what doesn't — a pipeline's exit code reflecting the rightmost failing command, not automatically catching every possible pipeline issue.

Migrate Shared Code Carefully, Verify Every Consumer

Consolidating duplicated logic must never break any of its existing consumers — verify each migrated project individually, not via one broad, unverified sweep.

🎤 Interview Preparation

Scenario: A script with set -e continues running past a command that clearly failed, inside an if statement. Is this a bug in Bash?
No — this is set -e's well-documented, standard behavior: a command's failure inside a condition being tested by if is specifically excluded from triggering errexit, since the whole point of testing a command's success/failure in a condition would be defeated if that test itself caused an immediate exit; this is exactly the kind of surprising exception this project explains and works around with an ERR trap instead.
Production Support: The ERR trap correctly reports a failing line number, but the reported exit code doesn't match what you'd expect from that specific command. What might explain this?
If the failing line is itself part of a pipeline, without pipefail the reported $? reflects only the last command in that pipe, not necessarily the command that actually failed earlier in the chain — confirming pipefail is active is the first thing to check when the reported exit code seems inconsistent with the apparent point of failure.
Shell Scripting: Why does error_handler use ${BASH_SOURCE[1]} instead of ${BASH_SOURCE[0]} to report which script failed?
BASH_SOURCE[0] inside a function defined in common.sh refers to common.sh itself (where the function is defined); BASH_SOURCE[1] refers to the caller one level up the call stack - the actual project script that sourced common.sh and triggered the trap - which is the genuinely useful information for diagnosing where the real failure occurred.
Troubleshooting: After migrating a project to source common.sh, its cron job silently stops producing any log output at all. What's the most likely migration mistake?
Almost certainly the project's own script still needs to define its own LOG_FILE variable before calling log_message - if that assignment was accidentally removed during the migration (assuming common.sh would somehow handle it), log_message's new default of /dev/stdout would send output to a cron job's stdout capture rather than the expected dated log file.
Manager Round: Why invest in a hardening sprint now, after all 28 projects were already individually built and working, rather than building this shared library from the very first project?
The specific, valuable shared patterns worth consolidating only became fully clear after building enough real, varied projects to see what was genuinely common versus what only looked similar at first; consolidating too early risks baking in a wrong abstraction, while this retrospective sprint benefits from real, accumulated evidence of what actually needed to be shared.
Architecture: Why does this project keep the ERR trap approach rather than simply recommending set -e everywhere despite its known pitfalls?
The ERR trap fires far more consistently and predictably than errexit across the varied contexts these 28 scripts actually use (conditionals, pipelines, command substitutions), and pairing it with this course's already-consistent explicit-check style gives precise diagnostics without inheriting set -e's well-known surprising exceptions.
Best Practice: Why is it critical that common.sh remain behaviorally compatible with what all 28 existing projects already expect, rather than "improving" function signatures during consolidation?
Breaking an existing, working, production-scheduled script's expectations during what's meant to be a safety-improving hardening pass would be a serious, self-defeating regression; any genuine improvement to a function's interface should be a separate, deliberately reviewed and tested change, not bundled invisibly into a consolidation migration.
Real Incident Discussion: What's the single most direct design decision in this project that would prevent a repeat of the pipefail-related disk-monitor near-miss, suite-wide, going forward?
Running ShellCheck across the entire suite as a standing practice, combined with the consolidated common.sh ensuring every project's baseline error-handling setup (set -uo pipefail, the ERR trap) is applied consistently rather than manually re-typed and potentially mistyped 28 separate times - the exact class of subtle, edge-case pipeline bug that caused the near-miss becomes mechanically detectable and structurally less likely across every project at once, not just the one where it happened to be noticed.
