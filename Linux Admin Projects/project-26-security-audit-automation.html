Security Audit Automation

An expensive external penetration test found an open debug port, root SSH login enabled, and world-writable files — none of which anyone had ever proactively checked for.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL ⏱️ Duration: 3 hrs

📖 The Story — Findings a Free Script Could Have Caught

NovaTrust's annual external penetration test came back with a list of findings that stung less because of their severity and more because of how avoidable they were: a debug port left open on several production servers since a forgotten troubleshooting session months earlier, PermitRootLogin still enabled in SSH configuration on servers that had simply never been hardened since initial setup, a handful of world-writable files sitting in a shared directory from an old, long-forgotten misconfiguration, and one unexpected SUID binary nobody could immediately explain. Every single finding was individually simple to detect — none required anything close to the sophistication of an actual penetration test.

Priya's assignment: "We paid a lot of money to learn things a scheduled Bash script could have told us for free, continuously, for months. I want an internal security audit sweep — open ports against an approved list, SSH hardening settings, world-writable files, unexpected SUID binaries, and overly broad sudo access — run regularly, so external pentest findings become confirmations of things we already know and are actively managing, not surprises."

This project is strictly read-only, like Project 23's DR validation — detecting and reporting security drift, never attempting to fix it automatically, since an automated security "fix" applied incorrectly can itself cause an outage or worse.
🔁 Reinforced from Projects 1–25
Project 12's baseline-comparison philosophy, Project 15/16's port-parsing techniques, and the strict read-only detection boundary from Project 23 all converge here in a dedicated security-posture context.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Continuously audit servers for common, well-known security misconfigurations — unauthorized open ports, weak SSH hardening, world-writable files, unexpected SUID binaries, and overly broad sudo access.

Customer Requirement

Security needs internal, continuous detection of exactly the class of finding an external audit would flag — catching drift between annual assessments, not only during them.

Banking Scenario

NovaTrust's Core Banking servers must maintain a hardened security posture continuously, not merely at the moment of an annual external penetration test.

Existing Manual Process / Prior Automation Gap

Security posture had only ever been checked during infrequent, expensive external assessments — no continuous internal equivalent existed for even the most basic, well-understood categories of misconfiguration.

Problems With Assessment-Only Security Posture Checking

Configuration drift accumulates silently between annual assessments — a forgotten debug port or an unhardened SSH setting can persist for months, fully exposed, before the next scheduled external review happens to catch it.

Business Impact & Risk

Every one of the pentest's findings represented real exposure time during which the vulnerability existed and was exploitable, entirely avoidable with continuous, low-cost internal detection.

Why Automation Is Required

Only a scheduled, automated sweep can continuously check these well-defined, well-understood security categories across the entire fleet — closing the gap between expensive, infrequent external assessments.

Solution Design

A weekly audit script compares listening ports against an approved baseline, checks SSH configuration against required hardening directives, scans for world-writable files and unexpected SUID/SGID binaries against an approved whitelist, and flags overly broad sudo grants — all strictly read-only, classified into a security-specific severity model.

Project Scope

In scope: read-only detection across the five categories above. Explicitly out of scope, permanently: any automatic remediation of a security finding — misapplied fixes (revoking the wrong sudo access, closing a port a legitimate service needs) can themselves cause outages, making human review mandatory for any actual change.

Expected Outcome

Weekly internal detection of exactly the class of finding the external pentest surfaced — turning future assessment results into confirmations of known, already-being-addressed issues rather than fresh surprises.

🧠 New Bash Concepts for This Project

1. Listening Ports vs. an Approved Baseline (ss -tuln, Reinforced)

What: ss -tuln lists all TCP/UDP listening ports — reinforcing Project 15/16's port-related parsing, now compared line-by-line against a configured list of approved ports rather than checked against a single expected service.
Why: Any listening port not on the approved list (like a forgotten debug port) represents unmanaged, unreviewed attack surface — exactly the class of finding the pentest caught manually.

2. Auditing SSH Hardening Directives

What: Parsing /etc/ssh/sshd_config with grep -E for specific directives (PermitRootLogin, PasswordAuthentication, X11Forwarding) and comparing each against its required secure value.
Why: SSH configuration is one of the highest-value, most commonly-checked hardening surfaces in any security assessment — automating this specific, well-known checklist closes a very standard, very expected gap.

3. Finding World-Writable Files (find -perm -0002)

What: find /path -type f -perm -0002 — the -0002 permission mode specifically matches files where the "others" write bit is set, regardless of any other permission bits also being set.
Why: A world-writable file means literally any user on the system can modify it — a serious, concrete integrity risk that's simple to detect but easy to accidentally introduce (a careless chmod 777) and then forget about.

4. Finding SUID/SGID Binaries (find -perm -4000 / -perm -2000)

What: find / -type f -perm -4000 finds SUID binaries (run with the file owner's privileges, often root, regardless of who executes them); -perm -2000 finds the SGID equivalent.
Why: SUID/SGID binaries are a well-known privilege-escalation vector; a legitimate system has a small, known, expected set of them — anything outside that expected set deserves immediate scrutiny.

5. Comparing Found SUID Binaries Against an Approved Whitelist (Reinforced Project 12 Pattern)

What: Loading an approved list of expected SUID binary paths into an array, then flagging any SUID binary found on the system that isn't in that list — the same baseline-comparison philosophy from Project 12's file integrity monitoring, now applied to a security-relevant binary inventory instead of configuration file checksums.

6. Auditing Sudo Access for Overly Broad Grants

What: Reading /etc/sudoers and /etc/sudoers.d/* (read-only, never edited by this script) for lines granting ALL=(ALL) NOPASSWD: ALL — an unrestricted, password-free sudo grant — and flagging any such entry found.
Why: A NOPASSWD: ALL grant means any compromise of that user's account immediately becomes full, unchallenged root access — one of the most consequential single misconfigurations a security audit checks for.

7. A Security-Specific Severity Taxonomy (New Classification Model)

What: CRITICAL / HIGH / MEDIUM / INFO — a distinct four-tier model from this project's own domain, different from the PASS/WARN/FAIL/CRITICAL pattern used throughout most of this course's operational monitoring.
Why: Security findings genuinely warrant a different vocabulary than operational health status — "CRITICAL" in a security context (like an unrestricted sudo grant) carries different weight and urgency than "CRITICAL" meaning a server is down, and using domain-appropriate language matters for how findings get triaged.

8. The Strongest Possible "Detection Only" Boundary (Reinforced Project 23)

What: Exactly like Project 23's DR validation, this script contains no code path capable of modifying a port, an SSH setting, a file permission, or a sudoers entry — detection and remediation are permanently, structurally separate.
Why: An automated "fix" for a security finding carries real risk of misfiring — auto-revoking sudo access from the wrong account, or closing a port an undocumented-but-legitimate service actually needs, could each cause a serious operational incident of their own.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Security audit helper functions (STRICTLY READ-ONLY)
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

write_finding() {
    local severity="$1" category="$2" detail="$3"
    echo "${severity},${category},\"${detail}\"" >> "$CSV_REPORT"
}

# ---------- get_listening_ports ----------
get_listening_ports() {
    ss -tuln 2>/dev/null | tail -n +2 | grep -oP ':\K[0-9]+(?=\s)' | sort -un
}

# ---------- check_ssh_directive ----------
# Purpose: Return the CURRENT value of an sshd_config directive (last matching, uncommented line wins)
check_ssh_directive() {
    local directive="$1"
    grep -iE "^\s*${directive}\s+" "$SSHD_CONFIG_PATH" 2>/dev/null | tail -n 1 | awk '{print $2}'
}

# ---------- find_world_writable_files ----------
find_world_writable_files() {
    local dir="$1"
    [[ -d "$dir" ]] || return
    find "$dir" -type f -perm -0002 2>/dev/null
}

# ---------- find_suid_sgid_binaries ----------
find_suid_sgid_binaries() {
    local root="$1"
    find "$root" -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null
}

# ---------- is_in_approved_list ----------
is_in_approved_list() {
    local value="$1"
    local list_file="$2"
    grep -qxF "$value" "$list_file" 2>/dev/null   # -x = whole-line exact match, -F = literal (not regex)
}

# ---------- find_nopasswd_all_grants ----------
find_nopasswd_all_grants() {
    local sudoers_dir="$1"
    [[ -d "$sudoers_dir" ]] || return
    grep -rlE "ALL=\(ALL(:ALL)?\)\s+NOPASSWD:\s*ALL" "$sudoers_dir" 2>/dev/null
}

Line-by-Line Highlights

  • ss -tuln | tail -n +2 | grep -oP ':\K[0-9]+(?=\s)' — skips the header row, then extracts just the port number from each address:port combination using the same \K-plus-lookahead technique from Projects 14 and 22.
  • check_ssh_directive takes the last matching line specifically, because sshd_config can legitimately contain a directive multiple times (an earlier default commented out, later overridden) — the last uncommented occurrence is what actually takes effect.
  • find "$dir" -type f -perm -0002 — the leading - before 0002 means "at least these bits are set," correctly matching a file that's world-writable regardless of what its owner/group permissions also happen to be.
  • find "$root" -type f \( -perm -4000 -o -perm -2000 \) — parenthesized, -o-joined find expression matching files with either the SUID or SGID bit set, in one single pass over the filesystem.
  • grep -qxF "$value" "$list_file" — -x requires the entire line to match exactly (not just a substring), preventing a partial-path false match against the approved-binaries whitelist.
  • Every single function in this file only reads from the filesystem — there is deliberately no function anywhere capable of modifying a port, a config file, a permission bit, or a sudoers entry.

🩺 Main Script

scripts/security_audit.sh
#!/bin/bash
# =====================================================================
# security_audit.sh
# NovaTrust Bank - Security Posture Audit (STRICTLY READ-ONLY)
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/security_audit.conf"

APPROVED_PORTS_FILE="$SCRIPT_DIR/../config/approved_ports.txt"
SSH_BASELINE_FILE="$SCRIPT_DIR/../config/ssh_hardening_baseline.txt"
APPROVED_SUID_FILE="$SCRIPT_DIR/../config/approved_suid_binaries.txt"

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/security_audit_${TODAY}.log"
CSV_REPORT="$SCRIPT_DIR/$REPORT_DIR/security_findings_${TODAY}.csv"
mkdir -p "$(dirname "$LOG_FILE")" "$(dirname "$CSV_REPORT")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Security audit run finished."' EXIT

echo "severity,category,detail" > "$CSV_REPORT"
log_message "INFO" "=== Starting security posture audit (READ-ONLY) ==="

FINDINGS_COUNT=0

# ---------- Category 1: Open ports vs approved baseline ----------
while IFS= read -r port; do
    [[ -z "$port" ]] && continue
    if ! is_in_approved_list "$port" "$APPROVED_PORTS_FILE"; then
        log_message "FAIL" "HIGH: Unapproved open port detected: $port"
        write_finding "HIGH" "Open Ports" "Port $port is listening but not in the approved baseline"
        ((FINDINGS_COUNT++))
    fi
done < <(get_listening_ports)

# ---------- Category 2: SSH hardening ----------
while IFS=':' read -r directive required_value; do
    [[ -z "$directive" || "$directive" == \#* ]] && continue
    current_value=$(check_ssh_directive "$directive")
    current_value_lower=$(echo "$current_value" | tr '[:upper:]' '[:lower:]')

    if [[ "$current_value_lower" != "$required_value" ]]; then
        log_message "FAIL" "CRITICAL: SSH directive $directive is '${current_value:-unset}' (required: $required_value)"
        write_finding "CRITICAL" "SSH Hardening" "$directive is '${current_value:-unset}', required '$required_value'"
        ((FINDINGS_COUNT++))
    fi
done < "$SSH_BASELINE_FILE"

# ---------- Category 3: World-writable files ----------
for dir in "${WORLD_WRITABLE_SCAN_DIRS[@]}"; do
    while IFS= read -r file; do
        [[ -z "$file" ]] && continue
        log_message "FAIL" "MEDIUM: World-writable file found: $file"
        write_finding "MEDIUM" "File Permissions" "World-writable: $file"
        ((FINDINGS_COUNT++))
    done < <(find_world_writable_files "$dir")
done

# ---------- Category 4: SUID/SGID binaries vs whitelist ----------
while IFS= read -r binary; do
    [[ -z "$binary" ]] && continue
    if ! is_in_approved_list "$binary" "$APPROVED_SUID_FILE"; then
        log_message "FAIL" "HIGH: Unexpected SUID/SGID binary: $binary"
        write_finding "HIGH" "SUID/SGID Binaries" "Not in approved whitelist: $binary"
        ((FINDINGS_COUNT++))
    fi
done < <(find_suid_sgid_binaries "$SUID_SCAN_ROOT")

# ---------- Category 5: Unrestricted sudo grants ----------
while IFS= read -r sudoers_file; do
    [[ -z "$sudoers_file" ]] && continue
    log_message "FAIL" "CRITICAL: Unrestricted NOPASSWD:ALL sudo grant found in $sudoers_file"
    write_finding "CRITICAL" "Sudo Access" "NOPASSWD:ALL grant in $sudoers_file"
    ((FINDINGS_COUNT++))
done < <(find_nopasswd_all_grants "$SUDOERS_DIR")

# ---------- Summary ----------
if [[ "$FINDINGS_COUNT" -eq 0 ]]; then
    log_message "INFO" "=== SUMMARY: Clean audit - 0 findings across all categories ==="
    exit 0
else
    log_message "INFO" "=== SUMMARY: $FINDINGS_COUNT security finding(s) - see $CSV_REPORT for details ==="
    exit 2
fi

Every Line, Explained

LineExplanation
current_value_lower=$(echo "$current_value" | tr '[:upper:]' '[:lower:]')SSH config values can legitimately appear with varying capitalization (No vs no) — normalizing to lowercase before comparison avoids a false-positive finding purely from a case difference that doesn't actually affect SSH's own behavior.
Five structurally independent sections, each with its own loopEach category is entirely self-contained — a bug or change in the SUID-checking logic, for instance, can't accidentally affect the SSH-hardening check, keeping each audit category easy to reason about and modify independently.
Every write_finding call is paired with a log_message "FAIL" callFindings are recorded to both the human-readable operational log and the structured CSV report simultaneously, consistent with every prior project's dual-output pattern.
No function or code path anywhere calls chmod, iptables, visudo, or edits sshd_configThis is the project's core safety guarantee, made structurally impossible to violate rather than merely documented — there is no remediation capability anywhere in this script to accidentally trigger.
exit 2 whenever FINDINGS_COUNT > 0Any finding at all, regardless of severity tier, is treated as worth a non-zero exit code — even a single MEDIUM-severity world-writable file deserves attention, not silent tolerance.

📄 README.md

README.md
# NovaTrust Bank - Security Audit Automation

## IMPORTANT: This script is strictly READ-ONLY
It detects and reports security findings only. It NEVER modifies a port,
an SSH configuration setting, a file permission, or a sudoers entry.
Remediating any finding requires deliberate human review and change control.

## Usage
    ./scripts/security_audit.sh

## Categories Audited
1. Open ports vs. an approved baseline
2. SSH configuration hardening directives
3. World-writable files in specified critical directories
4. SUID/SGID binaries vs. an approved whitelist
5. Unrestricted (NOPASSWD:ALL) sudo grants

## Severity Model
    CRITICAL = SSH root login/password auth enabled, unrestricted sudo grant
    HIGH     = Unapproved open port, unexpected SUID/SGID binary
    MEDIUM   = World-writable file

## Exit Codes
    0 = Clean audit, zero findings
    2 = One or more findings of any severity

🔄 What Happens Internally

  1. Five entirely independent audit categories — network state, a config file, filesystem permissions (twice, differently), and a privilege-grant file — demonstrate that "security audit" isn't one technique but a deliberate combination of several genuinely different investigative approaches.
  2. Baseline files (approved ports, SSH requirements, approved SUID binaries) are the only things that change as NovaTrust's legitimate configuration evolves — adding a new genuinely-needed open port means one line in approved_ports.txt, never a change to the audit logic itself.
  3. Case-insensitive comparison for SSH directive values specifically accounts for a real-world quirk (SSH configuration accepting mixed-case values) that a naive exact-string comparison would incorrectly flag as a false positive.
  4. Every single function is provably read-only — a careful line-by-line review of utils.sh confirms not one command anywhere writes to, modifies, or executes anything security-relevant, which is the structural proof behind this project's core safety claim.

🛡️ Production Best Practices

Never Auto-Remediate Security Findings

An automated "fix" applied incorrectly can itself cause a serious outage — every finding deserves deliberate human review before any actual change is made.

Baseline-Driven, Never Hardcoded

Approved ports, SSH requirements, and SUID whitelists all belong in config files — adding a legitimate new item should never require touching the audit script's own logic.

Use Domain-Appropriate Severity Language

A security-specific severity taxonomy communicates urgency and triage priority more accurately to a security audience than reusing generic operational health terms.

Scope Expensive Filesystem Scans Deliberately

A SUID/world-writable scan across an entire filesystem is expensive — scope directories thoughtfully to balance thoroughness against runtime and system load.

Normalize Before Comparing

Case sensitivity and formatting variance in configuration files are common sources of false positives — normalize both sides of any comparison consistently.

Continuous Internal Checks Complement, Never Replace, External Assessments

This kind of automation catches known, well-understood misconfiguration categories — a genuine external penetration test still finds things this specific, defined checklist never will.

🎤 Interview Preparation

Scenario: The audit flags an "unapproved" open port that turns out to be a legitimate new service the team forgot to register. How should this be handled?
Add the port to approved_ports.txt through the normal change process — this is exactly the intended workflow, and it's a feature, not a bug, that the audit doesn't distinguish "legitimate but unregistered" from "genuinely unauthorized"; both require the same corrective action (updating the baseline), just for different underlying reasons.
Production Support: The SSH hardening check reports PermitRootLogin as "unset" even though you can see it's clearly set to "no" in the config file. What might explain this?
Check whether the directive appears multiple times in the file (a common pattern — a default commented line, then an actual override elsewhere) and whether check_ssh_directive's regex is correctly matching the uncommented instance; also verify there's no typo or extra whitespace in the config line itself that the regex might not be matching.
Shell Scripting: Why does is_in_approved_list use grep -x (exact whole-line match) rather than a simple substring grep?
A substring match could produce a dangerous false negative — for example, /usr/bin/passwd would substring-match against a more specific unapproved path like /usr/bin/passwd-backup, incorrectly treating an unlisted binary as approved just because part of its path happens to overlap with a legitimate entry; exact whole-line matching eliminates this entire class of false negative.
Troubleshooting: The world-writable file scan reports zero findings, but you can manually confirm a world-writable file exists in a scanned directory. What's the likely bug?
Confirm the directory path in WORLD_WRITABLE_SCAN_DIRS is exactly correct and that the script actually has read/traverse permission into that directory — a permissions issue on the directory itself (not the target file) would cause find to silently skip files it can't reach, without necessarily producing an obvious error.
Manager Round: Why does this project treat even a single MEDIUM-severity finding (like one world-writable file) as worth a non-zero exit code, rather than only escalating on CRITICAL/HIGH findings?
Security posture drift tends to compound — one "minor" world-writable file today can become the specific detail that enables a larger compromise later; treating every finding, regardless of severity, as worth surfacing keeps the team continuously aware of and addressing drift rather than only reacting once something becomes severe enough to trigger an exit code.
Architecture: Why does this project maintain a hard, structural boundary against remediation, when Projects 5, 10, 12, and 19 all eventually built a gated, dry-run-first remediation path?
Those projects' remediation actions (compressing old logs, locking a user account, updating a checksum baseline, tagging a cloud resource) are relatively contained and reversible; security remediation (revoking sudo access, closing a port, changing SSH settings) carries meaningfully higher risk of causing an unrelated operational outage if applied incorrectly or against a misunderstood context, justifying a stricter, permanent detection-only boundary here rather than even a gated remediation option.
Best Practice: Why check SUID/SGID binaries against a positive whitelist (approved list) rather than a list of known-bad binaries to avoid?
A whitelist (default-deny, explicitly approve) is fundamentally safer than a blocklist (default-allow, explicitly deny) for a security-relevant inventory — a blocklist approach would silently miss any new or unusual SUID binary that simply wasn't yet known to be bad, while a whitelist correctly flags anything unexpected by default, regardless of whether it's specifically been seen as malicious before.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the pentest's open debug port finding months earlier, at effectively zero ongoing cost?
The weekly, automated comparison of actual listening ports against an explicit approved-ports baseline — the forgotten debug port would have shown up as a HIGH-severity finding in the very first weekly audit after it was left open, rather than remaining undetected for months until the next expensive external penetration test happened to find it.

Port-baseline comparison, SSH hardening directive auditing with proper case normalization, world-writable and SUID/SGID file detection via find -perm, whitelist-based (not blocklist-based) security inventory checking, and a domain-appropriate severity taxonomy distinct from operational health status.

Common Mistakes to Avoid

Comparing configuration values without normalizing case, using substring matching instead of exact-line matching against a security whitelist, scanning the entire filesystem unnecessarily for SUID binaries, using a blocklist instead of a whitelist approach, and ever adding any remediation capability to a strictly-read-only security audit tool.
