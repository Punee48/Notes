User Management Automation

A contractor's access review found an account still active 45 days after their last day — on a Core Banking production server.

🎯 Level: Intermediate–Advanced 🧠 New Concepts: 10 🏗️ Environment: Linux / WSL, root/sudo ⏱️ Duration: 3 hrs

📖 The Story — The Account Nobody Remembered to Remove

NovaTrust's quarterly access review turned up something uncomfortable: a contractor who left the organization 45 days earlier still had an active Linux account, with SSH key access, on a Core Banking production server. Nobody had done anything wrong exactly — HR sent the offboarding email, IT just never got around to actually removing the account, because it required someone to manually SSH into each of 200 servers and run userdel.

Priya's ask this time is different from every infrastructure project so far: "I want new-hire accounts created consistently, the moment they're approved, and I want departures removed the same day, automatically, from an HR-provided list. And because this script can delete a real person's access, I want dry-run mode, I want every single action logged for audit, and I want it to refuse to run unless it's actually running as root."

Today we leave infrastructure monitoring behind for the first time and step into identity and access management — arguably an even higher-stakes category of automation.
🔁 Reinforced from Projects 1–9
The mandatory dry-run pattern (Project 5), config-driven behavior, flock, and disciplined logging all continue — now applied to something that can affect a real person's ability to do their job.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Automate Linux user account provisioning and deprovisioning from an HR-approved input file, with a complete audit trail for every action taken.

Customer Requirement

Security and Audit need proof that account changes match HR records exactly, and that departures are removed same-day, not "eventually."

Banking Scenario

NovaTrust's Core Banking servers require named individual Linux accounts (never shared logins) for every engineer with production access, reviewed quarterly.

Existing Manual Process

An IT engineer manually SSHs into each relevant server and runs useradd/userdel by hand, based on an email from HR — with no consistent record of exactly what was done, when, or by whom.

Problems with Manual Process

Slow (multiplied across 200 servers), inconsistent (different engineers may configure new accounts slightly differently), and easy to simply forget, as the 45-day-late removal proved.

Business Impact & Risk

A departed contractor retaining production access to Core Banking systems is a serious security and regulatory finding — exactly the kind of gap an external audit would flag as a control failure.

Why Automation Is Required

Only a script, run consistently and immediately against an authoritative HR list, can guarantee same-day deprovisioning and a complete, reviewable audit trail every time.

Solution Design

A script reads a CSV-style input file of usernames and an action (create or deactivate), validates each entry, applies idempotent account changes, enforces password/account expiration policy on creation, and logs every single action to an audit-specific log file.

Project Scope

In scope: account creation with policy enforcement, account deactivation (locking, not immediate deletion), input validation, dry-run mode, and audit logging. Out of scope: SSH key distribution and centralized identity/LDAP integration (larger, separate initiatives).

Expected Outcome

One script, run against a daily HR export, that creates new joiners' accounts with correct policy and deactivates leavers' accounts the same day — with a complete, timestamped audit log of every action for the next access review.

🧠 New Bash Concepts for This Project

1. Requiring Root Privileges ($EUID)

What: [[ $EUID -eq 0 ]] || { echo "Must run as root"; exit 1; } — $EUID is Bash's built-in "effective user ID" variable; root is always 0.
Why: Every command in this script (useradd, usermod, chage) requires root privileges — failing fast with a clear message beats a confusing permission-denied error midway through processing a batch of users.

2. Reading CSV Input with a Custom Delimiter

What: IFS=',' read -r username fullname action <<< "$line" splits a comma-separated line into named fields, same technique as Project 6's colon-separated config, with a different delimiter.
Why: HR exports data in a standard CSV format — our script needs to consume that format directly rather than requiring HR to learn a custom syntax.

3. Strict Input Validation with Regex (Reinforced)

What: [[ "$username" =~ ^[a-z][a-z0-9_-]{2,31}$ ]] validates a username matches Linux's actual accepted username format before we ever pass it to useradd.
Why: A malformed or malicious CSV row (accidentally or deliberately) must never reach a privileged command like useradd unvalidated — this is a security control, not just a data-quality one.

4. Idempotency Checks Before Creating (id)

What: id "$username" >/dev/null 2>&1 checks whether a user already exists — its exit code tells us instantly.
Why: Re-running the script against the same HR export (which will happen — exports overlap, jobs retry) must never error out or attempt to create a duplicate account.

5. Creating Users with useradd

What: useradd -m -s /bin/bash -c "Full Name" "$username" — -m creates a home directory, -s sets the login shell, -c sets the GECOS comment field (typically the full name).

6. Generating a Secure Random Temporary Password

What: openssl rand -base64 16 generates a strong random string suitable as a one-time initial password.
Why: New accounts need a real initial credential, but hardcoding or guessing one defeats the entire purpose — a properly random generator is required.

7. Enforcing Password/Account Expiration Policy (chage)

What: chage -d 0 "$username" forces a password change at next login; chage -M 90 "$username" sets a 90-day maximum password age.
Why: A temporary generated password should never remain valid indefinitely — forcing an immediate change on first login is standard security policy for any new account.

8. Locking (Not Deleting) an Account (usermod -L / passwd -l)

What: usermod -L "$username" locks the account's password (login becomes impossible) while leaving the account, home directory, and file ownership completely intact.
Why: Locking is reversible in seconds if HR's list turns out to be wrong; userdel is destructive and can orphan files or break ownership records — the house rule after Project 5's dry-run lesson applies here even more strongly.

9. A Dedicated, Structured Audit Log (Distinct from the Operational Log)

What: A separate, append-only audit.log recording exactly who/what/when for every account action — distinct from the script's regular operational log used for day-to-day troubleshooting.
Why: Audit and Security need a clean, dedicated trail they can hand to an external auditor without wading through routine operational noise.

10. Case-Insensitive and Exact Matching for Actions (Reinforced case)

What: A case "$action" in create|CREATE) ... ;; deactivate|DEACTIVATE) ... ;; *) ... ;; esac pattern — case supports multiple patterns per branch separated by |.
Why: HR exports aren't always perfectly consistent in casing — being slightly forgiving on the action field (while remaining strict on the username) reduces avoidable processing failures.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - User lifecycle helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- audit_log ----------
# Purpose: Append a structured, permanent record to the dedicated audit trail
# Arguments: $1 = action (CREATED/DEACTIVATED/SKIPPED/REJECTED), $2 = username, $3 = detail
audit_log() {
    local action="$1"
    local username="$2"
    local detail="$3"
    local timestamp operator
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    operator="${SUDO_USER:-$(whoami)}"                  # Prefer the real human behind sudo, fall back to current user

    echo "${timestamp}|${operator}|${action}|${username}|${detail}" >> "$AUDIT_LOG"
}

# ---------- is_valid_username ----------
is_valid_username() {
    local username="$1"
    [[ "$username" =~ $USERNAME_REGEX ]]
}

# ---------- user_exists ----------
user_exists() {
    local username="$1"
    id "$username" >/dev/null 2>&1
}

# ---------- generate_temp_password ----------
generate_temp_password() {
    openssl rand -base64 16                              # ~22 characters of strong randomness, base64-encoded
}

# ---------- create_user_account ----------
# Purpose: Idempotently create a user with policy enforcement. Returns 0 on success, 1 if already existed.
create_user_account() {
    local username="$1"
    local fullname="$2"

    if user_exists "$username"; then
        return 1                                         # Signal "already existed" - caller decides how to log this
    fi

    local temp_password
    temp_password=$(generate_temp_password)

    useradd -m -s "$DEFAULT_SHELL" -c "$fullname" "$username"
    echo "${username}:${temp_password}" | chpasswd        # Set the generated temporary password

    if [[ "$FORCE_CHANGE_ON_FIRST_LOGIN" == "true" ]]; then
        chage -d 0 "$username"                             # Forces a password change at next login
    fi
    chage -M "$PASSWORD_MAX_DAYS" "$username"              # Enforces maximum password age going forward

    return 0
}

# ---------- deactivate_user_account ----------
# Purpose: Lock (never delete) a user's account. Returns 0 on success, 1 if account didn't exist.
deactivate_user_account() {
    local username="$1"
    user_exists "$username" || return 1
    usermod -L "$username"                                 # Locks the password - login becomes impossible
    chage -E "$(date -d 'today' '+%Y-%m-%d')" "$username"   # Also sets the account expiration date to today
    return 0
}

Line-by-Line Highlights

  • operator="${SUDO_USER:-$(whoami)}" — SUDO_USER is set automatically by sudo to the real human who invoked it (since the script itself runs as root); falling back to whoami covers the case of running directly as root with no sudo layer.
  • echo "${username}:${temp_password}" | chpasswd — chpasswd reads username:password pairs from stdin, the standard non-interactive way to set a password without an interactive prompt.
  • chage -d 0 "$username" — setting the last-password-change date to day zero (epoch) forces Linux to treat the password as immediately expired, triggering a mandatory change at next login.
  • usermod -L vs. userdel — -L prefixes the password hash with !, making password-based login impossible while leaving the account, UID, home directory, and file ownership completely untouched and instantly reversible with usermod -U.
  • chage -E "$(date ... '+%Y-%m-%d')" — setting an explicit account expiration date is a second, independent enforcement layer beyond just locking the password, covering authentication methods (like SSH keys) that don't go through the password check at all.

🩺 Main Script

scripts/user_lifecycle.sh
#!/bin/bash
# =====================================================================
# user_lifecycle.sh
# NovaTrust Bank - CSV-Driven User Provisioning & Deprovisioning
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/user_lifecycle.conf"

# ---------- Mandatory root check - fail before touching anything else ----------
if [[ $EUID -ne 0 ]]; then
    echo "ERROR: This script must be run as root (try: sudo $0 ...)" >&2
    exit 1
fi

DRY_RUN="false"
INPUT_FILE=""
while getopts "nf:h" opt; do
    case $opt in
        n) DRY_RUN="true" ;;
        f) INPUT_FILE="$OPTARG" ;;
        h) echo "Usage: sudo $0 -f input.csv [-n]"; exit 0 ;;
        *) echo "Usage: sudo $0 -f input.csv [-n]"; exit 1 ;;
    esac
done

[[ -n "$INPUT_FILE" && -f "$INPUT_FILE" ]] || { echo "ERROR: -f input CSV file is required and must exist" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/user_lifecycle_${TODAY}.log"
AUDIT_LOG="$SCRIPT_DIR/$AUDIT_LOG"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "User lifecycle run finished. Dry-run: $DRY_RUN"' EXIT

log_message "INFO" "=== Starting user lifecycle run against $INPUT_FILE (dry-run: $DRY_RUN) ==="

CREATED=0; DEACTIVATED=0; SKIPPED=0; REJECTED=0

while IFS=',' read -r username fullname action; do
    [[ -z "$username" || "$username" == \#* ]] && continue

    # ---------- Security gate: validate BEFORE doing anything else ----------
    if ! is_valid_username "$username"; then
        log_message "FAIL" "Rejected invalid username: '$username'"
        audit_log "REJECTED" "$username" "failed username format validation"
        ((REJECTED++))
        continue
    fi

    case "$action" in
        create|CREATE)
            if [[ "$DRY_RUN" == "true" ]]; then
                if user_exists "$username"; then
                    log_message "INFO" "[DRY-RUN] Would skip (already exists): $username"
                else
                    log_message "INFO" "[DRY-RUN] Would create: $username ($fullname)"
                fi
                continue
            fi

            if create_user_account "$username" "$fullname"; then
                log_message "PASS" "Created user: $username ($fullname)"
                audit_log "CREATED" "$username" "fullname=$fullname, forced_password_change=$FORCE_CHANGE_ON_FIRST_LOGIN"
                ((CREATED++))
            else
                log_message "INFO" "Skipped (already exists): $username"
                audit_log "SKIPPED" "$username" "account already existed - idempotent no-op"
                ((SKIPPED++))
            fi
            ;;

        deactivate|DEACTIVATE)
            if [[ "$DRY_RUN" == "true" ]]; then
                log_message "INFO" "[DRY-RUN] Would deactivate (lock): $username"
                continue
            fi

            if deactivate_user_account "$username"; then
                log_message "PASS" "Deactivated (locked) user: $username"
                audit_log "DEACTIVATED" "$username" "account locked and expired same-day"
                ((DEACTIVATED++))
            else
                log_message "WARN" "Cannot deactivate - account does not exist: $username"
                audit_log "SKIPPED" "$username" "deactivation requested but account did not exist"
                ((SKIPPED++))
            fi
            ;;

        *)
            log_message "FAIL" "Unknown action '$action' for user: $username"
            audit_log "REJECTED" "$username" "unrecognized action: $action"
            ((REJECTED++))
            ;;
    esac

done < "$INPUT_FILE"

log_message "INFO" "=== SUMMARY: Created $CREATED | Deactivated $DEACTIVATED | Skipped $SKIPPED | Rejected $REJECTED ==="
exit 0

LineExplanation

if ! is_valid_username "$username"; then ... continue; fiRuns before the case statement branches on action — an invalid username must never reach useradd or usermod regardless of what action was requested.

🔄 What Happens Internally

  1. The root check happens before getopts even runs — there's no reason to parse flags at all if the script can't perform any privileged action regardless of what's requested.
  2. Validation happens before the action case statement, not inside each branch — this guarantees no code path, present or future, can ever accidentally skip username validation.
  3. useradd, chpasswd, and chage are each separate privileged system calls under the hood, wrapped by our script into one logical "create" operation — if one succeeded and a later one failed, the account would exist in a partially-configured state, a real edge case worth hardening further as an exercise.
  4. The audit log and operational log are two entirely separate files, written to independently — this separation is deliberate so Project 5's log rotation can be configured differently (or excluded entirely) for the audit trail versus routine operational logs.

🛡️ Production Best Practices

Lock, Don't Delete

Deactivation should always be reversible — locking preserves the account, home directory, and ownership records intact in case of an HR data error.

Validate Before Any Privileged Call

Every input must pass strict validation before it ever reaches useradd/usermod — treat unvalidated CSV input exactly like the untrusted external data it is.

Separate Audit Trail from Operational Logs

Compliance-grade records need different retention, different rotation rules, and ideally different (more restricted) access than day-to-day troubleshooting logs.

Force Credential Rotation on New Accounts

A generated temporary password should always require an immediate change — never remain valid indefinitely as-issued.

Fail Closed on Privilege Checks

Checking $EUID before doing anything else is the identity-management equivalent of Project 7's credentials-file permission gate — refuse first, act second.

Idempotency Is Not Optional

Any script processing a real-world data export must tolerate being re-run against overlapping or repeated data without side effects — this will happen in production, not hypothetically.

🎤 Interview Preparation

Scenario: An access review finds a locked account that should have been fully deleted six months ago per data retention policy. Is this a bug in our design?
Not a bug, but a scope gap worth surfacing — this project deliberately treats locking as the terminal state for safety, but a mature identity lifecycle needs a separate, deliberately slower "purge after N months locked" process with its own explicit approval step, distinct from same-day deactivation.
Production Support: The script reports a user was "Created" but they can't log in at all, even with the temporary password. What would you check?
Verify each of the three separate privileged calls actually succeeded independently — useradd, then chpasswd, then the two chage calls — since a partial failure partway through (e.g., chpasswd failing silently) could leave an account created but without a usable password set.
Shell Scripting: Why check username validity with a regex instead of just trying useradd and seeing if it fails?
Letting an invalid or malicious string reach a privileged command at all is itself a risk (however useradd might handle it) — validating in our own script first is a defense-in-depth control that never depends on trusting an external command's own input handling.
Troubleshooting: Re-running the same CSV a second time throws an error on the second user instead of skipping it. What's likely wrong?
The idempotency check (user_exists via id) may not be running before useradd, or its exit code isn't being interpreted correctly — verify create_user_account's early return 1 path is actually reached and that the caller checks it before attempting creation.
Manager Round: Why did the team decide to keep deactivation as a same-day automated action, but treat any eventual account deletion as a separate, non-automated decision?
Deactivation (locking) is fast, safe, and fully reversible, making same-day automation low-risk; permanent deletion is irreversible and can have downstream effects (orphaned files, broken audit trails referencing that UID), so it's deliberately kept as a deliberate, reviewed decision rather than something a script does unattended.
Architecture: Why write the audit log in a simple pipe-delimited flat-file format instead of JSON or a database?
Consistent with Project 3 and Project 5's design philosophy — at this scale, a flat, append-only, grep-able format is simpler to produce, review, and hand to an auditor than adding a database dependency purely for record-keeping that doesn't need complex querying.
Best Practice: Why does the script check $EUID instead of just letting useradd fail naturally when run without sufficient privileges?
Failing on the very first user in a batch of fifty, deep inside a loop, with a generic "permission denied" from useradd, is a much worse operator experience than an immediate, clear, single message at the very start of the script explaining exactly what's required.
Real Incident Discussion: What's the single design decision in this project that most directly would have prevented the 45-day-late offboarding?
Same-day, automated processing of the HR export's deactivate rows via a scheduled run — rather than a manual per-server SSH task an engineer has to remember to do, the account would have been locked automatically on day one, with an audit trail proving it.

Key Learnings

Root privilege enforcement via $EUID, strict input validation before privileged commands, idempotent account creation, password policy enforcement with chage, lock-based (reversible) deactivation, and maintaining a dedicated audit trail separate from operational logs.

Common Mistakes to Avoid

Using userdel instead of locking, skipping username validation, forgetting idempotency for repeat runs, mixing audit and operational logs together, and letting a temp password remain valid indefinitely.
