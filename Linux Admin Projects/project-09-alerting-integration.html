Project 09 of 30 · Integration

Alerting Integration

Eight projects of beautifully formatted logs — and not one phone has ever rung. Today, that changes.

🎯 Level: Intermediate–Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + curl + mail ⏱️ Duration: 3 hrs

📖 The Story — Logs Nobody Reads at 3 AM

During a recent overnight incident, the CRITICAL line was sitting right there in the disk monitor's log file the entire time — for six hours — because nobody was watching the log at 2 AM. Our monitoring has been perfect at detecting problems and completely silent about telling anyone.

Priya lays out the ask: "Every project we've built writes gorgeous, detailed logs. None of them wake anybody up. I want one shared alerting system — Slack for anything WARNING or above, email as well for CRITICAL — that any of our nine scripts can plug into. And please, do not let it spam the channel with the same alert every five minutes forever."

Today's project is different from every one before it: we're not monitoring a new thing, we're finally closing the loop on everything we've already built.
🔁 Reinforced from Projects 1–8
Config-driven behavior, epoch-based time math (Project 3, Project 6), timeout-wrapped network calls, and tiered WARNING/CRITICAL classification all come together here.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Convert every WARNING/CRITICAL condition detected by any existing monitoring script into an actual human notification, without duplicate spam.

Customer Requirement

On-call Ops wants Slack for visibility on anything WARNING or worse, and email specifically for CRITICAL issues that need guaranteed, harder-to-miss delivery.

Banking Scenario

NovaTrust's on-call rotation currently has zero automated paging — every incident so far has been caught either by luck, a customer complaint, or someone happening to check a log file.

Existing Manual Process

None — this entire capability is new; logs have existed but nobody actively watches them in real time.

Problems We're Solving Proactively

A perfect detection script that never notifies anyone provides zero actual operational value during the exact hours (nights, weekends) incidents are most likely to go unnoticed.

Business Impact & Risk

The six-hour undetected CRITICAL disk alert is a direct preview of a much larger customer-facing outage that pure logging, with no alerting, will eventually fail to prevent.

Why Automation Is Required

Only an automated dispatcher, wired into every check we run, can guarantee a human is notified the moment a threshold is crossed — regardless of whether anyone happens to be watching a screen.

Solution Design

A generic, reusable alert dispatcher (Slack webhook + email) that any script can call, with alert de-duplication so the same unresolved issue doesn't re-notify every single run within a cooldown window.

Project Scope

In scope: Slack webhook integration, email integration, de-duplication with a cooldown period, and a generic wrapper that adds alerting to any existing script without modifying that script's own code. Out of scope: PagerDuty/on-call scheduling integration (a possible future project).

Expected Outcome

Every one of Projects 1–8, wrapped through this new dispatcher, now actually notifies a human — with WARNING going to Slack, CRITICAL going to both Slack and email, and no alert repeating more than once per cooldown window for the same underlying issue.

🧠 New Bash Concepts for This Project

1. Posting to a Slack Incoming Webhook with curl

What: curl -X POST -H 'Content-type: application/json' --data '{"text":"message"}' "$SLACK_WEBHOOK_URL" sends a message directly into a Slack channel.
Why: A webhook URL is a simple, secret, pre-configured endpoint — no separate authentication token juggling needed for basic notifications.

2. Safely Building a JSON Payload in Bash

What: Manually embedding a variable inside a JSON string ("text":"$MESSAGE") breaks badly if $MESSAGE contains a double-quote or newline — we need a small escaping function.
Why: An alert message often contains exactly the kind of characters (quotes from log lines, newlines from multi-line output) that would corrupt hand-built JSON.
Best practice: Use jq -Rs . to safely JSON-encode arbitrary text when jq is available — it handles every edge case correctly, unlike manual sed-based escaping.

3. Sending Email from Bash (mail / mailx)

What: mail -s "Subject line" recipient@novatrust.com <<< "body text" sends a plain-text email using the system's configured mail transfer agent.
Why: Email remains the most reliable, hard-to-miss channel for genuinely critical alerts, distinct from a Slack channel someone may have muted.
Production note: Requires a working local MTA (like postfix or ssmtp) configured to relay through NovaTrust's actual mail servers — this is an infrastructure prerequisite, not something the script itself sets up.

4. Generating a Stable Alert Fingerprint (md5sum)

What: echo -n "$SOURCE:$MESSAGE" | md5sum | awk '{print $1}' produces a short, consistent hash identifying "this exact alert."
Why: We need a reliable way to recognize "have we already sent this exact alert recently" without storing and comparing full message text every time.

5. Cooldown-Based De-Duplication with Epoch Timestamps (Reinforced)

What: Store each alert fingerprint's last sent epoch timestamp in a small state file; before sending, check whether now - last_sent < cooldown_seconds.
Why: The exact same epoch-math technique from Project 3's leak detection and Project 6's certificate expiry, now applied to suppressing repeat notifications instead of detecting trends.

6. A Generic Wrapper Script Using "$@"

What: "$@" represents all arguments passed to a script, individually quoted — run_with_alerting.sh /path/to/disk_monitor.sh -e prod forwards -e prod straight through to the wrapped script untouched.
Why: This lets one alerting wrapper run any of our nine existing scripts, with any of their own arguments, without modifying a single line of their code.
Common mistake: Using unquoted $@ or $* instead of "$@" — this breaks any argument containing spaces.

7. Capturing Both Output and Exit Code Together

What: OUTPUT=$("$@" 2>&1); EXIT_CODE=$? runs the wrapped script, capturing everything it printed (stdout and stderr combined) plus its exit code, in two clean steps.
Why: The wrapper needs to know both "did it fail" (exit code) and "what did it say" (output, to include in the alert message) — capturing them separately but immediately after each other keeps both accurate.

8. Extracting the Tail of Captured Output for the Alert Body

What: echo "$OUTPUT" | tail -n 10 — reinforced from Project 5, now trimming a wrapped script's full output down to a Slack-message-friendly size.
Why: A full log dump in a Slack message is unreadable; the last several lines (where the actual failure/summary usually is) are what matters most.

9. Escalation Branching on Exit Code (Reinforced case)

What: Mapping our now-familiar 0/1/2 exit code convention directly onto "do nothing / Slack only / Slack + email" — the exact same exit codes every project since Project 1 has already been producing.
Why: This is precisely why we've been disciplined about exit codes (0/1/2) since Project 1 — that consistency is what makes one generic wrapper able to alert for all nine different scripts.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Alerting helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- json_escape ----------
# Purpose: Safely turn arbitrary text into a valid JSON string value (with surrounding quotes)
json_escape() {
    local text="$1"
    if command -v jq >/dev/null 2>&1; then
        printf '%s' "$text" | jq -Rs .                 # -R = raw input, -s = slurp into one JSON string; safest option
    else
        # Fallback: manually escape backslashes, quotes, and newlines - covers the common cases only
        local escaped="${text//\\/\\\\}"                # Escape backslashes first (order matters!)
        escaped="${escaped//\"/\\\"}"                   # Then escape double quotes
        escaped="${escaped//$'\n'/\\n}"                 # Then escape literal newlines
        printf '"%s"' "$escaped"
    fi
}

# ---------- compute_fingerprint ----------
# Purpose: Generate a stable hash identifying "this exact alert" for de-duplication
compute_fingerprint() {
    local source="$1"
    local message="$2"
    echo -n "${source}:${message}" | md5sum | awk '{print $1}'
}

# ---------- is_duplicate_alert ----------
# Purpose: Return 0 (true/duplicate) if this fingerprint was sent within the cooldown window
is_duplicate_alert() {
    local fingerprint="$1"
    [[ -f "$STATE_FILE" ]] || return 1                  # No state file yet -> definitely not a duplicate

    local last_sent
    last_sent=$(grep "^${fingerprint}:" "$STATE_FILE" | tail -n 1 | cut -d':' -f2)
    [[ -z "$last_sent" ]] && return 1                   # Never sent before -> not a duplicate

    local now cooldown_seconds
    now=$(date '+%s')
    cooldown_seconds=$(( COOLDOWN_MINUTES * 60 ))

    (( (now - last_sent) < cooldown_seconds ))          # True (0) if still within the cooldown window
}

# ---------- record_alert_sent ----------
# Purpose: Append this fingerprint's send timestamp to the state file
record_alert_sent() {
    local fingerprint="$1"
    mkdir -p "$(dirname "$STATE_FILE")"
    echo "${fingerprint}:$(date '+%s')" >> "$STATE_FILE"
}

# ---------- send_slack_alert ----------
send_slack_alert() {
    local text="$1"
    local escaped_text
    escaped_text=$(json_escape "$text")
    local payload="{\"text\": ${escaped_text}}"

    timeout "$MAX_TIME" curl -s -o /dev/null -w "%{http_code}" \
        --connect-timeout "$CONNECT_TIMEOUT" \
        -X POST -H 'Content-type: application/json' \
        --data "$payload" "$SLACK_WEBHOOK_URL"
}

# ---------- send_email_alert ----------
send_email_alert() {
    local subject="$1"
    local body="$2"
    mail -s "$subject" -r "$EMAIL_FROM" "$EMAIL_TO" <<< "$body"
}

Line-by-Line Highlights

  • jq -Rs . — -R reads raw (non-JSON) input, -s slurps it into a single string, and . outputs it as one properly-escaped JSON value, quotes included.
  • "${text//\\/\\\\}" — the fallback path escapes backslashes first, deliberately, since escaping quotes or newlines afterward would double-escape the backslashes we just inserted.
  • grep "^${fingerprint}:" "$STATE_FILE" | tail -n 1 — takes the most recent recorded send time for this fingerprint, in case it appears more than once across the file's history.
  • (( (now - last_sent) < cooldown_seconds )) — arithmetic context returns true (exit 0) or false (exit 1) directly, letting this function be used straight inside an if without an extra comparison.
  • mail -s "$subject" -r "$EMAIL_FROM" "$EMAIL_TO" <<< "$body" — the here-string feeds the message body directly to mail's stdin, avoiding a temporary file for a simple plain-text email.

🩺 Alert Dispatcher

scripts/alert_dispatcher.sh
#!/bin/bash
# =====================================================================
# alert_dispatcher.sh
# NovaTrust Bank - Generic Slack/Email Alert Dispatcher with De-Duplication
# Meant to be SOURCED by run_with_alerting.sh, not run standalone.
# =====================================================================

# ---------- dispatch_alert ----------
# Purpose: Central entry point - decides Slack-only vs Slack+Email, and applies de-duplication
# Arguments: $1 = source name (e.g. "disk_monitor"), $2 = level (WARNING/CRITICAL), $3 = message text
dispatch_alert() {
    local source="$1"
    local level="$2"
    local message="$3"

    local fingerprint
    fingerprint=$(compute_fingerprint "$source" "$message")

    if is_duplicate_alert "$fingerprint"; then
        log_message "INFO" "Suppressed duplicate alert from $source (within ${COOLDOWN_MINUTES}m cooldown)"
        return 0
    fi

    local full_text="[$level] $source: $message"

    local slack_http_code
    slack_http_code=$(send_slack_alert "$full_text")
    if [[ "$slack_http_code" == "200" ]]; then
        log_message "INFO" "Slack alert sent for $source ($level)"
    else
        log_message "WARN" "Slack alert FAILED for $source (http_code=${slack_http_code:-none})"
    fi

    if [[ "$level" == "CRITICAL" ]]; then
        if send_email_alert "NovaTrust ALERT [$level]: $source" "$full_text"; then
            log_message "INFO" "Email alert sent for $source (CRITICAL)"
        else
            log_message "WARN" "Email alert FAILED for $source (CRITICAL)"
        fi
    fi

    record_alert_sent "$fingerprint"                    # Record AFTER attempting delivery, win or lose on delivery itself
}
📌 A Deliberate Design Choice
Notice record_alert_sent runs even if Slack/email delivery technically failed. We accept the small risk of a lost single notification over the much worse risk of retrying a broken webhook every single cron cycle and never actually suppressing anything.

🎁 The Generic Wrapper: Alerting for Any Existing Script

scripts/run_with_alerting.sh
#!/bin/bash
# =====================================================================
# run_with_alerting.sh
# NovaTrust Bank - Generic wrapper that adds Slack/Email alerting to ANY script
# Usage: ./run_with_alerting.sh /path/to/some_monitor.sh [args passed through untouched]
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/alerting.conf"
source "$SCRIPT_DIR/alert_dispatcher.sh"

[[ $# -ge 1 ]] || { echo "Usage: $0 /path/to/script.sh [args...]" >&2; exit 1; }

TARGET_SCRIPT="$1"
shift                                                    # Remove the script path, leaving only ITS OWN arguments in "$@"
SOURCE_NAME="$(basename "$TARGET_SCRIPT" .sh)"           # e.g. "disk_monitor" from "disk_monitor.sh"

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/alerting_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another alerting wrapper instance is already running. Exiting."; exit 0; }

log_message "INFO" "Running $SOURCE_NAME via alerting wrapper"

# ---------- Run the wrapped script, capturing BOTH output and exit code ----------
OUTPUT=$("$TARGET_SCRIPT" "$@" 2>&1)
EXIT_CODE=$?

SUMMARY=$(echo "$OUTPUT" | tail -n 10)                   # Last 10 lines - usually the most relevant part for an alert

case "$EXIT_CODE" in
    0)
        log_message "INFO" "$SOURCE_NAME completed healthy - no alert needed"
        ;;
    1)
        log_message "WARN" "$SOURCE_NAME reported WARNING - dispatching alert"
        dispatch_alert "$SOURCE_NAME" "WARNING" "$SUMMARY"
        ;;
    2)
        log_message "FAIL" "$SOURCE_NAME reported CRITICAL - dispatching alert"
        dispatch_alert "$SOURCE_NAME" "CRITICAL" "$SUMMARY"
        ;;
    *)
        log_message "FAIL" "$SOURCE_NAME exited with unexpected code $EXIT_CODE - dispatching alert"
        dispatch_alert "$SOURCE_NAME" "CRITICAL" "Unexpected exit code $EXIT_CODE. Output: $SUMMARY"
        ;;
esac

exit "$EXIT_CODE"                                        # Preserve the original script's exit code for cron/monitoring

Every Line, Explained

LineExplanation
[[ $# -ge 1 ]] || { ...; exit 1; }$# is the count of arguments passed to this wrapper — we require at least the target script's path.
TARGET_SCRIPT="$1"; shiftCaptures the first argument (the script to wrap) and then removes it from the positional parameters, so "$@" afterward contains only that script's own arguments.
OUTPUT=$("$TARGET_SCRIPT" "$@" 2>&1)Runs the target script with its original arguments faithfully forwarded, merging stderr into stdout so nothing the script printed is lost from our capture.
EXIT_CODE=$?Captured on the very next line after the command substitution — this is deliberately the wrapped script's exit code, not anything from the echo or tail commands that come after.
case "$EXIT_CODE" in ... esacThis is the payoff of every project's disciplined 0/1/2 exit-code convention — the wrapper needs zero special-case knowledge of what any individual script actually checks.
exit "$EXIT_CODE"The wrapper itself exits with the same code the wrapped script produced, so cron or any outer monitoring still sees an accurate status.

README.md
# NovaTrust Bank - Alerting Integration

## Usage
    ./scripts/run_with_alerting.sh /path/to/any_monitor.sh [its own args...]

## Escalation Rules
    Exit code 0        -> no alert
    Exit code 1 (WARN) -> Slack only
    Exit code 2 (CRIT) -> Slack + Email
    Any other exit code -> treated as CRITICAL (unexpected failure)

## De-Duplication
The same alert (same source script + same message text) will not be
re-sent more than once per COOLDOWN_MINUTES (default 60).

## Requirements
- A real Slack Incoming Webhook URL in config/alerting.conf (chmod 600 recommended)
- A working local mail transfer agent for email alerts (e.g. postfix, ssmtp)

🔄 What Happens Internally

  1. The wrapper is a genuinely separate script from anything it wraps — this is what lets it be reused across all nine (soon to be more) monitoring projects without touching any of their code.
  2. "$TARGET_SCRIPT" "$@" runs as its own child process, with the wrapper's OUTPUT=$(...) capturing everything that process printed via a pipe/subshell mechanism, exactly like every command substitution we've used since Project 1.
  3. The de-duplication check happens entirely before any network call — a suppressed duplicate costs us zero Slack API calls or email sends, not just a discarded response afterward.
  4. State persists in a flat file using the exact append-only pattern from Project 3's memory-leak state files — proven, simple, and consistent with the rest of the course.

🛡️ Production Best Practices

Never Let Alerting Crash Monitoring

A failed Slack POST or email send should be logged, never allowed to propagate as a fatal error back into the underlying monitoring script's own exit code.

De-Duplicate Before Any Network Call

Checking for a duplicate should happen first, so a suppressed alert costs nothing — not a webhook call whose result is then discarded.

Match Channel to Severity

Reserve email (harder to miss, but slower and easier to ignore in a busy inbox) for genuinely critical conditions; use Slack for the full WARNING+ range.

Build Wrappers, Not Copy-Paste

A generic wrapper that adds a capability to N existing scripts is almost always better than modifying all N scripts individually — easier to maintain, and impossible for any one script to "forget" to alert.

Always Preserve the Original Exit Code

A wrapper must never swallow or change the wrapped script's real exit code — outer tooling (cron, monitoring-of-monitoring) still depends on it being accurate.

Protect Webhook URLs Like Credentials

A leaked Slack webhook URL lets anyone post messages into that channel — treat its config file with the same permission discipline as Project 7's database credentials.

🎤 Interview Preparation

Scenario: A CRITICAL condition persists for eight hours, but the on-call engineer only got notified once, right at the start. Is this a bug?
Not a bug in the de-duplication logic itself — this is the exact expected behavior of a simple cooldown-based dedup with no separate escalation mechanism; it's a legitimate product gap addressed by the "Challenge task" in this project's lab (a longer-interval re-notification for still-unresolved issues).
Production Support: Slack alerts stopped arriving entirely, but the underlying monitoring scripts still show correct exit codes in their own logs. What do you check first?
Check the alerting log for the actual http_code returned by the Slack webhook call — a non-200 response (commonly 404 for a revoked webhook, or 403 for a removed app) would explain silent alert failures while leaving the underlying monitoring completely unaffected.
Shell Scripting: Why capture EXIT_CODE=$? on the very next line after the command substitution, rather than later in the script?
$? always reflects only the immediately preceding command — any command run in between (even something as simple as another variable assignment involving a command) would silently overwrite it with an unrelated exit code.
Troubleshooting: The fallback JSON escaping function produces broken payloads for certain messages. Why might that be, and what's the fix?
The manual sed/parameter-expansion approach only handles a few known special characters (backslash, quote, newline) and can miss others (like tabs or unicode edge cases) that a real JSON encoder would handle correctly — installing and preferring jq -Rs . resolves this class of issue entirely.
Manager Round: Why build one generic alerting wrapper instead of adding Slack calls directly into each of the nine existing scripts?
A shared wrapper means alerting logic (de-dup, escalation rules, credential handling) lives and is maintained in exactly one place; embedding it nine times would mean nine places to update if the Slack API, webhook URL, or escalation policy ever changes.
Architecture: Why does the wrapper preserve and re-exit with the wrapped script's original exit code?
Any outer tooling — cron's own logging, a higher-level "did today's health checks all run successfully" audit, or a future meta-monitoring layer — depends on that exit code being an honest reflection of the underlying check's actual result, not something the alerting layer silently altered.
Best Practice: Why record the alert as "sent" even when Slack or email delivery actually failed?
The alternative — retrying every single cron cycle until delivery finally succeeds — risks the exact spam problem de-duplication exists to prevent, especially if the failure is persistent (like a permanently revoked webhook); this is a deliberate, documented tradeoff favoring quiet degradation over noisy retry storms.
Real Incident Discussion: What's the single most important design decision in this project that would have prevented the six-hour undetected CRITICAL disk alert?
The generic wrapper pattern itself, applied retroactively to Project 2's disk monitor cron entry — the CRITICAL condition would have triggered an immediate Slack notification (and email) the very first time the threshold was crossed, rather than sitting silently in a log file nobody was actively watching.
