Incident Response Orchestration

Twenty-nine projects, each excellent on its own. Tonight, for the first time, they need to work together — automatically, in order, on a single live incident.

🎯 Level: Expert 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL ⏱️ Duration: 4 hrs

📖 The Story — Everything We Built, Working Together

It's 2 AM. Project 8's application health check detects a failing endpoint. Project 9's alerting fires. An engineer, half-awake, opens a terminal and manually runs Project 22's network diagnostic, reads the output, decides it looks like a disk issue, manually runs Project 2's disk monitor, confirms it, manually runs Project 5's log-rotation cleanup, waits, manually re-checks Project 8's health endpoint, confirms recovery, and finally — sometime around 3 AM — manually writes up what happened for the postmortem.

Every single tool involved already existed and worked perfectly. What didn't exist was anything connecting them. Priya's final assignment for this course: "Build the conductor. When something's detected, I want it to automatically diagnose using our existing tools, attempt safe remediation only where we've already decided that's acceptable, validate the fix actually worked, and produce one complete incident timeline and evidence report at the end — calling our existing 29 projects' scripts as building blocks, never rewriting their logic, and never, ever automatically doing anything we've explicitly decided requires a human — DR failover, security remediation, anything genuinely high-risk stays a human decision, always."

This capstone doesn't teach new monitoring techniques. It teaches how everything already built connects — the final, and arguably most important, skill in this entire course.
🔁 Every Prior Project Is a Building Block Here
This orchestrator calls Projects 1, 2, 5, 8, 9, 22, 24, and 25's scripts directly as subroutines, and follows every safety boundary established in Projects 12, 19, 23, and 26 — this is the course's genuine, comprehensive synthesis.

NovaTrust's 29 individual monitoring and remediation tools each work well independently, but incident response has always required a human to manually sequence them together, every single time.

An engineer manually runs each relevant tool in sequence during every incident, interpreting each tool's output by hand before deciding what to run next — slow, inconsistent between different engineers, and entirely dependent on whoever happens to be on call remembering the right sequence.

Well-understood, routine incident patterns (a full disk causing a health check failure, for instance) still require the same manual multi-tool sequencing every single time, even though the correct sequence of steps is already completely known.

Only an orchestrator can consistently, immediately sequence well-understood diagnostic and safe-remediation steps the moment a known pattern is detected — at 2 AM, automatically, exactly as correctly as the most experienced on-call engineer would, every single time.

A state-machine-driven orchestrator script calls existing project scripts in sequence — detect, diagnose, safely remediate where pre-approved, validate the fix, and produce a final timestamped, checksummed incident report — escalating to a human immediately for anything outside its pre-approved, low-risk scope.

Routine, well-understood incidents resolved automatically within minutes, with a complete, evidence-backed timeline — while anything genuinely uncertain or high-risk is still, correctly, escalated straight to a human.

🧠 New Bash Concepts for This Capstone

1. The Orchestrator ("Conductor") Pattern

What: A script whose entire job is calling other, already-built scripts in sequence — via plain command invocation (./other_project/script.sh) — using each one's exit code and output to decide the next action, rather than reimplementing any of their logic itself.
Why: This is the natural culmination of this entire course's consistent exit-code discipline and structured logging — 29 projects' worth of "this script's output is designed to be consumed" finally gets consumed, by this one final integration layer.

2. State Machine Thinking for an Incident Lifecycle

What: A simple STATE variable stepping through named values (DETECTED → DIAGNOSING → REMEDIATING → VALIDATING → RESOLVED or ESCALATED) via a case statement, with each state's logic deciding the next state.
Why: An incident's lifecycle genuinely has distinct phases with different valid next steps — representing this explicitly as a state machine, rather than one long linear script, keeps the logic's structure matching the real-world process it's automating.

3. Passing Structured Data Between Independently-Built Scripts

What: Reading one project's CSV/log output as structured input driving the orchestrator's next decision — e.g., parsing Project 22's diagnosis verdict to decide whether Project 5's log-cleanup remediation applies.
Why: This is exactly why this course insisted on consistent, parseable output formats from the very beginning — Project 1's disciplined SUMMARY: log line convention is what makes this final integration even possible.

4. One Unified Incident Timeline (Reinforced Project 25, New Scope)

What: A single, growing log file recording every stage transition and every underlying script's key result, building one coherent narrative of the entire incident — reinforcing Project 25's aggregation technique, but scoped to one incident's lifecycle rather than one day across all systems.

5. Idempotent Re-Execution (New Reliability Concept)

What: Checking a persisted state file at startup and resuming from the last completed stage, rather than blindly restarting from DETECTED — critically, never re-attempting a remediation action that a state check confirms already succeeded.
Why: An orchestrator coordinating multiple real actions must be safe to re-run if interrupted (a crashed session, a server reboot mid-incident) — repeating an already-successful remediation action unnecessarily could itself cause problems.

6. A Pre-Approved Remediation Whitelist (Reinforced, Strongest Form Yet)

What: A config file explicitly listing the only remediation actions this orchestrator is ever permitted to attempt automatically — anything not on this list results in immediate escalation, never an attempt.
Why: This is the culmination of every "detection vs. remediation" boundary drawn since Project 5 — the orchestrator's automation is explicitly bounded by a whitelist owned through the same change-control process as any other production change, never expanded by the script's own logic.

7. Escalation as a First-Class Outcome

What: ESCALATED is a fully legitimate, successful terminal state for this orchestrator — not a failure mode, but the correct outcome whenever a situation falls outside the pre-approved whitelist or a remediation attempt doesn't resolve the issue.
Why: An orchestrator that always tries to "do something" rather than correctly recognizing when a human is needed would be actively dangerous — explicitly designing escalation as a normal, expected, successful state keeps this boundary honest.

8. The Final Report as Closing the Entire Course's Loop

What: The orchestrator's final output combines Project 25's HTML report-generation technique with Project 27's checksummed evidence-integrity chain — one report that is both genuinely readable and cryptographically verifiable.
Why: This is a deliberate, direct callback: the very last thing this course's very last project produces uses techniques from two of its most recent projects, demonstrating that everything taught here really does compose.

🩺 The Orchestrator Script

scripts/incident_orchestrator.sh
#!/bin/bash
# =====================================================================
# incident_orchestrator.sh
# NovaTrust Bank - Capstone Incident Response Orchestrator
# Coordinates existing project scripts through a full incident lifecycle.
# Only pre-approved, whitelisted remediation is ever attempted automatically.
# =====================================================================

set -uo pipefail
source /home/devops/novatrust-shared-lib/common.sh
install_standard_error_trap

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/../config/orchestrator.conf"

WHITELIST_FILE="$SCRIPT_DIR/../config/remediation_whitelist.txt"

# ---------- Idempotent re-entry: resume an in-progress incident if one exists ----------
if [[ -f "$STATE_FILE" ]]; then
    read -r INCIDENT_ID STATE < "$STATE_FILE"
    echo "Resuming incident $INCIDENT_ID at state $STATE"
else
    INCIDENT_ID="INC-$(date '+%Y%m%d-%H%M%S')"
    STATE="DETECTED"
fi

INCIDENT_DIR="$SCRIPT_DIR/$INCIDENTS_DIR/$INCIDENT_ID"
mkdir -p "$INCIDENT_DIR"
TIMELINE="$INCIDENT_DIR/timeline.log"
LOG_FILE="$TIMELINE"                                # Reuse common.sh's log_message for the timeline itself

record_state() {
    STATE="$1"
    echo "$INCIDENT_ID $STATE" > "$STATE_FILE"
    log_message "STATE" "=== Incident $INCIDENT_ID -> $STATE ==="
}

# ---------- DETECTED: confirm the failure is real via Project 8's own health check ----------
if [[ "$STATE" == "DETECTED" ]]; then
    if bash "$SCRIPT_DIR/$HEALTH_CHECK_SCRIPT"; then
        log_message "INFO" "Health check now passing - no incident to act on. Exiting."
        rm -f "$STATE_FILE"
        exit 0
    fi
    record_state "DIAGNOSING"
fi

# ---------- DIAGNOSING: use Project 22's diagnostic tool against the affected host ----------
DIAGNOSIS=""
if [[ "$STATE" == "DIAGNOSING" ]]; then
    DIAGNOSIS_OUTPUT=$(bash "$SCRIPT_DIR/$NETWORK_DIAGNOSE_SCRIPT" "$TARGET_HOST" "$TARGET_PORT")
    DIAGNOSIS=$(echo "$DIAGNOSIS_OUTPUT" | grep -A1 "DIAGNOSIS" | tail -n 1)
    log_message "INFO" "Diagnosis result: $DIAGNOSIS"

    REMEDIATION_SCRIPT=""
    while IFS=':' read -r pattern script; do
        [[ -z "$pattern" || "$pattern" == \#* ]] && continue
        if echo "$DIAGNOSIS" | grep -qE "$pattern"; then
            REMEDIATION_SCRIPT=$(echo "$script" | xargs)
            break
        fi
    done < "$WHITELIST_FILE"

    if [[ -z "$REMEDIATION_SCRIPT" ]]; then
        record_state "ESCALATED"
        log_message "CRITICAL" "Diagnosis '$DIAGNOSIS' does not match any pre-approved remediation. Escalating to on-call human."
        exit 2
    fi
    echo "$REMEDIATION_SCRIPT" > "$INCIDENT_DIR/selected_remediation.txt"
    record_state "REMEDIATING"
fi

# ---------- REMEDIATING: run ONLY the specific whitelisted script matched above ----------
if [[ "$STATE" == "REMEDIATING" ]]; then
    REMEDIATION_SCRIPT=$(cat "$INCIDENT_DIR/selected_remediation.txt" 2>/dev/null)
    log_message "INFO" "Executing pre-approved remediation: $REMEDIATION_SCRIPT"
    bash "$SCRIPT_DIR/$REMEDIATION_SCRIPT" || log_message "WARN" "Remediation script reported a non-zero exit - proceeding to validate anyway."
    record_state "VALIDATING"
fi

# ---------- VALIDATING: re-run Project 8's health check to confirm actual recovery ----------
if [[ "$STATE" == "VALIDATING" ]]; then
    if bash "$SCRIPT_DIR/$HEALTH_CHECK_SCRIPT"; then
        record_state "RESOLVED"
    else
        record_state "ESCALATED"
        log_message "CRITICAL" "Remediation did not resolve the issue. Escalating to on-call human."
    fi
fi

# ---------- Final report: Project 25's HTML technique + Project 27's checksum technique ----------
REPORT_FILE="$INCIDENT_DIR/incident_report.html"
cat < "$REPORT_FILE"




Incident Report: ${INCIDENT_ID}


Final State: ${STATE}


$(cat "$TIMELINE")



EOF
sha256sum "$REPORT_FILE" > "${REPORT_FILE}.sha256"

log_message "INFO" "Incident $INCIDENT_ID complete. Final state: $STATE. Report: $REPORT_FILE"
[[ "$STATE" == "RESOLVED" ]] && rm -f "$STATE_FILE"     # Clear in-progress marker only on true resolution
exit 0

Every Stage, Explained

StageWhat Happens
Idempotent re-entryReading $STATE_FILE at startup means re-running this script after an interruption resumes exactly where it left off, rather than restarting the whole incident (and potentially re-running an already-successful remediation) from scratch.
DETECTEDDirectly invokes Project 8's actual health-check script — the orchestrator never reimplements health-checking logic, it calls the real, already-trusted tool.
DIAGNOSINGDirectly invokes Project 22's diagnostic tool, then checks its DIAGNOSIS line against the whitelist — this is the single decision point governing every remediation this script will ever attempt.
REMEDIATINGExecutes only the specific script matched during diagnosis — no other remediation script, whitelisted or not, is ever reachable from this code path.
VALIDATINGRe-runs Project 8's health check as independent proof the remediation genuinely worked — never simply trusting the remediation script's own exit code as sufficient evidence of resolution.
Final reportCombines Project 25's heredoc HTML technique with Project 27's sha256sum integrity technique — this capstone's very last lines directly reuse two of the course's most recent projects' own patterns.

README.md
# NovaTrust Bank - Incident Response Orchestrator (Capstone)

## Usage
    ./scripts/incident_orchestrator.sh
Safe to re-run at any time - resumes an in-progress incident from its last
recorded state rather than restarting from scratch.

## What This Script Does NOT Do
It never attempts any remediation action not explicitly listed in
config/remediation_whitelist.txt. Anything outside that list is escalated
to a human, every time, without exception.

## The Whitelist Is Not Owned By This Script
config/remediation_whitelist.txt is reviewed and approved through the same
change-control process as any other production change to NovaTrust systems.

## Output
    incidents/INC-/timeline.log           - full incident narrative
    incidents/INC-/incident_report.html    - final report
    incidents/INC-/incident_report.html.sha256 - integrity proof

🔄 What Happens Internally

  1. Every single external action this orchestrator takes is a call to an already-built, already-trusted script from an earlier project — this script contains essentially no monitoring or remediation logic of its own; its entire value is in the sequencing and the safety gate.
  2. The whitelist check is the one and only gate between diagnosis and any real action — structurally, there is no code path from an unmatched diagnosis to a remediation attempt, mirroring the hard boundaries built in Projects 23 and 26.
  3. The state file's persistence is what makes re-running this script after an interruption safe — without it, a second run would restart the entire incident from DETECTED, potentially re-triggering an already-successful remediation unnecessarily.
  4. The final report generation always runs, regardless of whether the incident resolved or escalated — every incident, successfully automated or not, gets the same complete, checksummed documentation.

🛡️ Production Best Practices

Orchestrate, Never Reimplement

Call existing, already-trusted scripts as building blocks rather than duplicating their logic — this is the entire value and risk-reduction case for an orchestration layer.

Make Escalation a First-Class, Successful Outcome

An orchestrator correctly recognizing "this needs a human" is a success, not a failure — never design a system that always tries to "do something" regardless of confidence.

Whitelist Remediation, Never Infer It

The set of automatically-actionable situations should be an explicit, change-controlled list — never something the orchestrator's own logic decides is "probably fine" to attempt.

Design for Safe Re-Entry From the Start

Any orchestrator coordinating real, potentially-impactful actions must be safe to re-run after an interruption — persisted state is what makes this possible.

Independently Validate, Never Trust a Remediation's Own Success Claim

Re-running the original detection check after remediation is the only genuine proof the underlying issue is actually resolved.

Document Every Incident the Same Way, Resolved or Escalated

A consistent, complete, checksummed report for every incident — regardless of outcome — builds the evidence base for future postmortems and process improvement.

🎤 Interview Preparation

Scenario: The orchestrator successfully auto-remediates an incident, but a human reviewing the incident report afterward disagrees that the remediation was actually the right fix. What does this reveal?
This reveals a gap in the remediation whitelist's design, not a failure of the orchestrator's execution — the whitelist itself, being a change-controlled artifact, should be revisited and refined based on this feedback; this is exactly why the whitelist is owned through the same review process as any other production change, rather than being something the orchestrator can silently expand on its own.
Production Support: The orchestrator escalates an incident, but the on-call engineer says the diagnosis clearly matches a pattern that should be on the whitelist. What's the most likely gap?
Either the whitelist genuinely doesn't yet cover this specific pattern (a legitimate gap to raise through change control) or the regex pattern in the whitelist file doesn't precisely match the exact wording Project 22's diagnostic tool actually produces — worth testing the specific diagnosis text against the whitelist pattern directly before assuming which explanation applies.
Shell Scripting: Why does the orchestrator use a case-like sequence of if [[ "$STATE" == "..." ]] blocks instead of an actual case statement for its state machine?
Each stage in this specific implementation needs to potentially fall through into the next stage within the same run (e.g., DETECTED transitioning immediately into DIAGNOSING without requiring a separate script invocation) — sequential if blocks checking and updating the same STATE variable naturally support this fall-through behavior, whereas a traditional case statement's branches are typically mutually exclusive within one evaluation.
Troubleshooting: After a genuine server crash mid-incident, re-running the orchestrator repeats an already-successful remediation action. What's the likely bug?
The state file write in record_state likely isn't being flushed/persisted reliably before the remediation action itself runs, or the remediation stage isn't properly recording its own completion before starting the actual remediation command — the state transition to VALIDATING should be recorded immediately upon successfully launching remediation, not only after it completes, to avoid exactly this double-execution risk on a crash mid-remediation.
Manager Round: Why build this orchestrator as the very last project in the course, rather than earlier, to save engineers time sooner?
This orchestrator's entire value depends on having genuinely reliable, well-tested, consistently-structured building blocks to call — attempting this integration before the 29 underlying tools existed and were proven would have meant building on an unstable foundation; the course's sequencing deliberately ensures orchestration is the capstone, not a premature shortcut.
Architecture: Why does this orchestrator call other projects' scripts as separate subprocesses (via bash script.sh) rather than sourcing their functions directly into one combined script?
Keeping each project as an independently-invokable script preserves their independent testability, ownership, and ability to be run standalone outside the orchestrator's context (exactly as they have been throughout this entire course); sourcing everything into one giant combined script would create tight coupling between 29 previously-independent codebases, making any one of them harder to safely modify without risking the others.
Best Practice: Why does the final incident report generate identically regardless of whether the incident ended RESOLVED or ESCALATED?
A consistent reporting format regardless of outcome ensures every incident - successfully automated or not - contributes equally to the organization's incident history and postmortem process; if only resolved incidents were documented this thoroughly, the record would be systematically biased toward success stories, hiding exactly the escalated cases most valuable for identifying gaps in the remediation whitelist.
Real Incident Discussion: What's the single most direct design decision in this capstone that would have saved the most time during that original 2 AM manual incident?
Automatically chaining Project 8's detection directly into Project 22's diagnosis the moment a failure is confirmed, with no human needing to manually decide "which diagnostic tool should I run next" — the exact sequence of decisions the half-awake engineer manually worked through, tool by tool, over the better part of an hour, would instead begin executing automatically within seconds of the original health-check failure being detected.
