Application Health Check

Every server was green. The database was healthy. And the NEFT API was still returning HTTP 500 to every single customer for twenty minutes.

🎯 Level: Intermediate 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + curl ⏱️ Duration: 2–3 hrs

📖 The Story — "Infrastructure Says Everything's Fine"

During a deployment last week, a configuration typo broke the NEFT Gateway's connection pool. The server was running. CPU, memory, and disk were all calm. The database was healthy and replicating on time. Every single check from Projects 1–7 would have reported a perfectly clean bill of health — while every real customer transaction hitting /api/neft/transfer received an HTTP 500 error for twenty straight minutes.

In the retro, Priya says it plainly: "We've been checking if the house is standing. We've never once checked if the front door actually opens. I want a script that calls our real API endpoints — the way a customer's request would — and checks not just that something answered, but that it answered correctly."

Today, for the first time, we stop checking servers and start checking the application itself, exactly the way a real user would experience it.
🔁 Reinforced from Projects 1–7
Timeout discipline, tiered classification, config-driven endpoint lists, and the consolidated report pattern all continue — now applied to HTTP instead of SSH, SQL, or TLS.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Verify that customer-facing APIs and web endpoints are not just reachable, but returning correct HTTP status codes and valid response content, within an acceptable response time.

Customer Requirement

Ops wants to know within minutes if any customer-facing service starts returning errors — not from a customer complaint, but from a proactive synthetic check.

Banking Scenario

NovaTrust exposes REST APIs for NEFT transfers, balance inquiries, and a general /health endpoint used by each application itself to report its own internal status.

Existing Manual Process

None — application-level correctness was previously inferred entirely from infrastructure health, which the incident proved is an unsafe assumption.

Problems With Infrastructure-Only Monitoring

A server can be perfectly healthy while the application running on it is completely broken — a bad config, a bad deployment, or an exhausted connection pool are all invisible to CPU/memory/disk checks.

Business Impact & Risk

Twenty minutes of failed NEFT transfers, undetected by any existing monitoring, represents both direct customer harm and a real regulatory reporting obligation once discovered after the fact.

Why Automation Is Required

Only a synthetic transaction — an automated script making the same kind of call a real customer's request makes — can verify true end-to-end application correctness on a continuous basis.

Solution Design

For each configured endpoint, send an HTTP request with strict timeouts, capture the status code and response time in one call, validate the response body contains the expected content, and retry transient failures before alerting.

Project Scope

In scope: HTTP status code validation, response-time thresholds, response-body content validation, and retry-with-backoff for transient failures. Out of scope: full end-to-end multi-step transaction simulation (a more advanced future project).

Expected Outcome

A report per endpoint showing HTTP status, response time, and content validation result — catching the exact "server's fine, application's broken" scenario that infrastructure checks alone cannot see.

🧠 New Bash Concepts for This Project

1. Multi-Field Capture with curl -w

What: curl -s -o /tmp/body -w "%{http_code} %{time_total}" URL captures the status code AND response time in one single request.
Why: Making two separate requests to measure two different things would double our load on the endpoint and risk inconsistent results between the two calls.
-o /tmp/body: saves the response body to a file so we can separately validate its content, while -w's output goes to stdout, captured by our script.
-s (silent): suppresses curl's own progress meter, which would otherwise pollute our captured output.

2. curl's Exit Code vs. the HTTP Status Code

What: curl itself exits 0 ("I successfully made an HTTP request") even when the server responds with a 404 or 500 — those are still valid HTTP responses as far as curl is concerned.
Why this matters: We must check the captured status code value separately from curl's own exit code — conflating them would mean a 500 error looks identical to a total success from curl's perspective.
When curl's exit code IS what to check: connection refused, DNS failure, or timeout — genuine inability to complete the HTTP exchange at all.

3. Dual Timeouts: --connect-timeout and --max-time

What: --connect-timeout 5 limits how long establishing the connection may take; --max-time 10 limits the entire request (connection + response) end-to-end.
Why: A connection can succeed quickly but then hang waiting for a slow response body — we need both guards, not just one.

4. Validating Response Body Content (grep -q)

What: grep -q '"status":"UP"' /tmp/body silently checks whether the expected marker text exists in the response, returning a true/false exit code without printing anything.
Why: An endpoint can return HTTP 200 with a completely empty, truncated, or wrong-content body — status code alone is not proof of a correct response.
Best practice: Where available, prefer jq for real JSON field validation over grep pattern matching on raw text, since grep can't distinguish structure from coincidental text matches.

5. Parsing JSON Properly with jq

What: jq -r '.status' /tmp/body extracts the actual value of a JSON field, structurally, rather than just searching for matching text.
Why: grep would happily "match" a status field with an unrelated part of a larger response; jq actually parses the JSON, so it retrieves precisely the field we mean.
Best practice: Always check command -v jq and provide a grep-based fallback for hosts where jq isn't installed.

6. The Retry-With-Backoff Pattern

What: A loop that retries a failed check a configurable number of times, pausing between attempts, before finally declaring failure.
Why: A single dropped packet or momentary blip shouldn't page an engineer at 3 AM — but a check that's still failing after several retries genuinely should.
Production example: for attempt in $(seq 1 "$MAX_RETRIES"); do check_endpoint && break; sleep "$RETRY_DELAY"; done

7. seq for Generating a Range

What: seq 1 3 prints 1, 2, 3 on separate lines — a simple way to drive a fixed-count retry loop.
Alternative: A C-style for (( i=1; i<=3; i++ )) loop works too; seq is often more readable for a simple fixed count.

8. Response-Time Thresholds as a Separate Signal From Correctness

What: An endpoint can return the exact right status and body, just slowly — classified as SLOW, distinctly from FAIL.
Why: A slow-but-correct response is an early warning sign (perhaps a database query getting gradually slower) worth surfacing well before it becomes an outright failure.

9. Comparing Decimal Response Times

What: time_total from curl is a decimal (e.g. 1.847) — comparing it against a threshold needs the same bc-based approach from Project 3's memory-delta math, not native Bash integer arithmetic.

🧩 Utility Functions (Extended)

scripts/utils.sh (additions)
# ---------- call_endpoint ----------
# Purpose: Make ONE HTTP request capturing status code + response time; save body to a temp file
# Arguments: $1 = URL
# Sets global variables: HTTP_STATUS, RESPONSE_TIME, BODY_FILE (deliberately simple for teaching purposes)
call_endpoint() {
    local url="$1"
    BODY_FILE=$(mktemp)                                  # A fresh temp file per call, cleaned up by the caller

    # -s silent, -o save body to file, -w print exactly the two values we need, space-separated
    local result
    result=$(curl -s -o "$BODY_FILE" \
        --connect-timeout "$CONNECT_TIMEOUT" \
        --max-time "$MAX_TIME" \
        -w "%{http_code} %{time_total}" \
        "$url" 2>/dev/null)
    local curl_exit=$?

    if [[ $curl_exit -ne 0 ]]; then
        HTTP_STATUS=""                                   # Empty signals "couldn't even complete the request"
        RESPONSE_TIME=""
        return 1
    fi

    read -r HTTP_STATUS RESPONSE_TIME <<< "$result"       # Split curl's -w output into the two variables
    return 0
}

# ---------- body_contains_marker ----------
# Purpose: Check whether the response body contains an expected marker string
body_contains_marker() {
    local body_file="$1"
    local marker="$2"
    grep -qF -- "$marker" "$body_file"                    # -F = fixed string, not regex; -- guards against a marker starting with a dash
}

# ---------- is_response_slow ----------
# Purpose: Return 0 (true) if response time is at/above the SLOW threshold, using bc for decimal comparison
is_response_slow() {
    local response_time="$1"
    (( $(echo "$response_time >= $SLOW_RESPONSE_SECONDS" | bc -l) ))
}

Line-by-Line Highlights

  • BODY_FILE=$(mktemp) — creates a uniquely named temporary file safely, avoiding any risk of two concurrent runs colliding on the same filename.
  • -w "%{http_code} %{time_total}" — curl's write-out format string; both values come from the exact same single request, guaranteeing they describe the same call.
  • if [[ $curl_exit -ne 0 ]]; then ...; fi — this checks curl's own exit code, catching connection-level failures (DNS, refused, timeout) distinctly from a valid-but-wrong HTTP status, which is handled separately by the caller.
  • grep -qF -- "$marker" — -F treats the marker as a literal string rather than a regular expression, avoiding surprises if the marker text happens to contain regex special characters like . or *.
  • bc -l — the -l flag loads bc's math library, needed for reliable decimal comparisons like the one here.

🩺 Main Script

scripts/app_health_check.sh
#!/bin/bash
# =====================================================================
# app_health_check.sh
# NovaTrust Bank - Synthetic Application/API Health Check
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/app_health_check.conf"

ENDPOINT_FILE="$SCRIPT_DIR/../config/endpoints.txt"
[[ -f "$ENDPOINT_FILE" ]] || { echo "ERROR: Endpoint file not found: $ENDPOINT_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/app_health_check_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Application health check run finished."' EXIT

log_message "INFO" "=== Starting application health check ==="

OVERALL_EXIT=0
HEALTHY=0; SLOW=0; FAILED=0

while IFS=':' read -r url expected_status expected_marker; do
    [[ -z "$url" || "$url" == \#* ]] && continue

    ATTEMPT=1
    SUCCESS="false"

    # ---------- Retry-with-backoff loop ----------
    while [[ "$ATTEMPT" -le "$MAX_RETRIES" ]]; do
        call_endpoint "$url"

        if [[ -n "$HTTP_STATUS" ]] && [[ "$HTTP_STATUS" == "$expected_status" ]] && body_contains_marker "$BODY_FILE" "$expected_marker"; then
            SUCCESS="true"
            rm -f "$BODY_FILE"
            break                                        # Success - stop retrying immediately
        fi

        rm -f "$BODY_FILE"
        log_message "WARN" "$url: attempt $ATTEMPT/$MAX_RETRIES failed (status=${HTTP_STATUS:-none})"
        ((ATTEMPT++))
        [[ "$ATTEMPT" -le "$MAX_RETRIES" ]] && sleep "$RETRY_DELAY"
    done

    # ---------- Final classification after all retries ----------
    if [[ "$SUCCESS" != "true" ]]; then
        log_message "FAIL" "$url: failed after $MAX_RETRIES attempts (last status=${HTTP_STATUS:-none})"
        ((FAILED++))
        OVERALL_EXIT=2
        continue
    fi

    if is_response_slow "$RESPONSE_TIME"; then
        log_message "SLOW" "$url: OK but slow (${RESPONSE_TIME}s, threshold ${SLOW_RESPONSE_SECONDS}s)"
        ((SLOW++))
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    else
        log_message "PASS" "$url: OK (${RESPONSE_TIME}s)"
        ((HEALTHY++))
    fi

done < "$ENDPOINT_FILE"

log_message "INFO" "=== SUMMARY ==="
log_message "INFO" "Healthy: $HEALTHY | Slow: $SLOW | Failed: $FAILED"

exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
while IFS=':' read -r url expected_status expected_markerSplits each config line into exactly three fields on the colon delimiter — note this assumes the marker itself never contains a colon, a deliberate simplification worth flagging as a real-world limitation.
if [[ -n "$HTTP_STATUS" ]] && [[ "$HTTP_STATUS" == "$expected_status" ]] && body_contains_marker ...All three conditions must hold for success: the request completed at all, the status matches, AND the body contains the expected marker — any single one failing means retry.
break inside the retry loopStops retrying the moment a success is achieved — there's no reason to burn additional attempts once the endpoint has already proven healthy.
[[ "$ATTEMPT" -le "$MAX_RETRIES" ]] && sleep "$RETRY_DELAY"Only sleeps if another attempt is actually coming — avoids an unnecessary final delay after the last attempt has already failed.
is_response_slow "$RESPONSE_TIME"Only evaluated after a successful status+body check — a genuinely failed endpoint is reported as FAIL, never as SLOW, since slowness is only a meaningful signal on an otherwise-correct response.

📄 README.md

README.md
# NovaTrust Bank - Application Health Check

## Usage
    ./scripts/app_health_check.sh

## What Counts as Healthy
A response only counts as healthy if ALL of the following are true:
1. The HTTP request completes within the configured timeouts.
2. The status code matches the expected value exactly.
3. The response body contains the expected marker text.
A correct-but-slow response is reported as SLOW, not FAIL.

## Exit Codes
    0 = All endpoints healthy
    1 = At least one endpoint SLOW
    2 = At least one endpoint FAILED after all retries

🔄 What Happens Internally

  1. One curl invocation per attempt captures status, timing, and body together — this atomicity is what makes the SLOW-vs-FAIL distinction trustworthy (both numbers describe the exact same request).
  2. The retry loop is nested inside the per-endpoint loop, so retries for one troubled endpoint never delay or affect the checks for other endpoints in the list.
  3. Temp files are created and removed on every single attempt, not just at the end — this prevents dozens of stale temp files from accumulating across retries and across cron runs.
  4. bc -l spawns a genuinely separate process for the decimal comparison in is_response_slow, exactly like Project 3's memory-delta calculation — this remains the correct tool anytime decimal precision matters in Bash.

🛡️ Production Best Practices

Status Code Is Not Enough

Always validate response body content too — a 200 with a broken or empty body is still a broken endpoint.

Never Conflate curl's Exit Code with HTTP Status

curl succeeding just means it completed the HTTP exchange — the actual status code is a completely separate thing to check.

Retry Before Alerting, But Not Forever

A bounded retry count with a short delay filters out transient blips without masking a genuine, sustained outage.

Separate Slow from Broken

A correct-but-slow response is an early warning signal, not a failure — conflating the two either causes alert fatigue or hides a real trend.

Always Clean Up Temp Files

Every mktemp'd file must be removed on every code path, including failure paths — not just the success path.

Prefer Structural JSON Parsing

jq validates actual JSON structure and values; grep only proves the text happened to appear somewhere in the response.

🎤 Interview Preparation

Scenario: An endpoint returns HTTP 200 and passes our body-marker check, but customers still report broken transactions. What's the likely gap?
The marker check may only be validating a shallow, always-present field (like a generic "status":"UP" on a health endpoint) rather than actually exercising the specific business logic that's broken — a true synthetic transaction test would need to call the actual transfer endpoint with real (test) data, not just a lightweight health-check route.
Production Support: The script reports FAIL, but manually curling the same URL right now works fine. What happened?
Most likely a transient issue that self-resolved between the automated check and your manual retest — check the log for exactly which of the MAX_RETRIES attempts failed and whether the failures were consistent or intermittent, which tells you whether this was a blip or matches a recurring pattern.
Shell Scripting: Why capture status code and response time in one curl call instead of two separate calls?
Two separate requests could hit different backend instances behind a load balancer, experience different network conditions, or even get different responses if application state changed between calls — one call guarantees both numbers describe the exact same request-response cycle.
Troubleshooting: The retry loop appears to run only once even though MAX_RETRIES is set to 3. What's a likely cause?
Check whether the success condition is being met on the very first attempt (in which case one run is correct), or whether the ATTEMPT counter isn't incrementing due to a logic error — also verify MAX_RETRIES is actually being sourced correctly from the config file.
Manager Round: How do you decide the SLOW_RESPONSE_SECONDS threshold isn't arbitrary?
Base it on the actual expected user experience and any existing SLA (e.g., "transfers should confirm within 2 seconds"), then validate against real historical response-time data rather than picking a number that merely feels reasonable.
Architecture: Why does this project check application-level endpoints in addition to everything Projects 1-7 already cover?
Infrastructure health (server, CPU, memory, disk, database) is necessary but not sufficient for correctness — a fully healthy stack can still serve a broken application due to configuration, deployment, or code-level issues invisible at the infrastructure layer, which is exactly what this incident demonstrated.
Best Practice: Why use grep -F instead of plain grep for the marker check?
-F treats the search string as a literal, not a regular expression — without it, a marker containing characters like ., *, or [ would be silently misinterpreted as regex syntax rather than matched literally, potentially causing false positives or negatives.
Real Incident Discussion: What's the one design principle from this project that most directly would have caught the 20-minute NEFT outage?
Treating "HTTP status correct" and "response body correct" as two independent, both-required conditions — the broken connection pool almost certainly still returned some HTTP response, and only a body-content check (not status code alone) reliably catches an application returning the wrong data while technically "responding."
