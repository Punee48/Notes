Multi-Server Disk Space Monitoring

Scaling yesterday's single-server check across all 200 Core Banking servers from one jump box, over SSH, with a consolidated report.

🎯 Level: Beginner–Intermediate 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL + SSH ⏱️ Duration: 2–3 hrs

📖 The Story — Scaling Up

We show Priya our finished single-server health check from yesterday. She's impressed, then says: "Good — now here's the real problem. We don't have one Core Banking server, we have 200, spread across two data centers. I don't want you SSHing into each one by hand and copy-pasting the script. Build this to run from a single jump box, loop through every hostname in our inventory, and give me one consolidated report — which servers are healthy, which are in warning, which have failed, and which didn't even respond."

She adds one more thing: "Last quarter, a server was decommissioned but nobody removed it from the monitoring list — the script hung for ten minutes waiting on a dead connection. Make sure that can never happen again."

Today we go from "check one machine" to "check a fleet," the way real infrastructure monitoring is built.

Config-driven thresholds, log_message(), exit codes, and the config/utils/main-script folder layout all carry forward unchanged — we're extending the same framework, not rebuilding it.

Business Requirement

Monitor disk space across the entire Core Banking server fleet from a single control point, with one consolidated daily report.

Customer Requirement

Operations wants a single glance — not 200 separate logins — to know exactly which servers need attention today.

Banking Scenario

NovaTrust's Core Banking estate spans 200 Linux servers across a primary and DR (Disaster Recovery) data center, reachable from one hardened jump box.

Problems with Manual Process

Unreachable/decommissioned servers cause long hangs; there's no single view of fleet-wide health; results aren't comparable across servers checked at different times.

Why Automation Is Required

A jump-box script reads a host inventory file, SSHes into each server with a hard timeout, runs the disk check remotely, and aggregates every result into one report and one log file.

Project Scope

In scope: disk space across multiple mount points, on multiple servers, via SSH, with unreachable-host detection and a lock file to prevent overlapping runs. Out of scope: email/Slack alerting (Project 9).

Expected Outcome

One command, ./disk_monitor.sh -e prod, that checks every server in the prod host list and prints/logs a single table: hostname, mount point, usage %, and status.

🧠 New Bash Concepts for This Project

1. Reading a File Into a Loop (while read)

What: while IFS= read -r line; do ... done < file.txt reads a file one line at a time.
Why: Our 200 hostnames live in a plain text file, one per line — this is how we turn each line into a loop iteration.
Internal working: read returns exit status 1 (false, ending the loop) when it hits end-of-file.
Best practice: Always set IFS= (empty) and use -r so lines with leading/trailing spaces or backslashes aren't mangled.
Common mistake: Piping into the while loop (cat file | while read...) — this runs the loop in a subshell, so variables set inside it vanish afterward. Use input redirection (< file) instead.

2. SSH From a Script (Non-Interactive)

What: ssh -o BatchMode=yes -o ConnectTimeout=5 user@host 'command' runs a command on a remote server without a password prompt or an open-ended hang.
Why: Our jump box needs to run the Project 1 style disk check remotely, on all 200 servers, without ever getting stuck waiting for a password or a dead connection.
BatchMode=yes: disables any interactive password prompt — if key-based auth fails, SSH fails immediately instead of hanging.
ConnectTimeout=5: caps how long SSH will wait to establish the connection itself.
Production example: This exact pattern is how Ansible-style tooling works under the hood before you ever install Ansible.

3. SSH Exit Codes

What: SSH returns 255 specifically when it cannot connect at all (DNS failure, timeout, refused connection) — as opposed to the remote command's own exit code, which SSH also passes through.
Why: We must tell "server unreachable" (255) apart from "server reachable but disk check failed" (the remote script's own exit code) — these need very different responses from Ops.
Best practice: Always check for 255 explicitly and label those hosts UNREACHABLE rather than lumping them in with CRITICAL.

4. Associative Arrays (declare -A)

What: An array indexed by string keys instead of numbers, e.g. declare -A RESULTS; RESULTS["server01"]="WARN".
Why: We need to remember each server's status by its hostname to build the final report table.
Common mistake: Forgetting declare -A before first use — Bash silently treats it as a regular indexed array instead, and string keys stop working correctly.

5. getopts in Practice

What: Bash's built-in flag parser. while getopts "e:h" opt; do case $opt in e) ENV=$OPTARG;; esac; done
Why: Ops needs to run the same script against prod or uat host lists without editing the script — -e prod vs -e uat.
Internal working: the colon after a letter (e:) tells getopts that flag requires a value, stored automatically in $OPTARG.

6. File Locking with flock

What: flock ensures only one instance of a script can run at a time, using a lock file as a mutex.
Why: If a run takes longer than expected (a slow server) and cron fires again before it finishes, we'd get two overlapping runs writing to the same log and report — flock prevents that.
Production example: flock -n /tmp/disk_monitor.lock ./disk_monitor.sh — -n makes it fail fast instead of queueing, so we know immediately if a previous run is still in progress.

7. printf for Aligned Reports

What: Unlike echo, printf supports column-width formatting, e.g. printf "%-20s %-10s %s\n" "$host" "$status" "$detail".
Why: A report of 200 rows is only useful if the columns actually line up — this is how real ops tooling renders readable tables.

8. Timeouts for Any Command (timeout)

What: The timeout command force-kills anything that runs longer than a given duration, e.g. timeout 10 ssh ....
Why: Belt-and-suspenders alongside SSH's own ConnectTimeout — protects against a remote command itself hanging even after the connection succeeds.

🧩 Utility Functions (Extended)

We extend Project 1's utils.sh with remote-check functions. log_message() is unchanged and reused as-is.

scripts/utils.sh (additions)
# ---------- check_host_reachable ----------
# Purpose: Return 0 if a host answers SSH within the configured timeout, 1 otherwise
# Arguments: $1 = hostname
check_host_reachable() {
    local host="$1"
    # -q = quiet, BatchMode=yes = never prompt for a password, ConnectTimeout = hard cap on connection attempt
    ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" "$SSH_USER@$host" exit
    return $?                                   # 0 = reachable, 255 = unreachable
}

# ---------- get_remote_disk_usage ----------
# Purpose: Run df -h for a given mount point on a remote host and return the usage %
# Arguments: $1 = hostname, $2 = mount point
get_remote_disk_usage() {
    local host="$1"
    local mount="$2"
    # timeout wraps the whole ssh call as a second safety net beyond ConnectTimeout
    timeout "$SSH_COMMAND_TIMEOUT" ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "$SSH_USER@$host" "df -h '$mount' | awk 'NR==2{print \$5}' | tr -d '%'"
}

# ---------- classify_usage ----------
# Purpose: Turn a raw percentage into a HEALTHY/WARNING/CRITICAL label
# Arguments: $1 = usage percentage (integer)
classify_usage() {
    local pct="$1"
    if [[ "$pct" -ge "$DISK_FAIL_THRESHOLD" ]]; then
        echo "CRITICAL"
    elif [[ "$pct" -ge "$DISK_WARN_THRESHOLD" ]]; then
        echo "WARNING"
    else
        echo "HEALTHY"
    fi
}

Line-by-Line Highlights

  • ssh -q -o BatchMode=yes ... exit — we don't need to run a real command just to test reachability; exit closes the remote session immediately after connecting, which is the cheapest possible reachability probe.
  • timeout "$SSH_COMMAND_TIMEOUT" ssh ... — wrapping ssh in timeout guards against the rare case where the connection succeeds but the remote command itself never returns.
  • The remote command string uses escaped \$5 — because it's inside a double-quoted string being sent to the remote shell, we must escape $ so awk on the remote host sees it, not our local shell.
  • classify_usage() returns a string via echo, which the caller captures with $( ) — this is the standard way Bash functions "return" non-numeric values.

🩺 Main Script

scripts/disk_monitor.sh
#!/bin/bash
# =====================================================================
# disk_monitor.sh
# NovaTrust Bank - Multi-Server Disk Space Monitor (runs from jump box)
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"                      # log_message, check_host_reachable, etc.

ENVIRONMENT="prod"                                 # Default environment if -e isn't passed

# ---------------- Argument Parsing ----------------
while getopts "e:h" opt; do                        # 'e:' expects a value, 'h' does not
    case $opt in
        e) ENVIRONMENT="$OPTARG" ;;                # -e prod  or  -e uat
        h) echo "Usage: $0 -e [prod|uat]"; exit 0 ;;
        *) echo "Invalid option. Usage: $0 -e [prod|uat]"; exit 1 ;;
    esac
done

source "$SCRIPT_DIR/../config/disk_monitor.conf"
HOST_FILE="$SCRIPT_DIR/../config/servers_${ENVIRONMENT}.txt"

if [[ ! -f "$HOST_FILE" ]]; then                   # Fail fast and clearly if the environment name is wrong
    echo "ERROR: Host file not found for environment '$ENVIRONMENT': $HOST_FILE" >&2
    exit 1
fi

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/disk_monitor_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

# ---------------- Prevent Overlapping Runs ----------------
exec 200>"$LOCK_FILE"                              # Open file descriptor 200 pointed at the lock file
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
# -n = non-blocking; if the lock is held, we exit immediately rather than queueing up

trap 'log_message "INFO" "Disk monitor run finished for environment: $ENVIRONMENT"' EXIT

log_message "INFO" "=== Starting disk monitor for environment: $ENVIRONMENT ==="

declare -A HOST_STATUS                             # hostname -> worst status found on that host
HEALTHY_COUNT=0; WARNING_COUNT=0; CRITICAL_COUNT=0; UNREACHABLE_COUNT=0
OVERALL_EXIT=0

# ---------------- Main Loop Over Hosts ----------------
while IFS= read -r host; do
    [[ -z "$host" || "$host" == \#* ]] && continue    # Skip blank lines and comment lines

    if ! check_host_reachable "$host"; then
        log_message "FAIL" "$host is UNREACHABLE"
        HOST_STATUS["$host"]="UNREACHABLE"
        ((UNREACHABLE_COUNT++))
        OVERALL_EXIT=2
        continue                                       # No point checking disk on a dead host
    fi

    WORST="HEALTHY"                                    # Tracks the worst mount-point status for this host
    for mount in "${MOUNT_POINTS[@]}"; do
        USAGE=$(get_remote_disk_usage "$host" "$mount")
        if [[ -z "$USAGE" ]]; then
            log_message "WARN" "$host:$mount returned no data (remote command may have failed)"
            continue
        fi
        STATUS=$(classify_usage "$USAGE")
        printf "[%s] %-40s %-10s %s%%\n" "$STATUS" "$host" "$mount" "$USAGE" | tee -a "$LOG_FILE"

        # Escalate WORST only upward: HEALTHY -> WARNING -> CRITICAL, never downward
        if [[ "$STATUS" == "CRITICAL" ]]; then
            WORST="CRITICAL"
        elif [[ "$STATUS" == "WARNING" && "$WORST" != "CRITICAL" ]]; then
            WORST="WARNING"
        fi
    done

    HOST_STATUS["$host"]="$WORST"
    case "$WORST" in
        HEALTHY)  ((HEALTHY_COUNT++)) ;;
        WARNING)  ((WARNING_COUNT++)); [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1 ;;
        CRITICAL) ((CRITICAL_COUNT++)); OVERALL_EXIT=2 ;;
    esac

done < "$HOST_FILE"                                    # Redirect the file straight into the while loop (no subshell!)

# ---------------- Consolidated Report ----------------
log_message "INFO" "=== SUMMARY for $ENVIRONMENT ==="
log_message "INFO" "Healthy: $HEALTHY_COUNT | Warning: $WARNING_COUNT | Critical: $CRITICAL_COUNT | Unreachable: $UNREACHABLE_COUNT"

exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
while getopts "e:h" optParses command-line flags; the colon after e means -e requires a value, captured into $OPTARG.
exec 200>"$LOCK_FILE"Opens (or creates) the lock file and assigns it to file descriptor 200 — an arbitrary but conventionally high number to avoid clashing with 0/1/2 (stdin/stdout/stderr).
flock -n 200 || { ... exit 0; }Tries to get an exclusive lock on FD 200 without waiting (-n); if another run already holds it, we log and exit cleanly instead of hanging or double-running.
[[ -z "$host" || "$host" == \#* ]] && continueSkips empty lines and comment lines (starting with #) in the inventory file — continue jumps to the next loop iteration.
((UNREACHABLE_COUNT++))Arithmetic evaluation context — increments an integer variable; this syntax is specific to Bash (not plain sh).
done < "$HOST_FILE"Feeds the file directly into the loop's stdin, so the loop runs in the current shell — meaning all our counters actually persist after the loop ends (unlike piping via cat file |).

🔄 What Happens Internally

  1. Lock acquisition: exec 200>file opens a file descriptor that stays open for the life of the script; flock attaches an advisory lock to it that the OS releases automatically when the script exits, even on a crash.
  2. Argument parsing happens once, up front, before any config is loaded, so the correct environment's host file can be chosen.
  3. Per-host subshell for SSH: each ssh call spawns a genuinely separate remote shell on the target server; anything that script does there (like running awk) happens in that machine's process space, not ours.
  4. Loop state persists because we redirect the file into the loop (done < file) rather than piping — this was a deliberate fix versus a naive first draft that piped through cat.
  5. Exit code aggregation: OVERALL_EXIT only ever escalates (0→1→2), matching the same "never downgrade a failure" rule from Project 1.

🛡️ Production Best Practices

Concurrency Control

Any script that might run longer than its own cron interval needs a lock file — this is non-negotiable at fleet scale.

Timeouts Everywhere

Every remote call needs both a connection timeout and a command timeout — never trust a remote system to always respond.

Fail Loud on Bad Input

An invalid -e environment value should stop the script immediately with a clear message, not silently check zero hosts.

Separate Reachability from Health

UNREACHABLE and CRITICAL mean very different things to Ops — never merge these categories.

Least Privilege

The SSH service account should only have read access needed for health checks — never a privileged or root account.

Idempotency

Running the script twice back-to-back (after the lock releases) should produce the same kind of report — no side effects that accumulate incorrectly.

🎤 Interview Preparation

Scenario: One server always shows UNREACHABLE, but you can SSH into it manually just fine. Why might a script report it as unreachable?
Most likely the manual SSH is using an interactive password or agent-forwarded key that the script's non-interactive BatchMode=yes call can't use — the service account's key may not be in that host's authorized_keys.
Production Support: Cron shows the job ran, but no report was produced. What do you check?
Check whether flock silently skipped the run because a previous instance was still holding the lock — look at the log's WARN line and check if the previous run is genuinely still active or crashed and left a stale lock.
Shell Scripting: Why does cat file | while read line lose variables set inside the loop, and how do you fix it?
The pipe creates a subshell for the while loop, so any variables it sets die when that subshell exits; redirecting the file directly (done < file) keeps the loop in the current shell.
Troubleshooting: SSH from the script hangs for a long time even with ConnectTimeout set. Why?
ConnectTimeout only limits the initial TCP/SSH handshake — a remote command that itself hangs (e.g., waiting on a lock) isn't covered by it, which is exactly why we additionally wrap the call in the external timeout command.
Manager Round: How do you justify a 30-minute check interval instead of checking continuously?
Frequent enough to catch a disk filling up before it becomes an outage, but not so frequent that 200 SSH connections every few minutes create their own load and audit-log noise — a balance decision, tunable via config.
Architecture: Why run this from a single jump box instead of each server monitoring itself and pushing results somewhere?
Centralizing the pull avoids installing and maintaining monitoring logic on 200 servers, and gives a single point of control/audit; the trade-off is the jump box becomes a single point of failure for monitoring, which should be documented as a known risk.
Best Practice: Why classify status per-mount-point and then roll up to a per-host "worst" status?
A single host can have one healthy and one critical mount point — reporting only a host-level average would hide the critical one; rolling up to "worst wins" ensures nothing critical is diluted away.
Real Incident Discussion: A decommissioned server hung the manual process for ten minutes. What two separate fixes did this project introduce to prevent a repeat?
An explicit ConnectTimeout/timeout on every SSH call, and treating SSH exit code 255 as its own UNREACHABLE category rather than retrying indefinitely.
