Kubernetes Node Health Check

One node quietly went NotReady. The scheduler rerouted around it so smoothly that nobody noticed — until three more nodes failed the same week and pods had nowhere left to go.

🎯 Level: Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + kubectl ⏱️ Duration: 3 hrs

📖 The Story — The Scheduler Was Too Good at Its Job

A worker node in NovaTrust's Kubernetes cluster developed a failing disk and quietly transitioned to NotReady, with a DiskPressure condition. Kubernetes' scheduler did exactly what it's designed to do: it stopped placing new pods there and let existing workloads get rescheduled elsewhere, completely automatically. From the outside, nothing looked wrong — services kept responding normally. Three weeks later, two more nodes developed similar issues in the same week, and suddenly there wasn't enough remaining cluster capacity to reschedule everything — pods started going Pending, unable to be placed anywhere, and a real service outage followed.

Priya's framing: "Kubernetes is built to self-heal around a bad node, and that's usually exactly what we want — but it also means a failing node can hide in plain sight for weeks with nobody noticing, right up until we run out of capacity to keep hiding it. I want node conditions checked directly, I want Pending pods tracked as an early warning sign, and I want a simple cluster-capacity percentage so we know how much headroom we actually have left."

This project takes everything we've learned about composite health signals and state tracking, and applies it at the level of an entire cluster rather than a single server or container.
🔁 Reinforced from Projects 1–17
jq JSON parsing (Project 17), compliance-percentage math (Project 13), and per-item restart-count tracking (Project 17's pattern, now applied to pods) all return here at cluster scale.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Detect failing Kubernetes nodes and early signs of cluster capacity exhaustion before self-healing behavior masks the problem long enough to cause a real outage.

Customer Requirement

Ops needs direct visibility into node conditions and pod scheduling health — signals the cluster's own self-healing deliberately hides from a surface-level view.

Banking Scenario

NovaTrust runs a subset of newer microservices (including the fraud-scoring service from Project 17) on a Kubernetes cluster spanning multiple worker nodes.

Existing Manual Process / Prior Automation Gap

None of Projects 1-17 monitor at the cluster-orchestration level — Kubernetes' own self-healing had, until now, been the only thing "watching" node health, silently.

Problems With Relying on Self-Healing Alone

Kubernetes rescheduling around a bad node is a resilience feature, but it also removes the natural, visible symptom (a service actually going down) that would otherwise have prompted investigation — the underlying problem can persist and compound for weeks.

Business Impact & Risk

Multiple silently-degraded nodes accumulating until remaining capacity is exhausted converts several individually-minor hardware issues into one sudden, large-scale service outage.

Why Automation Is Required

Only continuous, automated querying of node conditions and pod scheduling status can surface a self-healing-masked problem while it's still small, isolated, and easy to address.

Solution Design

Query all node conditions via kubectl, calculate a Ready-node percentage as a simple cluster-capacity headroom indicator, track Pending pods as an early unschedulability warning, and monitor pod restart counts cluster-wide using the same delta-detection pattern from Project 17.

Project Scope

In scope: node condition monitoring, Ready-node percentage, Pending-pod detection, and pod restart-count trend tracking. Out of scope: automated node draining/remediation or cluster autoscaling configuration — deliberately detection-only, consistent with this course's monitoring focus throughout.

Expected Outcome

A cluster health report showing exactly which nodes have concerning conditions, the overall Ready-node percentage, any Pending pods, and pod restart trends — catching the first failing node, not just the eventual capacity crisis.

🧠 New Bash Concepts for This Project

1. Querying Kubernetes Objects as JSON (kubectl get -o json)

What: kubectl get nodes -o json returns full node objects as structured JSON, ideal for jq processing — the Kubernetes equivalent of Project 17's docker inspect.
Why: Kubernetes' default table output is meant for humans reading a terminal; JSON output is what a script should always use for reliable parsing.

2. Node Conditions Array

What: Each node object contains .status.conditions[], an array of condition objects like {"type": "Ready", "status": "True"}, {"type": "DiskPressure", "status": "False"}, etc.
Why: A node's true health is fully described by this array — a node can technically be Ready: True while also reporting DiskPressure: True, both of which matter independently.

3. Filtering a JSON Array by Field with jq

What: jq -r '.status.conditions[] | select(.type=="Ready") | .status' — select() filters array elements matching a condition, then extracts a specific field from the match.
Why: This is how we pull out exactly the one condition type we care about from an array that may contain five or more different condition entries per node.

4. JSONPath as a kubectl-Native Alternative to jq

What: kubectl get nodes -o jsonpath='{.items[*].metadata.name}' extracts specific fields directly, using Kubernetes' own built-in query syntax, without needing a separate jq call.
Why: For simple field extractions, native jsonpath avoids an external dependency; for more complex filtering (like the select() above), jq piped from full JSON output is often clearer — knowing both tools means picking the simpler one for each specific task.

5. Detecting Cordoned/Unschedulable Nodes

What: jq -r '.spec.unschedulable // false' — a node manually cordoned (kubectl cordon) or auto-cordoned has this field set to true.
Why: An unschedulable node reduces effective cluster capacity just as much as a genuinely unhealthy one, and should be counted the same way in a capacity-headroom calculation.

6. Field Selectors for Filtering (--field-selector)

What: kubectl get pods --all-namespaces --field-selector=status.phase=Pending -o json filters server-side, returning only pods currently stuck in the Pending phase.
Why: Filtering on the server side (rather than requesting every pod and filtering locally) is both more efficient and simpler script logic — reinforcing the general principle from Project 2 of doing filtering as early as possible in a pipeline.

7. Cluster-Wide Ready-Node Percentage (Reinforced Project 13 Pattern)

What: READY_PCT=$(( READY_COUNT * 100 / TOTAL_COUNT )) — the exact multiply-before-divide pattern from Project 13's compliance percentage, now describing cluster capacity headroom instead of patch compliance.

8. Pod Restart Tracking at Cluster Scale (Reinforced Project 17 Pattern)

What: .status.containerStatuses[].restartCount per pod, compared against a persisted previous value — identical delta-detection logic to Project 17's container restart tracking, just sourced from kubectl instead of docker inspect.
Why: The exact same underlying problem (a crash-looping workload hidden by automatic restarts) exists at the pod level in Kubernetes as it did for standalone Docker containers — the detection technique transfers directly.

9. Recent Cluster Events (kubectl get events)

What: kubectl get events --field-selector type=Warning --sort-by='.lastTimestamp' surfaces recent scheduling failures, image pull errors, and other warning-level cluster events.
Why: Events often explain why a pod is Pending (e.g., "Insufficient memory") — valuable context alongside the raw Pending-pod count.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Kubernetes health check helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_node_condition ----------
# Purpose: Return the status ("True"/"False"/"Unknown") of a specific condition type for one node's JSON object
get_node_condition() {
    local node_json="$1"
    local condition_type="$2"
    echo "$node_json" | jq -r --arg type "$condition_type" \
        '.status.conditions[] | select(.type==$type) | .status'
}

# ---------- is_node_unschedulable ----------
is_node_unschedulable() {
    local node_json="$1"
    [[ "$(echo "$node_json" | jq -r '.spec.unschedulable // false')" == "true" ]]
}

# ---------- get_pending_pods ----------
# Purpose: Return "namespace/podname" for every currently Pending pod, cluster-wide
get_pending_pods() {
    kubectl get pods --all-namespaces --field-selector=status.phase=Pending \
        -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}' 2>/dev/null
}

# ---------- get_all_pod_restart_counts ----------
# Purpose: Return "namespace/podname:restartCount" for every pod, summing restarts across its containers
get_all_pod_restart_counts() {
    kubectl get pods --all-namespaces -o json 2>/dev/null | jq -r '
        .items[] |
        "\(.metadata.namespace)/\(.metadata.name):\([.status.containerStatuses[]?.restartCount // 0] | add // 0)"
    '
}

# ---------- get_previous_pod_restart_count ----------
get_previous_pod_restart_count() {
    local pod_key="$1"
    [[ -f "$STATE_FILE" ]] || { echo ""; return; }
    grep "^${pod_key}:" "$STATE_FILE" | tail -n 1 | cut -d':' -f2
}

# ---------- record_pod_restart_count ----------
record_pod_restart_count() {
    local pod_key="$1"
    local count="$2"
    mkdir -p "$(dirname "$STATE_FILE")"
    echo "${pod_key}:${count}" >> "$STATE_FILE"
}

Line-by-Line Highlights

  • jq -r --arg type "$condition_type" '... select(.type==$type) ...' — --arg safely passes a Bash variable into a jq filter as a named variable ($type), avoiding the risks of trying to interpolate shell variables directly into a jq program string.
  • kubectl get pods ... -o jsonpath='{range .items[*]}...{end}' — jsonpath's range/end syntax loops over each item in an array, letting us format one clean output line per pod directly from kubectl itself, without piping to jq at all.
  • [.status.containerStatuses[]?.restartCount // 0] | add // 0 — the ? after [] suppresses an error if a pod has no container statuses yet (e.g., still initializing); wrapping in [...] collects all containers' restart counts into an array, and add sums them, since a single pod can have multiple containers each with their own independent restart count.
  • get_previous_pod_restart_count and record_pod_restart_count are structurally identical to Project 17's container-restart state functions — proof that the same pattern generalizes cleanly from "one Docker host" to "an entire Kubernetes cluster."

🩺 Main Script

scripts/k8s_node_health.sh
#!/bin/bash
# =====================================================================
# k8s_node_health.sh
# NovaTrust Bank - Kubernetes Node Condition & Cluster Capacity Monitor
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/k8s_health.conf"

export KUBECONFIG="$KUBECONFIG_PATH"
STATE_FILE="$SCRIPT_DIR/$STATE_FILE"

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/k8s_health_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Kubernetes health check run finished."' EXIT

log_message "INFO" "=== Starting Kubernetes cluster health check ==="

OVERALL_EXIT=0

# ---------- Node condition checks ----------
NODES_JSON=$(kubectl get nodes -o json 2>/dev/null)
if [[ -z "$NODES_JSON" ]]; then
    log_message "FAIL" "Could not query cluster nodes - is kubectl configured correctly?"
    exit 2
fi

TOTAL_NODES=0
READY_NODES=0

mapfile -t NODE_NAMES < <(echo "$NODES_JSON" | jq -r '.items[].metadata.name')

for node_name in "${NODE_NAMES[@]}"; do
    ((TOTAL_NODES++))
    NODE_JSON=$(echo "$NODES_JSON" | jq -r --arg name "$node_name" '.items[] | select(.metadata.name==$name)')

    if is_node_unschedulable "$NODE_JSON"; then
        log_message "WARN" "$node_name: cordoned/unschedulable"
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
        continue                                        # Doesn't count toward Ready, and skip further condition checks
    fi

    READY_STATUS=$(get_node_condition "$NODE_JSON" "Ready")
    if [[ "$READY_STATUS" != "True" ]]; then
        log_message "FAIL" "$node_name: NOT READY (status: ${READY_STATUS:-unknown})"
        OVERALL_EXIT=2
        continue
    fi

    ((READY_NODES++))

    for pressure_type in "MemoryPressure" "DiskPressure" "PIDPressure"; do
        PRESSURE_STATUS=$(get_node_condition "$NODE_JSON" "$pressure_type")
        if [[ "$PRESSURE_STATUS" == "True" ]]; then
            log_message "WARN" "$node_name: $pressure_type detected"
            [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
        fi
    done

    log_message "PASS" "$node_name: Ready, no pressure conditions"
done

READY_PCT=$(( READY_NODES * 100 / TOTAL_NODES ))
if [[ "$READY_PCT" -le "$READY_NODE_CRITICAL_PCT" ]]; then
    log_message "FAIL" "Cluster capacity CRITICAL: ${READY_PCT}% nodes Ready ($READY_NODES/$TOTAL_NODES)"
    OVERALL_EXIT=2
elif [[ "$READY_PCT" -le "$READY_NODE_WARN_PCT" ]]; then
    log_message "WARN" "Cluster capacity WARNING: ${READY_PCT}% nodes Ready ($READY_NODES/$TOTAL_NODES)"
    [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
else
    log_message "PASS" "Cluster capacity healthy: ${READY_PCT}% nodes Ready ($READY_NODES/$TOTAL_NODES)"
fi

# ---------- Pending pod check ----------
PENDING_PODS=$(get_pending_pods)
PENDING_COUNT=$(echo "$PENDING_PODS" | grep -c . || true)

if [[ "$PENDING_COUNT" -ge "$PENDING_POD_CRITICAL_COUNT" ]]; then
    log_message "FAIL" "CRITICAL: $PENDING_COUNT pods Pending cluster-wide (possible capacity exhaustion)"
    OVERALL_EXIT=2
elif [[ "$PENDING_COUNT" -ge "$PENDING_POD_WARN_COUNT" ]]; then
    log_message "WARN" "$PENDING_COUNT pod(s) Pending: $(echo "$PENDING_PODS" | tr '\n' ' ')"
    [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
else
    log_message "PASS" "No Pending pods"
fi

# ---------- Pod restart-count trend (reinforced Project 17 pattern) ----------
while IFS=: read -r pod_key restart_count; do
    [[ -z "$pod_key" ]] && continue
    previous=$(get_previous_pod_restart_count "$pod_key")

    if [[ -n "$previous" && "$restart_count" -gt "$previous" ]]; then
        delta=$(( restart_count - previous ))
        log_message "WARN" "$pod_key: $delta new restart(s) since last check (total: $restart_count)"
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    fi

    record_pod_restart_count "$pod_key" "$restart_count"
done < <(get_all_pod_restart_counts)

log_message "INFO" "=== Kubernetes cluster health check complete ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
mapfile -t NODE_NAMES < <(echo "$NODES_JSON" | jq -r '.items[].metadata.name')Extracts just the node names into an array first, then re-queries the full JSON per node inside the loop — this keeps each iteration's jq filter simple and focused on one node object at a time.
is_node_unschedulable ... continueA cordoned node is deliberately excluded from the Ready count entirely (via continue, skipping the increment) — it's neither counted as contributing capacity nor double-flagged with a separate NotReady error, since cordoning is usually an intentional, known state.
READY_PCT=$(( READY_NODES * 100 / TOTAL_NODES ))Same multiply-before-divide pattern as Project 13 and Project 15, now describing cluster-wide node capacity.
PENDING_COUNT=$(echo "$PENDING_PODS" | grep -c . || true)grep -c . counts non-empty lines; the trailing || true prevents set -uo pipefail from treating grep's "no matches" exit code (1) as a script-ending error when there are legitimately zero Pending pods.
done < <(get_all_pod_restart_counts)Process substitution keeps the restart-tracking loop in the current shell (not a subshell), so OVERALL_EXIT correctly persists — the same technique used for Project 12's comm-based loops.

📄 README.md

README.md
# NovaTrust Bank - Kubernetes Node Health Check

## Requirements
- kubectl configured with read access to the target cluster
- jq installed

## Usage
    ./scripts/k8s_node_health.sh

## What Gets Checked
1. Every node's Ready condition and pressure conditions (Memory/Disk/PID)
2. Cluster-wide Ready-node percentage
3. Cluster-wide Pending pod count
4. Pod restart-count DELTA since last check (same pattern as Project 17's container monitoring)

## Exit Codes
    0 = Cluster healthy, no Pending pods, no new pod restarts
    1 = Cordoned node, resource pressure, elevated Pending pods, or new pod restarts
    2 = A node is NotReady, cluster capacity critical, or Pending pods at critical count

🔄 What Happens Internally

  1. Node conditions, Pending pods, and restart counts are three separate kubectl queries, each answering a genuinely different question about cluster health, mirroring Project 14's multi-signal approach at a much larger scale.
  2. Cordoned nodes are deliberately excluded from the Ready tally rather than counted as failures — an intentional operational state (someone draining a node for maintenance) is different from an unexpected failure, and the report reflects that distinction.
  3. Pod restart tracking reuses Project 17's exact state-file pattern, proving the underlying technique (persist a value, compare against next check, record the new value) transfers cleanly from single-host Docker to cluster-wide Kubernetes with no conceptual changes.
  4. jsonpath's range/end and jq's select()/--arg are used side by side in this same script — a deliberate demonstration that picking the right tool for each specific extraction (rather than dogmatically using only one) produces clearer code.

🛡️ Production Best Practices

Don't Let Self-Healing Hide Problems From You

A resilient system that automatically routes around failures still needs its individual failure points monitored directly — resilience isn't the same as "nothing is wrong."

Distinguish Intentional State from Failure

A cordoned node (a deliberate operational action) and a NotReady node (an unexpected failure) both reduce capacity but mean very different things — report them distinctly.

Pending Pods Are an Early Capacity Signal

Catching the first Pending pod is far more useful than waiting until dozens of pods can't be scheduled — treat even a single Pending pod as worth surfacing.

Filter Server-Side Where Possible

--field-selector reduces data transfer and script complexity compared to pulling everything and filtering locally — push filtering as early in the pipeline as the tool allows.

Reuse Proven Patterns Across Domains

Project 17's restart-delta tracking pattern transferred to Kubernetes pods with almost no conceptual change — recognize and reuse working patterns rather than reinventing them per technology.

Use --arg for Safe jq Variable Passing

Passing shell variables into jq filters via --arg avoids the injection and quoting risks of directly interpolating variables into a jq program string.

🎤 Interview Preparation

Scenario: The Ready-node percentage is 100%, yet several pods are stuck Pending. What does this combination suggest?
All nodes report technically healthy (Ready), but there's likely insufficient allocatable resources (CPU/memory) on any single node to satisfy the Pending pods' resource requests — a capacity-sizing problem rather than a node-health problem, best confirmed by checking kubectl describe pod or recent scheduling-failure events for the specific reason.
Production Support: A node shows Ready: True but also DiskPressure: True. Should this be treated as healthy or unhealthy?
Neither purely — this project deliberately reports it as a WARNING precisely because it's a mixed, degraded-but-still-technically-Ready state; DiskPressure often precedes a future NotReady transition, making it valuable early-warning information distinct from a clean pass/fail.
Shell Scripting: Why use jq's --arg instead of directly embedding a Bash variable into the jq filter string with double quotes?
Direct string interpolation risks both syntax breakage (if the variable contains a quote or special jq character) and, in more complex scripts, injection-style bugs; --arg name "$value" passes the value safely as a proper jq variable regardless of its contents.
Troubleshooting: Pod restart-delta tracking never detects a restart you know happened. What Kubernetes-specific behavior might explain this?
If the pod belongs to a Deployment/ReplicaSet, a crashing pod might be entirely replaced with a brand-new pod (a different name) rather than the same pod object incrementing its own restart count — the state file's name-based key would then simply see a "new" pod with 0 restarts rather than a detected increase on a known one.
Manager Round: Why does a cordoned node get excluded from the Ready-percentage calculation instead of counting against it as a failure?
Cordoning is typically a deliberate, known, and often temporary operational action (planned maintenance, a controlled drain) rather than an unplanned failure; folding it into the same "capacity problem" signal as a genuine NotReady node would create false alarms during routine, expected maintenance windows.
Architecture: Why check node conditions directly via kubectl instead of just trusting that services will alert us if something's actually broken?
This is precisely the point of the original incident — Kubernetes' self-healing can keep services running correctly for weeks while individual nodes silently degrade, meaning "services are fine" provides zero visibility into accumulating risk until capacity is suddenly exhausted.
Best Practice: Why calculate Ready-node percentage as a tiered metric rather than just alerting on any single NotReady node?
A tiered percentage captures the cumulative risk of multiple isolated issues compounding — one NotReady node in a 50-node cluster is very different from one NotReady node in a 3-node cluster, and the percentage view makes that proportional risk directly visible in a way a raw count alone wouldn't.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the original silently-failing node before capacity was exhausted?
Directly checking each node's Ready and pressure conditions on a continuous schedule — the very first node's transition to NotReady/DiskPressure would have generated an immediate, specific alert naming that node, rather than remaining invisible behind successful automatic rescheduling for three weeks until multiple failures compounded into an actual outage.
