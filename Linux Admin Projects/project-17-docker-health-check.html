Project 17 of 30 · Containers

Docker Health Check

docker ps said "running" the entire time. It just failed to mention the container had silently crashed and restarted 40 times that morning.

🎯 Level: Advanced 🧠 New Concepts: 9 🏗️ Environment: Linux / WSL + Docker ⏱️ Duration: 3 hrs

📖 The Story — "Running" Doesn't Mean "Not Crashing"

NovaTrust's new containerized fraud-scoring microservice had a memory leak that caused it to hit its container memory limit every few minutes. Docker's restart policy dutifully relaunched it every single time — which meant docker ps always showed it as Up, because at any given instant, it usually was. What that single-word status never revealed was that the container had been OOM-killed and restarted 40 times that morning, dropping every in-flight fraud check each time it died.

Priya's framing: "A container that's 'running' right now and a container that's been crash-looping all morning look identical if all you check is its current state. I want restart counts tracked over time, I want us specifically checking for OOM kills, and I want Docker's own HEALTHCHECK status factored in — not just whether the container object currently exists and is up."

Every check in this course so far has assumed a process running directly on a server. Containers add an entirely new layer: the container can restart itself, invisibly, without ever technically going "down" from the outside.
🔁 Reinforced from Projects 1–16
State-file comparison for detecting change over time (Project 3), jq JSON parsing (Projects 8 & 14), and tiered classification all return here, applied to Docker's own inspection data.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Detect containers that are crash-looping, OOM-killed, or reporting unhealthy via Docker's own HEALTHCHECK — conditions invisible to a simple "is it running" check.

Customer Requirement

Ops needs to know when a container is restarting repeatedly, not just whether it happens to be up at the moment of the check.

Banking Scenario

NovaTrust runs newer microservices, including fraud-scoring, in Docker containers alongside its traditional server-based Core Banking applications.

Existing Manual Process / Prior Automation Gap

None of Projects 1-16 account for container-specific lifecycle behavior — a restarting container looks identical to a stable one under a naive "is the process up" check, since the restart happens automatically and quickly.

Problems With "Is It Running" Alone

Docker's restart policies are specifically designed to make failures invisible from the outside by immediately relaunching a failed container — exactly the behavior that hid this incident for hours.

Business Impact & Risk

Every fraud-check request in flight during each of the 40 restarts that morning was silently dropped, directly undermining fraud detection coverage during the affected windows.

Why Automation Is Required

Only a script tracking restart count change over time (not just a snapshot) and explicitly checking for OOM-kill events can distinguish a genuinely stable container from a crash-looping one that happens to be up at the exact moment of inspection.

Solution Design

Query each monitored container's state via docker inspect, compare its restart count against the previous check (persisted state, reinforcing Project 3's pattern) to detect new restarts since last check, explicitly check for OOM-kill events, and factor in Docker's own HEALTHCHECK status where defined.

Project Scope

In scope: restart-count trend detection, OOM-kill detection, HEALTHCHECK status integration, and recent-log capture on a detected crash. Out of scope: container orchestration-level remediation (restart policy tuning, auto-scaling) — a separate concern from detection.

Expected Outcome

A report distinguishing genuinely stable containers from ones that have restarted recently, specifically flagging OOM-kill events and unhealthy HEALTHCHECK statuses, with relevant recent log lines captured automatically for any newly-detected crash.

🧠 New Bash Concepts for This Project

1. docker inspect and Its JSON Output

What: docker inspect <container> returns a detailed JSON array (one element) describing everything Docker knows about a container's current and recent state.
Why: This is the single source of truth for restart count, OOM status, health status, and much more — far richer than docker ps's one-line summary.

2. Extracting Fields with jq from docker inspect (Reinforced)

What: docker inspect "$container" | jq -r '.[0].RestartCount' — note the .[0], since docker inspect always returns a JSON array, even when inspecting just one container.
Why: Forgetting the array index is a very common first mistake when scripting against docker inspect output.

3. Detecting OOM Kills (.State.OOMKilled)

What: jq -r '.[0].State.OOMKilled' returns literal true/false, reflecting whether the container's most recent termination was specifically due to hitting its memory limit.
Why: This is the single most direct, unambiguous signal distinguishing "crashed because of a memory limit" from any other kind of container exit.

4. Reading Docker's Own HEALTHCHECK Status (.State.Health.Status)

What: If a container's image defines a HEALTHCHECK instruction, Docker itself continuously runs it and exposes the result as starting, healthy, or unhealthy.
Why: This is Docker's own built-in application-level health signal (conceptually similar to Project 8's HTTP health checks) — when available, it's valuable free signal our script should incorporate rather than duplicate.
Common mistake: Assuming every container has a HEALTHCHECK defined — this field is simply absent (null) for containers without one, which must be handled gracefully, not treated as an error.

5. Detecting NEW Restarts via State Comparison (Reinforced Project 3 Pattern)

What: Persisting each container's restart count to a state file after every check, then comparing today's count against the previous recorded value — the exact same "read previous, compare, record new" pattern from Project 3's memory-leak trend detection.
Why: RestartCount is cumulative since the container was created — a raw snapshot (e.g., "47 restarts") means nothing about whether it's currently stable or actively still crash-looping; only the delta since the last check reveals that.

6. Capturing Recent Container Logs (docker logs --tail)

What: docker logs --tail 20 "$container" retrieves just the most recent lines of a container's stdout/stderr output — reinforcing Project 5's tail familiarity in a new context.
Why: The moments just before a crash are the most diagnostically valuable — automatically capturing them the moment a new restart is detected saves an engineer from having to dig through potentially-rotated logs later.

7. Filtering Containers by Name Pattern (docker ps --filter)

What: docker ps --filter "name=novatrust-" --format '{{.Names}}' lists only containers whose name matches a pattern, using Docker's own Go-template output formatting.
Why: A host may run containers unrelated to NovaTrust's own services (sidecar/infrastructure containers) — filtering ensures monitoring targets exactly the intended set.

8. Reading Configured Memory Limits (.HostConfig.Memory)

What: jq -r '.[0].HostConfig.Memory' returns the container's configured memory limit in bytes (or 0 for unlimited).
Why: Knowing the configured limit alongside an OOM-kill event helps contextualize the finding — a container OOM-killed against a suspiciously small limit points toward a capacity/configuration fix, not necessarily an application bug.

9. Combining Docker-Native Signals Into One Composite Verdict (Reinforced)

What: New restarts, OOM status, and HEALTHCHECK status all feed into one "worst signal wins" composite verdict per container — the same philosophy applied consistently since Project 7.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Docker health check helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_monitored_containers ----------
get_monitored_containers() {
    docker ps --filter "name=${CONTAINER_NAME_FILTER}" --format '{{.Names}}'
}

# ---------- inspect_container ----------
# Purpose: Return the full docker inspect JSON for one container (element [0] already unwrapped)
inspect_container() {
    local container="$1"
    docker inspect "$container" 2>/dev/null | jq -r '.[0]'
}

# ---------- get_restart_count ----------
get_restart_count() {
    local inspect_json="$1"
    echo "$inspect_json" | jq -r '.RestartCount // 0'
}

# ---------- is_oom_killed ----------
is_oom_killed() {
    local inspect_json="$1"
    [[ "$(echo "$inspect_json" | jq -r '.State.OOMKilled // false')" == "true" ]]
}

# ---------- get_health_status ----------
# Purpose: Return healthy/unhealthy/starting/none - "none" if the container has no HEALTHCHECK defined
get_health_status() {
    local inspect_json="$1"
    echo "$inspect_json" | jq -r '.State.Health.Status // "none"'
}

# ---------- get_previous_restart_count ----------
get_previous_restart_count() {
    local container="$1"
    [[ -f "$STATE_FILE" ]] || { echo ""; return; }
    grep "^${container}:" "$STATE_FILE" | tail -n 1 | cut -d':' -f2
}

# ---------- record_restart_count ----------
record_restart_count() {
    local container="$1"
    local count="$2"
    mkdir -p "$(dirname "$STATE_FILE")"
    echo "${container}:${count}" >> "$STATE_FILE"
}

# ---------- capture_crash_context ----------
capture_crash_context() {
    local container="$1"
    mkdir -p "$CRASH_CONTEXT_DIR"
    local out_file="$CRASH_CONTEXT_DIR/${container}_$(date '+%Y%m%d_%H%M%S').log"
    docker logs --tail "$LOG_TAIL_LINES" "$container" > "$out_file" 2>&1
    echo "$out_file"
}

Line-by-Line Highlights

  • docker inspect "$container" | jq -r '.[0]' — unwrapping the array once, right at the source, means every other function in this file works with a clean object rather than each needing to remember the .[0] index separately.
  • jq -r '.RestartCount // 0' — the // default operator (reinforced from Project 14) ensures a missing field never produces an empty string that would break downstream arithmetic.
  • jq -r '.State.Health.Status // "none"' — explicitly defaults to the string "none" rather than leaving this empty, since "no HEALTHCHECK defined" is a normal, expected condition (mirroring Project 7's "not a replica" non-error case) that the main script needs to distinguish from an actual unhealthy status.
  • grep "^${container}:" "$STATE_FILE" | tail -n 1 — identical pattern to Project 9's alert-fingerprint lookup, taking the most recent recorded value for this specific container.
  • docker logs --tail "$LOG_TAIL_LINES" "$container" > "$out_file" 2>&1 — captures both stdout and stderr from the container into one timestamped file, preserving crash context exactly as Project 4 preserved CPU-spike process attribution.

🩺 Main Script

scripts/docker_health_check.sh
#!/bin/bash
# =====================================================================
# docker_health_check.sh
# NovaTrust Bank - Container Restart-Trend, OOM, and HEALTHCHECK Monitor
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/docker_health.conf"

STATE_FILE="$SCRIPT_DIR/$STATE_FILE"
CRASH_CONTEXT_DIR="$SCRIPT_DIR/$CRASH_CONTEXT_DIR"

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/docker_health_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Docker health check run finished."' EXIT

log_message "INFO" "=== Starting Docker container health check ==="

OVERALL_EXIT=0
CONTAINERS=$(get_monitored_containers)

if [[ -z "$CONTAINERS" ]]; then
    log_message "WARN" "No containers matched filter '${CONTAINER_NAME_FILTER}'"
    exit 0
fi

while IFS= read -r container; do
    [[ -z "$container" ]] && continue

    INSPECT_JSON=$(inspect_container "$container")
    if [[ -z "$INSPECT_JSON" || "$INSPECT_JSON" == "null" ]]; then
        log_message "FAIL" "$container: could not inspect (container may have just stopped)"
        OVERALL_EXIT=2
        continue
    fi

    CURRENT_RESTARTS=$(get_restart_count "$INSPECT_JSON")
    PREVIOUS_RESTARTS=$(get_previous_restart_count "$container")

    CONTAINER_STATUS="HEALTHY"
    NEW_RESTART="false"

    if [[ -n "$PREVIOUS_RESTARTS" && "$CURRENT_RESTARTS" -gt "$PREVIOUS_RESTARTS" ]]; then
        NEW_RESTART="true"
        DELTA=$(( CURRENT_RESTARTS - PREVIOUS_RESTARTS ))
        CONTEXT_FILE=$(capture_crash_context "$container")
        log_message "WARN" "$container: $DELTA new restart(s) since last check (total: $CURRENT_RESTARTS) - context saved to $CONTEXT_FILE"
        CONTAINER_STATUS="WARNING"
        [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    fi

    if is_oom_killed "$INSPECT_JSON"; then
        log_message "FAIL" "$container: most recent exit was an OOM KILL"
        CONTAINER_STATUS="CRITICAL"
        OVERALL_EXIT=2
    fi

    HEALTH_STATUS=$(get_health_status "$INSPECT_JSON")
    case "$HEALTH_STATUS" in
        unhealthy)
            log_message "FAIL" "$container: Docker HEALTHCHECK reports UNHEALTHY"
            CONTAINER_STATUS="CRITICAL"
            OVERALL_EXIT=2
            ;;
        starting)
            log_message "INFO" "$container: HEALTHCHECK still starting (grace period)"
            ;;
        healthy)
            log_message "PASS" "$container: HEALTHCHECK reports healthy"
            ;;
        none)
            : # No HEALTHCHECK defined for this container - not an error, nothing to log
            ;;
    esac

    if [[ "$CONTAINER_STATUS" == "HEALTHY" && "$NEW_RESTART" == "false" ]]; then
        log_message "PASS" "$container: stable (restart count: $CURRENT_RESTARTS, no new restarts)"
    fi

    log_message "INFO" "$container - COMPOSITE VERDICT: $CONTAINER_STATUS"

    record_restart_count "$container" "$CURRENT_RESTARTS"

done <<< "$CONTAINERS"

log_message "INFO" "=== Docker health check complete ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
if [[ -n "$PREVIOUS_RESTARTS" && "$CURRENT_RESTARTS" -gt "$PREVIOUS_RESTARTS" ]]; thenThe -n "$PREVIOUS_RESTARTS" check handles a container's very first-ever check (no prior state yet) gracefully — exactly Project 3's "no history, establish baseline, don't error" pattern.
CONTEXT_FILE=$(capture_crash_context "$container")Log capture happens immediately upon detecting a new restart, not later — by the time an engineer investigates, the container's log buffer may have already rotated past the crash.
is_oom_killed and HEALTHCHECK checks both run unconditionallyNeither check is skipped even if a new restart was already found — a container could have an unrelated OOM kill and a separate restart-count increase in the same window, and both deserve independent reporting.
case "$HEALTH_STATUS" in ... none) : ;; esacThe bare colon : is Bash's no-op command — used here specifically to make explicit that "no HEALTHCHECK defined" is a deliberately silent, expected case, not an oversight.
record_restart_count "$container" "$CURRENT_RESTARTS" at the very endRuns unconditionally for every container, exactly like Project 3's record_reading — today's count must always be saved so the next run has an accurate baseline to compare against.

📄 README.md

README.md
# NovaTrust Bank - Docker Container Health Check

## Usage
    ./scripts/docker_health_check.sh

## What Gets Checked (per monitored container)
1. Restart count DELTA since the last check (not just cumulative total)
2. OOMKilled flag on the container's most recent exit
3. Docker's own HEALTHCHECK status, where defined

## On a New Restart
Recent container logs (last LOG_TAIL_LINES) are automatically captured to
logs/crash_context/ for diagnostic review.

## Exit Codes
    0 = All monitored containers stable and healthy
    1 = At least one container has new restarts since the last check
    2 = At least one container was OOM-killed, reports unhealthy, or could not be inspected

🔄 What Happens Internally

  1. Three independent Docker-native signals converge on one composite verdict per container, exactly matching Project 14's port/pool/thread pattern, now applied to restart-delta/OOM/HEALTHCHECK.
  2. State persistence follows Project 3's exact append-only, read-most-recent-line pattern — proven across memory-leak detection, alert de-duplication, and now container restart tracking.
  3. Log capture happens synchronously, inline, the moment a new restart is detected — not as a separate later step — because a container's log buffer is a limited, rotating resource that could lose crash context before a delayed capture attempt runs.
  4. docker inspect's single JSON blob is fetched once per container and then queried multiple times via separate jq calls — avoiding redundant docker inspect invocations, which are relatively expensive Docker API calls compared to parsing already-retrieved JSON locally.

🛡️ Production Best Practices

Never Trust "Running" Alone

A container's current up/down state says nothing about its recent stability — always track restart-count trend, not just a snapshot.

Distinguish Restart Causes

An OOM kill, an application crash, and a manual restart are different findings requiring different responses — check for the specific, named cause wherever Docker exposes one.

Capture Crash Context Immediately

Container log buffers are limited and rotate — capture diagnostic logs the moment a crash is detected, not on a delay.

Leverage Built-In Signals Before Duplicating Them

Where Docker's own HEALTHCHECK already provides an application-level signal, incorporate it rather than building a redundant parallel check.

Handle "Feature Not Configured" Gracefully

A missing HEALTHCHECK, like a missing baseline or a first-ever check, is a normal condition to handle cleanly — never treat "not configured" the same as "failed."

Minimize Expensive API Calls

Fetch docker inspect's full JSON once per container and parse multiple fields locally, rather than re-querying Docker separately for each individual field.

🎤 Interview Preparation

Scenario: A container shows a restart-count delta of "5 new restarts" but the OOMKilled flag reads false. What does this suggest?
The container is crash-looping for a reason other than memory exhaustion — likely an application-level crash (uncaught exception, failed startup dependency, misconfiguration); the automatically-captured crash-context logs are exactly what's needed next to identify the actual root cause.
Production Support: The script always reports "0 new restarts" for a container you can visually see restarting in real time. What's the likely bug?
The state file most likely isn't persisting correctly between runs — check whether record_restart_count is actually writing successfully (permissions, path resolution) and whether get_previous_restart_count's grep pattern is matching the exact container name being recorded.
Shell Scripting: Why does inspect_container unwrap the [0] array index once, centrally, instead of every downstream function doing it individually?
Centralizing the unwrap means every other function operates on a plain object and stays simpler and less error-prone; if every function repeated .[0] independently, a single missed instance would silently produce wrong results without necessarily erroring loudly.
Troubleshooting: HEALTHCHECK status always shows "none" even for a container whose Dockerfile clearly defines a HEALTHCHECK instruction. What would you check?
Confirm the container was actually built and run from the updated image containing that HEALTHCHECK instruction (an old cached image or a docker-compose override could omit it), and verify with docker inspect manually whether .State.Health exists at all in the raw output for that specific container.
Manager Round: Why treat a new restart as WARNING rather than CRITICAL by default, reserving CRITICAL for OOM kills and unhealthy HEALTHCHECK status specifically?
A single restart can sometimes be an expected, benign event (a deliberate redeploy, a graceful update) rather than inherently a failure; escalating only on specific, unambiguous failure signals (OOM, HEALTHCHECK-confirmed unhealthy) avoids false-alarming on legitimate operational restarts while still catching genuine problems.
Architecture: Why is restart-count DELTA tracked via a persisted state file rather than just reading Docker's own container uptime?
Container uptime alone conflates "just started for the first time" with "just restarted after a crash" — they look identical from an uptime measurement; comparing the cumulative restart counter against its own previous value is what specifically isolates new restart activity since the last check.
Best Practice: Why capture crash-context logs synchronously, inline, the moment a new restart is detected, rather than as a separate follow-up step?
A container's log buffer is finite and continues accumulating new output after a restart; delaying capture risks the crash-relevant log lines being pushed out and lost by the time a separate, later process gets around to retrieving them.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the 40-restart fraud-scoring incident hours earlier?
Comparing restart count against the previous check's persisted value, every 5 minutes — the very first new restart after deployment would have immediately produced a WARNING with captured crash-context logs, rather than the crash-looping pattern remaining invisible behind Docker's own restart policy for the entire morning.
