Cron Job Automation & Self-Monitoring

The backup script had been failing at its very first line for two weeks. Cron dutifully "ran" it every night. Nobody noticed until a real restore was needed.

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL + cron ⏱️ Duration: 3 hrs

📖 The Story — Scheduled Isn't the Same as Successful

A routine OS patch quietly changed the system's default $PATH. Project 11's nightly backup script, which called several commands without full paths in one small section nobody had touched in months, started failing within its first few lines — every single night, for two weeks. Cron itself never noticed anything wrong: it successfully launched the script at 1:00 AM every night, exactly as scheduled, and the script exited (with a failure code cron doesn't inspect by default) in under a second each time. The failure was only discovered when a real restore was needed and every single backup from the previous two weeks turned out to be missing.

Priya's directive: "Every check we've built in this entire course has one blind spot in common — we've always assumed cron itself is reliable and that our scripts, once scheduled, keep running successfully forever. I want proof of life for every critical scheduled job — not 'cron tried to run it,' but 'it actually finished successfully, recently.' If a job goes quiet, I want to know within hours, not when we desperately need something it was supposed to have produced."

This is our final infrastructure-layer project before we shift toward release validation and reporting — and it directly protects every single script this course has built so far.
🔁 Reinforced from Projects 1–19
find -mtime/-mmin age-based file checks (Projects 3, 5, 11), state-file patterns, and the "detection, not remediation" philosophy from Project 19 all return here, protecting the scheduling layer itself.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Detect when a critical scheduled job has stopped completing successfully, independent of whether cron itself continues to launch it on schedule.

Customer Requirement

Ops needs proof of successful completion for every critical scheduled script, not just confirmation that cron attempted to run it.

Banking Scenario

By this point in the course, NovaTrust has 19 different scheduled scripts (health checks, backups, certificate monitoring, patch validation, and more) all depending entirely on cron running reliably, silently, in the background.

Existing Manual Process / Prior Automation Gap

None of Projects 1-19 verify their own continued successful execution over time — every one of them assumes, without checking, that cron keeps calling them and that they keep succeeding.

Problems With This Blind Spot

Cron's own logs only record whether it launched a job, never whether that job actually completed successfully — a script failing instantly at its first line looks, from cron's perspective, identical to one that ran flawlessly.

Business Impact & Risk

Two weeks of silently missing backups directly threatens disaster-recovery readiness — precisely the kind of gap Project 11 was built specifically to prevent, undone by an entirely different, unmonitored failure mode.

Why Automation Is Required

Only an independent "watcher" process, checking proof of recent successful completion for every critical job, can catch a silently-broken scheduled script before its absence is discovered the hard way.

Solution Design

Every critical script is updated to "touch" a timestamped heartbeat file as its very last action, only reached on successful completion; a separate watcher script checks each registered job's heartbeat freshness against its expected interval, flagging any job that's gone silent.

Project Scope

In scope: the heartbeat pattern itself, a job registry with expected intervals, and staleness detection. Out of scope: automatically restarting or fixing a failed job — this remains detection-only, consistent with this course's monitoring focus.

Expected Outcome

Any critical scheduled job that stops completing successfully is flagged within a small multiple of its normal interval — hours, not weeks — closing the exact blind spot that hid the broken backup script.

🧠 New Bash Concepts for This Project

1. The Heartbeat / Dead Man's Switch Pattern

What: A monitored script touches an empty, timestamped file as the very last thing it does, reached only if every prior step succeeded — the file's own modification time becomes the proof of "last successful completion."
Why: This is fundamentally different from logging — a log file can contain an error message and still exist; a heartbeat file's mere freshness is the entire signal, and it's simply never touched at all if the script fails before reaching that line.

2. Placing the Heartbeat Call Correctly (The Critical Design Decision)

What: The heartbeat touch must be the absolute last line before a script's final exit 0 — never at the start, and never inside a function that might be reached even on a partial failure.
Why: A heartbeat touched at the start of a script proves only that it began, exactly the same blind spot that hid the original two-week failure — the entire value of this pattern depends on strict placement discipline.

3. Checking File Age in Minutes (find -mmin, New Flag)

What: find "$heartbeat_file" -mmin +"$max_age_minutes" — reinforcing find's age-checking from Projects 3, 5, and 11, now using -mmin (minutes) instead of -mtime (days), since heartbeat intervals are typically far shorter than log-retention periods.
Why: A backup job checked daily needs day-granularity staleness detection; a health check running every 5 minutes needs minute-granularity — -mmin gives us that finer precision.

4. A Job Registry as the Single Source of Truth

What: A config file listing every critical job's name, heartbeat file path, and expected maximum interval — reinforcing the config-driven-behavior principle from every project since Project 1's threshold file.
Why: Adding a new critical job to monitoring should mean adding one line to this registry, never modifying the watcher script's own logic.

5. Distinguishing "Never Ran" from "Went Stale"

What: A registered job whose heartbeat file doesn't exist at all (new job never yet integrated, or a typo'd path) is a different, often more basic problem than one whose heartbeat file exists but is simply old.
Why: The same "distinguish different failure modes" discipline from Project 13 (missing vs. outdated package) and Project 7 (connection failure vs. data failure) — conflating them would hide a simple configuration mistake behind a more alarming "job is failing" message.

6. A Reusable Function Meant for Other Scripts to Adopt

What: A small, standalone heartbeat.sh library file, designed specifically to be sourced by any other script in this entire course — extending, rather than replacing, each script's existing utils.sh.
Why: This project's value only exists if it's actually integrated everywhere — designing for easy adoption into 19 already-existing scripts is as much a part of the solution as the watcher script itself.

7. Building a Composite "Everything's Health" Report

What: The watcher script itself follows the exact same tiered classification pattern (HEALTHY/STALE/MISSING) used by literally every prior monitoring project in this course.
Why: Demonstrates this course's central lesson at its most literal — the same small set of Bash patterns, learned once, genuinely does generalize across nineteen completely different monitoring domains.

8. The "Who Watches the Watcher" Problem (Acknowledged Limitation)

What: This watcher script is itself a cron job, and could itself silently fail the exact same way the original backup script did.
Why acknowledging this matters: No monitoring system fully escapes this problem — mitigations include running the watcher more frequently than what it monitors, alerting through a genuinely separate channel (Project 9's Slack/email), and periodically, manually verifying the watcher itself is still running as part of a broader operational review. This is a deliberately honest, unresolved edge worth understanding rather than a false promise of a complete fix.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Cron watcher helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- check_heartbeat ----------
# Purpose: Return "MISSING", "STALE", or "HEALTHY" for one registered job
check_heartbeat() {
    local job_name="$1"
    local max_interval_minutes="$2"
    local heartbeat_file="$HEARTBEAT_DIR/${job_name}.heartbeat"

    if [[ ! -f "$heartbeat_file" ]]; then
        echo "MISSING"
        return
    fi

    # find returns the file's path ONLY if it's older than max_interval_minutes; empty output means it's still fresh
    local stale_check
    stale_check=$(find "$heartbeat_file" -mmin +"$max_interval_minutes" 2>/dev/null)

    if [[ -n "$stale_check" ]]; then
        echo "STALE"
    else
        echo "HEALTHY"
    fi
}

# ---------- get_heartbeat_age_minutes ----------
# Purpose: Return how many minutes old a heartbeat file is, for inclusion in the report
get_heartbeat_age_minutes() {
    local heartbeat_file="$1"
    local file_epoch now_epoch
    file_epoch=$(stat -c '%Y' "$heartbeat_file" 2>/dev/null) || { echo "?"; return; }
    now_epoch=$(date '+%s')
    echo $(( (now_epoch - file_epoch) / 60 ))
}

Line-by-Line Highlights

  • find "$heartbeat_file" -mmin +"$max_interval_minutes" — run against a single file path (not a directory), find either prints that path (if it matches the age condition) or nothing at all — a compact way to get a boolean-style answer.
  • stat -c '%Y' — reinforcing Project 7's stat familiarity, here extracting the file's raw modification epoch timestamp (%Y) for a precise age-in-minutes calculation, rather than just the boolean stale/fresh answer find gives.
  • The three-way MISSING/STALE/HEALTHY return value is checked as a simple string comparison by the caller, following the same string-based status-return pattern used since Project 3's classify_usage function.

💓 The Reusable Heartbeat Library

This is the file every other project's script needs to source and call, right before its final exit 0.

scripts/heartbeat.sh
#!/bin/bash
# =====================================================================
# heartbeat.sh
# NovaTrust Bank - Reusable "proof of successful completion" library
#
# USAGE IN ANY OTHER PROJECT'S SCRIPT:
#   1. source this file near the top, alongside your existing utils.sh
#   2. call heartbeat_touch "unique_job_name" as the ABSOLUTE LAST LINE
#      before your script's final "exit 0" - never earlier, never in a
#      function that could be reached on partial failure.
# =====================================================================

HEARTBEAT_DIR="${HEARTBEAT_DIR:-/home/devops/novatrust-cron-watcher/heartbeats}"

# ---------- heartbeat_touch ----------
# Purpose: Record proof that a script reached this exact line successfully, right now
heartbeat_touch() {
    local job_name="$1"
    mkdir -p "$HEARTBEAT_DIR"
    touch "$HEARTBEAT_DIR/${job_name}.heartbeat"
}
Example: retrofitting Project 11's backup.sh (excerpt, end of file)
source "$SCRIPT_DIR/heartbeat.sh"   # Added near the top, alongside the existing utils.sh source line

# ... all of backup.sh's existing stages: space check, archive, checksum, offsite copy ...

log_message "INFO" "=== Backup completed successfully: local AND offsite checksum-verified ==="

⚠️ The One Rule That Makes This Whole Project Work
If heartbeat_touch is ever placed anywhere except literally the last line before a successful exit 0 — especially if it's accidentally placed near the start of a script "just to confirm it's running" — the entire pattern silently stops proving anything meaningful. This is worth double-checking on every single retrofit.

🩺 The Watcher Script

scripts/cron_watcher.sh
#!/bin/bash
# =====================================================================
# cron_watcher.sh
# NovaTrust Bank - Heartbeat Staleness Watcher ("who watches the jobs")
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/cron_watcher.conf"

HEARTBEAT_DIR="$SCRIPT_DIR/$HEARTBEAT_DIR"
REGISTRY_FILE="$SCRIPT_DIR/../config/job_registry.txt"
[[ -f "$REGISTRY_FILE" ]] || { echo "ERROR: Job registry not found: $REGISTRY_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/cron_watcher_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another watcher instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Cron watcher run finished."' EXIT

log_message "INFO" "=== Starting cron job heartbeat watch ==="

OVERALL_EXIT=0
HEALTHY=0; STALE=0; MISSING=0

while IFS=':' read -r job_name max_interval; do
    [[ -z "$job_name" || "$job_name" == \#* ]] && continue

    STATUS=$(check_heartbeat "$job_name" "$max_interval")
    HEARTBEAT_FILE="$HEARTBEAT_DIR/${job_name}.heartbeat"

    case "$STATUS" in
        MISSING)
            log_message "FAIL" "$job_name: NO heartbeat file found - never ran, or heartbeat not yet integrated"
            ((MISSING++))
            OVERALL_EXIT=2
            ;;
        STALE)
            AGE_MIN=$(get_heartbeat_age_minutes "$HEARTBEAT_FILE")
            log_message "FAIL" "$job_name: STALE - last success ${AGE_MIN} min ago (expected within ${max_interval} min)"
            ((STALE++))
            OVERALL_EXIT=2
            ;;
        HEALTHY)
            AGE_MIN=$(get_heartbeat_age_minutes "$HEARTBEAT_FILE")
            log_message "PASS" "$job_name: healthy - last success ${AGE_MIN} min ago"
            ((HEALTHY++))
            ;;
    esac

done < "$REGISTRY_FILE"

log_message "INFO" "=== SUMMARY: Healthy=$HEALTHY | Stale=$STALE | Missing=$MISSING ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
STATUS=$(check_heartbeat "$job_name" "$max_interval")A single call returns one of exactly three string values, which the case statement below then branches on — the classification logic itself stays entirely inside utils.sh, keeping the main script focused on reporting.
MISSING) branch has no age to reportDeliberately distinct from the STALE branch's age calculation — there's no meaningful "age" for a file that was never created at all, so the message and the underlying problem are both reported differently.
Both STALE and MISSING escalate to OVERALL_EXIT=2Both represent the same underlying risk (an unmonitored, potentially-failing critical job) even though their specific cause differs — the report distinguishes them for troubleshooting, but their severity to Ops is treated as equally urgent.
Registry-driven while loop with no hardcoded job names anywhereAdding NovaTrust's 21st, 22nd, and every future critical scheduled script to this watcher means adding one line to job_registry.txt — the watcher script itself never needs to change.

📄 README.md

README.md
# NovaTrust Bank - Cron Job Self-Monitoring (Heartbeat Watcher)

## Integrating a Script With Heartbeat Monitoring
1. source scripts/heartbeat.sh in your script (alongside your existing utils.sh)
2. Call heartbeat_touch "your_job_name" as the ABSOLUTE LAST line before "exit 0"
3. Add a line to config/job_registry.txt: your_job_name:max_interval_minutes

## Usage
    ./scripts/cron_watcher.sh

## Status Values
    MISSING = no heartbeat file exists at all (never run, or not yet integrated)
    STALE   = heartbeat file exists but is older than its registered max interval
    HEALTHY = heartbeat file is within its expected interval

## Exit Codes
    0 = All registered jobs healthy
    2 = At least one job MISSING or STALE

## Known Limitation
This watcher is itself a cron job and could itself silently fail the same
way any monitored job can. Mitigate via frequent scheduling, routing alerts
through a channel humans actually monitor, and periodic manual review.

🔄 What Happens Internally

  1. Two entirely separate scripts, running on entirely separate schedules, cooperate through nothing but a shared filesystem convention (the heartbeat file naming pattern) — no direct communication between the monitored job and the watcher is needed at all.
  2. The heartbeat file's content is irrelevant; only its modification timestamp matters — this is deliberately the simplest possible signal, avoiding any parsing logic that could itself become a source of bugs.
  3. find -mmin's single-file usage returns a clean, unambiguous present/absent result perfectly suited to a simple boolean check, without needing any date-arithmetic conversion in the watcher itself.
  4. The registry-driven loop means this watcher's own code never grows as more jobs are added — all 19 (soon more) of this course's projects can be integrated by editing only the registry file, never cron_watcher.sh itself.

🛡️ Production Best Practices

Heartbeat Placement Is Everything

The pattern only works if the touch call is genuinely the very last successful action — audit this placement carefully on every integration, since a misplaced call silently defeats the entire purpose.

Distinguish Never-Ran from Went-Stale

These point to different root causes (a configuration/integration gap versus an active failure) and deserve to be reported and investigated differently.

Build in Slack for Normal Variance

Registry intervals should comfortably exceed a job's actual cron frequency, absorbing normal run-time variation without false alarms.

Registry-Driven, Never Hardcoded

The watcher script's own code should never need to change as jobs are added or removed — that's what the registry file exists for.

Acknowledge Meta-Monitoring's Own Limits

No watcher can fully guarantee its own reliability — be honest about this limitation and mitigate through frequency, alerting-channel diversity, and periodic manual review, rather than claiming a complete technical solution.

Retrofit Systematically, Not Opportunistically

When adding a course-wide capability like this, work through every existing critical script deliberately rather than only the ones that happen to come to mind first.

🎤 Interview Preparation

Scenario: A job's heartbeat is fresh, but Ops later discovers the job has actually been silently producing wrong output for a week. Does this mean the heartbeat pattern failed?
No — the heartbeat pattern specifically proves "the script reached its final successful-exit line," which is a narrower guarantee than "the script's output was correct"; verifying output correctness is a separate concern (like Project 11's checksum verification or Project 8's response-body validation) that must be layered on top, not something a heartbeat alone was ever meant to catch.
Production Support: The watcher reports a job as MISSING, but you can see in its own operational log that it ran and logged a successful completion message just this morning. What's the likely cause?
The heartbeat_touch call is very likely missing from that script entirely, or was added but never actually reached due to a code path issue (perhaps an early, unconditional exit elsewhere in the script) — the operational log proving the script ran doesn't by itself prove the specific heartbeat line was executed.
Shell Scripting: Why does check_heartbeat's staleness check rely on find's own exit/output behavior rather than manually calculating file age with stat and comparing to a threshold in Bash?
Both approaches work, but a single find -mmin +N call combines the age lookup and the threshold comparison into one purpose-built command; the manual stat-plus-arithmetic approach (used separately in get_heartbeat_age_minutes for reporting the precise age) is more code for the same yes/no answer where find already does exactly what's needed.
Troubleshooting: After retrofitting ten scripts with heartbeat calls, one specific job still shows STALE every single check, even though it appears to run fine manually. What's a likely culprit?
Check whether that job's cron entry actually matches what's manually tested — a common cause is the cron-scheduled invocation failing for an environment reason (missing PATH, wrong working directory) that doesn't reproduce when run manually from an interactive shell, ironically the exact class of bug this whole project exists to catch.
Manager Round: Why is heartbeat monitoring described as closing a blind spot that Projects 1-19 all shared, rather than being folded into each of those projects individually from the start?
The blind spot (verifying continued successful execution over time) is a generic concern applicable identically to every scheduled script, regardless of what each one actually monitors — building it once as a shared, reusable capability and retrofitting it is more maintainable than having reinvented slightly different versions of the same logic in all nineteen prior projects.
Architecture: Why use a simple touched file rather than, say, a database table or a more structured state format for heartbeats?
The signal needed is genuinely just "a timestamp of last success" — a filesystem's own modification time already provides exactly that, for free, with zero additional code to write or maintain; introducing a database or structured format would add real complexity without adding any corresponding value for this specific, simple need.
Best Practice: Why must the registry's max_interval_minutes always be set somewhat longer than a job's actual cron schedule interval, rather than matching it exactly?
Real job runs have natural variance (a slightly slower night due to load, a brief lock-contention delay) — setting the threshold exactly equal to the schedule interval would false-alarm on entirely normal timing variation, training Ops to distrust or ignore the watcher's alerts over time.
Real Incident Discussion: What's the single most direct design decision in this project that would have caught the two-week silent backup failure within hours instead of weeks?
Placing heartbeat_touch as the literal last line of Project 11's backup script, only reachable after every verification stage succeeded — the very first night the PATH-related failure occurred, the heartbeat would never have been touched, and the watcher's next 15-minute check cycle would have flagged it as STALE well within that same day.

✅ End of Project 20

Key Learnings

The heartbeat/dead-man's-switch pattern and its critical placement discipline, minute-granularity staleness detection with find -mmin, distinguishing "never ran" from "went stale," and designing a reusable library specifically meant for retrofitting across many existing scripts.

Common Mistakes to Avoid
