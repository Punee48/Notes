Linux Server Health Check

Automating the pre-market morning check for NovaTrust Bank's Core Banking servers — replacing four manual hours with a 90-second Bash script.

🎯 Level: Beginner 🧠 New Concepts: 12 🏗️ Environment: Linux / WSL ⏱️ Duration: 2–3 hrs

📖 The Story — Day One at NovaTrust Bank

We have just joined NovaTrust Bank as a Junior DevOps Engineer, sitting in the Production Support pod for Core Banking.

On our very first stand-up, our Team Lead, Priya, tells us: "Every single morning, before the branches open at 9:00 AM, our Operations team logs into 200 Linux servers, one by one, to check CPU, memory, disk space, and whether the Core Banking service is actually running. It takes them almost four hours, and last month they missed a disk that was 96% full — the account-statement generation service crashed at 8:45 AM, right before branch opening."

Priya turns to us and says: "Your first task is to automate this health check using Bash. It needs to run on every server in under two minutes, log everything, and shout loudly the moment something crosses a danger threshold. This has to be production-grade — Audit will review this script."

Let's build it together, one concept at a time, exactly the way it would be built inside a real bank.
📌 Why this project is first
Every advanced DevOps script — patching, deployment validation, disaster recovery checks — is built on the same foundation: reading system state, comparing it to a threshold, and reacting. Project 1 gives us that foundation.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Ensure all Core Banking Linux servers are healthy before the banking day starts, with zero manual server logins.

Customer Requirement

Branch staff must never face a system outage at 9:00 AM due to disk, memory, or CPU exhaustion, or a stopped banking service.

Banking Scenario

NovaTrust Bank runs Core Banking, Account Statement, and NEFT/RTGS gateway services on Linux servers in an on-prem data center. Branches open at 9:00 AM sharp across time zones.

Existing Manual Process

An Ops engineer SSHs into each server, runs top, df -h, free -m, and systemctl status by hand, and pastes results into an Excel sheet.

Problems with Manual Process

Takes ~4 hours for 200 servers, is error-prone, is not repeatable at the same instant across servers, and has no historical log trail for audits.

Business Impact & Risk

A missed disk-full or stopped-service condition can halt account statement generation or fund transfers right at branch opening — direct revenue and regulatory impact (SLA breach, RBI/regulator reporting risk).

Why Automation Is Required

A script executes identically every time, finishes in seconds, produces an audit-ready log, and can be scheduled with cron to run every morning with zero human involvement.

Solution Design

A modular Bash solution: a config file for thresholds, a utils file for reusable functions, a main script that performs checks and logs PASS/FAIL/WARN, and a cron job that runs it daily at 6:00 AM.

Project Scope

In scope: CPU, memory, disk, load average, and Core Banking service status on a single server (extendable to 200 via a hostname loop in a later project). Out of scope for now: email/Slack alerting (Project 9).

Expected Outcome

A single command, ./health_check.sh, that checks the server in under 5 seconds, writes a timestamped log entry, prints a color-coded PASS/WARN/FAIL summary, and exits with a status code that other tools (like cron or monitoring) can read.

🧠 Bash Concepts You Need Before We Code

We introduce each concept the moment the story needs it — nothing is explained "just because."

1. The Shebang (#!/bin/bash)

What: The very first line of a script, telling Linux which interpreter should execute the file.
Why: Without it, Linux might try to run our script using sh instead of bash, and some features we use (arrays, [[ ]]) don't exist in plain sh.
Internal working: The kernel reads the first two bytes (#!) of an executable text file and hands the rest of the file to the interpreter path that follows.
Production example: Every one of NovaTrust's 40+ production scripts starts with #!/bin/bash, enforced by a code-review checklist.
Best practice: Use #!/usr/bin/env bash if bash's install path may vary across servers.
Common mistake: Forgetting the shebang — the script still might run if invoked as bash script.sh, but fails if invoked as ./script.sh without execute logic falling back correctly.

2. Variables & Data Types

What: Named containers for values, like HOSTNAME=$(hostname). Bash has no strict data types — everything is stored as a string, but can be treated as an integer for arithmetic.
Why: We need to store the current disk usage, CPU percentage, and thresholds somewhere to compare them.
Internal working: Bash stores variables in the shell's process memory; child processes don't see them unless exported.
Best practice: Always wrap variables in quotes when using them — "$VAR" — to avoid word-splitting bugs.
Common mistake: Writing VAR = 5 (with spaces) — Bash will treat this as trying to run a command called VAR. It must be VAR=5, no spaces.

3. Command Substitution $( )

What: Runs a command and captures its output into a variable.
Why: We need the output of df -h or free -m stored so we can extract numbers from it.
Example: DISK_USAGE=$(df -h / | awk 'NR==2{print $5}')
Best practice: Prefer $( ) over the older backtick ` ` syntax — it nests cleanly and is easier to read.
Common mistake: Forgetting that the captured value includes trailing newlines/percent signs, which then fail numeric comparisons unless cleaned with tr or parameter expansion.

4. Conditions: if / elif / else and [[ ]]

What: Decision-making — "if disk usage is above 80%, mark WARN."
Internal working: [[ ]] is a Bash keyword (not an external command like [ / test) that evaluates an expression and returns exit status 0 (true) or 1 (false).
Production example: if [[ $DISK_PCT -ge $DISK_THRESHOLD ]]; then ... fi
Best practice: Use [[ ]] instead of single [ ] in Bash scripts — it's safer with unquoted variables and supports pattern matching.
Common mistake: Comparing numbers with == instead of -eq, or comparing strings with -eq instead of ==.

5. Loops: for and while

What: Repeats a block of commands. We use a for loop to check each service in a list.
Why: NovaTrust runs multiple services per server — we don't want to copy-paste the same check five times.
Best practice: Loop over arrays with "${ARRAY[@]}" (quoted) to correctly handle any spaces in names.
Common mistake: Looping over unquoted $ARRAY[@], which can split on spaces unexpectedly.

6. Functions

What: A named, reusable block of code, e.g. log_message().
Why: Every check needs to write a log line the same way — we write that logic once and call it everywhere.
Internal working: A function runs in the current shell (not a subshell) unless piped, so it can modify variables in the calling script.
Best practice: Keep functions in a separate utils.sh file and source it into the main script — this is how real production repos are organized.

7. Exit Codes

What: Every command and script returns a number from 0–255 when it finishes; 0 means success, anything else means some kind of failure.
Why: Cron, monitoring tools, and other scripts decide what to do next based on this number — nobody reads our script's screen output at 6:00 AM.
Internal working: Stored in the special variable $? immediately after a command runs.
Production example: Our health check will exit 2 on FAIL so a monitoring tool like Nagios can page the on-call engineer automatically.
Common mistake: Forgetting that $? only reflects the immediately preceding command — checking it after an unrelated line in between gives the wrong result.

8. Redirection (>, >>, 2>) & Pipes (|)

What: Redirection sends command output to a file instead of the screen; pipes send one command's output as another command's input.
Why: We pipe df -h into awk to extract just the percentage, and we append (>>, never overwrite with >) our results to the daily log.
Best practice: Always use >> for logs so history isn't wiped on every run; redirect errors separately with 2> so real errors aren't lost inside normal output.

9. Text-processing tools: grep, awk, cut

grep — searches text for a pattern (e.g., find the "Mem:" line inside free -m output).
awk — a field-processing language; we use {print $5} style patterns to grab a specific column, like the disk-usage percentage in column 5 of df -h.
cut — extracts characters or fields by position/delimiter, useful for trimming the % sign off a percentage.
Common mistake: Assuming column numbers in df/free output never change across Linux distributions — always test the exact command on the target OS.

10. Arguments & getopts

What: Values passed to a script at run time, e.g. ./health_check.sh -e production. getopts is Bash's built-in way to parse flags like -e cleanly.
Why: Production scripts must support flags for environment name, verbosity, or a dry-run mode without editing the script itself.
Best practice: Always provide a -h/help flag and validate required arguments before running any checks.

11. trap and Signals

What: trap lets a script catch signals (like Ctrl+C, or SIGTERM) and run cleanup code before exiting.
Why: If Ops presses Ctrl+C mid-run, we still want the log file properly closed and a partial-run warning recorded, not a silently corrupted log.
Production example: trap cleanup EXIT ensures our temp files are always removed, even on failure.

12. cron

What: A Linux time-based job scheduler that runs commands automatically at fixed times.
Why: This is how our script runs every morning at 6:00 AM with zero human involvement.
Best practice: Cron runs with a minimal environment (no $PATH like your interactive shell) — always use full paths to commands and scripts inside crontab entries.

🧩 Utility Functions

Shared logic lives in one file and is sourced by the main script — this is standard practice so every project script logs identically.

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Shared helper functions for NovaTrust health scripts
# This file is meant to be "sourced", never executed directly.
# =====================================================

# ---------- log_message ----------
# Purpose: Write one consistent, timestamped line to today's log file
# Arguments: $1 = level (PASS/WARN/FAIL/INFO), $2 = message text
log_message() {
    local level="$1"                              # local = variable only exists inside this function
    local message="$2"                            # the human-readable text to log
    local timestamp                                # declare timestamp separately (best practice for readability)
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')         # command substitution: capture current date/time as text

    # Print to the screen AND append to the log file at the same time using tee -a
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_disk_usage ----------
# Purpose: Return the root filesystem's used disk percentage as a plain integer (no % sign)
get_disk_usage() {
    df -h / | awk 'NR==2 {print $5}' | tr -d '%'   # NR==2 = second line of df output; strip trailing % with tr
}

# ---------- get_memory_usage ----------
# Purpose: Return used memory as a percentage of total memory, rounded to nearest integer
get_memory_usage() {
    free | awk '/Mem:/ {printf "%.0f", ($3/$2) * 100}'   # $3 = used, $2 = total, from the "Mem:" line
}

# ---------- get_cpu_usage ----------
# Purpose: Return current CPU usage percentage (100 - idle%)
get_cpu_usage() {
    # top in batch mode (-b), 1 iteration (-n1); grab the "Cpu(s)" line; extract the idle field; subtract from 100
    top -bn1 | grep "Cpu(s)" | awk '{print 100 - $8}' | cut -d'.' -f1
}

# ---------- get_load_average ----------
# Purpose: Return the 1-minute load average as a plain number
get_load_average() {
    uptime | awk -F'load average:' '{print $2}' | awk -F',' '{print $1}' | tr -d ' '
}

# ---------- check_service_status ----------
# Purpose: Return 0 if the given service is active, 1 otherwise
# Arguments: $1 = service name
check_service_status() {
    local service_name="$1"
    systemctl is-active --quiet "$service_name"    # --quiet suppresses output; we only care about the exit code
    return $?                                      # pass that exit code back to whoever called this function
}

Line-by-Line: what's actually happening

  • local level="$1" — local keeps this variable scoped to the function only, so it can't accidentally overwrite a same-named variable in the main script.
  • tee -a "$LOG_FILE" — tee duplicates output to both the screen and a file; -a appends instead of overwriting, so history builds up correctly.
  • awk 'NR==2 {print $5}' — NR is awk's built-in "current line number" variable; we skip the header line (line 1) of df -h output.
  • tr -d '%' — tr deletes (-d) every % character so the value becomes a clean integer for numeric comparison.
  • systemctl is-active --quiet — a purpose-built systemd command whose only job is to answer "is this active?" via its exit code, which is exactly what an if statement needs.

🩺 Main Script

scripts/health_check.sh
#!/bin/bash
# =====================================================================
# health_check.sh
# NovaTrust Bank - Daily Core Banking Server Health Check
# Author: DevOps Team | Reviewed by: Priya (Team Lead)
# Purpose: Replace 4-hour manual server check with a sub-5-second script
# =====================================================================

set -uo pipefail
# set -u  -> treat unset variables as an error instead of silently using empty string
# -o pipefail -> if any command in a pipe fails, the whole pipe reports failure (not just the last command)

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
# ^ Reliably finds this script's own folder, regardless of where it is called from

source "$SCRIPT_DIR/../config/health_check.conf"    # Load all threshold values and service list
source "$SCRIPT_DIR/utils.sh"                       # Load reusable functions like log_message

TODAY=$(date '+%Y%m%d')                             # e.g. 20260722, used to name today's log file
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/health_check_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"                   # Create the logs folder if it doesn't already exist

EXIT_CODE=0                                         # 0 = all pass, 1 = warning found, 2 = failure found

# ---------- cleanup on interruption ----------
cleanup() {
    log_message "INFO" "Health check interrupted or finished. Exiting."
}
trap cleanup EXIT                                   # Runs 'cleanup' no matter how the script ends (success, error, Ctrl+C)

log_message "INFO" "=== Starting NovaTrust Health Check on $(hostname) ==="

# ---------------------------------------------------------------------
# CHECK 1: DISK USAGE
# ---------------------------------------------------------------------
DISK_PCT=$(get_disk_usage)
if [[ "$DISK_PCT" -ge "$DISK_FAIL_THRESHOLD" ]]; then
    log_message "FAIL" "Disk usage critical: ${DISK_PCT}% (threshold ${DISK_FAIL_THRESHOLD}%)"
    EXIT_CODE=2
elif [[ "$DISK_PCT" -ge "$DISK_WARN_THRESHOLD" ]]; then
    log_message "WARN" "Disk usage high: ${DISK_PCT}% (threshold ${DISK_WARN_THRESHOLD}%)"
    [[ $EXIT_CODE -lt 1 ]] && EXIT_CODE=1
else
    log_message "PASS" "Disk usage normal: ${DISK_PCT}%"
fi

# ---------------------------------------------------------------------
# CHECK 2: MEMORY USAGE
# ---------------------------------------------------------------------
MEM_PCT=$(get_memory_usage)
if [[ "$MEM_PCT" -ge "$MEM_FAIL_THRESHOLD" ]]; then
    log_message "FAIL" "Memory usage critical: ${MEM_PCT}% (threshold ${MEM_FAIL_THRESHOLD}%)"
    EXIT_CODE=2
elif [[ "$MEM_PCT" -ge "$MEM_WARN_THRESHOLD" ]]; then
    log_message "WARN" "Memory usage high: ${MEM_PCT}% (threshold ${MEM_WARN_THRESHOLD}%)"
    [[ $EXIT_CODE -lt 1 ]] && EXIT_CODE=1
else
    log_message "PASS" "Memory usage normal: ${MEM_PCT}%"
fi

# ---------------------------------------------------------------------
# CHECK 3: CPU USAGE
# ---------------------------------------------------------------------
CPU_PCT=$(get_cpu_usage)
if [[ "$CPU_PCT" -ge "$CPU_FAIL_THRESHOLD" ]]; then
    log_message "FAIL" "CPU usage critical: ${CPU_PCT}% (threshold ${CPU_FAIL_THRESHOLD}%)"
    EXIT_CODE=2
elif [[ "$CPU_PCT" -ge "$CPU_WARN_THRESHOLD" ]]; then
    log_message "WARN" "CPU usage high: ${CPU_PCT}% (threshold ${CPU_WARN_THRESHOLD}%)"
    [[ $EXIT_CODE -lt 1 ]] && EXIT_CODE=1
else
    log_message "PASS" "CPU usage normal: ${CPU_PCT}%"
fi

# ---------------------------------------------------------------------
# CHECK 4: LOAD AVERAGE
# ---------------------------------------------------------------------
LOAD_AVG=$(get_load_average)
LOAD_INT=${LOAD_AVG%.*}                              # Parameter expansion: strip everything from the decimal point onward
if [[ "$LOAD_INT" -ge "$LOAD_FAIL_THRESHOLD" ]]; then
    log_message "FAIL" "Load average critical: ${LOAD_AVG} (threshold ${LOAD_FAIL_THRESHOLD})"
    EXIT_CODE=2
elif [[ "$LOAD_INT" -ge "$LOAD_WARN_THRESHOLD" ]]; then
    log_message "WARN" "Load average high: ${LOAD_AVG} (threshold ${LOAD_WARN_THRESHOLD})"
    [[ $EXIT_CODE -lt 1 ]] && EXIT_CODE=1
else
    log_message "PASS" "Load average normal: ${LOAD_AVG}"
fi

# ---------------------------------------------------------------------
# CHECK 5: CRITICAL SERVICES
# ---------------------------------------------------------------------
for service in "${CRITICAL_SERVICES[@]}"; do          # Loop through every service listed in the config file
    if check_service_status "$service"; then
        log_message "PASS" "Service '$service' is active"
    else
        log_message "FAIL" "Service '$service' is NOT running"
        EXIT_CODE=2
    fi
done

# ---------------------------------------------------------------------
# SUMMARY
# ---------------------------------------------------------------------
case $EXIT_CODE in                                    # case statement: cleaner than if/elif for fixed known values
    0) log_message "INFO" "SUMMARY: All checks PASSED. Server is healthy." ;;
    1) log_message "INFO" "SUMMARY: One or more WARNINGS found. Review log." ;;
    2) log_message "INFO" "SUMMARY: One or more FAILURES found. Immediate action required." ;;
esac

exit $EXIT_CODE                                       # Hand this code back to cron / the calling shell

Every Line, Explained

LineExplanation
set -uo pipefailTwo safety nets in one line: undefined variables become hard errors, and a failure anywhere in a pipe (cmd1 | cmd2) is no longer hidden by cmd2's success.
SCRIPT_DIR="$(cd ... && pwd)"Makes the script location-independent — it can be run from cron, from another folder, or via a symlink and still find its own config/utils files.
sourceLoads variables and functions from another file into the current shell (as opposed to running it as a separate process), so they remain usable below.
trap cleanup EXITGuarantees the cleanup function runs whether the script finishes normally, hits an error, or is killed with Ctrl+C.
[[ "$DISK_PCT" -ge "$DISK_FAIL_THRESHOLD" ]]-ge is Bash's "greater than or equal to" for integers (never use >= for numbers in Bash conditionals).
[[ $EXIT_CODE -lt 1 ]] && EXIT_CODE=1A compact "if true, then" pattern: only escalates EXIT_CODE to 1 if it isn't already 2 (a FAIL should never be downgraded to a WARN).
${LOAD_AVG%.*}Parameter expansion that trims everything from the last . onward — turns 3.42 into 3 for integer comparison.
for service in "${CRITICAL_SERVICES[@]}"Iterates the array defined in the config file; quoting "${...[@]}" prevents word-splitting if a service name ever contains a space.
case $EXIT_CODE in ... esacCleaner than three separate if blocks when checking one variable against several fixed values.
exit $EXIT_CODEThe single most important line for automation — this is what cron, monitoring, and CI pipelines actually read to decide "did this succeed?"

🔄 What Happens Internally When You Run This Script

  1. Linux loads the script: the kernel reads the shebang line and hands execution to /bin/bash.
  2. Bash creates a new process: a child shell process is forked to run the script's commands, separate from your interactive shell.
  3. Variable initialization: set -uo pipefail takes effect immediately, followed by SCRIPT_DIR being computed.
  4. source runs in-process: unlike calling another script normally, source does not create a subshell — the config values and functions become directly available.
  5. Command execution & subshells: every $( ) command substitution (like $(hostname)) briefly spawns a subshell to run that one command, captures its output, then that subshell exits.
  6. Exit status propagation: each if [[ ... ]] reads the true/false result of the test; $? is updated after every command.
  7. Signal handling: if you press Ctrl+C, Bash sends SIGINT; our trap cleanup EXIT still fires because EXIT is a pseudo-signal caught on any script termination.
  8. Final exit: exit $EXIT_CODE terminates the child process and returns that number to whatever called the script (your shell, or cron).

🛡️ Production Best Practices

Logging

Always timestamp, always append, never overwrite. Rotate logs (Project 5) so disks don't fill from your own health-check logs.

Error Handling

set -uo pipefail catches whole classes of silent bugs before they reach production.

Input Validation

Validate config values are actually numbers before comparing — a typo'd threshold like 75% (with the percent sign left in) will break -ge comparisons.

Exit Codes

Never reuse exit code 1 for "success with a note" — reserve 0 strictly for a clean pass so monitoring tools aren't fooled.

Security & Permissions

Scripts should be owned by a dedicated service account, not root, and should be 750 (not world-writable).

Reusability

Keep thresholds and service lists in config, keep logic in utils — this exact file layout will be reused in every remaining project.

🎤 Interview Preparation

Scenario: Your health check script reports PASS on disk usage, but the server actually ran out of space an hour later. What could be wrong?
Likely checking the wrong mount point (only / was checked, not /data or /var/log where the actual growth happened), or the threshold was set too high, or the script only ran once at 6 AM and disk filled afterward — argue for more frequent checks or real-time monitoring for volatile partitions.
Production Support: Cron didn't run the script at all last night. How do you debug it?
Check /var/log/cron or grep CRON /var/log/syslog, verify the crontab entry with crontab -l, confirm the script path is absolute and executable, and check cron_stdout.log for any environment-related errors (missing $PATH is the classic cause).
Shell Scripting: What's the difference between $( ) and backticks?
Functionally similar, but $( ) nests cleanly for multiple levels of command substitution and is easier to read; backticks require escaping when nested and are considered legacy syntax.
Troubleshooting: The script exits with "unbound variable" in production but not on your laptop. Why?
Almost always a config file that's out of sync — the production health_check.conf is missing a variable that a newer version of the script expects. Always deploy config and script changes together.
Manager Round: Why should we invest engineering time automating something Ops already does manually?
Manual checks cost ~4 engineer-hours daily and are inconsistent; a script costs a few hours once, then runs free forever, with an audit trail regulators can review — a clear ROI and risk-reduction argument.
Architecture: Why keep thresholds in a separate config file instead of inside the script?
Separating configuration from logic means Ops can retune sensitivity without a code deployment or code review, reducing change-management overhead while keeping the audited script logic untouched.
Best Practice: Why use [[ ]] instead of [ ] in Bash?
[[ ]] is a Bash keyword with safer word-splitting behavior, supports &&/|| inside the brackets, and enables pattern matching — [ ] is the older POSIX test command with more edge cases.
Real Incident Discussion: A hardcoded 90% disk threshold missed a partition that failed at 85% due to a different filesystem's reserved blocks. What changed after this incident?
NovaTrust moved all thresholds into config files (as shown in this project) and added a WARN tier below FAIL so problems surface earlier, before they become full outages.
