Enterprise Monitoring Dashboard

Six engineers on an incident bridge, tabbing between 26 terminal windows, each asking the same question a different way: "what's actually happening right now?"

🎯 Level: Advanced 🧠 New Concepts: 8 🏗️ Environment: Linux / WSL ⏱️ Duration: 3 hrs

📖 The Story — Twenty-Six Windows, No Single View

During a major incident bridge call, six engineers sat on a video call, each tabbing between different terminal windows, each running tail -f on a different project's log, each periodically re-running Project 25's daily aggregator hoping for a fresher snapshot. Every individual monitoring project in this course does its own job well — but during a live, unfolding incident, nobody had one shared, continuously-updating screen everyone on the bridge could look at together.

Priya's final assignment: "I want a live dashboard — something we can put up on the war-room screen during an incident, refreshing every few seconds, showing the current status across everything we monitor, right there in the terminal. Not another daily email. Something alive, that updates while we're watching it."

This capstone project pulls together nearly everything this course has built — reading, parsing, classifying — into a genuinely new kind of tool: a long-running, continuously-refreshing, interactive terminal display, rather than a scheduled batch script.
🔁 Reinforced from Projects 1–27
Project 25's multi-source aggregation, Project 20's staleness-checking (find -mmin), and disciplined trap usage (since Project 1) all return here, adapted for a genuinely new execution model: a long-running interactive loop instead of a one-shot scheduled script.

🧠 New Bash Concepts for This Project

1. The Continuous Refresh Loop (New Execution Model)

What: while true; do render_dashboard; sleep "$REFRESH_SECONDS"; done — a genuinely long-running foreground loop, fundamentally different from every prior project's one-shot, cron-triggered execution model.
Why: A live dashboard's entire purpose requires it to keep running and updating for as long as someone is watching it — this is this course's first project designed around a continuous, interactive lifetime rather than a quick scheduled run.

2. Clearing and Redrawing the Terminal (tput clear, cursor control)

What: tput clear clears the terminal screen; tput cup 0 0 moves the cursor to the top-left corner — together allowing a full redraw each cycle without the previous frame's content visibly scrolling by.
Why: Without deliberate screen control, each refresh would simply print a new block of text below the last, scrolling the terminal endlessly rather than producing a clean, dashboard-like "live updating" effect.

3. Terminal Colors via tput (Reinforced, New Context)

What: tput setaf 2 sets the foreground text color (green); tput sgr0 resets formatting — the terminal-native equivalent of this entire course's HTML color-coding, now applied directly in a live terminal context.
Why: tput is more portable across different terminal types than hardcoding raw ANSI escape codes directly, since it looks up the correct sequence for whatever terminal is actually in use.

4. Detecting Terminal Width (tput cols)

What: tput cols returns the current terminal window's width in characters, letting the dashboard adjust column widths or truncate long text to fit whatever screen it's actually being displayed on.
Why: A war-room display might be a wide monitor or a narrow terminal window — checking the actual available width avoids badly wrapped, unreadable output.

5. Trapping Ctrl+C for Graceful Interactive Exit (trap ... SIGINT, New Signal Context)

What: trap cleanup_and_exit SIGINT — reinforcing trap from Project 1 (there used for EXIT-triggered cleanup), now specifically catching the interactive Ctrl+C signal a human actually presses to stop watching the dashboard.
Why: Without this, Ctrl+C would abruptly kill the script mid-redraw, potentially leaving the terminal in a modified state (wrong colors, hidden cursor) that persists uncomfortably even after the dashboard exits.

6. Efficient Re-Parsing via Modification-Time Caching

What: Before re-parsing a source's log file on each refresh cycle, first check whether its modification time has changed since the last cycle (stat -c '%Y', reinforced from Project 20) — only re-parse if it genuinely has.
Why: Re-reading and re-parsing 26 log files every few seconds, forever, is wasteful when most sources haven't actually produced new output since the last check — this optimization keeps the dashboard lightweight enough to run continuously for hours during a long incident.

7. A Fast-Refresh-Appropriate Staleness Threshold (Reinforced Project 20, Different Timescale)

What: Distinguishing "this source's data is current" from "this source hasn't updated in an oddly long time" using a threshold appropriate to a live, minutes-scale display — a different timescale than Project 20's hours-scale heartbeat monitoring.
Why: During a live incident, even a source going quiet for just a few minutes might itself be meaningful information worth surfacing on the shared display.

8. Hiding and Restoring the Cursor (tput civis / tput cnorm)

What: tput civis hides the blinking terminal cursor during the dashboard's run (avoiding a distracting flicker on every redraw); tput cnorm restores it — critically, always called during cleanup, even on an unexpected exit.
Why: A small but genuinely important terminal-UI polish detail — and a good, concrete example of exactly the kind of cleanup a trap handler must reliably guarantee runs, no matter how the script actually terminates.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Live dashboard helper functions
# =====================================================

# ---------- get_latest_log_path ----------
get_latest_log_path() {
    local log_dir="$1" filename_prefix="$2"
    local today
    today=$(date '+%Y%m%d')
    echo "$SCRIPT_DIR/$log_dir/${filename_prefix}${today}.log"
}

# ---------- get_file_mtime ----------
# Purpose: Return a file's modification epoch, or empty if it doesn't exist
get_file_mtime() {
    local file="$1"
    [[ -f "$file" ]] || { echo ""; return; }
    stat -c '%Y' "$file" 2>/dev/null
}

# ---------- get_latest_summary ----------
get_latest_summary() {
    local log_file="$1"
    grep "SUMMARY" "$log_file" 2>/dev/null | tail -n 1
}

# ---------- classify_for_dashboard ----------
classify_for_dashboard() {
    local summary="$1"
    if echo "$summary" | grep -qiE "critical|fail|breach|non_compliant"; then
        echo "FAIL"
    elif echo "$summary" | grep -qiE "warn"; then
        echo "WARN"
    else
        echo "PASS"
    fi
}

# ---------- color_for_status ----------
# Purpose: Print the tput escape sequence for a given status (call before printing status text)
color_for_status() {
    local status="$1"
    case "$status" in
        PASS)  tput setaf 2 ;;   # green
        WARN)  tput setaf 3 ;;   # yellow
        FAIL)  tput setaf 1 ;;   # red
        STALE) tput setaf 8 ;;   # grey
    esac
}

Line-by-Line Highlights

  • get_latest_log_path and get_latest_summary deliberately reuse Project 25's exact source-reading conventions — this dashboard is a genuinely new presentation layer over the same underlying data model, not a separate parsing implementation.
  • get_file_mtime returning an empty string for a missing file (rather than erroring) lets the main script's caching logic treat "file doesn't exist" and "file's mtime hasn't changed since I last checked" as cleanly distinguishable, comparable states.
  • tput setaf 2 — setaf stands for "set ANSI foreground," and the numbers (0-7) map to the standard eight terminal colors; using tput's named capability rather than a raw \033[32m escape code keeps this portable across different terminal emulators.

🩺 Main Script

scripts/dashboard.sh
#!/bin/bash
# =====================================================================
# dashboard.sh
# NovaTrust Bank - Live Terminal Infrastructure Dashboard
# Run this directly, in the foreground, during an active incident.
# Press Ctrl+C to exit.
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/dashboard.conf"

REGISTRY_FILE="$SCRIPT_DIR/../config/source_registry.txt"
[[ -f "$REGISTRY_FILE" ]] || { echo "ERROR: Source registry not found: $REGISTRY_FILE" >&2; exit 1; }

# ---------- Associative arrays acting as our lightweight cache ----------
declare -A LAST_MTIME       # source_name -> last-seen mtime (for change detection)
declare -A LAST_STATUS      # source_name -> last-parsed PASS/WARN/FAIL/STALE
declare -A LAST_SUMMARY     # source_name -> last-parsed summary text

# ---------- Graceful exit: always restore the cursor, no matter how we exit ----------
cleanup_and_exit() {
    tput cnorm                                  # Restore the visible cursor
    tput sgr0                                   # Reset all text formatting/color
    echo ""
    echo "Dashboard stopped."
    exit 0
}
trap cleanup_and_exit SIGINT                    # Fires specifically on Ctrl+C

tput civis                                      # Hide the cursor for a cleaner live display

while true; do
    # ---------- Refresh cache: only re-parse sources whose file actually changed ----------
    while IFS=':' read -r name log_dir filename_prefix; do
        [[ -z "$name" || "$name" == \#* ]] && continue

        LOG_PATH=$(get_latest_log_path "$log_dir" "$filename_prefix")
        CURRENT_MTIME=$(get_file_mtime "$LOG_PATH")

        if [[ -z "$CURRENT_MTIME" ]]; then
            LAST_STATUS["$name"]="STALE"
            LAST_SUMMARY["$name"]="No log file found for today"
            continue
        fi

        if [[ "${LAST_MTIME[$name]:-}" != "$CURRENT_MTIME" ]]; then
            SUMMARY=$(get_latest_summary "$LOG_PATH")
            LAST_STATUS["$name"]=$(classify_for_dashboard "$SUMMARY")
            LAST_SUMMARY["$name"]="$SUMMARY"
            LAST_MTIME["$name"]="$CURRENT_MTIME"
        fi
        # If mtime is unchanged, we deliberately do nothing - the cached values from the
        # associative arrays are simply reused as-is in the render step below.

    done < "$REGISTRY_FILE"

    # ---------- Render: clear and redraw the full screen from the cache ----------
    tput clear
    tput cup 0 0
    COLS=$(tput cols)
    echo "NOVATRUST BANK - LIVE INFRASTRUCTURE DASHBOARD  ($(date '+%H:%M:%S'))  [Ctrl+C to exit]"
    printf '%*s\n' "$COLS" '' | tr ' ' '-'

    for name in "${!LAST_STATUS[@]}"; do
        STATUS="${LAST_STATUS[$name]}"
        color_for_status "$STATUS"
        printf "%-30s [%-5s]" "$name" "$STATUS"
        tput sgr0
        printf "  %s\n" "${LAST_SUMMARY[$name]:0:60}"
    done

    sleep "$REFRESH_SECONDS"
done

Every Line, Explained

LineExplanation
declare -A LAST_MTIME LAST_STATUS LAST_SUMMARYThree parallel associative arrays, all keyed by source name, together forming this dashboard's entire in-memory cache — exactly the pattern reinforced from Project 12's baseline arrays, now serving a caching purpose instead of an integrity-comparison one.
trap cleanup_and_exit SIGINT before tput civisThe trap is registered before the cursor is ever hidden — guaranteeing that even a Ctrl+C pressed in the first fraction of a second is caught and correctly restores the cursor, rather than leaving the terminal in a hidden-cursor state if interrupted too early.

The inner registry-reading loop makes NO changes to the screen itselfCache-refreshing and screen-rendering are deliberately two separate, sequential phases within each cycle — first update whatever needs updating, then redraw the complete picture from the now-current cache in one clean pass.

🔄 What Happens Internally

  1. The trap is registered before any terminal state is modified, ensuring the very first Ctrl+C, at any point in the script's life, always triggers a correct, complete cleanup.
  2. The mtime-comparison cache turns what would otherwise be 26 full log-parses every 5 seconds into typically zero or very few — during a quiet period between real status changes, most cycles do almost no real work at all beyond the cheap stat calls checking for change.
  3. Rendering is entirely decoupled from parsing — the screen redraw always uses whatever is currently in the three cache arrays, regardless of whether this particular cycle updated zero, one, or all 26 of them.
  4. Every terminal control sequence (tput clear, civis, cnorm, setaf, sgr0) is looked up via tput's terminal-capability database, rather than hardcoded as raw escape sequences — the same dashboard code works correctly across different terminal emulators without modification.

🛡️ Production Best Practices

Always Restore Terminal State on Exit

Any script that hides the cursor or changes terminal formatting must guarantee restoration via a trap — leaving a user's terminal in a modified state after exit is a real, frustrating usability bug.

Cache Aggressively for Frequent-Refresh Tools

A dashboard refreshing every few seconds must avoid unconditionally re-doing expensive work every cycle — check for actual change first, exactly like this project's mtime comparison.

Separate Data Refresh from Rendering

Update the cache first, render from the cache second — this separation keeps the rendering logic simple and always working from one consistent, complete snapshot.

Use tput, Not Raw Escape Codes

Terminal capability lookups via tput are more portable across different terminal types than hardcoded ANSI sequences.

Register Traps Before Modifying State

A trap set up after hiding the cursor (rather than before) leaves a window where an early interrupt wouldn't be caught — register cleanup handlers as early as possible.

Design for the Room, Not Just the Individual

A war-room dashboard is read by a group at a glance — prioritize the most urgent information's visibility over exhaustive per-source detail.

🎤 Interview Preparation

Scenario: The dashboard shows a source as STALE, but you can confirm that source's underlying monitoring script ran successfully just five minutes ago. What might be happening?
Most likely the dashboard's expected log filename (constructed from today's date and the registry's filename prefix) doesn't match what the source actually produced — the same class of filename-mismatch issue seen in Project 25, now surfacing live rather than in a daily report.
Production Support: After the dashboard was closed with Ctrl+C, the terminal's cursor is invisible and colors look wrong. What went wrong?
The trap likely didn't fire correctly — possibly the process was actually killed with a signal that can't be trapped (like SIGKILL/kill -9), or the terminal session itself was closed abruptly rather than the script receiving a proper Ctrl+C; running tput cnorm; tput sgr0 manually restores the terminal in either case.
Shell Scripting: Why does the dashboard use "${LAST_MTIME[$name]:-}" instead of just "${LAST_MTIME[$name]}" when comparing mtimes?
On a source's very first check, no entry yet exists in the LAST_MTIME associative array for that key; with set -u active, referencing a truly unset associative-array key would trigger an "unbound variable" error, so the :- default-value expansion (defaulting to empty string) is required to safely handle that first-ever comparison.
Troubleshooting: The dashboard appears to hang and never redraws after the very first frame. What's a likely cause?
Check whether one of the registry's log directories is on a slow or unresponsive network filesystem — a stat call against an unreachable mount can hang, and since this loop has no timeout protection on its file operations (unlike this course's earlier network-facing projects), a single unresponsive source could stall the entire refresh cycle indefinitely.
Manager Round: Why build this as a terminal dashboard instead of a simple auto-refreshing web page, given this course already built plenty of HTML generation in Project 25?
A terminal tool requires zero additional infrastructure (no web server, no browser, nothing to keep running or securing) and can be launched instantly on any engineer's existing SSH session or war-room terminal — for the specific use case of an ad-hoc incident bridge, that immediacy and lack of dependencies often outweighs a web UI's visual polish.
Architecture: Why does this project deliberately separate the "check if data changed" phase from the "render the screen" phase within each loop cycle, rather than rendering immediately as each source is checked?
Rendering incrementally, one source at a time as each is checked, would produce a flickering, partially-updated screen mid-cycle; completing all cache updates first and only then performing one single, complete redraw guarantees every refresh shows one fully consistent snapshot, never a half-updated intermediate state.
Best Practice: Why is REFRESH_SECONDS a configurable value rather than a hardcoded constant?
Different incidents and different display contexts have different appropriate refresh needs — a very fast refresh adds unnecessary system load and terminal flicker for a slowly-evolving situation, while a slower refresh might feel sluggish during a fast-moving critical incident; making it configurable lets the person running the dashboard tune it to the actual situation.
Real Incident Discussion: What's the single most direct design decision in this project that would have prevented the original "26 windows, no shared view" problem during that incident bridge call?
The continuous refresh loop itself, displayed on one shared screen — instead of six engineers each independently tabbing between fragmented individual log windows, the entire bridge call would have been looking at the exact same, automatically current, single source of truth throughout the incident.
