Apache Monitoring

A marketing campaign drove a traffic spike, every Apache worker filled up, and new connections queued silently while the server itself looked perfectly "up."

📖 The Story — Every Worker Busy, Nothing Obviously Wrong

A marketing push drove a sudden surge of traffic to NovaTrust's online banking portal login page. Apache's process was running, the port was listening, CPU and memory on the web server were within normal range — every check built in Projects 1 through 14 would have reported this server healthy. But every single Apache worker slot was busy handling slow, backed-up requests, and new connections were queuing invisibly until they eventually timed out for real customers trying to log in.

Priya's assignment: "Apache has its own internal capacity — worker slots — completely separate from CPU or memory. I want to know exactly how many workers are busy versus idle, as a percentage of our configured maximum, and I want our request rate tracked over time so a traffic spike is visible as a trend, not just discovered after it's already maxed us out."

We're now over halfway through this masterclass — and this project applies nearly everything so far (thresholds, rate-of-change math, composite verdicts) to a completely new, web-tier-specific signal.
🔁 Reinforced from Projects 1–14
Tiered WARN/CRITICAL classification, curl with timeouts (Project 8), rate-of-change math using two samples (Project 3's delta pattern), and Project 14's "internal resource saturation, not just responsiveness" philosophy all return here.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Monitor Apache's own internal worker-slot saturation and request rate, independent of OS-level resource metrics already covered.

Customer Requirement

Ops needs early warning when Apache's worker pool is filling up, well before every slot is exhausted and new connections start queuing.

Banking Scenario

NovaTrust's public-facing online banking portal runs behind Apache HTTP Server, configured with a fixed maximum number of worker processes/threads (MaxRequestWorkers).

Existing Manual Process / Prior Automation Gap

Projects 1-14 check OS resources, the database, the application's connection pool, and basic endpoint responsiveness — none of them look inside Apache's own worker scoreboard specifically.

Problems With the Current Gap

Apache can saturate its own configured worker limit while the underlying OS still has plenty of free CPU and memory — a purely Apache-layer capacity problem invisible to every check built so far.

Business Impact & Risk

Worker exhaustion during a traffic spike directly blocks new customer logins and sessions at exactly the moment traffic (and therefore business value) is highest.

Why Automation Is Required

Only continuous, automated querying of Apache's own status interface can reveal worker-slot saturation trending upward, in time to act before a spike becomes an outage.

Solution Design

Query Apache's machine-readable status endpoint, parse the worker scoreboard to calculate busy-worker saturation percentage, and calculate requests-per-second using two time-separated samples of Apache's cumulative request counter.

Project Scope

In scope: worker-slot saturation, request-rate calculation, and configuration-syntax validation before any reload. Out of scope: actual auto-scaling or dynamic worker reconfiguration (a separate capacity-planning initiative).

Expected Outcome

A report showing Apache's current worker saturation percentage and requests-per-second, tiered into HEALTHY/WARNING/CRITICAL, catching a worker-exhaustion trend hours before the original incident's silent queuing began.

🧠 New Bash Concepts for This Project

1. Apache's Machine-Readable Status Endpoint (mod_status, ?auto)

What: With mod_status enabled, http://localhost/server-status?auto returns Apache's internal state as simple Key: Value lines instead of an HTML dashboard.
Why: The ?auto query parameter switches the output to a script-friendly plain-text format — the human-oriented HTML version would require far messier parsing.

2. The Worker Scoreboard String

What: One line of the status output, Scoreboard: ..., is a single string where each character represents one worker slot's current state — _ waiting for a connection, W actively sending a response, R reading a request, . an open/unused slot, and several other single-letter codes.
Why: This compact string is Apache's own real-time snapshot of exactly what every worker slot is doing right now.

3. Counting Characters in a String (grep -o Reinforced)

What: echo "$scoreboard" | grep -o "W" | wc -l counts how many W (actively sending/busy) characters appear in the scoreboard string.
Why: This is how we turn the compact scoreboard string into an actual busy-worker count — grep -o (reinforced from Project 8) prints one match per line, and wc -l counts those lines.

4. Total Worker Slots from String Length (${#variable})

What: ${#scoreboard} gives the length of the scoreboard string — which equals the total configured worker slots, since Apache pads the string to exactly that length.
Why: This gives us the denominator for our saturation percentage without needing a separate configuration lookup.

5. Rate Calculation from Two Time-Separated Samples

What: Apache's status page reports a cumulative "Total Accesses" counter that only ever increases. Taking two samples a known number of seconds apart and computing (count2 - count1) / (time2 - time1) gives requests-per-second.
Why: A single snapshot of a cumulative counter tells you nothing about current rate — exactly like Project 3's memory-leak delta, we need two points in time to calculate a meaningful rate of change.

6. Sleeping Between Two Samples Within One Script Run

What: Taking a first sample, sleep-ing for a fixed short interval (e.g., 5 seconds), then taking a second sample — all within the same script execution, rather than relying on comparing against yesterday's state file like Project 3.
Why: Request rate changes far faster than memory usage does — a same-run, seconds-apart pair of samples is appropriate here, whereas Project 3's day-over-day comparison would be far too slow to catch a rapid traffic spike.

7. Validating Configuration Syntax Before Any Reload (apachectl configtest)

What: apachectl configtest (or httpd -t) checks Apache's configuration files for syntax errors without actually reloading or restarting the service.
Why: Before ever triggering a graceful reload (to pick up a config change), confirming the new configuration is syntactically valid prevents accidentally taking down a running web server with a typo.

8. Graceful Reload vs. Full Restart (Conceptual, Reinforced Judgment Call)

What: apachectl graceful reloads configuration while letting in-flight requests finish naturally, as opposed to a hard restart that drops active connections immediately.
Why: Understanding this distinction matters even for a monitoring-focused script, since any related remediation tooling built later must never default to a disruptive hard restart when a graceful option achieves the same configuration update safely.

🧩 Utility Functions

scripts/utils.sh
#!/bin/bash
# =====================================================
# utils.sh - Apache monitoring helper functions
# =====================================================

log_message() {
    local level="$1"; local message="$2"; local timestamp
    timestamp=$(date '+%Y-%m-%d %H:%M:%S')
    echo "[$timestamp] [$level] $message" | tee -a "$LOG_FILE"
}

# ---------- get_status_field ----------
# Purpose: Extract one "Key: Value" field from Apache's ?auto status output
get_status_field() {
    local raw_status="$1"
    local field_name="$2"
    echo "$raw_status" | grep "^${field_name}:" | awk -F': ' '{print $2}' | tr -d '\r'
}

# ---------- fetch_apache_status ----------
fetch_apache_status() {
    curl -s --connect-timeout "$HTTP_CONNECT_TIMEOUT" --max-time "$HTTP_MAX_TIME" "$STATUS_URL" 2>/dev/null
}

# ---------- count_busy_workers ----------
# Purpose: Count worker slots in "busy" states (W=sending, R=reading, ... anything not idle/open)
count_busy_workers() {
    local scoreboard="$1"
    # Busy states in Apache's scoreboard: S(starting) R(reading) W(sending) K(keepalive) L(logging) D(DNS) C(closing) G(graceful)
    echo "$scoreboard" | grep -o '[SRWKLDCG]' | wc -l
}

# ---------- total_worker_slots ----------
total_worker_slots() {
    local scoreboard="$1"
    echo "${#scoreboard}"                              # String-length expansion gives total configured slots
}

# ---------- calculate_request_rate ----------
# Purpose: Given two access counts and two epoch timestamps, return requests/sec (integer)
calculate_request_rate() {
    local count1="$1" time1="$2" count2="$3" time2="$4"
    local delta_count=$(( count2 - count1 ))
    local delta_time=$(( time2 - time1 ))
    [[ "$delta_time" -le 0 ]] && { echo "0"; return; }  # Guard against a zero/negative interval
    echo $(( delta_count / delta_time ))
}

Line-by-Line Highlights

  • grep "^${field_name}:" — anchors the match to the start of the line specifically, so a field name that happens to be a substring of another field's name (e.g., Total Accesses vs Total kBytes) isn't accidentally matched.
  • tr -d '\r' — strips a trailing carriage-return character that can appear depending on how the status module or web server formats its output, which would otherwise silently corrupt numeric comparisons later.
  • grep -o '[SRWKLDCG]' | wc -l — the character class matches any one of Apache's several "worker is doing something" state letters, counting all of them as busy, distinct from _ (waiting/idle) and . (open/unused slot).
  • ${#scoreboard} — a length expansion, not a value expansion; this is a different syntax from anything used so far in the course and worth calling out explicitly as new.
  • [[ "$delta_time" -le 0 ]] && { echo "0"; return; } — a defensive guard against a division by zero (or negative, in the rare case of clock adjustment) that would otherwise crash the script's arithmetic.

🩺 Main Script

scripts/apache_monitor.sh
#!/bin/bash
# =====================================================================
# apache_monitor.sh
# NovaTrust Bank - Apache Worker Saturation & Request Rate Monitor
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"
source "$SCRIPT_DIR/../config/apache_monitor.conf"

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/apache_monitor_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Apache monitor run finished."' EXIT

log_message "INFO" "=== Starting Apache health check ==="

# ---------- Sample 1 ----------
STATUS_1=$(fetch_apache_status)
if [[ -z "$STATUS_1" ]]; then
    log_message "FAIL" "Could not reach Apache status endpoint: $STATUS_URL"
    exit 2
fi

SCOREBOARD=$(get_status_field "$STATUS_1" "Scoreboard")
ACCESSES_1=$(get_status_field "$STATUS_1" "Total Accesses")
TIME_1=$(date '+%s')

if [[ -z "$SCOREBOARD" || -z "$ACCESSES_1" ]]; then
    log_message "FAIL" "Apache status response missing expected fields - is mod_status enabled correctly?"
    exit 2
fi

BUSY_WORKERS=$(count_busy_workers "$SCOREBOARD")
TOTAL_SLOTS=$(total_worker_slots "$SCOREBOARD")
SATURATION_PCT=$(( BUSY_WORKERS * 100 / TOTAL_SLOTS ))

# ---------- Sample 2 (after a short, deliberate delay) ----------
sleep "$SAMPLE_INTERVAL_SECONDS"

STATUS_2=$(fetch_apache_status)
ACCESSES_2=$(get_status_field "$STATUS_2" "Total Accesses")
TIME_2=$(date '+%s')

REQUEST_RATE=$(calculate_request_rate "$ACCESSES_1" "$TIME_1" "$ACCESSES_2" "$TIME_2")

OVERALL_EXIT=0

# ---------- Classify worker saturation ----------
if [[ "$SATURATION_PCT" -ge "$SATURATION_CRITICAL_PCT" ]]; then
    log_message "FAIL" "Worker saturation CRITICAL: ${SATURATION_PCT}% ($BUSY_WORKERS/$TOTAL_SLOTS busy)"
    OVERALL_EXIT=2
elif [[ "$SATURATION_PCT" -ge "$SATURATION_WARN_PCT" ]]; then
    log_message "WARN" "Worker saturation WARNING: ${SATURATION_PCT}% ($BUSY_WORKERS/$TOTAL_SLOTS busy)"
    [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
else
    log_message "PASS" "Worker saturation healthy: ${SATURATION_PCT}% ($BUSY_WORKERS/$TOTAL_SLOTS busy)"
fi

# ---------- Classify request rate ----------
if [[ "$REQUEST_RATE" -ge "$RATE_CRITICAL_PER_SEC" ]]; then
    log_message "FAIL" "Request rate CRITICAL: ${REQUEST_RATE} req/sec"
    OVERALL_EXIT=2
elif [[ "$REQUEST_RATE" -ge "$RATE_WARN_PER_SEC" ]]; then
    log_message "WARN" "Request rate elevated: ${REQUEST_RATE} req/sec"
    [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
else
    log_message "PASS" "Request rate normal: ${REQUEST_RATE} req/sec"
fi

log_message "INFO" "=== Apache health check complete ==="
exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
TIME_1=$(date '+%s') immediately after capturing ACCESSES_1Recording the timestamp as close as possible to the counter sample keeps the rate calculation accurate — any delay between reading the counter and recording the time would introduce error into the eventual rate.
sleep "$SAMPLE_INTERVAL_SECONDS"A deliberate pause between two samples within the same script run — the entire point is measuring change over a known, controlled interval, similar in spirit to Project 3's day-over-day comparison but operating on a scale of seconds instead of days.
SATURATION_PCT=$(( BUSY_WORKERS * 100 / TOTAL_SLOTS ))The same multiply-before-divide integer arithmetic pattern used since Project 13, now applied to worker counts.
Two independent classification blocks (saturation, then rate)Each metric gets its own tier check and can independently escalate OVERALL_EXIT — consistent with every other project's principle of never letting one healthy signal mask another unhealthy one.

# NovaTrust Bank - Apache Monitoring

## Requirements
- mod_status enabled in Apache configuration
- /server-status restricted to localhost/internal access only (SECURITY REQUIREMENT)

## Usage
    ./scripts/apache_monitor.sh

## What Gets Checked
1. Worker saturation % (busy workers / total configured slots, from the scoreboard string)
2. Request rate (requests/sec, calculated from two samples taken 5 seconds apart)

## Exit Codes
    0 = Both signals healthy
    1 = Either signal at WARNING
    2 = Either signal at CRITICAL, or the status endpoint was unreachable

🔄 What Happens Internally

  1. Two genuinely separate HTTP requests to the same status endpoint, deliberately spaced by sleep — this is what turns a static counter into a meaningful rate measurement.
  2. The scoreboard string is parsed entirely within Bash's own process, using grep -o and string-length expansion — no external Apache-specific tooling is required beyond the curl call itself.
  3. Worker saturation and request rate are calculated from two different parts of the same status response (the scoreboard for saturation, the Total Accesses counter for rate) — one HTTP call per sample serves both purposes.
  4. Every threshold comparison follows the identical multiply-before-divide, tiered classification pattern established since Project 1 — by Project 15, this structure should feel completely familiar even applied to a brand-new metric domain.

🛡️ Production Best Practices

Restrict Status Endpoints to Internal Access

/server-status reveals operational detail that should never be reachable from the public internet — always gate it to localhost or an internal monitoring network.

Rate Requires Two Points in Time

A cumulative counter alone tells you nothing about current activity — always pair it with a timestamp and a second sample to calculate a meaningful rate.

Check the Web Server's Own Limits, Not Just the OS

Apache's worker-slot ceiling is a real, separate constraint from OS-level CPU/memory — a fully healthy OS can still be running a fully saturated web server.

Validate Config Before Any Reload

apachectl configtest before graceful or restart prevents a syntax typo from taking down a running, healthy web server.

Guard Against Counter Resets

A cumulative counter that resets (service restart) can produce a nonsensical negative rate if not explicitly checked for — defend against this exact edge case.

Independent Tiers for Independent Metrics

Worker saturation and request rate are related but distinct signals — classify and escalate each on its own, combining only at the final composite verdict.

🎤 Interview Preparation

Scenario: Worker saturation shows 95% but request rate looks completely normal. What could explain this combination?
A small number of requests are likely taking an unusually long time to complete (perhaps a slow backend dependency, like the database from Project 7 or the connection pool from Project 14) — holding workers busy for far longer than usual per request, without necessarily a high volume of new incoming requests.
Production Support: Request rate suddenly shows as a large negative number. What's the most likely cause?
Apache was restarted between the two samples within the same script run, resetting its cumulative Total Accesses counter back toward zero — the fix is explicitly detecting count2 < count1 and treating it as a reset event rather than a valid (impossible) negative rate.
Shell Scripting: Why use ${#scoreboard} instead of looking up MaxRequestWorkers directly from Apache's configuration file?
The scoreboard string's length is guaranteed by Apache itself to equal the actual currently-configured worker limit at runtime, sourced directly from the live process rather than requiring the script to separately parse a configuration file that could be stale, overridden, or in a different location per environment.
Troubleshooting: The busy-worker count seems too low compared to what "top" shows for Apache's actual process/thread activity. What might be missed?
Double-check the character class used in count_busy_workers actually covers every state code your specific Apache version and MPM (worker, event, or prefork) considers "busy" — different MPMs can report slightly different scoreboard codes, and an incomplete character class would undercount.
Manager Round: Why measure request rate over a 5-second window instead of using a full minute for a smoother average?
A shorter window is more responsive to a sudden spike (closer to real-time), at the cost of more noise/variance between individual runs; a full-minute window would smooth out noise but also react more slowly to a fast-developing surge — the right tradeoff depends on how quickly you need to detect and react to a spike.
Architecture: Why check Apache's own worker saturation as a distinct project from Project 14's middleware connection-pool check?
They represent genuinely different layers and different resource types — Apache's worker slots are a web-server-tier concern about handling incoming HTTP connections, while Project 14's connection pool is an application-tier concern about the app's own database access; a problem in either can occur completely independently of the other.
Best Practice: Why must /server-status be restricted to internal access only?
The endpoint reveals real-time operational details (request patterns, worker counts, potentially client IP information) that could aid an attacker in understanding server load and behavior — this is sensitive operational telemetry, not something appropriate for public exposure.
Real Incident Discussion: What's the one design decision in this project that most directly would have caught the marketing-driven traffic spike before every worker was exhausted?
Continuously tracking worker saturation as a percentage against a WARNING threshold well below 100% — the spike would have crossed the 70% WARNING tier with meaningful advance notice, giving Ops time to react (e.g., temporarily raising MaxRequestWorkers or engaging a CDN/rate-limiting response) before workers were fully exhausted.
