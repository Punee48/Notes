Memory Monitoring & Trend Detection

Catching a slow memory leak in the NEFT Payment Gateway before it becomes a 2 AM outage — by comparing today's reading against yesterday's, not just a single snapshot.

🎯 Level: Intermediate 🧠 New Concepts: 7 🏗️ Environment: Linux / WSL + SSH ⏱️ Duration: 2–3 hrs

📖 The Story — The Leak Nobody Saw Coming

Three weeks ago, the NEFT Payment Gateway service crashed at 2:14 AM. The post-incident review showed memory usage crept from 40% to 96% over three days — slowly enough that no single health check ever crossed the alert threshold until it was already too late.

In today's stand-up, Priya says: "Our disk and health checks are solid, but they're both just snapshots — a single point in time. A leak doesn't show up in one reading; it shows up as a trend. I want memory monitoring that remembers yesterday's number and tells us if today's number is climbing suspiciously, even while it's still technically under the WARNING threshold."

This is the first time our script needs to remember something between runs — a new kind of problem.
🔁 Reinforced from Projects 1 & 2
SSH-with-timeout, flock locking, config-driven thresholds, and the consolidated report pattern all carry forward unchanged.

🏛️ Business Requirement & Banking Scenario

Business Requirement

Detect gradually rising memory usage on Core Banking servers before it crosses a critical threshold, not only after.

Customer Requirement

Ops wants an early "this is climbing" signal distinct from the existing "this is already critical" signal.

Banking Scenario

The NEFT Payment Gateway and other Core Banking services run as long-lived processes that, under certain code paths, leak memory slowly over days rather than failing suddenly.

Existing Manual Process

None — memory was only checked reactively, after a service was already degraded or had crashed.

Problems with a Snapshot-Only Approach

A single reading of "62% used" tells you nothing about direction — 62% steady is fine, 62% after climbing from 40% in two days is a five-alarm fire.

Business Impact & Risk

Unplanned NEFT/RTGS outages have direct regulatory reporting implications and erode customer trust in real-time payments.

Why Automation Is Required

A human cannot mentally track 200 servers' day-over-day memory trend from memory (no pun intended) — the script must persist yesterday's reading and do the comparison itself.

Solution Design

Each run reads current memory usage, looks up the most recent previous reading from a small per-host state file, calculates the change, flags a "LEAK SUSPECTED" condition on a large day-over-day jump, then records today's reading for tomorrow's comparison.

Project Scope

In scope: memory usage snapshot, historical state persistence per host, day-over-day delta calculation, and leak-suspected flagging. Out of scope: automatic remediation or process restarts (a future project).

Expected Outcome

A report that shows, per host: current memory %, yesterday's memory %, the delta, and a clear status including a new LEAK_SUSPECTED flag when the jump is abnormally large.

🧠 New Bash Concepts for This Project

1. Persisting State Between Script Runs

What: A plain text file, one per host, that the script appends to on every run and reads from before appending.
Why: Bash scripts are normally stateless — every run starts fresh. To detect a trend, we must deliberately save data from today so tomorrow's run can read it.
Production example: state/corebanking-prod-01.state holds lines like 2026-07-24:61, one per day.
Best practice: Keep state files append-only and simple (plain text, one fact per line) — resist the urge to invent a complex format when you don't need one yet.

2. Floating-Point Math with bc

What: Bash's built-in arithmetic ((( )), $(( ))) is integer-only. bc is an external calculator we can pipe expressions into for decimal math.
Why: A delta like "usage rose by 12.5 percentage points" needs decimal precision that native Bash arithmetic cannot give us.
Example: echo "$TODAY - $YESTERDAY" | bc
Common mistake: Forgetting that bc's result is text, not automatically an integer — comparing it with [[ -ge ]] will fail on a decimal value; use bc itself for the comparison too, e.g. (( $(echo "$DELTA >= 10" | bc) )).

3. Date Arithmetic (date -d)

What: GNU date can compute relative dates, e.g. date -d "yesterday" '+%Y-%m-%d'.
Why: To find "yesterday's reading," we first need to reliably compute what "yesterday" means in YYYY-MM-DD form, matching how we store state.
Common mistake: Assuming date -d flags work identically on macOS — BSD date has different syntax; our scripts target Linux production servers, so this is safe here, but worth knowing if testing locally on a Mac.

4. Grabbing "the Last Line" of a Growing File (tail -n 1)

What: tail -n 1 file returns only the final line — the most recent reading, since we always append.
Why: We don't want the very first historical reading, we want the most recent one before today.

5. Regex Matching with [[ =~ ]]

What: Bash's built-in regular-expression test operator, e.g. [[ "$line" =~ ^([0-9]{4}-[0-9]{2}-[0-9]{2}):([0-9]+)$ ]].
Why: Before trusting a state file's line, we validate its shape — a corrupted or hand-edited line should never crash our date/number parsing.
Internal working: On a match, Bash populates the BASH_REMATCH array with the whole match and each capture group.
Best practice: Always validate external/persisted data before using it in arithmetic — never assume a file you wrote yesterday is still exactly the shape you expect today.

6. Pruning Old Files with find ... -mtime

What: find state/ -name "*.state" -mtime +30 -delete finds and removes files not modified in the last 30 days.
Why: Without pruning, state files (and their line counts) grow forever — small at 200 servers, but still a hygiene practice worth building correctly from day one.
Common mistake: Running -delete without first testing the same find command without -delete to confirm exactly which files match.

7. Here-Strings (<<<)

What: Feeds a string directly to a command's stdin without needing echo | command, e.g. bc <<< "$TODAY - $YESTERDAY".
Why: Slightly cleaner and marginally more efficient than piping an echo output into a command, for short one-line inputs.

🧩 Utility Functions (Extended)

scripts/utils.sh (additions)
# ---------- get_remote_memory_usage ----------
# Purpose: Return memory usage % (integer) for a remote host
get_remote_memory_usage() {
    local host="$1"
    timeout "$SSH_COMMAND_TIMEOUT" ssh -q -o BatchMode=yes -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "$SSH_USER@$host" "free | awk '/Mem:/ {printf \"%.0f\", (\$3/\$2)*100}'"
}

# ---------- get_previous_reading ----------
# Purpose: Return the most recent PREVIOUS memory reading recorded for a host, or empty if none exists
get_previous_reading() {
    local host="$1"
    local state_file="$STATE_DIR/${host}.state"
    [[ -f "$state_file" ]] || { echo ""; return; }      # No history yet -> return empty, not an error

    local last_line
    last_line=$(tail -n 1 "$state_file")

    # Validate the line's shape before trusting it: YYYY-MM-DD:NN
    if [[ "$last_line" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}:([0-9]+)$ ]]; then
        echo "${BASH_REMATCH[1]}"                        # The captured numeric group only
    else
        echo ""                                           # Corrupted/unexpected line -> treat as no history
    fi
}

# ---------- record_reading ----------
# Purpose: Append today's reading for a host to its state file
record_reading() {
    local host="$1"
    local pct="$2"
    local state_file="$STATE_DIR/${host}.state"
    mkdir -p "$STATE_DIR"
    echo "$(date '+%Y-%m-%d'):${pct}" >> "$state_file"    # Always append, never overwrite
}

# ---------- calculate_delta ----------
# Purpose: Return (today - yesterday) as a plain integer using bc for safety, "" if no previous value
calculate_delta() {
    local today="$1"
    local previous="$2"
    [[ -z "$previous" ]] && { echo ""; return; }
    bc <<< "$today - $previous"                            # Here-string feeds the expression straight into bc
}

# ---------- prune_old_state_files ----------
# Purpose: Delete state files that haven't been modified in STATE_RETENTION_DAYS
prune_old_state_files() {
    find "$STATE_DIR" -name "*.state" -mtime +"$STATE_RETENTION_DAYS" -delete
}

Line-by-Line Highlights

  • [[ -f "$state_file" ]] || { echo ""; return; } — the "no history yet" case is treated as a normal, expected outcome (a new host), not an error — this satisfies AC4 from our Agile backlog.
  • [[ "$last_line" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}:([0-9]+)$ ]] — validates the whole line matches YYYY-MM-DD:digits exactly before we trust it; BASH_REMATCH[1] is the first parenthesized group — the percentage.
  • bc <<< "$today - $previous" — a here-string; equivalent to echo "$today - $previous" | bc but without spawning an extra echo process.
  • find "$STATE_DIR" -name "*.state" -mtime +"$STATE_RETENTION_DAYS" -delete — -mtime +30 means "last modified more than 30 days ago"; combined with -delete, matching files are removed directly by find itself.

🩺 Main Script

scripts/memory_monitor.sh
#!/bin/bash
# =====================================================================
# memory_monitor.sh
# NovaTrust Bank - Trend-Aware Memory Monitor
# =====================================================================

set -uo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
source "$SCRIPT_DIR/utils.sh"

ENVIRONMENT="prod"
while getopts "e:h" opt; do
    case $opt in
        e) ENVIRONMENT="$OPTARG" ;;
        h) echo "Usage: $0 -e [prod|uat]"; exit 0 ;;
        *) echo "Invalid option. Usage: $0 -e [prod|uat]"; exit 1 ;;
    esac
done

source "$SCRIPT_DIR/../config/memory_monitor.conf"
HOST_FILE="$SCRIPT_DIR/../config/servers_${ENVIRONMENT}.txt"
STATE_DIR="$SCRIPT_DIR/$STATE_DIR"                 # Resolve relative path against script location

[[ -f "$HOST_FILE" ]] || { echo "ERROR: Host file not found: $HOST_FILE" >&2; exit 1; }

TODAY=$(date '+%Y%m%d')
LOG_FILE="$SCRIPT_DIR/$LOG_DIR/memory_monitor_${TODAY}.log"
mkdir -p "$(dirname "$LOG_FILE")" "$STATE_DIR"

exec 200>"$LOCK_FILE"
flock -n 200 || { log_message "WARN" "Another instance is already running. Exiting."; exit 0; }
trap 'log_message "INFO" "Memory monitor run finished for environment: $ENVIRONMENT"' EXIT

log_message "INFO" "=== Starting memory monitor for environment: $ENVIRONMENT ==="

OVERALL_EXIT=0
HEALTHY=0; WARNING=0; CRITICAL=0; LEAKS=0; UNREACHABLE=0

while IFS= read -r host; do
    [[ -z "$host" || "$host" == \#* ]] && continue

    if ! check_host_reachable "$host"; then
        log_message "FAIL" "$host is UNREACHABLE"
        ((UNREACHABLE++))
        OVERALL_EXIT=2
        continue
    fi

    CURRENT=$(get_remote_memory_usage "$host")
    if [[ -z "$CURRENT" ]]; then
        log_message "WARN" "$host returned no memory data"
        continue
    fi

    PREVIOUS=$(get_previous_reading "$host")
    DELTA=$(calculate_delta "$CURRENT" "$PREVIOUS")

    LEAK_FLAG=""
    if [[ -n "$DELTA" ]] && (( $(echo "$DELTA >= $LEAK_DELTA_THRESHOLD" | bc) )); then
        LEAK_FLAG=" [LEAK_SUSPECTED, +${DELTA}pts vs yesterday]"
        ((LEAKS++))
    fi

    if [[ "$CURRENT" -ge "$MEM_FAIL_THRESHOLD" ]]; then
        STATUS="CRITICAL"; ((CRITICAL++)); OVERALL_EXIT=2
    elif [[ "$CURRENT" -ge "$MEM_WARN_THRESHOLD" ]]; then
        STATUS="WARNING"; ((WARNING++)); [[ $OVERALL_EXIT -lt 1 ]] && OVERALL_EXIT=1
    else
        STATUS="HEALTHY"; ((HEALTHY++))
    fi

    if [[ -z "$PREVIOUS" ]]; then
        log_message "$STATUS" "$host: ${CURRENT}% (no prior history - baseline recorded)"
    else
        log_message "$STATUS" "$host: ${CURRENT}% (yesterday: ${PREVIOUS}%, delta: ${DELTA}pts)${LEAK_FLAG}"
    fi

    record_reading "$host" "$CURRENT"               # Always record today's value, win or lose, for tomorrow's comparison

done < "$HOST_FILE"

prune_old_state_files                                # Housekeeping: drop state files untouched for 30+ days

log_message "INFO" "=== SUMMARY ==="
log_message "INFO" "Healthy: $HEALTHY | Warning: $WARNING | Critical: $CRITICAL | Leak Suspected: $LEAKS | Unreachable: $UNREACHABLE"

exit $OVERALL_EXIT

Every Line, Explained

LineExplanation
STATE_DIR="$SCRIPT_DIR/$STATE_DIR"The config file defines STATE_DIR as a relative path (../state); we re-anchor it against the script's own location so the script works no matter which directory it's launched from.
DELTA=$(calculate_delta "$CURRENT" "$PREVIOUS")Returns empty string if there's no previous reading (first-ever run for that host) — this is the graceful "baseline" path required by AC4.
(( $(echo "$DELTA >= $LEAK_DELTA_THRESHOLD" | bc) ))bc prints 1 for true / 0 for false; wrapping that result in (( )) turns it back into a Bash truthy/falsy test.
record_reading "$host" "$CURRENT"Runs unconditionally at the end of every host's checks — even a CRITICAL host still needs today's value saved so tomorrow's delta calculation works.
prune_old_state_filesCalled once per script run, after all hosts are processed — simple, periodic housekeeping rather than a separate scheduled job.

## Usage

## Exit Codes
    0 = All hosts healthy
    1 = At least one WARNING
    2 = At least one CRITICAL or UNREACHABLE host

🔄 What Happens Internally

  1. State read happens before state write in every iteration — we must capture "yesterday" before today's value overwrites what "most recent" means.
  2. bc runs as a genuinely separate process spawned via the here-string; its stdout is captured back into our variable through command substitution.
  3. Regex validation via BASH_REMATCH happens entirely inside Bash's own process — no external grep call needed for this check.
  4. record_reading always executes regardless of a host's status this run, ensuring tomorrow's script always has a "yesterday" to compare against.
  5. Pruning runs once, after the loop, not per-host, since it's a directory-wide operation rather than a per-host concern.

🛡️ Production Best Practices

Never Trust Persisted Data Blindly

Always validate a state file's line shape (regex) before doing arithmetic on it — files get corrupted, truncated, or hand-edited.

Graceful First-Run Behavior

A brand-new host with no history must not error — it should establish a baseline silently.

Append-Only History

Never overwrite a state file — always append, so history for post-incident review is preserved.

Housekeeping Is Part of the Script

Retention/pruning logic should ship with the monitoring feature itself, not be left as a "someone will clean this up later" task.

Separate Signals, Separate Meaning

Absolute threshold breaches and trend-based leak suspicion are different signals and should never be silently merged into one status.

Use the Right Tool for the Math

Reach for bc (or awk) the moment decimals are involved — forcing decimal math through integer-only Bash arithmetic produces silently wrong results.

🎤 Interview Preparation

Scenario: A host shows LEAK_SUSPECTED every single day, even though memory always drops back down at night. What's likely wrong?
The check likely runs at a time of day when memory is naturally at its daily peak (e.g. right after a batch job), making day-over-day comparisons at the same check-time look artificially alarming — the fix is ensuring consistent time-of-day sampling or comparing against a multi-day baseline instead of a single prior point.
Production Support: The script errors out on a newly provisioned server that was never checked before. What edge case was missed?
The "no prior state file" case wasn't handled gracefully — in our design this is explicitly covered by get_previous_reading returning an empty string rather than erroring, which is exactly the kind of edge case AC4 exists to catch.
Shell Scripting: Why can't you just use (( )) for the delta calculation?
(( )) and $(( )) only support integer arithmetic in Bash — any decimal precision needed (or even just safety margin in comparisons) requires an external tool like bc or awk.
Troubleshooting: State files are growing every day but delta calculations always come back empty. Why?
Most likely the regex validation in get_previous_reading is failing against the actual line format being written — check for an extra trailing space, a wrong date format, or a locale-dependent date output format mismatch.
Manager Round: How do you decide the leak threshold of 10 percentage points isn't too sensitive or too loose?
Start with a value informed by the actual incident (the NEFT leak crossed roughly 18 points/day before it crashed), then tune down false positives over a few weeks of real data — this is a config value specifically so it can be tuned without a code change.
Architecture: Why store state as flat per-host text files instead of a database?
At current scale (200 hosts, one line per day) a database adds operational overhead without real benefit; flat files are simple, auditable, grep-able, and need no additional infrastructure — a database becomes worth it at much higher scale or query complexity.
Best Practice: Why record today's reading even for a CRITICAL host?
Skipping the record step for unhealthy hosts would break tomorrow's delta calculation entirely for exactly the hosts we most need to keep tracking — the recording step must be unconditional.
Real Incident Discussion: What single design decision in this project would have caught the original NEFT Gateway leak three days earlier?
The day-over-day LEAK_SUSPECTED flag itself — the original incident stayed under the absolute WARNING threshold for two of the three days, meaning only a trend-based check (not a snapshot threshold) would have surfaced it early.
