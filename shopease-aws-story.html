Chapter 1

Laying the Foundation
VPC, Subnets, Routing, Internet Gateway, NAT Gateway, Elastic IP, Security Groups, NACL, VPC Peering

📍 Pune, 2024. A coffee shop. Arjun stares at a blank AWS console. Arjun has a big idea — ShopEase, a marketplace for local artisans to sell handmade crafts online. He's a good developer, but AWS feels like a city he's never been to. He decides to start from the very beginning: setting up his own private piece of the internet.

"Think of it like building a new office complex," his mentor Priya tells him. "First you buy a plot of land — that's your VPC. Then you divide it into floors and rooms — those are your Subnets. You need a main gate — that's the Internet Gateway. A secure back door — that's the NAT Gateway. A fixed address — that's your Elastic IP. And security guards at every floor and building entrance — those are Security Groups and NACLs."

🏙️ VPC Virtual Private Cloud

Arjun creates shopease-vpc with CIDR 10.0.0.0/16 — giving him 65,536 private IP addresses. This is his fenced compound in AWS's massive cloud city.

  • Logically isolated section of the AWS cloud
  • You control IP range, subnets, routing, gateways
  • Spans all AZs in a region; spans multiple AZs via subnets
🏗️ AnalogyBuying a private plot of land in a city (AWS Region). The walls (VPC boundary) are invisible to others.

🏢 Subnets Public & Private

Arjun divides his VPC: Public Subnet (10.0.1.0/24, Mumbai AZ-a) for web servers, Private Subnet (10.0.2.0/24, Mumbai AZ-b) for databases. Public subnets route to the Internet Gateway.

  • Public subnet: route table has route to IGW (0.0.0.0/0 → igw)
  • Private subnet: no direct internet route — safer for databases
  • Each subnet lives in exactly one AZ

🚪 Internet Gateway IGW

Without this, ShopEase's web servers are completely cut off from buyers. Arjun attaches an IGW to his VPC — now traffic can flow in and out of his public subnet.

  • 1 IGW per VPC; horizontally scaled, redundant, HA
  • Performs NAT for instances with public IPs
  • Route table must point 0.0.0.0/0 → igw-id
🚪 AnalogyThe main electric gate of the office complex. Opens to the public road (internet).

🔒 NAT Gateway NAT GW

Arjun's private-subnet database server needs to download OS updates from the internet. But he doesn't want the internet to reach the DB directly. NAT Gateway lets outbound traffic flow, blocks inbound.

  • Placed in PUBLIC subnet; private subnets route 0.0.0.0/0 → nat-gw
  • Managed by AWS — highly available, scales automatically
  • One per AZ recommended for HA ($0.045/hr + data)
🔒 AnalogyA one-way door at the back of the building. Staff can go out to grab food; delivery can't come in unannounced.

📌 Elastic IP Static IP

Arjun's web server IP keeps changing every time he restarts it. Customers bookmark the IP. He allocates an Elastic IP — now shopease.in always points to the same address, forever.

  • Static public IPv4 address; survives instance stop/start
  • Free if associated with running instance; charged if idle
  • Can be remapped to different instances (fast failover)

🛡️ Security Groups Stateful Firewall

Arjun's web server SG: Allow inbound 80/443 from 0.0.0.0/0, Allow inbound 22 from office IP. Outbound: Allow all. Security Groups are stateful — if you allow inbound, the response automatically goes out.

  • Instance-level; stateful (connection tracked)
  • Allow-only rules (no explicit deny needed — implicit deny)
  • Can reference other SGs (allow traffic from web-sg to db-sg)
🛡️ AnalogyReceptionist at each office door. Remembers who came in; automatically lets them out.

🚧 NACL Network ACL

Someone is hammering Arjun's public subnet with traffic from a malicious IP. Security Groups can't block at subnet level. He adds a NACL DENY rule — the IP is blocked before it even reaches any server.

  • Subnet-level; stateless (each direction evaluated separately)
  • Supports Allow AND Deny rules — ordered by rule number
  • Default NACL allows all; custom NACL denies all by default
🚧 AnalogySecurity gate at the entrance of the entire building complex. Checks everyone entering AND leaving separately.

🔗 VPC Peering Cross-VPC

ShopEase acquires a logistics company. Their AWS infrastructure lives in a different VPC. Arjun sets up VPC Peering — a private, direct network connection between two VPCs (even across accounts or regions).

  • 1:1 relationship; not transitive (A↔B, B↔C ≠ A↔C)
  • Traffic stays on AWS backbone — never hits internet
  • Route tables on both sides must be updated
  • No overlapping CIDR blocks allowed
Chapter 2

Hiring the Team
IAM, Dynamic Policies, Roles, PassRole, EC2 Instance Roles, STS

📍 ShopEase has 3 employees. Arjun is sharing his AWS root account credentials via WhatsApp. Priya gasps. "That's like giving every employee the master key to the entire office, including the CEO's safe!" Priya exclaims. She introduces Arjun to IAM — AWS's identity and access management system. "Think of it as your HR department. Every person, service, and script gets their own badge with specific permissions."

Arjun creates separate IAM users for his developer Raj, his designer Meera, and his data analyst Vikram. Each gets exactly the permissions they need — nothing more.

👤 IAM Users, Groups & Policies Identity

Arjun creates User raj-dev, adds him to Group developers, attaches policy AmazonEC2FullAccess to the group. Raj can now manage EC2 — nothing else.

  • Users: individual people or services with long-term credentials
  • Groups: collection of users sharing the same policies
  • Policies: JSON documents defining Allow/Deny on Actions+Resources
  • Max 10 managed policies per user/group
{"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::shopease-*/*"}

📜 Dynamic Policies Conditions

Arjun wants Vikram (analyst) to access S3 — but only from the office IP and only on weekdays. He adds Conditions to the IAM policy.

  • Condition operators: StringEquals, IpAddress, DateGreaterThan
  • AWS global condition keys: aws:SourceIp, aws:RequestedRegion
  • Variable substitution: ${aws:username} for per-user isolation
{"Condition":{"IpAddress":{"aws:SourceIp":"203.x.x.x/32"}}}

🎭 Roles for AWS Services Service Roles

Arjun's EC2 web server needs to read from S3. He could hardcode credentials — but that's a security nightmare. Instead, he creates a Role with S3 read permissions and assigns it to the EC2 instance.

  • Roles have no passwords or access keys — they use temporary tokens
  • Trust policy defines WHO can assume the role
  • Permission policy defines WHAT the role can do
  • Use for: EC2, Lambda, ECS, CloudFormation, etc.
🎭 AnalogyA company uniform. Whoever wears it gets the associated access badge — no personal identity needed.

🔄 IAM PassRole Delegation

Arjun wants his junior dev to create EC2 instances with an IAM role attached. But he doesn't want them to assign admin roles! He grants only iam:PassRole for specific roles.

  • Prevents privilege escalation — you can only pass roles you're authorized to pass
  • Required when creating resources (EC2, Lambda) that need a role
  • Specify resource ARN to restrict which roles can be passed

🖥️ EC2 Instance Roles Profile

Arjun's web server app calls aws s3 cp to download product images. With an Instance Role attached, the EC2 metadata service (169.254.169.254) provides temporary credentials automatically — zero hardcoded secrets.

  • Attached via Instance Profile (wrapper around a role)
  • SDK auto-refreshes credentials before expiry
  • Metadata endpoint: 169.254.169.254/latest/meta-data/iam/

🎫 STS — Security Token Service Temporary Creds

A partner company needs temporary access to ShopEase's S3 bucket for 1 hour. Arjun uses STS AssumeRole to generate temporary credentials that expire automatically.

  • AssumeRole: cross-account or same-account temp access
  • GetSessionToken: MFA-protected access
  • Credentials: AccessKeyId + SecretAccessKey + SessionToken + Expiration
  • Max duration: 15 min to 12 hours depending on role settings
🎫 AnalogyA visitor badge that self-destructs after 1 hour. Security doesn't need to chase anyone out.
Chapter 3

Renting the Machines
EC2 Pricing, Storage, Placement, UserData, EBS, Instance Store, EFS

📍 Arjun's first EC2 bill arrives: ₹47,000. He nearly chokes on his chai. Priya sits down with him. "You left 3 large instances running 24/7 for testing. And you chose the most expensive option." She opens the EC2 pricing page. "AWS has 5 different ways to pay for compute. Choosing wrong is like hiring a taxi for your daily commute when a bus pass would cost 10x less."

Arjun also realizes his servers have no data yet — he hasn't thought about storage. Where does the OS live? Where do uploaded files go? And why does one of his servers lose all data on restart?

💰 EC2 Pricing Models Cost

  • On-Demand: Pay by second. No commitment. Best for unpredictable workloads.
  • Reserved: 1 or 3 year commit. Up to 72% discount. ShopEase's steady web servers.
  • Spot: Bid for unused capacity. Up to 90% off. Can be interrupted! Use for batch jobs.
  • Savings Plans: Commit to $/hr of usage across EC2+Lambda. Flexible on instance type.
  • Dedicated Host: Physical server for you — compliance/licensing needs.

📦 EC2 Storage Types Storage

  • EBS: Network-attached block storage. Persists independently. Most common.
  • Instance Store: Physically attached NVMe. Ephemeral — LOST on stop/terminate. Ultra-fast.
  • EFS: Managed NFS. Shared across multiple instances. Scales automatically.
  • S3: Object storage (not block). Used via API. Not mounted as disk.

📐 EC2 Placement Groups Placement

  • Cluster: All instances in same rack → ultra-low latency. Used for HPC, ML training. Single point of failure risk.
  • Spread: Each instance on separate hardware → max availability. Max 7 per AZ. For critical apps.
  • Partition: Logical partitions on separate racks. Kafka, Cassandra, HDFS — large distributed systems.

🚀 EC2 UserData Bootstrap

Arjun writes a bash script that runs on first boot: installs nginx, pulls ShopEase from GitHub, starts the service. Zero manual login needed.

#!/bin/bash yum update -y yum install -y nginx systemctl start nginx cd /var/www && git clone https://github.com/arjun/shopease
  • Runs as root at launch; only runs ONCE (on first start)
  • Useful for: install packages, pull code, configure env
  • Max 16KB; visible in instance metadata

💾 EBS — Elastic Block Store Persistent

Arjun's web server has a 20GB gp3 EBS volume. When he stops the instance, the volume persists. He can take snapshots (stored in S3) for backup.

  • gp3: General purpose SSD, 3000 IOPS baseline, independent throughput
  • io2: High performance, up to 64,000 IOPS — for databases
  • st1: Throughput-optimized HDD — big data, log processing
  • sc1: Cold HDD — infrequent access archiving
  • EBS volumes are tied to one AZ; snapshots are region-wide

⚡ Instance Store Ephemeral

Arjun uses instance store for temporary image processing — incoming raw photos go here, get resized, then moved to S3. Blazing fast NVMe speeds.

  • Physically attached to host machine — lowest latency possible
  • Data LOST on: stop, terminate, hardware failure
  • Cannot be detached or moved to another instance
  • Perfect for: buffers, caches, temp data, scratch space

📂 EFS — Elastic File System Shared NFS

ShopEase has 5 web servers, all needing to serve the same user-uploaded product images. Arjun mounts EFS on all 5 — they all read/write the same filesystem simultaneously.

  • NFS protocol; works with Linux only (not Windows)
  • Scales automatically to petabytes; pay per GB used
  • Multi-AZ: data replicated across multiple AZs
  • Storage classes: Standard and Infrequent Access (EFS-IA, cheaper)
Chapter 4

The Infinite Warehouse
S3 Storage Classes, Versioning, ACL, Policies, Static Hosting, Encryption, Pre-signed URLs, Access Points, Events

📍 ShopEase has 50,000 sellers. Each has 20+ product images. That's 1 million+ files — and growing. Arjun realizes he can't keep storing files on EC2 — it won't scale. Priya introduces S3: "Amazon S3 is the world's most scalable object storage. Think of it as a warehouse with infinite shelves. Every item (object) has a unique address (key), and the warehouse can hold as much as you throw at it — with zero capacity planning."

But soon Arjun has questions: How do you save money as files age? What happens when a file is accidentally deleted? Who can access what? How do you host a website without a server?

🏷️ S3 Storage Classes Cost Tiers

  • Standard: High durability, low latency. Active product images.
  • Standard-IA: Infrequent access. 45-day minimum. Older product photos.
  • One Zone-IA: Single AZ only — 20% cheaper but lower resilience.
  • Glacier Instant: Millis retrieval. Compliance archives with occasional access.
  • Glacier Flexible: 1-12h retrieval. Cheapest for cold archives.
  • Glacier Deep Archive: 12-48h. 7-year financial records. Cheapest storage in AWS.
  • Intelligent-Tiering: Auto-moves objects based on access patterns.

🗂️ S3 Versioning Version Control

A seller accidentally uploads a blank image over their product photo. Without versioning: gone forever. Arjun enables versioning — every PUT creates a new version; DELETE adds a delete marker but keeps old versions.

  • Enabled at bucket level; once enabled, cannot be fully disabled (only suspended)
  • Unversioned bucket: null version ID
  • Lifecycle rules can expire old versions automatically

🔏 S3 ACL & Bucket Policies Access Control

  • Bucket Policy (Resource-based): JSON policy on the bucket. Can allow/deny cross-account access, specific IPs, require MFA delete.
  • ACL (Legacy): Object/bucket level. Pre-defined grants (public-read, etc.). Disable Block Public Access before using.
  • Identity-based: IAM policies on users/roles — "My developers can read from shopease-assets"

🌐 S3 Static Website Hosting No Server

Arjun's marketing team wants a landing page for a Diwali sale campaign. He uploads index.html to S3, enables Static Website Hosting — no EC2, no nginx, no ops. ShopEase serves it from S3 + CloudFront for global speed.

  • Enable in bucket properties; set index and error documents
  • Public bucket policy required for unauthenticated access
  • S3 website endpoint ≠ S3 REST endpoint (different URL format)

🔐 S3 Encryption At Rest

  • SSE-S3 (AES-256): AWS manages everything. Default encryption.
  • SSE-KMS: You manage the key in KMS. Full audit trail. ShopEase uses this for seller PII.
  • SSE-C: You provide the encryption key on every request. AWS doesn't store it.
  • Client-Side: Encrypt before upload; AWS never sees plaintext.
  • In-transit: HTTPS enforced via bucket policy (aws:SecureTransport)

⏱️ Pre-signed URLs Temporary Access

A seller wants to upload a 500MB product video. Arjun's backend generates a pre-signed PUT URL valid for 15 minutes — the seller uploads directly to S3, bypassing Arjun's servers entirely.

  • Works for GET (download) and PUT (upload)
  • URL contains signature of the issuing IAM principal
  • Expiry: 1 second to 7 days (presigned URL for S3)
  • No AWS account needed on the client side

🎯 S3 Access Points Per-Team Access

ShopEase has 3 teams accessing the same bucket: Mobile App, Analytics, Seller Portal. Each gets their own Access Point with a custom policy — simpler than one giant bucket policy.

  • Each access point has its own hostname and policy
  • Can be restricted to a VPC (no internet access)
  • Multi-Region Access Points: route to nearest healthy bucket

📋 S3 Access Logs & Events Audit & Trigger

Access Logs: Every S3 API call logged to another S3 bucket — who downloaded what, when, from where.
S3 Events: New product image uploaded → S3 event → Lambda triggered → image resized → thumbnail stored.

  • Event destinations: Lambda, SQS, SNS
  • Event types: s3:ObjectCreated, s3:ObjectRemoved, s3:Replication
  • Access logs: eventual delivery (not real-time)
Chapter 5

The Diwali Surge
ELB, ALB, NLB, Gateway LB, Sticky Sessions, Auto Scaling Groups

📍 Diwali night. ShopEase goes viral on Instagram. 100,000 users hit the site simultaneously. The single EC2 instance catches fire (metaphorically). Arjun watches the error rate climb on his phone while his relatives enjoy fireworks. 504 Gateway Timeouts. CPU at 100%. Sellers are calling him.

He scrambles to spin up 5 more EC2 instances — but how does traffic get to them? He discovers Load Balancers. And then, "Wait — I have to manually add instances when traffic spikes? Never again." He discovers Auto Scaling Groups.

⚖️ Elastic Load Balancer ELB Overview

Arjun puts an ALB in front of his 5 web servers. Buyers hit the ALB endpoint — ALB distributes traffic evenly. No server gets overwhelmed.

  • Managed service — AWS handles scaling, HA, patching
  • Health checks: removes unhealthy instances from rotation
  • 3 types: ALB (Layer 7), NLB (Layer 4), GLB (Layer 3+4)
  • Cross-zone LB: distribute across all registered targets in all AZs

🔀 ALB — Application Load Balancer Layer 7

ShopEase's ALB routes: /api/* → API servers, /static/* → static servers, /seller/* → seller portal servers. One ALB, three target groups, intelligent routing.

  • Path-based routing: /api → target group A
  • Host-based routing: shop.in vs api.shop.in
  • Header/query-string based routing
  • Supports HTTP/2, WebSocket, gRPC
  • X-Forwarded-For header passes client IP to backend

⚡ NLB — Network Load Balancer Layer 4

ShopEase launches a real-time bidding service for ad placements — microsecond latency needed. NLB handles millions of TCP connections with ultra-low latency.

  • Layer 4 (TCP, UDP, TLS) — no HTTP inspection
  • Handles millions of requests per second
  • Preserves client IP (no X-Forwarded-For needed)
  • Static IP per AZ (or Elastic IP) — useful for whitelisting

🛡️ Gateway Load Balancer Layer 3

ShopEase's enterprise clients require all traffic to pass through third-party firewall appliances before reaching servers. GLB transparently routes ALL traffic through the security appliances first.

  • Deploy/scale/manage third-party network appliances
  • Operates at Layer 3 (IP packets); GENEVE protocol (port 6081)
  • Bump-in-the-wire architecture — transparent inspection

🍪 Sticky Sessions Session Affinity

ShopEase's shopping cart is stored in-memory on the web server. Without sticky sessions, each request might hit a different server — cart disappears. Sticky sessions pin a user to the same instance.

  • Cookie-based: ALB inserts AWSALB cookie; duration configurable
  • App-based: your app's own cookie used for routing
  • Problem: uneven load distribution if one user is very active
  • Better solution: move session to Redis/DynamoDB (stateless backend)

📈 Auto Scaling Groups ASG

Arjun configures: Min=2, Desired=3, Max=10 instances. CPU > 70%? Scale OUT. CPU < 30%? Scale IN. Next Diwali: ASG automatically spins up 9 instances at peak, scales back to 2 by midnight.

  • Launch Template: defines instance config (AMI, type, SG, role)
  • Scaling Policies: Target Tracking, Step, Simple, Scheduled
  • Cooldown period: wait before another scaling action
  • Lifecycle hooks: run scripts during scale-out/in events
  • Integrates with ALB: new instances auto-registered as targets
Chapter 6

Global Speed
CloudFront CDN, Cache Keys, Cache Behavior, Signed URLs, Geo Restriction

📍 ShopEase expands to Dubai and Singapore. Users complain product images take 8 seconds to load. Arjun checks: all images are served from Mumbai. A Dubai user's request travels Mumbai → Dubai → Mumbai → Dubai. 8 seconds is expected! Priya introduces CloudFront — AWS's Content Delivery Network with 450+ edge locations worldwide.

Now Dubai users get images from the Dubai edge cache. Singapore users from Singapore. Mumbai request goes once — then cached for everyone. 200ms instead of 8 seconds.

🌍 CloudFront CDN Edge Delivery

Arjun sets Origin = his S3 bucket. CloudFront distributes to 450+ PoPs globally. First user from Dubai fetches from S3 (cache MISS). Second Dubai user gets it from the Dubai edge (cache HIT — instant).

  • Edge Locations: cache content; Regional Edge Caches: larger intermediate cache
  • Origin can be: S3, ALB, EC2, HTTP server
  • Supports HTTP/HTTPS, HTTP/2, HTTP/3 (QUIC)
  • CloudFront sits in front of WAF, Shield for DDoS protection

🔑 Cache Key & Caching Policies Cache Control

Cache Key defines what makes a unique cached response. Arjun's product API: cache key = URL path + ?category= query parameter. Different categories = different cache entries.

  • Default cache key: URL only
  • Customize: include headers, query strings, cookies
  • Managed policies: CachingOptimized (for S3), CachingDisabled (for APIs)
  • TTL: min/default/max TTL; overridden by Cache-Control headers

🎯 Cache Behaviors Path Routing

One distribution, multiple behaviors: /images/* → Cache 24h from S3, /api/* → No cache, forward to ALB, /static/* → Cache 7 days. Different origins and cache rules per path pattern.

  • Default behavior (*) is the catch-all
  • Precedence order: most specific path wins
  • Per behavior: origin, methods, cache policy, headers to forward

🔒 Signed URLs & Signed Cookies Premium Content

ShopEase launches a premium artisan video tutorial series. Only paid subscribers can watch. Arjun generates a signed URL valid for 2 hours — even if a subscriber shares the URL, it expires soon.

  • Signed URL: one URL for one file. Best for downloadable content.
  • Signed Cookie: covers multiple files. Best for streaming/members area.
  • Signed with CloudFront Key Pair (not S3 pre-signed URL)
  • Trusted Key Groups: manage signing keys without root account

🗺️ Geographic Restriction Geo-blocking

Some ShopEase products (certain textiles) can't be exported due to Indian government regulations. Arjun configures CloudFront to block requests from outside India for those product pages.

  • Allowlist: serve only to listed countries
  • Blocklist: block specific countries, serve to everyone else
  • CloudFront uses IP-to-country database (MaxMind GeoIP)
  • Alternative: third-party geo-blocking with Lambda@Edge for granularity
Chapter 7

The Container Revolution
ECS, ECR, SQS, SNS, EventBridge, Step Functions, SAM

📍 ShopEase has 12 microservices. Deploying them on bare EC2 instances is chaos. "It works on my machine" is said 6 times a day. The engineering team decides to go all-in on Docker containers. Each service gets containerized. But now they need: somewhere to store images (ECR), something to run them (ECS), a way to handle 10,000 simultaneous orders without crashing (SQS), and a way to notify buyers instantly (SNS).

🐳 ECS — Elastic Container Service Containers

Arjun defines a Task Definition for the order-service container (image, CPU, memory, env vars). ECS runs it on either EC2 (you manage) or Fargate (serverless — AWS manages the hosts).

  • Cluster: logical grouping of tasks/services
  • Task Definition: like docker-compose.yml — image, ports, env, volumes
  • Service: keeps N tasks running; integrates with ALB for load balancing
  • Fargate: pay per CPU/RAM per second — no EC2 to manage

🔄 Updating ECS Tasks Rolling Deploy

Raj pushes a new version of order-service. ECS performs a rolling update: starts new tasks → waits for health check to pass → stops old tasks. Zero downtime.

  • Minimum healthy percent: % of tasks to keep running during deploy
  • Maximum percent: burst capacity during deployment
  • Blue/Green via CodeDeploy: traffic shifted gradually
  • Force new deployment: re-pulls same image if using :latest tag

📦 ECR — Elastic Container Registry Docker Registry

ShopEase's Docker images live in ECR — AWS's managed private container registry. No Docker Hub; images stay in the same VPC as ECS. Cross-account access via resource policies.

  • Private registry per account/region; Public Gallery for open images
  • Image scanning: detect OS and package vulnerabilities automatically
  • Lifecycle policies: auto-delete old/untagged images (save costs)
  • Integrated with ECS, EKS, Lambda container images

📬 SQS — Simple Queue Service Decoupling

10,000 orders hit ShopEase in 60 seconds. Instead of all hitting the DB directly, they go into an SQS queue. Order processors pull from the queue at their own pace — no overload, no lost orders.

  • Standard Queue: unlimited throughput, at-least-once delivery, best-effort ordering
  • FIFO Queue: exactly-once processing, strict order, 3,000 msg/s
  • Visibility Timeout: msg hidden while being processed (default 30s)
  • Long polling: wait up to 20s for messages (reduces API calls)

⚙️ SQS Settings & DLQ Configuration

  • Message Retention: 4 days default, max 14 days
  • Delay Queue: delay message delivery up to 15 min
  • Message Size: max 256KB; use S3 for large payloads (Extended Client)
  • Dead Letter Queue: failed messages (maxReceiveCount exceeded) routed to DLQ for investigation
  • DLQ Alarm: CloudWatch alarm on DLQ depth — Arjun gets alerted

📢 SNS — Simple Notification Service Pub/Sub

Order shipped! SNS topic order-shipped fans out simultaneously to: Email (buyer notification), SMS (OTP), Lambda (update order status), SQS (trigger warehouse system).

  • Topic: pub/sub channel. Publishers push; subscribers receive
  • Subscribers: Lambda, SQS, HTTP/S, Email, SMS, Mobile Push
  • Message Filtering: subscribers receive only relevant messages via filter policy
  • FIFO Topics: ordered delivery to FIFO SQS queues

🔀 Amazon EventBridge Event Bus

ShopEase's "seller updated product" event needs to reach: Search Indexer, Recommendation Engine, Audit Logger, Analytics Pipeline. EventBridge routes events to multiple targets based on rules — decoupled and scalable.

  • Default event bus: AWS service events; Custom bus: your app events
  • Rules: event pattern matching → route to target (Lambda, SQS, Step Functions...)
  • Scheduled rules: cron/rate expressions — "run every 5 minutes"
  • Schema Registry: discover and document event structure

🗺️ AWS Step Functions Workflows

ShopEase's order workflow: Verify Payment → Reserve Inventory → Notify Seller → Generate Invoice → Dispatch → Notify Buyer. Each step is a state. Step Functions orchestrates the entire saga with retries and error handling built in.

  • Standard Workflow: exactly-once, long-running (up to 1 year)
  • Express Workflow: at-least-once, high-volume, 5-min max
  • States: Task, Choice, Wait, Parallel, Map, Pass, Fail, Succeed
  • ASL (Amazon States Language): JSON definition of the state machine

The Serverless Kingdom
Lambda in all its forms — Triggers, Layers, Networking, Concurrency, Lambda@Edge

📍 Arjun is tired of managing EC2 instances for tasks that run for 2 seconds every hour. His cloud bill has EC2 charges even when nobody is shopping at 3 AM. Priya shows him AWS Lambda. "Write a function. AWS runs it when triggered. You pay only for the milliseconds it runs. No idle charges." Arjun converts 30% of ShopEase's workload to Lambda in one month.

λ Lambda Sync vs Async Invocation

  • Synchronous: Caller waits for response. API Gateway → Lambda → returns JSON. Errors returned to caller directly.
  • Asynchronous: Event placed in queue, caller gets 202 immediately. Lambda retries on error (up to 2 times). S3, SNS, EventBridge trigger async.
  • SQS event source mapping: Lambda polls queue — neither sync nor async but event-source mapping

📚 Lambda Layers Shared Code

10 Lambda functions all need pandas, Pillow, and the ShopEase internal SDK. Without layers, Arjun zips them into each function (bloated, inconsistent). With layers, the libraries are shared — functions stay tiny.

  • Up to 5 layers per function; max 250MB total unzipped
  • Version-controlled; can be shared across accounts
  • AWS provides managed layers: AWS SDK, Python scientific libs

🔀 Lambda + ALB HTTP Trigger

Instead of API Gateway, ShopEase uses ALB for some internal Lambda endpoints — cheaper for high-volume HTTP traffic. ALB sends HTTP request to Lambda as JSON event; Lambda returns a JSON response object.

  • ALB registers Lambda as a target in a target group
  • Multi-value headers: combine headers/query strings into arrays
  • Healthcheck: Lambda must return 200 for ALB health checks

🔑 Lambda Resource Policies Who Invokes

S3 needs to invoke Arjun's image-resizer Lambda. He grants S3 permission via a resource policy on the Lambda function itself (not IAM user). Similar to S3 bucket policies.

  • Resource-based policy: who can invoke this function
  • Cross-account: grant another account's services permission to invoke
  • Automatically created when adding triggers via console

🌿 Lambda Env Variables Config

DB connection string, API keys, feature flags — stored as environment variables. Encrypted at rest with KMS. Lambda reads them at startup. Change without redeploying code.

  • Encrypted at rest with Lambda service key or custom KMS key
  • Max 4KB of env vars per function
  • Prefer SSM Parameter Store / Secrets Manager for rotation

🏷️ Versions & Aliases Deployment

Arjun publishes Lambda v1, v2, v3. "prod" alias → v3. "canary" alias → 90% v3, 10% v4 (new untested). Gradually shifts weight to v4 as confidence grows — zero-downtime deployment.

  • Versions: immutable snapshots of function code + config
  • $LATEST: mutable working version
  • Aliases: named pointers to versions; support weighted routing
  • Use aliases in permissions instead of ARNs to avoid updates

📮 DLQ & Destinations Error Handling

  • DLQ: On async failure after retries → send event to SQS/SNS DLQ for review
  • Destinations (better): On success → EventBridge/SQS/Lambda. On failure → separate SQS for investigation. More metadata than DLQ.
  • Destinations work for async invocations and event source mappings

🌐 Lambda Networking VPC Access

ShopEase's Lambda needs to query the RDS database (private subnet). Arjun configures Lambda in the VPC — now it can reach private resources. But then: Lambda can't call external APIs anymore!

  • VPC Lambda: runs with an ENI in your subnet; can reach private resources
  • Internet access: VPC Lambda needs a NAT Gateway (same as EC2)
  • ENI cold start: takes ~10s to attach ENI (now improved with Hyperplane)

🔁 Execution Context & /tmp Warm Start

Arjun notices his Lambda connects to DB on first invocation (cold start ~800ms) but subsequent invocations are fast (warm start ~5ms). The execution context is reused — DB connection is cached!

  • Initialize DB connections, load ML models OUTSIDE the handler
  • /tmp: 512MB–10GB ephemeral storage; shared across warm invocations
  • Don't store sensitive data in /tmp — use Secrets Manager

🚦 Concurrency & Limits Scaling

  • Account limit: 1,000 concurrent by default (soft limit; request increase)
  • Reserved Concurrency: Cap a function — ensures quota for critical functions
  • Provisioned Concurrency: Pre-warm N instances — eliminates cold start for latency-sensitive functions
  • Timeout: 15 min max; Memory: 128MB–10GB

🌐 Lambda@Edge & CF Functions Edge Computing

ShopEase personalizes the homepage based on user's country. Lambda@Edge runs at CloudFront edge locations — no round trip to origin. CloudFront Functions (cheaper, faster) handle simple URL rewrites and header manipulation.

  • Lambda@Edge: Triggered at Viewer/Origin Request/Response. Full Lambda runtime. Max 5s.
  • CloudFront Functions: JS only. Sub-millisecond. Header manipulation, URL rewrites, A/B testing.
  • CF Functions are 10x cheaper than Lambda@Edge

📅 Lambda EventBridge Integration Scheduled

ShopEase runs inventory sync every night at 2 AM, generates daily reports every morning at 7 AM. EventBridge Scheduler triggers Lambda on a cron schedule — no EC2 cron jobs needed.

  • Rate: rate(5 minutes), rate(1 day)
  • Cron: cron(0 14 * * ? *) (7 AM IST = 2 AM UTC + 5:30)
  • One-time schedules: EventBridge Scheduler for future specific datetime

The Vault
KMS, Envelope Encryption, Parameter Store, Secrets Manager, ACM, Cognito, WAF

📍 ShopEase's legal team sends a 47-page compliance document. GDPR. PCI-DSS. Data encryption. Access logging. Arjun hasn't slept in three days. "Security isn't optional anymore," says Priya. "You handle payment data, addresses, phone numbers. One breach and ShopEase is done." She walks him through AWS's security arsenal — from encryption keys to bot protection.

🔑 KMS — Key Management Service Encryption

Arjun creates a Customer Managed Key (CMK) for ShopEase. This key encrypts his RDS database, S3 sensitive bucket, and EBS volumes. Every encryption/decryption is logged in CloudTrail.

  • CMK types: AWS Managed (free), Customer Managed (configurable), Customer-provided
  • Key Policies: who can use/manage the key
  • Automatic key rotation: once per year
  • Regional service: keys don't leave the region

🫙 Envelope Encryption KMS Pattern

A 5GB file can't be sent to KMS directly (max 4KB). KMS generates a Data Encryption Key (DEK). DEK encrypts the file. KMS then encrypts the DEK itself. Only the encrypted DEK is stored alongside the file.

  • GenerateDataKey API: returns plaintext DEK + encrypted DEK
  • Encrypt data with plaintext DEK, then discard plaintext DEK
  • To decrypt: call KMS to decrypt encrypted DEK → use DEK to decrypt file
  • Dramatically reduces KMS API calls and cost

🔧 KMS Encryption SDK Client-Side

ShopEase encrypts buyer PAN (payment card number) before it even reaches AWS. Using the AWS Encryption SDK with envelope encryption built-in — AWS never sees plaintext PAN.

  • Language SDKs: Python, Java, JavaScript, C, Go
  • Handles envelope encryption automatically
  • Encrypted message format includes algorithm suite + encrypted DEK
  • Multi-master keys: encrypt with multiple CMKs (disaster recovery)

📋 SSM Parameter Store Config Management

DB hostname, app version, feature flags — non-secret config stored in Parameter Store. Free tier. Lambda reads /shopease/prod/db_host at startup. Change centrally, all Lambdas pick it up.

  • Standard: 10,000 params free, 4KB max, no rotation
  • Advanced: 100KB, parameter policies (TTL), higher throughput
  • SecureString: encrypted with KMS (great for non-rotated secrets)
  • Hierarchical naming: /app/env/param for organization

🤫 Secrets Manager Secrets + Rotation

DB password, third-party API keys — in Secrets Manager. Arjun configures automatic rotation every 30 days. Secrets Manager calls a Lambda to generate a new password and update RDS — zero downtime, zero manual work.

  • Rotation: built-in for RDS, DocumentDB, Redshift; custom Lambda for others
  • Costs $0.40/secret/month (vs Parameter Store free tier)
  • Cross-account access via resource policy
  • Replicate secrets to multiple regions for DR

🔏 ACM — Certificate Manager SSL/TLS

shopease.in needs HTTPS. Arjun requests a free SSL certificate from ACM. CloudFront and ALB use it. ACM auto-renews before expiry. Never manually manage certs again.

  • Free public certificates for ALB, CloudFront, API Gateway
  • Validation: DNS (automatic, preferred) or Email
  • Private CA: for internal services (PKI)
  • Wildcard: *.shopease.in covers all subdomains

👤 Cognito User Pools Authentication

ShopEase buyers register and log in. Cognito User Pool handles: sign-up (email/phone verification), sign-in (JWT tokens), MFA, forgotten passwords, social login (Google/Facebook). Zero auth code written by Arjun's team.

  • Returns: ID Token, Access Token, Refresh Token (JWT)
  • Customizable UI (Hosted UI) or custom UI with Amplify
  • Triggers: Pre/Post authentication Lambda hooks for custom logic
  • Integrates directly with API Gateway as JWT authorizer

🎭 Cognito Identity Pools Authorization

After login, buyers need to upload profile photos directly to S3. Cognito Identity Pool exchanges the JWT token for temporary AWS credentials (STS) — buyer can PUT to s3://shopease-uploads/users/{userId}/* only.

  • Maps authenticated users to IAM roles
  • Supports: Cognito User Pool, Google, Facebook, SAML, OpenID
  • Unauthenticated guest role: allow limited access without login
  • Enhanced vs Basic authflow

🛡️ WAF — Web Application Firewall Protection

ShopEase faces SQL injection attacks, credential stuffing, and web scrapers. WAF sits in front of CloudFront — inspects every request. SQL injection attempt? Blocked. Bot traffic? Rate-limited. India-only product? Geo-blocked.

  • Rules: AWS Managed Rules + custom rules
  • Attach to: CloudFront, ALB, API Gateway, Cognito User Pool
  • Rate-based rules: block IPs exceeding N req/5min
  • Logging: WAF logs to CloudWatch, S3, Kinesis Firehose

Chapter 11

The Data Universe
RDS, Aurora, RDS Proxy, DynamoDB (full), ElastiCache, MemoryDB

📍 ShopEase has 2 million products, 500,000 users, 50,000 daily orders. The single MySQL server is sweating. Arjun's mentor Priya maps out the data landscape: "Not all data is the same. Orders need ACID transactions (RDS). Product catalog needs millisecond reads at any scale (DynamoDB). Hot product data needs microsecond access (ElastiCache). You need the right tool for each job."

🗄️ RDS — Relational Database SQL

ShopEase's order and transaction data in RDS MySQL. Multi-AZ: primary in Mumbai AZ-a, standby in AZ-b — automatic failover in 60 seconds if AZ fails. Read Replicas: 5 read-only copies for analytics queries.

  • Engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server
  • Multi-AZ: synchronous replication; automated failover; for HA
  • Read Replica: async replication; for read scaling; can promote to master
  • Automated backups: daily snapshots + transaction logs (PITR up to 35 days)

⚡ Aurora Cloud-Native DB

Aurora MySQL is 5x faster than regular MySQL. ShopEase migrates critical order tables to Aurora. The storage layer auto-scales from 10GB to 128TB. 6 copies of data across 3 AZs — extreme durability.

  • Aurora Serverless v2: scales from 0.5 to 256 ACUs — no idle costs
  • Global Database: replicate across regions in under 1 second
  • Aurora Cluster: 1 writer + up to 15 read replicas (auto-failover in 30s)
  • Backtrack: rewind DB to any point in last 72h without restore

🔄 RDS Proxy Connection Pooling

ShopEase's 500 Lambda functions each open a DB connection on cold start. RDS gets 500 simultaneous connections — it crashes. RDS Proxy pools connections: 500 Lambdas → 20 actual DB connections. Problem solved.

  • Reduces DB connections by up to 99%
  • Automatic failover: RDS Proxy handles it transparently (no code change)
  • IAM authentication for Lambda → Proxy (no DB credentials in code)
  • Pinning: check for session-level state; can reduce pooling effectiveness

⚡ DynamoDB NoSQL

ShopEase's product catalog (2M items), user sessions, and shopping carts in DynamoDB. Single-digit millisecond reads regardless of whether there are 100 or 100 million items. No schema migration nightmares.

  • Key structure: Partition Key (mandatory) + Sort Key (optional)
  • Items up to 400KB; tables with unlimited items
  • On-demand mode: pay per request; Provisioned: specify RCU/WCU
  • Global Tables: multi-region, active-active replication

📊 DynamoDB Indexes Query Patterns

Products table: PK=ProductId. Query: "all products in Electronics category sorted by price." Impossible with PK alone. Solution: GSI with PK=Category, SK=Price.

  • LSI (Local Secondary Index): Same partition key, alternate sort key. Created at table creation. Strong consistency available.
  • GSI (Global Secondary Index): Any attribute as PK/SK. Created anytime. Eventually consistent only. Has its own RCU/WCU.
  • Max 5 LSIs + 20 GSIs per table

📝 DynamoDB Key APIs Operations

  • GetItem: Single item by PK (+ SK if composite)
  • PutItem: Create or replace item
  • UpdateItem: Modify specific attributes (ADD, SET, REMOVE)
  • DeleteItem: Remove by PK
  • Query: All items with same PK; filter by SK (efficient)
  • Scan: Full table scan — avoid! Expensive and slow
  • BatchGetItem / BatchWriteItem: Up to 25 items per batch
  • TransactGetItems / TransactWriteItems: ACID transactions across items

🔒 DynamoDB Advanced Features Power Features

  • Conditional Writes: "Update stock only IF stock > 0" — prevents overselling
  • Optimistic Locking: version attribute; fails if concurrent update changed it
  • Transactions: All-or-nothing across multiple items/tables (same region)
  • TTL: Set expiry timestamp on items — auto-deleted by DynamoDB. Free! Great for sessions/carts.
  • Streams: Ordered record of item changes → triggers Lambda for CDC patterns

🚀 DynamoDB DAX Microsecond Cache

ShopEase product detail pages call DynamoDB 1,000 times/second during flash sales. With DAX (DynamoDB Accelerator), cached reads take microseconds instead of milliseconds. Compatible with DynamoDB API — no code change needed.

  • In-memory cache cluster; item cache + query cache
  • Write-through: writes go to DynamoDB AND DAX simultaneously
  • TTL: items expire from DAX cache; next read hits DynamoDB
  • For: read-heavy, eventually consistent workloads

⚡ ElastiCache Managed Cache

ShopEase's homepage "featured products" query takes 200ms from DynamoDB. With ElastiCache Redis, it's cached for 5 minutes — 1ms response. Also used for: user sessions, rate limiting, leaderboards.

  • Redis: Rich data structures (lists, sets, sorted sets, hashes). Persistence. Pub/Sub. Cluster mode.
  • Memcached: Simple key-value, multi-threaded, no persistence.
  • Read-through, write-through, lazy loading cache patterns
  • Redis Cluster: auto-sharding across nodes for scale

🧠 MemoryDB for Redis Durable Redis

ShopEase's real-time seller leaderboard (top sellers this week) is stored in Redis sorted sets. But if ElastiCache crashes, the leaderboard is lost. MemoryDB provides Redis with durable, persistent storage — microsecond reads, millisecond writes with durability guarantee.

  • Redis-compatible API — drop-in replacement
  • Data persisted to a distributed transaction log (Multi-AZ)
  • Can be primary database (not just cache)
  • Microsecond read / single-digit ms write latency

The Front Door
API Gateway — REST, WebSocket, Stages, Auth, Caching, CORS, OpenAPI

📍 ShopEase launches a mobile app. 3 frontend teams (iOS, Android, Web) are calling Lambda functions directly, managing auth separately, and duplicating rate limiting code. Priya sighs. "You need a single front door." She introduces API Gateway — the managed API layer that handles routing, auth, rate limiting, caching, and transformation — so backend services stay clean and consistent.

🚪 API Gateway REST API HTTP API

Arjun defines: GET /products → Lambda, POST /orders → Lambda, GET /users/{id} → Lambda. API Gateway handles SSL, request routing, response formatting.

  • REST API: feature-rich, more configuration options, higher cost
  • HTTP API: simpler, 70% cheaper, lower latency — for most use cases
  • Resources: hierarchical URL paths with methods
  • Integration types: Lambda, HTTP, Mock, AWS service, VPC Link

🚦 Stages & Canary Deployment Deployment

API Gateway stages: dev, staging, prod. Each stage can have different throttle limits, caching settings, and Lambda aliases. Canary: route 5% traffic to new stage version, 95% to stable.

  • Stage Variables: like env vars for stages (db endpoint, Lambda alias)
  • Canary release: gradual traffic shifting with easy rollback
  • Deployment: must deploy API after changes — not automatic

🔄 Integration Mapping Transform

The mobile app sends a different JSON format than what Lambda expects. Arjun uses API Gateway Mapping Templates (VTL) to reshape request/response — no Lambda code change needed.

  • Velocity Template Language (VTL) for transformations
  • Request: reshape headers/body before hitting integration
  • Response: reshape Lambda output before returning to client
  • HTTP API: simpler payload format (no VTL needed)

🌐 CORS Cross-Origin

Arjun's React app on shopease.in calls api.shopease.in. Browser blocks it (different origin). He enables CORS on API Gateway: allows shopease.in to call the API, specifying allowed methods and headers.

  • Enable CORS: API Gateway handles OPTIONS preflight automatically
  • Access-Control-Allow-Origin: specific domain or * (avoid in production)
  • Lambda must also set CORS headers in response body
  • HTTP API: simpler built-in CORS configuration

📖 OpenAPI / Swagger API Spec

Arjun defines the entire ShopEase API in an OpenAPI 3.0 YAML file — endpoints, request/response schemas, auth requirements. Import into API Gateway. Auto-generate SDK for mobile teams. Generate documentation site.

  • Import/export: API Gateway ↔ OpenAPI YAML/JSON
  • AWS extensions: x-amazon-apigateway-integration for Lambda
  • Validate request bodies automatically against schema
  • SDK Generation: Java, iOS, Android, JavaScript client SDKs

⚡ Caching API Cache

GET /products/bestsellers is called 10,000 times/minute but changes only every 5 minutes. Arjun enables API Gateway cache (TTL=300s) — Lambda is called once per 5 minutes instead of 10,000 times. 99.99% cost reduction for this endpoint.

  • Cache size: 0.5GB to 237GB; billed per hour
  • Per-method cache enable/disable
  • Cache key: include headers/query strings for varied responses
  • Invalidation: flush on demand or use Cache-Control: max-age=0

🔐 Auth & Authorization Security

  • Cognito Authorizer: Validate Cognito JWT tokens — buyers must be logged in
  • Lambda Authorizer (Token): Custom JWT/OAuth validation — bearer token in header
  • Lambda Authorizer (Request): Auth based on headers, query strings, IP
  • IAM Auth: AWS Signature v4 — for service-to-service calls
  • API Keys: For third-party developer access with usage plans

🔌 WebSocket vs REST API Protocol

ShopEase order tracking: buyer opens order page, wants real-time status updates. REST: poll every 5 seconds (wasteful). WebSocket: persistent connection — server pushes updates the instant status changes.

  • REST: Request-response. Stateless. Good for CRUD operations.
  • WebSocket: Persistent bidirectional. Routes: $connect, $disconnect, custom. Great for live updates, chat, gaming.
  • Connection IDs: API Gateway assigns; backend uses to push messages
  • Backend posts to callback URL to send message to specific client
