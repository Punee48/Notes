Chapter 1 · Before Automation Begins

You are the DevOps engineer who picks this up

It's Monday morning at ShopSphere, a large e-commerce company running four environments — DEV, QA, UAT, PROD — across an AWS estate. You're on the Cloud Automation / DevOps Team. Your job is not "write Ansible." Your job is to make sure that when the Payment Gateway team needs a server, they get exactly what was asked for, safely, repeatably, and with a full audit trail — without a human SSHing into AWS console and clicking buttons.

Right now, at ShopSphere, that request arrives as a ServiceNow ticket. Let's walk through what happens to REQ0012456 before your automation is even allowed to touch AWS — because in real enterprises, this pre-automation process is most of what goes wrong later.

Application Team (Payment Gateway) raises REQ0012456 │ ▼ ServiceNow Catalog Item "Request New Server" │ (structured form — not a free-text email) ▼ Business Approval — Application Owner signs off on cost / need │ ▼ Technical Approval — Infra/Platform Lead checks environment & sizing │ ▼ Change Record Created — CHG0034567 linked to REQ0012456 │ ▼ Ticket routed to Cloud Automation / DevOps Team queue │ ▼ Engineer (you) picks up ticket → this is where the masterclass begins
◆ Concept

A ServiceNow catalog request is a structured web form, not an email or Slack message. Every field — hostname, environment, CPU, memory, region — is captured as data before any human or automation acts on it. This structure is exactly what later becomes your RHAAP Survey (Module 31) and your Ansible extra_vars (Module 10). The form the application team fills in today is the input contract your playbooks will validate in Module 11.

✎ ShopSphere Story

The Payment Team's tech lead, Ananya, files REQ0012456 asking for a DEV app server for a new payments microservice. She doesn't know — and shouldn't need to know — what a VPC or an AMI is. She fills in application name, environment, expected CPU/memory, and port. Everything AWS-specific (VPC ID, subnet, security group, AMI ID) is not her job — that's populated later by your team's automation using environment-standard defaults, which is exactly why Module 2 separates "what the application team provides" from "what the AWS/Network/Security teams provide."

Why enterprises don't just let people request AWS access directly

A beginner's instinct is: "why not just give the Payment Team an AWS console login and let them create their own EC2 instance?" It's worth sitting with why that fails at enterprise scale, because the answer is the entire justification for this masterclass.

✓ Best Practice

Notice the pattern: almost nothing here is really about Ansible syntax. It's about turning "please build me a server" into a repeatable, auditable, least-privilege process. Every module from here forward is really answering one question: how do we make Ananya's request produce the same correct result every single time, with zero manual AWS console steps?

Who owns what, before automation starts

Per the masterclass's Rule 5, every requirement has an owner. For REQ0012456, before RHAAP is even launched:

  • Application Team (Payment Team): application name, environment, expected load/sizing, application port, business justification, cost center.
  • ServiceNow/CMDB Team: the request/change process itself, approval routing, and the eventual CMDB record that gets updated at the end (Module 40).
  • AWS Team: owns the account, the region's VPC/subnet layout, and confirms quota is available — you will look this up, not invent it (Module 5, Module 12).
  • Network Team: owns which subnet and security group are correct for a DEV Payment Gateway workload, and DNS zone design (Module 27).
  • Security Team: owns the hardening baseline, vulnerability scanning cadence, and EDR agent requirements (Modules 17, 21, 25).
  • Cloud Automation / DevOps Team (you): owns turning all of the above into one reliable, idempotent automation run.
⚠ Warning

A very common beginner mistake is designing automation as if the requester (Ananya) will supply AWS-level details like VPC ID or AMI ID. In real enterprises she almost never will, and she shouldn't have to. Your input validation role (Module 11) needs to know the difference between fields a human must supply and fields your automation derives from environment standards — conflating the two is one of the most common causes of failed provisioning runs in production.

LAB vs ENTERPRISE vs RECOMMENDED — how request intake differs by maturity

Lab approach: You SSH to AWS CLI or console yourself, typing values from memory. Fine for learning; fails the moment a second person needs a server.

Enterprise approach (many real environments today): ServiceNow catalog item → manual review → ticket handed to a DevOps engineer who manually triggers a RHAAP Job Template with parameters copied from the ticket. Better, but still has a human transcription step that can introduce typos.

Recommended production approach: ServiceNow catalog item integrates directly with RHAAP's API (or a middleware layer) so an approved ticket automatically launches the correct Workflow Job Template with the ticket's fields passed as extra_vars — no manual retyping, and the ServiceNow ticket number itself becomes a required tag/variable so every AWS resource can be traced back to the request that created it. We build toward this across Modules 30–32.

Module 01 — What Is Server Provisioning?

Foundations · Beginner → Enterprise

1 · Beginner explanation

Provisioning means taking a request for compute ("I need a server") and turning it into a running, usable machine — with an operating system installed, network access configured, and it ready to have software deployed onto it. That's the whole idea. Everything else in this masterclass is really just "provisioning, done properly, at scale, safely."

◆ Concept

Historically, "provisioning a server" meant a person physically racking a machine in a data center. Today, for pay-dev-app01, it means an API call to AWS that creates a virtual machine (an EC2 instance) inside someone else's data center in minutes. The concept hasn't changed — turn a request into a usable machine — but the mechanism has moved from a wrench to an API call, which is precisely why this can be automated with Ansible at all.

2 · Why enterprises need it — the compute spectrum

Not all "compute" is the same, and part of being a senior engineer is knowing which layer of the stack you're being asked to provision, because it changes what "provisioning" means.

LayerWhat it isWho provisions itShopSphere example

Cloud instance (EC2)AWS's hypervisor layer, provisioned via APICloud Automation team (you), via RHAAPpay-dev-app01 — this masterclass's whole subject

✎ ShopSphere Story

Why is Payment Gateway getting a full EC2 instance instead of a container? In this story, Payment Gateway is a legacy-influenced application with strict compliance requirements (PCI-DSS-adjacent controls) that ShopSphere's security team currently mandates run on dedicated, fully-hardened RHEL VMs with host-level EDR and vulnerability scanning — not yet approved for their shared Kubernetes platform. This is a completely realistic enterprise situation: the "right" architecture is often constrained by what security/compliance has approved, not by what's technically newest.

3 · Manual provisioning vs. automated provisioning

MANUAL PROVISIONING Engineer logs into AWS Console │ ▼ Clicks "Launch Instance" — picks AMI, size, VPC, subnet by hand │ ▼ Manually configures security group rules │ ▼ SSHes in, manually installs packages, hardens OS │ ▼ Manually registers DNS, monitoring, backup │ ▼ Result: took 90+ minutes, undocumented, inconsistent with the last 10 servers someone else built AUTOMATED PROVISIONING (RHAAP + Ansible) Engineer launches RHAAP Job Template with ticket's variables │ ▼ Ansible validates input, authenticates to AWS, provisions EC2 │ ▼ Same roles configure disks, harden OS, install agents — every time │ ▼ Result: ~10–15 minutes, fully logged, identical to every other DEV Payment Gateway server ever built
⚠ Warning

A subtle point beginners miss: automation isn't primarily about speed. A skilled engineer can click through the AWS console fast too. Automation's real value is consistency and auditability at the 50th server, not the 1st. If you only ever provision one server, manual is often actually fine. Enterprises automate because they provision hundreds, and because every server must be defensible in a security audit.

4 · The complete server lifecycle (the map for this entire masterclass)

Every module you'll go through maps onto one stage of this lifecycle. Keep coming back to this diagram — it's the spine of the whole curriculum:

Server Request → Requirement Gathering → Approval → Input Validation → AWS Authentication → Network Validation → EC2 Provisioning → Storage Configuration → DNS Registration → Linux Configuration → Security Hardening → Patching → Monitoring Agent → Logging Agent → Security/EDR Agent → Backup Configuration → Vulnerability Scan → Vulnerability Remediation → App Readiness Validation → CMDB Update → Notification → [server lives in production for months/years] → Ongoing Patching → OS Upgrade → Decommissioning

The stages before "EC2 Provisioning" are about process — you just walked through them in Chapter 1. The stages from "EC2 Provisioning" through "CMDB Update" are what Modules 5–32 build in Ansible. Everything after "Notification" is what most beginner tutorials skip entirely — but it's most of a real server's life, and it's why Modules 18–20 and 36 exist.

✓ Best Practice

Experienced engineers judge automation maturity by how much of this full circle is actually automated — not just "can you stand up an EC2 instance." A team that can provision fast but patches manually, or provisions fast but has no automated decommissioning, is going to accumulate cost and security debt. When you describe this project in an interview (Module 41), describing the full lifecycle — not just provisioning — is what signals real production experience.

- name: ...
The leading "-" means this is one item in a YAML list — specifically, one task in a list of tasks. name is a human-readable label for the task. It is not functional — Ansible would run the task without it — but it's what appears in the RHAAP job output log, so engineers reading a failed job at 2am rely entirely on this text to know what broke. A vague name like "run task" is a real production pain point; you'll see this called out again in Module 35 (Troubleshooting).
amazon.aws.ec2_instance:
This is a Fully Qualified Collection Name (FQCN): amazon is the namespace (the vendor/publisher), aws is the collection name (a bundle of related modules), and ec2_instance is the specific module. We cover collections properly in Module 8 and Module 9 (Execution Environments) — for now, just recognize the pattern namespace.collection.module.
◆ Concept — the internal flow you'll see repeated all masterclass

Every single automated action in this project — not just EC2 creation — follows the same chain. Memorizing this chain now will make every later module click faster:

RHAAP Job Template (you click Launch) │ ▼ Execution Environment (a container with Ansible + the right collections + boto3 pre-installed) │ ▼ Ansible Playbook (the .yml file that defines the play) │ ▼ Ansible Role (a reusable, organized set of tasks — e.g. roles/aws_provision) │ ▼ amazon.aws Module (e.g. ec2_instance) — this is Python code, not magic │ ▼ boto3 (AWS's official Python SDK, which the module calls internally) │ ▼ AWS Authentication (credentials resolved — Module 5) │ ▼ AWS API (HTTPS call to AWS's control plane) │ ▼ EC2 Service creates the actual instance │ ▼ Response flows back up → module registers a result variable → RHAAP job output
✕ Troubleshooting — preview

When something fails at 2am, it's almost always failing at one specific link in that chain — most often AWS Authentication (wrong/expired credentials) or the AWS API step (permission denied, quota exceeded, invalid parameter). Module 35 walks through 25+ real incidents; but even now, knowing "which link in the chain broke" is 80% of diagnosing any Ansible/AWS failure. We'll build that muscle deliberately as we go.

Module 02 — Enterprise Requirement Gathering

Foundations · Before You Ever Open Ansible

1 · Beginner explanation

Requirement gathering means writing down, precisely, what "a server" actually needs to mean before you provision it. "Give Payment Gateway a DEV server" is not enough information to build anything — you need a size, an OS, a network location, a security posture, and a set of operational hooks (monitoring, backup, patching) attached to it. Module 01 showed you the ServiceNow ticket for pay-dev-app01; this module breaks that ticket apart into every category of information a production-grade automation actually consumes.

2 · Why enterprises need it

A checklist like this exists because provisioning automation is only as good as its inputs. If your Ansible role assumes a value that was never actually confirmed — say, that a security group already exists — the job fails partway through, in production, in front of an audit. Enterprises write requirement checklists so that every field a playbook will need is known, owned by a specific team, and validated (Module 11) before AWS is ever touched.

◆ Concept

Think of the checklist below as the schema behind the ServiceNow form from Chapter 1, and as a preview of the RHAAP Survey you'll build in Module 31. Every row becomes either a survey question, a group_vars default, or a lookup your automation performs against AWS/CMDB at runtime. Nothing on this list is decorative — each one prevents a specific, real failure mode covered later.

3 · ShopSphere story — turning REQ0012456 into a checklist

Ananya's ticket gave you: application, environment, hostname, OS, CPU/memory, disks, region, port, owner, cost center. That's the business + compute half. As the automation engineer, you now fill in the rest by talking to the AWS, Network, and Security teams — this conversation, done once per environment (not once per server), is what lets Module 12's provisioning role run unattended for the 500th server.

⚠ Warning

Notice how few of these fields Ananya actually typed into ServiceNow in Chapter 1. That's correct and intentional — but it means your automation's group_vars/dev.yml (Module 10) has to carry the DEV-environment defaults for everything else: subnet, security group, KMS key, IAM profile, monitoring index. If those environment defaults are wrong or stale, every server built from them inherits the mistake. This is why Module 11's validation role checks environment-derived values too, not just user-supplied ones.

✓ Best Practice

Keep "requester-supplied" and "environment-derived" fields visibly separate in your documentation and your survey design (Module 31). The moment those two categories blur together, requesters start being asked technical questions they can't answer, and automation starts trusting user input it shouldn't (a real security risk — Module 11 covers input validation for exactly this reason).

☰ Interview Question

"How do you decide what goes in a Survey field versus what's hardcoded in group_vars?" Strong answer: survey fields are anything that legitimately varies per request and the requester can correctly answer (hostname, environment, sizing); group_vars/environment defaults are anything that's a platform standard the requester shouldn't be trusted or expected to specify (VPC, security group, KMS key, IAM profile).

This is why idempotency (Module 13) isn't a nice-to-have; it's what makes this whole architecture safe to partially retry.

Module 04 — RHAAP Architecture

Foundations · What Actually Happens When You Click "Launch"

1 · Beginner explanation

RHAAP (Red Hat Ansible Automation Platform, formerly "AWX/Tower" in its upstream/older branding) is the enterprise control plane for running Ansible. It's not a different automation language — it's the system that stores your credentials securely, controls who can run what, schedules and logs every execution, and packages Ansible into a repeatable, governed service instead of "someone's laptop running ansible-playbook."

2 · Why enterprises need it over plain Ansible CLI

Plain ansible-playbook from a laptopRHAAP
Credentials often sit in local files or shell env varsCredentials stored encrypted, injected at runtime, never visible in logs (Module 29)
Anyone with the repo can run anything against anythingRBAC — Organizations/Teams control who can launch which Job Template against which environment
No consistent record of who ran what, when, with what resultEvery run is a logged Job with full stdout, launched-by, and timestamp
"Works on my machine" — depends on whatever's installed locallyExecution Environment guarantees identical Ansible/collection/boto3 versions every run
Scheduling requires cron + disciplineBuilt-in scheduling, notifications, and workflow chaining

3 · ShopSphere story

At ShopSphere, only the Cloud Automation team's RHAAP service account (via an IAM role, Module 5) can actually reach AWS — no individual engineer's laptop has standing AWS credentials for PROD. When Ananya's ticket is approved, a DevOps engineer (or, eventually, ServiceNow itself) launches a RHAAP Workflow Job Template. RHAAP — not the engineer's laptop — does the work, which is exactly what makes the audit trail defensible.

◆ Concept

The Execution Environment is worth pausing on: it means your laptop's Ansible version is irrelevant to what actually runs in RHAAP. This is a very common source of confusion for beginners moving from "Ansible on my laptop" to "Ansible in an enterprise" — a playbook that runs fine locally can behave differently in RHAAP if the EE has a different collection version. Module 9 builds one of these from scratch.

⛨ Security

Credentials are decrypted only inside the running job's container, only for that job's duration. They are never written to the Git repo, never appear in plaintext in Job Output (RHAAP redacts known credential values from logs), and are scoped by RBAC so a DEV-only team member can't launch a PROD-targeted template even if they technically have "launch" permission on the Job Template. This is the enforcement point Module 29 (Secrets Management) and Module 5 (AWS Auth) both depend on.

⚠ Warning

A frequent real incident: a Job Template's Execution Environment is out of sync with what the Project's Git repo actually needs (e.g. a role now requires a newer amazon.aws collection than the pinned EE has). The job fails with a confusing "module not found" or unexpected-parameter error that has nothing to do with your YAML being wrong. This exact failure is incident #24 in Module 35's troubleshooting catalog — filed here so you recognize it immediately when we get there.

✓ Best Practice

Never let engineers edit playbooks directly inside RHAAP's UI. Projects should sync from Git only — this is what makes Module 38's CI/CD (lint → review → merge → sync) meaningful. If RHAAP is editable in place, your Git history stops being the source of truth, and your audit trail breaks.

Module 05 — AWS Authentication

AWS & Connectivity · How RHAAP Is Trusted to Touch AWS at All

1 · Beginner explanation

Before amazon.aws.ec2_instance can create anything, whatever is running that module — the RHAAP Execution Environment container — has to prove to AWS that it's allowed to. That proof is "authentication." AWS accepts several forms of proof, and enterprises care enormously about which form you use, because some forms are long-lived secrets that can leak, and some are short-lived tokens that expire on their own.

2 · Why enterprises care which method you pick

A leaked long-lived AWS access key is one of the most common real-world cloud breach vectors — it can sit in a Git history, a log file, or a laptop for years, silently usable by anyone who finds it. Enterprises design authentication specifically to minimize how much damage a single leaked credential can do, and for how long. That's the entire logic behind everything in this module.

3 · The options, explained

MethodWhat it isLifespan
IAM User + Access Key/Secret KeyA static, long-lived credential pair tied to a named IAM identityUntil manually rotated or revoked — can be years
IAM RoleAn identity with a policy attached, but with no permanent credentials — something else must "assume" itN/A — the role itself has no standing credentials
STS (Security Token Service)The AWS service that issues short-lived, temporary credentials when a role is assumedMinutes to hours (configurable)
AssumeRoleThe action of exchanging an identity for temporary STS credentials scoped to an IAM Role's policyProduces temporary credentials, per above
Instance profileA wrapper that attaches an IAM Role directly to an EC2 instance, so anything running on it can assume that role automatically, with no stored secret at allRotates automatically behind the scenes, roughly hourly
Cross-account roleAn IAM Role in Account B that trusts identities from Account A to assume it — used when ShopSphere's DEV and PROD live in separate AWS accountsSame as any role — temporary credentials on assumption
◆ Concept

The single idea underlying all of this: a Role is not a credential — it's a permission set that something else can temporarily borrow. STS is the service that hands out that temporary borrowed access. "AssumeRole" is just the verb for borrowing it. Once you see it this way, "IAM Role vs Access Key" stops being two flavors of the same thing and becomes two fundamentally different security models.

4 · Comparison — which enterprises actually prefer, and why

Access Keys (IAM User)IAM Role via Instance ProfileSTS AssumeRole (cross-account/federated)

✓ Best Practice

Enterprises strongly prefer IAM Roles (via instance profile) or STS AssumeRole over static Access Keys. At ShopSphere, the RHAAP execution nodes run with an instance profile granting a scoped provisioning role; when a job needs to reach into ShopSphere's separate PROD AWS account, that role then performs an AssumeRole into a PROD-scoped cross-account role. No access key ever exists in this chain. This is the reason Module 29 (Secrets Management) treats "we don't need to rotate a secret because there isn't one" as the gold-standard answer, not just a nice-to-have.

5 · ShopSphere story — provisioning pay-dev-app01's credentials

When the "Provision — Payment Gateway" Workflow Job Template runs, its RHAAP Credential is configured as "Instance Role Credential" — meaning: don't store any key at all, just use whatever role the RHAAP execution node already has. That role, shopsphere-rhaap-provisioner, is scoped narrowly to exactly what provisioning needs (see the sample policy below) — not full AdministratorAccess, which would be catastrophic if a playbook bug or a compromised job ever misused it.

Sid: Ec2InstanceLifecycle

Module 06 — Firewall Requirements

AWS & Connectivity · Nothing Works Until the Network Allows It

1–2 · Beginner explanation and why it matters

Every arrow in Module 3's architecture diagram is a network connection, and every network connection needs a firewall rule permitting it — in security groups, network ACLs, and often a corporate proxy or transparent firewall between RHAAP and the internet. Beginners write perfectly correct YAML that fails for reasons that have nothing to do with Ansible: a port is blocked. This module exists so that when that happens, you recognize it immediately instead of re-reading your playbook for an hour.

3 · ShopSphere story

ShopSphere's RHAAP cluster sits in a shared-services VPC with no direct internet egress — all outbound traffic goes through a corporate proxy or NAT gateway, and DNS resolves through internal resolvers only. This is completely typical for a regulated enterprise, and it's exactly why Module 9 (Execution Environment) matters so much: if RHAAP can't freely reach the public internet, every dependency (collections, packages) has to come from an internally mirrored source.

◆ Concept — the four ports worth understanding, not memorizing
  • TCP 443 (HTTPS): the workhorse of this entire project — AWS APIs, Git, Automation Hub, Vault, and (with SSM) even remote management all ride over 443. Most enterprise firewalls are far more permissive on 443 outbound than any other port, which is exactly why AWS designed its APIs this way.
  • TCP 22 (SSH): the traditional way Ansible reaches a target host to run tasks locally on it. Increasingly restricted or replaced entirely in favor of SSM (see box below), because it means no inbound port needs to be open on the instance at all.
  • DNS 53: without working DNS resolution, RHAAP can't resolve the Git server, Vault, or even AWS regional API endpoints by name — a DNS outage looks like everything is broken simultaneously, which is a strong diagnostic clue in itself (Module 35).
  • NTP 123: AWS API requests are signed with a timestamp; if the RHAAP execution node's clock has drifted more than about 5 minutes from real time, AWS will reject every single API call with a signature/expiry error that has nothing to do with credentials being wrong.
⚠ Warning

Clock drift causing RequestExpired or SignatureDoesNotMatch errors is a real, recurring, and confusing production incident — engineers often burn time re-checking IAM policies and credentials before realizing the actual problem is NTP. If every AWS API call in a job suddenly starts failing with an authentication-flavored error and nothing about the credentials or policy has changed, check the execution node's clock before anything else.

5 · Outbound internet vs. proxy vs. private/VPC endpoint connectivity — the three designs

DESIGN A — Direct internet egress RHAAP EE ──► NAT Gateway ──► Internet ──► AWS public API endpoints (Simple; least common in regulated enterprises — most restrict this) DESIGN B — Corporate proxy RHAAP EE ──► Configured HTTP(S) proxy ──► Internet/AWS (EE's http_proxy/https_proxy env vars and pip/dnf config must all agree — a very common source of "works from my laptop, fails from RHAAP" bugs) DESIGN C — VPC Endpoints (PrivateLink) — ShopSphere's actual design RHAAP EE ──► VPC Endpoint for ec2, sts, kms ──► AWS API (Traffic never leaves AWS's private network at all — no NAT, no proxy, no public internet exposure; the recommended enterprise pattern for AWS-only traffic)
✓ Best Practice

ShopSphere uses VPC Endpoints for AWS API traffic (ec2, sts, kms, ssm) specifically because it removes an entire class of firewall/proxy failure modes for the highest-volume traffic in this project, and it keeps that traffic off the public internet entirely — a security team's preferred answer whenever it's feasible. Git and Automation Hub traffic, which may point to genuinely external or SaaS endpoints, still goes through the corporate proxy (Design B).

⛨ Security

Prefer SSM (AWS Systems Manager Session Manager) over open inbound port 22 wherever the target OS and network support it. With SSM, the EC2 instance makes an outbound connection to the SSM service — no inbound security group rule for port 22 is needed at all, which meaningfully shrinks the instance's attack surface. ShopSphere's security baseline (Module 17) treats "no security group allows inbound 22 from outside the VPC" as a hard requirement for PROD.

✕ Troubleshooting

Symptom: a provisioning job hangs, then times out, on the very first AWS API call. Investigation order that actually works: (1) can the execution node resolve the AWS API hostname via DNS at all? (2) is there a route to it — direct, proxy, or VPC endpoint? (3) only then look at IAM/credentials. Engineers who jump straight to "must be a permissions problem" waste time, because a connectivity failure and a permissions failure can produce deceptively similar-looking timeouts/errors in job output.

Knowledge check — All AWS API calls in a job suddenly fail with a signature/expiry-related error, but nothing about credentials or IAM policy changed. What should you check first?

Module 08 — Collections

Code & Tooling · Where Modules Like ec2_instance Actually Come From

1 · Beginner explanation

Modern Ansible ships almost no modules in "Ansible Core" itself — nearly everything (AWS, Linux system config, third-party integrations) lives in separately versioned, separately installed collections. A collection is a packaged bundle of modules, plugins, and sometimes roles, published and versioned independently of Ansible Core itself — similar in spirit to a Python package.

2 · The vocabulary, precisely

TermMeaning
CollectionA versioned package of modules/plugins/roles — e.g. amazon.aws, at some specific version like 7.x.
ModuleA single unit of functionality inside a collection — e.g. ec2_instance inside amazon.aws.
PluginA broader category including modules, but also things like inventory plugins, lookup plugins, and callback plugins — e.g. the amazon.aws collection also ships an EC2 dynamic inventory plugin, relevant again in Module 14.
FQCN (Fully Qualified Collection Name)The full namespace.collection.module path — e.g. amazon.aws.ec2_instance — first introduced in Module 1, now you know exactly what each segment means.
requirements.ymlThe manifest file declaring which collections (and versions) a project needs — Ansible's equivalent of a dependency lockfile.
Version pinningSpecifying an exact or bounded version range for a collection, so a project doesn't silently break when a newer collection version changes behavior.
Certified collectionA collection Red Hat has tested and supports under a support contract (available via Automation Hub) — as opposed to community collections, which are best-effort and unsupported.

3 · The three collections this project uses

CollectionWhat it provides here
amazon.awsAll AWS provisioning modules — ec2_instance, ec2_vol, information-lookup modules like ec2_instance_info, and the EC2 dynamic inventory plugin (Modules 12, 13, 14).
ansible.posixPOSIX/Linux system-level modules — filesystem, mount, firewalld, and more — used throughout Linux baseline, disk configuration, and hardening (Modules 15–17).
community.generalA large, broadly useful community-maintained grab-bag — used here for smaller utility modules not covered by the two collections above (specific examples arrive as we reach the roles that need them).
◆ Concept

"amazon.aws" being certified and Red-Hat-supported, while "community.general" is community-maintained, is exactly why enterprises are careful about which collections make it into an Execution Environment (Module 9) at all — a certified collection has a support contract behind it if something breaks; a community one doesn't. This distinction is why ShopSphere's security/platform team reviews and approves any new collection before it's added to requirements.yml.

4–5 · Building requirements.yml — code and line-by-line explanation

collections/requirements.yml
collections:
  - name: amazon.aws
    version: ">=7.0.0,<8.0.0"
    source: https://console.redhat.com/api/automation-hub/

  - name: ansible.posix
    version: ">=1.5.0,<2.0.0"
    source: https://console.redhat.com/api/automation-hub/

  - name: community.general
    version: ">=8.0.0,<9.0.0"
    source: https://galaxy.ansible.com
collections:
The top-level key requirements.yml expects for a collection manifest (as opposed to a role manifest, which would use a roles: key instead — same filename convention, different content, easy to confuse when skimming Ansible docs).
- name: amazon.aws
One list item per required collection. The name is the namespace.collection pair — no module name here, since we're declaring the whole collection as a dependency, not a single module.
version: ">=7.0.0,<8.0.0"
A version pin using a range rather than an exact pin — allows picking up patch/minor releases (bug fixes, new AWS resource support) automatically, while blocking a major version bump that might introduce breaking changes without the team explicitly reviewing it. This is a deliberate middle ground between "always latest" (risky) and "exact version forever" (misses security fixes).
source: .../automation-hub/
Tells ansible-galaxy/the EE build process to pull this collection from Red Hat's certified Automation Hub rather than the public, unvetted Galaxy — this is exactly the certified-vs-community distinction from the concept box above, enforced in code, not just policy.
community.general source: galaxy.ansible.com
This one intentionally points to public Galaxy, because community.general isn't offered as a certified Automation Hub collection — the team has consciously accepted it as an approved exception, which is exactly the kind of decision that should be documented in the README (Module 7) and reviewed periodically.
⚠ Warning

An unpinned requirements.yml (no version: key at all) is a real production risk: it means every Execution Environment rebuild (Module 9) can silently pull a newer collection version, potentially changing module behavior or deprecating a parameter your roles rely on. This is exactly incident #24 referenced back in Module 4 — an EE that no longer matches what the roles expect. Version pinning here is the actual prevention for that incident, not just a "best practice" platitude.

✓ Best Practice

Treat requirements.yml changes like any other production dependency bump: a pull request, reviewed, tested against a non-PROD Execution Environment build first (Module 38's CI/CD), before it ever reaches the EE that PROD Job Templates use.

☰ Interview Question

"What's the difference between Ansible Core and a collection, and why does that distinction matter operationally?" A strong answer covers: Core ships the engine and a small set of built-ins, collections ship almost everything else including all cloud provider modules, and operationally this matters because collections version and can break independently of Core — which is exactly what pinning and Execution Environments (Module 9) exist to control.

Build the Automation · The Container Every Job Actually Runs Inside

1 · Beginner explanation

Module 4 mentioned the Execution Environment (EE) as "the container Ansible runs inside." This module builds one. An EE is a container image containing a specific Ansible Core version, the collections from Module 8's requirements.yml, and the Python/system packages those collections need underneath — most importantly, boto3 and botocore, AWS's SDK, which is what amazon.aws modules actually call.

2 · Why enterprises need it

Without a defined EE, "what Ansible version and collections actually run this job" depends on whatever happens to be installed on whichever RHAAP execution node picked it up — exactly the "works on my machine" drift Module 4 warned about. An EE makes that fully reproducible and versioned, so a job run today and the same job run in six months use identical tooling unless someone deliberately rebuilds the image.

3 · ShopSphere story

The Cloud Automation team maintains its own EE, shopsphere-aws-ee, built via ansible-builder and pushed to ShopSphere's Private Automation Hub (Module 6). Every provisioning, patching, and decommissioning Job Template points at a specific tagged version of this image — never :latest, for exactly the version-drift reasons covered in Module 8.

4 · The build chain

execution-environment.yml (what to build) │ ▼ ansible-builder (reads the definition, resolves all three requirement files below) │ ▼ Base image (Red Hat's minimal EE base) + Ansible Core + collections + Python/system deps │ ▼ Built container image → pushed to Private Automation Hub / registry │ ▼ RHAAP Job Template references this image tag → every job runs identically inside it

5–8 · The three requirement files, and execution-environment.yml itself

ansible-builder reads four files together to assemble one image. Here's all four, exactly as they sit in the repo from Module 7:

execution-environment.yml
version: 3

images:
  base_image:
    name: registry.redhat.io/ansible-automation-platform-24/ee-minimal-rhel9:latest

dependencies:
  galaxy: collections/requirements.yml
  python: requirements.txt
  system: bindep.txt

options:
  package_manager_path: /usr/bin/microdnf
version: 3
The schema version of the EE definition format itself — ansible-builder reads this file differently depending on version, so this line isn't decorative; it's how the tool knows how to parse everything below.
base_image: ...ee-minimal-rhel9...
The starting container image — Red Hat's minimal, supported EE base built on RHEL 9. "Minimal" matters: it means only what's strictly needed is present, which reduces both attack surface and image size versus a general-purpose Ansible image.
dependencies: galaxy / python / system
Three separate dependency layers, resolved in this order: galaxy (Ansible collections — Module 8's file), python (pip packages those collections need, e.g. boto3/botocore), system (OS-level packages needed underneath, e.g. compilers or libraries some Python packages require to install).
package_manager_path: microdnf
Tells the builder which package manager binary to use for the system dependency layer inside this RHEL-based minimal image — microdnf is the lightweight dnf variant used in minimal container images.
requirements.txt — Python (pip) dependencies
boto3>=1.34.0,<2.0.0
botocore>=1.34.0,<2.0.0

This is the file that matters most and confuses beginners least obviously: the amazon.aws collection itself contains no AWS logic — every module is a thin Python wrapper that calls boto3/botocore underneath. If these two packages are missing or the wrong version, every amazon.aws module fails immediately, even though the failure looks like it's "in Ansible." Pinning them here, in step with whichever amazon.aws version Module 8 pinned, keeps the two in sync — mismatches between an amazon.aws version and an incompatible botocore version are a real, documented source of provisioning failures.

bindep.txt — system-level package dependencies
gcc [platform:rpm compile]
python3-devel [platform:rpm compile]

Some Python packages (less often boto3/botocore themselves, but true of other dependencies picked up transitively) need to compile native extensions during install. bindep.txt declares OS packages needed for that — here, a C compiler and Python's development headers — scoped with [platform:rpm compile] so they're only pulled in on RPM-based images and only for the build stage, keeping the final runtime image lean.

◆ Concept

This completes the full internal chain first shown in Module 1: RHAAP → Execution Environment (built by exactly these four files) → Ansible → amazon.aws collection (Module 8) → boto3/botocore (this module) → AWS API. Every module in this masterclass that touches AWS ultimately depends on this EE being built correctly — it's the literal foundation everything else runs on.

⚠ Warning

Rebuilding an EE isn't free — it's a real event that should go through the same review as any dependency change (Module 38). A common incident: someone bumps amazon.aws in requirements.yml without also checking whether the pinned boto3/botocore range in requirements.txt still supports it, and the next EE build produces a working image that then fails at runtime with obscure attribute errors deep in a module's Python traceback — confusing because the YAML itself is completely correct.

✓ Best Practice

Tag every EE build with a specific version (e.g. shopsphere-aws-ee:2.3.0), never overwrite :latest in place, and update Job Templates to point at a new tag deliberately. This gives you the same rollback safety for your execution tooling that Module 34 gives you for a bad server deployment — if a new EE breaks something, templates can be pointed back at the last known-good tag instantly.

☰ Interview Question

"Why does amazon.aws need boto3 at all — isn't Ansible supposed to be agentless and self-contained?" Strong answer: Ansible's AWS modules are thin wrappers around AWS's own official SDK rather than reimplementing the AWS API themselves — this keeps modules in sync with AWS's actual API surface, but it does mean boto3/botocore become real runtime dependencies, which is exactly why the EE has to package them explicitly.

If not, just trace through the four files by hand and write out, in your own words, what would happen if requirements.txt were deleted entirely.

Module 10 — Variable Design

Build the Automation · Turning Module 2's Checklist Into Real Variables

1 · Beginner explanation

A variable is just a named value a playbook/role reads instead of a hardcoded literal — {{ vm_name }} instead of literally typing pay-dev-app01 inside a role. What matters for this masterclass isn't the mechanic (you likely already know that); it's where a given variable's value should live, because Ansible reads variables from many possible locations, and getting that placement wrong is one of the most common sources of "it used the wrong value and I don't know why" bugs.

◆ Concept — variable precedence, the part that actually causes bugs

When the same variable name is set in more than one place, Ansible has a defined precedence order that decides which value wins. From lowest to highest (the ranges that matter for this project): role defaults → group_vars → host_vars → play vars → extra_vars (including RHAAP survey answers). extra_vars wins over almost everything — which is exactly why a RHAAP survey answer will always override a group_vars/dev.yml default, even if that's not what someone intended.

✎ ShopSphere Story

group_vars/dev.yml sets instance_type: "t3.large" as the DEV-environment standard. But Module 31's survey also exposes an instance_type field so unusual requests (a data-heavy DEV test) can override it. Ananya's ticket didn't ask for anything unusual, so the survey field was left at its default — which, per precedence, still counts as an extra_var and still technically "wins," it just happens to equal the group_vars value. If someone did type an override into the survey, it would silently beat the environment standard — which is exactly why Module 11 validates instance_type against an approved list, regardless of which layer it came from.

⚠ Warning

A frequent real bug: an engineer changes a value in group_vars/dev.yml, tests it, and it appears to have no effect. The usual cause is a leftover extra_vars value from a saved Job Template or a previous survey answer sitting at higher precedence, silently overriding the group_vars change. Diagnosing this means checking the precedence chain top-down, not re-editing group_vars repeatedly hoping it takes effect.

✓ Best Practice

Keep the split from Module 2 visible in the variable design itself: anything a requester should be able to influence lives in the survey (→ extra_vars); anything that's a platform standard lives in group_vars and is deliberately not exposed on the survey at all — the safest way to prevent a requester's override from ever reaching a value they shouldn't control.

Knowledge check — group_vars/dev.yml sets security_group to "sg-payment-dev-app". A RHAAP survey field also happens to set security_group as an extra_var. Which value does the job actually use?
☰ Interview Question

"How do you decide where a variable's default value should live?" Tie the answer back to who owns the value (Module 2) and how exposed it should be to being overridden (Module 10's precedence chain) — platform standards go low and hidden from the survey; requester choices go high and exposed via survey.

Module 11 — Input Validation Role

Build the Automation · roles/validate_request — Trust Nothing Until It's Checked

1–2 · Beginner explanation and why it matters

This is the first role that actually runs when the "Provision — Payment Gateway" workflow executes, and deliberately so: it runs before a single AWS resource is touched. Its entire job is to catch a bad hostname, an invalid AMI, or a nonexistent subnet here — as a clear, human-readable failure — rather than letting a malformed value reach the AWS API and fail 8 steps into provisioning with a confusing error, or worse, silently succeed with the wrong value.

3 · ShopSphere story

This exact role is what will later catch the "wrong subnet" and "invalid AMI" incidents referenced back in the original curriculum outline — instead of pay-dev-app01 failing to provision halfway through with EBS attached and no clean way to tell what state it's in, the job fails in the first 10 seconds with a message an engineer can act on immediately.

4–8 · The code, in full, then explained line by line

roles/validate_request/tasks/main.yml
# 1. Hostname must follow ShopSphere's -- convention
- name: Validate hostname follows naming convention
  ansible.builtin.assert:
    that:
      - vm_name is match('^[a-z]+-(dev|qa|uat|prod)-[a-z]+[0-9]{2}$')
    fail_msg: "Hostname '{{ vm_name }}' does not match <app>-<env>-<role><NN>"
    success_msg: "Hostname format OK: {{ vm_name }}"

# 2. Environment must be one of exactly four approved values
- name: Validate environment is an approved value
  ansible.builtin.assert:
    that:
      - environment in ['dev','qa','uat','prod']
    fail_msg: "environment must be dev, qa, uat, or prod — got '{{ environment }}'"

# 3. Non-DEV environments must reference a real ServiceNow change record
- name: Validate change number format outside DEV
  ansible.builtin.assert:
    that:
      - change_number is match('^CHG[0-9]{7}$')
    fail_msg: "change_number '{{ change_number }}' is not a valid CHGnnnnnnn record"
  when: environment != 'dev'

# 4. Confirm the requested AMI actually exists and is usable, right now, in this region
- name: Look up requested AMI
  amazon.aws.ec2_ami_info:
    image_ids: "{{ ami_id }}"
    region: "{{ aws_region }}"
  register: ami_lookup

- name: Fail if AMI is missing or not available
  ansible.builtin.assert:
    that:
      - ami_lookup.images | length == 1
      - ami_lookup.images[0].state == 'available'
    fail_msg: "AMI {{ ami_id }} not found or not available in {{ aws_region }}"

# 5. Confirm the requested subnet actually belongs to the requested VPC
- name: Look up requested subnet inside requested VPC
  amazon.aws.ec2_vpc_subnet_info:
    region: "{{ aws_region }}"
    filters:
      subnet-id: "{{ subnet_id }}"
      vpc-id: "{{ vpc_id }}"
  register: subnet_lookup

- name: Fail if subnet does not belong to the expected VPC
  ansible.builtin.assert:
    that:
      - subnet_lookup.subnets | length == 1
    fail_msg: "Subnet {{ subnet_id }} not found inside VPC {{ vpc_id }}"
ansible.builtin.assert
A built-in module (note: ansible.builtin, not a third-party collection — it ships with Ansible Core itself) that evaluates a list of conditions and stops the play with a clear message if any is false. This is the correct tool for "this input must be true or we stop here," as opposed to fail (used for a single unconditional stop) or failed_when (used to redefine what counts as failure on a different task's result — Module 33).
that: - vm_name is match('^[a-z]+...$')
The match Jinja2 test runs a regular expression against the string, anchored at both ends (^...$) so partial matches don't slip through. This specific pattern requires lowercase letters, then a literal environment token, then a role name, then exactly two digits — rejecting things like Pay-Dev-App01 (wrong case) or pay-dev-app1 (one digit, not two) before they ever reach AWS.
fail_msg / success_msg
Custom messages shown in the RHAAP job output instead of Ansible's generic assertion-failed text — directly serving Module 1's point about task names mattering in job logs: a validation failure someone reads at 2am should explain itself, not require re-reading the YAML to understand.
when: environment != 'dev'
A conditional — this task only runs when the condition evaluates true. Here it means DEV requests are allowed to skip the strict change-number check (lower risk, faster iteration), while QA/UAT/PROD cannot — encoding Module 2's point that approval rigor should scale with environment risk directly into the validation logic.
amazon.aws.ec2_ami_info
An information/lookup module (note the _info suffix — an Ansible convention meaning "read-only, makes no changes") that queries AWS for AMI metadata. This is a live check against real AWS, not a static list — it will correctly reject an AMI that existed yesterday but was deregistered today.
register: ami_lookup
register captures a task's full result (here, the AMI info) into a named variable so later tasks can reference it — this is the exact "register variable" step shown generically in Module 1's internal-flow diagram, now made concrete.
ami_lookup.images | length == 1
The length Jinja2 filter counts items in the returned list. Checking for exactly 1 catches both failure shapes at once: zero results (AMI doesn't exist) and, in theory, an unexpectedly ambiguous filter (defensive coding, even though image_ids lookups are normally exact).
⛨ Security

Every one of these checks is also a security control, not just a correctness one: validating the subnet belongs to the expected VPC prevents a malformed or malicious input from provisioning a server into the wrong network segment; validating the AMI is in an "available" state (rather than trusting a raw ID blindly) prevents provisioning from a deregistered or unapproved image. Input validation and security hardening (Module 17) are closely related disciplines — this role is where that relationship starts.

✕ Troubleshooting

"Wrong subnet" incident: Symptom — the job fails immediately at the "Fail if subnet does not belong to the expected VPC" task. Investigation — compare the subnet_id extra_var actually passed in this run against Module 3's architecture; usually the cause is either a stale group_vars value from before a VPC redesign, or a requester-supplied override (Module 10) pointing at a QA subnet by copy-paste mistake. Fix — correct the variable at its source, re-run; the fact that this fails here, in seconds, instead of during EC2 creation with a partially-tagged resource, is the entire point of this module.

✓ Best Practice

Validate against live AWS state (as the AMI/subnet lookups do) wherever the correctness of an input can only really be known by asking AWS — never trust a static list of "valid" IDs that can silently go stale. Reserve pure regex/assert checks (hostname, environment, change number) for values that are correct by format rules alone.

☰ Interview Question

"Why validate before provisioning instead of just letting a bad value fail at the AWS API call?" Because a failure at the API call can happen after some resources are already partially created (Module 34's rollback problem), and produces a raw AWS error message instead of an actionable one. Validating first is cheaper to fail, faster to diagnose, and never leaves orphaned resources behind.

Module 12 — AWS Provisioning Role

Build the Automation · roles/aws_provision — Where pay-dev-app01 Actually Gets Created

1–3 · Beginner explanation, why, and story

This is the role that finally creates real AWS infrastructure. Everything before this module existed to make sure this role only ever runs with trustworthy, validated input. Because Module 11 already confirmed the AMI, VPC, and subnet are real, this role can focus purely on doing the provisioning correctly — instance sizing, encrypted storage, IAM attachment, tagging, and waiting for the instance to actually be reachable before declaring success.

4 · Code — the core provisioning task

roles/aws_provision/tasks/main.yml
# Idempotency check — does this instance already exist? (full logic in Module 13)
- name: Check whether {{ vm_name }} already exists
  amazon.aws.ec2_instance_info:
    region: "{{ aws_region }}"
    filters:
      "tag:Name": "{{ vm_name }}"
      instance-state-name: ["running", "stopped"]
  register: existing_instance

- name: Provision EC2 instance for {{ vm_name }}
  amazon.aws.ec2_instance:
    name: "{{ vm_name }}"
    region: "{{ aws_region }}"
    image_id: "{{ ami_id }}"
    instance_type: "{{ instance_type }}"
    vpc_subnet_id: "{{ subnet_id }}"
    security_groups: ["{{ security_group }}"]
    iam_instance_profile: "{{ iam_instance_profile }}"
    key_name: "{{ ssh_key_pair }}"
    wait: true
    state: running
    volumes:
      - device_name: /dev/sda1
        ebs:
          volume_size: "{{ root_volume_size }}"
          volume_type: gp3
          encrypted: true
          kms_key_id: "{{ kms_key_id }}"
      - device_name: /dev/sdb
        ebs:
          volume_size: "{{ data_volume_size }}"
          volume_type: gp3
          encrypted: true
          kms_key_id: "{{ kms_key_id }}"
    tags:
      Name: "{{ vm_name }}"
      Application: "{{ application_name }}"
      Environment: "{{ environment }}"
      Owner: "{{ owner }}"
      CostCenter: "{{ cost_center }}"
      ChangeNumber: "{{ change_number }}"
      ManagedBy: "RHAAP"
  register: ec2_result
  when: existing_instance.instances | length == 0

# Wait for SSH (or SSM) reachability before handing off to configuration plays
- name: Wait for SSH to become reachable
  ansible.builtin.wait_for:
    host: "{{ ec2_result.instances[0].private_ip_address }}"
    port: 22
    delay: 10
    timeout: 300
  when: ec2_result.instances is defined
amazon.aws.ec2_instance_info ... register: existing_instance
A read-only lookup filtered by the Name tag and instance state, run before the actual creation task — this is the idempotency check, covered in full in Module 13. It exists so re-running this role never blindly creates a second pay-dev-app01.
vpc_subnet_id / security_groups
These are exactly the values Module 11 already confirmed exist and belong together — this role trusts them because validation already ran, which is precisely why role ordering in the workflow (Module 32) matters as much as any single role's internal logic.
iam_instance_profile
Attaches an IAM Role to the instance itself (distinct from the role RHAAP uses to create it, Module 5) — this is what lets software running on pay-dev-app01 later call AWS APIs (e.g. CloudWatch, SSM) without any credential ever being stored on the box.
wait: true / state: running
state: running declares the desired end state (this is what makes the module idempotent in AWS's own terms, separate from Module 13's pre-check); wait: true tells the module to block until AWS actually reports the instance in that state, rather than returning immediately after the API accepts the request — critical, because the next task needs a real IP address to wait on.
volumes: (two EBS entries)
Root (100 GB, /dev/sda1) and data (200 GB, /dev/sdb) volumes straight from the ticket, each with encrypted: true and an explicit kms_key_id — satisfying the Security-team-owned encryption requirement from Module 2's storage checklist. Module 16 later formats and mounts this second device inside the OS.
tags: (six key/value pairs)
Every tag here maps to a Module 2 field with a named owner — this is what makes the "TaggingRequired" statement in Module 5's IAM policy meaningful, and what lets finance and CMDB (Module 40) trace this exact instance back to REQ0012456 without any manual bookkeeping.
when: existing_instance.instances | length == 0
The provisioning task itself only runs if the idempotency check found nothing — if pay-dev-app01 already exists, this task is skipped entirely (shown as "skipped," not "failed," in job output), and Module 13 covers what happens next in that branch.
ansible.builtin.wait_for: host / port 22
Blocks the play until a TCP connection succeeds on port 22 at the instance's private IP, retrying every few seconds up to the 300-second timeout. This closes the gap between "AWS says the instance is running" and "the OS has actually finished booting and SSH is accepting connections" — skipping this is a common cause of the next play failing with a connection-refused error a few seconds too early.
◆ Concept

This single role touches almost every AWS permission from Module 5's policy — RunInstances, CreateVolume, kms:Encrypt, CreateTags — which is exactly why that policy was built Sid-by-Sid around this role's actual needs, not designed abstractly first. Requirements (Module 2) → permissions (Module 5) → code (this module) is meant to be traceable in that direction the whole way through.

⚠ Warning

"IAM permission denied" incident: if iam_instance_profile is set but the RHAAP provisioning role itself lacks iam:PassRole scoped to that profile's ARN, this task fails with an access-denied error that can look identical to a plain credentials problem. The fix is adding a narrowly-scoped iam:PassRole statement (referenced back in Module 5) — never a broad IAM grant.

✓ Best Practice

Always pair wait: true on the EC2 task with an explicit wait_for (or SSM-readiness equivalent) afterward. AWS reporting "running" and the OS being ready to accept configuration are two different milestones — collapsing them causes intermittent, hard-to-reproduce failures in the very next play.

Module 13 — Idempotency

Build the Automation · Why Running This Twice Must Never Create Two Servers

1–2 · Beginner explanation and why it matters

Idempotent means running an operation multiple times produces the same end result as running it once. It's one of Ansible's core design philosophies — a well-written playbook, run five times in a row with no changes, should report "no changes" on runs 2 through 5, not repeat its actions blindly. For provisioning specifically, this isn't an abstract nicety: it's the only thing standing between a retried job and a duplicate, orphaned, billed EC2 instance nobody's tracking.

3 · ShopSphere story

Suppose the "Provision — Payment Gateway" workflow fails at the Monitoring Agent stage (Module 23) — well after pay-dev-app01 was successfully created. An engineer fixes the monitoring role and re-launches the same Workflow Job Template from the start, rather than trying to resume mid-workflow. Without the idempotency check from Module 12, this re-run would call ec2_instance again and — depending on parameters — could create a second, duplicate instance with a conflicting or auto-suffixed name, silently doubling ShopSphere's DEV bill for this application and leaving CMDB (Module 40) inconsistent.

4 · The decision flow

Job runs (re-launched after a mid-workflow failure) │ ▼ roles/aws_provision: ec2_instance_info filtered by tag:Name=pay-dev-app01 │ ▼ Found existing instance? │ ┌────┴────┐ YES NO │ │ ▼ ▼ Skip creation. Create EC2 Validate its (Module 12's attributes match main task) the request (size, AMI, tags) │ │ └─────┬─────┘ ▼ Continue workflow from here — remaining stages (baseline, hardening, monitoring, etc.) still run either way, since those roles have their own idempotent checks too
◆ Concept

Notice idempotency isn't one trick that lives only in roles/aws_provision — it's a discipline every role in this project needs individually. ansible.builtin.package is naturally idempotent (installing an already-installed package is a no-op); a raw shell command like useradd payapp is not (running it twice errors on the second run) unless guarded with a creates: argument or an existence check first. Module 12's ec2_instance_info pre-check is this project's specific answer for the EC2-creation case; later modules (15–17, 23–26) each need their own equivalent, appropriate to what they're configuring.

⚠ Warning

Idempotency at the "does the resource exist" level is necessary but not sufficient. Suppose pay-dev-app01 already exists but was originally created with a 50 GB root disk, and the re-run's ticket now requests 100 GB. Module 12's check as written will find the existing instance and skip creation entirely — silently leaving the disk size wrong. Real production roles typically follow the existence check with an explicit drift check (Module 33's assert pattern again) that fails loudly if the existing resource's attributes don't match the request, rather than silently accepting whatever already exists.

✓ Best Practice

Design every role to be safely re-runnable from the start of the workflow, not just resumable from the point of failure. RHAAP workflows can resume from a failed node (Module 32), but "just re-run the whole thing" is a common, simpler operational habit — your roles need to tolerate it without side effects, which is exactly the property idempotency guarantees.

Module 14 — Dynamic Inventory / add_host

Build the Automation · Handing a Freshly-Created Server Off to Its Own Configuration

1–2 · Beginner explanation and why it matters

Here's a genuine chicken-and-egg problem: Ansible needs an inventory entry (a host to connect to) before it can configure a server, but pay-dev-app01 doesn't have a private IP address — doesn't exist as a connectable host at all — until after Module 12's provisioning task finishes. add_host solves this by adding a host to Ansible's in-memory inventory during a play, using data just returned from the EC2 creation task itself.

3 · ShopSphere story

The provision.yml playbook is structured as two plays for exactly this reason: play one runs against localhost (since "create an EC2 instance" isn't an action performed on any existing host — it's an API call RHAAP's execution node makes on pay-dev-app01's behalf) and ends by registering the new instance's IP into a temporary in-memory group; play two then targets that group to run Linux baseline, hardening, and every subsequent configuration role, connecting to the server that didn't exist when the playbook started.

4 · The transition, as a diagram

PLAY 1 — hosts: localhost │ ├─► roles/validate_request (Module 11) ├─► roles/aws_provision (Module 12/13) → register: ec2_result │ ▼ add_host: name: "{{ ec2_result.instances[0].private_ip_address }}" groups: just_provisioned │ ▼ Ansible's in-memory inventory now contains a real, connectable host that did not exist when this playbook began │ ▼ PLAY 2 — hosts: just_provisioned │ ├─► roles/linux_baseline (Module 15) ├─► roles/disk_configuration (Module 16) ├─► roles/security_hardening (Module 17) └─► ... every later configuration role, targeting the real server

hosts: localhost / connection: local
Play 1 runs entirely on the RHAAP execution node itself, not over SSH to any remote machine — appropriate, since every task in it is an AWS API call, not an action performed on a server's own filesystem.
gather_facts: false
Skips Ansible's automatic fact-gathering (OS details, etc.) for this play, since there's no remote host to gather facts from yet and localhost facts are irrelevant here — a small performance/clarity optimization.
ansible.builtin.add_host: name: "{{ ec2_result...private_ip_address }}"
This is the pivotal line: it reads the IP address directly out of the ec2_result variable that Module 12's provisioning task registered moments earlier in this same play, and uses it as the new host's inventory name — the freshest possible source of truth, since it came straight from AWS's own API response.
groups: just_provisioned
Assigns the new host to an in-memory group that exists only for the duration of this playbook run — Play 2's hosts: targets this exact group name, which is what connects the two plays together.
ansible_user: ec2-user
Sets the connection username as an inventory variable at registration time — RHEL AMIs' default user, needed because nothing in a dynamically-added host otherwise tells Ansible who to SSH in as.
hosts: just_provisioned / become: true
Play 2 targets exactly the group created above — Ansible will now connect over SSH to the real private IP for the first time in this run. become: true escalates to root for the baseline/hardening/disk tasks that follow, which require it.
◆ Concept

This is different from a persistent dynamic inventory plugin (like the amazon.aws.aws_ec2 inventory plugin, which queries AWS fresh at the start of every run to build a full inventory of many hosts) — add_host here is a one-off, in-memory addition scoped to a single playbook run, purpose-built for the "I just created this host in the same run I need to configure it" case. Both are "dynamic inventory" in the general sense; they solve different problems.

✕ Troubleshooting

"SSH timeout" incident: Play 2 fails immediately with a connection timeout to the new private IP. Before suspecting Ansible/add_host at all, check: (1) did Module 12's wait_for task actually complete successfully, or was it skipped/timed out silently upstream? (2) is the RHAAP execution node's security group/network path actually permitted to reach the target's private IP on port 22 (Module 6)? Nine times out of ten this is a Module 6 connectivity gap, not an add_host or inventory problem — the diagnostic habit from Module 6 (connectivity before credentials/logic) applies here too.

✓ Best Practice

Always guard the add_host task with a when condition (as shown: ec2_result.instances is defined) so it behaves correctly on the idempotent "already existed, creation skipped" branch from Module 13 too — in that branch, add a parallel path that looks up the existing instance's IP via the existing_instance variable instead, so Play 2 still has a host to target either way.

Module 15 — Linux Baseline

Configure & Harden · roles/linux_baseline — Turning a Bare RHEL Boot Into a Standard Node

1–2 · Beginner explanation and why it matters

Straight out of Module 14's Play 2 handoff, pay-dev-app01 is just a stock RHEL 9 boot of the approved AMI — it doesn't yet know its own hostname is meaningful, isn't synced to ShopSphere's time source, can't resolve internal DNS, and has no application-ready OS settings. "Baseline" means: every server, regardless of what application eventually runs on it, gets this exact same starting configuration, every time. This is the role most directly responsible for eliminating the configuration-drift problem raised all the way back in Chapter 1.

3 · ShopSphere story

Different application teams at ShopSphere used to hand-configure timezone, DNS, and SSH settings inconsistently — one legacy incident traced a bizarre certificate-expiry false alarm to a server whose clock had silently drifted because NTP was never actually configured by whoever built it manually. This role exists specifically so "was NTP configured" is never again a question anyone has to ask.

ansible.builtin.hostname
Sets the live kernel hostname to exactly the validated vm_name from Module 11 — using the module (not a raw hostnamectl shell command) means Ansible can detect "no change needed" on re-runs, keeping this idempotent per Module 13's discipline.
community.general.timezone: Etc/UTC
Standardizing every server to UTC — regardless of which region it's deployed in — is what makes cross-region log correlation (Module 24) and monitoring timestamps (Module 23) comparable without timezone-math errors during an incident.
ansible.builtin.template ... notify: restart chronyd
template renders a Jinja2 file (chrony.conf.j2, holding ShopSphere's internal NTP server addresses) to the target path. notify queues a handler (defined separately in handlers/main.yml) that only fires if this task actually changed the file — this is Module 33's changed_when philosophy in its most common form: don't restart a service unless its config genuinely changed.
ansible.builtin.lineinfile ... when: corporate_proxy_url is defined
Adds the proxy line only if a proxy URL variable is set — this ties directly back to Module 6's Design B (corporate proxy) connectivity pattern; environments using Design C (VPC endpoints) simply never define this variable, and the task is skipped, not conditionally broken.
ansible.builtin.user: payapp / shell: /sbin/nologin
Creates a dedicated, non-interactive service account for the application to run as — deliberately not root, and with no usable login shell, so even if the application process were compromised, an attacker can't use this account to get an interactive shell.
sudoers.d/payapp ... NOPASSWD: /usr/bin/systemctl restart payapp.service
Grants exactly one privileged capability — restarting one specific service — rather than broad sudo access. validate: "visudo -cf %s" runs syntax validation on the rendered file before it's accepted, so a malformed sudoers file can never be written live (a genuinely dangerous class of mistake to get wrong).
ansible.posix.selinux: state: enforcing
Explicitly asserts SELinux stays in enforcing mode — never permissive or disabled — closing off a very common (and very risky) "just disable SELinux to make the app work" shortcut some engineers reach for under deadline pressure. Module 17 builds on this baseline with more targeted SELinux policy work.
ansible.posix.firewalld: port: "{{ app_port }}/tcp"
Opens exactly the application's port (8080, from Chapter 1's ticket) and nothing else — firewalld starts from a default-deny posture, and this task is the only reason inbound traffic to the app can reach the host at all.
ansible.posix.sysctl loop
Applies kernel network-hardening parameters — disabling ICMP redirect acceptance and broadcast ping responses, both classic network-hardening defaults — via a loop over a list of key/value pairs rather than one task per parameter, keeping the role compact as the tuning list grows.
community.general.pam_limits: nofile: 65536
Raises the payapp account's open-file-descriptor limit above the RHEL default — a common, very real production gotcha where a perfectly healthy application starts throwing "too many open files" errors under load purely because this OS-level limit was never raised for its service account.
✓ Best Practice

This role runs identically for every environment and every application at ShopSphere — application-specific values (app_port, service account name) come in as variables, but the structure and standards are universal. The moment a baseline role starts branching heavily by application, it's a sign application-specific setup belongs in a separate, later role instead — keep baseline genuinely generic.

⚠ Warning

"package installation failure" incident: the "Install baseline package set" task fails with a repository-unreachable error. Before assuming a typo in the package list, check Module 6's connectivity chain first — DNS resolution of the repo, the proxy config this same role just wrote, and whether the corporate repo mirror is actually reachable from this subnet. Module 16 — Disk Configuration

Configure & Harden · roles/disk_configuration — From Raw EBS to a Mounted Filesystem

1–2 · Beginner explanation and why it matters

Module 12 attached a 200 GB EBS volume at /dev/sdb — but AWS creating and attaching a block device is not the same as the OS having a usable, mounted filesystem at /opt/payapp/data. That gap — raw block device to a place an application can actually write files — is what this role closes, and it's a real, multi-step Linux storage chain worth understanding properly, not just scripting blindly.

3 · The chain, and the commands an engineer uses to inspect each stage

EBS volume (AWS object) │ ▼ Linux device — /dev/nvme1n1 (inspect: lsblk) │ ▼ Partition — /dev/nvme1n1p1 (created via parted/partitioning module) │ ▼ LVM Physical Volume (PV) — pvs to inspect │ ▼ Volume Group (VG) — vgs to inspect — groups PVs so space can be resized later │ ▼ Logical Volume (LV) — lvs to inspect — a flexible slice of the VG │ ▼ Filesystem — xfs, created on the LV (inspect: blkid) │ ▼ Mount — attached to /opt/payapp/data (inspect: mount, df -h) │ ▼ /etc/fstab entry — makes the mount survive a reboot (Module 18 relies on this)
◆ Concept — why LVM at all, instead of formatting the raw partition directly

You could format /dev/nvme1n1p1 directly with a filesystem and skip PV/VG/LV entirely — it works. Enterprises use LVM anyway because it decouples "how much disk space is allocated" from "how the underlying physical storage is organized." When Payment Gateway later needs more disk space, an engineer can extend the EBS volume, extend the PV, extend the LV, and grow the filesystem — all live, with the application still running — something far harder to do safely with a raw partition.

4–6 · Code and line-by-line explanation

roles/disk_configuration/tasks/main.yml
- name: Create partition on data device
  community.general.parted:
    device: "{{ data_device }}"
    number: 1
    state: present
    part_type: primary
    fs_type: xfs

- name: Create LVM physical volume
  community.general.lvg:
    vg: payapp_vg
    pvs: "{{ data_device }}1"

- name: Create logical volume using all available space
  community.general.lvol:
    vg: payapp_vg
    lv: payapp_lv
    size: 100%FREE
    shrink: false

- name: Create xfs filesystem on logical volume
  community.general.filesystem:
    fstype: xfs
    dev: /dev/payapp_vg/payapp_lv

- name: Create mount point directory
  ansible.builtin.file:
    path: /opt/payapp/data
    state: directory
    owner: payapp
    group: payapp
    mode: "0750"

- name: Mount data volume and persist in fstab
  ansible.posix.mount:
    path: /opt/payapp/data
    src: /dev/payapp_vg/payapp_lv
    fstype: xfs
    opts: defaults,nofail
    state: mounted
community.general.parted ... fs_type: xfs
Creates partition number 1 on the raw data device — the fs_type hint here influences the partition's type flag, not the actual formatting (that happens later, in the filesystem task) — a subtlety worth knowing so you don't assume the disk is usable after this task alone.
community.general.lvg: vg: payapp_vg, pvs: "{{ data_device }}1"
Initializes the partition as an LVM Physical Volume and creates the Volume Group in one task — "{{ data_device }}1" string-concatenates the device path with the partition number (e.g. /dev/nvme1n1 + 1), a common Ansible/Jinja2 pattern for building device paths from a base variable.
community.general.lvol: size: 100%FREE
Allocates the entire Volume Group's available space to this one Logical Volume — appropriate here since there's exactly one data mount per server, but in a multi-LV design you'd size each explicitly instead. shrink: false is a safety guard: it prevents this task from ever silently shrinking an existing LV on a re-run if the calculated size were somehow smaller than current.
community.general.filesystem: fstype: xfs
Formats the logical volume with xfs — RHEL's default and recommended filesystem, chosen (per Module 2's storage checklist) as ShopSphere's standard unless a specific application justifies an exception. The module is idempotent: it checks for an existing filesystem signature before formatting, so re-running this never destroys existing data.
ansible.posix.mount: opts: defaults,nofail ... state: mounted
state: mounted both mounts the filesystem immediately and writes the corresponding /etc/fstab line — a single task accomplishing what would otherwise be two ("mount now" plus "persist across reboot"). nofail is a deliberately important flag: without it, if this EBS volume ever failed to attach on a future boot, the entire server would drop to an emergency shell at boot time instead of booting normally without the data disk — nofail lets the OS boot regardless, so monitoring (Module 23) can catch and alert on the missing mount instead of the whole server becoming unreachable.
✕ Troubleshooting

"Disk mounting failure" / "LVM failure" / "fstab error" incidents: Symptom — the mount task fails, or worse, the server fails to boot cleanly after a change here. Investigation order: lsblk to confirm the device even shows up as attached (an AWS-side attach issue looks identical to an OS-side problem until you check this), then pvs/vgs/lvs to confirm each LVM layer actually exists as expected, then blkid to confirm the filesystem signature is really there, and only then look at the fstab line itself. Working top-down through this exact chain — the same chain from the diagram above — is faster than guessing.

✓ Best Practice

Always include nofail (and consider x-systemd.device-timeout= for EBS volumes that can take a few seconds to attach on boot) for any non-root fstab entry. A single misconfigured secondary mount should degrade one application's functionality, observably, in monitoring — it should never be able to take an entire server offline at boot.

☰ Interview Question

"Why use LVM instead of formatting the raw EBS partition directly?" Lead with online resizing/flexibility, and be ready to name the actual layer order (PV → VG → LV → filesystem) and the inspection command for each layer — pvs, vgs, lvs, blkid — since being able to name the right diagnostic tool per layer is what interviewers are really probing for.

▶ Hands-On

On any Linux VM (even a personal one, not AWS), attach a second small virtual disk and walk this entire chain by hand with raw commands first — parted, pvcreate, vgcreate, lvcreate, mkfs.xfs, then mount and a manual /etc/fstab edit. Doing it manually once makes every task in this role's YAML instantly recognizable rather than abstract.

Module 17 — Security Hardening

Configure & Harden · roles/security_hardening — Actively Reducing Attack Surface

1–2 · Beginner explanation and why it matters

Where Module 15's baseline made the server functional and standardized, this role makes it defensible in a security audit. The distinction matters: baseline is "does every server start the same way"; hardening is "does every server actively resist the specific attack patterns our security team cares about" — CIS Benchmarks-style controls, SSH restriction, and tamper-evident logging via auditd.

4–7 · Code and line-by-line explanation

roles/security_hardening/tasks/main.yml
# --- SSH hardening ---
- name: Disable SSH root login
  ansible.builtin.lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?PermitRootLogin'
    line: 'PermitRootLogin no'
  notify: restart sshd

- name: Disable SSH password authentication (keys only)
  ansible.builtin.lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?PasswordAuthentication'
    line: 'PasswordAuthentication no'
  notify: restart sshd

# --- Password policy ---
- name: Enforce minimum password length and complexity
  ansible.builtin.lineinfile:
    path: /etc/security/pwquality.conf
    regexp: '^minlen'
    line: 'minlen = 14'

# --- File permissions ---
- name: Restrict permissions on sensitive files
  ansible.builtin.file:
    path: "{{ item }}"
    mode: "0600"
  loop:
    - /etc/shadow
    - /etc/gshadow

# --- Remove/disable unnecessary services ---
- name: Disable and stop unneeded services
  ansible.builtin.systemd_service:
    name: "{{ item }}"
    state: stopped
    enabled: false
  loop:
    - rpcbind
    - cups
  failed_when: false

# --- auditd — tamper-evident logging (CIS control) ---
- name: Ensure auditd is installed and running
  ansible.builtin.systemd_service:
    name: auditd
    state: started
    enabled: true

- name: Audit all use of privilege escalation commands
  ansible.builtin.lineinfile:
    path: /etc/audit/rules.d/audit.rules
    line: "-w /usr/bin/sudo -p x -k privilege_escalation"
    create: true
  notify: restart auditd
PermitRootLogin no / PasswordAuthentication no
Two of the highest-value SSH hardening lines that exist: disabling root login forces every administrative session to authenticate as a named user first (accountability — Module 34 traceability again), and disabling password auth means SSH access requires possessing a private key, closing off brute-force and credential-stuffing attacks entirely.
regexp: '^#?PermitRootLogin'
Matches the line whether it's currently commented out (#PermitRootLogin ...) or already set — lineinfile then replaces whichever form it finds with the exact desired line:, making this task correctly idempotent regardless of the AMI's starting sshd_config state.
minlen = 14
A concrete CIS-style control — minimum 14-character passwords — chosen here as a specific, auditable number rather than a vague "strong passwords" policy; auditors and compliance scanners check for exact configured values like this.
file: /etc/shadow, mode: "0600"
Ensures the password hash file is readable only by root — a classic CIS Benchmark item; a permissive shadow file is a real, checked-for finding in vulnerability scans (Module 21) if this baseline control is ever skipped.
systemd_service ... failed_when: false
failed_when: false tells Ansible not to fail the play even if this task's underlying command returns non-zero — appropriate here because a minimal AMI may not have cups installed at all, and "the service doesn't exist to disable" isn't a real failure for this task's intent. Overusing failed_when: false elsewhere is a real anti-pattern (Module 33) — it's justified here specifically because the desired end state (service not running) is already true either way.
-w /usr/bin/sudo -p x -k privilege_escalation
A raw auditd watch rule: -w watches a path, -p x logs execute events specifically, -k tags matching log entries with a searchable key. This is exactly the kind of forensic hook a security team needs after an incident — "show me every execution of sudo on this host" becomes a single ausearch -k privilege_escalation command instead of grepping raw logs.
⛨ Security

This role is a direct, executable implementation of Module 2's security checklist and Module 3's trust-boundary discussion — SSH access model, and it's also exactly what an external security auditor or PCI-DSS-adjacent compliance review (referenced back in Module 1's story about why Payment Gateway needs a dedicated VM at all) will check line-by-line. Treat this role's task list as something that should be traceable to a named compliance control, not just "things that sound secure."

✓ Best Practice

Keep hardening rules data-driven where they repeat (the loop patterns above) so adding a new CIS control is a one-line addition to a list, not a new hand-written task — this is what lets a security team hand your team an updated CIS benchmark spreadsheet and have it become working automation quickly.

Remediation: patching a specific CVE a scanner just reported. The underlying distinction — proactive/uniform vs. reactive/specific — is the answer interviewers are checking for.

Module 18 — Patching

Operate the Fleet · The Server's Life Doesn't End at Provisioning

1–2 · Beginner explanation and why it matters

Everything through Module 17 builds pay-dev-app01 once. Patching is the first "ongoing operations" module — the process that runs against this same server monthly (or per ShopSphere's SLA) for its entire life. 3 · The enterprise patching workflow

ServiceNow Change (patching-specific CHG record) │ ▼ Approval (change advisory board for PROD; lighter-weight for DEV/QA) │ ▼ Pre-check — is the server healthy right now?   delay: 15
Pre-check ... Abort if not already healthy
A deliberate safety gate: never patch a server that's already unhealthy — if payapp is already down before you touch anything, patching won't be the fix, and proceeding anyway would make an existing incident harder to diagnose by conflating two problems into one.
dnf: name: "*", security: true, state: latest
security: true is the key parameter — it restricts the update to packages with security advisories only, deliberately not a blanket "update everything" (that's a much larger, riskier change, usually reserved for a planned OS upgrade — Module 20). This is exactly the distinction ShopSphere's monthly patch SLA is built around: security patches on a predictable cadence, feature/version upgrades on a separate, more deliberate track.
needs-restarting -r ... changed_when: false, failed_when: false
A raw shell command (RHEL's own reboot-advisory tool) wrapped so it never itself reports as a change (it's read-only) and never fails the play (its exit code is meaningful data, not an error) — its return code is what the next task's when condition actually reads.
ansible.builtin.reboot: when: reboot_check.rc == 1
Only reboots when needs-restarting -r returned exit code 1 (meaning "yes, a reboot is needed") — this is what makes patching correctly conditional: a run that only touched non-kernel userspace packages completes without ever rebooting the server, minimizing unnecessary downtime.
Post-check ... until / retries / delay
Polls the service state up to 10 times, 15 seconds apart, rather than checking once immediately after reboot — giving the application time to actually finish starting, since "the OS rebooted successfully" and "the application is healthy again" are, once again (echoing Module 12's wait_for lesson), two different milestones that shouldn't be conflated.
⚠ Warning

"Patch failure" / "Kernel issue" incidents: a patch applies cleanly but the post-reboot check never goes healthy. Before anything else, check whether the failure is patch-caused or coincidental (was the server already flaky pre-patch — this is exactly why the pre-check exists, to make that question answerable). If it is patch-caused, the fastest safe recovery is usually restoring from the Module 26 snapshot taken immediately before patching — not attempting to manually downgrade packages live under time pressure.

✓ Best Practice

Never patch and reboot in the same breath without a pre-check gate and a post-check gate around it. The three-part shape here — verify healthy, act, verify healthy again — is a pattern worth reusing in Module 20 (OS Upgrade) and Module 21 (Vulnerability Remediation) too, since both carry the same "we're about to change something on a live server" risk profile.

3 · The controls that make fleet-wide patching safe

ControlWhat it does

- name: Monthly security patching — PROD Payment Gateway fleet
  hosts: prod_payment_servers
  become: true
  serial:
    - 25
    - 25
    - "100%"
  max_fail_percentage: 10
  roles:
    - patching
serial: [25, 25, "100%"]
A staged ramp-up across three batches: the first 25 servers, then another 25, then whatever remains of the 500. Each batch runs the entire role (patch, reboot-if-needed, post-check) to completion for every host in that batch before the next batch starts — so batch 2 never begins until batch 1 has fully proven itself healthy.
max_fail_percentage: 10
If more than 10% of hosts in any single batch fail (2–3 servers out of the first 25, in this case), Ansible stops the entire play immediately rather than proceeding to batch 2 — this is the mechanism that actually prevents "the same bad patch just failed 300 more production servers," turning what could be a fleet-wide outage into a contained, 25-server incident.

✎ ShopSphere Story

Last quarter, a batch-1 run against 25 PROD Payment Gateway servers hit a 16% failure rate — four servers failed their post-patch health check due to an unrelated storage-team maintenance window nobody had cross-checked against the patching schedule. Because max_fail_percentage: 10 was configured, the run stopped automatically after batch 1 instead of proceeding to patch (and potentially degrade) the remaining 475 servers during an already-degraded storage event. This is the entire value of this module in one real incident.

✓ Best Practice

Start batch sizes small and escalate ([5, 25, "100%"] rather than one flat serial: 25) for the highest-risk environments — a 5-server first batch catches a catastrophically bad patch cheaply, before committing to a 25-server batch. DEV/QA can reasonably run with larger flat batch sizes or even no serial at all, since Module 2's risk tiering applies here too.

⚠ Warning

A serial batch is only as safe as the health check gating it. If the patching role's post-check (Module 18) is shallow — just "is the process running," not "is the application actually responding correctly" — a batch can report 100% success while genuinely degrading the fleet in a way max_fail_percentage never catches, because nothing failed loudly. Module 40's application-readiness validation logic is worth reusing here, not just a basic systemd status check.

Module 20 — OS Upgrade

Operate the Fleet · A Fundamentally Riskier Operation Than Patching

1–2 · Beginner explanation and why it's different from patching

Patching (Module 18) updates packages within the same major OS version — RHEL 9.3 to RHEL 9.4, say — where compatibility is largely guaranteed by Red Hat. An OS upgrade — RHEL 8 to RHEL 9 — is a major version jump: different kernel baseline, potentially different default versions of core libraries, and a real chance that something about the running application's dependencies genuinely doesn't work the same way afterward. This is categorically riskier, and enterprises treat it that way procedurally, not just technically.

3 · The workflow

RHEL 8 (current state) │ ▼ Pre-upgrade assessment — leapp preupgrade — inventories what might break │ ▼ Backup — full application-aware backup, not just an EBS snapshot alone │ ▼ Snapshot — EBS snapshot immediately before the upgrade, for fast infra-level rollback │ ▼ Compatibility checks — review leapp's report; resolve or explicitly accept each flagged risk │ ▼ Leapp — the actual in-place upgrade tool │ ▼ Upgrade — leapp performs the OS-level transition │ ▼ Reboot — required, unconditionally, unlike patching's conditional reboot │ ▼ RHEL 9 (target state) │ ▼ Validation — OS health, application readiness, monitoring — all three, thoroughly

4 · Why leapp specifically, and what it does

leapp is Red Hat's supported in-place major-version upgrade tool. leapp preupgrade runs a comprehensive inventory of the system — installed packages, custom kernel modules, configuration files known to change behavior across major versions — and produces a report of risks, ranging from informational to "will block the upgrade until addressed." Only after every blocking risk is resolved (or a documented, approved exception is made) does leapp upgrade actually proceed.

playbooks/os_upgrade.yml (structure, with safe checkpoints)
- name: RHEL 8 → 9 in-place upgrade with checkpoints
  hosts: pay_prod_app01
  become: true
  serial: 1
  tasks:

    - name: Run leapp pre-upgrade assessment
      ansible.builtin.command: leapp preupgrade --report-schema=1.2.0
      register: preupgrade_result
      changed_when: false

    - name: CHECKPOINT — take pre-upgrade EBS snapshot before proceeding
      amazon.aws.ec2_snapshot:
        instance_id: "{{ instance_id }}"
        device_name: /dev/sda1
        description: "pre-leapp-upgrade {{ change_number }}"
      register: pre_upgrade_snapshot

    - name: Execute leapp upgrade
      ansible.builtin.command: leapp upgrade
      register: upgrade_result

    - name: Reboot into the upgrade (mandatory, not conditional)
      ansible.builtin.reboot:
        reboot_timeout: 900
        msg: "RHEL 9 upgrade reboot — {{ change_number }}"

    - name: CHECKPOINT — confirm OS version is actually RHEL 9 post-reboot
      ansible.builtin.assert:
        that:
          - ansible_facts['distribution_major_version'] == '9'
        fail_msg: "Upgrade did not complete — still on major version {{ ansible_facts['distribution_major_version'] }}"
serial: 1
OS upgrades run one server at a time, unlike Module 19's larger patching batches — the risk profile of a major version jump justifies the slowest, most cautious rollout of anything in this masterclass.
leapp preupgrade ... changed_when: false
The assessment step makes no changes to the system — it only inspects and reports — so it's explicitly marked as never "changed," keeping Ansible's change-reporting accurate for anyone reviewing this job's output later.
amazon.aws.ec2_snapshot ... "pre-leapp-upgrade {{ change_number }}"
A named, change-record-tagged snapshot taken as the last safe checkpoint before anything irreversible happens — if the upgrade goes badly, this snapshot (paired with the instance's volume) is the fastest path back to a known-good RHEL 8 state, restoring by volume rather than trying to "undo" an in-place upgrade, which isn't realistically possible.
reboot: reboot_timeout: 900
A much longer timeout than Module 18's patching reboot (300s) — a major version upgrade's first boot genuinely takes longer as the new kernel and updated services initialize; using the same short timeout as routine patching here would cause false-failure aborts on a perfectly succeeding upgrade.
ansible_facts['distribution_major_version'] == '9'
The single most important checkpoint in this whole playbook: don't just assume the reboot succeeding means the upgrade succeeded — explicitly re-gather facts post-reboot and assert the OS is genuinely reporting as RHEL 9. This closes the same "assumed success ≠ verified success" gap Module 12's wait_for closed for provisioning.
⛨ Security

An OS stuck on an end-of-life major version (RHEL 8 past its support window) stops receiving security patches from Red Hat entirely — meaning Module 18's patching role has nothing left to apply, regardless of how well it's automated. OS upgrade planning is, in that sense, a security-driven deadline as much as a technical modernization one.

✓ Best Practice

Never treat leapp preupgrade's report as optional reading. A real, disciplined rollback plan for an OS upgrade means: snapshot taken, restore procedure tested (not just assumed to work) beforehand in a non-PROD environment, and an explicit go/no-go decision point between assessment and execution — not a single unattended playbook run from start to finish on a PROD server.

Module 21 — Vulnerability Management

Operate the Fleet · Closing the Loop From "Found" to "Verified Fixed"

1–2 · Beginner explanation and why it matters

Patching (Module 18) is scheduled and proactive. Vulnerability management is reactive and driven by an external scanner's findings — and it needs its own tracked lifecycle because "we applied a fix" and "the scanner confirms the vulnerability is actually gone" are two different, both-necessary facts. A vulnerability ticket that gets closed without a rescan is exactly the kind of gap a compliance audit will find.

3 · Vocabulary

TermMeaning
CVECommon Vulnerabilities and Exposures — a unique public identifier for one specific, documented security flaw (e.g. CVE-2024-XXXXX).
CVSSCommon Vulnerability Scoring System — a 0–10 numeric severity score computed from the flaw's exploitability and impact characteristics.
CriticalTypically CVSS 9.0–10.0 — remote, low-complexity exploitation with severe impact; usually mandates fastest remediation SLA (e.g. 48–72 hours in PROD).
HighTypically CVSS 7.0–8.9 — serious impact, may require more complex exploitation conditions; standard SLA often 7–14 days.
MediumTypically CVSS 4.0–6.9 — real but lower-urgency risk; often bundled into the next regular patch cycle (Module 18/19).
LowTypically CVSS 0.1–3.9 — minimal practical risk; tracked, but rarely the sole reason for an out-of-cycle change.

4 · The lifecycle

Security Scanner (Module 22 — Qualys/Tenable/Rapid7-style) │ ▼ Vulnerability Found → identified as a specific CVE │ ▼ Severity assigned (CVSS score → Critical/High/Medium/Low) │ ▼ ServiceNow Ticket created — SLA clock starts based on severity │ ▼ RHAAP — remediation Job Template launched (this module's role) │ ▼ Patch / Configuration Fix applied │ ▼ Reboot (if the fix requires it) │ ▼ Rescan — the scanner is asked to check this specific host/CVE again │ ▼ Ticket Closure — only after the rescan confirms the finding is actually gone

5–7 · Code and line-by-line explanation

playbooks/vulnerability_remediation.yml
- name: Remediate scanner-reported CVE on {{ vm_name }}
  hosts: "{{ target_host }}"
  become: true
  tasks:

    - name: Confirm the specific package version currently installed
      ansible.builtin.dnf:
        list: "{{ affected_package }}"
      register: current_pkg

    - name: Apply the specific fixed package version for {{ cve_id }}
      ansible.builtin.dnf:
        name: "{{ affected_package }}-{{ fixed_version }}"
        state: present
      register: remediation_result

    - name: Reboot if this package requires it
      ansible.builtin.reboot:
        msg: "Remediation reboot for {{ cve_id }} — {{ change_number }}"
      when: reboot_required | default(false)

    - name: Record remediation evidence for audit trail
      ansible.builtin.debug:
        msg: "{{ cve_id }} remediated on {{ vm_name }}: {{ affected_package }} -> {{ fixed_version }}, change {{ change_number }}"

    # Rescan is triggered externally against the scanner's own API/schedule —
    # this play's job is done once the fix + evidence exist; ticket closure
    # waits on the scanner's independent confirmation, by design (see below).
Confirm the specific package version ... register: current_pkg
Recorded before remediation as evidence of the starting state — useful both for the audit trail and for confirming, if something goes wrong, exactly what version was running when the CVE was reported.
name: "{{ affected_package }}-{{ fixed_version }}"
Installs the exact fixed version the scanner/vendor advisory specifies — deliberately narrower than Module 18's security: true blanket update, because a vulnerability remediation ticket is scoped to one specific CVE and one specific package, not a general patch sweep.
when: reboot_required | default(false)
The default(false) filter provides a safe fallback if reboot_required was never explicitly set by whatever passed this playbook its variables (typically populated from the scanner's own advisory data, via ServiceNow/RHAAP integration) — a task never accidentally reboots a server because a variable was simply missing.
Record remediation evidence ... ansible.builtin.debug
Writes a clear, structured line into the job output specifically so the eventual ServiceNow ticket closure has a concrete evidence trail to reference — connecting back to Module 1's point about job output being what an auditor or a 2am engineer actually reads.
◆ Concept — why this playbook deliberately does not trigger its own rescan

The rescan step is intentionally left to the scanner's own independent schedule or API trigger (Module 22), not bundled into this playbook. This is a deliberate separation of duties: the same system that applies a fix should not be the sole system that verifies the fix worked — an independent rescan is what actually proves remediation, rather than the remediation tool grading its own work.

⚠ Warning

"Vulnerability still detected" incident: a rescan still flags the same CVE after remediation ran successfully. Common real causes, in likely order: the fixed package version was installed but a running process is still using the old version in memory (needs a service restart or reboot, not just a package update); the CVE applies to a container image or embedded dependency the OS-level package manager doesn't touch at all; or the scanner's own vulnerability database hasn't refreshed since the fix. Each has a different fix — don't assume "still detected" always means "remediation didn't work."

✓ Best Practice

Track remediation SLA by severity explicitly (Critical/High/Medium/Low from the vocabulary table) and let that drive urgency — a Critical finding on a PROD server should be able to trigger an expedited, smaller-blast-radius Job Template run outside the normal monthly patch cycle, rather than waiting for the next scheduled Module 18/19 run.

roles/vulnerability_scan_agent/tasks/main.yml
- name: Download scanner agent installer from internal repository

get_url ... checksum: "sha256:{{ scanner_agent_sha256 }}"
Downloads from ShopSphere's own internal repository mirror (never the vendor's public internet endpoint directly, consistent with Module 6's connectivity design), and — critically — verifies a checksum before proceeding. This is a supply-chain safeguard: installing a security agent is exactly the kind of privileged action where you don't want to trust an unverified binary, even from an internal mirror.
scanner-agent-ctl --activation-key="{{ scanner_activation_key }}"
The activation key is what proves to the scanner's console that this agent belongs to ShopSphere's account/tenant — it's a credential, sourced from RHAAP's Credential store (Module 29), never hardcoded in this file or committed to Git.
no_log: true
Suppresses this task's arguments and output from appearing in RHAAP job logs at all — necessary because the command line itself contains the activation key; without no_log, a secret would leak straight into job output, defeating the entire purpose of storing it as a credential in the first place.
changed_when: "'already registered' not in agent_registration.stdout"
A custom idempotency signal: the raw registration command doesn't cleanly report Ansible-style changed/unchanged on its own, so this inspects its stdout text for a known "already registered" phrase to decide whether re-running this task actually did anything — a common, necessary pattern whenever wrapping a vendor CLI tool that wasn't designed with Ansible idempotency semantics in mind.

Download → Install → Configure → Register → Start → Validate

⛨ Security

⚠ Warning

Queries the monitoring platform's own API — not the local agent's own status, which could report "I think I'm fine" even if it's failing to actually reach the platform — asking the platform itself "do you see this host reporting" is a meaningfully stronger check.
until: monitoring_status.json.reporting == true / retries: 12 / delay: 10
Polls for up to two minutes (12 × 10s) waiting for the platform to confirm live data is flowing — agents typically take a few seconds to establish their first successful check-in, so an immediate single check would produce false failures on a perfectly healthy agent that just needs a moment.
no_log: true
Suppresses the task's full output (which includes the Authorization header) from job logs — the same secret-leakage concern from Module 22, applied here to the monitoring API token.
◆ Concept — why this role fails the workflow instead of just warning

Notice there's no failed_when: false anywhere in this role — if the monitoring platform never confirms the agent is reporting, the task genuinely fails, and (per Module 32's workflow design) the whole provisioning run is marked failed. This is a deliberate choice: an unmonitored server that silently "succeeded" provisioning is worse than a provisioning run that visibly fails and gets fixed before go-live — the entire point of Chapter 1's original problem (nobody notices a broken server) would otherwise reappear here, just one layer downstream.

⚠ Warning

"Monitoring agent installation failure" incident: the package installs and the service starts, but the platform never confirms reporting. Investigation order: is the config template rendering a correct endpoint URL (a stale group_vars value pointing at a decommissioned monitoring collector is a real, recurring cause)? Is outbound connectivity from this host to that endpoint actually permitted (Module 6)? Only after both check out should you suspect the agent binary itself or the API token's validity.

✓ Best Practice

Tier alert thresholds and paging behavior by environment, not by a one-size-fits-all default — a DEV server crossing 90% CPU shouldn't page anyone at 3am; the same threshold on a PROD Payment Gateway server should. Encoding this as a lookup keyed by the environment variable (rather than hardcoding thresholds per-role) keeps this consistent with every other environment-tiering decision made since Module 2.

"How do you know a server was successfully onboarded into monitoring, rather than just that the install command didn't error?" The answer is the validation task above — querying the monitoring platform's own API to confirm it's actually receiving data, with retries, and treating a failure to confirm as a hard workflow failure rather than a soft warning.

Module 25 — Security / EDR Agent

Observe & Protect · roles/edr_agent — The Last Mandatory Agent Before Go-Live

1–2 · Beginner explanation and why it matters

EDR (Endpoint Detection and Response) is host-level security software that watches for malicious behavior in real time — process execution patterns, unusual network connections, file tampering — and can alert or automatically respond (isolating a host from the network, killing a process) faster than a human ever could. Products like CrowdStrike Falcon or SentinelOne are common examples; this masterclass names them only as recognizable references, not as an endorsement of either — the pattern generalizes to any enterprise EDR platform.

3 · The universal onboarding pattern

Download — installer package, from an internal mirror, never the vendor's public internet endpoint directly (Module 6's connectivity design again) │ ▼ Install — package installed via the OS package manager │ ▼ Configure — sensor policy, tags (Application/Environment/CostCenter — same set as everywhere else), and the EDR console's tenant endpoint │ ▼ Register — the sensor authenticates itself to the vendor's cloud console using a scoped installation token (never a long-lived, broadly-privileged key) │ ▼ Start — the sensor service begins actively monitoring │ ▼ Validate — confirm, against the EDR console's own API, that this specific host now appears as an actively reporting, protected endpoint

4–6 · Code and line-by-line explanation

roles/edr_agent/tasks/main.yml
- name: Download EDR sensor installer from internal mirror
  ansible.builtin.get_url:
    url: "{{ edr_installer_url }}"
    dest: /tmp/edr-sensor.rpm
    checksum: "sha256:{{ edr_installer_sha256 }}"
    mode: "0644"

- name: Install EDR sensor package
  ansible.builtin.dnf:
    name: /tmp/edr-sensor.rpm
    state: present

- name: Register sensor to EDR console with scoped install token
  ansible.builtin.command:
    cmd: edr-sensor-ctl --install-token="{{ edr_install_token }}" --tag="Environment:{{ environment }},Application:{{ application_name }},CostCenter:{{ cost_center }}"
  register: edr_registration
  changed_when: "'already licensed' not in edr_registration.stdout"
  no_log: true

- name: Start EDR sensor service
  ansible.builtin.systemd_service:
    name: edr-sensor
    state: started
    enabled: true

- name: Validate host appears as protected in EDR console
  ansible.builtin.uri:
    url: "https://edr-console.shopsphere.internal/api/v1/hosts?hostname={{ vm_name }}"
    headers:
      Authorization: "Bearer {{ edr_api_token }}"
    status_code: 200
  register: edr_status
  until: edr_status.json.hosts | length == 1 and edr_status.json.hosts[0].status == 'protected'
  retries: 15
  delay: 10
  no_log: true
--install-token="{{ edr_install_token }}"
An install token is deliberately different from a general API credential — it's scoped narrowly to "register one new sensor," typically short-lived or single-tenant-scoped, so its exposure risk is far lower than a broad API key. This is the EDR-specific instance of Module 5's least-privilege philosophy.
--tag="Environment:...,Application:...,CostCenter:..."
The exact same three tag dimensions used for EC2 tagging (Module 12), monitoring (Module 23), and logging (Module 24) — a security analyst investigating an EDR alert on this host can immediately see which application, environment, and cost center it belongs to without cross-referencing a separate system.
no_log: true (both tasks)
Applied to both the registration command (contains the install token) and the validation query (contains the API token in its Authorization header) — consistent with Module 22 and Module 23's secret-handling discipline; by this point in the masterclass this should feel like a reflex, not a one-off decision.
until: ... hosts[0].status == 'protected'
Doesn't just check that the host is registered — checks that the console reports its status as actively protected, since some EDR platforms distinguish a "registered but not yet fully initialized" state from a genuinely active-protection state. Treating registration alone as success would be a false positive on exactly the control ShopSphere's compliance posture (Module 1) most needs to be real.
⛨ Security

EDR is very often the single hardest requirement to skip or fake convincingly in a compliance audit, precisely because "protected" is independently verifiable against the vendor's own console by an outside auditor — which is exactly why this role's validation step queries that same console rather than trusting the local sensor's self-reported status. Never mark this role successful based on the install command's exit code alone.

⚠ Warning

"Security agent failure" incident: the sensor installs and the service shows active, but the console never shows the host as protected. A frequent real cause: the sensor is running but can't reach the vendor's cloud console at all (outbound connectivity again — Module 6), so it's running locally but never actually phoning home. Another frequent cause: a stale or already-consumed install token — tokens are often single-use or short-lived by design, and a token reused across a batch of servers provisioned close together can fail on the second and subsequent hosts.

✓ Best Practice

Generate a fresh, single-use install token per provisioning run rather than reusing one static token across the whole fleet — this is both better security practice (limits blast radius of a leaked token) and avoids the exact "second server in a batch fails to register" failure mode above. Module 29 covers how to source a fresh token from Vault/CyberArk at runtime rather than a static credential.

☰ Interview Question

"How do you guarantee every provisioned server actually has EDR protection active before it's considered production-ready?" The answer is the validation task's specific check — status equals protected, confirmed against the vendor console's own API with retries — not simply "we install the agent as part of the role." Interviewers in regulated industries ask this question specifically because "we install it" and "we verify it's actually protecting" are different claims.

Module 26 — Backup

Observe & Protect · roles/backup — "Backup Completed" Is Not the Same Claim as "Restore Works"

1–2 · Beginner explanation and why it matters

This module's title line is worth sitting with: a backup job reporting success only proves data was copied somewhere — it says nothing about whether that copy can actually be restored into a working server. Enterprises that have been burned by this distinction (discovering, during a real incident, that months of "successful" backups were subtly corrupt or incomplete) treat restore testing as a first-class, scheduled activity, not an afterthought.

3 · The building blocks

MechanismWhat it capturesRestore speed
EBS SnapshotsBlock-level copy of a volume at a point in timeFast — new volume from snapshot in minutes
AWS BackupA managed service that orchestrates and centrally tracks snapshots (EBS and others) against defined backup plans/retention rulesSame underlying speed as EBS snapshots, with centralized policy and reporting on top
Application-aware backupA backup taken with the application quiesced or in a consistent state — critical for anything with in-flight transactions, like a payment gateway's dataDepends on the application's own consistency mechanism, but restore is meaningfully more trustworthy
RetentionHow long each backup is kept before automatic deletion — must match compliance/business requirements, not just "as long as convenient"N/A — a policy setting, not a mechanism
EncryptionBackups inherit the source volume's KMS encryption (Module 12) — an unencrypted backup of an encrypted volume would itself be a real compliance gapN/A

✎ ShopSphere Story

Application-aware backup matters specifically for pay-dev-app01's data volume because a block-level snapshot taken mid-write, while the application has data partially flushed to disk, can capture a filesystem in an inconsistent state — recoverable in theory, but not something ShopSphere's Payment Team wants to discover for the first time during an actual incident. This role coordinates with the application (a brief pre-snapshot hook, if the application supports one) rather than snapshotting blindly at an arbitrary moment.

4–6 · Code and line-by-line explanation

roles/backup/tasks/main.yml
- name: Register instance with AWS Backup plan via tag-based selection
  amazon.aws.ec2_tag:
    region: "{{ aws_region }}"
    resource: "{{ instance_id }}"
    tags:
      BackupPlan: "{{ backup_plan_name }}"
      RetentionDays: "{{ backup_retention_days }}"
    state: present

- name: Confirm AWS Backup plan has picked up this instance
  ansible.builtin.command:
    cmd: aws backup list-protected-resources --query "Results[?ResourceArn=='{{ instance_arn }}']" --output json
  register: backup_protection_check
  changed_when: false
  retries: 6
  delay: 30
  until: (backup_protection_check.stdout | from_json | length) > 0

- name: Take an immediate on-demand backup as day-one baseline
  amazon.aws.ec2_snapshot:
    instance_id: "{{ instance_id }}"
    description: "day-one baseline — {{ vm_name }} — {{ change_number }}"
    tags:
      Application: "{{ application_name }}"
      Environment: "{{ environment }}"
amazon.aws.ec2_tag: BackupPlan / RetentionDays
Rather than this role directly creating snapshot schedules itself, it tags the instance so AWS Backup's own tag-based resource selection automatically picks it up into the correct plan — this is a deliberate design choice: backup scheduling and retention policy live in one centrally managed place (AWS Backup), not scattered across every provisioning role's own logic.
aws backup list-protected-resources ... until: length > 0
Confirms, against AWS Backup's own inventory, that tag-based selection actually picked up this specific instance — tagging alone doesn't guarantee immediate pickup, so this validation (with retries, since AWS Backup's selection can take a short time to reflect a new tag) closes the same "don't just assume, verify" gap seen in Modules 23–25.
Take an immediate on-demand backup as day-one baseline
Rather than waiting for the first scheduled backup window (which could be up to 24 hours away), this task takes one immediate snapshot at provisioning time — so a server that's terminated or corrupted in its first hours of life still has at least one recovery point, instead of a gap where "backed up" was technically configured but nothing had actually run yet.

7 · Restore testing — the part that's easy to skip and shouldn't be

Scheduled restore-test job (separate from this role — runs periodically, e.g. quarterly) │ ▼ Pick a recent production backup at random (not always the newest — test older-in-retention backups too, since a subtle corruption might only show up several backup cycles later) │ ▼ Restore it into an isolated test environment — never directly into PROD │ ▼ Boot the restored instance; run automated health checks (reuse Module 40's application-readiness role — the same validation logic that certifies a new server also certifies a restored one) │ ▼ Record pass/fail, with evidence, as its own auditable record — distinct from and in addition to the routine backup job's own success/failure log
⚠ Warning

A backup job dashboard showing 100% success for months is not evidence the backups are restorable — it's only evidence the copy operation completed. The single most damaging finding a real incident postmortem can produce is discovering, only when a restore was actually needed, that backups had been quietly unusable the whole time. Restore testing is the only thing that closes this gap, and it needs to be scheduled and tracked with the same rigor as the backup job itself, not treated as optional due diligence.

✓ Best Practice

Set backup_retention_days per environment via the same group_vars pattern as everything else (Module 10) — DEV backups might reasonably retain for 7 days, PROD Payment Gateway backups for a much longer period driven by compliance requirements referenced back in Module 1. Never hardcode a single retention value across all environments.

☰ Interview Question

The honest, strong answer is never "the backup job shows success" alone — it's a scheduled, tracked restore-testing process that periodically proves a real backup can become a real, working, validated server again. Naming that distinction explicitly is what this question is really probing for.

Module 27 — DNS

Naming, Certs & Secrets · roles/dns_registration — pay-dev-app01 Gets a Name

1–2 · Beginner explanation and why it matters

Everything so far has addressed pay-dev-app01 by its raw private IP — fine for Ansible's own connections, but nothing an application team wants to hardcode into their own service configuration. DNS registration is what turns an IP address into a stable, memorable name that other services, load balancers, and humans can actually depend on — and critically, a name that doesn't change even if the underlying server ever gets rebuilt with a new IP.

3 · Route53 Private Hosted Zones — the enterprise pattern

ShopSphere doesn't use public DNS for internal servers — Payment Gateway's DEV server has no business being resolvable from the public internet at all. A Route53 Private Hosted Zone is a DNS zone that only resolves within specified VPCs — company.internal, in this story — giving ShopSphere the convenience of standard DNS tooling without any public exposure.

EC2 instance created (Module 12) → private IP known │ ▼ roles/dns_registration runs │ ▼ Route53 API call: create/update an A record in the Private Hosted Zone pay-dev-app01.company.internal → 10.10.5.25 │ ▼ Record only resolves for hosts inside VPCs associated with this Private Hosted Zone — never from the public internet │ ▼ Every subsequent reference to this server — monitoring (Module 23), logging (Module 24), application config the Payment Team writes — can use the stable DNS name instead of a private IP that could technically change on a rebuild

4–6 · Code and line-by-line explanation

roles/dns_registration/tasks/main.yml
- name: Register DNS A record in ShopSphere private zone
  amazon.aws.route53:
    state: present
    zone: company.internal
    private_zone: true
    record: "{{ vm_name }}.company.internal"
    type: A
    ttl: 300
    value: "{{ ec2_result.instances[0].private_ip_address }}"
    overwrite: true
  register: dns_result

- name: Confirm the record resolves before proceeding
  ansible.builtin.command:
    cmd: dig +short {{ vm_name }}.company.internal
  register: dns_check
  until: dns_check.stdout.strip() == ec2_result.instances[0].private_ip_address
  retries: 6
  delay: 10
  changed_when: false
private_zone: true
Explicitly targets the Private Hosted Zone rather than any public zone with a similar name — a genuinely important parameter to get right, since accidentally targeting a public zone would leak an internal hostname (and by implication, that this server exists) to the public internet.
ttl: 300
A relatively short 5-minute TTL (time-to-live) — deliberately short so that if this server is ever rebuilt with a new IP (Module 36 decommission followed by a fresh provisioning run), DNS caches across the fleet clear quickly rather than pointing stale clients at a dead IP for hours.
overwrite: true
Allows this task to update an existing record rather than failing if one already exists — necessary for Module 13's idempotency discipline: re-running provisioning against an existing server (or one rebuilt with a new IP) should update its DNS record cleanly, not error out because a record with that name is already present.
dig +short ... until: ... == ec2_result...private_ip_address
Doesn't just trust that the Route53 API call succeeded — actively resolves the name and confirms it returns the expected IP, with retries to allow for DNS propagation delay. This is the same "verify against the actual system, not just the API's acceptance of the request" pattern used for monitoring (Module 23), logging (Module 24), and EDR (Module 25).
⚠ Warning

"DNS failure" incident: the Route53 task reports success, but the name doesn't resolve when Play 2 or a later role tries to use it. The most common cause is the RHAAP execution node's own resolver configuration not actually pointing at Route53's private resolver for this VPC (Module 6's DNS 53 connectivity row) — the record can be perfectly correct in Route53 while still being unreachable from wherever the check is being run. This is exactly why the validation task above uses dig from within the automation flow itself, rather than assuming success from the API response alone.

✓ Best Practice

Standardize the DNS naming pattern (<vm_name>.company.internal) so it's fully predictable from data already known at request time (Module 2) — this lets other systems (Module 24's log group naming, Module 30's inventory patterns) construct the same hostname independently rather than needing to look it up, which is a small but real reliability win across the whole platform.

☰ Interview Question

"Why use a short TTL for internal server DNS records, and what's the tradeoff?" Short TTLs mean faster propagation of changes (a rebuilt server's new IP reaches dependent clients quickly) at the cost of more frequent DNS queries — a reasonable tradeoff for internal infrastructure records, less so for a very high-traffic public-facing record where query volume itself becomes a cost/scaling concern.

Module 28 — Certificates

Naming, Certs & Secrets · How pay-dev-app01 Gets a TLS Certificate It Can Trust

1–2 · Beginner explanation and why it matters

If Payment Gateway's application serves any traffic over HTTPS — and given Module 1's compliance story, it certainly does — the server needs a valid TLS certificate. Understanding how a certificate actually gets from "nothing" to "correctly installed and trusted" is core infrastructure knowledge, even though the deepest cryptographic details aren't this masterclass's focus.

3 · Vocabulary and the request flow

TermMeaning
Private keyGenerated on (or for) the server, never shared — the secret half of the key pair that must never leave the server it was generated for, or a secrets manager, unencrypted.
CSR (Certificate Signing Request)A request document generated from the private key, containing the public key and identifying details (the hostname, e.g. pay-dev-app01.company.internal) — sent to a CA for signing.
CA (Certificate Authority)The trusted entity that signs the CSR, producing the actual certificate — at ShopSphere, an internal enterprise CA for internal hostnames, not a public CA, since these names are never publicly resolvable anyway (Module 27).
CertificateThe signed document proving the public key belongs to the named host — what gets installed on the server and presented to connecting clients.
Certificate chainThe certificate plus every intermediate CA certificate needed for a client to trace trust back to a root CA it already trusts.
Expiry / renewalCertificates are time-bounded by design — an expired certificate breaks TLS connections entirely, making renewal automation a genuine availability concern, not just a security one.
Private key generated ON the server (never transmitted) │ ▼ CSR generated from the private key + hostname (pay-dev-app01.company.internal) │ ▼ CSR submitted to ShopSphere's internal CA (via its enrollment API) │ ▼ CA signs and returns the certificate + intermediate chain │ ▼ Certificate + chain installed on the server; private key never moves │ ▼ Application/webserver reloaded to pick up the new certificate │ ▼ Expiry monitored — renewal triggered automatically well before expiry, never manually, and never as a surprise outage

4–6 · Code and line-by-line explanation

roles/certificates/tasks/main.yml
- name: Generate private key on the target server
  community.crypto.openssl_privatekey:
    path: /etc/pki/tls/private/{{ vm_name }}.key
    size: 2048
    type: RSA
    mode: "0600"

- name: Generate CSR for this server's DNS name
  community.crypto.openssl_csr:
    path: /etc/pki/tls/private/{{ vm_name }}.csr
    privatekey_path: /etc/pki/tls/private/{{ vm_name }}.key
    common_name: "{{ vm_name }}.company.internal"
    organization_name: "ShopSphere"
  register: csr_result

- name: Submit CSR to internal CA and retrieve signed certificate
  ansible.builtin.uri:
    url: "https://ca.shopsphere.internal/api/v1/sign"
    method: POST
    body_format: json
    body:
      csr: "{{ lookup('file', '/etc/pki/tls/private/' + vm_name + '.csr') }}"
    headers:
      Authorization: "Bearer {{ internal_ca_api_token }}"
  register: ca_response
  no_log: true

- name: Install signed certificate and chain
  ansible.builtin.copy:
    content: "{{ ca_response.json.certificate }}{{ ca_response.json.chain }}"
    dest: /etc/pki/tls/certs/{{ vm_name }}.crt
    mode: "0644"
  notify: reload payapp
community.crypto.openssl_privatekey ... mode: "0600"
Generates the private key directly on the target server rather than centrally and shipping it over — the key never needs to leave this host, and locking it to 0600 (root-readable only) prevents any non-privileged local account from ever reading it.
common_name: "{{ vm_name }}.company.internal"
Ties the certificate's identity directly to the exact DNS name Module 27 registered — this is the field a connecting client checks against the hostname it's connecting to; a mismatch here is exactly what produces a TLS hostname-verification failure.
lookup('file', '/etc/pki/tls/private/' + vm_name + '.csr')
The lookup plugin reads the CSR file's content directly from the target host's filesystem (note: only the CSR, containing the public key — never the private key file) so it can be submitted in the API request body to the internal CA.
no_log: true
Suppresses the CA API call's full output — it contains both the bearer token and the returned certificate material — the same secret-leakage discipline applied consistently since Module 22.
content: "{{ ca_response.json.certificate }}{{ ca_response.json.chain }}"
Concatenates the leaf certificate and the intermediate chain into a single file — most webservers expect the full chain in one file (leaf first) so a connecting client can validate the entire trust path without needing to fetch intermediates separately.
notify: reload payapp
A config reload, not a full restart — most webservers/application runtimes can pick up a replaced certificate on reload without dropping active connections, which matters when this same role runs again for a routine renewal on a live PROD server.
⛨ Security

The private key generation happening on the target host itself, rather than centrally and then distributed, is a deliberate and important choice — it means the private key never traverses the network at all, eliminating an entire class of interception/leakage risk. This is the correct pattern whenever a private key doesn't strictly need to be shared or backed up centrally.

⚠ Warning

Certificate expiry is one of the most preventable, and most common, real-world outages — a certificate silently expiring takes down TLS entirely with no warning beyond the expiry date itself. This role handles issuance but not renewal scheduling — a real implementation needs a separate, monitored process (often integrated with Module 23's monitoring role, alerting well before expiry, not on the day of) that re-runs this exact role automatically ahead of the certificate's expiry date.

✓ Best Practice

Automate renewal well ahead of expiry (30 days is a common enterprise standard) rather than relying on a human to notice an expiry-date spreadsheet. Treat certificate expiry monitoring as its own explicit check in Module 23's monitoring role — "days until this certificate expires" is exactly the kind of metric that should page someone long before it becomes an incident.

Being able to explain that asymmetry clearly is what separates understanding from just having copied a role that "works."

Module 29 — Secrets Management

Naming, Certs & Secrets · Formalizing a Discipline You've Already Been Practicing Since Module 5

1–2 · Beginner explanation and why it matters

Every module since Module 5 has quietly followed a rule: no credential, token, or key ever appears as a literal value in this repository's YAML. This module makes that rule explicit and shows exactly what "the right way" looks like — because the wrong way is genuinely one of the most common, most damaging mistakes in real enterprise Ansible codebases.

3 · BAD vs. GOOD

BAD — never do this
- name: Configure application database connection
  ansible.builtin.template:
    src: app-config.j2
    dest: /opt/payapp/config.yml
  vars:
    db_password: MyPassword123 # NEVER — plaintext, committed to Git forever
GOOD — sourced from Vault at runtime, never stored in the repo
- name: Configure application database connection
  ansible.builtin.template:
    src: app-config.j2
    dest: /opt/payapp/config.yml
    mode: "0640"
  vars:
    db_password: "{{ lookup('community.hashi_vault.hashi_vault', 'secret=secret/data/payment-gateway/dev/db:password') }}"
  no_log: true
◆ Concept — what actually changed between BAD and GOOD

In the BAD version, the secret's value is a fact about the codebase — anyone with Git access (and anyone who ever had it, since Git history is forever, per Module 38) has it, forever, regardless of whether they should. In the GOOD version, the secret's value is a fact about Vault, at this moment — the code only contains a path and a reference to fetch it, and Vault itself controls who/what can retrieve it, when, and can revoke or rotate it without ever touching this repository at all. This is the entire philosophical shift secrets management represents.

4 · The options, and where each fits

MechanismHow it worksUsed in this project for
RHAAP CredentialEncrypted storage inside RHAAP itself, injected only into the running job's environment at execution time (Module 4, 5)The AWS provisioning role's assumed-role/instance-profile identity
HashiCorp VaultA dedicated secrets engine — secrets fetched dynamically via API/lookup plugin, often with short-lived leases that auto-expireApplication database credentials, internal CA API tokens (Module 28)
CyberArkAn enterprise privileged-access-management platform — commonly used for privileged account credentials with strict checkout/rotation workflowsAny account with standing elevated OS-level or infrastructure privileges
AWS Secrets ManagerAWS-native secret storage, retrievable via IAM-authenticated API calls — no separate credential needed if the caller already has an appropriate IAM roleAWS-specific secrets where staying inside the AWS IAM trust boundary (Module 5) is preferable to a separate Vault dependency

5–6 · The lookup pattern, explained

lookup('community.hashi_vault.hashi_vault', 'secret=secret/data/payment-gateway/dev/db:password')
A Jinja2 lookup plugin call — evaluated at runtime, inside the job, never written to disk as a static value anywhere in the repo. The path secret/data/payment-gateway/dev/db follows the same application/environment naming hierarchy used everywhere else in this project (Module 24's log groups, Module 12's tags) — Vault access policies are scoped to these paths, so ShopSphere's Vault admins can grant "read DEV Payment Gateway secrets" without granting access to PROD secrets at all.
no_log: true
Still required even when using Vault — the resolved value, once fetched, is just as sensitive as a hardcoded one would have been, and would still leak into job output without this. Sourcing from Vault protects the source; no_log protects the output.
⛨ Security

Notice that no_log: true has appeared in nearly every module since 22 — this wasn't incidental repetition; it's meant to build the reflex that any task handling a credential, token, or secret value needs it, regardless of where the secret came from. The two disciplines — never hardcoding a secret, and never letting a resolved secret leak into logs — are separate and both required.

⚠ Warning

"RHAAP credential failure" incident: a job fails with an authentication error against Vault, AWS, or the internal CA, but the credential was "definitely" configured correctly in RHAAP. A common real cause: RHAAP Credentials and Vault leases can both expire or be rotated independently of the job's own schedule — a credential that worked yesterday can be invalid today if it was rotated, revoked, or its underlying AssumeRole trust policy changed. Always check credential/lease validity directly (via the provider's own tooling) before assuming a code-level bug.

✓ Best Practice

Prefer dynamic, short-lived secrets (Vault leases, STS temporary credentials — Module 5) over static ones wherever the target system supports it. A leaked short-lived secret is a much smaller incident than a leaked long-lived one — this is the exact same blast-radius reasoning Module 5 used to prefer IAM Roles over Access Keys, applied generally to every secret in this project.

Module 33 — Error Handling

When Things Break · Formalizing Patterns You've Been Using Since Module 11

1–2 · Beginner explanation and why it matters

Every role since Module 11 has quietly used error-handling primitives — assert, failed_when, changed_when, retries/delay/until. This module names each one explicitly and adds the one pattern not yet formally introduced: block/rescue/always, Ansible's closest equivalent to a try/catch/finally construct — essential for anything that needs cleanup logic regardless of whether the main action succeeded.

3 · The primitives, each traced back to where you already used them

PrimitivePurposeWhere you've already seen it
failed_whenRedefines what counts as failure for a task, overriding the module's own default success/fail logicModule 18's reboot-check task inverted this via failed_when: false to treat a non-zero exit code as informational, not an error
changed_whenRedefines what counts as a change, independent of failure — controls Ansible's changed/ok reporting and downstream notify handlersModule 20's leapp preupgrade task, and Module 24's read-only log group check
retries / delay / untilPolls a task repeatedly until a condition is met or attempts are exhaustedModule 12's SSH wait, Module 18's post-patch health check, Module 23's monitoring confirmation
assertStops the play immediately with a clear message if a condition isn't metAll of Module 11's validation logic
block / rescue / alwaysGroups tasks so a failure anywhere in the block triggers rescue tasks, while always tasks run regardless of outcome — the primitive not yet formally usedNew in this module — needed for cleanup logic Module 34's rollback decisions depend on

4–7 · block/rescue/always — code and line-by-line explanation

roles/aws_provision/tasks/main.yml (excerpt — wrapped for safe cleanup)
- name: Provision EC2 with guaranteed cleanup notification on failure
  block:
    - name: Provision EC2 instance for {{ vm_name }}
      amazon.aws.ec2_instance:
        # ... full task from Module 12 ...
      register: ec2_result

    - name: Wait for SSH to become reachable
      ansible.builtin.wait_for:
        host: "{{ ec2_result.instances[0].private_ip_address }}"
        port: 22
        timeout: 300

  rescue:
    - name: Record provisioning failure details for the incident record
      ansible.builtin.set_fact:
        provisioning_failed: true
        failure_reason: "{{ ansible_failed_result.msg | default('unknown') }}"

    - name: Notify DevOps team of provisioning failure
      community.general.slack:
        token: "{{ slack_token }}"
        msg: "Provisioning FAILED for {{ vm_name }} ({{ change_number }}): {{ failure_reason }}"
      no_log: true

    - name: Re-raise so the workflow node correctly shows as failed
      ansible.builtin.fail:
        msg: "Provisioning failed — see notification and job output above for details"

  always:
    - name: Record job completion timestamp regardless of outcome
      ansible.builtin.debug:
        msg: "Provisioning attempt for {{ vm_name }} finished at {{ ansible_date_time.iso8601 }}"
block: (two tasks)
The "try" portion — if either the EC2 creation or the SSH wait fails, execution jumps immediately to rescue, skipping any remaining tasks in the block. Both tasks are grouped here because they represent one logical unit of work — "get a reachable server" — that either fully succeeds or needs the same failure handling.
rescue: set_fact ... failure_reason: "{{ ansible_failed_result.msg | default('unknown') }}"
ansible_failed_result is a special variable Ansible populates inside a rescue block, holding the failed task's actual result — this captures the real error message for the notification, rather than a generic "something failed" alert that would force an engineer to dig through job output before even knowing what broke.
community.general.slack ... no_log: true
Notifies the team immediately, using a token sourced per Module 29's discipline — no_log is still required since the Slack token itself is a credential, even inside a rescue block reacting to an unrelated failure.
ansible.builtin.fail: msg: "Provisioning failed..."
Crucial and easy to miss: a rescue block that completes without an explicit fail makes the overall play report success — because Ansible considers the failure "handled." This task deliberately re-raises the failure so RHAAP's workflow (Module 32) correctly routes to its own failure branch, rather than a rescued-and-silently-swallowed failure making the workflow graph show a false success.
always: Record job completion timestamp
Runs whether the block succeeded or was rescued — useful for anything that must happen unconditionally, like a completion timestamp for auditing, or (in a more complex role) releasing a lock or updating a status record regardless of outcome.
◆ Concept — the most common real mistake with rescue

A rescue block that logs the error and notifies but never calls fail again is a genuinely dangerous anti-pattern: from Ansible's and RHAAP's perspective, the play succeeded. This can produce the worst possible outcome — a workflow that shows green in RHAAP's dashboard while the server it was supposed to provision doesn't actually exist or isn't actually healthy. Always re-raise inside rescue unless you have a very deliberate, well-understood reason to swallow the failure (a truly optional step where failure is genuinely fine to ignore).

⚠ Warning

"RHAAP job output" incident — a workflow shows green but the server is broken: almost always traces back to exactly the anti-pattern above — a rescue block (or an overly broad failed_when: false) that silently absorbed a real failure. When investigating a "succeeded but clearly isn't right" incident, search the relevant role for every rescue: and failed_when: false first — one of them is very likely hiding the real story.

✓ Best Practice

Reserve failed_when: false for tasks that are genuinely informational (like Module 18's reboot-check, which reads a status rather than performing an action) — never use it to suppress a failure from an action task just to make a workflow "look" successful. If a task might legitimately fail in an expected way (Module 17's "service doesn't exist to disable" case), that's a narrower, more defensible use than blanket-suppressing all failures.

☰ Interview Question

"What's the difference between failed_when: false and a rescue block, and when would you use each?" failed_when: false changes whether one specific task's result counts as a failure at all — appropriate for tasks whose "failure" is actually just informational output. block/rescue lets multiple tasks fail as a unit and triggers cleanup/notification logic in response — appropriate when a failure is real but needs a structured response (logging, notifying, deciding whether to re-raise) rather than just being suppressed.

Retry immediatelyFast — if the failure was transient (a brief network blip), a retry might just workIf the failure is systemic, an unattended auto-retry can loop uselessly or, worse, mask a real problem behind eventual "success" after N attempts
Raise an incident, pause, let a human decideCorrect default for anything ambiguous — a human can quickly tell "known flaky dependency, safe to retry" from "something is genuinely broken, investigate first"Slower — not appropriate for every failure category
◆ Concept — the actual decision rule ShopSphere uses

The right answer depends on where in the workflow the failure happened, not a single fixed policy. A failure before any AWS resource exists (Module 11's validation) needs no rollback at all — nothing was created. A failure after EC2 creation but before the server is marked "ready" (exactly this scenario) should generally be kept in a clearly-tagged failed state, isolated from monitoring/traffic, with an incident raised — not deleted, and not silently retried. A failure during Module 36's decommissioning process is its own separate, careful case (covered there). The common thread: destructive actions (delete) need more certainty than the workflow has immediately after a failure, and silent auto-retry needs more confidence than an unexplained failure deserves.

5 · The actual mechanism — a "quarantine" tag, not a deletion

roles/aws_provision/tasks/main.yml (rescue block, extended from Module 33)
rescue:
  - name: Tag the instance as quarantined rather than deleting it
    amazon.aws.ec2_tag:
      region: "{{ aws_region }}"
      resource: "{{ ec2_result.instances[0].instance_id }}"
      tags:
        ProvisioningStatus: "FAILED_QUARANTINED"
        FailedStage: "{{ ansible_failed_task.name | default('unknown') }}"
      state: present

  - name: Remove instance from any traffic-facing security group
    amazon.aws.ec2_instance:
      instance_ids: "{{ ec2_result.instances[0].instance_id }}"
      region: "{{ aws_region }}"
      security_groups: ["{{ quarantine_security_group }}"]

  - name: Create ServiceNow incident linked to the original change
    ansible.builtin.uri:
      url: "https://shopsphere.service-now.com/api/now/table/incident"
      method: POST
      body_format: json
      body:
        short_description: "Provisioning failed for {{ vm_name }} at stage {{ ansible_failed_task.name }}"
        related_change: "{{ change_number }}"
        urgency: "{{ '1' if environment == 'prod' else '3' }}"
      headers:
        Authorization: "Bearer {{ servicenow_api_token }}"
    no_log: true

  - name: Re-raise so the RHAAP workflow node shows failed
    ansible.builtin.fail:
      msg: "{{ vm_name }} quarantined at stage '{{ ansible_failed_task.name }}' — incident raised"
ProvisioningStatus: "FAILED_QUARANTINED"
A tag, not a deletion — the instance still exists (preserving diagnostic evidence) but is now unambiguously marked as not production-ready. Any later inventory query, CMDB sync, or engineer manually browsing the AWS console immediately sees this server is not in a normal state — it can never be silently mistaken for a healthy one.
security_groups: ["{{ quarantine_security_group }}"]
Actively isolates the instance from application traffic and most inbound access — the Module 34 answer to "keep it, but don't leave it exposed": preserved for diagnosis, but no longer capable of serving traffic or being mistaken for an available server.
urgency: "{{ '1' if environment == 'prod' else '3' }}"
A Jinja2 conditional expression setting incident urgency based on environment — exactly Module 2's risk-tiering logic, applied here to how fast a human needs to respond to this specific failure.
ansible_failed_task.name
Another rescue-block special variable — captures which specific task failed (distinct from Module 33's ansible_failed_result, which captures the failure's message/details) — both together give a human reviewing the incident the full picture without needing to open RHAAP's job output first.
⚠ Warning

Never let an auto-retry loop happen silently and indefinitely — if a quarantine-and-retry policy is ever implemented, cap it at a small, explicit number of attempts (2–3) with escalating visibility, never an unbounded loop. An unattended provisioning workflow that quietly retries the same failing step 50 times overnight is its own incident, independent of whatever the original failure was.

✓ Best Practice

Quarantine, don't delete, as the default response to a mid-workflow failure — deletion is a decision for a human to make deliberately, after reviewing the incident, not something automation does reflexively. This mirrors real enterprise incident response discipline broadly: preserve evidence first, clean up second, once the cause is actually understood.

When Things Break · 25 Real Production Incidents, and the Method Behind Diagnosing Any of Them

3 · The diagnostic framework, restated once, applied 25 times below

Each card below is intentionally compact: Symptom, Investigation/Commands, Root Cause, Fix, Validation, Prevention. 1 — AWS AccessDenied

Symptom: An AWS API task fails with AccessDenied / UnauthorizedOperation.

Investigate: Identify the exact action and resource ARN from the error; compare against Module 5's IAM policy Sid-by-Sid.

Root cause: The provisioning role's IAM policy doesn't include the specific action needed (often a newly-added task calling a permission never granted).

Fix: Add a narrowly-scoped statement for exactly that action/resource — never widen to "*" actions.

Validation: Re-run the specific failed task in isolation before re-running the full workflow.

Prevention: New AWS interactions get a reviewed policy addition alongside the code change, in the same pull request (Module 38).

2 — Wrong IAM Role

Symptom: Provisioning succeeds but uses unexpected permissions, or fails with a permission error inconsistent with the documented policy.

Investigate: Confirm which role RHAAP's execution node actually assumed at runtime — not which role you think is configured.

Root cause: A Credential in RHAAP (Module 30) points at the wrong role ARN, often after an environment or account restructuring.

Fix: Correct the Credential configuration; verify against Module 5's documented role design.

Validation: A test job that calls sts:GetCallerIdentity and asserts the returned ARN matches expectations.

Prevention: Add exactly that GetCallerIdentity assertion as a standing first task in provisioning.

3 — Invalid AMI

Symptom: Module 11's AMI validation task fails, or (if validation was skipped) EC2 creation fails deep in Module 12.

Investigate: Query the AMI directly (ec2_ami_info) — confirm it exists, is available, and is in the target region.

Root cause: AMI was deregistered, or a region-specific AMI ID was reused in the wrong region's group_vars.

Fix: Update the AMI ID in the correct environment's group_vars; confirm the golden-image pipeline still publishes to all approved regions.

Validation: Module 11's own validation task passing is the validation.

Prevention: This is exactly why Module 11 validates live against AWS instead of trusting a static ID — the incident is caught in seconds, not mid-provisioning.

4 — Subnet Not Found

Symptom: Module 11's subnet/VPC validation fails.

Investigate: Compare the subnet_id and vpc_id extra_vars actually used in this run against Module 3's current architecture.

Root cause: Stale group_vars after a VPC redesign, or a requester-supplied survey override pointing at the wrong environment's subnet.

Fix: Correct the variable at its source (group_vars, or remove the ability to override it on the survey — Module 31).

Validation: Re-run validation only; no AWS resources were created yet.

Prevention: Keep subnet/security_group off the survey entirely, per Module 31's design.

5 — Security Group Missing

Symptom: EC2 creation fails referencing a nonexistent security group ID.

Investigate: ec2_vpc_security_group_info filtered by the group ID/name to confirm existence and which VPC it belongs to.

Root cause: A security group was deleted or renamed by the Network team without ShopSphere's group_vars being updated — a coordination gap, not a code bug.

Fix: Update group_vars; consider adding a security-group existence check to Module 11's validation (parallel to the subnet check).

Validation: Re-run validation stage.

Prevention: A change-notification process between the Network team and Cloud Automation team whenever shared security groups change.

6 — AWS API Timeout

Symptom: An AWS API call hangs, eventually times out.

Investigate: Module 6's connectivity chain first — DNS resolution of the API endpoint, then route (direct/proxy/VPC endpoint), only then credentials.

Root cause: Usually a network path issue (a VPC endpoint misconfiguration, a proxy outage) rather than AWS itself being slow.

Fix: Restore the broken network path; add appropriate task-level timeouts so failures surface faster next time.

Validation: A simple, fast AWS API call (e.g. sts:GetCallerIdentity) succeeding confirms the path is restored.

Prevention: Monitor the connectivity path itself (Module 23), not just the application.

7 — EC2 Quota Exceeded

Symptom: RunInstances fails with a service-quota error.

Investigate: Check the account's current vCPU/instance limit usage for the instance family via the AWS console/API.

Root cause: Fleet growth (Module 19's 500-server PROD scale) outpaced the account's default service quota.

Fix: Request a quota increase from AWS (not instant — plan ahead of known scale-up events).

Validation: A subsequent provisioning run for the same instance type succeeds.

Prevention: Monitor quota utilization proactively (a Module 23-style check) rather than discovering the limit at the worst moment — mid-batch during Module 19's patching or a scaling event.

8 — SSH Timeout

Symptom: Module 14's Play 2 fails to connect to the newly provisioned host.

Investigate: Did Module 12's wait_for actually complete? Is the execution node's security group/network path permitted to reach the target's private IP on port 22 (Module 6)?

Root cause: Overwhelmingly a Module 6 connectivity gap — not an Ansible or inventory bug.

Fix: Correct the security group rule or network path; consider SSM as an alternative (Module 6's security recommendation) to avoid this failure class entirely.

Validation: Play 2's first task succeeding.

Prevention: Keep wait_for in place (Module 12) and never assume "running" means "reachable."

9 — DNS Failure

Symptom: Module 27's DNS record resolves inconsistently or not at all from within the automation flow.

Investigate: Confirm the RHAAP execution node's resolver actually points at Route53's private resolver for the relevant VPC.

Root cause: A resolver misconfiguration or VPC association gap on the Private Hosted Zone — record can be correct in Route53 while unreachable from where it's checked.

Fix: Correct the VPC association or resolver config; re-run Module 27's dig-based validation.

Validation: The validation task itself, per Module 27.

Prevention: Never trust the Route53 API's "success" response alone — always resolve-and-verify, as Module 27 already does.

10 — Proxy Failure

Symptom: Package installs or external API calls fail specifically in environments using Module 6's Design B (corporate proxy).

Investigate: Test connectivity through the proxy directly (a simple curl through the configured proxy) separate from any Ansible task.

Root cause: Proxy config drift between what Module 15 templated and what the proxy server actually expects (auth changes, endpoint changes).

Fix: Update the proxy URL/credentials in group_vars; re-render Module 15's config.

Validation: A package install task succeeding.

Prevention: Where feasible, prefer Module 6's Design C (VPC endpoints) for AWS traffic specifically, removing proxy dependency for the highest-volume traffic.

11 — Repository Unavailable

Symptom: Module 15's "Install baseline package set" (or any dnf task) fails with a repo-unreachable error.

Investigate: DNS resolution of the repo mirror, then network path, then whether the repo mirror service itself is actually up.

Root cause: Usually connectivity (Module 6), occasionally a genuine internal repo mirror outage.

Fix: Restore connectivity or escalate to whoever owns the repo mirror.

Validation: Package install task succeeding.

Prevention: Monitor repo mirror availability as its own service (Module 23) — a repo outage affects every provisioning run fleet-wide, so it deserves its own alert.

12 — yum/dnf Locked

Symptom: A package task fails with a "could not acquire lock" error.

Investigate: ps aux | grep dnf or similar on the target — another process (often cloud-init's own first-boot package activity) is still holding the package manager lock.

Root cause: A race between Ansible connecting very soon after boot (Module 12's wait_for confirms SSH, not "cloud-init fully finished") and cloud-init's own background package operations.

Fix: Add a cloud-init status --wait task before the first package task in Module 15, ensuring cloud-init has genuinely finished first.

Validation: Package task succeeding on the next run.

Prevention: The added cloud-init status --wait gate, standing, in every baseline role from here forward.

13 — Disk Not Detected

Symptom: Module 16's partition task fails — the expected device doesn't exist.

Investigate: lsblk on the target — confirm whether the EBS volume even shows as attached at the OS level.

Root cause: An AWS-side attach issue (Module 12's volume attachment silently incomplete) or a device-naming mismatch (AWS's requested device name vs. the OS's actual assigned name, common on Nitro-based instances using NVMe naming).

Fix: Use a device-detection task (matching by volume size/tag via lsblk output) rather than hardcoding a device path assumption.

Validation: The corrected data_device variable resolving to a real, present device.

Prevention: Never hardcode device paths for Nitro-based instance types without a detection step first — this is a very well-known AWS/Ansible gotcha.

14 — LVM Failure

Symptom: Module 16's lvg/lvol tasks fail.

Investigate: Work top-down through Module 16's own inspection chain — lsblk, then pvs, then vgs, then lvs — to find exactly which layer is missing or malformed.

Root cause: Most often a partition step (task before it) didn't actually complete, so there's no valid PV target — a downstream symptom of an upstream failure.

Fix: Fix the actual failing layer identified by the chain walk, not the LVM task itself (rarely the real cause).

Validation: lvs showing the expected logical volume.

Prevention: Keep Module 16's tasks in their documented dependency order — never reorder them for convenience.

15 — fstab Error

Symptom: A reboot leaves the server in an unexpected state, or the mount silently isn't present after reboot.

Investigate: Check /etc/fstab for the entry Module 16 wrote — confirm the nofail option is present.

Root cause: A missing nofail option means a transient EBS attach delay at boot can drop the server to an emergency shell instead of booting normally.

Fix: Add nofail (and consider x-systemd.device-timeout=) as shown in Module 16 — this should never be missing if that module's role was used as written.

Validation: A test reboot confirms clean boot regardless of mount timing.

Prevention: Module 16's role, used exactly as documented, already prevents this — this incident is what happens when that guidance is skipped.

16 — Server Fails After Reboot

Symptom: A server that was healthy before a patch/upgrade reboot doesn't come back cleanly.

Investigate: Console/serial output if SSH is unreachable; check whether this correlates with a specific package or kernel update from that run.

Root cause: Varies — a bad kernel update, an fstab issue (see #15), or a service that doesn't start correctly under the new package versions.

Fix: Restore from the pre-patch snapshot (Module 18/20) rather than attempting live triage under time pressure on a PROD server.

Validation: Restored instance passing Module 40's application-readiness checks.

Prevention: This is exactly why Module 18 and Module 20 both mandate a pre-action snapshot as a non-optional checkpoint.

17 — Patch Failure

Symptom: Module 18's "Apply security patches" task itself fails (not the post-check — the patch application).

Investigate: The dnf error output directly — dependency conflicts are the most common cause.

Root cause: A package dependency conflict introduced by an out-of-band manual change on the server (configuration drift Module 13 is meant to prevent, but can still occur from emergency manual fixes).

Fix: Resolve the specific conflict; consider whether the manual change that caused drift should instead be codified into a role.

Validation: Patch task succeeding on retry after the conflict is resolved.

Prevention: Strongly discourage manual, undocumented changes to provisioned servers — anything needed should go through the automation, or be captured back into it afterward.

18 — Kernel Issue

Symptom: Post-patch or post-upgrade reboot succeeds, but the server exhibits instability (crashes, degraded performance) traced to the new kernel.

Investigate: Compare kernel version before/after; check for known issues with that specific kernel build.

Root cause: A specific kernel release with a regression affecting this workload — rare, but real, and exactly why Module 19's staged batch rollout exists.

Fix: Roll back via snapshot restore (or explicit kernel pinning to the previous version) while the issue is investigated with Red Hat support.

Validation: Restored/pinned instance stable under normal load.

Prevention: This is the entire justification for Module 19's small-first-batch strategy — catch a bad kernel on 5 or 25 servers, not 500.

19 — Monitoring Agent Failure

Symptom: Module 23's validation task never confirms the agent is reporting.

Investigate: Is the config template rendering the correct monitoring endpoint? Is outbound connectivity to that endpoint permitted (Module 6)?

Root cause: Most often a stale endpoint URL in group_vars (pointing at a decommissioned collector) or a connectivity gap — rarely the agent binary itself.

Fix: Correct the endpoint or connectivity; re-run the role (it's idempotent).

Validation: Module 23's own platform-side confirmation, per its design.

Prevention: Module 23's decision to fail the workflow (not just warn) on this exact incident is what prevents an unmonitored server from silently going live.

20 — Security Agent Failure

Symptom: Module 25's EDR console never shows the host as protected.

Investigate: Is the sensor service actually running locally? Can it reach the vendor's cloud console (outbound, Module 6)? Is the install token still valid/unused?

Root cause: Most commonly a stale or already-consumed install token, especially when multiple servers were provisioned close together reusing one static token.

Fix: Generate a fresh token per provisioning run (Module 25's stated best practice); re-register.

Validation: Module 25's own console-status confirmation.

Prevention: Fresh, single-use tokens sourced from Vault at runtime (Module 29) rather than one static long-lived token shared across a batch.

21 — Vulnerability Still Detected

Symptom: A rescan (Module 21) still flags a CVE after remediation ran successfully.

Investigate: Is the affected process actually restarted/rebooted to pick up the fixed library in memory? Does the CVE apply to a container/embedded dependency outside the OS package manager's reach? Has the scanner's own database refreshed since the fix?

Root cause: Any of the above — this incident specifically requires distinguishing which, not assuming remediation simply "didn't work."

Fix: Restart the affected service/reboot if that's the gap; escalate to the application team if it's an embedded dependency; wait and re-check if it's just scanner database lag.

Validation: A subsequent rescan showing the finding cleared.

Prevention: Module 21's deliberate separation of "fix applied" from "independently rescanned and confirmed" — this incident is exactly the gap that separation exists to catch.

22 — RHAAP Credential Failure

Symptom: A job fails authenticating to AWS, Vault, or another integrated system, despite "nothing having changed."

Investigate: Check the credential/lease's actual current validity directly against the provider (AWS STS, Vault) — not just RHAAP's stored configuration, which can look fine while the underlying trust relationship has changed.

Root cause: An independent rotation, revocation, or trust-policy change on the provider side that RHAAP's configuration doesn't yet reflect.

Fix: Update the Credential configuration to match the current, valid trust relationship.

Validation: A minimal test job authenticating successfully.

Prevention: A lightweight, scheduled credential-health-check Job Template that proactively catches this before a real provisioning run hits it.

23 — Project Sync Failure

Symptom: RHAAP's Project fails to sync from Git.

Investigate: Same connectivity chain as any external-system failure (Module 6) — DNS, network path, and the specific credential RHAAP uses to reach Git (often a deploy key, which can itself expire).

Root cause: Most commonly an expired/rotated Git deploy key, occasionally a genuine Git-side outage.

Fix: Refresh the deploy key/credential (per Module 29's discipline); re-sync.

Validation: Project sync completing successfully.

Prevention: Treat Git access credentials with the same rotation-awareness as any other credential in Module 29.

24 — Execution Environment Dependency Failure

Symptom: A job fails with a "module not found" or unexpected-parameter error that has nothing to do with the YAML itself.

Investigate: Compare the EE's actual pinned collection/boto3 versions (Module 9) against what the role's code (Module 8) actually requires.

Root cause: The EE was rebuilt (or the collection requirement bumped) without keeping the two files' pinned versions in step — the exact scenario warned about in Module 8 and Module 9.

Fix: Align requirements.yml and requirements.txt version ranges; rebuild and re-tag the EE; update the Job Template to point at the corrected tag.

Validation: The previously-failing task succeeding against the corrected EE tag.

Prevention: Any EE rebuild goes through the same review process as any other dependency change (Module 38) — never treat it as a routine, unreviewed action.

25 — Playbook Syntax Failure

Symptom: A job fails immediately, before any task runs, with a YAML/syntax error.

Investigate: The exact line/column RHAAP's job output reports — almost always indentation, a missing colon, or an unquoted string containing a special character.

Root cause: A syntax error that should have been caught before merge — a gap in the CI/CD pipeline (Module 38) rather than a mysterious runtime issue.

Fix: Correct the syntax; run ansible-lint/yamllint locally before pushing.

Validation: ansible-playbook --syntax-check passing locally, then a successful job run.

Prevention: This is precisely what Module 38's CI/CD pipeline (lint → syntax check → review → merge) exists to catch before it ever reaches RHAAP at all.

Module 36 — Server Decommissioning

End of Life & The Full Picture · The Stage Most Tutorials Skip Entirely

1–2 · Beginner explanation and why it matters

Chapter 1's original argument for automation included "decommissioning is often forgotten → orphaned, unpatched, billed servers." This module is the direct answer to that problem — a tracked, deliberate teardown process, not a server someone quietly forgets exists until a cost review finds it.

3 · The workflow

Decommission Request (ServiceNow — same intake discipline as Chapter 1's provisioning request) │ ▼ Approval (confirms this server is genuinely no longer needed — not a unilateral engineer decision, especially for PROD) │ ▼ Application Confirmation — the Payment Team explicitly confirms no traffic/dependency still relies on this specific server │ ▼ Final Backup — one last snapshot taken before anything is touched, in case something unexpected still depended on this server │ ▼ Monitoring Removal — deregister from Module 23's platform (prevents permanent "host unreachable" alerts on a server that's supposed to be gone) │ ▼ DNS Removal — remove the Module 27 record (prevents stale DNS pointing at an IP that may later be reassigned to a different instance) │ ▼ CMDB Update — mark the record decommissioned, not delete it (historical record retained for audit) │ ▼ EC2 Termination │ ▼ EBS Cleanup — confirm volumes are actually deleted (or retained per an explicit final-backup policy), not silently orphaned and still billing │ ▼ Security Cleanup — deregister from Module 25's EDR console, Module 22's scanner — an orphaned agent registration is itself a small security hygiene gap │ ▼ Validation — confirm every above step actually completed; nothing is assumed

4–6 · Code and line-by-line explanation

playbooks/decommission.yml
- name: Decommission {{ vm_name }}
  hosts: localhost
  tasks:

    - name: Take final backup snapshot before any teardown action
      amazon.aws.ec2_snapshot:
        instance_id: "{{ instance_id }}"
        description: "final-decommission-backup {{ vm_name }} — {{ change_number }}"

    - name: Deregister from monitoring platform
      ansible.builtin.uri:
        url: "https://monitoring.shopsphere.internal/api/v1/hosts/{{ vm_name }}"
        method: DELETE
        headers:
          Authorization: "Bearer {{ monitoring_api_token }}"
        status_code: [200, 404]
      no_log: true

    - name: Remove DNS record
      amazon.aws.route53:
        state: absent
        zone: company.internal
        private_zone: true
        record: "{{ vm_name }}.company.internal"
        type: A

    - name: Terminate EC2 instance
      amazon.aws.ec2_instance:
        instance_ids: "{{ instance_id }}"
        region: "{{ aws_region }}"
        state: absent
      register: termination_result

    - name: Confirm no orphaned EBS volumes remain for this instance
      amazon.aws.ec2_vol_info:
        region: "{{ aws_region }}"
        filters:
          "tag:Name": "{{ vm_name }}"
      register: orphan_check
      failed_when: orphan_check.volumes | selectattr('status', 'equalto', 'available') | list | length > 0

    - name: Update CMDB record to decommissioned (never deleted)
      ansible.builtin.uri:
        url: "https://shopsphere.service-now.com/api/now/table/cmdb_ci_server/{{ cmdb_sys_id }}"
        method: PATCH
        body_format: json
        body:
          install_status: "7" # ServiceNow's "Retired" status code
        headers:
          Authorization: "Bearer {{ servicenow_api_token }}"
      no_log: true
Take final backup snapshot before any teardown action
Always first, unconditionally — a last safety net in case the "Application Confirmation" step upstream (a human judgment call) turns out to have been wrong. This is Module 34's rollback philosophy applied to decommissioning: preserve evidence/recoverability before doing anything irreversible.
status_code: [200, 404]
Accepts either "successfully deregistered" (200) or "wasn't registered in the first place" (404) as success — an idempotency accommodation (Module 13's discipline) for a decommission playbook that might be re-run if an earlier attempt partially failed.
amazon.aws.route53: state: absent
The direct inverse of Module 27's registration task — same module, opposite state. Removing the DNS record prevents a future, unrelated server from ever being confused with this one if its IP is eventually reassigned by AWS to a different instance.
amazon.aws.ec2_instance: state: absent
Terminates the instance — the actually irreversible step in this entire playbook, which is exactly why every task before it (backup, monitoring/DNS deregistration) is designed to complete cleanly first.
ec2_vol_info ... failed_when: ...status == 'available' ... length > 0
After termination, checks for any EBS volume tagged with this server's name that's now in available state (detached, unattached to anything) — meaning AWS didn't auto-delete it and it's now an orphaned, silently-billing resource. This directly prevents Chapter 1's "orphaned, unpatched, billed servers" problem from recurring at the storage layer.
install_status: "7" # Retired
Updates, never deletes, the CMDB record — the server's full history (when it was requested, what change built it, every patch/incident tied to it) remains queryable for audit purposes long after the actual infrastructure is gone.
⚠ Warning

The single most common real decommissioning failure is exactly what the orphan-check task above catches: EBS volumes configured with "delete on termination" set to false (sometimes deliberately, for the data volume, as a safety measure — sometimes by accident) silently surviving instance termination and continuing to accrue cost indefinitely, discovered only during a much later cost audit. Never skip this check.

✓ Best Practice

Treat "Application Confirmation" as a genuine, non-skippable human gate for anything beyond DEV — an automated decommissioning workflow should never be able to terminate a PROD server based purely on an inactivity heuristic or a stale ticket, without an explicit, current confirmation from the application owner.

Module 38 — CI/CD For Ansible Code

Bringing It All Together · How a Code Change Safely Reaches Production RHAAP

1–2 · Beginner explanation and why it matters

Every role built across this masterclass lives in Git (Module 7), and RHAAP only ever syncs from Git, never accepting direct edits (Module 4, 30). This module is the missing piece connecting "an engineer changes a role" to "that change is safely running in RHAAP" — and it's the process that would have caught Incident #25 (playbook syntax failure) from Module 35 before it ever reached a real job.

3 · The pipeline

Developer writes/modifies a role or playbook │ ▼ Feature Branch — never commits directly to the tag RHAAP's PROD Project points at (Module 30) │ ▼ Ansible Code pushed to the feature branch │ ▼ ansible-lint — checks for Ansible-specific anti-patterns (missing name fields, deprecated syntax, risky module usage) │ ▼ yamllint — checks pure YAML formatting/structure issues │ ▼ Syntax Check — ansible-playbook --syntax-check, catching exactly Module 35's Incident #25 before it ever reaches RHAAP │ ▼ Testing — a non-PROD RHAAP Project (or a local/molecule-style test run) exercises the changed role against a real DEV-equivalent target │ ▼ Pull Request opened against the main integration branch │ ▼ Peer Review — a second engineer reviews for exactly the things this masterclass has flagged throughout: hardcoded secrets (Module 29), overly broad failed_when (Module 33), missing idempotency checks (Module 13) │ ▼ Merge into the reviewed integration branch │ ▼ RHAAP Project Sync — but only after a deliberate re-tag (Module 30's "pin a tag, not a floating branch" rule) — merging to the integration branch does NOT automatically change what PROD's Project points at │ ▼ Production — the new tag is deliberately assigned to the PROD Project only after the above, often with its own final approval gate

4 · Why the tag-pinning step is deliberately separate from merge

◆ Concept

Merging a pull request and deploying that change to PROD are two different decisions, made at two different times, by design. Module 30 already established that RHAAP's PROD Project pins a specific tag rather than following main — this module explains why that separation exists in the pipeline: it lets ShopSphere merge and integrate code continuously while still controlling exactly when a given version actually starts running against real PROD infrastructure, which might be hours, days, or an entire change-approval cycle after the merge itself.

5 · Sample CI configuration — what actually runs on every push

ansible-lint roles/ playbooks/
Catches Ansible-specific issues no generic YAML checker would — missing task names (Module 1's point about job-output readability), use of deprecated module syntax, and risky patterns like unpinned latest package installs where a specific version was intended.
ansible-playbook ... --syntax-check
Parses every top-level playbook without executing any tasks — this is specifically what would have caught Module 35's Incident #25 in seconds, in CI, rather than as a job failure in RHAAP visible to whoever happened to launch it next.
ansible-playbook ... --check
Ansible's dry-run mode — reports what would change without actually changing anything, run against a genuine DEV-equivalent test inventory. Not a substitute for the real DEV run inside RHAAP, but a fast, cheap first signal directly inside the CI pipeline before a human reviewer even looks at the PR.
rules: if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
Restricts the (more expensive) test stage to only run on actual merge request pipelines, not every single commit push — a practical efficiency choice once a pipeline has been running for a while and cost/time starts to matter.

PracticeWhy
Protected branchesThe integration branch and any PROD-referenced tags can't be force-pushed or committed to directly — every change goes through a PR, no exceptions, including for the Cloud Automation team's own senior engineers.

- name: Confirm application service is active
  ansible.builtin.systemd_service:
    name: payapp
  register: service_check
  failed_when: service_check.status.ActiveState != 'active'

- name: Confirm application responds correctly on its port
  ansible.builtin.uri:
    url: "http://localhost:{{ app_port }}/health"
    status_code: 200
  delegate_to: "{{ inventory_hostname }}"
  register: health_check
  retries: 6
  delay: 10
  until: health_check.status == 200

- name: Confirm data volume is mounted and writable
  ansible.builtin.tempfile:
    path: /opt/payapp/data
    state: file
    prefix: .validation_check_
  register: write_check
  become_user: payapp

- name: Clean up validation test file

    path: "{{ write_check.path }}"
    state: absent

- name: Confirm monitoring, logging, and EDR are all reporting (composite gate)

      - hostvars[inventory_hostname].edr_confirmed | default(false)

failed_when: service_check.status.ActiveState != 'active'

A genuinely meaningful check — not just "is the process alive" but "does it correctly answer a request." tempfile ... become_user: payapp

Bringing It All Together · Fifteen Questions, and Where Each Answer Lives in This Handbook

1–2 · Beginner explanation and how to use this module

Every question below has already been asked and answered — in miniature — inside a specific module's Interview Question box. 1 — Explain your AWS provisioning project

Lead with the ShopSphere story shape: an application team's ServiceNow ticket becomes a validated, automated RHAAP workflow that provisions, configures, hardens, and operationally onboards a server identically every time, across a real ten-server, four-environment fleet. Full answer: Module 40.

2 — How does RHAAP authenticate to AWS?

Via IAM Role/instance profile and STS AssumeRole — never long-lived static access keys — scoped by a least-privilege policy built specifically around what the provisioning role's tasks actually need. Full answer: Module 5.

3 — How do you prevent duplicate EC2 instances?

A pre-creation lookup (ec2_instance_info) filtered by the unique Name tag, gating the actual creation task with a when condition — plus a drift check for attribute mismatches on an existing instance. Full answer: Module 13.

4 — How do you manage secrets?

Never hardcoded — RHAAP Credentials for the provisioning identity itself, Vault/CyberArk lookups at runtime for application and third-party agent credentials, always paired with no_log: true on any task that touches the resolved value. Full answer: Module 29.

5 — How do you patch 500 production servers?

Staged serial batching (e.g. 25 → 25 → 100%) combined with max_fail_percentage, so a systemic bad patch is caught on the first small batch rather than propagating fleet-wide. Full answer: Module 19.

6 — How do you perform RHEL OS upgrades?

leapp preupgrade assessment, a mandatory pre-upgrade snapshot checkpoint, leapp upgrade, an unconditional (not conditional) reboot, and an explicit post-reboot major-version assertion — run one server at a time (serial: 1) given the categorically higher risk versus routine patching. Full answer: Module 20.

7 — How do you remediate vulnerabilities?

Scanner finding → CVE/CVSS severity → ServiceNow ticket → targeted package-specific fix (not a blanket patch) → independent rescan → only then ticket closure — deliberately never closing a ticket on "fix applied" alone. Full answer: Module 21.

8 — What happens when patching fails?

A pre-check/post-check gate structure prevents patching an already-unhealthy server and confirms health after; on genuine failure, recovery is via the pre-patch snapshot restore, not live manual triage under time pressure. Full answer: Module 18, incident detail in Module 35 #16–17.

9 — How do you perform rollback?

Depends on where the failure occurred — a mid-workflow provisioning failure is quarantined (tagged, isolated, incident raised) rather than reflexively deleted or silently retried; a patch/upgrade failure rolls back via snapshot restore. Full answer: Module 34.

10 — How do you handle AWS API failures?

Diagnose connectivity before credentials before logic — DNS resolution, network path (direct/proxy/VPC endpoint), then authentication, then the specific IAM permission — because failures at each layer can look deceptively similar. Full answer: Module 6, applied throughout Module 35.

11 — How do you dynamically add newly created servers to inventory?

add_host, run in a first play against localhost immediately after EC2 creation, using the freshly-registered private IP to populate an in-memory group that a second play then targets. Full answer: Module 14.

12 — How do you design reusable Ansible roles?

Thin playbooks, fat roles; environment-specific values live in group_vars, never hardcoded inside a role's tasks; the same security_hardening role runs unmodified whether called during provisioning or remediation. Full answer: Module 7, proven at scale in Module 40.

13 — How do you implement approval workflows?

A RHAAP workflow Approval node, required conditionally based on the environment survey answer — present for QA/UAT/PROD, skippable for DEV — matching the risk-tiering established all the way back in requirement gathering. Full answer: Module 32, roots in Module 2.

14 — How do you troubleshoot RHAAP jobs?

Identify which link in the internal RHAAP → EE → Ansible → collection → auth → API/network → destination chain actually broke, investigate that specific link with the right tool, and validate the fix against the destination's own truth rather than trusting local task success alone. Full answer: Module 1's chain, applied across all 25 incidents in Module 35.

15 — Explain one major production incident you faced

Structure the real answer the same way every card in Module 35 is structured: Symptom → Investigation → Root Cause → Fix → Validation → Prevention. That structure, more than which specific incident you pick, is what signals a disciplined incident-response habit. Full answer/template: Module 35.
