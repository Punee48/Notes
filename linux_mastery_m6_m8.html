6.1Systemd Architecture — PID 1 and the Boot Chain
▶
Priya: "Why did nginx not restart after the server rebooted last night? Because nobody set it up with systemd. Let me show you how the boot system works."
WHAT IS SYSTEMD?
Systemd is the init system — the first process Linux starts (PID 1). It is responsible for starting every other service, managing their lifecycle, handling dependencies ("start nginx AFTER the network is up"), and collecting their logs. Before systemd, Linux used SysV init scripts — messy shell scripts in /etc/init.d/. Systemd replaced all of that with clean, declarative unit files.
Boot Chain — What Happens When Linux Starts
BIOS/UEFI → finds boot device → loads GRUB bootloader
↓
GRUB → loads Linux kernel (vmlinuz) + initrd into RAM
↓
Kernel → mounts root filesystem → starts PID 1: systemd
↓
systemd → reads unit files → resolves dependencies
↓
Starts network.service → sshd.service → nginx.service → your-app.service
↓
Login prompt / SSH ready ✓
UNIT FILES — THE HEART OF SYSTEMD
Every service, socket, timer, mount, or device is described by a unit file. They live in /lib/systemd/system/ (package defaults) and /etc/systemd/system/ (your overrides — always use this one).
Unit TypeExtensionPurposeExample
Service.serviceA daemon/process to runnginx.service, sshd.service
Timer.timerSchedule — replacement for cronbackup.timer
Target.targetGroup of units / boot milestonemulti-user.target
Socket.socketStart service on demand when port gets trafficnginx.socket
Mount.mountMount filesystems via systemddata.mount
Exploring Systemd
# systemd is always PID 1 nebula@prod-01:~$ ps -p 1 -o pid,comm,args PID COMMAND COMMAND 1 systemd /sbin/init # See the full unit dependency tree nebula@prod-01:~$ systemctl list-units --type=service --state=running # list-units = show all loaded units # --type=service = only .service files # --state=running = only currently active ones # See what nginx depends on (what must start before it) nebula@prod-01:~$ systemctl list-dependencies nginx.service # See boot timing — what took longest to start? nebula@prod-01:~$ systemd-analyze blame | head -10 12.431s mysql.service 3.214s networking.service 0.892s nginx.service # Total boot time nebula@prod-01:~$ systemd-analyze Startup finished in 2.1s (kernel) + 14.8s (userspace) = 16.9s

ANATOMY OF A SERVICE UNIT FILE — EVERY LINE EXPLAINED
📄 /etc/systemd/system/nebula-api.service
# ════════════════════════════════════════════════ # [Unit] section: describes the unit and its relationships [Unit] Description=NebulaCloud REST API Service # Description: shown in systemctl status — make it informative After=network.target mysql.service # After: start AFTER these units are active. Ordering only — not dependency. Requires=mysql.service # Requires: HARD dependency — if mysql fails, this unit also fails # Use Wants= for soft dependency (if mysql fails, we still try to start) # ════════════════════════════════════════════════ # [Service] section: HOW to run the service [Service] Type=simple # Type=simple: ExecStart is the main process. systemd tracks it directly. # Other types: forking (daemon that forks), notify (sends ready signal), oneshot User=nebula Group=nebula # CRITICAL: run as this user/group, not root. Security principle of least privilege. WorkingDirectory=/opt/nebula-api # Set the working directory (where ExecStart runs from) EnvironmentFile=/etc/nebula-api/config.env # Load environment variables from a file (secrets, DB passwords, etc.) # In config.env: DB_PASSWORD=secret API_KEY=abc123 ExecStart=/usr/bin/python3 -m gunicorn -w 4 -b 0.0.0.0:5000 app:create_app() # ExecStart: the exact command to run. MUST use full absolute paths. ExecReload=/bin/kill -s HUP $MAINPID # ExecReload: command for 'systemctl reload'. $MAINPID = the service's PID. Restart=on-failure # Restart: when to auto-restart. # on-failure: restart if it exits non-zero or is killed by a signal # always: restart no matter what (even clean exit) # on-abnormal: restart on signal/watchdog/timeout only RestartSec=5 # Wait 5 seconds before restarting (avoid rapid restart loops) StandardOutput=journal StandardError=journal # Send stdout and stderr to systemd's journal (journalctl reads this) # Security hardening options NoNewPrivileges=true PrivateTmp=true # NoNewPrivileges: process can't gain new capabilities (sudo etc.) # PrivateTmp: isolate /tmp — process gets its own /tmp (can't see others') # ════════════════════════════════════════════════ # [Install] section: where to link this unit when 'enabled' [Install] WantedBy=multi-user.target # multi-user.target = normal server boot state (network up, no GUI) # When you run 'systemctl enable', it creates a symlink in # /etc/systemd/system/multi-user.target.wants/nebula-api.service

6.4Journald & Logging — Read Logs Like a Pro
▶
Priya: "The API is crashing at 3AM. I need to see logs from last night, filter only errors, and understand what happened 5 minutes before each crash."
journalctl — THE SYSTEMD LOG READER
Journald collects logs from all services (not just nginx — your app, the kernel, systemd itself) and stores them in a binary database with rich metadata: service name, priority level, PID, user, timestamp. journalctl is the query tool.
journalctl — Every Flag You'll Actually Use
# Follow logs in real-time (like tail -f but for everything) nebula@prod-01:~$ journalctl -f # Logs for ONE specific service nebula@prod-01:~$ journalctl -u nebula-api.service # -u = unit: filter by service name # Follow logs for ONE service (best for watching a service) nebula@prod-01:~$ journalctl -fu nebula-api.service # -f = follow, -u = unit. Together = live logs for that service only # Logs since a specific time nebula@prod-01:~$ journalctl -u nebula-api --since "2026-05-18 02:50:00" --until "2026-05-18 03:20:00" # --since and --until: time ranges (human-readable strings work!) nebula@prod-01:~$ journalctl -u nebula-api --since "1 hour ago" nebula@prod-01:~$ journalctl -u nebula-api --since yesterday # Filter by PRIORITY (severity level) nebula@prod-01:~$ journalctl -u nebula-api -p err # -p err = only errors and above (err, crit, alert, emerg) # Priority levels: debug info notice warning err crit alert emerg # Show last N lines (like tail) nebula@prod-01:~$ journalctl -u nebula-api -n 50 --no-pager # -n 50 = last 50 lines # --no-pager = output directly (don't use less — good for scripts) # Previous boot's logs (great for diagnosing crash-on-boot) nebula@prod-01:~$ journalctl -b -1 # -b = boot. -b 0 = this boot. -b -1 = previous boot. -b -2 = two boots ago. # Kernel messages only (like dmesg but from journal) nebula@prod-01:~$ journalctl -k --since "1 hour ago" # Output in JSON (for parsing in scripts) nebula@prod-01:~$ journalctl -u nebula-api -n 5 -o json | python3 -m json.tool # How much disk space do logs use? nebula@prod-01:~$ journalctl --disk-usage Archived and active journals take up 2.8G on disk. # Clean up old logs (keep only last 500MB) nebula@prod-01:~$ sudo journalctl --vacuum-size=500M
The crash investigation workflow: (1) journalctl -u myapp -p err --since yesterday → find error timestamps. (2) journalctl --since "HH:MM:SS" --until "HH:MM:SS" → get full context around each error. (3) journalctl -k --since "..." → check if kernel had issues too (OOM killer, disk errors).

7.3awk, sed & Regex — Text Processing Mastery
▶
Priya: "Parse the nginx access log, extract all 5xx errors with IPs, count them by hour, and output a CSV for the ops dashboard. You have 10 minutes."
awk — THE COLUMN PROCESSOR
awk processes files line by line, automatically splitting each line into fields ($1, $2...). Think of it as a mini programming language for structured text.
awk — From Basic to Pro
# Nginx log format: IP - - [date] "method url protocol" status bytes # 192.168.1.5 - - [18/May/2026:03:14:22] "GET /api/users HTTP/1.1" 500 234 # Print specific columns nebula@prod-01:~$ awk '{print $1, $9}' /var/log/nginx/access.log | head -5 # $1 = IP address $9 = HTTP status code # Filter only 5xx errors (pattern matching) nebula@prod-01:~$ awk '$9 ~ /^5/' /var/log/nginx/access.log # $9 ~ /^5/ = field 9 matches regex starting with 5 # ~ = match !~ = not match == = exact equal # Count 5xx errors by IP address nebula@prod-01:~$ awk '$9 ~ /^5/ {count[$1]++} END {for(ip in count) print count[ip], ip}' /var/log/nginx/access.log | sort -rn # {count[$1]++} = for each matching line, increment count[IP] # END {...} = run this block AFTER processing all lines # for(ip in count) = iterate over all keys in the count associative array # Extract hour from log timestamp and count 5xx per hour nebula@prod-01:~$ awk '$9 ~ /^5/ {split($4,t,":"); hour=substr(t[2],1,2); errors[hour]++} END {for(h in errors) print h":00,"errors[h]}' /var/log/nginx/access.log | sort > errors_by_hour.csv # split($4,t,":") = split field 4 on ":" into array t # substr(t[2],1,2) = get chars 1-2 of the hour field # Use custom field separator (-F) nebula@prod-01:~$ awk -F: '{print $1}' /etc/passwd # -F: = split fields on colon (default is whitespace)

sed — Find, Replace, Transform

#!/bin/bash # ── STRICT MODE (Always use this in production scripts) ────── set -e # Exit immediately when any command returns non-zero set -u # Treat unset variables as errors (catches typos like $SERVR_NAME) set -o pipefail # Catch failures in pipes: 'false | true' returns 1, not 0 # Or in one line: set -euo pipefail # ── TRAP — Run cleanup code on exit or error ────────────────── TMPFILE=$(mktemp /tmp/nebula-backup-XXXXXX.tmp) # mktemp = create secure unique temp file. XXXXXX = random characters cleanup() { local exit_code=$? # Capture exit code FIRST (before anything changes it) rm -f "$TMPFILE" # Always delete temp file if [[ $exit_code -ne 0 ]]; then echo "[ERROR] Script failed at line $BASH_LINENO with code $exit_code" >&2 # $BASH_LINENO = the line number where the error occurred # >&2 = send to stderr (errors belong in stderr, not stdout) fi } trap cleanup EXIT # Call cleanup() on ANY exit (success or failure) trap 'echo "Caught SIGINT — exiting" >&2; exit 130' INT # Handle Ctrl+C # ── SAFE COMMAND EXECUTION ─────────────────────────────────── run_step() { local description="$1"; shift # shift removes $1, so $@ is now the command echo "[STEP] $description" if "$@"; then # "$@" expands all args as separate words echo "[OK] $description" else echo "[FAIL] $description — aborting" >&2 exit 1 fi } # Usage — each step clearly named and verified: run_step "Sync code from git" git pull origin main run_step "Install dependencies" pip install -r requirements.txt run_step "Run database migrations" python manage.py migrate run_step "Restart API service" systemctl restart nebula-api run_step "Health check" curl -sf http://localhost:5000/health

#!/bin/bash set -euo pipefail # ── CONFIGURATION ──────────────────────────────────────────── readonly APP_DIR="/opt/nebula-api" readonly BACKUP_DIR="/home/nebula/nebula/backups" readonly SERVICE="nebula-api" readonly HEALTH_URL="http://localhost:5000/health" readonly BRANCH=${1:-main} # $1 = first arg, or 'main' if not provided TIMESTAMP=$(date +%Y%m%d-%H%M%S) ROLLBACK_COMMIT="" # Will store current commit for rollback # ── LOGGING ────────────────────────────────────────────────── LOG_FILE="/var/log/nebula/deploy-$TIMESTAMP.log" exec > >(tee -a "$LOG_FILE") 2>&1 # All output goes to screen AND log file # exec > >(...) = redirect stdout to a process substitution # tee -a $LOG = write to log while also passing to stdout # 2>&1 = merge stderr into stdout log() { echo "[$(date +%T)] $*"; } die() { echo "[ERROR] $*" >&2; rollback; exit 1; } # ── ROLLBACK FUNCTION ──────────────────────────────────────── rollback() { log "⚠️ ROLLING BACK to $ROLLBACK_COMMIT" if [[ -n "$ROLLBACK_COMMIT" ]]; then git -C "$APP_DIR" checkout "$ROLLBACK_COMMIT" systemctl restart "$SERVICE" log "✓ Rollback complete" fi } # ── DEPLOY STEPS ───────────────────────────────────────────── log "═══════════════════════════════════════" log "🚀 NEBULA DEPLOY — Branch: $BRANCH" log "═══════════════════════════════════════" # Step 1: Save current commit (for rollback) ROLLBACK_COMMIT=$(git -C "$APP_DIR" rev-parse HEAD) log "Current commit: $ROLLBACK_COMMIT" # Step 2: Backup database log "[1/5] Backing up database..." mysqldump -u nebula -p"${DB_PASS}" nebula_db > "$BACKUP_DIR/db-$TIMESTAMP.sql" \ || die "Database backup FAILED" gzip "$BACKUP_DIR/db-$TIMESTAMP.sql" log "✓ Database backed up" # Step 3: Pull new code log "[2/5] Pulling $BRANCH..." git -C "$APP_DIR" fetch origin || die "Git fetch FAILED" git -C "$APP_DIR" checkout "$BRANCH" || die "Git checkout FAILED" git -C "$APP_DIR" pull origin "$BRANCH" || die "Git pull FAILED" # Step 4: Install deps + migrate log "[3/5] Installing dependencies..." pip install -q -r "$APP_DIR/requirements.txt" || die "pip install FAILED" python3 "$APP_DIR/manage.py" migrate || die "Database migration FAILED" # Step 5: Restart service log "[4/5] Restarting $SERVICE..." systemctl restart "$SERVICE" || die "Service restart FAILED" # Step 6: Health check with retry loop log "[5/5] Health checking..." ok=false for i in {1..15}; do if curl -sf "$HEALTH_URL" &>/dev/null; then ok=true; break fi log "Waiting for app to start... ($i/15)" sleep 2 done $ok || die "Health check FAILED — app did not respond in 30s" log "═══════════════════════════════════════" log "✅ DEPLOY SUCCESSFUL — $(date)" log "═══════════════════════════════════════"
Run this with bash ./deploy.sh main. If any step fails, die() calls rollback() automatically. The full log is saved to /var/log/nebula/. This is professional-grade deployment scripting.

8.1The Systematic Diagnosis Framework — Never Panic Again
▶
3:07 AM. PagerDuty: "CRITICAL: nebula-api is returning 502 errors. 100% of requests failing. Revenue impact." Your hands are shaking. What do you do first?
THE 5-STEP DIAGNOSIS FRAMEWORK
The biggest mistake under pressure is jumping to solutions before understanding the problem. Engineers who stay calm and follow a system solve incidents faster than those who randomly try fixes. Here is the framework.
Systematic Troubleshooting — Always In This Order
1
DEFINE THE PROBLEM — What EXACTLY is broken? Who is affected? Since when? What changed?
2
CHECK THE BASICS — Is the service running? Is there disk/memory? Network up? DNS resolving?
3
READ THE LOGS — What do journalctl, app logs, and system logs say at the time of failure?
4
ISOLATE THE LAYER — OSI model: Physical→Network→Transport→Application. Test each layer in order.
5
FIX & VERIFY — One change at a time. Verify it worked. Document what you did for the post-mortem.
The First 5 Minutes — Your Opening Checklist
# ── Step 2: CHECK THE BASICS — Run these first, always ─────── # Is the service running? nebula@prod-01:~$ systemctl status nebula-api nginx mysql # Is disk full? (a classic cause of silent failures) nebula@prod-01:~$ df -h Filesystem Size Used Avail Use% Mounted on /dev/sda2 50G 50G 0 100% / ← DISK FULL! Found it. # Is memory exhausted? (OOM killer may have killed your process) nebula@prod-01:~$ free -h nebula@prod-01:~$ dmesg | grep -i "oom\|killed" | tail -20 # dmesg = kernel ring buffer — kernel messages including OOM events # What changed recently? (Deployments, config changes, package updates) nebula@prod-01:~$ last -n 20 # last = show login history (was someone logged in before this broke?) nebula@prod-01:~$ grep "upgrade\|install" /var/log/dpkg.log | tail -10 # dpkg.log = package installation history # System load — is the server overwhelmed? nebula@prod-01:~$ uptime 03:12:45 up 7 days, load average: 28.3, 26.1, 22.4 # Load average = how many processes waiting for CPU # Rule: load avg should be ≤ number of CPU cores. Check: nproc nebula@prod-01:~$ nproc 4 ← 4 cores. Load of 28 means the server is 7x overloaded!
The "what changed?" question solves 80% of incidents. If nothing changed, it's often a resource limit (disk, memory, file descriptors). Ask: "Did anyone deploy, change config, or run a big query in the last hour?" Check last, dpkg.log, and git log first.

8.3Performance Profiling — Find What's Eating Your Server
▶
Priya: "Response times jumped from 50ms to 8 seconds after last night's deploy. CPU is 95%. Something is wrong with the code. Find it."
PERFORMANCE TOOLBOX — CPU, MEMORY, DISK, PROCESSES
Performance Investigation
# ── CPU ────────────────────────────────────────────────────── # Interactive process viewer (press q to quit, k to kill, P=CPU sort, M=MEM sort) nebula@prod-01:~$ top nebula@prod-01:~$ htop # htop = prettier version. Install: sudo apt install htop # Top 5 CPU consumers right now nebula@prod-01:~$ ps aux --sort=-%cpu | head -6 USER PID %CPU %MEM COMMAND nebula 8901 94.2 3.1 python3 worker.py ← Found it! A worker eating CPU # strace: trace SYSTEM CALLS made by a process # "What is that process actually DOING?" nebula@prod-01:~$ sudo strace -p 8901 -c # -p 8901 = attach to running process (doesn't stop it) # -c = summary: count syscalls by type and time spent % time seconds usecs/call calls syscall 98.14 14.823421 14 999999 read ← reading 1M times! Infinite loop? # read() 999999 times = infinite loop reading from a file descriptor # See WHAT file it's reading from nebula@prod-01:~$ sudo strace -p 8901 -e trace=read,open,openat 2>&1 | head -20 # -e trace=syscall1,syscall2 = only trace these system calls # What files does the process have open? nebula@prod-01:~$ ls -la /proc/8901/fd # /proc/PID/fd = file descriptors open by that process # ── MEMORY ─────────────────────────────────────────────────── nebula@prod-01:~$ free -h nebula@prod-01:~$ cat /proc/meminfo | grep -E "MemTotal|MemFree|Cached|SwapFree" # If SwapFree is tiny → system is swapping heavily → very slow # ── DISK I/O ───────────────────────────────────────────────── nebula@prod-01:~$ iostat -xz 1 3 # iostat = I/O Statistics. -x = extended. -z = omit idle devices # 1 3 = sample every 1 second, 3 times # Key column: %util — if 100% = disk is maxed out # Which process is doing the most disk I/O? nebula@prod-01:~$ sudo iotop -o # iotop = like top but for I/O. -o = only show processes doing I/O # ── FILE DESCRIPTORS (common hidden limit) ──────────────────── nebula@prod-01:~$ ulimit -n # ulimit -n = max open files per process. Default often 1024 — too low for servers! nebula@prod-01:~$ cat /proc/8901/limits | grep "open files" nebula@prod-01:~$ ls /proc/8901/fd | wc -l # If these are equal → "Too many open files" error → raise limits in unit file
The Brendan Gregg USE Method: For every resource (CPU, memory, disk, network), check Utilization (how busy?), Saturation (is there a queue?), Errors (any failures?). This is the fastest way to find bottlenecks.

8.5Live Production Lab — 10 Real Scenarios, Timed
▶
Priya: "It's your final test. Ten production scenarios, each one something that actually happened at NebulaCloud. Diagnose each one. I want your commands, your reasoning, and your fix — not just the answer."
THE 10 PRODUCTION SCENARIOS
For each scenario: (1) Write your diagnosis commands. (2) Form a hypothesis. (3) Verify with a command. (4) Fix it. (5) Verify the fix works. Don't just read the hints — solve it first!
  • ① DISK
    Scenario: nginx returns 502. systemctl status nginx shows "active running". App logs stop suddenly at 03:14. Disk usage: ???
    Hint: always check disk first. What command? What to look for?
    df -h → 100% full. find /var/log -name "*.log" -size +100M → giant log file. truncate -s 0 /var/log/bigfile.log OR logrotate -f /etc/logrotate.conf → free up space → systemctl restart nebula-api
  • ② OOM
    Scenario: App process keeps dying every few minutes with no error in app logs. Memory is 99%. What happened?
    dmesg | grep -i oom → "Out of memory: Kill process" → OOM killer is murdering the process. Fix: add LimitMEMLOCK and LimitNOFILE to systemd unit, or add swap: dd if=/dev/zero of=/swapfile bs=1M count=2048 && mkswap /swapfile && swapon /swapfile, or fix a memory leak in the app.
  • ③ PORT
    Scenario: Service fails to start. Error: "bind: address already in use" for port 5000. How do you find and fix it?
    ss -tlnp | grep :5000 → find which PID is using port. Then: kill -9 PID OR systemctl stop conflicting-service → systemctl start nebula-api
  • ④ PERM
    Scenario: Deploy script fails: "Permission denied: /opt/nebula-api/logs/app.log". The file exists. What's wrong?
    ls -la /opt/nebula-api/logs/ → file is owned by root. chown nebula:nebula /opt/nebula-api/logs/app.log OR chown -R nebula:nebula /opt/nebula-api/logs/
  • ⑤ DNS
    Scenario: App logs: "getaddrinfo: Name or service not known: db.nebula.internal". ping to IP works but name fails.
    cat /etc/resolv.conf → check DNS server. dig db.nebula.internal @your-dns-server → if fails, DNS server issue. Quick fix: add to /etc/hosts. Real fix: check internal DNS server (systemctl status systemd-resolved OR bind9)
  • ⑥ ZOMBIE
    Scenario: ps aux shows many processes in state 'Z' (zombie). What is a zombie? Is it dangerous? How to clean up?
    Zombie = dead process whose parent hasn't read its exit code yet (wait() not called). Not dangerous (no CPU/memory) but PID leak. Find parent: ps aux | grep Z → look at PPID column. Kill parent (pkill -P PPID) → zombies vanish. Real fix: fix the parent process to properly reap children.
  • ⑦ LOAD
    Scenario: Load average is 45 on a 4-core server. System is crawling. How do you find the cause?
    top → sort by CPU (P key). ps aux --sort=-%cpu | head. Check if it's CPU bound: %us high → user code. %sy high → kernel/system calls → could be too many context switches. iostat → if %iowait high → disk I/O bottleneck (check for large queries, log writes, or a stuck fsync)
  • ⑧ FIREWALL
    Scenario: New developer can't SSH in. They get "Connection refused" on port 22. Other users work fine. Why?
    Check /etc/ssh/sshd_config: AllowUsers → their username not listed. OR check fail2ban: sudo fail2ban-client status sshd → their IP is banned. Fix: add username to AllowUsers → sudo systemctl reload sshd. OR: sudo fail2ban-client set sshd unbanip their.ip.address
  • ⑨ CRON
    Scenario: Cron job is in crontab but never runs. No errors visible. How do you debug a silent cron job?
    (1) grep CRON /var/log/syslog → did cron even try? (2) Add logging to the job: 0 2 * * * /script.sh >> /tmp/cron-out.log 2>&1 (3) Test manually with the EXACT command (3) Check: does the script use full paths? (cron has minimal PATH) (4) Check file permissions: chmod +x /script.sh (5) Check crontab syntax at crontab.guru
  • ⑩ SSL
    Scenario: Users get "SSL certificate expired" error. nginx is serving an old cert. How do you quickly check and renew?
    Check expiry: echo | openssl s_client -connect your-domain.com:443 2>/dev/null | openssl x509 -noout -dates → see notAfter. Renew: sudo certbot renew (or certbot certonly --nginx -d domain.com) → sudo systemctl reload nginx. Set up auto-renewal: sudo systemctl enable certbot.timer
