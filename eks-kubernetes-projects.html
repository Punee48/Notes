Blue/Green Deployment with AWS ALB & Argo Rollouts

Zero-downtime production releases used by Netflix, Amazon & Flipkart engineering teams
EKS 1.30Argo RolloutsAWS ALB IngressHelm 3ECRGitHub Actionskubectl
The Story
Scene: It's 2:00 AM at a leading Indian e-commerce company. The engineering team just pushed a critical payment service update. Within seconds, orders start failing — the new version has a bug. The on-call engineer breaks into a cold sweat.

The Problem: Their EKS cluster used a simple kubectl rolling update, which replaced all pods gradually. By the time someone noticed, 40% of production traffic was already hitting the broken version. Rolling back took 7 minutes — 7 minutes of revenue loss worth ₹2.3 crore.

The Solution: Enter Blue/Green Deployment with Argo Rollouts. Instead of replacing pods in-place, you run TWO complete environments simultaneously — the Blue (current stable) and the Green (new version). Traffic is instantly switchable. If Green misbehaves, one command flips the ALB back to Blue in under 5 seconds.

Define the Argo Rollout Resource
YAMLpayment-service-rollout.yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout               # ← custom resource type provided by Argo CRD
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 4               # run 4 pods for each environment
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
    spec:
      containers:
      - name: payment
        image: 123456789.dkr.ecr.ap-south-1.amazonaws.com/payment:v2.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "250m"    # request 250 millicores (0.25 vCPU)
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
  strategy:
    blueGreen:                # ← this is where the magic lives
      activeService: payment-active    # K8s service pointing to BLUE (live)
      previewService: payment-preview  # K8s service pointing to GREEN (new)
      autoPromotionEnabled: false       # require manual approval to promote
      scaleDownDelaySeconds: 30         # keep old pods 30s after switch
      prePromotionAnalysis:              # run analysis before promoting
        templates:
        - templateName: success-rate
        args:
        - name: service-name
          value: payment-preview
YAML KeyExplanation
kind: RolloutCustom Resource Definition (CRD) installed by Argo — extends Kubernetes vocabulary beyond standard Deployments
activeServiceThe K8s Service that serves 100% real user traffic — always points to the current stable (Blue) version
previewServicePoints to the new (Green) version — testers and QA can hit this URL to verify before promotion
autoPromotionEnabled: falseRequires a human (or CI pipeline) to explicitly approve the switch — adds a safety gate
scaleDownDelaySeconds: 30Keeps old Blue pods alive for 30 seconds after promotion — allows in-flight requests to complete gracefully
prePromotionAnalysisRuns automated health checks (success rate, latency) against Green before allowing promotion to proceed

GitOps Pipeline with Flux CD & Amazon ECR

The way Spotify, Zalando, and Adobe manage hundreds of microservices without manual kubectl
Flux CD v2GitHubECREKSKustomizeSOPS + AgeHelm
The Story
Scene: A DevOps engineer at a European fintech company is managing 120 microservices across 3 EKS clusters (dev/staging/prod). Every release requires someone to SSH into a machine, run kubectl apply, and hope nothing breaks. Six people share the kubeconfig. Two of them accidentally deployed to prod when they meant staging last month.

Enter GitOps: The core principle is revolutionary — Git is the single source of truth. Nobody runs kubectl manually. Instead, you commit desired state to a Git repo, and Flux CD continuously watches that repo. The moment a new image is pushed to ECR, Flux detects it, updates the YAML, commits back to Git, and reconciles the cluster. The cluster pulls its own configuration. No push. No credentials shared. Full audit trail.
Architecture

Step-by-Step Implementation
Bootstrap Flux on Your EKS Cluster
BASHflux-bootstrap.sh
# Install Flux CLI

  --path=./clusters/production \  # where cluster manifests live in the repo
  --personal

# Verify all Flux pods are running
kubectl get pods -n flux-system

Node Autoscaling with Karpenter — Smart, Fast, Cost-Optimal

How Airbnb reduced EC2 costs by 47% by replacing Cluster Autoscaler with Karpenter
Karpenter v0.37EKSEC2 SpotIRSANodePool CRDEC2NodeClass
The Story
Problem: A SaaS company's data pipeline ran 5,000 pods daily. Their old Cluster Autoscaler took 3-5 minutes to provision a new node — pods sat in Pending state during that time. Worse, it only scaled pre-defined node groups (e.g., "m5.xlarge group"), meaning even a pod needing just 2 vCPUs got a 4-vCPU machine because that was the group size.

Karpenter's Revolution: Karpenter watches for Pending pods and provisions the exact right instance type in under 60 seconds. It directly calls EC2 APIs — no Auto Scaling Groups needed. It can mix Spot + On-Demand intelligently. A pod needing 6GB RAM gets a c6g.large, not an overprovisioned m5.2xlarge. The result: faster scheduling and dramatically lower bills.
Architecture
Pending Pod (needs 4 vCPU, 8Gi RAM) │ ▼ Karpenter Controller │ ├─ Reads Pod resource requirements ├─ Queries EC2 price API for cheapest fitting instance ├─ Selects: c6g.xlarge Spot ($0.05/hr) vs m5.xlarge On-Demand ($0.19/hr) │ ▼ Launches EC2 instance directly (bypasses ASG) │ ▼ Node joins EKS cluster (via bootstrap script) │ ⏱ All this in ~45 seconds ▼ Pod scheduled onto new node NodePool (rules Karpenter follows): ├── Allow families: [c, m, r] series ├── Allow arch: [amd64, arm64] ├── Spot budget: 80%, On-Demand: 20% └── Consolidation: yes (bin-pack & terminate idle nodes)

Create NodePool — Karpenter's Provisioning Rules
YAMLnodepool.yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general-purpose
spec:
  template:
    spec:
      requirements:             # Rules: only provision these kinds of nodes
      - key: karpenter.sh/capacity-type
        operator: In
        values: ["spot", "on-demand"]  # prefer Spot, fallback to On-Demand
      - key: kubernetes.io/arch
        operator: In
        values: ["amd64", "arm64"]  # allow ARM (Graviton) for cost savings
      - key: node.kubernetes.io/instance-type
        operator: In
        values: ["m5.large","m5.xlarge","c6g.large","c6g.xlarge","r6g.large"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  limits:
    cpu: 1000       # max 1000 vCPUs total managed by this NodePool
    memory: 4000Gi
  disruption:
    consolidationPolicy: WhenUnderutilized  # merge underused nodes to save cost
    consolidateAfter: 30s                   # wait 30s before consolidating
---
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  amiFamily: AL2023      # Amazon Linux 2023 — latest hardened AMI
  role: "KarpenterNodeRole-my-production-cluster"
  subnetSelectorTerms:
  - tags:
      karpenter.sh/discovery: my-production-cluster
  securityGroupSelectorTerms:
  - tags:
      karpenter.sh/discovery: my-production-cluster
FieldExplanation
NodePoolNew CRD in Karpenter v1 — defines a set of rules for what kind of nodes to provision. Replaces old Provisioner resource
consolidationPolicy: WhenUnderutilizedKarpenter automatically identifies nodes running at <50% capacity and drains + terminates them, rescheduling pods elsewhere — automatic cost savings
EC2NodeClassDefines AWS-specific settings: which AMI, which subnets, which security groups — the AWS "shape" of the node

PROJECT 04 Multi-Tenancy · Security ⭐⭐⭐⭐ Expert

Multi-Tenant EKS with IRSA, RBAC & Namespace Hard Isolation

How Atlassian and ServiceNow run 50+ product teams on a single EKS cluster safely
EKSIRSARBACNetworkPolicyResourceQuotaKyvernoLimitRange
The Story
The Challenge: A multinational bank runs 40 development teams — each team builds a different microservice (Payments, Loans, KYC, Notifications). Running 40 separate EKS clusters would cost millions per month. The solution: one shared cluster, but with hard walls between tenants.

The Architecture: Each team gets their own namespace. Kubernetes RBAC ensures team-payments can never see or touch resources in team-loans. NetworkPolicy blocks cross-namespace network traffic. ResourceQuota caps CPU/Memory so one team can't hog the cluster. Each team's pods get their own IAM role via IRSA — team-payments' pods can only access their own S3 bucket, DynamoDB table, etc.
Step-by-Step Implementation
Create Namespace with Labels and Quotas
YAMLtenant-payments-namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: team-payments
  labels:
    tenant: payments
    environment: production
    pod-security.kubernetes.io/enforce: restricted  # PSA policy
---
apiVersion: v1
kind: ResourceQuota          # Caps total resources this namespace can consume
metadata:
  name: payments-quota
  namespace: team-payments
spec:
  hard:
    requests.cpu: "20"         # team can request up to 20 vCPUs total
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    count/pods: "50"           # max 50 pods in this namespace
    count/services: "10"
    persistentvolumeclaims: "20"
---
apiVersion: v1
kind: LimitRange             # Sets DEFAULT limits for pods that don't specify any
metadata:
  name: payments-limits
  namespace: team-payments
spec:
  limits:
  - type: Container
    default:
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:
      cpu: "100m"
      memory: "128Mi"

Enforce Network Isolation with NetworkPolicy
YAMLnetwork-policy-isolation.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-cross-namespace
  namespace: team-payments
spec:
  podSelector: {}             # applies to ALL pods in this namespace
  policyTypes:
  - Ingress                   # control INCOMING traffic
  - Egress                    # control OUTGOING traffic
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          tenant: payments    # ONLY allow traffic from same namespace
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          tenant: payments
  - to:                        # also allow DNS resolution
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - port: 53                  # DNS port — without this, pods can't resolve names
      protocol: UDP

PROJECT 05 Service Mesh · Security ⭐⭐⭐⭐ Expert

Service Mesh with Istio & mTLS Encryption Between Services

How Goldman Sachs ensures every microservice call is encrypted and authenticated end-to-end
Istio 1.22EKSmTLSEnvoy ProxyKialiJaeger TracingVirtualService
The Story
Problem: In a financial system with 80 microservices, service-A calls service-B over plain HTTP. A rogue pod or a misconfigured container could snoop on that traffic using a simple network capture. Regulators like RBI (Reserve Bank of India) demand encryption in transit for all internal service communication — not just external-facing APIs.

Istio's Solution: Istio injects a tiny Envoy sidecar proxy into every pod automatically. ALL traffic between pods flows through these sidecars, which establish mutual TLS (mTLS) — both sides present certificates, verify each other's identity, and encrypt the connection. Developers write zero TLS code. The mesh handles it transparently. Bonus: you get distributed tracing, traffic management, and circuit breaking for free.
Architecture

Enforce Strict mTLS Cluster-Wide
YAMLpeer-authentication.yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication       # Defines how mTLS is enforced
metadata:
  name: default
  namespace: istio-system     # namespace=istio-system → applies cluster-wide
spec:
  mtls:
    mode: STRICT              # STRICT = reject all non-mTLS connections
    # mode: PERMISSIVE = allow both mTLS and plain HTTP (for migration)
---
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy     # Who is allowed to call whom
metadata:
  name: payments-authz
  namespace: production
spec:
  selector:
    matchLabels:
      app: payment-service
  action: ALLOW
  rules:
  - from:
    - source:
        principals:             # only these service accounts can call payment-service
        - "cluster.local/ns/production/sa/api-gateway"
        - "cluster.local/ns/production/sa/order-service"
FieldExplanation
PeerAuthenticationGoverns how Envoy proxies authenticate with each other — STRICT means both sides must present valid certificates

YAMLrequire-resource-limits.yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate           # defines the schema AND the Rego logic
metadata:
  name: requireresourcelimits
spec:
  crd:
    spec:
      names:
        kind: RequireResourceLimits  # creates a new CRD with this name
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package requireresourcelimits  # Rego package declaration

      violation[{"msg": msg}] {      # violation block: adds to list if rule matches
        container := input.review.object.spec.containers[_]  # iterate all containers
        not container.resources.limits.cpu                   # true if CPU limit is missing
        msg := sprintf("Container '%v' has no CPU limit set", [container.name])
      }

      violation[{"msg": msg}] {
        container := input.review.object.spec.containers[_]
        not container.resources.limits.memory
        msg := sprintf("Container '%v' has no memory limit set", [container.name])
      }
---
# Constraint: APPLY the template to specific resources
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: RequireResourceLimits         # references the CRD created by the template
metadata:
  name: must-have-resource-limits
spec:
  enforcementAction: deny           # deny = block the request. warn = allow but log
  match:
    kinds:
    - apiGroups: ["*"]
      kinds: ["Pod"]
    excludedNamespaces:               # don't enforce in system namespaces
    - kube-system
    - gatekeeper-system
Rego ConceptExplanation
violation[{"msg": msg}]Rego rule — the body evaluates, and if all conditions are true, the violation is added to the result set with the message
input.review.objectThe Kubernetes resource being evaluated — this is the Pod/Deployment YAML submitted to the API server
containers[_]Rego's iteration syntax — [_] means "for each element in the array, assign it to an unnamed variable"
not container.resources.limits.cpuTrue when the CPU limit field is absent/undefined — triggers the violation
enforcementAction: denyHard block — kubectl apply returns 403 Forbidden with your message. Use "warn" first during rollout

KEDA v2.14AWS SQSEKSHPAScaledObjectTriggerAuthentication
The Story
The Lunch Rush Problem: An order processing service receives 10 orders/minute at 10 AM, but 5,000 orders/minute at 1 PM. Standard HPA scales based on CPU — but order processing pods are mostly waiting on database I/O, so CPU stays low even when the SQS queue has 50,000 unprocessed messages.

KEDA's Intelligence: KEDA (Kubernetes Event Driven Autoscaling) extends HPA to scale based on any external metric — SQS queue depth, Kafka lag, Redis list length, Prometheus metrics, even a custom HTTP endpoint. When the SQS queue grows, KEDA scales up workers proportionally. When the queue drains, it scales down to 0 — paying for compute only when needed.

  name: aws-sqs-auth
  namespace: production

Create ScaledObject — The Magic Configuration
YAMLorder-processor-scaled-object.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-processor-scaler
  namespace: production
spec:
  scaleTargetRef:
    name: order-processor       # the Deployment to scale
  minReplicaCount: 0           # scale to 0 when queue is empty (cost zero!)
  maxReplicaCount: 500         # max 500 pods during peak load
  cooldownPeriod: 300          # wait 5 minutes before scaling down
  pollingInterval: 15          # check SQS every 15 seconds
  triggers:
  - type: aws-sqs-queue
    authenticationRef:
      name: aws-sqs-auth
    metadata:
      queueURL: https://sqs.ap-south-1.amazonaws.com/ACCOUNT/orders-queue
      queueLength: "10"          # 1 pod for every 10 messages in queue
      awsRegion: ap-south-1
      identityOwner: operator   # KEDA operator uses its own IRSA role
FieldExplanation
minReplicaCount: 0KEDA's superpower — can scale to zero. Standard HPA minimum is 1. Zero means zero cost when idle
queueLength: "10"Target: each pod processes 10 messages. If queue has 100 messages, KEDA scales to 10 pods. 1000 messages → 100 pods
cooldownPeriod: 300After load decreases, wait 5 minutes before scaling down — prevents rapid scale-up/scale-down oscillation
pollingInterval: 15KEDA checks SQS every 15 seconds and adjusts HPA target accordingly — near real-time responsiveness

Zero-Downtime EKS Cluster Upgrade — v1.28 to v1.30 Production Strategy

The upgrade runbook used by Amazon internal teams to upgrade 10,000+ EKS clusters per year
eksctlkubectlaws-cliPodDisruptionBudgetkubectl drainManaged Node Groups
The Story
The Fear: Upgrading a production Kubernetes cluster feels like performing open-heart surgery on a running patient. Get it wrong and you have a broken control plane, stuck nodes, and panicked 3 AM calls. Many teams stay on old versions (some still on 1.23!) because they're too scared to upgrade.

The Reality: AWS makes EKS control plane upgrades remarkably safe — they manage the etcd, API server, and controller manager rollover automatically. Your risk is in the data plane (nodes). The key is: upgrade one minor version at a time (1.28→1.29→1.30, never skip), validate each step, and use Blue/Green node groups to keep user traffic uninterrupted throughout.
Step-by-Step Implementation
Pre-Upgrade Checklist & Compatibility Checks
BASHpre-upgrade-checks.sh
# 1. Check current cluster version
kubectl version --short

# 2. Run AWS upgrade insights — detects API deprecations BEFORE upgrade
aws eks list-insights \
  --cluster-name my-cluster \
  --filter category=UPGRADE_READINESS

# 3. Check for deprecated APIs being used in your cluster
kubectl get apiservices | grep False    # look for degraded API services

# 4. Install pluto — scans YAML for deprecated Kubernetes APIs
helm plugin install https://github.com/FairwindsOps/pluto
pluto detect-files -d ./k8s-manifests/ --target-versions k8s=v1.30.0

# 5. Check PodDisruptionBudgets — are they configured on all critical apps?
kubectl get pdb -A

# 6. Backup cluster with Velero before any upgrade
velero backup create pre-upgrade-backup-$(date +%Y%m%d)
Upgrade Control Plane (AWS Managed)
BASHupgrade-control-plane.sh
# Upgrade control plane — AWS handles this with zero downtime
# This upgrades: etcd, API server, controller-manager, scheduler
aws eks update-cluster-version \
  --name my-cluster \
  --kubernetes-version 1.29   # go one version at a time: 1.28 → 1.29

# Wait for upgrade to complete (typically 10-20 minutes)
aws eks wait cluster-active --name my-cluster

# Verify control plane version updated
aws eks describe-cluster --name my-cluster \
  --query 'cluster.version'

# Update kubeconfig to use new API server
aws eks update-kubeconfig --name my-cluster --region ap-south-1

# Update managed addons (must upgrade AFTER control plane)
# Order matters: vpc-cni FIRST, then coredns, then kube-proxy
aws eks update-addon --cluster-name my-cluster --addon-name vpc-cni
aws eks update-addon --cluster-name my-cluster --addon-name coredns
aws eks update-addon --cluster-name my-cluster --addon-name kube-proxy
Blue/Green Node Group Upgrade
BASHbluegreen-node-upgrade.sh
# Strategy: Create NEW node group with v1.29, migrate workloads, delete old

# Step 1: Create Green node group (v1.29 nodes)
eksctl create nodegroup \
  --cluster my-cluster \
  --name ng-v129-green \
  --node-type m5.xlarge \
  --nodes 5 \
  --kubernetes-version 1.29

# Step 2: Taint old (Blue) nodes — new pods won't schedule there
for node in $(kubectl get nodes -l eks.amazonaws.com/nodegroup=ng-v128-blue -o name); do
  kubectl taint node $node node-lifecycle=deprecated:NoSchedule
done

# Step 3: Cordon old nodes (mark unschedulable)
kubectl cordon -l eks.amazonaws.com/nodegroup=ng-v128-blue

# Step 4: Drain old nodes one by one (respects PodDisruptionBudgets!)
for node in $(kubectl get nodes -l eks.amazonaws.com/nodegroup=ng-v128-blue -o name); do
  kubectl drain $node \
    --ignore-daemonsets \        # DaemonSets can't be moved, skip them
    --delete-emptydir-data \    # remove pods using ephemeral emptyDir volumes
    --timeout=300s \             # wait max 5 minutes per node
    --grace-period=60            # give pods 60s to shutdown gracefully
  echo "Drained $node — sleeping 30s before next node"
  sleep 30                        # buffer between nodes
done

# Step 5: Delete old Blue node group
eksctl delete nodegroup --cluster my-cluster --name ng-v128-blue
CommandWhy it matters
kubectl taint + NoSchedulePrevents any new pods from being assigned to old nodes — new rollouts go to Green nodes automatically
kubectl cordonMarks node as unschedulable — existing pods stay running, new pods cannot land there
kubectl drain --ignore-daemonsetsSafely evicts all evictable pods. DaemonSets (like Datadog, Fluentd) are excluded — they'll be removed with the node
--grace-period=60Gives each pod 60 seconds to handle SIGTERM, close connections, finish in-flight requests before SIGKILL

The Story
The Breach: A cryptocurrency exchange was compromised through a Kubernetes cluster. An attacker found a publicly exposed Kubernetes Dashboard, exploited a misconfigured RBAC role, and within 10 minutes was running cryptominer containers. Damage: $6M stolen.

Defence in Depth: Security isn't one thing — it's layers. Write Custom Falco Rules
YAMLcustom-falco-rules.yaml
# custom-rules.yaml — add to Falco Helm values
- rule: Shell Running in Container
  desc: Alert when someone shells into a running container (post-exploitation)
  condition: |
    spawned_process           # a new process was created
    and container             # inside a container
    and proc.name in (bash, sh, dash, zsh, fish)  # is a shell
    and not proc.pname in (runc, containerd-shim)  # not launched by container runtime
  output: "Shell opened in container (user=%user.name container=%container.name image=%container.image.repository)"
  priority: WARNING
  tags: [container, shell, mitre_execution]

- rule: Sensitive File Read
  desc: Detect reads of sensitive files like /etc/shadow or /etc/passwd
  condition: |
    open_read
    and fd.name in (/etc/shadow, /etc/passwd, /etc/sudoers, /root/.ssh/authorized_keys)
    and container
  output: "Sensitive file read (file=%fd.name container=%container.name)"
  priority: CRITICAL

- rule: Crypto Mining Detected
  desc: Container connecting to known crypto mining pools
  condition: |
    outbound
    and fd.sip.name in (crypto_mining_ip_set)  # Falco maintains lists of known bad IPs
    and container
  output: "Crypto miner connecting out (container=%container.name dest=%fd.sip)"
  priority: CRITICAL
