Why OpenShift Virtualization? —
The VMware Exodus

Before you write a single line of Ansible for OCP-V, you need to understand WHY a company would move its virtual machines onto a Kubernetes platform in the first place. Once the business reason is clear in your head, every technical decision after this will make sense on its own.

KubeVirtOCP-VVirtualMachine CRDVMware migration
📖 The Story So Far

Puneeth, sit with this scene for a moment. It is a Monday morning at TechNova. The infrastructure manager walks into the stand-up holding a printed quotation from the VMware renewal team, and her face already tells you the number is bad. Since Broadcom took over VMware, the licensing model changed from "per CPU socket" to "per core, sold only in large bundles" — and TechNova's three-year renewal quote has jumped from eighteen lakh rupees a year to almost fifty lakh. Nobody budgeted for this. The CIO's question in that meeting is simple and blunt: "We already run OpenShift for our containers. Can our existing OpenShift clusters also run our four hundred virtual machines, so we stop paying VMware altogether?" That single question is the reason OpenShift Virtualization exists, and it is the reason companies across India — banks, telecom players, insurance firms — are hiring engineers exactly like you who can automate this migration.

🧠 Concept, Explained Slowly

Here is the idea in the simplest words possible. Normally, a Kubernetes cluster only runs containers — small, lightweight processes that share the operating system kernel of the node. A virtual machine is a completely different thing — it is a full, independent operating system with its own kernel, running on top of a hypervisor like VMware ESXi or KVM. For years, these two worlds — containers and VMs — lived on separate platforms, managed by separate teams, with separate tools.

OpenShift Virtualization changes that. It is built on an open-source project called KubeVirt, and what KubeVirt does is genuinely clever — it takes a virtual machine and wraps it inside a Kubernetes Pod. Inside that pod runs a process called virt-launcher, and inside virt-launcher runs the actual QEMU/KVM hypervisor process that boots your Windows Server or RHEL virtual machine. From Kubernetes' point of view, it just sees a pod. From your point of view as an engineer, you now manage a virtual machine using the exact same tool — oc or kubectl — and the exact same automation language — Ansible — that you already use for containers. One cluster, one control plane, one set of skills for both worlds. That is the entire business case in one sentence: stop paying for two platforms when one will do.

🛠️ Hands-On — A First Look, No Deep Dive Yet

🎯 Interview Questions — Chapter 21 (Practice speaking these out loud)
Q1: What is OpenShift Virtualization, in your own words?
I'd say something like — "OpenShift Virtualization, or OCP-V, is a feature built on top of OpenShift that lets you run traditional virtual machines, like a Windows Server or a RHEL box, directly on the same Kubernetes cluster where you're already running your containers. It's built using an open-source project called KubeVirt, which basically wraps the VM inside a pod. Q2: Why are companies moving away from VMware right now?
I'd answer — "Mainly cost. That's the main driver, alongside wanting one platform and one team instead of two."
Q3: How does a VM actually "run" inside a Kubernetes pod?
I'd explain it like — "Every VM gets its own pod, and inside that pod there's a process called virt-launcher. Virt-launcher is the one that actually starts the real hypervisor process, QEMU with KVM, and that's what boots the guest operating system. So Kubernetes just sees a normal pod from the scheduling and networking side, but inside that pod is a full virtual machine running its own kernel. That's the trick that makes it possible to manage VMs with the same tools as containers."

OCP-V Architecture —
What's Actually Running Under the Hood

Your team lead tells you plainly — "I will not let you write automation for something you cannot draw on a whiteboard." So before Chapter 23 takes you into AWS and Azure, slow down here and learn exactly what pieces make up OpenShift Virtualization.

virt-operatorvirt-launcherVMICDIHyperConverged
📖 The Story So Far

Puneeth asks his lead a fair question — "If I can just run oc apply on a YAML file to create a VM, why do I need to know what's happening underneath?" His lead's answer is the same answer any good senior engineer gives — "Because the day it breaks at 2 AM, and it will, the on-call engineer who understands the architecture fixes it in ten minutes, and the one who doesn't spends three hours guessing." That is reason enough to slow down here.

🧠 Concept, Explained Slowly — The Cast of Characters

Think of OCP-V as a small team of specialist components, each with one clear job, all installed together as one package called the HyperConverged Operator. Let's meet them one at a time, slowly:

virt-operator is the "manager" — it watches over the whole OCP-V installation and makes sure every other component below is deployed and healthy. If a component crashes, virt-operator notices and fixes it.

virt-api is the "reception desk" — every time you run oc create -f myvm.yaml, your request first passes through virt-api, which validates the VM definition before accepting it.

virt-controller is the "decision maker" — once a VirtualMachine object is accepted, virt-controller decides it's time to actually create a VirtualMachineInstance (the running copy) and asks Kubernetes to schedule a pod for it.

virt-handler runs as a DaemonSet, meaning one copy on every single worker node — it is the "local supervisor" that talks directly to the actual QEMU/KVM process running on that node and reports its real status back up.

virt-launcher is the pod itself, one per running VM — this is the container that holds the real QEMU process, the actual hypervisor doing the work of running your guest operating system.

Finally, CDI — the Containerized Data Importer — is the component in charge of getting a disk image (a qcow2 or raw file) INTO the cluster's storage so a VM can boot from it. You will work with CDI heavily in Chapter 26.

🛠️ Hands-On — Reading The Cluster Like An Architect
terminal — inspecting each layer
# See the control-plane components (the operator's own pods) — these run once per cluster, not per VM.
oc get pods -n openshift-cnv
# You will see pods named virt-operator-xxxx, virt-api-xxxx, virt-controller-xxxx
# and one virt-handler-xxxx pod PER WORKER NODE (because it's a DaemonSet).

# Now look at the VM's desired state object:
oc get vm my-rhel-vm -n technova-vms -o yaml
# Notice: this object exists even when the VM is switched OFF.
# It's the "definition", like a Deployment manifest — it doesn't disappear when the app stops.

# Now look at the running instance — this only exists while the VM is powered on:
oc get vmi my-rhel-vm -n technova-vms
# If the VM is off, this command returns "No resources found" — that's expected and normal.

# Finally, find the actual pod running the hypervisor for this one VM:
oc get pods -n technova-vms -l kubevirt.io/domain=my-rhel-vm
# The pod name will look like: virt-launcher-my-rhel-vm-xxxxx
# This is the real container holding the QEMU process for your VM.

VM vs VMI — The Confusion Every Beginner Has

ObjectWhat It Really Means
VirtualMachine (vm)The desired state. Exists whether the VM is running or stopped. This is what you save in Git and apply with Ansible. Comparable to a Deployment in plain Kubernetes.
VirtualMachineInstance (vmi)The actual running instance. Created automatically by virt-controller only when the VM is switched on. Comparable to a Pod created by a Deployment. You never create this directly.
⚠️ A Trap Beginners Fall Into

Do not try to edit a VMI directly to change VM settings like CPU or memory — your edit will simply be overwritten or ignored, because virt-controller treats the VirtualMachine object as the single source of truth. Always change the VirtualMachine spec, then, if the change requires it, restart the VM so a fresh VMI is generated from the updated definition.

🎯 Interview Questions — Chapter 22
Q1: What is the difference between a VirtualMachine and a VirtualMachineInstance in OCP-V?
I'd say — "VirtualMachine is the desired state, it's what you define in YAML and it stays there even when the VM is powered off, kind of like how a Deployment definition stays even if you scale it to zero. VirtualMachineInstance is the actual running copy, it only exists while the VM is switched on, and it gets created automatically by virt-controller. So VM is 'what I want', VMI is 'what's actually running right now'."
Q2: What is virt-launcher and why does it matter?
I'd explain — "virt-launcher is the actual pod that gets created for every running VM. Inside that pod is the real QEMU process with KVM, and that's what's actually executing the guest operating system. So when people say a VM 'runs inside a pod', virt-launcher is literally that pod. If you ever need to check resource usage or troubleshoot a specific VM at the pod level, you're looking for its virt-launcher pod."
Q3: What does CDI do in OpenShift Virtualization?
I'd say — "CDI stands for Containerized Data Importer, and its job is to get disk images into the cluster so VMs can actually boot from them. So if I have a golden RHEL image sitting in an S3 bucket or an HTTP server, CDI is the component that pulls it in, converts it if needed, and stores it as a disk that a VM can attach to. I'll be using this heavily when I talk about golden images in Chapter 26."

ROSA —
Building The Foundation On AWS

OCP-V cannot exist without an OpenShift cluster underneath it, and since TechNova already lives on AWS, the natural choice is ROSA — Red Hat OpenShift Service on AWS. In this chapter you build that foundation, and you build it the Ansible way, not the click-in-console way.

rosa cliSTSamazon.aws collectionVPC
📖 The Story So Far

TechNova's cloud architect calls Puneeth into a planning meeting. "We're on AWS already, our billing, our security team, our networking — everything is set up for AWS. I don't want a brand new platform to manage. I want OpenShift, but I want AWS and Red Hat to jointly run the control plane for us, so my small team isn't stuck patching master nodes at midnight." That request has a name — it is called ROSA, Red Hat OpenShift Service on AWS, and it is a managed service, meaning AWS and Red Hat share the operational burden of running the cluster's control plane, while TechNova only manages what runs on top — which, from Chapter 25 onward, will be OCP-V and the virtual machines living on it.

🧠 Concept, Explained Slowly

Two ideas matter before you touch any Ansible code. First, ROSA needs a VPC — a Virtual Private Cloud — with proper subnets, because every OpenShift node is really just an EC2 instance underneath, and EC2 instances need network space to live in. Second, ROSA does NOT want you to hand it a static AWS access key and secret key sitting in a config file somewhere, because a leaked static key is a leaked key forever, until someone manually rotates it. Instead, ROSA uses STS — AWS Security Token Service. With STS, instead of one all-powerful key, you create a small set of narrowly-scoped IAM roles ahead of time — an "account-wide" role and per-operator "operator roles" — and AWS itself issues short-lived, automatically-expiring credentials to each OpenShift component only when it actually needs them. This is far safer, and it is also exactly what most interviewers expect you to explain confidently.

🛠️ Hands-On — Ansible Playbook: Preparing The AWS Foundation

Here is a real playbook TechNova uses. Read every line slowly — I have written a comment above almost every task explaining not just WHAT it does, but WHY it's there.

rosa_vpc_setup.yml
- name: Prepare AWS networking foundation for a ROSA cluster
  hosts: localhost
  connection: local
  # connection: local — this playbook doesn't SSH anywhere, it only talks to the AWS API,
  # so we run every task directly from the Ansible control node itself.
  gather_facts: false

  vars:
    aws_region: ap-south-1
    # ap-south-1 = Mumbai region — chosen because TechNova's users are mostly in India,
    # and keeping the cluster close to users reduces latency.
    vpc_cidr: "10.20.0.0/16"
    cluster_name: technova-ocpv-prod

  tasks:
    - name: Create the VPC that will hold the ROSA cluster
      amazon.aws.ec2_vpc_net:
        name: "{{ cluster_name }}-vpc"
        cidr_block: "{{ vpc_cidr }}"
        region: "{{ aws_region }}"
        tags:
          Project: "OCP-V-Migration"
      register: vpc_result
      # register saves the output (including the new VPC's ID) into vpc_result,
      # so later tasks can reference vpc_result.vpc.id instead of us hardcoding it.

    - name: Create two private subnets across two Availability Zones for high availability
      amazon.aws.ec2_vpc_subnet:
        vpc_id: "{{ vpc_result.vpc.id }}"
        cidr: "{{ item.cidr }}"
        az: "{{ item.az }}"
        region: "{{ aws_region }}"
        tags:
          "kubernetes.io/role/internal-elb": "1"
          # This specific tag tells OpenShift's internal load balancers which subnets they're allowed to use.
          # Miss this tag and cluster creation will fail with a confusing networking error later.
      loop:
        - { cidr: "10.20.1.0/24", az: "ap-south-1a" }
        - { cidr: "10.20.2.0/24", az: "ap-south-1b" }
      # Two AZs, not one — if Mumbai's "1a" zone has an outage, "1b" keeps the cluster alive.
      register: subnet_result

    - name: Create the account-wide IAM roles that STS will hand out short-lived credentials from
      ansible.builtin.shell: |
        rosa create account-roles --mode auto --yes --region {{ aws_region }}
      # We drop to a plain shell task here because Red Hat's own "rosa" CLI does not (yet) have
      # a dedicated Ansible module — this is completely normal and expected in real-world playbooks.
      # --mode auto means rosa will create the IAM roles itself instead of just printing the AWS CLI commands.
      register: account_roles_out
      changed_when: "'Created' in account_roles_out.stdout"
      # changed_when here means: only report "changed" if new roles were actually created.
      # If the roles already exist from a previous run, rosa says so and this task correctly shows "ok".
🛠️ Hands-On — Creating The Cluster And Waiting For It To Be Ready
rosa_cluster_create.yml
- name: Create the ROSA cluster and wait until it is fully ready
  ansible.builtin.shell: |
    rosa create cluster --cluster-name technova-ocpv-prod \
      --sts --mode auto --yes \
      --region ap-south-1 \
      --machine-cidr 10.20.0.0/16 \
      --compute-nodes 3
  # --sts tells rosa to use the safer short-lived-credential model we discussed above.
  # --compute-nodes 3 gives us three worker nodes — enough headroom for OCP-V's own operator pods
  # PLUS a handful of virtual machines, without starving the cluster of CPU and memory.
  register: cluster_create_out

- name: Poll cluster status every 60 seconds until it reports "ready"
  ansible.builtin.shell: rosa describe cluster --cluster technova-ocpv-prod -o json
  register: cluster_status
  until: (cluster_status.stdout | from_json).state == "ready"
  # until + register together create a retry loop — Ansible keeps re-running this task
  # and checking the condition after "until:" until it becomes true.
  retries: 40
  delay: 60
  # 40 retries × 60 seconds = up to 40 minutes of waiting — ROSA cluster creation genuinely
  # takes 35-45 minutes because AWS is provisioning EC2 instances, load balancers, and DNS records.
  # A junior engineer who doesn't know this often panics and cancels the playbook — don't be that engineer.
💡 Tip — STS vs Static IAM User Keys

If an interviewer asks "why not just use an IAM access key", your answer should be: static keys don't expire on their own, so if one leaks — in a Git commit, a log file, a Slack message — it stays valid until someone notices and manually revokes it. STS-issued credentials expire automatically, often within an hour, which shrinks the damage window enormously even if something does leak.

🎯 Interview Questions — Chapter 23
Q1: What is ROSA and why would a company choose it over self-managed OpenShift?
I'd say — "ROSA is Red Hat OpenShift Service on AWS, it's a jointly managed offering where AWS and Red Hat run the control plane for you. A company picks it when they don't want their own team patching and upgrading master nodes — they'd rather focus their engineers on what runs ON the cluster, like our OCP-V virtual machines, and let the platform vendor handle the heavy lifting underneath."
Q2: Why does ROSA use STS instead of normal IAM access keys?
I'd explain — "STS gives out short-lived, temporary credentials instead of one permanent key. So instead of a single access key that could leak and stay valid forever, each OpenShift component gets scoped, expiring credentials through IAM roles set up ahead of time. It's just a much safer security model, and it's actually the recommended approach from AWS themselves, not just a ROSA thing."
Q3: In your Ansible playbook, why did you use a shell task instead of a proper module for cluster creation?
I'd answer honestly — "Because Red Hat's rosa CLI doesn't ship a native Ansible module, so wrapping the CLI in a shell task is the standard, accepted approach. What I do make sure of is that the task is idempotent-aware — I use changed_when and register so the playbook still reports state honestly, and I use until with retries to wait for the actual cluster-ready condition instead of just assuming a fixed sleep time is enough."

Building The Same Foundation On Azure

TechNova's European division standardized on Azure years ago, for reasons that have nothing to do with technology — mostly procurement contracts and data residency rules. The good news for you: the OCP-V skill you learned on AWS carries over almost completely. Only the foundation underneath changes.

📖 The Story So Far

Puneeth gets pulled into a call with TechNova's Frankfurt office. They ask the same question the AWS team asked in Chapter 23 — "we want OpenShift, jointly managed, so our small team isn't stuck patching master nodes" — but this time the answer starts with Azure instead of AWS, because Frankfurt's entire environment, billing, and compliance approvals already live there. The Azure equivalent of ROSA is called ARO — Azure Red Hat OpenShift, and it is worth genuinely appreciating this moment: once your cluster exists, everything you learned about OCP-V in Chapter 22 — VirtualMachine objects, virt-launcher pods, CDI — works completely unchanged. That is the real power of Kubernetes-based platforms — your automation skill is portable across clouds, even when the underlying infrastructure plumbing is not.

🧠 Concept, Explained Slowly

On Azure, instead of an IAM role, identity is handled by something called a Service Principal — think of it as an application's own "user account" inside Azure Active Directory, given just enough permission to create the resources ARO needs, and nothing more. And instead of a VPC with subnets, Azure calls its network container a VNet (Virtual Network), which also needs to be pre-created with the right address space before ARO can use it. The naming is different, the concepts underneath are nearly identical to what you just did with ROSA — that pattern recognition, by the way, is exactly what senior engineers get paid for.

🛠️ Hands-On — Ansible Playbook: Preparing The Azure Foundation
aro_vnet_setup.yml
- name: Prepare Azure networking foundation for an ARO cluster
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    resource_group: technova-ocpv-rg
    location: centralindia
    # centralindia = Azure's Pune region — again, chosen to stay close to Indian users.
    vnet_cidr: "10.30.0.0/22"
    # ARO requires a fairly specific minimum address space — /22 gives enough room
    # for both the "master" subnet and the "worker" subnet ARO needs, with room to grow.

  tasks:
    - name: Create the resource group — Azure's container for related resources
      azure.azcollection.azure_rm_resourcegroup:
        name: "{{ resource_group }}"
        location: "{{ location }}"
      # Every single Azure resource must live inside a resource group — think of it as a labeled
      # folder that groups the VNet, the cluster, and everything else together for billing and cleanup.

    - name: Create the VNet with two subnets — one for masters, one for workers
      azure.azcollection.azure_rm_virtualnetwork:
        resource_group: "{{ resource_group }}"
        name: "{{ resource_group }}-vnet"
        address_prefixes: "{{ vnet_cidr }}"
        subnets:
          - name: master-subnet
            address_prefix_cidr: "10.30.0.0/23"
          - name: worker-subnet
            address_prefix_cidr: "10.30.2.0/23"
      # ARO insists on this master/worker subnet split, unlike ROSA which can share subnets.
      # This is exactly the kind of small difference an interviewer loves to test you on.

    - name: Create the ARO cluster using the az CLI, wrapped in a shell task
      ansible.builtin.shell: |
        az aro create \
          --resource-group {{ resource_group }} \
          --name technova-ocpv-eu \
          --vnet {{ resource_group }}-vnet \
          --master-subnet master-subnet \
          --worker-subnet worker-subnet
      # Just like with rosa create cluster, there is no dedicated Ansible module for "az aro create",
      # so the shell task wrapping the official CLI remains the correct, honest approach.
      register: aro_create_out
      async: 3600
      poll: 0
      # async + poll: 0 = "fire this off and don't wait here" — ARO cluster creation can take
      # even longer than ROSA, often 40-50 minutes, so we let it run in the background
      # and check on it separately with async_status in a later task, rather than blocking this playbook.

Installing OpenShift Virtualization —
The Ansible Way, Not The Console Way

Your ROSA or ARO cluster is alive. Now comes the step that actually turns it into an OCP-V platform — installing the operator itself. TechNova's rule is simple: nothing gets clicked in the console that can't be reproduced by a playbook, because a click is not repeatable and a playbook is.

📖 The Story So Far

Puneeth's manager gives him a very specific instruction that will define how he works from now on — "If someone can walk into the OpenShift console, click a few buttons, and install OCP-V by hand, that's fine for a five-minute demo. But we are running production clusters for four hundred VMs across two clouds. If that install has to happen five more times — disaster recovery cluster, staging cluster, a second region — nobody remembers exactly which buttons they clicked eight months ago. A playbook remembers. Write the playbook first, before you ever touch the console."

🧠 Concept, Explained Slowly — OLM in Plain Words

OpenShift installs most add-on software, including OCP-V, through a system called OLM — Operator Lifecycle Manager. Three objects work together, and understanding their order genuinely matters. First, a Namespace — a dedicated project, always called openshift-cnv for OCP-V, that acts as the "home" for everything that follows. Second, an OperatorGroup — this tells OLM which namespace(s) the operator is allowed to watch and manage; without it, the operator has no defined scope and will not install correctly. Third, a Subscription — this is you saying "I want the HyperConverged Operator, from this update channel, please install it and keep it updated automatically." OLM reads the Subscription and, behind the scenes, creates a CSV — Cluster Service Version, which is the actual record of the operator being installed and its health status.

Once the operator itself is running, it still hasn't created any VM-capable infrastructure yet — that needs one more object, a custom resource called HyperConverged. Applying a HyperConverged object is the single action that tells the now-running operator, "go ahead, deploy KubeVirt, deploy CDI, deploy the network add-ons, and make this cluster VM-capable." Skip this step and you'll have an operator sitting there doing nothing.

🛠️ Hands-On — The Full Installation Playbook

This uses the kubernetes.core collection's k8s module, which is the standard, cloud-agnostic way to apply any Kubernetes or OpenShift object from Ansible — it works identically whether your cluster is ROSA, ARO, or completely on-premise.

install_ocpv.yml
- name: Install OpenShift Virtualization end to end
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Step 1 — Create the openshift-cnv namespace
      kubernetes.core.k8s:
        state: present
        # state: present means "make sure this exists" — if it already exists, nothing changes,
        # which is exactly the idempotence you want when re-running this playbook safely.
        definition:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: openshift-cnv

    - name: Step 2 — Create the OperatorGroup so OLM knows the install scope
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: operators.coreos.com/v1
          kind: OperatorGroup
          metadata:
            name: kubevirt-hyperconverged-group
            namespace: openshift-cnv
          spec:
            targetNamespaces:
              - openshift-cnv
            # targetNamespaces limited to just openshift-cnv itself — this is the recommended,
            # narrowest possible scope for the HyperConverged operator.

    - name: Step 3 — Subscribe to the HyperConverged Operator (this actually triggers the install)
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: operators.coreos.com/v1alpha1
          kind: Subscription
          metadata:
            name: hco-operatorhub
            namespace: openshift-cnv
          spec:
            channel: stable
            # "stable" channel — always prefer this over a fast/preview channel in production.
            name: kubevirt-hyperconverged
            source: redhat-operators
            sourceNamespace: openshift-marketplace
            installPlanApproval: Automatic
            # Automatic means new versions within the stable channel install without manual approval.
            # TechNova chose this after weighing convenience against control — some companies
            # prefer "Manual" here so a human reviews every operator upgrade first.

    - name: Step 4 — Wait until the operator's CSV reports Succeeded before moving on
      kubernetes.core.k8s_info:
        api_version: operators.coreos.com/v1alpha1
        kind: ClusterServiceVersion
        namespace: openshift-cnv
      register: csv_info
      until: csv_info.resources | selectattr('status.phase', 'defined') | selectattr('status.phase', 'equalto', 'Succeeded') | list | length > 0
      retries: 30
      delay: 20
      # k8s_info is the READ-ONLY counterpart to the k8s module — use it whenever you're just checking
      # status rather than creating or changing something. This loop waits up to 10 minutes.

    - name: Step 5 — Apply the HyperConverged custom resource, the switch that turns everything on
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: hco.kubevirt.io/v1beta1
          kind: HyperConverged
          metadata:
            name: kubevirt-hyperconverged
            namespace: openshift-cnv
          spec: {}
          # An empty spec is intentional and correct here — it tells the operator to deploy
          # KubeVirt, CDI, and the network add-ons using their sensible, built-in defaults.
        wait: true
        wait_condition:
          type: Available
          status: "True"
        wait_timeout: 600
        # wait: true with wait_condition tells the k8s module itself to block and poll
        # until the HyperConverged resource's "Available" condition becomes True —
        # a cleaner built-in alternative to writing our own until-loop for this particular object.
⚠️ A Real Failure TechNova Hit In Production

The very first time this playbook ran against the ARO cluster from Chapter 24, Step 3 failed silently — the Subscription was created, but no CSV ever appeared. The cause: ARO's OpenShift version was one minor release behind what the "stable" channel of that operator version required. The fix was simple once diagnosed — check oc get packagemanifest kubevirt-hyperconverged -o yaml BEFORE writing the Subscription, to confirm the channel name and supported OpenShift version actually match your cluster.

Q1: Walk me through how OLM installs an operator like OCP-V.
I'd explain it step by step — "First you need a namespace for the operator to live in, that's openshift-cnv for OCP-V. Then an OperatorGroup, which tells OLM what scope the operator should watch. Golden Images & DataVolumes —
Stamping Out VMs By The Dozen

The platform is ready. Now TechNova's application team asks for something very ordinary and very important — fifty identical RHEL virtual machines for a new project, all created the same way, all customized automatically on first boot. This is where Ansible earns its keep.

DataVolumeCDI importcloud-initgolden image
📖 The Story So Far

A project manager messages Puneeth — "We need fifty RHEL VMs for the new billing microservice team, by Friday, each one with our company's hardened base image, our monitoring agent pre-installed, and its own hostname." Puneeth's old VMware instinct would be to clone a template fifty times by hand in vCenter, an entire day of clicking. His new instinct, the one this course is building in him, is different — import the golden image exactly ONCE, then let one Ansible playbook with a loop stamp out all fifty VMs, each one customized automatically the moment it boots.

🧠 Concept, Explained Slowly

A DataVolume is the CDI object that actually fetches a disk image — from an HTTP URL, an S3 bucket, a container registry, or a cloned existing disk — and turns it into storage a VM can boot from. Think of it as the "download and prepare the golden image" step, done exactly once. After that, instead of re-downloading the same image fifty times, each new VM uses a dataVolumeTemplate inside its own spec, which tells CDI "clone from that golden image", a much faster operation than a fresh import because it reuses storage-level cloning.

The second half of the puzzle is cloud-init — a well-known, cloud-native standard (you'll recognize it if you've ever launched an AWS EC2 instance with "user data") that runs a small script the very first time a VM boots, before anyone logs in. This is how each of those fifty VMs gets its own unique hostname, its own SSH key, and its own set of pre-installed packages, all from the same golden image.

🛠️ Hands-On — Step 1: Import The Golden Image, Once
import_golden_image.yml
- name: Import TechNova's hardened RHEL 9 golden image from S3, once
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: rhel9-golden-image
        namespace: technova-vms
      spec:
        source:
          http:
            url: "https://technova-images.s3.ap-south-1.amazonaws.com/rhel9-hardened.qcow2"
            # This qcow2 file was baked once by the security team with all compliance
            # hardening already applied — that's why we import it rather than a plain public RHEL image.
        pvc:
          accessModes:
            - ReadWriteMany
          # ReadWriteMany (RWX), not ReadWriteOnce — because this golden image will be READ
          # by many clone operations at once as we stamp out fifty VMs from it. You'll see this
          # access-mode decision matter again in Chapter 29 when we talk about storage classes.
          resources:
            requests:
              storage: 20Gi
    wait: true
    wait_condition:
      type: Ready
      status: "True"
    wait_timeout: 900
    # Importing a 20Gi image over the network genuinely takes time — 900 seconds (15 minutes)
    # gives enough headroom without letting a stuck import hang the playbook forever.

🎯 Interview Questions — Chapter 26
Q1: What is a DataVolume and why do you import a golden image only once?
I'd say — "A DataVolume is CDI's way of pulling in a disk image and turning it into usable VM storage. I import the golden image just once because after that, every new VM can clone from it at the storage layer, which is much faster than downloading the same twenty gigabyte image fifty separate times. VM Lifecycle Automation —
Start, Stop, and Live Migration

Creating a VM is only the beginning of its life. Now TechNova needs to save money by shutting down non-production VMs overnight, and needs to move running VMs off a node before that node goes down for maintenance — without anyone noticing.

running: falseVMIMlive migrationnode drain
📖 The Story So Far

Two separate requests land on Puneeth's desk in the same week. The finance team notices that TechNova's forty development and test VMs run twenty-four hours a day even though nobody touches them outside office hours, and asks — can these switch off automatically every night and back on every morning, to cut the AWS and Azure bill? Separately, the platform team needs to patch the underlying worker nodes for a security update, which means every VM currently running on those nodes needs to move somewhere else first, ideally without the people using those VMs even noticing a blip. Two very different problems. Both solved by automation you write once and reuse forever.

🧠 Concept, Explained Slowly

Starting and stopping a VM is the simpler of the two ideas — remember from Chapter 26 that spec.running on the VirtualMachine object controls this. Flip it to false, and virt-controller gracefully shuts down the VMI and removes the virt-launcher pod, while the VirtualMachine definition itself stays safely intact, ready to be switched back to true whenever needed.

Live migration is a more interesting idea, and it is the OCP-V answer to what VMware users know as "vMotion". A VirtualMachineInstanceMigration (VMIM) object, when created, tells the platform "move this specific running VM to a different node, without powering it off." Behind the scenes, OCP-V copies the VM's memory state to the new node while it keeps running on the old one, and only switches over at the very last moment, once the copy is essentially complete — the result, done correctly, is an outage measured in milliseconds, not minutes. But — and this "but" matters a great deal in interviews — live migration only works if the VM's disk lives on storage that BOTH the old node and the new node can access at the same time. That means the disk's storage class must support ReadWriteMany (RWX). Get this wrong, using ReadWriteOnce storage, and instead of a smooth live migration, the platform is forced to simply evict and restart the VM elsewhere — a real outage, not a graceful move.

🛠️ Hands-On — Automatically Shutting Down Non-Prod VMs Overnight
shutdown_dev_vms.yml
- name: Power off every VM tagged as environment=dev
  kubernetes.core.k8s_json_patch:

    kind: VirtualMachine
    name: "{{ item.metadata.name }}"
    namespace: technova-vms
    patch:
      - op: replace
        path: /spec/running
        value: false
        # k8s_json_patch changes ONE field surgically, without needing the VM's full definition —
        # ideal here, because we only want to touch spec.running and leave everything else untouched.
  loop: "{{ dev_vms.resources }}"
  # dev_vms was populated by an earlier k8s_info task filtering on label environment=dev —
  # this whole playbook is triggered every evening by an AWX schedule, the same AWX you set up in Phase 2.
🛠️ Hands-On — Live-Migrating A VM Off A Node Before Maintenance
live_migrate_vm.yml
- name: Trigger live migration for a specific VM, away from a node marked for maintenance
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: kubevirt.io/v1
      kind: VirtualMachineInstanceMigration
      metadata:
        name: "migrate-{{ vm_name }}-{{ ansible_date_time.epoch }}"
        # Each migration needs a unique name, so we append a timestamp — this is a common,
        # reusable Ansible pattern anytime you need a guaranteed-unique object name.
        namespace: technova-vms
      spec:
        vmiName: "{{ vm_name }}"
        # Just naming the target VMI is enough — creating this object is the entire "trigger".
        # OCP-V's scheduler picks a healthy destination node automatically.
  register: migration_obj

- name: Wait until the migration reports Succeeded before continuing the node drain
  kubernetes.core.k8s_info:
    api_version: kubevirt.io/v1
    kind: VirtualMachineInstanceMigration
    name: "{{ migration_obj.result.metadata.name }}"
    namespace: technova-vms
  register: migration_status
  until: migration_status.resources[0].status.phase == "Succeeded"
  retries: 20
  delay: 10
  # Only once every VM on the node has migrated Successfully do we let a following task
  # actually cordon and drain the node for the security patch — never before.

Any candidate can say "OCP-V supports live migration." A stronger candidate immediately adds "...but only if the underlying storage is RWX-capable — if it's RWO, the platform falls back to evicting and restarting the VM instead." Saying that one sentence unprompted in an interview signals real hands-on experience, not just reading about the feature.

🎯 Interview Questions — Chapter 27
Q1: How do you start and stop a VM in OCP-V using Ansible?
I'd say — "You just change the spec.running field on the VirtualMachine object — true to power it on, false to power it off. I usually do this with a JSON patch task in Ansible so I'm only touching that one field and not risking any accidental change to the rest of the VM definition. We use this for scheduled shutdowns of non-production VMs to save cost overnight."
Q2: What is live migration and what has to be true for it to work properly?
I'd explain — "Live migration moves a running VM from one node to another without powering it off, similar to VMware's vMotion. You trigger it by creating a VirtualMachineInstanceMigration object naming the target VM. But the important condition is that the VM's disk has to be on ReadWriteMany storage, so both the source and destination node can access it at the same time. If it's on ReadWriteOnce storage instead, OCP-V can't do a true live migration, it just evicts and restarts the VM, which does cause a brief outage."
Q3: How would you safely drain a node that has ten running VMs on it for maintenance?
I'd walk through it — "First I'd loop through the VMs on that node and trigger a live migration for each one, and importantly wait and confirm each migration actually reaches the Succeeded phase before moving to the next step. Networking OCP-V VMs —
Multus & Bridges

Most VMs are perfectly happy with a normal, NAT'd pod-style IP address. But some VMs — a legacy database, an appliance expecting a real network presence — need to sit directly on TechNova's actual corporate network, with a real routable IP. This chapter is about giving a VM that second kind of network access.

MultusNetworkAttachmentDefinitionmasqueradebridge
📖 The Story So Far

A database administrator raises a ticket that confuses Puneeth at first — "The Oracle VM we migrated needs to be reachable at 10.5.40.22, exactly that address, because forty other on-prem systems have that IP hardcoded in their connection strings. A NAT'd cluster-internal IP won't work for us." Puneeth's first instinct is that this must be impossible on Kubernetes-based infrastructure — until his lead explains that OCP-V, through a component called Multus, can absolutely give a VM a real, direct presence on an existing VLAN, exactly like plugging a physical server's network cable straight into that VLAN's switch.

🧠 Concept, Explained Slowly

By default, every VM gets what's called masquerade binding — its network traffic is NAT'd through the pod network, exactly the same as normal container traffic. This is simple, requires no extra setup, and is right for the vast majority of VMs — anything that just needs outbound internet access or to talk to other services inside the cluster.

Multus is a "meta" network plugin whose entire job is to let a pod (or in our case, a VM's virt-launcher pod) attach to MORE than one network interface. Using Multus, you first define a NetworkAttachmentDefinition (NAD) — a plain custom resource describing an actual physical or VLAN-tagged network already present on your nodes. Then, in the VM's own spec, you add a second interface using bridge binding, referencing that NAD. The result: the VM keeps its default pod-network interface for normal cluster traffic, AND gains a second interface sitting directly on the real corporate VLAN, with the specific IP the database team asked for.

🛠️ Hands-On — Attaching A VM Directly To The Corporate VLAN
vlan_attachment.yml
- name: Define the NetworkAttachmentDefinition for VLAN 40 (the DB team's network)
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: k8s.cni.cncf.io/v1
      kind: NetworkAttachmentDefinition
      metadata:
        name: vlan40-corporate
        namespace: technova-vms
      spec:
        config: '{
          "cniVersion": "0.4.0",
          "type": "bridge",
          "bridge": "br-vlan40",
          "vlan": 40
        }'
        # "type": "bridge" tells Multus to use the bridge CNI plugin.
        # "bridge": "br-vlan40" must match a bridge interface your network team already
        # configured on the worker nodes — Ansible doesn't create the physical bridge itself here,
        # that's typically done once via a NodeNetworkConfigurationPolicy, a separate one-time setup.

- name: Patch the Oracle VM to add the second, VLAN-attached interface
  kubernetes.core.k8s_json_patch:
    api_version: kubevirt.io/v1
    kind: VirtualMachine
    name: oracle-db-vm
    namespace: technova-vms
    patch:
      - op: add
        path: /spec/template/spec/networks/-
        value:
          name: corporate-net
          multus:
            networkName: vlan40-corporate
            # "/spec/template/spec/networks/-" — the trailing dash appends to the existing
            # networks list rather than overwriting it, so we don't lose the default pod network.
      - op: add
        path: /spec/template/spec/domain/devices/interfaces/-
        value:
          name: corporate-net
          bridge: {}
          # An empty "bridge: {}" here is what selects BRIDGE binding for this specific interface,
          # in contrast to the VM's primary interface, which stays on the default masquerade binding.
          # The VM's guest OS then configures the static IP 10.5.40.22 on this new interface via its own netplan/nmcli config.
💡 How To Expose A VM Without Multus At All

Not every "reachability" request needs the Multus route. If a VM just needs to be reachable from OUTSIDE the cluster, without needing that one exact hardcoded corporate IP, a plain Kubernetes Service (for internal or LoadBalancer access) or Route (for HTTP/HTTPS) pointed at the VM's pod works perfectly well, no VLAN attachment required. Reach for Multus only when the exact IP or direct VLAN presence genuinely matters, since it adds real operational complexity.

🎯 Interview Questions — Chapter 28
Q1: What is the difference between masquerade and bridge binding for an OCP-V VM's network interface?
I'd say — "Masquerade is the default — it's NAT'd through the pod network, same as regular container traffic, and it's what almost every VM uses. Bridge binding, set up through Multus, gives the VM a direct, real presence on an actual VLAN, with a real routable IP, similar to plugging a physical server straight into that network's switch. I'd only reach for bridge binding when a VM genuinely needs a specific external IP or has to talk directly to legacy on-prem systems."
Q2: What is Multus and what problem does it solve?
I'd explain — "Multus is a meta CNI plugin that lets a pod, or in our case a VM, attach to more than one network at once. Normally a pod gets exactly one network interface. With Multus, I can define a NetworkAttachmentDefinition describing an additional network, like a specific VLAN, and attach that as a second interface on the VM, while it keeps its default pod-network interface too."
Q3: If a VM just needs to be reachable from outside the cluster, do you always need Multus?
I'd answer — "No, not at all. If the requirement is simply 'other things outside the cluster need to reach this VM', a normal Kubernetes Service, maybe of type LoadBalancer, or a Route for web traffic, is usually enough and is much simpler to manage. I'd only bring in Multus and bridge binding when there's a hard requirement for one specific IP address or direct Layer 2 presence on an existing corporate VLAN, which is a much narrower, more specific need."

Storage Automation —
CDI, Snapshots & Choosing The Right Backend

Every good migration project eventually asks the same two questions — "how do we back these VMs up?" and "which cloud storage type do we actually pick?" Get the storage class wrong here, and features like live migration from Chapter 27 simply stop working, quietly, with no warning.

VolumeSnapshotRWXAWS EFS CSIAzure Files CSI
📖 The Story So Far

Two more requests, back to back, the same week. The compliance team asks for nightly backups of every production VM's disk, retained for thirty days, fully automated, no manual step allowed to be forgotten. Separately, a developer asks Puneeth for "just a quick copy" of a test VM's disk so she can experiment without risking the original — she needs it in minutes, not after a fresh multi-gigabyte import. Both problems point to the same OCP-V feature: VolumeSnapshots.

🧠 Concept, Explained Slowly

A VolumeSnapshot is a point-in-time copy of a PVC's data, taken at the storage layer, which means it is fast and space-efficient compared to copying the whole disk file by file. Once a snapshot exists, you can create a brand-new DataVolume that clones FROM that snapshot instead of from a live disk — this is exactly how the developer above gets her "quick copy" in minutes.

Now, the storage class question, and this is where real production mistakes happen. Recall from Chapter 27 that live migration absolutely requires ReadWriteMany (RWX) storage. On AWS, the default and most common block storage — EBS — only supports ReadWriteOnce (RWO)EFS CSI driver (Elastic File System). The exact same story repeats on Azure — Azure Managed Disks are RWO-only, while Azure Files supports RWX. This single decision, made once at the very start of a migration project, determines whether your VMs will ever be able to live-migrate.

    name: "{{ item.metadata.name }}"
    namespace: technova-vms
  loop: "{{ old_snapshots.resources }}"
  # old_snapshots is filtered by comparing each snapshot's creationTimestamp against "30 days ago" —
  # a backup policy that never expires old data is not a backup policy, it's a slowly growing storage bill.

clone_from_snapshot.yml
- name: Create a new DataVolume cloned from yesterday's snapshot, for safe experimentation
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: test-copy-disk
        namespace: technova-vms
      spec:
        source:
          snapshot:
            namespace: technova-vms
            name: "{{ snapshot_to_clone }}"
            # Cloning from a snapshot rather than "pvc" (like we did in Chapter 26) — the difference
            # is the source: {}  key, "snapshot" instead of "pvc". Everything else about DataVolumes stays the same.
        pvc:
          accessModes: [ReadWriteOnce]
          resources:
            requests:
              storage: 20Gi
    # The developer now attaches this new, independent disk to a fresh test VM — completely isolated
    # from the original production disk, ready in minutes instead of a fresh multi-gigabyte re-import.
🎯 Interview Questions — Chapter 29
Q1: Why does the storage class you pick affect whether live migration works?
I'd say — "Because live migration needs the VM's disk to be accessible from both the source and destination node at the same time, which means the storage has to support ReadWriteMany. Common block storage like AWS EBS or Azure Managed Disks are ReadWriteOnce only, so VMs on that storage can't be truly live-migrated, they'd just get evicted and restarted instead. To get real live migration, you need something like AWS EFS or Azure Files, which do support ReadWriteMany."
Q2: How would you design an automated backup strategy for OCP-V VMs?
I'd explain — "I'd use VolumeSnapshots, scheduled through an AWX job template running nightly, snapshotting each production VM's PVC with a date in the name. And just as important as taking the snapshots is cleaning up old ones — I'd have a second task that deletes anything past a defined retention window, say thirty days, so the backup strategy doesn't quietly become an ever-growing storage cost."
Q3: What's the difference between cloning a disk from a PVC versus from a snapshot?
I'd answer — "Cloning from a live PVC, like I did for the golden image in Chapter 26, copies the current state of a disk that's potentially still in use. Cloning from a snapshot instead gives you a stable, point-in-time copy, which is safer when you want a consistent copy for testing or backup restoration, without any risk of copying a disk mid-write. In the DataVolume spec, the only real difference is whether the source key says pvc or snapshot."

🛠️ Hands-On — The Role Structure
roles/vm_provision/tasks/main.yml
- name: Confirm the requested golden image exists before doing anything else
  kubernetes.core.k8s_info:
    api_version: cdi.kubevirt.io/v1beta1
    kind: DataVolume
    name: "{{ vm_os }}-golden-image"
    namespace: technova-vms
  register: golden_check
  failed_when: golden_check.resources | length == 0
  # failed_when here, from Ansible Phase 2 Chapter 11, gives the developer a clear, immediate
  # error in AWX if they typed an OS name that doesn't have a golden image — much better
  # than the playbook failing confusingly three steps later.

- name: Create the VM, cloned from the confirmed golden image
  kubernetes.core.k8s:
    state: present
    definition: "{{ lookup('template', 'vm.yaml.j2') }}"
    # This project graduates from inline YAML (used in earlier chapters for clarity) to a proper
    # Jinja2 template file — the standard, cleaner approach once a playbook becomes reusable across teams.
    wait: true
    wait_condition:
      type: Ready
      status: "True"
    wait_timeout: 300

- name: Fetch the running VM's assigned IP address
  kubernetes.core.k8s_info:
    api_version: kubevirt.io/v1
    kind: VirtualMachineInstance
    name: "{{ vm_name }}"
    namespace: technova-vms
  register: vmi_info
  until: vmi_info.resources[0].status.interfaces[0].ipAddress is defined
  retries: 15
  delay: 10
  # The IP takes a few seconds to appear after the VM reports Ready, since the guest OS itself
  # has to finish booting and report its address back — the until loop absorbs that timing gap gracefully.

- name: Post the finished VM's details straight to the requester's Slack channel
  community.general.slack:
    token: "{{ vault_slack_token }}"
    channel: "#{{ requester_slack_channel }}"
    msg: "✅ Your VM `{{ vm_name }}` ({{ vm_os }}, {{ vm_size }}) is ready at {{ vmi_info.resources[0].status.interfaces[0].ipAddress }}"
    # This is the exact moment the manager's original request comes true — a developer clicks
    # Launch in AWX, and five minutes later, with zero engineer involvement, gets a Slack message
    # with a working VM's IP address.

Production Readiness Checklist Before This Goes Live

  • Resource quotas set per namespace, so one careless developer requesting a 64-core VM cannot starve the whole cluster.
  • RBAC on the Job Template (from Phase 2's Tower RBAC chapter) — developers get Execute-only access, never edit or credential access.
  • Survey field validation in AWX restricting vm_size to a fixed dropdown, not free text, preventing invalid or oversized requests.
  • A backup schedule (Chapter 29) automatically covering every newly created VM without manual enrollment.
  • Monitoring alert on the AWX Job Template itself, so a failed provisioning run pages the platform team, not just the disappointed developer.
