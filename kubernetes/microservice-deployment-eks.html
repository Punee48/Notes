1. The Business Scenario — Why This Project Exists

ShopNow Retail started three years ago as a single Java monolith — one giant Spring Boot application doing everything: catalog, cart, orders, payments, notifications. It worked when the company was small. It stopped working the day the catalog team wanted to deploy a small change and had to wait four hours for the entire monolith's test suite to pass, then discovered their unrelated change had broken the payments module because everything shared one codebase and one deployment. Engineering leadership made the call: break the monolith into independently deployable microservices, and let each team choose the best language for their domain — the Payments team, mostly ex-banking engineers, wanted .NET; the Catalog team already had a Python data pipeline; the fast-moving Notifications team wanted Node.js; and the core Order Service, the most business-critical piece, stayed in Java Spring Boot where the strongest engineers already were.

Your manager Ramesh hands you the task: "Puneeth, these four teams are building their services independently. I need you to design how all four run together on one EKS cluster — each with its own Dockerfile, its own Deployment, its own scaling behavior, but talking to each other cleanly and going out through one front door."

This is the single most common real-world DevOps problem: not "how do I deploy one app," but "how do I run a polyglot fleet of independently-owned services on shared infrastructure without them stepping on each other." This is what "microservices platform engineer" actually means day to day, and it's a stronger interview story than a single-app deployment because it proves you can operate infrastructure that other teams build on top of.

Every service is independently built, independently deployed, and independently scaled — that independence is the entire point of the migration, and it is also exactly what makes the Kubernetes and CI/CD design in this document non-trivial: four different Dockerfiles, four different pipelines, but one shared platform.

Why does Notification Service have no Ingress route? It has nothing for a browser to call directly — it only reacts to SQS messages. Giving it a public endpoint anyway would be an unnecessary attack surface. This is a real distinction interviewers listen for: not every microservice needs to be internet-facing.

4. EKS Cluster Design

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: shopnow-cluster
  region: ap-south-1
  version: "1.29"

managedNodeGroups:
  - name: ng-general
    instanceType: m5.large
    desiredCapacity: 3
    minSize: 3
    maxSize: 10
    labels: { workload: general }

  - name: ng-payment-secure
    instanceType: m5.large
    desiredCapacity: 2
    minSize: 2
    maxSize: 4
    labels: { workload: payment-secure }
    taints:
      - key: "dedicated"
        value: "payment"
        effect: "NoSchedule"

Order, Catalog and Notification share the general node group. Payment Service, because it handles card data, gets its own tainted node group — the same taint pattern you'd use for environment isolation, applied here instead for compliance isolation: PCI-related workloads physically separated from everything else, a distinction worth naming explicitly if asked "have you worked with any compliance-driven infrastructure requirements."

5. VPC and Networking

One VPC (10.30.0.0/16), public subnets for the ALB across 3 AZs, private subnets for all EKS worker nodes, and a dedicated set of private subnets for the RDS instances reachable only from the app subnets on port 5432. The Payment Service's node group sits in the same private subnets as everyone else — the isolation for Payment is enforced by NetworkPolicy and Security Group, not a separate VPC, keeping the network design simple while the strict boundary still holds.

6. IAM Roles and IRSA

Each microservice gets its own IAM role via IRSA, scoped to only the AWS resources that specific service touches — this is the single biggest security lesson of a microservices platform: blast radius. If the Catalog Service's Python code has a vulnerability and gets compromised, its IAM role cannot read the Payment Gateway API key, because that permission was never granted to it in the first place.

eksctl create iamserviceaccount --cluster shopnow-cluster --namespace prod \
  --name order-service-sa \
  --attach-policy-arn arn:aws:iam::111122223333:policy/order-service-policy --approve

eksctl create iamserviceaccount --cluster shopnow-cluster --namespace prod \

7. Dockerizing Each Microservice

Four different languages means four different build strategies, all following the same principle: multi-stage builds so the final image ships only the compiled artifact, not the build toolchain — smaller image, smaller attack surface, faster pull time.

# order-service/Dockerfile (Java / Spring Boot)
FROM eclipse-temurin:17-jdk AS build
WORKDIR /app
COPY . .
RUN ./gradlew bootJar --no-daemon

FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=build /app/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

# catalog-service/Dockerfile (Python / FastAPI)
FROM python:3.11-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

FROM python:3.11-slim
WORKDIR /app
COPY --from=build /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

# notification-service/Dockerfile (Node.js / Express)
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

FROM node:20-alpine
WORKDIR /app
COPY --from=build /app/node_modules ./node_modules
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]

# payment-service/Dockerfile (.NET 8)
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8081
ENTRYPOINT ["dotnet", "PaymentService.dll"]

8. Kubernetes Deployments and Services

All four services live in the same prod namespace but never share a Deployment — each gets its own manifest, its own resource sizing based on its actual workload shape.

# order-service-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: prod
  labels: { app: order-service, tier: business-critical }
spec:
  replicas: 6
  selector: { matchLabels: { app: order-service } }
  template:
    metadata: { labels: { app: order-service } }
    spec:
      serviceAccountName: order-service-sa
      containers:
        - name: order-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service:prod-v3.2.0
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: order-service-config }
            - secretRef: { name: order-service-secret }
          resources:
            requests: { cpu: "250m", memory: "512Mi" }   # JVM needs real memory headroom
            limits:   { cpu: "1",    memory: "1Gi" }
          readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, initialDelaySeconds: 20, periodSeconds: 10 }
          livenessProbe:  { httpGet: { path: /actuator/health/liveness,  port: 8080 }, initialDelaySeconds: 30, periodSeconds: 20 }
---
apiVersion: v1
kind: Service
metadata: { name: order-service-svc, namespace: prod }
spec:
  selector: { app: order-service }
  ports: [{ port: 80, targetPort: 8080 }]

9. ConfigMaps and Secrets

# order-service-config (ConfigMap) — non-sensitive
apiVersion: v1
kind: ConfigMap
metadata: { name: order-service-config, namespace: prod }
data:
  CATALOG_SERVICE_URL: "http://catalog-service-svc.prod.svc.cluster.local"
  PAYMENT_SERVICE_URL: "http://payment-service-svc.prod.svc.cluster.local"
  LOG_LEVEL: "info"

Notice the internal URLs use Kubernetes DNS (<service>.<namespace>.svc.cluster.local) — this is service-to-service communication happening entirely inside the cluster network, never bouncing out through the public ALB, which is both faster and more secure.

# External Secrets for the Payment Service — the most sensitive credential in the whole system
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: payment-service-secret, namespace: prod }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets-manager, kind: ClusterSecretStore }
  target: { name: payment-service-secret }
  data:
    - secretKey: PAYMENT_GATEWAY_API_KEY
      remoteRef: { key: shopnow/prod/payment-gateway-key }

10. Ingress with AWS Load Balancer Controller

# shopnow-ingress.yaml — one ALB, path-based routing to the three public-facing services
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shopnow-ingress
  namespace: prod
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:111122223333:certificate/xxxx
spec:
  rules:
    - host: shopnow.com
      http:
        paths:
          - path: /api/orders
            pathType: Prefix
            backend: { service: { name: order-service-svc, port: { number: 80 } } }
          - path: /api/catalog
            pathType: Prefix
            backend: { service: { name: catalog-service-svc, port: { number: 80 } } }
          - path: /api/payments
            pathType: Prefix
            backend: { service: { name: payment-service-svc, port: { number: 80 } } }

Notification Service is intentionally absent from this Ingress — it has no path, no public route, exactly as designed in section 3.

11. HPA and Autoscaling

# catalog-service-hpa.yaml — scales hardest because it absorbs the most read traffic
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: catalog-service-hpa, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: catalog-service }
  minReplicas: 8
  maxReplicas: 30
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
---
# order-service-hpa.yaml — narrower band, business-critical, prefers stability over aggressive scaling
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-service-hpa, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }
  minReplicas: 6
  maxReplicas: 15
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

Payment Service deliberately has no HPA — it runs a fixed 3 replicas on the secure node group, because scaling behavior for a PCI-scoped service is a change reviewed by security, not an automatic reaction to CPU load.

13. NetworkPolicies

# Default deny-all, then explicitly allow only the calls that should exist
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: prod }
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# Only Order Service may call Payment Service — Catalog and Notification cannot
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-order-to-payment, namespace: prod }
spec:
  podSelector: { matchLabels: { app: payment-service } }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: order-service } }
      ports: [{ protocol: TCP, port: 8081 }]
---
# Allow the ALB target group to reach Order and Catalog (both public)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-alb-to-order, namespace: prod }
spec:
  podSelector: { matchLabels: { app: order-service } }
  policyTypes: [Ingress]
  ingress: [{ from: [], ports: [{ protocol: TCP, port: 8080 }] }]
This is the technical enforcement of the microservice boundary drawn in section 2. "Catalog Service can never talk to Payment Service" is not just an architecture diagram — with this NetworkPolicy in place, a compromised Catalog pod that tries to open a TCP connection to Payment Service gets dropped at the packet level, before the request ever reaches the application.

15. CI/CD Pipeline — Jenkins and GitHub Actions

Because each microservice has its own repository and its own team, each gets its own pipeline file — but all four follow the same shape: test in the service's native toolchain, build a Docker image, push to that service's ECR repo, update the GitOps manifest.

Jenkins Pipeline — Order Service (Java)

// order-service/Jenkinsfile
pipeline {
  agent any
  environment {
    ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service"
    IMAGE_TAG = "prod-${GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Test') { steps { sh './gradlew test' } }
    stage('Build Image') { steps { sh 'docker build -t $ECR_REPO:$IMAGE_TAG .' } }
    stage('Push') {
      steps {
        sh '''
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:$IMAGE_TAG
        '''
      }
    }
    stage('Approval') {
      steps { timeout(time: 20, unit: 'MINUTES') { input message: 'Deploy order-service to prod?' } }
    }
    stage('Update GitOps repo') {
      steps {
        sh '''
          cd gitops-repo/services/order-service
          kustomize edit set image order-service=$ECR_REPO:$IMAGE_TAG
          git commit -am "order-service: deploy $IMAGE_TAG" && git push
        '''
      }
    }
    stage('Report & Notify') {
      steps {
        sh 'python3 generate_report.py --service order-service --status success --build ${BUILD_NUMBER}'
        sh 'python3 send_email.py --service order-service --report report.html'
      }
    }
  }
}

GitHub Actions — Catalog Service (Python)

# catalog-service/.github/workflows/deploy.yml
name: Catalog Service Deploy
on: { push: { branches: ["main"] } }
jobs:
  test-build-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: |
          pip install -r requirements-dev.txt
          pytest
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::111122223333:role/gha-ecr-push, aws-region: ap-south-1 }
      - name: Build and push
        run: |
          IMAGE_TAG=prod-${{ github.sha }}
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REGISTRY
          docker build -t $ECR_REGISTRY/catalog-service:$IMAGE_TAG .
          docker push $ECR_REGISTRY/catalog-service:$IMAGE_TAG
      - name: Update GitOps manifest
        run: |
          cd gitops-repo/services/catalog-service
          kustomize edit set image catalog-service=$ECR_REGISTRY/catalog-service:prod-${{ github.sha }}
          git commit -am "catalog-service: deploy ${{ github.sha }}" && git push

Notification (Node.js) and Payment (.NET) pipelines follow the identical shape — npm test / dotnet test in place of pytest, everything else the same — which is exactly the point: one pipeline pattern, reused across languages, is what makes a polyglot platform maintainable instead of four completely different operational nightmares.

16. Argo CD GitOps

# Four separate Argo CD Applications, one per microservice, so each team's deploys are independent
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: order-service, namespace: argocd }
spec:
  project: default
  source: { repoURL: https://github.com/shopnow/gitops-repo.git, targetRevision: main, path: services/order-service }
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy: { automated: { prune: true, selfHeal: true } }
---
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: payment-service, namespace: argocd }
spec:
  project: default
  source: { repoURL: https://github.com/shopnow/gitops-repo.git, targetRevision: main, path: services/payment-service }
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy: {}   # deliberately NOT automated — Payment Service always syncs manually, after security sign-off

This is the practical answer to "how do independent teams deploy to a shared cluster without stepping on each other" — Order Service's Argo CD Application only ever touches Order Service's manifests; the Catalog team can merge and auto-deploy fifty times a day without anyone from the Order team even being aware, because the two Applications, the two ECR repos, and the two GitOps folders never overlap.

17. Prometheus and Grafana

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata: { name: microservices-monitor, namespace: prod }
spec:
  selector:
    matchExpressions:
      - key: app
        operator: In
        values: [order-service, catalog-service, notification-service, payment-service]
  endpoints: [{ port: metrics, path: /metrics, interval: 30s }]

One Grafana dashboard per service, plus a single "fleet overview" dashboard with a $service variable showing request rate, p95 latency, and error rate side by side for all four — this is what lets you answer "is the slowness in Order Service or is it Catalog Service it's calling" in thirty seconds instead of grepping logs across four different pods.

18. CloudWatch Logging

apiVersion: v1
kind: ConfigMap
metadata: { name: fluent-bit-config, namespace: amazon-cloudwatch }
data:
  output.conf: |
    [OUTPUT]
        Name                cloudwatch_logs
        Match               kube.*
        region              ap-south-1
        log_group_name      /eks/shopnow/${kubernetes['labels']['app']}
        log_stream_prefix   ${kubernetes['pod_name']}-
        auto_create_group   true

Logs are grouped by service label, not by namespace this time, since all four services share the prod namespace — /eks/shopnow/order-service, /eks/shopnow/catalog-service, and so on, so a team can subscribe to just their own service's log group without wading through the other three.

19. Failure Testing

# Test 1: Kill Order Service pods, confirm PDB and self-healing hold
kubectl delete pod -n prod -l app=order-service --field-selector status.phase=Running | head -2
kubectl get pods -n prod -l app=order-service -w

# Test 2: Simulate Catalog Service being slow/unresponsive — confirm Order Service degrades gracefully
# instead of hanging forever (proves the timeout/circuit-breaker config in Order Service is real)
kubectl exec -it deploy/catalog-service -n prod -- sh -c "sleep 300 &"

# Test 3: Confirm the NetworkPolicy boundary actually blocks Catalog -> Payment
kubectl exec -it deploy/catalog-service -n prod -- curl -m 3 http://payment-service-svc.prod.svc.cluster.local
# expected result: connection timeout, proving the NetworkPolicy from section 13 is enforced

# Test 4: Load test Catalog Service and watch its HPA scale from 8 to 30
kubectl run load-test --image=williamyeh/hey --restart=Never -n prod -- -z 3m -c 100 http://catalog-service-svc.prod.svc.cluster.local

20. Rollback Strategy

# Because each service has its own Argo CD Application, rollback is scoped to exactly one service
cd gitops-repo/services/payment-service
git log --oneline -5
git revert <bad-commit-sha>
git push
# Only payment-service's Argo CD Application picks this up — order/catalog/notification are untouched

# Emergency native rollback, scoped to one Deployment:
kubectl rollout undo deployment/payment-service -n prod
kubectl rollout history deployment/payment-service -n prod
A rollback of Payment Service can never accidentally roll back Order Service, because they are two entirely separate Argo CD Applications pointed at two entirely separate GitOps folders — this per-service blast-radius containment is worth stating explicitly if asked how you'd handle an incident in one microservice without risking the others.

22. Ansible Automation

Ansible bootstraps a brand-new microservice onto the platform — when a fifth team spins up a Recommendation Service next quarter, this playbook creates its IRSA role, ECR repo, and Argo CD Application in one run instead of a manual checklist repeated by hand.

# bootstrap-microservice.yml
- name: Onboard a new microservice onto the ShopNow EKS platform
  hosts: localhost
  gather_facts: false
  vars:
    service_name: "{{ svc }}"

  tasks:
    - name: Create ECR repository
      community.aws.ecs_ecr:
        name: "{{ service_name }}"
        region: ap-south-1

    - name: Create IRSA service account
      command: >
        eksctl create iamserviceaccount --cluster shopnow-cluster --namespace prod
        --name {{ service_name }}-sa
        --attach-policy-arn {{ policy_arn }}
        --approve

    - name: Render base Deployment manifest from template
      template:
        src: templates/deployment.yaml.j2
        dest: "gitops-repo/services/{{ service_name }}/deployment.yaml"

    - name: Register Argo CD Application
      kubernetes.core.k8s:
        state: present
        template: templates/argocd-app.yaml.j2

ansible-playbook bootstrap-microservice.yml -e "svc=recommendation-service policy_arn=arn:aws:iam::111122223333:policy/recommendation-service-policy"

23. HTML Deployment/Job Report

# generate_report.py — extended to show all four services' status side by side
import argparse, subprocess, json, datetime

SERVICES = ["order-service", "catalog-service", "notification-service", "payment-service"]

def get_status(svc):
    out = subprocess.run(
        ["kubectl", "get", "deploy", svc, "-n", "prod", "-o", "json"],
        capture_output=True, text=True
    )
    d = json.loads(out.stdout)
    return d["status"].get("readyReplicas", 0), d["status"].get("replicas", 0)

def build_report(deployed_service, build_no, status):
    rows = ""
    for svc in SERVICES:
        ready, total = get_status(svc)
        highlight = ' style="font-weight:bold;color:#e8a33d"' if svc == deployed_service else ""
        rows += f"<tr{highlight}><td>{svc}</td><td>{ready}/{total}</td></tr>"
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Deploy Report — {deployed_service} (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>Service</th><th>Ready/Total Pods</th></tr>{rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.service, args.build, args.status)

The report always shows all four services, with the one that was just deployed highlighted — so a release manager sees at a glance whether an Order Service deploy accidentally affected any other service's pod count.

24. Email Notification

# send_email.py — same pattern as the multi-env use case, subject line now names the service
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(service, status, build_no, report_path):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] {service} deploy - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = f"{service}-team@shopnow.com, release-managers@shopnow.com"
    msg.attach(MIMEText(f"Service: {service}\nBuild: #{build_no}\nStatus: {status}", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.service, args.status, args.build, args.report)

Notice the recipient list — each deploy notifies that service's own team plus release managers, not everyone. This is the same "each team owns their own service" principle from section 2, now showing up in something as simple as an email recipient list.
