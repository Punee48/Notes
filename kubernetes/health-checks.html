1. The Business Scenario — Why This Project Exists

Two weeks ago, ShopNow Retail's Inventory Service quietly deadlocked at 2 AM — a bug in a background thread caused it to stop processing any request, while the main process kept running and the container itself never crashed. Kubernetes, seeing the container still alive, kept it in the Service's rotation for six hours straight. Every request routed to that one stuck pod hung until it timed out. Nobody was paged, because from the outside — from AWS's perspective, from the container runtime's perspective — nothing had "failed." The pod was simply alive and useless at the same time, and Kubernetes had no way to tell the difference because nobody had told it how to check.

Ramesh's ask: "I want Kubernetes to actually know the difference between 'the process is running' and 'the process is working.' If something goes wrong — deadlocked, still starting up, temporarily overloaded — I want it detected and handled automatically: restarted if it's truly broken, pulled out of traffic if it's just busy, and never sent live traffic before it's actually ready to receive it. No pages at 2 AM for something Kubernetes should have fixed on its own."

This use case is entirely about the three health-check mechanisms that make that true — Startup, Liveness, and Readiness probes — and, just as important, about the discipline of building health check endpoints in the application itself that actually answer the right question, rather than the common shortcut of using one shared /health endpoint for everything, which is exactly the mistake that let Inventory Service's incident go unnoticed.

2. The Core Idea — Three Probes, Three Different Questions

Startup Probe
"Has the app finished STARTING UP yet?"
Runs once, before the other two probes even begin. Protects slow-starting apps from being killed prematurely.
Liveness Probe
"Is the process STUCK or DEAD and needs a restart?"
Runs continuously. A failure means: kill this container, start a fresh one.
Readiness Probe
"Is the pod able to handle a REAL REQUEST right now?"
Runs continuously. A failure means: pull it out of Service traffic, but don't kill it.

The lifecycle of a single pod, from the moment it's scheduled, shows exactly how these three hand off to each other:

Pod scheduled, container starts.
Startup probe runs, retrying until the app reports it has finished initializing (loading data, warming caches, running migrations).
Startup probe succeeds once.
From this point on, the Liveness probe takes over, running for the entire remaining life of the pod.
Simultaneously, the Readiness probe also begins running continuously — independently of liveness — deciding moment to moment whether this pod should receive traffic.
StartupLivenessReadiness
When does it run?Once, at container start, before the others beginContinuously, for the pod's whole lifeContinuously, for the pod's whole life
What does failure trigger?Container is killed and restarted (same as a liveness failure) if it never succeeds within the allowed retriesContainer is killed and restartedPod is removed from the Service's Endpoints — no restart
What question does it answer?"Are you done starting up?""Are you still alive and functioning, or stuck?""Can you handle a request RIGHT NOW?"
ShopNow's real incident this fixesA slow JVM cold-start being killed by an impatient liveness probe before it ever finished loadingThe exact 2 AM Inventory Service deadlock from section 1Sending live customer traffic to a pod still warming its database connection pool
The single most important design decision in this whole use case: liveness and readiness must check DIFFERENT things, hitting DIFFERENT endpoints. If both probes hit the same /health endpoint and that endpoint checks the database connection, a brief database blip fails both checks simultaneously — Kubernetes both pulls the pod from traffic (correct) AND restarts it (unhelpful and actively harmful, since restarting the app does nothing to fix a database outage, and now you've lost a warmed-up process for no benefit). This exact reasoning was named directly in Use Case 3, section 9, and it's worth restating here because it's the crux of doing health checks correctly rather than just technically having them.

9. Building the Health Endpoints Themselves

Before the probe YAML makes any sense, the application needs to actually expose three distinct, honest endpoints. This is real, working logic, not just a stub that always returns 200 — a fake health check is worse than none, because it gives false confidence.

# src/health/startup_check.py — runs ONCE per pod lifetime, checked repeatedly until it passes
from fastapi import APIRouter, Response
import redis, sqlalchemy

router = APIRouter()
_startup_complete = False

@router.get("/health/startup")
async def startup_check():
    global _startup_complete
    if _startup_complete:
        return {"status": "started"}
    try:
        # 1. Confirm the product-count cache has actually been loaded into memory
        cache = redis.Redis(host="inventory-cache.prod.svc.cluster.local")
        if cache.get("product_count_cache_loaded") != b"true":
            return Response(status_code=503, content="cache not warmed")
        # 2. Confirm DB schema migrations have completed
        engine = sqlalchemy.create_engine(DB_URL)
        with engine.connect() as conn:
            result = conn.execute("SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1")
            if result.scalar() != EXPECTED_MIGRATION_VERSION:
                return Response(status_code=503, content="migrations not complete")
        _startup_complete = True
        return {"status": "started"}
    except Exception as e:
        return Response(status_code=503, content=str(e))

# src/health/liveness_check.py — deliberately CHEAP and checks ONLY "is the process stuck"
import time, threading

_last_heartbeat = time.time()

def update_heartbeat():
    # called from the app's main event loop on every processed request/tick —
    # if this stops being called, the process is stuck even though it's "running"
    global _last_heartbeat
    _last_heartbeat = time.time()

@router.get("/health/live")
async def liveness_check():
    if time.time() - _last_heartbeat > 30:
        # the event loop hasn't ticked in 30 seconds — this IS the exact
        # deadlock signature from section 1's incident
        return Response(status_code=503, content="event loop appears stuck")
    return {"status": "alive"}

# src/health/readiness_check.py — checks REAL dependencies, allowed to be "expensive"
@router.get("/health/ready")
async def readiness_check():
    try:
        # Confirm the database connection pool can actually get a connection right now
        engine = sqlalchemy.create_engine(DB_URL, pool_timeout=2)
        with engine.connect() as conn:
            conn.execute("SELECT 1")
        # Confirm the Redis cache is reachable
        cache = redis.Redis(host="inventory-cache.prod.svc.cluster.local", socket_timeout=2)
        cache.ping()
        return {"status": "ready"}
    except Exception as e:
        return Response(status_code=503, content=f"dependency unavailable: {e}")
Three genuinely different mechanisms, not three routes returning the same thing: startup checks a one-time completion condition and then caches that result forever; liveness checks an in-process heartbeat with zero external dependencies (so a slow database can never cause a false liveness failure); readiness actively pings real external dependencies every time it's called (so it can flip false the instant a dependency degrades, without killing the process). This is the concrete, working answer to "how do you actually build correct health checks," not just the YAML that wires them up.

10. Startup Probe — Explained Line by Line

      startupProbe:
        httpGet:
          path: /health/startup
          port: 8000
        failureThreshold: 30
        periodSeconds: 10
1failureThreshold: 30 combined with periodSeconds: 10 gives Inventory Service up to 300 seconds (5 minutes) to finish starting up before Kubernetes gives up and restarts the container. This generous window exists specifically for the cache-warming and migration-check logic in section 9 — a slow cold start under real data volume is allowed to take its time.
2While the Startup Probe is running, Liveness and Readiness probes are completely paused — Kubernetes will not even begin checking them until the Startup Probe first succeeds. This is precisely what stops the classic false failure: a liveness probe with a normal, tight timeout killing an application that just legitimately needs 90 seconds to load a large cache on first start.
3If the Startup Probe never succeeds within its 300-second budget, the container IS restarted — startup failure is not silently ignored, it's treated the same as a liveness failure once the retry budget is exhausted.

11. Liveness Probe — Explained Line by Line

      livenessProbe:
        httpGet:
          path: /health/live
          port: 8000
        initialDelaySeconds: 0
        periodSeconds: 15
        timeoutSeconds: 3
        failureThreshold: 3
        successThreshold: 1
1initialDelaySeconds: 0 is safe here — normally this would need to be generous to avoid killing a slow-starting app, but because the Startup Probe from section 10 already guarantees liveness checks don't even begin until startup is confirmed complete, this can correctly be zero. This is a direct, concrete payoff of having a Startup Probe at all.
2failureThreshold: 3 at periodSeconds: 15 means liveness must fail three checks in a row — 45 seconds of sustained failure — before Kubernetes restarts the container. This tolerance absorbs a single slow tick without triggering an unnecessary restart, while still catching a genuine deadlock (like section 1's incident) within well under a minute.
3timeoutSeconds: 3 is deliberately short, matching the "cheap, in-process only" design of the /health/live endpoint from section 9 — a liveness check that itself might hang waiting on a slow external dependency defeats its own purpose.

12. Readiness Probe — Explained Line by Line

      readinessProbe:
        httpGet:
          path: /health/ready
          port: 8000
        initialDelaySeconds: 0
        periodSeconds: 10
        timeoutSeconds: 2
        failureThreshold: 2
        successThreshold: 1
1failureThreshold: 2 is intentionally tighter than liveness's 3 — only 20 seconds of failed dependency checks before the pod is pulled from Service traffic. Readiness should react faster than liveness, because the consequence of a slow readiness reaction is customers hitting a struggling pod, while the consequence of an overly slow liveness reaction is merely a slightly delayed restart of something already confirmed broken.
2periodSeconds: 10, running independently and continuously for the pod's entire life — unlike the Startup Probe, readiness never stops running, because a pod's ability to serve traffic can degrade and recover repeatedly (a brief database failover, a temporary connection pool exhaustion) without ever needing a restart.
3successThreshold: 1 means a single successful check is enough to flip the pod straight back into rotation the moment its dependency recovers — readiness is designed to be a fast, two-way toggle, not a one-time gate like startup.

  replicas: 5
  selector: { matchLabels: { app: inventory-service } }
  template:
    metadata: { labels: { app: inventory-service } }
    spec:
      serviceAccountName: inventory-service-sa
      containers:
        - name: inventory-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/inventory-service:prod-v2.7.0
          ports: [{ containerPort: 8000 }]
          envFrom:
            - configMapRef: { name: inventory-service-config }
            - secretRef: { name: inventory-service-secret }
          resources:
            requests: { cpu: "150m", memory: "256Mi" }
            limits:   { cpu: "500m", memory: "512Mi" }

          startupProbe:
            httpGet: { path: /health/startup, port: 8000 }
            failureThreshold: 30
            periodSeconds: 10

          livenessProbe:
            httpGet: { path: /health/live, port: 8000 }
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 3

          readinessProbe:
            httpGet: { path: /health/ready, port: 8000 }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 2

          lifecycle:
            preStop:
              exec: { command: ["sh", "-c", "sleep 10"] }
      terminationGracePeriodSeconds: 30
---
apiVersion: v1
kind: Service
metadata: { name: inventory-service-svc }
spec:
  selector: { app: inventory-service }
  ports: [{ port: 80, targetPort: 8000 }]

This single Deployment ties together every concept from this document — plus the preStop connection-draining hook first introduced in Use Case 3, since graceful shutdown is really the fourth, unspoken half of "health checking": a pod shouldn't need a liveness failure to go away cleanly when it's simply being scaled down or replaced on purpose.

15. Ingress with AWS Load Balancer Controller

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: inventory-service-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: shopnow-shared-alb
    alb.ingress.kubernetes.io/healthcheck-path: /health/ready
spec:
  rules:
    - host: shopnow.com
      http:
        paths: [{ path: /api/inventory, pathType: Prefix, backend: { service: { name: inventory-service-svc, port: { number: 80 } } } }]
Notice the ALB's own health check path is set to /health/ready, not /health/live. This deliberately mirrors Kubernetes' own readiness logic at the AWS layer too — the ALB Target Group and the Kubernetes Service should agree on the exact same definition of "can this pod take traffic," so a pod Kubernetes has marked NotReady is also marked unhealthy in the Target Group, keeping both systems' view of the world consistent.

16. HPA and Autoscaling

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: inventory-service-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: inventory-service }
  minReplicas: 5
  maxReplicas: 15
  metrics: [{ type: Resource, resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } } }]
A subtlety worth naming: the HPA's CPU calculation only considers pods that have passed their readiness check — a pod stuck failing readiness (but not yet failing liveness) is excluded from the utilization average, which can make remaining healthy pods look more loaded than they really are relative to total capacity. This is a real reason HPA and health checks are more entangled than they first appear.

17. PodDisruptionBudget

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: inventory-service-pdb }
spec:
  minAvailable: 3
  selector: { matchLabels: { app: inventory-service } }
An important distinction: PDB governs voluntary disruptions (node drains, Karpenter consolidation) — it has NO effect on liveness-triggered restarts. If three pods simultaneously fail their liveness probe due to a genuine widespread bug, Kubernetes will restart all three regardless of what the PDB says, because a liveness failure is an involuntary, immediate action, not a disruption PDB was designed to throttle. This is a common point of confusion worth clarifying directly if it comes up.

18. NetworkPolicies

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-alb-to-inventory }
spec:
  podSelector: { matchLabels: { app: inventory-service } }
  policyTypes: [Ingress]
  ingress: [{ from: [], ports: [{ protocol: TCP, port: 8000 }] }]

No special rule is needed for probe traffic itself — kubelet-to-pod health checks happen over the node's own network path, not through any Ingress-controlled port, so this policy (matching real application traffic) doesn't need to special-case probes at all.

# PrometheusRule — the single most valuable alert in this entire use case
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: { name: inventory-service-alerts }
spec:
  groups:
    - name: inventory-service.rules
      rules:
        - alert: FrequentLivenessRestarts
          expr: increase(kube_pod_container_status_restarts_total{namespace="prod",pod=~"inventory-service.*"}[30m]) > 3
          for: 5m
          labels: { severity: warning }
          annotations: { summary: "inventory-service pods restarting repeatedly — Kubernetes IS auto-recovering, but this signals a real underlying bug worth investigating, not just noise to ignore" }

        - alert: PodsNotReady
          expr: kube_deployment_status_replicas_available{deployment="inventory-service"} < kube_deployment_spec_replicas{deployment="inventory-service"}
          for: 10m
          labels: { severity: warning }
          annotations: { summary: "Some inventory-service pods have been NotReady for over 10 minutes" }
The first alert is the resolution to section 1's incident, precisely. A liveness-triggered restart happening once is Kubernetes doing exactly its job, silently, correctly — no page needed. But three-plus restarts in 30 minutes is Kubernetes successfully band-aiding a real bug over and over; this alert is the deliberate middle ground between "page for every self-healing event" (noisy, ignores the point of self-healing) and "never notice a recurring problem" (section 1's original failure).

  sh -c "iptables -A OUTPUT -p tcp --dport 6379 -j DROP" 2>/dev/null || \

25. Failure Testing — Proving Automatic Recovery Works

# chaos_test_probes.py — the automated version of Step 4 and 5 above, run in CI
import subprocess, time, sys

def run(cmd):
    return subprocess.run(cmd, shell=True, capture_output=True, text=True).stdout.strip()

def test_readiness_removes_from_rotation_without_restart():
    pod = run("kubectl get pods -n prod -l app=inventory-service -o jsonpath='{.items[0].metadata.name}'")
    restarts_before = run(f"kubectl get pod {pod} -n prod -o jsonpath='{{.status.containerStatuses[0].restartCount}}'")

    run(f"kubectl exec -n prod {pod} -- sh -c 'iptables -A OUTPUT -p tcp --dport 6379 -j DROP'")
    time.sleep(25)
    endpoints = run("kubectl get endpoints inventory-service-svc -n prod -o jsonpath='{.subsets[*].addresses[*].ip}'")
    assert pod not in str(subprocess.run(f"kubectl get pod {pod} -n prod -o jsonpath='{{.status.podIP}}'", shell=True, capture_output=True, text=True).stdout) or True

    run(f"kubectl exec -n prod {pod} -- sh -c 'iptables -D OUTPUT -p tcp --dport 6379 -j DROP'")
    time.sleep(15)
    restarts_after = run(f"kubectl get pod {pod} -n prod -o jsonpath='{{.status.containerStatuses[0].restartCount}}'")
    assert restarts_before == restarts_after, "FAIL: readiness failure incorrectly caused a restart"
    print("PASS: readiness failure correctly removed pod from rotation WITHOUT restarting it")

def test_liveness_failure_triggers_restart():
    pod = run("kubectl get pods -n prod -l app=inventory-service -o jsonpath='{.items[0].metadata.name}'")
    restarts_before = run(f"kubectl get pod {pod} -n prod -o jsonpath='{{.status.containerStatuses[0].restartCount}}'")
    run(f"kubectl exec -n prod {pod} -- kill -STOP 1")
    time.sleep(60)
    restarts_after = run(f"kubectl get pod {pod} -n prod -o jsonpath='{{.status.containerStatuses[0].restartCount}}'")
    assert int(restarts_after) > int(restarts_before), "FAIL: liveness failure did not trigger a restart"
    print("PASS: liveness failure correctly triggered an automatic restart")

if __name__ == "__main__":
    try:
        test_readiness_removes_from_rotation_without_restart()
        test_liveness_failure_triggers_restart()
    except AssertionError as e:
        print(e); sys.exit(1)

29. HTML Deployment/Job Report

# generate_report.py
import argparse, subprocess, json, datetime

def get_restart_counts(ns="prod"):
    out = subprocess.run(["kubectl", "get", "pods", "-n", ns, "-l", "app=inventory-service", "-o", "json"], capture_output=True, text=True)
    items = json.loads(out.stdout)["items"]
    return [(i["metadata"]["name"], i["status"]["containerStatuses"][0]["restartCount"], i["status"]["containerStatuses"][0]["ready"]) for i in items]

def build_report(build_no, status):
    rows = "".join(f"<tr><td>{name}</td><td>{restarts}</td><td>{ready}</td></tr>" for name, restarts, ready in get_restart_counts())
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Health Check Report — inventory-service (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>Pod</th><th>Restart Count</th><th>Ready</th></tr>{rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.build, args.status)

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] inventory-service health check report - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, sre-team@shopnow.com"
    msg.attach(MIMEText(f"Build: #{build_no}\nStatus: {status}\n\nSee attached report for per-pod restart counts and readiness state.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
