1. The Business Scenario — Why This Project Exists

Three weeks ago, ShopNow Retail's platform team rotated the RDS security group as part of a routine network hardening pass. The change was correct for every service except one: Order Service's new release, sitting in the deploy pipeline that same afternoon, had never actually been tested against the updated security group. The pipeline built the image, ran unit tests (which mocked the database entirely), pushed to ECR, and rolled the new pods out to production — where every single pod immediately started `CrashLoopBackOff`, unable to reach the database at all. The old, working pods had already been terminated by the rolling update before anyone noticed. Customers hit a fully broken Order Service for eleven minutes before a manual rollback restored the previous version.

Ramesh's ask, direct and specific: "Before a single new pod ever takes real traffic, I want the pipeline to actually prove it can reach every single thing it depends on — the database, the cache, the queue, the third-party APIs, the other microservices it calls. If even one of those checks fails, stop right there. Don't roll anything out. Don't touch what's already running."

This use case builds exactly that: a pre-deployment dependency validation gate that checks connectivity to RDS, DynamoDB, Redis, Kafka, external APIs, and internal microservices — and is wired into the CI/CD pipeline so that a failure at this gate stops the deployment cold, before any existing healthy pod is ever touched.

2. The Core Idea — A Deployment Gate, Not a Runtime Check

This use case is deliberately NOT the same thing as Use Case 10's health checks, even though both involve "checking dependencies." Readiness probes (Use Case 10) run continuously, after a pod is already running, deciding whether it should receive traffic right now. Dependency validation, here, runs once, before any new pod is even created, as a hard gate in the deployment pipeline itself. The distinction matters: a readiness probe failing pulls one pod out of rotation while others keep serving; a dependency validation failure should stop the entire rollout from starting, because it means the new version fundamentally cannot work in this environment at all — continuing anyway would just fail the same way, pod after pod, exactly as it did in section 1's incident.

7. VPC and Networking

Standard VPC layout. One requirement specific to this use case: the CI/CD runner (Jenkins agent or GitHub Actions runner) that executes the pipeline-stage version of the validator must itself sit inside the VPC, or connect via a VPN/peering link, since RDS, ElastiCache, and MSK are all in private subnets with no public endpoint — this is a common real-world gotcha worth naming: a validator that works fine as an in-cluster init container can fail entirely as a CI step if the CI runner has no network path to the same private resources.

# dependency-validator/validator/run_all.py — the orchestrator
import yaml, sys, importlib, time

CHECK_MODULES = {
    "rds": "check_rds", "dynamodb": "check_dynamodb", "redis": "check_redis",
    "kafka": "check_kafka", "external_api": "check_external_api", "internal_service": "check_internal_service",
}

def main(config_path):
    with open(config_path) as f:
        config = yaml.safe_load(f)

    results = []
    for dep in config["dependencies"]:
        module = importlib.import_module(CHECK_MODULES[dep["type"]])
        start = time.time()
        try:
            module.check(dep)
            results.append((dep["name"], dep["type"], "PASS", time.time() - start, None))
        except Exception as e:
            results.append((dep["name"], dep["type"], "FAIL", time.time() - start, str(e)))

    print(f"\n{'DEPENDENCY':<25}{'TYPE':<18}{'RESULT':<8}{'TIME':<8}DETAIL")
    for name, dtype, result, elapsed, detail in results:
        print(f"{name:<25}{dtype:<18}{result:<8}{elapsed:.2f}s   {detail or ''}")

    failed = [r for r in results if r[2] == "FAIL"]
    if failed:
        print(f"\n{len(failed)} DEPENDENCY CHECK(S) FAILED — DEPLOYMENT BLOCKED")
        sys.exit(1)
    print("\nALL DEPENDENCY CHECKS PASSED — SAFE TO PROCEED")
    sys.exit(0)

if __name__ == "__main__":
    main(sys.argv[1] if len(sys.argv) > 1 else "config/order-service-dependencies.yaml")

This single orchestrator, driven entirely by the declarative YAML file, is what makes the validator reusable across ShopNow's whole fleet — onboarding a new service's dependency checks is a config change, never a code change.

10. Validating RDS

# dependency-validator/validator/check_rds.py
import sqlalchemy, os

def check(dep):
    engine = sqlalchemy.create_engine(os.environ["DB_URL"], connect_args={"connect_timeout": 5})
    with engine.connect() as conn:
        # 1. Can we even connect and run a trivial query?
        conn.execute("SELECT 1")
        # 2. Is the schema at the version THIS release expects — catches the
        # class of incident where a deploy assumes a migration that hasn't run yet
        result = conn.execute("SELECT version FROM schema_migrations ORDER BY version DESC LIMIT 1")
        actual_version = result.scalar()
        if actual_version != dep["expected_migration_version"]:
            raise Exception(f"schema version mismatch: expected {dep['expected_migration_version']}, found {actual_version}")
Checking the migration version is what turns this from a generic "is the network open" check into a real, release-specific validation. A security-group change (section 1's actual root cause) and a missing migration are both real, common causes of a broken deploy, and this single check catches both categories.

11. Validating DynamoDB

# dependency-validator/validator/check_dynamodb.py
import boto3

def check(dep):
    client = boto3.client("dynamodb", region_name="ap-south-1")
    resp = client.describe_table(TableName=dep["name"])
    status = resp["Table"]["TableStatus"]
    if status != "ACTIVE":
        raise Exception(f"table {dep['name']} is not ACTIVE (status: {status})")

No item-level read/write is attempted here deliberately — DescribeTable is enough to confirm both IAM permission and table existence/health without needing to write test data into a production table, keeping the check side-effect-free.

12. Validating Redis

# dependency-validator/validator/check_redis.py
import redis, os, uuid

def check(dep):
    client = redis.Redis(host=os.environ["REDIS_HOST"], socket_timeout=5)
    if not client.ping():
        raise Exception("PING failed")
    # A real write+read round-trip, using a throwaway key with a short TTL —
    # PING alone can succeed even if the underlying storage layer is degraded
    test_key = f"depcheck:{uuid.uuid4()}"
    client.set(test_key, "ok", ex=10)
    if client.get(test_key) != b"ok":
        raise Exception("write/read round-trip failed")
    client.delete(test_key)

13. Validating Kafka

# dependency-validator/validator/check_kafka.py
from kafka import KafkaAdminClient
import os

def check(dep):
    admin = KafkaAdminClient(bootstrap_servers=os.environ["KAFKA_BROKERS"], request_timeout_ms=5000)
    topics = admin.describe_topics([dep["name"]])
    if not topics:
        raise Exception(f"topic {dep['name']} not found")
    partition_count = len(topics[0]["partitions"])
    if partition_count != dep["expected_partitions"]:
        raise Exception(f"expected {dep['expected_partitions']} partitions, found {partition_count}")
Checking partition count specifically catches a subtle, real-world class of bug: a consumer group's partition-assignment logic can behave very differently if the topic's partition count changed since the code was written (say, someone repartitioned order-events from 3 to 6 partitions for throughput) — this check surfaces that mismatch before deploy, rather than as a mysterious consumer-lag issue discovered hours later.

14. Validating External APIs

# dependency-validator/validator/check_external_api.py
import requests

def check(dep):
    resp = requests.get(dep["url"], timeout=5)
    if resp.status_code != 200:
        raise Exception(f"{dep['name']} returned HTTP {resp.status_code}")
Deliberately a lightweight status check, never a real transaction. Validating the Payment Gateway means confirming its /v1/status endpoint is reachable and healthy — it must never mean submitting a real or even sandboxed payment as part of a deployment gate. The check proves network and basic API health; it says nothing about business-logic correctness, which is what integration tests exist for separately.

15. Validating Internal Microservices

# dependency-validator/validator/check_internal_service.py
import requests

def check(dep):
    resp = requests.get(dep["url"], timeout=3)
    if resp.status_code != 200:
        raise Exception(f"{dep['name']} readiness check returned HTTP {resp.status_code}")
This check deliberately reuses Use Case 10's /health/ready endpoint contract rather than inventing a separate one. Catalog Service and Payment Service already expose a well-defined, dependency-aware readiness endpoint — asking Order Service's deploy gate to hit that same endpoint means the two use cases in this series reinforce each other: a bad Catalog Service deploy that's failing its OWN readiness check is automatically also caught here, before Order Service is deployed on top of an already-degraded dependency.

16. The Init Container Gate — Stopping a Bad Deploy Before It Starts

# base/deployment.yaml (relevant excerpt) — the validator runs as an initContainer,
# BEFORE the main application container is even started
spec:
  template:
    spec:
      serviceAccountName: order-service-sa
      initContainers:
        - name: dependency-validator
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/dependency-validator:v1.2.0
          args: ["config/order-service-dependencies.yaml"]
          envFrom:
            - configMapRef: { name: order-service-config }
            - secretRef: { name: order-service-secret }
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "250m", memory: "256Mi" }
      containers:
        - name: order-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service:prod-v3.5.0
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: order-service-config }
            - secretRef: { name: order-service-secret }
          startupProbe: { httpGet: { path: /health/startup, port: 8080 }, failureThreshold: 30, periodSeconds: 10 }
          livenessProbe:  { httpGet: { path: /health/live, port: 8080 }, periodSeconds: 15, failureThreshold: 3 }
          readinessProbe: { httpGet: { path: /health/ready, port: 8080 }, periodSeconds: 10, failureThreshold: 2 }
1An init container runs to completion before any regular container in the same pod starts. If dependency-validator exits non-zero (any check failed), the main order-service container never starts at all — the pod sits in Init:Error / Init:CrashLoopBackOff, and critically, it never becomes Ready, so it's never added to the Service's Endpoints and never receives traffic.
2Because this happens per-pod during a rolling update, a failed validation on the very first new pod means the RollingUpdate's maxUnavailable: 0 guarantee (from Use Case 3) naturally does the rest of the work: since the new pod never becomes Ready, Kubernetes never proceeds to touch a second old pod. The old, working ReplicaSet keeps serving 100% of traffic indefinitely, exactly matching Ramesh's ask that "existing pods stay untouched."
3This init-container gate is the in-cluster, last-line-of-defense version of validation — section 23's CI/CD pipeline stage is the earlier, faster-feedback version of the exact same checks, run before the image is even deployed at all. Having both is deliberate defense in depth: the CI stage catches most problems in seconds without ever touching the cluster; the init container catches anything that's true specifically in this cluster/environment at this moment (like a security group change that happened after the CI run passed).

Init containers run on EVERY new pod, including ones the HPA creates during a scale-up event — not just during a deploy. This means a transient dependency blip during a traffic spike could theoretically delay HPA's ability to add capacity exactly when it's needed most. ShopNow's validator is deliberately fast (each check has a short timeout, typically completing in well under 5 seconds total) specifically to keep this overhead negligible relative to the value of the safety check.

// Jenkinsfile — the validation stage runs BEFORE deploy, as a standalone container run,
// completely separate from the in-cluster init container gate in section 16
pipeline {
  agent any
  environment { ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service" }
  stages {
    stage('Test') { steps { sh './gradlew test' } }
    stage('Build & Push') {
      steps {
        sh '''
          docker build -t $ECR_REPO:${GIT_COMMIT} .
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:${GIT_COMMIT}
        '''
      }
    }

    stage('Validate Dependencies (PRE-DEPLOY GATE)') {
      steps {
        sh '''
          docker run --rm \\
            --env-file prod.env \\
            111122223333.dkr.ecr.ap-south-1.amazonaws.com/dependency-validator:latest \\
            config/order-service-dependencies.yaml
        '''
      }
      // If this stage fails, Jenkins stops the pipeline HERE — the deploy stage
      // below never even runs. No kubectl command touches the cluster.
    }

    stage('Deploy') {
      steps {
        sh '''
          kubectl apply -k gitops-repo/services/order-service/overlays/prod
          kubectl rollout status deployment/order-service -n prod --timeout=180s
        '''
      }
    }

    stage('Report & Notify') {
      steps {
        sh 'python3 pipeline-scripts/generate_report.py --status success --build ${BUILD_NUMBER}'
        sh 'python3 pipeline-scripts/send_email.py --report report.html'
      }
    }
  }
  post {
    failure {
      sh 'python3 pipeline-scripts/generate_report.py --status failed --build ${BUILD_NUMBER}'
      sh 'python3 pipeline-scripts/send_email.py --status FAILED --report report.html'
    }
  }
}

          kubectl apply -k gitops-repo/services/order-service/overlays/prod
The GitHub Actions needs: dependency chain is the exact mechanism enforcing "stop the deployment" from the original ask. The deploy job's needs: validate-dependencies line means GitHub Actions will not run it at all if the prior job exits non-zero — this is a structural guarantee, not a convention someone has to remember to check.

29. Rollback Strategy

# In the common case, there IS no rollback needed — the gate prevents the bad
# version from ever displacing the good one, which is the entire point.

# If a dependency check itself was WRONG (a false positive blocking a genuinely
# good deploy — e.g. an overly strict migration version check), fix the check:
cd dependency-validator
git revert <bad-check-commit-sha> && git push

# If a bad version somehow DID get deployed despite the gate (e.g. the gate
# itself had a bug), standard GitOps revert applies as in every earlier use case:
cd gitops-repo/services/order-service/overlays/prod
git revert <bad-commit-sha> && git push

32. HTML Deployment/Job Report

# generate_report.py
import argparse, datetime, json, os

def build_report(build_no, status, results_json="validator_results.json"):
    results = json.load(open(results_json)) if os.path.exists(results_json) else []
    rows = "".join(
        f"<tr><td>{r['name']}</td><td>{r['type']}</td><td style='color:{'#5ec98f' if r['result']=='PASS' else '#e35d5d'}'>{r['result']}</td><td>{r.get('detail','')}</td></tr>"
        for r in results
    )
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Dependency Validation Report — order-service (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>Dependency</th><th>Type</th><th>Result</th><th>Detail</th></tr>{rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.build, args.status)

33. Email Notification

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] order-service dependency validation - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, sre-team@shopnow.com"
    body = f"Build: #{build_no}\nStatus: {status}\n\n"
    if status != "success":
        body += "DEPLOYMENT WAS BLOCKED — one or more dependency checks failed. Existing production pods were NOT affected. See attached report for which dependency failed.\n"
    msg.attach(MIMEText(body, "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
