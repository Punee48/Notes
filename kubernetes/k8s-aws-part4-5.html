💾 Volumes — Ephemeral vs Persistent

📖 Story

ShopNow's order processor writes invoice PDFs to the container's local filesystem. A pod restarts — all PDFs gone. A container crash wipes the data. You need storage that outlives the container lifecycle. That's what Kubernetes Volumes solve.

In Docker, container storage is ephemeral — it dies with the container. Kubernetes Volumes are attached to the Pod lifecycle (not the container), so data survives container restarts. PersistentVolumes survive even pod restarts and rescheduling.

Volume Type Hierarchy

EPHEMERAL (dies when Pod dies) ├── emptyDir — scratch space shared between containers in a pod │ (e.g., init container writes config, app reads it) └── hostPath — mounts a directory from the NODE filesystem (used only by system pods like DaemonSets) NODE-LOCAL (dies when Node dies) └── hostPath — same as above; dangerous for stateful workloads PERSISTENT (survives pod and node failures) ├── PersistentVolume (PV) backed by: │ ├── AWS EBS — block storage, ReadWriteOnce (1 pod at a time) │ ├── AWS EFS — NFS, ReadWriteMany (many pods simultaneously) │ └── AWS FSx — high-performance Lustre / Windows file system └── Provisioned via PVC + StorageClass (dynamic provisioning) CONFIG/SECRET VOLUMES (special purpose) ├── configMap — mount ConfigMap keys as files in container └── secret — mount Secret keys as files in container

emptyDir — Shared Scratch Space

YAMLemptydir-example.yaml
apiVersion: v1
kind: Pod
metadata:
  name: pdf-processor
  namespace: shopnow
spec:
  volumes:
  - name: shared-data          # ← Declare the volume at Pod level
    emptyDir: {}               # ← Empty directory created when pod starts
                               #   Stored in node's /var/lib/kubelet/pods/.../volumes/
                               #   DELETED when pod is removed from node

  containers:
  - name: generator            # ← Container 1: generates the file
    image: shopnow/pdf-gen:v1
    volumeMounts:
    - name: shared-data        # ← Mount the volume declared above
      mountPath: /output       # ← Inside this container, it's at /output

  - name: uploader             # ← Container 2: reads the file and uploads to S3
    image: shopnow/s3-uploader:v1
    volumeMounts:
    - name: shared-data        # ← SAME volume — both containers share this directory
      mountPath: /input        # ← Inside this container, it's at /input
    # generator writes to /output/invoice.pdf
    # uploader reads from /input/invoice.pdf (same file, different mount path)
emptyDir: {}
What {} means: The curly braces mean "use defaults". You can also write emptyDir: {medium: Memory} to create a RAM-backed tmpfs volume — much faster I/O, but uses pod memory. Useful for caches, temporary computation buffers, or high-speed inter-container data transfer.

🗃️ PersistentVolume, PVC & StorageClass

📖 Story — The Hotel Analogy

Think of PersistentVolumes (PV) as hotel rooms (pre-provisioned or dynamically created). PersistentVolumeClaims (PVC) are your booking requests — "I need a room with a double bed and WiFi". StorageClass is the hotel chain — it defines what type of room (gp2 SSD, io1 high-IOPS) you get and provisions it on demand. You never manually create EBS volumes — StorageClass does it automatically when you create a PVC.

The Full Binding Flow

Developer writes PVC StorageClass watches AWS creates EBS volume (claim: 10Gi, gp3) ──► PVC and provisions ──► (10Gi gp3 SSD in same AZ) │ ▼ PersistentVolume (PV) created automatically │ ▼ PVC bound to PV │ ▼ Pod references PVC EBS volume mounted at /var/lib/mysql

StorageClass — Define Your Storage Tier

YAMLstorageclass.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd                        # ← Name referenced by PVCs
  annotations:
    storageclass.kubernetes.io/is-default-class: "false"  # ← Don't make this default
provisioner: ebs.csi.aws.com           # ← Which driver provisions storage
                                        #   (AWS EBS CSI driver)
volumeBindingMode: WaitForFirstConsumer # ← DON'T create EBS until a Pod claims this PVC
                                        #   Ensures EBS is created in the SAME AZ as the pod
                                        #   (critical! EBS is AZ-specific)
reclaimPolicy: Retain                  # ← When PVC deleted: Retain EBS (don't delete data)
                                        #   Options: Retain | Delete | Recycle
allowVolumeExpansion: true             # ← Allow resizing PVC after creation
parameters:
  type: gp3                            # ← EBS volume type
                                        #   gp3 = general purpose (best default)
                                        #   io1/io2 = provisioned IOPS (databases)
                                        #   st1 = throughput-optimized HDD (Kafka)
  iops: "3000"                         # ← For gp3: 3000 baseline IOPS (free)
  throughput: "125"                    # ← MB/s throughput (gp3 baseline)
  encrypted: "true"                    # ← Encrypt EBS volume at rest (always!)
  kmsKeyId: "arn:aws:kms:..."         # ← Use your own KMS key (optional)
---
# Default StorageClass for general use (gp3)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"  # ← PVCs that don't specify
                                                           #   a class get this one
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
allowVolumeExpansion: true
parameters:
  type: gp3
  encrypted: "true"

PersistentVolumeClaim — Request Storage

YAMLmysql-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-pvc
  namespace: shopnow
spec:
  accessModes:
  - ReadWriteOnce              # ← RWO: only ONE node can mount at a time (block storage)
                               #   ReadWriteMany (RWX): multiple nodes (EFS/NFS only)
                               #   ReadOnlyMany (ROX): many nodes read-only
  storageClassName: fast-ssd   # ← Which StorageClass to use
  resources:
    requests:
      storage: 20Gi            # ← Request 20GB (EBS volume will be exactly this size)
---
# Use the PVC in a Pod/Deployment/StatefulSet
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mysql
  namespace: shopnow
spec:
  replicas: 1                  # ← MUST be 1 with EBS (ReadWriteOnce = 1 node!)
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        volumeMounts:
        - name: mysql-storage
          mountPath: /var/lib/mysql  # ← MySQL data directory
      volumes:
      - name: mysql-storage
        persistentVolumeClaim:
          claimName: mysql-data-pvc  # ← Reference the PVC by name
volumeBindingMode: WaitForFirstConsumer
Why this is critical: EBS volumes are AZ-specific. If the PVC is bound immediately (Immediate mode), the EBS might be created in AZ-1a, but the pod is later scheduled to a node in AZ-1c — and can't attach! WaitForFirstConsumer waits until the pod is assigned to a node, then creates the EBS in the same AZ. Always use this on EKS.
reclaimPolicy: Retain vs Delete
Retain: When you delete the PVC, the EBS volume is NOT deleted — data preserved (manual cleanup needed). Use for production databases. Delete: PVC deletion → EBS deletion. Use for dev/test. WARNING: the default for dynamic provisioning is often Delete — always check before using in production.

Check PV/PVC Status

bash
kubectl get pvc -n shopnow
# NAME             STATUS   VOLUME                    CAPACITY   ACCESS MODES   STORAGECLASS
# mysql-data-pvc   Bound    pvc-abc123-def456-...      20Gi       RWO            fast-ssd

kubectl get pv
# NAME                       CAPACITY   RECLAIM POLICY   STATUS   CLAIM
# pvc-abc123-def456-...      20Gi       Retain           Bound    shopnow/mysql-data-pvc

# STATUS meanings:
# Pending  → PVC created, waiting for a pod to schedule (WaitForFirstConsumer)
# Bound    → PVC matched to a PV, EBS volume created and attached
# Lost     → PV no longer exists (EBS was manually deleted)

# Resize a PVC (increase storage — decrease NOT supported by EBS)
kubectl patch pvc mysql-data-pvc -n shopnow \
  -p '{"spec":{"resources":{"requests":{"storage":"40Gi"}}}}'
# EBS volume resizes online — no pod restart needed with CSI driver

⚡ AWS EBS CSI Driver

The CSI (Container Storage Interface) driver is the bridge between Kubernetes and AWS EBS. Without it, Kubernetes can't provision, attach, or mount EBS volumes. On EKS it runs as an add-on.

bash
# Install EBS CSI driver as EKS managed add-on
# Step 1: Create IAM role for EBS CSI driver (using IRSA)
eksctl create iamserviceaccount \
  --name ebs-csi-controller-sa \
  --namespace kube-system \
  --cluster shopnow-cluster \
  --role-name AmazonEKS_EBS_CSI_DriverRole \
  --role-only \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve

# Step 2: Install the add-on
aws eks create-addon \
  --cluster-name shopnow-cluster \
  --addon-name aws-ebs-csi-driver \
  --service-account-role-arn arn:aws:iam::ACCOUNT_ID:role/AmazonEKS_EBS_CSI_DriverRole \
  --region ap-south-1

# Verify it's running
kubectl get pods -n kube-system | grep ebs
# ebs-csi-controller-xxx   6/6   Running   0   2m
# ebs-csi-node-xxx         3/3   Running   0   2m  (DaemonSet — on every node)

# Check storage classes available
kubectl get storageclass
# NAME            PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE
# gp2 (default)   kubernetes.io/aws-ebs   Delete          Immediate
# gp3             ebs.csi.aws.com         Retain          WaitForFirstConsumer
💡 EBS CSI vs in-tree driver: The old in-tree AWS EBS driver (kubernetes.io/aws-ebs) is deprecated since K8s 1.23. Always use the CSI driver (ebs.csi.aws.com) — it supports gp3, volume snapshots, volume resizing, and encryption with custom KMS keys.

EBS Volume Snapshots — Backup Strategy

YAMLvolume-snapshot.yaml
# Install snapshot CRDs and controller first:
# kubectl apply -f https://raw.githubusercontent.com/kubernetes-csi/external-snapshotter/master/client/config/crd/snapshot.storage.k8s.io_volumesnapshotclasses.yaml

# Create a SnapshotClass
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ebs-vsc
driver: ebs.csi.aws.com
deletionPolicy: Retain        # ← Keep EBS snapshot even if VolumeSnapshot object deleted
---
# Take a snapshot of the MySQL PVC
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: mysql-backup-2024-01-15
  namespace: shopnow
spec:
  volumeSnapshotClassName: ebs-vsc
  source:
    persistentVolumeClaimName: mysql-data-pvc   # ← Snapshot this PVC
---
# Restore snapshot to a new PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-restored
  namespace: shopnow
spec:
  dataSource:
    name: mysql-backup-2024-01-15
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  accessModes: [ReadWriteOnce]
  storageClassName: gp3
  resources:
    requests:
      storage: 20Gi

📁 AWS EFS — Shared Storage (ReadWriteMany)

AWS EBS (Block Storage)

  • ReadWriteOnce — 1 node at a time
  • AZ-specific — must be in same AZ as pod
  • High performance (gp3: 3000 IOPS)
  • Best for: databases, stateful single-pod apps
  • Priced per GB provisioned

AWS EFS (Network File System)

  • ReadWriteMany — unlimited pods across all AZs
  • Multi-AZ — no AZ affinity needed
  • Lower IOPS than EBS
  • Best for: shared config, media files, ML datasets
  • Priced per GB used (not provisioned)
bash
# Install EFS CSI driver
eksctl create iamserviceaccount \
  --name efs-csi-controller-sa \
  --namespace kube-system \
  --cluster shopnow-cluster \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEFSCSIDriverPolicy \
  --approve

aws eks create-addon \
  --cluster-name shopnow-cluster \
  --addon-name aws-efs-csi-driver \
  --region ap-south-1
YAMLefs-storageclass.yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: efs-sc
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap              # ← EFS Access Point (per-PVC subdirectory)
  fileSystemId: fs-0abc123def456789     # ← Your EFS File System ID from AWS Console
  directoryPerms: "700"                 # ← Permissions for the directory
  gidRangeStart: "1000"
  gidRangeEnd: "2000"
  basePath: "/shopnow"                  # ← Root path in EFS for this StorageClass
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-media-pvc
  namespace: shopnow
spec:
  accessModes:
  - ReadWriteMany                       # ← Multiple pods, multiple nodes, multiple AZs!
  storageClassName: efs-sc
  resources:
    requests:
      storage: 5Gi                      # ← EFS ignores this; you pay for actual usage
💡 When to use EFS: User-uploaded content (images, videos) accessed by multiple frontend pods across AZs. ML training data shared by multiple training pods. Application config files shared by a pod fleet. WordPress media directory. When you need ReadWriteMany — EFS is the go-to answer on AWS EKS.

⚙️ ConfigMap — Externalise Application Configuration

📖 Story

Your API server needs to know: which database host to connect to, the log level, the feature flags. Hardcoding these in the Docker image means rebuilding the image for every environment (dev, staging, prod). ConfigMaps decouple config from code — same image, different configs per environment.

YAMLapp-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: shopnow-config
  namespace: shopnow
data:
  # Simple key-value pairs (used as environment variables)
  APP_ENV: "production"
  LOG_LEVEL: "info"
  DB_HOST: "mysql-svc.shopnow.svc.cluster.local"
  DB_PORT: "3306"
  REDIS_HOST: "redis-svc.shopnow.svc.cluster.local"
  MAX_CONNECTIONS: "100"

  # Multi-line value (used as a mounted file)
  app.properties: |               # ← The | means multi-line string (literal block)
    server.port=8080
    spring.datasource.url=jdbc:mysql://mysql-svc:3306/shopnow
    spring.cache.type=redis
    feature.new-checkout=true

  nginx.conf: |                   # ← Full nginx config file stored in ConfigMap
    server {
      listen 80;
      location /api {
        proxy_pass http://api-svc:8080;
      }
    }

Two Ways to Use ConfigMaps in Pods

YAMLpod-using-configmap.yaml
spec:
  containers:
  - name: api
    image: shopnow/api:v2
    
    # ── METHOD 1: Inject ALL ConfigMap keys as environment variables ──
    envFrom:
    - configMapRef:
        name: shopnow-config      # ← APP_ENV, LOG_LEVEL, DB_HOST all become env vars

    # ── METHOD 2: Inject SPECIFIC key as a named env variable ──
    env:
    - name: DATABASE_HOST         # ← Your chosen env var name
      valueFrom:
        configMapKeyRef:
          name: shopnow-config
          key: DB_HOST            # ← Which ConfigMap key to read

    # ── METHOD 3: Mount ConfigMap as FILES in a volume ──
    volumeMounts:
    - name: config-files
      mountPath: /etc/shopnow     # ← Files appear here inside container
      readOnly: true

  volumes:
  - name: config-files
    configMap:
      name: shopnow-config
      items:
      - key: app.properties       # ← Mount only this key
        path: application.properties  # ← As this filename at /etc/shopnow/application.properties
      - key: nginx.conf
        path: nginx.conf          # ← /etc/shopnow/nginx.conf
envFrom vs env
envFrom imports ALL keys from the ConfigMap as env vars — convenient but be careful of key name collisions. env with configMapKeyRef imports a specific key with your own chosen variable name — more explicit and safe. Prefer env for critical configs.
Volume mount vs env var
Key difference: When ConfigMap is updated, file mounts refresh automatically (within ~60 seconds) — no pod restart needed. Environment variables are set at pod startup and NEVER update — you must restart the pod to pick up env changes. Use file mounts for hot-reloadable configs (nginx.conf, etc.).
⚠️ ConfigMap size limit: ConfigMaps are stored in etcd, which has a 1MB limit per object. For large config files (ML model parameters, big JSON configs), use a PVC or SSM Parameter Store instead.

🔐 Secrets — Managing Sensitive Data

⚠️ Critical misconception: Kubernetes Secrets are NOT encrypted by default. They are base64-encoded (which is just encoding, not encryption). Anyone with etcd access or kubectl get secret permissions can read them. We cover how to actually secure them in Part 5 and Section 7 below.
bash
# Create a secret imperatively (values auto-base64 encoded)
kubectl create secret generic db-credentials \
  --from-literal=username=shopnow_user \
  --from-literal=password=Sup3rS3cr3tP@ss! \
  -n shopnow

# Create from files (e.g., TLS certificate)
kubectl create secret tls shopnow-tls \
  --cert=cert.pem \
  --key=privkey.pem \
  -n shopnow

# Create Docker registry pull secret
kubectl create secret docker-registry ecr-pull-secret \
  --docker-server=123456789.dkr.ecr.ap-south-1.amazonaws.com \
  --docker-username=AWS \
  --docker-password=$(aws ecr get-login-password) \
  -n shopnow

# View a secret (base64 encoded)
kubectl get secret db-credentials -n shopnow -o yaml

# Decode a secret value
kubectl get secret db-credentials -n shopnow \
  -o jsonpath='{.data.password}' | base64 --decode
YAMLdb-secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: shopnow
type: Opaque                    # ← Generic secret. Other types:
                                #   kubernetes.io/tls (TLS certs)
                                #   kubernetes.io/dockerconfigjson (registry auth)
                                #   kubernetes.io/service-account-token
data:
  username: c2hvcG5vd191c2Vy  # ← base64("shopnow_user")
  password: U3VwM3JTM2NyM3RA UGFzcyE=  # ← base64("Sup3rS3cr3tP@ss!")

# OR use stringData (plain text — K8s encodes automatically on apply)
stringData:
  username: shopnow_user        # ← Plain text — never commit this to Git!

Using Secrets in Pods

YAMLpod-with-secrets.yaml
spec:
  containers:
  - name: api
    image: shopnow/api:v2
    
    # Method 1: Inject as environment variables
    env:
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: username
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: password
          optional: false         # ← Pod FAILS to start if secret missing (safe default)

    # Method 2: Mount as files (more secure — not exposed in process env)
    volumeMounts:
    - name: db-secret-vol
      mountPath: /etc/secrets
      readOnly: true              # ← Container cannot modify secret files

  volumes:
  - name: db-secret-vol
    secret:
      secretName: db-credentials
      defaultMode: 0400           # ← File permission: owner read-only (most restrictive)
      # Files created: /etc/secrets/username, /etc/secrets/password
      # App reads: password = open('/etc/secrets/password').read()
💡 Env vars vs file mounts for Secrets: File mounts are more secure — env vars can be accidentally logged, leaked in crash dumps, or exposed via /proc/<pid>/environ. Critical secrets (DB passwords, API keys) should always be mounted as files at defaultMode: 0400.

🔑 AWS Secrets Manager Integration (Secrets Store CSI Driver)

📖 Story — The Right Way

Storing secrets in etcd is risky. The production-grade approach: store secrets in AWS Secrets Manager (audited, rotatable, encrypted with KMS). Use the Secrets Store CSI Driver to mount them as files in pods automatically — zero secrets in Kubernetes, zero secrets in Git.

Production Secret Flow: AWS Secrets Manager Kubernetes Pod ┌──────────────────────┐ ┌─────────────────────────────┐ │ secret: db/password │ │ /mnt/secrets/db-password │ │ value: "abc123!" │──────────► │ (file contents: "abc123!") │ └──────────────────────┘ │ │ ▲ │ reads via open() │ │ IRSA (pod's IAM role) └─────────────────────────────┘ │ Secrets Store CSI Driver (DaemonSet on each node) fetches secret from AWS and mounts as file
bash
# Install Secrets Store CSI Driver
helm repo add secrets-store-csi-driver https://kubernetes-sigs.github.io/secrets-store-csi-driver/charts
helm install csi-secrets-store secrets-store-csi-driver/secrets-store-csi-driver \
  --namespace kube-system \
  --set syncSecret.enabled=true    # ← Also sync to K8s Secret objects

# Install AWS provider
kubectl apply -f https://raw.githubusercontent.com/aws/secrets-store-csi-driver-provider-aws/main/deployment/aws-provider-installer.yaml
YAMLsecretproviderclass.yaml
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: shopnow-aws-secrets
  namespace: shopnow
spec:
  provider: aws                    # ← Use AWS Secrets Manager
  parameters:
    objects: |
      - objectName: "shopnow/prod/db-password"   # ← Secret name in AWS Secrets Manager
        objectType: "secretsmanager"
        objectAlias: "db-password"                # ← Filename in the pod
      - objectName: "shopnow/prod/api-key"
        objectType: "secretsmanager"
        objectAlias: "api-key"
  secretObjects:                   # ← Also create a K8s Secret for apps that need env vars
  - secretName: db-secret-synced
    type: Opaque
    data:
    - objectName: "db-password"
      key: password
---
# Pod using AWS Secrets Manager via CSI
apiVersion: v1
kind: Pod
metadata:
  name: api-pod
  namespace: shopnow
spec:
  serviceAccountName: shopnow-api-sa   # ← Must have IRSA role with secretsmanager:GetSecretValue
  containers:
  - name: api
    image: shopnow/api:v2
    volumeMounts:
    - name: secrets-store
      mountPath: /mnt/secrets
      readOnly: true
    env:
    - name: DB_PASSWORD              # ← Optionally also inject as env var from synced K8s secret
      valueFrom:
        secretKeyRef:
          name: db-secret-synced
          key: password
  volumes:
  - name: secrets-store
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: shopnow-aws-secrets

🎯 Interview Q&A — Part 4

🎯 Interview Prep — 4 YOE Level

Q1: What is the difference between a ConfigMap and a Secret in Kubernetes?

A: ConfigMap stores non-sensitive configuration (app settings, env names, port numbers) as plain text key-value pairs or files. Secret stores sensitive data (passwords, tokens, certificates) with base64 encoding. Both can be injected as env vars or file mounts. The key differences: Secrets have type annotations (Opaque, TLS, docker-registry), are base64-encoded (not encrypted by default), can be encrypted at rest via etcd encryption or an external KMS, and kubectl describes them with values hidden. In production, Secrets should be backed by AWS Secrets Manager via the Secrets Store CSI Driver — never stored in Git.

Q2: Explain PV, PVC, and StorageClass. What is dynamic provisioning?

A: A PersistentVolume (PV) is a piece of storage provisioned by an admin or dynamically. A PersistentVolumeClaim (PVC) is a request for storage by a user — specifying size and access mode. A StorageClass defines the "type" of storage and its provisioner. Dynamic provisioning means: you create a PVC, the StorageClass's provisioner (e.g., EBS CSI) automatically creates the PV (and the AWS EBS volume) — no manual admin step needed. The PVC binds to the auto-created PV, and the pod mounts the PVC.

Q3: When would you use EBS vs EFS on EKS?

A: EBS (block storage): use for single-pod stateful workloads like databases (MySQL, PostgreSQL), since EBS is ReadWriteOnce — only one pod/node can mount at a time. It's AZ-specific, high performance. EFS (network file system): use when multiple pods across multiple AZs need to share the same filesystem — media uploads, ML training datasets, shared configuration files. EFS is ReadWriteMany. For anything database-like → EBS. For shared content needing multi-pod access → EFS.

Q4: If you update a ConfigMap, do running pods see the change automatically?

A: It depends on how the ConfigMap is used. If mounted as a volume file, pods receive the updated file within about 60 seconds (controlled by kubelet's sync period) — no restart needed, though the app must re-read the file to pick up changes. If injected as environment variables via envFrom or env.valueFrom, the pod NEVER sees the update — env vars are set at pod startup and are immutable for the lifetime of that pod. You must delete/restart the pod. Best practice: use file mounts for hot-reloadable configs.

Q5: How do you ensure Kubernetes Secrets are actually secure in production?

A: Base64 alone is not security. Production approach: (1) Enable etcd encryption at rest (EncryptionConfiguration with AES-CBC or KMS provider). (2) Use AWS Secrets Manager + Secrets Store CSI Driver — secrets never enter etcd at all. (3) Apply RBAC to limit who can kubectl get secret. (4) Enable audit logging to detect secret access. (5) Use IRSA so pods authenticate to AWS with IAM roles, not hardcoded credentials. (6) Rotate secrets regularly via AWS Secrets Manager automatic rotation. (7) Never put Secrets YAML (with stringData) in Git — use Sealed Secrets or External Secrets Operator.

  namespace: shopnow            # ← Only applies in this namespace
rules:
- apiGroups: [""]               # ← "" = core API group (pods, services, configmaps, secrets)
  resources: ["pods", "pods/log", "pods/exec"]  # ← Which resource types
  verbs: ["get", "list", "watch", "create"]     # ← Which actions are allowed
                                                 # ALL verbs: get|list|watch|create|update|patch|delete|exec
- apiGroups: ["apps"]           # ← apps API group (deployments, statefulsets)
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch"]   # ← Read-only for deployments

- apiGroups: [""]
  resources: ["secrets"]

- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "create", "update", "patch"]

- apiGroups: [""]
  resources: ["secrets"]
  verbs: []                      # ← Explicitly no secret access

🤖 ServiceAccounts & IRSA

A ServiceAccount is a Kubernetes identity for processes (pods), as opposed to a User identity for humans. Every pod runs under a ServiceAccount and gets its JWT token automatically mounted — used to authenticate to the K8s API Server and (via IRSA) to AWS.

YAMLserviceaccount-irsa.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: shopnow-api-sa
  namespace: shopnow
  annotations:
    # IRSA: Link this ServiceAccount to an AWS IAM Role
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/ShopNowAPIRole
    # When a pod uses this SA, AWS SDK automatically assumes ShopNowAPIRole
    # No AWS access keys needed in the container!
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shopnow-api
  namespace: shopnow
spec:
  template:
    spec:
      serviceAccountName: shopnow-api-sa   # ← Assign the ServiceAccount to the pod
      automountServiceAccountToken: true    # ← Mount JWT token at /var/run/secrets/...
      containers:
      - name: api
        image: shopnow/api:v2
        # AWS SDK inside this container can now call S3, DynamoDB, SES etc.
        # using the IAM role ShopNowAPIRole — no credentials needed!

Create the IAM Role for IRSA

bash
# Using eksctl (easiest)
eksctl create iamserviceaccount \
  --cluster=shopnow-cluster \
  --namespace=shopnow \
  --name=shopnow-api-sa \
  --attach-policy-arn=arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess \
  --attach-policy-arn=arn:aws:iam::aws:policy/AmazonSESFullAccess \
  --approve \
  --override-existing-serviceaccounts

# This creates the IAM role with a trust policy that only allows:
# 1. The OIDC provider of your EKS cluster
# 2. The specific ServiceAccount: shopnow/shopnow-api-sa
# Nobody else can assume this role!
💡 Why IRSA is better than node instance profiles: With instance profiles, ALL pods on a node share the same AWS permissions — a compromised pod gets all permissions. IRSA is per-ServiceAccount — each pod gets only the AWS permissions it specifically needs. Plus AWS CloudTrail shows which pod made which API call, not just "the node".
🔐 Default ServiceAccount: Every namespace has a default ServiceAccount. Pods that don't specify a ServiceAccount use it. Best practice: always create a dedicated ServiceAccount per application and set automountServiceAccountToken: false on the default SA to prevent accidental API access.

🔒 Pod Security — Standards & Security Contexts

📖 Story

A compromised pod running as root with hostNetwork and hostPath access can escape the container and own your EC2 node — and then every other pod on that node. Pod Security hardens the container runtime boundary so even a compromised pod is contained.

Pod Security Standards (PSS) — 3 Profiles

ProfileRestrictionsUse Case
privilegedNone — everything allowedSystem/infra namespaces only (kube-system, CNI)
baselineBlocks most known escapes (no hostNetwork, no privileged containers)Default for most workloads
restrictedStrict — must run as non-root, drop all capabilities, no privilege escalationHigh security: payments, PII data
bash
# Apply Pod Security Standards to a namespace via labels
kubectl label namespace shopnow \
  pod-security.kubernetes.io/enforce=baseline \     # ← Reject pods that violate
  pod-security.kubernetes.io/warn=restricted \      # ← Warn if violates restricted
  pod-security.kubernetes.io/audit=restricted        # ← Audit log violations

# Test: try to create a privileged pod in shopnow namespace
kubectl run bad-pod \
  --image=nginx \
  --overrides='{"spec":{"containers":[{"name":"nginx","image":"nginx","securityContext":{"privileged":true}}]}}' \
  -n shopnow
# Error: pod violates baseline policy: privileged containers not allowed

SecurityContext — Harden Individual Pods & Containers

YAMLsecure-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-api
  namespace: shopnow
spec:
  securityContext:               # ← Pod-level: applies to ALL containers
    runAsNonRoot: true           # ← Reject pod if image tries to run as UID 0 (root)
    runAsUser: 1000              # ← Force container to run as UID 1000 (non-root)
    runAsGroup: 3000             # ← Force GID 3000
    fsGroup: 2000                # ← Mounted volumes owned by GID 2000
    seccompProfile:
      type: RuntimeDefault       # ← Apply default seccomp profile (syscall filtering)
  
  containers:
  - name: api
    image: shopnow/api:v2
    securityContext:             # ← Container-level (more specific than pod-level)
      allowPrivilegeEscalation: false  # ← Can't sudo or setuid inside container
      readOnlyRootFilesystem: true     # ← Container filesystem is read-only
                                       #   Prevents malware writing to disk
      capabilities:
        drop: ["ALL"]            # ← Drop ALL Linux capabilities (NET_ADMIN, SYS_PTRACE etc.)
        add: ["NET_BIND_SERVICE"] # ← Re-add only what's needed (bind to port < 1024)
    
    volumeMounts:
    - name: tmp-dir
      mountPath: /tmp            # ← App needs to write tmp files — give it an emptyDir
    - name: cache-dir
      mountPath: /app/cache
  
  volumes:
  - name: tmp-dir
    emptyDir: {}                 # ← Writable scratch space (readOnlyRootFilesystem needs this)
  - name: cache-dir
    emptyDir: {}

Security Context Fields — Word by Word

runAsNonRoot: true
What it enforces: The container image's USER directive must be a non-zero UID. If the image runs as root (UID 0), Kubernetes rejects it with "container has runAsNonRoot and image will run as root". Your Dockerfile must have USER 1000 — enforce this in your base images.
readOnlyRootFilesystem: true
Why it matters: Prevents an attacker from writing malicious scripts to the container filesystem. If your app needs to write files, you must explicitly mount writable volumes (emptyDir for temp, PVC for persistence). This is a defense-in-depth measure — a compromised container can't easily persist malware.
capabilities: drop: ["ALL"]
Linux capabilities: Root in a container has many capabilities (CAP_NET_ADMIN, CAP_SYS_PTRACE, CAP_CHOWN etc.) that can be used for privilege escalation or container escape. Dropping ALL capabilities removes these even if the process runs as root — then add back only what's actually needed. Most web apps only need NET_BIND_SERVICE (port binding) or nothing extra.
allowPrivilegeEscalation: false
What it blocks: Prevents a process inside the container from gaining more privileges than its parent (no sudo, no setUID binaries, no su). Critical for preventing post-compromise escalation — even if an attacker runs code, they can't become root.

🚦 Admission Controllers & OPA/Gatekeeper

Admission Controllers intercept every request to the Kubernetes API Server before objects are persisted to etcd. They can mutate (modify) or validate (accept/reject) API requests. They are the enforcement layer for cluster policies.

kubectl apply ──► API Server ──► Authentication ──► Authorization (RBAC) │ ▼ Admission Controllers ┌─────────────────────┐ │ Mutating Webhooks │ ← modify objects │ (auto-inject sidecars,│ │ add labels, set defaults) │ │ │ Validating Webhooks │ ← accept/reject │ (OPA/Gatekeeper, │ │ Kyverno, PSA) │ └─────────────────────┘ │ Persist to etcd

OPA Gatekeeper — Policy as Code

bash
# Install OPA Gatekeeper
kubectl apply -f https://raw.githubusercontent.com/open-policy-agent/gatekeeper/master/deploy/gatekeeper.yaml
YAMLgatekeeper-policy.yaml
# ── Step 1: Define a ConstraintTemplate (the policy logic in Rego) ──
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: requiredlabels
spec:
  crd:
    spec:
      names:
        kind: RequiredLabels
      validation:
        openAPIV3Schema:
          type: object
          properties:
            labels:
              type: array
              items:
                type: string
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package requiredlabels
      violation[{"msg": msg}] {
        provided := {label | input.review.object.metadata.labels[label]}
        required := {label | label := input.parameters.labels[_]}
        missing := required - provided
        count(missing) > 0
        msg := sprintf("Missing required labels: %v", [missing])
      }
---
# ── Step 2: Apply the Constraint to enforce the policy ──
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: RequiredLabels
metadata:
  name: must-have-team-label
spec:
  match:
    kinds:
    - apiGroups: ["apps"]
      kinds: ["Deployment"]      # ← Apply to all Deployments
    namespaces: ["shopnow"]      # ← Only in shopnow namespace
  parameters:
    labels: ["team", "env", "version"]  # ← These labels are REQUIRED

# Now any Deployment without team, env, version labels is REJECTED at apply time

Kyverno — Simpler Policy Alternative

YAMLkyverno-policy.yaml
# Install Kyverno
helm repo add kyverno https://kyverno.github.io/kyverno/
helm install kyverno kyverno/kyverno -n kyverno --create-namespace

---

  name: require-resource-limits

  validationFailureAction: Enforce   # ← Enforce (reject) or Audit (warn only)
  background: false

  - name: check-resource-limits
    match:
      any:
      - resources:
          kinds: ["Pod"]

        spec:
          containers:

PART 5 · SECTION 16

🎯 Interview Q&A — Part 5 (Security & RBAC)

🎯 Interview Prep — 4 YOE Level

Q1: Explain Kubernetes RBAC. What are the four main objects involved?

A: RBAC (Role-Based Access Control) controls who can do what on which resources. The four objects: (1) Role — defines permissions (verbs on resources) within one namespace. (2) ClusterRole — same but cluster-wide, or for non-namespaced resources like Nodes and PVs. (3) RoleBinding — grants a Role or ClusterRole to a Subject within one namespace. (4) ClusterRoleBinding — grants a ClusterRole to a Subject across the entire cluster. Subjects can be Users (humans), Groups, or ServiceAccounts (pods).

Q2: What is IRSA and why is it the recommended way for pods to access AWS services?

A: IRSA (IAM Roles for Service Accounts) links a K8s ServiceAccount to an AWS IAM Role via the EKS OIDC provider. When a pod uses that ServiceAccount, the AWS SDK auto-fetches a short-lived token and assumes the IAM role. It's preferred over: node instance profiles (which give all pods on a node the same permissions) and hardcoded access keys (which never expire and risk leakage). IRSA enables least-privilege per pod, auto-rotates credentials (hourly), and provides CloudTrail attribution per pod identity.

Q3: What is a SecurityContext in Kubernetes? Give examples of important fields.

A: SecurityContext defines privilege and access control settings for pods and containers. Key fields: runAsNonRoot: true — rejects pods running as UID 0; readOnlyRootFilesystem: true — prevents writing to container filesystem; allowPrivilegeEscalation: false — blocks sudo and setuid inside container; capabilities.drop: [ALL] — removes all Linux capabilities; seccompProfile: RuntimeDefault — syscall filtering. Pod-level securityContext applies to all containers; container-level overrides it. Best practice: set runAsNonRoot and drop all capabilities on every production pod.

Q4: What are Admission Controllers? Name two you've used.

A: Admission Controllers intercept API Server requests before objects are persisted to etcd. They come in two types — Mutating (can modify the object, e.g., inject a sidecar, add default labels) and Validating (can accept or reject, e.g., enforce required labels, block privileged pods). Built-in examples: PodSecurity (enforces PSS profiles), ResourceQuota (blocks pods exceeding namespace quotas), LimitRanger (sets default resource limits). External webhook-based: OPA Gatekeeper (policy as Rego code), Kyverno (policy as YAML patterns), Istio (auto-inject Envoy sidecar). I've used Kyverno to enforce resource limits on all pods and OPA Gatekeeper to require team labels on all Deployments.

Q5: How would you prevent pods from accessing the AWS EC2 metadata endpoint (IMDS)?

A: EC2 IMDS (169.254.169.254) exposes the node's IAM role credentials — a malicious pod could steal node-level AWS permissions. Prevention options: (1) Use IMDSv2 with hop limit = 1 on EKS nodes (eksctl sets this by default) — pods can't reach IMDS because they're 2 hops away. (2) Block via NetworkPolicy: deny egress to 169.254.169.254/32. (3) Use IRSA — pods use their own pod-level role, not the node's. (4) AWS recommends IMDSv2 + hop limit 1 as the standard defense on EKS. With IRSA + hop limit 1, even a compromised pod can't steal node credentials.

Q6: What is the difference between a Role and a ClusterRole? When would you use ClusterRoleBinding with a Role?

A: A Role exists in a specific namespace and can only grant permissions on resources in that namespace. A ClusterRole has no namespace and can grant permissions on cluster-scoped resources (Nodes, PVs, Namespaces) or all namespaces. Trick answer: you CAN use a ClusterRole with a RoleBinding — the ClusterRole defines the permissions but the binding restricts them to one namespace. This is useful for reusing a common permission template (like "pod-reader") across multiple namespaces without duplicating Role objects. ClusterRoleBinding + ClusterRole = applies to ALL namespaces.
