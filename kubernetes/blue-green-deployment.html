1. The Business Scenario — Why This Project Exists

ShopNow Retail's Payment Service (the .NET service from Use Case 1) processes real money. A rolling update, even a perfect zero-downtime one, still means for a few minutes there are two different versions of the Payment Service running side by side, each potentially interpreting a transaction slightly differently if the new version changed how it talks to the payment gateway. Last quarter, a rolling update introduced a rounding difference in tax calculation, and for the six minutes both versions were live, roughly 40 orders were charged two different ways — a support and finance nightmare that took two weeks to fully reconcile.

Ramesh's ask this time is specific: "For anything touching money, I don't want a gradual mix of old and new pods ever again. I want the new version fully tested in production-like conditions, completely isolated from customers, and then flipped on for everyone in one atomic switch — and if anything looks wrong, I want to flip back in seconds, not minutes."

This is the exact business justification for Blue-Green Deployment, and it's a different tool from Use Case 3's rolling update — not a better one, a different one for a different problem. Knowing when to reach for which is exactly the kind of judgment call a senior engineer is expected to make, and exactly what this document will let you explain with confidence.

2. The Core Idea — Blue-Green vs Rolling Update

BLUE — Current Production

Full set of pods running the currently-live version. 100% of real customer traffic goes here right now.

GREEN — New Version

A completely separate, fully-scaled set of pods running the new version. Deployed and running, but receiving zero real customer traffic — reachable only internally for testing.

Once Green passes every validation check, one single change — updating which environment the Service's selector points to — instantly moves 100% of traffic from Blue to Green. There is no in-between state where both versions serve real customers at once. That is the single sentence that separates Blue-Green from everything in Use Case 3.

Rolling Update (Use Case 3)Blue-Green (this use case)
Old and new versions serving real traffic simultaneously?Yes, briefly, by designNever — it's one or the other, atomically
Extra compute cost during deploy?Small (1 extra pod via maxSurge)Large (a full second fleet running in parallel)
Can you fully test the new version under real-like load before any customer sees it?Not really — it takes live traffic as soon as it's ReadyYes — Green can be smoke-tested and load-tested while fully isolated
Rollback speedSeconds to minutes (reverse rolling update)Instant (flip the selector back)
Best fitMost stateless services, frequent deploysPayment, checkout, anything where a mixed-version window is unacceptable
Why not use Blue-Green for everything, then? Cost and complexity — running two full-scale fleets simultaneously means doubling your compute bill for the duration of every deploy, and database schema changes become much harder to reason about when two full versions might both be writing. This is why ShopNow uses Rolling Update for Cart Service and Catalog Service, but Blue-Green specifically for Payment Service — matching the deployment strategy to the actual risk of the workload is the senior-level judgment call here.

3. Application Architecture

                     Customer Browser
                             |
                   ALB (Ingress) - shopnow.com
                             |
              Kubernetes Service: payment-service-svc
                    selector: version=blue   ← the ONE line that decides everything
                        /            \
              [BLUE pods, live]   [GREEN pods, isolated]
              version=blue         version=green
              3 replicas            3 replicas
                    |                    |
              Real customer         payment-service-green-svc (internal only)
              transactions          used ONLY by QA/smoke tests, never by real users

The application itself is the same Payment Service (.NET 8) from Use Case 1 — Blue-Green is not a different application architecture, it's a different deployment architecture layered on top of the same service.

4. AWS Architecture

AWS ServiceRole in this project
EKSRuns both Blue and Green ReplicaSets simultaneously in the same namespace, distinguished by the version label
ALBSingle external entry point — it never knows Blue/Green exists, it only ever talks to one stable Service name
ECRTwo image tags live at once during a deployment window — e.g. payment-service:blue-v1.4.2 and payment-service:green-v1.5.0
RDS PostgreSQLOne database, shared by both Blue and Green — this is the detail requiring the most care (see the callout below)
CloudWatchSeparate log streams for Blue and Green pods so validation logs never mix with production logs
The hardest part of Blue-Green in real systems: the database. Both Blue and Green pods usually connect to the same RDS instance, because running two separate databases and keeping them in sync is its own huge problem. This means any database schema change deployed with Green must be backward-compatible with Blue — for example, adding a new nullable column is safe, but renaming or dropping a column Blue still reads from will break Blue while Green is being validated. This is exactly the kind of "gotcha" interviewers probe for when they ask "what's hard about Blue-Green in practice."

5. EKS Cluster Design

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: shopnow-cluster
  region: ap-south-1
  version: "1.29"
managedNodeGroups:
  - name: ng-payment-secure
    instanceType: m5.large
    desiredCapacity: 4      # sized for BOTH Blue and Green running together, not just Blue alone
    minSize: 4
    maxSize: 8
    labels: { workload: payment-secure }
    taints:
      - key: "dedicated"
        value: "payment"
        effect: "NoSchedule"

Note the node group is deliberately sized larger than Use Case 1's version — with 3 Blue replicas and 3 Green replicas both scheduled at once during a deployment window, you need headroom for 6 payment pods simultaneously, not 3. Under-sizing this is one of the most common Blue-Green mistakes: Green pods stuck Pending because nobody accounted for the doubled capacity need.

6. VPC and Networking

Same VPC and subnet layout as the earlier use cases — Blue and Green pods both run in the same private subnets, on the same tainted secure node group. There is no network-level separation between Blue and Green; the isolation is entirely at the Service selector layer, which is exactly what section 9 explains in detail.

8. Blue and Green Deployments — Full Manifests

Two separate Deployment objects, never one — this is the key structural difference from a rolling update, which uses a single Deployment. Each carries a distinct version label that the Service (section 9) will target.

# payment-service-blue-deployment.yaml — the CURRENT production version
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service-blue
  namespace: prod
  labels: { app: payment-service, version: blue }
spec:
  replicas: 3
  selector:
    matchLabels: { app: payment-service, version: blue }
  template:
    metadata:
      labels: { app: payment-service, version: blue }
    spec:
      serviceAccountName: payment-service-sa
      nodeSelector: { workload: payment-secure }
      tolerations:
        - key: "dedicated"
          operator: "Equal"
          value: "payment"
          effect: "NoSchedule"
      containers:
        - name: payment-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/payment-service:blue-v1.4.2
          ports: [{ containerPort: 8081 }]
          envFrom:
            - configMapRef: { name: payment-service-config }
            - secretRef: { name: payment-service-secret }
          resources:
            requests: { cpu: "200m", memory: "384Mi" }
            limits:   { cpu: "500m", memory: "768Mi" }
          readinessProbe: { httpGet: { path: /health/ready, port: 8081 }, initialDelaySeconds: 15, periodSeconds: 10 }
          livenessProbe:  { httpGet: { path: /health/live,  port: 8081 }, initialDelaySeconds: 20, periodSeconds: 20 }

# payment-service-green-deployment.yaml — the NEW version, identical shape, different label + image

      tolerations:
        - key: "dedicated"
          operator: "Equal"
          value: "payment"

          envFrom:
            - configMapRef: { name: payment-service-config }
            - secretRef: { name: payment-service-secret }
          resources:
            requests: { cpu: "200m", memory: "384Mi" }
            limits:   { cpu: "500m", memory: "768Mi" }
          readinessProbe: { httpGet: { path: /health/ready, port: 8081 }, initialDelaySeconds: 15, periodSeconds: 10 }
          livenessProbe:  { httpGet: { path: /health/live,  port: 8081 }, initialDelaySeconds: 20, periodSeconds: 20 }

Notice both Deployments' pod templates are almost byte-for-byte identical except for version: green vs version: blue and the image tag — this is deliberate. Any other difference between them (different resource limits, different node placement) would mean you aren't really testing Green under the same conditions Blue runs in, defeating the purpose of the validation step in section 10.

9. The Service Switch — How Traffic Actually Moves

# payment-service-svc.yaml — THE Service real customer traffic hits, via the ALB
apiVersion: v1
kind: Service
metadata: { name: payment-service-svc, namespace: prod }
spec:
  selector:
    app: payment-service
    version: blue    # <-- THIS LINE is the entire switch. Change to "green" to cut over.
  ports: [{ port: 80, targetPort: 8081 }]
---
# payment-service-green-svc.yaml — INTERNAL ONLY, used purely for validating Green before cutover
apiVersion: v1
kind: Service
metadata: { name: payment-service-green-svc, namespace: prod }
spec:
  selector: { app: payment-service, version: green }
  ports: [{ port: 80, targetPort: 8081 }]
  type: ClusterIP    # never attached to the Ingress/ALB

The switch itself, once Green is validated, is one command:

kubectl patch service payment-service-svc -n prod \
  -p '{"spec":{"selector":{"app":"payment-service","version":"green"}}}'
Why is this instant, with zero pod restarts? Nothing about the pods changes at all — Green's 3 pods were already running, already Ready, already warmed up before this command runs. All that changes is which pods the Service's internal iptables/IPVS rules point new connections to. This is the mechanical reason Blue-Green rollback (section 22) can be instant: flipping the selector back to blue is the same one-line patch, and Blue's pods never stopped running in the first place.

10. Validating Green Before the Switch

This is the step that actually earns the trust to flip traffic — Green is fully deployed and Ready, but only reachable through the internal-only payment-service-green-svc, so you can hammer it exactly like production without any real customer ever touching it.

# smoke_test_green.py — runs a realistic transaction flow against Green only
import requests, sys

GREEN_URL = "http://payment-service-green-svc.prod.svc.cluster.local"

def run_smoke_tests():
    checks = []

    r = requests.get(f"{GREEN_URL}/health/ready")
    checks.append(("health check", r.status_code == 200))

    r = requests.post(f"{GREEN_URL}/api/payments/authorize", json={
        "amount": 499.00, "currency": "INR", "card_test_token": "tok_test_visa"
    })
    checks.append(("test authorization", r.status_code == 200 and r.json().get("status") == "authorized"))

    r = requests.post(f"{GREEN_URL}/api/payments/refund", json={"transaction_id": r.json().get("transaction_id")})
    checks.append(("test refund", r.status_code == 200))

    failed = [name for name, ok in checks if not ok]
    if failed:
        print("SMOKE TEST FAILED:", failed)
        sys.exit(1)
    print("ALL SMOKE TESTS PASSED — Green is safe to promote")

if __name__ == "__main__":
    run_smoke_tests()

# Also load test Green in isolation before trusting it with real traffic volume
kubectl run load-test --image=williamyeh/hey --restart=Never -n prod -- \
  -z 2m -c 30 http://payment-service-green-svc.prod.svc.cluster.local/api/payments/authorize
Manual UAT gate: beyond automated smoke tests, ShopNow's process requires the QA lead to manually test 5 real-world scenarios (successful payment, declined card, timeout from the gateway, refund, partial refund) against payment-service-green-svc using a port-forward, and sign off in the pipeline's approval step before anyone is allowed to flip the Service selector.

11. PodDisruptionBudget for Both Environments

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: payment-service-blue-pdb, namespace: prod }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: payment-service, version: blue } }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: payment-service-green-pdb, namespace: prod }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: payment-service, version: green } }

Both get their own PDB, scoped by the version label, because a node drain during the validation window shouldn't be allowed to wipe out Green mid-testing any more than it should be allowed to wipe out live Blue traffic.

13. Ingress with AWS Load Balancer Controller

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: payment-service-ingress
  namespace: prod
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:111122223333:certificate/xxxx
spec:
  rules:
    - host: shopnow.com
      http:
        paths:
          - path: /api/payments
            pathType: Prefix
            backend:
              service: { name: payment-service-svc, port: { number: 80 } }

The Ingress only ever points at payment-service-svc — the single stable Service name from section 9. It has no idea Blue or Green exist; the entire Blue-Green mechanism is invisible above the Service layer, which is exactly why the switch is safe and instant.

# Only the ALB target group and Order Service may reach whichever version is LIVE
# — the policy targets the app label, not the version label, so it automatically

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-order-and-alb-to-payment, namespace: prod }
spec:
  podSelector: { matchLabels: { app: payment-service } }

    - from: [{ podSelector: { matchLabels: { app: order-service } } }, {}]

17. CI/CD Pipeline — Jenkins and GitHub Actions

// Jenkinsfile — Blue-Green pipeline for Payment Service
pipeline {
  agent any
  environment {
    ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/payment-service"
    GREEN_TAG = "green-${GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Test') { steps { sh 'dotnet test' } }

    stage('Build & Push Green Image') {
      steps {
        sh '''
          docker build -t $ECR_REPO:$GREEN_TAG .
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:$GREEN_TAG
        '''
      }
    }

    stage('Deploy Green (isolated, no live traffic)') {
      steps {
        sh '''
          kubectl set image deployment/payment-service-green payment-service=$ECR_REPO:$GREEN_TAG -n prod
          kubectl rollout status deployment/payment-service-green -n prod --timeout=180s
        '''
      }
    }

    stage('Smoke Test Green') {
      steps { sh 'python3 smoke_test_green.py' }
    }

    stage('Manual UAT Sign-off') {
      steps {
        timeout(time: 60, unit: 'MINUTES') {
          input message: 'QA lead: has Green passed manual UAT? Approve to switch traffic.', submitter: 'qa-leads'
        }
      }
    }

    stage('Switch Traffic to Green') {
      steps {
        sh 'kubectl patch service payment-service-svc -n prod -p \\'{"spec":{"selector":{"app":"payment-service","version":"green"}}}\\''
      }
    }

    stage('Post-Switch Verification') {
      steps { sh 'python3 verify_live_traffic.py --url https://shopnow.com/api/payments/health --duration 120' }
    }

    stage('Report & Notify') {
      steps {
        sh 'python3 generate_report.py --service payment-service --status success --build ${BUILD_NUMBER}'
        sh 'python3 send_email.py --service payment-service --report report.html'
      }
    }
  }
  post {
    failure {
      sh '''
        echo "Switching back to Blue due to pipeline failure"
        kubectl patch service payment-service-svc -n prod -p '{"spec":{"selector":{"app":"payment-service","version":"blue"}}}'
      '''
      sh 'python3 send_email.py --service payment-service --status FAILED --build ${BUILD_NUMBER}'
    }
  }
}

# .github/workflows/blue-green-deploy.yml
name: Payment Service Blue-Green Deploy
on: { workflow_dispatch: {} }
jobs:
  deploy-green:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::111122223333:role/gha-eks-deploy, aws-region: ap-south-1 }
      - name: Update kubeconfig
        run: aws eks update-kubeconfig --name shopnow-cluster --region ap-south-1
      - name: Deploy Green
        run: |
          kubectl set image deployment/payment-service-green payment-service=$ECR_REGISTRY/payment-service:green-${{ github.sha }} -n prod
          kubectl rollout status deployment/payment-service-green -n prod --timeout=180s
      - name: Smoke test Green
        run: python3 smoke_test_green.py
  switch-traffic:
    needs: deploy-green
    runs-on: ubuntu-latest
    environment: production-switch   # separate GitHub Environment holding the required-reviewer rule
    steps:
      - name: Flip selector to Green
        run: kubectl patch service payment-service-svc -n prod -p '{"spec":{"selector":{"app":"payment-service","version":"green"}}}'

18. Argo CD GitOps for Blue-Green

# Two Argo CD Applications so Green can be synced/deployed independently of Blue
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: payment-service-blue, namespace: argocd }
spec:
  project: default
  source: { repoURL: https://github.com/shopnow/gitops-repo.git, targetRevision: main, path: services/payment-service/blue }
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy: {}
---
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: payment-service-green, namespace: argocd }
spec:
  project: default
  source: { repoURL: https://github.com/shopnow/gitops-repo.git, targetRevision: main, path: services/payment-service/green }
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy: { automated: { prune: true, selfHeal: false } }   # Green auto-deploys since it's isolated and safe to update freely

The Service selector patch from section 9 is deliberately kept outside of Argo CD's automated sync — it's the one manual, deliberate action in this whole pipeline, executed only after the human UAT sign-off, which is why it's a separate pipeline stage rather than something Argo CD does on its own.

The Grafana dashboard has a $version template variable (blue/green) so you can watch Green's error rate and latency in complete isolation from Blue's live production numbers during the validation window — then, right after the traffic switch, watch the same panel filtered to version=green flip from "test traffic only" to "100% of production" and confirm the numbers stay healthy under real load.

21. Running the Code — Full End-to-End Workflow

Step 1 — Confirm Blue is currently live and healthy

kubectl get deployment payment-service-blue -n prod
kubectl get service payment-service-svc -n prod -o jsonpath='{.spec.selector}'
# Expect: {"app":"payment-service","version":"blue"}
curl -s https://shopnow.com/api/payments/health

Step 2 — Deploy Green with the new version, fully isolated

kubectl apply -f payment-service-green-deployment.yaml
kubectl apply -f payment-service-green-svc.yaml
kubectl apply -f payment-service-green-hpa.yaml
kubectl apply -f payment-service-green-pdb.yaml

kubectl rollout status deployment/payment-service-green -n prod --timeout=180s
kubectl get pods -n prod -l version=green
# Expect: 3/3 Running, 3/3 Ready — and note NONE of this affects real traffic yet

Step 3 — Validate Green from inside the cluster only

# Port-forward for manual QA testing
kubectl port-forward svc/payment-service-green-svc -n prod 8081:80
# now hit http://localhost:8081/api/payments/... from Postman for manual UAT

# Automated smoke test
kubectl run smoke-test --image=python:3.11-slim --restart=Never -n prod --rm -it -- \
  sh -c "pip install requests -q && python3 -c \"$(cat smoke_test_green.py)\""

# Load test Green in isolation
kubectl run load-test --image=williamyeh/hey --restart=Never -n prod --rm -- \
  -z 2m -c 30 http://payment-service-green-svc.prod.svc.cluster.local/api/payments/authorize

Step 4 — Get sign-off, then switch traffic

# Only after smoke tests pass AND QA lead approves in the pipeline's manual gate:
kubectl patch service payment-service-svc -n prod \
  -p '{"spec":{"selector":{"app":"payment-service","version":"green"}}}'

# Confirm the switch took effect immediately
kubectl get service payment-service-svc -n prod -o jsonpath='{.spec.selector}'
# Expect: {"app":"payment-service","version":"green"}

kubectl get endpoints payment-service-svc -n prod
# Confirm the endpoint IPs now match Green's pod IPs, not Blue's

Step 5 — Watch real traffic on Green immediately after the switch

python3 verify_live_traffic.py --url https://shopnow.com/api/payments/health --duration 120
# Same style script as Use Case 3's zero-downtime checker — confirms the switch
# itself introduced no failed requests

kubectl logs -n prod -l version=green -f --tail=50
# Watch real production traffic hitting Green pods live, for the first time

Step 6 — Once confident, decommission old Blue (after a safe soak period)

# ShopNow's policy: keep old Blue running, unused, for 24 hours before deleting —
# it's the fastest possible rollback path if a subtle issue surfaces after the switch
sleep 86400
kubectl delete deployment payment-service-blue -n prod
kubectl delete hpa payment-service-blue-hpa -n prod
kubectl delete pdb payment-service-blue-pdb -n prod

23. Rollback Strategy — The Instant Switch Back

# The entire rollback, start to finish, if something looks wrong after the switch:
kubectl patch service payment-service-svc -n prod \
  -p '{"spec":{"selector":{"app":"payment-service","version":"blue"}}}'

# That's it. Blue's 3 pods never stopped running, so this is a live cutover back,
# not a redeploy — typically complete in under 5 seconds end to end.
This is the headline benefit stated back in section 1: compare this one-line, sub-5-second rollback to the rolling-update rollback in Use Case 3, which — while also safe — still has to run an actual reverse rollout across every pod. Blue-Green rollback has no rollout to run at all, because the old version was never taken down.

      vars: { version_label: green }

    - name: Render the stable Service pointing at Blue by default

      vars: { active_version: blue }

    - name: Render the internal Green-only validation Service
      template: { src: templates/green-service.yaml.j2, dest: "gitops-repo/services/{{ service_name }}/green-service.yaml" }

    - name: Apply everything
      kubernetes.core.k8s: { state: present, src: "gitops-repo/services/{{ service_name }}/" }

26. HTML Deployment/Job Report

# generate_report.py — shows both colors side by side, plus which one is currently live
import argparse, subprocess, json, datetime

def get_active_version(service_svc, ns="prod"):
    out = subprocess.run(["kubectl", "get", "svc", service_svc, "-n", ns, "-o", "json"], capture_output=True, text=True)
    return json.loads(out.stdout)["spec"]["selector"].get("version", "unknown")

def build_report(service, build_no, status):
    active = get_active_version(f"{service}-svc")
    color = "#5ec98f" if status == "success" else "#e35d5d"
    active_color = "#3a7bd5" if active == "blue" else "#3fb87a"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Blue-Green Deploy Report — {service} (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <h3 style="color:{active_color}">Currently LIVE: {active.upper()}</h3>
    </body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.service, args.build, args.status)

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(service, status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] {service} Blue-Green switch - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, payments-team@shopnow.com"
    msg.attach(MIMEText(f"Service: {service}\nBuild: #{build_no}\nStatus: {status}\n\nRollback command if needed:\nkubectl patch service {service}-svc -n prod -p '{{\\"spec\\":{{\\"selector\\":{{\\"version\\":\\"blue\\"}}}}}}'", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.service, args.status, args.build, args.report)

Notice the rollback command is included directly in the email body — the goal is that anyone on the payments team who sees a problem right after a switch doesn't need to go find documentation, the exact command to undo it is sitting in their inbox.
