SECTION 1

🏢 The Story — Why Kubernetes Exists

📖 Real-World Story

Imagine you're an engineer at a startup called ShopNow. Your app runs on a single EC2 server. Black Friday arrives — traffic spikes 100x. Your server crashes. Orders are lost. The CEO calls. This is the problem Kubernetes was built to solve.

The Evolution: From Bare Metal → Containers → Kubernetes

Let's walk through every stage to understand why each layer was invented:

EraHow apps ranProblem it created
1990s–2000s One app per physical server Wasted 90% of server capacity, slow to provision
2000s–2010s Virtual Machines (VMware, EC2) Better utilization, but VMs are heavy (GBs), slow to start (mins)
2013+ Docker Containers Lightweight (MBs), fast (seconds). But: who manages 1000 containers?
2014+ Kubernetes (K8s) Orchestrates containers at scale — auto-heal, auto-scale, zero-downtime deploy

What Kubernetes Does (The 5 Superpowers)

⚙️

Orchestration

Decides which server (node) runs which container automatically.

🔄

Self-Healing

Detects crashed containers and restarts them automatically within seconds.

📈

Auto-Scaling

Adds/removes container replicas based on CPU, memory, or custom metrics.

🚢

Rolling Deploys

Updates apps with zero downtime — new pods come up before old ones go down.

🌐

Service Discovery

Every service gets a stable DNS name — no hardcoded IPs needed.

💡 Mental Model: Think of Kubernetes as an operating system for your data center. Just like Linux manages CPU, RAM, and processes on one machine — Kubernetes manages CPU, RAM, and containers across a fleet of machines.

🏗️ Kubernetes Architecture — The Brain & The Workers

📖 Story Analogy

Think of K8s as a restaurant. The Control Plane is the management office (takes orders, decides who cooks what). The Worker Nodes are the kitchen staff (actually cook and serve). You (the developer) are the customer — you describe what you want, the system makes it happen.

Control Plane Components — Explained Word by Word

1. kube-apiserver — The Front Door

Every command you run (kubectl apply, kubectl get pods) hits the API Server first. It is the single source of truth gateway. It validates requests, authenticates users, and writes state to etcd.

Why it matters: Nothing in Kubernetes happens without going through the API Server. Every component (scheduler, kubelet, controller) only talks to the API Server — never directly to each other. This is the hub-and-spoke design.

2. etcd — The Memory

etcd is a distributed, strongly-consistent key-value store. It stores all cluster state — every pod, service, secret, configmap. If etcd is lost, the cluster's brain is wiped.

Interview fact: etcd uses the Raft consensus algorithm to guarantee that data is consistent across multiple etcd replicas. In production, you run 3 or 5 etcd nodes.

3. kube-scheduler — The Placement Engine

When a new Pod is created, it starts as Pending (no node assigned). The Scheduler watches for Pending pods and picks the best node based on: available CPU/RAM, node affinity rules, taints/tolerations, and topology spread constraints.

4. kube-controller-manager — The Robot Army

This runs a collection of controllers, each watching for a specific type of desired state vs actual state mismatch:

  • ReplicaSet Controller: "I want 3 pods. I see 2. Create 1 more."
  • Node Controller: "Node #3 hasn't reported in 40 seconds. Mark it NotReady."
  • Endpoint Controller: "A new pod matched Service X's selector. Add its IP to the endpoints."

Worker Node Components

kubelet — The Node Agent

Each worker node runs a kubelet. It constantly watches the API Server for pods assigned to its node, then tells the container runtime (containerd/Docker) to start/stop containers. It also reports node health back to the API Server.

kube-proxy — The Network Plumber

Maintains iptables / IPVS rules on every node so that traffic to a Service's ClusterIP gets load-balanced to the correct Pod IPs. Without kube-proxy, Services wouldn't route traffic.

Container Runtime — The Engine

The software that actually runs containers. Modern K8s uses containerd (Docker was deprecated as runtime in K8s 1.24+). EKS uses containerd by default.

🎯 Interview Q&A — Architecture

Q: What happens when you run kubectl apply -f deployment.yaml?

A: 1) kubectl sends an HTTP POST to the API Server. 2) API Server authenticates & validates the request. 3) API Server writes the desired state to etcd. 4) The Deployment Controller detects the new Deployment and creates a ReplicaSet. 5) The ReplicaSet Controller creates Pod objects. 6) The Scheduler assigns each Pod to a Node. 7) kubelet on that Node sees the Pod assignment, pulls the image, and starts the container. 8) kubelet updates Pod status back to API Server.

Q: What is the difference between kubelet and kube-proxy?

A: kubelet manages the pod lifecycle (start/stop containers). kube-proxy manages network rules so Services route traffic to the correct pods. They are separate agents on every worker node.

SECTION 4

📦 Core Kubernetes Objects — The Building Blocks

Everything in Kubernetes is an object — a record of desired state stored in etcd. You declare what you want in YAML, and Kubernetes makes it real. Let's learn the hierarchy:

Namespace (logical boundary) └── Deployment (manages ReplicaSets → rolling updates) └── ReplicaSet (ensures N pods always run) └── Pod (1 or more containers — the smallest unit) └── Container (your Docker image) Service (stable network endpoint → load balances to pods) ConfigMap (non-sensitive config → mounted as env/file in pods) Secret (sensitive config → base64 encoded, mounted as env/file) PersistentVolume / PersistentVolumeClaim (storage) Ingress (HTTP/S routing → external traffic to Services)

Pod — The Atomic Unit

A Pod is the smallest deployable unit. It wraps one or more containers that share: network namespace (same IP), storage volumes, and lifecycle. In 99% of cases, one container per pod.

YAML simple-pod.yaml 
apiVersion: v1          # ← Which API group/version this object belongs to
kind: Pod               # ← What type of object this is
metadata:               # ← Data ABOUT the object (not the app itself)
  name: my-nginx        # ← Unique name within the namespace
  namespace: default    # ← Logical group (like a folder)
  labels:               # ← Key-value tags used for selection
    app: nginx
    env: dev
spec:                   # ← The DESIRED STATE — what you want
  containers:           # ← List of containers in this pod
  - name: nginx         # ← Container name (for logs, exec)
    image: nginx:1.25   # ← Docker image to run (repo:tag)
    ports:
    - containerPort: 80 # ← Document which port app listens on (informational)
    resources:          # ← CPU/Memory limits (critical for scheduling!)
      requests:         # ← Minimum guaranteed resources
        cpu: "100m"     # ← 100 millicores = 0.1 CPU core
        memory: "128Mi" # ← 128 Mebibytes of RAM
      limits:           # ← Maximum allowed resources
        cpu: "500m"     # ← 0.5 CPU core max
        memory: "256Mi" # ← 256 MiB max (OOMKilled if exceeded)

Word-by-Word Code Annotation

apiVersion: v1
What it is: Declares the Kubernetes API version. v1 is the core stable API containing Pods, Services, ConfigMaps. Other groups: apps/v1 (Deployments), networking.k8s.io/v1 (Ingress).
kind: Pod
What it is: The object type. K8s uses this to know which controller/schema to validate against. Valid kinds: Pod, Deployment, Service, ConfigMap, Secret, Ingress, PVC, etc.
metadata.labels
What it is: Arbitrary key-value pairs attached to objects. Used by selectors in Services and Deployments to find pods. Without labels, Services can't route traffic to your pods.
resources.requests.cpu: "100m"
What it is: The Scheduler uses requests to decide placement — it finds a node with at least 100m free CPU. If you skip requests, the scheduler has no info and may over-pack nodes.
resources.limits.memory: "256Mi"
What it is: If the container uses more than 256Mi RAM, the Linux kernel's OOM killer terminates it → pod restarts. This prevents one rogue pod from starving the whole node.

Deployment — The Recommended Way to Run Apps

You rarely create Pods directly. A Deployment manages them — ensuring N replicas always run, handling rolling updates, and enabling rollbacks.

YAML nginx-deployment.yaml 
apiVersion: apps/v1          # ← Deployments live in the 'apps' API group
kind: Deployment
metadata:
  name: nginx-deploy
  namespace: default
spec:
  replicas: 3                # ← Always keep 3 pods running
  selector:                  # ← How the Deployment FINDS its pods
    matchLabels:
      app: nginx             # ← Match pods that have label app=nginx
  strategy:
    type: RollingUpdate      # ← Update pods gradually, not all at once
    rollingUpdate:
      maxSurge: 1            # ← Temporarily allow 1 extra pod (4 total) during update
      maxUnavailable: 0      # ← Never go below 3 running pods (zero downtime!)
  template:                  # ← Blueprint for each Pod the Deployment creates
    metadata:
      labels:
        app: nginx           # ← MUST match selector.matchLabels above
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
        livenessProbe:       # ← K8s restarts container if this fails
          httpGet:
            path: /          # ← HTTP GET to / should return 200
            port: 80
          initialDelaySeconds: 10  # ← Wait 10s before first check
          periodSeconds: 5         # ← Check every 5s
        readinessProbe:      # ← K8s removes pod from Service if this fails
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 3
🔑 Critical Concept — livenessProbe vs readinessProbe:
livenessProbe answers: "Is this container alive?" → If NO: restart it.
readinessProbe answers: "Is this container ready to serve traffic?" → If NO: remove from Service endpoints (stop sending traffic, but don't restart).
In production, ALWAYS define both probes.

Service — Stable Networking for Pods

Pod IPs change every time they restart. A Service gives a stable virtual IP (ClusterIP) and DNS name that load-balances to matching pods.

YAML nginx-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: nginx-svc         # ← DNS name within cluster: nginx-svc.default.svc.cluster.local
  namespace: default
spec:
  type: ClusterIP         # ← Internal only (default). Other types: NodePort, LoadBalancer
  selector:
    app: nginx            # ← Route traffic to pods with label app=nginx
  ports:
  - protocol: TCP
    port: 80              # ← Port the Service listens on (what clients call)
    targetPort: 80        # ← Port on the Pod to forward to
Service TypeAccessible FromUse Case
ClusterIPInside cluster onlyInternal microservice communication
NodePortVia any node's IP + portDev/test, not for production
LoadBalancerInternet via AWS ALB/NLBExposing services publicly
ExternalNameDNS alias to external URLIntegrating external services

Lab 1B: Create a Real EKS Cluster on AWS (Optional — has cost ~$0.10/hr)

1

Create EKS cluster with eksctl — one command does everything (VPC, subnets, node group, IAM roles):

bashcluster.yaml
# First, create a cluster config file
cat > cluster.yaml <<'EOF'
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: shopnow-cluster      # Your cluster name
  region: ap-south-1         # Mumbai region (closest for India)
  version: "1.29"            # K8s version

managedNodeGroups:
  - name: ng-workers
    instanceType: t3.medium  # 2 vCPU, 4GB RAM (~$0.04/hr each)
    minSize: 2               # Minimum 2 nodes (for HA)
    maxSize: 5               # Scale up to 5 nodes
    desiredCapacity: 2
    volumeSize: 20           # 20GB EBS per node
    ssh:
      allow: false           # No SSH for security
    labels:
      role: worker
    tags:
      environment: learning
EOF

# Create the cluster (takes ~15 minutes)
eksctl create cluster -f cluster.yaml

# After creation, test kubectl connection
kubectl get nodes
# NAME                                          STATUS   ROLES    AGE   VERSION
# ip-192-168-X-X.ap-south-1.compute.internal   Ready    <none>   2m    v1.29.0
# ip-192-168-Y-Y.ap-south-1.compute.internal   Ready    <none>   2m    v1.29.0

🎯 Interview Questions & Answers — Part 1

🎯 Interview Prep — 4 YOE Level

Q1: Explain the Kubernetes control plane and its components.

A: The control plane is the brain of Kubernetes. It has 4 key components: (1) kube-apiserver — the only gateway; all components communicate through it. (2) etcd — distributed key-value store holding all cluster state. (3) kube-scheduler — assigns Pending pods to nodes based on resources and constraints. (4) kube-controller-manager — runs controllers (ReplicaSet, Node, Endpoint) that continuously reconcile desired vs actual state.

Q2: What is the difference between a Pod and a Deployment?

A: A Pod is the smallest unit — it runs one or more containers. A Deployment is a higher-level controller that manages a ReplicaSet, which manages Pods. The Deployment ensures N replicas are always running, handles rolling updates with zero downtime, and enables rollbacks. You should always use Deployments (not bare Pods) for stateless apps in production.

Q3: How does Kubernetes handle container failures?

A: When a container crashes, kubelet detects it and restarts it based on the pod's restartPolicy (default: Always). If a pod itself is deleted/crashes and it belongs to a ReplicaSet, the ReplicaSet Controller creates a replacement Pod. The livenessProbe also periodically checks container health and triggers a restart if it fails — catching stuck/deadlocked containers that haven't crashed but aren't functional.

Q4: What is the role of etcd? What happens if etcd goes down?

A: etcd stores all cluster state — every API object (pods, services, secrets, configmaps). If etcd goes down: the API Server cannot read/write state, so kubectl commands fail. Existing pods CONTINUE RUNNING because they're managed by kubelet locally. But no new pods can be scheduled, services can't be updated, and no state changes happen. This is why production etcd runs as a 3 or 5-node cluster using Raft consensus.

Q5: What is the difference between livenessProbe and readinessProbe?

A: livenessProbe checks if the container is alive. If it fails, kubelet kills and restarts the container. Use it for deadlock detection. readinessProbe checks if the container is ready to serve traffic. If it fails, Kubernetes removes the pod from the Service's endpoints (no traffic sent), but doesn't restart it. Use it for startup warmup or temporary unavailability. A container can be alive but not ready.

Q6: What is the difference between ClusterIP, NodePort, and LoadBalancer services?

A: ClusterIP (default) — only accessible within the cluster, used for internal microservice communication. NodePort — exposes the service on a static port on every node's IP (30000–32767), useful for dev/test. LoadBalancer — provisions a cloud load balancer (AWS NLB/ALB on EKS), giving a public IP/DNS. In EKS production, we use LoadBalancer type with the AWS Load Balancer Controller or use an Ingress controller.

Q7: In AWS EKS, what does AWS manage and what do you manage?

A: AWS manages: the Control Plane (API Server, etcd, Controller Manager, Scheduler), HA across AZs, version patching for the control plane. You manage: Worker Nodes (EC2 instances, OS patches, AMI updates unless using Managed Node Groups), the container images, Kubernetes YAML manifests, networking add-ons (AWS VPC CNI, CoreDNS), storage drivers (EBS CSI), and the AWS Load Balancer Controller.
