1. The Business Scenario — Why This Project Exists

ShopNow Retail's Catalog Service (the Python/FastAPI service from Use Case 1) had a Blue-Green deploy go strange three weeks ago. Green passed every smoke test and every manual UAT scenario cleanly — but under the real, chaotic mix of actual customer search queries at 7 PM on a weekday, a subtle change to how the search-ranking algorithm handled queries with special characters caused a slow memory leak that only showed up after about twenty minutes of real production load. By the time anyone noticed rising latency, 100% of customers were already on the leaking version, because Blue-Green had already switched everyone over in one shot.

Ramesh's ask this time: "I don't want an all-or-nothing switch for services where the risk is 'this behaves subtly wrong under real traffic patterns we can't fully simulate in testing.' I want new versions to earn more traffic gradually — start small, watch the numbers, and only let it grow if the numbers stay healthy. And I want the growing and the watching to happen automatically, not depend on someone staring at a dashboard at 7 PM."

This is Canary Deployment with Progressive Traffic — the third and most gradual of the three deployment strategies in this series. Where Blue-Green is a single all-or-nothing switch validated before the switch, Canary is a series of small, increasing switches validated continuously during the rollout, using real production traffic itself as the test.

2. The Core Idea — Canary vs Blue-Green vs Rolling Update

Stage 1
V1: 90%  |  V2: 10%
Stage 2
V1: 75%  |  V2: 25%
Stage 3
V1: 50%  |  V2: 50%
Stage 4
V1: 0%  |  V2: 100%

Between every stage above, an automated check runs against error rate, p95 latency, and CPU usage. If the new version ("the canary") looks healthy, traffic advances to the next stage. If it looks unhealthy at any point, the rollout pauses or automatically rolls back to 0% canary traffic — before most customers were ever exposed.

Rolling UpdateBlue-GreenCanary (this use case)
How much real traffic sees the new version before full rollout?Grows as fast as pods become Ready0%, until one instant 100% switchA small %, growing in controlled, measured steps
How is "is the new version okay" decided?Only readiness probesPre-switch smoke tests + manual UATContinuous automated metric analysis against live production traffic
Blast radius if the new version is subtly brokenAll pods eventually, but caught fast via probes100% of customers, immediately, if pre-switch testing missed itCapped at whatever % it reached before the gate caught it — often just 10%
Best fitMost stateless services, routine deploysPayment/checkout — needs a clean atomic cutoverCatalog/search/recommendation — behavior only fully knowable under real traffic mix
Why Catalog Service is the right fit for Canary, specifically. Its risk profile is exactly "looks fine in every test, misbehaves only under the messy variety of real customer queries" — the opposite of Payment Service's risk profile, which is "must never process the same transaction two different ways, so no mixed-version window is acceptable at all." Matching deployment strategy to actual risk shape is the same judgment call from Use Case 4, applied to a different kind of risk.

The weighted ALB Target Group split is the actual mechanism behind the percentages in the diagram. "10% traffic to canary" isn't a Kubernetes-native concept at the Service layer the way the Blue-Green selector switch was in Use Case 4 — the AWS Load Balancer Controller, driven by Argo Rollouts, adjusts the weight

8. Introducing Argo Rollouts — Why Plain Kubernetes Isn't Enough

Plain Kubernetes has exactly one built-in Deployment strategy that matters for traffic control: RollingUpdate, based on pod counts, not percentages, and with no concept of "pause here and check metrics before continuing." Trying to hand-build a percentage-based, metric-gated, multi-stage progressive rollout out of raw Deployments and Services means writing and babysitting your own custom controller — a serious undertaking. Argo Rollouts is a Kubernetes controller, installed once on the cluster, that replaces the Deployment object with a Rollout object supporting exactly this: canary steps, weights, pauses, and automated analysis, all declared in YAML.
# One-time cluster install
kubectl create namespace argo-rollouts
kubectl apply -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml

# kubectl plugin for visualizing rollouts (very useful during the workflow steps later)
kubectl argo rollouts version

9. The Rollout Manifest — Full Progressive Canary Steps

# catalog-service-rollout.yaml — replaces the plain Deployment from Use Case 1
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: catalog-service
  namespace: prod
spec:
  replicas: 10
  selector:
    matchLabels: { app: catalog-service }
  template:
    metadata: { labels: { app: catalog-service } }
    spec:
      serviceAccountName: catalog-service-sa
      containers:
        - name: catalog-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/catalog-service:prod-v1.9.4
          ports: [{ containerPort: 8000 }]
          envFrom:
            - configMapRef: { name: catalog-service-config }
            - secretRef: { name: catalog-service-secret }
          resources:
            requests: { cpu: "150m", memory: "256Mi" }
            limits:   { cpu: "500m", memory: "512Mi" }
          readinessProbe: { httpGet: { path: /health, port: 8000 }, initialDelaySeconds: 5, periodSeconds: 10 }
  strategy:
    canary:
      canaryService: catalog-service-canary-svc
      stableService: catalog-service-stable-svc
      trafficRouting:
        alb:
          ingress: catalog-service-ingress
          servicePort: 80
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: catalog-service-health-check
        - setWeight: 25
        - pause: { duration: 5m }
        - analysis:
            templates:
              - templateName: catalog-service-health-check
        - setWeight: 50
        - pause: { duration: 10m }
        - analysis:
            templates:
              - templateName: catalog-service-health-check
        - setWeight: 100

Reading this steps list top to bottom is reading the exact sequence from section 2's diagram: weight 10, wait 5 minutes, run the automated health check, and only if it passes does the controller move to the next line — weight 25, wait, check again — all the way to 100. If any analysis step fails, Argo Rollouts automatically halts and, depending on configuration, either pauses indefinitely for a human to look, or rolls the weight back to 0.

10. AnalysisTemplate — Automated Metric Gates

# catalog-service-analysistemplate.yaml — the actual "monitor errors, latency, CPU" logic
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: catalog-service-health-check
  namespace: prod
spec:
  metrics:
    - name: error-rate
      interval: 1m
      successCondition: result < 0.02      # error rate must stay under 2%
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus-server.monitoring.svc.cluster.local
          query: |
            sum(rate(http_requests_total{app="catalog-service",version="canary",status=~"5.."}[2m]))
            /
            sum(rate(http_requests_total{app="catalog-service",version="canary"}[2m]))

    - name: p95-latency
      interval: 1m
      successCondition: result < 400        # p95 latency must stay under 400ms
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus-server.monitoring.svc.cluster.local
          query: |
            histogram_quantile(0.95,
              sum(rate(http_request_duration_seconds_bucket{app="catalog-service",version="canary"}[2m])) by (le)
            ) * 1000

    - name: cpu-usage
      interval: 1m
      successCondition: result < 75          # average CPU utilization must stay under 75%
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus-server.monitoring.svc.cluster.local
          query: |
            avg(rate(container_cpu_usage_seconds_total{pod=~"catalog-service-canary.*"}[2m])) * 100

Three metrics, three questions, all asked automatically every minute against only the canary pods' data — exactly matching the business ask in the original request ("monitor errors, latency, and CPU usage before increasing traffic"):

error-rate < 2%
Is the canary actually failing requests more than we'd tolerate?
p95-latency < 400ms
Is the canary noticeably slower for real users?
cpu-usage < 75%
Is the canary a resource hog that will fall over under full load?

failureLimit: 2 means a metric is allowed to fail its check up to twice (to tolerate normal noise) before Argo Rollouts treats the whole analysis as failed and halts the promotion — this is what stops a single brief network blip from unfairly killing an otherwise-healthy canary.

11. Stable and Canary Services, and Weighted Routing

apiVersion: v1
kind: Service
metadata: { name: catalog-service-stable-svc, namespace: prod }
spec:
  selector: { app: catalog-service }   # Argo Rollouts injects a rollouts-pod-template-hash label automatically
  ports: [{ port: 80, targetPort: 8000 }]
---
apiVersion: v1
kind: Service
metadata: { name: catalog-service-canary-svc, namespace: prod }
spec:
  selector: { app: catalog-service }
  ports: [{ port: 80, targetPort: 8000 }]

Unlike Use Case 4's manual Service-selector patch, here you never touch these Services by hand — the Argo Rollouts controller automatically manages which pods each Service's selector matches (using a hash label it adds to each ReplicaSet) and automatically updates the ALB Target Group weights behind the Ingress from section 14 to match whatever setWeight value the current step specifies. This is the entire value of adopting the tool instead of hand-rolling the same idea.

12. PodDisruptionBudget

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: catalog-service-pdb, namespace: prod }
spec:
  minAvailable: 7      # out of 10 total replicas across stable+canary combined
  selector: { matchLabels: { app: catalog-service } }

One PDB targeting the shared app: catalog-service label covers both stable and canary pods together, since a node drain during a canary rollout shouldn't be allowed to push the combined healthy pod count below a safe floor, regardless of how traffic happens to be split between the two versions at that moment.

14. Ingress with AWS Load Balancer Controller

# catalog-service-ingress.yaml — Argo Rollouts manages the weighted forward-actions
# on this Ingress automatically; you only declare the base routing rule once
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: catalog-service-ingress
  namespace: prod
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:111122223333:certificate/xxxx
spec:
  rules:
    - host: shopnow.com
      http:
        paths:
          - path: /api/catalog
            pathType: Prefix
            backend:
              service: { name: catalog-service-stable-svc, port: { number: 80 } }

You write this Ingress pointing at the stable Service exactly once. From that point on, Argo Rollouts rewrites the underlying ALB listener rule's forward action behind the scenes to include both Target Groups with the current step's weight — you never manually edit percentages into this file again after the initial setup.

15. HPA and Autoscaling

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: catalog-service-hpa, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: argoproj.io/v1alpha1, kind: Rollout, name: catalog-service }
  minReplicas: 10
  maxReplicas: 30
  metrics: [{ type: Resource, resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } } }]

Note scaleTargetRef.kind is Rollout, not Deployment — Argo Rollouts implements the scale subresource so the HPA can target it exactly the same way it would a normal Deployment, scaling the total pod count while Argo Rollouts separately manages how that total is split between stable and canary based on the current step's weight.

16. NetworkPolicies

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-alb-to-catalog, namespace: prod }
spec:
  podSelector: { matchLabels: { app: catalog-service } }
  policyTypes: [Ingress]

18. CI/CD Pipeline — Jenkins and GitHub Actions

// Jenkinsfile
pipeline {
  agent any
  environment {
    ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/catalog-service"
    IMAGE_TAG = "canary-${GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Test') { steps { sh 'pytest' } }
    stage('Build & Push') {
      steps {
        sh '''
          docker build -t $ECR_REPO:$IMAGE_TAG .
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:$IMAGE_TAG
        '''
      }
    }
    stage('Trigger Progressive Rollout') {
      steps {
        sh '''
          kubectl argo rollouts set image catalog-service catalog-service=$ECR_REPO:$IMAGE_TAG -n prod
        '''
      }
    }
    stage('Watch Rollout Progress') {
      steps {
        sh 'kubectl argo rollouts status catalog-service -n prod --timeout 1800s'
        // this call blocks and only returns success once weight has reached 100%
        // and returns failure automatically if Argo Rollouts aborts the rollout
      }
    }
    stage('Report & Notify') {
      steps {
        sh 'python3 generate_report.py --service catalog-service --status success --build ${BUILD_NUMBER}'
        sh 'python3 send_email.py --service catalog-service --report report.html'
      }
    }
  }
  post {
    failure {
      sh 'kubectl argo rollouts abort catalog-service -n prod'
      sh 'python3 send_email.py --service catalog-service --status FAILED --build ${BUILD_NUMBER}'
    }
  }
}

23. Failure Testing — Proving Auto-Rollback Works

# Test 1: Deploy a canary that deliberately returns 500s on 15% of requests
# and confirm the error-rate gate catches it and halts before 25% weight
kubectl argo rollouts set image catalog-service catalog-service=...:canary-broken-errors -n prod
kubectl get analysisrun -n prod -w
# Expected: AnalysisRun shows error-rate metric flip to Failed within ~2 minutes,
# and the Rollout status shows "Degraded" — weight never advances past 10%

# Test 2: Deploy a canary with an artificial CPU-hogging bug
kubectl argo rollouts set image catalog-service catalog-service=...:canary-cpu-bug -n prod
# Expected: cpu-usage metric fails the <75% threshold, rollout halts automatically

# Test 3: Confirm stable pods are completely unaffected while canary is failing
curl -s https://shopnow.com/api/catalog/health
# Still 200 OK throughout — 90% (or more, if the gate caught it at step 1) of
# customers never touched the broken version at all

24. Rollback Strategy

# Automatic — this is the headline behavior: an AnalysisTemplate failure aborts
# the Rollout on its own, no human action required, weight returns to 0% canary

# Manual abort at any stage, any time a human wants to stop it early:
kubectl argo rollouts abort catalog-service -n prod

# Full undo back to the previous stable revision:
kubectl argo rollouts undo catalog-service -n prod

# GitOps version — revert the image tag in Git, Argo CD re-syncs the Rollout spec:
cd gitops-repo/services/catalog-service
git revert <bad-commit-sha> && git push
The core promise of this use case, restated precisely: in Use Case 3 and 4, rollback is something a human or a pipeline stage triggers after noticing a problem. Here, for the metrics explicitly named in the original ask — errors, latency, CPU — rollback can happen with zero human involvement, often within one or two minutes of the metric crossing its threshold, capping exposure at whatever the current step's traffic weight was.

# bootstrap-canary-rollout.yml — converts an existing plain Deployment service
# to a canary-enabled Rollout with sensible default steps and thresholds
- name: Migrate a service to Argo Rollouts canary strategy
  hosts: localhost
  gather_facts: false
  vars:
    service_name: "{{ svc }}"

  tasks:
    - name: Render Rollout manifest from existing Deployment spec
      template: { src: templates/rollout.yaml.j2, dest: "gitops-repo/services/{{ service_name }}/rollout.yaml" }

    - name: Render default AnalysisTemplate
      template: { src: templates/analysistemplate.yaml.j2, dest: "gitops-repo/services/{{ service_name }}/analysistemplate.yaml" }
      vars:
        error_rate_threshold: 0.02
        latency_threshold_ms: 400
        cpu_threshold_pct: 75

    - name: Render stable and canary Services
      template: { src: templates/service.yaml.j2, dest: "gitops-repo/services/{{ service_name }}/{{ item }}-svc.yaml" }
      loop: [stable, canary]

    - name: Apply everything
      kubernetes.core.k8s: { state: present, src: "gitops-repo/services/{{ service_name }}/" }

27. HTML Deployment/Job Report

# generate_report.py — shows the step-by-step weight progression and gate results
import argparse, subprocess, json, datetime

def get_rollout_status(service, ns="prod"):
    out = subprocess.run(["kubectl", "get", "rollout", service, "-n", ns, "-o", "json"], capture_output=True, text=True)
    return json.loads(out.stdout)

def build_report(service, build_no, status):
    r = get_rollout_status(service)
    current_step = r["status"].get("currentStepIndex", "?")
    weight = r["status"].get("canary", {}).get("weights", {}).get("canary", "?")
    phase = r["status"].get("phase", "Unknown")
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Canary Deploy Report — {service} (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <p>Final Phase: {phase} | Final Step Reached: {current_step} | Final Canary Weight: {weight}%</p>
    </body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.service, args.build, args.status)

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(service, status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] {service} canary rollout - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, catalog-team@shopnow.com"
    body = f"Service: {service}\nBuild: #{build_no}\nStatus: {status}\n\n"
    if status != "success":
        body += "Rollout was auto-aborted or halted by an analysis gate. Check AnalysisRun details:\nkubectl describe analysisrun -n prod\n"
    msg.attach(MIMEText(body, "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.service, args.status, args.build, args.report)
