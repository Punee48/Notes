1. The Business Scenario — Why This Project Exists

ShopNow Retail's Frontend Service had a rough week. Marketing wanted a small feature flag flipped — turn off the "Buy Now Pay Later" banner for QA testing while a partnership issue got sorted out — and the only way the on-call engineer knew how to do it was to change a hard-coded constant in the React code, rebuild the Docker image, push to ECR, and run the full deploy pipeline. What should have been a thirty-second change took forty-five minutes, required a full CI run, and — because the change was baked into the image itself — the exact same slow process had to be repeated separately for Dev, QA, UAT, and Prod, four times, for one boolean flag.

Ramesh's ask: "Application URLs, log levels, feature flags, API endpoints — none of that should ever require rebuilding a Docker image. I want us to be able to change a config value and just restart the pods, in seconds, per environment, without touching the image at all."

This is exactly the problem ConfigMaps exist to solve, and it's one of the most fundamental — and most asked-about in interviews — Kubernetes concepts precisely because almost every engineer has lived through the "why did we bake config into the image" pain at least once.

2. The Core Idea — What a ConfigMap Actually Solves

The rule this whole use case is built around: a Docker image should be environment-agnostic — the exact same image, byte for byte, should be deployable to Dev, QA, UAT, and Prod. Anything that differs between those environments — a URL, a log level, a flag, an endpoint — does not belong baked into the image. It belongs in a ConfigMap, injected into the container at pod-start time.

This single rule is what makes "build once, deploy many times" — the foundation of every CI/CD pipeline in this whole document series — actually true. Without it, you'd need a separate image build per environment, which defeats the entire point of a build pipeline and, worse, means the exact artifact you tested in QA is not byte-for-byte the same one you eventually ship to Prod.

Belongs in the Docker imageBelongs in a ConfigMap (or Secret)
Application code, compiled binariesApplication URLs (dev.shopnow.com vs shopnow.com)
Language runtime, OS packagesLog level (debug in Dev, warn in Prod)
Static assets bundled at build timeFeature flags (enable new checkout: true/false)
Fixed business logicExternal API endpoints (sandbox vs live payment gateway)
 Any other environment variable that differs by environment

The rule that keeps this structure honest: nothing under base/ ever mentions an environment name, a specific URL, or a specific flag value. 8. IAM Roles and IRSA

# Only needed for pulling SECRETS (see section 10) — plain ConfigMaps need no AWS
# IAM permission at all, since they are native Kubernetes objects with no AWS backing
eksctl create iamserviceaccount --cluster shopnow-cluster --namespace prod \
  --name frontend-service-sa \
  --attach-policy-arn arn:aws:iam::111122223333:policy/frontend-service-secrets-policy --approve
Worth stating explicitly in an interview: ConfigMaps are pure Kubernetes objects — they need zero AWS IAM permissions to read, because kubelet mounts them directly from the Kubernetes API server. IRSA only enters this use case because of the Secrets half (section 10), not the ConfigMap half. Conflating the two is a common mistake to avoid saying out loud on a call.

9. ConfigMaps — All Four Environments, Explained Line by Line

# overlays/dev/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-service-config

data:

apiVersion: v1

data:
  APP_URL: "https://uat.shopnow.com"
  API_BASE_URL: "https://uat.shopnow.com/api"
  LOG_LEVEL: "info"
  FEATURE_NEW_CHECKOUT: "true"
  FEATURE_BNPL_BANNER: "true"
  FEATURE_DARK_MODE: "false"
  PAYMENT_GATEWAY_ENDPOINT: "https://staging.paygateway.com"

# overlays/prod/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: frontend-service-config, namespace: prod }
data:
  APP_URL: "https://shopnow.com"
  API_BASE_URL: "https://shopnow.com/api"
  LOG_LEVEL: "warn"
  FEATURE_NEW_CHECKOUT: "false"   # not yet enabled for real customers — still soaking in UAT
  FEATURE_BNPL_BANNER: "true"
  FEATURE_DARK_MODE: "false"
  PAYMENT_GATEWAY_ENDPOINT: "https://live.paygateway.com"

Notice all four ConfigMaps have exactly the same keys, only the values differ — this consistency is deliberate and important: the application code reads a fixed, known set of environment variable names (APP_URL, LOG_LEVEL, and so on) regardless of which environment it's running in, and never needs to know or care which environment that actually is.

1Same key set across environments means the same Deployment manifest (from the shared base/ folder) works unmodified everywhere — only the ConfigMap referenced changes per overlay.
2Feature flags as plain strings ("true"/"false"), not native YAML booleans — this is intentional. Kubernetes ConfigMap data values are always strings; the application code is responsible for parsing "true" into an actual boolean. Forgetting this and writing FEATURE_X: true (unquoted) is a very common real-world mistake worth mentioning if asked about ConfigMap gotchas.
3PAYMENT_GATEWAY_ENDPOINT differs by environment — this is a non-sensitive URL (not a credential), so it correctly belongs in the ConfigMap; the actual API key used to authenticate against that endpoint belongs in a Secret instead, covered next.

10. Secrets — What Never Goes in a ConfigMap

# overlays/prod/external-secret.yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: frontend-service-secret, namespace: prod }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets-manager, kind: ClusterSecretStore }
  target: { name: frontend-service-secret }
  data:
    - secretKey: PAYMENT_GATEWAY_API_KEY
      remoteRef: { key: shopnow/prod/payment-gateway-key }
    - secretKey: ANALYTICS_WRITE_KEY
      remoteRef: { key: shopnow/prod/analytics-write-key }
The line that separates a ConfigMap value from a Secret value: "would I be comfortable with this value showing up in a git log that every engineer on the team can read?" A log level, a feature flag, a public API URL — yes. An API key, a database password, any credential — no, ever. ConfigMaps are stored in plaintext in both Git and the Kubernetes API (etcd); they were never designed for confidentiality, only for configuration.

11. Consuming Config — envFrom vs env vs Volume Mounts

There are three different ways a pod can actually receive ConfigMap data, and knowing when to use which is a real interview differentiator:

# Method 1: envFrom — inject EVERY key in the ConfigMap as an environment variable.
# Simplest, used when the app just wants all config values available as env vars.
      containers:
        - name: frontend-service
          envFrom:
            - configMapRef: { name: frontend-service-config }
            - secretRef:    { name: frontend-service-secret }

# Method 2: env with valueFrom — pick individual keys, optionally rename them.
# Used when you only need a couple of specific values, or need a different env var name.
      containers:
        - name: frontend-service
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef: { name: frontend-service-config, key: LOG_LEVEL }
            - name: STRIPE_STYLE_GATEWAY_KEY   # renamed on the way in
              valueFrom:
                secretKeyRef: { name: frontend-service-secret, key: PAYMENT_GATEWAY_API_KEY }

# Method 3: Volume mount — mount the ConfigMap as FILES inside the container.
# Used for config that isn't a simple key=value (a full nginx.conf, a JSON feature-flag file).
      containers:
        - name: frontend-service
          volumeMounts:
            - name: nginx-config
              mountPath: /etc/nginx/conf.d
      volumes:
        - name: nginx-config
          configMap: { name: frontend-nginx-config }
MethodBest forKey behavior difference
envFromSimple flat config, most of this use caseRequires a pod restart to pick up any change — env vars are only read once, at container start
env + valueFromSelective values, renamingSame restart requirement as envFrom, but explicit and self-documenting per variable
Volume mountWhole config files, structured JSON/YAML configKubernetes automatically updates the mounted file's contents in-place within about a minute of a ConfigMap change — no pod restart needed, if the app watches the file for changes

This last row is the most important nuance in the entire use case, and it directly connects to section 14's "update without rebuilding" requirement — the mechanism (restart vs auto-refresh) depends entirely on which of these three methods you chose.

12. Kustomize Overlays — One Base, Four Environments

# base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
  - hpa.yaml
  - pdb.yaml
  - networkpolicy.yaml
  - ingress.yaml

# overlays/prod/kustomization.yaml
resources:
  - ../../base
  - configmap.yaml
  - external-secret.yaml
namespace: prod
patches:
  - path: patch-replicas.yaml
    target: { kind: Deployment, name: frontend-service }

# overlays/prod/patch-replicas.yaml
- op: replace
  path: /spec/replicas
  value: 6

This is Kustomize doing exactly what the folder structure in section 3 promises: kubectl kustomize overlays/prod combines the shared base/ manifests with prod's own ConfigMap, Secret reference, and replica-count patch into one final, environment-specific set of objects — without a single copy-pasted Deployment file anywhere in the repo.

13. Deployment and Service

# base/deployment.yaml — references the ConfigMap/Secret by NAME only,
# never by environment — the actual object each name resolves to depends
# entirely on which overlay/namespace this gets applied into
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-service
  labels: { app: frontend-service }
spec:
  replicas: 2
  selector: { matchLabels: { app: frontend-service } }
  template:
    metadata:
      labels: { app: frontend-service }
      annotations:
        configHash: "PLACEHOLDER"   # see section 14 — Kustomize replaces this automatically
    spec:
      serviceAccountName: frontend-service-sa
      containers:
        - name: frontend-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/frontend-service:v2.3.0
          ports: [{ containerPort: 80 }]
          envFrom:
            - configMapRef: { name: frontend-service-config }
            - secretRef: { name: frontend-service-secret }
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "300m", memory: "256Mi" }
          readinessProbe: { httpGet: { path: /health, port: 80 }, initialDelaySeconds: 5, periodSeconds: 10 }
---
apiVersion: v1
kind: Service
metadata: { name: frontend-service-svc }
spec:
  selector: { app: frontend-service }
  ports: [{ port: 80, targetPort: 80 }]

Note the image tag v2.3.0 stays fixed across every environment overlay — that is the entire point being proven here: the same tested, promoted artifact runs everywhere, and only its surrounding ConfigMap changes.

14. Updating Config Without Rebuilding — Restart and Hot-Reload

Here is exactly how "update configurations without rebuilding the application image" actually happens, both the simple way and the smarter way.

The simple way — edit and restart

# Change the value directly
kubectl edit configmap frontend-service-config -n qa
# or, GitOps-correct way: edit overlays/qa/configmap.yaml, commit, push

# Pods do NOT automatically pick up envFrom/env changes — they must restart
kubectl rollout restart deployment/frontend-service -n qa
kubectl rollout status deployment/frontend-service -n qa

This restart is itself a normal RollingUpdate (same mechanism as Use Case 3) — so even "just restart the pods to pick up new config" is zero-downtime by default, as long as the Deployment still has its RollingUpdate strategy, readiness probes, and PDB in place from that earlier use case.

The smarter way — automatic restart triggered by the config change itself

# overlays/qa/kustomization.yaml — Kustomize's configMapGenerator with a hash suffix
configMapGenerator:
  - name: frontend-service-config
    literals:
      - APP_URL=https://qa.shopnow.com
      - LOG_LEVEL=info
      - FEATURE_BNPL_BANNER=false
generatorOptions:
  disableNameSuffixHash: false
What this does, in plain words: instead of a ConfigMap always named frontend-service-config, Kustomize generates a name like frontend-service-config-8f2c4d6b, where that suffix is a hash of the actual content. Change one value, the hash changes, the ConfigMap gets a brand-new name — and because the Deployment references that generated name, Kubernetes sees the Deployment spec itself as changed and automatically triggers a rolling restart, with zero need for the manual kubectl rollout restart command above. This is the single most useful Kustomize feature for this exact use case, and it directly prevents a real, common bug: forgetting to restart pods after a ConfigMap edit and wondering why the change "didn't take effect."

The volume-mount way — true zero-restart hot reload

Referring back to section 11's Method 3: if FEATURE_DARK_MODE and similar flags were instead delivered as a mounted JSON file (/etc/config/feature-flags.json) and the application code watches that file with a filesystem watcher, Kubernetes updates the file contents in place roughly once a minute — the running application process picks up the new flag value without restarting at all. This is the technique real feature-flag-heavy frontends use for flags that need to change instantly without any deploy event whatsoever.

20. CI/CD Pipeline — Jenkins and GitHub Actions

// Jenkinsfile — notice there is NO per-environment build stage; only one build,
// then four different "apply the right overlay" deploy stages
pipeline {
  agent any
  environment { ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/frontend-service" }
  stages {
    stage('Test') { steps { sh 'npm ci && npm test' } }
    stage('Build ONE Image') {
      steps {
        sh '''
          docker build -t $ECR_REPO:${GIT_COMMIT} .
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:${GIT_COMMIT}
        '''
      }
    }
    stage('Deploy to Dev') { steps { sh 'kubectl apply -k gitops-repo/services/frontend-service/overlays/dev' } }
    stage('Deploy to QA')  { steps { sh 'kubectl apply -k gitops-repo/services/frontend-service/overlays/qa' } }
    stage('Approve UAT')   { steps { input message: 'Promote same image to UAT?' } }
    stage('Deploy to UAT') { steps { sh 'kubectl apply -k gitops-repo/services/frontend-service/overlays/uat' } }
    stage('Approve Prod')  { steps { input message: 'Promote same image to Prod?', submitter: 'release-managers' } }
    stage('Deploy to Prod') { steps { sh 'kubectl apply -k gitops-repo/services/frontend-service/overlays/prod' } }
    stage('Report & Notify') {
      steps {
        sh 'python3 pipeline-scripts/generate_report.py --status success --build ${BUILD_NUMBER}'
        sh 'python3 pipeline-scripts/send_email.py --report report.html'
      }
    }
  }
}

# .github/workflows/deploy.yml
name: Frontend Service Config-Aware Deploy

23. CloudWatch Logging

apiVersion: v1
kind: ConfigMap
metadata: { name: fluent-bit-config, namespace: amazon-cloudwatch }

  output.conf: |
    [OUTPUT]
        Name                cloudwatch_logs

        auto_create_group   true

Because LOG_LEVEL itself is a ConfigMap-controlled value, Dev's CloudWatch log group fills up with verbose debug lines while Prod's stays lean — this is a direct, visible payoff of the whole use case: one config change (LOG_LEVEL: debug in an overlay) measurably changes real operating cost and log noise, entirely without touching code.

26. Rollback Strategy

# Because every config change is a Git commit, rollback is a Git revert, same as code:
cd gitops-repo/services/frontend-service/overlays/qa
git log --oneline -5
git revert <bad-config-commit-sha>
git push
# Argo CD (or the next pipeline run) re-applies, generates a new hash, rolls pods back

# Emergency direct rollback without waiting for Git/Argo CD:
kubectl apply -f gitops-repo/services/frontend-service/overlays/qa/configmap.yaml.bak
kubectl rollout restart deployment/frontend-service -n qa

29. HTML Deployment/Job Report

# generate_report.py — shows config diffs across environments in one view
import argparse, subprocess, json, datetime

ENVS = ["dev", "qa", "uat", "prod"]

def get_config(ns):
    out = subprocess.run(
        ["kubectl", "get", "configmap", "-n", ns, "-l", "app=frontend-service", "-o", "json"],
        capture_output=True, text=True
    )
    items = json.loads(out.stdout)["items"]
    return items[0]["data"] if items else {}

def build_report(build_no, status):
    all_config = {env: get_config(env) for env in ENVS}
    keys = sorted({k for cfg in all_config.values() for k in cfg})
    rows = ""
    for key in keys:
        cells = "".join(f"<td>{all_config[e].get(key,'-')}</td>" for e in ENVS)
        rows += f"<tr><td>{key}</td>{cells}</tr>"
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Frontend Config Report — Build #{build_no}</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>Key</th><th>Dev</th><th>QA</th><th>UAT</th><th>Prod</th></tr>
      {rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.build, args.status)

This report is genuinely useful beyond just this pipeline run — it's a live cross-environment config diff, letting a release manager instantly spot, for example, a feature flag that's accidentally still true in Prod when it should have been turned off after a campaign ended.

30. Email Notification

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] frontend-service config report - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, frontend-team@shopnow.com"
    msg.attach(MIMEText(f"Build: #{build_no}\nStatus: {status}\n\nSee attached cross-environment config diff.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
