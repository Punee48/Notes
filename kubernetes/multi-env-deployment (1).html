1. The Business Scenario — Why This Project Exists

ShopNow Retail runs an online store. Every festival season — Diwali, Republic Day sale, End of Season Sale — the engineering team ships fifteen to twenty code changes a week. In the old world, all of this went through one shared server. A developer's half-finished feature would sit next to the code going live for customers. Twice last quarter, an untested change reached production and the checkout page went down for eleven minutes during a flash sale. The VP of Engineering lost trust in the release process, and your manager, Ramesh, was asked one direct question in the leadership review: "Why don't we have separate environments like every other serious company?"

Ramesh gives you the task in a one-line message: "Puneeth, set up proper Dev, QA, UAT and Prod environments on our EKS cluster. Same application, same pipeline, but each environment must be isolated — its own namespace, its own config, its own secrets, its own approval gate before Prod."

This is not a toy exercise. This is the exact problem every mid-size and large company solves with Kubernetes namespaces, GitOps, and pipeline promotion gates. Understanding this end-to-end is what separates a 2-year engineer who can write a YAML file from a 4+ year engineer who can design a release process.

Why namespaces and not four separate clusters? Four clusters means four control planes to patch, four sets of IAM roles, four times the operational cost. One cluster with four namespaces gives you logical isolation (network policies, resource quotas, RBAC) at a fraction of the cost and operational burden — this is exactly why almost every real company does it this way, and exactly why interviewers ask "namespace vs cluster isolation, when would you choose which."

2. Application Architecture

The application ShopNow runs is a simple three-tier web app, deliberately kept realistic rather than complicated, because in interviews you must be able to explain every box you draw:

Customer Browser
→
ALB (Ingress)
→
Frontend Pods (React, served via Nginx)
→
Backend API Pods (Node.js / Spring Boot style REST API)
→
RDS PostgreSQL (managed, outside the cluster)

Only the frontend and backend run as Kubernetes Deployments inside EKS. The database is deliberately kept as a managed AWS RDS instance per environment — this mirrors real companies, where stateful databases are almost never run inside Kubernetes for production workloads because of the operational complexity of managing persistent storage, backups, and failover by hand.

4. EKS Cluster Design

You size and design one EKS cluster shared by all four environments, using separate managed node groups so that a runaway load test in QA can never starve Production of compute capacity.

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: shopnow-cluster
  region: ap-south-1
  version: "1.29"

vpc:
  cidr: "10.20.0.0/16"
  nat:
    gateway: Single   # one NAT gateway to control cost in non-prod

managedNodeGroups:
  - name: ng-shared-nonprod
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 2
    maxSize: 5
    labels: { workload-tier: non-prod }
    tags: { Environment: shared-nonprod }
    taints:
      - key: "tier"
        value: "non-prod"
        effect: "NoSchedule"

  - name: ng-prod
    instanceType: m5.large
    desiredCapacity: 3
    minSize: 3
    maxSize: 8
    labels: { workload-tier: prod }
    tags: { Environment: prod }
    taints:
      - key: "tier"
        value: "prod"
        effect: "NoSchedule"
Why taints and node groups? A taint on the prod node group, matched with a toleration only on prod Deployments, guarantees that a QA pod can physically never be scheduled onto a production node — even by human mistake. This is the real-world answer to "how do you enforce environment isolation at the compute layer," a question you will very likely get asked.

5. VPC and Networking

Public Subnets (3 AZs)
Hold the ALB only. Internet-facing.
Private App Subnets (3 AZs)
Hold EKS worker nodes for all four namespaces.
Private DB Subnets (3 AZs)
Hold RDS instances, reachable only from the app subnets.
NAT Gateway
Lets private subnets reach the internet (pull images, hit external APIs) without being reachable from it.

Every namespace's pods live on the same private subnets — isolation between Dev/QA/UAT/Prod at the network layer is enforced with Kubernetes NetworkPolicies and Security Groups, not by giving each environment its own VPC (that would be over-engineering for one application and would multiply your NAT Gateway and peering costs for no real benefit).

6. IAM Roles and IRSA

IRSA stands for IAM Roles for Service Accounts. It solves one very old and very dangerous problem: how does a pod running inside Kubernetes get permission to call AWS APIs (like reading a secret from Secrets Manager) without you hard-coding an AWS access key into the container image?

Before IRSA, the old way was to give every EC2 worker node one big IAM role, and every pod on that node inherited the same wide permissions — a QA pod could theoretically read a production S3 bucket if the node role allowed it. IRSA fixes this by binding a narrow IAM role to one Kubernetes ServiceAccount, so a pod only gets exactly the AWS permissions its own workload needs.
# 1. Create an IAM policy scoped to only what the backend pod needs
aws iam create-policy \
  --policy-name shopnow-backend-secrets-read \
  --policy-document file://backend-secrets-policy.json

# 2. Create the IAM role trusted by the EKS OIDC provider, one per environment
eksctl create iamserviceaccount \
  --cluster shopnow-cluster \
  --namespace prod \
  --name shopnow-backend-sa \
  --attach-policy-arn arn:aws:iam::111122223333:policy/shopnow-backend-secrets-read \
  --approve

# backend-secrets-policy.json — scoped to prod secrets only
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:ap-south-1:111122223333:secret:shopnow/prod/*"
    }
  ]
}

Notice the resource ARN ends in shopnow/prod/*. The exact same policy, created for the QA namespace, would end in shopnow/qa/*. This one line is the actual technical enforcement of "QA cannot touch Prod secrets" — not a convention, not a promise, but an IAM boundary the AWS API itself refuses to cross.

7. Namespaces per Environment

kubectl create namespace dev
kubectl create namespace qa
kubectl create namespace uat
kubectl create namespace prod

# Label each for policy targeting and cost reporting
kubectl label namespace dev  environment=dev  team=shopnow
kubectl label namespace qa   environment=qa   team=shopnow
kubectl label namespace uat  environment=uat  team=shopnow
kubectl label namespace prod environment=prod team=shopnow criticality=high

# Resource Quota — stop non-prod environments from eating the shared node group

apiVersion: v1
kind: ResourceQuota
metadata:
  name: dev-quota
  namespace: dev
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 4Gi
    limits.cpu: "4"
    limits.memory: 8Gi
    pods: "20"

The same ResourceQuota, applied to qa and uat, and a much larger one for prod, guarantees that a developer accidentally scaling a Dev Deployment to 500 replicas cannot take down the shared cluster.

8. Kubernetes Manifests — Deployment and Service

Here is the full backend Deployment for the dev namespace. The QA, UAT, and Prod manifests are identical in shape — only the namespace, replica count, resource limits, image tag, and environment variables change. This is the core idea of environment promotion: the same manifest structure, different values.

# backend-deployment-dev.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shopnow-backend
  namespace: dev
  labels:
    app: shopnow-backend
    environment: dev
spec:
  replicas: 2
  selector:
    matchLabels:
      app: shopnow-backend
  template:
    metadata:
      labels:
        app: shopnow-backend
        environment: dev
    spec:
      serviceAccountName: shopnow-backend-sa
      containers:
        - name: backend
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/shopnow-backend:dev-a1b2c3d
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: shopnow-backend-config
            - secretRef:
                name: shopnow-backend-secret
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "250m", memory: "256Mi" }
          readinessProbe:
            httpGet: { path: /health/ready, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet: { path: /health/live, port: 8080 }
            initialDelaySeconds: 15
            periodSeconds: 20
      tolerations: []   # dev pods do not tolerate the prod taint, and never can be
---
apiVersion: v1
kind: Service
metadata:
  name: shopnow-backend-svc
  namespace: dev
spec:
  selector:
    app: shopnow-backend
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP

For the prod version, four lines change: replicas: 6, resource limits are roughly doubled, the image tag is a release tag like prod-v2.4.1 instead of a commit SHA, and this block is added under spec.template.spec:

      tolerations:
        - key: "tier"
          operator: "Equal"
          value: "prod"
          effect: "NoSchedule"
      nodeSelector:
        workload-tier: prod

9. ConfigMaps and Secrets per Environment

ConfigMaps hold values that are not sensitive but do change per environment — log level, feature flags, external API base URLs. Secrets hold anything sensitive — database passwords, third-party API keys.

# configmap-dev.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: shopnow-backend-config
  namespace: dev
data:
  LOG_LEVEL: "debug"
  FEATURE_NEW_CHECKOUT: "true"
  DB_HOST: "shopnow-dev.abcxyz.ap-south-1.rds.amazonaws.com"
  PAYMENT_GATEWAY_URL: "https://sandbox.paygateway.com"
---
# the same key structure for prod, values change:
# LOG_LEVEL: "warn"
# FEATURE_NEW_CHECKOUT: "false"   (not yet enabled for real customers)
# PAYMENT_GATEWAY_URL: "https://live.paygateway.com"

Secrets are never written by hand into a YAML file that goes into Git — that is one of the most common real-world security mistakes. Instead, you use the External Secrets Operator to pull from AWS Secrets Manager and materialize a native Kubernetes Secret automatically:

# external-secret-prod.yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: shopnow-backend-secret
  namespace: prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: shopnow-backend-secret
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: shopnow/prod/db-password
    - secretKey: PAYMENT_API_KEY
      remoteRef:
        key: shopnow/prod/payment-api-key
Interview line to remember: "We never store plaintext secrets in Git. The ExternalSecret object only stores a *reference* — the key name in Secrets Manager — and the operator pulls the actual value at runtime using the pod's IRSA-bound IAM role."

10. Ingress with AWS Load Balancer Controller

One shared Application Load Balancer routes to all four environments using host-based routing, which is far cheaper than provisioning a separate ALB per environment.

# ingress-dev.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shopnow-ingress
  namespace: dev
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:111122223333:certificate/xxxx
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
spec:
  rules:
    - host: dev.shopnow.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: shopnow-backend-svc
                port: { number: 80 }

The same object, repeated for qa.shopnow.com, uat.shopnow.com, and shopnow.com (prod), all attach to the same underlying ALB because the AWS Load Balancer Controller groups Ingress objects sharing an alb.ingress.kubernetes.io/group.name annotation — a cost-saving detail worth mentioning in an interview.

11. HPA and Autoscaling

# hpa-prod.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: shopnow-backend-hpa
  namespace: prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: shopnow-backend
  minReplicas: 6
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 65 }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
    scaleDown:
      stabilizationWindowSeconds: 300   # scale down slowly to avoid flapping during a sale

Dev and QA get a much smaller HPA, typically minReplicas: 1, maxReplicas: 3, because there is no real customer traffic to absorb — this difference itself is a talking point: "we size autoscaling per environment based on actual traffic patterns, not a copy-paste of prod settings."

12. PodDisruptionBudget

# pdb-prod.yaml — guarantees at least 4 pods stay up during node drains / upgrades
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: shopnow-backend-pdb
  namespace: prod
spec:
  minAvailable: 4
  selector:
    matchLabels:
      app: shopnow-backend
Why this matters: Without a PDB, a routine EKS node upgrade (draining nodes one by one) could evict enough backend pods at once to drop below the traffic capacity you need, causing a self-inflicted outage during a maintenance window. PDB is the safety rail that makes "we patch prod nodes without downtime" true.

13. NetworkPolicies

# netpol-prod-deny-cross-namespace.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-from-other-namespaces
  namespace: prod
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector: {}   # only allow traffic from pods inside the SAME namespace
---
# netpol-allow-ingress-from-alb.yaml — still let the ALB target group reach the pods
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-alb-ingress
  namespace: prod
spec:
  podSelector:
    matchLabels: { app: shopnow-backend }
  policyTypes: [Ingress]
  ingress:
    - from: []
      ports:
        - protocol: TCP
          port: 8080

This is the network-layer version of the same story you saw in IAM: a pod in qa namespace, even sitting on the same physical node as a prod pod, is denied at the packet level from ever initiating a connection to it.

15. CI/CD Pipeline — Jenkins and GitHub Actions

The core idea in both tools is identical: one pipeline, environment as a parameter, with a manual approval gate before UAT and before Prod.

Jenkins Declarative Pipeline

// Jenkinsfile
pipeline {
  agent any
  parameters {
    choice(name: 'DEPLOY_ENV', choices: ['dev','qa','uat','prod'], description: 'Target environment')
  }
  environment {
    ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/shopnow-backend"
    IMAGE_TAG = "${params.DEPLOY_ENV}-${GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Checkout') { steps { checkout scm } }

    stage('Unit Test') { steps { sh 'npm ci && npm test' } }

    stage('Build & Push Image') {
      steps {
        sh """
          aws ecr get-login-password --region ap-south-1 | docker login --username AWS --password-stdin ${ECR_REPO}
          docker build -t ${ECR_REPO}:${IMAGE_TAG} .
          docker push ${ECR_REPO}:${IMAGE_TAG}
        """
      }
    }

    stage('Approval Gate') {
      when { expression { params.DEPLOY_ENV == 'uat' || params.DEPLOY_ENV == 'prod' } }
      steps {
        timeout(time: 30, unit: 'MINUTES') {
          input message: "Approve deployment to ${params.DEPLOY_ENV}?", submitter: 'release-managers'
        }
      }
    }

    stage('Deploy to Kubernetes') {
      steps {
        sh """
          kubectl set image deployment/shopnow-backend backend=${ECR_REPO}:${IMAGE_TAG} -n ${params.DEPLOY_ENV}
          kubectl rollout status deployment/shopnow-backend -n ${params.DEPLOY_ENV} --timeout=180s
        """
      }
    }

    stage('Generate Report & Notify') {
      steps {
        sh 'python3 generate_report.py --env ${DEPLOY_ENV} --status success --build ${BUILD_NUMBER}'
        sh 'python3 send_email.py --env ${DEPLOY_ENV} --report report.html'
      }
    }
  }
  post {
    failure {
      sh 'python3 send_email.py --env ${DEPLOY_ENV} --status FAILED --build ${BUILD_NUMBER}'
    }
  }
}

GitHub Actions Equivalent

# .github/workflows/deploy.yml
name: ShopNow Multi-Env Deploy
on:
  workflow_dispatch:
    inputs:
      environment:
        type: choice
        options: [dev, qa, uat, prod]
  push:
    branches: ["develop"]   # pushes to develop auto-deploy to dev only

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/github-actions-ecr-push
          aws-region: ap-south-1
      - name: Build and push
        run: |
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REGISTRY
          docker build -t $ECR_REGISTRY/shopnow-backend:${{ github.event.inputs.environment }}-${{ github.sha }} .
          docker push $ECR_REGISTRY/shopnow-backend:${{ github.event.inputs.environment }}-${{ github.sha }}

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    environment: ${{ github.event.inputs.environment }}   # GitHub Environments hold the approval rule for uat/prod
    steps:
      - name: Update kustomize image tag and push to GitOps repo
        run: |
          cd gitops-repo/overlays/${{ github.event.inputs.environment }}
          kustomize edit set image shopnow-backend=$ECR_REGISTRY/shopnow-backend:${{ github.event.inputs.environment }}-${{ github.sha }}
          git commit -am "Deploy ${{ github.sha }} to ${{ github.event.inputs.environment }}"
          git push
Notice the GitHub Actions job never runs kubectl apply directly. It pushes an image-tag change to a Git repository, and Argo CD (next section) picks that up and applies it to the cluster. This pattern is called GitOps, and it is the single most important modern concept to be able to explain in an interview.

16. Argo CD GitOps

The old way: a Jenkins job runs kubectl apply directly against the cluster. The problem — if someone manually edits a Deployment with kubectl edit during an incident at 2 AM, there's no record of that change anywhere, and the next Jenkins run silently overwrites it. GitOps flips the model: Git becomes the single source of truth, and Argo CD's job is only to continuously make the cluster match what's in Git.
# app-of-apps: one Argo CD Application per environment, all pointing at the same repo, different folder
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shopnow-backend-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/shopnow/gitops-repo.git
    targetRevision: main
    path: overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true   # if someone manually edits prod, Argo CD reverts it back to Git within minutes
    syncOptions: ["CreateNamespace=false"]

The overlays/ folder is a Kustomize structure, which is the cleanest way to express "same base manifests, different values per environment":

gitops-repo/
  base/
    deployment.yaml
    service.yaml
    kustomization.yaml
  overlays/
    dev/    kustomization.yaml   (replicas: 2, image tag: dev-*)
    qa/     kustomization.yaml   (replicas: 2, image tag: qa-*)
    uat/    kustomization.yaml   (replicas: 3, image tag: uat-*)
    prod/   kustomization.yaml   (replicas: 6, image tag: prod-*)

# overlays/prod/kustomization.yaml
resources:
  - ../../base
namespace: prod
replicas:
  - name: shopnow-backend
    count: 6
images:
  - name: shopnow-backend
    newTag: prod-a1b2c3d

selfHeal: true combined with automated sync for dev/qa but a manual sync for prod is exactly how a real release manager balances speed against control — you would say in an interview: "dev and QA auto-deploy on every merge, UAT and Prod require someone to click Sync in Argo CD after the approval gate passes."

17. Prometheus and Grafana

# ServiceMonitor — tells Prometheus Operator to scrape the backend's /metrics endpoint
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: shopnow-backend-monitor
  namespace: prod
spec:
  selector:
    matchLabels: { app: shopnow-backend }
  endpoints:

      path: /metrics
      interval: 30s

# PrometheusRule — alert when error rate crosses 5% for 5 minutes, scoped per environment via label
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: shopnow-backend-alerts
  namespace: prod
spec:
  groups:
    - name: shopnow.rules
      rules:
        - alert: HighErrorRate
          expr: |
            sum(rate(http_requests_total{namespace="prod",status=~"5.."}[5m]))
            /
            sum(rate(http_requests_total{namespace="prod"}[5m])) > 0.05
          for: 5m
          labels: { severity: critical, environment: prod }
          annotations:
            summary: "Prod backend error rate above 5% for 5 minutes"

In Grafana, you build one dashboard with a namespace variable ($environment) at the top, so the same dashboard flips between showing Dev, QA, UAT, and Prod metrics instead of maintaining four separate dashboards — panels for request rate, p95 latency, error rate, pod CPU/memory, and HPA current-vs-max replicas.

19. Failure Testing

Before this project is called "done," you deliberately break things to prove the safety nets actually work — this is what turns a deployment setup into a resume line that survives interview cross-questioning.

# Test 1: Kill a pod and confirm the Deployment self-heals
kubectl delete pod -n prod -l app=shopnow-backend --field-selector status.phase=Running --grace-period=0 --force | head -1
kubectl get pods -n prod -w   # watch a new pod get scheduled within seconds

# Test 2: Simulate a bad deploy (image that crashes on startup)

20. Rollback Strategy

# Because Argo CD tracks Git history, rollback is a Git revert, not a manual kubectl command
cd gitops-repo/overlays/prod
git log --oneline -5
git revert <bad-commit-sha>
git push
# Argo CD detects the revert and syncs the cluster back automatically

# For an emergency where you cannot wait for the Git flow, native rollback:
kubectl rollout undo deployment/shopnow-backend -n prod
kubectl rollout undo deployment/shopnow-backend -n prod --to-revision=3
kubectl rollout history deployment/shopnow-backend -n prod
Golden rule stated in the runbook: "Emergency kubectl rollout undo is allowed to stop the bleeding immediately, but within the hour the same fix must be committed to the GitOps repo — otherwise the next Argo CD sync will silently redeploy the broken version, because Git still thinks that's the desired state."

22. Ansible Automation

Ansible wraps the manual setup steps (namespace creation, base RBAC, initial secrets bootstrap) into one repeatable playbook, so that spinning up a brand-new environment — say ShopNow adds a fifth "staging" tier next year — takes one command instead of a checklist.

# playbook.yml
- name: Bootstrap a new ShopNow environment on EKS
  hosts: localhost
  gather_facts: false
  vars:
    env_name: "{{ target_env }}"

  tasks:
    - name: Create namespace
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: "{{ env_name }}"
            labels: { environment: "{{ env_name }}", team: shopnow }

    - name: Apply ResourceQuota
      kubernetes.core.k8s:
        state: present
        src: "templates/resourcequota.yaml.j2"

    - name: Create IRSA service account via eksctl
      command: >
        eksctl create iamserviceaccount
        --cluster shopnow-cluster
        --namespace {{ env_name }}
        --name shopnow-backend-sa
        --attach-policy-arn {{ irsa_policy_arn }}
        --approve

    - name: Register ExternalSecret for this environment
      kubernetes.core.k8s:
        state: present
        template: "templates/external-secret.yaml.j2"

    - name: Register Argo CD Application
      kubernetes.core.k8s:
        state: present
        template: "templates/argocd-app.yaml.j2"

    - name: Wait for Deployment rollout
      kubernetes.core.k8s_info:
        kind: Deployment
        namespace: "{{ env_name }}"
        name: shopnow-backend
      register: dep_status
      until: dep_status.resources[0].status.readyReplicas is defined
      retries: 10
      delay: 15

# Run it:
ansible-playbook playbook.yml -e "target_env=staging irsa_policy_arn=arn:aws:iam::111122223333:policy/shopnow-backend-secrets-read"

23. HTML Deployment/Job Report Generator

Every pipeline run ends by generating a small, self-contained HTML report, attached to the notification email and archived as a Jenkins/GitHub Actions artifact — this is what a release manager opens instead of scrolling through console logs.

# generate_report.py
import argparse, subprocess, datetime, json

def get_pod_status(namespace):
    out = subprocess.run(
        ["kubectl", "get", "pods", "-n", namespace, "-o", "json"],
        capture_output=True, text=True
    )
    return json.loads(out.stdout)["items"]

def build_report(env, status, build_no, pods):
    rows = "".join(
        f"<tr><td>{p['metadata']['name']}</td><td>{p['status']['phase']}</td></tr>"
        for p in pods
    )
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Deployment Report — {env.upper()}</h2>
    <p>Build: #{build_no} | Status: {status.upper()} | Time: {datetime.datetime.now()}</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>Pod</th><th>Phase</th></tr>
      {rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--env", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    pods = get_pod_status(args.env)
    build_report(args.env, args.status, args.build, pods)
    print("report.html generated")

24. Email Notification

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(env, status, build_no, report_path=None):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] Deployment to {env.upper()} - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com"

    body = f"Environment: {env}\nBuild: #{build_no}\nStatus: {status}\n\nSee attached report for pod-level detail."
    msg.attach(MIMEText(body, "plain"))

    if report_path and os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)

    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:   # AWS SES
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--env", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default=None)
    args = parser.parse_args()
    send(args.env, args.status, args.build, args.report)

This uses AWS SES (Simple Email Service) as the SMTP relay, which is the standard choice inside AWS-hosted pipelines because it needs no separate mail server and integrates with the same IAM boundary as everything else in this project.
