1. The Business Scenario — Why This Project Exists

Six months ago, ShopNow Retail's production cluster and its Git repository quietly drifted apart. An engineer, chasing a live incident at 11 PM, ran kubectl scale deployment payment-service --replicas=12 directly against the cluster to handle a traffic spike — a completely reasonable emergency action. The incident passed. Nobody ever scaled it back down, and nobody ever updated the Git repo to reflect 12 replicas as the new normal. Three weeks later, a routine CI/CD pipeline run for an unrelated change applied the Deployment manifest from Git — which still said replicas: 6 — and silently cut Payment Service's capacity in half during a moderately busy afternoon, causing a fresh, smaller incident that took an hour to diagnose because nobody remembered the original manual change at all.

Ramesh's ask: "I want it to be impossible for the cluster and Git to quietly disagree with each other. Git should be the one and only source of truth for what's supposed to be running — and I want something continuously watching the real cluster, comparing it against Git, and telling us the moment they don't match, or better yet, fixing it automatically."

This use case is the direct, complete answer: Argo CD as ShopNow's GitOps engine, continuously reconciling the entire EKS cluster's actual state against what's declared in Git — not as a one-time deploy tool, but as an always-running control loop that makes drift visible, alertable, and in most cases self-correcting.

2. The Core Idea — the Continuous Reconciliation Loop

Developer
→
Git Repository
→
Argo CD
→
Amazon EKS

This is the exact flow from the original ask, and it looks like a simple one-way pipeline — but the crucial detail, and the entire reason Argo CD exists rather than a plain kubectl apply script, is that the arrow from Argo CD to EKS is not one-directional. It's a loop:

THE RECONCILIATION LOOP — running continuously, roughly every 3 minutes, forever

Argo CD reads the desired state from Git  ↔  Argo CD reads the actual state from the live EKS cluster  →  diffs the two  →  reports Synced or OutOfSync  →  (if configured) automatically corrects the cluster to match Git

Every earlier use case in this series that mentioned Argo CD used it in this exact way, always briefly. This use case is the one that stops and explains the mechanism itself in full — what "desired state" and "actual state" concretely mean, how the diff is computed, what the three sync policy modes actually do differently, and how to prove, with a real live demonstration, that the loop genuinely closes.

Traditional CI/CD push model (Use Case 12's deploy stage, in isolation)GitOps pull model (Argo CD, this use case)
Pipeline has direct kubectl credentials to productionArgo CD, running inside the cluster, pulls from Git — no external system needs cluster-admin credentials
Deployment happens once, at pipeline run timeReconciliation happens continuously, forever, whether or not a pipeline just ran
A manual kubectl edit in prod is invisible until someone noticesA manual kubectl edit is detected within the next reconciliation cycle and flagged (or reverted)
"What's actually running in prod?" requires querying the cluster directly"What's actually running in prod?" is answered by reading Git, with Argo CD's UI confirming they match

Notice this entire repository contains no Dockerfiles, no application source code, and no CI pipeline definitions. This is a deliberate, structural separation: the shopnow-order-service-repo (application code, from Use Case 12) is where developers work and CI runs; shopnow-gitops-repo (this one) is where only deployment state lives, written to almost exclusively by pipelines, and read continuously by Argo CD. Mixing the two into one repository is one of the most common GitOps anti-patterns, because it makes it much harder to reason about exactly what Argo CD is watching.

4. Application Architecture

        Developer pushes application code (separate app repo, Use Case 12's pipeline)
                          |
              CI/CD pipeline builds, tests, scans, pushes to ECR,
              then commits the new image tag to shopnow-gitops-repo
                          |
              +------------------------------------------+
              |     Argo CD (running inside EKS itself)   |
              |   watches shopnow-gitops-repo continuously |
              +------------------------------------------+
                          |
              Detects the new commit within ~3 minutes (or instantly via webhook)
                          |
              Computes a diff: Git's desired state vs the live cluster's actual state
                          |
              Applies the diff (auto-sync) or waits for a human to click Sync (manual)
                          |

This use case governs all four of ShopNow's services from earlier use cases — Order, Catalog, Payment, and Notification — demonstrated together specifically because the App-of-Apps pattern (section 10) only really shows its value when managing more than one application at once.

apiVersion: eksctl.io/v1alpha5

metadata:
  name: shopnow-cluster
  region: ap-south-1

iam:
  withOIDC: true
managedNodeGroups:
  - name: ng-platform
    instanceType: m5.large
    desiredCapacity: 3
    minSize: 3
    maxSize: 6
    labels: { workload: platform }

Argo CD's own components (API server, repo server, application controller, Redis) run on this dedicated ng-platform node group, deliberately separated from application workloads — the reasoning is identical to the dedicated node groups seen for secure/compliance workloads earlier in this series: platform tooling that every other deployment depends on shouldn't compete for capacity with, or be affected by, the noisy neighbor behavior of the applications it's managing.

The Argo CD UI is internal-scheme only, deliberately. 10. The App-of-Apps Pattern — Managing the Whole Fleet From One Root

# apps/root-app.yaml — ONE Application object that itself manages the other four
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: shopnow-root, namespace: argocd }
spec:
  project: shopnow
  source:
    repoURL: https://github.com/shopnow/gitops-repo.git
    targetRevision: main
    path: apps          # this folder contains the OTHER four Application manifests
  destination: { server: https://kubernetes.default.svc, namespace: argocd }
  syncPolicy: { automated: { prune: true, selfHeal: true } }

# apps/order-service.yaml — one of the FOUR "child" Applications the root manages
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: order-service-prod, namespace: argocd }
spec:
  project: shopnow
  source: { repoURL: https://github.com/shopnow/gitops-repo.git, targetRevision: main, path: services/order-service/overlays/prod }
  destination: { server: https://kubernetes.default.svc, namespace: prod }
  syncPolicy: { automated: { prune: true, selfHeal: true } }
1The root-app Application's source is the apps/ folder — which contains ordinary Kubernetes YAML files that happen to themselves be Argo CD Application objects. Argo CD applies those YAML files exactly like any other manifest, which means it creates the four child Applications.
2Once created, each child Application independently starts managing its own service, exactly as if it had been created by hand. Onboarding a fifth service — say, the Fulfillment gRPC Service from Use Case 8 — becomes a single new YAML file dropped into apps/ and committed; the root Application syncs it in automatically, and from that moment on it's fully managed.
3This is the concrete answer to "how do you manage a growing fleet of microservices without manually configuring Argo CD for each one" — the fleet's membership itself becomes declarative and version-controlled, not just each service's own contents.

11. Sync Policies — Automated, Manual, and Self-Heal Explained

syncPolicy:
  automated:
    prune: true
    selfHeal: true
  syncOptions:
    - CreateNamespace=false
SettingWhat it precisely controls
automated present at allArgo CD applies a detected Git change to the cluster automatically, with no human clicking "Sync." Omitting this block entirely means Argo CD only ever reports OutOfSync and waits for a manual sync — this is what ShopNow uses for Payment Service's Blue-to-Green switch step, matching the manual gate from Use Case 4.
prune: trueIf a resource is removed from Git (a manifest file deleted), Argo CD deletes the corresponding object from the cluster too. Without this, deleted-from-Git resources simply linger in the cluster forever, orphaned and undocumented.
selfHeal: trueThis is the setting that directly answers section 1's incident. If the live cluster drifts from Git — a manual kubectl scale, a kubectl edit, anything — Argo CD doesn't just report OutOfSync, it actively reverts the cluster back to match Git, typically within the next reconciliation cycle (a few minutes, or near-instantly if a webhook triggers an immediate refresh).
ShopNow's actual policy, by service, is deliberately not uniform — and that's the point. Order, Catalog, and Notification Service run full automated + selfHeal, since fast, confident auto-correction fits their risk profile. Payment Service's traffic-switching Service object (the Blue/Green selector from Use Case 4) is deliberately excluded from selfHeal via a resource-level ignoreDifferences rule, because that one field is meant to be changed outside of a normal Git commit as part of the controlled Blue-Green cutover process — a case where blanket self-heal would fight the very workflow Use Case 4 was built around.
# Excluding one specific field from self-heal, for Payment Service specifically
spec:
  ignoreDifferences:
    - group: ""
      kind: Service
      name: payment-service-svc
      jsonPointers: ["/spec/selector/version"]

12. Sync Waves and Resource Hooks — Ordering the Rollout

# A ConfigMap or Secret should exist BEFORE the Deployment that references it —
# sync waves let you declare that ordering explicitly
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-service-config
  annotations:
    argocd.argoproj.io/sync-wave: "0"   # applied FIRST
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  annotations:
    argocd.argoproj.io/sync-wave: "1"   # applied SECOND, after wave 0 finishes

# A PreSync hook — runs a database migration job BEFORE any new pod starts,
# and only proceeds to sync-wave "0" if this Job succeeds
apiVersion: batch/v1
kind: Job
metadata:
  name: order-service-migration
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      containers: [{ name: migrate, image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service:prod-latest, command: ["./migrate.sh"] }]
      restartPolicy: Never
This directly connects to Use Case 11's dependency-check logic, from the opposite direction. Where Use Case 11 validates that a migration has already run before deploying, a PreSync hook can perform that migration as an ordered, gated step within the sync itself — both patterns are legitimate and often used together: the hook runs the migration, and the init-container validator (Use Case 11) double-checks it actually landed before the app container starts.

13. Argo CD Projects and RBAC

# platform/argocd/projects/shopnow-project.yaml — scopes what CAN be deployed where
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata: { name: shopnow, namespace: argocd }
spec:
  sourceRepos: ["https://github.com/shopnow/gitops-repo.git"]
  destinations:
    - namespace: "dev"
      server: https://kubernetes.default.svc
    - namespace: "qa"
      server: https://kubernetes.default.svc
    - namespace: "prod"
      server: https://kubernetes.default.svc
  clusterResourceWhitelist: []   # applications in this project CANNOT touch cluster-scoped resources at all
  roles:
    - name: developer
      policies:
        - p, proj:shopnow:developer, applications, sync, shopnow/*-dev, allow
        - p, proj:shopnow:developer, applications, sync, shopnow/*-prod, deny
      groups: ["shopnow-engineers"]
    - name: release-manager
      policies:
        - p, proj:shopnow:release-manager, applications, sync, shopnow/*, allow
      groups: ["shopnow-release-managers"]
This is the Argo CD equivalent of the IAM/IRSA scoping running throughout this whole series. A regular engineer's SSO group can sync any service to Dev freely (fast iteration, low risk) but is explicitly denied syncing to Prod — that requires the release-manager group. clusterResourceWhitelist: [] additionally means even a compromised or misconfigured Application in this project can never create a ClusterRole, a Namespace, or any other cluster-scoped object — its blast radius is structurally capped to namespaced resources only.

17. HPA, PDB, and NetworkPolicies

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-service-hpa }
spec: { scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }, minReplicas: 6, maxReplicas: 15, metrics: [{ type: Resource, resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } } }] }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: order-service-pdb }
spec: { minAvailable: 4, selector: { matchLabels: { app: order-service } } }
A subtlety worth being precise about: the HPA's replicas field is a legitimate, expected exception to "Git is the only source of truth." HPA actively and continuously changes the live replica count based on load, which will constantly differ from whatever static number sits in Git. Argo CD handles this correctly out of the box — it recognizes HPA-managed fields and doesn't treat the resulting drift as OutOfSync, but this is worth understanding explicitly, since it's a common point of confusion: "why doesn't selfHeal fight my HPA?"

18. Jenkins and GitHub Actions — Where CI Ends and Argo CD Begins

// The relevant tail end of Use Case 12's full pipeline — everything up to and
// including this step is CI's job; everything after is Argo CD's job, running
// independently and continuously regardless of pipeline activity
stage('Update GitOps Repo') {
  steps {
    sh '''
      cd gitops-repo/services/order-service/overlays/prod
      kustomize edit set image order-service=$ECR_REPO:$IMAGE_TAG
      git commit -am "order-service: deploy $IMAGE_TAG"
      git push
    '''
  }
  // Pipeline's job ends here. It does NOT run kubectl apply, does NOT hold
  // cluster credentials, and does NOT wait around babysitting the rollout —
  // that responsibility now belongs entirely to Argo CD's own reconciliation loop.
}
stage('Optionally Nudge Argo CD') {
  steps { sh 'argocd app sync order-service-prod --async' }
  // Purely a convenience to skip waiting for the next poll interval — Argo CD
  // would eventually apply this exact same change on its own even without this line
}
This is the cleanest possible statement of the CI/CD-vs-GitOps boundary, worth having ready verbatim for an interview: "our CI/CD pipeline's responsibility ends the moment it commits a new image tag to the GitOps repository. Argo CD, running independently inside the cluster, picks up that change and is solely responsible for making it real — the pipeline never touches the cluster directly, and if the pipeline crashed the instant after that git push, the deployment would still happen correctly."

19. Argo CD Notifications

# platform/argocd/notifications/notifications-cm.yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: argocd-notifications-cm, namespace: argocd }
data:
  service.email: |
    host: email-smtp.ap-south-1.amazonaws.com
    port: 587
    username: $email-username
    password: $email-password
    from: devops-bot@shopnow.com

  template.app-out-of-sync: |
    email:
      subject: "[ShopNow] {{.app.metadata.name}} drifted from Git"
    message: |
      {{.app.metadata.name}} is OutOfSync.
      Live cluster state no longer matches Git — check whether selfHeal will
      correct this automatically, or whether manual investigation is needed.

  trigger.on-sync-failed: |
    - when: app.status.operationState.phase in ['Error', 'Failed']
      send: [app-sync-failed]

  trigger.on-out-of-sync: |
    - when: app.status.sync.status == 'OutOfSync'
      send: [app-out-of-sync]

These triggers fire for exactly the two events this whole use case cares about most: a sync that failed outright, and drift being detected at all — the second one is what would have caught section 1's incident within minutes, rather than three weeks later.

spec:

          labels: { severity: warning }
          annotations: { summary: "{{ $labels.name }} has been OutOfSync for over 10 minutes" }

The official Argo CD Grafana dashboard (imported from its public dashboard ID) gives a fleet-wide view — every managed Application's sync status, health status, and last-sync time on one screen, the direct visual answer to "what's actually running everywhere, right now, compared to Git."

22. Running the Code — Full End-to-End Workflow

Step 1 — Install and bootstrap the whole fleet via the App-of-Apps root

kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl apply -f platform/argocd/projects/shopnow-project.yaml
kubectl apply -f apps/root-app.yaml

argocd app get shopnow-root
# Expect: Synced, Healthy, and four child Applications listed as its managed resources

argocd app list
# Expect: shopnow-root, order-service-prod, catalog-service-prod, payment-service-prod,
# notification-service-prod — all Synced, all Healthy

Step 2 — Make a real Git change and watch the loop pick it up

cd gitops-repo/services/order-service/overlays/prod
sed -i 's/replicas: 6/replicas: 8/' patch-replicas.yaml
git commit -am "order-service: bump baseline replicas to 8"
git push

argocd app get order-service-prod --refresh
# Within seconds of a manual refresh (or ~3 min automatically), status flips
# to OutOfSync, briefly, then back to Synced once the change is applied

kubectl get deployment order-service -n prod -o jsonpath='{.spec.replicas}'
# Expect: 8 — the cluster now matches Git

Step 3 — THE key demonstration: prove drift detection and self-heal, live

# Deliberately recreate section 1's exact incident — a manual, unauthorized change
kubectl scale deployment order-service -n prod --replicas=20

# Watch Argo CD notice, in real time
argocd app get order-service-prod --refresh --hard-refresh
# Expect: Sync Status flips to OutOfSync, with the diff clearly showing
# "replicas: live=20, desired=8"

# Watch selfHeal correct it automatically, without anyone running `argocd app sync`
kubectl get deployment order-service -n prod -w
# Expect: within roughly 3 minutes (the default reconciliation interval),
# the replica count reverts from 20 back to 8, entirely on its own

argocd app get order-service-prod
# Expect: back to Synced, Healthy — with an event in the app's history logging
# that a self-heal operation occurred

This single demonstration is the most important one in the entire use case — it is the literal, live proof that the incident from section 1 could not have gone unnoticed for three weeks under this system; the drift would have been visible within minutes, and in most configurations, corrected automatically before anyone even needed to look.

24. Rollback Strategy — Using Argo CD's Own History

# Argo CD tracks every sync as a numbered, browsable revision — rollback doesn't
# require a manual Git revert if the previous state is still in Argo CD's history
argocd app history order-service-prod

ID  DATE                           REVISION
7   2026-08-20 14:02:11 +0530 IST  a1b2c3d (order-service: deploy prod-v3.6.0)
6   2026-08-18 09:41:03 +0530 IST  9f8e7d6 (order-service: deploy prod-v3.5.0)

argocd app rollback order-service-prod 6
# This performs a live, immediate rollback to revision 6's exact state

# The GitOps-correct follow-up: still commit the revert to Git, or the next
# automated sync will simply roll FORWARD again to whatever Git currently says
git revert <bad-commit-sha> && git push
This is worth stating precisely, because it's a common point of confusion: argocd app rollback changes the live cluster immediately, but if selfHeal is on and Git still points at the bad version, Argo CD will notice the "drift" from its own rollback and helpfully sync it right back to the broken state within minutes. A true rollback under GitOps always ultimately needs a Git-level change — argocd app rollback is best used as a fast stop-gap while the proper Git revert is prepared, exactly mirroring the emergency-vs-proper-fix pattern from earlier use cases in this series.

27. HTML Deployment/Job Report

# generate_report.py — fleet-wide sync/health snapshot, not just one service
import argparse, subprocess, json, datetime

def get_all_apps():
    out = subprocess.run(["argocd", "app", "list", "-o", "json"], capture_output=True, text=True)
    apps = json.loads(out.stdout)
    return [(a["metadata"]["name"], a["status"]["sync"]["status"], a["status"]["health"]["status"]) for a in apps]

def build_report(build_no, status):
    rows = ""
    for name, sync, health in get_all_apps():
        sync_color = "#5ec98f" if sync == "Synced" else "#e35d5d"
        health_color = "#5ec98f" if health == "Healthy" else "#e35d5d"
        rows += f"<tr><td>{name}</td><td style='color:{sync_color}'>{sync}</td><td style='color:{health_color}'>{health}</td></tr>"
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow GitOps Fleet Report (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>Application</th><th>Sync Status</th><th>Health</th></tr>{rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.build, args.status)

28. Email Notification

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] GitOps fleet report - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, platform-team@shopnow.com"
    msg.attach(MIMEText(f"Build: #{build_no}\nStatus: {status}\n\nSee attached fleet-wide Argo CD sync/health report.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
