🌐 Kubernetes Networking Model

📖 The 3 Networking Problems K8s Solves

1) Pod-to-Pod: How does the checkout service talk to the inventory service? 2) Pod-to-Service: Which pod IP do I call when pods restart constantly? 3) External-to-Service: How do users on the internet reach my app?

The 4 Kubernetes Networking Rules

  • Every Pod gets its own unique IP address (no NAT between pods)
  • Any Pod can communicate with any other Pod directly using its IP
  • Pods on the same node communicate via a virtual bridge (cbr0)
  • Pods on different nodes communicate via the CNI plugin (AWS VPC CNI on EKS)

The Full Networking Picture

EXTERNAL USER (internet) │ HTTPS ▼ AWS ALB (Application Load Balancer) │ HTTP forward ▼ Ingress Controller (nginx / AWS ALB Ingress) │ Route by path/host ┌────┴──────────────────┐ ▼ ▼ Service: frontend-svc Service: api-svc (ClusterIP) (ClusterIP) │ │ │ iptables load balance │ ├──► frontend-pod-1 ├──► api-pod-1 ├──► frontend-pod-2 └──► api-pod-2 └──► frontend-pod-3 Pod-to-Pod (within cluster): api-pod-1 ──► mysql-svc:3306 ──► mysql-0, mysql-1 DNS Resolution (CoreDNS): mysql-svc → 10.100.45.23 (ClusterIP) mysql-0.mysql.shopnow.svc.cluster.local → 10.0.1.5 (StatefulSet pod)

🔍 CoreDNS — Service Discovery in Kubernetes

CoreDNS is the DNS server that runs inside every Kubernetes cluster. It allows pods to find each other by name instead of IP address. When you create a Service, CoreDNS automatically creates DNS entries for it.

DNS Name Format

textDNS naming patterns
# Full DNS name format for a Service:
<service-name>.<namespace>.svc.cluster.local

# Examples:
mysql-svc.shopnow.svc.cluster.local      # MySQL service in shopnow namespace
api-svc.default.svc.cluster.local        # API service in default namespace
nginx-svc.shopnow.svc.cluster.local      # nginx service

# Short-form DNS (works from within SAME namespace):
mysql-svc              # Same as mysql-svc.shopnow.svc.cluster.local
api-svc                # Same as api-svc.default.svc.cluster.local

# Cross-namespace (must use full name or at least service.namespace):
mysql-svc.shopnow      # Calling shopnow's mysql from another namespace

# StatefulSet pod DNS (via Headless Service):
mysql-0.mysql.shopnow.svc.cluster.local  # Pod mysql-0
mysql-1.mysql.shopnow.svc.cluster.local  # Pod mysql-1

Verify DNS from inside a Pod

bash
# Run a debug pod with DNS tools
kubectl run dns-debug \
  --image=busybox:1.28 \
  --rm -it \
  --restart=Never \
  -n shopnow \
  -- /bin/sh

# Inside the pod:
nslookup nginx-svc                          # Short name (same namespace)
nslookup nginx-svc.shopnow.svc.cluster.local  # Full name
nslookup kubernetes.default.svc.cluster.local  # K8s API server
cat /etc/resolv.conf  # See DNS search domains configured by K8s
💡 /etc/resolv.conf inside pods:
Kubernetes configures each pod's /etc/resolv.conf with search domains:
search shopnow.svc.cluster.local svc.cluster.local cluster.local
This is why you can use short names — the search domain expands them automatically.

🚪 Ingress — The HTTP Routing Gateway

📖 Story — The Problem Without Ingress

ShopNow has 5 microservices. Without Ingress, each needs its own AWS LoadBalancer ($20/month each = $100/month). With Ingress, ONE LoadBalancer receives all traffic and routes by URL path or hostname to the right service. Save 80% on cloud costs, plus get TLS termination in one place.

Ingress vs Service LoadBalancer

Without IngressWith Ingress
5 services = 5 LoadBalancers = $100/mo1 Ingress = 1 LoadBalancer = $20/mo
5 SSL certificates to manage1 SSL certificate (wildcard)
5 different public IPs/DNS names1 DNS name, different paths
No path-based routingRoute /api, /web, /admin separately

Ingress Architecture

Internet User │ GET https://shopnow.com/api/orders ▼ AWS ALB (Load Balancer) ← Ingress Controller creates this │ ▼ Ingress Controller Pod ← Reads Ingress YAML rules (nginx-ingress or aws-alb-ingress) │ ├── /api/* ──────────────► Service: api-svc:8080 ├── /web/* ──────────────► Service: frontend-svc:80 └── /admin/* ──────────────► Service: admin-svc:3000 Host-based routing: ├── api.shopnow.com ───────► Service: api-svc └── app.shopnow.com ───────► Service: frontend-svc

Ingress Resource YAML (nginx Ingress Controller)

YAMLshopnow-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shopnow-ingress
  namespace: shopnow
  annotations:
    # Which ingress controller handles this resource:
    kubernetes.io/ingress.class: "nginx"
    
    # Redirect HTTP to HTTPS:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    
    # Enable CORS headers:
    nginx.ingress.kubernetes.io/enable-cors: "true"
    
    # Rate limiting: 100 requests per minute per IP
    nginx.ingress.kubernetes.io/limit-rpm: "100"
    
    # Rewrite /api/v1/orders → /orders (strip prefix):
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    
spec:
  ingressClassName: nginx            # ← Which IngressClass to use (K8s 1.18+)
  
  tls:                               # ← TLS/HTTPS configuration
  - hosts:
    - shopnow.com
    - api.shopnow.com
    secretName: shopnow-tls          # ← K8s Secret with TLS cert/key
    
  rules:
  - host: shopnow.com                # ← Match this hostname
    http:
      paths:
      - path: /                      # ← Match this path
        pathType: Prefix             # ← Prefix: /foo matches /foo/bar
                                     #   Exact: /foo only matches /foo
        backend:
          service:
            name: frontend-svc       # ← Forward to this Service
            port:
              number: 80
              
  - host: api.shopnow.com            # ← Separate host for API
    http:
      paths:
      - path: /v1                    # ← API v1 endpoint
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 8080
      - path: /health                # ← Health check endpoint
        pathType: Exact
        backend:
          service:
            name: api-svc
            port:
              number: 8080

Word-by-Word Annotations

annotations
What they do: Ingress annotations are controller-specific configuration. nginx has 100+ annotations. The Ingress object itself is just routing rules — annotations tell the controller HOW to handle traffic (timeouts, SSL, rate limiting, rewrites). Different controllers (nginx vs AWS ALB) have completely different annotation keys.
pathType: Prefix vs Exact
Prefix: /api matches /api, /api/, /api/users, /api/orders/123. Exact: /health matches ONLY /health, not /health/check. ImplementationSpecific: controller decides the interpretation. Use Prefix for APIs, Exact for specific endpoints like /healthz or /metrics.
tls.secretName: shopnow-tls
What's inside the Secret: A TLS secret must contain two keys: tls.crt (the certificate) and tls.key (the private key). Create with: kubectl create secret tls shopnow-tls --cert=cert.pem --key=key.pem. In production, use cert-manager to auto-issue Let's Encrypt certs.

bash

☁️ AWS Load Balancer Controller (EKS)

📖 Story

On EKS, when you create a Service of type LoadBalancer, by default Kubernetes creates a Classic Load Balancer (CLB) — outdated and limited. The AWS Load Balancer Controller replaces this: Services get Network Load Balancers (NLB), and Ingress resources get Application Load Balancers (ALB) with path routing, WAF, Cognito auth, and SSL via ACM.

ResourceWithout ControllerWith AWS LBC
Service LoadBalancerClassic LB (CLB)NLB (faster, cheaper)
IngressNot native to AWSALB with path routing, WAF, Auth
SSLManual setupACM certificate auto-attached
Target modeNodePort onlyIP mode (direct pod targeting)

Install AWS Load Balancer Controller

bash
# Step 1: Create IAM policy for the controller
curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.7.1/docs/install/iam_policy.json

aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

# Step 2: Create IAM service account (IRSA - IAM Roles for Service Accounts)
eksctl create iamserviceaccount \
  --cluster=shopnow-cluster \
  --namespace=kube-system \
  --name=aws-load-balancer-controller \
  --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn=arn:aws:iam::ACCOUNT_ID:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

# Step 3: Install via Helm
helm repo add eks https://aws.github.io/eks-charts
helm repo update

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=shopnow-cluster \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=ap-south-1 \
  --set vpcId=vpc-0abc123def456

# Verify
kubectl get deployment -n kube-system aws-load-balancer-controller

Ingress with AWS ALB

YAMLalb-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shopnow-alb-ingress
  namespace: shopnow
  annotations:
    # Tell AWS LBC to create an ALB (not nginx handles this)
    kubernetes.io/ingress.class: alb
    
    # ALB scheme: internet-facing (public) or internal (private VPC)
    alb.ingress.kubernetes.io/scheme: internet-facing
    
    # Target type: ip = route directly to pod IPs (more efficient)
    alb.ingress.kubernetes.io/target-type: ip
    
    # SSL: ACM certificate ARN
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:123:certificate/abc-123
    
    # Force HTTPS redirect
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    
    # AWS WAF association (attach a WebACL for DDoS protection)
    alb.ingress.kubernetes.io/wafv2-acl-arn: arn:aws:wafv2:...
    
    # Health check configuration
    alb.ingress.kubernetes.io/healthcheck-path: /health
    alb.ingress.kubernetes.io/healthcheck-interval-seconds: "30"
    
    # Attach ALB to specific subnets (public subnets)
    alb.ingress.kubernetes.io/subnets: subnet-abc123, subnet-def456

spec:
  ingressClassName: alb
  rules:
  - host: shopnow.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-svc
            port:
              number: 80
💡 IRSA (IAM Roles for Service Accounts): AWS LBC needs IAM permissions to create ALBs, Target Groups, and Security Groups. IRSA links a Kubernetes Service Account to an AWS IAM Role, so pods running with that Service Account can make AWS API calls without using EC2 instance credentials. This is the AWS-native, secure way to grant AWS permissions to pods.

🔒 Network Policies — Pod-Level Firewall

📖 Story

By default, every pod in your cluster can talk to every other pod — including pods in other namespaces. A hacker who compromises your frontend pod can directly connect to your database! Network Policies let you say: "Only the API pod can connect to MySQL. Frontend pods cannot."

⚠️ Default K8s behavior: All pods can communicate with all other pods across all namespaces. This is an open network. You MUST add Network Policies in production to implement least-privilege networking.
YAMLdeny-all-then-allow.yaml
# ── STEP 1: Deny ALL ingress to the database namespace ────────────
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress          # ← Start with zero trust
  namespace: shopnow
spec:
  podSelector: {}                 # ← {} means: apply to ALL pods in namespace
  policyTypes:
  - Ingress                       # ← Block all incoming connections
  # No ingress rules = deny everything
---
# ── STEP 2: Allow ONLY api pods to reach mysql pods ───────────────
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-mysql
  namespace: shopnow
spec:
  podSelector:                    # ← Apply this policy TO mysql pods
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress                       # ← Control incoming connections to mysql
  ingress:
  - from:                         # ← Allow traffic FROM:
    - podSelector:
        matchLabels:
          app: api                # ← Only pods with label app=api
      namespaceSelector:          # ← AND only from shopnow namespace
        matchLabels:
          kubernetes.io/metadata.name: shopnow
    ports:
    - protocol: TCP
      port: 3306                  # ← Only on MySQL port
---
# ── STEP 3: Allow API pods to receive traffic from Ingress ────────
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-to-api
  namespace: shopnow
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress-nginx
      podSelector:
        matchLabels:
          app.kubernetes.io/name: ingress-nginx
    ports:
    - protocol: TCP
      port: 8080

Word-by-Word: podSelector in policyTypes

podSelector: {} (empty)
Meaning: Apply this policy to ALL pods in the namespace. If you specify matchLabels, it applies only to pods with those labels.
ingress.from with both podSelector AND namespaceSelector
AND vs OR logic: When you put podSelector and namespaceSelector in the SAME list item (using -), it's an AND (must match both). If you put them as separate - items, it's an OR. This is a common confusion in K8s network policy.
⚠️ Network Policy requires a CNI that supports it!
AWS VPC CNI by itself does NOT enforce NetworkPolicies. On EKS you need either: 1) AWS VPC CNI + Network Policy Controller (aws-network-policy-controller add-on), or 2) Install Calico or Cilium as a replacement CNI.

Enable Network Policy on EKS

bash
# Enable the Amazon VPC CNI Network Policy Controller (AWS-native, no Calico needed)
aws eks update-addon \
  --cluster-name shopnow-cluster \
  --addon-name vpc-cni \
  --configuration-values '{"enableNetworkPolicy": "true"}' \
  --region ap-south-1

# OR install Calico (open source, more features)
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.27.0/manifests/calico.yaml

🏗️ AWS VPC CNI — How EKS Pod Networking Works

The AWS VPC CNI (Container Network Interface) plugin is what runs on every EKS node and gives each pod a real VPC IP address from your subnets. This is fundamentally different from how vanilla Kubernetes (or GKE) handles networking.

Without AWS VPC CNI (generic K8s): With AWS VPC CNI (EKS): Node IP: 10.0.1.100 Node IP: 10.0.1.100 Pod IPs: 192.168.1.x (overlay network) Pod IPs: 10.0.1.101, 10.0.1.102 Pod→External: NAT translation needed Pod→External: No NAT (VPC native) AWS VPC CNI Architecture: EC2 Node (t3.medium = max 6 ENIs × 6 IPs = 36 pods max) ┌────────────────────────────────────────────────────────┐ │ eth0 (primary ENI): 10.0.1.100 │ │ eth1 (secondary ENI): 10.0.1.101, 10.0.1.102 │ │ ├── pod-1 (10.0.1.101) │ │ └── pod-2 (10.0.1.102) │ │ eth2 (secondary ENI): 10.0.1.103, 10.0.1.104 │ │ ├── pod-3 (10.0.1.103) │ │ └── pod-4 (10.0.1.104) │ └────────────────────────────────────────────────────────┘ ✅ Each pod has a REAL VPC IP visible in your AWS Console ✅ Pods can talk to RDS, ElastiCache, other AWS services directly ✅ Security Groups on pods (not just nodes) ⚠️ Pod count limited by instance type's ENI/IP limits

  -n shopnow

  --port=80 \
  --name=api-svc \
  -n shopnow

# Create Ingress routing /api → api-svc, / → frontend-svc
cat > shopnow-ingress.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shopnow-ingress
  namespace: shopnow
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - host: shopnow.local
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-svc
            port:
              number: 80
EOF

kubectl apply -f shopnow-ingress.yaml

# Get minikube IP
minikube ip   # e.g., 192.168.49.2

# Add to /etc/hosts (Linux/Mac):
echo "$(minikube ip) shopnow.local" | sudo tee -a /etc/hosts

# Test routing
curl http://shopnow.local/         # Gets nginx (frontend)
curl http://shopnow.local/api      # Gets httpd (api)

Lab 6: Test Network Policies

1
bash
# Deploy two pods: web and db
kubectl run web --image=nginx:1.25 --labels=app=web -n shopnow
kubectl run db  --image=nginx:1.25 --labels=app=db  -n shopnow

# Test: web can reach db (default = open)
kubectl exec web -n shopnow -- wget -q -O- http://$(kubectl get pod db -n shopnow -o jsonpath='{.status.podIP}')
# Should succeed: "Welcome to nginx!"

# Apply deny-all policy
cat > deny-all.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: shopnow
spec:
  podSelector: {}
  policyTypes:
  - Ingress
EOF
kubectl apply -f deny-all.yaml

# Test again: web cannot reach db now!
kubectl exec web -n shopnow -- wget -q -O- --timeout=3 http://$(kubectl get pod db -n shopnow -o jsonpath='{.status.podIP}')
# Timeout! Network policy is blocking it.

# Allow web → db selectively
cat > allow-web-to-db.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: shopnow
spec:
  podSelector:
    matchLabels:
      app: db
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web
EOF
kubectl apply -f allow-web-to-db.yaml

# Test: web → db works, other pods → db still blocked
kubectl exec web -n shopnow -- wget -q -O- http://$(kubectl get pod db -n shopnow -o jsonpath='{.status.podIP}')
# ✅ Succeeds again — only web pod allowed!

🎯 Interview Questions — Part 3

🎯 Interview Prep — 4 YOE Level

Q1: What is an Ingress in Kubernetes? How is it different from a Service?

A: A Service provides a stable ClusterIP and does L4 (TCP) load balancing to pods. An Ingress provides L7 (HTTP/HTTPS) routing based on hostname and URL path. Ingress can route requests to multiple different Services from a single entry point, handle TLS termination, and implement rate limiting or auth — things a Service cannot do. You need an Ingress Controller (nginx, AWS ALB) to actually implement the Ingress rules.

Q2: Explain how AWS VPC CNI differs from standard Kubernetes networking.

A: Standard K8s networking uses an overlay network — pods get IPs from a virtual network (like 192.168.x.x) that doesn't exist in the underlying infrastructure. Traffic between nodes needs encapsulation (VXLAN/tunneling). AWS VPC CNI gives every pod a real VPC IP from your subnet CIDR — pods are first-class citizens in your VPC. This means: no NAT for pod traffic, pods appear in VPC routing tables, Security Groups can be applied per pod (not just per node), and pods communicate directly with AWS services like RDS. The tradeoff: pod count per node is limited by EC2 ENI/IP limits.

Q3: What is the default behavior for pod-to-pod network communication? Is it secure by default?

A: By default, all pods can communicate with all other pods across all namespaces — no network restrictions. This is NOT secure. If a frontend pod is compromised, an attacker can directly connect to your database pod. Network Policies add the zero-trust model. Best practice: start with a deny-all Network Policy in every namespace, then add explicit allow rules for only the connections that are needed. Also note: Network Policies require a CNI that supports them (AWS VPC CNI with the network policy add-on, or Calico/Cilium).

Q4: What is IRSA and why is it important on EKS?

A: IRSA (IAM Roles for Service Accounts) links a Kubernetes Service Account to an AWS IAM Role. When a pod uses that Service Account, the AWS SDK running inside the pod automatically assumes the IAM role — no credentials needed in the container. This replaces the older approach of attaching IAM permissions to EC2 node instance profiles (which gives ALL pods on that node the same AWS permissions). IRSA enables least-privilege — each pod gets only the AWS permissions it needs.

Q5: How does CoreDNS enable service discovery in Kubernetes?

A: CoreDNS runs as pods in kube-system namespace and watches the K8s API for Services. When a Service is created, CoreDNS automatically adds a DNS A record: service-name.namespace.svc.cluster.local → ClusterIP. Each pod's /etc/resolv.conf is configured by kubelet to search these domains automatically. So a pod in the "shopnow" namespace can reach mysql-svc just by name — no hardcoded IPs needed. For StatefulSets with a headless service, CoreDNS creates individual records per pod: pod-0.service-name.namespace.svc.cluster.local.
