1. The Business Scenario — Why This Project Exists

When ShopNow Retail first moved to EKS, the engineer setting it up did the fastest thing that worked: kubectl expose deployment order-service --type=LoadBalancer. This silently provisions a "Classic Load Balancer" for every single service that needs one — and eight months later, ShopNow's AWS bill review turned up fourteen separate Classic Load Balancers, one per service, each billed independently, none of them supporting modern routing rules, host-based paths, or WAF integration, and several of them completely forgotten about, still running, attached to services nobody used anymore.

Ramesh's ask: "I want one clean, understood way that traffic gets from the internet into our pods. HTTP and HTTPS traffic should go through a shared Application Load Balancer with proper routing. Anything that genuinely needs raw TCP — like our internal gRPC service — should go through a Network Load Balancer instead, deliberately, not by accident. And I want to be able to draw the exact path a request takes, from a customer's browser down to a specific pod, on a whiteboard, in under a minute."

This use case builds exactly that clarity: the AWS Load Balancer Controller as the single, understood bridge between AWS's load balancing layer and Kubernetes' own Ingress and Service objects — replacing ad-hoc, expensive, unmanaged load balancers with a consistent, GitOps-managed pattern.

2. The Core Idea — ALB vs NLB vs Ingress, and How They Actually Relate

User
↓
AWS ALB
↓
Kubernetes Ingress
↓
Service
↓
Application Pods

This diagram, exactly as given in the original ask, is the mental model for the entire use case — but each arrow hides a mechanism worth naming precisely, because "how does traffic actually get from the ALB to a pod" is a very common interview question that a surprising number of engineers can't answer past "the Ingress routes it."

LayerWhat it actually isWho manages it
AWS ALBA real AWS resource (Application Load Balancer) — Layer 7, understands HTTP/HTTPS, host and path routingCreated and updated automatically by the AWS Load Balancer Controller, based on your Ingress object
Kubernetes IngressA Kubernetes API object — just a set of routing rules, with no traffic-handling capability of its ownYou declare it in YAML; it does nothing by itself without a controller watching it
AWS Load Balancer ControllerA pod running inside your cluster that watches Ingress and Service objects and translates them into real AWS API callsInstalled once per cluster (section 9)
Service (type: ClusterIP)Internal-only Kubernetes networking — the ALB Controller registers pod IPs directly into an AWS Target Group, bypassing the Service's own internal load-balancing entirely when using target-type: ipYou declare it; kube-proxy and the ALB Controller both use it, differently
Application PodsWhere the request finally landsYour Deployment
The detail most engineers get wrong: with target-type: ip (the mode used throughout this series), the ALB sends traffic directly to pod IPs, not to the Service at all. The Service object still exists and still matters — the Ingress references it by name, and the ALB Controller reads the Service's Endpoints to learn which pod IPs to register — but the actual customer request, once the Target Group is built, never passes through kube-proxy or the Service's virtual IP. This is different from target-type: instance (the older mode), which does route through the Service via a NodePort. Knowing this distinction, and being able to explain why ip mode is preferred (fewer network hops, more accurate health checks, no dependency on NodePort ranges) is exactly the kind of depth that separates a surface-level answer from a strong one.

Where NLB fits — a genuinely different tool, not a smaller ALB

Application Load Balancer (ALB)Network Load Balancer (NLB)
OSI LayerLayer 7 (HTTP/HTTPS)Layer 4 (raw TCP/UDP)
UnderstandsHosts, paths, headers — can route /api/orders and /api/catalog differentlyOnly IP + port — no visibility into HTTP semantics at all
Kubernetes object usedIngressService of type: LoadBalancer, with NLB annotations
ShopNow's useAll customer-facing web/API traffic (shopnow.com)Internal gRPC service between Order Service and a fulfillment partner's system, and the TLS-terminating internal webhook receiver from Use Case 7
Why not just use ALB for everything?—gRPC and raw TCP protocols don't fit HTTP host/path routing semantics; NLB's ultra-low latency and static IP support also matter for time-sensitive internal traffic

4. Application Architecture

   Customer Browser (HTTPS)                Internal Fulfillment Partner (gRPC/TCP)
           |                                              |
     AWS ALB (Layer 7)                          AWS NLB (Layer 4)
           |                                              |
   Kubernetes Ingress                         Kubernetes Service (type=LoadBalancer,
    (host + path rules)                        NLB annotations, no Ingress involved)
           |                                              |
  order-service-svc (ClusterIP)               fulfillment-grpc-svc
           |                                              |
    Order Service Pods                    Fulfillment gRPC Service Pods

Both paths terminate in ordinary Kubernetes pods — the entire difference between them is which AWS load balancer type sits at the front door and which Kubernetes object (Ingress vs Service) the AWS Load Balancer Controller is watching to configure it.

No exposure-specific node sizing is needed — the AWS Load Balancer Controller itself is lightweight (typically 2 small replicas for HA) and the ALB/NLB resources it manages live entirely outside the cluster in AWS, not as cluster compute.

7. VPC and Networking

This use case has one VPC requirement that's easy to get wrong: subnets must be explicitly tagged so the AWS Load Balancer Controller knows where it's allowed to place load balancer network interfaces.

# Public subnets — tag for ALB/NLB internet-facing placement
aws ec2 create-tags --resources subnet-pub1 subnet-pub2 subnet-pub3 \
  --tags Key=kubernetes.io/role/elb,Value=1

# Private subnets — tag for internal-facing load balancer placement
aws ec2 create-tags --resources subnet-priv1 subnet-priv2 subnet-priv3 \
  --tags Key=kubernetes.io/role/internal-elb,Value=1

# Every subnet also needs the cluster-association tag (usually set by eksctl automatically)
aws ec2 create-tags --resources subnet-pub1 subnet-pub2 subnet-pub3 subnet-priv1 subnet-priv2 subnet-priv3 \
  --tags Key=kubernetes.io/cluster/shopnow-cluster,Value=shared
Missing these tags is the single most common reason an Ingress or LoadBalancer Service gets stuck with no ADDRESS. The AWS Load Balancer Controller uses these exact tags to auto-discover which subnets it's allowed to use — without them, it has no idea where to place the load balancer's network interfaces, and fails silently in its own logs rather than in anything visible from kubectl get ingress.

8. IAM Roles and IRSA for the Controller Itself

# The controller needs broad EC2/ELB permissions — it's provisioning real AWS
# infrastructure (load balancers, target groups, security group rules) on your behalf
curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json

aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

eksctl create iamserviceaccount \
  --cluster shopnow-cluster \
  --namespace kube-system \
  --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::111122223333:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve
This is the same IRSA pattern from Use Case 7, applied to a platform component instead of an application. The controller pod itself has no long-lived AWS credentials — it authenticates via its ServiceAccount's bound IAM role, and that role is what actually has permission to call CreateLoadBalancer, CreateTargetGroup, ModifyListener, and similar EC2/ELB APIs on ShopNow's behalf.

10. Exposing HTTP(S) Traffic via ALB Ingress

# services/order-service/base/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-service-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: shopnow-shared-alb   # <-- see callout below
    alb.ingress.kubernetes.io/healthcheck-path: /actuator/health/readiness
    alb.ingress.kubernetes.io/healthcheck-interval-seconds: "15"
    alb.ingress.kubernetes.io/success-codes: "200"
spec:
  rules:
    - host: shopnow.com
      http:
        paths:
          - path: /api/orders
            pathType: Prefix
            backend: { service: { name: order-service-svc, port: { number: 80 } } }
The group.name annotation is the answer to section 1's "fourteen load balancers" problem. Every Ingress across every service in ShopNow that shares this same group.name value gets merged by the controller into one single ALB, with each Ingress contributing its own listener rule. Catalog Service's Ingress, Payment Service's Ingress, and this one all point at the same physical load balancer — this is the exact mechanism that took ShopNow from fourteen billed load balancers down to one.

11. HTTPS/TLS — ACM, Redirect, and Security Policy

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-service-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: shopnow-shared-alb
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:111122223333:certificate/xxxx
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/ssl-policy: ELBSecurityPolicy-TLS13-1-2-2021-06
spec:
  rules:
    - host: shopnow.com
      http:
        paths:
          - path: /api/orders
            pathType: Prefix
            backend: { service: { name: order-service-svc, port: { number: 80 } } }
1certificate-arn points at an ACM certificate — TLS is terminated at the ALB, not inside the pods. This means Order Service's containers only ever need to speak plain HTTP on port 8080 internally; they never handle certificates or private keys at all, which is deliberately simpler and matches the "certificates are AWS's job when they can be" principle from Use Case 7.
2listen-ports opens both 80 and 443, and ssl-redirect: "443" makes the controller automatically configure the ALB to redirect any plain HTTP request straight to HTTPS — customers typing http://shopnow.com are bounced to the secure version before the request ever reaches a pod.
3ssl-policy pins the allowed TLS versions and ciphers — TLS13-1-2-2021-06 disables old, weak TLS versions at the load balancer, protecting every backend service behind this shared ALB without any application code change.

12. Exposing TCP Traffic via Network Load Balancer

# services/fulfillment-grpc-service/base/service-nlb.yaml
apiVersion: v1
kind: Service
metadata:
  name: fulfillment-grpc-svc
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: external
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-scheme: internal   # never internet-facing — internal traffic only
    service.beta.kubernetes.io/aws-load-balancer-healthcheck-protocol: TCP
spec:
  type: LoadBalancer
  selector: { app: fulfillment-grpc-service }
  ports:
    - port: 50051
      targetPort: 50051
      protocol: TCP

Notice there is no Ingress object at all for this service — NLB exposure happens directly through annotations on a Service of type: LoadBalancer, exactly matching the "Kubernetes Service" row from section 2's comparison table. The AWS Load Balancer Controller watches for these specific annotations and provisions a Network Load Balancer instead of the older, unmanaged Classic Load Balancer that plain type: LoadBalancer would have created before this controller existed.

Why scheme: internal here specifically? This gRPC service talks only to ShopNow's fulfillment partner over a private connection (a VPN or Direct Connect link, not the public internet), so it deliberately never gets a public IP at all — a concrete example of matching exposure scope to actual need, the same judgment-call theme that's run through every deployment-strategy use case in this series.

13. Deployment and Service — Completing the Flow

# services/order-service/base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-service, labels: { app: order-service } }
spec:
  replicas: 6
  selector: { matchLabels: { app: order-service } }
  template:
    metadata: { labels: { app: order-service } }
    spec:
      containers:
        - name: order-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service:prod-v3.4.0
          ports: [{ containerPort: 8080 }]
          readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, initialDelaySeconds: 20, periodSeconds: 10 }
          resources:
            requests: { cpu: "250m", memory: "512Mi" }
            limits:   { cpu: "1", memory: "1Gi" }
---
# services/order-service/base/service.yaml — a plain ClusterIP, deliberately NOT
# type: LoadBalancer, because the Ingress + ALB in front of it already handles
# external exposure; this Service exists only to give the Ingress a name to
# reference and a set of pod IPs to discover
apiVersion: v1
kind: Service
metadata: { name: order-service-svc }
spec:
  type: ClusterIP
  selector: { app: order-service }
  ports: [{ port: 80, targetPort: 8080 }]
A ClusterIP Service in front of an ALB Ingress is correct, not a mistake — this trips people up. Since target-type: ip means the ALB talks to pod IPs directly, the Service never needs to be internet-reachable itself; it only needs to exist so the Ingress has something to point at and the controller can read its Endpoints. Setting this Service's type to LoadBalancer as well would be redundant and would create a second, unwanted load balancer.

15. HPA and Autoscaling

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-service-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }
  minReplicas: 6
  maxReplicas: 15
  metrics: [{ type: Resource, resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } } }]
An important behavior worth knowing: when the HPA scales the Deployment up or down, the AWS Load Balancer Controller automatically detects the Service's changed Endpoints and updates the ALB Target Group's registered IPs to match — no manual Target Group management is ever needed, even as pod count changes continuously.

CloudWatch (section 22) shows what the ALB itself measured — request counts, target health, 4xx/5xx rates directly from AWS's perspective. Comparing both together is how you catch, for example, an ALB reporting healthy targets while the application itself is quietly logging elevated error rates — two different vantage points on the same request path.

22. CloudWatch Logging — ALB Access Logs

# Enable ALB access logs, delivered to S3, via an Ingress annotation
    alb.ingress.kubernetes.io/load-balancer-attributes: |
      access_logs.s3.enabled=true,
      access_logs.s3.bucket=shopnow-alb-access-logs,
      access_logs.s3.prefix=order-service

# Standard Fluent Bit shipping for application-level pod logs, unchanged from earlier use cases
apiVersion: v1
kind: ConfigMap
metadata: { name: fluent-bit-config, namespace: amazon-cloudwatch }
data:
  output.conf: |
    [OUTPUT]
        Name                cloudwatch_logs
        Match               kube.*
        region              ap-south-1
        log_group_name      /eks/shopnow/order-service
        auto_create_group   true
ALB access logs and pod logs answer different questions, and both matter. ALB access logs (in S3, queryable via Athena) show every request that hit the load balancer — including ones that never reached a healthy pod at all, such as requests rejected by WAF or ones that hit a target group with zero healthy targets. Pod logs only show what the application itself actually processed. A request that "disappeared" — the customer saw an error but no pod log shows it — is a classic sign to check the ALB access logs first.

# generate_report.py
import argparse, subprocess, json, datetime

def get_ingress_status(name, ns="prod"):
    out = subprocess.run(["kubectl", "get", "ingress", name, "-n", ns, "-o", "json"], capture_output=True, text=True)
    d = json.loads(out.stdout)
    return d.get("status", {}).get("loadBalancer", {}).get("ingress", [{}])[0].get("hostname", "NOT ASSIGNED")

def build_report(build_no, status):
    alb_host = get_ingress_status("order-service-ingress")
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Exposure Report — order-service (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <p>ALB Hostname: {alb_host}</p>
    </body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":

    args = parser.parse_args()

# verify_exposure.py — the pipeline gate referenced in section 19
import requests, argparse, sys

def verify(url):
    checks = []
    r = requests.get(url.replace("https://", "http://"), allow_redirects=False, timeout=5)
    checks.append(("HTTP redirects to HTTPS", r.status_code in (301, 302)))

    r = requests.get(url, timeout=5)
    checks.append(("HTTPS returns 200", r.status_code == 200))

    failed = [name for name, ok in checks if not ok]
    if failed:
        print("EXPOSURE VERIFICATION FAILED:", failed)
        sys.exit(1)
    print("EXPOSURE VERIFIED: HTTPS live, HTTP redirect working")

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--url", required=True)
    args = p.parse_args()
    verify(args.url)

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] order-service exposure deploy - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com"
    msg.attach(MIMEText(f"Build: #{build_no}\nStatus: {status}\n\nSee attached report for ALB hostname and health status.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
