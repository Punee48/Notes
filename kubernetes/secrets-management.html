1. The Business Scenario — Why This Project Exists

A new hire at ShopNow Retail was debugging the Order Service last month and ran git log -p out of curiosity. Three commits back, in a YAML file someone had "temporarily" hard-coded for a quick local test, sat the production RDS database password in plaintext. It had been sitting in the Git history — visible to every engineer with repo access, and permanently unremovable without a painful history rewrite — for six weeks before anyone noticed. Nobody had misused it. But the security team's incident report was blunt: "We got lucky. This is exactly how a breach starts."

Ramesh's ask, delivered with more urgency than usual: "Every credential — database passwords, API keys, AWS credentials, certificates, third-party tokens — needs to live somewhere that isn't Git and isn't a plaintext Kubernetes Secret either. I want it centrally managed, encrypted, access-controlled per service, rotatable without a redeploy, and I want an audit trail of who or what read it and when."

This use case is the direct answer: AWS Secrets Manager as the single source of truth for every credential ShopNow's applications use, synced securely into Kubernetes via IRSA. This is one of the highest-value skills you can demonstrate, because "how do you handle secrets" is a question that comes up in nearly every DevOps interview, and a shaky answer here undermines confidence in everything else you say.

2. The Core Idea — Why Not Just Use Kubernetes Secrets Alone

The uncomfortable truth about native Kubernetes Secrets: despite the name, a plain Kubernetes Secret object is only base64-encoded, not encrypted, by default. Base64 is an encoding, not encryption — anyone with kubectl get secret -o yaml access and thirty seconds can decode it. Kubernetes Secrets are also stored in etcd, and unless etcd encryption-at-rest is explicitly configured, they sit there in a form barely more protected than a ConfigMap.

This use case doesn't abandon Kubernetes Secrets — it uses them as the final, in-cluster delivery mechanism, but treats AWS Secrets Manager as the actual source of truth and security boundary, with three concrete benefits Kubernetes Secrets alone can't give you:

CapabilityKubernetes Secret aloneAWS Secrets Manager + IRSA + External Secrets Operator
Encryption at restOnly if etcd encryption is separately configuredAlways encrypted with a KMS key, by default
Access control granularityKubernetes RBAC only — namespace/cluster-scopedPer-secret IAM policy, scoped to exactly one pod's identity via IRSA
Automatic rotationNot built in — requires custom toolingNative rotation support (e.g. RDS password rotation) with zero app-side changes
Audit trailKubernetes audit logs only, if enabledEvery read logged in AWS CloudTrail, showing exactly which IAM role fetched which secret and when
Central management across clusters/accountsEach cluster's Secrets are siloedOne Secrets Manager, referenced by any number of clusters or accounts via IAM

4. Application Architecture

              Order Service pod starts up
                        |
        kubelet mounts the ServiceAccount token
        (bound to the order-service-sa IRSA role)
                        |
        External Secrets Operator, running as its
        own pod, uses that IRSA-backed identity to
        call AWS Secrets Manager's GetSecretValue API
                        |
        AWS validates the IAM role is allowed to read
        EXACTLY this secret (scoped IAM policy)
                        |
        Secret value returned, ESO writes it into a
        native Kubernetes Secret object in-cluster
                        |
        Order Service pod mounts/reads that Secret,
        exactly like any normal Kubernetes Secret

The service used for this use case is ShopNow's Order Service (Java Spring Boot) — chosen because it genuinely needs every category of sensitive data named in the original ask: a database password, a payment gateway API key, AWS credentials for writing invoices to S3, a TLS certificate for a secure webhook endpoint, and a third-party token for the shipping-carrier API.

6. EKS Cluster Design

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: shopnow-cluster
  region: ap-south-1
  version: "1.29"
iam:
  withOIDC: true    # REQUIRED — IRSA cannot work without an OIDC provider associated to the cluster
managedNodeGroups:
  - name: ng-general
    instanceType: m5.large
    desiredCapacity: 3
    minSize: 3
    maxSize: 8
withOIDC: true is the single most important line in this entire section. IRSA works by having AWS IAM trust your EKS cluster's OIDC identity provider — without this, none of the IRSA role bindings anywhere else in this document can function, and Kubernetes ServiceAccounts have no way to prove their identity to AWS at all.

7. VPC and Networking

Standard VPC design from earlier use cases. One addition specific to this use case: an Interface VPC Endpoint for Secrets Manager (com.amazonaws.ap-south-1.secretsmanager) in the private subnets, so that calls from pods to Secrets Manager never leave the AWS network via the NAT Gateway and public internet — keeping credential-fetch traffic entirely inside AWS's private network path.

aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --service-name com.amazonaws.ap-south-1.secretsmanager \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-priv1 subnet-priv2 subnet-priv3 \
  --security-group-ids sg-secretsmanager-endpoint

8. IAM Roles and IRSA — The Full Trust Chain, Explained

This is the mechanism the entire use case is built on, so it's worth walking through every link in the chain rather than just showing the final command.

1EKS's OIDC provider is registered as a trusted identity provider in AWS IAM (enabled by withOIDC: true above). This means AWS IAM is now willing to trust tokens issued by your Kubernetes cluster's own token issuer, the same way it trusts AWS's own IAM users.
2An IAM Role is created with a trust policy that says, specifically: "trust tokens from this EKS cluster's OIDC provider, but only if the token belongs to ServiceAccount order-service-sa in namespace prod." This is the scoping that stops any other pod in the cluster from assuming this role.
3A Kubernetes ServiceAccount named order-service-sa is annotated with that IAM Role's ARN. This annotation is what tells the AWS SDK running inside the pod which role to request tokens for.
4The pod's spec sets serviceAccountName: order-service-sa. When the pod starts, EKS's Pod Identity webhook automatically injects a projected, short-lived, auto-rotating token and the right environment variables — the application code (or, in this use case, the External Secrets Operator) never handles a long-lived AWS access key at all.
# Step 2 + 3 combined, via eksctl
eksctl create iamserviceaccount \
  --cluster shopnow-cluster \
  --namespace prod \
  --name order-service-sa \
  --attach-policy-arn arn:aws:iam::111122223333:policy/order-service-secrets-policy \
  --approve

# The IAM policy — scoped to ONLY order-service's own secrets, nothing else
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue", "secretsmanager:DescribeSecret"],
      "Resource": "arn:aws:secretsmanager:ap-south-1:111122223333:secret:shopnow/prod/order-service/*"
    },
    {
      "Effect": "Allow",
      "Action": ["kms:Decrypt"],
      "Resource": "arn:aws:kms:ap-south-1:111122223333:key/shopnow-secrets-key",
      "Condition": { "StringEquals": { "kms:ViaService": "secretsmanager.ap-south-1.amazonaws.com" } }
    }
  ]
}
Two permissions, not one. Reading a secret from Secrets Manager isn't enough by itself — the secret is encrypted with a KMS key, so the role also needs kms:Decrypt on that specific key. Forgetting the KMS half of this policy is one of the most common real-world IRSA misconfigurations, and produces a confusing "access denied" error that looks like a Secrets Manager permission problem when it's actually a KMS one.

9. Creating the Secrets in AWS Secrets Manager

# Database password
aws secretsmanager create-secret \
  --name shopnow/prod/order-service/db-password \
  --secret-string '{"username":"order_svc","password":"REPLACED_AT_CREATE_TIME"}' \
  --kms-key-id alias/shopnow-secrets-key

# Payment gateway API key
aws secretsmanager create-secret \
  --name shopnow/prod/order-service/payment-api-key \
  --secret-string '{"api_key":"REPLACED_AT_CREATE_TIME"}' \
  --kms-key-id alias/shopnow-secrets-key

# AWS credentials for writing invoice PDFs to a specific S3 bucket
# (used only where IRSA itself can't be used directly — e.g. a legacy library
# that requires static keys instead of the SDK's default credential chain)
aws secretsmanager create-secret \
  --name shopnow/prod/order-service/invoice-s3-creds \
  --secret-string '{"access_key_id":"REPLACED","secret_access_key":"REPLACED"}' \
  --kms-key-id alias/shopnow-secrets-key

# Third-party shipping carrier API token
aws secretsmanager create-secret \
  --name shopnow/prod/order-service/shipping-carrier-token \
  --secret-string '{"token":"REPLACED_AT_CREATE_TIME"}' \
  --kms-key-id alias/shopnow-secrets-key
Why is there a separate "invoice-s3-creds" secret if IRSA already gives pods AWS access? This is intentionally included as a teaching point: the strongly preferred approach is to give the pod an IRSA role with direct S3 permissions and never create static AWS access keys at all. The only time you'd store AWS credentials as a secret is a legacy or third-party library that can't use the AWS SDK's automatic credential chain. If asked in an interview "when would you store AWS credentials as a Secret," the correct answer starts with "ideally never — IRSA replaces that need — except for this narrow legacy case."

10. External Secrets Operator — Installation and SecretStore

# One-time cluster install, via Helm
helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets \
  --namespace external-secrets --create-namespace

# The Operator ALSO needs its own IRSA role — it's the one making the AWS calls
eksctl create iamserviceaccount \
  --cluster shopnow-cluster \
  --namespace external-secrets \
  --name external-secrets-sa \
  --attach-policy-arn arn:aws:iam::111122223333:policy/external-secrets-readall-policy \
  --approve

# platform/external-secrets-operator/cluster-secret-store.yaml
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: ap-south-1
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
            namespace: external-secrets
Two IRSA roles are involved in every secret fetch, not one. The External Secrets Operator's own ServiceAccount needs permission to read broadly across ShopNow's secrets (since it serves every team), while each individual application's ServiceAccount (section 8) is scoped narrowly to just its own secrets. This two-layer model is exactly how ShopNow can run one shared operator while still keeping per-service boundaries — the operator is the plumbing, the per-service IAM policy is the actual security boundary.

11. ExternalSecret Objects — Every Sensitive Data Type

# overlays/prod/external-secret.yaml — ONE object per logical secret group,
# pulling every category named in the original business ask
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: order-service-secrets
  namespace: prod
spec:
  refreshInterval: 15m
  secretStoreRef: { name: aws-secrets-manager, kind: ClusterSecretStore }
  target:
    name: order-service-secrets
    creationPolicy: Owner
  data:
    # Database password
    - secretKey: DB_USERNAME
      remoteRef: { key: shopnow/prod/order-service/db-password, property: username }
    - secretKey: DB_PASSWORD
      remoteRef: { key: shopnow/prod/order-service/db-password, property: password }

    # Third-party payment gateway API key
    - secretKey: PAYMENT_API_KEY
      remoteRef: { key: shopnow/prod/order-service/payment-api-key, property: api_key }

    # AWS credentials (legacy invoice library only — see section 9's callout)
    - secretKey: INVOICE_S3_ACCESS_KEY_ID
      remoteRef: { key: shopnow/prod/order-service/invoice-s3-creds, property: access_key_id }
    - secretKey: INVOICE_S3_SECRET_ACCESS_KEY
      remoteRef: { key: shopnow/prod/order-service/invoice-s3-creds, property: secret_access_key }

    # Third-party shipping carrier token
    - secretKey: SHIPPING_CARRIER_TOKEN
      remoteRef: { key: shopnow/prod/order-service/shipping-carrier-token, property: token }

Every category in the original business ask — database passwords, API keys, AWS credentials, third-party tokens — maps to exactly one remoteRef entry here. Certificates are handled separately in the next section, because TLS material has its own lifecycle (expiry, renewal) that a generic ExternalSecret isn't well suited to manage.

12. Certificates — TLS via cert-manager and ACM

Two different certificate needs exist at ShopNow, handled two different ways:

1Public-facing TLS (the ALB's certificate) — handled by AWS Certificate Manager (ACM), referenced directly in the Ingress annotation, as seen in every earlier use case in this series. ACM handles issuance and renewal automatically; nothing in Kubernetes ever touches this certificate's private key at all.
2Internal service-to-service TLS (Order Service's secure webhook endpoint, used by the shipping carrier to push delivery status updates) — handled by cert-manager, running inside the cluster, which issues and auto-renews a certificate as a native Kubernetes Secret.
# platform/cert-manager/cluster-issuer.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: { name: shopnow-internal-ca }
spec:
  ca:
    secretName: shopnow-internal-ca-keypair
---
# overlays/prod/certificate.yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: { name: order-service-webhook-tls, namespace: prod }
spec:
  secretName: order-service-webhook-tls
  duration: 2160h        # 90 days
  renewBefore: 360h     # renew 15 days before expiry, automatically
  issuerRef: { name: shopnow-internal-ca, kind: ClusterIssuer }
  dnsNames: [order-service-webhook.prod.svc.cluster.local]

cert-manager watches this Certificate object continuously and automatically issues a new certificate into the order-service-webhook-tls Secret well before the old one expires — solving certificate expiry, one of the most common causes of unplanned production outages, without any manual renewal process at all.

13. Deployment — Consuming Secrets Correctly

# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-service, labels: { app: order-service } }
spec:
  replicas: 6
  selector: { matchLabels: { app: order-service } }
  template:
    metadata: { labels: { app: order-service } }
    spec:
      serviceAccountName: order-service-sa   # <-- the IRSA identity from section 8
      containers:
        - name: order-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service:prod-v3.4.0
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: order-service-config }
            - secretRef: { name: order-service-secrets }
          volumeMounts:
            - name: webhook-tls
              mountPath: /etc/tls/webhook
              readOnly: true
          resources:
            requests: { cpu: "250m", memory: "512Mi" }
            limits:   { cpu: "1", memory: "1Gi" }
          readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, initialDelaySeconds: 20, periodSeconds: 10 }
      volumes:
        - name: webhook-tls
          secret: { secretName: order-service-webhook-tls }

Two different consumption methods, deliberately, matching the nature of the data: the envFrom secretRef block for credentials the app reads as simple key=value strings (DB password, API keys, tokens), and a volume mount for the TLS certificate, because certificates are files (a cert and a private key), not simple strings — the same env-var-vs-volume-mount distinction explained for ConfigMaps in Use Case 6, section 11, applies identically here.

14. Secret Rotation — Automatic, Without a Redeploy

# Enable native RDS password rotation in Secrets Manager — AWS handles changing
# the actual database password AND updating the secret value, on a schedule
aws secretsmanager rotate-secret \
  --secret-id shopnow/prod/order-service/db-password \
  --rotation-lambda-arn arn:aws:lambda:ap-south-1:111122223333:function:SecretsManagerRDSPostgreSQLRotationSingleUser \
  --rotation-rules AutomaticallyAfterDays=30

Here is the full loop this creates, and why the earlier refreshInterval: 15m from section 11 is the piece that closes it:

AWS rotates the RDS password on schedule
→
Secrets Manager's stored value updates
→
ESO's next refresh (within 15 min) picks up the new value
→
The in-cluster Kubernetes Secret updates
→
App reads the new password — if it re-reads on each connection, no restart needed
The one gap left to call out honestly: if the Order Service caches its database connection pool with credentials read once at startup (common with connection pool libraries), the running pods still won't notice a rotated password until they restart — the same env-var-freeze limitation from Use Case 6. The production-grade fix is a reloader-style controller (or the same configMapGenerator-hash trick, applied to Secrets) that triggers a rolling restart whenever the ExternalSecret's content changes — worth mentioning as the natural next improvement if asked "what would you add to make this fully automatic."

15. RBAC — Who Can Even Read a Secret

# base/rbac.yaml — even engineers with cluster access can't casually read
# raw secret VALUES via kubectl, only Secrets Manager audit-logged access can
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: no-secret-read, namespace: prod }
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["list"]   # engineers can see secret NAMES exist, never their VALUES
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: developers-no-secret-read, namespace: prod }
subjects:
  - kind: Group
    name: shopnow-developers
roleRef: { kind: Role, name: no-secret-read, apiGroup: rbac.authorization.k8s.io }

This closes the loop back to section 2's whole premise: even with everything above in place, a Kubernetes RBAC rule that carelessly grants get on secrets to every developer would let anyone decode the in-cluster Secret directly and bypass the entire AWS-side audit trail. Least-privilege RBAC on the Kubernetes Secret objects themselves is just as necessary as the IAM scoping in section 8 — the two layers protect against different paths to the same data.

19. NetworkPolicies

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-alb-to-order }
spec:
  podSelector: { matchLabels: { app: order-service } }
  policyTypes: [Ingress]
  ingress: [{ from: [], ports: [{ protocol: TCP, port: 8080 }] }]
---
# Restrict egress so a compromised pod can't exfiltrate secrets to an arbitrary
# external endpoint — only allow the specific external hosts the app actually needs
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: order-service-restricted-egress }
spec:
  podSelector: { matchLabels: { app: order-service } }
  policyTypes: [Egress]
  egress:
    - to: [{ podSelector: { matchLabels: { app: catalog-service } } }, { podSelector: { matchLabels: { app: payment-service } } }]
    - to: []
      ports: [{ protocol: TCP, port: 443 }]   # AWS APIs, payment gateway, shipping carrier — HTTPS only
    - to: []
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]  # DNS
Why an egress policy belongs in a secrets use case specifically: even a well-scoped IRSA role can only be misused if a pod can reach the internet to exfiltrate what it fetches. Restricting egress to only the specific destinations Order Service legitimately needs (HTTPS only, no arbitrary outbound) is a defense-in-depth layer against exactly the scenario where a dependency-confusion or supply-chain attack tries to phone a fetched credential home.

21. CI/CD Pipeline — Jenkins and GitHub Actions

// Jenkinsfile
pipeline {
  agent any
  environment { ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/order-service" }
  stages {
    stage('Test') { steps { sh './gradlew test' } }

    stage('Secret Scan Source Code') {
      steps { sh 'gitleaks detect --source . --no-git -v' }
      // fails the build immediately if any credential-shaped string is committed —
      // this is the direct pipeline-level fix for the exact incident in section 1
    }

    stage('Build & Push') {
      steps {
        sh '''
          docker build -t $ECR_REPO:${GIT_COMMIT} .
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:${GIT_COMMIT}
        '''
      }
    }

    stage('Scan Image') {
      steps { sh 'aws ecr start-image-scan --repository-name order-service --image-id imageTag=${GIT_COMMIT}' }
    }

    stage('Deploy') {
      steps {
        sh '''
          kubectl apply -k gitops-repo/services/order-service/overlays/prod
          kubectl rollout status deployment/order-service -n prod --timeout=180s
        '''
      }
    }

    stage('Verify Secrets Synced Correctly') {
      steps {

  syncPolicy: { automated: { prune: true, selfHeal: true } }
This is exactly why ExternalSecret was chosen over sealed-secrets or storing encrypted blobs in Git. Argo CD syncing this Application only ever applies an ExternalSecret object — a reference — never an actual credential. Even a fully compromised Git repository, in this design, leaks zero real secret values, only the names/ARNs of where they live in AWS, which are themselves useless without the matching IRSA-scoped IAM permission.

24. CloudWatch Logging — and What Never Gets Logged

apiVersion: v1
kind: ConfigMap
metadata: { name: fluent-bit-config, namespace: amazon-cloudwatch }
data:
  filters.conf: |
    [FILTER]
        Name          modify
        Match         kube.*
        Condition     Key_value_matches log (?i)(password|api[_-]?key|secret|token)\s*[:=]
        Set           log [REDACTED - possible credential in log line]
  output.conf: |
    [OUTPUT]
        Name                cloudwatch_logs
        Match               kube.*
        region              ap-south-1
        log_group_name      /eks/shopnow/order-service
        auto_create_group   true
This Fluent Bit filter is not optional decoration — it's a required control. Application logs are one of the most common places secrets accidentally leak, usually via a debug log line someone forgot to remove (log.info("connecting with password=" + dbPassword)). A pattern-based redaction filter at the log-shipping layer is a real, standard defense-in-depth control, catching what code review sometimes misses.

30. HTML Deployment/Job Report

# generate_report.py — reports sync health, never secret values
import argparse, subprocess, json, datetime

def get_externalsecret_status(ns="prod"):
    out = subprocess.run(["kubectl", "get", "externalsecret", "-n", ns, "-o", "json"], capture_output=True, text=True)
    items = json.loads(out.stdout)["items"]
    return [(i["metadata"]["name"], i.get("status", {}).get("conditions", [{}])[0].get("status", "Unknown")) for i in items]

def build_report(build_no, status):
    rows = "".join(f"<tr><td>{name}</td><td>{synced}</td></tr>" for name, synced in get_externalsecret_status())
    color = "#5ec98f" if status == "success" else "#e35d5d"
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Secure Deploy Report — order-service (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <p>No secret VALUES are ever included in this report — only sync health.</p>
    <table border="1" cellpadding="8" style="border-collapse:collapse">
      <tr><th>ExternalSecret</th><th>Synced</th></tr>{rows}
    </table></body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    args = parser.parse_args()
    build_report(args.build, args.status)
The report generator's design is itself part of the security model: it deliberately queries only the status.conditions field of each ExternalSecret — never the Secret's data field — so it is structurally impossible for a credential to leak into a report file, an email attachment, or a build log by accident.

31. Email Notification

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] order-service secure deploy - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, security-team@shopnow.com"
    msg.attach(MIMEText(f"Build: #{build_no}\nStatus: {status}\n\nSee attached report. No secret values are ever included in this notification.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
