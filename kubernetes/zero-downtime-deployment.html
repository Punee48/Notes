1. The Business Scenario — Why This Project Exists

Every Friday night, ShopNow Retail's engineering team used to send out a message in the company Slack channel: "Deploying in 5 minutes, checkout will be briefly unavailable." For a company built on impulse purchases during evening scrolling, "briefly unavailable" meant real lost revenue — the old deployment script would stop all running containers, pull the new image, and start fresh containers, and for the ninety seconds in between, every customer hitting shopnow.com got a blank white screen. Last month, a deploy landed exactly when a marketing email went out, and support tickets flooded in asking if the site had been hacked.

Ramesh calls you in: "Puneeth, I don't want to hear 'deploying in 5 minutes' ever again. I want us to be able to ship code in the middle of the day, during peak traffic, and have zero customers notice. Make that true, and prove it's true."

This use case is the answer to that exact ask. It is arguably the single most-asked Kubernetes interview topic, because "how do you deploy without downtime" is a question every company that has ever had a bad Friday-night deploy will ask you. By the end of this document you won't just be able to describe it — you'll have run it, watched it happen live in your terminal, and broken it on purpose to prove the safety nets work.

2. The Core Idea — How Kubernetes Achieves Zero Downtime

Before touching any YAML, it helps to see the mental model in one picture. A rolling update never has an "all pods down" moment — it always keeps enough old pods serving traffic while it slowly brings up new pods, checks that each one is actually healthy, and only then retires an old one.

Start: 4 old pods, 100% traffic
Step 1: 1 new pod added (maxSurge), still all 4 old pods serving
Step 2: new pod passes readiness → 1 old pod removed (maxUnavailable)
Step 3: repeat — one new pod up, one old pod down, always overlapping
Finish: 4 new pods, traffic never touched zero healthy pods

Four separate Kubernetes features work together to make this true, and this use case implements and proves every one of them:

FeatureWhat it guarantees
RollingUpdate strategyControls the pace — how many new pods can come up ahead of schedule, how many old pods can go down at once
Readiness probeStops the Service from sending traffic to a new pod until it proves it's actually able to handle requests, not just "started"
PodDisruptionBudgetProtects against a second, unrelated disruption (like a node drain) happening at the same time as a rolling update and pushing available pods below a safe floor
Multiple replicasWithout at least 2+ replicas, there's no "old pod" to keep serving while a "new pod" comes up — a single-replica Deployment can never be zero-downtime by definition

The detail that matters most here: the AWS Load Balancer Controller watches Kubernetes Endpoints and automatically registers/deregisters pod IPs in the ALB's Target Group as pods become Ready or get terminated — this is the missing link between "Kubernetes knows a pod is ready" and "AWS actually stops sending real customer traffic to a pod that isn't." Without this controller working correctly, everything else in this document can be perfect and customers would still see errors, because the load balancer would keep sending traffic to pod IPs that no longer exist.

Nothing exotic is needed at the cluster level for zero-downtime deploys — this is intentional and worth saying out loud in an interview: zero-downtime deployment is achieved almost entirely through workload-level configuration (Deployment strategy, probes, PDB), not special cluster infrastructure. That's what makes it applicable to any EKS cluster you're handed, not just one built a specific way.

6. VPC and Networking

Standard three-tier VPC — public subnets across 3 AZs for the ALB, private subnets for the EKS worker nodes running the Cart Service pods, and private subnets for the RDS instance. Spreading nodes across 3 Availability Zones matters directly to this use case: with replicas: 4 spread across AZs, an entire AZ going down during a deploy still leaves healthy pods serving traffic in the other two.

8. Deployment with RollingUpdate Strategy — Explained Line by Line

# cart-service-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cart-service
  namespace: prod
  labels: { app: cart-service }
spec:
  replicas: 4
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  minReadySeconds: 10
  selector:
    matchLabels: { app: cart-service }
  template:
    metadata: { labels: { app: cart-service } }
    spec:
      serviceAccountName: cart-service-sa
      terminationGracePeriodSeconds: 30
      containers:
        - name: cart-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/cart-service:prod-v4.1.0
          ports: [{ containerPort: 3000 }]
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 10"]
          envFrom:
            - configMapRef: { name: cart-service-config }
            - secretRef: { name: cart-service-secret }
          resources:
            requests: { cpu: "150m", memory: "256Mi" }
            limits:   { cpu: "400m", memory: "512Mi" }

Every field in strategy and around it exists for a specific reason. Here is what each one does, in the plain language you'd use explaining it out loud on a call:

1replicas: 4 — there must be more than one pod for "keep some old ones running while new ones come up" to even be possible. A Deployment with replicas: 1 physically cannot be rolled out without a gap, no matter what strategy settings you pick.
2maxSurge: 1 — Kubernetes is allowed to create one extra pod above the desired count of 4 while rolling out, so briefly there can be 5 pods total. This is what lets a new pod come up and prove itself before any old pod is touched.
3maxUnavailable: 0 — this is the single most important line in this whole document. It tells Kubernetes it is never allowed to drop below 4 available pods during the rollout. Combined with maxSurge:1, the only possible sequence is: add one new pod, wait for it to be Ready, then remove one old pod — never the other way around.
4minReadySeconds: 10 — even after a new pod's readiness probe first passes, Kubernetes waits an extra 10 seconds of continued healthiness before considering it truly available and moving on to the next pod. This protects against a pod that passes one readiness check and then immediately crashes.
5terminationGracePeriodSeconds: 30 and the preStop hook with sleep 10 — this pair solves a real, commonly-missed race condition: when a pod is marked for termination, Kubernetes tells the Service to stop routing to it and tells the container to shut down at almost the same time. If the container shuts down instantly, a request that was already in flight — or one that the ALB hasn't yet noticed should stop being sent — gets dropped. The preStop sleep buys 10 seconds for that in-flight traffic to drain before the process actually receives SIGTERM.

9. Readiness and Liveness Probes — Explained Line by Line

          readinessProbe:
            httpGet:
              path: /health/ready
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
            successThreshold: 1
          livenessProbe:
            httpGet:
              path: /health/live
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3
1readinessProbe asks one question, repeatedly: "is this pod ready to receive real user traffic right now?" It checks /health/ready, an endpoint the Cart Service exposes that verifies its own database connection pool is initialized and warmed up. Until this passes, Kubernetes never adds the pod's IP to the Service's list of routable endpoints — this is the exact mechanism that stops the new pod in the diagram from getting traffic before it's actually able to serve it.
2livenessProbe asks a different question: "is this pod stuck or deadlocked and needs to be killed and restarted?" It checks /health/live, a much cheaper endpoint that just confirms the process is responsive. This is not about traffic routing — a container can fail liveness and get restarted even though it was never receiving traffic in the first place.
3Why two separate endpoints, not one shared /health? If they were the same endpoint, a temporary database blip would make readiness fail (correctly pulling the pod out of rotation) but would also make liveness fail, causing Kubernetes to restart a perfectly healthy process that was just waiting on the database — restarting it does nothing to fix a database problem and only adds churn. Splitting them lets each probe do only the one job it's meant for.

10. PodDisruptionBudget

# cart-service-pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: cart-service-pdb, namespace: prod }
spec:
  minAvailable: 3
  selector: { matchLabels: { app: cart-service } }
PDB is not for rolling updates — it's for everything else happening at the same time as one. The RollingUpdate maxUnavailable: 0 setting only controls disruptions caused by the Deployment itself. It has zero effect on a completely separate event, like an EKS-managed node upgrade draining a node in the background while your rollout is also in progress. A PDB is a cluster-wide contract that applies no matter why pods are being evicted — with minAvailable: 3 set, Kubernetes will refuse to let a voluntary eviction (a node drain, a cluster-autoscaler scale-down) push the Cart Service below 3 available pods, even in the middle of a deploy.

11. Service and Multiple Replicas

apiVersion: v1
kind: Service
metadata: { name: cart-service-svc, namespace: prod }
spec:
  selector: { app: cart-service }
  ports: [{ port: 80, targetPort: 3000 }]
  type: ClusterIP

The Service's selector is what ties everything together: it doesn't point at specific pod names or IPs, it points at the label app: cart-service. During a rollout, old pods and new pods both carry this same label simultaneously, which is exactly why the Service can smoothly send traffic to a mix of old and new pods mid-rollout without any reconfiguration — from the Service's point of view, there's no such thing as "old" or "new," only "pods with this label that are currently Ready."

13. Ingress with AWS Load Balancer Controller

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cart-service-ingress
  namespace: prod
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-path: /health/ready
    alb.ingress.kubernetes.io/healthcheck-interval-seconds: "10"
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:ap-south-1:111122223333:certificate/xxxx
spec:
  rules:
    - host: shopnow.com
      http:
        paths:
          - path: /api/cart
            pathType: Prefix
            backend: { service: { name: cart-service-svc, port: { number: 80 } } }

Using target-type: ip means the ALB registers pod IPs directly rather than node ports — this is what allows registration and deregistration to happen at the speed of the readiness probe rather than waiting on a slower node-level health check, keeping the ALB's view of "who's healthy" tightly in sync with what Kubernetes already knows.

14. HPA and Autoscaling

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: cart-service-hpa, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: cart-service }
  minReplicas: 4
  maxReplicas: 12
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }

minReplicas: 4 matches the Deployment's baseline — this is deliberate: the HPA is never allowed to scale the fleet down to a count so low that a rolling update's maxUnavailable: 0 guarantee stops being meaningful.

17. CI/CD Pipeline — Jenkins and GitHub Actions

// Jenkinsfile
pipeline {
  agent any
  environment {
    ECR_REPO = "111122223333.dkr.ecr.ap-south-1.amazonaws.com/cart-service"
    IMAGE_TAG = "prod-${GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Test') { steps { sh 'npm ci && npm test' } }
    stage('Build & Push') {
      steps {
        sh '''
          docker build -t $ECR_REPO:$IMAGE_TAG .
          aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REPO
          docker push $ECR_REPO:$IMAGE_TAG
        '''
      }
    }
    stage('Approval') {
      steps { timeout(time: 20, unit: 'MINUTES') { input message: 'Deploy cart-service to prod?' } }
    }
    stage('Rolling Deploy') {
      steps {
        sh '''
          kubectl set image deployment/cart-service cart-service=$ECR_REPO:$IMAGE_TAG -n prod
          kubectl rollout status deployment/cart-service -n prod --timeout=180s
        '''
      }
    }
    stage('Verify Zero Downtime') {
      steps {
        sh 'python3 verify_zero_downtime.py --url https://shopnow.com/api/cart/health --duration 180'
      }
    }
    stage('Report & Notify') {
      steps {
        sh 'python3 generate_report.py --service cart-service --status success --build ${BUILD_NUMBER}'
        sh 'python3 send_email.py --service cart-service --report report.html'
      }
    }
  }
  post { failure { sh 'python3 send_email.py --service cart-service --status FAILED --build ${BUILD_NUMBER}' } }
}

Step 4 — Start a continuous traffic probe BEFORE triggering the deploy

This is the step that actually proves zero downtime, rather than just assuming it. Open a second terminal and leave this running throughout the entire rollout:

# verify_zero_downtime.py — hits the app once per 200ms and records every single failure
import requests, time, argparse, sys

def run(url, duration):
    total, failed, start = 0, 0, time.time()
    failures = []
    while time.time() - start < duration:
        total += 1
        try:
            r = requests.get(url, timeout=2)
            if r.status_code != 200:
                failed += 1
                failures.append((time.time(), r.status_code))
        except Exception as e:
            failed += 1
            failures.append((time.time(), str(e)))
        time.sleep(0.2)
    print(f"Total requests: {total}, Failed: {failed}, Success rate: {(total-failed)/total*100:.2f}%")
    if failed > 0:
        print("FAILURES DETECTED:", failures)
        sys.exit(1)
    print("ZERO DOWNTIME CONFIRMED")

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--url", required=True)
    p.add_argument("--duration", type=int, default=120)
    args = p.parse_args()
    run(args.url, args.duration)

# Terminal 2 — run this and leave it going
python3 verify_zero_downtime.py --url https://shopnow.com/api/cart/health --duration 180

Step 5 — Trigger the rolling update, in Terminal 1, while Terminal 2 is still running

kubectl set image deployment/cart-service \

22. Failure Testing — Proving Zero Downtime Under Stress

# Test 1: Node drain DURING a rollout — confirms PDB and RollingUpdate cooperate correctly
kubectl set image deployment/cart-service cart-service=...:prod-v4.3.0 -n prod &
kubectl drain <a-node-running-cart-pods> --ignore-daemonsets --delete-emptydir-data
# Expected: drain respects the PDB (minAvailable: 3) and waits/retries rather than
# forcefully evicting past the budget, even while the rollout is independently in progress

# Test 2: Deliberately push a broken image and confirm the rollout HALTS instead of taking the app down
kubectl set image deployment/cart-service cart-service=...:broken-build -n prod
kubectl rollout status deployment/cart-service -n prod --timeout=60s
# Expected: times out because the new pods never pass readiness — but the OLD pods
# were never touched (maxUnavailable: 0), so the app stays fully up on the last-good version

# Test 3: Kill a pod mid-rollout and confirm the ReplicaSet replaces it without dropping below floor
kubectl delete pod -n prod -l app=cart-service --field-selector status.phase=Running | head -1

23. Rollback Strategy

# Because Test 2 above shows the rollout halts on its own, "rollback" here means
# explicitly abandoning the stuck rollout and returning to the last-good ReplicaSet
kubectl rollout undo deployment/cart-service -n prod
kubectl rollout status deployment/cart-service -n prod

# The undo is ITSELF a rolling update back to the old image — so even the rollback
# is zero-downtime, using the exact same maxSurge/maxUnavailable/readiness mechanism

# GitOps-managed version:
cd gitops-repo/services/cart-service
git revert <bad-commit-sha> && git push

25. Ansible Automation

Ansible standardizes the "zero-downtime deployment settings" as a reusable role, so every new service ShopNow builds inherits the same RollingUpdate/PDB/probe defaults instead of each team re-deriving them from scratch.

# roles/zero-downtime-deploy/tasks/main.yml
- name: Render Deployment with zero-downtime defaults
  template:
    src: deployment.yaml.j2
    dest: "gitops-repo/services/{{ service_name }}/deployment.yaml"
  vars:
    max_surge: 1
    max_unavailable: 0
    min_ready_seconds: 10
    replica_count: "{{ replicas | default(4) }}"

- name: Render PodDisruptionBudget
  template:
    src: pdb.yaml.j2
    dest: "gitops-repo/services/{{ service_name }}/pdb.yaml"
  vars:
    min_available: "{{ (replica_count | int) - 1 }}"

- name: Apply to cluster
  kubernetes.core.k8s:
    state: present
    src: "gitops-repo/services/{{ service_name }}/"

# generate_report.py — includes the zero-downtime verification result
import argparse, subprocess, json, datetime

def get_rollout_events(service, ns="prod"):
    out = subprocess.run(
        ["kubectl", "rollout", "history", f"deployment/{service}", "-n", ns],
        capture_output=True, text=True
    )
    return out.stdout

def build_report(service, build_no, status, downtime_check):
    color = "#5ec98f" if status == "success" else "#e35d5d"
    dt_color = "#5ec98f" if "CONFIRMED" in downtime_check else "#e35d5d"
    history = get_rollout_events(service)
    html = f"""<html><body style="font-family:Arial;background:#0b0f14;color:#dbe6f0;padding:24px">
    <h2 style="color:{color}">ShopNow Zero-Downtime Deploy Report — {service} (Build #{build_no})</h2>
    <p>Time: {datetime.datetime.now()} | Status: {status.upper()}</p>
    <h3 style="color:{dt_color}">Zero-Downtime Verification: {downtime_check}</h3>
    <pre style="background:#0a0e14;padding:12px;border-radius:6px">{history}</pre>
    </body></html>"""
    with open("report.html", "w") as f:
        f.write(html)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--downtime-check", default="ZERO DOWNTIME CONFIRMED")
    args = parser.parse_args()
    build_report(args.service, args.build, args.status, args.downtime_check)

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(service, status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] {service} zero-downtime deploy - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com"
    msg.attach(MIMEText(f"Service: {service}\nBuild: #{build_no}\nStatus: {status}\n\nSee attached report for rollout history and zero-downtime verification.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--service", required=True)
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.service, args.status, args.build, args.report)
