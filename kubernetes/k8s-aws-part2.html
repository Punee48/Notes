SECTION 2

🗄️ StatefulSet — For Databases & Stateful Applications

📖 Story — Why Deployment Fails for MySQL

You try running MySQL as a Deployment. Three replicas start, but they all try to write to data at the same time — disaster. When you restart a pod, it gets a new hostname (nginx-abc123) and a new volume — all data is lost! Databases need: stable names, stable storage, and ordered start/stop. That's StatefulSet.

Deployment vs StatefulSet

Deployment (stateless)

  • Pods: nginx-abc123 (random hash)
  • Pods are identical and interchangeable
  • Start/stop in any order
  • Shared or no persistent storage
  • Any pod can serve any request

StatefulSet (stateful)

  • Pods: mysql-0, mysql-1, mysql-2
  • Each pod has a unique, stable identity
  • Start sequentially (0, 1, 2) — stop in reverse
  • Each pod gets its own PersistentVolume
  • mysql-0 is the primary, mysql-1/2 are replicas

StatefulSet YAML — Complete with Annotations

YAMLmysql-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet              # ← Key: not Deployment
metadata:
  name: mysql
  namespace: shopnow
spec:
  serviceName: "mysql"         # ← REQUIRED: name of the Headless Service
                               #   This gives pods DNS: mysql-0.mysql.shopnow.svc.cluster.local
  replicas: 3                  # ← Creates mysql-0, mysql-1, mysql-2
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      initContainers:          # ← Runs BEFORE main container; used for setup
      - name: init-mysql
        image: mysql:8.0
        command:               # ← Shell script to assign server-id
        - bash
        - "-c"
        - |
          # mysql-0 gets server-id=1, mysql-1 gets server-id=2, etc.
          [[ $HOSTNAME =~ -([0-9]+)$ ]] && echo $((${BASH_REMATCH[1]} + 1)) > /mnt/conf.d/server-id.cnf
        volumeMounts:
        - name: conf
          mountPath: /mnt/conf.d
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:      # ← Read password from a Secret (not hardcoded!)
              name: mysql-secret
              key: password
        ports:
        - containerPort: 3306
          name: mysql
        volumeMounts:
        - name: data           # ← References volumeClaimTemplates below
          mountPath: /var/lib/mysql
        - name: conf
          mountPath: /etc/mysql/conf.d
        resources:
          requests:
            cpu: "500m"
            memory: "512Mi"
          limits:
            cpu: "1000m"
            memory: "1Gi"
        livenessProbe:
          exec:
            command: ["mysqladmin", "ping"]   # ← Check if MySQL is responsive
          initialDelaySeconds: 30
          periodSeconds: 10
      volumes:
      - name: conf
        emptyDir: {}           # ← Temporary volume shared between init + main container

  volumeClaimTemplates:        # ← THIS is what makes StatefulSet special!
  - metadata:
      name: data               # ← Each pod gets: data-mysql-0, data-mysql-1, data-mysql-2
    spec:
      accessModes: ["ReadWriteOnce"]  # ← Only ONE pod can mount at a time (block storage)
      storageClassName: gp2           # ← AWS EBS gp2 SSD (or gp3 for newer clusters)
      resources:
        requests:
          storage: 10Gi               # ← 10GB per pod = 30GB total for 3 replicas

Word-by-Word: The Critical Parts

serviceName: "mysql"
Why it's required: StatefulSet needs a Headless Service (clusterIP: None) to create stable DNS entries for each pod. Without this, pods can't address each other by stable hostname — critical for database replication.
volumeClaimTemplates
What it does: Automatically creates a unique PersistentVolumeClaim for EACH pod. mysql-0 gets PVC data-mysql-0, mysql-1 gets data-mysql-1. When a pod is deleted and recreated, it reattaches to the SAME PVC — data survives pod restarts.
initContainers
What it does: Runs to completion BEFORE the main container starts. Used for setup tasks: copying config files, waiting for dependencies, DB schema migration. The main container starts only after all initContainers succeed.

Headless Service for StatefulSet

YAMLmysql-headless-svc.yaml
apiVersion: v1
kind: Service
metadata:
  name: mysql          # ← Must match StatefulSet's spec.serviceName
  namespace: shopnow
spec:
  clusterIP: None      # ← THIS makes it "headless" — no virtual IP created
                       #   Instead, DNS returns individual pod IPs directly
  selector:
    app: mysql
  ports:
  - port: 3306
    name: mysql
# Result: Stable DNS names per pod:
# mysql-0.mysql.shopnow.svc.cluster.local → 10.0.1.5
# mysql-1.mysql.shopnow.svc.cluster.local → 10.0.1.6
# mysql-2.mysql.shopnow.svc.cluster.local → 10.0.1.7
💡 Interview Gold: "Why does StatefulSet need a Headless Service?" — Because Kubernetes creates stable DNS entries (pod-name.service-name.namespace.svc.cluster.local) for each StatefulSet pod using the headless service. This allows replicas to find the primary node by a predictable hostname, which is essential for database replication configuration.
SECTION 3

👾 DaemonSet — One Pod Per Node

📖 Story

ShopNow's ops team needs log collection (Fluentd) and monitoring (Prometheus Node Exporter) running on EVERY server. When a new EC2 node joins the cluster, it must automatically get these agents. When a node is removed, the agent should stop. This is exactly what DaemonSet does.

A DaemonSet ensures that all (or some) nodes run a copy of a specific pod. When new nodes are added to the cluster, pods are automatically added. When nodes are removed, pods are garbage collected.

Common DaemonSet Use Cases

📋

Log Collectors

Fluentd, Filebeat, Fluent Bit — reads logs from node filesystem

📊

Metrics Agents

Prometheus Node Exporter, Datadog Agent — collect node-level metrics

🔒

Security Agents

Falco, AWS GuardDuty agent — security scanning per node

🌐

Network Plugins

AWS VPC CNI, Calico — must run on every node to set up networking

YAMLfluentd-daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet                # ← Automatically runs on every node
metadata:
  name: fluentd
  namespace: kube-system       # ← System-level agents go in kube-system
spec:
  selector:
    matchLabels:
      app: fluentd
  updateStrategy:
    type: RollingUpdate        # ← Update nodes one by one (vs OnDelete)
    rollingUpdate:
      maxUnavailable: 1        # ← Update 1 node at a time
  template:
    metadata:
      labels:
        app: fluentd
    spec:
      tolerations:             # ← CRITICAL: Allow pod to run on control-plane nodes too
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: fluentd
        image: fluent/fluentd-kubernetes-daemonset:v1.16
        env:
        - name: FLUENT_ELASTICSEARCH_HOST
          value: "elasticsearch.logging.svc.cluster.local"
        - name: FLUENT_ELASTICSEARCH_PORT
          value: "9200"
        resources:
          limits:
            memory: 200Mi      # ← Log agents should be lightweight
          requests:
            cpu: 100m
            memory: 200Mi
        volumeMounts:
        - name: varlog          # ← Mount host's /var/log to read container logs
          mountPath: /var/log
        - name: varlibdockercontainers
          mountPath: /var/lib/docker/containers
          readOnly: true
      terminationGracePeriodSeconds: 30
      volumes:
      - name: varlog
        hostPath:              # ← hostPath: mounts a DIRECTORY from the NODE filesystem
          path: /var/log       #   into the container — needed to read log files
      - name: varlibdockercontainers
        hostPath:
          path: /var/lib/docker/containers
tolerations: NoSchedule
Why it matters: Control-plane nodes have a taint that prevents regular pods from being scheduled there. Tolerations allow the DaemonSet pod to "tolerate" (ignore) that taint and still run on control-plane nodes — essential for cluster-wide agents.
hostPath volumes
What it does: Mounts a path from the HOST node's filesystem into the container. DaemonSet log collectors need this to access the actual log files written by other containers on the node. Security note: hostPath is powerful and should be used only for system-level pods.
SECTION 4

⏱️ Jobs & CronJobs — Batch Processing

Job — Run Once, Complete, Done

📖 Story

ShopNow launches a new feature. Before going live, the team needs to run a database migration script once — adding new columns to the orders table. This should run, complete successfully, and stop. Never restart unless it fails. That's a Job.

YAMLdb-migration-job.yaml
apiVersion: batch/v1            # ← Jobs are in the 'batch' API group
kind: Job
metadata:
  name: db-migration-v2
  namespace: shopnow
spec:
  completions: 1               # ← Run 1 successful pod (default)
  parallelism: 1               # ← Run 1 pod at a time
  backoffLimit: 3              # ← Retry up to 3 times if pod fails
  activeDeadlineSeconds: 300   # ← Kill job if it runs more than 5 minutes
  ttlSecondsAfterFinished: 600 # ← Auto-delete job 10 min after completion (cleanup)
  template:
    spec:
      restartPolicy: OnFailure # ← REQUIRED for Jobs: Never or OnFailure
                               #   (NOT Always — that would loop forever!)
      containers:
      - name: migration
        image: shopnow/backend:v2.0
        command: ["python", "manage.py", "migrate"]  # ← Run django migrations
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: url
        resources:
          requests:
            cpu: "200m"
            memory: "256Mi"
restartPolicy: OnFailure
Critical difference: Regular pods use Always (restart forever). Jobs must use OnFailure or Never. OnFailure restarts the container on the SAME pod if it crashes. Never creates a NEW pod if it fails (useful to preserve logs of failed attempt).
completions & parallelism
Power combo: Set completions: 10, parallelism: 3 to process 10 tasks with 3 workers at a time — like a worker queue. Each pod processes one item. When 3 finish, 3 more start, until all 10 complete.

CronJob — Scheduled Jobs

YAMLnightly-report-cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-sales-report
  namespace: shopnow
spec:
  schedule: "0 2 * * *"          # ← Cron syntax: minute hour day month weekday
                                  #   "0 2 * * *" = 2:00 AM every day
                                  #   "*/15 * * * *" = every 15 minutes
                                  #   "0 9 * * 1" = 9 AM every Monday
  concurrencyPolicy: Forbid       # ← If prev job still running, SKIP new one
                                  #   Options: Allow | Forbid | Replace
  successfulJobsHistoryLimit: 3   # ← Keep last 3 successful job logs
  failedJobsHistoryLimit: 1       # ← Keep last 1 failed job log
  startingDeadlineSeconds: 60     # ← If missed schedule, only start if within 60s
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: report-generator
            image: shopnow/reports:latest
            command: ["python", "generate_sales_report.py", "--date=yesterday"]
            resources:
              requests:
                cpu: "100m"
                memory: "128Mi"
📅 Cron Cheatsheet:
* * * * * = every minute
0 * * * * = every hour at :00
0 2 * * * = 2:00 AM daily
0 2 * * 0 = 2:00 AM every Sunday
0 2 1 * * = 2:00 AM on 1st of every month
Use crontab.guru to verify your schedule.
SECTION 5

📈 HPA — Horizontal Pod Autoscaler

📖 Story

It's 9 PM on a Saturday. ShopNow's checkout service goes from 10 req/sec to 1000 req/sec. The team is asleep. Manually scaling would be too slow. HPA detects the CPU spike and automatically adds pods — from 2 to 20 — in minutes. When traffic drops at 2 AM, it scales back down to save costs. No human needed.

How HPA Works

┌────────────────────────────────────────────────────────────┐ │ HPA Control Loop (every 15s) │ │ │ │ 1. HPA reads metrics from Metrics Server │ │ (CPU: 450m used / 200m requested = 225% utilization) │ │ │ │ 2. Calculate desired replicas: │ │ desiredReplicas = ceil(currentReplicas × (current/target)) │ = ceil(2 × (225%/50%)) = ceil(9) = 9 replicas │ │ │ │ 3. Scale Deployment from 2 → 9 replicas │ │ │ │ 4. Wait for stabilization window (300s) before scaling in │ └────────────────────────────────────────────────────────────┘

Step 1: Install Metrics Server (required for CPU/Memory HPA)

bash
# On Minikube
minikube addons enable metrics-server

# On EKS (using Helm or manifest)
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Verify metrics server is working
kubectl top nodes        # Shows CPU/Memory per node
kubectl top pods -n shopnow  # Shows CPU/Memory per pod

HPA YAML — CPU & Memory Scaling

YAMLcheckout-hpa.yaml
apiVersion: autoscaling/v2          # ← v2 supports multiple metrics
kind: HorizontalPodAutoscaler
metadata:
  name: checkout-hpa
  namespace: shopnow
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-service            # ← Which Deployment to scale
  minReplicas: 2                      # ← Never go below 2 (for HA)
  maxReplicas: 20                     # ← Never exceed 20 pods
  metrics:
  - type: Resource                    # ← CPU-based scaling
    resource:
      name: cpu
      target:
        type: Utilization             # ← Percentage of requested CPU
        averageUtilization: 50        # ← Scale up if avg CPU > 50% of requests
                                      #   Scale down if avg CPU < 50%
  - type: Resource                    # ← Memory-based scaling
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70        # ← Scale up if avg memory > 70%
  behavior:                           # ← Control HOW FAST it scales
    scaleUp:
      stabilizationWindowSeconds: 0   # ← Scale up immediately (no wait)
      policies:
      - type: Pods
        value: 4                      # ← Add at most 4 pods per 60s
        periodSeconds: 60
      - type: Percent
        value: 100                    # ← Or double the pods per 60s
        periodSeconds: 60
      selectPolicy: Max               # ← Use whichever policy scales MORE
    scaleDown:
      stabilizationWindowSeconds: 300 # ← Wait 5 min before scaling down
                                      #   (avoids flapping during traffic spikes)
      policies:
      - type: Pods
        value: 2                      # ← Remove at most 2 pods per 60s
        periodSeconds: 60
averageUtilization: 50
Important: This is % of the pod's CPU request, not the node's total CPU. If pod requests 200m CPU and uses 120m, that's 60% — HPA would scale up. If you don't set resource requests on pods, HPA cannot calculate utilization and won't work!
stabilizationWindowSeconds: 300
Why it matters: Without a stabilization window on scale-down, HPA would remove pods as soon as CPU drops — then immediately add them back as the remaining pods get overloaded. The 5-minute window prevents this "flapping" pattern.
⚠️ Common HPA Mistake: HPA requires resources.requests to be set on containers. If requests are missing, kubectl get hpa shows <unknown>/50% for current utilization and scaling never works.
SECTION 6

⚖️ VPA — Vertical Pod Autoscaler

VPA adjusts the CPU/memory requests and limits of containers automatically — making containers bigger or smaller instead of adding/removing replicas. Use VPA for apps that can't scale horizontally (single-instance databases, ML training jobs).

HPA (Horizontal)

  • Adds/removes PODS
  • Best for stateless apps
  • Requires app to handle multiple replicas
  • Scales fast (seconds)

VPA (Vertical)

  • Adjusts CPU/Memory of existing pods
  • Best for stateful or single-instance apps
  • Pod must restart to apply new limits
  • Good for rightsizing resource requests
YAMLvpa.yaml
# First install VPA:
# kubectl apply -f https://github.com/kubernetes/autoscaler/releases/latest/download/vertical-pod-autoscaler.yaml

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: mysql-vpa
  namespace: shopnow
spec:
  targetRef:
    apiVersion: apps/v1
    kind: StatefulSet
    name: mysql
  updatePolicy:
    updateMode: "Auto"          # ← Options:
                                #   "Off" = only recommend, don't apply
                                #   "Initial" = set only on new pods
                                #   "Auto" = evict and recreate pods with new limits
  resourcePolicy:
    containerPolicies:
    - containerName: mysql
      minAllowed:               # ← Never go below this
        cpu: 250m
        memory: 256Mi
      maxAllowed:               # ← Never exceed this
        cpu: 4
        memory: 8Gi
      controlledResources:      # ← Which resources VPA manages
        - cpu
        - memory
⚠️ Warning: Do NOT use HPA and VPA (Auto mode) together on the same deployment for CPU/memory — they conflict. Use VPA in "Off" mode for recommendations only, then manually apply the suggested values to your resource requests.
SECTION 7

⚡ KEDA — Event-Driven Autoscaling

📖 Story

ShopNow processes orders via an SQS queue. When queue depth is 0, the processing pods should scale to 0 (no cost!). When 10,000 orders flood in, scale to 50 pods immediately — based on queue length, not CPU. Standard HPA can't do this. KEDA (Kubernetes Event-Driven Autoscaling) can scale to/from zero based on external event sources.

bash
# Install KEDA on EKS
helm repo add kedacore https://kedacore.github.io/charts
helm repo update
helm install keda kedacore/keda --namespace keda --create-namespace
YAMLsqs-keda-scaler.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject                    # ← KEDA's custom resource
metadata:
  name: order-processor-scaler
  namespace: shopnow
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-processor             # ← Which Deployment to scale
  minReplicaCount: 0                  # ← Scale TO ZERO when queue is empty (saves cost!)
  maxReplicaCount: 50
  cooldownPeriod: 300                 # ← Wait 5 min before scaling to zero
  pollingInterval: 15                 # ← Check queue every 15 seconds
  triggers:
  - type: aws-sqs-queue               # ← Trigger type: SQS queue depth
    authenticationRef:
      name: aws-credentials           # ← Reference to credentials (TriggerAuthentication)
    metadata:
      queueURL: https://sqs.ap-south-1.amazonaws.com/123456789/orders-queue
      queueLength: "100"              # ← Add 1 replica per 100 messages in queue
      awsRegion: ap-south-1

KEDA supports 50+ scalers including: SQS, Kafka, RabbitMQ, Redis, Prometheus metrics, HTTP requests, CloudWatch, Azure Service Bus, and many more.

🎯 Interview Questions & Answers — Part 2

🎯 Interview Prep — 4 YOE Level

Q1: When would you use a StatefulSet instead of a Deployment?

A: StatefulSet is for applications that require stable network identity, stable persistent storage, and ordered deployment/scaling. Examples: MySQL, PostgreSQL, MongoDB, Kafka, Elasticsearch, ZooKeeper. The key differentiators are: (1) Pods get stable names (mysql-0, mysql-1) — critical for primary/replica configuration, (2) Each pod gets its own PVC via volumeClaimTemplates — data survives pod restarts, (3) Pods start and stop in a defined order — mysql-0 starts before mysql-1, ensuring the primary is ready before replicas connect.

Q2: Explain how HPA calculates the desired number of replicas.

A: HPA uses the formula: desiredReplicas = ceil(currentReplicas × (currentMetricValue / targetMetricValue)). For example, if 3 pods are running and avg CPU is 90% with a target of 50%: desired = ceil(3 × 90/50) = ceil(5.4) = 6 replicas. HPA reads metrics every 15 seconds from the Metrics Server. It has a scale-down stabilization window (default 5 minutes) to prevent flapping.

Q3: What is the difference between HPA and VPA? Can you use both?

A: HPA scales horizontally — adds/removes pod replicas. VPA scales vertically — adjusts CPU/memory requests of pods. Both should NOT be used together on the same resource metric (both managing CPU causes conflicts). However, you can use VPA in "Off" mode for recommendations while HPA manages CPU scaling. A valid combination: VPA manages memory, HPA manages custom metrics (like queue depth via KEDA). Also, Cluster Autoscaler can be combined with HPA — HPA adds pods, Cluster Autoscaler adds nodes when pods are Pending due to insufficient resources.

Q4: What is a DaemonSet used for? Give three real examples.

A: DaemonSet ensures exactly one pod runs on every (or selected) node. Real examples: (1) Fluentd/Fluent Bit — reads log files from /var/log on every node and ships to Elasticsearch. (2) Prometheus Node Exporter — collects OS-level metrics (disk, network, CPU) from each node. (3) AWS VPC CNI — manages pod networking on every EKS node. DaemonSets automatically add pods when new nodes join the cluster and remove pods when nodes leave — no manual scaling needed.

Q5: What is KEDA and when would you use it over standard HPA?

A: KEDA (Kubernetes Event Driven Autoscaling) extends HPA to scale based on external event sources like message queue depth, HTTP requests per second, database query counts, or Prometheus metrics. The key advantage over standard HPA is the ability to scale TO ZERO — when there are no events, KEDA can scale the deployment to 0 pods (saving 100% of cost), and scale back up when events arrive. Use KEDA when: you process SQS/Kafka/RabbitMQ messages, you have bursty or time-based workloads, or you want scale-to-zero for cost optimization.

Q6: What is restartPolicy in a Job and what values are valid?

A: restartPolicy defines what happens when a container in a pod exits. For Jobs, valid values are: Never (create a new pod on failure — preserves logs of failed pods) and OnFailure (restart the container within the same pod on failure). The value Always is NOT valid for Jobs — it would cause the Job to restart indefinitely even after success. Deployments use Always because their pods should keep running.
