1. The Business Scenario — Why This Project Exists

ShopNow Retail's Diwali flash sale started at 10:00 AM. At 9:59, the Catalog Service was humming along on 3 pods, comfortably handling normal browsing traffic. At 10:00:15, fifteen seconds after the sale banner went live, traffic jumped nearly 8x as thousands of customers hit the search and product pages at once. The HPA that existed did eventually scale up — but it took almost four minutes to reach enough replicas, because there weren't enough nodes in the cluster to schedule the new pods onto, and the Cluster Autoscaler took its own additional time to notice, provision, and join new EC2 capacity. For those four minutes, checkout error rates spiked and ShopNow's socials filled with screenshots of "Service Unavailable."

Ramesh's ask, this time covering the whole stack rather than one layer: "I want scaling that works end to end — pods that scale on the right signal, not just CPU, and nodes that show up fast enough to actually hold those pods. Show me 3 pods on a normal Tuesday afternoon and 20 pods within the first minute of a flash sale, then back down to 3 once it's over — automatically, every time, without anyone watching a dashboard."

This use case builds the complete autoscaling stack that answers that ask — not just one tool, but the four that work together at different layers: HPA (how many pods), VPA (how big each pod is), KEDA (scaling on signals beyond CPU), and Cluster Autoscaler / Karpenter (how many nodes exist to hold all those pods).

2. The Core Idea — Four Tools, Four Different Questions

HPA
"Do I need MORE COPIES of this pod?"
Scales replica count, based on CPU/memory or custom metrics.
VPA
"Is each copy the RIGHT SIZE?"
Adjusts CPU/memory requests and limits on existing pods.
KEDA
"What if the right signal isn't CPU at all?"
Scales on external events — queue depth, request rate, cron schedule.
Cluster Autoscaler / Karpenter
"Do I have enough MACHINES to run all these pods?"
Scales the underlying EC2 node fleet itself.

The scenario from the original ask — 3 pods normal, 20 pods under load, back to 3 after — is only fully achievable when all four layers work together. HPA alone scaling from 3 to 20 pods is meaningless if there's no node capacity to schedule those extra 17 pods onto; that's exactly what happened in section 1's incident.

Why this use case chooses Karpenter as the primary node-scaler, with Cluster Autoscaler shown for comparison: Cluster Autoscaler works in terms of pre-defined node groups with fixed instance types, and its scale-up decision loop is measurably slower — this was the literal four-minute gap in section 1's incident. Karpenter provisions nodes directly, picking the best available instance type and size for the exact pending pods, and does it roughly 3-5x faster. Knowing why ShopNow moved from one to the other, with a real incident as the reason, is a stronger interview answer than reciting a feature comparison from memory.

Only a small, fixed managed node group exists for guaranteed baseline capacity (system pods, the autoscaling controllers themselves, and Catalog Service's normal 3-pod footprint). Everything above that baseline — the burst capacity for flash-sale traffic — is handled entirely by Karpenter provisioning nodes directly, with no eksctl-managed node group involved at all for that burst tier.

9. Horizontal Pod Autoscaler — Scaling Pod COUNT

# overlays/prod/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: catalog-service-hpa, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: catalog-service }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0     # react INSTANTLY to a spike, no waiting
      policies:
        - type: Percent
          value: 100                     # allowed to DOUBLE pod count in one step
          periodSeconds: 15
        - type: Pods
          value: 6
          periodSeconds: 15
      selectPolicy: Max                      # use whichever policy scales up MORE aggressively
    scaleDown:
      stabilizationWindowSeconds: 300     # wait 5 minutes of sustained low load before scaling down
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60

This minReplicas: 3, maxReplicas: 20 pairing is directly and literally the "3 pods normal, 20 pods peak" numbers from the original ask. The behavior block is what makes the scale-up side fast (doubling pod count every 15 seconds, no stabilization delay) while keeping the scale-down side deliberately cautious (a full 5-minute window of sustained low load before removing pods) — asymmetric on purpose, because the cost of scaling up too slowly (an outage) is far worse than the cost of scaling down too slowly (a few extra minutes of mild over-provisioning).

10. Vertical Pod Autoscaler — Scaling Pod SIZE

# platform/vpa/ — one-time cluster install
git clone https://github.com/kubernetes/autoscaler.git
./autoscaler/vertical-pod-autoscaler/hack/vpa-up.sh

# overlays/prod/vpa.yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: { name: catalog-service-vpa, namespace: prod }
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: catalog-service }
  updatePolicy:
    updateMode: "Off"   # <-- deliberately "Off": recommend only, never auto-apply. See callout.
  resourcePolicy:
    containerPolicies:
      - containerName: catalog-service
        minAllowed: { cpu: "100m", memory: "128Mi" }
        maxAllowed: { cpu: "1", memory: "1Gi" }
Why VPA runs in "Off" mode here — and why HPA and VPA fighting each other is a very real, very common mistake. VPA in "Auto" mode evicts and restarts pods to resize them — and if you're also running HPA on the exact same CPU metric, the two controllers can enter a feedback loop: HPA adds pods to handle load, VPA notices per-pod CPU dropped and shrinks each pod's request, which makes the HPA's utilization percentage look different, triggering another HPA reaction. ShopNow runs VPA in "Off" (recommendation-only) mode specifically to avoid this — engineers review VPA's suggested requests/limits periodically and apply them manually during a planned change, while HPA alone continues to handle real-time replica scaling. This exact "don't run HPA and VPA on the same metric in Auto mode together" rule is one of the highest-value things to be able to say out loud in an interview.
# Reading VPA's recommendation, without ever letting it act automatically
kubectl describe vpa catalog-service-vpa -n prod
# Output includes a Recommendation section like:
#   Container: catalog-service
#     Target:        { cpu: 180m, memory: 310Mi }
#     Lower Bound:   { cpu: 100m, memory: 256Mi }
#     Upper Bound:   { cpu: 420m, memory: 512Mi }
# An engineer reviews this monthly and hand-tunes the Deployment's requests/limits
# accordingly — turning guesswork into data-backed resource sizing

11. KEDA — Scaling on Events, Not Just CPU

# platform/keda/ — one-time cluster install
helm repo add kedacore https://kedacore.github.io/charts
helm install keda kedacore/keda --namespace keda --create-namespace \
  --set serviceAccount.name=keda-operator

# overlays/prod/scaledobject.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: catalog-service-scaledobject, namespace: prod }
spec:
  scaleTargetRef: { name: catalog-service }
  minReplicaCount: 3
  maxReplicaCount: 20
  pollingInterval: 10        # check the queue every 10 seconds
  cooldownPeriod: 300        # same asymmetric caution as HPA's scaleDown above
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.ap-south-1.amazonaws.com/111122223333/search-index-refresh-queue
        queueLength: "5"          # target: 5 messages per pod
        awsRegion: ap-south-1
      authenticationRef: { name: keda-aws-credentials }
---
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata: { name: keda-aws-credentials, namespace: prod }
spec:
  podIdentity: { provider: aws-eks }   # uses IRSA, same pattern as every other AWS integration in this series
What KEDA actually does under the hood, precisely: KEDA doesn't replace the HPA — it creates and manages a HorizontalPodAutoscaler object on your behalf, translating "5 messages per pod in this SQS queue" into the same replica-count math the native HPA understands. Run kubectl get hpa -n prod after applying the ScaledObject above and you'll see a second, KEDA-generated HPA object (keda-hpa-catalog-service-scaledobject) sitting right alongside the manually-authored one from section 9 — both driving the same Deployment's replica count, whichever one currently demands more replicas wins, since Kubernetes always reconciles toward the highest requested replica count when multiple HPAs somehow target one object (in ShopNow's actual setup, only one HPA per Deployment is kept active at a time in practice — either the plain CPU-based one or a KEDA ScaledObject with a CPU trigger added alongside the SQS trigger, to avoid ambiguity).

This directly matches the original ask's spirit — "monitor errors, latency, and CPU usage" style thinking from earlier use cases, extended here to "traffic isn't only measurable by CPU": a backlog of pending search-index jobs is a leading indicator of a flash sale starting, often visible in the SQS queue a few seconds before CPU utilization itself climbs, giving KEDA-based scaling a head start over pure CPU-based HPA.

12. Cluster Autoscaler vs Karpenter — Scaling NODES

# platform/karpenter/helm-values.yaml — install
helm install karpenter oci://public.ecr.aws/karpenter/karpenter \
  --namespace karpenter --create-namespace \
  --set settings.clusterName=shopnow-cluster \
  --set serviceAccount.name=karpenter

# platform/karpenter/ec2nodeclass.yaml — what KIND of nodes Karpenter is allowed to create
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata: { name: shopnow-burst-nodes }
spec:
  amiFamily: AL2023
  subnetSelectorTerms: [{ tags: { karpenter.sh/discovery: shopnow-cluster } }]
  securityGroupSelectorTerms: [{ tags: { karpenter.sh/discovery: shopnow-cluster } }]
  role: KarpenterNodeRole-shopnow-cluster

# platform/karpenter/nodepool.yaml — the scaling POLICY itself
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: shopnow-burst }
spec:
  template:
    spec:
      nodeClassRef: { name: shopnow-burst-nodes, kind: EC2NodeClass, group: karpenter.k8s.aws }
      requirements:
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["m", "c"]
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]   # no spot for this burst pool — need guaranteed capacity during a sale
      expireAfter: 720h
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 5m   # actively bin-packs and removes underused nodes 5 min after load drops
  limits:
    cpu: 200   # hard ceiling — Karpenter can never provision beyond this even under a runaway scale event
1Karpenter has no fixed node group or instance type list — it watches for Pending pods (ones the scheduler couldn't place anywhere), reads exactly what CPU/memory they need, and picks the best-fitting real EC2 instance type available at that moment, launching it directly via the EC2 API. This is fundamentally different from Cluster Autoscaler, which can only add more of whatever instance type a pre-defined node group is configured with.
2consolidationPolicy: WhenEmptyOrUnderutilized is Karpenter actively working to shrink the fleet back down — not just declining to add nodes, but proactively identifying nodes running below capacity, cordoning and draining them, and consolidating pods onto fewer, better-packed nodes. This is the direct mechanism behind the "back to 3 pods, back to 3 nodes" half of the original scenario.
3The limits.cpu: 200 ceiling is a cost-safety net — a runaway scaling loop (a bug causing HPA to keep demanding more replicas) can still only ever provision up to 200 vCPUs worth of nodes total, capping the financial blast radius of any autoscaling misconfiguration.
# For comparison — what the OLDER Cluster Autoscaler approach looked like,
# shown so the tradeoff from section 2 is concrete, not just described
helm install cluster-autoscaler autoscaler/cluster-autoscaler \
  --namespace kube-system \
  --set autoDiscovery.clusterName=shopnow-cluster \
  --set awsRegion=ap-south-1
# Cluster Autoscaler can ONLY scale the eksctl-managed node group's desiredCapacity
# up toward its maxSize=8 ceiling — it cannot introduce a NEW instance type or
# node group on its own, unlike Karpenter

13. Deployment and Service

apiVersion: apps/v1
kind: Deployment
metadata: { name: catalog-service, labels: { app: catalog-service } }
spec:
  replicas: 3
  selector: { matchLabels: { app: catalog-service } }
  template:
    metadata: { labels: { app: catalog-service } }
    spec:
      containers:
        - name: catalog-service
          image: 111122223333.dkr.ecr.ap-south-1.amazonaws.com/catalog-service:prod-v1.9.4
          ports: [{ containerPort: 8000 }]
          envFrom: [{ configMapRef: { name: catalog-service-config } }]
          resources:
            requests: { cpu: "150m", memory: "256Mi" }   # <-- these are what VPA's recommendation refines over time
            limits:   { cpu: "400m", memory: "512Mi" }
          readinessProbe: { httpGet: { path: /health, port: 8000 }, initialDelaySeconds: 5, periodSeconds: 10 }
---
apiVersion: v1
kind: Service
metadata: { name: catalog-service-svc }
spec:
  selector: { app: catalog-service }
  ports: [{ port: 80, targetPort: 8000 }]
Accurate requests values are the load-bearing detail of this entire use case. HPA's CPU percentage is calculated against the requests value, and Karpenter decides what instance type to launch based on the sum of pending pods' requests — an under- or over-stated requests value throws off both HPA's scaling math and Karpenter's node-sizing decisions simultaneously. This is exactly why VPA's recommendation-only role (section 10) matters even without auto-applying: getting this one number right is what makes every other layer in this use case behave correctly.

15. Ingress with AWS Load Balancer Controller

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: catalog-service-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: shopnow-shared-alb
spec:
  rules:
    - host: shopnow.com
      http:
        paths: [{ path: /api/catalog, pathType: Prefix, backend: { service: { name: catalog-service-svc, port: { number: 80 } } } }]

As covered in depth in Use Case 8, the ALB Controller automatically re-registers the changing set of pod IPs into its Target Group as HPA/KEDA scale replica count — no manual action needed here even as pod count swings from 3 to 20 and back.

16. PodDisruptionBudget

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: catalog-service-pdb }
spec:
  minAvailable: 2
  selector: { matchLabels: { app: catalog-service } }
The PDB matters more here than in earlier use cases, specifically because of Karpenter's consolidation behavior. When Karpenter identifies an underutilized node and drains it during scale-down, it's performing the exact same kind of voluntary eviction a manual node drain does — the PDB is what stops Karpenter's own scale-down consolidation from ever pushing Catalog Service below 2 available pods, even while it's actively working to shrink the fleet.

# load_test_and_watch_scaling.py — the pipeline gate AND the report data source
import subprocess, time, json, argparse

def get_replica_count(ns="prod"):
    out = subprocess.run(["kubectl", "get", "deployment", "catalog-service", "-n", ns, "-o", "json"], capture_output=True, text=True)
    return json.loads(out.stdout)["status"].get("readyReplicas", 0)

def get_node_count():
    out = subprocess.run(["kubectl", "get", "nodes", "-l", "karpenter.sh/nodepool=shopnow-burst", "-o", "json"], capture_output=True, text=True)
    return len(json.loads(out.stdout)["items"])

def run(expected_min, expected_max):
    subprocess.Popen(["kubectl", "run", "load-test", "--image=williamyeh/hey", "--restart=Never", "-n", "prod",
                       "--", "-z", "3m", "-c", "200", "http://catalog-service-svc.prod.svc.cluster.local/api/catalog/search"])
    peak_replicas, peak_nodes = 0, 0
    for _ in range(40):   # poll for ~10 minutes
        r, n = get_replica_count(), get_node_count()
        peak_replicas, peak_nodes = max(peak_replicas, r), max(peak_nodes, n)
        time.sleep(15)
    print(f"Peak replicas: {peak_replicas}, Peak burst nodes: {peak_nodes}")
    assert peak_replicas >= expected_min, "Scaling did not reach expected minimum peak"

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--min", type=int, default=3)
    p.add_argument("--max", type=int, default=20)
    args = p.parse_args()
    run(args.min, args.max)

# send_email.py
import argparse, smtplib, os
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def send(status, build_no, report_path="report.html"):
    msg = MIMEMultipart()
    msg["Subject"] = f"[ShopNow] catalog-service autoscaling verification - Build #{build_no} - {status.upper()}"
    msg["From"] = "devops-bot@shopnow.com"
    msg["To"] = "release-managers@shopnow.com, sre-team@shopnow.com"
    msg.attach(MIMEText(f"Build: #{build_no}\nStatus: {status}\n\nSee attached report.", "plain"))
    if os.path.exists(report_path):
        with open(report_path, "rb") as f:
            part = MIMEApplication(f.read(), Name="report.html")
        part["Content-Disposition"] = 'attachment; filename="report.html"'
        msg.attach(part)
    with smtplib.SMTP("email-smtp.ap-south-1.amazonaws.com", 587) as server:
        server.starttls()
        server.login(os.environ["SES_USER"], os.environ["SES_PASS"])
        server.send_message(msg)

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--status", default="success")
    parser.add_argument("--build", required=True)
    parser.add_argument("--report", default="report.html")
    args = parser.parse_args()
    send(args.status, args.build, args.report)
