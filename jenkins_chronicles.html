Architecture & Installation

What Jenkins Actually Is

Jenkins is an open-source, Java-based automation server. It watches your source code, and when you push, it automatically: pulls the code → builds it → tests it → packages it → deploys it. This is called a CI/CD Pipeline.

CI — Continuous IntegrationEvery code push is automatically built and tested within minutes. You know instantly if something broke.
CD — Continuous DeliveryAfter tests pass, the artifact (JAR/Docker image) is packaged and ready to deploy with one click.

Job / ProjectA single unit of work in Jenkins (e.g., "build the API service")
BuildOne run of a job. Every run has a number: #1, #2, #3...

Installing Jenkins with Docker

At BuildForge, we run Jenkins inside Docker. This is the cleanest, most reproducible way to run it — no system-level Java installs, easy version control, portable.

BASH install-jenkins.sh 
# Step 1: Create a Docker network so Jenkins can talk to other containers
docker network create buildforge-net

# Step 2: Create a named volume to persist Jenkins data across container restarts
# Without this, every restart = fresh Jenkins (no jobs, no config)
docker volume create jenkins-data

# Step 3: Run Jenkins controller
docker run \
  -d \                          # -d = detached (runs in background)
  --name jenkins-controller \  # Name the container
  --network buildforge-net \   # Connect to our network
  -p 8080:8080 \               # Port 8080 (host) → 8080 (container) = Web UI
  -p 50000:50000 \             # Port 50000 = Jenkins agent communication (JNLP)
  -v jenkins-data:/var/jenkins_home \ # Mount volume → ALL data persists here
  -v /var/run/docker.sock:/var/run/docker.sock \ # Mount Docker socket so Jenkins
                                                    # can run Docker commands inside pipelines
  jenkins/jenkins:lts-jdk17    # Official Jenkins LTS image with Java 17

# Step 4: Get the initial admin password
docker exec jenkins-controller cat /var/jenkins_home/secrets/initialAdminPassword
ℹ️The /var/run/docker.sock mount is the "Docker-in-Docker" trick. It lets the Jenkins container communicate with the HOST machine's Docker daemon, so your pipelines can build Docker images without needing a separate Docker installation inside Jenkins.

Interview Q&A
💬 What is Jenkins and why do companies use it over alternatives like GitHub Actions?
Jenkins is a self-hosted, open-source automation server that runs your CI/CD pipelines on your own infrastructure. Companies prefer it when they need full control over their build environment, need to run builds on private networks (no internet access), have complex multi-platform requirements, or have compliance requirements that prevent using cloud-based CI/CD. Alternatives like GitHub Actions are SaaS — managed by GitHub, simpler to start with, but less customizable and your builds run on GitHub's infrastructure.
💬 What is the difference between Jenkins Controller and Jenkins Agent?
The Controller (master) is the management node — it hosts the UI, stores configuration, schedules jobs, and orchestrates pipelines. It should NOT run builds itself (best practice). Agents (workers/nodes) are the machines that actually execute pipeline steps — compile code, run tests, build Docker images. This separation allows scaling: add more agents when you need more build capacity, without touching the controller.
💬 What is $JENKINS_HOME and what does it contain?
$JENKINS_HOME is the root directory where Jenkins stores ALL its data — typically /var/jenkins_home inside the container. It contains: jobs/ (all job configurations and build histories), plugins/ (installed plugin files), config.xml (global Jenkins configuration), secrets/ (encrypted credentials store), workspace/ (where code is checked out for builds), and nodes/ (agent configurations).

BASH Build Step Shell Script 
#!/bin/bash
# This is the shell script Jenkins runs as a BUILD STEP
# Every line that succeeds continues. Any non-zero exit code = BUILD FAILURE.

# ── SECTION 1: Print Build Metadata ──────────────────────────────────────
echo "=============================================="
echo "  BuildForge Inc. — System Health Check"
echo "  Job Name    : $JOB_NAME"       # Jenkins auto-injects this env var
echo "  Build Number: $BUILD_NUMBER"   # Auto-increments each run: 1, 2, 3...
echo "  Build URL   : $BUILD_URL"      # Full URL to this specific build
echo "  Workspace   : $WORKSPACE"      # Dir where code is checked out
echo "  Timestamp   : $(date)"         # $(date) = runs the `date` command inline
echo "=============================================="

# ── SECTION 2: System Info ────────────────────────────────────────────────
echo "\n--- OS Information ---"
uname -a      # Print kernel name, machine, OS (tells us what machine Jenkins is on)

echo "\n--- Disk Space ---"
df -h         # -h = human readable. Shows disk usage per mount point

echo "\n--- Memory Usage ---"
free -m       # -m = show in megabytes. Shows total/used/free RAM

echo "\n--- Java Version (Jenkins runs on Java!) ---"
java -version  # Jenkins itself is a Java app. Good to confirm the JDK version

# ── SECTION 3: Simulate a Build Task ─────────────────────────────────────
echo "\n--- Simulating Build ---"
echo "[INFO] Compiling Java classes..."
sleep 2       # sleep 2 = pause 2 seconds (simulating compilation time)
echo "[INFO] Running unit tests..."
sleep 1
echo "[SUCCESS] Build completed!"

# ── SECTION 4: Write a report file (will be archived as an artifact) ──────
echo "Build Report - $(date)" > build-report.txt
echo "Job: $JOB_NAME | Build: #$BUILD_NUMBER" >> build-report.txt
echo "Status: SUCCESS" >> build-report.txt
# The >> operator APPENDS to file. The > operator OVERWRITES.
# This file will be available in Post-build → Archived Artifacts

echo "\nReport written to build-report.txt"
exit 0  # exit 0 = success. exit 1 = failure (Jenkins marks build as FAILED)

Interview Q&A
💬 What is the difference between a Freestyle job and a Pipeline job in Jenkins?
A Freestyle job is configured entirely through the Jenkins UI — it's click-based, not code-based. It's simple but has limitations: you can't version-control it in Git, it's hard to reproduce across Jenkins instances, and it lacks advanced features like parallel stages, retry logic, and shared libraries. A Pipeline job is defined as a Jenkinsfile — actual Groovy code stored in your repository. It's version-controlled, reviewable, reproducible, and supports the full power of Jenkins Pipeline DSL. For any real CI/CD work, Pipeline is always preferred.
💬 What does "archiving artifacts" mean in Jenkins?
After a build runs, some files are important to keep — compiled JARs, test reports, Docker image digests, deployment logs. Archiving artifacts tells Jenkins to copy these files out of the workspace (which gets wiped on next build) and store them permanently with the build record. You can then download them from the build's page in the Jenkins UI. This is how you track what was built in build #42 vs build #43.

Declarative Pipeline
& The Jenkinsfile

This is the heart of modern Jenkins. A Jenkinsfile turns your pipeline into code — versioned, reviewable, and reproducible. This is how BuildForge does real CI/CD.

🏢 THE STORY

After the Freestyle demo, your manager is impressed but says: "That's nice, but I want this config in Git. If Jenkins crashes, I don't want to reconfigure 50 jobs by hand. Also, I want developers to propose pipeline changes via pull requests."

The solution: Jenkinsfile. You store the pipeline definition directly in the application repository. Jenkins reads the file and runs it. The pipeline is now code, living next to the app code.

📊
Two Pipeline Syntaxes

Declarative syntax is structured, readable, and has built-in error handling. It enforces a specific structure which makes it easy to read and lint. This is what you should always use.

Scripted syntax is raw Groovy code — fully flexible but harder to read and maintain. You'll see it in older Jenkins setups. Modern pipelines use Declarative. You might need to read Scripted pipelines during interviews or when debugging legacy systems.

📄
The Jenkinsfile — Complete Anatomy

Let's write BuildForge's first real Jenkinsfile for the inventory service. We'll break down every single keyword:

GROOVY (JENKINSFILE) Jenkinsfile 
pipeline {                    // ← TOP-LEVEL BLOCK. Every Declarative pipeline MUST start here.
                              //   Everything lives inside this curly-brace block.

  agent any                   // ← WHERE to run this pipeline.
                              //   'any' = Jenkins picks any available agent.
                              //   Can also be: agent none, agent { label 'linux' }
                              //   agent { docker { image 'maven:3.9' } }

  options {                   // ← GLOBAL options that apply to the whole pipeline
    buildDiscarder(logRotator(numToKeepStr: '10'))
    // ↑ Keep only last 10 build logs. Saves disk space on Jenkins server.
    timestamps()              // ↑ Prefix every console line with a timestamp
    timeout(time: 30, unit: 'MINUTES') // Entire pipeline fails if it runs > 30 min
    disableConcurrentBuilds() // Prevents 2 builds of this job running at same time
  }

  environment {              // ← GLOBAL environment variables available in ALL stages
    APP_NAME       = 'inventory-service'  // Our service name
    MAVEN_OPTS     = '-Xmx512m'           // JVM heap for Maven builds
    DOCKER_REGISTRY= 'registry.buildforge.io'
    IMAGE_TAG      = "${BUILD_NUMBER}"    // ← ${} = reference a var. BUILD_NUMBER is Jenkins built-in.
                                            //   Double quotes allow variable interpolation in Groovy.
  }

  stages {                    // ← CONTAINER for all your stage{} blocks. Required.
                              //   Stages run SEQUENTIALLY by default (top to bottom).

    stage('Checkout') {       // ← A named stage. The string is just a label shown in UI.
      steps {                 // ← CONTAINER for the actual commands in this stage.
        checkout scm          // ← 'scm' = Source Code Manager configured in job settings.
                              //   Jenkins clones/fetches the git repo here.
                              //   scm is a special Pipeline variable that reads the job's git config.
        sh 'git log --oneline -5'  // sh{} = run a shell command. Shows last 5 commits.
      }
    }

    stage('Build') {
      steps {
        sh '''                  // ← Triple single-quotes = multi-line shell block
          echo "Building $APP_NAME version $IMAGE_TAG"
          mvn clean package -DskipTests
          # -DskipTests: compile code but skip running tests (tests are in next stage)
          # clean: delete target/ directory first (fresh build)
          # package: compile → test (skipped) → create JAR in target/
        '''
      }
      post {                  // ← Stage-level post block (runs AFTER this stage)
        success {             // ← Only runs if this stage SUCCEEDED
          echo '✅ Build stage passed'
        }
        failure {             // ← Only runs if this stage FAILED
          echo '❌ Build stage failed — check Maven output above'
        }
      }
    }

    stage('Test') {
      steps {
        sh 'mvn test'          // Run ALL unit tests. If any test fails, mvn exits non-zero → stage fails
      }
      post {
        always {              // ← 'always' runs regardless of success/failure
          junit 'target/surefire-reports/*.xml'
          // ↑ Publish JUnit test results. Jenkins parses these XML files
          //   and shows a test trend graph on the job dashboard.
          //   'target/surefire-reports/' is where Maven writes test reports.
        }
      }
    }

    stage('Archive Artifacts') {
      steps {
        archiveArtifacts(
          artifacts: 'target/*.jar',  // Glob pattern — archive all JAR files in target/
          fingerprint: true           // Compute MD5 fingerprint — tracks which build produced what
        )
      }
    }

  } // end stages

  post {                      // ← PIPELINE-LEVEL post block. Runs after ALL stages complete.
    always {                  // Runs every time, regardless of outcome
      cleanWs()              // ← Clean the workspace (delete all files) after build
                              //   Prevents disk fill-up from accumulated build files
    }
    success {
      echo "🎉 Pipeline SUCCESS — $APP_NAME build #${BUILD_NUMBER} is ready!"
    }
    failure {
      echo "🔥 Pipeline FAILED — check console output"
    }
    unstable {               // ← 'unstable' = tests ran but some failed. Yellow in Jenkins UI.
      echo "⚠️ Pipeline UNSTABLE — tests have failures"
    }
    aborted {               // ← Someone clicked "Abort" or timeout triggered
      echo "⏹️ Pipeline ABORTED"
    }
  }

} // end pipeline
Complete Keyword Reference
KeywordExplanation
pipeline { }The mandatory top-level block. Everything in a Declarative Jenkinsfile lives inside this.
agentDefines WHERE the pipeline (or a stage) runs. any=any available agent. none=no default (must specify per-stage). label 'x'=only on agents with label x. docker { image 'x' }=run inside a Docker container.
options { }Pipeline-wide settings: timeouts, log rotation, concurrent build behavior, ANSI color output.
environment { }Define env vars as key=value. Available to all steps as shell env vars AND as Groovy variables via env.VAR_NAME.
stages { }Container block for all stage definitions. Required. Has exactly one child for each stage.
stage('Name') { }A logical phase of the pipeline. Shows up as a column in Blue Ocean and the Stage View. Each has a steps block.
steps { }Container for the actual commands in a stage. Each line is a step (sh, echo, sh, bat, etc.).
sh '...'Execute a shell command on Linux/Mac agents. For Windows agents use bat '...'.
post { }Runs after stages complete. Conditions: always, success, failure, unstable, aborted, changed (ran when status CHANGED from last run).

Interview Q&A
💬 What is "Pipeline as Code" and why is it better than UI-based jobs?
Pipeline as Code means the CI/CD pipeline definition (the Jenkinsfile) lives in the same Git repository as the application code. Benefits: (1) Version controlled — you can see history of pipeline changes, roll back, compare diffs. (2) Reviewable — pipeline changes go through the same PR process as code changes. (3) Reproducible — on a new Jenkins server, point it at the repo and the pipeline recreates itself. (4) Auditable — compliance teams can audit what the pipeline does. (5) Portable — easier to migrate to a new CI/CD tool.
💬 What's the difference between single quotes and double quotes in a Jenkinsfile?
This is a Groovy language rule. Double quotes "..." support string interpolation — variables like ${BUILD_NUMBER} get replaced with their actual values. Single quotes '...' are literal strings — no variable substitution happens. So sh "echo Build #${BUILD_NUMBER}" prints the actual build number, while sh 'echo Build #${BUILD_NUMBER}' prints the literal text ${BUILD_NUMBER}. Triple single quotes ''' ... ''' are multi-line literal strings used for multi-line shell blocks.

Parallel Stages

Run multiple stages simultaneously on different agents. This can cut pipeline time dramatically.

GROOVY Parallel stages in Jenkinsfile 
stage('Parallel Tests') {
  parallel {                      // ← parallel{} tells Jenkins to run all child stages AT THE SAME TIME
                                  //   Each branch runs on a separate executor (same or different agent)

    stage('Unit Tests') {         // Branch 1: Runs concurrently with 'Integration Tests'
      steps {
        sh 'mvn test -Dtest=Unit*'  // Only run classes matching Unit* pattern
      }
      post {
        always {
          junit 'target/surefire-reports/Unit*.xml'
        }
      }
    }

    stage('Integration Tests') {  // Branch 2: Runs at the same time as 'Unit Tests'
      steps {
        sh '''
          docker compose up -d postgres  # Start test database
          mvn verify -Dtest=Integration*
          docker compose down             # Clean up
        '''
      }
    }

    stage('Lint & Static Analysis') {  // Branch 3: Also runs in parallel
      steps {
        sh 'mvn checkstyle:check'
      }
    }

  }
  // Jenkins WAITS HERE until ALL parallel branches complete.
  // If ANY branch fails, the parallel stage fails.
  // Use failFast: true to abort other branches if one fails.
}

stage('Parallel Tests with failFast') {
  failFast true         // ← If any parallel branch fails, immediately abort all others
  parallel {
    stage('Test A') { steps { sh '...' } }
    stage('Test B') { steps { sh '...' } }
  }
}

Conditional Stages — when { }

Control whether a stage runs based on conditions. Essential for branch-based deployments.

GROOVY when{} conditions 
stage('Deploy to Staging') {
  when {                          // ← when{} block: stage ONLY runs if condition is true
    branch 'main'                // ← Only runs when building the 'main' branch
                                  //   feature/* branches will SKIP this stage
  }
  steps { sh './deploy.sh staging' }
}

stage('Deploy to Production') {
  when {
    allOf {                       // ← allOf = ALL conditions must be true (AND logic)
      branch 'main'
      environment name: 'DEPLOY_ENV', value: 'production'
      // environment: checks if an env var equals a specific value
    }
  }
  steps { sh './deploy.sh production' }
}

stage('Run Smoke Tests') {
  when {
    anyOf {                       // ← anyOf = ANY condition true is enough (OR logic)
      branch 'main'
      branch 'release/*'
    }
  }
  steps { sh './smoke-test.sh' }
}

stage('Conditional on Parameter') {
  when {
    expression { return params.RUN_SONAR == true }
    // ↑ expression{} evaluates a Groovy boolean expression
    //   params.RUN_SONAR references a pipeline parameter (Chapter 5)
  }
  steps { sh 'mvn sonar:sonar' }
}

Manual Approval Gate — input { }

Pause the pipeline and wait for a human to approve before continuing. Critical for production deployments at BuildForge.

GROOVY Production approval gate 
stage('Approval Gate: Deploy to Production') {
  when { branch 'main' }        // Only on main branch
  input {                         // ← input{} PAUSES the pipeline and shows a UI button
    message 'Deploy inventory-service to PRODUCTION?'
    // The message shown in Jenkins UI when awaiting approval

    ok 'Yes, deploy now!'         // Text on the "approve" button

    submitter 'tech-lead,devops-team'
    // ↑ Only these Jenkins users/groups can approve. Others see the button but can't click.

    parameters [                  // Ask for additional info when approving
      choice(
        name: 'DEPLOYMENT_REGION',
        choices: ['ap-south-1', 'us-east-1'],
        description: 'Target AWS region'
      )
    ]
  }
  steps {
    echo "Deploying to ${DEPLOYMENT_REGION}"
    sh "./deploy-prod.sh ${DEPLOYMENT_REGION}"
  }
}

Retry, Timeout & Error Handling
GROOVY Retry & timeout patterns 
stage('Push Docker Image') {
  steps {
    retry(3) {                    // ← retry(N) reruns the block up to N times if it fails
                                  //   Great for flaky network ops like docker push
      sh 'docker push registry.buildforge.io/inventory:latest'
    }
    // If the push fails 3 times, THEN the stage fails
  }
}

stage('Health Check') {
  steps {
    timeout(time: 5, unit: 'MINUTES') {  // ← Stage-level timeout
                                              //   If these steps take > 5 min, abort them
      waitUntil {                            // ← Keep retrying until returns true
        def response = sh(
          script: 'curl -s -o /dev/null -w "%{http_code}" http://staging.buildforge.io/health',
          returnStdout: true             // ← Capture shell output as a Groovy string
        ).trim()
        return response == '200'        // Return true when health check passes → exit waitUntil
      }
    }
  }
}

stage('Unstable on Lint Failure') {
  steps {
    script {                      // ← script{} lets you write plain Groovy inside Declarative
      def result = sh(script: './run-lint.sh', returnStatus: true)
      // returnStatus: true → instead of failing the step, returns the exit code as an int
      if (result != 0) {
        currentBuild.result = 'UNSTABLE'  // Mark as UNSTABLE (yellow) instead of FAILED (red)
        echo 'Lint issues found but not blocking the build'
      }
    }
  }
}

retry(N)Re-runs the enclosed block up to N times. Stops retrying once it succeeds. Fails the step after N failed attempts.
timeout(time:N, unit:'MINUTES')Aborts the enclosed block if it runs longer than the specified time. Prevents stuck builds.
waitUntil { }Repeatedly evaluates the closure until it returns true. Useful for polling health checks or waiting for resources to be ready.
script { }Drops into "Scripted Pipeline" mode inside Declarative — allows arbitrary Groovy code, if/else, loops, closures. Use sparingly.

Environment Variables

Make your pipelines dynamic and reusable. Parameters let humans (or other jobs) pass values to a pipeline at runtime.

🏢 THE STORY

BuildForge has 3 environments: dev, staging, and production. Right now you have 3 separate pipeline jobs for each environment. Your manager says: "This is silly. One pipeline should handle all three. We just tell it WHERE to deploy when we kick it off."

GROOVY Jenkinsfile — Full Parameters Example 
pipeline {
  agent any

  parameters {              // ← PARAMETERS BLOCK: defines what inputs this pipeline accepts
                            //   First time you build, Jenkins shows a form with these fields.

    string(                 // ← string parameter: free-text single-line input
      name: 'APP_VERSION',   // The variable name — access as params.APP_VERSION
      defaultValue: '1.0.0',// Pre-filled value
      description: 'Semantic version to tag this build (e.g., 1.2.3)'
    )

    choice(                 // ← choice parameter: dropdown menu
      name: 'DEPLOY_ENV',
      choices: ['dev', 'staging', 'production'],
      // ↑ First item in the list is the DEFAULT selection
      description: 'Target deployment environment'
    )

    booleanParam(           // ← boolean parameter: checkbox (true/false)
      name: 'RUN_INTEGRATION_TESTS',
      defaultValue: true,
      description: 'Run integration tests? Uncheck to speed up builds on feature branches.'
    )

    booleanParam(
      name: 'SKIP_SONAR',
      defaultValue: false,
      description: 'Skip SonarQube scan? Use only in emergencies.'
    )

    text(                   // ← text parameter: multi-line text area
      name: 'RELEASE_NOTES',
      defaultValue: 'No release notes provided',
      description: 'Describe what changed in this release'
    )

    password(               // ← password parameter: masked input (use Credentials for real secrets!)
      name: 'DB_MIGRATE_PASS',
      defaultValue: '',
      description: 'DB password for migration (only used during schema changes)'
    )
  }

  environment {
    APP_NAME = 'inventory-service'
    // You can also build env vars FROM params:
    FULL_IMAGE_TAG = "${APP_NAME}:${params.APP_VERSION}-${BUILD_NUMBER}"
    // e.g. → inventory-service:1.0.0-47
  }

  stages {
    stage('Print Build Config') {
      steps {
        echo "=== BUILD CONFIGURATION ==="
        echo "App Version  : ${params.APP_VERSION}"
        echo "Deploy To    : ${params.DEPLOY_ENV}"
        echo "Run Int Tests: ${params.RUN_INTEGRATION_TESTS}"
        echo "Full Image   : ${FULL_IMAGE_TAG}"  // Uses env var built from params
      }
    }

    stage('Integration Tests') {
      when {
        expression { return params.RUN_INTEGRATION_TESTS == true }
        // ↑ SKIPS this entire stage if checkbox is unchecked
      }
      steps { sh 'mvn verify -P integration' }
    }

    stage('Deploy') {
      steps {
        script {
          // Use params in if/else logic inside script{}
          if (params.DEPLOY_ENV == 'production') {
            echo "🔴 PRODUCTION DEPLOY — extra caution!"
            sh "./deploy.sh production ${params.APP_VERSION}"
          } else {
            echo "🟢 Deploying to ${params.DEPLOY_ENV}"
            sh "./deploy.sh ${params.DEPLOY_ENV} ${params.APP_VERSION}"
          }
        }
      }
    }
  }
}

GROOVY Using Credentials in a Jenkinsfile 
pipeline {
  agent any

  environment {
    // METHOD 1: environment{} block — credential bound to an env var
    // The credential ID is the string you gave it when saving in Jenkins UI

    DOCKER_CREDS = credentials('dockerhub-buildforge')
    // ↑ For "Username with password" type credentials, Jenkins creates:
    //   DOCKER_CREDS     = "username:password" (combined, masked)
    //   DOCKER_CREDS_USR = "username" (just the username)
    //   DOCKER_CREDS_PSW = "password" (just the password, always masked in logs)

    SLACK_TOKEN = credentials('slack-webhook-token')
    // ↑ For "Secret text" type — SLACK_TOKEN is the secret string, masked in logs

    AWS_CREDENTIALS = credentials('aws-buildforge-prod')
    // ↑ For "AWS Credentials" — creates:
    //   AWS_ACCESS_KEY_ID (the access key)
    //   AWS_SECRET_ACCESS_KEY (the secret key)
    //   These are the EXACT env vars that AWS CLI and SDKs look for automatically!
  }

  stages {
    stage('Docker Login & Push') {
      steps {
        sh '''
          # Jenkins automatically masks $DOCKER_CREDS_PSW in the console output
          # You'll see ****** instead of the actual password
          echo "$DOCKER_CREDS_PSW" | docker login -u "$DOCKER_CREDS_USR" --password-stdin
          # --password-stdin: reads password from stdin (more secure than -p flag)

          docker push registry.buildforge.io/inventory:latest
        '''
      }
    }

    stage('Deploy to AWS ECS') {
      steps {
        sh '''
          # AWS CLI automatically uses AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY from env
          aws ecs update-service \
            --cluster buildforge-prod \
            --service inventory-service \
            --force-new-deployment \
            --region ap-south-1
        '''
      }
    }

    stage('SSH Deploy to Server') {
      steps {
        // METHOD 2: withCredentials{} block — inline credential injection
        withCredentials([
          sshUserPrivateKey(
            credentialsId: 'prod-server-ssh-key',  // Credential ID from Jenkins store
            keyFileVariable: 'SSH_KEY',              // Jenkins writes the key to a temp file → $SSH_KEY path
            usernameVariable: 'SSH_USER'             // Username stored in $SSH_USER
          )
        ]) {
          sh """
            ssh -i \$SSH_KEY -o StrictHostKeyChecking=no \$SSH_USER@prod.buildforge.io \
              'cd /opt/inventory && docker pull && docker-compose up -d'
          """
          // After this withCredentials{} block closes, the temp key file is deleted
        }
      }
    }

    stage('Use Kubeconfig Secret File') {
      steps {
        withCredentials([
          file(credentialsId: 'k8s-prod-kubeconfig', variable: 'KUBECONFIG')
          // ↑ Jenkins writes the secret file to a temp path → $KUBECONFIG points to it
        ]) {
          sh 'kubectl apply -f k8s/deployment.yaml'
          // kubectl automatically reads $KUBECONFIG env var to find the cluster config
        }
      }
    }
  }
}
🚫NEVER DO THIS: sh "docker login -u admin -p mysecretpass" — The password appears in the Jenkins console log in plain text, is stored in build history, and can be seen by anyone with read access to the job. Always use credentials() or withCredentials().

Agent Labels & Stage-Level Agents
GROOVY Multi-agent pipeline 
pipeline {
  agent none    // ← 'none' at pipeline level = NO default agent
                //   This FORCES each stage to declare its own agent.
                //   Best practice for multi-agent pipelines.

  stages {

    stage('Build on Linux') {
      agent { label 'linux && maven' }  // ← Run on agents with BOTH 'linux' AND 'maven' labels
                                          //   Labels are assigned to agents in: Manage Jenkins → Nodes
                                          //   && = AND, || = OR, ! = NOT
      steps {
        sh 'mvn clean package'
        stash name: 'build-output', includes: 'target/*.jar'
        // ↑ stash{} saves files from this agent's workspace
        //   to the controller, so they can be retrieved by another agent
        //   'name' = identifier for this stash
        //   'includes' = glob pattern of files to stash
      }
    }

    stage('Test on Linux') {
      agent { label 'linux' }           // Different agent from Build stage (separate workspace!)
      steps {
        unstash 'build-output'          // ← unstash retrieves the stashed files here
        //   Now the JAR from the Build stage is available in this agent's workspace
        sh 'mvn test'
      }
    }

    stage('Build Docker (Docker Agent)') {
      agent {
        docker {
          image 'docker:24-dind'       // Run this stage inside a Docker container
          args  '-v /var/run/docker.sock:/var/run/docker.sock'
          // ↑ Mount Docker socket so this container can run docker commands
        }
      }
      steps {
        sh 'docker build -t buildforge/inventory:latest .'
      }
    }

    stage('iOS Build (Mac Agent)') {
      agent { label 'macos && xcode' }  // Only on Mac agents with Xcode installed
      when { branch 'main' }
      steps {
        sh 'xcodebuild -scheme BuildForgeApp -configuration Release'
      }
    }

  }
}

Docker in
Jenkins Pipelines

Use Docker containers as build environments, build Docker images of your apps, and push them to container registries — all inside Jenkins.

🏢 THE STORY

BuildForge's inventory service is being containerized. The dev team delivers a Dockerfile. Your job: wire Jenkins to automatically build that Docker image on every push to main, tag it with the build number, and push it to ECR (AWS Elastic Container Registry). Then update the ECS service to use the new image.

GROOVY Full Docker CI/CD Jenkinsfile 
pipeline {
  agent any

  environment {
    AWS_REGION      = 'ap-south-1'
    ECR_REGISTRY    = '123456789.dkr.ecr.ap-south-1.amazonaws.com'
    ECR_REPO        = 'buildforge/inventory-service'
    IMAGE_TAG       = "${BUILD_NUMBER}"                     // e.g., "47"
    FULL_IMAGE_URI  = "${ECR_REGISTRY}/${ECR_REPO}:${IMAGE_TAG}"
    // e.g., 123456789.dkr.ecr.ap-south-1.amazonaws.com/buildforge/inventory-service:47

    AWS_CREDS       = credentials('aws-buildforge-prod')
    // Injects: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY into the shell environment
  }

  stages {

    stage('Checkout') {
      steps { checkout scm }
    }

    stage('Build App') {
      agent {
        docker {
          image 'maven:3.9-eclipse-temurin-17'
          // ↑ Run the Maven build INSIDE this Docker container
          //   Means: no need to install Maven on the Jenkins agent itself!
          //   The container has exactly the right version of Maven + JDK.
          args '-v $HOME/.m2:/root/.m2'
          // ↑ Mount Maven local repository cache from host to container
          //   Without this: every build re-downloads ALL dependencies (slow!)
          //   With this: dependencies are cached across builds (fast!)
        }
      }
      steps {
        sh 'mvn clean package -DskipTests'
      }
    }

    stage('Build Docker Image') {
      steps {
        sh """
          # Build the Docker image from the Dockerfile in the current workspace root
          docker build \
            -t \${FULL_IMAGE_URI} \         # Full ECR URI with build number tag
            -t \${ECR_REGISTRY}/\${ECR_REPO}:latest \  # Also tag as 'latest'
            --build-arg BUILD_NUM=\${BUILD_NUMBER} \   # Pass build number as a Docker ARG
            --build-arg GIT_COMMIT=\${GIT_COMMIT} \   # Bake git SHA into the image (for tracing)
            .                                          # . = build context = current directory (workspace)
        """
      }
    }

    stage('Push to ECR') {
      steps {
        retry(3) {                            // Retry push up to 3 times (network flakiness)
          sh """
            # Step 1: Get a temporary ECR login token (valid 12 hours)
            aws ecr get-login-password \
              --region \${AWS_REGION} | \    # aws ecr get-login-password outputs a token to stdout
            docker login \
              --username AWS \              # ECR always uses "AWS" as username
              --password-stdin \            # Read password from stdin (the token from above)
              \${ECR_REGISTRY}              # Authenticate against our ECR registry URL

            # Step 2: Push both tags to ECR
            docker push \${FULL_IMAGE_URI}   # Push the build-number-tagged version
            docker push \${ECR_REGISTRY}/\${ECR_REPO}:latest  # Push 'latest' tag
          """
        }
      }
    }

    stage('Deploy to ECS') {
      when { branch 'main' }
      steps {
        sh """
          # Update ECS service to force a new deployment
          # ECS will pull the new :latest image from ECR for each task
          aws ecs update-service \
            --cluster buildforge-prod-cluster \
            --service inventory-svc \
            --force-new-deployment \
            --region \${AWS_REGION}

          # Wait for ECS deployment to stabilize (all tasks running new version)
          aws ecs wait services-stable \
            --cluster buildforge-prod-cluster \
            --services inventory-svc \
            --region \${AWS_REGION}
          # aws ecs wait = polls until the condition is met (or timeout after 10 min)
        """
      }
    }

    stage('Cleanup Local Images') {
      steps {
        sh """
          # Remove local Docker images to free up disk space on Jenkins agent
          docker rmi \${FULL_IMAGE_URI} || true  # '|| true' prevents failure if image not found
          docker rmi \${ECR_REGISTRY}/\${ECR_REPO}:latest || true
          docker image prune -f               # Remove dangling (untagged) images
        """
      }
    }

  }

  post {
    always { cleanWs() }
    success { echo "✅ Image ${FULL_IMAGE_URI} built & deployed!" }
    failure { echo "❌ Docker pipeline failed — check logs" }
  }
}

BuildForge has 15 services. Each Jenkinsfile is 200 lines of copy-pasted code. When you need to update the Docker push step, you'd need to edit 15 files. Shared Libraries solve this.

🏢 THE STORY

Your tech lead is reviewing your pipeline PRs and says: "Every service has the same Docker build, ECR push, and ECS deploy logic. This violates DRY. Build a Shared Library — a central Groovy code repo that all Jenkinsfiles can import and call like functions."

📁

GROOVY vars/buildDockerImage.groovy 
// This file defines a global function called 'buildDockerImage'
// It can be called from ANY Jenkinsfile that imports this library

// The special method name 'call()' makes this a callable: buildDockerImage(...)
def call(Map config = [:]) {   // Map config = [:] means: accept a Groovy map of named arguments
                              // [:] is an empty map (default if nothing passed)
  // Extract values from the config map with defaults
  def imageName  = config.get('imageName', 'myapp')
  def imageTag   = config.get('imageTag', env.BUILD_NUMBER)
  def dockerfile = config.get('dockerfile', 'Dockerfile')
  def context    = config.get('context', '.')

  echo "[buildDockerImage] Building ${imageName}:${imageTag}"

  sh """
    docker build \
      -f ${dockerfile} \
      -t ${imageName}:${imageTag} \
      -t ${imageName}:latest \
      --build-arg BUILD_NUMBER=${imageTag} \
      ${context}
  """

  // Return the full image reference so callers can use it
  return "${imageName}:${imageTag}"
}

COPY src ./src    # Now copy source code (this layer changes every commit)
RUN mvn package -DskipTests -q   # Build the JAR

# ── STAGE 2: Runtime Stage ───────────────────────────────────────────────
# Use a minimal JRE image (not full JDK) — smaller, fewer attack surface
FROM eclipse-temurin:17-jre-alpine
              # ↑ alpine = tiny Linux (5MB vs 80MB). jre = only Java Runtime (no compiler)

ARG GIT_COMMIT
ARG BUILD_DATE

LABEL org.opencontainers.image.revision="${GIT_COMMIT}"
LABEL org.opencontainers.image.created="${BUILD_DATE}"
LABEL maintainer="devops@buildforge.io"

COPY --from=builder /build/target/*.jar app.jar
     # ↑ --from=builder references Stage 1 by its 'AS builder' name

Complete Interview Q&A — Jenkins Expert Level
💬 How do you implement zero-downtime deployments with Jenkins + ECS?
Using ECS Rolling Update deployment type (default). ECS gradually replaces old tasks with new ones. Key settings: minimumHealthyPercent=50 (keep at least 50% running during deployment), maximumPercent=200 (allow up to 200% of desired count during replacement). Jenkins uses 'aws ecs wait services-stable' to block until deployment completes. For true zero-downtime, configure the ALB health check grace period to match Spring Boot startup time (typically 60-90s).
💬 How do you handle rollbacks in Jenkins pipelines?
Strategy: Before deploying, save the current ECS task definition ARN to a file and stash it. In the post{failure} block, unstash that file and call 'aws ecs update-service --task-definition [old-ARN]' to revert. For Docker-based deployments, the old image tag still exists in ECR (never overwrite existing tags — always use build number tags). For database migrations, use Flyway's repair/undo features, but design migrations to be backward-compatible so app rollback doesn't break the schema.
💬 What is a Jenkins Shared Library and when would you create one?
A Shared Library is a Groovy code repository referenced by Jenkinsfiles across many jobs. Create one when: (1) Multiple Jenkinsfiles contain duplicate logic (DRY violation), (2) You want to enforce organizational standards (required security scans, notification formats), (3) Pipeline logic is complex enough to benefit from unit testing. The library lives in its own Git repo with a vars/ directory for global functions and src/ for Groovy classes. Any pipeline can import it with @Library('name') and call functions directly.
💬 How do you secure Jenkins against unauthorized access?
Key security measures: (1) Enable authentication — Matrix-based security or LDAP/AD integration. (2) Use role-based access control (RBAC) via the Role-Based Strategy plugin — devs get build/read access, only DevOps can manage agents/credentials. (3) Disable remote API without authentication. (4) Use Credentials store for all secrets — never plaintext in Jenkinsfiles. (5) Enable CSRF protection (on by default in modern Jenkins). (6) Restrict which nodes/agents pipelines can run on using folder-based access. (7) Enable script security for Groovy sandboxing. (8) Regularly update Jenkins and plugins (known CVEs).
💬 Jenkins vs GitHub Actions — when do you choose each?
Choose Jenkins when: self-hosted infrastructure required (compliance, air-gapped networks), complex multi-platform builds (Linux + Windows + Mac agents), existing heavy customization investment, need for very long-running or resource-intensive builds on dedicated hardware. Choose GitHub Actions when: starting fresh, team is GitHub-native, quick setup is a priority, cost-per-minute model is acceptable, builds are containerizable, public OSS projects (free minutes). Many enterprises use both: GitHub Actions for quick lint/test PRs (fast), Jenkins for production deployment pipelines (full control).
