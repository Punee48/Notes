"Hello World" VM Provisioner —
Authenticating Ansible to OpenShift

Before Ansible can create anything on OPC-V (OpenShift Container Platform Virtualization), it has to prove who it is to the cluster's API server. This is the very first project of the series — no templates, no DataVolume cloning, no networking. Just: connect, authenticate, and confirm Ansible can talk to the cluster. Everything later in this series builds on getting this part right.

redhat.openshift_virtualizationkubernetes.corekubeconfigServiceAccount tokenROSA / AWS EBS
📞 The Ask

It's your first week on the OPC-V automation effort. Ravi keeps it simple: "Puneeth, forget templates and networking for now. I want to see ONE thing: Ansible reaching out to our OpenShift cluster on AWS and standing up a single, boring RHEL VM. No fancy sizing, no VLANs — just prove the connection works end to end. Call it your 'Hello World.'"

TechNova's OPC-V cluster runs as a ROSA (Red Hat OpenShift Service on AWS) cluster, which matters for one specific reason later in this chapter: its default StorageClass is backed by AWS Elastic Block Store (EBS) — so any VM disk you create rides on EBS volumes without you touching the AWS console at all.

💡 Concept — How Ansible Authenticates to an OpenShift Cluster

Ansible doesn't talk to KubeVirt or OpenShift Virtualization through a special VM API — it talks to the same Kubernetes API server that every oc or kubectl command hits, using the kubernetes.core collection's connection plugin. The redhat.openshift_virtualization collection then layers VM-specific modules and roles on top of that same connection. There are two supported ways to authenticate:

  • kubeconfig file — the same file oc login writes to ~/.kube/config. Good for interactive/local runs.
  • ServiceAccount token + API host — the enterprise pattern. AAP (Ansible Automation Platform) stores the token as a Credential, never a checked-in file, and injects it at job runtime.

🛠️ Hands-On — Setting Up the ServiceAccount and Collections
setup/01_create_serviceaccount.sh — one-time cluster setup (run by a cluster-admin)
# Run once by a platform admin — NOT part of the Ansible playbook itself.
# This creates the identity Ansible will authenticate as.
oc create serviceaccount ansible-vm-provisioner -n technova-dev-vms
# Grant it just enough RBAC to manage VMs and their dependent objects —
# never cluster-admin. This is the same least-privilege principle used
# for AAP Execute-only roles in the RHAAP masterclass series.
oc create role vm-provisioner-role -n technova-dev-vms \
  --verb=get,list,watch,create,update,patch,delete \
  --resource=virtualmachines.kubevirt.io,virtualmachineinstances.kubevirt.io,datavolumes.cdi.kubevirt.io

oc create rolebinding vm-provisioner-binding -n technova-dev-vms \
  --role=vm-provisioner-role \
  --serviceaccount=technova-dev-vms:ansible-vm-provisioner

# Extract the token — this value goes into an AAP Credential, never a
# plaintext file in the playbook repo.
oc create token ansible-vm-provisioner -n technova-dev-vms --duration=8760h
requirements.yml — collections this project depends on
collections:
  - name: redhat.openshift_virtualization
    # Ships the VM-focused modules/roles built on top of kubernetes.core —
    # this is the collection Ravi specifically asked you to use.
  - name: kubernetes.core
    # Provides k8s / k8s_info — the generic Kubernetes API modules that
    # redhat.openshift_virtualization itself depends on under the hood.
playbooks/00_test_connection.yml — confirm auth works before creating anything
- name: Step 0 — Prove Ansible can authenticate to the OpenShift API
  hosts: localhost
  gather_facts: false
  vars:
    # In real use these come from an AAP Credential (kubernetes.core.k8s
    # auth), NOT from vars checked into git. Shown here for clarity only.
    k8s_auth:
      host: "{{ lookup('env', 'OPCV_API_HOST') }}"
      api_key: "{{ lookup('env', 'OPCV_SA_TOKEN') }}"
      validate_certs: true
  tasks:

    - name: List namespaces as a pure authentication smoke test
      kubernetes.core.k8s_info:
        host: "{{ k8s_auth.host }}"
        api_key: "{{ k8s_auth.api_key }}"
        validate_certs: "{{ k8s_auth.validate_certs }}"
        kind: Namespace
      register: ns_check
      # If the token or host is wrong, THIS task fails immediately with a
      # clear 401/connection error — long before any VM object is attempted.

    - name: Confirm our target namespace is visible to this ServiceAccount
      assert:
        that: "'technova-dev-vms' in (ns_check.resources | map(attribute='metadata.name') | list)"
        fail_msg: "Authenticated, but this ServiceAccount cannot see 'technova-dev-vms' — check the RoleBinding"
        success_msg: "Authentication confirmed — target namespace is visible"
💡 Production Tip

Never put api_key in a vars file that gets committed to git — even encrypted repos get cloned to laptops. In AAP, this token lives as an OpenShift Credential type and is injected as environment variables at job-run time; the playbook only ever references lookup('env', ...) or the credential-backed connection vars, exactly like the Vault-sourced root password pattern from Project 2.

🎯 Interview Questions — Chapter 1
Q1: Does Ansible need a special "VM API" to manage OpenShift Virtualization, or does it reuse something you already know?
It reuses the standard Kubernetes API server — the exact same endpoint `oc` and `kubectl` use. VMs, DataVolumes, and NetworkAttachmentDefinitions are just Custom Resource Definitions (CRDs). The `redhat.openshift_virtualization` collection adds VM-shaped modules and roles, but underneath, authentication and API calls flow through `kubernetes.core` exactly like managing a Deployment or ConfigMap.

Q2: Why authenticate with a ServiceAccount token instead of a personal kubeconfig in an automated pipeline?
A personal kubeconfig is tied to a human's identity, permissions, and session — it expires, changes when that person leaves, and often carries far more access than automation needs. A dedicated ServiceAccount with a narrowly-scoped Role (only the verbs and resources this pipeline actually touches) gives automation its own auditable, revocable identity — the same least-privilege principle behind AAP's Execute-only roles.
Q3: Why run a "test connection" playbook (listing namespaces) before ever trying to create a VM?
It isolates the failure domain. If the very first VM-creation task fails, you don't immediately know if it's an auth problem, an RBAC problem, or a VM-spec problem. A cheap, read-only smoke test (`k8s_info` listing namespaces) confirms auth and connectivity are solid first, so any later failure can only be about the VM definition itself.

Deploying Your First VM —
CPU, Memory, Disk & AWS EBS

Authentication is proven. Now the actual "Hello World": one Ansible playbook, using redhat.openshift_virtualization, that defines a minimal RHEL VM's CPU, memory, and disk size — and lets it land on whatever default AWS EBS-backed StorageClass the ROSA cluster already provides, with zero manual AWS console work.

📞 The Ask

Ravi checks in again: "Connection works, good. Now deploy an actual VM — 2 CPU, 4GB RAM, 30GB disk, RHEL 9. Don't worry about which storage backend it uses. We're on AWS — whatever EBS-backed StorageClass is already the cluster default is exactly what I want it to use. Don't hardcode anything AWS-specific."

💡 Concept — Relying on the Default StorageClass on AWS/ROSA

A ROSA cluster ships with a default StorageClass (commonly gp3-csi) provisioned by the AWS EBS CSI driver — every PVC created without an explicit storageClassName automatically binds to it. This means a VM's disk request can stay completely cloud-agnostic in the playbook: no AWS account IDs, no EBS volume types, no region logic. The moment this same playbook runs against a bare-metal or vSphere-backed OpenShift cluster instead, it silently uses whatever that cluster's default StorageClass is — with no code change. That portability is the entire point of never hardcoding a StorageClass in a "Hello World" project.

🛠️ Hands-On — The Minimal VM Playbook
playbooks/01_hello_world_vm.yml
- name: Hello World — deploy one minimal RHEL VM on OPC-V
  hosts: localhost
  gather_facts: false
  collections:
    - redhat.openshift_virtualization
  vars:
    vm_name: hello-world-vm
    vm_namespace: technova-dev-vms
    vm_cpu_cores: 2
    vm_memory: 4Gi
    vm_disk_size: 30Gi
  tasks:

    - name: Create a minimal DataVolume — no storageClassName means "use the cluster default"
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: cdi.kubevirt.io/v1beta1
          kind: DataVolume
          metadata:
            name: "{{ vm_name }}-disk"
            namespace: "{{ vm_namespace }}"
          spec:
            source:
              registry:
                # Pulling straight from Red Hat's container-native RHEL 9
                # guest image registry — simplest possible boot source for
                # a "Hello World," no golden-image PVC dependency yet.
                url: "docker://registry.redhat.io/rhel9/rhel-guest-image:latest"
            pvc:
              accessModes:
                - ReadWriteOnce
              resources:
                requests:
                  storage: "{{ vm_disk_size }}"
              # storageClassName is DELIBERATELY absent. On this ROSA
              # cluster that resolves to gp3-csi (AWS EBS) automatically —
              # on a different cluster it would resolve to THAT cluster's
              # own default. The playbook never needs to know or care.

    - name: Create the VirtualMachine with minimal CPU/memory sizing
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: kubevirt.io/v1
          kind: VirtualMachine
          metadata:
            name: "{{ vm_name }}"
            namespace: "{{ vm_namespace }}"
          spec:
            running: true
            # running: true right away — this is a "Hello World," we WANT
            # to see it boot immediately for the demo. Project 2 is where
            # you'll see the more careful running:false-first pattern.
            template:
              spec:
                domain:
                  cpu:
                    cores: "{{ vm_cpu_cores }}"
                  resources:
                    requests:
                      memory: "{{ vm_memory }}"
                  devices:
                    disks:
                      - name: rootdisk
                        disk:
                          bus: virtio
                volumes:
                  - name: rootdisk
                    dataVolume:
                      name: "{{ vm_name }}-disk"
      # Notice: no networks/interfaces block at all. Default masquerade
      # pod-network is fine for "Hello World" — Multus/VLAN attachment is
      # exactly the piece Project 2 adds on top of this foundation.

    - name: Confirm the VM object was accepted by the API server
      kubernetes.core.k8s_info:
        api_version: kubevirt.io/v1
        kind: VirtualMachine
        name: "{{ vm_name }}"
        namespace: "{{ vm_namespace }}"
      register: hello_vm_check

    - name: Print a friendly confirmation — the actual "Hello World" moment
      debug:
        msg: "Hello, OPC-V! '{{ vm_name }}' exists in namespace '{{ vm_namespace }}' with {{ vm_cpu_cores }} vCPU / {{ vm_memory }} RAM on a {{ vm_disk_size }} disk backed by whatever StorageClass this cluster defaults to."

⚠️ Common Mistake

Hardcoding storageClassName: gp3-csi "to be explicit" defeats the purpose of this exercise — it silently ties the playbook to AWS/ROSA specifically. Omitting it and trusting the cluster default is what makes the same playbook portable across environments, which is exactly the AWS aspect Ravi asked you to lean on rather than fight.

🎯 Interview Questions — Chapter 2
Q1: Why does the DataVolume in this playbook omit `storageClassName` entirely?
Omitting it lets Kubernetes' admission logic bind the PVC to whichever StorageClass is marked default in that cluster — on TechNova's ROSA cluster that's an AWS EBS-backed class (e.g. `gp3-csi`), provisioned automatically by the AWS EBS CSI driver. The playbook stays portable: run it against a different OpenShift cluster with a different default (NetApp, Ceph, vSphere) and it still works, with zero edits.
Q2: What's the practical difference between this DataVolume's `registry` source and Project 2's `pvc` clone source?
A registry source pulls the guest disk image straight from a container registry on every DataVolume creation — simple, dependency-free, but slower and repeated per VM. A pvc clone source (used in Project 2) clones from an already-imported "golden image" PVC sitting in the cluster — much faster at scale since the image is only pulled once and then thin-cloned for every subsequent VM. Project 1 uses `registry` because it's the simplest path with no prerequisite golden-image setup.
Q3: Why is it acceptable here to set `running: true` immediately, when Project 2 deliberately creates the VM stopped first?
Project 1 is a single, disposable "Hello World" VM with no production stakes — booting immediately and watching it come up is the whole point of the exercise. Project 2's `running:false`-then-flip pattern exists for production self-service provisioning, where you want to verify the object was accepted cleanly (disks, network, sizing) before spending compute cycles booting it. Different risk profile, different pattern — both are valid depending on the goal.
