Chapter 1 · Serverless Kubernetes

EKS Fargate — Run Pods Without Managing EC2 Nodes

No nodes to patch, no capacity to plan. AWS manages the infrastructure completely.
📖 The Fargate Story

You're running ShopEasy on EKS with 5 EC2 worker nodes. You have to manage those nodes: patch their OS, upgrade Kubernetes on them, choose the right instance type, handle spot interruptions, and make sure they're not sitting idle at 3 AM wasting money.

Your colleague says: "Just use Fargate. You describe a pod's CPU and memory. AWS finds the right server, runs your pod on it, and you never touch a node. The server disappears when your pod terminates." No more node management, no idle capacity, no OS patching. You pay per second, per pod, only for what actually runs.

Tradeoff: Fargate is ~20-30% more expensive per vCPU than EC2, has slower cold starts, and can't run privileged pods or DaemonSets. Use it for batch jobs, dev/test workloads, and variable traffic services. Use EC2 node groups for stateful apps and high-throughput APIs.

1.2 Fargate Profile — How to Enable It

A Fargate Profile tells EKS which pods to run on Fargate. It matches pods by namespace and labels. Any pod matching the selector gets scheduled onto Fargate instead of EC2 nodes.

fargate-profile.yaml
YAML · Fargate Profile via eksctl 
# eksctl config to add Fargate profile to existing cluster
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: shopeasy-cluster
  region: ap-south-1

fargateProfiles:                        # Define which pods go to Fargate

  - name: batch-jobs-profile             # Profile name
    selectors:                           # Rules: which pods match this profile?
      - namespace: batch                 # All pods in 'batch' namespace → Fargate

  - name: dev-profile
    selectors:
      - namespace: development          # Dev namespace → Fargate (cheap, no idle nodes)

  - name: scheduled-tasks-profile
    selectors:
      - namespace: production           # Only specific pods in production
        labels:
          workload-type: batch         # Only pods with this label → Fargate
                       # Pods without this label → EC2 nodes (your API, DB)

1.3 A Real Fargate Use Case — Nightly Report Job

report-cronjob.yaml
YAML · CronJob on Fargate 
apiVersion: batch/v1                  # "batch" API group = CronJobs, Jobs
kind: CronJob                         # Runs a job on a schedule (like Linux cron)
metadata:
  name: nightly-sales-report
  namespace: batch                   # This namespace is in our Fargate profile
spec:
  schedule: "0 2 * * *"              # Run at 02:00 AM every day (cron syntax)
                                        # "0 2 * * *" = minute:0 hour:2 day:* month:* weekday:*
  successfulJobsHistoryLimit: 3       # Keep last 3 successful job records
  failedJobsHistoryLimit: 1           # Keep last 1 failed job for debugging
  jobTemplate:                        # What to run each time
    spec:
      template:
        metadata:
          labels:
            workload-type: batch     # Matches our Fargate profile selector!
        spec:
          restartPolicy: OnFailure   # Retry if job fails (not Never = give up)
          containers:
          - name: report-generator
            image: 123456.dkr.ecr.ap-south-1.amazonaws.com/shopeasy-reports:latest
            command: ["node", "generate-report.js"]
            env:
            - name: REPORT_DATE
              value: "yesterday"
            resources:                # Fargate uses EXACT values (no overcommit)
              requests:
                cpu: "1"             # Fargate valid CPU: 0.25, 0.5, 1, 2, 4 vCPU
                memory: "2Gi"       # Fargate valid memory: depends on CPU choice
              limits:
                cpu: "1"             # In Fargate, requests = limits (what you pay)
                memory: "2Gi"

Chapter 2 · Next-Gen Autoscaling

Karpenter — Smart Node Provisioning in Seconds

Cluster Autoscaler scales in minutes. Karpenter provisions the perfect node in under 60 seconds.
📖 Why Karpenter Replaced Cluster Autoscaler

The old way: Cluster Autoscaler works with pre-defined Auto Scaling Groups (ASGs). You choose an instance type (e.g., m5.xlarge) and the autoscaler adds more of the same. Problem: if your pods need different sizes — some need 1 CPU, some need 16 CPU — you need multiple ASGs, and the autoscaler is slow (3-5 minutes to add a node).

Karpenter is different. It watches for pending pods, calculates the exact right instance type based on what those pods actually need, provisions it directly via EC2 Fleet API, and has your pod running in under 60 seconds. It also picks Spot instances automatically when safe, consolidates underutilized nodes, and replaces expensive nodes with cheaper ones when pods are shifted around — all automatically.

2.1 Karpenter vs Cluster Autoscaler

FeatureCluster AutoscalerKarpenter ✅
Node Provisioning Speed3–5 minutesUnder 60 seconds

Spot IntegrationManual ASG configurationAutomatic spot with fallback
Node ConsolidationManual / basicAutomatic consolidation (saves cost)
ConfigurationComplex, many flagsSimple NodePool YAML
Cloud SupportMulti-cloudAWS-native (best on EKS)

2.3 NodePool — Word by Word

A NodePool is Karpenter's config object. It defines what kinds of nodes Karpenter can create, what workloads can use them, and how to handle spot interruptions and consolidation.

nodepool-default.yaml
YAML · Karpenter NodePool 
apiVersion: karpenter.sh/v1beta1
kind: NodePool                       # Karpenter's CRD — replaces ASG configs
metadata:
  name: default
spec:
  template:
    spec:
      nodeClassRef:                   # Reference to EC2NodeClass (AWS-specific config)
        apiVersion: karpenter.k8s.aws/v1beta1
        kind: EC2NodeClass
        name: default
      requirements:                   # What kinds of nodes are allowed?
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
                    # Try Spot first (up to 80% cheaper). Fall back to on-demand if no spot.
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["m5.large", "m5.xlarge", "m6i.large", "m6i.xlarge", "c5.large", "c5.xlarge"]
                    # Many instance types = better spot availability
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64"]              # x86 architecture (ARM = arm64 for Graviton)
        - key: kubernetes.io/os
          operator: In
          values: ["linux"]

  limits:                             # Cost guardrails — never exceed this
    cpu: "100"                       # Max 100 total CPU across all Karpenter nodes
    memory: 400Gi                    # Max 400GB total RAM

  disruption:                         # How to handle node removal / consolidation
    consolidationPolicy: WhenUnderutilized
        # If a node is underutilized, move its pods to another node and delete it. Saves money!
    consolidateAfter: 30s             # Wait 30s after becoming underutilized before moving pods
    expireAfter: 720h                 # Force-replace nodes after 30 days (security patching)

---
apiVersion: karpenter.k8s.aws/v1beta1
kind: EC2NodeClass                   # AWS-specific node configuration
metadata:
  name: default
spec:
  amiFamily: AL2                     # Use Amazon Linux 2 (EKS-optimized)
  role: KarpenterNodeRole-shopeasy-cluster
    # IAM Role for the node (must have AmazonEKSWorkerNodePolicy, AmazonEC2ContainerRegistryReadOnly)
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: shopeasy-cluster
                # Karpenter looks for subnets tagged with this key — your VPC private subnets
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: shopeasy-cluster
  blockDeviceMappings:
    - deviceName: /dev/xvda
      ebs:
        volumeSize: 50Gi             # 50GB root volume per node
        volumeType: gp3              # gp3 is faster and cheaper than gp2
        encrypted: true

Chapter 3 · Enterprise Architecture

Multi-Cluster EKS — One App, Multiple Regions

Run ShopEasy across Mumbai, Singapore, and Frankfurt simultaneously for global HA.
📖 Why Multi-Cluster?

ShopEasy has grown. You now have 500,000 users across India, Southeast Asia, and Europe. A single Mumbai EKS cluster gives 200ms latency to European users. If that cluster has an AWS outage, all users are affected simultaneously.

The enterprise answer: 3 regional clusters (Mumbai, Singapore, Frankfurt), with AWS Route53 routing users to the nearest healthy cluster. Each cluster runs a full copy of ShopEasy. A central management cluster with ArgoCD deploys to all 3 using ApplicationSets. If Mumbai goes down, Route53 routes traffic to Singapore in under 60 seconds.

3.2 ArgoCD ApplicationSet — Deploy to All Clusters at Once

applicationset-global.yaml
YAML · ArgoCD ApplicationSet 
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet               # ArgoCD's "Application factory" — creates many apps at once
metadata:
  name: shopeasy-global
  namespace: argocd
spec:
  generators:                       # How to generate multiple Applications
  - list:                           # "list" generator: create one App per item in the list
      elements:
      - cluster: mumbai              # ShopEasy in Mumbai
        url: https://mumbai-eks.ap-south-1.eks.amazonaws.com
        env: production
        region: ap-south-1
      - cluster: singapore
        url: https://singapore-eks.ap-southeast-1.eks.amazonaws.com
        env: production
        region: ap-southeast-1
      - cluster: frankfurt
        url: https://frankfurt-eks.eu-central-1.eks.amazonaws.com
        env: production
        region: eu-central-1

  template:                         # The Application template (uses {{ }} variables from list above)
    metadata:
      name: shopeasy-{{cluster}}   # → creates: shopeasy-mumbai, shopeasy-singapore, shopeasy-frankfurt
    spec:
      project: default
      source:
        repoURL: https://github.com/yourorg/shopeasy-k8s
        targetRevision: HEAD
        path: helm/backend
        helm:
          valueFiles:
          - values-{{env}}.yaml        # → uses values-production.yaml for each
          parameters:
          - name: aws.region
            value: {{region}}         # Each cluster gets its own region value
      destination:
        server: {{url}}              # Deploy to each cluster's API endpoint
        namespace: production
      syncPolicy:
        automated:
          prune: true
          selfHeal: true

Chapter 4 · Disaster Recovery

Velero — Backup & Restore Your Entire Cluster

When disaster strikes, restore your cluster state in minutes, not days.
📖 The Disaster Story

A junior developer runs kubectl delete namespace production instead of kubectl delete namespace staging. All your deployments, services, configmaps, secrets — gone in 2 seconds. Without a backup, you're rebuilding from scratch. With Velero, you restore in 5 minutes.

Velero takes snapshots of all your K8s objects (Deployments, Services, ConfigMaps, Secrets, PVCs) and stores them in S3. It also snapshots your EBS volumes. You can restore the entire cluster, a single namespace, or just one resource. Schedule backups every hour, retain for 30 days.

velero-backup-schedule.yaml
YAML · Velero Backup Schedule 
# Schedule — automatically backup every hour
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: production-hourly-backup
  namespace: velero                # Velero lives in its own namespace
spec:
  schedule: "0 * * * *"           # Every hour at :00 (cron syntax)
  template:
    includedNamespaces:           # Which namespaces to backup
    - production
    - monitoring
    - argocd
    snapshotVolumes: true        # Also snapshot EBS volumes (EBS Snapshots via AWS API)
    storageLocation: default     # Where to store: S3 bucket (configured at install)
    ttl: 720h                     # Keep backups for 30 days (720 hours)
                                     # Old backups auto-deleted after TTL
    labelSelector:                # (Optional) backup only pods with these labels
      matchLabels:
        backup: "true"            # Only backup resources tagged backup=true

Chapter 5 · Resilience

Chaos Engineering — Break Things Intentionally to Build Confidence

If you haven't broken it on purpose, it will break at the worst possible time.
📖 The Netflix Philosophy

Netflix runs a tool called Chaos Monkey in production. It randomly kills EC2 instances to verify their systems actually recover. Sounds insane — but the philosophy is sound: if failure is inevitable, you should control when, how, and what happens when it occurs.

For ShopEasy on EKS: Does your app recover when a pod is killed? When a node goes down? When the database connection fails? When the network is slow? Chaos Engineering is the discipline of answering these questions in a controlled way, before your users discover the answers for you.

LitmusChaos is the CNCF-graduated chaos engineering platform for Kubernetes. It injects failures as K8s experiments — kill pods, drain nodes, add network latency, exhaust CPU, fill disk — and measures if your system meets its SLOs.

5.2 ChaosEngine — Pod Kill Experiment

chaos-pod-delete.yaml
YAML · LitmusChaos ChaosEngine 
apiVersion: litmuschaos.io/v1alpha1
kind: ChaosEngine                   # The "run this experiment" object
metadata:
  name: backend-pod-kill-test
  namespace: production
spec:
  appinfo:
    appns: production               # Which namespace the target app is in
    applabel: app=backend           # Which pods to target (app=backend)
    appkind: deployment            # Type of workload (deployment, statefulset)

  engineState: active              # "active" = run the experiment, "stop" = halt

  chaosServiceAccount: litmus-admin
    # ServiceAccount with permissions to kill pods

  monitoring: true                 # Export metrics to Prometheus during chaos

  experiments:
  - name: pod-delete               # Which chaos experiment to run
    spec:
      components:
        env:
        - name: TOTAL_CHAOS_DURATION
          value: "60"               # Run chaos for 60 seconds
        - name: CHAOS_INTERVAL
          value: "10"               # Kill a pod every 10 seconds
        - name: PODS_AFFECTED_PERC
          value: "33"               # Kill 33% of backend pods at a time
        - name: FORCE
          value: "false"            # Graceful termination (false) vs SIGKILL (true)
      probe:                         # Steady-state hypothesis: is the app still working?
      - name: http-probe
        type: httpProbe
        httpProbe/inputs:
          url: https://shopeasy.yourdomain.com/api/health
          insecureSkipVerify: false
          responseTimeout: 2000      # API must respond within 2 seconds during chaos
          method:
            get:
              criteria: ==
              responseCode: "200"    # Must return 200 — if not, experiment FAILS
        mode: Continuous            # Check continuously throughout experiment
        runProperties:
          probeTimeout: 5           # 5s timeout per probe check
          interval: 5               # Check every 5 seconds
          retry: 3                   # Allow 3 failures before marking experiment as failed

5.3 Chaos Experiment Results — What to Look For

✅
Pass: Self-Healing Works
Pods get killed, Deployment restarts them within 10s. HTTP probe stays 200. Your app is resilient.
⚠️
Partial: Slow Recovery
Pods restart but take 45s. HTTP probe has 5-second gaps. Fix: add readinessProbe + increase replicas.
❌
Fail: Complete Outage
All pods killed, no traffic. Fix: PodDisruptionBudget + increase minReplicas in HPA.
🔍
Discovery: Hidden Bug
Pod restart causes DB connection pool to overflow. Fix: add connection retry + circuit breaker.
pdb-backend.yaml
YAML · PodDisruptionBudget 
# PodDisruptionBudget: Tells K8s "never take down more than X pods at once"
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: backend-pdb
  namespace: production
spec:
  selector:
    matchLabels:
      app: backend
  minAvailable: 2                 # ALWAYS keep at least 2 backend pods running
                                     # So if you have 3 pods, only 1 can be evicted at a time
                                     # Even during: node drain, rolling update, chaos experiment

6.2 Tactic 1 — Spot Instances with Karpenter

Already covered in Chapter 2 — Karpenter's capacity-type: spot gives you up to 80% savings on EC2 cost. Use multiple instance families to maximize spot pool availability. Run stateless APIs and batch jobs on spot. Keep databases and stateful apps on on-demand.

6.3 Tactic 2 — Cluster Shutdown Schedule (Dev/Staging)

shutdown-schedule.yaml + Lambda
YAML · Scale Down Dev at Night 
# Scale DOWN dev cluster at 8 PM every day (nobody using it at night)
# Scale UP dev cluster at 8 AM every day (team starts work)
# Saves ~65% on dev node costs

# Option A: K8s CronJob that scales deployments to 0 at night
apiVersion: batch/v1
kind: CronJob
metadata:
  name: scale-down-dev
  namespace: development
spec:
  schedule: "0 20 * * 1-5"         # 8 PM Monday-Friday (IST = UTC+5:30)
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: scale-operator
          restartPolicy: OnFailure
          containers:
          - name: kubectl
            image: bitnami/kubectl:latest
            command:
            - /bin/sh
            - -c
            - |
                            # Scale all deployments in development to 0 replicas
              kubectl scale deployment --all --replicas=0 -n development
                            # This terminates all pods (and their EC2 nodes via Karpenter)
              echo "Dev cluster scaled down. Saving ~$200/night"
---
# Scale back UP at 8 AM
apiVersion: batch/v1
kind: CronJob
metadata:
  name: scale-up-dev
  namespace: development
spec:
  schedule: "30 2 * * 1-5"         # 8 AM IST = 02:30 UTC, Monday-Friday
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: scale-operator
          restartPolicy: OnFailure
          containers:
          - name: kubectl
            image: bitnami/kubectl:latest
            command: ["/bin/sh", "-c", "kubectl scale deployment --all --replicas=2 -n development"]

6.4 Tactic 3 — One ALB Ingress Instead of Many LoadBalancers

Every type: LoadBalancer Service creates an AWS Classic Load Balancer (~$18/month each). If you have 10 services, that's $180/month just for load balancers, plus data processing fees. Replace all of them with one AWS ALB Ingress controller — one ALB routes to all services based on path. Under $10/month total.

⚠️
Quick Win — Run This Right Now

Find all LoadBalancer services: kubectl get svc --all-namespaces | grep LoadBalancer. Count them. Each one is ~$18/month. Replace with ClusterIP + Ingress and see immediate savings.

6.5 Tactic 4 — Right-Size with VPA (Vertical Pod Autoscaler)

vpa-backend.yaml
YAML · Vertical Pod Autoscaler 
# VPA watches your pods' actual CPU + memory usage
# and recommends (or auto-applies) right-sized resource requests
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: backend-vpa
  namespace: production
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend-deployment
  updatePolicy:
    updateMode: "Off"               # "Off" = only show recommendations, don't auto-change
                                        # "Auto" = automatically resize pods (causes restarts)
                                        # Use "Off" first to understand recommendations

# After applying, check VPA recommendations:
# kubectl get vpa backend-vpa -o yaml
# Look for: status.recommendation.containerRecommendations
#   lowerBound: cpu: 180m, memory: 90Mi    ← minimum safe values
#   target:     cpu: 400m, memory: 200Mi   ← what VPA recommends
#   upperBound: cpu: 1200m, memory: 600Mi  ← ceiling
#
# If you set 1000m but VPA says 400m → you're wasting 600m CPU × every pod × every node!
