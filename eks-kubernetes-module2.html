Chapter 1 · Package Manager

Helm — The apt-get of Kubernetes

Stop copy-pasting YAMLs. Package, version, and install apps in seconds.
📖 The Problem Helm Solves

In Module 1, you wrote separate YAML files for your Deployment, Service, ConfigMap, Secret, HPA, and Ingress. That's 6+ files per service. ShopEasy has 3 services → 18+ files. And when you need a dev, staging, and production environment with slightly different values (different image tags, replica counts, domain names) — you'd need 54 files, mostly identical.

Helm solves this with templating + packaging. You write one set of templates with variables ({{ .Values.replicaCount }}), and a values.yaml file per environment. One command installs or upgrades the entire app. Helm also tracks history so you can rollback a whole release, not just one deployment.

1.1 Helm Core Concepts

📁
Chart
A folder of K8s YAML templates. Like a Docker image for your entire app stack. Can be shared on Artifact Hub.
⚙️
Values
A values.yaml file with default variable values. Override per environment without touching templates.
🚀
Release
A deployed instance of a Chart. Installing a chart creates a Release. You can have multiple releases of the same chart in different namespaces.
🗂️
Repository
A collection of Charts (like Docker Hub but for Helm). Use Artifact Hub, Bitnami, or your own ECR repo.

1.2 Helm Chart Directory Structure

shopeasy-backend/ (Helm Chart)
File Tree 
shopeasy-backend/               # Root folder = the Chart name
├── Chart.yaml                  # Chart metadata: name, version, description
├── values.yaml                 # DEFAULT values (overridden per environment)

1.5 Deployment Template — Helm Templating Syntax

templates/deployment.yaml
YAML · Helm Template 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "shopeasy-backend.fullname" . }}
    # "include" calls a named template from _helpers.tpl
    # "." passes the current context (chart + values) into it
  labels:
    {{- include "shopeasy-backend.labels" . | nindent 4 }}
        # "nindent 4" = add a newline then indent 4 spaces (YAML formatting)
        # The dash "-" in {{- trims whitespace BEFORE the tag
spec:
  {{- if not .Values.autoscaling.enabled }}
    # if autoscaling is OFF, hardcode replicas (otherwise HPA controls it)
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "shopeasy-backend.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "shopeasy-backend.selectorLabels" . | nindent 8 }}
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
                # CLEVER TRICK: When ConfigMap changes, annotation changes → pods restart automatically
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
                # Combines repo + tag: 123456.dkr.ecr.../backend:abc1234
        imagePullPolicy: {{ .Values.image.pullPolicy }}
        ports:
        - containerPort: {{ .Values.service.targetPort }}
        envFrom:
        - configMapRef:
            name: {{ include "shopeasy-backend.fullname" . }}-config
        resources:
          {{- toYaml .Values.resources | nindent 10 }}
                    # "toYaml" converts the Go struct to YAML string. "nindent 10" = 10 spaces indent
        livenessProbe:
          httpGet:
            path: {{ .Values.livenessProbe.path }}
            port: {{ .Values.service.targetPort }}
          initialDelaySeconds: {{ .Values.livenessProbe.initialDelaySeconds }}

Chapter 2 · Security

RBAC — Who Can Do What in Your Cluster

Lock down your EKS cluster so only the right people and services have the right permissions.
📖 The RBAC Story

ShopEasy now has 5 developers, 2 DevOps engineers, and an on-call ops team. By default in K8s, anyone with access to the cluster has full admin powers — they can delete namespaces, read secrets, exec into any pod. That's a disaster waiting to happen.

RBAC (Role-Based Access Control) solves this with a simple principle: give people only the permissions they absolutely need. A developer should be able to view logs and port-forward but NOT delete secrets. A CI/CD system should only be able to update images in its own namespace, nothing else.

2.1 RBAC — 4 Core Objects

📋
Role
A list of permissions within ONE namespace. E.g. "can get/list pods in the production namespace". Like a job description.
🌐
ClusterRole
Same as Role but cluster-wide (all namespaces). Use for cluster-level resources like nodes, PersistentVolumes.
🔗
RoleBinding
Attaches a Role to a User or ServiceAccount in ONE namespace. "Give Alice the developer role in production."
🌍
ClusterRoleBinding
Attaches a ClusterRole to a User/ServiceAccount across ALL namespaces. Reserved for cluster-admins.

2.2 Real Scenario — Developer Role

rbac-developer.yaml
YAML · Role + RoleBinding 
# ─────────────────────────────────────────────────────────────
# PART 1: Define WHAT a developer is allowed to do
# ─────────────────────────────────────────────────────────────
apiVersion: rbac.authorization.k8s.io/v1
kind: Role                           # Scoped to ONE namespace (production)
metadata:
  name: developer-role
  namespace: production
rules:                               # List of permissions (allow-list, no deny)

  # Permission set 1: Read pods and their logs
- apiGroups: [""]                   # "" = core API group (pods, services, configmaps)
  resources: ["pods", "pods/log"]  # WHAT resources
  verbs: ["get", "list", "watch"]  # WHAT actions: get=single, list=all, watch=stream

  # Permission set 2: Port-forward to pods (for local debugging)
- apiGroups: [""]
  resources: ["pods/portforward"]
  verbs: ["create"]                 # Port-forward = creating a tunnel (needs create)

  # Permission set 3: Read deployments and services (NOT modify)
- apiGroups: ["apps"]              # "apps" group = Deployments, StatefulSets, DaemonSets
  resources: ["deployments"]
  verbs: ["get", "list"]          # Can VIEW but NOT update/delete/create

  # ❌ Developers CANNOT: delete pods, read secrets, exec into pods
  # (anything not listed here is implicitly DENIED)

---
# ─────────────────────────────────────────────────────────────
# PART 2: GIVE the role to a specific person (Alice)
# ─────────────────────────────────────────────────────────────
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding                   # Bind role to a subject in this namespace
metadata:
  name: alice-developer-binding
  namespace: production
subjects:                           # WHO gets the role (can be multiple)
- kind: User                       # User = AWS IAM user (mapped via aws-auth ConfigMap)
  name: alice@shopeasy.com         # Must match the IAM username EXACTLY
  apiGroup: rbac.authorization.k8s.io
roleRef:                            # WHICH role to bind
  kind: Role
  name: developer-role             # Must match the Role name above
  apiGroup: rbac.authorization.k8s.io

2.3 ServiceAccount — Identity for Your Pods

Every Pod needs an identity too — for when it calls the K8s API (like an HPA, operator, or ArgoCD agent would). That identity is a ServiceAccount. By default, pods use the default ServiceAccount which has no permissions. Always create dedicated ServiceAccounts for apps.

ci-serviceaccount.yaml
YAML · ServiceAccount 
# ServiceAccount: Identity for our CI/CD pipeline
apiVersion: v1
kind: ServiceAccount
metadata:
  name: cicd-deployer              # Name pods/processes will use
  namespace: production

---
# Give the CI/CD deployer permission to update deployments only
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployment-updater
  namespace: production
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "patch", "update"]
    # patch = change specific fields (image tag). update = replace entire spec.

---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: cicd-binding
  namespace: production
subjects:
- kind: ServiceAccount             # Kind = ServiceAccount (not User)
  name: cicd-deployer             # The SA we created above
  namespace: production
roleRef:
  kind: Role
  name: deployment-updater
  apiGroup: rbac.authorization.k8s.io

Chapter 3 · Network Security

Network Policies — Firewalls Between Pods

By default ALL pods can talk to ALL pods. Lock it down.
📖 Why This Matters

In your EKS cluster, the frontend, backend, and database pods can freely talk to each other — even if they're in different namespaces. If an attacker compromises your frontend pod, they can directly hit your PostgreSQL database.

Network Policies are like firewall rules at the pod level. You declare: "Only the backend pod can talk to PostgreSQL on port 5432. Everyone else is blocked." This is called Zero Trust Networking and is mandatory for any production cluster.

netpol-database.yaml
YAML · NetworkPolicy 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: postgres-network-policy
  namespace: production

spec:
  podSelector:                      # WHICH pods does this policy apply to?
    matchLabels:
      app: postgres               # This policy protects pods with label app=postgres

  policyTypes:
  - Ingress                        # Control INCOMING traffic to postgres pods
  - Egress                         # Control OUTGOING traffic from postgres pods

  ingress:                          # WHO is allowed IN to postgres?
  - from:
    - podSelector:
        matchLabels:
          app: backend           # ONLY pods with app=backend can connect
                                    # Frontend pods: BLOCKED. Other namespaces: BLOCKED.
    ports:
    - protocol: TCP
      port: 5432                  # Only on PostgreSQL port (not 80, not 443)

  egress:                           # WHERE can postgres send traffic OUT?
  - ports:                         # Allow DNS resolution (CoreDNS on port 53)
    - protocol: UDP
      port: 53                    # Without this, DNS breaks and pod can't resolve names

---
# Default deny-all: Block ALL traffic in production namespace
# Apply FIRST, then whitelist what's needed
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}                   # {} = applies to ALL pods in namespace
  policyTypes:
  - Ingress
  - Egress
    # No "ingress" or "egress" rules = deny everything by default
⚠️
Requires CNI Support

Network Policies only work if your CNI plugin supports them. EKS uses AWS VPC CNI which does NOT enforce NetworkPolicies by default. You need to install Calico or enable the Network Policy controller addon: eksctl create addon --name vpc-cni --cluster shopeasy-cluster --configuration-values '{"enableNetworkPolicy":"true"}'

Chapter 4 · GitOps

ArgoCD — Your Cluster Continuously Mirrors Git

The most powerful deployment pattern: Git is the single source of truth. ArgoCD makes it real.
📖 The GitOps Revolution

In Module 1, CI/CD ran kubectl apply from GitHub Actions. That works — but it's push-based. The pipeline pushes changes to the cluster. Problems: if someone manually changes something in the cluster (drift), you won't know. If the pipeline breaks, nothing deploys.

GitOps flips this. ArgoCD runs inside your cluster and continuously watches your Git repo. When it detects that the cluster state differs from Git, it pulls the changes and syncs. Git becomes the single source of truth. Manual changes to the cluster are detected and overwritten. Every change is traceable, reviewable, and reversible via Git.

4.3 ArgoCD Application — Connect Git to EKS

argocd-app-shopeasy.yaml
YAML · ArgoCD Application 
apiVersion: argoproj.io/v1alpha1
kind: Application                   # ArgoCD custom resource — an "Application" to manage
metadata:
  name: shopeasy-backend
  namespace: argocd               # All ArgoCD resources live in argocd namespace
spec:
  project: default               # ArgoCD project (for grouping and RBAC)

  source:                          # WHERE to get the desired state from
    repoURL: https://github.com/yourorg/shopeasy-k8s
        # The Git repo containing your Helm charts or plain YAML manifests
    targetRevision: HEAD          # HEAD = latest commit on default branch
    path: backend/helm             # Folder inside the repo with the chart
    helm:                          # Helm-specific config
      releaseName: shopeasy-prod
      valueFiles:
      - values-production.yaml     # Use production values file
      parameters:                   # Dynamic overrides (image tag from CI)
      - name: image.tag
        value: abc1234             # CI updates this via: argocd app set ... --helm-set image.tag=newsha

  destination:                     # WHERE to deploy (which cluster + namespace)
    server: https://kubernetes.default.svc
        # "kubernetes.default.svc" = the cluster ArgoCD itself runs in (in-cluster)
    namespace: production

  syncPolicy:                      # HOW should ArgoCD sync changes
    automated:                     # Enable auto-sync (no manual click needed)
      prune: true                  # Delete K8s resources that are removed from Git
      selfHeal: true               # If someone manually changes cluster, auto-revert to Git state
    syncOptions:
    - CreateNamespace=true         # Auto-create namespace if it doesn't exist
    - PrunePropagationPolicy=foreground
    retry:                         # Retry if sync fails
      limit: 5                     # Try up to 5 times
      backoff:
        duration: 5s               # Wait 5s between retries
        factor: 2                  # Double wait each time (5s → 10s → 20s)

  revisionHistoryLimit: 10        # Keep last 10 sync histories (for rollback)
ArgoCD FieldWhat It DoesWhy It Matters
automated.prune: trueDeletes K8s resources removed from GitPrevents "zombie" resources cluttering your cluster
automated.selfHeal: trueReverts manual kubectl changesEnforces Git as the only valid way to change infra
targetRevision: HEADTracks latest commitCan also pin to a branch, tag, or specific commit SHA for stability
retry.backoffExponential backoff on failurePrevents thrashing when a deployment fails repeatedly
server: kubernetes.default.svcDeploy to the same cluster ArgoCD runs inFor multi-cluster, use the remote cluster's API URL + kubeconfig

Chapter 5 · Observability

Prometheus + Grafana — See Everything in Your Cluster

Metrics collection, dashboards, and alerting — all running inside K8s.
📖 Why You Need Observability

ShopEasy is live in production. At 2 AM, checkout starts failing. Without monitoring, you'd have no idea why — pods look healthy, no obvious errors. But Grafana shows CPU on the backend spiked to 100% at 1:47 AM. Prometheus shows the database connection pool was exhausted. You find the query with missing indexes and fix it in 10 minutes instead of 2 hours.

Prometheus scrapes metrics from every pod every 15 seconds. Grafana visualizes them in real-time dashboards. Alertmanager fires PagerDuty/Slack alerts when thresholds are crossed. The kube-prometheus-stack Helm chart installs ALL of these in one command.

5.2 Instrument Your App — Add /metrics Endpoint

backend/server.js (add metrics)
JavaScript · Node.js 
// Install: npm install prom-client
const client = require('prom-client');      // Prometheus client library for Node.js

// Create a Registry — container for all your metrics
const register = new client.Registry();

// Collect DEFAULT Node.js metrics (memory, CPU, GC, event loop lag)
client.collectDefaultMetrics({ register });   // This adds ~20 standard metrics automatically

// Create a CUSTOM metric: count HTTP requests by route + status code
const httpRequestCounter = new client.Counter({
  name: 'http_requests_total',             // Metric name (used in Prometheus queries)
  help: 'Total number of HTTP requests',    // Human description in Prometheus UI
  labelNames: ['method', 'route', 'status'], // Dimensions to slice data by
  register,                                  // Register with our registry
});

// Create a HISTOGRAM: measure API response times
const httpDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'route'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 3], // Measure latency buckets: 10ms, 50ms, 100ms...
  register,
});

// Expose /metrics endpoint — Prometheus scrapes this every 15 seconds
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', register.contentType); // Required content type for Prometheus
  res.end(await register.metrics());             // Returns all metrics in Prometheus text format
});

5.3 ServiceMonitor — Tell Prometheus to Scrape Your App

backend-servicemonitor.yaml
YAML · ServiceMonitor 
apiVersion: monitoring.coreos.com/v1        # API group from kube-prometheus-stack CRDs
kind: ServiceMonitor                        # Tells Prometheus: "scrape this service"
metadata:
  name: backend-monitor
  namespace: production
  labels:
    release: kube-prometheus-stack          # MUST match Prometheus selector label
spec:
  selector:                                  # Which K8s Service to monitor
    matchLabels:
      app: backend                          # Service with label app=backend
  endpoints:
  - port: http                             # Port name on the Service
    path: /metrics                         # Path to scrape (your Express endpoint)
    interval: 15s                          # Scrape every 15 seconds
    scrapeTimeout: 10s                     # Give up after 10s if no response

Chapter 6 · Stateful Apps

StatefulSets + EBS — Running PostgreSQL on EKS

Deployments are for stateless apps. Databases need StatefulSets + persistent storage.
📖 Stateful vs Stateless

Your Node.js backend is stateless — you can kill it and restart it on any node without data loss, because it stores nothing locally. But PostgreSQL is stateful — it stores data on disk. If you move it to a new node, the data must follow.

A Deployment gives each pod a random name (postgres-7d8b9-xxxxx). A StatefulSet gives stable, ordered names (postgres-0, postgres-1). Each pod gets its own PersistentVolumeClaim backed by an AWS EBS volume. Even when the pod is rescheduled to a different node, EBS re-attaches and the data is intact.

postgres-statefulset.yaml
YAML · StatefulSet + PVC 
# First: Create a StorageClass for EBS gp3 volumes
apiVersion: storage.k8s.io/v1
kind: StorageClass                    # Defines HOW to provision storage
metadata:
  name: ebs-gp3                       # Name used in PVC's storageClassName
provisioner: ebs.csi.aws.com         # AWS EBS CSI driver (installed in Module 1)
parameters:
  type: gp3                          # EBS volume type: gp3 is faster + cheaper than gp2
  encrypted: "true"                  # Encrypt data at rest (compliance requirement)
volumeBindingMode: WaitForFirstConsumer
  # Don't create EBS volume until a pod actually needs it (saves cost + ensures right AZ)
reclaimPolicy: Retain               # When PVC deleted: KEEP the EBS volume (don't delete data!)

---
apiVersion: apps/v1
kind: StatefulSet                    # NOT a Deployment — this is for stateful apps
metadata:
  name: postgres
  namespace: production
spec:
  serviceName: postgres-headless    # MUST reference a headless Service (for stable DNS)
  replicas: 1                        # 1 for standalone. 3 for HA (with Patroni/replication)
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:15-alpine    # Alpine = smaller image. :15 = major version only
        ports:
        - containerPort: 5432
        env:
        - name: POSTGRES_DB
          value: shopeasy
        - name: POSTGRES_USER
          valueFrom:
            secretKeyRef:             # Pull specific key from Secret (not entire Secret)
              name: postgres-secret
              key: POSTGRES_USER
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: postgres-secret
              key: POSTGRES_PASSWORD
        volumeMounts:                 # WHERE inside the container to mount the volume
        - name: postgres-data
          mountPath: /var/lib/postgresql/data
                    # PostgreSQL stores all its data here. This maps to EBS volume.
        resources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "2Gi"
            cpu: "2000m"

  volumeClaimTemplates:             # KEY DIFFERENCE: StatefulSet creates PVC per pod
  - metadata:
      name: postgres-data           # pod 0 gets: postgres-data-postgres-0
                                     # pod 1 gets: postgres-data-postgres-1 (different EBS!)
    spec:
      accessModes: ["ReadWriteOnce"] # Only ONE pod/node can mount at a time (EBS limitation)
      storageClassName: ebs-gp3    # Use our StorageClass above
      resources:
        requests:
          storage: 50Gi           # Provision a 50GB EBS gp3 volume

Chapter 7 · AWS Security

IRSA — Pods Get AWS Permissions Without Keys

IAM Roles for Service Accounts: the most secure way to grant AWS access to pods.
📖 The Problem IRSA Solves

Your backend pod needs to upload files to S3. The old (bad) way: put AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY into a K8s Secret. Problems: the keys can leak, they don't expire, you have to rotate them manually, and they give access to your entire AWS account.

IRSA (IAM Roles for Service Accounts) is the modern approach. A Pod's ServiceAccount is linked to an IAM Role via OIDC (Open ID Connect). When the pod calls s3.putObject(), AWS SDK automatically gets temporary credentials from the EKS OIDC provider. The credentials expire every hour, are scoped to exactly what the role allows, and there's zero key management.

IRSA Token Flow
📦 Pod
Needs S3 access
→
🎫 K8s OIDC
Issues JWT token
→
🔑 AWS STS
Validates token
→
⏱️ Temp Creds
1 hour, scoped
↓
☁️ S3 / DynamoDB / Secrets Manager
Only what the IAM Role allows

Lab 7 — Set Up IRSA for S3 Access
5 steps from zero to passwordless AWS access
# STEP 1: Enable OIDC provider on your EKS cluster $ eksctl utils associate-iam-oidc-provider \
  --region ap-south-1 \
  --cluster shopeasy-cluster \
  --approve
# [✔] associated IAM OIDC provider for cluster...
# STEP 2: Create IAM policy for S3 access $ cat > s3-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
    "Resource": "arn:aws:s3:::shopeasy-uploads/*"
  }]
}
EOF
$ aws iam create-policy --policy-name shopeasy-s3-policy --policy-document file://s3-policy.json
# STEP 3: Create IAM Role + ServiceAccount in ONE eksctl command $ eksctl create iamserviceaccount \
  --name backend-s3-sa \
  --namespace production \
  --cluster shopeasy-cluster \
  --region ap-south-1 \
  --attach-policy-arn arn:aws:iam::123456789:policy/shopeasy-s3-policy \
  --approve \
  --override-existing-serviceaccounts

# This creates: IAM Role + K8s ServiceAccount with annotation $ kubectl describe sa backend-s3-sa -n production
# Annotations: eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/...
# STEP 4: Use the ServiceAccount in your Deployment # Add this to your deployment spec.template.spec: # serviceAccountName: backend-s3-sa

# STEP 5: In your Node.js code — NO KEYS NEEDED! # const s3 = new AWS.S3(); ← SDK auto-gets creds via IRSA token # s3.putObject({ Bucket: 'shopeasy-uploads', ... }) ← just works!

IRSA Also Works For…

Any AWS SDK call: DynamoDB, SQS, SNS, Secrets Manager, SSM Parameter Store, ECR, CloudWatch. Use separate ServiceAccounts with minimal IAM roles for each microservice. The backend gets S3 + SQS. The frontend gets nothing. The cronjob gets only SES for emails. Principle of least privilege.
