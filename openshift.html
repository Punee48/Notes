Deep Dive
OpenShift Architecture
📖 Story: The City Analogy

Think of OpenShift as a well-planned city. The Control Plane is the City Hall — it makes all decisions. Worker Nodes are districts where actual work happens. Pods are offices inside buildings. Services are street addresses. Routes are the highway exits that connect the city to the outside world.

Control Plane Components

🧠
API Server (kube-apiserver)
The brain. Every oc/kubectl command talks to this. It validates, stores, and distributes all cluster state changes. It is the ONLY component that reads/writes to etcd.
📚
etcd
The memory. A distributed key-value store that holds the entire cluster state. If etcd is healthy, your cluster can recover from anything. Back this up daily in production!
🎯
Scheduler
The placement engine. When a Pod needs to run, Scheduler picks the best worker node based on: available CPU/memory, affinity rules, taints/tolerations, and topology spread.
🔄
Controller Manager
The autopilot. Runs control loops: "Is desired state = actual state?" If you want 5 replicas and only 3 are running, it creates 2 more. Handles Deployments, ReplicaSets, Jobs, etc.
🤖
kubelet
The on-node agent. Runs on every worker. Takes instructions from API Server and manages pod lifecycle on that node. Reports node health back.
🌐
kube-proxy
The network traffic manager. Maintains iptables/ipvs rules on each node so that Service virtual IPs route traffic to the right pod endpoints.

OpenShift-Specific Components

🔑
OAuth Server
Built-in identity provider. Supports HTPasswd, LDAP, GitHub, Google SSO. Handles all authentication for web console and CLI.
🖼️
Image Registry
Internal Docker/OCI registry. Stores built images from S2I/Tekton. Can be backed by object storage (S3, GCS). Integrates with Quay for enterprise.
🛣️
HAProxy Router
The ingress controller. Manages Routes. Automatically provisions TLS, sticky sessions, rate limiting. Runs as pods that watch Route objects.
📦
Operator Framework
Automated Day-2 operations. Operators are controllers for complex stateful apps (databases, Kafka, etc.) that know how to install, upgrade, back up, and heal themselves.

How a Pod Gets Created — The Full Flow

You run: oc apply -f deployment.yaml
The oc CLI sends an HTTP POST request to the API Server with your YAML decoded to JSON.
API Server Validates & Persists
API Server validates schema, applies admission webhooks (security checks, mutating defaults), then writes the Deployment object to etcd.
Deployment Controller Reacts
Controller Manager detects new Deployment → creates a ReplicaSet → ReplicaSet creates Pod objects in etcd (status: Pending).
Scheduler Assigns a Node
Scheduler sees unscheduled Pods → runs filtering (which nodes have resources?) → runs scoring (which node is best?) → binds Pod to a Node by writing nodeName to etcd.
kubelet Pulls & Starts Container
kubelet on chosen node sees Pod assigned to it → pulls container image → calls CRI (containerd/cri-o) → container starts → kubelet updates Pod status to Running.
Ready!
Pod is running. kube-proxy updates iptables. If Service exists, traffic can now reach your pod. Route (if exists) starts receiving external traffic.

Projects & Namespaces
📖 Story: The Office Building

Imagine a large office building with multiple companies. Each company rents their own floor. They have their own rooms, keys, and security guards. They can't walk into another company's floor without permission. In OpenShift, a Project (or Namespace) is that floor. It's your isolated workspace.

Project vs Namespace — What's the Difference?

A Namespace is a pure Kubernetes concept — a logical partition in the cluster. An OpenShift Project wraps a namespace and adds extra metadata, access controls, and display name. When you create a Project in OpenShift, it automatically creates a Namespace underneath.

Project Resource Quotas — Protect the Cluster

In production, every project gets a ResourceQuota — a maximum budget for CPU, memory, and object counts. This prevents one noisy team from hogging all cluster resources.

YAML
shopease-quota.yaml 
apiVersion: v1
kind: ResourceQuota            # What type of object this is
metadata:
  name: shopease-quota          # Name of this quota object
  namespace: shopease-dev      # Which project this applies to
spec:
  hard:                           # "hard" = absolute maximum limits
    pods: "20"                   # Max 20 pods in this project
    requests.cpu: "4"           # Total guaranteed CPU = 4 cores
    requests.memory: 8Gi       # Total guaranteed RAM = 8 GiB
    limits.cpu: "8"             # Max burst CPU = 8 cores
    limits.memory: 16Gi        # Max burst RAM = 16 GiB
    persistentvolumeclaims: "10" # Max 10 storage volumes
    services: "10"              # Max 10 services
    secrets: "30"               # Max 30 secrets
    configmaps: "20"            # Max 20 configmaps
🔍 Word-by-Word Explanation: ResourceQuota
apiVersion: v1apiVersion tells OpenShift which API group handles this resource. v1 means it's a core Kubernetes resource (stable, no prefix needed).
kind: ResourceQuotakind is the type of object. ResourceQuota enforces maximum resource consumption within a namespace.
metadata.nameThe unique identifier of this quota object within the namespace. You reference it by this name.
metadata.namespaceWhich project/namespace this quota governs. Every quota is scoped to one namespace.
spec.hardhard limits are enforced strictly. If you try to create a pod that would exceed the quota, the API Server rejects it immediately with a 403 error.
requests.cpu: "4"requests = the guaranteed, reserved amount. The cluster Scheduler uses this to place pods. "4" = 4 CPU cores total guaranteed across all pods in this project.
limits.cpu: "8"limits = the maximum burst. A pod can use more CPU temporarily (up to its individual limit) but total across project cannot exceed 8 cores.
8Gi / 16GiGi = Gibibytes (1 GiB = 1024³ bytes). OpenShift uses binary prefixes (Ki, Mi, Gi) not decimal (KB, MB, GB).

LimitRange — Default Resource Allocation

YAML
shopease-limitrange.yaml 
apiVersion: v1
kind: LimitRange               # Sets defaults + min/max per container
metadata:
  name: shopease-limits
  namespace: shopease-dev
spec:
  limits:
  - type: Container             # Apply these rules to every Container
    default:                     # Default LIMITS (if container doesn't specify)
      cpu: 500m                 # 500m = 0.5 CPU cores (m = millicores)
      memory: 512Mi            # 512 MiB default limit
    defaultRequest:             # Default REQUESTS (if container doesn't specify)
      cpu: 100m                 # 100m = 0.1 CPU core guaranteed
      memory: 128Mi            # 128 MiB guaranteed RAM
    min:                         # Minimum any container MUST request
      cpu: 50m
      memory: 64Mi
    max:                         # Maximum any single container can have
      cpu: 2                    # No container can get more than 2 cores
      memory: 4Gi

Pods & Containers
📖 Story: The Shipping Container

A Container is like a shipping container. It holds your application and everything it needs (code, runtime, libraries) — packed tightly, isolated from others. A Pod is like a ship's cargo hold — it can carry one or more containers that share the same network and storage space. They travel together, land together, and live or die together.

Anatomy of a Pod

YAML
shopease-pod.yaml 
apiVersion: v1
kind: Pod                        # This is a Pod resource
metadata:
  name: shopease-product-pod    # Unique name in this namespace
  namespace: shopease-dev
  labels:                        # Key-value tags — used for grouping/selection
    app: shopease              # app label = "shopease"
    tier: backend             # tier label = "backend"
    version: "1.0"            # version label = "1.0"
spec:                            # The desired state of this Pod
  containers:                  # List of containers in this pod
  - name: product-service     # Container name (for logs, exec)
    image: quay.io/shopease/product-service:1.0  # Docker image to run
    ports:
    - containerPort: 8080     # Port inside the container (informational)
      protocol: TCP
    env:                       # Environment variables injected into container
    - name: DB_HOST           # Variable name
      value: "postgres-svc"  # Variable value
    - name: DB_PORT
      value: "5432"
    resources:                 # CPU & Memory boundaries
      requests:               # Guaranteed minimum (for scheduling)
        cpu: 200m            # 200 millicores = 0.2 CPU core
        memory: 256Mi       # 256 MiB RAM minimum
      limits:                 # Hard maximum (container killed if exceeded)
        cpu: 500m
        memory: 512Mi
  - name: sidecar-logger      # SECOND container — sidecar pattern
    image: fluent/fluent-bit:2.1
    resources:
      requests: { cpu: 50m, memory: 64Mi }
      limits:   { cpu: 100m, memory: 128Mi }
🔍 Word-by-Word Explanation: Pod Spec
kind: PodYou're defining the smallest deployable unit. A Pod runs one or more tightly-coupled containers that must run together on the same node.
metadata.labelsLabels are arbitrary key-value pairs. They have no meaning to Kubernetes by themselves, but Services, Deployments, and other objects use them to select pods (like a filter).
spec.containersA YAML list (notice the - dash). Each item is one container definition. All containers in a pod share the same network namespace (same IP, same localhost) and can share volumes.
image: quay.io/...The container image to pull. Format: registry/repository:tag. OpenShift by default blocks root-run images for security (unlike vanilla Kubernetes).
containerPort: 8080Tells OpenShift which port your app listens on. This is informational only — it doesn't open a firewall rule. Traffic routing is handled by Services.
envEnvironment variables passed to the container at startup. The running process can read these with System.getenv("DB_HOST") in Java, os.environ["DB_HOST"] in Python, etc.
resources.requestsThe Scheduler uses requests to find a node with enough free capacity. The node reserves this amount for your container. Always set this — without it, your pod competes for resources blindly.
resources.limitsHard ceiling. If the container tries to use more CPU than limit, it gets throttled. If it exceeds memory limit, the kernel kills it with OOMKilled. This protects other pods on the same node.
200m CPUm = millicores. 1000m = 1 full CPU core. So 200m = 20% of one core, 500m = half a core, 2 = 2 full cores. Modern servers have 32-128 cores.
sidecar-loggerThe Sidecar Pattern: a helper container that runs alongside your main app container. Here Fluent Bit collects logs from the main container. Both share the same pod filesystem via volumeMounts.

Pod Lifecycle States

Pending
Pod accepted by cluster, but container(s) not yet started. Scheduler looking for a node, or image being pulled. Can be stuck here if no node has enough resources.
Running
At least one container is running. Pod is bound to a node. Note: Running doesn't mean your app is ready — it might still be initializing.
Succeeded
All containers have exited with code 0. Seen in Jobs/CronJobs where completion is expected.
Failed
At least one container exited with non-zero code and won't restart. Check logs: oc logs <pod> --previous
CrashLoopBackOff
Container keeps crashing and restarting. OpenShift adds exponential backoff delay between restarts. Check logs immediately. Common causes: bad config, missing env var, wrong image.

Core Concept · Basic
Deployments & ReplicaSets
📖 Story: The Factory Manager

A Deployment is like a factory manager. You tell them: "I need exactly 5 workers assembling product boxes at all times." If a worker gets sick, the manager hires a new one. If you want a raise in wages (new app version), the manager gradually replaces workers one by one with the new contract — so production never stops. That's a Rolling Update.

Deployment vs DeploymentConfig

OpenShift historically had its own DeploymentConfig (DC) resource. Red Hat now recommends using the standard Kubernetes Deployment resource. We'll use Deployments throughout this guide.

YAML
product-deployment.yaml 
apiVersion: apps/v1               # Deployment lives in apps/v1 API group
kind: Deployment
metadata:
  name: product-service
  namespace: shopease-dev
  labels:
    app: product-service
    version: v1
  annotations:
    deployment.kubernetes.io/revision: "1"
spec:
  replicas: 3                      # Run 3 identical pod instances
  selector:                        # Which pods does THIS deployment manage?
    matchLabels:                 # Pods must have ALL these labels
      app: product-service
  strategy:                        # How to update pods when image changes
    type: RollingUpdate           # Gradually replace old pods with new
    rollingUpdate:
      maxSurge: 1               # Allow 1 extra pod during update (so 4 total briefly)
      maxUnavailable: 0         # Never reduce below 3 — zero downtime!
  template:                        # Blueprint for each pod (this IS a pod spec)
    metadata:
      labels:                    # Pod labels MUST match selector.matchLabels
        app: product-service
        version: v1
    spec:
      terminationGracePeriodSeconds: 30  # Give app 30s to finish requests on shutdown
      containers:
      - name: product-service
        image: quay.io/shopease/product-service:1.0
        imagePullPolicy: Always    # Always pull latest from registry
        ports:
        - containerPort: 8080
        env:
        - name: SPRING_PROFILES_ACTIVE
          value: production
        resources:
          requests: { cpu: 200m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }
        readinessProbe:            # Is the pod ready to receive traffic?
          httpGet:
            path: /actuator/health/readiness
            port: 8080
          initialDelaySeconds: 20  # Wait 20s before first check (app startup)
          periodSeconds: 10       # Check every 10 seconds
          failureThreshold: 3     # Mark unready after 3 consecutive failures
        livenessProbe:             # Is the pod alive? (restart if not)
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 15
          failureThreshold: 3
🔍 Rolling Update Deep Dive
replicas: 3The ReplicaSet controller ensures exactly 3 pods matching the selector are always running. If you delete one manually, it creates a new one within seconds.
selector.matchLabelsCritical — this is the "glue" between Deployment and its Pods. The Deployment only manages pods that have all these labels. Never have two Deployments with the same matchLabels in the same namespace.
strategy: RollingUpdateDuring an update, OpenShift replaces pods gradually. The alternative is Recreate (kill all, start all — causes downtime). RollingUpdate gives zero-downtime upgrades.
maxSurge: 1During rolling update, temporarily allow 1 extra pod. So with replicas:3, we briefly have 4 pods. New pods start, pass readiness, then old pods terminate.
maxUnavailable: 0Zero pods can be unavailable during update. Combined with maxSurge:1, this guarantees that at all times you have at least 3 working pods serving traffic.
terminationGracePeriod: 30When a pod is marked for deletion, OpenShift stops sending it new requests, then waits 30 seconds for in-flight requests to complete before force-killing. Critical for zero-downtime.
imagePullPolicy: AlwaysForce-pulls the image on every pod start. Use this in dev/staging. In prod, use specific image tags (not :latest) and IfNotPresent to avoid surprises and speed up startup.

bash
$ # Apply the deployment

Services & Routes
📖 Story: The Reception Desk

Pods have their own IP addresses, but pods die and get replaced constantly — their IPs change. A Service is like a company's reception desk — it has a stable phone number (ClusterIP). No matter which employee (pod) answers, the number stays the same. A Route is the company's public address — it opens a door from the outside internet to the reception desk.

Service Types

🔒
ClusterIP (Default)
Internal-only virtual IP. Only accessible from within the cluster. Used for pod-to-pod communication. e.g., product-service calling database-service.
🚪
NodePort
Exposes service on a static port (30000-32767) on every node's IP. Rarely used in OpenShift — use Routes instead. Useful for non-HTTP protocols.
⚖️
LoadBalancer
Provisions a cloud load balancer (AWS ELB, Azure LB). Expensive for many services. In OpenShift, prefer Routes for HTTP/S traffic.
🛣️
Route (OpenShift)
OpenShift-specific. Provides external HTTP/HTTPS access with auto-TLS, custom hostnames, sticky sessions, and path-based routing. The preferred way to expose apps.
YAML
product-service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: product-svc              # DNS name: product-svc.shopease-dev.svc.cluster.local
  namespace: shopease-dev
  labels:
    app: product-service
spec:
  type: ClusterIP               # Internal only (default)
  selector:                     # Select pods that have these labels
    app: product-service       # Routes traffic to pods with app=product-service
  ports:
  - name: http                 # Port name (useful for Istio/service mesh)
    port: 80                   # Service listens on port 80 (inside cluster)
    targetPort: 8080           # Forwards to container port 8080
    protocol: TCP
  - name: metrics
    port: 9090
    targetPort: 9090           # Prometheus scrape port

---
apiVersion: route.openshift.io/v1  # OpenShift-specific API group
kind: Route
metadata:
  name: product-route
  namespace: shopease-dev
  annotations:
    haproxy.router.openshift.io/timeout: 60s        # HAProxy request timeout
    haproxy.router.openshift.io/balance: roundrobin # Load balancing algorithm
spec:
  host: products.shopease.apps.cluster.example.com  # Custom hostname
  path: /api/products           # Only route /api/products traffic here
  to:
    kind: Service
    name: product-svc          # Forward to the product-svc Service
    weight: 100                # 100% of traffic (used for A/B testing if <100)
  port:
    targetPort: http           # Use the "http" named port from Service
  tls:                          # TLS configuration
    termination: edge          # TLS terminates at the router (not in pod)
    insecureEdgeTerminationPolicy: Redirect  # Redirect HTTP → HTTPS
🔍 Service DNS Resolution
DNS Full NameOpenShift CoreDNS auto-creates: <service>.<namespace>.svc.cluster.local. A pod in ANY namespace can reach product-svc via this full name.
Short nameWithin the same namespace, just use product-svc. CoreDNS adds the namespace suffix automatically.
selectorThe Service continuously watches for pods matching these labels. As pods come and go (rolling update, crashes), the Service's endpoint list updates dynamically. kube-proxy keeps iptables in sync.
port vs targetPortport = what other services call (e.g., port 80 — nice and clean). targetPort = what the container actually listens on (e.g., 8080 — your app's config). This lets you change your app's internal port without telling every caller.
tls.termination: edgeTLS is terminated at the HAProxy router. Traffic between router and pod is plain HTTP (inside the cluster, usually safe). Alternatives: passthrough (TLS goes all the way to pod), reencrypt (TLS re-encrypted between router and pod).
insecureEdgeTerminationPolicy: RedirectAny plain HTTP request to this Route automatically gets 301-redirected to HTTPS. Never allow plain-text traffic in production.

ConfigMaps & Secrets
📖 Story: The Notice Board vs Safe

Your application needs two types of information. Non-sensitive config (server port, feature flags, log level) goes on the office notice board — that's a ConfigMap. Sensitive data (database passwords, API keys, TLS certificates) goes in the safe — that's a Secret. OpenShift treats them differently in terms of access control and encryption.

YAML
shopease-configmap.yaml 
apiVersion: v1
kind: ConfigMap
metadata:
  name: product-config
  namespace: shopease-dev
data:                              # Key-value pairs (all plain text)
  SERVER_PORT: "8080"
  LOG_LEVEL: "INFO"
  CACHE_TTL_SECONDS: "300"
  FEATURE_NEW_CHECKOUT: "true"   # Feature flag
  application.properties: |      # MULTI-LINE value (entire config file!)
    server.port=8080
    spring.datasource.url=jdbc:postgresql://postgres-svc:5432/shopdb
    spring.jpa.hibernate.ddl-auto=validate
    cache.ttl=300
    logging.level.com.shopease=INFO

---
apiVersion: v1
kind: Secret
metadata:
  name: product-secrets
  namespace: shopease-dev
type: Opaque                       # Generic secret type. Others: kubernetes.io/tls, dockerconfigjson
stringData:                        # Use stringData (plain text → auto base64 encoded)
  DB_PASSWORD: "Sup3rS3cur3P@ss!"  # NEVER hardcode in code. Only in Secrets!
  DB_USERNAME: "shopease_user"
  JWT_SECRET: "my-jwt-signing-key-256-bit"
  STRIPE_API_KEY: "sk_live_xxxxxxxxxxxx"

# NOTE: In production, use Vault/ExternalSecrets instead of raw Secrets!

Consuming ConfigMaps & Secrets in Pods

YAML (in Deployment spec)
deployment-with-config.yaml (containers section) 
      containers:
      - name: product-service
        image: quay.io/shopease/product-service:1.0

        # ── METHOD 1: Inject specific keys as env vars ──
        env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:         # Get value from a ConfigMap key
              name: product-config    # ConfigMap name
              key: LOG_LEVEL          # Which key to read
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:            # Get value from a Secret key
              name: product-secrets
              key: DB_PASSWORD

        # ── METHOD 2: Inject ALL keys from ConfigMap as env vars ──
        envFrom:
        - configMapRef:
            name: product-config     # All keys become env variables
        - secretRef:
            name: product-secrets   # All secret keys become env variables

        # ── METHOD 3: Mount as files (best for config files) ──
        volumeMounts:
        - name: config-volume
          mountPath: /app/config   # Mount here inside container
          readOnly: true
        - name: secret-volume
          mountPath: /app/secrets
          readOnly: true
      volumes:
      - name: config-volume
        configMap:
          name: product-config      # Each key = file, value = file content
      - name: secret-volume
        secret:
          secretName: product-secrets
          defaultMode: 0400        # File permissions (read-only by owner)
⚠️

Production Secret Management: OpenShift Secrets are base64 encoded (NOT encrypted at rest by default). For production, use HashiCorp Vault with the Vault Agent Injector, or Bitnami Sealed Secrets, or ExternalSecrets Operator with AWS Secrets Manager / Azure Key Vault. Enable etcd encryption at rest in your cluster.

Persistent Storage
📖 Story: The Filing Cabinet

Containers are stateless by design — when a container restarts, all its data vanishes. That's like writing notes on a whiteboard: crash = erase. But databases need data that survives crashes. A PersistentVolume (PV) is like a filing cabinet — durable storage. A PersistentVolumeClaim (PVC) is your request for a cabinet of a certain size. The StorageClass is the vendor (AWS EBS, Azure Disk, NFS, etc.).

YAML
postgres-storage.yaml 
# ── PersistentVolumeClaim — Request for storage ──
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
  namespace: shopease-dev
spec:
  accessModes:
    - ReadWriteOnce               # One node can mount read-write at a time
  storageClassName: gp3-csi    # StorageClass (gp3-csi = AWS EBS gp3 via CSI)
  resources:
    requests:
      storage: 50Gi            # Request 50 GiB of storage

---
# ── StatefulSet for PostgreSQL ──
apiVersion: apps/v1
kind: StatefulSet                # For stateful apps (databases, queues)
metadata:
  name: postgres
  namespace: shopease-dev
spec:
  serviceName: postgres-svc     # Headless service for stable DNS
  replicas: 1                    # Start with 1 (add replicas for HA)
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
      - name: postgres
        image: postgres:15-alpine
        env:
        - name: POSTGRES_DB
          value: shopdb
        - name: POSTGRES_USER
          valueFrom:
            secretKeyRef: { name: product-secrets, key: DB_USERNAME }
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef: { name: product-secrets, key: DB_PASSWORD }
        ports:
        - containerPort: 5432
        volumeMounts:
        - name: postgres-data
          mountPath: /var/lib/postgresql/data  # PostgreSQL data directory
        resources:
          requests: { cpu: 500m, memory: 512Mi }
          limits:   { cpu: 2, memory: 2Gi }
  volumeClaimTemplates:           # StatefulSet creates one PVC per replica automatically
  - metadata:
      name: postgres-data
    spec:
      accessModes: [ ReadWriteOnce ]
      storageClassName: gp3-csi
      resources:
        requests: { storage: 50Gi }
🔍 StatefulSet vs Deployment
StatefulSetUsed for stateful apps (PostgreSQL, Kafka, Redis cluster). Provides: stable network identity (postgres-0, postgres-1), ordered startup/shutdown (postgres-0 before postgres-1), and per-replica PVCs that survive pod restarts.
DeploymentUsed for stateless apps. Pods are interchangeable. Scales up/down freely. Pod names are random (product-service-abc12).
ReadWriteOnceOnly one node can mount this volume read-write simultaneously. Good for databases. Compare: ReadWriteMany (NFS — multiple nodes can mount), ReadOnlyMany (shared read-only config).
volumeClaimTemplatesStatefulSet creates a unique PVC for each replica automatically. postgres-0 gets postgres-data-postgres-0, postgres-1 gets postgres-data-postgres-1. When postgres-1 pod dies, its new replacement binds to the SAME PVC — data preserved!

Health Checks & Resource Limits
📖 Story: The HR Department & Security Guard

The Liveness Probe is the HR doctor — they check: "Is this employee even alive?" If not, HR fires them (restarts the pod). The Readiness Probe is the security guard at the front desk — they check: "Is this employee ready to take customer calls?" Until ready, no calls are forwarded (removed from Service endpoints). The Startup Probe is the onboarding period — "Give the new hire extra time before we start judging."

YAML
health-probes.yaml (inside container spec) 
        # ── STARTUP PROBE: Give app time to initialize ──
        startupProbe:
          httpGet:
            path: /actuator/health  # Spring Boot health endpoint
            port: 8080
          failureThreshold: 30     # Allow 30 * 10s = 5 minutes to start
          periodSeconds: 10       # Check every 10 seconds
          # startupProbe disables liveness until it passes!

        # ── READINESS PROBE: Ready for traffic? ──
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 8080
            httpHeaders:            # Optional: custom headers for auth
            - name: Accept
              value: application/json
          initialDelaySeconds: 5  # Wait 5s after startup probe passes
          periodSeconds: 10
          successThreshold: 1     # 1 success = ready
          failureThreshold: 3     # 3 failures = remove from service
          timeoutSeconds: 5      # Give endpoint 5s to respond

        # ── LIVENESS PROBE: Is app still healthy? ──
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 20
          failureThreshold: 3     # 3 * 20s = after 60s of being sick, restart

        # ── EXEC probe alternative (for non-HTTP apps) ──
        # livenessProbe:
        #   exec:
        #     command: ["redis-cli", "ping"]  # Returns "PONG" if Redis is alive

        # ── TCP probe alternative (for TCP-only services) ──
        # livenessProbe:
        #   tcpSocket:
        #     port: 5432  # Just check TCP port is open
✅

CI/CD with OpenShift Pipelines (Tekton)
📖 Story: The Assembly Line

Imagine a car factory assembly line. Station 1 welds the frame. Station 2 installs the engine. Station 3 paints. Station 4 does quality checks. Station 5 ships. Each station is independent but chained. That's Tekton. Each Task does one thing. A Pipeline chains them in order. A PipelineRun is one run of the entire assembly line for a specific code commit.

Tekton Concepts

📋
Task
A single unit of work. Runs as a pod. Contains one or more Steps (sequential commands). Reusable across Pipelines. e.g., "Run unit tests", "Build image", "Push to registry".
🔗
Pipeline
A DAG (directed acyclic graph) of Tasks. Defines order, dependencies, parallel execution, and how data flows between tasks via Workspaces.
▶️
PipelineRun
An instance of a Pipeline execution. Created when a webhook fires (on git push) or manually with tkn CLI. Contains the run history and logs.
📁
Workspace
Shared storage between tasks in a pipeline. Tasks read/write files via workspaces (PVC, emptyDir, Secret, ConfigMap). Like shared /tmp between pipeline stages.
YAML — Full CI/CD Pipeline
shopease-pipeline.yaml 
apiVersion: tekton.dev/v1beta1
kind: Pipeline
metadata:
  name: shopease-cicd-pipeline
  namespace: shopease-dev
spec:
  params:                          # Input parameters for this pipeline
  - name: GIT_REPO
    type: string
    description: Source Git repository URL
  - name: GIT_REVISION
    type: string
    default: main
  - name: IMAGE_NAME
    type: string
    description: Target image name with registry

  workspaces:                      # Shared storage declarations
  - name: source                 # Source code workspace
  - name: maven-cache           # Maven dependency cache (speeds up builds!)
  - name: registry-credentials  # Docker registry push secret

  tasks:                           # Pipeline stages (Tasks)

  # ── STAGE 1: Clone source code ──
  - name: clone-source
    taskRef:
      name: git-clone            # ClusterTask from Tekton Hub
      kind: ClusterTask
    params:
    - name: url
      value: $(params.GIT_REPO) # $(params.X) = reference to pipeline param
    - name: revision
      value: $(params.GIT_REVISION)
    workspaces:
    - name: output
      workspace: source

  # ── STAGE 2: Run unit tests ──
  - name: run-tests
    taskRef:
      name: maven
      kind: ClusterTask
    runAfter: [clone-source]    # Wait for stage 1 to complete
    params:
    - name: GOALS
      value: [test]             # mvn test
    workspaces:
    - name: source
      workspace: source
    - name: maven-settings
      workspace: maven-cache

  # ── STAGE 3: SonarQube code quality scan ──
  - name: code-quality-scan
    taskRef:
      name: sonarqube-scanner
    runAfter: [run-tests]
    params:
    - name: SONAR_HOST_URL
      value: http://sonarqube-svc:9000
    - name: SONAR_PROJECT_KEY
      value: shopease-product-service
    workspaces:
    - name: source
      workspace: source

  # ── STAGE 4: Build & push container image ──
  - name: build-push-image
    taskRef:
      name: buildah               # Buildah = rootless container image builder
      kind: ClusterTask
    runAfter: [code-quality-scan]
    params:
    - name: IMAGE
      value: $(params.IMAGE_NAME):$(tasks.clone-source.results.commit)
    - name: DOCKERFILE
      value: ./Dockerfile
    - name: CONTEXT
      value: .
    workspaces:
    - name: source
      workspace: source
    - name: dockerconfig
      workspace: registry-credentials

  # ── STAGE 5: Deploy to dev environment ──
  - name: deploy-to-dev
    taskRef:
      name: openshift-client      # Runs oc commands
      kind: ClusterTask
    runAfter: [build-push-image]
    params:
    - name: SCRIPT
      value: |
        oc set image deployment/product-service \
          product-service=$(params.IMAGE_NAME):$(tasks.clone-source.results.commit) \
          -n shopease-dev
        oc rollout status deployment/product-service -n shopease-dev

Networking & Security Policies
📖 Story: The Firewall Rules

By default, all pods in OpenShift can talk to all other pods — like an open office floor where everyone can talk to everyone. NetworkPolicies are your firewall rules. You can say: "Only the API gateway pod can talk to the product-service. Nobody else." This is zero-trust networking — deny all by default, whitelist explicitly.

YAML
network-policies.yaml 
# ── Policy 1: Deny ALL ingress by default ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: shopease-dev
spec:
  podSelector: {}               # {} = applies to ALL pods in namespace
  policyTypes:
  - Ingress                      # Block all incoming traffic (no ingress rules = deny all)

---
# ── Policy 2: Allow only API-gateway → product-service ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-apigateway-to-product
  namespace: shopease-dev
spec:
  podSelector:
    matchLabels:
      app: product-service       # This policy protects product-service pods
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api-gateway       # Only from api-gateway pods
    - namespaceSelector:
        matchLabels:
          name: shopease-dev    # Only from shopease-dev namespace
    ports:
    - protocol: TCP
      port: 8080

---
# ── Policy 3: Allow Prometheus scraping (monitoring namespace) ──
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-prometheus-scrape
  namespace: shopease-dev
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          openshift.io/cluster-monitoring: "true"  # Prometheus namespace
    ports:
    - protocol: TCP
      port: 9090                # Metrics port

RBAC — Role-Based Access Control
📖 Story: The Office Badge System

In a big company, the janitor has a badge that opens the supply closet. The developer has a badge for the code lab. The manager has a badge for everything. Nobody accidentally has access to the server room unless explicitly given. OpenShift RBAC works exactly like this: Roles define what a badge can open. RoleBindings assign a badge to a person or service account.

YAML
shopease-rbac.yaml 
# ── Developer Role: Can deploy but not delete ──
apiVersion: rbac.authorization.k8s.io/v1
kind: Role                        # Role = scoped to ONE namespace
metadata:
  name: shopease-developer
  namespace: shopease-dev
rules:
- apiGroups: [""]               # "" = core API group (pods, services, configmaps)
  resources:
  - pods
  - pods/log
  - pods/exec
  - services
  - configmaps
  verbs: [get, list, watch, create, update, patch]  # Can't delete!
- apiGroups: [apps]             # apps API group (deployments, replicasets)
  resources: [deployments, replicasets]
  verbs: [get, list, watch, create, update, patch]
- apiGroups: [route.openshift.io]
  resources: [routes]
  verbs: [get, list]             # Can see routes but not create them

---
# ── Bind Role to a user ──
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-developer-binding
  namespace: shopease-dev
subjects:                         # WHO gets this role
- kind: User
  name: alice@shopease.com      # OpenShift username
  apiGroup: rbac.authorization.k8s.io
roleRef:                          # WHAT role to assign
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: shopease-developer

---
# ── ServiceAccount for Pipeline ──
apiVersion: v1
kind: ServiceAccount             # Machine identity (used by pods, not humans)
metadata:
  name: shopease-pipeline-sa
  namespace: shopease-dev

Auto-scaling: HPA & KEDA
📖 Story: The Shopping Mall Escalators

Imagine a shopping mall. On regular days, you run 2 escalators. On Black Friday, you turn on all 10. When the rush ends, you switch back to 2. That's Horizontal Pod Autoscaler (HPA) — it adds/removes pod replicas based on CPU or custom metrics. You never run 10 escalators on a quiet Tuesday — you save electricity (money).

YAML
shopease-hpa.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: product-service-hpa
  namespace: shopease-dev
spec:
  scaleTargetRef:                 # What to scale
    apiVersion: apps/v1
    kind: Deployment
    name: product-service
  minReplicas: 3                 # Never go below 3 (high availability)
  maxReplicas: 20                # Never exceed 20 (cost control)
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # Scale UP when avg CPU > 70%. Scale DOWN when < 70%
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 400Mi     # Scale when avg memory per pod > 400Mi
  - type: Pods                   # Custom metric from Prometheus
    pods:
      metric:
        name: http_requests_per_second  # Custom metric name
      target:
        type: AverageValue
        averageValue: "1000"    # Scale when RPS per pod > 1000
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30   # Wait 30s before scaling up again
      policies:
      - type: Pods
        value: 4                # Add at most 4 pods per scale event
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300  # Wait 5 min before scaling down (avoid flapping)
      policies:
      - type: Pods
        value: 1                # Remove at most 1 pod per 60s (slow, careful)
        periodSeconds: 60

Kustomize: Environment Overlays

Kustomize lets you maintain one base config and override values per environment without duplicating YAML.

YAML — Production Overlay
environments/prod/kustomization.yaml 
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: shopease-prod               # Override namespace for all resources
namePrefix: prod-                       # Prefix all resource names

bases:
  - ../../base                           # Inherit from base configs

images:
  - name: quay.io/shopease/product-service
    newTag: v1.3.2                      # Production-pinned image tag

patches:                                # Override specific fields
  - target:
      kind: Deployment
      name: product-service
    patch: |
      - op: replace
        path: /spec/replicas
        value: 5                         # Prod needs more replicas than dev's 3
      - op: replace
        path: /spec/template/spec/containers/0/resources/limits/memory
        value: 2Gi                      # More memory for prod load

configMapGenerator:                     # Generate ConfigMaps with env-specific values
  - name: product-config
    literals:
      - LOG_LEVEL=WARN                  # Less verbose logs in prod
      - FEATURE_NEW_CHECKOUT=false      # Feature flag off in prod
      - CACHE_TTL_SECONDS=600

Blue-Green Deployment Strategy

Blue-Green keeps two identical environments (Blue = current production, Green = new version). You switch traffic by changing the Service selector — near-instant, zero-downtime, instant rollback.

YAML
blue-green-strategy.yaml 
# ── BLUE deployment (current production) ──
apiVersion: apps/v1
kind: Deployment
metadata:
  name: product-service-blue
spec:
  replicas: 5
  selector:
    matchLabels:
      app: product-service
      slot: blue                        # "slot" label distinguishes blue from green
  template:
    metadata:
      labels: { app: product-service, slot: blue, version: v1 }
    spec:
      containers:
      - name: product-service
        image: quay.io/shopease/product-service:v1.0  # v1 = current

---
# ── GREEN deployment (new version — warming up) ──
apiVersion: apps/v1
kind: Deployment
metadata:
  name: product-service-green
spec:
  replicas: 5
  selector:
    matchLabels:
      app: product-service
      slot: green
  template:
    metadata:
      labels: { app: product-service, slot: green, version: v2 }
    spec:
      containers:
      - name: product-service
        image: quay.io/shopease/product-service:v2.0  # v2 = new version

---
# ── Service: currently points to BLUE ──
apiVersion: v1
kind: Service
metadata:
  name: product-svc
spec:
  selector:
    app: product-service
    slot: blue                        # ← CHANGE THIS to "green" to switch traffic!
  ports:
  - port: 80
    targetPort: 8080
Blue-Green Switch
$ # Green is ready and healthy. Switch traffic in ONE command!
$ oc patch service product-svc \
-p '{"spec":{"selector":{"slot":"green"}}}'
service/product-svc patched

✓ 100% traffic now on GREEN (v2.0). BLUE (v1.0) still running.
✓ If problems: patch back to "blue" in milliseconds

$ # Verify switch
$ oc get svc product-svc -o jsonpath='{.spec.selector}'
{"app":"product-service","slot":"green"}

GitOps with ArgoCD
📖 Story: The Self-Driving Deployment

GitOps means your Git repository is the single source of truth. Instead of you running oc apply, ArgoCD continuously watches your Git repo and automatically syncs the cluster state to match. If someone manually changes something in the cluster, ArgoCD detects "drift" and corrects it. Your cluster is always exactly what your Git says it should be.

YAML — ArgoCD Application
argocd/shopease-prod-app.yaml 
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shopease-production
  namespace: openshift-gitops       # ArgoCD's own namespace
  finalizers:
    - resources-finalizer.argocd.argoproj.io  # Delete all resources when App deleted
spec:
  project: default

  source:
    repoURL: https://github.com/shopease/shopease-openshift
    targetRevision: main             # Watch main branch
    path: environments/prod           # Kustomize overlay for prod

  destination:
    server: https://kubernetes.default.svc  # This cluster
    namespace: shopease-prod

  syncPolicy:
    automated:                       # Auto-sync on git changes
      prune: true                    # Delete resources removed from Git
      selfHeal: true                 # Fix manual cluster changes (drift correction)
      allowEmpty: false             # Don't sync if result would be empty (safety)
    syncOptions:
    - CreateNamespace=true          # Create namespace if it doesn't exist
    - PrunePropagationPolicy=foreground  # Wait for deletion to complete
    - PruneLast=true               # Prune resources last (after creating new ones)
    retry:
      limit: 5                      # Retry sync 5 times on failure
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m

  ignoreDifferences:               # Ignore expected runtime differences
  - group: apps
    kind: Deployment
    jsonPointers:
    - /spec/replicas                # Ignore replica count (HPA manages this)

Full GitOps CI/CD Flow

Developer pushes code to GitHub
git push origin feature/new-product-api → PR opened → merged to main
GitHub Webhook → Tekton Pipeline
EventListener receives webhook → creates PipelineRun → runs: test → sonar → build → push image to Quay
Pipeline updates image tag in Git
Pipeline final step: git commit -m "ci: update product-service to sha-abc123" → pushes to shopease-openshift repo
ArgoCD detects Git change → auto-syncs
ArgoCD polls repo every 3 minutes (or webhook) → detects new image tag → applies Kustomize overlay → updates Deployment → rolling update begins
New pods pass health checks → traffic switches
Readiness probes pass → Service endpoints update → new traffic goes to new pods → old pods terminate gracefully
Prometheus alerts watch for issues
Error rate spike? → PagerDuty alert fires → SRE investigates → if needed: git revert → ArgoCD auto-rollbacks → previous image deployed
