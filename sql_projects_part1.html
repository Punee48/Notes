Step 3 — Stored Procedure for New Admissions
Stored Procedure — AdmitPatient
-- A stored procedure is a saved SQL program with a name
-- You call it like a function, passing inputs (parameters)
CREATE PROCEDURE sp_AdmitPatient
    @FullName       NVARCHAR(100),  -- input: patient's name
    @DOB            DATE,           -- input: date of birth
    @Gender         CHAR(1),        -- input: M, F, or O
    @BloodGroup     VARCHAR(5),     -- input: blood group
    @AssignedDoctor INT,            -- input: doctor's ID number
    @Diagnosis      NVARCHAR(200),  -- input: diagnosis text
    @Cost           DECIMAL(10,2)   -- input: treatment cost
AS
BEGIN
    -- SET NOCOUNT ON: stops SQL from printing "1 row(s) affected" messages
    -- Makes the procedure run cleaner and faster
    SET NOCOUNT ON;

    -- Declare a local variable to store the newly created PatientID
    DECLARE @NewPatientID INT;

    -- Step 1: Insert the patient into the Patients table
    INSERT INTO Patients (FullName, DateOfBirth, Gender, BloodGroup, AssignedDoctor)
    VALUES (@FullName, @DOB, @Gender, @BloodGroup, @AssignedDoctor);

    -- SCOPE_IDENTITY() returns the last ID that was just auto-generated
    -- We save it so we can use it in the next INSERT
    SET @NewPatientID = SCOPE_IDENTITY();

    -- Step 2: Automatically create a Visit record for this new patient
    INSERT INTO Visits (PatientID, Diagnosis, TreatmentCost)
    VALUES (@NewPatientID, @Diagnosis, @Cost);

    -- Print a confirmation message
    PRINT 'Patient admitted successfully. ID: ' + CAST(@NewPatientID AS VARCHAR);
END;
GO

EXEC sp_AdmitPatient
    @FullName       = 'Raju Shetty',
    @DOB            = '1988-03-10',
    @Gender         = 'M',
    @BloodGroup     = 'B+',
    @AssignedDoctor = 1,
    @Diagnosis      = 'Chest Pain',
    @Cost           = 3200.00;

Step 4 — Management Reporting View
View — DoctorPatientSummary
-- A VIEW is like a virtual table — it's a saved SELECT query
-- Management can query this view without knowing the complex JOIN logic
CREATE VIEW vw_DoctorPatientSummary
AS
SELECT
    d.DoctorName,                          -- doctor's name from Doctors table
    d.Speciality,                           -- their medical speciality
    COUNT(p.PatientID) AS TotalPatients,    -- count of patients assigned
    SUM(v.TreatmentCost) AS TotalRevenue   -- total money generated by this doctor
FROM Doctors d
-- alias 'd' is a short name for Doctors table — just to type less
LEFT JOIN Patients p
    ON d.DoctorID = p.AssignedDoctor
-- LEFT JOIN: include ALL doctors, even those with zero patients
LEFT JOIN Visits v
    ON p.PatientID = v.PatientID
GROUP BY d.DoctorName, d.Speciality;
-- GROUP BY: combine all rows that have the same DoctorName and Speciality
-- Then apply COUNT() and SUM() per group
GO

-- Run this view anytime to see the report
SELECT * FROM vw_DoctorPatientSummary
ORDER BY TotalRevenue DESC;
Interview Questions

🎤 Likely Interview Questions from This Project

Q: What is the difference between CHAR, VARCHAR, and NVARCHAR?
CHAR is fixed-length (always uses exactly n bytes). VARCHAR is variable-length (uses only what is needed). NVARCHAR stores Unicode characters and takes 2 bytes per character — you use it when you need to support non-English languages. In an MNC with global users, always prefer NVARCHAR for name fields.
Q: What is SCOPE_IDENTITY() and why use it instead of @@IDENTITY?
SCOPE_IDENTITY() returns the last identity value generated in the current scope (your stored procedure). @@IDENTITY returns the last identity value generated anywhere — including inside triggers. If a trigger runs an INSERT, @@IDENTITY may give you the trigger's ID, not yours. SCOPE_IDENTITY() is always safer.
Q: When should you use a View vs a Stored Procedure?
A View is used for read-only reporting — it's like a saved SELECT. A Stored Procedure is used when you need logic, parameters, DML operations (INSERT/UPDATE/DELETE), or multiple steps. Views are also used to restrict what columns a user can see without giving full table access.

Step 2 — Analytics using CTEs and Window Functions
CTE — Monthly Revenue with Previous Month Comparison
-- CTE = Common Table Expression
-- Think of it like a temporary table you define at the top
-- and use immediately in the same query

WITH MonthlyRevenue AS (
    -- This is the CTE body — give it a name, then write the SELECT
    SELECT
        YEAR(OrderDate)  AS OrderYear,
        -- YEAR() extracts just the year part from a date
        MONTH(OrderDate) AS OrderMonth,
        -- MONTH() extracts just the month number (1=Jan, 12=Dec)
        SUM(TotalAmount)  AS Revenue
    FROM Orders
    GROUP BY YEAR(OrderDate), MONTH(OrderDate)
)
-- Now use the CTE in the main SELECT
SELECT
    OrderYear,
    OrderMonth,
    Revenue,
    LAG(Revenue, 1, 0) OVER (ORDER BY OrderYear, OrderMonth) AS PrevMonthRevenue,
    -- LAG(column, offset, default): looks BACK by offset rows
    -- LAG(Revenue,1,0) = revenue from 1 row before this one, default 0 if no row
    Revenue - LAG(Revenue, 1, 0) OVER (ORDER BY OrderYear, OrderMonth) AS GrowthAmount
FROM MonthlyRevenue
ORDER BY OrderYear, OrderMonth;
GO
Window Function — Top 2 Customers per City
-- ROW_NUMBER() assigns a sequential number within each group
-- PARTITION BY City: restart numbering for each city
-- ORDER BY TotalSpend DESC: rank by who spent the most

WITH CustomerSpend AS (
    SELECT
        c.CustomerName,
        c.City,
        SUM(o.TotalAmount) AS TotalSpend
    FROM Customers c
    INNER JOIN Orders o ON c.CustomerID = o.CustomerID
    -- INNER JOIN: only show customers who have at least one order
    GROUP BY c.CustomerName, c.City
),
RankedCustomers AS (
    SELECT
        CustomerName,
        City,
        TotalSpend,
        ROW_NUMBER() OVER (
            PARTITION BY City              -- separate ranking for each city
            ORDER BY TotalSpend DESC        -- highest spender gets rank 1
        ) AS CityRank
    FROM CustomerSpend
)
SELECT CustomerName, City, TotalSpend, CityRank
FROM RankedCustomers
WHERE CityRank <= 2
-- Only top 2 customers per city
ORDER BY City, CityRank;

Window Functions Explained

OVER()The magic keyword that makes it a window function. Without OVER(), ROW_NUMBER() doesn't work. OVER() defines the "window" (subset of rows) the function looks at.
PARTITION BYDivides the data into groups. Like GROUP BY, but it does NOT collapse rows — each row still shows in the result. Think of it as "restart the counter for each group."
LAG / LEADLAG looks backward (previous row). LEAD looks forward (next row). Very useful for comparing current vs previous period — like month-over-month revenue growth.
ROW_NUMBER vs RANKROW_NUMBER always gives unique consecutive numbers (1,2,3,4). RANK gives the same number to ties and skips numbers (1,1,3). DENSE_RANK gives same number to ties but doesn't skip (1,1,2).
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between ROW_NUMBER(), RANK(), and DENSE_RANK()?
ROW_NUMBER always gives unique sequential numbers even for ties. RANK gives the same rank to ties but then skips — if two rows tie at rank 2, the next gets rank 4. DENSE_RANK gives same rank to ties but doesn't skip — next gets rank 3. In interview, always remember the "tie" scenario.
Q: What is a CTE and when would you use it over a subquery?
A CTE (Common Table Expression) is a named temporary result set defined with the WITH keyword. Use CTE when you need to reference the same subquery multiple times, or when the query is complex and you want to break it into readable steps. CTEs also support recursion, which subqueries cannot do.

Step 2 — The Fraud Detection Trigger
AFTER INSERT Trigger
-- CREATE TRIGGER: define a trigger with a name
CREATE TRIGGER trg_FraudCheck
ON Transactions           -- this trigger watches the Transactions table
AFTER INSERT               -- fires AFTER a new row is successfully inserted
AS
BEGIN
    SET NOCOUNT ON;

    -- Inside a trigger, SQL Server gives you two special virtual tables:
    -- INSERTED: contains the new row(s) that were just inserted
    -- DELETED:  contains old row(s) that were just deleted (for UPDATE/DELETE triggers)

    -- Check if any newly inserted transaction exceeds 1,00,000
    INSERT INTO FraudAlerts (TxnID, AccountID, Amount, AlertReason)
    SELECT
        i.TxnID,
        i.AccountID,
        i.Amount,
        -- Build an alert reason message using string concatenation
        'Large transaction detected: Amount = '
            + CAST(i.Amount AS VARCHAR)
            + ' on '
            + CONVERT(VARCHAR, i.TxnDate, 103)
        -- CONVERT with style 103 = DD/MM/YYYY format
    FROM INSERTED i           -- read from the special INSERTED virtual table
    WHERE i.Amount > 100000; -- only flag if amount > 1 lakh
END;
GO

Step 3 — Dynamic SQL for Flexible Fraud Reports
Dynamic SQL — Flexible Fraud Report Generator
-- Dynamic SQL means: build the SQL query as a string
-- then execute it. Useful when the WHERE conditions change at runtime.
CREATE PROCEDURE sp_FraudReport
    @MinAmount   DECIMAL(15,2) = NULL,  -- optional filter: min amount
    @Status      VARCHAR(20)    = NULL,  -- optional filter: PENDING or REVIEWED
    @FromDate    DATE           = NULL   -- optional filter: start date
AS
BEGIN
    -- NVARCHAR(MAX) holds very long strings — enough for a full SQL query
    DECLARE @SQL    NVARCHAR(MAX);
    DECLARE @Params NVARCHAR(MAX);

    -- Start building the base query as a string
    SET @SQL = N'SELECT AlertID, TxnID, Amount, AlertReason, AlertedOn, Status
                FROM FraudAlerts
                WHERE 1=1 ';
    -- WHERE 1=1 is a trick: it's always true, so we can safely append AND clauses

    -- Add conditions only if parameter is provided (not NULL)
    IF @MinAmount IS NOT NULL
        SET @SQL = @SQL + N' AND Amount >= @MinAmount ';

    IF @Status IS NOT NULL
        SET @SQL = @SQL + N' AND Status = @Status ';

    IF @FromDate IS NOT NULL
        SET @SQL = @SQL + N' AND CAST(AlertedOn AS DATE) >= @FromDate ';

    -- Define the parameter types for sp_executesql
    SET @Params = N'@MinAmount DECIMAL(15,2), @Status VARCHAR(20), @FromDate DATE';

    -- Execute the dynamically built SQL string safely
    -- sp_executesql is safer than EXEC(@SQL) because it prevents SQL injection
    EXEC sp_executesql
        @SQL,
        @Params,
        @MinAmount = @MinAmount,
        @Status    = @Status,
        @FromDate  = @FromDate;
END;
GO

-- Usage examples:
EXEC sp_FraudReport @MinAmount = 50000;
EXEC sp_FraudReport @Status = 'PENDING';
EXEC sp_FraudReport @FromDate = '2024-01-01', @MinAmount = 100000;
Interview Questions

🎤 Likely Interview Questions

Q: What are INSERTED and DELETED tables inside a trigger?
They are special virtual tables created by SQL Server automatically during trigger execution. INSERTED contains the new rows being added (for INSERT and UPDATE). DELETED contains the old rows being removed (for DELETE and UPDATE). You use these to read what changed and act on it.
Q: What is the risk of Dynamic SQL and how do you prevent SQL injection?
If you directly embed user input into a SQL string (EXEC(@SQL)), a malicious user can inject harmful SQL code. The safe way is to use sp_executesql with parameterized queries — you define the parameter types separately and pass values as parameters, never as part of the string itself. This is a must-know for any SQL Developer interview.

CREATE TABLE SalaryAudit (
    AuditID      INT IDENTITY(1,1) PRIMARY KEY,
    EmpID        INT,
    OldSalary    DECIMAL(12,2),
    NewSalary    DECIMAL(12,2),
    ChangedBy    NVARCHAR(100) DEFAULT SYSTEM_USER,
    -- SYSTEM_USER returns the SQL Server login name of who ran this query
    ChangedOn    DATETIME DEFAULT GETDATE()
);
GO

-- AFTER UPDATE trigger on Employees table
-- Fires whenever any UPDATE happens on the Employees table
CREATE TRIGGER trg_SalaryAudit
ON Employees
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    -- UPDATE(Salary) is a trigger function that returns TRUE
    -- only if the Salary column was included in the UPDATE statement
    IF UPDATE(Salary)
    BEGIN
        INSERT INTO SalaryAudit (EmpID, OldSalary, NewSalary)
        SELECT
            d.EmpID,
            d.Salary,   -- DELETED holds the OLD values before the update
            i.Salary    -- INSERTED holds the NEW values after the update
        FROM DELETED d
        INNER JOIN INSERTED i ON d.EmpID = i.EmpID
        WHERE d.Salary <> i.Salary;
        -- Only log if salary actually changed (not just other column updates)
    END
END;
GO
Step 2 — Transaction with TRY CATCH
Payroll Update with Full Error Handling
-- A TRANSACTION groups multiple SQL statements into one unit
-- Either ALL statements succeed, or NONE of them are saved
CREATE PROCEDURE sp_UpdateSalary
    @EmpID      INT,
    @NewSalary  DECIMAL(12,2)
AS
BEGIN
    SET NOCOUNT ON;

    -- TRY block: SQL tries to run this code
    BEGIN TRY
        -- Validate: salary cannot be negative
        IF @NewSalary <= 0
            -- THROW raises a custom error and jumps to the CATCH block
            THROW 50001, 'Salary must be greater than zero.', 1;

        -- BEGIN TRANSACTION: start grouping statements
        BEGIN TRANSACTION;

            UPDATE Employees
            SET Salary = @NewSalary
            WHERE EmpID = @EmpID;
            -- The trigger trg_SalaryAudit will fire automatically here

            -- Check if any row was actually updated
            IF @@ROWCOUNT = 0
                THROW 50002, 'Employee ID not found.', 1;
            -- @@ROWCOUNT is a system variable: number of rows affected by last statement

        -- COMMIT saves the transaction permanently
        COMMIT TRANSACTION;
        PRINT 'Salary updated successfully.';

    END TRY
    BEGIN CATCH
        -- CATCH block runs if ANY error occurred inside TRY
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;
        -- @@TRANCOUNT tells us if a transaction is still open
        -- ROLLBACK undoes everything done inside BEGIN TRANSACTION

        -- Show the error message to the caller
        PRINT 'ERROR: ' + ERROR_MESSAGE();
        -- ERROR_MESSAGE() returns the text of the error that occurred
    END CATCH
END;
GO

EXEC sp_UpdateSalary @EmpID = 1, @NewSalary = 95000;
SELECT * FROM SalaryAudit; -- Should show old=80000, new=95000

-- Test: error case

Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between COMMIT and ROLLBACK?
COMMIT permanently saves all changes made inside a transaction to the database. ROLLBACK undoes all changes made since the BEGIN TRANSACTION, leaving the data exactly as it was before. Think of it like a save button vs an undo button in a document editor.
Q: What is @@TRANCOUNT and why check it before ROLLBACK?
@@TRANCOUNT tells you how many active transactions are currently open. You check it before calling ROLLBACK to make sure a transaction is actually open — calling ROLLBACK when there's no transaction causes an error. It's a safety check always recommended in CATCH blocks.

-- This says: split data into 4 ranges based on CallDate
-- Partition 1: before 2024-02-01
-- Partition 2: between 2024-02-01 and 2024-03-01
-- Partition 3: between 2024-03-01 and 2024-04-01
-- Partition 4: 2024-04-01 and beyond
CREATE PARTITION FUNCTION pf_CDRByMonth (DATE)
AS RANGE RIGHT FOR VALUES (
    '2024-02-01',
    '2024-03-01',
    '2024-04-01'
);
-- RANGE RIGHT means: the boundary value belongs to the RIGHT (next) partition
GO

-- PARTITION SCHEME: maps partition ranges to FILEGROUPS
-- In production you'd have separate filegroups on different disks
-- Here we map everything to PRIMARY (the default filegroup)
CREATE PARTITION SCHEME ps_CDRByMonth
AS PARTITION pf_CDRByMonth
ALL TO ([PRIMARY]);
GO

-- Now create the CDR table ON the partition scheme
-- The column in brackets is the PARTITION COLUMN (must be in partition function)
CREATE TABLE CallDetailRecords (
    CDRID        BIGINT IDENTITY(1,1),
    -- BIGINT for very large numbers (up to 9.2 quadrillion)
    CallerNumber VARCHAR(15) NOT NULL,
    ReceiverNumber VARCHAR(15) NOT NULL,
    CallDate     DATE    NOT NULL,
    CallDuration INT,            -- duration in seconds
    CallType     VARCHAR(10),    -- LOCAL, STD, ISD
    ChargeAmount DECIMAL(8,4)
) ON ps_CDRByMonth (CallDate);
-- ON ps_CDRByMonth(CallDate) = use this partition scheme, split by CallDate
GO

-- Insert test data across different months
INSERT INTO CallDetailRecords (CallerNumber, ReceiverNumber, CallDate, CallDuration, CallType, ChargeAmount)
VALUES

  ('9876543214', '9876543215', '2024-03-20', 45,  'ISD',   5.25),  -- partition 3
  ('9876543216', '9876543217', '2024-04-05', 200, 'LOCAL', 1.00);  -- partition 4
GO

-- Verify which partition each row is stored in
SELECT

Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between RANGE LEFT and RANGE RIGHT in partition functions?
RANGE RIGHT means the boundary value belongs to the right (next) partition. For example, with boundary 2024-02-01, RANGE RIGHT puts Feb 1 itself into the second partition. RANGE LEFT puts Feb 1 into the first partition. In most date-based partitioning scenarios, RANGE RIGHT is more intuitive — "month starts from the 1st."
Q: When would you use a Columnstore Index instead of a regular B-tree index?
Use Columnstore indexes for data warehouse or OLAP workloads where you run aggregation queries (SUM, COUNT, AVG) on large tables. They compress data column-by-column and read only the needed columns, making them 10–100x faster for analytics. For OLTP workloads with many INSERT/UPDATE operations, regular B-tree indexes are better since Columnstore has slower write performance.

CREATE TABLE Inventory.Products (

Step 2 — MERGE Statement
MERGE — Upsert (Insert or Update)
-- MERGE combines INSERT and UPDATE into one statement
-- It compares a SOURCE (new incoming data) with a TARGET (existing table)
-- Based on a match condition, it decides what to do

-- First, create a staging table with new stock data coming in
CREATE TABLE Inventory.StockStaging (
    ProductID   INT,
    ProductName NVARCHAR(100),
    UnitPrice   DECIMAL(10,2),
    NewQty      INT
);

INSERT INTO Inventory.StockStaging VALUES
  (1, 'Rice 5kg',     250, 100),  -- product 1 already exists
  (NULL, 'Wheat 10kg', 420, 50);  -- new product, no existing ID

MERGE Inventory.Products AS Target
-- MERGE TARGET AS alias: the table you want to modify
USING Inventory.StockStaging AS Source
-- USING SOURCE AS alias: the table with incoming data
ON Target.ProductID = Source.ProductID
-- ON: the matching condition — how to find if the record already exists

-- WHEN MATCHED: record exists in both Target and Source
WHEN MATCHED THEN
    UPDATE SET
        Target.QuantityInStock = Target.QuantityInStock + Source.NewQty,
        Target.UnitPrice        = Source.UnitPrice

-- WHEN NOT MATCHED BY TARGET: Source has it but Target doesn't = INSERT
WHEN NOT MATCHED BY TARGET THEN
    INSERT (ProductName, UnitPrice, QuantityInStock)
    VALUES (Source.ProductName, Source.UnitPrice, Source.NewQty);
-- Semicolon is REQUIRED at the end of MERGE
GO
Interview Questions

🎤 Likely Interview Questions

Q: What is a computed column and when would you add PERSISTED?
A computed column is a virtual column whose value is automatically derived from a formula using other columns. By default it's calculated every time you query it. Adding PERSISTED stores the computed value physically on disk — this makes reads faster but takes extra storage. Use PERSISTED when the column is frequently queried and the base columns don't change very often.
Q: What is the MERGE statement and what are its use cases?
MERGE is an "upsert" operation — it updates if a record exists, inserts if it doesn't. This is very useful in ETL pipelines where you receive daily data and need to sync it with the main table. In one single statement, MERGE handles all three scenarios: WHEN MATCHED (update), WHEN NOT MATCHED BY TARGET (insert), and optionally WHEN NOT MATCHED BY SOURCE (delete).

Scalar Function — GetGrade
-- A SCALAR FUNCTION returns ONE single value
-- You can use it anywhere you use a column or expression
CREATE FUNCTION dbo.fn_GetGrade (@Marks INT)
RETURNS VARCHAR(5)
AS
BEGIN
    DECLARE @Grade VARCHAR(5);

    -- CASE WHEN: like an if-elseif-else ladder
    SET @Grade = CASE
        WHEN @Marks >= 90 THEN 'A+'
        WHEN @Marks >= 75 THEN 'A'
        WHEN @Marks >= 60 THEN 'B'
        WHEN @Marks >= 40 THEN 'C'
        ELSE 'F'
    END;

    RETURN @Grade; -- return the computed grade
END;
GO

FROM StudentMarks

Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between a Scalar Function and a Table-Valued Function?
A Scalar Function returns a single value (like a number or string). You use it in SELECT, WHERE, or SET statements. A Table-Valued Function returns an entire result set (like a table). You use it in the FROM clause as if it were a table. Inline Table-Valued Functions (with just a single SELECT inside) are faster than multi-statement TVFs.
Q: What is COALESCE and how is it different from ISNULL?
Both return the first non-NULL value. ISNULL takes exactly 2 arguments: ISNULL(expression, replacement). COALESCE can take multiple arguments and returns the first non-NULL: COALESCE(a, b, c, d). COALESCE is ANSI standard and works across all SQL databases. ISNULL is SQL Server specific. In MNC interviews, knowing the ANSI standard version is always better.

Step 2 — Cursor-Based Claim Processing
CURSOR — Row-by-Row Claim Validation
CREATE PROCEDURE sp_ProcessClaims
AS
BEGIN
    SET NOCOUNT ON;

    -- Variables to hold values from each row
    DECLARE @ClaimID      INT;
    DECLARE @PolicyID     INT;
    DECLARE @ClaimAmount  DECIMAL(12,2);
    DECLARE @InsuredAmt   DECIMAL(12,2);
    DECLARE @PremiumPaid  BIT;

    -- DECLARE CURSOR: define the set of rows to loop through
    -- FORWARD_ONLY means: move only forward, one row at a time
    -- READ_ONLY means: we won't update rows through this cursor
    DECLARE claims_cursor CURSOR FORWARD_ONLY READ_ONLY FOR
    SELECT ClaimID, PolicyID, ClaimAmount
    FROM Claims
    WHERE ClaimStatus = 'PENDING';

    -- OPEN the cursor: executes the SELECT query, prepares the result set
    OPEN claims_cursor;

    -- FETCH NEXT: move the pointer to the next row and load values
    FETCH NEXT FROM claims_cursor
    INTO @ClaimID, @PolicyID, @ClaimAmount;

    -- @@FETCH_STATUS = 0 means FETCH was successful (row was returned)
    -- @@FETCH_STATUS = -1 means no more rows (end of cursor)
    WHILE @@FETCH_STATUS = 0
    BEGIN
        -- Look up policy details for this claim
        SELECT
            @InsuredAmt  = InsuredAmount,
            @PremiumPaid = PremiumPaid
        FROM Policies
        WHERE PolicyID = @PolicyID;

        -- VALIDATION 1: Policy must exist
        IF @InsuredAmt IS NULL
        BEGIN
            INSERT INTO ErrorLog(ClaimID, ErrorMessage)
            VALUES(@ClaimID, 'Policy not found');
        END
        -- VALIDATION 2: Premium must be paid
        ELSE IF @PremiumPaid = 0
        BEGIN
            INSERT INTO ErrorLog(ClaimID, ErrorMessage)
            VALUES(@ClaimID, 'Premium not paid — claim rejected');
        END
        -- VALIDATION 3: Claim must not exceed insured amount
        ELSE IF @ClaimAmount > @InsuredAmt
        BEGIN
            INSERT INTO ErrorLog(ClaimID, ErrorMessage)
            VALUES(@ClaimID, 'Claim exceeds insured amount');
        END
        ELSE
        BEGIN
            -- All checks passed: approve the claim
            UPDATE Claims SET ClaimStatus = 'APPROVED'
            WHERE ClaimID = @ClaimID;
        END

        -- Reset variable for next iteration
        SET @InsuredAmt = NULL;

        -- FETCH NEXT: move to the next row
        FETCH NEXT FROM claims_cursor
        INTO @ClaimID, @PolicyID, @ClaimAmount;
    END

    -- Always CLOSE and DEALLOCATE the cursor to free memory
    CLOSE claims_cursor;
    DEALLOCATE claims_cursor;
END;
GO

EXEC sp_ProcessClaims;
SELECT * FROM Claims;
SELECT * FROM ErrorLog;

Q: Cursors are slow — why would you still use them?
You're right that cursors process row by row and are slower than set-based operations. However, cursors are necessary when you need to apply different business logic for each row individually — like sending different emails per row, calling external stored procedures per record, or handling complex conditional branching that cannot be expressed as a single set-based UPDATE. In practice, always mention: "I try to avoid cursors by using set-based operations, but when individual row logic is unavoidable, I use FORWARD_ONLY READ_ONLY cursors for minimum overhead."

Step 2 — Covering Index
Covering Index — Answering Queries Without Touching Main Table
-- A regular non-clustered index stores the indexed column + pointer to row
-- SQL Server still has to do a second lookup (Key Lookup) to get other columns
-- A COVERING INDEX includes all columns needed by the query in the index itself
-- So SQL Server NEVER has to go back to the main table = much faster

-- This query pattern is common: filter by City, return Title and Price
SELECT Title, Price
FROM Properties
WHERE City = 'Bengaluru';

-- Create a covering index that includes City (filter) + Title and Price (output)
CREATE NONCLUSTERED INDEX idx_Props_City_Cover
ON Properties (City)                       -- search key
INCLUDE (Title, Price);                     -- INCLUDE adds extra columns to index pages
-- Now the above SELECT query reads only the index — never touches the table
-- You can verify this by pressing Ctrl+M in SSMS (Actual Execution Plan)
-- Look for "Index Seek" (good) vs "Table Scan" (slow)
GO
Interview Questions

🎤 Likely Interview Questions

Q: What is the difference between Clustered and Non-Clustered indexes?
A Clustered Index determines the physical order of data in the table. There can only be ONE clustered index per table because data can be physically sorted in only one way — it's usually the primary key. A Non-Clustered Index is a separate structure that points back to the data. You can have many non-clustered indexes per table. Think of the Clustered Index as the dictionary itself (words in alphabetical order), and Non-Clustered as the index at the back of a book (pointing you to pages).
Q: What is a Covering Index and when does it help?
A Covering Index includes all the columns that a specific query needs — both the filter columns and the SELECT columns. When SQL Server finds all needed data in the index itself, it never has to do a "Key Lookup" back to the main table. This eliminates one I/O operation per row, which on millions of rows makes a huge difference. You design covering indexes by analyzing your most frequent query patterns.

Application Log Analytics & Performance Monitor

Scenario: Capgemini / TCS IT Operations — Querying DMVs for database health checks

DMVs (sys.dm_exec_*)Query Store Missing Index DMVsWait Statisticssp_whoisactive
The Story
It's 2 AM. The on-call alert fires: "Database CPU at 98%." You SSH into the production server and open SSMS. You need to find: "What queries are currently running?", "Which query is consuming the most CPU?", "Are there missing indexes that are causing slow queries?", "What is SQL Server waiting on right now?" These questions are answered using DMVs — Dynamic Management Views. They are built-in system views in SQL Server that expose the engine's internal state in real-time. Every senior SQL Developer and DBA must know these. This is the most impressive topic in any interview.
DMV Queries — Learn These by Heart
1. Currently Running Queries
-- Find all queries currently executing on the SQL Server
-- This is the first thing you run during an incident
SELECT
    r.session_id,               -- session number (like a process ID)
    r.status,                    -- running, sleeping, suspended
    r.cpu_time,                  -- CPU milliseconds consumed
    r.total_elapsed_time,        -- how long this query has been running (ms)
    r.wait_type,                 -- what is this query waiting for (if suspended)
    SUBSTRING(
        st.text,
        (r.statement_start_offset/2)+1,
        ((CASE r.statement_end_offset
          WHEN -1 THEN DATALENGTH(st.text)
          ELSE r.statement_end_offset
        END - r.statement_start_offset)/2)+1
    ) AS CurrentStatement
    -- SUBSTRING extracts the exact SQL statement being executed right now
FROM sys.dm_exec_requests r
-- sys.dm_exec_requests: all currently active requests in SQL Server
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
-- CROSS APPLY calls dm_exec_sql_text for each row — returns the query text
WHERE r.session_id > 50  -- session IDs below 50 are system processes
ORDER BY r.cpu_time DESC;
2. Top 10 Most Expensive Queries (by CPU)
-- sys.dm_exec_query_stats: statistics for all cached query plans
-- This shows which queries have consumed the most CPU since server start
SELECT TOP 10
    SUBSTRING(st.text, 1, 200)       AS QueryText,
    qs.execution_count                AS ExecutionCount,
    qs.total_worker_time / 1000      AS TotalCPU_ms,
    qs.total_worker_time
        / qs.execution_count / 1000   AS AvgCPU_ms,
    qs.total_logical_reads            AS TotalLogicalReads
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_worker_time DESC;
3. Missing Index Recommendations
-- SQL Server tracks which queries would have benefited from an index
-- sys.dm_db_missing_index_details: lists suggested indexes by SQL Server
SELECT TOP 10
    mid.statement                              AS TableName,
    mid.equality_columns                       AS EqualityColumns,
    -- columns used in WHERE col = value conditions
    mid.inequality_columns                     AS InequalityColumns,
    -- columns used in WHERE col > or col < conditions
    mid.included_columns                       AS IncludedColumns,
    -- columns that would make this a covering index
    ROUND(migs.avg_user_impact, 2)             AS EstImprovementPct,
    -- estimated % improvement if you create this index
    migs.user_seeks + migs.user_scans         AS TotalUsage
FROM sys.dm_db_missing_index_details mid
JOIN sys.dm_db_missing_index_groups mig
    ON mid.index_handle = mig.index_handle
JOIN sys.dm_db_missing_index_group_stats migs
    ON mig.index_group_handle = migs.group_handle
ORDER BY migs.avg_user_impact DESC;

DMV Glossary — Know These Terms

sys.dm_exec_requestsReal-time: shows every query currently executing. First stop during an incident.
sys.dm_exec_query_statsHistorical: cumulative CPU, reads, writes, executions for all cached queries. Use to find the most expensive queries.
CROSS APPLYLike a JOIN but calls a table-valued function for each row. Used here to get query text for each sql_handle.
sql_handleA binary identifier for a SQL query stored in the plan cache. You pass it to dm_exec_sql_text() to get the actual query text.
wait_typeTells you WHY a query is suspended — LCK_M_X = waiting for a lock, PAGEIOLATCH = waiting for disk read, CXPACKET = parallel query coordination.
Interview Questions

🎤 Likely Interview Questions

Q: If a production database suddenly becomes slow, what is your first step?
My first step is to query sys.dm_exec_requests to see what is currently running and check the status and wait_type for each session. If sessions are in "suspended" state with LCK_M_X wait type, there's a blocking/locking issue. If they're running with high cpu_time, it's a CPU-intensive query issue. Then I query dm_exec_query_stats to find the top CPU-consuming queries and dm_db_missing_index_details to see if missing indexes are causing table scans. This 3-step approach covers 90% of production issues.
Q: What is CROSS APPLY and how is it different from INNER JOIN?
CROSS APPLY calls a table-valued function or correlated query for each row from the left table and combines the results. It's like an INNER JOIN but the right side is a function call that depends on values from the left side. In DMV queries, we use CROSS APPLY to call sys.dm_exec_sql_text() for each row, passing the sql_handle from that specific row. A regular JOIN cannot do this because you can't pass row-specific values as function parameters in a JOIN.
