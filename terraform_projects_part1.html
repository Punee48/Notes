01

Deploy Your First EC2 Instance on AWS

Terraform Basics AWS EC2 Beginner
📖 The Story

You just joined TechNova Solutions, a mid-sized MNC. Your manager says: "We've been creating servers manually on AWS console for years. One dev deleted the wrong server last week and we lost 2 hours of revenue. I need you to start automating our infrastructure with Terraform. Start simple — just spin up an EC2 instance the right way." This is Day 1. You open your laptop and begin.

🧠 Concepts Covered
  • Provider: Tells Terraform which cloud (AWS, Azure, GCP) to talk to
  • Resource: The actual cloud component you want to create (server, database, etc.)
  • Variables: Dynamic values so you don't hardcode things
  • Outputs: Values printed after deployment (like IP address)
  • terraform init / plan / apply / destroy: The 4 core Terraform commands
  • State file (.tfstate): Terraform's memory of what it created

Understanding the Folder Structure

In any Terraform project, you split your code into multiple files for clarity. Terraform reads all .tf files in the same directory together.

my-ec2-project/
├── main.tf      ← where resources are defined
├── variables.tf  ← where input variables are declared
├── outputs.tf   ← what Terraform prints after deployment
└── terraform.tfvars ← actual values for your variables

The Code — File by File

📄 main.tf

main.tf HCL 
# ─── PROVIDER BLOCK ───────────────────────────────────────────
# Tell Terraform: "We are working with Amazon Web Services"
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"   # Official AWS plugin by HashiCorp
      version = "~> 5.0"          # Use version 5.x (any minor update)
    }
  }
}

# Configure the AWS provider
provider "aws" {
  region = var.aws_region   # Use the region from variables.tf
}

# ─── DATA SOURCE ──────────────────────────────────────────────
# Fetch the latest Amazon Linux 2 AMI automatically
# (Instead of hardcoding ami-0abc123 which changes by region)
data "aws_ami" "amazon_linux" {
  most_recent = true           # Get the newest one
  owners      = ["amazon"]   # Only from Amazon's official account

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]  # Pattern for Amazon Linux 2
  }
}

# ─── SECURITY GROUP ───────────────────────────────────────────
# A firewall rule for our EC2 instance
resource "aws_security_group" "web_sg" {
  name        = "technova-web-sg"
  description = "Allow SSH and HTTP traffic"

  # INBOUND rule: Allow SSH (port 22) from anywhere
  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]   # WARNING: production should restrict this
  }

  # INBOUND rule: Allow HTTP (port 80)
  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  # OUTBOUND rule: Allow all outbound traffic
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"           # -1 means all protocols
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name    = "technova-web-sg"
    Project = "technova"
    Env     = var.environment
  }
}

# ─── EC2 INSTANCE ─────────────────────────────────────────────
resource "aws_instance" "web_server" {
  ami           = data.aws_ami.amazon_linux.id   # From data source above
  instance_type = var.instance_type               # From variables

  vpc_security_group_ids = [aws_security_group.web_sg.id]
  # Reference the security group we created above

  key_name = var.key_pair_name   # Your AWS key pair for SSH access

  # Run this script when instance first boots
  user_data = <<-EOF
    #!/bin/bash
    yum update -y
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    echo "<h1>Hello from TechNova - Terraform Managed!</h1>" > /var/www/html/index.html
  EOF

  tags = {
    Name        = "technova-web-server"
    Environment = var.environment
    ManagedBy   = "Terraform"    # Always tag Terraform-managed resources!
  }
}
🔍 Word-by-Word Explanation
terraform {}
The settings block for Terraform itself. Here you declare which providers (cloud plugins) are needed.
required_providers
Mandatory declaration — Terraform needs to download these plugins before it can do anything.
source = "hashicorp/aws"
This tells Terraform to download the AWS provider from the HashiCorp registry at registry.terraform.io.
version = "~> 5.0"
The tilde-arrow operator means "5.x but not 6.0". Prevents breaking changes from auto-updating.
provider "aws" {}
Configures the AWS provider. The region tells AWS which data center to create resources in.
data "aws_ami" {}
A data source reads existing information without creating anything. Here we FIND the latest AMI ID dynamically so we never need to hardcode it.
resource "aws_instance" "web_server"
"aws_instance" is the Terraform resource type. "web_server" is YOUR local name. You reference this later as aws_instance.web_server.id
user_data = <<-EOF
A heredoc string. Everything between EOF markers is a shell script that runs on first boot. Here it installs Apache web server.
ManagedBy = "Terraform"
Professional best practice — always tag resources so your team knows they are Terraform-managed and shouldn't be changed manually.

📄 variables.tf

variables.tf HCL 
variable "aws_region" {
  description = "AWS region to deploy resources"
  type        = string
  default     = "us-east-1"  # Override in terraform.tfvars
}

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t2.micro"   # Free tier eligible
}

variable "environment" {
  description = "Deployment environment"
  type        = string
  default     = "dev"

  # Validation ensures only allowed values are used
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod."
  }
}

variable "key_pair_name" {
  description = "AWS Key Pair name for SSH"
  type        = string
  # No default — user MUST provide this value
}

📄 outputs.tf

outputs.tf HCL 
output "instance_public_ip" {
  description = "Public IP of the web server"
  value       = aws_instance.web_server.public_ip
}

output "instance_id" {
  description = "EC2 Instance ID"
  value       = aws_instance.web_server.id
}

output "web_url" {
  description = "URL to access the website"
  value       = "http://${aws_instance.web_server.public_ip}"
}

✅ AWS CLI installed
✅ Terraform installed
✅ AWS Key Pair created

Step 1: Install Terraform on your laptop

# macOS (Homebrew)
brew tap hashicorp/tap && brew install hashicorp/tap/terraform

# Windows (Chocolatey)
choco install terraform

# Ubuntu/Debian
sudo apt-get update && sudo apt-get install -y gnupg software-properties-common
wget -O- https://apt.releases.hashicorp.com/gpg | gpg --dearmor | sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg
sudo apt update && sudo apt install terraform

# Verify
terraform version

Step 2: Configure AWS credentials

aws configure
# Enter your AWS Access Key ID, Secret Access Key, region
  1. Create a folder: mkdir terraform-ec2 && cd terraform-ec2
  2. Create all three files: main.tf, variables.tf, outputs.tf with the code above
  3. Create terraform.tfvars and add: key_pair_name = "your-key-name"
  4. Run terraform init — this downloads the AWS provider plugin (you'll see a .terraform folder appear)
  5. Run terraform plan — this shows you WHAT will be created. Read it carefully! Green "+" means create.
  6. Run terraform apply — type "yes" when prompted. Watch your server get created!
  7. Copy the output web_url and open it in browser — you'll see the Apache page!
  8. IMPORTANT: Run terraform destroy when done to avoid AWS charges

Custom VPC with Public & Private Subnets

AWS Networking VPC / Subnets Intermediate
📖 The Story

Three weeks in at TechNova. Your manager Priya calls you: "Our security audit failed. All our EC2 instances are in the default VPC with public IPs — including our database server! The auditor says our DB should NEVER be publicly accessible. Build us a proper network with a public zone for web servers and a private zone for databases. No exceptions." This is the fundamental networking pattern used by every serious company on AWS.

🧠 Concepts Covered
  • VPC (Virtual Private Cloud): Your own isolated network on AWS — like your own private data center
  • Public Subnet: Servers here get public IPs and can be reached from the internet
  • Private Subnet: Servers here have NO public IP — databases, internal services go here
  • Internet Gateway: The door between your VPC and the public internet
  • NAT Gateway: Lets private subnet servers access internet (for updates) WITHOUT being publicly accessible
  • Route Tables: The rules that say where traffic should go
  • CIDR Blocks: IP address ranges — e.g., 10.0.0.0/16
AWS Cloud
└── VPC: 10.0.0.0/16
    ├── Public Subnet 10.0.1.0/24 (AZ-a) ── Internet Gateway ── 🌐 Internet
    ├── Public Subnet 10.0.2.0/24 (AZ-b)
    │     └── NAT Gateway ┐
    ├── Private Subnet 10.0.3.0/24 (AZ-a) <─ NAT (outbound only)
    └── Private Subnet 10.0.4.0/24 (AZ-b) <─ NAT (outbound only)

The Code

main.tf HCL 
# ─── VPC ──────────────────────────────────────────────────────
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"  # 65,536 IPs available in this VPC
  enable_dns_hostnames = true           # Instances get DNS names like ec2-xxx.compute.amazonaws.com
  enable_dns_support   = true           # Required for DNS to work inside VPC

  tags = { Name = "technova-vpc" }
}

# ─── INTERNET GATEWAY ─────────────────────────────────────────
# Without this, NOTHING can reach the internet from your VPC
resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id    # Attach to our VPC
  tags   = { Name = "technova-igw" }
}

# ─── PUBLIC SUBNETS ───────────────────────────────────────────
# We create 2 public subnets in different Availability Zones for HA
resource "aws_subnet" "public_1" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"  # 256 IPs
  availability_zone       = "us-east-1a"
  map_public_ip_on_launch = true            # Instances get public IPs automatically
  tags = { Name = "technova-public-1" }
}

resource "aws_subnet" "public_2" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.2.0/24"
  availability_zone       = "us-east-1b"
  map_public_ip_on_launch = true
  tags = { Name = "technova-public-2" }
}

# ─── PRIVATE SUBNETS ──────────────────────────────────────────
resource "aws_subnet" "private_1" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.3.0/24"
  availability_zone = "us-east-1a"
  # NO map_public_ip_on_launch — these instances stay PRIVATE
  tags = { Name = "technova-private-1" }
}

resource "aws_subnet" "private_2" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.4.0/24"
  availability_zone = "us-east-1b"
  tags = { Name = "technova-private-2" }
}

# ─── ELASTIC IP for NAT Gateway ───────────────────────────────
resource "aws_eip" "nat_eip" {
  domain     = "vpc"
  depends_on = [aws_internet_gateway.igw]  # IGW must exist first
}

# ─── NAT GATEWAY ──────────────────────────────────────────────
# Lives in PUBLIC subnet, gives private subnet internet access
resource "aws_nat_gateway" "nat" {
  allocation_id = aws_eip.nat_eip.id      # The fixed public IP
  subnet_id     = aws_subnet.public_1.id  # NAT must sit in a PUBLIC subnet
  tags          = { Name = "technova-nat" }
}

# ─── ROUTE TABLES ─────────────────────────────────────────────
# Public route: send internet traffic through Internet Gateway
resource "aws_route_table" "public_rt" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"            # All traffic (0.0.0.0/0 = internet)
    gateway_id = aws_internet_gateway.igw.id  # Goes through IGW
  }
  tags = { Name = "technova-public-rt" }
}

# Private route: send internet traffic through NAT Gateway
resource "aws_route_table" "private_rt" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.nat.id  # Goes through NAT (one-way)
  }
  tags = { Name = "technova-private-rt" }
}

# ─── SUBNET ASSOCIATIONS ──────────────────────────────────────
# Link each subnet to the correct route table
resource "aws_route_table_association" "public_1" {
  subnet_id      = aws_subnet.public_1.id
  route_table_id = aws_route_table.public_rt.id
}

resource "aws_route_table_association" "public_2" {
  subnet_id      = aws_subnet.public_2.id
  route_table_id = aws_route_table.public_rt.id
}

resource "aws_route_table_association" "private_1" {
  subnet_id      = aws_subnet.private_1.id
  route_table_id = aws_route_table.private_rt.id
}

resource "aws_route_table_association" "private_2" {
  subnet_id      = aws_subnet.private_2.id
  route_table_id = aws_route_table.private_rt.id
}
💸

Cost Warning: NAT Gateways cost ~$32/month plus data transfer costs. For learning, destroy the stack after practice with terraform destroy. In production, this cost is justified by security.

🖥️ Hands-On Steps

  1. Create folder mkdir terraform-vpc && cd terraform-vpc
  2. Create main.tf with the code above. Create outputs.tf to print subnet IDs
  3. Run terraform init then terraform plan — you should see ~14 resources to be created
  4. Run terraform apply -auto-approve
  5. Go to AWS Console → VPC → verify your VPC, subnets, and route tables were created
  6. Launch an EC2 in private subnet — verify it has NO public IP
  7. Run terraform destroy to clean up (NAT Gateway is expensive!)
🎯

Interview Tip: "Explain the difference between Internet Gateway and NAT Gateway." — IGW allows two-way communication (inbound + outbound). NAT Gateway allows private instances to make OUTBOUND connections only. Traffic can't initiate FROM the internet TO a private instance.

Auto Scaling Group with Application Load Balancer

High Availability AWS ASG / ALB Intermediate
📖 The Story

TechNova's app is growing. Last month, during a product launch, traffic spiked 10x and the single web server crashed. Your manager Priya lost sleep. She calls you: "We need the system to automatically add servers when traffic is high and remove them when it's low. And if any server dies, traffic must automatically route to the healthy ones. No downtime, ever." This is Auto Scaling — the heart of every production AWS architecture.

🧠 Concepts Covered
  • Launch Template: The blueprint for new EC2 instances (AMI, type, security groups, user data)
  • Auto Scaling Group (ASG): Maintains a fleet of EC2 instances, adds/removes based on demand
  • Application Load Balancer (ALB): Distributes incoming traffic across all healthy instances
  • Target Group: The group of instances that the ALB routes traffic to
  • Health Checks: ALB constantly checks if instances are alive, removes dead ones
  • Scaling Policies: Rules that trigger scale-out/scale-in (e.g., CPU > 70%)
main.tf — ALB + Auto Scaling HCL 
# ─── APPLICATION LOAD BALANCER ────────────────────────────────
resource "aws_lb" "web_alb" {
  name               = "technova-alb"
  internal           = false          # false = internet-facing (public)
  load_balancer_type = "application"  # ALB works at HTTP/HTTPS layer (Layer 7)
  security_groups    = [aws_security_group.alb_sg.id]
  subnets            = [aws_subnet.public_1.id, aws_subnet.public_2.id]
  # ALB must span at least 2 AZs for high availability

  enable_deletion_protection = false   # true in production to prevent accidents
}

# ─── TARGET GROUP ─────────────────────────────────────────────
# This is the "pool" of instances the ALB will send traffic to
resource "aws_lb_target_group" "web_tg" {
  name     = "technova-web-tg"
  port     = 80          # Traffic is sent to instances on port 80
  protocol = "HTTP"
  vpc_id   = aws_vpc.main.id

  health_check {
    enabled             = true
    path                = "/"         # ALB checks this URL on each instance
    port                = "traffic-port"  # Same port as traffic (80)
    protocol            = "HTTP"
    healthy_threshold   = 2          # 2 consecutive passes = healthy
    unhealthy_threshold = 2          # 2 consecutive fails = unhealthy (removed)
    timeout             = 5          # Wait 5 sec for response
    interval            = 30         # Check every 30 seconds
    matcher             = "200"      # HTTP 200 = healthy response
  }
}

# ─── ALB LISTENER ─────────────────────────────────────────────
# ALB listens on port 80 and forwards to our target group
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.web_alb.arn
  port              = "80"
  protocol          = "HTTP"

  default_action {
    type             = "forward"   # Forward incoming requests to target group
    target_group_arn = aws_lb_target_group.web_tg.arn
  }
}

# ─── LAUNCH TEMPLATE ──────────────────────────────────────────
# Blueprint: when ASG needs a new server, use these settings
resource "aws_launch_template" "web_lt" {
  name_prefix   = "technova-web-"    # Each version gets a numbered suffix
  image_id      = data.aws_ami.amazon_linux.id
  instance_type = "t2.micro"

  network_interfaces {
    associate_public_ip_address = true
    security_groups             = [aws_security_group.web_sg.id]
  }

  user_data = base64encode(<<-EOF
    #!/bin/bash
    yum update -y
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    # Get instance ID from metadata service
    INSTANCE_ID=$(curl -s http://169.254.169.254/latest/meta-data/instance-id)
    echo "<h1>Hello from TechNova! Server: $INSTANCE_ID</h1>" > /var/www/html/index.html
  EOF)
  # user_data must be base64 encoded in launch templates

  lifecycle {
    create_before_destroy = true   # Deploy new version before destroying old
  }
}

# ─── AUTO SCALING GROUP ───────────────────────────────────────
resource "aws_autoscaling_group" "web_asg" {
  name                = "technova-web-asg"
  desired_capacity    = 2       # Start with 2 instances
  max_size            = 6       # Scale up to max 6 instances
  min_size            = 1       # Always keep at least 1 instance running
  vpc_zone_identifier = [aws_subnet.public_1.id, aws_subnet.public_2.id]
  # Spread instances across both AZs

  target_group_arns = [aws_lb_target_group.web_tg.arn]
  # Register new instances automatically with the ALB

  health_check_type         = "ELB"  # Use ALB health checks (not just EC2 status)
  health_check_grace_period = 300    # Give new instances 5 min to start up

  launch_template {
    id      = aws_launch_template.web_lt.id
    version = "$Latest"   # Always use the newest template version
  }

  tag {
    key                 = "Name"
    value               = "technova-asg-instance"
    propagate_at_launch = true  # Apply this tag to all launched instances
  }
}

# ─── SCALING POLICY (CPU Based) ───────────────────────────────
resource "aws_autoscaling_policy" "cpu_scaling" {
  name                   = "technova-cpu-scaling"
  autoscaling_group_name = aws_autoscaling_group.web_asg.name
  policy_type            = "TargetTrackingScaling"  # AWS manages scaling automatically

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value = 70.0  # Keep average CPU around 70%
    # If CPU goes above 70%, add servers. If below, remove them.
  }
}
🔍 Key Concepts Explained
internal = false
The ALB is internet-facing (has a public DNS). Set to true for internal load balancers that only apps inside VPC can access.
healthy_threshold = 2
An instance must pass health checks 2 times in a row before being considered "healthy" and receiving traffic.
base64encode()
Launch templates require user_data to be base64 encoded. This built-in Terraform function handles that encoding.
create_before_destroy = true
A lifecycle meta-argument. When updating the launch template, Terraform creates the new one FIRST, then destroys the old one. Prevents downtime.
desired_capacity = 2
ASG always tries to maintain exactly 2 instances. If one crashes, it automatically replaces it.
TargetTrackingScaling
The simplest scaling policy type. You give AWS a target metric value and it automatically adds/removes instances to maintain that target.

🖥️ Hands-On Steps

  1. Build on top of Project 2 — you need the VPC, subnets, and security groups
  2. Add the ALB security group (allow port 80 from internet, allow all from ALB to EC2)
  3. Run terraform apply — wait about 5 minutes for ALB to become active
  4. Get ALB DNS from outputs: terraform output alb_dns_name
  5. Open the ALB URL in browser — you'll see the Apache page
  6. Refresh multiple times — notice the Instance ID changes (different servers!)
  7. Manually terminate one instance in AWS Console — watch ASG replace it automatically
🏆

MNC Interview Answer: When asked "How do you handle zero-downtime deployments?", say: "We use ASG with rolling updates — the launch template is updated, and ASG gradually replaces instances. Combined with ALB health checks, traffic only goes to healthy new instances."

S3 Static Website with CloudFront CDN

AWS S3 CloudFront CDN Static Hosting
📖 The Story

TechNova's marketing team built a React app for their product launch. The frontend developer says: "We don't need a server — it's just static HTML, CSS, and JS files. But the CEO says it must load in under 1 second globally. Users in Mumbai, London, and New York are all complaining about slow load times." The answer: S3 for storage + CloudFront CDN to cache content at 400+ edge locations worldwide. This setup is used by Netflix, Airbnb, and thousands of MNCs.

🧠 Concepts Covered
  • S3 Bucket: Object storage — stores files (HTML, CSS, JS, images)
  • S3 Static Website: S3 can serve files as a website with a URL
  • CloudFront Distribution: AWS's CDN — caches your content at edge locations near users
  • Origin Access Control (OAC): Locks S3 bucket — ONLY CloudFront can read it (not public)
  • Bucket Policy: JSON policy controlling who can access your S3 bucket
  • Cache Behaviors: Rules on how long CloudFront caches different file types
main.tf — S3 + CloudFront HCL 
# ─── S3 BUCKET ────────────────────────────────────────────────
resource "aws_s3_bucket" "website" {
  bucket = "technova-website-${random_id.suffix.hex}"
  # S3 bucket names must be globally unique — add random suffix
}

# Generate random 4-character suffix for unique bucket name
resource "random_id" "suffix" {
  byte_length = 4
}

# Block ALL public access — only CloudFront can access this bucket
resource "aws_s3_bucket_public_access_block" "website" {
  bucket                  = aws_s3_bucket.website.id
  block_public_acls       = true   # Block public ACLs
  block_public_policy     = true   # Block public policies
  ignore_public_acls      = true   # Ignore any public ACLs
  restrict_public_buckets = true   # Restrict public bucket access
}

# Upload the index.html file to S3
resource "aws_s3_object" "index" {
  bucket       = aws_s3_bucket.website.id
  key          = "index.html"             # The path inside the bucket
  source       = "./website/index.html"  # Local file on your laptop
  content_type = "text/html"             # MIME type — browser renders as HTML
  etag         = filemd5("./website/index.html")
  # etag detects file changes so Terraform re-uploads when content changes
}

# ─── CLOUDFRONT ORIGIN ACCESS CONTROL ────────────────────────
resource "aws_cloudfront_origin_access_control" "oac" {
  name                              = "technova-oac"
  origin_access_control_origin_type = "s3"
  signing_behavior                  = "always"   # Always sign requests to S3
  signing_protocol                  = "sigv4"    # AWS Signature Version 4
}

# ─── CLOUDFRONT DISTRIBUTION ──────────────────────────────────
resource "aws_cloudfront_distribution" "cdn" {
  enabled             = true
  default_root_object = "index.html"   # When user visits /, serve this file

  origin {
    domain_name              = aws_s3_bucket.website.bucket_regional_domain_name
    origin_id                = "S3Origin"   # A name to identify this origin

Remote State Management with S3 + DynamoDB Locking

State Management Team Collaboration Advanced
📖 The Story

TechNova now has 5 DevOps engineers. Yesterday, two engineers (Raj and Priya) both ran terraform apply at the same time on the same infrastructure. The state file on their local laptops was different — they created duplicate resources and broke production. Your senior architect Vijay calls you: "We need a SINGLE source of truth for state that all engineers share. And when one person is applying, others must be LOCKED OUT. 🧠 Concepts Covered
  • Remote Backend: Store state file on S3 instead of local disk — shared by all team members
  • State Locking: DynamoDB table acts as a lock — only one terraform apply at a time
  • State Encryption: S3 server-side encryption protects sensitive data in state
  • Versioning: S3 versioning keeps history of state files — you can roll back
  • Backend Configuration: The backend block in Terraform settings
  • terraform state commands: list, show, mv, rm — state management tools
backend-setup/main.tf — Create the backend infrastructure first HCL

  # Include account ID to make bucket name globally unique
}

# Get current AWS account details
data "aws_caller_identity" "current" {}

    status = "Enabled"   # Every state file change creates a new version

  ignore_public_acls      = true
  restrict_public_buckets = true

  hash_key     = "LockID"            # MUST be "LockID" — Terraform requires this exact name

🔍 Key State Commands
terraform state list
Lists all resources tracked in the state file. Use to verify what Terraform knows about.
terraform state show aws_instance.web
Shows all attributes of a specific resource as stored in state. Useful for debugging.
terraform state mv old.name new.name
Renames a resource in state without recreating it. Use when refactoring code.

Removes a resource from state WITHOUT deleting it in AWS. Use when you want Terraform to "forget" about a resource.

Manually release a stuck lock. Only use if you're SURE no other apply is running.

🧠 Concepts Covered
  • Terraform Workspace: Multiple named state files for the same code — isolated environments
  • terraform.workspace: Built-in variable that returns current workspace name ("dev", "prod")
  • Variable Maps: Using lookup() to return different values based on workspace
  • locals block: Local values computed from other variables — useful for environment logic
  • Conditional expressions: condition ? true_value : false_value
  • for_each on maps: Create multiple resources from a map of configurations
main.tf — One codebase, three environments HCL 
# ─── ENVIRONMENT CONFIGURATION MAP ────────────────────────────
# All environment-specific values are defined in ONE place
locals {
  env = terraform.workspace   # Returns "dev", "staging", or "prod"

  # Map: environment → configuration values
  env_config = {
    dev = {
      instance_type    = "t2.micro"
      instance_count   = 1
      rds_class        = "db.t3.micro"
      multi_az         = false         # Dev doesn't need Multi-AZ
      enable_backups   = false
      retention_period = 1
    }
    staging = {
      instance_type    = "t3.medium"
      instance_count   = 2
      rds_class        = "db.t3.small"
      multi_az         = false
      enable_backups   = true
      retention_period = 3
    }
    prod = {
      instance_type    = "t3.large"
      instance_count   = 4
      rds_class        = "db.r5.large"
      multi_az         = true          # Prod MUST have Multi-AZ
      enable_backups   = true
      retention_period = 30            # 30-day backup retention in prod
    }
  }

  # Fetch config for current environment
  config = local.env_config[local.env]
}

# ─── EC2 INSTANCES (count varies by environment) ──────────────
resource "aws_instance" "web" {
  count         = local.config.instance_count  # 1 in dev, 2 in staging, 4 in prod
  ami           = data.aws_ami.amazon_linux.id
  instance_type = local.config.instance_type  # t2.micro, t3.medium, or t3.large

  tags = {
    Name        = "technova-${local.env}-web-${count.index + 1}"
    Environment = local.env
  }
}

# ─── CONDITIONAL RESOURCE ─────────────────────────────────────
# Only create WAF in production (expensive, not needed in dev)
resource "aws_wafv2_web_acl" "main" {
  count = local.env == "prod" ? 1 : 0
  # count = 1 if prod → creates resource
  # count = 0 if dev/staging → skips resource

  name  = "technova-prod-waf"
  scope = "REGIONAL"
  default_action { allow {} }
  visibility_config {
    cloudwatch_metrics_enabled = true
    metric_name                = "technova-waf"
    sampled_requests_enabled   = true
  }
}

# ─── RDS with environment-specific settings ───────────────────
resource "aws_db_instance" "main" {
  identifier              = "technova-${local.env}-db"

  engine_version          = "8.0"

  backup_retention_period = local.config.retention_period

  allocated_storage   = 20
  db_name             = "technova"
  username            = "admin"
  password            = var.db_password
  skip_final_snapshot = local.env != "prod"
  # Skip snapshot for dev/staging, take snapshot for prod

  # IMPORTANT: Each workspace has its own state file, so
  # dev DB and prod DB are completely independent resources
}

main.tf — Lambda + API Gateway HCL 
# ─── ZIP THE LAMBDA CODE ──────────────────────────────────────
# Terraform packages your code into a zip automatically
data "archive_file" "lambda_zip" {
  type        = "zip"
  source_dir  = "${path.module}/src"  # Your Python/Node.js code lives here
  output_path = "${path.module}/lambda.zip"  # Output zip file

IAM Roles, Policies & Least Privilege Security

IAM Security Access Control Critical
📖 The Story

TechNova's security team ran an AWS audit. The findings were alarming: "Developer IAM users have AdministratorAccess. A compromised developer credential could delete your entire AWS account. Intern accounts have the same access as senior engineers. EC2 instances use hardcoded access keys in the code — if that code is pushed to GitHub, it's a breach." The auditor issued a stern warning. You need to implement proper IAM with least-privilege principle — each user/service gets ONLY the permissions they absolutely need.

🧠 Concepts Covered
  • IAM User: A person identity in AWS — avoid using root account!
  • IAM Group: Bundle users together and assign permissions to the group
  • IAM Role: An identity assumed by services (EC2, Lambda) — no permanent credentials
  • IAM Policy: JSON document defining allowed/denied actions on resources
  • Instance Profile: Wraps an IAM role so EC2 can assume it
  • Least Privilege: Give only the exact permissions needed, nothing more
  • Policy Conditions: Restrict policies by IP, time, MFA, tags

# ─── DEVELOPER POLICY ─────────────────────────────────────────
# Developers can deploy apps but NOT touch networking or IAM
resource "aws_iam_policy" "developer_policy" {
  name        = "technova-developer-policy"
  description = "Allows developers to deploy apps, not manage infra"

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        # Allow: specific EC2 actions (read + instance management)
        Sid    = "EC2ReadAndDeploy"
        Effect = "Allow"
        Action = [
          "ec2:Describe*",         # Read all EC2 resources
          "ec2:StartInstances",
          "ec2:StopInstances",
          "ec2:RebootInstances"
        ]
        Resource = "*"
        Condition = {
          StringEquals = {
            "ec2:ResourceTag/Environment" = ["dev", "staging"]
            # ONLY allowed in dev/staging — cannot touch production!
          }
        }
      },
      {
        # Allow: S3 access for deployment artifacts
        Sid    = "S3DeploymentAccess"
        Effect = "Allow"
        Action = ["s3:GetObject", "s3:PutObject", "s3:ListBucket"]
        Resource = [
          "arn:aws:s3:::technova-deployments-*",
          "arn:aws:s3:::technova-deployments-*/*"
        ]
      },
      {
        # DENY: Explicitly deny high-risk actions
        Sid    = "DenyDangerousActions"
        Effect = "Deny"    # Explicit Deny OVERRIDES any Allow
        Action = [
          "iam:*",                 # Cannot touch IAM
          "organizations:*",       # Cannot manage org
          "ec2:DeleteVpc",
          "ec2:DeleteSubnet"
        ]
        Resource = "*"
      }
    ]
  })
}

🔍 IAM Core Rules
Effect = "Deny"
Explicit Deny ALWAYS wins over any Allow. Even if another policy allows the action, a Deny will block it. Use Deny for critical guardrails.
ec2:Describe*
The wildcard * matches anything. Describe* means DescribeInstances, DescribeVpcs, DescribeSubnets, etc. — all read-only Describe actions.
aws_iam_instance_profile
EC2 cannot directly use an IAM role — it needs an Instance Profile as a container. The profile is what you attach to the EC2 instance.
sts:AssumeRole
STS = Security Token Service. AssumeRole = request temporary credentials for the specified role. The trust policy controls WHO can assume the role.
