A raw landing zone where source data lands unmodified. All transformations happen here before touching the DW.

📅

Load only new/changed rows using a high-watermark timestamp column instead of truncating and reloading all data daily.

An artificial primary key (IDENTITY column) used in the DW, separate from business keys, to handle SCD and joins efficiently.

🚫

Using ROW_NUMBER() with PARTITION BY to eliminate duplicate records that arrive from resent source files.

SCD Type 2 Stored Procedure

T-SQL — SCD Type 2
CREATE PROCEDURE SP_LoadDim_Product
AS
BEGIN
    SET NOCOUNT ON;

    -- Step 1: Expire changed products (SCD Type 2)
    UPDATE dw.Dim_Product
    SET    EffectiveTo = CAST(GETDATE() AS DATE) - 1,
           IsCurrent   = 0
    FROM   dw.Dim_Product dp
    INNER JOIN stg.Products sp
        ON dp.ProductID = sp.ProductID
       AND dp.IsCurrent = 1
    WHERE dp.UnitPrice <> sp.UnitPrice
       OR dp.Category  <> sp.Category;

    -- Step 2: Insert new / updated records
    INSERT INTO dw.Dim_Product
           (ProductID, ProductName, Category, UnitPrice, EffectiveFrom, EffectiveTo, IsCurrent)
    SELECT sp.ProductID, sp.ProductName, sp.Category, sp.UnitPrice,
           CAST(GETDATE() AS DATE),
           '9999-12-31',
           1
    FROM   stg.Products sp
    WHERE  NOT EXISTS (
               SELECT 1 FROM dw.Dim_Product dp
               WHERE dp.ProductID = sp.ProductID
               AND   dp.IsCurrent = 1
           );
END;

T-SQL — Dedup
WITH Ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY TransactionID, StoreID, SaleDate
               ORDER BY     StageLoadDate DESC
           ) AS rn
    FROM   stg.StagingSales
)
DELETE FROM Ranked WHERE rn > 1;
BasicWhat is the difference between OLTP and OLAP?
OLTP (Online Transaction Processing) handles day-to-day operations — fast reads/writes for single rows (store POS systems). OLAP (Online Analytical Processing) is optimized for analytical queries that aggregate millions of rows — the data warehouse. OLTP is normalized (3NF) to reduce redundancy; OLAP uses denormalized star/snowflake schemas for query speed.
BasicWhat are SCD Type 1, Type 2, and Type 3?
Type 1: Overwrite old value — no history kept. Use when history doesn't matter (e.g., correcting a typo). Type 2: Insert new row with effective dates — full history retained. Use when history matters (e.g., product price changes). Type 3: Add a new column for the previous value — only one level of history. Use when you need to compare current vs. previous value easily.
IntermediateHow would you handle duplicate records in an ETL pipeline?
I use ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY load_date DESC) to rank rows. Only rows with rn=1 are inserted. Alternatively, use MERGE statements or a hash-based dedup where I compute a CHECKSUM of all business columns and store it — if the same hash exists, skip the row. For SSIS, the Sort + Remove Duplicates transformation works for stream-based dedup.
IntermediateWhat is a high-watermark pattern and why is it used?
A high-watermark is the last successfully processed value (usually a timestamp or ID) stored in a control table. On each run, the ETL reads only records WHERE LastModifiedDate > @lastWatermark. This enables incremental loads — avoiding full table scans on billions of rows. After a successful load, the watermark is updated. It's a critical optimization for large-scale ETL.
AdvancedHow would you redesign this pipeline if the store files arrived 3 hours late?
Implement a retry mechanism with SQL Server Agent: check file arrival in a loop with WAITFOR DELAY, or use a file watcher event (SSIS File System Watcher). Build a dependency table tracking which stores have reported. If a store is missing past a cutoff (e.g., 4 AM), flag it in the ETL_Log and send an alert to operations. The fact table load should be idempotent — using MERGE or DELETE+INSERT based on load date — so late-arriving data can be reprocessed safely without duplication.
AdvancedHow do you handle schema drift in source files?
Schema drift (unexpected columns/types) in flat files is handled by: 1) Loading everything to a staging table with all VARCHAR columns first — never reject raw data. 2) Using a metadata-driven mapping table that maps source column names to target columns — if a column is renamed, update the mapping table without code change. 3) Adding data profiling queries that alert when unexpected nulls, value ranges, or new column counts appear. 4) Versioning your SSIS packages and source mappings in source control (Azure DevOps).

MERGE Upsert Statement

T-SQL — MERGE
MERGE dbo.MasterEmployee AS target
USING (
    SELECT NormalizedEmail, FullName, Department,
           PhoneClean, DOJStd, Salary, SourceSystem
    FROM   stg.CleanedEmployees
) AS source
    ON target.NormalizedEmail = source.NormalizedEmail
WHEN MATCHED AND (
    target.FullName    <> source.FullName   OR
    target.Department  <> source.Department OR
    target.Phone       <> source.PhoneClean
)
THEN UPDATE SET
    target.FullName    = source.FullName,
    target.Department  = source.Department,
    target.Phone       = source.PhoneClean,
    target.ModifiedDate = GETDATE()
WHEN NOT MATCHED BY TARGET THEN
    INSERT (Email, FullName, Department, Phone, DOJ, Salary, SourceSystem, CreatedDate)
    VALUES (source.NormalizedEmail, source.FullName, source.Department,
            source.PhoneClean, source.DOJStd, source.Salary,
            source.SourceSystem, GETDATE())
WHEN NOT MATCHED BY SOURCE THEN
    UPDATE SET target.IsActive = 0;  -- soft delete
BasicWhat is the MERGE statement and when do you use it?
MERGE is a SQL Server DML statement that performs INSERT, UPDATE, and DELETE operations in a single pass based on join conditions. It's ideal for ETL when you need to synchronize a target table with a source — new records are inserted, changed records are updated, and records in the target but not in the source can be deleted or soft-deleted. It's atomic, meaning all operations are wrapped in an implicit transaction.
IntermediateHow do you handle PII data in an ETL pipeline?
PII (Personally Identifiable Information) like salary, SSN, and phone numbers need protection: 1) Data Masking — use SQL Server Dynamic Data Masking to show masked values to unauthorized users. 2) Encryption — Always Encrypted ensures data is encrypted at rest and in transit; only authorized apps with the key can decrypt. 3) Tokenization — replace real values with tokens in the DW, keep mapping only in a secure vault. 4) Access Controls — row-level security (RLS) in SQL Server. In the ETL itself, never write PII to log files, and use parameterized queries to prevent SQL injection.
AdvancedHow would you validate data quality before loading into the master table?
I implement a "quality gate" pattern: 1) Run statistical profiling queries (COUNT of nulls, value distributions, min/max ranges) and compare against expected baselines. 2) Create a DataQuality_Rules table with rules like "Email must match regex pattern", "Salary must be between 0 and 10,000,000". 3) Validate each row against these rules and route failures to a Rejected_Records table with a rejection reason. 4) Only load rows that pass all rules. 5) If rejection rate exceeds a threshold (e.g., >5%), abort the load and alert. This is the "control break" pattern. In SSIS, use a Conditional Split to route invalid rows to an error output.

Fraud Detection with Window Functions

T-SQL — Fraud Rules
-- Flag accounts with >3 failed attempts before success
WITH AttemptPatterns AS (
    SELECT
        AccountID,
        TransactionID,
        Status,
        TransactionDT,
        SUM(CASE WHEN Status = 'FAILED' THEN 1 ELSE 0 END)
            OVER (PARTITION BY AccountID
                  ORDER BY TransactionDT
                  ROWS BETWEEN 5 PRECEDING AND CURRENT ROW
            ) AS RecentFailures
    FROM stg.Transactions
),
RollingSum AS (
    SELECT
        AccountID,
        TransactionID,
        Amount,
        SUM(Amount) OVER (
            PARTITION BY AccountID
            ORDER BY TransactionDT
            RANGE BETWEEN
                INTERVAL '24 HOURS' PRECEDING AND CURRENT ROW
        ) AS Rolling24HrTotal
    FROM stg.Transactions
    WHERE TransactionType = 'CASH'
)

INSERT INTO dbo.Fraud_Alerts (AccountID, TransactionID, RuleCode, AlertDate)
SELECT
    ap.AccountID,
    ap.TransactionID,
    'RULE-003: Multiple Failures Before Success',
    GETDATE()
FROM AttemptPatterns ap
WHERE ap.RecentFailures >= 3
AND   ap.Status = 'SUCCESS';

T-SQL — Partitioning
-- Partition Function: one partition per month
CREATE PARTITION FUNCTION PF_Monthly (DATE)
AS RANGE RIGHT FOR VALUES (
    '2024-01-01', '2024-02-01', '2024-03-01',
    '2024-04-01', '2024-05-01', '2024-06-01'
);

-- Partition Scheme: all partitions on PRIMARY
CREATE PARTITION SCHEME PS_Monthly
AS PARTITION PF_Monthly ALL TO ([PRIMARY]);

-- Partitioned Fact Table with Columnstore Index
CREATE TABLE Fact_Transactions (
    TransactionID  BIGINT        NOT NULL,
    AccountID      VARCHAR(20)  NOT NULL,
    TransactionDate DATE        NOT NULL,
    Amount         DECIMAL(18,2) NOT NULL,
    TxType         VARCHAR(20)  NOT NULL,
    IsFlagged      BIT           DEFAULT 0
) ON PS_Monthly(TransactionDate);

-- Clustered Columnstore for analytics
CREATE CLUSTERED COLUMNSTORE INDEX CCI_Fact_Transactions
ON Fact_Transactions;
BasicWhat is table partitioning and why is it used in ETL?
Table partitioning divides a large table into smaller, manageable pieces based on a partition key (usually a date column). Physically, each partition can reside in a separate filegroup. Benefits: 1) Partition elimination — queries with a date filter only scan the relevant partition, not the whole table. 2) Partition switching — loading a new month's data by swapping a staging table's partition in is near-instantaneous (metadata-only operation). 3) Maintenance — rebuild indexes on one partition without locking others. In banking with 5M transactions/day, partitioning is essential for EOD performance.
IntermediateWhat is a columnstore index and how does it differ from a rowstore?
Traditional rowstore indexes store data row by row (good for OLTP — fetch one row quickly). Columnstore indexes store data column by column: all values of a column are stored together. For analytics (SUM, AVG, GROUP BY on millions of rows), only the needed columns are read from disk. SQL Server also applies batch mode execution and compression, giving 5–10x storage reduction and up to 100x faster analytical queries. In ETL, clustered columnstore indexes on fact tables dramatically speed up aggregation queries but have slower single-row inserts (use delta stores for this).
AdvancedHow do you handle late-arriving facts in a financial ETL?
Late-arriving facts (transactions logged 1-2 hours after actual occurrence) break watermark-based incremental loads. Solutions: 1) Overlap window: always reprocess the last N hours of data (e.g., 4 hours) on each run. Use MERGE so that late arrivals update existing records rather than creating duplicates. 2) Event time vs. processing time: store both TransactionTimestamp (event time) and LoadTimestamp (processing time). Use TransactionTimestamp for business logic, LoadTimestamp for ETL incremental control. 3) Staging buffer: hold late-arriving rows in a buffer table for up to 24 hours, then reprocess. 4) Log all late arrivals in an ETL_LateArrivals audit table for SLA reporting.

IntermediateWhat is a dead letter queue in ETL and how do you implement it?

BasicWhat is SOUNDEX in SQL Server and when is it useful?
SOUNDEX() returns a four-character code that represents the phonetic sound of a word — words that sound similar get the same code. Example: SOUNDEX('Smith') = SOUNDEX('Smyth') = 'S530'. Useful in ETL for fuzzy matching of names across systems where spelling variations exist. Limitations: works best for English words, short (4-char) code can create false positives. For production use, combine SOUNDEX with other matching criteria (DOB, postal code) to reduce false matches.
IntermediateWhat is Dynamic Data Masking in SQL Server?
DDM is a feature that obscures sensitive data to unauthorized users at query time — without changing the stored data. You define masking functions on columns: default() masks completely (0, x, or dates become 01/01/1900), email() shows first letter + XXX@XXXX.com, partial(prefix, padding, suffix) shows n chars on each side, random(min, max) for numbers. Authorized users with UNMASK permission see actual data. Important: DDM is a presentation-layer protection — a user with sufficient T-SQL knowledge can bypass it by writing workaround queries. For serious security, use column-level encryption or row-level security instead.
AdvancedHow do you build a Master Patient Index (MPI) in SQL Server ETL?
MPI building involves: 1) Blocking: partition records into blocks that might match (same surname, same birth year) to avoid O(n²) comparisons. 2) Scoring: for each candidate pair, compute a score based on matching: exact Aadhar (100pts), SOUNDEX name match (30pts), DOB match (40pts), postal code match (20pts). 3) Threshold: pairs above a high threshold are auto-linked; pairs in a middle range go to a manual review queue. 4) Persistence: store the enterprise-to-source mapping in an ID_CrossReference table. 5) Golden Record: merge attributes from multiple source records (take most recent non-null value for each field). Tools like Microsoft Master Data Services (MDS) can help automate parts of this.

       (DateKey, WarehouseSK, SKUSK, OpeningQty, NetMovement, ClosingQty)

    d.DateKey,
    w.WarehouseSK,
    s.SKUSK,
    prev.ClosingQty                                          AS OpeningQty,

            WHEN 'ISSUE'        THEN -mv.Quantity
            WHEN 'TRANSFER_IN'  THEN  mv.Quantity
            WHEN 'TRANSFER_OUT' THEN -mv.Quantity
            WHEN 'SCRAP'        THEN -mv.Quantity
            ELSE                       0
        END
    ), 0)                                                   AS NetMovement,
    prev.ClosingQty + ISNULL(SUM(...), 0)                 AS ClosingQty
FROM   Dim_Date d
CROSS JOIN Dim_Warehouse w
CROSS JOIN Dim_SKU s
LEFT JOIN  Fact_StockMovements mv
    ON  mv.DateKey      = d.DateKey
    AND mv.WarehouseSK  = w.WarehouseSK
    AND mv.SKUSK        = s.SKUSK
LEFT JOIN  Fact_InventorySnapshot prev
    ON  prev.DateKey    = d.DateKey - 1
    AND prev.WarehouseSK = w.WarehouseSK
    AND prev.SKUSK      = s.SKUSK
WHERE  d.DateKey = CONVERT(INT, CONVERT(VARCHAR, GETDATE(), 112))
GROUP BY d.DateKey, w.WarehouseSK, s.SKUSK, prev.ClosingQty;
BasicWhat is the difference between a transaction fact table and a snapshot fact table?
Transaction fact: one row per event (each stock movement is a row). Grain = individual transaction. Useful for "what happened" queries. Grows unboundedly. Snapshot fact: one row per SKU/warehouse per day showing the state at that point. Grain = one period-end state per dimension combination. Useful for "what is the current/historical state" queries — easy to calculate inventory levels on any past date. In inventory management, you often need both: transactions for movement history, snapshots for current/historical stock levels. Snapshots require periodic ETL even if there were no movements (to carry forward unchanged balances).
IntermediateHow does SQL Server handle timezone conversions?
SQL Server 2016+ has AT TIME ZONE syntax that converts DATETIME or DATETIMEOFFSET values between timezones. Key points: 1) AT TIME ZONE converts a DATETIME (treated as local) to a DATETIMEOFFSET. 2) Chaining two AT TIME ZONE converts from one timezone to another. 3) Timezone names must match Windows timezone names (use sys.time_zone_info to see all valid names). 4) For pre-2016 SQL Server, you need a timezone offset lookup table and manual DATEADD conversion. Best practice: store all timestamps in UTC (DATETIME2 or DATETIMEOFFSET) in the database; convert to local time only at the presentation layer.
AdvancedHow do you handle inventory reconciliation discrepancies in ETL?
Reconciliation discrepancies (calculated stock ≠ system stock) are handled by: 1) Write all discrepancies to a Reconciliation_Exceptions table with SKU, warehouse, calculated qty, system qty, difference, and load date. 2) Classify by severity: <1% difference = rounding/timing (auto-accept); 1-5% = flag for review; >5% = halt the snapshot load for that warehouse, send alert. 3) For timing differences (movements crossing midnight), implement a "grace period" — allow up to 1 hour of late-arriving movements to reconcile before flagging. 4) Provide a manual override table where warehouse managers can submit approved adjustments. The golden rule: never silently correct discrepancies — always log and escalate.

BasicWhat is BULK INSERT and when should you use it?
BULK INSERT is a T-SQL command that loads data from a flat file (CSV, TSV, fixed-width) directly into a SQL Server table with minimal logging. It's 10-100× faster than row-by-row INSERT because it uses the bulk copy API and bypasses standard transaction logging (with TABLOCK hint). Use it for: loading large flat files (logs, data exports), initial data migrations, nightly ETL loads from CSV sources. Key parameters: FIELDTERMINATOR (delimiter), ROWTERMINATOR, FIRSTROW (skip headers), BATCHSIZE (commit frequency), MAXERRORS (tolerate N bad rows). For even faster loads, use the bcp utility or SSIS's OLE DB Destination in fast load mode.
IntermediateHow do you detect anomalies in time series ETL data?
Common approaches: 1) Rolling average + stddev: calculate the 7-day moving average and standard deviation for each hour slot. Flag if current value > mean + 2σ (Z-score > 2). In T-SQL, use AVG() OVER (PARTITION BY HourOfDay ORDER BY DateKey ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING) for rolling stats. 2) Percentage change: flag if current hour's value is >X% higher than the same hour last week. 3) Threshold rules: simple but effective — if error rate > 5%, alert. 4) Isolation Forest: machine learning approach, better suited for Azure ML or Python; results can be loaded back to SQL Server. For most ETL purposes, the rolling average approach with configurable σ multipliers works well and is fully implemented in T-SQL.
AdvancedHow do you optimize ETL for very large log files (multi-GB)?
Multi-GB log processing optimizations: 1) Minimal logging: use BULK INSERT with TABLOCK in SIMPLE or BULK_LOGGED recovery model — reduces transaction log writes by 90%. 2) Pre-filter at source: if possible, use OS-level tools (grep, findstr) to pre-filter the log file to only relevant lines before loading to SQL Server. 3) Parallel file processing: split large files into chunks (e.g., by hour) and run multiple BULK INSERT sessions in parallel — be careful about tempdb contention. 4) Staging table heap: drop all indexes on the staging table before load, add them after. 5) Read-only filegroup: for completed months, move partitions to read-only filegroups — reduces backup size significantly. 6) Page compression: enable on the staging table (log data compresses 5-10× due to repetitive patterns).

BasicWhat is NULLIF and why is it important in ETL calculations?
NULLIF(expr1, expr2) returns NULL if expr1 equals expr2, otherwise returns expr1. In ETL, it's critical for safe division: instead of getting a "divide by zero" error, NULLIF(denominator, 0) converts zero to NULL, and dividing by NULL returns NULL — which is a valid business result meaning "not applicable". Example: CPC = Spend / NULLIF(Clicks, 0) returns NULL when there were no clicks, rather than crashing. Always use NULLIF in ETL when computing derived metrics. Also useful for treating empty strings as NULL: NULLIF(TRIM(ColumnName), '').
IntermediateHow do you handle data restatement in historical fact tables?
Restatement (when a source revises past data) requires the ETL to UPDATE historical rows rather than just INSERT. Implementation: 1) Use MERGE with a business key (CampaignID + Date + Platform) — WHEN MATCHED updates the row, WHEN NOT MATCHED inserts it. 2) Add a RestatementCount column that increments each time a row is updated — helps with auditing. 3) Optionally, use a historical_snapshots table to keep a full copy before each update (insert-only audit trail). 4) Track restatement impact: log which rows changed and by how much — alerts the BI team that historical reports may differ from previous versions.
AdvancedHow would you design a metadata-driven ETL for multiple marketing platforms?
Metadata-driven ETL stores configuration in database tables instead of code. For multi-platform marketing: 1) PlatformConfig table: PlatformID, APIEndpoint, AuthType, PageSize, RateLimit. 2) FieldMapping table: PlatformID, SourceFieldName, TargetFieldName, DataType, TransformationRule. 3) ScheduleConfig table: PlatformID, FrequencyMinutes, LookbackDays. A single generic SSIS/T-SQL framework reads these tables and executes accordingly. Adding a new platform = inserting rows into config tables, zero code changes. This approach scales to 100 platforms with the same codebase. Pair with an ETL_Run_Log table for monitoring all platform loads in one place.

-- Smooth noisy sensor readings with 5-point moving average
WITH SmoothedReadings AS (
    SELECT
        ReadingID,
        MachineID,
        SensorType,
        ReadingTime,
        RawValue,
        AVG(RawValue) OVER (
            PARTITION BY MachineID, SensorType
            ORDER BY     ReadingTime
            ROWS BETWEEN 4 PRECEDING AND CURRENT ROW
        ) AS SmoothedValue,
        STDEV(RawValue) OVER (
            PARTITION BY MachineID, SensorType
            ORDER BY     ReadingTime
            ROWS BETWEEN 29 PRECEDING AND CURRENT ROW
        ) AS Rolling30StdDev
    FROM stg.SensorReadings_Raw
)
INSERT INTO Fact_SensorReadings
       (ReadingID, MachineID, SensorType, ReadingTime, RawValue, SmoothedValue)
SELECT ReadingID, MachineID, SensorType, ReadingTime, RawValue, SmoothedValue
FROM   SmoothedReadings;

Consecutive Anomaly Detection

T-SQL — Anomaly Detection
-- Flag machines with 3+ consecutive above-threshold readings
WITH ThresholdBreaches AS (
    SELECT
        sr.MachineID,
        sr.SensorType,
        sr.ReadingTime,
        sr.SmoothedValue,
        dm.MaxNormalValue,
        CASE WHEN sr.SmoothedValue > dm.MaxNormalValue THEN 1 ELSE 0 END AS IsAboveThreshold
    FROM   Fact_SensorReadings sr
    JOIN   Dim_Machine dm
        ON  dm.MachineID  = sr.MachineID
        AND dm.SensorType = sr.SensorType
),
ConsecutiveBreaches AS (
    SELECT *,
           SUM(IsAboveThreshold) OVER (
               PARTITION BY MachineID, SensorType
               ORDER BY     ReadingTime
               ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
           ) AS ConsecutiveHighCount
    FROM   ThresholdBreaches
)
INSERT INTO Machine_Alerts (MachineID, SensorType, AlertType, DetectedAt)
SELECT DISTINCT MachineID, SensorType, 'CONSECUTIVE_HIGH_READING', GETDATE()
FROM   ConsecutiveBreaches
WHERE  ConsecutiveHighCount = 3
AND NOT EXISTS (
    SELECT 1 FROM Machine_Alerts ma
    WHERE  ma.MachineID  = ConsecutiveBreaches.MachineID
    AND    ma.ResolvedAt IS NULL  -- don't re-alert if open alert exists
);
BasicWhat is the difference between batch ETL and streaming ETL?
Batch ETL: processes data in large chunks at scheduled intervals (hourly, nightly). Data latency = batch interval. Examples: SSIS, T-SQL scheduled jobs. Good for high-volume, lower urgency (daily sales reports). Streaming ETL: processes events individually or in small micro-batches as they arrive, with latency of milliseconds to seconds. Examples: Azure Stream Analytics, Apache Kafka/Flink. Good for real-time alerting (machine anomalies, fraud detection, live dashboards). Choosing between them: if decisions need to be made within seconds → streaming. If hourly/daily is fine → batch. Many architectures combine both (Lambda architecture).
IntermediateWhat are tumbling and sliding windows in streaming analytics?
Tumbling window: fixed-size, non-overlapping windows. Events belong to exactly one window. Example: "average temperature per machine every 5 minutes" — 00:00-00:05, 00:05-00:10, etc. Sliding window: overlapping windows that move with every new event. Example: "did temperature exceed 90°C at least 3 times in any 10-minute period?" — the window slides forward with each reading. In Azure Stream Analytics (SAQL): TUMBLING WINDOW and SLIDING WINDOW are keywords. In SQL Server, simulate with ROWS BETWEEN N PRECEDING AND CURRENT ROW for micro-batch scenarios. Tumbling = efficiency; Sliding = sensitivity for pattern detection.
AdvancedHow would you design a scalable IoT ETL pipeline for 10,000 machines in SQL Server?
At 10K machines × every 5 seconds = 2,000 events/second = 172M events/day, a pure SQL Server solution needs careful design: 1) Table partitioning: partition Fact_SensorReadings by day (not month) — each day gets its own filegroup. 2) In-memory OLTP: use SQL Server's In-Memory tables (SCHEMA_AND_DATA durability) for the hot insert path — 30-40× faster inserts than disk tables. Batch-move to disk tables every 5 minutes. 3) Delayed durability: configure the database with DELAYED_DURABILITY=FORCED — accepts some data loss risk in exchange for 5× write throughput. 4) Columnstore on summary: store raw readings in rowstore for 7 days, then move to a compressed columnstore table for historical analysis. 5) For true scale, front SQL Server with Azure Event Hubs + Stream Analytics — SQL Server becomes the analytics layer, not the intake point. 6) Data archival: automate monthly partition archival to Azure Blob (Parquet format) and drop old partitions to keep the hot table small.
