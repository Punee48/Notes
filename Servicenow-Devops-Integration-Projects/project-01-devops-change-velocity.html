DevOps Change Velocity — Automated Change Request Creation from a Jenkins Pipeline

The foundation project of the whole track. Every later project (Terraform tracking, ArgoCD, Kubernetes, risk-based CAB, rollback automation) builds on top of what you implement here, so we go slowly and explain every moving part.

01 The Production Story — ABC Bank

Knowledge Transfer Session — Principal Architect to New DevOps Engineer

We joined ABC Bank as ServiceNow DevOps Engineers, sitting inside the Enterprise Release Management team.

ABC Bank runs roughly 260 application deployments a month across Core Banking, Internet Banking, and Mobile Banking. Every one of those deployments is supposed to have a Change Request in ServiceNow before it touches production — that is a regulatory requirement, not just good practice, because the bank is audited under RBI/PCI-DSS style controls.

Right now, a developer finishes a Jenkins build, pings the release coordinator on email, and the release coordinator manually opens a Change Request in ServiceNow, copies the build number, guesses the risk level, and routes it for CAB approval. This takes 30–90 minutes per deployment and it is done differently by every coordinator.

Our manager, the Head of Release Engineering, has given us the first milestone: when a Jenkins pipeline finishes a build for the Internet Banking application, ServiceNow must automatically create the Change Request, attach the build and commit details, calculate a risk score, and route it — with zero manual data entry.

This is the DevOps Change Velocity capability. Let's build it end‑to‑end.

02 Business & Customer Requirement

Business Requirement

Every production deployment must have a traceable, auditable Change Request that links directly back to the exact Jenkins build, the exact Git commit, and the exact pipeline that produced it — with no manual re-typing of data.

Customer Requirement (Release Engineering Head)

Cut the average time-to-create-a-CR from ~45 minutes to under 2 minutes, remove human data-entry errors, and give the CAB a consistent, structured view of every change before they approve it.

03 Current Infrastructure, Manual Process, Risks

Current infrastructure

  • Jenkins (on-prem, version 2.4x) running the Internet Banking build and deploy jobs.
  • Git repository (Bitbucket Server) holding the Internet Banking application code.
  • ServiceNow instance with standard change_request, change_task tables, no DevOps plugin activated yet.
  • No MID Server currently needed for this project — Jenkins will call ServiceNow directly over HTTPS through the bank's internal API gateway.

Existing manual process

  1. Developer merges code, Jenkins builds it.
  2. Developer emails the release coordinator with build number and change summary.
  3. Coordinator manually opens a Change Request, types the description, guesses risk (Low/Medium/High) from experience.
  4. Coordinator manually assigns CAB approval group.
  5. After approval, coordinator manually tells the Jenkins team "you're clear to deploy."

Problems

Operational

Inconsistent risk ratings between coordinators; CRs missing build/commit references, which makes rollback investigation slow during an incident.

Compliance / Business Risk

Auditors have flagged that CRs cannot always be traced to a specific artifact — a PCI-DSS control gap. Manual risk rating is not defensible in an audit.

Business impact

Release delays average 40+ minutes per deployment purely on CR paperwork; at 260 deployments a month that is roughly 170+ hours a month of coordinator time, and it is a recurring audit finding.

04 Why ServiceNow DevOps (and why not something else)

Why ServiceNow DevOps Change Velocity specifically: it gives us a native, governed pipeline between the CI/CD tool and the change_request table, with an out-of-the-box orchestration table (sn_devops_orchestration_task) that tracks the pipeline stage, and native "gate" checks so a pipeline can be paused until ServiceNow approves the change. That governance layer is the whole point — it's not just "create a record," it's "control whether the deployment is even allowed to continue."

Alternative solutions considered

AlternativeWhy it was rejected
Custom REST API only (no DevOps plugin)Works for creating the CR, but we would have to build our own orchestration/gate tracking from scratch, and lose native Jenkins plugin support and DORA metrics.
Jenkins post-build email + manual CRThis is the current broken process — no automation, no audit trail linking build to CR.

05 Core Concepts — Explained Before We Touch Code

DevOps Change Velocity — what it is, why it exists, how it works internally

What it is: DevOps Change Velocity is a ServiceNow plugin/capability (sn_devops) that connects CI/CD tools (Jenkins, GitHub Actions, Azure DevOps, GitLab...) to ServiceNow's Change Management process. It listens for pipeline events (build started, build finished, deployment started) and turns them into governed records.

Why it exists: Before this capability, banks either slowed CI/CD down to a crawl (manual CR for every deploy) or skipped governance entirely (fast but not auditable). Change Velocity's goal is literally in the name — keep the *velocity* of DevOps while keeping the *control* of ITSM.

Internal working: The Jenkins/GitHub plugin sends a webhook-style callback to a ServiceNow REST endpoint whenever a pipeline stage changes. ServiceNow writes that event into sn_devops_orchestration_task, correlates it to a "DevOps Change Control" configuration, and — if a Change Request doesn't already exist for that pipeline run — creates one automatically using a template. If a "gate" is configured, the pipeline literally pauses (Jenkins polls a status endpoint) until the Change Request reaches an approved state.

Real banking example: Internet Banking release pipeline — build finishes → orchestration task created → risk calculated → if Low risk, standard change auto-approved in under a minute; if High risk, CR routed to CAB and the Jenkins pipeline literally sits paused on a "Waiting for Change Approval" stage until someone approves it.

Alternative approaches: Build your own middleware (MuleSoft/custom Node service) polling Jenkins and calling the Table API — more flexible, but you lose native gate support and DORA metrics, and you now own an extra integration layer to secure and maintain.

Best practice: Always model risk calculation as its own reusable Script Include (not inline in a Business Rule) so every entry point — Flow, REST API, scheduled job — uses identical logic. We do exactly that below.

Common mistake: Teams often let the CI tool decide the risk level itself and just push it into ServiceNow. That's backwards — ServiceNow (the system of record for risk/compliance) should own the risk calculation, not the pipeline.

Orchestration Task — what it is and why we need a table at all

What it is: A record on sn_devops_orchestration_task represents one execution of one stage of a pipeline (e.g., "Build #482, stage = deploy-to-prod"). It is the glue record between "a thing that happened in Jenkins" and "a thing ServiceNow understands."

Why it exists: A Change Request is too heavy to represent every pipeline event — you don't want 15 CRs for one pipeline run. The orchestration task is the lightweight, high-frequency record; the Change Request is the heavyweight, governed record created (or updated) from it.

Internal working: Each event Jenkins sends becomes one orchestration task row, tagged with a correlation ID (the Jenkins build number + job name). ServiceNow uses that correlation ID to avoid creating a duplicate Change Request if Jenkins retries the callback.

Risk Calculation — what it is and why the CAB cares

What it is: A scoring function that looks at attributes of the deployment (which application, which environment, time of day, past failure rate of this pipeline, size of the change) and outputs Low / Medium / High risk.

Why it exists: A human CAB cannot manually re-evaluate 260 changes a month with consistent judgment. A deterministic score means every change is judged by the same rule, which is exactly what an auditor wants to see.

Real banking example: A deploy to the Internet Banking production environment between 9 AM–6 PM on a weekday is automatically High risk (customer-facing hours); the same deploy at 11 PM on a Saturday, with a clean pipeline history, is Low risk and can be a Standard Change with pre-approval.

07 Complete Solution Design

  • Tool record: a sn_devops_tool record represents the Jenkins instance, holding its base URL and a scoped integration user token.
  • Inbound endpoint: a custom Scripted REST API resource, /api/x_bank/devops/pipeline_event, that Jenkins calls with build metadata as its last pipeline step.
  • Orchestration table: we log every event to sn_devops_orchestration_task so we have full pipeline history even if no CR is created yet.
  • Flow Designer flow: "Create Change from Pipeline Event" — subscribed to the orchestration task's insert, it checks for an existing CR by correlation ID, and if none exists, creates one and calls the Risk Calculator.
  • Script Include: x_bank_devops.RiskCalculator — pure scoring logic, callable from anywhere.
  • Business Rule: on the Change Request table, before insert/update, auto-approves Standard Changes when risk = Low and marks CAB routing when risk ≥ Medium.
  • Gate endpoint: a second Scripted REST resource, /api/x_bank/devops/gate_status, that Jenkins polls before the deploy stage runs.

10 Implementation Step 3 — Risk Calculator Script Include

This is the most important piece of logic in the whole project. It is deliberately written as a reusable Script Include so the Flow, the REST API, and any future scheduled job can all call the same risk logic and get the same answer.

Script Include · x_bank_devops.RiskCalculator (Client callable: false)
var RiskCalculator = Class.create();                          // Defines a new reusable server-side class using ServiceNow's Class.create() pattern
RiskCalculator.prototype = {

    initialize: function() {                                    // Constructor — runs automatically when "new RiskCalculator()" is called
        this.HIGH_RISK_APPS = ['Internet Banking', 'Core Banking', 'ATM Switch']; // Hardcoded list of apps treated as customer-critical; in production this would read from a CMDB attribute instead
    },

    // Main entry point: takes an orchestration task sys_id, returns 'low' | 'medium' | 'high'
    calculateRisk: function(orchestrationTaskSysId) {
        var task = new GlideRecord('sn_devops_orchestration_task');  // Opens a GlideRecord cursor on the orchestration task table
        if (!task.get(orchestrationTaskSysId)) {                     // .get() loads the specific record by sys_id; returns false if not found
            return 'high';                                          // Fail-safe: if we can't even read the task, treat it as High risk so a human reviews it
        }

        var appName = task.getValue('pipeline_name');                // getValue() returns the raw string value (not the display value) of the field — safer for logic than dot-walking
        var score = 0;                                                // Running numeric score; higher = riskier

        if (this._isCustomerFacingApp(appName)) {                    // Calls a private helper method (defined below) to check the app criticality
            score += 40;                                              // Customer-facing apps automatically start with a high baseline score
        }

        if (this._isBusinessHours()) {                                // Checks current bank time against business hours
            score += 30;                                              // Deploying during business hours is riskier because more customers are actively using the system
        }

        var failureRate = this._getRecentFailureRate(appName);        // Looks up how often this pipeline's last 10 deployments failed
        score += Math.round(failureRate * 30);                        // Converts a 0.0–1.0 failure rate into up to 30 additional risk points

        return this._scoreToLabel(score);                             // Converts the final numeric score into a Low/Medium/High label
    },

    _isCustomerFacingApp: function(appName) {                        // Private helper (underscore prefix is a ServiceNow convention meaning "internal use only")
        return this.HIGH_RISK_APPS.indexOf(appName) > -1;             // indexOf() returns -1 if not found; > -1 means the app IS in our critical list
    },

    _isBusinessHours: function() {
        var gdt = new GlideDateTime();                                // Gets the current date/time in the instance's configured time zone
        var hour = gdt.getLocalTime().toString().split(':')[0];       // Extracts just the hour portion (e.g. "14") from the local time string
        var h = parseInt(hour, 10);                                   // Converts the string hour into an actual number for comparison
        return (h >= 9 && h < 18);                                    // Business hours defined as 9 AM to 6 PM, matching ABC Bank's branch/digital-channel peak hours
    },

    _getRecentFailureRate: function(pipelineName) {
        var gr = new GlideAggregate('sn_devops_orchestration_task');  // GlideAggregate lets us run COUNT/SUM/AVG queries efficiently instead of looping over records in script
        gr.addQuery('pipeline_name', pipelineName);                   // Filters to only this pipeline's history
        gr.orderByDesc('sys_created_on');                              // Sorts newest first so we can look at the most recent runs
        gr.setLimit(10);                                               // Only look at the last 10 runs — recent history matters more than all-time history
        gr.addAggregate('COUNT');                                     // Tells GlideAggregate to compute a total row count
        gr.query();                                                    // Executes the query against the database
        var total = 0, failed = 0;
        while (gr.next()) {                                           // Iterates through each matching record
            total++;
            if (gr.getValue('status') == 'failed') {                  // Compares the stage status field to the literal string 'failed'
                failed++;
            }
        }
        return total > 0 ? (failed / total) : 0;                      // Returns a 0.0–1.0 ratio; guards against divide-by-zero when there is no history yet
    },

    _scoreToLabel: function(score) {
        if (score >= 60) return 'high';                                // 60+ points → High risk, must go to CAB
        if (score >= 30) return 'medium';                               // 30–59 points → Medium risk, goes to a lightweight approval
        return 'low';                                                    // Under 30 points → Low risk, eligible for Standard Change auto-approval
    },

    type: 'RiskCalculator'                                             // Required by ServiceNow — tells the platform the class name string, used internally for script reflection
};

Line-by-line: what matters most here

Class.create()

This is ServiceNow's standard pattern for defining a reusable, instantiable server-side object — think of it like a class in Java. Every Script Include you ever write in ServiceNow starts this way.

GlideRecord vs GlideAggregate

GlideRecord is for reading/writing individual records. GlideAggregate is for COUNT/SUM/AVG style queries — much faster than looping through GlideRecord rows when you only need a number, which matters a lot at banking transaction volumes.

getValue() vs dot-walk

task.getValue('pipeline_name') returns the raw stored value. If you instead wrote task.pipeline_name.toString() on a reference field you'd get the sys_id, not the display text — a classic beginner mistake that becomes a production bug under load.

type: 'RiskCalculator'

Every Script Include must end with this line matching the class name exactly. If it's missing or mismatched, the platform throws a runtime error the moment the class is instantiated — this trips up almost everyone the first time.

Production best practice: Notice the score thresholds (30 / 60) and the business-hours window are the only two "magic numbers" in this class. In a real bank implementation, move these into a System Property (x_bank_devops.risk.high_threshold) so Release Management can tune them without a developer touching code.
Common mistake: Calling new RiskCalculator() directly from a Client Script. This class has no client callable flag and touches server tables — it must only ever be called from server-side code (Business Rules, Flow script steps, Scripted REST APIs).

11 Implementation Step 4 — Flow Designer: "Create Change from Pipeline Event"

Flow Designer is where the orchestration event actually becomes a Change Request. We build this as a Record-Triggered Flow.

Flow settingValue
Trigger typeRecord Created on sn_devops_orchestration_task
Conditionstage_name is deploy AND change_request is empty
Run asSystem user (so it works regardless of which integration account triggered the insert)

Flow steps

  1. Look Up Records — search change_request where correlation_id equals the trigger record's correlation_id. This is our duplicate-prevention check.
  2. Flow Logic → If — "Look Up Records returned 0 rows" (no existing CR for this build).
  3. Script Step — call RiskCalculator and store the result in a flow variable risk_level.
  4. Create Record — create a change_request with the fields shown below.
  5. Update Record — write the new Change Request's sys_id back onto the triggering orchestration task's change_request field, closing the loop.
Flow Designer · Script Step "Calculate Risk"
(function execute(inputs, outputs) {
    // inputs.orchestration_task_id is wired in the Flow Designer canvas from the trigger record's sys_id
    var calculator = new RiskCalculator();          // Instantiates the Script Include we just built
    var risk = calculator.calculateRisk(inputs.orchestration_task_id); // Runs the scoring logic against this specific pipeline event
    outputs.risk_level = risk;                        // Publishes the result as a Flow output variable, usable by every later step in this Flow
})(inputs, outputs);

In Flow Designer's Script Step, inputs and outputs are pre-defined objects the platform gives you — you declare which inputs the step expects (here, orchestration_task_id as a Reference to the orchestration task table) and which outputs it produces (risk_level as a String) using the step's configuration panel, not in the script body itself.

Create Record step — field mapping

short_description"Automated deploy — " + trigger.pipeline_name + " build #" + trigger.build_number

Why this matters: The correlation_id field is doing double duty — it's how the Flow prevents duplicate CRs, and it's also the audit trail linking one specific CR to one specific Jenkins build forever. This directly closes the audit gap described in Section 3.

12 Implementation Step 5 — Business Rule: Auto-Approve Low-Risk Standard Changes

We add a "before insert" Business Rule on change_request so Low risk Standard Changes don't sit waiting for a human at all — this is the actual "velocity" part of DevOps Change Velocity.

Business Rule · Auto-Approve Standard Change (before, insert)
(function executeRule(current, previous /*null when async*/) {

    if (current.type != 'standard') {                     // Only Standard Changes are eligible for auto-approval — Normal/Emergency always need a human
        return;                                            // Exits the function immediately, leaving the record untouched, for any non-standard change
    }

    if (current.risk != 'low') {                          // Double-check the risk level even though the Flow already filtered for this — defense in depth
        return;                                             // A Business Rule should never fully trust that upstream logic ran correctly
    }

    current.approval = 'approved';                          // Sets the standard ServiceNow approval state field directly
    current.state = 3;                                       // State 3 = "Scheduled" in the out-of-box change_request state model — ready to implement
    current.work_notes = 'Auto-approved by DevOps Change Velocity: Low risk, Standard Change, correlation_id=' + current.correlation_id; // Leaves a permanent, auditable trail explaining WHY this was approved without a human

})(current, previous);
current / previous

Every Business Rule script receives current (the record being inserted/updated, as a GlideRecord) and previous (the record's prior state — null on insert or on async rules). We only need current here since this fires on insert.

before, insert

Running as a "before" rule means our field changes (approval, state) are written into the same database operation as the insert — no second database round trip, which matters at 260+ changes/month scale.

Common mistake: Doing this logic in an "after" Business Rule and calling current.update() — that causes a second insert trigger cycle and can create infinite-loop risk if you're not careful with conditions. Always prefer "before" rules for same-record field edits.

13 Implementation Step 6 — Scripted REST API: Deployment Gate

This is the endpoint Jenkins polls before it's allowed to run the actual deploy stage. It is the enforcement point — this is what actually stops an unapproved deployment from happening.

Scripted REST Resource · GET /api/x_bank/devops/gate_status
(function process(/*RESTAPIRequest*/ request, /*RESTAPIResponse*/ response) {

    var correlationId = request.queryParams.correlation_id;        // Reads the ?correlation_id=... query string parameter Jenkins sends

    if (!correlationId) {                                           // Guard clause — Jenkins forgot to pass the parameter
        response.setStatus(400);                                     // HTTP 400 = Bad Request, tells Jenkins its call was malformed
        response.setBody({ error: 'correlation_id is required' });   // JSON body explaining exactly what went wrong, so pipeline logs are useful
        return;
    }

    var cr = new GlideRecord('change_request');                     // Opens a GlideRecord on the Change Request table
    cr.addQuery('correlation_id', correlationId);                    // Filters to the exact build this gate check is for
    cr.query();                                                       // Executes the query

    if (!cr.next()) {                                                 // .next() moves the cursor to the first matching row and returns false if none exist
        response.setStatus(404);                                      // HTTP 404 = the Change Request doesn't exist yet (Flow may not have run yet)
        response.setBody({ status: 'not_found' });                    // Jenkins should treat this as "keep waiting / retry", not as a hard failure
        return;
    }

    var approvalState = cr.getValue('approval');                      // Reads the approval field: 'requested', 'approved', 'rejected', etc.
    var gateResponse = {
        change_number: cr.getValue('number'),                         // Human-readable CR number (e.g. CHG0012345), useful in Jenkins console logs
        risk: cr.getValue('risk'),                                     // Echoes the risk level back for visibility in the pipeline log
        status: (approvalState == 'approved') ? 'approved' : 'pending'  // Collapses ServiceNow's approval states into a simple two-value contract for Jenkins
    };

    response.setStatus(200);                                          // HTTP 200 = the check itself succeeded (regardless of approved/pending)
    response.setBody(gateResponse);                                    // Sends the JSON payload back to Jenkins

})(request, response);
request.queryParams

Scripted REST APIs expose query string parameters through this object automatically — you never manually parse the URL string yourself.

response.setStatus / setBody

These two calls together form the entire HTTP response. Always set a meaningful status code — Jenkins pipelines can branch logic on HTTP status alone, so 400 vs 404 vs 200 are not interchangeable here.

Production best practice: This endpoint deliberately never returns a 500 for "not yet approved" — an HTTP 500 would make Jenkins treat the whole pipeline as broken. "Pending" is a normal, expected state, not an error, and the HTTP code should reflect that.

14 Implementation Step 7 — Jenkinsfile

Jenkinsfile · Internet Banking Deploy Pipeline
pipeline {
    agent any
    environment {
        SN_INSTANCE = 'https://abcbank.service-now.com'      // Base URL of the ServiceNow instance, stored as a Jenkins environment variable
        CORR_ID = "internet-banking-${env.BUILD_NUMBER}"      // Builds a unique correlation ID from the job name and Jenkins' own build number
    }
    stages {
        stage('Build') {
            steps { sh 'mvn clean package' }                   // Standard Maven build step for the Internet Banking Java application
        }
        stage('Notify ServiceNow') {
            steps {
                sh """
                curl -X POST "${SN_INSTANCE}/api/x_bank/devops/pipeline_event" \
                  -u "\$SN_USER:\$SN_TOKEN" \
                  -H "Content-Type: application/json" \
                  -d '{
                        "correlation_id": "${CORR_ID}",
                        "pipeline_name": "Internet Banking",
                        "stage_name": "deploy",
                        "build_number": "${env.BUILD_NUMBER}",
                        "build_url": "${env.BUILD_URL}"
                      }'
                """                                              // Sends the pipeline event to our Scripted REST endpoint, triggering the Flow that creates the Change Request
            }
        }
        stage('Wait for Change Approval') {
            steps {
                script {
                    timeout(time: 30, unit: 'MINUTES') {         // Caps how long the pipeline will wait for a human approver before failing the build
                        waitUntil {
                            def resp = sh(
                                script: "curl -s '${SN_INSTANCE}/api/x_bank/devops/gate_status?correlation_id=${CORR_ID}'",
                                returnStdout: true
                            )                                      // Polls our gate_status endpoint and captures its JSON response as a string
                            return resp.contains('"status":"approved"') // Jenkins keeps re-checking on an interval until this condition is true
                        }
                    }
                }
            }
        }
        stage('Deploy to Production') {
            steps { sh './deploy.sh production' }                 // This stage only runs after the previous stage confirms ServiceNow approval — the actual gate enforcement
        }
    }
}
Common mistake: Polling too aggressively (every few seconds) hammers the ServiceNow instance with load, especially across dozens of pipelines. Use Jenkins' waitUntil with a sensible built-in backoff, or better, configure a longer poll interval explicitly — production banking implementations typically poll every 60 seconds, not every 5.

15 Execution Flow — What Actually Happens, Step by Step

  1. Developer merges code → Jenkins "Build" stage compiles the Internet Banking app.
  2. "Notify ServiceNow" stage POSTs the pipeline event to /pipeline_event.
  3. That endpoint (built the same way as the gate endpoint) writes a new row into sn_devops_orchestration_task.
  4. The insert fires our Record-Triggered Flow.
  5. Flow checks for a duplicate CR by correlation_id — finds none.
  6. Flow's Script Step calls RiskCalculator.calculateRisk().
  7. Risk Calculator queries recent pipeline history via GlideAggregate, checks business hours, checks app criticality, returns a label.
  8. Flow creates the Change Request with that risk label and type (Standard or Normal).
  9. The change_request insert fires our "before insert" Business Rule.
  10. If Low risk + Standard → Business Rule auto-approves instantly. If Medium/High → record stays in "Requested" state, routed to CAB per the out-of-box approval engine.
  11. Flow writes the new CR's sys_id back onto the orchestration task, closing the correlation loop.
  12. Jenkins' "Wait for Change Approval" stage polls /gate_status every interval.
  13. Once approval = approved (instantly for Low risk, or after a CAB member approves for Medium/High), the gate endpoint returns status: approved.
  14. Jenkins proceeds to "Deploy to Production."
  15. Post-deployment, a follow-up event (not built in this project — covered in Project 4: Deployment Validation) would close the Change Request automatically.

18 Interview Preparation

Q: How does ServiceNow prevent duplicate Change Requests when a CI/CD webhook fires twice?
A: By using a correlation ID (built from the job name + build number) as a unique business key, and having the Flow do a Look Up Records check before ever creating a new Change Request.
Q: Why calculate risk in ServiceNow instead of letting Jenkins send a risk level?
A: ServiceNow is the system of record for compliance and audit. If the CI tool self-declares risk, the rating isn't independently governed, and an auditor won't accept it as a real control.
Q: A pipeline is stuck forever on "Wait for Change Approval." How do you troubleshoot it?
A: Check the orchestration task for the correlation_id — did the Flow actually create a Change Request? If yes, check the CR's approval state and CAB assignment. If no CR exists, check the Flow's execution log for a failed condition or a script error in the Risk Calculator.
Q: Why is the Business Rule "before insert" instead of "after insert" with a GlideRecord update?
A: "Before" rules modify the record in the same database write — more efficient and avoids re-triggering insert-based Business Rules a second time, which "after" + manual update can accidentally do.
Q: How would you scale this if the bank added 15 more applications and pipelines?
A: The Risk Calculator's hardcoded app list should move to a CMDB attribute (Application Service criticality field) so onboarding a new app is a data change, not a code change — no redeploy needed.
Q: What's the real production incident this design prevents?
A: An unauthorized or unreviewed change reaching Core Banking or Internet Banking production without going through CAB — which is both an operational risk and a direct regulatory violation.

19 Common Mistakes Seen in Real Implementations

  • Putting risk-scoring logic directly inside a Business Rule instead of a Script Include — impossible to reuse or unit test in isolation.
  • Using an admin account as the Jenkins integration user "to make the demo work faster," then forgetting to lock it down before go-live.
  • Forgetting the duplicate-prevention Look Up step in the Flow — causes a new CR on every Jenkins retry, flooding CAB queues.
  • Returning HTTP 500 from the gate endpoint for a normal "pending" state, which makes Jenkins mark healthy pipelines as broken.
  • Not adding a correlation_id field to change_request at design time, then having to retrofit it later once hundreds of CRs already exist without it.
