Core Concepts

☸️ Kubernetes Objects You Must Know for CI/CD

📌 How Kubernetes Fits in CI/CD

In a Kubernetes CI/CD pipeline: your pipeline builds a Docker image and pushes it to ECR, then uses kubectl apply to send a Deployment manifest to Kubernetes. Kubernetes reads the manifest, pulls the new image, and performs a rolling update — replacing old pods with new ones one at a time, with zero downtime.

📦 Pod

The smallest unit in Kubernetes — one or more containers running together on the same node. Your Docker container runs inside a Pod. Pods are ephemeral — they can be killed and restarted at any time. Never manage Pods directly — use a Deployment instead.

🔄 Deployment

Manages a set of identical Pods and ensures a desired number are always running. Handles rolling updates — when you update the image tag, it replaces pods gradually. If a new pod fails to start, it stops the rollout automatically. This is what your CI/CD pipeline updates.

🌐 Service

A stable network endpoint for your Pods. Since pods are ephemeral and get new IPs when restarted, a Service provides a fixed IP and DNS name. A LoadBalancer type Service creates an AWS ALB automatically and routes external traffic to your pods.

🗂️ Namespace

A virtual cluster inside your Kubernetes cluster. Use namespaces to separate environments: cloudmart-dev, cloudmart-staging, cloudmart-prod — all on one cluster but fully isolated. Each has its own resources, secrets, and RBAC permissions.

Kubernetes Manifests

📄 Kubernetes Deployment Manifest — Word by Word

k8s/deployment.yaml — CloudMart App DeploymentYAML
# ─── apiVersion ────────────────────────────────────────────────────────
# Kubernetes API group and version for this resource type
# "apps/v1" is the stable API for Deployments
apiVersion: apps/v1

kind: Deployment
# "kind" → what type of Kubernetes object this file describes
# Other kinds: Pod, Service, ConfigMap, Secret, HorizontalPodAutoscaler

metadata:
  name: cloudmart-app
    # The name of this Deployment — used in kubectl commands
  namespace: cloudmart-prod
    # Which namespace this belongs to — isolates it from dev/staging
  labels:
    app: cloudmart
    tier: frontend
    version: v2.4.1
    # Labels are key-value pairs used to identify and select resources

spec:
    # "spec" → the desired state — what you WANT Kubernetes to maintain

  replicas: 3
    # "replicas" → run exactly 3 identical pods at all times
  # If one pod crashes, Kubernetes immediately starts a replacement

  selector:
    matchLabels:
      app: cloudmart
    # "selector" → tells the Deployment which pods it manages
  # It manages all pods with label "app: cloudmart"

  strategy:
    type: RollingUpdate
        # "RollingUpdate" → update pods one by one, not all at once
    # Ensures at least some pods are always running during deployment
    rollingUpdate:
      maxSurge: 1
            # Allow 1 EXTRA pod above the desired 3 during the update
      # So during rollout: up to 4 pods can run temporarily
      maxUnavailable: 0
            # ZERO pods can be unavailable — guarantees zero downtime
      # New pod must be READY before old pod is terminated

  template:
        # "template" → the blueprint for each Pod this Deployment creates
    metadata:
      labels:
        app: cloudmart
                # Pods inherit these labels — must match selector.matchLabels above
    spec:
      containers:
      - name: cloudmart
        image: 123456789.dkr.ecr.ap-south-1.amazonaws.com/cloudmart-app:IMAGE_TAG
                # IMAGE_TAG is replaced by the pipeline at deploy time (see below)
        # This is the Docker image from ECR — with a specific commit SHA tag

        ports:
        - containerPort: 3000
                    # The port the container listens on inside the pod

        resources:
          requests:
            memory: "128Mi"
            cpu:    "100m"
                    # "requests" → minimum guaranteed resources
          # "100m" = 100 millicores = 0.1 CPU cores
          # Kubernetes uses this for scheduling — placing pod on a node
          limits:
            memory: "256Mi"
            cpu:    "500m"
                    # "limits" → maximum allowed — pod killed if it exceeds memory limit
          # Always set both requests AND limits in production

        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 15
          periodSeconds:       10
                    # "livenessProbe" → Kubernetes checks /health every 10 seconds
          # If it fails 3 times in a row → pod is considered dead → RESTART IT
          # "initialDelaySeconds: 15" → wait 15s before first check (app start time)

        readinessProbe:
          httpGet:
            path: /ready
            port: 3000
          initialDelaySeconds: 5
          periodSeconds:       5
                    # "readinessProbe" → checks if pod is READY TO RECEIVE TRAFFIC
          # During rolling update: new pod is NOT added to Service until ready
          # This is what prevents "maxUnavailable: 0" from causing downtime

        env:
        - name:  NODE_ENV
          value: production
        - name:  DB_HOST
          valueFrom:
            secretKeyRef:
              name: cloudmart-db-secret
              key:  host
                    # Read env var from a Kubernetes Secret (not hardcoded)
          # Kubernetes Secrets store base64-encoded values — more secure than plain YAML

⚙️ Deploying to EKS from GitHub Actions

.github/workflows/deploy-eks.ymlYAML
  deploy-to-eks:
    name: Deploy to AWS EKS
    runs-on: ubuntu-latest
    needs: build-and-push

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.EKS_DEPLOY_ROLE_ARN }}
          aws-region: ap-south-1

      - name: Update kubeconfig for EKS cluster
        run: |
          aws eks update-kubeconfig \
            --name cloudmart-prod-cluster \
            --region ap-south-1
                    # "update-kubeconfig" → writes ~/.kube/config so kubectl can connect
          # to the EKS cluster using the current AWS credentials (IAM role)

      - name: Replace image tag in manifest
        run: |
          sed -i 's|IMAGE_TAG|${{ github.sha }}|g' k8s/deployment.yaml
                    # "sed -i" → sed = stream editor, -i = in-place (edit the file)
          # Replaces the placeholder "IMAGE_TAG" in deployment.yaml
          # with the actual commit SHA from this pipeline run
          # e.g. IMAGE_TAG → a3f9b2c8d1e4f5a6

      - name: Apply Kubernetes manifests
        run: |
          kubectl apply -f k8s/namespace.yaml
          kubectl apply -f k8s/deployment.yaml
          kubectl apply -f k8s/service.yaml
                    # "kubectl apply -f" → send these YAML manifests to Kubernetes API
          # "-f" = from file. Kubernetes reads the desired state and reconciles
          # If Deployment already exists → UPDATE it (rolling update)
          # If it doesn't exist → CREATE it

      - name: Wait for rollout to complete
        run: |
          kubectl rollout status deployment/cloudmart-app \
            --namespace cloudmart-prod \
            --timeout=5m
                    # "kubectl rollout status" → watches the deployment and waits
          # until all pods have been updated and are Running + Ready
          # "--timeout=5m" → if not done in 5 minutes → command fails → pipeline fails
          # This is critical: without this, pipeline says "success" even if pods crash

      - name: Rollback on failure
        if: failure()
                # "if: failure()" → only runs if previous step failed
        run: |
          kubectl rollout undo deployment/cloudmart-app \
            --namespace cloudmart-prod
          echo "Rollback complete — previous version restored"

k8s/hpa.yaml — Auto-scaling for Black FridayYAML
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cloudmart-hpa
  namespace: cloudmart-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind:       Deployment
    name:       cloudmart-app
  minReplicas: 3
    # Never scale below 3 pods — always have minimum capacity
  maxReplicas: 20
    # Maximum 20 pods — protects against runaway scaling costs
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type:               Utilization
        averageUtilization: 70
                # "averageUtilization: 70" → when average CPU across all pods > 70%
        # Kubernetes automatically adds more pods
        # When CPU drops back below 70% → Kubernetes removes extra pods (after cool-down)

🎯 Chapter 13 Interview Questions

📋 Kubernetes in CI/CD — Frequently Asked

These come up in every DevOps/Cloud interview where Kubernetes is in the JD.

Q1

How does a CI/CD pipeline deploy an application to Kubernetes?

The pipeline builds a Docker image and pushes it to a registry like AWS ECR with a unique tag (git SHA). Then the pipeline uses kubectl apply with a Deployment YAML manifest — the image tag in the manifest is updated to the new version using sed or a tool like kustomize. Kubernetes performs a rolling update — replacing old pods with new ones while ensuring the readiness probe passes before removing old pods. The pipeline then runs kubectl rollout status to wait for all pods to be Ready. If the rollout fails, the pipeline calls kubectl rollout undo for automatic rollback.

Q2

What is the difference between livenessProbe and readinessProbe?

A livenessProbe checks whether the container is alive (healthy). If it fails, Kubernetes restarts the container. It answers: "is this process running or stuck?" A readinessProbe checks whether the container is ready to accept traffic. If it fails, Kubernetes removes the pod from the Service's endpoints — no traffic is routed to it — but does not restart it. It answers: "is this pod ready to serve requests?" In CI/CD, the readinessProbe is critical for rolling updates — Kubernetes ensures the new pod passes its readiness check before routing traffic to it and before terminating the old pod.

💬 The key distinction: liveness = restart the pod. Readiness = remove from traffic. Most candidates confuse these.

Q3

What is the difference between resource requests and limits in Kubernetes?

Requests are the minimum guaranteed resources a pod needs — Kubernetes uses this for scheduling decisions. The pod is guaranteed at least this much CPU and memory on its node. Limits are the maximum allowed — if a pod exceeds its memory limit, it is killed (OOMKilled). If it exceeds its CPU limit, it is throttled. Always set both in production. Setting requests too high wastes resources. Setting limits too low causes unexpected pod kills. A common pattern for production: requests = expected normal usage, limits = 2–3x requests as a safety buffer.

Q4

What is a Kubernetes Horizontal Pod Autoscaler?

The HPA (Horizontal Pod Autoscaler) automatically adjusts the number of pod replicas in a Deployment based on observed metrics — typically CPU or memory utilisation. You configure a target utilisation (e.g., 70% CPU) and a min/max replica range (e.g., 3–20). The HPA controller checks metrics every 15 seconds — if average CPU across all pods exceeds 70%, it adds more pods. When load drops, it gradually scales down. In CI/CD, HPA manifests are applied to the cluster just like Deployment manifests — they are version-controlled in Git and deployed in the same pipeline. This is how we handled the CloudMart Black Friday traffic spike automatically.

Q5

What is a Kubernetes namespace and why do you use multiple namespaces?

A namespace is a virtual partition inside a Kubernetes cluster that isolates resources from each other. Resources in one namespace cannot accidentally access resources in another. I use multiple namespaces for environment isolation: cloudmart-dev, cloudmart-staging, cloudmart-prod — all on the same EKS cluster, keeping infrastructure costs lower than running three separate clusters. Each namespace has its own Secrets, ConfigMaps, and RBAC roles. The CI/CD pipeline uses separate IAM roles with permissions scoped to specific namespaces — the dev pipeline cannot deploy to the prod namespace.

🕵️
CloudMart India · Audit Review · Week 24

The Kubernetes Cluster Had 47 Manual Changes Nobody Documented

CloudMart India had been using Kubernetes for two months. The deployment pipeline was working well. But during a cost review, the finance team noticed the EKS cluster bill had doubled. Investigation revealed that multiple engineers had been running kubectl commands directly on the cluster to "quickly fix" things — scaling replicas up and never back down, adding ConfigMaps that were never in Git, changing resource limits without updating the manifests.

The cluster had drifted so far from the Git manifests that nobody trusted the YAML files anymore. Engineers feared running kubectl apply because it might accidentally revert someone's undocumented fix and break production.

The solution was GitOps with ArgoCD. ArgoCD watches your Git repository. If the cluster state drifts from what is in Git, ArgoCD either alerts you or automatically reverts the cluster back. Direct kubectl changes are blocked. All changes must go through Git → PR → merge → ArgoCD sync. The cluster state becomes 100% reproducible from Git.

Core Concept

🔀 GitOps — The Philosophy First

📌 The Four GitOps Principles

1. Declarative: All desired system state is expressed declaratively (YAML files, not scripts). 2. Versioned: All desired state is stored in Git — with full history and auditability. 3. Pulled automatically: Software agents (like ArgoCD) pull state from Git and apply it — not pushed by pipelines. 4. Continuously reconciled: Agents continuously compare desired state (Git) with actual state (cluster) and correct drift automatically.

🗺️

Analogy — ArgoCD is a GPS That Never Lets You Deviate

Imagine a GPS that not only shows you the route but also automatically steers the car back when you drift off course. If you try to take a different road, the GPS overrides the steering and brings you back. Your Git repository is the "correct route". ArgoCD is the GPS. If anyone manually changes something in the Kubernetes cluster that is not in Git, ArgoCD detects the deviation and reconciles — bringing the cluster back to match Git. You cannot deviate from the declared route.

argocd/cloudmart-app.yaml — ArgoCD ApplicationYAML
apiVersion: argoproj.io/v1alpha1
# ArgoCD's own API version — installed as a CRD (Custom Resource Definition)
kind: Application
# "Application" is ArgoCD's custom resource type — it represents one app to manage

metadata:
  name: cloudmart-production
  namespace: argocd
    # ArgoCD Application objects always live in the "argocd" namespace

spec:

  project: default
    # ArgoCD project — used to group apps and set RBAC policies
  # "default" = no restrictions. In production, create a dedicated project

  source:
        # "source" → WHERE IS THE DESIRED STATE? (the Git repository)
    repoURL: https://github.com/cloudmartindia/cloudmart-manifests.git
        # The Git repo containing Kubernetes YAML manifests
    # Best practice: use a SEPARATE repo for manifests (not same as app code)
    # This is called "GitOps repo" or "config repo"
    targetRevision: HEAD
        # "HEAD" = always sync with the latest commit on the default branch
    # You can also pin to a specific branch: "main", "production", or a tag: "v2.4.1"
    path: environments/production
        # Which folder in the repo contains the manifests for this environment
    # This allows one repo to hold manifests for all environments

  destination:
        # "destination" → WHERE TO APPLY? (the Kubernetes cluster)
    server: https://kubernetes.default.svc
        # "kubernetes.default.svc" = the cluster where ArgoCD itself is running
    # For external clusters: paste the API server URL of that cluster
    namespace: cloudmart-prod
        # Which namespace to deploy into on the destination cluster

  syncPolicy:
        # "syncPolicy" → when and how to sync Git changes to the cluster
    automated:
            # "automated" → ArgoCD syncs AUTOMATICALLY when Git changes
      prune: true
            # "prune: true" → if you DELETE a file from Git, ArgoCD deletes
      # the corresponding resource from the cluster too
      # Without this, deleted manifests leave orphaned resources in the cluster
      selfHeal: true
            # "selfHeal: true" → if ANYONE manually changes the cluster state
      # (e.g., kubectl edit), ArgoCD detects the drift and reverts it automatically
      # This is the "GPS that steers you back" behaviour

    syncOptions:
    - CreateNamespace=true
        # If the "cloudmart-prod" namespace doesn't exist yet, create it automatically
    - ApplyOutOfSyncOnly=true
        # Only apply resources that have ACTUALLY changed — skip unchanged resources
    # This makes syncs faster and reduces unnecessary API calls to Kubernetes

  revisionHistoryLimit: 10
    # Keep history of last 10 syncs — allows you to roll back to any of them

🔗 How CI Pipeline Updates the GitOps Repo

In GitOps, your CI pipeline does NOT deploy directly to Kubernetes. Instead it updates the image tag in the manifest file in Git — and ArgoCD notices the Git change and deploys it. The pipeline and ArgoCD have separate responsibilities.

📋 GitOps & ArgoCD — High-Value in Senior DevOps Interviews

GitOps knowledge separates mid-level from senior DevOps candidates.

Q1

What is GitOps and how is it different from traditional CI/CD?

GitOps is a deployment model where Git is the single source of truth for the desired state of all infrastructure and applications. An operator (like ArgoCD) continuously watches the Git repository and ensures the actual cluster state matches what is declared in Git. In traditional CI/CD, the pipeline actively pushes changes to the cluster — the pipeline is the deployment actor. In GitOps, the pipeline only updates Git, and the cluster pulls changes itself. This gives complete auditability (every change is a Git commit), easy rollback (revert the commit), and prevents drift (the operator continuously reconciles).

Q2

What is ArgoCD and what problem does it solve?

ArgoCD is a declarative GitOps continuous delivery tool for Kubernetes. It solves the problem of cluster drift — when the actual cluster state diverges from the declared state in Git due to manual kubectl commands or ad-hoc fixes. ArgoCD runs inside the cluster, watches a Git repository containing Kubernetes manifests, detects when the cluster state differs from Git, and either alerts the team or automatically syncs the cluster back to the desired state. It also provides a visual dashboard showing the health and sync status of all applications.

Q3

What does "selfHeal: true" mean in an ArgoCD Application?

When selfHeal: true is set, ArgoCD continuously compares the live cluster state with the Git state, and if they differ — for any reason — ArgoCD automatically reverts the cluster to match Git. This means if an engineer runs kubectl edit to manually change a deployment's replica count, ArgoCD detects the change within minutes and reverts it back to what Git says. This enforces that Git is truly the only way to make changes, preventing undocumented manual fixes from accumulating. It is the key feature that prevents the drift problem that motivated CloudMart India to adopt GitOps.

Q4

Why do GitOps teams use a separate manifests repository?

Using a separate manifests repository (separate from the application code repo) provides several benefits. First, separation of concerns — application code changes and infrastructure changes have different review processes and different approval requirements. Second, clear audit trail — every deployment is a commit to the manifest repo with a message like "update production to commit abc123", making deployment history crystal clear. Third, access control — the CI pipeline has write access to the manifest repo, but not to the application code repo, and vice versa. Fourth, it allows ArgoCD to watch one focused repo rather than scanning through application code for changed YAML files.

Q5

What is the difference between ArgoCD sync and ArgoCD health status?

Sync status compares what is in Git (desired state) with what is in the cluster (actual state). Status is Synced (cluster matches Git exactly) or OutOfSync (cluster has drifted — something differs). Health status tells you whether the application is actually running correctly, regardless of sync state. Status is Healthy (all pods running and ready), Progressing (deployment is in progress), Degraded (pods are crashing or not ready), or Missing (resource not found in cluster). A common scenario: Synced but Degraded — the manifest matches Git, but the application is crashing. Or OutOfSync but Healthy — someone manually scaled up pods (higher than Git), the app is running fine but Git state doesn't match.

CloudMart India · Bug Bounty Report · Week 26

A Security Researcher Found What the Team Missed

CloudMart India had a basic bug bounty programme. A security researcher submitted a report: the Node.js version in CloudMart's Docker image had a known remote code execution vulnerability — CVE-2024-XXXX, severity: CRITICAL. The base image used was node:18.12.0-alpine, which had not been updated in 9 months. The updated version (node:18.19.1-alpine) had patched this CVE 6 months ago.

The vulnerability had existed in production for half a year. No developer noticed because nobody was scanning the Docker image for CVEs. The build pipeline only ran tests on application code — it never checked the operating system packages and runtime inside the container.

The fix was updating one line in the Dockerfile. But the real solution was adding Trivy — a container image security scanner — to the pipeline. DevSecOps

🛡️ Shift-Left Security — Security Early, Not Late

📌 What is DevSecOps / Shift-Left Security?

"Shift-left" means moving security checks earlier in the development process — into the CI/CD pipeline — instead of doing security reviews only at the end before release. Every code push triggers automated security scans. Problems are found by the developer in minutes, not by a security team weeks later or (worst case) by a hacker in production.

🔍 Trivy — Container Image Scanner in the Pipeline

.github/workflows/security-scan.yml — Trivy Image ScanYAML
name: Security Scanning Pipeline
on:
  push:
    branches: [main, develop]

jobs:

    # ─── JOB 1: Scan dependencies for known CVEs ──────────────────────
  dependency-scan:
    name: Snyk Dependency Scan
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: snyk/actions/node@master
        env:
          SNYK_TOKEN: ${{ secrets.SNYK_TOKEN }}
        with:
          args: --severity-threshold=high
                    # Scan npm packages in node_modules for known CVEs
          # "--severity-threshold=high" → only FAIL on HIGH or CRITICAL CVEs
          # LOW and MEDIUM are reported but do not fail the pipeline

    # ─── JOB 2: Build Docker image + scan with Trivy ─────────────────
  trivy-scan:
    name: Trivy Image Security Scan
    runs-on: ubuntu-latest
    needs: dependency-scan
    steps:
      - uses: actions/checkout@v4

      - name: Build Docker image (local only — not pushed yet)
        run: docker build -t cloudmart-app:scan-test .
                # Build the image locally first — scan it BEFORE pushing to ECR
        # If scan fails → we never push a vulnerable image to the registry

      - name: Run Trivy — scan image for CVEs
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: cloudmart-app:scan-test
          format:    sarif
                    # "sarif" = Standard format for security findings — readable by GitHub Security tab
          output:    trivy-results.sarif
          severity:  CRITICAL,HIGH
                    # Only report CRITICAL and HIGH severity CVEs
          # MEDIUM and LOW are too noisy for daily pipeline blocking

                    # "exit-code: 1" → if any CRITICAL or HIGH CVE is found → FAIL this step
          # The pipeline stops here — the vulnerable image is NOT pushed to ECR

                # "if: always()" → upload results even if Trivy found vulnerabilities and failed

Q1

What is Trivy and how do you use it in a CI/CD pipeline?

Trivy is an open-source vulnerability scanner by Aqua Security. It scans Docker images, filesystems, Git repositories, Terraform files, and Kubernetes manifests for known CVEs (security vulnerabilities) and misconfigurations. In a CI/CD pipeline, I build the Docker image locally and immediately run Trivy on it before pushing to ECR. I configure Trivy with exit-code: 1 and severity: CRITICAL,HIGH — so if any critical or high CVE is found, the pipeline step fails and the image is never pushed to the registry. I also use ignore-unfixed: true to skip vulnerabilities that have no available patch, avoiding permanent pipeline blocks.

Q2

What is the difference between SCA, SAST, and DAST?

SCA (Software Composition Analysis) scans the open-source libraries and dependencies your application uses — checking if they have known CVEs. Tools: Snyk, Trivy, OWASP Dependency-Check. Runs at the build stage. SAST (Static Application Security Testing) analyses your own source code without running it — looking for insecure coding patterns like SQL injection, hardcoded passwords, or input validation issues. Tools: SonarQube, Checkmarx. Runs at the code review/build stage. DAST (Dynamic Application Security Testing) tests the running application by sending malicious inputs — simulating a real attacker. Tools: OWASP ZAP, Burp Suite. Runs after deploying to a staging environment. A mature DevSecOps pipeline uses all three.

Q3

What is a CVE and what severity levels does Trivy use?

A CVE (Common Vulnerabilities and Exposures) is a publicly disclosed security vulnerability identified with a unique ID like CVE-2024-12345. The National Vulnerability Database (NVD) assigns a CVSS score (0–10) and severity level: CRITICAL (9.0–10.0), HIGH (7.0–8.9), MEDIUM (4.0–6.9), and LOW (0.1–3.9). In pipeline configuration, I block deployments on CRITICAL and HIGH severity CVEs. MEDIUM and LOW are reported to a dashboard for tracking but do not block the pipeline, because failing builds on medium CVEs causes too many false blockages — teams start ignoring alerts entirely.

Q4

How do you handle a Trivy finding that has no fix available?

When a vulnerability has no patch (no fixed version of the library exists yet), I use ignore-unfixed: true in Trivy — this skips unfixed CVEs from the pipeline check. For tracking purposes, I maintain a .trivyignore file in the repository listing specific CVE IDs that are accepted risks, with a comment explaining the acceptance reasoning and an expiry date for review. For critical unfixed CVEs, I implement compensating controls — network segmentation, WAF rules, or temporary feature disabling — and track the CVE for when a fix becomes available. This balance avoids permanently blocking deployments while maintaining a record of known risks.

Q5

What is OWASP ZAP and at which stage does it run in a pipeline?

OWASP ZAP (Zed Attack Proxy) is a free DAST tool that tests a running web application for security vulnerabilities by acting as a proxy and sending specially crafted requests — testing for XSS, SQL injection, CSRF, security misconfigurations, insecure headers, and more. In a CI/CD pipeline, ZAP runs after the application is deployed to the staging environment — never on production. In GitHub Actions, I use the zaproxy/action-full-scan action pointing to the staging URL. ZAP generates an HTML report. The pipeline can be configured to fail on a risk level threshold. I also run ZAP in baseline scan mode on every PR for quick feedback, and the full scan only on merges to main.

The 3 Pillars

🔭 The Three Pillars of Observability

📊 Metrics

Numerical measurements over time — error rate, request latency, CPU usage, memory, request count. Collected by Prometheus, visualised in Grafana. Ideal for dashboards, alerting, and trending. "What is the error rate of the payment endpoint?"

📋 Logs

Timestamped text records of events — every request, every error, every database call. Collected by Fluentd / Fluent Bit, stored in Elasticsearch or CloudWatch, searched in Kibana. "What was the exact error message for payment failures?"

🔗 Traces

A trace follows one user request across all microservices — showing where time was spent and where errors occurred. Tools: Jaeger, AWS X-Ray, OpenTelemetry. "Which service is causing the 3-second delay in checkout?"

Post-Deploy Validation

⚕️ Post-Deployment Health Validation in Pipeline

Pipeline Stage — Post-Deployment Monitoring CheckYAML
  post-deploy-validation:
    name: Post-Deployment Health Validation
    runs-on: ubuntu-latest
    needs: deploy-production
    steps:
      - name: Wait for deployment to stabilise
        run: sleep 300
                # Wait 5 minutes (300 seconds) before checking metrics
        # This gives the new pods time to start serving real traffic
        # and for any startup errors to surface in Prometheus

      - name: Check error rate via Prometheus API
        run: |
          ERROR_RATE=$(curl -s \
            "https://prometheus.cloudmart.in/api/v1/query?query=sum(rate(http_requests_total{status=~'5..',app='cloudmart'}[5m]))/sum(rate(http_requests_total{app='cloudmart'}[5m]))*100" \
            | jq -r '.data.result[0].value[1]')
                    # Query Prometheus HTTP API — returns JSON with the metric value
          # The PromQL query calculates: (5xx errors / total requests) × 100 = error rate %
          # "jq -r" parses the JSON and extracts just the numeric value

          echo "Current error rate: ${ERROR_RATE}%"

          if (( $(echo "$ERROR_RATE > 1.0" | bc -l) )); then
            echo "ERROR RATE TOO HIGH: ${ERROR_RATE}% — triggering rollback!"
            exit 1
                        # "exit 1" fails this step → triggers the rollback in the "failure" post action
          fi
          echo "Error rate normal: ${ERROR_RATE}% — deployment validated ✓"

      - name: Check p99 latency via Prometheus API
        run: |
          P99=$(curl -s \
            "https://prometheus.cloudmart.in/api/v1/query?query=histogram_quantile(0.99,rate(http_request_duration_seconds_bucket{app='cloudmart'}[5m]))" \
            | jq -r '.data.result[0].value[1]')
          echo "p99 latency: ${P99}s"
          if (( $(echo "$P99 > 2.0" | bc -l) )); then
            echo "LATENCY TOO HIGH: ${P99}s — triggering rollback!"
            exit 1
          fi

      - name: Auto-rollback on validation failure
        if: failure()
        run: |
          kubectl rollout undo deployment/cloudmart-app -n cloudmart-prod
          kubectl rollout status deployment/cloudmart-app -n cloudmart-prod
          echo "Automatic rollback complete"

Q1

What are the three pillars of observability and what tool do you use for each?

The three pillars are Metrics, Logs, and Traces. For metrics — numerical data like error rates, latency, and CPU usage — I use Prometheus for collection and Grafana for visualisation and alerting. For logs — structured text records of application events — I use Fluent Bit as the log collector in Kubernetes and either Elasticsearch + Kibana or AWS CloudWatch Logs Insights for search and analysis. For distributed traces — following a request across multiple microservices — I use AWS X-Ray or OpenTelemetry with Jaeger. In a CI/CD context, metrics are most critical — the pipeline queries Prometheus after deployment to validate error rates and latency.

Q2

How do you add post-deployment monitoring to a CI/CD pipeline?

After a deployment job completes, I add a post-deployment validation job that: first, waits 3–5 minutes for the new pods to stabilise and start serving real traffic; then queries Prometheus via its HTTP API using PromQL — checking error rate (should be under 1%), p99 latency (should be under 2 seconds), and pod restart count (should be zero for new pods). If any metric breaches its threshold, the job exits with error code 1, which triggers a kubectl rollout undo for automatic rollback. This closes the feedback loop — the pipeline is responsible not just for deploying but for validating that the deployment was actually successful from a user experience perspective.

Q3

What is PromQL? Give an example.

PromQL (Prometheus Query Language) is a functional query language for querying metrics from Prometheus. It allows you to filter, aggregate, and calculate metrics. For example: rate(http_requests_total{status=~"5..", app="cloudmart"}[5m]) — this calculates the per-second rate of HTTP requests that returned a 5xx error for the cloudmart app, averaged over the last 5 minutes. The curly braces are label filters (like WHERE clauses in SQL). The rate() function converts a counter metric to a per-second rate. I use PromQL in pipeline scripts to check post-deployment health, and in Grafana to build dashboards for real-time monitoring.

Q4

What is a /health endpoint and what should it contain?

A /health endpoint is an HTTP endpoint in your application that returns whether the application is alive. Kubernetes uses it as a liveness probe — if this endpoint stops responding, Kubernetes restarts the container. It should be very simple — just confirm the process is alive and returning 200. It should NOT check external dependencies like databases, because a database failure should not cause your application pod to restart continuously. For checking external dependencies, use a separate /ready endpoint — if the database is down, /ready returns 503, Kubernetes stops sending traffic to this pod (removes from Service) but does not restart it. This distinction is critical for graceful handling of dependency failures.

Q5

What is p99 latency and why is it more useful than average latency?

p99 latency (99th percentile) means that 99% of requests completed in that time or less — only 1% of requests were slower. Average latency is misleading because a few very slow requests (outliers) are hidden by thousands of fast requests — the average looks fine while 5% of users experience terrible performance. For example, if average latency is 120ms but p99 is 8 seconds, the average looks healthy, but 1 in 100 users waits 8 seconds. In e-commerce, that 1% is thousands of customers with a bad experience. In CI/CD, I monitor both p50 (median — typical experience) and p99 (worst 1% — outlier experience) after each deployment.

🏆 Top 7 Pipeline Optimisation Rules

  1. Cache everything — npm, pip, Maven, Gradle, Docker layers. Cache = biggest single win.
  2. Run independent jobs in parallel — lint, test, security scan should all run at the same time.
  3. Use conditional execution — skip test/build/deploy for doc-only changes.
  4. Fail fast — run quickest checks first (format, lint, unit tests). Fail before expensive steps.
  5. Pin versions — never use @latest in actions — cache invalidates on version changes.
  6. Minimise checkout depth — use fetch-depth: 1 unless full history is needed.
  7. Use reusable workflows — define common jobs once, reference from all pipelines.

Q1

How do you improve the speed of a slow CI/CD pipeline?

I approach pipeline optimisation in four steps. First, measure — use pipeline timing reports to identify the slowest stages. Second, cache aggressively — package managers (npm, pip, Maven) and Docker layers are the biggest time savers. A cached npm install takes 8 seconds vs 3 minutes fresh. Third, parallelise — run independent jobs simultaneously: lint, unit tests, security scans can all run at the same time instead of sequentially. Fourth, conditional execution — use path filtering so documentation changes skip the full 25-minute pipeline entirely. In one CloudMart pipeline optimisation, these changes reduced pipeline time from 28 minutes to 6 minutes — a 78% improvement.

Q2

How does Docker layer caching work in CI/CD?

Docker builds images layer by layer. Each instruction in a Dockerfile creates one layer. Docker caches each layer by a hash of its contents plus all previous layers. If a layer's hash matches the cache, it is reused instantly instead of re-executing. In CI/CD, I use docker/build-push-action with cache-from: type=gha — storing layer cache in GitHub Actions Cache. For maximum cache efficiency, I structure Dockerfiles with rarely-changing instructions first (FROM, COPY package.json, RUN npm ci) and frequently-changing instructions last (COPY . . to copy source code). This way, the expensive npm install layer is cached and reused on every push that doesn't change package.json.

Q3

What is a reusable workflow in GitHub Actions?

A reusable workflow is a workflow YAML file that can be called from other workflows, similar to a function or shared library. You define it with on: workflow_call: and it accepts inputs and secrets as parameters. Other workflows call it with uses: org/repo/.github/workflows/shared-deploy.yml@main. This avoids duplicating the same 50-line deploy job across 10 different service pipelines. If you need to update the deployment process, you change it in one place and all services automatically use the updated version. In Jenkins, the equivalent is Shared Libraries — Groovy functions stored in a separate Git repository and loaded by all Jenkinsfiles.

Q4

What does "fail fast" mean in CI/CD pipeline design?

Fail fast means designing the pipeline so that the cheapest and fastest checks run first — and if they fail, the pipeline stops before running expensive later stages. For example: run lint and format checks first (5 seconds) — if the code has a syntax error, fail immediately and skip the 3-minute test suite, 4-minute security scan, and 6-minute Docker build. Order from fastest to slowest: formatting check → unit tests → integration tests → security scan → Docker build → deployment. A developer gets feedback in 10 seconds for a syntax error, rather than waiting 20 minutes for a full pipeline run to complete before discovering the problem.

DORA Metrics

📊 DORA Metrics — Measuring Your CI/CD Maturity

📌 What are DORA Metrics?

DORA (DevOps Research and Assessment) metrics are 4 key measurements that predict software delivery performance and organisational success. They come from research by Google's DevOps Research team studying thousands of engineering teams. Elite teams (like Google, Amazon) score high on all 4. These metrics are now the industry standard for measuring CI/CD health.

Deployment Frequency
🚀 How often?

How often does your team deploy to production? Elite: multiple times per day. High: daily to weekly. Medium: weekly to monthly. Low: monthly or less. CloudMart target: 3–5 deployments per day.

Lead Time for Changes
⏱️ How fast?

Time from code commit to running in production. Elite: less than 1 hour. High: 1 day to 1 week. Medium: 1 week to 1 month. Low: more than 1 month. CloudMart before CI/CD: 3 weeks. After: 45 minutes.

Change Failure Rate
💥 How reliable?

What % of deployments cause a production incident requiring rollback or hotfix? Elite: 0–15%. High: 16–30%. Medium: 16–45%. Low: 46–60%. CloudMart before: 25% (1 in 4 deploys broke something). After: 3%.

Mean Time to Recovery (MTTR)
🔧 How recoverable?

How long does it take to restore service after a production incident? Elite: less than 1 hour. High: less than 1 day. Medium: 1 day to 1 week. Low: more than 1 week. With auto-rollback: CloudMart MTTR went from 2 hours to 8 minutes.

🎯 Chapter 18 Interview Questions

📋 DORA Metrics & Pipeline Visibility — Senior-Level Differentiator

Mentioning DORA metrics in an interview signals you think about DevOps at a strategic level.

Q1

What are DORA metrics and why do they matter?

DORA metrics are four key measurements from Google's DevOps Research and Assessment team that predict software delivery performance: Deployment Frequency (how often you deploy), Lead Time for Changes (commit to production time), Change Failure Rate (% of deployments causing incidents), and Mean Time to Recovery (how quickly you restore service). They matter because they give engineering leadership an objective measure of CI/CD health and team performance. Elite teams — deploying multiple times per day with MTTR under 1 hour — consistently outperform medium-performing teams on business metrics. I use these to benchmark improvements: at CloudMart, Lead Time went from 3 weeks to 45 minutes after implementing the full CI/CD pipeline.

Q2

How do you implement Slack notifications in a Jenkins pipeline?

I use the Jenkins Slack plugin. After installing it, configure the Slack workspace token in Jenkins → Manage Jenkins → System → Slack. In the Jenkinsfile, use slackSend() in the post { } block: post { success { slackSend(channel: '#deployments', color: 'good', message: "✅ ...") } failure { slackSend(channel: '#alerts', color: 'danger', message: "❌ ...") } }. I always include the build URL, job name, build number, and the name of the person who triggered the build in the message. For GitHub Actions, I use the slackapi/slack-github-action action with a Slack Bot Token stored as a GitHub Secret. Critical failures go to an alerts channel with @here so the on-call engineer sees it immediately.

Q3

What is Lead Time for Changes and how does CI/CD reduce it?

Lead Time for Changes is the time from when a developer commits code to when that code is running in production. Without CI/CD, this is typically weeks — code accumulates, manual testing takes days, deployment is a big quarterly event. With CI/CD, every commit triggers an automated pipeline that builds, tests, scans, and deploys within minutes. The lead time collapses from weeks to under an hour for elite teams. At CloudMart India, our lead time went from 3 weeks to 45 minutes. Reducing lead time means faster feature delivery to customers, faster bug fixes, and faster competitive response. It is a direct measure of how well your CI/CD pipeline is working.

Q4

What is Mean Time to Recovery and how does CI/CD improve it?

MTTR is the average time to restore service after a production incident. CI/CD improves it in three ways. First, automated rollback — when smoke tests or post-deployment monitoring detect a problem, the pipeline immediately runs kubectl rollout undo — restoring the previous version in minutes without human involvement. Second, small, frequent deployments — when you deploy small changes frequently, each deployment has a smaller blast radius. Identifying which change caused an incident is much faster. Third, traceable artifacts — every deployment is tagged with a git SHA. Redeploying a specific previous version is a one-command operation rather than a manual investigation to find which version was running.

Q5

How would you present the value of a CI/CD pipeline investment to management?

I present CI/CD value using three types of evidence. First, DORA metrics improvement — show before and after: Lead Time from 3 weeks to 45 minutes, Deployment Frequency from monthly to daily, MTTR from 2 hours to 8 minutes. Second, business impact numbers — at CloudMart, each deployment previously had a 25% failure rate causing 2-hour downtime costing ₹14 lakhs. After CI/CD, failure rate dropped to 3% and MTTR to 8 minutes — reducing deployment incidents from ₹14L to ₹400K loss per event. Third, developer productivity — removing 28-minute pipeline waits across 8 developers saved 14+ person-hours per day — equivalent to nearly 2 additional developers of capacity. I always connect technical metrics to business outcomes because that is what management responds to.
