Core Concept

📦 What is Git? — The Foundation of Every Pipeline

📌 Definition

Git is a version control system — a tool that tracks every change made to your code, who made it, when they made it, and why. It allows multiple developers to work on the same codebase simultaneously without overwriting each other's work.

📸

Analogy — Git is Like Google Photos for Your Code

Think of Google Photos. Every photo you take is automatically saved with a timestamp, your location, and the device. You can scroll back in time to any photo from any day. You can see what changed between two photos. You can restore a deleted photo. Git does exactly the same thing for your code files — every save (called a "commit") is a snapshot of your code at that moment, with a message explaining what changed.

Why Does CI/CD Need Git?

Every CI/CD pipeline starts with a Git event. When you do git push, that push event is what triggers your pipeline to run. Without Git, there is no way for the pipeline to know that new code is ready. Git is not just for collaboration — it is the starting point of every automation in DevOps.

Git (Local Tool)

Git is software you install on your laptop. It tracks changes in a folder (called a repository). Everything is stored locally — on your own machine. You can work offline.

GitHub (Cloud Platform)

GitHub is a website that stores your Git repository in the cloud. It is where your team shares code. It also provides the pipeline (GitHub Actions), issue tracking, and code review tools.

Other platforms similar to GitHub: GitLab (used in many companies), Bitbucket (used with Jira). The Git commands are the same everywhere — only the platform UI is different.

Branching Strategy

🌿 Branches — The Most Important Concept for CI/CD

A branch is an independent line of development inside your repository. You create a branch so you can work on a new feature without touching the working code that is already in production.

🛣️

Analogy — A Branch is a New Road Under Construction

Imagine a main highway. Cars (users) are driving on it all day. You need to build a flyover at one junction. You do not close the highway while building — that would stop all traffic. Instead, you build the flyover on a separate construction path. When it is fully built and tested, you open it and connect it to the main highway. A Git branch is that construction path. Your feature is built separately — main branch keeps running — and when ready, you merge it in.

The Branching Strategy CloudMart Uses

main branch

This is the production-ready branch. Code here is live on the website. No developer pushes directly to main — all changes go through Pull Requests. Every push to main triggers the production pipeline.

develop branch

This is the integration branch. All feature branches merge here first. Every push to develop triggers the staging pipeline — deploy to test server, run all tests.

feature/xxx branch

Individual developers create these. For example: feature/payment-gateway or feature/diwali-sale. Every push here triggers the CI pipeline — build and run unit tests only.

hotfix/xxx branch

Emergency fixes for production bugs. Created from main, fixed, and merged back to both main and develop. Every push here triggers a fast pipeline — build, critical tests only, deploy.

Daily Git Workflow at CloudMart IndiaBASH
# Morning routine — always start here

git pull origin main    # Get latest code from GitHub

What is a Pull Request (PR)?

A Pull Request (also called Merge Request in GitLab) is a formal request to merge your feature branch into the main branch. When you open a PR on GitHub, three things happen automatically:

  1. 1.The CI pipeline runs automatically — building the code and running all tests on your branch.
  2. 2.Your teammates can review the code changes, leave comments, and request changes.
  3. 3.Only when the pipeline is green AND reviewers approve — the PR can be merged into main.

Q1

What is the difference between Git and GitHub?

Git is a version control tool that you install on your local machine. It tracks changes to your code and allows you to take snapshots called commits. GitHub is a cloud-based platform that hosts your Git repositories online so that teams can collaborate. Think of Git as the tool, and GitHub as the place where you store and share your work. You can use Git without GitHub, but most teams use both together.

Q2

What is a branch in Git and why is it important for CI/CD?

A branch is an independent copy of the codebase where you can make changes without affecting the main code. It is important for CI/CD because different branches can trigger different pipelines. For example, a push to a feature branch triggers unit tests only, a push to the develop branch triggers the staging deployment, and a push to main triggers the production deployment. This way, code is tested at every stage before it reaches production.

💬 Tip: Mention the branch-to-pipeline connection — most candidates only explain what a branch is but forget to connect it to CI/CD. This detail shows senior-level thinking.

Q3

What is a Pull Request and how does it connect to the CI pipeline?

A Pull Request is a request to merge code from one branch into another, usually from a feature branch into main. When a Pull Request is opened on GitHub, the CI pipeline is triggered automatically — it builds the code and runs all tests. If the pipeline fails, the Pull Request cannot be merged. If it passes and the team approves the code review, then the merge is allowed. This ensures that only tested, reviewed code reaches the main branch.

Q4

What is git rebase and when do you use it?

git rebase is a way to move or combine commits from one branch onto another branch, creating a cleaner, linear commit history. You use it when you want to update your feature branch with the latest changes from main without creating a merge commit. In CI/CD workflows, rebase is used to keep feature branches up to date with main so that Pull Request merges are clean. However, never rebase a branch that other people are working on — it rewrites commit history and causes conflicts.

Q5

How do you resolve a merge conflict in Git?

A merge conflict happens when two people changed the same line of code in different ways, and Git cannot automatically decide which change to keep. To resolve it: first run git pull to download the conflicting code. Git marks the conflict in the file with special markers — <<<<<<<, =======, and >>>>>>> — showing both versions. You manually edit the file to keep the correct version and delete the markers. Then run git add, git commit, and push. In a CI/CD pipeline, merge conflicts must be resolved before the pipeline can run.

Core Concept

🔧 What is GitHub Actions?

📌 Definition

GitHub Actions is a built-in CI/CD platform inside GitHub. It allows you to automate tasks — like building, testing, and deploying your code — by writing instructions in a YAML file. When a specific event happens (like a git push), GitHub automatically reads your YAML file and runs all the steps you defined — on a fresh computer that GitHub provides for free.

Key Advantage 1 — Free Runners

GitHub provides virtual machines (called runners) for free. You don't need to set up your own server. GitHub gives you Ubuntu, Windows, or macOS machines — they spin up, run your pipeline, and disappear.

Key Advantage 2 — Marketplace Actions

The GitHub Marketplace has 20,000+ ready-made "actions" — pre-built tools like "setup Node.js", "login to AWS", "build Docker image". You use them with one line instead of writing 30 commands yourself.

Workflow Anatomy

📄 The Anatomy of a GitHub Actions Workflow File

A workflow file is a YAML file stored inside your repository at this exact path: .github/workflows/your-pipeline-name.yml. Let us understand every single part:

.github/workflows/ci-pipeline.ymlYAML — Word by Word
# ═══ PART 1: WORKFLOW NAME ═══════════════════════════════════════════
name: CloudMart CI Pipeline
# "name:" → what you want to call this workflow
# This name appears in the GitHub Actions tab
# You can have MULTIPLE workflow files — each has a different name

# ═══ PART 2: TRIGGERS — When should this workflow run? ═══════════════
on:
  # "on:" → the list of events that start this workflow

  push:
      # Trigger when someone does "git push"
    branches:
      - main        # Only when pushing to the main branch
      - develop    # Also when pushing to develop branch

  pull_request:
      # Also trigger when a Pull Request is opened or updated
    branches:
      - main        # Only PRs targeting the main branch

  workflow_dispatch:
      # This adds a manual "Run workflow" button in the GitHub UI
    # Very useful for on-demand deployments

  schedule:
      # Run on a schedule (like a cron job)
    - cron: '0 2 * * 1'  # Every Monday at 2:00 AM UTC

# ═══ PART 3: ENVIRONMENT VARIABLES ══════════════════════════════════
env:
  # "env:" → variables available to ALL jobs in this workflow
  NODE_ENV: test
  APP_NAME: cloudmart-india

# ═══ PART 4: JOBS — What to actually do ═════════════════════════════
jobs:
  # "jobs:" → one workflow can have MULTIPLE jobs
  # By default, all jobs run IN PARALLEL (at the same time)
  # You can make them run in sequence using "needs:" (Chapter 4)

  build-and-test:
    # This is the JOB ID — you name it yourself
  # Job ID: no spaces allowed, use hyphens

    runs-on: ubuntu-latest
        # "runs-on:" → which OS/machine to use for this job
    # "ubuntu-latest" → latest Ubuntu Linux (most common choice)
    # Other options: "windows-latest", "macos-latest"
    # GitHub creates a FRESH machine every time — nothing is saved between runs

    steps:
        # "steps:" → the list of commands to run IN ORDER, one by one
    # If ANY step fails → all remaining steps are skipped → job fails

      - name: Checkout code from GitHub
        uses: actions/checkout@v4
                # "uses:" → use a pre-built action from the Marketplace
        # "actions/checkout" → downloads your repo code onto the runner
        # "@v4" → use version 4 (always pin versions for stability!)

      - name: Setup Node.js version 20
        uses: actions/setup-node@v4
        with:
                    # "with:" → pass configuration to the action (like function arguments)
          node-version: '20'
                    # Installs Node.js v20 on the runner machine
          cache: 'npm'
                    # "cache: npm" → saves node_modules between runs
          # Next run will be MUCH faster — no re-downloading packages

      - name: Install dependencies
        run: npm ci
                # "run:" → run a shell command directly on the runner
        # "npm ci" → clean install (faster and more reliable than npm install)
        # "ci" stands for clean install — it uses package-lock.json exactly

      - name: Run linting check
        run: npm run lint
                # Runs ESLint — checks for code style errors and potential bugs
        # If linting fails → step fails → job fails → PR cannot merge

      - name: Run unit tests
        run: npm test
                # Runs Jest or Mocha test suite
        # Output shows how many tests passed and failed

      - name: Print success message
        run: echo "All tests passed! Pipeline is green ✓"

Understanding the Cron Schedule Format

Cron Schedule Format ExplainedCRON
# Format:  minute  hour  day-of-month  month  day-of-week
#               ↓      ↓       ↓          ↓        ↓
cron: '0    2     *          *        1'
#    "0"  = at minute 0 (start of the hour)
#    "2"  = at 2 AM UTC
#    "*"  = every day of the month (asterisk = "any")
#    "*"  = every month
#    "1"  = only on Monday (0=Sun, 1=Mon, 2=Tue ... 6=Sat)
# Result: runs every Monday at 2:00 AM UTC

# More examples:
'0 0 * * *'    # Every day at midnight
'*/15 * * * *' # Every 15 minutes
'0 9 * * 1-5'  # Every weekday (Mon-Fri) at 9 AM

Q1

What is GitHub Actions and how is it different from Jenkins?

GitHub Actions is a cloud-native CI/CD platform built directly into GitHub. It requires no separate server setup — GitHub provides the runners for free. You write YAML files inside your repository and pipelines run automatically on GitHub's infrastructure. Jenkins is an open-source automation server that you install and manage on your own server or VM. Jenkins gives more control and is better for complex enterprise setups or when you need to run pipelines on private infrastructure. GitHub Actions is easier to start with; Jenkins is more powerful for customisation. I have used both — GitHub Actions for cloud projects and Jenkins for on-premise pipelines.

💬 Always say you have used both — it shows breadth. Then mention one specific strength of each.

Q2

What are the main components of a GitHub Actions workflow?

A GitHub Actions workflow has four main components. First, the name — the display name of the workflow. Second, the trigger (on) — the events that start the workflow, such as a push, pull request, or schedule. Third, jobs — the main units of work, each running on its own runner machine. Each job has a runs-on specifying the OS. Fourth, steps inside each job — the actual commands, either using pre-built actions with "uses" or shell commands with "run". All of these are defined in a YAML file stored in .github/workflows/.

Q3

What is a GitHub Actions runner?

A runner is the machine (virtual or physical) that executes the steps in a job. GitHub provides GitHub-hosted runners for free — you specify the OS with "runs-on: ubuntu-latest" and GitHub spins up a fresh virtual machine for each job run, then destroys it after. You can also set up self-hosted runners — your own machine or server registered with GitHub — which is useful when you need to run pipelines inside a private network, like accessing an internal database or deploying to on-premise servers.

Q4

What is the difference between "uses" and "run" in a step?

"uses" invokes a pre-built action from the GitHub Marketplace — a reusable, packaged piece of functionality written by the community or GitHub. For example, actions/checkout@v4 automatically downloads your repository code. "run" executes a raw shell command directly on the runner, like npm test or docker build .. You use "uses" for complex, reusable tasks to avoid reinventing the wheel, and "run" for simple, direct commands.

Q5

How do you pass environment variables to a GitHub Actions workflow?

There are three ways. First, the env: key at the workflow level sets variables available to all jobs. Second, the env: key at the job or step level sets variables scoped to just that job or step. Third, for sensitive values like passwords and API keys, you use GitHub Secrets — stored encrypted in your repository settings and referenced in YAML as ${{ secrets.MY_SECRET_NAME }}. Secrets are never exposed in logs — GitHub masks them automatically. I always use Secrets for credentials and env for non-sensitive configuration.

Job Dependencies

🔗 Job Dependencies — Making Jobs Run in Sequence

By default, all jobs in a workflow run in parallel — at the same time. But in a real pipeline, you want jobs to run in a specific order. You do not want to build a Docker image if the tests fail. You use the needs: keyword to create dependencies between jobs.

.github/workflows/full-pipeline.ymlYAML — Multi-Job Pipeline
name: CloudMart Full CI/CD Pipeline

on:
  push:
    branches: [main]

jobs:

  # ─── JOB 1: Test ────────────────────────────────────────────────────
  test:
    name: Run Unit Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm test

  # ─── JOB 2: Build & Push Docker Image ──────────────────────────────
  build-and-push:
    name: Build and Push Docker Image
    runs-on: ubuntu-latest

    needs: test
        # "needs: test" → this job will NOT start until the "test" job finishes
    # If "test" fails → "build-and-push" is SKIPPED automatically
    # You can also depend on multiple jobs: needs: [test, lint, security-scan]

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id:     ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region:            ap-south-1
                    # "${{ secrets.NAME }}" → reads a secret stored in GitHub repo settings
          # Secrets are ENCRYPTED — never visible in logs or to anyone
          # Store them at: GitHub Repo → Settings → Secrets → Actions

      - name: Login to Amazon ECR
        id: login-ecr
                # "id:" → give this step a name so other steps can reference its output
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build, tag, and push Docker image to ECR
        env:
          ECR_REGISTRY:   ${{ steps.login-ecr.outputs.registry }}
                    # Reference the output from the "login-ecr" step above
          ECR_REPOSITORY: cloudmart-app
          IMAGE_TAG:      ${{ github.sha }}
                    # "github.sha" → the Git commit hash (unique ID for each commit)
          # This gives every image a unique tag — very important for tracking
        run: |
                    # The "|" pipe means "multi-line run command" — run multiple commands
          docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
          docker push  $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
                    # "docker build" → builds the Docker image from your Dockerfile
          # "-t" → tag = give the image a name
          # "." → use the Dockerfile in the current directory
          # "docker push" → upload the image to AWS ECR

  # ─── JOB 3: Deploy to Staging ──────────────────────────────────────
  deploy-staging:
    name: Deploy to Staging Environment
    runs-on: ubuntu-latest
    needs: build-and-push
        # This job runs only after build-and-push succeeds
    environment: staging
        # "environment: staging" → links to a GitHub Environment with protection rules
    # You can require approvals before this job runs
    steps:
      - run: echo "Deploying to staging server..."
            # In a real pipeline: run aws ecs update-service or kubectl apply here
Secrets & Artifacts

🔐 GitHub Secrets + 📦 Artifacts

🔐 GitHub Secrets

Sensitive values like passwords, API keys, and tokens stored encrypted in GitHub. Accessed in workflows as ${{ secrets.NAME }}. Never printed in logs. Set at: Repo → Settings → Secrets and variables → Actions. Common secrets: AWS_ACCESS_KEY_ID, DOCKER_PASSWORD, SONAR_TOKEN.

📦 Artifacts

Files produced by one job that need to be used by another job or downloaded later. Examples: test results, coverage reports, build files. Uploaded with actions/upload-artifact and downloaded with actions/download-artifact. Stored for 90 days by default.

Uploading and Downloading ArtifactsYAML
# In Job 1 — after running tests, save the test report
      - name: Upload test results
        uses: actions/upload-artifact@v4
        with:
          name: test-results        # Name to give this artifact
          path: coverage/            # Folder or file to upload
          retention-days: 30       # How long to keep it (default: 90)

# In Job 2 — download the artifact uploaded by Job 1
      - name: Download test results
        uses: actions/download-artifact@v4
        with:
          name: test-results         # Must match the name used when uploading
          path: ./downloaded-results # Where to put it on the runner
Matrix Builds

🔢 Matrix Builds — Test on Multiple Versions at Once

A matrix build lets you run the same job multiple times in parallel, each time with different variable values. For example, test your app on Node.js 18, 20, and 22 all at the same time.

Matrix Build — Test on Multiple Node.js VersionsYAML
  test-matrix:
    runs-on: ubuntu-latest

    strategy:
      matrix:
                # "matrix:" → define the variables and their possible values
        node-version: [18, 20, 22]
                # GitHub will create 3 SEPARATE JOB RUNS in parallel:
        # Run 1: node-version = 18
        # Run 2: node-version = 20
        # Run 3: node-version = 22
        os: [ubuntu-latest, windows-latest]
                # Now we have 3 versions × 2 OSes = 6 parallel runs!

      fail-fast: false
            # "fail-fast: false" → if one matrix run fails, don't cancel others
      # Default is true — we set false to see ALL failures

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
                    # "${{ matrix.node-version }}" → use the current matrix value
          # This is how you READ the matrix variable inside a step
      - run: npm ci && npm test

📋 Advanced GitHub Actions Questions

These come up for 3-5 YOE DevOps interviews.

Q1

How do you make one GitHub Actions job wait for another job to finish?

You use the needs: keyword. By adding needs: test to a job, that job will not start until the "test" job completes successfully. If the "test" job fails, the dependent job is skipped automatically. You can also depend on multiple jobs by writing needs: [test, lint, security-scan] — in this case the job waits for ALL of them to pass. Without "needs", all jobs run in parallel by default.

Q2

How do you store and use sensitive information like AWS keys in GitHub Actions?

I store sensitive values as GitHub Secrets. To add a secret, go to Repository Settings → Secrets and variables → Actions → New repository secret. In the YAML workflow, you access them using the expression ${{ secrets.SECRET_NAME }}. GitHub automatically masks secret values in logs — they never appear as plain text. For AWS authentication specifically, I prefer using OIDC (OpenID Connect) with aws-actions/configure-aws-credentials — this generates short-lived tokens instead of storing long-lived access keys, which is more secure.

💬 Mentioning OIDC as the preferred method shows senior security awareness. Most candidates only know about storing access keys.

Q3

What is a matrix build and when would you use it?

A matrix build runs the same job multiple times in parallel with different variable combinations. I use it to test code compatibility across multiple versions of a language or operating system. For example, testing a Node.js application on Node versions 18, 20, and 22 simultaneously — instead of waiting for each version sequentially. The matrix is defined under strategy.matrix, and the variable is referenced inside steps using ${{ matrix.variable-name }}. This ensures our application works across all supported environments before deployment.

Q4

What are GitHub Actions artifacts and when do you use them?

Artifacts are files that one job produces and another job (or a human) needs to access. For example, after running tests, I upload the code coverage report as an artifact using actions/upload-artifact. In a later job, I can download it using actions/download-artifact. Artifacts are also useful for saving compiled binaries or build output that needs to be deployed. They are stored for 90 days by default and can be downloaded directly from the GitHub Actions run page.

Q5

How do you use GitHub Environments for deployment approval?

A GitHub Environment is a named deployment target (like staging or production) with optional protection rules. You define environment: production in a job, then go to Repository Settings → Environments → configure protection rules, such as "required reviewers" — named team members who must approve before the job runs. The pipeline pauses and sends a notification. When an approver clicks "Approve", the deployment job continues. This gives you a proper approval gate for production deployments without needing a separate tool.

Ravi's Node.js application ran perfectly on his MacBook — Node.js 20, all dependencies installed, PostgreSQL 14. The CI pipeline also passed — GitHub runners use Ubuntu with Node.js 20. But when the application deployed to the production EC2 server, it crashed immediately. Now it runs the same way everywhere. The container is the environment. The environment travels with the code.

Core Concept

📦 What is Docker — Simply Explained

📌 Definition

Docker is a tool that packages your application and everything it needs to run — the code, the runtime, the libraries, the configuration — into a single portable unit called a container. A container runs identically on any machine that has Docker installed, regardless of the underlying operating system.

🚢

Analogy — Docker is Like a Shipping Container

Before shipping containers, loading a ship was chaotic — every item needed its own special handling. After containers were invented, you could pack anything inside a standard-sized metal box. A crane picks up the box and places it on a ship, then a truck, then a train — the box works on all of them without modification. Docker containers are exactly this for software. You pack your app into a container. It runs on your laptop, on GitHub's runner, on AWS EC2, on Kubernetes — all the same way, no special handling needed.

Docker Image vs Docker Container

A Docker image is the blueprint — a read-only template with all the code and settings inside. A Docker container is a running instance of an image. Like: image = blueprint of a house, container = the actual house you built from it. One image can run as many containers as needed.

Docker Registry

A registry is where Docker images are stored. Docker Hub is the public registry (free). AWS ECR (Elastic Container Registry) is private — your company's images stay inside AWS. The pipeline builds an image and pushes it to the registry. Deployment pulls from the registry.

Dockerfile

📝 The Dockerfile — Every Word Explained

A Dockerfile is a text file with instructions for building a Docker image. Each instruction creates a new layer in the image. Let us read a real Dockerfile for the CloudMart Node.js app, word by word:

Dockerfile — CloudMart Node.js AppDOCKERFILE
# ─── INSTRUCTION 1: FROM ─────────────────────────────────────────────
# "FROM" → the base image to start from
# Every Docker image is built ON TOP of another image
# "node:20-alpine" means:
#   → node    = an image with Node.js pre-installed
#   → 20      = Node.js version 20
#   → alpine  = based on Alpine Linux (a tiny 5MB Linux distro)
#              = makes our final image much smaller than using ubuntu
FROM node:20-alpine

# ─── INSTRUCTION 2: WORKDIR ──────────────────────────────────────────
# "WORKDIR" → set the working directory INSIDE the container
# All following commands (COPY, RUN) happen in this folder
# If this folder does not exist, Docker creates it automatically
# Think of it as "cd /app" but permanent
WORKDIR /app

# ─── INSTRUCTION 3: COPY package files first (important optimisation)
# "COPY" → copy files FROM your machine TO inside the container
# Format: COPY <source-on-your-machine>  <destination-inside-container>
# We copy ONLY package.json and package-lock.json first (not all code)
# Reason: Docker caches each layer — if package files didn't change,
#         the next "RUN npm ci" layer is reused from cache → faster builds
COPY package.json package-lock.json ./

# ─── INSTRUCTION 4: RUN ──────────────────────────────────────────────
# "RUN" → execute a shell command while BUILDING the image
# This is NOT run at container startup — it runs during image creation
# "npm ci" → clean install all dependencies from package-lock.json
# "--only=production" → skip devDependencies (Jest, ESLint etc)
#                       these are not needed at runtime — smaller image
RUN npm ci --only=production

# ─── INSTRUCTION 5: COPY the rest of the app code ───────────────────
# Now we copy all the remaining application code
# We did this AFTER npm ci so package install is cached separately
# "." means "everything in current folder" → copies to WORKDIR (/app)
COPY . .

# ─── INSTRUCTION 6: EXPOSE ───────────────────────────────────────────
# "EXPOSE" → tells Docker that the container listens on this port
# This is DOCUMENTATION only — it does not actually open the port
# To actually open the port, you use "-p 3000:3000" when running
EXPOSE 3000

# ─── INSTRUCTION 7: USER (Security Best Practice) ───────────────────
# By default, containers run as root user — this is a security risk
# "USER node" → switch to the non-root "node" user (built into node images)
# Run processes as least-privileged user → best practice in production
USER node

# ─── INSTRUCTION 8: CMD ──────────────────────────────────────────────
# "CMD" → the default command to run when the CONTAINER STARTS
# Use JSON array format (exec form) — not string format
# This is different from RUN → CMD runs at container startup, not build time
# There can only be ONE CMD per Dockerfile (the last one wins)
CMD ["node", "app.js"]
Multi-Stage Build

🏗 Multi-Stage Build — Production-Grade Dockerfile

A multi-stage build uses multiple FROM instructions in one Dockerfile. The idea is: use a large image for building, then copy only the output to a small image for running. This keeps production images tiny and secure — no build tools, no source code, no dev dependencies.

Dockerfile.multistage — Two-Stage Production BuildDOCKERFILE
# ════ STAGE 1: BUILD STAGE ═══════════════════════════════════════════
# This stage has Node.js + all dev tools needed to build the app
# We call it "builder" — just a label we choose
FROM node:20-alpine AS builder

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci           # install ALL dependencies (including devDeps)
COPY . .
RUN npm run build     # compile TypeScript or build React app → outputs to /app/dist
RUN npm test          # run tests as part of the image build

# ════ STAGE 2: PRODUCTION STAGE ══════════════════════════════════════
# This is the FINAL image — small, clean, production-ready
# It starts fresh from node:20-alpine again
FROM node:20-alpine AS production

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --only=production    # only runtime dependencies

# "COPY --from=builder" → copy files FROM the builder stage, not from your machine
# We only copy the compiled output — NOT the source code or test files
COPY --from=builder /app/dist ./dist

EXPOSE 3000
USER node
CMD ["node", "dist/app.js"]

# Result: Stage 1 image = ~400MB (has source + dev tools)
#         Stage 2 image = ~80MB  (only runtime + compiled output)
# Docker uses ONLY the final stage — stage 1 is discarded

The .dockerignore File

Like .gitignore for Git, a .dockerignore file tells Docker which files to skip when copying from your machine. Always create one — it keeps images small and avoids copying sensitive files.

.dockerignoreTEXT
# Exclude these folders/files when running COPY . .
node_modules      # 200MB+ folder — rebuilt inside container, don't copy
.git              # Git history — not needed inside container
.github           # GitHub Actions files — not needed at runtime
coverage/         # Test coverage reports
*.test.js         # Test files — don't include in production image
.env              # Environment file with secrets — NEVER copy into image
Dockerfile        # The Dockerfile itself — no need to include
README.md         # Documentation

🎯 Chapter 5 Interview Questions

📋 Docker Questions for DevOps Interviews

These are the most commonly asked Docker questions for 3-5 YOE roles.

Q1

What is the difference between a Docker image and a Docker container?

A Docker image is a static, read-only template — it contains the application code, runtime, libraries, and all dependencies packaged together. It is like a blueprint or a class in object-oriented programming. A Docker container is a running instance of an image — it is the actual process that executes. You can run multiple containers from one image simultaneously. When a container stops, the image remains unchanged. Changes made inside a running container are lost unless you commit them to a new image.

Q2

What is a multi-stage Docker build and why is it important in CI/CD?

A multi-stage build uses multiple FROM instructions in one Dockerfile. The first stage (build stage) uses a larger image with all build tools — compilers, test runners, dev dependencies — to build the application. The second stage (production stage) starts fresh from a minimal base image and only copies the compiled output from the first stage. The final image is much smaller because it contains no source code, no test files, and no build tools. In CI/CD, this is important because smaller images pull faster, deploy faster, have a smaller attack surface for security, and cost less in registry storage.

💬 Always mention the three benefits: smaller size, faster deploy, better security. This shows you think about production quality.

Q3

What is Docker layer caching and how do you optimise a Dockerfile for it?

Docker builds images layer by layer — each instruction creates one layer. Docker caches each layer and reuses the cache if that layer has not changed. If layer 5 changes, all layers after 5 are rebuilt, but layers 1–4 are reused from cache. To optimise, you should put instructions that change rarely near the top and instructions that change frequently near the bottom. The most important optimisation is to copy package.json first, run npm install, and then copy the application code. This way, when only your code changes (which is every commit), the expensive npm install layer is served from cache and the build is much faster.

Q4

What is the difference between CMD and ENTRYPOINT in a Dockerfile?

CMD defines the default command to run when a container starts. It can be overridden when you run the container — for example, docker run myapp bash replaces CMD with "bash". ENTRYPOINT defines the main executable that always runs — arguments passed to docker run are appended to it rather than replacing it. In practice, I use CMD for containers where the command might change (like development containers), and ENTRYPOINT for production containers where you always want the same process to run regardless of arguments.

Q5

How does Docker fit into a CI/CD pipeline?

Docker sits at the centre of a modern CI/CD pipeline. The pipeline uses Docker in three ways. First, the pipeline itself may run inside Docker containers — GitHub Actions runners use Docker containers to provide consistent build environments. Second, the pipeline builds a Docker image of the application as an artifact — this image is tagged with the git commit SHA for traceability. Third, the image is pushed to a registry like AWS ECR, and deployment simply pulls the latest image and runs it. This means every environment — CI, staging, production — runs the exact same image, eliminating environment inconsistencies entirely.

Jenkins Architecture

🔧 Jenkins Architecture — Master and Agent

📌 What is Jenkins?

Jenkins is an open-source automation server written in Java. You install it on a server, connect it to your Git repository, and it automatically runs your pipeline every time code is pushed. It is highly customisable through 1,800+ plugins. Jenkins is used by companies like LinkedIn, Netflix, and almost every large IT company in India for on-premise CI/CD.

🖥 Jenkins Master (Controller)

The brain of Jenkins. It: reads the Jenkinsfile and decides what to run, schedules jobs and distributes work to agents, stores build history and logs, provides the web UI for viewing pipelines, manages credentials and plugins. Never run heavy build tasks on the master — it should only orchestrate.

⚙️ Jenkins Agent (Node)

The worker machine that actually runs your pipeline steps. You can have multiple agents — Linux agents for building Node.js apps, Windows agents for .NET, agents with Docker installed for container builds. Agents connect to the master via SSH or JNLP (a Java protocol). One pipeline job runs on one agent at a time.

🏗️

Analogy — Jenkins is Like a Construction Company

The Jenkins Master is the project manager sitting in the office. It receives the blueprint (Jenkinsfile), assigns tasks, and tracks progress. The Jenkins Agents are the construction workers out in the field. The manager does not swing a hammer — they manage. Workers do the actual building. Multiple workers can work on different parts of the building simultaneously. This is exactly how Jenkins scales — one master, many agents running parallel jobs.

The Jenkinsfile

📄 Declarative Jenkinsfile — Every Word Explained

A Jenkinsfile is a text file stored in your Git repository (at the root level) that defines your entire Jenkins pipeline. It uses a language called Groovy DSL — but you do not need to know Groovy. Jenkins has a Declarative syntax (the modern, recommended way) that reads almost like English.

Jenkinsfile — CloudMart India Full PipelineGROOVY DSL (Declarative)
// ═══ PART 1: PIPELINE BLOCK ═════════════════════════════════════════
// "pipeline" → the top-level block — wraps everything
// ALL declarative pipelines must start with this word
pipeline {

    // ═══ PART 2: AGENT ════════════════════════════════════════════════
  // "agent" → WHERE should this pipeline run?
  // "agent any" → run on any available Jenkins agent (worker machine)
  // Other options: agent { label 'docker' } → only on agents tagged 'docker'
  //                agent none → define agent per stage (more flexible)
  agent any

    // ═══ PART 3: ENVIRONMENT VARIABLES ═══════════════════════════════
  // "environment" → define variables available to ALL stages
  // Like a top-level env: block in GitHub Actions
  environment {
    APP_NAME     = 'cloudmart-app'
    ECR_REGISTRY = '123456789.dkr.ecr.ap-south-1.amazonaws.com'
    IMAGE_TAG    = "${env.BUILD_NUMBER}"
        // "env.BUILD_NUMBER" → built-in Jenkins variable
    // Jenkins automatically increments BUILD_NUMBER for each run: 1, 2, 3...
    // Other built-in variables: env.BRANCH_NAME, env.GIT_COMMIT, env.JOB_NAME

    AWS_CREDENTIALS = credentials('aws-ecr-credentials')
        // "credentials('name')" → read a secret stored in Jenkins Credentials Store
    // 'aws-ecr-credentials' is the ID you gave the credential when you added it
    // Credentials are NEVER hardcoded — always stored in Jenkins, not in code
  }

    // ═══ PART 4: OPTIONS ══════════════════════════════════════════════
  // Pipeline-level settings
  options {
    timeout(time: 30, unit: 'MINUTES')  // fail if pipeline runs more than 30 min
    buildDiscarder(logRotator(numToKeepStr: '10'))  // keep only last 10 builds
    disableConcurrentBuilds()           // don't run two builds at the same time
  }

    // ═══ PART 5: STAGES ═══════════════════════════════════════════════
  // "stages" → container for all your pipeline stages
  // Stages run IN ORDER — one after another (unless parallelised)
  stages {

        // ─── STAGE 1: Checkout ────────────────────────────────────────
    // "stage('Name')" → one step in your pipeline
    // The name appears in the Jenkins UI as a coloured box
    stage('Checkout') {
      steps {
                // "steps" → the actual commands/actions inside this stage
        checkout scm
                // "checkout scm" → git clone the repository configured in this Jenkins job
        // "scm" = Source Control Management — reads the Git URL from job config
      }
    }

        // ─── STAGE 2: Install Dependencies ───────────────────────────
    stage('Install Dependencies') {
      steps {
        sh 'npm ci'
                // "sh 'command'" → run a shell command on the agent
        // "sh" = shell = runs on Linux/Mac agents
        // For Windows agents: use "bat 'command'" (batch) instead
      }
    }

        // ─── STAGE 3: Run Tests ───────────────────────────────────────
    stage('Test') {
      steps {
        sh 'npm test'
      }
      post {
                // "post" inside a stage → runs AFTER this specific stage
        // "always" → runs whether the stage passed or failed
        always {
          junit 'test-results/**/*.xml'
                    // "junit" → Jenkins plugin that reads JUnit XML test reports
          // Jenkins displays test pass/fail results with trend graphs
        }
      }
    }

        // ─── STAGE 4: Build Docker Image ─────────────────────────────
    stage('Build Docker Image') {
      steps {
        script {
                    // "script {}" → use when you need Groovy logic (variables, loops, if)
          // Inside script, you have full Groovy access
          dockerImage = docker.build("${ECR_REGISTRY}/${APP_NAME}:${IMAGE_TAG}")
                    // "docker.build()" → Jenkins Docker plugin
          // Builds image and stores reference in "dockerImage" variable
        }
      }
    }

        // ─── STAGE 5: Push to ECR ────────────────────────────────────
    stage('Push to ECR') {
      steps {
        script {
          docker.withRegistry("https://${ECR_REGISTRY}", 'ecr:ap-south-1:aws-ecr-credentials') {
                        // "docker.withRegistry" → logs in to registry, runs block, logs out
            // Credentials managed by Jenkins — never exposed
            dockerImage.push(IMAGE_TAG)    // Push with build number tag
            dockerImage.push('latest')      // Also tag as "latest"
          }
        }
      }
    }

        // ─── STAGE 6: Deploy to Staging ──────────────────────────────
    stage('Deploy to Staging') {
      when {
                // "when" → conditional — only run this stage IF this condition is true
        branch 'main'
                // Only deploy when the pipeline is running on the "main" branch
        // Feature branch pushes run test+build but do NOT deploy
      }
      steps {
        sh """
          aws ecs update-service \\
            --cluster cloudmart-staging \\
            --service cloudmart-app \\
            --force-new-deployment
        """
                // Triple-quoted strings allow multi-line shell commands
        // \\ = line continuation inside triple-quoted string
      }
    }

  }

    // ═══ PART 6: POST — After all stages finish ════════════════════
  post {
        // "post" at pipeline level → runs after ALL stages
    // Different blocks run based on the final result

    success {
            // Runs ONLY if all stages passed
      echo 'Pipeline completed successfully! Notifying team.'
      slackSend(channel: '#deployments', message: "✅ ${APP_NAME} deployed to staging")
    }

    failure {
            // Runs ONLY if any stage failed
      echo 'Pipeline FAILED! Sending alert.'
      slackSend(channel: '#alerts', color: 'danger', message: "❌ Build failed: ${env.JOB_NAME} #${env.BUILD_NUMBER}")
      mail(to: 'devops@cloudmart.in', subject: "Build Failed", body: "Check: ${env.BUILD_URL}")
    }

    always {
            // Runs regardless of success or failure — good for cleanup
      cleanWs()
            // "cleanWs()" → Jenkins Workspace Cleanup plugin
      // Deletes all files from the agent workspace after the build
      // Important: agents have limited disk — always clean up
    }
  }

}
Parallel Stages

⚡ Running Stages in Parallel — Speed Up Your Pipeline

Just like GitHub Actions runs jobs in parallel by default, Jenkins can run stages in parallel inside a single job using the parallel block. Use this to run tests and code quality checks at the same time.

Parallel Stages in JenkinsfileGROOVY DSL
    stage('Quality Checks') {
      parallel {
                // "parallel {}" → all stages inside run AT THE SAME TIME

        stage('Unit Tests') {
          steps { sh 'npm test' }
        }

        stage('Code Lint') {
          steps { sh 'npm run lint' }
        }

        stage('Security Scan') {
          steps { sh 'npm audit --audit-level=high' }
        }
      }
            // All three run simultaneously — total time = longest single stage
      // Instead of 3 min + 2 min + 4 min = 9 min sequential,
      // parallel gives: max(3,2,4) = 4 min total — more than 2x faster
    }
Credentials in Jenkins

🔐 Jenkins Credentials — How to Store Secrets Safely

Where to Add Credentials

Go to Jenkins Dashboard → Manage Jenkins → Credentials → System → Global credentials → Add Credentials. Give each credential a unique ID (like "aws-ecr-credentials") — this ID is what you reference in your Jenkinsfile.

Types of Credentials

Username with password — for Docker Hub, databases. Secret text — for API tokens, Sonar tokens. SSH Username with private key — for SSH into servers. AWS Credentials — via the AWS credentials plugin for ECR, ECS, S3 access.

Using Credentials in JenkinsfileGROOVY DSL
  environment {
        // Method 1: Bind credential to environment variable
    // Jenkins sets SONAR_TOKEN automatically from the stored credential
    SONAR_TOKEN = credentials('sonarqube-token')
  }

    stage('SonarQube Analysis') {
      steps {
                // Method 2: withCredentials block — safer, only available inside block
        withCredentials([usernamePassword(
          credentialsId: 'docker-hub-creds',
          usernameVariable: 'DOCKER_USER',
          passwordVariable: 'DOCKER_PASS'
        )]) {
          sh 'echo $DOCKER_PASS | docker login -u $DOCKER_USER --password-stdin'
                    // Jenkins masks $DOCKER_PASS in logs — shows *** instead
        }
      }
    }

Run Jenkins Locally Using Docker

The fastest way to start Jenkins — no installation needed, just Docker.

  2. 2

  3. 3

  4. 4
    Create a Pipeline job
    Click "New Item" → name it "cloudmart-pipeline" → select "Pipeline" → click OK. In the configuration, scroll to "Pipeline" section → select "Pipeline script" → paste a simple Jenkinsfile (just a hello world: pipeline { agent any stages { stage('Hello') { steps { echo 'Hello CloudMart!' } } } }).

🎯 Chapter 6 Interview Questions

📋 Jenkins — High-Frequency Interview Questions

Jenkins questions come up in almost every DevOps interview in India.

Q1

What is Jenkins and what is it used for?

Jenkins is an open-source automation server written in Java, used primarily for Continuous Integration and Continuous Deployment. It monitors a source code repository, and whenever new code is pushed, it automatically runs a series of tasks defined in a Jenkinsfile — such as building the application, running tests, creating Docker images, and deploying to servers. Jenkins is highly extensible with over 1,800 plugins and can be installed on any server that runs Java. It is widely used in enterprise companies in India for on-premise CI/CD because it runs on your own infrastructure rather than on a third-party cloud.

Q2

What is the difference between Declarative and Scripted pipeline in Jenkins?

Jenkins supports two syntaxes. Declarative pipeline is the newer, recommended approach — it has a strict, structured format using the pipeline { } block with predefined sections like agent, stages, and post. It is easier to read, has built-in validation, and is less error-prone. Scripted pipeline is the older approach — it uses a node { } block and gives full Groovy programming power, allowing complex logic, loops, and dynamic behaviour. In practice, I use Declarative for most pipelines because it is cleaner and easier to maintain. I use a script { } block inside Declarative when I need Groovy logic for specific steps.

💬 This is asked in almost every Jenkins interview. Know both names and one key difference.

Q3

What is a Jenkins agent and why do you use multiple agents?

A Jenkins agent (also called a node) is a machine that the Jenkins master connects to and uses to run pipeline jobs. The master itself should only orchestrate — all heavy build work should run on agents. You use multiple agents for two reasons. First, scalability — multiple jobs can run in parallel on different agents, reducing wait times. Second, specialisation — different agents can be configured for different workloads. For example, a "docker" agent with Docker installed for container builds, a "java" agent with JDK for Maven builds, or a Windows agent for .NET applications. You assign agents to jobs using the label field — e.g., agent { label 'docker' }.

Q4

How do you handle credentials and secrets in Jenkins?

I store all credentials in the Jenkins Credentials Store — accessible via Manage Jenkins → Credentials. Jenkins supports several types: username/password, secret text, SSH private keys, and AWS credentials. Each credential gets a unique ID. In the Jenkinsfile, I reference them using the credentials('credential-id') function in the environment block, or using the withCredentials([]) block for more granular control. Jenkins automatically masks credential values in build logs — they appear as asterisks. I never hardcode secrets in the Jenkinsfile or commit them to Git.

Q5

What are post build actions in Jenkins and what types are available?

The post block in a Declarative Jenkinsfile defines actions that run after the pipeline or a specific stage completes. It has several condition blocks: always — runs regardless of the result (used for cleanup with cleanWs()); success — runs only when everything passed (used for sending success notifications or triggering the next pipeline); failure — runs only when something failed (used for sending alerts to Slack, email, or PagerDuty); unstable — runs when tests failed but the build compiled; changed — runs when the build result is different from the previous run (from green to red, or red to green). I always include at least a failure notification and an always-cleanup in my pipelines.

Q6

How do you trigger a Jenkins pipeline automatically when code is pushed to GitHub?

There are two ways. The recommended way is using GitHub webhooks — in your GitHub repository settings, you add a webhook URL pointing to http://your-jenkins-url/github-webhook/. Whenever code is pushed, GitHub sends an HTTP POST request to Jenkins, which triggers the pipeline immediately. You also need the GitHub plugin installed in Jenkins and "GitHub hook trigger for GITScm polling" checked in the job configuration. The second way is polling — Jenkins periodically checks GitHub for new commits using a cron schedule (e.g., every 5 minutes with "H/5 * * * *"). Webhooks are preferred because they trigger immediately and use no resources when there are no pushes.
