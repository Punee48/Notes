🐛 "Tests Are Green But Production Is Broken!"

🧪
CloudMart India · Post-Release Review · Week 8

The Pipeline Lied — 100% Pass, 0% Confidence

The CI pipeline had been running for three weeks. Tests were passing on every push. The team felt confident. Then on a Tuesday, a bug in the payment checkout module slipped to production — a user's cart total was doubling on page refresh. The pipeline had shown green. How?

Arjun investigated. The team only had unit tests — tests for individual functions in isolation. Nobody had written integration tests — tests that check how multiple parts work together. The cart doubling bug happened because two functions worked perfectly alone but broke when they interacted with each other. The unit tests never caught it because they never tested the interaction.

More importantly, the team had no code coverage metric. They thought all code was tested, but in reality only 31% of the codebase had tests. 69% had no tests at all. The pipeline was green because the tests that existed were passing — but most of the code was untested entirely.

That meeting ended with one decision: build a proper test strategy with all three test types, a coverage threshold, and quality gates that block deployment if coverage drops below 80%.

Core Concept

🔺 The Test Pyramid — The Most Important Testing Concept

📌 The Testing Rule

Write many unit tests (fast, cheap, specific), some integration tests (medium speed, medium scope), and few end-to-end tests (slow, expensive, full flow). This ratio — many at the bottom, few at the top — is called the Test Pyramid.

The Test Pyramid — CloudMart India

🌐 E2E Tests (5–10%)
🔗 Integration Tests (20–30%)
⚡ Unit Tests (60–70%)

Bottom = many, fast, cheap. Top = few, slow, expensive.

⚡ Unit Tests

Test a single function or method in complete isolation. All external things (database, API, other functions) are replaced with mocks — fake versions. Very fast: 1000 tests run in under 5 seconds. Tools: Jest (JS), JUnit (Java), pytest (Python).

🔗 Integration Tests

Test how multiple parts work together. For example: does the order service correctly talk to the payment service and the database? No mocks — uses real connections. Slower: tens of seconds to minutes. Tools: Supertest (Node), Spring Test (Java).

🌐 E2E Tests

Test the entire application flow from a user's point of view — opens a real browser, clicks buttons, fills forms. The most realistic but slowest. Minutes to run. Tools: Cypress, Playwright, Selenium.

Code Coverage

📊 Code Coverage — The Safety Net Measurement

Code coverage is a percentage that tells you how much of your application code is actually executed when your tests run. If you have 100 lines of code and your tests execute 80 of them, your coverage is 80%. Coverage below 80% in a production application is considered risky.

// ─── app/cart.js ─────────────────────────────────────────────────────
// This is the function we want to test
function calculateCartTotal(items, discountCode) {
    // sum all item prices
  let total = items.reduce((sum, item) => sum + item.price * item.qty, 0);

    // apply discount if code is valid
  if (discountCode === 'DIWALI10') {
    total = total * 0.90;  // 10% off
  } else if (discountCode === 'FLAT50') {
    total = total - 50;     // flat ₹50 off
  }

  return Math.max(0, total); // total can never be negative
}

// "describe" = group related tests together under one name
describe('calculateCartTotal', () => {

    // "test" (or "it") = one individual test case

        // "expect" = the actual value we got
        // ".toBe()" = the value we EXPECT (assert)
    expect(calculateCartTotal(items, null)).toBe(550); // 200×2 + 150×1 = 550
  });

🎯 Chapter 7 Interview Questions

📋 Testing Questions for DevOps / 4 YOE Interviews

These questions test whether you understand testing depth, not just tools.

Q1

What is the test pyramid and why does it matter in CI/CD?

The test pyramid is a strategy that says you should have many unit tests at the base, fewer integration tests in the middle, and very few end-to-end tests at the top. Unit tests are fast, cheap, and specific — they run in milliseconds and give immediate feedback. E2E tests are slow and fragile. In CI/CD, if you invert the pyramid — many E2E tests, few unit tests — your pipeline takes 30 minutes to run instead of 3, and minor UI changes break dozens of tests. The pyramid shape keeps pipelines fast, reliable, and cheap to maintain.

Q2

What is code coverage and what is a good coverage target?

Code coverage measures what percentage of your source code is executed when your tests run. A coverage of 80% means 80% of lines, branches, and functions are tested. The industry standard for production applications is 80% minimum, with critical modules like payment processing requiring 90%+. However, I also explain to teams that 100% coverage does not mean zero bugs — you can cover every line but still write bad assertions. Coverage is a safety net measurement, not a guarantee of quality. In the pipeline, we set coverage thresholds in Jest config — the build fails automatically if coverage drops below the defined percentage.

💬 Mentioning that 100% ≠ zero bugs shows senior thinking. Most candidates just say "aim for 100%".

Q3

What is the difference between unit tests and integration tests?

Unit tests test a single function or class in complete isolation — all dependencies like databases, APIs, and external services are replaced with mocks. They run in milliseconds and tell you if a specific piece of logic is correct. Integration tests test how multiple components work together with real connections — a real test database, real service calls. They verify that the plumbing between components is correct. In a CI/CD pipeline, I always run unit tests first because they are fast. If unit tests fail, there is no point running the slower integration tests. Integration tests only run after unit tests pass.

Q4

What is a smoke test and when does it run?

A smoke test is a minimal, fast test that runs immediately after deployment to verify that the application is alive and the most critical functions work — like the home page loads, the login endpoint responds, and the health check returns 200. It is named after the smoke test in electronics — power it on and check if smoke comes out. In CI/CD, smoke tests run as the first check after each deployment. If the smoke test fails, the pipeline triggers an automatic rollback immediately, before real users are affected.

Q5

How do you run tests that need a database in a CI/CD pipeline?

I use service containers in GitHub Actions or Docker Compose in Jenkins. In GitHub Actions, the services: block spins up a Docker container (like postgres:15) alongside your test job. The test job connects to it using localhost and the container's port. Health checks ensure the service is ready before tests start. This is better than mocking the database for integration tests because you are testing against the real database engine. After the job completes, GitHub destroys the service container automatically. The test database never touches production data.

Core Concept

🔬 What is SonarQube — Static Code Analysis Explained

📌 Definition

SonarQube is a static application security testing (SAST) tool that analyses your source code without running it — looking for bugs, security vulnerabilities, code smells, and duplications. It generates a report with a Quality Gate — a pass/fail result based on configurable thresholds. In CI/CD, the pipeline waits for this result and stops if the quality gate fails.

🐛 Bugs

Code that will definitely cause wrong behaviour or crashes at runtime. Example: using a variable before checking if it is null. SonarQube finds these by analysing code paths. Rated: Blocker, Critical, Major, Minor.

🔒 Security Vulnerabilities

Code patterns that attackers can exploit — SQL injection, XSS (cross-site scripting), hardcoded passwords, insecure HTTP connections, weak cryptography. These map to OWASP Top 10 security risks.

🌡️ Code Smells

Code that works but is hard to maintain — functions that are too long, too many parameters, deeply nested conditions, duplicated logic. Not bugs now, but they create bugs in the future when someone misunderstands the code.

📋 Duplications

The same block of code copy-pasted in multiple places. When that logic needs to change, a developer might update one copy and forget the others — causing inconsistent behaviour. SonarQube flags this so you can extract shared logic into a function.

Quality Gates

🚦 Quality Gates — The Pass/Fail Decision

A Quality Gate in SonarQube is a set of conditions that your code must meet to be considered "good enough to deploy". If any condition fails, the quality gate returns FAILED and your CI/CD pipeline stops deployment. If all conditions pass, it returns PASSED and the pipeline continues.

ConditionThresholdWhat it means
New Blocker Issues= 0Zero new blocker-level bugs in this PR/push
New Critical Issues= 0Zero new critical bugs
New Security Vulnerabilities= 0No new security holes introduced
New Coverage≥ 80%New code must be 80%+ covered by tests
New Duplicated Lines≤ 3%New code must not be highly duplicated
New Maintainability Rating≥ ANew code must have rating A (least technical debt)

Important: SonarQube's default "Sonar Way" quality gate checks new code only — code introduced in the current PR or push. This is smarter than checking everything — it does not punish you for old legacy issues, it only blocks new problems.

Pipeline Integration

⚙️ SonarQube in GitHub Actions — Word by Word

.github/workflows/sonar-analysis.ymlYAML
name: SonarQube Code Analysis
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  sonar-scan:
    name: SonarQube Analysis
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code with full history
        uses: actions/checkout@v4
        with:
          fetch-depth: 0
                    # "fetch-depth: 0" = download the COMPLETE git history
          # SonarQube needs full history to calculate "new code" correctly
          # Default fetch-depth is 1 (only latest commit) — not enough for Sonar

      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci

      - name: Run tests and generate coverage report
        run: npm run test:coverage
                # SonarQube reads the coverage report generated here
        # Coverage report is typically at: coverage/lcov.info (LCOV format)

      - name: SonarQube Scan
        uses: SonarSource/sonarqube-scan-action@master
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
                    # SONAR_TOKEN → generated in SonarQube: My Account → Security → Tokens
          # Never hardcode this — always use a GitHub Secret
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
                    # URL of your SonarQube server, e.g. https://sonar.cloudmart.in
          # For SonarCloud (the free cloud version): https://sonarcloud.io

      - name: Check Quality Gate Result
        uses: SonarSource/sonarqube-quality-gate-action@master
        timeout-minutes: 5
                # This step WAITS for SonarQube to finish analysis and return the gate result
        # If quality gate = FAILED → this step fails → pipeline stops
        # If quality gate = PASSED → pipeline continues to Docker build + deploy
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

📋 Code Quality Questions

These questions test whether you understand WHY code quality matters, not just the tool name.

Q1

What is SonarQube and how does it fit in a CI/CD pipeline?

SonarQube is a static code analysis tool that scans your source code — without running it — to find bugs, security vulnerabilities, code smells, and duplications. In a CI/CD pipeline, it runs as a stage after the tests pass and before the Docker image is built. The pipeline sends the code to SonarQube, which analyses it and returns a Quality Gate result — pass or fail. If the quality gate fails because of new critical bugs or security vulnerabilities, the pipeline stops and deployment does not happen. This prevents known defects from reaching production.

Q2

What is SAST and how is it different from DAST?

SAST (Static Application Security Testing) analyses your source code or compiled binary without running the application — it reads the code and identifies patterns that indicate security risks. Tools: SonarQube, Checkmarx, Veracode. It runs early in the pipeline — at the code review or build stage. DAST (Dynamic Application Security Testing) tests the running application by sending malicious inputs — like a real attacker would. Tools: OWASP ZAP, Burp Suite. It runs after deployment to a test environment. Both are needed: SAST catches code-level issues early, DAST catches runtime vulnerabilities that only appear when the app is running.

💬 Knowing both SAST and DAST is a strong differentiator — most candidates know only one.

Q3

What is a SonarQube Quality Gate?

A Quality Gate is a set of configurable conditions that define whether code is acceptable for release. It is like a checkpoint — if any condition fails, the gate blocks the deployment. The default "Sonar Way" quality gate focuses on new code only — code introduced in the current push or PR. Conditions typically include: zero new blocker bugs, zero new security vulnerabilities, new code coverage above 80%, and new code maintainability rating of A. This "new code" focus is very practical — it prevents the quality gate from blocking releases because of old legacy issues while ensuring new features meet quality standards.

Q4

What are OWASP Top 10 and how does SonarQube help with them?

The OWASP Top 10 is a list of the 10 most critical web application security risks, published by the Open Web Application Security Project. The list includes: injection (SQL, NoSQL), broken authentication, sensitive data exposure, XML external entities, broken access control, security misconfiguration, cross-site scripting (XSS), insecure deserialisation, using components with known vulnerabilities, and insufficient logging. SonarQube maps its security vulnerability rules directly to these categories — when it finds an SQL injection pattern in your code, it labels it as OWASP A1. This helps developers understand the risk category and prioritise fixes.

Q5

What is the difference between a bug and a code smell in SonarQube?

A bug in SonarQube represents code that will almost certainly cause incorrect behaviour or a crash at runtime — it is a definite defect. Examples: a null pointer dereference, an unreachable catch block, or a resource that is opened but never closed. A code smell is not a bug — the code works correctly today — but it indicates a maintainability problem. Examples: a function with 200 lines of code, a method with 8 parameters, or deeply nested if-statements with cyclomatic complexity above 15. Code smells slow down future development and increase the chance of introducing bugs during maintenance. I prioritise fixing bugs first, then address critical code smells during refactoring sprints.

The Story

🏷️ "Which Image Is Running in Production Right Now?"

📦
CloudMart India · Incident Review · Week 12

The Midnight Question Nobody Could Answer

Production was showing wrong prices for some products. The on-call engineer, Ravi, needed to answer one question immediately: what version of the application is currently running in production? He could not answer it. Every image had been tagged as "latest" and pushed. The last 20 builds all had the same "latest" tag. There was no way to know which code was running.

To rollback, he needed to redeploy the previous version — but there was no previous version to go back to. All older "latest" images had been overwritten by newer ones. The ECR repository had only one image. They had to redeploy from the previous commit, wait for a full build, and lose 45 minutes. If they had proper tagging with git commit SHAs, a rollback would have taken 2 minutes.

This incident led to CloudMart India adopting a proper image tagging strategy — every image gets both a unique commit SHA tag and a version tag. "latest" is still used, but only in addition to the versioned tag, never alone.

Image Tagging Strategy

🏷️ Docker Image Tagging — The Right Way

A Docker image tag is a label given to an image — like a filename. The same image can have multiple tags. Proper tagging is what enables rollbacks, traceability, and environment promotion.

Tag TypeExampleWhen to useGood for rollback?

.github/workflows/build-push-ecr.yml — Full Tagging StrategyYAML
name: Build and Push to ECR — Proper Tagging
on:
  push:
    branches: [main]
  release:
    types: [published]
        # Also trigger when a GitHub Release is published (for version tags)

env:
  AWS_REGION:      ap-south-1
  ECR_REPOSITORY:  cloudmart-app
  AWS_ACCOUNT_ID:  ${{ secrets.AWS_ACCOUNT_ID }}

jobs:
  build-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up image tags
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.AWS_ACCOUNT_ID }}.dkr.ecr.${{ env.AWS_REGION }}.amazonaws.com/${{ env.ECR_REPOSITORY }}
          tags: |
            type=sha,prefix=commit-,format=short
                        # Creates tag: commit-a3f9b2c (short git SHA)
            type=ref,event=branch
                        # Creates tag: main (branch name)
            type=semver,pattern={{version}}
                        # Creates tag: v2.4.1 when a release is published
            type=raw,value=latest,enable={{is_default_branch}}
                        # Creates "latest" only for the default branch (main)
                # After this step: ${{ steps.meta.outputs.tags }} has ALL tags
        # ${{ steps.meta.outputs.labels }} has OCI standard labels

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
                    # OIDC-based auth — no long-lived access keys needed (most secure)
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push with all tags
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags:    ${{ steps.meta.outputs.tags }}
                    # Pushes ALL tags generated by the metadata-action step
          labels:  ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to:   type=gha,mode=max
                    # "cache-from/to: type=gha" → GitHub Actions Cache for Docker layers
          # Reuses unchanged layers from previous builds → much faster builds
AWS ECR

☁️ AWS ECR — Your Private Docker Registry

What is AWS ECR?

📋 Artifact & Registry Questions

Frequently asked in pipeline design and AWS DevOps interviews.

Q1

What is the problem with using only the "latest" Docker tag?

Using only the "latest" tag creates several serious problems. First, no traceability — you cannot tell which version of the code is inside an image tagged "latest". Second, no rollback — every new build overwrites the previous "latest" tag, so you lose the ability to redeploy a previous version quickly. Third, non-deterministic deployments — if two deployments happen close together, one server might pull the old "latest" and another pulls the new one. Best practice is to always tag images with the git commit SHA — this gives every image a unique, immutable identifier. Use "latest" as an additional convenience tag on top of the versioned tag.

Q2

What is AWS ECR and why use it instead of Docker Hub?

AWS ECR is Amazon's managed private container registry. I use it over Docker Hub for production workloads for several reasons. First, security — images are private by default, access is controlled through AWS IAM policies, and there are no public exposure risks. Second, performance — when deploying to ECS or EKS in AWS, pulling from ECR is much faster because the registry is in the same region and network. Third, native integration — ECS, EKS, CodeBuild, and Lambda all integrate with ECR natively without extra authentication steps. Fourth, image scanning — ECR scans images for vulnerabilities automatically on push using Amazon Inspector.

Q3

What is an ECR lifecycle policy and why is it important?

An ECR lifecycle policy is a set of rules that automatically delete old or unused Docker images from your registry. Without one, images accumulate indefinitely — increasing storage costs and making the registry difficult to navigate. A typical policy keeps the last 30 tagged images and immediately deletes untagged (dangling) images. Lifecycle policies run as a background AWS service — you configure them once and ECR handles cleanup automatically. This is a best practice for any active CI/CD pipeline that pushes multiple images per day.

Q4

What is semantic versioning and how do you use it in a pipeline?

Semantic versioning (SemVer) uses a three-part version number: MAJOR.MINOR.PATCH — for example, v2.4.1. MAJOR changes when you make breaking changes. MINOR changes when you add new features backwards-compatibly. PATCH changes for bug fixes. In a CI/CD pipeline, I use GitHub Releases to create version tags. When a team lead creates a release like "v2.4.1" on GitHub, the pipeline is triggered, builds the image, and tags it with both the version (v2.4.1) and a commit SHA. This gives both human-readable version tracking and machine-level traceability.

⏰ "Why Does Deployment Always Need Downtime?"

🚦
CloudMart India · Product Meeting · Week 14

Every Deployment Is a Maintenance Window

The CloudMart product team was frustrated. Every deployment required a "maintenance window" — the website would show "We'll be back soon" for 3–5 minutes while the new version was deployed. This happened 2–3 times a week. Customers were complaining about the interruptions. The business team calculated that each 5-minute downtime during peak hours cost approximately ₹2 lakhs in lost orders.

Arjun explained the root cause: the deployment process was "stop old version, start new version". There was a gap between stopping and starting where nothing was running. The solution was to use deployment strategies that ensure the new version is running before the old version is stopped — zero overlap means zero downtime.

CloudMart adopted Blue-Green deployment for major releases and Canary deployment for risky feature rollouts. The maintenance windows disappeared completely.

Strategy 1

🔵🟢 Blue-Green Deployment — Zero Downtime Guaranteed

📌 How Blue-Green Works

You maintain two identical production environments — Blue (currently live) and Green (new version). Deploy to Green, test it, then switch the load balancer to point to Green. Blue is still running — instant rollback is possible by switching back. After confidence, Blue becomes the new inactive environment for the next deployment.

✈️

Analogy — Like a Runway Switchover

An airport has two runways. Planes are landing on Runway A (Blue). The maintenance team prepares Runway B (Green) — new tarmac, new lights. When B is ready and tested, air traffic control switches all incoming planes to Runway B instantly. Runway A is still intact — if anything is wrong with B, all planes switch back to A in seconds. This is Blue-Green deployment.

✅ Advantages

  • Zero downtime — traffic switch is instant
  • Instant rollback — just point load balancer back to Blue
  • Easy to test Green before going live
  • Same environment as production for final testing

❌ Disadvantages

  • Costs 2x infrastructure — two full environments running
  • Database schema changes are complex (both versions must share DB)
  • Not suitable for continuous deployment (too expensive)

Strategy 2

🕯️ Canary Deployment — Test With Real Users Safely

📌 How Canary Works

Deploy the new version to a small percentage of servers (5–10%). Real user traffic flows to both versions — 5% see the new version, 95% see the old version. Monitor error rates and performance. If metrics are good, gradually increase the percentage. If bad, roll back the 5% immediately — 95% of users were never affected.

🐤

Analogy — The Coal Mine Canary

Coal miners used to carry a canary into new tunnels. If dangerous gas was present, the canary (more sensitive) would be affected first — giving miners time to escape before they were harmed. Canary deployment works the same way — the new code version is deployed to a small group (the "canary") first. If something breaks, it affects only 5% of users (the canary), not everyone. The team detects it quickly and rolls back before the full release causes widespread damage.

✅ When to Use Canary

  • High-risk feature releases (new payment flow)
  • Performance-sensitive changes
  • When you want real user feedback before full rollout
  • A/B testing new UI features

📊 Key Metrics to Monitor

  • Error rate (should not increase)
  • Response latency (should not increase)
  • Business metrics: conversion rate, cart adds
  • Log anomalies and exception counts
Strategy 3

🔄 Rolling Deployment — The Default Strategy

Rolling deployment updates servers one at a time (or in small batches), replacing the old version with the new version gradually. At any point, some servers run old code and some run new code. This is the default ECS deployment strategy and is suitable for most releases.

📋 Deployment Strategy Questions — High Value in Interviews

These are asked in almost every senior DevOps and cloud engineer interview.

Q1

What is Blue-Green deployment and how does rollback work?

Blue-Green deployment maintains two identical production environments. Blue is the current live version and Green is the new version being deployed. The new version is fully deployed and tested on Green while Blue continues serving all traffic. When Green is validated, the load balancer is switched to direct all traffic from Blue to Green — this takes seconds and causes no downtime. If anything goes wrong, rollback is instant — switch the load balancer back to Blue, which is still running. In AWS, this is implemented with two ECS target groups behind an Application Load Balancer, managed by AWS CodeDeploy.

Q2

What is a Canary deployment and when would you use it?

Canary deployment routes a small percentage of production traffic — typically 5–10% — to the new version while the rest continues on the old version. Teams monitor metrics (error rate, latency, business KPIs) on the canary group. If all metrics look healthy, traffic is gradually shifted — 5% → 25% → 50% → 100%. If any metric degrades, the canary is rolled back and only 5% of users were affected. I use Canary for high-risk features, significant architectural changes, or when I want real user validation before full release. Tools for canary: AWS CodeDeploy with linear traffic shifting, Argo Rollouts in Kubernetes.

Q3

What is the difference between rolling and blue-green deployment?

In a rolling deployment, servers are updated one at a time — at any moment, some servers run the old version and some run the new version simultaneously. Infrastructure cost stays at 1x. Rollback means re-deploying the old version progressively. In Blue-Green, the entire new version is deployed to a completely separate environment before any traffic is switched. Both full environments run simultaneously — 2x cost. Rollback is instant — just switch the load balancer. Rolling is the default for most deployments; Blue-Green is used when instant rollback capability and zero-downtime guarantee are required, especially in regulated or financial systems.

Q4

What is a feature flag and how does it relate to deployment strategy?

A feature flag (or feature toggle) is a configuration switch that enables or disables a feature in code at runtime, without redeploying. You deploy code with the new feature but it is gated behind a flag — disabled by default. You enable the flag for specific users, percentage of traffic, or specific regions. This decouples deployment from release — the code is in production but the feature is not visible until the flag is turned on. Tools: LaunchDarkly, AWS AppConfig, environment variables. Combined with Canary, you can deploy to 100% of servers but only enable the feature for 5% of users — finer control than traffic-level canary.

Q5

What is a smoke test in the context of deployments?

A smoke test is a minimal, fast test that runs immediately after deployment to verify the application is alive and critical paths work — typically checking that the health endpoint returns 200, the login API responds, and one or two core business endpoints work. It is not comprehensive — it is designed to catch catastrophic failures within 60 seconds of deployment. In CI/CD, the smoke test result triggers an automatic rollback if it fails — before real users notice. The name comes from electronics: power on a circuit and check if smoke comes out — if yes, shut it down immediately.

The solution was Terraform. All infrastructure — security groups, load balancers, ECS clusters, RDS databases — is defined in Terraform code files. Core Concept

🔧 Terraform in CI/CD — The IaC Pipeline

📌 The IaC Pipeline Pattern

In an IaC (Infrastructure as Code) pipeline: Pull Request opened → run terraform plan (show what changes WOULD happen, no actual change) → post plan as a PR comment → human reviews and approves → merge to main → pipeline runs terraform apply (actually make the changes to AWS).

terraform plan

Compares your .tf files with the actual current state in AWS. Shows exactly what will be created (+), changed (~), or destroyed (-). Makes no changes — it is a dry run / preview. Run on every PR so reviewers see the infrastructure impact before approving.

terraform apply

Actually creates, modifies, or destroys infrastructure in AWS. Always run with -auto-approve in pipelines (non-interactive). Only runs after PR is merged to main and the plan has been reviewed. Never run apply without first reviewing the plan.

.github/workflows/terraform.yml — Complete IaC PipelineYAML
name: Terraform Infrastructure Pipeline
on:
  pull_request:
    paths: ['terraform/**']
        # Only trigger if files inside "terraform/" folder changed
    # App code changes don't trigger this pipeline — only infrastructure changes
  push:
    branches: [main]
    paths: ['terraform/**']

defaults:
  run:
    working-directory: terraform/
        # All "run:" commands execute inside the terraform/ folder by default
    # No need to prefix every command with "cd terraform &&"

jobs:
  terraform-plan:
    name: Terraform Plan (on PR)
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
        # This job ONLY runs on Pull Requests (not on push to main)

    steps:
      - uses: actions/checkout@v4

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: '1.7.0'
                    # Always pin terraform version — a version upgrade can change behaviour

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.TERRAFORM_ROLE_ARN }}
          aws-region: ap-south-1

      - name: Terraform Init
        run: terraform init
                # "terraform init" = initialise the working directory
        # Downloads the required provider plugins (aws, kubernetes etc.)
        # Configures the remote backend (S3 for state storage)
        # Must run BEFORE any other terraform command

      - name: Terraform Format Check
        run: terraform fmt -check
                # Checks that all .tf files are formatted correctly
        # "-check" fails the step if formatting is wrong — does not modify files
        # Developers must run "terraform fmt" before committing

      - name: Terraform Validate
        run: terraform validate
                # Checks syntax and internal consistency of .tf files
        # Does NOT connect to AWS — purely local validation
        # Catches typos, missing required arguments, wrong data types

      - name: Terraform Plan
        id: plan
        run: terraform plan -no-color -out=tfplan
        continue-on-error: true
                # "terraform plan" = connects to AWS, reads current state, shows diff
        # "-no-color" = removes ANSI color codes (better for GitHub PR comments)
        # "-out=tfplan" = saves the plan to a file (used by apply in the next job)
        # "continue-on-error: true" = even if plan fails, continue to post the error as PR comment

      - name: Post Plan as PR Comment
        uses: actions/github-script@v7
        with:
          script: |
            const output = `
            #### Terraform Plan 📋

            \`\`\`
            ${{ steps.plan.outputs.stdout }}
            \`\`\`
            `;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: output
            });
                    # Posts the terraform plan output as a comment on the PR
          # Reviewers see exactly what infrastructure will change before approving

  terraform-apply:
    name: Terraform Apply (on merge to main)
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        # This job ONLY runs when code is pushed/merged to main

    environment: production-infra
        # Require manual approval in GitHub before applying to production

    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: '1.7.0' }
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: ${{ secrets.TERRAFORM_ROLE_ARN }}, aws-region: ap-south-1 }
      - run: terraform init
      - run: terraform apply -auto-approve
                # "-auto-approve" = skip the manual yes/no prompt (required for automation)
        # Safety: The approval gate is the PR review, not the apply prompt
Remote State

🗃️ Terraform Remote State — S3 Backend

Terraform stores the current state of your infrastructure in a state file (terraform.tfstate). Never store this locally — CI/CD pipelines create fresh machines each run. Use S3 as a remote backend so state is shared across all pipeline runs and team members.

terraform/backend.tf — S3 Remote StateHCL
terraform {
  backend "s3" {
    bucket         = "cloudmart-terraform-state-prod"
        # S3 bucket where the state file is stored
    # Create this bucket MANUALLY first (not via Terraform — chicken-and-egg problem)
    key            = "cloudmart/app/terraform.tfstate"
        # Path of the state file inside the bucket (like a folder path)
    region         = "ap-south-1"
    encrypt        = true
        # "encrypt: true" = state file is encrypted at rest in S3 (important!)
    # State file contains sensitive data — resource IDs, sometimes passwords
    dynamodb_table = "cloudmart-terraform-locks"
        # DynamoDB table for state LOCKING
    # When one pipeline run is applying, another cannot start simultaneously
    # Prevents two applies running at the same time and corrupting state
  }
}

📋 Terraform in CI/CD — Asked in IaC and DevOps Interviews

Your Terraform + DevOps background makes these high-value answers.

Q1

What is the CI/CD pattern for Terraform and why is it different from application pipelines?

The Terraform CI/CD pattern separates plan from apply. On a Pull Request, the pipeline runs terraform plan — which connects to AWS, reads the current state, and shows exactly what would change — but makes no actual changes. The plan is posted as a PR comment for human review. Only after the PR is approved and merged to main does the pipeline run terraform apply. This is different from application pipelines where everything after tests passes automatically — infrastructure changes require human review because a wrong change (like deleting a database) can cause immediate, irreversible damage.

Q2

What is Terraform state and why must it be stored remotely in a CI/CD pipeline?

The Terraform state file (terraform.tfstate) is a JSON file that records the current state of all infrastructure Terraform manages — it maps your .tf resource definitions to real AWS resource IDs. Without state, Terraform cannot know what already exists and would try to re-create everything. In a CI/CD pipeline, each run starts with a fresh virtual machine — a local state file would be lost after every run. Remote state in S3 persists across all pipeline runs and allows multiple team members to share the same state. I also enable DynamoDB locking so only one pipeline can apply changes at a time, preventing state corruption from concurrent runs.

Q3

What is configuration drift and how does Terraform prevent it?

Configuration drift happens when infrastructure environments — like staging and production — become different from each other over time, usually because someone made a manual change in the AWS Console. Drift is dangerous because staging no longer accurately represents production, so testing in staging gives false confidence. Terraform prevents drift in two ways. First, all infrastructure changes must go through code — no manual console changes. Second, terraform plan always compares the desired state (.tf files) with the actual current state — it detects and reports drift. Some teams run terraform plan on a schedule (every night) purely to detect drift that may have been introduced manually.

Q4

What does "terraform init" do and when must it run?

terraform init initialises the working directory for Terraform. It does three things: downloads the required provider plugins (like the AWS provider) that are specified in .tf files; configures the remote backend (connects to S3 for state storage); and initialises modules if your configuration uses reusable Terraform modules. It must run before any other Terraform command — before plan, validate, or apply. In CI/CD, it is always the first step in the Terraform job. It is safe to run multiple times — it is idempotent.

Q5

How do you handle Terraform for multiple environments (dev, staging, prod)?

There are two common approaches. The first is Terraform workspaces — a single configuration with different workspaces (dev, staging, prod), each with its own state file. Variables change per workspace. The second is separate directories — a directory per environment (terraform/dev/, terraform/staging/, terraform/prod/) each with its own state file and variable file. I prefer separate directories for production because it prevents accidental changes to the wrong environment and allows different approval workflows per environment. The CI/CD pipeline deploys in sequence: apply to dev → smoke test → apply to staging → integration test → manual approval → apply to production.

Environment Architecture

🌍 The Three-Environment Model

🧪 Development (Dev)

Where developers test their own changes. Small infrastructure, fake/seed data, no real payments or emails. Deploys on every push to develop branch. Secrets: Dev-specific credentials, test API keys. Cost: minimal.

🔬 Staging

Identical to production in configuration and infrastructure size. Used for QA testing, integration testing, and final pre-release validation. Deploys after dev tests pass. Secrets: staging credentials, sandbox payment keys. Must mirror production exactly.

🚀 Production

The live environment serving real customers. Highest level of access control and approval gates. Deploys only after staging passes AND manual approval. Secrets: real production credentials, live payment keys. Strictly monitored.

                    # DEV_DEPLOY_ROLE is stored in the "development" GitHub Environment secrets

    needs: deploy-dev
        # Staging only deploys AFTER dev succeeds

    environment: staging

      - uses: aws-actions/configure-aws-credentials@v4

    runs-on: ubuntu-latest

Secrets Management

🔐 AWS Secrets Manager vs Parameter Store

🔑 AWS Secrets Manager

For sensitive credentials that must be rotated automatically — database passwords, API keys, OAuth tokens. Key features: automatic rotation (changes password in both Secrets Manager and the database without downtime), fine-grained IAM permissions, versioning (can go back to previous secret version). Costs ~$0.40/secret/month. Use for: DB passwords, third-party API keys, JWT secrets.

⚙️ AWS SSM Parameter Store

For non-sensitive configuration and some sensitive values. Two tiers: Standard (free) for config like app version, environment name, service URLs; SecureString (small cost) for sensitive values, encrypted with KMS. Does not have auto-rotation. Use for: database host/port (not password), feature flags, application config.

        uses: aws-actions/aws-secretsmanager-get-secrets@v2
        with:
          secret-ids: |

The Golden Rules of Secrets Management

  • 1.Never hardcode secrets in code — not even in "temporary" commits
  • 2.Never share secrets over Slack, email, or WhatsApp
  • 3.Never commit .env files to Git — add .env to .gitignore immediately
  • 4.Each environment (dev/staging/prod) must have its own separate secrets
  • 5.Rotate secrets regularly — especially after any team member leaves
  • 6.Use least-privilege IAM roles — the pipeline only gets permissions it needs
  • 7.Enable GitHub secret scanning on all repositories — catches accidental pushes
Interview Prep

🎯 Chapter 12 Interview Questions

📋 Environments & Secrets — Senior-Level Questions

These show your understanding of production-grade pipelines beyond just tooling.

Q1

How do you manage different configurations for dev, staging, and production environments?

I use a layered configuration approach. Non-sensitive configuration like service URLs and feature flags are stored in AWS SSM Parameter Store under separate paths per environment: /cloudmart/dev/*, /cloudmart/staging/*, /cloudmart/prod/*. Sensitive credentials like database passwords are in AWS Secrets Manager with separate secrets per environment. In the CI/CD pipeline, each deployment job is linked to a GitHub Environment (dev, staging, production), which has its own set of secrets and its own IAM role with access only to that environment's AWS resources. The application code has zero configuration hardcoded — everything is fetched from Parameter Store or Secrets Manager at startup.

Q2

What is the difference between AWS Secrets Manager and Parameter Store?

Both store configuration and secrets, but with different capabilities. AWS Secrets Manager is specifically designed for sensitive credentials — it supports automatic rotation (changes a database password automatically on a schedule without downtime), charges per secret per month, has rich rotation integrations with RDS and Redshift, and provides a complete audit trail. Parameter Store is for general configuration — it has a Standard tier that is free, a SecureString tier for sensitive values encrypted with KMS, but no automatic rotation. I use Secrets Manager for actual credentials (passwords, API keys) and Parameter Store for application configuration (hostnames, ports, feature flags).

💬 The automatic rotation feature of Secrets Manager is the key differentiator — always mention it.

Q3

What is environment promotion in CI/CD?

Environment promotion is the controlled process of moving the same build artifact (Docker image) progressively through environments — from dev to staging to production — after passing tests and approvals at each stage. The key principle is: build once, deploy everywhere. You build a Docker image exactly once and tag it with the git commit SHA. That exact same image is promoted through environments — you never rebuild for staging or production. This ensures you test the same binary that will run in production. The promotion pipeline: dev deploy → smoke tests → staging deploy → integration and regression tests → manual approval gate → production deploy.

Q4

A developer accidentally commits a secret to a public GitHub repository. What do you do?

First and most importantly, rotate the secret immediately — change the password or revoke the API key regardless of whether it was accessed. This must happen within minutes. Second, check the audit logs of the service the secret belongs to — look for any unauthorized access in the time window between the commit and the rotation. Third, remove the secret from Git history using git-filter-branch or BFG Repo Cleaner — just deleting it in a new commit is not enough, it is still visible in the old commit. Fourth, force-push the cleaned history. Fifth, report the incident to the security team as required by your company policy. For prevention: add GitHub secret scanning, pre-commit hooks with tools like detect-secrets, and add .env to .gitignore at project creation.

Q5

What is the "build once, deploy everywhere" principle and why is it important?

The "build once, deploy everywhere" principle means the Docker image (or binary artifact) is built exactly once from a specific git commit, and that exact same image is deployed to every environment — dev, staging, production — without rebuilding. This is critical for two reasons. First, consistency — you are testing the exact binary that will go to production. If you rebuild for each environment, the builds might differ due to dependency version changes or environment-specific code paths. Second, efficiency — building is expensive; pulling an already-built image from ECR for staging and production is much faster. The image is identified by its git commit SHA tag, making it fully traceable and reproducible.
