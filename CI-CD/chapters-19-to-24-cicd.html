🗄️ "The Deploy Worked But the Database Didn't Match"

⚠️
CloudMart India · Release Night · Week 34

New Code, Old Schema — A Crash Within Seconds

A new feature added a loyalty_points column to the users table. The application code was updated to read and write this column. The Docker image was built, the pipeline passed, and the new pods rolled out successfully to production. Within seconds, every API request started failing with: "column users.loyalty_points does not exist".

The application code expected a column that did not exist in the production database, because the SQL migration to add that column had never been run on production — only on the developer's local database. The application and database were now out of sync, and the entire site was down.

The team rolled back the application — but the rollback also failed initially, because the OLD code expected the OLD schema, and someone had manually run the migration on production while debugging, which broke the rollback path too.

The fix: database migrations must be part of the pipeline, version-controlled like code, run automatically and in the correct order, BEFORE the new application code is deployed — using a tool like Flyway or Liquibase that tracks exactly which migrations have run.

Core Concept

🔧 Flyway — Version-Controlled Database Migrations

📌 How Flyway Works

Flyway is a database migration tool. You write SQL files with a strict naming convention — V1__description.sql, V2__description.sql, etc. Flyway maintains a table called flyway_schema_history in your database that records which versions have already run. When the pipeline runs flyway migrate, Flyway compares the migration files against this history table and runs only the new, unapplied migrations, in order.

db/migrations/ — Versioned SQL Migration FilesSQL
-- ═══ V1__create_users_table.sql ═══════════════════════════════════════
-- "V1" = version 1 — runs FIRST, ever, on a fresh database
-- "__" = double underscore separates version from description
-- Description is for humans only — Flyway ignores it for ordering
CREATE TABLE users (
  id          SERIAL PRIMARY KEY,
  email       VARCHAR(255) UNIQUE NOT NULL,
  name        VARCHAR(255) NOT NULL,
  created_at  TIMESTAMP DEFAULT NOW()
);

-- ═══ V2__create_orders_table.sql ═══════════════════════════════════════
-- Runs SECOND — only after V1 has successfully completed
CREATE TABLE orders (
  id          SERIAL PRIMARY KEY,
  user_id     INTEGER REFERENCES users(id),
  total       DECIMAL(10,2) NOT NULL,
  created_at  TIMESTAMP DEFAULT NOW()
);

-- ═══ V3__add_loyalty_points_to_users.sql ═══════════════════════════════
-- This is the migration the team FORGOT to run in the incident above
-- "ADD COLUMN ... DEFAULT 0" → safe for existing rows, no NULL values created
ALTER TABLE users
  ADD COLUMN loyalty_points INTEGER NOT NULL DEFAULT 0;

-- ═══ V4__add_index_on_orders_user_id.sql ═══════════════════════════════
-- CONCURRENTLY → does NOT lock the table while building the index
-- Critical for production tables with millions of rows
-- Without CONCURRENTLY, this would lock "orders" for the duration —
-- every order placement would freeze until the index finishes building
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);
.github/workflows/db-migrate.yml — Migration in PipelineYAML
  database-migration:
    name: Run Database Migrations
    runs-on: ubuntu-latest
    needs: test
        # Migrations run AFTER tests pass, BEFORE the new application is deployed
    # Order matters: schema must be ready BEFORE new code that depends on it starts
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Run Flyway migrations
        uses: docker://flyway/flyway:10-alpine
        with:
          args: >
            -url=jdbc:postgresql://${{ secrets.DB_HOST }}:5432/cloudmart
            -user=${{ secrets.DB_USER }}
            -password=${{ secrets.DB_PASSWORD }}
            -locations=filesystem:db/migrations
            migrate
                # "migrate" command:
        # 1. Connects to the production database
        # 2. Reads flyway_schema_history table — sees V1, V2 already applied
        # 3. Finds V3, V4 are new — runs them in order, inside a transaction
        # 4. Records V3, V4 in flyway_schema_history as applied
        # If V3 fails halfway → transaction rolls back → database unchanged
        # → pipeline FAILS → application deployment is BLOCKED

      - name: Verify migration status
        uses: docker://flyway/flyway:10-alpine
        with:
          args: >
            -url=jdbc:postgresql://${{ secrets.DB_HOST }}:5432/cloudmart
            -user=${{ secrets.DB_USER }}
            -password=${{ secrets.DB_PASSWORD }}
            info
          # "info" → prints a table of all migrations and their status (Success/Pending)
          # Good for the pipeline logs — proof of exactly what ran

    # Application deployment now runs AFTER migration succeeds
  deploy-application:
    needs: database-migration
    runs-on: ubuntu-latest
    steps:
      - run: echo "Schema is ready — deploying new application version"
Zero-Downtime Schema Changes

🔄 Backward-Compatible Migrations — The Expand/Contract Pattern

During a rolling deployment, old and new application code run simultaneously for a few minutes. If a migration changes the schema in a way the old code cannot handle, the old pods will crash before they are replaced. The solution is the Expand/Contract pattern — make changes in small, backward-compatible steps across multiple deployments.

Goal❌ Unsafe (one step)✅ Safe (Expand/Contract — 3 deployments)
Rename a column
(email_address → email)		ALTER TABLE users RENAME COLUMN email_address TO email;
Old code crashes immediately — column no longer exists.		1. Expand: Add new column "email", copy data, keep both columns. App writes to both.
2. Deploy new code that reads "email".
3. Contract: Once old code is fully retired, drop "email_address".
Make column NOT NULLALTER TABLE orders ALTER COLUMN status SET NOT NULL;
Old code may insert NULL — fails immediately.		1. Add column as nullable with a default.
2. Deploy code that always sets a value.
3. Backfill existing NULLs.
4. Add NOT NULL constraint once all rows are populated.
Drop a columnALTER TABLE users DROP COLUMN old_field;
Old code (still running during rollout) crashes referencing it.		1. Deploy new code that stops using the column (but column still exists).
2. Wait for full rollout — confirm no pods reference it.
3. In a separate, later migration — drop the column.

📋 Database Migration Questions — Senior DevOps Differentiator

Q1

How do you handle database schema changes in a CI/CD pipeline?

I use a database migration tool like Flyway or Liquibase, which stores versioned SQL migration files in the same Git repository as the application code. Each migration file follows a strict naming pattern (V1__, V2__...) and the tool maintains a history table in the database tracking which migrations have run. In the pipeline, a dedicated database-migration job runs before the application deployment job — it connects to the database and applies any new, unapplied migrations inside a transaction. If a migration fails, the transaction rolls back and the pipeline stops — the old application version continues running against the unchanged schema. Only after migrations succeed does the new application code deploy.

Q2

What is the Expand/Contract pattern for database migrations?

The Expand/Contract pattern (also called Parallel Change) makes schema changes backward-compatible across multiple small deployments, instead of one breaking change. "Expand" adds new structures (new columns, new tables) without removing old ones — both old and new application code can run simultaneously during the rollout. After the new code is fully deployed and verified, a later "Contract" migration removes the old, now-unused structures. This is essential because during a rolling deployment, old and new pods run side-by-side for several minutes — a breaking schema change would crash the old pods before they are replaced.

💬 Give a concrete example like renaming a column in 3 steps — interviewers want to see you've actually dealt with this.

Q3

What happens if a database migration fails halfway through in production?

Tools like Flyway wrap each migration in a database transaction (for databases that support transactional DDL, like PostgreSQL). If the migration fails partway through, the transaction rolls back entirely — the database returns to its exact previous state, as if the migration never ran. Flyway also marks the migration as failed in its history table and refuses to proceed to later migrations or be re-run until the issue is fixed (using flyway repair if needed). The CI/CD pipeline detects the non-zero exit code from the migration step and fails the pipeline — the application deployment job (which depends on migration success) never runs. The previous application version keeps serving traffic against the unchanged schema.

Q4

Why should you avoid running "CREATE INDEX" without CONCURRENTLY on a production table?

In PostgreSQL, a plain CREATE INDEX takes a lock that blocks all writes (INSERT, UPDATE, DELETE) to the table for the entire duration of the index build — which can be minutes or hours on a large table. During this time, the application appears frozen for any operation touching that table. CREATE INDEX CONCURRENTLY builds the index without blocking writes — it takes longer and uses more resources, but the application continues to function normally. The tradeoff: CONCURRENTLY can fail and leave an invalid index behind, which then needs to be dropped and retried. For any table with live production traffic, CONCURRENTLY is mandatory.

Q5

How do you roll back a database migration if you need to revert a deployment?

Most migration tools, including Flyway's community edition, do not support automatic "undo" migrations by default — rolling forward is preferred over rolling back for databases. My strategy: write migrations that are additive and backward-compatible (Expand/Contract), so that rolling back the application code does not require rolling back the schema — the old code simply ignores the new columns/tables. For situations where a true rollback is required, I write a corresponding "down" migration script manually, test it in staging, and keep it ready — but I treat schema rollbacks as a last resort, since they risk data loss if the new schema has already received writes. The safer default is always: fix forward with a new migration, not backward.

🧩 "One Small Fix Triggered 6 Deployments"

🔀
CloudMart India · Microservices Migration · Week 36

The Monolith Split Into Services — But the Pipeline Didn't

CloudMart India had grown to 6 microservices: user-service, product-service, cart-service, payment-service, order-service, and notification-service — all living in one Git repository (a monorepo). A developer fixed a typo in the notification-service README. The pipeline triggered, rebuilt, retested, and redeployed all 6 services — because the workflow had no concept of "which service actually changed".

This wasted 25 minutes of pipeline time and, worse, redeployed 5 services that had nothing to do with the change — increasing risk of unrelated issues during a routine documentation fix. Separately, when payment-service genuinely needed an urgent hotfix, it had to wait in a queue behind the unnecessary full-repo pipeline run.

The fix was a path-based, service-aware pipeline — using path filters to detect exactly which service folders changed, and only building/testing/deploying those specific services. Each service also got its own Docker image, its own ECR repository, and its own Kubernetes Deployment — fully independent release cycles.

Monorepo vs Polyrepo

📁 Monorepo vs Polyrepo — The First Big Decision

📦 Monorepo

All microservices live in one Git repository, in separate folders (services/user-service, services/payment-service, etc). Pros: easy cross-service refactoring, shared CI configuration, one PR can touch multiple services atomically, simpler dependency management. Cons: pipeline must be path-aware to avoid rebuilding everything; large repo size over time; requires careful access control if teams shouldn't see each other's code.

📚 Polyrepo

Each microservice has its own Git repository with its own pipeline. Pros: clean separation, independent versioning, simple per-team access control, smaller repos. Cons: cross-service changes require coordinating multiple PRs across multiple repos; shared CI logic must be in reusable workflows/shared libraries to avoid duplication.

CloudMart India chose a monorepo because the 6 services were closely related and the team was small (8 engineers) — coordination overhead of polyrepo outweighed its benefits at this scale. Large companies like Google use monorepos at massive scale with custom build tools (Bazel).

Path-Based Pipeline

⚙️ Service-Aware Monorepo Pipeline

.github/workflows/microservices-ci.yml — Build Only Changed ServicesYAML
name: CloudMart Microservices Pipeline
on:
  push:
    branches: [main]

jobs:
    # ─── Detect which service folders changed ──────────────────────────
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      services: ${{ steps.filter.outputs.changes }}
            # "changes" → a JSON array string like ["user-service","payment-service"]
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          list-files: json
          filters: |
            user-service:     'services/user-service/**'
            product-service:  'services/product-service/**'
            cart-service:     'services/cart-service/**'
            payment-service:  'services/payment-service/**'
            order-service:    'services/order-service/**'
            notification-service: 'services/notification-service/**'
                    # Each key checks ONE service folder for changes
          # "changes" output collects all keys where files changed = "true"

    # ─── Build, test, deploy ONLY changed services — using a matrix ────
  build-changed-services:
    needs: detect-changes
    if: needs.detect-changes.outputs.services != '[]'
        # Skip this job entirely if NOTHING in services/ changed
    # (e.g. only README.md or docs/ changed)
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: ${{ fromJSON(needs.detect-changes.outputs.services) }}
                # "fromJSON()" → converts the JSON array string into a real matrix
        # If 2 services changed → 2 parallel matrix jobs run
        # If 6 services changed → 6 parallel matrix jobs run (one per service)
        # If 1 service changed → ONLY 1 job runs — others are completely skipped
      fail-fast: false
            # If user-service fails, payment-service's job still completes independently

    steps:
      - uses: actions/checkout@v4

      - name: Build and test ${{ matrix.service }}
        working-directory: services/${{ matrix.service }}
                # "${{ matrix.service }}" → dynamically becomes "user-service",
        # "payment-service" etc — depending on which matrix job is running
        run: |
          npm ci
          npm test

      - name: Build and push Docker image for ${{ matrix.service }}
        uses: docker/build-push-action@v5
        with:
          context: services/${{ matrix.service }}
          push: true
          tags: ${{ secrets.ECR_REGISTRY }}/${{ matrix.service }}:${{ github.sha }}
                    # Each service gets its OWN ECR repository: user-service, payment-service etc
          # All tagged with the SAME commit SHA — useful for tracing a release across services

      - name: Deploy ${{ matrix.service }} to Kubernetes
        run: |
          kubectl set image deployment/${{ matrix.service }} \
            ${{ matrix.service }}=${{ secrets.ECR_REGISTRY }}/${{ matrix.service }}:${{ github.sha }} \
            -n cloudmart-prod
          kubectl rollout status deployment/${{ matrix.service }} -n cloudmart-prod
                    # "kubectl set image" → updates only this ONE service's deployment
          # Other 5 services' deployments are completely untouched

♻️ Reusable Workflows — Avoid Duplicating Pipeline Code 6 Times

.github/workflows/_reusable-build-deploy.yml — Shared TemplateYAML
name: Reusable Build and Deploy
on:
  workflow_call:
        # "workflow_call" → makes this workflow CALLABLE by other workflows
    # This is the GitHub Actions equivalent of a Jenkins Shared Library function
    inputs:
      service-name:
        required: true
        type: string
      service-path:
        required: true
        type: string
    secrets:
      ECR_REGISTRY:
        required: true

jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cd ${{ inputs.service-path }} && npm ci && npm test
      - run: docker build -t ${{ secrets.ECR_REGISTRY }}/${{ inputs.service-name }}:${{ github.sha }} ${{ inputs.service-path }}
      - run: docker push ${{ secrets.ECR_REGISTRY }}/${{ inputs.service-name }}:${{ github.sha }}

## ─── Calling workflow (per service) — caller-payment-service.yml ────────
jobs:
  payment-service:
    uses: ./.github/workflows/_reusable-build-deploy.yml
        # References the reusable workflow file in this same repo
    with:
      service-name: payment-service
      service-path: services/payment-service
    secrets:
      ECR_REGISTRY: ${{ secrets.ECR_REGISTRY }}
        # Update the shared logic ONCE in _reusable-build-deploy.yml
    # → all 6 services automatically use the updated pipeline logic

🎯 Chapter 20 Interview Questions

📋 Microservices Pipeline Architecture Questions

Q1

How do you design a CI/CD pipeline for a monorepo with multiple microservices?

The key principle is only build, test, and deploy what changed. I use path filters (like dorny/paths-filter) to detect which service folders were modified in a push. The output feeds into a matrix strategy — only the changed services get a build job; unchanged services are skipped entirely. Each service has its own Dockerfile, its own ECR repository, and its own Kubernetes Deployment, so deploying one service does not touch the others. To avoid duplicating pipeline logic across services, I extract common build/test/deploy logic into a reusable workflow that each service's job calls with its own parameters — service name and path.

Q2

What are the tradeoffs between a monorepo and polyrepo for microservices?

A monorepo — all services in one repository — makes cross-service changes easier (one PR can update multiple services atomically), simplifies shared tooling and CI configuration, and gives full visibility into the entire system in one place. The downside is the pipeline must be carefully designed to be path-aware, otherwise every commit triggers builds for unrelated services, wasting time and increasing risk. A polyrepo — each service in its own repository — gives clean isolation, independent versioning and release cadences, and simpler per-team access control. The downside is coordinating changes that span multiple services requires multiple PRs across multiple repos, and shared pipeline logic must live in external shared libraries or templates. The choice depends on team size, service coupling, and organisational structure — there is no universally correct answer.

Q3

How do you handle a change that affects multiple microservices at once, like a shared library update?

If a shared library (e.g., a common authentication module used by all 6 services) changes, the path filter for that shared folder should be configured to trigger all dependent services — not just the one folder that changed. I maintain a small dependency map in the pipeline configuration: if services/shared-lib/** changes, the matrix includes all 6 services rather than zero. This is a deliberate exception to the "only build what changed" rule — because logically, all 6 services DID change (their dependency updated), even though their own folders are untouched. Some teams instead version the shared library as a separate npm package, so each service explicitly bumps its dependency version in its own commit — making the impact explicit and traceable.

Q4

What is a reusable workflow in GitHub Actions and why is it useful for microservices?

A reusable workflow is defined with on: workflow_call and accepts inputs and secrets as parameters — similar to a function. Other workflows invoke it with uses: ./.github/workflows/template.yml and pass specific values. For a microservices monorepo with 6 nearly-identical pipelines (build, test, push, deploy), instead of maintaining 6 copies of the same 80-line YAML, I write the logic once in a reusable workflow and have each service's workflow call it with its service name and path. If the deployment process needs to change — say, adding a new security scan step — I update the reusable workflow once, and all 6 services automatically inherit the change on their next run. This is the equivalent of Jenkins Shared Libraries.

Q5

How do you ensure two microservices that are released together stay compatible (contract testing)?

I use contract testing with a tool like Pact. The consumer service (e.g., order-service, which calls payment-service) defines a "contract" — the exact requests it will send and the responses it expects. This contract is published to a Pact Broker. The provider service's (payment-service's) pipeline runs a provider verification test against this contract — confirming that payment-service's actual API still satisfies what order-service expects, before payment-service is deployed. If payment-service changes its API in a way that breaks the contract, its pipeline fails immediately — before deployment — rather than discovering the incompatibility through a production incident or a slow, flaky end-to-end test across all 6 services.

📋 "Show Us the Approval Record for This Deployment"

🏦
CloudMart India · Compliance Audit · Week 38

A New Banking Partner Requires SOC2-Style Controls

CloudMart India partnered with a bank for a new "Buy Now Pay Later" feature. The bank's security team required a compliance audit before integration. One of their questions: "For your last 10 production deployments, show us who approved each one, what changed, and whether it went through code review."

CloudMart's pipeline had a single "production" GitHub Environment, but anyone on the team could approve their own deployment — including the person who wrote the code. There was no requirement for a second person to review. There was also no record connecting "this deployment" to "this approved Pull Request" in an easily auditable way.

The fixes: required reviewers on the production environment (minimum 2, and the author cannot approve their own deployment); branch protection rules requiring at least 1 code review approval before merge; and a deployment audit log — every production deployment automatically records who approved it, what commit was deployed, what PR it came from, and when — stored for 1 year.

Approval Gates

🚦 GitHub Environment Protection Rules

Required Reviewers

Configure 1–6 specific people or teams who must approve before a job using environment: production can run. The pipeline pauses at this job, sends a notification, and waits. Self-approval can be disabled — meaning the person who triggered the workflow cannot also be the approver, enforcing separation of duties.

Wait Timer

Add a mandatory delay (e.g., 10 minutes) before a job can proceed — even with approval. Useful for "soak time" — giving the team a window to cancel a deployment if something looks wrong, or to ensure off-hours deployments don't happen instantly.

Deployment Branches

Restrict which branches can deploy to this environment — e.g., only main or tags matching v*.*.* can deploy to production. Prevents accidental deployment of a feature branch directly to production.

Environment Secrets

Secrets scoped to this environment only — production secrets are invisible to workflows running in dev/staging contexts, even within the same repository. Reduces blast radius if a non-production workflow is compromised.

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
        # No approval required — automatic deployment

      - run: echo "Deploying to staging automatically"

    # Required reviewers: QA Lead, QA Engineer (either one can approve)

  deploy-production:

    # Required reviewers: Engineering Manager AND Security Lead (BOTH must approve)

📋 Compliance & Governance — Asked in Regulated Industry Interviews

Banking, fintech, healthcare, and government projects in India ask these.

Q1

How do you implement separation of duties in a CI/CD pipeline?

Separation of duties means the person who writes and deploys a change cannot be the same person who approves it. I implement this using GitHub Environment protection rules — configuring "production" as a protected environment with required reviewers, and explicitly disabling "allow administrators to bypass" and self-review. Branch protection rules also require at least one approving code review before a PR can be merged, and the PR author cannot approve their own PR. This ensures every production change has at least two distinct people involved — the author and the approver — satisfying audit requirements for SOC2 and similar frameworks.

Q2

What information should an audit log capture for a production deployment?

A complete deployment audit record should capture: the commit SHA deployed (exact version), the Pull Request number it came from (for context on what changed), who authored the change, who approved the deployment (the reviewer, distinct from the author), when it was deployed (timestamp), which environment it went to, and the pipeline run URL for full logs. I add a step in the production deployment job that posts this information to an audit API or a dedicated audit log table, retained for the period required by the compliance framework — typically 1 year for SOC2, longer for some financial regulations.

Q3

How do branch protection rules contribute to CI/CD security?

Branch protection rules on the main branch enforce several controls before code can be merged: requiring the CI pipeline to pass (status checks), requiring at least one code review approval, requiring branches to be up to date with main before merging (prevents merging stale code that hasn't been tested against latest changes), and preventing force-pushes or deletion of the main branch (preserving history for audits). Combined, these rules ensure that no code reaches production without passing automated tests AND human review — both technical correctness and business logic correctness are verified before any deployment pipeline even begins.

Q4

What is the difference between a "wait timer" and "required reviewers" in environment protection rules, and when would you use both?

Required reviewers means a human must explicitly click "Approve" before the job proceeds — an active, deliberate decision. A wait timer is a passive delay — the job automatically proceeds after N minutes, with no action required, unless someone cancels it. I use required reviewers for production deployments where business sign-off matters — e.g., a release manager confirming the timing is appropriate. I use wait timers for situations like "deploy 15 minutes after merge to allow time to cancel if a critical issue is spotted in code review comments after merge" — a safety buffer without requiring someone to be actively present. Some pipelines use both: a wait timer for a cooling-off period, followed by required reviewer approval for the final go-ahead.

RTO and RPO

⏱️ RTO and RPO — The Two Numbers That Define Your DR Strategy

RTO — Recovery Time Objective

"How long can we be down?" The maximum acceptable time between an outage starting and service being restored. CloudMart's target RTO: 1 hour. This drives architecture decisions — an RTO of 1 hour requires automation (Terraform + pipeline-driven recovery); an RTO of seconds requires active-active multi-region with automatic failover (much more expensive).

RPO — Recovery Point Objective

"How much data can we lose?" The maximum acceptable time of data loss, measured backward from the outage. CloudMart's target RPO: 5 minutes. This drives backup frequency — an RPO of 5 minutes requires continuous replication (RDS read replica in another region) or very frequent snapshots; an RPO of 24 hours allows daily backups.

💡 The Cost-vs-Risk Tradeoff

Lower RTO/RPO = higher infrastructure cost (multi-region active-active, continuous replication) but lower business risk during an outage. Higher RTO/RPO = lower cost but accepts more downtime/data loss risk. CloudMart chose RTO=1hr / RPO=5min — a "warm standby" approach — balancing cost against the business impact of an e-commerce outage during peak hours.

.github/workflows/dr-backup.yml — Scheduled Cross-Region BackupYAML
name: Disaster Recovery — Automated Backup
on:
  schedule:
    - cron: '*/15 * * * *'
        # Every 15 minutes — supports our RPO of 5 minutes
    # (RDS continuous backup handles the finer granularity; this snapshot
    # is an ADDITIONAL safety net for cross-region copy)
  workflow_dispatch:
        # Allow manual trigger for on-demand backups before risky operations

jobs:
  backup-database:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: ${{ secrets.DR_ROLE_ARN }}, aws-region: ap-south-1 }

      - name: Create RDS snapshot
        run: |
          SNAPSHOT_ID="cloudmart-prod-$(date +%Y%m%d-%H%M%S)"
          aws rds create-db-snapshot \
            --db-instance-identifier cloudmart-prod-db \
            --db-snapshot-identifier $SNAPSHOT_ID
          echo "SNAPSHOT_ID=$SNAPSHOT_ID" >> $GITHUB_ENV

      - name: Wait for snapshot to complete
        run: |
          aws rds wait db-snapshot-completed \
            --db-snapshot-identifier ${{ env.SNAPSHOT_ID }}

      - name: Copy snapshot to DR region (ap-southeast-1)
        run: |
          aws rds copy-db-snapshot \
            --source-db-snapshot-identifier arn:aws:rds:ap-south-1:123456789:snapshot:${{ env.SNAPSHOT_ID }} \
            --target-db-snapshot-identifier ${{ env.SNAPSHOT_ID }}-dr \
            --source-region ap-south-1 \
            --region ap-southeast-1
                    # Snapshot now exists in BOTH ap-south-1 (Mumbai) and ap-southeast-1 (Singapore)
          # If Mumbai region is fully unavailable, Singapore copy can be restored independently

      - name: Delete snapshots older than 7 days
        run: |
          aws rds describe-db-snapshots \
            --query "DBSnapshots[?SnapshotCreateTime<='$(date -u -d '7 days ago' +%Y-%m-%d)'].DBSnapshotIdentifier" \
            --output text | xargs -n1 -I{} aws rds delete-db-snapshot --db-snapshot-identifier {}
                    # Cleanup — without this, snapshot storage costs grow unbounded

    # ─── Monthly DR drill — actually test the restore ────────────────────
  dr-restore-drill:
    runs-on: ubuntu-latest
    if: github.event.schedule == '0 0 1 * *'
        # Runs once a month — separate cron entry for "1st of month, midnight"
    steps:
      - name: Restore latest DR snapshot into a TEST instance
        run: |
          aws rds restore-db-instance-from-db-snapshot \
            --db-instance-identifier cloudmart-dr-drill-test \
            --db-snapshot-identifier ${{ env.LATEST_DR_SNAPSHOT }} \
            --region ap-southeast-1

      - name: Run validation queries against restored instance
        run: |
          psql -h cloudmart-dr-drill-test.xxx.ap-southeast-1.rds.amazonaws.com \
            -c "SELECT count(*) FROM users; SELECT count(*) FROM orders; SELECT version_num FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 1;"
                    # Confirms: data exists, row counts look reasonable, schema version matches expected
          # If this query FAILS or returns unexpected results → alert the team
          # THIS is what CloudMart skipped before the Mumbai outage — and paid for it

      - name: Tear down test instance
        if: always()
        run: |
          aws rds delete-db-instance \
            --db-instance-identifier cloudmart-dr-drill-test \
            --skip-final-snapshot --region ap-southeast-1
                    # "if: always()" → ensure cleanup happens even if validation step failed
          # Otherwise the test instance keeps running and costing money

🎯 Chapter 22 Interview Questions

📋 Disaster Recovery — Asked at Senior/Lead DevOps Level

Q1

What are RTO and RPO and how do they shape your DR strategy?

RTO (Recovery Time Objective) is the maximum acceptable downtime — how long the business can tolerate the system being unavailable after a disaster. RPO (Recovery Point Objective) is the maximum acceptable data loss, measured in time — how much recent data can be lost. These two numbers drive every architecture decision. A low RTO (minutes) requires automated, pipeline-driven recovery or multi-region active-active setups — expensive. A low RPO (minutes) requires continuous data replication or very frequent backups. I always start a DR conversation by asking the business to define acceptable RTO/RPO in business terms — "how much revenue do we lose per hour of downtime" — and design the technical solution to meet those numbers at a justified cost.

Q2

Why is it important to actually test (restore) your backups, not just create them?

A backup that has never been restored is an assumption, not a guarantee. Common failure modes: the backup process silently failed for weeks without anyone noticing (no monitoring on backup jobs), the backup is missing data due to a configuration error, or the restore process itself doesn't work because of permission issues, version incompatibilities, or missing steps that were never documented (like running migrations in the correct order). I implement regular restore drills — automatically restoring the latest backup to a temporary instance and running validation queries (row counts, schema version checks) to confirm the backup is actually usable. This should be scheduled and automated, run at least monthly, because manual drills get skipped when teams are busy — exactly when you most need them to have been done.

Q3

How does Infrastructure as Code (Terraform) help with disaster recovery?

If your entire infrastructure — VPC, subnets, security groups, EKS cluster, RDS instance, load balancers — is defined in Terraform, you can recreate the entire stack in a different AWS region by running terraform apply with a different region variable. Without IaC, recreating infrastructure manually from memory or outdated documentation during an active outage is slow and error-prone — exactly when mistakes are most costly. With IaC, the DR runbook becomes: "run terraform apply targeting ap-southeast-1, then restore the latest cross-region database snapshot, then run the deployment pipeline to deploy the application." This is testable in advance, version-controlled, and dramatically reduces RTO.

Q4

What is the difference between "warm standby" and "active-active" DR architectures?

In a warm standby, a secondary region has infrastructure running at reduced capacity (or scaled to zero, using Terraform to scale up on demand) with continuously replicated data. During normal operations, it serves no traffic. During a disaster, you scale it up and redirect traffic — this takes minutes (your RTO). It costs less than full duplication but requires a manual or automated failover step. In active-active, both regions run at full capacity simultaneously, both serving live traffic, with data replicated bi-directionally in near real-time. If one region fails, traffic automatically shifts to the other with near-zero downtime (RTO close to zero) — but it costs roughly 2x infrastructure and requires solving complex data consistency challenges across regions. CloudMart India chose warm standby because their RTO target of 1 hour did not justify the cost and complexity of active-active.

Cost Levers

💰 Where CI/CD Pipelines Spend Money

🖥️ Compute (Runners/Agents)

GitHub-hosted runners are billed per minute beyond the free tier. Self-hosted Jenkins agents on EC2 cost the same whether running 1 job or zero — 24/7 idle agents are pure waste. Fix: use ephemeral, auto-scaling agents (scale to zero when idle).

📦 Storage (Registries/Artifacts)

Every Docker image push to ECR costs storage. Without lifecycle policies (Chapter 9), old images accumulate forever. Build artifacts uploaded on every run, kept for 90 days by default, add up across hundreds of daily runs.

🌐 Data Transfer

Pulling Docker images cross-region (e.g., pipeline in one region, EKS cluster in another) incurs data transfer costs. Pulling large base images repeatedly without registry caching adds up at scale — thousands of pulls per day across nodes.

Auto-Scaling Runners

⚙️ Self-Hosted Runners That Scale to Zero

Karpenter / EKS Spot Configuration for Jenkins AgentsYAML
# Karpenter NodePool — runs Jenkins agent pods on SPOT instances
# Spot instances cost 60-90% less than On-Demand, ideal for CI workloads
# (CI jobs are short-lived and retryable — perfect spot candidates)
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: ci-runners-spot
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: [spot]
                    # Only provision SPOT instances for this node pool
          # If a CI job pod gets interrupted (spot reclaim) → pipeline retries automatically
      taints:
        - key: ci-only
          value: "true"
          effect: NoSchedule
                    # Only CI agent pods (with matching toleration) can run on these nodes
          # Keeps CI workload isolated from application pods
  disruption:
    consolidationPolicy: WhenEmpty
    consolidateAfter:    60s
        # If a node has been EMPTY (no pods) for 60 seconds → terminate it
    # This is the "scale to zero" — when no CI jobs are running, NO nodes exist
    # Compare: a fixed Jenkins agent EC2 instance costs the same 24/7
    # whether running 50 builds/day or 0 builds/day
  limits:
    cpu: "100"
        # Hard cap — even with auto-scaling, never exceed 100 vCPUs total
    # Prevents a runaway pipeline loop from creating unlimited (expensive) nodes

  schedule:
    - cron: '0 20 * * 1-5'

    runs-on: ubuntu-latest

      - name: Scale down or up based on schedule trigger
        run: |
          HOUR=$(date -u +%H)
          if [ "$HOUR" == "14" ]; then
                        # 8 PM IST — scale down to 0 replicas overnight + weekends
            # Saves ~60% of staging compute cost (16 hrs/day + weekends not running)
            kubectl scale deployment --all --replicas=0 -n cloudmart-staging
            echo "Staging scaled down for the night"
          else
                        # 8 AM IST — scale back up for the working day
            kubectl scale deployment cloudmart-app --replicas=2 -n cloudmart-staging
            echo "Staging scaled up for the day"
          fi

📋 FinOps / Cost Optimisation — Increasingly Common in 2024+

Q1

How would you reduce the cost of CI/CD infrastructure without reducing capability?

I focus on eliminating idle capacity rather than cutting features. For self-hosted CI runners, I use auto-scaling node pools that scale to zero when no jobs are running — instead of fixed 24/7 EC2 instances at low utilisation. I run CI workloads on Spot instances — 60-90% cheaper than On-Demand, which is acceptable for CI because jobs are short and retryable. For non-production environments like staging, I implement scheduled scale-down outside business hours and weekends — staging doesn't need to run 24/7 if nobody tests at 2 AM on Sunday. For storage, I apply ECR lifecycle policies to delete old images and reduce artifact retention periods where compliance allows. Each of these reduces cost without removing any pipeline capability — they just eliminate paying for capacity nobody is using.

Q2

What are Spot Instances and when are they appropriate vs not appropriate?

Spot Instances are spare AWS compute capacity offered at a 60-90% discount compared to On-Demand pricing, with the tradeoff that AWS can reclaim them with a 2-minute warning if it needs the capacity back. They are appropriate for stateless, fault-tolerant, retryable workloads — CI/CD build agents are a perfect fit, because if a build pod is interrupted, the pipeline simply retries on a new node, with no data loss and minimal time impact. They are not appropriate for stateful workloads like databases, or for production application pods serving live user traffic where an unexpected interruption would cause a user-facing error — unless the architecture explicitly handles graceful interruption with sufficient redundancy.

Q3

How do you investigate an unexpected increase in cloud costs?

I start with AWS Cost Explorer, filtering by service and grouping by tags to identify which service (EC2, RDS, data transfer, etc.) and which environment (production, staging, DR) drove the increase, and over what time period. I correlate the cost increase timeline with infrastructure change history — recent Terraform applies, HPA configuration changes, or new environments stood up — using Git history of the infrastructure repository. Common culprits I check first: HPA misconfigurations causing pods to never scale down, forgotten test/POC resources that were never torn down, data transfer between regions or AZs that wasn't accounted for, and non-production environments inadvertently sized like production. I always implement cost alerts/budgets in AWS Budgets after such an incident, so the next anomaly is caught within days, not months.

Q4

What is the relationship between Horizontal Pod Autoscaler misconfiguration and cloud cost?

If the HPA's target metric never drops below threshold — due to a bug in metric collection, an incorrect resource request causing artificially high utilisation percentages, or a target threshold set too low — the HPA will scale up but never scale back down. Pods remain at maxReplicas indefinitely, and the underlying node group (especially with cluster autoscaler/Karpenter) keeps nodes provisioned to host them. This directly translates to paying for compute capacity that isn't needed. I check HPA behaviour using kubectl get hpa to see current vs target metric values over time, and Grafana dashboards showing pod count history — a flat line at maxReplicas for days is a strong signal of HPA misconfiguration costing money.

Q1 — Opening

Walk me through how you would design a complete CI/CD pipeline for a new e-commerce application, from code commit to production.

I'd design this in layers, starting from the developer's commit and ending in production. First, the trigger — a developer pushes code to a feature branch, which triggers a CI pipeline in GitHub Actions running on every push and pull request. Second, the CI stage — checkout code, install dependencies with caching enabled, run unit tests with a coverage threshold of 80%, run a SonarQube scan for code quality and security issues, then build a Docker image and scan it with Trivy for critical vulnerabilities before pushing to ECR with a commit-SHA tag. Third, the CD stage — for the develop branch, automatically deploy to a staging environment in its own Kubernetes namespace, run integration and smoke tests there. Fourth, production deployment — only from the main branch, behind a manual approval gate with required reviewers, deploying via a rolling update in Kubernetes with readiness probes ensuring zero downtime. Finally, post-deployment — automated health checks against Prometheus metrics for error rate and latency, with automatic rollback if thresholds are breached, and Slack notifications for both success and failure.

💬 This answer touches Chapters 3, 5, 7, 8, 10, 13, 16, 18 — show breadth first, then offer to go deeper anywhere the interviewer wants.

Q2 — Going deeper

You mentioned zero-downtime deployment. Walk me through exactly how that works at the Kubernetes level.

Zero downtime in Kubernetes relies on three things working together. First, the Deployment's RollingUpdate strategy with maxUnavailable: 0 and maxSurge: 1 — this means Kubernetes can temporarily run one extra pod above the desired count, but it will never drop below the desired count of available pods. Second, the readinessProbe — when a new pod starts, Kubernetes calls its /ready endpoint repeatedly, and only adds the pod to the Service's load-balancing endpoints once it returns 200. The old pod is only terminated after the new pod is confirmed ready. Third, graceful shutdown — when Kubernetes terminates the old pod, it sends a SIGTERM and waits for a configurable grace period before force-killing it, allowing in-flight requests to complete. Combined, this means at every moment during the rollout, there is always at least the desired number of pods ready to serve traffic — users never experience a gap.

💬 This is the kind of follow-up that separates candidates who memorised buzzwords from those who actually configured this. Be ready to draw the timeline if asked.

Q3 — Failure scenario

The deployment to production succeeds, but 10 minutes later, error rates spike. What happens in your pipeline?

This is exactly why I include a post-deployment validation job after the deploy job — not just relying on "the pipeline said success". After deployment completes and rollout status confirms all pods are ready, the pipeline waits 5 minutes for traffic to stabilise, then queries Prometheus using PromQL to check the error rate — specifically, the ratio of 5xx responses to total requests over the last 5 minutes. If that exceeds 1%, or if p99 latency exceeds 2 seconds, the validation step exits with a failure code. This triggers a post: failure block that runs kubectl rollout undo, reverting to the previous ReplicaSet — which Kubernetes keeps available specifically for this purpose. The rollback itself follows the same zero-downtime rolling update process. Finally, a Slack alert goes to the #pipeline-alerts channel with @here, including a link to the failed run and the rollback confirmation. The whole detect-and-rollback cycle typically completes within 6-8 minutes of the original deployment — well within our 1-hour MTTR target.

💬 Mentioning MTTR here connects this answer to DORA metrics — shows you think about the bigger picture, not just the mechanism.

Q4 — Scaling the team

Your company is now splitting this monolith into 5 microservices, each owned by a different team. How does your pipeline architecture change?

The core CI/CD principles stay the same, but the structure changes to support team autonomy. I'd move to a monorepo with path-based pipelines if the teams are closely coordinated, or polyrepo with reusable workflow templates if teams need more independence — the choice depends on how often changes span multiple services. Either way, each service gets its own Docker image, its own ECR repository with its own lifecycle policy, its own Kubernetes Deployment and namespace-scoped resources, and its own independent release cadence — team A can deploy 10 times a day while team B deploys weekly, without coordination overhead. To avoid duplicating the 80% of pipeline logic that's identical across services — build, test, scan, deploy — I'd extract that into a reusable workflow that each service's pipeline calls with its own parameters. For cross-service compatibility, I'd introduce contract testing with Pact so that a breaking API change in one service's pipeline is caught before deployment, not discovered in a shared staging environment days later. And I'd adopt GitOps with ArgoCD so each team's deployments are visible in one place, with selfHeal preventing any team's manual kubectl changes from causing drift.

💬 This connects Chapters 14 and 20 — showing you can reason about organisational scaling, not just technical scaling.

Q5 — Security focus

A security team review flags that your pipeline doesn't have any security scanning. How do you prioritise adding it?

I'd implement security in layers, prioritised by where in the pipeline they catch issues earliest and cheapest to fix — the "shift-left" principle. First priority: secrets scanning — gitleaks or GitHub's built-in secret scanning on every push, because a leaked credential is the highest-severity, easiest-to-prevent issue. Second: dependency scanning with Snyk or Trivy on package.json/requirements.txt, catching known CVEs in third-party libraries before they're even built into an image — this runs in seconds. Third: SAST with SonarQube on the application source code, catching insecure patterns like SQL injection in the developer's own code, with a quality gate that blocks merges on new critical issues. Fourth: container image scanning with Trivy after the Docker build, with exit-code blocking on CRITICAL/HIGH severity, before the image is pushed to ECR — this also catches OS-level CVEs in the base image. Fifth, after staging deployment: DAST with OWASP ZAP, testing the running application for runtime vulnerabilities like XSS that static analysis can't catch. I'd roll these out incrementally — starting with secrets and dependency scanning in week 1, since they're low-effort and high-impact, then SAST and container scanning in week 2-3 with a grace period before enforcing blocking, and DAST last since it requires a stable staging environment.
