Linux User & Group Administration
in a Banking Environment

A senior DevOps engineer's complete guide to managing users, groups, passwords, sudo privileges, SSH access, and PAM authentication in a real BFSI production environment — from design to Day 2 operations.

🏦 BFSI Domain 🐧 RHEL 8 / Ubuntu 22 ⏱ 5+ Years Level 🔐 Security Hardened 🏢 Enterprise Grade

1Project Introduction

You just joined SecureBank Ltd. — a leading private sector bank with 12,000 employees, 2,400 branches across India, and over ₹8 lakh crore in assets. The IT infrastructure has 600+ Linux servers running core banking, payments, internet banking, mobile banking, and data analytics.

It's Day 1. Your manager, Rajesh Sharma (Head of Linux Infrastructure), calls you into his cabin and says:

"We have a serious problem. The RBI auditors are coming in 3 weeks. During the last audit, they flagged that our Linux servers have shared accounts, no password policies, and some ex-employees still have active accounts. If we don't fix this, we could face a ₹50 crore penalty and a banking license risk. I need you to lead the User Access Management (UAM) remediation. You have 2 weeks."

This is your first real assignment. Let's do it right.

What You Will Learn in This Project

  • How to create and manage Linux users and groups at enterprise scale
  • How to enforce password policies compliant with RBI/ISO 27001 standards
  • How to configure sudo with least-privilege access
  • How to manage SSH key-based authentication and disable password SSH
  • How to audit and remove stale/shared accounts
  • How to automate user provisioning with Bash scripts used in real MNCs
  • How to configure PAM (Pluggable Authentication Modules) for advanced controls
  • How to generate compliance reports for auditors
ℹ️ Why This Project Matters
User and group management is the foundation of every Linux administration role. Every other skill — NFS, Cron, Services, Backup — depends on your users and groups being correctly configured. RBI Circular RBI/2021-22/112 and ISO 27001 Annex A.9 explicitly mandate user access reviews, strong authentication, and privilege separation.

Phase 2 — Emergency Deprovisioning (Incident INC0091874)

Always handle security incidents first. Ex-employee raman.k still has access. Here's what a senior admin does immediately:

  1. Lock the account immediately — prevent further login without deleting evidence
    BASH
    # Lock the account immediately (blocks password auth)
usermod -L raman.k

# Also expire the account to block SSH key login too
usermod -e 1 raman.k

# Verify it's locked
passwd -S raman.k
  2. Collect forensic evidence before making further changes
    BASH
    # What was the user doing? Check last logins
last raman.k

# Check currently running processes owned by this user
ps -u raman.k

# What files did this user access/modify recently?
find / -user raman.k -newer /etc/passwd -ls 2>/dev/null

# Check auth logs for login history
grep "raman.k" /var/log/secure | tail -50

# Check if they left any cron jobs
crontab -u raman.k -l 2>/dev/null
  3. Revoke SSH keys
    BASH
    # Back up then remove SSH authorized_keys
cp /home/raman.k/.ssh/authorized_keys /root/forensics/raman.k_keys_backup_$(date +%Y%m%d)
echo "" > /home/raman.k/.ssh/authorized_keys
chmod 000 /home/raman.k/.ssh/authorized_keys
  4. Archive home directory (for legal/audit hold)
    BASH
    # Archive with timestamp — DO NOT delete until legal clears it tar -czf /data/archive/raman.k_home_$(date +%Y%m%d_%H%M%S).tar.gz /home/raman.k # Set restricted permissions on archive chmod 400 /data/archive/raman.k_home_*.tar.gz
  5. Send incident report to Security team with all evidence gathered

Now we handle ticket RITM0045231. Let's provision Priya Nair, Karthik Menon, and Ananya Singh.

# -d = specify home directory path
# -g = primary group
# -G = supplementary groups (dbagrp + linuxusers for baseline)

useradd -m -d /home/priya.nair -g dbagrp -G linuxusers -s /bin/bash \

Phase 4 — Configuring Password Policy with PAM

ℹ️ What is PAM?
PAM (Pluggable Authentication Modules) is the framework Linux uses for all authentication tasks. It's modular — you can plug in different modules to enforce password complexity, account lockout, login hours, and more. Think of it as a security gate with multiple checkpoints.

Configure Password Complexity

CONFIG: /etc/security/pwquality.conf
# ── SecureBank Password Quality Configuration ────────────────────── # RBI Compliance: Minimum 12 characters, mixed case, special char minlen = 14 # Minimum password length (14 for banking) dcredit = -1 # At least 1 digit (-1 means "require 1") ucredit = -1 # At least 1 uppercase letter lcredit = -1 # At least 1 lowercase letter ocredit = -1 # At least 1 special character (other) maxrepeat = 3 # No more than 3 consecutive same characters gecoscheck = 1 # Cannot use username/GECOS fields in password dictcheck = 1 # Check against dictionary words difok = 5 # New password must differ by at least 5 chars

Configure Password Aging

BASH
# Set password aging GLOBALLY for new users (in /etc/login.defs) # Edit these values: grep -E "^PASS_MAX_DAYS|^PASS_MIN_DAYS|^PASS_WARN_AGE" /etc/login.defs # Set existing users' password aging with chage # -M = max days before password expires # -m = min days before password can be changed # -W = warning days before expiry # -I = inactive days after expiry before account lock chage -M 90 -m 1 -W 14 -I 7 priya.nair chage -M 90 -m 1 -W 14 -I 7 karthik.menon chage -M 90 -m 1 -W 14 -I 7 ananya.singh # Verify aging settings chage -l priya.nair

Configure Account Lockout (PAM faillock)

CONFIG: /etc/security/faillock.conf
# ── SecureBank Account Lockout Configuration ─────────────────────── # PCI-DSS Requirement 8.1.6: Lock after 6 failed attempts deny = 5 # Lock after 5 failed attempts unlock_time = 900 # Auto-unlock after 900 seconds (15 minutes) fail_interval = 900 # Count failures within 15-minute window even_deny_root # Also lock root (belt + suspenders) audit # Log to audit log

Phase 5 — Configuring Sudo with Least Privilege

Never give a team ALL sudo unless absolutely necessary. Let's configure each team's sudo access correctly using the /etc/sudoers.d/ directory (never edit /etc/sudoers directly — always use visudo).

🚨 CRITICAL — Always Use visudo
NEVER edit /etc/sudoers with a regular text editor. A syntax error in sudoers will lock ALL users out of sudo, potentially bricking the server. Always use visudo which validates syntax before saving. Use /etc/sudoers.d/ drop-in files for team-specific rules.
CONFIG: /etc/sudoers.d/dbagrp
# ── DBA Team Sudo Configuration ──────────────────────────────────── # Only allows DBA-relevant commands. No shell access via sudo. # Define command aliases (group related commands) Cmnd_Alias DBA_CMDS = /bin/systemctl start oracle, \ /bin/systemctl stop oracle, \ /bin/systemctl restart oracle, \ /bin/systemctl status oracle, \ /usr/bin/sqlplus, \ /opt/oracle/bin/*, \ /bin/su - oracle # Grant dbagrp members the ability to run DBA_CMDS as root # NOPASSWD means they don't need to re-enter password for these commands %dbagrp ALL=(root) NOPASSWD: DBA_CMDS # Deny shell escape (prevents getting a root shell via sudo) %dbagrp ALL=(root) !NOPASSWD: /bin/bash, /bin/sh, /bin/dash
CONFIG: /etc/sudoers.d/appteam
# ── Application Support Team Sudo Configuration ──────────────────── # Can only manage specific application services Cmnd_Alias APP_CMDS = /bin/systemctl start corebanking, \ /bin/systemctl stop corebanking, \ /bin/systemctl restart corebanking, \ /bin/systemctl start tomcat, \ /bin/systemctl stop tomcat, \ /bin/systemctl restart tomcat, \ /bin/systemctl status *, \ /usr/bin/journalctl -u corebanking, \ /usr/bin/journalctl -u tomcat %appteam ALL=(root) NOPASSWD: APP_CMDS
BASH — Verify sudo config syntax
# ALWAYS check sudoers syntax after any change! visudo -c # Check specific drop-in file visudo -c -f /etc/sudoers.d/dbagrp # Test as a DBA user (dry run) sudo -l -U priya.nair

Quarterly Access Audit Script

15Security Best Practices

✅ The CIS RHEL 8 Benchmark Checklist (User Management)
  1. No shared accounts ever. Every human = 1 unique account. Service accounts are separate and documented.
  2. Disable root SSH. PermitRootLogin no in sshd_config. Only allow root access via sudo from personal accounts.
  3. SSH keys only for interactive access. PasswordAuthentication no in sshd_config for all production servers.

18Interview Questions

  • Q1. What is the difference between passwd -l and usermod -L? Which is better for blocking SSH access?

    Both lock the account by prepending ! to the password hash in /etc/shadow, making password authentication fail. However, neither blocks SSH key-based authentication.

    To fully block a user including SSH key access, you must either: (1) expire the account with usermod -e 1 username, (2) remove the authorized_keys file, or (3) change the shell to /sbin/nologin. In a BFSI environment, we combine all three for security incidents.

    passwd -l and usermod -L are functionally identical. usermod -L is preferred in scripts because usermod has a more consistent exit code behavior.

  • Q2. What happens internally when you run useradd?

    When useradd runs, it: (1) reads /etc/login.defs and /etc/default/useradd for defaults, (2) adds a new line to /etc/passwd with username, UID, GID, home, shell, (3) adds a locked password entry in /etc/shadow (the ! placeholder), (4) creates or updates /etc/group for the primary group, (5) if -m is used, creates the home directory and copies skeleton files from /etc/skel (.bashrc, .bash_profile, .bash_logout), (6) sets directory ownership to the new user.

  • Q3. What is /etc/skel and how do you use it in an enterprise?

    /etc/skel (skeleton) contains template files that are copied to every new user's home directory when their account is created with useradd -m.

    In SecureBank, we customize /etc/skel to include: (1) a custom .bashrc with company aliases and the audit prompt that shows username and hostname in the shell, (2) a .bash_profile that sets PATH and security warnings, (3) a .ssh/ directory with proper permissions already set, (4) a README.txt explaining company security policies. This ensures all users start with a consistent, secure baseline without extra manual steps.

  • Q4. A user says they were always able to sudo but suddenly can't. They didn't change anything. What do you check?

    Check in this order: (1) id username — did they get removed from the sudo group? Group memberships can change if usermod -G was run without -a, (2) visudo -c — was the sudoers file recently edited with a syntax error?, (3) Did they log out and back in after being added to a new group? Group membership only takes effect on new login sessions, (4) sudo -l -U username — what does sudo think they can run?, (5) Check if the sudoers.d file was accidentally deleted by another admin, (6) Check /var/log/secure for sudo denial messages with the exact reason.

  • Q5. What is PAM and why do we need it when Linux already has /etc/shadow for passwords?

    /etc/shadow only stores the hashed password. It doesn't have the intelligence to enforce rules like: "reject passwords containing username", "lock after 5 failures", "don't allow login between 11 PM and 6 AM", "require two-factor authentication".

    PAM (Pluggable Authentication Modules) is a framework that sits between the login process and the actual authentication. It processes requests through a stack of modules, each handling a specific aspect: pam_unix for basic password check, pam_pwquality for complexity rules, pam_faillock for lockout, pam_time for time-of-day restrictions, pam_google_authenticator for TOTP 2FA. This modular design means you can add or change security policies without touching application code.

  • Q6. Why do we use UID 6001+ for employees and not let the system auto-assign?

    In enterprise environments with NFS-mounted home directories (common in banks), file ownership is determined by UID, not username. If user priya.nair has UID 1002 on server01 but UID 1003 on server02 (due to different auto-assignment history), she will not own her own files when accessing them via NFS.

    By manually assigning UIDs from a reserved range (we use 6001+ for employees, 5001+ for service accounts) and maintaining a UID registry, we ensure the same user always has the same UID on every server. This is critical for NFS, and also makes audit logs consistent across servers — the same UID means the same person everywhere.

19Common Mistakes

🚨 Mistake 1 — Using usermod -G without -a

usermod -G dbagrp priya.nair — This REPLACES all supplementary groups with just dbagrp. If she was also in linuxusers and appteam, she loses those. Always use usermod -aG dbagrp priya.nair. The -a means APPEND.

🚨 Mistake 2 — Editing /etc/sudoers directly

Never use nano /etc/sudoers. A typo can lock all users out of sudo immediately. Always use visudo which checks syntax, or use /etc/sudoers.d/ drop-in files with visudo -f /etc/sudoers.d/teamname.

🚨 Mistake 3 — Deleting ex-employee accounts immediately

Never userdel -r username immediately for an ex-employee. Files owned by that UID become orphaned. Home directories may contain critical business data. Legal/compliance holds may require data retention. Always: lock → archive → wait for legal clearance → then delete.

⚠️ Mistake 4 — Setting .ssh permissions incorrectly

If ~/.ssh is 755 (world-readable) or authorized_keys is 644, SSH will SILENTLY ignore the keys. No error message. Users get "Permission denied" and think the key is wrong. Always: ~/.ssh = 700, authorized_keys = 600, both owned by the user.

⚠️ Mistake 5 — Forgetting to reload SSH after config changes

After editing /etc/ssh/sshd_config, run systemctl reload sshd (not restart — reload is graceful). Before reloading, ALWAYS test the config: sshd -t. A syntax error in sshd_config + systemctl restart sshd can break SSH access to the server.
