Chapter 1 · Foundation

AWS Overview & Identity (IAM)

Before touching any AWS service, you must first understand what the cloud IS, how AWS organises its data centres around the world, and how it decides who is allowed to do what — that is the job of IAM.

📖 The Story — "ShopKart" is born in the cloud

Imagine you are the DevOps engineer at a startup called ShopKart — an e-commerce company based in Bengaluru. The founder says: "We need our website to be available 24/7 to customers across India. We cannot afford to buy physical servers and manage a data centre." You say: "Let us use AWS — Amazon's cloud platform — and pay only for what we use."

But before you create a single server, your security-conscious CTO asks: "Who is allowed to create, modify, or delete resources? We cannot let a developer accidentally delete the production database!" This is where IAM — Identity and Access Management comes in. IAM is the security guard at the front door of your entire AWS account.

What is AWS? (The Big Picture)
🌍
Global Infrastructure
AWS has 33 Regions (like Mumbai, Singapore, US-East). Each Region has 3+ Availability Zones — separate physical data centres with their own power and cooling so that if one building fails, your app still runs.
💰
Pay-as-you-go
You pay by the hour or second. No upfront cost. If your traffic is high today and low tomorrow, you pay accordingly — just like your electricity bill.
🔧
200+ Services
Compute (EC2), Storage (S3), Database (RDS), Networking (VPC), Serverless (Lambda), Monitoring (CloudWatch) and more — all managed by Amazon.
🌐
Mumbai Region
For Indian companies, ap-south-1 (Mumbai) gives the lowest latency to Indian users. Always choose Mumbai for India-facing apps.
IAM — The Security Guard

IAM lets you control who (identity) can do what (permissions) on which AWS resource. There are four main building blocks:

IAM ConceptWhat it isReal-world analogy
Root AccountThe god-mode account created when you first sign up. Has unlimited power.The owner's master key — keep it locked in a safe, never use daily.
IAM UserA person in your organisation — developer, DBA, tester — each gets their own login.A staff ID card for each employee.
IAM GroupA collection of Users. Attach one policy to the group, all users in it inherit the permissions.A department in the office. "Developers" group = all developers get the same access.
IAM RolePermissions assumed temporarily by a service or person. No username/password needed.A visitor badge — given for a limited purpose, returned after use.
IAM PolicyA JSON document that says: "Allow/Deny action X on resource Y."The written rulebook — it defines exactly what is allowed.
IAM Policy — Code Explained Word by Word
💡This is a real IAM policy that allows a developer to read from S3 but not delete anything. Let us read it line by line so you understand every word.
JSONdeveloper-s3-readonly-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::shopkart-assets",
        "arn:aws:s3:::shopkart-assets/*"
      ]
    }
  ]
}
▶

"Version": "2012-10-17" — This is NOT today's date. It is the version of the IAM policy language itself. Always use 2012-10-17 — it is the latest and most powerful version that supports all modern features like policy variables.

▶

"Statement": [...] — A policy can have multiple statements (rules). Each statement is one rule. Here we have only one rule inside the array.

▶

"Sid": "AllowS3ReadOnly" — Sid means Statement ID. It is just a label you give to this rule so you can identify it later. It is optional but recommended for clarity.

▶

"Effect": "Allow" — The verdict. Either Allow or Deny. Here we are saying "yes, allow this action." If you write Deny, AWS blocks it — and Deny always wins over Allow.

▶

"Action": ["s3:GetObject","s3:ListBucket"] — These are the specific AWS API calls this person can make. GetObject = download a file from S3. ListBucket = see the list of files inside the bucket. We did NOT include s3:DeleteObject — so deleting is forbidden by default.

▶

"Resource": [...] — This limits the permission to only the shopkart-assets bucket. The first ARN covers the bucket itself. The second ARN with /* covers all files inside it. ARN = Amazon Resource Name — the unique ID of any AWS resource.

EC2 — Your Virtual Server in the Cloud

EC2 (Elastic Compute Cloud) is the backbone of AWS. It gives you a virtual computer in the cloud that you can start, stop, resize, and terminate anytime — in minutes.

📖 The Story — ShopKart needs its first web server

ShopKart is ready to launch its website. Ravi, the backend developer, has written a Node.js application. Now you, the DevOps engineer, need to put this app on a server that the internet can reach. In the old world, you would buy a physical server, install an OS, wait 2 weeks for delivery. With AWS EC2, you launch a virtual server in under 5 minutes — from your laptop!

You choose an Amazon Linux 2 server (like a Linux computer in the cloud), install Node.js on it, deploy Ravi's code, and the website is live. Tomorrow, if traffic doubles, you can upgrade the server size with two clicks — no downtime!

S3 — Infinite Object Storage

Amazon S3 (Simple Storage Service) lets you store any type of file — images, videos, logs, backups, code — at infinite scale, with 99.999999999% (11 nines) durability. AWS stores your file in at least 3 different physical locations automatically.

📖 The Story — ShopKart's Product Photos Problem

ShopKart sells 10,000 products. Each product has 5 photos. That's 50,000 images. Storing all these photos on the EC2 server's hard disk is a terrible idea — the disk will fill up, and if the server crashes, all photos are gone forever!

Instead, you store all product images in S3. S3 is like a Google Drive for your application — except it never fills up, it never goes down, and it can serve millions of users simultaneously. When a customer opens a product page, the image URL points directly to S3. Your EC2 server doesn't even get involved — S3 delivers the image straight to the customer's browser.

S3 Key Concepts
ConceptMeaning
BucketA container for files. Like a folder on your computer, but globally unique. Name must be unique across ALL of AWS worldwide. Example: shopkart-product-images-2024
ObjectAny single file you store in S3. Each object has: Key (file path/name), Value (the actual file data), Metadata (information about the file), and a Version ID.
KeyThe "path" or name of the object inside the bucket. Example: products/electronics/phone-1.jpg
Storage ClassHow frequently you access the file decides the cost. S3 Standard (daily), S3 IA (monthly), S3 Glacier (yearly). Less frequent = much cheaper.
Bucket PolicyA JSON rule that says who can access this bucket from the internet. Like a Security Group, but for S3.
VersioningS3 keeps every previous version of a file. If someone overwrites a file by mistake, you can restore the old version. Like Git for your files.
Pre-signed URLA temporary secret URL that gives someone access to a private file for a limited time (e.g., 1 hour). Used to share private files securely.
Static WebsiteYou can host a complete HTML/CSS/JS website directly from S3 — no EC2 server needed! Very cheap.
AWS CLI — Upload Files to S3 (Explained Word by Word)
💡AWS CLI is a command-line tool you install on your laptop. It lets you control ALL of AWS from the terminal — much faster than clicking in the console. Install from: aws.amazon.com/cli
BASHs3-operations.sh
# STEP 1: Configure AWS CLI with your IAM user credentials
aws configure
# This will ask you for:
# AWS Access Key ID — from the IAM user CSV you downloaded
# AWS Secret Access Key — also from the CSV
# Default region — type: ap-south-1  (this is Mumbai)
# Default output format — type: json

# STEP 2: Create a new S3 bucket
aws s3 mb s3://shopkart-product-images-2024
# aws = the CLI tool
# s3 = we are working with the S3 service
# mb = make bucket (create a new empty bucket)
# s3://shopkart-product-images-2024 = the bucket name
# must be globally unique — if this name is taken, try another

# STEP 3: Upload a single file
aws s3 cp ./phone-1.jpg s3://shopkart-product-images-2024/products/phone-1.jpg
# cp = copy (just like the Linux cp command)
# ./phone-1.jpg = source file on YOUR local laptop
# s3://.../.../phone-1.jpg = destination path inside the bucket
# products/ is a "folder" (S3 doesn't have real folders, but the
# slash / in the key name creates a virtual folder structure)

# STEP 4: Upload an entire folder (all product images at once)
aws s3 sync ./product-images/ s3://shopkart-product-images-2024/products/ --delete
# sync = compare local folder and S3 bucket, upload only the
# files that are NEW or CHANGED. Much smarter than cp.
# ./product-images/ = the folder on your laptop
# s3://.../ = the destination in S3
# --delete = if a file was deleted locally, delete it in S3 too
# This keeps S3 perfectly in sync with your local folder

# STEP 5: List files in your bucket
aws s3 ls s3://shopkart-product-images-2024/products/
# ls = list (show all files, just like ls in Linux)
# shows file name, size, and last modified date for each object

# STEP 6: Make a single file publicly accessible (for a product image)
aws s3api put-object-acl \
  --bucket shopkart-product-images-2024 \
  --key products/phone-1.jpg \
  --acl public-read
# put-object-acl = set access control for this specific object
# --bucket = which bucket this object lives in
# --key = the "path" (name) of the file inside the bucket
# --acl public-read = anyone on the internet can VIEW this file
# (but they cannot write/delete, only read)

VPC — Your Private Network in AWS

VPC (Virtual Private Cloud) is your own isolated section of the AWS cloud. Think of it as building a private neighbourhood in a city — you control the roads, gates, and who is allowed in or out.

📖 The Story — ShopKart needs a secure network

ShopKart is growing. Now they have a web server (EC2), a database (coming soon — RDS), and an internal admin panel. The CTO has one strict requirement: "The database must NEVER be directly accessible from the internet. Only the web server should be able to talk to the database." This is exactly what VPC architecture solves.

You design a VPC with two types of spaces: a Public Subnet (where the web server lives — internet can reach it) and a Private Subnet (where the database lives — only servers inside the VPC can talk to it). The internet cannot reach the database directly even if it wanted to.

VPC Architecture Diagram

EC2 Web Server

RDS Database

VPC Key Concepts
ConceptWhat it Does
CIDR BlockThe range of private IP addresses your VPC will use. Example: 10.0.0.0/16 = you have 65,536 possible IP addresses to assign to your servers.
SubnetA smaller piece of your VPC. Public Subnet (10.0.1.0/24) = 256 IPs for public resources. Private Subnet (10.0.2.0/24) = 256 IPs for private resources.
Internet GatewayThe front door of your VPC. Attach it to your VPC and update the Route Table to allow internet traffic to reach your public subnet.
Route TableA set of rules that say: "traffic going to 0.0.0.0/0 (the internet) should go through the Internet Gateway." Without this, even your public subnet cannot talk to the internet.
NAT GatewayAllows private subnet resources (like your database) to initiate outbound internet connections (e.g., to download software updates) WITHOUT allowing inbound connections from the internet.
Security GroupA stateful virtual firewall at the instance level. You define inbound and outbound rules per port and protocol.
NACLNetwork ACL — a stateless firewall at the subnet level. Acts as a second layer of defence. Stateless means you must define both inbound AND outbound rules separately.

RDS — Managed Relational Database

RDS (Relational Database Service) gives you a fully managed database — MySQL, PostgreSQL, MariaDB, Oracle, SQL Server — where AWS handles all the boring but critical parts: automated backups, software patching, multi-AZ failover, and scaling.

📖 The Story — ShopKart needs a reliable database

ShopKart's database stores everything: customer orders, product inventory, payment records. This data is the most valuable asset. If the database crashes or gets corrupted, the company loses money every second it's down. Running a database yourself on EC2 means YOU are responsible for all backups, updates, and disaster recovery — that is a full-time job on its own!

Instead, you use RDS. AWS runs the database for you. Every night, AWS automatically takes a backup. If your primary database server fails (e.g., a hardware fault in one AZ), RDS automatically switches to a standby copy in a different AZ in under 2 minutes — your app barely notices.

RDS Key Features
🔄
Multi-AZ Deployment
AWS maintains a standby copy of your DB in a different AZ. If the primary fails, automatic failover happens in minutes. Your data is safe even if one data centre burns down.
📖
Read Replicas
Create read-only copies of your DB in different regions. Heavy reporting/analytics queries hit the replica — your primary DB stays fast for write operations.
💾
Automated Backups
AWS takes daily snapshots and stores transaction logs. You can restore your DB to ANY point in the last 35 days — down to the exact second!
🔐
Encryption at Rest
All data stored on disk is encrypted using AWS KMS keys. Even if someone steals the hard drive, they cannot read your data without the encryption key.
Connect Node.js App to RDS — Code Explained
JavaScriptdb-connection.js (ShopKart App)
const mysql = require('mysql2/promise');
// require() = import this library into our file
// mysql2 = the MySQL driver for Node.js (must run: npm install mysql2)
// /promise = use the modern async/await version (not callback-based)

const pool = mysql.createPool({
// createPool = create a "pool" of database connections
// A pool keeps multiple connections open and reuses them
// This is much faster than opening a new connection for every query

  host: process.env.DB_HOST,
// host = the address of your RDS instance
// We DON'T hardcode the address here — that would be a security risk
// Instead we read it from an environment variable DB_HOST
// In EC2, set this as: DB_HOST=shopkart-db.xyz.ap-south-1.rds.amazonaws.com

  user: process.env.DB_USER,
  password: process.env.DB_PASS,
// user and password also come from environment variables
// NEVER put passwords in code files that go to Git!

  database: 'shopkart_db',
// database = the specific database schema to connect to
// One RDS instance can host multiple databases (schemas)

  connectionLimit: 10,
// Maximum 10 connections open at the same time
// If 11 requests come in simultaneously, the 11th waits for
// one of the first 10 to finish before getting a connection

  ssl: { rejectUnauthorized: true }
// ssl = use encrypted TLS connection between our app and RDS
// rejectUnauthorized: true = reject any fake/invalid certificates
// This prevents man-in-the-middle attacks on the DB connection
});

// Export the pool so other files in the app can use it
module.exports = pool;

Lambda — Serverless Computing

AWS Lambda lets you run code WITHOUT managing any server. You just upload your function, define what event triggers it, and AWS runs it automatically. You pay only for the milliseconds your code actually runs. No server = no idle cost!

📖 The Story — The Image Resize Problem

When a ShopKart seller uploads a product photo (5MB raw image), the website needs THREE sizes: a thumbnail (100x100px), a medium card image (400x400px), and a full-size view (1200x1200px). This resize process is CPU-heavy and should NOT happen on the main web server (it would slow down customer requests).

The solution: you set up a Lambda function. Whenever a new image is uploaded to the S3 "raw-uploads" bucket, S3 automatically triggers your Lambda function. Lambda downloads the image, creates three resized versions, saves them back to a "processed-images" bucket — all within 2 seconds. The web server never had to do any work!

Lambda Function — Python Code Explained
Pythonlambda_function.py — Image Resizer
import boto3
# boto3 = the official AWS SDK for Python
# It lets you talk to ANY AWS service from Python code
# Lambda has boto3 pre-installed, you don't need to install it

import json
from PIL import Image
import io
# PIL = Python Imaging Library (Pillow). Used to resize images
# io = lets us work with data in memory without saving to disk
# (Lambda has no permanent disk, so we must use memory)

s3_client = boto3.client('s3')
# boto3.client('s3') = create an S3 "client" object
# A client is how you send commands to an AWS service
# Lambda's execution role automatically provides permissions —
# no username/password needed here!

SIZES = {
    'thumbnail': (100, 100),
    'medium':    (400, 400),
    'large':     (1200, 1200)
}
# SIZES = a dictionary of the three sizes we want to create
# key = human-friendly name, value = (width, height) in pixels

def lambda_handler(event, context):
## lambda_handler = the ENTRY POINT function AWS calls when
## Lambda triggers. It MUST be named lambda_handler (by default)
## event = a dict containing info about what triggered this Lambda
##   (in our case: which S3 bucket and which file was uploaded)
## context = runtime info like time remaining, memory used

    # Extract the bucket name and file key from the S3 event
    record = event['Records'][0]
    ## Records[0] = S3 sends an array of events, we take the first

    source_bucket = record['s3']['bucket']['name']
    object_key    = record['s3']['object']['key']
    ## source_bucket = e.g. "shopkart-raw-uploads"
    ## object_key = e.g. "seller-42/product-photo.jpg"

    # Download the original image from S3 into memory
    response = s3_client.get_object(
        Bucket=source_bucket,
        Key=object_key
    )
    image_data = response['Body'].read()
    ## get_object = download file from S3
    ## response['Body'].read() = read the raw bytes of the image

    original_image = Image.open(io.BytesIO(image_data))
    ## io.BytesIO = wraps raw bytes so PIL can treat them like a file
    ## Image.open() = open the image from memory — ready to resize

    for size_name, dimensions in SIZES.items():
    ## Loop through each of the 3 sizes in our SIZES dictionary

        resized = original_image.copy()
        resized.thumbnail(dimensions)
        ## .thumbnail() = resize the image proportionally
        ## It will NOT stretch the image — it keeps the aspect ratio

        buffer = io.BytesIO()
        resized.save(buffer, format='JPEG', quality=85)
        ## Save the resized image to a memory buffer (not to disk!)
        ## quality=85 = good quality but 30% smaller file size than 100

        buffer.seek(0)
        ## seek(0) = move the reading position back to the start
        ## Without this, S3 upload would get an empty file!

        dest_key = f"processed/{size_name}/{object_key}"
        s3_client.put_object(
            Bucket='shopkart-processed-images',
            Key=dest_key,
            Body=buffer,
            ContentType='image/jpeg'
        )
        ## put_object = upload the resized image to the destination S3
        ## The key will be like: processed/thumbnail/seller-42/photo.jpg

    return {'statusCode': 200, 'body': 'Images resized!'}
# Return a response — statusCode 200 means SUCCESS

ALB + Auto Scaling — Handle Any Traffic

A Load Balancer distributes incoming traffic across multiple servers so no single server gets overwhelmed. Auto Scaling automatically adds or removes servers based on traffic — so you always have exactly the right number of servers running.

📖 The Story — Big Billion Day Sale

ShopKart is running a "Big Billion Day" sale. Traffic is expected to be 50x normal. With a single EC2 server, the website will crash in minutes. You need a way to automatically start 10 more servers as traffic increases, and automatically stop them when the sale ends (to avoid paying for idle servers).

Solution: You put an Application Load Balancer (ALB) in front. The ALB receives all traffic and distributes it across a group of EC2 instances. You create an Auto Scaling Group (ASG) that monitors CPU — when CPU > 60%, it adds more EC2s. When CPU drops below 20%, it removes them. The website handles millions of visitors without a single manual intervention!

Key Terms Explained
TermMeaning
Target GroupA group of EC2 instances that the ALB sends traffic to. The ALB does a "health check" on each instance — if an instance fails 3 health checks (returns error 500 or times out), ALB stops sending traffic to it.
ListenerThe ALB "listens" on port 80 (HTTP) or 443 (HTTPS). You configure rules: "If path is /api/*, forward to API target group. If path is /images/*, forward to image-server target group."
Launch TemplateA recipe that tells Auto Scaling: "When you create a new server, use this AMI, this instance type, this security group, and run this User Data script." The ASG uses this to automatically spin up identical servers.
Scaling PolicyThe rule for when to add/remove servers. Target Tracking policy: "Keep average CPU at 60%. If CPU goes above 60%, add servers. If it drops below, remove them." Simplest and most recommended policy.
Cooldown PeriodAfter adding a server, wait 300 seconds before making another scaling decision. This prevents rapid-fire scaling (adding servers every 5 seconds in a loop).

ECS — Running Containers on AWS

ECS (Elastic Container Service) is AWS's fully managed container orchestration platform. You package your application into a Docker container and ECS runs it, scales it, and restarts it automatically if it crashes — without you managing any servers (with Fargate mode).

📖 The Story — ShopKart adopts Microservices

ShopKart is scaling fast. The single Node.js app is now becoming a problem — every small update requires deploying the entire app. Developers want to split it into microservices: user-service, product-service, order-service, each built and deployed independently as a Docker container.

With ECS Fargate, you don't manage EC2 servers at all. You say: "Run 3 copies of order-service using 0.5 vCPU and 1GB RAM each." AWS handles all the server infrastructure. If one container crashes, ECS automatically starts a new one. During high traffic, ECS can scale from 3 to 30 containers in seconds.

ECS Key Components
ComponentWhat it is
ClusterA logical group where your containers run. With Fargate, the cluster has no servers — AWS manages the underlying compute invisibly.
Task DefinitionA blueprint (JSON file) describing: which Docker image to use, how much CPU and RAM to give it, which ports to expose, which environment variables to set, and which IAM role it should have.
TaskOne running instance of your container, created from a Task Definition. Like a running copy of your Docker container.
ServiceKeeps a specified number of Tasks running at all times. If a Task crashes, the Service immediately starts a replacement. Integrates with ALB for load balancing.
ECRElastic Container Registry — AWS's private Docker Hub. Push your Docker images here. ECS pulls images from ECR to run them.
FargateServerless compute for containers. You specify CPU + RAM needed, and AWS runs the containers on invisible managed servers. No EC2 management needed!
Dockerfile + ECS Deployment — Explained

CloudFormation — Infrastructure as Code

CloudFormation lets you describe your entire AWS infrastructure in a YAML or JSON file. Run the file once, and AWS creates every resource automatically — VPC, EC2, RDS, ALB — in the exact right order. Delete the "stack" and everything is destroyed cleanly. Infrastructure as Code (IaC) is the modern DevOps standard.

📖 The Story — ShopKart needs 3 environments

ShopKart now needs three separate environments: Development (for developers to test code), Staging (for QA team to test before release), and Production (for real customers). Manually clicking through the AWS console to create all resources for each environment would take days and would be error-prone. With CloudFormation, you write the infrastructure once in a YAML file, and deploy it three times with different parameters — dev, staging, prod. Perfectly identical environments, created in minutes.

CloudFormation Template — Explained Section by Section
YAMLshopkart-stack.yaml (CloudFormation Template)
AWSTemplateFormatVersion: '2010-09-09'
# The version of CloudFormation template format
# Always use '2010-09-09' — it's the only valid value today

Description: 'ShopKart Web Application Stack'
# A human-readable description of what this stack creates

Parameters:
# Parameters allow you to reuse this same template for
# dev, staging, prod — just change the parameter values
  Environment:
    Type: String
    AllowedValues: [dev, staging, prod]
    ## AllowedValues = the user MUST choose one of these
    ## CloudFormation will reject any other value
  InstanceType:
    Type: String
    Default: t2.micro
    ## Default = if not specified, use t2.micro

Conditions:
# Conditions let you create resources only in certain situations
  IsProduction: !Equals [!Ref Environment, prod]
  ## IsProduction = true only when Environment parameter = "prod"
  ## We'll use this to enable Multi-AZ ONLY in production

Resources:
# Resources = the ACTUAL AWS resources to create. This is the
# most important section of every CloudFormation template.

  ShopKartVPC:
    Type: AWS::EC2::VPC
    ## Type = the AWS resource type. Format: AWS::Service::ResourceType
    Properties:
      CidrBlock: 10.0.0.0/16
      EnableDnsHostnames: true
      ## EnableDnsHostnames = EC2 instances get hostnames like
      ## ec2-1-2-3-4.ap-south-1.compute.amazonaws.com
      Tags:
        - Key: Name
          Value: !Sub 'shopkart-vpc-${Environment}'
          ## !Sub = string substitution. Replaces ${Environment}
          ## with the actual parameter value. Result: shopkart-vpc-prod

  PublicSubnet:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref ShopKartVPC
      ## !Ref = reference another resource in this same template
      ## CloudFormation knows ShopKartVPC must be created FIRST
      ## before PublicSubnet — it handles the order automatically!
      CidrBlock: 10.0.1.0/24
      MapPublicIpOnLaunch: true
      ## MapPublicIpOnLaunch = every EC2 in this subnet
      ## automatically gets a public IP address

  WebServerInstance:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: !Ref InstanceType
      ## !Ref InstanceType = use the InstanceType parameter value
      ImageId: ami-0f5ee92e2d63afc18
      ## Mumbai (ap-south-1) Amazon Linux 2 AMI ID
      SubnetId: !Ref PublicSubnet
      UserData:
        Fn::Base64: |
          #!/bin/bash
          yum update -y
          yum install -y nodejs
          ## Fn::Base64 = CloudFormation encodes this script in base64
          ## because EC2's UserData field requires base64-encoded scripts

Outputs:
# Outputs display important values after stack creation
# like the website URL — so you know where to access it
  WebsiteURL:
    Description: 'ShopKart Website URL'
    Value: !Sub 'http://${WebServerInstance.PublicIp}'
    ## After stack creation, this URL is shown in the console

SNS + SQS — Messaging & Decoupling

SNS (Simple Notification Service) is a pub/sub messaging service — broadcast a message to many subscribers. SQS (Simple Queue Service) is a message queue — one service puts a message in the queue, another service picks it up and processes it. Together, they make your microservices loosely coupled and resilient.

📖 The Story — Order Placed! Now What?

When a customer places an order on ShopKart, FIVE things need to happen: (1) Confirm payment, (2) Send confirmation email, (3) Send SMS notification, (4) Update inventory, (5) Notify the warehouse to pack and ship. All of this cannot happen synchronously — the customer cannot wait 10 seconds for all these operations to finish before seeing "Order Confirmed!"

Solution: The Order Service publishes one message "OrderPlaced" to an SNS Topic. SNS instantly fans out (broadcasts) this message to multiple SQS queues: email-queue, sms-queue, inventory-queue, warehouse-queue. Each service reads from its own queue and processes the order at its own pace. The customer gets "Order Confirmed!" in milliseconds. All the backend work happens asynchronously in the background.

Architecture: SNS Fan-out to SQS

Python Code — Publish to SNS from Lambda
Pythonorder_service.py — Publish event after order creation
import boto3, json, os

sns = boto3.client('sns')
# Create an SNS client to talk to the SNS service
# boto3 auto-detects the region from the Lambda environment

def place_order(order_data):
    # 1. Save order to database (RDS) — not shown here
    # 2. Publish event to SNS so all downstream services know

    event_payload = {
        "event":       "OrderPlaced",
        "orderId":     order_data['id'],
        "customerId":  order_data['customer_id'],
        "totalAmount": order_data['total'],
        "items":       order_data['items']
    }
    ## event_payload = the message we are broadcasting
    ## We include ALL relevant data so downstream services
    ## don't need to query the database to get order details

    response = sns.publish(
        TopicArn=os.environ['ORDER_TOPIC_ARN'],
        ## TopicArn = the unique ID of the SNS Topic
        ## We read it from env variable — not hardcoded

        Message=json.dumps(event_payload),
        ## Message = the actual content to publish
        ## json.dumps = converts the Python dict to a JSON string
        ## because SNS messages must be strings, not Python objects

        Subject='New Order Placed',
        ## Subject = optional. Used when SNS delivers to email
        ## becomes the email subject line

        MessageAttributes={
            'eventType': {
                'DataType': 'String',
                'StringValue': 'OrderPlaced'
            }
        }
        ## MessageAttributes = extra metadata attached to the message
        ## SQS subscribers can FILTER on this attribute
        ## e.g. SMS queue only subscribes to OrderPlaced events
        ## not to InventoryUpdated events — saving processing cost
    )
    return response['MessageId']
    # MessageId = a unique ID SNS assigns to this published message
    # Useful for debugging: "which message caused this error?"

env:

    ## Parameter Store at BUILD time — NEVER hardcode secrets in buildspec!

phases:
# Phases = stages of the build. CodeBuild runs them in order.

  install:
    ## install = set up the build environment
    runtime-versions:
      nodejs: 18
      ## Tell CodeBuild: I need Node.js version 18 on my build server
    commands:
      - npm install
      ## Install dependencies needed for running tests

  pre_build:
    ## pre_build = run BEFORE the main build step
    ## Perfect for: running tests, security scans, linting
    commands:
      - echo "Running unit tests..."
      - npm test
      ## If tests FAIL, CodeBuild marks the phase as FAILED
      ## and the pipeline STOPS. Code never reaches production!

      - echo "Logging in to ECR..."
      - aws ecr get-login-password --region $AWS_REGION |
          docker login --username AWS --password-stdin
          $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
      ## Login to ECR so we can push the Docker image
      ## $AWS_ACCOUNT_ID is automatically set by CodeBuild

      - COMMIT_HASH=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-7)
      ## CODEBUILD_RESOLVED_SOURCE_VERSION = the git commit hash
      ## cut -c 1-7 = take only first 7 characters (short hash)
      ## We tag Docker images with the commit hash — so we can
      ## always trace exactly which code is running in production

  build:
    ## build = the main build step
    commands:
      - echo "Building Docker image..."
      - docker build -t $ECR_REPO:$COMMIT_HASH .
      - docker tag $ECR_REPO:$COMMIT_HASH
          $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$ECR_REPO:$COMMIT_HASH
      - docker push
          $AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/$ECR_REPO:$COMMIT_HASH
      ## Build the Docker image and push it to ECR
      ## Tagged with the git commit hash for full traceability

  post_build:
    ## post_build = runs after build. Used to create deployment
    ## artifacts that CodeDeploy needs
    commands:
      - printf '[{"name":"order-service","imageUri":"%s"}]'

      ## which Docker image to deploy in the CodeDeploy stage
      ## Without this file, CodeDeploy doesn't know what image to use

artifacts:
  files: imagedefinitions.json
  ## artifacts = files to pass from the build stage to the deploy stage
  ## CodePipeline stores these in S3 between stages
