PROJECT 01 · BASIC · S3 + CLOUDFRONT

Static Website Hosting on S3 + CloudFront

Host a global, fast, cheap, and highly available website — served from 400+ edge locations worldwide — without managing a single server.

S3CloudFrontRoute 53ACMHTML/CSS

Meet Priya, a startup founder who just built her product landing page. She needs it online FAST — but hiring a DevOps engineer is expensive, and she can't afford downtime. Her developer friends say "just use S3 static hosting". What does that even mean?

S3 (Simple Storage Service) is AWS's object storage — think of it as a Google Drive in the cloud, but designed for machines, not humans. When you tell S3 a bucket is a "website", it knows to serve HTML files to browsers. CloudFront is AWS's CDN (Content Delivery Network): it caches Priya's website at AWS edge locations in Mumbai, Singapore, Frankfurt, New York — so users everywhere get blazing-fast load times.

💡 Core Concepts

  • S3 Bucket — A container for objects (files). Each bucket has a globally unique name. Objects are files: HTML, CSS, JS, images.
  • Static Website Hosting — An S3 setting that makes the bucket serve HTTP requests. It adds an endpoint like bucket.s3-website.amazonaws.com.
  • CloudFront Distribution — A CDN layer that sits in front of S3, caches content at edge locations, adds HTTPS, and reduces S3 costs.
  • Origin Access Control (OAC) — Ensures only CloudFront can read from S3. Users can't bypass the CDN and hit S3 directly.
  • ACM (AWS Certificate Manager) — Free SSL/TLS certificates for HTTPS. CloudFront requires certs in us-east-1.

🛠 Hands-On Steps

1

Prerequisites — Install AWS CLI & Configure Credentials

First, install the AWS CLI on your machine. Then configure it with your Access Key ID and Secret Access Key (from IAM → Users → Security Credentials in AWS Console).

curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip" unzip awscliv2.zip && sudo ./aws/install # For macOS: brew install awscli # Configure your credentials aws configure

When prompted, enter: AWS Access Key ID, AWS Secret Access Key, Default region (e.g., ap-south-1 for Mumbai), Output format (json).

2

Create an S3 Bucket

Bucket names must be globally unique. Replace priya-startup-site-2024 with your own unique name.

aws s3 mb s3://priya-startup-site-2024 --region ap-south-1

What each part means:

  • aws → the AWS CLI tool
  • s3 → the S3 sub-command group
  • mb → "make bucket"
  • s3://priya-startup-site-2024 → bucket URI (s3:// is the protocol, then bucket name)
  • --region ap-south-1 → Mumbai data centre
3

Create Your Website Files

Create a local folder with your website content:

mkdir mysite && cd mysite cat > index.html << 'EOF' <!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>Priya's Startup</title> <style> body { font-family: sans-serif; text-align: center; padding: 60px; background: #0a0c10; color: white; } h1 { font-size: 48px; color: #00d4ff; } p { color: #94a3b8; } </style> </head> <body> <h1>Hello from AWS S3! 🚀</h1> <p>This site is served from S3 + CloudFront</p> </body> </html> EOF
4

Upload Files to S3

aws s3 sync . s3://priya-startup-site-2024 --delete

sync = only upload changed files (like rsync). --delete = remove files from S3 that no longer exist locally. This makes your bucket mirror your local folder exactly.

5

Block All Public Access (Security Best Practice)

Keep the bucket private. CloudFront will access it via OAC — not public URLs.

aws s3api put-public-access-block \ --bucket priya-startup-site-2024 \ --public-access-block-configuration \ "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"
6

Create CloudFront Distribution

Go to AWS Console → CloudFront → Create Distribution. Set:

  • Origin domain → your S3 bucket
  • Origin access → Origin Access Control (create new OAC)
  • Viewer protocol policy → Redirect HTTP to HTTPS
  • Default root object → index.html
  • Price class → Use all edge locations (best performance)

CloudFront will generate a d1abc123.cloudfront.net domain. Your site is live globally in ~10 minutes.

7

Attach S3 Bucket Policy to Allow CloudFront

After creating the OAC, CloudFront shows you a bucket policy. Apply it:

aws s3api put-bucket-policy --bucket priya-startup-site-2024 --policy '{ "Version": "2012-10-17", "Statement": [{ "Sid": "AllowCloudFrontServicePrincipal", "Effect": "Allow", "Principal": { "Service": "cloudfront.amazonaws.com" }, "Action": "s3:GetObject", "Resource": "arn:aws:s3:::priya-startup-site-2024/*", "Condition": { "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::YOUR_ACCOUNT_ID:distribution/YOUR_DIST_ID" } } }] }'

PROJECT 02 · BASIC · EC2 + AUTO SCALING

EC2 Web Server with Auto Scaling Group

Launch a virtual machine, install a web server, then make it automatically scale from 1 to 10 instances under load — and back down when traffic drops.

EC2Auto Scaling GroupALBLaunch TemplateSecurity Groups

It's 11 PM on a Monday. Raj's e-commerce site just got featured on a popular tech blog. Traffic explodes from 100 visitors/hour to 50,000 visitors/hour. His single EC2 instance crashes. He loses ₹5 lakh in sales in 2 hours.

The solution? An Auto Scaling Group (ASG). Instead of one server, you define a template ("my server should look like this") and tell AWS: "always keep 2 servers running, but if CPU goes above 70%, add more — up to 10 maximum." AWS monitors your fleet and scales automatically. An Application Load Balancer (ALB) sits in front, distributing traffic across all healthy instances.

💡 Core Concepts

  • EC2 (Elastic Compute Cloud) — Virtual machines in AWS. You choose CPU, RAM, storage, and OS. Think of it as renting a computer in a data centre.
  • Launch Template — A saved "recipe" for EC2 instances: AMI (OS image), instance type, security groups, user data script. ASG uses this to create identical instances.
  • Auto Scaling Group (ASG) — A fleet of EC2 instances managed automatically. Defines min/max/desired count and scaling policies.
  • Application Load Balancer (ALB) — Layer 7 (HTTP/HTTPS) load balancer. Routes requests to healthy instances. Performs health checks.
  • Security Group — A virtual firewall for EC2. Rules control inbound/outbound traffic by port, protocol, and IP range.
  • User Data — A bash script that runs automatically when an EC2 instance first boots. Used to install software, configure services.

1

Create a Key Pair (to SSH into EC2)

aws ec2 create-key-pair \ --key-name raj-webserver-key \ --query 'KeyMaterial' \ --output text > raj-webserver-key.pem chmod 400 raj-webserver-key.pem

--query 'KeyMaterial' extracts just the private key from the JSON response. chmod 400 makes it readable only by you — SSH refuses to use a key that others can read (security protection).

2

Create Security Groups

One for the ALB (public internet → ALB) and one for EC2 (ALB → EC2 only):

# Security Group for ALB aws ec2 create-security-group \ --group-name raj-alb-sg \ --description "Allow HTTP/HTTPS from internet" # Allow HTTP to ALB aws ec2 authorize-security-group-ingress \ --group-name raj-alb-sg \ --protocol tcp \ --port 80 \ --cidr 0.0.0.0/0 # Security Group for EC2 (only ALB can talk to it) aws ec2 create-security-group \ --group-name raj-ec2-sg \ --description "Allow HTTP only from ALB" aws ec2 authorize-security-group-ingress \ --group-name raj-ec2-sg \ --protocol tcp \ --port 80 \ --source-group raj-alb-sg

5

Create Auto Scaling Group

aws autoscaling create-auto-scaling-group \ --auto-scaling-group-name raj-web-asg \ --launch-template LaunchTemplateName=raj-webserver-template,Version='$Latest' \ --min-size 2 \ --max-size 10 \ --desired-capacity 2 \ --target-group-arns arn:aws:elasticloadbalancing:ap-south-1:123:targetgroup/raj-web-tg/abc \ --availability-zones ap-south-1a ap-south-1b \ --health-check-type ELB \ --health-check-grace-period 300

Breaking this down: min-size 2 = never go below 2 instances. max-size 10 = never exceed 10. desired-capacity 2 = start with 2. health-check-grace-period 300 = give new instances 5 minutes to start before checking health.

6

Create CPU-Based Scaling Policy

aws autoscaling put-scaling-policy \ --auto-scaling-group-name raj-web-asg \ --policy-name raj-cpu-scaling \ --policy-type TargetTrackingScaling \ --target-tracking-configuration '{ "TargetValue": 70.0, "PredefinedMetricSpecification": { "PredefinedMetricType": "ASGAverageCPUUtilization" } }'

Target Tracking Scaling is like cruise control for your fleet — tell it "keep CPU at 70%" and it automatically adds/removes instances to hit that target. You don't write scale-up and scale-down policies separately.

PROJECT 03 · BASIC · LAMBDA + API GATEWAY + DYNAMODB

Serverless REST API with Lambda & API Gateway

Build a fully functional CRUD REST API — no servers, no OS patching, no capacity planning. Pay only for what you use, down to the millisecond.

LambdaAPI GatewayDynamoDBIAMPython 3.12

Aisha is building a todo app. She needs an API: POST /todos to create, GET /todos to list, DELETE /todos/{id} to remove. The traditional approach would be: rent a server, install Python, run Flask/Django, set up nginx, manage SSL, worry about crashes.

With AWS Lambda + API Gateway, Aisha writes just the business logic — a Python function. AWS runs it on-demand: when a request arrives, AWS spins up the function in milliseconds, runs it, and shuts it down. Zero servers to manage. DynamoDB is a fully managed NoSQL database — perfect for simple key-value data like todos, with single-digit millisecond latency.

💡 Core Concepts

  • Lambda Function — Code that runs on-demand without a server. Supports Python, Node.js, Go, Java, and more. First 1 million requests per month are FREE.
  • API Gateway — A managed HTTP endpoint that routes requests to Lambda. Handles auth, rate limiting, CORS, SSL automatically.
  • DynamoDB — Serverless NoSQL database. Stores items as JSON-like documents. Scales to millions of TPS automatically.
  • Lambda Handler — The entry-point function: def handler(event, context). event contains the HTTP request data; context has runtime metadata.
  • IAM Execution Role — Lambda needs permission to access DynamoDB. An IAM role attached to Lambda grants these permissions.

🛠 Hands-On Steps

1

Create DynamoDB Table

aws dynamodb create-table \ --table-name Todos \ --attribute-definitions AttributeName=id,AttributeType=S \ --key-schema AttributeName=id,KeyType=HASH \ --billing-mode PAY_PER_REQUEST \ --region ap-south-1

2

Create the Lambda Function Code (lambda_function.py)

Create a file called lambda_function.py with this content:

lambda_function.py PYTHON 3.12 
import json       # Parse/create JSON data for HTTP requests/responses
import boto3      # AWS SDK for Python — lets us talk to DynamoDB, S3, etc.
import uuid       # Generate universally unique IDs for each todo item
from datetime import datetime  # Track when todos were created

# boto3.resource() creates a high-level DynamoDB client
# 'dynamodb' tells boto3 which AWS service to connect to
dynamodb = boto3.resource('dynamodb')

# .Table('Todos') gives us a reference to our specific table
# This doesn't make a network call yet — it's just a reference object
table = dynamodb.Table('Todos')


def lambda_handler(event, context):
    """
    Main entry point for Lambda.
    'event' = dict containing the full HTTP request from API Gateway
    'context' = Lambda runtime info (timeout, memory, request ID)
    """

    # event['httpMethod'] contains 'GET', 'POST', or 'DELETE'
    method = event['httpMethod']

    # Route to the correct handler based on HTTP method
    if method == 'GET':
        return get_todos()

    elif method == 'POST':
        # event['body'] is a JSON string — parse it to a dict
        body = json.loads(event['body'])
        return create_todo(body)

    elif method == 'DELETE':
        # Path parameters like /todos/{id} come in pathParameters
        todo_id = event['pathParameters']['id']
        return delete_todo(todo_id)

    # If method is not handled, return 405 Method Not Allowed
    return response(405, {'error': 'Method not allowed'})


def get_todos():
    # scan() reads EVERY item in the table — fine for small tables
    # For large tables, use query() with an index instead
    result = table.scan()

    # result['Items'] is a list of dicts — each dict is one todo
    return response(200, result['Items'])


def create_todo(body):
    # Generate a unique ID using UUID4 (random UUID)
    # str() converts UUID object to string like "a1b2c3d4-..."
    todo = {
        'id': str(uuid.uuid4()),

        # .get() safely reads 'title' from body; '' is default if missing
        'title': body.get('title', ''),

        'done': False,   # New todos are not done by default

        # isoformat() gives "2024-01-15T10:30:00" — sortable timestamp
        'createdAt': datetime.utcnow().isoformat()
    }

    # put_item() inserts or replaces an item in DynamoDB
    table.put_item(Item=todo)

    # Return 201 Created with the new todo item
    return response(201, todo)


def delete_todo(todo_id):
    # delete_item() removes item matching the given primary key
    # 'Key' must include the partition key (and sort key if exists)
    table.delete_item(Key={'id': todo_id})
    return response(200, {'message': 'Deleted'})


def response(status_code, body):
    """
    API Gateway requires a specific response format.
    statusCode = HTTP status number
    headers = allow browser CORS (cross-origin requests)
    body = must be a JSON STRING (not dict) — that's why json.dumps()
    """
    return {
        'statusCode': status_code,
        'headers': {
            'Content-Type': 'application/json',
            'Access-Control-Allow-Origin': '*'  # Allow all origins (for dev)
        },
        # json.dumps converts Python dict → JSON string
        'body': json.dumps(body, default=str)
    }

PROJECT 04 · INTERMEDIATE · RDS + SECRETS MANAGER

RDS MySQL with Secrets Manager

Deploy a managed relational database with automatic backups, Multi-AZ failover, and zero hardcoded passwords — the production way to handle databases.

RDSSecrets ManagerVPCParameter GroupsMySQL 8.0

Sanjay's team just got flagged in a security audit: their database password is hardcoded in config.py as DB_PASSWORD = "mysecretpassword123". Worse, it was checked into GitHub. Any developer with repo access — or anyone who finds the repo — has their production database password.

AWS RDS is a fully managed relational database service — AWS handles backups, patching, failover, and scaling. Secrets Manager stores your database credentials encrypted, rotates them automatically every 30 days, and lets your application fetch the password at runtime via an API call — the password never lives in your code or environment variables.

💡 Core Concepts

  • RDS (Relational Database Service) — Managed MySQL, PostgreSQL, Oracle, SQL Server. AWS handles all DBA tasks. You just run queries.
  • Multi-AZ — Deploys a synchronous standby replica in another Availability Zone. If primary fails, AWS auto-fails over in ~60 seconds — zero data loss.
  • DB Subnet Group — Tells RDS which subnets (across AZs) it can deploy in. Always use private subnets for databases.
  • Secrets Manager — Encrypted key-value store for credentials. Integrates natively with RDS for automatic password rotation.
  • Parameter Group — Database engine settings (max connections, query cache size, etc.). Like a config file for MySQL.

Retrieve Credentials in Your Application

Your Python app never stores the password — it fetches it at runtime:

import boto3      # AWS SDK
import json       # Parse the secret JSON string
import pymysql    # MySQL connector for Python

def get_db_connection():
    # Create Secrets Manager client in ap-south-1
    client = boto3.client('secretsmanager', region_name='ap-south-1')

    # Fetch the secret — get_secret_value makes an HTTPS API call
    # The secret value is returned as an encrypted string, AWS decrypts it
    secret_response = client.get_secret_value(
        SecretId='prod/mysql/credentials'
    )

    # 'SecretString' contains the JSON we stored — parse it to a dict
    creds = json.loads(secret_response['SecretString'])

    # Connect to MySQL using the fetched credentials
    # pymysql.connect() opens a TCP connection to the RDS instance
    conn = pymysql.connect(
        host=creds['host'],         # RDS endpoint hostname
        user=creds['username'],     # 'admin'
        password=creds['password'], # Fetched from Secrets Manager — never hardcoded!
        database=creds['dbname'],   # 'appdb'
        port=creds['port'],         # 3306 (MySQL default port)
        cursorclass=pymysql.cursors.DictCursor  # Returns rows as dicts
    )

    return conn

# Usage:
conn = get_db_connection()
with conn.cursor() as cursor:
    cursor.execute("SELECT * FROM users LIMIT 10")
    rows = cursor.fetchall()  # Returns list of dicts
    print(rows)

Every git push automatically builds, tests, and deploys your application to production — a fully automated DevOps pipeline.

Dev team at TechCo deploys manually: developer finishes code, SSHs into server, runs git pull, restarts the service. It takes 20 minutes. They do it wrong sometimes. Once they deployed the wrong branch. Production was down for 3 hours.

With AWS CodePipeline, every merge to the main branch automatically triggers: CodeBuild compiles and tests the code, then CodeDeploy pushes it to EC2 instances with zero-downtime rolling deployments. The pipeline is visual — you can see exactly where a deployment is and what failed.

💡 Core Concepts

  • CodePipeline — Orchestrates the entire CI/CD flow. Connects stages: Source → Build → Test → Deploy. Visualises progress.
  • CodeBuild — Managed build server. Runs your buildspec.yml — install dependencies, run tests, compile code, package artifacts.
  • CodeDeploy — Deploys code to EC2, Lambda, or ECS. Supports rolling, blue/green, and canary deployments.
  • buildspec.yml — YAML file in your repo root. Tells CodeBuild exactly what commands to run at each build phase.
  • appspec.yml — YAML file for CodeDeploy. Tells it where to put files and what scripts to run before/after deployment.

Custom VPC with Public & Private Subnets

Build a production-grade AWS network: web servers in public subnets, databases in private subnets, internet access via NAT Gateway — the foundation of every real AWS architecture.

VPCSubnetsInternet GatewayNAT GatewayRoute TablesNACLs

Imagine your office building. The reception area (public subnet) is open to visitors. The server room (private subnet) is locked — only employees with key cards can enter. The building has a main entrance (Internet Gateway) — anyone can come in through reception. But the server room connects to the outside world through a secure proxy (NAT Gateway) — servers can initiate internet connections (for OS updates, API calls) but outsiders can't reach them directly.

This is exactly how a production VPC works. Your database servers are in private subnets — they have no route from the internet. Only your web servers (in public subnets) can talk to them. This is called a multi-tier architecture and it's the industry standard.

IAM Roles, Policies & Security Best Practices

Master AWS Identity and Access Management — the backbone of all AWS security. Build least-privilege roles, federate identities, and prevent misconfigurations.

IAMRolesPoliciesMFASCPsAWS SSO

A startup's AWS bill jumped from $500 to $87,000 in one month. A developer accidentally leaked their AWS root access keys on GitHub. A cryptocurrency miner found the keys and spun up 500 GPU instances to mine Bitcoin — all on the startup's bill.

IAM (Identity and Access Management) is AWS's security foundation. With proper IAM: no one uses root keys (ever), every service gets only the minimum permissions it needs (least privilege), all human access goes through SSO with MFA, and Service Control Policies prevent anyone from bypassing security rules — even admins.

💡 Core Concepts

  • IAM User — A person or app with permanent credentials. Avoid for applications; use roles instead. Humans should use SSO.
  • IAM Role — Temporary credentials assumed by services (EC2, Lambda) or users. Expires after hours, not years. No stored keys.
  • IAM Policy — JSON document defining what actions are allowed/denied on which resources. Attached to users, groups, or roles.
  • Least Privilege — Grant only the minimum permissions needed. Start with zero, add only what's required.
  • Service Control Policy (SCP) — Organization-level guardrails. Even if an IAM policy allows it, an SCP can block it. Prevents regions, services, or actions org-wide.
  • MFA (Multi-Factor Authentication) — Require a second factor (authenticator app) for all human logins. Stops 99.9% of account compromise attacks.
lambda-dynamodb-policy.json JSON — IAM Policy 
{
  // Version: always "2012-10-17" — this is the current policy language version
  "Version": "2012-10-17",
  "Statement": [
    {
      // Sid: Statement ID — a label for this permission block (optional but recommended)
      "Sid": "AllowDynamoDBReadWriteTodosTable",

      // Effect: "Allow" grants access; "Deny" blocks it (Deny always wins)
      "Effect": "Allow",

      // Action: what API calls are permitted
      // Only the 4 actions our Lambda actually needs — not dynamodb:*
      "Action": [
        "dynamodb:GetItem",     // Read one item by primary key
        "dynamodb:PutItem",     // Insert or replace an item
        "dynamodb:DeleteItem",  // Delete one item
        "dynamodb:Scan"         // Read all items (our GET /todos handler)
      ],

      // Resource: WHICH resource these actions apply to
      // Pinned to the EXACT Todos table ARN — not all DynamoDB tables!
      "Resource": "arn:aws:dynamodb:ap-south-1:ACCOUNT:table/Todos"
    },
    {
      // Second statement: allow CloudWatch Logs (Lambda needs to write logs)
      "Sid": "AllowCloudWatchLogs",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      // * here = all log groups for this Lambda (acceptable for logs)
      "Resource": "arn:aws:logs:ap-south-1:ACCOUNT:log-group:/aws/lambda/*"
    }
  ]
}

OmniShop's checkout flow: Order Service calls Payment Service (sync HTTP call). If Payment Service is slow, Order Service waits. If Payment Service crashes, the entire checkout fails. Both services are tightly coupled — a problem in one cascades to the other.

payment_processor.py PYTHON — SQS Triggered Lambda 
import json
import boto3
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    """
    SQS sends events in BATCHES — event['Records'] is a list of messages.
    Lambda Event Source Mapping can batch up to 10 SQS messages per invocation.
    This is more efficient than one Lambda invocation per message.
    """

    # Track which messages failed (for partial batch failures)
    batch_item_failures = []

    # Process EACH message in the batch
    for record in event['Records']:

        # record['body'] is the SQS message body (a string)
        # When SNS sends to SQS, it wraps the original message in another JSON layer
        sqs_body = json.loads(record['body'])

        # SNS wraps the original message in its own envelope
        # sqs_body['Message'] contains the actual order event JSON string
        order_event = json.loads(sqs_body['Message'])

        try:
            # Extract order details from the event
            order_id = order_event['orderId']
            amount   = order_event['amount']
            customer = order_event['customerId']

            logger.info(f"Processing payment: order={order_id}, amount=₹{amount}")

            # Process payment (call payment gateway, update DB, etc.)
            process_payment(order_id, amount, customer)

            logger.info(f"Payment succeeded for order {order_id}")

        except Exception as e:
            logger.error(f"Payment FAILED for order {order_id}: {e}")

            # Report this message as failed — it won't be deleted from SQS
            # SQS will retry it (up to maxReceiveCount=3, then → DLQ)
            batch_item_failures.append({
                "itemIdentifier": record['messageId']
            })

    # Return failed message IDs — only these get retried
    # Successfully processed messages are auto-deleted from the queue
    return {"batchItemFailures": batch_item_failures}

💡 Core Concepts

  • GuardDuty — ML-based threat detection. Analyses CloudTrail, VPC Flow Logs, DNS. Detects compromised credentials, crypto mining, data exfiltration attempts.
  • AWS Config — Tracks configuration changes to all AWS resources. Evaluates against Config Rules. Creates a compliance timeline.
  • Config Rules — Checks like "all S3 buckets must have encryption", "no security groups allow 0.0.0.0/0 on port 22". Managed or custom Lambda-based rules.
  • CloudTrail — Logs every AWS API call: who did what, when, from where. The audit trail for forensic investigation.
  • Security Hub — Aggregates findings from GuardDuty, Config, Inspector, Macie into a single dashboard. Prioritises by severity.
  • Auto-Remediation — Config Rules can trigger SSM Automation to fix violations automatically (e.g., close open SSH port, enable encryption).

2

Enable AWS Config with Managed Rules

# Enable AWS Config recording aws configservice put-configuration-recorder \ --configuration-recorder '{ "name": "default", "roleARN": "arn:aws:iam::ACCOUNT:role/AWSServiceRoleForConfig", "recordingGroup": { "allSupported": true, "includeGlobalResourceTypes": true } }' # Enable S3 delivery for Config snapshots aws configservice put-delivery-channel \ --delivery-channel '{ "name": "default", "s3BucketName": "fintech-config-snapshots", "configSnapshotDeliveryProperties": { "deliveryFrequency": "TwentyFour_Hours" } }' aws configservice start-configuration-recorder --configuration-recorder-name default # Add managed rule: no unrestricted SSH access aws configservice put-config-rule --config-rule '{ "ConfigRuleName": "restricted-ssh", "Source": { "Owner": "AWS", "SourceIdentifier": "INCOMING_SSH_DISABLED" } }' # Add managed rule: RDS must be encrypted aws configservice put-config-rule --config-rule '{ "ConfigRuleName": "rds-storage-encrypted", "Source": { "Owner": "AWS", "SourceIdentifier": "RDS_STORAGE_ENCRYPTED" } }' # Add managed rule: S3 buckets must have encryption aws configservice put-config-rule --config-rule '{ "ConfigRuleName": "s3-bucket-server-side-encryption-enabled", "Source": { "Owner": "AWS", "SourceIdentifier": "S3_BUCKET_SERVER_SIDE_ENCRYPTION_ENABLED" } }'

💡 Core Concepts

  • Cost Explorer — Visualise and analyse your AWS costs. Filter by service, region, account, tag. Identify cost anomalies and trends.
  • AWS Budgets — Set spending limits with email/SNS alerts when forecasted spend will exceed budget. Prevent bill shock.
  • Savings Plans — Commit to $X/hour of compute usage for 1 or 3 years → get 30-72% discount vs On-Demand. More flexible than Reserved Instances.
  • Compute Optimizer — ML analysis of your actual EC2/Lambda/ECS usage → recommends rightsizing (smaller or more efficient instance types).
  • S3 Intelligent-Tiering — Automatically moves objects between S3 tiers based on access patterns. Objects not accessed in 30 days move to Infrequent Access (saves 40%).
  • EC2 Spot Instances — Unused AWS capacity at 60-90% discount. For fault-tolerant, stateless workloads (batch processing, CI/CD workers).

This is step 0 of FinOps. Without tags, you can only see total costs. With tags, you know EXACTLY which team/project/environment is spending what — and who to talk to about reducing it.
