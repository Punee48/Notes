Concept
CONCEPT

What Is RHAAP/AAP, Really?

What is it

Red Hat Ansible Automation Platform (RHAAP, formerly known as Ansible Tower / AWX upstream, and referred to by Red Hat as AAP from version 2 onward) is a control plane that sits on top of Ansible. Ansible itself is just a Python tool that reads YAML and connects to hosts over SSH or WinRM. RHAAP is the enterprise layer around that tool: a web UI, a REST API, a database, RBAC, scheduling, credential storage, logging, and a job execution engine.

Think of it this way: Ansible is the engine. RHAAP is the car — the dashboard, the locked glovebox for credentials, the seatbelt (RBAC) that stops the wrong person from driving it into production, and the black-box recorder (audit log) that tells you what happened after an incident.

Why does it exist

Raw Ansible run from a laptop or jump box has real problems at bank scale:

Problem with raw AnsibleWhat RHAAP adds
Anyone with SSH keys can run anything against anythingRBAC: Organizations, Teams, Roles scoped to specific objects
Secrets sit in plaintext files, vault passwords shared over SlackEncrypted credential store; secrets injected at execution time and never shown to the user
"It worked on my laptop" — different Ansible/Python/collection versions per engineerExecution Environments: versioned, container-based, identical every run
No record of who ran what, when, against which hostsEvery job is logged: user, time, inventory, credential used (not the secret itself), full output
No self-service — engineers wait on the one person who "knows the script"Job Templates + Surveys let non-experts safely launch pre-approved automation

What problem does it solve, concretely, for ABC Bank

It turns "40 engineers running ad hoc scripts" into "a governed platform where the Linux team can restart a service, the Windows team can install a patch, and the Fraud Detection team can roll out a config change — each only within their own lane, each fully logged, each using the exact same tested automation content every time."

Where is it used

Typical footprint: OS patching and configuration management, application deployment orchestration, network device configuration, cloud provisioning, compliance remediation ("bring these 4,000 servers back into compliance with this CIS benchmark"), and incident response runbooks ("restart this service on this exact host set, with an approval gate, with a Slack notification").

Common mistakes beginners make

  • ✗Treating RHAAP as "just a UI for Ansible" — it's an execution and governance platform; the UI is one of three ways to drive it
  • ✗Giving every new user Administrator so "it's easier" — this is the single most common audit finding
  • ✗Skipping Execution Environments early on and letting jobs run against whatever collections happen to be installed on the control node
▲

Production consideration: RHAAP does not replace writing good Ansible. A badly-written, non-idempotent playbook is exactly as dangerous inside RHAAP as outside it — RHAAP controls who can run it and how it's logged, not whether the playbook itself is correct.

Fig 1.1 — Control plane decides WHAT runs and WHO is allowed to run it. Execution plane actually runs it, isolated inside a container. Nothing touches target systems except the execution plane.

The pieces, one at a time

🔷 Automation Controller

The brain. Hosts the web UI and REST API, stores configuration and job history in PostgreSQL, enforces RBAC, and decides which execution node should run a given job.

🔷 Execution Node / Plane

Where jobs actually run. Uses Ansible Runner to launch the playbook inside a container (the Execution Environment), then streams output back to the Controller in real time over the Receptor mesh network.

🔷 Execution Environment (EE)

A container image with Ansible Core, Python, and the exact collections a job needs — already pinned. Covered at intro depth in this project, in full depth in Project 17.

🔷 Receptor

The overlay network / mesh that lets the Controller securely dispatch work to execution nodes, including nodes in different networks or data centers, without every node needing a direct route to the Controller's database.

Where your data lives

Configuration objects (Organizations, Teams, Job Templates, RBAC assignments, job history and logs) are stored in a PostgreSQL database that the Controller manages. You will never edit this database directly — every change goes through the API, the UI, or Ansible-against-the-API, which is exactly why RHAAP-as-code (Project 22) works: the API is the single source of truth interface, regardless of which of the three methods you used to call it.

◆

The idea to hold onto for this whole course: UI, API, and Ansible (awx.awx collection) are three doors into the same house. The UI calls the same REST API you'll call directly. The awx.awx Ansible modules also call that same REST API. Learning the API well makes the other two easier, not harder.

Core Object 1 of 9

Organizations

WHAT

The top-level container in RHAAP. Every Project, Inventory, Credential, Team, and Job Template belongs to exactly one Organization (with a small set of exceptions for shared/global objects on some setups). It is the outermost security boundary.

WHY

Large banks run many business units through one RHAAP instance — Linux Automation, Windows Automation, Network Automation, Cloud Automation. Organizations let you isolate them so that a Network team admin cannot accidentally (or maliciously) see a Cloud team's credentials, even though they share the same platform.

WHERE

Created once per business unit / division, rarely per project. ABC Bank will have roughly one Organization per major automation domain.

DEPENDENCIES

None — it's the root. Everything else depends on it.

SECURITY

Organization Admin is a powerful role — it can manage everything inside that Organization, including creating Teams and assigning RBAC. Hand it out as carefully as you'd hand out root.

COMMON MISTAKES

  • Creating one Organization per project instead of per business domain — this explodes admin overhead and defeats the purpose of shared platform governance
  • Making every engineer an Organization Admin instead of scoping them to specific Teams and objects

ANSIBLE Automate RHAAP itself with awx.awx

org.yml
---
- name: Configure ABC Bank RHAAP organization
  hosts: localhost
  connection: local
  gather_facts: false

  vars:
    controller_host: "https://rhaap.abcbank.internal"
    controller_oauthtoken: "{{ lookup('env', 'RHAAP_TOKEN') }}"

  tasks:
    - name: Ensure Banking Automation organization exists
      awx.awx.organization:
        name: "Banking Automation"
        description: "Primary organization for ABC Bank infrastructure automation."
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_oauthtoken }}"
        validate_certs: true
        state: present
Explain every line of this playbook

hosts: localhost + connection: local — this playbook doesn't SSH anywhere. It's calling the RHAAP REST API from wherever ansible-playbook runs, so the "target" is the local control machine, not a remote server.

controller_oauthtoken pulled from an environment variable via lookup('env', ...) — never hard-code the token in the YAML file, since that file goes into Git.

awx.awx.organization is the module (works identically against upstream AWX and RHAAP/AAP Controller). state: present means "create it if missing, update it if the description changed, do nothing if it already matches" — this is what makes the playbook idempotent: running it 50 times produces the same end state as running it once.

validate_certs: true — in production, always verify TLS. Only ever set this false in an isolated lab, and even then, prefer trusting the internal CA properly.

Users

A User is an individual account. Users can be created locally in RHAAP or, far more commonly in a bank, synced in from an enterprise identity provider (LDAP/AD, SAML, OIDC) — external auth is covered later; today we create local users to keep focus on RBAC mechanics.

Why no_log: true here?

Because the task's variables include a password. no_log: true suppresses the task's input/output from appearing in job output and logs. Without it, even a templated password lookup could be echoed into log text visible to anyone who can view the job. This is a habit to build now — you'll need it constantly once you reach Custom Credential Types in Project 19.

Core Object 4 of 9 — Read This One Twice

RBAC — Role-Based Access Control

RBAC is the single most audited part of RHAAP in a bank. Get comfortable with one idea before anything else: roles are granted on specific objects, not globally. "Amit is an Admin" means nothing in RHAAP. "Amit is an Admin of the Project named linux-ops-automation" is a real, checkable statement.

The roles you'll use constantly

RoleApplies toGrants
AdminAny objectFull control of that object, including deleting it and changing its permissions
ExecuteJob TemplateCan launch the template, cannot edit it
UseInventory / Credential / ProjectCan reference the object inside a Job Template you're building, without seeing its secrets or editing it
ReadAny objectCan view it in the UI/API, cannot change or launch anything
UpdateProjectCan trigger a Git sync

ABC Bank's Project 1 RBAC design

Requirement, from Priya

"Linux Operators should be able to launch the restart-service job whenever they need to. They should not be able to edit the Job Template, and they must never be able to see the SSH private key we use to connect to those servers."

WhoObjectRole grantedWhy
Team: Linux OperationsJob Template "Linux — Restart Service"ExecuteSelf-service launch, no edit rights
Team: Linux OperationsInventory "Linux Servers"ReadCan see which hosts exist, cannot modify the inventory
a.verma (team lead)Project "linux-ops-automation"UpdateCan trigger a manual Git resync when the team pushes new playbooks
Team: Linux OperationsCredential "Linux SSH Key"noneThe Job Template references the credential internally — the team never needs direct access to it
■

This is the control an auditor tests first. A team can launch a job that uses a credential without ever being granted access to the credential object itself. That's the entire point of Job-Template-level credential attachment — the secret never has to be shared with the people running the automation.

Why wait: true?

Creating a Project triggers an initial Git sync as a background job. wait: true tells Ansible to block until that sync finishes and fail the play if the sync fails — instead of reporting "project created" while the sync is still silently running or has already failed in the background.

Execution Environments

Full EE development (building custom images with ansible-builder) is Project 17. Today you only need to understand what one is and how to attach an existing one to a Job Template.

WHAT

An Execution Environment is a container image bundling: Ansible Core, Python, the specific Ansible Collections a job needs (e.g. ansible.posix, community.general), and any system libraries those collections depend on.

WHY

Before EEs, RHAAP (as "Ansible Tower") ran jobs using whatever Python/collections happened to be installed on the control node — the classic "works on the control node, fails on the new one" problem. EEs make every job run inside an identical, versioned, portable container, regardless of which execution node picks it up.

WHERE

Referenced at the Organization level (a sensible default for every job in that org), the Project level, or overridden per Job Template.

The Playbook Itself

Everything above is scaffolding. Here's what actually executes: playbooks/restart-service.yml, living in the linux-ops-automation Git repo.

playbooks/restart-service.yml
---
- name: Restart a named service on Linux Operations hosts
  hosts: rhel_web
  become: true
  gather_facts: true

  vars:
    service_name: "httpd"   # replaced by a Survey variable from Project 8 onward

  tasks:
    - name: Ensure the target service is currently known to systemd
      ansible.builtin.service_facts:

    - name: Fail fast if the service does not exist on this host
      ansible.builtin.fail:
        msg: "Service {{ service_name }} not found on {{ inventory_hostname }}"
      when: (service_name + '.service') not in ansible_facts.services

    - name: Restart the service
      ansible.builtin.systemd:
        name: "{{ service_name }}"
        state: restarted
        enabled: true

    - name: Confirm the service is active after restart
      ansible.builtin.systemd:
        name: "{{ service_name }}"
      register: post_restart

    - name: Report final state
      ansible.builtin.debug:
        msg: "{{ service_name }} on {{ inventory_hostname }} is now {{ post_restart.status.ActiveState }}"
Explain every task, line by line

hosts: rhel_web — targets the group you built in the Inventory section, not individual hostnames. This is why group design matters: change the group's membership once, and every Job Template using it updates automatically.

become: true — uses the privilege escalation (sudo) configured on the attached Machine credential; the playbook itself never states a sudo password.

service_facts — gathers a list of all services systemd knows about into ansible_facts.services, before attempting anything destructive.

The fail task with a when guard — this is defensive playbook design: if service_name is misspelled or doesn't exist on that host, stop immediately with a clear message instead of the systemd module throwing a less obvious runtime error.

ansible.builtin.systemd with state: restarted — idempotent in the sense that running it twice is safe (it will always restart, which is the intended behavior here — contrast with state: started, which would do nothing if already running).

register: post_restart captures the module's return data so the final debug task can report the confirmed post-restart status back into the job output — this is what an operator watching the job log actually wants to see, not just "changed: true."

◆

Note the hard-coded service_name default. That's intentional for Project 1 — Surveys (Project 8) are how service_name becomes something an operator chooses at launch time instead of something you edit in Git every time. Don't build the Survey yet; understand the plain variable first.

How The Job Template Actually Executes The Playbook

1. User (or Ansible via API) clicks Launch
        |
2. Controller checks RBAC: does this user have Execute on this Job Template?
        |  NO -> HTTP 403, nothing runs
        |  YES
        v
3. Controller resolves: Project revision + Inventory + Credential(s) + EE
        |
4. Controller dispatches the job to an available Execution Node via Receptor
        |
5. Execution Node pulls the Execution Environment container image (cached after first pull)
        |
6. Ansible Runner starts inside the container:
        - decrypts the Credential, injects it as an SSH identity (never written to disk in plaintext beyond the run)
        - loads the Inventory as a temporary in-memory/JSON inventory

   connection the UI/API is watching
        |
8. Job finishes: status + full stdout + host-by-host results are stored
        |
9. Container is torn down. No state persists in it between runs.

This is worth internalizing because every troubleshooting session in this course starts from this exact sequence — you'll always ask "which of these nine steps failed?" before looking at anything else.

Security Notes For Project 1

■

Credentials are opaque to job launchers. A user with Execute on a Job Template can use the attached credential but cannot view, export, or copy its secret value — by design, and it's exactly what lets you hand self-service automation to operators without handing them the keys.

▲

Service accounts, not personal accounts. svc_ansible — not any individual engineer's own SSH key — is what RHAAP authenticates as on target hosts. This keeps "who ran the automation" (the RHAAP user, in the audit log) separate from "what identity touched the server" (the service account) in a way that's actually auditable, and it means access doesn't break when an engineer leaves the team.

◆

Least privilege by default. Every RBAC grant in this project was the narrowest role that satisfies the actual requirement — Execute, not Admin; Read, not Update. Widening a grant later is a one-line change. Narrowing an over-broad grant after the fact means finding everyone who came to depend on the extra access.

Slack message from Sara Khan, 4:52 PM

"Hey — tried to launch 'Linux — Restart Service' against lnx-web-02 and it failed almost instantly. I don't have access to see the credential, just the error. Can you take a look?"

StageWhat you do
OBSERVEOpen the job in the UI/API. Status: failed, elapsed: 1.2s — too fast to have even attempted an SSH connection. That timing alone is a clue.
COLLECT EVIDENCERead the job output. You see: Permission denied, please try again. Permission denied (publickey,password).
ISOLATE FAILURE1.2 seconds + a publickey error means it never got past authentication — this isn't a playbook logic bug, it's an auth/connectivity problem.

FIXEdit the Credential → replace the SSH Private Key field with the new key material. (Recall: you can only replace it, never view the old one.)
VALIDATERe-launch the Job Template against a single host using Limit. Confirm successful status and correct output in the job log.
PREVENT RECURRENCEAdd the credential rotation step to the Linux team's key-rotation runbook: "update the RHAAP Machine Credential in the same change window." This becomes a governance checklist item revisited in Project 30.

Interview Preparation

RHAAP Administration

Q1. What's the difference between RHAAP and plain Ansible?
Ansible is the automation engine (YAML + SSH). RHAAP is the enterprise control plane on top of it — RBAC, credential management, scheduling, logging, a REST API, and containerized execution environments — that lets an organization run Ansible safely and auditable at scale.
Likely follow-up: "Could a bank get by without RHAAP?" — Yes at very small scale, but you lose auditability, RBAC, and self-service, which becomes untenable past a handful of engineers.
Q2. What is an Organization and why does it matter?
The top-level security boundary — every Project, Inventory, Credential, and Team belongs to exactly one Organization. It's how one RHAAP instance can safely host multiple business units without their objects and secrets bleeding into each other.
Follow-up: "Should you create a new Organization per project?" — No; that fragments governance. Organize by business domain.

RBAC

Q3. How would you let a team run a job without letting them see the credential it uses?
Grant the team Execute on the Job Template only — not any role on the Credential object itself. The Job Template references the Credential internally; RHAAP injects the secret at runtime without exposing it to the launcher.
Follow-up: "What if they also need to edit the survey?" — That requires broader Job Template rights; usually resolved by having template changes flow through Git + governed sync rather than granting edit access directly.
Q4. What's the difference between the Use role and the Read role on an Inventory?
Use lets you attach that Inventory while building a new Job Template you're creating; Read only lets you view it. A user might need Use on an Inventory but not need to browse its host list independently.

Architecture

Q5. Walk me through what happens between clicking "Launch" and a playbook actually running.
RBAC check → Controller resolves Project/Inventory/Credential/EE → job dispatched to an execution node via Receptor → Execution Environment container starts → Ansible Runner runs the playbook inside it, injecting the credential → output streams back live → job status and full output are persisted → container torn down.
Q6. Why do Execution Environments exist instead of just installing collections on the control node?
They guarantee every job runs against the exact same, versioned set of Ansible Core/Python/collections regardless of which execution node picks it up — eliminating "works here, fails there" drift and making automation reproducible.

REST API

Q7. How does the awx.awx Ansible collection relate to the REST API?
It's a thin, idempotent wrapper — every awx.awx module ultimately calls the same REST endpoints you'd hit directly with curl or Python. The module just adds "check current state, only change what's different" logic on top.

Scenario-Based

Q8. A job that worked yesterday fails today with a permission-denied error in under two seconds. What do you check first, and why that order?
Sub-two-second failure with an auth-shaped error means it never reached the target host, so check the Credential first (recent rotation?), then the target's authorized_keys/local account state, before ever looking at the playbook's task logic — the timing rules out a mid-playbook failure.

Manager Round

Q9. How would you justify RHAAP's licensing/operational cost to a manager skeptical of "just another tool"?
Frame it around risk reduction and time recovered: eliminated ungoverned access to production credentials, an audit trail that turns a 4-hour incident investigation into a 10-minute log lookup, and self-service that removes the platform team as a bottleneck for routine, pre-approved changes.
