What Private Automation Hub Is

Private Automation Hub is a self-hosted content repository serving two related purposes: it's a Galaxy-compatible collection registry (fulfilling the same role as public Ansible Galaxy, but internally hosted and governed), and it's a container registry for Execution Environment images — the same role Project 17's registry.abcbank.internal played, ideally consolidated into PAH rather than kept as a separate system.

The Content Supply Chain

StageWhat happensWho's responsible
Public sourceThe collection exists on public Galaxy, maintained by its upstream authorsUpstream community — outside ABC Bank's control
Sync listPAH pulls specifically named, specifically versioned collections into a staging repository — nothing unlisted, nothing unpinnedPlatform team, via the sync list configuration (built below)
ReviewA human (or, eventually, an automated scan per Project 43's CI/CD) confirms the pulled version is what was expected and free of known vulnerabilitiesPlatform team
PromotionThe reviewed collection version moves from staging to the approved/published repositoryPlatform team, a deliberate action
ConsumptionEE builds and (where configured) ad hoc ansible-galaxy install commands resolve only against the approved repositoryEvery engineer, enforced by the Organization's Galaxy Credential configuration
Concept

Sync Lists vs. Approval Repos

▲

A sync list is not the same as approval. Syncing a collection into PAH's staging repository just means "we've pulled a copy" — it doesn't mean anyone has looked at it. Treating "it's in PAH" as equivalent to "it's approved" would defeat the entire governance purpose of this project. The explicit promotion step from staging to the published/approved repository is where actual review happens.

Authenticating to PAH

UI

  1. In Private Automation Hub, generate an API token for a dedicated service account (never a personal account) with permissions scoped to sync and publish collections.
  2. In RHAAP: Automation Execution → Credentials → Create Credential.
  3. Name: Private Automation Hub, Credential Type: Ansible Galaxy/Automation Hub API Token.
  4. Galaxy Server URL: https://pah.abcbank.internal/api/galaxy/content/published/ — the published, approved repository endpoint, not the staging one.
  5. API Token: paste the service account's token.
  6. Save.

ANSIBLE

pah_credential.yml
- name: Create the Private Automation Hub Galaxy credential
  awx.awx.credential:
    name: "Private Automation Hub"
    organization: "Banking Automation"
    credential_type: "Ansible Galaxy/Automation Hub API Token"
    inputs:
      url: "https://pah.abcbank.internal/api/galaxy/content/published/"
      auth_url: "https://pah.abcbank.internal/api/galaxy/pulp/api/v3/"
      token: "{{ lookup('env', 'PAH_API_TOKEN') }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true

Building the Sync List

The three collections Project 17 pulled directly from public Galaxy now need to flow through PAH instead. Define exactly what's synced — nothing broader.

pah_sync_list.yml (documentation of the PAH-side configuration)
---
# This file documents the sync list configured directly in Private
# Automation Hub's UI/API (PAH's own remote/repository management is
# a separate system from RHAAP's controller API — this file exists
# so the sync list itself is reviewable via Git, per this course's
# governance model, even though applying it happens through PAH's
# own interface).

sync_list:
  remote_source: "https://galaxy.ansible.com"
  requested_collections:
    - name: ansible.posix
      version: "1.5.4"
    - name: community.general
      version: "8.2.0"
    - name: awx.awx
      version: "23.7.0"

# Approval note: each entry above requires a platform-team review
# and explicit promotion from PAH's staging repository to its
# published/approved repository before any EE build or Job
# Template can consume it. See CHANGELOG.md for promotion history.
◆

Notice the versions match Project 17's requirements.yml exactly. This isn't a coincidence — the sync list's entire purpose is to make sure PAH actually has the specific versions the EE definition already expects, reviewed and promoted, before that EE is ever rebuilt against PAH as its source.

Pointing the Organization at PAH — Closing the Project 2 Gap

ANSIBLE

org_galaxy_credential.yml
- name: Set the Organization's default Galaxy credential to Private Automation Hub
  awx.awx.organization:
    name: "Banking Automation"
    galaxy_credentials:
      - "Private Automation Hub"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
◆

This single task is the direct answer to Project 2's deferred setting. Every Project sync within Banking Automation that resolves Galaxy requirements now goes through PAH's approved repository by default — not because every engineer remembered to change a setting, but because the Organization-level default now enforces it.

Rebuilding the EE Through PAH

execution-environment.yml (updated — Project 17's EE, v1.1.0)
---
version: 3

images:
  base_image:
    name: registry.access.redhat.com/ubi9/ubi-minimal:latest

dependencies:
  galaxy: requirements.yml
  python: requirements.txt
  system: bindep.txt

additional_build_steps:
  prepend_base:
    - RUN microdnf update -y
  append_final:
    - LABEL org.abcbank.team="linux-operations"
    - LABEL org.abcbank.ee-version="1.1.0"
    - LABEL org.abcbank.collection-source="pah.abcbank.internal"
Build command — now resolving via PAH
# ansible-builder resolves collections using whatever Galaxy server(s)
# are configured in the build environment's own ansible.cfg — point
# it at PAH's published repository, not public Galaxy, before building

export ANSIBLE_GALAXY_SERVER_LIST=pah
export ANSIBLE_GALAXY_SERVER_PAH_URL="https://pah.abcbank.internal/api/galaxy/content/published/"
export ANSIBLE_GALAXY_SERVER_PAH_TOKEN="$PAH_API_TOKEN"

ansible-builder build \
  --tag linux-ops-ee:1.1.0 \
  --container-runtime podman \
  -v3
▲

The ansible.cfg baked into the EE build environment (not necessarily the same as the one inside the final image) controls where ansible-builder resolves collections from at build time. This is easy to get wrong — a build machine with a leftover default pointing at public Galaxy will silently succeed while quietly bypassing PAH entirely, which is exactly this project's incident below.

Security Notes For Project 18

■

The staging-to-published promotion step is the actual security control — protect it accordingly. Whoever can promote content in PAH effectively decides what's trusted platform-wide. Scope that permission as carefully as any RBAC grant from Project 3 — it should not be broadly held.

▲

A sync list pulling an unpinned version range is a governance gap disguised as convenience. Always sync specific, named versions — never "latest available" — or a future upstream release could enter staging (and, if promotion isn't carefully re-reviewed, production) without anyone having deliberately chosen it.

◆

PAH's own API token is a real Credential and deserves the same rotation discipline as Project 6's overlap-window rotation strategy — plan for it, don't treat it as a "set once and forget" secret.

Run It — Production Incident

Incident: The EE Build "Succeeded" But Still Used Public Galaxy

Security team, during a routine air-gap readiness review

"We tried building the Linux Ops EE with no internet access, as a test of air-gap readiness. It failed — but when we checked network logs from a normal, non-air-gapped build, we saw outbound traffic to galaxy.ansible.com even after this project's PAH cutover. Something's still reaching the public internet."

StageWhat you do
OBSERVEBuilds on a normal, internet-connected machine succeeded and produced a working image — masking the fact that public Galaxy was still being contacted underneath.
COLLECT EVIDENCECheck the build environment's effective Galaxy server configuration at the moment of the build — not just the environment variables you intended to set, but what ansible-builder actually resolved.
ISOLATE FAILUREYou find a pre-existing ansible.cfg in the build machine's home directory (left over from before this project, used for unrelated ad hoc Galaxy installs) that explicitly hard-coded the public Galaxy server list — and per Ansible's configuration precedence, this local file was taking priority over the environment variables set in this project's build command.
CHECK DEPENDENCIESConfirm this same stale config exists on every machine engineers use to build this EE, not just one — the risk is systemic, not a single machine's misconfiguration.
IDENTIFY ROOT CAUSEEnvironment-variable-based configuration is not the highest-precedence source for this specific setting on affected machines — a leftover local config file silently won, and the build's apparent success gave no indication anything was wrong.
FIXRemove or correct the stale local ansible.cfg on every build machine, and — more durably — move the PAH server configuration into the EE repository's own committed ansible.cfg (already present in the repo structure) rather than relying on each engineer's local environment variables or personal config files.
VALIDATERe-run the air-gap test: disconnect the build machine from the internet entirely and confirm the build still succeeds using only PAH.
PREVENT RECURRENCEAdd an air-gap build test as a required step before any EE version is considered production-ready, and add a check to the governance checklist (Project 9) confirming the EE repository's own ansible.cfg — not engineer-local configuration — is what actually governs collection resolution.
◆

The teaching point: "the build succeeded" and "the build only used approved content" are two different claims, and only the second one actually satisfies Security's original question. A working image is not proof of a governed supply chain — proving that requires deliberately testing the failure mode (no public internet access) directly, not just trusting a green build.

Interview Preparation

Q1. What two kinds of content does Private Automation Hub typically manage?
Ansible Collections (as a Galaxy-compatible registry) and container images (as a registry for Execution Environments) — consolidating both governed content types under one internally hosted, access-controlled system.
Q2. Why is a sync list not the same thing as content approval?
Syncing just pulls a copy of specified content into a staging repository — it doesn't imply anyone has reviewed it. The actual governance control is the deliberate promotion step from staging to the published/approved repository, which is where a human (or automated check) confirms the content is trustworthy before anything can consume it.
Q3. How would you prove an Execution Environment build genuinely doesn't depend on public internet access?
Actually attempt the build with no internet connectivity available and confirm it still succeeds — a successful build on an internet-connected machine doesn't prove air-gap readiness, since it can't distinguish "used only approved internal sources" from "silently also reached the public internet."
Q4. Where should an EE's Galaxy server configuration live to avoid engineer-to-engineer inconsistency?
Committed directly in the EE's own repository (e.g. a version-controlled ansible.cfg) rather than relying on each engineer's local environment variables or personal configuration files, which can silently diverge or be overridden by a stale, pre-existing local config.
Q5. A build machine's environment variables specify one Galaxy server, but the build still contacts a different one. What would you check?
Ansible configuration precedence — a local ansible.cfg file can take priority over environment variables depending on where it sits in the resolution order, so check for any pre-existing config file on the build machine that might be silently overriding the intended environment-variable configuration.

◆

Lab vs. Enterprise Production: a real Private Automation Hub instance requires either a licensed RHAAP/AAP deployment with PAH included or a compatible open-source Galaxy-protocol server for lab purposes — this is one of the few pieces of this course genuinely difficult to fully replicate without enterprise-grade infrastructure. Where unavailable, focus on the sync-list/promotion/EE-cutover reasoning conceptually.

  1. If you have access to a lab PAH instance (or a compatible Galaxy-protocol server), configure a sync list for the same three collections used in Project 17's EE.
  2. Create the corresponding RHAAP Credential and set it as your lab Organization's default Galaxy credential.
  3. Rebuild your Project 17 EE with the build environment explicitly pointed at your PAH/lab server instead of public Galaxy.
  4. Test the build with network access to public Galaxy deliberately blocked (e.g. via a firewall rule or /etc/hosts entry), and confirm it still succeeds using only your internal source.
  5. Reproduce the incident: leave a stale, conflicting ansible.cfg in your build environment's home directory, rebuild, and use network monitoring (even simple, e.g. checking DNS resolution logs) to confirm whether public Galaxy was contacted despite your intended configuration.
