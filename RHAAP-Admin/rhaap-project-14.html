Concept

Retry vs. Rollback vs. Escalation

Three genuinely different responses to failure, each appropriate to a different situation. Conflating them — retrying forever, or escalating for a one-off blip — is its own kind of failure.

StrategyAppropriate forWhere it lives
RetryTransient, self-resolving issues — a brief SSH connection blip, a momentary resource contentionInside the playbook itself, at the task level (Ansible's until/retries/delay)
RollbackA real failure where the safest response is attempting to restore a known-good stateThe workflow graph — a Failure-linked node (Project 12)
EscalationRollback itself failing, or any situation where automation has exhausted its own remediation options and a human must actThe workflow graph — a Failure-linked node attached to the Rollback node specifically (today's addition)
◆

This directly answers both of Priya's and Amit's questions in one framework. Amit's transient SSH blips belong at the retry layer, inside the playbook — they should never even reach the workflow's Failure branch if a second attempt would have succeeded. Priya's "manual intervention required" message belongs at the escalation layer — a distinct, loud, workflow-level response to Rollback's own failure, not a debug line lost in job output.

Concept

Task-Level Retry Logic — With a Hard Ceiling

Ansible's until/retries/delay re-runs a task until a condition is met or a retry limit is reached. This is fundamentally different from the workflow-level Failure branching in Project 12 — it happens entirely within a single task, invisible to the workflow graph unless every retry is exhausted.

■

Every retry loop must have a hard ceiling. Retrying indefinitely turns a real, non-transient failure into a job that appears "still running" for far longer than it should — precisely the kind of hang Project 7's Timeout setting exists to catch, but a retry loop without its own bound can still waste significant time before that outer Timeout finally intervenes.

Build

Adding Retry to the Restart Task

playbooks/restart-service.yml (updated)
---
- name: Restart a named service on Linux Operations hosts
  hosts: rhel_web
  become: true
  gather_facts: true

  vars:
    service_name: "httpd"

  tasks:
    - name: Ensure the target service is currently known to systemd
      ansible.builtin.service_facts:

    - name: Fail fast if the service does not exist on this host
      ansible.builtin.fail:
        msg: "Service {{ service_name }} not found on {{ inventory_hostname }}"
      when: (service_name + '.service') not in ansible_facts.services

    - name: Restart the service, retrying briefly for transient SSH/connection blips
      ansible.builtin.systemd:
        name: "{{ service_name }}"
        state: restarted
        enabled: true
      register: restart_result
      until: restart_result is succeeded
      retries: 2
      delay: 5
      # Total worst case: 3 attempts, ~10 seconds of delay between them —
      # bounded, and far shorter than the 300s Timeout on this Job Template
      # (Project 7), so a genuinely stuck task still surfaces promptly.

    - name: Confirm the service is active after restart
      ansible.builtin.systemd:
        name: "{{ service_name }}"
      register: post_restart

    - name: Report final state
      ansible.builtin.debug:
        msg: "{{ service_name }} on {{ inventory_hostname }} is now {{ post_restart.status.ActiveState }}"
Why retries: 2 and not something larger?

retries: 2 means the task attempts up to 3 total executions (the original attempt plus 2 retries) — enough to absorb Amit's described transient blip without meaningfully changing the job's total runtime, while still failing fast into the workflow's Rollback path for anything that isn't actually transient. A much larger retry count would start masking real failures behind a long, silent wait — exactly the risk called out in the Concept section above.

Critically: this retry logic lives entirely inside the Restart node's own playbook. From the workflow graph's perspective (Project 12's Success/Failure links), this task either ultimately succeeds (possibly after retries) or ultimately fails — the graph itself doesn't need to know retries happened at all.

Building the Escalation Node

playbooks/escalate-incident.yml
---
- name: Escalate — automated remediation has been exhausted
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    service_name: "httpd"
    change_ticket: "unknown"

  tasks:
    - name: Record a clear, structured escalation summary in job output
      ansible.builtin.debug:
        msg: >
          🔺 ESCALATION: automated rollback failed for service
          '{{ service_name }}' (change ticket {{ change_ticket }}).
          Manual intervention is now required. This job's Slack/email
          notification is the primary alert — do not assume anyone
          has already seen this.

    # A future enhancement (tracked for a later project once Custom
    # Credential Types exist — Project 19) would post directly to
    # ABC Bank's ITSM system here, using a Webhook credential to open
    # an incident ticket automatically rather than only notifying.

ANSIBLE — wrap it and wire it into the workflow

escalation_setup.yml
- name: Create the escalation job template
  awx.awx.job_template:
    name: "Linux — Escalate Incident"
    job_type: run
    inventory: "Linux Servers"
    project: "linux-ops-automation-prod"
    playbook: "playbooks/escalate-incident.yml"
    execution_environment: "Default execution environment"
    timeout: 60
    allow_simultaneous: true   # deliberately allows simultaneous escalations —
                                # never let a concurrency lock silently swallow
                                # a second, unrelated escalation
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Attach a high-urgency Slack notification to the escalation template
  awx.awx.job_template:
    name: "Linux — Escalate Incident"
    notification_templates_success:
      - "Linux Ops PAGE-WORTHY Slack Channel"
    notification_templates_error:
      - "Linux Ops PAGE-WORTHY Slack Channel"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Wire the Rollback node's Failure path to Escalate
  awx.awx.workflow_job_template_node:
    workflow_job_template: "Linux — Governed Service Restart"
    identifier: "rollback"
    failure_nodes: ["escalate"]
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Register the Escalate node itself
  awx.awx.workflow_job_template_node:
    workflow_job_template: "Linux — Governed Service Restart"
    identifier: "escalate"
    unified_job_template: "Linux — Escalate Incident"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
▲

Notice allow_simultaneous: true here, deliberately opposite to every other template in this course so far. An escalation path is exactly the wrong place to apply Project 7's usual "block concurrent runs" default — if two independent incidents both need to escalate around the same time, the second escalation must never be silently blocked by the first.

◆

A separate, distinctly-named "PAGE-WORTHY" Slack channel/notification template (versus the routine channel from Project 11) is a deliberate design choice — escalation alerts need to visually and audibly stand apart from routine Success/Failure chatter, or they risk being lost in the same noise Project 11 worked to prevent.

Security Notes For Project 14

■

Escalation notifications must never depend on the same channel/mechanism that might already be failing. If, hypothetically, the routine Slack integration itself were down, an escalation routed only to that same channel would be silently lost at exactly the worst moment. Consider a secondary channel or notification type for true escalations as the platform matures — noted here as a design tension worth revisiting, not fully solved in this project.

▲

A retry loop is still subject to RBAC and credential scoping exactly like a single attempt — it doesn't introduce a new privilege surface, but it does mean a misbehaving retry could attempt a state-changing action multiple times against production hosts. This is one more reason the retry ceiling must stay small and deliberate.

Run It — Production Incident

Incident: Retries Quietly Absorbed a Real Failure

Sara Khan

"The restart for sshd on lnx-web-04 took almost 40 seconds instead of the usual couple seconds. It did eventually succeed, but that felt slow."

StageWhat you do
OBSERVEThe job ultimately reported successful — no workflow-level failure, no Rollback triggered — but the elapsed time was abnormally long for this specific host.
COLLECT EVIDENCEJob output shows the Restart task actually succeeded only on its third attempt — both retries were consumed, meaning something genuinely intermittent (not a one-off blip) was happening specifically on lnx-web-04.
ISOLATE FAILUREBecause the task eventually succeeded within the retry ceiling, the workflow correctly proceeded down the Success path — the retry logic did exactly what it was designed to do. But "eventually succeeded" masked a real, worsening problem on that specific host from ever surfacing as a visible failure.
CHECK DEPENDENCIESInvestigate lnx-web-04 directly — you find intermittent network flakiness on that host's connection, likely a failing NIC or a flaky switch port, not something any application-layer retry can meaningfully fix.
IDENTIFY ROOT CAUSEThe retry logic is working as designed; the actual issue is that "succeeded after retries" currently looks identical, in reporting, to "succeeded on the first try" — there's no visibility into how many retries a job actually needed, which is itself useful signal being silently discarded.
FIXAdd a task that explicitly reports the retry count achieved (Ansible exposes this via the registered result's attempts field) into job output and, ideally, into the Success notification message from Project 11 — so "succeeded, but needed 3 attempts" is visibly different from a clean first-try success.
VALIDATERe-run against lnx-web-04 and confirm the retry count is now visible in both job output and the Slack notification.
PREVENT RECURRENCEFile a separate infrastructure ticket for lnx-web-04's underlying network issue — automation retry logic correctly kept the immediate task working, but it should never be treated as a substitute for actually investigating and fixing a host with a recurring, worsening problem.
◆

The broader lesson: retry logic that successfully recovers can hide a signal worth acting on. Designing for resilience (Project 14's whole point) doesn't mean designing away visibility — surface how much resilience was actually needed, don't just silently benefit from it.

Practice

Interview Preparation

Q1. When would you use task-level retry versus a workflow-level Rollback node?
Retry is for genuinely transient issues — a brief connection blip likely to succeed on a second attempt — and belongs inside the playbook itself with a small, hard-bounded retry count. Rollback is for real failures where automated remediation is worth attempting, and belongs as a Failure-linked node in the workflow graph, since it's a distinct, visible action rather than a silent internal retry.
Q2. Why must a retry loop always have a hard ceiling?
Without one, a genuinely broken (non-transient) failure could retry indefinitely, consuming time and potentially masking a real problem behind what looks like a still-running job, rather than failing promptly into whatever recovery path — rollback, escalation — actually addresses non-transient failures.
Q3. How would you design an escalation path so it doesn't get lost in routine notification noise?
Route it to a distinctly separate, clearly higher-urgency notification channel or template rather than reusing the same channel as routine Success/Failure alerts, and avoid applying routine concurrency restrictions (like blocking simultaneous runs) that could suppress a second, unrelated escalation.
Q4. A job succeeded, but took much longer than usual. What would make you suspect masked retry behavior, and how would you confirm it?
An abnormal elapsed time on an otherwise-quick task is the signal; confirming it means checking the job output for retry attempts on the specific task (Ansible's registered result exposes an attempt count), which reveals whether the task actually needed multiple tries to succeed rather than completing cleanly on the first attempt.
Q5. Why is "the job succeeded" not always sufficient information for a resilient automation platform?
Because it can hide how much effort was needed to reach that success — a task that barely scraped by after several retries reports identically to one that succeeded cleanly, unless the automation is explicitly designed to surface that difference, which itself is valuable signal for spotting a degrading host or service before it becomes an outright failure.
