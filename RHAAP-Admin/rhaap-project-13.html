Concept

The Approval Node

An Approval node is a distinct workflow node type — it isn't a Job Template at all. When a workflow's execution reaches an Approval node, the workflow pauses. Nothing downstream runs until someone with the Approve role on that Workflow Job Template explicitly approves or denies the request.

              Start
                |
                v
           Pre-Check
                |
          +-----+-----+
          |           |
       SUCCESS      FAILURE
          |           |
          v           v
   [ Approval Gate ]  (stop — unsafe to proceed)
          |
    +-----+-----+
    |           |
 APPROVED     DENIED
    |           |
    v           v
  Restart    (stop — change not authorized)
    |
    +-- ... same Success/Failure branches as Project 12 from here
Fig 13.2 — the workflow genuinely pauses at the gate. Nothing about "Approved" vs "Denied" is automatic; a specific human action is required either way.
Concept

Approval and Separation of Duties, Made Real

Recall Project 3's design: the Approve role must never be held by the same people who hold Developer-level Admin on the underlying automation. Today that stops being a paper design and becomes an actual RBAC boundary enforced by the platform.

RoleWhoCan doCannot do
DeveloperAmit Verma (per Project 3's persona matrix)Admin on Job Templates and the Workflow Job Template's structureHold Approve on the same workflow — deliberately excluded
ApproverChange Approvers team (built below) — e.g. a change-management lead outside Linux Operations entirelyApprove or Deny a paused workflow runEdit the workflow, its nodes, or any Job Template — Approvers only ever see the request and its context, per Project 3's Read-heavy Approver row
■

This is the concrete answer to the auditor's original question from Project 3. "Can the same person who writes automation also approve its production use?" — now, provably, no: the RBAC grants for Developer and Approver are held by disjoint sets of people, and the Approval node itself is the enforcement point, not just a policy statement.

Concept

Timeout Behavior — Directly Addressing Priya's Concern

An Approval node can have a Timeout. If nobody approves or denies within that window, the node times out — and, depending on configuration, this is typically treated as equivalent to a denial, halting the workflow. Priya's concern is legitimate: a well-intentioned timeout control can itself become an outage if approvers simply aren't notified in time.

SettingABC Bank's choiceWhy
Timeout4 hoursLong enough to reasonably expect a business-hours response, short enough that a request doesn't sit forgotten for days
Notification on approval-node-pendingWired to the Change Approvers' Slack channel (Project 11 pattern)Directly resolves Priya's "nobody was watching" concern — the approver is alerted the moment their action is needed, not left to notice on their own
▲

A Timeout without a matching notification is close to useless. The two must be designed together — this project treats them as a single deliverable, not two separate settings to configure independently.

Build

Adding the Approval Node

UI

  1. Open Linux — Governed Service Restart → Visualizer.
  2. Click the link between Pre-Check (Success) and Restart, and insert a new node in between — select node type Approval instead of a Job Template.
  3. Name: Approve Production Restart
  4. Timeout: 4 hours
  5. Description: include guidance for approvers — what to check before approving (e.g., "confirm the change ticket is valid and the maintenance window from Project 10 applies").
  6. Save. Re-link: Pre-Check (Success) → Approval Gate (Approved) → Restart; Approval Gate (Denied) → stop (no further link needed — a denial simply ends that branch).
  7. Grant the Change Approvers team the Approve role on this Workflow Job Template (built in the next section) — separate from, and in addition to, Linux Operations' Execute role.

ANSIBLE

governed_service_restart_workflow.yml (updated)
- name: Insert the Approval node between Pre-Check and Restart
  awx.awx.workflow_job_template_node:
    workflow_job_template: "Linux — Governed Service Restart"
    identifier: "approval_gate"
    unified_job_template: null
    all_parents_must_converge: false
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  # Note: exact module support for approval-type nodes varies by
  # awx.awx collection version — some versions expose a dedicated
  # `approval_node` parameter set (timeout, name, description)
  # rather than treating it as a template-less workflow node. Verify
  # against your installed collection version's module documentation
  # before relying on the exact task shape shown here.

- name: Re-wire Pre-Check to lead into the Approval gate on success
  awx.awx.workflow_job_template_node:
    workflow_job_template: "Linux — Governed Service Restart"
    identifier: "precheck"
    success_nodes: ["approval_gate"]
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Approval gate leads into Restart only when approved
  awx.awx.workflow_job_template_node:
    workflow_job_template: "Linux — Governed Service Restart"
    identifier: "approval_gate"
    success_nodes: ["restart"]
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Grant the Change Approvers team the Approve role
  awx.awx.role:
    team: "Change Approvers"
    role: approve
    workflow_job_templates: "Linux — Governed Service Restart"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
▲

Stated plainly, per this course's standards on version-specific behavior: approval-node automation is one of the areas most likely to differ across RHAAP/AWX versions and collection releases. Always confirm the exact module parameters against your installed awx.awx collection's documentation before treating the task shape above as universally exact — the underlying concept (a distinct, template-less node type that pauses the workflow pending human action) is stable across versions.

The Emergency Lane

Consistent with Project 9's two-lane change process, a true emergency shouldn't be stuck waiting 4 hours for approval while production is actively broken. Build a second, clearly-separate Workflow Job Template without the Approval gate, for genuine emergencies only.

Linux — Governed Service Restart          Linux — EMERGENCY Service Restart
   (standard lane, this project)              (emergency lane)
        |                                          |
   Pre-Check                                   Pre-Check
        |                                          |
  [ Approval Gate ]                           (no approval gate —
        |                                       goes straight through)
    Restart                                    Restart
        |                                          |
   Validate/Rollback                          Validate/Rollback
                                                    |
                                             MANDATORY: retroactive
                                             review within 24h, logged
                                             as an Emergency Change
                                             (Project 9's pattern)
emergency_workflow.yml
- name: Create the emergency-lane workflow (no approval gate)
  awx.awx.workflow_job_template:
    name: "Linux — EMERGENCY Service Restart"
    organization: "Banking Automation"
    description: >
      Emergency-only lane. Bypasses the standard Approval gate.
      Every use MUST be followed by a retroactive review within 24
      hours per the Project 9 Emergency Change process.
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Restrict Execute on the emergency lane to the team lead only
  awx.awx.role:
    user: "a.verma"
    role: execute
    workflow_job_templates: "Linux — EMERGENCY Service Restart"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
■

Deliberate, narrow access is what keeps the emergency lane from becoming a routine way to skip approval. Only Amit (the team lead) — not the whole Linux Operations team — has Execute on it, and every use is expected to trigger the same retroactive-review discipline as any other Emergency Change.

Run It — Production Incident

Incident: A Legitimate Change, Auto-Denied

Sara Khan, Friday afternoon

"I requested the restart workflow this morning for a real, approved change. It just got auto-denied by timeout. The change ticket was valid and everything — nobody just... approved it in time."

StageWhat you do
OBSERVEThe workflow correctly paused at the Approval gate, then correctly timed out after 4 hours with no action — the platform behaved exactly as configured; the question is why no one acted.
COLLECT EVIDENCECheck the Slack channel wired to fire on approval-pending — no message appears in the channel history for this request at all.
ISOLATE FAILUREThe notification never fired, meaning the Change Approvers had no signal a request was waiting on them — a delivery problem, not a human-attentiveness problem.
CHECK DEPENDENCIESCheck the Workflow Job Template's notification_templates_approvals attachment — you find it was configured on the Job Template used inside the workflow (a leftover habit from Project 11) rather than on the Workflow Job Template's own approval-specific notification hook.
IDENTIFY ROOT CAUSEApproval-pending is a workflow-level event, not a job-level one — attaching the notification to the wrong object meant it was configured to fire on an event that was never going to happen in this context.
FIXAttach the notification specifically to the Workflow Job Template's approval-pending hook, exactly as shown in the Ansible task above, and remove the incorrect job-level attachment that was never going to fire for this purpose.
VALIDATETrigger a new test workflow run, confirm the Slack channel receives an approval-pending alert immediately when the gate is reached, then approve it and confirm the workflow proceeds correctly.
PREVENT RECURRENCEAdd "confirm the approval-pending notification is attached to the Workflow Job Template itself, not a node's Job Template" to the governance checklist (Project 9) as an approval-workflow-specific line item.
◆

This incident validates Priya's original concern precisely. The Timeout setting worked correctly — the gap was entirely in the notification wiring, which is exactly why this project treated Timeout and notification as a single deliverable rather than two independent settings.

Practice

Interview Preparation

Q1. What is an Approval node, and how does it differ from a regular workflow node?
It's a distinct node type with no underlying Job Template — when execution reaches it, the workflow pauses entirely until someone holding the Approve role on that Workflow Job Template explicitly approves or denies it, rather than any automated logic deciding the outcome.
Q2. How do you enforce Separation of Duties using an Approval node?
Grant the Approve role to a team whose membership is deliberately disjoint from the Developers/Admins who built and maintain the underlying automation — verified directly by checking RBAC role membership, not by policy statement alone.
Q3. What happens if an Approval node's timeout expires with no action taken?
It's typically treated as a denial, halting that branch of the workflow — which is why a Timeout must always be paired with a reliable notification to the approvers the moment their action is needed, or a legitimate request can fail purely due to lack of visibility rather than an actual decision to deny it.
Q4. How would you design an emergency bypass for an approval-gated workflow without undermining the control?
A genuinely separate Workflow Job Template without the gate, with Execute access restricted to a very small, named set of people (e.g. a team lead), paired with a mandatory retroactive review requirement for every use — never simply allowing the standard lane's approval step to be skipped on request.
Q5. A legitimate change request was denied by an approval timeout. How do you investigate?
First confirm whether the timeout itself behaved correctly (it likely did, since that's simple, deterministic logic), then check whether the approvers were actually notified when the request reached the gate — a missing or misattached notification, rather than human inattentiveness, is the more common root cause.

Practice Assignment

◆

Lab vs. Enterprise Production: Approval nodes, timeouts, and notifications are fully practicable on a lab RHAAP/AWX instance — use a short timeout (a few minutes) during testing so you don't have to wait hours to observe the timeout behavior.

  1. Insert an Approval node into your lab's governed-restart workflow between Pre-Check and Restart.
  2. Create a second test user, add them to a new "Approvers" team distinct from your Developer/Operator test accounts, and grant that team the Approve role on the workflow.
  3. Launch the workflow as an Operator test user and confirm it pauses at the gate; approve it as the Approver test user and confirm Restart proceeds.
  4. Set a short timeout (e.g. 2 minutes), launch again, and deliberately let it expire — confirm the workflow halts and observe how the denial is recorded.
  5. Wire a notification to the approval-pending event and confirm it fires correctly — then deliberately misattach it to a node's Job Template instead, reproducing this project's incident, and confirm it does not fire in that misconfigured state.
