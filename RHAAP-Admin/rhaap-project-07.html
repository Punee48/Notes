Concept

Run vs. Check Mode

Every Job Template has a Job Type. You've only used Run so far. Check mode runs the playbook with Ansible's --check flag: modules report what would change without actually changing it.

Job TypeBehaviorWhen to use
RunExecutes normally — makes real changesThe actual production action, after validation
CheckDry-run — reports what would change, no actual changes made (assuming every task in the playbook properly supports check mode)Compliance/audit-style checks; pre-validating a change before running it for real
▲

Check mode isn't automatically safe for every playbook. A task using ansible.builtin.command or shell to run an arbitrary script generally cannot report a meaningful dry-run — it either skips or behaves unpredictably under --check. Design playbooks intended for Check-mode use with proper, check-mode-aware modules (like ansible.builtin.package, ansible.builtin.systemd) rather than raw shell commands.

ABC Bank's design: build two Job Templates from the same Project and playbook — one with Job Type Check for the compliance dry-run Compliance actually asked for, and, later, a Run variant if remediation is ever automated (not today — today's playbook only reports, it doesn't remediate).

Concept

Forks, Timeout & Concurrency — Designing for 40 Hosts, Not 2

Forks

How many hosts Ansible connects to and runs tasks against in parallel. Default is often 5. At 40 hosts with forks=5, a simple task takes 8 sequential batches; raising forks reduces wall-clock time but increases simultaneous load on target hosts and the execution node. A reasonable middle ground for 40 RHEL hosts running lightweight checks: forks=15–20.

Timeout

The maximum time (seconds) RHAAP allows the entire job to run before forcibly cancelling it. Without one, a job stuck on one unresponsive host (exactly Amit's "looked stuck" moment) can sit indefinitely, blocking visibility into whether it's truly hung or just slow.

Concurrent Jobs

Answering Amit directly: unchecking Concurrent Jobs (the default) means RHAAP will queue or reject a second launch of the same Job Template while one is already running, instead of letting two runs execute against the same hosts simultaneously — which is almost never what you want for a state-changing operation, and even for a read-only compliance check, avoids confusing duplicate reports.

SettingABC Bank's Project 7 choiceWhy
Forks15Balances wall-clock time against load, appropriate for 40 hosts today and headroom toward 100
Timeout600 seconds (10 minutes)Generous enough for legitimate slow runs, short enough that a truly hung job surfaces within a coffee break, not a full day
Concurrent JobsOff (unchecked)Prevents Amit's double-launch scenario and duplicate/contradictory compliance reports
Concept

Labels & Organization

At 7 Job Templates, remembering names is fine. At 40+ (where ABC Bank is headed across multiple teams), Labels let you filter and report — "show me every Job Template tagged compliance," or every one tagged linux-ops, regardless of which Project or Organization it lives in.

Suggested label taxonomy
team:      linux-ops        # which team owns it
category:  compliance        # what kind of automation it is
risk:      read-only          # read-only vs state-changing, for quick risk scanning
Build

The Patch Compliance Playbook

playbooks/patch-compliance-check.yml
---
- name: Report patch compliance status without making changes
  hosts: rhel_web:rhel_db
  gather_facts: true
  vars:
    max_allowed_pending_updates: 5

  tasks:
    - name: Check for pending package updates (dnf)
      ansible.builtin.dnf:
        list: updates
      register: pending_updates
      check_mode: false   # a read-only query is safe to run even under Check mode

    - name: Count pending security-relevant updates
      ansible.builtin.set_fact:
        pending_count: "{{ pending_updates.results | default([]) | length }}"

    - name: Report compliance status per host
      ansible.builtin.debug:
        msg: >
          {{ inventory_hostname }}: {{ pending_count }} pending updates
          ({{ 'COMPLIANT' if pending_count | int <= max_allowed_pending_updates | int
              else 'NON-COMPLIANT — exceeds threshold of ' ~ max_allowed_pending_updates }})

    - name: Flag non-compliant hosts clearly for downstream reporting
      ansible.builtin.set_fact:
        compliance_status: "{{ 'NON-COMPLIANT' if pending_count | int > max_allowed_pending_updates | int else 'COMPLIANT' }}"
Explain the check-mode-aware design choices

check_mode: false on the dnf query task explicitly allows this specific, read-only task to actually execute even when the whole job is launched in Check mode — since listing updates doesn't change anything, there's no reason to skip it under --check.

The playbook never calls state: latest or any actual installation module — it's a pure reporting playbook, which is exactly why it's a safe, appropriate fit for a Check-type Job Template. Remediation (actually installing patches) would be a deliberately separate, Run-type Job Template with its own, likely stricter, RBAC and approval requirements.

Why allow_simultaneous: false directly answers Amit's request

With this set, a second launch attempt while a job is already running for this template is rejected/queued rather than executed in parallel. Amit's accidental double-launch would now either wait for the first to finish or clearly show a "job already running" state, instead of silently running two overlapping jobs against the same 40 hosts.

Wiring Notifications Onto This Template

Project 2 built an Organization-wide notification for Project sync failures. Today, attach a Job-Template-specific notification so Compliance actually hears about a non-compliant fleet, not just a platform failure.

UI

  1. Open Linux — Patch Compliance Check → Notifications tab.
  2. Under Success, enable a notification template addressed to the Compliance team's channel — every successful run still delivers the compliance report content in job output/summary.
  3. Under Failure, enable the same Platform Team — Project Sync Failures-style template pattern from Project 2, addressed instead to the platform team, for genuine job failures (distinct from "ran successfully but reported non-compliant hosts," which is expected, valid output, not a failure).
◆

Distinguish "the job failed" from "the job succeeded and found a problem." A Check-mode compliance job that runs successfully and reports non-compliant hosts is a successful job with an interesting result — not a job failure. Piping that distinction correctly into Success vs Failure notification channels prevents Compliance from being alert-fatigued by routine reports and prevents the platform team from being paged for someone else's patch backlog.

Security Notes For Project 7

▲

A Check-mode template is not automatically low-risk just because it's "read-only." If the underlying playbook mixes read-only tasks with tasks that aren't properly check-mode-aware, a "dry run" could still make unintended changes. Review every task in a playbook meant for Check-mode use, not just the template's Job Type setting.

◆

Timeout is a safety control, not just an operational convenience. A job with no timeout that hangs on a broken host can hold RBAC-relevant state (like "this job is still running, so simultaneous launches are blocked") indefinitely, which itself becomes an availability problem for the team depending on it.

Practice

Interview Preparation

Q1. What's the difference between Run and Check job types, and when would you use Check?
Run executes the playbook normally, making real changes. Check runs in Ansible's dry-run mode, reporting what would change without changing it — appropriate for compliance reporting or pre-validating a change, provided the playbook's tasks are actually check-mode-aware.
Q2. Why set a Timeout on a Job Template?
Without one, a job stuck on an unresponsive host can run indefinitely, blocking visibility into whether it's genuinely hung and potentially blocking future launches if Concurrent Jobs is also disabled. A Timeout forces a bounded, predictable failure instead of an indefinite hang.
Q3. When should Concurrent Jobs be allowed?
Almost never for state-changing automation — simultaneous runs against the same hosts risk conflicting changes. Even for read-only jobs, disabling it avoids confusing, duplicate reports from overlapping runs. It's occasionally appropriate for genuinely independent, non-overlapping target sets, but that's the exception, not the default.
Q4. How would you choose a Forks value for a growing inventory?
Balance wall-clock execution time against load on target hosts and the execution node — too low and jobs take unnecessarily long as the inventory grows; too high and you risk overwhelming target systems or the execution infrastructure. Validate the choice against real host counts, not just the current small pilot group.
Q5. A job that normally finishes in two minutes has been "running" for an hour. What's your investigation approach?
Check the job's per-host output to see if the fleet completed except for one or a few stragglers versus the whole job being stuck — a single hung host with no Timeout configured is the most common cause, versus a platform-wide issue if nothing progressed at all.

Practice Assignment
