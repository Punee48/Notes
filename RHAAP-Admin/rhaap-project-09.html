Job Template Governance

Two incidents so far — the missing-credential template edit in Project 3, and the stray set_fact in Project 8 — trace back to the same root cause: Job Templates being live-edited directly in the UI with no review step. Today you close that gap: Job Template definitions become reviewed, version-controlled configuration, with a checklist standard every future template must pass before it's considered production-ready.

Concept

Why Governance, Concretely — Not Abstractly

"Governance" can sound like paperwork for its own sake. Ground it in what actually happened this course:

IncidentWhat went wrongWhat governance would have caught
Project 3 — greyed-out Launch buttonA Developer's live UI edit accidentally removed the attached CredentialA reviewed diff would show a Credential being removed — an obvious, catchable red flag before it reached Operators
Project 8 — wrong service restartedLeftover debug code (set_fact) silently overrode a survey-supplied variableCode review of the playbook change would likely have caught an unexplained set_fact left in from testing
◆

The pattern in both cases: a small, well-intentioned live edit, made directly against production, with nobody else looking at it before Operators were affected. Governance doesn't prevent mistakes — it catches them before they reach people who trusted the template to already be correct.

Concept

The Live-Edit Problem, Precisely

TODAY (ungoverned):
  Developer opens UI -> edits Job Template directly -> Save
       |
       v
  Change is LIVE IMMEDIATELY, visible to every Operator with Execute
       |
       v
  Nobody else saw it. No diff. No review. No rollback path except
  "remember what it looked like before."

GOVERNED (this project's target):
  Developer edits an Ansible-managed Job Template definition in Git
       |
       v
  Pull Request opened -> reviewed by a second person -> approved
       |
       v
  Merge triggers (or a human runs) the Ansible playbook that applies
  the change via the API
       |
       v
  Git history IS the audit trail and the rollback path
Fig 9.1 — the destination isn't "never touch the UI again." It's "the UI reflects what Git says, not the other way around."

Job Templates as Reviewed Code

Convert the Linux — Restart Service template — survey and all — into one canonical Ansible definition, living in Git. This is a focused, single-template preview of the full RHAAP-as-code pattern built out completely in Project 22.

linux-ops-automation/
│
├── playbooks/
│   └── restart-service.yml
│
├── rhaap-config/                      <- NEW, this project
│   └── job_templates/
│       └── restart_service.yml         <- the full, reviewed Job Template
│                                            + survey definition
│
├── README.md
└── CHANGELOG.md
rhaap-config/job_templates/restart_service.yml
---
- name: Apply the reviewed definition of Linux — Restart Service
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    controller_host: "https://rhaap.abcbank.internal"
    controller_oauthtoken: "{{ lookup('env', 'RHAAP_TOKEN') }}"

  tasks:
    - name: Apply the job template's core configuration
      awx.awx.job_template:
        name: "Linux — Restart Service"
        job_type: run
        inventory: "Linux Servers"
        project: "linux-ops-automation-prod"
        playbook: "playbooks/restart-service.yml"
        execution_environment: "Default execution environment"
        credentials:
          - "Linux SSH Key"
        forks: 15
        timeout: 300
        allow_simultaneous: false
        labels:
          - "team:linux-ops"
          - "category:operations"
          - "risk:state-changing"
        survey_enabled: true
        survey_spec:
          name: "Restart Service Survey"
          description: "Collects operator input for the restart-service template."
          spec:
            - question_name: "Which service should be restarted?"
              variable: service_name
              type: multiplechoice
              choices: "httpd\nsshd\nchronyd"
              required: true
            - question_name: "Change ticket number"
              variable: change_ticket
              type: text
              min: 10
              max: 10
              required: true
            - question_name: "Reason for restart (optional)"
              variable: restart_reason
              type: textarea
              required: false
            - question_name: "Confirm production impact"
              variable: confirm_production
              type: multiplechoice
              choices: "Yes, I understand this affects production\nNo — cancel"
              required: true
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_oauthtoken }}"
        state: present

    - name: Apply RBAC — Linux Operations gets Execute only
      awx.awx.role:
        team: "Linux Operations"
        role: execute
        job_templates: "Linux — Restart Service"
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_oauthtoken }}"
        state: present
◆

This single file is now the answer to "what does this Job Template look like?" — not "whatever the UI currently shows," which could include an unreviewed live edit. Running this playbook is idempotent (Project 1's lesson, applied here): if the live template already matches, nothing changes; if it's drifted, this brings it back in line.

A Lightweight Drift Check

Full drift detection across the entire platform is Project 23's dedicated focus. Today, build a narrow, immediately useful version: detect when a live Job Template no longer matches its Git-defined configuration.

drift_check.yml
---
- name: Detect drift between live Job Template and its reviewed definition
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    controller_host: "https://rhaap.abcbank.internal"
    controller_oauthtoken: "{{ lookup('env', 'RHAAP_TOKEN') }}"
    expected_credentials: ["Linux SSH Key"]
    expected_timeout: 300
    expected_allow_simultaneous: false

  tasks:
    - name: Fetch the live job template
      ansible.builtin.uri:
        url: "{{ controller_host }}/api/controller/v2/job_templates/?name=Linux — Restart Service"
        headers: { Authorization: "Bearer {{ controller_oauthtoken }}" }
        return_content: true
      register: live_template

    - name: Extract the live configuration
      ansible.builtin.set_fact:
        live_timeout: "{{ live_template.json.results[0].timeout }}"
        live_allow_simultaneous: "{{ live_template.json.results[0].allow_simultaneous }}"

    - name: Flag drift in timeout
      ansible.builtin.debug:
        msg: "DRIFT DETECTED: timeout is {{ live_timeout }}, expected {{ expected_timeout }}"
      when: live_timeout | int != expected_timeout

    - name: Flag drift in concurrency setting
      ansible.builtin.debug:
        msg: "DRIFT DETECTED: allow_simultaneous is {{ live_allow_simultaneous }}, expected {{ expected_allow_simultaneous }}"
      when: live_allow_simultaneous != expected_allow_simultaneous

    - name: Fetch attached credentials
      ansible.builtin.uri:
        url: "{{ controller_host }}/api/controller/v2/job_templates/{{ live_template.json.results[0].id }}/credentials/"
        headers: { Authorization: "Bearer {{ controller_oauthtoken }}" }
        return_content: true
      register: live_credentials

    - name: Flag drift in attached credentials
      ansible.builtin.debug:
        msg: "DRIFT DETECTED: live credentials {{ live_credentials.json.results | map(attribute='name') | list }} do not match expected {{ expected_credentials }}"
      when: (live_credentials.json.results | map(attribute='name') | list) != expected_credentials
◆

Run this on the same schedule as the RBAC self-audit from Project 3 (once Schedules exist formally in Project 10) — together they form an early, practical governance dashboard: "does live RHAAP configuration actually match what we reviewed and approved."

The New Change Process — Answering Amit

Directly addressing Amit's concern: governance must not mean "open a PR while production is on fire." Design two lanes:

Standard Change

Edit the Ansible definition in Git → open a Pull Request → one reviewer approves → merge → run the playbook (manually today; automated once CI/CD arrives in Project 32). Used for planned, non-urgent changes — new surveys, credential swaps, new templates.

Emergency Change

Fix directly in the UI to restore service immediately, exactly as before — but within 24 hours, update the Git-managed definition to match what was actually changed, and run the drift check to confirm the two are back in sync. The incident writeup itself becomes the retroactive review record.

◆

This directly resolves Amit's objection without weakening the control. Emergency changes are still allowed to move fast — they just can't be allowed to permanently diverge from the reviewed source of truth. The drift check is exactly the mechanism that catches an emergency fix that never got backfilled into Git.

Security Notes For Project 9

■

Governance is a compensating control for the fact that Developer-role Admin access is inherently powerful. Recall Project 3's persona matrix — Automation Developers hold Admin on Job Templates by design, because they need to build and maintain them. Config-as-code plus review is what keeps that necessary power from becoming an unchecked single point of failure.

▲

A drift check with no one reading its output is just a script. Route its findings into the same notification pattern from Projects 2 and 7 — a drift check that nobody sees defeats the purpose.

Run It — Production Incident

Incident: An Emergency Fix Never Made It Back to Git

Drift check output, three weeks after this project shipped

"DRIFT DETECTED: live credentials ['Linux SSH Key', 'Linux Ops Vault Password'] do not match expected ['Linux SSH Key']"

StageWhat you do
OBSERVEThe drift check itself is the alert — no Operator complaint prompted this, which is exactly the point of running it proactively.
COLLECT EVIDENCECheck recent job history and team chat around the time this likely changed — you find an Emergency Change three weeks ago: a vault credential was added directly in the UI to unblock a legitimate, urgent playbook update, following the Emergency Change lane correctly.
ISOLATE FAILUREThe emergency fix itself was appropriate and correctly applied — the failure is procedural: the 24-hour Git backfill step from the change process never happened.
CHECK DEPENDENCIESConfirm the vault credential addition is still actually needed (it is — the playbook it supports is still in use) before deciding how to resolve the drift.
IDENTIFY ROOT CAUSEA process gap, not a technical one: nothing enforced the 24-hour backfill requirement — it depended entirely on someone remembering.
FIXUpdate the Git-managed definition to include the vault credential, matching the live state exactly, and merge it through the standard review lane (a low-risk, after-the-fact review, since the change is already proven safe in production).
VALIDATERe-run the drift check; confirm it now reports no drift.
PREVENT RECURRENCEMake the drift check itself the enforcement mechanism going forward — scheduled to run daily (Project 10) with its findings routed to a notification channel, so an un-backfilled emergency change surfaces within 24 hours automatically instead of being discovered by chance three weeks later.
◆

This incident validates the whole design, rather than undermining it. The Emergency Change lane worked exactly as intended — fast, safe, unblocking. The drift check caught the one place the process still depended on human memory, and gives you a concrete reason to automate that step next.

Interview Preparation

Q1. Why is live-editing Job Templates in the UI a governance risk, even for small, well-intentioned changes?
Because the change goes live immediately with no review step and no diff for anyone else to catch a mistake — a Credential accidentally removed, or leftover debug code left in, reaches Operators before anyone else has a chance to notice.
Q2. How do you avoid governance becoming a bottleneck during an active incident?
A two-lane change process — a standard reviewed lane for planned changes, and an emergency lane that allows an immediate direct fix, with a mandatory, time-boxed requirement to backfill the change into the reviewed, version-controlled definition afterward, verified by an automated drift check.
Q3. What does a drift check actually verify, and why is it necessary even with a good change process?
It compares the live configuration of an object against its version-controlled, reviewed definition and flags any mismatch. It's necessary because even a well-designed process (like the Emergency Change lane) can still depend on a manual follow-up step that gets forgotten — the drift check catches exactly that failure mode automatically instead of relying on someone noticing.
Q4. How would you build a governance checklist that a team actually follows?
Ground every line item in a real incident or concrete failure the team has actually experienced, rather than generic best-practice advice — a checklist that visibly traces back to "this is why line 4 exists" is far more likely to be respected than an abstract policy document.
