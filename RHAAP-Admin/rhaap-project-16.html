Concept — Read This Carefully

Smart vs. Constructed Inventory — A Version-Specific Note

State this plainly, because it genuinely differs by platform version: older Ansible Tower / early AWX releases offered Smart Inventories — a saved host-filter query across an Organization's existing hosts, read-only, with no ability to add its own groups or variables. Newer RHAAP/AAP releases introduce (and in many current versions, favor) Constructed Inventories — a more powerful mechanism that combines one or more existing Inventories as explicit "input inventories," and lets you layer groups, compose, and filtering logic on top, much like the plugin syntax from Project 15's dynamic source.

CapabilitySmart Inventory (older)Constructed Inventory (current)
Combines multiple existing InventoriesNo — queries hosts within a single Organization by filterYes — explicitly lists one or more source Inventories as inputs
Can define new groups/variables on topNo — purely a filtered viewYes — supports groups, compose, similar to a dynamic source plugin
Usable as a Job Template's InventoryYes, with real limitations in some versionsYes, and generally the more actively maintained/recommended path going forward
▲

Check which mechanism your specific RHAAP/AAP version actually exposes before following this project's steps literally. This project builds using Constructed Inventory concepts, since that's the direction the platform has moved — if your instance only offers Smart Inventory, the underlying goal ("one queryable view spanning multiple sources without manual list maintenance") is achieved differently, with real capability limits worth confirming against your version's documentation.

How a Constructed Inventory Works

Constructed Inventory: "All Production — Linux"
   |
   +-- Input Inventory 1: "Linux Servers"
   |      (static prod_db group + dynamic prod_web source, Project 15)
   |
   +-- limit / filter: only hosts where group == "production" family
   |
   +-- compose / groups: reshape the combined result
   |      (e.g., tag every resulting host with a normalized `tier` variable)
   |
   v
Presents as a single, ordinary-looking Inventory to any Job Template —
Operators and Job Templates don't need to know or care that it's actually
combining a static group and a live cloud query underneath.

Build

Building "All Production — Linux"

UI

  1. Automation Execution → Inventories → Create Inventory → Constructed Inventory.
  2. Name: All Production — Linux, Organization: Banking Automation.
  3. Input Inventories: add Linux Servers (the single Inventory already holding both the static prod_db group and the Project 15 dynamic prod_web source).
  4. Limit: an Ansible host-pattern-style expression selecting only production-family groups, e.g. prod_db:role_web:&env_production (syntax varies by version — verify against your instance's constructed inventory limit syntax reference).
  5. Update options: enable automatic refresh so the constructed view stays current whenever its input Inventory's dynamic source re-syncs (Project 15's 10-minute cadence).
  6. Save, then Sync and confirm the resulting host count matches "every prod_db host plus every currently-running prod_web instance," and nothing from staging.

ANSIBLE

all_production_linux_constructed.yml
- name: Create the constructed inventory spanning static and dynamic production hosts
  awx.awx.inventory:
    name: "All Production — Linux"
    organization: "Banking Automation"
    kind: constructed
    input_inventories:
      - "Linux Servers"
    limit: "prod_db:role_web:&env_production"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  # Module support and exact parameter names for constructed inventories
  # are newer additions to the awx.awx collection and vary meaningfully
  # by version — verify the current module documentation for your
  # installed collection release before relying on this task verbatim.
Explain the limit expression

prod_db:role_web:&env_production uses Ansible's host-pattern syntax: : means "union" (include hosts in either group), and & means "intersection" (include only hosts also in this group). Read left to right: include everything in prod_db OR role_web, but — because of the trailing &env_production — restrict the final result to only those also tagged env_production. Since prod_db itself has no non-production members (Project 5's design), and role_web comes entirely from the Project 15 dynamic source tagged Environment=production, this expression correctly yields exactly the production fleet across both sources — nothing from staging.

Build

RBAC Inheritance

A Constructed Inventory does not create a new, independent set of hosts — it's a computed view over its input Inventories. RBAC follows accordingly: a user's effective visibility into a Constructed Inventory's hosts is still bounded by whatever access they actually have to the underlying input Inventory (or Inventories).

GrantEffect
Read on All Production — Linux only, no grant on Linux ServersDepending on version-specific enforcement, this may still surface host data drawn from an Inventory the user has no direct grant on — always test this explicitly rather than assuming either behavior
Read on both the Constructed Inventory and its input Linux Servers InventoryUnambiguous, consistent visibility — the safer, recommended pattern
■

Don't assume — verify this specific behavior on your own RHAAP/AAP version before trusting it for an RBAC-sensitive design. Whether a Constructed Inventory's RBAC strictly re-derives from its inputs or can be granted somewhat independently is exactly the kind of detail that varies by release and is easy to get wrong by assumption. Grant Read on both the constructed view and its inputs to the same audience, rather than relying on inherited-only visibility, until you've explicitly confirmed your version's behavior.

Re-Targeting the Compliance Check

Directly resolving Priya's request: the Patch Compliance Check Job Template (Project 7) moves from pointing at the whole, undifferentiated Linux Servers Inventory to pointing explicitly at All Production — Linux.

patch_compliance_check.yml (updated)
- name: Re-point the compliance check at the explicit production view
  awx.awx.job_template:
    name: "Linux — Patch Compliance Check"
    inventory: "All Production — Linux"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
◆

This one-line change is the entire point of the project. The Job Template's definition now says exactly what it means — "run against production" — instead of implicitly depending on which groups happen to exist in a broader, mixed-purpose Inventory. If staging ever grows new groups later, the compliance check's targeting doesn't silently change; it's explicitly scoped.

Security Notes For Project 16

■

A Constructed Inventory can quietly widen a Job Template's effective reach if its limit expression is looser than intended. A single misplaced : instead of & in the limit syntax is the difference between "production only" and "production or literally anything in the second group" — always validate the actual resulting host list after any change to a limit expression, never just trust that the syntax "looks right."

▲

Treat RBAC on Constructed Inventories conservatively until proven otherwise on your specific version. Grant visibility on both the constructed view and its inputs to the same audience rather than assuming inheritance alone is sufficient or correctly scoped.

Incident: The Compliance Check Suddenly Covered Fewer Hosts

Amit Verma

"This week's compliance report only shows 2 hosts. We should have at least the 3 prod_db hosts plus however many prod_web instances are running — definitely more than 2."

StageWhat you do
OBSERVEThe constructed Inventory's host count dropped sharply and unexpectedly — worth checking whether this is a real infrastructure change or a construction-logic problem before assuming either.
COLLECT EVIDENCECheck the constructed Inventory's actual host list directly — it shows exactly 2 hosts, both from prod_db. Zero prod_web hosts appear, despite Project 15's dynamic source showing 3 running instances when checked independently.
ISOLATE FAILUREThe dynamic source itself is healthy and correctly populated — the gap is specifically in how the constructed layer is combining it, not in the underlying data.
CHECK DEPENDENCIESReview the constructed Inventory's limit expression — you find someone recently "cleaned up" the syntax and accidentally changed prod_db:role_web:&env_production to prod_db:role_web&env_production (dropped the leading colon before the ampersand), which changes the expression's grouping entirely.
IDENTIFY ROOT CAUSEA small, easy-to-miss syntax edit silently narrowed the effective host-pattern logic, and nothing caught it before it reached production — exactly the kind of change Project 9's governance model exists to catch, but this edit happened directly in the UI rather than through the reviewed Ansible definition.
FIXRestore the correct limit expression via the reviewed all_production_linux_constructed.yml definition, re-applying it through Ansible rather than patching the UI directly again.
VALIDATESync and confirm the host count returns to the expected combined total (3 prod_db + current prod_web instance count).
PREVENT RECURRENCEAdd "verify the constructed Inventory's actual resulting host count after any limit expression change" as an explicit governance checklist item (Project 9), and extend the drift-check playbook to flag if the Constructed Inventory's live definition no longer matches its Git-managed version.
◆

This incident is a direct, concrete argument for applying Project 9's governance model to Inventory definitions, not just Job Templates. A one-character syntax slip in a limit expression is exactly the class of change a reviewed diff would likely have caught before it silently under-scoped a production compliance check.

Interview Preparation

Q1. What's the difference between a Smart Inventory and a Constructed Inventory?
A Smart Inventory is an older, read-only saved host-filter query within a single Organization, with no ability to define its own groups or variables. A Constructed Inventory is the newer mechanism that explicitly combines one or more existing Inventories as inputs and supports layering groups/compose/filtering logic on top, similar to a dynamic source plugin.
Follow-up: "Which should you use today?" — Depends on the specific RHAAP/AAP version; Constructed Inventory is the more actively developed, generally recommended direction, but always confirm what your specific instance actually supports.
Q2. Why build a combined inventory instead of just adding a static group listing every production host manually?
Because part of the production fleet (prod_web) is dynamically sourced and changes frequently — a manually maintained combined list would immediately drift out of sync with reality, defeating the entire point of Project 15's dynamic sourcing work.
Q3. How does RBAC on a Constructed Inventory relate to RBAC on its input Inventories?
It's derived from the underlying input Inventories rather than being fully independent, though the exact enforcement behavior can vary by version — the safe practice is to grant visibility on both the constructed view and its inputs to the same audience rather than assuming inheritance alone is sufficient.
Q4. A Constructed Inventory's host count dropped unexpectedly. What's your investigation approach?
First confirm whether the underlying input Inventory/source itself is healthy and has the expected hosts — if it does, the problem is almost certainly in the constructed layer's own limit/filter expression, which should be checked next for a recent, possibly small, syntax change.
Q5. Why apply Project 9's governance model to Inventory definitions, not just Job Templates?
Because a small, easy-to-miss change to a limit or filter expression can silently and significantly change what a Job Template actually targets, with no obvious error — exactly the kind of change a reviewed diff is well-suited to catch before it reaches production.
