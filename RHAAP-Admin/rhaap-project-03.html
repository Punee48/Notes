Concept

The Full RBAC Model

Two categories of roles exist in RHAAP. Conflating them is the most common design mistake.

System-wide roles

Apply across the entire platform, not scoped to one object: System Administrator (full control of everything) and System Auditor (read-only visibility into everything). Reserved for a tiny number of people.

Object-level roles

Apply to one specific Organization, Team, Project, Inventory, Credential, or Job Template. This is 95% of real RBAC design — the "who can do what to this specific thing" grants you've built in Projects 1–2.

▲

Design mistake to avoid: reaching for System Administrator or System Auditor to solve a problem that object-level roles could solve more narrowly. "She needs to see everything the Linux team does" is almost never true — it's usually "she needs Read on these three specific objects," which is a very different, much safer grant.

Concept

Separation of Duties (SoD)

SoD is a control, not a feature — it's a design decision you enforce using ordinary RBAC grants, structured deliberately. The core question the auditor asked: can one person write a change and also be the one who approves it running in production?

Developer                  Approver
   |                           |
   v                           v
Can Admin the                Can Approve the
Job Template inside          Workflow Job Template's
a Workflow                   approval node
   |                           |
   +-------- must NOT be the same person --------+
                       |
                 SoD control

RHAAP doesn't have a single checkbox for this — SoD is achieved by never granting the same individual both the editing role and the approval role on the same automation, and by designing Teams so that "who's on the Developer team" and "who's on the Approver team" are deliberately non-overlapping sets (with narrow, documented exceptions if the bank's policy allows them, e.g. for small teams).

■

Full Approval workflow mechanics — the actual approval node, pause/resume behavior — are built in Project 13. Today you're designing the RBAC boundary that will make that control meaningful once it exists. Building the workflow first without this boundary would let a Developer approve their own change, which defeats the entire point.

ANSIBLE — the whole persona, as code

auditor_persona.yml
---
- name: Implement the Auditor persona for Linux Operations
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    controller_host: "https://rhaap.abcbank.internal"
    controller_oauthtoken: "{{ lookup('env', 'RHAAP_TOKEN') }}"

  tasks:
    - name: Create the Compliance Auditors team
      awx.awx.team:
        name: "Compliance Auditors"
        organization: "Banking Automation"
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_oauthtoken }}"
        state: present

    - name: Add Meera Pillai as a member
      awx.awx.role:
        user: "m.pillai"
        team: "Compliance Auditors"
        role: member
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_oauthtoken }}"
        state: present

    - name: Grant read-only access across the Linux Operations object set
      awx.awx.role:
        team: "Compliance Auditors"
        role: read
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_oauthtoken }}"
        state: present
        "{{ item.key }}": "{{ item.value }}"
      loop:
        - { key: projects,      value: "linux-ops-automation" }
        - { key: inventories,   value: "Linux Servers" }
        - { key: credentials,   value: "Linux SSH Key" }
        - { key: job_templates, value: "Linux — Restart Service" }
Explain the loop trick in the last task

The awx.awx.role module accepts different keyword arguments depending on which object type you're granting against (projects:, inventories:, credentials:, job_templates:). Using "{{ item.key }}": "{{ item.value }}" inside the loop dynamically supplies whichever keyword each iteration needs, so one task handles all four object types instead of writing four nearly-identical tasks. This is a real pattern you'll reuse constantly once RBAC-as-code (Project 22) scales across dozens of objects.

Auditing Your Own RBAC Model

Before the real annual audit, catch your own violations. Three checks worth automating today:

CheckWhy it matters
Any user with a direct Admin grant on a CredentialShould almost always be a Team grant, not an individual one — individual Admin grants are exactly the kind of thing that lingers after someone changes roles (see Project 2's incident)
Any Team with Admin on an object it only needs Execute/Read onClassic over-provisioning — often a leftover from early, less careful onboarding
Any overlap between the Developer team and a future Approver team on the same automationDirect SoD violation once Project 13's approval workflow goes live
rbac_audit.yml
---
- name: Self-audit RBAC for common violations
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    controller_host: "https://rhaap.abcbank.internal"
    controller_oauthtoken: "{{ lookup('env', 'RHAAP_TOKEN') }}"

  tasks:
    - name: Pull all credentials
      ansible.builtin.uri:
        url: "{{ controller_host }}/api/controller/v2/credentials/"
        headers: { Authorization: "Bearer {{ controller_oauthtoken }}" }
        return_content: true
      register: all_credentials

    - name: For each credential, check who has direct Admin access
      ansible.builtin.uri:
        url: "{{ controller_host }}/api/controller/v2/credentials/{{ item.id }}/access_list/"
        headers: { Authorization: "Bearer {{ controller_oauthtoken }}" }
        return_content: true
      loop: "{{ all_credentials.json.results }}"
      loop_control: { label: "{{ item.name }}" }
      register: access_lists

    - name: Flag individual (non-team) Admin grants on credentials
      ansible.builtin.debug:
        msg: >
          FINDING: user {{ perm.summary_fields.user.username }} has a direct
          Admin-level grant on credential '{{ item.item.name }}' —
          verify this should be a Team grant instead.
      loop: "{{ access_lists.results | subelements('json.results', skip_missing=True) }}"
      loop_control: { label: "{{ item.0.item.name }}" }
      when: >
        item.1.summary_fields.direct_access is defined and
        item.1.summary_fields.direct_access | selectattr('role.name', 'equalto', 'Admin') | list | length > 0
◆

Run this on a schedule, not just once. RBAC drifts as fast as onboarding happens. A scheduled version of this playbook (Schedules arrive formally in Project 10) turns "hope nothing's wrong" into "get a report every Monday morning."

Security Notes For Project 3

■

Prefer Team grants over individual grants, always. Every direct grant to a named user is a grant someone has to remember to clean up individually when that person's role changes. Team grants clean themselves up the moment membership changes — this is the single biggest lever for reducing audit findings over time.

▲

Auditor visibility is not the same as Auditor authority. Read access lets Compliance verify controls exist; it must never come bundled with Execute, Update, or Admin on the same objects — an Auditor who can also change what they're auditing isn't providing independent assurance.

◆

Design the Approver pool before you need it. Even though Project 13 builds the mechanism, deciding today which humans are allowed to be Approvers — and confirming none of them are also Developers on the same automation — means the control is ready the moment the feature is.

Run It — Production Incident

Incident: "I Can See It But Can't Launch It"

Slack message from Sara Khan

"Weird one — I can see 'Linux — Restart Service' in my Templates list, but the Launch button is greyed out. Yesterday it worked fine."

StageWhat you do
OBSERVETemplate is visible (implies at least Read) but not launchable (implies Execute is missing) — this is an RBAC symptom, not a platform outage; nobody else reported issues.
COLLECT EVIDENCEGET /api/controller/v2/users/{sara_id}/roles/ and her team memberships. You find she's still on the Linux Operations team, and the team still shows Execute on the template.
ISOLATE FAILUREIf the Team's grant is intact and she's still a member, her access should be unaffected — so check the Job Template itself, not just her side.
CHECK DEPENDENCIESYou find the Job Template's Credentials field is empty — someone editing the template yesterday (a Developer-role action) accidentally removed the attached Linux SSH Key credential. RHAAP greys out Launch when a Job Template is missing a required credential, regardless of the launcher's RBAC.
IDENTIFY ROOT CAUSENot an RBAC bug at all — a Developer's edit accidentally broke the template's configuration. The symptom looked like an access problem because Sara, correctly, has no visibility into why Launch is disabled — she only has Execute, not Admin, so she can't see the credential field is empty.
FIXRe-attach the Linux SSH Key credential to the Job Template.
VALIDATEConfirm with Sara that Launch is active again; launch it yourself with Limit set to one host as a sanity check.
PREVENT RECURRENCEThis is exactly the argument for Job Template Governance (Project 9) — putting Job Template definitions under change review instead of allowing live-edit-in-UI, so a misconfiguration like this goes through review before it reaches Operators.
◆

The RBAC lesson here: "greyed-out button" symptoms aren't always RBAC problems — but ruling RBAC in or out first, by checking direct and inherited access exactly as you learned in Project 2, is still the fastest way to eliminate an entire category of causes in under a minute.

Practice

Interview Preparation

RBAC

Q1. What's the difference between a system-wide role and an object-level role?
System-wide roles (System Administrator, System Auditor) apply across the entire platform and should be held by very few people. Object-level roles are scoped to one specific Organization, Project, Inventory, Credential, or Job Template — this is how the vast majority of real RBAC design should work, since it keeps grants narrow and auditable.
Q2. How do you implement separation of duties in RHAAP?
There's no single toggle — SoD is achieved by structuring RBAC so the same identity never holds both the editing/Admin role on an automation and the Approve role on its workflow, typically enforced by keeping Developer and Approver teams as non-overlapping groups.
Follow-up: "How would you catch a violation automatically?" — Script a check that cross-references Developer team membership against Approver team membership and flags any overlap, run on a schedule.
Q3. Why prefer Team-level grants over direct user grants?
Team grants automatically follow membership — remove someone from the team and their inherited access goes with them. Direct grants require someone to remember to revoke them individually, which is exactly the kind of gap that shows up in audit findings months later.

Scenario-Based

Q4. A user can see a Job Template but can't launch it, and their RBAC looks correct. What else would you check?
Whether the template itself is misconfigured — missing a required credential, inventory, or execution environment — since RHAAP disables Launch for configuration reasons independent of the launcher's own RBAC. Confirm the user's grants first to rule RBAC in or out, then check the object's own completeness.

Manager Round

Q5. How would you explain your RBAC model to a non-technical auditor?
Frame it around four named roles — who writes automation, who runs it, who approves it for production, who verifies it — with a plain statement of what each role can and can't touch, especially that the approver and the writer are never the same person, and that anyone with visibility into secrets never has more than that: visibility, not access to the secret value itself.

Lab vs. Enterprise Production: the full persona matrix is practicable on a lab RHAAP/AWX instance. A real external audit interview and a live SoD violation with real production consequences can't be simulated meaningfully — treat those conceptually using this project's reasoning.
