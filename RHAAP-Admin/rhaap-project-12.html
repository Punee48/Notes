Workflow Job Templates

Every Job Template so far has been one playbook doing one thing. Today, chain multiple Job Templates into a single governed sequence — pre-check, action, validate, and a rollback path that triggers automatically on failure — the foundation everything from Project 13's approvals to Project 36's change-management workflows builds on.

Concept

What a Workflow Job Template Is

A Workflow Job Template (WFJT) is its own object type — not a Job Template, but a container that orchestrates a graph of nodes, where each node can be a Job Template, another nested Workflow, an approval gate (Project 13), or a few other node types. RHAAP evaluates the graph, launching each node according to the outcome of the node(s) before it.

WITHOUT a workflow (what existed before this project):
  Operator manually launches "Pre-Check" -> waits -> manually
  launches "Restart" -> waits -> manually launches "Validate"
  -> if something failed, operator manually decides what to do next

WITH a Workflow Job Template:
              Start
                |
                v
           Pre-Check
                |
          +-----+-----+
          |           |
       SUCCESS      FAILURE
          |           |
          v           v
       Restart      (stop here — unsafe to proceed)
          |
    +-----+-----+
    |           |
 SUCCESS      FAILURE
    |           |
    v           v
 Validate    Rollback
                |
                v
           Notify team
Fig 12.1 — the graph itself encodes the decision logic that used to live only in an operator's head.
◆

This directly answers Priya's request. "Only restart if it's safe" becomes a real, enforced Success/Failure branch — not a step an operator might skip under time pressure.

Concept

Node Types & Edges

Link typeFires when the parent node...Used for
On SuccessCompleted successfullyThe normal, happy-path progression — Pre-Check succeeding leads to Restart
On FailureFailedError-handling paths — Restart failing leads to Rollback
AlwaysCompleted, regardless of outcomeSteps that should run no matter what happened before — e.g., a final "Notify team" node that should fire whether the workflow succeeded or hit the rollback path
▲

A node can have multiple outgoing links of different types simultaneously — e.g., Restart can have both an On Success link to Validate and an On Failure link to Rollback. Both edges exist in the graph at once; only the one matching the actual outcome fires for any given run.

Concept

Variable & Credential Flow Through a Workflow

Answering Sara's question directly: a Survey attached at the Workflow level (not on each individual Job Template node) is answered exactly once, at launch. Those answers become extra variables available to every node in the workflow — this is precisely the mechanism, and precisely why today's design moves the survey up from the individual Job Template to the Workflow Job Template itself.

Workflow launch
    |
    | operator answers ONE survey: service_name, change_ticket, etc.
    v
Workflow-level extra_vars established
    |
    +-- Pre-Check node uses {{ service_name }}
    +-- Restart node uses {{ service_name }}
    +-- Validate node uses {{ service_name }}
    +-- Rollback node uses {{ service_name }}
        (all four nodes see the SAME answers — asked once)

Credentials, by contrast, are still attached per node (per underlying Job Template) — the workflow doesn't have its own single credential that overrides each node's own. Each node continues using whatever Credential its own Job Template definition specifies, exactly as it would if launched standalone.

Build

Designing the Restart Workflow

Four Job Templates, most reusing existing patterns, one genuinely new:

NodeJob TemplateNew or existing?Purpose
Pre-CheckLinux — Service Health Pre-CheckNew (built below)Confirm the service exists and is not already in a broken state before touching it
RestartLinux — Restart ServiceExisting (Projects 1, 8, 9)The actual restart action
ValidateLinux — Service Health Pre-CheckReusedThe same health check, run again post-restart to confirm success — reusing one template for two different graph positions
RollbackLinux — Service Rollback NotifyNew (built below)Best-effort remediation attempt plus mandatory team notification if the restart failed
playbooks/service-health-check.yml
---
- name: Confirm a service exists and report its current health
  hosts: rhel_web
  gather_facts: false
  vars:
    service_name: "httpd"

  tasks:
    - name: Gather current service facts
      ansible.builtin.service_facts:

    - name: Fail if the service isn't known to systemd at all
      ansible.builtin.fail:
        msg: "Service {{ service_name }} does not exist on {{ inventory_hostname }} — unsafe to proceed."
      when: (service_name + '.service') not in ansible_facts.services

    - name: Report current state
      ansible.builtin.debug:
        msg: "{{ service_name }} on {{ inventory_hostname }} is currently {{ ansible_facts.services[service_name + '.service'].state }}"
playbooks/service-rollback-notify.yml
---
- name: Best-effort rollback attempt and mandatory team notification
  hosts: rhel_web
  gather_facts: false
  vars:
    service_name: "httpd"

  tasks:
    - name: Attempt to start the service again (best effort)
      ansible.builtin.systemd:
        name: "{{ service_name }}"
        state: started
      ignore_errors: true
      register: rollback_attempt

    - name: Report rollback outcome clearly for the notification layer
      ansible.builtin.debug:
        msg: >
          ROLLBACK {{ 'SUCCEEDED' if rollback_attempt is succeeded else 'FAILED — MANUAL INTERVENTION REQUIRED' }}
          for {{ service_name }} on {{ inventory_hostname }}
▲

Rollback is best-effort, not a guarantee — say so explicitly, including in the automation itself. ignore_errors: true lets the rollback node report its own outcome clearly rather than the workflow simply failing again with no useful signal — but a rollback that itself fails must be loudly, unambiguously flagged, which is exactly what the notification message is designed to do.

Building the Workflow Job Template

UI

  1. First create the two new Job Templates (Linux — Service Health Pre-Check, Linux — Service Rollback Notify) following the exact same pattern as Project 7 — Inventory, Project, Credential, Timeout, Concurrent Jobs off, Labels.
  2. Automation Execution → Templates → Create Workflow Job Template.
  3. Name: Linux — Governed Service Restart, Organization: Banking Automation.
  4. Save, then click Visualizer to open the graph editor.
  5. Click the Start node's + → select Job Template Linux — Service Health Pre-Check → link type defaults to On Success from Start (Start always proceeds to its first node).
  6. From Pre-Check, click + on the Success path → select Linux — Restart Service.
  7. From Restart, add two links: Success → Linux — Service Health Pre-Check (reused, as Validate); Failure → Linux — Service Rollback Notify.
  8. Save the graph. Validate: the Visualizer should show the exact shape from Fig 12.1 (minus the separate "Notify team" node, since notification is embedded in the Rollback template itself for this design).
  9. Grant Linux Operations Team Execute on the Workflow Job Template itself (a separate RBAC grant from any of the individual node templates) — Operators only need Execute on the workflow, not on each underlying node template directly.

ANSIBLE

governed_restart_workflow.yml
- name: Create the two new supporting job templates
  awx.awx.job_template:
    name: "{{ item.name }}"
    job_type: run
    inventory: "Linux Servers"
    project: "linux-ops-automation-prod"
    playbook: "{{ item.playbook }}"
    execution_environment: "Default execution environment"
    credentials: ["Linux SSH Key"]
    timeout: 180
    allow_simultaneous: false
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  loop:
    - { name: "Linux — Service Health Pre-Check", playbook: "playbooks/service-health-check.yml" }
    - { name: "Linux — Service Rollback Notify", playbook: "playbooks/service-rollback-notify.yml" }

- name: Create the Workflow Job Template
  awx.awx.workflow_job_template:
    name: "Linux — Governed Service Restart"
    organization: "Banking Automation"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Define the full workflow node graph
  awx.awx.workflow_job_template_node:
    workflow_job_template: "Linux — Governed Service Restart"
    unified_job_template: "{{ item.template }}"
    identifier: "{{ item.id }}"
    success_nodes: "{{ item.on_success | default([]) }}"
    failure_nodes: "{{ item.on_failure | default([]) }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  loop:
    - id: precheck
      template: "Linux — Service Health Pre-Check"
      on_success: [restart]
    - id: restart
      template: "Linux — Restart Service"
      on_success: [validate]
      on_failure: [rollback]
    - id: validate
      template: "Linux — Service Health Pre-Check"
    - id: rollback
      template: "Linux — Service Rollback Notify"

- name: Grant Linux Operations Execute on the workflow itself
  awx.awx.role:
    team: "Linux Operations"
    role: execute
    workflow_job_templates: "Linux — Governed Service Restart"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
◆

Note the node identifier field — a short internal name for each node used purely to wire the graph together within this Ansible definition (precheck, restart, etc.), separate from the underlying Job Template's own name. This lets the same Job Template appear at multiple graph positions (as Linux — Service Health Pre-Check does, for both precheck and validate) without ambiguity.

The Workflow-Level Survey

Move the survey from Project 8's individual Job Template up to this Workflow Job Template — this directly resolves Sara's "will I fill this out twice" concern.

ANSIBLE

workflow_survey.yml
- name: Attach the survey at the workflow level, not per-node
  awx.awx.workflow_job_template:
    name: "Linux — Governed Service Restart"
    survey_enabled: true
    survey_spec:
      name: "Governed Restart Survey"
      description: "Answered once; available to every node in the workflow."
      spec:
        - question_name: "Which service should be restarted?"
          variable: service_name
          type: multiplechoice
          choices: "httpd\nsshd\nchronyd"
          required: true
        - question_name: "Change ticket number"
          variable: change_ticket
          type: text
          min: 10
          max: 10
          required: true
        - question_name: "Confirm production impact"
          variable: confirm_production
          type: multiplechoice
          choices: "Yes, I understand this affects production\nNo — cancel"
          required: true
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
◆

The individual "Linux — Restart Service" Job Template's own survey (Project 8) can now be left in place as a fallback for direct/standalone launches, or removed if the team decides the workflow is now the only sanctioned way to restart a service — that's a policy decision for Priya and Amit, not a technical requirement either way.

Security Notes For Project 12

■

RBAC on a Workflow Job Template is separate from RBAC on its constituent node templates. Granting a Team Execute on the workflow does not automatically grant them any direct access to the underlying Job Templates — this is a feature, not a gap: Operators can run the governed sequence end-to-end without ever needing standalone access to, say, the Rollback template directly.

▲

A rollback path is a second production-impacting action, not a safety net that removes risk. Give the Rollback node the same scrutiny (Timeout, Concurrent Jobs, Credential scoping) as any other node — a rollback playbook with a bug is just as capable of causing harm as the original action it's meant to remediate.

Run It — Production Incident

Incident: The Validate Node Checked the Wrong Service

Sara Khan

"I ran the workflow to restart sshd. Pre-Check and Restart both said sshd, but Validate's output talked about httpd instead."

StageWhat you do
OBSERVETwo nodes (Pre-Check, Restart) correctly used sshd; the reused Validate node — the same underlying template as Pre-Check — used httpd instead, despite both nodes belonging to the same workflow run.
COLLECT EVIDENCEOpen the workflow run's detail view and inspect each node's individual job's recorded extra_vars. Pre-Check and Restart both show service_name: sshd. Validate shows service_name: httpd.
ISOLATE FAILUREThe Linux — Service Health Pre-Check Job Template itself still has its own hard-coded playbook default (service_name: "httpd") from before it was reused as the Validate node — and workflow-level survey answers don't automatically override a node's own template-level defaults unless the node is explicitly configured to inherit/prompt for them at launch.
CHECK DEPENDENCIESCheck the workflow node's configuration for a setting controlling whether it prompts for (inherits) the workflow's survey variables versus always using its own Job Template's defaults — this varies by RHAAP version's exact node configuration options.
IDENTIFY ROOT CAUSEThe Validate node was added to the graph without explicitly enabling variable inheritance from the workflow launch — so it silently fell back to its own template's hard-coded default instead of the operator's actual survey answer.
FIXUpdate the Validate node's configuration to prompt for (inherit) the workflow's extra_vars, ensuring service_name flows through consistently to every node, not just the ones configured by default to expect it.
VALIDATERe-run the workflow with sshd selected and confirm all four relevant nodes' recorded extra_vars now show sshd consistently.
PREVENT RECURRENCEAdd "confirm every reused node correctly inherits workflow-level survey variables" to the Job Template Governance checklist (Project 9) as a workflow-specific line item — this is a new failure mode this course hadn't encountered before workflows existed.
◆

The general lesson: moving a survey to the workflow level (solving Sara's original "twice" concern) introduces a new, non-obvious dependency — every node must be correctly configured to actually receive those answers. "It's defined at the workflow level" is necessary but not sufficient; each node's own inheritance setting still has to be checked.

Practice

Interview Preparation

Q1. What's the difference between manually launching several Job Templates in sequence and building a Workflow Job Template?
A workflow encodes the sequencing and branching logic — Success/Failure/Always paths — as a real, enforced graph, so decisions like "only restart if the pre-check passes" happen automatically and consistently, rather than depending on an operator remembering the correct manual sequence and making the right judgment call every time.
Q2. Explain the three workflow link types.
On Success fires when the parent node completed successfully; On Failure fires when it failed; Always fires regardless of outcome — commonly used for a final step, like a notification, that should run no matter which path the workflow took.
Q3. Where should a Survey live if you want operators to answer it only once for a multi-step process?
At the Workflow Job Template level rather than on an individual node's Job Template — but every node still needs to be explicitly configured to inherit those workflow-level answers, or it will silently fall back to its own template's defaults instead.
Follow-up: "What's the risk if a node isn't configured to inherit correctly?" — It can silently use stale or default variable values instead of the operator's actual input, producing inconsistent behavior across nodes that all appear to belong to the same governed run.
Q4. How does RBAC work differently for a Workflow Job Template versus its underlying node templates?
They're independent — granting Execute on the workflow doesn't grant any access to the individual node templates directly. This lets Operators run an entire governed sequence without needing standalone access to sensitive nodes like a rollback template.
Q5. Why should a Rollback node get the same scrutiny (timeout, concurrency, credentials) as any other production Job Template?
Because it's still a real, production-impacting action — a buggy or misconfigured rollback playbook can cause just as much harm as the original failure it's meant to remediate, so it shouldn't be treated as an automatically-safe afterthought.
