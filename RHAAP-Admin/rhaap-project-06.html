Concept

How Credential Injection Really Works

Recall Project 1's execution flow: the container never has plaintext access to the RHAAP database. Here's the actual mechanism, one level deeper.

1. RHAAP database stores the credential's secret material
   ENCRYPTED AT REST (using a platform-managed encryption key)
        |
2. At job launch time, the Controller decrypts the secret
   in memory — never written to disk in plaintext on the
   Controller itself
        |
3. The decrypted secret is passed into the Execution Environment
   container via one of two mechanisms, depending on credential type:
        a) as a short-lived, in-memory file mounted into the
           container's filesystem (e.g. an SSH private key file)
        b) as an environment variable inside the container process
           (defined per credential type's "injector" configuration)
        |
4. Ansible Runner uses it for the duration of the job only
        |
5. Container is destroyed after the job — the mounted file/env var
   is destroyed with it. Nothing persists on the execution node.
Fig 6.1 — the secret's entire lifetime as plaintext is: decrypted in Controller memory → passed into one container → destroyed with that container.
◆

This is exactly why no role — not even Admin — can "view" a credential's secret after saving it. The UI/API simply never exposes a read path for the decrypted value; the only operations available are "use it" (delegated to a job) and "replace it" (overwrite with a new secret). This isn't a permission you're missing — it's a capability that doesn't exist for anyone, by design.

Build

Ansible Vault Credentials

Sara's use case: an encrypted connection string, committed to Git as an encrypted !vault block, decrypted only at execution time.

group_vars/prod_db/vault.yml (committed to Git, safely encrypted)
db_connection_string: !vault |
          $ANSIBLE_VAULT;1.1;AES256
          62383934656536623765616...(encrypted content, safe to commit)...

UI

  1. Automation Execution → Credentials → Create Credential.
  2. Name: Linux Ops Vault Password, Credential Type: Vault.
  3. Vault Password: the password used to originally encrypt the file with ansible-vault encrypt.
  4. Optional: Vault Identifier — set this if the team uses multiple vault IDs (e.g. separate passwords per environment); leave blank for a single default vault.
  5. Save, then attach this credential to the relevant Job Template alongside the existing Machine credential — a Job Template can hold multiple credentials of different types simultaneously.

ANSIBLE

vault_credential.yml
- name: Create the Linux Operations vault credential
  awx.awx.credential:
    name: "Linux Ops Vault Password"
    organization: "Banking Automation"
    credential_type: "Vault"
    inputs:
      vault_password: "{{ lookup('env', 'VAULT_PW') }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true

- name: Attach both Machine and Vault credentials to the job template
  awx.awx.job_template:
    name: "Linux — Restart Service"
    credentials:
      - "Linux SSH Key"
      - "Linux Ops Vault Password"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
◆

Answering Amit directly: yes, this works exactly as the team is used to from raw Ansible — the only change is that the vault password itself now lives in a RHAAP Credential instead of a local file or environment variable on someone's laptop, which is strictly safer and removes "who has the vault password file" as an informal, untracked access list.

Credential Ownership & Cross-Template Linking

Answering Priya's question: a single Credential object can be attached to multiple Job Templates — this is normal and often correct (e.g. the same Linux SSH Key used by both a restart-service template and a patch-compliance template, since both target the same hosts with the same account). The real question isn't "is this allowed," it's "does this widen the blast radius appropriately."

Credential: "Linux SSH Key"
      |
      +-- used by --> Job Template: "Linux — Restart Service"
      |
      +-- used by --> Job Template: "Linux — Patch Compliance Check"  (new)

Blast radius if this credential is ever compromised or misused:
      BOTH job templates' target hosts — same as if it were one,
      because they already share the same target hosts and account.
Fig 6.2 — sharing a credential is fine when the templates already share the same trust boundary (same hosts, same account). It becomes a problem when templates with different trust boundaries start sharing one credential just for convenience.
▲

The check to actually run: before reusing a Credential on a new Job Template, ask "do these two templates already target the same hosts, using the same intended account?" If yes, sharing is fine and reduces credential sprawl. If no — e.g. reusing a production credential on a template meant for a different, lower-trust audience — create a separate Credential instead, even if it means storing the same underlying secret twice. Isolation, not convenience, wins that trade-off.

# which Job Templates reference this credential — always check this
# before attaching a credential somewhere new, so you know the current
# blast radius before you widen it.

A Real Rotation Strategy

Priya wants a process, not a scramble. Design it as a checklist tied to Security's rotation calendar:

StepWhenWho
Security notifies platform team of upcoming key rotationT-3 weeks (per Security's existing calendar)Security team → Platform team
Platform team identifies every Credential object referencing the affected key/accountT-2 weeksYou — using the credential cross-reference check above
New key generated; both old and new keys valid on target hosts simultaneously (overlap window)T-1 weekSecurity + Linux Operations (dual-key overlap is a standard, safe rotation pattern)
Update the RHAAP Credential object(s) with the new key, during the overlap windowT-1 week, scheduled maintenance slotYou, via Ansible for a repeatable, logged change
Validate: launch each affected Job Template with Limit against one hostImmediately after the updateYou
Old key revoked from target hosts once validation passesEnd of overlap windowSecurity
rotate_credential.yml
- name: Rotate the Linux SSH Key credential to the new key material
  awx.awx.credential:
    name: "Linux SSH Key"
    organization: "Banking Automation"
    credential_type: "Machine"
    inputs:
      username: svc_ansible
      ssh_key_data: "{{ lookup('file', '/secure/keys/svc_ansible_new.pem') }}"
      become_method: sudo
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true

- name: Validate — launch the restart-service template against one host only
  awx.awx.job_launch:
    job_template: "Linux — Restart Service"
    limit: "lnx-web-01.abcbank.internal"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
  register: validation_launch

- name: Wait and confirm success before declaring rotation complete
  awx.awx.job_wait:
    job_id: "{{ validation_launch.id }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
  register: validation_result

- name: Fail loudly if rotation validation didn't succeed
  ansible.builtin.fail:
    msg: "Credential rotation validation failed — do not close the rotation window yet."
  when: validation_result.status != "successful"
◆

This turns Project 1's incident into a non-event. The overlap window means both old and new keys work during the transition, so the update-and-validate step above can happen calmly, ahead of the old key's revocation — instead of finding out about a rotation from a failed job after the fact.

Security Notes For Project 6

■

No role can ever read back a credential's secret value — this is a platform guarantee, not a permission setting. If someone asks you to "just export the key so I can double check it," the correct answer is that this isn't possible by design, and the correct remedy for a lost/forgotten key is rotation, not retrieval.

▲

Credential sharing is a deliberate trust-boundary decision, not a default convenience. Before attaching an existing Credential to a new Job Template, always check what else already uses it and whether the new use case shares the same trust boundary.

◆

Overlap-window rotation beats "rotate and pray." A rotation process with zero downtime risk always beats a faster one that risks an unplanned outage — this is worth defending to a team that wants to skip the overlap step "to save time."

Interview Preparation

Q1. Walk through exactly how a credential's secret gets from the RHAAP database into a running job.
It's stored encrypted at rest; at launch time the Controller decrypts it in memory and passes it into the Execution Environment container — either as a mounted file (e.g. an SSH key) or an environment variable, depending on the credential type's injector configuration. The container is destroyed after the job, and the secret is destroyed with it. No user, including Admin, can ever read the decrypted value back out through the UI or API.
Q2. How do you use Ansible Vault-encrypted variables inside RHAAP?
Create a Vault-type Credential holding the vault password, attach it to the Job Template alongside any other needed credentials (e.g. Machine) — RHAAP passes the vault password to ansible-playbook at runtime so it can decrypt any !vault-encrypted content the playbook references, exactly as it would locally.
Q3. Is it ever appropriate to attach the same Credential to multiple Job Templates?
Yes, when the templates already share the same trust boundary — same target hosts, same intended account — sharing reduces credential sprawl without meaningfully increasing blast radius. It becomes inappropriate when it's done purely for convenience across templates with different trust boundaries, in which case separate credential objects are the right call even if the underlying secret happens to be the same.
Q4. How would you design a credential rotation process to avoid unplanned job failures?
Use an overlap window where both old and new credentials remain valid on target systems simultaneously; update the RHAAP Credential object during that window, validate with a limited-scope job launch, and only revoke the old credential after validation succeeds — never rotate and revoke in the same step.

Practice Assignment

◆

Lab vs. Enterprise Production: Vault credentials and rotation mechanics are fully practicable on a lab instance. A real enterprise key-rotation calendar and coordination with a separate Security team can't be simulated meaningfully — treat that part conceptually using this project's checklist.

  1. Create a vault-encrypted variable file locally using ansible-vault encrypt, commit it to your lab Git repo, and reference it from a test playbook.
  2. Create a Vault credential in your lab RHAAP instance and attach it to a Job Template alongside a Machine credential; launch and confirm successful decryption.
  3. Simulate a rotation: generate a new SSH key, add it as an additional authorized key on your lab target (don't remove the old one yet), update the Machine Credential to the new key, validate with a limited launch, then remove the old key from the target.
  4. Reproduce the incident: remove the Vault credential from the Job Template, observe the failure, then fix it.
  5. Write a one-page rotation checklist for your own lab setup, modeled on this project's table.
