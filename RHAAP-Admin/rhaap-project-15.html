Dynamic Inventory

Project 5's naming standard and nested groups assumed someone manually adds and removes hosts. That assumption breaks the moment ABC Bank's Linux fleet starts autoscaling. Today, the Inventory queries a real cloud source automatically — new hosts appear, decommissioned ones disappear, with zero manual editing, and Project 5's group/variable discipline still applies on top of it.

Concept

Why Static Inventory Stops Scaling

Static inventory assumption (Project 5)Breaks when...
A host exists until someone manually removes itAutoscaling terminates instances automatically based on load — nobody manually removes anything
Group membership is assigned by a humanNew instances launch faster than any human workflow could keep up with, especially during a scale-out event
The Inventory is a reasonably accurate snapshot of realityAt autoscale, the Inventory is either perpetually stale or requires constant manual babysitting — neither is acceptable
◆

This isn't a rejection of Project 5's design — it's an evolution of it. The nested group structure and variable precedence model from Project 5 stay exactly the same; what changes is how group membership gets populated — automatically, from live cloud metadata, instead of by hand.

Concept

Inventory Sources & Plugins

A Dynamic Inventory Source is a sub-object of an Inventory (alongside any static groups/hosts you keep). It's backed by a plugin — a piece of code that knows how to query a specific external system (AWS, Azure, GCP, VMware, OpenStack, a custom script, and others) and translate its response into Ansible-compatible hosts and groups.

Inventory: "Linux Servers"
   |
   +-- Static Groups (Project 5) — prod_db, stg_web, stg_db
   |     (unchanged; still manually managed — smaller, stable footprint)
   |
   +-- Inventory Source: "AWS — prod_web Autoscaling Group"   <-- NEW
         plugin: amazon.aws.aws_ec2
         credential: AWS Read-Only Cloud Credential
         filters: tag:Team=linux-ops, tag:Environment=production, tag:Role=web
         sync: every 10 minutes (or triggered by a webhook/event, where supported)
Fig 15.2 — dynamic and static coexist in the same Inventory; only the prod_web portion of the fleet, the part that actually autoscales, moves to dynamic sourcing.
Concept

The Sync Model

Similar in spirit to a Project sync (Project 4), an Inventory Source sync queries the external system fresh and reconciles the result into the Inventory's host/group list. Unlike a Project sync, this can run frequently — every few minutes — since querying a cloud API is far cheaper than a full Git clone.

TriggerBehavior
Manual syncSame as a Project's manual sync — useful when testing a new filter/tag configuration
Scheduled sync (Project 10 pattern)ABC Bank's choice: every 10 minutes, frequent enough that autoscaling events reflect in RHAAP promptly without excessive API load
Update on launchAvailable, same trade-off discussion as Project 4's Project sync-on-launch — adds latency to every job launch in exchange for absolute freshness
Build

The Cloud Credential

Exactly like Project 4's Source Control credential principle: this credential only ever needs to list instances — read-only, scoped as narrowly as the cloud provider's IAM system allows.

UI

  1. Automation Execution → Credentials → Create Credential.
  2. Name: AWS Read-Only Cloud Credential, Credential Type: Amazon Web Services.
  3. Access Key / Secret Key: generated from an IAM user or role scoped only to ec2:DescribeInstances and related read-only describe actions — never anything with launch, terminate, or modify permissions.
  4. Save.

ANSIBLE

cloud_credential.yml
- name: Create the read-only AWS credential for dynamic inventory
  awx.awx.credential:
    name: "AWS Read-Only Cloud Credential"
    organization: "Banking Automation"
    credential_type: "Amazon Web Services"
    inputs:
      username: "{{ lookup('env', 'AWS_ACCESS_KEY_ID') }}"
      password: "{{ lookup('env', 'AWS_SECRET_ACCESS_KEY') }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true
■

An overly broad cloud credential here is a far bigger blast radius than a compromised SSH key. A key scoped only to Describe* actions can, at absolute worst, leak information about your infrastructure's existence. A key with launch/terminate/modify permissions attached to the same credential could allow an attacker (or a bug in the plugin configuration) to actually change cloud infrastructure — always verify IAM scoping directly in AWS, not just by trusting the credential's RHAAP-side label.

Build

Building the Inventory Source

UI

  1. Open Linux Servers Inventory → Sources tab → Create Source.
  2. Name: AWS — prod_web Autoscaling Group
  3. Source: Amazon EC2
  4. Credential: AWS Read-Only Cloud Credential
  5. Regions: restrict to the specific AWS region(s) ABC Bank actually operates in — never leave this as "all regions" by default.
  6. Instance Filters / Source Variables: configure the plugin to only return instances tagged Team=linux-ops, Environment=production, Role=web — the exact same boundary Project 5's naming standard already implied, now enforced by the query itself.
  7. Update options: enable Overwrite (so terminated instances are correctly removed, not left stale) and Overwrite Variables.
  8. Save, then click Sync and confirm hosts appear under a new, plugin-generated group structure.

ANSIBLE

prod_web_dynamic_inventory.yml
- name: Create the AWS dynamic inventory source for prod_web
  awx.awx.inventory_source:
    name: "AWS — prod_web Autoscaling Group"
    inventory: "Linux Servers"
    source: ec2
    credential: "AWS Read-Only Cloud Credential"
    source_regions: "ap-south-1"
    overwrite: true
    overwrite_vars: true
    update_on_launch: false
    source_vars:
      filters:
        "tag:Team": "linux-ops"
        "tag:Environment": "production"
        "tag:Role": "web"
      keyed_groups:
        - key: tags.Role
          prefix: "role"
        - key: tags.Environment
          prefix: "env"
      compose:
        ansible_host: public_ip_address
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
Build

Composed Groups & Variables — Recreating Project 5's Structure Automatically

keyed_groups is what recreates Project 5's env_function naming pattern without a human assigning it. Every instance tagged Role=web and Environment=production automatically lands in groups like role_web and env_production — the plugin does the group assignment that used to be a manual Project 5 step.

EC2 instance tags:              -->    RHAAP dynamic groups (auto-generated):
  Team: linux-ops                        role_web
  Environment: production                env_production
  Role: web

compose: ansible_host: public_ip_address
  -->  ensures Ansible connects using the instance's live public IP,
       not a stale value that might change on instance replacement
◆

The naming standard from Project 5 didn't disappear — it moved into the cloud tagging convention. "Tag every instance with Team, Environment, and Role" is now the enforcement point, and it's a conversation with whoever manages the cloud provisioning/Terraform for these instances, not something RHAAP can enforce on its own.

Security Notes For Project 15

■

Scope the cloud credential's IAM permissions as tightly as the provider allows, and verify it on the cloud side, not just in RHAAP. RHAAP has no way to know if the underlying AWS credential is actually scoped correctly — that verification happens in IAM, and it's your responsibility to confirm it, the same discipline as the read-only Git deploy key from Project 4.

▲

The Overwrite option is powerful and slightly dangerous. It removes any host/group in the Inventory that the source no longer reports — correct behavior for a fully dynamic group, but if a filter is misconfigured and returns zero results, Overwrite could wipe out an entire group's membership unexpectedly. Test filter changes with Overwrite temporarily disabled before trusting a new configuration.

◆

Restrict Regions explicitly. Leaving a cloud inventory source scanning "all regions" both slows every sync down and — more importantly — could surface unrelated infrastructure from other teams' AWS usage into a Job Template's potential target scope if tags/filters aren't airtight.

Run It — Production Incident

Incident: New Instances Never Showed Up

Sara Khan

"We scaled out to handle load this morning — three new web instances launched — but the compliance check this afternoon only covered the original two. The new ones aren't in RHAAP at all."

StageWhat you do
OBSERVEThe Inventory Source's last successful sync timestamp is from before the scale-out event — either the scheduled sync hasn't run recently, or it ran and still didn't pick up the new instances.
COLLECT EVIDENCEManually trigger a sync and check its job output — it completes successfully but still reports the same two hosts.
ISOLATE FAILURESince a manual sync ran cleanly but still missed the new instances, this points at the filter/tag configuration itself, not a scheduling or connectivity problem.
CHECK DEPENDENCIESCheck the actual tags on the new EC2 instances directly in AWS — you find the provisioning automation (Terraform, managed by a different team) tagged them environment: production (lowercase) instead of Environment: production as the filter expects.
IDENTIFY ROOT CAUSEA tag-casing mismatch between the cloud provisioning process and the Inventory Source's filter configuration — the filter is doing exactly what it's configured to do; the underlying tags simply don't match what it's looking for.
FIXEither correct the filter to match the actual tag casing in use, or — the more durable fix — coordinate with the provisioning team to standardize tag casing going forward, and document the required exact tag keys/casing in this project's repository reference file.
VALIDATERe-sync and confirm all five instances (two original plus three new) now appear correctly grouped.
PREVENT RECURRENCEPublish the exact required tag keys and casing as a hard requirement for any team provisioning infrastructure destined for RHAAP-managed automation — add it to the platform team's onboarding documentation so the next provisioning team doesn't hit the same mismatch.
◆

The diagnostic habit worth keeping: when a dynamic source "misses" hosts, a clean, successful sync with a wrong result almost always means the filter criteria don't match reality — check the actual tags/metadata on the cloud side directly, rather than assuming the sync itself is broken.

Practice

Interview Preparation

Q1. Why does a static inventory stop being viable for autoscaling infrastructure?
Static inventories assume a human adds and removes hosts as they're provisioned and decommissioned. Autoscaling launches and terminates instances automatically, often faster than any manual process could track, making a static inventory either perpetually stale or an unsustainable manual burden.
Q2. How do keyed_groups in a dynamic inventory source relate to a manually-designed static group structure like Project 5's?
keyed_groups automatically derives group membership from cloud metadata (like tags), recreating the same kind of environment/function group structure a human would otherwise assign by hand — the group design principle stays the same; only the mechanism populating it changes.
Q3. What credential scope is appropriate for a dynamic cloud inventory source?
Read-only, describe/list-level permissions only — never anything capable of launching, terminating, or modifying cloud resources, since the credential's only real job is enumerating what already exists.
Q4. What's a risk specific to the "Overwrite" option on an inventory source sync?
If a filter is misconfigured and returns fewer results than expected (including zero), Overwrite will remove hosts/groups the source no longer reports — which could unexpectedly wipe out a group's membership rather than just failing to add new hosts. Testing filter changes with Overwrite temporarily disabled reduces this risk.
Q5. New cloud instances aren't appearing in the Inventory after a sync that completes successfully. What's your investigation approach?
Since the sync itself succeeded, focus on whether the filter/tag criteria actually match the new instances' real metadata — a successful sync with an incomplete result is almost always a filter/tag mismatch rather than a connectivity or scheduling problem.

Practice Assignment

◆

Lab vs. Enterprise Production: a real dynamic inventory source requires an actual cloud account (a free-tier AWS/Azure/GCP account is sufficient for a couple of test instances) — this genuinely cannot be faithfully simulated with only local VMs, unlike most of this course's exercises so far.

  1. Launch two or three small, free-tier cloud instances tagged consistently (pick your own tag scheme, document it).
  2. Create a scoped, read-only credential in your cloud provider's IAM system, and register it in your lab RHAAP instance.
  3. Build the Inventory Source with filters matching your tags, and sync it — confirm your instances appear correctly grouped.
  4. Deliberately introduce a tag mismatch (rename a tag key on one instance) and observe it silently disappear from the expected group on the next sync — reproducing this project's incident directly.
  5. Fix the tag and confirm the instance reappears correctly on the next sync.
