Concept

Why a Custom Credential Type

RHAAP ships with built-in Credential Types for common cases — Machine, Source Control, Vault, cloud providers, Container Registry. ABC Bank's ITSM API doesn't fit any of them: it needs exactly four fields, in a shape no built-in type anticipates. A Custom Credential Type lets you define precisely that shape once, and every future Credential created from it gets the same fields, the same secret handling, and the same injection behavior — without inventing a one-off workaround (like stuffing values into a Vault-type credential's password field, which would work mechanically but obscure intent and lose RHAAP's structured field validation).

Concept

Input Configuration

The input configuration defines what fields a Credential of this type has — their names, types, labels, and, critically, which ones are secret.

Field propertyPurpose
idThe internal field name, referenced later by the injector configuration
typestring (or other supported types) — the field's data type
labelWhat's shown to the person filling in the field in the UI
secret: trueMasks the field's value in the UI after saving, exactly like a password field — this is the mechanism that directly satisfies Priya's requirement
Concept

Injector Configuration

The injector configuration defines how each input field's value actually reaches the running job — as an environment variable, as an extra variable, or written into a file the playbook can reference by path. This is the same underlying mechanism explained in Project 6's injection deep-dive, now under your own explicit control instead of RHAAP's built-in logic.

Input field: api_token (secret: true)
        |
        | injector maps it to...
        v
Environment variable: ITSM_API_TOKEN
        |
        | available inside the Execution Environment container
        | for the duration of the job only
        v
Playbook reads it via: lookup('env', 'ITSM_API_TOKEN')
        |
        | never printed, never logged, never in job output

Defining the ITSM Credential Type

UI

  1. Administration → Credential Types → Create Credential Type.
  2. Name: ABC Bank ITSM API
  3. Paste the Input Configuration YAML (below) into that field.
  4. Paste the Injector Configuration YAML (below) into that field.
  5. Save.
Input Configuration
fields:
  - id: api_url
    type: string
    label: "ITSM API URL"
  - id: api_token
    type: string
    label: "API Token"
    secret: true
  - id: client_id
    type: string
    label: "Client ID"
  - id: client_secret
    type: string
    label: "Client Secret"
    secret: true
required:
  - api_url
  - api_token
  - client_id
  - client_secret
Injector Configuration
env:
  ITSM_API_URL: "{{ api_url }}"
  ITSM_API_TOKEN: "{{ api_token }}"
  ITSM_CLIENT_ID: "{{ client_id }}"
  ITSM_CLIENT_SECRET: "{{ client_secret }}"
Explain the Jinja templating in the injector

Each value on the right ({{ api_url }}, etc.) references the input field's id from the Input Configuration — RHAAP substitutes the actual stored value (decrypted in memory, exactly per Project 6's mechanism) at job launch time. The keys on the left (ITSM_API_URL, etc.) are the environment variable names the playbook will actually see inside the container. These two names don't have to match — and that mismatch is exactly this project's incident below.

ANSIBLE

itsm_credential_type.yml
- name: Define the ABC Bank ITSM API custom credential type
  awx.awx.credential_type:
    name: "ABC Bank ITSM API"
    kind: cloud
    inputs:
      fields:
        - id: api_url
          type: string
          label: "ITSM API URL"
        - id: api_token
          type: string
          label: "API Token"
          secret: true
        - id: client_id
          type: string
          label: "Client ID"
        - id: client_secret
          type: string
          label: "Client Secret"
          secret: true
      required: [api_url, api_token, client_id, client_secret]
    injectors:
      env:
        ITSM_API_URL: "{{ '{{' }} api_url {{ '}}' }}"
        ITSM_API_TOKEN: "{{ '{{' }} api_token {{ '}}' }}"
        ITSM_CLIENT_ID: "{{ '{{' }} client_id {{ '}}' }}"
        ITSM_CLIENT_SECRET: "{{ '{{' }} client_secret {{ '}}' }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
◆

The {{ '{{' }} ... {{ '}}' }} escaping in the Ansible task is necessary because the injector's own Jinja placeholders ({{ api_url }}) would otherwise be evaluated by this playbook's templating engine instead of being passed through literally for RHAAP to evaluate later, at job launch time. This is a real, easy-to-miss detail when writing credential type definitions as Ansible-managed code.

Creating a Credential From It

ANSIBLE

itsm_credential.yml
- name: Create the ABC Bank ITSM API credential
  awx.awx.credential:
    name: "ABC Bank ITSM Integration"
    organization: "Banking Automation"
    credential_type: "ABC Bank ITSM API"
    inputs:
      api_url: "https://itsm.abcbank.internal/api/v2"
      api_token: "{{ lookup('env', 'ITSM_API_TOKEN_SECRET') }}"
      client_id: "{{ lookup('env', 'ITSM_CLIENT_ID_SECRET') }}"
      client_secret: "{{ lookup('env', 'ITSM_CLIENT_SECRET_SECRET') }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true

- name: Attach the ITSM credential to the Escalate Incident job template
  awx.awx.job_template:
    name: "Linux — Escalate Incident"
    credentials:
      - "ABC Bank ITSM Integration"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

Updating the Escalation Playbook

playbooks/escalate-incident.yml (updated)
---
- name: Escalate — create a real ITSM ticket and notify the team
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    service_name: "httpd"
    change_ticket: "unknown"

  tasks:
    - name: Create an incident ticket in ABC Bank's ITSM system
      ansible.builtin.uri:
        url: "{{ lookup('env', 'ITSM_API_URL') }}/incidents"
        method: POST
        headers:
          Authorization: "Bearer {{ lookup('env', 'ITSM_API_TOKEN') }}"
          X-Client-Id: "{{ lookup('env', 'ITSM_CLIENT_ID') }}"
          X-Client-Secret: "{{ lookup('env', 'ITSM_CLIENT_SECRET') }}"
        body_format: json
        body:
          title: "Automated rollback failed for {{ service_name }}"
          description: >
            RHAAP automated rollback failed for service '{{ service_name }}'
            (change ticket {{ change_ticket }}). Manual intervention required.
          priority: "high"
          source: "rhaap-linux-ops-automation"
        status_code: 201
      register: itsm_response
      no_log: true
      # no_log suppresses this task's full request/response from job output,
      # since the request headers contain the token/client secret directly —
      # even though they're already masked as Credential inputs, defense in
      # depth means never echoing them into logs a second time via task output.

    - name: Report the created ticket number in job output (safe — no secrets here)
      ansible.builtin.debug:
        msg: "ITSM ticket created: {{ itsm_response.json.ticket_id | default('unknown — check ITSM system directly') }}"
◆

Notice the second task is deliberately not under no_log. Its message contains only the ticket ID — safe, useful output — while the first task's no_log: true specifically protects the request itself, which carries the actual secret headers. Applying no_log too broadly would also hide the useful ticket-ID confirmation; applying it too narrowly would leak the token. This is a deliberate, task-level choice, not a blanket setting.

Security Notes For Project 19

■

Marking a field secret: true in the input configuration is what actually protects it — this is not optional or cosmetic. An unmarked field's value can appear in the UI, in certain API responses, and potentially in job output if a playbook task isn't careful. Every genuinely sensitive field in a Custom Credential Type must be explicitly marked secret; this is the single most important line in the entire definition.

▲

Apply no_log at the task level, deliberately, not as a blanket rule. Over-applying it hides genuinely useful, non-sensitive output (like a confirmation ticket ID); under-applying it risks leaking a secret into job logs even though the Credential itself is properly protected. Review each task individually.

◆

A Custom Credential Type follows the exact same no-retrieval guarantee from Project 6. Once saved, nobody — including Admins — can read the api_token or client_secret values back out through the UI or API. Rotation follows the same overlap-window discipline built in Project 6.

Run It — Production Incident

Incident: The Ticket Never Got Created

Amit Verma, after a deliberate test escalation

"We forced a rollback failure to test the new ITSM integration. The Slack notification fired fine, but no ticket ever showed up in ITSM."

StageWhat you do
OBSERVEThe job itself reported a failure on the "Create an incident ticket" task — so the escalation workflow correctly triggered, but the API call within it failed.
COLLECT EVIDENCEBecause that task uses no_log: true, job output shows only FAILED with no request/response detail — appropriately protecting the secret headers, but making this diagnosis harder by design. You temporarily re-run the same job with no_log removed in a non-production test credential/environment specifically to see the actual error, then restore no_log immediately after.
ISOLATE FAILUREThe actual error: 401 Unauthorized — an authentication failure, not a network or URL problem.
CHECK DEPENDENCIESCompare the injector configuration's environment variable names against exactly what the playbook references — you find the injector was defined with ITSM_CLIENT_SECRET, but an earlier draft of the playbook (copied from a different internal example during development) referenced ITSM_CLIENT_SECRET_KEY instead — a naming mismatch.
IDENTIFY ROOT CAUSEBecause environment variables that don't exist simply resolve to an empty string via lookup('env', ...) rather than raising an error, the playbook silently sent an empty X-Client-Secret header — the ITSM API correctly rejected the request as unauthenticated, but nothing in RHAAP itself flagged the naming mismatch as a configuration error.
FIXCorrect the playbook to reference ITSM_CLIENT_SECRET, matching the injector configuration exactly.
VALIDATERe-run the test escalation and confirm a real ticket now appears in ITSM.
PREVENT RECURRENCEAdd a documented, single source of truth (a comment block at the top of both the credential type definition and the consuming playbook) explicitly listing the exact environment variable names both sides must agree on — and consider a lightweight pre-flight task that fails loudly and explicitly if any expected environment variable is empty, rather than silently sending a blank credential header.
◆

The teaching point: an empty environment variable is a silent failure mode by default in Ansible — lookup('env', 'NAME') doesn't error on a missing variable, it just returns an empty string. When wiring a Custom Credential Type's injector to a playbook, a fail-fast check for unexpectedly empty required variables is worth adding deliberately, precisely because the alternative failure (like this project's 401) can look like a completely unrelated problem.

Practice

Interview Preparation

Q1. When would you build a Custom Credential Type instead of using a built-in one?
When integrating with a system whose authentication shape doesn't match any built-in type — RHAAP's Machine, Source Control, Vault, and cloud types cover common cases, but a bespoke internal API often needs its own specific set of fields, which a Custom Credential Type lets you define explicitly rather than working around with a mismatched built-in type.
Q2. What's the relationship between input configuration and injector configuration?
The input configuration defines what fields a credential has and which are secret; the injector configuration defines how each field's value actually reaches a running job — as an environment variable, extra variable, or file — using Jinja templating that references the input fields by their defined IDs.
Q3. Why is marking a field secret: true important, specifically?
It's the mechanism that actually masks the field's value in the UI after saving and prevents it from being retrievable — without it, a field intended to hold a sensitive value like an API token would be treated as ordinary, visible data.
Q4. How would you decide where to apply no_log: true in a playbook consuming a custom credential's injected values?
Task by task, deliberately — apply it specifically to tasks whose request/response would expose the secret value directly (like an API call carrying a token in its headers), while leaving unrelated, non-sensitive output (like a resulting ticket ID) visible, rather than blanket-suppressing an entire play's output.
Q5. An API call using an injected credential fails with an authentication error, but the credential was definitely entered correctly. What would you check?
Whether the environment variable name the playbook actually references matches exactly what the injector configuration defines — a naming mismatch causes lookup('env', ...) to silently return an empty string rather than erroring, which produces an authentication failure that looks unrelated to the real, underlying configuration problem.

Practice Assignment

◆

Lab vs. Enterprise Production: Custom Credential Types and injectors are fully practicable on a lab RHAAP/AWX instance — for the API target, use any free, publicly available test API (e.g. a mock/echo API service) that accepts a token/header-based request, standing in for ABC Bank's real ITSM system.

  1. Define a Custom Credential Type with at least one secret and one non-secret field, targeting a test API of your choice.
  2. Create a Credential from it and attach it to a test Job Template.
  3. Write a playbook task using the uri module to call your test API using the injected environment variables.
  4. Run it and confirm the call succeeds, with the secret field properly masked in the UI.
  5. Deliberately rename one environment variable in the injector configuration without updating the playbook, reproducing this project's incident — observe the resulting failure and its (likely misleading) error message, then fix it.
  6. Add a fail-fast pre-flight check for empty expected variables, and confirm it now produces a clear, specific error instead of the original confusing one.
