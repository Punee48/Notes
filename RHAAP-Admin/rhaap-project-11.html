Concept

The Notification Model

A Notification Template defines how to send an alert — the channel, the credentials/webhook, the destination. A separate step attaches that template to a specific state (Started, Success, Error) on a specific object (Organization, Project, Job Template, Workflow Job Template). The same Notification Template can be reused across many objects and states.

Notification Template: "Linux Ops Slack Channel"
   |
   +-- attached to: Organization "Banking Automation" -> Error only
   |      (Project 2's org-wide safety net — catches Project sync failures
   |       across every team, regardless of which specific template)
   |
   +-- attached to: Job Template "Linux — Patch Compliance Check" -> Error only
   |      (a job that ran but found non-compliant hosts is Success,
   |       not Error — per Project 7's distinction)
   |
   +-- attached to: Job Template "Linux — Restart Service" -> Success + Error
          (Operators specifically want confirmation a restart worked,
           not just alerts when it fails)
Fig 11.1 — one Notification Template, multiple attachment points, each choosing its own relevant state(s). This is what lets the org-wide net and the template-specific alerts coexist without you duplicating the Slack configuration everywhere.

Match the notification type to the urgency and audience. Email is right for Compliance's audit trail. Slack is right for a team that needs fast visibility during their working hours. Concept

Inheritance — How the Layers Coexist

Answering Priya's fatigue concern directly: notification state selection per attachment point is the actual control. The Organization-level notification from Project 2 only fires on Project sync Error — it says nothing about individual Job Template runs. Job-Template-level notifications are configured independently, per template, per state. Nothing here causes duplicate alerts unless you deliberately attach the same template to the same state at multiple levels for the same event — which you won't, if each attachment point is scoped to what it's actually meant to catch.

LevelCatchesState(s) to attach, per ABC Bank's design
OrganizationProject sync failures, platform-wide issues not tied to one templateError only (Project 2)
Job Template — Patch Compliance CheckThe check itself failing to run (not "found non-compliant hosts," which is a successful run)Error only (Project 7)
Job Template — Restart ServiceEvery operator-initiated restart, success or failure — Operators specifically asked for confirmationSuccess + Error (today's build)
Build

Slack Notification Template

RHAAP's Slack notification type uses a Slack Incoming Webhook — a per-channel URL that accepts a simple HTTP POST. Generate this on the Slack side first.

  1. In Slack, create (or reuse) an app with the Incoming Webhooks feature enabled, scoped to the Linux Operations channel.
  2. Copy the generated webhook URL — treat it as a secret; anyone with this URL can post to the channel.

UI

  1. Administration → Notifications → Create Notification Template.
  2. Name: Linux Ops Slack Channel, Organization: Banking Automation.
  3. Type: Slack.
  4. Token: paste the Incoming Webhook URL.
  5. Channel: confirm/override the channel if the webhook supports posting to more than one.
  6. Save.

ANSIBLE

slack_notification.yml
- name: Create the Linux Operations Slack notification template
  awx.awx.notification_template:
    name: "Linux Ops Slack Channel"
    organization: "Banking Automation"
    notification_type: slack
    notification_configuration:
      token: "{{ lookup('env', 'SLACK_WEBHOOK_URL') }}"
      channels: ["#linux-operations"]
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true

Custom Message Content

By default, notifications carry a generic message. RHAAP lets you customize the message per notification state using Jinja-style templating against job metadata — this is how you surface the change ticket and the specific failed task Amit asked for.

UI — customize messages on the Job Template's Notifications tab

  1. Open Linux — Restart Service → Notifications tab.
  2. Enable Linux Ops Slack Channel for both Success and Error.
  3. Click the message customization option (often a small edit/pencil icon next to the notification state) to override the default message body.
  4. For Success, set a message using job template variables (exact Jinja variable names vary slightly by RHAAP version — verify against your instance's message customization reference).
  5. For Error, include the failed task name where the templating engine exposes it.
Success message template
✅ *{{ job.name }}* completed successfully
Service: {{ job.extra_vars.service_name }}
Change Ticket: {{ job.extra_vars.change_ticket }}
Launched by: {{ job.launched_by.name }}
Duration: {{ job.elapsed }}s
<{{ job.url }}|View job output>
Error message template
🔴 *{{ job.name }}* FAILED
Service: {{ job.extra_vars.service_name }}
Change Ticket: {{ job.extra_vars.change_ticket }}
Failed at task: {{ job.job_explanation | default('see job output') }}
Launched by: {{ job.launched_by.name }}
<{{ job.url }}|Investigate now>
#linux-operations
✅ Linux — Restart Service #4821 completed successfully
Service: httpd  |  Change Ticket: CHG-042871
Launched by: s.khan  |  Duration: 6.3s
#linux-operations

ANSIBLE — attach with custom messages

wire_notifications.yml
- name: Attach Slack notifications with custom messages to restart-service
  awx.awx.job_template:
    name: "Linux — Restart Service"
    notification_templates_success:
      - "Linux Ops Slack Channel"
    notification_templates_error:
      - "Linux Ops Slack Channel"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

# template's messages field or the job template's notification
# customization endpoint, depending on RHAAP version — verify the
# exact field name (e.g. `messages` on the notification template
# object) against your instance's API schema before scripting it,
# since this is one of the areas most likely to differ between
# RHAAP/AWX versions.
▲

Version-specific caution, stated explicitly per this course's rules: the exact mechanism and available Jinja variables for message customization have changed across RHAAP/AWX releases. Always check your specific instance's notification message customization documentation before assuming the variable names above are exact — the concepts (job metadata available for templating, per-state message override) are stable; the precise field names are not guaranteed to be.

Security Notes For Project 11

■

A Slack webhook URL is a bearer secret — anyone who has it can post to the channel as your integration. Store it the same way you'd store any credential: via no_log: true in Ansible, never committed to Git in plaintext, and rotated if it's ever accidentally exposed (e.g. pasted into the wrong chat).

▲

Never let a Password-type survey answer (Project 8) flow into a notification message. Even though the UI masks a Password field's display, message templating pulls from the underlying extra_vars — a message template naively including a raw password-type variable could post a secret directly into a Slack channel. Only reference variables you've deliberately reviewed for a notification message.

◆

Notification fatigue is a real security concern, not just an annoyance. A channel that's muted because it's too noisy is a channel that won't be watched during an actual incident — Priya's instinct to be selective about states per template is a genuine control, not just tidiness.

Run It — Production Incident

Incident: The Slack Notifications Went Silent

Amit Verma, two weeks after launch

"I don't think we've gotten a Slack notification in a few days, even though I know jobs have run. Is something broken?"

StageWhat you do
OBSERVEConfirm jobs genuinely did run successfully in that window (checked via the RHAAP UI directly) — so this is a notification-delivery problem, not a platform outage.
COLLECT EVIDENCEOpen the Notification Template's own job/notification history in RHAAP — most versions log each individual notification attempt and its result, separate from the job it's attached to.
ISOLATE FAILUREThe notification history shows repeated delivery failures with an HTTP 404 or "invalid_token"-style response from Slack's side, not a RHAAP-side error.
CHECK DEPENDENCIESCheck the Slack app/webhook configuration directly — you find the Slack workspace admin rotated/regenerated the app's webhook as part of an unrelated Slack app review, without knowing RHAAP depended on the old URL.
IDENTIFY ROOT CAUSEAn external, unrelated change (Slack-side webhook rotation) silently broke the integration — the RHAAP side had no reason to detect this on its own until someone specifically checked notification history.
FIXGenerate a new Incoming Webhook URL in Slack, and update the Notification Template's Token field with it.
VALIDATETrigger a test notification (many notification templates support a "Test" button in the UI) or launch a real job with Limit against one host, and confirm the message actually appears in the channel.
PREVENT RECURRENCEAsk Slack workspace admins to notify the platform team before rotating any webhook RHAAP depends on, and add a periodic notification-delivery check (a scheduled test message, using the Project 10 scheduling pattern) so silent failures surface within a day instead of "a few days" of nobody noticing.
◆

The diagnostic habit worth keeping: when a notification "goes silent," don't assume the automation itself failed — check the notification template's own delivery history first, since that's a much narrower, faster place to isolate the problem than re-investigating every job that should have triggered it.

Practice

Interview Preparation

Q1. What's the relationship between a Notification Template and the object it's attached to?
The Notification Template defines the delivery mechanism — channel, credentials/webhook, destination. It's attached separately, per object and per state (Started/Success/Error), which lets one reusable template serve many different alerting needs across the platform without duplicating the underlying integration configuration.
Q2. How would you prevent notification fatigue while still giving teams useful visibility?
Be deliberate about which states are attached at which level — an org-wide safety net should catch only genuinely cross-cutting failures (like Project sync errors), while template-specific notifications should be scoped to what that specific team actually needs to see, and not every state for every template by default.
Q3. What's a security concern specific to custom notification message templating?
A naively written message template could accidentally include a sensitive variable — for example, a Password-type survey answer — directly in a Slack message or email body, since message templating pulls from the job's actual extra_vars regardless of how they're masked for display elsewhere in the UI.
Q4. A team reports they haven't received expected notifications in several days, but the underlying jobs ran fine. How do you investigate?
Check the Notification Template's own delivery/notification history first — most RHAAP versions log each individual delivery attempt separately from the job itself — to isolate whether RHAAP attempted delivery and failed (often an external, credential/webhook-side issue) versus never attempting it at all (a configuration/attachment issue).

◆

Lab vs. Enterprise Production: Slack notifications are fully practicable with a free Slack workspace and a test channel of your own — you don't need ABC Bank's actual infrastructure to build and test this end-to-end.

  1. Create a Slack workspace (or reuse an existing one) and generate an Incoming Webhook for a test channel.
