Organizations, Deeper

One Organization or Many? A Real Decision Framework

Priya's question — does Windows Operations get its own Organization — has a real answer, not a preference. Use this framework:

Ask thisIf YES → separate OrganizationIf NO → same Organization, new Team
Do they need completely separate credential/secret boundaries with zero shared visibility, even between admins?Separate OrgSame Org
Do they report through an entirely different business unit with its own budget/governance owner?Separate OrgSame Org
Will they largely reuse the same Execution Environments, notification integrations, and platform conventions?—Same Org (Team)
Is the only real difference "which OS they automate"?—Same Org (Team) — this is Windows Operations' case

Windows Operations reports to the same platform-engineering governance as Linux Operations, shares the bank's EE standards, and doesn't need a harder secret boundary than Team-level RBAC already provides — a new Team inside Banking Automation, not a new Organization.

Users, Deeper

User Types and Where Identity Really Comes From

Project 1 created local users to keep focus on RBAC mechanics. In production, ABC Bank will not manage 400 engineers' passwords by hand inside RHAAP — identity comes from the enterprise IdP.

Auth sourceHow it worksWhen ABC Bank uses it
LocalUsername/password stored and managed inside RHAAPBreak-glass/emergency admin accounts only — a handful, tightly controlled
LDAP/ADRHAAP authenticates against the bank's Active Directory; can auto-map AD groups to RHAAP Teams/OrganizationsCommon in on-prem enterprise setups — likely ABC Bank's primary method
SAML / OIDC (SSO)RHAAP delegates login to a corporate identity provider (Okta, Azure AD, etc.)Preferred where the bank already runs enterprise SSO everywhere else
▲

Why this matters for today's project: even once external auth is configured, the RBAC model you build — Teams, Roles, object-level grants — doesn't change. External auth changes how a user proves who they are; RBAC still governs what they can do. Full LDAP/SAML configuration is out of scope for Project 2 — you're building the RBAC model that will sit underneath it either way.

Users, Deeper

Direct vs. Indirect Access — Answering Meera's Question Properly

This is the concept that actually resolves the Compliance email. A user's effective access in RHAAP comes from two possible sources:

① Direct role assignment

A role granted straight to the user on a specific object — e.g. r.iyer personally given Read on a Credential. Visible on the user's Access/Roles tab.

② Indirect via team membership

A role granted to a Team the user belongs to. The user inherits it for as long as they're a member. Visible on the team's Roles tab, and reflected on the user only as "member of Team X."

"Deepak Rao is no longer on the Linux Operations roster" only proves you removed him from source #2's membership list. It does not prove he has zero direct grants (source #1) that were made to him personally at some point and never cleaned up — for example, if someone once gave him personal Admin on the linux-ops-automation Project directly, removing him from the Team does nothing to that grant.

API The actual verification query

Check a user's own direct rolesGET
GET /api/controller/v2/users/18/roles/
# id 18 = Deepak Rao. Returns every role granted DIRECTLY to this user,
# across every object in the platform he has ever been granted access to —
# independent of any team membership.
Confirm team membership statusGET
GET /api/controller/v2/users/18/teams/
# Should return an empty result set if he was properly removed.

The correct answer to Meera requires both queries returning clean: no team memberships, and no direct role grants remaining. That's what "confirmed at the access level" actually means — and it's exactly the incident this project's Troubleshooting section walks through.

UI

  1. Open the user's profile → Roles tab. This shows direct grants only — the UI clearly separates this from team-inherited access.
  2. Open the user's profile → Teams tab. Confirms current team memberships.
  3. Cross-reference both before signing off on any access-review question.

ANSIBLE — an access-review helper

access_review.yml
- name: Fetch a user's direct roles for an access review
  ansible.builtin.uri:
    url: "{{ controller_host }}/api/controller/v2/users/{{ target_user_id }}/roles/"
    headers:
      Authorization: "Bearer {{ controller_oauthtoken }}"
    return_content: true
  register: direct_roles

- name: Fetch a user's current team memberships
  ansible.builtin.uri:
    url: "{{ controller_host }}/api/controller/v2/users/{{ target_user_id }}/teams/"
    headers:
      Authorization: "Bearer {{ controller_oauthtoken }}"
    return_content: true
  register: team_memberships

- name: Fail the play if any residual access exists
  ansible.builtin.fail:
    msg: "User {{ target_user_id }} still has residual access — direct roles: {{ direct_roles.json.count }}, teams: {{ team_memberships.json.count }}"
  when: direct_roles.json.count > 0 or team_memberships.json.count > 0
Why script this instead of checking manually every time?

Quarterly access reviews at bank scale mean this exact check, repeated for dozens or hundreds of departed/transferred users. A scripted, idempotent check gives you a reliable, repeatable answer instead of a manual UI click-through that's easy to get wrong under review-cycle time pressure — and produces a log you can hand directly to Compliance as evidence.

Teams, Deeper

Team Design Patterns

Beyond "one team per function," a few patterns recur across banks:

Multi-team membership

A user can belong to more than one Team. Example: Amit Verma (Linux Operations lead) could also join a cross-functional Change Approvers Team once approval workflows exist (Project 13) — he'd inherit both teams' roles simultaneously.

Function-based, not project-based

Teams named for what people do (Linux Operations) rather than what they're currently working on (Q3-Migration-Team) — the latter multiplies teams endlessly and orphans RBAC grants once the project ends.

Demonstrate: add Amit to a second team

multi_team.yml
- name: Create a cross-functional Change Approvers team
  awx.awx.team:
    name: "Change Approvers"
    organization: "Banking Automation"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Add Amit Verma to Change Approvers, in addition to Linux Operations
  awx.awx.role:
    user: "a.verma"
    team: "Change Approvers"
    role: member
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

Amit now inherits the union of both teams' object-level roles. This is normal and expected — but it's exactly why the access-review query above must always check a user's full team list, not just the one team you remember adding them to.

Delegated Administration — Without Handing Out Org Admin

Priya doesn't want the platform team fielding every "please add a new hire to Linux Operations" ticket forever. The fix is delegating team membership management to the team lead, without making him an Organization Admin (which would also let him touch every other team's Credentials and Projects).

Org: Banking Automation
 |
 +-- a.verma granted "Admin" role scoped to
 |    just the Team object "Linux Operations"
 |    (NOT Organization Admin)
 |
 +-- Effect: a.verma can add/remove Linux Operations
      members and manage that team's object,
      but cannot touch Windows Operations,
      Credentials at the Org level, or other Teams

UI

  1. Open Team: Linux Operations → Access tab.
  2. Click Add → select User a.verma → Role: Admin (this Admin role is scoped to the Team object itself, not the Organization).
  3. Save. Validate: logged in as a.verma, he can now see a Users management option on the Linux Operations Team page, but Windows Operations, Credentials, and other Organization-wide settings remain invisible or read-only to him.

delegate_admin.yml
- name: Delegate team-scoped admin to the Linux Operations lead
  awx.awx.role:
    user: "a.verma"
    role: admin
    team: "Linux Operations"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"

Security Notes For Project 2

■

Team removal is not access removal. Removing someone from a Team's roster only revokes the access they held through that team. Any direct grant made to them personally survives and must be checked and revoked separately — this is the single most common gap found in real audits.

▲

Delegated Admin is still a privileged grant. Team-scoped Admin lets someone add new members to that team — and new members inherit whatever that team can already do. Delegating membership management is safe; delegating it to someone who doesn't understand the RBAC already attached to that team is not.

◆

Prefer external auth group-mapping once available. Automatically mapping an AD group to RHAAP Team membership (covered later in the course) removes the manual "did someone remember to remove him" failure mode almost entirely — HR's offboarding process removing someone from AD does the RHAAP cleanup for free.

Incident: The Compliance Access-Review Finding

Email from Meera Pillai, Risk & Controls

"Following up — our automated scan flagged that user Deepak Rao still shows an active role grant on object 'linux-ops-automation' (Project), despite being removed from the Linux Operations team roster on the 3rd. Please explain and remediate."

StageWhat you do
OBSERVEMeera's finding names a specific object type (Project) and a specific user — start there, not with a platform-wide sweep.
COLLECT EVIDENCEGET /api/controller/v2/users/18/roles/ — confirms a direct Update role on the linux-ops-automation Project, granted three months ago, separate from his (already-removed) Team membership.

IDENTIFY ROOT CAUSERoot cause isn't "a bug" — it's a process gap: offboarding checked team rosters but not direct grants, because Project 1's RBAC model didn't yet include a formal offboarding checklist.
FIXRevoke the direct role: DELETE the specific role association via /users/18/roles/ (or the equivalent awx.awx.role task with state: absent).
VALIDATERe-run the access-review helper playbook from earlier in this project against user id 18 — both direct roles and team memberships should now return empty.
PREVENT RECURRENCEAdd "run the access-review helper playbook" as a mandatory step in the offboarding runbook, and note in this project's governance backlog (feeding Project 30) that direct-object grants to individuals should be an exception requiring sign-off, not a routine convenience.

Practice

Interview Preparation

RHAAP Architecture

Q1. When would you split into two Organizations instead of two Teams in one?
When the two groups need a genuinely separate secret/credential boundary that even admins shouldn't cross, or when they belong to entirely different governance/business units. If the difference is just "what they automate," Teams inside one Organization are almost always the right call.

RBAC

Q2. A user was removed from a team. How do you prove they have zero remaining access?
Check two things independently: their team membership list (should be empty of relevant teams) and their direct role grants via /users/{id}/roles/ (should show nothing lingering). Team removal alone does not revoke direct grants.
Follow-up: "How would you automate this for a whole offboarding batch?" — Loop the same two API queries over a list of departed user IDs and fail/report on any non-empty result, exactly like the access-review helper playbook built in this project.
Q3. Can a user belong to more than one Team, and what happens to their permissions if so?
Yes. Their effective access becomes the union of every role granted to every team they belong to, plus any direct grants. There's no conflict resolution needed — RBAC in RHAAP is additive, not deny-based.

Governance / Manager Round

Q4. How do you let a team lead manage their own team's roster without making them a platform admin?
Grant them the Admin role scoped specifically to the Team object itself (not the Organization) — they gain membership-management rights over that one team, with no visibility or control over other teams, credentials, or organization settings.

Scenario-Based

Q5. Compliance says a departed employee still shows a role grant weeks after offboarding. Walk through your investigation.
Start from the specific object and user named in the finding, query their direct roles, confirm the grant's origin and age, revoke it, re-run the verification query to confirm zero residual access, then fix the process gap — usually adding the access-review check as a mandatory offboarding step — so the same finding doesn't recur for the next departure.
