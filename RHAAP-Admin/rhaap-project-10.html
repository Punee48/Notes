Concept

What a Schedule Actually Is

A Schedule attaches a recurrence rule (an RRULE, the same standard used by iCalendar) to a Job Template or Workflow Job Template. RHAAP's scheduler evaluates active RRULEs continuously and launches the associated job whenever the rule's next occurrence is reached — functioning like a governed, centralized cron, but tied to RBAC, logging, and everything else the platform already provides.

Schedule object
   |
   +-- attached to: Job Template "Linux — Patch Compliance Check"
   +-- rrule: FREQ=WEEKLY;BYDAY=SU;BYHOUR=2;BYMINUTE=0
   +-- timezone: Asia/Kolkata
   |
   v
Every Sunday at 02:00 IST, RHAAP's scheduler launches the job
automatically — same execution flow as a manual launch (Project 1),
except the "launcher" is the schedule itself, not a human user.
Fig 10.1 — the RRULE defines when; the Job Template defines what. A Schedule doesn't duplicate the template's configuration — it just triggers it.
Concept — Read This Twice

Time Zones — The Single Most Common Scheduling Mistake

This directly explains Amit's incident, before you even open the troubleshooting section. A Schedule's RRULE defines hour/minute values, but those values mean nothing without a time zone attached — and the default a person assumes is not always the default RHAAP actually uses.

AssumptionReality
"The schedule uses my browser's local time zone automatically"The Schedule object has its own explicit Time Zone field — if it's left at a default that doesn't match what the person creating it assumed, the job fires at the wrong local time, exactly as happened to Amit
"2:00 AM is 2:00 AM everywhere"2:00 AM UTC and 2:00 AM Asia/Kolkata (IST, UTC+5:30) are over five hours apart — a schedule created assuming IST but saved with UTC (or vice versa) will fire at a very different local time than intended
"Once set correctly, it's set forever"Regions observing Daylight Saving Time shift their UTC offset twice a year — a schedule tied to a DST-observing zone can drift by an hour around those transitions if not using a proper IANA time zone identifier that RHAAP correctly adjusts for
■

Always set the Schedule's Time Zone field explicitly to a proper IANA identifier (e.g. Asia/Kolkata, America/New_York) rather than assuming a default, and always state the intended local time explicitly when documenting or discussing a schedule with the team — "2 AM" alone is not a complete specification.

Concept

Conflict Management

Recall Project 7's allow_simultaneous: false setting on the compliance-check template. Schedules don't bypass this — if a scheduled launch fires while a previous run (scheduled or manual) is still executing, RHAAP handles it the same way it would handle any other simultaneous-launch attempt: the new launch is blocked/queued rather than running in parallel.

ScenarioBehavior with allow_simultaneous: false
Scheduled launch fires while a manual launch is still runningScheduled launch is rejected or queued behind the running job, depending on RHAAP version/configuration — it does not run in parallel
Two schedules on the same template with overlapping trigger timesSame protection applies — only one execution proceeds at a time
A long-running job whose next scheduled occurrence arrives before it finishesThis is exactly why Project 7's Timeout matters here too — an unbounded job could cause every subsequent scheduled occurrence to be skipped or queued indefinitely
◆

This is a direct payoff of Project 7's hardening work. Because the compliance-check template already has a sane Timeout and Concurrent Jobs disabled, scheduling it today is safe by construction — you're not introducing a new class of risk, just automating the trigger.

Scheduling the Patch Compliance Check

UI

  1. Open Linux — Patch Compliance Check Job Template → Schedules tab → Create Schedule.
  2. Name: Weekly Compliance Check — Sunday 02:00 IST
  3. Start Date/Time: pick any upcoming Sunday, 02:00.
  4. Time Zone: explicitly select Asia/Kolkata — do not leave this at whatever the field defaults to.
  5. Repeat Frequency: Weekly, On: Sunday.
  6. Save. Validate: the Schedules tab shows the correctly computed "Next Run" timestamp — visually confirm it matches the intended local time before trusting it.

API

POST /api/controller/v2/job_templates/{id}/schedules/POST
{
  "name": "Weekly Compliance Check — Sunday 02:00 IST",
  "rrule": "DTSTART;TZID=Asia/Kolkata:20260830T020000 RRULE:FREQ=WEEKLY;BYDAY=SU",
  "enabled": true
}

ANSIBLE

schedules.yml
- name: Schedule the weekly patch compliance check
  awx.awx.schedule:
    name: "Weekly Compliance Check — Sunday 02:00 IST"
    unified_job_template: "Linux — Patch Compliance Check"
    rrule: "DTSTART;TZID=Asia/Kolkata:20260830T020000 RRULE:FREQ=WEEKLY;BYDAY=SU"
    enabled: true
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
Explain the RRULE string field by field

DTSTART;TZID=Asia/Kolkata:20260830T020000 — the anchor date/time and, critically, the explicit TZID that ties every future occurrence to Indian Standard Time regardless of where the RHAAP server itself is physically hosted or what its own system time zone is set to.

RRULE:FREQ=WEEKLY;BYDAY=SU — repeats weekly, specifically on Sundays. FREQ can also be DAILY, MONTHLY, or YEARLY; BYDAY constrains which day(s) within that frequency.

The explicit TZID is the single detail that prevents Amit's incident — without it, the rule's hour value is ambiguous relative to a time zone, and RHAAP falls back to a default that may not match what was intended.

Scheduling the Governance Checks

The RBAC self-audit (Project 3) and drift-detection check (Project 9) aren't Job Templates yet in this course's narrative — they're standalone playbooks. To schedule them properly, first wrap each as its own Job Template (pointing at a small "governance" Project), then schedule that template exactly like any other.

PlaybookWrapped as Job TemplateSchedule
rbac_audit.yml (Project 3)Platform — RBAC Self-AuditWeekly, Monday 06:00 IST — ahead of the work week, giving time to act on findings
drift_check.yml (Project 9)Platform — Job Template Drift CheckDaily, 07:00 IST — frequent enough to catch un-backfilled emergency changes quickly, per Project 9's incident

- name: Create the RBAC self-audit job template
  awx.awx.job_template:

                                    # a reachable localhost pattern satisfies the
                                    # Job Template's required Inventory field
    project: "platform-governance-automation"
    playbook: "playbooks/rbac_audit.yml"
    execution_environment: "Default execution environment"
    timeout: 300
    allow_simultaneous: false
    controller_host: "{{ controller_host }}"

Designing a Maintenance Window Concept

Full patch-remediation workflow automation (Pre-Check → Patch → Reboot → Validation) is Project 19's and Project 36's territory, built on Workflow Job Templates from Project 12. Today, lay the scheduling groundwork: define what "maintenance window" means for ABC Bank before any automation depends on that definition.

ABC Bank's approved maintenance window (Linux Operations):

  Every Sunday, 02:00 - 04:00 IST
        |
        +-- 02:00  Compliance check runs (read-only, already scheduled today)
        +-- 02:15  (future, Project 19) Patch remediation would begin here,
        |           only for hosts flagged non-compliant
        +-- 03:30  (future) Reboot window, if required
        +-- 04:00  Window closes — no further automated changes permitted
                    outside this box without an Emergency Change
                    (same two-lane concept from Project 9)
Fig 10.2 — today's deliverable is the window definition and the first scheduled job inside it (the compliance check). The remediation steps are explicitly deferred, not built today, per the "don't overwhelm" principle applied to scheduling scope.
▲

A maintenance window is a policy concept, not a single RHAAP setting. RHAAP doesn't have a literal "maintenance window" object at this stage of the course — you express it through disciplined scheduling (jobs only scheduled to fire inside the approved box) and, later, through Workflow Job Template design. Document the window definition itself clearly, since every future schedule in this domain should be validated against it.

Enable/Disable for Freeze Periods

Banks commonly enforce change freezes — e.g., no non-emergency automation during fiscal year-end close. Rather than deleting schedules (losing their configuration) during a freeze, disable them.

UI

  1. Open the Job Template's Schedules tab.
  2. Toggle the specific Schedule's Enabled switch off.
  3. The Schedule's configuration (RRULE, time zone) remains intact — it simply won't trigger any launches while disabled.
  4. Re-enable once the freeze period ends.

ANSIBLE

freeze_period.yml
- name: Disable the weekly compliance check during fiscal year-end freeze
  awx.awx.schedule:
    name: "Weekly Compliance Check — Sunday 02:00 IST"
    unified_job_template: "Linux — Patch Compliance Check"
    enabled: false
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

# Run this same task with enabled: true once the freeze window ends —
# using a scheduled reminder (or a second, dated Ansible run) so
# re-enabling doesn't depend on someone remembering, the same lesson
# from Project 9's incident applied here.

Security Notes For Project 10

■

Scheduled jobs run with zero human review at launch time, by definition. This raises the importance of everything built in Projects 3, 7, and 9 — RBAC, Timeout/Concurrency hardening, and Governance/drift-checking — since a misconfiguration that a human might have caught before clicking Launch will instead execute silently, on schedule, unattended.

▲

A schedule inherits the Job Template's attached Credentials automatically. There's no additional human-in-the-loop credential check at trigger time — this is expected and correct, but it means the RBAC and credential-scoping decisions from Projects 1, 3, and 6 are doing real, unsupervised work every time the schedule fires.

◆

Attribute scheduled job runs clearly in any audit conversation. A scheduled job's "launched by" will show the schedule itself, not a person — make sure Compliance and Security understand this distinction so a scheduled run isn't mistaken for unauthorized manual access during a review.

Incident: Wrong Time Zone, Wrong Time of Day

Amit Verma

"The compliance check fired at 2 PM, not 2 AM. Right during business hours, with job output flooding the team channel while everyone was working."

StageWhat you do
OBSERVEThe schedule fired — it's not a "did nothing" failure, it's a "fired at the wrong local time" failure, a distinct and more subtle class of bug.
COLLECT EVIDENCEOpen the Schedule object and check its configured Time Zone field. You find it was left at UTC — whoever created it typed "2:00" intending 2 AM IST, but never explicitly changed the time zone dropdown from its default.
ISOLATE FAILURE2:00 AM UTC is 7:30 AM IST — not even a full 12-hour flip, which is why the mismatch initially looked confusing rather than an obvious "exactly 12 hours off" pattern. (Further investigation shows the specific schedule had actually been recreated once already with a slightly different start time, compounding the confusion — but the root mechanism is the same time zone gap.)
CHECK DEPENDENCIESAudit every other existing Schedule created before this project's explicit-time-zone discipline was established, for the same silent-default risk.
IDENTIFY ROOT CAUSEThe Schedule creation UI's time zone field defaulted to something other than what the creator assumed, and nothing forced an explicit confirmation.
FIXEdit the Schedule, explicitly set Time Zone to Asia/Kolkata, and re-verify the computed "Next Run" timestamp displays the intended local time before saving.
VALIDATELet the next scheduled occurrence fire naturally (or use a near-term test occurrence) and confirm it now happens at the intended local time.
PREVENT RECURRENCEAdd "explicitly confirm the Time Zone field, never accept the default" to the governance checklist from Project 9, and add a check to the drift-check playbook (Challenge 2 below) that flags any Schedule whose time zone isn't the bank's standard Asia/Kolkata.
◆

This incident is exactly why the Time Zones section above insists on "read this twice." It's a genuinely easy mistake to make once, and a genuinely easy one to prevent forever after — the fix is a one-line discipline, not a platform limitation.

Practice

Interview Preparation

Q1. How does a RHAAP Schedule decide when to launch a job?
It's built on an RRULE — an iCalendar-style recurrence rule — anchored to a specific start date/time and, critically, an explicit time zone. RHAAP's scheduler continuously evaluates active schedules and launches the associated Job Template or Workflow Job Template at each computed occurrence.
Q2. What's the most common mistake people make when creating a Schedule, and how do you prevent it?
Leaving the Time Zone field at whatever it defaults to instead of explicitly setting it to the intended zone — this causes the job to fire at an unexpected local time. Prevent it by always explicitly setting the Time Zone field and verifying the computed "Next Run" timestamp before trusting the schedule.
Q3. What happens if a scheduled launch collides with a still-running previous execution and Concurrent Jobs is disabled?
The same protection applies as any other simultaneous-launch attempt — the new launch is blocked or queued rather than running in parallel, which is why pairing Schedules with sane Timeout and Concurrency settings (Project 7) matters even more once launches are unattended.
Q4. How would you pause automation during a change freeze without losing the schedule's configuration?
Disable the Schedule rather than deleting it — its RRULE and settings remain intact, and it can be re-enabled once the freeze period ends, ideally via a tracked, dated action rather than relying on someone remembering.
Q5. Why does scheduling raise the stakes on earlier governance work like RBAC and Timeout settings?
Because a scheduled launch happens with no human reviewing it in the moment — any misconfiguration that a person might have caught before clicking Launch manually instead executes silently and unattended, on whatever cadence the schedule defines.

◆

Lab vs. Enterprise Production: Schedules are fully practicable on a lab RHAAP/AWX instance — you don't need to wait a full week to validate one; set a near-term test occurrence a few minutes out to observe real end-to-end behavior quickly.

  1. Schedule your lab's restart-service or compliance-check Job Template to run a few minutes from now, explicitly setting your own local time zone.
  2. Confirm it fires at the expected time and produces normal job output.
  3. Deliberately create a second schedule with the time zone left at a different default, and compare the two "Next Run" timestamps to see the discrepancy directly — this is the fastest way to internalize the incident in this project.
  4. Disable one of the schedules, confirm it no longer appears in upcoming runs, then re-enable it.
  5. Wrap a simple playbook (even just a debug task) as its own Job Template and schedule it daily, simulating the governance-check pattern from this project.
