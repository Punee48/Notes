Inventories and Inventory Variables

Project 1's Inventory was a flat pair of groups. Today: nested groups, the full variable precedence chain from inventory all the way to role defaults, host-vars-vs-group-vars trade-offs, and treating the Inventory as the authoritative source of truth for "what exists" — because a wrong variable silently overriding another is a much quieter failure than a missing credential.

Concept

Inventory Design Principles

A good Inventory answers two questions cleanly at once: what environment is this host in? and what role does it play? Flat groups (Project 1's rhel_web/rhel_db) answer only the second. Nested groups answer both.

Linux Servers (Inventory)
   |
   +-- production
   |     +-- prod_web
   |     |     +-- lnx-web-01.abcbank.internal
   |     |     +-- lnx-web-02.abcbank.internal
   |     +-- prod_db
   |           +-- lnx-db-01.abcbank.internal
   |
   +-- non_production
         +-- stg_web
         |     +-- lnx-web-stg-01.abcbank.internal
         +-- stg_db
               +-- lnx-db-stg-01.abcbank.internal
Fig 5.1 — production and non_production are parent groups; prod_web/stg_web are child groups nested beneath them. A host's group variables come from every ancestor group, not just its direct parent.

This directly resolves Sara's confusion: she set env: staging as a host variable, but a group variable on production — set higher up the hierarchy, applying to the entire group tree beneath it — was overriding it, because of where it sits in the precedence chain (next section).

Concept — Read Carefully

Variable Precedence, In Order

This is Ansible's actual precedence order, from lowest to highest. Ansible always applies the highest-precedence value it finds for a given variable name.

#SourceExample in this course's context
1 (lowest)Role defaults (roles/x/defaults/main.yml)A sane fallback baked into a shared role
2Inventory group variables (parent groups first, then children — children win over parents)env: production set on the production parent group
3Inventory host variablesSara's env: staging set directly on a host
4Playbook vars:service_name: httpd from Project 1's playbook
5Role/task vars:A variable set inside a specific task block
6Job Template extra variables (survey answers, from Project 8 onward)An operator's choice at launch time
7 (highest)extra_vars passed explicitly at launch (e.g. via the API's extra_vars field, or -e on the CLI)A one-off override for a single manual run
■

This resolves the incident precisely — but not the way it first appears. Notice host variables (#3) actually rank above group variables (#2) in real Ansible precedence. So if Sara's host variable really was set correctly, it should have won. The fact that it didn't points at a different, more interesting root cause — worked through fully in this project's Troubleshooting section below. Don't assume you already know the answer; verify it.

◆

The practical habit this table builds: whenever a variable's value is "not what I expected," don't guess — check every level in this table from the top down for that specific host, in order. Project 8 (Surveys) and Project 18 (Extra Variables) will each add real, hands-on precedence exercises on top of this table.

Build

Building Nested Groups

UI

  1. Open Linux Servers Inventory → Groups tab → Create Group → name production. Repeat for non_production.
  2. Open the production group → Related Groups (or nested-group management, depending on UI version) → add prod_web and prod_db as child groups.If your RHAAP version's UI doesn't expose nested-group creation directly on this tab, create prod_web/prod_db as standalone groups first, then use "Group → Related Groups → Associate" to nest them under production.
  3. Move existing hosts (lnx-web-01, lnx-web-02) into prod_web; move lnx-db-01 into prod_db.
  4. Create stg_web/stg_db beneath non_production, and add staging hosts.
  5. On the production parent group's Variables tab, set: env: production. On non_production: env: staging.
  6. Validate: Inventory → Hosts → click into lnx-web-01 → Variables preview (or run a debug playbook) should show it inheriting env: production from its ancestor group.

ANSIBLE

nested_inventory.yml
- name: Create top-level environment groups
  awx.awx.group:
    name: "{{ item }}"
    inventory: "Linux Servers"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  loop: [production, non_production]

- name: Set environment variable on the production group
  awx.awx.group:
    name: "production"
    inventory: "Linux Servers"
    variables:
      env: production
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Create function-based child groups
  awx.awx.group:
    name: "{{ item }}"
    inventory: "Linux Servers"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  loop: [prod_web, prod_db, stg_web, stg_db]

- name: Nest prod_web and prod_db under production
  awx.awx.group:
    name: "production"
    inventory: "Linux Servers"
    children:
      - prod_web
      - prod_db
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Assign hosts to their function group
  awx.awx.host:
    name: "{{ item.host }}"
    inventory: "Linux Servers"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  loop:
    - { host: lnx-web-01.abcbank.internal, group: prod_web }
    - { host: lnx-web-02.abcbank.internal, group: prod_web }
    - { host: lnx-db-01.abcbank.internal,  group: prod_db }
Build

Choosing Between Host Vars and Group Vars

Use a Group Variable when...Use a Host Variable when...
The value applies to every host performing that function or in that environment (e.g. env: production, ansible_user: svc_ansible)The value is genuinely specific to one machine (e.g. a host's unique backup window, a specific NIC name, a host-specific feature flag for a canary rollout)
You want changing it once to affect an entire fleetYou need to override the group's default for exactly one exceptional host, temporarily or permanently
Example: group-level default, host-level override
# group_vars for prod_web (applies to lnx-web-01 and lnx-web-02)
backup_window: "02:00-04:00"

# host_vars for lnx-web-02 only — this host has a documented exception
backup_window: "04:00-06:00"   # runs a heavier nightly batch job first

Per the precedence table above, the host variable on lnx-web-02 correctly wins over the group default — this is the intended, expected use of host-level overrides, and the opposite of what went wrong in Sara's incident.

Build

Inventory as the Source of Truth

A recurring anti-pattern: engineers keep a personal spreadsheet or a stale hosts.ini file "just to be sure," alongside the RHAAP Inventory. This always drifts, and it always causes exactly the kind of confusion Sara ran into.

▲

Rule going forward: if a host isn't in the RHAAP Inventory, it doesn't exist for automation purposes — full stop. Decommissioned hosts get removed from the Inventory the same day they're decommissioned, not "eventually." New hosts get added before any Job Template references them, never after someone discovers a job silently skipped a host that was never added.

Static inventories like this one are appropriate for the current dozen-host scale. Once ABC Bank's footprint grows into the hundreds or thousands, dynamic and constructed inventories (Projects 15–16) pull host lists automatically from a cloud provider or CMDB — removing manual drift entirely. Hold that as the next evolution, not today's task.

Security Notes For Project 5

▲

Group variables are not a secrets store. It's tempting to put something like an API key in a group variable because it's convenient — don't. Group and host variables are visible to anyone with Read on the Inventory (recall the Auditor persona from Project 3, which intentionally has Inventory Read). Secrets belong in Credentials, injected at runtime, never in inventory variables.

◆

Keep the environment boundary (production/non_production) as a real RBAC boundary too, eventually. Today both live in one Inventory for simplicity; as the fleet grows, consider whether production and non-production deserve separate Inventories with separate RBAC, so a Job Template misconfiguration can't accidentally target production when someone meant to test against staging.

Run It — Production Incident

Incident: Resolving Sara's Precedence Confusion

StageWhat you do
OBSERVESara set a host variable, expected it to apply, but the playbook behaved as if the group's value applied instead — which, per the precedence table, shouldn't happen (host vars outrank group vars).
COLLECT EVIDENCEYou pull up the actual host's Variables tab in the UI. It's empty — she never actually saved the variable at the host level; she'd edited it in a scratch text file locally and never pasted it into RHAAP's host variables field.
ISOLATE FAILUREThis isn't a precedence bug at all — it's a "the variable was never actually set where she thought it was" issue. Precedence rules only apply to variables that actually exist in the sources being compared.
CHECK DEPENDENCIESAlso worth checking: was she testing against the right host in the first place? Confirm the host she edited locally matches the host the Job Template's Limit field actually targeted at launch.
IDENTIFY ROOT CAUSEA process/tooling gap, not a platform bug: nothing in her workflow made it obvious the variable change hadn't actually been saved to the Inventory before she launched the job.
FIXSet the host variable properly through the UI (or API/Ansible) this time, and re-run.
VALIDATEAdd a debug task early in test playbooks that prints the resolved value of any variable under test — ansible.builtin.debug: msg="env={{ env }}" — so "is this actually set" becomes a one-line, visible check instead of an assumption.
PREVENT RECURRENCEDocument the precedence table from this project in the team wiki, plus the specific habit: "when a variable doesn't behave as expected, first confirm it's actually saved where you think it is — with a debug task — before assuming a precedence problem."
◆

The teaching point: a huge fraction of real "precedence bugs" are actually "the variable isn't set where I assumed" bugs. Verify existence before reasoning about precedence — this incident is a deliberately realistic example of exactly that trap.

Practice

Interview Preparation

Q1. Recite Ansible's variable precedence order from lowest to highest.
Role defaults, inventory group variables (parents before children), inventory host variables, play variables, role/task variables, Job Template survey/extra variables, and finally explicit extra_vars passed at launch — the highest wins.
Q2. Between a host variable and a group variable, which wins, and does that ever surprise people?
Host variables win over group variables. It surprises people less because of precedence and more because they assume a variable is set somewhere it actually isn't — always verify existence with a debug task before assuming a precedence explanation.
Q3. Why nest groups by environment and function instead of keeping one flat list?
Nesting lets you set a variable once at the environment level (like env: production) and have it apply to every function group beneath it, instead of repeating the same variable on every individual function group — and it makes RBAC and reporting boundaries between production and non-production much easier to reason about later.
Q4. Should secrets ever live in inventory variables?
No — inventory variables are visible to anyone with Read access on the Inventory, including Auditor-type personas by design. Secrets belong exclusively in Credentials, injected at execution time.
