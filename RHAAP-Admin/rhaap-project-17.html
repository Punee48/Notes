Execution Environment Development

Every job template built since Project 1 has quietly used "Default execution environment" without asking what's actually inside it. Today that stops — Linux Operations gets its own versioned, reproducible, dependency-pinned container image, built with ansible-builder, pushed to a real registry, and registered in RHAAP as a first-class Execution Environment object.

Enterprise Story

Week Seventeen — What's Actually Inside "Default"?

Priya Nair, Head of Platform Engineering

"Every Job Template we've built — sixteen projects' worth — has used 'Default execution environment' without any of us asking what Ansible Core version it runs, which collections it has, or who controls when it changes. That's a real risk: if Red Hat updates that default image and a collection version shifts underneath us, our playbooks could start behaving differently with zero code change on our side. I want Linux Operations running on our own, explicitly versioned image. And Security wants to know we can eventually run fully air-gapped, without a live connection to public Galaxy at job-run time — the EE needs to already contain everything it needs."

Concept

Execution Environments, Full Depth

Project 1 introduced EEs at a glance: a container bundling Ansible Core, Python, and collections. Here's the complete picture.

Execution Environment image contains:
   |
   +-- A base OS layer (e.g. a minimal UBI-based image)
   +-- Python interpreter + pip
   +-- ansible-core (a specific, pinned version)
   +-- Ansible Collections (community.general, ansible.posix, etc.
   |    — each pinned to a specific version)
   +-- Any Python libraries those collections depend on
   +-- Any system (RPM/deb) packages those collections or libraries
        depend on (e.g. openssh-clients, libxml2)

Every job that uses this EE runs inside a fresh container built
from this exact image — identical every single time, on every
execution node, regardless of what's installed on the node itself.
Fig 17.2 — "identical every time" is the entire value proposition. It's also what makes air-gapped operation possible: once built, this image needs no further internet access to run jobs.
◆

This directly resolves both of Priya's concerns. An explicitly-versioned, ABC-Bank-controlled EE means Red Hat's default image updating no longer silently changes Linux Operations' runtime. And because collections/dependencies are baked into the image at build time (not fetched live during a job run), the resulting image can run in a fully air-gapped RHAAP deployment.

Build

Defining the Linux Ops EE

execution-environment.yml
---
version: 3

images:
  base_image:
    name: registry.access.redhat.com/ubi9/ubi-minimal:latest
    # NOTE: pin this to a specific digest (not a mutable tag) before
    # this image is considered production-ready — see Security Notes.

dependencies:
  galaxy: requirements.yml
  python: requirements.txt
  system: bindep.txt

additional_build_steps:
  prepend_base:
    - RUN microdnf update -y
  append_final:
    - LABEL org.abcbank.team="linux-operations"
    - LABEL org.abcbank.ee-version="1.0.0"
requirements.yml
---
collections:
  - name: ansible.posix
    version: "1.5.4"
  - name: community.general
    version: "8.2.0"
  - name: awx.awx
    version: "23.7.0"
requirements.txt
resolvelib>=0.5.3,<0.9.0
packaging==23.2
bindep.txt
openssh-clients [platform:rpm]
rsync [platform:rpm]
Explain every pinned version and why pinning matters here specifically

ansible.posix and community.general pinned to exact versions — these provide modules the restart-service and health-check playbooks rely on (ansible.builtin.systemd is core, but several other modules used across this course's playbooks live in community.general). Pinning means "the collection behaves exactly the way it did when this EE was built and tested" — an unpinned collections: [ansible.posix] entry would silently pull whatever the latest version happens to be at build time, potentially introducing a breaking change with zero warning.

openssh-clients in bindep.txt — needed because the container itself needs an SSH client to connect out to target hosts; this is exactly the kind of system-level dependency that used to be "whatever happened to be installed on the control node" before EEs existed.

The LABEL instructions in additional_build_steps bake ownership and version metadata directly into the image itself — so podman inspect or a registry UI can answer "who owns this and what version is it" without needing to cross-reference anything external.

Build

Building With ansible-builder

Build the imageRUN
cd linux-ops-execution-environment/

ansible-builder build \
  --tag linux-ops-ee:1.0.0 \
  --container-runtime podman \
  -v3

# -v3 gives verbose output — worth using on every build until you're
# confident the definition is correct; silent build failures are
# painful to debug after the fact.
◆

ansible-builder generates an intermediate Containerfile from your execution-environment.yml and dependency files, then hands it to Podman (or Docker) to actually build the image. You can inspect this generated Containerfile (in the build context's output directory) if you need to debug exactly what instructions are being run — it's not a black box.

Build

Testing Before Publishing

Never register a freshly built EE directly into production RHAAP without testing it locally first — exactly the same discipline as testing a Job Template against one host before trusting it against the full fleet (Project 1, Project 7).

Local smoke test
# Confirm the image runs and reports the expected Ansible/collection versions
podman run --rm linux-ops-ee:1.0.0 ansible --version
podman run --rm linux-ops-ee:1.0.0 ansible-galaxy collection list

# Run an actual playbook against a local test target using ansible-navigator,
# which is purpose-built for testing playbooks against a specific EE image
ansible-navigator run playbooks/service-health-check.yml \
  --execution-environment-image linux-ops-ee:1.0.0 \
  --mode stdout \
  -i test-inventory.ini
▲

"It built successfully" is not the same as "it works." A clean ansible-builder build only confirms the image assembled without error — it says nothing about whether the collections inside actually support the specific modules your playbooks call. The ansible-navigator smoke test above is what actually validates that.

Build

Versioning & Pushing to a Registry

■

Never tag or reference an EE image as latest in production. latest is a mutable pointer — a Job Template referencing it could silently start running a completely different image the next time someone pushes an update, with zero visibility into what changed. Every EE image gets an explicit, semantic version tag, exactly like the Git tag discipline from Project 4's production Project pinning.

Tag and push
podman tag linux-ops-ee:1.0.0 \
  registry.abcbank.internal/platform-team/linux-ops-ee:1.0.0

podman push registry.abcbank.internal/platform-team/linux-ops-ee:1.0.0

# Optional but recommended: scan before pushing
trivy image linux-ops-ee:1.0.0
◆

A vulnerability scan (e.g. Trivy, Grype) as a standard pre-push step is worth adopting now, ahead of the full CI/CD pipeline built in Project 43 — catching a known-vulnerable base package before the image ever reaches RHAAP is far cheaper than discovering it after the fact.

Registering It in RHAAP

UI

  1. First, create a Container Registry Credential pointing at registry.abcbank.internal, if the registry requires authentication.
  2. Automation Execution → Execution Environments → Create Execution Environment.
  3. Name: Linux Ops EE v1.0.0
  4. Image: registry.abcbank.internal/platform-team/linux-ops-ee:1.0.0 — the explicit tag, never latest.
  5. Pull: Only pull image if not present (avoids re-pulling on every job once cached, while still fetching automatically the first time or after a version bump).
  6. Credential: the Container Registry credential from step 1.
  7. Save, then update the Linux — Restart Service, Linux — Patch Compliance Check, and other Linux Operations Job Templates to use this EE instead of "Default execution environment."

ANSIBLE

register_ee.yml
- name: Register the container registry credential
  awx.awx.credential:
    name: "ABC Bank Internal Registry"
    organization: "Banking Automation"
    credential_type: "Container Registry"
    inputs:
      host: "registry.abcbank.internal"
      username: "{{ lookup('env', 'REGISTRY_USER') }}"
      password: "{{ lookup('env', 'REGISTRY_PASSWORD') }}"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  no_log: true

- name: Register the Linux Ops execution environment
  awx.awx.execution_environment:
    name: "Linux Ops EE v1.0.0"
    image: "registry.abcbank.internal/platform-team/linux-ops-ee:1.0.0"
    pull: missing
    credential: "ABC Bank Internal Registry"
    organization: "Banking Automation"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present

- name: Point every Linux Operations job template at the new EE
  awx.awx.job_template:
    name: "{{ item }}"
    execution_environment: "Linux Ops EE v1.0.0"
    controller_host: "{{ controller_host }}"
    controller_oauthtoken: "{{ controller_oauthtoken }}"
    state: present
  loop:
    - "Linux — Restart Service"
    - "Linux — Patch Compliance Check"
    - "Linux — Service Health Pre-Check"
    - "Linux — Service Rollback Notify"
    - "Linux — Escalate Incident"

Security Notes For Project 17

■

Pin the base image to a digest, not just a tag, before this is truly production-ready. Even ubi9/ubi-minimal:latest is mutable upstream — a sha256: digest reference guarantees byte-for-byte reproducibility of the base layer itself, closing the exact gap Priya originally raised about Red Hat's default image changing underneath the team.

▲

Every pinned collection and package version is now a maintenance responsibility. Pinning trades "silently drifting behavior" for "a known set of versions someone must deliberately update and re-test" — a real trade, worth making, but not a free one. Track EE versions and their contents in the CHANGELOG, exactly like any other governed artifact in this course.

◆

The registry pull credential is a real Credential object and deserves the same RBAC discipline as any other from Project 6 — scope it to read/pull access only, never anything capable of pushing or deleting images from the registry.

Run It — Production Incident

Incident: A Module Went Missing After Switching EEs

Sara Khan, the day after the cutover

"The patch compliance check is failing now — something about dnf module not being found. It worked fine yesterday."

StageWhat you do
OBSERVEThe failure started exactly when the Job Templates were switched to the new EE — a strong, specific signal pointing at the EE change itself as the cause.
COLLECT EVIDENCEJob output shows: couldn't resolve module/action 'ansible.builtin.dnf' — a module the compliance-check playbook (Project 7) depends on directly.
ISOLATE FAILURECheck what collections the new linux-ops-ee:1.0.0 actually contains via podman run --rm linux-ops-ee:1.0.0 ansible-galaxy collection list — ansible.builtin modules should always be present (they ship with ansible-core itself), so this points at something more specific: possibly an ansible-core version mismatch, or the module simply requiring a package not present in this minimal base image.
CHECK DEPENDENCIESYou discover the dnf Python bindings package (a system-level dependency the dnf module needs to actually interact with the package manager) was never added to bindep.txt — the default/original EE happened to include it; this new, deliberately minimal EE does not, by design.
IDENTIFY ROOT CAUSEBuilding a genuinely minimal EE (as Project 17 deliberately chose) means dependencies that were previously "just there" in a fuller default image now have to be explicitly identified and added — this is the direct cost of the minimal-base decision, surfacing for the first time on a module the original EE definition didn't anticipate.
FIXAdd the missing system package to bindep.txt, rebuild the image as linux-ops-ee:1.0.1 (a new version, never overwriting 1.0.0), re-test locally with ansible-navigator against the compliance-check playbook specifically, then re-tag the Job Templates to the new version.
VALIDATERe-run the compliance check against the full production inventory and confirm successful completion.
PREVENT RECURRENCEBefore any future EE cutover, run every existing Job Template's playbook through the ansible-navigator local smoke test against the candidate EE — not just a generic ansible --version check — so a missing dependency surfaces during testing, not the day after a production switch.
◆

This incident is the direct, lived cost of choosing a minimal base image over a "batteries included" one. It's not an argument against the minimal choice — it's the reason the Testing section above insists on running actual playbooks against a candidate EE, not just checking that it builds and reports a version number.

Practice

Interview Preparation

Q1. Walk through the structure of an execution-environment.yml file.
A version field for the schema itself, an images.base_image defining the starting container layer, a dependencies section pointing at separate files for Galaxy collections, Python packages, and system packages, and an optional additional_build_steps escape hatch for anything the structured sections don't cover.
Q2. Why choose a minimal base image over a fuller, "batteries included" one?
Smaller attack surface and full, explicit control over exactly what's present — every dependency is deliberately declared rather than inherited implicitly. The trade-off is that dependencies which "just worked" under a fuller default image now have to be explicitly identified and added, which can surface as a missing-module failure if something is overlooked.
Q3. Why should an EE image never be tagged or referenced as latest in production?
latest is a mutable pointer — a Job Template referencing it could start running an entirely different image after any push to that tag, with no visibility into what changed. Explicit semantic version tags make every EE reference deterministic and auditable.
Q4. How do you validate a newly built EE before trusting it in production?
Beyond confirming the build itself succeeds, run actual representative playbooks against the candidate image using a tool like ansible-navigator — a clean build only proves the image assembled correctly, not that every module a real playbook depends on is actually present and functional.
Q5. A playbook that worked fine suddenly fails with a "module not found" error right after an EE version change. What's your diagnosis path?
Confirm the timing correlation with the EE change first, then inspect the new EE's actual installed collections and system packages directly (e.g. via ansible-galaxy collection list inside the container) to identify what's missing compared to the previous EE, rather than assuming it's a playbook-side regression.

Practice Assignment

◆

Lab vs. Enterprise Production: building and testing an EE locally requires ansible-builder, Podman or Docker, and (ideally) ansible-navigator — all installable on a personal machine or lab VM with no RHAAP dependency at all. Pushing to a real private registry requires at least a local/throwaway registry (e.g. a local Podman-hosted registry container) if you don't have access to an enterprise one.

  1. Install ansible-builder, ansible-navigator, and Podman (or Docker) locally.
  2. Write your own execution-environment.yml, requirements.yml, requirements.txt, and bindep.txt for one of the playbooks from earlier in this course (e.g. the restart-service playbook).
  3. Build the image and confirm it succeeds; then run ansible-galaxy collection list inside it to verify the expected collections are present.
  4. Use ansible-navigator to run the actual playbook against a local test target using your new image.
  5. Deliberately omit a dependency you know the playbook needs, rebuild, and reproduce this project's incident — observe the specific failure, then fix it and confirm resolution.
  6. Tag your final image with an explicit semantic version and push it to a local or lab registry.
