Advanced Surveys

Project 1's playbook hard-coded service_name: httpd. Today, Operators choose it themselves at launch time — safely, with validation, defaults, and a change-ticket field for audit purposes — without you editing the playbook every time someone needs to restart a different service. This is where self-service automation actually becomes self-service.

Sara Khan, Linux Operations

"The restart-service template only ever restarts httpd because that's hard-coded. Yesterday I needed to restart sshd on one host and had to ask you to edit the template. Can Operators just... pick the service?"

Priya Nair

"Yes — but I want two things alongside it. One, a Change Ticket field, so every restart is tied to a real change record, not just 'someone clicked launch.' Two, I don't want this to become a way for someone to type in anything at all and have it run as a shell command — I remember reading that unsanitized text input into automation is exactly how injection vulnerabilities happen. Design it carefully."

Concept

What Is a Survey?

A Survey is a set of questions attached to a Job Template. When a user with Execute launches it, RHAAP presents a form built from these questions. Each answer becomes an extra variable passed into the playbook run — exactly like the vars: block in Project 1's playbook, except supplied by the launcher instead of hard-coded by the developer.

Operator clicks Launch
        |
        v
Survey form rendered (questions defined by the Automation Developer)
        |
        | operator fills in answers
        v
Answers become extra_vars for this specific job run
        |
        v
playbooks/restart-service.yml
   vars:
     service_name: "{{ service_name }}"   <- now populated from the survey answer,
                                              not a hard-coded default
Fig 8.1 — the playbook itself barely changes; it already expected a service_name variable, which used to come from a hard-coded default and now comes from the launcher's answer.

Field Types

▲

The Password field type is not a Credential. It masks the value in the UI and job output for display purposes, but the value still flows through as a normal variable — it is not encrypted at rest the way a Credential's secret is, and it should never be used for anything that needs the actual security guarantees built in Project 6. Use it for things like a one-off token an operator pastes in, not for anything you'd call a real secret.

Concept

Surveys and Variable Precedence — Closing the Loop From Project 5

Recall Project 5's precedence table. Survey answers sit at level 6 — Job Template extra variables — just below explicit launch-time extra_vars (level 7), and above the playbook's own vars: block (level 4).

◆

Practical implication: a survey answer will always override whatever default the playbook's vars: block sets — which is exactly the mechanism that lets Sara's chosen service name win over the old hard-coded httpd default, without you needing to delete that default from the playbook. Leaving a sensible default in the playbook is actually good practice: it's what runs if the template is ever launched by something that bypasses the survey (e.g. certain API-driven or scheduled launches, depending on configuration) — covered further in Project 18.

Build

Designing ABC Bank's Survey

Answering Priya's safety concern directly: service_name should not be free text. Constrain it to a known-safe Multiple Choice list of services this template is actually approved to restart — this is the core defense against both operator typos and injection risk, covered in full in the Security section below.

Service NameMultiple Choice (single)YesChoices: httpd, sshd, chronyd — the only services this template is approved to touch
Change TicketTextYesRegex-validated to match ABC Bank's ticket format, e.g. CHG-\d{6}
Reason for RestartTextareaNoFree text, but only ever used for the job's human-readable audit trail — never interpolated into a shell command (see Security)

Build

Building The Survey

UI

  1. Open Linux — Restart Service Job Template → Survey tab → toggle On.
  2. Click Add to create the first question.
  3. Question: "Which service should be restarted?" Answer variable name: service_name. Answer type: Multiple Choice (single select). Multiple Choice Options: one per line — httpd, sshd, chronyd. Required: Yes.
  4. Add the second question: "Change ticket number" → variable change_ticket → type Text → set Minimum length and Maximum length appropriately, and a validation pattern of ^CHG-\d{6}$ if your RHAAP version's survey editor supports regex validation directly.
  5. Add "Reason for restart (optional)" → variable restart_reason → type Textarea → Required: No.
  6. Add "Confirm production impact" → variable confirm_production → type Multiple Choice → options as listed above → Required: Yes.
  7. Reorder questions with drag handles so Service Name appears first — the most decision-relevant question first is better UX than burying it under administrative fields.
  8. Save. Validate: log in as Sara (or impersonate) and click Launch — the survey form should appear before the job starts, and attempting to launch without a Change Ticket should be blocked by the Required flag.

Build

Validation Rules — Beyond "Required"

RuleWhat it prevents
RequiredLaunching without answering a mandatory field
Min/Max length (Text/Textarea)Empty-ish garbage answers, or absurdly long input that wasn't intended
Min/Max value (Integer/Float)Out-of-range numeric input, e.g. a "number of retries" field accepting a negative number or 100,000
Multiple Choice (instead of Text)The single most important control in this project — constrains input to a known-safe, pre-approved set instead of arbitrary text
◆

Default rule of thumb: if a field's answer is ever going to influence which command runs or which host/service is targeted, prefer Multiple Choice over Text, every time — even if it means updating the survey's choice list when a new valid option is added. If a field is purely descriptive (like restart_reason), free text is fine, provided the playbook never uses it unsafely (next section).

Security Notes For Project 8

■

The command-injection risk, explained concretely. Imagine the playbook had instead been written as:

ansible.builtin.shell: "systemctl restart {{ service_name }}"

If service_name were a free-text field, an operator (or anyone who compromised an operator's session) could enter something like httpd; rm -rf /var/log — and because shell passes the string to a real shell, everything after the semicolon executes too. Constraining service_name to Multiple Choice makes this specific attack impossible: the value can never be anything other than one of the three approved strings, regardless of what's typed into the UI (the UI doesn't even offer a text box for this field). This is precisely why Project 1's playbook already used ansible.builtin.systemd — a proper module takes name: as a structured parameter, not a shell string, which is a second, independent layer of protection beyond the survey's own input constraint.

▲

Free-text fields are not automatically dangerous — they're dangerous specifically when their value flows into something that interprets it as code or a command. restart_reason is safe as free text because the playbook only ever uses it in a debug message or as metadata, never as part of a command string.

◆

Password-type survey fields are not Credentials. They're masked for display, not encrypted at rest the way Project 6's Credentials are. If a workflow genuinely needs a secret, use a Credential — never a Password-type survey question standing in for one.

Run It — Production Incident

Incident: "My Survey Answer Isn't Reaching the Playbook"

Sara Khan

"I picked sshd in the survey, but the job output shows it restarted httpd anyway."

StageWhat you do
OBSERVEJob completed successfully, but acted on the wrong service — not a failure, a silent wrong-behavior bug, which is often more concerning than an outright failure.
COLLECT EVIDENCEOpen the job's Details tab → check the actual extra_vars that were passed into this specific job run. You find service_name: httpd was recorded — meaning the survey answer genuinely wasn't sshd for this run, or something overrode it.
ISOLATE FAILURECheck the playbook itself for anything that could out-rank a survey answer. You find a leftover task: set_fact: service_name: httpd placed after the variable is first used, added during early testing in Project 1 and never removed.
CHECK DEPENDENCIESPer the precedence table, a set_fact inside the play itself takes effect for every subsequent task in that run — it doesn't "lose" to the survey answer, because Ansible facts set mid-play simply overwrite the variable going forward from that point.
IDENTIFY ROOT CAUSELeftover debug/testing code in the playbook was silently overwriting the survey's variable — a code-review gap, not a RHAAP or survey misconfiguration.
FIXRemove the stray set_fact task from the playbook, commit and tag the fix following Project 4's promotion process, and update the production Project's pinned tag.
VALIDATERe-launch with the survey, selecting sshd again, and confirm the job's recorded extra_vars and actual behavior now match.
PREVENT RECURRENCEAdd "no stray set_fact overwriting survey-supplied variables" as a specific line item in the Job Template Governance checklist being built in Project 9.
◆

The diagnostic habit worth keeping: when a survey answer doesn't seem to take effect, check the job's actual recorded extra_vars first — this tells you definitively whether the survey passed the value correctly, separating "RHAAP didn't send it" from "the playbook received it and then something inside the playbook overwrote it," which are very different bugs with very different fixes.

Practice

Interview Preparation

Q1. How do survey answers make their way into a playbook?
Each survey question's "answer variable name" becomes an extra variable for that specific job run — functionally identical to variables passed any other way, just supplied interactively by the launcher instead of hard-coded or set elsewhere.
Q2. Where do survey answers sit in Ansible's variable precedence?
As Job Template extra variables — below explicit launch-time extra_vars, but above the playbook's own vars: block, inventory variables, and role defaults. This lets a survey answer override a playbook's built-in default without editing the playbook.
Q3. Why prefer Multiple Choice over free text for a field like a service name?
It constrains the possible values to a pre-approved, known-safe set, which both prevents typos/invalid input and — critically — closes off command-injection risk if that variable is ever used to construct a command string. Free text should be reserved for genuinely descriptive fields that never influence what actually executes.
Follow-up: "Is a proper Ansible module enough protection on its own?" — It helps a lot (structured parameters instead of raw shell strings), but constraining the input itself at the survey level is a second, independent layer of defense — defense in depth, not an either/or.
Q4. Is a Password-type survey field the same as a Credential?
No. It's masked for on-screen and log display, but it's not encrypted at rest the way a Credential's secret is. Genuine secrets should always use a Credential object, not a Password survey question.
Q5. A survey answer doesn't seem to be reaching the playbook as expected. How do you investigate?
First check the job's actual recorded extra_vars to confirm whether RHAAP passed the value correctly — if it did, look inside the playbook for something with equal or higher effective precedence at that point in execution, like a set_fact task overwriting it mid-play, rather than assuming a RHAAP-side bug.
