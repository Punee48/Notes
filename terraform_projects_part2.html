Amazon EKS Kubernetes Cluster

Kubernetes AWS EKS Advanced
📖 The Story

TechNova is going all-in on microservices. They have 15 services, each on separate EC2 instances. Operations are a nightmare — deployments are manual, scaling is manual, and a single failed EC2 means a service is down. Your CTO attends AWS re:Invent and returns with one message: "We're moving everything to Kubernetes. EKS on AWS. I need a fully managed cluster ready in 2 weeks. No excuses." You open your Terraform editor and start building the cluster that will host TechNova's entire production workload.

🧠 Concepts Covered
  • EKS (Elastic Kubernetes Service): AWS-managed Kubernetes control plane. AWS handles etcd, API server, scheduler.
  • Node Groups: EC2 instances that run your containers (worker nodes). Managed by AWS Auto Scaling.
  • IAM for Service Accounts (IRSA): Pods get IAM permissions without hardcoding credentials — using OIDC federation
  • Cluster Add-ons: CoreDNS, kube-proxy, VPC CNI — AWS-managed Kubernetes plugins
  • Fargate Profile: Run pods on serverless compute — no EC2 nodes to manage
  • aws_eks_cluster data source: Fetch cluster info for kubectl configuration
EKS Control Plane (AWS Managed — you don't see these EC2s)
└── API Server · etcd · Scheduler · Controller Manager

Your VPC
├── Public Subnets ── ALB Ingress Controller
└── Private Subnets
    ├── Node Group: system (t3.medium × 2) ── CoreDNS, kube-proxy
    ├── Node Group: app (t3.large × 3) ── Your 15 microservices
    └── Fargate Profile ── Batch/cron jobs

  name = "technova-eks-cluster-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "eks.amazonaws.com" }
      # The EKS service assumes this role to manage AWS resources
    }]
  })
}

# Attach AWS-managed policies to cluster role
resource "aws_iam_role_policy_attachment" "eks_cluster_policy" {
  policy_arn = "arn:aws:iam::aws:policy/AmazonEKSClusterPolicy"
  role       = aws_iam_role.eks_cluster_role.name
}

# ─── EKS CLUSTER ──────────────────────────────────────────────
resource "aws_eks_cluster" "main" {
  name     = "technova-cluster"
  role_arn = aws_iam_role.eks_cluster_role.arn
  version  = "1.29"   # Kubernetes version

  vpc_config {
    subnet_ids              = concat(
      [aws_subnet.public_1.id,  aws_subnet.public_2.id],
      [aws_subnet.private_1.id, aws_subnet.private_2.id]
    )
    # EKS needs subnets in multiple AZs. Control plane uses all.

    endpoint_public_access  = true
    # Allow kubectl from the internet (restrict with public_access_cidrs in prod)
    endpoint_private_access = true
    # Nodes communicate with control plane via private network

    public_access_cidrs = ["0.0.0.0/0"]
    # PRODUCTION: restrict to your office IP or VPN CIDR
  }

  enabled_cluster_log_types = [
    "api",            # API server logs
    "audit",          # Who did what in K8s
    "authenticator",  # Authentication logs
    "controllerManager",
    "scheduler"
  ]

  depends_on = [aws_iam_role_policy_attachment.eks_cluster_policy]
}

# Three managed policies required for worker nodes
locals {
  node_policies = [
    "arn:aws:iam::aws:policy/AmazonEKSWorkerNodePolicy",
    # Allows nodes to connect to EKS cluster
    "arn:aws:iam::aws:policy/AmazonEKS_CNI_Policy",
    # Allows VPC CNI plugin to manage pod networking
    "arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly"
    # Allows nodes to pull container images from ECR
  ]
}

resource "aws_iam_role_policy_attachment" "node_policies" {
  for_each   = toset(local.node_policies)
  # for_each on a set creates one resource per policy
  policy_arn = each.value   # each.value = current policy ARN in loop
  role       = aws_iam_role.node_group_role.name
}

# ─── NODE GROUP: System (for system pods) ─────────────────────
resource "aws_eks_node_group" "system" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "system"
  node_role_arn   = aws_iam_role.node_group_role.arn
  subnet_ids      = [aws_subnet.private_1.id, aws_subnet.private_2.id]
  # Worker nodes ALWAYS go in private subnets

  instance_types = ["t3.medium"]
  disk_size      = 20   # GB of EBS storage per node
  ami_type       = "AL2_x86_64"   # Amazon Linux 2 — recommended for EKS

  scaling_config {
    desired_size = 2
    max_size     = 4
    min_size     = 1
  }

  update_config {
    max_unavailable = 1   # During node updates, only 1 node down at a time
  }

  # Taint: mark system nodes so only system pods schedule here
  taint {
    key    = "node-role"
    value  = "system"
    effect = "NO_SCHEDULE"   # App pods cannot schedule here unless they tolerate this taint
  }

  labels = { role = "system" }
  depends_on = [aws_iam_role_policy_attachment.node_policies]
}

# ─── NODE GROUP: Application (for your microservices) ─────────
resource "aws_eks_node_group" "app" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "app"
  node_role_arn   = aws_iam_role.node_group_role.arn
  subnet_ids      = [aws_subnet.private_1.id, aws_subnet.private_2.id]
  instance_types  = ["t3.large"]

  scaling_config {
    desired_size = 3

🔍 Word-by-Word Explanation
version = "1.29"
Kubernetes version for the control plane. Always pin a version — auto-updates can break things. Plan upgrades carefully.
endpoint_private_access = true
Nodes talk to the API server over the private network. Critical for security — without this, node↔control plane traffic goes over the internet.
for_each = toset(local.node_policies)
Creates one aws_iam_role_policy_attachment resource per policy ARN in the list. More DRY than writing 3 separate attachment blocks.
taint / NO_SCHEDULE
A Kubernetes taint marks a node as special. NO_SCHEDULE means only pods with a matching "toleration" can schedule on these nodes — used to reserve nodes for system workloads.
max_unavailable = 1
During a rolling node update, at most 1 node is drained and replaced at a time. Prevents full cluster downtime during Kubernetes version upgrades.
vpc-cni addon
The VPC Container Network Interface plugin. In EKS, each pod gets a real VPC IP address (not a virtual overlay IP). This allows direct pod-to-pod communication within the VPC.

Interview Answer: "What's the difference between EKS and ECS?" — EKS runs standard Kubernetes (portable, open-source). ECS is AWS-proprietary container orchestration. EKS lets you use the same Kubernetes knowledge on any cloud. Most MNCs use EKS because teams can port workloads to GKE (Google) or AKS (Azure) without rewiring.

CI/CD Pipeline with AWS CodePipeline + CodeBuild

CI/CD CodePipeline Advanced
📖 The Story

TechNova's developers deploy by SSHing into servers and running git pull. Last Friday, a developer ran git pull on the production server without realizing it — pulling in half-tested code. The entire checkout feature broke during peak traffic. Your manager Priya says: "I need a pipeline. Code goes to GitHub → automated tests run → Docker image builds → deploys to ECS. Nobody touches production servers manually. EVER again." You're about to build TechNova's first proper CI/CD pipeline.

🧠 Concepts Covered
  • CodePipeline: AWS orchestration — connects source → build → deploy stages
  • CodeBuild: AWS-managed build environment that runs your tests and builds Docker images
  • ECR (Elastic Container Registry): AWS's Docker Hub — private Docker image registry
  • buildspec.yml: The instruction file CodeBuild follows (like a Jenkinsfile)
  • S3 Artifact Store: CodePipeline stores pipeline artifacts (build outputs) in S3
  • CodeStar Connection: The secure link between CodePipeline and GitHub
  • Pipeline Stages: Source → Build → Test → Deploy — gates that code must pass through

# ─── CODEPIPELINE ─────────────────────────────────────────────
resource "aws_codepipeline" "app" {
  name     = "technova-payment-pipeline"
  role_arn = aws_iam_role.codepipeline_role.arn

  artifact_store {
    location = aws_s3_bucket.pipeline_artifacts.bucket
    type     = "S3"
  }

  # ── STAGE 1: Source ────────────────────────────────────────
  stage {
    name = "Source"
    action {
      name             = "GitHub_Source"
      category         = "Source"
      owner            = "AWS"
      provider         = "CodeStarSourceConnection"
      version          = "1"
      output_artifacts = ["source_output"]

      configuration = {
        ConnectionArn    = aws_codestarconnections_connection.github.arn
        FullRepositoryId = "technova/payment-service"
        BranchName       = "main"   # Trigger on pushes to main branch
        DetectChanges    = "true"   # Auto-trigger on git push
      }
    }
  }

  # ── STAGE 2: Build & Test ──────────────────────────────────
  stage {
    name = "Build"
    action {
      name             = "Build_and_Test"
      category         = "Build"
      owner            = "AWS"
      provider         = "CodeBuild"
      version          = "1"
      input_artifacts  = ["source_output"]   # Receives source from Stage 1
      output_artifacts = ["build_output"]    # Passes image definition to Stage 3

      configuration = {
        ProjectName = aws_codebuild_project.app_build.name
      }
    }
  }

  # ── STAGE 3: Deploy to ECS ─────────────────────────────────
  stage {
    name = "Deploy"
    action {
      name            = "Deploy_to_ECS"
      category        = "Deploy"
      owner           = "AWS"
      provider        = "ECS"
      version         = "1"
      input_artifacts = ["build_output"]

      configuration = {
        ClusterName = aws_ecs_cluster.main.name
        ServiceName = aws_ecs_service.payment.name
        FileName    = "imagedefinitions.json"
        # imagedefinitions.json: tells ECS which new image to deploy
        # CodeBuild creates this file with the new ECR image tag
      }
    }
  }
}

📄 buildspec.yml — Place this in your repository root

buildspec.yml (in your GitHub repo) YAML 
version: 0.2

phases:
  pre_build:
    commands:
      # Log in to ECR (get a Docker token)
      - aws ecr get-login-password --region $AWS_DEFAULT_REGION | docker login --username AWS --password-stdin $ECR_REPO_URI
      # Set image tag = first 8 chars of git commit SHA (unique per commit)
      - IMAGE_TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-8)

  build:
    commands:
      # Run unit tests first — if they fail, build stops here
      - pip install -r requirements.txt && python -m pytest tests/ -v
      # Build Docker image
      - docker build -t $ECR_REPO_URI:$IMAGE_TAG .
      # Also tag as "latest" for convenience
      - docker tag $ECR_REPO_URI:$IMAGE_TAG $ECR_REPO_URI:latest

  post_build:
    commands:
      # Push both tags to ECR
      - docker push $ECR_REPO_URI:$IMAGE_TAG
      - docker push $ECR_REPO_URI:latest
      # Create imagedefinitions.json — CodePipeline needs this to deploy to ECS
      - printf '[{"name":"payment-service","imageUri":"%s"}]' $ECR_REPO_URI:$IMAGE_TAG > imagedefinitions.json

artifacts:
  files:
    - imagedefinitions.json   # Pass this to the Deploy stage

CloudWatch Monitoring, Alarms & Auto-Remediation

Monitoring CloudWatch Observability
📖 The Story

TechNova's on-call engineer Ravi gets woken up at 3 AM. The payment service is down. Nobody knew for 45 minutes — users were silently getting errors. Ravi asks: "Why didn't anyone alert us?" The answer: there are no monitors. No dashboards. No alarms. Your CTO now mandates: "I need to know about any problem within 60 seconds, not 45 minutes. CPU spikes, error rates, disk full — everything must be monitored and alert our on-call team on Slack and phone."

🧠 Concepts Covered
  • CloudWatch Metrics: AWS automatically collects CPU, network, disk metrics for most services
  • CloudWatch Alarms: Triggers when a metric breaches a threshold for N consecutive periods
  • SNS (Simple Notification Service): Fan-out notification system — sends alerts to email, Slack, SMS, Lambda
  • CloudWatch Dashboard: Visual monitoring board — defined as code with Terraform
  • CloudWatch Log Groups + Metric Filters: Extract metrics from log patterns (e.g., count 5xx errors)
  • CloudWatch Composite Alarms: Combine multiple alarms with AND/OR logic

# ─── EC2 CPU ALARM ────────────────────────────────────────────
resource "aws_cloudwatch_metric_alarm" "high_cpu" {
  alarm_name          = "technova-high-cpu"
  comparison_operator = "GreaterThanThreshold"
  # Fire when metric > threshold
  evaluation_periods  = 3
  # Must breach threshold for 3 consecutive periods (3 × 5 min = 15 min)
  metric_name         = "CPUUtilization"  # Built-in EC2 metric
  namespace           = "AWS/EC2"          # Where the metric lives
  period              = 300                # Evaluate every 5 minutes (300 seconds)
  statistic           = "Average"          # Use average CPU across the period
  threshold           = 85                 # Alert if CPU > 85%
  alarm_description   = "EC2 CPU above 85% for 15 minutes"

  dimensions = {
    AutoScalingGroupName = aws_autoscaling_group.web_asg.name
    # Target the specific ASG (can also target specific instance ID)
  }

  alarm_actions = [aws_sns_topic.alerts.arn]     # Notify when ALARM
  ok_actions    = [aws_sns_topic.alerts.arn]     # Notify when back to OK
  insufficient_data_actions = []
}

# ─── RDS CONNECTION COUNT ALARM ───────────────────────────────
resource "aws_cloudwatch_metric_alarm" "rds_connections" {
  alarm_name          = "technova-rds-high-connections"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "DatabaseConnections"
  namespace           = "AWS/RDS"
  period              = 60         # Check every 1 minute
  statistic           = "Maximum"  # Use peak connections, not average
  threshold           = 400        # Alert if DB connections > 400

  dimensions = {
    DBInstanceIdentifier = aws_db_instance.primary.identifier
  }

  alarm_actions = [aws_sns_topic.alerts.arn]
}

# ─── CUSTOM METRIC FILTER (Extract from Logs) ─────────────────
# Count HTTP 5xx errors from application logs
resource "aws_cloudwatch_log_group" "app" {
  name              = "/technova/payment-service"
  retention_in_days = 30   # Auto-delete logs after 30 days (saves cost)
}

resource "aws_cloudwatch_log_metric_filter" "error_count" {
  name           = "5xx-error-count"
  pattern        = "[timestamp, requestId, level=\"ERROR\", ...]"
  # Pattern matches log lines containing "ERROR" — counts them as a metric
  log_group_name = aws_cloudwatch_log_group.app.name

  metric_transformation {
    name      = "ErrorCount"
    namespace = "TechNova/Application"   # Your custom namespace
    value     = "1"   # Each matching log line counts as 1
    unit      = "Count"
  }
}

# Alarm on the custom metric extracted above
resource "aws_cloudwatch_metric_alarm" "error_rate" {
  alarm_name          = "technova-high-error-rate"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 1
  metric_name         = "ErrorCount"
  namespace           = "TechNova/Application"   # Custom namespace
  period              = 60
  statistic           = "Sum"     # Total errors in the 60-second window
  threshold           = 10        # Alert if more than 10 errors per minute
  treat_missing_data  = "notBreaching"   # No data = no errors = OK
  alarm_actions       = [aws_sns_topic.alerts.arn]
}

Route 53 DNS Management + ACM SSL Certificates

Route 53 SSL/TLS DNS
📖 The Story

TechNova just bought the domain technova.io. Users currently access the app via the ugly ALB URL: http://technova-alb-1234567.us-east-1.elb.amazonaws.com. The CEO sees this in a demo and is embarrassed. Also, the site is HTTP — no HTTPS. The security team flags it as a critical vulnerability. You need: https://app.technova.io → ALB, with a valid SSL certificate. And you need it done via Terraform, not by clicking around in the console.

🧠 Concepts Covered
  • Route 53 Hosted Zone: AWS's DNS service — contains all DNS records for your domain
  • A Record (ALIAS): Maps domain name to AWS resource (ALB, CloudFront) — free and no TTL issues
  • ACM (Certificate Manager): Free SSL/TLS certificates that auto-renew — zero cost
  • DNS Validation: ACM proves you own the domain by adding a CNAME record to Route 53
  • ALB HTTPS Listener: Terminates SSL at the load balancer — backends use plain HTTP
  • Health Checks + Failover Routing: Route 53 can detect failures and route to a backup region
main.tf — Route 53 + ACM HCL 
# ─── ROUTE 53 HOSTED ZONE ─────────────────────────────────────
# Option A: Create new zone (if you're transferring domain to Route 53)
resource "aws_route53_zone" "main" {
  name = "technova.io"
  # After creation, copy the 4 nameservers from outputs and
  # update them at your domain registrar (GoDaddy, Namecheap, etc.)
}

# Option B: Reference existing zone (more common in MNCs)
data "aws_route53_zone" "main" {
  name         = "technova.io"
  private_zone = false   # Public hosted zone (not internal DNS)
}

# ─── ACM SSL CERTIFICATE ──────────────────────────────────────
# Request a free SSL cert from AWS Certificate Manager
resource "aws_acm_certificate" "main" {
  domain_name       = "technova.io"
  validation_method = "DNS"   # Prove domain ownership via DNS record
  # Alternative: "EMAIL" — sends to whois email addresses

  subject_alternative_names = [
    "*.technova.io"   # Wildcard covers app.technova.io, api.technova.io, etc.
  ]

  lifecycle {
    create_before_destroy = true
    # Always create new cert before destroying old one
    # Prevents a moment where no valid cert exists
  }
}

# ─── CERTIFICATE VALIDATION ───────────────────────────────────
# ACM tells you: "Add this CNAME to your DNS to prove domain ownership"
# Terraform does this automatically!

resource "aws_route53_record" "cert_validation" {
  for_each = {
    for dvo in aws_acm_certificate.main.domain_validation_options : dvo.domain_name => {
      name   = dvo.resource_record_name
      record = dvo.resource_record_value
      type   = dvo.resource_record_type
    }
  }
  # This creates one Route 53 CNAME record per domain in the cert

  allow_overwrite = true
  name            = each.value.name
  records         = [each.value.record]
  ttl             = 60
  type            = each.value.type
  zone_id         = data.aws_route53_zone.main.zone_id
}

# Wait for ACM to validate the certificate
resource "aws_acm_certificate_validation" "main" {
  certificate_arn         = aws_acm_certificate.main.arn
  validation_record_fqdns = [for record in aws_route53_record.cert_validation : record.fqdn]
  # Terraform waits here until ACM confirms the DNS validation passes
  # This can take 1-30 minutes
}

# ─── ALB HTTPS LISTENER ───────────────────────────────────────
# Add HTTPS (443) listener to the ALB from Project 3
resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.web_alb.arn
  port              = "443"
  protocol          = "HTTPS"
  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  # TLS 1.3 policy — most secure option. Blocks old TLS 1.0/1.1.
  certificate_arn   = aws_acm_certificate_validation.main.certificate_arn

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.web_tg.arn
  }
}

# HTTP listener: redirect HTTP → HTTPS (not forward)
resource "aws_lb_listener" "http_redirect" {
  load_balancer_arn = aws_lb.web_alb.arn
  port              = "80"
  protocol          = "HTTP"

  default_action {
    type = "redirect"   # 301 redirect, not forward
    redirect {
      port        = "443"
      protocol    = "HTTPS"
      status_code = "HTTP_301"   # Permanent redirect
    }
  }
}

# ─── DNS RECORD: app.technova.io → ALB ───────────────────────
resource "aws_route53_record" "app" {
  zone_id = data.aws_route53_zone.main.zone_id
  name    = "app.technova.io"
  type    = "A"   # A record points to an IP

  alias {
    name                   = aws_lb.web_alb.dns_name
    zone_id                = aws_lb.web_alb.zone_id
    evaluate_target_health = true
    # ALIAS record (not CNAME) — free, faster, works at zone apex
    # evaluate_target_health: Route 53 monitors the ALB health
  }
}

Event-Driven Architecture with SQS + SNS

SQS / SNS Event-Driven Decoupling
📖 The Story

TechNova's payment system calls the notification service directly (synchronous). When a payment completes → it calls the SMS API → then the email API → then updates the analytics DB. This chain takes 3 seconds. If the SMS service is down, the whole payment fails. Your architect Ramesh explains: "Services should not call each other directly. When payment completes, it fires an event. All other systems subscribe to that event independently. Payment doesn't know or care who's listening. That's decoupling."

🧠 Concepts Covered
  • SNS Topic: The "publisher" — sends one message to many subscribers (fan-out)
  • SQS Queue: A buffer that stores messages until a consumer processes them
  • SNS→SQS Fan-out: SNS sends one event to multiple SQS queues simultaneously
  • Dead Letter Queue (DLQ): Where failed messages go after max retry attempts
  • Visibility Timeout: How long a message is "invisible" while being processed
  • SQS + Lambda Event Source Mapping: Lambda automatically polls SQS and processes messages
Payment Service → SNS Topic "payment.completed"
    ├── SQS Queue: notification-queue → Lambda → SMS + Email
    ├── SQS Queue: analytics-queue → Lambda → Update DynamoDB
    └── SQS Queue: audit-queue → Lambda → Write audit log to S3

Each queue has its own DLQ for failed messages

  name = "payment-completed"
  # Payment service publishes here when a payment succeeds
  # It doesn't know or care who listens

# ─── DEAD LETTER QUEUES ───────────────────────────────────────

resource "aws_sqs_queue" "notification_dlq" {
  name                      = "notification-dlq"
  message_retention_seconds = 1209600   # Keep failed messages for 14 days
}

# ─── SQS QUEUES ───────────────────────────────────────────────
resource "aws_sqs_queue" "notification" {
  name                       = "notification-queue"
  visibility_timeout_seconds = 60
  # When Lambda picks up a message, it's hidden for 60 seconds
  # If Lambda crashes, message reappears after 60 seconds

  message_retention_seconds  = 86400   # Keep messages 1 day if unprocessed
  receive_wait_time_seconds  = 20      # Long polling: wait up to 20s for messages (cheaper)

  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.notification_dlq.arn
    maxReceiveCount     = 3
    # After 3 failed processing attempts, send to DLQ
    # DLQ lets you investigate and reprocess failed messages
  })
}

resource "aws_sqs_queue" "analytics" {
  name                       = "analytics-queue"
  visibility_timeout_seconds = 300   # Analytics processing can take up to 5 min
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.analytics_dlq.arn
    maxReceiveCount     = 5
  })
}

# ─── SQS QUEUE POLICY ─────────────────────────────────────────
# Allow SNS topic to send messages to SQS queue

    Version   = "2012-10-17"

      Effect    = "Allow"
      Principal = { Service = "sns.amazonaws.com" }
      Action    = "sqs:SendMessage"

        ArnEquals = { "aws:SourceArn" = aws_sns_topic.payment_events.arn }
        # Only this specific SNS topic can send messages here
      }
    }]
  })
}

resource "aws_sns_topic_subscription" "to_notification" {

  protocol             = "sqs"

  # raw_message_delivery=true: sends the message body directly
  # false (default): wraps in SNS envelope JSON — less useful for most cases
}

resource "aws_sns_topic_subscription" "to_analytics" {
  topic_arn = aws_sns_topic.payment_events.arn

  raw_message_delivery = true

# ─── LAMBDA EVENT SOURCE MAPPING ──────────────────────────────
# Lambda polls SQS and auto-triggers on new messages
resource "aws_lambda_event_source_mapping" "notification_trigger" {
  event_source_arn                   = aws_sqs_queue.notification.arn
  function_name                      = aws_lambda_function.notification_handler.arn
  batch_size                         = 10
  # Process up to 10 messages at once (batching = more efficient)
  maximum_batching_window_in_seconds = 5
  # Wait up to 5 seconds to accumulate 10 messages before triggering

  function_response_types = ["ReportBatchItemFailures"]
  # Partial batch failures: if 2 of 10 messages fail, only requeue those 2
  # Without this: all 10 are retried even if 8 succeeded

Transit Gateway — Multi-VPC Hub-and-Spoke Network

Transit Gateway Advanced Networking Enterprise
📖 The Story

TechNova has grown. They now have 4 separate AWS accounts: Production, Staging, Shared Services (security tools, monitoring), and Dev. Each account has its own VPC. The security team needs a shared VPC with a WAF and intrusion detection system that ALL traffic must pass through. The payment team's VPC must talk to the shared services VPC, but NOT to the dev VPC. Without Transit Gateway, you'd need N×(N-1)/2 VPC peering connections — 6 connections for 4 VPCs. Transit Gateway is the central hub.

🧠 Concepts Covered
  • Transit Gateway (TGW): A regional network hub that connects VPCs and on-premise networks
  • TGW Attachments: Connect each VPC to the Transit Gateway
  • TGW Route Tables: Control which VPCs can talk to each other — fine-grained isolation
  • VPC Peering vs TGW: Peering = point-to-point, TGW = hub-and-spoke (scales better)
  • Resource Access Manager (RAM): Share TGW across AWS accounts
  • Supernet routing: Route 10.0.0.0/8 at TGW to catch all spoke VPC traffic
Transit Gateway (us-east-1)
├── Attachment: Production VPC (10.10.0.0/16)
├── Attachment: Staging VPC (10.20.0.0/16)
├── Attachment: Shared Services VPC (10.30.0.0/16) ← security tools, monitoring
└── Attachment: Dev VPC (10.40.0.0/16)

TGW Route Tables:
• Production RT: → Shared Services ✅ → Dev ❌
• Dev RT: → Shared Services ✅ → Production ❌

🧠 Concepts Covered
  • ElastiCache: AWS-managed Redis or Memcached — in-memory data store, microsecond latency
  • Redis Cluster Mode: Shards data across multiple nodes — scales horizontally
  • Replication Group: Primary + read replicas — HA for ElastiCache
  • Cache Subnet Group: Like DB subnet group — tells ElastiCache which subnets to use
  • Automatic Failover: If primary fails, a read replica is promoted automatically
  • TTL (Time-To-Live): Keys expire automatically — prevents stale cache data

Terraform CI/CD Pipeline — GitHub Actions + Plan/Apply Automation

GitOps GitHub Actions Production Workflow
📖 The Story

TechNova's infrastructure has grown to 120 Terraform resources. Five engineers all have terraform apply access on their laptops. Last week an engineer applied an untested change on a Friday at 5 PM and broke the production database security group — it took 2 hours and 3 engineers to fix. Your architect Vijay sets a new rule: "No one applies Terraform manually anymore. ALL changes go through a Pull Request. Terraform plan runs automatically on every PR. The plan output is posted as a PR comment for review. terraform apply only runs on merge to main. This is GitOps — infrastructure is code and code goes through code review."

🧠 Concepts Covered
  • GitOps: Infrastructure changes treated like code — reviewed, tested, auditable
  • GitHub Actions: CI/CD automation that runs on git events (PR, push, merge)
  • OIDC Authentication: GitHub Actions proves identity to AWS without storing secret keys
  • PR Comments: Terraform plan output is automatically posted as a PR review comment
  • Concurrency Controls: Prevent two plan/apply jobs running simultaneously
  • Environment Protection Rules: Require approvals before applying to production
  • terraform fmt / validate / plan / apply: Full quality gate pipeline

📄 .github/workflows/terraform.yml

.github/workflows/terraform.yml YAML 
name: Terraform CI/CD

on:
  pull_request:
    branches: [main]       # Trigger on PRs targeting main
    paths: ['terraform/**'] # Only when terraform files change
  push:
    branches: [main]       # Trigger on merge to main
    paths: ['terraform/**']

concurrency:
  group: terraform-${{ github.ref }}
  cancel-in-progress: false
  # Prevent concurrent runs on the same branch
  # cancel-in-progress: false = queue them, don't cancel

permissions:
  id-token: write    # REQUIRED for OIDC token request
  contents: read
  pull-requests: write  # Post comments on PRs

jobs:
  # ── JOB 1: Runs on every PR ──────────────────────────────────
  terraform-plan:
    name: Terraform Plan
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    environment: staging   # Runs in staging environment context

    steps:
      # 1. Check out the code
      - name: Checkout
        uses: actions/checkout@v4

      # 2. Configure AWS credentials via OIDC (no secrets stored!)
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-terraform-role
          aws-region: us-east-1
          # GitHub proves its identity to AWS via OIDC token
          # No AWS access keys stored in GitHub Secrets!

      # 3. Install Terraform (specific version for reproducibility)
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.7.0   # Pin version — consistency across team

      # 4. Format check — fails if code isn't formatted
      - name: Terraform Format Check
        id: fmt
        run: terraform fmt -check -recursive
        working-directory: ./terraform

      # 5. Initialize Terraform (download providers, init backend)
      - name: Terraform Init
        id: init
        run: terraform init
        working-directory: ./terraform

      # 6. Validate HCL syntax and internal consistency
      - name: Terraform Validate
        id: validate
        run: terraform validate -no-color
        working-directory: ./terraform

      # 7. Run terraform plan, save output to file
      - name: Terraform Plan
        id: plan
        run: |
          terraform plan \
            -var-file="environments/${{ github.base_ref }}.tfvars" \
            -out=tfplan \
            -no-color \
            2>&1 | tee plan_output.txt
        working-directory: ./terraform
        continue-on-error: true   # Continue to post PR comment even if plan fails

      # 8. Post plan output as PR comment
      - name: Post Plan to PR
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const planOutput = fs.readFileSync('./terraform/plan_output.txt', 'utf8');
            const truncated = planOutput.length > 65000
              ? planOutput.substring(0, 65000) + '\n... (truncated)'
              : planOutput;

            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## 🏗️ Terraform Plan Results\n\`\`\`hcl\n${truncated}\n\`\`\`\n\n**Status:** ${{ steps.plan.outcome }}`
            });

  # ── JOB 2: Runs ONLY on merge to main ───────────────────────
  terraform-apply:
    name: Terraform Apply
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    environment: production   # Requires manual approval in GitHub Settings!

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-terraform-role
          aws-region: us-east-1

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.7.0

      - name: Terraform Init
        run: terraform init
        working-directory: ./terraform

      - name: Terraform Apply
        run: terraform apply -var-file="environments/prod.tfvars" -auto-approve
        working-directory: ./terraform
        # -auto-approve: no interactive "yes" needed in CI/CD
        # The GitHub "production" environment approval replaces the manual confirmation

# Create the OIDC identity provider for GitHub
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
  # thumbprint = GitHub's TLS certificate fingerprint
}

# IAM role that GitHub Actions can assume
resource "aws_iam_role" "github_terraform" {
  name = "github-terraform-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Federated = aws_iam_openid_connect_provider.github.arn }
      Action    = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "token.actions.githubusercontent.com:aud" = "sts.amazonaws.com"
        }
        StringLike = {
          "token.actions.githubusercontent.com:sub" = "repo:technova/*:ref:refs/heads/main"
          # ONLY the technova GitHub org, ONLY the main branch can assume this role
          # This is the critical security constraint!
        }
      }
    }]
  })
}

# Give this role permissions to manage Terraform infrastructure
resource "aws_iam_role_policy_attachment" "github_terraform" {

🔍 Key Workflow Concepts
concurrency: cancel-in-progress: false
Queues concurrent runs instead of cancelling them. You don't want a plan cancelled mid-execution — that could leave state in a bad position.
permissions: id-token: write
REQUIRED for OIDC. Allows the GitHub Actions job to request a JWT identity token from GitHub's token service, which AWS then validates.
environment: production
Links the job to a GitHub Environment. You can configure required reviewers in GitHub Settings → Environments. No one can apply to prod without someone approving.
-var-file="environments/prod.tfvars"
Different variable files for different environments. prod.tfvars has larger instance sizes, Multi-AZ enabled, higher retention. dev.tfvars has minimal settings.
StringLike: repo:technova/*:ref:refs/heads/main
The trust condition in the IAM role. Only GitHub Actions running in the technova org AND only on the main branch can assume this role. This prevents forks or feature branches from having AWS access.
