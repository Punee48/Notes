Project 27 — Just Enough Administration & Secure Remoting

Every script in this academy has run as a full administrator. That was always the biggest risk in the room.

Twenty-six projects of remoting have all quietly assumed the same thing: whoever authenticates gets full administrative power on the target server. If any single automation credential were ever compromised, the blast radius is the entire fleet. Today you build a constrained endpoint that lets an account run exactly the commands it needs — nothing more.

svc-healthcheck — can run Get-Service, Get-CimInstance only
Same account, no JEA — could run Remove-Item on anything
Compromised credential — blast radius now: read-only

01 The Production Story

A question during a security review that nobody had a comfortable answer to.
Security Architecture Review — A Question Nobody Wanted to Answer

A security architect reviewing the automation suite built across this entire academy asks a simple, uncomfortable question: "The service account these scripts run as — svc-healthcheck, svc-patchautomation, and the others — what can they actually do on a target server, if that credential were ever stolen?" The honest answer: essentially anything. Every script in this series has authenticated with an account holding local administrator rights on every target server, because that's what full remoting access requires by default.

The health check script only ever needs to read a handful of things — CPU, memory, service status. But the credential it authenticates with can, technically, delete files, stop any service, modify the registry, or do anything else a local administrator can do. If that one credential were ever phished, leaked in a config file, or misused by an insider, the actual damage ceiling has nothing to do with what the health check script was ever designed to do — it's bounded only by what a full administrator can do.

"This is the single biggest structural risk in everything we've built," Priya says. "Every account we've used has had far more power than any individual script has ever actually needed. I want us to build a constrained PowerShell endpoint — Just Enough Administration — where the health check account can run exactly the read-only commands it needs, and genuinely nothing else, even if someone tries to abuse that exact credential directly."

This project revisits every prior project's remoting model with a critical eye — the goal isn't a new check, it's reducing the real-world consequences of the worst-case scenario for everything already built.

Business Requirement

Limit automation service accounts to exactly the commands their specific scripts require, regardless of the account's underlying permissions.

Customer Requirement

Every script authenticates with a broadly privileged administrative account, because that's the simplest way to make remoting work.

Business Challenges

An over-privileged automation account is one of the highest-value targets for an attacker specifically because its real capability vastly exceeds its apparent purpose.

A JEA role capability file defining exactly the read-only cmdlets the health check role needs, registered as a constrained PowerShell session endpoint.

Project Scope

Expected Benefits

A compromised health-check credential becomes capable of almost nothing beyond exactly what the health check itself does — a dramatically smaller real-world risk.

03 New Concepts (Building on Projects 01–26)

You've used remoting in nearly every project. Here's how to constrain it — genuinely new, security-critical territory.
Just Enough Administration (JEA) — The Core Idea

What it is: A PowerShell security feature that lets you define a constrained remoting endpoint — connecting to it, even with administrative credentials, only allows running a specific, pre-approved list of commands, nothing else.

Why it's used today: This directly answers the security architect's question — instead of an account being able to do anything a local admin can do, JEA makes it so the account can ONLY run what's explicitly listed, regardless of what underlying permissions that account otherwise holds.

Role Capability Files (.psrc)

What it is: A PowerShell data file (New-PSRoleCapabilityFile) explicitly listing which cmdlets, functions, and even which specific parameters are allowed within a JEA session — everything not listed is simply unavailable, not just discouraged.

Why it's used today: This is the actual enforcement mechanism — a role capability file for the health check role would list exactly Get-Service, Get-CimInstance, and nothing resembling Remove-Item or Stop-Service, regardless of what the connecting account could otherwise do.

Session Configuration Files (.pssc) & Register-PSSessionConfiguration

What it is: A session configuration file ties a role capability to an actual named endpoint that scripts can connect to, and Register-PSSessionConfiguration installs that endpoint on the target server, ready for connections.

Why it's used today: This is what turns the role capability definition from a written policy into an actually enforced, connectable, constrained remoting endpoint — Invoke-Command -ConfigurationName "HealthCheckRole" instead of connecting to the full, unconstrained default session.

Virtual (RunAs) Accounts

What it is: JEA endpoints can be configured to actually execute commands under a temporary, privileged "virtual account" behind the scenes, while the account that connected never itself needs standing administrative rights at all — the connecting credential can be genuinely low-privileged, with JEA elevating only the specific, pre-approved commands.

Why it matters: This is the deepest version of least-privilege here — not just constraining WHAT commands run, but removing the need for the connecting account to hold real administrative rights in the first place.

This project's lesson applies retroactively to everything built in this academy: every prior project's Invoke-Command calls were technically capable of running any command the connecting account's underlying permissions allowed — JEA is what actually closes that gap for real, not just by convention or good intentions.

04 Architecture

The dashed line to "blocked" isn't a request being denied at runtime — it's a command that structurally doesn't exist inside this session at all, the same way a cmdlet from an unimported module simply isn't available.

06 The Code

RoleCapabilities\HealthCheckRole.psrc 
@{
    # Only cmdlets listed here can be run inside this JEA session — everything else simply isn't available
    VisibleCmdlets = @(
        'Get-Service',                                    # Read-only: matches Project 01/05's actual needs
        'Get-Process',                                     # Read-only: matches Project 09's actual needs
        @{ Name = 'Get-CimInstance'; Parameters = @{ Name = 'ClassName'; ValidateSet = 'Win32_OperatingSystem','Win32_LogicalDisk','Win32_Processor' } }
                                                             # Even an ALLOWED cmdlet can be restricted to only specific parameter values
    )

    VisibleFunctions = @('Write-AcademyLog')                # The shared module function from Project 21 — logging is fine, everything else stays blocked

    # Explicitly NOT listed, and therefore NOT available in this session at all:
    #   Remove-Item, Stop-Service, Set-ItemProperty, New-ADUser, Invoke-Sqlcmd, and literally everything else
}
Scripts\Register-JEAEndpoint.ps1 
<#
.SYNOPSIS
    JEA Constrained Endpoint Setup - ABC Bank Production Support
.DESCRIPTION
    Creates a session configuration tied to the HealthCheckRole
    capability and registers it as a connectable, constrained
    endpoint — run ONCE per server, as Administrator.
#>

# ============================================================
# STEP 1: CREATE THE SESSION CONFIGURATION FILE
# ============================================================

New-PSSessionConfigurationFile -Path "C:\JEA\HealthCheckEndpoint.pssc" `
    -SessionType RestrictedRemoteServer `                  # The baseline "start from nothing, add only what's listed" mode
    -RunAsVirtualAccount `                                  # Commands run under a temporary elevated virtual account — the CONNECTING account itself stays low-privilege
    -RoleDefinitions @{
        'ABCBANK\svc-healthcheck' = @{ RoleCapabilities = 'HealthCheckRole' }   # Only THIS account maps to THIS constrained role
    }

# ============================================================
# STEP 2: REGISTER IT AS A CONNECTABLE ENDPOINT
# ============================================================

Register-PSSessionConfiguration -Name "HealthCheckEndpoint" `                # The name scripts will connect to
    -Path "C:\JEA\HealthCheckEndpoint.pssc" `
    -Force

Write-Host "JEA endpoint 'HealthCheckEndpoint' registered. Test with:"
Write-Host '  Invoke-Command -ComputerName <server> -ConfigurationName HealthCheckEndpoint -ScriptBlock { Get-Service }' -ForegroundColor Cyan
Example: Using the constrained endpoint from Project 01's health check 
# The ONLY change needed in Project 01's original script: add -ConfigurationName
Invoke-Command -ComputerName $Server -ConfigurationName "HealthCheckEndpoint" -ScriptBlock {
    Get-CimInstance -ClassName Win32_OperatingSystem       # This works — it's on the allowed list
}

# This would FAIL inside the constrained session — Remove-Item was never made visible:
Invoke-Command -ComputerName $Server -ConfigurationName "HealthCheckEndpoint" -ScriptBlock {
    Remove-Item -Path "C:\Windows\System32\important.dll"              # CommandNotFoundException — it structurally doesn't exist here
}

07 Line-by-Line Explanation

@{ Name = 'Get-CimInstance'; Parameters = @{ Name = 'ClassName'; ValidateSet = 'Win32_OperatingSystem','Win32_LogicalDisk','Win32_Processor' } }
Even an allowed cmdlet can be constrained further at the parameter level — Get-CimInstance is permitted, but ONLY when its -ClassName parameter is one of these three specific values, blocking someone from using the same cmdlet to query something unrelated to health checking, like security event data.
-SessionType RestrictedRemoteServer
This starts the session configuration from a nearly-empty baseline rather than the normal full PowerShell environment — the opposite default from every unconstrained Invoke-Command used throughout this entire academy, where everything is available unless specifically restricted.
-RunAsVirtualAccount
Commands inside this JEA session actually execute under a short-lived, automatically-managed elevated identity — meaning the real svc-healthcheck account connecting to it never needs to hold genuine administrative rights on the target server at all, only the right to connect to this one specific constrained endpoint.
-ConfigurationName "HealthCheckEndpoint" on Invoke-Command
This is the entire change required in any earlier project's script to route it through the constrained endpoint instead of the full, unconstrained default session — proof that JEA can be adopted incrementally, project by project, without rewriting the actual check logic itself.
Common mistake: assuming JEA is only about which cmdlets are visible. As the ClassName ValidateSet example shows, real production JEA configurations often need parameter-level constraints too — an allowed cmdlet used with the wrong parameter value can still cause real harm if the cmdlet itself is powerful enough.

08 Script Execution Flow

StepWhat Happens
1. Endpoint Registration (one-time)An administrator runs Register-JEAEndpoint.ps1 once per server, installing the constrained endpoint alongside the normal, unconstrained default session.
2. Connection AttemptA script specifying -ConfigurationName "HealthCheckEndpoint" connects to the constrained session instead of the default one — this is an explicit, deliberate choice by the caller.
3. Command FilteringEvery command inside that session is checked against the role capability's VisibleCmdlets/VisibleFunctions list before it's even allowed to exist in that session's scope.
4. Virtual Account ExecutionAllowed commands actually execute under the temporary virtual account, not the connecting account's own (potentially much lower) privileges.
5. DisconnectionThe virtual account and any elevated context exist only for the duration of that session — nothing persists beyond it.

09 Windows Internals — In Simple English

How PowerShell Remoting Sessions Normally Work

By default, Invoke-Command against a server gives the connecting account's full underlying permissions inside that session — if the account is a local admin, the session has full admin capability, with no further restriction beyond whatever the script itself happens to run.

How JEA Actually Enforces Restrictions

JEA works by starting a session in a nearly-empty state and explicitly whitelisting only specific commands (and even specific parameter values) — anything not explicitly allowed genuinely doesn't exist in that session's command table, rather than existing but being blocked by a policy check.

What a Virtual Account Actually Is

A RunAs Virtual Account is a temporary, automatically-created and destroyed local administrator-equivalent identity that exists only for the lifetime of one JEA session — the connecting user's own real-world credentials never need standing elevated rights, dramatically reducing what's actually at risk if that specific credential is ever compromised.

Test the Constraint Actually Works

PowerShell — proving the constraint is real
# This should succeed — Get-Service is on the allowed list
Invoke-Command -ComputerName localhost -ConfigurationName "HealthCheckEndpoint" -ScriptBlock { Get-Service | Select-Object -First 3 }

# This should FAIL with a command-not-found style error — Stop-Service was never listed
Invoke-Command -ComputerName localhost -ConfigurationName "HealthCheckEndpoint" -ScriptBlock { Stop-Service -Name Spooler }

The second command failing is the entire point of this lab — if it succeeds, the constraint isn't actually working, and it's worth carefully re-reviewing the role capability file for what might have gone wrong.

12 Production Best Practices

Design JEA roles around what a script genuinely needs, discovered by reading its actual logic — not around convenient, broad guesses.
Constrain parameters, not just cmdlets, whenever a cmdlet is powerful enough that its parameters matter — Get-CimInstance's ClassName is a perfect example.
Use RunAs Virtual Accounts so connecting credentials themselves never need standing administrative rights — the JEA session grants elevation only for its own duration.
Adopt JEA incrementally, one automation role at a time, starting with your highest-risk or most broadly-scoped existing service accounts.

13 Interview Preparation

Q: Why does every prior project in this academy represent a real security risk, even though each individual script only does what it's designed to do?
The script's own logic isn't the actual security boundary — the connecting account's underlying permissions are, and every prior project authenticated with an account holding full administrative rights, meaning a compromised credential's real capability is bounded by what an admin can do, not by what the script itself was ever designed to do.
Q: How is JEA different from just trusting people not to run destructive commands?
JEA is a structural, enforced constraint — disallowed commands genuinely don't exist inside a JEA session, the same way an unimported module's cmdlets aren't available — it doesn't rely on discipline, policy, or trust, which is exactly what makes it a real security control rather than a guideline.
Q: Why constrain a cmdlet's parameters, not just whether the cmdlet itself is allowed?
Some cmdlets are powerful enough that the parameter values matter as much as the cmdlet name itself — Get-CimInstance is harmless for OS/disk/CPU classes but could expose unrelated, more sensitive data if used with a different ClassName, so constraining allowed parameter values closes that gap.
Q: What would you prioritize first when rolling JEA out across a large existing automation suite like this one?
The highest-risk or most broadly-scoped existing service accounts first — ones running with genuinely unnecessary administrative breadth relative to their actual script logic — rather than attempting to convert every single project simultaneously.

14 Key Learnings & Assignment

Key Learnings

  • Every prior project's remoting model granted far more capability than any individual script actually needed — the connecting account's permissions, not the script logic, define the real security boundary
  • JEA role capability files structurally remove disallowed commands from a session, rather than merely discouraging their use
  • Parameter-level constraints matter for cmdlets powerful enough that their arguments meaningfully change what they can do
  • RunAs Virtual Accounts let the connecting credential itself stay genuinely low-privileged, with elevation happening only inside the constrained session
