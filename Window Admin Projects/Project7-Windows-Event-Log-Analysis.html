Project 07 — Windows Event Log Analysis

The answer was already sitting in the Event Log — nobody had looked in one place, across all servers, at once

Windows records almost everything that goes wrong on its own. Today's project doesn't detect a live problem — it hunts through history, across dozens of servers at once, groups repeating errors together, and surfaces the pattern a human staring at one server's Event Viewer would never notice.

01 The Production Story

A recurring, low-grade problem that nobody connected — until someone finally looked at all the servers together.
Monday, 11:00 AM — The Recurring Mystery Ticket

For three weeks, a handful of app servers have intermittently thrown brief service hiccups — nothing bad enough to page anyone, just the occasional blip that a health check catches and a restart fixes. Each time, a different engineer investigates that one server, finds "a service crashed unexpectedly," restarts it, and closes the ticket.

Priya pulls you aside. "I just noticed something. I opened Event Viewer on three different servers this morning, comparing notes with two other tickets from last week. They're all the exact same Event ID, from the exact same source, within minutes of each other, across servers nobody thought were related. Nobody caught it because nobody was looking at more than one server's log at a time — Event Viewer just isn't built for that."

"I want a script that pulls Error and Critical-level events from the last 24 hours across our whole server list, groups them by Event ID so we can see which problems are actually recurring patterns versus one-off noise, and ranks them by how often they're happening. If the same Event ID is showing up on six servers in one day, that's not six unrelated incidents — that's one root cause we haven't found yet."

This project is about turning scattered, per-server noise into a single cross-server signal — the exact kind of pattern-finding a human manually clicking through Event Viewer, one server at a time, will almost always miss.

03 New Concepts (Building on Projects 01–06)

You already know remoting, config files, and Group-Object from Project 02. Here's what's new for log analysis.
Get-WinEvent (the Modern Replacement for Get-EventLog)

What it is: The current, faster cmdlet for querying the Windows Event Log, built on the modern ETW (Event Tracing for Windows) architecture. The older Get-EventLog only supports "classic" logs and is noticeably slower on large log files.

Why it's used today: Get-WinEvent can query any log (System, Application, Security, and modern application/service logs), and its -FilterHashtable parameter filters at the source before data even reaches PowerShell — critical for performance when scanning many servers.

Common mistake: Using Get-EventLog in new scripts out of old habit — it's considered legacy and doesn't scale as well across a large fleet.

-FilterHashtable

What it is: A hash table passed to Get-WinEvent that filters events at the Windows Event Log service itself — by LogName, Level (severity), time range, and more — before anything is sent back to your script.

Why it matters: Filtering here instead of piping to Where-Object afterward means Windows itself does the heavy lifting, only returning the (usually much smaller) set of events you actually asked for — a huge performance difference on a busy server's log.

Event Levels & Level Numbers

What it is: Every Windows event has a numeric Level: 1 = Critical, 2 = Error, 3 = Warning, 4 = Information, 5 = Verbose. -FilterHashtable @{ Level = 1,2 } asks only for Critical and Error events.

Why it's used today: We deliberately exclude Warning/Information noise — Priya wants the signal (things that actually failed), not the much larger volume of routine informational entries.

Time-Based Filtering — StartTime

What it is: -FilterHashtable @{ StartTime = (Get-Date).AddHours(-24) } asks only for events from the last 24 hours — the same date arithmetic from Project 06, applied to a query instead of a certificate.

Group-Object for Cross-Server Pattern Detection

What it is: You saw Group-Object in Project 02 grouping compliance results by status. Today it groups every error event, across every server, by its Event ID — instantly revealing which specific error is repeating most often, fleet-wide.

Why it's the heart of this project: This single grouping operation is exactly what turns "six separate tickets on six separate servers" into "one recurring pattern, six occurrences" — the insight Priya's story was built around.

Notice the reuse: Group-Object from Project 02, date arithmetic from Project 06, config-driven server lists from Project 02 — very little here is actually brand new logic. Most of production engineering is recombining a small set of solid techniques in a new context.

04 Architecture

Every server's log is scattered data in isolation. The Group-Object step is what turns 40 separate logs into a single ranked, fleet-wide pattern view — that consolidation is the entire value of this project.

06 The Script — Get-CrossServerEventPatterns.ps1

Scripts\Get-CrossServerEventPatterns.ps1 
<#
.SYNOPSIS
    Cross-Server Event Log Pattern Analysis - ABC Bank Production Support
.DESCRIPTION
    Pulls Error and Critical events from System and Application logs
    across a server list for a given time window, then groups them by
    Event ID to reveal recurring patterns hidden across individual logs.
#>

param(
    [int]$HoursBack = 24                          # How far back to look — configurable per run
)

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers = Get-Content -Path "C:\EventLogAnalysis\Config\servers.txt"
$LogNames = @("System", "Application")              # Logs we care about for this analysis
$Levels   = @(1, 2)                                # 1 = Critical, 2 = Error — deliberately excludes Warning/Info noise

$TimeTag       = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile       = "C:\EventLogAnalysis\Logs\EventAnalysis_$TimeTag.log"
$SummaryCSV    = "C:\EventLogAnalysis\Reports\EventAnalysis_${TimeTag}_Summary.csv"
$RawEventsCSV  = "C:\EventLogAnalysis\Reports\EventAnalysis_${TimeTag}_RawEvents.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-SERVER EVENT COLLECTION
# ============================================================

function Get-ServerErrorEvents {
    param([string]$ComputerName)

    try {
        $FilterParams = @{                          # Splatting the filter — same technique from Project 03
            LogName   = $LogNames
            Level     = $Levels
            StartTime = (Get-Date).AddHours(-$HoursBack)   # Date arithmetic, same pattern as Project 06
        }

        $Events = Invoke-Command -ComputerName $ComputerName -ArgumentList $FilterParams -ScriptBlock {
            param($Filter)
            Get-WinEvent -FilterHashtable $Filter -ErrorAction SilentlyContinue   # SilentlyContinue: no matching events isn't an error, it's good news
        }

        Write-Log "$ComputerName : found $($Events.Count) Error/Critical event(s) in the last $HoursBack hour(s)" "INFO"

        foreach ($Evt in $Events) {
            [PSCustomObject]@{
                ServerName = $ComputerName
                TimeCreated= $Evt.TimeCreated
                LogName    = $Evt.LogName
                EventID    = $Evt.Id
                LevelName  = $Evt.LevelDisplayName
                Source     = $Evt.ProviderName
                Message    = ($Evt.Message -split "`n")[0]     # Just the first line — full messages can be very long
            }
        }
    }
    catch {
        Write-Log "Error querying $ComputerName : $($_.Exception.Message)" "ERROR"
    }
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Event Pattern Analysis across $($Servers.Count) server(s), last $HoursBack hour(s) =====" "INFO"

$AllEvents = foreach ($Server in $Servers) {
    Get-ServerErrorEvents -ComputerName $Server
}

# ---- RAW EVENT EXPORT — every individual event, for drill-down ----
$AllEvents | Export-Csv -Path $RawEventsCSV -NoTypeInformation

# ---- PATTERN SUMMARY — grouped by Event ID, ranked by frequency ----
$Summary = $AllEvents |
    Group-Object EventID, Source |                                       # Group by the COMBINATION of Event ID and Source
    Sort-Object Count -Descending |                                      # Most frequent pattern first — the one most worth investigating
    Select-Object @{Name="EventID_Source";Expression={$_.Name}},
                  Count,
                  @{Name="AffectedServers";Expression={ ($_.Group.ServerName | Sort-Object -Unique) -join ", " }},   # Unique server list per pattern
                  @{Name="ServerCount";Expression={ ($_.Group.ServerName | Sort-Object -Unique).Count }},
                  @{Name="SampleMessage";Expression={ $_.Group[0].Message }}

$Summary | Format-Table -AutoSize -Wrap

$Summary | Export-Csv -Path $SummaryCSV -NoTypeInformation

$TopPattern = $Summary | Select-Object -First 1
if ($TopPattern -and $TopPattern.ServerCount -ge 3) {
    Write-Log "PATTERN ALERT: $($TopPattern.EventID_Source) occurred $($TopPattern.Count) times across $($TopPattern.ServerCount) servers" "WARNING"
}

Write-Log "===== Event Pattern Analysis Completed. Summary: $SummaryCSV =====" "INFO"

07 Line-by-Line Explanation

Get-WinEvent -FilterHashtable $Filter -ErrorAction SilentlyContinue
When a server genuinely has zero matching events, Get-WinEvent actually throws a "No events found" error rather than just returning an empty result — SilentlyContinue treats that as the good news it actually is, instead of letting it look like a real error in the log.
(StartTime = (Get-Date).AddHours(-$HoursBack)) inside the FilterHashtable
This is the same date-arithmetic idea from Project 06, but instead of measuring time until a future date, we're measuring back from right now — both are just DateTime math.
Group-Object EventID, Source
Passing two properties to Group-Object groups by the unique combination of both — this matters because the same numeric Event ID can mean different things depending on which source (service/application) raised it.
@{Name="AffectedServers"; Expression={ ($_.Group.ServerName | Sort-Object -Unique) -join ", " }}
Inside a Group-Object result, .Group holds every original event in that bucket. This calculated property pulls out just the server names from those grouped events, removes duplicates, and joins them into one readable string — exactly how we know a pattern spans "6 servers" without writing a separate counting loop.
Common mistake: grouping by Event ID alone without the Source/ProviderName. Different applications can reuse the same generic Event ID numbers for completely unrelated conditions — grouping by ID alone can make unrelated events look like one pattern.

08 Script Execution Flow

StepWhat Happens
1. Filter ConstructionThe FilterHashtable is built once, then splatted into every server's remote query — one consistent filter definition, reused everywhere.
2. Remote QueryEach server's own Windows Event Log service does the actual filtering before any data crosses the network — far more efficient than pulling everything and filtering locally.
3. Raw CollectionEvery individual matching event across every server accumulates into one flat array, tagged with which server it came from.
4. Grouping & RankingGroup-Object collapses potentially thousands of individual events into a short list of distinct patterns, sorted by how often each occurs.
5. Dual ReportingThe raw CSV preserves full drill-down detail; the summary CSV gives the "what should I look at first" view — different audiences need different levels of detail.

09 Windows Internals — In Simple English

How Event Viewer Actually Stores Logs

Modern Windows logs are stored in a binary, indexed format (.evtx files) managed by the Windows Event Log service, built on ETW — a high-performance logging framework used throughout the OS.

Why Get-WinEvent Is Faster Than Get-EventLog

Get-WinEvent queries the underlying ETW-based log store directly and supports server-side filtering; Get-EventLog uses an older API that generally has to pull more data before filtering can happen.

System vs Application Logs

The System log records OS and driver-level events (services, hardware, drivers); the Application log records events raised by installed software and applications — both matter for a complete picture.

12 Production Best Practices

Always filter at the source with FilterHashtable, not with Where-Object afterward — pulling every event from a busy log before filtering locally is slow and wasteful at scale.
Group by more than just Event ID when the same ID can mean different things from different sources — always include the provider/source in the grouping key.
Keep both a summary view and a raw drill-down export — Ops leadership wants the ranked pattern; the engineer fixing it needs the full detail.
Treat "no matching events" as a success outcome, not an error — SilentlyContinue plus a log line distinguishing "found nothing" from "the query itself failed" avoids false alarms.

13 Interview Preparation

Q: Why use Get-WinEvent instead of Get-EventLog?
Get-WinEvent is built on the modern ETW-based logging architecture, supports server-side filtering via FilterHashtable for much better performance, and can query any log type, not just the classic ones Get-EventLog is limited to.
Q: Why group by Event ID AND Source instead of Event ID alone?
Different applications and services can reuse the same generic numeric Event IDs for completely unrelated conditions — grouping by the source too ensures we're comparing genuinely the same recurring problem, not coincidentally identical ID numbers.
Q: How would you decide a pattern is worth escalating versus just noise?
A combination of frequency (how many times) and breadth (how many distinct servers) — a single error repeating hundreds of times on one server might just be a noisy but harmless condition, while the same error appearing even a handful of times across many different servers points to a shared root cause worth investigating.
Q: What's a real incident this project's approach would catch that individual server monitoring wouldn't?
Exactly the story's scenario — the same underlying issue quietly repeating across many servers, with each occurrence treated as an isolated, unrelated ticket until someone finally compares notes across the whole fleet at once.
