Same team, same bank, the next Monday. Your health check script from Project 01 is now running every morning — Priya has a new problem for you.

"Your health check script has been a lifesaver," Priya says. "Caught two stopped services already this week before anyone noticed. Now I need your help with something the auditors are hounding us about."

"Every second Tuesday of the month is Patch Tuesday — Microsoft releases security updates, and our Patch Management team pushes them out to all 500 servers within 72 hours per our compliance policy. But right now, confirming that a patch actually installed successfully on every server is still manual — someone RDPs in and checks Windows Update history one server at a time."

"Last quarter's audit flagged us because three servers were found still missing a critical security patch, six weeks after it was supposed to be deployed. Nobody caught it because nobody checked. That's now a documented compliance finding with my name on it."

"I need a script that takes our list of 'required KBs for this month' and checks every server against it — reachable or not, patched or not — and flags exactly which servers are missing exactly which patches. This time, instead of running on each server manually, we're going to reach out to each server using PowerShell Remoting — the real enterprise way multiple servers get managed at once."

This project introduces PowerShell Remoting — the single most important skill for managing more than one server at a time. Everything after this project will build on it.

03 New Concepts (Building on Project 01)

You already know variables, objects, pipelines, functions, try/catch, and CIM. Here's what's new today.
PowerShell Remoting & Invoke-Command

What it is: In Project 01, CIM queries reached out to remote servers behind the scenes over WinRM. Invoke-Command does this more directly — it literally runs a block of PowerShell code inside the remote server's own PowerShell session and sends the results back to you.

Why it's used today: Checking installed hotfixes is a command (Get-HotFix) that needs to run locally on each target server. Invoke-Command -ComputerName $Server -ScriptBlock { Get-HotFix } executes it remotely and returns the result to our script as if it ran locally.

Internally: WinRM opens an HTTP (or HTTPS) listener on the target server (default port 5985/5986). Your script authenticates, a temporary remote session is created, the script block runs there, and only the output objects travel back over the network — not raw text.

Best practice: Enable WinRM fleet-wide via Group Policy, not manually per server. Common mistake: forgetting WinRM must be enabled on the target server (Enable-PSRemoting) — it's off by default on workstations.

Get-HotFix

What it is: A built-in cmdlet that returns the list of Windows updates (KB articles) installed on a machine, each as an object with a HotFixID property like KB5034441.

Production nuance: Get-HotFix reads from the same source as "installed updates" in Control Panel — for a more complete picture including pending/failed updates, enterprises often use the Windows Update COM API or WSUS reporting, but Get-HotFix is the fast, no-dependency starting point.

Get-Content — Reading a Server List From a File

What it is: Reads a text file line by line and returns each line as a string. In Project 01 our server list was hardcoded in an array; today it comes from servers.txt, one hostname per line.

Why it matters: In production, you never hardcode a 500-server list inside a script — Operations updates a config file, and the script just reads whatever is current at run time.

ConvertFrom-Json — Reading Structured Config

What it is: Converts a JSON text file into a real PowerShell object you can work with directly, e.g. $Required = Get-Content required-kbs.json -Raw | ConvertFrom-Json.

Why it's used today: The "list of required KBs for this month" is exactly the kind of config that changes monthly — storing it as JSON keeps it outside the script and easy for the Patch Management team to update without touching code.

Where-Object & Compare-Object

Where-Object: Filters a collection down to only the objects matching a condition, e.g. finding which required KBs are missing from the installed list.

Compare-Object: Compares two collections and tells you exactly what's in one but not the other — perfect for diffing "required KBs" against "installed KBs" without writing manual loop-and-check logic.

Group-Object

What it is: Groups objects by a shared property value — e.g. grouping all our results by ComplianceStatus so the summary can say "3 servers Non-Compliant, 1 Partial, 496 Compliant" in one line.

Notice the pattern from Project 01 repeating: config stays in files, logic stays in the script, and results stay as structured objects until the very last step (export). That separation is what makes scripts maintainable at bank scale.

06 The Script — Test-PatchCompliance.ps1

Same disciplined structure as Project 01: config, logging function, worker function, main loop, export.
Scripts\Test-PatchCompliance.ps1 
<#
.SYNOPSIS
    Monthly Patch Compliance Validation - ABC Bank Production Support
.DESCRIPTION
    Uses PowerShell Remoting to check installed hotfixes on every server
    in Config\servers.txt against the required KB list in
    Config\required-kbs.json, then reports compliance status per server.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers = Get-Content -Path "C:\PatchValidation\Config\servers.txt"   # Read server list, one hostname per line

$RequiredConfig = Get-Content -Path "C:\PatchValidation\Config\required-kbs.json" -Raw |  # Read the JSON file as one raw string
                   ConvertFrom-Json                                                     # Parse it into a real PowerShell object

$RequiredKBs = $RequiredConfig.RequiredKBs                             # Pull just the array of required KB IDs

$TimeTag    = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile    = "C:\PatchValidation\Logs\PatchCheck_$TimeTag.log"
$ReportCSV  = "C:\PatchValidation\Reports\PatchCheck_$TimeTag.csv"
$ReportHTML = "C:\PatchValidation\Reports\PatchCheck_$TimeTag.html"

# ============================================================
# SECTION 2: LOGGING FUNCTION (same pattern as Project 01)
# ============================================================

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 3: MAIN COMPLIANCE CHECK FUNCTION
# ============================================================

function Test-ServerPatchCompliance {                # Checks ONE server's patch compliance
    param(
        [string]$ComputerName,
        [string[]]$RequiredKBs                          # Array of KB IDs this server must have
    )

    $Result = [PSCustomObject]@{
        ServerName       = $ComputerName
        Reachable        = $false
        InstalledCount   = 0
        MissingKBs       = ""
        ComplianceStatus = "UNKNOWN"
        CheckedAt        = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        if (-not (Test-Connection -ComputerName $ComputerName -Count 2 -Quiet)) {   # Same reachability gate as Project 01
            Write-Log "$ComputerName is UNREACHABLE" "ERROR"
            $Result.ComplianceStatus = "UNKNOWN - UNREACHABLE"
            return $Result
        }
        $Result.Reachable = $true

        # ---- REMOTE HOTFIX QUERY ----
        $InstalledHotFixes = Invoke-Command -ComputerName $ComputerName -ScriptBlock {   # Runs Get-HotFix INSIDE the remote server
            Get-HotFix | Select-Object -ExpandProperty HotFixID                          # Just the KB ID strings, e.g. "KB5034441"
        }

        $Result.InstalledCount = $InstalledHotFixes.Count

        # ---- COMPARE INSTALLED VS REQUIRED ----
        $Missing = Compare-Object -ReferenceObject $RequiredKBs -DifferenceObject $InstalledHotFixes |   # Diff the two lists
                   Where-Object { $_.SideIndicator -eq "<=" } |                              # "<=" means it's in Required but NOT in Installed
                   Select-Object -ExpandProperty InputObject                                # Pull out just the KB ID text

        if ($Missing) {
            $Result.MissingKBs = ($Missing -join ", ")                       # Turn the array into a readable comma list
            $Result.ComplianceStatus = if ($Missing.Count -eq $RequiredKBs.Count) { "NON-COMPLIANT" } else { "PARTIAL" }
        }
        else {
            $Result.ComplianceStatus = "COMPLIANT"
        }

        Write-Log "$ComputerName : $($Result.ComplianceStatus) (missing: $($Result.MissingKBs))" "INFO"
    }
    catch {
        Write-Log "Error checking $ComputerName : $($_.Exception.Message)" "ERROR"
        $Result.ComplianceStatus = "UNKNOWN - CHECK FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 4: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Patch Compliance Check for $($Servers.Count) servers =====" "INFO"
Write-Log "Required KBs this cycle: $($RequiredKBs -join ', ')" "INFO"

$AllResults = foreach ($Server in $Servers) {
    Test-ServerPatchCompliance -ComputerName $Server -RequiredKBs $RequiredKBs
}

$AllResults | Sort-Object ComplianceStatus | Format-Table -AutoSize

# ---- COMPLIANCE SUMMARY BY STATUS ----
$AllResults | Group-Object ComplianceStatus | ForEach-Object {                     # Groups results by status, one group per status value
    Write-Log "$($_.Name): $($_.Count) server(s)" "INFO"                              # $_.Name is the status text, $_.Count is how many servers share it
}

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$AllResults | ConvertTo-Html -Title "ABC Bank Monthly Patch Compliance Report" `
    -PreContent "<h1>Patch Compliance - $($RequiredConfig.Month)</h1>" |
    Out-File -FilePath $ReportHTML

Write-Log "===== Patch Compliance Check Completed. Report: $ReportHTML =====" "INFO"

07 Line-by-Line Explanation

Focused on what's genuinely new versus Project 01.
Invoke-Command -ComputerName $ComputerName -ScriptBlock { Get-HotFix | Select-Object -ExpandProperty HotFixID }
The { } is a script block — code that gets shipped over WinRM and executed on the remote server. -ExpandProperty unwraps just the HotFixID string values instead of returning full hotfix objects, giving us a clean array of KB IDs like "KB5034441".
Compare-Object -ReferenceObject $RequiredKBs -DifferenceObject $InstalledHotFixes
Returns every item that differs between the two lists, tagged with a SideIndicator: <= means "only in Reference" (required but not installed — what we want), => means "only in Difference" (installed but not required — irrelevant here).
Where-Object { $_.SideIndicator -eq "<=" }
Filters the compare results down to only the missing patches — this is the line that actually answers "what is this server missing?"
$AllResults | Group-Object ComplianceStatus | ForEach-Object { ... }
Group-Object buckets our 500 result objects by their ComplianceStatus value. Each bucket has a .Name (the status) and .Count (how many servers). This is how we build a one-line executive summary without writing manual counting logic.
Common mistake: reversing Reference and Difference in Compare-Object flips the meaning of <= and => — always double-check which list is "the standard we're checking against" (Reference) versus "what we actually found" (Difference).

08 Script Execution Flow

StepWhat Happens
1. Config LoadedGet-Content reads servers.txt into an array; ConvertFrom-Json parses required-kbs.json into an object with a .RequiredKBs array property.
2. Reachability GateSame as Project 01 — Test-Connection filters out dead servers before wasting a remoting attempt on them.
3. Remote SessionInvoke-Command opens a temporary WinRM session, authenticates, ships the script block, and runs it inside the remote server's own PowerShell host process.
4. Data ReturnsOnly the final output of the script block (the KB ID strings) is serialized and sent back across the network — not the entire remote session state.
5. Local ComparisonCompare-Object runs locally, on our automation host, comparing the returned list against the required list.
6. ReportingSame export pattern as Project 01: CSV for audit records, HTML for a readable management view, log file throughout.

09 Windows Internals — In Simple English

How Windows Updates Are Tracked

Windows keeps a local update history database. Each successfully installed patch gets a KB (Knowledge Base) article number recorded there — that's exactly what Get-HotFix reads.

How PowerShell Remoting Authenticates

By default, Invoke-Command uses the credentials of the account running the script (Kerberos, when the automation host and target are in the same Active Directory domain) — no password is typed or stored anywhere in our script.

WinRM Ports

WinRM listens on TCP 5985 (HTTP) or 5986 (HTTPS) by default. Banking environments almost always require the encrypted 5986 (HTTPS) listener for compliance.

12 Production Best Practices

Keep required-KB lists in version-controlled config files, not hardcoded — Patch Management updates this monthly and shouldn't need to touch script code.
Prefer HTTPS (5986) WinRM listeners in regulated environments — plain HTTP remoting sends data unencrypted on the wire.
Always gate remote calls behind a reachability check first — a hung Invoke-Command against a dead server can stall an entire run without a timeout.
Treat "UNREACHABLE" as its own status, never silently as "Compliant" — an unknown state must never look like a pass in a compliance report.

13 Interview Preparation

Q: What's the difference between CIM (used in Project 01) and Invoke-Command (used here)?
CIM queries a specific management data class through the CIM/WMI repository. Invoke-Command runs an arbitrary block of PowerShell code on the remote machine and returns whatever it outputs — much more flexible, since it can run any cmdlet, including ones with no CIM equivalent, like Get-HotFix.
Q: How would you scale this to 500 servers without it taking hours?
Invoke-Command natively supports passing an array of computer names and runs against them in parallel with a configurable throttle limit, instead of looping one server at a time — that's the first optimization I'd make.
Q: A server shows UNKNOWN - UNREACHABLE in the report. Is that a compliance failure?
It's a separate finding, not automatically a failure — but it must be investigated and resolved, since an unreachable server means we genuinely don't know its patch state, which is itself a risk worth escalating.
Q: Why store the required KB list as JSON instead of a simple text file like servers.txt?
The required-KB data needed extra structure (a month label alongside the KB array), which JSON supports naturally; a flat text file works fine when you only need one value per line, like the server list.

14 Key Learnings & Assignment

Key Learnings

  • PowerShell Remoting (Invoke-Command) runs code directly on remote servers and returns only the results
  • External config files (text and JSON) keep scripts flexible without code changes
  • Compare-Object is the fast, correct way to diff two lists instead of writing manual nested loops
  • Group-Object turns raw results into an executive summary in one line
