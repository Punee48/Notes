Project 09 — CPU & Memory Monitoring

A single reading lies. A sample window tells the truth — and names the process responsible.

Project 01's CPU check was one instant snapshot — exactly the kind of number that can trigger a false alarm from a half-second spike, or miss a real problem that started a moment before the check ran. Today we sample repeatedly over a real window using performance counters, and when something's genuinely sustained, we name exactly which process is responsible.

01 The Production Story

A false alarm and a missed real problem, in the same week — both caused by the same root issue.
Tuesday — Two Opposite Failures, One Cause

On Tuesday morning, your Project 01 health check flags SRV-APP02 as CRITICAL — CPU at 96%. An engineer drops everything to investigate... and finds the server sitting at a completely normal 22% CPU by the time they log in. Whatever spiked was gone in seconds — a single-instant snapshot caught a half-second blip and turned it into a false alarm that cost someone twenty minutes.

That same afternoon, SRV-DB01 has been running at 90%+ CPU for the better part of an hour — a genuinely serious, sustained load that's actually slowing down real transactions — but the health check happened to run during a brief lull and reported HEALTHY. Nobody noticed until customers started complaining about slow logins.

Priya connects the dots at the retro. "Both problems come from the exact same flaw: we're taking a single instant photograph and treating it like the whole movie. I want two things: first, sample CPU and memory over a real window — say, every 2 seconds for 30 seconds — and only call something CRITICAL if it's sustained across most of those samples, not just one lucky or unlucky moment. Second, when we DO confirm a real sustained problem, I want the report to immediately tell us which specific process is actually responsible, so whoever picks up the ticket doesn't have to go hunting."

This project fixes a subtle but common monitoring flaw: a single point-in-time measurement can't distinguish a momentary blip from a genuine sustained problem — only sampling over time can.

03 New Concepts (Building on Projects 01–08)

You already know CIM queries for a single reading. Here's what's new for sampling over time and finding root cause.
Get-Counter — Windows Performance Counters

What it is: A cmdlet that reads live Windows Performance Counters — the same underlying data source Performance Monitor (perfmon.exe) graphs — directly into PowerShell objects. Counters are addressed by path, e.g. \Processor(_Total)\% Processor Time or \Memory\Available MBytes.

Why it's used today: Unlike a single Get-CimInstance snapshot, Get-Counter is built specifically for repeated, time-based sampling — it's the right tool the moment "one reading" isn't enough.

-SampleInterval and -MaxSamples

What it is: Get-Counter parameters controlling how many readings to take and how many seconds to wait between each — e.g. -SampleInterval 2 -MaxSamples 15 takes 15 readings, 2 seconds apart, spanning a real 30-second window.

Why it's used today: This is the direct fix for the story's problem — a value has to hold up across many samples over real time, not just look bad (or fine) for one instant.

"Majority of Samples" Logic — Filtering Signal From Noise

What it is: Instead of requiring every single sample to exceed a threshold (too strict — one good sample would clear a genuine problem) or just one sample (too loose — the original flaw), we require a majority — e.g. more than half of all samples — to be over threshold before calling it sustained.

Why it matters: This single design decision is what separates "a blip" from "a real, ongoing problem," directly addressing both failures from the story.

Get-Process for Root-Cause Identification

What it is: Returns every running process as an object with CPU and memory usage properties (.CPU, .WorkingSet64). Sorting by CPU or memory and taking the top few instantly shows what's actually consuming resources.

Why it's used today: Priya specifically asked for this — the moment a sustained problem is confirmed, naming the responsible process (like sqlservr.exe) turns "something's wrong" into "here's exactly where to look first."

Measure-Object -Average — Summarizing a Sample Set

What it is: You've used Measure-Object since Project 01 for a single average; today it summarizes an entire array of samples collected over the monitoring window into one representative average value for the report.

The core lesson: monitoring accuracy is often less about a cleverer formula and more about measuring over the right window of time. A dumb average over 30 seconds beats a "smart" single reading almost every time.

06 The Script — Test-SustainedResourceLoad.ps1

Scripts\Test-SustainedResourceLoad.ps1 
<#
.SYNOPSIS
    Sustained CPU/Memory Load Detection - ABC Bank Production Support
.DESCRIPTION
    Samples CPU and memory repeatedly over a real time window per server,
    confirms a sustained (not momentary) issue using a majority-of-samples
    rule, and identifies the top resource-consuming process when confirmed.
#>

param(
    [int]$SampleIntervalSeconds = 2,          # Seconds between each sample
    [int]$MaxSamples = 15,                    # 15 samples x 2s = 30 second monitoring window
    [int]$CpuThreshold = 85,                 # % CPU considered high for a single sample
    [int]$MemThreshold = 85                  # % Memory used considered high for a single sample
)

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers   = Get-Content -Path "C:\ResourceMonitor\Config\servers.txt"
$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\ResourceMonitor\Logs\ResourceCheck_$TimeTag.log"
$ReportCSV = "C:\ResourceMonitor\Reports\ResourceCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: SUSTAINED LOAD CHECK FOR ONE SERVER
# ============================================================

function Test-ServerSustainedLoad {
    param([string]$ComputerName)

    $Result = [PSCustomObject]@{
        ServerName       = $ComputerName
        AvgCPU           = $null
        CpuSustained     = $false
        AvgMemUsedPct    = $null
        MemSustained     = $false
        TopProcess       = "N/A"
        OverallStatus    = "UNKNOWN"
        CheckedAt        = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        # ---- SAMPLE CPU OVER THE FULL WINDOW ----
        $CpuSamples = (Get-Counter -Counter "\Processor(_Total)\% Processor Time" `
                        -ComputerName $ComputerName -SampleInterval $SampleIntervalSeconds -MaxSamples $MaxSamples
                      ).CounterSamples.CookedValue          # Array of raw % values, one per sample taken

        $Result.AvgCPU = [math]::Round(($CpuSamples | Measure-Object -Average).Average, 1)

        $CpuBreaches = ($CpuSamples | Where-Object { $_ -ge $CpuThreshold }).Count   # How many samples were over threshold
        $Result.CpuSustained = ($CpuBreaches / $MaxSamples) -gt 0.5     # TRUE only if MORE THAN HALF the samples breached

        # ---- SAMPLE MEMORY OVER THE SAME WINDOW ----
        $MemSamples = (Get-Counter -Counter "\Memory\% Committed Bytes In Use" `
                        -ComputerName $ComputerName -SampleInterval $SampleIntervalSeconds -MaxSamples $MaxSamples
                      ).CounterSamples.CookedValue

        $Result.AvgMemUsedPct = [math]::Round(($MemSamples | Measure-Object -Average).Average, 1)

        $MemBreaches = ($MemSamples | Where-Object { $_ -ge $MemThreshold }).Count
        $Result.MemSustained = ($MemBreaches / $MaxSamples) -gt 0.5

        # ---- IF SUSTAINED, IDENTIFY THE TOP RESOURCE-CONSUMING PROCESS ----
        if ($Result.CpuSustained -or $Result.MemSustained) {
            $TopProc = Invoke-Command -ComputerName $ComputerName -ScriptBlock {
                Get-Process | Sort-Object CPU -Descending | Select-Object -First 1 -Property Name, CPU, `
                    @{Name="MemoryMB"; Expression={ [math]::Round($_.WorkingSet64 / 1MB, 0) }}
            }
            $Result.TopProcess = "$($TopProc.Name) (CPU: $($TopProc.CPU), Mem: $($TopProc.MemoryMB)MB)"
            $Result.OverallStatus = "CRITICAL - SUSTAINED LOAD"
            Write-Log "$ComputerName : SUSTAINED load confirmed. Top process: $($Result.TopProcess)" "WARNING"
        }
        else {
            $Result.OverallStatus = "HEALTHY"
            Write-Log "$ComputerName : within normal range (Avg CPU $($Result.AvgCPU)%, Avg Mem $($Result.AvgMemUsedPct)%)" "INFO"
        }
    }
    catch {
        Write-Log "Error monitoring $ComputerName : $($_.Exception.Message)" "ERROR"
        $Result.OverallStatus = "CRITICAL - CHECK FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Sustained Load Check ($MaxSamples samples, ${SampleIntervalSeconds}s apart) for $($Servers.Count) server(s) =====" "INFO"

$AllResults = foreach ($Server in $Servers) {
    Test-ServerSustainedLoad -ComputerName $Server
}

$AllResults | Sort-Object OverallStatus | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

Write-Log "===== Sustained Load Check Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

(Get-Counter -Counter "\Processor(_Total)\% Processor Time" -SampleInterval 2 -MaxSamples 15).CounterSamples.CookedValue
Get-Counter returns a rich result object; .CounterSamples.CookedValue drills down to just the array of numeric readings we actually want — 15 separate CPU percentages spanning a real 30-second window, not one instant number.
$CpuBreaches = ($CpuSamples | Where-Object { $_ -ge $CpuThreshold }).Count
Counts how many of the 15 samples individually crossed the threshold — this is the raw ingredient the majority rule needs, distinct from the average, which could hide a mix of very high and very low readings.
$Result.CpuSustained = ($CpuBreaches / $MaxSamples) -gt 0.5
This single line is the fix for both failures in the story: a lone spike gives a low breach ratio (false alarm avoided); an hour-long sustained problem gives a high breach ratio across the sample window (missed incident avoided).
Get-Process | Sort-Object CPU -Descending | Select-Object -First 1
Only runs when a sustained issue is already confirmed — deliberately avoiding the cost of a full process inventory on every single healthy check, only paying that cost when it's actually going to be useful.
Common mistake: comparing the average of all samples against the threshold instead of counting individual breaches. Averaging can smooth a genuinely sustained-but-fluctuating high load down below the threshold, hiding exactly the problem you're trying to catch — the majority-of-samples approach is more robust for this reason.

08 Script Execution Flow

StepWhat Happens
1. CPU Sampling WindowGet-Counter blocks for the full 30-second window, taking a reading every 2 seconds, before returning any results — this is a real elapsed-time cost per server.
2. Memory Sampling WindowA second, separate 30-second sampling window runs for memory — the two aren't combined into a single pass in this version.
3. Majority Rule EvaluationBreach counts for both metrics are compared against the 50% threshold independently — either one being sustained triggers the CRITICAL branch.
4. Conditional Root-Cause LookupGet-Process only runs on servers that just failed the sustained check — healthy servers skip this entirely, keeping routine checks fast.
5. ReportingSame CSV/log pattern as every project, now carrying both the average AND the sustained verdict, plus the responsible process when relevant.

09 Windows Internals — In Simple English

What Performance Counters Actually Are

Windows continuously tracks hundreds of live system metrics (CPU, memory, disk queue length, network throughput) in an in-memory counter database — Performance Monitor, Get-Counter, and third-party monitoring tools all read from this same underlying source.

Why CPU Readings Fluctuate So Much

Modern CPUs handle many short-lived tasks constantly; a single instant reading naturally captures whatever happened to be running in that exact millisecond, which is precisely why one-off snapshots are so prone to both false positives and false negatives.

Why This Check Takes Real Time to Run

Unlike Project 01's instant CIM query, Get-Counter with -MaxSamples genuinely waits in real time between each sample — accuracy here is deliberately traded for a longer per-server check duration.

12 Production Best Practices

Never judge a resource problem from a single instant reading — sample over a real window whenever the cost of a false alarm or a missed incident is high.
Use a majority-of-samples rule rather than either "any single breach" (too sensitive) or "the average" (can mask a genuinely fluctuating problem).
Only pay for expensive diagnostic steps (like a full process inventory) when a problem is actually confirmed — keep the common, healthy case fast.
Make your sampling window and thresholds configurable parameters, not hardcoded values — different servers and workloads may need different sensitivity.

13 Interview Preparation

Q: Why sample over a window instead of taking one reading, like Project 01 did?
A single instant reading can't distinguish a momentary spike from genuinely sustained load — sampling repeatedly over real time and requiring a majority of samples to breach threshold catches real problems while filtering out the noise a single snapshot can't tell apart.
Q: Why use a majority-of-samples rule instead of just averaging all the samples?
Averaging can mask a load that's genuinely fluctuating between very high and moderate — a majority-breach count directly answers "was this high most of the time" rather than "what was the overall mean," which is a more direct measure of sustained impact.
Q: Why only run Get-Process when a sustained issue is already confirmed?
Enumerating every running process has a real performance cost; paying that cost on every single healthy check across the whole fleet would be wasteful — it only needs to run on the servers that actually need root-cause investigation.
Q: How does this project directly address both failures described in the story?
The false alarm was a single spike being treated as sustained — the majority rule fixes that. The missed real incident was a lucky-timed single snapshot during a lull — sampling continuously over a real window instead of one instant fixes that.

14 Key Learnings & Assignment

Key Learnings

  • A single point-in-time reading can produce both false alarms and missed real incidents — sampling over time fixes both
  • Get-Counter with -SampleInterval and -MaxSamples is the right tool the moment "one reading" isn't reliable enough
  • A majority-of-samples rule is often more robust than either a single-breach trigger or a plain average
  • Expensive diagnostic steps (like full process enumeration) should be conditional on a confirmed problem, not run on every check
