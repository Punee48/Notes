Project 18 — Certificate Store Monitoring & Trust Chain Validation

The certificate had 340 days left. TLS still failed. Expiry was never the problem.

Project 06 caught certificates running out of time. But a certificate can be perfectly unexpired and still completely broken — a missing intermediate certificate snaps the trust chain, or a private key that isn't actually accessible makes the certificate useless for the service that needs it. Today's script checks the things expiry monitoring alone can never see.

partner-gateway cert — chain broken, intermediate missing
SRV-APP02 IIS cert — private key NOT accessible to service account

01 The Production Story

Your Project 06 dashboard shows every certificate green. A partner integration is still failing TLS handshakes.
Monday — "Your Certificate Monitoring Says We're Fine. We're Not."

A partner bank's integration team reports their systems can no longer establish a secure connection to ABC Bank's partner gateway — a TLS handshake failure, right at the certificate validation step. You immediately check the Project 06 dashboard: partner-gateway.abcbank.com shows 340 days remaining on its certificate. Not even close to expiring. Confused, you dig deeper.

The actual cause: a routine cleanup task on the server removed what looked like an old, unused intermediate certificate from the certificate store — except it wasn't unused. It was the exact intermediate certificate that linked the partner gateway's certificate up to a trusted root. Without it, any client trying to validate the chain hits a dead end partway up and rejects the connection entirely — completely independent of whether the end certificate itself has 340 days or 3 hours left.

A second, quieter issue turns up during the same investigation: SRV-APP02's IIS certificate was recently renewed, but the new certificate's private key permissions were never granted to the IIS application pool's service account — meaning IIS technically has a valid, unexpired certificate bound to the site, but can't actually use it to complete a TLS handshake at all.

"Expiry is one specific way a certificate check can fail," Priya says, "but it's not the only way, and apparently not even the most common one for us. I want a script that validates the full chain of trust — not just the one certificate's own dates — and confirms the private key is actually usable by whatever needs it. 'Not expired' was never the whole promise we needed to keep."

This project deliberately builds on Project 06 rather than replacing it — expiry monitoring remains valuable and necessary, but this project closes the gap between "not expired" and "actually works."

03 New Concepts (Building on Projects 01–17)

You already know the Cert: PSDrive and X509Certificate2 basics from Project 06. Here's what's new for validating chains and keys.
X509Chain — Building and Validating the Full Trust Chain

What it is: A .NET class (System.Security.Cryptography.X509Certificates.X509Chain) that attempts to build the complete chain from a certificate up to a trusted root, checking every link along the way — exactly what a browser or any TLS client does internally before trusting a connection.

Why it's used today: Project 06 only ever looked at one certificate's own .NotAfter date. X509Chain is what actually reproduces the real validation a client performs — including whether every intermediate certificate needed to complete the chain is present and itself valid.

Interpreting ChainStatus

What it is: After calling $Chain.Build($Certificate), $Chain.ChainStatus is an array describing exactly what, if anything, is wrong with the chain — status values include things like PartialChain (a link is missing), Revoked, NotTimeValid, or an empty array meaning the chain is fully valid.

Why it's used today: PartialChain is specifically the status that would have been raised by the story's missing intermediate certificate — reading this array directly tells us not just "is it broken" but "how, specifically."

HasPrivateKey and Testing Actual Key Access

What it is: $Certificate.HasPrivateKey reports whether a private key is associated with the certificate at all — but that alone doesn't confirm the CURRENT process or account can actually use it. Attempting an actual operation with the key (or checking its file-level permissions) is what confirms genuine accessibility.

Why it's used today: This is exactly the gap in the story's second finding — SRV-APP02's certificate technically had a private key present, but the IIS service account lacked permission to actually use it, a distinction HasPrivateKey alone cannot reveal.

Checking Multiple Certificate Store Locations

What it is: Beyond Cert:\LocalMachine\My (personal certificates) from Project 06, Windows maintains separate stores including Cert:\LocalMachine\CA (intermediate certificates) and Cert:\LocalMachine\Root (trusted root authorities) — chain validation depends on the right certificates being present across these different stores.

Why it's used today: The story's missing intermediate certificate was removed from exactly this kind of secondary store — a check that only ever looked at the My store, like Project 06 did, would never have noticed it was gone.

This project is a direct sequel to Project 06, not a duplicate — recognize the pattern of building genuinely new capability on top of an earlier project rather than always starting from zero. Real production automation suites grow this way, incrementally, project by project.

06 The Script — Test-CertificateChainAndKeys.ps1

Scripts\Test-CertificateChainAndKeys.ps1 
<#
.SYNOPSIS
    Certificate Trust Chain & Private Key Validation - ABC Bank Production Support
.DESCRIPTION
    Companion to Project 06's expiry monitoring — validates the FULL
    trust chain for each certificate and confirms its private key is
    genuinely accessible, catching failures expiry checks cannot see.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers   = Get-Content -Path "C:\CertChainValidation\Config\servers.txt"
$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\CertChainValidation\Logs\ChainCheck_$TimeTag.log"
$ReportCSV = "C:\CertChainValidation\Reports\ChainCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-SERVER CHAIN & KEY VALIDATION
# ============================================================

function Test-ServerCertificates {
    param([string]$ComputerName)

    try {
        $CertResults = Invoke-Command -ComputerName $ComputerName -ScriptBlock {

            $Certs = Get-ChildItem -Path "Cert:\LocalMachine\My" |
                     Where-Object { $_.NotAfter -gt (Get-Date) }   # Only bother chain-checking certs that aren't already expired

            foreach ($Cert in $Certs) {
                # ---- CHECK 1: BUILD AND VALIDATE THE FULL TRUST CHAIN ----
                $Chain = New-Object System.Security.Cryptography.X509Certificates.X509Chain
                $Chain.ChainPolicy.RevocationMode = "NoCheck"   # Skip online revocation lookup — focus purely on chain completeness here
                $ChainIsValid = $Chain.Build($Cert)                # Returns $true only if the FULL chain builds cleanly to a trusted root
                $ChainProblems = ($Chain.ChainStatus | Select-Object -ExpandProperty Status) -join ", "

                # ---- CHECK 2: IS THE PRIVATE KEY GENUINELY ACCESSIBLE? ----
                $KeyAccessible = $false
                if ($Cert.HasPrivateKey) {
                    try {
                        $null = $Cert.PrivateKey                # Actually touching this property forces an access attempt
                        $KeyAccessible = $true
                    }
                    catch {
                        $KeyAccessible = $false              # HasPrivateKey was true, but accessing it actually failed — exactly the story's SRV-APP02 scenario
                    }
                }

                [PSCustomObject]@{
                    Subject         = $Cert.Subject
                    Thumbprint      = $Cert.Thumbprint
                    ChainValid      = $ChainIsValid
                    ChainProblems   = $ChainProblems
                    HasPrivateKey   = $Cert.HasPrivateKey
                    KeyAccessible   = $KeyAccessible
                }
            }
        }

        foreach ($CertResult in $CertResults) {
            $Verdict = if (-not $CertResult.ChainValid) { "CRITICAL - BROKEN CHAIN" }
                      elseif ($CertResult.HasPrivateKey -and -not $CertResult.KeyAccessible) { "CRITICAL - KEY INACCESSIBLE" }
                      else { "VALID" }

            [PSCustomObject]@{
                ServerName    = $ComputerName
                Subject       = $CertResult.Subject
                Thumbprint    = $CertResult.Thumbprint
                ChainValid    = $CertResult.ChainValid
                ChainProblems = $CertResult.ChainProblems
                KeyAccessible = $CertResult.KeyAccessible
                OverallStatus = $Verdict
                CheckedAt     = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
            }

            if ($Verdict -ne "VALID") {
                Write-Log "$ComputerName : $($CertResult.Subject) -> $Verdict ($($CertResult.ChainProblems))" "ERROR"
            }
        }
    }
    catch {
        Write-Log "Error checking certificates on $ComputerName : $($_.Exception.Message)" "ERROR"
    }
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Certificate Chain & Key Validation for $($Servers.Count) server(s) =====" "INFO"

$AllResults = foreach ($Server in $Servers) { Test-ServerCertificates -ComputerName $Server }

$AllResults | Sort-Object OverallStatus -Descending | Format-Table -AutoSize -Wrap

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$CriticalCount = ($AllResults | Where-Object { $_.OverallStatus -like "CRITICAL*" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount certificate(s) FAILED chain or key validation — review required" "WARNING"
}

Write-Log "===== Certificate Chain & Key Validation Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

$Chain.ChainPolicy.RevocationMode = "NoCheck"
By default, X509Chain also tries to check online revocation status (CRL/OCSP), which requires internet access and can be slow or unreliable from an internal automation host — setting this to NoCheck focuses the check purely on chain completeness, which is this project's specific scope; a production version might add revocation checking as a further enhancement with appropriate network access.
$ChainIsValid = $Chain.Build($Cert)
This single method call is doing real work: it searches the local certificate stores (My, CA, Root) trying to link the given certificate all the way up to something trusted, exactly replicating what a TLS client does during a real handshake — a return of $false means that chain-building genuinely failed.
if ($Cert.HasPrivateKey) { try { $null = $Cert.PrivateKey; $KeyAccessible = $true } catch { $KeyAccessible = $false } }
Merely checking HasPrivateKey only confirms a key is associated with the certificate in principle — actually reading the .PrivateKey property forces Windows to attempt real access to it, which is what can fail due to a permissions problem even when a key genuinely exists, exactly as happened on SRV-APP02.
if (-not $CertResult.ChainValid) { "CRITICAL - BROKEN CHAIN" } elseif ($CertResult.HasPrivateKey -and -not $CertResult.KeyAccessible) { "CRITICAL - KEY INACCESSIBLE" }
Chain validity is checked before key accessibility — a certificate with a broken chain is unusable for TLS validation regardless of key access, so it's reported as the more fundamental problem first.
Common mistake: treating HasPrivateKey as proof the key is usable. As this project's story demonstrates, HasPrivateKey can be true while the actual access attempt still fails due to a permissions gap — only an actual access attempt reveals the real, usable state.

08 Script Execution Flow

StepWhat Happens
1. Certificate EnumerationOnly non-expired certificates are considered — an already-expired certificate's chain status is moot, since it's already failing for a different, Project 06-covered reason.
2. Chain BuildX509Chain attempts to construct the complete path to a trusted root, searching across the relevant certificate stores on that specific server.
3. Key Access AttemptAn actual property access, not just a boolean flag check, is what genuinely tests whether the private key is usable right now.
4. Layered VerdictChain validity is checked first as the more fundamental requirement, then key accessibility — mirroring the layered verdict pattern from Projects 04, 12, 15, and 17.
5. ReportingSame log/CSV pattern as every prior project, giving Security and Ops a clear view of exactly which certificates are broken and how.

09 Windows Internals — In Simple English

Why Chains Need Intermediate Certificates

Root Certificate Authorities keep their signing keys extremely tightly protected and rarely used directly — instead, they sign intermediate certificates, which then sign the actual server certificates. A client must have every link in that chain to build trust all the way up, which is exactly why a single missing intermediate breaks everything above it.

How Windows Stores Private Keys Separately

A certificate's private key isn't actually stored inside the same file structure as the certificate itself — Windows manages private keys through a separate cryptographic key storage system with its own access control list, which is exactly why key access can fail independently of the certificate object itself looking completely fine.

Why This Failure Mode Is Common After Certificate Renewal

When a certificate is renewed, Windows often creates a new key container — if the process granting the service account access to that new key isn't part of the renewal automation, the service silently loses key access on an otherwise perfectly valid, freshly-issued certificate.

12 Production Best Practices

Treat chain validation and expiry monitoring as companion checks, not substitutes for each other — a certificate can fail either independently of the other.
Always actually attempt private key access rather than trusting HasPrivateKey alone — the boolean flag and genuine usability are different things.
Include private key permission verification as an explicit step in any certificate renewal process, not an afterthought — this is specifically where the story's second incident originated.
Report chain and key problems as distinct finding types — they have different root causes and different remediation steps.

13 Interview Preparation

Q: How can a certificate with 340 days left still cause a TLS handshake failure?
Expiry is only one of several requirements for a certificate to work — a broken trust chain (a missing intermediate certificate) or an inaccessible private key can each independently cause a complete handshake failure, regardless of how much time is left before the end certificate's own expiry.
Q: Why isn't checking HasPrivateKey enough to confirm a certificate is usable?
HasPrivateKey only reports that a key is associated with the certificate in principle — it doesn't confirm the current account or process actually has permission to use that key, which requires a genuine access attempt to verify.
Q: Why does this project deliberately turn off revocation checking?
Online revocation checking requires live network access to a CRL or OCSP endpoint and can be slow or fail for reasons unrelated to the chain's actual structural completeness — scoping this project to chain completeness keeps it focused and fast, with revocation checking as a legitimate, separate future enhancement.
Q: This project and Project 06 both check certificates — why not combine them into one script?
They check genuinely different, independent properties (time validity versus chain/key validity) using different techniques — keeping them separate keeps each script focused and easier to reason about, though a mature automation suite might eventually compose both checks into one unified certificate health report.

14 Key Learnings & Assignment

Key Learnings

  • "Not expired" is only one requirement for a working certificate — chain completeness and private key accessibility are equally essential, independent requirements
  • X509Chain.Build() reproduces the real validation a TLS client performs, including checking for missing intermediate certificates
  • HasPrivateKey confirms presence, not usability — a genuine access attempt is required to confirm the key actually works
  • Building a companion project on top of an earlier one (Project 06) rather than duplicating it is how real automation suites grow incrementally
