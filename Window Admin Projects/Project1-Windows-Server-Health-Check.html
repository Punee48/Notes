03 Concepts You Need First

Assume nothing. Every concept used in today's script is explained here before you see it in code. Click each one open.
Variables — $Something

What it is: A named container that holds a value in memory while your script runs. In PowerShell every variable name starts with a dollar sign, e.g. $ServerName.

Why it exists: You need somewhere to store the server list, the results, thresholds, and file paths so you can reuse them instead of retyping values.

Internally: PowerShell variables live in a "variable drive" called Variable: for the current session — you can literally run dir Variable: to see every variable currently in memory.

Best practice: Use PascalCase names that describe the content ($CriticalServices, not $x). Common mistake: forgetting the $ when reading a variable — PowerShell will treat the bare word as plain text instead.

Objects (not just text)

What it is: Every single thing that comes out of a PowerShell command is a structured .NET object with named properties — not a line of plain text like in old-school batch scripting.

Why it matters here: When we run Get-Service, we don't get text we have to parse with regular expressions — we get an object with a real .Status property we can compare directly, e.g. $Service.Status -eq "Running".

Production use case: This is the single biggest reason PowerShell beats batch/VBScript for enterprise automation — reliable, structured data instead of fragile text-scraping.

The Pipeline — Cmdlet-A | Cmdlet-B

What it is: The | symbol passes the object output of one cmdlet directly into the next cmdlet as input, one object at a time.

Why it exists: It lets you build a chain of small, single-purpose commands instead of one giant block of code — e.g. Get-Service | Where-Object {...} | Export-Csv ....

Internally: PowerShell streams objects through the pipeline one at a time where possible, which keeps memory usage efficient even over large result sets.

Cmdlets & Aliases

Cmdlets: PowerShell's built-in commands, always named Verb-Noun (e.g. Get-Service, Test-Connection). The consistent naming is deliberate so commands are predictable.

Aliases: Short nicknames for cmdlets, e.g. gsv for Get-Service, or % for ForEach-Object. Best practice: use full cmdlet names in production scripts — aliases are fine for interactive typing but hurt readability in code that a teammate will maintain at 2 AM during an incident.

Functions & Parameters

What it is: A named, reusable block of code defined with function Name { }. A param() block declares the inputs it accepts, just like arguments to a method in any programming language.

Why it's used today: We define Get-ServerHealth once and call it once per server, instead of copy-pasting the same 20 lines of checking logic 500 times.

Arrays & Hash Tables

Array: An ordered list of values, e.g. @("SRV-APP01","SRV-APP02"). We use it to hold the list of servers and the list of critical services.

Hash Table: A collection of Key = Value pairs, e.g. @{ CPUWarning = 70 }. We use it to hold our threshold configuration, because it's more readable than five separate variables.

Loops & Conditions — foreach / if / elseif

foreach: Repeats a block of code once for every item in a collection — we use it to run the health check function against every server in the list.

if / elseif / else: Branches logic based on a condition — we use it to decide whether a server's status is HEALTHY, WARNING, or CRITICAL based on the thresholds.

Error Handling — Try / Catch

What it is: try { } wraps code that might fail; catch { } runs only if an error occurs inside the try block, letting you handle it gracefully instead of crashing the whole script.

Why it's critical in banking: If one server is unreachable or misbehaves, the script must keep checking the other 499 servers — not crash and leave the whole morning report missing.

CIM / WMI — Get-CimInstance

What it is: Windows Management Instrumentation (WMI) is a built-in Windows subsystem that exposes hardware and OS information — CPU load, memory, disk, and much more — as queryable data. Get-CimInstance is the modern PowerShell way to query it.

Why it's used: It's the standard, reliable way to pull CPU/memory/disk stats from both local and remote Windows servers without installing anything extra.

Test-Connection, Get-Service, Export-Csv, ConvertTo-Html

Test-Connection: PowerShell's version of "ping" — confirms whether a server responds on the network before we bother querying it further.

Get-Service: Returns Windows service objects with a live .Status property (Running, Stopped, etc.), locally or on a remote computer.

Export-Csv: Writes objects to a CSV file — the standard format Operations and Audit teams open in Excel.

ConvertTo-Html: Turns objects into a formatted HTML table — useful for emailing a readable report to management.

Notice the pattern: nearly every cmdlet here is Verb-Noun and returns an object. Learn this pattern once and you can guess the name of most PowerShell commands correctly on your first try.

06 The Script — Get-WindowsServerHealth.ps1

Complete, production-ready, and fully commented — every line explains itself, then we explain it again in Section 7.
Scripts\Get-WindowsServerHealth.ps1 
<#
.SYNOPSIS
    Daily Windows Server Health Check - ABC Bank Production Support
.DESCRIPTION
    Checks connectivity, CPU, memory, disk space, and critical services
    across the production Windows server fleet, then produces CSV/HTML
    reports and a timestamped log for audit purposes.
.AUTHOR
    Windows Operations Team - ABC Bank
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers = @("SRV-APP01","SRV-APP02","SRV-DB01")   # Array holding the list of target servers to check

$CriticalServices = @("W3SVC","MSSQLSERVER","Spooler")  # Services considered critical to the bank

$Thresholds = @{                       # Hash table storing warning/critical thresholds
    CPUWarning     = 70          # CPU % above this triggers WARNING
    CPUCritical    = 90          # CPU % above this triggers CRITICAL
    MemWarning     = 75          # Memory % above this triggers WARNING
    MemCritical    = 90          # Memory % above this triggers CRITICAL
    DiskWarningGB  = 20          # Free disk space below this (GB) triggers WARNING
    DiskCriticalGB = 10          # Free disk space below this (GB) triggers CRITICAL
}

$TimeTag    = Get-Date -Format 'yyyyMMdd_HHmmss'              # One shared timestamp used in every filename this run
$LogFile    = "C:\HealthCheck\Logs\HealthCheck_$TimeTag.log"    # Build the log file path
$ReportCSV  = "C:\HealthCheck\Reports\HealthCheck_$TimeTag.csv"  # Build the CSV report path
$ReportHTML = "C:\HealthCheck\Reports\HealthCheck_$TimeTag.html" # Build the HTML report path

# ============================================================
# SECTION 2: LOGGING FUNCTION
# ============================================================

function Write-Log {                                  # Reusable function to write timestamped log entries
    param(
        [string]$Message,                              # The text to log
        [string]$Level = "INFO"                        # Severity: INFO, WARNING, or ERROR
    )
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"       # Current time, human readable
    $Entry = "[$Stamp] [$Level] $Message"              # Build the full log line
    Add-Content -Path $LogFile -Value $Entry         # Append the line to the log file on disk
    Write-Host $Entry                                    # Also print it live to the console
}

# ============================================================
# SECTION 3: MAIN HEALTH CHECK FUNCTION
# ============================================================

function Get-ServerHealth {                          # Checks ONE server and returns ONE result object
    param(
        [string]$ComputerName                            # The server name passed in from the main loop
    )

    $Result = [PSCustomObject]@{                      # Build an empty result object with all fields we'll fill in
        ServerName    = $ComputerName
        Reachable     = $false
        CPUUsage      = $null
        MemoryUsage   = $null
        FreeDiskGB    = $null
        ServiceStatus = "N/A"
        OverallStatus = "UNKNOWN"
        CheckedAt     = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {                                                # Everything that could fail per-server goes inside try
        if (-not (Test-Connection -ComputerName $ComputerName -Count 2 -Quiet)) {  # Ping twice, -Quiet returns True/False
            Write-Log "$ComputerName is UNREACHABLE" "ERROR"
            $Result.OverallStatus = "CRITICAL - UNREACHABLE"
            return $Result                                  # Stop here for this server, no point checking further
        }

        $Result.Reachable = $true
        Write-Log "$ComputerName is reachable. Proceeding with checks." "INFO"

        # ---- CPU CHECK ----
        $CPU = Get-CimInstance -ClassName Win32_Processor -ComputerName $ComputerName |  # Query CPU load
               Measure-Object -Property LoadPercentage -Average                          # Average across all cores/CPUs
        $Result.CPUUsage = [math]::Round($CPU.Average, 2)  # Round to 2 decimals

        # ---- MEMORY CHECK ----
        $OS = Get-CimInstance -ClassName Win32_OperatingSystem -ComputerName $ComputerName  # OS-level memory stats
        $UsedMemPct = [math]::Round( (($OS.TotalVisibleMemorySize - $OS.FreePhysicalMemory) / $OS.TotalVisibleMemorySize) * 100, 2 )  # % memory used
        $Result.MemoryUsage = $UsedMemPct

        # ---- DISK CHECK ----
        $Disk = Get-CimInstance -ClassName Win32_LogicalDisk -ComputerName $ComputerName -Filter "DeviceID='C:'"  # C: drive info
        $Result.FreeDiskGB = [math]::Round($Disk.FreeSpace / 1GB, 2)  # Bytes to GB

        # ---- SERVICE CHECK ----
        $FailedServices = @()                              # Collects any critical service that is NOT running
        foreach ($Svc in $CriticalServices) {              # Loop through each critical service name
            $SvcStatus = Get-Service -ComputerName $ComputerName -Name $Svc -ErrorAction SilentlyContinue  # Don't crash if service doesn't exist here
            if ($null -eq $SvcStatus -or $SvcStatus.Status -ne "Running") {
                $FailedServices += $Svc                     # Add to the failed list
            }
        }
        $Result.ServiceStatus = if ($FailedServices.Count -eq 0) { "All Critical Services Running" }
                                else { "STOPPED: " + ($FailedServices -join ", ") }

        # ---- OVERALL STATUS DECISION ----
        if ($Result.CPUUsage -ge $Thresholds.CPUCritical -or
            $Result.MemoryUsage -ge $Thresholds.MemCritical -or
            $Result.FreeDiskGB -le $Thresholds.DiskCriticalGB -or
            $FailedServices.Count -gt 0) {
            $Result.OverallStatus = "CRITICAL"              # Any critical breach OR a stopped service = CRITICAL
        }
        elseif ($Result.CPUUsage -ge $Thresholds.CPUWarning -or
              $Result.MemoryUsage -ge $Thresholds.MemWarning -or
              $Result.FreeDiskGB -le $Thresholds.DiskWarningGB) {
            $Result.OverallStatus = "WARNING"
        }
        else {
            $Result.OverallStatus = "HEALTHY"
        }

        Write-Log "$ComputerName check complete. Status: $($Result.OverallStatus)" "INFO"
    }
    catch {                                              # Catches ANY unexpected error during the checks above
        Write-Log "Error checking $ComputerName : $($_.Exception.Message)" "ERROR"
        $Result.OverallStatus = "CRITICAL - CHECK FAILED"   # We couldn't verify it, so treat it as critical
    }

    return $Result                                        # Hand the finished object back to the main loop
}

# ============================================================
# SECTION 4: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Health Check for $($Servers.Count) servers =====" "INFO"

$AllResults = foreach ($Server in $Servers) {           # Loop through every server in the list
    Get-ServerHealth -ComputerName $Server                 # Call the function, collect its returned object
}

$AllResults | Sort-Object OverallStatus | Format-Table -AutoSize   # Console preview, worst statuses grouped together

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation     # Save audit-ready CSV

$AllResults | ConvertTo-Html -Title "ABC Bank Daily Server Health Report" `
    -PreContent "<h1>Daily Windows Server Health Report</h1>" |
    Out-File -FilePath $ReportHTML                       # Save readable HTML report

$CriticalCount = ($AllResults | Where-Object { $_.OverallStatus -like "CRITICAL*" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount server(s) are CRITICAL. Alert email would be sent here." "WARNING"
    # Send-MailMessage goes here in production, via the bank's secure internal relay
}

Write-Log "===== Health Check Completed. Report: $ReportHTML =====" "INFO"

07 Line-by-Line Explanation

The highlights teams get asked about most in code review and production support. Every block above is commented; here are the parts worth slowing down on.
Test-Connection -ComputerName $ComputerName -Count 2 -Quiet
Pings the server twice. -Quiet collapses the result to a single $true/$false instead of detailed ping objects — perfect for a simple reachability gate. Alternative: Test-NetConnection gives more detail (port testing) but is slower for a simple sweep of 500 servers.
Get-CimInstance -ClassName Win32_Processor -ComputerName $ComputerName
CIM is the modern successor to WMI (Get-WmiObject, now deprecated). It queries the remote server's management interface for live CPU data. Common mistake: using the old Get-WmiObject in new scripts — it's on its way out and doesn't support the newer WinRM-based remoting cleanly.
-ErrorAction SilentlyContinue on Get-Service
If a service name doesn't exist on a particular server, PowerShell would normally throw a red error. This tells it to continue quietly so one missing service on one server doesn't disrupt the loop — we still catch it because $SvcStatus will be $null.
[PSCustomObject]@{ ... }
Builds our own structured object with exactly the properties we want, in a fixed order. This is what makes Export-Csv and ConvertTo-Html produce clean, consistent columns every time.
$AllResults = foreach ($Server in $Servers) { Get-ServerHealth ... }
Assigning a loop directly to a variable automatically collects every object the loop produces into an array — no need for a separate $AllResults += ... line inside the loop, which is slower and considered poor practice for large collections.
Common mistake in production: forgetting -ErrorAction SilentlyContinue combined with a try/catch means one unreachable server can throw a wall of red text into an otherwise clean scheduled task log, making real problems harder to spot.

08 Script Execution Flow — What Happens Internally

StepWhat Happens
1. Execution Policy CheckWindows checks the local Execution Policy (Restricted, RemoteSigned, etc.) before allowing the .ps1 file to run at all. On production servers this is normally set to RemoteSigned.
2. Script Loaded by EngineThe PowerShell engine (pwsh.exe or powershell.exe) parses the whole script into an Abstract Syntax Tree before executing a single line.
3. Variables & Functions DefinedSection 1–3 run top to bottom: config variables and both functions are loaded into memory, but Get-ServerHealth doesn't execute yet — only defined.
4. Main Loop ExecutesFor each server, the CIM/WMI calls use WinRM (Windows Remote Management) to talk to the remote server's management service over the network.
5. Object CreationEach check builds a [PSCustomObject] in memory — nothing is written to disk until the loop finishes.
6. Export & LoggingExport-Csv and ConvertTo-Html serialize the in-memory objects to disk; Write-Log has already been appending to the log file throughout the run.
7. ExitThe script ends naturally after the last line; a Scheduled Task wrapper captures the exit code to know if the run "succeeded" at the process level.

09 Windows Internals — In Simple English

How Windows Services Work

A Windows Service is a background program managed by the Service Control Manager (SCM). Each has a state: Running, Stopped, Paused. Get-Service just asks the SCM for that state.

How WinRM Works

Windows Remote Management is the transport that lets one server ask another server questions (like CIM queries) securely over HTTP/HTTPS, without an interactive login.

How WMI/CIM Works

WMI is a database-like repository built into Windows that describes hardware and OS state. CIM is the current standards-based way PowerShell talks to that repository.

How Task Scheduler Works

A Scheduled Task tells Windows: "at this time, run this program, as this account." It's how our script runs unattended every morning at 6 AM without a human present.

12 Production Best Practices

Log everything with a timestamp and severity level — during a 2 AM incident, the log file is often the only evidence of what actually happened.
Wrap every remote call in try/catch — one bad server should never take down a run covering 500 others.
Never hardcode credentials — production versions store server lists in a config file, and any credentials in a secure vault (e.g. Windows Credential Manager or a secrets manager), never in plain text in the script.
Give the automation account least privilege — read-only monitoring rights are enough for a health check; it should never have rights to change anything on the target servers.
Timestamp every output file — never overwrite yesterday's report; auditors and incident reviews need history.

13 Interview Preparation

Q: Why did you use Get-CimInstance instead of Get-WmiObject?
CIM is the current standard, uses WinRM instead of legacy DCOM for remoting (better firewall/security compatibility), and Get-WmiObject is deprecated in newer PowerShell versions.
Q: How does your script handle a server that is completely down?
Test-Connection fails first, so the script marks it CRITICAL - UNREACHABLE and returns immediately without wasting time on further checks against a dead server — and the loop continues to the next one.
Q: A production incident: your report showed a server as HEALTHY, but it was actually down five minutes later. How do you explain this to your manager?
A health check is a point-in-time snapshot, not continuous monitoring. I'd explain the check interval (once daily) versus real-time monitoring tools, and recommend increasing frequency or layering in a dedicated monitoring solution for critical systems if that gap is unacceptable.
Q: Why use a hash table for thresholds instead of separate variables?
It groups related configuration together, is easier to read and maintain, and could later be loaded from an external JSON config file without changing the rest of the script's logic.
Q: What would you change to make this ready for 500 real servers instead of 3?
Move the server list to an external config file, add parallel execution (e.g. PowerShell 7 ForEach-Object -Parallel or runspaces) so 500 sequential remote calls don't take too long, and add retry logic for transient network blips.
