Project 19 — Windows Firewall Validation

A rule that's "enabled" isn't the same as a port that's actually reachable — or actually restricted

Two opposite firewall failures, same week: a required port silently got blocked, breaking legitimate traffic, while on another server a sensitive port was wide open to "Any" address when it should have been restricted to one partner IP range. Today's script checks required rules exist and work, AND audits for dangerously permissive rules nobody meant to leave open.

Port 443 (Online Banking) — rule enabled, port reachable
Port 1433 (SQL) — rule enabled but port unreachable
Port 22 (SFTP) — open to "Any", should be partner IP only

01 The Production Story

Two firewall incidents in the same week, pulling in exactly opposite directions.
This Week — Two Firewall Incidents, Two Different Lessons

Incident one: after a routine Group Policy update pushes new baseline firewall settings across the fleet, the batch integration service on SRV-APP03 starts failing to connect outbound. Investigation finds the specific rule allowing that connection still shows as "Enabled" in Windows Firewall — but the GPO push had silently altered its port scope, and the rule no longer actually covers the port the service needs. Enabled and correct are two different things.

Incident two, discovered days later during an unrelated security review: an SFTP port used for a partner file exchange was supposed to be restricted to that partner's specific IP range only, per the original change request. It's actually configured wide open — Any remote address — and has been that way since the rule was first created eight months ago, apparently a mistake nobody caught during initial setup.

"These are opposite problems," Priya says, "but they're really the same root issue: nobody's actually verifying our firewall configuration matches what it's supposed to be, in either direction. I want two checks. First: confirm every rule we depend on for legitimate business traffic is not just enabled, but actually achieves what we need — test the real port, don't just read the rule's config. Second: audit every rule for scope that's broader than it should be, especially 'Any' address on anything sensitive, and flag it before a security review catches it for us."

This project mirrors Project 15's cluster lesson one more time: a configuration setting "looking right" (Enabled = True) is not the same as verifying it actually produces the intended real-world effect.

02 Business Case

Business Requirement

Ensure required firewall rules genuinely enable needed connectivity, and no rule is more permissive than its business justification requires.

Customer Requirement

Ops wants confirmed real connectivity for critical services; Security wants proactive detection of overly broad rule scopes.

Banking Scenario

Partner integrations, batch services, and customer-facing applications all depend on precisely-scoped firewall rules — not too narrow, not too broad.

Current Manual Process

Firewall rules are set once at creation and rarely re-verified against either their intended effect or their original scope justification.

Problems With Current Process

A rule can silently stop achieving its intended purpose after any change, and an overly broad rule can persist unnoticed indefinitely.

Business Challenges

"Is this rule correct" requires two genuinely different checks — does it work, and is it appropriately scoped — that pull in opposite directions.

Risk Analysis

A blocked required port causes an outage; an overly broad rule is a standing security exposure — both are real, ongoing risks.

Business Impact

Catching either failure proactively prevents an outage on one side and a security finding on the other.

Why Automation Is Required

Only automation can verify real connectivity and audit rule scope across every critical server, consistently and on a real schedule.

Solution Design

A PowerShell script combining required-rule connectivity testing with a scope audit against an approved baseline for sensitive ports.

Project Scope

Phase 1 covers connectivity verification for defined critical rules and scope auditing for defined sensitive ports.

Expected Benefits

Both connectivity breaks and scope creep get caught by routine automation instead of an outage or an external security review.

03 New Concepts (Building on Projects 01–18)

You already know layered independent verdicts and config-vs-baseline comparison. Here's what's new for the firewall specifically.
Get-NetFirewallRule & Associated Filter Cmdlets

What it is: Get-NetFirewallRule returns a rule's high-level properties (name, enabled state, direction, action) — but the actual port and address details live in separate, associated objects retrieved with Get-NetFirewallPortFilter and Get-NetFirewallAddressFilter, piped from the rule via | Get-NetFirewallPortFilter.

Why it's split this way: This mirrors AD's group-membership model from Project 10 — the rule object and its filter details are related but separate objects, reflecting how Windows Firewall actually stores this configuration internally.

"Enabled" vs "Actually Reachable" — Reinforcing a Recurring Lesson

What it is: A firewall rule can show Enabled = True while its scope, port, or interaction with other rules means the port isn't actually reachable — exactly like the story's SRV-APP03 incident. Test-NetConnection -ComputerName $Server -Port $Port is the real, end-to-end verification, conceptually identical to Project 04's Invoke-WebRequest check.

Why it's used today: This is the same "config says X, does the real world actually show X" pattern you've now applied to IIS (04), clusters (15), and certificate keys (18) — firewall rules are simply the next place this lesson applies.

Auditing Rule Scope — RemoteAddress "Any" Detection

What it is: Get-NetFirewallAddressFilter exposes a rule's RemoteAddress property — a value of "Any" means the rule permits traffic from literally any source address, the broadest possible scope.

Why it's used today: Just like Project 11's local admin audit and Project 12's share permissions, this is a direct security scope check — comparing actual configuration against what was approved, flagging anything broader than intended.

Two Independent Verdicts From One Rule Set

What it is: This project deliberately runs two genuinely different kinds of checks — connectivity verification for required rules, and scope auditing for sensitive rules — against the same underlying firewall configuration, producing two distinct categories of finding.

Why it's used today: These aren't the same question asked twice — "does this work" and "is this too permissive" can each be true or false completely independently of the other, exactly as the story's two incidents demonstrate.

By Project 19, you should be able to predict this project's shape before reading the code: check the real-world effect, not just the configuration; audit scope against an approved baseline; treat "works" and "appropriately scoped" as separate questions. That instinct is the actual skill this academy has been building.

06 The Script — Test-FirewallCompliance.ps1

Scripts\Test-FirewallCompliance.ps1 
<#
.SYNOPSIS
    Windows Firewall Validation - ABC Bank Production Support
.DESCRIPTION
    Verifies required ports are genuinely reachable (not just configured)
    and audits sensitive ports for overly broad remote address scope.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$RequiredPorts  = Get-Content -Path "C:\FirewallValidation\Config\required-ports.json"  -Raw | ConvertFrom-Json
$SensitivePorts = Get-Content -Path "C:\FirewallValidation\Config\sensitive-ports.json" -Raw | ConvertFrom-Json

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\FirewallValidation\Logs\FirewallCheck_$TimeTag.log"
$ReportCSV = "C:\FirewallValidation\Reports\FirewallCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: CHECK 1 — REQUIRED PORT CONNECTIVITY
# ============================================================

function Test-RequiredPort {
    param([string]$ServerName, [int]$Port, [string]$Description)

    $TestResult = Test-NetConnection -ComputerName $ServerName -Port $Port -WarningAction SilentlyContinue   # Real connection attempt, not a config read

    $Status = if ($TestResult.TcpTestSucceeded) { "REACHABLE" } else { "CRITICAL - UNREACHABLE" }

    if (-not $TestResult.TcpTestSucceeded) {
        Write-Log "$ServerName`:$Port ($Description) is UNREACHABLE despite being a required port" "ERROR"
    }

    [PSCustomObject]@{
        CheckType     = "Connectivity"
        ServerName    = $ServerName
        Port          = $Port
        Description   = $Description
        Detail        = ""
        OverallStatus = $Status
        CheckedAt     = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }
}

# ============================================================
# SECTION 3: CHECK 2 — SENSITIVE PORT SCOPE AUDIT
# ============================================================

function Test-PortScope {
    param([string]$ServerName, [int]$Port, [string]$ApprovedRemoteAddress, [string]$Description)

    try {
        $ActualScope = Invoke-Command -ComputerName $ServerName -ArgumentList $Port -ScriptBlock {
            param($PortNum)
            $Rules = Get-NetFirewallRule -Direction Inbound -Enabled True |
                     Where-Object { ($_ | Get-NetFirewallPortFilter).LocalPort -eq $PortNum }   # Find rules actually covering this port
            $Rules | Get-NetFirewallAddressFilter | Select-Object -ExpandProperty RemoteAddress
        }

        $IsOverlyBroad = $ActualScope -contains "Any" -and $ApprovedRemoteAddress -ne "Any"   # Flag ONLY if "Any" wasn't actually approved

        $Status = if ($IsOverlyBroad) { "CRITICAL - SCOPE TOO BROAD" } else { "COMPLIANT" }

        if ($IsOverlyBroad) {
            Write-Log "$ServerName`:$Port ($Description) is open to ANY address — approved scope is $ApprovedRemoteAddress" "ERROR"
        }

        [PSCustomObject]@{
            CheckType     = "ScopeAudit"
            ServerName    = $ServerName
            Port          = $Port
            Description   = $Description
            Detail        = "Actual: $($ActualScope -join ', ') | Approved: $ApprovedRemoteAddress"
            OverallStatus = $Status
            CheckedAt     = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
        }
    }
    catch {
        Write-Log "Error auditing scope for $ServerName`:$Port : $($_.Exception.Message)" "ERROR"
    }
}

# ============================================================
# SECTION 4: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Firewall Validation =====" "INFO"

$ConnectivityResults = foreach ($Req in $RequiredPorts) {
    Test-RequiredPort -ServerName $Req.ServerName -Port $Req.Port -Description $Req.Description
}

$ScopeResults = foreach ($Sens in $SensitivePorts) {
    Test-PortScope -ServerName $Sens.ServerName -Port $Sens.Port `
                    -ApprovedRemoteAddress $Sens.ApprovedRemoteAddress -Description $Sens.Description
}

$AllResults = $ConnectivityResults + $ScopeResults

$AllResults | Sort-Object CheckType, OverallStatus -Descending | Format-Table -AutoSize -Wrap

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$CriticalCount = ($AllResults | Where-Object { $_.OverallStatus -like "CRITICAL*" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount finding(s) require review — see report" "WARNING"
}

Write-Log "===== Firewall Validation Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

Test-NetConnection -ComputerName $ServerName -Port $Port -WarningAction SilentlyContinue
This attempts a genuine TCP connection to the actual port, exactly as the real dependent service would — TcpTestSucceeded is ground truth, immune to whatever the firewall rule configuration merely claims. -WarningAction SilentlyContinue suppresses the noisy warning PowerShell prints to the console on a failed connection, since we're already capturing the real result in the object.
Where-Object { ($_ | Get-NetFirewallPortFilter).LocalPort -eq $PortNum }
Piping each rule individually into Get-NetFirewallPortFilter retrieves that specific rule's port details — necessary because port information isn't a direct property of the rule object itself, mirroring the same "related but separate object" pattern from AD group membership in Project 10.
$IsOverlyBroad = $ActualScope -contains "Any" -and $ApprovedRemoteAddress -ne "Any"
Deliberately only flags "Any" scope when "Any" wasn't the actual approved configuration — some ports (like a public-facing web server on 443) legitimately should be open to Any, and this check must be able to distinguish that intentional case from the story's genuine mistake.
$AllResults = $ConnectivityResults + $ScopeResults
Combining two arrays of genuinely different result shapes (both share common columns, but represent different check types) into one report — the shared CheckType column is what lets a reader immediately tell which of the two independent questions each row is actually answering.
Common mistake: flagging every port scoped to "Any" as a finding, without checking whether "Any" was actually the intended, approved configuration. A public HTTPS port is correctly open to Any — the check must compare against what's approved, not apply a blanket rule that would generate constant false findings.

08 Script Execution Flow

StepWhat Happens
1. Connectivity LoopEvery required port gets a genuine, real-time connection attempt — this directly reflects what the dependent service actually experiences.
2. Scope Audit LoopEvery sensitive port's actual configured remote address scope is read directly from the live firewall rule and compared to what was approved.
3. Independent EvaluationA port can pass connectivity and fail scope, or vice versa — the two loops never influence each other's verdict.
4. Combined ReportingBoth categories of finding land in one report, tagged by CheckType so a reader immediately understands which question each row answers.

09 Windows Internals — In Simple English

How Windows Firewall Rule Evaluation Works

Windows Firewall evaluates all applicable rules for a given connection attempt, and — critically — an explicit Block rule anywhere in that evaluation can override an Allow rule elsewhere, which is exactly how a seemingly-enabled Allow rule can still result in a blocked connection if another rule interferes.

Why Rule Objects and Filter Objects Are Separate

Windows Firewall's internal design separates a rule's general properties (name, action, enabled state) from its specific match criteria (ports, addresses, protocols, applications) — allowing the same underlying filter engine to evaluate many different kinds of criteria consistently.

CIDR Notation for Address Ranges

An approved scope like "203.0.113.0/24" describes a specific range of IP addresses using CIDR notation — the "/24" indicates how many addresses that range actually covers, and restricting a rule to a specific partner's range instead of "Any" is precisely the security control the story's second incident had failed to apply.

12 Production Best Practices

Always test real connectivity for business-critical ports — a rule's Enabled property alone is not proof the port is actually reachable.
Compare actual scope against an explicitly approved baseline, never a blanket "flag all Any rules" — some Any-scoped rules are entirely correct and intentional.
Treat connectivity failures and scope findings as genuinely different categories requiring different responses — one is an outage, the other is a security exposure.
Re-verify firewall rules after any bulk configuration change (like a GPO push) — exactly the trigger event in this project's first incident.

13 Interview Preparation

Q: Why isn't checking a firewall rule's Enabled property sufficient to confirm a port is actually reachable?
Multiple rules interact, an explicit Block rule elsewhere can override an Allow, and scope or port details can silently change without disabling the rule itself — only an actual connection attempt confirms real reachability, exactly as this project's Test-NetConnection check does.
Q: Why does the scope audit only flag "Any" when it wasn't the approved configuration?
Some rules legitimately need to be open to any source — a public HTTPS listener, for example — so the check needs to compare against what was actually approved for that specific port, not apply a blanket rule that would generate constant false findings on intentionally open ports.
Q: How do these two checks in this project relate to each other?
They're independent questions about the same underlying firewall configuration — whether it achieves required connectivity, and whether it's scoped no more broadly than necessary — a port can pass one and fail the other completely independently.
Q: What's a realistic trigger for re-running this validation outside its normal schedule?
Any bulk firewall configuration change — a Group Policy update, a security baseline push, or a manual rule change — exactly the kind of event that caused this project's first incident, where a config change silently altered a rule's actual effect without disabling it.

14 Key Learnings & Assignment

Key Learnings

  • A firewall rule's Enabled property is configuration, not proof of real-world effect — Test-NetConnection provides the actual verification
  • Rule scope auditing must compare against an approved baseline, not apply a blanket rule, since some broad scopes are entirely intentional
  • Connectivity and scope-appropriateness are independent questions that can each fail without the other failing
  • Bulk configuration changes (like GPO pushes) are a realistic, recurring trigger for firewall drift worth explicitly watching for
