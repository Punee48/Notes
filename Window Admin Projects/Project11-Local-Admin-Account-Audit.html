Project 11 — Local Administrator Account Audit

Somewhere on 500 servers, an account nobody remembers adding still has full local admin rights

Domain accounts (Project 10) are only half the access story — every Windows server also has its own local Administrators group, and over years of ad-hoc troubleshooting, contractor access, and forgotten "just for now" additions, that group quietly accumulates accounts nobody can explain. Today's script finds every one of them, across the whole fleet, and flags anything that isn't on the approved list.

SRV-APP02 — "temp_contractor" still a local admin
SRV-DB01 — unrecognized account "bkup_svc2"

01 The Production Story

A routine annual security audit turns up something nobody can explain.
Wednesday — Annual Security Audit, External Auditor On-Site

ABC Bank's annual security audit is underway, and the external auditor asks a simple-sounding question: "Can you show me exactly who has local administrator rights on every production Windows server, right now?" Priya's team goes quiet. Nobody has a current, complete answer — it would mean RDPing into hundreds of servers and manually checking Local Users and Groups on each one.

Two days of manual checking later, they find it: a local account called temp_contractor, added eleven months ago for a two-week project, still sitting in the local Administrators group on six servers. Nobody remembers approving it staying that long. It's exactly the kind of finding that turns a routine audit into a serious compliance conversation.

"Never again," Priya says. "I want a script that checks the local Administrators group on every server, compares it against an approved list we maintain, and flags anything — any account, built-in or not — that shouldn't be there. I don't want us finding this stuff during an audit. I want us finding it every single week, automatically, before an auditor ever has to ask."

This project is a direct security control, not just an operational check — in banking, unaccounted-for privileged access is one of the most serious findings an audit can produce, and it's also one of the easiest to prevent with a scheduled, automated check.

Business Requirement

Continuously verify that only approved accounts hold local administrator rights on every production Windows server.

A PowerShell script comparing each server's local Administrators group against a maintained approved-accounts list, flagging any mismatch.

Unauthorized privileged access gets caught within days, not discovered as a surprise finding during an annual audit.

03 New Concepts (Building on Projects 01–10)

You already know Compare-Object from Project 02 and remoting throughout. Here's what's new for local account auditing.
Get-LocalGroupMember — Reading Local Group Membership

What it is: Returns every member of a local group (like Administrators) on a Windows machine, whether that member is a local account, a domain user, or a domain group — each with a .Name and .ObjectClass property.

Why it's used today: This is the direct, modern replacement for manually opening Local Users and Groups (lusrmgr.msc) — Get-LocalGroupMember -Group "Administrators" gives us exactly what the auditor asked for, as structured objects.

Distinguishing Local Accounts From Domain Accounts in the Same Group

What it is: The Administrators group commonly contains a mix: local accounts (e.g. SRV-APP01\Administrator) and domain accounts or groups (e.g. ABCBANK\Domain Admins). The .Name property's prefix tells you which is which.

Why it matters: The story's problem — a forgotten local account — specifically means we need to identify and flag local accounts distinctly, since domain group membership is typically managed and audited through Active Directory itself (as in Project 10), a separate control.

Compare-Object Revisited — Against a Maintained Allow-List

What it is: The same cmdlet from Project 02, now comparing "who's actually in the Administrators group right now" against "who's approved to be there," per server.

Why it's used today: This single comparison is the heart of the audit — anything present that isn't on the approved list is exactly the kind of finding the story's audit uncovered the hard way.

-notin — Set Membership Testing

What it is: A cleaner alternative to Compare-Object for a simple case: $Account -notin $ApprovedList directly asks "is this single value absent from this list?" and returns true/false.

Why it's used today: For checking one account name at a time inside a loop, -notin reads more naturally than a full Compare-Object call — different tools for slightly different shapes of the same underlying question.

Built-In Account Exceptions

What it is: Every Windows server has certain accounts that are expected to be local administrators by default (like the built-in Administrator account itself) — these need to be explicitly allowed, not flagged as a surprise finding every single run.

Why it's used today: A good audit script separates "expected and fine" from "genuinely needs review" — flagging default, expected accounts as findings every week would train the team to ignore the report entirely.

This project is really a specific application of a general pattern you've now used several times: read the current real-world state, compare it against a defined "should be" state, and report only the differences. Health checks, patch compliance, and now security audits are all the same shape.

06 The Script — Test-LocalAdminCompliance.ps1

Scripts\Test-LocalAdminCompliance.ps1 
<#
.SYNOPSIS
    Local Administrator Account Audit - ABC Bank Production Support
.DESCRIPTION
    Checks the local Administrators group on every server against a
    maintained approved-accounts list, flagging any unauthorized member.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers       = Get-Content -Path "C:\LocalAdminAudit\Config\servers.txt"
$ApprovedConfig = Get-Content -Path "C:\LocalAdminAudit\Config\approved-admins.json" -Raw | ConvertFrom-Json

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\LocalAdminAudit\Logs\AdminAudit_$TimeTag.log"
$ReportCSV = "C:\LocalAdminAudit\Reports\AdminAudit_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-SERVER AUDIT FUNCTION
# ============================================================

function Test-ServerLocalAdmins {
    param([string]$ComputerName)

    # Build this server's full approved list: Global approved + anything specific to this server
    $ApprovedForThisServer = $ApprovedConfig.GlobalApproved
    if ($ApprovedConfig.PerServerApproved.$ComputerName) {
        $ApprovedForThisServer += $ApprovedConfig.PerServerApproved.$ComputerName   # Add any server-specific approved accounts too
    }

    try {
        $CurrentAdmins = Invoke-Command -ComputerName $ComputerName -ScriptBlock {
            Get-LocalGroupMember -Group "Administrators" -ErrorAction Stop |
                Select-Object -ExpandProperty Name             # Just the account names, e.g. "SRV-APP01\jsmith" or "ABCBANK\Domain Admins"
        }

        $Findings = @()
        foreach ($Admin in $CurrentAdmins) {
            # Strip the "SERVERNAME\" or "DOMAIN\" prefix for a simpler comparison against the approved list's short names where relevant
            $ShortName = ($Admin -split '\\')[-1]

            if ($Admin -notin $ApprovedForThisServer -and $ShortName -notin $ApprovedForThisServer) {   # Check both full and short forms
                $Findings += $Admin
                Write-Log "$ComputerName : UNAPPROVED local admin found -> $Admin" "WARNING"
            }
        }

        [PSCustomObject]@{
            ServerName        = $ComputerName
            TotalAdminCount   = $CurrentAdmins.Count
            UnapprovedFound   = $Findings.Count
            UnapprovedAccounts= ($Findings -join "; ")
            ComplianceStatus  = if ($Findings.Count -eq 0) { "COMPLIANT" } else { "FINDING - REVIEW REQUIRED" }
            CheckedAt         = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
        }
    }
    catch {
        Write-Log "Error auditing $ComputerName : $($_.Exception.Message)" "ERROR"
        [PSCustomObject]@{
            ServerName = $ComputerName; TotalAdminCount = $null; UnapprovedFound = $null
            UnapprovedAccounts = ""; ComplianceStatus = "CHECK FAILED"; CheckedAt = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
        }
    }
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Local Admin Audit for $($Servers.Count) server(s) =====" "INFO"

$AllResults = foreach ($Server in $Servers) { Test-ServerLocalAdmins -ComputerName $Server }

$AllResults | Sort-Object ComplianceStatus -Descending | Format-Table -AutoSize -Wrap

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$FindingsCount = ($AllResults | Where-Object { $_.ComplianceStatus -eq "FINDING - REVIEW REQUIRED" }).Count
if ($FindingsCount -gt 0) {
    Write-Log "$FindingsCount server(s) have unapproved local admin accounts requiring review" "WARNING"
}

Write-Log "===== Local Admin Audit Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

$ApprovedForThisServer = $ApprovedConfig.GlobalApproved then += a per-server list
Building a combined list per server (global rules plus any server-specific exception) means most servers only need the global list maintained once, while a database server needing its own service account doesn't require duplicating the entire global list.
$ShortName = ($Admin -split '\\')[-1]
Splits a value like "ABCBANK\jsmith" on the backslash and takes the last element, giving just "jsmith" — useful because the approved list might reasonably contain either the full domain-qualified name or just the short name, and we want to catch a match either way.
if ($Admin -notin $ApprovedForThisServer -and $ShortName -notin $ApprovedForThisServer)
Only flags an account as a finding if NEITHER its full name NOR its short name appears anywhere in the approved list — this dual check avoids false-positive findings caused purely by formatting differences between how an account is listed versus how it actually appears in the group.
Sort-Object ComplianceStatus -Descending
Puts "FINDING - REVIEW REQUIRED" ahead of "COMPLIANT" alphabetically in descending order — a small touch, but it means whoever opens the report sees the servers that actually need attention first, not buried after 490 compliant ones.
Common mistake: forgetting that Get-LocalGroupMember output includes domain groups and accounts alongside local ones. Treating every entry as if it were a local account can misclassify legitimate domain-managed access as a local-account finding — the approved list needs to explicitly account for expected domain entries too.

08 Script Execution Flow

StepWhat Happens
1. Build Approved ListGlobal and per-server approved accounts are combined fresh for each server before any comparison happens.
2. Remote QueryGet-LocalGroupMember runs inside the remote session, reading that specific server's actual local Administrators membership right now.
3. Per-Account ComparisonEach admin account is checked in both its full and short forms against the approved list — this is where every finding is actually decided.
4. Result AssemblyA server with zero unapproved accounts reports COMPLIANT; any unapproved account, even just one, marks it as a finding requiring review.
5. ReportingSame log/CSV pattern as every prior project, sorted so findings surface first for the reviewer.

09 Windows Internals — In Simple English

Local vs Domain Security Principals

A Windows server's local Administrators group can contain local accounts (defined only on that machine), domain user accounts, and domain groups all at once — Windows treats all of them as valid "security principals" it can grant access to.

Why This Group Specifically Matters So Much

Membership in the local Administrators group grants full control over that machine — installing software, changing any setting, reading any file — making it one of the highest-value targets for both attackers and audit scrutiny.

Why "Temporary" Access Often Isn't

Local group membership has no built-in expiration — an account added "just for two weeks" stays exactly as privileged as day one until someone manually removes it, which is precisely why the story's contractor account lasted eleven months.

12 Production Best Practices

Treat the approved-accounts list as a real, jointly-owned control document — reviewed and updated by both Ops and Security, not something one engineer edits alone.
Check both full and short account name formats — inconsistent naming between how an account appears in a group versus how it's listed in config is a common source of false findings.
Report findings, don't auto-remediate, for privileged access changes — removing someone's admin rights automatically without human review carries its own risk of breaking something legitimate.
Run this on a real recurring schedule (weekly, not just before an audit) — the entire value of this project is turning a once-a-year scramble into continuous assurance.

13 Interview Preparation

Q: Why does this script only report findings instead of automatically removing unapproved accounts?
Removing privileged access automatically risks breaking something a human hasn't yet had a chance to verify is truly unnecessary — for security-sensitive changes like this, a human review-and-approve step before removal is the safer, more defensible process.
Q: How do you handle the fact that the Administrators group can contain both local and domain accounts?
The approved list needs to explicitly include expected domain accounts and groups alongside local ones, and the comparison checks both the full domain-qualified name and the short name to avoid false positives from formatting differences.
Q: How would you convince a skeptical manager this is worth building?
By pointing directly at the story's real cost — two days of manual, reactive checking during an audit, versus this running automatically every week going forward, catching the same kind of finding within days instead of nearly a year.
Q: What's the biggest risk in this script's own design?
The approved list itself becoming stale or incomplete — if it isn't actively maintained alongside real access changes, the script will either produce noisy false findings or, worse, silently miss something because it was incorrectly pre-approved.

14 Key Learnings & Assignment

Key Learnings

  • Get-LocalGroupMember is the scriptable equivalent of manually checking Local Users and Groups on every server
  • Local privileged access has no built-in expiration — "temporary" access requires active removal, not the passage of time
  • Read current state, compare against defined state, report the difference — the same pattern from health checks and patch compliance, applied to security
  • Security-sensitive findings should be reported for human review, not automatically remediated
