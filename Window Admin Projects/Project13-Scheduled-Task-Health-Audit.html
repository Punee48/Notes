Project 13 — Scheduled Task Health Audit

Task Scheduler shows a green checkmark for a job that's failed silently for two weeks

Windows Task Scheduler will happily run a broken job forever without ever raising an alarm — "the task ran" and "the task succeeded" are two completely different things, and only one of them is visible at a glance. Today's script reads every critical scheduled task's actual last-run result code and translates the ones that matter.

01 The Production Story

A scheduled task that's been quietly failing for two weeks, discovered by accident.
Monday — A Disk Space Ticket Leads Somewhere Unexpected

An engineer investigates a disk space warning on SRV-BATCH01 — using the exact forecasting script from Project 08 — and traces it to a folder of temporary batch files that should have been cleaned up nightly by a scheduled task. Curious, they open Task Scheduler and check the task's history. It's been failing every single night for two weeks, with result code 0x1. Task Scheduler shows no red flag anywhere in its default view — the task simply "ran," on schedule, exactly as configured. It just never actually succeeded at what it was supposed to do.

Priya isn't surprised, exactly — she's seen this pattern before. "Task Scheduler tells you a task executed. It does not proactively tell you whether it worked. Nobody looks at Task Scheduler's history tab unless they already suspect a problem — which means a silently failing task can run 'successfully' from Windows' point of view for months. I want a script that checks every scheduled task we care about, reads its actual last result code, and tells us in plain English whether it actually succeeded — not just whether it ran."

"And while we're at it — I want it to flag any task that's been disabled, or hasn't run when it was supposed to, since both of those are just as invisible as a silent failure."

This project's core lesson: "ran" and "succeeded" are different claims, and a monitoring tool that only checks the first one gives a false sense of safety.

03 New Concepts (Building on Projects 01–12)

You already know remoting and hashtable-based verdict logic. Here's what's new for scheduled task auditing.
Get-ScheduledTask & Get-ScheduledTaskInfo

What it is: Get-ScheduledTask returns a task's definition (name, path, whether it's enabled); Get-ScheduledTaskInfo returns its actual run history summary — LastRunTime, LastTaskResult, and NextRunTime. They're two separate cmdlets because one describes the task's configuration and the other describes what actually happened when it ran.

Why it's used today: LastTaskResult is the exact value the story's engineer had to dig into Task Scheduler's UI to find — this project reads it directly and in bulk instead.

Interpreting Task Result Codes (Hex Values)

What it is: LastTaskResult is a numeric code, conventionally shown in hexadecimal — 0x0 means success; nonzero values mean something went wrong, ranging from a simple non-zero exit code from the task's own program (0x1) to Task Scheduler-specific codes like 0x41303 (task is currently running) or 0x8004131F (an instance is already running).

Why it's used today: Priya specifically wants plain English, not a hex code — a lookup table translating the common codes into a real explanation is what actually makes the report usable by someone who isn't a Task Scheduler internals expert.

Formatting Numbers as Hex — the -f Format Operator

What it is: '0x{0:X}' -f $ResultCode uses PowerShell's format operator to render a decimal number as a hexadecimal string, matching the format Task Scheduler itself displays results in — since LastTaskResult actually comes back from PowerShell as a plain decimal integer.

Why it matters: Without this, the report would show something like 1 where Ops is used to seeing 0x1 from the Task Scheduler UI — a small formatting detail that meaningfully affects whether the report feels trustworthy and familiar to the people reading it.

Detecting Overdue Tasks via NextRunTime

What it is: Comparing a task's NextRunTime against the current time — if a task's next scheduled run was supposed to already happen and hasn't, or its LastRunTime is much older than its expected interval, that's a strong sign something is wrong even before checking the result code.

Why it's used today: A disabled task never generates a failure result code at all — it simply stops running — so overdue detection is what catches the specific gap a result-code check alone would completely miss.

Notice this project reuses the exact hashtable-lookup translation pattern from Project 09's HTTP status verdict (Project 04's switch statement) — turning an opaque code into a human-readable explanation is a recurring, valuable technique across almost every monitoring domain.

04 Architecture

Two independent detection paths feed one report: a bad result code catches an active failure, while the overdue check catches the case a result code can't — a task that stopped running entirely.

06 The Script — Test-ScheduledTaskHealth.ps1

Scripts\Test-ScheduledTaskHealth.ps1 
<#
.SYNOPSIS
    Scheduled Task Health Audit - ABC Bank Production Support
.DESCRIPTION
    Checks every critical scheduled task's enabled state, last run
    result, and overdue status, translating cryptic result codes into
    plain English so silent task failures are no longer invisible.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$CriticalTasks = Get-Content -Path "C:\TaskAudit\Config\critical-tasks.json" -Raw | ConvertFrom-Json

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\TaskAudit\Logs\TaskAudit_$TimeTag.log"
$ReportCSV = "C:\TaskAudit\Reports\TaskAudit_$TimeTag.csv"

# Lookup table translating the most common Task Scheduler result codes into plain English
$ResultCodeMeanings = @{
    0           = "Success"
    1           = "Incorrect function called or unknown function — the task's program returned a generic error"
    2           = "File not found — the task's target program or script is missing"
    267009      = "Task is currently running"          # 0x41301
    267011      = "Task has not yet run"               # 0x41303
    2147943785  = "The user account (credentials) for this task is invalid"   # 0x8007052E
}

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-TASK HEALTH CHECK
# ============================================================

function Test-TaskHealth {
    param(
        [string]$ServerName,
        [string]$TaskPath,
        [string]$TaskName,
        [int]$MaxHoursSinceLastRun
    )

    $Result = [PSCustomObject]@{
        ServerName      = $ServerName
        TaskName        = $TaskName
        Enabled         = $null
        LastRunTime     = $null
        LastResultHex   = ""
        LastResultMeaning = ""
        HoursSinceRun   = $null
        OverallStatus   = "UNKNOWN"
        CheckedAt       = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        $TaskData = Invoke-Command -ComputerName $ServerName -ArgumentList $TaskPath, $TaskName -ScriptBlock {
            param($Path, $Name)
            $Task     = Get-ScheduledTask -TaskPath $Path -TaskName $Name -ErrorAction Stop   # The task's definition/configuration
            $TaskInfo = Get-ScheduledTaskInfo -TaskPath $Path -TaskName $Name -ErrorAction Stop   # The task's actual run history
            [PSCustomObject]@{
                Enabled      = ($Task.State -ne "Disabled")
                LastRunTime  = $TaskInfo.LastRunTime
                LastResult   = $TaskInfo.LastTaskResult      # Comes back as a plain decimal integer
            }
        }

        $Result.Enabled     = $TaskData.Enabled
        $Result.LastRunTime = $TaskData.LastRunTime
        $Result.LastResultHex = '0x{0:X}' -f $TaskData.LastResult    # Format as hex, matching Task Scheduler's own display

        # ---- TRANSLATE THE RESULT CODE ----
        $Result.LastResultMeaning = if ($ResultCodeMeanings.ContainsKey([int]$TaskData.LastResult)) {
            $ResultCodeMeanings[[int]$TaskData.LastResult]
        } else {
            "Unrecognized result code — needs manual lookup"
        }

        # ---- OVERDUE CHECK ----
        $Result.HoursSinceRun = [math]::Round(((Get-Date) - $TaskData.LastRunTime).TotalHours, 1)

        # ---- OVERALL VERDICT ----
        if (-not $Result.Enabled) {
            $Result.OverallStatus = "WARNING - DISABLED"
        }
        elseif ($TaskData.LastResult -ne 0) {
            $Result.OverallStatus = "CRITICAL - LAST RUN FAILED"
        }
        elseif ($Result.HoursSinceRun -gt $MaxHoursSinceLastRun) {
            $Result.OverallStatus = "WARNING - OVERDUE"       # Succeeded last time, but hasn't run again when expected
        }
        else {
            $Result.OverallStatus = "HEALTHY"
        }

        Write-Log "$ServerName\$TaskName : $($Result.OverallStatus) (Last result: $($Result.LastResultHex) - $($Result.LastResultMeaning))" `
                  (if ($Result.OverallStatus -eq "HEALTHY") { "INFO" } else { "WARNING" })
    }
    catch {
        Write-Log "Error checking task $TaskName on $ServerName : $($_.Exception.Message)" "ERROR"
        $Result.OverallStatus = "CRITICAL - CHECK FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Scheduled Task Health Audit for $($CriticalTasks.Count) task(s) =====" "INFO"

$AllResults = foreach ($Task in $CriticalTasks) {
    Test-TaskHealth -ServerName $Task.ServerName -TaskPath $Task.TaskPath `
                     -TaskName $Task.TaskName -MaxHoursSinceLastRun $Task.MaxHoursSinceLastRun
}

$AllResults | Sort-Object OverallStatus | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$UnhealthyCount = ($AllResults | Where-Object { $_.OverallStatus -ne "HEALTHY" }).Count
if ($UnhealthyCount -gt 0) {
    Write-Log "$UnhealthyCount task(s) need review — see report" "WARNING"
}

Write-Log "===== Scheduled Task Health Audit Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

$Result.LastResultHex = '0x{0:X}' -f $TaskData.LastResult
The -f format operator substitutes {0} with the value that follows it, formatted according to the :X specifier, which means "as hexadecimal." This turns the decimal integer PowerShell returns (e.g. 1) into the familiar 0x1 format Task Scheduler's own UI displays.
if ($ResultCodeMeanings.ContainsKey([int]$TaskData.LastResult))
.ContainsKey() checks a hash table for a key without risking an error if it's missing — casting to [int] first ensures the lookup key type matches exactly what's defined in the hash table, avoiding a silent type-mismatch miss.
$Result.HoursSinceRun = [math]::Round(((Get-Date) - $TaskData.LastRunTime).TotalHours, 1)
The same DateTime-subtraction pattern from Projects 06 and 08, this time measuring elapsed hours instead of days — reused here because it's exactly the right tool for "how long ago did this last happen."
elseif ($TaskData.LastResult -ne 0) { "CRITICAL - LAST RUN FAILED" }
This check comes BEFORE the overdue check deliberately — a task that ran recently but failed is a more urgent, more specific finding than a vaguer "hasn't run in a while," so the verdict logic checks the more actionable condition first.
Common mistake: assuming every task result code follows the simple "0 = good, nonzero = bad" rule without exception. A handful of Task Scheduler-specific codes (like "task is currently running") are nonzero but not actually failures — a naive check would generate false CRITICAL alerts for those; the lookup table is what prevents that.

08 Script Execution Flow

StepWhat Happens
1. Remote Task QueryBoth Get-ScheduledTask and Get-ScheduledTaskInfo run inside the same remote script block, avoiding two separate remote round-trips per task.
2. Hex FormattingThe raw decimal result code is converted to hex locally, purely for readability in the final report.
3. Lookup TranslationThe hash table converts the numeric code into plain English, falling back to an honest "needs manual lookup" for anything not explicitly mapped.
4. Layered VerdictDisabled state is checked first (most silent failure mode), then actual failure result codes, then overdue timing — in that specific priority order.
5. ReportingSame log/CSV pattern as every prior project, now carrying both the raw hex code and its plain-English meaning side by side.

09 Windows Internals — In Simple English

How Task Scheduler Actually Runs a Task

At the scheduled trigger time, the Task Scheduler service launches the configured program or script under the specified account, and records whatever exit code that program returns as the task's LastTaskResult — Task Scheduler itself has no idea whether that exit code represents genuine success.

Why Exit Code 0 Means Success (By Convention)

Returning 0 from a program to indicate success is a decades-old convention across essentially all operating systems — any nonzero value is available for a program to use to signal a specific kind of failure, which is exactly why the meaning of a nonzero code depends on the specific program.

Why a Disabled Task Produces No Failure Signal

A disabled task simply never triggers at all — there's no execution, no exit code, and therefore nothing for a result-code-only check to ever see; it can only be caught by checking the Enabled state directly, which is exactly why this project checks it as a separate, explicit condition.

12 Production Best Practices

Never assume "the task ran" means "the task succeeded" — always check the actual result code, not just execution history.
Check for disabled tasks explicitly — a disabled task produces no failure signal at all, since it never executes to generate one.
Maintain a real, growing lookup table for result codes rather than a generic "nonzero = bad" rule — some nonzero codes aren't actual failures.
Check overdue status even when the last known result was success — a task that stopped running entirely is just as dangerous as one that's actively failing.

13 Interview Preparation

Q: Why isn't "the task ran" enough information to know a scheduled task is healthy?
Task Scheduler only tracks whether the configured program was launched and what exit code it returned — it has no awareness of whether the underlying job actually accomplished what it was supposed to, which is exactly why the actual LastTaskResult must be checked and interpreted.
Q: Why does a disabled task need its own separate check instead of relying on the result code?
A disabled task never executes at all, so it never produces any result code — good or bad — meaning a check that only looks at LastTaskResult would completely miss it; only directly checking the Enabled state catches this failure mode.
Q: How do you decide the order of your verdict checks (disabled, then failed, then overdue)?
By specificity and urgency — a disabled task is the most silent and easiest to miss, an active failure is directly actionable and urgent, and overdue-but-previously-successful is a softer signal worth flagging but slightly less alarming than an active failure.
Q: What's a real limitation of this approach?
The result code lookup table only covers codes someone has already identified and documented — an unrecognized code falls back to "needs manual lookup," which still requires a human the first time any new code appears.

14 Key Learnings & Assignment

Key Learnings

  • "Ran" and "succeeded" are different claims — Task Scheduler only guarantees the former by default
  • Get-ScheduledTask and Get-ScheduledTaskInfo together give the full picture: configuration plus actual run history
  • A hash table lookup for translating cryptic codes into plain English is a broadly reusable technique across many monitoring domains
  • A disabled task and a failing task are different failure modes requiring different, explicit detection logic
