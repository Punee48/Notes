Project 17 — SQL Backup Validation

Right size, right timestamp, right name — and SQL Server itself says the backup is unreadable

Project 14 checked backup files from the outside: does it exist, is it recent, is its size normal. Today we go further and ask SQL Server itself to verify the backup's internal integrity — and check something Project 14 couldn't: whether a database's recovery model actually matches its real backup strategy, a gap that silently breaks point-in-time recovery.

01 The Production Story

A backup that looks perfect from the file system... and isn't, once SQL Server actually tries to read it.
Thursday — A Restore Test Nobody Expected to Fail

Following up on Project 14's lesson, the team starts periodically test-restoring backups to prove they genuinely work — not just look right from the outside. The very first test restore of a full backup fails immediately: SQL Server reports the backup file is corrupt and cannot be restored. The file existed. Its size was completely normal, right in line with historical averages — Project 14's exact checks would have shown it as perfectly VALIDATED. But something in the underlying data had been silently corrupted during the backup write, and only SQL Server's own internal page checksums could actually detect it.

In the same investigation, a second, quieter problem surfaces: the ReportingDB database is configured in FULL recovery model — meaning it's supposed to have regular transaction log backups feeding a continuous log chain — but nobody has been taking log backups for it at all. The full backups look fine, but full recovery model without log backups means the transaction log has been growing unchecked (feeding right back into Project 08's disk forecasting) and true point-in-time recovery is completely broken, even though a full backup "exists."

"Project 14 checks the outside of the box," Priya says. "Today I want us checking the inside. Ask SQL Server itself to verify a backup is actually readable and intact using its own internal checksum — not just trust the file looks right from the outside. And separately, check that every database's actual backup strategy matches what its recovery model requires — because a full backup alone is not a real backup strategy for a database that's supposed to be protected down to the transaction."

This project deepens Project 14's core lesson one more level: even independently checking the file's existence, recency, and size — genuinely good practice — still isn't the same as verifying the backup is actually restorable. Only the system that wrote the format can truly validate it.

03 New Concepts (Building on Projects 01–16)

You already know T-SQL querying from Project 16 and file-based backup checks from Project 14. Here's what's new.
msdb.dbo.backupset — SQL Server's Own Backup History

What it is: SQL Server records every backup it takes — full, differential, and log — directly in the backupset table inside the msdb system database, including when it ran and what type it was.

Why it's used today: This is a more authoritative source than checking file timestamps on disk — it's SQL Server's own record of what backups it actually performed, immune to the file being moved, renamed, or a separate copy job's timing confusing a file-based check.

RESTORE VERIFYONLY — True Integrity Verification

What it is: A T-SQL command that checks whether a backup file is complete and internally readable — including verifying checksums, if the backup was created with them — without actually performing a restore or touching any live database.

Why it's used today: This is the exact check that would have caught the story's corrupted backup — a file that looks completely normal from the outside can still fail this check, because it examines the backup's actual internal structure and data integrity, not just its size or timestamp.

Production nuance: VERIFYONLY is a lighter-weight check than a full test restore — it confirms the backup is structurally sound and readable, but a genuine periodic test restore remains the strongest possible verification, and is worth pursuing as a further initiative beyond this project's scope.

Recovery Model vs Backup Strategy

What it is: Every SQL Server database has a recovery model (SIMPLE, FULL, or BULK_LOGGED) that determines how its transaction log behaves. A database in FULL recovery model is specifically designed to support point-in-time recovery — but only if transaction log backups are actually being taken regularly; without them, the log simply grows indefinitely and no point-in-time capability is actually achieved.

Why it's used today: This is a genuinely different kind of check than "did a backup happen" — it's "does this database's actual backup pattern make sense given how it's configured," which is exactly the mismatch the story's ReportingDB had.

Joining Data From Two Different Sources in PowerShell

What it is: This project runs two separate T-SQL queries (recovery model from sys.databases, backup history from msdb.dbo.backupset) and combines their results per database in PowerShell — the same pattern as comparing two independent lists, applied here to correlate two related but separately-sourced facts about the same database.

This project's real lesson, layered on top of Project 14's: verification has depths. File-level checks catch obvious problems (missing, stale, wrong size). Only asking the actual system that owns the format — SQL Server itself — can catch true internal corruption. Know which depth of verification your risk actually requires.

04 Architecture

Two independent verdicts — is the backup file itself intact, and does the backup strategy actually match the recovery model — both roll into one combined result, since either one failing means the database isn't genuinely protected the way it appears to be.

06 The Script — Test-SqlBackupIntegrity.ps1

Scripts\Test-SqlBackupIntegrity.ps1 
<#
.SYNOPSIS
    SQL Backup Validation - ABC Bank Production Support
.DESCRIPTION
    Verifies SQL Server backup integrity using RESTORE VERIFYONLY and
    confirms each database's actual backup pattern matches what its
    recovery model requires (e.g. FULL model needs log backups too).
#>

Import-Module SqlServer

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Instances = Get-Content -Path "C:\SqlBackupValidation\Config\sql-instances.txt"
$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\SqlBackupValidation\Logs\SqlBackupCheck_$TimeTag.log"
$ReportCSV = "C:\SqlBackupValidation\Reports\SqlBackupCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-DATABASE BACKUP VALIDATION
# ============================================================

function Test-DatabaseBackup {
    param(
        [string]$InstanceName,
        [string]$DatabaseName,
        [string]$RecoveryModel
    )

    $Result = [PSCustomObject]@{
        InstanceName       = $InstanceName
        DatabaseName       = $DatabaseName
        RecoveryModel      = $RecoveryModel
        LastFullBackup     = $null
        LastLogBackup      = $null
        IntegrityVerified  = $false
        StrategyCompliant  = $false
        OverallStatus      = "UNKNOWN"
        CheckedAt          = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        # ---- GET LAST FULL AND LOG BACKUP FROM SQL SERVER'S OWN HISTORY ----
        $BackupHistoryQuery = @"
SELECT TOP 1 backup_finish_date, physical_device_name
FROM msdb.dbo.backupset bs
INNER JOIN msdb.dbo.backupmediafamily bmf ON bs.media_set_id = bmf.media_set_id
WHERE bs.database_name = '$DatabaseName' AND bs.type = 'D'   -- 'D' = Database (Full) backup
ORDER BY backup_finish_date DESC
"@
        $LastFull = Invoke-Sqlcmd -ServerInstance $InstanceName -Query $BackupHistoryQuery -QueryTimeout 15
        $Result.LastFullBackup = $LastFull.backup_finish_date

        if (-not $LastFull) {
            Write-Log "$InstanceName/$DatabaseName : NO full backup found in history" "ERROR"
            $Result.OverallStatus = "CRITICAL - NO FULL BACKUP"
            return $Result
        }

        # ---- CHECK 1: INTEGRITY — ASK SQL SERVER TO VERIFY THE ACTUAL BACKUP FILE ----
        $VerifyQuery = "RESTORE VERIFYONLY FROM DISK = N'$($LastFull.physical_device_name)'"
        try {
            Invoke-Sqlcmd -ServerInstance $InstanceName -Query $VerifyQuery -QueryTimeout 120   # Can take a while on large backups
            $Result.IntegrityVerified = $true                          # No exception thrown = SQL Server confirms the backup is valid
        }
        catch {
            Write-Log "$InstanceName/$DatabaseName : RESTORE VERIFYONLY FAILED — $($_.Exception.Message)" "ERROR"
            $Result.IntegrityVerified = $false
        }

        # ---- CHECK 2: STRATEGY — DOES BACKUP PATTERN MATCH RECOVERY MODEL? ----
        if ($RecoveryModel -eq "FULL") {
            $LogQuery = "SELECT MAX(backup_finish_date) AS LastLog FROM msdb.dbo.backupset WHERE database_name = '$DatabaseName' AND type = 'L'"   # 'L' = Log backup
            $LastLog = Invoke-Sqlcmd -ServerInstance $InstanceName -Query $LogQuery -QueryTimeout 15
            $Result.LastLogBackup = $LastLog.LastLog

            if (-not $Result.LastLogBackup -or ((Get-Date) - $Result.LastLogBackup).TotalHours -gt 24) {
                Write-Log "$InstanceName/$DatabaseName : FULL recovery model but NO recent log backup — point-in-time recovery is broken" "ERROR"
                $Result.StrategyCompliant = $false
            }
            else {
                $Result.StrategyCompliant = $true
            }
        }
        else {
            $Result.StrategyCompliant = $true      # SIMPLE/BULK_LOGGED models don't require log backups for this check's purposes
        }

        # ---- OVERALL VERDICT ----
        if (-not $Result.IntegrityVerified) {
            $Result.OverallStatus = "CRITICAL - BACKUP CORRUPT"
        }
        elseif (-not $Result.StrategyCompliant) {
            $Result.OverallStatus = "CRITICAL - RECOVERY GAP"
        }
        else {
            $Result.OverallStatus = "VALIDATED"
            Write-Log "$InstanceName/$DatabaseName : VALIDATED — integrity confirmed, backup strategy matches recovery model" "INFO"
        }
    }
    catch {
        Write-Log "Error validating backup for $InstanceName/$DatabaseName : $($_.Exception.Message)" "ERROR"
        $Result.OverallStatus = "CHECK FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting SQL Backup Validation =====" "INFO"

$AllResults = foreach ($Instance in $Instances) {
    $Databases = Invoke-Sqlcmd -ServerInstance $Instance `
        -Query "SELECT name, recovery_model_desc FROM sys.databases WHERE database_id > 4"   # Skips system databases (IDs 1-4)

    foreach ($Db in $Databases) {
        Test-DatabaseBackup -InstanceName $Instance -DatabaseName $Db.name -RecoveryModel $Db.recovery_model_desc
    }
}

$AllResults | Sort-Object OverallStatus -Descending | Format-Table -AutoSize -Wrap

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$CriticalCount = ($AllResults | Where-Object { $_.OverallStatus -like "CRITICAL*" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount database(s) FAILED backup validation — immediate DBA review required" "WARNING"
}

Write-Log "===== SQL Backup Validation Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

RESTORE VERIFYONLY FROM DISK = N'$($LastFull.physical_device_name)'
This T-SQL command asks SQL Server's own engine to read through the backup file and confirm it's structurally complete and internally consistent — it never touches the live database, but it exercises the exact same reading logic a real restore would use, which is why it can catch corruption a file-size check cannot.
try { Invoke-Sqlcmd ... $Result.IntegrityVerified = $true } catch { ... $Result.IntegrityVerified = $false }
If the backup fails verification, SQL Server raises an actual error, which Invoke-Sqlcmd surfaces as a PowerShell exception — the try/catch here is what turns "did this throw an error" into a clean, structured true/false result field.
WHERE bs.database_name = '$DatabaseName' AND bs.type = 'D'
The backupset table's type column uses single-letter codes: 'D' for Database (full), 'I' for Differential, and 'L' for Log — filtering explicitly on 'D' ensures we're finding the last FULL backup specifically, not accidentally picking up a differential or log backup instead.
if (-not $Result.LastLogBackup -or ((Get-Date) - $Result.LastLogBackup).TotalHours -gt 24)
Two conditions combine here: either no log backup has EVER been taken for this database (a completely missing strategy), or one exists but it's stale — both represent the same underlying problem the story's ReportingDB had, just at different stages of severity.
Common mistake: treating "a full backup exists and is recent" as sufficient for a database in FULL recovery model. As this project's story shows, a technically-valid full backup provides a false sense of security if the required log backup chain supporting point-in-time recovery has quietly never existed.

08 Script Execution Flow

StepWhat Happens
1. Database EnumerationEvery user database (system databases excluded) on each instance is discovered fresh at the start of each run — new databases are automatically included without config changes.
2. Backup History LookupSQL Server's own msdb history — not the file system — is the authoritative source for when and what was last backed up.
3. Integrity VerificationRESTORE VERIFYONLY genuinely exercises SQL Server's backup-reading logic — this step can take real time on large databases, unlike anything checked purely via file properties.
4. Strategy CheckOnly databases in FULL recovery model are held to the log-backup requirement — this branch is skipped entirely for SIMPLE/BULK_LOGGED databases, where it wouldn't apply.
5. Combined VerdictCorruption is checked before strategy compliance — an unreadable backup is the more fundamental, more urgent failure of the two.

09 Windows Internals — In Simple English

How SQL Server Backups Can Silently Corrupt

Disk errors, network interruptions during a backup to a remote share, or storage subsystem issues can all corrupt bytes within a backup file without the backup job itself failing — the write operation completes, the file exists, but the content isn't what it should be.

Why Recovery Models Exist

SIMPLE recovery model automatically reclaims transaction log space, trading away point-in-time recovery for operational simplicity; FULL recovery model retains the log specifically to support point-in-time restores, but only fulfills that promise if log backups are actually taken to periodically clear and archive that retained log.

Why an Unchecked Log Can Grow Indefinitely

In FULL recovery model, the transaction log only truncates (frees space) after a successful log backup — without one, the log file grows continuously with every transaction, directly connecting this project's finding back to Project 08's disk capacity forecasting.

12 Production Best Practices

Use RESTORE VERIFYONLY as routine practice, not just incident investigation — it's inexpensive relative to the risk it catches, especially for critical databases.
Always validate that a database's actual backup pattern matches its recovery model — a technically valid full backup can still leave point-in-time recovery completely broken.
Trust SQL Server's own backup history (msdb) over file system timestamps — it's the authoritative record, immune to file copies or moves confusing an external check.
Treat integrity failures and strategy gaps as distinct finding types in your reporting — a DBA needs to know immediately which kind of problem they're looking at.

13 Interview Preparation

Q: How is RESTORE VERIFYONLY different from the file-level checks in Project 14?
Project 14 checks external file properties — existence, timestamp, size — none of which can detect internal data corruption. RESTORE VERIFYONLY asks SQL Server's own engine to actually read through the backup's internal structure, catching corruption that looks completely normal from the outside.
Q: Why does a FULL recovery model database need log backups specifically, not just full backups?
FULL recovery model retains the transaction log specifically to enable point-in-time recovery, but that promise is only fulfilled if log backups are actually taken — without them, the log simply grows without ever being truncated, and true point-in-time recovery is never actually achieved despite full backups existing.
Q: Why query msdb.dbo.backupset instead of just checking file timestamps like Project 14 did?
SQL Server's own backup history is authoritative and can't be confused by an external file copy, a rename, or a separate archival job's timing — it directly reflects what SQL Server itself actually did, at the moment it did it.
Q: What's a genuine limitation even of RESTORE VERIFYONLY?
It confirms the backup is structurally readable and internally consistent, but a true, full test restore followed by actually querying the restored data remains the strongest possible verification — VERIFYONLY is a strong, inexpensive first layer, not a complete replacement for periodic real restore testing.
