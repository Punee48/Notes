Project 22 — VMware Windows VM Validation

Below the OS, below the disk you can see — a hypervisor layer with its own entirely separate way to fail

Everything so far checked the Windows Server itself. But almost every one of ABC Bank's servers is actually a virtual machine, running on VMware underneath — a layer with its own health, its own configuration, and its own classic failure mode: the snapshot everyone forgot about.

01 The Production Story

A slow VM that no Windows-level check could ever explain — because the problem wasn't in Windows at all.
Friday — A Mystery Slowdown That Wasn't in Windows At All

SRV-DB01 has been getting progressively, mysteriously slower over the past few weeks. Every check you've built in this academy comes back clean: CPU normal, memory normal, disk space fine, no blocking chains, services all running. Genuinely nothing wrong with Windows itself. An infrastructure engineer finally logs into vCenter directly — the VMware management layer, a completely different system from anything checked so far — and finds it immediately: a snapshot taken 134 days ago before a change that was never actually rolled back, still sitting there, still active, growing larger every single day as changes accumulate in it.

A VMware snapshot doesn't show up anywhere in Windows. The Windows Server has absolutely no visibility into it — from inside the guest operating system, there is no possible way to detect that a snapshot exists, let alone how old or how large it's become. The snapshot was silently causing serious disk I/O overhead on the underlying datastore, which manifested inside Windows only as vague, hard-to-diagnose "everything feels a little slow."

"This is a genuinely new layer for us," Priya says. "Everything we've built checks the operating system or something running inside it. This is checking the actual virtual machine itself, from the hypervisor's point of view — completely below and outside anything Windows can see. I want us checking for old snapshots and confirming VMware Tools is current across our whole VM fleet, on a real schedule, because nothing inside Windows will ever tell us about a problem at this layer."

This is the final new "layer" in a running theme across this academy: OS (01), application (04), cluster (15), database (16), and now virtualization (22) — each one genuinely invisible to every layer above it.

02 Business Case

Business Requirement

Detect virtualization-layer problems — old snapshots, outdated VMware Tools — invisible to any check running inside the guest OS.

Customer Requirement

Infrastructure wants proactive detection of forgotten snapshots before they cause performance degradation or datastore exhaustion.

Banking Scenario

The overwhelming majority of ABC Bank's server fleet runs as virtual machines — the hypervisor layer underneath is just as critical as the OS layer above it.

Current Manual Process

Nobody checks vCenter proactively — snapshot and VM configuration issues are only discovered when someone manually investigates an otherwise-unexplained symptom.

Problems With Current Process

A forgotten snapshot can grow for months, causing gradual performance degradation with no possible detection from inside the affected VM itself.

Business Challenges

This layer requires an entirely different toolset (VMware PowerCLI) and a different connection target (vCenter, not the individual servers).

Risk Analysis

An old, growing snapshot risks both performance degradation and, in the worst case, filling the underlying datastore entirely — a risk to every VM sharing that storage, not just one.

Business Impact

Proactive snapshot and VMware Tools monitoring catches virtualization-layer problems before they manifest as a confusing, hard-to-diagnose Windows-level symptom.

Why Automation Is Required

Only automation can check every VM's snapshot age and VMware Tools status across the fleet, consistently, at a layer nothing inside Windows can see.

Solution Design

A PowerShell script using VMware PowerCLI to check snapshot age and VMware Tools status across every VM in vCenter.

Project Scope

Phase 1 covers snapshot age detection and VMware Tools status — not full VM resource allocation or performance analytics.

Expected Benefits

Snapshot-related performance and capacity risks get caught within days, not discovered after weeks of gradual, mysterious degradation.

03 New Concepts (Building on Projects 01–21)

You already know date-based age checks and layered independent verdicts. Here's what's genuinely new: an entirely different platform.
VMware PowerCLI — A Completely Different Module Ecosystem

What it is: PowerCLI is VMware's own official PowerShell module suite for managing vSphere/vCenter environments — Connect-VIServer, Get-VM, Get-Snapshot, and dozens of related cmdlets, installed separately from anything Windows-native.

Why it's used today: Everything checked so far talks to Windows Server directly. PowerCLI talks to vCenter — the management layer for the hypervisor itself — an entirely different target system with its own authentication, its own object model, and its own separate installation.

Connect-VIServer — Authenticating to vCenter

What it is: Establishes an authenticated session against a vCenter server, required before any other PowerCLI cmdlet will work — conceptually similar to how Invoke-Sqlcmd needed a SQL Server connection, but to an entirely different kind of system.

Why it's used today: This is the entry point for every check in this project — without a successful connection, nothing about the VM layer is reachable at all.

Get-Snapshot — Finding Forgotten Snapshots

What it is: Returns every snapshot that exists for a given VM (or across all VMs), including its .Created date — from which the exact same date-arithmetic pattern from Projects 06 and 08 calculates snapshot age.

Why it's used today: This is the direct fix for the story's incident — a snapshot older than a defined threshold (say, 7 days) is almost always either forgotten or something that should have been cleaned up as part of whatever change created it.

Checking VMware Tools Status

What it is: VMware Tools is a set of drivers and services installed inside the guest OS that improve performance and enable features like accurate time sync and graceful shutdown — a VM's ExtensionData.Guest.ToolsStatus property (accessible via Get-VM) reports whether it's current, out of date, or not running.

Why it's used today: Outdated VMware Tools is a common, low-visibility source of subtle performance and reliability issues — exactly the kind of thing worth checking proactively rather than discovering during an investigation.

The single biggest lesson of this project: no matter how thoroughly you monitor inside a system, some problems are structurally invisible from inside it. The hypervisor is a perfect, concrete example — Windows genuinely cannot see its own snapshot, no matter how good your OS-level monitoring is.

06 The Script — Test-VMwareHealth.ps1

Scripts\Test-VMwareHealth.ps1 
<#
.SYNOPSIS
    VMware Windows VM Validation - ABC Bank Production Support
.DESCRIPTION
    Connects directly to vCenter to check for aging snapshots and
    outdated VMware Tools across the VM fleet — problems that are
    completely invisible from inside the Windows guest OS itself.
#>

Import-Module VMware.PowerCLI -ErrorAction Stop
Set-PowerCLIConfiguration -InvalidCertificateAction Ignore -Confirm:$false | Out-Null   # Lab-friendly setting; production should use valid vCenter certificates

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Config = Get-Content -Path "C:\VMwareValidation\Config\vcenter.json" -Raw | ConvertFrom-Json

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\VMwareValidation\Logs\VMCheck_$TimeTag.log"
$ReportCSV = "C:\VMwareValidation\Reports\VMCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: CONNECT TO VCENTER
# ============================================================

try {
    Connect-VIServer -Server $Config.VCenterServer -ErrorAction Stop | Out-Null   # Prompts for credentials interactively if not otherwise supplied
    Write-Log "Connected to vCenter: $($Config.VCenterServer)" "INFO"
}
catch {
    Write-Log "FAILED to connect to vCenter: $($_.Exception.Message)" "ERROR"
    throw                                          # Nothing else in this script can run without a connection — stop here
}

# ============================================================
# SECTION 3: CHECK 1 — AGING SNAPSHOTS
# ============================================================

$SnapshotResults = Get-Snapshot -VM * |                    # Every snapshot, across every VM, in one call
    ForEach-Object {
        $AgeDays = ((Get-Date) - $_.Created).Days     # Same date-arithmetic pattern as Projects 06 and 08
        [PSCustomObject]@{
            CheckType   = "Snapshot"
            VMName      = $_.VM.Name
            Detail      = "'$($_.Name)' created $($_.Created.ToString('yyyy-MM-dd')), $AgeDays day(s) old"
            SizeGB      = [math]::Round($_.SizeGB, 1)
            OverallStatus = if ($AgeDays -gt $Config.MaxSnapshotAgeDays) { "CRITICAL - AGED SNAPSHOT" } else { "OK" }
        }
    }

$SnapshotResults | Where-Object { $_.OverallStatus -ne "OK" } | ForEach-Object {
    Write-Log "$($_.VMName) : $($_.Detail) ($($_.SizeGB) GB) — exceeds $($Config.MaxSnapshotAgeDays) day threshold" "ERROR"
}

# ============================================================
# SECTION 4: CHECK 2 — VMWARE TOOLS STATUS
# ============================================================

$ToolsResults = Get-VM |                                # Every VM in the connected vCenter
    Select-Object Name, @{Name="ToolsStatus"; Expression = { $_.ExtensionData.Guest.ToolsStatus }} |
    ForEach-Object {
        [PSCustomObject]@{
            CheckType     = "VMwareTools"
            VMName        = $_.Name
            Detail        = "ToolsStatus: $($_.ToolsStatus)"
            SizeGB        = $null
            OverallStatus = if ($_.ToolsStatus -eq "toolsOk") { "OK" } else { "WARNING - TOOLS NOT CURRENT" }
        }
    }

$ToolsResults | Where-Object { $_.OverallStatus -ne "OK" } | ForEach-Object {
    Write-Log "$($_.VMName) : $($_.Detail)" "WARNING"
}

# ============================================================
# SECTION 5: COMBINE, REPORT, DISCONNECT
# ============================================================

$AllResults = $SnapshotResults + $ToolsResults

$AllResults | Sort-Object CheckType, OverallStatus -Descending | Format-Table -AutoSize -Wrap

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$CriticalCount = ($AllResults | Where-Object { $_.OverallStatus -like "CRITICAL*" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount aged snapshot(s) found — review and clean up required" "WARNING"
}

Disconnect-VIServer -Server $Config.VCenterServer -Confirm:$false   # Always close the vCenter session cleanly when done

Write-Log "===== VMware Validation Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

Connect-VIServer -Server $Config.VCenterServer -ErrorAction Stop
Establishes the authenticated session every subsequent PowerCLI cmdlet in the script depends on — wrapping it in try/catch with a re-thrown error is deliberate: there is genuinely no useful way to continue the script if this fails, unlike a single unreachable server in a larger fleet check.
Get-Snapshot -VM *
The -VM * wildcard asks for snapshots across every VM in the connected vCenter in a single call, rather than looping through VM names individually — PowerCLI's own filtering handles the fan-out efficiently.
$_.ExtensionData.Guest.ToolsStatus
ExtensionData exposes the full, raw underlying vSphere API object behind the friendlier Get-VM result — ToolsStatus specifically isn't surfaced as a simple top-level property on the VM object, so reaching into ExtensionData is the standard PowerCLI pattern for properties like this one.
Disconnect-VIServer -Server $Config.VCenterServer -Confirm:$false
Explicitly closing the vCenter session when the script finishes is good practice, mirroring the same "always clean up your connections" discipline as closing the TcpClient/SslStream in Project 06 — -Confirm:$false suppresses an interactive prompt that would otherwise block unattended/scheduled execution.
Common mistake: assuming a Windows-level check (like Project 08's disk forecasting) would ever catch a growing snapshot. A snapshot lives entirely in the VMware datastore layer — from inside the guest OS, the VM's own C: drive can show completely stable free space while the underlying snapshot grows unbounded, invisible to literally every check built earlier in this academy.

08 Script Execution Flow

StepWhat Happens
1. vCenter ConnectionA single authenticated session is established before anything else can run — this is a hard prerequisite, not an optional first check.
2. Snapshot EnumerationEvery snapshot across every VM is pulled in one call, with age calculated using the same DateTime subtraction pattern from earlier projects.
3. Tools Status EnumerationEvery VM's ToolsStatus is read from the deeper ExtensionData object, since it isn't exposed as a simple top-level property.
4. Combined ReportingTwo genuinely different check types (snapshot age, tools status) combine into one report, tagged by CheckType for clarity.
5. Clean DisconnectThe vCenter session is explicitly closed at the end, regardless of how many findings were reported.

09 Windows Internals — In Simple English

What a VMware Snapshot Actually Is

A snapshot freezes a VM's disk state at a point in time and redirects all subsequent writes into a separate delta file — the longer a snapshot exists, the larger that delta file grows, and the more overhead is added to every disk operation the VM performs.

Why Snapshots Are Meant to Be Temporary

VMware explicitly documents snapshots as a short-term tool (typically hours to a few days, for something like taking a backup or testing a risky change) — not a long-term backup strategy, precisely because of the accumulating performance and storage overhead the story's incident demonstrates.

Why the Guest OS Genuinely Cannot See a Snapshot

A snapshot operates entirely at the hypervisor's storage virtualization layer, below anything the guest operating system has any visibility into — Windows simply sees a virtual disk behaving normally; it has no API, no registry key, no possible way to know a snapshot exists.

11 Hands-On Lab

This lab requires access to a vCenter environment (a nested lab vCenter/ESXi setup is common for practice, but genuinely optional infrastructure most learners won't have readily available). If you don't have access, focus on the conceptual walkthrough below.

Prerequisites

  • Install-Module -Name VMware.PowerCLI -Scope CurrentUser
  • Access to a test vCenter server with at least one test VM you can safely snapshot

If You Have vCenter Access

  1. Update vcenter.json with your test vCenter's address and a short MaxSnapshotAgeDays (e.g. 0, for immediate testing purposes)
  2. Take a real snapshot of a test VM: New-Snapshot -VM "YourTestVM" -Name "Lab Test Snapshot"
  3. Run the script — with MaxSnapshotAgeDays set to 0, even a brand-new snapshot should immediately report CRITICAL - AGED SNAPSHOT, letting you verify the logic without waiting real days
  4. Clean up: Get-Snapshot -VM "YourTestVM" | Remove-Snapshot -Confirm:$false

If You Don't Have vCenter Access

  • Review VMware's official PowerCLI documentation examples for Get-Snapshot and Get-VM to understand the real object properties and shapes you'd be working with
  • Trace through the script's logic by hand with a hypothetical snapshot dataset: three VMs, one with a 2-day-old snapshot, one with a 45-day-old snapshot, one with none — write out what you'd expect the report to show for each

12 Production Best Practices

Never treat snapshots as a long-term backup solution — they're a short-term tool with a real, accumulating performance cost the longer they exist.
Always explicitly disconnect a PowerCLI session when finished — leaving vCenter sessions open unnecessarily is both a resource and security consideration.
Remember that hypervisor-layer problems are structurally invisible from inside the guest OS — no amount of OS-level monitoring sophistication substitutes for checking this layer directly.
Keep the snapshot age threshold realistic and enforced — a 7-day threshold with no actual cleanup process behind it is just a report nobody acts on.

13 Interview Preparation

Q: Why is a growing VMware snapshot invisible to every OS-level check built earlier in this academy?
A snapshot exists entirely at the hypervisor's storage virtualization layer — the guest OS has no API or mechanism to detect it, since from Windows' perspective the virtual disk simply continues to behave normally regardless of what's happening underneath it at the datastore level.
Q: Why shouldn't snapshots be used as a long-term backup strategy?
The delta file backing a snapshot grows continuously as changes accumulate, adding increasing disk I/O overhead the longer it exists — VMware explicitly documents snapshots as a short-term tool, not a backup mechanism, which is why Project 14/17-style genuine backups remain necessary regardless of snapshot usage.
Q: What's the real organizational risk of not monitoring this layer?
Exactly this project's story — gradual, hard-to-diagnose performance degradation that every OS-level check reports as healthy, potentially escalating to full datastore exhaustion affecting every VM sharing that storage, not just the one with the forgotten snapshot.
Q: How does this project fit into the broader pattern from this academy?
It's the same "check the layer you're actually responsible for, don't assume a layer above or below is fine just because everything visible looks fine" lesson as Projects 04, 15, 16, and 19 — applied here to the deepest layer covered in the whole series, below the operating system itself.
