Project 08 — Disk Space Monitoring & Capacity Forecasting

Don't tell me the disk is 85% full. Tell me it'll be full in 9 days.

Project 01 checked one drive against one static threshold. Today we check every fixed drive on every server, keep a running history of every reading, and use that history to calculate a real growth rate — turning "it's getting full" into "here's exactly when it runs out, at this rate."

SRV-APP01 D: — 340 days until full
SRV-DB01 E: — 22 days until full
SRV-DB01 L: (logs) — 4 days until full

01 The Production Story

A weekend outage that a simple threshold check would have caught days too late.
Sunday, 3:40 AM — SQL Server Transaction Log Full

The core banking database's transaction log drive fills up completely at 3:40 AM Sunday. SQL Server can't write new transactions. Every banking application connected to it starts failing simultaneously. It takes the on-call DBA forty minutes to diagnose, free up space, and recover — forty minutes of a fully down core banking system on a Sunday morning.

Monday's post-incident review is blunt. "Our disk check only ever looks at the C: drive, and it only tells us the number right now," Priya says. "That log drive had been filling steadily for two weeks. If we'd been tracking the trend, we would have known exactly which day it would hit zero — with enough warning to schedule a fix calmly during business hours, instead of firefighting at 3:40 on a Sunday."

"I want two upgrades to your original disk check from Project 01: first, check every fixed drive on every server, not just C:. Second — and this is the important part — keep history. Every time this runs, save today's numbers alongside everything we've already collected, so we can calculate how fast each drive is actually filling up, and forecast exactly when it'll run out at that rate."

This is the first project where a single run of the script isn't the whole story — today's value comes from comparing today's reading against a growing history the script builds up over time, one run at a time.

02 Business Case

Business Requirement

Forecast disk capacity exhaustion days or weeks in advance, not just alert once a static threshold is already crossed.

Customer Requirement

Ops wants an estimated "days until full" figure per drive, not just a current percentage-used snapshot.

Banking Scenario

Database transaction logs, batch processing staging areas, and application log drives can all fill gradually and predictably before an abrupt failure.

Current Manual Process

Project 01's health check reports current disk usage on C: only, with no trend or forecast, and no coverage of other drives.

Problems With Current Process

A static "20GB free" threshold treats a drive that's been stable for months the same as one filling up fast enough to hit zero by tomorrow.

Business Challenges

Predicting "when" requires historical data — a single point-in-time check can never calculate a growth rate on its own.

Risk Analysis

A full transaction log or staging drive can halt an entire dependent system all at once, exactly like the story's incident.

Business Impact

Forecasted capacity turns a 3 AM emergency into a scheduled, calm Tuesday-afternoon maintenance task.

Why Automation Is Required

Only automation can consistently capture, store, and analyze daily readings across every drive on every server, indefinitely.

Solution Design

A PowerShell script that captures every fixed drive's usage, appends it to a running history file, and calculates a forecast from that history.

Project Scope

Phase 1 covers all fixed drives, a growing historical CSV, and a simple linear days-until-full forecast per drive.

Expected Benefits

Capacity issues become scheduled maintenance instead of weekend emergencies, with weeks of advance notice instead of none.

03 New Concepts (Building on Projects 01–07)

You already know CIM queries and date math. Here's what's new for building a forecast out of accumulating history.
Checking Every Fixed Drive, Not Just C:

What it is: Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" returns every fixed drive (DriveType 3), as opposed to network drives, removable media, or CD-ROM drives — automatically covering D:, E:, L:, or however many drives a given server has.

Why it's used today: The story's incident happened on a drive letter Project 01 never checked. Enumerating all fixed drives instead of hardcoding "C:" closes exactly that gap.

Append-Only Historical Data with Export-Csv -Append

What it is: Export-Csv normally overwrites a file. Adding -Append instead adds new rows to the end of an existing CSV, preserving everything written by previous runs.

Why it's used today: Forecasting requires history. Each time the script runs (e.g. daily via Scheduled Task), it appends one more snapshot per drive to a single, ever-growing history file, rather than replacing yesterday's data.

Import-Csv — Reading History Back In

What it is: The reverse of Export-Csv: reads a CSV file back into PowerShell as real objects, letting today's run analyze everything every previous run has recorded.

Why it matters: This is what makes the forecast possible — the script reads its own accumulated history at the start of each run to calculate a trend, then adds today's new reading at the end.

Simple Linear Trend Calculation

What it is: A straightforward rate-of-change calculation: take the oldest and newest historical readings for a drive, find how much free space changed and over how many days, and divide to get a daily rate — then divide remaining free space by that rate to estimate days until full.

Why a simple approach is the right starting point: True statistical forecasting (linear regression across every point, seasonality, etc.) is more accurate but considerably more complex — a first-to-last comparison is honest, easy to explain to a non-technical stakeholder, and catches the story's scenario perfectly well. Production teams often start simple and add sophistication only if the simple version proves insufficient.

Grouping Historical Rows by Server + Drive

What it is: The history file contains readings for every drive on every server, all in one file. Group-Object (from Projects 02 and 07) separates that history back out per unique server-and-drive-letter combination before calculating each one's individual trend.

This project's real lesson: some of the most valuable automation isn't a smarter single check — it's simply remembering yesterday. A history file plus basic arithmetic often beats a much more "clever" one-shot check.

06 The Script — Get-DiskCapacityForecast.ps1

Scripts\Get-DiskCapacityForecast.ps1 
<#
.SYNOPSIS
    Disk Capacity Monitoring & Forecasting - ABC Bank Production Support
.DESCRIPTION
    Scans every fixed drive across the server list, appends today's
    reading to a growing history file, then calculates a simple
    days-until-full forecast per drive from that accumulated history.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers      = Get-Content -Path "C:\DiskForecast\Config\servers.txt"
$HistoryFile  = "C:\DiskForecast\History\disk-history.csv"
$WarningDays  = 30                       # Forecasted days-until-full at or below this = WARNING
$CriticalDays = 7                        # Forecasted days-until-full at or below this = CRITICAL

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\DiskForecast\Logs\DiskForecast_$TimeTag.log"
$ReportCSV = "C:\DiskForecast\Reports\DiskForecast_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: TODAY'S SNAPSHOT — ALL FIXED DRIVES, ALL SERVERS
# ============================================================

function Get-TodaysDiskSnapshot {
    param([string]$ComputerName)

    try {
        $Disks = Get-CimInstance -ClassName Win32_LogicalDisk -ComputerName $ComputerName -Filter "DriveType=3"  # 3 = Fixed disk, covers EVERY drive letter

        foreach ($Disk in $Disks) {
            [PSCustomObject]@{
                Date         = Get-Date -Format "yyyy-MM-dd"          # Day-level granularity is enough for a daily trend
                ServerName   = $ComputerName
                DriveLetter  = $Disk.DeviceID
                SizeGB       = [math]::Round($Disk.Size / 1GB, 2)
                FreeSpaceGB  = [math]::Round($Disk.FreeSpace / 1GB, 2)
                PercentFree  = [math]::Round(($Disk.FreeSpace / $Disk.Size) * 100, 1)
            }
        }
    }
    catch {
        Write-Log "Error scanning disks on $ComputerName : $($_.Exception.Message)" "ERROR"
    }
}

# ============================================================
# SECTION 3: FORECAST CALCULATION FROM HISTORY
# ============================================================

function Get-CapacityForecast {
    param($HistoryRows)              # All historical rows for ONE specific server+drive combination

    $Sorted = $HistoryRows | Sort-Object { [datetime]$_.Date }   # Oldest first — CSV values come back as text, so cast to [datetime]
    $Oldest = $Sorted | Select-Object -First 1
    $Newest = $Sorted | Select-Object -Last 1

    $DaysBetween = ([datetime]$Newest.Date - [datetime]$Oldest.Date).Days
    if ($DaysBetween -lt 1) {
        return "INSUFFICIENT HISTORY"       # Need at least 2 different days of data to calculate any rate at all
    }

    $FreeSpaceChange = [double]$Newest.FreeSpaceGB - [double]$Oldest.FreeSpaceGB   # Negative = shrinking (filling up)
    $DailyRate = $FreeSpaceChange / $DaysBetween              # GB gained or lost per day

    if ($DailyRate -ge 0) {
        return "STABLE OR GROWING"          # Free space isn't shrinking — no forecast needed
    }

    $DaysUntilFull = [math]::Round([double]$Newest.FreeSpaceGB / [math]::Abs($DailyRate), 0)   # Remaining free space ÷ daily loss rate
    return $DaysUntilFull
}

# ============================================================
# SECTION 4: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Disk Capacity Scan for $($Servers.Count) server(s) =====" "INFO"

$TodaysSnapshot = foreach ($Server in $Servers) { Get-TodaysDiskSnapshot -ComputerName $Server }

$TodaysSnapshot | Export-Csv -Path $HistoryFile -Append -NoTypeInformation   # -Append: ADD to history, never overwrite it
Write-Log "Appended $($TodaysSnapshot.Count) new reading(s) to history" "INFO"

$FullHistory = Import-Csv -Path $HistoryFile              # Read back EVERY reading ever recorded, including today's

$ForecastResults = $FullHistory |
    Group-Object ServerName, DriveLetter |               # One group per unique server+drive combination
    ForEach-Object {
        $Latest = $_.Group | Sort-Object { [datetime]$_.Date } | Select-Object -Last 1   # Today's reading for this drive
        $Forecast = Get-CapacityForecast -HistoryRows $_.Group

        $Verdict = switch ($true) {
            { $Forecast -is [string] }                    { "N/A" }             # "INSUFFICIENT HISTORY" or "STABLE OR GROWING"
            { $Forecast -le $CriticalDays }             { "CRITICAL" }
            { $Forecast -le $WarningDays }              { "WARNING" }
            default                                     { "OK" }
        }

        [PSCustomObject]@{
            ServerName        = $Latest.ServerName
            DriveLetter       = $Latest.DriveLetter
            CurrentFreeGB     = $Latest.FreeSpaceGB
            CurrentPercentFree= $Latest.PercentFree
            ForecastDaysLeft  = $Forecast
            Verdict           = $Verdict
        }
    }

$ForecastResults | Sort-Object @{Expression={ if ($_.ForecastDaysLeft -is [int]) { $_.ForecastDaysLeft } else { 99999 } }} |  # Most urgent numeric forecast first
    Format-Table -AutoSize

$ForecastResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$CriticalCount = ($ForecastResults | Where-Object { $_.Verdict -eq "CRITICAL" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount drive(s) forecasted to run out of space within $CriticalDays days" "WARNING"
}

Write-Log "===== Disk Capacity Forecast Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

Export-Csv -Path $HistoryFile -Append -NoTypeInformation
Without -Append, this would completely overwrite the history file with only today's readings, destroying every previous day's data — the entire forecast depends on this one flag being present.
Sort-Object { [datetime]$_.Date }
Every value read back by Import-Csv is plain text, even a column that looks like a date — casting it to [datetime] inside the sort script block ensures dates sort chronologically (Jan 2, Jan 10, Jan 21) instead of alphabetically as text (Jan 10, Jan 2, Jan 21).
$DailyRate = $FreeSpaceChange / $DaysBetween
A deliberately simple trend: total change in free space divided by total days elapsed between the very first and very latest reading. It ignores day-to-day noise in favor of the overall direction — good enough to catch a drive on a genuine multi-week decline, which is exactly the story's scenario.
switch ($true) { { $Forecast -is [string] } { "N/A" } { $Forecast -le $CriticalDays } { "CRITICAL" } ... }
An advanced switch pattern: switching on the literal value $true with script-block conditions lets each case be its own boolean test, evaluated top to bottom — a clean way to express several independent conditions without a long if/elseif chain.
Common mistake: comparing CSV values directly without casting them first. Everything Import-Csv returns is a string, so "9.5" -gt "10" would compare as text (true!) instead of numbers (false) unless explicitly cast with [double] as done here.

08 Script Execution Flow

StepWhat Happens
1. Today's ScanEvery fixed drive on every server is measured fresh, exactly like a Project 01-style check, but for all drives instead of just C:.
2. Append to HistoryToday's readings are added to the end of the history file — everything ever recorded by every prior run remains intact.
3. Read Full HistoryThe complete history, including today's brand-new rows, is read back into memory as objects.
4. Per-Drive GroupingHistory is split back into one bucket per unique server+drive combination before any trend math happens.
5. Forecast MathOldest vs. newest reading per drive produces a daily rate, then a days-until-full estimate, only when the drive is actually shrinking.
6. ReportingSame log/CSV pattern as every prior project, now carrying a forecast instead of just a snapshot.

09 Windows Internals — In Simple English

DriveType Values

Win32_LogicalDisk's DriveType property is a simple code: 2 = Removable, 3 = Fixed (local hard disks), 4 = Network, 5 = CD-ROM — filtering on 3 is the standard way to target "real" local storage only.

Why Transaction Log Drives Fill Predictably

Database transaction logs record every change before it's committed; under heavy write activity or delayed log backups, they grow at a fairly steady, trackable rate — exactly the kind of pattern a simple linear forecast is well-suited to catch.

Why CSV Round-Trips Lose Type Information

CSV is a plain-text format — every value, whether originally a number, date, or boolean, becomes text the moment it's written, which is exactly why re-imported values need explicit casting before doing math or date comparisons on them.

Simulate Multiple Days of History

Since you can't wait three real weeks to test a trend, manually simulate history by editing disk-history.csv directly (or running the script, then hand-editing the Date column of a copied row to be several days in the past with a slightly higher FreeSpaceGB value) before re-running the forecast logic.

  1. Run the script once today — this creates disk-history.csv with one row per drive
  2. Open disk-history.csv, duplicate one drive's row, and change its Date to 10 days ago and its FreeSpaceGB to a noticeably higher number (simulating "10 days ago, this drive had more free space")
  3. Re-run the script (or just the forecast section against Import-Csv) and confirm it now calculates a real ForecastDaysLeft instead of "INSUFFICIENT HISTORY"
This manual history simulation is a legitimate and common way to test trend/forecast logic without waiting for real time to pass — just remember to remove your simulated test rows before relying on the file for real capacity planning.

12 Production Best Practices

Never overwrite historical data — always append, and treat the history file itself as something worth backing up.
Always cast CSV values back to their real type (int, double, datetime) before doing math or comparisons — every round-trip through CSV turns everything into text.
Start with a simple trend calculation before reaching for statistical sophistication — a defensible, explainable oldest-vs-newest comparison often catches the real-world problem just fine.
Handle "not enough history yet" as its own explicit state — never let a forecast silently produce a misleading number from a single data point.

13 Interview Preparation

Q: Why use a simple oldest-vs-newest trend instead of full linear regression across every data point?
A simple trend is easy to explain and verify, requires no extra statistical libraries, and is sufficient to catch a genuinely declining drive — regression adds real value once you need to smooth out noisy day-to-day fluctuations, which can be a deliberate future iteration rather than a Phase 1 requirement.
Q: What happens if a drive only has one day of history?
The forecast function explicitly detects fewer than one full day between the oldest and newest reading and returns "INSUFFICIENT HISTORY" rather than attempting — and risking — a misleading calculation from a single data point.
Q: Why does everything from Import-Csv need to be cast back to its real type?
CSV is a text format — every value, including numbers and dates, is written and read back as plain strings, so any math or chronological sorting requires explicitly casting those strings back to numeric or DateTime types first.
Q: How does this project directly address the story's Sunday outage?
A transaction log drive filling steadily over two weeks would have shown a clear, trackable negative trend days in advance — the forecast would have flagged it as WARNING or CRITICAL with enough lead time to schedule a fix during business hours instead of firefighting overnight.
