Project 04 — IIS Health Check

The server can be "healthy" and the banking website can still be down

Projects 01–03 checked the server. Today we go one layer up the stack: is IIS itself running, is the website started, is the application pool alive, and — the test that actually matters to a customer — does the login page respond with a real HTTP 200?

01 The Production Story

A new kind of incident this week — one your Project 01 health check completely missed.
Wednesday, 8:52 AM — Customer Complaints Rising

Your phone buzzes. It's Priya. "Online banking login page is throwing a generic error for customers right now. I just checked your Project 01 health check report from this morning — every server shows HEALTHY. CPU fine, memory fine, disk fine. So what's actually broken?"

You RDP into SRV-APP01 and find it: the Windows Server itself is perfectly healthy, but the IIS Application Pool hosting the Online Banking site had crashed and stopped an hour ago. The server's OS didn't care — CPU and memory looked completely normal — but the actual banking website behind IIS was serving nothing.

"This is exactly the gap," Priya says. "We check the house is standing, but we never check if the front door actually opens. I need a health check specifically for IIS — is the service running, is the website started, is the application pool alive, and — most important — if I actually browse to the login page right now, do I get a real response back, not just 'the server says it's fine'?"

"Build this as a companion to your Project 01 script. Same server list, same reporting style, but this time we're checking the web layer, not just the OS layer."

This is a recurring theme in real production support: a healthy server and a healthy application are two different things, and most serious customer-facing outages live in that gap.

02 Business Case

Business Requirement

Confirm that customer-facing banking websites are actually serving pages, not just that the underlying servers are up.

Customer Requirement

Operations wants IIS-level visibility (sites, app pools, worker processes) alongside the existing OS-level health check.

Banking Scenario

Online banking, mobile banking APIs, and the payment gateway all run as IIS-hosted applications on the app server tier.

Current Manual Process

Nobody checks IIS proactively — engineers only look at it reactively, after a customer complaint or ticket arrives.

Problems With Current Process

Server-level health checks give false confidence; an application-level outage can hide completely behind a "healthy" server.

Business Challenges

Detecting app-layer failures requires checking IIS internals AND actually testing the end-user experience via HTTP.

Risk Analysis

A stopped application pool on a customer-facing site directly blocks transactions — the most damaging kind of outage.

Business Impact

Faster detection of app-pool or site failures shrinks the gap between "it broke" and "someone is fixing it."

Why Automation Is Required

IIS state and real HTTP response checks need to run continuously across the fleet — not only when a customer complains.

Solution Design

A PowerShell script using the IIS Administration module plus a real HTTP request test against each site's actual URL.

Project Scope

Phase 1 covers IIS service state, website state, app pool state, and one live HTTP check per site.

Expected Benefits

Application-layer outages get caught by monitoring instead of by customer complaints landing in Priya's inbox.

03 New Concepts (Building on Projects 01–03)

You already know remoting, functions, try/catch, and parallel execution. Here's what's specific to IIS today.
The IIS: PSDrive & WebAdministration Module

What it is: Once the WebAdministration (or IISAdministration) module is imported, PowerShell exposes IIS configuration as a navigable drive, exactly like C:\ — you can literally run Get-ChildItem IIS:\Sites the same way you'd list files in a folder.

Why it exists: IIS configuration used to only be reachable through the GUI (IIS Manager) or the low-level appcmd.exe tool. The PSDrive gives PowerShell a clean, object-based way to read and change it instead.

Get-Website & Get-WebAppPoolState

Get-Website: Returns every website configured in IIS on that server, with a .State property (Started / Stopped) — exactly what we need to confirm the Online Banking site is actually running.

Get-WebAppPoolState: Returns the current state of a specific Application Pool by name. An app pool can crash and stop independently of the website configuration still looking "fine" on paper — this is the check that would have caught this week's incident.

Invoke-WebRequest — Testing the Real Customer Experience

What it is: Sends an actual HTTP request to a URL, just like a web browser would, and returns the response, including its StatusCode (e.g. 200, 404, 500) and how long it took.

Why it's the most important check today: Everything else (service running, site started, app pool alive) is still an internal, "should be working" signal. Invoking the real login page URL is the only check that proves an actual customer would get a real response right now.

Production nuance: Enterprise monitoring tools do this same thing from multiple geographic locations, simulating a real user, precisely because internal health looking fine doesn't guarantee the outside world can reach it.

Measure-Command — Response Time

What it is: Wraps any block of code and returns exactly how long it took to run, down to milliseconds — we wrap our Invoke-WebRequest call in it to capture response time, since a page that's slow but technically "up" is still a real problem for customers.

Switch Statements

What it is: A cleaner alternative to a long chain of if / elseif / elseif when you're comparing one value against several possibilities — e.g. turning an HTTP status code into a plain-English health verdict.

Why it's used today: Status codes have many possible values (200, 301, 404, 500, 503...) — a switch statement reads far more clearly than a wall of elseif checks for each one.

Notice the layering across projects: Project 01 checked the OS. Today we check the application platform (IIS) AND the actual customer-facing behavior (HTTP response). Real production monitoring is always built in these layers — infrastructure, platform, application, and end-user experience.

04 Architecture

Each of the four checks can fail independently — that independence is exactly why last Wednesday's incident slipped through a server-only health check. Today's script checks all four layers explicitly, every time.

06 The Script — Test-IISHealth.ps1

Scripts\Test-IISHealth.ps1 
<#
.SYNOPSIS
    IIS Application Health Check - ABC Bank Production Support
.DESCRIPTION
    Checks the IIS service, website state, application pool state, and
    performs a real HTTP request against each configured site's test URL.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Sites = Get-Content -Path "C:\IISHealthCheck\Config\sites.json" -Raw | ConvertFrom-Json   # Load site definitions

$TimeTag    = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile    = "C:\IISHealthCheck\Logs\IISHealth_$TimeTag.log"
$ReportCSV  = "C:\IISHealthCheck\Reports\IISHealth_$TimeTag.csv"
$ReportHTML = "C:\IISHealthCheck\Reports\IISHealth_$TimeTag.html"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: STATUS CODE TO VERDICT (SWITCH STATEMENT)
# ============================================================

function Get-HttpVerdict {
    param([int]$StatusCode)
    switch ($StatusCode) {                       # Cleaner than a long if/elseif chain for many possible codes
        200     { "OK" }
        301     { "REDIRECT - CHECK CONFIG" }
        404     { "NOT FOUND - PAGE MISSING" }
        500     { "SERVER ERROR" }
        503     { "SERVICE UNAVAILABLE" }
        default { "UNEXPECTED STATUS: $StatusCode" }   # Catches any status code not explicitly listed above
    }
}

# ============================================================
# SECTION 3: MAIN IIS HEALTH CHECK FUNCTION
# ============================================================

function Test-SiteHealth {
    param(
        [string]$ServerName,
        [string]$SiteName,
        [string]$AppPoolName,
        [string]$TestUrl
    )

    $Result = [PSCustomObject]@{
        ServerName      = $ServerName
        SiteName        = $SiteName
        IISServiceState = "UNKNOWN"
        SiteState       = "UNKNOWN"
        AppPoolState    = "UNKNOWN"
        HttpStatusCode  = $null
        HttpVerdict     = "UNKNOWN"
        ResponseTimeMs  = $null
        OverallStatus   = "UNKNOWN"
        CheckedAt       = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        # ---- CHECK 1: IIS SERVICE (W3SVC) ----
        $W3SVC = Get-Service -ComputerName $ServerName -Name "W3SVC" -ErrorAction Stop  # The core IIS Windows service
        $Result.IISServiceState = $W3SVC.Status

        if ($W3SVC.Status -ne "Running") {
            $Result.OverallStatus = "CRITICAL - IIS SERVICE DOWN"
            Write-Log "$ServerName : W3SVC is $($W3SVC.Status)" "ERROR"
            return $Result                              # No point checking sites if IIS itself isn't running
        }

        # ---- CHECK 2 & 3: SITE STATE AND APP POOL STATE (remote, via Invoke-Command) ----
        $IISState = Invoke-Command -ComputerName $ServerName -ArgumentList $SiteName, $AppPoolName -ScriptBlock {
            param($Site, $Pool)                          # Values passed in from -ArgumentList, since remote sessions don't see local variables
            Import-Module WebAdministration -ErrorAction Stop         # Loads IIS cmdlets INSIDE the remote session
            [PSCustomObject]@{
                SiteState    = (Get-Website -Name $Site).State                # "Started" or "Stopped"
                AppPoolState = (Get-WebAppPoolState -Name $Pool).Value        # "Started" or "Stopped"
            }
        }
        $Result.SiteState    = $IISState.SiteState
        $Result.AppPoolState = $IISState.AppPoolState

        # ---- CHECK 4: REAL HTTP REQUEST ----
        $Timer = Measure-Command {                                    # Times how long the web request takes
            $Script:WebResponse = Invoke-WebRequest -Uri $TestUrl -UseBasicParsing -TimeoutSec 10 -ErrorAction Stop
        }
        $Result.HttpStatusCode = $WebResponse.StatusCode
        $Result.HttpVerdict    = Get-HttpVerdict -StatusCode $WebResponse.StatusCode
        $Result.ResponseTimeMs = [math]::Round($Timer.TotalMilliseconds, 0)

        # ---- OVERALL VERDICT ----
        if ($Result.SiteState -ne "Started" -or $Result.AppPoolState -ne "Started" -or $Result.HttpStatusCode -ne 200) {
            $Result.OverallStatus = "CRITICAL"              # Any layer failing = whole check fails
        }
        elseif ($Result.ResponseTimeMs -gt 2000) {
            $Result.OverallStatus = "WARNING - SLOW RESPONSE"    # Technically up, but too slow for customers
        }
        else {
            $Result.OverallStatus = "HEALTHY"
        }

        Write-Log "$ServerName/$SiteName : $($Result.OverallStatus)" "INFO"
    }
    catch {
        Write-Log "Error checking $ServerName/$SiteName : $($_.Exception.Message)" "ERROR"
        $Result.OverallStatus = "CRITICAL - CHECK FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 4: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting IIS Health Check for $($Sites.Count) site(s) =====" "INFO"

$AllResults = foreach ($Site in $Sites) {
    Test-SiteHealth -ServerName $Site.ServerName -SiteName $Site.SiteName `
                     -AppPoolName $Site.AppPoolName -TestUrl $Site.TestUrl
}

$AllResults | Sort-Object OverallStatus | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$AllResults | ConvertTo-Html -Title "ABC Bank IIS Application Health Report" |
    Out-File -FilePath $ReportHTML

Write-Log "===== IIS Health Check Completed. Report: $ReportHTML =====" "INFO"

07 Line-by-Line Explanation

switch ($StatusCode) { 200 { "OK" } 404 { ... } default { ... } }
Each numbered block is a possible match; PowerShell runs the block matching the value of $StatusCode and returns its output. default catches anything not explicitly listed — critical here, since HTTP has dozens of possible status codes we can't all enumerate by hand.
Invoke-Command -ComputerName $ServerName -ArgumentList $SiteName, $AppPoolName -ScriptBlock { param($Site, $Pool) ... }
Remote script blocks run in a separate session that can't see your local script's variables directly. -ArgumentList explicitly passes values in, and param() inside the script block receives them — this is the correct, explicit way to get local data into a remote call (an alternative to the $using: scope modifier you saw briefly in Project 03).
$Timer = Measure-Command { $Script:WebResponse = Invoke-WebRequest ... }
Measure-Command swallows the output of whatever's inside its braces and returns only timing information — so we deliberately capture the actual web response into $Script:WebResponse (a script-scoped variable) to use afterward, since we need both the timing and the response.
Invoke-WebRequest -Uri $TestUrl -UseBasicParsing -TimeoutSec 10
-UseBasicParsing avoids a dependency on Internet Explorer's engine on older systems; -TimeoutSec 10 ensures one unresponsive site can't hang the whole health check run.
Common mistake: not wrapping Invoke-WebRequest in try/catch. A site returning a 500 error actually throws a terminating error in PowerShell by default rather than just returning the status code — without a catch block, one broken site would stop the whole script.

08 Script Execution Flow

StepWhat Happens
1. IIS Service GateIf W3SVC itself isn't running, the script short-circuits immediately — checking individual sites on a dead IIS instance is pointless.
2. Remote IIS QueryWebAdministration is imported inside the remote session (not on the automation host) since it needs to read that specific server's IIS configuration.
3. Real HTTP RequestThis call goes over the actual network path a customer's browser would use — DNS, TLS handshake, and all — proving genuine end-to-end reachability.
4. Verdict AssemblyAll three layers (service, site/pool, HTTP) must pass for HEALTHY; any single failure marks the whole result CRITICAL.
5. ReportingSame CSV/HTML/log pattern established since Project 01 — consistency across projects means anyone on the team can read any report the same way.

09 Windows Internals — In Simple English

How IIS Is Structured

IIS runs one or more Sites, each bound to a hostname/port. Each site is served by an Application Pool — an isolated worker process (w3wp.exe) that actually executes the application code.

Why App Pools Crash Independently

Application Pools are deliberately isolated from each other so one crashing application doesn't take down every other site on the same server — but that isolation also means one pool can silently die while everything else, including the IIS service itself, looks fine.

How HTTP Status Codes Work

The web server includes a 3-digit status code in every response: 2xx means success, 3xx means redirect, 4xx means the client asked for something wrong (like a missing page), and 5xx means the server itself failed to handle the request.

12 Production Best Practices

Always test the real customer-facing URL, not just internal service/site state — internal state can look fine while the real experience is broken.
Set a timeout on every HTTP check — an unresponsive site should fail fast, not hang your entire monitoring run.
Treat "up but slow" as its own category, separate from fully down — customers experience both as a problem, but they need different responses from Ops.
Keep site/app-pool/URL mappings in an external config file — new applications get added to the fleet regularly, and Ops shouldn't need to edit script code to onboard one.

13 Interview Preparation

Q: Why check the app pool state separately from the website state?
A website can be configured and "Started" in IIS while its backing application pool has independently crashed — the site accepts the request but has no worker process to actually handle it, so both need to be checked explicitly.
Q: Why is the HTTP check considered the most important of the four checks?
It's the only check that verifies the complete path a real customer would use — DNS, network routing, TLS, IIS, the application, and the app pool all have to work together for that single request to succeed.
Q: How would you extend this to catch a "slow but not down" incident before customers complain?
Track response time trends over multiple runs (not just a single threshold), so a site that's gradually getting slower over several health checks gets flagged before it crosses into full customer-visible failure.
Q: What's a real production incident this kind of check would have caught?
Exactly this project's story — a crashed application pool on a customer-facing banking site, while the underlying Windows Server reported completely healthy in server-level monitoring.

14 Key Learnings & Assignment

Key Learnings

  • Server health and application health are two separate things that must both be monitored
  • IIS exposes Sites and Application Pools as independently-stateful objects that can fail separately
  • Invoke-WebRequest is the only check that proves real end-to-end customer reachability
  • Switch statements are cleaner than long if/elseif chains when matching one value against many possibilities

Resume Point
