01 The Production Story

Three weeks of manual evidence-gathering for an audit that automation had already been proving, silently, every single day.
Three Weeks Before the Annual Audit

The annual compliance audit is coming, and per tradition, an engineer spends the better part of three weeks manually gathering evidence: screenshots of the local admin group on a sample of servers, exported firewall rule lists, a written summary of the patch compliance process, manually pulled certificate expiry dates. Every single one of these is something this academy has already been automatically checking and reporting on, in some cases for over a year.

Worse, the manual evidence has a credibility problem an auditor immediately raises: a screenshot taken today, three weeks before the audit, doesn't actually prove ongoing compliance throughout the audit period — and there's no way to prove the screenshot itself hasn't been touched up. The auditor specifically asks for "evidence that's provably unaltered and tied to specific control requirements, not just point-in-time screenshots."

"We've been generating exactly the evidence they want, automatically, for months," Priya says. "We just never packaged it as evidence. I want a script that maps each compliance control we're actually audited against to the specific automation project that already proves it, pulls the real report, computes a cryptographic hash of every file so nobody can credibly claim it was altered afterward, and packages the whole thing into one auditor-ready archive with a clear manifest. Turn three weeks of manual screenshot-gathering into one script run."

This project's real insight: you've been generating audit evidence the entire time without realizing it. The work here is packaging and mapping, not inventing new proof.

03 New Concepts (Building on Projects 01–23)

You already know config-driven report consolidation from Project 23. Here's what's new for formal audit evidence.
Mapping Technical Checks to Compliance Controls

What it is: A config file explicitly linking a formal control identifier (like "AC-2: Account Management" from a framework such as NIST 800-53, or an equivalent internal control ID) to the specific automation project whose report serves as evidence for it.

Why it's used today: Auditors think in terms of controls, not scripts — this mapping is the translation layer between "here's a PowerShell report" and "here's proof control AC-2 is operating effectively," which is exactly the language an audit actually requires.

Get-FileHash — Cryptographic Evidence Integrity

What it is: Computes a cryptographic hash (SHA-256 by default) of a file's exact contents — any change to the file at all, even a single byte, produces a completely different hash value.

Why it's used today: Recording each evidence file's hash at collection time creates a mathematically verifiable proof that the file hasn't been altered since — directly answering the auditor's specific concern about screenshot credibility, in a way no manual process ever could.

Compress-Archive — Packaging Evidence for Delivery

What it is: A built-in cmdlet that creates a standard ZIP archive from a set of files — no external tools required.

Why it's used today: A single, self-contained ZIP file — containing every piece of evidence plus the manifest describing it — is a natural, portable format to hand directly to an auditor or upload to a compliance management system.

Generating a Manifest — The Evidence Package's Own Table of Contents

What it is: A structured file (JSON, in this project) listing every piece of evidence included in the package: which control it maps to, its source file, its computed hash, and when it was collected — essentially a formal index an auditor can use to navigate and verify the package.

Why it's used today: Without a manifest, an auditor receiving twenty files has to guess what each one proves — the manifest is what makes the package genuinely self-explaining and audit-ready, not just a folder of exports.

This project's real lesson connects directly to Project 23's: once you have a mature automation suite, some of the highest-value new work is reframing and packaging what already exists for a different audience — here, auditors instead of Ops engineers — rather than building new checks.

06 The Script — New-ComplianceEvidencePackage.ps1

Scripts\New-ComplianceEvidencePackage.ps1 
<#
.SYNOPSIS
    Compliance Audit Evidence Automation - ABC Bank Production Support
.DESCRIPTION
    Maps compliance controls to existing automation reports, collects
    the latest evidence for each, computes integrity hashes, and
    packages everything into one auditor-ready, manifested archive.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Mapping     = Get-Content -Path "C:\ComplianceAudit\Config\control-mapping.json" -Raw | ConvertFrom-Json
$TimeTag     = Get-Date -Format 'yyyyMMdd'
$StagingFolder = "C:\ComplianceAudit\Staging\$TimeTag"
$OutputZip   = "C:\ComplianceAudit\Output\EvidencePackage_$TimeTag.zip"
$LogFile     = "C:\ComplianceAudit\Logs\ComplianceAudit_$TimeTag.log"

$null = New-Item -Path $StagingFolder -ItemType Directory -Force   # Clean staging area for this run's evidence

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Entry = "[$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: COLLECT, HASH, AND STAGE EVIDENCE PER CONTROL
# ============================================================

$ManifestEntries = foreach ($Control in $Mapping) {

    $LatestReport = Get-ChildItem -Path $Control.ReportsFolder -Filter "*.csv" -ErrorAction SilentlyContinue |
        Sort-Object LastWriteTime -Descending | Select-Object -First 1   # Same latest-file pattern as Project 23

    if (-not $LatestReport) {
        Write-Log "$($Control.ControlID) ($($Control.ControlName)) : NO EVIDENCE FOUND in $($Control.ReportsFolder)" "ERROR"
        [PSCustomObject]@{
            ControlID = $Control.ControlID; ControlName = $Control.ControlName
            EvidenceFile = "MISSING"; SHA256Hash = "N/A"; EvidenceDate = "N/A"
        }
        continue                                     # Move to the next control — a gap here is itself an important finding, not a script error
    }

    $StagedFileName = "$($Control.ControlID)_$($LatestReport.Name)"          # Prefix with control ID so the staged filename is self-describing
    $StagedPath = Join-Path $StagingFolder $StagedFileName
    Copy-Item -Path $LatestReport.FullName -Destination $StagedPath            # Copy evidence into the staging area for this run

    $Hash = (Get-FileHash -Path $StagedPath -Algorithm SHA256).Hash        # Compute integrity hash of the STAGED copy

    Write-Log "$($Control.ControlID) ($($Control.ControlName)) : evidence collected from $($LatestReport.Name), hash computed" "INFO"

    [PSCustomObject]@{
        ControlID    = $Control.ControlID
        ControlName  = $Control.ControlName
        EvidenceFile = $StagedFileName
        SHA256Hash   = $Hash
        EvidenceDate = $LatestReport.LastWriteTime.ToString("yyyy-MM-dd HH:mm:ss")
    }
}

# ============================================================
# SECTION 3: WRITE THE MANIFEST
# ============================================================

$Manifest = [PSCustomObject]@{
    PackageGeneratedAt = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    GeneratedBy         = $env:USERNAME
    TotalControls       = $Mapping.Count
    ControlsWithEvidence= ($ManifestEntries | Where-Object { $_.EvidenceFile -ne "MISSING" }).Count
    Entries             = $ManifestEntries
}
$Manifest | ConvertTo-Json -Depth 4 | Out-File -FilePath (Join-Path $StagingFolder "manifest.json") -Encoding UTF8

# ============================================================
# SECTION 4: PACKAGE INTO ONE ARCHIVE
# ============================================================

Compress-Archive -Path "$StagingFolder\*" -DestinationPath $OutputZip -Force   # Everything staged — evidence files AND manifest — into one ZIP

$MissingCount = ($ManifestEntries | Where-Object { $_.EvidenceFile -eq "MISSING" }).Count
if ($MissingCount -gt 0) {
    Write-Log "$MissingCount control(s) have NO current evidence — review before submitting to audit" "WARNING"
}

Write-Log "===== Evidence Package Complete: $OutputZip ($($Manifest.ControlsWithEvidence)/$($Manifest.TotalControls) controls with evidence) =====" "INFO"

07 Line-by-Line Explanation

$Hash = (Get-FileHash -Path $StagedPath -Algorithm SHA256).Hash
Computing the hash on the staged COPY, immediately after it's copied and before packaging, records exactly what state that file was in at evidence-collection time — anyone can later re-run Get-FileHash against the same file inside the delivered ZIP and confirm the hash matches, proving it hasn't been altered since.
if (-not $LatestReport) { ... continue }
A missing evidence source is deliberately treated as its own manifest entry ("MISSING"), not silently skipped — an auditor needs to see explicitly which controls currently lack automated evidence, since that gap is itself a meaningful compliance finding worth surfacing, not hiding.
$StagedFileName = "$($Control.ControlID)_$($LatestReport.Name)"
Prefixing the staged filename with the control ID makes every file inside the final ZIP self-describing at a glance — an auditor opening the archive doesn't need to cross-reference the manifest for every single file just to know what it's looking at.
Compress-Archive -Path "$StagingFolder\*" -DestinationPath $OutputZip -Force
Compressing the entire staging folder's contents — both the copied evidence files and the manifest.json generated moments earlier — into one ZIP produces a single, complete, self-contained deliverable ready to hand directly to an auditor.
Common mistake: computing the file hash BEFORE copying the file into staging, rather than after. Hashing the original source file doesn't prove anything about the copy that actually ships in the evidence package — always hash the exact file that will be delivered, not a different copy of it.

08 Script Execution Flow

StepWhat Happens
1. Staging SetupA fresh, dated staging folder is created for this run — evidence never accumulates across runs, keeping each package a clean, current snapshot.
2. Per-Control CollectionEach control's latest report is located, copied into staging with a self-describing filename, and hashed — a missing source is recorded as its own explicit finding.
3. Manifest GenerationOne JSON file summarizes every control, its evidence file, hash, and collection date — this becomes the package's own table of contents.
4. Archive PackagingEverything in staging, evidence and manifest together, compresses into one final ZIP file ready for delivery.
5. Coverage ReportingThe log explicitly calls out how many controls have current evidence versus how many don't — a clear, honest coverage summary, not just "done."

09 Windows Internals — In Simple English

How Cryptographic Hashing Proves Integrity

SHA-256 produces a fixed-length fingerprint from a file's exact contents — changing even a single bit anywhere in the file produces a completely different hash, with no practical way to alter a file while preserving its original hash, which is exactly what makes a hash a credible integrity proof.

Why Auditors Specifically Value Hash-Verified Evidence

A hash recorded at collection time, alongside the evidence itself, lets anyone independently verify — at any later point — that the specific file they're looking at is exactly what was originally collected, addressing tampering concerns that a plain screenshot or export simply cannot answer.

Compliance Frameworks and Control IDs

Frameworks like NIST 800-53 or PCI-DSS define specific, numbered controls (like AC-2 for account management) that map to concrete technical and procedural requirements — this project's control-mapping.json is a simplified example of the kind of control-to-evidence mapping real compliance programs maintain formally.

12 Production Best Practices

Always hash the exact file that ships in the final package, computed after any copy step — never hash a different copy than what's actually delivered.
Treat a control with no current evidence as its own explicit, visible finding — never silently omit it from the manifest.
Keep control mappings maintained as a real, owned document jointly with Compliance — like the security baselines in Projects 11 and 20, this is a living control artifact, not a one-time config file.
Generate a fresh, dated evidence package for each audit cycle rather than reusing or appending to an old one — evidence should always reflect current state.

13 Interview Preparation

Q: Why is a SHA-256 hash more credible evidence than a screenshot?
A hash is mathematically tied to the exact contents of a specific file — any alteration, however small, produces a completely different hash, giving anyone a way to independently verify the evidence hasn't changed since collection; a screenshot offers no comparable, independently verifiable integrity proof.
Q: Why record a control as "MISSING" evidence rather than simply excluding it from the package?
A control with no current automated evidence is itself an important, visible gap that Compliance needs to know about and address — silently omitting it would hide exactly the kind of finding an audit exists to catch.
Q: How does this project relate to Project 23's dashboard?
Both consolidate existing report outputs rather than introducing new checks, but for different audiences and purposes — Project 23 serves Ops with a live operational view, while this project serves Compliance/Audit with a formal, hash-verified, point-in-time evidence package mapped to specific controls.
Q: What's a genuine limitation of this automated evidence approach?
It's only as strong as the underlying checks and the control mapping itself — if a mapped automation project has a bug, or the control mapping is stale or incorrect, the "evidence" would be confidently wrong rather than absent, which argues for periodically reviewing the mapping itself, not just running the script.

Key Learnings

  • An automation suite generates real audit evidence continuously, whether or not anyone has packaged it as such yet

  • A manifest is what makes a folder of files into a genuinely navigable, self-explaining evidence package for someone unfamiliar with how it was produced
