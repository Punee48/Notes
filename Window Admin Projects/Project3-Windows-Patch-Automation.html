01 The Production Story

Two weeks after Project 02 went live. Your compliance report is now catching gaps automatically — but catching them isn't fixing them.
Tuesday, 10:00 AM — Patch Tuesday +3 days

Your patch compliance report from Project 02 lands in Priya's inbox every morning now. This morning it shows 40 servers still Non-Compliant, three days after this month's patches were released.

"Great, now we know we have a problem instead of finding out from an auditor," Priya says, "but the Patch Management team is still installing these by hand, server by server, through Windows Update. At 40 servers a cycle, that's most of someone's week — and every server they touch manually needs a reboot scheduled around it too."

"Here's the next piece: I want a script that takes our list of non-compliant servers — the exact ones your Project 02 report already found — and actually installs the missing patches. It needs to run against many servers at once, not one at a time, because we genuinely don't have days to spare. And it has to be safe: no server should get patched by accident if someone runs this script without thinking. I want a dry-run mode, a real confirmation step, and clear handling of the reboot, because half our incidents around patching come from a server that needed a reboot and nobody realized until the next health check flagged it."

"Once it's solid, I also want it scheduled to just... happen. Every patch cycle, automatically, without one of us kicking it off by hand."

This project touches production systems more directly than the read-only checks in Projects 01–02. Every new concept here exists specifically to make that safe: WhatIf/Confirm, modules from a trusted source, parallel throttling, and explicit reboot handling.

02 Business Case

Business Requirement

Close patch compliance gaps quickly after Patch Tuesday, within the bank's 72-hour SLA, without manual server-by-server work.

Customer Requirement

Patch Management wants one controlled run that installs missing patches across many servers and reports exactly what happened.

Banking Scenario

Every day a known vulnerability stays unpatched is a day it can be exploited — regulators expect the 72-hour window to be a hard deadline, not a guideline.

Current Manual Process

An engineer opens Windows Update or Server Manager on each non-compliant server and installs patches one at a time, manually tracking reboots.

Problems With Current Process

Slow at 40+ servers, inconsistent reboot handling, and no single record of exactly what was installed and when.

Business Challenges

Patching too aggressively without controls risks an outage; patching too slowly risks a compliance breach — both are real risks to manage.

Risk Analysis

An uncontrolled mass-patch run without dry-run/confirmation safeguards could reboot production servers during business hours by mistake.

Business Impact

Faster, safer patch closure reduces both security exposure and the audit findings that come from missed SLAs.

Why Automation Is Required

Only automation can install patches across dozens of servers in parallel within a tight compliance window.

Solution Design

A PowerShell script using the PSWindowsUpdate module, run in parallel with a throttle limit, with WhatIf/Confirm safety and reboot tracking.

Project Scope

Phase 1 covers installing already-identified missing patches from Project 02's output and reporting reboot status — not full patch orchestration.

Expected Benefits

Non-compliant servers close out in a single controlled run instead of a week of manual work, with a clear audit trail.

03 New Concepts (Building on Projects 01–02)

You already know remoting, config files, comparing lists, and logging. Here's what's new — all of it exists to make touching production safe.
Modules — Install-Module & Import-Module

What it is: A module is a packaged set of extra cmdlets that don't ship with Windows by default. Install-Module downloads one from the PowerShell Gallery (an online repository); Import-Module loads an already-installed module into your current session.

Why it's used today: Installing actual Windows Updates from PowerShell needs the community PSWindowsUpdate module — there's no built-in cmdlet for it the way Get-HotFix covers reading update history.

Best practice: In a bank, modules aren't installed ad-hoc from the internet on production servers. They go through security review, get hosted on an internal, approved repository, and are deployed the same controlled way as any other software. Common mistake: running Install-Module directly against production without going through that approval process.

WhatIf & Confirm — Safety Switches

What it is: Cmdlets that change system state (installing updates, restarting a computer) can support -WhatIf, which shows you exactly what would happen without actually doing it, and -Confirm, which pauses and asks "Are you sure?" before each change.

Why it's used today: Priya explicitly asked for a dry-run mode. Building our own function with [CmdletBinding(SupportsShouldProcess)] gives us that for free — anyone can run -WhatIf first, see the plan, and only then run it for real.

Production use case: This is the single most important habit for any script that changes production systems — always give the person running it a way to preview before committing.

Background Jobs & Parallel Execution

What it is: Instead of patching 40 servers one after another, PowerShell can run the same operation against several servers at the same time. Invoke-Command accepts an array of computer names directly and runs against all of them concurrently, with a -ThrottleLimit controlling how many run at once.

Why it matters: Patching one server at a time serially could easily blow past the compliance window; running 10 at a time in parallel finishes the same work far faster.

Best practice: Never set the throttle limit to "unlimited" against production — a sane limit (e.g. 10) protects your network and the automation host from being overwhelmed.

Restart-Computer with -Wait

What it is: Triggers a reboot on a remote computer. Adding -Wait makes PowerShell pause and monitor the server until it comes back online and is responsive again, instead of firing the reboot and immediately moving on blind.

Why it's used today: Priya specifically called out that unhandled reboots are a recurring incident cause — waiting and confirming the server actually returns closes that gap.

Splatting — Cleaner Parameter Passing

What it is: Instead of writing a cmdlet call with many inline parameters on one long line, you put the parameters into a hash table and pass the whole table in with @ instead of $, e.g. Invoke-Command @RemoteParams.

Why it's used today: Our remote calls now have several parameters (ComputerName, ScriptBlock, ThrottleLimit, credentials). Splatting keeps the call readable instead of one unreadable 200-character line.

Register-ScheduledTask (Deploying the Automation)

What it is: Creates a Windows Scheduled Task directly from PowerShell, defining the trigger (when), the action (what to run), and the account it runs as — instead of clicking through Task Scheduler's UI.

Why it's used today: Priya wants this to "just happen" every patch cycle. Scripting the Scheduled Task creation means it's repeatable and version-controlled, not a manual UI setup someone has to remember to redo.

Every new concept this project introduces is a safety or scale mechanism. That's deliberate — the moment a script starts changing production, "does it work" matters less than "can it be trusted not to cause an outage."

06 The Script — Install-MissingPatches.ps1

Same disciplined shape as Projects 01–02, now with WhatIf/Confirm safety, parallel remoting, and reboot handling.
Scripts\Install-MissingPatches.ps1 
<#
.SYNOPSIS
    Missing Patch Installation - ABC Bank Production Support
.DESCRIPTION
    Installs missing Windows Updates on a list of non-compliant servers
    using the PSWindowsUpdate module, in parallel with a safe throttle
    limit, and handles reboots explicitly. Supports -WhatIf for a safe
    dry run before any real change is made.
#>

[CmdletBinding(SupportsShouldProcess)]                        # Enables -WhatIf and -Confirm on THIS script
param(
    [int]$ThrottleLimit = 10                              # Max number of servers patched at the same time
)

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers    = Get-Content -Path "C:\PatchAutomation\Config\non-compliant.txt"   # Servers flagged by Project 02
$TimeTag    = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile    = "C:\PatchAutomation\Logs\PatchInstall_$TimeTag.log"
$ReportCSV  = "C:\PatchAutomation\Reports\PatchInstall_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: MODULE CHECK
# ============================================================

if (-not (Get-Module -ListAvailable -Name PSWindowsUpdate)) {              # Check if the module is already installed
    Write-Log "PSWindowsUpdate module not found. Install from the approved internal repository first." "ERROR"
    throw "Missing required module: PSWindowsUpdate"                       # Stop the script — don't proceed blind
}
Import-Module PSWindowsUpdate                                             # Load the module's cmdlets into this session

# ============================================================
# SECTION 3: PER-SERVER PATCH FUNCTION
# ============================================================

function Install-ServerPatches {
    param([string]$ComputerName)

    $Result = [PSCustomObject]@{
        ServerName    = $ComputerName
        Reachable     = $false
        InstallStatus = "NOT ATTEMPTED"
        RebootNeeded  = $false
        RebootResult  = "N/A"
        CheckedAt     = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    if (-not (Test-Connection -ComputerName $ComputerName -Count 2 -Quiet)) {
        Write-Log "$ComputerName is UNREACHABLE" "ERROR"
        $Result.InstallStatus = "SKIPPED - UNREACHABLE"
        return $Result
    }
    $Result.Reachable = $true

    # $PSCmdlet.ShouldProcess is what actually makes -WhatIf / -Confirm work for this custom function
    if ($PSCmdlet.ShouldProcess($ComputerName, "Install missing Windows Updates and reboot if required")) {

        try {
            # ---- INSTALL PATCHES REMOTELY (real run only — WhatIf never reaches here) ----
            $InstallOutput = Invoke-Command -ComputerName $ComputerName -ScriptBlock {
                Get-WindowsUpdate -Install -AcceptAll -IgnoreReboot -Verbose:$false   # Installs everything pending, defers reboot for us to control
            }
            $Result.InstallStatus = "INSTALLED"
            Write-Log "$ComputerName : patches installed successfully" "INFO"

            # ---- CHECK IF A REBOOT IS PENDING ----
            $PendingReboot = Invoke-Command -ComputerName $ComputerName -ScriptBlock {
                Test-Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPending"   # Registry flag Windows sets when a reboot is required
            }
            $Result.RebootNeeded = $PendingReboot

            if ($PendingReboot) {
                Write-Log "$ComputerName requires a reboot. Restarting and waiting for it to come back..." "WARNING"
                Restart-Computer -ComputerName $ComputerName -Force -Wait -For PowerShell -Timeout 600   # Reboots and blocks until PowerShell is responsive again, or 10 min timeout
                $Result.RebootResult = "REBOOTED - BACK ONLINE"
                Write-Log "$ComputerName is back online after reboot" "INFO"
            }
            else {
                $Result.RebootResult = "NOT REQUIRED"
            }
        }
        catch {
            Write-Log "Error patching $ComputerName : $($_.Exception.Message)" "ERROR"
            $Result.InstallStatus = "FAILED"
        }
    }
    else {
        $Result.InstallStatus = "WHATIF - NO CHANGE MADE"              # -WhatIf path: we only report, never touch the server
    }

    return $Result
}

# ============================================================
# SECTION 4: MAIN EXECUTION (PARALLEL, THROTTLED)
# ============================================================

Write-Log "===== Starting Patch Install for $($Servers.Count) server(s), Throttle=$ThrottleLimit =====" "INFO"

$AllResults = $Servers | ForEach-Object -Parallel {                       # PowerShell 7 parallel pipeline
    # Note: -Parallel runs in isolated runspaces, so we re-import the function via $using:
    $Server = $_
    & $using:Install-ServerPatches -ComputerName $Server
} -ThrottleLimit $ThrottleLimit                                                # Caps concurrent server patching, protects the network/host

$AllResults | Sort-Object InstallStatus | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$FailedCount = ($AllResults | Where-Object { $_.InstallStatus -eq "FAILED" }).Count
if ($FailedCount -gt 0) {
    Write-Log "$FailedCount server(s) FAILED to patch and need manual review." "WARNING"
}

Write-Log "===== Patch Install Completed. Report: $ReportCSV =====" "INFO"
Simplified for teaching: ForEach-Object -Parallel runs each server in an isolated runspace, so functions defined in the main script aren't automatically visible inside it — production code typically re-declares the function inside the parallel block itself, or dot-sources it via $using: a script file path. We show the concept here; treat the exact syntax as something to test carefully in your own lab before relying on it.
Scripts\Register-PatchTask.ps1 
# Run ONCE to schedule the patch installer for every patch cycle

$Action  = New-ScheduledTaskAction -Execute "pwsh.exe" `                              # Defines WHAT the task runs
            -Argument '-File "C:\PatchAutomation\Scripts\Install-MissingPatches.ps1" -Confirm:$false'

$Trigger = New-ScheduledTaskTrigger -Weekly -DaysOfWeek Tuesday -At 10:00PM `      # Defines WHEN — patch Tuesday nights
            -WeeksInterval 2

$Principal = New-ScheduledTaskPrincipal -UserId "ABCBANK\svc-patchautomation" `       # Runs as a dedicated service account, NOT a personal login
              -LogonType ServiceAccount -RunLevel Highest

Register-ScheduledTask -TaskName "ABCBank-PatchAutomation" `                          # Creates the actual Scheduled Task entry
    -Action $Action -Trigger $Trigger -Principal $Principal `
    -Description "Installs missing patches on non-compliant servers. Owned by Windows Ops."

07 Line-by-Line Explanation

[CmdletBinding(SupportsShouldProcess)] at the top of the script
Turns on advanced function features for the whole script, including automatic -WhatIf and -Confirm parameters — you get them for free without writing your own flag-checking logic.
if ($PSCmdlet.ShouldProcess($ComputerName, "Install missing Windows Updates and reboot if required"))
This single line is what actually implements the safety switch. If the caller ran with -WhatIf, this returns $false automatically and PowerShell prints what it would have done — the real install code inside the if block never runs.
Get-WindowsUpdate -Install -AcceptAll -IgnoreReboot
From the PSWindowsUpdate module: installs all pending updates but deliberately does NOT reboot automatically — -IgnoreReboot hands reboot control back to our script, so we can log and monitor it ourselves instead of an uncontrolled surprise restart.
Restart-Computer -ComputerName $ComputerName -Force -Wait -For PowerShell -Timeout 600
-Wait -For PowerShell blocks the script here until the remote server's PowerShell service responds again after reboot — confirming the server actually came back, not just that we sent a restart command into the void.
$Servers | ForEach-Object -Parallel { ... } -ThrottleLimit $ThrottleLimit
A PowerShell 7+ feature that runs the script block against multiple pipeline items concurrently, capped at $ThrottleLimit at a time — this is what turns a slow sequential 40-server patch run into a fast, controlled parallel one.
Common mistake: forgetting -IgnoreReboot and letting the update tool reboot the server itself — you lose the ability to log, wait, and confirm the server actually returned, which is exactly the gap that was causing incidents in the story.

08 Script Execution Flow

StepWhat Happens
1. Module CheckScript verifies PSWindowsUpdate is already installed before doing anything else — it refuses to proceed blind if the dependency is missing.
2. WhatIf Decision PointFor every server, ShouldProcess decides in real time whether to actually run the install logic or just report what would happen.
3. Parallel DispatchPowerShell 7 opens up to $ThrottleLimit concurrent runspaces, each independently working through the install/reboot logic for one server.
4. Remote InstallEach runspace's Invoke-Command opens its own WinRM session to install patches on that specific server.
5. Reboot GateThe registry-based reboot-pending check runs before deciding whether Restart-Computer -Wait is even needed.
6. AggregationOnce every parallel runspace finishes, PowerShell collects all their result objects back into $AllResults on the main thread.
7. ReportingSame CSV/log pattern as Projects 01–02, now capturing install status and reboot outcome per server.

09 Windows Internals — In Simple English

How Windows Updates Actually Install

Windows downloads the update package, verifies its digital signature, and applies it through the Component-Based Servicing (CBS) system, which may stage changes that only take effect after a reboot.

Why Some Updates Need a Reboot

Files currently in use (like core system DLLs) can't be replaced while Windows is running — CBS marks a reboot as pending so it can swap them during the next restart, before most services start.

How Scheduled Tasks Run as a Service Account

Windows Task Scheduler can run a task under a dedicated service account's identity, with its own permissions, entirely independent of any human being logged in — exactly what you want for unattended automation.

12 Production Best Practices

Always support -WhatIf on any script that changes production state — it costs one attribute and saves you from irreversible mistakes.
Never let an automated reboot go unmonitored — always wait and verify the server actually returns before marking the job successful.
Run scheduled automation under a dedicated service account with least privilege, never under a personal admin login that might be disabled when someone leaves the team.
Set a sane, explicit ThrottleLimit — protect the automation host and network instead of hoping "it'll be fine" at full concurrency.
Source modules only from an internally approved repository in regulated environments — not directly from the public PowerShell Gallery on production servers.

13 Interview Preparation

Q: How does -WhatIf actually work under the hood in a custom function?
Adding [CmdletBinding(SupportsShouldProcess)] wires up PowerShell's built-in ShouldProcess mechanism. Calling $PSCmdlet.ShouldProcess() checks whether -WhatIf or -Confirm was passed and returns false automatically for -WhatIf, skipping the actual change while still printing what would have happened.
Q: Why explicitly handle the reboot instead of letting the update tool reboot automatically?
Handling it ourselves lets us log the exact moment, wait and confirm the server actually returns, and catch a server that fails to come back — an automatic, unmonitored reboot gives us none of that visibility.
Q: A patch install failed on 3 out of 40 servers overnight. What's your next step?
Check the log and CSV report for the specific failure reason per server first — connectivity issue, disk space, a conflicting update — then manually investigate just those three rather than re-running the whole batch blind.
Q: Why run this as a Scheduled Task under a service account instead of a person's login?
A service account isn't tied to a specific employee's status, has permissions scoped exactly to what the automation needs, and keeps the audit trail clean about what ran the job versus who personally executed something.

14 Key Learnings & Assignment

  • SupportsShouldProcess + ShouldProcess is how you build real -WhatIf/-Confirm safety into your own functions

  • Register-ScheduledTask deploys automation the same repeatable, scriptable way you deploy the automation itself
