Project 20 — Registry Security Baseline Validation

The bank-wide security mandate went out eight months ago. Six servers never got the memo.

Security hardening at ABC Bank ultimately comes down to specific registry values — SMBv1 disabled, weak TLS versions turned off, specific audit policies enabled. A Group Policy push is supposed to enforce these everywhere, but GPOs can fail silently on individual servers. Today's script checks the actual registry values directly, and — carefully, safely — can fix what's wrong.

01 The Production Story

A mandate everyone believed was fully rolled out — until a penetration test proved otherwise.
Tuesday — Penetration Test Findings Land

Eight months ago, ABC Bank issued a bank-wide security mandate: disable the legacy SMBv1 protocol on every Windows server, following a well-documented history of serious vulnerabilities associated with it. A Group Policy Object was created and deployed to enforce it. Everyone considered it done.

This week's external penetration test report includes a finding nobody expected: SMBv1 is still enabled and actively responding on six servers, including two in the core banking segment. Investigation finds the GPO simply never applied cleanly to those six — a combination of a stale Group Policy cache on some, and one server that had been rebuilt after the GPO rollout and never received a fresh policy refresh before going back into production.

"A GPO push isn't the same as verified compliance," Priya says, doing that thing again where a project's whole thesis becomes obvious in one sentence. "We pushed a setting. We never actually verified, server by server, that the registry value the setting is supposed to produce is genuinely there. I want a script that checks the actual registry keys directly against our security baseline — not whether we deployed a policy, but whether the setting genuinely took effect. And where it's safe and clearly defined, I want the option to fix it too, with the same WhatIf discipline as everything risky we've built so far."

This is the same lesson as Project 15's cluster nodes and Project 19's firewall rules, at the deepest layer yet: a deployed policy is an intention, not a verified outcome. Only reading the actual resulting configuration confirms the truth.

03 New Concepts (Building on Projects 01–19)

You already know WhatIf-gated remediation from Projects 03 and 10, and baseline comparison throughout. Here's what's new for the registry specifically.
The Registry as a PSDrive — HKLM:

What it is: Just like Cert:\ and IIS:\ from earlier projects, PowerShell exposes the Windows Registry as navigable drives — HKLM: for HKEY_LOCAL_MACHINE, the hive containing system-wide security settings. Get-ItemProperty reads a specific value; Test-Path confirms a key exists at all.

Why it's used today: Registry values are the literal, physical representation of the security settings a GPO is supposed to configure — checking them directly is checking ground truth, not a deployment status.

Handling a Missing Key as Its Own Finding

What it is: A registry value can be in one of three meaningfully different states: present with the correct value, present with the wrong value, or entirely absent — the third case (like SRV-DB02's rebuilt server that never received the policy at all) needs its own explicit handling, since Get-ItemProperty throws an error rather than returning a "false" value when a key doesn't exist.

Why it matters: Treating "missing" the same as "wrong" would work for reporting purposes, but conflates two genuinely different root causes — one is drift, the other is a setting that was simply never applied at all.

Reusing SupportsShouldProcess for Registry Remediation

What it is: The exact same [CmdletBinding(SupportsShouldProcess)] and $PSCmdlet.ShouldProcess() pattern from Project 03's patch installer and Project 10's AD onboarding, now applied to Set-ItemProperty calls against the registry.

Why it's used today: Directly modifying the registry is at least as consequential as installing a patch or creating an AD account — the same WhatIf-first discipline is non-negotiable here, not optional.

Type-Aware Comparison — DWORD Values

What it is: Many security settings (like SMBv1's enable/disable flag) are stored as DWORD (32-bit integer) values, typically 0 or 1. Comparing the actual value against an expected value requires making sure both sides are compared as the same type — a string "0" and a numeric 0 won't reliably compare equal without care.

Why it matters: This is the same type-casting discipline from Project 08's CSV history data, applied here to registry values, which can also arrive in a type that doesn't automatically match a hardcoded comparison value.

By this point, the shape of this project should be entirely predictable to you: read the actual state, compare it against a defined baseline, report the gap, and — only with explicit WhatIf-gated permission — offer to fix it. That's nearly the entire academy's philosophy, applied one more time to the deepest configuration layer: the registry itself.

04 Architecture

The dashed line to remediation is deliberate — it's a separate, optional path gated entirely behind WhatIf/Confirm, never an automatic consequence of finding drift.

06 The Script — Test-RegistryBaseline.ps1

Scripts\Test-RegistryBaseline.ps1 
<#
.SYNOPSIS
    Registry Security Baseline Validation - ABC Bank Production Support
.DESCRIPTION
    Directly verifies security-mandated registry settings across the
    fleet against a defined baseline, distinguishing missing settings
    from incorrect ones, with optional WhatIf-gated remediation.
#>

[CmdletBinding(SupportsShouldProcess)]                        # Enables -WhatIf/-Confirm for the remediation path
param(
    [switch]$Remediate                                # Explicit opt-in — default behavior is report-only
)

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Servers  = Get-Content -Path "C:\RegistryBaseline\Config\servers.txt"
$Baseline = Get-Content -Path "C:\RegistryBaseline\Config\security-baseline.json" -Raw | ConvertFrom-Json

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\RegistryBaseline\Logs\RegistryCheck_$TimeTag.log"
$ReportCSV = "C:\RegistryBaseline\Reports\RegistryCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-SETTING VALIDATION (AND OPTIONAL REMEDIATION)
# ============================================================

function Test-RegistrySetting {
    param(
        [string]$ComputerName,
        [string]$SettingName,
        [string]$RegistryPath,
        [string]$ValueName,
        $ExpectedValue,
        [string]$ValueType
    )

    $Result = [PSCustomObject]@{
        ServerName    = $ComputerName
        SettingName   = $SettingName
        ActualValue   = ""
        ExpectedValue = $ExpectedValue
        Remediated    = $false
        ComplianceStatus = "UNKNOWN"
        CheckedAt     = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    $RemoteResult = Invoke-Command -ComputerName $ComputerName `
        -ArgumentList $RegistryPath, $ValueName, $ExpectedValue, $ValueType, $Remediate.IsPresent `
        -ScriptBlock {
        param($Path, $Name, $Expected, $Type, $ShouldRemediate)

        if (-not (Test-Path -Path $Path)) {
            return [PSCustomObject]@{ Status = "KEY MISSING"; ActualValue = $null; Remediated = $false }   # The key/path itself doesn't exist — a distinct finding
        }

        $CurrentValue = (Get-ItemProperty -Path $Path -Name $Name -ErrorAction SilentlyContinue).$Name

        if ($null -eq $CurrentValue) {
            return [PSCustomObject]@{ Status = "VALUE MISSING"; ActualValue = $null; Remediated = $false }   # Key exists, but this specific value name doesn't
        }

        if ([int]$CurrentValue -eq [int]$Expected) {                        # Explicit [int] cast on BOTH sides for a reliable comparison
            return [PSCustomObject]@{ Status = "COMPLIANT"; ActualValue = $CurrentValue; Remediated = $false }
        }

        # ---- VALUE IS WRONG — REMEDIATE ONLY IF EXPLICITLY REQUESTED AND CONFIRMED ----
        if ($ShouldRemediate -and $PSCmdlet.ShouldProcess("$Path\$Name", "Set to $Expected")) {
            Set-ItemProperty -Path $Path -Name $Name -Value $Expected -Type $Type
            return [PSCustomObject]@{ Status = "NON-COMPLIANT - REMEDIATED"; ActualValue = $CurrentValue; Remediated = $true }
        }

        return [PSCustomObject]@{ Status = "NON-COMPLIANT"; ActualValue = $CurrentValue; Remediated = $false }
    }

    $Result.ActualValue = $RemoteResult.ActualValue
    $Result.Remediated  = $RemoteResult.Remediated
    $Result.ComplianceStatus = $RemoteResult.Status

    if ($RemoteResult.Status -ne "COMPLIANT") {
        Write-Log "$ComputerName : $SettingName -> $($RemoteResult.Status) (actual: $($RemoteResult.ActualValue), expected: $ExpectedValue)" "WARNING"
    }

    return $Result
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Registry Baseline Check ($($Baseline.Count) setting(s), $($Servers.Count) server(s)) — Remediate: $($Remediate.IsPresent) =====" "INFO"

$AllResults = foreach ($Server in $Servers) {
    foreach ($Setting in $Baseline) {
        Test-RegistrySetting -ComputerName $Server -SettingName $Setting.SettingName `
            -RegistryPath $Setting.RegistryPath -ValueName $Setting.ValueName `
            -ExpectedValue $Setting.ExpectedValue -ValueType $Setting.ValueType
    }
}

$AllResults | Sort-Object ComplianceStatus -Descending | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$NonCompliantCount = ($AllResults | Where-Object { $_.ComplianceStatus -like "*MISSING*" -or $_.ComplianceStatus -like "NON-COMPLIANT*" }).Count
if ($NonCompliantCount -gt 0) {
    Write-Log "$NonCompliantCount setting(s) are non-compliant across the fleet" "WARNING"
}

Write-Log "===== Registry Baseline Check Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

if (-not (Test-Path -Path $Path)) { return ... "KEY MISSING" ... }
Checked before attempting to read any value — trying to read a value from a key that doesn't exist at all would throw a different, more confusing error than deliberately checking for and reporting this specific, meaningful case first.
if ([int]$CurrentValue -eq [int]$Expected)
Registry DWORD values and JSON-sourced expected values can arrive as different underlying .NET types even when they represent "the same number" — explicitly casting both sides to [int] guarantees a reliable, type-safe comparison instead of risking a subtle type-mismatch bug.
if ($ShouldRemediate -and $PSCmdlet.ShouldProcess("$Path\$Name", "Set to $Expected"))
Two separate gates must both be true before any change happens: the caller must have explicitly passed -Remediate (opt-in at the script level) AND ShouldProcess must confirm (opt-in at the WhatIf/Confirm level) — this double-gating is deliberately stricter than earlier projects, appropriate for something as security-sensitive as direct registry modification.
$RemoteResult = Invoke-Command ... -ArgumentList $RegistryPath, $ValueName, $ExpectedValue, $ValueType, $Remediate.IsPresent
$Remediate.IsPresent converts the switch parameter into an explicit boolean before passing it into the remote script block — switches don't cross the remoting boundary as cleanly as plain values, so this conversion avoids a subtle bug.
Common mistake: running this kind of script with -Remediate enabled by default, or without first reviewing a full -WhatIf run across the fleet. Registry changes to security settings can have wide-reaching effects (like SMBv1 changes potentially affecting legacy device compatibility) — always review before committing at scale.

08 Script Execution Flow

StepWhat Happens
1. Key Existence CheckA completely missing registry path is identified and reported distinctly before any value comparison is even attempted.
2. Value Existence CheckA key that exists but lacks the specific expected value name is also reported distinctly — a second, different "missing" case.
3. Type-Safe ComparisonBoth sides of the comparison are explicitly cast to ensure a reliable match, regardless of the underlying representation each side arrived in.
4. Double-Gated RemediationOnly when both -Remediate was passed AND ShouldProcess confirms does Set-ItemProperty actually run — two independent opt-ins, not one.
5. ReportingSame log/CSV pattern as every project, distinguishing missing, non-compliant, remediated, and compliant as genuinely different states.

09 Windows Internals — In Simple English

How Group Policy Actually Applies Settings

Most GPO security settings ultimately work by writing specific values into specific registry keys during a policy refresh cycle — which is exactly why checking the registry directly verifies the true, physical outcome, completely independent of whether that policy refresh cycle actually completed successfully on a given machine.

Why Policy Refresh Can Silently Fail

A stale Group Policy cache, a network issue during refresh, a conflicting local policy, or — as in this project's story — a server rebuilt after the policy's original rollout and never given a fresh refresh, can all result in a GPO never actually taking effect, with no obvious error surfaced anywhere.

DWORD vs String Registry Value Types

The registry stores values with an explicit declared type (DWORD, String, Binary, etc.) — Set-ItemProperty's -Type parameter must match what the setting actually expects, since writing the right data with the wrong type can cause Windows to simply ignore the value.

12 Production Best Practices

Never trust policy deployment status as proof of compliance — verify the actual resulting registry state directly.
Distinguish "key missing," "value missing," and "value wrong" as separate findings — they have different root causes and may need different remediation approaches.
Double-gate any remediation path (explicit opt-in parameter AND WhatIf/Confirm) for anything touching security-sensitive configuration — never single-gate a change this consequential.
Always cast values to a consistent type before comparing — registry values and JSON-sourced expected values can carry subtly different underlying types.

13 Interview Preparation

Q: Why isn't "we deployed the GPO" sufficient evidence of security baseline compliance?
Group Policy application can fail silently for many reasons — stale caches, a server rebuilt after rollout, policy conflicts — with no obvious error anywhere; only directly reading the actual resulting registry value confirms the setting genuinely took effect on that specific machine.
Q: Why distinguish "key missing" from "value wrong" instead of treating both as simply non-compliant?
They represent different root causes — a missing key often means the setting was never applied to that server at all (like a rebuilt machine), while a wrong value might mean a local override or a partial policy conflict — knowing which helps target the right remediation.
Q: Why require both -Remediate AND ShouldProcess confirmation before making a change?
Registry changes to security settings can have broad, sometimes unexpected effects — double-gating ensures a change can never happen from simply running the script normally, and even with remediation explicitly requested, still requires a final confirmed commit.
Q: What real-world risk exists even after this script confirms compliance?
A future Group Policy refresh, a manual local change, or another automated process could revert the setting after this check runs — this is exactly why the check needs to run on a genuine recurring schedule, not as a one-time verification.

Key Learnings

  • Type-safe comparison matters even for something as simple as a 0-or-1 registry flag
