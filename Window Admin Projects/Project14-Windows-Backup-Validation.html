Project 14 — Windows Backup Validation

Every backup for six months said "Success." Every one of them was nearly empty.

A backup job reporting success only proves the software finished running — it says nothing about whether the backup file it produced is actually a usable, complete copy of the data. Today's script checks three independent things: did the job report success, does the backup file exist and look recent, and is its size consistent with backup history — reusing Project 08's trend technique in a new, higher-stakes context.

01 The Production Story

The worst possible moment to discover a backup was never actually working.
Friday — A Real Restore, Six Months of False Confidence

A corrupted table forces the team to restore SRV-DB01's core banking database from last night's backup. The restore runs — and comes back nearly empty. They try the backup from two nights ago. Same problem. Three nights ago. Same problem. Going back through the backup history, every single job for the past six months reported "Success" in the backup software's own summary — but the actual backup files had been silently shrinking to a fraction of their expected size for months, quietly capturing almost nothing useful.

The root cause, once found: a configuration change months earlier had narrowed what the backup job actually included, without anyone noticing, because the job itself still completed and reported success every single night. "Success" meant "the software finished running its configured steps." It never meant "the resulting backup is actually good."

Priya is unusually direct about this one. "This is the incident that actually scares me the most out of everything we've built so far. I want a script that doesn't just check whether the backup job says it succeeded — I want it to check the backup FILE. Does it exist? Was it written recently? And — this is the part that would have caught this exact incident — is its size roughly consistent with what we've seen before, or did it just quietly shrink to a fraction of normal?"

This project's lesson generalizes far beyond backups: a system reporting "success" only proves it completed its own internal steps — it says nothing about whether the actual output is correct, unless something independently verifies the output itself.

03 New Concepts (Building on Projects 01–13)

You already know history-based trend analysis from Project 08. Here's how it applies to a very different, higher-stakes problem.
Windows Server Backup Cmdlets — Get-WBJob / Get-WBSummary

What it is: If using Windows Server Backup, Get-WBSummary returns the overall backup status, and Get-WBJob returns details of recent backup jobs — the same kind of "software's own opinion of what happened" status this project deliberately treats as necessary but not sufficient.

Why it's checked FIRST, not ONLY: The story's whole point is that this status alone was misleading for six months — it remains a useful first signal (a job that reports outright failure is definitely bad), but it can never be the only check.

File Existence and Recency — Independent of Job Status

What it is: Using Test-Path and a file's LastWriteTime to independently confirm a backup file actually exists where expected and was genuinely written recently — regardless of what the backup software's own status claims.

Why it matters: This is a second, independent source of truth. A job could report success while the file wasn't actually updated (a misconfigured destination path, for example) — checking the file directly catches that gap.

Reusing Project 08's History Pattern for Size Anomaly Detection

What it is: The exact same Export-Csv -Append / Import-Csv historical pattern from disk capacity forecasting, now tracking backup file sizes over time instead of free disk space — building a rolling average to compare each new backup against.

Why it's used today: This is the check that directly would have caught the story's incident — a backup that's still "there" and "recent" but has quietly shrunk to a fraction of its historical average is exactly the pattern a fixed-size threshold would miss, but a historical comparison catches naturally.

Percentage Deviation From a Rolling Average

What it is: (($Average - $Today) / $Average) * 100 calculates how far below (or above) today's value is compared to the historical average, as a percentage — far more robust than a fixed GB threshold, since it automatically scales as a system's normal backup size naturally grows over time.

Why it's used today: A 95% drop in backup size is suspicious on ANY system, regardless of whether "normal" is 5GB or 500GB — percentage deviation is threshold-agnostic in a way a fixed number can never be.

This project's central lesson, worth carrying into everything you build afterward: "success" reported by the system doing the work is a claim, not proof. Wherever the stakes are high enough, verify the actual output independently — don't just trust the status flag.

04 Architecture

All three checks feed into the same history file and the same verdict — a backup only counts as genuinely validated when the job succeeded, the file is really there and current, AND its size holds up against its own track record.

06 The Script — Test-BackupIntegrity.ps1

Scripts\Test-BackupIntegrity.ps1 
<#
.SYNOPSIS
    Backup Validation - ABC Bank Production Support
.DESCRIPTION
    Verifies backups are genuinely usable, not just "reported successful":
    checks file existence/recency, and compares today's backup size
    against a rolling historical average to catch silent shrinkage.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$BackupTargets = Get-Content -Path "C:\BackupValidation\Config\backup-targets.json" -Raw | ConvertFrom-Json
$HistoryFile   = "C:\BackupValidation\History\backup-size-history.csv"

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\BackupValidation\Logs\BackupCheck_$TimeTag.log"
$ReportCSV = "C:\BackupValidation\Reports\BackupCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: PER-BACKUP VALIDATION
# ============================================================

function Test-BackupFile {
    param(
        [string]$ServerName,
        [string]$BackupFilePath,
        [int]$MaxAgeHours,
        [int]$MaxDeviationPercent
    )

    $Result = [PSCustomObject]@{
        ServerName        = $ServerName
        BackupFilePath    = $BackupFilePath
        FileExists        = $false
        AgeHours          = $null
        SizeGB            = $null
        HistoricalAvgGB   = $null
        DeviationPercent  = $null
        OverallStatus     = "UNKNOWN"
        CheckedAt         = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        # ---- CHECK 1: DOES THE FILE ACTUALLY EXIST? ----
        $FileInfo = Invoke-Command -ComputerName $ServerName -ArgumentList $BackupFilePath -ScriptBlock {
            param($Path)
            if (Test-Path -Path $Path) { Get-Item -Path $Path } else { $null }
        }

        if (-not $FileInfo) {
            Write-Log "$ServerName : backup file NOT FOUND at $BackupFilePath" "ERROR"
            $Result.OverallStatus = "CRITICAL - FILE MISSING"
            return $Result
        }
        $Result.FileExists = $true

        # ---- CHECK 2: IS IT RECENT? ----
        $Result.AgeHours = [math]::Round(((Get-Date) - $FileInfo.LastWriteTime).TotalHours, 1)
        $Result.SizeGB   = [math]::Round($FileInfo.Length / 1GB, 2)

        if ($Result.AgeHours -gt $MaxAgeHours) {
            Write-Log "$ServerName : backup file is STALE ($($Result.AgeHours)h old)" "ERROR"
            $Result.OverallStatus = "CRITICAL - STALE BACKUP"
            return $Result            # A stale backup fails regardless of its size — no point checking further
        }

        # ---- CHECK 3: RECORD TODAY'S SIZE, THEN COMPARE AGAINST HISTORY ----
        [PSCustomObject]@{
            Date = Get-Date -Format "yyyy-MM-dd"; ServerName = $ServerName; SizeGB = $Result.SizeGB
        } | Export-Csv -Path $HistoryFile -Append -NoTypeInformation   # Same -Append pattern as Project 08

        $History = Import-Csv -Path $HistoryFile | Where-Object { $_.ServerName -eq $ServerName }
        $PriorReadings = $History | Select-Object -SkipLast 1   # Everything EXCEPT the reading we just added

        if ($PriorReadings.Count -lt 3) {
            $Result.OverallStatus = "OK - BUILDING HISTORY"    # Not enough history yet for a meaningful comparison
            Write-Log "$ServerName : backup OK, still building size history ($($PriorReadings.Count) prior readings)" "INFO"
            return $Result
        }

        $AvgSize = ($PriorReadings | Measure-Object -Property SizeGB -Average).Average
        $Result.HistoricalAvgGB = [math]::Round($AvgSize, 2)
        $Result.DeviationPercent = [math]::Round( (( $AvgSize - $Result.SizeGB) / $AvgSize) * 100, 1)   # Positive = today is SMALLER than average

        if ($Result.DeviationPercent -ge $MaxDeviationPercent) {
            Write-Log "$ServerName : backup size ANOMALY — $($Result.DeviationPercent)% below historical average ($($Result.SizeGB)GB vs avg $($Result.HistoricalAvgGB)GB)" "ERROR"
            $Result.OverallStatus = "CRITICAL - SIZE ANOMALY"
        }
        else {
            $Result.OverallStatus = "VALIDATED"
            Write-Log "$ServerName : backup VALIDATED ($($Result.SizeGB)GB, $($Result.DeviationPercent)% vs historical average)" "INFO"
        }
    }
    catch {
        Write-Log "Error validating backup on $ServerName : $($_.Exception.Message)" "ERROR"
        $Result.OverallStatus = "CHECK FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 3: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Backup Validation for $($BackupTargets.Count) target(s) =====" "INFO"

$AllResults = foreach ($Target in $BackupTargets) {
    Test-BackupFile -ServerName $Target.ServerName -BackupFilePath $Target.BackupFilePath `
                     -MaxAgeHours $Target.MaxAgeHours -MaxDeviationPercent $Target.MaxDeviationPercent
}

$AllResults | Sort-Object OverallStatus | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$CriticalCount = ($AllResults | Where-Object { $_.OverallStatus -like "CRITICAL*" }).Count
if ($CriticalCount -gt 0) {
    Write-Log "$CriticalCount backup(s) FAILED validation — see report immediately" "WARNING"
}

Write-Log "===== Backup Validation Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

if ($Result.AgeHours -gt $MaxAgeHours) { ... return $Result }
A stale backup fails and returns immediately, before even reaching the size-history comparison — checking the size of an already-too-old backup wouldn't add useful information, since the file being stale is already disqualifying on its own.
$PriorReadings = $History | Select-Object -SkipLast 1
Deliberately excludes the reading we just appended a moment ago from the average calculation — comparing today's size against an average that already includes today's own value would understate any real anomaly, since today's bad reading would be pulling down its own comparison baseline.
$Result.DeviationPercent = ((($AvgSize - $Result.SizeGB) / $AvgSize) * 100
A positive result means today's backup is smaller than the historical average, by that percentage — this is the exact calculation that would have caught the story's incident, since a 6-months-gradual or even sudden shrink shows up clearly as a large positive deviation regardless of the system's normal baseline size.
if ($PriorReadings.Count -lt 3) { $Result.OverallStatus = "OK - BUILDING HISTORY" ... return }
Exactly the same "insufficient history" honesty from Project 08 — refusing to produce a potentially misleading anomaly verdict from too few data points, rather than guessing.
Common mistake: only checking whether the job status says "Success" and treating that as sufficient. As this project's entire story demonstrates, that single check can be true for months while the actual backup output is nearly useless — independent verification of the file itself is not optional for anything this critical.

08 Script Execution Flow

StepWhat Happens
1. File Existence GateA missing file fails immediately and unconditionally — no size or history comparison is even attempted.
2. Recency GateA stale file fails immediately after that — age is checked before size, since an old backup is disqualifying regardless of how large it is.
3. Record Today's SizeOnly after passing both gates does today's size get appended to history — a failed backup shouldn't pollute the historical average other checks rely on.
4. Historical ComparisonPrior readings (explicitly excluding today's own new entry) are averaged and compared against today's actual size.
5. ReportingSame log/CSV pattern as every prior project, now carrying the full evidence trail: existence, age, size, and historical comparison.

09 Windows Internals — In Simple English

Why Backup Software Can Report False Success

Most backup tools consider a job "successful" if it completes its configured steps without an internal error — it has no independent way of knowing whether a scope misconfiguration silently excluded the data that actually mattered.

LastWriteTime vs LastAccessTime

A file's LastWriteTime reflects when its content was last actually modified — the right property for confirming a backup was genuinely regenerated, as opposed to LastAccessTime, which can change just from something reading the file.

Why Percentage-Based Anomaly Detection Scales Better

A database that naturally grows from 400GB to 450GB over a year would trip a fixed-size threshold constantly; a percentage-deviation check automatically adapts as the historical average itself shifts, without any manual retuning.

12 Production Best Practices

Never trust a job status alone for anything business-critical — independently verify the actual output whenever the stakes justify the extra check.
Use percentage-based anomaly detection against historical data instead of a fixed size threshold — it scales naturally as normal size changes over time.
Exclude today's own new reading from the historical average it's being compared against — including it understates genuine anomalies.
Check existence and recency before size — a missing or stale backup is disqualifying on its own, regardless of what its size comparison might show.

13 Interview Preparation

Q: Why isn't checking the backup job's own "Success" status sufficient?
A job reports success based on completing its own configured steps without internal error — it has no way of independently verifying that the resulting file is a complete, usable copy of the intended data, which is exactly the gap this project's story incident fell through for six months.
Q: Why use percentage deviation from a historical average instead of a fixed minimum file size?
A fixed threshold requires constant manual retuning as a system's normal backup size naturally grows, and risks being set either too loose to catch a real problem or too tight and constantly false-alarming — percentage deviation from a rolling average adapts automatically to what's actually normal for that specific system.
Q: Why exclude today's reading from the average it's compared against?
Including it would let a bad reading partially average itself into its own baseline, understating the true size of a genuine anomaly — excluding it keeps the comparison honest against only what's actually been observed before today.
Q: What's a genuine limitation of this size-based approach?
It can't detect a backup that's the right size but contains corrupted or logically incorrect data — a true guarantee of restorability ultimately requires periodic actual restore testing, which this project explicitly scopes out as a larger future initiative.
