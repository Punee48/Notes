Project 21 — Production Server Readiness Check

Twenty checklists in twenty engineers' heads. Today, one script, one shared module, one formal answer.

Every server that goes live is supposed to pass a mental checklist — patched, firewalled correctly, right disk space, right security baseline. But a mental checklist varies by who's running it and how tired they are. Today you build your first real PowerShell module — shared, reusable code — and compose it with pieces of everything you've built so far into one formal go/no-go readiness gate.

SRV-BRANCH12 — 6/6 checks passed, READY
SRV-BRANCH13 — SMBv1 still enabled, NOT READY
SRV-BRANCH14 — disk forecast < 30 days, REVIEW

01 The Production Story

A new branch launch, and a checklist that lived only in people's memory.
Monday — Branch Expansion, Twelve New Servers, One Missed Step

Remember the fifteen new hires from Project 10's onboarding story? Their branch expansion needs twelve new servers stood up alongside them. Each one is supposed to pass a go-live checklist before being released to production: fully patched, correct firewall rules, adequate disk space, no security baseline drift, all required services running. In practice, that checklist has always lived in each engineer's head, applied a little differently by whoever happens to be doing the provisioning that week.

It happens exactly as you'd guess: SRV-BRANCH13 goes live during a particularly busy week, and one engineer — genuinely not negligent, just going fast — skips the SMBv1 check that Project 20 automated, assuming "someone else already confirmed the security baseline on the image." Three weeks later, the same penetration test scope that found the earlier gap catches it again, on a server that had never even been part of the original eight-month-old mandate.

"We've built almost every individual check this server needs, across the last twenty projects," Priya says. "What we've never built is one thing that runs ALL of them together and gives a single, honest answer: is this server actually ready for production, yes or no. And I want us to stop copy-pasting the same Write-Log function into every single script — build it once, as a real shared module, and have everything import it from now on."

This project is deliberately a synthesis project — building a real PowerShell module for the first time, and composing pieces of your prior work into one orchestrated readiness gate, rather than introducing an entirely new monitoring domain.

03 New Concepts (Building on Projects 01–20)

You already know every individual check this project composes. Here's what's genuinely new: building your own module and orchestrating.
Building Your Own PowerShell Module (.psm1)

What it is: A .psm1 file is a module file — a container for functions meant to be reused across many scripts. Import-Module loads it, and Export-ModuleMember controls which of its functions become available to whatever imports it.

Why it's used today: You've written a near-identical Write-Log function in every single project so far. That's exactly the kind of duplication a module exists to eliminate — write it once, in one place, and every script that needs it imports it instead of redefining it.

Export-ModuleMember — Controlling the Module's Public Surface

What it is: By default, functions defined inside a module aren't automatically visible outside it — Export-ModuleMember -Function Write-AcademyLog, Get-CompositeVerdict explicitly declares which functions become part of the module's public, usable interface.

Why it matters: This is the same "public surface vs internal detail" idea from good function design generally — a module can have internal helper logic that isn't meant to be called directly, alongside the functions it deliberately exposes.

Composing Multiple Checks Into One Weighted Verdict

What it is: Rather than one more independent pass/fail check, this project runs several — patch compliance, disk space, firewall, critical service, security baseline — and combines their individual results into one overall READY / NOT READY / REVIEW decision for the whole server.

Why it's used today: This is the actual point of the project: a formal go-live decision needs to synthesize many independent signals into one clear answer, not just present five separate reports someone has to mentally combine themselves.

Generating a Formal Sign-Off Report

What it is: Beyond a routine CSV, this project's output is framed explicitly as a change-management artifact — a dated, named record suitable for attaching to a change ticket or go-live approval, not just an operational log.

Why it's used today: Priya wants a durable record proving the checklist was actually applied, addressing the story's core problem: right now, there's no record at all of which checks were performed before SRV-BRANCH13 went live.

This project's real skill isn't a new monitoring technique — it's software engineering discipline applied to your own growing automation suite: stop duplicating code, start composing what you've already built. That instinct is what separates a collection of scripts from an actual automation platform.

06 The Code

Modules\PSAcademyCommon.psm1 
# PSAcademyCommon.psm1
# Shared functions used across the ABC Bank PowerShell automation suite.
# Import with: Import-Module "C:\ServerReadiness\Modules\PSAcademyCommon.psm1"

function Write-AcademyLog {                    # The SAME logging logic that's been copy-pasted since Project 01 — now defined ONCE
    param(
        [Parameter(Mandatory)][string]$LogFile,       # Caller specifies which log file, since every script has its own
        [Parameter(Mandatory)][string]$Message,
        [string]$Level = "INFO"
    )
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

function Get-CompositeVerdict {                # Shared logic for combining several PASS/FAIL/WARN results into one verdict
    param([Parameter(Mandatory)][array]$CheckResults)   # Array of objects, each with a .Status property

    if ($CheckResults.Status -contains "FAIL") {
        return "NOT READY"            # Any hard failure blocks readiness outright
    }
    elseif ($CheckResults.Status -contains "WARN") {
        return "REVIEW REQUIRED"      # Warnings don't block, but need a human's judgment call
    }
    else {
        return "READY"
    }
}

Export-ModuleMember -Function Write-AcademyLog, Get-CompositeVerdict   # Only these two functions become usable by scripts that import this module
Scripts\Test-ServerReadiness.ps1 
<#
.SYNOPSIS
    Production Server Readiness Check - ABC Bank Production Support
.DESCRIPTION
    Composes patch status, disk space, firewall, critical service, and
    security baseline checks into one formal go/no-go readiness verdict
    and sign-off report for a server about to go into production.
#>

param([Parameter(Mandatory)][string]$ServerName)   # Run against ONE server per readiness check — a deliberate, focused gate

Import-Module "C:\ServerReadiness\Modules\PSAcademyCommon.psm1" -Force   # Load the shared functions

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\ServerReadiness\Logs\Readiness_${ServerName}_$TimeTag.log"
$ReportCSV = "C:\ServerReadiness\Reports\Readiness_${ServerName}_$TimeTag.csv"

# ============================================================
# SECTION 2: INDIVIDUAL READINESS CHECKS
# ============================================================
# Each check below is a simplified version of logic already built in
# earlier projects — this script's real job is composing them, not
# reinventing them.

function Test-PatchStatus {
    param([string]$Server)
    $PendingUpdates = Invoke-Command -ComputerName $Server -ScriptBlock {
        (Get-HotFix | Measure-Object).Count                    # Simplified stand-in for full Project 02-style KB compliance
    }
    [PSCustomObject]@{ CheckName = "Patch Status"; Status = if ($PendingUpdates -gt 0) { "PASS" } else { "WARN" }; Detail = "$PendingUpdates hotfix(es) on record" }
}

function Test-DiskSpace {
    param([string]$Server)
    $Disk = Get-CimInstance -ClassName Win32_LogicalDisk -ComputerName $Server -Filter "DeviceID='C:'"   # Same pattern as Project 01/08
    $FreeGB = [math]::Round($Disk.FreeSpace / 1GB, 1)
    [PSCustomObject]@{ CheckName = "Disk Space"; Status = if ($FreeGB -lt 20) { "FAIL" } elseif ($FreeGB -lt 50) { "WARN" } else { "PASS" }; Detail = "$FreeGB GB free on C:" }
}

function Test-RequiredPortOpen {
    param([string]$Server, [int]$Port = 3389)
    $Result = Test-NetConnection -ComputerName $Server -Port $Port -WarningAction SilentlyContinue   # Same pattern as Project 19
    [PSCustomObject]@{ CheckName = "Required Port ($Port)"; Status = if ($Result.TcpTestSucceeded) { "PASS" } else { "FAIL" }; Detail = "TcpTestSucceeded: $($Result.TcpTestSucceeded)" }
}

function Test-CriticalServiceRunning {
    param([string]$Server, [string]$ServiceName = "W3SVC")
    $Svc = Get-Service -ComputerName $Server -Name $ServiceName -ErrorAction SilentlyContinue   # Same pattern as Project 01
    [PSCustomObject]@{ CheckName = "Critical Service ($ServiceName)"; Status = if ($Svc.Status -eq "Running") { "PASS" } else { "FAIL" }; Detail = "Status: $($Svc.Status)" }
}

function Test-SecurityBaselineSMB1 {
    param([string]$Server)
    $Value = Invoke-Command -ComputerName $Server -ScriptBlock {
        (Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters" -Name SMB1 -ErrorAction SilentlyContinue).SMB1   # Same pattern as Project 20
    }
    [PSCustomObject]@{ CheckName = "SMBv1 Disabled"; Status = if ($Value -eq 0) { "PASS" } else { "FAIL" }; Detail = "SMB1 registry value: $Value" }
}

# ============================================================
# SECTION 3: MAIN EXECUTION — RUN ALL CHECKS, COMPOSE VERDICT
# ============================================================

Write-AcademyLog -LogFile $LogFile -Message "===== Starting Production Readiness Check for $ServerName ====="

$CheckResults = @(
    Test-PatchStatus              -Server $ServerName
    Test-DiskSpace                -Server $ServerName
    Test-RequiredPortOpen         -Server $ServerName -Port 3389
    Test-CriticalServiceRunning   -Server $ServerName -ServiceName "W3SVC"
    Test-SecurityBaselineSMB1     -Server $ServerName
)

foreach ($Check in $CheckResults) {
    $LogLevel = if ($Check.Status -eq "FAIL") { "ERROR" } elseif ($Check.Status -eq "WARN") { "WARNING" } else { "INFO" }
    Write-AcademyLog -LogFile $LogFile -Message "$($Check.CheckName): $($Check.Status) — $($Check.Detail)" -Level $LogLevel
}

$FinalVerdict = Get-CompositeVerdict -CheckResults $CheckResults   # The shared module function makes the final call

$CheckResults | Format-Table -AutoSize

Write-Host "`n===== FINAL READINESS VERDICT for ${ServerName}: $FinalVerdict =====`n" -ForegroundColor $(if($FinalVerdict -eq "READY"){"Green"}elseif($FinalVerdict -eq "REVIEW REQUIRED"){"Yellow"}else{"Red"})

$CheckResults | Select-Object @{Name="ServerName";Expression={$ServerName}}, CheckName, Status, Detail |
    Export-Csv -Path $ReportCSV -NoTypeInformation

Write-AcademyLog -LogFile $LogFile -Message "===== Readiness Check Completed. Verdict: $FinalVerdict. Report: $ReportCSV ====="

07 Line-by-Line Explanation

Import-Module "C:\ServerReadiness\Modules\PSAcademyCommon.psm1" -Force
-Force re-imports the module even if a version is already loaded in the current session — useful while actively developing the module, since without it, a previous version could remain cached and your edits wouldn't take effect.
Export-ModuleMember -Function Write-AcademyLog, Get-CompositeVerdict
This is the line that actually makes the module's functions usable elsewhere — without it, even a correctly imported module would expose nothing, since PowerShell defaults to keeping module contents private unless explicitly exported.
$CheckResults = @( Test-PatchStatus ... Test-DiskSpace ... )
Wrapping several function calls in @( ) collects each one's returned object into a single flat array — this is the exact composition step that turns five separate, independent checks into one unified collection ready for a combined verdict.
if ($CheckResults.Status -contains "FAIL") { return "NOT READY" }
PowerShell's member-enumeration feature lets $CheckResults.Status return every result's Status property as an array in one expression, without an explicit loop — -contains then checks whether "FAIL" appears anywhere in that array, checking all five results' status in a single readable line.
Common mistake: forgetting -Force on Import-Module while actively iterating on a module's code during development — you can spend a confusing amount of time debugging a "bug" that's actually just PowerShell running a stale, already-loaded version of your module from before your latest edit.

08 Script Execution Flow

StepWhat Happens
1. Module ImportThe shared PSAcademyCommon module loads first, making Write-AcademyLog and Get-CompositeVerdict available for the rest of the script.
2. Five Independent ChecksEach check function runs completely independently, using the exact same techniques from their respective earlier projects, simplified for this composite context.
3. CompositionAll five results collect into one array — this is the moment five separate answers become one dataset ready for a unified decision.
4. Composite VerdictGet-CompositeVerdict, from the shared module, applies one consistent rule (any FAIL blocks, any WARN needs review, otherwise READY) to the whole array.
5. Sign-Off ReportingBoth the console output and the CSV are framed as a formal go-live record, with the server name and final verdict prominently included.

09 Windows Internals — In Simple English

How PowerShell Finds and Loads Modules

PowerShell maintains a list of module paths (PSModulePath) it searches automatically, but a module can also be loaded by its explicit full file path, as this project does — useful for a self-contained project folder that doesn't require installing the module system-wide.

Why Export-ModuleMember Defaults to Restrictive

Without any Export-ModuleMember statement, a .psm1 file actually exports everything by default — explicitly calling Export-ModuleMember switches to an intentional, restrictive allow-list, which is considered the better practice for any module meant to be reused by others, since it creates a clear, deliberate public interface.

Member Enumeration — A PowerShell-Specific Convenience

$CheckResults.Status automatically returning an array of every object's Status property (rather than requiring a manual loop) is a PowerShell-specific language feature, not something most other scripting languages provide as concisely — it's one of the small conveniences that makes PowerShell particularly pleasant for exactly this kind of object-collection work.

12 Production Best Practices

The moment you notice yourself copy-pasting the same function into a third script, that's the signal to extract it into a shared module instead.
Keep a module's exported surface intentional and minimal via Export-ModuleMember — a clear public interface is easier to maintain and reason about than "everything is available."
Design composite verdicts around the most severe individual result (any FAIL blocks) rather than an average or majority — a go-live gate should never let one serious problem get diluted by several passing checks.
Treat a formal readiness/sign-off report as a real change-management artifact — name it, date it, and store it somewhere durable and retrievable for audit purposes.

13 Interview Preparation

Q: Why build a shared module now instead of at the very start of this academy?
The need for it only becomes obvious after real duplication accumulates — building an abstraction too early, before you've seen the actual repeated pattern across multiple real projects, risks designing the wrong shared interface; refactoring toward a module once the pattern is proven is a common and reasonable real-world sequence.
Q: Why does any single FAIL block readiness, regardless of how many other checks pass?
A production readiness gate exists specifically to catch the one thing that would cause a real incident — averaging or requiring only a majority to pass would let a genuinely serious problem, like the story's disabled SMBv1 check, slip through simply because other unrelated checks happened to look fine.
Q: How would you extend this to check many new servers in a batch, like the story's twelve-server branch expansion?
Wrap the existing single-server logic in an outer loop (or parallel execution, using the ForEach-Object -Parallel technique from Project 03) over a list of server names, producing one sign-off report per server rather than combining them into one ambiguous batch result.
Q: What's the real organizational value of a formal sign-off report here, beyond the technical check itself?
It creates an auditable record proving the checklist was actually and consistently applied before go-live — directly addressing the story's root problem, where there was no record at all of what had or hadn't been verified before SRV-BRANCH13 went into production.

14 Key Learnings & Assignment

Key Learnings

  • A .psm1 module with Export-ModuleMember is how you stop duplicating shared logic (like logging) across every script in a growing suite
  • Composing several independent checks into one verdict is a deliberate design decision — most severe result wins, not an average
  • A formal, durable sign-off report is itself a real deliverable, not just a byproduct of running checks
  • Real automation platforms grow by refactoring toward shared code once duplication becomes obvious, not by planning every abstraction upfront
