Project 25 — Disaster Recovery Validation

The DR plan says four hours. Nobody has actually measured what it takes.

Every "DR ready" checkbox in this bank's history has meant "we have a documented plan and a secondary site." Almost none of them have meant "we recently measured how much data we'd actually lose, and how long recovery would genuinely take." Today's project puts real numbers behind those two questions — RPO and RTO — instead of assumptions.

01 The Production Story

A DR plan that had been "ready" on paper for years, and untested in exactly the way that mattered most.
Quarterly DR Test — The First Real One in a While

ABC Bank's Disaster Recovery plan has always technically existed: a documented runbook, a secondary site, a stated commitment of a 4-hour Recovery Time Objective (RTO) and a 15-minute Recovery Point Objective (RPO) — meaning, on paper, no more than 15 minutes of data should ever be lost in a real disaster. Nobody has actually measured either number against reality in longer than anyone on the current team can remember.

This quarter's test finally does. The results are humbling. The core banking database's replication to the DR site is healthy — genuinely a few seconds of lag, comfortably inside the stated RPO. But the reporting database's replication had silently broken three weeks earlier, with nobody noticing, meaning a real disaster today would have lost three weeks of reporting data, not fifteen minutes. And nobody could say with any confidence what the actual RTO would be either, because the runbook itself hadn't been walked through in over a year.

"A DR plan that's never actually measured is a hope, not a plan," Priya says. "I want us doing what a real DR test should do: actually check current replication lag for our RPO-critical systems, in real numbers, not assumptions — and check that DR-site backups themselves are recent and valid, using exactly what we already built in Project 17. This is one of the last projects in this whole series, and it deliberately pulls together nearly everything we've built: SQL health, backup validation, date math, layered independent verdicts — all in service of the one question that matters most in a genuine disaster: could we actually recover, and how much would we lose?"

This project is the natural culmination of the "verify, don't assume" theme running through this entire academy — applied here to the single scenario where an unverified assumption is most catastrophic: an actual disaster.

03 New Concepts (Building on Projects 01–24)

This project deliberately composes techniques from across the whole series more than it introduces brand-new ones.
RPO and RTO — Turning DR Language Into Measurable Numbers

What it is: Recovery Point Objective (RPO) is the maximum acceptable amount of data loss, measured in time — "no more than 15 minutes of data" means replication lag must never exceed 15 minutes. Recovery Time Objective (RTO) is the maximum acceptable time to actually restore service after a disaster.

Why it's used today: This project's whole purpose is measuring the ACTUAL current value behind these two numbers, rather than trusting the documented target as if it were automatically being met.

Measuring Replication Lag via SQL Server DMVs

What it is: For an Always On Availability Group or similar replication technology, SQL Server exposes live replica synchronization state through system views like sys.dm_hadr_database_replica_states, including how far behind the secondary replica currently is.

Why it's used today: This is the direct, technical answer to "what is our actual current RPO" — reusing exactly the Invoke-Sqlcmd technique from Project 16, pointed at a genuinely new diagnostic question.

Composing Project 17's Backup Validation for the DR Site

What it is: The exact same RESTORE VERIFYONLY and backup-history logic from Project 17, applied specifically to backups taken at or shipped to the DR site — genuine reuse of prior work rather than reinvention, exactly like Project 21's readiness gate.

Why it's used today: Even with healthy replication, DR readiness also depends on DR-site backups being genuinely current and restorable in their own right — this project deliberately doesn't rebuild that logic, it composes it.

A Final Composite DR Readiness Verdict

What it is: Combining measured replication lag (against the stated RPO target) and DR backup validation into one final assessment — reusing the exact "any critical dimension failing blocks readiness" philosophy from Project 21's Get-CompositeVerdict.

By this point in the academy, recognize this project for what it is: not a new domain, but a demonstration that everything you've built genuinely composes together to answer the single highest-stakes operational question a bank ever has to answer honestly — could we actually recover, right now, if we had to.

06 The Script — Test-DisasterRecoveryReadiness.ps1

Scripts\Test-DisasterRecoveryReadiness.ps1 
<#
.SYNOPSIS
    Disaster Recovery Validation - ABC Bank Production Support
.DESCRIPTION
    Measures actual database replication lag against stated RPO targets
    and validates DR-site backup currency, producing a real, measured
    DR readiness verdict instead of an assumed one.
#>

Import-Module SqlServer

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$Systems  = Get-Content -Path "C:\DRValidation\Config\dr-systems.json" -Raw | ConvertFrom-Json
$TimeTag  = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile  = "C:\DRValidation\Logs\DRCheck_$TimeTag.log"
$ReportCSV = "C:\DRValidation\Reports\DRCheck_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Entry = "[$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: MEASURE REPLICATION LAG (RPO)
# ============================================================

function Measure-ReplicationLag {
    param([string]$PrimaryInstance, [string]$DatabaseName, [int]$RpoTargetMinutes)

    $LagQuery = @"
SELECT
    DATEDIFF(SECOND, last_commit_time, GETDATE()) AS LagSeconds
FROM sys.dm_hadr_database_replica_states rs
INNER JOIN sys.databases d ON rs.database_id = d.database_id
WHERE d.name = '$DatabaseName' AND rs.is_primary_replica = 0    -- Only the SECONDARY replica's lag matters for RPO
"@

    try {
        $LagResult = Invoke-Sqlcmd -ServerInstance $PrimaryInstance -Query $LagQuery -QueryTimeout 15

        if (-not $LagResult) {
            return [PSCustomObject]@{ LagMinutes = $null; Status = "CRITICAL - REPLICATION NOT FOUND" }   # No replica state at all — replication itself may be broken, exactly like the story
        }

        $LagMinutes = [math]::Round($LagResult.LagSeconds / 60, 1)
        $Status = if ($LagMinutes -gt $RpoTargetMinutes) { "CRITICAL - RPO EXCEEDED" } else { "OK" }

        [PSCustomObject]@{ LagMinutes = $LagMinutes; Status = $Status }
    }
    catch {
        [PSCustomObject]@{ LagMinutes = $null; Status = "CRITICAL - CHECK FAILED" }
    }
}

# ============================================================
# SECTION 3: VALIDATE DR BACKUP CURRENCY (REUSING PROJECT 17'S APPROACH)
# ============================================================

function Test-DRBackupCurrency {
    param([string]$PrimaryInstance, [string]$DatabaseName)

    $BackupQuery = "SELECT MAX(backup_finish_date) AS LastBackup FROM msdb.dbo.backupset WHERE database_name = '$DatabaseName' AND type = 'D'"   # Same query shape as Project 17
    $Result = Invoke-Sqlcmd -ServerInstance $PrimaryInstance -Query $BackupQuery -QueryTimeout 15

    if (-not $Result.LastBackup) {
        return [PSCustomObject]@{ HoursSinceBackup = $null; Status = "CRITICAL - NO BACKUP FOUND" }
    }

    $HoursSince = [math]::Round(((Get-Date) - $Result.LastBackup).TotalHours, 1)   # Same date-math pattern used throughout this academy
    $Status = if ($HoursSince -gt 26) { "CRITICAL - BACKUP STALE" } else { "OK" }

    [PSCustomObject]@{ HoursSinceBackup = $HoursSince; Status = $Status }
}

# ============================================================
# SECTION 4: MAIN EXECUTION — COMPOSITE DR VERDICT PER SYSTEM
# ============================================================

Write-Log "===== Starting Disaster Recovery Validation for $($Systems.Count) system(s) =====" "INFO"

$AllResults = foreach ($System in $Systems) {

    $Lag    = Measure-ReplicationLag -PrimaryInstance $System.PrimaryInstance -DatabaseName $System.DatabaseName -RpoTargetMinutes $System.RpoTargetMinutes
    $Backup = Test-DRBackupCurrency  -PrimaryInstance $System.PrimaryInstance -DatabaseName $System.DatabaseName

    # Composite verdict: same "any CRITICAL blocks readiness" philosophy as Project 21's Get-CompositeVerdict
    $OverallStatus = if ($Lag.Status -like "CRITICAL*" -or $Backup.Status -like "CRITICAL*") { "DR NOT READY" } else { "DR READY" }

    if ($OverallStatus -eq "DR NOT READY") {
        Write-Log "$($System.SystemName) : DR NOT READY — Lag: $($Lag.Status) ($($Lag.LagMinutes) min) | Backup: $($Backup.Status) ($($Backup.HoursSinceBackup)h ago)" "ERROR"
    }
    else {
        Write-Log "$($System.SystemName) : DR READY — Lag $($Lag.LagMinutes) min (target $($System.RpoTargetMinutes) min), backup $($Backup.HoursSinceBackup)h ago" "INFO"
    }

    [PSCustomObject]@{
        SystemName        = $System.SystemName
        RpoTargetMinutes  = $System.RpoTargetMinutes
        MeasuredLagMinutes= $Lag.LagMinutes
        ReplicationStatus = $Lag.Status
        HoursSinceBackup  = $Backup.HoursSinceBackup
        BackupStatus      = $Backup.Status
        OverallStatus     = $OverallStatus
        CheckedAt         = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }
}

$AllResults | Sort-Object OverallStatus -Descending | Format-Table -AutoSize -Wrap

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$NotReadyCount = ($AllResults | Where-Object { $_.OverallStatus -eq "DR NOT READY" }).Count
if ($NotReadyCount -gt 0) {
    Write-Log "$NotReadyCount system(s) are DR NOT READY — this is a business continuity risk requiring immediate attention" "WARNING"
}

Write-Log "===== Disaster Recovery Validation Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

DATEDIFF(SECOND, last_commit_time, GETDATE()) AS LagSeconds
This T-SQL calculation runs the date subtraction directly in the database engine rather than in PowerShell — a deliberate choice here, since last_commit_time is a live, constantly-changing value best measured at the exact moment of the query, not after a round-trip back to PowerShell.
WHERE d.name = '$DatabaseName' AND rs.is_primary_replica = 0
Filtering to is_primary_replica = 0 specifically selects the SECONDARY replica's state — RPO is fundamentally about how far behind the standby copy is, so measuring the primary's own state would answer a completely different, irrelevant question.
if (-not $LagResult) { return ... "CRITICAL - REPLICATION NOT FOUND" }
An empty result here doesn't mean "zero lag" — it means the replication relationship itself couldn't be found at all, exactly the story's ReportingDB scenario. Treating "no data" as "everything's fine" would be a dangerous logic error; this explicitly distinguishes the two.
$OverallStatus = if ($Lag.Status -like "CRITICAL*" -or $Backup.Status -like "CRITICAL*") { "DR NOT READY" }
This is Project 21's composite verdict philosophy applied one more time — either dimension failing (replication OR backup) is enough to mark the whole system DR NOT READY, since real disaster recovery genuinely requires both to be sound simultaneously.
Common mistake: treating a missing replication state as healthy simply because no error was thrown. A query returning zero rows is a completely different, and often more concerning, outcome than a query returning a row showing acceptable lag — always check for "nothing found" as its own explicit case, exactly as this project's story's incident demonstrates.

09 Windows Internals — In Simple English

How Always On Availability Groups Replicate Data

Changes committed on the primary replica are continuously shipped to secondary replicas, which apply them to stay in sync — the gap between when a change commits on the primary and when it's confirmed applied on the secondary is exactly what "lag" measures, and exactly what determines real-world RPO.

Why Lag Can Silently Grow

Network issues between sites, a secondary replica falling behind under heavy load, or the replication link breaking entirely (as in the story) can each cause lag to grow — often with no obvious alert unless something is specifically watching for it, exactly the gap this project closes.

Why DR Backups Need Their Own Independent Validation

Even a perfectly replicating database doesn't remove the need for genuine backups at the DR site — replication protects against a primary-site failure, but not against, say, a logical data corruption that would replicate to the secondary just as faithfully as any legitimate change.

11 Hands-On Lab

A genuine Always On Availability Group lab requires multiple SQL Server instances configured for replication — meaningful infrastructure most learners won't have on hand. Focus this lab on the conceptual trace-through unless you have such an environment available.

If You Have an AG Lab Environment

  1. Run the script against a healthy AG and confirm it reports DR READY with a small, real lag value
  2. Pause data movement on the secondary replica (Suspend-SqlAvailabilityDatabase) to simulate the story's broken replication, re-run, and confirm lag grows and eventually the system reports DR NOT READY
  3. Resume data movement (Resume-SqlAvailabilityDatabase) and confirm the system returns to DR READY once lag catches back up

Without an AG Lab Environment

  • Review Microsoft's documentation on sys.dm_hadr_database_replica_states to understand the real columns and values this query relies on

12 Production Best Practices

Measure RPO against live replication state, never assume the documented target is automatically being met — exactly this project's central lesson.
Always distinguish "no replication data found" from "healthy, zero lag" — they represent very different, and very differently urgent, situations.
Reuse proven logic (like Project 17's backup validation) rather than reinventing it — composition of trusted prior work is a strength, not a shortcut.
Run genuine DR measurement on a real recurring schedule, not just during an annual, largely ceremonial review.

13 Interview Preparation

Q: Why measure actual replication lag instead of trusting the documented RPO target?
A documented target describes an intention, not a guarantee — as this project's story demonstrates, replication can silently break entirely while the documented commitment remains technically "in place" on paper, which is exactly the gap between an assumed and a measured DR posture.
Q: Why does DR readiness require BOTH healthy replication AND current backups, rather than either one alone?
Replication protects against a primary-site outage but faithfully propagates logical corruption to the secondary just as quickly as any legitimate change — independent, valid backups are what protect against that different failure mode, so genuine DR readiness needs both simultaneously.
Q: How does this project demonstrate the value of the earlier work in this academy?
It directly reuses Project 17's backup validation logic and Project 21's composite verdict philosophy rather than rebuilding either — concrete proof that a well-designed automation suite compounds in value as later projects genuinely build on and combine earlier ones.
Q: What's the most important thing this project still doesn't fully validate?
Actual RTO — how long a real failover and recovery would genuinely take — since that requires an actual failover exercise, not just a measurement of current state; this project measures RPO precisely but treats full RTO validation as a larger, separately-scoped future initiative.
