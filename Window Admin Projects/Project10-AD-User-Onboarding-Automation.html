Project 10 — Active Directory User Onboarding Automation

Ten new hires, one script, zero inconsistent accounts — and idempotent enough to run twice safely

Your first project touching Active Directory: bulk-create user accounts from an HR-provided CSV, place them in the right OU, generate secure temporary passwords, add them to the right groups — and, critically, never create a duplicate if the script accidentally runs twice.

01 The Production Story

A new kind of request from a new stakeholder — HR, not Priya's own team, but with the same production stakes.
Monday, 9:00 AM — HR Onboarding Meeting

ABC Bank is hiring 15 new employees for a branch expansion, all starting the same Monday in three weeks. HR's current process: an engineer manually creates each Active Directory account by hand — typing the name, generating a username, picking the right Organizational Unit for their department, setting a temporary password, and adding them to the right security groups for their role. For 15 people at once, that's a full day of repetitive, error-prone manual work, and it's happened before that a rushed manual entry left someone in the wrong group or without access to a system they needed on day one.

Priya loops you in. "HR is going to keep giving us these bulk onboarding lists — sometimes 2 people, sometimes 30. I want a script that takes a CSV of new hires — name, department, role, email — and creates every account consistently: right naming convention, right OU, right groups, a secure temporary password they have to change on first login. And here's the part that matters most in a bank: if someone re-runs this by accident, or the same person appears twice in two different HR exports, it must NEVER create a duplicate account or silently overwrite an existing one. Check first, always."

"This is our first project touching Active Directory directly — treat it with exactly that level of care."

This project creates real accounts with real access in a real identity system — the idempotency check (never acting on something that already exists) isn't a nice-to-have here, it's the single most important safety property of the whole script.

A PowerShell script using the ActiveDirectory module that checks for existing accounts first, then creates, places, and groups new ones from a CSV.

Phase 1 covers account creation, OU placement, group membership, and a secure temporary password — with strict duplicate protection.

A batch of 15 accounts goes from a full day of manual work to minutes, applied identically and safely every time.

03 New Concepts (Building on Projects 01–09)

You already know CSV-driven bulk operations and try/catch resilience. Here's what's new for Active Directory specifically.
The ActiveDirectory Module & Get-ADUser for Existence Checks

What it is: The ActiveDirectory PowerShell module (from RSAT, Remote Server Administration Tools) provides cmdlets like Get-ADUser, New-ADUser, and Add-ADGroupMember for managing AD objects directly.

Why Get-ADUser comes FIRST: Before creating anything, we check whether an account with that username already exists using Get-ADUser -Filter. This existence check is what makes the whole script idempotent — safe to run more than once without side effects.

New-ADUser — Creating the Account

What it is: Creates a new Active Directory user object with parameters like -Name, -SamAccountName (the login name), -UserPrincipalName (the email-style login), -Path (which OU to place it in), and -AccountPassword.

Why it's used today: This is the actual account-creation action — everything before it in the script exists to prepare safe, correct, validated inputs for this one call.

ConvertTo-SecureString — Handling Passwords Safely

What it is: AD cmdlets never accept a plain-text password directly — -AccountPassword requires a SecureString object, created with ConvertTo-SecureString -AsPlainText -Force.

Why it matters: A SecureString holds the password encrypted in memory rather than as plain readable text for as long as possible — reducing (though not eliminating) the window where a password sits in memory unprotected. It is not a substitute for a proper secrets vault in real production use.

Generating a Random Temporary Password

What it is: A small custom function that builds a password by randomly selecting characters from a defined character set using Get-Random, ensuring it meets complexity rules (upper, lower, number, symbol).

Why it's used today: Every new hire needs a unique, unguessable starting password, combined with -ChangePasswordAtLogon $true so they're forced to set their own on first login — nobody keeps the auto-generated one.

Add-ADGroupMember — Role-Based Group Assignment

What it is: Adds a user to one or more AD security groups, which is how role-based access (which systems and shares someone can reach) actually gets granted in most enterprise environments.

Why it's used today: Mapping "Department" from the HR CSV to the correct AD group is exactly the manual step most prone to human error in the current process — the story specifically calls this out.

ValidatePattern — Catching Bad Input Before It Reaches AD

What it is: A parameter validation attribute that checks a string against a regular expression before the function body runs — e.g. confirming an email address has a basic valid shape.

Why it's used today: HR data isn't always clean; catching an obviously malformed entry before attempting to create an AD account with it avoids partially-created or malformed accounts.

The single most important idea in this project: check before you act. Every AD-changing operation here is preceded by a check that confirms it's safe and necessary — this is the difference between automation you can trust with real identities and automation that's one accidental re-run away from an incident.

06 The Script — New-EmployeeAccounts.ps1

Scripts\New-EmployeeAccounts.ps1 
<#
.SYNOPSIS
    Bulk Active Directory Onboarding - ABC Bank Production Support
.DESCRIPTION
    Creates AD user accounts from an HR-provided CSV, checking for
    existing accounts first (idempotent), assigning department-based
    group membership, and generating secure temporary passwords.
#>

[CmdletBinding(SupportsShouldProcess)]                          # Reuse the -WhatIf safety pattern from Project 03
param()

Import-Module ActiveDirectory                                     # Loads Get-ADUser, New-ADUser, Add-ADGroupMember, etc.

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$NewHires       = Import-Csv -Path "C:\ADOnboarding\Config\new-hires.csv"
$GroupMapping   = Get-Content -Path "C:\ADOnboarding\Config\department-groups.json" -Raw | ConvertFrom-Json
$TargetOU       = "OU=Employees,OU=ABCBank,DC=abcbank,DC=internal"

$TimeTag   = Get-Date -Format 'yyyyMMdd_HHmmss'
$LogFile   = "C:\ADOnboarding\Logs\Onboarding_$TimeTag.log"
$ReportCSV = "C:\ADOnboarding\Reports\Onboarding_$TimeTag.csv"

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Stamp = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    $Entry = "[$Stamp] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: SECURE TEMPORARY PASSWORD GENERATOR
# ============================================================

function New-TemporaryPassword {
    $Upper  = 'ABCDEFGHJKLMNPQRSTUVWXYZ'.ToCharArray()      # Excludes easily-confused letters like I, O
    $Lower  = 'abcdefghjkmnpqrstuvwxyz'.ToCharArray()
    $Digits = '23456789'.ToCharArray()                    # Excludes 0 and 1, easily confused with O and l
    $Symbols = '!@#$%'.ToCharArray()

    $Password = -join (
        ($Upper   | Get-Random -Count 3) +                # 3 random uppercase letters
        ($Lower   | Get-Random -Count 4) +                # 4 random lowercase letters
        ($Digits  | Get-Random -Count 2) +                # 2 random digits
        ($Symbols | Get-Random -Count 1)                  # 1 random symbol — satisfies complexity requirements
    )
    return ($Password.ToCharArray() | Get-Random -Count $Password.Length) -join ""   # Shuffle so it's not always Upper-Lower-Digit-Symbol in order
}

# ============================================================
# SECTION 3: PER-EMPLOYEE ONBOARDING FUNCTION
# ============================================================

function New-EmployeeAccount {
    param(
        [string]$FirstName,
        [string]$LastName,
        [string]$Department,
        [ValidatePattern('^[\w\.\-]+@[\w\.\-]+\.\w+$')][string]$Email   # Basic shape check: something@something.something
    )

    $SamAccountName = ("$FirstName.$LastName").ToLower() -replace '\s',''   # e.g. "jordan.smith" — company's standard convention

    $Result = [PSCustomObject]@{
        SamAccountName = $SamAccountName
        FullName       = "$FirstName $LastName"
        Department     = $Department
        Action         = "NOT ATTEMPTED"
        GroupsAdded    = ""
        ProcessedAt    = Get-Date -Format "yyyy-MM-dd HH:mm:ss"
    }

    try {
        # ---- IDEMPOTENCY CHECK: DOES THIS ACCOUNT ALREADY EXIST? ----
        $Existing = Get-ADUser -Filter "SamAccountName -eq '$SamAccountName'" -ErrorAction SilentlyContinue

        if ($Existing) {
            Write-Log "$SamAccountName already exists. Skipping creation (idempotent, safe re-run)." "WARNING"
            $Result.Action = "SKIPPED - ALREADY EXISTS"
            return $Result                          # Stop here — NEVER modify or recreate an existing account in this script
        }

        # ---- LOOK UP THE RIGHT GROUPS FOR THIS DEPARTMENT ----
        $Groups = $GroupMapping.$Department
        if (-not $Groups) {
            Write-Log "$SamAccountName : unrecognized Department '$Department'. Account NOT created — needs manual review." "ERROR"
            $Result.Action = "FAILED - UNKNOWN DEPARTMENT"
            return $Result                          # Refuse to guess a group mapping — fail safe, not silently
        }

        if ($PSCmdlet.ShouldProcess($SamAccountName, "Create AD user account")) {   # WhatIf/Confirm safety from Project 03

            $TempPassword = New-TemporaryPassword
            $SecurePassword = ConvertTo-SecureString -String $TempPassword -AsPlainText -Force   # AD cmdlets require SecureString, never plain text

            # ---- CREATE THE ACCOUNT ----
            New-ADUser -Name "$FirstName $LastName" `
                       -SamAccountName $SamAccountName `
                       -UserPrincipalName $Email `
                       -GivenName $FirstName -Surname $LastName `
                       -Path $TargetOU `
                       -AccountPassword $SecurePassword `
                       -ChangePasswordAtLogon $true `                     # Forces the user to set their own password on first login
                       -Enabled $true

            Write-Log "$SamAccountName created in $TargetOU" "INFO"

            # ---- ADD TO DEPARTMENT-BASED GROUPS ----
            foreach ($Group in $Groups) {
                Add-ADGroupMember -Identity $Group -Members $SamAccountName
                Write-Log "$SamAccountName added to $Group" "INFO"
            }

            $Result.Action      = "CREATED"
            $Result.GroupsAdded = ($Groups -join ", ")
        }
        else {
            $Result.Action = "WHATIF - WOULD CREATE"
        }
    }
    catch {
        Write-Log "Error onboarding $SamAccountName : $($_.Exception.Message)" "ERROR"
        $Result.Action = "FAILED"
    }

    return $Result
}

# ============================================================
# SECTION 4: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Onboarding for $($NewHires.Count) new hire(s) =====" "INFO"

$AllResults = foreach ($Hire in $NewHires) {
    New-EmployeeAccount -FirstName $Hire.FirstName -LastName $Hire.LastName `
                         -Department $Hire.Department -Email $Hire.Email
}

$AllResults | Sort-Object Action | Format-Table -AutoSize

$AllResults | Export-Csv -Path $ReportCSV -NoTypeInformation

$FailedCount = ($AllResults | Where-Object { $_.Action -like "FAILED*" }).Count
if ($FailedCount -gt 0) {
    Write-Log "$FailedCount account(s) need manual review — see report" "WARNING"
}

Write-Log "===== Onboarding Completed. Report: $ReportCSV =====" "INFO"

07 Line-by-Line Explanation

$Existing = Get-ADUser -Filter "SamAccountName -eq '$SamAccountName'" -ErrorAction SilentlyContinue
This one line is the entire idempotency guarantee: it runs before anything else, and if it finds a match, the function returns immediately — no create, no modify, no group changes. Running the whole script twice on the same CSV produces the exact same end state as running it once.
[ValidatePattern('^[\w\.\-]+@[\w\.\-]+\.\w+$')][string]$Email
Rejects an obviously malformed email (missing @, no domain) before the function body even runs, at the parameter binding stage — PowerShell throws a clear validation error immediately rather than letting bad data reach New-ADUser.
ConvertTo-SecureString -String $TempPassword -AsPlainText -Force
The -Force flag is required specifically because using -AsPlainText is inherently a little risky (the source string briefly existed as plain text) — PowerShell requires this explicit acknowledgment rather than allowing it silently.
if (-not $Groups) { ... return $Result }
If the CSV's Department value doesn't match anything in department-groups.json, the script deliberately refuses to create an account with no group assignment — failing safely and flagging it for a human, rather than guessing or creating an under-provisioned account.
Common mistake: putting the existence check anywhere other than the very first step. If group assignment or password generation happened before the Get-ADUser check, a re-run could still cause partial side effects (like a duplicate password reset) even without creating a duplicate account.

08 Script Execution Flow

StepWhat Happens
1. Input ValidationValidatePattern rejects a malformed email before any AD interaction is even attempted for that record.
2. Existence CheckGet-ADUser queries Active Directory directly — this is a real-time check against the live directory, not a cached guess.
3. Department LookupThe JSON mapping is checked before any account creation — an unrecognized department fails safely rather than proceeding with no groups.
4. WhatIf GateShouldProcess decides whether to actually call New-ADUser or just report what would happen, exactly like Project 03's patch installer.
5. Account & Group CreationNew-ADUser creates the account object in AD; Add-ADGroupMember runs once per mapped group afterward.
6. ReportingEvery outcome — created, skipped, failed — lands in the same report, giving HR and IT a complete, auditable picture of the batch.

09 Windows Internals — In Simple English

What Active Directory Actually Is

Active Directory is a distributed directory database that stores every user, computer, and group in the organization as an object, replicated across domain controllers so any of them can answer a query like Get-ADUser.

Why OUs (Organizational Units) Matter

OUs are folders within AD used to organize objects and apply Group Policy consistently — placing a new account in the correct OU ensures it inherits the right security and configuration policies automatically.

How Group Membership Grants Access

Most enterprise systems check AD group membership to decide who can access what — adding a user to a group is often the actual mechanism that grants (or denies) access to a file share, application, or VPN.

12 Production Best Practices

Always check for existence before creating or modifying an identity object — idempotency is a safety requirement, not an optimization, for anything touching Active Directory.
Fail safely on unrecognized input (like an unknown department) rather than guessing — a human reviewing one flagged record beats an incorrectly-provisioned account.
Never store or log generated passwords in the main report — use a separate, access-restricted delivery mechanism.
Always force a password change at first logon for any automation-generated password — nobody should be using the auto-generated string long-term.

13 Interview Preparation

Q: Why is idempotency so critical for this specific script, more than most others in this series?
This script directly creates and modifies identity and access objects — accidentally re-running it, or processing a duplicate HR row, could create phantom accounts or duplicate access grants, which is a serious security and audit concern in a regulated bank.
Q: Why check for the department mapping BEFORE calling New-ADUser, rather than creating the account and fixing groups afterward?
Failing before any AD object is created avoids leaving a partially-provisioned account with no group access sitting in the directory — it's cleaner to never create it than to create and then need to remember to fix it.
Q: How does ConvertTo-SecureString actually protect a password, and what are its limits?
It reduces how long the password exists as plain, readable text in memory, but the string still originates from plain text in this script — for genuinely sensitive production secrets, a dedicated secrets vault with proper access controls is the stronger solution.
Q: What would you add before trusting this fully for a real 30-person onboarding batch?
A dry-run WhatIf review step built into the actual process (not just optional), a secure, separate password delivery mechanism, and likely a manager or HR sign-off step before the real run executes against production AD.

14 Key Learnings & Assignment

Key Learnings

  • Idempotency — check before you act — is non-negotiable for any script that creates or modifies identity objects
  • New-ADUser, Get-ADUser, and Add-ADGroupMember are the core building blocks for AD account lifecycle automation
  • ConvertTo-SecureString is required for AD password parameters, with real but limited protection
  • Failing safely on bad or unrecognized input beats guessing, especially for access-granting automation
