03 New Concepts (Building on Projects 01–25)

You already know reading reports and secure credential handling. Here's what's genuinely new: talking to a web API.
Invoke-RestMethod — PowerShell's Web API Client

What it is: A cmdlet that sends an HTTP request to a web API and automatically parses the JSON (or XML) response back into PowerShell objects — no manual parsing required, unlike a lower-level tool.

Why it's used today: Modern enterprise systems — ITSM platforms, cloud services, SaaS tools — overwhelmingly expose themselves through REST APIs. This is the single most broadly useful new skill in the whole academy for integrating PowerShell automation with literally anything outside the Windows/SQL/VMware ecosystem covered so far.

Building a JSON Request Body

What it is: Most REST APIs that create something (like a ticket) expect the request body as JSON — build a PowerShell hash table describing the ticket, then convert it with ConvertTo-Json before sending.

Why it's used today: This is the same JSON-handling skill from every config file read throughout this academy (ConvertFrom-Json), used here in the opposite direction — producing JSON to send, not just consuming it.

API Authentication — Headers and Tokens

What it is: REST APIs typically require an authentication token or API key sent in the request headers, rather than a username/password in the URL — Invoke-RestMethod -Headers @{ Authorization = "Bearer $Token" } is a common pattern.

Why it matters: Handling this credential safely follows the exact same "never hardcode a secret in plain text" discipline from Project 10's AD passwords — here applied to an API token instead.

Duplicate Suppression — Checking Before Creating

What it is: Before creating a new ticket, query the ITSM API for any existing open ticket referencing the same finding (e.g. by a consistent identifier embedded in the ticket description) — the same "check before you act" idempotency principle from Project 10's AD onboarding, applied here to avoid a flood of duplicate tickets for one ongoing issue.

A Fallback Path When the API Itself Fails

What it is: If the ITSM API is unreachable, the script falls back to Project 05's Send-MailMessage escalation pattern — ensuring a CRITICAL finding never simply vanishes just because one specific downstream system happens to be down at the wrong moment.

This project's biggest lesson: detection without a reliable path to action is incomplete monitoring. A truly mature automation suite doesn't stop at "we found the problem" — it ensures the problem enters a system that will actually track it to resolution.

The dashed line to the fallback path is deliberate — it only triggers if the primary API path itself fails, ensuring a genuine CRITICAL finding always reaches a human by some route, even if the preferred one is down.

06 The Script — New-IncidentFromFindings.ps1

Scripts\New-IncidentFromFindings.ps1 
<#
.SYNOPSIS
    Automated Incident Ticketing - ABC Bank Production Support
.DESCRIPTION
    Scans monitored reports for CRITICAL findings and automatically
    creates tickets in the ITSM system via its REST API, suppressing
    duplicates and falling back to email if the API is unreachable.
#>

# ============================================================
# SECTION 1: CONFIGURATION
# ============================================================

$ItsmConfig   = Get-Content -Path "C:\IncidentTicketing\Config\itsm-config.json" -Raw | ConvertFrom-Json
$MonitoredReports = Get-Content -Path "C:\IncidentTicketing\Config\monitored-reports.json" -Raw | ConvertFrom-Json
$LogFile  = "C:\IncidentTicketing\Logs\Ticketing_$(Get-Date -Format 'yyyyMMdd_HHmmss').log"

# The API token itself is never stored in plain text in config — retrieved securely at runtime
$ApiToken = (Get-Credential -Message "Enter ITSM API Token" -UserName "itsm-automation").GetNetworkCredential().Password

function Write-Log {
    param([string]$Message, [string]$Level = "INFO")
    $Entry = "[$(Get-Date -Format 'yyyy-MM-dd HH:mm:ss')] [$Level] $Message"
    Add-Content -Path $LogFile -Value $Entry
    Write-Host $Entry
}

# ============================================================
# SECTION 2: CHECK FOR AN EXISTING OPEN TICKET (DUPLICATE SUPPRESSION)
# ============================================================

function Test-ExistingTicket {
    param([string]$FindingId)                     # A consistent identifier for this specific finding, e.g. "SMB1-SRVAPP04"

    $Headers = @{ Authorization = "Bearer $ApiToken" }
    $Uri = "$($ItsmConfig.ApiBaseUrl)/tickets?search=$FindingId&status=open"

    try {
        $Response = Invoke-RestMethod -Uri $Uri -Method Get -Headers $Headers -TimeoutSec 15
        return ($Response.tickets.Count -gt 0)          # TRUE if a matching open ticket already exists
    }
    catch {
        Write-Log "Could not check for existing tickets: $($_.Exception.Message)" "ERROR"
        throw                                          # Let the caller decide how to handle an unreachable API
    }
}

# ============================================================
# SECTION 3: CREATE A TICKET VIA THE ITSM REST API
# ============================================================

function New-ItsmTicket {
    param([string]$FindingId, [string]$Title, [string]$Description, [string]$SourceProject)

    $Headers = @{ Authorization = "Bearer $ApiToken"; "Content-Type" = "application/json" }

    $Body = @{                                      # Build the ticket as a hash table first...
        short_description = $Title
        description        = "$Description`n`nFinding ID: $FindingId`nSource: $SourceProject (automated)"
        urgency            = "1"                          # Highest urgency — this is a CRITICAL finding by definition"Infrastructure"
    } | ConvertTo-Json                                         # ...then convert the whole thing to JSON for the request body

    $Uri = "$($ItsmConfig.ApiBaseUrl)/tickets"

    $Response = Invoke-RestMethod -Uri $Uri -Method Post -Headers $Headers -Body $Body -TimeoutSec 15
    return $Response.ticket_number                     # The API returns the newly created ticket's number
}

# ============================================================
# SECTION 4: FALLBACK — EMAIL ESCALATION IF THE API IS DOWN
# ============================================================

function Send-FallbackAlert {
    param([string]$Title, [string]$Description)
    try {
        Send-MailMessage -To "oncall-windowsops@abcbank.com" -From "automation@abcbank.com" `
            -Subject "[TICKETING API DOWN] $Title" -Body $Description -SmtpServer "smtp-relay.abcbank.internal"   # Same pattern as Project 05
        Write-Log "Fallback email sent for: $Title" "WARNING"
    }
    catch {
        Write-Log "FALLBACK EMAIL ALSO FAILED for: $Title — $($_.Exception.Message)" "ERROR"   # Both paths failed — the loudest possible log entry
    }
}

# ============================================================
# SECTION 5: MAIN EXECUTION
# ============================================================

Write-Log "===== Starting Incident Ticketing Sweep =====" "INFO"

foreach ($Source in $MonitoredReports) {
    $LatestReport = Get-ChildItem -Path $Source.ReportsFolder -Filter "*.csv" -ErrorAction SilentlyContinue |
        Sort-Object LastWriteTime -Descending | Select-Object -First 1

    if (-not $LatestReport) { continue }

    $CriticalFindings = Import-Csv -Path $LatestReport.FullName |
        Where-Object { $_.$($Source.StatusColumn) -like "*CRITICAL*" }

    foreach ($Finding in $CriticalFindings) {
        $FindingId = "$($Source.DomainName)-$($Finding.ServerName)"   # A consistent, reproducible ID for THIS specific finding

        try {
            if (Test-ExistingTicket -FindingId $FindingId) {
                Write-Log "$FindingId : ticket already open, skipping (duplicate suppression)" "INFO"
                continue
            }
            $TicketNumber = New-ItsmTicket -FindingId $FindingId -Title "CRITICAL: $($Source.DomainName) finding on $($Finding.ServerName)" `
                -Description ($Finding | Out-String) -SourceProject $Source.DomainName
            Write-Log "$FindingId : created ticket $TicketNumber" "INFO"
        }
        catch {
            Write-Log "$FindingId : ITSM API unreachable, falling back to email" "WARNING"
            Send-FallbackAlert -Title "CRITICAL: $($Source.DomainName) finding on $($Finding.ServerName)" -Description ($Finding | Out-String)
        }
    }
}

Write-Log "===== Incident Ticketing Sweep Completed =====" "INFO"

07 Line-by-Line Explanation

(Get-Credential -Message "Enter ITSM API Token" -UserName "itsm-automation").GetNetworkCredential().Password
Reuses Get-Credential — normally used for a username/password prompt — as a convenient, secure way to interactively capture a single secret value (the API token) without ever writing it to a script or config file in plain text; in a real scheduled/unattended run, this would instead pull from a proper secrets vault.
$Body = @{ ... } | ConvertTo-Json
Building the request body as a PowerShell hash table first, then converting to JSON only at the very end, keeps the code readable — you're working with familiar PowerShell syntax right up until the moment the API actually needs JSON specifically.
catch { Write-Log ... throw } inside Test-ExistingTicket
Re-throwing the error (rather than swallowing it) is deliberate — this function's caller (the main loop) needs to know the API check itself failed, so it can correctly fall back to email, rather than silently treating an API outage as "no duplicate found, proceed normally."
$FindingId = "$($Source.DomainName)-$($Finding.ServerName)"
A consistent, reproducible identifier built from stable values (domain and server name) is what makes duplicate suppression actually work — the same underlying finding produces the same FindingId on every run, letting Test-ExistingTicket reliably recognize "we've already ticketed this."
Common mistake: catching the ITSM API failure inside New-ItsmTicket itself and just logging it there, rather than letting the exception propagate to the main loop where the fallback email logic actually lives. Handling an error too early, in the wrong place, can silently prevent the fallback path from ever running.

08 Script Execution Flow

StepWhat Happens
1. Report ScanningEvery monitored project's latest report (same latest-file pattern as Projects 23–24) is scanned for CRITICAL findings.
2. Duplicate CheckBefore creating anything, the ITSM API is queried for an already-open ticket matching this specific finding's ID.
3. Ticket CreationA genuinely new finding triggers a real POST request, creating an actual tracked ticket in the ITSM system.
4. Fallback on API FailureIf either the duplicate check or ticket creation fails (the API itself is unreachable), the finding still reaches a human via the Project 05-style email fallback.
5. LoggingEvery outcome — created, suppressed as duplicate, or fell back to email — is logged distinctly, giving a complete audit trail of what happened to every single finding.

09 Windows Internals — In Simple English

How REST APIs Actually Work

A REST API exposes specific URLs ("endpoints") that respond to standard HTTP verbs — GET to retrieve data, POST to create something new — with the request and response bodies typically formatted as JSON, a lightweight, human-readable data format almost every modern system speaks.

Why Bearer Tokens Are Used Instead of Passwords

A bearer token is a temporary, revocable credential specifically scoped for API access — unlike a real user password, it can be issued with limited permissions and rotated or revoked independently, without affecting any human user's actual login credentials.

Why Duplicate Suppression Matters at API Scale

Without it, a persistent finding checked every hour would create a new ticket every single hour — quickly overwhelming the ITSM system with noise and actively working against the goal of focused, trustworthy accountability.

12 Production Best Practices

Always check for an existing open ticket before creating a new one — unsuppressed duplicates quickly erode trust in automated ticketing.
Never let a downstream integration's failure cause a finding to simply vanish — always have a fallback path, even a simple one, for when the primary integration is down.
Never store API tokens in plain text in a script or config file — use a proper secrets vault or, at minimum, an interactive secure prompt as this lab does.
Build a consistent, reproducible identifier for each distinct finding — reliable duplicate detection depends entirely on it.

13 Interview Preparation

Q: Why is detecting a problem not the same as actually solving the underlying monitoring gap?
A correctly detected finding that nobody acts on provides zero real protection — this project's story shows a genuinely correct detection sitting unactioned for days simply because nobody happened to open that specific report, which is functionally identical in outcome to never having detected it at all.
Q: Why re-throw the exception in Test-ExistingTicket instead of handling it locally?
The decision about what to do when the API is unreachable — specifically, falling back to email — belongs in the calling code, which has the full context; handling the error too early inside the helper function would prevent that fallback logic from ever running.
Q: How does duplicate suppression actually work here, and why does it matter at scale?
A consistent, reproducible FindingId lets the script query the ITSM system for an already-open ticket before creating a new one — without this, a persistent finding checked on every scheduled run would flood the ticketing system with duplicate tickets for the same underlying issue.
Q: What's a realistic next step to make this even more production-ready?
Adding retry-with-backoff (Project 05's pattern) around the API calls before falling back to email, so a brief transient network issue doesn't unnecessarily trigger the fallback path for what would have succeeded on a second attempt moments later.
