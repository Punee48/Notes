🏗️ Foundation: AWS + Terraform Basics

infrastructure as code · providers · state · first resource
📖 The Story

You sit down at your laptop. Before writing a single line of code, you ask yourself: "What IS infrastructure?" Servers, networks, databases, load balancers — everything your app needs to run. Traditionally, you'd click around the AWS console. But ShopNow needs repeatability, version control, and zero human error. That's where Terraform comes in — you describe infrastructure as code, and Terraform builds it.

☁️

What is AWS?

Amazon Web Services is a cloud platform providing 200+ services — compute, storage, networking, databases — all rented on-demand. You pay only for what you use.

🏗️

What is Terraform?

HashiCorp Terraform is an Infrastructure as Code (IaC) tool. You write declarative config files describing what you want, and Terraform figures out HOW to create it.

📋

Why IaC?

Version control your infra, reproduce environments instantly, review changes like code, never click the AWS console manually again. Teams collaborate on infra like they do on app code.

THE TERRAFORM WORKFLOW
1

terraform init

Downloads the provider plugins (AWS, Azure etc.) into .terraform/ folder. Like npm install — sets up dependencies. Run this FIRST in every project.

2

terraform plan

Reads your .tf files, compares with current state, and shows a preview of what will be CREATED (+), CHANGED (~), or DESTROYED (-). Like a dry run. ALWAYS review before applying.

3

terraform apply

Executes the plan. Makes API calls to AWS and creates your infrastructure. Updates the state file. Add -auto-approve in CI/CD to skip the yes/no prompt.

4

terraform destroy

Tears down ALL resources Terraform created. Use with caution in production. In CI/CD, you usually destroy test environments to save cost.

providers.tf — Telling Terraform to use AWS

providers.tf
# ── TERRAFORM BLOCK ────────────────────────────────────────────
# This is the meta-configuration for Terraform itself.
# It defines the version requirements and required providers.

terraform {

  # required_version pins the Terraform CLI version.
  # ">= 1.5.0" means "version 1.5.0 or higher is required".
  # This prevents junior devs from using old versions that
  # might behave differently. Always pin your versions!
  required_version = ">= 1.5.0"

  # required_providers tells Terraform WHICH plugins to download
  # during 'terraform init'. Each provider has its own registry.
  required_providers {

    # "aws" is the name we'll use to reference this provider.
    # source = "hashicorp/aws" means: download from
    # registry.terraform.io/hashicorp/aws
    aws = {
      source  = "hashicorp/aws"
      # "~> 5.0" means: any 5.x version (5.0, 5.1, 5.99)
      # but NOT 6.0. The "~>" operator = pessimistic constraint.
      version = "~> 5.0"
    }
  }
}

# ── PROVIDER BLOCK ─────────────────────────────────────────────
# This configures the AWS provider specifically.
# It's like logging into AWS — telling Terraform WHERE and WHO.

provider "aws" {

  # region = which AWS data center location to use.
  # "ap-south-1" = Mumbai, India (closest to Bengaluru!)
  # Other options: us-east-1 (Virginia), eu-west-1 (Ireland)
  # We use a variable here so we can change it without editing code.
  region = var.aws_region

  # default_tags applies these tags to EVERY resource we create.
  # Tags are like labels — crucial for cost tracking & organization.
  # "Environment" tag lets you filter dev vs prod resources in AWS console.
  default_tags {
    tags = {
      Project     = "ShopNow"
      ManagedBy   = "Terraform"      # So anyone seeing this knows NOT to edit manually
      Environment = var.environment  # "dev", "staging", or "production"
    }
  }
}

variables.tf — Defining Inputs

variables.tf
# ── VARIABLE DEFINITIONS ───────────────────────────────────────
# Variables make your Terraform code reusable and configurable.
# Think of them like function parameters — define them here,
# set their values in terraform.tfvars.

# "variable" keyword starts a variable block.
# "aws_region" is the NAME — we reference it as var.aws_region
variable "aws_region" {
  # description = human-readable explanation. Shown in terraform plan.
  # ALWAYS write descriptions — your future self will thank you.
  description = "AWS region to deploy all ShopNow resources"

  # type = what kind of data is this variable? 
  # string = plain text. Also: number, bool, list, map, object
  type        = string

  # default = value used if NOT provided in tfvars.
  # Mumbai region — great for India-based apps (low latency).
  default     = "ap-south-1"
}

variable "environment" {
  description = "Deployment environment (dev, staging, production)"
  type        = string
  default     = "dev"

  # validation block = enforce rules on variable values.
  # If someone passes "test" or "qa", Terraform will ERROR with
  # the error_message before doing ANYTHING. Catches mistakes early!
  validation {
    # condition = a boolean expression that must be TRUE.
    # contains() checks if a value exists in a list.
    # This ensures only "dev", "staging", or "production" is valid.
    condition     = contains(["dev", "staging", "production"], var.environment)
    error_message = "Environment must be dev, staging, or production."
  }
}

variable "project_name" {
  description = "Project name used as prefix in all resource names"
  type        = string
  default     = "shopnow"
}

# A map variable — like a dictionary/object in other languages.
# map(string) = key-value pairs where both key and value are strings.
variable "common_tags" {
  description = "Common tags applied to all resources"
  type        = map(string)
  default     = {
    Team  = "DevOps"
    Owner = "ShopNow Engineering"
  }
}
⚠️

NEVER hardcode secrets in variables.tf or terraform.tfvars! AWS Access Keys, passwords, API tokens — these should come from environment variables (TF_VAR_secret_key) or AWS Secrets Manager. Committing secrets to Git = security incident.

✅

Best Practice: terraform.tfvars Create a terraform.tfvars file for your values: aws_region = "ap-south-1" and environment = "dev". Add it to .gitignore if it contains secrets. Terraform auto-loads *.tfvars files.

🌐 Networking: VPC, Subnets & Routing

vpc · subnets · internet gateway · route tables · nat gateway
📖 The Story

Before launching any server, you need a network. Think of it like building ShopNow's office building before hiring anyone. The VPC is your private office building. Public subnets are rooms with windows to the street (internet-facing). Private subnets are the back rooms — secure, no direct internet access (your database lives here). The Internet Gateway is your front door. The NAT Gateway lets private rooms make outgoing calls without revealing their internal address.

networking.tf — Building the Entire Network Stack

networking.tf
# ═══════════════════════════════════════════════════════════════
# VPC — VIRTUAL PRIVATE CLOUD
# Your isolated network inside AWS. Like your own data center,
# but fully virtual. Every resource lives inside a VPC.
# ═══════════════════════════════════════════════════════════════

resource "aws_vpc" "main" {
  # cidr_block = IP address range for your entire network.
  # 10.0.0.0/16 gives us 65,536 IP addresses (10.0.0.0 → 10.0.255.255).
  # /16 = first 16 bits are fixed, last 16 bits = host addresses.
  # Rule: Pick a range that doesn't overlap with your office network.
  cidr_block = "10.0.0.0/16"

  # enable_dns_hostnames = gives EC2 instances a DNS name like:
  # ec2-13-126-x-x.ap-south-1.compute.amazonaws.com
  # Must be TRUE for RDS and many AWS services to work correctly.
  enable_dns_hostnames = true

  # enable_dns_support = enables AWS's internal DNS resolver.
  # Without this, resources CANNOT resolve each other by hostname.
  # Always set to true unless you have a custom DNS setup.
  enable_dns_support   = true

  tags = {
    # Name tag = what shows in the AWS Console. Very important!
    # "${var.project_name}-vpc" = "shopnow-vpc" (string interpolation)
    Name = "${var.project_name}-vpc"
  }
}

# ═══════════════════════════════════════════════════════════════
# INTERNET GATEWAY
# The door between your VPC and the public internet.
# Without this, NOTHING in your VPC can talk to the internet.
# Each VPC can have only ONE Internet Gateway.
# ═══════════════════════════════════════════════════════════════

resource "aws_internet_gateway" "main" {
  # vpc_id attaches this IGW to our VPC.
  # aws_vpc.main.id = the ID of the VPC resource defined above.
  # This is a RESOURCE REFERENCE — Terraform resolves dependencies
  # automatically. It will create the VPC BEFORE the IGW.
  vpc_id = aws_vpc.main.id

  tags = { Name = "${var.project_name}-igw" }
}

# ═══════════════════════════════════════════════════════════════
# PUBLIC SUBNETS — 2 in different Availability Zones (AZ)
# Subnets are subdivisions of your VPC.
# PUBLIC subnet = has route to Internet Gateway (internet-accessible).
# We create 2 for HIGH AVAILABILITY — if one AZ goes down, the other works.
# ═══════════════════════════════════════════════════════════════

resource "aws_subnet" "public" {
  # count = 2 creates TWO copies of this resource block.
  # Instead of writing aws_subnet "public_1" and "public_2" separately,
  # we use count to loop. Access them as aws_subnet.public[0] and [1].
  count = 2

  vpc_id = aws_vpc.main.id

  # cidrsubnet() = built-in Terraform function to calculate subnet CIDRs.
  # cidrsubnet("10.0.0.0/16", 8, count.index + 1)
  # - "10.0.0.0/16" = parent network
  # - 8 = add 8 more bits to prefix (so /16 + 8 = /24)
  # - count.index = 0 for first, 1 for second
  # Result: count=0 → 10.0.1.0/24 | count=1 → 10.0.2.0/24
  # Each /24 subnet has 256 IP addresses (254 usable).
  cidr_block = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index + 1)

  # availability_zone = which physical data center (within the region).
  # data.aws_availability_zones.available.names = list of AZ names:
  # ["ap-south-1a", "ap-south-1b", "ap-south-1c"]
  # count.index % 2 rotates between [0] and [1] → two different AZs.
  availability_zone = data.aws_availability_zones.available.names[count.index % 2]

  # map_public_ip_on_launch = TRUE means any EC2 launched here
  # automatically gets a PUBLIC IP address. This is what makes
  # a subnet "public" — resources can be reached from the internet.
  # For PRIVATE subnets, this is FALSE.
  map_public_ip_on_launch = true

  tags = { Name = "${var.project_name}-public-${count.index + 1}" }
}

# ── DATA SOURCE: Get list of available AZs in the region ───────
# "data" = read-only lookup of existing AWS info (no creation).
# This gets the available AZ names for whatever region we're in.
# Using data sources makes our code PORTABLE across regions.
data "aws_availability_zones" "available" {
  # state = "available" filters to only healthy AZs.
  # Excludes "unavailable" AZs that AWS might have issues with.
  state = "available"
}

# ── PRIVATE SUBNETS ─────────────────────────────────────────────
# App servers live here — NOT directly internet accessible.
# They can still reach the internet via NAT Gateway (one-way door).

resource "aws_subnet" "private" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  # 10.0.11.0/24 and 10.0.12.0/24 — offset by 10 from public
  cidr_block        = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index + 11)
  availability_zone = data.aws_availability_zones.available.names[count.index % 2]
  # FALSE — private subnet instances do NOT get public IPs.
  map_public_ip_on_launch = false
  tags = { Name = "${var.project_name}-private-${count.index + 1}" }
}

# ── DATABASE SUBNETS ─────────────────────────────────────────────
# Deepest layer — no internet, isolated from app servers.
resource "aws_subnet" "database" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index + 21)
  availability_zone = data.aws_availability_zones.available.names[count.index % 2]
  map_public_ip_on_launch = false
  tags = { Name = "${var.project_name}-db-${count.index + 1}" }
}

# ═══════════════════════════════════════════════════════════════
# ELASTIC IPs for NAT Gateways
# NAT Gateway needs a FIXED public IP address.
# Elastic IP = static public IP that doesn't change on restart.
# ═══════════════════════════════════════════════════════════════
resource "aws_eip" "nat" {
  count  = 2
  # domain = "vpc" means this EIP is for use inside a VPC.
  # (Old syntax was instance/vpc boolean — new Terraform uses this.)
  domain = "vpc"
  # depends_on ensures IGW exists before creating EIP.
  # Terraform usually figures this out, but explicit is safer.
  depends_on = [aws_internet_gateway.main]
  tags = { Name = "${var.project_name}-nat-eip-${count.index + 1}" }
}

# ═══════════════════════════════════════════════════════════════
# NAT GATEWAY
# Allows private subnet instances to REACH the internet
# (for updates, API calls) WITHOUT being reachable FROM internet.
# Like a one-way mirror — you can look out, nobody can look in.
# ═══════════════════════════════════════════════════════════════
resource "aws_nat_gateway" "main" {
  count = 2
  # allocation_id = the Elastic IP to attach to this NAT Gateway.
  # Each NAT GW needs its own EIP — hence count = 2 for both.
  allocation_id = aws_eip.nat[count.index].id
  # NAT Gateway MUST be in a PUBLIC subnet (it needs internet access).
  subnet_id     = aws_subnet.public[count.index].id
  tags = { Name = "${var.project_name}-nat-${count.index + 1}" }
}

# ═══════════════════════════════════════════════════════════════
# ROUTE TABLES — Traffic Routing Rules
# A route table = GPS for network traffic. 
# It says "traffic going to X.X.X.X/X should go through Y gateway".
# ═══════════════════════════════════════════════════════════════

# PUBLIC Route Table — routes ALL internet traffic through IGW
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    # cidr_block "0.0.0.0/0" = ALL traffic (default route / "catch-all").
    # This says: "Any traffic not destined for the VPC,
    # send it to the Internet Gateway."
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
  tags = { Name = "${var.project_name}-public-rt" }
}

# PRIVATE Route Tables — routes internet traffic through NAT Gateway
resource "aws_route_table" "private" {
  count  = 2
  vpc_id = aws_vpc.main.id

  route {
    cidr_block     = "0.0.0.0/0"
    # nat_gateway_id instead of gateway_id — routes through NAT.
    # Private instance → NAT Gateway → Internet Gateway → Internet
    nat_gateway_id = aws_nat_gateway.main[count.index].id
  }
  tags = { Name = "${var.project_name}-private-rt-${count.index + 1}" }
}

# ── ROUTE TABLE ASSOCIATIONS ──────────────────────────────────
# A route table doesn't do anything until you ASSOCIATE it
# with specific subnets. Like assigning a GPS to a car.

resource "aws_route_table_association" "public" {
  count          = 2
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table_association" "private" {
  count          = 2
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}
💡

Why 2 NAT Gateways? One per Availability Zone. If you use a single NAT Gateway and its AZ goes down, ALL private instances lose internet access. 2 NAT Gateways = HA (High Availability). Tradeoff: costs ~$32/month each.

⚡ Compute: EC2 & Security Groups

ec2 · ami · security groups · key pairs · user data
📖 The Story

The network is built. Now it's time to put servers inside it. EC2 (Elastic Compute Cloud) is AWS's virtual machine service. Security Groups are like bouncers at the door — they decide who gets IN and OUT. Key Pairs are like secure keycards — the only way to SSH into your instance. User Data is a startup script — commands that run automatically when the instance first boots.

compute.tf — EC2 Instance with Security Groups

compute.tf
# ═══════════════════════════════════════════════════════════════
# SECURITY GROUP FOR WEB SERVERS
# Security Groups = virtual firewalls for EC2 instances.
# Think of them as whitelists: DENY all by default, ALLOW specific traffic.
# ═══════════════════════════════════════════════════════════════

resource "aws_security_group" "web_server" {
  name        = "${var.project_name}-web-sg"
  description = "Security group for ShopNow web servers"
  # Attach this SG to our VPC — SGs are VPC-scoped.
  vpc_id      = aws_vpc.main.id

  # ── INGRESS RULES (INBOUND TRAFFIC) ──────────────────────────
  # ingress = traffic COMING IN to the instance

  ingress {
    # Allow HTTP on port 80 from ANYWHERE (0.0.0.0/0 = all IPv4).
    # This lets users browse your website via http://
    description = "HTTP from internet"
    from_port   = 80    # Start of port range
    to_port     = 80    # End of port range (same = single port)
    protocol    = "tcp" # TCP protocol (HTTP is TCP-based)
    cidr_blocks = ["0.0.0.0/0"]  # from ALL internet IPs
  }

  ingress {
    # Allow HTTPS on port 443 — encrypted web traffic.
    description = "HTTPS from internet"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    # SSH on port 22 — ONLY from your office IP.
    # NEVER open SSH to 0.0.0.0/0 — you WILL be attacked!
    # Replace "YOUR_OFFICE_IP/32" with your actual IP address.
    description = "SSH from office only"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = [var.office_ip_cidr]  # e.g. "1.2.3.4/32"
  }

  # ── EGRESS RULES (OUTBOUND TRAFFIC) ──────────────────────────
  # egress = traffic LEAVING the instance.
  # This allows ALL outbound traffic (typical — restricting
  # egress is usually done at the network/firewall level).
  egress {
    from_port   = 0          # 0 = all ports
    to_port     = 0
    protocol    = "-1"       # "-1" = ALL protocols (TCP, UDP, ICMP...)
    cidr_blocks = ["0.0.0.0/0"]  # to everywhere
  }

  tags = { Name = "${var.project_name}-web-sg" }
}

# ── DATA SOURCE: Find the Latest Amazon Linux 2023 AMI ─────────
# Instead of hardcoding "ami-0abcdef1234567890" (which changes by region!),
# we QUERY AWS for the latest AMI automatically.
# This keeps your code always up-to-date and region-portable.

data "aws_ami" "amazon_linux" {
  # most_recent = true → if multiple AMIs match, pick the newest.
  most_recent = true
  # owners = ["amazon"] → only trust AMIs published by Amazon.
  # Never use unverified community AMIs in production — security risk!
  owners      = ["amazon"]

  filter {
    # Filter by name pattern — matches Amazon Linux 2023 AMIs.
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }

  filter {
    # Only HVM (Hardware Virtual Machine) type — required for modern instances.
    name   = "virtualization-type"
    values = ["hvm"]
  }
}

# ═══════════════════════════════════════════════════════════════
# KEY PAIR — For SSH Access
# You generate a key pair locally, upload the PUBLIC key to AWS.
# Keep the PRIVATE key safe — it's your only way to log in.
# ═══════════════════════════════════════════════════════════════

resource "aws_key_pair" "shopnow" {
  key_name   = "${var.project_name}-key"
  # public_key = contents of your ~/.ssh/id_rsa.pub file.
  # file() = Terraform function that reads a local file's contents.
  # NEVER commit the private key — only the public key goes here.
  public_key = file("~/.ssh/shopnow.pub")
}

# ═══════════════════════════════════════════════════════════════
# EC2 INSTANCE — The Web Server
# This creates a virtual machine running Amazon Linux 2023
# in one of our private subnets, with the web server software
# automatically installed via user_data.
# ═══════════════════════════════════════════════════════════════

resource "aws_instance" "web_server" {
  # ami = Amazon Machine Image — the OS snapshot/template.
  # We reference our data source above instead of hardcoding.
  ami           = data.aws_ami.amazon_linux.id

# APPLICATION LOAD BALANCER (ALB)
# Receives all incoming HTTP/HTTPS traffic and distributes it
# across multiple EC2 instances using algorithms (round-robin etc.)
# ═══════════════════════════════════════════════════════════════

resource "aws_lb" "main" {
  name               = "${var.project_name}-alb"
  # internal = false means this is INTERNET-FACING.
  # internal = true for internal/private load balancers (microservices).
  internal           = false
  # load_balancer_type = "application" = ALB (HTTP/HTTPS, path routing).
  # "network" = NLB (TCP/UDP, ultra-low latency).
  # "gateway" = GWLB (for firewalls/inspection appliances).
  load_balancer_type = "application"
  # Security group controls what traffic reaches the ALB.
  # We allow HTTP (80) and HTTPS (443) from internet.
  security_groups    = [aws_security_group.alb.id]

  # Splat [*].id returns all public subnet IDs as a list.

# ── TARGET GROUP ─────────────────────────────────────────────
# A Target Group is a LIST of servers that the ALB sends traffic to.
# Each group has health check settings — unhealthy targets are removed.
resource "aws_lb_target_group" "web" {

  vpc_id   = aws_vpc.main.id

  # If it returns HTTP 200, the instance is "healthy" and receives traffic.
  # If it fails 3 times, the instance is "unhealthy" and removed.
  health_check {
    enabled             = true
    path                = "/health"    # Your app MUST respond to GET /health
    port                = "traffic-port"  # Same as the target group port
    protocol            = "HTTP"
    healthy_threshold   = 2   # 2 consecutive successes = healthy
    unhealthy_threshold = 3   # 3 consecutive failures = unhealthy
    timeout             = 5   # Wait 5 seconds for response
    interval            = 30  # Check every 30 seconds
    matcher             = "200"  # HTTP 200 = success
  }
}

# Monitors a specific metric and fires when it crosses a threshold.
# ═══════════════════════════════════════════════════════════════

# ALARM 1: High CPU on EC2 instances
resource "aws_cloudwatch_metric_alarm" "high_cpu" {
  alarm_name          = "${var.project_name}-high-cpu"
  alarm_description   = "EC2 average CPU > 80% for 10 minutes"

  # namespace = which AWS service's metrics to watch.
  # "AWS/EC2" = EC2 metrics. "AWS/RDS" = RDS metrics.
  namespace           = "AWS/EC2"
  # metric_name = specific metric within the namespace.
  # CPUUtilization = 0-100% CPU usage of the instance.
  metric_name         = "CPUUtilization"

  # dimensions = filter to WHICH resource.
  # Without this, it'd watch ALL EC2 instances in your account!
  dimensions = {
    AutoScalingGroupName = aws_autoscaling_group.web.name
  }

  # statistic = how to aggregate the metric over the period.
  # "Average" = mean CPU across all instances in the ASG.
  # Others: "Sum", "Maximum", "Minimum", "SampleCount"
  statistic           = "Average"
  # period = how many SECONDS per data point. 300 = 5 minutes.
  period              = 300
  # evaluation_periods = how many consecutive periods must breach.
  # 2 = alarm only fires if CPU > 80% for 2 consecutive 5-min periods = 10 min.
  # Prevents false alarms from momentary spikes.
  evaluation_periods  = 2
  # threshold = the value to compare against.
  # comparison_operator: "GreaterThanThreshold" = alert if metric > threshold.
  threshold           = 80
  comparison_operator = "GreaterThanThreshold"

  # alarm_actions = what to DO when alarm fires.
  # Here: send to SNS topic → email your team.
  alarm_actions       = [aws_sns_topic.alerts.arn]
  # ok_actions = what to do when alarm RECOVERS (returns to normal).
  ok_actions          = [aws_sns_topic.alerts.arn]
}

🚀 CI/CD: GitHub Actions Pipeline

github actions · automated terraform · pr checks · environment protection
📖 The Story

ShopNow's infra is working, but deploying changes manually is risky and slow. CI/CD (Continuous Integration/Continuous Delivery) automates the entire process. Every Pull Request automatically runs terraform plan — the team reviews changes before merging. Merging to main automatically runs terraform apply — infrastructure updates deploy themselves. No more SSH sessions, no more manual clicks. Pure automation.

.github/workflows/terraform.yml — Full CI/CD Pipeline

.github/workflows/terraform.yml
# ═══════════════════════════════════════════════════════════════
# GITHUB ACTIONS WORKFLOW — Automated Terraform CI/CD
# This file defines automated jobs that run on GitHub's servers.
# Triggers on: pull requests (plan) and merges to main (apply).
# ═══════════════════════════════════════════════════════════════

# name = what this workflow is called (shown in GitHub UI)
name: Terraform Infrastructure CI/CD

# "on" = WHEN does this workflow run?
on:
  # pull_request: trigger when a PR is opened/updated targeting 'main'
  pull_request:
    branches: [main]
    paths:
      # Only run if Terraform files changed — skip for README edits
      - '**/*.tf'
      - '**/*.tfvars'
  # push: trigger when code is pushed/merged to 'main'
  push:
    branches: [main]
    paths:
      - '**/*.tf'
      - '**/*.tfvars'

# env = environment variables available to ALL jobs
env:
  # TF_VERSION = which Terraform version to install
  TF_VERSION: '1.6.0'
  # AWS_REGION = where to deploy
  AWS_REGION: 'ap-south-1'
  # TF_WORKING_DIR = where our .tf files live
  TF_WORKING_DIR: './infrastructure'

# jobs = the actual work to do
jobs:

  # ── JOB 1: TERRAFORM PLAN (runs on every PR) ────────────────
  terraform-plan:
    name: Terraform Plan
    # runs-on = what machine to use. ubuntu-latest = free Linux VM on GitHub.
    runs-on: ubuntu-latest
    # Only run this job on Pull Requests (not on direct pushes to main)
    if: github.event_name == 'pull_request'

    # permissions = what GitHub token can do.
    # pull-requests:write = allows the workflow to post PR comments (plan output).
    # id-token:write = allows OIDC authentication with AWS (no keys needed!).
    permissions:
      pull-requests: write
      id-token: write  # Required for OIDC AWS auth
      contents: read

    # steps = sequential tasks within the job
    steps:

      # STEP 1: Checkout — download your code onto the runner VM
      - name: 📥 Checkout Code
        # "uses" = reference a pre-built Action from GitHub Marketplace
        uses: actions/checkout@v4

      # STEP 2: AWS Authentication via OIDC (NO ACCESS KEYS IN CODE!)
      # OIDC = OpenID Connect. GitHub proves its identity to AWS.
      # AWS trusts GitHub → issues temporary credentials automatically.
      # This is the SECURE way — no long-lived access keys stored in GitHub.
      - name: 🔐 Configure AWS Credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          # role-to-assume = which IAM role to use.
          # GitHub will get temporary credentials for this role.
          # Stored as a GitHub Secret: Settings → Secrets → AWS_ROLE_ARN
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
          # role-session-name = name shown in AWS CloudTrail audit logs
          role-session-name: GitHubActions-Plan-${{ github.run_id }}

      # STEP 3: Install Terraform CLI
      - name: 🏗️ Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      # STEP 4: terraform init — download providers & initialize backend
      - name: ⚡ Terraform Init
        working-directory: ${{ env.TF_WORKING_DIR }}
        run: |
          terraform init \
            -backend-config="bucket=${{ secrets.TF_STATE_BUCKET }}" \
            -backend-config="region=${{ env.AWS_REGION }}"

      # STEP 5: terraform fmt -check — ensures code is properly formatted.
      # Fails if anyone committed unformatted code. Enforces standards.
      - name: 🎨 Terraform Format Check
        working-directory: ${{ env.TF_WORKING_DIR }}
        run: terraform fmt -check -recursive

      # STEP 6: terraform validate — checks syntax and config validity.
      # Catches errors without contacting AWS API.
      - name: ✅ Terraform Validate
        working-directory: ${{ env.TF_WORKING_DIR }}
        run: terraform validate

      # STEP 7: terraform plan — show what WOULD change.
      # -out=tfplan saves the plan to a file (used in apply step).
      # id: plan — gives this step an ID so other steps can reference its output.
      - name: 📋 Terraform Plan
        id: plan
        working-directory: ${{ env.TF_WORKING_DIR }}
        run: |
          terraform plan \
            -var="environment=production" \
            -out=tfplan \
            -no-color 2>&1 | tee plan_output.txt
        # continue-on-error:true = don't fail the workflow if plan fails.
        # We want to post the error in the PR comment regardless.
        continue-on-error: true

      # STEP 8: Post plan output as a PR comment for review.
      # Team members can see exactly what will change before approving.
      - name: 💬 Post Plan to PR
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('${{ env.TF_WORKING_DIR }}/plan_output.txt', 'utf8');
            const status = '${{ steps.plan.outcome }}' === 'success' ? '✅' : '❌';
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## ${status} Terraform Plan\n\`\`\`hcl\n${plan}\n\`\`\``
            });

  # ── JOB 2: TERRAFORM APPLY (runs on merge to main) ──────────
  terraform-apply:
    name: Terraform Apply
    runs-on: ubuntu-latest
    # Only run on direct pushes to main (i.e., merged PRs)
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    # environment = links to GitHub Environments feature.
    # Allows required reviewers before deployment! 
    # Set up in: Settings → Environments → production → Required reviewers
    environment: production

    permissions:
      id-token: write
      contents: read

    steps:
      - name: 📥 Checkout
        uses: actions/checkout@v4

      - name: 🔐 Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: 🏗️ Setup Terraform
        uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}

      - name: ⚡ Terraform Init
        working-directory: ${{ env.TF_WORKING_DIR }}
        run: terraform init

      # -auto-approve = don't prompt for "yes" confirmation (needed in CI)
      # ONLY safe because we reviewed the plan in the PR step already!
      - name: 🚀 Terraform Apply
        working-directory: ${{ env.TF_WORKING_DIR }}
        run: |
          terraform apply \
            -var="environment=production" \
            -auto-approve \
            -no-color
✅

OIDC vs Access Keys: Never store AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY as GitHub Secrets. Use OIDC instead — GitHub gets temporary 1-hour credentials automatically. Zero long-lived keys to rotate or accidentally leak.

📖 The Story

ShopNow grows. You now need to manage dev, staging, and production environments. Copy-pasting Terraform code for each environment = nightmare. backend.tf — Remote State with S3 + DynamoDB Locking

backend.tf
# ═══════════════════════════════════════════════════════════════
# REMOTE BACKEND — Store State in S3 with DynamoDB Locking
# 
# Without remote backend: state is in local terraform.tfstate file.
# Problems: can't collaborate, accidental deletion, no locking.
#
# With remote backend:
# - State stored in S3 (versioned, durable, encrypted)
# - DynamoDB table prevents concurrent applies (locking)
# - Team members always use the SAME state file
# ═══════════════════════════════════════════════════════════════

terraform {
  backend "s3" {
    # bucket = S3 bucket to store the state file.
    # Create this bucket MANUALLY first (or with a bootstrap script).
    # You can't use Terraform to create the bucket that stores its own state!
    bucket  = "shopnow-terraform-state-prod"

    # key = the path/filename of the state file within the bucket.
    # Using environment in the path separates dev/prod state files.
    key     = "shopnow/production/terraform.tfstate"

    region  = "ap-south-1"

    # encrypt = encrypt the state file at rest in S3.
    # State files contain SENSITIVE data (passwords, IPs)!
    # ALWAYS encrypt.
    encrypt = true

    # dynamodb_table = for state LOCKING.
    # When 'terraform apply' starts, it writes a LOCK RECORD to DynamoDB.
    # If someone else runs apply simultaneously → they get:
    # "Error: Error acquiring the state lock"
    # When apply finishes (success or fail), lock is released.
    dynamodb_table = "shopnow-terraform-locks"
  }
}

# ── CREATE THE DYNAMODB LOCK TABLE (bootstrap only) ──────────
# Run this ONCE with local state, THEN migrate to S3 backend.
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "shopnow-terraform-locks"
  # billing_mode = "PAY_PER_REQUEST" = serverless pricing.
  # Only pay when lock records are written/read. Very cheap for this use case.
  billing_mode = "PAY_PER_REQUEST"
  # hash_key = the primary key of the table.
  # Terraform REQUIRES this to be "LockID" — it's hardcoded in Terraform.
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    # type = "S" = String. DynamoDB attribute types: S (string), N (number), B (binary)
    type = "S"
  }

  tags = { Name = "Terraform State Lock Table" }
}

# ═══════════════════════════════════════════════════════════════
# TERRAFORM MODULE — Reusable VPC
# A module is just a directory containing .tf files.
# Call it from your root with:
#   module "vpc" {
#     source = "./modules/vpc"
#     cidr   = "10.0.0.0/16"
#   }
# 
# Modules = DRY (Don't Repeat Yourself) for infrastructure.
# Write once → use for dev, staging, production environments.
# ═══════════════════════════════════════════════════════════════

# Module inputs — caller must provide these values
variable "vpc_cidr"       { type = string }
variable "environment"    { type = string }
variable "project_name"   { type = string }
variable "public_subnets" {
  type    = list(string)
  default = ["10.0.1.0/24", "10.0.2.0/24"]
}

resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true
  tags = { Name = "${var.project_name}-${var.environment}-vpc" }
}

# for_each — more powerful than count for creating named resources.
# Instead of count = 2 giving us [0] and [1],
# for_each = toset(var.public_subnets) gives us named keys.
# Access with: aws_subnet.public["10.0.1.0/24"].id
resource "aws_subnet" "public" {
  # toset() converts a list to a set (removes duplicates, enables for_each)
  for_each = toset(var.public_subnets)

  vpc_id     = aws_vpc.this.id
  # each.key = the current item from the for_each set (the CIDR string)
  cidr_block = each.key
  map_public_ip_on_launch = true
  tags = { Name = "${var.project_name}-public-${each.key}" }
}

# Module outputs — expose values for the caller to use
output "vpc_id" {
  description = "The ID of the created VPC"
  value       = aws_vpc.this.id
}

output "public_subnet_ids" {
  description = "IDs of all public subnets"
  # values() = get all values from a map. 
  # for_each creates a map: {cidr: subnet_resource}
  # values() extracts all the subnet resources, then [*].id gets their IDs.
  value       = values(aws_subnet.public)[*].id
}
