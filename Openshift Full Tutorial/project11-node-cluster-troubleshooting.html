1. The Production Story

Scenario The payment-api platform has been stable for months. This morning, on-call gets paged: node-worker-03 is NotReady, and shortly after, one ClusterOperator shows Degraded. The team has never had a standard first-response playbook for node/cluster-level issues — everyone improvises with a different set of oc commands.
Business Problem Inconsistent incident response means some engineers miss key diagnostic steps under pressure, extending outages longer than necessary.
Our Mandate Build a read-only Ansible cluster-health playbook that any on-call engineer can run first, producing a structured triage report — then use it live on today's two incidents.

3. Architecture

ConceptOpenShift's control plane health is layered: individual Nodes report Ready/NotReady based on kubelet heartbeats and condition checks (disk/memory/PID pressure); ClusterOperators report on the health of platform components (networking, ingress, etcd, etc.); ClusterVersion reports overall upgrade/reconciliation state. A single incident can show symptoms at one or all three layers.
Node conditions (Ready, MemoryPressure, DiskPressure, PIDPressure) │ aggregated by ▼ kubelet → API Server → Node object status │ ▼ ClusterOperators (network, ingress, kube-apiserver, etcd, ...) │ each reports: Available / Progressing / Degraded ▼ ClusterVersion — overall cluster health/upgrade state │ ▼ Our Ansible triage playbook queries ALL THREE layers in one pass
LayerCommandWhat it tells you
Nodeoc get nodes, oc describe nodeIs the machine itself healthy and schedulable?
ClusterOperatoroc get clusteroperatorsIs a specific platform component (e.g. ingress, etcd) healthy?
ClusterVersionoc get clusterversionIs the cluster fully reconciled / mid-upgrade / failing to progress?

4. The Playbooks — Fully Commented

4.1 playbooks/cluster_health.yml

playbooks/cluster_health.yml
---
# READ-ONLY triage playbook -- every task here only queries state,
# never modifies the cluster. Safe for any on-call engineer to run
# first, before any remediation action.
- name: OpenShift cluster health triage
  hosts: localhost
  connection: local
  gather_facts: true                                                    # need ansible_date_time for the report timestamp

  tasks:
    - name: Query all Node objects                                       # read-only fetch of every node's live status
      kubernetes.core.k8s_info:                                           # info module -- guarantees no mutation
        kind: Node                                                        # cluster-scoped object type
      register: nodes                                                     # holds full Node list with .status.conditions

    - name: Identify NotReady nodes                                       # filter down to just the problem nodes
      ansible.builtin.set_fact:
        not_ready_nodes: >-
          {{ nodes.resources | selectattr('status.conditions', 'defined')
             | map(attribute='status.conditions')
             | map('selectattr', 'type', 'equalto', 'Ready')
             | map('first')
             | zip(nodes.resources | map(attribute='metadata.name'))
             | selectattr('0.status', 'ne', 'True')
             | map(attribute='1') | list }}                                # pulls out just the names of nodes whose Ready condition isn't True

    - name: Query all ClusterOperators                                     # platform component health
      kubernetes.core.k8s_info:
        kind: ClusterOperator                                               # OpenShift-specific cluster-scoped object
        api_version: config.openshift.io/v1                                 # config API group
      register: cluster_operators                                           # holds every operator's status.conditions

    - name: Identify Degraded ClusterOperators                               # filter to just the unhealthy ones
      ansible.builtin.set_fact:
        degraded_operators: >-
          {{ cluster_operators.resources
             | selectattr('status.conditions', 'defined')
             | map(attribute='status.conditions')
             | map('selectattr', 'type', 'equalto', 'Degraded')
             | map('first', default={'status':'False'})
             | zip(cluster_operators.resources | map(attribute='metadata.name'))
             | selectattr('0.status', 'equalto', 'True')
             | map(attribute='1') | list }}                                  # names of operators whose Degraded condition is True

    - name: Query ClusterVersion                                              # overall cluster reconciliation state
      kubernetes.core.k8s_info:
        kind: ClusterVersion
        api_version: config.openshift.io/v1
        name: version                                                          # fixed, well-known singleton name
      register: cluster_version                                                # holds .status.conditions and current version

    - name: Build and write the triage report                                  # human-readable summary, not a cluster change
      ansible.builtin.copy:                                                     # writes a local file, NOT a k8s object -- purely local output
        dest: "./cluster-health-report.txt"                                     # relative to where ansible-playbook was run
        content: |
          Cluster Health Triage Report — {{ ansible_date_time.iso8601 }}
          =====================================================
          NotReady Nodes: {{ not_ready_nodes | length }}
          {{ not_ready_nodes | join(', ') if not_ready_nodes else '  (none)' }}

          Degraded ClusterOperators: {{ degraded_operators | length }}
          {{ degraded_operators | join(', ') if degraded_operators else '  (none)' }}

          ClusterVersion: {{ cluster_version.resources[0].status.desired.version }}

    - name: Surface a clear warning in play output if anything is unhealthy       # fails the play visibly -- useful in CI/scheduled runs
      ansible.builtin.fail:
        msg: "Cluster health issues found -- see cluster-health-report.txt"
      when: (not_ready_nodes | length > 0) or (degraded_operators | length > 0)   # only fails if something is actually wrong

NoteThis playbook is intentionally NOT idempotency-tested in the usual "changed=0" sense — it makes zero changes on every run by design. Its output changing between runs reflects real cluster state, not a bug.

6. Live Incident — NotReady Node + Degraded ClusterOperator

7:02 AM — PageAlert fires for node-worker-03 NotReady.
Step 1 — run the triage playbook first, always
ansible-playbook playbooks/cluster_health.yml
cat cluster-health-report.txt
NotReady Nodes: 1
  node-worker-03
Degraded ClusterOperators: 1
  image-registry

Both symptoms confirmed in one read-only pass — now we know the scope before touching anything.

Step 2 — investigate the node
oc describe node node-worker-03
Conditions:
  Type             Status
  MemoryPressure   True
  DiskPressure     False
  Ready            False

Events:
  Warning  NodeHasInsufficientMemory  kubelet reports insufficient memory
Step 3 — check what's consuming memory on the node
oc adm top node node-worker-03
NAME              CPU    MEMORY   MEMORY%
node-worker-03    340m   15872Mi  98%

oc get pods -A --field-selector spec.nodeName=node-worker-03 -o wide
# a batch analytics job (unrelated to payment-api) was scheduled here without memory limits
Root cause (node)An unrelated batch job with no memory limit consumed nearly all available memory on the node, triggering kubelet's MemoryPressure condition and evicting/blocking other workloads — including pods the image-registry operator depends on for that zone.
Step 4 — connect the dots to the Degraded ClusterOperator
oc describe clusteroperator image-registry
Message: Degraded: unable to schedule registry pod: node-worker-03 under memory pressure,
  no other node available in this zone
Step 5 — mitigate: evict/kill the offending workload, let kubelet recover
oc delete pod batch-job-7f2a -n analytics
# kubelet clears MemoryPressure once usage drops below the eviction threshold
Step 6 — re-run the triage playbook to confirm recovery
ansible-playbook playbooks/cluster_health.yml
PLAY RECAP *** ok=6 changed=0 failed=0   # no failure = fully healthy again
7:34 AM — ResolvedNode returned to Ready, image-registry operator recovered automatically once scheduling was possible again.

RCA Summary

FieldDetail
ImpactOne node NotReady ~32 min; image-registry Degraded for the same window
Root causeAn unrelated batch job with no memory limit exhausted node memory, cascading into a platform ClusterOperator
FixEvicted the offending pod; kubelet self-recovered once pressure cleared
Preventive actionEnforce a namespace-level LimitRange (Project 1 pattern) on the analytics namespace so this class of workload can never go unbounded again

7. Additional Break-Fix Labs

Break-Fix — kubelet certificate expired 
oc get csr | grep Pending
oc describe node node-worker-04
Ready condition unknown -- kubelet stopped posting node status

Root cause: node's kubelet serving certificate expired and wasn't auto-approved. Fix: oc get csr, review, then oc adm certificate approve <csr-name> for legitimate pending requests.

Break-Fix — ClusterVersion stuck, not progressing 
oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING   SINCE
version   4.15.2     True        True          4h

oc describe clusterversion
Unable to apply 4.15.3: the cluster operator monitoring is degraded

Root cause: an upgrade is blocked because a specific ClusterOperator won't go healthy. Fix: resolve the named operator's Degraded condition first — upgrades will not proceed past a Degraded operator by design, which is a safety feature, not a bug.

8. Security Review

ControlDetail
Read-only by designThe triage playbook uses only k8s_info — impossible to accidentally change cluster state during an incident
Least privilege for triageOnly needs read access to Nodes/ClusterOperators/ClusterVersion — narrower than full cluster-admin
Blast-radius containmentPreventive LimitRange enforcement prevents one misbehaving namespace from affecting platform components again

9. Interview Preparation

Interviewer: "A node is NotReady — what do you check?"

Answer: oc describe node first — the Conditions section shows exactly which pressure condition tripped (Memory/Disk/PID) and Events usually names the trigger. In one real incident, MemoryPressure was caused by an unrelated batch job with no memory limit running on that node, which also cascaded into a Degraded ClusterOperator whose pods couldn't be scheduled anywhere in that zone.

Interviewer: "Why start every incident with a read-only playbook instead of jumping straight to fixes?"

Answer: It establishes full scope in one consistent pass before anyone touches anything — otherwise you risk fixing the symptom you happened to notice first while missing a related, causally-connected issue elsewhere, like the ClusterOperator in this case.
