1. The Production Story

Scenario The database team asks platform engineering to raise the kernel's vm.max_map_count on worker nodes — a common requirement for database and search workloads with heavy memory-mapped I/O, including the PostgreSQL cluster from Project 7. This is a node OS-level change, not something a Deployment manifest can set.
Business Problem A previous engineer tried to "fix this fast" by SSHing into a worker node and running sysctl directly. It worked — until that node was rebooted during a routine upgrade, and the setting silently reverted, causing an outage nobody understood for hours.
Our Mandate Make this change the declarative, correct way — via MachineConfig — so it survives reboots and node replacement, and Ansible's role is to author and apply the MachineConfig, then get out of the way and let OpenShift's Machine Config Operator handle the actual node-by-node rollout.

3. Architecture

ConceptMachineConfigs are rendered into a single combined config per MachineConfigPool (typically master and worker). The Machine Config Operator (MCO) — not Ansible — handles the actual node-by-node cordon, drain, apply, and reboot sequence, one node at a time by default, to avoid taking down the whole pool simultaneously.
Ansible applies a MachineConfig object (declarative intent) │ ▼ Machine Config Controller renders it into the pool's combined config │ ▼ Machine Config Operator, PER NODE in the pool: 1. Cordon the node (no new pods scheduled) 2. Drain existing pods (respecting PodDisruptionBudgets) 3. Apply the new config (write files, run the sysctl, etc.) 4. Reboot the node 5. Uncordon once healthy │ ▼ Repeats for the NEXT node -- one at a time, not all simultaneously
ConceptDetail
MachineConfigDeclares files, systemd units, or kernel args to apply at the OS level via Ignition
MachineConfigPool (MCP)Groups nodes (master/worker/custom) and tracks their rollout status together
maxUnavailableHow many nodes in the pool can be updating simultaneously (default 1)
Rendered configMCO merges all MachineConfigs targeting a pool into one combined, versioned config
MachineConfig vs Ansible — where the line isAnsible's job is to declare and apply the desired MachineConfig object. The actual node drain/reboot orchestration is OpenShift's own job via the MCO — don't try to script cordon/drain/reboot in Ansible yourself; that's fighting the platform's own declarative control plane and will conflict with it.

4. The Playbooks — Fully Commented

4.1 roles/node_kernel_config/tasks/main.yml

roles/node_kernel_config/tasks/main.yml
---
# Applies a MachineConfig to raise vm.max_map_count on worker nodes,
# then WAITS for the MachineConfigPool to finish rolling out --
# Ansible does not drive the rollout itself, only observes it.

- name: Apply MachineConfig for vm.max_map_count sysctl                  # the declarative OS-level change
  kubernetes.core.k8s:
    state: present                                                        # idempotent create-or-update
    definition:
      apiVersion: machineconfiguration.openshift.io/v1                     # MCO's own API group
      kind: MachineConfig
      metadata:
        name: 99-worker-max-map-count                                       # '99-' prefix convention: applies LAST, after platform-managed configs
        labels:
          machineconfiguration.openshift.io/role: worker                     # targets the 'worker' MachineConfigPool specifically
      spec:
        config:
          ignition:
            version: 3.2.0                                                    # Ignition spec version RHCOS expects
          storage:
            files:
              - path: /etc/sysctl.d/99-max-map-count.conf                       # where the sysctl override actually lives on disk
                mode: 0644                                                        # standard readable config file permissions
                overwrite: true                                                    # replace if it already exists from a prior version of this MachineConfig
                contents:
                  source: "data:,vm.max_map_count%3D262144%0A"                      # URL-encoded inline content: 'vm.max_map_count=262144\n'
  register: mc_result                                                                # capture for assert

- name: Assert MachineConfig apply succeeded                                          # fail fast on API rejection (e.g. malformed Ignition config)
  ansible.builtin.assert:
    that: [mc_result is succeeded]
    fail_msg: "Failed to apply MachineConfig 99-worker-max-map-count"

- name: Wait for the worker MachineConfigPool to finish updating                       # THIS is what proves the rollout actually completed, not just started
  kubernetes.core.k8s_info:
    kind: MachineConfigPool                                                             # tracks pool-wide rollout state
    api_version: machineconfiguration.openshift.io/v1
    name: worker                                                                          # the pool this MachineConfig targets
  register: mcp_status                                                                     # holds live .status.conditions
  until: >
    (mcp_status.resources[0].status.conditions
     | selectattr('type', 'equalto', 'Updated') | map(attribute='status') | first) == "True"  # Updated condition True = fully rolled out
  retries: 60                                                                                # node drains + reboots take a while
  delay: 30                                                                                  # 30s apart -- up to 30 minutes max wait, reasonable for a rolling node reboot

- name: Report rollout completion                                                             # human-readable confirmation only
  ansible.builtin.debug:
    msg: "Worker MachineConfigPool fully updated with vm.max_map_count=262144"

6. Live Incident — Manual sysctl Reverted After Reboot

ReportPostgreSQL pods on the CloudNativePG cluster (Project 7) start crash-looping right after a routine node reboot during patching. Nobody changed the database config.
Step 1 — check pod logs
oc logs payment-api-pg-1 -n payment-api-prod
FATAL: could not create shared memory segment: max_map_count too low
Step 2 — check the actual live sysctl value on the affected node
oc debug node/node-worker-02 -- chroot /host sysctl vm.max_map_count
vm.max_map_count = 65530   # default value -- the earlier manual fix from before this project is gone
Root causeA previous engineer had set this value manually via SSH months ago (exactly the anti-pattern flagged in Section 1). That manual change was never persisted through MachineConfig, so it silently reverted on this node's routine reboot.
Step 3 — confirm whether our MachineConfig (Section 4.1) was ever actually applied cluster-wide
oc get mcp worker
NAME     UPDATED   UPDATING   DEGRADED
worker   False     True       False
# rollout was left mid-flight from an earlier partial run and never finished
Step 4 — fix properly: re-run the Ansible playbook to completion
ansible-playbook playbooks/node_config.yml
# this time the 'until' loop actually waits for UPDATED=True across every node
Step 5 — validate on the specific node that failed
oc debug node/node-worker-02 -- chroot /host sysctl vm.max_map_count
vm.max_map_count = 262144
ResolvedValue now persists at the MachineConfig layer — it will survive every future reboot and every future node replacement, unlike the original manual fix.

7. Additional Break-Fix Labs

Break-Fix — MachineConfigPool Degraded 
oc get mcp worker
NAME     UPDATED   UPDATING   DEGRADED
worker   False     False      True

oc describe mcp worker
Message: Node node-worker-05 is reporting: "failed to parse Ignition config"

Root cause: malformed Ignition content (e.g. bad URL-encoding in the inline data source) rejected by the node's Ignition parser. Fix: validate the file's contents.source encoding carefully before applying — a single wrong character breaks the whole pool's rollout.

Break-Fix — rollout stuck at 1 of N nodes updating 
oc get mcp worker
NAME     UPDATED   UPDATING   MACHINECOUNT   READYMACHINECOUNT
worker   False     True       6              5

Root cause: the updating node can't drain — likely a PodDisruptionBudget on that node blocking eviction of its last replica. Fix: oc get pdb -A to find the blocking budget, coordinate with the app team to temporarily relax it or ensure enough replicas exist elsewhere first.

9. Interview Preparation

Interviewer: "How do you change a kernel parameter across all worker nodes in OpenShift?"

Answer: Through a MachineConfig, not manual SSH — I write a sysctl drop-in file into the MachineConfig's Ignition storage section, targeted at the worker role label. The Machine Config Operator then handles cordon/drain/apply/reboot one node at a time automatically. Ansible's role is just to apply that MachineConfig object and wait for the MachineConfigPool's Updated condition — the actual rollout orchestration belongs to OpenShift, not to my playbook.

Interviewer: "Why did a manual kernel setting revert after a reboot?"

Answer: RHCOS nodes are meant to be immutable and reconciled from declarative config — anything set by hand outside of MachineConfig isn't part of that reconciliation source and doesn't survive a reboot or a node replacement. That's the exact mechanism, and it's a feature, not a bug — it's why MachineConfig is the only supported way to make this kind of change stick.
