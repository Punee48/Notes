1. The Production Story

Scenario Fifteen projects in, we have monitoring, logging, scaling, backup, and a dozen individually-learned troubleshooting methods. What we don't have is one consistent framework that ties them together — every engineer still investigates differently, and RCA quality varies wildly. Leadership asks platform engineering to formalize a single incident management process.
Business Problem Without a shared framework, severity gets assigned inconsistently, communication during incidents is ad hoc, and RCAs range from thorough to "it's fixed now" with no real root cause captured.
Our Mandate Define severity levels, a standard incident timeline structure, and an Ansible-assisted evidence-collection playbook that any engineer can run at the start of ANY incident — then prove it on a full severity-1 multi-layer outage.

3. The Framework

3.1 Severity Levels

SeverityDefinitionResponse
SEV-1Full outage or data integrity risk, all customers affectedImmediate, all-hands, exec notified
SEV-2Major degradation, subset of customers or one critical flow affectedImmediate, on-call + one escalation
SEV-3Minor degradation, workaround existsBusiness-hours response acceptable
SEV-4Cosmetic/non-urgentNormal backlog

3.2 The Framework, End to End

1. DETECTION — alert fires (Project 8) or report received 2. INITIAL ASSESS — severity assigned, incident channel opened 3. EVIDENCE — run incident_evidence.yml FIRST, always (Section 4) 4. HYPOTHESIS — layered triage: Node → ClusterOperator (P11) → App (P3-5) → Route (P4) → Storage (P6) → Perf (P15) 5. MITIGATION — fastest safe action: rollback (P5), scale (P10), or restore (P14) -- restore service BEFORE full RCA 6. FIX — root cause addressed via Ansible, never a hand-edit 7. VALIDATION — reuse Project 13's post-upgrade validation pattern 8. MONITORING — confirm relevant Project 8 alerts would have caught this 9. RCA — structured document, see Section 6 10. PREVENTIVE ACTION — filed as a tracked follow-up, not just discussed

3.3 Why Evidence Collection Comes Before Hypothesis

ConceptUnder pressure, engineers naturally jump straight to their favorite hypothesis and start "fixing." Collecting a fixed evidence bundle FIRST — cluster health, pod status, recent events, recent deploys — means the RCA later has real data instead of memory, and it stops a wrong-hypothesis fix from starting before anyone's looked at what actually changed.

4. The Playbooks — Fully Commented

4.1 playbooks/incident_evidence.yml

playbooks/incident_evidence.yml
---
# STEP ZERO of any incident: collect a complete evidence bundle
# before forming any hypothesis or taking any mitigating action.
# 100% read-only -- this playbook must never be able to make an
# incident worse.
- name: Collect incident evidence bundle
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: Create a dated evidence directory for this incident               # one folder per incident ID, never overwritten
      ansible.builtin.file:
        path: "incidents/{{ incident_id }}"                                     # e.g. incidents/INC-2091/
        state: directory                                                          # create if missing, no-op if it already exists
        mode: "0755"                                                              # standard readable directory permissions

    - name: Snapshot cluster health (reuses Project 11)                            # same shared tasks file as Projects 11 and 13
      ansible.builtin.import_tasks: cluster_health_checks.yml                       # populates not_ready_nodes / degraded_operators facts

    - name: Snapshot all pods for the affected app                                  # exact pod state at the moment evidence was collected
      kubernetes.core.k8s_info:
        kind: Pod
        namespace: "{{ app_name }}-{{ environment }}"
      register: pod_snapshot                                                         # full pod objects, not just names

    - name: Snapshot recent Events in the affected namespace                          # often contains the single most useful diagnostic line
      kubernetes.core.k8s_info:
        kind: Event
        namespace: "{{ app_name }}-{{ environment }}"
      register: event_snapshot                                                         # events expire after ~1hr by default -- capturing NOW matters

    - name: Snapshot the current Deployment image versions                              # "what changed recently" is the single most common root cause category
      kubernetes.core.k8s_info:
        kind: Deployment
        namespace: "{{ app_name }}-{{ environment }}"
      register: deploy_snapshot                                                          # includes image tags and revision annotations

    - name: Write the raw evidence bundle to disk                                          # JSON, not prose -- preserves full fidelity for later RCA analysis
      ansible.builtin.copy:
        dest: "incidents/{{ incident_id }}/evidence-{{ ansible_date_time.epoch }}.json"      # timestamped so multiple snapshots during one incident don't collide
        content: "{{ {
            'timestamp': ansible_date_time.iso8601,
            'not_ready_nodes': not_ready_nodes,
            'degraded_operators': degraded_operators,
            'pods': pod_snapshot.resources,
            'events': event_snapshot.resources,
            'deployments': deploy_snapshot.resources
          } | to_nice_json }}"                                                                # serializes the whole evidence set as pretty-printed JSON

    - name: Print a quick human-readable summary to the terminal                                 # immediate value while the JSON bundle is being written
      ansible.builtin.debug:
        msg:
          - "Incident {{ incident_id }} evidence collected at {{ ansible_date_time.iso8601 }}"
          - "NotReady nodes: {{ not_ready_nodes | length }}"
          - "Degraded operators: {{ degraded_operators | length }}"
          - "Pods NOT Running: {{ pod_snapshot.resources | rejectattr('status.phase','equalto','Running') | map(attribute='metadata.name') | list }}"  # surfaces the most actionable line immediately

6. Full Incident Walkthrough — SEV-1 Multi-Layer Outage

10:00 AM — DetectionProject 8's PaymentApiNoHealthyEndpoints alert fires. Support simultaneously reports total checkout failure. Declared SEV-1.
10:01 — Incident channel opened, incident_id=INC-2091 assigned.
10:02 — incident_evidence.yml run immediately (Section 5 output above). Confirms: one degraded ClusterOperator, one backend pod not Running.
10:04 — Hypothesis layer 1 (Project 11 method): oc describe clusteroperator ingress → Degraded, "insufficient replicas in one zone."
10:06 — Hypothesis layer 2 (Project 3 method): oc logs on the non-Running backend pod → ImagePullBackOff, unrelated to the ingress issue — TWO simultaneous problems, not one.
10:09 — Mitigation for problem 1 (Project 4/11 method): ingress operator self-recovers once the affected zone's node capacity issue clears — same pattern as Project 11's incident.
10:11 — Mitigation for problem 2 (Project 5 method): scripted rollback playbook run — the ImagePullBackOff traces to a bad tag from a deploy 20 minutes earlier.
10:15 — Both mitigations confirmed; validation playbook (Project 13 pattern) run — all green.
10:18 — Incident downgraded from SEV-1, customer-facing impact ended.

7. Additional Break-Fix Labs

Break-Fix — evidence playbook itself fails mid-incident 
fatal: [localhost]: FAILED! => {"msg": "Permission denied: incidents/"}

Root cause: the directory is owned by a different user from a prior manual run. Fix: this is exactly why the evidence playbook must be tested and trusted BEFORE a real incident — run it in a drill regularly, not for the first time under pressure.

Break-Fix — two engineers investigate simultaneously, conflicting actions

Symptom: one engineer scales up replicas while another starts a rollback at the same time, producing confusing intermediate state.

Root cause: no single incident commander was designated. Fix: the framework (Section 3.2) explicitly assigns one person to drive mitigation decisions; others contribute evidence/hypotheses but only the commander executes changes.

9. Interview Preparation

Interviewer: "Walk me through your incident response process end to end."

Answer: Detection is usually an automated alert. First action, always, is a read-only evidence collection — cluster health, pod state, recent events, recent deploys — before anyone touches anything. Then layered hypothesis testing using the same order every time: node/cluster health, then application, then network/routing, then storage, then performance. Mitigation is scripted where possible — rollback, scale, restore — because scripted actions are faster and safer under pressure than improvised commands. Root cause work and the RCA document happen after service is restored, not before, and every RCA produces at least one tracked preventive action, not just a description of what happened.

Interviewer: "Tell me about a time you found two unrelated problems during one incident."

Answer: During a SEV-1, evidence collection surfaced both a degraded ingress operator from zone capacity AND a separate ImagePullBackOff from an unrelated bad deploy 20 minutes earlier — pure coincidence, but without collecting full evidence first, it would have been easy to fix one and assume the incident was over while the other kept failing.
