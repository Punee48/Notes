1. The Production Story

Scenario Sixteen projects of Ansible automation later, the app team asks a fair question: "why do WE have to ping platform engineering and ask someone to run a playbook every time we want to change a ConfigMap value?" They want self-service, Git-driven deploys — push to Git, see it applied automatically — without losing any of the governance (RBAC, quota, NetworkPolicy) platform engineering has built.
Business Problem Ansible-driven deployment (what we've built so far) requires someone to actually run ansible-playbook. There's no continuous reconciliation — if someone manually changes something in the cluster, nothing corrects it until the next manual run (exactly the drift problems from Projects 2 and 12).
Our Mandate Introduce Argo CD for the application layer (Deployments, Services, Routes, ConfigMaps) while KEEPING Ansible for platform-governed baseline (namespace, quota, RBAC, NetworkPolicy) — the two tools solving different problems, not competing.

3. Ansible-Driven vs GitOps-Driven — Where Each Fits

ANSIBLE-DRIVEN (Projects 1-16): Engineer runs playbook → k8s API → object created/updated Reconciliation: ONLY when someone runs the playbook again Best for: platform baseline, RBAC, one-time/scheduled operations, operator lifecycle, upgrades, backup/restore GITOPS-DRIVEN (this project): Engineer commits to Git → Argo CD detects change → syncs to cluster Reconciliation: CONTINUOUS -- Argo CD constantly compares Git vs live state and can auto-correct drift Best for: application manifests that change frequently, multi- environment promotion via Git branches/directories, teams wanting self-service without direct cluster access
DimensionAnsible-drivenGitOps (Argo CD)
TriggerSomeone runs a playbookGit commit (push-based intent, pull-based sync)
Drift correctionOnly on next manual/scheduled runContinuous — can auto-heal within seconds
Audit trailAnsible run logs / Automation Controller job historyGit commit history — arguably clearer for app changes
Good fitRBAC, quota, Operators, upgrades, DR — governed, infrequent, complex logicApp Deployments/ConfigMaps/Routes — frequent, simple, team self-service
Our decisionKeep for Projects 1-2 (baseline/RBAC), 5-14 (ops)Adopt for Project 3's app-layer objects only

4. The Playbooks — Fully Commented

4.1 playbooks/gitops_operator.yml

playbooks/gitops_operator.yml
---
# Installs the OpenShift GitOps Operator, reusing Project 7's
# operator_install role -- no new installation logic needed.
- name: Install OpenShift GitOps Operator
  hosts: localhost
  connection: local
  gather_facts: false

  roles:
    - role: operator_install                                          # the exact reusable role from Project 7
      vars:
        operator_name: openshift-gitops-operator                         # overrides the variable that role expects
        operator_channel: latest                                          # GitOps operator's own channel naming convention
        # NOTE: OpenShift GitOps auto-creates its own Argo CD instance
        # named 'openshift-gitops' in the 'openshift-gitops' namespace --
        # no separate ArgoCD CR needed for the default instance.

4.2 playbooks/argocd_app.yml

playbooks/argocd_app.yml
---
# Creates an Argo CD Application object -- this is the ONE-TIME
# Ansible action that hands ongoing reconciliation off to Argo CD.
# After this runs, further app-layer changes go through Git, not
# through re-running Ansible.
- name: Register payment-api as an Argo CD Application
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Create the Argo CD Application object                        # the actual GitOps registration
      kubernetes.core.k8s:
        state: present                                                    # idempotent -- re-running with same Git ref makes no change
        definition:
          apiVersion: argoproj.io/v1alpha1                                  # Argo CD's own CRD API group
          kind: Application
          metadata:
            name: "{{ app_name }}-{{ environment }}"                         # one Application per app/environment pair
            namespace: openshift-gitops                                      # Applications live in the Argo CD instance's namespace
          spec:
            project: default                                                  # Argo CD's built-in project; use scoped AppProjects for real multi-tenant setups
            source:
              repoURL: "{{ git_repo_url }}"                                    # the Git repo holding manifests -- Git is now the source of truth
              targetRevision: "{{ git_branch | default('main') }}"              # which branch/tag to track
              path: "base"                                                      # subfolder within the repo containing this app's manifests
            destination:
              server: "https://kubernetes.default.svc"                          # in-cluster destination -- same cluster Argo CD runs on
              namespace: "{{ app_name }}-{{ environment }}"                      # the SAME namespace Ansible's baseline role (Project 1) already created
            syncPolicy:
              automated:
                prune: true                                                       # remove cluster objects no longer defined in Git
                selfHeal: true                                                     # THE key behavior difference from Ansible -- auto-corrects manual drift
              syncOptions:
                - CreateNamespace=false                                            # explicitly false -- namespace lifecycle stays owned by Ansible/Project 1, never Argo CD
      register: app_result                                                          # capture for assert

    - name: Assert Application registration succeeded                                # fail fast on API rejection
      ansible.builtin.assert:
        that: [app_result is succeeded]
        fail_msg: "Failed to register Argo CD Application for {{ app_name }}-{{ environment }}"

    - name: Wait for initial sync to reach Synced/Healthy                             # confirms the handoff actually worked, not just that the object was created
      kubernetes.core.k8s_info:
        kind: Application
        api_version: argoproj.io/v1alpha1
        name: "{{ app_name }}-{{ environment }}"
        namespace: openshift-gitops
      register: sync_status                                                           # holds live .status.sync and .status.health
      until: >
        sync_status.resources[0].status.sync.status == "Synced" and
        sync_status.resources[0].status.health.status == "Healthy"                     # both conditions required for a true success
      retries: 20                                                                       # initial sync is usually fast, generous margin anyway
      delay: 15

5. Execution & Idempotency

ansible-playbook playbooks/gitops_operator.yml
ansible-playbook playbooks/argocd_app.yml -e app_name=payment-api -e environment=dev \
  -e git_repo_url=https://github.com/yourorg/gitops-payment-api.git
First run
PLAY RECAP *** ok=5 changed=3 failed=0
Second run
PLAY RECAP *** ok=5 changed=0 failed=0
Important distinctionAnsible's idempotency here only covers the Application REGISTRATION object. Once registered, changes to the actual Deployment/Service/Route manifests happen via Git commits, and Argo CD — not Ansible — is what applies and reconciles those.

6. Live Incident — Manual Drift Auto-Corrected (and one that wasn't)

ReportAn engineer, under pressure during a different incident, manually scales the backend Deployment from 3 to 10 replicas with oc scale directly, forgetting this app is now Argo CD-managed.
Step 1 — within seconds, Argo CD reverts it
oc get application payment-api-dev -n openshift-gitops
NAME               SYNC STATUS   HEALTH STATUS
payment-api-dev    OutOfSync     Healthy

# moments later, selfHeal kicks in:
oc get deployment payment-api-backend -n payment-api-dev
NAME                   READY   UP-TO-DATE
payment-api-backend    3/3     3          # back to 3 -- Git's value -- automatically
This is GitOps working as designedUnlike Projects 2 and 12's incidents — where manual drift silently persisted until someone noticed — selfHeal: true corrected this within seconds, with zero human intervention. This is the exact problem class GitOps is best at solving.
Step 2 — but a SEPARATE manual change to the NAMESPACE itself is NOT reverted
oc label namespace payment-api-dev team=wrong-team --overwrite
oc get namespace payment-api-dev --show-labels
# the incorrect label PERSISTS -- Argo CD never touches this object
Why this one wasn't caughtWe deliberately set CreateNamespace=false and scoped Argo CD's destination to app-layer objects only (Section 4.2) — the namespace itself remains Ansible-governed (Project 1). This drift needs Project 2's RBAC/baseline audit playbook, not Argo CD, which is exactly the intended division of responsibility.

Step 3 — fix the namespace drift the Ansible way
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=dev
ResolvedBoth drift types corrected — one automatically by Argo CD, one manually via the Ansible baseline playbook — because each tool owns exactly the objects it's responsible for.

7. Additional Break-Fix Labs

Break-Fix — Application stuck OutOfSync, won't self-heal 
oc get application payment-api-dev -n openshift-gitops
SYNC STATUS: OutOfSync
HEALTH STATUS: Degraded

oc describe application payment-api-dev -n openshift-gitops
Message: ComparisonError: rpc error: repository not found

Root cause: Git repo URL typo or a private repo with no credentials configured in Argo CD. Fix: verify git_repo_url, and for private repos, register a Repository credential Secret before creating the Application.

Break-Fix — prune deleted something that shouldn't have been Argo-managed
BreakA ConfigMap created manually (not in Git) inside the app namespace gets deleted by Argo CD's prune: true.

Root cause: once a namespace is an Argo CD destination, prune: true removes ANY object type it manages that isn't declared in Git — including things created outside the GitOps flow entirely. Fix: everything in an Argo-managed namespace must go through Git; this is a feature, not a bug, but it means the team needs to fully commit to the workflow, not mix manual and GitOps changes.

9. Interview Preparation

Interviewer: "When would you choose Ansible over GitOps, or vice versa, for OpenShift deployments?"

Answer: I use them for different jobs, not as competitors. Ansible fits governed, infrequent, or logic-heavy operations — namespace/RBAC baseline, Operator lifecycle, upgrades, backup/restore — where a human or pipeline deliberately triggers a run. GitOps fits frequently-changing application manifests where continuous reconciliation and Git-based audit trail matter more, and where you want app teams to self-serve via pull requests instead of needing direct cluster access or platform team involvement.

Interviewer: "What's the risk of GitOps' self-healing behavior?"

Answer: Anything not declared in Git inside a pruning-enabled Argo CD destination gets deleted, and anything manually changed gets silently reverted — which is great for catching drift but means the whole namespace has to commit to the GitOps workflow. Mixing manual changes with GitOps management in the same objects leads to confusing fights between a human's change and Argo CD's reconciliation loop.

10. Resume Points

  • Introduced Argo CD/GitOps for application-layer deployment while retaining Ansible for platform-governed baseline, RBAC, and operational workflows — establishing a clear ownership boundary between the two.
  • Demonstrated GitOps drift self-healing in production, automatically reverting an unauthorized manual scaling change within seconds versus the silent, undetected drift seen in earlier Ansible-only incidents.
