Image Registry & Software Supply Chain Security

Automating an ImagePolicy that blocks unsigned or unscanned images from ever being admitted, plus registry mirroring for a restricted network, and resolving a live incident where an unscanned dependency shipped a critical CVE to PROD.

1. The Production Story

Scenario Project 18's pipeline scans images at BUILD time, but nothing stops someone from manually deploying an unscanned image straight to the cluster, bypassing the pipeline entirely — the same class of bypass risk as Project 23's promotion-chain incident, but for security scanning specifically. Security asks for a cluster-level backstop: images should be REJECTED AT ADMISSION if they aren't from a trusted, signed source.
Business Problem Pipeline-time scanning is necessary but not sufficient — it only works if every deploy path goes through the pipeline. We need enforcement at the cluster's admission boundary, not just in CI.
Our Mandate Automate an ImagePolicy (or equivalent admission control) requiring images to come from an allow-listed, signed registry, and set up registry mirroring so the restricted PROD network never pulls directly from the public internet.

3. Architecture

Image Build (Project 18's pipeline) │ security scan (Trivy) -- Critical/High blocks the BUILD ▼ Push to trusted registry (quay.io/yourorg only) │ ▼ ADMISSION TIME (this project's backstop, independent of pipeline): ImageContentSourcePolicy / allowedRegistries -- rejects any image reference from a non-allow-listed registry -- this catches the bypass case: someone deploying directly, skipping the pipeline entirely │ ▼ Pod admitted ONLY if its image registry is on the allow-list (regardless of HOW the deploy was triggered -- Ansible, Helm, Kustomize, kubectl, doesn't matter -- admission is the backstop)
LayerWhat it catchesProject
Pipeline-time scanVulnerable dependencies, BEFORE an image is pushedProject 18
Admission-time registry allow-listImages from untrusted sources, regardless of deploy pathThis project
Registry mirroringRestricted networks that can't reach the public internet directlyThis project
Why both layers matterPipeline scanning is the best place to catch problems EARLY, with full context and fast feedback to the developer. Admission-time policy is the last line of defense that works regardless of which tool or person is doing the deploying — exactly the same "belt and suspenders" reasoning as Project 21's explicit egress deny rule.

4. The Playbooks — Fully Commented

4.1 roles/image_policy/tasks/main.yml

roles/image_policy/tasks/main.yml
---
# Configures cluster-wide image signature policy AND an allow-list
# of trusted registries -- images from anywhere else are rejected
# at admission, regardless of how the deploy was triggered.

- name: Configure allowed registries for image pulls                        # cluster-wide admission-time enforcement
  kubernetes.core.k8s:
    state: present                                                            # patches the cluster-scoped singleton config object
    definition:
      apiVersion: config.openshift.io/v1                                       # cluster config API group
      kind: Image                                                                # the cluster-wide Image config singleton
      metadata:
        name: cluster                                                             # fixed, required name -- there is only ever one
      spec:
        registrySources:
          allowedRegistries:                                                        # EXPLICIT allow-list -- anything not listed is rejected
            - "{{ allowed_registry }}"                                                # our trusted org registry, e.g. quay.io/yourorg
            - "quay.io/openshift-release-dev"                                          # required for OpenShift's own release images -- easy to forget and breaks upgrades
            - "registry.redhat.io"                                                     # required for Red Hat certified Operator/base images used across this series
  register: image_config_result                                                        # capture for assert

- name: Assert Image config apply succeeded                                              # fail fast -- a bad registry list can break EVERYTHING including the cluster itself
  ansible.builtin.assert:
    that: [image_config_result is succeeded]
    fail_msg: "Failed to configure allowed registries"

- name: Configure signature verification policy for the trusted registry                   # beyond just WHERE -- also verify cryptographic signature
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: config.openshift.io/v1
      kind: Image
      metadata:
        name: cluster
      spec:
        additionalTrustedCA:
          name: "{{ registry_ca_configmap | default(omit) }}"                              # custom CA for a private/mirrored registry, if applicable
  register: sig_config_result

- name: Assert signature policy apply succeeded
  ansible.builtin.assert:
    that: [sig_config_result is succeeded]
    fail_msg: "Failed to configure signature verification policy"

- name: Warn about the enforcement gap that motivated this project                           # documentation-as-code -- explains WHY this exists, visible to future engineers
  ansible.builtin.debug:
    msg: >-
      This allow-list is the ADMISSION-TIME backstop for Project 18's pipeline
      scanning -- it exists specifically to catch deploys that bypass CI/CD.

4.2 roles/registry_mirror/tasks/main.yml

roles/registry_mirror/tasks/main.yml
---
# Configures the cluster to pull certain image references through
# an internal mirror instead of directly from the public internet --
# required for restricted/air-gapped PROD networks.

- name: Create ImageDigestMirrorSet routing public refs through the internal mirror   # current preferred CRD (supersedes ImageContentSourcePolicy)
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: config.openshift.io/v1                                                # cluster config API group
      kind: ImageDigestMirrorSet                                                          # digest-based mirroring -- pairs naturally with Project 23's digest-promotion approach
      metadata:
        name: internal-mirror                                                              # descriptive name
      spec:
        imageDigestMirrors:
          - source: "registry.redhat.io"                                                     # the PUBLIC reference the cluster would normally reach for
            mirrors:
              - "{{ internal_mirror_host }}/redhat"                                            # our internal mirror serving the same content, e.g. mirror.internal.corp/redhat
          - source: "quay.io/{{ allowed_registry_org }}"                                       # our own org's registry, also mirrored internally
            mirrors:
              - "{{ internal_mirror_host }}/yourorg"
  register: mirror_result                                                                       # capture for assert

- name: Assert ImageDigestMirrorSet apply succeeded                                                # fail fast -- a broken mirror config can block ALL image pulls cluster-wide
  ansible.builtin.assert:
    that: [mirror_result is succeeded]
    fail_msg: "Failed to configure ImageDigestMirrorSet"

- name: Wait for the MachineConfigPool to finish applying mirror config                             # mirror config changes roll out via MachineConfig, same mechanism as Project 12
  kubernetes.core.k8s_info:
    kind: MachineConfigPool
    api_version: machineconfiguration.openshift.io/v1
    name: worker
  register: mcp_status                                                                               # same pattern as Project 12's wait logic
  until: >
    (mcp_status.resources[0].status.conditions
     | selectattr('type','equalto','Updated') | map(attribute='status') | first) == "True"
  retries: 60
  delay: 30

6. Live Incident — Unscanned Image Reached PROD via a Bypass

ReportSecurity's external scanner flags a critical CVE running in a PROD pod. Project 18's pipeline records show no build ever produced this exact digest.
Step 1 — identify the actual image and where it came from
oc get pod suspicious-pod -n payment-api-prod -o jsonpath='{.spec.containers[0].image}'
docker.io/someteam/quick-fix:latest   # NOT from our trusted registry at all
Root cause candidateSomeone deployed a quick manual fix directly from a public Docker Hub image, entirely outside the pipeline, the promotion chain, and — critically — BEFORE this project's admission policy was in place.
Step 2 — confirm this couldn't happen again post-policy
oc run test-bypass --image=docker.io/someteam/quick-fix:latest -n payment-api-prod
Error from server (Forbidden): admission webhook denied the request:
  image registry "docker.io" is not in the allowed list
Policy working as designedThe exact bypass that caused this incident is now structurally impossible — not just discouraged by process, but rejected at admission regardless of who attempts it or which tool they use.
Step 3 — remediate the existing exposure: remove the bad pod, deploy the proper fix through the pipeline
oc delete pod suspicious-pod -n payment-api-prod

# proper fix goes through Project 18's pipeline and Project 23's promotion chain:
git commit -am "Fix: proper CVE remediation"
git push   # triggers pipeline: test, scan, build, promote through DEV->QA->STAGE->PROD
Step 4 — validate no other unauthorized images exist cluster-wide
oc get pods -A -o jsonpath='{range .items[*]}{.spec.containers[*].image}{"\n"}{end}' | \
  grep -v "quay.io/yourorg\|registry.redhat.io\|quay.io/openshift-release-dev"
# scans every running pod's image against the allow-list -- confirms no other exposure exists
ResolvedBad image removed, proper fix deployed through governed channels, and the admission policy now structurally prevents recurrence of this exact bypass class.

7. Additional Break-Fix Labs

Break-Fix — cluster upgrade fails after ImagePolicy applied 
oc get clusterversion
Message: Unable to apply: image not allowed: quay.io/openshift-release-dev/...

Root cause: the allow-list forgot to include OpenShift's own release image registry. Fix: our role always includes quay.io/openshift-release-dev and registry.redhat.io explicitly (Section 4.1) for exactly this reason — a security policy that breaks the platform's own upgrade path is a self-inflicted outage.

Break-Fix — mirror configured but images still pulled from the public internet 
oc get mcp worker
UPDATED: False   # mirror config never finished rolling out

Root cause: ImageDigestMirrorSet changes require a MachineConfig rollout (same mechanism as Project 12) — if that rollout stalls, nodes keep using their old, unmirrored configuration. Fix: apply Project 11's node/MCP troubleshooting method to find why the rollout is stuck.

9. Interview Preparation

Interviewer: "Your CI pipeline scans images for vulnerabilities — isn't that enough?"

Answer: Only if every single deploy path goes through the pipeline, and in practice that's never guaranteed — someone will eventually deploy directly during an incident, or from a personal workstation. Pipeline scanning is necessary but not sufficient; I add an admission-time registry allow-list as a structural backstop that rejects images from untrusted sources regardless of which tool or person is doing the deploying. It's the same defense-in-depth reasoning as pairing a NetworkPolicy allow rule with an explicit deny — belt and suspenders, at different layers.

Interviewer: "How did an unscanned image reach production in your environment, and how did you prevent it from happening again?"

Answer: Someone deployed a quick manual fix directly from a public Docker Hub image during an incident, bypassing our pipeline and promotion chain entirely — before we had any admission-level enforcement. The real fix wasn't just removing that pod; it was implementing a cluster-wide registry allow-list so that class of bypass becomes structurally impossible, not just against policy. I made sure to explicitly allow-list OpenShift's own release registries too, since a security control that accidentally blocks cluster upgrades creates a different kind of outage.
