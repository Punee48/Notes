1. The Production Story

Scenario payment-api has been running at a fixed 3 replicas since Project 3. A marketing promotion goes live and traffic triples in 10 minutes. The fixed replica count can't absorb it, and there's no cluster capacity headroom either — worker nodes are already near full.
Business Problem Nobody configured autoscaling for payment-api or the cluster's worker MachineSets, so scaling has always meant a manual, reactive oc scale command — too slow for a traffic spike that happens in minutes.
Our Mandate Automate a HorizontalPodAutoscaler for the backend, tuned against the CPU/memory metrics already flowing from Project 8, and a MachineAutoscaler so the cluster itself can grow when pod scaling alone isn't enough.

3. Architecture

Metrics (from Project 8's monitoring pipeline) │ ▼ HorizontalPodAutoscaler — watches CPU/memory vs target utilization │ scales ▼ Deployment replica count adjusts up/down within min/max bounds │ ▼ If nodes lack capacity for new pods → Pending │ ▼ Cluster Autoscaler notices Pending + unschedulable → triggers MachineAutoscaler to add a new worker node (IPI clusters only)
ConceptDetail
HPAAdjusts Deployment/StatefulSet replica count based on observed metrics vs target
Resource requestsHPA's CPU/memory percentage targets are relative to the pod's requests, not limits — sizing these correctly (Project 1/3) directly affects scaling behavior
MachineAutoscalerPer-MachineSet min/max node count; only adds nodes when something is actually Pending and unschedulable
Cluster AutoscalerThe cluster-wide controller that watches for unschedulable pods and drives MachineAutoscaler decisions

4. The Playbooks — Fully Commented

4.1 roles/app_hpa/tasks/main.yml

roles/app_hpa/tasks/main.yml
---
# Creates a HorizontalPodAutoscaler for the backend Deployment,
# targeting CPU utilization relative to its resource REQUESTS.

- name: Confirm the backend Deployment has resource requests set          # HPA math is meaningless without this -- fail loudly instead of silently misbehaving
  kubernetes.core.k8s_info:                                                # read-only lookup
    kind: Deployment
    api_version: apps/v1
    name: "{{ app_name }}-backend"
    namespace: "{{ app_name }}-{{ environment }}"
  register: backend_deploy                                                  # holds the live Deployment spec

- name: Assert CPU requests are defined on the backend container            # prerequisite check before creating the HPA
  ansible.builtin.assert:
    that:
      - backend_deploy.resources[0].spec.template.spec.containers[0]
          .resources.requests.cpu is defined                                 # dig into the nested container spec
    fail_msg: "Backend Deployment has no CPU request set -- HPA cannot compute utilization"

- name: Create HorizontalPodAutoscaler for the backend                       # the actual autoscaling policy
  kubernetes.core.k8s:
    state: present                                                           # idempotent apply
    definition:
      apiVersion: autoscaling/v2                                              # v2 supports multiple metrics and behavior tuning
      kind: HorizontalPodAutoscaler
      metadata:
        name: "{{ app_name }}-backend-hpa"
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        scaleTargetRef:                                                        # which object this HPA controls
          apiVersion: apps/v1
          kind: Deployment
          name: "{{ app_name }}-backend"                                        # must match the existing Deployment name exactly
        minReplicas: "{{ hpa_min | default(2) }}"                                # never scale below 2 -- keeps basic HA even at idle
        maxReplicas: "{{ hpa_max | default(10) }}"                               # hard ceiling -- protects downstream DB connections from being overwhelmed
        metrics:
          - type: Resource                                                       # built-in resource metric type (vs external/custom)
            resource:
              name: cpu                                                          # scale on CPU utilization
              target:
                type: Utilization                                                 # percentage of the REQUEST, not the limit
                averageUtilization: "{{ hpa_cpu_target | default(70) }}"           # scale up once average CPU crosses 70% of requested
        behavior:
          scaleDown:
            stabilizationWindowSeconds: 300                                        # wait 5 min of sustained low usage before scaling down -- avoids flapping
          scaleUp:
            stabilizationWindowSeconds: 0                                          # scale up immediately -- no reason to delay absorbing a spike
            policies:
              - type: Pods
                value: 2                                                            # add at most 2 pods per scaling step
                periodSeconds: 60                                                    # ...per 60 seconds, preventing a runaway scale-up loop
  register: hpa_result                                                                # capture for assert

- name: Assert HPA apply succeeded                                                     # fail fast on API rejection
  ansible.builtin.assert:
    that: [hpa_result is succeeded]
    fail_msg: "Failed to create HPA for {{ app_name }}-backend"

4.2 roles/cluster_autoscale/tasks/main.yml

roles/cluster_autoscale/tasks/main.yml
---
# Cluster-level autoscaling -- IPI clusters only (needs machine-api).
# Ensures HPA has somewhere to actually schedule new pods when
# existing nodes are full.

- name: Create the cluster-wide ClusterAutoscaler singleton                 # only ONE of these can exist per cluster, name is always 'default'
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: autoscaling.openshift.io/v1                                 # OpenShift-specific autoscaling API
      kind: ClusterAutoscaler
      metadata:
        name: default                                                          # fixed required name -- cluster-scoped singleton
      spec:
        resourceLimits:
          maxNodesTotal: "{{ cluster_max_nodes | default(12) }}"                 # hard ceiling on total nodes -- cost control
        scaleDown:
          enabled: true                                                          # allow shrinking back down when load drops
          delayAfterAdd: 10m                                                     # wait 10 min after a scale-up before considering scale-down -- avoids thrashing
  register: ca_result

- name: Assert ClusterAutoscaler apply succeeded
  ansible.builtin.assert:
    that: [ca_result is succeeded]
    fail_msg: "Failed to create ClusterAutoscaler"

- name: Create MachineAutoscaler for the worker MachineSet                    # per-MachineSet min/max bounds the cluster autoscaler respects
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: autoscaling.openshift.io/v1beta1                             # MachineAutoscaler API version
      kind: MachineAutoscaler
      metadata:
        name: "{{ worker_machineset_name }}-autoscaler"                          # conventional naming tied to the target MachineSet
        namespace: openshift-machine-api                                          # required namespace for machine-api objects
      spec:
        minReplicas: "{{ worker_min | default(3) }}"                              # never scale this MachineSet below 3 nodes
        maxReplicas: "{{ worker_max | default(6) }}"                              # cap growth -- matches cost/capacity planning
        scaleTargetRef:
          apiVersion: machine.openshift.io/v1beta1
          kind: MachineSet
          name: "{{ worker_machineset_name }}"                                     # must match an existing MachineSet exactly
  register: ma_result
  when: worker_machineset_name is defined                                            # skip entirely on non-IPI clusters where this variable is never set

- name: Assert MachineAutoscaler apply succeeded
  ansible.builtin.assert:
    that: [ma_result is succeeded]
    fail_msg: "Failed to create MachineAutoscaler for {{ worker_machineset_name }}"
  when: worker_machineset_name is defined

6. Live Incident — Traffic Tripled, Pods Didn't Scale

ReportMarketing promo drove a traffic spike; response times climbed and some requests started timing out.
Step 1 — check the HPA's actual status
oc get hpa payment-api-backend-hpa -n payment-api-prod
NAME                       TARGETS         MINPODS   MAXPODS   REPLICAS
payment-api-backend-hpa    <unknown>/70%   2         10        2
Root cause candidateTARGETS shows <unknown> instead of an actual percentage — the HPA has no metrics to act on at all, so it never scales regardless of real load.
Step 2 — describe the HPA for the specific error
oc describe hpa payment-api-backend-hpa -n payment-api-prod
Warning  FailedGetResourceMetric  unable to get metrics for resource cpu:
  no metrics returned from resource metrics API
Step 3 — check if the backend Deployment actually has CPU requests set in PROD specifically
oc get deployment payment-api-backend -n payment-api-prod -o jsonpath='{.spec.template.spec.containers[0].resources}'
{"limits":{"cpu":"500m","memory":"512Mi"}}
# 'requests' key is completely absent in PROD -- only limits were set
Root causePROD's Deployment was hand-edited at some point and lost its requests.cpu field (limits alone remained) — without a CPU request, the resource-utilization percentage the HPA needs is mathematically undefined, so it can never compute a scaling decision.
Step 4 — fix via Ansible (restores requests, since our role always sets both)
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=prod
Step 5 — validate the HPA now sees real metrics
oc get hpa payment-api-backend-hpa -n payment-api-prod
NAME                       TARGETS      MINPODS   MAXPODS   REPLICAS
payment-api-backend-hpa    83%/70%      2         10        4
ResolvedHPA immediately scaled from 2 to 4 replicas once it had real data; response times recovered within two minutes.

7. Additional Break-Fix Labs

Break-Fix — HPA maxReplicas too low, still can't absorb spike 
oc get hpa payment-api-backend-hpa -n payment-api-prod
TARGETS      REPLICAS
95%/70%      10          # pinned at maxReplicas, still over target

Root cause: the ceiling itself is too conservative for this traffic level. Fix: deliberately raise hpa_max via Ansible (a reviewed, auditable change) rather than editing it by hand mid-incident, then confirm downstream DB connection limits (Project 3/7) can actually support the higher pod count.

Break-Fix — pods Pending, cluster out of capacity 
oc get pods -n payment-api-prod
payment-api-backend-9f-z9   0/1   Pending

oc describe pod payment-api-backend-9f-z9 -n payment-api-prod
Warning  FailedScheduling  0/6 nodes are available: 6 Insufficient cpu

Root cause: HPA wants more pods but no node has room. Fix: this is exactly what MachineAutoscaler (Section 4.2) exists to solve on IPI clusters — confirm it's configured with headroom in maxReplicas, or manually add capacity on non-IPI clusters.

9. Interview Preparation

Interviewer: "Traffic spiked and pods weren't scaling — how do you debug that?"

Answer: oc get hpa first — if TARGETS shows <unknown>, the HPA has no metrics to act on, which is a different problem than "it saw the load and chose not to scale." oc describe hpa usually names the exact failure. In one case it turned out a manual edit had stripped the CPU request off the Deployment, and utilization percentage is mathematically undefined without a request to compare against.

Interviewer: "What's the relationship between HPA and the Cluster Autoscaler?"

Answer: HPA scales pod count within the capacity that already exists. If there isn't enough node capacity for the new pods, they go Pending, and the Cluster Autoscaler notices unschedulable pods and asks a MachineAutoscaler to add nodes. They're two layers of the same scaling problem — pod-level and node-level — and both need sensible min/max bounds to avoid runaway cost.
