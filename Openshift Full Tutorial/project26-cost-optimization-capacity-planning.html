1. The Production Story

Scenario Finance flags that the OpenShift cluster's cloud bill has grown steadily for three months with no corresponding growth in traffic. Nobody on the platform team has ever formally reviewed resource requests/limits against ACTUAL usage — every value across this entire series (Projects 1, 3, 15) was set once, deliberately, but never revisited.
Business Problem Over-provisioned resource requests directly inflate the ResourceQuota (Project 1) and therefore the node capacity (and MachineAutoscaler ceiling, Project 10) needed to run the same actual workload — pure waste that compounds across every environment.
Our Mandate Build an Ansible-driven right-sizing report comparing configured requests/limits against real observed usage (via Project 8's metrics), automate cost-attribution labels for chargeback, and investigate the specific spend spike.

3. Architecture

ConceptCost in Kubernetes/OpenShift is driven overwhelmingly by resource REQUESTS, not actual usage — the scheduler reserves capacity based on requests regardless of whether a pod ever uses it. A pod requesting 1 CPU but averaging 100m usage is still "costing" the cluster a full CPU's worth of reserved capacity. Right-sizing means closing that gap deliberately, informed by real data, not guesswork.
For each workload: 1. Configured request (from the Deployment spec, e.g. Project 3's role) 2. Actual P95 usage over a meaningful window (Prometheus, Project 8) 3. Gap = configured - actual 4. If gap is large AND consistent over time → over-provisioned, candidate for reduction 5. If actual regularly exceeds configured → under-provisioned, candidate for the OPPOSITE fix (this is Project 15's throttling scenario in reverse) Chargeback: every namespace/object labeled with team + cost-center → finance can attribute cluster spend without engineering effort per report cycle
MetricQuery basis
P95 CPU usagequantile_over_time(0.95, container_cpu_usage_seconds_total[7d])
P95 Memory usagequantile_over_time(0.95, container_memory_working_set_bytes[7d])
Configured requestRead directly from the live Deployment spec
Waste ratioconfigured request ÷ actual P95 usage — closer to 1.0 is better-sized

4. The Playbooks — Fully Commented

4.1 playbooks/rightsizing_report.yml

playbooks/rightsizing_report.yml
---
# READ-ONLY report comparing configured resource requests against
# real P95 usage over the last 7 days, producing a prioritized
# right-sizing recommendation list.
- name: Generate right-sizing report
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: Get configured CPU/memory requests from the live Deployment          # the 'configured' half of the comparison
      kubernetes.core.k8s_info:
        kind: Deployment
        name: "{{ app_name }}-backend"
        namespace: "{{ app_name }}-{{ environment }}"
      register: deploy_info                                                       # holds the current resources.requests values

    - name: Query actual P95 CPU usage over the last 7 days                          # the 'actual' half -- direct Prometheus API query
      ansible.builtin.uri:
        url: "https://thanos-querier.openshift-monitoring.svc:9091/api/v1/query"
        method: GET
        body_format: form-urlencoded
        body:
          query: >-
            quantile_over_time(0.95,
              rate(container_cpu_usage_seconds_total{namespace="{{ app_name }}-{{ environment }}",
              container="backend"}[5m])[7d:5m])                                        # P95 of the 5-minute CPU usage rate, over a 7-day window
        headers:
          Authorization: "Bearer {{ lookup('env', 'PROM_TOKEN') }}"                      # service account token, never hardcoded
        validate_certs: true
      register: cpu_p95_query                                                             # holds the raw Prometheus response

    - name: Query actual P95 memory usage over the last 7 days                               # same pattern, memory metric
      ansible.builtin.uri:
        url: "https://thanos-querier.openshift-monitoring.svc:9091/api/v1/query"
        method: GET
        body_format: form-urlencoded
        body:
          query: >-
            quantile_over_time(0.95,
              container_memory_working_set_bytes{namespace="{{ app_name }}-{{ environment }}",
              container="backend"}[7d])
        headers:
          Authorization: "Bearer {{ lookup('env', 'PROM_TOKEN') }}"
        validate_certs: true
      register: mem_p95_query

    - name: Extract the numeric values from both Prometheus responses                          # Prometheus API responses are nested JSON -- pull just the value
      ansible.builtin.set_fact:
        actual_cpu_p95: "{{ (cpu_p95_query.json.data.result[0].value[1] | float) }}"              # cores, e.g. 0.15
        actual_mem_p95_mb: "{{ (mem_p95_query.json.data.result[0].value[1] | float / 1048576) | round(0) }}"  # bytes to MB
        configured_cpu: "{{ deploy_info.resources[0].spec.template.spec.containers[0].resources.requests.cpu }}"  # e.g. '1' or '500m'

    - name: Compute the waste ratio                                                              # the key decision metric
      ansible.builtin.set_fact:
        waste_ratio: "{{ (configured_cpu | regex_replace('m','') | float / (1000 if 'm' not in configured_cpu else 1)) / (actual_cpu_p95 | float) | round(2) }}"  # configured / actual -- normalizes millicores vs cores

    - name: Write the right-sizing report                                                          # local file, human-reviewable output
      ansible.builtin.copy:
        dest: "./rightsizing-report.txt"
        content: |
          Right-Sizing Report — {{ app_name }}-{{ environment }} — {{ ansible_date_time.iso8601 }}
          =====================================================
          Configured CPU request: {{ configured_cpu }}
          Actual P95 CPU usage (7d): {{ actual_cpu_p95 }} cores
          Actual P95 memory usage (7d): {{ actual_mem_p95_mb }} MB
          Waste ratio: {{ waste_ratio }}x
          Recommendation: {{ 'REDUCE request -- over-provisioned' if (waste_ratio | float) > 2.0
                              else 'INCREASE request -- under-provisioned, risk of throttling (see Project 15)' if (waste_ratio | float) < 1.0
                              else 'Well-sized -- no action needed' }}

4.2 playbooks/chargeback_labels.yml

playbooks/chargeback_labels.yml
---
# Ensures every environment's namespace carries cost-attribution
# labels, so finance tooling can report spend by team/cost-center
# without engineering involvement each cycle.
- name: Apply chargeback labels across all environments
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Label each environment's namespace with cost attribution        # loops over every environment for this app
      kubernetes.core.k8s:
        state: present                                                       # idempotent label patch
        definition:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: "{{ app_name }}-{{ item }}"                                  # iterates dev/qa/stage/prod
            labels:
              cost-center: "{{ cost_center | default('CC-4471-PLATFORM') }}"      # finance's cost-center code, same convention Project 1 used for team/owner
              billing-team: "{{ team | default('payments') }}"                    # reuses Project 1's team variable convention
      loop: ["dev", "qa", "stage", "prod"]                                         # every environment gets the same attribution -- consistent reporting
      loop_control: {label: "{{ item }}"}                                          # cleaner loop output in play results

6. Investigation — "Cost Doubled, Traffic Didn't"

ReportFinance's monthly cloud bill for the cluster nearly doubled over the last quarter, but Project 8's dashboards show flat request volume the whole time.
Step 1 — check total cluster node count over time
oc get machineset -n openshift-machine-api
NAME             DESIRED   CURRENT
worker-us-east-1a   6         6      # up from a baseline of 3, per change history
Root cause candidateWorker node count doubled — but if traffic is flat, something is consuming double the capacity for the same actual work.
Step 2 — run the right-sizing report across EVERY environment, not just PROD
ansible-playbook playbooks/rightsizing_report.yml -e app_name=payment-api -e environment=dev
Waste ratio: 8.2x   # DEV is drastically over-provisioned

ansible-playbook playbooks/rightsizing_report.yml -e app_name=payment-api -e environment=qa
Waste ratio: 7.9x   # QA too
Step 3 — check WHEN the requests changed, correlating with the cost trend
git log --oneline -- payment-stack/roles/backend/tasks/main.yml
a1b2c3d  "bump resources for load testing"   # 3 months ago -- matches the cost trend start
Root causeA resource bump made for a one-time load test 3 months ago was never reverted afterward, and — critically — the SAME inflated values were copy-pasted into DEV and QA's overlays as well (Project 22's shared-base risk, playing out in exactly the way Project 22's break-fix warned about), multiplying the waste across every environment simultaneously.
Step 4 — fix: revert to right-sized values based on actual P95 data, across all environments
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=dev \
  -e backend_cpu_request=200m   # derived from the 0.18 core P95 usage, with reasonable headroom
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=qa -e backend_cpu_request=200m
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=prod -e backend_cpu_request=300m
Step 5 — validate the MachineAutoscaler ceiling can now come down too
ansible-playbook playbooks/scaling.yml -e worker_max=4   # reduced from 6, reflecting genuinely needed capacity
ResolvedRight-sized requests reduce the ResourceQuota footprint enough that the cluster can run on fewer nodes for the same actual workload — directly reducing cloud spend.

7. Additional Break-Fix Labs

Break-Fix — right-sizing recommendation would break a throttling-sensitive workload
TrapBlindly applying the "reduce" recommendation to a workload with occasional legitimate traffic spikes could recreate Project 15's CPU throttling incident.

Root cause: P95 usage smooths over rare-but-real spikes. Fix: always cross-reference the right-sizing report against Project 15's throttling metric and Project 8's traffic patterns before applying a reduction — right-sizing is a data input to a decision, not an automatic action.

Break-Fix — chargeback labels missing from a newly-created namespace

Symptom: finance's monthly report shows an "unattributed" cost bucket.

Root cause: a new environment or namespace was created outside Project 1's baseline playbook, so it never received chargeback labels. Fix: add the label application directly into Project 1's baseline role itself, so it's impossible to create a namespace without cost attribution going forward, rather than relying on remembering to run this project's playbook separately.

9. Interview Preparation

Interviewer: "How do you approach right-sizing Kubernetes workloads?"

Answer: Compare configured resource requests against actual P95 usage over a meaningful window — a week or more, to smooth out day-of-week patterns — via Prometheus. A large, consistent gap signals over-provisioning worth reducing; usage regularly exceeding the request signals the opposite problem, which risks the CPU throttling scenario I hit in an earlier project. I never apply a reduction blindly — I cross-check against known traffic spike patterns first, since P95 alone can mask rare-but-legitimate load.

Interviewer: "Cloud costs doubled with no traffic increase — how do you investigate?"

Answer: Start with what actually scaled — node count, in this case — then work backward to why. Running a right-sizing report across every environment, not just the one that seemed relevant, showed the same inflated resource requests everywhere, and Git history pinned it to a temporary load-testing change that was never reverted and had been copy-pasted into other environments' configs. The fix was reverting to data-driven values everywhere, plus adding a scheduled report so this kind of drift gets caught within weeks, not quarters.
