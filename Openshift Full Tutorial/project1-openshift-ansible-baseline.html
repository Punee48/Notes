1. The Production Story

Scenario We've joined the Platform Engineering team at a large telecom company. The company runs customer-facing applications across four OpenShift environments: DEV, QA, STAGE, and PROD. Right now, whenever an application team needs a new environment, a platform engineer logs into the cluster and manually runs a sequence of oc create and oc apply commands: create the project, apply quotas, create service accounts, bind roles, apply network policies, and seed baseline ConfigMaps/Secrets.
Business Problem Manual setup means every engineer does it slightly differently. Some projects are missing LimitRanges. Some have overly broad RBAC. A recent audit found one DEV project where a ServiceAccount had cluster-admin bound by mistake, and a PROD project with no NetworkPolicy at all. Onboarding a new application takes half a day of manual, error-prone clicking and typing. Our manager wants this eliminated.
Our Mandate Build an Ansible automation solution that takes a small set of inputs — application name, environment, team, owner — and produces a consistent, secure, auditable OpenShift project baseline, every single time, in every environment, with zero manual steps.

3. Architecture

3.1 OpenShift Objects Involved

Concept A "project baseline" in OpenShift is not one object — it's a bundle of related objects that together define a safe, governed tenant boundary. We are automating the creation of all of them together, atomically, from one source of truth.
ObjectPurposeAPI Group
ProjectNamespace + OpenShift metadata (display name, requester annotation)project.openshift.io/v1
ResourceQuotaCaps total CPU/memory/object counts for the namespacev1
LimitRangeSets default request/limit per container so pods can't go unboundedv1
ServiceAccountIdentity the application's pods run as (not a human user)v1
RoleBindingGrants the app team's group the edit ClusterRole, scoped to this namespace onlyrbac.authorization.k8s.io/v1
NetworkPolicyDefault-deny ingress + explicit allow from same namespace and routernetworking.k8s.io/v1
ConfigMapNon-sensitive baseline configuration (e.g. environment name, log level)v1

3.2 Automation Flow

Engineer │ provides: app_name, environment, team, owner ▼ Ansible Controller (or Automation Controller Job Template) │ loads: group_vars/<env> + role defaults ▼ Role: openshift_project → creates Project Role: openshift_quota → applies ResourceQuota + LimitRange Role: openshift_rbac → creates ServiceAccount + RoleBinding Role: openshift_network → applies default-deny + allow NetworkPolicy Role: openshift_application → seeds baseline ConfigMap │ ▼ kubernetes.core.k8s module → OpenShift API Server → etcd │ ▼ Validation playbook confirms all objects Ready

4. Repository Structure

Why structured this way Roles are split by concern (project, quota, rbac, network, application) so each can be tested, reused, and version-controlled independently. Environments live in separate inventories so PROD variables can never accidentally leak into a DEV run, and vice-versa.

6. The Playbooks

6.1 Role: openshift_project

What / WhyCreates the Project (OpenShift's wrapper around a Kubernetes Namespace) with a display name and a requester annotation, plus governance labels used later for cost reporting and NetworkPolicy selectors.
roles/openshift_project/tasks/main.yml
---
# Creates the OpenShift Project for this application/environment pair.
# Using kubernetes.core.k8s with state: present makes this idempotent:
# re-running with identical input produces no change (reports 'ok').
- name: Create OpenShift project {{ app_name }}-{{ environment }}
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: project.openshift.io/v1
      kind: Project
      metadata:
        name: "{{ app_name }}-{{ environment }}"
        labels:
          app: "{{ app_name }}"
          team: "{{ team }}"
          environment: "{{ environment }}"
        annotations:
          openshift.io/display-name: "{{ app_name }} ({{ environment }})"
          openshift.io/requester: "{{ owner }}"
  register: project_result

# Fail fast and loudly if the API call didn't succeed, instead of
# letting later roles run against a namespace that doesn't exist.
- name: Assert project creation succeeded
  ansible.builtin.assert:
    that:
      - project_result is succeeded
    fail_msg: "Failed to create project {{ app_name }}-{{ environment }}"

Task-by-task explanation

QuestionAnswer
What API does it touch?project.openshift.io/v1 Project — OpenShift-specific, sits on top of a core Kubernetes Namespace.
Idempotent?Yes — k8s module diffs desired vs actual state server-side.
First run result?changed — project didn't exist, now it does.
Second run result?ok — desired state already matches; no API write happens.
If task removed?Every downstream role (quota, rbac, network) would fail — they target a namespace that doesn't exist.
If it fails?Usually RBAC — the Ansible service account lacks create on projectrequests. Assert task stops the play instead of silently continuing.

6.2 Role: openshift_quota

roles/openshift_quota/tasks/main.yml
---
# ResourceQuota caps the TOTAL consumption for the whole namespace.
# Values come from environment group_vars, not hardcoded here —
# this is what lets one role serve DEV and PROD safely.
- name: Apply ResourceQuota
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ResourceQuota
      metadata:
        name: "{{ app_name }}-quota"
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        hard:
          requests.cpu: "{{ quota_cpu_limit }}"
          requests.memory: "{{ quota_memory_limit }}"
          pods: "{{ quota_pod_count }}"

# LimitRange sets PER-CONTAINER defaults so a developer who forgets
# to set requests/limits doesn't accidentally consume the whole quota
# with one unbounded pod.
- name: Apply LimitRange
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: LimitRange
      metadata:
        name: "{{ app_name }}-limits"
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        limits:
          - type: Container
            defaultRequest:
              cpu: "{{ default_container_cpu_request }}"
              memory: "128Mi"
            default:
              cpu: "500m"
              memory: "512Mi"

6.3 Role: openshift_rbac

Least PrivilegeApplication teams get the built-in edit ClusterRole bound only inside their own namespace — never admin, and never a ClusterRoleBinding. This is the single most important security control in this project.
roles/openshift_rbac/tasks/main.yml
---
# ServiceAccount = the identity the application's PODS run as.
# This is NOT for human login — humans authenticate via SSO/OIDC groups.
- name: Create application ServiceAccount
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name: "{{ app_name }}-sa"
        namespace: "{{ app_name }}-{{ environment }}"

# Bind the HUMAN team group to 'edit' — scoped with a RoleBinding
# (namespace-local), never ClusterRoleBinding (cluster-wide).
# 'edit' allows create/update/delete on most objects but NOT
# RBAC changes and NOT quota changes — that stays with platform team.
- name: Bind team group to edit role in this namespace only
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: rbac.authorization.k8s.io/v1
      kind: RoleBinding
      metadata:
        name: "{{ team }}-edit-binding"
        namespace: "{{ app_name }}-{{ environment }}"
      subjects:
        - kind: Group
          name: "{{ team }}-developers"
          apiGroup: rbac.authorization.k8s.io
      roleRef:
        kind: ClusterRole
        name: edit
        apiGroup: rbac.authorization.k8s.io

6.4 Role: openshift_network

roles/openshift_network/tasks/main.yml
---
# Default-deny ALL ingress first. Zero-trust starting point:
# nothing can reach pods in this namespace unless explicitly allowed below.
- name: Apply default-deny NetworkPolicy
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: networking.k8s.io/v1
      kind: NetworkPolicy
      metadata:
        name: default-deny-all
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        podSelector: {}
        policyTypes: [Ingress]

# Explicitly allow traffic from the OpenShift Router (so Routes work)
# and from pods within the same namespace (so multi-tier apps can talk).
- name: Allow router and same-namespace traffic
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: networking.k8s.io/v1
      kind: NetworkPolicy
      metadata:
        name: allow-router-and-internal
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        podSelector: {}
        ingress:
          - from:
              - namespaceSelector:
                  matchLabels:
                    network.openshift.io/policy-group: ingress
              - podSelector: {}
        policyTypes: [Ingress]

6.5 Role: openshift_application (baseline)

roles/openshift_application/tasks/main.yml
---
# A minimal, non-sensitive baseline ConfigMap every app can read
# to confirm which environment it's running in. Real app config
# is added later by the application team's own deploy pipeline.
- name: Seed baseline ConfigMap
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ConfigMap
      metadata:
        name: "{{ app_name }}-baseline"
        namespace: "{{ app_name }}-{{ environment }}"
      data:
        ENVIRONMENT: "{{ environment }}"
        TEAM: "{{ team }}"

7. Execution & Idempotency

Command
ansible-playbook -i inventories/dev playbooks/site.yml \
  -e app_name=payment-api -e environment=dev \
  -e team=payments -e owner=platform-team

First run — every task reports changed: nothing existed yet.

First run output (excerpt) 
PLAY RECAP *********************************************
localhost : ok=9  changed=9  unreachable=0  failed=0  skipped=0

Second run — identical input, identical objects already exist. This is the idempotency proof.

Second run output (excerpt) 
PLAY RECAP *********************************************
localhost : ok=9  changed=0  unreachable=0  failed=0  skipped=0
Why this matters changed=0 on the second run is the proof an SRE looks for before trusting a playbook in PROD. If a "safe to re-run" playbook shows changed every time, something is non-deterministic — usually a field the API server normalizes differently than how Ansible wrote it (e.g. resource quantities like "4" vs 4).

Validate
oc get project payment-api-dev
oc get resourcequota,limitrange -n payment-api-dev
oc get rolebinding -n payment-api-dev
oc get networkpolicy -n payment-api-dev
Command partMeaning
oc getRetrieve current state of a resource from the API server.
resourcequota,limitrangeComma-separated resource types — one API call, one combined table.
-n payment-api-devScopes the query to that namespace only.

8. Break-Fix Labs

Learning sequence for each: BUILD → VERIFY → BREAK → OBSERVE → TROUBLESHOOT → ROOT CAUSE → FIX → VALIDATE

Break-Fix 1 — Wrong project name variable
BreakRun with -e app_name=payment_api (underscore instead of hyphen).
TASK [openshift_project : Create OpenShift project] ***
fatal: [localhost]: FAILED! => {"msg": "Failure creating Project payment_api-dev: ... 
a DNS-1123 label must consist of lower case alphanumeric characters or '-' ..."}

Root cause: Kubernetes namespace names must be RFC 1123 DNS labels — no underscores. Fix: add an Ansible assert at the top of site.yml that validates app_name against a regex before any object is created, so the failure happens in 1 second instead of mid-run.

# Add near the top of site.yml, before the roles run:
- name: Validate app_name format
  ansible.builtin.assert:
    that:
      - app_name is match("^[a-z0-9]([-a-z0-9]*[a-z0-9])?$")
    fail_msg: "app_name must be lowercase alphanumeric with hyphens only"
Break-Fix 2 — Incorrect RBAC (group typo)
BreakA developer reports: "I can't deploy into payment-api-prod."
Investigate
oc auth can-i create deployments -n payment-api-prod --as=jane@company.com
> no

oc get rolebinding -n payment-api-prod -o yaml | grep -A2 subjects

Output shows the RoleBinding subject is payments-developers but the actual OIDC group is payment-developers (singular) — a typo in group_vars.

Root cause chainUser → Group membership (correct) → RoleBinding subject name (WRONG, typo) → no match → API server denies the request.

Fix: correct team: payments variable derivation or the group-naming template, re-run the playbook (idempotent — only the RoleBinding changes), validate with oc auth can-i again.

Break-Fix 3 — Quota too low, pods stuck Pending
BreakTeam deploys 25 pods into a namespace where quota_pod_count: 20.
oc get pods -n payment-api-prod
NAME                     READY   STATUS    RESTARTS
payment-api-6c8d-abcde   0/1     Pending   0

oc describe pod payment-api-6c8d-abcde -n payment-api-prod
Events:
  Warning  FailedCreate  ReplicaSet  pods "payment-api-..." is forbidden: 
  exceeded quota: payment-api-quota, requested: pods=1, used: pods=20, limited: pods=20

Root cause: ResourceQuota object count exceeded — not a scheduling or node capacity problem. Fix: raise quota_pod_count in inventories/prod/group_vars/all.yml deliberately (a reviewed, auditable change), re-run playbook, confirm pods schedule.

Break-Fix 4 — NetworkPolicy blocking legitimate traffic
BreakApplication works when accessed via oc exec from inside the pod, but the Route returns 503.
oc get networkpolicy -n payment-api-dev
NAME                        POD-SELECTOR
default-deny-all            <none>
# allow-router-and-internal is MISSING — it was never applied

Root cause: default-deny was applied but the allow-router policy task was skipped because of a bad when condition in an earlier edit. Fix: re-run openshift_network role, confirm both NetworkPolicies exist, re-test the Route.

10. Monitoring Checklist

  • Alert if ResourceQuota usage exceeds 90% of any hard limit (early warning before Pending pods).
  • Alert if a RoleBinding is created that references ClusterRole: admin or cluster-admin in an application namespace (policy drift detector).
  • Alert if a namespace exists with zero NetworkPolicy objects (misses the baseline).
  • Dashboard: count of provisioned namespaces per environment, quota utilization %, RBAC drift events.

12. Interview Preparation

Interviewer: "How would you design Ansible automation to provision OpenShift projects consistently across four environments?"

Answer: I'd separate what changes per environment (quota sizing, limits) from what doesn't (the object structure), using Ansible inventories with per-environment group_vars and roles that reference those variables rather than hardcoding values. Each concern — project, quota, RBAC, network, application baseline — gets its own role so it's independently testable and reusable. I'd use kubernetes.core.k8s with state: present for idempotency, add an upfront variable-validation step, and prove idempotency by running the playbook twice and checking for changed=0 on the second run.

Follow-up: "What if PROD needs an approval gate that DEV doesn't?" — I'd run this through Ansible Automation Platform Job Templates with a Workflow Template that adds an approval node before the PROD job template, rather than encoding approval logic inside the playbook itself.

Interviewer: "A developer says they can't deploy to their namespace. Walk me through your troubleshooting."

Answer: I check oc auth can-i create deployments -n <ns> --as=<user> first — that isolates it to RBAC immediately. If it says no, I check their group membership, then the RoleBinding's subject name and roleRef, then confirm the ClusterRole itself has the verb. I follow the chain User → Group → Role → RoleBinding → Namespace rather than guessing.

Interviewer: "How do you know your Ansible playbook is actually idempotent, not just claiming to be?"

Answer: I run it twice against the same target and check the play recap — a truly idempotent playbook shows changed=0 on the second run. If any task keeps reporting changed, I inspect that task's diff — it's usually a value normalization mismatch, like Ansible sending a quota as a string and the API server storing it differently.

Interviewer: "Why RoleBinding and not ClusterRoleBinding here?"

Answer: ClusterRoleBinding grants the permission across every namespace in the cluster. Application teams should only ever operate in their own namespace, so RoleBinding — which references a ClusterRole but scopes the grant to one namespace — is the least-privilege choice.

Manager round: "How do you make sure this doesn't become 'shadow IT' where teams bypass it?"

Answer: Make it the path of least resistance — a single Job Template survey in Automation Controller is faster than manual oc commands, and tie it to a Git-tracked request so there's an audit trail. Removing direct edit/admin self-service project creation from users also removes the incentive to go around it.

15. Key Learnings

OpenShift concepts

Project vs Namespace, ResourceQuota, LimitRange, RoleBinding vs ClusterRoleBinding, default-deny NetworkPolicy pattern, router traffic allow-listing.

Ansible concepts

kubernetes.core.k8s module, idempotency verification via repeated runs, role decomposition by concern, environment-scoped group_vars, upfront assert validation.

Commands learned

oc get, oc describe, oc auth can-i --as=, ansible-playbook -e, quota/limitrange inspection.

Troubleshooting method learned

Follow the object chain (User → Group → Role → RoleBinding → Namespace) rather than guessing; use describe events as the first evidence source.

Common mistakes

Underscore in namespace names; typo'd group names in RoleBinding subjects; forgetting the allow-NetworkPolicy after default-deny; hardcoding quota values inside role tasks instead of group_vars.
