1. The Production Story

Scenario An internal reporting team wants to deploy a legacy vendor image onto payment-api's namespace to generate compliance reports from the database. The image's Dockerfile hardcodes USER root and expects to run as UID 0. Their pod immediately fails to start.
Business Problem The fastest "fix" — granting the anyuid or worse, privileged, SCC to the namespace's default ServiceAccount — would undo every least-privilege control built since Project 1 and 2, cluster-wide within that namespace, for every pod, not just this one image.
Our Mandate Understand SCC admission well enough to grant the legacy image exactly what it needs — nothing more — scoped to only its own ServiceAccount, and automate that scoping correctly with Ansible.

3. Architecture

ConceptSCCs don't attach to Pods directly — they're evaluated at admission time against the identity (ServiceAccount) creating the Pod. The API server tries every SCC the caller's ServiceAccount has access to, in priority order, and admits the Pod using the first SCC whose constraints the Pod spec satisfies. This is why "the pod is failing because of SCC" almost always traces back to WHICH ServiceAccount it's using, not a property of the image itself.
Pod creation request (as ServiceAccount X) │ ▼ API server collects all SCCs ServiceAccount X can use (via RBAC: 'use' verb on the SCC resource) │ ▼ Sorted by priority (custom SCCs can out-rank defaults) │ ▼ First SCC whose constraints the Pod spec satisfies → Pod ADMITTED using that SCC's UID range / capabilities / volume types │ ▼ If NO SCC in the list satisfies the Pod spec → Pod REJECTED ("unable to validate against any security context constraint")
SCC (built-in)Key constraint
restricted-v2Default for most workloads; random UID from namespace range, no privilege escalation, drops ALL capabilities
nonroot-v2Any non-zero UID the container specifies, but not root
anyuidAllows the container to run as ANY UID including root — broad, avoid unless truly required
privilegedEssentially unrestricted — host access, all capabilities — reserved for infrastructure components only

4. The Playbooks — Fully Commented

4.1 roles/legacy_workload_scc/tasks/main.yml

roles/legacy_workload_scc/tasks/main.yml
---
# Grants root-equivalent UID access ONLY to a dedicated
# ServiceAccount for this one legacy workload -- never to the
# namespace's default ServiceAccount, and never anyuid/privileged
# cluster-wide.

- name: Create a DEDICATED ServiceAccount for the legacy workload             # isolation is the whole point -- never reuse the default SA
  kubernetes.core.k8s:
    state: present                                                             # idempotent create-or-update
    definition:
      apiVersion: v1
      kind: ServiceAccount
      metadata:
        name: "{{ app_name }}-legacy-report-sa"                                 # purpose-specific name, not generic
        namespace: "{{ app_name }}-{{ environment }}"
  register: sa_result                                                            # capture for assert

- name: Assert ServiceAccount creation succeeded
  ansible.builtin.assert:
    that: [sa_result is succeeded]
    fail_msg: "Failed to create legacy-report ServiceAccount"

- name: Create a MINIMAL custom SCC allowing only what this image needs         # narrower than anyuid -- pinned to the EXACT UID the image needs, not any UID
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: security.openshift.io/v1                                       # SCC's own API group
      kind: SecurityContextConstraints
      metadata:
        name: "{{ app_name }}-legacy-report-scc"                                   # descriptive, purpose-specific name
      allowPrivilegedContainer: false                                               # explicitly NOT privileged -- this is the critical difference from the tempting shortcut
      allowPrivilegeEscalation: false                                               # blocks setuid-style escalation even within the container
      runAsUser:
        type: MustRunAs                                                              # pins to an EXACT uid, not MustRunAsRange (any) or RunAsAny (unrestricted)
        uid: 0                                                                        # the specific UID this legacy image requires -- root, but ONLY this exact identity, not a free-for-all
      seLinuxContext:
        type: MustRunAs                                                               # still enforce SELinux confinement -- narrowing UID doesn't mean abandoning other controls
      fsGroup:
        type: MustRunAs                                                                # still constrain filesystem group ownership
      supplementalGroups:
        type: MustRunAs
      volumes: ["configMap", "secret", "emptyDir", "persistentVolumeClaim"]              # explicit allow-list -- no hostPath, no other risky volume types
      users: []                                                                          # users field left empty -- access is granted via RBAC 'use' verb below, not listed here directly
  register: scc_result

- name: Assert custom SCC creation succeeded
  ansible.builtin.assert:
    that: [scc_result is succeeded]
    fail_msg: "Failed to create legacy-report SCC"

- name: Grant ONLY the dedicated ServiceAccount permission to 'use' this SCC        # the actual narrow grant -- this is what limits blast radius
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: rbac.authorization.k8s.io/v1                                        # standard RBAC API, same pattern as Project 2
      kind: RoleBinding                                                                # namespace-scoped, not ClusterRoleBinding
      metadata:
        name: "{{ app_name }}-legacy-report-scc-binding"
        namespace: "{{ app_name }}-{{ environment }}"
      subjects:
        - kind: ServiceAccount                                                          # subject is the SPECIFIC ServiceAccount, not a human group
          name: "{{ app_name }}-legacy-report-sa"                                         # must match the SA created above exactly
          namespace: "{{ app_name }}-{{ environment }}"
      roleRef:
        kind: ClusterRole                                                                 # SCC 'use' access is granted via a ClusterRole that wraps the SCC resource
        name: "system:openshift:scc:{{ app_name }}-legacy-report-scc"                       # OpenShift auto-generates this ClusterRole name per SCC
        apiGroup: rbac.authorization.k8s.io
  register: binding_result

- name: Assert SCC RoleBinding succeeded                                                    # fail loudly rather than leaving the SA unable to use its own SCC
  ansible.builtin.assert:
    that: [binding_result is succeeded]
    fail_msg: "Failed to bind {{ app_name }}-legacy-report-sa to its SCC"

6. Live Incident — "Pod Failing Because It Expects to Run as Root"

ReportThe reporting team's pod is stuck in CreateContainerConfigError.
Step 1 — check the actual admission error
oc describe pod legacy-report -n payment-api-dev
Events:
  Warning  FailedCreate  unable to validate against any security context
    constraint: [provider "restricted-v2": .spec.securityContext.runAsUser:
    Invalid value: 0: must be in the ranges: [1000660000, 1000669999]]
Root causeThe pod is running under the namespace's DEFAULT ServiceAccount, which only has access to restricted-v2 — and that SCC enforces a random non-root UID range. This confirms it's an SCC/identity problem, not an image problem per se.
Step 2 — the tempting-but-wrong fix (shown for contrast, NOT what we do)
Anti-patternoc adm policy add-scc-to-user anyuid -z default -n payment-api-dev would "fix" this instantly — and also silently grant every OTHER pod using the default ServiceAccount in this namespace the ability to run as root, undoing Project 1's baseline for the entire namespace, not just this one workload.
Step 3 — the correct fix: apply this project's scoped role, then redeploy using the dedicated SA
ansible-playbook playbooks/legacy_scc.yml -e app_name=payment-api -e environment=dev

oc delete pod legacy-report -n payment-api-dev
oc run legacy-report --image=quay.io/example/legacy-report:1.0 -n payment-api-dev \
  --overrides='{"spec":{"serviceAccountName":"payment-api-legacy-report-sa"}}'   # explicitly uses the scoped SA, not default
Step 4 — validate
oc get pod legacy-report -n payment-api-dev
NAME            READY   STATUS    RESTARTS
legacy-report   1/1     Running   0

oc get pod legacy-report -n payment-api-dev -o jsonpath='{.spec.securityContext.runAsUser}'
0   # running as root, but ONLY this pod, ONLY via its own dedicated SA and SCC
Step 5 — confirm the blast radius is actually contained
oc auth can-i use scc/payment-api-legacy-report-scc --as=system:serviceaccount:payment-api-dev:default
no   # confirmed -- the default ServiceAccount still cannot use this SCC
ResolvedThe legacy workload runs as required, and every other pod in the namespace remains under restricted-v2 exactly as Project 1 intended.

7. Additional Break-Fix Labs

Break-Fix — custom SCC created but pod still rejected 
Events: unable to validate against any security context constraint

Root cause: the RoleBinding referenced the wrong auto-generated ClusterRole name (a typo in system:openshift:scc:<name>). Fix: confirm the exact SCC name matches character-for-character between the SCC object and the RoleBinding's roleRef.name — this naming convention is exact and case-sensitive.

Break-Fix — SCC works in DEV but fails in PROD

Symptom: the same playbook run against PROD still fails admission.

Root cause: PROD's namespace UID range (set at namespace creation) differs from DEV's, and the custom SCC's uid: 0 pin doesn't depend on that — but double check the Pod spec explicitly sets securityContext.runAsUser: 0 too; SCC permits it, but the Pod spec must still request it explicitly in some OpenShift versions.

9. Interview Preparation

Interviewer: "A pod needs to run as root — how do you handle that in OpenShift?"

Answer: I never grant anyuid or privileged broadly to solve a single workload's requirement — that affects every pod under whatever ServiceAccount receives it. Instead I create a dedicated ServiceAccount just for that workload, a custom SCC pinned to the exact UID it needs with every other constraint left as restrictive as possible, and a RoleBinding granting 'use' access to only that ServiceAccount. The blast radius stays limited to exactly the one workload that actually needs the exception.

Interviewer: "How does OpenShift decide which SCC a pod actually gets?"

Answer: It's evaluated per the ServiceAccount creating the pod, not the pod spec alone — the API server collects every SCC that ServiceAccount has 'use' access to via RBAC, sorts them by priority, and admits using the first one whose constraints the pod spec satisfies. That's why the same pod spec can succeed or fail purely based on which ServiceAccount it's submitted under — which is also why troubleshooting SCC issues starts with identifying the ServiceAccount, not the image.

12. Key Learnings

OpenShift concepts

SCC admission is ServiceAccount-driven, not pod-spec-driven in isolation; SCC priority/ordering; the difference between MustRunAs, MustRunAsRange, and RunAsAny; why anyuid/privileged are namespace/cluster-wide risks, not single-pod fixes.

Ansible concepts

Modeling a three-object security pattern (ServiceAccount + SCC + RoleBinding) as one cohesive, idempotent role; verifying a security grant's actual scope with a follow-up can-i-style check rather than assuming the RBAC was correct.

Commands learned

oc get scc, oc describe scc, oc auth can-i use scc/..., reading SCC-related Pod admission failure events.

Common mistakes

Granting anyuid/privileged to a shared ServiceAccount instead of scoping a dedicated one; typos in the auto-generated SCC ClusterRole name; forgetting to also constrain volumes/capabilities while relaxing the UID requirement.
