1. The Production Story

Scenario Twenty-four projects of safeguards are now in place: HPA, self-healing GitOps, scripted rollback, backup/DR, admission policy, promotion chains. Leadership's question is fair: "how do we KNOW all of this actually works together, instead of just individually in each project's lab?" The only real answer is deliberately breaking things on purpose and watching what happens.
Business Problem Every safeguard so far has been tested in isolation, in its own project. Nobody has verified that, say, a node failure during a deploy during high load behaves the way the sum of Projects 5, 10, and 11 would predict.
Our Mandate Build a small, safe, Ansible-driven chaos toolkit (pod kill, node cordon, network delay, dependency failure injection) and run a structured game day against payment-api in a non-PROD environment, treating it exactly like Project 16's incident framework — including a real RCA.

3. Architecture

ConceptA good chaos experiment has a hypothesis stated BEFORE it runs — "if we kill a backend pod, the HPA/Deployment should replace it within 30 seconds with zero dropped requests, because of Projects 3/5/10" — and the experiment either confirms or disproves that hypothesis with evidence. Chaos without a hypothesis is just breaking things; chaos WITH one is an experiment.
For each experiment: 1. STATE the hypothesis (which safeguard should catch this, from which project) 2. Record baseline (Project 16's evidence-collection pattern) 3. INJECT the failure 4. Observe: did the expected safeguard actually engage? 5. Measure: how long did recovery take? 6. Record result: hypothesis CONFIRMED or DISPROVEN 7. If disproven -- this becomes a real backlog item, same severity process as Project 16's incident framework

4. The Playbooks — Fully Commented

4.1 playbooks/chaos/pod_kill.yml

playbooks/chaos/pod_kill.yml
---
# Chaos Experiment: Pod Kill
# Hypothesis: killing one backend pod results in a replacement pod
# becoming Ready within 30 seconds, with zero request failures,
# because of the Deployment controller and readiness probes built
# in Project 3.
- name: "Chaos experiment: pod kill"
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: SAFETY CHECK -- refuse to run against payment-api-prod            # hard-coded guardrail, not just a warning
      ansible.builtin.assert:
        that:
          - environment != 'prod'                                              # this experiment class never runs against PROD in this playbook
        fail_msg: "Refusing to run chaos experiments against PROD -- use a game day change window with explicit sign-off instead"

    - name: Record baseline pod count and readiness before injection             # the 'before' picture -- needed to measure recovery
      kubernetes.core.k8s_info:
        kind: Pod
        namespace: "{{ app_name }}-{{ environment }}"
        label_selectors: ["app={{ app_name }}-backend"]
      register: baseline_pods                                                    # holds pre-experiment pod state

    - name: INJECT -- delete one backend pod                                       # the actual chaos action
      kubernetes.core.k8s:
        state: absent                                                              # deletes the specific object
        kind: Pod
        name: "{{ baseline_pods.resources[0].metadata.name }}"                       # targets exactly ONE pod -- controlled blast radius
        namespace: "{{ app_name }}-{{ environment }}"
      register: kill_result                                                          # capture for the record

    - name: Start timing recovery                                                      # marks T+0 for the hypothesis's 30-second claim
      ansible.builtin.set_fact:
        injection_time: "{{ ansible_date_time.epoch }}"                                  # epoch seconds for easy math later

    - name: OBSERVE -- wait for replacement pod to become Ready                          # tests the actual hypothesis
      kubernetes.core.k8s_info:
        kind: Pod
        namespace: "{{ app_name }}-{{ environment }}"
        label_selectors: ["app={{ app_name }}-backend"]
      register: recovery_check                                                            # re-polled repeatedly by the until loop
      until: >
        (recovery_check.resources | selectattr('status.phase','equalto','Running')
         | selectattr('status.containerStatuses.0.ready','equalto',true) | list | length)
        == (baseline_pods.resources | length)                                                # back to the same Ready count as baseline
      retries: 30                                                                              # poll for up to 30 * 2s = 60s -- generous margin beyond the 30s hypothesis
      delay: 2

    - name: Calculate actual recovery time                                                      # the measured result, compared against the stated hypothesis
      ansible.builtin.set_fact:
        recovery_seconds: "{{ ansible_date_time.epoch | int - injection_time | int }}"

    - name: Record the experiment result as evidence                                              # same evidence-first discipline as Project 16
      ansible.builtin.copy:
        dest: "gamedays/{{ app_name }}/pod-kill-{{ ansible_date_time.epoch }}.json"
        content: "{{ {
            'experiment': 'pod_kill',
            'hypothesis': 'replacement Ready within 30s',
            'measured_recovery_seconds': recovery_seconds,
            'hypothesis_confirmed': (recovery_seconds | int) <= 30,                             # the actual pass/fail judgment, recorded as data
            'timestamp': ansible_date_time.iso8601
          } | to_nice_json }}"

    - name: Report result                                                                          # immediate human-readable feedback
      ansible.builtin.debug:
        msg: "Recovery took {{ recovery_seconds }}s -- hypothesis {{ 'CONFIRMED' if (recovery_seconds | int) <= 30 else 'DISPROVEN' }}"

4.2 playbooks/chaos/gameday.yml

playbooks/chaos/gameday.yml
---
# Orchestrates the full game day: runs each experiment in sequence,
# with a cooldown between them, and produces a single summary report.
- name: Payment-API Game Day
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: SAFETY CHECK -- confirm non-PROD target                              # same hard guardrail, checked again at the orchestration level
      ansible.builtin.assert:
        that: [environment != 'prod']
        fail_msg: "Game days run in non-PROD only within this playbook"

    - name: Snapshot pre-gameday cluster health (Project 11's pattern)              # baseline before ANY experiment runs
      ansible.builtin.import_tasks: cluster_health_checks.yml                         # the same shared tasks file used since Project 11

    - name: Experiment 1 -- Pod Kill                                                  # delegates to the standalone experiment playbook
      ansible.builtin.include_tasks: pod_kill_tasks.yml                                # extracted task-only version of Section 4.1's logic

    - name: Cooldown between experiments                                                # avoid compounding effects that make results hard to attribute
      ansible.builtin.pause:
        seconds: 60                                                                       # deliberate pause -- lets the system fully settle

    - name: Experiment 2 -- Node Cordon and Drain                                          # tests Project 11/12's rescheduling behavior
      ansible.builtin.include_tasks: node_cordon_tasks.yml

    - name: Cooldown
      ansible.builtin.pause: {seconds: 60}

    - name: Experiment 3 -- Config Deletion (GitOps self-heal check)                          # tests Project 17's selfHeal specifically
      ansible.builtin.include_tasks: config_delete_tasks.yml

    - name: Snapshot post-gameday cluster health                                                # confirms the cluster ends in a healthy state, not just that each experiment individually recovered
      ansible.builtin.import_tasks: cluster_health_checks.yml

    - name: Assert cluster is fully healthy after the full game day                               # the final, cumulative pass/fail gate
      ansible.builtin.assert:
        that:
          - not_ready_nodes | length == 0
          - degraded_operators | length == 0
        fail_msg: "Cluster did NOT return to full health after the game day -- treat as a real incident (Project 16)"

6.1 Real Finding: Missing Pod Anti-Affinity

The actual gap this game day foundThe CloudNativePG Cluster CR from Project 7 never configured pod anti-affinity, so nothing prevented 2 of 3 database replicas from landing on the SAME node — meaning a single node failure could take out a majority of the database cluster at once, a much bigger blast radius than intended.
Fix — add anti-affinity to the CloudNativePG Cluster spec via Ansible
# Addition to Project 7's roles/postgres_cluster/tasks/main.yml Cluster CR:
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:              # soft preference -- CloudNativePG has its own primitive too, shown for the general pattern
        - weight: 100                                                  # strong preference, not a hard requirement (avoids scheduling deadlock at 3 nodes)
          podAffinityTerm:
            labelSelector:
              matchLabels: {cnpg.io/cluster: "{{ app_name }}-pg"}         # spreads replicas of the SAME cluster apart
            topologyKey: kubernetes.io/hostname                            # spread across distinct nodes
ansible-playbook playbooks/postgres_cluster.yml -e app_name=payment-api -e environment=dev

7. Additional Break-Fix Labs

Break-Fix — chaos experiment itself hangs indefinitely 
TASK [OBSERVE -- wait for replacement pod to become Ready] ***
# still running after several minutes, no timeout hit yet

Root cause: a missing or too-generous retries value can leave an experiment running long after it's clear the hypothesis has failed. Fix: always set a firm retries/delay ceiling well beyond the hypothesis threshold but not unbounded — the goal is a clear disproven result, not an infinite hang.

Break-Fix — experiment accidentally targets more than intended
BreakA label selector typo in a custom experiment matches pods across MULTIPLE apps, not just payment-api.

Root cause: insufficiently scoped selector. Fix: always dry-run new experiments with --check first, and require the selector to include both app AND a namespace scope explicitly — never rely on namespace alone to limit blast radius.

9. Interview Preparation

Interviewer: "Why run chaos experiments if you already have monitoring, alerting, and DR tested individually?"

Answer: Because individual safeguards can each work perfectly in isolation and still fail together — in our game day, the database's HA replica count was fine, PodDisruptionBudgets were fine, but nobody had configured anti-affinity, so a single node held a majority of database replicas without anyone noticing until we deliberately drained that node. That's a real availability gap that no single project's own testing would surface, because it only exists at the intersection of two different concerns.

Interviewer: "How do you structure a chaos experiment so it's useful, not just destructive?"

Answer: State a specific, falsifiable hypothesis before running it — which safeguard should catch this, and within what time bound — then measure the actual outcome against that hypothesis and record it as evidence, confirmed or disproven. A disproven hypothesis becomes a tracked backlog item with the same rigor as a real incident's RCA, which is exactly what happened with our anti-affinity gap.
