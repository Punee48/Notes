1. The Production Story

Scenario Compliance flags that payment-api has no documented, tested disaster recovery process. There's a vague assumption that "the database has snapshots somewhere," but nobody has ever actually tried to restore from them. The company needs a defined RTO/RPO and proof that recovery actually works.
Business Problem An untested backup is not a backup — it's a hope. We need to know, concretely, how long recovery takes and whether it actually works, before an auditor or a real disaster forces us to find out the hard way.
Our Mandate Define RTO/RPO targets, automate application-level backup (CloudNativePG's built-in backup plus a manifest export of every Ansible-managed object), and run a full restore drill against a simulated disaster.

2. Run This On Your Device

Scope noteetcd backup/restore is a cluster-admin, node-level operation typically run via oc adm scripts provided by Red Hat, not something to reinvent in Ansible — this project automates the pre-check and application-level backup/restore, and treats etcd backup as an operational prerequisite we verify exists.

4. The Playbooks — Fully Commented

4.1 roles/dr_backup/tasks/main.yml

roles/dr_backup/tasks/main.yml
---
# Triggers a CloudNativePG backup and exports every Ansible-managed
# manifest for this app/environment as a point-in-time record.

- name: Verify etcd backup is configured as a cluster prerequisite         # read-only check, NOT an attempt to script etcd backup ourselves
  ansible.builtin.stat:                                                     # checks for a marker file our platform team's separate etcd-backup cronjob writes
    path: /var/run/etcd-backup-last-success                                  # convention: that job touches this file on each successful run
  register: etcd_marker                                                       # holds file existence/mtime info
  delegate_to: localhost                                                       # runs on the Ansible control node, not against the cluster API

- name: Warn if etcd backup hasn't run recently                                # advisory, not a hard failure -- etcd backup is out of this role's scope
  ansible.builtin.debug:
    msg: "WARNING: etcd backup marker missing or stale -- confirm the platform-level etcd backup job is healthy"
  when: not etcd_marker.stat.exists                                             # only warns, doesn't stop the play

- name: Trigger an on-demand CloudNativePG Backup                               # the actual application data backup
  kubernetes.core.k8s:
    state: present                                                              # creating a Backup CR triggers the Operator to act
    definition:
      apiVersion: postgresql.cnpg.io/v1                                          # same Operator CRD API group as Project 7
      kind: Backup                                                                # CloudNativePG's on-demand backup CRD
      metadata:
        name: "{{ app_name }}-backup-{{ ansible_date_time.epoch }}"                 # unique name per run using the current epoch timestamp
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        cluster:
          name: "{{ app_name }}-pg"                                                 # must match the Cluster CR name from Project 7
  register: backup_result                                                            # capture for the wait below

- name: Assert Backup CR creation succeeded                                           # fail fast on API rejection
  ansible.builtin.assert:
    that: [backup_result is succeeded]
    fail_msg: "Failed to trigger backup for {{ app_name }}-pg"

- name: Wait for the backup to complete                                               # confirms the backup actually finished, not just started
  kubernetes.core.k8s_info:
    kind: Backup
    api_version: postgresql.cnpg.io/v1
    name: "{{ backup_result.result.metadata.name }}"                                    # the exact backup object we just created
    namespace: "{{ app_name }}-{{ environment }}"
  register: backup_status                                                                # holds live .status.phase
  until: backup_status.resources[0].status.phase | default('') == "completed"             # CloudNativePG's own success phase string
  retries: 30                                                                              # database backups can take a few minutes for larger datasets
  delay: 10

- name: Export every Ansible-managed manifest as a point-in-time record                     # covers everything OUTSIDE the database itself
  ansible.builtin.shell: |                                                                    # shell used here deliberately for oc's native export capability
    oc get all,configmap,secret,pvc,route,rolebinding,networkpolicy \
      -n {{ app_name }}-{{ environment }} -o yaml \
      > backups/{{ app_name }}-{{ environment }}-{{ ansible_date_time.date }}.yaml   # dated filename -- one snapshot per day, kept in Git or object storage
  args:
    creates: "backups/{{ app_name }}-{{ environment }}-{{ ansible_date_time.date }}.yaml"  # idempotency for the shell task -- skips if today's export already exists
  changed_when: true                                                                          # explicit -- shell tasks don't auto-detect changed state

4.2 playbooks/restore.yml

playbooks/restore.yml
---
# Full restore drill -- reuses EVERY prior project's playbooks in
# sequence, then restores the database from the latest Backup CR.
- name: Disaster recovery restore
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: Rebuild namespace baseline (Project 1)                          # same role, same idempotent apply logic -- nothing DR-specific here
      ansible.builtin.include_role: {name: openshift_project}
    - ansible.builtin.include_role: {name: openshift_quota}
      name: Rebuild quota (Project 1)

    - name: Rebuild RBAC (Project 2)                                        # restores access before anyone needs it post-restore
      ansible.builtin.include_role: {name: openshift_rbac}

    - name: Rebuild network policy (Project 1)
      ansible.builtin.include_role: {name: openshift_network}

    - name: Restore PostgreSQL from the latest Backup CR                     # the actual data recovery step
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: postgresql.cnpg.io/v1
          kind: Cluster                                                        # CloudNativePG restores by creating a NEW Cluster from a backup source
          metadata:
            name: "{{ app_name }}-pg"
            namespace: "{{ app_name }}-{{ environment }}"
          spec:
            instances: "{{ pg_instance_count | default(3) }}"
            bootstrap:
              recovery:                                                          # recovery bootstrap mode instead of initdb
                source: "{{ app_name }}-backup-source"                             # references the backup's external cluster definition
            externalClusters:
              - name: "{{ app_name }}-backup-source"
                barmanObjectStore:
                  destinationPath: "{{ backup_object_storage_path }}"               # where CloudNativePG's backups actually live
      register: restore_result

    - name: Wait for restored cluster to be healthy                            # same pattern as Project 7's original cluster creation
      kubernetes.core.k8s_info:
        kind: Cluster
        api_version: postgresql.cnpg.io/v1
        name: "{{ app_name }}-pg"
        namespace: "{{ app_name }}-{{ environment }}"
      register: restore_status
      until: restore_status.resources[0].status.phase | default('') == "Cluster in healthy state"
      retries: 40
      delay: 15

    - name: Re-apply application tiers (Projects 3-4)                          # backend, frontend, Route/TLS -- all idempotent, safe to reapply
      ansible.builtin.include_role: {name: backend}
    - ansible.builtin.include_role: {name: frontend}
      name: Re-apply frontend (Project 3-4)

    - name: Run post-upgrade validation as the restore's final proof           # reuses Project 13's playbook -- same bar as any other health confirmation
      ansible.builtin.import_tasks: post_upgrade_validate_tasks.yml             # extracted shared tasks, same pattern as Project 13

5. Execution & Idempotency

ansible-playbook playbooks/backup.yml -e app_name=payment-api -e environment=dev
First run
PLAY RECAP *** ok=6 changed=3 failed=0
Note on idempotency hereBackup triggers are intentionally NOT idempotent in the usual sense — running the playbook again should create a NEW backup, not skip because one already exists. The creates: guard on the manifest export is date-scoped specifically so it's idempotent per-day, not per-run.

7. Additional Break-Fix Labs

Break-Fix — restore fails, backup object storage path wrong 
TASK [Wait for restored cluster to be healthy] ***
fatal: [localhost]: FAILED! => {"msg": "Timeout waiting for cluster.status.phase"}

oc describe cluster payment-api-pg -n payment-api-dev
Message: failed to connect to object store: NoSuchBucket

Root cause: the backup_object_storage_path variable pointed at the wrong bucket/environment. Fix: store this per-environment in group_vars (same pattern as every other environment-specific value in this series) rather than typing it by hand during a drill.

Break-Fix — manifest export missing a resource type

Symptom: after restore, a custom Secret referenced by the app is missing — it wasn't in the exported manifest list.

Root cause: the oc get resource-type list in Section 4.1 didn't include every object kind actually in use. Fix: maintain that list deliberately as new object types are introduced (e.g. Project 8's ServiceMonitor/PrometheusRule, Project 9's ClusterLogForwarder) rather than assuming it's complete forever.

9. Interview Preparation

Interviewer: "How do you know your backups actually work?"

Answer: By restoring from them, on a schedule, not just taking them. We run a quarterly DR drill that deletes an entire namespace in a disposable environment and times a full recovery using the same Ansible playbooks we'd use in a real disaster — namespace, RBAC, database restore, application tiers, then the same validation suite from our upgrade process. That drill is what actually proves the RTO/RPO numbers, not the backup schedule alone.

Interviewer: "How did you decide the RTO and RPO targets?"

Answer: RPO followed directly from how frequently we could reasonably archive WAL data without adding meaningful overhead — 15 minutes. RTO of 30 minutes was a business conversation, then validated against what our drill actually achieves; we found the database restore step is the largest chunk of that time, which tells us where to focus if the business ever needs a tighter RTO.
