1. The Production Story

Scenario The payment-api stack from Project 3 is running. Now the security team requires all customer-facing Routes to use re-encrypt TLS (not just edge) so traffic is encrypted all the way to the pod, and a customer just reported the app "sometimes shows a 503 error." We need to both automate the Route/TLS upgrade and build the muscle memory to debug traffic issues under pressure.
Business Problem Routes were being hand-created with inconsistent TLS modes — some edge, some passthrough, one with no redirect policy at all, meaning users could load the payment page over plain HTTP.
Our Mandate Standardize Route creation via Ansible with re-encrypt TLS and enforced HTTPS redirect, and build a repeatable troubleshooting method for Route-layer incidents.

3. Traffic Flow — The Path Every Request Takes

User Browser │ DNS resolves *.apps.cluster.example.com ▼ OpenShift Router (HAProxy) — reads the Route's host + TLS config │ terminates/re-encrypts TLS per Route spec ▼ Service (ClusterIP) — payment-api-frontend │ selects pods by label, load-balances across endpoints ▼ Pod — matched by Service selector, must be Ready │ ▼ Container — actually serves the HTTP response
Why this order matters for troubleshootingWork top-down: DNS resolves? Route exists and admitted? Router has it configured? Service has endpoints? Pod is Ready? Each layer's failure produces a different symptom, so identifying which layer is broken narrows the investigation immediately.

3.1 TLS Termination Modes

ModeWhere TLS endsUse case
EdgeAt the RouterSimple HTTPS sites; backend traffic is plain HTTP internally
PassthroughAt the PodApp terminates its own TLS; Router only forwards encrypted bytes
Re-encryptRouter decrypts, then re-encrypts to the Pod with a separate certCompliance requirement for end-to-end encryption (our case here)

4. The Playbooks — Fully Commented

4.1 roles/route_tls/tasks/main.yml

roles/route_tls/tasks/main.yml
---
# Upgrades the frontend Route from edge to re-encrypt TLS, per the
# security team's new requirement for end-to-end encryption.

- name: Store destination CA cert as a ConfigMap                    # Router needs this to trust the backend pod's cert
  kubernetes.core.k8s:                                               # declarative apply module
    state: present                                                   # create-or-update
    definition:
      apiVersion: v1                                                  # core API group
      kind: ConfigMap                                                 # plain data object -- CA cert is public, not secret
      metadata:
        name: "{{ app_name }}-dest-ca"
        namespace: "{{ app_name }}-{{ environment }}"
      data:
        ca.crt: "{{ dest_ca_cert }}"                                    # PEM-encoded CA cert passed in as a variable

- name: Configure Route with re-encrypt TLS termination                # the main object being changed
  kubernetes.core.k8s:
    state: present                                                     # idempotent update if the Route already exists
    definition:
      apiVersion: route.openshift.io/v1                                 # OpenShift-specific Route API
      kind: Route
      metadata:
        name: "{{ app_name }}-frontend"                                  # must match the existing Route name from Project 3
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        to:
          kind: Service                                                  # backing object type
          name: "{{ app_name }}-frontend"                                 # unchanged from Project 3
        tls:
          termination: reencrypt                                          # CHANGED from 'edge' -- Router decrypts, re-encrypts to pod
          insecureEdgeTerminationPolicy: Redirect                          # still force HTTP -> HTTPS for any plain requests
          destinationCACertificate: "{{ dest_ca_cert }}"                    # tells the Router which CA to trust for the backend leg
  register: route_result                                                  # capture for the assert below

- name: Assert Route update succeeded                                     # fail the play instead of silently leaving old TLS mode
  ansible.builtin.assert:
    that:
      - route_result is succeeded
    fail_msg: "Failed to update TLS termination for {{ app_name }}-frontend"

- name: Read back the Route to confirm admitted status                    # READ-ONLY check -- confirms the Router actually accepted it
  kubernetes.core.k8s_info:                                                # info module never mutates state
    kind: Route
    api_version: route.openshift.io/v1
    name: "{{ app_name }}-frontend"
    namespace: "{{ app_name }}-{{ environment }}"
  register: route_status                                                   # holds .status.ingress[].conditions

- name: Fail if the Route was not admitted by the Router                   # catches DNS/host conflicts that 'present' alone won't surface
  ansible.builtin.assert:
    that:
      - route_status.resources[0].status.ingress[0].conditions[0].status == "True"  # Admitted condition must be True
    fail_msg: "Route exists but was NOT admitted -- check for a host conflict"

6. Live Incident — Intermittent 503s

ReportCustomers occasionally see "503 Service Unavailable" when loading the payment page. It's not constant — refreshing sometimes works.
Step 1 — is the Route admitted?
oc get route payment-api-frontend -n payment-api-dev
NAME                    HOST/PORT                     ADMITTED
payment-api-frontend    payment-api-dev.apps...       True

Route is fine. Move down a layer.

Step 2 — check Service endpoints
oc get endpoints payment-api-frontend -n payment-api-dev
NAME                    ENDPOINTS
payment-api-frontend    10.128.2.14:8080

Only one endpoint listed, but the Deployment specifies 3 replicas.

Step 3 — check pod status
oc get pods -n payment-api-dev -l app=payment-api-frontend
NAME                          READY   STATUS    RESTARTS
payment-api-frontend-7f-a1    1/1     Running   0
payment-api-frontend-7f-b2    0/1     Running   0
payment-api-frontend-7f-c3    0/1     Running   0

Two of three pods are Running but not Ready — the "intermittent" symptom is the Router load-balancing across a mix of ready and not-ready pods, and OpenShift only routes to Ready ones — except a brief window right after a rolling update where the Router's view lags slightly.

Step 4 — why aren't they Ready?
oc describe pod payment-api-frontend-7f-b2 -n payment-api-dev
Warning  Unhealthy  Readiness probe failed: HTTP probe failed with statuscode: 500
oc logs payment-api-frontend-7f-b2 -n payment-api-dev
Error: cannot reach backend service payment-api-backend:8080 -- connection refused
Root causeThe frontend's readiness probe depends on reaching the backend, and 2 of 3 backend pods were mid-rollout (from an unrelated backend deploy happening at the same time) and briefly unreachable, cascading into frontend readiness failures.

Fix: not a Route/TLS problem at all — the fix is adding a maxUnavailable: 0 rolling update strategy on the backend Deployment so old pods aren't removed until new ones are Ready, preventing this cascade during future rollouts.

# Add to backend Deployment spec.strategy in Project 3's role:
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0        # never drop below full capacity during a rollout
    maxSurge: 1               # allow one extra pod temporarily while updating

7. Additional Break-Fix Labs

Break-Fix — wrong TLS termination causes browser cert error
BreakSet termination: passthrough but the pod is only listening on plain HTTP, not HTTPS.
curl -v https://payment-api-dev.apps.cluster.example.com
curl: (35) OpenSSL SSL_connect: Connection reset by peer

Root cause: passthrough mode requires the pod itself to terminate TLS; ours only speaks HTTP. Fix: either switch back to edge/reencrypt (Router or app doesn't need its own TLS), or make the app actually serve HTTPS if passthrough is a hard requirement.

Break-Fix — 404 from Route, correct host, wrong Service name 
oc get route payment-api-frontend -o yaml -n payment-api-dev
spec:
  to:
    name: payment-frontend    # typo -- actual Service is payment-api-frontend

Root cause: Route's spec.to.name doesn't match any real Service, so the Router returns 503/404 depending on version. Fix: correct the to.name via the Ansible variable, re-run, re-test.

9. Interview Preparation

Interviewer: "A user reports intermittent 503s on a Route. How do you troubleshoot?"

Answer: I go top-down through the traffic path: confirm the Route is Admitted, check the Service's endpoints list for how many pods are actually backing it, then check pod Ready status and readiness probe events. In one real case, the 503s were intermittent because only some pods were Ready during a rollout — the actual root cause was a Deployment rollout strategy without maxUnavailable: 0, not the Route itself.

Interviewer: "Explain edge vs passthrough vs re-encrypt Route TLS."

Answer: Edge terminates TLS at the Router and talks plain HTTP to the pod — simplest, but internal traffic is unencrypted. Passthrough forwards encrypted bytes straight to the pod, which must terminate TLS itself. Re-encrypt terminates at the Router like edge, but then opens a new TLS connection to the pod using a destination CA cert, giving end-to-end encryption while still letting the Router inspect/route based on the request.
