1. The Production Story

Scenario Everything from Projects 1-7 is running: namespace baseline, RBAC, the multi-tier app, Routes/TLS, safe deploys, storage, and now an Operator-managed database. But nobody gets alerted when something breaks — every incident so far has started with a customer complaint, not a page. The platform team is asked to close that gap.
Business Problem OpenShift ships cluster monitoring by default, but it doesn't watch application-level metrics unless you explicitly opt in and configure it. Nobody has done that for payment-api.
Our Mandate Enable user workload monitoring, scrape payment-api's own metrics via a ServiceMonitor, define alerting rules for the failure modes we've already hit in Projects 4-6 (pod restarts, high error rate, PVC nearing capacity), and route alerts somewhere a human will see them.

3. Architecture

Backend Pod exposes /metrics (Prometheus text format) │ ▼ ServiceMonitor tells Prometheus WHERE to scrape (via Service label match) │ ▼ User Workload Prometheus scrapes on interval, stores time series │ ▼ PrometheusRule defines alert conditions over those metrics │ ▼ Alertmanager receives firing alerts → routes to Slack/PagerDuty/email
ObjectPurpose
ServiceMonitorDeclarative scrape config — which Service (by label), which port, which path
PrometheusRulePromQL-based alerting/recording rules, evaluated continuously
AlertmanagerDedupes, groups, and routes firing alerts to notification receivers
User Workload MonitoringThe opt-in Prometheus stack for application (not just platform) metrics

4. The Playbooks — Fully Commented

4.1 roles/app_monitoring/tasks/main.yml

roles/app_monitoring/tasks/main.yml
---
# Enables user workload monitoring cluster-wide, then configures
# scraping and alerting specifically for payment-api.

- name: Enable user workload monitoring at the cluster level              # one-time cluster config, safe to re-apply
  kubernetes.core.k8s:
    state: present                                                        # idempotent create-or-update
    definition:
      apiVersion: v1                                                       # plain ConfigMap -- this is how OpenShift monitoring is configured
      kind: ConfigMap
      metadata:
        name: cluster-monitoring-config                                    # fixed, well-known name the monitoring operator watches
        namespace: openshift-monitoring                                    # must live in this exact namespace
      data:
        config.yaml: |                                                      # YAML-as-a-string -- the monitoring operator parses this itself
          enableUserWorkload: true                                          # the actual opt-in switch

- name: Create ServiceMonitor for payment-api backend                       # tells Prometheus what to scrape
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: monitoring.coreos.com/v1                                   # Prometheus Operator's CRD API group
      kind: ServiceMonitor
      metadata:
        name: "{{ app_name }}-backend-monitor"
        namespace: "{{ app_name }}-{{ environment }}"                          # lives alongside the app it monitors
      spec:
        selector:
          matchLabels: {app: "{{ app_name }}-backend"}                         # must match the backend Service's labels exactly
        endpoints:
          - port: http                                                          # must match a NAMED port on the Service, not just a number
            path: /metrics                                                      # where the app exposes Prometheus-format metrics
            interval: 30s                                                       # scrape frequency -- balance freshness vs Prometheus load
  register: sm_result                                                            # capture for assert

- name: Assert ServiceMonitor apply succeeded                                     # fail fast rather than silently having no metrics
  ansible.builtin.assert:
    that: [sm_result is succeeded]
    fail_msg: "Failed to create ServiceMonitor for {{ app_name }}-backend"

- name: Create PrometheusRule with alerting rules for known failure modes           # encodes lessons from Projects 4-6's incidents
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: monitoring.coreos.com/v1
      kind: PrometheusRule
      metadata:
        name: "{{ app_name }}-alerts"
        namespace: "{{ app_name }}-{{ environment }}"
        labels:
          role: alert-rules                                                       # required label so the monitoring stack picks this rule up
      spec:
        groups:
          - name: "{{ app_name }}.rules"                                            # logical grouping name
            rules:
              - alert: PaymentApiHighRestartRate                                      # catches the CrashLoopBackOff pattern from Project 3's incident
                expr: increase(kube_pod_container_status_restarts_total{namespace="{{ app_name }}-{{ environment }}"}[15m]) > 3  # PromQL: more than 3 restarts in 15 min
                for: 5m                                                               # must stay true for 5 minutes before firing -- avoids noisy flapping
                labels: {severity: warning}                                           # used for Alertmanager routing
                annotations:
                  summary: "{{ app_name }} pods restarting frequently"                 # human-readable text shown in the alert

              - alert: PaymentApiPVCNearFull                                           # catches the storage incident pattern from Project 6
                expr: kubelet_volume_stats_used_bytes{namespace="{{ app_name }}-{{ environment }}"}
                      / kubelet_volume_stats_capacity_bytes{namespace="{{ app_name }}-{{ environment }}"} > 0.70  # 70% threshold -- proactive, from Project 6's preventive action
                for: 10m
                labels: {severity: warning}
                annotations:
                  summary: "{{ app_name }} PVC usage above 70%"

              - alert: PaymentApiNoHealthyEndpoints                                     # catches the intermittent-503 pattern from Project 4
                expr: kube_endpoint_address_available{namespace="{{ app_name }}-{{ environment }}",
                      endpoint="{{ app_name }}-backend"} == 0                             # zero Ready endpoints backing the Service
                for: 2m
                labels: {severity: critical}                                              # critical -- this means the app is fully down
                annotations:
                  summary: "{{ app_name }} backend has zero healthy endpoints"
  register: rule_result

- name: Assert PrometheusRule apply succeeded
  ansible.builtin.assert:
    that: [rule_result is succeeded]
    fail_msg: "Failed to create PrometheusRule for {{ app_name }}"

6. Live Incident — "Dashboard Is Green But Customers Are Complaining"

ReportSupport says payment failures are spiking, but the Grafana dashboard shows all pods healthy and no alerts firing.
Step 1 — check if Prometheus is actually scraping the right target
oc get servicemonitor -n payment-api-prod
NAME                          AGE
payment-api-backend-monitor   14d

# In console: Observe > Targets, filter payment-api-prod
# Target shows: DOWN -- "context deadline exceeded"
Root cause candidate 1Prometheus can't reach the /metrics endpoint at all — that's why the dashboard looks "healthy": it has no fresh data, not because everything is actually fine. A stale dashboard silently freezes on its last good values.
Step 2 — check the Service port name matches the ServiceMonitor
oc get service payment-api-backend -n payment-api-prod -o yaml | grep -A3 ports
ports:
  - port: 8080
    targetPort: 8080
    # no 'name: http' field -- ServiceMonitor's endpoint.port: http can't match anything
Root causeThe backend Service's port was never given a name, but the ServiceMonitor references the named port http. Since the names never matched, Prometheus silently had zero valid targets for weeks — nobody noticed because "no alerts firing" looked the same as "everything healthy."
Step 3 — fix the Service definition (add the missing port name) and re-run
# In the backend Service definition from Project 3, add:
ports:
  - name: http        # NEW -- required for named-port ServiceMonitor references
    port: 8080
    targetPort: 8080
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=prod
Step 4 — validate scraping resumed
# Observe > Targets now shows payment-api-backend: UP
ResolvedMetrics flowing again; the actual payment failure spike (a separate, real issue) is now visible in the data and can be investigated with real signal instead of a blind dashboard.

7. Additional Break-Fix Labs

Break-Fix — alert defined but never fires
BreakDeploy a PrometheusRule without the role: alert-rules label.

Root cause: the monitoring stack's rule selector only picks up PrometheusRule objects carrying that specific label — without it, the rule is created but silently never loaded. Fix: our role always sets it explicitly (Section 4.1) for exactly this reason.

Break-Fix — testing an alert without a real outage (dummy exporter)

If your backend has no /metrics endpoint yet, you can validate the pipeline end-to-end with a tiny placeholder:

# quick lab-only metrics stub, NOT for production use
oc run metrics-stub -n payment-api-dev --image=nginx --port=80 \
  --overrides='{"metadata":{"labels":{"app":"payment-api-backend"}}}'

This lets you confirm the ServiceMonitor/Prometheus wiring works before wiring up real application metrics.

9. Interview Preparation

Interviewer: "Your dashboard shows healthy but users are reporting errors — how is that possible?"

Answer: A dashboard is only as good as the scrape pipeline behind it. If Prometheus loses its target — say, a Service port name mismatch with the ServiceMonitor — the dashboard just stops updating and freezes on the last good values, which can look identical to "everything is fine." I always check Observe > Targets for target health before trusting a green dashboard during an active incident.

Interviewer: "How do you decide alert thresholds and durations?"

Answer: I anchor them to real incidents where possible — our PVC-at-70% alert exists because we hit a near-full disk at 92% with no warning. The for: duration matters as much as the threshold: without it, a single noisy sample fires an alert; requiring the condition to hold for several minutes filters out blips while still catching real trends.
