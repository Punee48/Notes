1. The Production Story

Scenario payment-api is up, no pods are crashing, no alerts are firing — but customers report checkout "feels slow," and the support team can't quantify it beyond that. This is the hardest kind of incident: nothing is obviously broken, so the team needs a structured way to actually find the bottleneck instead of guessing.
Business Problem Performance investigations have historically been ad hoc — whoever's on call tries a random assortment of commands. We need a repeatable, layered triage method: CPU → memory → I/O → network → application, in that order, backed by the metrics/logs infrastructure we already built.
Our Mandate Build an Ansible performance-triage playbook that pulls CPU/memory/throttling data across the stack in one pass, and use it live to find the real bottleneck.

3. Architecture

ConceptPerformance triage follows a strict layer order because each layer can produce misleading symptoms at the layer above it. CPU throttling looks like slow application code. Memory pressure looks like random restarts. Disk I/O saturation looks like a slow database when the database itself is fine. Working top-down (or in a fixed order) prevents chasing the wrong layer.
1. CPU — oc adm top pod, cpu throttling metric (container_cpu_cfs_throttled) 2. Memory — oc adm top pod, working set vs limit, OOMKilled history 3. Disk I/O — PVC-backed workloads: read/write latency from kubelet_volume_stats 4. Network — Service latency, DNS resolution time 5. Application — actual code-level slowness, visible only once 1-4 are ruled out
LayerKey metric/signalTool
CPUUsage vs request/limit; throttled periodsoc adm top pod, Prometheus container_cpu_cfs_throttled_periods_total
MemoryWorking set vs limit; OOMKilled countoc adm top pod, oc get events
Disk I/OVolume read/write latencyPrometheus kubelet_volume_stats_*
NetworkService-to-service latency, DNS lookup timeApplication logs (Project 9 correlation IDs), oc rsh + dig

4. The Playbooks — Fully Commented

4.1 playbooks/perf_triage.yml

playbooks/perf_triage.yml
---
# READ-ONLY layered performance triage: CPU, then memory, then
# recent OOM events, then a throttling check. Produces one report
# instead of requiring the engineer to remember command sequences.
- name: Performance triage for {{ app_name }}
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: Get current CPU/memory usage for all app pods                  # 'oc adm top' isn't a native Ansible module -- shell it, read-only
      ansible.builtin.command:                                              # command, not shell -- no piping needed, slightly safer
        cmd: >
          oc adm top pod -n {{ app_name }}-{{ environment }}
          --no-headers                                                       # drop the header row for easier parsing
      register: top_output                                                   # raw text output, one line per pod
      changed_when: false                                                     # explicitly a read-only query -- never reports 'changed'

    - name: Get resource requests/limits for comparison                       # raw usage numbers are meaningless without their bounds
      kubernetes.core.k8s_info:                                                # structured, safer than parsing text for this part
        kind: Pod
        namespace: "{{ app_name }}-{{ environment }}"
        label_selectors: ["app={{ app_name }}-backend"]                         # scoped to the tier customers actually reported as slow
      register: pods_info                                                       # holds full pod specs including resources

    - name: Check for recent OOMKilled events                                    # memory pressure often manifests as silent restarts, not obvious errors
      kubernetes.core.k8s_info:
        kind: Event                                                               # Kubernetes Event objects, short-lived (~1hr retention by default)
        namespace: "{{ app_name }}-{{ environment }}"
        field_selectors: ["reason=OOMKilling"]                                     # filters server-side to just this reason
      register: oom_events                                                          # holds any matching events in the retention window

    - name: Query CPU throttling metric via Prometheus (Thanos Querier)               # the single most-missed CPU-layer signal
      ansible.builtin.uri:                                                             # direct HTTP query against the cluster's metrics API
        url: "https://thanos-querier.openshift-monitoring.svc:9091/api/v1/query"
        method: GET
        body_format: form-urlencoded
        body:
          query: >-
            rate(container_cpu_cfs_throttled_periods_total{namespace="{{ app_name }}-{{ environment }}"}[5m])  # PromQL: throttled periods per second over 5m
        headers:
          Authorization: "Bearer {{ lookup('env', 'PROM_TOKEN') }}"                     # service account token, never hardcoded -- pulled from environment
        validate_certs: true
      register: throttle_query                                                            # holds the raw Prometheus API JSON response
      ignore_errors: true                                                                  # don't fail the whole triage if Thanos Querier access isn't configured yet

    - name: Write the performance triage report                                            # local file, not a cluster object -- pure output
      ansible.builtin.copy:
        dest: "./perf-triage-report.txt"
        content: |
          Performance Triage Report — {{ ansible_date_time.iso8601 }}
          =====================================================
          CPU/Memory (oc adm top):
          {{ top_output.stdout }}

          OOMKilled events in retention window: {{ oom_events.resources | length }}
          {{ oom_events.resources | map(attribute='message') | join('\n') if oom_events.resources else '  (none)' }}

          CPU throttling query: {{ 'reachable' if throttle_query is succeeded else 'query failed -- check PROM_TOKEN / Thanos access' }}

    - name: Surface a warning if any OOMKilled events were found                             # fails the play visibly -- same pattern as Project 11's health gate
      ansible.builtin.fail:
        msg: "OOMKilled events found -- see perf-triage-report.txt"
      when: oom_events.resources | length > 0

6. Live Incident — "Slow But Nothing Is Crashing"

ReportCheckout feels slow. No alerts firing, no pod restarts, no errors in the logs.
Step 1 — run the triage playbook first
ansible-playbook playbooks/perf_triage.yml -e app_name=payment-api -e environment=prod
cat perf-triage-report.txt
CPU/Memory (oc adm top):
payment-api-backend-7f-a1   480m   210Mi
payment-api-backend-7f-b2   495m   205Mi

OOMKilled events: 0
CPU throttling query: reachable

CPU usage is near the 500m limit on both pods — a strong lead. Check the actual throttling number, not just usage.

Step 2 — query the throttling metric directly in the console
PromQL in Observe > Metrics:
rate(container_cpu_cfs_throttled_periods_total{namespace="payment-api-prod"}[5m])
> 0.85   # pods are being throttled ~85% of measured periods
Root cause candidateThe backend's CPU limit (500m, set back in Project 3) is now too low for current load — the container is being CPU-throttled by the kernel's CFS scheduler well before it hits any crash condition. This produces exactly the symptom reported: slow, not broken.
Step 3 — cross-check against actual request latency via logs (Project 9)
{kubernetes_namespace_name="payment-api-prod"} | json | duration_ms > 2000
# confirms a spike in slow requests correlating with the same time window as the throttling
Step 4 — fix: raise the CPU limit deliberately via Ansible (not a hotfix hand-edit)
# In roles/backend/tasks/main.yml, update:
resources:
  requests: {cpu: 200m, memory: 256Mi}
  limits: {cpu: "1", memory: 512Mi}     # raised from 500m -- based on observed throttling, not a guess
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=prod
Step 5 — validate
ansible-playbook playbooks/perf_triage.yml -e app_name=payment-api -e environment=prod
# throttling metric drops toward 0 over the following 15 minutes
ResolvedCheckout latency returned to normal; root cause was CPU limit sizing, not a code regression or infrastructure failure.

RCA Summary

FieldDetail
ImpactElevated checkout latency, no hard failures, hard to notice without deliberate triage
Root causeBackend CPU limit (500m) too low for current traffic, causing CFS throttling well under the alerting thresholds from Project 8
FixRaised CPU limit based on observed throttling data, applied via Ansible

7. Additional Break-Fix Labs

Break-Fix — disk I/O bottleneck on the database tier 
PromQL:
rate(kubelet_volume_stats_write_latency_seconds_sum{namespace="payment-api-prod"}[5m])
> 0.05   # 50ms+ average write latency -- unusually high for the configured StorageClass

Root cause: the StorageClass backing the database PVC (Project 6) uses a slower storage tier than expected — checking oc get storageclass -o yaml confirms the provisioner parameters. Fix: migrate to a faster StorageClass (requires the PVC migration runbook, not a simple expand) or reduce write volume via application-level batching.

Break-Fix — DNS resolution adding latency 
oc rsh deploy/payment-api-backend -n payment-api-prod
time nslookup payment-api-postgres
# real 0m1.240s -- unusually slow for in-cluster DNS, should be ms not seconds

Root cause: CoreDNS pods under resource pressure on a specific node. Fix: apply the same node-triage method from Project 11 to the nodes running CoreDNS pods specifically.

9. Interview Preparation

Interviewer: "An app is slow but nothing is crashing or alerting — how do you approach it?"

Answer: I go layer by layer — CPU, memory, disk I/O, network, then application code — because each layer can produce misleading symptoms at the layer above. In one real case, usage looked fine at a glance, but the actual CPU throttling metric showed pods being throttled 85% of the time — the container was hitting its CFS limit constantly, which reads as "slow" rather than "crashed" because the kernel just delays execution instead of killing anything.

Interviewer: "Why didn't your existing alerts catch this?"

Answer: Our Project 8 alerts covered restart rate and endpoint availability — real failure signals — but not sustained CPU throttling, which is a degradation signal, not a failure signal. That gap became the direct preventive action: add a throttling-specific alert so this class of issue pages someone before a customer notices.

10. Resume Points
