1. The Production Story

Scenario The hand-rolled PostgreSQL Deployment from Project 3 works, but it doesn't handle failover, backups, or minor-version patching on its own — someone has to do all of that manually. The database team wants a real, Operator-managed PostgreSQL cluster with automated failover and backups, deployed the same repeatable way as everything else: through Ansible.
Business Problem Operators are usually installed by hand through the OperatorHub console, which means there's no record of exactly which channel/version was approved, and no way to guarantee DEV, STAGE, and PROD all run the same Operator version.
Our Mandate Automate the full Operator lifecycle — Subscription, approval, health check — and then automate creation of the actual database via its Custom Resource, so "give me a Postgres cluster" becomes one Ansible run.

2. Run This On Your Device

Confirm OLM (Operator Lifecycle Manager) is present — it ships with OpenShift by default. 
oc get pods -n openshift-operator-lifecycle-manager
Confirm your Ansible identity has permission to manage Subscriptions (usually cluster-admin or a scoped operator-installer role). 
oc auth can-i create subscriptions -n openshift-operators
Add the operator role files from Section 4 to your repo. 
mkdir -p payment-stack/roles/{operator_install,postgres_cluster}/tasks
Install the Operator. 
ansible-playbook playbooks/operator.yml -e operator_name=cloudnative-pg
Watch the CSV reach Succeeded (can take 1-2 minutes). 
oc get csv -n openshift-operators -w
Create the actual database cluster via its Custom Resource. 
ansible-playbook playbooks/postgres_cluster.yml \
  -e app_name=payment-api -e environment=dev

3. Architecture

ConceptAn Operator is a controller that watches for instances of a Custom Resource (CR) and reconciles the cluster to match what the CR describes — the same control-loop pattern OpenShift itself uses internally, extended to application-specific logic like "run a 3-node Postgres cluster with automated failover."
Ansible │ creates ▼ Subscription (which Operator, which channel, which approval mode) │ OLM resolves ▼ InstallPlan → approved (manual or automatic) │ ▼ ClusterServiceVersion (CSV) → phase: Succeeded │ Operator pod now running, watching for its CRD ▼ Ansible creates a Custom Resource: "Cluster" (CloudNativePG's CRD) │ ▼ Operator reconciles: creates StatefulSet, Services, generates certs, configures replication, sets up automated backups
ObjectPurpose
SubscriptionDeclares intent: "I want Operator X from channel Y"
InstallPlanThe concrete set of resources OLM will create to satisfy the Subscription
CSV (ClusterServiceVersion)Describes the Operator's own deployment and its owned CRDs; phase reflects install health
Custom Resource (CR)The application-specific object you create (e.g. a "Cluster") that the Operator reconciles against

4. The Playbooks — Fully Commented

4.1 roles/operator_install/tasks/main.yml

roles/operator_install/tasks/main.yml
---
# Installs an Operator via a Subscription and WAITS for its CSV to
# reach Succeeded before considering the play done -- installing the
# Subscription is not the same as the Operator being ready to use.

- name: Create OperatorGroup (scopes which namespaces the Operator watches)  # required before any Subscription in a custom namespace
  kubernetes.core.k8s:
    state: present                                                     # idempotent create-or-update
    definition:
      apiVersion: operators.coreos.com/v1                                # OLM's OperatorGroup API
      kind: OperatorGroup
      metadata:
        name: "{{ operator_name }}-group"
        namespace: openshift-operators                                    # using the shared cluster-wide operators namespace
      spec: {}                                                              # empty spec = watch all namespaces (fine for a cluster-wide DB operator)

- name: Create the Subscription                                           # the actual "install this operator" declaration
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: operators.coreos.com/v1alpha1                            # OLM Subscription API version
      kind: Subscription
      metadata:
        name: "{{ operator_name }}"
        namespace: openshift-operators
      spec:
        channel: "{{ operator_channel | default('stable') }}"               # explicit channel -- never leave this implicit
        name: "{{ operator_name }}"                                          # package name in the catalog, e.g. 'cloudnative-pg'
        source: "{{ operator_source | default('redhat-operators') }}"        # which CatalogSource to pull from
        sourceNamespace: openshift-marketplace                               # standard namespace catalog sources live in
        installPlanApproval: "{{ operator_approval | default('Automatic') }}" # Automatic for DEV speed; Manual recommended for PROD
  register: sub_result                                                        # capture for assert below

- name: Assert Subscription creation succeeded                                # fail fast on API errors
  ansible.builtin.assert:
    that: [sub_result is succeeded]
    fail_msg: "Failed to create Subscription for {{ operator_name }}"

- name: Wait for the CSV to reach Succeeded                                   # THIS proves the operator pod is actually healthy, not just requested
  kubernetes.core.k8s_info:
    kind: ClusterServiceVersion                                               # OLM's install-status object
    api_version: operators.coreos.com/v1alpha1
    namespace: openshift-operators
    label_selectors:
      - "operators.coreos.com/{{ operator_name }}.openshift-operators="       # label OLM sets automatically per-package
  register: csv_check                                                          # will contain the CSV once OLM creates it
  until: >
    csv_check.resources | length > 0 and
    csv_check.resources[0].status.phase == "Succeeded"                          # only exit the loop once truly healthy
  retries: 30                                                                    # poll up to 30 times
  delay: 10                                                                      # 10s apart -- 5 minute max wait for install

4.2 roles/postgres_cluster/tasks/main.yml

roles/postgres_cluster/tasks/main.yml
---
# Creates the actual database by creating a Custom Resource that the
# already-installed CloudNativePG Operator watches and reconciles.

- name: Create the Postgres Cluster custom resource                    # NOT a Deployment -- the Operator builds that for us
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: postgresql.cnpg.io/v1                                  # the Operator's own CRD API group
      kind: Cluster                                                       # the CustomResourceDefinition this Operator provides
      metadata:
        name: "{{ app_name }}-pg"
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        instances: "{{ pg_instance_count | default(3) }}"                  # 3 = primary + 2 replicas, automated failover
        storage:
          size: "{{ db_storage_size | default('10Gi') }}"                   # Operator creates the PVC itself per instance
        bootstrap:
          initdb:
            database: paymentdb                                            # initial database name created on first boot
            owner: "{{ db_user }}"                                          # from vault.yml, same pattern as Project 3
      # Note: we do NOT set the password field directly here -- CloudNativePG
      # auto-generates a Secret; we just reference the app's expected
      # secret name below so downstream roles keep working unchanged.
  register: cluster_result                                                   # capture for assert

- name: Assert Cluster CR apply succeeded                                     # fail fast on malformed CR / API rejection
  ansible.builtin.assert:
    that: [cluster_result is succeeded]
    fail_msg: "Failed to create Postgres Cluster CR for {{ app_name }}"

- name: Wait for the Operator to report the cluster healthy                   # reconciliation takes time -- don't declare success prematurely
  kubernetes.core.k8s_info:
    kind: Cluster
    api_version: postgresql.cnpg.io/v1
    name: "{{ app_name }}-pg"
    namespace: "{{ app_name }}-{{ environment }}"
  register: cluster_status                                                    # holds live .status from the Operator
  until: cluster_status.resources[0].status.phase | default('') == "Cluster in healthy state"  # CloudNativePG's own health phase string
  retries: 40                                                                   # DB bootstrap + replica sync can take a few minutes
  delay: 15

6. Live Incident — Operator Degraded After Cluster Upgrade

ReportAfter a routine OpenShift minor version upgrade, the CloudNativePG Operator shows as degraded and the database CR stops reconciling.
Step 1 — check cluster operators and the Operator's own CSV
oc get csv -n openshift-operators
NAME                     PHASE
cloudnative-pg.v1.22.0   Failed

oc describe csv cloudnative-pg.v1.22.0 -n openshift-operators
Message: unsupported ocp version, requires >=4.13 <4.16, cluster is 4.16.2
Root causeThe installed Operator version doesn't support the new OpenShift minor version — the Subscription's channel pinned an older release line that has an explicit OCP version ceiling.
Step 2 — check for a newer channel that supports the new OCP version
oc get packagemanifest cloudnative-pg -n openshift-marketplace -o yaml | grep -A3 currentCSV
Step 3 — fix via Ansible: bump the channel, re-run
ansible-playbook playbooks/operator.yml -e operator_name=cloudnative-pg -e operator_channel=stable-v1.23
Step 4 — validate the existing database CR reconciles again
oc get cluster payment-api-pg -n payment-api-prod
NAME             INSTANCES   READY   STATUS
payment-api-pg   3           3       Cluster in healthy state
ResolvedOperator upgraded to a supported channel; existing database CR resumed reconciling without any data disruption — Operators manage their own upgrade path without touching the underlying StatefulSet data.

7. Additional Break-Fix Labs

Break-Fix — InstallPlan stuck awaiting manual approval 
oc get installplan -n openshift-operators
NAME            APPROVAL   APPROVED
install-abc12   Manual     false

Root cause: installPlanApproval: Manual was set (correct for PROD) but nobody approved it. Fix: add an explicit approval task, gated behind a variable so it's still a deliberate action:

# Only runs when explicitly requested -- keeps Manual approval meaningful
- name: Approve pending InstallPlan
  kubernetes.core.k8s:
    state: patched
    kind: InstallPlan
    api_version: operators.coreos.com/v1alpha1
    name: "{{ installplan_name }}"
    namespace: openshift-operators
    definition:
      spec:
        approved: true
  when: approve_installplan | default(false)   # must be explicitly passed -e approve_installplan=true
Break-Fix — Custom Resource rejected, CRD not yet registered 
fatal: [localhost]: FAILED! => {"msg": "Failed to create object: 
no matches for kind \"Cluster\" in version \"postgresql.cnpg.io/v1\""}

Root cause: the CR was created before the Operator's CSV reached Succeeded, so its CRD wasn't registered with the API server yet. Fix: this is exactly why operator_install's wait-until-Succeeded task exists — running postgres_cluster.yml only after that role completes prevents this race condition entirely.

9. Interview Preparation

Interviewer: "Why use an Operator instead of a plain Deployment for a database?"

Answer: An Operator encodes operational knowledge — failover, backup scheduling, minor-version patching — as a control loop, so instead of me scripting all of that by hand, I declare desired state via a Custom Resource and the Operator continuously reconciles toward it. For something stateful and operationally complex like Postgres, that's a large reduction in manual toil versus a hand-rolled Deployment.

Interviewer: "An Operator shows Failed after a cluster upgrade — how do you approach it?"

Answer: oc describe csv almost always states the reason directly — in this case an explicit OCP version compatibility ceiling. The fix is finding a channel whose CSV supports the new OpenShift version and moving the Subscription there; the underlying database data isn't touched by an Operator version bump.
