1. The Production Story

Scenario Other teams at the company are starting to reuse payment-api's patterns for their own services, and they're asking for a genuinely reusable, parameterized package — not a copy-pasted Ansible role tree. Meanwhile, our own DEV/QA/STAGE/PROD environment differences (Project 1's quota sizing, Project 3's replica counts) have grown into a sprawling pile of -e
Business Problem Two different problems, two different tools needed: other teams want a distributable, versioned PACKAGE (Helm's strength), while we want clearer, diffable environment-specific OVERLAYS of our own manifests (Kustomize's strength). Forcing either tool to solve both problems awkwardly.
Our Mandate Package payment-api as a Helm chart for other teams to consume, restructure our OWN environment differences as Kustomize overlays for clarity, and have Ansible orchestrate both — install/upgrade the Helm release, and apply the correct Kustomize overlay per environment.

4. The Playbooks — Fully Commented

4.1 kustomize/overlays/prod/kustomization.yaml (reference, not Ansible)

kustomize/overlays/prod/kustomization.yaml
# Kustomize overlay -- patches the shared base for PROD specifically.
# This file itself isn't Ansible, but Ansible applies it below.
resources:
  - ../../base                          # inherits every base manifest (Deployment, Service, Route skeleton)
patches:
  - path: replica-patch.yaml              # PROD-specific patch: higher replica count
  - path: resources-patch.yaml            # PROD-specific patch: higher CPU/memory limits (Project 15's lesson)
namespace: payment-api-prod               # target namespace -- must already exist via Project 1's Ansible baseline

4.2 playbooks/helm_deploy.yml

playbooks/helm_deploy.yml
---
# Ansible drives Helm using the kubernetes.core.helm module --
# NOT shelling out to raw 'helm' commands, so we get the same
# idempotency guarantees as every other playbook in this series.
- name: Deploy payment-api via Helm chart
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Confirm the target namespace exists (Project 1's baseline)     # Helm doesn't manage namespace lifecycle here -- Ansible/Project 1 does
      kubernetes.core.k8s_info:
        kind: Namespace
        name: "{{ app_name }}-{{ environment }}"
      register: ns_check                                                    # empty resources if missing

    - name: Assert namespace exists before Helm install                       # fail with a clear message rather than a confusing Helm error
      ansible.builtin.assert:
        that: [ns_check.resources | length > 0]
        fail_msg: "Namespace {{ app_name }}-{{ environment }} missing -- run Project 1's baseline first"

    - name: Install or upgrade the Helm release                                # the actual Helm operation, made idempotent by the module
      kubernetes.core.helm:                                                     # dedicated Helm module -- not a shell command
        name: "{{ app_name }}-{{ environment }}"                                 # Helm release name -- one release per app/environment
        chart_ref: "./payment-api-chart"                                          # local path to the packaged chart; could also be a chart repo URL
        release_namespace: "{{ app_name }}-{{ environment }}"                      # target namespace -- matches Ansible's own naming convention
        create_namespace: false                                                    # explicitly false -- namespace lifecycle stays owned by Project 1's Ansible role, never Helm
        values:                                                                     # overrides passed to the chart's values.yaml
          image:
            tag: "{{ backend_image_tag }}"                                           # same variable convention as Project 5's release role
          replicaCount: "{{ backend_replicas | default(3) }}"                         # mirrors Project 3's Deployment replica variable
          resources:
            requests: {cpu: "{{ backend_cpu_request | default('200m') }}"}             # same resource-sizing discipline as every prior project
      register: helm_result                                                            # capture for assert

    - name: Assert Helm release succeeded                                                # fail fast on chart rendering or apply errors
      ansible.builtin.assert:
        that: [helm_result is succeeded]
        fail_msg: "Helm release failed for {{ app_name }}-{{ environment }}"

4.3 playbooks/kustomize_apply.yml

playbooks/kustomize_apply.yml
---
# Renders the correct Kustomize overlay and applies it declaratively
# -- rendering is delegated to 'oc kustomize' (the trusted, built-in
# renderer), but APPLYING goes through kubernetes.core.k8s for the
# same idempotency and error-handling as everything else.
- name: Apply Kustomize overlay for {{ environment }}
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Render the environment-specific overlay to raw manifests          # rendering only -- no cluster changes from this task
      ansible.builtin.command:
        cmd: "oc kustomize kustomize/overlays/{{ environment }}"                # built-in Kustomize renderer, trusted and version-matched to the cluster's oc
      register: rendered_manifests                                              # holds the full rendered YAML as text
      changed_when: false                                                        # pure rendering -- never itself a 'changed' cluster operation

    - name: Apply the rendered manifests declaratively                            # THIS is the actual cluster-changing step
      kubernetes.core.k8s:
        state: present                                                             # idempotent create-or-update, same as every other playbook
        definition: "{{ rendered_manifests.stdout | from_yaml_all | list }}"          # parses the multi-document YAML string into a list of objects
      register: apply_result                                                         # capture for assert

    - name: Assert Kustomize overlay applied successfully                              # fail fast rather than a partial apply going unnoticed
      ansible.builtin.assert:
        that: [apply_result is succeeded]
        fail_msg: "Failed to apply Kustomize overlay for {{ environment }}"

6. Live Incident — DEV Config Leaked Into PROD

ReportPROD backend pods are running with DEV-sized resource limits (200m CPU instead of the expected 1 core) right after a routine Kustomize overlay update.
Step 1 — check what actually got applied
oc get deployment payment-api-backend -n payment-api-prod -o jsonpath='{.spec.template.spec.containers[0].resources}'
{"requests":{"cpu":"200m"}}   # DEV's value, not PROD's expected 1 core
Step 2 — check which overlay was actually rendered
ansible-playbook playbooks/kustomize_apply.yml -e environment=prod --check --diff
# --check mode shows what WOULD change without applying
# diff shows the resources-patch.yaml for prod was never actually included

cat kustomize/overlays/prod/kustomization.yaml
resources: [../../base]
patches:
  - path: replica-patch.yaml
  # resources-patch.yaml line is MISSING -- someone removed it while editing replica-patch nearby
Root causeA recent edit to the PROD overlay's kustomization.yaml accidentally dropped the resources-patch.yaml line while someone was updating the replica count patch — Kustomize silently falls back to the BASE manifest's values (which match DEV-like defaults) for anything not explicitly patched, with no error or warning that a patch reference went missing.
Step 3 — fix by restoring the missing patch reference
# kustomize/overlays/prod/kustomization.yaml, corrected:
resources: [../../base]
patches:
  - path: replica-patch.yaml
  - path: resources-patch.yaml    # restored
ansible-playbook playbooks/kustomize_apply.yml -e environment=prod
Step 4 — validate
oc get deployment payment-api-backend -n payment-api-prod -o jsonpath='{.spec.template.spec.containers[0].resources}'
{"requests":{"cpu":"1"},"limits":{"cpu":"1"}}   # correct PROD values restored
ResolvedPROD resource sizing restored; the --check --diff technique used in Step 2 becomes a standing pre-apply habit going forward.

7. Additional Break-Fix Labs

Break-Fix — Helm release stuck in "pending-upgrade" 
helm list -n payment-api-dev
NAME                STATUS
payment-api-dev     pending-upgrade   # a previous run was interrupted mid-upgrade

Root cause: a prior Helm operation didn't complete cleanly (e.g. Ansible control node lost connectivity mid-run). Fix: helm rollback to the last good revision first, THEN re-run the Ansible playbook — Helm's own state must be clean before Ansible's idempotent re-apply will succeed.

Break-Fix — Kustomize base change breaks ALL overlays simultaneously

Symptom: a well-intentioned fix to base/deployment.yaml breaks DEV, QA, STAGE, and PROD all at once.

Root cause: unlike Helm's per-release isolation, Kustomize's shared base means ANY base change ripples to every overlay simultaneously — there's no natural staging boundary unless you build one deliberately. Fix: always render and diff EVERY overlay (--check --diff across dev/qa/stage/prod) before committing a base change, not just the one environment you're actively working on.

9. Interview Preparation

Interviewer: "When would you choose Helm vs Kustomize vs plain Ansible-applied manifests?"

Answer: Helm when I need a distributable, versioned package other teams or consumers will install with their own values — it's built for that distribution model. Kustomize when I'm managing my OWN environment differences on top of a shared base and want patches that are easy to diff and review without a templating language. Plain Ansible-applied manifests for anything that's more than just rendering — governed operations, RBAC, Operator lifecycle, backup/DR — where I need real control flow, not just YAML templating. They're not mutually exclusive; I've used Ansible to orchestrate both Helm and Kustomize for the same application, each for the part it's actually good at.

Interviewer: "A Kustomize overlay silently applied wrong values in production — how do you prevent that?"

Answer: The dangerous part is that Kustomize doesn't error when a patch reference goes missing — it just silently falls back to the base value. Since then I treat --check --diff (or oc kustomize ... | diff) as a mandatory step before any overlay change reaches PROD, and I'd add a CI check asserting each overlay references its expected minimum patch set, so a missing reference fails a pipeline instead of reaching a cluster.

12. Key Learnings

OpenShift/tooling concepts

Helm chart/release/values model, Kustomize base/overlay/patch model, the silent-fallback risk of a missing Kustomize patch reference, per-release isolation (Helm) vs shared-base ripple effects (Kustomize).

Ansible concepts

kubernetes.core.helm module for idempotent chart releases, rendering external tool output (oc kustomize) then applying it through the same k8s module used everywhere else, using --check --diff as a review gate.

Commands learned

helm list, helm rollback, oc kustomize, ansible-playbook --check --diff.
