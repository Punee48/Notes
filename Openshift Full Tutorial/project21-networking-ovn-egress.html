1. The Production Story

Scenario Project 20's reporting workload needs to query the payment-api database from its OWN namespace (reporting-prod), not from inside payment-api-prod itself. Project 1's default-deny NetworkPolicy blocks all cross-namespace traffic by design — we need deliberate, narrow multi-tenant rules, not a blanket opening. Separately, security wants to restrict which external destinations payment-api's backend can reach at all (egress control), since it should only ever talk to the payment gateway's known IP range.
Business Problem "Just open the namespace to everything" is the fast answer and the wrong one — it undoes the isolation multi-tenancy depends on. We need namespace-to-namespace policy that's as narrow as the RBAC scoping from Projects 2 and 20.
Our Mandate Automate a namespace-scoped NetworkPolicy allowing only the reporting namespace to reach the database port, plus an EgressFirewall restricting payment-api's outbound traffic to only the payment gateway's IP range.

3. Architecture

ConceptOVN-Kubernetes implements NetworkPolicy as flows in a distributed virtual switch (OVN/OVS) spanning every node — there's no single central firewall to inspect. Each node's ovnkube-node pod programs local flow rules based on NetworkPolicy/EgressFirewall objects, which is why troubleshooting sometimes means checking a SPECIFIC node's OVN state, not just the Kubernetes API objects.
Pod A (reporting-prod) wants to reach Pod B (payment-api-prod, port 5432) │ ▼ OVN evaluates NetworkPolicy objects in payment-api-prod (the DESTINATION namespace) │ ├── default-deny-all (Project 1) → denies by default └── allow-reporting-to-db (this project) → explicit allow, namespace label match │ ▼ If an explicit allow matches → traffic permitted; else dropped silently (no 403, no error -- just a connection timeout, which is why this class of issue is hard to diagnose without knowing to check policy) EGRESS (payment-api-prod → external gateway): Pod → OVN egress evaluation → EgressFirewall rules (allow/deny by CIDR) → if no explicit allow matches a non-default-deny rule set, denied
ConceptDetail
NetworkPolicy directionRules live in and are evaluated against the DESTINATION namespace's policies, matched against the SOURCE's labels
namespaceSelectorMatches pods based on labels on the source namespace itself, not the pod
EgressFirewallOpenShift-specific CRD (not upstream NetworkPolicy) controlling OUTBOUND traffic to external CIDRs, evaluated in order, first match wins
Silent drop behaviorDenied traffic doesn't error explicitly — it just times out, which is the single biggest diagnostic trap in network troubleshooting

4. The Playbooks — Fully Commented

4.1 roles/multi_tenant_network/tasks/main.yml

roles/multi_tenant_network/tasks/main.yml
---
# Allows ONLY the reporting namespace to reach the database port,
# on top of Project 1's default-deny-all baseline -- multiple
# NetworkPolicies in a namespace are ADDITIVE (union of all allows).

- name: Label the reporting namespace so it can be selected by name              # namespaceSelector needs a stable label to match against
  kubernetes.core.k8s:
    state: present                                                                # idempotent patch-style apply
    definition:
      apiVersion: v1
      kind: Namespace                                                              # labeling the namespace object itself, not a namespaced resource
      metadata:
        name: reporting-prod                                                        # the SOURCE namespace we want to selectively allow
        labels:
          purpose: reporting                                                          # the label our NetworkPolicy's namespaceSelector will match on
  register: ns_label_result                                                          # capture for assert

- name: Assert namespace labeling succeeded
  ansible.builtin.assert:
    that: [ns_label_result is succeeded]
    fail_msg: "Failed to label reporting-prod namespace"

- name: Allow ONLY the reporting namespace to reach the database port on 5432        # the actual narrow cross-namespace allow rule
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: networking.k8s.io/v1                                                # standard upstream NetworkPolicy API -- portable across distros
      kind: NetworkPolicy
      metadata:
        name: allow-reporting-to-db                                                     # descriptive name -- shows intent clearly in 'oc get networkpolicy'
        namespace: "{{ app_name }}-{{ environment }}"                                    # lives in the DESTINATION namespace -- this is where the rule is evaluated
      spec:
        podSelector:
          matchLabels: {app: "{{ app_name }}-postgres"}                                   # applies ONLY to the database pods, not the whole namespace
        policyTypes: [Ingress]                                                             # this policy only concerns inbound traffic
        ingress:
          - from:
              - namespaceSelector:
                  matchLabels: {purpose: reporting}                                          # matches the label we just set on reporting-prod
            ports:
              - protocol: TCP
                port: 5432                                                                    # ONLY the database port -- not a blanket namespace-to-namespace opening
  register: np_result                                                                          # capture for assert

- name: Assert NetworkPolicy apply succeeded                                                     # fail fast rather than silently leaving reporting unable to connect
  ansible.builtin.assert:
    that: [np_result is succeeded]
    fail_msg: "Failed to create allow-reporting-to-db NetworkPolicy"

4.2 roles/egress_firewall/tasks/main.yml

roles/egress_firewall/tasks/main.yml
---
# Restricts payment-api's OUTBOUND traffic to only the payment
# gateway's known IP range, plus DNS -- everything else denied.

- name: Apply EgressFirewall restricting outbound traffic                     # OpenShift-specific CRD, not standard NetworkPolicy
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: k8s.ovn.org/v1                                               # OVN-Kubernetes's own EgressFirewall API group
      kind: EgressFirewall
      metadata:
        name: default                                                            # fixed required name -- ONE EgressFirewall per namespace
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        egress:                                                                   # rules evaluated TOP TO BOTTOM, first match wins
          - type: Allow                                                             # explicit allow for the payment gateway's IP range
            to:
              cidrSelector: "{{ payment_gateway_cidr }}"                              # e.g. 203.0.113.0/24 -- the ONLY external destination this app should ever need
          - type: Allow                                                              # DNS must be explicitly allowed too -- easy to forget and breaks EVERYTHING
            to:
              cidrSelector: "0.0.0.0/0"                                                # any destination...
            ports:
              - protocol: UDP
                port: 53                                                                # ...but ONLY for DNS resolution
          - type: Deny                                                                 # explicit catch-all deny -- belt and suspenders even though default behavior denies unmatched traffic
            to:
              cidrSelector: "0.0.0.0/0"                                                  # everything else, blocked
  register: egress_result                                                                 # capture for assert

- name: Assert EgressFirewall apply succeeded                                              # fail fast -- a broken egress rule can silently break the whole app
  ansible.builtin.assert:
    that: [egress_result is succeeded]
    fail_msg: "Failed to apply EgressFirewall for {{ app_name }}-{{ environment }}"

6. Live Incident — "Works Internally But Not Externally... Sort Of"

ReportRight after the EgressFirewall (Section 4.2) is deployed, the backend starts failing ALL payment gateway calls — even though the CIDR was supposedly configured correctly.
Step 1 — confirm it's specifically an egress problem, not the gateway itself
oc rsh deploy/payment-api-backend -n payment-api-prod
curl -v https://gateway.paymentprovider.com/health
curl: (28) Failed to connect: Connection timed out
# no HTTP error at all -- consistent with a silent network-layer drop, not an app-layer rejection
Step 2 — check the EgressFirewall rules actually applied
oc get egressfirewall default -n payment-api-prod -o yaml
spec:
  egress:
    - type: Allow
      to: {cidrSelector: "203.0.113.0/8"}    # WRONG -- /8 instead of /24, but that's not even the real bug here
Step 3 — resolve the actual gateway IP and compare
dig +short gateway.paymentprovider.com
198.51.100.42    # the gateway's REAL current IP is completely outside 203.0.113.0/24 entirely
Root causeThe payment gateway vendor rotated their IP range months ago (a CDN/load-balancer change on their end) and the CIDR baked into our EgressFirewall was stale — nobody had a process to notice, because without an EgressFirewall, outbound traffic just worked regardless of destination IP, so IP changes on the vendor's side were invisible to us until this project's stricter policy exposed the gap.
Step 4 — get the current authoritative range from the vendor and fix via Ansible
ansible-playbook playbooks/network_policy.yml -e app_name=payment-api -e environment=prod \
  -e payment_gateway_cidr=198.51.100.0/24
Step 5 — validate
oc rsh deploy/payment-api-backend -n payment-api-prod
curl -v https://gateway.paymentprovider.com/health
HTTP/1.1 200 OK
ResolvedRestored connectivity with the corrected CIDR — and surfaced a real operational gap: without an EgressFirewall, vendor IP rotations are invisible; WITH one, they must be tracked deliberately.

RCA Summary

FieldDetail
ImpactComplete payment gateway connectivity loss immediately after EgressFirewall rollout
Root causeConfigured CIDR was stale relative to the vendor's actual current IP range, previously masked by having no egress restriction at all
FixUpdated the CIDR via Ansible using the vendor's current authoritative range
Preventive actionRequest the vendor's officially published/stable IP range (many vendors publish these specifically for firewall allow-listing) rather than a single resolved IP, and add a periodic connectivity check (extends Project 8's monitoring) that would catch this class of drift proactively

7. Additional Break-Fix Labs

Break-Fix — forgot the DNS allow rule
BreakDeploy an EgressFirewall without the UDP/53 allow rule.
oc rsh deploy/payment-api-backend -n payment-api-prod
nslookup gateway.paymentprovider.com
;; connection timed out; no servers could be reached

Root cause: DNS resolution itself is outbound traffic subject to the EgressFirewall — without an explicit allow, even hostname lookups fail, which then LOOKS like the destination is unreachable when it's actually DNS that's blocked. Fix: our role always includes the DNS allow rule (Section 4.2) for exactly this reason — it's one of the most common EgressFirewall mistakes.

Break-Fix — reporting can reach the Service but query times out (pod-level, not policy) 
nc -zv payment-api-postgres.payment-api-prod.svc.cluster.local 5432
Connection succeeded   # NetworkPolicy is fine -- TCP connects

# but actual queries hang -- this is NOT a networking issue anymore

Root cause: once TCP connects, a hanging query points back to database-layer investigation (Project 15's performance triage), not NetworkPolicy — a good example of confirming which layer you're actually debugging before continuing to dig in the wrong place.

9. Interview Preparation

Interviewer: "How do you allow controlled cross-namespace traffic without breaking multi-tenant isolation?"

Answer: I label the source namespace with something stable and descriptive, then add a narrow NetworkPolicy in the DESTINATION namespace using a namespaceSelector matched to that label, scoped to just the specific pod selector and port that's actually needed — never a blanket namespace-to-namespace opening. It's additive on top of a default-deny baseline, so everything else stays blocked exactly as before.

Interviewer: "You rolled out an EgressFirewall and it broke production — what happened and what did you learn?"

Answer: The configured CIDR was stale — the vendor had rotated IPs months earlier, invisible to us because without any egress restriction, outbound traffic just worked regardless of destination. The real lesson wasn't the CIDR typo itself, it was that egress control introduces a new maintenance burden: vendor IP changes now need active tracking, which we hadn't planned for. We requested the vendor's officially published stable range instead of a single resolved IP, and added a periodic connectivity check to catch drift before it becomes an outage.
