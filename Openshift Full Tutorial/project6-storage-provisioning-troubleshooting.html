1. The Production Story

Scenario The PostgreSQL tier from Project 3 has been running for a few months. Storage requests have so far been ad hoc — some namespaces got a fast SSD-backed StorageClass, others silently got the cluster default, which is slower and not built for database workloads. The database is also approaching its original 5Gi allocation.
Business Problem Nobody standardized which StorageClass database workloads should use, and there's no repeatable, safe process for expanding a PVC when a database grows — engineers have been improvising during incidents.
Our Mandate Make StorageClass selection explicit and environment-aware in Ansible, and build a safe, auditable volume-expansion playbook — then use it during a live "disk almost full" incident.

3. Architecture

ConceptA PersistentVolumeClaim (PVC) is a request; a StorageClass tells the cluster's CSI driver HOW to fulfill it (which backend, which performance tier, whether expansion is allowed). The actual PersistentVolume (PV) is created dynamically and bound to the PVC — you rarely create PVs by hand in a modern cluster.
Ansible (PVC request: 5Gi, StorageClass=fast-ssd) │ ▼ PersistentVolumeClaim (Pending) │ StorageClass's provisioner (CSI driver) is invoked ▼ PersistentVolume dynamically created + bound │ ▼ Pod mounts the PVC → reads/writes go to the backing CSI volume Expansion: PVC.spec.resources.requests.storage increased (if StorageClass allows) │ ▼ CSI driver resizes the underlying volume │ ▼ Filesystem resize triggered on next pod mount/restart (driver-dependent)
ConceptDetail
StorageClassDefines provisioner, parameters, reclaim policy, and whether volume expansion is allowed
Access ModesReadWriteOnce (single node), ReadWriteMany (shared, needs a capable backend), ReadOnlyMany
Reclaim PolicyDelete (PV removed with PVC) vs Retain (PV kept for manual recovery) — PROD databases should use Retain
Volume expansionOnly works if the StorageClass has allowVolumeExpansion: true; you can only grow, never shrink

4. The Playbooks — Fully Commented

4.1 roles/db_storage/tasks/main.yml

roles/db_storage/tasks/main.yml
---
# Manages the PostgreSQL PVC: creates it if missing, or safely
# EXPANDS it if the requested size is larger than what exists.
# Never attempts to shrink -- Kubernetes doesn't support that.

- name: Confirm the target StorageClass allows expansion               # read-only pre-check before we ever touch the PVC
  kubernetes.core.k8s_info:                                             # info module -- never mutates
    kind: StorageClass                                                  # cluster-scoped object type
    api_version: storage.k8s.io/v1                                      # storage API group
    name: "{{ db_storage_class }}"                                       # the class we intend to use, e.g. 'fast-ssd'
  register: sc_info                                                      # holds the StorageClass definition

- name: Fail early if expansion is not supported by this class           # prevents a confusing failure later during a real resize
  ansible.builtin.assert:
    that:
      - sc_info.resources[0].allowVolumeExpansion | default(false)       # must be explicitly true
    fail_msg: "StorageClass {{ db_storage_class }} does not support volume expansion"
  when: db_storage_size is defined                                       # only relevant when we might resize

- name: Check current PVC size, if it exists                             # need this to detect grow-vs-noop before applying
  kubernetes.core.k8s_info:
    kind: PersistentVolumeClaim
    api_version: v1
    name: "{{ app_name }}-db-pvc"
    namespace: "{{ app_name }}-{{ environment }}"
  register: existing_pvc                                                  # empty resources list if PVC doesn't exist yet

- name: Refuse to apply a SMALLER size than what already exists            # Kubernetes rejects shrink requests; catch it here with a clear message
  ansible.builtin.assert:
    that:
      - (db_storage_size | regex_replace('Gi','') | int) >=
        (existing_pvc.resources[0].spec.resources.requests.storage
          | regex_replace('Gi','') | int)                                  # strip 'Gi' and compare as integers
    fail_msg: "Refusing to shrink PVC from {{ existing_pvc.resources[0].spec.resources.requests.storage }} to {{ db_storage_size }}"
  when: existing_pvc.resources | length > 0                                # only check if the PVC already exists

- name: Create or expand the PostgreSQL PVC                                 # the actual declarative apply
  kubernetes.core.k8s:
    state: present                                                          # idempotent create-or-update
    definition:
      apiVersion: v1
      kind: PersistentVolumeClaim
      metadata:
        name: "{{ app_name }}-db-pvc"
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        accessModes: [ReadWriteOnce]                                        # single-node mount, correct for a single DB pod
        storageClassName: "{{ db_storage_class }}"                           # explicit -- never rely on an implicit cluster default
        resources:
          requests:
            storage: "{{ db_storage_size }}"                                 # the new/target size
  register: pvc_result                                                        # capture for the assert below

- name: Assert PVC apply succeeded                                            # fail loudly instead of assuming success
  ansible.builtin.assert:
    that: [pvc_result is succeeded]
    fail_msg: "Failed to create/expand PVC for {{ app_name }}"

- name: Restart the DB pod so the filesystem resize takes effect              # many CSI drivers need a remount to finish resizing the filesystem
  kubernetes.core.k8s:
    state: patched                                                            # patch, not full replace -- only touches the annotation
    kind: Deployment
    api_version: apps/v1
    name: "{{ app_name }}-postgres"
    namespace: "{{ app_name }}-{{ environment }}"
    definition:
      spec:
        template:
          metadata:
            annotations:
              storage-resize-triggered-at: "{{ ansible_date_time.iso8601 }}"   # unique value forces a rolling pod restart
  when: existing_pvc.resources | length > 0 and
        existing_pvc.resources[0].spec.resources.requests.storage != db_storage_size  # only restart on an actual size CHANGE, not first creation

6. Live Incident — Database Disk Almost Full

ReportMonitoring alert: PostgreSQL PVC usage at 92%. Write latency climbing.
Step 1 — confirm current usage and size
oc rsh deploy/payment-api-postgres -n payment-api-prod
df -h /var/lib/pgsql/data
Filesystem      Size  Used Avail Use%
/dev/...          5G  4.6G  200M  92%
Step 2 — confirm the StorageClass supports expansion before promising anything
oc get storageclass fast-ssd -o jsonpath='{.allowVolumeExpansion}'
true
Step 3 — expand via the playbook (never a manual oc edit under pressure)
ansible-playbook playbooks/storage.yml -e app_name=payment-api -e environment=prod \
  -e db_storage_class=fast-ssd -e db_storage_size=20Gi
Step 4 — validate the resize actually reached the filesystem
oc get pvc payment-api-db-pvc -n payment-api-prod
NAME                 STATUS   CAPACITY
payment-api-db-pvc   Bound    20Gi

oc rsh deploy/payment-api-postgres -n payment-api-prod
df -h /var/lib/pgsql/data
Filesystem      Size  Used Avail Use%
/dev/...         20G  4.6G   15G  23%
ResolvedCapacity restored with zero data loss and a single rolling pod restart.
Root causeNo proactive alert existed until 92% usage — too close to the edge for a database. Preventive action: add a monitoring alert at 70% usage, and schedule a quarterly capacity review using growth trend data.

7. Additional Break-Fix Labs

Break-Fix — PVC Pending forever, no StorageClass set 
oc describe pvc payment-api-db-pvc -n payment-api-dev
Events: waiting for a volume to be created, either by the external
  provisioner 'none' or manually by the system administrator

Root cause: storageClassName was omitted and the cluster has no default StorageClass. Fix: our role always sets storageClassName explicitly (Section 4.1) precisely to prevent this class of failure.

Break-Fix — expansion request rejected 
ansible-playbook playbooks/storage.yml -e db_storage_class=slow-hdd -e db_storage_size=10Gi
TASK [Fail early if expansion is not supported] ***
fatal: [localhost]: FAILED! => {"msg": "StorageClass slow-hdd does not support volume expansion"}

Root cause: that StorageClass's allowVolumeExpansion is false. Fix: this is caught by our own pre-check before touching the PVC — the real fix is migrating to a StorageClass that supports expansion, which requires creating a new PVC and copying data (a separate, more careful runbook).

9. Interview Preparation

Interviewer: "How would you safely expand a PVC in production?"

Answer: First confirm the StorageClass has allowVolumeExpansion: true — otherwise the request will just fail. Update the PVC's requested storage size upward (never downward — Kubernetes doesn't support shrinking), then depending on the CSI driver, the pod may need a restart for the filesystem itself to pick up the new size. I automate this with an Ansible role that refuses to apply a smaller size than what's already there, so a bad variable can't accidentally trigger something unsupported.

Interviewer: "PVC is stuck Pending — what do you check?"

Answer: oc describe pvc first — the Events section almost always states exactly why: no StorageClass, no available PV, or a provisioner error. Missing StorageClass, when there's no cluster default, is the most common cause I've seen.
