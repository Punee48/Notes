1. The Production Story

Scenario We're still on the Platform Engineering team, building on the namespace baseline from Project 1. Now the security team has flagged that RBAC across the cluster is inconsistent: some namespaces bind the wrong ClusterRole, some Groups don't match the identity provider's actual group names, and nobody can quickly answer "who can deploy to payments-prod?" We're asked to formalize RBAC as versioned, automated, auditable code — and be ready to troubleshoot access incidents fast when they happen.
Business Problem This morning, a developer, Priya, reports she can no longer deploy the payment-api application into the payment-api-prod namespace. Deploys are blocked. This is now a live incident, not just a cleanup task.
Our Mandate Build reusable Ansible roles that manage Users, Groups, Roles, and RoleBindings declaratively — then use that same mental model to diagnose and fix Priya's incident live.

3. Architecture

3.1 RBAC Object Model

Concept OpenShift RBAC is a chain: a human User belongs to a Group (usually synced from your SSO/IdP). A RoleBinding (or ClusterRoleBinding) connects that Group to a Role or ClusterRole. The Role/ClusterRole defines the actual verbs (get, list, create, update, delete) on resource types. Access is only granted if every link in that chain is correct.
User (priya@company.com) │ is member of ▼ Group (payments-developers) │ referenced as 'subject' in ▼ RoleBinding (payments-edit-binding, namespace-scoped) │ references ▼ ClusterRole (edit) │ defines ▼ Allowed verbs on resources (create/update/delete Deployments, Pods, etc.)

5.1 group_vars/all.yml

group_vars/all.yml
# ---------------------------------------------------------------
# Central mapping: OpenShift/IdP group name for each team.
# Keeping this in ONE place prevents the typo bug we hit in the
# incident below (team var vs actual synced group name mismatch).
# ---------------------------------------------------------------
team_group_map:                     # dictionary: team key -> real IdP group name
  payments: payments-developers     # must exactly match the group synced from SSO/LDAP
  billing: billing-developers       # same pattern for the billing team
  platform: platform-admins         # platform team gets a separate, higher-trust group

rbac_role_for_teams: edit           # ClusterRole app teams get -- NEVER 'admin' or 'cluster-admin'
rbac_role_for_platform: admin       # platform team gets 'admin' (still namespace-scoped, not cluster-admin)

5.2 roles/openshift_rbac/tasks/main.yml

roles/openshift_rbac/tasks/main.yml
---
# =================================================================
# Role: openshift_rbac
# Purpose: create the ServiceAccount for the app's pods, and bind
#          the correct human Group to the correct ClusterRole,
#          scoped to exactly one namespace.
# =================================================================

- name: Look up the real IdP group name for this team          # human-readable task name shown in play output
  ansible.builtin.set_fact:                                     # set_fact creates a variable usable by later tasks
    resolved_group: "{{ team_group_map[team] }}"                 # dictionary lookup: team='payments' -> 'payments-developers'
  # If 'team' isn't a valid key in team_group_map, this task fails
  # immediately with a clear KeyError instead of silently binding
  # a wrong/empty group -- this is what prevents typo incidents.

- name: Create application ServiceAccount                        # identity that PODS (not humans) run as
  kubernetes.core.k8s:                                            # module that talks to the OpenShift/K8s API
    state: present                                                # declarative: create if missing, leave alone if it matches
    definition:                                                   # the actual object manifest, inline
      apiVersion: v1                                              # core K8s API group for ServiceAccount
      kind: ServiceAccount                                        # object type
      metadata:
        name: "{{ app_name }}-sa"                                  # e.g. payment-api-sa
        namespace: "{{ app_name }}-{{ environment }}"               # scoped to this app's namespace only
  register: sa_result                                             # capture result so we can assert on it below

- name: Assert ServiceAccount creation succeeded                  # fail fast, don't continue with a broken identity
  ansible.builtin.assert:                                         # built-in assertion module
    that:
      - sa_result is succeeded                                    # true only if the API call didn't error
    fail_msg: "Failed to create ServiceAccount for {{ app_name }}"  # shown to the engineer on failure

- name: Bind resolved group to the correct ClusterRole in this namespace  # the actual access grant
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: rbac.authorization.k8s.io/v1                     # RBAC API group
      kind: RoleBinding                                            # namespace-scoped binding (NOT ClusterRoleBinding)
      metadata:
        name: "{{ team }}-{{ rbac_role_for_teams }}-binding"          # e.g. payments-edit-binding
        namespace: "{{ app_name }}-{{ environment }}"                 # scope: this namespace only
        labels:
          managed-by: ansible                                       # marks this object as automation-owned, for drift audits
      subjects:                                                      # WHO is being granted access
        - kind: Group                                                # subject type: an SSO/IdP group, not an individual user
          name: "{{ resolved_group }}"                                # the looked-up, correct group name -- NOT the raw team var
          apiGroup: rbac.authorization.k8s.io                         # required apiGroup for Group subjects
      roleRef:                                                       # WHAT they are being granted
        kind: ClusterRole                                            # built-in role definition (edit/view/admin)
        name: "{{ rbac_role_for_teams }}"                              # 'edit' for app teams -- least privilege
        apiGroup: rbac.authorization.k8s.io                           # required apiGroup for the roleRef
  register: rb_result                                               # capture for validation

- name: Assert RoleBinding succeeded                                # confirm the grant actually landed
  ansible.builtin.assert:
    that:
      - rb_result is succeeded
    fail_msg: "Failed to bind {{ resolved_group }} in {{ app_name }}-{{ environment }}"

playbooks/site.yml

  hosts: localhost                                                   # run on the control node itself
  connection: local                                                  # no SSH -- talk to OpenShift API directly
  gather_facts: false                                                # skip host fact-gathering, irrelevant to API calls, saves time

  vars_files:
    - ../group_vars/all.yml                                          # load the team -> group mapping

  roles:
    - openshift_rbac                                                 # the only role this playbook runs

5.4 playbooks/audit_rbac.yml — read-only drift check

playbooks/audit_rbac.yml
---
# Read-only playbook: lists every RoleBinding across app namespaces
# and flags any that reference 'admin' or 'cluster-admin' -- these
# should never appear on an application team's namespace.
- name: Audit RBAC for privilege drift
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Fetch all RoleBindings labeled as Ansible-managed        # only audit objects we own
      kubernetes.core.k8s_info:                                      # READ-ONLY module -- never mutates state
        kind: RoleBinding                                            # object type to query
        label_selectors:
          - "managed-by=ansible"                                     # matches the label we set in Section 5.2
      register: bindings                                              # store the query result

    - name: Flag any binding to admin or cluster-admin                # the actual policy check
      ansible.builtin.debug:                                          # prints to console, no cluster change
        msg: "DRIFT: {{ item.metadata.name }} in {{ item.metadata.namespace }} binds {{ item.roleRef.name }}"
      loop: "{{ bindings.resources }}"                                 # iterate every RoleBinding found
      when: item.roleRef.name in ['admin', 'cluster-admin']            # only print the risky ones

7. Live Incident — Priya Can't Deploy

10:14 AM — Report"I can't deploy payment-api to prod. Getting a permissions error in the pipeline."
Step 1 — isolate: is this RBAC at all?
oc auth can-i create deployments -n payment-api-prod --as=priya@company.com
> no
Step 2 — check her group membership
oc get identity | grep priya
oc describe group payments-developers

Priya is listed as a member of payments-developers. Membership is correct — the problem is downstream.

Step 3 — inspect the RoleBinding actually applied in the namespace
oc get rolebinding -n payment-api-prod -o yaml
subjects:
  - kind: Group
    name: payment-developers        # <-- singular "payment", not "payments"
roleRef:
  kind: ClusterRole
  name: edit
Root causeThe RoleBinding subject says payment-developers (singular) but the real synced IdP group is payments-developers (plural). Someone edited this RoleBinding manually last week outside of Ansible, introducing drift and breaking the lookup table this project enforces.
Step 4 — fix via Ansible, not a manual oc edit
ansible-playbook playbooks/site.yml \
  -e app_name=payment-api -e environment=prod \
  -e team=payments -e owner=platform-team

Because the role always sets name: "{{ resolved_group }}" from the central team_group_map, re-running it overwrites the drifted value with the correct one — this is changed=1 on this run specifically, which is expected and desired.

Step 5 — validate
oc auth can-i create deployments -n payment-api-prod --as=priya@company.com
> yes
10:41 AM — ResolvedPriya confirms her pipeline deploy succeeds.

8. Additional Break-Fix Labs

Break-Fix — invalid team variable
BreakRun with -e team=shipping (not in team_group_map).
fatal: [localhost]: FAILED! => {"msg": "'shipping' is undefined"}

Root cause: dictionary lookup fails when the key doesn't exist. Fix: add the team to group_vars/all.yml, or add an explicit assert before the lookup with a clearer message.

Break-Fix — ServiceAccount permission denied
BreakRun Ansible as a token that only has view on the cluster.
fatal: [localhost]: FAILED! => {"msg": "Failed to create object: 
serviceaccounts is forbidden: User cannot create resource"}

Root cause: the identity Ansible is logged in as lacks write RBAC. Fix: use a service account/token with admin rights scoped to the namespaces being managed, ideally via Ansible Automation Platform credentials, not a personal token.

10. Interview Preparation

Interviewer: "Walk me through troubleshooting a developer who suddenly can't deploy."

Answer: First I confirm it's actually RBAC with oc auth can-i ... --as= rather than assuming. Then I walk the chain: is the user in the right group, does the RoleBinding subject match that group exactly, does the roleRef point to a ClusterRole with the right verbs. In this incident the break was a silent manual edit that drifted from what our Ansible source of truth expected — so the real fix was re-applying automation, not hand-patching the RoleBinding again.

Interviewer: "How do you prevent RBAC drift from manual changes?"

Answer: Label everything automation manages, run a scheduled read-only audit playbook that flags unexpected values, and where possible use an admission policy or GitOps controller to reject changes that don't come through the pipeline.

Manager round: "How long did resolution take and what would you change?"

Answer: ~27 minutes from report to validated fix. I'd add the scheduled audit job so this class of drift is caught before a developer is blocked, not after.

13. Key Learnings

OpenShift concepts

User/Group/Role/RoleBinding/ClusterRole chain, oc auth can-i --as=, drift between declared and actual RBAC state.

Ansible concepts

set_fact for dictionary lookups, assert for fail-fast validation, k8s_info for read-only audits, labeling automation-owned objects.

Commands learned

oc auth can-i, oc describe group, oc get rolebinding -o yaml, ansible-galaxy collection install.

Troubleshooting method learned

Isolate with can-i before investigating further; walk the RBAC chain link by link; prefer re-running automation over one-off manual fixes.

Common mistakes

Manual oc edit on automation-managed objects; group name typos; granting admin/cluster-admin instead of edit.

Practice tasks

  • Schedule audit_rbac.yml via cron or Automation Controller and alert on any DRIFT lines.
  • Add a Molecule test that asserts the RoleBinding subject always equals the resolved group.
