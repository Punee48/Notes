1. The Production Story

Scenario The payment-api stack (Projects 1-4) is live. The application team now ships multiple releases a week. Today at 2:00 PM, they push version v2.4.0 of the backend to PRODUCTION during business hours. Fifteen minutes later, customers start reporting failed payments.
Business Problem There is no standardized, automated way to deploy a new image version, watch the rollout, and — critically — roll back fast if something goes wrong. Right now someone would have to remember the right oc rollout commands under pressure.
Our Mandate Build an Ansible-driven deployment playbook that updates the image version safely, waits for rollout success, and gives us a scripted rollback path — then use it live to fix today's incident.

3. Architecture

ConceptAn OpenShift Deployment doesn't replace pods directly — it creates a new ReplicaSet per revision and shifts traffic from the old ReplicaSet to the new one according to the rolling update strategy. The revision history lets you roll back to any prior ReplicaSet by re-activating it.
Deployment (desired state: image v2.4.0) │ ├── ReplicaSet rev N (v2.4.0) ← scaling UP └── ReplicaSet rev N-1 (v2.3.1) ← scaling DOWN │ ▼ Rollback = re-point Deployment at rev N-1's spec │ ▼ New ReplicaSet rev N+1 created MATCHING rev N-1's spec (rollback is itself a new revision, not a time-machine)
ConceptWhat it means
Revision historyEach spec change to a Deployment creates a new ReplicaSet; kept up to revisionHistoryLimit
maxUnavailableHow many pods can be down during a rollout (0 = zero-downtime)
maxSurgeHow many extra pods can exist temporarily above desired replica count
RollbackCreates a NEW revision whose spec matches an old one — never literally "goes back in time"

4. The Playbooks — Fully Commented

4.1 roles/app_release/tasks/main.yml

roles/app_release/tasks/main.yml
---
# Updates the backend Deployment's image and WAITS for the rollout
# to actually finish successfully before the play is considered done.

- name: Record current image before changing it                     # capture 'last known good' for potential rollback
  kubernetes.core.k8s_info:                                          # read-only lookup, never mutates state
    kind: Deployment                                                  # object type to query
    api_version: apps/v1                                              # apps API group
    name: "{{ app_name }}-backend"                                     # target Deployment name
    namespace: "{{ app_name }}-{{ environment }}"                       # target namespace
  register: current_deploy                                             # stores full object for later reference

- name: Save previous image to a fact                                  # used only for the human-readable summary at the end
  ansible.builtin.set_fact:
    previous_image: "{{ current_deploy.resources[0].spec.template.spec.containers[0].image }}"  # dig into the nested JSON path

- name: Apply new backend image                                        # the actual deployment update
  kubernetes.core.k8s:
    state: present                                                     # create-or-update -- update here since it already exists
    definition:
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: "{{ app_name }}-backend"
        namespace: "{{ app_name }}-{{ environment }}"
      spec:
        replicas: "{{ backend_replicas | default(3) }}"                  # keep replica count explicit and stable across releases
        strategy:
          type: RollingUpdate                                             # zero-downtime style rollout, not Recreate
          rollingUpdate:
            maxUnavailable: 0                                              # never drop below full capacity (fixes Project 4's incident)
            maxSurge: 1                                                    # one extra pod allowed temporarily during the swap
        selector:
          matchLabels: {app: "{{ app_name }}-backend"}                     # must stay identical across revisions or the update is rejected
        template:
          metadata:
            labels: {app: "{{ app_name }}-backend"}
          spec:
            containers:
              - name: backend
                image: "{{ backend_image }}"                                # the ONLY field that actually changes on a normal release
                ports: [{containerPort: 8080}]
                readinessProbe:                                             # rollout won't proceed to next pod until this passes
                  httpGet: {path: /healthz, port: 8080}
                  initialDelaySeconds: 5
  register: apply_result                                                    # capture for the assert below

- name: Assert the apply itself succeeded                                   # catches API-level failures immediately
  ansible.builtin.assert:
    that: [apply_result is succeeded]
    fail_msg: "Failed to apply new image for {{ app_name }}-backend"

- name: Wait for rollout to actually complete                               # THIS is what makes the play trustworthy -- 'applied' != 'healthy'
  kubernetes.core.k8s_info:
    kind: Deployment
    api_version: apps/v1
    name: "{{ app_name }}-backend"
    namespace: "{{ app_name }}-{{ environment }}"
  register: rollout_check                                                     # re-query the Deployment's live status
  until: >                                                                     # retry condition: all replicas updated AND available
    rollout_check.resources[0].status.updatedReplicas | default(0) ==
    rollout_check.resources[0].spec.replicas and
    rollout_check.resources[0].status.availableReplicas | default(0) ==
    rollout_check.resources[0].spec.replicas
  retries: 30                                                                  # check up to 30 times
  delay: 10                                                                    # 10 seconds between checks -- 5 minute max wait

- name: Report release summary                                                 # human-readable confirmation, not a cluster change
  ansible.builtin.debug:
    msg: "Released {{ app_name }}-backend: {{ previous_image }} -> {{ backend_image }}"

4.2 playbooks/rollback.yml

playbooks/rollback.yml
---
# Scripted rollback -- re-runs app_release with the LAST KNOWN GOOD
# image instead of guessing at oc rollout undo timing under pressure.
- name: Roll back backend to previous known-good image
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Look up the previous ReplicaSet's image                          # find what was running before the current bad revision
      kubernetes.core.k8s_info:
        kind: ReplicaSet                                                      # ReplicaSets hold the actual revision history
        api_version: apps/v1
        namespace: "{{ app_name }}-{{ environment }}"
        label_selectors:
          - "app={{ app_name }}-backend"                                       # all ReplicaSets belonging to this Deployment
      register: replicasets                                                    # list of all matching ReplicaSets, old and new

    - name: Sort and pick the second-most-recent ReplicaSet's image             # index 1 = previous revision, 0 = current
      ansible.builtin.set_fact:
        rollback_image: >-
          {{ (replicasets.resources | sort(attribute='metadata.creationTimestamp', reverse=true))
             [1].spec.template.spec.containers[0].image }}                       # pulls the image string from that ReplicaSet's pod template

    - name: Re-apply the release role with the rollback image                  # REUSES the same tested apply+wait logic, no duplicated code
      ansible.builtin.include_role:
        name: app_release                                                       # the exact same role from Section 4.1
      vars:
        backend_image: "{{ rollback_image }}"                                    # overrides the var the role expects, pointing at the OLD image

5. Execution & Idempotency

ansible-playbook playbooks/release.yml -e app_name=payment-api -e environment=dev \
  -e backend_image="quay.io/yourorg/payment-backend:v2.4.0"
First run (new image)
PLAY RECAP *** ok=5 changed=2 failed=0
Second run (same image, idempotency proof)
PLAY RECAP *** ok=5 changed=0 failed=0
Note on "changed"The until loop task itself always reports ok, not changed — it's a read-only poll. Only the k8s apply task reports changed, and only when the image actually differs from what's already deployed.

6. Live Incident — Bad Release at 2:00 PM

2:15 PM — ReportCustomers report failed payments since roughly 2:05 PM, right after the v2.4.0 deploy.
Step 1 — confirm the rollout and check recent events
oc rollout status deployment/payment-api-backend -n payment-api-prod
Waiting for deployment "payment-api-backend" rollout to finish: 1 old replicas are pending termination...

oc get pods -n payment-api-prod
NAME                          READY   STATUS    RESTARTS
payment-api-backend-9c-a1     1/1     Running   0
payment-api-backend-9c-b2     1/1     Running   0
payment-api-backend-7f-old    1/1     Running   0   # old revision still up -- rollout stuck, not failed outright
Step 2 — check logs on the new revision's pods
oc logs payment-api-backend-9c-a1 -n payment-api-prod
ERROR: payment gateway SDK version mismatch -- expects config key
  PAYMENT_GATEWAY_TIMEOUT_MS, found none. Falling back to 0ms -- all
  requests time out immediately.
Root causev2.4.0 introduced a new required config value (PAYMENT_GATEWAY_TIMEOUT_MS) that was never added to the ConfigMap. Every payment request times out instantly. This is an application-config gap, not an infrastructure bug — but the fastest mitigation is rollback, then fix config properly before re-attempting.
Step 3 — mitigate immediately with the rollback playbook
ansible-playbook playbooks/rollback.yml -e app_name=payment-api -e environment=prod
TASK [Report release summary] ***
ok: [localhost] => {"msg": "Released payment-api-backend: v2.4.0 -> v2.3.1"}
Step 4 — validate
oc rollout status deployment/payment-api-backend -n payment-api-prod
deployment "payment-api-backend" successfully rolled out

curl -X POST https://payment-api-prod.apps.../health-check-payment
{"status":"ok"}
2:29 PM — MitigatedPayments succeeding again on v2.3.1. Root cause (missing config key) tracked as a follow-up before v2.4.0 is re-attempted.

7. Additional Break-Fix Labs

Break-Fix — rollout stuck, ImagePullBackOff 
oc get pods -n payment-api-dev
payment-api-backend-9c-x1   0/1   ImagePullBackOff

oc describe pod payment-api-backend-9c-x1 -n payment-api-dev
Failed to pull image "...:v2.4.0": manifest unknown

Root cause: the tag doesn't exist in the registry — typo or the image was never actually pushed. Fix: the until loop in Section 4.1 will time out after 5 minutes and fail the play instead of hanging forever — confirm the correct tag, re-run.

Break-Fix — maxUnavailable misconfigured causes downtime anyway
BreakSet maxUnavailable: 1 with only 1 replica.

Root cause: with a single replica, any nonzero maxUnavailable means that one pod IS the entire service — a rollout briefly takes it fully offline. Fix: either run at least 2 replicas or accept a brief gap for single-replica dev environments; never do this in PROD.

9. Interview Preparation

Interviewer: "A deployment is failing in production and traffic is affected — walk me through it."

Answer: First oc rollout status to see if it's stuck or actively failing, then oc get pods to see the mix of old/new revisions, then logs on the new pods specifically — that's usually where the real signal is. In this incident, the new image needed a config key that didn't exist, so logs showed the exact failure immediately. I mitigated with a scripted rollback rather than trying to hot-patch the new version under pressure, then tracked the real fix as a follow-up.

Interviewer: "How does an OpenShift rollback actually work under the hood?"

Answer: It's not reverting history — it creates a new revision whose pod template matches an older ReplicaSet's spec, then does a normal rolling update to that spec. That's why my rollback playbook reuses the exact same apply-and-wait logic as a forward release; a rollback is just a release with an older image.
