1. The Production Story

Scenario It's time for the quarterly OpenShift minor version upgrade (4.14 → 4.15). Last quarter's upgrade caused a two-hour outage because nobody checked that a ClusterOperator was already Degraded before starting, and nobody validated the payment-api stack afterward — an app-level regression went unnoticed for a day.
Business Problem Upgrades have been "point-and-click in the console and hope," with no consistent pre-flight check and no consistent post-upgrade validation of application health.
Our Mandate Build an Ansible pre-upgrade gate (reusing Project 11's health triage) that blocks the upgrade from being greenlit if the cluster isn't already healthy, and a post-upgrade validation playbook that confirms both the platform and payment-api are fully healthy before declaring success.

2. Run This On Your Device

ImportantDo not practice a real cluster upgrade on a shared/production cluster casually. On CRC you can review the workflow and pre/post-checks safely; the actual oc adm upgrade trigger is shown for completeness but should only be run against a cluster you're authorized to upgrade.

3. Architecture

Pre-Upgrade Gate (Ansible, reuses Project 11's checks) │ fails the play if cluster isn't already healthy ▼ Maintenance Window Communicated │ ▼ oc adm upgrade --to=X.Y.Z (OpenShift-native trigger -- NOT reimplemented in Ansible) │ ▼ Cluster Version Operator drives the upgrade: MachineConfigPools roll node-by-node (Project 12's mechanism) ClusterOperators update one at a time │ ▼ Post-Upgrade Validation (Ansible): 1. ClusterVersion reports desired version reached 2. All ClusterOperators Available, not Degraded 3. payment-api pods healthy, Route reachable, HPA has metrics
Why the upgrade trigger itself isn't in AnsibleThis masterclass has consistently used kubernetes.core.k8s for declarative object management, but triggering an upgrade is a one-time imperative action best driven through OpenShift's own tooling (oc adm upgrade or the console) — Ansible's value here is in the surrounding pre-flight and validation discipline, not reimplementing the upgrade orchestration itself.

4. The Playbooks — Fully Commented

4.1 playbooks/pre_upgrade_check.yml

playbooks/pre_upgrade_check.yml
---
# Pre-upgrade GATE -- fails loudly if the cluster is not already
# fully healthy. An upgrade should never be started on top of an
# existing, unresolved problem.
- name: Pre-upgrade health gate
  hosts: localhost
  connection: local
  gather_facts: true

  tasks:
    - name: Reuse Project 11's cluster health checks                       # avoids duplicating the Node/ClusterOperator/ClusterVersion logic
      ansible.builtin.import_tasks: cluster_health_checks.yml                # extracted shared tasks file, see note below
      # NOTE: refactor Project 11's inline tasks into
      # playbooks/cluster_health_checks.yml (same content, just
      # extracted) so both playbooks import the same source of truth.

    - name: Check for any in-progress MachineConfigPool rollout             # starting an upgrade mid-rollout compounds risk
      kubernetes.core.k8s_info:
        kind: MachineConfigPool                                              # tracks node config rollout state
        api_version: machineconfiguration.openshift.io/v1
      register: mcps                                                          # holds all pools (worker, master, custom)

    - name: Assert no MachineConfigPool is mid-update                         # hard stop if true
      ansible.builtin.assert:
        that:
          - item.status.conditions | selectattr('type','equalto','Updating')
              | map(attribute='status') | first == "False"                    # Updating condition must be False on every pool
        fail_msg: "MachineConfigPool {{ item.metadata.name }} is mid-rollout -- wait before upgrading"
      loop: "{{ mcps.resources }}"                                             # check every pool, not just 'worker'
      loop_control: {label: "{{ item.metadata.name }}"}                        # cleaner loop output -- just the pool name

    - name: Assert no NotReady nodes and no Degraded operators                 # the actual gate condition, using facts from the imported tasks
      ansible.builtin.assert:
        that:
          - not_ready_nodes | length == 0
          - degraded_operators | length == 0
        fail_msg: "Cluster is NOT healthy -- resolve issues before starting the upgrade (see cluster-health-report.txt)"

    - name: Gate passed                                                        # clear positive confirmation, not just absence of failure
      ansible.builtin.debug:
        msg: "Pre-upgrade gate PASSED -- cluster is healthy and stable, safe to proceed"

4.2 playbooks/post_upgrade_validate.yml

playbooks/post_upgrade_validate.yml
---
# Post-upgrade validation -- confirms BOTH platform health AND
# application health before the upgrade is declared successful.
- name: Post-upgrade validation
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Confirm ClusterVersion reached the desired version                 # platform-level confirmation
      kubernetes.core.k8s_info:
        kind: ClusterVersion
        api_version: config.openshift.io/v1
        name: version
      register: cv                                                              # holds .status.history and .status.desired

    - name: Assert the latest history entry is Completed                        # not just 'desired matches' -- confirms it finished cleanly
      ansible.builtin.assert:
        that:
          - cv.resources[0].status.history[0].state == "Completed"               # most recent entry, index 0, must show Completed
        fail_msg: "ClusterVersion history shows the upgrade did not complete cleanly"

    - name: Re-run the platform health checks (same as pre-upgrade)              # confirms nothing broke DURING the upgrade
      ansible.builtin.import_tasks: cluster_health_checks.yml                     # same shared tasks file as the pre-upgrade gate

    - name: Assert platform is still fully healthy post-upgrade                   # same bar as the pre-upgrade gate, now checked again
      ansible.builtin.assert:
        that:
          - not_ready_nodes | length == 0
          - degraded_operators | length == 0
        fail_msg: "Platform health regressed after upgrade -- see cluster-health-report.txt"

    - name: Confirm payment-api backend pods are Running and Ready               # application-level confirmation, not just platform
      kubernetes.core.k8s_info:
        kind: Pod
        namespace: "{{ app_name }}-{{ environment }}"
        label_selectors: ["app={{ app_name }}-backend"]                            # same label convention used since Project 1
      register: app_pods                                                            # holds live pod list post-upgrade

    - name: Assert every backend pod is Ready                                        # catches the "app-level regression" gap from last quarter's incident
      ansible.builtin.assert:
        that:
          - item.status.containerStatuses[0].ready == true                           # each pod's container must report ready
        fail_msg: "Pod {{ item.metadata.name }} is not Ready after upgrade"
      loop: "{{ app_pods.resources }}"
      loop_control: {label: "{{ item.metadata.name }}"}

    - name: Confirm the frontend Route responds successfully                          # end-to-end check, closest to what a real user experiences
      ansible.builtin.uri:                                                             # makes an actual HTTP request
        url: "https://{{ route_host }}/health-check-payment"                             # the app's own health endpoint, reached externally
        status_code: 200                                                                # must return OK
        validate_certs: true                                                            # confirms TLS is also still valid post-upgrade
      register: route_check
      retries: 5                                                                        # brief retry -- allow a few seconds for post-upgrade router reload
      delay: 10

    - name: Validation passed                                                            # clear success confirmation
      ansible.builtin.debug:
        msg: "Post-upgrade validation PASSED -- platform and payment-api both healthy"

6. Live Incident — Upgrade Stuck at 80%

ReportTwo hours into the upgrade window, oc adm upgrade still shows progress stalled around 80%, past the expected completion time.
Step 1 — check ClusterVersion for the specific blocker
oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING
version   4.14.18   True        True

oc describe clusterversion
Message: Unable to apply 4.15.9: wait has exceeded 40 minutes for these
  operators: monitoring
Step 2 — check the specific blocking operator (reusing Project 11's method)
oc describe clusteroperator monitoring
Message: Degraded: reconciling Prometheus StatefulSet: 0/2 replicas ready --
  PersistentVolumeClaim prometheus-k8s-db-prometheus-k8s-1 pending
Step 3 — check the actual PVC
oc describe pvc prometheus-k8s-db-prometheus-k8s-1 -n openshift-monitoring
Events: waiting for first consumer to be created before binding
# WaitForFirstConsumer mode PVC combined with a zone the new node's
# CSI driver can't currently reach -- a transient capacity issue in
# one specific availability zone during the mid-upgrade node churn
Root causeA monitoring-stack PVC couldn't bind because of transient zone capacity during the upgrade's node churn, blocking one Prometheus replica, which blocked the monitoring ClusterOperator, which blocked the whole upgrade from progressing past it — using exactly the layered troubleshooting approach from Project 11 (Node → ClusterOperator → underlying resource).
Step 4 — mitigate: this resolves once zone capacity frees up; confirm and wait rather than force anything
oc get pvc prometheus-k8s-db-prometheus-k8s-1 -n openshift-monitoring -w
# eventually transitions to Bound as capacity becomes available
Step 5 — once resolved, confirm the upgrade resumes and completes
oc get clusterversion
NAME      VERSION   AVAILABLE   PROGRESSING
version   4.15.9    True        False
Step 6 — run post-upgrade validation as normal
ansible-playbook playbooks/post_upgrade_validate.yml -e app_name=payment-api -e environment=prod
ResolvedUpgrade completed to 4.15.9; both platform and payment-api validated healthy.

7. Additional Break-Fix Labs

Break-Fix — pre-upgrade gate blocks on a stale MCP rollout 
TASK [Assert no MachineConfigPool is mid-update] ***
fatal: [localhost]: FAILED! => {"msg": "MachineConfigPool worker is mid-rollout -- wait before upgrading"}

Root cause: Project 12's MachineConfig change was still rolling out from earlier that day. Fix: this is the gate working correctly — wait for oc get mcp to show UPDATED=True before proceeding, exactly as designed.

Break-Fix — post-upgrade Route check fails, everything else passes 
TASK [Confirm the frontend Route responds successfully] ***
fatal: [localhost]: FAILED! => {"msg": "Status code was 503"}

Root cause: platform and pods are healthy, but this maps straight back to Project 4's troubleshooting method — check Route admission, then Service endpoints, then pod readiness specifically, since a new OpenShift router version occasionally needs a Route re-admission after upgrade.

9. Interview Preparation

Interviewer: "How do you approach planning an OpenShift cluster upgrade?"

Answer: I never start an upgrade on top of an unhealthy cluster — a pre-upgrade gate checks for NotReady nodes, Degraded ClusterOperators, and any in-progress MachineConfigPool rollout, and refuses to proceed if anything's outstanding. The actual upgrade trigger I leave to OpenShift's own tooling — oc adm upgrade — since the Cluster Version Operator already has sophisticated sequencing logic I don't want to fight. After it completes, I validate both platform health and application health, including an actual HTTP check against the app's real endpoint, not just checking that pods say Ready.

Interviewer: "An upgrade is stuck partway through — how do you debug it?"

Answer: oc describe clusterversion almost always names the specific blocking operator. From there it's the same layered approach as any ClusterOperator investigation — oc describe clusteroperator <name>, then follow its Message field down to the actual underlying resource, which in one case was a PVC blocked by transient zone capacity.
