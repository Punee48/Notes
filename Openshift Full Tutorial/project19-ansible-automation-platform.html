1. The Production Story

Scenario Every playbook so far has been run from someone's laptop or a Jenkins agent with their personal oc login session and locally-stored credentials. That's fine for a lab, but it means no central audit log of who ran what against PROD, no approval gate before a PROD-impacting playbook runs, and every engineer needs their own copy of every credential.
Business Problem Compliance asks a simple question nobody can answer cleanly: "show me every Ansible run against the PROD cluster in the last 90 days, who triggered each one, and what changed." Laptop-run playbooks leave no such record.
Our Mandate Move execution into Automation Controller: Job Templates for each existing playbook, credentials stored centrally (never on a laptop), a Survey for common inputs, and a Workflow Template chaining pre-checks → deploy → validation → with a manual approval node before anything touches PROD.

2. Run This On Your Device

NoteAutomation Controller itself needs an AAP installation (trial license available from Red Hat for lab use) — this is infrastructure you stand up once, not something CRC provides out of the box.
Confirm Automation Controller is reachable and log in. 
curl -k https://<controller-host>/api/v2/ping/
Add a Project in Controller pointing at your existing Git repo (all playbooks from Projects 1-18 live here already).
Add a Credential of type "OpenShift or Kubernetes API Bearer Token" — never a personal oc login session.
Create the Job Templates and Workflow using the awx.awx collection playbook from Section 4 (configuration-as-code, not clicking through the UI). 
ansible-galaxy collection install awx.awx
ansible-playbook controller_config.yml -e controller_host=https://controller.example.com \
  -e controller_token=$CONTROLLER_TOKEN
Launch the Workflow Template for a DEV deploy and watch it run in the Controller UI.

3. Architecture

Job Template = ONE playbook + Project + Credential + default variables │ ▼ Survey = user-facing form for the variables a human should choose (app_name, environment) -- NOT secrets, those stay in Credentials │ ▼ Workflow Template = a DAG of Job Templates: [Pre-Deploy Check] ──pass──▶ [Approval Node -- PROD only] ──▶ [Deploy] │fail │ ▼ ▼ [Notify] [Post-Deploy Validate] │fail ▼ [Rollback]
ConceptPurpose
ProjectController's pointer to the Git repo holding all our playbooks — always pulls the latest commit
CredentialCentrally stored, RBAC-controlled — engineers never see the raw token
Job TemplateBinds one playbook to one Project/Credential/Inventory combination
SurveyA form UI for the handful of variables a human should choose (app_name, environment) — not a way to bypass Credentials
Workflow TemplateChains Job Templates with success/failure branching and optional manual approval nodes
Execution EnvironmentA container image with Ansible + required collections pre-installed — guarantees every run uses identical tooling versions

4. Configuration-as-Code — Fully Commented

Meta noteWe use Ansible itself (the awx.awx collection) to configure Automation Controller — Job Templates, Surveys, and Workflows are defined as code and version-controlled, not clicked through the UI by hand, for the exact same drift-prevention reasons as every prior project.

4.1 controller_config.yml

controller_config.yml
---
# Defines Job Templates and a Workflow Template as code, using the
# awx.awx collection's modules against the Controller API.
- name: Configure Automation Controller for payment-api
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Create Job Template for pre-deploy validation                 # wraps Project 18's pre_deploy_check.yml
      awx.awx.job_template:                                                # awx.awx module -- talks to the Controller API, not the OpenShift API
        name: "payment-api-pre-deploy-check"                                # shown in the Controller UI job list
        job_type: run                                                       # normal run, not check-mode-only
        project: "payment-stack-repo"                                       # must match an existing Controller Project name
        playbook: "playbooks/pre_deploy_check.yml"                           # path within that Project's Git repo
        credentials: ["payment-api-openshift-token"]                         # references a centrally-stored Credential, never inline
        controller_host: "{{ controller_host }}"                             # Controller API endpoint
        controller_username: "{{ controller_username | default(omit) }}"      # auth -- omit lets token-based auth take over if provided instead
        controller_password: "{{ controller_password | default(omit) }}"
        controller_oauthtoken: "{{ controller_token | default(omit) }}"        # preferred: a scoped OAuth token, not username/password
        survey_enabled: true                                                   # turns on the Survey form for this template
        survey_spec:                                                           # the actual form fields shown to whoever launches this
          name: ""
          description: "Deployment target"
          spec:
            - question_name: "Application Name"                                 # label shown in the UI
              variable: app_name                                                  # maps to the -e app_name=... variable
              type: text
              default: "payment-api"                                              # pre-filled default value
              required: true                                                       # can't launch without filling this in
            - question_name: "Environment"
              variable: environment
              type: multiplechoice                                                  # dropdown, not free text -- prevents typos like Project 2's incident
              choices: "dev\nqa\nstage\nprod"                                         # fixed valid options only
              required: true

    - name: Create Job Template for deployment (reuses Project 3/5's playbook)        # same survey pattern, different playbook target
      awx.awx.job_template:
        name: "payment-api-deploy"
        job_type: run
        project: "payment-stack-repo"
        playbook: "playbooks/site.yml"
        credentials: ["payment-api-openshift-token"]
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_token }}"
        survey_enabled: true
        survey_spec: "{{ shared_survey_spec }}"                                        # reuses the same app_name/environment questions via a shared var

    - name: Create Job Template for post-deploy validation (Project 13's pattern)         # same reuse pattern
      awx.awx.job_template:
        name: "payment-api-post-deploy-validate"
        job_type: run
        project: "payment-stack-repo"
        playbook: "playbooks/post_upgrade_validate.yml"
        credentials: ["payment-api-openshift-token"]
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_token }}"

    - name: Create Job Template for rollback (Project 5's playbook)                        # kept ready, invoked only on workflow failure
      awx.awx.job_template:
        name: "payment-api-rollback"
        job_type: run
        project: "payment-stack-repo"
        playbook: "playbooks/rollback.yml"
        credentials: ["payment-api-openshift-token"]
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_token }}"

    - name: Create the Workflow Template chaining all of the above                          # the actual governed pipeline, as code
      awx.awx.workflow_job_template:
        name: "payment-api-governed-deploy"                                                  # what engineers actually launch
        controller_host: "{{ controller_host }}"
        controller_oauthtoken: "{{ controller_token }}"
        survey_enabled: true
        survey_spec: "{{ shared_survey_spec }}"                                                # one form drives the whole workflow's variables
        workflow_nodes:                                                                         # the DAG structure itself
          - identifier: pre_check
            unified_job_template: "payment-api-pre-deploy-check"                                  # first node -- always runs
            related:
              success_nodes: [approval_gate]                                                       # only proceeds on success

          - identifier: approval_gate                                                              # manual human gate, PROD-critical
            unified_job_template: "payment-api-prod-approval"                                        # a Workflow Approval node type, defined separately
            related:
              success_nodes: [deploy]

          - identifier: deploy
            unified_job_template: "payment-api-deploy"
            related:
              success_nodes: [post_validate]
              failure_nodes: [rollback]                                                             # deploy failure triggers rollback directly

          - identifier: post_validate
            unified_job_template: "payment-api-post-deploy-validate"
            related:
              failure_nodes: [rollback]                                                              # validation failure ALSO triggers rollback

          - identifier: rollback
            unified_job_template: "payment-api-rollback"                                              # terminal node -- no further branching needed

6. Live Incident — Untracked Laptop Run Bypasses the Approval Gate

ReportA PROD config change appears in the cluster that nobody remembers approving through the Workflow Template.
Step 1 — check Automation Controller's job history for the relevant time window
Controller UI > Jobs, filtered to payment-api-prod, last 24 hours:
(no matching jobs)
Root cause candidateThe change didn't go through Controller at all — meaning it bypassed both the audit log AND the approval gate entirely.
Step 2 — check who has direct cluster credentials outside Controller
oc get events -n payment-api-prod --sort-by='.lastTimestamp' | tail -5
# shows the change was applied by a personal kubeconfig token, not the Controller service account
Root causeAn engineer still had a personal oc login session with direct write access to PROD and ran ansible-playbook from their laptop instead of going through the governed Workflow Template — the migration to Controller (this project) hadn't yet revoked standing personal PROD access.
Step 3 — remediate: revoke standing personal access, funnel all PROD changes through Controller
# RBAC change (Project 2 pattern): remove direct 'edit'/'admin' RoleBindings
# for individual engineers in payment-api-prod; only the Controller
# service account retains write access.
ansible-playbook playbooks/site.yml -e app_name=payment-api -e environment=prod \
  -e team=platform -e rbac_role_for_teams=view   # humans get read-only 'view' directly; writes only via Controller
Step 4 — validate the gate can no longer be bypassed
oc auth can-i update deployments -n payment-api-prod --as=engineer@company.com
> no   # correct -- all PROD writes must now go through the Controller Workflow
ResolvedPROD changes now physically cannot bypass the approval gate and audit log, closing the compliance gap that started this project.

RCA Summary

FieldDetail
ImpactOne untracked, unapproved PROD change — no customer impact, but a real audit/compliance gap
Root causeMigration to Automation Controller didn't include revoking standing personal write RBAC to PROD, so the old bypass path still worked
FixReduced personal RBAC to view in PROD; only the Controller's own credential retains write access
Preventive actionAdd this RBAC reduction as a required final step in any future "move X to governed execution" migration checklist

7. Additional Break-Fix Labs

Break-Fix — Workflow stuck at the approval node 
Controller UI: Workflow Job #4021 -- status: "Pending Approval"
# stuck for hours, nobody approved it

Root cause: the approval node had no notification configured, so nobody knew it was waiting. Fix: attach a Notification Template (Slack/email) to the approval node so it actively pages the approver instead of silently waiting.

Break-Fix — Job Template fails, "collection not found" 
ERROR! couldn't resolve module/action 'kubernetes.core.k8s'

Root cause: the Execution Environment image used by this Job Template doesn't include the kubernetes.core collection. Fix: build/select an Execution Environment image with the required collections pre-installed rather than relying on whatever happens to be on a default image.

9. Interview Preparation

Interviewer: "Why move from standalone ansible-playbook runs to Automation Controller?"

Answer: Three things a laptop-run playbook can't give you: centralized, RBAC-controlled credentials so individual engineers never hold raw PROD tokens; a full audit trail of who ran what and when; and enforceable approval gates for sensitive environments via Workflow Templates. I define all of this as code using the awx.awx collection rather than clicking through the UI, for the same drift-prevention reasons as everything else in this series.

Interviewer: "You migrated to governed execution but an unapproved change still got through — what happened?"

Answer: The migration added the governed path but didn't remove the old one — an engineer still had standing personal write RBAC to PROD and ran the playbook locally, bypassing Controller entirely. The real fix wasn't a Controller setting, it was reducing that engineer's direct RBAC to read-only, so the old bypass physically stopped working. It's a good reminder that a new control only works if the old path is actually closed, not just discouraged.
