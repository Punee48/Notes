1. The Production Story

Scenario The company is expanding into a new region and regulatory requirements mean payment-api needs a second, geographically-separate OpenShift cluster — not just another namespace, an entirely separate cluster, with its own nodes and control plane. Managing two clusters by running every playbook from Projects 1-26 twice, by hand, against two different oc login contexts, doesn't scale and reintroduces exactly the drift risk Project 19 solved for a single cluster.
Business Problem Without central multi-cluster management, the two clusters will drift apart in RBAC, NetworkPolicy baseline, and SCC configuration within weeks — nobody will consistently remember to apply every governance change to both.
Our Mandate Stand up RHACM's hub-and-spoke model, import the second cluster as a managed cluster, and use RHACM Policies (backed by our existing Ansible playbooks as the actual enforcement mechanism) to guarantee both clusters stay governed identically.

3. Architecture

HUB CLUSTER (RHACM / multicluster engine) │ ├── ManagedCluster: payment-api-us-east (existing, from Projects 1-26) └── ManagedCluster: payment-api-eu-west (new, imported this project) │ ▼ Policy objects (created once, on the HUB): - RBAC baseline policy (wraps Project 2's role logic) - NetworkPolicy baseline policy (wraps Project 1/21's roles) - SCC policy (wraps Project 20's role) │ ▼ PlacementRule -- targets BOTH managed clusters │ ▼ Policy propagated and enforced on EACH spoke independently │ ▼ PolicyReport aggregated back to the HUB -- one dashboard shows compliance status across every cluster simultaneously
ConceptPurpose
Hub clusterRuns RHACM itself; the single control point for governance across all managed clusters
ManagedClusterA spoke cluster registered with the hub via an agent, reporting status and receiving Policies
PolicyRHACM's governance object — can wrap raw Kubernetes objects OR reference existing Ansible automation as the actual remediation
PlacementRuleDetermines WHICH managed clusters a given Policy applies to (label-based selection)

4. The Playbooks — Fully Commented

4.1 playbooks/import_cluster.yml

playbooks/import_cluster.yml
---
# Imports an existing standalone OpenShift cluster as an RHACM
# ManagedCluster -- run against the HUB cluster's API.
- name: Import a cluster into RHACM
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Create the ManagedCluster object on the hub                     # registers intent to manage this cluster
      kubernetes.core.k8s:
        state: present                                                       # idempotent apply
        definition:
          apiVersion: cluster.open-cluster-management.io/v1                    # RHACM's cluster registration API group
          kind: ManagedCluster
          metadata:
            name: "{{ cluster_name }}"                                          # unique cluster identifier, e.g. payment-api-eu-west
            labels:
              region: "{{ cluster_region | default('unspecified') }}"              # used later by PlacementRule label selection
              environment: production                                              # distinguishes this from any lab/test clusters
          spec:
            hubAcceptsClient: true                                                  # hub explicitly agrees to manage this cluster -- a deliberate opt-in, not automatic
      register: mc_result                                                            # capture for assert

    - name: Assert ManagedCluster creation succeeded                                  # fail fast on API rejection
      ansible.builtin.assert:
        that: [mc_result is succeeded]
        fail_msg: "Failed to register ManagedCluster {{ cluster_name }}"

    - name: Retrieve the generated import command/manifest                              # RHACM generates a bootstrap manifest to run ON the spoke cluster
      kubernetes.core.k8s_info:
        kind: Secret
        name: "{{ cluster_name }}-import"                                                 # auto-created Secret containing the klusterlet bootstrap YAML
        namespace: "{{ cluster_name }}"
      register: import_secret                                                              # holds the import manifest -- applied manually on the spoke, or via a separate Ansible run targeting that cluster's own API

    - name: Wait for the spoke cluster to report itself Available                            # confirms the klusterlet agent successfully connected back to the hub
      kubernetes.core.k8s_info:
        kind: ManagedCluster
        api_version: cluster.open-cluster-management.io/v1
        name: "{{ cluster_name }}"
      register: mc_status                                                                     # holds live .status.conditions
      until: >
        (mc_status.resources[0].status.conditions
         | selectattr('type','equalto','ManagedClusterConditionAvailable')
         | map(attribute='status') | first) == "True"                                            # confirms the spoke is actually reachable, not just registered
      retries: 20                                                                                  # import can take a few minutes
      delay: 15

4.2 playbooks/acm_policy.yml

playbooks/acm_policy.yml
---
# Creates a Policy on the hub that enforces our RBAC baseline
# (wrapping Project 2's actual logic) across EVERY managed cluster
# matching the PlacementRule -- one definition, many clusters.
- name: Apply governance Policy across all managed clusters
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Create the Policy object                                            # the governance rule itself
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: policy.open-cluster-management.io/v1                        # RHACM's governance API group
          kind: Policy
          metadata:
            name: "{{ app_name }}-rbac-baseline"                                    # descriptive, one Policy per governance concern
            namespace: open-cluster-management-policies                             # conventional namespace for Policy objects on the hub
          spec:
            remediationAction: enforce                                               # actively FIXES drift, not just reports it -- the multi-cluster equivalent of Project 2's re-apply-on-drift behavior
            policy-templates:
              - objectDefinition:
                  apiVersion: policy.open-cluster-management.io/v1
                  kind: ConfigurationPolicy                                            # the actual object-comparison sub-policy
                  metadata:
                    name: "{{ app_name }}-rbac-baseline-config"
                  spec:
                    remediationAction: enforce                                            # must also be set at this level
                    severity: high                                                          # shown in the compliance dashboard's prioritization
                    object-templates:
                      - complianceType: musthave                                              # the RoleBinding MUST exist with this exact spec
                        objectDefinition:
                          apiVersion: rbac.authorization.k8s.io/v1                              # mirrors Project 2's actual RoleBinding definition exactly
                          kind: RoleBinding
                          metadata:
                            name: payments-edit-binding
                            namespace: "{{ app_name }}-prod"
                          subjects:
                            - kind: Group
                              name: payments-developers                                            # same value Project 2's incident fixed -- now enforced across every cluster automatically
                              apiGroup: rbac.authorization.k8s.io
                          roleRef:
                            kind: ClusterRole
                            name: edit
                            apiGroup: rbac.authorization.k8s.io
      register: policy_result                                                                        # capture for assert

    - name: Assert Policy creation succeeded
      ansible.builtin.assert:
        that: [policy_result is succeeded]
        fail_msg: "Failed to create {{ app_name }}-rbac-baseline Policy"

    - name: Create the PlacementRule targeting all production payment-api clusters      # decides WHICH clusters this Policy actually reaches
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: apps.open-cluster-management.io/v1                                 # RHACM's placement API group
          kind: PlacementRule
          metadata:
            name: "{{ app_name }}-placement"
            namespace: open-cluster-management-policies
          spec:
            clusterSelector:
              matchLabels: {environment: production}                                       # matches the label set during import (Section 4.1) -- both clusters qualify
      register: placement_result

    - name: Assert PlacementRule creation succeeded
      ansible.builtin.assert:
        that: [placement_result is succeeded]
        fail_msg: "Failed to create PlacementRule for {{ app_name }}"

6. Live Incident — Compliant on Hub, Violated on Spoke

ReportThe RHACM dashboard shows the RBAC baseline Policy as "Compliant" across both clusters, but an engineer in the EU region reports the exact same "can't deploy" symptom as Project 2's original incident.
Step 1 — check the Policy status more closely, per-cluster
oc get policy payment-api-rbac-baseline -n open-cluster-management-policies -o yaml
status:
  compliant: Compliant
  status:
    - clustername: payment-api-us-east
      compliant: Compliant
    - clustername: payment-api-eu-west
      compliant: Compliant   # both say compliant -- but the symptom says otherwise
Step 2 — check directly on the EU spoke cluster itself
# (logged into the EU cluster directly, not through the hub)
oc get rolebinding payments-edit-binding -n payment-api-prod
NAME                    ROLE           AGE
payments-edit-binding   ClusterRole/edit   45d
oc get rolebinding payments-edit-binding -n payment-api-prod -o yaml | grep -A2 subjects
subjects:
  - kind: Group
    name: payments-developers-eu   # DIFFERENT group name -- the EU region's IdP uses a region-suffixed naming convention
Root causeThe Policy's musthave comparison only checks that a RoleBinding named payments-edit-binding EXISTS with a roleRef of edit — it wasn't strict enough to catch that the SUBJECT'S group name was wrong for this region's actual IdP group naming convention. The Policy was technically satisfied by its own (too-loose) definition while still being functionally broken for EU users.
Step 3 — fix: make the Policy region-aware using Ansible variable templating before it's applied
# Instead of one static Policy, template per region and re-apply:
ansible-playbook playbooks/acm_policy.yml -e app_name=payment-api \
  -e group_name_suffix="-eu"   # produces 'payments-developers-eu' for the EU-targeted Policy variant
Step 4 — validate against the actual EU IdP group
oc auth can-i create deployments -n payment-api-prod --as=engineer@eu.company.com
> yes
ResolvedBeyond the immediate fix, this revealed a real gap: "Compliant" in RHACM only means the Policy's OWN definition matched — it says nothing about whether that definition was actually correct or complete for every region it applies to.

RCA Summary

FieldDetail
ImpactEU engineers blocked from deploying while the dashboard showed full compliance, delaying detection
Root causeA single, region-agnostic Policy definition didn't account for the EU cluster's different IdP group naming convention
FixTemplated region-specific Policy variants via Ansible rather than one static definition assumed to fit every cluster
Preventive actionAdd an actual functional check (oc auth can-i-style, per region) alongside the structural Policy check — "the object matches" and "the object actually grants the intended access" are different questions

7. Additional Break-Fix Labs

Break-Fix — ManagedCluster stuck, never becomes Available 
oc get managedcluster payment-api-eu-west
AVAILABLE: Unknown

Root cause: the klusterlet import manifest was never actually applied on the spoke cluster's own API — Section 4.1 only generates it, applying it is a separate step against the SPOKE's credentials. Fix: confirm the import Secret's manifest was applied with oc apply -f against the spoke cluster specifically, not the hub.

Break-Fix — Policy shows NonCompliant, enforce doesn't seem to fix it 
oc get policy payment-api-rbac-baseline -o yaml
status: {compliant: NonCompliant}
# stays NonCompliant even after several minutes

Root cause: the RHACM agent on the spoke cluster lacks RBAC permission to actually create/patch the target object itself. Fix: confirm the klusterlet's own ServiceAccount has sufficient cluster permissions — a governance tool needs write access to enforce anything, same principle as Project 19's Controller credential scoping.

9. Interview Preparation

Interviewer: "How do you keep governance consistent across multiple OpenShift clusters?"

Answer: RHACM's hub-and-spoke model lets me define a Policy once on the hub and have it enforced independently on every managed cluster, with compliance status aggregated back centrally. I template the actual object definitions from the same Ansible roles I already use for single-cluster governance, so there's one source of truth rather than maintaining parallel Policy YAML by hand. The key thing I learned is that a Policy showing 'Compliant' only means its own definition matched — if that definition doesn't account for real differences between clusters, like a different IdP group naming convention per region, you can be fully compliant and still functionally broken.

Interviewer: "A multi-cluster policy showed 100% compliant but a real access problem still existed — how do you explain that?"

Answer: Structural compliance (does the object exist with the expected shape) and functional correctness (does it actually grant the intended access, for THIS cluster's real identities) are different questions. Our RBAC Policy checked that a RoleBinding existed pointing at 'edit' — true on every cluster — but not that its subject's group name matched each region's actual IdP convention. I added region-specific Policy variants and a functional can-i-style check alongside the structural one, since compliance dashboards can create false confidence if they only check shape.
