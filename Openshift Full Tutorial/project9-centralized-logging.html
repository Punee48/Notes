1. The Production Story

Scenario Project 8 gave us metrics and alerts, but when the "high restart rate" alert fires, we still have to manually oc logs pod by pod to figure out what actually happened. As the app scales to more replicas, that stops being practical. The team wants centralized, searchable logs with the ability to trace one customer's request across frontend, backend, and database log lines.
Business Problem Logs currently only exist as long as a pod does — once a CrashLoopBackOff pod is replaced, its logs are gone unless someone was watching in real time.
Our Mandate Deploy the OpenShift Logging stack (Loki + Vector-based collection) via Ansible/Operator automation, and standardize correlation-ID logging so one failed payment can be traced across every tier.

3. Architecture

Pod stdout/stderr (frontend, backend, postgres) │ ▼ Vector collector (runs as a DaemonSet on every node) │ reads container log files, adds Kubernetes metadata ▼ ClusterLogForwarder — routes logs by type (application/infra/audit) │ ▼ LokiStack (object storage-backed, indexed by labels not full text) │ ▼ Console "Observe > Logs" or Grafana — LogQL queries, correlated by correlation_id label across frontend/backend/db log lines
ObjectPurpose
LokiStackThe actual log storage/query backend, sized by tenant (application/audit/infra)
ClusterLogForwarderDeclares which log types go where — Loki, external SIEM, both
VectorNode-level collector; reads container logs, attaches pod/namespace labels automatically
Correlation IDAn app-generated request ID logged at every tier, letting you filter one request's full path

4. The Playbooks — Fully Commented

4.1 roles/logging_operator/tasks/main.yml

roles/logging_operator/tasks/main.yml
---
# Installs Loki Operator + Cluster Logging Operator, reusing the
# Subscription + wait-for-CSV pattern established in Project 7.

- name: Install Loki Operator                                          # reuses the operator_install role from Project 7 -- no duplicated logic
  ansible.builtin.include_role:
    name: operator_install                                              # the exact role built in Project 7
  vars:
    operator_name: loki-operator                                         # overrides the variable that role expects
    operator_channel: stable-5.9                                          # explicit channel, never implicit 'latest'

- name: Install Cluster Logging Operator                                 # second operator, same reused role
  ansible.builtin.include_role:
    name: operator_install
  vars:
    operator_name: cluster-logging
    operator_channel: stable

- name: Create LokiStack instance sized for our lab                       # the actual log storage backend
  kubernetes.core.k8s:
    state: present                                                        # idempotent apply
    definition:
      apiVersion: loki.grafana.com/v1                                       # Loki Operator's CRD API group
      kind: LokiStack
      metadata:
        name: logging-loki                                                   # fixed, well-known name Cluster Logging expects by default
        namespace: openshift-logging                                         # standard namespace for the logging stack
      spec:
        size: "{{ loki_size | default('1x.demo') }}"                          # 1x.demo = small footprint, fine for lab; use 1x.medium+ for real PROD volume
        storage:
          schemas:
            - version: v13                                                     # current recommended schema version
              effectiveDate: "2024-01-01"                                       # schema activation date -- required field
          secret:
            name: loki-object-storage                                          # references a pre-created Secret with S3/object-storage creds
            type: s3                                                            # backend type -- swap per your actual object storage provider
        storageClassName: "{{ db_storage_class | default('standard') }}"        # reuses the same StorageClass variable pattern from Project 6
  register: loki_result                                                          # capture for assert

- name: Assert LokiStack apply succeeded                                          # fail fast if the CRD/spec is rejected
  ansible.builtin.assert:
    that: [loki_result is succeeded]
    fail_msg: "Failed to create LokiStack instance"

4.2 roles/log_forwarder/tasks/main.yml

roles/log_forwarder/tasks/main.yml
---
# Configures WHICH logs get collected and WHERE they go.

- name: Create ClusterLogForwarder routing application logs to Loki       # the actual routing declaration
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: observability.openshift.io/v1                            # current ClusterLogForwarder API group
      kind: ClusterLogForwarder
      metadata:
        name: instance                                                       # conventional fixed name
        namespace: openshift-logging
      spec:
        outputs:
          - name: default-loki                                                # logical name referenced by pipelines below
            type: lokiStack                                                    # output type -- points at our LokiStack instance
            lokiStack:
              target: {name: logging-loki, namespace: openshift-logging}        # must match the LokiStack created above
        pipelines:
          - name: app-logs-to-loki                                              # pipeline name -- shown in status/troubleshooting
            inputRefs: [application]                                            # built-in input type: container stdout/stderr from app namespaces
            outputRefs: [default-loki]                                          # must match an output name above
  register: clf_result

- name: Assert ClusterLogForwarder apply succeeded                                # fail fast rather than silently having no log flow
  ansible.builtin.assert:
    that: [clf_result is succeeded]
    fail_msg: "Failed to create ClusterLogForwarder"

- name: Ensure backend ConfigMap instructs structured JSON logging with correlation IDs  # app-side convention, enforced via config
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ConfigMap
      metadata:
        name: "{{ app_name }}-logging-config"
        namespace: "{{ app_name }}-{{ environment }}"
      data:
        LOG_FORMAT: json                                                          # structured logs parse far better in Loki/LogQL than free text
        LOG_CORRELATION_HEADER: "X-Request-ID"                                     # tells the app which inbound header to propagate/log as correlation_id

6. Live Incident — "Which Request Actually Failed?"

ReportA customer says their payment failed around 3:40 PM, but the error rate metric from Project 8 only shows an aggregate spike — not which specific request, or why.
Step 1 — search application logs by time window in Observe > Logs
{kubernetes_namespace_name="payment-api-prod"} |= "3:4" | json

Too broad — hundreds of lines in that window across all three tiers.

Step 2 — narrow using the correlation ID once the customer provides their confirmation/error reference
{kubernetes_namespace_name="payment-api-prod"} | json | correlation_id="req-8f3a21"
frontend  correlation_id=req-8f3a21  "POST /checkout received"
backend   correlation_id=req-8f3a21  "calling payment gateway, timeout=0ms"
backend   correlation_id=req-8f3a21  "ERROR: gateway call failed: context deadline exceeded"
frontend  correlation_id=req-8f3a21  "returned 502 to client"
Root causeSame underlying issue as Project 5's incident — a timeout=0ms misconfiguration — but this time we found the EXACT failing request in under a minute by filtering on correlation ID, instead of guessing from aggregate metrics alone.
Step 3 — confirm this is isolated or widespread
{kubernetes_namespace_name="payment-api-prod"} | json | line_format "{{.correlation_id}}" | line_format "{{__error__}}" |= "timeout=0ms"
# count of matching lines in the last hour tells us blast radius
ResolvedConfirmed via logs that this affected a small window right after a config change, corrected the config, and — because we now have both metrics AND logs — closed the loop with concrete evidence in the RCA instead of a best guess.

7. Additional Break-Fix Labs

Break-Fix — logs not appearing in Loki at all 
oc get clusterlogforwarder instance -n openshift-logging -o yaml
status:
  conditions:
    - type: Ready
      status: "False"
      message: "output default-loki: LokiStack not found"

Root cause: ClusterLogForwarder was applied before the LokiStack finished provisioning. Fix: sequence the roles so log_forwarder only runs after logging_operator's LokiStack reaches Ready — add a k8s_info wait similar to Project 7's CSV wait pattern before creating the ClusterLogForwarder.

Break-Fix — correlation_id missing from log lines

Symptom: LogQL queries filtering on correlation_id return nothing, even though logs exist.

Root cause: the app isn't actually reading LOG_CORRELATION_HEADER from the ConfigMap yet — a config value alone doesn't change app behavior; the application code has to consume it. Fix: confirm with the application team that their logging middleware reads this env var (a config/app-code gap, not an infrastructure bug).

9. Interview Preparation

Interviewer: "How do you correlate logs across a multi-tier application?"

Answer: Every request gets an ID at the edge — usually from an inbound header like X-Request-ID, or generated if absent — and every tier logs that same ID with every line related to that request. In Loki/LogQL, that means one filter (correlation_id="...") pulls the entire request's path across frontend, backend, and database logs, which is far faster than grepping pod-by-pod.

Interviewer: "Why Loki instead of Elasticsearch for OpenShift logging?"

Answer: Loki indexes by label rather than full text, which is cheaper to run and operate at scale, and pairs naturally with the same Prometheus-style label model we're already using for metrics — it's the current default recommendation for OpenShift Logging.
