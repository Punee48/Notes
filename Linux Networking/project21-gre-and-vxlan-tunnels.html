1The Task

The platform team is extending a single logical network across two data centers that are only connected by ordinary routed IP — no shared switch, no dark fiber, nothing that could carry a VLAN trunk directly. They still need workloads in both locations to behave as if they're on the same flat Layer 2 or Layer 3 private network.

"We need servers in DC-1 and DC-2 to reach each other on a private 10.99.x.x network, completely separate from the public routed path between the sites, and eventually we want to run an overlay network across both for container workloads. Neither site can see the other's internal network directly today."

This is exactly what tunneling protocols are for — wrapping one network's traffic inside packets that can travel across a completely different, unrelated network (the "underlay"), and unwrapping them on the other side. We'll build the two most common Linux tunneling mechanisms: GRE, a simple point-to-point tunnel, and VXLAN, a more flexible overlay technology built for exactly this kind of multi-site or multi-host virtual networking.

🔵 Why this project matters

Tunneling is the mechanism behind an enormous share of modern infrastructure — VPN technologies, cloud provider overlay networks, Kubernetes CNI plugins that need cross-node pod networking (like Flannel's VXLAN backend), and traditional WAN designs connecting data centers. Understanding encapsulation directly — building it by hand — demystifies all of these.

2Tunneling Foundation

2.1 Encapsulation — a packet inside a packet

🔵 Concept

Tunneling works by taking an entire original packet (the "inner" packet — which might itself be a full Ethernet frame, or just an IP packet) and wrapping it inside a NEW outer packet, addressed using completely different source/destination IPs — the "underlay" network's addressing. The underlay network only ever sees the outer packet and has no idea what's inside it; only the tunnel endpoints know how to unwrap it back to the original inner packet.

2.2 GRE — a simple, generic point-to-point tunnel

🔵 Concept

GRE (Generic Routing Encapsulation) is one of the oldest and simplest tunneling protocols — it wraps an IP packet inside another IP packet, creating a virtual point-to-point link between exactly two endpoints. It's straightforward to configure and widely supported, making it a common choice for simple site-to-site connectivity, though it lacks built-in encryption (it's often paired with IPsec when confidentiality matters) and doesn't natively carry full Ethernet frames.

2.3 VXLAN — an overlay built for carrying Layer 2 across a Layer 3 network

🔵 Concept

VXLAN (Virtual Extensible LAN) wraps entire Ethernet frames inside UDP packets, letting you stretch a genuine Layer 2 broadcast domain across a routed IP network — exactly like Project 10's bridge, but with its "wire" now able to span an entire routed network instead of just a local segment. Each VXLAN network is identified by a VNI (VXLAN Network Identifier, similar in spirit to a VLAN ID but with a vastly larger range — up to about 16 million), letting many isolated overlay networks share the same physical underlay.

2.4 The underlay must already work — tunnels don't fix broken routing

🔵 Concept

A tunnel is built ON TOP of ordinary IP connectivity between its two endpoints — if the underlay network can't route packets between the tunnel endpoints' real IP addresses, the tunnel itself can never come up, no matter how correctly it's configured. This is the same "does the network even work first" instinct from Project 1, just applied one layer deeper.

4Troubleshooting Method

  • 1. Confirm the underlay works FIRST — can the two tunnel endpoints reach each other over plain, un-tunneled IP?
    • ↓
  • 2. Check the tunnel interface itself is up and correctly configured on both ends (matching remote/local addresses, matching VNI for VXLAN)
    • ↓
  • 3. Check MTU — encapsulation adds overhead, and the inner path's effective MTU is always smaller than the underlay's (Project 14's lesson, guaranteed to apply here)
    • ↓
  • 4. Capture on the UNDERLAY interface to see the outer, encapsulated packets directly
    • ↓
  • Once the tunnel itself is confirmed healthy, troubleshoot the "inner" overlay network using every tool from earlier in this masterclass, as if it were any other network
🟠 Warning

Always verify underlay connectivity before touching tunnel configuration — a huge fraction of "the tunnel won't come up" tickets are actually "the underlay can't reach the other endpoint's IP at all," which no amount of tunnel reconfiguration will fix.

5Build a GRE Tunnel

bash — run as root/sudo; simulate two data centers connected only by routed IP
1sudo ip netns add ns-dc1              # data center 1
2sudo ip netns add ns-underlay         # represents the routed WAN/internet between the two sites
3sudo ip netns add ns-dc2              # data center 2
4sudo ip link add veth-dc1 type veth peer name u-dc1-in
5sudo ip link add veth-dc2 type veth peer name u-dc2-in
6sudo ip link set veth-dc1 netns ns-dc1; sudo ip link set u-dc1-in netns ns-underlay
7sudo ip link set veth-dc2 netns ns-dc2; sudo ip link set u-dc2-in netns ns-underlay
8sudo ip netns exec ns-dc1 ip addr add 203.0.113.1/24 dev veth-dc1   # DC-1's real, routable underlay address
9sudo ip netns exec ns-underlay ip addr add 203.0.113.254/24 dev u-dc1-in
10sudo ip netns exec ns-underlay ip addr add 203.0.114.254/24 dev u-dc2-in
11sudo ip netns exec ns-dc2 ip addr add 203.0.114.1/24 dev veth-dc2   # DC-2's real, routable underlay address
12for ns in ns-dc1 ns-underlay ns-dc2; do sudo ip netns exec $ns ip link set lo up; done
13sudo ip netns exec ns-dc1 ip link set veth-dc1 up
14sudo ip netns exec ns-dc2 ip link set veth-dc2 up
15sudo ip netns exec ns-underlay bash -c "ip link set u-dc1-in up; ip link set u-dc2-in up; sysctl -w net.ipv4.ip_forward=1"
16sudo ip netns exec ns-dc1 ip route add 203.0.114.0/24 via 203.0.113.254   # DC-1 knows how to reach DC-2's underlay subnet, via the WAN
17sudo ip netns exec ns-dc2 ip route add 203.0.113.0/24 via 203.0.114.254   # DC-2 knows how to reach DC-1's underlay subnet, via the WAN

5.1 Build the GRE tunnel on top of this underlay

bash — on ns-dc1
1sudo ip netns exec ns-dc1 ip tunnel add gre1 mode gre remote 203.0.114.1 local 203.0.113.1 ttl 255   # create a GRE tunnel: remote/local are the UNDERLAY addresses of each end
2sudo ip netns exec ns-dc1 ip addr add 10.99.1.1/24 dev gre1   # the tunnel's own "inner" (overlay) IP address
3sudo ip netns exec ns-dc1 ip link set gre1 up
bash — on ns-dc2, the matching configuration
1sudo ip netns exec ns-dc2 ip tunnel add gre1 mode gre remote 203.0.113.1 local 203.0.114.1 ttl 255   # remote/local are swapped relative to DC-1's config, since this is DC-2's perspective
2sudo ip netns exec ns-dc2 ip addr add 10.99.1.2/24 dev gre1
3sudo ip netns exec ns-dc2 ip link set gre1 up
TokenMeaning
ip tunnel add gre1 mode gre remote <ip> local <ip>Creates a GRE tunnel device: remote is the OTHER end's real underlay IP, local is THIS end's real underlay IP — these are the addresses used for the outer, encapsulating packet.
ip addr add 10.99.1.1/24 dev gre1Assigns the tunnel's inner/overlay IP — completely separate address space from the underlay, exactly like a VLAN subinterface's address is separate from its trunk's.

6Build a VXLAN Overlay

Now let's build a VXLAN overlay across the same underlay, alongside our GRE tunnel, to see the difference directly.

bash — on ns-dc1
1sudo ip netns exec ns-dc1 ip link add vxlan100 type vxlan id 100 remote 203.0.114.1 local 203.0.113.1 dstport 4789   # id 100 is our VNI; dstport 4789 is the standard VXLAN UDP port
2sudo ip netns exec ns-dc1 ip addr add 10.99.2.1/24 dev vxlan100
3sudo ip netns exec ns-dc1 ip link set vxlan100 up
bash — on ns-dc2, matching VNI
1sudo ip netns exec ns-dc2 ip link add vxlan100 type vxlan id 100 remote 203.0.113.1 local 203.0.114.1 dstport 4789   # same VNI (100) — this is what makes them the same overlay network
2sudo ip netns exec ns-dc2 ip addr add 10.99.2.2/24 dev vxlan100
3sudo ip netns exec ns-dc2 ip link set vxlan100 up
TokenMeaning
type vxlan id 100The VNI — the overlay network identifier. Only endpoints configured with the SAME VNI are part of the same logical network, exactly like a VLAN ID's role from Project 20.
dstport 4789The UDP port VXLAN traffic uses — 4789 is the IANA-assigned standard, though older implementations sometimes defaulted differently, which is itself a common real-world mismatch source.

7Verify Baseline

bash — test both tunnels
1sudo ip netns exec ns-dc1 ping -c 2 10.99.1.2   # over the GRE tunnel
    2 received, 0% packet loss
2sudo ip netns exec ns-dc1 ping -c 2 10.99.2.2   # over the VXLAN overlay
    2 received, 0% packet loss
3sudo ip netns exec ns-underlay tcpdump -i u-dc1-in -nn -c 2 'udp port 4789'   # see the VXLAN encapsulation directly on the underlay
    ...203.0.113.1.xxxx > 203.0.114.1.4789: VXLAN, flags [I] vni 100 ... (inner Ethernet frame follows)
🟢 Baseline confirmed

Both a GRE tunnel and a VXLAN overlay are working across the same simulated WAN, and the capture proves VXLAN's encapsulation is visible directly on the underlay as ordinary UDP traffic to port 4789.

8Break-Fix #1 — Underlay Route Missing (Tunnel Endpoint Unreachable)

🔴 Break It

Remove DC-1's route to DC-2's underlay subnet — simulating a WAN routing change that broke basic connectivity between the two sites, without anyone touching the tunnel configuration at all.

bash — on ns-dc1
1sudo ip netns exec ns-dc1 ip route del 203.0.114.0/24 via 203.0.113.254

Observe

bash — on ns-dc1
1sudo ip netns exec ns-dc1 ping -c 2 10.99.1.2   # try the tunnel's inner address
    100% packet loss
2sudo ip netns exec ns-dc1 ping -c 2 203.0.114.1   # now test the UNDERLAY address directly, bypassing the tunnel entirely
    Network is unreachable   (this is the real problem — has nothing to do with the tunnel itself)
🔵 Reading the symptom

The tunnel's own configuration is completely untouched and correct — but it doesn't matter, because the underlay can't even route a plain packet to the remote endpoint's real address. Testing the underlay address directly instantly isolates this from a tunnel-configuration problem — exactly the discipline described in Section 4's method. Someone troubleshooting only at the tunnel/overlay level here would waste significant time re-checking GRE settings that were never the issue.

🔴 Root Cause

The underlay route to the remote tunnel endpoint's real IP address was missing, so the tunnel could never actually deliver its encapsulated packets, regardless of how correctly it was configured.

bash — fix
1sudo ip netns exec ns-dc1 ip route add 203.0.114.0/24 via 203.0.113.254
🟦 Production Best Practice

Always test plain underlay connectivity to the remote tunnel endpoint's real IP FIRST, before investigating any tunnel-specific configuration — this single check instantly separates "the tunnel is broken" from "the network beneath the tunnel is broken."

9Break-Fix #2 — MTU Overhead Not Accounted For

🔴 Break It

Reproduce Project 14's MTU black hole lesson, but this time the "reduction" comes from the tunnel's own encapsulation overhead rather than an external network segment.

bash — on ns-underlay, block ICMP fragmentation-needed messages, exactly like Project 14
1sudo ip netns exec ns-underlay iptables -A FORWARD -p icmp --icmp-type fragmentation-needed -j DROP

Observe

bash — on ns-dc1, check the tunnel interface's own MTU, then test a large payload
1sudo ip netns exec ns-dc1 ip link show vxlan100   # check the VXLAN interface's own MTU
    vxlan100: mtu 1450   (automatically smaller than the underlay's 1500 — accounting for VXLAN's own encapsulation overhead)
2sudo ip netns exec ns-dc1 ping -M do -s 1472 -c 2 10.99.2.2   # try to send a full-sized, DF-set payload over the VXLAN overlay anyway
    ping: local error: Message too long, mtu=1450   (caught immediately, locally — this is actually the GOOD outcome)
🔵 Reading the symptom

Notice the kernel already automatically accounted for VXLAN's encapsulation overhead by giving the vxlan100 interface a smaller MTU (1450) than the underlay's 1500 — this self-awareness is one of VXLAN's conveniences. The failure we forced here (blocking ICMP) is the SAME black-hole mechanism from Project 14, but this time affecting traffic riding on top of the overlay's own network (for example, if an application inside the overlay itself doesn't respect the tunnel's smaller MTU, or if something along the underlay path has an even smaller MTU than expected). Every tunnel adds overhead, which means the "inner" usable MTU is always smaller than the outer path's — and that math has to be right end-to-end, including any additional segments beyond just the tunnel itself.

🔴 Root Cause

An application or device sending traffic into the tunnel assumed the full underlay MTU was available, without accounting for the tunnel's own encapsulation overhead reducing the usable inner MTU — compounded by blocked ICMP breaking Path MTU Discovery's ability to self-correct.

bash — fix: restore ICMP (letting PMTUD work), and/or explicitly clamp MSS on tunnel traffic like Project 14
1sudo ip netns exec ns-underlay iptables -D FORWARD -p icmp --icmp-type fragmentation-needed -j DROP
🟦 Production Best Practice

Any tunneling technology adds encapsulation overhead — always know the exact overhead for your chosen tunnel type and confirm the resulting inner MTU is correctly propagated to anything sending traffic through it. This is Project 14's entire lesson, guaranteed to be relevant on literally every tunnel you'll ever configure.

10Break-Fix #3 — VXLAN VNI Mismatch

🔴 Break It

Simulate a provisioning mistake — DC-2's VXLAN interface is accidentally created with the wrong VNI, exactly the same category of mistake as Project 20's VLAN ID mismatch, one layer up.

bash — on ns-dc2, recreate with the wrong VNI
1sudo ip netns exec ns-dc2 ip link set vxlan100 down
2sudo ip netns exec ns-dc2 ip link delete vxlan100
3sudo ip netns exec ns-dc2 ip link add vxlan100 type vxlan id 200 remote 203.0.113.1 local 203.0.114.1 dstport 4789   # typo: VNI 200 instead of 100
4sudo ip netns exec ns-dc2 ip addr add 10.99.2.2/24 dev vxlan100
5sudo ip netns exec ns-dc2 ip link set vxlan100 up

Observe

bash
1sudo ip netns exec ns-dc1 ping -c 2 10.99.2.2
    100% packet loss
2sudo ip netns exec ns-underlay tcpdump -i u-dc1-in -nn -c 2 'udp port 4789'   # confirm the encapsulated traffic is still leaving DC-1 correctly
    ...VXLAN, flags [I] vni 100...   (DC-1 is sending correctly, tagged with VNI 100)
3sudo ip netns exec ns-dc2 ip -d link show vxlan100   # check DC-2's actual configured VNI
    vxlan id 200 ...   (there's the mismatch)
🔵 Reading the symptom

The underlay delivers DC-1's VXLAN-encapsulated packets to DC-2 perfectly fine — the outer UDP packet reaches the right host on the right port. But DC-2's kernel, seeing a VNI of 100 in the VXLAN header while its own vxlan100 interface is configured for VNI 200, doesn't recognize this traffic as belonging to any overlay network it's part of, and discards it. This is architecturally identical to Project 20's VLAN ID mismatch — same "arrives at the right physical destination but gets discarded by tag/ID filtering" pattern, just one encapsulation layer further from the original Ethernet frame.

🔴 Root Cause

The two VXLAN endpoints were configured with different VNIs for what was supposed to be the same overlay network, so encapsulated traffic correctly reached the remote host but was discarded there as belonging to a different, unrecognized overlay.

bash — fix
1sudo ip netns exec ns-dc2 ip link delete vxlan100
2sudo ip netns exec ns-dc2 ip link add vxlan100 type vxlan id 100 remote 203.0.113.1 local 203.0.114.1 dstport 4789
3sudo ip netns exec ns-dc2 ip addr add 10.99.2.2/24 dev vxlan100
4sudo ip netns exec ns-dc2 ip link set vxlan100 up
🟦 Production Best Practice

Treat VNI assignment with the same rigor as VLAN ID assignment — a documented, centrally tracked mapping prevents this class of mismatch, especially as the number of overlay networks grows across a multi-site or multi-cluster deployment.

11Production Best Practices

🟦 Verify the underlay before the tunnel

Test plain connectivity to the remote endpoint's real IP first — tunnels can't work if the network beneath them doesn't.

🟦 Always account for encapsulation MTU overhead

Every tunnel type reduces the usable inner MTU — know the exact overhead and confirm it propagates correctly.

🟦 Treat VNIs like VLAN IDs

Mismatched VNIs produce silent, tag-filtered discards — document and centrally track VNI assignments.

🟦 Capture on the underlay to see the real encapsulation

Confirms both that packets are actually leaving correctly tagged/encapsulated, and that they're reaching the right destination at all.

13Interview Preparation

ScenarioA GRE or VXLAN tunnel between two sites isn't passing any traffic. Where do you start?

Before looking at the tunnel configuration at all, I'd confirm the underlay can route to the remote endpoint's real IP address directly — a plain ping to that address, bypassing the tunnel entirely. Tunnels are built on top of ordinary IP connectivity, so if that basic connectivity is broken, no tunnel configuration can fix it. Only once that's confirmed working would I move on to checking the tunnel's own settings.

Interviewer follow-up: "The underlay works fine, but the tunnel still doesn't pass traffic — what next?" — Answer: I'd check that both ends agree on the tunnel's identifying configuration — matching remote/local addresses for GRE, or a matching VNI for VXLAN — since a mismatch there causes traffic to arrive at the right host but get silently discarded as unrecognized.
ConceptWhat's the difference between GRE and VXLAN?

GRE is a simple point-to-point tunnel that encapsulates IP packets inside other IP packets, connecting exactly two endpoints. VXLAN encapsulates entire Ethernet frames inside UDP packets, letting you extend a genuine Layer 2 broadcast domain across a routed network, and uses a VNI to support many isolated overlay networks sharing the same underlay — closer in spirit to extending VLANs across an IP network than to a simple point-to-point link.

TroubleshootingWhy does MTU always need special attention when working with tunnels?

Because encapsulation adds overhead — the outer packet's headers take up space that reduces how much of the original payload can fit within the underlay's MTU. This means the tunnel's usable "inner" MTU is always smaller than the underlay's MTU, and if that's not accounted for correctly, you get exactly the MTU black-hole symptoms from earlier in this masterclass — small payloads working fine, large ones silently hanging.
