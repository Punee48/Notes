2Why This Only Happens Under Load

2.1 Connection reuse hides DNS changes from long-lived clients

🔵 Concept

A client that resolves a hostname once and then reuses that TCP connection for many subsequent requests (exactly the connection-pooling behavior we praised as a best practice back in Project 4) never re-resolves DNS for the lifetime of that connection. If the backend behind that hostname changes — a new IP is added, an old one is removed — a client holding an existing connection to the OLD backend keeps working fine, completely oblivious to the DNS change, right up until that specific connection eventually closes.

2.2 New connections, created under load, are the ones that actually re-resolve

🔵 Concept

Under normal, steady traffic, a connection pool's existing connections handle almost all requests — new DNS resolutions are rare. Under a SUDDEN traffic spike, the pool needs many new connections quickly, and every one of those brand-new connections performs a fresh DNS lookup. If the DNS answer at that exact moment is stale or pointing at a backend that's mid-rotation, a disproportionate number of failures cluster exactly during the spike — while the pre-existing, already-connected traffic keeps working perfectly, making the problem look inconsistent and impossible to reproduce with a single manual test.

2.3 TTL is a promise the resolver doesn't always keep precisely

🔵 Concept

A DNS record's TTL (Time To Live) tells resolvers how long they may cache an answer. In a real production DNS chain, there are usually MULTIPLE caching layers — the application's own resolver cache, an OS-level resolver like systemd-resolved, and often an internal caching DNS server in front of the authoritative source — and each layer's cache can independently hold a stale answer slightly past when it should have expired, especially under load when cache-refresh background work competes with everything else for CPU time.

2.4 Why manual checks always look "fine"

🔵 Concept

A single manual getent hosts check, run calmly after the incident, triggers exactly ONE fresh resolution — which will almost always return the current, correct answer, because the transient staleness has already passed by the time anyone checks. This is precisely why this class of incident is so notoriously hard to catch after the fact: the very act of checking calmly, well after the spike, erases the evidence.

4Compound-Incident Investigation Method

  • 1. Note precisely WHEN the failures cluster — if it's tied to load/traffic spikes rather than a constant rate, suspect something that only triggers under new-connection volume
    • ↓
  • 2. Distinguish failures on NEW connections from failures on EXISTING/reused ones — this single split often reveals the whole mechanism
    • ↓
  • 3. Capture DNS resolution AT THE MOMENT of the spike, not calmly afterward — a post-incident manual check will almost always look clean
    • ↓
  • 4. Check every layer of the resolution chain independently — application cache, OS resolver, internal DNS server — for cache TTL handling under load
    • ↓
  • Resist declaring victory at the first plausible single-cause explanation — confirm the full mechanism end-to-end before closing the ticket
🟠 Warning

An incident that "goes away when you restart something" is not necessarily fixed — a restart can coincidentally clear a stale cache or force new connections, masking the underlying mechanism without addressing it. This exact pattern (fixed by restart, twice) is what let this incident survive two previous investigations.

7Break-Fix #1 — Backend Rotates, Long-Lived Connections Keep Working

🟠 Scenario

Open a long-lived connection to the current (old) gateway BEFORE the DNS rotation happens — simulating a connection from the pool that was established before the deployment.

bash — on ns-checkout, open and hold a connection to the OLD gateway
1sudo ip netns exec ns-checkout bash -c "exec 3<>/dev/tcp/10.201.1.21/8443; sleep 60" &   # open a raw TCP connection directly to the OLD gateway's IP and hold it open for 60 seconds, simulating a pooled connection

Now the deployment happens — DNS is updated to point at the new gateway.

bash — on ns-dns, update the record
1sudo ip netns exec ns-dns pkill dnsmasq
2sudo ip netns exec ns-dns bash -c "cat > /tmp/dns.conf" <<'EOF'
no-resolv
listen-address=10.201.1.53
address=/payment-gateway.internal/10.201.1.22
EOF
3sudo ip netns exec ns-dns dnsmasq -C /tmp/dns.conf -k &

Observe

🔵 Reading the situation

Our held-open connection from before the switch is still talking to the OLD gateway's IP address directly (10.201.1.21) — it has no reason to re-resolve DNS, because it never disconnects. Meanwhile, a BRAND NEW connection made right now would resolve DNS fresh and correctly reach the new gateway. This is expected, normal behavior — connection reuse is exactly why old and new backends can coexist briefly during a safe rotation. The trouble starts in the next section.

🟦 Note

This isn't a bug by itself — a graceful backend rotation typically expects some overlap where both old and new backends are briefly valid, precisely because long-lived connections won't switch mid-flight. The DANGER is what happens next.

8Break-Fix #2 — New Connections Under Load Hit a Stale DNS Answer

🔴 The Real Problem

Now simulate the flash-sale traffic spike — many brand-new connections, created right around the moment of the DNS change, exactly reproducing the timing of the real incident.

bash — on ns-dns, revert to the OLD answer again, then change it WHILE a burst of new client requests is in flight — reproducing the transient window
1sudo ip netns exec ns-dns pkill dnsmasq
2sudo ip netns exec ns-dns bash -c "cat > /tmp/dns.conf" <<'EOF'
no-resolv
listen-address=10.201.1.53
address=/payment-gateway.internal/10.201.1.21
EOF
3sudo ip netns exec ns-dns dnsmasq -C /tmp/dns.conf -k &
4sudo ip netns exec ns-gateway-old pkill -f "http.server 8443"   # the OLD gateway is being decommissioned as part of this rotation — it's going away for real
5for i in $(seq 1 20); do sudo ip netns exec ns-checkout curl -s --max-time 2 -o /dev/null -w "%{http_code}\n" http://payment-gateway.internal:8443/i.html & done; wait   # simulate a burst of 20 near-simultaneous NEW checkout requests, exactly like a flash-sale spike
    (a meaningful fraction show "000" or connection failures — every one of them was resolved to the now-dead OLD gateway)

Observe — confirm calmly, afterward, and see it "disappear"

bash — on ns-checkout, a calm check moments later
1sleep 3 && sudo ip netns exec ns-checkout getent hosts payment-gateway.internal   # the exact "let me just double check DNS" move from Day 1 of the incident
    10.201.1.21  payment-gateway.internal   (STILL shows the dead old gateway — but by now it might be a moment before or after this actually flips)
🔵 Reading the symptom — the whole mechanism in one place

The failures clustered exactly during the burst of NEW connections, right at the moment the old gateway was being decommissioned — the exact window this incident always occurs in. A calm check moments later can go either way depending on exact timing relative to the DNS record's actual TTL expiry, which is precisely why manual post-incident checks have twice come back "looking fine." The mechanism: DNS said "old gateway" right up until (or slightly past) the moment it stopped existing, and every brand-new connection made during that exact window inherited a now-dead destination — while any connections that happened to already be established kept working the whole time, invisible to this failure entirely.

🔴 Root Cause

A backend rotation removed the old gateway before every DNS-caching layer had definitively expired its cached answer for it, and a traffic spike at exactly that moment created a large number of brand-new connections that resolved to the now-decommissioned backend.

🟦 The real fix — sequencing, not a single setting

The durable fix is procedural: update DNS, wait for a period comfortably longer than the record's TTL (and any known caching-layer slack) across the ENTIRE resolution chain, THEN decommission the old backend — never simultaneously or in the wrong order. This is a deployment sequencing discipline, not a single sysctl or config value.

9Break-Fix #3 — The Resolver's Own Cache Outlives the TTL

🟠 Compounding Factor

Even with correct sequencing, one more layer can independently extend the staleness window: the resolver itself holding an answer slightly past its stated TTL, especially under load. Let's demonstrate the concept directly.

bash — on ns-dns, configure a short but real TTL, and observe cache behavior
1sudo ip netns exec ns-dns pkill dnsmasq
2sudo ip netns exec ns-dns bash -c "cat > /tmp/dns.conf" <<'EOF'
no-resolv
listen-address=10.201.1.53
address=/payment-gateway.internal/10.201.1.22
local-ttl=5
EOF
3sudo ip netns exec ns-dns dnsmasq -C /tmp/dns.conf -k &   # local-ttl=5 means this resolver tells clients "you may cache this for 5 seconds"
4sudo ip netns exec ns-checkout getent hosts payment-gateway.internal   # resolve once, starting the 5-second clock
    10.201.1.22  payment-gateway.internal
5sudo ip netns exec ns-dns pkill dnsmasq   # simulate the resolver itself becoming briefly unavailable/overloaded right as the record should expire
6sleep 6 && sudo ip netns exec ns-checkout getent hosts payment-gateway.internal   # wait past the stated TTL, then check again
    (fails or times out entirely, since the resolver isn't even running anymore in this simulation — in a real environment, an overloaded resolver might instead momentarily keep serving a cached answer past its TTL rather than failing outright)
🔵 Reading the concept

TTL is advisory guidance to caching layers, not a hard real-time guarantee enforced by the universe — a resolver under heavy load, mid-restart, or with its own internal caching quirks can serve an answer slightly past its nominal expiry. In a real multi-layer resolution chain (application cache → OS resolver → internal caching DNS server → authoritative), each hop is an independent opportunity for this kind of small timing slip, and they can stack. This is why the sequencing fix in Break-Fix #2 explicitly builds in extra margin beyond the raw TTL value — the TTL is the minimum guarantee, not the maximum possible staleness window in practice.

🟦 Production Best Practice

When sequencing a backend rotation, budget meaningfully more time than the raw DNS TTL before decommissioning the old backend — account for the realistic behavior of every caching layer in the actual resolution chain, not just the textbook TTL value from the DNS record itself.

10Production Best Practices

🟦 Split failures by connection age

New vs. reused connections often reveals a DNS/connection-pooling interaction that a single aggregate failure rate hides.

🟦 Capture evidence during the incident, not after

A calm post-incident DNS check will very often look completely clean — that's not proof nothing was wrong.

🟦 Sequence backend rotations with real margin past TTL

Never decommission an old backend at the same time as (or before) the DNS change fully propagates through every caching layer.

🟦 "Fixed by restart" isn't the same as root-caused

A restart can coincidentally clear caches or force reconnection — treat it as a clue, not a resolution.

12Interview Preparation

ScenarioA production issue only happens during traffic spikes and never reproduces when you test manually afterward. How do you approach it?

I'd treat the load-dependence itself as the key clue rather than an obstacle — something that only breaks under new-connection volume, not steady-state traffic. I'd try to capture evidence DURING the next occurrence rather than relying on calm post-incident checks, which very often look clean because the transient condition has already passed. I'd also specifically split failures by whether they occurred on brand-new connections versus long-lived reused ones, since that split often reveals a DNS-and-connection-pooling interaction.

Interviewer follow-up: "The team already 'fixed' this twice by restarting something — why isn't that enough?" — Answer: a restart can coincidentally clear a stale cache or force reconnections without addressing why the staleness occurred in the first place — it's a mitigation that looks like a fix until the same underlying timing condition happens again.
ConceptWhy can a backend rotation cause failures even when DNS was updated correctly?

Because DNS TTL is advisory guidance for caching layers, not an instantaneous, globally-enforced cutover — every layer in the resolution chain (application cache, OS resolver, internal DNS server) can independently hold a cached answer slightly past its nominal expiry, especially under load. If the old backend is decommissioned before every caching layer has genuinely expired its old answer, any new connection resolved during that window will be sent to a backend that no longer exists.

TroubleshootingWhy would connection pooling make this kind of DNS issue harder to detect?

Because connections that were already established before the DNS change keep working fine — they never re-resolve DNS for their lifetime. Only new connections are exposed to a stale answer, so the overall failure rate can look small and inconsistent, and testing with a single new connection well after the transient window has passed will show nothing wrong at all.
