1The Incident

We're supporting a telecom company's billing platform, which integrates with a partner's usage-rating API. A large nightly batch job that used to finish in 40 minutes now regularly takes 3+ hours, and nobody can point to a specific error — just "it's slow."

"We pulled a packet capture during last night's run — it's about 90MB and has tens of thousands of packets. We don't even know what we're looking for. Can Linux infra take a pass at it?"

This is a completely different kind of challenge from our previous projects — we already have the evidence, but it's too large to read line by line the way we did with tcpdump's raw text output in Project 5. This is exactly the situation Wireshark's visual tools were built for.

🔵 Why this project matters

Reading raw tcpdump output works great for a handful of packets. It falls apart at scale. Wireshark takes the exact same packet data and gives you filtering, coloring, statistics, and stream-reconstruction tools that turn "somewhere in these 50,000 packets" into "here are the exact 12 packets that explain the whole incident." Every senior Linux/DevOps engineer eventually needs this skill for capture files too large or too complex to read as plain text.

2Why Wireshark, Not Just tcpdump

🔵 Concept

Wireshark and tcpdump both use the same underlying capture library (libpcap) and can read each other's files. The difference is entirely in analysis: Wireshark adds a GUI with color-coded rows, a "Follow TCP Stream" feature that reconstructs an entire conversation into readable order, an "Expert Info" panel that automatically flags retransmissions/resets/zero-windows for you, and a powerful display-filter language that's separate from (and more expressive than) tcpdump's capture-time BPF filters.

🔵 Concept — Wireshark's built-in TCP analysis

Wireshark doesn't just show you raw packets — it tracks the state of every TCP stream as it reads a capture and automatically annotates suspicious patterns for you: [TCP Retransmission], [TCP Dup ACK], [TCP ZeroWindow], [TCP Out-Of-Order]. This turns manual pattern-spotting (like we did by eye in Project 5) into something you can filter for directly by name.

4Capture Filters vs Display Filters — Do Not Confuse These

🟠 Warning — the #1 beginner mistake in Wireshark

Capture filters (using BPF syntax, same as tcpdump — host 10.10.9.50 and port 8443) decide what gets captured in the first place, applied BEFORE packets are saved. Display filters (Wireshark's own, different syntax — tcp.analysis.retransmission) decide what's shown to you from an ALREADY-captured file, and can be changed as many times as you like without recapturing anything. They look similar but use completely different syntax — putting a display filter into the capture filter box (or vice versa) simply won't work.

Display FilterWhat It Shows
tcp.analysis.retransmissionEvery packet Wireshark identified as a retransmitted segment — the visual equivalent of spotting duplicate sequence numbers by eye.
tcp.analysis.duplicate_ackPackets where the receiver re-acknowledged the same byte position it already acknowledged — usually a sign the receiver is telling the sender "I'm still missing something," often preceding a retransmission.
tcp.analysis.zero_windowPackets where a host advertised a TCP window size of 0 — telling the sender "stop sending, my receive buffer is full" — a strong signal of a slow reader on the receiving side.
tcp.flags.reset == 1Every packet with the RST flag set — instantly find every reset in a huge capture.
dnsShow only DNS query/response packets.
httpShow only HTTP request/response packets.
tls.handshake.type == 1Show only TLS Client Hello packets — the very first step of a TLS handshake, useful for confirming a TLS negotiation even started.
ip.addr == 10.10.9.50 && tcp.port == 8443Combine host and port filters using Wireshark's own AND syntax (&&, different from tcpdump's "and").

5Analysis Workflow for a Large Capture

  • 1. Open the file. Go to Statistics → Conversations to see which host pairs carried the most traffic/time — narrow down to the relevant flow
    • ↓
  • 2. Go to Statistics → Expert Information — Wireshark's automatic summary of every warning/error it detected (retransmissions, resets, zero windows) with counts
    • ↓
  • 3. Apply a display filter matching the most common warning type from Expert Info to jump straight to the interesting packets
    • ↓
  • 4. Right-click a packet in that stream → Follow → TCP Stream, to see the whole conversation in order, reconstructed and readable
    • ↓
  • Correlate what you found back to application-level timing (when did the batch job slow down?) to confirm cause and effect
🟦 Production Best Practice

Never scroll through a large capture packet-by-packet looking for problems. Always start with Statistics → Expert Information — it does the pattern-spotting for you and tells you exactly how many of each issue type exist, which is the fastest way to know whether you're looking at one weird packet or a systemic issue affecting thousands.

9Break-Fix #2 — Duplicate ACKs

🔴 Break It

Use netem's duplicate option to simulate a network segment that occasionally delivers the same packet twice — common on certain WAN links and misconfigured redundant paths.

bash
1sudo ip netns exec ns-billing-client tc qdisc add dev veth-bc root netem duplicate 25%
2sudo ip netns exec ns-rating-api tshark -i veth-ra -f "tcp port 8443" -w /tmp/03-dupack.pcap -c 60 &
3sudo ip netns exec ns-billing-client curl -s -o /dev/null http://10.50.1.20:8443/

Open /tmp/03-dupack.pcap in Wireshark and filter:

Wireshark display filter
tcp.analysis.duplicate_ack
Packet List Pane — simulated view
No.TimeSourceDestinationProtoInfo
90.05010.50.1.2010.50.1.10TCP[TCP Dup ACK 8#1] 8443 → 51301 [ACK]
100.05110.50.1.2010.50.1.10TCP[TCP Dup ACK 8#2] 8443 → 51301 [ACK]
🔵 Reading the symptom

The label [TCP Dup ACK 8#1] tells you exactly which original packet (frame 8, in this example) this is a duplicate acknowledgment of, and Wireshark numbers repeated dup-ACKs for the same segment (#1, #2, #3...). A small number of duplicate ACKs is often harmless — but three duplicate ACKs for the same segment is the classic trigger for TCP's "fast retransmit" mechanism, where the sender resends data without even waiting for a timeout, because three dup-ACKs is treated as strong evidence of loss.

bash — cleanup
1sudo ip netns exec ns-billing-client tc qdisc del dev veth-bc root netem

10Break-Fix #3 — Zero Window (The Real Culprit Behind the Batch Job)

🔴 Break It

Simulate a slow-reading receiver — an application that accepts data slower than the network can deliver it, forcing its TCP receive buffer to fill up. We'll use a Python client that reads in tiny, deliberately delayed chunks.

bash — on ns-billing-client, create a deliberately slow reader
1sudo ip netns exec ns-billing-client bash -c "cat > /tmp/slow_reader.py" <<'EOF'
import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 1024)  # tiny receive buffer
s.connect(('10.50.1.20', 8443))
s.send(b"GET / HTTP/1.0\r\nHost: rating-api\r\n\r\n")
while True:
    data = s.recv(64)   # read very small chunks
    if not data:
        break
    time.sleep(0.5)      # simulate a slow application not draining the buffer
EOF
2sudo ip netns exec ns-rating-api tshark -i veth-ra -f "tcp port 8443" -w /tmp/04-zerowindow.pcap -c 80 &
3sudo ip netns exec ns-billing-client python3 /tmp/slow_reader.py
TokenMeaning
SO_RCVBUF, 1024Shrinks the kernel's receive buffer for this socket down to 1KB — a small buffer fills up much faster, making a zero-window condition easy to reproduce on demand in a lab.
time.sleep(0.5)Simulates a slow application — one that isn't calling recv() fast enough to drain the buffer, exactly like a batch job doing heavy processing on each chunk before asking for more data.

Open /tmp/04-zerowindow.pcap in Wireshark and filter:

Wireshark display filter
tcp.analysis.zero_window
Packet List Pane — simulated view
No.TimeSourceDestinationProtoInfo
220.51210.50.1.1010.50.1.20TCP[TCP ZeroWindow] 51402 → 8443 [ACK] Win=0
341.03010.50.1.2010.50.1.10TCP[TCP ZeroWindowProbe] 8443 → 51402 [ACK]
🔵 Reading the symptom — the real root cause

Win=0 is the client explicitly telling the server "stop sending, my buffer is full." The server then periodically sends small "ZeroWindowProbe" packets asking "any room yet?" — and transfer basically stalls until the client's application catches up and drains its buffer. THIS is what a slow-consuming application looks like on the wire, and it's a very different root cause from packet loss or a firewall issue — the network is delivering data perfectly fine; the receiving application simply can't keep up. For a nightly batch job that got slower over time, this pattern — check whether the client-side application logic (not the network) is the actual bottleneck — is exactly where a senior engineer's instincts should go next.

🟦 Fix — this is an application/tuning fix, not a network fix

The real-world fix is either speeding up the application's own processing of received data (so it drains its buffer faster) or increasing the socket's receive buffer size (a mitigation, not a cure, if the application itself is genuinely too slow) — never a routing, firewall, or DNS change.

🔵 Reading the symptom

In the Packet List, RST packets are typically shown in a distinct dark/black color by Wireshark's default coloring rules, making them easy to spot visually even without filtering. Right-click the RST packet → Follow → TCP Stream to see the entire short-lived conversation in one readable window — you'll see the SYN, the SYN-ACK never arriving (or arriving then immediately reset, depending on where the REJECT is applied), confirming exactly where the conversation broke down.

12Production Best Practices

🟦 Start with Expert Information

Never manually scroll a large capture — let Wireshark's automatic analysis point you at the interesting packets first.

🟦 Know your filter language

Capture filters (BPF, same as tcpdump) and display filters (Wireshark's own syntax) are not interchangeable — mixing them up is the most common beginner mistake.

🟦 Zero window ≠ network problem

A zero-window condition means the receiving application is the bottleneck, not the network — don't waste time chasing routing or firewall causes for this pattern.

🟦 Follow TCP Stream for context

Individual packets rarely tell the full story — reconstructing the whole conversation in order is often what actually explains an incident.

🟦 tshark for headless capture, Wireshark for analysis

Servers rarely have a GUI — capture with tshark over SSH, then transfer the .pcap to your workstation for the visual deep-dive.

14Interview Preparation

ScenarioYou're handed a large packet capture with no context and told "figure out why this was slow." Where do you start?

I wouldn't scroll through it manually — I'd open Statistics → Conversations first to identify the relevant host pair and time range, then go straight to Statistics → Expert Information, which automatically summarizes every retransmission, duplicate ACK, reset, and zero-window event Wireshark detected. Whichever pattern dominates tells me where to focus — for example, a huge count of zero-window events points to a slow-consuming application rather than a network problem, while lots of retransmissions points to packet loss.

Interviewer follow-up: "What's the difference between a retransmission and a zero-window issue, in terms of root cause?" — Answer: retransmissions mean data is being lost in transit and needs to be resent — a network-path problem. A zero window means the data IS arriving fine, but the receiving application isn't reading it fast enough, so its buffer fills up and it tells the sender to pause — that's an application or receiver-side performance problem, not a network problem.
ConceptWhat's the difference between a Wireshark capture filter and a display filter?

A capture filter uses BPF syntax, the same as tcpdump, and determines what gets captured in the first place — it's applied before any data is saved. A display filter uses Wireshark's own separate syntax and is applied afterward, to an already-captured file, purely to control what's shown on screen — you can change it as many times as you want without recapturing anything.

TroubleshootingWhat does a TCP zero-window condition tell you, and what would you check next?

It tells me the receiving side's TCP buffer is full because the application isn't draining it fast enough — the network delivered the data successfully. I'd check what the receiving application is doing with each chunk of data — heavy processing per request, blocking I/O, or an undersized read loop are common causes — rather than looking at routing, DNS, or firewall configuration.

ProductionWhy capture with tshark instead of the Wireshark GUI on a production server?

Production servers rarely have a graphical environment, and even if they did, running a full GUI application isn't appropriate on a production host. tshark shares the exact same capture and protocol-analysis engine as Wireshark but runs entirely from the command line, so I can capture remotely over SSH and then transfer the resulting .pcap file to my workstation for visual analysis.
