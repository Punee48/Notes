1The Task

We're building local development infrastructure for a platform team ahead of a bigger container rollout. The requirement: several service namespaces on one physical Linux host need to talk to each other as if they were plugged into the same physical switch — same subnet, no routing, just plain Layer 2 connectivity, with the option to add more "hosts" later without redesigning anything.

"We don't want a router between these services yet — just a flat, simple network, like they're all plugged into the same switch in the same rack. And we want to understand what's actually happening under the hood before we let Docker manage it for us automatically."

Every namespace, veth pair, and route we've built so far in this masterclass has been about connecting SEPARATE Layer 3 networks. A bridge is different — it doesn't route between networks, it MERGES multiple interfaces into a single, shared Layer 2 broadcast domain, exactly like a physical Ethernet switch. Understanding this distinction is the whole point of this project.

🔵 Why this project matters

Every default Docker network, every KVM/libvirt virtual machine's network, and a huge amount of Kubernetes CNI plumbing all rely on Linux bridges under the hood. If you understand exactly how a Linux bridge learns MAC addresses and forwards frames, container and VM networking in the next several projects stops looking like magic and starts looking like "oh, it's just a bridge with extra automation."

2Bridge Foundation — Layer 2, Not Layer 3

2.1 A bridge is a software switch, not a router

🔵 Concept

Every routing concept in this masterclass so far — routing tables, ip route get, gateways — operates at Layer 3, forwarding based on IP addresses, between DIFFERENT networks. A Linux bridge (brctl/ip link ... type bridge) operates at Layer 2, forwarding based on MAC addresses, WITHIN the same network. Interfaces attached to a bridge don't each need their own IP — the bridge itself can optionally hold one IP for the whole segment, while the attached ports simply forward Ethernet frames to each other, exactly like ports on a physical switch.

2.2 One shared broadcast domain

🔵 Concept

Every interface attached to the same bridge shares ONE broadcast domain — a broadcast frame (like an ARP request) sent by one attached namespace is flooded out every other port on the bridge, exactly like a physical switch would. This is fundamentally different from our earlier namespace labs, where each veth pair connected exactly two points and any additional connectivity required explicit routing.

2.3 The forwarding database (fdb) — the bridge's "memory"

🔵 Concept

A bridge builds and maintains a forwarding database mapping MAC addresses to the specific port they were last seen on. The first time a new MAC is seen (usually via a broadcast, like an ARP request), the bridge doesn't know which port it belongs to yet, so it floods the frame everywhere. Once it learns that MAC's specific port from a subsequent frame, it can forward directly to just that one port instead of flooding — this is "MAC learning," and it's the core mechanism that makes a switch smarter than a hub.

5Troubleshooting Method for Bridge Incidents

  • 1. Is the bridge interface itself administratively up? (ip link show br0)
    • ↓
  • 2. Is the specific veth actually attached (a "port"/"slave") to the bridge? (ip link show master br0)
    • ↓
  • 3. Is that veth's own link state up?
    • ↓
  • 4. Has the bridge learned the expected MAC on the expected port? (bridge fdb show)
    • ↓
  • 5. Is Spanning Tree Protocol putting a port into a blocking state? (bridge -d link show — check "state")
    • ↓
  • Only after confirming L2 connectivity, revisit IP-layer concerns (duplicate IPs, ARP conflicts)
🟠 Warning

An interface can be "up" in the sense of link state (cable/veth connected) while still not being an attached PORT of the bridge — these are two separate facts, and confusing them is the single most common bridge misconfiguration.

6Build the Bridge

bash — run as root/sudo, in the root namespace (bridges are typically built in the host's default namespace, or a dedicated one)
1sudo ip netns add ns-br-host
2sudo ip netns exec ns-br-host ip link add br0 type bridge
3sudo ip netns exec ns-br-host ip link set br0 up
4sudo ip netns add ns-svc-a
5sudo ip netns add ns-svc-b
6sudo ip netns add ns-svc-c
7sudo ip link add veth-a type veth peer name veth-a-br
8sudo ip link add veth-b type veth peer name veth-b-br
9sudo ip link add veth-c type veth peer name veth-c-br
10sudo ip link set veth-a netns ns-svc-a
11sudo ip link set veth-b netns ns-svc-b
12sudo ip link set veth-c netns ns-svc-c
13sudo ip link set veth-a-br netns ns-br-host
14sudo ip link set veth-b-br netns ns-br-host
15sudo ip link set veth-c-br netns ns-br-host
16# THE KEY STEP: attach each host-side veth end to the bridge as a port
17sudo ip netns exec ns-br-host ip link set veth-a-br master br0
18sudo ip netns exec ns-br-host ip link set veth-b-br master br0
19sudo ip netns exec ns-br-host ip link set veth-c-br master br0
20sudo ip netns exec ns-br-host bash -c "ip link set veth-a-br up; ip link set veth-b-br up; ip link set veth-c-br up"
21sudo ip netns exec ns-svc-a bash -c "ip addr add 10.80.1.11/24 dev veth-a; ip link set veth-a up; ip link set lo up"
22sudo ip netns exec ns-svc-b bash -c "ip addr add 10.80.1.12/24 dev veth-b; ip link set veth-b up; ip link set lo up"
23sudo ip netns exec ns-svc-c bash -c "ip addr add 10.80.1.13/24 dev veth-c; ip link set veth-c up; ip link set lo up"
TokenMeaning
ip link add br0 type bridgeCreates the bridge device itself — this is the virtual switch. It exists as its own network interface, separate from any of the veth ports attached to it.
ip link set veth-a-br master br0The crucial step — attaches this interface as a PORT ("slave") of br0. Without this, the interface can be perfectly up and configured, but frames will never flow through the bridge to or from it.
10.80.1.11/24 ... 10.80.1.13/24All three namespaces share the SAME subnet — this is what makes it Layer 2 connectivity rather than routed Layer 3, matching our requirement of "same switch, same subnet."

7Verify the Baseline

bash — on ns-svc-a
1sudo ip netns exec ns-svc-a ping -c 2 10.80.1.12
    2 received, 0% packet loss
bash — on ns-br-host, inspect the forwarding database after that ping
1sudo ip netns exec ns-br-host bridge fdb show br br0
    aa:bb:cc:...  dev veth-a-br master br0
    dd:ee:ff:...  dev veth-b-br master br0
🟢 Validation

Both namespaces' MAC addresses are now learned against their correct ports — direct proof that MAC learning worked exactly as described in Section 4. This is our working baseline.

8Break-Fix #1 — Veth Never Attached to the Bridge

🔴 Break It

Detach ns-svc-c's port from the bridge, simulating a step accidentally skipped during provisioning — the interface itself is still up, addressed, and looks fine at a glance.

bash — on ns-br-host
1sudo ip netns exec ns-br-host ip link set veth-c-br nomaster

Observe

bash — on ns-svc-a
1sudo ip netns exec ns-svc-a ping -c 2 10.80.1.13
    2 packets transmitted, 0 received, 100% packet loss
bash — on ns-br-host, the key diagnostic
1sudo ip netns exec ns-br-host ip link show veth-c-br
    5: veth-c-br@if4: <BROADCAST,MULTICAST,UP,LOWER_UP> ... state UP
    (notice: no "master br0" shown — it's UP but not attached to anything)
2sudo ip netns exec ns-br-host bridge link show
    (veth-c-br is absent from this list entirely — bridge link show only lists actual bridge ports)
🔵 Reading the symptom

This is the trap Section 5's warning called out directly: ip link show reports veth-c-br as UP with LOWER_UP — everything about the individual interface LOOKS healthy. The only way to see the actual problem is to check bridge membership specifically, either by the absence of "master br0" in the link details or by checking bridge link show, which only lists interfaces that are genuinely attached bridge ports. An interface being "up" and an interface being "a member of this bridge" are two completely separate facts.

🔴 Root Cause

The veth interface was administratively up and correctly addressed inside its namespace, but was never (or no longer) attached as a port of the bridge, so no frames could flow through it via br0.

bash — fix
1sudo ip netns exec ns-br-host ip link set veth-c-br master br0
🟢 Validate

Re-run bridge link show — veth-c-br should reappear, and the ping test should succeed.

9Break-Fix #2 — The Bridge Interface Itself Is Down

🔴 Break It

Bring the bridge device itself down — every port can be individually up and correctly attached, but if br0 itself isn't up, nothing flows through it at all.

bash — on ns-br-host
1sudo ip netns exec ns-br-host ip link set br0 down

Observe

bash — on ns-svc-a
1sudo ip netns exec ns-svc-a ping -c 2 10.80.1.12
    100% packet loss
bash — on ns-br-host
1sudo ip netns exec ns-br-host ip link show br0
    ...<BROADCAST,MULTICAST> mtu 1500 ... state DOWN
🔵 Reading the symptom

ALL traffic across every attached port fails simultaneously, even though each individual veth is correctly attached — that "everything at once" pattern is the signature of the bridge device itself, not any individual port, being the problem. Always check the bridge's own state as a whole before investigating individual ports when the failure is total rather than partial.

🔴 Root Cause

The bridge device itself was administratively down — a parent-level failure that silently disables every attached port's connectivity regardless of each port's own individual state.

bash — fix
1sudo ip netns exec ns-br-host ip link set br0 up

10Break-Fix #3 — Duplicate IP Address (ARP Conflict)

🔴 Break It

Accidentally assign ns-svc-c the same IP as ns-svc-b — a classic manual-provisioning or copy-paste mistake, especially common when cloning VM/container templates without updating the address.

bash — on ns-svc-c
1sudo ip netns exec ns-svc-c ip addr del 10.80.1.13/24 dev veth-c
2sudo ip netns exec ns-svc-c ip addr add 10.80.1.12/24 dev veth-c

Observe

bash — on ns-svc-a, ping the now-duplicated address repeatedly
1sudo ip netns exec ns-svc-a ping -c 6 10.80.1.12
    (inconsistent — some replies succeed, some time out, and replies may show DUP! or alternate between two different MAC addresses)
2sudo ip netns exec ns-svc-a ip neigh show 10.80.1.12
    10.80.1.12 dev veth-a lladdr <MAC> STALE   (the learned MAC may flip-flop between two different values on repeated checks)
🔵 Reading the symptom

Two different hosts answering ARP requests for the same IP causes exactly this kind of unstable, intermittent behavior — whichever host's ARP reply arrives first (or most recently) "wins" the requester's ARP cache entry temporarily, until the other one answers a subsequent request and flips it back. This instability, rather than a clean total failure, is the tell-tale sign of an IP conflict rather than a connectivity problem — connectivity is fine, but two hosts are fighting over the same identity.

🔴 Root Cause

Two namespaces on the same L2 segment were assigned the identical IP address, causing ARP resolution to become unpredictable as both hosts answered for the same address.

bash — fix
1sudo ip netns exec ns-svc-c ip addr del 10.80.1.12/24 dev veth-c
2sudo ip netns exec ns-svc-c ip addr add 10.80.1.13/24 dev veth-c
🟦 Production Best Practice

On any bridge segment (or plain L2 network), watch for intermittent, unstable connectivity to one specific IP as a strong signal of a duplicate address rather than a general network fault — clean total failures and unstable/flapping failures point to very different root causes.

11Break-Fix #4 — STP Blocking a Looped Port

🟠 Scenario

Bridges (like real switches) run Spanning Tree Protocol by default to prevent broadcast storms if a physical or logical loop is accidentally created — for example, connecting two bridges together with two separate links. Let's create exactly that loop and observe STP protecting us from it automatically.

bash — create a second bridge and connect it to br0 with TWO links (a deliberate loop)
1sudo ip netns exec ns-br-host ip link add br1 type bridge
2sudo ip netns exec ns-br-host ip link set br1 up
3sudo ip netns exec ns-br-host ip link add link1a type veth peer name link1b
4sudo ip netns exec ns-br-host ip link add link2a type veth peer name link2b
5sudo ip netns exec ns-br-host bash -c "ip link set link1a master br0; ip link set link1b master br1; ip link set link2a master br0; ip link set link2b master br1"
6sudo ip netns exec ns-br-host bash -c "ip link set link1a up; ip link set link1b up; ip link set link2a up; ip link set link2b up"
7# enable STP on both bridges so they can detect and break the loop
8sudo ip netns exec ns-br-host bash -c "ip link set br0 type bridge stp_state 1; ip link set br1 type bridge stp_state 1"

Observe

bash — on ns-br-host, wait a few seconds for STP to converge, then check port states
1sleep 5 && sudo ip netns exec ns-br-host bridge -d link show
    link1a: master br0 state forwarding ...
    link2a: master br0 state blocking ...   ← STP put this redundant path into blocking
TokenMeaning
bridge -d link showShows detailed per-port bridge state, including STP's port state — forwarding (actively passing traffic) vs blocking (up, attached, but deliberately not forwarding to prevent a loop).
state blockingSTP has determined this link is a redundant path that would create a loop, and is deliberately NOT forwarding frames on it — the port is fully up and attached, but intentionally inactive for traffic purposes.
🔵 Reading the symptom

If a port shows "up" and "attached to the bridge" but traffic still mysteriously doesn't flow through it, and there happens to be more than one physical/logical path between two bridges, STP's blocking state is a very plausible explanation — and critically, THIS IS CORRECT, EXPECTED BEHAVIOR, not a fault to fix. Without STP, this exact topology would cause a broadcast storm — the same frame endlessly circulating and being flooded around the loop, potentially saturating the network. STP is protecting us, not breaking us.

🟦 Production Best Practice

Never manually try to force a blocked STP port into forwarding without understanding why STP blocked it — doing so can immediately trigger a broadcast storm. If redundant paths are genuinely desired, that's a deliberate design decision requiring proper topology planning, not something to fight against port by port.

bash — cleanup: remove the intentional loop from the lab
1sudo ip netns exec ns-br-host ip link del link1a
2sudo ip netns exec ns-br-host ip link del link2a
3sudo ip netns exec ns-br-host ip link del br1

12Production Best Practices

🟦 "Up" ≠ "attached"

An interface's own link state and its bridge membership are separate facts — always verify both independently.

🟦 Check the bridge device's own state first

A total, all-ports-at-once failure points to the bridge itself, not any individual port.

🟦 Unstable ≠ down

Intermittent, flapping connectivity to one specific address is the signature of a duplicate IP/ARP conflict, not a general network fault.

🟦 Respect STP blocking states

A blocked port on a looped topology is protecting the network from a broadcast storm — don't force it active without understanding the topology.

🟦 Use bridge fdb and bridge link, not just ip link

These bridge-specific commands show port membership and learned MAC addresses that plain ip link output won't reveal.

14Interview Preparation

ConceptWhat's the difference between a Linux bridge and routing between two networks?

A bridge operates at Layer 2, forwarding Ethernet frames based on MAC addresses within a single shared broadcast domain — attached interfaces are typically on the same subnet and don't need a routing decision to reach each other. Routing operates at Layer 3, forwarding IP packets between genuinely separate networks based on the routing table, and requires a gateway. A bridge merges networks into one; routing connects separate ones.

TroubleshootingA specific host on a bridge can't be reached, but its interface shows as UP. What would you check?

Being administratively up and being an attached port of the bridge are two separate facts — I'd check whether the interface actually has "master br0" set, or use bridge link show, which only lists genuine bridge ports. It's a very common mistake for an interface to be correctly configured and up on its own, but never actually attached to the bridge.

ConceptHow does a Linux bridge learn where to forward traffic?

It maintains a forwarding database mapping MAC addresses to the port they were last seen on. The first frame from an unknown MAC is flooded to every port since the bridge doesn't know where it lives yet; once that host sends traffic through a specific port, the bridge learns that association and can forward directly to just that port afterward instead of flooding.

ProductionWhy might a bridge port be up, correctly attached, but still not passing traffic?

Spanning Tree Protocol may have placed it in a blocking state because it detected a redundant path that would otherwise create a loop and risk a broadcast storm. That's expected, protective behavior, not a fault — I'd confirm with bridge -d link show and investigate the topology rather than trying to force the port active.
