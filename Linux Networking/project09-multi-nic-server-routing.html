1The Incident

We're supporting a telecom company's core infrastructure bastion host, bastion-core-01, deliberately built with three NICs: one for management (SSH/monitoring), one for production traffic, and one for a disaster-recovery link to a secondary site. Each network has its own gateway and must never mix traffic with the others — compliance and security require strict, guaranteed separation.

"We configured routes for all three networks, but traffic sourced from the DR interface is randomly going out the production interface instead — inconsistent, hard to reproduce, and our DR failover tests keep failing intermittently. Project 2's fix — checking metrics and specific routes — doesn't fully explain it this time."

With three (or more) interfaces and a requirement that traffic STAY on the interface it's associated with, a single shared routing table — no matter how carefully you tune metrics — eventually breaks down. This is exactly the scenario policy routing (ip rule + multiple routing tables) was built to solve properly, rather than as the "advanced preview" we glimpsed in Project 2.

🔵 Why this project matters

Bastion hosts, NAT gateways, and any server with 3+ NICs in an enterprise, telecom, or banking environment need this exact skill — full policy-based routing, not just static routes with careful metrics. It's also the direct conceptual ancestor of VRF (Virtual Routing and Forwarding), which we'll touch on in the Advanced Networking phase later in this masterclass.

2Policy Routing Foundation

2.1 One routing table isn't enough when interfaces must never mix

🔵 Concept

A normal (single, "main") routing table only looks at the destination IP to decide where a packet goes. But our requirement is different: traffic sourced from the DR interface's IP must ALWAYS leave via the DR interface, regardless of destination, and must never accidentally be routed out production just because production's route table entry happened to match more specifically. This requires deciding the outgoing path based on SOURCE, which the main table alone cannot express cleanly for three or more interfaces at once.

2.2 ip rule — the policy database that picks WHICH table to use

🔵 Concept

ip rule manages the kernel's Routing Policy Database (RPDB) — an ordered list of rules, each with a priority (lower number = evaluated first), that decide WHICH routing table to consult for a given packet, based on criteria like source address, incoming interface, or firewall mark. Once a rule matches, the kernel looks up that specific table and stops evaluating further rules — the exact same "first match wins" logic from firewall chains, applied one level up, at the table-selection stage.

2.3 Named custom tables via /etc/iproute2/rt_tables

🔵 Concept

Beyond the built-in tables, you can define your own named tables (like "mgmt-table", "prod-table", "dr-table") in /etc/iproute2/rt_tables, each holding its OWN independent default route and any other routes specific to that interface's network. This is what lets each interface have a genuinely separate view of "how do I reach the world" instead of fighting over one shared table.

4The Built-In Tables You Didn't Know Existed

🔵 Concept — this trips up almost everyone the first time

Even before you add any custom tables, Linux already has THREE built-in routing tables, evaluated by built-in ip rules with these default priorities: local (priority 0 — highest, contains routes for the server's own addresses, always wins), main (priority 32766 — the "normal" table you've used since Project 2), and default (priority 32767 — lowest, rarely used). Custom rules you add typically need priorities BETWEEN 0 and 32766 to actually take effect before the main table gets a chance — and the local table's priority-0 position means it always wins for anything matching the server's own addresses, no matter what custom rules you add.

bash — see the built-in rules that already exist on every Linux host
1ip rule show
    0:      from all lookup local
    32766:  from all lookup main
    32767:  from all lookup default

5Troubleshooting Method for Multi-NIC Policy Routing

  • 1. List ip rule show — are the expected custom rules present, and in the right priority order?
    • ↓
  • 2. For the specific source IP in question, test with ip route get <dest> from <source> — does it select the table/interface you expect?
    • ↓
  • 3. Inspect the specific custom table directly: ip route show table <name> — is its default route correct?
    • ↓
  • 4. Is the application actually binding to (sourcing from) the intended interface's IP, or letting the kernel pick automatically?
    • ↓
  • Confirm no built-in table (especially local) is unexpectedly intercepting traffic before your custom rules get a chance
🟠 Warning

ip route get without an explicit from <source> uses the server's default source-selection logic, which may NOT be the source address you actually care about — always specify from explicitly when testing policy routing, or you may be testing the wrong scenario entirely.

6Lab Setup — Three Upstream Networks

bash — run as root/sudo
1sudo ip netns add ns-bastion
2for zone in mgmt prod dr; do sudo ip netns add ns-$zone-gw; done
3sudo ip link add eth-mgmt type veth peer name gw-mgmt-in
4sudo ip link add eth-prod type veth peer name gw-prod-in
5sudo ip link add eth-dr type veth peer name gw-dr-in
6for i in mgmt prod dr; do sudo ip link set eth-$i netns ns-bastion; sudo ip link set gw-$i-in netns ns-$i-gw; done
7sudo ip netns exec ns-bastion ip addr add 10.70.1.10/24 dev eth-mgmt
8sudo ip netns exec ns-bastion ip addr add 10.70.2.10/24 dev eth-prod
9sudo ip netns exec ns-bastion ip addr add 10.70.3.10/24 dev eth-dr
10sudo ip netns exec ns-mgmt-gw ip addr add 10.70.1.1/24 dev gw-mgmt-in
11sudo ip netns exec ns-prod-gw ip addr add 10.70.2.1/24 dev gw-prod-in
12sudo ip netns exec ns-dr-gw ip addr add 10.70.3.1/24 dev gw-dr-in
13sudo ip netns exec ns-bastion bash -c "ip link set eth-mgmt up; ip link set eth-prod up; ip link set eth-dr up; ip link set lo up"
14for i in mgmt prod dr; do sudo ip netns exec ns-$i-gw bash -c "ip link set gw-$i-in up; ip link set lo up"; done
15for i in mgmt prod dr; do sudo ip netns exec ns-$i-gw python3 -m http.server 80 --bind 10.70.$([ $i = mgmt ] && echo 1 || ([ $i = prod ] && echo 2 || echo 3)).1 & done

6.1 Define the custom tables

bash — on ns-bastion
1sudo ip netns exec ns-bastion bash -c "echo '100 mgmt-table' >> /etc/iproute2/rt_tables"
2sudo ip netns exec ns-bastion bash -c "echo '200 prod-table' >> /etc/iproute2/rt_tables"
3sudo ip netns exec ns-bastion bash -c "echo '300 dr-table' >> /etc/iproute2/rt_tables"

Note: network namespaces share the host's /etc/iproute2/rt_tables in some setups; if `ip netns exec` doesn't isolate this file for you, just use the numeric table IDs (100/200/300) directly in the commands below — the behavior is identical either way.

6.2 Give each table its own default route out its own interface

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip route add default via 10.70.1.1 dev eth-mgmt table mgmt-table
2sudo ip netns exec ns-bastion ip route add default via 10.70.2.1 dev eth-prod table prod-table
3sudo ip netns exec ns-bastion ip route add default via 10.70.3.1 dev eth-dr table dr-table

6.3 Add policy rules binding SOURCE address to the matching table

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip rule add from 10.70.1.10 table mgmt-table priority 100
2sudo ip netns exec ns-bastion ip rule add from 10.70.2.10 table prod-table priority 200
3sudo ip netns exec ns-bastion ip rule add from 10.70.3.10 table dr-table priority 300
TokenMeaning
ip rule add from 10.70.3.10 table dr-table priority 300Adds an entry to the RPDB: "for any packet SOURCED from 10.70.3.10, use dr-table instead of main" — with priority 300, meaning it's evaluated before the built-in main table's priority 32766, but after local's priority 0.

7Verify Baseline Policy Routing

bash — on ns-bastion, test each source explicitly
1sudo ip netns exec ns-bastion ip route get 8.8.8.8 from 10.70.3.10
    8.8.8.8 from 10.70.3.10 via 10.70.3.1 dev eth-dr table dr-table
2sudo ip netns exec ns-bastion ip route get 8.8.8.8 from 10.70.2.10
    8.8.8.8 from 10.70.2.10 via 10.70.2.1 dev eth-prod table prod-table
🟢 Validation

Even though both queries ask about the SAME destination (8.8.8.8), the kernel selects a completely different table and exit interface purely based on source address — exactly the guarantee our compliance requirement needed. This is our working baseline.

8Break-Fix #1 — Missing ip rule Entirely

🔴 Break It

Remove the DR interface's policy rule, simulating a config management run that only templated two of the three rules.

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip rule del from 10.70.3.10 table dr-table priority 300

Observe

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip route get 8.8.8.8 from 10.70.3.10
    8.8.8.8 from 10.70.3.10 via 10.70.2.1 dev eth-prod table main
🔵 Reading the symptom

With no rule sending DR-sourced traffic to dr-table, it falls through to the built-in main table — which only has ONE default route configured (whichever was added last, or whichever has the best metric), and here that happens to be via eth-prod. DR traffic is now leaking out the PRODUCTION interface — precisely the compliance violation and intermittent DR-test failure from the incident report. "Intermittent" here really means "whichever default route happens to exist in main at the time," which is exactly the kind of fragile, order-dependent behavior policy routing is meant to eliminate.

🔴 Root Cause

The policy rule binding the DR source address to its dedicated table was missing, so that traffic fell through to the shared main table instead of being guaranteed isolation.

bash — fix
1sudo ip netns exec ns-bastion ip rule add from 10.70.3.10 table dr-table priority 300

9Break-Fix #2 — Wrong Rule Priority Order

🔴 Break It

Add a broad, catch-all rule at a LOWER priority number (meaning it's evaluated FIRST) than our specific per-interface rules — simulating a rule added without checking existing priorities.

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip rule add from 10.70.0.0/16 table prod-table priority 50

Observe

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip rule show
    0:      from all lookup local
    50:     from 10.70.0.0/16 lookup prod-table
    100:    from 10.70.1.10 lookup mgmt-table
    200:    from 10.70.2.10 lookup prod-table
    300:    from 10.70.3.10 lookup dr-table
    32766:  from all lookup main
2sudo ip netns exec ns-bastion ip route get 8.8.8.8 from 10.70.3.10
    8.8.8.8 from 10.70.3.10 via 10.70.2.1 dev eth-prod table prod-table
🔵 Reading the symptom

Our correctly-configured priority-300 DR rule is still sitting right there in the list — but it never gets a chance to run, because the new priority-50 rule matches the entire 10.70.0.0/16 supernet FIRST (lower priority number = evaluated earlier) and sends everything to prod-table before the kernel ever reaches rule 300. This is the exact same "first match wins, position matters more than existence" lesson from firewall rule ordering in Project 7, now applied to the routing policy database instead of a firewall chain.

🔴 Root Cause

A broad policy rule was added with a lower priority number (higher precedence) than the specific per-interface rules, shadowing all of them for any matching source.

bash — fix: remove the overly broad rule
1sudo ip netns exec ns-bastion ip rule del from 10.70.0.0/16 table prod-table priority 50
🟦 Production Best Practice

Always run ip rule show before AND after adding a new policy rule, and think in terms of "lower priority number = evaluated first" — the same discipline used for firewall rule ordering applies directly here.

10Break-Fix #3 — Application Not Binding to the Intended Source Address

🔴 Break It

Our ip rule setup only works if traffic is actually SOURCED from the right interface's IP in the first place. If an application doesn't explicitly bind to a specific local address before connecting, the kernel's own source-address-selection algorithm picks one for it — which may not be the one you intended.

bash — on ns-bastion, a naive curl WITHOUT specifying a source interface
1sudo ip netns exec ns-bastion curl -s -o /dev/null -w "%{local_ip}\n" http://10.70.1.1/
    10.70.2.10   (NOT the mgmt IP we might have expected — the kernel chose based on its own routing logic for this destination)
🔵 Reading the symptom

Without an explicit source binding, the kernel picks a source address by first making a normal destination-based routing decision (in this test, toward 10.70.1.1, which is directly reachable, so main/local logic applies) and then uses whatever address belongs to the chosen outgoing interface — it does NOT know "this application conceptually belongs to the DR network" unless you tell it. Our entire policy-routing setup depends on the SOURCE address already being correct; it does nothing to help you pick one in the first place.

🔴 Root Cause

The application/tool made no explicit choice of local source address, so the outcome depended on the kernel's default source-selection behavior rather than the operator's intended network segregation.

bash — fix: force the correct source address explicitly
1sudo ip netns exec ns-bastion curl -s --interface eth-dr -o /dev/null -w "%{local_ip}\n" http://10.70.1.1/
    10.70.3.10
TokenMeaning
curl --interface eth-drExplicitly tells curl to bind its outgoing connection to this interface (and therefore its address) — forcing the correct source address so our ip rule policy actually applies as intended.
🟦 Production Best Practice

On multi-NIC hosts with policy routing, applications and scripts that need guaranteed interface segregation must explicitly bind their source address/interface (via application config, SO_BINDTODEVICE, or tool-specific flags) — never assume the kernel will "figure out" which network a given piece of traffic conceptually belongs to.

11Break-Fix #4 — The Local Table's Silent Precedence

🔴 Break It

Simulate a well-intentioned but misguided attempt to "fix" routing for the bastion's own IP by adding a custom rule for traffic sourced from 10.70.3.10 destined back to itself — expecting it to change behavior.

bash — on ns-bastion
1sudo ip netns exec ns-bastion ip rule add from 10.70.3.10 to 10.70.3.10 table dr-table priority 10
2sudo ip netns exec ns-bastion ip route get 10.70.3.10 from 10.70.3.10
    local 10.70.3.10 from 10.70.3.10 dev lo table local
🔵 Reading the symptom

No matter what priority we give our new rule, traffic destined for the server's OWN address is always intercepted first by the built-in local table at priority 0 — nothing we add can ever have a lower (earlier) priority than 0. The output confirms it: the kernel resolves this as a local delivery via the loopback interface, never even considering our dr-table rule. This isn't a bug to fix — it's expected, correct behavior — but it's a common source of confusion when someone expects a custom rule to affect traffic destined to the host's own addresses.

🔴 Root Cause

Not actually a fault — a misunderstanding that a custom policy rule could override the built-in local table's priority-0 handling of the server's own addresses, which is architecturally impossible.

bash — cleanup: remove the unnecessary rule
1sudo ip netns exec ns-bastion ip rule del from 10.70.3.10 to 10.70.3.10 table dr-table priority 10
🟦 Production Best Practice

Policy routing governs how traffic LEAVES a host toward other destinations — it has no effect on traffic destined for the host's own addresses, which the local table always claims first, unconditionally. Don't spend time debugging "why doesn't my rule affect traffic to my own IP" — by design, it never will.

12Production Best Practices

🟦 Always specify "from" when testing

ip route get without an explicit source tests the wrong scenario for policy routing — always include from <address>.

🟦 Priority numbers: lower = first

Same discipline as firewall rule ordering — audit ip rule show for unintentionally broad or low-priority rules shadowing specific ones.

🟦 Applications must bind explicitly

Policy routing only works if the source address is already correct — make sure applications/tools explicitly bind to the intended interface rather than trusting kernel defaults.

🟦 The local table is untouchable

Traffic to the host's own addresses always resolves via the built-in local table at priority 0 — no custom rule can or should try to override this.

🟦 Give every custom table its own complete default route

A custom table with no default route of its own will fail for any destination outside its directly-connected subnet.

14Interview Preparation

ScenarioA server with three NICs needs to guarantee traffic from each interface never crosses over to another. How would you implement and verify this?

I'd use policy-based routing — separate named routing tables per interface, each with its own default route, and ip rule entries binding each interface's source address to its matching table with an appropriate priority. To verify, I'd never rely on eyeballing the config — I'd use ip route get with an explicit from address for each interface's IP and confirm it resolves through the correct table and device.

Interviewer follow-up: "What if the rule is correctly configured but traffic still leaks?" — Answer: I'd check whether the application generating that traffic is actually binding to the intended source address at all — policy routing only works if the source is already correct; if the app lets the kernel pick a source automatically, it might not use the address your rule is keyed on.
ConceptWhat are the three built-in Linux routing tables, and why does it matter?

local, main, and default, evaluated in that priority order — local at priority 0, main at 32766, default at 32767. It matters because local always wins for traffic to the host's own addresses regardless of any custom rules you add, and any custom rule needs a priority number between 0 and 32766 to actually take effect before the main table would otherwise handle it.

TroubleshootingYou added a policy rule for a specific source address but it doesn't seem to be taking effect. What would you check?

First I'd run ip rule show and check the full priority-ordered list for a broader or lower-priority-number rule that might be matching the same traffic first — since rules are evaluated in priority order and the first match wins, a rule can exist correctly and still never be reached. I'd also confirm with ip route get using an explicit from address exactly which table and interface the kernel is actually selecting.

DevOpsHow does this concept relate to more modern infrastructure?

This is the direct conceptual foundation of VRF (Virtual Routing and Forwarding), which extends the same idea further for stricter isolation, and it's conceptually similar to what cloud providers do internally with multiple ENIs and route tables per subnet on multi-homed instances — understanding ip rule and custom tables at the Linux level makes those higher-level abstractions much easier to reason about.
