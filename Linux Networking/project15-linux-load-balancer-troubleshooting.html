1The Incident

We're back with the e-commerce platform team. Their product-listing service runs across three backend servers, sitting behind a lightweight Linux load balancer built on IPVS — the load balancing engine that's actually built into the Linux kernel, sitting right alongside netfilter.

"Traffic distribution looks weird — one backend seems to be getting almost nothing while the other two are working overtime. And separately, someone mentioned backend-2 crashed during a deploy about twenty minutes ago, but we're not sure if the load balancer even noticed."

This is a genuinely different kind of Linux networking problem from anything we've covered so far — it's not about whether one connection works, it's about whether MANY connections are being distributed the way they should be, and whether the load balancer's view of backend health matches reality.

🔵 Why this project matters

IPVS (IP Virtual Server) is the same underlying technology behind kube-proxy's IPVS mode in Kubernetes, and it's a genuinely common choice for a lightweight, high-performance Layer 4 load balancer in front of any pool of backend servers. Understanding it directly builds on everything we already know — netfilter, connection tracking, and NAT from Projects 7 and 8 — applied to a new problem: distributing load across many destinations instead of just one.

2Load Balancing Foundation

2.1 Layer 4 vs Layer 7 load balancing

🔵 Concept

A Layer 4 load balancer makes its decision using only IP and port information — it doesn't look inside the packet's application data at all, which makes it extremely fast but also protocol-agnostic (it works the same for HTTP, a database connection, anything TCP or UDP). A Layer 7 load balancer (like Nginx or HAProxy in HTTP mode) actually reads the application-layer content — HTTP headers, URLs, cookies — and can make smarter, content-aware routing decisions, at the cost of more CPU work per connection. IPVS, which we're using in this project, is a Layer 4 load balancer living directly in the kernel.

2.2 IPVS — a load balancer built into the Linux kernel

🔵 Concept

IPVS (IP Virtual Server) is a kernel-level Layer 4 load balancing engine, configured through the ipvsadm command-line tool. You define a "virtual service" (a single IP:port that clients connect to) and a pool of "real servers" (the actual backends) behind it. The kernel then transparently distributes incoming connections across the pool according to a scheduling algorithm you choose — all without any userspace proxy process handling the actual data.

2.3 Scheduling algorithms — how IPVS picks a backend

🔵 Concept

The most common IPVS schedulers are rr (round robin — each new connection goes to the next backend in a simple rotating order), wrr (weighted round robin — backends with a higher configured weight get proportionally more connections), and lc (least connections — new connections go to whichever backend currently has the fewest active connections). A backend's weight is a critical, easy-to-overlook setting — a backend with weight 0 stays visible in the pool but never receives new connections at all.

2.4 NAT mode — the simplest IPVS forwarding method

🔵 Concept

IPVS supports a few forwarding methods; NAT mode is the simplest to understand because it works exactly like the DNAT we already built in Project 8 — the load balancer rewrites the destination address of an incoming packet to point at the chosen backend, and it must also handle the return path, rewriting the response back to look like it came from the load balancer's own virtual IP. This means every backend's default route MUST point back through the load balancer — otherwise, exactly like our missing-MASQUERADE incident in Project 8, replies will try to route directly to the client and never make it back correctly.

Figure 1 — The client only ever knows about the virtual IP. Every backend must route its default traffic back through the load balancer for the reply to reach the client correctly.

4Troubleshooting Method

  • 1. Check the service and backend pool exists: ipvsadm -Ln — is every expected backend listed?
    • ↓
  • 2. Check live connection distribution: ipvsadm -Ln --stats — is one backend getting zero or a wildly disproportionate share?
    • ↓
  • 3. Check each backend's weight — a weight of 0 means "still in the pool, but never gets new connections"
    • ↓
  • 4. Confirm each backend is actually healthy — is a health-check mechanism removing dead backends, or is IPVS blindly trusting a static config?
    • ↓
  • 5. For NAT mode specifically: does each backend's default route point back through the load balancer?
    • ↓
  • Once the pool, weights, health, and NAT return path are all confirmed, move to the individual backend's own application health if problems persist
🟠 Warning

IPVS itself has no built-in health checking — it will happily keep sending traffic to a backend that's completely dead unless something else (like keepalived, or a custom script) actively monitors backend health and updates the pool. Never assume "it's in the ipvsadm table" means "it's healthy."

5.1 Configure the IPVS virtual service and backend pool

bash — on ns-lb
1sudo ip netns exec ns-lb ipvsadm -A -t 10.110.1.100:80 -s rr   # -A = add a new virtual service; -t = TCP; -s rr = use round-robin scheduling
2sudo ip netns exec ns-lb ipvsadm -a -t 10.110.1.100:80 -r 10.110.2.11:80 -m -w 1   # -a = add a real server to the service; -m = NAT (masquerade) forwarding mode; -w 1 = weight 1
3sudo ip netns exec ns-lb ipvsadm -a -t 10.110.1.100:80 -r 10.110.2.12:80 -m -w 1
4sudo ip netns exec ns-lb ipvsadm -a -t 10.110.1.100:80 -r 10.110.2.13:80 -m -w 1
TokenMeaning
-A -t 10.110.1.100:80 -s rrCreates the virtual service — clients will connect to this single IP:port, and IPVS will distribute their connections using round-robin scheduling.
-a -t <service> -r <real> -m -w 1Adds one backend to that service's pool: -r is the real server's address, -m selects NAT forwarding (the DNAT-like mode from Section 2.4), and -w 1 gives it a normal, equal weight relative to the others.

7Break-Fix #1 — Backend Weight Silently Zero

🔴 Break It

Simulate a common automation mistake — a deploy script accidentally sets backend-2's weight to 0 instead of removing and re-adding it properly during a rolling update.

bash — on ns-lb
1sudo ip netns exec ns-lb ipvsadm -e -t 10.110.1.100:80 -r 10.110.2.12:80 -m -w 0   # -e = edit an existing real server's settings; weight changed from 1 to 0

Observe

bash — on ns-client
1for i in 1 2 3 4 5 6; do sudo ip netns exec ns-client curl -s http://10.110.1.100/; done
    backend-1 response
    backend-3 response
    backend-1 response
    backend-3 response
    backend-1 response
    backend-3 response   (backend-2 never answers, even though it's healthy and fully able to serve requests)
2sudo ip netns exec ns-lb ipvsadm -Ln   # list the pool without stats — just to see current configuration
    -> 10.110.2.12:80    Masq    0        0          0    (Weight column shows 0 — there's the answer)
🔵 Reading the symptom

backend-2 is completely healthy — if you curl it directly, it answers instantly. But it's silently excluded from IPVS's scheduling decisions because its weight is 0. This is exactly the kind of issue that looks like a backend health problem but is actually purely a load balancer configuration issue — the fix has nothing to do with the backend itself.

🔴 Root Cause

The backend's weight was set to 0, which keeps it visible in the pool listing but permanently excludes it from receiving new connections, regardless of its actual health.

bash — fix
1sudo ip netns exec ns-lb ipvsadm -e -t 10.110.1.100:80 -r 10.110.2.12:80 -m -w 1   # restore the weight back to 1
🟦 Production Best Practice

Always check backend weight explicitly with ipvsadm -Ln whenever traffic distribution looks uneven — "in the pool" and "actually receiving traffic" are two different facts, exactly like the bridge-port lesson from Project 10.

8Break-Fix #2 — Dead Backend Still in Rotation

🔴 Break It

Kill backend-2's web server process to simulate a real crash, without removing it from the IPVS pool — reproducing the "did the load balancer even notice?" part of our incident report.

bash — on ns-backend2
1sudo ip netns exec ns-backend2 pkill -f "http.server 80"   # simulate a crash — the process is gone but IPVS was never told

Observe

bash — on ns-client
1for i in 1 2 3 4 5 6; do sudo ip netns exec ns-client curl -s --max-time 2 http://10.110.1.100/ || echo "FAILED"; done
    backend-1 response
    FAILED
    backend-3 response
    backend-1 response
    FAILED
    backend-3 response   (every 3rd request, on average, hits the dead backend and fails)
🔵 Reading the symptom

IPVS has no idea backend-2 is dead — it's a pure Layer 4 forwarding table, not a health-aware system. It will keep sending its fair share of round-robin traffic to a completely unresponsive backend forever, until something else actively removes it. In real production, this "something else" is usually a separate health-check daemon like keepalived, running alongside IPVS and updating the pool automatically.

🔴 Root Cause

There was no active health-check mechanism monitoring the backends, so IPVS kept treating a crashed backend exactly like a healthy one, causing a consistent fraction of client requests to fail.

bash — fix: manually remove the dead backend (a real health-check tool would automate this)
1sudo ip netns exec ns-lb ipvsadm -d -t 10.110.1.100:80 -r 10.110.2.12:80   # -d = delete this real server from the service's pool entirely
2sudo ip netns exec ns-backend2 bash -c "cd /tmp && python3 -m http.server 80 --bind 10.110.2.12 &"   # bring the backend back for later
3sudo ip netns exec ns-lb ipvsadm -a -t 10.110.1.100:80 -r 10.110.2.12:80 -m -w 1   # re-add it once it's confirmed healthy again
🟦 Production Best Practice

IPVS should never run without an accompanying health-check mechanism in production — keepalived is the classic pairing, actively probing each backend and calling ipvsadm to add/remove them from the pool automatically as their health changes.

9Break-Fix #3 — Broken NAT-Mode Return Path

🔴 Break It

Remove backend-3's default route back through the load balancer — simulating a misconfigured or newly-provisioned server that was never set up correctly for NAT-mode load balancing.

bash — on ns-backend3
1sudo ip netns exec ns-backend3 ip route del default via 10.110.2.1   # remove the route that sends return traffic back through the load balancer

Observe

bash — on ns-client
1for i in 1 2 3 4 5 6; do sudo ip netns exec ns-client curl -s --max-time 2 http://10.110.1.100/ || echo "FAILED"; done
    backend-1 response
    backend-2 response
    FAILED
    backend-1 response
    backend-2 response
    FAILED   (backend-3's turn always times out now)
bash — confirm with a capture on the load balancer's backend-facing interface
1sudo ip netns exec ns-lb tcpdump -i lb-b3-in -nn 'tcp port 80' -c 4   # watch what actually crosses the link to backend-3
    (the SYN from the load balancer to backend-3 is visible, going out fine)
    (no reply is ever captured coming back on this interface — backend-3 is replying somewhere else entirely)
🔵 Reading the symptom

This is exactly Project 8's missing-MASQUERADE lesson, wearing a load-balancer costume. The load balancer's DNAT-like rewrite sends the connection to backend-3 fine — but without a route back through the load balancer, backend-3's kernel doesn't know to send its reply back that way. Instead it tries to route the reply using its own normal routing logic, which has no path back to the original client's real address at all, so the reply goes nowhere useful and the client's request simply times out.

🔴 Root Cause

backend-3's default route no longer pointed back through the load balancer, breaking the NAT-mode return path required for the load balancer to correctly deliver replies back to clients.

bash — fix
1sudo ip netns exec ns-backend3 ip route add default via 10.110.2.1   # restore the route back through the load balancer
🟦 Production Best Practice

When onboarding a new backend to an IPVS NAT-mode pool, always verify its default route points back through the load balancer as a required provisioning step — it's easy to forget on a freshly built server, and the failure it causes looks exactly like a random, one-backend-in-three connectivity issue rather than an obvious routing mistake.

10Production Best Practices

🟦 "In the pool" ≠ "receiving traffic"

Always check weight explicitly — a weight-0 backend stays listed but gets nothing.

🟦 IPVS has no built-in health checking

Pair it with an active health-check daemon like keepalived, or dead backends stay in rotation forever.

🟦 NAT mode requires a return route on every backend

Treat it as a mandatory provisioning step, not an optional detail — this is Project 8's MASQUERADE lesson applied to load balancing.

🟦 Use --stats, not just -Ln

Live connection counters are the fastest way to spot uneven distribution before you go hunting for a specific misconfiguration.

12Interview Preparation

ScenarioTraffic distribution across your load-balanced backends looks uneven. How do you investigate?

I'd start with ipvsadm -Ln --stats to see live connection counts per backend, and cross-check ipvsadm -Ln for each backend's configured weight — a weight of 0 is a very common, easy-to-miss cause of a healthy backend receiving zero traffic. If weights look correct, I'd verify each backend is actually healthy and, if using NAT mode, confirm every backend's default route points back through the load balancer.

Interviewer follow-up: "What if a backend is dead but IPVS keeps sending it traffic?" — Answer: IPVS itself has no health-checking logic — it's a pure Layer 4 forwarding table. A separate mechanism, typically keepalived, needs to actively probe backend health and add or remove them from the pool automatically.
ConceptWhat's the difference between Layer 4 and Layer 7 load balancing?

Layer 4 balancing makes decisions using only IP and port information, without inspecting application data — fast and protocol-agnostic. Layer 7 balancing reads application-layer content like HTTP headers or URLs to make smarter, content-aware routing decisions, at the cost of more processing per connection. IPVS is a Layer 4 balancer built into the Linux kernel; tools like Nginx or HAProxy in HTTP mode operate at Layer 7.

TroubleshootingIn IPVS NAT mode, why would a specific backend intermittently fail to respond even though it's running fine?

NAT mode requires the load balancer to rewrite both the outbound request's destination and the backend's reply on the way back, and for that to work, the backend's own default route needs to point back through the load balancer. If that route is missing or wrong, the backend's replies get routed elsewhere and never reach the client, even though the backend itself is completely healthy and processed the request correctly.
