1The Task

After Project 24's NAT port exhaustion incident — the one that was nearly impossible to catch live because it self-resolved within a minute or two — the platform team has one clear ask: make sure the next occurrence triggers an alert automatically, instead of relying on an engineer noticing and investigating in real time.

"We can't keep relying on someone happening to run conntrack -L at exactly the right moment. We need this graphed continuously and alerting automatically — but we also don't want to be that team with 200 alerts a day that everyone starts ignoring."

Every manual diagnostic command from this masterclass has a direct, continuously-running equivalent in the Prometheus/node_exporter ecosystem. The real skill in this project isn't learning new commands — it's learning to design alerts that fire exactly when something is actually wrong, not constantly, and not never.

🔵 Why this project matters

Poorly designed monitoring is arguably worse than no monitoring — a system with constant false-positive alerts trains engineers to ignore it, and a system with silent blind spots gives false confidence. Understanding the specific, common mistakes in network metric alerting (counter-vs-rate confusion, absolute vs normalized thresholds, missing coverage) is what separates monitoring that actually helps from monitoring that's just noise or theater.

2Monitoring Foundation

2.1 Counters vs gauges — the single most important metric-type distinction

🔵 Concept

A counter only ever goes up (or resets to zero on restart) — total bytes transmitted, total retransmitted segments, total errors. A gauge can go up or down freely — current number of established connections, current conntrack table size. Almost every interesting network metric from earlier projects — retransmissions (Project 13), interface errors (Project 12), ListenOverflows (Project 18) — is a COUNTER. You almost never want to alert on a counter's raw value directly; you want its RATE of change over time, which is exactly what PromQL's rate() function computes.

2.2 node_exporter — automating what we've done by hand all masterclass

🔵 Concept

node_exporter is the standard Prometheus agent for exposing Linux host metrics, and its network-related metrics are drawn from exactly the same sources we've used manually throughout this series: node_network_receive_errs_total and node_network_transmit_errs_total (from the same source as Project 12's ip -s link), node_netstat_Tcp_RetransSegs (the same counter nstat reads in Project 13), and node_nf_conntrack_entries / node_nf_conntrack_entries_limit (exactly what Project 7 and Project 24 checked manually with conntrack -L and sysctl nf_conntrack_max).

2.3 PromQL's rate() — turning a counter into something you can actually alert on

🔵 Concept

rate(node_netstat_Tcp_RetransSegs[5m]) computes the PER-SECOND average rate of increase of that counter over the trailing 5 minutes — exactly turning a constantly-climbing raw number into a meaningful "how much is this happening RIGHT NOW" value, which is almost always what you actually want to alert on rather than the raw cumulative total.

2.4 Alert design: specific, actionable, and rare

🔵 Concept

A well-designed alert should fire rarely, mean something specific and actionable when it does, and be tuned against REAL observed baseline behavior rather than a guessed round number. Every break-fix in this project demonstrates a common way alert design goes wrong despite the underlying metric being completely correct and available.

4Alert Design Method

  • 1. Is this metric a counter or a gauge? If a counter, are you alerting on rate(), not the raw value?
    • ↓
  • 2. Is the threshold based on observed real baseline behavior, or a guessed round number?
    • ↓
  • 3. Should this be an absolute count or normalized against traffic volume (a percentage/ratio)?
    • ↓
  • 4. Does every resource that has caused a past incident (Project 24's conntrack/NAT ports, Project 18's socket buffers) have explicit coverage?
    • ↓
  • Test the alert against both a known-good period and a reproduced incident (like our lab break-fixes) before trusting it in production
🟠 Warning

A metric being COLLECTED is not the same as it being ALERTED ON or even displayed on a dashboard anyone looks at regularly — collection without visibility is a silent blind spot that feels like coverage but isn't.

5Build a Minimal Network Metrics Exporter

We'll write a small Python exporter that reads real data from /proc/net — the exact files behind ss, nstat, and ip -s link all masterclass — and exposes it in the same text format node_exporter uses, so the PromQL concepts translate directly to a real deployment.

bash — run as root/sudo, in ns-checkout or any namespace with active traffic (reuse any earlier lab)
1sudo ip netns add ns-monitored   # a host we'll monitor
2sudo ip netns exec ns-monitored ip link set lo up
3sudo ip netns exec ns-monitored bash -c "cat > /tmp/mini_exporter.py" <<'EOF'
import re, time
from http.server import HTTPServer, BaseHTTPRequestHandler

def read_retrans_segs():
    # /proc/net/snmp holds the same TCP counters `nstat` reads - we grab
    # RetransSegs specifically, exactly like Project 13's diagnostic
    with open('/proc/net/snmp') as f:
        lines = f.read().splitlines()
    headers = next(l for l in lines if l.startswith('Tcp:')).split()
    values = next(l for l in lines if l.startswith('Tcp:') and l != lines[lines.index(next(l for l in lines if l.startswith('Tcp:')))]).split()
    idx = headers.index('RetransSegs')
    return int(values[idx])

def read_iface_errors(iface='lo'):
    # /proc/net/dev holds the same RX/TX error counters Project 12's
    # `ip -s link` reads
    with open('/proc/net/dev') as f:
        for line in f:
            if iface + ':' in line:
                fields = line.split(':')[1].split()
                rx_errs = int(fields[2])   # 3rd field after the interface name is RX errors
                tx_errs = int(fields[10])  # matching TX errors field
                return rx_errs, tx_errs
    return 0, 0

class MetricsHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != '/metrics':
            self.send_response(404); self.end_headers(); return
        retrans = read_retrans_segs()
        rx_err, tx_err = read_iface_errors('lo')
        body = (
            "# HELP node_netstat_Tcp_RetransSegs Total TCP segments retransmitted\n"
            "# TYPE node_netstat_Tcp_RetransSegs counter\n"
            f"node_netstat_Tcp_RetransSegs {retrans}\n"
            "# HELP node_network_receive_errs_total Receive errors\n"
            "# TYPE node_network_receive_errs_total counter\n"
            f'node_network_receive_errs_total{{device="lo"}} {rx_err}\n'
        ).encode()
        self.send_response(200)
        self.send_header('Content-Type', 'text/plain')
        self.end_headers()
        self.wfile.write(body)

HTTPServer(('127.0.0.1', 9100), MetricsHandler).serve_forever()
EOF
4sudo ip netns exec ns-monitored python3 /tmp/mini_exporter.py &   # start our exporter on the standard node_exporter port, 9100

open('/proc/net/snmp')The exact kernel file nstat parses under the hood — we're reading the same TCP-layer counters Project 13 used to diagnose retransmission behavior, just automated into a continuously-scrapable endpoint.

7Break-Fix #1 — Alerting on a Raw Counter Instead of Its Rate

🔴 The Mistake

Someone writes an alert rule directly against the raw counter value, without rate():

ALERT: HighRetransmissions expr: node_netstat_Tcp_RetransSegs > 1000 for: 5m # PROBLEM: this is the RAW CUMULATIVE COUNTER, not a rate

Reading the mistake

🔵 Why this breaks in two different, equally bad ways

A counter only ever goes up. Once total retransmissions cross 1000 — which will happen eventually on ANY sufficiently long-lived, busy host, even with a perfectly healthy, low retransmission RATE — this alert fires and then NEVER STOPS firing, because the counter never decreases. The team will either mute it permanently (creating a real blind spot for a genuine future spike) or become numb to it exactly like the "200 alerts a day" problem from Section 1's request. Meanwhile, a genuinely dangerous SPIKE in retransmissions — say, jumping from a totally normal baseline to 10x that rate in five minutes — might not even cross the static 1000 threshold at all if the host hasn't been up very long, meaning the alert can simultaneously be too noisy AND blind to a real problem.

🔴 Root Cause

The alert rule was written against a raw, ever-increasing counter value instead of its rate of change, making the threshold meaningless relative to actual current behavior.

ALERT: HighRetransmissionRate expr: rate(node_netstat_Tcp_RetransSegs[5m]) > 5 for: 5m # FIXED: alerts on segments/sec over the trailing 5 minutes, # a value that reflects CURRENT behavior and can rise and # fall with real conditions
🟦 Production Best Practice

Any alert expression referencing a metric of TYPE counter should almost always wrap it in rate() (or irate() for more responsive, spikier detection) — treat a bare counter reference in an alert rule as an immediate red flag during alert review.

8Break-Fix #2 — A Silent Blind Spot: Conntrack Never Monitored

🔴 The Mistake

The team deploys node_exporter, builds dashboards for interface throughput and error rates, and calls monitoring "done" — but conntrack table usage, the exact resource that caused Project 24's incident, was never added to any dashboard or alert.

Reading the mistake

🔵 Why this is invisible until it's too late

node_exporter DOES expose node_nf_conntrack_entries and node_nf_conntrack_entries_limit by default — the data was always available. But "the metric exists and is being scraped" is not the same as "someone would notice if it approached its limit." Without an explicit alert (or even a dashboard panel anyone actually looks at), the exact Project 24 incident could recur, get fully collected in Prometheus's historical data, and still go completely unnoticed in real time — the team would only discover it existed by looking at historical data AFTER the fact, exactly the reactive position Section 1's request was trying to move away from.

🔴 Root Cause

A metric that was technically being collected had no corresponding alert or actively-monitored dashboard, creating a coverage gap that felt like monitoring but functioned identically to having no monitoring at all for that specific resource.

ALERT: ConntrackTableNearLimit expr: (node_nf_conntrack_entries / node_nf_conntrack_entries_limit) > 0.8 for: 2m # fires when conntrack usage crosses 80% of its configured # max - exactly the resource that caused the Project 24 # incident, now actively watched instead of just collected
🟦 Production Best Practice

After every real incident, explicitly cross-check: is the resource that caused this now covered by BOTH a dashboard panel someone actually looks at AND an alert with a sensible threshold — not just "is the metric technically available somewhere." Treat this cross-check as a standard, non-optional part of every RCA's follow-up actions (exactly like Project 25's RCA template required).

9Break-Fix #3 — Absolute Error Count Instead of Error Rate

🔴 The Mistake

An alert is written against the absolute number of interface errors, without normalizing against traffic volume:

ALERT: InterfaceErrors expr: rate(node_network_receive_errs_total[5m]) > 10 # PROBLEM: 10 errors/sec sounds meaningful, but has no # relationship to how much traffic is actually flowing

Reading the mistake

🔵 Why "10 errors per second" means completely different things at different traffic levels

On a quiet interface handling 50 packets per second, 10 errors/sec is a catastrophic 20% error rate — a genuine, severe problem that this threshold WOULD catch. But on a busy interface handling 500,000 packets per second, that exact same 10 errors/sec is a vanishingly small 0.002% error rate — likely within completely normal, healthy variance — yet the identical alert fires identically in both cases, either crying wolf constantly on the busy interface or (worse) being tuned so high to avoid that noise that it becomes blind on the quiet one.

🔴 Root Cause

The alert threshold was an absolute error count with no relationship to traffic volume, making it simultaneously too sensitive at low traffic and not sensitive enough at high traffic.

ALERT: InterfaceErrorRate expr: | ( rate(node_network_receive_errs_total[5m]) / rate(node_network_receive_packets_total[5m]) ) > 0.01 for: 5m # FIXED: fires when errors exceed 1% of received packets, # a threshold that means the same thing regardless of # current traffic volume
🟦 Production Best Practice

Whenever an error or failure count could plausibly scale with traffic volume, normalize the alert as a ratio or percentage of total traffic, not an absolute count — this is the network-monitoring equivalent of Project 13's core lesson that a raw percentage-loss number alone doesn't tell you the real impact without context.

10Best Practices

🟦 Never alert on a bare counter

Always wrap in rate() — a raw counter alert is either permanently stuck firing or effectively meaningless.

🟦 "Collected" ≠ "monitored"

Cross-check every past incident's root-cause resource against an actual dashboard panel and alert, not just metric availability.

🟦 Normalize error counts against traffic volume

An absolute threshold means different things at different traffic levels — use a ratio instead.

🟦 Tune thresholds against real observed baselines

A guessed round number is rarely correct in either direction — validate against actual historical data.

12Interview Preparation

ScenarioYou're asked to write an alert for TCP retransmissions. What would you watch out for?

The metric is a counter — it only increases — so I'd never alert on its raw value directly, since it will eventually cross any static threshold on a long-lived host regardless of current health. I'd wrap it in rate() to get a per-second value reflecting current behavior, and tune the threshold against real observed baseline retransmission rates rather than a guessed number.

Interviewer follow-up: "What if the alert needs to account for varying traffic levels?" — Answer: I'd normalize it as a ratio — retransmission rate divided by total segment rate — rather than an absolute value, so the threshold means the same thing whether traffic is low or high, exactly like normalizing interface errors against total packet rate.
ConceptWhat's the difference between a Prometheus counter and a gauge, and why does it matter for alerting?

A counter only ever increases (or resets on restart) — total errors, total retransmissions, total bytes. A gauge can go up or down — current connection count, current conntrack table size. It matters because alerting on a counter's raw value is almost always wrong; you need its rate of change over time using rate(), while a gauge can often be alerted on directly since its current value is already meaningful.

ProductionHow would you make sure a resource that caused a past incident doesn't cause a silent recurrence?

I'd explicitly verify it has both a dashboard panel that's actually part of a regularly-reviewed view, AND a specific alert with a sensible, rate-or-ratio-based threshold — not just confirm the underlying metric is technically being collected. A metric existing in Prometheus's data but never surfaced anywhere functions identically to no monitoring at all when the actual incident happens.
