2What a Network Namespace Actually Is

2.1 A namespace is a kernel object, not a "fake machine"

🔵 Concept

A network namespace is a Linux kernel feature that gives a process (or a whole set of processes) its own private copy of the network stack — its own interfaces, its own routing table, its own iptables rules, its own /proc/net. It is NOT a virtual machine and NOT a container by itself — containers and pods are built USING network namespaces, plus several other kinds of namespaces (PID, mount, UTS, etc.) that we're not covering here.

2.2 Two ways to reference a namespace — named vs by-PID

🔵 Concept

Everything we've done with ip netns add ns-something creates a NAMED namespace — the kernel keeps a reference to it at /var/run/netns/<name> even with no process running inside it, which is why we can `ip netns exec` into an "empty" namespace at any time. Docker and Kubernetes usually DON'T create named namespaces this way — instead, a container's namespace is tied to its main process's PID, and you enter it with nsenter --target <pid> --net instead of `ip netns exec`. Both are the exact same underlying kernel feature, just referenced differently.

2.3 veth pairs are the only way namespaces talk to anything

🔵 Concept

A freshly created namespace has NOTHING but a loopback interface — completely isolated. The only way to connect it to anything else (another namespace, a bridge, the host) is a veth pair, exactly as we've built dozens of times. Understanding this makes namespace-based topologies predictable: if two namespaces can't reach each other, there is ALWAYS a specific veth, bridge, or routing link missing somewhere in the chain — never "mysterious" isolation.

2.4 Namespace lifetime and cleanup

🔵 Concept

A named namespace persists until you explicitly delete it with ip netns delete — even after every process inside it exits. This is different from a PID-based namespace (like a container's), which is automatically cleaned up by the kernel once the last process using it exits. Forgetting to clean up named namespaces is the single most common cause of "why do I have twenty phantom namespaces on my lab machine" — a very real, very common annoyance once you've worked through this masterclass.

3Architecture — A 4-Hop Chain

Figure 1 — Traffic from segment A to segment C must be correctly routed through BOTH router namespaces — a genuinely multi-hop topology, unlike anything we've built with just two or three namespaces before.

4Troubleshooting Method for Multi-Hop Namespace Labs

  • 1. List every namespace: ip netns list — confirm the full topology actually exists
    • ↓
  • 2. From the source, run ip route get to the final destination — does it even know a next hop?
    • ↓
  • 3. Check each router's ip_forward sysctl — a router namespace that can't forward is a dead end, even with perfect routes and interfaces
    • ↓
  • 4. Hop by hop, confirm each router has correct routes for BOTH directions (forward and return)
    • ↓
  • Isolate exactly which hop breaks using ping/traceroute from each intermediate point, not just from the two endpoints
🟠 Warning

Never debug a multi-hop chain only from the two endpoints — always test connectivity FROM each intermediate router too, to narrow down exactly which single hop is broken instead of guessing across the whole chain.

5Build the 4-Hop Chain

bash — run as root/sudo
1sudo ip netns add ns-segment-a       # leftmost segment — where our "client" lives
2sudo ip netns add ns-router-1        # first router, connects segment A to segment B
3sudo ip netns add ns-router-2        # second router, connects segment B to segment C
4sudo ip netns add ns-segment-c       # rightmost segment — where our "server" lives
5sudo ip link add veth-a type veth peer name r1-a-in    # link 1: segment A <-> router 1
6sudo ip link add r1-b-out type veth peer name r2-b-in   # link 2: router 1 <-> router 2 (this is "segment B", the middle transit link)
7sudo ip link add r2-c-out type veth peer name veth-c    # link 3: router 2 <-> segment C
8sudo ip link set veth-a netns ns-segment-a
9sudo ip link set r1-a-in netns ns-router-1
10sudo ip link set r1-b-out netns ns-router-1
11sudo ip link set r2-b-in netns ns-router-2
12sudo ip link set r2-c-out netns ns-router-2
13sudo ip link set veth-c netns ns-segment-c
14sudo ip netns exec ns-segment-a ip addr add 10.201.1.10/24 dev veth-a
15sudo ip netns exec ns-router-1 ip addr add 10.201.1.1/24 dev r1-a-in    # router-1's IP on segment A's side
16sudo ip netns exec ns-router-1 ip addr add 10.202.1.1/24 dev r1-b-out   # router-1's IP on the transit link toward router-2
17sudo ip netns exec ns-router-2 ip addr add 10.202.1.2/24 dev r2-b-in    # router-2's IP on the same transit link
18sudo ip netns exec ns-router-2 ip addr add 10.203.1.1/24 dev r2-c-out   # router-2's IP on segment C's side
19sudo ip netns exec ns-segment-c ip addr add 10.203.1.10/24 dev veth-c
20for ns in ns-segment-a ns-router-1 ns-router-2 ns-segment-c; do sudo ip netns exec $ns ip link set lo up; done
21sudo ip netns exec ns-segment-a ip link set veth-a up
22sudo ip netns exec ns-router-1 bash -c "ip link set r1-a-in up; ip link set r1-b-out up"
23sudo ip netns exec ns-router-2 bash -c "ip link set r2-b-in up; ip link set r2-c-out up"
24sudo ip netns exec ns-segment-c ip link set veth-c up
25sudo ip netns exec ns-router-1 sysctl -w net.ipv4.ip_forward=1   # router-1 must be allowed to forward packets between its two interfaces
26sudo ip netns exec ns-router-2 sysctl -w net.ipv4.ip_forward=1   # same for router-2
27# now the routing — segment A needs a route to segment C's whole network, via router-1
28sudo ip netns exec ns-segment-a ip route add 10.203.1.0/24 via 10.201.1.1
29sudo ip netns exec ns-segment-a ip route add 10.202.1.0/24 via 10.201.1.1   # also needs a route to the transit link itself, for return traffic diagnostics later
30# router-1 needs to know how to reach segment C, via router-2
31sudo ip netns exec ns-router-1 ip route add 10.203.1.0/24 via 10.202.1.2
32# router-2 needs to know how to reach segment A, via router-1 (the return path!)
33sudo ip netns exec ns-router-2 ip route add 10.201.1.0/24 via 10.202.1.1
34# segment C needs a route back to segment A, via router-2
35sudo ip netns exec ns-segment-c ip route add 10.201.1.0/24 via 10.203.1.1
36sudo ip netns exec ns-segment-c ip route add 10.202.1.0/24 via 10.203.1.1
🟠 Note the pattern

Every single hop needed a route added in BOTH directions — this is the multi-hop equivalent of Project 2's "check both legs of the conversation." A route missing on just one router, in just one direction, breaks the whole chain even though everything else is perfect.

6Verify Baseline

bash — full end-to-end test, four hops away
1sudo ip netns exec ns-segment-a ping -c 3 10.203.1.10   # ping segment C's host from segment A — traffic must cross both routers
    3 received, 0% packet loss
2sudo ip netns exec ns-segment-a traceroute 10.203.1.10   # confirm the actual hop-by-hop path matches our intended topology
    1  10.201.1.1   (router-1)
    2  10.202.1.2   (router-2)
    3  10.203.1.10  (segment C, destination reached)
🟢 Baseline confirmed

Traffic correctly traverses both routers in order, and traceroute proves the exact path — this is our reusable, working 4-hop lab.

7Break-Fix #1 — A Missing Hop in the Middle

🔴 Break It

Remove router-2's route back to segment A — simulating a very easy mistake to make in a multi-hop chain: forgetting the RETURN route on an intermediate hop, even though the forward path is perfectly configured.

bash — on ns-router-2
1sudo ip netns exec ns-router-2 ip route del 10.201.1.0/24 via 10.202.1.1

Observe

bash — on ns-segment-a
1sudo ip netns exec ns-segment-a ping -c 3 10.203.1.10
    100% packet loss   (from the source, this looks just like total connectivity failure)

Isolate the exact hop — test FROM each intermediate router, not just the endpoints

bash — walk the chain hop by hop
1sudo ip netns exec ns-router-1 ping -c 2 10.203.1.10   # from router-1 forward to segment C — does the forward direction work?
    2 received   (forward direction is fine — the request packet CAN reach segment C)
2sudo ip netns exec ns-router-2 ip route get 10.201.1.10   # from router-2, ask: how would I route BACK to segment A?
    RTNETLINK answers: Network is unreachable   (there's our answer — no route at all)
🔵 Reading the symptom

The forward path (segment A → router-1 → router-2 → segment C) works completely fine — the ping REQUEST genuinely arrives at segment C. But segment C's reply, on its way back, hits router-2 and router-2 has no idea how to reach 10.201.1.0/24 anymore, so the reply is silently dropped. From segment A's perspective this looks identical to total failure, but it's actually a one-directional break, two hops away from the source — exactly why testing only from the endpoints would have taken much longer to isolate than testing hop by hop.

🔴 Root Cause

An intermediate router's return route was missing, breaking only the reply direction of the conversation two hops from where the symptom was observed.

bash — fix
1sudo ip netns exec ns-router-2 ip route add 10.201.1.0/24 via 10.202.1.1

8Break-Fix #2 — A Router Namespace Without ip_forward Enabled

🔴 Break It

Disable forwarding on router-1 — every interface, address, and route can be perfect, and the chain still won't work.

bash — on ns-router-1
1sudo ip netns exec ns-router-1 sysctl -w net.ipv4.ip_forward=0

Observe

bash
1sudo ip netns exec ns-segment-a ping -c 3 10.203.1.10
    100% packet loss
2sudo ip netns exec ns-segment-a ping -c 2 10.201.1.1   # can segment A even reach router-1 itself?
    2 received   (router-1's own interface is completely fine and reachable)
3sudo ip netns exec ns-router-1 sysctl net.ipv4.ip_forward   # check the specific sysctl
    net.ipv4.ip_forward = 0
🔵 Reading the symptom

router-1 is reachable on its own interface, proving the veth link and addressing are fine — but any packet trying to pass THROUGH it, rather than TO it, is silently dropped, because without ip_forward=1 the kernel refuses to forward traffic between interfaces at all, regardless of how correct the routing table looks. This is exactly the setting we've enabled by habit on every router namespace since Project 2 — this break shows you precisely what happens when it's missing.

🔴 Root Cause

The router namespace had IP forwarding disabled at the kernel level, so it refused to relay any traffic between its interfaces even though every address and route was correctly configured.

bash — fix
1sudo ip netns exec ns-router-1 sysctl -w net.ipv4.ip_forward=1
🟦 Production Best Practice

Whenever a namespace/host is supposed to act as a router but forwards nothing despite correct addressing and routes, check ip_forward before anything else — it's a single, easy-to-overlook sysctl with an all-or-nothing effect.

9Break-Fix #3 — Orphaned veth After a Namespace Is Deleted

🟠 Scenario

This one isn't about connectivity — it's about the cleanup problem mentioned in Section 2.4. Let's delete a namespace incorrectly and see what's left behind.

bash — delete segment C's namespace WITHOUT first considering its veth
1sudo ip netns delete ns-segment-c   # deletes the namespace and everything inside it, including its end of the veth pair

Observe

bash — on ns-router-2, check what happened to its side of that link
1sudo ip netns exec ns-router-2 ip link show r2-c-out
    5: r2-c-out@if4: <NO-CARRIER,BROADCAST,MULTICAST,UP> ...   (NO-CARRIER — the other end of its virtual cable is simply gone)
🔵 Reading the symptom

A veth pair is exactly two ends of one virtual cable — when you delete a namespace, the kernel automatically deletes ITS end too, since a veth end can't exist without a namespace to live in, and its automatically-deleted peer takes the interface state to NO-CARRIER on the remaining side (like unplugging one end of an Ethernet cable). This leftover NO-CARRIER interface on router-2 is now dead weight, cluttering `ip link show` output and easy to mistake for an active, working link if you're not paying attention.

🔴 Root Cause

Deleting a namespace destroys its own end of any veth pair automatically, leaving a dead, NO-CARRIER interface behind on whatever it was connected to — a cleanup detail that's easy to overlook and easy to mistake for a live link later.

bash — proper cleanup, on ns-router-2
1sudo ip netns exec ns-router-2 ip link delete r2-c-out   # explicitly remove the orphaned end too, rather than leaving it dangling
🟦 Production Best Practice

When tearing down a lab or a real namespace-based environment, always clean up BOTH ends of any veth pair deliberately, and periodically audit `ip link show` for NO-CARRIER interfaces left behind by past deletions — they're inert but confusing clutter, and in automated environments they can silently accumulate for a long time.

10Production Best Practices

🟦 Every hop needs routes in both directions

A multi-hop chain breaks completely if even one intermediate router is missing the return route.

🟦 Test from intermediate points, not just endpoints

Walking the chain hop by hop isolates the exact break far faster than only testing source-to-destination.

🟦 ip_forward is all-or-nothing per namespace

Perfect routes and addressing mean nothing if a router namespace isn't allowed to forward at all.

🟦 Clean up veth pairs deliberately

Deleting a namespace orphans the other end of any veth pair — audit for NO-CARRIER leftovers.

12Interview Preparation

ScenarioIn a multi-hop network, end-to-end connectivity fails. How do you isolate exactly which hop is broken?

I wouldn't just test from the two endpoints — I'd test connectivity from every intermediate router as well, working hop by hop in both directions. A packet can successfully reach the final destination while the REPLY fails at some point on the way back, which looks identical to total failure from the source but is actually a one-directional break partway through the chain.

Interviewer follow-up: "What's the most common cause of that kind of one-directional break?" — Answer: a missing return route on one of the intermediate routers — it's very easy to correctly configure the forward path and simply forget the route back, especially as a topology grows past two or three hops.
ConceptWhat's the difference between a named network namespace and a container's network namespace?

A named namespace, created with ip netns add, persists until explicitly deleted, even with no processes running inside it, and is referenced by name via ip netns exec. A container's namespace is tied to its main process's PID — it's created and destroyed automatically alongside that process, and you enter it with nsenter targeting that PID. Both are the same underlying kernel feature, just managed and referenced differently.

TroubleshootingA namespace meant to act as a router has correct IPs and routes on both interfaces, but nothing passes through it. What would you check?

Whether IP forwarding is enabled in that namespace — net.ipv4.ip_forward. It's a single kernel setting, off by default, and without it a namespace will refuse to relay any traffic between its interfaces no matter how correct the addressing and routing table are.
