1The Incident

We're back with the bank's real-time settlement platform. Two separate performance complaints landed on the same day. First: replication to the disaster-recovery site, which sits on a deliberately high-latency dedicated link, is nowhere near the bandwidth the network team insists is available. Second: during market-open, when thousands of connections arrive in a very short burst, some client connections are failing before the application ever logs anything about them at all.

"CPU is fine, memory is fine, the network team says the link has plenty of headroom, and the app team says their code hasn't changed. But we're not getting anywhere near the throughput we should on the DR link, and market-open connection bursts are dropping silently — no application log entry, nothing."

Both of these symptoms point past the layers we've tuned so far, into the kernel's own network stack tunables — socket buffer sizes, connection backlog limits, and congestion control behavior. These are settings most engineers never touch, which is exactly why understanding them is such high-leverage knowledge.

🔵 Why this project matters

Default kernel network tunables are chosen to work reasonably for a wide range of use cases — they are NOT tuned for high-bandwidth, high-latency links, or for absorbing large sudden connection bursts. Financial systems, replication links, and high-traffic-event workloads are exactly the scenarios where these defaults become the bottleneck, and "nothing shows up in application logs" is the signature that tells you to look at the kernel layer, not the app.

2Kernel Tuning Foundation

2.1 Bandwidth-Delay Product — why long-distance links need bigger buffers

🔵 Concept

TCP can only have a limited amount of unacknowledged data "in flight" at once — bounded by its socket buffer / window size. The theoretical maximum throughput of a connection is roughly bandwidth × round-trip-time — this is the Bandwidth-Delay Product (BDP). On a low-latency local link, even small buffers are plenty. On a high-latency link (like our bank's DR site, or any long-distance/satellite/cross-region link), the same bandwidth needs a MUCH bigger buffer to keep the pipe full — otherwise the sender runs out of "allowed in-flight data" and sits idle waiting for ACKs, capping throughput far below the link's real capacity, even with zero packet loss.

2.2 Socket buffer tunables — system caps vs auto-tuned per-connection values

🔵 Concept

net.core.rmem_max / net.core.wmem_max set the absolute system-wide ceiling any single socket's receive/send buffer can ever grow to. net.ipv4.tcp_rmem / net.ipv4.tcp_wmem are each a triplet — minimum, default, and maximum — that the kernel uses to AUTOMATICALLY size each individual TCP connection's buffer within those bounds, growing it as needed up to the maximum. If either the core max or the tcp max is too small, no amount of auto-tuning can grow a connection's buffer past that ceiling, even on a link that would benefit from a much larger one.

2.3 somaxconn and the SYN backlog — kernel-level connection queue limits

🔵 Concept

Project 12 covered an application's OWN listen() backlog. But there's a kernel-level ceiling ABOVE that: net.core.somaxconn caps the maximum backlog size the kernel will allow ANY application to request, no matter what value the app asks for — an application requesting a backlog of 1024 while somaxconn is 128 will silently be capped at 128. Separately, net.ipv4.tcp_max_syn_backlog governs how many half-open (SYN received, handshake not yet complete) connections the kernel will track at once — a burst of new connection attempts can overflow this queue before the application even gets a chance to accept() anything.

2.4 Congestion control algorithm — not all workloads want the same behavior

🔵 Concept

Project 13 covered how TCP's congestion window collapses and slowly recovers after loss — that specific behavior comes from the active congestion control algorithm, and Linux supports multiple, selectable via net.ipv4.tcp_congestion_control. The traditional default, cubic, is loss-based — it treats any packet loss as a congestion signal and backs off hard. Newer algorithms like bbr model the actual available bandwidth and round-trip time directly, and tend to perform noticeably better on links with some background loss that ISN'T actually caused by congestion (common on long-distance and wireless-adjacent links) — exactly the kind of link our DR site connection might be.

4Troubleshooting Method

  • 1. Measure actual throughput and compare against theoretical BDP for the link's bandwidth and RTT
    • ↓
  • 2. Check current socket buffer tunables: sysctl net.core.rmem_max, net.ipv4.tcp_rmem, etc.
    • ↓
  • 3. Check for kernel-level connection drops: nstat -az, specifically ListenOverflows and ListenDrops
    • ↓
  • 4. Check the current congestion control algorithm and whether it matches the link's characteristics
    • ↓
  • Change tunables deliberately, one at a time, and re-measure — never tune blind, always confirm with a real before/after number
🟠 Warning

Application logs will show NOTHING for kernel-level connection drops (somaxconn/SYN backlog overflow) — the connection never reaches the application at all. Only nstat / /proc/net/netstat counters reveal this class of failure.

7Break-Fix #1 — Throughput Capped by Small Socket Buffers (BDP)

🔴 Diagnose It

Check the current buffer tunables to see what's actually constraining us.

bash — on ns-primary, inspect the current kernel buffer settings
1sudo ip netns exec ns-primary sysctl net.ipv4.tcp_rmem   # shows the min/default/max triplet the kernel auto-tunes receive buffers within
    net.ipv4.tcp_rmem = 4096  131072  6291456   (max is only ~6MB — may not be enough for this link)
2sudo ip netns exec ns-primary sysctl net.core.rmem_max   # the absolute system-wide ceiling, above the tcp_rmem max
    net.core.rmem_max = 212992

Calculate what we actually need

🔵 Doing the BDP math

If the link's real available bandwidth is, say, 1 Gbit/s (125 MB/s) and our round-trip time is 80ms (0.08s), the bandwidth-delay product is roughly 125 MB/s × 0.08s ≈ 10 MB. To keep this pipe full, we need socket buffers that can hold at least that much unacknowledged data in flight — well above the ~6MB max we saw configured, and far above the tiny 212KB core.rmem_max ceiling.

bash — on both ns-primary and ns-dr, raise the buffer ceilings to match the BDP
1sudo ip netns exec ns-primary sysctl -w net.core.rmem_max=16777216   # raise the system-wide receive buffer ceiling to 16MB
2sudo ip netns exec ns-primary sysctl -w net.core.wmem_max=16777216   # same for the send-side ceiling
3sudo ip netns exec ns-primary sysctl -w net.ipv4.tcp_rmem="4096 131072 16777216"   # raise the auto-tuning max for receive buffers to match
4sudo ip netns exec ns-primary sysctl -w net.ipv4.tcp_wmem="4096 131072 16777216"   # same for send buffers
5sudo ip netns exec ns-dr sysctl -w net.core.rmem_max=16777216   # the receiving side needs matching headroom too — both ends matter
6sudo ip netns exec ns-dr sysctl -w net.ipv4.tcp_rmem="4096 131072 16777216"

Re-test

bash — on ns-primary
1sudo ip netns exec ns-primary iperf3 -c 10.120.1.20 -t 5
    Bitrate: substantially higher than before — the same physical link, same latency, same zero packet loss
🔵 Reading the fix

Nothing about the network path changed at all — same latency, same bandwidth, same loss rate. The ONLY thing that changed was how much unacknowledged data the kernel was willing to let a single connection have in flight at once. This is precisely why "network team says the link has plenty of headroom" and "we're not getting anywhere near that throughput" can both be true simultaneously — the link isn't the bottleneck, the buffer ceiling is.

🟦 Production Best Practice

Any high-bandwidth, high-latency link (DR replication, cross-region traffic, satellite links) needs its BDP calculated explicitly, and socket buffer maximums sized to match — on both ends of the connection, not just one.

8Break-Fix #2 — Connection Bursts Dropped by somaxconn

🔴 Break It

Set somaxconn artificially low, then simulate a market-open-style burst of near-simultaneous connection attempts.

bash — on ns-dr, simulate a too-small kernel-level backlog ceiling
1sudo ip netns exec ns-dr sysctl -w net.core.somaxconn=8   # artificially small — real production default is usually much higher (often 4096+)
2sudo ip netns exec ns-dr bash -c "cat > /tmp/burst_server.py" <<'EOF'
import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('10.120.1.20', 9600))
s.listen(1024)     # the APPLICATION asks for a large backlog...
print("listening, requested backlog 1024")
time.sleep(30)     # ...but doesn't accept() anything for 30 seconds, simulating a slow-starting app under load
EOF
3sudo ip netns exec ns-dr python3 /tmp/burst_server.py &
TokenMeaning
s.listen(1024)The application explicitly asks the kernel for a backlog of 1024 — but as covered in Section 2.3, the kernel will silently cap this at whatever net.core.somaxconn allows, here just 8.

Observe

bash — on ns-primary, fire a burst of connections quickly
1for i in $(seq 1 30); do sudo ip netns exec ns-primary bash -c "timeout 1 bash -c 'exec 3<>/dev/tcp/10.120.1.20/9600' &" ; done; wait   # 30 near-simultaneous connection attempts, well above our tiny backlog of 8
2sudo ip netns exec ns-dr nstat -az | grep -i listen   # the key diagnostic — kernel-level counters for backlog overflow events
    TcpExtListenOverflows    22    0.0   (22 connection attempts were dropped at the kernel level, before the app ever saw them)
    TcpExtListenDrops        22    0.0
🔵 Reading the symptom

Notice there is NOTHING about this in the application's own logs — from the application's point of view, these 22 connections simply never happened, because they never made it far enough to reach accept(). The only place this failure is visible at all is in the kernel's own counters. This is exactly the "connections dropping silently, no application log entry" pattern from the incident report, and nstat's ListenOverflows/ListenDrops counters are the single most direct way to prove it's happening.

🔴 Root Cause

net.core.somaxconn was capping the effective connection backlog far below what the application requested and far below what the burst of incoming connections needed, causing the kernel to silently drop excess connection attempts before the application layer was ever involved.

bash — fix
1sudo ip netns exec ns-dr sysctl -w net.core.somaxconn=4096   # raise the kernel-level ceiling to comfortably exceed expected burst sizes
2sudo ip netns exec ns-dr sysctl -w net.ipv4.tcp_max_syn_backlog=4096   # raise the half-open connection queue limit to match
🟦 Production Best Practice

Size somaxconn (and tcp_max_syn_backlog) for your worst-case burst, not your average load, and always check nstat's Listen* counters as a standard part of investigating any "connections silently fail during traffic spikes" ticket — application logs will never show this class of failure.

9Break-Fix #3 — Congestion Control Algorithm Mismatch

🟠 Scenario

Combine our high-latency DR link with a small amount of background packet loss (common on long-distance links, not necessarily a sign of congestion) and compare cubic against bbr, if your kernel has bbr available.

bash — check what's available and what's currently active
1sysctl net.ipv4.tcp_available_congestion_control   # lists which algorithms this kernel supports
2sysctl net.ipv4.tcp_congestion_control   # shows which one is currently active
🔵 Note on this section

bbr requires the kernel module to be loaded and available, which depends on your specific environment and may not be possible in every lab/sandbox setting. If it's unavailable, the commands below will show an error naming the missing algorithm — that's expected, and the concept still applies even if you can't run this specific comparison right now.

bash — on ns-primary, add light background loss alongside our existing latency
1sudo ip netns exec ns-primary tc qdisc change dev veth-primary root netem delay 40ms loss 1%   # keep the 40ms delay, add a small 1% loss rate — realistic for a long-haul link
2sudo ip netns exec ns-primary sysctl -w net.ipv4.tcp_congestion_control=cubic   # explicitly select cubic, the traditional loss-based default
3sudo ip netns exec ns-primary iperf3 -c 10.120.1.20 -t 5   # measure throughput under cubic with latency + light loss
    Bitrate: noticeably reduced — cubic interprets the 1% loss as a strong congestion signal and backs off aggressively
4sudo ip netns exec ns-primary sysctl -w net.ipv4.tcp_congestion_control=bbr   # switch to bbr, if available on this kernel
5sudo ip netns exec ns-primary iperf3 -c 10.120.1.20 -t 5   # measure throughput again, same link conditions, only the algorithm changed
    Bitrate: noticeably higher — bbr doesn't treat this level of non-congestive loss as a strong signal to back off
🔵 Reading the difference

Nothing about the physical link changed between the two tests — same latency, same loss rate. cubic's loss-based design assumes almost all loss means congestion and reacts by shrinking its congestion window hard, exactly like we saw in Project 13. On links where some baseline loss is just a normal characteristic of long-distance transmission rather than actual congestion, that assumption costs real throughput. bbr's model-based approach is far less reactive to this kind of loss, which is precisely why it's a common recommendation for exactly this kind of link.

🟦 Production Best Practice

Congestion control algorithm choice is a real, measurable performance lever for high-latency links with any non-congestive loss — but always validate with real before/after measurements on your actual link, since the "best" algorithm genuinely depends on the specific path's characteristics, not a universal rule.

10Production Best Practices

🟦 Calculate BDP before tuning buffers blindly

bandwidth × RTT tells you the real minimum buffer size needed to fill a given link.

🟦 somaxconn caps the app's own request silently

An application asking for a large backlog can still be capped hard by a small kernel-level ceiling.

🟦 Application logs won't show kernel-level connection drops

nstat's ListenOverflows/ListenDrops counters are the only place this failure is visible.

🟦 Congestion control choice matters most on lossy, high-latency links

Always measure before/after — it's not a universal "always switch to bbr" rule.

12Interview Preparation

ScenarioA high-bandwidth, high-latency replication link isn't hitting expected throughput, even though there's no packet loss. What would you check?

I'd calculate the bandwidth-delay product for the link — bandwidth times round-trip time — which tells me the minimum socket buffer size needed to keep the connection's pipe full. Then I'd check the actual configured socket buffer tunables, net.core.rmem_max/wmem_max and net.ipv4.tcp_rmem/tcp_wmem, on both ends of the connection. If the configured maximum is smaller than the calculated BDP, that's the bottleneck — the link has the bandwidth, but the kernel isn't allowing enough data in flight to use it.

Interviewer follow-up: "Why does it matter on both ends?" — Answer: the sender's send buffer and the receiver's receive buffer both need to accommodate the BDP — undersizing either end caps the achievable throughput regardless of the other end's configuration.
ConceptWhat's the difference between an application's listen() backlog and net.core.somaxconn?

The application requests a backlog size in its own listen() call, but that request is silently capped by net.core.somaxconn, a system-wide kernel ceiling the application has no control over. An application can ask for a backlog of 1024 and still effectively get far less if somaxconn is configured lower — and this cap applies system-wide, to every listening socket on the host.

TroubleshootingConnections are failing during a traffic burst, but there's nothing in the application's logs about it. What would you check?

Kernel-level connection queue drops — I'd run nstat and look specifically at ListenOverflows and ListenDrops counters. A connection that never makes it past the kernel's backlog queue never reaches the application's accept() call, so it's completely invisible to application-level logging; the kernel's own counters are the only place this shows up.
