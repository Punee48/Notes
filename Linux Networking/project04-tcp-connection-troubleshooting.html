1The Incident

We support the DevOps platform team's CI/CD infrastructure. Build agents on ci-runner-03 pull dependencies from an internal artifact registry over TCP. Two separate but related symptoms have been reported this week.

"Some build jobs just hang forever trying to reach the artifact registry — no error, they just never finish. Separately, our monitoring says ci-runner-03 is slowly running out of available file descriptors and has to be restarted every few days. Nobody can explain either one."

Both symptoms are TCP state problems in disguise. To find them, we need to stop thinking of TCP connections as "working" or "not working" and start thinking of them as a state machine — a connection is always in one specific, nameable state, and the state itself tells you exactly what's wrong.

🔵 Why this project matters

Every "hung connection," "resource exhaustion," or "connection reset" ticket you'll ever get as a Linux/DevOps engineer is really a question about which TCP state a connection is stuck in and why. Being able to read ss output and instantly know whether you're looking at a client problem, a server problem, or an application bug is one of the highest-leverage skills in this entire masterclass.

2TCP State Foundation

2.1 A TCP connection is a state machine, not a boolean

🔵 Concept

"Connected" isn't one state — it's the end result of a sequence of states the kernel walks through, and both sides of a connection track their own state independently. Every packet exchanged (SYN, SYN-ACK, ACK, FIN, RST) is a trigger that moves a connection from one state to the next. If you know the current state, you know exactly what has and hasn't happened yet.

2.2 The three-way handshake, revisited with state names

🔵 Concept

Client sends SYN, and its state becomes SYN-SENT. Server receives it, replies SYN-ACK, and its state becomes SYN-RECEIVED. Client receives the SYN-ACK, sends the final ACK, and both sides move to ESTABLISHED. A connection stuck in SYN-SENT means the client is still waiting for a SYN-ACK that never arrived — the exact symptom our CI runner is showing.

2.3 Closing a connection takes FOUR steps, not one

🔵 Concept

Unlike opening (3 steps), closing a TCP connection is a 4-way process because each side must close its own direction of the conversation independently. Side A sends FIN ("I'm done sending"), Side B acknowledges it and moves to CLOSE-WAIT — meaning "the other side is done, but I might still have data to send, and my application hasn't called close() yet." Side B eventually sends its own FIN, Side A acknowledges, and Side A enters TIME-WAIT for a cooldown period before fully closing.

2.4 CLOSE-WAIT is an application bug, not a network bug

🔵 Concept

This is one of the most important facts in this entire project: a connection sitting in CLOSE-WAIT means the remote side has already said "I'm done" (sent FIN), but OUR OWN application process has not yet called close() on its socket. It is never a network problem — a connection cannot get stuck in CLOSE-WAIT because of a firewall or routing issue. It is always, 100% of the time, a local application that forgot to close a socket.

2.5 TIME-WAIT exists on purpose — it's not a bug

🔵 Concept

After a connection fully closes on the side that initiated the close, the kernel holds it in TIME-WAIT for a cooldown period (commonly 60 seconds, tunable) to guarantee any last, delayed duplicate packets from the old connection can't be confused with a brand-new connection reusing the same ports. A moderate number of TIME-WAIT connections is completely normal and healthy. A very large, growing number usually means an application is opening huge numbers of very short-lived connections instead of reusing them.

4The Full TCP State Table

StateMeaningWho typically sees it
LISTENA socket is bound and waiting to accept new incoming connections.Server only
SYN-SENTWe sent a SYN and are waiting for a SYN-ACK reply.Client (connection initiator)
SYN-RECEIVEDWe received a SYN, replied with SYN-ACK, waiting for the final ACK.Server
ESTABLISHEDHandshake complete — normal, healthy, data-flowing state.Both sides
FIN-WAIT-1We sent a FIN (we're done sending) and are waiting for it to be acknowledged.The side that closes first

5Troubleshooting Method for TCP State Incidents

  • 1. Reproduce and immediately capture the connection's state with ss -tn state <state>
    • ↓
  • 2. SYN-SENT stuck? → suspect firewall drop / routing black hole (revisit Projects 1 & 2's method)
    • ↓
  • 3. Seeing RST via tcpdump? → something actively refused or reset the connection — check firewall REJECT rules and app crash logs
    • ↓
  • 4. Large/growing CLOSE-WAIT count? → this is always local — check which PID owns those sockets and why it isn't calling close()
    • ↓
  • 5. Large/growing TIME-WAIT count? → check for excessive short-lived connection churn; consider connection reuse/pooling
    • ↓
  • Match the exact state to the exact cause — never guess "it's probably the network" without checking ss first
🟠 Warning

CLOSE-WAIT accumulation is one of the most commonly misdiagnosed production issues — engineers often blame "the network" or "the other server," when the fix is almost always in their OWN application's connection-handling code.

We'll use a tiny Python TCP server that we can control precisely — including making it deliberately misbehave (never calling close()) to reproduce CLOSE-WAIT on demand.

bash — create the misbehaving server script on ns-registry
1sudo ip netns exec ns-registry bash -c "cat > /tmp/leaky_server.py" <<'EOF'
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('10.40.1.20', 9443))
s.listen(50)
print("listening on 9443")
conns = []
while True:
    c, addr = s.accept()
    print("accepted", addr, "- never closing it")
    conns.append(c)   # BUG: we accept but never call c.close()
EOF
TokenMeaning
s.listen(50)Sets the accept backlog to 50 — the maximum number of fully-handshaked connections the kernel will queue waiting for our application to call accept().
conns.append(c)The deliberate bug: we keep every accepted connection object alive in a list but never call .close() on it — this is exactly the pattern that leaves sockets in CLOSE-WAIT in real production code, often caused by an exception path that skips a cleanup/finally block.

8Break-Fix #1 — Stuck in SYN-SENT

🔴 Break It

Stop the registry server and add a firewall DROP rule so the SYN just disappears (same underlying cause as Project 1's firewall break, but now we read it through the TCP-state lens specifically).

bash — on ns-registry
1sudo ip netns exec ns-registry iptables -A INPUT -p tcp --dport 9443 -j DROP

Observe from the client

bash — on ns-runner, in one terminal start a connection attempt, in another watch its state
1sudo ip netns exec ns-runner curl --max-time 20 http://10.40.1.20:9443/ &
2sudo ip netns exec ns-runner ss -tn state syn-sent
    SYN-SENT 0  1  10.40.1.10:51222  10.40.1.20:9443
TokenMeaning
ss -tn state syn-sentFilters socket output to show ONLY connections currently in the SYN-SENT state — extremely useful for finding exactly which stuck connections are affecting a host during an incident.
🔵 Reading the symptom

The connection sits in SYN-SENT — the kernel is retransmitting the SYN a few times internally (visible in tcpdump as repeated SYN packets a few seconds apart, with increasing backoff) before eventually giving up. This is exactly what "build jobs just hang" looks like — the process isn't frozen, it's legitimately still waiting on a TCP handshake that will never complete.

🔴 Root Cause

A firewall rule silently dropped the SYN packet, so the handshake could never progress past its very first step.

bash — fix
1sudo ip netns exec ns-registry iptables -D INPUT -p tcp --dport 9443 -j DROP

9Break-Fix #2 — Connection Reset (RST)

🔴 Break It

Instead of DROP, use REJECT — which sends an active RST back instead of staying silent. This simulates either a firewall explicitly refusing the connection, or a server-side crash mid-handshake.

bash — on ns-registry, make sure the healthy server is stopped first
1sudo ip netns exec ns-registry iptables -A INPUT -p tcp --dport 9443 -j REJECT --reject-with tcp-reset

Observe

bash — on ns-runner
1sudo ip netns exec ns-runner curl -v http://10.40.1.20:9443/
    curl: (56) Recv failure: Connection reset by peer
2sudo ip netns exec ns-registry tcpdump -i veth-registry -nn 'tcp port 9443'
    ...Flags [S]...
    ...Flags [R.]  ← RST-ACK sent back immediately
🔵 Reading the symptom

Unlike Break #1 (silence, then timeout), this fails immediately with an explicit reset. "Connection reset by peer" always means some machine — client, server, or something in between like a firewall or load balancer — actively and deliberately terminated the connection, as opposed to the packet simply vanishing. This distinction (RST vs. silence) is one of the fastest ways to know whether to investigate a firewall DROP rule or a firewall REJECT rule / crashing service.

🔴 Root Cause

A firewall REJECT rule (or, in a real incident, potentially a crashing/restarting service) actively sent a TCP reset instead of allowing the connection.

bash — fix
1sudo ip netns exec ns-registry iptables -D INPUT -p tcp --dport 9443 -j REJECT --reject-with tcp-reset

10Break-Fix #3 — CLOSE_WAIT Accumulation (the File-Descriptor Leak)

🔴 Break It

Start our deliberately buggy leaky_server.py from Section 6, then send it several requests and close the CLIENT side each time — but the server never calls close(), so its side of each connection piles up in CLOSE-WAIT.

bash — on ns-registry
1sudo ip netns exec ns-registry python3 /tmp/leaky_server.py &
bash — on ns-runner, open and close several connections
1for i in 1 2 3 4 5; do sudo ip netns exec ns-runner bash -c "exec 3<>/dev/tcp/10.40.1.20/9443; exec 3<&-"; done

Observe

bash — on ns-registry
1sudo ip netns exec ns-registry ss -tn state close-wait
    CLOSE-WAIT  0  0  10.40.1.20:9443  10.40.1.10:51301
    CLOSE-WAIT  0  0  10.40.1.20:9443  10.40.1.10:51305
    CLOSE-WAIT  0  0  10.40.1.20:9443  10.40.1.10:51309
    ... (one per client connection, and it keeps growing)
2sudo ip netns exec ns-registry ss -tnp state close-wait
    ... users:(("python3",pid=4821,fd=7))
TokenMeaning
ss -tnp state close-waitSame filter as before, plus -p to reveal exactly which process (PID and name) owns each stuck socket — this is how you find the guilty application in a real incident with many processes running.
🔵 Reading the symptom

Every client already closed its side cleanly — but the count of CLOSE-WAIT sockets on the SERVER keeps growing with every new request, and each one holds an open file descriptor for as long as the process runs. This is precisely the "slowly running out of file descriptors" symptom from the incident report — it's a slow leak, one unclosed connection at a time, and it is 100% caused by application code on ns-registry, not by ci-runner-03, the network, or the firewall.

🔴 Root Cause

The server application accepted connections but never called close() on them after use — likely an error-handling path in real code that skips cleanup — leaving every finished connection permanently parked in CLOSE-WAIT, consuming a file descriptor forever.

🟦 Fix — this is a code fix, not a network fix

The real fix is in the application: always close sockets in a finally block (or use a context manager / connection pool with proper lifecycle handling) so a connection is closed no matter which code path finishes. For this lab, kill the leaky server and restart the healthy one from Section 7 to represent the deployed fix.

bash — stop the leaky server
1sudo ip netns exec ns-registry pkill -f leaky_server.py
🟢 Validate

Re-run ss -tn state close-wait — the list should now be empty (or non-growing) after deploying a server that properly closes its sockets.

11Break-Fix #4 — TIME-WAIT Growth from Connection Churn

🔴 Break It

Simulate a build script that opens a brand-new short-lived connection for every tiny operation instead of reusing one connection — a very common anti-pattern in scripts calling an API in a tight loop.

bash — on ns-registry, healthy server running from Section 7
1sudo ip netns exec ns-runner bash -c "for i in \$(seq 1 40); do curl -s -o /dev/null http://10.40.1.20:9443/; done"

Observe

bash — on ns-runner, immediately after
1sudo ip netns exec ns-runner ss -tn state time-wait | wc -l
    41
🔵 Reading the symptom

Each of those 40 curl calls opened a brand-new TCP connection, used it once, and closed it — leaving 40 connections parked in TIME-WAIT on the client (each holding a local ephemeral port for the cooldown period). This is harmless at small scale, but at high volume — think a build script hammering an API thousands of times per minute — TIME-WAIT entries can exhaust the available local ephemeral port range, causing brand-new connection attempts to fail with "cannot assign requested address," which looks like a totally unrelated networking failure.

🔴 Root Cause

The client script opened a new short-lived TCP connection per request instead of reusing a persistent connection, causing unnecessary TIME-WAIT churn.

🟦 Fix — connection reuse, not a kernel tweak

The durable fix is at the application level: use HTTP keep-alive / a connection pool (e.g. curl's -K reused connections, or a requests.Session() in Python, or an HTTP client with pooling) so many requests share one TCP connection instead of opening a new one each time.

bash — demonstrate connection reuse with curl
1sudo ip netns exec ns-runner curl -s -o /dev/null http://10.40.1.20:9443/ http://10.40.1.20:9443/ http://10.40.1.20:9443/
# curl automatically reuses one connection across multiple URLs to the same host in a single invocation
🟠 Note on kernel tuning

Tunables like net.ipv4.tcp_tw_reuse exist and can help in specific, well-understood cases, but reducing unnecessary connection churn at the application level is almost always the better and safer first fix — we'll cover these sysctl tunables properly in the Performance Troubleshooting phase later in this masterclass.

12Production Best Practices

🟦 Filter ss by state

ss -tn state <state> is far faster than scrolling through every connection — learn to jump straight to the state you're investigating.

🟦 CLOSE-WAIT is always your code

Never spend time blaming the network or the remote server for CLOSE-WAIT accumulation — go straight to the local process holding the socket.

🟦 RST vs silence tells you where to look

An explicit reset means something actively intervened; silence means the packet vanished — these point you toward completely different root causes.

🟦 Prefer connection reuse for high-volume clients

Scripts and services making many rapid requests to the same host should use keep-alive/pooling to avoid unnecessary TIME-WAIT churn and ephemeral port exhaustion.

🟦 Always confirm with -p

ss -tnp tells you exactly which PID owns a problem socket — essential for finding the guilty process quickly during an incident.

14Interview Preparation

ScenarioA server is slowly running out of file descriptors and you notice thousands of connections in CLOSE-WAIT. What's your diagnosis?

CLOSE-WAIT means the remote side already sent a FIN and closed their end, but our local application never called close() on its socket. It's always a local application bug, never a network issue. I'd use ss -tnp state close-wait to find exactly which process and PID owns those sockets, then look at that application's connection handling code — usually the fix is making sure sockets are closed in a finally block or equivalent so cleanup happens even on error paths.

Interviewer follow-up: "Could restarting the service fix it temporarily?" — Answer: yes, restarting releases all the leaked file descriptors immediately, but that's a mitigation, not a fix — the leak will return at the same rate until the underlying code is patched to properly close connections.
TCP/IPExplain the difference between a connection stuck in SYN-SENT versus one that receives an immediate RST.

SYN-SENT stuck means our SYN packet went out but nothing ever came back — commonly a firewall silently dropping the packet or a routing issue, and it fails slowly via timeout. An immediate RST means a machine somewhere actively refused or terminated the connection right away — commonly a firewall REJECT rule, a service that isn't listening, or an application crash mid-handshake. The key distinguishing factor is silence versus an explicit, fast response.

ConceptWhy does TCP need a four-step close instead of just closing both sides at once?

Because each direction of a TCP connection is independent — one side might be done sending but still willing to receive more data. The four-way close lets each side announce "I'm done sending" (FIN) separately, so a connection can be half-closed instead of forcing both directions to end at the exact same moment.

ProductionWhat would you check if you saw a very high number of TIME-WAIT connections on a client host?

I'd first confirm it's actually a problem and not just healthy high-volume traffic — some TIME-WAIT is completely normal. If it's growing to the point of exhausting the local ephemeral port range, I'd look at whether the application is opening a new connection per request instead of reusing connections via keep-alive or a connection pool, since that's the most common and most correct fix, rather than jumping straight to kernel-level tunables.
