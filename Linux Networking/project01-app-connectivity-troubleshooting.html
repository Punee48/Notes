1The Incident

We've just joined the Linux Infrastructure team at a mid-size e-commerce company. It's 10:14 AM. A message lands in the on-call channel:

"Checkout is down for some customers. The order-service on app-server-01 can't reach the checkout-service on app-server-02 on port 8443. App team says checkout-service is running fine locally. Network team says there's no firewall change today. Can Linux infra take a look?"

This is a completely normal Tuesday for a Linux Engineer. Nobody has given you a root cause — only symptoms, and two teams who have each already ruled themselves out. Your job is not to guess. Your job is to walk the path the traffic takes, one layer at a time, and let evidence tell you where it breaks.

🔵 Why this project matters

"Connectivity between two servers on a specific port" is the single most common Linux production ticket you will see in your career — in banking, telecom, e-commerce, and DevOps/cloud roles alike. If you master this one investigation pattern, you can apply it to almost every "X can't reach Y" incident you'll ever get paged for, including Kubernetes pods, Docker containers, and cloud load balancers later in this masterclass.

2Foundation Concepts (Just Enough to Investigate)

We are not going to memorize the OSI model today. We're going to learn exactly enough about five things — sockets, ports, the TCP handshake, routing, and the firewall — to understand where a connection attempt can die.

2.1 What is a socket, really?

🔵 Concept

On Linux, a socket is a kernel object that represents "one endpoint of a network conversation." When the checkout-service process calls bind() and listen() on port 8443, the kernel creates a listening socket and remembers: "if any TCP SYN packet arrives addressed to this IP and port 8443, hand it to this process." Without a listening socket, the kernel has nowhere to send an incoming connection — it will refuse it immediately with a TCP RST (connection refused), even if every other layer is perfect.

2.2 Ports are a promise, not a guarantee

🔵 Concept

"The application listens on 8443" is a claim made by a config file or a developer. It is not automatically true. The Linux Engineer's job is to verify the claim against the kernel's actual socket table — not against what the YAML file says, and not against what the app team believes.

2.3 The TCP three-way handshake (just enough for now)

🔵 Concept

Before any application data flows, TCP performs a handshake: the client sends SYN ("I want to connect"), the server replies SYN-ACK ("I heard you, I'm listening, go ahead"), and the client replies ACK ("confirmed, let's talk"). If you see a SYN go out and nothing ever comes back, the packet died somewhere between the client and the server's kernel — before it ever reached the application. If you see a SYN go out and an RST come back immediately, the packet reached the server's kernel, but nothing is listening on that port. This one distinction — silence vs RST — tells you which side of the investigation to focus on. We'll go much deeper into TCP states in a later project; today we only need this much.

2.4 Routing, in one sentence

🔵 Concept

Before the kernel sends a packet anywhere, it asks its routing table one question: "based on the destination IP, which interface and which next-hop should carry this packet?" If the routing table has no answer, or the wrong answer, the packet never leaves the server in the direction you expect.

2.5 The firewall, in one sentence

🔵 Concept

Linux has its own firewall inside the kernel (netfilter, configured via iptables/nftables/firewalld). Even if the packet is routed correctly and a process is listening, the kernel can still be told to silently drop or explicitly reject the packet before it reaches the socket. A firewall drop and "nothing listening" can look identical from the client side (both can hang or time out) — which is exactly why we need a layered method instead of guessing.

🟣 Architecture

Every one of these layers is a place the connection can fail — and every layer has a Linux command that lets us inspect it directly.

5The Troubleshooting Method

🟦 Production Best Practice

Never start an incident by randomly running commands. A senior Linux Engineer works outside-in and inside-out at the same time: confirm the destination is even reachable at the network layer first, then confirm something is listening, then confirm the firewall allows it, then confirm the application actually responds. This order avoids the classic junior mistake of spending 20 minutes reading application logs when the real problem is a missing route.

  • 1. Can I resolve/confirm the destination IP? (DNS, if hostname used)
    • ↓
  • 2. Does a route exist to the destination from this server?
    • ↓
  • 3. Is the destination reachable at the network layer (ping/traceroute)?
    • ↓
  • 4. Does the TCP handshake complete on the target port? (nc / curl)
    • ↓
  • If SYN gets no reply at all → suspect firewall drop or routing black hole
  • If SYN gets an immediate RST → nothing is listening on that port
  • If handshake completes → problem is in the application layer, not networking
🟠 Warning

"Ping works" only proves ICMP is allowed and routing exists. It proves nothing about whether TCP port 8443 is reachable — many production firewalls allow ICMP but block specific TCP ports. Don't stop investigating just because ping succeeded.

6Hands-On Lab Setup

You can reproduce this entire incident on a single laptop using Linux network namespaces — no cloud account and no second VM required. A network namespace gives you an isolated, private copy of the Linux network stack (its own interfaces, routing table, and firewall rules) inside your one machine, connected to another namespace by a virtual cable. This is the same underlying mechanism containers use — which is a nice preview of Phase 13 later in this masterclass.

Option A — Recommended

1 Ubuntu 22.04/24.04 or RHEL/Rocky 9 VM (1 vCPU, 1GB RAM is enough) with root/sudo access. We'll build two namespaces inside it: ns-order and ns-checkout.

Option B — Two VMs

If you prefer real separate hosts (closer to production), spin up two small VMs (VirtualBox, or free-tier cloud) on the same private network, named app-server-01 and app-server-02.

The rest of this project shows Option A commands (namespaces). If you're using Option B, every command is identical except you drop the ip netns exec ns-xxx prefix and simply run commands directly on each VM.

6.1 Build the two namespaces and connect them

bash — run as root or with sudo
1sudo ip netns add ns-order
2sudo ip netns add ns-checkout
3sudo ip link add veth-order type veth peer name veth-checkout
4sudo ip link set veth-order netns ns-order
5sudo ip link set veth-checkout netns ns-checkout
6sudo ip netns exec ns-order ip addr add 10.10.1.20/24 dev veth-order
7sudo ip netns exec ns-checkout ip addr add 10.10.2.45/24 dev veth-checkout
8sudo ip netns exec ns-order ip link set veth-order up
9sudo ip netns exec ns-checkout ip link set veth-checkout up
10sudo ip netns exec ns-order ip link set lo up
11sudo ip netns exec ns-checkout ip link set lo up
Word-by-word breakdown of this lab setup (click to expand)
TokenMeaning
ip netns add ns-orderCreates a new, isolated network namespace named ns-order — it gets its own loopback, its own routing table, its own firewall rule set, completely separate from the host and from ns-checkout.
ip link add veth-order type veth peer name veth-checkoutCreates a veth pair — think of it as a virtual patch cable with two ends. Whatever goes in one end comes out the other. This is how two isolated namespaces get network connectivity to each other.
ip link set veth-order netns ns-orderMoves one end of the virtual cable into the ns-order namespace, like plugging that end of the cable into that "room."
ip netns exec ns-order <command>Runs <command> as if you were inside the ns-order namespace — this is how we configure and troubleshoot each "server" separately from our one physical machine.
ip addr add 10.10.1.20/24 dev veth-orderAssigns the IP address 10.10.1.20 with a /24 subnet mask to the veth-order interface inside ns-order — this becomes our simulated app-server-01.
ip link set veth-order upBrings the interface to the UP administrative state — an interface that's DOWN cannot send or receive any traffic, regardless of IP configuration.
ip link set lo upBrings up the loopback interface inside the namespace — many applications and tools implicitly rely on loopback being up even in a minimal namespace.

6.2 Validate the lab network is up

bash
1sudo ip netns exec ns-order ip addr show veth-order
    inet 10.10.1.20/24 scope global veth-order
2sudo ip netns exec ns-order ping -c 2 10.10.2.45
    2 packets transmitted, 2 received, 0% packet loss
🟢 Validation

If ping succeeds here, our "network cable" and IP addressing are healthy. This gives us a known-good baseline before we intentionally introduce failures later.

7Build the Checkout Application

We don't need a real e-commerce app to reproduce this incident — we just need a process that listens on TCP 8443 the same way checkout-service would. ncat (from the nmap package) is perfect for this; it's what many senior engineers use to simulate an application quickly during a real incident, too.

bash — on ns-checkout ("app-server-02")
1# install a minimal netcat-style listener if not already present
2sudo ip netns exec ns-checkout bash -c "which nc || apt install -y netcat-openbsd"
3# start checkout-service listening on 8443
4sudo ip netns exec ns-checkout nc -lk 10.10.2.45 8443
TokenMeaning
ncnetcat — a small utility that can open TCP/UDP connections or listen on a port, standing in for our checkout-service.
-lListen mode — turns nc into a server instead of a client.
-kKeep listening after a client disconnects, instead of exiting after one connection (so we can test repeatedly).
10.10.2.45 8443Bind address and port — exactly what checkout-service is expected to bind to in production.
🟠 Note

Leave this command running in its own terminal/tab — it represents checkout-service actively running. Open a second terminal for the remaining steps.

8Verify the Baseline Works

bash — on ns-order ("app-server-01"), second terminal
1sudo ip netns exec ns-order nc -zv 10.10.2.45 8443
    Connection to 10.10.2.45 8443 port [tcp/*] succeeded!
TokenMeaning
ncnetcat again, now used as a client instead of a listener.
-zZero-I/O mode — just attempt the TCP handshake and report success/failure, don't send any data. This is exactly what we want for a connectivity check.
-vVerbose — print the result instead of staying silent.
10.10.2.45 8443Target IP and port we are testing — this simulates order-service's outbound call to checkout-service.
🟢 Validation

"Succeeded" means the full three-way handshake completed: SYN → SYN-ACK → ACK. This is our healthy baseline. Now we deliberately break it, one failure mode at a time, and practice diagnosing each one using only the evidence the system gives us — exactly like a real incident.

9Break-Fix #1 — Application Not Listening

🔴 Break It

Go to the ns-checkout terminal and press Ctrl+C to kill the nc listener. checkout-service is now down, but everything else (network, routing, firewall) is untouched.

Observe

bash — on ns-order
1sudo ip netns exec ns-order nc -zv 10.10.2.45 8443
    nc: connect to 10.10.2.45 port 8443 (tcp) failed: Connection refused
🔵 Reading the symptom

"Connection refused" is a very specific message. It means our SYN packet reached app-server-02's kernel, the kernel checked its socket table, found nobody listening on port 8443, and sent back a TCP RST immediately. This already tells us: routing works, the firewall (if any) allowed it, and the problem is 100% on app-server-02, at the application layer.

Troubleshoot on the server side

bash — on ns-checkout
1sudo ip netns exec ns-checkout ss -tlnp
    State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port
    (no line for 10.10.2.45:8443 — nothing is listening)
TokenMeaning
ssSocket Statistics — the modern replacement for netstat, reads socket info directly from the kernel.
-tShow TCP sockets only (we don't care about UDP for this check).
-lShow listening sockets only — the ones that can accept new incoming connections.
-nNumeric — show raw IPs/ports instead of resolving them to names, which is both faster and avoids DNS masking the real address.
-pShow the process (PID and name) that owns each socket, when we have permission — critical for confirming which app, if any, owns a port.

Root cause & fix

🔴 Root Cause

checkout-service process was not running — it had stopped (in production, this could be a crash, an OOM-kill, a failed deployment, or someone forgetting to restart it after maintenance).

bash — fix: restart the listener
1sudo ip netns exec ns-checkout nc -lk 10.10.2.45 8443
🟢 Validate

Re-run ss -tlnp on ns-checkout — it should now show a LISTEN entry for :8443. Re-run nc -zv from ns-order — it should now succeed.

10Break-Fix #2 — Application Listening on the Wrong Port/Interface

🔴 Break It

Restart checkout-service, but this time bind it to the wrong port on purpose — 8080 instead of 8443.

bash — on ns-checkout
1sudo ip netns exec ns-checkout nc -lk 10.10.2.45 8080

Observe

bash — on ns-order
1sudo ip netns exec ns-order nc -zv 10.10.2.45 8443
    Connection refused
2sudo ip netns exec ns-order nc -zv 10.10.2.45 8080
    succeeded!
🔵 Reading the symptom

The same "connection refused" message as break #1 — but this time the process IS running. This is exactly why we never assume "an app is running" means "an app is reachable on the port people expect." A process running on the wrong port produces the identical client-side symptom as a process not running at all. The only way to tell them apart is to check the server's actual socket table.

bash — on ns-checkout, confirm with ss
1sudo ip netns exec ns-checkout ss -tlnp
    LISTEN  0  1  10.10.2.45:8080   0.0.0.0:*   users:(("nc",pid=...))
🔴 Root Cause

A misconfigured startup parameter (wrong port in a config file, environment variable, or launch command) caused checkout-service to bind 8080 instead of the documented 8443.

🟢 Fix & Validate

Correct the port in the app's configuration and restart it bound to 8443, then re-run ss -tlnp and nc -zv to confirm.

11Break-Fix #3 — Firewall Blocking the Port

🔴 Break It

Make sure checkout-service is correctly listening on 8443 again (undo break #1/#2 first). Now add a firewall rule on ns-checkout that drops inbound traffic to 8443.

bash — on ns-checkout
1sudo ip netns exec ns-checkout nc -lk 10.10.2.45 8443 &
2sudo ip netns exec ns-checkout iptables -A INPUT -p tcp --dport 8443 -j DROP
TokenMeaning
iptablesThe classic Linux firewall configuration tool that programs netfilter rules in the kernel.
-A INPUTAppend this rule to the INPUT chain — the chain that evaluates traffic destined for this host itself (as opposed to FORWARD, which handles traffic passing through).
-p tcpMatch only TCP protocol packets.
--dport 8443Match only packets whose destination port is 8443.
-j DROPJump to the DROP target — silently discard the packet with no response sent back at all (as opposed to REJECT, which would send back an explicit refusal).

Observe

bash — on ns-order
1sudo ip netns exec ns-order nc -zv -w 3 10.10.2.45 8443
    (hangs for 3 seconds, then) nc: connect to 10.10.2.45 port 8443 timed out
🔵 Reading the symptom — the key distinction

This is completely different from break #1/#2. There is no "connection refused" — there is silence, followed by a timeout. Silence means the SYN packet was thrown away somewhere and nobody ever replied — the classic signature of a firewall DROP rule (or a routing black hole, which we'll test next). This is why the difference between "refused instantly" and "times out slowly" is one of the most important signals in all of Linux network troubleshooting.

Confirm with a packet capture

bash — on ns-checkout, capture while ns-order tries to connect
1sudo ip netns exec ns-checkout tcpdump -i veth-checkout -nn 'tcp port 8443'
    10.10.1.20.51234 > 10.10.2.45.8443: Flags [S], seq 123456
    (no SYN-ACK, no RST ever follows — SYN arrived but got no reply)
TokenMeaning
tcpdumpCaptures raw packets seen by a network interface.
-i veth-checkoutCapture on this specific interface only.
-nnDon't resolve hostnames or port names — show raw numeric IPs and ports, which is faster and avoids DNS lookups interfering with the capture.
'tcp port 8443'Berkeley Packet Filter (BPF) expression — capture only TCP traffic on port 8443, filtering out noise.
Flags [S]S = SYN flag — this is the very first packet of the handshake.
🔴 Root Cause

The SYN packet successfully arrived at app-server-02's NIC (we can see it in the capture), which proves routing was fine — but an iptables DROP rule on the INPUT chain silently discarded it before it could ever reach the listening socket, so no SYN-ACK was ever sent.

bash — fix: remove the block
1sudo ip netns exec ns-checkout iptables -D INPUT -p tcp --dport 8443 -j DROP
🟢 Validate

-D deletes the matching rule (mirrors the -A we used to add it). Re-run the nc test from ns-order — it should now succeed immediately, no more hang.

12Break-Fix #4 — Wrong Route

🔴 Break It

On ns-order, add a bogus static route that sends 10.10.2.0/24 traffic toward a next-hop that doesn't exist.

bash — on ns-order
1sudo ip netns exec ns-order ip route add 10.10.2.0/24 via 10.10.1.99
TokenMeaning
ip route addAdds a new entry to the kernel routing table.
10.10.2.0/24The destination network this route applies to — checkout-service's subnet.
via 10.10.1.99The next-hop gateway to send matching traffic to — here, an address that doesn't actually exist on our segment, simulating a bad static route entry (very common after a manual network change or a misapplied config management run).

Observe

bash — on ns-order
1sudo ip netns exec ns-order ip route get 10.10.2.45
    10.10.2.45 via 10.10.1.99 dev veth-order
2sudo ip netns exec ns-order ping -c 2 10.10.2.45
    Destination Host Unreachable
TokenMeaning
ip route get 10.10.2.45Asks the kernel to actually run its route-selection logic for this one destination and print the result — the single best command to answer "which path will the kernel actually choose?" before you send a single packet.
🔵 Reading the symptom

"Destination Host Unreachable" here is generated locally by our own kernel or the segment's ARP resolution failing — because 10.10.1.99 doesn't exist to forward to. This is a different failure signature again: it fails immediately and locally, before the packet ever leaves in a meaningful direction, and it fails identically for ANY destination in that /24 — a strong clue that the problem is routing, not this one host.

🔴 Root Cause

An incorrect static route was pointing traffic for checkout-service's subnet at a non-existent gateway.

bash — fix: remove the bad route
1sudo ip netns exec ns-order ip route del 10.10.2.0/24 via 10.10.1.99
🟢 Validate

Re-run ip route get 10.10.2.45 — it should now resolve via the correct directly-connected interface, and ping/nc should succeed again.

13Break-Fix #5 — DNS Failure (Works by IP, Fails by Hostname)

🔴 Break It

In production, order-service almost never hardcodes an IP — it connects to checkout-service.internal. Let's simulate a broken internal DNS entry by adding a wrong mapping to /etc/hosts on ns-order.

bash — on ns-order
1sudo ip netns exec ns-order bash -c "echo '10.10.2.99 checkout-service.internal' >> /etc/hosts"

Observe

bash — on ns-order
1sudo ip netns exec ns-order getent hosts checkout-service.internal
    10.10.2.99  checkout-service.internal
2sudo ip netns exec ns-order nc -zv checkout-service.internal 8443
    Connection to 10.10.2.99 8443 failed: No route to host / timed out
3sudo ip netns exec ns-order nc -zv 10.10.2.45 8443
    succeeded!
TokenMeaning
getent hosts <name>Asks the C library's standard name resolution path (the same one nearly every application uses) to resolve a hostname — checking /etc/hosts, then DNS, according to /etc/nsswitch.conf. This is the single most reliable way to see exactly what an application will see when it resolves a name, because it goes through the real resolution path instead of a tool with its own resolver logic.
🔵 Reading the symptom — the classic "works by IP, fails by hostname"

This is one of the most common enterprise tickets that exists: "the application works when I connect by IP, but fails when I connect by hostname." The moment you hear this sentence, your instinct should immediately go to DNS or /etc/hosts — not the firewall, not routing, not the application. We just proved it directly: the correct IP (10.10.2.45) connects fine; the hostname resolves to the WRONG IP (10.10.2.99), and that's the actual server we can't reach.

🔴 Root Cause

A stale or manually-mistyped entry in /etc/hosts (or, in real production, a stale internal DNS A record) pointed checkout-service.internal at the wrong IP address.

bash — fix
1sudo ip netns exec ns-order sed -i '/checkout-service.internal/d' /etc/hosts
2sudo ip netns exec ns-order bash -c "echo '10.10.2.45 checkout-service.internal' >> /etc/hosts"
🟢 Validate

Re-run getent hosts checkout-service.internal — confirm it now returns 10.10.2.45 — then re-run the nc test by hostname.

14Production Best Practices

🟦 Verify, don't trust

Never accept "the app is running" or "the firewall is fine" as fact from another team without confirming it yourself against the kernel's actual state (ss, iptables -L, ip route).

🟦 Layer by layer

Always work outward from routing → reachability → handshake → application, in that order. It's the fastest way to eliminate whole categories of causes quickly.

🟦 Learn the symptom language

"Connection refused" = nothing listening. "Timed out / silence" = firewall drop or routing black hole. "Works by IP, fails by hostname" = DNS/hosts file. Recognizing these instantly saves hours.

🟦 Capture before you change

Where possible, take a tcpdump capture of the failure before making any fix — it's often the only definitive evidence of what actually happened, and it protects you if the root cause is disputed later.

🟦 Change one thing at a time

In this project we broke and fixed one variable per test. Do the same in real incidents — changing routing and firewall rules simultaneously makes it impossible to know which fix actually worked.

16Interview Preparation

ScenarioAn application can't connect to another server on a specific port. Walk me through your troubleshooting approach.

I'd work layer by layer instead of guessing. First I'd confirm whether a hostname is involved and resolve it with getent hosts to rule out DNS. Then I'd check ip route get to the destination to confirm the server even knows how to reach that network. Next I'd test the actual port with nc -zv rather than just ping, since ping only proves ICMP works. If the connection is refused instantly, I know nothing is listening — I'd check with ss -tlnp on the target. If it hangs and times out instead, I'd suspect a firewall drop or bad route, and I'd confirm with a packet capture on the target's interface to see whether the SYN even arrived.

Interviewer follow-up: "How do you tell a firewall drop apart from a routing problem?" — Answer: a routing failure usually fails immediately and locally (Destination Host Unreachable), and fails for the whole destination subnet, not just one host. A firewall drop lets the packet leave and travel across the network, but never gets a reply — which I can only confirm by capturing traffic on the destination side and seeing the SYN arrive with no SYN-ACK.
TCP/IPWhat's the difference between "connection refused" and a connection that times out?

Connection refused means the SYN packet reached the destination kernel, found no listening socket on that port, and the kernel replied instantly with a TCP RST. A timeout means either the SYN packet never got a reply at all — commonly because a firewall silently dropped it, or a route sent it nowhere useful — so the client just keeps waiting until it gives up.

TroubleshootingAn application works when you connect using the IP address but fails when you use the hostname. What would you check first?

That's almost always a DNS or /etc/hosts problem, not a network or firewall issue, because the successful IP-based connection already proves routing, firewall, and the listening socket are all fine. I'd run getent hosts on the hostname to see exactly what IP the application's own resolution path returns, and compare that against the correct IP.

Manager RoundTell me about a connectivity issue you diagnosed and how you communicated it to other teams.

I'd describe using a namespace-based lab to reproduce a checkout-service unreachable-on-port-8443 style incident, walking layer by layer from DNS through routing, firewall, and the socket table rather than guessing, and how identifying the exact failure signature (refused vs. timeout vs. DNS mismatch) let me hand the right team — app, network, or DNS — a specific, evidence-backed root cause instead of a vague "it's not working."
