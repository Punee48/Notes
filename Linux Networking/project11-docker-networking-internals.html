2Docker Networking Foundation

2.1 A container is a network namespace (plus more)

🔵 Concept

From a pure networking standpoint, a Docker container is exactly what we've been calling ns-something throughout this entire masterclass — a network namespace with its own interfaces, routing table, and iptables rules, isolated from the host and other containers. Docker just creates and manages that namespace for you automatically instead of you typing ip netns add.

2.2 docker0 is a Linux bridge — literally, exactly like Project 10

🔵 Concept

By default, Docker creates a bridge device named docker0 (you can see it with plain ip link show on any Docker host) and gives it an address like 172.17.0.1/16. Every container on the default network gets a veth pair, exactly like we built by hand in Project 10 — one end stays on the host attached to docker0, the other end is moved into the container's network namespace and typically renamed eth0 inside the container.

2.3 Publishing a port (-p) is a DNAT rule — literally, exactly like Project 8

🔵 Concept

When you run docker run -p 8080:80 nginx, Docker adds an iptables rule to a chain it manages (named DOCKER) in the nat table's PREROUTING chain: traffic arriving on the host's port 8080 gets DNAT'd to the container's internal IP on port 80 — precisely the pattern we built by hand for the settlement API in Project 8. Docker also adds the matching FORWARD allow rule and a MASQUERADE rule for the container's outbound traffic, automating exactly the rule PAIRS we had to remember to add ourselves in that project.

2.4 Container-to-container name resolution depends on WHICH network you use

🔵 Concept

Docker's DEFAULT bridge network (the one named "bridge", auto-created) does NOT provide automatic DNS resolution between containers by name — only user-defined bridge networks (created with docker network create) get Docker's embedded DNS server, letting containers reach each other by container name instead of only by IP. This single fact explains an enormous number of "why can't my containers find each other" tickets.

5Build "Docker" by Hand

🐳 Note on this lab

If you have real Docker installed, run the equivalent docker commands shown alongside each step and compare — ip link show, iptables -t nat -L DOCKER -n -v, and docker network inspect bridge will show you the real thing. This lab rebuilds the same mechanism manually with tools you already know, so it works everywhere and makes the internals explicit.

bash — build our own "docker0"-equivalent bridge and two "containers"
1sudo ip netns add ns-dockerhost
2sudo ip netns exec ns-dockerhost ip link add docker0-lab type bridge
3sudo ip netns exec ns-dockerhost ip addr add 172.17.0.1/16 dev docker0-lab
4sudo ip netns exec ns-dockerhost ip link set docker0-lab up
5sudo ip netns exec ns-dockerhost sysctl -w net.ipv4.ip_forward=1
6# "container" 1: nginx-like web container
7sudo ip netns add ns-web-container
8sudo ip link add veth-web type veth peer name veth-web-br
9sudo ip link set veth-web netns ns-web-container
10sudo ip link set veth-web-br netns ns-dockerhost
11sudo ip netns exec ns-dockerhost ip link set veth-web-br master docker0-lab
12sudo ip netns exec ns-dockerhost ip link set veth-web-br up
13sudo ip netns exec ns-web-container bash -c "ip addr add 172.17.0.2/16 dev veth-web; ip link set veth-web up; ip link set lo up; ip route add default via 172.17.0.1"
14sudo ip netns exec ns-web-container python3 -m http.server 80 --bind 172.17.0.2 &
Our Manual StepReal Docker Equivalent
ip link add docker0-lab type bridgeAutomatically created the first time the Docker daemon starts, named docker0
ip netns add ns-web-containerAutomatically created by docker run — you never see the namespace name directly, but docker inspect <container> --format '{{.State.Pid}}' lets you find and enter it manually
veth pair + master docker0-labAutomatically created and attached for you as part of container startup on the default bridge network

5.1 Publish a port — the manual DNAT equivalent of "-p"

bash — on ns-dockerhost, simulate `docker run -p 8080:80 nginx`
1sudo ip netns exec ns-dockerhost iptables -t nat -N DOCKER-LAB
2sudo ip netns exec ns-dockerhost iptables -t nat -A PREROUTING -m addrtype --dst-type LOCAL -j DOCKER-LAB
3sudo ip netns exec ns-dockerhost iptables -t nat -A DOCKER-LAB -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
4sudo ip netns exec ns-dockerhost iptables -A FORWARD -d 172.17.0.2 -p tcp --dport 80 -j ACCEPT
5sudo ip netns exec ns-dockerhost iptables -t nat -A POSTROUTING -s 172.17.0.0/16 -j MASQUERADE
TokenMeaning
-N DOCKER-LABCreates a new, separate chain — real Docker does exactly this with a chain literally named DOCKER, keeping its auto-managed rules cleanly separated from any rules you add yourself.
-m addrtype --dst-type LOCAL -j DOCKER-LABJumps to our custom chain only for traffic destined to a LOCAL address (i.e., the host itself) — this is exactly the pattern real Docker uses to hand off port-published traffic to its own management chain.
DNAT --to-destination 172.17.0.2:80The exact same DNAT concept from Project 8 — rewrite host:8080 traffic to the container's real internal address and port.

6Verify the Baseline

bash — simulate an external client reaching the published port
1sudo ip netns exec ns-dockerhost curl -s -o /dev/null -w "%{http_code}\n" http://172.17.0.1:8080/
    200
🟢 Validation

Traffic to the "host's" published port 8080 correctly reaches the container's nginx-equivalent on port 80 — this is our working baseline, and it's mechanically identical to what docker port <container> would show you on a real Docker host.

7Break-Fix #1 — Published Port, but Nothing Listening Inside

🔴 Break It

Kill the "container's" web server, simulating an application crash inside a container while the container itself (namespace) stays running.

bash
1sudo ip netns exec ns-web-container pkill -f "http.server 80"

Observe

bash
1sudo ip netns exec ns-dockerhost curl --max-time 3 http://172.17.0.1:8080/
    curl: (56) Recv failure: Connection reset by peer
2sudo ip netns exec ns-web-container ss -tlnp
    (empty — nothing listening on port 80 anymore)
🔵 Reading the symptom

This is Project 1's very first lesson, now applied one layer deeper: the DNAT translation happens correctly (you'd see the counter incrementing on the DNAT rule), but once the packet arrives inside the container's namespace, there's nobody home. On a real Docker host, this looks like "the published port doesn't work" but the real cause is entirely inside the container — check the application/process, not Docker's networking, first.

🔴 Root Cause

The application inside the container crashed or stopped, so nothing was listening on the port the DNAT rule was correctly forwarding to.

bash — fix
1sudo ip netns exec ns-web-container python3 -m http.server 80 --bind 172.17.0.2 &
🟦 Production Best Practice

On real Docker, docker logs <container> and docker exec <container> ss -tlnp are your equivalent first checks — always confirm the process inside the container before assuming Docker's networking is at fault.

8Break-Fix #2 — Container-to-Container "DNS" Fails on the Default Bridge

🔴 Break It

Add a second "container" (an app server) on the same bridge, and try to reach the web container BY NAME rather than by IP — exactly like an application configured with a hostname instead of a hardcoded address.

bash — add a second container
1sudo ip netns add ns-app-container
2sudo ip link add veth-app type veth peer name veth-app-br
3sudo ip link set veth-app netns ns-app-container
4sudo ip link set veth-app-br netns ns-dockerhost
5sudo ip netns exec ns-dockerhost bash -c "ip link set veth-app-br master docker0-lab; ip link set veth-app-br up"
6sudo ip netns exec ns-app-container bash -c "ip addr add 172.17.0.3/16 dev veth-app; ip link set veth-app up; ip link set lo up"

Observe

bash — on ns-app-container, try reaching the web container by NAME (like a real container would use)
1sudo ip netns exec ns-app-container curl --max-time 3 http://web-container/
    curl: (6) Could not resolve host: web-container
2sudo ip netns exec ns-app-container curl -s -o /dev/null -w "%{http_code}\n" http://172.17.0.2/
    200
🔵 Reading the symptom

By IP, everything works perfectly — the bridge, veths, and connectivity are all fine. By NAME, resolution fails outright, exactly matching Section 2.4's warning: the default bridge network provides NO automatic name-to-IP resolution between containers. This is one of the single most common real-world Docker networking complaints, and it's not a bug — the default bridge was simply never designed to include an embedded DNS server; only user-defined networks (created with docker network create) get that feature.

🔴 Root Cause

The containers were using Docker's default bridge network, which does not provide automatic container-name DNS resolution, causing hostname-based connections to fail while IP-based connections succeeded.

🟦 Fix — on real Docker, use a user-defined network

The real fix isn't a networking patch — it's using the right kind of network: docker network create my-app-net, then run both containers with --network my-app-net instead of the default bridge. Docker's embedded DNS then resolves container names automatically. In our manual lab, this is equivalent to standing up a small DNS server (as we did with dnsmasq in Project 3) serving the bridge segment — which is genuinely close to what Docker does internally.

9Break-Fix #3 — Missing Outbound MASQUERADE

🔴 Break It

Remove the MASQUERADE rule, simulating a custom iptables cleanup script that accidentally flushed Docker's own NAT rules — a genuinely common real-world incident when other automation touches iptables without care.

bash
1sudo ip netns exec ns-dockerhost iptables -t nat -D POSTROUTING -s 172.17.0.0/16 -j MASQUERADE

Observe

🔵 Reading the symptom

This reproduces Break-Fix #1 from Project 8 exactly, in a Docker context: containers can reach each other on the bridge fine (that's pure L2/L3 connectivity, unaffected), but any container trying to reach the internet or another external network will fail, because its private 172.17.x.x source address leaks out untranslated and external hosts have no route back to it. This is precisely why real Docker installs a MASQUERADE rule for its whole subnet automatically — without it, containers would be isolated from everything except the bridge and the host.

🔴 Root Cause

The MASQUERADE rule for the container subnet was missing, so container-originated traffic leaving toward external networks kept its private, non-routable source address.

bash — fix
1sudo ip netns exec ns-dockerhost iptables -t nat -A POSTROUTING -s 172.17.0.0/16 -j MASQUERADE
🟦 Production Best Practice

Never run generic iptables "cleanup" or "flush all rules" scripts on a Docker host without accounting for the rules Docker itself manages — this is a well-known, recurring category of self-inflicted outage. Docker actually re-adds its own rules on daemon restart specifically because other tooling sometimes wipes them.

10Break-Fix #4 — Host Port Already in Use

🔴 Break It

Simulate another process already bound to the host port you're trying to publish a container on — a very common "works on one host, fails on another" issue.

bash — on ns-dockerhost, something else grabs port 8080 first
1sudo ip netns exec ns-dockerhost python3 -m http.server 8080 --bind 172.17.0.1 &
2# now imagine trying to "docker run -p 8080:80" a second time on this host

Observe

bash
1sudo ip netns exec ns-dockerhost ss -tlnp | grep 8080
    LISTEN 0 5 172.17.0.1:8080 ... users:(("python3",pid=...))
Real Docker error you'd seeMeaning
Error starting userland proxy: listen tcp 0.0.0.0:8080: bind: address already in useDocker's own port-publishing mechanism (a small "userland proxy" process, plus the DNAT rule) can't bind to a host port that's already claimed by something else — this is a straightforward, ordinary "port already in use" condition, no different from any other Linux service failing to bind a busy port.
🔵 Reading the symptom

This isn't really a "Docker networking" problem at all — it's the exact same port-conflict situation any two ordinary Linux processes would have trying to bind the same port. The Docker-specific part is only that the error message comes from Docker's startup process instead of a generic "bind" failure, which can make it feel more mysterious than it is.

🔴 Root Cause

Another process was already bound to the host port the new container tried to publish on.

bash — fix: identify and free the port, or choose a different one
1sudo ip netns exec ns-dockerhost pkill -f "http.server 8080"
🟦 Production Best Practice

Before publishing a port, check ss -tlnp on the host for existing binders — this is ordinary Linux port-conflict triage (same skill from Project 1), Docker doesn't change the fundamentals at all.

11Production Best Practices

🟦 Translate Docker terms to primitives

Container = namespace, published port = DNAT rule, container network = bridge — every tool from earlier projects still applies.

🟦 Check inside the container first

A working DNAT rule with nothing listening inside looks identical from outside to a broken DNAT rule — verify the process, not just the network.

🟦 Default bridge ≠ user-defined bridge for DNS

Container-name resolution only works on user-defined networks — this single fact resolves a huge share of "containers can't find each other" tickets.

🟦 Don't blindly flush iptables on Docker hosts

Generic rule-cleanup scripts can silently break every published port and all outbound container traffic by removing Docker's managed rules.

🟦 Port conflicts are ordinary Linux port conflicts

"Address already in use" from Docker is the same bind() failure any two processes would have — check ss -tlnp on the host.

14Interview Preparation

ScenarioA container's published port isn't reachable from outside. How do you troubleshoot it?

I'd break it into the same layers I'd use for any Linux networking issue. First, inside the container, is anything actually listening on the expected port — docker exec and ss -tlnp. If yes, I'd check the DNAT rule Docker manages in the nat table's DOCKER chain to confirm it's translating to the right container IP and port. If that's correct too, I'd check the FORWARD chain allows traffic to that container IP, since Docker manages that too but it can still be affected by other firewall rules or automation on the host.

Interviewer follow-up: "What if it worked yesterday and broke today with no deployment?" — Answer: I'd suspect something external modified iptables — a cleanup script, a security tool, or manual intervention that flushed or altered Docker's managed NAT/filter rules — since Docker doesn't typically change its own rules without a container lifecycle event.
ConceptWhy can't my containers reach each other by name on Docker's default bridge network?

Docker's default bridge network doesn't run an embedded DNS server for container name resolution — that feature only exists on user-defined networks created with docker network create. On the default bridge, containers can only reach each other by IP address unless you switch to a user-defined network.

ConceptWhat actually happens when you run docker run -p 8080:80 nginx?

Docker creates a network namespace for the container, attaches a veth pair to it with one end on the docker0 bridge, assigns the container an internal IP, and adds an iptables DNAT rule in its own DOCKER chain so traffic to the host's port 8080 gets rewritten to the container's internal IP on port 80 — plus a FORWARD rule allowing that traffic and a MASQUERADE rule for the container's outbound connections. It's the same namespace, bridge, and NAT mechanisms available in plain Linux, just automated.

ProductionWhy should you be careful running generic iptables cleanup or flush scripts on a Docker host?

Docker manages its own iptables rules — DNAT for published ports, FORWARD rules for container traffic, and MASQUERADE for outbound connectivity — in its own chains. A generic flush can wipe those out, silently breaking every published port and all container internet access at once, without any container itself actually changing or restarting.
