1The Task

The platform team is finally migrating their product-catalog and checkout services from Docker Compose to Kubernetes. Before anyone runs a single kubectl apply in production, our manager wants the Linux infra team able to explain what's actually happening on the wire — not just recite Kubernetes vocabulary.

"When someone says 'the pod can't reach the service' or 'DNS isn't resolving inside the cluster,' I want us thinking in terms of bridges, iptables rules, and namespaces — the same way we'd debug anything else — not just restarting the pod and hoping."

Here's the reassuring part: we've already built almost every piece. A pod is a network namespace (Project 1). The node's pod network is a bridge (Project 10). A Service is a load-balanced virtual IP backed by real pod IPs, implemented with either iptables DNAT rules (Project 7/8) or IPVS (Project 15). Cluster DNS is just DNS (Project 3), scoped to a cluster-specific naming convention. Kubernetes automates and orchestrates these pieces at scale — it doesn't invent new networking physics.

🔵 Why this project matters

An enormous share of real-world Kubernetes networking tickets — "pod can't reach service," "DNS resolution fails intermittently," "service has no healthy endpoints" — are genuinely just the Linux primitives from this masterclass, wearing Kubernetes terminology. Engineers who understand the underlying mechanism debug these in minutes; engineers who only know kubectl commands end up guessing.

2Kubernetes Networking Foundation

2.1 A Pod is (at minimum) a network namespace

🔵 Concept

Every pod gets its own network namespace — exactly the ns-something primitive we've built dozens of times in this masterclass. If a pod has multiple containers, they SHARE that one namespace (and therefore one IP address, one loopback, one port space) — this is why two containers in the same pod can reach each other over localhost, but two containers in different pods cannot.

2.2 CNI — the plugin that wires a pod into the node's network

🔵 Concept

CNI (Container Network Interface) is the standard interface Kubernetes uses to delegate "give this new pod a network namespace, an IP, and connectivity to the rest of the cluster" to a plugin (Flannel, Calico, Cilium, and others). At the simplest level — exactly what we'll build by hand — a CNI plugin typically creates a veth pair, attaches one end to a bridge on the node (conceptually the same as our docker0 stand-in from Project 11), moves the other end into the pod's namespace, and assigns an IP from the node's slice of the cluster's pod CIDR.

2.3 Three separate address spaces — don't mix them up

🔵 Concept

Pod IP — every pod gets a real, routable (within the cluster) IP address, assigned by the CNI plugin from the pod CIDR. Node IP — the actual physical/VM network address of the Kubernetes node itself, same as any Linux server we've worked with all masterclass. Service IP (ClusterIP) — a virtual, stable IP that never corresponds to any single real host — it exists purely as an entry in kube-proxy's load-balancing rules (iptables or IPVS), pointing at a changing set of real pod IPs behind it. Confusing these three is one of the most common sources of Kubernetes networking confusion.

2.4 kube-proxy — Services are load balancing rules, not real servers

🔵 Concept

kube-proxy watches the Kubernetes API for Services and their backing Pods (called Endpoints), and programs the node's kernel accordingly — either as iptables DNAT-style rules (the historically default mode, directly built on the same netfilter mechanisms from Projects 7 and 8) or as IPVS rules (exactly Project 15's mechanism, just automated). When a pod connects to a Service's ClusterIP, the kernel transparently rewrites the destination to one of the healthy backing pod IPs — a Service is never a real listening process; it's purely a load-balancing rule.

2.5 CoreDNS — cluster DNS is still just DNS

🔵 Concept

CoreDNS runs as regular pods inside the cluster and answers DNS queries for Service and Pod names, following a structured naming convention like service-name.namespace.svc.cluster.local. Every resolver concept from Project 3 — nsswitch, search domains, getent hosts — still applies; CoreDNS is just the nameserver every pod's /etc/resolv.conf is automatically pointed at.

5Build a "Mini Cluster Node" by Hand

☸ Note on this lab

If you have access to a real cluster (minikube, kind, or a managed one), run the equivalent kubectl commands shown alongside each step. This lab reconstructs the same mechanism using tools you already know, so it works everywhere and keeps the internals visible instead of hidden behind the API server.

bash — build our own "node" with a CNI-style bridge and three "pods"
1sudo ip netns add ns-node                                    # represents the Kubernetes node's own root network namespace
2sudo ip netns exec ns-node ip link add cni0-lab type bridge   # our stand-in for the CNI bridge (like Flannel's cni0 or Docker's docker0)
3sudo ip netns exec ns-node ip addr add 10.244.1.1/24 dev cni0-lab   # bridge gateway IP — the node's own address on the pod subnet
4sudo ip netns exec ns-node ip link set cni0-lab up
5sudo ip netns exec ns-node sysctl -w net.ipv4.ip_forward=1
6# create three "pods" — pod-catalog-a, pod-catalog-b (two replicas), and pod-coredns
7for p in catalog-a catalog-b coredns; do sudo ip netns add ns-pod-$p; done   # one namespace per pod, exactly like Project 1
8sudo ip link add veth-ca type veth peer name cni-ca-in
9sudo ip link add veth-cb type veth peer name cni-cb-in
10sudo ip link add veth-dns type veth peer name cni-dns-in
11sudo ip link set veth-ca netns ns-pod-catalog-a; sudo ip link set cni-ca-in netns ns-node
12sudo ip link set veth-cb netns ns-pod-catalog-b; sudo ip link set cni-cb-in netns ns-node
13sudo ip link set veth-dns netns ns-pod-coredns; sudo ip link set cni-dns-in netns ns-node
14sudo ip netns exec ns-node bash -c "ip link set cni-ca-in master cni0-lab; ip link set cni-cb-in master cni0-lab; ip link set cni-dns-in master cni0-lab"   # attach every pod's host-side veth to the bridge — this IS what "CNI wires the pod into the node" means
15sudo ip netns exec ns-node bash -c "ip link set cni-ca-in up; ip link set cni-cb-in up; ip link set cni-dns-in up"
16sudo ip netns exec ns-pod-catalog-a bash -c "ip addr add 10.244.1.2/24 dev veth-ca; ip link set veth-ca up; ip link set lo up; ip route add default via 10.244.1.1"
17sudo ip netns exec ns-pod-catalog-b bash -c "ip addr add 10.244.1.3/24 dev veth-cb; ip link set veth-cb up; ip link set lo up; ip route add default via 10.244.1.1"
18sudo ip netns exec ns-pod-coredns bash -c "ip addr add 10.244.1.9/24 dev veth-dns; ip link set veth-dns up; ip link set lo up; ip route add default via 10.244.1.1"
19sudo ip netns exec ns-pod-catalog-a bash -c "echo 'reply from catalog-a' > /tmp/index.html; cd /tmp && python3 -m http.server 8080 --bind 10.244.1.2 &"
20sudo ip netns exec ns-pod-catalog-b bash -c "echo 'reply from catalog-b' > /tmp/index.html; cd /tmp && python3 -m http.server 8080 --bind 10.244.1.3 &"
Our Manual StepReal Kubernetes Equivalent
ip netns add ns-pod-catalog-aAutomatically created by the kubelet + CNI plugin as part of pod startup — kubectl get pod catalog-a -o wide shows the resulting pod IP
veth pair + master cni0-labExactly what a CNI plugin (Flannel, Calico's simplest mode, etc.) does automatically for every new pod
ip addr add 10.244.1.2/24The CNI plugin's IPAM (IP Address Management) component assigns this from the node's slice of the cluster's pod CIDR

5.1 Create a "Service" — the kube-proxy equivalent, iptables mode

bash — on ns-node, simulate a ClusterIP Service backed by both catalog pods
1sudo ip netns exec ns-node iptables -t nat -N KUBE-SVC-CATALOG-LAB   # kube-proxy creates one chain per Service; we're mimicking its exact naming pattern
2sudo ip netns exec ns-node iptables -t nat -A PREROUTING -d 10.96.0.10 -p tcp --dport 80 -j KUBE-SVC-CATALOG-LAB   # traffic to our fake ClusterIP 10.96.0.10:80 gets handed to our service chain
3sudo ip netns exec ns-node iptables -t nat -A KUBE-SVC-CATALOG-LAB -m statistic --mode random --probability 0.5 -j DNAT --to-destination 10.244.1.2:8080   # 50% of connections go to pod catalog-a — this random-probability trick is exactly how real kube-proxy load-balances in iptables mode
4sudo ip netns exec ns-node iptables -t nat -A KUBE-SVC-CATALOG-LAB -j DNAT --to-destination 10.244.1.3:8080   # remaining 50% (no probability match needed on the last rule) go to pod catalog-b
5sudo ip netns exec ns-node iptables -A FORWARD -d 10.244.1.0/24 -j ACCEPT   # allow forwarding to the pod subnet, same FORWARD-chain lesson from Project 7
TokenMeaning
-m statistic --mode random --probability 0.5The actual mechanism real kube-proxy uses in iptables mode to distribute load across multiple backend pods — each Service chain is a small cascade of probability-weighted DNAT rules, functionally similar to round robin but implemented as weighted randomness.
10.96.0.10Our stand-in ClusterIP — notice it doesn't correspond to any real interface or listening process anywhere; it only exists as this DNAT rule.

7Break-Fix #1 — Pod Not Attached to the CNI Bridge

🔴 Break It

Detach catalog-b's veth from the bridge, simulating a CNI plugin failure during pod startup — a genuinely common real-world Kubernetes incident, especially under node resource pressure.

bash — on ns-node
1sudo ip netns exec ns-node ip link set cni-cb-in nomaster   # detach it from the bridge — the interface itself stays up, exactly like Project 10's Break-Fix #1

Observe

bash
1sudo ip netns exec ns-node curl --max-time 2 http://10.244.1.3:8080/   # try reaching catalog-b's pod IP directly
    curl: (28) Connection timed out
2sudo ip netns exec ns-node bridge link show   # the real diagnostic — only lists genuinely attached bridge ports
    (cni-cb-in is missing from this list — it's up, but not a bridge member)
🔵 Reading the symptom

On a real cluster, this would show up as kubectl describe pod catalog-b reporting Running, with a perfectly valid assigned IP — but the pod would be completely unreachable, and kubectl exec into it would show a healthy-looking interface from inside. The actual fault, exactly like Project 10, is invisible from inside the pod's own namespace — you can only see it by checking bridge membership from the node side.

🔴 Root Cause

The pod's veth interface was administratively up and correctly addressed, but was never attached (or was detached) as a port of the node's CNI bridge, so no traffic could reach it despite the pod appearing healthy in every pod-level check.

bash — fix
1sudo ip netns exec ns-node ip link set cni-cb-in master cni0-lab
🟦 Production Best Practice

When a pod is Running but completely unreachable, check the CNI-level plumbing on the node (bridge membership, veth state) before assuming an application-level problem — this is a node-networking issue wearing a pod-health costume.

8Break-Fix #2 — Service Works by IP, Not by DNS Name

🔴 Break It

Set up a CoreDNS-style resolver for our lab (dnsmasq, same tool as Project 3), but configure it with the WRONG namespace in the service's DNS record — a very common copy-paste mistake when defining cluster DNS entries or, in real clusters, when a Service is deployed to a different namespace than expected.

bash — on ns-pod-coredns, our lab's CoreDNS stand-in
1sudo ip netns exec ns-pod-coredns bash -c "cat > /tmp/dnsmasq-cluster.conf" <<'EOF'
no-resolv
listen-address=10.244.1.9
address=/catalog-svc.staging.svc.cluster.local/10.96.0.10
EOF
2sudo ip netns exec ns-pod-coredns dnsmasq -C /tmp/dnsmasq-cluster.conf -k &   # our simulated CoreDNS, but the record is under the "staging" namespace
3sudo ip netns exec ns-pod-catalog-a bash -c "echo 'nameserver 10.244.1.9' > /etc/resolv.conf; echo 'search catalog-a.production.svc.cluster.local production.svc.cluster.local svc.cluster.local cluster.local' >> /etc/resolv.conf"   # this pod is actually running in the "production" namespace, matching real kubelet-generated resolv.conf behavior

Observe

bash — on ns-pod-catalog-a, try reaching the service by its short cluster name
1sudo ip netns exec ns-pod-catalog-a getent hosts catalog-svc.production.svc.cluster.local   # the name our production pod would actually try to use
    (no output — resolution failed)
2sudo ip netns exec ns-pod-catalog-a getent hosts catalog-svc.staging.svc.cluster.local   # the name that's actually registered
    10.96.0.10  catalog-svc.staging.svc.cluster.local
🔵 Reading the symptom

The ClusterIP works perfectly by raw IP — namespace mismatches never affect Layer 3/4 connectivity at all. The failure is purely in the DNS name's namespace segment: the Service's DNS record was published under staging, but the calling pod (correctly, following its own real namespace) was looking for it under production. This is exactly Project 3's "works by IP, fails by hostname" lesson, with a Kubernetes-specific twist — the "hostname" here is a structured FQDN where the namespace segment has to match exactly.

🔴 Root Cause

The Service's DNS record existed under the wrong namespace segment of the cluster DNS naming convention, so a pod in a different (correct) namespace, following the standard naming pattern, could not resolve it.

bash — fix: correct the DNS record's namespace
1sudo ip netns exec ns-pod-coredns pkill dnsmasq
2sudo ip netns exec ns-pod-coredns bash -c "cat > /tmp/dnsmasq-cluster.conf" <<'EOF'
no-resolv
listen-address=10.244.1.9
address=/catalog-svc.production.svc.cluster.local/10.96.0.10
EOF
3sudo ip netns exec ns-pod-coredns dnsmasq -C /tmp/dnsmasq-cluster.conf -k &
🟦 Production Best Practice

On a real cluster, this incident is really "the Service was deployed to the wrong namespace" — the fix is almost never a DNS change, it's correcting which namespace the Service (and often the whole deployment) actually lives in. Always confirm namespace alignment first with kubectl get svc -A | grep catalog-svc before suspecting CoreDNS itself.

9Break-Fix #3 — Stale kube-proxy Rule (Dead Pod in Rotation)

🔴 Break It

Kill catalog-b's process without updating our Service rules — simulating a pod crash where, for whatever reason, kube-proxy's rule update lagged behind reality (rare on a healthy real cluster, but a very real transient-failure-window scenario, and a great way to isolate the exact mechanism).

bash — on ns-pod-catalog-b
1sudo ip netns exec ns-pod-catalog-b pkill -f "http.server 8080"   # simulate the pod's container crashing

Observe

bash — on ns-node
1for i in 1 2 3 4; do sudo ip netns exec ns-node curl -s --max-time 2 http://10.96.0.10/ || echo FAILED; done   # call the Service repeatedly again
    reply from catalog-a
    FAILED
    reply from catalog-a
    FAILED   (roughly half of requests fail — matching our 50/50 DNAT rule split)
2sudo ip netns exec ns-node iptables -t nat -L KUBE-SVC-CATALOG-LAB -n -v   # our Service chain still lists BOTH pods as valid targets
    (catalog-b's DNAT rule is still there, with no way for iptables itself to know the pod behind it is dead)
🔵 Reading the symptom

This is Project 15's "IPVS has no health checking" lesson, applying equally to iptables-mode kube-proxy — the DNAT rules themselves have zero awareness of whether the pod behind them is alive. On a real cluster, this exact window is normally very brief, because kubelet's readiness probes mark the pod NotReady, which removes it from the Service's Endpoints, which kube-proxy then reflects by removing its rule — but if that pipeline stalls or is misconfigured (missing or misconfigured readiness probe is the classic cause), a dead pod can keep receiving a share of traffic indefinitely, exactly like this.

🔴 Root Cause

A pod backing the Service had crashed, but the kube-proxy-managed forwarding rule for it hadn't been removed, so it kept receiving its normal share of Service traffic and failing every time.

bash — fix: manually update the rule (a healthy cluster's readiness-probe pipeline does this automatically)
1sudo ip netns exec ns-node iptables -t nat -D KUBE-SVC-CATALOG-LAB -j DNAT --to-destination 10.244.1.3:8080   # remove the dead pod's rule
2sudo ip netns exec ns-pod-catalog-b bash -c "cd /tmp && python3 -m http.server 8080 --bind 10.244.1.3 &"   # bring the pod back
3sudo ip netns exec ns-node iptables -t nat -A KUBE-SVC-CATALOG-LAB -j DNAT --to-destination 10.244.1.3:8080   # re-add it once healthy
🟦 Production Best Practice

Always configure proper readiness probes on real Kubernetes workloads — they're the mechanism that keeps kube-proxy's rules (whether iptables or IPVS) honest about which pods can actually serve traffic. A missing or too-lenient readiness probe is the most common real-world cause of "the Service intermittently fails" tickets.

10Production Best Practices

🟦 Translate first, troubleshoot second

Pod = namespace, Service = load-balancing rule, ClusterDNS = a DNS server — reframe every Kubernetes networking complaint in these terms before reaching for kubectl.

🟦 "Running" ≠ "network-attached"

A pod can report Running while its CNI plumbing is broken — check the node's bridge/veth state directly, same as Project 10.

🟦 Namespace mismatches break DNS, never IP connectivity

If it works by ClusterIP but fails by name, check the FQDN's namespace segment before touching CoreDNS itself.

🟦 Readiness probes are what keep Service rules honest

kube-proxy's rules have no built-in health awareness — that entirely depends on readiness probes updating Endpoints correctly.

12Interview Preparation

ScenarioA pod shows Running in kubectl but nothing can reach it. How do you troubleshoot it at the networking level?

I'd treat the pod as a network namespace and check its CNI-level attachment on the node — specifically whether its veth interface is actually a member of the node's CNI bridge, using bridge link show, rather than just ip link show which can look healthy even when the interface isn't attached to anything. This is the same "up doesn't mean attached" lesson that applies to any Linux bridge.

Interviewer follow-up: "What if the bridge attachment looks fine?" — Answer: I'd check routing next — does the pod have a correct default route pointing at the bridge gateway — and then move up to whether kube-proxy's Service rules, if relevant, are correctly pointing at this pod's IP.
ConceptWhat's the difference between a Pod IP, a Node IP, and a ClusterIP?

A Pod IP is a real, routable address assigned to an individual pod by the CNI plugin. A Node IP is the actual physical or VM network address of the Kubernetes node itself. A ClusterIP is a virtual address that never corresponds to any real listening host — it only exists as a set of load-balancing rules, in iptables or IPVS, that kube-proxy maintains, rewriting traffic to one of the real pod IPs behind it.

TroubleshootingA Service works when called by its ClusterIP but fails to resolve by its DNS name. What would you check?

Since it works by IP, connectivity and the Service's load-balancing rules are fine — this is a pure DNS issue. I'd check whether the FQDN's namespace segment matches where the Service actually lives, since Kubernetes DNS names are namespace-scoped, and a pod in one namespace using the short name won't automatically find a Service in a different namespace without the fully-qualified name.

ProductionWhy might a Service keep sending traffic to a pod that has already crashed?

kube-proxy's forwarding rules, whether iptables or IPVS, have no built-in awareness of pod health — they only reflect the cluster's Endpoints, which are updated based on readiness probe results. If a readiness probe is missing, misconfigured, or too lenient, a crashed pod can keep receiving its share of Service traffic until the probe (or the pod's restart) catches up.
