1The Incident

This is the capstone incident — a synthesis of nearly everything in this masterclass, presented the way a genuinely bad production day actually unfolds: not as one clean root cause, but as a sequence of separate problems that each hide the next one behind it.

TimeEvent
09:14Bank's online banking checkout-equivalent service (fund transfers) goes completely down
09:16Engineer fixes an obvious DNS problem — service partially recovers
09:22Still broken for most users. A firewall rule is found and fixed — more recovery, still not 100%
09:31Load balancer investigation finds a dead backend still in rotation — fixed, throughput improves
09:40One specific container never responds at all, despite looking "up" — a networking-layer issue is found and fixed
09:52Service finally handles transfers end-to-end, but a downstream fraud-check call from the backend itself is still silently failing

"We keep thinking we've found THE problem, fixing it, seeing things get better, and then hitting a wall again. This has happened five separate times in this one incident."

This is a genuinely realistic shape for a major incident — especially one that started during a period when several small, unrelated issues had been quietly accumulating and only became visible once traffic patterns changed or something else broke first. Peeling back one layer often reveals the next.

🔵 Why this project matters

Real major incidents are rarely a single clean root cause — they're often several genuinely separate issues that happened to compound or mask each other. The skill this capstone builds is resisting the urge to declare victory after the first fix, and instead systematically re-validating end-to-end after every change, exactly the discipline every RCA template (Project 25) and every earlier compound incident (Projects 23, 24) has been building toward.

2Why Layered Incidents Happen

🔵 Concept

Layered incidents typically happen for one of two reasons: either several small, independent problems (a stale DNS entry, a slightly wrong firewall rule, a container that silently lost its network attachment) had been quietly present for a while, invisible individually because normal traffic patterns never exercised the exact path that would expose them — or one root event (a deployment, a network change) had multiple simultaneous, unrelated side effects. Either way, the investigation pattern is the same: fix what you find, RE-TEST FULLY, and don't assume the next problem you find is somehow "the same issue" just because it's in the same incident.

🟠 The trap this project is designed to build resistance against

After finding and fixing ONE real, legitimate problem, it's extremely tempting to declare the incident resolved the moment things visibly improve — exactly what happened four separate times in our timeline before someone caught the pattern. Partial improvement is not full resolution; always re-validate against the complete, original set of acceptance criteria (Project 25's lesson) before closing anything.

4Layered Incident Method

  • 1. Fix the current, confirmed problem — but treat "improvement" as a checkpoint, not a resolution
    • ↓
  • 2. After every fix, re-run the FULL end-to-end test — not just a check of the specific thing you just fixed
    • ↓
  • 3. If the full end-to-end test still fails, start the layer-by-layer method fresh — don't assume the new symptom is related to the previous root cause
    • ↓
  • 4. Track every fix explicitly (this is exactly what Project 25's RCA documentation is for) — five separate legitimate root causes need five separate, clearly attributed fixes on record
    • ↓
  • Only declare the incident resolved when the full end-to-end test passes completely, not when things "look better"

5Build the Full Stack

This lab combines Projects 3 (DNS), 7 (firewall), 8 (NAT), 10 (bridge), 11 (containers), and 15 (load balancing) into one connected environment. Build it exactly as shown — every piece will matter.

bash — run as root/sudo; this is a long setup, matching the real complexity of the stack
1sudo ip netns add ns-client        # the online banking client
2sudo ip netns add ns-dns           # cluster/internal DNS
3sudo ip netns add ns-fw            # the perimeter firewall
4sudo ip netns add ns-lb            # the load balancer (IPVS, exactly Project 15)
5sudo ip netns add ns-container-a   # backend container A
6sudo ip netns add ns-container-b   # backend container B
7sudo ip netns add ns-fraud-api     # external fraud-check API the backend calls outbound
8# client <-> firewall
9sudo ip link add veth-client type veth peer name fw-client-in
10sudo ip link set veth-client netns ns-client; sudo ip link set fw-client-in netns ns-fw
11sudo ip netns exec ns-client ip addr add 10.240.1.10/24 dev veth-client
12sudo ip netns exec ns-fw ip addr add 10.240.1.1/24 dev fw-client-in
13# dns <-> client (shared with firewall subnet for simplicity)
14sudo ip link add veth-dns type veth peer name fw-dns-in
15sudo ip link set veth-dns netns ns-dns; sudo ip link set fw-dns-in netns ns-fw
16sudo ip netns exec ns-dns ip addr add 10.240.1.53/24 dev veth-dns
17sudo ip netns exec ns-fw ip addr add 10.240.1.2/24 dev fw-dns-in
18# firewall <-> load balancer
19sudo ip link add fw-lb-out type veth peer name lb-fw-in
20sudo ip link set fw-lb-out netns ns-fw; sudo ip link set lb-fw-in netns ns-lb
21sudo ip netns exec ns-fw ip addr add 10.240.2.1/24 dev fw-lb-out
22sudo ip netns exec ns-lb ip addr add 10.240.2.10/24 dev lb-fw-in
23# load balancer <-> a bridge shared by both containers
24sudo ip netns exec ns-lb ip link add br0 type bridge
25sudo ip link add lb-br-out type veth peer name lb-br-in
26sudo ip link set lb-br-in netns ns-lb; sudo ip netns exec ns-lb ip link set lb-br-in master br0
27sudo ip link add veth-ca type veth peer name br-ca-in
28sudo ip link add veth-cb type veth peer name br-cb-in
29sudo ip link set veth-ca netns ns-container-a; sudo ip link set br-ca-in netns ns-lb
30sudo ip link set veth-cb netns ns-container-b; sudo ip link set br-cb-in netns ns-lb
31sudo ip netns exec ns-lb bash -c "ip link set br-ca-in master br0; ip link set br-cb-in master br0"
32sudo ip netns exec ns-lb ip addr add 10.240.3.1/24 dev br0
33sudo ip netns exec ns-container-a ip addr add 10.240.3.11/24 dev veth-ca
34sudo ip netns exec ns-container-b ip addr add 10.240.3.12/24 dev veth-cb
35# container A <-> NAT egress path <-> external fraud API (via the firewall acting as NAT gateway too)
36sudo ip link add fw-fraud-out type veth peer name fraud-fw-in
37sudo ip link set fw-fraud-out netns ns-fw; sudo ip link set fraud-fw-in netns ns-fraud-api
38sudo ip netns exec ns-fw ip addr add 203.0.117.1/24 dev fw-fraud-out
39sudo ip netns exec ns-fraud-api ip addr add 203.0.117.10/24 dev fraud-fw-in
40# bring everything up
41for ns in ns-client ns-dns ns-fw ns-lb ns-container-a ns-container-b ns-fraud-api; do sudo ip netns exec $ns ip link set lo up; done
42sudo ip netns exec ns-client bash -c "ip link set veth-client up; ip route add default via 10.240.1.1"
43sudo ip netns exec ns-dns ip link set veth-dns up
44sudo ip netns exec ns-fw bash -c "ip link set fw-client-in up; ip link set fw-dns-in up; ip link set fw-lb-out up; ip link set fw-fraud-out up; sysctl -w net.ipv4.ip_forward=1"
45sudo ip netns exec ns-lb bash -c "ip link set lb-fw-in up; ip link set lb-br-in up; ip link set br0 up; ip link set br-ca-in up; ip link set br-cb-in up; sysctl -w net.ipv4.ip_forward=1"
46sudo ip netns exec ns-container-a bash -c "ip link set veth-ca up; ip route add default via 10.240.3.1"
47sudo ip netns exec ns-container-b bash -c "ip link set veth-cb up; ip route add default via 10.240.3.1"
48sudo ip netns exec ns-fraud-api ip link set fraud-fw-in up
49sudo ip netns exec ns-fw ip route add 10.240.3.0/24 via 10.240.2.10   # firewall knows how to reach the backend subnet via the LB
50sudo ip netns exec ns-container-a bash -c "echo 'reply from container-a' > /tmp/i.html; cd /tmp && python3 -m http.server 8443 --bind 10.240.3.11 &"
51sudo ip netns exec ns-container-b bash -c "echo 'reply from container-b' > /tmp/i.html; cd /tmp && python3 -m http.server 8443 --bind 10.240.3.12 &"
52sudo ip netns exec ns-fraud-api python3 -m http.server 9443 --bind 203.0.117.10 &
53# DNS: transfers.bank.internal -> the LB's IP
54sudo ip netns exec ns-dns bash -c "cat > /tmp/dns.conf" <<'EOF'
no-resolv
listen-address=10.240.1.53
address=/transfers.bank.internal/10.240.2.10
EOF
55sudo ip netns exec ns-dns dnsmasq -C /tmp/dns.conf -k &
56sudo ip netns exec ns-client bash -c "echo 'nameserver 10.240.1.53' > /etc/resolv.conf"
57# firewall: allow client -> LB, and NAT for the backend's own outbound fraud-check calls
58sudo ip netns exec ns-fw iptables -A FORWARD -m state --state ESTABLISHED,RELATED -j ACCEPT
59sudo ip netns exec ns-fw iptables -A FORWARD -s 10.240.1.10 -d 10.240.2.10 -p tcp --dport 443 -j ACCEPT
60# load balancer: IPVS service for transfers, backed by both containers
61sudo ip netns exec ns-lb ipvsadm -A -t 10.240.2.10:443 -s rr
62sudo ip netns exec ns-lb ipvsadm -a -t 10.240.2.10:443 -r 10.240.3.11:8443 -m -w 1
63sudo ip netns exec ns-lb ipvsadm -a -t 10.240.2.10:443 -r 10.240.3.12:8443 -m -w 1

6Confirm the Incident Reproduces

Now we deliberately introduce all five layers of breakage at once, exactly matching the incident's real starting state.

bash — introduce all five problems
1sudo ip netns exec ns-dns pkill dnsmasq
2sudo ip netns exec ns-dns bash -c "cat > /tmp/dns-bad.conf" <<'EOF'
no-resolv
listen-address=10.240.1.53
address=/transfers.bank.internal/10.240.2.99
EOF
3sudo ip netns exec ns-dns dnsmasq -C /tmp/dns-bad.conf -k &   # LAYER 1: DNS points at a decommissioned LB IP that doesn't exist
4sudo ip netns exec ns-fw iptables -I FORWARD 1 -s 10.240.1.0/24 -d 10.240.2.0/24 -j DROP   # LAYER 2: an overly broad rule shadows the correct allow rule
5sudo ip netns exec ns-container-b pkill -f "http.server 8443"   # LAYER 3: container-b crashed, still in the LB rotation
6sudo ip netns exec ns-lb ip link set br-ca-in nomaster   # LAYER 4: container-a's veth silently detached from the bridge
7# LAYER 5 will reveal itself once the earlier four are fixed — no action needed yet, it's a route that was simply never added
🔴 Confirmed: total failure

At this point, the client cannot reach the service at all. This matches 09:14 in our timeline — total outage, before any investigation has begun.

7Layer 1 — DNS Resolves to a Decommissioned LB IP

PROJECT 3 METHOD
bash — on ns-client
1sudo ip netns exec ns-client getent hosts transfers.bank.internal
    10.240.2.99  transfers.bank.internal   (the real LB is at 10.240.2.10 — this is stale/wrong)
🔵 Diagnosis

Exactly Project 3's method — a DNS record pointing at the wrong address entirely. Fix it and re-test the FULL path, not just DNS.

bash — fix
1sudo ip netns exec ns-dns pkill dnsmasq
2sudo ip netns exec ns-dns dnsmasq -C /tmp/dns.conf -k &   # restore the correct config from initial setup
3sudo ip netns exec ns-client curl --max-time 3 https://transfers.bank.internal/i.html   # full end-to-end re-test, not just DNS
    (still fails — this is 09:16 in the timeline: "partial recovery," but not resolved)

8Layer 2 — Firewall Blocks the Correct LB

PROJECT 7 METHOD
bash — on ns-fw
1sudo ip netns exec ns-fw iptables -L FORWARD -n -v --line-numbers
    1  ...  DROP    10.240.1.0/24  10.240.2.0/24   (matching, climbing counter — shadowing everything below it)
🔵 Diagnosis

Exactly Project 7's rule-order lesson — DNS is now correct, but a broad DROP rule sits above the correct ACCEPT rule.

bash — fix
1sudo ip netns exec ns-fw iptables -D FORWARD 1
2sudo ip netns exec ns-client curl --max-time 3 https://transfers.bank.internal/i.html   # full re-test again
    reply from container-a   (SOME traffic now succeeds — 09:22 in the timeline)
3for i in 1 2 3 4; do sudo ip netns exec ns-client curl -s --max-time 2 https://transfers.bank.internal/i.html || echo FAILED; done   # but check MULTIPLE requests, not just one
    reply from container-a
    FAILED
    reply from container-a
    FAILED   (roughly half still failing — not fully resolved)

9Layer 3 — LB Backend Pool Has a Dead Container

PROJECT 15 METHOD
bash — on ns-lb
1sudo ip netns exec ns-lb ipvsadm -Ln
    -> 10.240.3.12:8443   Masq   1   (this backend is dead — container-b crashed)
🔵 Diagnosis

Exactly Project 15's "dead backend still in rotation" lesson — IPVS has no health awareness of its own.

bash — fix
1sudo ip netns exec ns-lb ipvsadm -d -t 10.240.2.10:443 -r 10.240.3.12:8443
2sudo ip netns exec ns-client curl --max-time 3 https://transfers.bank.internal/i.html   # full re-test
    reply from container-a   (09:31 in the timeline — throughput improves, single-backend but working)

10Layer 4 — Container-A Was Never Attached to the Bridge

PROJECT 10 METHOD
🟠 Wait — this looks fine so far. Let's bring container-b back and see what's really going on.

With only container-a in rotation, we've been accidentally masking Layer 4 this whole time. Let's restart container-b and re-add it, simulating the natural next step of the real incident (bringing the crashed container back).

bash — restore container-b and re-add it to the pool
1sudo ip netns exec ns-container-b bash -c "cd /tmp && python3 -m http.server 8443 --bind 10.240.3.12 &"
2sudo ip netns exec ns-lb ipvsadm -a -t 10.240.2.10:443 -r 10.240.3.12:8443 -m -w 1
3for i in 1 2 3 4; do sudo ip netns exec ns-client curl -s --max-time 2 https://transfers.bank.internal/i.html || echo FAILED; done
    FAILED
    reply from container-b
    FAILED
    reply from container-b   (container-a's turn always fails now — 09:40 in the timeline)
bash — on ns-lb, the exact Project 10 diagnostic
1sudo ip netns exec ns-lb bridge link show
    (br-ca-in is missing — it's up, but not a bridge member)
🔵 Diagnosis

Exactly Project 10's core lesson — container-a's link is administratively up, but was never (or no longer) attached to the bridge. This was hidden by Layer 3's coincidence — with container-b dead, ALL traffic went to container-a anyway via the LB's rules, but container-a's traffic was never actually able to physically reach it through the broken bridge attachment... which means Layer 3's "fix" earlier only appeared to work because our small number of manual test requests happened to get lucky, or more precisely, the LB's DNAT rule still pointed traffic there but it was never actually confirmed end-to-end with enough requests. This is exactly why re-testing thoroughly, not just once, matters.

bash — fix
1sudo ip netns exec ns-lb ip link set br-ca-in master br0
2for i in 1 2 3 4 5 6; do sudo ip netns exec ns-client curl -s --max-time 2 https://transfers.bank.internal/i.html; done
    reply from container-a
    reply from container-b
    reply from container-a
    reply from container-b
    reply from container-a
    reply from container-b   (fully working, both backends, every request — 09:52 in the timeline)

11Layer 5 — NAT Egress Missing for the Backend's Own Outbound Call

PROJECT 8 METHOD
🟠 The client-facing path is fully fixed. But is the INCIDENT fully resolved?

Following our own method from Section 4 — re-test the FULL end-to-end business function, not just "the client got a 200." A funds transfer isn't complete until the backend's own downstream fraud-check call succeeds too.

bash — simulate container-a making its own outbound call to the fraud-check API, exactly like a real transfer would trigger
1sudo ip netns exec ns-container-a curl --max-time 3 http://203.0.117.10:9443/
    curl: (28) Connection timed out   (the backend itself can't reach the external fraud API at all)
🔵 Diagnosis

Exactly Project 8's missing-MASQUERADE lesson — nobody ever configured NAT/egress routing for the BACKEND's own outbound traffic to the fraud API; only the client-to-LB path was ever set up. This is a completely separate, fifth root cause, invisible from the client's perspective entirely (their request to the LB succeeds), and would only surface once an actual fund transfer tried to complete its downstream fraud check.

bash — fix: add the missing route and NAT for the backend's outbound path, on ns-fw
1sudo ip netns exec ns-fw iptables -t nat -A POSTROUTING -s 10.240.3.0/24 -o fw-fraud-out -j MASQUERADE
2sudo ip netns exec ns-fw iptables -A FORWARD -s 10.240.3.0/24 -d 203.0.117.10 -p tcp --dport 9443 -j ACCEPT
3sudo ip netns exec ns-container-a ip route add 203.0.117.0/24 via 10.240.3.1   # container-a needs a route toward the fraud API's network too, via the LB acting as its gateway
4sudo ip netns exec ns-lb ip route add 203.0.117.0/24 via 10.240.2.1   # and the LB needs to know how to forward that onward to the firewall
5sudo ip netns exec ns-container-a curl --max-time 3 http://203.0.117.10:9443/
    200   (fully resolved — every layer confirmed working end-to-end)
🟢 Incident fully resolved

Five genuinely separate root causes, each requiring its own fix, each hiding the next until fully resolved. This is the shape of a real major incident.

12Best Practices

🟦 Partial improvement is a checkpoint, not resolution

Re-test the complete end-to-end business function after every fix, not just the specific thing you changed.

🟦 Don't assume the next symptom relates to the last root cause

Start the diagnostic method fresh for each new symptom — this incident had five UNRELATED root causes.

🟦 Test with enough requests to see the real pattern

A single successful test can get lucky and mask a partial failure (exactly Layer 4, hidden by Layer 3's coincidence).

🟦 Validate the FULL business function, not just the entry point

Layer 5 was invisible from the client's perspective entirely — always trace the complete transaction path.

14Interview Preparation

ScenarioTell me about the most complex incident you've worked through, technically.

I'd describe a capstone-style scenario with five genuinely separate root causes compounding in one incident — a stale DNS record, a shadowed firewall rule, a dead load-balancer backend still receiving traffic, a container that looked healthy but was never actually attached to its bridge, and a missing NAT path for a downstream call the client never even saw. Each fix produced visible improvement, which made it tempting to declare victory early four separate times, but re-testing the complete end-to-end business function after every single change is what caught each subsequent layer.

Interviewer follow-up: "How did you know when to stop investigating?" — Answer: when the full end-to-end test — not just a single request, and not just the client-facing entry point, but the complete business transaction including downstream calls — passed reliably across multiple attempts.
ConceptWhy is it dangerous to declare an incident resolved as soon as things "look better"?

Because layered incidents can have multiple, genuinely independent root causes that each produce partial improvement when fixed — improvement doesn't prove full resolution, it just proves that specific fix helped. A later symptom might be completely unrelated to the one you just fixed, and treating it as "probably the same issue" can send you down the wrong investigative path entirely.
