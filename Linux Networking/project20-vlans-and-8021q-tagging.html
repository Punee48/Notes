1The Task

We're supporting a bank's data center network segmentation project. A single Linux server needs simultaneous, fully isolated connectivity to two separate network segments — the finance/trading systems segment and a general corporate segment — but there's only one physical (or virtual, in a cloud/hypervisor setting) network link available to that server.

"We can't run two separate cables to every server, and we definitely can't have finance and general corporate traffic mixing on the same broadcast domain — that's a compliance violation. We need one link, two completely isolated logical networks."

This is precisely the problem VLANs solve. A single physical link can carry multiple logically separate networks simultaneously, using a small tag embedded in each Ethernet frame to say which VLAN it belongs to — switches and hosts that understand these tags can then keep each VLAN's traffic completely isolated, even while sharing the same wire.

🔵 Why this project matters

VLANs are foundational in virtually every real data center and enterprise network — server virtualization hosts routinely carry a dozen VLANs down one physical uplink, and cloud provider virtual networks use conceptually identical tagging mechanisms internally. Misunderstanding VLAN tagging is a very common source of "it should be isolated but somehow isn't" or "it should be connected but somehow isn't" incidents.

2VLAN Foundation

2.1 802.1Q — a small tag that creates a separate broadcast domain

🔵 Concept

802.1Q tagging inserts a small 4-byte tag into an Ethernet frame, containing (among other things) a VLAN ID from 1 to 4094. Switches and hosts that understand this tag treat frames with different VLAN IDs as belonging to entirely separate broadcast domains — exactly like Project 10's bridges, but now MULTIPLE isolated bridges can effectively share the same physical wire, distinguished purely by this tag.

2.2 Access ports vs trunk ports

🔵 Concept

An access port carries exactly one VLAN, untagged — the device connected to it has no idea VLANs are even involved; the switch adds/removes the tag on its behalf. A trunk port carries MULTIPLE VLANs simultaneously, with every frame tagged so the receiving end knows which VLAN each one belongs to. Our server, needing two isolated networks over one link, needs that link configured as a trunk — and needs to understand 802.1Q tagging itself, since there's no switch doing the tagging translation on its behalf.

2.3 Linux VLAN subinterfaces

🔵 Concept

Linux implements 802.1Q directly — you create a VLAN subinterface on top of a real interface, and the kernel handles adding/removing the tag automatically. A physical (or veth) interface named eth0 gets a VLAN 10 subinterface conventionally named eth0.10, which behaves like any other network interface (gets its own IP, its own place in the routing table) but transparently tags/untags VLAN 10 frames on the underlying physical link.

2.4 The native/untagged VLAN — a common source of confusion

🔵 Concept

Some trunk configurations designate one VLAN as "native" or untagged — frames for that specific VLAN are sent without a tag at all, while every other VLAN on the same trunk is tagged. If the two ends of a trunk disagree about which VLAN (if any) is untagged, frames can be silently misdelivered to the wrong VLAN, or dropped — a subtle and common real-world misconfiguration.

4Troubleshooting Method

  • 1. Confirm both ends of the link agree on which VLAN IDs are in use — a simple typo (10 vs 20) breaks everything silently
    • ↓
  • 2. Confirm both ends agree on tagged vs untagged (native VLAN) handling for the link
    • ↓
  • 3. Capture on the underlying physical/trunk interface (not the VLAN subinterface) to see the raw tagged frames directly
    • ↓
  • 4. Check for accidental IP/subnet overlap between VLAN subinterfaces on the same host
    • ↓
  • Treat VLAN mismatches like Project 3's DNS namespace mismatches — same IP-layer symptoms, but the actual fault is one layer below, in the tag itself
🟠 Warning

A tcpdump capture on the VLAN SUBinterface (e.g. eth0.10) will already show untagged, de-encapsulated traffic — the tag itself is invisible there. To see the raw 802.1Q tag and diagnose tagging problems directly, capture on the underlying PHYSICAL/trunk interface instead.

5Build a Trunk with Two VLAN Subinterfaces

bash — run as root/sudo
1sudo ip netns add ns-server-a
2sudo ip netns add ns-server-b
3sudo ip link add trunk-a type veth peer name trunk-b   # this single veth pair is our "trunk link" — it will carry BOTH VLANs
4sudo ip link set trunk-a netns ns-server-a
5sudo ip link set trunk-b netns ns-server-b
6sudo ip netns exec ns-server-a ip link set trunk-a up   # the underlying trunk interface itself gets no IP — only its VLAN subinterfaces do
7sudo ip netns exec ns-server-b ip link set trunk-b up
8for ns in ns-server-a ns-server-b; do sudo ip netns exec $ns ip link set lo up; done
9# create VLAN 10 (finance) subinterfaces on both ends
10sudo ip netns exec ns-server-a ip link add link trunk-a name trunk-a.10 type vlan id 10   # create a VLAN 10 subinterface riding on top of trunk-a
11sudo ip netns exec ns-server-b ip link add link trunk-b name trunk-b.10 type vlan id 10   # matching VLAN 10 subinterface on the other end
12sudo ip netns exec ns-server-a ip addr add 10.30.10.1/24 dev trunk-a.10
13sudo ip netns exec ns-server-b ip addr add 10.30.10.2/24 dev trunk-b.10
14sudo ip netns exec ns-server-a ip link set trunk-a.10 up
15sudo ip netns exec ns-server-b ip link set trunk-b.10 up
16# create VLAN 20 (corporate) subinterfaces on both ends
17sudo ip netns exec ns-server-a ip link add link trunk-a name trunk-a.20 type vlan id 20
18sudo ip netns exec ns-server-b ip link add link trunk-b name trunk-b.20 type vlan id 20
19sudo ip netns exec ns-server-a ip addr add 10.30.20.1/24 dev trunk-a.20
20sudo ip netns exec ns-server-b ip addr add 10.30.20.2/24 dev trunk-b.20
21sudo ip netns exec ns-server-a ip link set trunk-a.20 up
22sudo ip netns exec ns-server-b ip link set trunk-b.20 up
TokenMeaning
ip link add link trunk-a name trunk-a.10 type vlan id 10Creates a VLAN subinterface: link trunk-a says which real interface it rides on top of, name trunk-a.10 is the conventional naming pattern (physical-interface.vlan-id), and type vlan id 10 specifies this subinterface handles VLAN ID 10 specifically — the kernel automatically tags outgoing frames and filters incoming frames on this VLAN ID.

6Verify Baseline and Isolation

bash — confirm both VLANs work, and confirm they're actually isolated from each other
1sudo ip netns exec ns-server-a ping -c 2 10.30.10.2   # VLAN 10 connectivity test
    2 received, 0% packet loss
2sudo ip netns exec ns-server-a ping -c 2 10.30.20.2   # VLAN 20 connectivity test
    2 received, 0% packet loss
3sudo ip netns exec ns-server-a tcpdump -i trunk-a -nn -c 4 vlan   # capture on the TRUNK interface, filter for VLAN-tagged frames, to see the tags directly
    ...vlan 10, p 0, ethertype IPv4...
    ...vlan 20, p 0, ethertype IPv4...   (both VLAN tags visible directly on the wire)
🟢 Baseline confirmed

Both VLANs work over the single trunk link, and the capture proves each frame carries the correct tag. This is our working baseline before we start breaking things.

7Break-Fix #1 — VLAN ID Mismatch

🔴 Break It

Simulate a typo during provisioning — server-b's "VLAN 10" subinterface is accidentally created with VLAN ID 30 instead.

bash — on ns-server-b, remove and recreate with the wrong ID
1sudo ip netns exec ns-server-b ip link delete trunk-b.10
2sudo ip netns exec ns-server-b ip link add link trunk-b name trunk-b.30 type vlan id 30   # typo: created as VLAN 30 instead of 10
3sudo ip netns exec ns-server-b ip addr add 10.30.10.2/24 dev trunk-b.30   # same IP address, but on the wrong VLAN entirely
4sudo ip netns exec ns-server-b ip link set trunk-b.30 up

Observe

bash — on ns-server-a
1sudo ip netns exec ns-server-a ping -c 2 10.30.10.2
    100% packet loss
2sudo ip netns exec ns-server-a tcpdump -i trunk-a -nn -c 2 vlan 10   # confirm our side is sending correctly tagged VLAN 10 frames
    (VLAN 10 tagged ARP/ping requests ARE leaving correctly)
3sudo ip netns exec ns-server-b tcpdump -i trunk-b -nn -c 2 vlan 10   # check what server-b's underlying trunk actually sees
    (nothing captured — because server-b has no subinterface listening for VLAN 10 anymore, only VLAN 30)
🔵 Reading the symptom

Server-a is doing everything correctly — sending properly tagged VLAN 10 frames onto the trunk. But server-b's kernel, having no subinterface configured for VLAN 10 anymore (only VLAN 30), simply discards those frames at the tag-filtering stage — they never reach any IP-layer processing at all, let alone the interface with the matching IP address. This looks, from a ping perspective, exactly like a routing or firewall failure, but the actual break is happening below IP entirely, in VLAN tag filtering.

🔴 Root Cause

The two ends of the link were configured with mismatched VLAN IDs for what was supposed to be the same logical network, so frames tagged for VLAN 10 were silently discarded by the side only listening for VLAN 30.

bash — fix
1sudo ip netns exec ns-server-b ip link delete trunk-b.30
2sudo ip netns exec ns-server-b ip link add link trunk-b name trunk-b.10 type vlan id 10
3sudo ip netns exec ns-server-b ip addr add 10.30.10.2/24 dev trunk-b.10
4sudo ip netns exec ns-server-b ip link set trunk-b.10 up
🟦 Production Best Practice

Always confirm VLAN ID agreement explicitly between both ends of any trunk configuration — this class of mismatch produces IP-layer symptoms (looks like routing/firewall) with a root cause one layer below IP entirely, so IP-layer troubleshooting alone won't find it.

8Break-Fix #2 — Tagged vs Untagged Mismatch

🔴 Break It

Simulate server-a sending VLAN 20 traffic completely UNTAGGED (as if it were a plain access-port device), while server-b still correctly expects it tagged.

bash — on ns-server-a, replace the VLAN 20 subinterface with a plain IP directly on the trunk interface (no tagging at all)
1sudo ip netns exec ns-server-a ip link delete trunk-a.20
2sudo ip netns exec ns-server-a ip addr add 10.30.20.1/24 dev trunk-a   # IP placed directly on the trunk itself — frames leave completely untagged

Observe

bash
1sudo ip netns exec ns-server-a ping -c 2 10.30.20.2
    100% packet loss
2sudo ip netns exec ns-server-a tcpdump -i trunk-a -nn -c 2 icmp   # confirm these frames are leaving WITHOUT any VLAN tag
    (ICMP frames visible, but with no "vlan" tag prefix at all in the output — confirming they're untagged)
🔵 Reading the symptom

Server-b's kernel only has VLAN subinterfaces (trunk-b.10 and trunk-b.20) actively listening for TAGGED frames — an untagged frame arriving on trunk-b has nowhere defined to go (unless trunk-b itself also happens to have its own IP directly on it, acting as an implicit native/untagged VLAN, which it doesn't in our setup) and is simply dropped. This is the classic real-world "one end is a trunk port, the other end is an access port" mismatch — one side assumes tagging, the other doesn't, and neither side will report an explicit error; traffic just silently fails to arrive.

🔴 Root Cause

One end of the link was sending VLAN 20 traffic completely untagged, while the other end only had a tagged VLAN 20 subinterface configured, with no matching untagged/native handling — a tagged-vs-untagged mismatch, not a wrong-ID mismatch like Break-Fix #1.

bash — fix: restore the proper tagged subinterface on server-a
1sudo ip netns exec ns-server-a ip addr del 10.30.20.1/24 dev trunk-a
2sudo ip netns exec ns-server-a ip link add link trunk-a name trunk-a.20 type vlan id 20
3sudo ip netns exec ns-server-a ip addr add 10.30.20.1/24 dev trunk-a.20
4sudo ip netns exec ns-server-a ip link set trunk-a.20 up
🟦 Production Best Practice

Whenever configuring a trunk, explicitly confirm both ends agree on which VLANs (if any) are untagged/native — never assume "no tag" defaults to matching behavior on both sides, since that assumption is exactly what causes this class of silent, hard-to-spot mismatch.

9Break-Fix #3 — Overlapping Subnets Across VLANs

🔴 Break It

Simulate a provisioning mistake where the finance VLAN and the corporate VLAN accidentally get assigned the SAME subnet — a very real risk when VLANs are configured by hand across many devices.

bash — on ns-server-a, accidentally give VLAN 20 the same subnet as VLAN 10
1sudo ip netns exec ns-server-a ip addr add 10.30.10.5/24 dev trunk-a.20   # VLAN 20 subinterface now ALSO has an address in the 10.30.10.0/24 range, same as VLAN 10

Observe

bash — on ns-server-a
1sudo ip netns exec ns-server-a ip route get 10.30.10.2   # which interface will the kernel actually use to reach a VLAN 10 address now?
    10.30.10.2 dev trunk-a.10 src 10.30.10.1   (this time it picked correctly, but it's now genuinely ambiguous)
2sudo ip netns exec ns-server-a ip addr show | grep -A1 "trunk-a\."   # see the overlap directly
    trunk-a.10: inet 10.30.10.1/24
    trunk-a.20: inet 10.30.10.5/24   (both interfaces now claim addresses in the exact same /24)
🔵 Reading the symptom

With two different interfaces holding addresses in the same subnet, the kernel's route selection for any address in that range becomes ambiguous and implementation-dependent — it might pick correctly today and inconsistently after an interface flap, a reboot, or a kernel update reorders things. This directly echoes Project 9's multi-NIC routing lessons, but the root cause here is a VLAN provisioning mistake rather than a routing configuration mistake — the VLANs themselves are tagged and isolated correctly at Layer 2, but the IP addressing plan on top of them was broken.

🔴 Root Cause

Two VLAN subinterfaces on the same host were assigned addresses within the same IP subnet, creating ambiguous routing behavior even though the underlying VLAN tagging and isolation were both working correctly.

bash — fix: give VLAN 20 its own, non-overlapping subnet
1sudo ip netns exec ns-server-a ip addr del 10.30.10.5/24 dev trunk-a.20
2sudo ip netns exec ns-server-a ip addr add 10.30.20.1/24 dev trunk-a.20   # correct, distinct subnet for VLAN 20
🟦 Production Best Practice

Maintain a clear, centrally documented IP address plan mapping every VLAN to its own distinct, non-overlapping subnet — this class of mistake is easy to make by hand across many devices and hard to notice until routing behaves unpredictably.

10Production Best Practices

🟦 Confirm VLAN ID agreement on both ends

A single-digit typo (10 vs 30) produces IP-layer symptoms with a Layer-2 root cause.

🟦 Confirm tagged vs untagged agreement explicitly

Never assume both ends handle the native/untagged VLAN the same way.

🟦 Capture on the trunk, not the subinterface, to see tags directly

VLAN subinterfaces show already-decapsulated traffic — the tag itself is only visible on the underlying interface.

🟦 Keep a documented, non-overlapping IP plan per VLAN

VLANs isolate at Layer 2 — nothing stops a mistaken IP plan from creating Layer 3 ambiguity on top.

12Interview Preparation

ScenarioTwo servers on what's supposed to be the same VLAN can't reach each other, but everything else on their trunk links works fine. What would you check?

I'd confirm both ends are actually configured with the same VLAN ID for that logical network — a simple typo, like VLAN 10 on one side and VLAN 30 on the other, produces exactly this symptom: complete isolation on just that one VLAN while everything else is unaffected. I'd check with ip -d link show on each VLAN subinterface, and confirm directly by capturing on the underlying trunk interface to see the actual tag values in the frames.

Interviewer follow-up: "What if the VLAN IDs match on both ends and it's still not working?" — Answer: I'd check whether one end is sending that VLAN's traffic tagged while the other expects it untagged (or vice versa) — a tagged/untagged mismatch produces the same kind of silent, complete isolation but for a different underlying reason.
ConceptWhat's the difference between a trunk port and an access port?

An access port carries exactly one VLAN, untagged, and the connected device has no VLAN awareness at all — the switch handles tagging on its behalf. A trunk port carries multiple VLANs simultaneously, with every frame tagged so the receiving end can tell which VLAN it belongs to — both ends of a trunk link need to actively understand and agree on 802.1Q tagging.

TroubleshootingWhy would capturing on a VLAN subinterface not show you the VLAN tag itself?

Because by the time a frame reaches the VLAN subinterface, the kernel has already stripped the tag and delivered it as ordinary de-encapsulated traffic — that's the whole point of the subinterface abstraction. To see the raw 802.1Q tag on the wire, you need to capture on the underlying physical or trunk interface instead, before that de-encapsulation happens.
