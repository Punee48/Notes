1The Task

Three separate complaints landed in the platform team's queue this week, all about the CI/CD pipeline, all seemingly unrelated. A build pipeline that calls an external package registry started failing intermittently with no config changes. A different pipeline reliably fails when uploading large build artifacts, but only the large ones. And during the last big merge-day rush, several pipelines saw random DNS resolution failures that resolved themselves once traffic died down.

"Nothing changed on our end for any of these. They're all in different pipelines, different teams, different symptoms. Feels like three unrelated flukes, but maybe there's something we're missing about how our CI environment is set up."

These three symptoms share a root cause pattern, even though they look completely different on the surface: CI/CD runners are ephemeral (spun up fresh for every run, with no warm cache or established state) and typically sit behind restrictive egress controls — two properties that create failure modes ordinary long-lived servers rarely encounter.

🔵 Why this project matters

CI/CD infrastructure is genuinely different from typical application infrastructure in ways that matter specifically for networking — the ephemeral, high-concurrency, tightly-egress-controlled nature of build runners creates its own characteristic failure patterns. Recognizing these patterns quickly is a distinct, valuable skill for any DevOps engineer who owns pipeline infrastructure.

2Why CI/CD Networking Is Different

2.1 Ephemeral runners mean zero warm state, every single run

🔵 Concept

A long-lived server accumulates DNS cache entries, established connections, and local state over its uptime — a CI runner typically starts completely fresh for every pipeline run and is destroyed afterward. This means every single run pays the FULL cost of DNS resolution and connection setup that a long-lived server would only pay once — any transient issue with a DNS resolver or a registry connection affects every run freshly, with no cached fallback to fall back on.

2.2 Egress allowlisting — necessary security, but a specific failure surface

🔵 Concept

CI runners commonly sit behind a restrictive egress firewall permitting only explicitly allowlisted destinations — package registries, git remotes, artifact stores — exactly Project 7's deny-by-default posture. The specific risk is HOW that allowlist is defined: many external services (especially anything behind a CDN) don't have fixed IP addresses, so an allowlist built from a snapshot of IPs at setup time can silently go stale as the external service's infrastructure changes, with no warning until pipelines start failing.

2.3 Reverse proxies in front of internal registries need CI-appropriate timeouts

🔵 Concept

An internal artifact/package registry is very commonly placed behind a reverse proxy (Nginx or similar) for TLS termination, caching, or load balancing. Reverse proxy default timeouts are often tuned for typical web traffic (small, fast requests) — but CI/CD artifact uploads and downloads can be large and comparatively slow, and a timeout that's perfectly reasonable for a web app can silently truncate large build artifact transfers well before they'd naturally complete.

2.4 High concurrency multiplies DNS load in a way steady traffic doesn't

🔵 Concept

Because ephemeral runners have no DNS cache to fall back on, a burst of many pipelines starting simultaneously (a common pattern around merge windows or scheduled builds) creates a genuine spike in fresh DNS query volume all at once — directly analogous to Project 24's NAT port exhaustion pattern, but for DNS resolver capacity instead of NAT ports. A resolver that handles steady traffic fine can become a bottleneck exactly during these concurrency spikes.

4Troubleshooting Method

  • 1. Confirm whether the failure correlates with WHICH external service (specific registry/CDN), WHICH transfer size, or WHICH concurrency level — each points toward a different mechanism
    • ↓
  • 2. For "intermittent, no config change" failures against external CDN-backed services: check whether the egress allowlist is IP-based and whether the target's IPs could have changed
    • ↓
  • 3. For "fails only on large transfers": check reverse proxy timeout settings against realistic large-artifact transfer duration
    • ↓
  • 4. For "fails only under high pipeline concurrency": check DNS resolver capacity and whether ephemeral runners are amplifying query volume with no caching
    • ↓
  • Remember: ephemeral infrastructure means every run is a fresh reproduction of the SAME conditions — a fix must work from true cold-start, not just "after warming up"
🟠 Warning

Never assume a CI/CD networking fix works just because a manual retry succeeded — a retry on the SAME runner might benefit from partial warm state (an already-resolved DNS entry, an already-open connection) that a genuinely fresh runner won't have. Always validate against a true cold-start run.

1sudo ip netns add ns-runner          # our CI runner — we'll treat it as freshly created for each test

9sudo ip link set veth-cdn netns ns-external-cdn; sudo ip link set gw-cdn-in netns ns-egressgw
10sudo ip link set veth-registry netns ns-registry-backend; sudo ip link set gw-registry-in netns ns-egressgw
11sudo ip netns exec ns-runner ip addr add 10.230.1.10/24 dev veth-runner
12sudo ip netns exec ns-egressgw ip addr add 10.230.1.1/24 dev gw-runner-in
13sudo ip netns exec ns-egressgw ip addr add 198.51.100.1/24 dev gw-cdn-in
14sudo ip netns exec ns-external-cdn ip addr add 198.51.100.10/24 dev veth-cdn
15sudo ip netns exec ns-egressgw ip addr add 10.230.2.1/24 dev gw-registry-in
16sudo ip netns exec ns-registry-backend ip addr add 10.230.2.10/24 dev veth-registry
17sudo ip netns exec ns-runner ip route add default via 10.230.1.1
18for ns in ns-runner ns-egressgw ns-external-cdn ns-registry-backend; do sudo ip netns exec $ns ip link set lo up; done

7Break-Fix #1 — IP-Based Egress Allowlist Breaks on IP Rotation

🔴 Break It

Simulate the external CDN-backed registry rotating to a new IP address — something entirely outside our control, and something that happens regularly with real CDN-fronted services.

bash — simulate the external service now being served from a different IP
1sudo ip netns exec ns-external-cdn ip addr add 198.51.100.20/24 dev veth-cdn   # the "CDN" now also answers on a new IP — simulating a real provider's infrastructure change
2sudo ip netns exec ns-external-cdn pkill -f "http.server 443"
3sudo ip netns exec ns-external-cdn python3 -m http.server 443 --bind 198.51.100.20 &   # the service is now ONLY reachable at the new IP, exactly like a real CDN cutover

Observe

bash — on ns-runner
1sudo ip netns exec ns-runner curl --max-time 3 http://198.51.100.20:443/
    curl: (28) Connection timed out
2sudo ip netns exec ns-egressgw iptables -L FORWARD -n -v --line-numbers | grep 198.51.100   # confirm our allowlist rule still only references the OLD IP
    2  ...  ACCEPT  tcp  --  10.230.1.10  198.51.100.10  tcp dpt:443   (still the old address — nothing matches the new one)
🔵 Reading the symptom

Nothing changed in OUR pipeline configuration at all — the external provider's infrastructure changed underneath us, and our IP-based allowlist, which was completely correct when written, silently became stale. This produces exactly the "intermittent failures with no configuration change on our end" pattern from the incident report — from our perspective it looks random, but it's entirely deterministic once you know the external provider rotated IPs and our allowlist never caught up.

🔴 Root Cause

The egress allowlist was defined against a specific IP address for an external, CDN-backed service whose IP addresses are subject to change outside our control, and the allowlist was never updated when that change occurred.

bash — immediate fix: add the new IP
1sudo ip netns exec ns-egressgw iptables -A FORWARD -s 10.230.1.10 -d 198.51.100.20 -p tcp --dport 443 -j ACCEPT
🟦 Production Best Practice — the durable fix isn't just "add the new IP"

For services that don't publish stable IP ranges, IP-based allowlisting is fundamentally fragile long-term. Better options: use the provider's published stable CIDR ranges if they exist, route egress through an explicit forward proxy that allowlists by HOSTNAME (via SNI inspection) rather than IP, or if IP-based allowlisting is unavoidable, build automated monitoring that detects when a previously-working destination starts failing and flags a possible IP-rotation cause specifically.

8Break-Fix #2 — Reverse Proxy Timeout Fails Only Large Artifacts

🔴 Break It

Put a reverse proxy in front of our internal registry with a timeout tuned for typical web traffic, then test both a small and a large artifact transfer.

bash — on ns-egressgw, a minimal reverse proxy in front of the registry with a short timeout
1sudo ip netns exec ns-registry-backend bash -c "head -c 2M /dev/urandom > /tmp/small-artifact.bin"   # a small artifact — should transfer quickly
2sudo ip netns exec ns-registry-backend bash -c "head -c 200M /dev/urandom > /tmp/large-artifact.bin"   # a realistic large build artifact
3sudo ip netns exec ns-registry-backend bash -c "cd /tmp && python3 -m http.server 80 --bind 10.230.2.10 &"
4sudo ip netns exec ns-registry-backend tc qdisc add dev veth-registry root tbf rate 5mbit burst 32kbit latency 400ms   # cap bandwidth to make the large transfer take a realistic amount of time in our lab, exposing timeout behavior

Observe — simulate the proxy's timeout behavior directly

bash — on ns-runner, test both artifact sizes with a short client-side timeout standing in for the proxy's own short timeout
1sudo ip netns exec ns-runner curl -s --max-time 5 -o /dev/null -w "small artifact: %{http_code} in %{time_total}s\n" http://10.230.2.10:80/small-artifact.bin
    small artifact: 200 in 0.04s   (well within a short timeout)
2sudo ip netns exec ns-runner curl -s --max-time 5 -o /dev/null -w "large artifact: %{http_code} in %{time_total}s\n" http://10.230.2.10:80/large-artifact.bin
    large artifact: 000 in 5.001s   (times out — at 5mbit and 200MB, this transfer genuinely needs well over 5 seconds)
🔵 Reading the symptom — the "small artifacts work, large ones fail" signature

A reverse proxy's default read/send timeout (commonly a value like 60 seconds, sometimes even shorter, tuned for typical fast web requests) will handle small package downloads without any issue at all — the transfer simply completes well within the window. A large build artifact, especially over a constrained or congested link, can genuinely need much longer to complete, and the proxy cuts the connection at exactly its configured timeout regardless of whether the transfer was still making healthy progress. This produces the precise real-world symptom — pipelines handling small dependencies work fine, pipelines uploading or downloading large build artifacts fail reliably.

🔴 Root Cause

The reverse proxy's timeout was configured for typical web-request durations and was too short for realistic large-artifact transfer times, causing the proxy to terminate otherwise-healthy, still-progressing large transfers.

🟦 Fix — this is a proxy configuration change

In a real Nginx reverse proxy, this means raising proxy_read_timeout and proxy_send_timeout (and potentially client_max_body_size for upload size limits) to values that comfortably exceed realistic large-artifact transfer times given your actual bandwidth — calculated similarly to Project 18's bandwidth-delay-product reasoning, but for total transfer duration rather than in-flight data.

bash — cleanup
1sudo ip netns exec ns-registry-backend tc qdisc del dev veth-registry root

9Break-Fix #3 — DNS Overload from Concurrent Ephemeral Runners

🟠 Scenario

Simulate a merge-window burst of many pipelines starting simultaneously, each performing fresh DNS resolution with no cache to fall back on — directly analogous to Project 24's connection-churn pattern, but for DNS queries.

bash — set up a lab DNS resolver with a deliberately tiny effective capacity, to make the concurrency effect reproducible on demand
1sudo ip netns exec ns-egressgw bash -c "cat > /tmp/dns.conf" <<'EOF'
no-resolv
listen-address=10.230.1.1
address=/registry.internal/10.230.2.10
dns-forward-max=2
EOF
2sudo ip netns exec ns-egressgw dnsmasq -C /tmp/dns.conf -k &   # dns-forward-max artificially limits concurrent in-flight queries this resolver will handle at once — simulating a resolver under real capacity pressure
3sudo ip netns exec ns-runner bash -c "echo 'nameserver 10.230.1.1' > /etc/resolv.conf"

Observe — simulate many "fresh runners" resolving simultaneously

bash — on ns-runner, fire a burst of concurrent fresh DNS lookups, exactly like many ephemeral runners starting at once
1for i in $(seq 1 20); do (sudo ip netns exec ns-runner getent hosts registry.internal &); done; wait   # 20 near-simultaneous, cold DNS lookups — no runner in this simulation has a warm cache
    (some resolve immediately; some are slow or fail outright, especially the later ones in the burst)
🔵 Reading the symptom

Every one of these lookups is genuinely a COLD, fresh query — exactly what happens when many independent, cache-less ephemeral runners all start at once, unlike a fleet of long-lived servers where most hosts already have a warm, cached answer most of the time and only a small fraction generate fresh resolver load. Under low concurrency, this resolver handles queries fine; under the burst, it becomes a real bottleneck, exactly the load-dependent, easy-to-miss-until-it-happens pattern from Project 24, just manifesting as DNS failures during merge-window pipeline bursts instead of NAT port exhaustion.

🔴 Root Cause

A burst of simultaneously-starting ephemeral CI runners, each performing a fully cold DNS resolution with no caching to fall back on, exceeded the resolver's effective concurrent query capacity during the burst window.

🟦 Fix — scale resolver capacity and/or reduce cold-lookup volume

Real fixes include ensuring the DNS resolver serving CI infrastructure is sized for realistic peak concurrent pipeline counts (not just average load), and where possible, using a local caching resolver layer even within short-lived runner images (a lightweight local cache still helps within a single run doing many lookups of the same hostname) to reduce the number of queries that actually need to leave the runner.

10Best Practices

🟦 Avoid pure IP-based egress allowlists for CDN-backed services

Prefer stable published CIDR ranges or hostname-based (SNI) allowlisting through a forward proxy where possible.

🟦 Size reverse proxy timeouts for realistic large-transfer durations

Not just typical web-request durations — calculate against actual artifact sizes and available bandwidth.

🟦 Size DNS resolver capacity for peak CI concurrency

Ephemeral, cache-less runners generate far more cold-lookup load per host than long-lived servers — plan for bursts, not averages.

🟦 Always validate fixes against a true cold start

A retry on the same runner may benefit from partial warm state a genuinely fresh runner won't have.

12Interview Preparation

ScenarioA CI pipeline that calls an external package registry started failing intermittently with no configuration changes on your side. What would you check?

If the registry is behind an egress allowlist and the failure is intermittent with no changes on our end, I'd suspect the external service's IP addresses changed — very common for CDN-backed services — while our allowlist, if it's IP-based, wasn't updated. I'd resolve the target hostname fresh and compare the current IPs against what's actually permitted in the egress firewall rules.

Interviewer follow-up: "How would you prevent this from recurring?" — Answer: where the provider publishes stable CIDR ranges, allowlist those instead of individual IPs; otherwise, route egress through a forward proxy that allowlists by hostname via SNI inspection rather than by IP, since the hostname is stable even when the underlying IPs aren't.
ConceptWhy are CI/CD runners more prone to DNS-related load issues than typical long-lived servers?

Because ephemeral runners start completely fresh for every pipeline run, with no accumulated DNS cache from previous activity. A fleet of long-lived servers mostly serves DNS lookups from cache; a burst of many ephemeral runners starting simultaneously generates a proportionally much larger volume of genuinely fresh, cold DNS queries all at once, which can exceed a resolver's capacity specifically during concurrency spikes even if it handles steady-state load fine.

TroubleshootingA build pipeline reliably fails when uploading large artifacts but works fine for small ones. What would you investigate?

I'd check the timeout configuration on any reverse proxy sitting in front of the destination — proxy timeouts are often tuned for typical fast web requests and can be far shorter than what a large artifact transfer genuinely needs to complete, especially over a bandwidth-constrained link. I'd compare the configured timeout against a realistic estimate of transfer duration for the actual artifact sizes involved.
