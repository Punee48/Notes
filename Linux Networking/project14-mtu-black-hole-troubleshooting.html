1The Incident

DevOps team on-prem data center-a cloud VPC-oda site-to-site VPN link vachu connect pannirukanga. Basic connectivity ellame sari — ping works, chinna API calls work, TCP handshake um clean-a complete aagudhu.

"Health check endpoint sari-a work aagudhu, chinna JSON response varudhu. Aana file upload API-a call panna, ya periya certificate bundle download panna, connection just... hang aayidudhu. No error, no reset, adhu forever wait pannikittu irukku."

Ithu dhaan classic "works with small packets, hangs with big ones" symptom — namba innum paakadha oru layer: MTU (Maximum Transmission Unit) — oru link-la evlo periya packet pogalam nu limit. Chinna packet ellam MTU-ku kaeezha irukும், easy-a pogும். Periya packet MTU-a cross panna, oru "fragmentation needed" process trigger aaganum — adhu correctly nadakalana, packet silent-a drop aagi, "black hole" nu solranga.

🔵 Ithu yean important

VPN tunnels (IPsec, GRE, WireGuard), cloud overlay networks, ellame extra headers add pannும், adhunala effective MTU kammi aagும். Ithு romba common production issue — "small stuff works, big stuff hangs" nu kettaudhane, MTU black hole-a suspect pannanும். Firewall/ICMP filtering konjo aggressive-a irundha, ithு especially frequent-a varum.

2MTU Foundation

2.1 MTU — oru link-la max packet size

🔵 Concept

Ethernet-la default MTU 1500 bytes — idhukku mela oru packet periya-a irundha, adha anுppுra munnaadi, konjo pannanும். VPN tunnels-la, IPsec/GRE headers add aagுறதுனால், "effective" MTU kammi-a irukும் (like 1400 or 1436) — ஆனா client-ku ithு theriyாdhு, adhu still 1500 nu nenaikும், unless namba explicit-a solli vaikும்.

2.2 DF bit — "Don't Fragment"

🔵 Concept

Modern TCP stacks, packet anுppுறாppo, DF (Don't Fragment) bit-a set pannும் — idhu router-ku solllுறthu, "indha packet-a fragment pannாதே; fit aagலைனா, drop pannிடு, aana enakku solllu." Ithு efficiency-ku nalladhு (fragmentation romba expensive), aana correctly work aaganும்na, router "fragmentation needed" message thirumba anுppanும்.

2.3 Path MTU Discovery (PMTUD) — automatic-a correct size kandupidikுறathு

🔵 Concept

Sender oru periya, DF-set panna packet anுppுறாru. Path-la edho router-ku அது periyaனு fit aagலைனа, adhு packet-a drop pannிடும், aana ஒரு ICMP "Fragmentation Needed" (Type 3, Code 4) message thirும்ப anுppuvarnும், "indha size mattum dhaan support pannுறேன்" nu solli. Sender indha ICMP message vaangி, adhுkku match aagும் padி, chinna packets anுppத் தொடங்குறாரு. Idhே PMTUD — automatic, self-correcting mechanism.

2.4 Black hole — PMTUD-oda ICMP reply, path-la evlo blocked

🔵 Concept — indha project-oda main villain

Konjo firewalls, "security"-ku nu, ellaa ICMP-a um block pannும் — including indha crucial "Fragmentation Needed" message. Adhu blocked aana, sender-ku ஒருபோதும் theriyாதू, "chinna packet anுppणும்" nu. Adhு periya packet-a repeat repeat-a anுppிக்கிட்டே irukும், every time silent-a drop aagும், no error, no ICMP, connection just hangs forever. Idhுdhaan "MTU black hole" — namba incident exact-a idhு dhaan.

4Troubleshooting Method

  • 1. Confirm the "small works, big hangs" pattern — chinna curl request test pannu, periya payload test pannu
    • ↓
  • 2. ping -M do -s <size> vachu, binary search pannிடி, evlo size varaikkும் DF-set packet pogुthu nu kandுpudi
    • ↓
  • 3. tracepath vachu, automatic-a path MTU discover pannு try pannு
    • ↓
  • 4. tcpdump-la, ICMP type 3 code 4 (frag needed) messages varuthaa nu paaru — varadhu-na, black hole confirm
    • ↓
  • Fix — MTU adjust pannலாm, illa TCP MSS clamping (ICMP-a depend pannாma) use pannலாம்
🟠 Warning

Plain ping (DF bit illama) always success aagும், even MTU problem irundhalும் — because default ping packets chinna-a irukும். Always -M do -s <size> vachu explicit-a periya, DF-set packet test pannu.

7Break-Fix #1 — The Black Hole (ICMP Blocked)

🔴 Break Pannalam

Gateway-la, ICMP "fragmentation needed" message-a block pannுவோம் — romba common "security hardening" mistake, real production firewalls-la.

bash — on ns-vpn-gw
1sudo ip netns exec ns-vpn-gw iptables -A FORWARD -p icmp --icmp-type fragmentation-needed -j DROP   # exact-a idhே message-a mattum block pannுறom, PMTUD-a break panna

Paathukalaam

bash — on ns-onprem, periya, DF-set packet anுppி paaru
1sudo ip netns exec ns-onprem ping -M do -s 1472 -c 3 10.100.2.10   # -M do = DF bit set pannு; -s 1472 = 1472 bytes payload (+28 bytes header = 1500 total, exact-a on-prem MTU limit)
    100% packet loss   (no ICMP reply, no error — simple-a silent-a drop aagுthu)
2sudo ip netns exec ns-onprem timeout 8 curl http://10.100.2.10:8080/bigfile.bin   # periya file download try pannு (namba oru bigfile create pannanum, next command)
    (hangs, no error, no data — exact-a incident-la sonna symptom)
bash — capture vachu confirm pannலாm
1sudo ip netns exec ns-vpn-gw tcpdump -i gw-onprem-in -nn 'icmp or (tcp and greater 1400)' -c 5   # ICMP packets or periya TCP segments mattum capture pannு
    (periya packets client-ilருந்து varுthu, aana ஒரே ஒரு ICMP reply-um kaanadhu)
🔵 Reading the symptom

Ithு dhaan black hole — periya, DF-set packet anுppினா, silent-a drop aaguthu, ICMP reply illa. Client-ku ஒருபோதும் theriyாthு "chinna packet anுppणும்" nu, adhு same periya size-a repeat repeat-a try pannிக்கிட்டே irukும், every time silent-a fail aagும். No error message, no reset, connection just hangs — classic MTU black hole signature.

🔴 Root Cause

VPN tunnel segment-oda MTU (1400), on-prem client-oda MTU (1500) vida chinna-a irundhadhு, adhு periya problem illa — real problem, PMTUD-ku thevaiaana ICMP "fragmentation needed" message-a gateway firewall block pannிருந்தது, adhுனால் client-ku correct size-a ஒருபோதும் theriyாmal poaduthu.

bash — cleanup, next break-la ICMP allow pannலாm
1sudo ip netns exec ns-vpn-gw iptables -D FORWARD -p icmp --icmp-type fragmentation-needed -j DROP   # block remove pannிடலாம்

8Break-Fix #2 — Same MTU Drop, but PMTUD Works Properly

🟠 Compare Pannலாம்

Ippo, same MTU mismatch (1400 vs 1500) irukும், aana ICMP block pannாma — PMTUD sari-a work pannும்னா enna aagும் nu paakalam.

Test pannலாm

bash — on ns-onprem, same periya packet test
1sudo ip netns exec ns-onprem ping -M do -s 1472 -c 3 10.100.2.10   # same test, ICMP இப்போ block illa
    ping: local error: Message too long, mtu=1400   (ippo IMMEDIATE-a error varுthu — hang aagலைii)
2sudo ip netns exec ns-onprem tracepath 10.100.2.10   # tracepath — automatic-a path MTU discover pannும் tool
    1:  10.100.1.1     0.123ms
    1:  10.100.1.1     0.045ms pmtu 1500
    2:  10.100.2.10     0.089ms
        Resume: pmtu 1400   (tracepath correctly kandupudichuruchu, path MTU 1400 nu)
🔵 Reading the difference

Ippo enna maariduchunu paaru — ping IMMEDIATE-a "Message too long, mtu=1400" nu solllுthu, hang aagலை. Yean-na, gateway correctly ICMP "fragmentation needed" reply anுppuchu, on-prem client-oda kernel adha vaangி, path MTU cache pannிக்கிட்டு, appuram automatic-a chinna packets anுppத் தொடங்குறாrudhu. tracepath um exact-a same information-a kaattுdhu — path MTU 1400 nu clean-a confirm pannuthu, no hang, no mystery.

🟢 Ithu dhaan "correct" behavior

MTU mismatch irundhalும், ICMP path clear-a irundha, PMTUD automatic-a self-heal pannிடும். Namba Break #1-la paatha problem, MTU mismatch-oda problem illa — ICMP blocking-oda problem.

🟦 Best Practice

Firewall rules design pannுறாppo, ICMP type 3 (destination unreachable) — especially code 4 (fragmentation needed) — ellame block pannாதீங்க. "ICMP block pannுறathு security-ku nalladhு" nu blanket rule vachा, ithு maadhiri silent black holes create aagும்.

9Break-Fix #3 — The Real Production Fix: TCP MSS Clamping

🟠 Scenario

Reality-la, namba control pannாthа networks (partner links, public internet path) la, ICMP evlo devices block pannும்னு namba control panna mudியாthு. Adhுனால், ICMP-a depend pannாmal, direct-a MSS (Maximum Segment Size)-a clamp pannுறathு standard production fix.

bash — on ns-vpn-gw, ICMP thirumba block pannி, MSS clamping mattum vachu paakalam
1sudo ip netns exec ns-vpn-gw iptables -A FORWARD -p icmp --icmp-type fragmentation-needed -j DROP   # ICMP thirumba block pannுறom, worst-case simulate panna
2sudo ip netns exec ns-vpn-gw iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu   # TCP handshake-oda SYN packet-la, MSS value-a automatic-a correct-a rewrite pannும்
TokenMeaning
-t mangle -A FORWARDmangle table — packet contents modify panna (headers rewrite panna) use pannும். FORWARD chain, idhு pass-through traffic-ku, namba gateway scenario exact-a idhே.
--tcp-flags SYN,RST SYNSYN packets mattum match pannும் (TCP handshake-oda first packet) — MSS value idhே packet-la dhaan negotiate aagும், so idhே dhaan correct place to intercept.
TCPMSS --clamp-mss-to-pmtuMSS value-a automatic-a, indha gateway-oda outgoing interface MTU-ku match aagும் padி, rewrite pannும் — ICMP, PMTUD, edhுவும் thevai illa. Handshake stage-la dhaan correct segment size negotiate aagிடும்.

Test pannலாm

bash — on ns-onprem, periya file download try pannு, ippo ICMP blocked-um
1sudo ip netns exec ns-cloud-server bash -c "head -c 5M /dev/urandom > /tmp/bigfile.bin"   # 5MB test file create pannு
2sudo ip netns exec ns-cloud-server python3 -m http.server 8080 --bind 10.100.2.10 --directory /tmp &   # idha serve panna
3sudo ip netns exec ns-onprem curl -s -o /dev/null -w "downloaded in %{time_total}s\n" http://10.100.2.10:8080/bigfile.bin   # ippo periya file download pannு, MSS clamping active-a irukும் state-la
    downloaded in 0.412s   (successfully complete aayiduchu — ICMP blocked irundhalும்!)
🔵 Reading the fix

ICMP இப்போவும் blocked-a dhaan irukு, aana connection ippo work aaguthu — yean-na TCP handshake time-lae, MSS value correct-a negotiate aayiduchu (mangle table rule vachu). Adhukku appuram, client never even TRIES to send an oversized packet — so PMTUD, ICMP, edhுவும் thevai illa. Idhு dhaan production VPN gateways-la, MSS clamping ivvalavு commonly use pannுறathுku reason — ICMP filtering evlo unpredictable-a irundhalும், idhு reliable-a work pannும்.

🟢 Validate

Curl download clean-a complete aagிடுchu, no hang, ICMP thevai இல்லாம்லேயே. Ithு dhaan real production-la recommend pannுற fix.
