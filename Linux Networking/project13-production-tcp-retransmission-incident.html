2Retransmission Internals

2.1 RTO — Retransmission Timeout

🔵 Concept

TCP oru packet anuppitu, adhukku ACK vara evlo time wait pannanum nu, dynamic-a calculate pannum — idhுdhaan RTO (Retransmission Timeout). Ithu fixed value illa — connection-oda measured RTT (round trip time) vachu, kernel continuously adjust pannikittu irukkum. RTT evlo consistent-a irukka, adhu vachu RTO tight-a irukkum; RTT fluctuate aana, RTO safety margin-oda periya-a irukkum.

2.2 Exponential backoff — retry ஒவ்வொரு time-um wait double aagum

🔵 Concept

Oru packet lost aayi, RTO expire aagi, TCP retransmit pannuchu-nu vachukalam. Adhே packet AGAIN lost aana, next retry-ku wait time DOUBLE aagum (1s → 2s → 4s → 8s...). Ithு "exponential backoff" — network already stressed-a irundha, konjo konjo-a retry pannuradhu, network-a innum overload pannama irukka. Ithu dhaan namba incident-la "sometimes connections randomly hang for several seconds" nu symptom kaattudhu.

2.3 Congestion window (cwnd) — loss aana, TCP "brake" podum

🔵 Concept

TCP-oda congestion control, evlo data "in flight" (sent but not yet acknowledged) irukkalam nu track pannum — ithே congestion window (cwnd). Loss detect aana (retransmission via duplicate ACKs or timeout), TCP assume pannum "network congested-a irukku" nu, cwnd-a DRASTIC-a kammi pannidum — sometimes half-a, sometimes almost zero-ku (timeout case-la). Appuram, "slow start" mode-la, konjo konjo-a cwnd-a thirumba build pannum. Idhु exact-a namba incident symptom — chinna loss, periya throughput drop, slow recovery.

2.4 Nagle's algorithm + Delayed ACK — rendு nalla features, serndha problem

🔵 Concept

Nagle's algorithm — chinna packets-a individual-a anuppama, batch pannitu anுppுவது (efficiency-ku). Delayed ACK — receiver side-la, ACK immediate-a anுppாமல், konjo wait pannitu (piggyback pannitu) anுppுவது. Rendும individually nalla optimization dhaan — aana rendும serndhu vandha, sender Nagle-vachu wait pannுtu irukkும், receiver delayed ACK-vachu wait pannுtu irukkும், rendுperum wait pannுtu classic ~40ms stall varum. Ithு loss illa — pure timing interaction problem.

7Break-Fix #1 — RTO Exponential Backoff, Live

🔴 Break Pannalam

Server-a completely unreachable pannuvom (firewall drop) — SYN retries-oda backoff-a live-a paakalam.

bash — on ns-billing-api
1sudo ip netns exec ns-billing-api iptables -A INPUT -p tcp --dport 8080 -j DROP   # SYN packet silent-a drop pannidum, no reply varadhu

Paathukalaam

bash — on ns-recharge-client, capture pannitu, connection try pannu
1sudo ip netns exec ns-recharge-client tcpdump -i veth-client -nn 'tcp port 8080' -c 6 &   # first 6 packets mattum capture pannu — namba retries-a paakanum
2sudo ip netns exec ns-recharge-client timeout 20 curl http://10.95.1.20:8080/   # 20 seconds wait pannitu give up pannu
    14:00:00.000  SYN   (attempt 1)
    14:00:01.000  SYN   (retry — ~1s wait, RTO #1)
    14:00:03.000  SYN   (retry — ~2s wait, RTO #2, doubled)
    14:00:07.000  SYN   (retry — ~4s wait, RTO #3, doubled again)
🔵 Reading the symptom

Namba Section 3-la paatha diagram, ippo real capture-la kaanudhu — ovvoru retry-kum wait time double aagudhu (1s, 2s, 4s...). Application side-la, ithu "connection just hangs for a while" nu feel aagum, aana underneath, TCP systematically, predictable-a retry pannikittu irukku, network-a overload pannama.

🔴 Root Cause

Server unreachable-a irundhadhunala, TCP exponential backoff mode-la retry pannikittu irundhudhu — expected behavior dhaan, aana application timeout config romba periya-a irundha, user-ku romba naala wait pannanum nu varum.

bash — fix
1sudo ip netns exec ns-billing-api iptables -D INPUT -p tcp --dport 8080 -j DROP   # block remove pannidalam
🟦 Best Practice

Application-level connection timeout, evlo naala TCP retry pannum nu accept pannalam nu, deliberate-a set pannanum — default OS-level retry behavior-ku wait pannama, app-level-la reasonable short timeout vachu, fast-fail pannaradhu nalla practice.

8Break-Fix #2 — Congestion Window Collapse

🔴 Break Pannalam

Chinna % packet loss introduce pannuvom (namba incident-la irundha 2-3% maadhiri) — periya bulk transfer-la evlo throughput drop aagudhu nu paakalam.

bash — on ns-recharge-client
1sudo ip netns exec ns-recharge-client tc qdisc add dev veth-client root netem loss 3%   # realistic-a chinna 3% loss simulate pannுdhu, namba incident maadhiri

Paathukalaam

bash — periya file transfer download pannu, size measure pannu
1sudo ip netns exec ns-billing-api bash -c "head -c 20M /dev/urandom > /tmp/bigfile.bin"   # 20MB test file create pannu
2sudo ip netns exec ns-billing-api python3 -m http.server 8080 --bind 10.95.1.20 --directory /tmp &   # idha serve panna, restart the server pointing at /tmp
3sudo ip netns exec ns-recharge-client bash -c "time curl -s -o /dev/null http://10.95.1.20:8080/bigfile.bin"   # download time measure pannu, 3% loss vachu
    real   0m8.412s   (namba baseline-la, loss illama, ithu konjo seconds mattum dhaan aaganum)
🔵 Reading the symptom

3% packet loss dhaan — chinna number maadhiri thonum. Aana result — download time DRAMATICALLA periya aayidhudhu. Yean-na, ovvoru loss detect aana, TCP cwnd-a drastic-a kammi pannidum, appuram slow-start mode-la konjo konjo-a mattum thirumba build pannும். Sustained loss irundha, cwnd never fully recover aagadhu, throughput permanently kammi-a irukkum. Idhு dhaan namba incident-oda "chinna loss, periya latency impact" mystery-oda answer.

🔴 Root Cause

Sustained, chinna % packet loss, TCP-oda congestion control mechanism-a repeatedly trigger pannuchu — cwnd baaru baaru collapse aagi, slow-start-la mattum recover aaganum-nu irundhadhunala, achievable throughput permanently kammi-a irundhudhu.

bash — fix (lab cleanup; real fix — network path-la loss address pannanum)
1sudo ip netns exec ns-recharge-client tc qdisc del dev veth-client root netem   # loss simulation remove pannidalam
🟦 Best Practice

"Only X% loss" nu dismiss pannadha — sustained loss, TCP-oda congestion control vachu, romba periya throughput impact create pannும். Real fix — network path-la (cable, switch, driver, wireless link) actual loss source-a kandupudichu fix pannanum, app-level workaround mattum podradhu illa.

9Break-Fix #3 — Nagle + Delayed ACK Stall

🔴 Break Pannalam

Loss illa indha case-la — pure timing interaction problem. Chinna, chinna messages rapid-a anுppுra client script vachu simulate pannுவோம்.

bash — on ns-recharge-client, small-write client (Nagle's algorithm default-a ON irukkum)
1sudo ip netns exec ns-recharge-client bash -c "cat > /tmp/small_writes.py" <<'EOF'
import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect(('10.95.1.20', 8080))
start = time.time()
for i in range(5):
    s.send(b"x")          # ஒரே ஒரு byte anuppுறோம் — Nagle algorithm ithை wait pannitu batch pannும் try pannும்
    data = s.recv(100)    # reply-ku wait pannுறோம்
print("total time:", time.time() - start)
EOF
2sudo ip netns exec ns-recharge-client python3 /tmp/small_writes.py   # run pannu, total time-a paaru
    total time: 0.203s   (5 chinna sends-ku, ithu expect panradhை vida romba periya-a irukku)
🔵 Reading the symptom

~40ms per round trip maadhiri delay kaanum, total-a serndhu 200ms+ aagidhudhu — ellame chinna byte anுppுறதுக்கு. Ithு classic Nagle + delayed ACK interaction — sender chinna packet-a batch pannanum-nu wait pannுறாரு, receiver ACK-a delay pannுறாரு, rendும் perum wait pannுறாரு, ஒருவர் oruvara timeout pannும் varaikkும். Loss illa, retransmission illa — pure protocol-level timing mismatch.

🔴 Root Cause

Application chinna, chinna writes pannுtu irundhadhunala (batch pannாமல்), Nagle's algorithm (sender side) and delayed ACK (receiver side) rendும் serndhு, ovvoru round-trip-kum artificial delay create pannுchu.

bash — fix: TCP_NODELAY vachu Nagle-a disable pannu, indha connection-ku
1sudo ip netns exec ns-recharge-client bash -c "cat > /tmp/nodelay_writes.py" <<'EOF'
import socket, time
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)  # Nagle's algorithm-a OFF pannுறோம் இந்த socket-ku
s.connect(('10.95.1.20', 8080))
start = time.time()
for i in range(5):
    s.send(b"x")
    data = s.recv(100)
print("total time:", time.time() - start)
EOF
2sudo ip netns exec ns-recharge-client python3 /tmp/nodelay_writes.py
    total time: 0.012s   (romba fast-a aayidhudhu, TCP_NODELAY vachu)
TokenMeaning
socket.TCP_NODELAY, 1Idhu Nagle's algorithm-a off pannும் socket option — ovvoru send() um immediate-a wire-ku pogum, batch pannும் wait pannாmal. Latency-sensitive, chinna-message protocols (like this billing API's request/response pattern) ku ithு very commonly recommended.
🟦 Best Practice

Request/response, chat-style, ya real-time protocols (romba chinna messages, frequent-a) ku, TCP_NODELAY set pannுவது common practice. Aana bulk data transfer (large file, streaming) ku Nagle's algorithm nalladhu-dhaan — efficiency kudukும். Idhு "one size fits all" fix illa, workload pattern-a base panni decide pannanும்.

10Production Best Practices

🟦 Chinna loss %-a underestimate pannadha

Sustained loss, TCP congestion control vachu, periya throughput impact create pannும்.

🟦 Backoff pattern-a recognize pannu

1s, 2s, 4s, 8s doubling — capture-la ithை paartha, immediate-a RTO/backoff-a suspect pannu.

🟦 Nagle vs TCP_NODELAY, workload-a base pannி

Chinna, frequent messages-ku NODELAY; bulk transfer-ku default Nagle nalladhu.

🟦 App-level timeout deliberate-a set pannु

OS-level retry/backoff-ku exposed-a irundha, user experience-a badly affect pannும்.
