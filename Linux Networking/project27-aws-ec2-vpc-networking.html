1The Task

The platform team is migrating the e-commerce checkout system from on-prem to AWS. Everyone on the call keeps treating VPCs, security groups, and route tables as entirely new, cloud-specific concepts to learn from scratch.

"We keep getting connectivity issues that 'shouldn't be possible' according to the AWS console — the security group looks right, but something's still blocked. I think we're missing something about how this actually works underneath the console."

Here's the thing worth knowing before diving into any AWS-specific documentation: a VPC is conceptually a private network you already know how to build (Project 1-2), a subnet is exactly what it sounds like, a route table is exactly Project 2's routing table, a security group is a stateful firewall extremely similar to what we built in Project 7, and VPC peering is architecturally similar to Project 21's tunneling concept. AWS didn't invent new networking — it built a managed control plane on top of the same fundamentals.

2Translating AWS Terms to Linux Primitives

2.1 VPC and subnets — a private network and its segments

🔵 Concept

A VPC (Virtual Private Cloud) is a private IP address space you define — conceptually identical to any private network we've built with namespaces throughout this masterclass. Subnets divide that VPC into smaller address ranges, typically mapped to availability zones — the same segmentation concept from Project 20's VLANs, just managed through AWS's control plane instead of manual 802.1Q tagging.

2.2 Route tables — exactly Project 2, with an AWS-managed interface

🔵 Concept

An AWS route table is functionally identical to the Linux routing tables from Project 2 — a list of "for this destination CIDR, send traffic this way" entries, evaluated by longest-prefix-match, exactly like every Linux route table we've inspected with ip route. A route table associated with a subnet controls exactly what that subnet's instances can reach directly.

2.3 Security groups vs Network ACLs — stateful vs stateless, exactly Project 7's lesson

🔵 Concept

Security groups are STATEFUL — attached to individual instances/interfaces, and if you allow inbound traffic on a port, the corresponding return traffic is automatically allowed, exactly like Project 7's ESTABLISHED,RELATED rule pattern; you never write a separate "allow the reply" rule. Network ACLs (NACLs) are STATELESS and applied at the subnet level — you must explicitly allow BOTH inbound and outbound directions separately, exactly like the fully manual, pre-conntrack firewall rule pairs we'd have needed without connection tracking. This stateful-vs-stateless distinction is the single most common source of "the security group looks completely correct but it's still not working" tickets.

2.4 NAT Gateway and VPC Peering — Project 8 and Project 21, managed

🔵 Concept

An AWS NAT Gateway does exactly what our hand-built MASQUERADE rules did in Project 8 — lets instances in a private subnet (no public IP) reach the internet outbound, translating their source address, while remaining unreachable from the internet inbound. VPC Peering connects two separate VPCs' private address spaces together, conceptually similar to Project 21's tunneling — an underlay (AWS's own network) carrying traffic between two otherwise-separate private networks, coordinated through route table entries on both sides.

4Troubleshooting Method

  • 1. Check the route table associated with the relevant subnet first — exactly Project 2's method, just AWS-managed
    • ↓
  • 2. Check the security group (stateful, instance-level) — remember return traffic is automatic, don't add a redundant reverse rule
    • ↓
  • 3. Check the NACL (stateless, subnet-level) — remember BOTH directions need explicit rules here, unlike security groups
    • ↓
  • 4. For cross-VPC traffic, check the peering connection's route table entries on BOTH sides — exactly like Project 21's underlay routing requirement
    • ↓
  • Once route table, security group, and NACL are all confirmed correct, the remaining troubleshooting is identical to any earlier project — DNS, application-layer, etc.
🟠 Warning

The single most common AWS networking confusion is applying stateful-firewall thinking to a NACL — forgetting that NACLs need explicit rules for BOTH directions, unlike security groups. A security group that's "obviously correct" combined with a NACL missing the return direction produces exactly the symptom from Section 1's complaint.

5Model a VPC with Two Subnets Locally

We don't need an AWS account to understand these mechanics — every piece maps directly onto tools we've already used.

bash — run as root/sudo
1sudo ip netns add ns-public-subnet    # models the public subnet — has a route straight to the "internet"
2sudo ip netns add ns-private-subnet   # models the private subnet — checkout-app lives here, no direct internet route
3sudo ip netns add ns-internet         # represents the internet / an external API our checkout-app needs to reach
4sudo ip link add veth-pub type veth peer name igw-pub-in
5sudo ip link add veth-priv type veth peer name nat-priv-in
6sudo ip link set veth-pub netns ns-public-subnet; sudo ip link set igw-pub-in netns ns-internet
7sudo ip link set veth-priv netns ns-private-subnet; sudo ip link set nat-priv-in netns ns-public-subnet   # the NAT Gateway "lives inside" the public subnet, exactly like real AWS
8sudo ip netns exec ns-public-subnet ip addr add 10.50.1.10/24 dev veth-pub
9sudo ip netns exec ns-internet ip addr add 203.0.116.1/24 dev igw-pub-in
10sudo ip netns exec ns-public-subnet ip addr add 10.50.2.1/24 dev nat-priv-in   # the NAT gateway's address on the private subnet's side
11sudo ip netns exec ns-private-subnet ip addr add 10.50.2.10/24 dev veth-priv
12for ns in ns-public-subnet ns-private-subnet ns-internet; do sudo ip netns exec $ns ip link set lo up; done
13sudo ip netns exec ns-public-subnet bash -c "ip link set veth-pub up; ip link set nat-priv-in up; sysctl -w net.ipv4.ip_forward=1"
14sudo ip netns exec ns-private-subnet ip link set veth-priv up
15sudo ip netns exec ns-internet ip link set igw-pub-in up
16sudo ip netns exec ns-private-subnet ip route add default via 10.50.2.1   # private subnet's route table: default route points at the NAT Gateway, not the internet directly
17sudo ip netns exec ns-public-subnet ip route add 203.0.116.0/24 dev veth-pub   # public subnet's route table: knows how to reach the "internet" segment directly
18sudo ip netns exec ns-public-subnet iptables -t nat -A POSTROUTING -s 10.50.2.0/24 -o veth-pub -j MASQUERADE   # the NAT Gateway's actual mechanism — identical to Project 8
19sudo ip netns exec ns-public-subnet iptables -A FORWARD -s 10.50.2.0/24 -j ACCEPT
20sudo ip netns exec ns-internet python3 -m http.server 443 --bind 203.0.116.1 &   # an external API our checkout-app needs to reach

6Verify Baseline

bash — confirm the private-subnet instance can reach the internet via the NAT gateway
1sudo ip netns exec ns-private-subnet curl -s -o /dev/null -w "%{http_code}\n" http://203.0.116.1:443/
    200
🟢 Baseline confirmed

The private-subnet instance successfully reaches an external service through the NAT Gateway, exactly like a real checkout-app instance would reach a payment provider's API. This is our working baseline.

7Break-Fix #1 — Security Group Correct, NACL Blocking

☁ AWS Framing

In real AWS, this would be: security group on the checkout-app instance correctly allows outbound HTTPS, but the subnet's NACL only has an inbound allow rule for the return traffic missing — because someone configured it thinking statefully, forgetting NACLs aren't.

🔴 Break It (modeled with iptables, standing in for a stateless NACL)

We'll simulate a stateless NACL by adding explicit, DIRECTION-SPECIFIC rules on the public subnet's forwarding path — allowing outbound but forgetting the inbound return leg, exactly the security-group-vs-NACL mental model mismatch.

bash — on ns-public-subnet, simulate a stateless NACL missing the return direction
1sudo ip netns exec ns-public-subnet iptables -F FORWARD   # clear our previous stateful rule to simulate stateless NACL-style rules instead
2sudo ip netns exec ns-public-subnet iptables -A FORWARD -s 10.50.2.0/24 -d 203.0.116.0/24 -p tcp --dport 443 -j ACCEPT   # "NACL outbound rule" — allows the request to leave
3# MISSING: no corresponding rule allowing the return traffic (source port 443, destination = private subnet) back in — exactly the stateless NACL trap

Observe

bash
1sudo ip netns exec ns-private-subnet curl --max-time 3 http://203.0.116.1:443/
    curl: (28) Connection timed out
🔵 Reading the symptom

The request leaves correctly (the "NACL outbound" rule matches), but the reply — coming back from source port 443 to the private subnet's address — has no matching rule allowing it back in, since we're modeling stateless behavior with no automatic ESTABLISHED,RELATED handling. This is precisely the real-world "security group looks completely correct, but a NACL doesn't have return traffic explicitly allowed" incident — the engineer checking only the security group (correctly configured, stateful) never finds the problem, because it's one level up, at the stateless subnet-level NACL.

🔴 Root Cause

A stateless rule set (modeling a NACL) only permitted the outbound direction of the connection, with no explicit rule for the inbound return traffic — the exact mistake that's easy to make when applying stateful mental models to a stateless control.

bash — fix: restore stateful handling (in real AWS, this means checking/fixing the NACL's inbound rule, not the security group)
1sudo ip netns exec ns-public-subnet iptables -A FORWARD -m state --state ESTABLISHED,RELATED -j ACCEPT
🟦 Production Best Practice

When troubleshooting AWS connectivity, always check BOTH the security group AND the NACL explicitly — and remember they follow different models entirely: security groups are stateful (Project 7's ESTABLISHED,RELATED pattern applies automatically), NACLs are stateless (you must explicitly allow both directions, like pre-conntrack firewall rules).

8Break-Fix #2 — Route Table Missing a Peering Route

☁ AWS Framing

Two VPCs are peered (the connection itself shows "Active" in the console), but one side's route table was never updated to actually route traffic through the peering connection — a very common real-world oversight, since creating the peering connection and adding the routing entries are two entirely separate steps.

🔴 Break It

Simulate this by removing the private subnet's route to a hypothetical peered VPC, while leaving everything else about the "peering" (our underlay connectivity) intact.

bash — first, add a route representing "the peered VPC exists and is reachable at the network layer"
1sudo ip netns exec ns-private-subnet ip route add 10.90.0.0/16 via 10.50.2.1   # route table entry pointing toward a peered VPC's CIDR, via the (in real AWS) peering connection
2sudo ip netns exec ns-private-subnet ip route del 10.90.0.0/16 via 10.50.2.1   # now REMOVE it, simulating the common mistake: peering connection created, but route table entry never added

Observe

bash
1sudo ip netns exec ns-private-subnet ip route get 10.90.1.5   # where would traffic to the peered VPC actually go right now?
    10.90.1.5 via 10.50.2.1 dev veth-priv   (falls through to the DEFAULT route — toward the NAT Gateway/internet, NOT toward the peered VPC at all)
🔵 Reading the symptom

Exactly Project 2's "missing specific route falls back to default" lesson — without an explicit route table entry for the peered VPC's CIDR, traffic destined for it silently follows the default route instead (toward the NAT Gateway, ultimately trying to reach the real internet, where the peered VPC's private addresses mean nothing). In the AWS console, this is deceptively easy to miss because the peering connection itself shows as healthy and "Active" — the connection working has nothing to do with whether any given subnet's route table actually uses it.

🔴 Root Cause

The peering connection existed and was active, but the private subnet's route table had no entry directing traffic for the peered VPC's CIDR through it, so that traffic silently fell through to the default route instead.

bash — fix
1sudo ip netns exec ns-private-subnet ip route add 10.90.0.0/16 via 10.50.2.1
🟦 Production Best Practice

A VPC peering connection being "Active" only proves the connection itself exists — it says nothing about whether any specific subnet's route table actually directs traffic through it. Always verify route table entries explicitly on BOTH sides of a peering relationship, exactly like Project 21's underlay-routing verification for tunnels.

9Break-Fix #3 — No NAT Gateway for Private Subnet Egress

☁ AWS Framing

A new private subnet was created for a batch of instances, but nobody added a NAT Gateway route to its route table — the instances have no way to reach the internet at all, not even for routine things like package updates or calling external APIs.

🔴 Break It

Remove the private subnet's default route entirely, simulating a route table that was never configured with any egress path.

bash — on ns-private-subnet
1sudo ip netns exec ns-private-subnet ip route del default via 10.50.2.1

Observe

bash
1sudo ip netns exec ns-private-subnet curl --max-time 2 http://203.0.116.1:443/
    curl: (7) Couldn't connect to server
2sudo ip netns exec ns-private-subnet ip route show   # confirm there's genuinely no default route at all
    10.50.2.0/24 dev veth-priv proto kernel scope link src 10.50.2.10   (only the directly-connected subnet — nothing else)
🔵 Reading the symptom

This is the simplest failure in this project, but a genuinely common real-world one — a private subnet's route table was simply never given a path to anywhere outside its own CIDR at all. Unlike Break-Fix #2 (which had a route, just the wrong one — the default), this subnet has NO default route whatsoever, so any destination outside its own directly-connected range fails immediately with "no route," rather than silently going the wrong way.

🔴 Root Cause

The private subnet's route table was never configured with any route to the NAT Gateway (or any other egress path), leaving instances in it completely unable to reach anything outside the subnet's own address range.

bash — fix
1sudo ip netns exec ns-private-subnet ip route add default via 10.50.2.1
🟦 Production Best Practice

When provisioning any new private subnet, explicitly verify it has a route to a NAT Gateway (or other appropriate egress) as a standard, checklist-level provisioning step — exactly the kind of thing that's trivial to catch with peer review (Project 25) before it ships.

10Best Practices

🟦 Know which AWS control is stateful and which isn't

Security groups are stateful (like Project 7's conntrack rules); NACLs are stateless — never assume one behaves like the other.

🟦 "Active" peering ≠ routed peering

Always verify explicit route table entries on both sides — the connection existing says nothing about whether traffic actually uses it.

🟦 Treat NAT Gateway routes as a provisioning checklist item

Every new private subnet needs an explicit egress route — this is easy to forget and easy to catch in review.

🟦 Translate to Linux primitives when stuck

VPC=private network, subnet=segment, route table=Project 2, security group=Project 7, NAT Gateway=Project 8, peering=Project 21 — every AWS troubleshooting tool from this masterclass still applies conceptually.

12Interview Preparation

ScenarioA security group looks completely correct, but an EC2 instance still can't receive expected traffic. What would you check?

I'd check the subnet's Network ACL next, since it's a completely separate, stateless control — unlike a security group, which automatically allows return traffic for anything it permits, a NACL requires explicit rules in BOTH directions. A very common mistake is configuring a NACL with stateful assumptions, forgetting to add the inbound rule for return traffic on an otherwise-correct outbound-allow rule.

Interviewer follow-up: "What if both the security group and NACL look correct?" — Answer: I'd check the subnet's route table next — confirming the traffic is even being routed where it's expected to go, especially for cross-VPC traffic where a peering connection can be active without the route table actually directing traffic through it.
ConceptWhat's the difference between a security group and a Network ACL?

A security group is stateful and attached at the instance/interface level — if you allow inbound traffic on a port, the corresponding outbound reply is automatically permitted, similar to a Linux firewall with connection tracking. A NACL is stateless and applied at the subnet level — you must explicitly allow both inbound and outbound directions separately, since there's no automatic tracking of established connections.

TroubleshootingTwo VPCs show an active peering connection, but instances still can't reach each other. What's the likely cause?

The peering connection being active only confirms the underlying connection exists — it doesn't mean any subnet's route table is actually configured to send traffic through it. I'd check the route tables on both sides explicitly for an entry directing the peer VPC's CIDR range through the peering connection; a very common oversight is creating the peering connection without adding the corresponding routes on one or both sides.
