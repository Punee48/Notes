1The Task

Every project so far has ended the moment the technical fix worked. In a real bank's infrastructure team, that's roughly the halfway point. A new fraud-detection microservice needs a firewall rule opened between two network zones — mechanically, this is exactly Project 7's Break-Fix #1 lab. But this time, we need to actually ship it the way a real enterprise requires.

"I don't just want the iptables rule. I want to see this go through a proper story, get reviewed by someone else, go through change management, and if anything ever goes wrong with it, I want a real RCA on file — not a Slack message saying 'fixed it.'"

This project isn't about learning a new networking concept — it's about learning the organizational scaffolding around every networking change we've made in this masterclass, and understanding exactly which failure modes that scaffolding exists to prevent.

🔵 Why this project matters

A huge number of preventable production incidents trace back not to a technical mistake, but to a skipped process step — no peer review catching an ordering bug, no rollback plan turning a two-minute fix into a two-hour outage, no RCA meaning the same root cause quietly recurs months later. Understanding WHY each stage of enterprise change management exists — not just that it exists — is what lets you follow it intelligently instead of resentfully.

2How Work Actually Reaches an Engineer

2.1 Epic → Feature → Story — work gets broken down before it reaches you

🔵 Concept

An Epic is a large body of work ("Launch fraud-detection service in production"). It's broken into Features ("Network connectivity between fraud-detection and scoring API"). Each Feature is broken into individual Stories — the actual ticket that lands on an engineer's desk ("Open firewall rule allowing fraud-detection to reach scoring-api on port 9090"). By the time work reaches you as a networking engineer, someone has usually already made the business case; your job starts at the technical story level.

2.2 Acceptance criteria — how "done" gets defined before you start

🔵 Concept

Acceptance criteria are specific, testable conditions that must be true for a story to be considered complete — "fraud-detection pod can reach scoring-api:9090" is testable; "networking works" is not. Well-written acceptance criteria remove ambiguity about what "done" means, and double as your test plan.

2.3 Peer review — a second set of eyes before anything ships

🔵 Concept

Before any change reaches production, another engineer reviews it — checking not just "does this rule look syntactically correct" but "is this rule ordered correctly, does it have unintended side effects, does it follow least-privilege" — exactly the kind of rule-ordering mistake we deliberately created in Project 7. Peer review exists specifically to catch the class of error that's invisible to the person who just wrote the change, because they're too close to it.

2.4 Change Request and CAB — proving impact and rollback were actually considered

🔵 Concept

A Change Request (CR) documents WHAT is changing, WHY, the assessed RISK and IMPACT if it goes wrong, and — critically — the ROLLBACK PLAN. The Change Advisory Board (CAB) reviews and approves CRs, particularly for production, regulated, or high-risk systems, specifically to catch changes being made without a real rollback plan or without considering their blast radius, before they're allowed to happen.

2.5 RCA — closing the loop so failures don't repeat

🔵 Concept

A Root Cause Analysis (RCA) is written after any significant incident — not just "what we did to fix it," but the actual mechanism, contributing factors, and concrete follow-up actions to prevent recurrence. We've directly seen the cost of skipping this in Project 23, where the same incident recurred twice because it was "fixed by restart" without ever being properly root-caused and documented.

4What Each Stage Is Actually For

  • Technical Analysis — decide the actual approach (which chain, which rule pattern) before writing any commands
    • ↓
  • Implementation + Testing — build and verify in a non-production environment first, exactly like every lab in this masterclass
    • ↓

    • ↓

5Stage 1-4 — Story Through Peer Review

Let's run a real story through the pipeline, using Project 7's exact segmentation firewall lab as our implementation target.

STORY: FRAUD-142 Title: Allow fraud-detection service to reach scoring-api on port 9090 Epic: Launch fraud-detection service in production Feature: Network connectivity — fraud-detection to scoring-api Acceptance Criteria: - AC1: A NEW connection from 10.60.1.10 (fraud-detection) to 10.60.2.10:9090 (scoring-api) succeeds through the segmentation firewall - AC2: No other new source/destination pair gains access as a side effect of this change - AC3: Return traffic for the above connection is correctly permitted (stateful rule present)

5.1 Technical analysis — decide the approach before touching iptables

🔵 Technical Analysis

This is precisely Project 7's baseline configuration: a scoped NEW-state ACCEPT rule for the specific source/destination/port, placed correctly relative to the existing ESTABLISHED,RELATED rule and default DROP policy. No broader rule is appropriate — AC2 specifically requires we avoid the shadowed-rule and overly-broad-rule mistakes from Project 7's break-fix scenarios.

5.2 Implementation and testing — exactly Project 7's lab

bash — on the segmentation firewall (reusing Project 7's ns-segfw), implement the story
1sudo ip netns exec ns-segfw iptables -A FORWARD -s 10.60.1.10 -d 10.60.2.10 -p tcp --dport 9090 -m state --state NEW -j ACCEPT   # AC1: scoped exactly to the required source/destination/port
2sudo ip netns exec ns-segfw iptables -L FORWARD -n -v --line-numbers   # AC3 check: confirm the existing ESTABLISHED,RELATED rule still sits above this, unaffected
bash — test against every acceptance criterion explicitly, exactly as written
1sudo ip netns exec ns-app-zone curl -s -o /dev/null -w "%{http_code}\n" http://10.60.2.10:9090/   # AC1 test
    200
2sudo ip netns exec ns-app-zone curl -s --max-time 2 -o /dev/null -w "%{http_code}\n" http://10.60.2.10:9091/   # AC2 test — a different port should NOT have gained access
    (times out, correctly still blocked)

5.3 Peer review — a second engineer checks the diff

PEER REVIEW — FRAUD-142 Reviewer: [second engineer] Checked: [x] Rule is scoped to exact source/destination/port (not a /24 or "any" that would violate AC2) [x] Rule is positioned correctly relative to existing ESTABLISHED,RELATED rule (order matters — see rule-order class of bugs) [x] No FORWARD default policy change [x] Confirmed against AC1, AC2, AC3 test evidence attached to the story Comment: Looks correctly scoped. Approved for CR submission.
🟦 Why this specific review matters here

The reviewer is explicitly checking for the exact rule-ordering mistake we deliberately created in Project 7's Break-Fix #1 — this is the entire point of peer review: catching a class of error the original author is structurally unlikely to catch themselves, because they already believe their rule is correct.

6Stage 5-6 — Change Request and CAB

CHANGE REQUEST — CR-8841 Story: FRAUD-142 Change: Add scoped FORWARD ACCEPT rule permitting fraud-detection (10.60.1.10) to reach scoring-api (10.60.2.10:9090) Risk Assessment: LOW - Scoped to exact source/destination/port - Additive only — no existing rule modified or removed - Peer-reviewed against acceptance criteria Impact if this change fails to apply correctly: - fraud-detection remains unable to reach scoring-api (no new functionality, no regression to existing traffic) Rollback Plan: iptables -D FORWARD -s 10.60.1.10 -d 10.60.2.10 -p tcp --dport 9090 -m state --state NEW -j ACCEPT (single command, removes exactly what was added, no other side effects) Implementation Window: [maintenance window] Approvers: [CAB]
🔵 Why the rollback plan is the most important line in this document

Notice the rollback plan is literally the exact inverse command of the implementation — because we scoped the change precisely (per AC2 and the peer review), undoing it is trivial and unambiguous. A vague or broad change would make this section far harder to write honestly, which is itself a signal — if you can't write a clean rollback plan, that's often a sign the change itself isn't scoped tightly enough yet.

🟢 CAB approval and production implementation

With risk, impact, and rollback explicitly documented and peer-reviewed evidence attached, CAB approves the change. Production implementation is the exact same single command from Section 5.2, run in the approved maintenance window, followed by re-running the exact AC1/AC2/AC3 tests as validation evidence attached to the closed story.

7Break-Fix #1 — Skipped Peer Review

🔴 What Goes Wrong

Imagine the same story, but the engineer — confident and in a hurry — pushes straight to production without peer review, reproducing Project 7's exact rule-ordering mistake.

bash — the mistake that peer review was specifically designed to catch
1sudo ip netns exec ns-segfw iptables -I FORWARD 1 -s 10.60.1.0/24 -d 10.60.2.0/24 -j DROP   # an unrelated "cleanup" rule, inserted at the top without realizing it shadows our new rule entirely

Observe

🔵 Reading what happened

This is the exact Break-Fix #1 scenario from Project 7 — a broad rule shadowing a correctly-scoped one, discoverable in seconds via iptables -L FORWARD -n -v --line-numbers and its counters. A peer reviewer checking the diff, specifically looking for rule-order issues (as our sample review in Section 5.3 explicitly did), would very likely have caught this before it ever reached production. Without that second set of eyes, it ships, and the fraud-detection team reports the exact same "the rule is there but it doesn't work" symptom from Project 7's original incident.

🔴 Root Cause

The change bypassed peer review, so a rule-ordering mistake that a second reviewer would very likely have caught went straight to production undetected.

🟦 Production Best Practice

Peer review isn't a formality to route around when you're confident — it exists precisely because the person who wrote a change is structurally the worst-positioned person to spot their own blind spots in it.

8Break-Fix #2 — No Rollback Plan

🔴 What Goes Wrong

Imagine the CR was submitted without a real rollback plan — just "revert if needed" — and approved anyway under time pressure. Now the change causes an unexpected problem in production.

🔵 Reading what happened

Without a specific, pre-written rollback command, the responding engineer during an active incident has to reconstruct exactly what changed and how to safely undo it — under pressure, often without the original context fresh in mind. What should have been a ten-second fix (running the exact inverse command, already written and reviewed in the CR) turns into a much longer, riskier improvisation, potentially compounding the original problem with a rushed, unreviewed "fix for the fix."

🔴 Root Cause

The change request was approved without a concrete, pre-verified rollback plan, turning what should have been a fast, safe recovery into a slow, improvised one during an active incident.

🟦 Production Best Practice

A rollback plan should be the literal, tested inverse of the implementation — written and reviewed BEFORE the change ships, not improvised during an incident. If you can't write one cleanly, treat that as a signal to scope the change more tightly, exactly as Section 6 noted.

9Break-Fix #3 — Missing RCA — The Same Incident Recurs

🔴 What Goes Wrong

Imagine Break-Fix #1's shadowed-rule incident happened, got fixed by directly deleting the offending rule, and the ticket was closed with a one-line comment: "removed bad rule, fixed." No RCA was written.

Three months later...

🟠 The Recurrence

A different engineer, working on an entirely unrelated cleanup task, adds a similarly broad "temporary" rule at the top of the same FORWARD chain — with no documented history showing this exact pattern already caused an incident once. The same class of failure recurs, and the team spends time re-discovering a root cause that was already fully understood three months earlier, simply because it was never written down anywhere searchable.

🔵 Reading what happened — this is Project 23's exact lesson, at the process level

This is structurally identical to Project 23's "fixed by restart, twice" pattern — a real fix was applied, but without documenting the actual mechanism and root cause, the organization's institutional knowledge didn't improve at all. The next engineer to touch this system has no way to know this specific mistake has already happened before.

RCA — INC-4471 (what SHOULD have been written the first time) Incident: fraud-detection intermittently unable to reach scoring-api despite a correctly-configured allow rule Root Cause: A broad cleanup rule was inserted at FORWARD chain position 1, shadowing the specific fraud-detection allow rule added under FRAUD-142. Linux firewall rules evaluate top-to- bottom with first-match-wins; the broad rule matched first. Contributing Factor: Change bypassed peer review (see INC-4471 timeline). Corrective Actions: 1. [DONE] Removed the shadowing rule 2. [FOLLOW-UP] Add a pre-commit lint check flagging any -I (insert) rule added to FORWARD without an explicit position review 3. [FOLLOW-UP] Document this failure pattern in the team's firewall runbook, with this incident as the reference example
🟦 Production Best Practice

Write the RCA even for a fix that only took a few minutes — the value isn't in how long the fix took, it's in preventing the NEXT engineer from making the same mistake without ever knowing it was already made once.

10Best Practices

🟦 Write acceptance criteria as tests, not descriptions

Specific and testable ("X can reach Y on port Z") beats vague ("networking works") — and doubles as your validation evidence.

🟦 Never skip peer review under time pressure

It exists specifically to catch what the author structurally can't see in their own change.

🟦 Rollback plans should be the literal tested inverse

If you can't write one cleanly, the change probably isn't scoped tightly enough yet.

🟦 Write the RCA even for quick fixes

The value is preventing recurrence, not documenting how long the fix took.

12Interview Preparation

ScenarioWalk me through how a network change you make actually reaches production in an enterprise environment.

It starts as a story with specific, testable acceptance criteria, broken down from a larger feature or epic. I do a technical analysis to decide the right approach, implement and test it in a non-production environment against those exact acceptance criteria, then it goes through peer review — someone else checking for issues like rule ordering or unintended scope that I might not catch myself. For anything touching production, especially in a regulated environment, it goes through a change request documenting risk, impact, and a concrete rollback plan, reviewed by a change advisory board before implementation.

Interviewer follow-up: "What's the most important part of that process, in your experience?" — Answer: the rollback plan, specifically written as the literal tested inverse of the change beforehand — it's the difference between a ten-second recovery and an improvised, risky one during an active incident.
ConceptWhy does peer review matter even for a change you're confident is correct?

Because the person who wrote a change is structurally the worst-positioned person to spot their own blind spots in it — they already believe it's correct, which is exactly why they wrote it that way. A second reviewer, checking with fresh eyes against explicit criteria like rule ordering or scope, catches a class of mistake the original author is very unlikely to catch themselves, no matter how careful they were.

ProductionWhy write an RCA even for an incident that only took a few minutes to fix?

Because the value of an RCA isn't proportional to how long the incident lasted — it's about capturing the actual root cause and mechanism so the next engineer, who may have no idea this already happened, doesn't repeat the exact same mistake. Without it, institutional knowledge doesn't improve, and the same class of failure can recur months later as if it were brand new.
