1The Task

Quarterly PCI-DSS-adjacent security audit season has arrived for the bank's Linux infrastructure. This isn't a specific incident to fix — it's a proactive audit, the kind of task that turns up problems before they become incidents, and it draws directly on nearly every diagnostic skill from this masterclass.

"We need documented proof for every server: exactly what's listening on the network, that nothing unexpected is listening, that the firewall genuinely blocks what our policy says it should — not just that a rule exists — and that every TLS-terminating service has a currently valid certificate. Compliance wants evidence, not our word."

Every technique in this project is something we've already used to troubleshoot incidents — we're just applying the same tools proactively, systematically, and with an adversarial mindset, instead of reactively after something breaks.

🔵 Why this project matters

Security auditing is a genuinely common, recurring responsibility for Linux/DevOps engineers, especially in regulated industries. Being able to systematically produce evidence — not just assurances — of a server's actual network security posture is a distinct, high-value skill from incident troubleshooting, even though it draws on the exact same toolkit.

2Security Auditing Foundation

2.1 Listening port audits — know exactly what's exposed

🔵 Concept

Every listening socket on a host is a potential entry point. A security audit starts with a complete, accurate inventory — ss -tlnp, exactly as we've used since Project 1 — compared explicitly against a documented BASELINE of what should be listening. Anything present that isn't on the baseline is either a legitimate gap in documentation or a genuine security concern, and the audit's job is to force that distinction to be made explicitly rather than assumed away.

2.2 Firewall validation — proving a rule works, not just exists

🔵 Concept

Project 7 taught us that a rule existing in the config is not the same as a rule actually taking effect. A proper security audit doesn't just read the iptables ruleset — it actively tests from an appropriate vantage point (another host, ideally outside the expected-to-be-blocked zone) that traffic which SHOULD be blocked genuinely is, and traffic that SHOULD be allowed genuinely is. Reading a ruleset proves intent; testing proves reality.

2.3 TLS certificate validation — expiry, chain, and hostname

🔵 Concept

A TLS-terminating service can be technically network-reachable and still functionally broken (or insecure) if its certificate has expired, doesn't match the hostname clients actually connect with, or has a broken chain of trust back to a recognized root. openssl s_client lets you inspect exactly what certificate a service is presenting and validate all three of these independently, from the command line — the same tool a client library uses internally, just exposed for manual inspection.

2.4 Reverse path filtering — a built-in anti-spoofing defense, with real tradeoffs

🔵 Concept

rp_filter is a kernel feature that drops incoming packets whose source address wouldn't be reachable back out the SAME interface the packet arrived on — a defense against source-address spoofing (an attacker claiming to be a trusted internal host). It has a few modes: 0 (off), 1 (strict — the packet's return path must exactly match the interface it arrived on), and 2 (loose — the source just needs to be reachable via ANY interface, not necessarily the same one). Strict mode is a strong security default, but on genuinely multi-homed or asymmetrically-routed hosts (exactly like Project 9's scenario), it can incorrectly drop completely legitimate traffic.

3The Audit Workflow

Figure 1 — Four independent checks, each producing concrete evidence rather than an assumption.

4Troubleshooting Method

  • 1. Inventory every listening port with ss -tlnp -o, including the owning process — compare against a documented baseline
    • ↓
  • 2. For anything unexpected, identify the process, when it started, and why — never assume it's benign without checking
    • ↓
  • 3. Test firewall rules from an actual external vantage point, not just by reading the ruleset
    • ↓
  • 4. For every TLS-terminating service, check certificate validity, expiry, and hostname match with openssl s_client
    • ↓
  • Check rp_filter mode against the host's actual routing topology — strict mode on a genuinely multi-homed host needs deliberate justification, not just the default
🟠 Warning

An audit that only reads configuration files proves intent, not reality. Wherever practical, actively test — connect from outside, check a live certificate, attempt traffic that should be blocked — rather than trusting that a config file describes the truth.

5Lab Setup — A Server With Several Services

bash — run as root/sudo
1sudo ip netns add ns-bankserver     # the server we're auditing
2sudo ip netns add ns-auditor        # represents an external auditor's vantage point, outside the server's own perspective
3sudo ip link add veth-server type veth peer name veth-auditor
4sudo ip link set veth-server netns ns-bankserver
5sudo ip link set veth-auditor netns ns-auditor
6sudo ip netns exec ns-bankserver ip addr add 10.170.1.10/24 dev veth-server
7sudo ip netns exec ns-auditor ip addr add 10.170.1.50/24 dev veth-auditor
8sudo ip netns exec ns-bankserver ip link set veth-server up
9sudo ip netns exec ns-auditor ip link set veth-auditor up
10for ns in ns-bankserver ns-auditor; do sudo ip netns exec $ns ip link set lo up; done
11# two legitimate, documented services
12sudo ip netns exec ns-bankserver python3 -m http.server 8443 --bind 10.170.1.10 &   # documented API service
13sudo ip netns exec ns-bankserver python3 -m http.server 22 --bind 10.170.1.10 &   # stand-in for SSH, port 22, also documented
14# baseline firewall — deny by default, allow only the documented services
15sudo ip netns exec ns-bankserver iptables -P INPUT DROP
16sudo ip netns exec ns-bankserver iptables -A INPUT -i lo -j ACCEPT
17sudo ip netns exec ns-bankserver iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
18sudo ip netns exec ns-bankserver iptables -A INPUT -p tcp --dport 22 -j ACCEPT
19sudo ip netns exec ns-bankserver iptables -A INPUT -p tcp --dport 8443 -j ACCEPT

6Establish a Baseline

bash — on ns-bankserver, the documented inventory
1sudo ip netns exec ns-bankserver ss -tlnp   # -t TCP, -l listening, -n numeric, -p show owning process — our full port inventory
    LISTEN 0.0.0.0:22    (documented — SSH stand-in)
    LISTEN 0.0.0.0:8443  (documented — API service)

    200   (allowed, as documented)

🟢 Baseline documented

Exactly two listening services, both documented, and the firewall correctly allows only what's expected. This is our clean starting point.

7Break-Fix #1 — An Unexpected Listening Service

🔴 Break It

Simulate a leftover debug service someone started during troubleshooting weeks ago and forgot to remove — a very common, very real source of audit findings.

bash — on ns-bankserver
1sudo ip netns exec ns-bankserver python3 -m http.server 8081 --bind 0.0.0.0 &   # an undocumented debug service, bound to ALL interfaces, left running

Observe — run the audit

bash — on ns-bankserver
1sudo ip netns exec ns-bankserver ss -tlnp   # re-run our inventory command
    LISTEN 0.0.0.0:22
    LISTEN 0.0.0.0:8081   users:(("python3",pid=5821))    ← NOT on our documented baseline
    LISTEN 0.0.0.0:8443
2sudo ip netns exec ns-bankserver ps -p 5821 -o pid,lstart,cmd   # investigate the owning process directly — when did it start, what is it actually running
    (shows it's been running since a date weeks ago — a genuine forgotten leftover, not something actively deployed today)
🔵 Reading the finding

This is exactly what a listening-port audit is designed to catch — a service that's neither malicious nor currently "in use," but represents genuine unmanaged exposure: unpatched, unmonitored, and running with whatever permissions it happened to start with weeks ago. The ss -tlnp comparison against a documented baseline is what turns "we think everything is fine" into "we have proof of exactly what's listening and can account for all of it."

🔴 Root Cause

A debug/testing service was started at some point and never properly shut down, remaining exposed and unaccounted-for in the server's documented service inventory.

bash — fix
1sudo ip netns exec ns-bankserver pkill -f "http.server 8081"   # stop the undocumented service
🟦 Production Best Practice

Run listening-port audits on a recurring schedule, not just during formal audit season, and maintain the documented baseline as living documentation that's updated whenever a new service is deliberately deployed — an outdated baseline makes every future audit noisier and less trustworthy.

8Break-Fix #2 — Invalid TLS Certificate

🔴 Break It

Generate a self-signed certificate for the wrong hostname, and configure a TLS-terminating service with it — simulating a certificate that was issued or renewed incorrectly.

bash — on ns-bankserver, generate a mismatched certificate
1sudo ip netns exec ns-bankserver openssl req -x509 -newkey rsa:2048 -keyout /tmp/key.pem -out /tmp/cert.pem -days 1 -nodes -subj "/CN=wrong-hostname.internal"   # -x509 self-signed cert; -days 1 makes it expire almost immediately, simulating an expiry issue too; CN is deliberately the WRONG hostname
2sudo ip netns exec ns-bankserver python3 -c "
import ssl, http.server
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.load_cert_chain('/tmp/cert.pem', '/tmp/key.pem')
httpd = http.server.HTTPServer(('10.170.1.10', 8444), http.server.SimpleHTTPRequestHandler)
httpd.socket = ctx.wrap_socket(httpd.socket, server_side=True)
httpd.serve_forever()
" &   # a minimal TLS-terminating service using our mismatched, near-expired certificate
3sudo ip netns exec ns-bankserver iptables -A INPUT -p tcp --dport 8444 -j ACCEPT   # allow it through the firewall so we can actually test it

Observe — audit the certificate directly

bash — on ns-auditor
1sudo ip netns exec ns-auditor openssl s_client -connect 10.170.1.10:8444 -servername bank-api.internal </dev/null 2>&1 | grep -E "subject=|Verify return"   # -servername is the hostname we'd actually expect clients to use; feed empty stdin since we just want the handshake info
    subject=CN = wrong-hostname.internal
    Verify return code: 62 (hostname mismatch)   ← the certificate's name doesn't match what clients actually connect with
2sudo ip netns exec ns-auditor openssl s_client -connect 10.170.1.10:8444 </dev/null 2>&1 | openssl x509 -noout -dates   # extract just the validity dates from the presented certificate
    notAfter=... (about to expire, or already expired, within roughly a day of creation)
🔵 Reading the finding

Two separate, independently serious findings from one certificate check: the CN (hostname the certificate was issued for) doesn't match the hostname clients would actually use to reach this service, AND the certificate is set to expire almost immediately. Either one alone would cause client-side TLS validation failures that look, from the outside, like a vague "can't connect" or "SSL error" — openssl s_client is what turns that vague symptom into two specific, actionable findings.

🔴 Root Cause

The TLS certificate was issued for the wrong hostname and with an extremely short validity period, meaning any client performing proper certificate validation would reject connections to this service.

bash — fix (in the lab): regenerate with the correct hostname and a proper validity period
1sudo ip netns exec ns-bankserver openssl req -x509 -newkey rsa:2048 -keyout /tmp/key.pem -out /tmp/cert.pem -days 365 -nodes -subj "/CN=bank-api.internal"   # correct hostname, sensible validity period
🟦 Production Best Practice

Include certificate expiry monitoring as a standing, automated check (not just a manual audit-season task) — certificates silently expiring is one of the most common, entirely preventable causes of unplanned outages in production.

9Break-Fix #3 — Reverse Path Filtering Too Strict for Multi-Homing

🟠 Scenario

This one isn't a simple "break it" — it's a genuine security-vs-availability tradeoff finding, exactly the kind of nuanced result a real audit produces. Let's check rp_filter's current mode and reason about it in the context of a hypothetical multi-homed extension of this server.

bash — on ns-bankserver, check the current rp_filter setting
1sudo ip netns exec ns-bankserver sysctl net.ipv4.conf.all.rp_filter   # the system-wide default setting
    net.ipv4.conf.all.rp_filter = 1   (strict mode — common secure default)

Reasoning through the tradeoff

🔵 The security case for strict mode

rp_filter=1 (strict) means the kernel will drop any incoming packet whose source address wouldn't be routed back out the SAME interface it arrived on. This directly defends against a class of spoofing attack where someone forges a trusted internal source address on packets sent from an untrusted network — without strict rp_filter, those forged packets would be processed normally.

🟠 The availability risk for a multi-homed host

Recall Project 9's bastion host, with separate management and production interfaces and potentially asymmetric routing paths for legitimate operational reasons. On a host like that, strict rp_filter can incorrectly drop entirely legitimate traffic whose reply happens to take a different interface than its request arrived on — treating normal multi-homed asymmetry as if it were spoofing.

bash — demonstrating the compromise: loose mode, for hosts where strict causes problems
1sudo ip netns exec ns-bankserver sysctl -w net.ipv4.conf.all.rp_filter=2   # loose mode — source just needs to be reachable via SOME interface, not necessarily the one it arrived on
ModeBehaviorWhen to Use
0No filtering at allRarely appropriate — removes this entire defense; needs strong justification
1Strict — must return via the SAME interfaceBest default for single-homed, symmetrically-routed hosts
2Loose — must be reachable via ANY interfaceA reasonable middle ground for genuinely multi-homed hosts with legitimate asymmetric routing
🟦 Production Best Practice — this is an audit FINDING, not a bug

The correct audit outcome here isn't "fix" or "leave alone" — it's documenting the deliberate choice: confirm whether this specific host is genuinely multi-homed with legitimate asymmetric routing (in which case loose mode is a justified, documented exception) or whether it's single-homed (in which case strict mode should stay, and any packet drops deserve investigation as potential spoofing attempts rather than being loosened away). An audit's job is to force this decision to be explicit and documented, not to silently pick one.

10Production Best Practices

🟦 Maintain a living, documented service baseline

Compare ss -tlnp against it regularly, not just during formal audits.

🟦 Test firewall behavior, don't just read the ruleset

Config intent and actual behavior can diverge — verify from an external vantage point.

🟦 Automate certificate expiry monitoring

Don't rely on manual audits to catch expiring certificates — they're entirely preventable outages.

🟦 Document rp_filter mode decisions explicitly

Strict vs loose is a real security-availability tradeoff — never leave it as an unexamined default on a multi-homed host.

12Interview Preparation

ScenarioYou're asked to audit a server's network security posture. What's your approach?

I'd start with a complete listening port inventory using ss -tlnp, comparing it against a documented baseline of expected services, and investigate anything unaccounted for by checking the owning process directly. Then I'd actively test the firewall from an external vantage point rather than just reading the ruleset, since a rule existing in config doesn't guarantee it's actually taking effect. For any TLS-terminating service, I'd use openssl s_client to check certificate validity, hostname match, and expiry directly.

Interviewer follow-up: "What would you do if you found an unexpected listening port?" — Answer: identify the owning process and when it started using ps, rather than assuming intent either way — it could be a forgotten debug service, a legitimate service missing from documentation, or something more serious, and the investigation determines which.
ConceptWhat's the difference between strict and loose reverse path filtering?

Strict mode (rp_filter=1) drops incoming packets unless their source address would be routed back out the exact same interface they arrived on — a strong defense against source-address spoofing. Loose mode (rp_filter=2) only requires the source to be reachable via SOME interface on the host, not necessarily the one the packet arrived on — a more permissive setting appropriate for genuinely multi-homed hosts with legitimate asymmetric routing, where strict mode would incorrectly drop real traffic.

TroubleshootingA client reports intermittent TLS connection failures to a service that appears to be running fine. What would you check?

I'd use openssl s_client to inspect the actual certificate the service presents, checking three things independently: whether it's currently within its validity period, whether its CN or SAN matches the hostname the client is actually connecting with, and whether its chain of trust resolves properly. Any one of these being wrong causes exactly this kind of vague, hard-to-diagnose client-side TLS failure.
