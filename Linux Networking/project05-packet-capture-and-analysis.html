1The Incident

We're back with the e-commerce platform team. Checkout works for most customers, but a noticeable slice of transactions take 4-8 seconds instead of the usual 200ms — and it's not consistent enough to reproduce on demand from the application logs alone.

"Routing is fine, firewall is fine, DNS is fine, the app team says their code hasn't changed, and TCP connections do eventually complete — they're just slow sometimes. We're out of ideas from the application side."

Every tool we've used so far (ss, ip route, getent, dig) gives us a summary — a snapshot of state. None of them show us the actual sequence and timing of packets on the wire. When every summary says "fine" but the real-world symptom persists, it's time to capture and read the raw conversation itself.

🔵 Why this project matters

tcpdump is the ground truth of Linux networking — every other tool in this masterclass is really just summarizing what tcpdump can show you directly. Learning to build precise capture filters and read raw output fluently is what separates an engineer who can theorize about a problem from one who can prove it.

2Why Capture Packets At All

🔵 Concept

Tools like ss tell you the current state of a connection. They cannot tell you HOW LONG the handshake took, whether a packet was retransmitted, or whether the server responded instantly and the delay happened elsewhere. tcpdump captures the actual packets crossing an interface, with real timestamps — the only source of truth for timing-related and intermittent problems.

🔵 Concept — retransmission, the likely culprit here

When the sender doesn't receive an acknowledgment for data within an expected window, TCP assumes the packet was lost and sends it again — a retransmission. This is normal and self-healing, but each retransmission costs real time (following an exponential backoff), and a connection that had to retransmit even once can easily take seconds longer than one that didn't. This is invisible to ss, invisible to application logs, and only visible in a packet capture.

3Where tcpdump Sits

🟣 Architecture

tcpdump uses a kernel facility (libpcap, backed by AF_PACKET sockets) to receive a copy of every packet that crosses a given interface — both inbound and outbound — before or after normal kernel processing, depending on where the interface sits. It does not interfere with the actual traffic; it's a read-only tap on the wire.

Figure 1 — tcpdump taps the traffic without altering it, which is exactly why it can show us ground truth that state-summarizing tools can't.

4Safe Production Capture Method

🟦 Production Best Practice

Never run an unfiltered, unbounded tcpdump on a busy production interface — it can consume significant CPU and disk, and an accidentally broad filter can capture sensitive data (credentials, tokens, PII) into a file that then has to be handled carefully. The professional pattern is: filter as precisely as possible (by host and port, never capture "everything"), bound the capture with a packet count or file size, and write to disk instead of trying to eyeball a live, fast-scrolling terminal.

  • 1. Define the narrowest possible filter — specific host(s) and port(s), never a bare protocol alone
    • ↓
  • 2. Bound the capture — use -c (packet count) or a rotate/size limit, never let it run forever unattended
    • ↓
  • 3. Write to a file with -w instead of printing live, especially under load
    • ↓
  • 4. Reproduce the problem (or wait for it) while the capture runs
    • ↓
  • Analyze the .pcap afterward with -r, or open it in Wireshark for deeper visual analysis (Project 6)

5BPF Filters, Word by Word

tcpdump's filter language is called BPF (Berkeley Packet Filter). Getting comfortable combining these expressions is what separates a useful, targeted capture from an overwhelming firehose.

Filter TokenMeaning
host 10.10.9.50Match packets where EITHER the source OR destination IP is 10.10.9.50.
src 10.10.9.50Match only packets where 10.10.9.50 is the SOURCE — narrower than host, useful for isolating one direction of traffic.
dst 10.10.9.50Match only packets where 10.10.9.50 is the DESTINATION.
port 8443Match packets where either the source or destination port is 8443.
src port 51234Match only packets whose SOURCE port is 51234 — useful for following one specific client connection.
tcpMatch only TCP protocol packets, excluding UDP, ICMP, ARP, etc.
udpMatch only UDP protocol packets — useful for DNS queries, which typically use UDP.
icmpMatch only ICMP packets — pings and related control messages.
net 10.10.9.0/24Match packets where either address falls within this entire subnet.
and / or / notBoolean combinators — build precise compound filters, e.g. tcp and port 8443 and not host 10.10.1.5 to exclude a known-noisy health-check source.
bash — example combined filter
1sudo tcpdump -i eth0 'tcp and host 10.10.9.50 and port 8443 and not src host 10.10.1.5'
🔵 Reading this filter

"Show me only TCP traffic to or from 10.10.9.50 on port 8443, but exclude anything sourced from 10.10.1.5" — this is exactly the shape of filter you'd write to isolate one problematic checkout connection while excluding a noisy monitoring probe that keeps polling the same port.

6tcpdump Flags, Word by Word

FlagMeaning
-i eth0Capture on this specific interface. Use -i any to capture on all interfaces at once (useful when you're not sure which interface carries the traffic).
-nnDon't resolve IP addresses to hostnames AND don't resolve port numbers to service names — shows raw numeric values, which is both faster and avoids DNS lookups interfering with (or being confused with) the very traffic you're capturing.
-vvvIncrease verbosity to maximum — shows more protocol detail per packet (TTL, packet ID, more TCP options), useful once you've narrowed down to a small set of packets worth examining closely.
-XShow packet contents in both hex AND ASCII — useful for inspecting application-layer payload data (e.g. is this actually an HTTP request? what does the body contain?).
-AShow packet contents in ASCII only — a lighter-weight version of -X when you just want to read plain-text protocols like HTTP.
-c 100Capture exactly 100 packets and then stop automatically — essential for bounding a capture so it can't run away on a busy interface.
-w capture.pcapWrite raw captured packets to a file instead of printing them, preserving full fidelity for later analysis or for opening in Wireshark.
-r capture.pcapRead and print packets from a previously saved capture file instead of capturing live traffic.

7Reading Raw tcpdump Output

example output line
14:02:11.238471 IP 10.10.1.20.51234 > 10.10.9.50.8443: Flags [S], seq 1458203912, win 64240, length 0
FieldMeaning
14:02:11.238471Timestamp with microsecond precision — critical for measuring exactly how much time passed between packets, e.g. between a SYN and its retransmission.
IPThis is an IPv4 packet (would show IP6 for IPv6).
10.10.1.20.51234Source IP and source port (the last number after the final dot is the port).
>Direction indicator — "going to."
10.10.9.50.8443Destination IP and destination port.
Flags [S]TCP flags set on this packet. S=SYN, .=ACK (shown as part of combinations like [S.] for SYN-ACK), F=FIN, R=RST, P=PSH (push, deliver data to the app immediately).
seq 1458203912The sequence number — identifies this packet's position in the byte stream, used by both sides to detect loss and reordering.
win 64240The TCP window size being advertised — how many bytes the sender is willing to receive before needing an ACK; useful when investigating throughput problems.
length 0Payload length in bytes — 0 here because a bare SYN carries no application data, only the handshake signal.

8Lab Setup

bash — run as root/sudo
1sudo ip netns add ns-client
2sudo ip netns add ns-checkout
3sudo ip link add veth-client type veth peer name veth-checkout
4sudo ip link set veth-client netns ns-client
5sudo ip link set veth-checkout netns ns-checkout
6sudo ip netns exec ns-client ip addr add 10.10.1.20/24 dev veth-client
7sudo ip netns exec ns-checkout ip addr add 10.10.9.50/24 dev veth-checkout
8sudo ip netns exec ns-client ip link set veth-client up
9sudo ip netns exec ns-checkout ip link set veth-checkout up
10for ns in ns-client ns-checkout; do sudo ip netns exec $ns ip link set lo up; done
11sudo ip netns exec ns-checkout python3 -m http.server 8443 --bind 10.10.9.50 &

9Verify a Baseline Capture

terminal A — on ns-checkout, start capturing
1sudo ip netns exec ns-checkout tcpdump -i veth-checkout -nn 'tcp port 8443' -c 20
terminal B — on ns-client, generate traffic
1sudo ip netns exec ns-client curl -s -o /dev/null http://10.10.9.50:8443/
🟢 Validation

You should see a clean SYN → SYN-ACK → ACK, then a data exchange, then a clean FIN sequence — no retransmissions, no resets, tightly spaced timestamps. This is our known-good baseline to compare against.

10Break-Fix #1 — Capturing Retransmissions (the Slow Checkout Mystery)

🔴 Break It

Use Linux's traffic control (tc) to simulate a lossy link between the two namespaces — this reproduces intermittent packet loss without touching firewall or routing config at all, so ss, ip route, and the firewall will all correctly report "fine," exactly like the incident.

bash — on ns-client, introduce 15% packet loss
1sudo ip netns exec ns-client tc qdisc add dev veth-client root netem loss 15%
TokenMeaning
tc qdisc add dev veth-client root netem loss 15%Attaches the netem (network emulation) queueing discipline to this interface and tells it to randomly drop 15% of outgoing packets — a standard way to simulate real-world lossy links (bad cabling, congested WAN links, flaky wifi) in a lab.

Observe with a capture

terminal A — on ns-checkout
1sudo ip netns exec ns-checkout tcpdump -i veth-checkout -nn 'tcp port 8443' -c 40 -w /tmp/slow-checkout.pcap
terminal B — on ns-client, time a request
1sudo ip netns exec ns-client bash -c "time curl -s -o /dev/null http://10.10.9.50:8443/"
    real    0m2.847s   (versus a sub-50ms baseline)

Read the capture

bash — analyze the saved capture
1sudo ip netns exec ns-checkout tcpdump -nn -r /tmp/slow-checkout.pcap
    14:10:02.001022 IP 10.10.1.20.51301 > 10.10.9.50.8443: Flags [S], seq 100, length 0
    14:10:02.001501 IP 10.10.9.50.8443 > 10.10.1.20.51301: Flags [S.], seq 500, ack 101, length 0
    14:10:02.301944 IP 10.10.1.20.51301 > 10.10.9.50.8443: Flags [S], seq 100, length 0
    14:10:02.301944 ← same SYN, retransmitted ~300ms later — the original ACK to the SYN-ACK never arrived, so the client's timer fired again
🔵 Reading the symptom

This is the smoking gun ss and application logs could never show us: the exact same sequence number appearing a second time is a textbook retransmission, and the gap between the two timestamps (roughly 300ms here) is time the connection spent doing nothing productive, waiting to recover from loss. Multiply this across several retransmitted segments in a longer transfer and you get exactly the multi-second delays customers were experiencing — all while every state-based tool reports a perfectly healthy, ESTABLISHED connection, because the connection DID eventually succeed.

🔴 Root Cause

Intermittent packet loss on the network path was causing TCP retransmissions, each one costing hundreds of milliseconds to multiple seconds of delay — invisible to any tool that only reports connection state rather than packet-level timing.

bash — fix (in the lab, remove the simulated loss)
1sudo ip netns exec ns-client tc qdisc del dev veth-client root netem
🟦 Production Best Practice

In a real incident, the "fix" for packet loss is investigating the physical/virtual network path — bad cabling, an overloaded switch port, a saturated link, or a misbehaving virtualization NIC driver — not something you fix on the Linux host itself. But finding it starts with exactly this kind of packet capture, since it's the only tool that reveals retransmission as the mechanism.

11Break-Fix #2 — Capturing a Firewall Drop in the Act

🔴 Break It

Revisit Project 1's firewall-drop scenario, but this time PROVE it definitively with a capture instead of inferring it from a timeout.

bash — on ns-checkout
1sudo ip netns exec ns-checkout iptables -A INPUT -p tcp --dport 8443 -j DROP
2sudo ip netns exec ns-checkout tcpdump -i veth-checkout -nn 'tcp port 8443' -c 5 -w /tmp/dropped.pcap &
bash — on ns-client
1sudo ip netns exec ns-client timeout 3 curl http://10.10.9.50:8443/

Read the capture

bash
1sudo ip netns exec ns-checkout tcpdump -nn -r /tmp/dropped.pcap
    14:15:00.100221 IP 10.10.1.20.51400 > 10.10.9.50.8443: Flags [S], seq 900, length 0
    (capture ends here — nothing else was ever captured on this interface for this flow)
🔵 Reading the symptom — a crucial, precise distinction

Notice the SYN WAS captured arriving on veth-checkout — that proves the packet physically reached this host's NIC and kernel. But no SYN-ACK was ever sent back, because iptables' INPUT chain DROP rule discarded it after the NIC received it but before the application ever saw it. This precisely pinpoints the drop to the local firewall layer on THIS host, rather than somewhere out on the network — a distinction that matters enormously when deciding which team or which device to investigate next.

bash — fix
1sudo ip netns exec ns-checkout iptables -D INPUT -p tcp --dport 8443 -j DROP

12Break-Fix #3 — Saving, Filtering, and Replaying a Capture

🟠 Scenario

In a real incident, you often can't sit and watch a live capture — you need to capture broadly for a while, then filter down afterward to find the interesting packets. Let's practice exactly that workflow using the retransmission capture from Break-Fix #1.

bash — re-run the lossy capture to generate a fresh file
1sudo ip netns exec ns-client tc qdisc add dev veth-client root netem loss 15%
2sudo ip netns exec ns-checkout tcpdump -i veth-checkout -nn 'tcp port 8443' -c 60 -w /tmp/investigate.pcap &
3sudo ip netns exec ns-client curl -s -o /dev/null http://10.10.9.50:8443/
bash — filter the saved file down to just the retransmissions, offline
1sudo ip netns exec ns-checkout tcpdump -nn -r /tmp/investigate.pcap 'tcp[tcpflags] & tcp-syn != 0'
TokenMeaning
-r /tmp/investigate.pcapRead from the previously saved file instead of capturing live — this is the "replay" half of the workflow, letting you re-analyze the same data with different filters as many times as needed without re-running the incident.
'tcp[tcpflags] & tcp-syn != 0'An advanced BPF expression that matches only packets with the SYN flag set — useful specifically for spotting retransmitted SYNs (duplicates) after the fact, buried among dozens of other packets in a larger capture.
🟢 Validation

You should be able to count how many SYNs appear for what should have been a single connection attempt — any count greater than 1 confirms at least one retransmission occurred during that request.

bash — cleanup
1sudo ip netns exec ns-client tc qdisc del dev veth-client root netem
🟦 Production Best Practice

This capture-then-filter-offline workflow is exactly how you handle production incidents where you can't predict precisely when the problem will occur — capture broadly and safely with -w and -c, then take your time analyzing afterward instead of trying to catch the issue live.

13Production Best Practices

🟦 Never capture unfiltered on a busy host

Always scope to specific hosts/ports, and always bound with -c or a size/time limit.

🟦 Write to a file, analyze after

-w plus -r separates the risky live-capture window from the safe, unlimited-time analysis phase.

🟦 Duplicate sequence numbers = retransmission

The single most important pattern to recognize by eye in raw tcpdump output.

🟦 A captured SYN with no reply pinpoints the host

If tcpdump on the SERVER shows the SYN arriving but nothing going back out, the problem is on that host (firewall, or nothing listening) — not somewhere out on the network.

🟦 Handle captures like sensitive data

.pcap files can contain credentials, tokens, and PII in plaintext protocols — store and share them as carefully as you would a password.

15Interview Preparation

ScenarioAn application is intermittently slow but every state-based check (connection status, firewall rules, routing) looks fine. How would you investigate?

State-based tools only show a snapshot, not timing or history, so I'd move to a packet capture to see the actual sequence and timestamps of packets. I'd filter narrowly to the specific host and port involved, bound it with a packet count, and write it to a file so I could analyze it without pressure. The key thing I'd look for is duplicate sequence numbers, which indicate TCP retransmissions — each one costs real time due to backoff and would explain intermittent slowness that never shows up as an outright failure.

Interviewer follow-up: "How do you know it's retransmission and not just a slow server?" — Answer: a slow server would show a normal handshake completing quickly, followed by a long gap before the response payload. A retransmission shows the exact same SYN or data segment appearing more than once with the same sequence number, which only happens when the original wasn't acknowledged in time.
ConceptWhat's the difference between running tcpdump live versus using -w and -r?

Live capture prints packets to the terminal as they arrive, which works fine for quick, low-volume checks but is risky on a busy interface since you can't easily bound or revisit it. Using -w writes raw packets to a file instead, letting you safely bound the capture and analyze it later with -r and different filters as many times as needed, without re-triggering the original incident.

ProductionWhy should you avoid capturing traffic with no filter on a production host?

An unfiltered capture on a busy interface can consume significant CPU and disk I/O, potentially making performance worse during an active incident, and can also capture large volumes of unrelated, possibly sensitive traffic that then has to be stored and handled carefully. A precise filter — specific host and port — keeps the capture lightweight and focused on the actual problem.

TroubleshootingYou captured a SYN packet arriving at a server's NIC, but no SYN-ACK was ever sent. What does that tell you?

It tells me the packet successfully reached this host at the network layer, so routing and the physical/virtual path are fine — the problem is local to this host, most likely a firewall rule silently dropping the packet, or possibly nothing listening on that port, which I'd confirm next with ss.
