1The Incident

We're extending last project's segmented banking network. Two new requirements just landed on the same gateway host, ns-segfw, which now also has a third interface facing a simulated "public"/partner-facing network.

"First: our app-zone servers need outbound internet access to pull vendor threat-intel feeds — they're all on private 10.60.1.0/24 addresses, so they need to go out through the gateway's public IP. Second: our clearing partner needs to reach our settlement API on 10.60.2.10:9090, but only via a published address on our public interface, port 8080 — we can't expose the internal IP directly. Neither one is working yet."

Both requirements are solved by the same underlying kernel mechanism — Network Address Translation — just running in opposite directions. Understanding NAT properly means understanding exactly which direction each type rewrites, and exactly where in the packet's journey that rewrite happens.

🔵 Why this project matters

NAT is everywhere in real infrastructure — every home router, every cloud NAT gateway, every Kubernetes Service using iptables/IPVS mode, and nearly every enterprise perimeter firewall relies on exactly the SNAT/DNAT concepts in this project. Understanding it at the Linux kernel level makes every higher-level NAT abstraction (cloud NAT gateways, K8s kube-proxy) far less mysterious later in this masterclass.

2NAT Foundation

2.1 Source NAT (SNAT) — rewriting who a packet is FROM

🔵 Concept

SNAT rewrites a packet's SOURCE address as it leaves, typically used so many internal hosts with private addresses can share one public-facing IP for outbound traffic. The kernel remembers the translation (via conntrack) so replies can be un-translated and delivered back to the correct original internal host.

2.2 MASQUERADE — SNAT for a dynamic/unknown public IP

🔵 Concept

MASQUERADE is a special case of SNAT that automatically uses whatever IP is currently assigned to the outbound interface, instead of a hardcoded address. This is exactly what makes it perfect for gateways whose public IP might be assigned dynamically (DHCP, cloud-assigned elastic IPs) — you don't have to hardcode an address that might change.

2.3 Destination NAT (DNAT) — rewriting who a packet is TO

🔵 Concept

DNAT rewrites a packet's DESTINATION address (and often port) as it arrives, used to publish an internal service on a public-facing address/port without exposing the real internal IP directly — exactly our clearing-partner requirement. The reply traffic is automatically un-translated by conntrack so the external partner never sees the real internal address at all.

2.4 Why timing matters: DNAT happens BEFORE routing, SNAT happens AFTER

🔵 Concept — the single most important NAT fact

DNAT is applied in the PREROUTING chain — before the kernel has even decided how to route the packet — which means the ROUTING DECISION is made using the NEW, rewritten destination, not the original one. SNAT/MASQUERADE is applied in POSTROUTING — after routing and after FORWARD — which means FORWARD chain rules must match the packet's ORIGINAL source, but its PRE-DNAT-rewrite destination has already changed by the time FORWARD sees it. This ordering explains most "my NAT rule exists but nothing works right" confusion.

4Troubleshooting Method for NAT Incidents

  • 1. Identify which direction is broken — outbound (needs SNAT) or inbound-published (needs DNAT)?
    • ↓
  • 2. Check the nat table directly: iptables -t nat -L -n -v — is the expected rule present and matching (non-zero counters)?
    • ↓
  • 3. For DNAT: after the rewrite, does the FORWARD chain still allow the NEW (translated) destination?
    • ↓
  • 4. For SNAT/MASQUERADE: is it actually being applied on the correct outbound interface, and is the FORWARD chain allowing the ORIGINAL source?
    • ↓
  • 5. Check conntrack for the actual translation being applied: conntrack -L shows both original and translated tuples
    • ↓
  • Confirm the return path — does the replying host know how to route back to the translated/original address as appropriate?
🟠 Warning

The filter table (INPUT/OUTPUT/FORWARD) and the nat table are separate — remember to check both explicitly with -t nat, since a default iptables -L only shows the filter table.

5Lab Setup — Add a Public Network to the Gateway

We're extending Project 7's ns-app-zone / ns-segfw / ns-data-zone lab. Add a fourth namespace, ns-public, simulating the internet/partner-facing network, connected to a new interface on ns-segfw.

bash — run as root/sudo (assumes Project 7's lab is still up; recreate it first if needed)
1sudo ip netns add ns-public
2sudo ip link add veth-public type veth peer name fw-public-in
3sudo ip link set veth-public netns ns-public
4sudo ip link set fw-public-in netns ns-segfw
5sudo ip netns exec ns-public ip addr add 203.0.113.10/24 dev veth-public
6sudo ip netns exec ns-segfw ip addr add 203.0.113.1/24 dev fw-public-in
7sudo ip netns exec ns-public ip link set veth-public up
8sudo ip netns exec ns-segfw ip link set fw-public-in up
9sudo ip netns exec ns-public ip link set lo up
10sudo ip netns exec ns-public ip route add default via 203.0.113.1
11# pretend a "vendor threat-intel feed" service exists out on the public network
12sudo ip netns exec ns-public python3 -m http.server 80 --bind 203.0.113.10 &

203.0.113.0/24 is TEST-NET-3, a documentation/lab range reserved by RFC 5737 — safe to use for exercises like this without colliding with any real address.

5.1 Configure MASQUERADE for outbound app-zone traffic

bash — on ns-segfw
1sudo ip netns exec ns-segfw iptables -t nat -A POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j MASQUERADE
2sudo ip netns exec ns-segfw iptables -A FORWARD -s 10.60.1.0/24 -o fw-public-in -m state --state NEW -j ACCEPT
3sudo ip netns exec ns-app-zone ip route add 203.0.113.0/24 via 10.60.1.1
TokenMeaning
-t nat -A POSTROUTINGAdds this rule to the nat table's POSTROUTING chain — where source rewriting happens, after routing and FORWARD.
-s 10.60.1.0/24 -o fw-public-in -j MASQUERADEFor traffic sourced from the app zone, leaving via the public-facing interface, rewrite its source to whatever address fw-public-in currently holds.

5.2 Configure DNAT to publish the settlement API

bash — on ns-segfw
1sudo ip netns exec ns-segfw iptables -t nat -A PREROUTING -i fw-public-in -p tcp --dport 8080 -j DNAT --to-destination 10.60.2.10:9090
2sudo ip netns exec ns-segfw iptables -A FORWARD -d 10.60.2.10 -p tcp --dport 9090 -m state --state NEW -j ACCEPT
3sudo ip netns exec ns-segfw iptables -t nat -A POSTROUTING -s 203.0.113.0/24 -d 10.60.2.0/24 -o fw-data-in -j MASQUERADE
TokenMeaning
-t nat -A PREROUTING -i fw-public-in -p tcp --dport 8080 -j DNAT --to-destination 10.60.2.10:9090For traffic arriving on the public interface targeting port 8080, rewrite the destination to the internal settlement API's real address and port — this happens BEFORE routing, so the routing decision that follows will correctly send it toward the data zone.
-d 10.60.2.10 -p tcp --dport 9090 ... ACCEPTThe FORWARD rule must match the NEW (post-DNAT) destination, not the original public IP:8080 — a very common point of confusion, covered in Break-Fix #3.
POSTROUTING ... -j MASQUERADE (third rule)A "hairpin"-adjacent SNAT so the data-zone server's reply routes back through the gateway correctly rather than trying to reply directly to a public IP its own routing table doesn't understand — a common companion rule to DNAT in segmented networks.

6Verify Baseline SNAT and DNAT

bash — test outbound (SNAT/MASQUERADE)
1sudo ip netns exec ns-app-zone curl -s -o /dev/null -w "%{http_code}\n" http://203.0.113.10/
    200
2sudo ip netns exec ns-public tcpdump -i veth-public -nn -c 1 'tcp port 80'
    ...203.0.113.1.xxxxx > 203.0.113.10.80... (source shows the GATEWAY's public IP, never the real 10.60.1.10)
bash — test inbound (DNAT)
1sudo ip netns exec ns-public curl -s -o /dev/null -w "%{http_code}\n" http://203.0.113.1:8080/
    200
🟢 Validation

Outbound traffic correctly appears to originate from the gateway's public IP, and the partner-facing curl to the published port reaches the real internal settlement API. This is our working baseline.

7Break-Fix #1 — Missing MASQUERADE (Asymmetric Return)

🔴 Break It

Remove the outbound MASQUERADE rule, simulating a firewall rebuild that forgot to re-add it.

bash — on ns-segfw
1sudo ip netns exec ns-segfw iptables -t nat -D POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j MASQUERADE

Observe

bash — on ns-app-zone
1sudo ip netns exec ns-app-zone curl --max-time 3 http://203.0.113.10/
    curl: (28) Connection timed out
🔵 Reading the symptom

The FORWARD chain still correctly allows the connection out, and it physically reaches the "vendor" server on ns-public — but with its ORIGINAL private source address (10.60.1.10) untranslated. The vendor server tries to reply directly to 10.60.1.10 — an address that means nothing on the public network and has no route back. This is asymmetric routing again (Project 2's concept), but caused by a missing NAT rule instead of a bad route — a private, non-routable source address leaking onto a network that can't route back to it.

🔴 Root Cause

The MASQUERADE rule was missing, so outbound packets kept their private, non-internet-routable source address, making replies undeliverable.

bash — fix
1sudo ip netns exec ns-segfw iptables -t nat -A POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j MASQUERADE
🟦 Production Best Practice

Whenever private-address hosts need outbound internet/partner access, MASQUERADE (or static SNAT) is not optional — it's what makes the private address space usable at all beyond the local network. Losing this rule is one of the most common "the internet suddenly stopped working for our whole subnet" incidents.

8Break-Fix #2 — DNAT to the Wrong Target

🔴 Break It

Simulate a typo during a maintenance window — the DNAT rule points to the wrong internal port.

bash — on ns-segfw
1sudo ip netns exec ns-segfw iptables -t nat -D PREROUTING -i fw-public-in -p tcp --dport 8080 -j DNAT --to-destination 10.60.2.10:9090
2sudo ip netns exec ns-segfw iptables -t nat -A PREROUTING -i fw-public-in -p tcp --dport 8080 -j DNAT --to-destination 10.60.2.10:9091

Observe

bash — on ns-public
1sudo ip netns exec ns-public curl --max-time 3 http://203.0.113.1:8080/
    curl: (28) Connection timed out (or Connection refused, depending on whether anything listens on 9091)
bash — confirm with the nat table directly
1sudo ip netns exec ns-segfw iptables -t nat -L PREROUTING -n -v --line-numbers
    1  ...  DNAT  tcp  --  ...  dpt:8080 to:10.60.2.10:9091
🔵 Reading the symptom

The published port (8080) is correctly being intercepted — the DNAT rule matches and fires — but it's rewriting to a port (9091) where nothing is actually listening on the real settlement API host. This looks, from the partner's side, exactly like a firewall block or a down service, but the real fault is entirely in the NAT translation target — always confirm the exact --to-destination value directly from the nat table rather than assuming it matches what documentation says it should be.

🔴 Root Cause

The DNAT rule's translation target port didn't match the port the real internal service was actually listening on.

bash — fix
1sudo ip netns exec ns-segfw iptables -t nat -D PREROUTING -i fw-public-in -p tcp --dport 8080 -j DNAT --to-destination 10.60.2.10:9091
2sudo ip netns exec ns-segfw iptables -t nat -A PREROUTING -i fw-public-in -p tcp --dport 8080 -j DNAT --to-destination 10.60.2.10:9090

9Break-Fix #3 — DNAT Works, but FORWARD Still Blocks the Real Destination

🔴 Break It

Remove the FORWARD allow rule but leave DNAT intact — a very common mistake since it's easy to think "I added the port-forward rule" and forget the filter table still needs to separately allow the translated destination.

bash — on ns-segfw
1sudo ip netns exec ns-segfw iptables -D FORWARD -d 10.60.2.10 -p tcp --dport 9090 -m state --state NEW -j ACCEPT

Observe

bash — on ns-public
1sudo ip netns exec ns-public curl --max-time 3 http://203.0.113.1:8080/
    curl: (28) Connection timed out
bash — confirm: the nat rule fires, but FORWARD still drops it
1sudo ip netns exec ns-segfw iptables -t nat -L PREROUTING -n -v
    (counter on the DNAT rule increases with each attempt — the translation IS happening)
2sudo ip netns exec ns-segfw iptables -L FORWARD -n -v
    (packet count increasing on the default DROP policy at the bottom, not on any specific ACCEPT rule)
🔵 Reading the symptom — the crucial DNAT-then-filter ordering

This is exactly the timing fact from Section 2.4 in action: the DNAT rewrite happens in PREROUTING, which runs BEFORE the routing decision and BEFORE FORWARD. So by the time FORWARD evaluates the packet, its destination is ALREADY the real internal address (10.60.2.10:9090) — meaning your FORWARD rule must match the translated address, not the original public-facing port 8080. Here, we removed that FORWARD rule entirely, so despite a perfectly working DNAT translation, the filter table's default DROP policy catches the (already-translated) packet.

🔴 Root Cause

The nat table's DNAT rule was correctly translating the destination, but the filter table's FORWARD chain had no corresponding allow rule for the translated (real internal) destination, so the packet was dropped by default policy after translation.

bash — fix
1sudo ip netns exec ns-segfw iptables -A FORWARD -d 10.60.2.10 -p tcp --dport 9090 -m state --state NEW -j ACCEPT
🟦 Production Best Practice

Every DNAT/port-forward rule needs a matching FORWARD allow rule written against the TRANSLATED (internal, real) address and port — never the original public-facing port. Treat these as a pair that must always be added and removed together.

10Break-Fix #4 — Stale Static SNAT After a Gateway IP Change

🔴 Break It

Some environments use a hardcoded SNAT rule (instead of MASQUERADE) for predictability. Simulate a gateway that got reassigned a new public IP, but the SNAT rule still references the old one.

bash — on ns-segfw, switch to a hardcoded (stale) SNAT instead of MASQUERADE
1sudo ip netns exec ns-segfw iptables -t nat -D POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j MASQUERADE
2sudo ip netns exec ns-segfw iptables -t nat -A POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j SNAT --to-source 203.0.113.99
# 203.0.113.99 is NOT actually assigned to this gateway's interface — a stale/incorrect address

Observe

bash — on ns-app-zone
1sudo ip netns exec ns-app-zone curl --max-time 3 http://203.0.113.10/
    curl: (28) Connection timed out
bash — confirm on ns-public with a capture
1sudo ip netns exec ns-public tcpdump -i veth-public -nn -c 3 'tcp port 80'
    203.0.113.99.xxxxx > 203.0.113.10.80: Flags [S]...
    (reply never comes back to this namespace's gateway — 203.0.113.99 isn't a real, reachable address on this segment)
🔵 Reading the symptom

Unlike MASQUERADE, a static SNAT rule doesn't automatically track the interface's real current address — it blindly rewrites to whatever was hardcoded, even if that address is stale, wrong, or was reassigned elsewhere. The traffic leaves with a source address that either doesn't exist or belongs to a different host, so replies go nowhere useful. This is exactly why MASQUERADE is generally preferred over static SNAT on interfaces whose address might ever change.

🔴 Root Cause

A static SNAT rule referenced a public IP address that was no longer actually assigned to the gateway's outbound interface.

bash — fix: switch back to MASQUERADE (self-correcting) or update the static address
1sudo ip netns exec ns-segfw iptables -t nat -D POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j SNAT --to-source 203.0.113.99
2sudo ip netns exec ns-segfw iptables -t nat -A POSTROUTING -s 10.60.1.0/24 -o fw-public-in -j MASQUERADE
🟦 Production Best Practice

Prefer MASQUERADE over static SNAT whenever the outbound interface's address could change (DHCP, cloud-managed IPs) — it's self-correcting by design. Reserve static SNAT for cases where you deliberately need a specific, stable, guaranteed address and can guarantee it will never drift from what's actually configured on the interface.

11Production Best Practices

🟦 Check both tables explicitly

iptables -t nat -L is separate from the default filter table — always check both when troubleshooting NAT-involved traffic.

🟦 DNAT rules need a matching FORWARD rule for the translated address

Never assume a port-forward rule alone is enough — the filter table still evaluates the post-translation destination.

🟦 Prefer MASQUERADE for dynamic interfaces

Static SNAT can silently go stale if the outbound interface's address ever changes; MASQUERADE tracks it automatically.

🟦 Private source addresses must never leak untranslated onto public networks

Missing SNAT/MASQUERADE causes replies to go nowhere, since the private address means nothing outside its own network.

🟦 Use conntrack -L to see the actual live translation

It shows both the original and translated address/port pairs for every tracked connection — direct proof of what NAT is really doing.

14Interview Preparation

ScenarioYou configured a port-forwarding (DNAT) rule to publish an internal service, but external clients still can't connect. What do you check?

First I'd confirm the DNAT rule itself is matching, using iptables -t nat -L PREROUTING -n -v and checking its packet counter. If it's incrementing, the translation is working, so I'd move to the filter table's FORWARD chain — since DNAT happens in PREROUTING before routing and FORWARD, the FORWARD rule needs to match the NEW, translated internal destination, not the original public port. A very common mistake is writing a FORWARD rule for the public-facing port instead of the real internal address and port.

Interviewer follow-up: "What if the DNAT counter itself is at zero?" — Answer: then the packet isn't even matching the DNAT rule — I'd check that it's in the right chain (PREROUTING), on the right incoming interface, and matching the correct destination port that clients are actually connecting to.
ConceptWhat's the difference between SNAT and MASQUERADE?

Both rewrite a packet's source address, but SNAT uses a fixed, explicitly configured address, while MASQUERADE automatically uses whatever address is currently assigned to the outbound interface. MASQUERADE is generally preferred when that interface's address might change, like with DHCP or cloud-assigned IPs, because it's self-correcting — a static SNAT rule can silently go stale if the interface's real address changes and nobody updates the rule.

ConceptWhy does DNAT happen in PREROUTING and SNAT in POSTROUTING?

DNAT needs to happen before the routing decision, because the kernel needs the FINAL, real destination to know how to route the packet correctly — that's why it's in PREROUTING. SNAT happens after routing and after FORWARD, in POSTROUTING, because the packet's original source address is what the filter table's rules should evaluate against, and only after that decision is made should the source be rewritten for its trip out onto the next network.

TroubleshootingAn internal server's outbound internet access broke after a network change, but nothing changed on the server itself. What would you investigate?

I'd suspect the gateway's NAT configuration rather than the server — specifically, whether a static SNAT rule is referencing an IP address that's no longer actually assigned to the gateway's outbound interface. I'd compare the interface's real current address with the SNAT rule's --to-source value, and if they don't match, that confirms the cause; switching to MASQUERADE would prevent this from recurring.
