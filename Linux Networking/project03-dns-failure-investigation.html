1The Incident

We're supporting infrastructure for a bank's payments gateway. Every outbound transaction call goes to a partner bank's API at partner-bank-api.internal. Around mid-morning, alerts start firing.

"About 1 in 5 payment calls are failing with a DNS resolution error. It's intermittent — retrying the exact same request 30 seconds later often works. The partner bank swears their API has had 100% uptime. Application logs just show 'could not resolve host'."

Intermittent DNS failures are some of the trickiest tickets in this masterclass so far, because "sometimes it works" rules out the simplest explanations (a fully broken config would fail every time) and points us toward caching, multiple nameservers, or timing-dependent behavior.

🔵 Why this project matters

DNS sits in front of almost every other networking layer we've covered — before routing, before the firewall, before the TCP handshake even begins, an application usually has to resolve a name first. A huge fraction of "the network is down" tickets turn out to be DNS, and DNS is one of the few layers where the failure can be silent, intermittent, and cache-dependent — which is exactly why it deserves its own deep project instead of being treated as "just check resolv.conf."

2DNS Foundation — Just Enough to Investigate

2.1 Resolution doesn't start at a DNS server — it starts in glibc

🔵 Concept

When an application calls a function like getaddrinfo() to resolve a hostname, it isn't talking to a DNS server directly — it's talking to the C library's resolver, which consults /etc/nsswitch.conf to decide, in order, WHERE to look for the answer (local files first? DNS first? both?). This is why two different tools can give you two different-looking answers for the "same" lookup — some tools use the full system resolver path, others (like classic nslookup) talk to DNS directly and skip /etc/hosts entirely.

2.2 /etc/nsswitch.conf — the traffic cop

🔵 Concept

The line hosts: files dns in /etc/nsswitch.conf tells the resolver: check /etc/hosts FIRST, and only fall through to DNS if there's no match there. This ordering is a very common source of "but I updated DNS and it's still resolving to the old IP" tickets — if a stale entry sits in /etc/hosts, DNS is never even consulted.

2.3 /etc/resolv.conf — where to ask

🔵 Concept

/etc/resolv.conf lists the actual DNS servers (nameserver lines) the resolver will query, in order, plus optional search domains that get appended to short (unqualified) hostnames before they're queried. On systemd-based distros this file is frequently managed automatically by systemd-resolved or NetworkManager, which is why manually editing it sometimes "doesn't stick" — it gets regenerated.

2.4 Search domains — why a short name behaves differently from an FQDN

🔵 Concept

If you look up a short name like partner-bank-api instead of the fully-qualified partner-bank-api.internal, the resolver appends each configured search domain in turn and tries each combination until one resolves. If the search domain is missing or wrong, a short name can fail to resolve even though the fully-qualified version works perfectly — a very easy thing to overlook when only some code paths in an application use short names.

2.5 Caching and TTL — the source of "sometimes it works"

🔵 Concept

DNS answers come with a Time-To-Live (TTL) telling resolvers how long they're allowed to cache the answer. A caching layer (systemd-resolved, dnsmasq, or the application's own resolver cache) will keep answering from cache until the TTL expires — meaning a DNS fix, a failing nameserver, or a changed record can all produce inconsistent, timing-dependent results depending on exactly when a given host or process last refreshed its cache. This is very often the root cause behind "it's intermittent."

5Troubleshooting Method for DNS Incidents

  • 1. Reproduce using getent hosts (the real application resolution path) — not just dig, which skips /etc/hosts and caching layers
    • ↓
  • 2. Is the result consistent across repeated attempts, or does it change? (points to caching/multiple nameservers if inconsistent)
    • ↓
  • 3. Check /etc/hosts for a matching, possibly stale, entry
    • ↓
  • 4. Check /etc/resolv.conf — are the nameservers correct and reachable? Is a needed search domain present?
    • ↓
  • 5. Query each configured nameserver directly with dig to see if they disagree with each other
    • ↓
  • Once the resolver path and every nameserver agree, DNS is cleared — move to routing/firewall/socket layers
🟠 Warning

Don't diagnose DNS issues using only dig or nslookup — both bypass /etc/hosts and nsswitch.conf entirely and talk to a nameserver directly. If dig succeeds but the application still fails, the bug is very likely in /etc/hosts or nsswitch ordering, not in DNS itself. Always cross-check with getent hosts, which follows the real application resolution path.

6Lab Setup — A Namespace with Its Own DNS Server

We'll build two namespaces: ns-paygw (our payments gateway) and ns-dns (running dnsmasq as our lab's internal DNS resolver, authoritative for the .internal zone).

bash — run as root/sudo
1sudo ip netns add ns-paygw
2sudo ip netns add ns-dns
3sudo ip link add veth-paygw type veth peer name veth-dns
4sudo ip link set veth-paygw netns ns-paygw
5sudo ip link set veth-dns netns ns-dns
6sudo ip netns exec ns-paygw ip addr add 10.30.1.10/24 dev veth-paygw
7sudo ip netns exec ns-dns ip addr add 10.30.1.53/24 dev veth-dns
8sudo ip netns exec ns-paygw ip link set veth-paygw up
9sudo ip netns exec ns-dns ip link set veth-dns up
10for ns in ns-paygw ns-dns; do sudo ip netns exec $ns ip link set lo up; done
11# install dnsmasq for our lab DNS server
12sudo ip netns exec ns-dns bash -c "which dnsmasq || apt install -y dnsmasq"

6.1 Configure the lab DNS server to answer for partner-bank-api.internal

bash — on ns-dns
1sudo ip netns exec ns-dns bash -c "cat > /tmp/dnsmasq-lab.conf" <<'EOF'
no-resolv
no-hosts
listen-address=10.30.1.53
address=/partner-bank-api.internal/10.30.9.99
EOF
2sudo ip netns exec ns-dns dnsmasq -C /tmp/dnsmasq-lab.conf -k &
TokenMeaning
no-resolvTells dnsmasq not to read the host's own /etc/resolv.conf for upstream servers — we want it to act as a self-contained authoritative answer for our lab zone only.
listen-address=10.30.1.53Binds dnsmasq to listen for DNS queries on this specific IP.
address=/partner-bank-api.internal/10.30.9.99A static DNS mapping — any query for this exact name gets answered with 10.30.9.99, simulating the partner bank's real, correct IP.
-kKeep dnsmasq running in the foreground so we can see it (in a real lab, run it in its own terminal or as a background job).

6.2 Point the payments gateway at our lab DNS server

bash — on ns-paygw
1sudo ip netns exec ns-paygw bash -c "mkdir -p /etc/netns/ns-paygw; echo 'nameserver 10.30.1.53' > /etc/resolv.conf; echo 'search internal' >> /etc/resolv.conf"
2sudo ip netns exec ns-paygw cat /etc/resolv.conf
    nameserver 10.30.1.53
    search internal
TokenMeaning
nameserver 10.30.1.53The DNS server this host will query — order matters when there are multiple lines; the first is tried first.
search internalA short (unqualified) hostname will have ".internal" appended automatically before being queried.

7Verify the Baseline

bash — on ns-paygw
1sudo ip netns exec ns-paygw getent hosts partner-bank-api.internal
    10.30.9.99  partner-bank-api.internal
2sudo ip netns exec ns-paygw dig +short partner-bank-api.internal
    10.30.9.99
🟢 Validation

Both the real application resolution path (getent) and a direct query (dig) agree. This is our known-good baseline before we start breaking things.

8Break-Fix #1 — Wrong Nameserver IP

🔴 Break It

Simulate a typo or a misapplied config push that points resolv.conf at a nameserver IP that doesn't exist.

bash — on ns-paygw
1sudo ip netns exec ns-paygw bash -c "echo 'nameserver 10.30.1.99' > /etc/resolv.conf; echo 'search internal' >> /etc/resolv.conf"

Observe

bash — on ns-paygw
1sudo ip netns exec ns-paygw getent hosts partner-bank-api.internal
    (no output, non-zero exit — after a multi-second delay)
2sudo ip netns exec ns-paygw dig partner-bank-api.internal
    ;; connection timed out; no servers could be reached
🔵 Reading the symptom

A completely unreachable nameserver produces a slow, total failure — no answer, no error message immediately, just a hang followed by a timeout. This is different from Break #2 and #3 below, which will fail fast with a definite (wrong) answer instead of a slow non-answer. The speed and shape of the failure is itself diagnostic evidence.

🔴 Root Cause

resolv.conf pointed at a nameserver IP with no DNS service listening — every query times out with no reply at all.

bash — fix
1sudo ip netns exec ns-paygw bash -c "echo 'nameserver 10.30.1.53' > /etc/resolv.conf; echo 'search internal' >> /etc/resolv.conf"
🟢 Validate

Re-run getent hosts — should return instantly with the correct IP again.

9Break-Fix #2 — Stale /etc/hosts Entry Overriding DNS

🔴 Break It

DNS is correctly configured and healthy — but someone added an old troubleshooting entry to /etc/hosts months ago and forgot to remove it.

bash — on ns-paygw
1sudo ip netns exec ns-paygw bash -c "echo '10.30.9.200 partner-bank-api.internal' >> /etc/hosts"

Observe

bash — on ns-paygw
1sudo ip netns exec ns-paygw getent hosts partner-bank-api.internal
    10.30.9.200  partner-bank-api.internal
2sudo ip netns exec ns-paygw dig +short partner-bank-api.internal
    10.30.9.99
🔵 Reading the symptom

This is the single most confusing DNS symptom you'll see in production: dig (which talks to the nameserver directly, bypassing /etc/hosts) shows the CORRECT answer, while getent hosts (the real path applications use) shows a WRONG, stale answer. Anyone troubleshooting with dig alone will conclude "DNS is fine" and get stuck — because the actual bug isn't in DNS at all, it's in nsswitch's "files" precedence combined with a forgotten local override.

🔴 Root Cause

A stale entry in /etc/hosts, checked before DNS per nsswitch.conf's "files dns" order, was silently overriding the correct, up-to-date DNS answer.

bash — fix
1sudo ip netns exec ns-paygw sed -i '/partner-bank-api.internal/d' /etc/hosts
🟢 Validate

Re-run getent hosts — it should now fall through to DNS and return 10.30.9.99, matching dig.

🟦 Production Best Practice

Whenever getent hosts and dig disagree, trust getent hosts as "what the application actually experiences," and go straight to checking /etc/hosts and nsswitch.conf ordering rather than re-checking the DNS server.

10Break-Fix #3 — Missing Search Domain (Short Name Fails, FQDN Works)

🔴 Break It

Some parts of the payments application were recently refactored to call the short name partner-bank-api instead of the fully-qualified name. Remove the search domain to simulate a config regression.

bash — on ns-paygw
1sudo ip netns exec ns-paygw bash -c "echo 'nameserver 10.30.1.53' > /etc/resolv.conf"

Observe

bash — on ns-paygw
1sudo ip netns exec ns-paygw getent hosts partner-bank-api
    (no output — resolution failed)
2sudo ip netns exec ns-paygw getent hosts partner-bank-api.internal
    10.30.9.99  partner-bank-api.internal
🔵 Reading the symptom

This is the classic "works with the full name, fails with the short name" pattern, and it's a search-domain problem, not a DNS server problem — our lab DNS server never even received a well-formed query for the bare short name, because there was no search suffix left to append to it before querying.

🔴 Root Cause

The search domain entry was missing from resolv.conf, so short (unqualified) hostnames could no longer be automatically expanded to their fully-qualified form before lookup.

bash — fix
1sudo ip netns exec ns-paygw bash -c "echo 'search internal' >> /etc/resolv.conf"
🟢 Validate

Re-run getent hosts partner-bank-api (short name) — it should now succeed by trying "partner-bank-api.internal" automatically.

🟦 Production Best Practice

Prefer fully-qualified domain names in application configuration wherever practical — they don't depend on search-domain configuration being correct on every host the app might run on, which makes behavior far more predictable across environments.

11Break-Fix #4 — Dead Primary Nameserver Causing Slow, Intermittent Failures

🔴 Break It

This reproduces the original incident's "about 1 in 5 calls fail, retries usually work" symptom. Add a second, healthy nameserver — but list the dead one FIRST.

bash — on ns-paygw
1sudo ip netns exec ns-paygw bash -c "printf 'nameserver 10.30.1.199\nnameserver 10.30.1.53\nsearch internal\n' > /etc/resolv.conf"

Observe

bash — on ns-paygw, run this several times
1sudo ip netns exec ns-paygw time getent hosts partner-bank-api.internal
    10.30.9.99  partner-bank-api.internal
    real    0m5.021s   (much slower than the baseline's near-instant response)
🔵 Reading the symptom

Every single lookup eventually succeeds — but only after the resolver first times out waiting for the dead primary nameserver (10.30.1.199) and THEN falls through to the healthy secondary (10.30.1.53). Under normal load this shows up as slow, and under time pressure or short application-level timeouts, this exact multi-second delay is enough to make some fraction of calls fail outright — precisely the "about 1 in 5 calls fail" pattern from the incident report. This is one of the most underrated DNS incident patterns: a "working" secondary nameserver can still cause production failures if it's listed second and the first one is dead.

🔴 Root Cause

A dead nameserver was listed first in resolv.conf; every lookup paid its full timeout penalty before falling back to a working nameserver, and application-level timeouts weren't tolerant of that added delay.

bash — fix: remove the dead nameserver, keep only the healthy one
1sudo ip netns exec ns-paygw bash -c "printf 'nameserver 10.30.1.53\nsearch internal\n' > /etc/resolv.conf"
🟢 Validate

Re-run the timed getent hosts command — response time should return to near-instant.

12Production Best Practices

🟦 Always test with getent hosts

It's the only tool that follows the exact same resolution path a real application uses — dig and nslookup skip /etc/hosts and can mislead you.

🟦 Keep /etc/hosts clean

Temporary troubleshooting entries left behind in /etc/hosts are one of the most common causes of "DNS looks fine but the app is wrong" incidents.

🟦 Prefer FQDNs in app config

Fully-qualified names remove dependency on search-domain configuration being correct everywhere the app runs.

🟦 Order nameservers by health, not habit

A dead nameserver listed first silently taxes every single lookup with a timeout delay before falling through — monitor nameserver health, don't just add redundancy blindly.

🟦 Remember caching when "it just started working again"

If an issue resolves itself without any config change, suspect a TTL expiring or a cache refreshing rather than assuming the underlying problem is gone for good.

14Interview Preparation

ScenarioAn application intermittently fails to resolve a hostname, but retries usually succeed. How do you approach it?

Intermittent success rules out a fully broken config, so I'd suspect either multiple nameservers where one is unhealthy, or a caching/TTL effect. I'd use getent hosts repeatedly, timing it, to see if some lookups are simply slow rather than failing outright — a dead nameserver listed first in resolv.conf is a very common cause, since the resolver has to time out on it before trying the next one, and that delay alone can trip an application's own timeout.

Interviewer follow-up: "dig says it resolves fine every time — why would the app still fail?" — Answer: dig talks directly to a nameserver and bypasses /etc/hosts and nsswitch entirely, so if there's a stale /etc/hosts entry or the app is using a short name without the right search domain, dig can look perfectly healthy while the real application resolution path fails. I'd always cross-check with getent hosts, which follows the exact same path as the application.
ConceptWhat's the difference between dig, nslookup, and getent hosts?

dig and nslookup query a DNS server directly and bypass local resolution mechanisms like /etc/hosts and nsswitch ordering. getent hosts goes through the full system resolver path — the same one glibc-based applications use — so it's the most accurate way to reproduce what an application will actually see.

TroubleshootingAn app works using a fully-qualified hostname but fails using a short name. What's the likely cause?

That points to the search domain configuration in /etc/resolv.conf being missing or wrong — short names rely on a configured search suffix being appended automatically before the lookup happens; without it, the bare short name gets queried as-is and typically fails.

DevOpsWhy does DNS troubleshooting matter for Kubernetes or containerized environments?

CoreDNS in Kubernetes and Docker's embedded DNS both follow the same fundamental resolver concepts — search domains (which is why Kubernetes Services can be reached by short names within a namespace), caching, and resolution order. The debugging instincts from plain Linux DNS troubleshooting — cross-checking getent-style resolution against direct queries, watching for stale entries — transfer directly.
