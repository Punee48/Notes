1The Incident Timeline

We support a telecom company's NAT gateway, which translates thousands of internal servers' outbound connections through a small number of public IPs. It's been rock solid for months — except during specific, unpredictable windows where a small percentage of brand-new outbound connections hang indefinitely in SYN-SENT, then usually recover on their own within a few minutes.

TimeEvent
14:02Monitoring flags a spike in connection timeouts from several internal services calling external APIs through the NAT gateway
14:04Engineer checks the NAT gateway — CPU, memory, and interface counters all look completely normal
14:06ss -tn on an affected client shows several connections sitting in SYN-SENT for well over a minute
14:09By the time anyone captures packets, the affected connections have already resolved themselves — the window passed
14:15Everything looks completely normal again. No firewall rule changed, no deployment happened, no obvious trigger.

"It's not constant, it's not tied to any specific destination, and by the time we look closely it's already stopped. It seems to correlate loosely with periods when a LOT of short outbound connections are happening at once, but we can't reproduce it on demand."

This has the exact fingerprint of a resource exhaustion problem in something that only becomes scarce under specific load conditions and recovers once that load subsides — and on a NAT gateway, the resource most people forget to monitor is the available pool of source ports.

🔵 Why this project matters

NAT gateways handling many outbound connections through a limited number of public IPs are extremely common — corporate internet gateways, cloud NAT gateways, telecom infrastructure. The specific failure mode in this project — source port exhaustion under connection churn — is a genuinely common, genuinely hard-to-reproduce-on-demand class of incident that catches experienced engineers off guard specifically because it's invisible in every "normal" health metric.

2Why NAT Ports Are a Hidden Finite Resource

2.1 Every NAT-translated connection consumes one source port on the public IP

🔵 Concept

Recall Project 8's MASQUERADE — when the gateway translates an internal server's outbound connection, it must pick a source port on its own public IP to represent that specific connection (since many internal hosts are sharing one public IP, the port number is what keeps their connections distinguishable). The pool of usable ports for this is finite — roughly the ephemeral port range, about 64,000 ports per public IP, MINUS whatever's currently in use or still lingering in TIME-WAIT from a recently-closed connection.

2.2 TIME-WAIT connections still hold their port — this is the hidden cost

🔵 Concept

Project 4 taught us TIME-WAIT is normal, healthy TCP behavior after a connection closes. On a NAT gateway specifically, EVERY translated connection that closes leaves its allocated source port in TIME-WAIT for roughly 60 seconds by default — meaning under a high enough rate of short-lived connection churn, the gateway can genuinely run out of ports to allocate to brand-new connections, even though the "old" connections using those ports are technically already finished, just not fully released yet.

2.3 What happens when NAT can't allocate a port for a new connection

🔵 Concept

When the NAT gateway's kernel can't find a free source port to translate a brand-new outbound connection, the SNAT/MASQUERADE operation itself fails for that packet — the SYN is dropped internally before it can even be sent out translated. From the CLIENT's perspective, this looks exactly like a silent firewall drop or a network black hole: the connection sits in SYN-SENT, retransmitting via the exact exponential backoff pattern from Project 13, with no error and no obvious cause, because the actual failure happened invisibly inside the NAT gateway's own port allocation logic.

2.4 Why it self-resolves and why it's nearly impossible to catch live

🔵 Concept

As soon as enough of those TIME-WAIT entries age out (that ~60 second default), ports free back up, and new connections start succeeding again — the whole incident window is naturally short and self-healing, which is exactly why it never survives long enough for a leisurely investigation. This combination — invisible in normal health checks, self-resolving, and load-triggered — is precisely what makes this class of incident so notoriously difficult, and exactly why understanding the mechanism ahead of time (rather than trying to catch it live) is the practical path to diagnosing it.

5Lab Setup — A Constrained NAT Gateway

bash — run as root/sudo; reuse Project 8's NAT pattern, but with a deliberately narrow port range to make exhaustion reproducible on demand
1sudo ip netns add ns-internal       # many "internal servers" will simulate their traffic from here
2sudo ip netns add ns-natgw          # the NAT gateway
3sudo ip netns add ns-external       # the external destination our internal traffic is calling
4sudo ip link add veth-int type veth peer name gw-int-in
5sudo ip link add veth-ext type veth peer name gw-ext-in
6sudo ip link set veth-int netns ns-internal; sudo ip link set gw-int-in netns ns-natgw
7sudo ip link set veth-ext netns ns-external; sudo ip link set gw-ext-in netns ns-natgw
8sudo ip netns exec ns-internal ip addr add 10.220.1.10/24 dev veth-int
9sudo ip netns exec ns-natgw ip addr add 10.220.1.1/24 dev gw-int-in
10sudo ip netns exec ns-natgw ip addr add 203.0.115.1/24 dev gw-ext-in
11sudo ip netns exec ns-external ip addr add 203.0.115.10/24 dev veth-ext
12sudo ip netns exec ns-internal ip route add default via 10.220.1.1
13for ns in ns-internal ns-natgw ns-external; do sudo ip netns exec $ns ip link set lo up; done
14sudo ip netns exec ns-internal ip link set veth-int up
15sudo ip netns exec ns-natgw bash -c "ip link set gw-int-in up; ip link set gw-ext-in up; sysctl -w net.ipv4.ip_forward=1"
16sudo ip netns exec ns-external ip link set veth-ext up
17sudo ip netns exec ns-external python3 -m http.server 9000 --bind 203.0.115.10 &   # our external API endpoint stand-in
18# deliberately narrow SNAT port range — this is the artificial constraint that makes the incident reproducible on demand
19sudo ip netns exec ns-natgw iptables -t nat -A POSTROUTING -s 10.220.1.0/24 -o gw-ext-in -j MASQUERADE --to-ports 40000-40010   # --to-ports restricts SNAT to just 11 possible source ports — normally this range would be thousands wide
20sudo ip netns exec ns-natgw iptables -A FORWARD -s 10.220.1.0/24 -j ACCEPT
TokenMeaning
--to-ports 40000-40010Restricts MASQUERADE to choosing a source port only from this narrow 11-port range — in a real environment this would normally span thousands of ports; we're narrowing it deliberately so port exhaustion becomes reproducible in a lab in seconds instead of requiring genuinely massive real-world traffic.
net.ipv4.ip_forward=1Same forwarding requirement as every router/NAT namespace we've built since Project 2.

7Break-Fix #1 — NAT Source Port Exhaustion Under Churn

🔴 Reproduce It

Fire a burst of many short-lived connections at once — simulating the internal services' traffic churn from the incident report — through our artificially narrow 11-port NAT range.

bash — on ns-internal, generate a connection-churn burst
1for i in $(seq 1 25); do (sudo ip netns exec ns-internal curl -s --max-time 3 -o /dev/null -w "conn-$i: %{http_code} in %{time_total}s\n" http://203.0.115.10:9000/ &); done; wait   # 25 near-simultaneous new connections, well beyond our 11-port budget
    conn-1: 200 in 0.011s
    conn-2: 200 in 0.014s
    ...
    conn-14: 000 in 3.003s   (timed out — ran out of available NAT ports)
    conn-15: 000 in 3.002s
    ...

Diagnose — check the actual mechanism, not just the symptom

bash — on ns-internal, check the failed connections' actual TCP state
1sudo ip netns exec ns-internal ss -tn state syn-sent   # exactly the state from our incident report
    SYN-SENT  0  1  10.220.1.10:xxxxx  203.0.115.10:9000   (one or more connections genuinely stuck here)
2sudo ip netns exec ns-natgw conntrack -L 2>/dev/null | grep 9000 | wc -l   # how many connections is the gateway actually tracking against port 9000 right now
    11   (exactly at our artificial ceiling — every available port is currently in use or in TIME-WAIT)
3sudo ip netns exec ns-natgw dmesg 2>/dev/null | tail -5   # check for kernel-level messages about the failed translation
    (may show messages referencing port allocation failure for MASQUERADE, depending on kernel version/verbosity)
🔵 Reading the symptom

Exactly 11 connections succeeded (or were actively tracked) — our artificial port ceiling — and everything past that point hung in SYN-SENT, indistinguishable from a firewall drop or network black hole from the client's perspective, but with a completely different, invisible-to-standard-monitoring root cause: the NAT gateway simply had no source port left to allocate for the translation. This is precisely the fingerprint from the incident report — intermittent, load-correlated, nothing wrong with CPU/memory, and it will self-resolve within about 60 seconds as the earliest connections' TIME-WAIT entries age out and free their ports.

🔴 Root Cause

The NAT gateway's available source port range for translated connections was too narrow for the rate of new connection churn, causing new connections to fail SNAT translation entirely and hang in SYN-SENT until enough previously-used ports aged out of TIME-WAIT.

bash — fix: widen the available port range dramatically
1sudo ip netns exec ns-natgw iptables -t nat -D POSTROUTING -s 10.220.1.0/24 -o gw-ext-in -j MASQUERADE --to-ports 40000-40010
2sudo ip netns exec ns-natgw iptables -t nat -A POSTROUTING -s 10.220.1.0/24 -o gw-ext-in -j MASQUERADE   # no --to-ports restriction — use the full available ephemeral range
🟢 Validate

Re-run the 25-connection burst — all should now succeed, since the available port pool is thousands wide instead of 11.

8Break-Fix #2 — Conntrack Table Pressure Compounding It

🟠 Compounding Factor

Port exhaustion is one resource; the conntrack table itself (Project 7's lesson) is a separate, independently exhaustible resource that compounds the exact same symptom under heavier load.

bash — on ns-natgw, restore a wide port range, but now constrain the conntrack table instead
1sudo ip netns exec ns-natgw sysctl -w net.netfilter.nf_conntrack_max=15   # artificially tiny conntrack table — a second, independent bottleneck

Observe

bash — on ns-internal, repeat the burst
1for i in $(seq 1 25); do (sudo ip netns exec ns-internal curl -s --max-time 3 -o /dev/null -w "conn-$i: %{http_code}\n" http://203.0.115.10:9000/ &); done; wait
    (again, roughly the first ~15 succeed, the rest fail — but this time for a DIFFERENT underlying reason)
2sudo ip netns exec ns-natgw dmesg 2>/dev/null | grep -i "table full"   # Project 7's exact diagnostic, now relevant in this compound scenario
    nf_conntrack: table full, dropping packet
🔵 Reading the symptom — same client-side signature, different root cause

From the client's perspective, this looks absolutely identical to Break-Fix #1 — connections hang in SYN-SENT under load, and everything recovers once load subsides. But the underlying resource is completely different: here it's the conntrack table's total entry count, not the NAT port range specifically. This is exactly why compound incidents are hard — two, or even three, independent finite resources (port range, conntrack table size, and in a differently-configured environment, potentially other limits too) can each independently produce the identical client-visible symptom, and only checking the gateway's own internal state (conntrack count vs. max, dmesg messages, actual port usage) distinguishes which one is actually in play during any given occurrence.

🔴 Root Cause

The connection tracking table's maximum size was too small for the connection churn rate, independently producing the same SYN-SENT-under-load symptom as the port exhaustion in Break-Fix #1, but via a completely separate kernel resource.

bash — fix
1sudo ip netns exec ns-natgw sysctl -w net.netfilter.nf_conntrack_max=262144   # restore to a realistic production-scale value
🟦 Production Best Practice

On any NAT gateway, monitor BOTH the conntrack table utilization (current count vs. nf_conntrack_max) AND effective NAT port availability under peak load as standing metrics — neither shows up in standard CPU/memory/interface dashboards, and either one alone can produce this exact incident signature independently.

9Production Best Practices

🟦 Monitor NAT port utilization directly

Not just conntrack table size — the actual available source ports per public IP under realistic peak connection churn.

🟦 Recognize the load-dependent, self-resolving fingerprint

Intermittent, correlates with connection rate, invisible in standard health metrics, resolves on its own — treat this pattern as a strong signal to check kernel-internal resource limits.

🟦 Reproduce deliberately when live capture isn't feasible

A narrowed resource (port range, conntrack max) in a lab reproduces in seconds what might take real traffic hours to trigger.

🟦 Multiple independent resources can share one symptom

Port exhaustion and conntrack exhaustion look identical to the client — always check the gateway's own internal state to distinguish them.

11Interview Preparation

ScenarioConnections through a NAT gateway intermittently hang in SYN-SENT during high-traffic periods, but every standard health metric looks fine. What would you check?

I'd suspect a kernel-internal resource that's finite but not tracked by standard monitoring — specifically NAT source port availability and the connection tracking table size. Both are shared, per-gateway resources that can be exhausted under high connection churn even when CPU, memory, and interface counters look completely normal, and both produce the exact same client-visible symptom: SYN-SENT connections that eventually retry successfully once load subsides.

Interviewer follow-up: "How would you tell those two possible causes apart?" — Answer: I'd check the gateway's own internal state directly — conntrack -L compared against nf_conntrack_max for table pressure, and dmesg for "table full" messages specifically; for port exhaustion, I'd look at how many connections are actively using the available NAT port range relative to the connection churn rate.
ConceptWhy can a NAT gateway run out of source ports even though 64,000 is a very large number?

Because every closed connection's port stays reserved in TIME-WAIT for roughly 60 seconds by default before it's actually free to reuse. Under a high enough rate of short-lived connection churn — many connections opening and closing per second — the gateway can genuinely exhaust its available port pool faster than TIME-WAIT entries age out and free them back up, even though the total range is large.

TroubleshootingWhy is this specific class of incident so hard to catch through live investigation?

Because it's inherently self-resolving — as soon as connection churn drops enough for TIME-WAIT entries to age out, the resource frees up and everything returns to normal on its own, often within a minute or two. By the time an engineer gets a packet capture or detailed investigation running, the transient condition has usually already passed, which is exactly why understanding the underlying mechanism ahead of time, and monitoring for it proactively, matters more than trying to catch it reactively.
