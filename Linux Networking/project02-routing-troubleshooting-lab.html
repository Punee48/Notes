1The Incident

We're now supporting a telecom company's monitoring infrastructure. There's a Linux server, mon-server-01, deliberately built with two network interfaces — one facing the internal management network, one facing the monitored production network. This is called a multi-homed server, and it's extremely common in telecom, banking, and enterprise DevOps environments (bastion hosts, jump servers, monitoring collectors, NAT gateways all look like this).

"mon-server-01 can reach some devices on the production network fine, but polling for the core-switch-14 subnet keeps timing out. Also, our security team says they're seeing weird half-open connections in their firewall logs from that server — like it's sending traffic but never getting proper replies logged."

Two different symptoms, one root skill: understanding exactly how the Linux kernel decides where a packet goes when a server has more than one way out.

🔵 Why this project matters

The moment a Linux server has more than one NIC — which is true of almost every serious production server, bastion host, or cloud instance with multiple ENIs — routing stops being "obvious" and becomes a decision the kernel makes using rules you must understand. Multi-homed routing problems are one of the top causes of "it works from my laptop but not from the server" tickets in enterprise environments, and they show up again later in this masterclass when we cover VRF, container networking, and Kubernetes node networking.

2Routing Foundation — Just Enough to Investigate

2.1 The routing table is a list of "if destination matches X, send it via Y"

🔵 Concept

Every Linux host keeps a routing table — a list of rules the kernel checks, in a specific order of specificity, every single time it needs to send a packet. Each entry says: "packets going to this network should leave via this interface, optionally through this next-hop gateway." Run ip route and you're looking directly at the kernel's decision table.

2.2 Connected routes vs static routes vs the default route

🔵 Concept

A connected route is created automatically the instant you assign an IP to an interface — the kernel already knows "this /24 is directly reachable through this NIC, no gateway needed." A static route is one a human or automation tool explicitly adds for networks that are NOT directly connected — "to reach that other network, go through this gateway first." The default route (destination 0.0.0.0/0) is the fallback: "if nothing more specific matches, send it here" — usually pointing at the main internet or core-network gateway.

2.3 Longest prefix match — the single most important routing rule

🔵 Concept

If a destination IP matches more than one route in the table, the kernel always picks the most specific match — the one with the longest subnet mask (the smallest, most precise network) — never the shortest. A route to 10.10.5.0/24 always wins over a route to 10.10.0.0/16 for a packet going to 10.10.5.7, even if the /16 route was added first. This single rule explains most "why did my packet go the wrong way" mysteries.

2.4 Route metrics — the tiebreaker

🔵 Concept

If two routes match a destination with the same prefix length (for example, two default routes from two NICs), the kernel uses the metric

2.5 Policy-based / source-based routing — why one routing table isn't always enough

🔵 Concept

A normal routing table only looks at the destination IP. But on a multi-homed server you often need traffic that came in or originates from one interface to also leave through that same interface — otherwise you get asymmetric routing, which many stateful firewalls will silently drop because they never saw the outbound leg of the "conversation." Linux solves this with ip rule (policy routing) and multiple named routing tables in /etc/iproute2/rt_tables — letting you say "traffic sourced from 10.20.1.5 uses routing table 100, not the main table."

5Troubleshooting Method for Routing Incidents

  • 1. What does ip route get <destination> say the kernel will actually do?
    • ↓
  • 2. Is there a specific route for that destination, or is it silently falling back to the default route?
    • ↓
  • 3. Are there multiple candidate routes (duplicate default routes, overlapping statics)? Compare prefix length and metric.
    • ↓
  • 4. Does outbound traffic and its expected return traffic use the SAME interface? (asymmetric routing check)
    • ↓
  • 5. Are there any policy rules (ip rule) overriding the main table?
    • ↓
  • Once route selection is confirmed correct, THEN move on to firewall/socket-layer checks from Project 1
🟠 Warning

Don't assume "there's a route in the table" means "that's the route being used." Always confirm with ip route get, which runs the kernel's real decision logic — reading the table with your eyes and mentally picking a route is exactly how routing bugs get missed.

6Lab Setup — Building a Multi-Homed Namespace

We'll build three namespaces: ns-mon (our multi-homed server, with two veth interfaces), ns-mgmt-gw (simulating the management network's gateway/router), and ns-prod-gw (simulating the production network's gateway, which also has a route onward to core-switch-14's subnet).

bash — run as root/sudo
1# create the three namespaces
2sudo ip netns add ns-mon
3sudo ip netns add ns-mgmt-gw
4sudo ip netns add ns-prod-gw
5# veth pair 1: ns-mon (mgmt side) <-> ns-mgmt-gw
6sudo ip link add eth-mgmt type veth peer name gw-mgmt-in
7sudo ip link set eth-mgmt netns ns-mon
8sudo ip link set gw-mgmt-in netns ns-mgmt-gw
9# veth pair 2: ns-mon (prod side) <-> ns-prod-gw
10sudo ip link add eth-prod type veth peer name gw-prod-in
11sudo ip link set eth-prod netns ns-mon
12sudo ip link set gw-prod-in netns ns-prod-gw
13# assign addresses
14sudo ip netns exec ns-mon ip addr add 10.20.1.5/24 dev eth-mgmt
15sudo ip netns exec ns-mon ip addr add 10.10.9.5/24 dev eth-prod
16sudo ip netns exec ns-mgmt-gw ip addr add 10.20.1.1/24 dev gw-mgmt-in
17sudo ip netns exec ns-prod-gw ip addr add 10.10.9.1/24 dev gw-prod-in
18# simulate core-switch-14's subnet living behind ns-prod-gw
19sudo ip netns exec ns-prod-gw ip addr add 10.10.14.1/24 dev lo:1 2>/dev/null || sudo ip netns exec ns-prod-gw ip addr add 10.10.14.1/32 dev gw-prod-in
20# bring everything up
21for ns in ns-mon ns-mgmt-gw ns-prod-gw; do sudo ip netns exec $ns ip link set lo up; done
22sudo ip netns exec ns-mon bash -c "ip link set eth-mgmt up; ip link set eth-prod up"
23sudo ip netns exec ns-mgmt-gw ip link set gw-mgmt-in up
24sudo ip netns exec ns-prod-gw ip link set gw-prod-in up
25# enable forwarding on the gateways so they can route onward
26sudo ip netns exec ns-mgmt-gw sysctl -w net.ipv4.ip_forward=1
27sudo ip netns exec ns-prod-gw sysctl -w net.ipv4.ip_forward=1
Word-by-word breakdown of the new pieces (click to expand)
TokenMeaning
ip link add eth-mgmt type veth peer name gw-mgmt-inCreates a virtual cable with two ends: eth-mgmt and gw-mgmt-in — one end goes to our multi-homed server, the other to the simulated management gateway.
net.ipv4.ip_forward=1A kernel sysctl that tells Linux "you are allowed to forward packets between interfaces instead of only handling traffic addressed to yourself." Without this, our simulated gateways would silently drop everything that isn't addressed directly to them — this is exactly what turns a namespace into a router.

6.1 Add default and static routes on mon-server-01 (ns-mon)

bash — on ns-mon
1# default route out the management interface
2sudo ip netns exec ns-mon ip route add default via 10.20.1.1 dev eth-mgmt metric 100
3# static route to core-switch-14's subnet via the production gateway
4sudo ip netns exec ns-mon ip route add 10.10.14.0/24 via 10.10.9.1 dev eth-prod
5sudo ip netns exec ns-mon ip route show
    default via 10.20.1.1 dev eth-mgmt metric 100

6.2 Let the gateways route onward correctly

bash — on ns-prod-gw
1sudo ip netns exec ns-prod-gw ip route add 10.10.9.0/24 dev gw-prod-in 2>/dev/null; true

7Verify the Baseline

bash — on ns-mon
1sudo ip netns exec ns-mon ip route get 10.10.14.5

8Break-Fix #1 — Missing Specific Route (Falls Back to Default)

🔴 Break It

Remove the static route to core-switch-14's subnet, simulating what happens after someone reboots the server and a static route defined only via a runtime ip route add (not persisted in config) disappears.

bash — on ns-mon
1sudo ip netns exec ns-mon ip route del 10.10.14.0/24 via 10.10.9.1 dev eth-prod

Observe

bash — on ns-mon
1sudo ip netns exec ns-mon ip route get 10.10.14.5
    10.10.14.5 via 10.20.1.1 dev eth-mgmt src 10.20.1.5
🔵 Reading the symptom

Notice the kernel didn't error out — it silently fell back to the default route and sent the packet out the management interface instead, where core-switch-14's subnet was never reachable to begin with. This is the dangerous part of missing specific routes: there's often no obvious error, just traffic quietly going the wrong way and eventually timing out at the application layer, which looks identical to a firewall problem from the outside.

🔴 Root Cause

The static route to 10.10.14.0/24 was missing, so longest-prefix-match had nothing more specific to select than the default route.

bash — fix
1sudo ip netns exec ns-mon ip route add 10.10.14.0/24 via 10.10.9.1 dev eth-prod
🟦 Production Best Practice

Never add production static routes only with a runtime ip route add — persist them properly (e.g. via NetworkManager profiles, systemd-networkd .network files, or your distro's route config files) so they survive reboots. A route that only exists in RAM disappears exactly when you can least afford it.

9Break-Fix #2 — Duplicate Default Routes with a Bad Metric

🔴 Break It

Add a second default route out eth-prod with a lower (better) metric than the intended management default route — simulating a common mistake when DHCP or automation adds a default route on a second NIC without anyone intending it to become primary.

bash — on ns-mon
1sudo ip netns exec ns-mon ip route add default via 10.10.9.1 dev eth-prod metric 50
2sudo ip netns exec ns-mon ip route show
    default via 10.10.9.1 dev eth-prod metric 50
    default via 10.20.1.1 dev eth-mgmt metric 100
    ...

Observe

bash — on ns-mon, test traffic to something NOT explicitly routed
1sudo ip netns exec ns-mon ip route get 8.8.8.8
    8.8.8.8 via 10.10.9.1 dev eth-prod src 10.10.9.5
🔵 Reading the symptom

General/internet-bound or otherwise unmatched traffic is now silently leaving via the production interface instead of the intended management interface, because the lower metric (50) beats the original (100) for the tied /0 prefix. On a real server this could mean monitoring/management traffic starts leaving through a network segment with different firewall rules, NAT behavior, or no internet egress at all — again, with no obvious error message, just traffic going somewhere unexpected.

🔴 Root Cause

Two default routes existed simultaneously with different metrics, and the lower metric silently won, overriding the intended primary path.

bash — fix: remove the unintended default route
1sudo ip netns exec ns-mon ip route del default via 10.10.9.1 dev eth-prod metric 50
🟢 Validate

Re-run ip route get 8.8.8.8 — it should now show the eth-mgmt route again as the only default.

10Break-Fix #3 — Asymmetric Routing (The Security Team's "Half-Open Connections")

🔴 Break It

This reproduces the second symptom from the incident report. Imagine ns-prod-gw is a stateful firewall/gateway — it only allows return traffic for connections whose outbound leg it actually saw leave through it. Now add a route on ns-mon that sends traffic to a specific host (10.10.9.50) out through eth-mgmt instead of eth-prod, even though eth-prod is the "correct", directly connected path.

bash — on ns-mon (misconfigured, more-specific-looking static route)
1sudo ip netns exec ns-mon ip route add 10.10.9.50/32 via 10.20.1.1 dev eth-mgmt

Observe

bash — on ns-mon
1sudo ip netns exec ns-mon ip route get 10.10.9.50
    10.10.9.50 via 10.20.1.1 dev eth-mgmt src 10.20.1.5
🔵 Reading the symptom

A /32 route (the most specific prefix possible) always wins by longest-prefix-match, even though the destination is physically on the eth-prod segment. So outbound packets to 10.10.9.50 now leave via eth-mgmt — but 10.10.9.50 will naturally try to reply back via eth-prod, since that's its own directly connected network. The stateful gateway on the production side never saw the outbound SYN, so it treats the reply as unsolicited and drops it. This is asymmetric routing, and it's exactly the "weird half-open connections" the security team reported — the connection isn't blocked outright, it just never completes because the two legs of the conversation take physically different paths.

🔴 Root Cause

An overly specific static route sent outbound traffic to a production host via the wrong interface, breaking the symmetry that stateful firewalls require to track connections.

bash — fix: remove the bad /32 route
1sudo ip netns exec ns-mon ip route del 10.10.9.50/32 via 10.20.1.1 dev eth-mgmt
🟦 Production Best Practice — the real, robust fix

Removing one bad route fixes this instance, but the durable fix on multi-homed servers is policy-based (source) routing: force any traffic sourced from a given interface's IP to always route back out that same interface, regardless of what static routes exist elsewhere. Preview of how that looks (we'll build this hands-on in a later Advanced Networking project):

bash — policy routing preview
1echo "100 prod-table" | sudo tee -a /etc/iproute2/rt_tables
2sudo ip netns exec ns-mon ip route add default via 10.10.9.1 dev eth-prod table prod-table
3sudo ip netns exec ns-mon ip rule add from 10.10.9.5 table prod-table
TokenMeaning
/etc/iproute2/rt_tablesThe file that names additional routing tables beyond the default "main" table, so we can reference "prod-table" by name instead of only a number.
ip route add ... table prod-tableAdds a route into this separate table instead of the main one — it has no effect until something tells the kernel to actually use it.
ip rule add from 10.10.9.5 table prod-tableA policy rule: "for any packet whose SOURCE address is 10.10.9.5, ignore the main table and use prod-table instead." This guarantees symmetry — anything sourced from the production IP always routes back out via production, no matter what more-specific routes exist in the main table.

11Break-Fix #4 — Blackhole Route

🔴 Break It

A blackhole route intentionally and silently discards matching traffic at the routing layer itself — sometimes used deliberately (to stop routing loops, or block a known-bad subnet), but occasionally left behind by mistake after decommissioning a network segment.

bash — on ns-mon
1sudo ip netns exec ns-mon ip route add blackhole 10.10.14.0/24

Observe

bash — on ns-mon
1sudo ip netns exec ns-mon ping -c 2 10.10.14.5
    connect: Network is unreachable
2sudo ip netns exec ns-mon ip route get 10.10.14.5
    RTNETLINK answers: Network is unreachable
🔵 Reading the symptom

Unlike a firewall drop (which lets the packet leave the box and disappear on the wire, producing a timeout), a blackhole route rejects the packet inside the kernel itself, before it's ever transmitted, and does so instantly rather than after a timeout. "Network is unreachable" returned instantly, for every single destination in that /24, is a strong signature of a blackhole or unreachable route entry — very different from the earlier firewall DROP scenario in Project 1, which hung until timeout.

bash — confirm and fix
1sudo ip netns exec ns-mon ip route show | grep blackhole
    blackhole 10.10.14.0/24
2sudo ip netns exec ns-mon ip route del blackhole 10.10.14.0/24
🔴 Root Cause

A leftover (or maliciously/mistakenly added) blackhole route was silently discarding all traffic to core-switch-14's subnet at the kernel level.

🟢 Validate

Re-add the correct static route from Section 6.1 if needed, then confirm with ip route get 10.10.14.5 and a successful ping.

12Production Best Practices

🟦 Always use ip route get

Never eyeball the routing table and guess — ask the kernel directly what it will actually do for a specific destination.

🟦 Set explicit metrics on multi-homed hosts

Never let two default routes exist with equal or accidental metrics — be explicit about which interface should win.

🟦 Watch for asymmetric routing on multi-NIC servers

Whenever a multi-homed server talks to stateful firewalls or NAT devices, verify outbound and expected return traffic use the same interface — use policy routing (ip rule + rt_tables) to guarantee it.

🟦 Persist routes properly

Runtime-only routes vanish on reboot — always persist static routes through your distro's proper network configuration mechanism.

🟦 Know your instant-fail vs slow-fail signatures

"Network unreachable" (instant) = local routing/blackhole issue. Timeout (slow) = firewall drop or unreachable next-hop somewhere downstream. This distinction alone often tells you which team to loop in first.

14Interview Preparation

ScenarioA server with two NICs sends traffic out the wrong interface. How do you troubleshoot it?

I'd start with ip route get for the exact destination to see the kernel's real decision, not just eyeball the table. If it's using an unexpected interface, I'd check whether a more specific route exists that shouldn't — longest prefix match always wins regardless of insertion order. If there are two routes with the same prefix length, like duplicate default routes, I'd compare their metrics, since the lower metric wins ties.

Interviewer follow-up: "What if the routing table looks completely correct on the sending server?" — Answer: I'd check for asymmetric routing — the outbound path might be correct, but the destination's reply could be taking a different path back, which a stateful firewall in between would drop. I'd verify by checking the return path's routing on the other host, or by capturing traffic on both sides.
ConceptWhat is longest prefix match and why does it matter?

When multiple routes in the table could match a destination IP, the kernel always chooses the most specific one — the one with the longest subnet mask — regardless of which route was added first or which one looks like the "main" route. It matters because it's the rule that explains almost every unexpected routing decision; a /32 static route will always beat a /24 or a default route for a matching destination.

TroubleshootingWhat's the difference between a firewall drop and a blackhole route, from the client's perspective?

A firewall drop lets the packet leave the sending server and travel across the network, and the client experiences it as a timeout because no reply ever comes back. A blackhole route rejects the packet inside the sender's own kernel before it's even transmitted, so the client gets an immediate, explicit "Network is unreachable" error instead of a slow timeout.

DevOpsWhy does this matter for cloud or Kubernetes environments?

Multi-homed routing logic is exactly what's happening under the hood with EC2 instances that have multiple ENIs, NAT gateways, and even Kubernetes nodes that route pod traffic across different interfaces — understanding longest prefix match and policy routing on a plain Linux box makes those higher-level platforms much less mysterious when something misroutes.
