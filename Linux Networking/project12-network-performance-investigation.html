1The Incident

Namma e-commerce platform team-oda checkout backend, product-catalog service-oda kitta call panra, adhu konjam slow-a irukku nu complaint vandhudhu. Naama already routing sari-nu paathom, firewall sari-nu paathom, DNS um sari, TCP handshake um clean-a complete aaguthu.

"Connection is fine boss, everything connects properly. But throughput konjo kammi maadhiri irukku, and sometimes latency spike aaguthu randomly. App team says nothing changed on their side."

Ithu vera maadhiri problem — connectivity illa, performance. Ella earlier project layer um "connected-a irukka, illaya" nu paathom. Ippo namba "eppadi nalla irukku, illa mosama irukku" nu measure pannanum — latency, throughput, packet loss, errors, ellame numbers vachu paakanum.

🔵 Ithu yean important

Production-la "network is slow" nu complaint vandha, adhu vague-a irukkadhu — exact-a enga problem-nu kandupudika, konjo metrics theriyanum: bandwidth vera, latency vera, packet loss vera. Ella performance ticket-ku, indha basic vocabulary theriyama poana, guess pannikittu irupom dhaan.

2Performance Foundation

2.1 Latency vs Throughput — rendume same illa

🔵 Concept

Latency means — oru packet send pannitu, adha reply vara evlo time aaguthu (usually milliseconds-la measure pannuvom). Throughput means — evlo data, evlo fast-a transfer pannalam (megabits per second, etc). Rendும vera vera irukku — high latency, high throughput link irukkalam (satellite link maadhiri — slow to respond, but bulk data nalla pogum). Adhu maadhiri, low latency, low throughput um irukkalam. Checkout-la "slow" nu sonna, first question — latency problem-a, illa throughput problem-a nu kandupudikanum, rendும fix vera vera.

2.2 Packet loss and retransmission — namba already paathom (Project 5), ippo measure pannuvom

🔵 Concept

Project 5-la tcpdump vachu retransmission-a kandupudichom. Ippo namba system-level-a, evlo % packet loss irukku nu measure pannuvom — ping statistics, iperf3 loss report, TCP retransmit counters (nstat command vachu).

2.3 NIC-level errors — hardware/driver layer

🔵 Concept

Sometimes problem TCP layer-la illa — physical/virtual NIC layer-la irukkum. RX/TX errors, dropped packets, CRC errors — ivanga ellam ip -s link and ethtool -S command-la theriyum. Cable problem, bad driver, oversubscribed virtual NIC — ithu ellam ivvalavu low-level-la kaanum.

2.4 Socket backlog and ephemeral ports — application layer bottleneck

🔵 Concept

Server side-la, connections accept panna kaathurukkura queue-a "backlog" nu solluvom — adhu full aaiten, new connections drop aagum, even though server healthy-a run aagudhu. Client side-la, konjo connections rapid-a open/close pannina, local ports (ephemeral range) exhaust aagalam — Project 4-la TIME-WAIT paathom, adhu direct-a ithoda connected.

3Where Each Metric Comes From

Figure 1 — Ovvoru layer-kum, adhoda own metric and own command irukku. Adha confuse pannama, exact layer-a target pannanum.

4Troubleshooting Method

  • 1. Measure latency first — ping / traceroute RTT numbers, baseline vachu compare pannu
    • ↓
  • 2. Measure throughput separately — iperf3 vachu, actual achievable bandwidth-a paaru, not assumed
    • ↓
  • 3. Check NIC counters — ip -s link, ethtool -S — errors/drops climbing-a irukka
    • ↓
  • 4. Check application-level limits — socket backlog (ss -lnt "Recv-Q/Send-Q"), ephemeral port usage
    • ↓
  • Correlate — enga exact-a bottleneck irukku nu, oru layer-a point pannu, appuram fix pannu
🟠 Warning

"Slow" nu solli mattum start pannadha — first exact metric measure pannu (latency-a, throughput-a, loss-a). Illana, wrong layer-la time waste aagum.

5Lab Setup

bash — root/sudo vachu run pannu
1sudo ip netns add ns-catalog       # "server" namespace — product-catalog service run aagum idhu
2sudo ip netns add ns-checkout      # "client" namespace — checkout backend, ithuvaa catalog-a call pannum
3sudo ip link add veth-checkout type veth peer name veth-catalog   # virtual cable rendu end
4sudo ip link set veth-checkout netns ns-checkout   # oru end checkout namespace-ku move pannu
5sudo ip link set veth-catalog netns ns-catalog     # marradhu end catalog namespace-ku move pannu
6sudo ip netns exec ns-checkout ip addr add 10.90.1.10/24 dev veth-checkout   # checkout side IP set pannu
7sudo ip netns exec ns-catalog ip addr add 10.90.1.20/24 dev veth-catalog     # catalog side IP set pannu
8sudo ip netns exec ns-checkout ip link set veth-checkout up   # interface UP pannu, illana traffic pogadhu
9sudo ip netns exec ns-catalog ip link set veth-catalog up     # idhuvum UP pannanum
10for ns in ns-checkout ns-catalog; do sudo ip netns exec $ns ip link set lo up; done  # loopback um up pannu, rendu namespace-kkum
11sudo ip netns exec ns-catalog iperf3 -s -B 10.90.1.20 &   # iperf3-a server mode-la start pannu, catalog IP-la bind pannitu — ithu namba throughput test-ku

7Break-Fix #1 — Throughput Drop

🔴 Break Pannalam

tc vachu bandwidth-a artificial-a limit pannuvom — real world-la, oversubscribed virtual NIC, or a slow uplink maadhiri simulate pannuradhu.

bash
1sudo ip netns exec ns-checkout tc qdisc add dev veth-checkout root tbf rate 10mbit burst 32kbit latency 400ms   # tbf = token bucket filter, ithu bandwidth-a exact-a 10 megabits/sec-ku cap pannidum

Paathukalaam (Observe)

bash
1sudo ip netns exec ns-checkout iperf3 -c 10.90.1.20 -t 5   # same test, ippo evlo throughput varudhu nu paaru
    Bitrate  ~9.4 Mbits/sec   (namba baseline-la irundhadhu evlovo, ippo veere level-ku vandhudhu)
2sudo ip netns exec ns-checkout ping -c 5 10.90.1.20   # latency check pannu — ithu affect aagumaanu paaru
    latency almost same-a irukkum, konjo increase mattum (queueing delay because of the shaping)
🔵 Reading the symptom

Ithu dhaan important point — latency (ping RTT) mostly same-a irundhudhu, aana throughput (iperf3 bitrate) dramatically kammi aayidhudhu. Idhu clear signal — bandwidth-oda ceiling problem, not a connectivity or routing problem. Real production-la ithu maadhiri symptom vandha, physical link capacity, oversubscribed virtual NIC, ya ISP-oda throttling nu check pannanum.

🔴 Root Cause

Bandwidth artificial-a (or real-a, hardware/provider level-la) cap pannirundhudhu — link-oda maximum achievable throughput kammi aayidhudhu, aana individual packet round-trip time affect aagalai.

bash — fix
1sudo ip netns exec ns-checkout tc qdisc del dev veth-checkout root   # namba potta bandwidth limit-a remove pannidalam

8Break-Fix #2 — NIC Errors and Drops

🔴 Break Pannalam

Konjo packet loss simulate pannuvom, netem vachu — real-a hardware/driver-la error varradha represent pannudhu.

bash
1sudo ip netns exec ns-checkout tc qdisc add dev veth-checkout root netem loss 10%   # 10% packets randomly drop pannum, simulate panna

Paathukalaam

bash
1sudo ip netns exec ns-checkout ping -c 20 10.90.1.20   # 20 pings anupu, evlo % loss aaguthu nu paaru
    ~10% packet loss   (namba potta rate matching aagudhu)
2sudo ip netns exec ns-checkout nstat -az TcpRetransSegs   # nstat = network statistics tool, TcpRetransSegs = evlo TCP segments retransmit pannirukku nu counter
    TcpRetransSegs   climbing steadily   (loss irundha, retransmission automatic-a increase aagum)
🔵 Reading the symptom

Ping loss % um, TCP retransmit counter um rendும correlate aaguthu — idhu confirm pannuthu, network layer-la real packet loss irukku nu. Production-la, ithu maadhiri irundha, next step — cable, switch port, ya virtual NIC driver-a check pannanum, ethtool -S vachu specific error counters paaru.

bash — NIC-level counters, production-la ippadi paakalam
1ip -s link show eth0   # -s means statistics — RX/TX packets, errors, dropped, overrun ellame kaatum
2ethtool -S eth0 | grep -i err   # ethtool -S = driver-level detailed statistics, "err" grep pannitu error counters mattum paaru
🔴 Root Cause

Network path-la packet loss irundhudhu (namba lab-la artificial-a create pannirukom, real-a hardware/cable/driver issue-a irukkalam), adhunala TCP retransmit pannikittu irundhudhu, adhu throughput-a um affect pannum.

bash — fix (lab cleanup)
1sudo ip netns exec ns-checkout tc qdisc del dev veth-checkout root   # loss simulation remove pannidalam

9Break-Fix #3 — Socket Backlog Overflow

🔴 Break Pannalam

Server-oda accept backlog-a romba chinna-a set pannuvom — production-la, sudden traffic spike-la ithu maadhiri dhaan aagum.

bash — on ns-catalog, tiny backlog vachu oru server
1sudo ip netns exec ns-catalog bash -c "cat > /tmp/tiny_backlog_server.py" <<'EOF'
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('10.90.1.20', 9500))
s.listen(1)     # backlog = 1 mattum — romba chinna, real app-la ithu common mistake
print("listening with backlog=1")
import time
time.sleep(60)  # accept() call pannama vera vela pannikittu irukkura app-a simulate pannudhu
EOF
2sudo ip netns exec ns-catalog python3 /tmp/tiny_backlog_server.py &

Paathukalaam

bash — on ns-checkout, multiple connections rapid-a try pannu
1for i in 1 2 3 4 5; do sudo ip netns exec ns-checkout timeout 2 bash -c "exec 3<>/dev/tcp/10.90.1.20/9500 && echo conn-$i ok" || echo "conn-$i FAILED"; done   # 5 connections quick-a try pannu, evlo success aaguthu nu paaru
    conn-1 ok
    conn-2 FAILED
    conn-3 FAILED
    conn-4 FAILED
    conn-5 FAILED   (backlog queue full aayiduchu, rest ellam refuse aagudhu)
🔵 Reading the symptom

Server process healthy-a run aagudhu, port-um open-a irukku — aana backlog queue romba chinna irundhadhunala, konjo connections mattum accept aagum, mudhindhavanga refuse aagidum. Idhu, production-la sudden traffic spike vandha, "server is up but some requests fail randomly" nu complaint varudhu — exact-a idhe pattern.

🔴 Root Cause

Application-oda listen backlog value romba chinna-a set pannirundhadhu, adhunala high connection rate vandha, kernel queue full aayidhu, extra connections drop aayidum.

bash — fix: cleanup, real fix app config-la backlog increase pannanum
1sudo ip netns exec ns-catalog pkill -f tiny_backlog_server.py   # namba test server-a kill pannidalam
🟦 Best Practice

Production application config-la, listen backlog value, expected peak concurrent connection rate-a base pannu set pannanum — chinna value vachu, sudden traffic-la silent-a connections drop aagum, adhu debug panna romba kashtam because process itself healthy-a dhaan run aagudhu.

10Break-Fix #4 — Ephemeral Port Exhaustion

🔴 Break Pannalam

Client side-la, ephemeral port range-a artificial-a romba chinna-a pannuvom — production-la, romba naala short-lived connections open pannina, ithu maadhiri dhaan symptom varum.

bash — on ns-checkout
1sudo ip netns exec ns-checkout sysctl -w net.ipv4.ip_local_port_range="60000 60005"   # normal range thousands of ports, ippo namba 6 ports mattum kudukurom — exhaustion fast-a varum

Paathukalaam

bash — konjo connections rapid-a open/close pannu
1for i in $(seq 1 15); do sudo ip netns exec ns-checkout curl -s --max-time 1 -o /dev/null http://10.90.1.20:9500/ 2>&1; done; echo done   # 15 quick connections try pannu, chinna port range vachu
2sudo ip netns exec ns-checkout ss -tn state time-wait | wc -l   # evlo TIME-WAIT connections irukku, namba chinna range-a already fill pannirukka nu paaru
    (climbs to near the max of our tiny 6-port range fast)
🔵 Reading the symptom

Project 4-la paatha TIME-WAIT concept, ippo directly connect aaguthu — chinna ephemeral port range vachu, konjo short connections pannina, ellam available ports use pannirum, appuram new connections "cannot assign requested address" nu fail aagum. Production-la, high-traffic client (batch job, ya microservice calling another service romba frequent-a) ithu maadhiri symptom kaatum.

🔴 Root Cause

Ephemeral port range romba chinna-a irundhadhunala (namba intentional-a chinna pannirukom, real-a default range um high-churn scenario-la exhaust aagalam), rapid connection churn vandha, available local ports fast-a run out aayidum.

bash — fix
1sudo ip netns exec ns-checkout sysctl -w net.ipv4.ip_local_port_range="32768 60999"   # normal, wide range-ku reset pannidalam
🟦 Best Practice

Kernel tunable (port range increase pannuradhu) oru mitigation dhaan — real fix, Project 4-la paatha maadhiri, connection reuse/pooling implement pannuradhu, appadi na romba connections rapid-a open/close pannradhu avoid aagum.

11Production Best Practices

🟦 Latency and throughput vera vera

🟦 NIC counters regular-a check pannu

🟦 Backlog sizing production traffic-ku match pannanum

Chinna backlog, healthy process irundhalum silent-a connections drop pannum.

Port range increase panradhu temporary, connection reuse dhaan permanent fix.

13Interview Preparation

ScenarioApp team says network "slow" — eppadi start pannuveenga?

First, latency-a throughput-a nu clarify pannuven — ping vachu RTT check pannuven, iperf3 vachu actual bandwidth measure pannuven. Rendும healthy-a irundha, NIC counters (ip -s link, ethtool -S) paakalam, appuram application-level limits — backlog, ephemeral ports.

Follow-up: "Latency normal, throughput kammi-nu irundha?" — Answer: bandwidth ceiling problem-a irukkum, link capacity, oversubscription, ya throttling check pannanum, routing/firewall problem illa.
ConceptLatency and throughput-oda difference enna?

Latency evlo fast reply varudhu nu measure pannum (round-trip time). Throughput evlo data evlo fast move pannalam nu measure pannum. High latency-um high throughput-um oru link-la irukkalam, ore samayathula.

TroubleshootingHealthy server, aana high load-la konjo connections refuse aaguthu — enna check pannuveenga?

Listen backlog size check pannuven — application romba chinna backlog vachu configure panniruntha, kernel queue full aayi, extra connections silently drop aagum, even though the process itself is completely healthy.
