1The Incident

We support a telecom company's core routing infrastructure. Every core server has two NICs bonded together specifically so that pulling one cable during maintenance should be a non-event — traffic should silently continue over the other link.

"During last night's maintenance window, someone unplugged what they thought was the standby NIC. Instead of failing over instantly like it's supposed to, the server sat in a broken, half-working state for about four minutes before the bond finally noticed and switched over. We need to understand why it took that long."

Bonding looks simple from the outside — "two NICs become one, redundancy happens automatically" — but exactly how quickly and reliably that failover happens depends entirely on a handful of specific, easy-to-misconfigure settings.

🔵 Why this project matters

NIC bonding (also called teaming) is standard practice on any server where network redundancy or throughput aggregation actually matters — core infrastructure, storage servers, hypervisor hosts. A bond that LOOKS configured but doesn't fail over correctly gives you false confidence right up until the moment it matters most.

2Bonding Foundation

2.1 A bond combines multiple physical interfaces into one logical one

🔵 Concept

Linux bonding creates a single virtual interface (conventionally bond0) backed by two or more real "slave" interfaces. Applications and the routing table only ever see bond0 — the bonding driver handles which underlying physical NIC actually carries each frame, according to the selected mode.

2.2 Bonding modes — redundancy vs aggregation are different goals

🔵 Concept

active-backup (mode 1) is the simplest and most common — one slave is active at a time, carrying all traffic; the other sits idle, ready to take over the instant the active one fails. No special switch configuration is required. 802.3ad / LACP (mode 4) actively aggregates multiple links for combined throughput, but requires the connected switch to also be configured for link aggregation and to negotiate via LACP — the two sides exchange LACPDUs to agree they're bonded together. Without switch cooperation, LACP mode simply won't aggregate correctly, no matter how correctly the Linux side is configured.

2.3 miimon — how the bond notices a slave has died

🔵 Concept

miimon sets how often (in milliseconds) the bonding driver polls each slave's link state (via the MII — Media Independent Interface — register) to check if it's still physically up. If miimon is 0 (disabled, unfortunately still the historical default on some distros unless explicitly set), the bonding driver has NO way to detect a dead link on its own — it will keep sending traffic to a slave with no cable plugged in, silently blackholing that share of traffic, until something else notices.

2.4 Failback behavior — primary, updelay, and downdelay

🔵 Concept

When a failed slave comes back, whether the bond switches back to it depends on the primary option (which slave should be preferred whenever it's available) combined with updelay (how long a recovered link must stay stable before being trusted again — avoiding flapping back and forth on a marginal link). Without a configured primary, active-backup mode generally just keeps using whichever slave is currently active, even after the original "preferred" one recovers — which can surprise operators who assumed it would automatically switch back.

4Troubleshooting Method

  • 1. Check bond status directly: cat /proc/net/bonding/bond0 — mode, current active slave, miimon interval
    • ↓
  • 2. If failover was slow or didn't happen: check miimon — is it actually enabled and set to a reasonable interval?
    • ↓
  • 3. If failback behavior is surprising: check the primary and updelay settings
    • ↓
  • 4. If using LACP/802.3ad: confirm the switch side is actually configured for link aggregation — Linux alone cannot make this work unilaterally
    • ↓
  • Test failover deliberately (bring a slave down) rather than assuming it works from configuration alone
🟠 Warning

Never trust that a bond is correctly redundant just because it's configured — always test an actual failover deliberately, in a maintenance window, before you need it to work for real.

5Build a Bonded Interface

Network namespaces don't have real physical NICs, but the bonding driver works on any network device — so we'll bond two veth interfaces inside one namespace to simulate two physical NICs feeding into one logical bond.

bash — run as root/sudo
1sudo ip netns add ns-core           # our core routing server
2sudo ip netns add ns-switch         # represents the upstream switch (or two switches, in a real redundant design)
3sudo ip link add veth-nic1 type veth peer name sw-p1   # simulated physical link 1
4sudo ip link add veth-nic2 type veth peer name sw-p2   # simulated physical link 2
5sudo ip link set veth-nic1 netns ns-core
6sudo ip link set veth-nic2 netns ns-core
7sudo ip link set sw-p1 netns ns-switch
8sudo ip link set sw-p2 netns ns-switch
9sudo ip netns exec ns-switch ip link add br-switch type bridge   # the switch side bridges both ports together, like a real switch would
10sudo ip netns exec ns-switch bash -c "ip link set sw-p1 master br-switch; ip link set sw-p2 master br-switch"
11sudo ip netns exec ns-switch bash -c "ip link set sw-p1 up; ip link set sw-p2 up; ip link set br-switch up; ip link set lo up"
12# now build the bond on ns-core
13sudo ip netns exec ns-core ip link add bond0 type bond mode active-backup miimon 100   # create bond0, active-backup mode, check link state every 100ms
14sudo ip netns exec ns-core ip link set veth-nic1 down   # slaves must be down before being enslaved
15sudo ip netns exec ns-core ip link set veth-nic2 down
16sudo ip netns exec ns-core ip link set veth-nic1 master bond0   # enslave NIC 1 to the bond
17sudo ip netns exec ns-core ip link set veth-nic2 master bond0   # enslave NIC 2 to the bond
18sudo ip netns exec ns-core bash -c "ip link set veth-nic1 up; ip link set veth-nic2 up; ip link set bond0 up; ip link set lo up"
19sudo ip netns exec ns-core ip addr add 10.150.1.10/24 dev bond0   # the IP lives on bond0, never on the individual slaves
TokenMeaning
type bond mode active-backup miimon 100Creates the bond device directly with its mode and link-monitoring interval set at creation time — mode active-backup means only one slave carries traffic at once; miimon 100 means check link state every 100 milliseconds.
ip link set veth-nic1 master bond0Enslaves this interface to the bond — same "master" concept as bridge port attachment from Project 10, just attaching to a bond device instead of a bridge.

7Break-Fix #1 — miimon Disabled, Dead Link Not Detected

🔴 Break It

Rebuild the bond with miimon set to 0 — reproducing a genuinely common historical default and misconfiguration.

bash — on ns-core, tear down and rebuild with miimon disabled
1sudo ip netns exec ns-core ip link set bond0 down
2sudo ip netns exec ns-core ip link delete bond0
3sudo ip netns exec ns-core ip link add bond0 type bond mode active-backup miimon 0   # miimon 0 means link monitoring is OFF entirely
4sudo ip netns exec ns-core bash -c "ip link set veth-nic1 down; ip link set veth-nic2 down; ip link set veth-nic1 master bond0; ip link set veth-nic2 master bond0; ip link set veth-nic1 up; ip link set veth-nic2 up; ip link set bond0 up"
5sudo ip netns exec ns-core ip addr add 10.150.1.10/24 dev bond0

Observe

bash — fail the active link exactly like before
1sudo ip netns exec ns-core cat /proc/net/bonding/bond0 | grep "Currently Active"
    Currently Active Slave: veth-nic1
2sudo ip netns exec ns-core ip link set veth-nic1 down   # simulate the cable pull again
3sleep 1 && sudo ip netns exec ns-core cat /proc/net/bonding/bond0 | grep -A1 "Currently Active"
    Currently Active Slave: veth-nic1   (still shows nic1 as active — the bond has no idea it's down!)
🔵 Reading the symptom

With miimon disabled, the bonding driver has no mechanism at all to notice a slave's link state changed — it will keep considering veth-nic1 the active slave and keep sending traffic to it, even though the link is physically down, until something ELSE (like an actual carrier-detection event from certain drivers, or manual intervention) triggers a change. This is exactly the four-minute delay from our incident — someone eventually noticed the outage and manually intervened, which is a completely different, much slower mechanism than the automatic sub-second failover we saw with miimon properly configured.

🔴 Root Cause

miimon was set to 0, disabling the bonding driver's link-state monitoring entirely, so a dead slave was never automatically detected or failed over from.

bash — fix: rebuild with miimon properly set (100ms is a common, reasonable value)
1sudo ip netns exec ns-core ip link set bond0 down; sudo ip netns exec ns-core ip link delete bond0
2sudo ip netns exec ns-core ip link add bond0 type bond mode active-backup miimon 100
3sudo ip netns exec ns-core bash -c "ip link set veth-nic1 up; ip link set veth-nic1 master bond0; ip link set veth-nic2 master bond0; ip link set bond0 up"
4sudo ip netns exec ns-core ip addr add 10.150.1.10/24 dev bond0
🟦 Production Best Practice

Never deploy a bond without explicitly setting miimon to a sane, non-zero value — treat it as a mandatory setting, not an optional tuning knob, since a bond without it provides zero automatic redundancy despite looking fully configured.

8Break-Fix #2 — No Failback to the Primary Slave

🟠 Scenario

With a healthy miimon-enabled bond, fail the active slave, let it fail over, then bring the ORIGINAL slave back — and see whether the bond switches back to it.

bash — on ns-core, fail nic1 (which should be active after our fix above) and let it fail over
1sudo ip netns exec ns-core ip link set veth-nic1 down
2sleep 1 && sudo ip netns exec ns-core cat /proc/net/bonding/bond0 | grep "Currently Active"
    Currently Active Slave: veth-nic2   (failed over correctly, as expected)

Observe — bring the original NIC back and see what happens

bash
1sudo ip netns exec ns-core ip link set veth-nic1 up   # the "preferred" NIC is physically healthy again
2sleep 1 && sudo ip netns exec ns-core cat /proc/net/bonding/bond0 | grep "Currently Active"
    Currently Active Slave: veth-nic2   (still on nic2 — no automatic failback happened)
🔵 Reading the symptom

This surprises a lot of operators — active-backup mode, without an explicitly configured primary slave, does NOT automatically switch back to the "original" NIC once it recovers. It simply keeps using whichever slave is currently active, since without a stated preference, both slaves are considered equally acceptable. If there's some reason NIC1 is actually preferred (perhaps it has better hardware, or a more direct switch path), you need to say so explicitly.

🔴 Root Cause

The bond had no configured primary slave, so once it failed over to veth-nic2, it had no reason to switch back to veth-nic1 after that link recovered.

bash — fix: rebuild with an explicit primary and a stability delay
1sudo ip netns exec ns-core ip link set bond0 down; sudo ip netns exec ns-core ip link delete bond0
2sudo ip netns exec ns-core ip link add bond0 type bond mode active-backup miimon 100 primary veth-nic1 updelay 200   # primary = prefer nic1 whenever it's available; updelay = wait 200ms after it comes back up before trusting it, to avoid flapping
3sudo ip netns exec ns-core bash -c "ip link set veth-nic1 master bond0; ip link set veth-nic2 master bond0; ip link set bond0 up"
4sudo ip netns exec ns-core ip addr add 10.150.1.10/24 dev bond0
TokenMeaning
primary veth-nic1Explicitly states that veth-nic1 should always be preferred and become active again as soon as it's available and stable.
updelay 200After a slave comes back up, wait 200ms before trusting it as available — protects against a flapping/marginal link causing rapid, disruptive back-and-forth failovers.
🟦 Production Best Practice

Decide deliberately whether failback behavior is wanted for your specific bond, and configure primary explicitly either way — don't leave it to the default and be surprised later. Pair it with a reasonable updelay to avoid flapping on a marginal link.

9Break-Fix #3 — LACP Mode Without a Cooperating Partner

🟠 Scenario

Someone decides to switch the bond to LACP mode for extra throughput, but the connected switch is never configured to match — a very common real-world rollout mistake.

bash — on ns-core, reconfigure the bond for 802.3ad/LACP
1sudo ip netns exec ns-core ip link set bond0 down; sudo ip netns exec ns-core ip link delete bond0
2sudo ip netns exec ns-core ip link add bond0 type bond mode 802.3ad miimon 100   # switch to LACP mode — this REQUIRES a cooperating, correctly configured switch
3sudo ip netns exec ns-core bash -c "ip link set veth-nic1 master bond0; ip link set veth-nic2 master bond0; ip link set bond0 up"
4sudo ip netns exec ns-core ip addr add 10.150.1.10/24 dev bond0

Meanwhile, our lab's "switch" (ns-switch) is still just a plain Linux bridge from Section 5 — it has no idea what LACP is and will never send or respond to LACPDUs.

Observe

bash — check the bond's aggregation status
1sudo ip netns exec ns-core cat /proc/net/bonding/bond0
    802.3ad info
    Aggregator selection policy (ad_select): stable
    bond bond0 has no active aggregator   (neither slave has successfully aggregated — LACP negotiation never completed)
2sudo ip netns exec ns-core ping -c 3 -I bond0 10.150.1.1   # (assume a gateway would live here) — with no active aggregator, traffic has nowhere reliable to go
    (fails or is highly unreliable — with no active aggregator, the bond effectively has no usable path)
🔵 Reading the symptom

"bond bond0 has no active aggregator" is the unambiguous signature of this exact problem — the Linux side is correctly configured for LACP, but without a partner on the other end of the wire that ALSO speaks LACP and agrees to aggregate these specific ports, the bonding driver refuses to consider any slave part of a working aggregate, since 802.3ad's entire safety model depends on both sides actively agreeing. This is completely different from active-backup, which needs zero cooperation from the switch.

🔴 Root Cause

The bond was configured for 802.3ad/LACP mode, but the connected switch (or in this simplified lab, our plain bridge standing in for one) had no matching LACP configuration, so the two sides never successfully negotiated an aggregate.

bash — fix (in this lab): revert to active-backup, which needs no switch cooperation
1sudo ip netns exec ns-core ip link set bond0 down; sudo ip netns exec ns-core ip link delete bond0
2sudo ip netns exec ns-core ip link add bond0 type bond mode active-backup miimon 100 primary veth-nic1
3sudo ip netns exec ns-core bash -c "ip link set veth-nic1 master bond0; ip link set veth-nic2 master bond0; ip link set bond0 up"
4sudo ip netns exec ns-core ip addr add 10.150.1.10/24 dev bond0
🟦 Production Best Practice

Never switch a production bond to LACP/802.3ad mode without first coordinating with the network team to configure matching link aggregation on the actual switch ports — this is fundamentally a two-sided negotiation, and misconfiguring just the server side leaves you with a bond that provides neither redundancy nor throughput benefit.

10Production Best Practices

🟦 Always set miimon explicitly

A bond without link monitoring provides no real automatic redundancy, regardless of how correctly everything else is configured.

🟦 Decide on failback deliberately

Set primary (and a sensible updelay) if you want the bond to prefer a specific slave and switch back to it — don't assume the default behavior matches your expectation.

🟦 LACP needs the switch's cooperation

Never enable 802.3ad mode without coordinating matching switch-side configuration — check /proc/net/bonding/bond0 for "has no active aggregator" as the tell-tale failure sign.

🟦 Test failover for real, in a maintenance window

Configuration alone doesn't prove redundancy — pull a cable (or bring a slave down) deliberately and confirm the behavior matches expectations.

12Interview Preparation

ScenarioA bonded interface didn't fail over when a cable was unplugged. What would you check?

First, whether miimon is enabled and set to a reasonable interval — without it, the bonding driver has no way to detect a dead link on its own. I'd check cat /proc/net/bonding/bond0 to see the configured miimon value and each slave's reported MII status.

Interviewer follow-up: "What if miimon is correctly set, but it still didn't fail back after the cable was reconnected?" — Answer: that's actually expected default behavior in active-backup mode without a configured primary slave — the bond has no reason to prefer one slave over the other once it's already failed over, unless you explicitly tell it to with the primary option.
ConceptWhat's the difference between active-backup and LACP bonding modes?

Active-backup uses only one slave at a time for traffic, with the other on standby, and requires no special configuration on the connected switch. LACP (802.3ad) actively aggregates multiple links for combined throughput, but requires the switch to also be configured for link aggregation and to negotiate via LACP — without that switch-side cooperation, LACP mode won't successfully aggregate at all.

TroubleshootingYou configured a bond in 802.3ad mode but it seems to provide no benefit. What would you check?

I'd check cat /proc/net/bonding/bond0 for the aggregator status — "has no active aggregator" specifically means the two sides never successfully negotiated LACP. That almost always means the connected switch ports aren't configured for matching link aggregation, since 802.3ad requires active cooperation from both ends, unlike active-backup.
